# DRAM row locality and bank parallelism: reusable methods

## Scope and evidence boundary

This note concerns the DRAM row buffer, bank/bank-group scheduling, channel mapping, and experiments that can distinguish locality from parallelism. It does not infer a DRAM bottleneck from Strata's current pool wall time or logical byte visits. The earlier Zen 3 counter-free reference covers general CPU/DRAM attribution; the store-forwarding note covers CPU pipeline false aliases at equal 4 KiB offsets. Neither establishes the physical address-to-bank mapping or a DRAM row conflict in this application.

## Mechanism: reuse versus independent banks

A DRAM bank has a row buffer holding one open row. A column access to that row is a row hit. A request to a closed bank must activate a row (miss); a request to another row in an open bank requires precharge then activation (conflict). These are different service cases: conflicts include the close/reopen sequence and can cost more than a cold miss. The controller may keep a row open, close it, or reorder queued requests; software sees none of these decisions directly. [Moscibroda and Mutlu, IEEE S&P 2007](https://static.usenix.org/event/sec07/tech/full_papers/moscibroda/moscibroda_html/index.html)

Bank parallelism hides activation/precharge and other bank service intervals when enough independent requests are in flight. It does not make a dependency-chained random pointer walk fast: that walk has low memory-level parallelism (MLP), so each miss waits on the previous address. Conversely, a stream can sustain high bandwidth with row hits and bursts even if only a subset of banks is active at once. A workload with many independent streams may expose more banks and channels, but can lose locality if it interleaves accesses among different rows of the same bank. It can also add queue contention, refresh interference, and cache/TLB traffic. Thus “more banks touched” and “more useful throughput” are separate hypotheses.

DDR4 adds bank groups. The device timing rules permit different command spacing depending on same/different bank group (for example tRRD_S/L for ACTIVATE and tCCD_S/L for column commands); tFAW also limits activation rate. These timings explain why spreading commands may help an activation-bound schedule, but they do not reveal how a CPU maps virtual or physical address bits to groups. [Samsung DDR4 Device Operations, rev. 1.1, timing sections](https://image.semiconductor.samsung.com/resources/data-sheet/DDR4_Device_Operations_Rev11_Oct_14-0.pdf)

## Address mapping is platform-specific

Channel, rank, bank-group, bank, row and column are selected from physical-address information by the memory controller and DIMM organization. Some systems XOR/hash address bits; the mapping may change across CPU generation, firmware, channel population, DIMM rank/organization and memory configuration. DRAMA reverse-engineered mappings on several then-current systems using physical bus probing or timing; it demonstrates that the mapping is discoverable on a specific machine, not that its equations transfer to Ryzen 5000. Its work also distinguishes same-bank/same-row hits from same-bank/different-row conflicts. [Pessl et al., USENIX Security 2016](https://www.usenix.org/system/files/conference/usenixsecurity16/sec16_paper_pessl.pdf)

ZenHammer recovered and physically validated configuration-specific DDR4 address functions on a Zen 3 Ryzen 5 5600G system, including a system-specific 768 MiB PCI-hole offset. This establishes that a Zen 3 mapping can be recovered, not that it transfers: its tested CPU, motherboard, DIMM geometry/rank and physical-address offset do not establish the active mapping of a Ryzen 5 5600X system. [Jattke et al., USENIX Security 2024](https://www.usenix.org/system/files/usenixsecurity24-jattke.pdf) Do not call a virtual stride a bank conflict or reuse Intel/Haswell mapping bits on Zen 3. AMD's public EPYC 7003 guide does not publish a consumer AM4 mapping. [AMD Software Optimization Guide for EPYC 7003, 56665 rev. 3.0](https://docs.amd.com/v/u/en-US/56665)

Software-controllable factors are the logical order/stride of accesses, number of independent streams, reuse distance, working-set size, and (within allocator/OS facilities) virtual allocation, first-touch and placement. They are only indirect controls on physical bank/channel placement. Page size changes translation reach and can make low physical-offset bits known within a large page, but does not select a bank or guarantee row locality. Huge pages can also alter TLB behavior, physical contiguity and placement, so treat backing as a confound; do not request huge pages or change placement as a first test.

## Workload signatures and tradeoffs

| Access pattern | Expected DRAM tendency | Competing explanation / caveat |
|---|---|---|
| Long contiguous reads | Adjacent cache lines often map to columns in the open row until a row boundary; bursts amortize activation. Multiple channels/banks may still be interleaved by controller. | CPU caches can satisfy much of the stream; prefetching, cache-line width, NUMA placement and bandwidth limits can dominate. A large benchmark is not proof each byte reached DRAM. |
| Latency-sensitive random expert-like accesses | If requests repeatedly target different rows of one bank, conflicts can serialize; if distributed across banks and enough misses overlap, bank-level parallelism can hide part of the latency. | Random lookup may be cache/TLB/branch limited, may have too little MLP, or may hit LLC. A shuffled index does not imply random physical bank selection. |
| Several independent streams | More independent misses can raise MLP and let controller schedule across banks/channels; within-stream row reuse can remain if each stream walks contiguous slabs. | Interleaving or stride may map streams to one bank or separate rows and destroy row hits; more outstanding traffic can increase queueing and contention. |

The DDR4 timing constraints mean a deliberate stride that alternates rows in one bank can be worse than contiguous row reuse, even if it appears to “spread” requests. If it actually selects independent banks, it may improve overlap for a latency-limited pattern, but only up to controller, channel, activation-rate, MLP and CPU limits. Extra gathers, padding, duplicate copies, or larger metadata may cost more traffic and cache capacity than saved row activations. A good layout can preserve contiguous access within each stream and interleave independent streams at a coarse grain; which granularity helps is empirical and mapping-dependent.

Cloudflare's original EPYC 7713 server measurement compared two 8-channel configurations, each with eight 32 GB DDR4-3200 Samsung RDIMMs (2Rx4 versus 2Rx8). Their MLC all-read result differed by 0.21%; the largest stated difference was 3.88% for lmbench write. This is evidence for that configuration, not Zen 3 or bank mapping. [Cloudflare, “DDR4 memory organization and how it affects memory bandwidth”](https://blog.cloudflare.com/ddr4-memory-organization-and-how-it-affects-memory-bandwidth/)

## Keep distinct mechanisms separate

* **DRAM bank/row conflicts** occur after a cache miss reaches the memory controller and depend on physical channel/bank/row mapping and open-row state.
* **CPU 4 KiB store/load false aliases** are an execution-pipeline dependency while older stores and loads are in flight; addresses can have equal low 12 bits but refer to different physical locations. The prior Zen 3 store-forwarding report covers this separately. It is not a DRAM row collision and can occur even when accesses hit in cache.
* **Cache-set conflicts** are cache indexing/associativity effects. Two cache lines can evict each other in L1/L2/LLC without reaching DRAM. Changing virtual or physical offsets can alter cache set and DRAM bank selection together, so a timing delta alone cannot identify either.

Do not use a 4 KiB stride, cache-line stride, page coloring, or huge-page allocation as a stand-in for a known bank selector. A mapping claim needs platform-specific evidence; timing-only conflicts can establish a repeatable address-class effect, not the exact controller hash unless validated against independent mapping evidence.

## Discriminating designs (proposals only)

Use these only after actual useful CPU critical-path work and DRAM-relevant misses are established by compatible attribution. These are designs, not local results; no local experiment, hardware inspection or process check was performed for this report.

1. **First separate cache-resident from memory-resident access.** Compare a small hot footprint with a footprint larger than LLC, keeping access count, arithmetic, dependency shape and number of streams fixed. Include sequential and randomized orders; report latency per dependent access and throughput for independent accesses separately. If the candidate effect disappears when data is hot and appears only in the large footprint, that supports a memory-path contribution but does not distinguish row conflicts from bandwidth, TLB or controller queueing. If both arms move similarly, DRAM row policy is less likely to explain the effect.
2. **Contrast reuse and bank-parallel opportunities without assuming mapping.** For each fixed footprint, compare (a) contiguous within-slab reuse, (b) many dependent random accesses, and (c) several independent streams, sweeping a small declared stream count. Hold total useful bytes, reads/writes, cache-line footprint and CPU work constant; distinguish dependent latency from aggregate throughput.
3. **Test row locality only with a validated address class.** On a machine where a lawful, platform-specific mapping is already available, choose two disjoint sets with same-bank/same-row addresses versus same-bank/different-row addresses, plus addresses mapped to different banks. Randomize test order, verify data correctness and vary the number of outstanding independent requests. Without mapping evidence, a timing classifier can screen candidate conflict pairs but requires cache-flush/eviction care, randomized controls and repeated separation; label it “address-class timing,” not a proven row-hit counter.
4. **Check cache-set and translation confounds.** Counterbalance offsets that change cache index bits, test hot-cache behavior, and keep page count/working-set size comparable. Where page size is already available without system changes, record actual backing and treat it as a separate factor. Do not infer bank selection from huge-page backing or virtual addresses. A matched result that tracks a candidate bank class after cache-set and TLB controls is stronger, but still needs target-specific corroboration.

Keep per-process samples, placement/first-touch, thread affinity, memory channels and DIMM configuration, page backing, actual bytes, dependent/independent access mode and working-set/cache state. A single-thread dependent chase answers latency; streaming or multi-stream throughput answers a different question. Never add requested logical byte counts and call the sum physical DRAM traffic. DRAM bandwidth, row-hit rate, bank utilization and controller queue depth remain unknown without a supported counter or validated mapping/protocol measurement.

## Conditional relevance to Strata

Current Strata pool wall time and logical byte visits do not establish useful CPU critical-path work, DRAM traffic, row conflicts, MLP insufficiency, or DRAM saturation. Follow-up `schedulable_now: false`: require source/call-path evidence and useful CPU critical-path attribution for memory-latency work, compatible target-host placement evidence and a validated address class; bound cache/translation alternatives first. Any later layout proposal must compare added bytes, packing/gather cost, cache footprint and decode behavior against the measured prefill path; prefill and decode remain independent decisions. No host settings, page policy, memory timings, runtime flags or application layouts are changed or recommended by this collection.
