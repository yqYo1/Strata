## Exact tile and head work

The kernel fixes `Dim=256`, 12 real Q heads, 2 KV heads, 32 cells per tile, a 128-work-item group, and required SIMD16 subgroups (source lines 24, 177–210). Each workgroup owns one query and one KV head; it stages 16 head rows, with 12 real and four padded rows. Four subgroups produce QK for eight-head blocks, each covering one 16-cell half. Four matrix accumulator fragments per subgroup cover the PV output dimensions. The installed-path source template called `prefix_batch_impl<33,false,false,true,true,true,true,false>` in the bounded projection maps to cached Q, vector-four K and V gather, subgroup softmax, ordered exponentials, no diagnostic capture. The current source allocates 20,036 requested local bytes for that cache-Q variant, including scores, online state, row IDs and padded probability storage (lines 42–49, 169–175). This number is an explicit payload estimate, not occupancy or usable-device-capacity evidence.

For selected width `w`, the source loop runs `ceil(w/32)` tile recurrences. At the stated cap `w=2,051`, that is 65 tiles: 2,080 cell slots, only 29 padding slots (1.414%). Each tile issues, by source geometry, two KV-head groups × QK and PV × 16 padded head rows × 32 cells × 256 dimensions × 2 FLOPs/FMA = 1,048,576 nominal matrix FLOPs. Per query at cap this is 68,157,440 padded-issued FLOPs; real-head logical work is 50,405,376 FLOPs. Across 8,192 cap-width queries and 12 layers the source model gives 6.700 TFLOPs issued versus 4.955 TFLOPs logical. These count matrix work only: they omit gather/address, scale, exp, reductions, normalizer updates, masking, and stores. Partial tiles are still matrix-issued at the padded extent; actual compiler instruction issue is not measured.

The local streaming buffer holds one 32×256 BF16 tile (16 KiB) and is reused first for K then for V. Each tile decodes cell IDs, page-table mapping, physical row and per-row validity into 32 local row slots; invalid entries are zero-filled during the K/V copy (lines 232–282, 377–402). K and V each require a global gather of `32×256×2` bytes per KV head group. Across two KV groups, two tensors, and 12 layers, the ideal requested packed payload model is `w×2×2×256×2×12` bytes per query. At 2,051 cells this is 4,200,448 bytes per query per layer, or 412,920,840,192 bytes (about 412.9 decimal GB) for 8,192 queries and 12 layers. It is repeated per query even when selected cells overlap other queries; it is requested source payload, not measured physical VRAM traffic. Cache residency, transaction amplification, row alignment, and overlap are unknown.

For an independent 131,072-live-cell incidence bound, each selected incidence represents 2,048 requested K/V bytes per layer and 24,576 real logical QK/PV FLOPs; at full tile alignment the padded issued model is 32,768 FLOPs per cell. Thus 131,072 incidences correspond to 268,435,456 bytes (256 MiB) requested per layer, 3.22 decimal GB if repeated across all 12 layers, 3.22 GF logical FLOPs per layer, and 4.295 GF padded issued FLOPs per layer. If “131,072 live cells” instead means total across all layers, use the one-layer figures without multiplying by 12. This is a capacity/work-count translation, not a saturation point or prediction of service time.

## Softmax, barriers, and observed service

After QK, each SIMD16 subgroup owns two head rows. Lanes cover cells `lane` and `lane+16`; a subgroup max reduction and broadcast establish the new tile maximum. The `OrderedExp` branch computes 32 base-2 exponentials in parallel, then all lanes execute 32 uniform `select_from_group` exchanges while lane zero adds probabilities in ascending cell order. Online state then applies `fma(old_norm, exp2(old_max-new_max), tile_sum)`; BF16 probability conversion follows the FP32 sum (lines 302–349). This preserves the serial cell-add order for the tile sum, while maximum reduction, exponent approximation and cross-tile online recurrence still require their own numerical contract. Padded heads are participants in matrix and softmax collectives, so they cannot be removed casually.

At source level, the cached-query setup has one workgroup local barrier after Q staging. Each tile then has five local barriers: after row-ID publication; after K staging; after QK score production; after V/probability staging before PV; and after PV before overwriting/reusing storage (lines 221–230, 247–249, 279–301, 403–421). These are workgroup synchronization points, not five host/API barrier commands. The pinned profile projection itself does not encode a device identity; the nominal B580 reference below is applicable only if Main confirms that device for the captured run. The profile’s `barrier_or_other_L0` reports 16 tiny service entries across a profiled 128K request, and cannot count or time these in-kernel barriers.

The projection records 384 `qsa_prefix` events and 30.490s summed device-event service for a profiled 128K request (about 79.4ms/event), with a second profiled request at 30.450s. At 32K the corresponding projection has 96 events and 6.834s. These are nonexclusive profiler-observed device service sums inside whole controlled requests, not clean kernel-only wall time, a critical path, arithmetic utilization, wire bytes, DRAM bandwidth, or proof of physical saturation. The projection explicitly leaves hardware arithmetic/VRAM/PCIe ceilings and full critical path unknown. Intel lists B580 Xe2 graphics bandwidth as 456 GB/s ([Intel product specifications](https://www.intel.com/content/www/us/en/products/sku/241598/intel-arc-b580-graphics/specifications.html)); dividing the requested 412.9 GB projection by that nominal peak gives a 0.906-second idealized transfer floor if every byte had to reach VRAM. It does not imply that these bytes do reach VRAM or that the kernel is bandwidth-bound. Similarly, 256 MiB / 456 GB/s is 0.588 ms per layer for the 131,072-incidence case. No matching arithmetic peak for the actual BF16 mixed-matrix instruction path is established here, so an arithmetic roofline ratio would be invented.

## Mechanism comparison and next controlled unit

Three credible mechanisms have distinct resource targets and counterevidence:

1. **Increase cross-query K/V reuse.** The repeated per-query gather model offers a large possible byte reduction if adjacent queries reuse selected rows. Prior retained research on sparse cross-query reuse explicitly treats union blocks, ordering and inverse schedules as open costs; the present source still performs row decode and K/V copy for each workgroup. Reuse adds selector-union/index storage, irregular ownership, and potentially more work or latency. Its prerequisite is measured selector overlap at the real prefill callsite plus an exact output/causal mapping; byte counts alone do not establish a win.
2. **Change matrix workgroup geometry.** WG64 and WG256 variants are documented in the supplied index as passing bounded numerical/component gates but slower on all three tested component shapes/processes; both were rejected in favor of WG128. That is direct counterevidence to “more/fewer workers automatically helps,” while not identifying the cause (register pressure, occupancy, or scheduling remain unmeasured). A larger tile can reduce recurrence count but may add padding, SLM and live state; at cap 32-cell padding is already just 1.4%.
3. **Separate K and V SLM tiles to gather both before their consumers (proposed).** This does not reduce global bytes; it targets serialization between K gather→QK→softmax and V gather→PV. The coherent unit is an additional 16 KiB K/V buffer, simultaneous/cooperative K and V gathers, and explicit consumer barriers, with all arithmetic, row mapping, vector width, cached-Q and ordered sum held fixed. For the current cached-Q payload, requested local storage rises from 20,036 to approximately 36,420 bytes if query storage remains aliased as source currently does; if it must become non-aliased, budget another 8,192 bytes (44,608 total). This remains below no verified residency threshold: device capacity, compiler allocation, bank behavior, occupancy and spills need exact-kernel admission/codegen evidence. Extra simultaneous traffic may contend for cache/memory issue slots, and a single workgroup may not expose useful overlap; the proposal is latency-oriented, not a capacity or bandwidth reduction.

For that third unit, compare only the isolated two-buffer variant against its exact source-identical baseline first; do not combine it with a tile-size or head-geometry change. If it passes numerical/state and physical-context bounds plus exact resource admission and has consistent component evidence, separately test the next smallest option (for example, existing query-cache or vector-four paths as fixed-factor comparisons) and only then their combination. Numerical risks are altered barrier placement, K/V buffer alias/lifetime, out-of-range/page-invalid zeroing, odd/tail rows, padded-head state, and unintended FP32/BF16 conversion movement. Proposed implementation provenance is new Strata-authored code based solely on MIT-licensed Strata source and official SYCL/Intel API documentation; no third-party kernel code is proposed. The SYCL standard defines local accessors and subgroup collective semantics, but not Intel matrix lowering or performance ([Khronos SYCL 2020 specification](https://registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html)).

## Scope readiness

This source audit does not qualify code or a speed claim. The two-buffer unit is **not schedulable now** unless Main first closes its active direct-versus-prefix comparison and confirms a current source-frozen QSA candidate, exact selected workload, numerical/state oracle, hardware/compiler identity, and a component timing plan. Then it is a substantive bounded next comparison: exact named-kernel resource admission; unchanged Q/output/state across empty, tail, invalid-page and physical-262144 cases; one isolated A/B; and only if that passes, separate independent comparisons before combinations. The current profile is useful service attribution, not measured saturation. No adoption or speed assertion follows from this report.
