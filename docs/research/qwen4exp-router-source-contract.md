# Qwen4Exp production router source crosswalk

This is a source-only retrieval note for a future router arithmetic or dispatch decision. Target identity is the previously bounded GGUF header: `qwen4exp`, E=512, K=10. It does not establish that either framework loads that GGUF. Collection report: SHA256 `0f22baea26491266d6da3649a170de35f052c293769bd003ee73fda0d29699b5`. Local source revision: `00de0f2f4a806f6f8ccce6bb464b58f82373b321`; the review digest lists the six local pins actually rechecked.

**SGLang, commit `73bf84e90f1cc14ccf65de37b57f4d3d8653ea85`.** Qwen4Exp decoder layers extend Qwen3.5; Qwen3.5 recognizes `qwen4_exp_text` as MoE and creates `Qwen2MoeSparseMoeBlock`. Its gate is a bias-free `ReplicatedLinear`; TopK takes `num_experts_per_tok` and `norm_topk_prob`. On XPU, the 512/10 shape predicts `forward_xpu` selecting the torch-native branch, then `fused_topk_torch_native`. Its no-bias wrapper casts logits to FP32 before softmax, uses `torch.topk`, and, when renormalizing, divides by an FP32 sum plus 1e-20. This wrapper does not establish stable tie ordering or the compiled/PyTorch reduction details. Qwen4Exp also has a CUDA-only one-row BF16 eager decode bypass through `qwen4_decode_moe`; it is absent on XPU.

**vLLM, commit `34b495a4d982a0c7f29b0c77021ed751dd2ebb4a`.** The package initializer rejects XPU/TPU. CUDA/ROCm model code defines `Qwen4ExpSparseMoeBlock(Qwen3NextSparseMoeBlock)`; the base wires GateLinear to FusedMoEFactory. The decoder can choose `Qwen4ExpMegaMoeBlock` for a configured native MegaMoE backend. A standard FusedTopKRouter allocates FP32 weights and dispatches to `ops.topk_softmax`, except eligible ROCm AITER launches; the exact binary kernel, tie rule and accumulation are unresolved without a concrete config. GateLinear's generic fallback is `ReplicatedLinear` with conditional input/output casts. The `F.linear(x.float(), weight)` call belongs to specialized helper fallback code, so do not infer a universal FP32 producer from it.

Local Strata source comparison: generic router uses FP64 exponentials and full-expert sum, FP32 probability storage and a 2^-14 selected-sum floor. Native router uses FP32 exponentials and reductions, the same floor, and lower expert ID for computed ties; finite inputs are assumed, not validated. The two sources therefore do not establish a matching Qwen4Exp production contract. In particular, FP32 logits [0,-1e-8] remain distinct while stored FP32 softmax probabilities can tie.
