# GDN recurrent decode fusion and speculative verification

**Retrieval synopsis.** For ordinary one-row decode, the most coherent GPU design is a head/state-tile recurrent kernel: load a state tile once, keep it live while applying Q/K normalization, gate and delta updates, emit the per-row output, then store the new state. For four-position verification, fusion alone does not remove recurrence order: each row consumes the prior row's state. The main choice is between one sequential state-resident kernel that retains intermediate checkpoints, and a more parallel short-sequence recurrence/scan with additional temporaries and a changed reduction schedule. The public engines illustrate both opportunities and hazards: FLA exposes in-kernel gate/norm switches; vLLM has packed single-row and specialized MTP routes; SGLang has avoided materializing intermediate GDN QKV in verification and has explicit no-convolution-state-write fixes. A useful Xe2 transfer is to fuse adjacent scalar/vector work around a state tile and amortize dispatch across verifier rows while preserving FP32 recurrence. No B570 performance result follows from this research.

## Two execution strategies

### 1. Single-row packed recurrence, extended only as far as needed

The Gated Delta Rule update is sequential in token position: decay old state, read with the query, form the key/value prediction error, apply beta, rank-one update state, and produce output. The original GDN paper presents parallel algorithms for training, but autoregressive decode has a known incoming state and only one new row; its work is a small dense state update rather than a sequence-wide scan. [Gated Delta Networks, ICLR 2025](https://openreview.net/pdf?id=r8H7xhYPwz).

FLA's official `fla/ops/gated_delta_rule/fused_recurrent.py` provides a useful baseline pattern. Its Triton program maps work over sequence/head/value tiles, carries a state tile in the kernel, loops over T, and optionally fuses Q/K L2 normalization and raw-gate activation (`use_qk_l2norm_in_kernel`, `use_gate_in_kernel`, `use_beta_sigmoid_in_kernel`). It returns FP32 final state when requested. The API separates recurrence from upstream projections; these switches do not fuse QKV GEMM or convolution. The file's documented state shape is `[N, HV, K, V]`, with default K-major layout and optional V-first. This source is pinned to `b9afc14`, the abbreviated FLA revision identified in issue #1096. FLA's repository is Apache-2.0 (`LICENSE`). [FLA fused recurrent implementation at `b9afc14`](https://github.com/fla-org/flash-linear-attention/blob/b9afc14/fla/ops/gated_delta_rule/fused_recurrent.py), [FLA issue #1096](https://github.com/fla-org/flash-linear-attention/issues/1096), [FLA license](https://github.com/fla-org/flash-linear-attention/blob/main/LICENSE).

vLLM release notes distinguish a packed-recurrent pure-decode route from speculative verification and report a fused GDN MTP route for Qwen head ratios (#52539); another release entry names a fused post-convolution MTP kernel (#51674). The current `main` source and release notes were checked 2026-11-04, but those two feature PRs' exact merge revisions were not resolved here. This is a concrete specialization pattern: share dispatch and post-convolution outputs with a verifier-specific kernel, rather than forcing the single-row kernel to handle all shapes. The issue record for recent vLLM source describes three distinct production kernels by verifier width (packed single-row; CUDA fused decode-MTP through eight state positions; Triton recurrent update above that threshold), and notes different FP32 reduction trees. It is a user issue/source report, not a maintainer guarantee; pin current upstream before relying on its threshold. [vLLM releases](https://github.com/vllm-project/vllm/releases), [reported route split and numerical differences](https://github.com/vllm-project/vllm/issues/61738). A packed path avoids materializing Q, K, V and gate intermediates for one row; this is a strong small-batch idea because launch and scratch overhead can dominate a short recurrence. But it is not proof that one-row packing extends efficiently to four rows: each speculative row's output and state depends on the previous row. Keeping one workgroup's state in registers across four serial updates can save state rereads and launches, but lengthens live ranges and may lower occupancy or spill on Xe2. A width-4 kernel needs enough independent head/value tiles to expose parallelism even while each tile serializes its four token steps.

### 2. Batched verifier rows with transaction-aware state handling

A 4-position verifier can share kernel setup and schedule many independent request/head tiles, but cannot treat the four GDN rows as independent GEMM rows. There are two reasonable sub-strategies:

* **Sequential tile loop:** each workgroup loads one incoming `[K,V]` state tile, executes four ordered recurrence updates, computes all four outputs, and writes final state plus the intermediate states needed for acceptance. This is the closest extension of packed decode. It minimizes repeated state loads and kernel dispatches, but the checkpoint policy is central: rejection may accept any prefix length, including zero through four. To commit the correct prefix state without replay, the verifier must preserve a state version for each possible accepted boundary (or enough deltas to reconstruct it). If only final state is retained, the engine must restore the input checkpoint and replay the accepted prefix after sampling, adding another pass and synchronization.
* **Short scan / transformed recurrence:** compose the four state transformations or use an associative/parallel formulation to increase row parallelism. This can reduce serial dependency depth but adds temporary state/coefficient traffic, composition arithmetic, and a numerically different order. It is attractive only if state tiles are too small to use the GPU efficiently in the sequential scheme. The existing prefill WY/chunk algorithm is not automatically a decode solution: its setup and temporary representation may exceed four steps' work.

The transaction cost scales with state size. If each request-layer state contains `HV*K*V` FP32 values, one full state snapshot is `4*HV*K*V` bytes; retaining all four post-row checkpoints costs roughly four such state copies per active request and GDN layer, plus allocator/metadata cost. A tiled kernel may write checkpoints as it goes, but still moves equivalent payload. A copy-on-write pointer swap is insufficient when state is dense and each tile is mutated. Alternatives to measure are: full per-row checkpoint writes; save only the original state and replay accepted rows; or store per-row update vectors/readouts and reconstruct the accepted state. The last option trades snapshot bandwidth for extra arithmetic and storage and needs exact derivation. Include convolution history separately: a fused causal-convolution update must not mutate persistent history speculatively unless it also has accepted-prefix snapshots/rollback. SGLang release history contains a fix explicitly titled “Don't write conv state from the fused KDA verify kernel” (#39524), a concrete warning against stateful fusion without a transaction contract. [SGLang releases](https://github.com/sgl-project/sglang/releases).

SGLang PR #33778 is more specific than its title: merged 2026-09-22 at `9fdb717`; it lets compatible target-verification kernels consume strided Q/K/V views from the already packed causal-convolution output, avoiding a QKV split/copy launch per GDN layer. Its route capability flag preserves contiguous materialization for consumers such as prefill, FlashInfer and CuTeDSL. Reported matched H200 traces show 24 split launches removed and a 1.129% graph-span reduction for one workload; this is not Xe2 evidence. The PR says recurrence math, state updates and sampling are unchanged, so it is a data-movement boundary optimization rather than deeper projection/recurrent fusion. [SGLang PR #33778, merged commit `9fdb717`](https://github.com/sgl-project/sglang/pull/33778), [release list including the later conv-state fix #39524](https://github.com/sgl-project/sglang/releases). Keep this distinct from FLA's in-recurrence gate/norm switches.

## What transfers to Xe2, and what does not

Intel lists B570 as Xe2 with 144 XMX engines, 144 vector engines, 10 GB GDDR6 and 380 GB/s rated memory bandwidth. Those are ceilings/specifications, not measurements of recurrent decode. [Intel Arc B570 specifications](https://www.intel.com/content/www/us/en/products/sku/241676/intel-arc-b570-graphics/specifications.html). Intel's GPU optimization guide describes per-thread GRF and Xe-core shared L1/SLM; it supports the usual trade-off between keeping recurrent tiles near the arithmetic and limiting register pressure, but the cited architecture breakdown is data-center Xe and should not be treated as a B570 occupancy table. [Intel Xe GPU architecture guide](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2025-2/intel-xe-gpu-architecture.html).

Transferable candidates are methodological:

1. Fuse gate activation, sigmoid/softplus, Q/K normalization and scalar elementwise operations into the recurrence consumer when the exact arithmetic boundaries match. Keep the dense projections separate unless the matrix kernel can hand off the needed values without a costly layout conversion or excessive register lifetime. For small batch, an intermediate write/read and a kernel launch can cost more than the scalar math; conversely, fusing all projections can inflate registers, duplicate work, or break an efficient matrix path.
2. Map work by state tile/head and expose independent heads, value tiles, and requests as the grid. Preserve a contiguous dimension for coalesced state accesses. Benchmark K-major versus V-major layouts for the actual recurrent read/update pattern; FLA's selectable layout shows this is a meaningful parameter, not a universal winner.
3. Treat 4-row verification as both a recurrence and a transaction. Fuse ordered row updates, produce per-row outputs, and explicitly select accepted-prefix state. Consider a second replay pass only if it is cheaper than writing every state checkpoint. Run 1-row and 4-row dispatches as separate specializations under an explicit runtime policy; do not mutate process environment after SYCL initialization or couple this choice to prefill.

The Intel-specific counterexample is current vLLM-XPU GDN. The official vLLM-XPU-kernels v0.1.16 release (2026-10-16, tag resolves to abbreviated commit `8b95ea6`) lists a fix for ragged speculative-token traversal (#600), while the earlier public issue #510 documents that a SYCL GDN entrypoint rejected mixed speculative and non-spec batches. These show that fused GPU-local execution can fail at metadata/raggedness boundaries even if a fixed-width component kernel is correct. Another issue describes padded graph inputs reaching a GDN wrapper with inconsistent `num_actual_tokens`; it is an issue report, not proof of current-release behavior. The XPU kernels repository declares Apache-2.0. [vLLM-XPU-kernels v0.1.16 release](https://github.com/vllm-project/vllm-xpu-kernels/releases/tag/v0.1.16), [issue #510](https://github.com/vllm-project/vllm-xpu-kernels/issues/510), [issue #320](https://github.com/vllm-project/vllm-xpu-kernels/issues/320), [repository license](https://github.com/vllm-project/vllm-xpu-kernels/blob/main/LICENSE).

## Precision and correctness traps

State storage dtype is not the only precision boundary. FLA's API allocates output from `v` but creates optional final state in FP32. For low-precision activations, gates and beta may be produced in one dtype while recurrence accumulation and state remain FP32. vLLM/SGLang have a documented bug report where packed decode rounded `sigmoid(beta)` through BF16 then converted it back to FP32; the report attributes context-dependent recurrent drift to that discarded mantissa. vLLM PR #53877 is titled “Keep packed GDN decode beta in FP32,” merged 2026-08-30 at `56058fd`. This is evidence to retain FP32 beta/gate intermediates where required; it is not evidence that the state itself must always be FP32 or that every backend shares identical behavior. [SGLang issue #38975 and linked vLLM fix](https://github.com/sgl-project/sglang/issues/38975), [vLLM PR #53877](https://github.com/vllm-project/vllm/pull/53877).

A second trap is row alignment. vLLM PR #51812 fixed a mixed-batch path that gathered QKV by speculative token indices but passed unsorted `a`/`b` gates to the recurrent kernel. The maintainer report says the recurrence consumed the first Tspec gate rows; short experiments saw log-prob drift even when greedy IDs matched. This is a strong reason to validate gathered gate, beta, Q/K/V and state-slot arrays under non-spec rows before spec rows, ragged counts, and padding. PR merged 2026-08-11 as `5af7c8d`. [vLLM PR #51812](https://github.com/vllm-project/vllm/pull/51812).

Further gates: compare every speculative row's output to a serial reference; verify acceptance 0/1/2/3/4 and rejection-tail behavior; ensure rejected rows do not leave state or convolution-history writes; test batch 1 and mixed batch, non-power-of-two row counts, padded graph capture, and restore/resume at a recurrent-cache boundary. FP32 accumulation does not erase changed reduction order, fast-math sigmoid/exp, normalization epsilon, QK scaling, or rounding of projection outputs. Compare the serving framework's actual dtype and operator contract, not a higher-precision oracle as the sole adoption criterion. The local prior `gdn_runtime_contract_review` already notes runtime pool dtype was unobserved; this report does not resolve it.

## Scoped future comparison

If Main selects a GDN decode experiment after its current work, freeze an exact production source/build and compare the existing path against two source-pinned variants: (A) single-row packed state-tile kernel, and (B) four ordered rows with either checkpoint writes or restore-plus-replay. Keep prefill untouched. First run a source/host metadata contract for ragged, mixed, padded and accepted-prefix cases; then bounded numerical checks against a serial FP32-state reference and target-framework contract. Measure clean 1-row and 4-row kernel batches plus end-to-end decode separately, retaining launch count, state bytes read/written, snapshot/replay bytes, GRF/spills, occupancy/resource metadata, and client-visible latency. Measure with state already resident and with the actual state cache path; do not call completion-wait CPU saturation. Include long-context repeated decode because beta rounding and state drift can accumulate. No B570 gain should be claimed without this matched evidence.
