# Zen 3 non-temporal stores for CPU output buffers

**Retrieval synopsis:** Compare ordinary cached stores with AVX2 non-temporal stores for a large, write-once CPU output that may later feed another CPU stage or a discrete-GPU transfer. This is a mechanism reference only. It establishes no local Strata bottleneck, B570 behavior, threshold or speedup.

## What the store policy changes

An ordinary write-back store to a cold line usually obtains coherent ownership and may cause read-for-ownership traffic. It keeps the resulting data useful in the CPU cache hierarchy. An AVX2 streaming store such as `_mm256_stream_si256` maps to `VMOVNTDQ` on the relevant x86 targets and requires a 32-byte-aligned destination. It hints that the data need not displace useful cached data. It is not a promise to write directly to DRAM or bypass every cache. Line residency and memory type can change behavior; the Intel manual documents Intel-specific resident-line cases and weak ordering, not an AMD implementation promise.

Keep three things separate: an NT instruction hint, a WC page-memory type, and the processor's write-combining buffers. Software normally does not remap a user buffer as WC to use NT stores. AMD's *Software Optimization Guide for AMD EPYC 7003 Processors* (document 56665, rev. 3.00, §2.13) describes Family 19h write-combining buffers used by streaming-store instructions. It reports 64-byte line buffers, best throughput from complete lines and a small number of simultaneous streams, and possible delays for partial buffers. Treat this as Family 19h generation guidance, not a Ryzen 5000 model-specific guarantee or measured result for a particular host.

NT stores fit best when a producer writes a large, contiguous, one-pass output, overwrites every byte it owns, and the old destination is dead. Two aligned 32-byte AVX2 stores make a common 64-byte line. Use a valid aligned main loop and an explicit head/tail path. Never issue an aligned intrinsic without proving alignment, cross a live object's bounds, or overwrite bytes that must be preserved. Partial lines can waste bus bandwidth or hold combining resources; their exact handling varies. Interleaving many fragmented streams can exhaust finite buffers before lines fill. Staging writes into complete lines may help only when its extra reads, writes and setup cost less than the avoided fragmentation.

## Ordering and consumers

NT stores are weakly ordered. After the final NT stores, execute the architecture/compiler-prescribed store fence (x86 `SFENCE`) before publishing completion or allowing a consumer to read the bytes. A fence orders stores; it does not publish a ready flag, make a record atomic or extend object lifetime. For another CPU thread, use valid release/acquire or mutex/barrier synchronization and ensure the intrinsic has the intended compiler-visible effects. Conflicting unsynchronized non-atomic accesses remain a C++ data race; `volatile` is not synchronization.

For a discrete GPU, CPU `SFENCE` is not a DMA operation, PCIe flush, copy, or SYCL queue/event dependency. If the path uses NT stores, order their completion before handing the buffer to the runtime, then follow the selected SYCL or driver API's host-memory and copy-ordering contract. Keep the source alive and unchanged through asynchronous consumption. A transfer event or queue dependency handles operation completion; it does not replace the CPU store fence. Whether host registration, USM, pinning or staging is used is runtime-specific. NT stores do not remove H2D bytes or prove a transfer win. Measure production, fence/API handoff, copy, overlap and consumer reuse together.

Prefer ordinary cached stores for small outputs, partial updates, read-modify-write/accumulation, hot destinations, sparse or heavily interleaved streams, and data read soon by the same CPU. A cached consumer may use the line immediately; NT can force a later refill, incur tails/fences/setup, or underperform when line residency and write-combining behavior are unfavorable. Do not use an NT store to implement atomics, counters, locks or `+=`.

## Thresholds and evidence limits

Thresholds belong to a particular library, CPU, compiler and workload. A glibc change raised one x86 non-temporal threshold from roughly three-quarters of per-core shared L3 to one-quarter of shared L3 after its maintainers reported cases where `REP MOVSB` beat NT stores by multiples. The commit's rationale is counterevidence to a universal “larger than cache means NT” rule; its number is not a Zen 3 recommendation. glibc has separate copy/fill dispatch controls. LLVM libc PR #187108 added an optional 1 MiB x86 memcpy NTA path and PR #216149 later enabled its configuration by default; their stated downstream/ML outcomes are workload-specific. GCC and Intel compiler controls show that size, alignment, target and compiler policy can select inline loops, library calls or streaming stores. A source flag does not prove generated code.

For a concrete future comparison, first verify the production path, emitted instructions, line coverage, tails, old-byte ownership, number of streams, immediate CPU readers and GPU handoff. Compare the actual temporal/library path with a bounded NT path at small, cache-resident and large sizes; include aligned and offset buffers, complete-line and tail cases, one and multiple streams, no reread and immediate CPU reuse, and a correctly synchronized H2D case if it is a real consumer. Charge setup, dispatch, alignment prologue/tail, fence and transfer on the same critical path. Keep correctness and individual repeated samples separate from mechanism attribution. A component-copy result does not establish a model throughput gain.
