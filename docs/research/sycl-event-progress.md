## Completion is a source-lifetime boundary

SYCL queue memcpy is asynchronous and returns an event representing that copy. Waiting on its event or queue blocks until completion; that makes the corresponding host bytes reusable. Queue flush/submission does not mean completion. The Unified Runtime queue-flush contract guarantees commands are issued to the device but explicitly does not guarantee completion. Neither SYCL nor UR promises a particular host-side progress mechanism or wait latency; whether a Level Zero event wait polls, blocks on host synchronization, or uses interrupt-driven facilities is backend/runtime/device configuration dependent. [SYCL 2020 rev. 13](https://registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html) [UR queue flush and flags](https://oneapi-src.github.io/unified-runtime/core/api.html)

The pinned four-slot staging class has per-slot optional events. Before reusing a slot it waits that slot's prior copy event; then it CPU-copies source bytes into a host-USM slot and enqueues queue.memcpy to the expert destination. Each slot holds up to 16 MiB (64 MiB total before guards/stride). This event protects the host-source slot. Once copy completes, later device readers of the destination do not prolong the source-slot lifetime. The bounded four-slot scheme is correct by construction for that source lifetime, but may make the producer wait when it wraps to a still-active event.

## Submission, batching, and observation

Level Zero distinguishes regular recorded command lists (executed later) from immediate command lists (append submits). UR currently documents batching/immediate submission hints, batch-size controls, event visibility choices, and an optional Level Zero low-power event hint. Those knobs can trade host utilization, event overhead, and completion latency; they are not universal speedups. The Level Zero programming guide warns that waiting on a host-signaled event that will only be signaled after submission can prevent forward progress. A host wait for a copy's completion is different: it waits for already submitted work. [UR Level Zero reference](https://oneapi-src.github.io/unified-runtime/core/LEVEL_ZERO.html) [UR queue flags](https://oneapi-src.github.io/unified-runtime/core/api.html#ur-queue-flags-t) [Level Zero 1.17.24 programming guide](https://oneapi-src.github.io/level-zero-spec/level-zero/1.17.24/core/PROG.html)

The pinned producer uses ordinary queue memcpy and SYCL events; do not assume a particular immediate/recorded mode from SYCL alone. Current online UR/Level Zero docs are not proof of the installed runtime revision or its v2 path. To resolve that for a concrete implementation, retrieve the runtime identity from the native run receipt, then the matching intel/llvm Unified Runtime Level Zero adapter sources and headers; trace queue creation/properties, enqueue, event wait, submission/flush triggers, event visibility, and copy-engine selection at that exact revision. The old oneapi-src/unified-runtime project points future development to intel/llvm, so current main is not a substitute for the pinned runtime.

A larger ring can permit more copies in flight and move slot-reuse waits farther apart, but it also increases pinned/USM memory and only helps if the producer can submit useful independent work before needing the slot again. Iterative upload-compute may expose little overlap; whole-layer immutable preparation could expose more CPU preparation/copy overlap, at greater memory cost and only if the next source data is genuinely ready and immutable. These are hypotheses, not findings about a slow sample. Useful bounded comparisons, only when motivated by measured waits, are 4 versus a finite larger ring; per-slot event wait versus a batched event retirement; and an explicit flush policy versus normal queue semantics. Change one factor, preserve correctness/ownership, and compare clean end-to-end runs.

Logging and profiling may change host submission pacing: API tracing, synchronization, formatting, and flushes consume host time and can create gaps between enqueue calls, changing how much work is queued when the device reaches it. They can therefore change overlap in either direction. Intel guidance separates host submission, device execution, and transfer time, and VTune documents tracing modes; this supports the possibility of host-side measurement perturbation, not a claim that it caused any specific result here. Counterevidence matters: coarse workloads may amortize observer overhead, and device timestamp collection need not add meaningful host gaps. Verify with matched clean processes and separate diagnostic processes; do not infer causality from traced-vs-clean differences alone. [Intel GPU launch timing guidance](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2024-0/kernel-launch.html) [VTune 2025.1 guide](https://cdrdv2-public.intel.com/848603/vtune-profiler_user-guide_2025.1-766319-848603.pdf) [ALCF Intel VTune technical session](https://www.alcf.anl.gov/sites/default/files/2024-09/2024_Sep_ALCF_DevSession_Intel_Tools_v03.pdf)

## Keep three lifetimes distinct

The copy event retires source bytes only. Afterward both IQ dequantizers read the expert destination blob; GU and Down GEMMs read decoded weight arrays and their respective inputs/outputs/scratch. Those device objects must remain valid through their actual readers. A host source-slot event is not a valid retirement signal for them. Conversely, waiting for IQ/GEMM readers before reusing the host slot is unnecessarily conservative. The pinned SYCL GEMM adapter stores workspace_ but the earlier source review found this backend does not consume it; do not infer workspace readers from the member's existence. Cross-queue readers need explicit dependencies because SYCL in-order properties do not order work on other queues. [SYCL queue ordering](https://registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html#sec:queue-in-order)

## Applicability and evidence limits

The native S comparison uses the actual layer-2 512-expert source corpus (about 1.009 GB requested H2D across 512 jobs), ordinary read-only mapped RAM through the full production cudaMemcpyAsync compatibility wrapper, versus four-slot host-USM staging. It is a whole-layer/all-expert source-adapter fixture, not a whole-model/full-prompt run or a hardware-ceiling measurement. All 30 clean samples across five row shapes and three paired orders are retained; all 42 native processes exited normally, correctness/bitwise reference and guards passed. No slow samples were excluded.

The paired staged/direct ratios are mixed. For 1024 rows the three ratios are 0.754, 0.996, 1.007; for 4096 rows 1.218, 1.000, 0.876. No tested shape won all three pairs. Staged preparation adds CPU work, while direct timing includes its complete production wrapper, so this does not isolate CPU memcpy or device copy service. The evidence supports no repeatable source-adapter gain and does not establish saturation, a ceiling, or a product slowdown. Prior mapped-source/global-stage failures and the older immutable-USM lookahead result remain separate evidence and should not be combined with S.
