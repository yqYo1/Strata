# Selected-KV attention fusion for small decode batches

**Retrieval synopsis.** The selected Strata build already uses the central fused pattern: each `(verifier row, KV head, 64-cell chunk)` workgroup resolves that row's selected IDs through the page table, loads/dequantizes INT8 K/V, computes QK and online-softmax partials, and accumulates V; a separate kernel merges chunks. It does not share selected IDs between rows. The most credible alternatives are (A) keep independent row-specific fused work and tune row/chunk scheduling, or (B) materialize a gathered/dequantized buffer (or an exact union with row-membership masks) before attention. B can make attention more regular, but adds traffic and launches; an exact union is only correct when it preserves each row's membership and causal/tail rules. Current public sources show that both styles exist, but none establishes a B570 speedup.

**Classification:** methods collection; no implementation proposal, bottleneck attribution, or local speed claim. Public source inspection dated 2026-11-04. References to `main` below identify discovery pages as observed on that date, not immutable implementation pins. ## Scope and prior coverage

This question is specifically about the small-query decode/verifier path: fuse selected-row address resolution, INT8 dequantization, and attention; and how to process batches of one to four verifier rows whose selected sets can differ. It is not a survey of cache capacity or long-prefill formats. The indexed long-context K/V report covers scale granularity, format payload and 262K context. The earlier one-row MTP report covers dense paged decode, GQA reuse, split-KV/merge, and launch geometry. The cross-query locality report covers workgroup ordering, clusters and union scheduling as a locality question; the irregular-GQA report covers query-head packing. Those remain useful retrieval references, but none compares selected-row fusion with an intermediate dequantized gather for B=1..4 while explicitly retaining independent row IDs and exact causal semantics. The new focus here is dataflow and verifier-row independence, not another format or generic tiling survey.

## Selected Strata implementation: fused row-local gather and attention

The task-provided compiled generation is `/home/yayoi/.local/state/strata-sycl/post-reboot-tuning-20261007/cache-map-model-v1/source`, with recipe `479a6fdac8cbaa35a9bf3a41d2b6e23be5260e54` and engine SHA-256 `552b1616d21ad1b9aa6a317cb940d375c003246b896a255a935e09292804c96a`. This is the source snapshot named by the task, not a claim about the live generator or current worktree. In its SYCL `decode_attention.cpp`, `qsa_decode_attn_batch` launches one first-stage group for each verifier row, 64-cell capacity chunk and KV head (`HD=256`, `G=12`, `WG=256`). The group reads IDs from `ids[batch * cap + cell]`, resolves logical cell → page-table entry → physical KV row, and gathers K/V as needed. For INT8 it reads signed codes and one FP16 scale per 64 dimensions, applies code × widened scale in FP32, computes QK, multiplies logits by `0.0625`, forms FP32 partial max/sum, and accumulates weighted V. A second kernel merges the per-chunk partials. Thus gather, dequant and first-stage attention are already fused; split merge is not.

This work decomposition is a sensible baseline for small B because it avoids a full gathered-KV materialization and its write/read pass. Dimension-contiguous addresses within a selected token make lanes' K/V loads regular across D even when selected token IDs are irregular across cells. The page-table lookup remains a per-cell indirection, and each verifier row has its own ID array. The 12 query heads sharing a KV head reuse the same cell's K/V load within a group; this does not imply reuse across different query rows. For B=1..4, row independence gives correctness and exposes independent work without assuming top-k lists match. At B=1, launch and the second merge can be appreciable; at B=4, first-stage parallelism multiplies, but each row may fetch unrelated pages. CPU/GPU wait time and configured capacity are not evidence that either launch overhead or memory service limits the full request.

### Exact row semantics

Each row must retain its own selected-ID sequence, its own valid count/step and its own causal-visible extent. Do not feed row 0's IDs to rows 1..3, sort or deduplicate IDs unless multiplicity/order semantics are proven irrelevant, or merge rows based on presumed overlap. For an exact union, form a set of physical/logical entries and carry per-row membership (and multiplicity if duplicates are meaningful); absent members must contribute `-inf` to that row's logits before max/normalization, not zero logits or merely zero V. Also preserve locally required recent/tail tokens if selection expansion adds them separately. The causal predicate is on logical token position relative to that query's decode position, not on packed/gathered order or physical page slot. A cell's block translation and row-specific cutoff therefore cannot be dropped just because rows share some selected pages.

For the current symmetric per-64 INT8 contract, K and V each have `row × head × 256` signed codes and four FP16 scales. A fused path should multiply each selected K code by its K scale before QK accumulation, and each V code by its V scale in the weighted-V sum. It should preserve the scale's location relative to accumulation and the local FP32 behavior. A staged gather-dequant can round values into a storage dtype (for example BF16) before attention; that is a distinct numerical contract from multiplying the FP16 scale in FP32 and accumulating scores/weighted values in FP32. Zero/invalid rows, partial final chunks, duplicate IDs, page aliases, scale extremes and all-masked tiles need explicit treatment. Algebraic equivalence does not guarantee the same rounding or stable empty-row result.

## Alternative 1: independent fused work with small-batch-aware scheduling

Keep one row's selected IDs attached to that row and perform page resolution, K/V reads, dequantization, score/softmax and V accumulation in the same attention pass. A B-aware kernel may map rows to workgroups, or pack multiple independent query rows into one workgroup while retaining separate row descriptors and separate normalization state. The former preserves simple ownership and grows workgroups linearly with B; the latter may share launch/setup and improve cache reuse if physical addresses overlap, but increases live Q/score/softmax state and can reduce occupancy. In either layout, Q-to-KV head grouping and the cell-major / dimension-contiguous lane mapping should be selected together. Batching queries alone does not create reuse if selected addresses differ.

FlashInfer's current MSA sparse API is useful as a scheduling counterexample, not a B570 recipe. Its documentation describes sparse decode routes with explicit accepted shapes; for compute capability 10.0/10.3/10.7 it uses a direct persistent M16 ownership route for Q1 and multi-token decode rather than split-K, and it has a separate supported FP8-KV Q1..Q32 route. Other paths reject unsupported output/layout forms, and generic TopK16 restrictions apply on that family. This shows that persistent direct decode can be a deliberate alternative to a multi-kernel split/merge, but the GPU architecture, tensor geometry, graph rules and dtypes differ. FlashInfer's sparse MSA APIs are not proof that arbitrary QSA IDs or Intel SYCL layouts are supported.

SGLang's Qwen3.8 SM121 packed-varlen README describes a specialized path for one packed query row per sequence, BF16 Q/K/V/O, head dimension 256, 12 Q heads per KV head, and per-sequence selected lengths. It groups those 12 heads in a CTA and uses online softmax with split K/V rows and a stable merge; its reported A/B results are on GB10, not Intel. It illustrates that per-sequence row lengths can remain dynamic while a schedule is selected, but is CUDA/SM121-specific. SGLang also has an explicit counterexample: an issue documents BF16 queries paired with FP8 K/V reaching an attention dtype assertion on one QSA route. A cache flag alone is not a complete attention contract.

## Alternative 2: gather/dequant first, then regular sparse attention

A separate gather/dequant pass writes only selected rows into contiguous scratch, then attention traverses the scratch using compact row offsets. This regularizes subsequent reads, can simplify the consumer kernel, and may be a good compatibility fallback when the sparse attention primitive accepts a supported BF16 layout but not compressed cache. Its full cost includes index and page-table reads, dequant arithmetic, scratch writes, later scratch reads, allocation/metadata, and at least one additional launch or dependency. It can win if the fused kernel's repeated page/scale address work is expensive or if gathered data is reused by multiple consumers; it loses when rows are consumed once and materialized bytes/launch exceed savings. For B=1..4, scratch is bounded by `B × selected_width × head_dim × dtype_bytes`, but bytes alone do not predict service time or allocation behavior.

A concrete Intel reference exists in vLLM's DeepSeek-V4 XPU path, not Qwen3.8: `xpu_sparse_decode_fp8.py` dequantizes selected FP8 cache slots into BF16 workspace, packs sparse and sliding-window indices, then calls the BF16 sparse MLA attention interface. Its own description says dequantization happens on the fly and reuses the validated BF16 attention kernel; code materializes the gathered values and launches attention afterward. This is a useful proof of a production XPU compatibility strategy and an honest counterexample to “always fuse.” It is not a matched comparison: V4 uses a mixed 448-FP8/64-BF16 key record and UE8M0 scales, distinct from Strata's symmetric INT8 K/V; the V4 path's FP8 scale decode and output contract must not be substituted for Strata's FP16 per-64 scales. The current vLLM Qwen3.8 recipe says initial implementation does not support XPU, so the V4 path does not establish Qwen3.8 XPU support.

An exact tile-union is a third, conditional variant between these two: for rows with genuine overlap, load each unique K/V element once and apply an independent membership mask and softmax state per row. It can reduce duplicate cache-line fetches but requires union construction, row-to-union incidence, causal tail handling, extra state and potentially a lower number of independent workgroups. For B≤4, a bounded pairwise comparison may be simpler than general sorting, but only after measuring actual selected-set overlap. If the union is nearly as large as the concatenated lists, it adds work without removing much. If lists differ, a union is still semantically possible, but every row needs exact membership; using the union as a common attention mask is wrong. Prior QUILT/union studies and the indexed inter-query report address larger prefill/query-cluster scheduling; their evidence does not show B=2..4 decode overlap on this build.

## Selection criteria and scoped experiments

First verify the compiled source and entrypoint for the selected engine hash, then compare two bounded mechanisms under the same production decode entrypoint: (i) current fused row-local gather/dequant/attention with B=1,2,4 verifier rows; (ii) an exact selected-row gather/dequant scratch plus sparse attention consumer. Hold each row's Q, IDs, step, valid count, page table and cache bytes constant. Include independent disjoint-ID lists, naturally observed overlap, and a deliberate identical-ID positive control, but report them separately. For a union candidate, include exact membership and an adversarial low-overlap negative control. Freeze a new plan before measurement; require row-wise numerical comparison against the same selected-set reference, invalid/tail/page-boundary safety, MTP state handoff and request output checks before interpreting speed. Measure total dependency time including preparation and merge, not only attention kernel service. Keep first-use and warmed timings distinct, repeat independent processes, and collect no profiler-based saturation claim without proper attribution.

What is genuinely new here is the combined small-verifier question: how to fuse a row-specific selected gather and asymmetric-to-the-actual-format dequant path without conflating B rows, and how to use a staged XPU gather as a credible alternative with explicit extra costs. The earlier single-row report already identifies GQA reuse and split/merge tradeoffs; the K/V-format report already covers storage granularity. Neither selects a winner here. Unknowns remain actual B distribution, selected-ID overlap and page/line locality, physical traffic, B570 kernel/launch costs, cache-scale data placement, and whole-model decode impact. CPU and device completion waiting remain unassigned resources. No local performance result or adoption decision follows from this survey.
