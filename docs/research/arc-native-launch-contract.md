The root `setup.py` routes `--backend sycl` to `sycl/setup_intel.py` and checks that path before launching it. The separately supplied `tools/setup_intel.py` is not called by that route. The pinned source bundle does not include `sycl/setup_intel.py`, so its absence from the complete checkout is unresolved; do not describe setup as broken on this evidence alone.

The CLI runner has a direct Arc adoption path: on a setup failure it can call `adopt.plan()` and `adopt.write()` without going through `tools/setup_intel.validate_config()` or `to_native()`. `adopt.plan()` emits `--ple-io ram` for i915 and `--stream-experts` for other detected drivers. In the pinned native parser, `--ple-io ram` and `--vram-reserve-mib` are recognized, but `--stream-experts` is not; unknown arguments exit with status 2. Thus the non-i915 adoption branch can persist an argument the native executable rejects at startup. This is a source-derived conditional inference, not an observed launch.

`adopt.plan()` builds a fresh config and `adopt.write()` writes it directly. That path does not merge prior launch choices. The separate `tools/setup_intel.to_native()` does check dropped old arguments and preserves selected host, key, library-directory, and vision fields, but those checks do not cover direct adoption. The adapter's `cli_flags()` is a regex over textual parser comparisons, so it cannot establish value validity, compile-time availability, or cross-option compatibility.

For the native server contract, `--serve` requires `--spec >= 2`, either an MTP directory or DFlash2, and a prefill chunk; `--draft` accepts `mtp` or `dflash2`, with no `off` value. The SYCL DFlash2 admission rejects vision, layer split, coupled drafting, partial prefill, and multi-card/remote expert options. `--vision` enables GENI/SVE1 input at the native stdin protocol, but encoder availability and Python image conversion remain outside this source evidence. Native `QUIT` is protocol shutdown; managed process ownership and stop behavior belong to the Python runtime.
