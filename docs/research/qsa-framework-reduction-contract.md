# Qwen QSA sparse-prefill contracts and parallel online softmax

**Scope and evidence date: 2026-11-18.** This is a source-level comparison of Qwen3.8-Flash-Next (called Qwen4-Exp in current vLLM/SGLang paths) sparse GQA attention and the supplied Strata prefix snapshot. Framework `main` is mutable; links below identify the inspected upstream paths, not immutable release guarantees. The local Strata comparison is pinned by the input manifest to native source commit `14508acbf1b70eb994fdf37f97fb6d0f5cff7d43` and the rules snapshot to `bb2310969e70e2b648db8531932d09d5f67150e2`. The local project license is MIT. vLLM and SGLang source repositories declare Apache-2.0; this report proposes independent experiments and does not copy source. Any future port/adaptation must preserve upstream notices and be checked against those licenses and Strata's MIT policy. XeStrata was excluded.

## What the current paths actually compute

The vLLM NVIDIA QSA kernel loads BF16 Q and selected K, computes QK in Q's dtype through `tl.dot`, and applies `softmax_scale * log2(e)` to the FP32 score. It explicitly avoids scaling and re-quantizing Q to BF16. FP8 K is first dequantized/upcast to Q dtype, and FP8 V is upcast to FP16 for PV. Invalid page/index entries are masked to zero loads and score `-1e20`; `valid_count` bounds the tile loop. Per tile, it updates `m=max(m_old,tile_max)`, `alpha=exp2(m_old-m)`, `p=exp2(score-m)`, FP32 normalizer `l=l_old*alpha+sum(p)`, and FP32 PV accumulator `o=o_old*alpha+dot(p,V)`. Probabilities are cast to the value dtype for PV, not first written into a BF16 scratch array. For one split the normalized result is rounded to output dtype (typically BF16) before the output gate; split paths save partial output/LSE and merge in FP32, then round before gating. See [vLLM QSA kernel](https://github.com/vllm-project/vllm/blob/main/vllm/models/qwen4_exp/nvidia/ops/qsa.py) (Apache-2.0).

SGLang's generic Triton `_sparse_gqa_prefill` and chunk-prefill path make a materially different query-rounding choice: load Q, multiply by `scale*log2(e)`, then cast the scaled Q back to its original dtype before the dot. QK products and online `max_value`, `normalizer`, and `accumulator` are otherwise explicit FP32 state in the Triton kernel. It uses `-inf` for invalid score columns, reduces tile maxima and probability sums across columns, casts probabilities to V dtype for PV, and returns normalized output in the output tensor's dtype. Chunk prefill also makes FP8 cache inputs compatible by converting K/V to Q dtype before dot. These statements are for the generic sparse GQA kernels; SGLang dispatches other backends on other hardware/modes. See [SGLang sparse GQA kernels](https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/layers/attention/qsa/sparse_attn.py) and [Qwen sparse-attention dispatch](https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/layers/attention/qwen_sparse_attn_backend.py) (Apache-2.0).

The supplied Strata `prefix_batch_impl` is its own typed SYCL design, not a drop-in mirror of either framework. It dequantizes quantized K/V to FP32, then stores BF16 scratch; Q is decoded from BF16, multiplied by 1/16 and `log2(e)`, then BF16-rounded before QK. QK and PV use BF16 matrix operands with FP32 accumulator fragments. Softmax `m`, `alpha`, `l`, and scores are FP32; each tile's probabilities are computed FP32 then rounded to BF16 scratch before the FP32-accumulating PV matrix product. The final output divides FP32 accumulator by FP32 normalizer, then rounds BF16. Thus the strongest common contract worth carrying forward is **BF16 Q/K/V operands and probabilities with FP32 online state/accumulation**, but Q scaling-rounding, V conversion, exp implementation, tile summation and final post-ops are not yet common contracts. Exact boundaries matter more than the phrase “BF16 attention.”

| Small coherent unit | vLLM QSA NVIDIA | SGLang generic QSA prefill | Strata supplied prefix |
|---|---|---|---|
| Scale Q / scores | QK first, then FP32 score scale in log2 units; no scaled-Q BF16 round | Scale Q in log2 units then round to Q dtype before QK | Scale Q by 1/16 then log2(e), BF16 round before QK |
| P storage for PV | Cast to V's compute dtype at dot; no BF16 P buffer | Cast to V dtype at dot | BF16 P buffer, then BF16 matrix operand |
| `m`, `l`, `o` | FP32 online; split partials and merge FP32 | FP32 online, one row/query group CTA | FP32 online, subgroup or per-head tile state; FP32 matrix accumulator |
| Invalid/missing | masked indices/pages excluded; empty split represented by `-inf` LSE and merged safely | missing index excluded with `-inf`; no explicit score-isfinite recovery branch in this kernel | absent IDs become zero-filled operands / zero probability; nonfinite live score or query flags head; invalid scales flag output; empty valid set yields zero |
| Summation | Triton axis reductions; split merge reduction when split count > 1 | Triton axis reductions, tile by tile | current subgroup variant tree-reduces 32 probabilities; ordered-exp variant parallelizes exp but sums ascending through lane 0 |

This is not bitwise framework equivalence. vLLM's FP16 V compute route and unrounded probability path differ from local BF16-V/P. SGLang's Q-rounding before dot agrees in kind with Strata; vLLM retains higher precision scale placement. Neither framework kernel has Strata's explicit “nonfinite score poisons output” diagnostic policy. Zero masks, `-1e20` vs `-inf`, all-masked rows, NaN/Inf, FP8 scales and empty selections need explicit expected results before adopting common arithmetic.

## Parallelism, reduction order, and limits

The frameworks expose distinct parallel patterns. SGLang assigns one query row and KV-head group to a program and distributes selected cells across Triton lanes; tile `max`/`sum` are parallel reductions, while tiles are visited serially with online rescaling. vLLM can distribute one row's KV tiles across `NUM_SPLITS` programs and merge partial LSE/output in a second kernel. It takes max partial LSE, exponentiates shifted LSEs, weighted-sums partial normalized outputs, and divides by weight sum. This adds parallel work for long rows, at cost of scratch, another launch and a changed FP32 reduction tree. This NVIDIA path does not establish Intel SYCL suitability.

Strata maps each 128-work-item group to two KV heads and 24 real query heads padded to 32. SIMD16 subgroups process two heads and 32 cells; the subgroup softmax variant uses two scores/lane, subgroup max, and a tree reduction of `p0+p1`. The ordered-exp variant parallelizes exponentials and max but broadcasts values to lane 0 for the original ascending 32-term FP32 sum. PV updates four FP32 accumulator fragments after each 32-cell tile, multiplying old state by alpha before each tile update. The direct-vs-ordered reduction and subgroup-vs-single-work-item designs already have extensive prior local study: the index records an isolated cached parallel sum speed rejection (geomean latency ratio 0.993646; do not repeat), an ordered-exp mechanism and real-head softmax gate history, and a prior ordered-parallel survey. This report does not reopen those experiments. A measured profile projection reports 6.8335 s summed service for 96 `qsa_prefix` events in one profiled first-use 32K request; that is device-event service attribution, not exclusive wall time, attention-only critical path, utilization, physical saturation, or memory bandwidth. It supplies context for cost, not a claim that softmax is the bottleneck.

## Smallest independent alternatives, then combinations

1. **Keep Q/K/PV contract, change only Q scaling placement.** Compare framework-shaped alternatives: (a) Strata's BF16-round scaled Q before dot (closest to SGLang generic); (b) BF16 dot then FP32 score scaling (vLLM). Pin scale factor, log2 conversion and compiler contraction. Treat output and intermediate FP32 state separately; score differences can reorder near-tied probabilities/top-k-independent attention mass. Validate at real 12-head extent and adversarial peaked/near-tied scores. This is justified as a numerical-contract question; no gain is established.
2. **Keep online recurrence, change only probability storage/operand precision.** Compare BF16-rounded P used by PV against framework-style FP32 P cast to the existing V compute dtype at the dot. Do not conflate with accumulator precision: retain FP32 `m/l/o` in both. BF16 P is cheaper/narrower but can zero small mass or perturb a peaked output; FP16 preserves more mantissa but changes storage/traffic. Current source references do not prove which is faster on B570. The local existing P staging is BF16, so this comparison must avoid duplicating earlier P / subgroup studies unless it tests a distinct combined path with the active selected variant.
3. **Keep each query's exact selected set, change only query scheduling.** A vLLM open RFC reports tile-union prefill: for R adjacent queries, gather the union of selected blocks once and mask each row's nonmembers within online softmax. Its author reports 87–94% neighboring block overlap and standalone kernel path gains on GB10; these are issue-reported measurements, not independently verified upstream release behavior. Exact membership masking preserves each query's mathematical selection, but changes visitation/reduction order and costs a union builder, membership storage, and skew handling. The RFC found R=4 widened unions and lost at longer context and rejected compact membership masks due spills. Applicable specifically to long prefill with high adjacent-row overlap; not decode, not a generic sparsity win. See [vLLM tile-union RFC](https://github.com/vllm-project/vllm/issues/55394).
4. **Keep row-local arithmetic, change only split parallelism.** vLLM's LSE merge is a concrete alternative when long selected rows underfill the GPU; test split counts against one-program-per-row and account for an extra launch/scratch and tree-order change. For Strata's large prefill query count, current data does not establish row underfill, so this is not schedulable without new per-shape occupancy/critical-path evidence. Do not equate a large sum of QSA event durations with saturation.

After isolated units are accepted, combinations can test (A) scaled-Q BF16 rounding + FP32 P cast + existing recurrence for framework boundary alignment; (B) tile union + unchanged recurrence for duplicate-gather savings; (C) union + split-K only if union programs remain underfilled. Include preprocessing and test membership, padding, causal tail, zero-live/all-masked tiles, NaN/Inf, and invalid pages/scales. Preserve separate baselines so a combination does not hide which unit changed results.

## Applicability, counterevidence, and next scope

Model applicability is narrow and explicit: Qwen3.8/Qwen4-Exp full-attention/QSA layers, 256-wide heads, 12 query heads per KV head in the supplied path, selected top-k cells, BF16 local Q/K/V path; Qwen3.8 alternates QSA with GDN and is not “all attention.” vLLM file is NVIDIA/Triton-specific; SGLang's generic sparse Triton code and runtime dispatch have CUDA/ROCm/backend branches. Neither source establishes Intel execution or the exact runtime-selected path for Strata's quantized GGUF. Qwen3.5 dense/hybrid attention, DeepSeek DSA, dense FlashAttention, and other head widths are not evidence for this route. The maintained index already records prior cross-query reuse surveys; this new RFC is a concrete upstream proposal to retrieve only if Main establishes adjacency overlap and preprocessing cost. Existing Strata selected-path/profile work should be consulted before choosing a duplicate normalizer or ordering trial.

**schedulable_now: false for a substantive kernel change.** The first defensible next scope is a source-and-fixture contract review only if Main names which boundary (scaled-Q rounding, P cast, or invalid-row behavior) a current measured comparison needs. For a performance scope, prerequisites are a current matched profile resolving QSA's share and critical-path overlap, actual per-query selected-width/overlap distributions for tile union, and a frozen numerical fixture covering live model head dimensions and failure cases. No performance/adoption assertion follows from this report. The profile describes service, not physical saturation. A report-level proposal is not qualified code; compile, numerical, physical 262144-context, lifecycle, and matched model gates remain Main-owned.
