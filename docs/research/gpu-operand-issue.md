# GPU arithmetic operand supply and issue

This is a methods reference for a future, specifically identified GPU arithmetic path. It contains no B570 measurement, register-file map, local bottleneck attribution or adoption result. Retrieve it only after the selected Strata source/build and final native ISA/JIT identity are pinned.

An instruction may wait for an operand dependency (RAW/scoreboard), a busy execution pipeline, register-operand service, or a lack of independent ready work. These causes are distinct. Multiple encoded sources do not prove serialized register reads; a dependency chain does not prove a bank conflict; instruction issue rate is not arithmetic throughput. Modeled operand collectors and bank-conflict behavior can fail to predict hardware behavior, so cross-vendor models are hypotheses rather than Xe2 facts.

Intel GEN destination/source fields and regions describe encoding. vISA is a virtual representation lowered for a target. Neither establishes Xe2 physical banks, ports, read bandwidth or emitted mapping. Pinned IGC flags document experimental/debug options such as `EnableGroupScheduleForBC`, BCR thresholds and operand-overlap avoidance. They carry no performance or conformance guarantee; some BCR thresholds apply to OpenCL shaders. They are not a public SYCL control or proof that a particular JIT uses the pass. The IGC license is MIT; this reference reproduces no implementation.

Intel VTune 2024.2 says a `Pipe` stall can have a GRF bank conflict as a cause. Its named XVE stall reasons are documented for Data Center GPU Max, not as B570 telemetry. This is a possible-cause label, not a dedicated operand-read signal. Xe/Xe2/B570 bank mapping, read-port service, reuse/bypass behavior and local conflict signals remain unknown. GEN source count, NVIDIA PTX/SASS, AMD wait encodings and GPU models such as BOW or the cited NVIDIA study do not transfer their physical mappings to Xe2.

Reuse and scheduling are conditional. Reuse can reduce repeated reads if the target supports it, but may lengthen live ranges, expose dependencies, concentrate operand demand or add WAR/WAW constraints. Moving independent accumulators can hide a recurrence when execution capacity is available, but changes instruction-level parallelism, register use and potentially reduction order/rounding. It is not a fixed-allocation schedule test. Source renaming can change allocation and instruction selection. In SYCL, `reqd_sub_group_size` constrains subgroup shape and `work_group_size_hint` has implementation-defined effect; neither specifies GRF assignment, operand service or instruction order. Source order and compiler flag names do not prove emitted scheduling.

For a future discriminator, first pin compiler/runtime/build and map the production call to its final ISA, operands, register assignments, SIMD width and dependency annotations. To test recurrence latency, vary independent chains while checking instruction count, math order and resource mapping. To test schedule sensitivity under fixed allocation, preserve the native instructions, operands, assignments and count, changing only legal order/reuse distance. A repeatable change supports schedule sensitivity, not bank geometry. A register-operand claim additionally needs target-specific evidence or a native test that fixes dependency structure, pipeline mix and mapping, with a relevant signal or robust positive/negative controls. Separate memory/send waits, pipeline limits, synchronization and changed codegen. Timing alone cannot identify a bank conflict; absent direct evidence, report only the effect actually isolated. Numerical changes and whole-model impact are separate gates.
