# Zen 3 store-to-load hazards in quantized producer/consumer loops

## Scope

This note isolates two hazards that could occur when CPU pack/dequant code stores data which a later operation soon loads: (1) a real overlap that fails Zen 3's store-forwarding coverage rule, and (2) a false dependency between different addresses sharing a 4 KiB page offset. These are mechanisms to discriminate, not findings about Strata's current CPU path. The selected Ryzen 5600X `znver3` reference's CPU-expert-pool wall includes waits and scheduling; it does not identify arithmetic, store forwarding, DRAM, or any CPU resource as the cause.

## Zen 3 evidence

AMD's *Software Optimization Guide for AMD EPYC 7003 Processors*, doc 56665 rev 3.00 (the Zen 3 Family 19h Models 00h–0Fh guide), discusses the load/store unit in section 2.12 (printed p. 46). Store-to-load forwarding requires one older store to cover every requested byte and have its data ready. The guide says linear-address bits 11:0 determine forwarding eligibility and warns against simultaneous in-flight stores to distinct addresses with matching low 12 bits when a load may need forwarding; it recommends grouping loads that follow stores to similar address space. A possible hold while fuller addresses are resolved is the mechanism inferred here, not a separately specified or quantified AMD timing contract. Separate C/C++ buffers can be object-disjoint yet share this page-offset pattern. Source: [AMD document 56665](https://docs.amd.com/v/u/en-US/56665) (AMD landing page gives revision and source ZIP).

Agner Fog's original measurement-based *The microarchitecture of Intel and AMD CPUs*, Zen 3 sections 23.16–23.17 (2026-05-23 edition), independently reports the 4 KiB-spaced false dependence and an approximately 10-clock penalty for partial overlap. It reports little or no general penalty for unaligned reads/writes except across a page boundary. These are Zen 3 microarchitecture-guide observations, not a Ryzen 5600X/Strata measurement receipt, and do not predict how much out-of-order work hides the delay. Source: [Agner Fog's manual](https://www.agner.org/optimize/microarchitecture.pdf), pp. 246–247 as numbered in that edition.

Do not reduce these facts to “unaligned is slow.” A load fully contained in one older store can forward even when it starts at a different offset; alignment by itself is not the general disqualifier in the Zen 3 guide. A partial overlap is different: a load spans bytes the store did not write. A load wider than its store has the same issue. Do not assume two narrow stores jointly forward one wider load: the documented eligibility condition is one older store covering all requested bytes. Partial overlap and page crossing are separate cases.

Zen 3 Predictive Store Forwarding (PSF) is also distinct. AMD describes PSF as learning/predicting a store/load relationship before address calculation finishes; its security paper discusses training and speculation limits. PSF does not show that a normal quantized loop has a repeated throughput penalty, and it is not the 4 KiB resolved-address alias mechanism. Sources: [AMD PSF overview](https://www.amd.com/en/blogs/2021/predictive-store-forwarding.html), [AMD PSF security analysis](https://www.amd.com/content/dam/amd/en/documents/processor-tech-docs/white-papers/security-analysis-of-amd-predictive-store-forwarding.pdf).

## Quantized dataflow cases and counterevidence

### 1. True overlap: byte/word pack store followed by a wider reload

A packer may emit a short tail or subfield with byte/word stores, then its consumer reloads a wider word/vector spanning that field plus neighboring bytes. Nibble packing can create the same shape if a containing byte is written and a wider packed group is immediately read. If one store covers only part of the load, Zen 3 cannot satisfy the whole load from that entry; Fog's approximately 10-cycle partial-overlap penalty makes this a candidate dependency-chain cost. It is most plausible at a block tail, a producer/consumer boundary, or where fields are stored separately then reread.

Counterexamples: register-only assembly/consumption has no memory forwarding edge; a full-width store followed by a contained load is forwardable; and a later function/kernel/request may run after the store has drained, so there is no critical in-flight edge. Compiler scalar replacement can also remove a source-level store. Therefore source syntax alone does not establish the machine pattern.

Any prospective store-width change must preserve packed encoding, quant values, scales, rounding, initialized tail bytes and object boundaries. Defined byte operations or a correctly sized `memcpy` into a live object may produce different code, but lowering is unverified. Do not introduce typed access to byte storage, untrue alignment promises, padding reads, or writes across object/lifetime boundaries merely to make a store forwardable.

### 2. False overlap: different buffers with equal low 12 address bits

A pack stage can store a quantized scratch tile while a nearby consumer still has those stores outstanding and loads activations, original weights, scales, indices or a neighboring tile from another buffer. AMD warns about distinct in-flight store addresses with matching low 12 bits when a later load may need forwarding. A conservative partial-address check or hold while fuller addresses resolve is a plausible interpretation; AMD 56665 does not specify a replay mechanism or quantify its penalty. The relevant pattern is the in-flight page-offset collision, not mere proximity of arrays.

Counterexamples: the consumer reads a register value; the producer store has drained before the independent load issues; low 12 bits differ; or the hot loop contains no such store/load coexistence. Even when page offsets match, address resolution may be quick and independent dot/dequant work may hide it. Separate allocations alone do not rule it out, but a same-offset pair alone does not establish a costly replay.

A quantized dot loop may read several operands and write a transient packed/dequantized tile, or it may keep intermediates in registers and only read operands. Format names do not predict which. The actual call path and emitted instructions are needed to establish simultaneous relevant stores/loads. This report does not claim that the frozen optional cache-map source or current production code contains either shape.

## Intel-only evidence boundary and generation differences

Intel optimization/VTune materials describe Intel load-block/4K-alias events such as `LD_BLOCKS_PARTIAL.ADDRESS_ALIAS` on supported Intel cores. They can guide an Intel test, but do not establish an equivalent AMD event, semantics, penalty or threshold. This event name is Intel- and processor-specific; cite the applicable platform's PMU table (for example, [Intel Jaketown core events](https://perfmon-events.intel.com/platforms/jaketown/core-events/core/)) when naming it. Intel partial-forwarding demonstrations are not a Zen 3 contract; use AMD 56665 and Fog's Zen 3 section for the rules above. Zen 2 and Zen 4/5 have different forwarding/memory-operand-mirroring details; Fog reports 1 KiB false-dependency spacing for Zen 4/5, not Zen 3. Keep the target to Zen 3 Ryzen 5000 / EPYC 7003. The [Intel 64 and IA-32 Architectures Optimization Reference Manual](https://cdrdv2-public.intel.com/821612/248966-Optimization-Reference-Manual-V1-050.pdf) is general Intel context, not evidence of an AMD counter or behavior.

## Bounded no-PMU discriminators (proposals only)

Neither design was built or run for this report. Use only if actual source or attribution makes the question relevant.

1. **Forwarding shape.** In a tiny defined-code loop, compare separate arms: (a) exact same-size store/load, (b) a load fully contained in a wider store but starting at a different offset, (c) partial overlap, (d) a load wider than its store, and (e) no relevant store. Keep the checksum and non-memory computation constant, initialize every byte read, and document each arm's access widths; these cases cannot have identical memory-uop work. Keep touched lines L1-resident where feasible and avoid cache-line/page crossings unless testing them separately. Inspect optimized assembly for exact sizes, addresses and order. Time a serialized dependent chain separately from an independent-work loop on the same Zen 3 core. Excess latency isolated to (c)/(d) is consistent with forwarding failure; no measurable excess for the production-relevant shape, or complete hiding by independent work, rejects it as a useful explanation there. A serial chain shows possible latency, not production throughput loss. Keep every access within a live object and allocation; do not read padding or uninitialized bytes.
2. **Page-offset alias.** Use distinct valid buffers with a producer store and independent consumer load. Compare different addresses with equal low 12 bits against offsets that differ in low 12 bits; include a no-store arm. Verify the addresses and assembly, and construct the arm so an older store address can remain unresolved when the load is ready to issue. If the emitted dependency/order does not permit that condition, a null result is inconclusive for the mechanism. Hold computation, useful bytes, alignment, line/page footprint and residency comparable. Changing bits 11:6 also changes L1 set selection, so rotate/counterbalance address pairs and set occupancy; control page count, vectorization and allocator effects as well. Only a timing difference that tracks the low-12 match after these controls supports the hypothesis. No difference can reject materiality for that tested shape only when the unresolved-store condition is met; timing still does not identify a PMU event or prove the production path has the pattern.

For both: pin one worker, hold compiler/options and data fixed, use finite repeated process timings and report individual values/spread. Assembly inspection matters because C/C++ can be register-forwarded or transformed. A timing result can support or reject the hypothesis only for the verified shape and conditions tested; it cannot identify a PMU event, prove current code suffers, or establish DRAM/arithmetic saturation. A later quantized-path comparison must preserve values, output encoding, scale interpretation and rounding.

## Limits and conditional use

AMD 56665 is a vendor guide; its public landing page exposes a ZIP, not searchable page text. Fog does not identify a 5600X-specific test receipt, variance, or contribution to a larger loop. Thus ~10 cycles is a shape-level indicator, not a total-loop prediction. Neither source shows that the selected CPU expert pool is on a useful-compute critical path or that these hazards occur in frozen/current code. Intel's alias counter cannot fill this AMD evidence gap.

This is distinct from the prior indexed Zen 3 multirow-kernel and counter-free cache/DRAM collections. At most two follow-ups are conditional:

- **Partial-overlap forwarding discriminator — `schedulable_now: false`.** Require source and emitted-code evidence of a partial-overlap store/load edge in a hot pack/dequant loop, plus CPU attribution identifying that interval as useful critical-path work. If met, pin exact encoding/parity rules before comparing the forwarding shapes.
- **Page-offset alias discriminator — `schedulable_now: false`.** Require source and emitted-code evidence of distinct in-flight stores and same-offset independent loads in a hot path, plus CPU attribution identifying that interval as useful critical-path work. If met, compare controlled page-offset arms while preserving object lifetime, alignment, page residency and all quantized values/rounding.

No source change, benchmark, PMU session, profiler, local speed estimate, model qualification or hardware-saturation claim follows from this report.
