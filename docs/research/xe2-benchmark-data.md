# Xe2 memory compression and microbenchmark data representativeness

**Classification:** knowledge collection. **Scope:** Arc B570 (Xe2-HPG/Battlemage), device allocations and GPU-produced tensors; no runtime experiment. **Use:** retrieval reference for deciding whether synthetic constant operands can stand in for real BF16/Q8 inputs. Sources checked 2026-10-29.

## Finding

The observed component result (zero Q/K, constant V, Page16; 6,491 selected IDs; 36 samples; wall ratio 0.879438) and frozen model result (real Q/K/V, Page4; 12 QSA layers, 117,488 engine rows, 384 prefill slots, GPU residuals; 24 requests passed gates; paired/original time ratio 1.161284) establish a representativeness gap, not a mechanism. Neither result contains physical-memory traffic or saturation evidence. Do not infer that zero data compressed, that the model loss is caused by compression, or that requested bytes equal external-memory traffic.

**Evidence levels matter:** Intel identifies Xe2/Battlemage and advertises “8:N Compression” among render-slice changes for the B570/B580, but this is not a statement that arbitrary SYCL global-memory loads/stores of device USM are transparently compressed. Separately, Intel Compute Runtime source has a debug setting named `EnableUsmCompression`, described as enabling compression support for Level Zero USM **Device and Shared** sides (`-1 default, 0 disable, 1 enable`). This source declares a debug setting whose description names those classes, not the installed build’s effective setting, allocation/kernel-buffer eligibility, BF16/Q8 eligibility, or actual compressed traffic. The source also defines `FormatForStatelessCompressionWithUnifiedMemory`, indicating format/policy matters. [Intel B570/B580 Media Deck, Xe2 slide](https://download.intel.com/newsroom/2024/client-computing/Intel-Arc-B580-B570-Media-Deck.pdf); [Compute Runtime debug variables, `master`, observed 2026-10-29](https://github.com/intel/compute-runtime/blob/7954bf2e2c56741cb2b4fa101844a2ce5b1b8544/shared/source/debug_settings/debug_variables_base.inl).

Intel’s Xe-HPG article describes unified lossless compression for color/depth/stencil, media and compute, with compressed or uncompressed L2 storage. It is earlier silicon: evidence of Xe-HPG capability, not a guarantee for Xe2 B570. Conversely, Xe2’s render-slice label does not prove compression is render-only; public sources do not settle general USM coverage. [Intel Xe-HPG architecture article, L2 Cache, Compression, and Memory](https://www.intel.com/content/www/us/en/developer/articles/technical/introduction-to-the-xe-hpg-architecture.html).

## Mechanisms and counterexamples

- **Lossless memory compression (conditional, unresolved here).** If a hardware/runtime path compresses eligible cachelines/pages, constant or low-entropy bit patterns can reduce backing-store traffic/capacity; real BF16 activations or Q8 values may compress less. But BF16 zero/constant payload is only a candidate pattern. Compression may be disabled, restricted to particular allocation/resource formats or usage, not triggered for generic stateless accesses, or ineffective at the actual granularity. Real-valued tensors can also be compressible. GPU-produced versus host-initialized is not itself a proof of eligibility: the allocation/resource metadata and access path are more probative than who wrote the bytes. No source reviewed establishes that `malloc_device`/`zeMemAllocDevice` output of arbitrary SYCL stores gets Xe2 lossless compression.
- **Cache residency and address reuse (well-established mechanism; independent of values).** A repeatedly reused working set that fits in a cache can avoid backing-memory reads; a larger or differently mapped working set can miss. Repeating the same all-zero input at the same addresses can therefore make a microbenchmark “warm” even if data values are irrelevant. Same shapes and nominal bytes do not control address footprint, cache priming, reuse distance, or competition from weights/KV. Intel describes Xe2’s L1/L2/L3 hierarchy and oneAPI guidance explicitly notes cache miss/access-pattern effects; its cache hierarchy does not say equal-valued bytes are free. [Intel Xe2 cache architecture (Core Ultra 200V datasheet, Rev. 004, May 2025)](https://cdrdv2-public.intel.com/829568/829568-004.pdf); [Intel GPU optimization guide, cache/access discussion](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2025-0/multi-stack-gpu-architecture.html).
- **Data-dependent execution (possible only where code makes it so).** Sparse attention may derive masks, selected blocks, valid-length bounds, or skips from indices/metadata; values can also influence explicit predicates, early exits or routing. All-equal Q/K can collapse attention scores, while constant V can make reductions/output uniform, but this does not automatically remove dense dot-products or memory operations. If dispatch, loops, masks and work counts are fixed independently of tensor values, the operand bits alone do not change the algorithmic operation count. The cited public Xe2 sources do not claim value-sensitive generic execution for BF16/Q8 kernels. Check kernel branches and actual executed work separately from memory effects.
- **Numerical/data-generation confounds.** All-zero Q/K and constant V change score distributions, softmax outputs, accumulation patterns and potentially NaN/underflow/exception behavior relative to real model tensors. They can also accidentally simplify CPU-side compression, initialization or validation helpers if those are timed. Keep such preparation and reference checks outside the kernel timing unless measuring them.

## What would establish applicability on this B570?

A claim about this workload needs the exact GPU PCI ID/family and OS; kernel/driver, Level Zero loader/runtime and Compute Runtime package versions/build; SYCL compiler and IGC version; environment/debug settings including effective compression controls; selected device and allocation API/class; allocation size/alignment, residency and memory region; resource/format/usage and relevant kernel addressing/surface mode; whether host copy, GPU fill, or kernel production initialized it; and the actual launch shape, reuse order and competing working set. Runtime evidence should establish the allocation’s compression eligibility/metadata or expose an applicable compression counter/trace, and a documented counter should distinguish bytes requested from bytes actually moved. Availability of a runtime knob is not an observation that it is set or honored for a given allocation. Intel’s SYCL/Level Zero documentation distinguishes device USM (device-resident, explicit copy), host USM (host-resident/remote access) and shared USM (migration possible); allocation kind/location therefore must be recorded before extrapolating device-USM behavior to a buffer. [Intel Level Zero backend guide, Memory](https://www.intel.com/content/www/us/en/docs/dpcpp-cpp-compiler/developer-guide-reference/2025-2/programming-with-intel-oneapi-level-zero-backend.html); [Intel USM allocation guide](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2024-2/unified-shared-memory-allocations.html).

The Compute Runtime source URL tracks moving `master` and names controls, not B570 effective configuration. Public docs give no arbitrary Q8/BF16 compute-buffer contract. Deployed runtime/IGC revisions, allocation metadata, physical-memory/compression/cache counters and saturation evidence are unavailable for these runs. B570 Xe2-HPG discrete GDDR6 is not Xe2-LPG integrated graphics; older Xe-HPG/Xe-HPC and other vendors do not fill this gap.

## Small matched controls (future measurement, not run here)

Hold source/binary, dispatch, dimensions, strides, precision, allocation class/alignment, synchronization, warm-up, timing boundary and number of launches fixed; validate output separately. Use separate processes or explicit data parameters, never runtime environment mutation after initialization.

1. **Operand entropy, same addresses/footprint:** compare realistic captured BF16/Q8 operands against all-zero and repeated-constant operands, then a deterministic high-entropy pattern. Keep selected IDs/masks/valid lengths and dispatch fixed. If timings track value entropy, that is consistent with compression or value-sensitive code, but alone distinguishes neither; identical timings weaken a large data-dependent effect for this case, not all compression.
2. **Cache-size and priming crossover:** for each operand class, sweep a working set below/around/above the documented device cache capacity (account for all tensors and concurrent reuse) and compare immediately reused versus explicitly displaced/cold data with the same kernel. A benefit that follows footprint/priming across all value classes supports cache residency; a value-only delta at matched footprint keeps compression or code predicates in scope. Include real-model-style competing weight/KV footprint; do not call the result external-memory traffic without counters.
3. **Production versus preinitialized inputs:** compare host-initialized then copied tensors with GPU-produced tensors in the same device allocation, and GPU-produced real versus GPU-produced constant tensors. Exclude producer/copy cost from the consumer-only interval, then optionally report end-to-end separately. A producer-origin effect points toward allocation/resource/access-path state or cache priming, not proof of compression; no effect falsifies a large origin effect under that exact setup.

Repeat clean independent processes and preserve individual samples/spread, including first-use and warmed cases. Keep the real Page4 end-to-end model comparison as the relevance check: microbench controls can discriminate a mechanism but cannot qualify model throughput or adoption. Do not change driver, safety, cache or compression knobs as an adopted optimization on this evidence.
