# このワークスペースの性能比較

モデルの性能比較には、上流が提供する `bench.sh` とその Python クライアントを変更せず使う。
上流、XeStrata、ローカルの候補を同じクライアントのリビジョンで測定する。
モデルの設定は各構成で調整し、起動コマンド、実際の設定、環境、モデル・バイナリ・ソースの
識別情報を記録する。上流の箱出し設定だけで最適値と判断しない。

専用のサーバーを `127.0.0.1` に起動してから、上流の worktree で実行する。
クライアントの `--url` を指定し、サーバーの起動と終了は測定の管理側で行う。

```sh
./bench.sh --url http://127.0.0.1:18095 --long --runs 3 --out /path/to/results
```

測定には上流の通常のプロンプト生成、HTTP リクエスト、集計を使う。
独自の GEN プロトコルや独自の入力でモデルの速度を代替しない。
小さなカーネル、転送帯域、プロファイラーの測定は、原因を調べる補助測定として扱う。

## 結果の判定

`--long` は約 32K の入力を追加する。比較ではラベルだけでなく、各リクエストの実際の
入力トークン数と再利用数を確認する。32,768 トークン未満の試行は長文の採用判定から外し、
結果自体は残す。短い入力や agent セッションの結果は補助結果として残す。
64K を追加する場合は測定方法の変更を明記する。

prefill と decode は別々に判断する。少なくとも 3 回の個別試行、中央値と範囲を残し、
ばらつきで判定できなければ反復を増やす。長文リクエストの decode は `results.json` の
個別データを使い、短い chat の decode と混ぜない。標準の長文出力上限は 24 トークンなので、
実際の出力数も記録する。

初回の診断では GPU の経過とエラーを記録し、速度の判定にはログや検証の負荷を分けた
測定を使う。各ジョブに期限とログ容量の上限を設定し、所有するプロセスの終了と GPU の
前後の状態を確認する。クライアントの終了コードに加えて、結果内の失敗リクエストも確認する。
途中停止や障害の結果を正常な速度試行に変えない。

生成文の完全一致は品質の必須条件にしない。速度測定と品質評価を分け、精度や計算経路を
変える候補は固定履歴の尤度・分布とタスク成績で評価する。
以前の独自測定は履歴として残し、新しい HTTP 測定と同じ集計に混ぜない。
最大コンテキストを設定できたことと、物理的な 256K 入力を検証したことも区別する。

個別結果、設定、エラー、終了の証拠を Git のレポートに残す。
必要な証拠を抽出して確認した後、重複した成功ログを削除し、パス・ハッシュ・理由を記録する。
