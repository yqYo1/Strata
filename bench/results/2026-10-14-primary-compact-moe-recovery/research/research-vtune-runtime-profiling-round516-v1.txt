## Decision

Use the primary-owned exact-runtime Level Zero trace as the first device diagnostic, after Main's clean unprofiled 32K measurement is closed. Admit that trace with a small existing 64-handoff L0 health fixture first. The local unitrace 2.4.0 binary and a source-built VTune 2026.4 installation are present, but neither has been demonstrated here against the current model binary/runtime. The health fixture must use the exact current v711 stack before a model request is admitted.

VTune XPU Offload is the requested secondary view, conditional on a bounded smoke proving that this installed collector records the current B570 + custom SYCL/UR/L0 stack. VTune GPU Hotspots hardware-counter collection is not the route: the current Intel support list does not establish consumer Arc B570 support (it lists Arc Pro B-series), and this host has Xe observation restrictions. No sysctl, group, driver, or counter-permission change is part of this plan. If XPU Offload does not produce a complete linked timeline, preserve that as unavailable and use the PTI trace if it passes. Do not retry VTune CPU sampling: prior host records show software sampling denied at `ptrace_scope=1`, and `perf_event_paranoid=4` blocks unprivileged PMU sampling. Use application phase wall/thread CPU clocks as the decode fallback, with their instrumentation overhead recorded.

The question is the current main-root response path, not isolated peak capability: whether FP16 expert GU/down GEMMs, expert dequant/gather, staging/copies, host queue gaps/waits, or CPU decode consume the serialized critical tail. Existing roofs (host RAM 36.87 GB/s, H2D 6.447 GB/s, D2H 5.643 GB/s, logical VRAM copy 330 GB/s, hot/rotating GEMM and CPU FMA figures) are synthetic ceilings or separate microbenchmarks. They are context only and do not identify this request's limiting component. The old 343.8 versus current 175.3 prefill comparison remains unattributed; no oneMKL event or profiler kernel sum can settle it alone.

## Existing evidence to preserve

R511/R513 are proposals, not results. R513's source audit puts the ordinary route-table H2D and host synchronization before expert grouping; the synchronized `m.cnt` yields actual `T`, `K`, layer, and per-expert `ne`. In non-MMQ FP16 fallback, each nonzero expert submits GU `X[ne,N] × W[1280,N]^T` then Down `H[ne,640] × W[N,640]^T`; for the inspected recovery shape `N=2560`. Dequant and gather precede these calls. The pending exact `ne` histogram/call-site proposal owned by Sol is the source for shape/route joins; this report does not propose a second histogram implementation.

`STRATA_PREFILL_TIMING` phase buckets include queue idle/host gaps and explicit waits can coexist with other work. Its GEMM buckets are not exclusive kernel service. A returned oneMKL event's profiling interval may refer to an internal/last action, not the complete BLAS operation. Keep these separate: host wrapper submission duration; each event-associated action if already available; profiler kernel/copy records; complete operation dependency tail; and clean request wall time. Never sum overlapping kernel intervals into operation latency or align unrelated host and GPU clocks by subtracting timestamps.

For decode, `STRATA_DECODE_TIMING` is an existing host-wall window report that can count pool/wait/host categories but does not identify worker CPU service, DRAM traffic, or which device/event reaches the final token. `STRATA_VERIFY_PROFILE` changes branch eligibility and adds stamps/readback, so keep it off. `STRATA_PREFILL_SERVICE_EVENTS` changes queue/copy policy and omits captured graph commands; do not use it as a substitute timeline. The 7.8 tok/s serving observation and historical short decode samples are end-to-end evidence, not attribution.

## Required joins and interpretation

For each trace, retain a compact ordered ledger: layer/chunk; actual `T,K,N,ne` histogram and route count; format/MMQ/compact state; GU/Down call order; actual kernel and copy names; profiler queue/engine; same-tool timestamps; host L0/UR call intervals; and any exported dependency/correlation IDs. Keep H2D bytes/duration, mapped host-USM reads, device-local cache hits, and copies as distinct categories. A mapped GPU read is not an H2D copy. Route counts or a frequent kernel name alone cannot assign cost to one expert.

Attribute a limiting phase only when a valid dependency chain puts it on the last-token/request tail. Identify overlap only from same-profiler timeline/queue records. If oneMKL internals cannot be linked, report internal rows `unattributed`; do not infer expert ownership by timestamp proximity. Keep oneMKL wrapper/event durations separate from operation tail and complete request wall. Compare profiler overhead against the immediately preceding clean same-request reference, but never use profiled tokens/s as performance evidence. No roofline/ceiling comparison is warranted until operation scope, bytes, and critical-tail join are evidenced.

Correctness/fault/progress is mandatory: normal READY, expected progress, full requested output count, DONE, normal QUIT/exit; record any request fault or async error unchanged. Confirm parent/child/process-tree exit and closed result before inspection. On timeout or uncertain device completion, close as a failed diagnostic, preserve the failure record and do not retry on the same live session. A successful profile with missing correlation is a valid completed request but an unresolved attribution result.
