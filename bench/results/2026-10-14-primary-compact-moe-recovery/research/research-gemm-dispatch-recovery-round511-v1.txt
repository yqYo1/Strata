Date: 2026-10-14. Read-only source, committed-report and primary-source research. No repository edits, build, test, GPU, profiler, cleanup, fetch, or Git mutation. The sole write is this requested report under the external research directory. I did not inspect `prefill-gemm-only-contract-root-v1/record.json` or broad private environment/log material.

## Finding

No source evidence establishes that the old and current FP16 GEMM compute different algebra, precision mode, or mathematical result. Their remaining plausible oneMKL dispatch distinction is the call layout/orientation: the selected old 1eb SYCL source calls DPCT's column-major GEMM with `(m=N,n=T,k=K, trans,nontrans)`, while current `src/prefill/sycl/gemm.cpp` calls the direct oneMKL row-major interface with `(m=T,n=N,k=K, nontrans,trans)`. Those are two representations of `Y[T,N] = X[T,K] * W[N,K]^T`, with `alpha=1`, the caller's `beta`, half inputs, float output, `K` input leading dimensions, and output row stride `ld`. The source/report audit records old `mm_default` as DPCT-mapped `compute_mode::unset`; current omits the argument, also `unset`. Both builds used oneMKL 2026.1 dynamic SYCL BLAS and sequential threading. Public API documentation defines shape/layout behavior, not an identical internal dispatch or accumulation order for those two call orientations.

The supplied 343.8 PP result (old 1eb, 4096, split off) versus 175.3 on the current FP16 older binary is a reason to investigate, not proof of an orientation effect. Source family, compiler and runtime differ, and the measurements do not isolate a GEMM factor. Do not attribute the gap to one kernel or oneMKL until a same-binary, same-runtime orientation A/B and then a component-level model check exist.

## Source and dispatch trace

- Current `src/prefill/sycl/gemm.cpp` SHA256: `0fe1904787462a4156185bc08b2076e047f9cf51d9517ede4c8f482fa76c5410`. `multiply()` validates the row-major span/shape, calls `oneapi::mkl::blas::row_major::gemm(queue, nontrans, trans, T,N,K, 1.f, X,K,W,K,beta,Y,ld)`, then calls `finish(stream,event)`. `Gemm::f16` selects this template directly. Native quantized weights are dequantized to FP16 in row tiles and then go through the same `f16` wrapper.
- Old selected source `.tools/pre-xe-1eb-source-v1/sycl/src/prefill/gemm.dp.cpp` SHA256: `11a2c943ccc323c328b58d99119d77b3b4ed95c92a0f680480bf5ede96bcb705`. The source's old SYCL `Gemm::f16` ends at DPCT GEMM with `transpose::trans, nontrans`, dimensions `(N,T,K)`, `W` as the first operand, `X` second, float `Y` output and `ldy`. The DPCT adapter routes this through oneMKL's column-major operation. Historical compile evidence and the R499 report pin this as the selected TU; the old build did not select an MMQ implementation for this route.
- Current MoE `src/prefill/prefill.cpp` computes `ne = m.cnt[e]` and `o0 = m.off[e]` for each routed expert in a prefill chunk. On the FP16 fallback it submits `f16(Xs + scratch_row*N, dq_gu[q], GU + scratch_row*1280, ne,1280,N)`, applies SwiGLU, then submits `f16(Hh + scratch_row*640, dq_d[q], Dm + o0*N, ne,N,640)`. Thus the variable row dimension is routed expert rows `ne`, not a fixed GEMM batch. This source tree has counters but the canonical retained material inspected here does not include an actual `ne` histogram for the target 64K workload.
- `GEMM_WS` is a 32 MiB region in prefill allocation and is passed to the wrapper, but the current `gemm.cpp` and old SYCL wrapper do not consume it in their oneMKL GEMM calls. It must not be treated as evidence of GEMM workspace use. This follows the supplied correction and prior source audit.
- Current tree SHA at inspection: `8d13cef8d9ca82887358d066d2e3d1982cb191eb`; worktree was clean. These are checkout hashes, distinct from the main process's live-binary/source receipt supplied with this task.

## Nearest meaningful experiment

After the current stock run closes, compare call orientation in an isolated probe using the *same* built probe binary and installed oneMKL 2026.1/runtime on the B570. One arm must use the exact current row-major argument form; the other the algebraically equivalent old column-major form. Keep data, pointer alignment, shape, `beta`, stream/queue, compiler flags, and all runtime environment identical. Start with the actual observed routed MoE shape tuples `(ne,1280,N)` and `(ne,N,640)` from representative target prompts; include the dense FP16 call shapes only as a separate series. Capture enough real `ne` observations to show frequency/tail regimes, then use a bounded set of their frequent and tail values for repeated alternating A/B samples. Verify numerical error, finite outputs, output stride and untouched padding. Measure API/host submission and event/device elapsed separately; do not turn verbose synchronous timing into the speed sample.

Use `MKL_VERBOSE=1` (or the oneMKL API's mode 1) only in a diagnostic process to confirm the actual GEMM entrypoint, dimensions, layout and compute-mode fields. Intel documents GPU verbose mode 1 as output without timing; mode 2 synchronizes and times, so avoid mode 2 in performance samples. Verbose output can establish high-level call/mode details; it does not identify the internal GPU kernel. Keep the actual `MKL_BLAS_COMPUTE_MODE` and relevant environment explicit in both arms. If row/column orientation gives a repeatable material difference on real shapes, only then consider a shape/role-limited wrapper branch and verify it in a same-condition long prefill run, with decode observed separately. A tie or unstable difference leaves the current wrapper in place.

This experiment isolates orientation and library dispatch. It does not establish which factor caused the historical model-level gap, since old/new compilers and surrounding prefill implementations remain different. If an orientation difference is not material, next work should profile cumulative FP16 GEMM share and staging/dequant/activation costs before trying another dispatch hypothesis.

## External primary-source techniques and limits

1. **oneMKL grouped GEMM is a real candidate API, not a speed promise.** Intel's 2026.0 DPC++ reference documents a USM pointer-array `gemm_batch` group API, including `sycl::half × sycl::half -> float`, per-group `m/n/k`, leading dimensions and scalars, and an event plus optional dependencies. A group of one GEMM per expert can represent distinct routed row counts (`m_i=ne_i`) while sharing the common `N,K` where applicable. This differs from strided batching, which expects a common shape and fixed strides. However current Strata reuses dequantized-weight slots and one current Xs gather scratch as it walks experts. A grouped call would need pointers/weights/outputs alive together through its event and a changed stage schedule; it is not a drop-in call substitution. The previous R496 isolated probe found one probe-specific 4-expert down-GEMM gain of about 2.85%, with most 2-expert cases slower and no model-quality result. Retain per-expert default until a fresh shape histogram, grouped-vs-separate probe on oneMKL 2026.1/B570, safe data lifetime, practical numerical/model checks and model latency support a dispatch.
   - Intel DPC++ [`gemm_batch` 2026.0](https://www.intel.com/content/www/us/en/docs/onemkl/developer-reference-dpcpp/2026-0/gemm-batch.html)
   - Intel DPC++ [`gemm` 2026.0 type/layout contract](https://www.intel.com/content/www/us/en/docs/onemkl/developer-reference-dpcpp/2026-0/gemm.html)
   - Prior committed project evidence: `bench/results/2026-10-14-pre-Xe-replay/research/research-fp16-grouped-gemm-runtime-quality-round496-v1.txt` and `research-fp16-gemm-effective-contract-round499-v1.txt`.

2. **Keep expert-size scheduling dynamic and shape-aware.** The vLLM HPC-Ops author post describes low-latency MoE as uneven, small per-expert GEMMs; its design builds a per-tile task map and uses persistent CTAs to balance uneven expert tiles. The same article describes fusing gather and other MoE stages, but the reported implementation is FP8 and NVIDIA Hopper-only. Treat it as an architectural source for the problem (uneven small work and launch/gather overhead), not a B570/FP16 kernel port or evidence of a SYCL speedup. For this fork, first record routed `ne` histograms and current phase costs, then test the smallest compatible lever (orientation or grouped API); a persistent fused MoE redesign would cross dequantization, activation, routing, storage and numerical contracts.
   - vLLM project technical post, [HPC-Ops MoE backend](https://github.com/vllm-project/vllm-project.github.io/blob/main/_posts/2026-07-06-vllm-hpc-ops.md) (particularly the shape/occupancy rationale and explicit Hopper/FP8 hardware limits).
   - vLLM primary API/source, [`get_cutlass_moe_mm_data`](https://github.com/vllm-project/vllm/blob/main/vllm/_custom_ops.py#L3598): routed top-k yields per-expert offsets, problem sizes and permutations for grouped calls. This is CUTLASS/CUDA plumbing and quantized GEMM; use it only as evidence that dispatch metadata should encode actual per-expert work.
   - SGLang-JAX author/project architecture page, [GMM-based Expert Parallel](https://github.com/sgl-project/sglang-jax/blob/main/docs/architecture/06-layers-and-attention.md#6521-epmoe--gmm-based-expert-parallel): explicit `group_sizes` for variable rows and CSR-like expert offsets; its Pallas/TPU algorithm is not portable evidence for oneMKL. This reinforces that a variable-row schedule needs exact offsets/counts rather than a guessed global batch.

3. **Do not borrow CPU-only GEMM JIT knobs for this GPU path.** Intel's author technical post on small-matrix JIT describes `MKL_DIRECT_CALL_JIT`/dedicated JIT as SGEMM/DGEMM features for CPU AVX/AVX2/AVX-512 with dimensions far smaller than this path's N/K. It does not establish an optimization for SYCL half inputs on B570. Intel's CPU batch GEMM post likewise does not transfer its performance chart to the GPU. Do not change CPU placement, compiler/runtime, or device assignment under this GEMM investigation.
   - Intel authors, [oneMKL small-matrix GEMM JIT](https://www.intel.com/content/www/us/en/developer/articles/technical/onemkl-improved-small-matrix-performance-using-just-in-time-jit-code.html)
   - Intel author, [Introducing Batch GEMM Operations](https://www.intel.com/content/www/us/en/developer/articles/technical/introducing-batch-gemm-operations.html) (CPU benchmarks; API concept only).

4. **Verbose mode is a call/mode diagnostic, not a kernel identity tool.** Intel oneMKL 2026.0 docs say GPU verbose reports enabled/selected compute modes, and API mode 1 does not time while mode 2 does synchronous timing. Use mode 1 to verify what the deployed runtime receives; don’t infer a hidden kernel name or use diagnostic timing as clean performance evidence.
   - Intel DPC++ [`compute modes`](https://www.intel.com/content/www/us/en/docs/onemkl/developer-reference-dpcpp/2026-0/compute-modes.html)
   - Intel C API [`mkl_verbose`](https://www.intel.com/content/www/us/en/docs/onemkl/developer-reference-c/2026-0/mkl-verbose.html)
   - Intel DPC++ [`GPU initialization/runtime costs`](https://www.intel.com/content/www/us/en/docs/onemkl/developer-reference-dpcpp/2026-0/onemkl-initialization-on-gpu.html)

## Decision

The actual old/current dispatch discrepancy remains **unmeasured**: row-major versus column-major is a credible, narrowly isolatable hypothesis, while the algebra and documented compute-mode default match. The historical model speed gap remains unattributed. Do not make a code or compiler/runtime change from the current evidence. First finish the current stock work; then run a same-runtime orientation A/B over observed routed shapes. Grouped GEMM stays an optional second candidate, informed by oneMKL's documented grouped API and the already mixed R496 result, but requires batching/lifetime design and its own latency/quality gate. Keep prefill and decode decisions separate.
