## Current fused lifetimes

At current root lines 1767–1776, the normal path calculates `gr_norm_rs(R, norm_weight, grs, xn16)` unless the previous residual write already produced the next norm. The down and inject projections consume `xn16`; `gr_mix_r` consumes `R`, `grs`, the norm weight and `gated`. After attention and MoE, lines 2660–2673 can call `gr_write_norm_rs`, which writes the residual and precomputes `grs` plus `xn16` for the next HC half. `normed=true` carries these values across GDN/QSA/MoE and into the next HC read. Therefore keep `grs`, `xn16`, and conditional `xn16_lo` in the outer allocation for this route. The proposal’s `GR_UNFUSED=1` premise avoids exactly this carry, so its all-HC scratch formula is not valid for fused GR.

The HC temporaries `lo`, `lo16`, `gated` die before the GDN/QSA/MoE region is used: down writes `lo`; SiLU writes `lo16`; up writes `gated`; then `gr_mix_r` consumes `gated`. Under BF16X2 HC, `lo16_lo` is also used only through the up projection and dies before that region. Those spans can be carved in the shared phase region, alongside (but disjoint from) the existing GDN, QSA and MoE sets. Keep `inj` outside: its projection is early, but `gr_write` / `gr_write_norm_rs` consumes it only after the attention and MoE phases. Keep the HC spans mutually disjoint while their kernels read/write them.

The embedding buffer is live only from embedding output through `gr_broadcast` into `R`, before the first HC mix writes `mixed`. Thus `emb` can share one outer `T*N) FP32 allocation with `bo`. `mixed` must stay separate: GDN/QSA projections write their output into `bo` while `mixed`/its converted forms remain needed by the layer’s later MoE. The older proposal’s `emb == mixed == bo` class is unsafe on this path. Do not alias `mixed` with `bo`.

Current QSA `q` and `attn` are distinct takes in the shared region and must remain distinct. Preserve existing KV state/staging ownership, sizing, and relayout fences; this recovery changes neither QSA shapes nor KV state. Also keep the current size/range validation at allocation and kernel boundaries.

## Candidate byte impact at the supplied 4096 FP16 case

For `Alloc::take`, each span costs `A(n,b)=align256(n*b+256)`. At T=4096, D=10240, LR=320, N=2560:

- HC phase scratch `gated + lo + lo16`: `A(T*D,4)+A(T*LR,4)+A(T*LR,2)=175,637,248 bytes` (167.5007 MiB).
- With BF16X2 HC, add `lo16_lo`: total `178,258,944 bytes` (170.0010 MiB). Keep `xn16_lo` outside with `xn16`.
- The safe `emb/bo` sharing saves one `T*N) FP32 take: `41,943,296 bytes` (40.0002 MiB).
- Given Main’s supplied existing phase-region size of 968,510,976 bytes (923.5 MiB), it remains the max: either HC scratch set above is smaller, so the phase region does not grow. Under that exact layout/accounting premise, potential requested-arena reduction is 217,580,544 bytes (207.5 MiB) without BF16X2 HC, or 220,202,240 bytes (210.0 MiB) with it.

This is a source-derived capacity opportunity, not measured savings or proof of allocation success. It assumes the supplied shared-region number is the same T/configuration and the candidate preserves its sizing inputs. It does not establish runtime peak VRAM, speed, or fit at another T. The phase count and carve must use the same new HC-set helper and `max(HC phase, GDN, QSA, MoE)`. Update `bytes_needed` consistently with its existing behavior: it conservatively counts the unfused `xn` span even though normal fused carve sets `m.xn=nullptr`; do not report this estimator as actual carve. Keep all products guarded before multiplication and preserve current `size_t` bounds; in particular, the old proposal’s simple `104320*T` expression is not sufficient protection. Account for allocator padding/alignment and optional low buffers.

## Scope and decision

A narrow fused-compatible proposal is plausible: move only `lo`, `lo16`, `gated` and optional `lo16_lo` into the already-maximized phase region; keep `grs`, `xn16`, optional `xn16_lo`, `inj`, `mixed`, and distinct `q`/`attn` as they are; make only `emb`/ `bo` share an outer span. Retain existing `GR_UNFUSED` behavior and decline any shape/configuration that cannot satisfy the same lifetime/layout guards, using the original allocation/carve as fallback. The exact requested scope specifically avoids requiring GR_UNFUSED for the candidate.

This should be evaluated as an allocation-only candidate first, with Main checking count/carve parity, default and declined paths, BF16X2 low-span behavior, normal fused carry across both HC halves, actual T tails, matrix and scalar attention, resident/streamed expert routes, borrowed relayout, and numerical equality/fault behavior before performance. No source change or adoption is recommended from this read-only proof alone.
