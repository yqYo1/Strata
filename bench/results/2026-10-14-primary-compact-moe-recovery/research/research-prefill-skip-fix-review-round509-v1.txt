## Reviewed ordering and conclusion

Current `release_to` flushes an open MMQ group, conditionally calls `give_back(consumed)` in threaded mode, calls `wait_issued(k)`, then records `used[sl]`, writes `used_of[sl] = sl`, advances `consumed`, and publishes the new prefix. This is the right minimal order for the identified host race in this source configuration:

- `flush()` queues the group's reads and records its shared last-slot `used` event, then installs the grouped `used_of` mappings.
- Publishing the prior `consumed` prefix lets an issuer that has reached its ring-capacity limit move. It does not release the skipped entry itself.
- The acquire loop in `wait_issued(k)` observes the issuer's release store after its `used_of[sl]` read and copy/event submissions. The following mapping write is therefore ordered after that read.
- The final `give_back(consumed)` publishes the skipped generation only after its event and mapping are installed. The issuer's capacity acquire orders any later slot reuse after that publication.

This also removes the need to rely on `ring >= MMQ_GROUP` to prevent a wait for `k` from deadlocking behind unreleased group capacity. It does not wait for the skipped payload to be read by compute. `wait_issued` waits for host submission, while the skip does not consume the incoming payload.

I found no new normal-path deadlock or race caused by this ordering in the reviewed single-producer/single-consumer route. In particular, the acquire can observe a later `a_issued` value safely because the issuer processes indices in order; reaching a value greater than `k` implies its mapping read for `k` completed. Repeated chunks preserve the same rule even though `stage_live` persists: each chunk has a fresh local issuer/atomics, and each subsequent producer reads the previous chunk's map before publishing its own index. On an early return, `IssuerJoin` sets stop and joins before `StagerDone` calls `finish`; an issuer waiting for ring capacity notices stop, while an issuer waiting on a staged job can finish that job because Stager workers remain active until `finish`. `wait_issued` itself has no stop escape, as do the existing routed waits; an asynchronous producer failure/hung source would already strand the consumer and is not made into a new ordinary-path failure by this change.

## Queue, event, and staging assumptions

The current `Prefill::init` assigns `m.copy = m.cs` (line 716 in the reviewed tree); no private copy queue exists in this path. The single compat queue is in-order. With the default `STRATA_SYCL_PREFILL_SAME_QUEUE` setting absent, `copy_events` is enabled even though the queue handles alias. `wait_issued(k)` ensures the copy and copied-event barrier have been submitted before the consumer submits the skip's used-event record on that same queue. In-order submission then places that used event after the skipped copy, and a future producer reuse waits on the latest used event. With explicit same-queue event suppression, the producer short-circuits the `used_of` read and queue order provides the device dependency; the added wait remains harmless. Compat's event state mutex protects the stored event object, but it is not the host map synchronization—the atomics and ordering above provide that.

A separate copy queue would need a distinct skip-side device dependency on the skipped entry's copy before marking its slot used. The reviewed fix alone does not establish that cross-queue dependency. This is outside this review's current source/configuration: `m.copy` aliases `m.cs`, and no queue/context change is part of R509.

Stager's host-buffer lease is separate. `issued_one(job, m.copy)` records `dma_done` after the host-to-device copy is submitted and releases the pinned buffer to the Stager workers; the skip fix neither releases that lease early nor bypasses `Stager::wait(job)`. The current same-queue ordering also keeps the skip used event after the DMA, so a later device-slot reuse cannot overtake that copy.

## Remaining validation gap and minimal diagnostic shape

This is a source-ordering review, not an executed race or functional result. R8's explicit `STRATA_PREFILL_RING=8` returns `STAGE` and keeps `stream_all`/threaded issue disabled, independent of `STREAM_MIN`; it cannot validate the fix. A short functional diagnostic can make the path eligible with a fresh process by selecting `STRATA_PREFILL_RING=16` (8 is the explicit routed-only opt-out) and setting `STRATA_PREFILL_STREAM_MIN` to a positive value no larger than the actual chunk `T` (greater than 1 avoids a zero-sized `stream_all_min()-1` fused tail). Keep `STRATA_PREFILL_ISSUER=1`; for the group case use a compatible native MMQ layer with `STRATA_PREFILL_GROUP_GATHER=1`. Verify effective `T`, ring, and branch activation in the process before interpreting results. Compare issuer enabled/disabled on the same diagnostic configuration for output/correctness, and ensure the exercised routing includes skipped entries and, for the group case, a skip after an open group. The stream-min override also feeds workspace sizing and path selection, so this is a functional diagnostic only; its throughput is not comparable with the default path. A short prompt alone does not guarantee the required skip/group interleaving, and the current source has no explicit counter proving that exact subcase ran. That remains the principal practical validation gap.

R504's scoped claim remains: the original skip path had a non-atomic `used_of` read/write race with event-enabled threaded issue; R8 did not exercise it; and that race is not evidence by itself for the historical GPU hang cause. R509 confirms the proposed ordering closes that host generation handoff in the current aliased, in-order queue path, subject to the functional validation above. No performance, race-sanitizer, or GPU correctness claim is made.
