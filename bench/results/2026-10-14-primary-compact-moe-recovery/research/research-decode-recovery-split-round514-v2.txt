## Updated conclusion

The split geometry conclusion remains: old selected `record_window` uses `G=(split_ && T>=2 && !batch_rec_) ? 2 : 1`; current source uses `G=(split_ && T>=2) ? 2 : 1`. For an ordinary speculative MTP verify window (`batch_rec_ == false`), `--spec-split` produces the same two contiguous groups in both: A `[0,ceil(T/2))`, B `[ceil(T/2),T)`. For batch-recognition, old deliberately keeps a single group while current does not. Both generators default split OFF; `--spec-split` opts in and `--no-spec-split` clears it.

The exact old selected overlay schedule is important. In `record_window`, it queues `pre(first_layer,A)`, then `pre(first_layer,B)`. For each layer it queues `post(layer,A)` and then `pre(next_layer,A)`, followed by `post(layer,B)` and `pre(next_layer,B)`. Thus the SYCL queue's ordered work for B's mixer/router can run while the CPU worker handles A's published expert misses, and the next A layer can run while B's CPU misses are being handled. `post` consumes the CPU result only after the matching ring/flag is ready. This is a real group-level host/device overlap opportunity, gated by actual CPU misses, worker service, and the existing event/ring path. The nearby `sh_fork`/`ev_fork_`/`ev_join_` logic is a separate shared-expert GPU queue overlap; it should not be mistaken for CPU routed-expert overlap. The source establishes an opportunity and the ordering contract, not how much overlap the measured arm achieved. Current split should be compared under the same MTP policy before attributing a result to this mechanism.

With split OFF, T=4 gives one four-row group; split ON gives two two-row groups. Per distinct CPU-miss expert, `ExpertJobMulti::nt` is the number of routed rows for that expert in that group, so it is at most 4 with split OFF and at most 2 with split ON. Old selected `expert_source.cpp` scans the rows in its group, deduplicates CPU-miss expert IDs, attaches each matching activation/output row to that expert's job, publishes the expert plan to the host service, and later waits for that group's CPU rows before combine. The compiled CPU implementation is the root `src/kernels/cpu/native_expert.cpp` and `pool.cpp`; it quantizes activations once per token, executes the job's gate/up and down rows, and batches native jobs through `run_split_multi_native`. Both group policies retain group-local dedup: splitting can lose cross-half reuse of a repeated expert while making the above overlap available.

This supports a split-first experiment, not an adoption claim. Historical earlier-fork decode at 16.6 tok/s and current 2.5–3.7 tok/s short measurements do indicate a large observed performance gap across unlike configurations and phases; the three 24-token stock decode samples are insufficient for a causal or stable statistical estimate. Keep the recovery concern visible, and report the gap as unresolved rather than claiming either no issue or a measured regression.

## CPU dispatch applicability remains narrow

The earlier call-shape comparison survives when tied to the actual selected CPU source. The old stock CPU environment had the default `STRATA_IQ_MT_MIN=2`; the current canonical stock environment has `STRATA_IQ_SINGLE_EXACT` absent, so its parser returns false. At these defaults on the AVX2/no-AVX512 Ryzen 5 5600X, IQ IDs 16 (IQ2_XXS), 17 (IQ2_XS), 18 (IQ3_XXS), 21 (IQ3_S), 22 (IQ2_S), and 23 (IQ4_XS) all use GGML `vec_dot` at nt=1 and AVX2 multi-row kernels at nt>=2. The row-kernel identity is therefore the same for a given `(type,nt)` old/current in this measured environment. NT1 exact is a current opt-in limited to GU IDs 18/21/22; it is inactive in stock, does not handle down rows, and cannot be used to explain the stock difference. `STRATA_IQ3S_MT1` is a different historical opt-in and was absent in the accepted old stock environment. The old Q8_K AVX2 activation quantizer is a distinct shared per-token/layer component absent from current native quantization; measure and prove byte parity on its own.

Do not use IQ22/IQ20 NT1→4 pool measurements (90.98→38.74 us/expert-token) as all-format or model-decode evidence. CPU FMA 0.818 TFLOP/s and RAM read 36.87 GB/s are contextual measured limits, not an IQ integer roofline.

The selected old verifier's phase flow is specifically the SYCL ring/doorbell implementation. During `pre`, it publishes routed inputs/IDs and signals the pool-side service. In `post`, it consumes the device/PCIe/CPU result classes and waits for the relevant group completion flags before combining. The native shared expert may be forked to `sh_cs_` and joined with its own events. These are distinct overlap mechanisms and should get separate counters/timings in a future bounded diagnostic. The source does not support a claim that every `--spec-split` workload improves decode, nor a claim that a single GPU-only phase number accounts for CPU service.
