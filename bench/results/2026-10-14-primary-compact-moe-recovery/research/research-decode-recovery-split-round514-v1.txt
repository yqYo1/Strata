# R514 — decode recovery: verifier split and CPU expert dispatch

Date: 2026-10-14 (Asia/Tokyo). Read-only source and primary-source review for the supplied `feature/sycl` checkout at `8d13cef8d9ca82887358d066d2e3d1982cb191eb` and frozen pre-Xe source snapshot `.tools/pre-xe-1eb-source-v1` (1eb lineage, not Xe). No source/build/test/GPU/profiler/Git/cleanup/fetch/service operation was performed. I did not access the prohibited prefill contract record or broad private environment/session material. Only this report was written.

## Finding and boundary

There is no causal or statistical evidence yet that decode regressed. The matched-same-client old stock record is 32,049 input / 24 output / chunk 4096 / split OFF: prefill 343.8 median tok/s and decode 7.3, 4.1, 2.8 tok/s across three short samples. Current FP16 stock is 175.3 prefill and decode 2.8, 3.7, 2.5. These three decode values are too few and unstable to support an adoption claim. The older 449.698 prefill / 16.635 immediate decode result is a different phase and configuration (32,768 / 64, chunk 8192, compact2, layout1, speculative4, split ON); 22.165 RESTORE is a different phase again. Do not use these as a controlled before/after.

The most useful candidate is still a one-factor split-on/off decode comparison, because the old accepted tuned arm had `--spec-split` and the current short stock arm had `--no-spec-split`. For ordinary MTP verify windows, the actual group geometry is the same when both are ON: two contiguous groups, A=`[0,ceil(T/2))`, B=`[ceil(T/2),T)`. The old selected native verifier has `G=(split_ && T>=2 && !batch_rec_) ? 2 : 1`; current has `G=(split_ && T>=2) ? 2 : 1`. The difference is batch-recognition only: old suppresses splitting for a batch-rec window; current does not. The MTP verify case under discussion is not that batch-rec path, so for it `--spec-split` has the same two-group partition. CLI parsing in both generators sets the flag only for `--spec-split`; default is false, and `--no-spec-split` explicitly clears it.

With split OFF, T=4 has one four-row group. With split ON, it has two two-row groups; for odd T the first gets the extra row. In the old schedule the group A/B expert and mixer/router phases are interleaved to overlap CPU expert work for one group with device work for the other. Current has the same two-group shape and group-indexed work arrangement. Both complete host-visible work through their established stream/event completion; this source comparison does not reveal a missing wait or justify a split correctness change. Split changes QSA/attention batch row sizes and launch count too, so the A/B result measures the full split policy, not only CPU experts.

## Selected CPU expert call shapes

For each verifier group, `expert_source.cpp` creates a job for each distinct CPU-miss expert and appends each routed token activation/output belonging to that expert. Thus `ExpertJobMulti::nt` is the number of rows for that distinct expert in the group, bounded by group rows (not `T*k`): split ON at T=4 means nt≤2; split OFF means nt≤4. Duplicate routes to one expert in one token are not expected in top-k output, and device/cache hits do not enter the CPU job. CPU activations are quantized once per token/layer before the job pool; gate/up and down kernels receive packed weights and quantized activation rows. `run_split_multi_native` batches experts into bounded chunks and splits GU and down row ranges into pool tasks. Both old and current implementations deduplicate per group, so split ON creates independent job sets for A/B and loses cross-half expert reuse in one CPU job, while enabling CPU/device overlap. Route overlap, miss ownership, and actual nt histograms are not present in the retained stock summaries.

The old and current native call contracts are close for these jobs, but not identical in policy. Both dispatch by `gu_type`, `d_type`, actual `nt`, AVX ISA availability, `STRATA_IQ_MT_MIN` (default 2), and per-format support; both use GGML `vec_dot` fallback. The old pool uses `3*(workers + host participant)` task granularity for multi-token phases. Current uses `phase_tasks(rows)` and caps task count to row count; default `--pool-tasks=0` maps to the normal 3x participant policy with that row cap. This is a narrow secondary comparison; no evidence says pool granularity explains the timing values.

For IQ gate/up rows on this Ryzen 5 5600X (AVX2, no AVX-512), at default mt_min=2:

| GGML type | ID | nt=1 old / current | nt≥2 old / current | Notes |
|---|---:|---|---|---|
| IQ2_XXS | 16 | GGML / GGML | AVX2 multi / AVX2 multi | Current NT1 exact helper does not support it. |
| IQ2_XS | 17 | GGML / GGML | AVX2 multi / AVX2 multi | Same NT1 limitation. |
| IQ3_XXS | 18 | GGML / GGML | AVX2 multi / AVX2 multi | Current exact NT1 supports it only if explicitly enabled. |
| IQ3_S | 21 | GGML / GGML | AVX2 multi / AVX2 multi | Current exact NT1 supports it only if explicitly enabled. |
| IQ2_S | 22 | GGML / GGML | AVX2 multi / AVX2 multi | Current exact NT1 supports it only if explicitly enabled. |
| IQ4_XS | 23 | GGML / GGML | AVX2 multi / AVX2 multi | AVX2-only row kernel. |

The NT1 column describes the canonical measured stock setup, where `STRATA_IQ_SINGLE_EXACT` is absent and the current parser returns false. (R505's earlier statement that this stock arm pinned it to 1 is corrected by the current task's environment reconciliation; its source-level description of the opt-in's scope remains useful.) If separately launched with `STRATA_IQ_SINGLE_EXACT=1`, current adds only an NT1 gate/up fast route for IDs 18, 21, 22; it consumes packed IQ rows and the Q8_K activation and preserves GGML reduction order, with an existing bitwise test source. This is not a generic dequant path. That knob does not select down-projection or the NT≥2 route, and cannot explain the absent-env stock arm.

A split ON MTP4 window can therefore change per-expert CPU nt distribution from up-to-4 rows to up-to-2, and it can affect the NT1 share as experts are distributed between halves. However, both implementations at the recorded defaults use GGML for NT1 and AVX2 multi-row for nt≥2. In this exact stock environment, the IQ row-kernel identity for a given `(type, nt)` is consequently the same old/current. The noteworthy source-level differences are (a) split overlap/group-local dedup policy and (b) current's opt-in NT1 exact path, which is inactive here. The older `STRATA_IQ3S_MT1` was also opt-in and absent in the recorded old arm; it must not be conflated with current single-exact.

Separate but potentially recurrent: old `native_quant_act` and `native_quant_h` have a Q8_K AVX2 activation quantizer guarded by AVX2 support and `STRATA_NO_Q8K_AVX2`; current calls GGML `from_float` directly. This affects shared per-token/per-layer activation quantization, not the IQ row-dot implementation. Consider it only as its own CPU-only component with byte-parity and timings; do not bundle it with split or IQ dispatch.

## Recovery proposal

1. After Main closes the active stock run and schedules a future decode run, repeat the official same-client workload long enough for stable decode estimates, with alternating split OFF/ON order, same binary, input/output target, prompt/chunk, cache/resident geometry, CPU pool, MTP settings, and all environment settings. Do not change prefill knobs. Use actual generated tokens and report medians and individual samples.
2. At the same time, collect non-invasive, bounded per-window counts: T and G; for each native layer, distinct CPU-miss expert jobs and their `(gu_type, nt, d_type, nt)` histograms; CPU cache/refusal/hit counts; drafts offered/accepted; verify rows; and CPU quant/GU/down phase time versus device/event phase time. This will show whether split trades cross-group batching for useful overlap or simply changes the workload. Do not infer MTP proposal count from lookup rows.
3. If split helps, keep that as a decode verify-policy result and check token/logit correctness plus cancellation/bounds and repeated long-output quality. Do not call it a restoration of the full historical 16.6 tok/s. If split loses, keep it off for this workload and move to one isolated CPU component only when measured counts implicate it.
4. Candidate next CPU isolation: compare Q8_K activation quantization on/off on the same eligible CPU-only fixture or bounded engine diagnostic, first requiring byte-identical quantized activations; then measure call time. Separately compare current IQ exact flag only if stock counters prove NT1 jobs in IQ3_XXS/IQ3_S/IQ2_S. Keep current default false unless correctness, bounds, and whole decode latency justify enabling it. A per-format, nt-aware dispatch is preferable to a blanket adoption.
5. Do not set `STRATA_IQ_MT_MIN=1` as a speed restoration: it changes rounding behavior for nt1 and has a documented historical decode cost on a different CPU/format. Likewise, don't treat split alone or an old unpaired speed sample as proof.

Existing measured constraints are context, not an IQ integer roofline: CPU FMA 0.818 TFLOP/s and RAM read 36.87 GB/s were measured previously; prior IQ22/IQ20 pool work NT1→4 decreased from 90.98 to 38.74 us/expert-token, but it is not an all-format result and does not identify the current model's phase. Preserve those scope labels.

## External implementation references

These references support only general scheduling concepts. They do not establish a transferable performance result or a CUDA/HIP port obligation:

- SGLang's official [expert-parallelism guide](https://github.com/sgl-project/sglang/blob/main/docs/docs/advanced_features/expert_parallelism.mdx) describes two-batch overlap and single-batch overlap of expert/shared work with communication. Its EP/deep communication setup targets distributed GPU serving, so only the independent-work overlap idea maps here; do not import its backend or throughput claim.
- SGLang's official [CPU backend optimization roadmap issue](https://github.com/sgl-project/sglang/issues/8281) explicitly discusses CPU MoE prefill blocking and split-K, while its decode/MTP items are roadmap entries, not validated Zen3 results. It supports counting actual small work shapes before redesign, not a kernel adoption.
- The official [llama.cpp CLI documentation](https://github.com/ggml-org/llama.cpp/blob/master/tools/cli/README.md) documents expert placement on CPU (`--n-cpu-moe`) and CPU affinity controls. This shares CPU-resident expert inference context but is a different scheduler and does not supply a compatible batching kernel or matched measurements.
- Intel IPEX-LLM's [GPU inference guide](https://github.com/intel/ipex-llm/blob/main/docs/mddocs/Overview/KeyFeatures/inference_on_gpu.md) describes Intel GPU execution, not this Ryzen CPU expert path; no useful directly portable CPU MoE batch implementation was established in this search.
