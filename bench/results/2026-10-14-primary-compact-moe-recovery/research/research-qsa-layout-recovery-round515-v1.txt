## Comparison and concrete differences

The old measured arm had PP 449.674 t/s at 32,768 input / 64 output, context 262,144, chunk 8,192, compact=2, attention layout=1, MTP split enabled. Current comparison was the separate official stock 32,049 / 24 workload with chunk 4,096 and compact/split off; the MMQ=0 FP16 run measured 175.3 t/s. These figures demonstrate a recovery gap only. They do not establish that attention layout caused it. Old/current settings and binaries differ, and no QSA-only timing exists.

The concrete recoverable layout difference is in the fallback decode attention kernel. Old layout 1 dispatches `launch_chunk_variant<KV_MODE,32,true,false>`: local size 8x32, 64 selected cells per chunk, 12 query heads per KV head, and `TRANSPOSE_Q=true`. Threads first load the query vector linearly into local memory using a transposed lane/dimension mapping; score threads then read the transposed query while each lane loads eight adjacent K dimensions. Current fallback uses fixed subgroup 32 / work-group 256 and stores each query row linearly in local memory; its lanes load eight adjacent K and Q dimensions. Both compute per-64-cell chunk online-softmax partials and then merge partials in a separate kernel. So the narrow candidate is Q local-memory layout and its associated load mapping, not a different attention algorithm, cell chunk size, or selected-cell representation.

The old per-query batching default is 32 (clamped by T) and invokes the decode fallback on that batch when prompt attention is disabled or declines. Current prefill first tries its whole-chunk prompt attention kernel for all T; only when it returns false does it call the decode fallback in `m.attn_batch` slices. Thus a `layout=1` port is only exercised on the fallback route. It would not affect calls accepted by current `qsa_prompt_attn_batch`. Any comparison must prove the selected route, record the accepted chunk and fallback query batch, and either force the prompt kernel off through a dedicated test seam or compare only actual fallback calls. Do not assume a layout knob toggles an absent current selector.

The old SYCL range expresses (queries, KV heads, chunks) with chunk last/fastest for default variant 1. The current flattened group id recovers chunk first, then KV head, then batch; this yields the same logical chunk-fast ordering. Grid syntax is different but no ordering win is established here. Intel's XPU Triton backend describes layout and grid order as hardware-sensitive tuning parameters, including cache reuse opportunities, but its stated axis convention belongs to that backend and is not a measurement or contract for this SYCL launch. The source review therefore selects the query-local layout as the first hypothesis, not an axis-order rewrite.

Q, selection IDs, step metadata, and paged K/V have matching logical meanings in both paths: query-major rows, per-query IDs with `cap` stride, per-query step tuple, then page-table lookup per selected cell and KV head. Old layout 1 does not change these buffers or perform a KV gather. Both paths mask nonresident page-table entries and preserve partials for a separate merge. Current top-k selection is capped at 32,768 selected cells (`kTopkMaxCells`); this is not a cap on total context. Both designs can cover a 262,144-position context by selecting a sparse subset. No basis found to change admission/page streaming, tails, or storage lifetime as part of a layout port.

## Smallest candidate and gates

Candidate proposal only: add an opt-in current fallback attention variant that changes the query's work-group local-memory mapping to the old variant-1 transpose while retaining the current paged-row checks, current `size_t` indexing/span validation, current scratch layout, query/step/ID strides, format dispatch, score expression and reduction tree, chunk partial format, merge, and default prompt-kernel dispatch. Keep the existing fixed kernel as default. Do not transplant the migrated donor kernel wholesale; port only the layout mapping and required lane reads. Do not combine this with compact HC, chunk 8192, prompt-kernel routing, arithmetic, KV format, indexing, or queue changes.

Before any speed claim, Main should separately establish (1) a matched current fallback baseline and arm with the same binary aside from the variant, input, context, accepted prefill chunk, compact/MMQ/split settings, KV residency/admission, and MTP conditions; (2) output and residual parity, especially partial chunks and selected IDs containing final-tail cells; (3) bounds/lifetime safety for zero-width and irregular tails, cap=32768, near-context-end pages, masked/unresident pages, each enabled KV format, and multiple query batches; and (4) repeated PP samples under the official client. Record the precise fallback invocation count and shape counts by QSA layer so a few tail calls cannot be mistaken for the dominant path. A matched end-to-end gain would justify deeper profiling; source appearance alone does not.

Keep chunk admission as its own arm: compare compact=2 with compact off at the same admitted 4,096 chunk first; request 8,192 only after current allocator admission at the same context/KV/cache. Do not attribute an 8,192 improvement to attention layout. The historical old 1eb arm's separate chunk 8,192 and split-enabled setting remain confounders.

## Decision

The old QSA variant-1 query transpose is a concrete, low-scope recovery candidate with plausible benefit because it changes how each 256-element query is staged/read by subgroup lanes while leaving attention math/dataflow intact. It is not yet an adopted change and has no attributed performance result. A prototype is justified only after Main completes its currently owned matched-source/session work. If current prompt attention handles the official geometry, first prove it reaches the fallback; otherwise the variant cannot explain or close that workload's gap. Keep source/compiler, 1eb-vs-current build, chunk, compact, MTP, and split confounders explicit.

## Primary external references

- Intel XPU backend for Triton tuning guidance says tile/layout and grid ordering can materially affect performance and recommends tuning for hardware/shapes. This is an implementation-author reference for the general hypothesis, not direct evidence for this SYCL kernel: https://github.com/intel/intel-xpu-backend-for-triton
- Intel XPU backend architecture documentation describes explicit backend layouts and lowering to device-specific IR, supporting the view that lane-to-element mapping is a real implementation choice: https://github.com/intel/intel-xpu-backend-for-triton/blob/main/docs/ARCHITECTURE.md
- Intel oneAPI GPU Optimization Guide index covers subgroup vectorization, work-group size, register pressure, local memory, and reductions as separate performance concerns; it supplies tuning context, not a specific winning QSA layout: https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2024-2/kernels.html
