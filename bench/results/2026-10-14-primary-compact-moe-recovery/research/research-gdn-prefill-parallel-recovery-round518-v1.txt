## Finding: actual prefill algorithm

The public prefill dispatch in `src/prefill/prefill.cpp` computes the GDN projections over the whole current chunk `T`: mixed hidden rows feed `attn_qkv`, `attn_gate`, `ssm_alpha`, and `ssm_beta` projections. Then `gdn_gates` derives 48 scalar decay values and 48 beta values per token, `gdn_conv` applies the four-tap causal convolution using a three-step history and normalizes q/k, and `gdn_recurrence` runs the state update and output normalization. The output projection consumes FP16 `y_h`. These operations are queued in source order on the caller's compute stream. The convolution input positions are parallelized over token and channel; it reads the old history for all output rows, then an ordered kernel updates history to the final three inputs of the chunk.

`src/kernels/sycl/fused_gdn.cpp::recurrence` launches one work-group per value head (`hv=48` for the declared Strata geometry), each with 512 lanes, four 128-lane row groups, and 128 columns. A group loads its 128x128 state into 32 registers per lane. It then has a literal `for (t=0; t<n; ++t)` over chunk tokens. For each token it loads shared q/k, computes the state/key projection, forms the delta, updates its assigned state rows, computes q readout, then normalizes/writes the output. Barriers and local-memory reductions occur inside every token iteration. State for the prompt is updated at the end of the kernel. `single=true` permits arbitrarily large positive `T` up to the kernel's integer bound; it does not mean that the time loop is parallel. The `keep`/partial-verification route is a separate bounded mode and is not the normal prefill route.

Thus recurrence has broad parallelism across 48 value heads and the 128x128 state elements, but a single prompt has no batch dimension. Time dependence is sequential within each head. At the primary shape, one layer's state is 48*128*128 FP32 = 3 MiB, and the recurrent inner work is about 128x128 state update plus 128x128 q/k dot/readout work per token/head, with a serial step and several barriers per token. A rough lower bound is about 1.5 million FP32 multiply-accumulate operations per token per GDN layer before normalization, gate, convolution and projection costs. These are source-derived shape/work estimates, not measurements or a claim that recurrence dominates prompt latency. The current phase timer can distinguish `gdn recurrence`, `gdn conv+gates`, and `gdn out proj`; use that evidence before optimization.

The current GDN state in `SessionState` is FP32 (`float* gdn_state`) and initialized/copied as such. The per-token output consumed by `ssm_out` is rounded to FP16 (`y_h`); q/k/v and intermediate state remain FP32 in this recurrence. The output rounding does not make persistent-state narrowing an equivalent storage-layout edit. Any state-dtype change changes every subsequent recurrent update and save/restore representation.

## Parallel algorithm candidates and portability

1. **Keep current state dtype and recurrence, reduce launch/phase overhead first.** If a real phase profile identifies recurrence as costly, first consider small SYCL kernel-local changes that preserve the exact time order and FP32 state (for example, improved load/register mapping or fusing only compatible per-step work). This is the lowest-risk candidate, but it may not increase occupancy beyond the 48 head groups and cannot remove the serial dependence. Do not optimize based solely on theoretical arithmetic or device peaks.
2. **Chunkwise gated-delta algorithm (preferred architecture research candidate).** The Gated Delta Networks paper derives a hardware-oriented parallel training algorithm using chunkwise/WY representation. FLA's inference forward exposes this as a chunk kernel family: compute chunk-local gate cumulative sums and WY terms (`prepare_wy_repr` / `recompute_w_u`), do intra-chunk token-parallel work, then propagate chunk boundary state and produce outputs. The mathematical state boundary remains ordered across chunks, while time work within a chunk is parallel. For this one-sequence workload, this could expose more independent work than 48 head groups. Candidate chunk sizes in the FLA GDN API are 16/32/64; these are reference implementation settings, not justified Strata settings. A SYCL implementation would need its own work-group layout, intermediate scratch, stable triangular/WY solve, and exact state/output semantics. XMX/matrix instructions are optional, not a prerequisite; scalar/vector subgroup arithmetic and local memory are portable SYCL options, while Intel-specific matrix extensions are a separate capability-gated experiment. Do not import CUDA/Triton kernels or infer Arc performance from them.
3. **Associative scan of affine chunk transforms.** A recurrence's chunk can be represented by a state transition plus an accumulated write contribution, which composes associatively. A parallel prefix can reduce chunk-to-chunk depth, but each transition is a large matrix or structured operator; materializing/composing it may cost more bandwidth/work than it saves. This is a more speculative alternative to WY, not a justified first implementation for this 128x128 per-head state.
4. **Parallelize independent heads and overlap independent layers?** Head parallelism already exists. GDN layers are not independent because the layer residual and MoE outputs feed the next layer; do not overlap sequential layers by violating the model dependency. Batch requests could supply a batch axis in a service scheduler, but it does not improve single-request prefill without changing execution and memory admission.

A chunkwise prefill/recurrent decode split is an established design in FLA/vLLM: prefill processes chunks with a chunk algorithm and exports the final recurrent state; decode applies the one-token recurrence. vLLM documentation also notes prefill autotune/warmup behavior and keeps the decode kernel separate. This validates the architecture pattern, not a drop-in algorithm, measured Arc speedup, or matching numerical behavior. The current 4096-token chunk setting is an outer layer/MoE streaming chunk; it must not be confused with a proposed inner GDN WY tile size.

## State and lifecycle constraints

Any replacement must preserve (a) initial state and convolution tail, (b) exact prompt token order and final FP32 recurrent state, (c) GDN layer ordinal mapping and multi-chunk continuation, and (d) correct output for every token consumed by downstream residual/MoE and the MTP `on_chunk` callback. In particular, a partial final WY tile must not read beyond the actual token count or commit padded tokens into state. The existing callback runs per outer prefill chunk and uses the final residual rows; intermediate kernel tiles must not invoke it, expose partial state, or reorder rows.

Cancellation is polled at the outer chunk boundary. A failure or STOP after a chunk has advanced GDN, QSA, PLE, or MTP state must follow the existing request rollback/pending-commit behavior; do not publish partial final state or lose the old recurrent/convolution state. `Prefill::reset` synchronizes queues before releasing workspaces. Conversation checkpoint save/restore includes GDN recurrent state and convolution history; any changed dtype/layout needs matching snapshot formats, validation, and round-trip behavior. The current public snapshot semantics and R512 coverage remain required. A tile-level algorithm must preserve cross-chunk history/state even when outer `T` is smaller/larger than its tile.

## FP32 state and quality evidence

There is no applicable quality benchmark in the reviewed project record that compares FP32 versus BF16/FP16 persistent GDN state on this exact model, prompt distribution, context range and Arc B570 runtime. The ICLR 2025 paper establishes GDN's modeling motivation and evaluates model-level language/reasoning/retrieval/long-context tasks, but its reported model comparisons do not isolate inference-state precision for this checkpoint. FLA/vLLM kernel support for BF16 recurrent state is implementation capability, not evidence of equivalent quality on this Strata model. The SGLang report of CPU BF16 NaNs past roughly 4096 input tokens is a different CPU failure report and neither establishes a GPU defect nor supports narrowing this state. Therefore FP32 necessity for quality is unanswered; keep FP32 until an exact-model quality/numerical test supports a dtype change.

For the first chunkwise trial, keep FP32 state, gates, and beta and compare prefill outputs plus final state against current recurrence across short, odd, tile-boundary, multi-outer-chunk, and long prompts including 64K/256K where capacity allows. First establish elementwise/reference error bounds and deterministic logits/top-token behavior; then evaluate next-token logprob/perplexity on a fixed representative corpus, retrieval/needle and long-context tasks, plus long deterministic generation. Record all differences rather than requiring universal exact token-string identity; exact strings alone are neither a numerical oracle nor a quality benchmark. For any lower-precision state proposal, require a separate paired FP32-vs-candidate quality set (same prompts, decoding and seeds), perplexity/logprob deltas, retrieval/long-context and generation checks, long-horizon state drift/finite-value checks, snapshot save/restore round-trip, and performance plus memory evidence. No dtype adoption follows from faster isolated kernels.

## Smallest proposed trial and gates

No change is proposed for adoption now. First collect a clean current-path phase profile on this same model and configuration to establish GDN recurrence's share and call/shape counts. If recurrence is a material fraction, prototype one FP32-state chunkwise/WY GDN implementation behind a prefill-only dispatch. Keep one-token decode unchanged. Start at a single inner tile size chosen from measured chunk shapes; compare it to the current recurrence with identical inputs. Do not alter outer chunking, MoE gathering, state storage format, cancellation, or callback timing in the same trial.

A trial is reviewable only with: (1) source/compiler/runtime and effective settings pinned; (2) numerical comparisons of each token output and final recurrent/conv state, including multi-chunk and partial tiles; (3) identical QSA/PLE/MTP/256K boundary and cancellation/save/restore behavior; (4) current baseline and candidate prefill timing samples with identical model, prompt, outer chunk, cache/compact settings and clean processes; (5) decode measured separately and not regressed; (6) actual long-context capacity admission; and (7) model-quality checks described above. Adopt only if correct and repeatably faster in whole-model prefill with no meaningful decode, memory, or quality regression. Otherwise retain current stock recurrence.

## Research references and scope

- Yang, Kautz, Hatamizadeh, [Gated Delta Networks: Improving Mamba2 with Delta Rule, ICLR 2025](https://proceedings.iclr.cc/paper_files/paper/2025/file/4904fad153f6434a7bcf04465d4be2cc-Paper-Conference.pdf): gated delta recurrence, memory tradeoff, chunkwise parallel training algorithm and model-task evaluations. These are algorithm/quality context, not Strata runtime results.
- FLA maintainers, [GDN chunk forward implementation](https://github.com/fla-org/flash-linear-attention/blob/main/fla/ops/gated_delta_rule/chunk.py): production reference for chunk-size restrictions and orchestration of gate cumulative sum, WY preparation, intra-chunk forward, and state propagation. CUDA/Triton-specific implementation; no Arc timing claim.
- vLLM maintainers, [GDN linear attention implementation/API docs](https://docs.vllm.ai/en/v0.20.0/api/vllm/model_executor/layers/mamba/gdn_linear_attn/): separate chunk-prefill and recurrent decode paths; reports a fixed chunk size/warmup path. Platform and version differ from Strata.
- vLLM Intel-XPU maintainers, [XPU kernel configuration reference](https://github.com/vllm-project/vllm-xpu-kernels/blob/main/KERNEL_CONFIGURATION.md): demonstrates XPU-specific policy/build selection. Its documented chunk-prefill table is general attention, not direct evidence that its separate GDN algorithm is portable or faster on B570; a GDN XE2 path would need source-level review and independent validation.
- SGLang maintainers, [GDN attention backend documentation](https://github.com/sgl-project/sglang/blob/main/docs/docs/advanced_features/attention_backend.mdx): GDN uses a distinct linear-attention backend with separate prefill/decode implementation selection. CUDA backend constraints do not transfer to Strata SYCL.

No CUDA/HIP implementation, full engine, third-party release workflow, or upstream replacement is recommended. Niko1221/Strata remains the only upstream; XeStrata remains an optional reference. This round's new finding is the exact current SYCL per-head token loop and the bounded chunkwise candidate/gates above; prior project reports already cover prompt chunk state lifetimes, cancellation, checkpoint/restore scope and general phase-timer constraints, so those reports are referenced rather than duplicated as new findings.
