## Finding: the route counts are already host-authoritative

In current `src/prefill/prefill.cpp` (SHA-256 `484764fccef4cf58909bfe27fb01934da19dbffaca7f7be2565424d36ab86578`), the ordinary host grouping path first copies `T*K` routing IDs to host and synchronizes `m.cs` (around lines 2097–2105). It then clears `m.cnt`, validates each ID, increments `m.cnt[e]`, constructs `m.off`, and fills the expert-grouped `src` and slot tables (2118–2195). This point knows the actual `T`, layer `l`, `K`, every expert count including zeros, and the source order/offsets. It has already paid for the route-table synchronization; reading counts here requires no device readback or additional sync.

In the non-MMQ FP16 fallback, `compute()` consumes `ne=m.cnt[e]` and `o0=m.off[e]` (2547 onward). When `ne>0`, native or GGUF expert weights are converted to FP16, then it submits exactly:

- Gate/up: `X[ne,N] × W_GU[1280,N]^T`, via `Gemm::f16(..., ne, 1280, N)`.
- Down: `H[ne,640] × W_D[ N,640]^T`, via `Gemm::f16(..., ne, N, 640)`.

Here model `N` is the actual model embedding width (the inspected recovery context uses `N=2560`). The two operations apply only to experts present in `order`; zero-count experts have no corresponding FP16 GEMM. Their routed token rows sum to `T*K` for the chunk, but the expert count histogram includes zero experts. A record must therefore retain `T`, `K`, `N`, `layer`, and `ne`, not infer all shapes from a single batch size.

The capture must be placed specifically in this fallback after the `use_mmq` branch and at the FP16 `compute()` calls. Do not count MMQ grouped GEMM, fused native MoE, dense FFN, router/shared expert, or MTP work as these routed FP16 expert GEMMs. `K` is routing top-k here; each route contributes one row to one expert, so total active expert rows are `T*K`. The outer layer loop and chunk loop delimit distinct observations. `m.compact_moe_fp16` changes gather/scratch row addressing but not `ne` or either GEMM shape; report its effective value because stock is currently off and the pending OFF/ON comparisons must remain separately attributable. Keep model source format (`lay.native` versus GGUF; and relevant per-layer weight types), `use_mmq`, compact flag, and chunk capacity versus actual chunk `T` in the run header.

## Smallest bounded histogram proposal

Add an opt-in diagnostic flag (default off; fresh process only) around the host-authoritative count loop. Accumulate fixed-size counters in memory and emit one summary per measured invocation/chunk or, if output volume needs a tighter cap, per layer plus a bounded chunk aggregate. Do not print one line per expert or retain route IDs/tensors.

Suggested fixed 16-bin `ne` histogram: bin 0 for `ne=0`; exact bins for 1 and 2; then power-of-two ranges 3–4, 5–8, 9–16, ... up to the chunk limit (merge any overflow into a final `>2^13` bin when `T<=8192`; define ranges algorithmically from actual T). Include `n_expert`, zero-expert count, active expert count, `sum(ne)`, max `ne`, and row-weighted counts `sum(ne)` per bin in addition to expert-count frequency per bin. This bounded distribution tells the next experiment both which row sizes recur and how much routed work each interval carries. Emit the exact max and `T`; bins must not hide a rare large expert behind the count-only mode. For the target shape, include a deterministic derived work tally per layer/chunk and cumulative totals:

- GEMM calls: two per nonzero expert.
- Row-products: `sum(ne)` separately for GU and Down (equal for the pair).
- FP32-equivalent FLOPs estimate: `2*sum(ne)*1280*N` GU and `2*sum(ne)*N*640` Down (state explicitly this is shape-based FLOP accounting, not measured instructions or time).

The records can be a compact TSV/JSONL with a schema version, run identifier, source SHA, layer/chunk, actual `T`, allocation/capacity `T_max`, `K`, `N`, expert count, source format, MMQ/compact flags, both histogram vectors, max and row sum, and cumulative totals. Set a report-level cap (e.g. 1 MiB of diagnostic output, well below the project default 64 MiB raw-job log budget) and a maximum number of chunks/records; if exceeded, emit an explicit truncated/incomplete status and preserve cumulative totals to that point. Include a process owner/run identity in the actual measurement receipt. No raw tensors, IDs, full traces, repeated poll/sync logs, or normal successful API trace are needed. Record output hashes and deletion disposition per `docs/ARTIFACT_RETENTION.md` after the later run closes; do not cleanup any active run.

The most source-local location for histogram capture is immediately after the `m.cnt` construction and before `m.off`/grouping mutates order. Add timing/call accounting only at the FP16 call sites in `compute()`; preferably pass `ne` and route metadata into a narrow diagnostic accumulator there rather than summing every existing GEMM call in the binary. The insertion must be guarded so default execution creates no extra queue waits, event queries, logging, counters allocation, or output.

## Cost accounting: what is already measured and what it means

`STRATA_PREFILL_TIMING` currently creates CUDA timing events and labels compute-stream intervals by phase. At the routed expert path it marks `kPfDequant`, `kPfGather`, `kPfGemmGU`, and `kPfGemmD` around the relevant work (near 2537–2560). These are valuable phase totals, but the `PfTimer` comment and implementation define them as gaps between sequential event marks, folded after host syncs. A phase bucket can include idle gaps while the GPU waits for host grouping or an expert copy; `kPfWaitCopy` marks explicit waits, but total overlapping/copy work and host delays still make these buckets a GPU timeline breakdown, not exclusive kernel service time. The timing mode also records many events and shares the queue execution with the diagnostic. Do not report `kPfGemmGU + kPfGemmD` as isolated FP16 kernel time or call the phase percentages a complete MoE cost attribution. It is useful as a cumulative timeline baseline if same configuration, same flags and the existing `STRATA_PREFILL_TIMING` mode are used after the current clean OFF/ON run is complete.

For the SYCL GEMM, `src/prefill/sycl/gemm.cpp` SHA-256 `0fe1904787462a4156185bc08b2076e047f9cf51d9517ede4c8f482fa76c5410` obtains a oneMKL event from the row-major GEMM and passes it to `finish()`. With the normal non-null Strata stream, `finish()` does not wait; the wrapper discards the event and returns after enqueue. The compute queue is in-order. `src/sycl/runtime.cpp` already constructs its compute queue with both `in_order` and `enable_profiling` properties (lines 68–71); its transfer queue has only `in_order`. Thus current compute-queue event profiling is supported in principle, but no FP16 event is retained for later timing. Do not create a new profiling queue or change queue properties for the first diagnostic.

A minimal, conditional cost extension can retain the event returned by each of the two FP16 calls (or expose it via a diagnostic-only callback) and store it tagged GU/Down, `ne`, layer and chunk. Query `command_start` and `command_end` only after a later known completion point on this same in-order compute queue, then sum device elapsed times by GU/Down and optionally by row bin. Since the callsites execute serially on the in-order queue, the event durations can be summed as command service estimates; still label this as device event duration, not total model critical path. Avoid querying per call: profiling reads before completion may block, and forcing per-expert completion destroys overlap. The existing route-grouping sync at the next MoE layer can serve as a batch query boundary only if source control flow proves all recorded events on the queue have completed there; otherwise use the already-required end-of-chunk/stream completion, then query. Bound retained events by number of actual GEMM calls and the measured chunks; if that storage is too large, aggregate counts/histogram only and use existing phase totals instead. Validate behavior in a separate diagnostic run before treating the event totals as evidence.

Measure three quantities separately:

1. **Call submission time:** optional host `steady_clock` around each FP16 wrapper call, accumulated by GU/Down. This is CPU-side enqueue/API time and may include library/service work; it is not GPU execution time. Its instrumentation overhead must be reported.
2. **Device event duration:** `command_end-command_start` per retained FP16 GEMM event, queried after completion; sum by phase and shape bin. It excludes host preprocessing and cannot by itself determine end-to-end critical path.
3. **End-to-end/overlap context:** retain the existing `STRATA_PREFILL_TIMING` phase timeline and clean stock prefill samples separately. Report dequant, gather, waits, host grouping/staging, and total wall alongside FP16 event sums. Compare OFF and ON with the same clean-source/run settings only after current OFF/ON run is closed. Do not add profiling or logging to the clean stock samples.

The compact mode’s full-size source table and `Dm` placement remain unchanged, and Xs/GU/Hh scratch uses row zero per expert only when compact mode is active; this does not alter the row histogram. In the current supplied state, the clean accepted stock prefill history and compact source validation contain no retained actual routed `ne` distribution linked to the target workload. The next orientation/grouped probe should wait for this observation, then use representative frequent bins plus the observed maximum/tail values; do not substitute uniform random shapes or dense prefill T. The already-measured transfer and GEMM numbers in the task record remain measured facts, not unknowns or absolute ceilings.

## Recommendation and limits

After the active stock OFF/ON work closes, the smallest useful implementation is an opt-in fixed-bin host histogram at the already-synchronized `m.cnt` point plus conditional tagged FP16 event retention at only the GU/Down calls. Preserve clean stock runs as the timing reference. First compare the diagnostic’s own host submission totals, event elapsed sums, and current phase timeline for consistent counts/shapes and expected event completion. If event retention is judged too invasive, capture histogram and shape FLOPs first, and use the existing phase timeline explicitly as a non-exclusive proxy. The report is a proposal, not an implementation or measured result. Actual shape frequencies, event-timing overhead, call attribution accuracy, the best number of histogram bins, and grouped/orientation performance remain unmeasured.
