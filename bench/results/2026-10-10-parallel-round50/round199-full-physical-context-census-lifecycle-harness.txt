## Narrow recommendation

Use one opt-in diagnostic-only command mode in the generation driver, with two explicit phases in the same fresh session: (A) the ordinary production prefill route with bounded caller census at an actual `Prefill::run` count of at least 32,768 positions; (B) optional strict physical-capacity lifecycle qualification at exactly 262,144 positions. Do not make the census itself the proof of the full-context seam, and do not make a helper-only benchmark the model census. Keep the production route and arithmetic unchanged.

Prefer separate invocations for the census and each 262,144 split-control arm, each in a fresh process/session. This avoids contaminating measured ordinary prefill with giant lifecycle snapshots. If resource cost demands one process, each arm still needs fresh session initialization and complete reset receipts; a partially reset session is invalid. Store only bounded aggregate JSON/text receipts plus hashes and status. No full per-expert log or raw tensor dump is needed for the minimal harness.

## Actual 32K census contract

The CLI must observe `n_batched >= 32768` at the actual call `prefill.run(tokens, n_batched, 0, err)` (generate.cpp prompt path), not infer it from prompt length. For a plain-text ordinary CLI prompt use at least 32,769 prompt tokens so the normal final token remains in the token loop, then record exact `n_prompt`, `n_batched`, chunk `(c0,T)` and their reconciled sum. Freeze the actual model pack/hash, tokenizer assets and token-ID hash, route-affecting options, source/build identity, native-layout status and effective MMQ/fused/private-helper flags. The selected production IQ4NL path here is native IQ-to-FP16 followed by oneMKL GEMMs; source metadata alone does not establish calls.

The narrow census insertion is at existing expert route/call decision points in `sycl/src/prefill/prefill.cpp`, as specified in R195: bounded fixed-capacity host records allocated before timing; append one record for each positive expert decision (including bypass); no allocation, locks, text formatting, clock reads, per-expert wait, extra queue submission or event ownership in the measured path. Each record needs only chunk ordinal/c0/T, layer/expert, routed rows, loaded native `d_type` and dimensions where present, selected route/wrapper (including not-called), helper returned/incomplete status, compressed payload bytes, FP16 destination bytes, and staged/resident plus actual transferred bytes. Correct type-20 packed payload formula is `n / 32 * 18`; do not reuse R195's superseded `n / 256 * 18` or its impossible 32-byte all-fields record estimate. Compute `sizeof(record)` and checked capacity from the actual schema; overflow fails closed. Favor aggregate counters with route breakdown over retaining full records if direct invariant reconciliation can be done online with checked counters.

Summarize only after `Prefill::run` returns successfully. `Prefill::run` selects ordinary or layer-major execution and then calls `drain_pipeline`; success includes that drain, while a false return or failed drain is not a census pass. Preserve the causal distinction in the receipt: helper returned means its wrapper submitted and immediate check passed, not that async work completed. Async completion is admitted only by the enclosing completion/drain boundary and subsequent queue/fault checks; unknown completion, async error, process interruption, overflow, missing receipt, mismatched count, or absent drain means INVALID/INCOMPLETE, never PASS. No retry or tolerance-based pass. Fail-stop without GPU reset.

Minimum census receipt: exact source/build/model/tokenizer/input hashes; command/options and effective route choices; `n_prompt`, actual `n_batched`, chunk ledger and sum; per-route/per-wrapper decision/call/returned counts; rows and unique chunks; payload/output/staging byte totals; aggregate capacity/overflow status; `Prefill::run` result; drain completion; queue/fault result; and successful/failed/unknown completion label. Reconcile each positive local expert order item to one decision; direct calls to one returned wrapper; GEMMs only after returned direct dequant; bypasses accounted; routed rows to route metadata (including peer/fused where attributable); staging bytes to actual staging transfers. If the current fused route cannot provide per-expert attribution, mark it opaque and invalidate any claim requiring that attribution. Do not use diagnostic-build elapsed time as a performance result. Separate gates remain: census pass, independent decode-success check, and 262,144-position lifecycle qualification.

## Minimal no-output lifecycle seam

R172 remains directionally correct: `generate.cpp` rejects `max_new <= 0`; session initialization receives `o.max_context`; prompt split calls `prefill.run(..., n_batched, 0)` then token processing starts at `pos_start=n_batched`. The final prompt input must execute through `put_input`, the existing session layer path (`session_loop`/`session_token` depending on capture configuration), `run_head`, logits readback and finite-value validation. Add an opt-in test-only branch immediately after successful final-position head completion and validation, before `sample_tokens`, sampled-token readback, append to `produced`, or next-token bookkeeping. This branch must report consumed input position `N-1`; it cannot claim success after batched prefill alone. Keep positive-output behavior on the ordinary branch. This explicit mode alone may allow zero output and it must require exact `n_prompt == max_context == 262144`, plain text, supported split, and `produced.size()==0`.

Canonical complete-capacity run is `262143 + 1`: batch prefix 262143, then token path consumes the last position. Run `262140 + 4` as a tail control; run the canonical split separately as the normal-final-token control. Both must consume exactly the same 262144 token IDs and emit zero tokens. Compare final state receipts between splits and repeat fresh sessions for determinism. Do not try `262144 + 0` as a “strict” split: that fails to run the final position's session/head state path. For usable positive-output boundary controls at unchanged physical cap, run separate fresh sessions with `n_prompt=262143,max_context=262144,max_new=1` and with `n_prompt=262140,max_context=262144,max_new=4`; each must finish the ordinary output count and validate finite logits. These controls demonstrate the last allocatable input/output budget with actual generated tokens; they do not replace the N-consumed/0-emitted lifecycle run. Any decode after a no-output prefill is a separate experiment/session because decoding consumes additional positions and would violate strict physical-N occupancy.

Receipt only compact descriptors and hashes, not full state tensors by default: prompt hash; configured and logical capacity; valid-position bitmap/high-water mark; accepted input count/last position; emitted count; sample launch/readback/append counts; finite-logit status; queue drain and fault journal interval; GDN/recurrent and convolution state, QSA KV/state/index, PLE history/window and other carved-state shape/byte-count/hash; KV logical cells versus resident streaming cells, pinned backing, mapped VMM and padded/guard reservation separately; capture identity/replay counts; initialization/reset identity; boundary-write receipts; available guard canaries. End PASS requires every required subsystem receipt, no valid position >=N, no write accepted at N, no sample/output, all state comparisons/canaries valid, known queue completion, clean fault interval and exact input counts. If allocator does not expose adjacent guard canaries, explicitly report unavailable and do not claim canary coverage. Elastic KV's growth rounding and `N+64` requests must be accounted separately from logical cap; it cannot turn padding/guards into usable positions. Keep capture and no-capture configurations separate because their path and pool hooks differ.

## Failure and lifecycle policy

All failures are terminal for that run. On async error, a failed wait/drain, unknown event completion, cancellation/interruption, session init failure, receipt write failure, or cleanup wait uncertainty: label failed or incomplete, retain the minimal representative diagnostic with progress/error/fault evidence under the established retention policy, do not retry, do not reset the GPU, and do not emit a success receipt. Release only resources whose ownership and completion are known; if completion is unknown, preserve resources until process teardown and mark ownership unresolved rather than freeing memory still potentially in use. Bound records and output; write final receipt atomically only after known completion and checked close. A receipt-write failure invalidates the run result.
