Actual caller and grouped shapes
In `Prefill::init`, `m.cs` is the caller's compute stream and `m.copy` is a separate stream created on the current runtime/device. For the seven native IQ GU/down format pairs in the R292 scope, the fallback dequant path materializes group-of-16 FP16 weights: `GU_ELEMS=1280*2560` and `D_ELEMS=2560*640` half elements per expert. Each count is a multiple of 32 half elements, so the expert stride in bytes is divisible by 64. The actual grouped calls are GU `(N=1280,K=2560)` and down `(N=2560,K=640)`; both meet `xmx_gemm_ok`'s N multiple-of-16 and K multiple-of-32 gates. The caller passes the aligned allocation bases `Xs`/`Hh`, `dq_gu`/`dq_d`, and `GU`/`Dm`; the kernel applies expert row starts from `bounds`, rather than passing a row-offset output pointer.

The native resident fused prefix is separate: when `fuse_res` is admitted, resident experts with at most `kIqGemmTileRows` tokens go through `iq_gemm_grouped_f16` directly on resident blobs. The remaining GPU experts (including larger resident experts and streamed experts) are grouped in up-to-16 FP16-dequantized slots and use `Gemm::f16_groups`, falling back to `xmx_gemm_grouped` when that helper declines. The CPU-assigned experts, when that route is active, are put after GPU rows. This is why the XMX grouped audit applies specifically to the non-fused, non-MMQ fallback arm; it does not qualify fused IQ GEMM or the other native formats themselves.

Bounds, extents, and maximum rows
The router's stable top-k marks each winning expert as taken before selecting the next rank (`src/kernels/xe/router.cpp`, `s_taken` in `router_top10_launch`), so a token cannot contribute twice to one expert. Thus for a chunk of T rows, each expert count `cnt[e]` is in `[0,T]`; this is a source property, not a statistical expectation. The prefill host grouping writes GPU expert starts cumulatively into `m.off` in `order`, then CPU expert starts after them, and stores `m.off[n_expert]` as the final total. It sets `rows_gpu=T*K-rows_cpu`. For non-MMQ, `xb_host` is `m.off[order[j]]` for each GPU expert and its sentinel is exactly `rows_gpu`; this is uploaded as `xb_dev`. Each DQ batch uses contiguous starts and the next expert's start (or final sentinel) as its endpoint. `maxr` is the maximum `cnt` among that batch, so `0 <= maxr <= T`; G is at most 16. Empty routes have no GPU `order` entry and do not call grouped GEMM.

The GEMM input is the whole gathered `Xs` or `Hh` allocation. `gather_rows16` fills up to T*K rows; each bound endpoint is at most `rows_gpu <= T*K`. Outputs are allocated for T*K rows (`GU`: T*K*1280 FP32, `Hh`: T*K*640 FP16, `Dm`: T*K*N FP32), and the final grouped endpoint cannot pass the GPU row count. Bounds are nondecreasing: only positive-count experts enter the order, in expert-id order within fused/non-fused partitions, and starts are accumulated counts. Every expert in each grouped batch is resident or staged before its product call. I found no actual invalid alignment, `w_stride < N*K`, out-of-extent bounds, or `max_rows > T` precondition among these valid production caller paths.

DQ slot and expert-ring lifetime
The DQ group slot index is `(j-nf) % 16`. Dequant writes GU/down into slot q on `m.cs`; before q is reused after a full group, the caller queues that group's GU product, SwiGLU, and down product on the same in-order compute stream. Thus reuse of a DQ slot follows submission of the previous group's final down operation. For the actual path this is an ordering guarantee of the in-order queue, not a host wait.

For T >= 2048 with the prescribed `STRATA_PREFILL_RING=8`, Xe's `ring_slots` clamps the effective count to at least 16; `m.ring=16 > STAGE=8` and `stream_all` is enabled when `m.src` is non-null. This changes behavior relative to current D: D's `ring_slots` explicitly returns STAGE when env is set to 8, so D remains routed-only (`m.ring==8`) while pristine Xe enters the cross-layer stream-all walk at this large T. This is an actual comparison mismatch to record, not a hidden kernel input violation. Stream-all copies every nonresident pair into its ordered ring, including experts not selected by a given layer, whereas routed-only stages selected experts as the layer runs.

The Xe `STRATA_PREFILL_CPU_SHARE` default is measured `auto` if unset, whereas D has no matching CPU-share control in the inspected source. At the actual Xe stream-all T/ring above, `cpu_maybe` includes `!stream_all`; therefore CPU expert splitting is off in this exact large-chunk arm despite the auto default. Do not describe the default auto as causing CPU/GPU placement differences for this arm. If ring is exactly STAGE or chunk < 2048, stream-all is false and the Xe auto CPU route may become active where current D has no corresponding switch; that is a separate configuration and would change expert placement/numerics.

Queues, events, and concurrent host workers
`Runtime` creates compute, transfer, and engine streams as `sycl::queue`s in one device context with `property::queue::in_order`. The prefill's copy queue is created from that same runtime/device; XMX launches are submitted on `m.cs` and the public API does not wait when passed a non-null stream. Host-to-device copies are queued on `m.copy`; `copied[slot]` is recorded after each copy, and the compute queue submits a dependency wait before using the staged blob. The compute path records `used` after its final reader; the copy queue waits on the corresponding used event before overwriting the ring slot. In stream-all, `a_issued`/`a_consumed` release-acquire atomics publish the copied/used event handles before the other host thread consumes them. `Stager::work` calls `OnDevice(m.device)` before `event_sync`, so `Runtime::get()` on that worker resolves to the event's GPU. Event objects are reused only after those handoffs. On source inspection, the intended Level Zero host-thread/queue/event association is internally consistent; no missing cross-queue dependency or DQ/ring lifetime error is demonstrated. This is a code-ordering conclusion only, not a Level Zero runtime qualification.

Concrete failure-path gap
The staging callers ignore the boolean result of `gpu::copy_async_after` in both inline `issue_until` and the threaded issuer (`prefill.cpp` around lines 1311–1316 and 1358–1363). `gpu::copy_async_after` catches submit exceptions and returns false (`gpu.cpp` 242–251). The callers still advance `issued` / `a_issued`, and threaded staging can also signal the host buffer as issued; consumers may then wait on a stale or absent `copied` event and use old/uninitialized slot contents. The adjacent `stream_wait_event` and `event_record` helpers also return bool, and these call sites do not check them. This is a real error-propagation hole if SYCL submission or event recording fails; it is not evidence that a valid normal run's preconditions are violated. The report distinguishes it from the no-fault main run reported by root.

Disposition and limits
For the seven R292 format pairs and the actual nonfused FP16 fallback route, caller-established shape, stride, alignment, bounds, output extents, maximum rows, and same-queue DQ slot ordering satisfy the grouped kernel's checked assumptions. The primary production comparison discrepancy is effective ring behavior: env=8 means ring 16 plus stream-all on pristine Xe, but ring 8 plus routed-only on current D. The auto CPU-share default is source-different but inactive in the described Xe stream-all arm. Staging submit/event failures are not propagated and should be counted as a fault-path gap. No hostile inputs, unpinned fallback pair, hardware fault, model correctness, runtime liveness, or complete numerical qualification was tested here.
