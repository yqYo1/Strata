## Finding and candidate

The plausible CPU fork is one narrow dispatch change: try XeStrata's default AVX2 IQ2_S (GGML type 22) gate/up row path at NT=1 on the target Zen 3 / Ryzen 5 5600X, keeping current W0141's Down20 behavior and all other code fixed. Use the exact `(GU22,Down20,H=2560,FF=640,NT=1)` component as the first candidate because it is the largest 22/20 pair in the current actual-prefill census (29,271 calls) and the existing CPU capacity fixture already covers 22/20. The audit does not show that the whole XeStrata fork is better or that its NT1 numerical change is acceptable. Promote only after a paired component measurement and the existing quality contract; otherwise retain current W0141 behavior. Do not add another generic pool/service timer for this check.

The candidate rationale is the dispatch delta, not a claim that XeStrata's general kernel body is new or universally faster. W0141's default on the target CPU keeps IQ2_S GU NT1 in ggml-cpu `vec_dot`; its custom AVX2 path starts at NT2. XeStrata lowers the default MT minimum to one for every GU type except type 16 when AVX2 is available, AVX-512 is absent, `STRATA_NO_IQ256` is absent, and `STRATA_IQ_MT_MIN` is unset (`native_expert.cpp`: W0141 106–123, 133–164; Xe 94–113, 115–142). W0141 keeps IQ3_S's NT1 exception opt-in via `STRATA_IQ3S_MT1`; Xe makes that default broad. R286 already separates current target behavior: for `(22,20)`, NT1 uses ggml for both dots in W0141; NT2–4 may use custom IQ256 GU22 and IQ4NL Down20. NT3/NT4 remain capacity-only until production exposure is captured.

Eligibility for the seven source/census pairs is route-specific. The observed pairs are 18/20 (27,283 calls), 18/42 (5,801), 21/20 (17,634), 21/42 (2,005), 22/20 (29,271), 22/42 (9,662), 23/20 (1,849). All four GU IDs 18,21,22,23 are in `iq256_supported`; grouped IQ256 GU can use them at NT≥the selected MT minimum on an AVX2, non-AVX512 host. Down20 can use the custom IQ4_NL down kernel only for NT≥2 under its default threshold; Down42 has no matching custom down kernel and stays in ggml. Thus at NT1 the candidate applies only to GU, and at NT2+ the current W path already has the relevant custom GU / optional Down routes. `native_fmt` is still gated by the loaded ggml-cpu `vec_dot` traits, activation quantizers and whole-block shapes; these format IDs are source support, not proof that a given runtime pack loaded that pair.

## Arithmetic and numerical consequences

For IQ2_S GU, both paths consume the existing Q8_K activation representation and the same packed IQ2_S weights. `native_quant_act` selects `q8k_quant_avx2` only when runtime AVX2 is present and `STRATA_NO_Q8K_AVX2` is absent; otherwise it uses ggml's trait quantizer (W0141 and Xe `native_expert.cpp`: 86–104 / 74–92). The Xe and W0141 quantizer code has the same arithmetic, including scale selection, magic-constant rounding, clamp, low-byte behavior and block sums. The source says its byte output matches `quantize_row_q8_K_ref` (`iq_avx2.cpp`: W 387–454, Xe 390–457); the changed `amax` spelling (`!amax` to `amax == 0.f`) is equivalent for zero and NaN comparisons. This is a source claim backed by the named parity check, not a parity test run in this audit. Down20 uses ggml's type-selected activation quantization before its custom or ggml dot; Xe does not change that quantizer logic.

The custom IQ2/3 GU row kernel decodes grid, sign and scale fields, forms integer products with AVX2 (`maddubs` then `madd`/add, or AVX-VNNI integer dot on supported hardware), converts block partial sums to float, accumulates scaled block sums with explicit `_mm256_fmadd_ps`, then horizontally sums lanes (`iq_avx2_rows.inl`: `row_dot`, 34–61; IQ2_XS specialization 69–149; VNNI helper 15–31). This is not the same reduction order as ggml's single-token `vec_dot`. Xe's own comment says lone-token and grouped rows can round differently and that the greedy output may depend on draft-window size; it just elects the custom route by default for more NT1 formats. Exact token parity cannot be inferred from equal input bytes or matching formulas.

For Down20, `iq4nl_rows` expands nibbles and absolute weight bytes once per block, then computes the integer dot with Q8_0 values and uses explicit float FMA accumulation (`iq_avx2_rows.inl`: 241–273). This custom path starts at NT2 in both default W0141 and Xe; NT1 uses ggml's dot. The signed/unsigned multiply-add intrinsic saturates 16-bit pair sums in general, but the IQ4_NL code's documented bound makes the pair sum at most `2*127*128=32512`, below 32767. Do not generalize that bound to other formats without rechecking their code ranges.

The source contains intentional protections around quantizer rounding: GCC can contract the quantizer multiply-plus-magic-add under `-ffp-contract=fast`, so the implementation forces the multiply result to remain separate before the rounding add. The row dots use explicit FMA intrinsics, independent of ordinary expression contraction. GCC documents when expression contraction can form FMA, and Intel's guide/reference documents the AVX2 and FMA intrinsics and their instruction mapping. These documents explain why rounding boundaries must be reviewed; they do not establish the output delta of this candidate. [GCC `-ffp-contract` documentation](https://gcc.gnu.org/onlinedocs/gcc/Optimize-Options.html), [Intel Intrinsics Guide](https://www.intel.com/content/www/us/en/docs/intrinsics-guide/index.html), [Intel intrinsic reference for `VPMADDUBSW`](https://www.intel.com/content/dam/develop/external/us/en/documents/cpp_compiler_classic.pdf).

The Xe decoder refines are mostly source-safety/readability changes: explicit `reinterpret_cast` on intrinsic pointers; widening a few pointer-offset products to `ptrdiff_t`; `std::atoi` to `std::strtol`; and per-type gather selection that defaults to gather only for IQ3_S instead of the W0141 per-thread gather-fast choice. The q8k `if (!amax)` spelling changes to equality as noted above. The source-level integer products and reduction algorithm in the shared row kernels otherwise match. In the targeted IQ2_S plain kernel, the Xe and W sources show the same decode and integer/float reduction logic; it is the NT1 dispatch threshold that exposes that arithmetic to production decode.

SIMD behavior has explicit safety conditions. W0141 guards both AVX2 GU and IQ4_NL Down entry with `cpu_avx2_ok()`; Xe's corresponding booleans check only the disable environment variable, while the surrounding selection tests AVX-512 availability / supported type (`native_expert.cpp`: W 133–160, 185–194; Xe 122–140, 161–165). A wholesale transplant would remove a runtime ISA check and can call a compiled AVX2/FMA function on an unsupported CPU. Keep W's feature gate. On the target Ryzen 5 5600X, R286 records Zen 3 AVX2 and no AVX-512, but that target fact does not make the missing guard acceptable for other systems.

The integer accumulators use packed SIMD add operations with defined wrap semantics; valid target dimensions are fixed and small enough that the expected IQ/Q8 block partials fit in signed 32-bit range. The main numerical caveat is floating summation order, not an identified signed-overflow dependency. The source uses x86 unaligned-load intrinsics over GGUF byte storage and explicit-width `memcpy` helpers for scalar reads. The code is architecture-specific; any importer must preserve the compile/runtime ISA split and format-layout invariants rather than relying on native C++ aliasing or alignment assumptions.

## Minimal benchmark and decision boundary

If testing this fork, build an isolated component harness for GU22 NT1 with the current W0141 and candidate dispatch body, same compiler flags, same 5600X, same actual packed IQ2_S rows and deterministic Q8_K activations. First compare every GU output against the current ggml route using the established row-level parity metrics and record max/RMS error, exact-bit rate, nonfinite values, and downstream SwiGLU output. Then measure paired warm and streaming-192 row-kernel service for the same shape and row count, with no changes to the live pool's clocks, tasking, quantizer, route, or worker topology. Treat resulting times as component evidence, not production decode t/s. If accepted for import, take only the IQ2_S NT1 dispatch adjustment and retain current W feature gating, gather policy, quantizer and all Down paths; rerun full decode correctness before any production claim. Existing whole-model performance eligibility remains false until the normal current-runtime qualification is completed.

This choice respects the CPU contract: the separate target is 70 measured decode tokens/s; the 64K prompt allowance and ~1000 tok/s prefill target do not transfer to decode. R286's 22/20 capacity values are synthetic-prequantized component controls and not current production service rates. The existing production instrumentation contract R284 already defines the eventual route/NT join and worker service data; this proposal adds no generic task-0 service instrumentation.

## External source context

Intel's official Intrinsics Guide documents the extension families, and GCC's official option documentation describes expression contraction. As an implementer discussion rather than a transferable benchmark, the llama.cpp IQ2_XS author thread describes how AVX2 sign decoding changed a dot-product path, then reports machine-dependent results and maintainer cautions; it reinforces the need to preserve GGUF layout and test on the target, not a speedup estimate for Strata. [llama.cpp “Accelerating IQ2_XS” discussion](https://github.com/ggml-org/llama.cpp/discussions/5152).
