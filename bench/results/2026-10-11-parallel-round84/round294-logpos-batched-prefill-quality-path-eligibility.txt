R294 — Does STRATA_LOGPOS measure the batched candidate path?

Conclusion

No. `STRATA_LOGPOS` is a verifier-window hook in the `--serve` request loop. It does not observe logits emitted by `Prefill::run` / `run_layer_major`, and it cannot by itself produce a complete paired teacher-forced NLL for a reference completion after an exact 64K batched prefill. On a long fresh request, the large prompt segment still goes through the selected Prefill path; only separately eligible short segments go through verifier windows. The log therefore risks being mistaken for candidate-prefill quality while actually measuring a different residual/state path.

Path evidence

1. The only `STRATA_LOGPOS` reader in `generate.cpp` is inside the persistent-server `read_windows` lambda (around lines 9519–9557). For each verifier window, it forms `win[t] = cur[q+t]` and `nxt[t] = cur[q+t+1]`, calls `ver.run(T, win, q, ...)`, then passes `nxt` to `ver.window_logprobs`. It commits that same verifier window afterwards. In `verify.cpp`, `window_logprobs` copies `head_logits_` produced by that window and writes rows `(position, target_id, target_logprob, argmax_id, argmax_logprob, match, extra_logprob, without_extra_logprob[, top-K])`; each target is `targets[t]`, while the row position is `pos0+t`. Thus the logged target at a window input position is the *next* prompt token `q+t+1`, not that input token's own conditional probability.
2. The candidate Prefill call is separate. Standalone `generate` computes `n_batched` and invokes `prefill.run(o.tokens.data(), n_batched, 0, err)` around lines 11137–11205; the token loop starts at the remaining last prompt position. In serve, `read_part` calls `sp.run(...)` for batched segments (around 9706–9712); `Prefill::run` dispatches to `run_layer_major` only when `STRATA_PREFILL_LAYER_MAJOR` and its chunk/count predicate select it (candidate file lines 2435–2444). There is no `STRATA_LOGPOS` callback in either Prefill implementation. `on_chunk` supplies residual rows to MTP/checkpoint work, not verifier logits.
3. Serve selects windows per segment, not per request: `windows_ok(a,b)` rejects windows when `STRATA_CKPT_REREAD` is present, when `b-a > req_short_read`, or when any image embedding row is in the segment. The default short-read length is 64. The loop routes an eligible segment to `read_windows`; otherwise it lends buffers and calls `read_part` (around 9371–9385, 9810–9828, 9878–9900). `STRATA_LOGPOS` only disables pipelined `read_windows_pl` so the serial verifier loop can log; it does not make a long segment eligible for windows. A fresh ~64K text prefix therefore remains batched, and the hook sees at most the short verifier-window segment(s), such as a short assistant suffix. This is the key applicability gap.
4. Resume is selected from the longest matching live/checkpoint/slot/parked prefix; after restore, the request rewrites from `resume`, reports `RESUME`, and reads `[read_from,n-1)` before the final prompt token's first verify window (around 9124–9385 and 9930 onward). A resumed request does not recompute the prefix. To score completion token `c0` after a prefix of length `P`, the predicting logits are those after consuming prefix token `P-1`. If a request resumes at `P` and windows start with `c0` at position `P`, `window_logprobs` reports `c1` from that row, not `c0`; it has no saved logits from the batched prefill. Likewise, if a long batched segment ends at a turn boundary and the short verifier segment begins there, the first target is one token after that segment's first input. The first completion-token probability is therefore missing from ordinary LOGPOS rows unless the harness separately captures the batched prefix's terminal logits or deliberately arranges an overlap from a state before the final prefix token.

What a valid comparison needs

Keep the 64K prefix on the candidate path with the fixed candidate flags, model, token IDs, chunking and state initialization. Do not set a short-read threshold large enough to turn the entire prefix into verifier windows: that would bypass the modified residual storage. Then score the fixed reference completion with forced IDs while retaining the post-prefill session state. Existing `STRATA_LOGPOS` can measure only the portion that is actually passed through `Verifier::run`; it can be used for a deliberately short suffix, but its coverage must be position-checked and the first target must be supplied from the terminal batched-prefix logits. The current generator exposes neither that mixed-path teacher-forcing contract nor the needed terminal-head row from Prefill. A complete paired-NLL/top-K comparison therefore needs a dedicated harness or a narrowly scoped quality hook that takes final Prefill logits/state and teacher-forces the reference IDs through verifier windows. Record each row's absolute target position and assert exact completion coverage, including token zero of the completion. Do not label a suffix-only LOGPOS trace as NLL after the full candidate prefill.

Physical context boundary

The model's trained positional boundary is 262,144, but serve request admission reserves generation slack: it rejects when `n + max_new + 8 > o.max_context` (around line 5393). With `--max-context 262144` and `max_new=1`, the largest admitted prompt is 262,135 tokens; a 262,144-token prompt is not admissible in this server path. A 64K prefill plus reference completion must fit this same inequality. Keep the separate physical-boundary lifecycle gate at 262,144 as a context/state admission test; it does not repair LOGPOS's path mismatch, and a successful 64K quality trace does not substitute for it. `Verifier::run` also rejects a window when `pos0 + T` exceeds the allocated QSA context (verify.cpp around line 1180).

Decision

Treat the existing LOGPOS hook as ineligible for direct evaluation of the changed layer-major residual-store candidate. It remains useful for reference scoring on verifier-window segments and for a separate decode/window control. Do not use it as the candidate's paired-NLL acceptance gate until the prefix terminal logits and full reference-completion token coverage are captured on the same actual candidate run.
