# R155 — compact layer-major route-group transfer screen

Date: 2026-10-10 (Asia/Tokyo). Read-only source audit of the frozen route-group candidate and fixed WPROBE 609a270daac23c9b1a26d26ec092b2f60d2da335, plus official project sources. No source edit, build/compiler/disassembly, test/runtime/model payload, GPU/profiler, Git, lock, cleanup, service, or reset operation was performed. No timing or production-selection claim is made.

## Disposition

A single bounded transfer seam exists: per compact layer-major chunk, replace only the host-built slot/src permutation with the existing integer GPU count/scan/place route-group kernel. Keep the host counts, expert-ID order, layer-cache residency, expert compute loop, dequant/GEMM/SwiGLU/combine, and callbacks as they are. The map must remain chunk-local. This would preserve expert scheduling and weight staging, but it would not preserve exact within-expert row order: the existing atomic placer is unstable. R153 establishes no oneMKL bitwise row-permutation contract, so this is a source-feasible candidate only, not ready for implementation or use until parity is resolved and R154/root timing shows that the CPU map work is material.

If “without changing order” means preserving the exact existing route-rank order within each expert, the answer is no: the existing atomic grouping kernel cannot provide that guarantee. This screen does not propose a stable-sort replacement.

## What compact layer-major actually runs

R152 is correct that the current route-group opt-in cannot select here. Its integration gate requires noncompact mode, no on_chunk/on_stage_chunk callbacks, and the whole layer range; layer-major deliberately sets compact mode, bounds each run_impl call to one layer, installs both callbacks, and later layers set hand_in. Those constraints are not accidental ways to route into the existing candidate.

The actual layer-major function requires full single-GPU compact FP16 processing, resident K/V pages, no helper/peer/next stage, and rejects PLE preload (WPROBE sycl/src/prefill/prefill.cpp:2399-2425). For every layer it waits/finishes prior queues, loads that layer's experts into layer_cache, sets stage_lb=layer and stage_le=layer+1, sets hand_in for layers after the first, installs on_stage_chunk and on_chunk, then calls run_impl with the whole request n (lines 2690-2768). run_impl still iterates chunks using its init-time workspace size m.T (2912-2964). The layer-major callback stores each completed chunk's residual into the existing GPU rows or host rows before the next layer/chunk proceeds (2722-2738, 5100-5178). A map-only transfer must fit inside this existing chunk path and must not bypass or move these callback/state handoffs.

Within each run_impl layer/chunk, current host mapping copies device routed ids into ids_host and waits on the compute queue; it validates each id, builds per-expert counts, exclusive offsets in expert-ID order, slot[i], src[p]=i/K, and an expert order containing nonempty experts in ID order (4082-4180). It then uploads slot/src and continues. For compact mode it skips the one-shot full T*K activation gather; each expert's compute gathers mixed_h rows from src_dev+o0 into the reused Xs buffer, whose capacity is T*N half elements, then runs per-expert GEMM, SwiGLU and down GEMM. GU and Hh are also compact T-row scratch; Dm remains the route-sized T*K*N FP32 destination because combine later consumes route slots (4211-4237, 4782-4802, 4888). The gather and the next expert's reuse are ordered on m.cs. The route slot map still feeds moe_combine; replacing it incorrectly would break token/rank association even if expert products were correct.

Weights have a separate schedule. Layer-major stages the whole layer into layer_cache before run_impl begins, then the host expert order drives the same sequential compute loop; cache hits return immediately from stage_one, so this path does not use the ordinary host-to-device STAGE ring for each expert (2690-2717, 4598-4637, 4814-4829). Leave that load/lease/restore behavior, order vector, and compute sequence unchanged. The DQ=2 dequantized FP16 scratch is reused in order on the same compute queue, and layer/chunk callback waits remain the residual and error boundary. Do not move map generation across a layer load, chunk callback, layer-cache restore, or state handoff.

For a 262,144-token physical-cap request, run_impl sees request n but loops its bounded workspace chunks. At an 8,192-token chunk size this is 32 chunks per layer; maps remain 81,920 route entries per chunk (T*K, K=10), not a 2,621,440-entry full-context map. The exact m.T is chosen at init and must be recorded rather than assumed. Existing layer-major may already retain full-context residual rows in GPU/host storage according to its R_GPU choice; this candidate must add no route, activation, output, or saved-intermediate tensor proportional to n.

## Bounded transfer seam and admission/accounting requirements

The existing route-group kernel accepts the current chunk's device ids, slot and src maps plus small int32 scratch; it computes counts, expert-ID prefix offsets and slot/src. A compact transfer could run it on the same in-order compute queue after router ids are ready, copy only counts to the host, and keep building the same host m.off/order from those counts. The existing count-to-host synchronization remains necessary because the weight schedule needs the counts and expert order; the factor would remove the device-id download, O(T*K) host slot/src construction, and slot/src uploads, while adding the integer GPU phases. It does not remove the router wait or change the layer/chunk schedule. There is no timing evidence here that this exchange wins.

A future implementation would need an explicit internal layer-major admission marker, not a broad exception for callbacks or partial layer bounds. Require exactly the known full-single-GPU compact layer-major caller; retain the route-map shape/capacity checks, in-order queue, no-MMQ/no-fused fallback, stable opt-in lifecycle configuration, and native IQ3S format check used by the narrow existing candidate. The normal server callback path and arbitrary split/helper/callback paths must remain excluded. Keep n>=32768 as the whole-request threshold and T>=1024 for the current chunk; tails below 1024 stay on the existing host path. For the normal CLI n_prompt-1 convention, a prompt of 32,768 supplies only 32,767 to run and misses that whole-request gate; physical 262,144 does pass it. Record actual format and per-layer selection rather than inferring from the environment.

No new full-context mapping storage is needed. Compact already carves T*K int32 ids, slot and src and has host vectors sized for T*K; its scratch view is separate. Add the route-group scratch as typed int32 storage to both the compact count-only moe_set_bytes calculation and its matching carve, using the same predicate/order and allocator accounting. The existing kernel requires 3E+1 words (counts[E], offsets[E+1], fill[E]); at E=512 that is 1,537 words / 6,148 payload bytes, independent of T. R150 observed 6,656 accounted bytes for an E=512 scratch take in the existing noncompact accounting path; recompute and verify exact compact count-only/carve equality rather than assuming this payload is the total reserved bytes. Continue to make the whole shared region the max of attention and MoE consumers. The current compact region already contains the existing route maps and scratch intermediates; the additional group scratch is only O(E), but it must not silently raise workspace beyond the actual post-relayout region or overlap attention/MoE aliased views.

Preserve these map/lifetime rules:

- Check counts sum to T*K and each src/slot pair remains a complete valid mapping; verify src[slot[i]]==i/K and expert interval membership before any gather/GEMM/combine consumer. Invalid routed ids must abort before consumers.
- Host m.off and device offsets must agree for the same counts. Expert order stays ascending ID order, so layer-cache reads, dequant sequence and DQ ring alternation do not move.
- Same-queue ordering must keep completed route maps ahead of per-expert compact gathers. Each gather writes Xs before that expert's GU GEMM; GU writes before SwiGLU; Hh before down GEMM; Dm before combine. The next expert may reuse Xs/GU/Hh only under that queue ordering.
- Do not use a host/device scratch map beyond the current T*K route chunk. Keep layer-major callback and cancellation/error restoration behavior; asynchronous failures must surface before callback/state advancement.

## Numerical and external transfer evidence

The route-group map changes row order within each expert; R153 found unchanged per-expert GEMM dimensions/call structure but no documented oneMKL row-permutation bitwise contract. Compact uses a different gather arrangement from the noncompact test path, so the actual compact Xs/GU/Hh/Dm and final combined/state outputs still require their own parity discriminator. Preserve the existing expert compute order and compare each product by routed source token, then compare combine, logits and saved state. Do not invent an error tolerance or take the R153 noncompact audit as compact parity evidence.

The vLLM implementation uses route-alignment outputs such as sorted_token_ids, expert_ids, and scatter mappings around its MoE GEMM path; its tests check that active routed entries are covered and that the scatter mapping corresponds to the original assignments ([vLLM alignment implementation](https://github.com/vllm-project/vllm/blob/main/csrc/libtorch_stable/moe/moe_align_sum_kernels.cu), [vLLM MoE alignment tests](https://github.com/vllm-project/vllm/blob/main/tests/kernels/moe/test_moe_align_block_size.py)). This is useful precedent for treating grouped maps and inverse scatter as a joint contract, not a drop-in proof for Strata's DPCT/oneMKL expert loop. A recent vLLM implementer report says legal within-expert token reorderings produced differing BF16 Marlin MoE W13 outputs in a split-K region, and that canonicalizing order removed that observed divergence; it is a different kernel/data path, but reinforces that row order must be measured ([vLLM issue #52525](https://github.com/vllm-project/vllm/issues/52525)).

SGLang documents its expert path as dispatch → pre-permute → runner/grouped GEMM → post-permute → combine, with the runner and permutation hooks coupled ([SGLang Expert Parallelism](https://github.com/sgl-project/sglang/blob/main/docs/docs/advanced_features/expert_parallelism.mdx)). That architecture supports keeping source-to-slot recovery beside the GEMM path, but its CUDA/Triton/DeepGEMM backends do not establish transferability to this compact SYCL FP16 implementation. No external implementation establishes that this exact oneMKL FP16 row permutation is bitwise harmless or that the map-only exchange pays for the extra kernels.

## Minimal discriminator if the candidate is reopened

First require R153's numerical gate on actual compact layer-major data in the root's tuned configuration. Instrument exactly one actual eligible layer/chunk to retain baseline and candidate maps, prove the source permutation and map invariants, compare gate/up, SwiGLU, down, combine/logits and saved recurrent/KV/indexer state, and record the owning protocol's acceptance result. Then require root's timer evidence to identify CPU grouping and map-copy cost separately from the unavoidable router wait, host count/order work, weight loads, expert compute and callback/state transfers. Only if the parity contract passes and the removable host work is material should the single bounded map-only transfer proceed to a private prototype.

The qualification request must include the actual layer-major request at or above 32K and the physical 262,144-token cap with exact m.T/chunk boundaries, loaded IQ3S layers, compact flag, full single-GPU/KV preconditions, route map selection count, per-chunk bytes, memory peak, unchanged layer-cache weight order, callback/state continuity, and final partial chunk behavior. No result from this source screen establishes selection, compilation, correctness, performance, memory health, or adoption.
