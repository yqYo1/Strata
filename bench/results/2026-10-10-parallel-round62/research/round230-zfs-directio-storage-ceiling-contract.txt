# R230 — ZFS Direct-I/O storage-ceiling contract for the PLE shard

Date: 2026-10-10 (Asia/Tokyo). Read-only audit of the root-supplied storage observations, the pinned PLE reader behavior from R221/R226, and primary OpenZFS 2.4.1/Linux documentation and source. No current device, process, mount, sysfs or runtime query was made. No benchmark, build, test, profiler, source edit, Git operation, service action or cleanup was performed. This report is the only file written.

## Finding

The PLE shard's current `O_RDONLY | O_DIRECT` read path is eligible to bypass the ZFS ARC on the observed Linux/OpenZFS 2.4.1 pool, because the reader issues page-aligned 4 KiB or 8 KiB requests into a page-aligned buffer. That statement is conditional on the loaded module's `zfs_dio_enabled` setting, the containing dataset's `direct` property, and the target range not being mmap-mapped. The root-supplied observation establishes that the shard is on `rpool/USERDATA/yayoi` and the module package is `2.4.1-1ubuntu5.1`; it does not report the current dataset property or module parameter values. Therefore the existing R212 PLE timing cannot yet be classified as ARC-bypassing or physical-SSD service.

OpenZFS 2.4.1 makes the source-level decision in `zfs_setup_direct()`: an explicit `O_DIRECT` request is routed away from the direct path when the module switch is off or `direct=disabled`; a misaligned request falls back to uncached ARC I/O unless strict mode requests `EINVAL`; and a range with a mapped page is read through the ARC for coherence. Otherwise the code prepares direct-I/O pages and passes `DMU_DIRECTIO` to the DMU read. Linux defaults in that source are `zfs_dio_enabled=1` and `zfs_dio_strict=0`. The `direct=standard` dataset setting honors an application's `O_DIRECT`; `direct=always` forces properly aligned requests direct; `direct=disabled` ignores the flag. Do not assume the target uses `standard` merely because it is the documented default. Record the actual inherited/local property and loaded-module setting before interpreting a future run. [OpenZFS 2.4.1 read-path source](https://github.com/openzfs/zfs/blob/zfs-2.4.1/module/zfs/zfs_vnops.c), [OpenZFS Direct I/O property documentation](https://openzfs.github.io/openzfs-docs/man/master/7/zfsprops.7.html), [OpenZFS 2.4.1 module parameters](https://github.com/openzfs/zfs/blob/zfs-2.4.1/man/man4/zfs.4)

## Mapping the PLE reader to the ZFS conditions

The root's read-only GGUF inspection found `per_layer_token_embd.weight` at byte offset 192, with shape `[160,320001536]`, 90-byte rows, tensor bytes `28,800,138,240`, and file size `28,800,138,432`. The POSIX `DirectFile` opens the original file `O_RDONLY | O_DIRECT`; its mapping used for GGUF parsing is closed before the direct descriptor is opened. `PleReader` computes each row's absolute file offset, rounds the read offset down to a 4 KiB page, groups same-page rows, extends to 8 KiB for rows crossing a page, sorts jobs by offset and uses a 4 KiB-aligned slab. `DirectFile::submit` checks request offset, length and buffer alignment against its 4096-byte alignment. This matches the OpenZFS source's page alignment condition for these 4/8 KiB jobs, if the kernel page size and module are the expected Linux build. The app makes blocking `pread` calls on worker threads; its 256-slot slab bounds queued jobs, while active blocking reads are bounded by the 1/16/64 worker setting. Configured slots are not achieved storage queue depth.

There is a predictable EOF exception. The tensor starts 192 bytes into the file, and the file size is 3,264 bytes past a 4 KiB boundary. Thus the final page-sized reader job can request a full 4 KiB beyond EOF and return only the 3,264 bytes remaining in the file. The reader records `pread`'s actual returned byte count and accepts that completion only when every requested row lies within those returned bytes. OpenZFS's `zfs_read()` source handles an unaligned EOF tail through the ARC after the page-aligned direct portion. A last-page result can therefore contain an ARC-routed tail despite an aligned O_DIRECT API request. It is a very small fraction of this file, but it matters when reconciling exact direct-path counts and bytes. Count it separately; do not call the entire nominal final 4 KiB job a direct device read.

For a controlled full-page reference, the first complete 4 KiB page wholly inside the tensor begins at offset 4096. The last full page wholly within the file begins at `floor((file_size - 4096)/4096) * 4096`; the trailing 3,264 bytes are not a full 4 KiB page. A 1 MiB sequential reference should start at an absolute 4 KiB boundary at or after the tensor start and end at a 1 MiB boundary before the file end. These bounds keep all test requests read-only, aligned and inside the existing file; they omit only the unavoidable leading/trailing fragments. The source-derived PLE row-ticket path remains the later test for rows in those edge pages.

## What bypassing ARC does and does not mean

When the conditions above hold, a direct request is accounted by OpenZFS as `DMU_DIRECTIO` and its data is not satisfied through the ARC's ordinary cached-data path. It still traverses the OpenZFS DMU/ZIO stack, vdev queueing, checksumming, any applicable decompression/decryption, redundancy mapping and Linux block stack. `O_DIRECT` does not turn a ZFS file read into a raw-device read, bypass checksums, guarantee that the media rather than a device/controller cache supplied the data, or promise a one-for-one mapping between 4 KiB user reads and physical 4 KiB operations. [OpenZFS DMU flags](https://github.com/openzfs/zfs/blob/zfs-2.4.1/include/sys/dmu.h), [OpenZFS checksum documentation](https://openzfs.github.io/openzfs-docs/Basic%20Concepts/Data%20Storage/Checksums.html)

Read alignment is page-size based in the 2.4.1 property rules; it is not constrained to align to ZFS `recordsize`. `recordsize` still matters to existing on-disk blocks and can affect how file data is laid out and serviced. Changing the dataset's present `recordsize` would not rewrite the existing shard, and no property should be changed for this control. Compression changes the physical size and CPU work of stored records; copies, mirrors, RAIDZ/dRAID layout, `ashift`, and any special/cache devices change where and how many vdev operations occur. These are workload and pool facts to record, not knobs to mutate. `primarycache` and `secondarycache` can describe buffered/L2ARC policy, but setting them cannot establish that a particular O_DIRECT request was direct or prove physical-media traffic. The upstream property docs say that reads need no recordsize alignment for Direct I/O, every request still needs page-aligned memory and page-multiple length, and an mmap'd range is redirected through buffered I/O for coherence.

## Minimal finite same-file control

`fio` is unavailable on this host per the root's inspection, so use the already-proposed bounded blocking-`pread` control rather than adding a package or substituting a raw-device test. A small standalone, read-only harness should open the exact original shard with `O_RDONLY | O_DIRECT`, allocate page-aligned buffers, stay inside the tensor extent, and record every submitted/completed offset and byte count. It should use fixed finite operation counts and report achieved active reads, not only requested threads. The PLE `DirectFile` API is already blocking `pread` per worker, making this a closer filesystem control than a fio `libaio` replay.

- **Sequential reference:** stream a fixed aligned tensor-file extent with 1 MiB requests at one worker; optionally use 16 and 64 workers over disjoint aligned stripes as separately labeled concurrency arms. Report bytes, elapsed time, latency distribution and actual outstanding `pread` high-water. This is a contiguous ZFS/vdev path reference, not PLE's random-page behavior.
- **Uniform random page reference:** read a fixed, seeded set of 4 KiB aligned page offsets selected uniformly from the complete-page portion of the tensor/file range. Compare 1, 16 and 64 workers; use finite counts rather than unbounded duration. This is a generic 4 KiB random reference, not the PLE distribution: PLE rows have a 90-byte stride, page collisions, occasional 8 KiB straddlers and per-ticket source-order sorting. Add an 8 KiB direct-read control only if a separate discriminator needs to match the PLE straddler job; do not combine 4 KiB and 8 KiB results into one rate.
- **Source-matched reader follow-up:** run the existing CPU-only `PleReader`/`PleTable::gather_batch` route over a pinned deterministic row/ticket fixture on the same original shard, with the actual 4/8 KiB grouping and exact cache settings. Record actual routed row IDs or fixture hash, page job count and size distribution, `ReaderStats.requests/cache_hits/dedup_rows/reads/bytes/wait_us/submit_us/read_us_sum` and the per-read latency samples. Compare a `cache_rows=0` process to the default 1,048,576-row cache and one same-process repeat; this describes the reader's software cache without dropping ARC, filesystem or device caches. Set PLE keepalive to zero or separately attribute its reads; the model path's default keepalive can otherwise contaminate pool and device deltas.

The property/mount/module facts needed for the receipt are read-only: loaded OpenZFS package/module revision, dataset `direct`, `recordsize`, `compression`, `checksum`, `copies`, `primarycache`, `secondarycache`, pool topology/leaf identities and `ashift`, system page size, and the direct-I/O module switches. Also verify the reader did not leave the relevant range mmap'ed. Do not set `direct=always`, set `direct=disabled`, change recordsize/compression/cache properties, tune ZFS queues, unload modules, drop caches, write/trim, or read a raw device. The actual file and loaded property state should remain unchanged before and after each trial.

## Counters and admissible interpretation

Take short, time-matched deltas around each isolated trial, not since-boot totals. On Linux OpenZFS 2.4.1, the pool iostats expose `direct_read_count`/`direct_read_bytes` and `arc_read_count`/`arc_read_bytes`; `spa_iostats_read_add()` increments the direct fields when the request carries `DMU_DIRECTIO`, and otherwise increments the ARC fields. In a quiet isolated same-file run, an increase in direct-read fields alongside the known aligned pread requests is valuable evidence that OpenZFS selected its direct-data path; an ARC delta can reveal fallbacks or unrelated reads. These are pool-wide DMU request counters, not file-specific, vdev-level or physical-medium byte counters. Background metadata and other pool I/O can affect them, so a noisy/unreconciled delta is inconclusive. [OpenZFS 2.4.1 pool iostat accounting](https://github.com/openzfs/zfs/blob/zfs-2.4.1/module/zfs/spa_stats.c)

Capture `zpool iostat -v -p -r -w -l -q` or equivalent bounded interval output for the identified pool and leaf vdevs. In OpenZFS 2.4.1, `-r` reports individual and aggregated leaf-vdev request-size histograms, `-w` reports I/O wait histograms, `-l` reports mean queue/disk waits, and `-q` samples instantaneous pending/active queues. Pair these with the corresponding Linux block-device/partition `diskstats` deltas and major/minor identities, including all relevant device-mapper and leaf layers. The ZFS counters distinguish request-path categories; vdev and Linux counters show traffic at their respective storage layers. They include unrelated I/O and can reflect aggregation, redundancy, compression, metadata and cache effects. [OpenZFS 2.4.1 `zpool-iostat(8)`](https://github.com/openzfs/zfs/blob/zfs-2.4.1/man/man8/zpool-iostat.8), [Linux block I/O statistics](https://docs.kernel.org/admin-guide/iostats.html)

Keep these measures separate: application logical row payload; the PLE reader's completed bytes and jobs; OpenZFS DMU direct/ARC read counter deltas; ZFS leaf-vdev operations/bytes and latency/queue histograms; Linux block-layer sectors/bytes/merges; and foreground PLE gather/wait/request wall. Linux diskstats sectors are 512-byte sector units and describe block-layer traffic, not NAND bytes. ZFS direct bytes describe DMU path accounting, not vdev bytes. A close match among these cannot establish that the SSD controller missed its cache or that NAND was saturated. A storage-capacity claim requires repeatable same-file direct-path service, confirmed OpenZFS direct-path selection, low enough unrelated traffic to reconcile layers, and a matching PLE reader result whose wait is substantial on the same request. PLE gather wall, `read_us_sum`, and logical row bytes alone cannot prove an SSD ceiling.
