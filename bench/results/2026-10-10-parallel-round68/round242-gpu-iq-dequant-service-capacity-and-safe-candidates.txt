Production call path and eligibility
The normal streamed native MoE branch reaches `compute` in `sycl/src/prefill/prefill.cpp` only when it does not take the compiled/runtime MMQ or fused route: for the standard SYCL build the fused source is `moe_fused_stub.cpp` (CMake 270-274), and MMQ is compile-gated/disabled absent its supported build. In that branch, after the packed blob is staged and its copy-event dependency is enqueued, the compute-queue code at prefill.cpp:4900-4947 calls `iq_dequant_gu_f16(f.gu_type, blob_dev, blob_dev + f.up_off, f.n_ff, f.n_embd, m.dq_gu[q], m.cs)`, `iq_dequant_f16(f.d_type, blob_dev + f.down_off, f.n_embd*f.n_ff, m.dq_d[q], m.cs)`, then the two FP16 GEMMs and SwiGLU. The in-order same-queue program order is a data dependency: dequant outputs must be ready before GEMM reads them; q selects a DQ ring slot and must remain unchanged until the corresponding product consumes its weights. The copy source blob must remain live through queued dequant reads. Preserve the current copy-event/compute ordering and the qualified safe SG32/direct-submission/copy-offload settings. Do not add cross-queue overlap or change any of those settings in this discriminator.

Exact generic dequant kernels compiled into the standard SYCL build are in `sycl/src/kernels/cuda/iq_kernels.dp.cpp`; CMake includes `iq_kernels.cu`, resolved to that `.dp.cpp` (`sycl/CMakeLists.txt:244-262`). `iq_dequant_gu_f16` dispatches `dequant_gu_kernel` at lines 4390-4417. `iq_dequant_f16` dispatches `dequant_flat_kernel<sycl::half>` at lines 4292-4316. Both use work-groups of exactly 32 work-items, one group per 256 decoded values; the wrappers check `sycl::aspect::fp16`. The helper then does a uniform runtime `switch` through `dq_dispatch` (2724-2773) and the per-format decoder. These two dequant launchers themselves have no subgroup-size attribute and no internal barrier. Do not conflate that with the separate quantized native GEMV/grouped path, which has its own subgroup requirements.

Format selection is per layer: `f.gu_type` and `f.d_type` come from the expert layout, not one model-wide constant. In the actual mixed historical pack the per-expert packed blob sizes range 1,510,400–2,662,400 B (parent correction); the R240 CPU capacity fixture's 384 experts and its selected type pair 22/20 (IQ2_S/IQ4_NL) are a fixture cohort, not the graph's expert count or proof that every layer uses those formats. Existing production artifacts also do not establish the active route's full per-layer type/call histogram. The actual dequant format/type for an operation is the `f.*_type` captured at that call. `dq_dispatch` supports the compiled IQ set; type 14/Q6_K is behind `STRATA_Q6K_EXPERTS`; the broader generic `is_iq` guard is not identical to the role-specific grouped kernel format lists. Record actual layer/type/shape eligibility before timing a type-specialized route.

Exact H=2560, FF=640 output geometry (format-independent)
- GU represents two `[FF,H]` matrices, each 1,638,400 values. The kernel computes `per_row=H/256=10`; the launch has `2*FF*per_row=12,800` groups of 32 work-items, one 256-value block per group and gate/up parity. It writes `2*FF*H=3,276,800` FP16 values = 6,553,600 B in interleaved gate/up row order.
- Down is `[H,FF]`, flattened to 1,638,400 values; the launch has 6,400 groups ×32 and writes 1,638,400 FP16 values = 3,276,800 B.
- Per expert: 19,200 groups / 614,400 work-items across the two launches; 9,830,400 B logical FP16 output writes. The following two GEMMs logically read those GU and Down weight tensors once each: another 9,830,400 B of weight input reads. These are source-derived logical bytes, not DRAM or L2 traffic.
- Device dequant input reads the packed blobs, sized by each layer's format and layout. For the historic production mix that is 1.5104–2.6624 MB/expert. H2D separately transfers the packed blob once for each streamed/cache-miss expert; no assumption that all 384 fixture entries or all graph entries transfer per chunk is made here. Total logical packed-input read plus FP16 output write in dequant is 11.3408–12.4928 MB/expert for that historical size range. Add the one-time H2D payload and downstream GEMM reads only when computing those distinct path totals; do not convert the source byte count into a bandwidth claim.
- For a type-22 GU / type-20 Down fixture only, IQ2_S is 82 B/256 and IQ4_NL 18 B/32: packed bytes are 1,049,600 GU + 921,600 Down = 1,971,200 B/expert. This is useful as one exact selected-format test cell only, not the production mixed-pack range.

Current decoder implementation and established memory layout
The current source explicitly changed scalar half stores to `store_run<half,8>` (`:2363-2385`): each lane evaluates eight output values then writes one aligned 16-byte vector; lane-to-output offsets are multiples of eight elements and the block's 32 lanes cover all 256 values. IQ2_S uses grid index, sign mask and local scale to calculate eight outputs (`:2417+`); IQ4_NL reads packed nibbles, maps them through `kvalues_iq4nl`, scales, then stores the same eight-value run (`:2487+`). IQ4_NL's block is 32 values, and the flat 256-value group traverses 8 such blocks; this pointer arithmetic is type-specific. The source comment records a prior ~80 GB/s write-rate observation on Xe and says the vector store was introduced because it improved output store coalescing. That historical comment is not a fresh measurement, does not give an isolated current-route capacity result, and does not justify another generic wider-store test.

The most plausible format-only low-risk candidate is host dispatch to a type-specialized template kernel so each work-item directly calls the existing unchanged `dq_iq2_s`, `dq_iq4_nl`, etc. rather than running the all-format runtime `dq_dispatch` switch. Upstream llama.cpp SYCL `convert.cpp` already dispatches IQ2_S and IQ4_NL to separate per-format dequant functions/launchers, providing an implementation precedent, not a performance result. A prior report R148 (`round148-active-iq-dequant-new-factor.txt`) proposed this candidate; do not count it as new or re-propose it if the root has already screened it. No current result establishes whether the compiler has already folded the uniform switch or whether this path is significant.

Safe-candidate constraints:
1. A type-specialized direct decoder can preserve the same packed indexing, lookup tables, operation order, `cvt<half>` conversion, 8-value `store_run`, destination geometry, 32-work-item group, queue, and scratch rings. Only admit types observed on this route and keep the generic fallback. Do not invent wider packed loads: IQ2_S block stride is 82 B and is not 16-byte aligned across consecutive blocks; actual row offsets may also be non-aligned. Any input vectorization must use legal unaligned loads or separately stage/align bytes while preserving block decode. The existing output run is already aligned because each 8-half run starts at a 16-byte multiple and the bases/row spans for the actual geometry are aligned. Exact FP16 output bits must match, including subnormal and signed-zero behavior. The source `-fp-model=precise` and all runtime safety settings remain fixed.
2. The source also has a private `xmx_gemm_iq` implementation in `iq_kernels.dp.cpp:5200-5347` that fuses dequant tile production in local memory with joint-matrix GEMM, avoiding the full global FP16 weight write and reread (up to 19,660,800 B logical traffic/expert for H=2560/FF=640, before cache effects). It is not called by production prefill; its only source caller found is `xmx_gemm_bench`. Eligibility rejects some IQ types; it needs `n_out%16==0`, K divisible by 256 or special whole-strip conditions, and <=96 KiB local memory. GU K=2560/n_out=1280 is block-aligned; Down K=640/n_out=2560 selects whole-strip mode and passes divisibility checks. Its kernel requires subgroup 16, joint-matrix XMX support, SLM barriers, padded-tail zero fill, and exact pointer/scratch lifetimes. It violates the currently qualified SG32 setting and must not be substituted in the present safe configuration; it is a separate candidate requiring explicit root decision, supported-device check and numerical/thermal/fault qualification. Do not claim production eligibility or performance from the existence of this function.
3. External weight-only quantization uses the more substantial approach of decoding tiles in the matmul path, then overlapping tile load and dequantization. Intel's official WOQ article describes ESIMD and pipeline overlap for its formats. The principle is relevant to avoid global FP16 materialization, but this implementation uses different packing/tiles and device-specific ESIMD; no direct port or speed claim follows. Any new fusion must preserve two-phase local-memory producer/consumer barriers (all work-items converge), align each format-specific input block before vector loads, keep quantized source alive until all reads finish, hold the output accumulator and shared/local tile across the dequant→multiply lifetime, and prove tails/format boundaries. Since current safe SG32/direct submission is pinned, first candidate stays within the generic dequant launch and same queue; fusion is deferred.

Finite isolated dequant capacity recipe (for a later root-owned GPU qualification)
Use the dequant-specific harness `sycl/src/kernels/dequant_bench.cpp` only as a launch scaffold: it currently uses n_ff=1280 for Down rather than production 640, uses synthetic random bytes, hashes only first/last expert, and is not an exactness test (per R163). Build a bounded diagnostic variant that reads the actual active native expert formats per layer from the graph metadata and uses H=2560/FF=640, actual packed offsets/sizes and the same production kernels/work-group shape, destination type/layout, in-order compute queue, safe SG32 setting, direct submission/copy-offload settings and two-slot scratch ring. No oneMKL GEMMs in the isolated microbench. Collect the exact `(layer, type, packed bytes, n, call count)` manifest from the admitted route; run each actual GU/Down operation type, not only the 22/20 CPU fixture. Warm once separately; then time queued batches with kernel/device event timing and an end wait, recording individual GPU event durations and host submit/wall spans without a host wait after every kernel. Run 3 fresh-process cells with 25+ samples/cell (same build/runtime/settings), retaining raw sample rows and process medians/ranges; include first-use/JIT separately. Verify every output element's FP16 bits against the generic baseline on actual packed bytes, without readback/hash inside timing samples. Report effective packed-read/output-write logical GB/s only as a normalized attained rate for this exact combined operation; also report time/call by format and output bytes. Reject any candidate whose type branch was never reached, whose format coverage is incomplete, whose exact bits or prefill route regress, or whose timing gain is inside process variation. Then a separate matched prefill run is needed to show effect on total; no model-speed inference is made here. Preserve original successful and fault status and current artifact-retention rules.

Capacity conclusions
The existing `HARDWARE_LIMITS.md` GPU measurements are host↔GPU transfer, VRAM copy, and FP16 GEMM rates. They are not IQ dequant throughput. The CPU register-FMA peak and CPU native quantized expert service are unrelated. No isolated dequant sample/capacity result appears in the current reviewed report registry read for this round. Thus dequant's operation-specific attained capacity and route exposure remain unmeasured here. The next decisive operation-specific measurement is the per-format, production-shape, actual-data isolated GPU dequant above; only after that should a fused route be compared. No speedup estimate is asserted.
