## Question and source contract

The CMake option `STRATA_SYCL_PREFILL_IQ4NL_DEQUANT` defaults OFF and defines the macro only for `strata_prefill` and `strata_kernels` when enabled (`sycl/CMakeLists.txt:283–286`). The private declaration in `src/prefill/iq4nl_dequant.hpp` and the private dispatch in `src/kernels/cuda/iq_kernels.dp.cpp` are macro-guarded. With the build option ON, `Prefill::init` separately accepts runtime environment `STRATA_SYCL_PREFILL_IQ4NL_DEQUANT=0|1`, rejects malformed values, and freezes the value in `m.iq4nl_down_dequant` (`src/prefill/prefill.cpp:1058–1073`). The native direct path invokes the helper only when enabled and `f.d_type == 20`; otherwise it calls the generic `iq_dequant_f16` (`prefill.cpp:4799–4810`). Earlier source audit R169 found that MMQ and fused paths bypass this call, so runtime exercise still requires fresh process, `STRATA_PREFILL_LAYER_MAJOR=2`, `STRATA_PREFILL_MMQ=0`, compile option ON, runtime option 1, native format type 20, and at least one selected expert on the relevant layer.

The narrow claim to prove statically is: the OFF linked executable contains no IQ4NL-private device kernel image/entry, while the ON executable contains that entry in its Intel SPIR-V or AOT image. A separate lowering claim asks whether the private kernel image removes the generic runtime type switch and what device instructions differ. Neither claim proves dispatch at runtime or a speedup.

## Why the artifacts are distinct

Intel's DPC++ design describes the default SYCL flow as device LLVM IR to SPIR-V embedded in a host fat binary; target-specific native code is produced later by a backend, normally at runtime for the default SPIR-V target. AOT targets instead invoke the backend during compilation. Therefore an extracted `spir64` SPIR-V image is evidence of compiled device IR, not Level Zero native ISA or an instruction count. It can show kernel entries, constants/branches and call/dataflow differences at the SPIR-V level; it cannot settle final IGC lowering or native instruction cost. [Compiler/runtime flow](https://intel.github.io/llvm/design/CompilerAndRuntimeDesign.html#ahead-of-time-aot-compilation)

`-fsycl-device-code-split=per_kernel` means separate modules are produced per kernel, and their symbol tables help the runtime select modules. This is helpful to inspect, but a module's existence does not mean it was selected or created during a particular run. Prove the split flag is the same in OFF and ON builds, and do not use an image count or symbol grep as a runtime-launch receipt. [Device code splitting](https://github.com/intel/llvm/blob/sycl/sycl/doc/design/CompilerAndRuntimeDesign.md#device-code-splitting)

## Controlled OFF/ON build pair and artifact extraction

Build two clean, separately named build trees from the same source commit and toolchain: (A) the normal default `STRATA_SYCL_PREFILL_IQ4NL_DEQUANT=OFF`; (B) only that option changed to ON. Hold all remaining CMake cache entries, host/device compiler invocations, optimization level, language mode, SYCL target(s), device-code-split mode, `-fsycl-rdc`, link mode, include paths and macros constant. In particular, do not let the ON tree inherit different `-ffast-math`, `-fno-fast-math`, FP contraction, LTO, or target architecture flags. Capture cache diff and `compile_commands.json` diff; whitelist only the requested option and its two expected target compile definitions. Pin compiler/tool versions and hashes, full configure/build commands, source revision, compile-command file hash, and final executable hash. Avoid comparing two pre-existing binaries without establishing these pins.

For each executable and any final linked host object being qualified, use the installed matching DPC++ `clang-offload-extract` to copy embedded target bundles to a fresh evidence directory; Intel's documented form is `clang-offload-extract <binary> --output=<prefix>`. Inspect the extracted bundle target identifiers as text first, then use the matching `clang-offload-bundler` with the exact listed target to unbundle the Intel SPIR-V image. For a statically linked archive, also inventory archive members and extracted offload objects, but treat the final executable as the inclusion authority: an unused member may contain an image that the final link discarded. Intel documents both the linked executable extraction flow and target-bundle inspection. [Extracting SYCL device images](https://intel.github.io/llvm/developer/Debugging.html#extract-device-binary-from-sycl-application)

Disassemble SPIR-V with the matching `spirv-dis` and retain the binary and disassembly hashes. Inspect `OpEntryPoint` names and the body/dataflow for the private kernel and generic path, not just `strings` or host `nm`. Compare OFF and ON image inventories, entrypoint lists, and relevant kernel body. Record whether the private entry is absent from every Intel device image in OFF and present in at least one final ON image. If names are transformed or split, follow the image's kernel metadata/symbol table; explain the mapping rather than inferring from mangled source names. Keep generated listing slices small; store compact hashes, names and necessary instruction excerpts, not duplicate large dumps.

Tool command details can vary across compiler releases and old/new offload packaging formats. Resolve actual installed tool paths by listing the oneAPI 2026.1 compiler bin directory and use tools from that same installation; do not use help output as evidence of the binary under test. The LLVM offload design explicitly describes archive member extraction and more than one fat-object packaging representation, so process both the final executable and relevant archive/object members when the build layout requires it. [Offload packaging and archives](https://github.com/intel/llvm/blob/sycl/sycl/doc/design/OffloadDesign.md)

## Lowering comparison and runtime boundary

For an instruction-cost hypothesis, obtain a target-specific artifact using a CPU-only method: either compile the same extracted SPIR-V with the matching installed Intel GPU offline compiler for the exact architecture and retain its native binary/disassembly, or request a supported target AOT build with the same source, compiler, optimization and backend settings for both variants. Compare the IQ4NL private kernel against the generic type-20 kernel with identical architecture/backend version. Record kernel entry mapping, instruction totals by category, memory operations, conversions, branches, register/spill evidence if available, and exact disassembly hashes. If the local IGC does not expose native disassembly for this artifact, state that the instruction comparison is unavailable; do not substitute SPIR-V operation counts for native instructions. Official DPC++ docs describe AOT as backend compilation at build time and JIT as deferred backend compilation; Intel recommends consulting the matching local `ocloc` manual because supported backend syntax is release-dependent. [AOT vs JIT and backend selection](https://intel.github.io/llvm/design/CompilerAndRuntimeDesign.html#ahead-of-time-aot-compilation)

An AOT image generated offline can show how that compiler/backend lowers the input for the chosen architecture. It is not proof of the exact Level Zero JIT result used by the normal `spir64` executable. For runtime-created-image evidence in a later authorized run, `SYCL_DUMP_IMAGES=2` is documented to dump images actually used at runtime (as distinct from dumping every image in the binary). Pair this with a trace that records successful `zeModuleCreate`/`zeKernelCreate` or corresponding UR calls and kernel names, image hashes, driver/IGC versions, and cache state. The documented `SYCL_UR_TRACE=2` traces UR calls; verify it actually reports relevant create calls in the installed release, or use an instrumented Level Zero/UR interception tool. A graph/kernel split table alone is static metadata, not observation of module or kernel creation. A persistent cache can change what gets compiled/reused; pin/record cache policy and cold/warm status. The DPC++ docs mark these variables as development/debugging interfaces whose semantics may change. [Runtime image dump and tracing](https://github.com/intel/llvm/blob/sycl/sycl/doc/EnvironmentVariables.md#debugging-variables-for-dpc-runtime) [Persistent compiled-code cache](https://github.com/intel/llvm/blob/sycl/sycl/doc/EnvironmentVariables.md#environment-variables)

Only after static image qualification should runtime exercise be claimed: use the supported private-path inputs above, preserve a production-caller receipt showing direct-private call counts and zero generic/MMQ/fused bypass for the claimed calls, and separately capture actual module/kernel create and launch observations. That verifies dispatch/selection for the run; it still does not establish instruction-cost reduction without native target disassembly or a controlled performance result.

## Interpretation limits

A successful OFF/ON static comparison establishes compiled-image inclusion/absence under the pinned builds. A private kernel entry alone does not prove it is called, selected by Level Zero, or used by the production prefill workload. SPIR-V differences do not establish native instructions saved. AOT-native lowering is informative but may differ from normal JIT lowering if target/backend versions, options, driver, device, or caches differ. Neither image evidence nor a synthetic parity PASS establishes production performance, default adoption, image absence from all possible targets unless all are inspected, or a full-KV result. Current registry decisions remain default OFF and do not establish speed or production adoption.
