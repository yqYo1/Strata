# R173 — Prefill external-consumer boundaries after private IQ4NL Down submit

Date: 2026-10-10 (Asia/Tokyo). Read-only source trace against the stable sibling prefill prototype. This report maps where work after a possible private IQ4NL Down submission can cross from its compute queue to host code, another queue, another prefill stage, or the next layer. It is a source audit only: no implementation, build, compiler/disassembly, tests, import, device/GPU query, profiler, model/payload, Git, lock, cleanup, service, or reset operation was performed. No injected asynchronous fault was tested.

## Finding

The private Down dequant is submitted within the native-expert callback on `m.cs`; its same-queue consumers (down GEMM, MoE combine, residual write and subsequent same-stage commands) are ordered by the in-order compute queue. The meaningful host visibility boundaries are later chunk callbacks, layer-major residual copies, stage handoff, and method return/drain. Several have a completion wait, but the source uses `wait()` rather than `wait_and_throw()` at these boundaries. Thus completion before data consumption is often present, while reliable async error delivery before that consumption is not established.

`DPCT_CHECK_ERROR` does not fix this distinction. Direct definition in `sycl/include/dpct/dpct.hpp` catches `std::exception` thrown by the expression, prints `what()`, and returns `default_error`; it does not call a queue's asynchronous handler. Applied to `queue.wait()`, it can report a synchronous exception from that call, but it does not turn the wait into `wait_and_throw()` or prove queued async errors were delivered. The dummy error string explicitly says SYCL has no error codes. This is a limitation of the migrated wrapper, not proof that every asynchronous failure is lost forever; later owning drains may demand rethrowing.

## Boundary inventory

1. **Private dequant to expert GEMM and combine — same compute queue, not an external handoff.** At `prefill.cpp` around 4805–4810, the native expert branch submits GU dequant and then the conditional private type-20 Down dequant to `m.cs`, before `m.gemm.f16` consumes `m.dq_d[q]`. The expert results flow into `moe_combine` on `m.cs` (~5018). Queue ordering is the relevant dependency; no host wait belongs between each expert's dequant and GEMM. `dpct::sync_barrier(m.used[slot], m.cs)` around the slot release/reuse protects queued staging-slot order and is not a host async-error receipt.

2. **Intra-run host diagnostics/readbacks — compute completion may precede host consumption.** Opt-in selection/debug paths read device results into host vectors and inspect/write them around ~3850–3955 and ~4918–4950; trace and residual dumps occur ~5011 onward and ~5120–5165; end-state dumps occur ~5330+. They use combinations of `m.cs->wait()`, copy events' `.wait()`, or `dpct::get_in_order_queue().memcpy(...).wait()`. When these are later than the private submit on the same in-order queue, queue order plus completion protects the host readback from racing the preceding compute. A wait on the separate default queue is only relevant where the copy itself was submitted there and carries no implicit evidence about a different queue. These are opt-in diagnostic boundaries, not a suitable production per-expert fix; most do not translate asynchronous queue failure into the owning prefill result.

3. **Layer-split residual to successor stage — explicit host copy and async stage handoff.** In `run_impl`, when `next_ != nullptr`, around ~5112–5138, the code copies `m.R` to the stage handoff host buffer `h` on `m.cs`, then checks both the memcpy event and `DPCT_CHECK_ERROR(m.cs->wait())`. Only afterward does it invoke `on_stage_chunk`, await the direct successor's prior future if valid, set `next_->hand_in_ = h`, and launch `next_->run_impl(...)` asynchronously. This is a genuine producer-to-host-to-other-stage consumer boundary. The direct compute wait establishes completion before host data is forwarded, but its wrapper only detects synchronous exceptions. Awaiting `next_run_` propagates a Boolean/error string from that successor; it does not itself deliver this stage's compute queue's async errors. The design intentionally permits later stages to remain active, so do not replace this with a wait for the entire downstream pipeline at every chunk.

4. **Chunk callbacks — compute to host callback.** Around ~5183–5203, when `on_stage_chunk` or `on_chunk` is installed, the code calls `DPCT_CHECK_ERROR(m.cs->wait())`, then invokes callbacks with the completed chunk. This is the key callback consumer boundary: host callback code may inspect/copy/retain `m.R`, and layer-major's callback uses it as the input to the next operation. Completion precedes callback invocation; async delivery before callback is not demonstrated. The callback's own result/error is checked and can stop the run, but that is distinct from a queue async error.

5. **Layer-major residual handoff from one layer to the next.** `run_layer_major` sets callbacks before each `run_impl` at ~2743–2760. For nonfinal layers its `on_chunk` copies each residual chunk either device-to-device into the GPU residual rows (`transfers.device_residual`) or device-to-host into `rows` (`transfers.activation`), and waits on the returned transfer event. The callback is reached only after boundary 4's compute `wait()`. Thus the residual copy is downstream of completed compute, and the event wait completes that copy before the next layer gets `hand_in_` at ~2740–2742. The copy is submitted on `m.cs` in the shown calls; in contrast, expert-cache layer loading uses `m.copy` and is drained separately. A compute-queue async error receipt is still absent before this residual consumer, and a copy-event completion is not a compute-queue async drain.

6. **Next layer / next chunk entry.** The next layer invokes `run_impl` after callback return; when `hand_in_` is non-null, its entry path copies that input into `m.R` via residual transfer (~2990 onward), and the transfer event is checked/waited as appropriate. This consumes the previous layer's output only after the prior callback has completed its residual transfer event. For a layer-split successor, the host pointer is consumed asynchronously on the next invocation, after producer copy/wait and future synchronization as described in boundary 3. No additional per-expert wait is needed here; if the desired guarantee is “error known before consumer,” the correction point is the existing producer-side host boundary, not every kernel launch.

7. **Layer-major loop transition and restoration.** At each layer start (~2706) the code calls `m.cs->wait()`, `m.copy->wait()`, and `m.stager->finish()` before loading the next layer's expert cache; cache DMA then runs on `m.copy`, waits at ~2728, and staging job results are checked. These are separate queue domains: the compute drain orders prior layer compute before cache/staging reuse; the copy drain orders expert cache DMA before use. `run_impl`'s final `m.cs->wait()` (~5239) is followed by a separate checked `m.copy->wait()` (~5258). The `Restore` destructor (~2681) repeats completion waits for both queues and stager before restoring the caller's state, including on early return. These waits protect resource/lifetime ordering, but plain waits are not an async-error delivery guarantee.

8. **Run return and successor-pipeline drain.** `Prefill::run` dispatches layer-major or ordinary `run_impl` and then calls `drain_pipeline` (~2353–2398). `drain_pipeline` (~5357–5366) gets the direct successor future, records its Boolean/error, and recursively drains later stages. The ordinary `run_impl` also drains its compute and copy queues at its tail (~5239–5258). Therefore work is completed before the normal return path finishes; this does not establish that async compute errors were converted into the current `run` false/error result at the earlier data handoffs. `Prefill::release` and global shutdown drains described in R167 are later owning scopes, not substitutes for pre-consumer error delivery.

## Narrow candidate boundary and remaining limits

For a private-opt-in fault receipt, the narrowest production boundaries are the existing compute wait before host callbacks/stage handoff (boundary 3/4), and the ordinary tail wait where no earlier callback hands output away (boundary 8). At these existing synchronization points, an opt-in `wait_and_throw()` caught and translated into `err`/false could make the affected run fail before host/cross-stage consumers, without adding a per-expert wait or an extra normal-path synchronization. It must cover every route that can return or hand off output early, including the split-stage branch and callback branch; a tail-only check cannot retroactively protect a callback already called. This is a candidate boundary, not an implemented or runtime-validated fix. Existing `run_impl` exception handling and later destructor/release waits need to be considered so a delivered exception becomes a usable run error and does not escape during teardown.

This only concerns compute queue errors. Expert-copy/stager failures need their own `m.copy`/stager result path; a compute `wait_and_throw()` cannot report them. A waited residual-copy event ensures transfer completion but needs its own exception/result translation. Successor future errors must still be gathered via `get()`/pipeline drain. The report does not claim source validation of all SYCL runtime async-handler semantics beyond the direct `DPCT_CHECK_ERROR` definition and the observed call sites.

No default behavior, decode behavior, model result, performance result, or full-KV adoption is claimed. The prior R167 conclusion remains: a later rethrowing release/global drain may eventually observe an async error, but it does not certify the result before it was handed to consumers. Runtime fault injection on the actual supported queue configuration remains necessary to validate any candidate.
