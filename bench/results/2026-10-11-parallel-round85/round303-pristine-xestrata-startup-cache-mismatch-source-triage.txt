# Round 303: pristine XeStrata startup cache mismatch source triage

## Finding

The recorded pristine XeStrata run exits in startup cache verification, before READY/prefill. Its stderr says `ExpertCache::verify_slot: slot 84 differs from the arena at byte 0 (of 2662400)`. In source, this check reads back the slot assigned to `profile[0]`, then compares it byte-for-byte with the same first profile expert from the host source. Thus the evidence establishes a byte mismatch in that first fill; it does not establish whether the differing bytes originated in the source mapping/layout, the host-to-device copy, or the device cache/readback path.

The observed `--expert-cache 128` becoming 144 slots is explained by the explicit per-layer policy, not an unexplained extra allocation. The native-pack path treats 128 largest-blob slots as a byte budget, divides it by the sum of one aligned blob per layer, obtains three slots per layer, and creates 48 × 3 = 144 physical slots. The log independently records exactly that result (`128 uniform slots -> 144 slots, 3 per layer`). `ExpertCache::open_sized` constructs 256-byte-aligned offsets in this same layer-major order; the cache then assigns each layer its contiguous quota. Slot 84 is therefore the first slot in layer 28's range under the logged 48-layer geometry. The failing blob length, 2,662,400 bytes, is the per-layer size passed for the first profile entry; the private profile was not opened or parsed here.

No evident slot-size/order contradiction explains this single mismatch: the sizing vector is built as quota copies of each layer's blob in layer order, `open_sized` offsets that vector in order, and `verify_slot` resolves the residency slot for the same `profile[0]` pair just filled. This is a source-level consistency observation, not proof that every runtime index or pointer is correct.
