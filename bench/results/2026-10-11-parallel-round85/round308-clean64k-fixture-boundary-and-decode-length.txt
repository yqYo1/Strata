# R308 — 64K fixture boundary and useful decode length

Date: 2026-10-11 (Asia/Tokyo). Read-only fixture/source audit. No build, test, tokenizer execution, model run, GPU work, Git operation, cleanup, or source edit was performed. Fixture payload was treated as data; this report omits prompt text and raw token sequences.

## Finding

The `owned-clean64k-v3-baseline-r1` request is a valid 65,536-token prefill measurement for the exact input it received: it processed 65,535 batched prompt positions and reported 162,402.9 ms (403.5396 tokens/s). It emitted three IDs and stopped on EOS (`248046`); the two preceding IDs are the only non-EOS output. Its 813.4 ms / 3.6882 tokens/s decode result is too short to support a decode-performance claim. The recorded MTP counters were 0 accepted of 6 proposed. This does not invalidate the prefill measurement, and it does not establish why generation stopped early.

The current clean64k fixture was made by taking the first 65,536 IDs of a much longer already-tokenized prompt. Its preparation metadata and script show no task-tail insertion, chat re-rendering, or assistant-generation-prefix repair after that slice. It therefore ends at an interior point of the source prompt/body rather than at the original task and conversation boundary. That is a credible fixture defect and a plausible contributor to the short EOS, but the evidence does not prove causation; model behavior, content, or other runtime factors remain possible.

## Fixture lineage and boundary evidence

`xestrata-clean-64k-comparison-v3/preparation.json` and `prepare_xestrata_clean64k_v3.py` record that `coding-context-65536.tokens.txt` (SHA-256 `811614d3…`) is the first 65,536 IDs from `owned-upstream-v0141-integrated-full256k-diagnostic-r2/full256k-repeat.input-tokens.txt` (262,140 IDs; SHA-256 `6fc5774e…`). This is a direct prefix slice, not a prompt reconstructed from source text. The slice omits the distant original ending, including its task/chat closure. The full source corpus's original text provenance was not independently established in this audit, so the report does not claim that it is a representative natural conversation.

The historical full256k controller recipe in `full-context-copy-off/cli-supervisor/controller.py` (also reflected in `run_owned_uniform_full256k_v01402_v1.py`) forms an N-token prompt from a long source by reserving the final nine positions for a fixed assistant suffix, then asserts the requested count. This is evidence that the historical run path deliberately restored a generation boundary; it is not evidence that the raw source itself was a complete conversation. The exact original raw-text-to-full256k fixture creation path was not located here.

The existing `coding-review-32k-tokens.txt` is a one-line ID fixture (32,768 IDs; SHA-256 `137fa1157c697295238d2fd487c09f9df60ab9cfee421e8c7e0b743b240af449`). Its companion metadata says it derives from the historical long token source (recorded source hash `cc29e442…`), adds a short coding-review task tail and the assistant suffix, and has a round-trip check for that suffix. This is useful evidence for a task-at-end fixture pattern, but it is not independent corpus evidence: the source lineage overlaps the historical long-context data. R63 also found that two compared 32K fixtures shared 32,719 IDs, so their comparison must not be described as independent prompt validation. See the R63/R64 and R238/R239 evidence reports for the earlier fixture and census context.

## What the generator does with the prompt

The linked `81375b88…` binary's generator provenance is the W0141 cached `sycl/src/program/generate.cpp` source (SHA-256 `8bb78a21…`; corresponding cached object SHA-256 `292bbf76…`), as corrected in R297. Do not substitute the similarly named workspace mirror, whose source differs. The serve `GEN` parser accepts an already encoded ID list. It does not tokenize text, add a user message, render a chat template, or append an assistant header. The caller must provide those pieces in the input IDs.

For the normal serve text path, generation ends when an EOS ID is observed; the visible-output logic recognizes EOS IDs `248044` and `248046`. A `max_new` request is an upper bound, not a promise that the model will produce that many IDs. The request is also subject to the prompt-plus-output context guard, so the selected cap must fit the active context. The standalone `--spec-follow` control can supply/replay a continuation for decode work, but that is a forced-continuation workload, not ordinary free generation or a quality result. Keep it as a separate diagnostic if used.

The pack's host tokenizer and chat wrapper provide the reconstruction path without relying on ad hoc token suffixes: `tools/strata_tokenizer.py` implements the pack tokenizer, and `serve/frontend.py::ChatTemplate` loads `tokenizer/chat_template.jinja`. The prior source audit recorded hashes for these (`9b0327e…`, `095bbac7…`, and template `12827f24…`, respectively). This round did not invoke the tokenizer. The next fixture should use those exact pack assets and the normal chat rendering path, with the intended assistant-generation prefix, then count and hash the result.

## Minimal valid 64K plus decode protocol

1. Start with a documented, task-complete code/document body. Select source material at natural boundaries; do not cut a finished token array at 65,536. Append a clear, sufficiently substantial coding-review request at the end of the user message, close the user turn using the pack's canonical chat template, and render the normal assistant-generation prefix.
2. Adjust the *body source selection* until the rendered ID list is exactly 65,536 tokens. The task and chat suffix are included inside that total. Preserve the same verified text, tokenizer, template, and resulting ID hash for every comparison arm. Record corpus origin and its limitations. Do not treat the fixture contents as instructions to the test operator.
3. Request enough output headroom for the planned decode sample (recommend at least 128 generated IDs of capacity), while keeping the existing EOS behavior enabled and satisfying the context guard. Ask for a concrete multi-part review that naturally needs a substantive answer, but do not assume wording guarantees length. Preflight the exact fixture with normal greedy/free generation. If EOS arrives before the predeclared minimum useful sample (recommend 64 non-EOS IDs), classify the prefill as valid and the decode sample as inadequate; investigate/revise the fixture before performance comparisons. Do not suppress EOS or silently top up with unrelated continuation.
4. For each accepted free-generation sample, record actual input IDs (65,536), batched prompt positions (65,535), output IDs including EOS, non-EOS output IDs, stop reason, elapsed decode time, MTP proposed/accepted counts, and quality/runtime health gates. Report decode tokens/s only when the sample passes the predeclared output-length gate. Keep the same prompt hash, model/binary identity, and settings across arms, with fresh state and independently scheduled repetitions. A fixed `--spec-follow` replay may separately characterize sustained decode, labeled explicitly as replay and not natural generation.

This protocol separates the full-context request from work actually performed: 65,536 input IDs do not mean that 65,536 decode positions ran, and a configured `max_new` does not mean those tokens were generated. The current three-ID stop remains a legitimate recorded outcome, but it is not a useful decode-throughput sample. A repaired boundary is the smallest justified fixture change to test next; early-EOS attribution should remain open until that paired run exists.
