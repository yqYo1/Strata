# Round 304: prepare-for-copy before host writes — contract and source audit

Date: 2026-10-11 (Asia/Tokyo). Read-only source and primary-document audit. No GPU/runtime operation, model/profile access, build, test, execution, Git operation, or source edit was performed. This report is independent of the D-engine mirror. The target Xe source is pristine commit `39bdadcc9e2b89b1e3c8be7bb2a603b04fa0e197`.

## Conclusion

Under the published `sycl_ext_oneapi_copy_optimize` contract, preparing a host range before the CPU initializes it is not undefined behavior. `prepare_for_device_copy` informs the implementation that the specified host range may be used as the source or destination of subsequent explicit copy operations. The extension does not require the range to be pre-faulted or populated before prepare, and does not prohibit ordinary host writes made before an explicit copy begins. The Intel guide asks applications to preserve pointer/range lifetime through all uses and transfers; it does not say the host contents must be immutable from prepare until release. The two explicit undefined-behavior rules are overlapping prepared ranges, and releasing with a pointer/context that does not match the outstanding prepare.

So the Xe ordering is permitted by the public contract: it reserves a stable virtual range, prepares subranges, loads bytes into those ranges, and only later issues explicit copies. A rule silently requiring “touch every page before prepare” is not present in the cited specification or optimization guide. If that order alone causes a prepared range to keep referring to stale physical pages, the likely classification is an implementation/backend defect or an undocumented implementation precondition, rather than caller UB under the published extension. The observed cache verifier failure alone does not prove this is the cause, so this audit does not declare a confirmed driver bug.

## Range size, alignment, and overlap

The official extension defines the prepared range as `[Ptr, Ptr + NumBytes)` and specifies no page-alignment requirement or maximum range size. Intel’s optimization guide says to use the transfer size when it differs from the underlying allocation, permits preparing less than the true allocation, and calls importing beyond the true allocation a user error. It also describes prepare/release as an experimental optimization whose range and lifetime correctness remain the application’s responsibility.

The Xe helper aligns the overall `base` to 2 MiB and bounds each piece by the device allocation limit. Internal piece endpoints come from expert/layout cuts or the final byte count; the helper itself does not round those endpoints to a page size. Its exact prepared intervals are consecutive and non-overlapping, so they do not violate the extension’s literal overlap rule. The source should still record whether all actual layout cuts are page-aligned before attributing page behavior to them; that alignment is not asserted in `register_pieces` itself.

Do not transfer an alignment restriction from a different API. The Unified Runtime’s separate `urUSMHostAllocRegisterExp` implementation explicitly requires page-aligned pointer and size, but this is not the API used by `prepare_for_device_copy`. The closest public Compute Runtime source examined for ordinary host-pointer import rounds the pointer down and size up to its page size in its Linux memory manager. That source-level behavior suggests page-rounded handling below SYCL, but does not add a published alignment precondition to the SYCL experimental API.

## COW, page faults, and the imported backing

`MAP_NORESERVE` plus the source’s own description means the 50 GB reservation does not imply 50 GB of populated physical pages at prepare time. First CPU writes can fault pages into the anonymous mapping; Linux documents `MAP_PRIVATE` as copy-on-write. That makes a COW/stale-page hypothesis coherent: if the importer resolves or pins physical pages while the map is untouched, and a later CPU write changes a page’s physical backing, a device-side user-pointer mapping established earlier might refer to old pages. The exact cache check then sees bytes that differ from the host expert.

That sequence is only a hypothesis. The available public Intel Linux source shows `HostPointerManager` constructing an external-host-pointer graphics allocation for the requested address/size, and `DrmMemoryManager` page-rounding that range before creating a GEM_USERPTR object. It does not, by itself, prove when the kernel faults or pins the pages, whether `prepare_for_device_copy` eagerly materializes backing, or how the installed kernel driver updates any IOMMU/graphics page tables after a later CPU fault. The Linux kernel pinning documentation explains that DMA pinning and writes to pinned page contents require deliberate handling, but does not establish that this Xe userptr path pins pages during prepare. No kernel source tied to the running system was inspected.

The two source-side candidates remain distinct: (1) a mapping/page-population/import interaction, including COW or stale device mapping, and (2) another host-source or H2D/readback discrepancy. The byte-zero verifier failure does not distinguish them. The fact that the program reaches the cache check establishes that the prepare call path did not throw; it does not prove the implementation imported the intended physical pages or that all later writes remained visible to the copy.

## Follow-up interpretation

The planned unchanged-source `STRATA_ARENA_HOST_USM=1` diagnostic is well-targeted and should keep the same `verify_slot` check. If host USM passes while the default prepared anonymous mapping fails, that would support an allocation/import/page-population interaction, but would not isolate COW from other changes in the host allocation path. If it fails too, the pre-touch hypothesis weakens, while source bytes, transfer/readback and other shared paths remain open. Neither outcome warrants suppressing the verifier.
