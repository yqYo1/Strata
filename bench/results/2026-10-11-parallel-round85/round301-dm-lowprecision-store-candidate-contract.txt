## Current buffer, lifetime, and exact route map

For this artifact `N=2,560`, `K=10`, and each prompt row has ten routed slots. `m.Dm` is currently `float[T*K*N]`. `moe_set_bytes` and runtime `carve` allocate the same full plane; `bytes_needed_impl` repeats the same plane in its size calculation. Compact mode shrinks other MoE arrays but **does not** shrink Dm. Each output row is indexed in the grouped expert row order; `slot_dev[token*K+rank]` selects it later. The row count is `T*K` even when an individual compact expert has at most T rows. The buffer remains live from the down products through `moe_combine`.

Current readers/aliases: the normal final reader is `moe_combine(m.Dm, slot_dev, w, shared, sg, bo, T, cs)`. Its kernel applies ten `sycl::fma(float(w), float(Dm[row,d]), sum)` operations in route-rank order, then adds `shared*sigm(sg)`. Preserve this float multiply/accumulation order; only convert each stored Dm value back to float at load. Both the scalar and aligned four-column combine kernels need a 16-bit-Dm variant, or the optimized path must be disabled for this mode. `STRATA_DBG_NAN` also scans all `T*K*N` Dm entries as float and must decode/scan the new format (or exclude the candidate when enabled). Peer paths copy Dm values as FP32. The shared-expert result `m.shared[T*N]` remains FP32 and is not Dm.

The single-GPU compact path has an existing `m.bo[T*N]` float allocation; compact base layout aliases `emb`, `mixed`, and `bo` to the same image. This is large enough for one down output with `ne<=T`, but only after all readers of that layer's `mixed`/image and the shared expert have finished. Source order and the in-order compute queue make a per-expert temporary/pack plausible; this liveness must be asserted and documented before use. The final combine overwrites `bo` with the required FP32 result. Never treat `bo` as a spare independent buffer in compact layout or overlap a live input.

## GEMM output and conversion contract

The linked `Gemm::f16` interface takes `float* Y`. The SYCL implementation in `gemm.dp.cpp` calls oneMKL with half A/B, `real_float` C, and `compute_type::f32`; `f16_event` has the same float output. It therefore preserves FP32 accumulation today, but exposes no 16-bit C storage API. No linked Strata-specific XMX Dm-output API is used by this compact call; any XMX instruction selection by oneMKL is backend behavior and does not change the declared float output contract. The custom fused and MMQ down outputs also declare float destinations. A separate XMX/oneMKL FP32-accumulate + FP16/BF16-store path is not established by these sources.

Preferred implementation shape for the compact-only first arm: keep the existing GEMM and its FP32 accumulation, write `ne*N` float results into a dead `bo` tile, enqueue one FP32→BF16 (or FP16) pack to `uint16_t Dm16 + o0*N`, then have combine widen on load and keep weights and all FMA/add arithmetic FP32. This avoids a full extra FP32 Dm plane, but adds per-output FP32 tile writes and reads plus 16-bit pack traffic. It is an extra conversion pass over each down result and may cost more than the combine's reduced read traffic; measure only after correctness. A direct half/bfloat16 C-output GEMM with f32 accumulation would avoid that staging traffic if the specific oneMKL backend supports it, but this source has no such overload and support is unverified. Do not claim a conversion-free or speed-positive path based on XMX capability alone.

BF16 has FP32-like exponent range and would avoid FP16's finite limit of 65,504; FP16 retains more mantissa bits but needs explicit overflow/underflow accounting. The user has specified “tiny” ability loss but no numeric bound. No format should be accepted from an error-only synthetic tensor or a finite-only check.

## Shared-workspace accounting: net allocation is clipped by the maximum

Use the exact compact formulas in `moe_set_bytes`, `gdn_set_bytes`, `ple_set_bytes`, `qsa_set_bytes`, `hc_set_bytes`, and the `region=max(...)` carve. For compact native fallback, before alignment the MoE term is 132,772 B/T, including Dm at 102,400 B/T; replacing Dm FP32 with 16-bit changes those to 81,572 B/T and Dm 51,200 B/T. The raw Dm plane halves, but the single allocated shared region is the maximum of independent overlaid planes. In the linked caller's current unaliased compact PLE formula, PLE is 142,352 B/T (BF16X2 arm: 147,472 B/T), GDN is 107,264 B/T, and MoE is 132,772 B/T. PLE remains the maximum after Dm is halved. This is still less than the raw Dm half-plane saving. R283 is a distinct, conditional proposal, not an adopted premise for this report; do not add its reduction to any actual capacity claim without its own acceptance.

## Predeclared qualification gates

Before opening a low-precision result, freeze the F32-storage control and candidate protocol, model/weights, routing, chunking, context length, decode settings, and comparison margins. The source-supported local quality harness needs the R294/R297 paired-continuation correction: the compiled generator's `STRATA_LOGPOS` covers tokens through `read_windows`, not long batched Prefill; the first-logits hook alone covers only the first next-token distribution. A valid paired score must capture that first distribution after the actual batched prompt, force the reference continuation token, score every subsequent fixed token, and prove exact target-position coverage.

Acceptance requires all of the following, separately reported:

1. **Whole-layer numeric/finite gate:** for each layer, compare all actual Dm output rows before and after the chosen 16-bit store, and compare final MoE `bo`. Record NaN/Inf counts, FP16 overflow/underflow/saturation and BF16 subnormal/rounding counts, plus max, p99.9, RMS, and relative error by layer. Reject any nonfinite Dm/bo or any unexplained missing/duplicate route row. Freeze error ceilings from F32 control repeatability and the explicit task allowance before candidate data; source inspection cannot supply those thresholds.
2. **Head/log-probability gate:** compare post-full-prompt first-head logits, top-1/top-K identities and margins, then paired teacher-forced per-token log-probability/NLL and top-K agreement across the intended long-context positions. Re-run the same control to establish its noise floor. Keep intended long-context and output lengths explicit.
3. **Task-ability gate:** evaluate fixed code and retrieval continuations plus representative reasoning tasks; report each task/seed and exact score delta, not only an aggregate. Pass only if all predeclared task deltas remain within the user's defined tiny-loss allowance. R299's recurrent-state papers are cautionary context, not a Dm quality prediction.
4. **Physical 262,144-cell lifecycle gate:** independently run the selected candidate through a real 262,144-token occupancy lifecycle with the final prompt-conditioning token, final cell/tail, continuation, restore/reset, and state/head comparison against same-source FP32 control; record physical occupancy/admission and verify no read/write crosses the allocation. A source bound, a shorter prompt, or another binary's previous lifecycle result does not qualify it.
5. **Fit/transfer/performance gate:** report actual selected chunk, shared-region and outer workspace receipt, device free/reserve at the correct phase, and conversion time. Do not call raw Dm bytes net capacity, and do not run performance conclusions before the above correctness/quality gates pass.

## Recommendation

Keep the compact-only, single-GPU native fallback as the smallest candidate because it confines Dm writers to one existing FP16-input/FP32-accumulate GEMM route and avoids MMQ, fused, peer, and CPU ambiguity. First resolve the PLE shared maximum if capacity savings are the purpose: under the current linked caller, Dm16's raw 400/600/800 MiB plane reduction yields zero shared-region reduction at T=8,192/12,288/16,384. If root later accepts the separate PLE alias, the conditional ceiling reduction is capped at the GDN gap shown above. Preserve FP32 default behavior for all other branches. Source inspection recommends only this bounded experiment; it does not recommend enabling or adopting it.
