Failure propagation in pristine Xe

`gpu.cpp` returns `bool` from `copy_async_after`, `event_record`, and `stream_wait_event`. Each catches `const std::exception&`, calls `fail(...)`, and returns false. `copy_async_after` assigns `done->ev` only after `queue.submit` succeeds; on failure the event object is left as-is. `event_record` likewise assigns its optional event only on successful submit. An empty event is treated by `stream_wait_event` as success/no-op.

The stream-all issuer ignores these booleans at both inline and threaded sites (`prefill.cpp` 1301–1321, 1344–1369). It marks the stage live and advances `issued` or `a_issued` after the ignored copy result. For an unpinned blob it also calls `Stager::issued_one`, whose `event_record(dma_done, copy)` result is ignored before publishing the host-buffer issued counter (Stager around 355–359). The consumer waits for the published counter, then calls unchecked `stream_wait_event` before using the staged slot (around 1374–1381 and the streamed walk around 2164–2180). Thus a failed copy can leave the copied event empty or pointing at an earlier transfer while the counter says the new transfer is ready. The host stager can similarly treat an older/empty DMA event as completion and recycle a host source buffer prematurely.

The reverse edge is unchecked too. Before reusing a slot, the issuer ignores `stream_wait_event(copy, used)` (stream-all copy path around 1308–1316 / 1355–1364). In routed-only `stage_one`, slot wait, `copy_async`, and `event_record(copied)` are unchecked (around 1971–1997); consumers later ignore the copied wait (2140–2148). The MMQ group gather path and streamed release path also ignore copied/used event submission results (2017–2037, 2155–2161, 2167–2176). If a used event submission fails, the next DMA may overwrite a ring slot while its last compute read is pending. If a copied event or wait submission fails, compute can read stale/partial bytes. An event may be empty on first failure or stale after reuse; either can satisfy an unchecked wait as no-op/old completion. The code may corrupt data or race buffer reuse; these specific submit failures do not inherently deadlock because the producer counters still advance.

The Xe GPU helpers contain the synchronous submit exceptions and translate them to false, so the callers' normal exception boundary cannot catch those failures. `Runtime` stores asynchronous errors in its handler (`device.cpp` 178–183), checks the stored error on runtime-owned submissions (`298–312`), and propagates at `wait_and_throw` (`314–335`). The helpers in question submit directly on queue handles and do not call `Runtime::check_async`; a later runtime drain may report an asynchronous fault, but that is later than the point where host counters/events currently authorize a consumer. Runtime's GPU wait watchdog is not a substitute for checking these API results.

Failure propagation in D1

D1's stream-all path does not use Xe's `copy_async_after` boolean wrapper. It submits the transfer through `ExpertTransferTimer::copy` / `q->memcpy`, retains the returned `sycl::event` for the stager where needed, then calls `dpct::sync_barrier(copied[slot], copy)` before setting `stage_live`, incrementing `issued`/`a_issued`, and publishing the slot (around 3449–3489 and 3517–3565). These operations can throw synchronously. Inline `issue_until` catches `sycl::exception`, writes a failure receipt where enabled and calls `std::exit(1)` (3491–3496). The threaded issuer catches `std::exception` and unknown exceptions and calls `std::_Exit(1)` with an explicit no-GPU-cleanup message (3567–3576). With the service ledger enabled, `transfers.copy` catches any exception and its `lane.fatal("copy_submission_failure")` terminates via the ledger's fatal path; otherwise raw `q->memcpy` exceptions reach the surrounding catches. For a synchronous transfer/barrier submission exception, no ready counter is advanced, and the process terminates instead of letting the consumer use that slot.

The D event-reuse edge uses direct `(copy)->ext_oneapi_submit_barrier({*used[...]})` before copying; consumer dependencies similarly use direct `cs->ext_oneapi_submit_barrier({*copied[...]})` (e.g. 3457–3458, 3533–3534, 4195–4200). The routed-only arm uses ordinary in-order queue submissions and `dpct::sync_barrier`. Exceptions from these sites are within the prefill's synchronous exception exits; if they throw, the subsequent staged counters are not published. D1 also records a concrete DMA completion event and generation before the host staging buffer can be reused (`Stager::issued_one` around 521–529), and its host wait checks event completion instead of blindly acknowledging a buffer. The D host wait budget is finite (five minutes) and `_Exit`s without freeing in-flight memory on timeout (`host_wait.hpp`).

This is stronger synchronous submit failure handling than Xe's bool-return path, but is not a blanket proof of all asynchronous faults. The copy queue is configured with an async handler; D's pinned `sycl_error.hpp` reports each asynchronous error and rethrows the first. SYCL asynchronous errors are dispatched at `wait_and_throw`, `throw_asynchronous`, or queue/context destruction; a plain `wait` only waits for command completion and reports synchronous errors. D's generic `dpct::sync_barrier` submits an event barrier; it does not itself drain/report asynchronous queue errors except when it takes its default-queue device-wide wait branch. Therefore eventual error discovery and the exact runtime cleanup path remain distinct from the synchronous submission contract above. In the stream-all path, when copy/barrier submission throws before counter publication, process-fatal behavior prevents ordinary consumer progress; it does not demonstrate that an asynchronous device fault is caught at that exact edge.

Normal path vs failure path

On the inspected normal path, Xe's comments and queue/event order describe the expected ring protocol: the copy queue waits on a used mark, copies bytes, records copied; compute waits on copied, reads the expert, records used; host atomics publish issuer progress only after the copy submission sequence. No source evidence here shows that these normal preconditions fail or that an observed hang used this failure mode. The defect is that Xe's returned status does not guard those transitions. D1's normal path keeps the same submission-before-counter ordering and synchronously terminates on thrown submission failures. Neither audit establishes behavior for every Level Zero/driver asynchronous fault.

Minimal fail-fast contract for Xe

Treat every operation in the staging dependency chain as a required transition: used-wait submit, copy submit, copied-event creation, consumer copied-wait submit, compute used-event creation. Advance slot state, issued/consumed counters, host-DMA acknowledgement, or resident/source-buffer lifetime only after the required operation succeeds and its event handle is valid for this generation. On any failure, record the first operation/slot/sequence/error in a thread-safe fatal status, publish that fatal status to all issuer/consumer/stager waits, and stop admitting further work. Since a failed dependency can leave GPU work outstanding, do not unwind/free the ring, pinned host source, cache slot, or model USM until every relevant queue is known quiescent. If completion cannot be established, terminate without GPU cleanup (the D1 host-wait pattern); do not return a slot or weaken the existing GPU/host watchdog. Graceful recovery is permitted only after all submitted work is successfully drained and event/counter state is reset as a new generation.

For Xe's current bool helpers, the minimal implementation point is to check and propagate each return before mutating state. Make a failed issuer operation visible to the consumer's wait predicate so it exits promptly rather than spins; make `Stager::issued_one` propagate failed event recording instead of publishing issued. Do not “fix” this by replacing a failed event with a fresh completed marker, because that falsely asserts the missing dependency completed.

Validation ideas only; none were run

- CPU-only deterministic fault injection around the staging submit adapter: with a one-slot ring and a fake copy/event backend, inject failure at each edge (used wait, copy, copied mark, consumer wait, used mark, stager DMA acknowledgement). Assert that the corresponding counter/generation is not published, the consumer never gets a readable slot, host source reuse is denied, every blocked host waiter sees the failure within the existing bounded wait policy, and cleanup is not called with work of unknown completion. Include first-use empty events and reused stale event handles, plus both inline and issuer-thread modes. Keep the ordinary successful state-machine case as a control.
- Main-owned small-GPU admission: only as a separate fault-injection diagnostic process, not as part of rawXe/64K speed samples. Inject each selected API failure before backend submission (or through a test adapter), verify the process emits the named fault/sequence receipt, exits without normal GPU destructors when completion is uncertain, and does not advance into the consumer kernel. A separate non-injected smoke case may verify normal ring reuse. Preserve existing process deadline and GPU watchdog and retain one compact failure receipt; do not trigger real driver loss or weaken watchdogs.

Official rule used

The Khronos SYCL 2020 specification distinguishes synchronous submit errors from asynchronous queue errors. Queue/event `wait` waits for commands; `wait_and_throw` / `throw_asynchronous` deliver queued async errors to the handler. The source contract above therefore requires checking synchronous submission status at its publication edge and separately draining/reporting async errors at a safe completion boundary. Reference: [SYCL 2020 specification, queue and event waits and asynchronous errors](https://registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html), especially sections 4.6.6, 4.6.7, and 4.13.1.
