Exact bound for `--spec 4 --spec-min-p 0 --spec-split --pool-tasks 6`

`o.spec` is passed directly as `max_t` to `Verifier::init` for this non-pipeline path (`sycl/src/program/generate.cpp:12120-12140`); `Verifier::init` stores it as `max_t_` and requires it not exceed CPU `MAXT` (`sycl/src/core/verify.cpp:418-432`). `S_mtp` is `min(mtp_max_t, S)` when explicitly limited, otherwise `S`; with the requested `S=4`, it cannot exceed four (`generate.cpp:8448-8452`, and serial path `12365+`). For `spec_min_p == 0`, the serial window loop skips the probability-trimming loop, sets `T=S_mtp`, then first-window logic reduces only the initial window to `T=1` (`generate.cpp:12380-12406`). Thus later windows can reach four tokens; they cannot exceed four. There is no suffix-draft or lookup-chain expansion in the stated configuration (those options enlarge `o.spec` only when enabled; `generate.cpp:2268-2277`).

The verifier's split path divides tokens into A `[0,(T+1)/2)` and B `[(T+1)/2,T)` (`verify.cpp:773-775`). Its host-boundary executor calls the pool separately for each group, passing `te-tb` as `n_tok`, with the corresponding group-offset activation and routing pointers (`verify.cpp:1681-1724`). At maximum `T=4`, these are two-token pool calls. `expert_pool_dispatch_multi` uses that `n_tok`; its `ExpertJobMulti.nt` is incremented once per CPU-routed occurrence of a given expert within that call (`sycl/src/core/expert_source.cpp:2549-2559, 2722-2796`). Therefore under the exact flags an individual native expert job has `nt <= 2`. Without split it could reach four, still below eight. `--pool-tasks 6` is supplied to the pool initialization (`generate.cpp:4177`) and controls row-task scheduling; it does not merge group calls or increase `n_tok`/`nt`. This is a source-derived upper bound, not an observed histogram.

Decision on the R30 IQ panel proposal

The R30 candidate was an 8-row-by-8-token IQ GU panel, based on pinned llama.cpp IQP. The implementation uses a minimum expert batch of eight (`ggml/src/ggml-cpu/ggml-cpu.c:1680-1682` in pinned commit `85c55223caf0a2ad0d1d88e5a73ab3fe36107867`; panel contract/code in [`iqp.cpp`](https://github.com/ggml-org/llama.cpp/blob/85c55223caf0a2ad0d1d88e5a73ab3fe36107867/ggml/src/ggml-cpu/iqp.cpp)). This configuration cannot reach its eligibility threshold: maximum grouped native `nt` is two. The candidate is inapplicable to the requested traffic and should not be prototyped against the synthetic NT8 wrapper harness as evidence for this configuration.

No distinct NT1–2 kernel or scheduling technique is recommended in this round. R30 already notes that Strata decodes each IQ block once across the available tokens for a row; R17 covers task shaping, R21 cache-line/spill work, R25 Q2 Gate/Up pairing, and R9 hot-expert predecode. The nearby upstream IQP source supports only the >=8-token panel. The inspected material did not establish another primary-source mechanism with a credible path to improve this exact small-NT IQ GU route. Avoid filling the gap with a speed conjecture. A future different configuration that removes `--spec-split` would raise the source bound to four, still insufficient for IQP; a verifier window of at least eight plus unsplit execution and a measured real-route histogram would be prerequisites before reopening that panel.

Falsifier and scope

The bound would be falsified if the stated exact flags permit `Verifier::run` to call `expert_pool_dispatch_multi` with `n_tok > 2`, or if a single group call accumulates an expert's tokens from both groups. The inspected call sites show neither. Confirm via a read-only source update if the call graph changes; otherwise a future request-scoped actual `nt` histogram can check runtime exposure but is not needed to establish this structural maximum.
