Call path and exact NT1 dot implementation

In `sycl/src/core/expert_source.cpp:2549-2559, 2722-2796`, the verifier dispatch builds a `NativeExpertJob` per CPU-missed expert and increments its `nt` for each routed occurrence. `src/kernels/cpu/native_expert.cpp:106-160` resolves the GU path; the default multi-token threshold is 2, so NT1 falls through to `NativeDispatch::Ggml`. `native_gu_rows` then obtains the layer format's `ggml_type_traits_cpu::vec_dot` once for that call, and calls it twice per output row (Gate and Up), iterating tokens inside the row (`native_expert.cpp:167-192`). This is a per-token dot path, not evidence that native expert work is serial globally: six row tasks and their worker scheduling are separate.

The pinned ggml CPU trait table maps IQ3_XXS, IQ3_S and IQ2_S to `ggml_vec_dot_iq3_xxs_q8_K`, `ggml_vec_dot_iq3_s_q8_K` and `ggml_vec_dot_iq2_s_q8_K`, each with Q8_K activations and `nrows=1` (`ggml-cpu.c:349-365`). IQ4_XS is likewise a Q8_K dot trait. The matching x86 dot bodies in pinned `ggml-cpu/arch/x86/quants.c` are guarded by `#if defined(__AVX2__)`; the active branches use AVX2 integer SIMD (`_mm256_*`, `maddubs`, `madd_epi16` and 8-lane accumulation), with generic scalar code only in the `#else` branch. The IQ3_S implementation assembles IQ codebook vectors with scalar `iq3s_grid[index]` reads and `_mm256_set_epi32`; its source explicitly leaves `_mm256_i32gather_epi32` commented out and says the gather tested slower on the author's Ryzen 7950X (`quants.c:3384-3590`, especially 3420-3450). IQ2_S similarly uses scalar codebook indexing to assemble vectors (`quants.c:3075 onward`). Thus “ggml fallback” here is the pinned library's per-token AVX2 dot path, not the scalar-only generic fallback.

Build/CPU mapping: the exact T build's `build-sycl-decode-pool-phase-timing-v0141-v1/compile_commands.json` records `icx -O3 -march=native -fno-associative-math` for pinned `ggml-cpu/arch/x86/quants.c` and `ggml-cpu.c`; its CMake cache records `GGML_NATIVE=ON`. The source has the AVX2 implementation under the `__AVX2__` compile-time guard. Root's T/old-production CPU admission identifies the actual host as Ryzen 5 5600X (AuthenticAMD, AVX2/FMA/F16C, no AVX-512 or AVX-VNNI). This supports selecting the AVX2 branch for that native build/host pair. I did not inspect object instructions or claim a particular instruction sequence from disassembly; no exact compiled-symbol disassembly artifact was used. This distinction matters: the NT1 call is ggml's implementation and ABI, while ggml itself has compiled AVX2 specialization.

Why no distinct candidate is justified

1. The closest algorithmic alternative is a one-token Strata IQ row kernel. That is already in `src/kernels/cpu/iq_avx2.cpp` / `iq_avx2_rows.inl`; the dispatcher deliberately holds it for NT>=2 by default. The source documents the measured decision: multi-token rows beat ggml at three tokens, but showed no faster result at one because both are bound by codebook lookups (`native_expert.cpp:106-160`). The narrow opt-in IQ3_S MT1 rule is limited to a no-AVX512 CPU with the selected fast-gather configuration and is already implemented as a dispatch exception. The root histogram's reported scalar variant does not show a gather-enabled Zen3 route. Re-enabling or broadly lowering the threshold would repeat an existing implementation/known selection experiment, and NT1 rounding differences still require the full established model gate.
2. A gather-based lookup rewrite is also not a new lead: Strata's IQ256 kernel already has gathered grid-decoder variants for IQ3_XXS/IQ3_S/IQ2_S (`iq_avx2.cpp:293-345`), and the pinned ggml IQ3_S author code records the reason a direct AVX2 gather was not selected on a Ryzen 7950X. That is not evidence that the gather loses on the 5600X, but is sufficient to reject an unmeasured recommendation as “new.”
3. The previously proposed row-panel algorithm is R30's NT8 IQP route and is not applicable to this traffic. R17 paired GU reuse, R21 row/cache-line concerns, R25 Q2 pairing, R9 hot-expert predecode and the already-existing block-once NT>1 decoder are excluded by assignment.
4. Repacking to another quant layout would change stored model weights/format and is outside the exact active GGUF path; it cannot be treated as a no-approximation kernel substitution without a distinct model-quality and output-admission study.

Therefore this round recommends no new NT1 mechanism. That is a bounded no-candidate result, not a claim that the current implementation is optimal. `NT1 selects ggml` alone does not identify the caller/job assembly, indirect-call overhead, codebook decode, CPU-memory behavior, task scheduling or GPU/CPU overlap as the critical path. The partial histogram cannot distinguish those costs. A future candidate would need both source-mechanism novelty and exact-production component evidence before an end-to-end proposal; any changed floating-point order must pass the unchanged head/state/logprob/MTP gate.
