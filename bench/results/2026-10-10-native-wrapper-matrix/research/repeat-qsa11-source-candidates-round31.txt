## Evidence boundary

It does not by itself implicate stage reuse.

## Candidate and discriminating observation

The narrowest remaining source-level candidate is an input divergence before the layer-11 K/V and indexer projections, potentially in the preceding GDN/MoE/residual path or its reused compact workspace. K/V quantization and indexer pooling both consume per-token activations, so their simultaneous first change at the same cell is compatible with that explanation. The first changed cell is 24 tokens into an 8192-token chunk, so a chunk-boundary-only explanation is not supported by the location. No inspected line proves this candidate.

A discriminating capture should compare, between first and repeated executions, the layer-11 input residual and the outputs of `attn_k`, `attn_v`, and `indexer.k_proj` at rows 0–31 of chunk `p0=98304`, before KV append/quantization; also compare pre-append stage bytes and host K/V for cells 98328–98331. If the residual/raw projection already differs, trace the first preceding layer's output; if projections match but persisted K/V differs, isolate `kv_append`/stage writes; if K/V matches but pooled output differs, isolate the indexer append kernel. Existing evidence does not currently include these intermediate values.

## Conclusion

This audit found no concrete source defect that explains the reported byte onset. It narrows the next useful observation to transient layer-11 inputs/projection outputs versus append outputs. Treat the suspected upstream activation/workspace path as a falsifiable lead, not a diagnosis. No status or validation result is changed.
