# H native-dispatch histogram controller review (round 32)

Read-only independent review of v2 controller `run_owned_native_dispatch_histogram_v0141_code32k_v2.py` (SHA256 `ff6d8ad537b9e9fb81511725dd5cf936a3a0d460bae271d79707777f38d0a599`), its source pins and existing receipts. No preflight, test, runtime, GPU, profiler, cleanup, or Git action was performed. Scope is source/schema/admission correctness, not runtime qualification.

## Findings

I found no remaining blocker in the requested producer-order, request-binding, or GU/Down arithmetic checks.

- Producer order is source-backed. `ExpertPool::native_histogram_begin()` clears both phase tables and marks the histogram active at `sycl/src/program/generate.cpp:10404`. Native split-multi records GU after `run_phase(5)` and Down after `run_phase(6)` (`src/kernels/cpu/pool.cpp:849-873`); `wait_done`/`wait_parked` in `run_phase` precede the counter read (`:691-700`). `native_histogram_report(stderr)` follows `ver.wait_commit` (`generate.cpp:11297-11304`); its final `fprintf` is followed by `fflush(out)` (`pool.cpp:827-846`), and `DONE` is printed/flushed afterward (`generate.cpp:11498-11505`). Thus a request’s flushed histogram precedes its protocol completion.
- Controller request binding is coherent: it records stderr file offsets immediately before sending each `GEN` and after receiving that request’s `DONE` (`v2:609-629`), then requires exactly one histogram and exactly one matching phase line wholly inside each interval (`:711-731`). The inferior stderr is opened as a direct file descriptor by the owned helper (`owned_gdb.py:55-63`), so offsets do not depend on an asynchronous log-copy reader. Complete newline, ASCII, and 64-KiB line bounds are checked before parsing.
- GU/Down totals match caller semantics. The producer adds one expert count, `nt` tokens, and `FF` or `H` output rows per caller job (`pool.cpp:778-813`); the frozen model geometry is GU 640 rows and Down 2560. It records after completed worker phases, on the calling thread. The parser checks `tokens == experts*NT`, row arithmetic, totals by phase, and per-NT expert equality. These are logical jobs observed on the native path, not task fragments or CPU-job coverage; the controller/report correctly avoids stronger claims.
- The prior v1 parser accepted NT1–8, although the task’s exact spec4/split bound is NT2. V2 changes the parser to reject NT>2 (`:103`) and records that source-bound ceiling. That correction is appropriate for this exact profile. `MAXT=8` is only storage capacity and is not evidence that this run’s structural ceiling is eight. The v2 bound should remain scoped to this exact spec4/split diagnostic, not generalized to other execution modes.
- Zen3 expected labels and settings agree with the pinned implementation: resolver settings are taken from the dispatch functions (`pool.cpp:816-845`); GU NT1 falls back to ggml, supported GU types at NT2 use IQ256 at default minimum 2, Down type20 uses IQ4NL256 at NT2, Down type42 uses Q2 AVX2, and selected variant remains scalar on this non-VNNI/non-AVX512 CPU. The parser’s exact profile and eligibility checks are counter-schema checks; they do not claim that selection is recomputed for every worker.
- Root correction to v2’s prior-T build admission is sound: it reads the separately pinned T build receipt (`:260-267`) rather than treating the H build’s unrelated prior-admission list as the T build record. H receipt admission additionally checks closed/complete state, empty cleanup/survivors, dead recorded process identities, binary digest, and recorded source digests (`:191-219`). The flags receipt is bound to this build/binary and checks complete source/object coverage with no missing or differing flags (`:223-227`). The passed CPU matrix is properly treated as CPU wrapper parity only, not model/GPU dispatch qualification (`:304-314`).

## Limits to retain

The histogram only sees `run_split_multi_native` jobs with the H native pool path. It is not a count of every routed expert, all worker calls, or fallback work. The parser’s positive matched phase totals establish some exposure in both phases; they do not prove every model type or every route was exposed. Existing reference comparisons and lifecycle/fault gates remain independent and necessary. I did not find an arithmetic, flush/order, or offset-binding issue that warrants changing v2 before the root’s serial CPU admission.

The prior v1 review statement allowing NT through 8 is superseded by v2. This report makes no runtime, correctness, performance, adoption, or GPU-execution claim.
