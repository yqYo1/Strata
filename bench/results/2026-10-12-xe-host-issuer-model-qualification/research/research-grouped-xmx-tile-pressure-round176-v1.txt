## Decision

The active fallback’s nominal XMX workgroup tile is 128×256, but the source divides that into sixteen 32×64 subgroup tiles. Each subgroup keeps a 4×4 array of 8×16 FP32 `joint_matrix` accumulators: 16×128 values = 2,048 FP32 values per 16-lane subgroup, or a structural 128 FP32 accumulator values per lane (128 32-bit slots) before operands, pointers, bounds, and compiler temporaries. This is a source-level resource count, not compiler allocation evidence. The kernel requests Intel large-GRF mode (256 GRFs); the existing comment says the 16-accumulator form and operands spill with 128 GRFs. No native B570 binary inspection or current spill measurement is available.

**Rank 1 conditional candidate for a finite AOT discriminator:** a second grouped XMX specialization with two-by-two (rather than four-by-four) 8×16 accumulator fragments per subgroup. That gives a 16×32 subgroup output tile and a 32×64 workgroup tile with four 16-lane subgroups. The structural accumulator footprint falls from 128 to 32 FP32 values/lane. This changes the kernel’s intra-subgroup accumulator tiling; changing only the current `WM/WN` workgroup dimensions would not reduce the per-subgroup accumulator footprint, because `SGM=4` and `SGN=4` are fixed in `tile()`. The candidate is worth Main-owned AOT/codegen screening only if the matched target’s exact current lowering shows material spill or register/occupancy pressure under its admitted large-GRF mode. It is not eligible for dispatch adoption from this static report. If that discriminator shows no spill/pressure, stop rather than pay the smaller-tile scheduling cost.

For an ideal divisible interior, the proposed 32×64/four-subgroup workgroup covers one quarter as many outputs as the current 128×256/sixteen-subgroup workgroup. It therefore needs 16 times as many workgroups for the same M×N extent and four times as many total subgroup instances, while each subgroup’s accumulator footprint is one quarter. This is the explicit trade: potentially lower per-subgroup register pressure against more workgroup and matrix-fragment scheduling. It can lose even if it removes spills. The two model N dimensions (GU 1280, Down 2048) divide the candidate N tile 64; the K dimensions (GU 2048, Down 640) remain multiples of the existing 32-value prefetch step. No transfer of measured speed is claimed.

## Quantified source algebra and alternatives screened

Current per-subgroup output is 32×64 = 2,048 elements. Its 4×4 `joint_matrix` accumulator array has 16 matrices, each 8×16 FP32 = 128 values, for 2,048 accumulator values/subgroup. Dividing by subgroup width 16 yields 128 values/lane. Proposed 2×2 accumulator fragments give 16×32 = 512 values/subgroup and 32 values/lane. These are arithmetic storage counts only; joint-matrix allocation, lifetimes, compiler scalarization, register assignment, and spill traffic require codegen evidence.

Current direct XMX `tile()` declares no `local_accessor`, so its explicit local-memory/SLM allocation is zero. It prefetches with `joint_matrix_prefetch` at PD=3 (96 K values ahead in the current KC units) and stages no A/B tile through software-managed local memory. The portable `mma_gemm.cpp` is a separate route that uses two SLM buffers and a 32-value K step; changes there would not tune the current XMX specialization. The XMX direct path already uses the requested 256-GRF mode, so an environment-only larger-GRF flag is not a candidate.

- **Smaller workgroup shape alone:** rejected as a register-pressure candidate. The existing `tile<E,WM,WN,PD>` retains the same subgroup-local 4×4 accumulator array when `WM/WN` change. A meaningful accumulator-pressure candidate must change `SGM/SGN` and subgroup tile coverage together. Workgroup-only tiling can still alter scheduling but has no demonstrated bottleneck here.
- **Shorter prefetch distance (PD 3→2 or 1):** not ranked. It is an easy specialization but no retained evidence shows the current global prefetch sequence is harmful; it may merely shorten memory lookahead and hurt latency hiding. Compare only after codegen or a bounded native discriminator identifies prefetch/register pressure.
- **SLM/double-buffer rewrite:** not eligible for this XMX branch. It adds explicit copies/barriers to a path currently reading row-major USM with joint-matrix loads and no SLM. The existing SLM-staged portable MMA implementation is another backend and has its own capability-gated fallback.
- **Grouped row-count bucketing (R164):** distinct from tile pressure and previously screened. It can reduce groups reserved by `max_rows`, but requires new metadata/ABI and exact route census; it does not reduce an active subgroup’s accumulator footprint. Not repeated as the candidate here.
- **External implementations:** DeepGEMM’s SM100 mega-MoE uses expert-row/block counts to form variable expert block ranges, but is NVIDIA-specific and is not a direct Xe kernel or tile-size prescription: https://github.com/DeepSeek-ai/DeepGEMM/blob/main/deep_gemm/include/deep_gemm/impls/sm100_bf16_mega_moe.cuh. Intel AutoRound ARK documents an XPU grouped-GEMM interface with per-expert token counts, but it does not establish a matching Strata GGUF-IQ path or a better XMX tile: https://github.com/intel/auto-round/blob/main/auto_round_extension/ark/README.md. These reinforce that ragged row metadata and product tile pressure are separate concerns.
