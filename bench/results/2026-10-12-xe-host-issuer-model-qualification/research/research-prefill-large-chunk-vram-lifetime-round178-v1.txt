## Current run boundary supplied by Main

The current closed diagnostic context supplied for this question is a B570 10-GiB device, 64K prompt with --max-context=262144, native GGUF, INT8 main KV with kv_resident=32768, --no-prefill-borrow, fixed T8192, effective ring 16, expert group 16, native batch 0, fused 0, CPU share 0, PCIe share 0, cache 144 slots / 281 MiB, and 714 MiB reported READY free. The physical main-KV allocation of 6.1875 GiB is carried forward from the earlier source receipts; R178 did not query or remeasure it. Six quiet T8192 64K prefill samples average 353.577 tokens/s. This remains far below the 1,000 tokens/s goal. The passing 32K output and fault checks do not qualify a larger chunk, warmed decode, a cache rebuild, or full-context endpoint execution.

kv_resident=32768 is a residency limit, not permission to lower the logical 262,144-position session. For this proposal, keep max_context=262144, the same INT8 KV format and resident-cell setting, the existing host-backed cells/page map, and all prefix state. Do not treat a short physical resident window as a short context.

## Source-derived prefill request growth

Current Prefill::bytes_needed() mirrors init()'s counted carve and returns that carve plus 8 MiB alignment slack (src/prefill/prefill.cpp:1064-1107). The shared attention/MoE region is the maximum of the GDN, QSA, and MoE sets, and carve() lays all three views over that one region (:773-833). The checked T-row Xs/GU/Hh form is already present in this production source; GU and Dm remain FP32 and Dm remains T*K*N route-sized (:640-657, 818-832). The compact MoE path is opt-in through STRATA_PREFILL_COMPACT_MOE_SCRATCH and requires the no-MMQ fallback (:628-639). The run settings supplied for R178 do not state that effective flag, so the table below is explicitly the favorable compact no-MMQ branch; if it was disabled, the actual MoE request is larger. No new MoE scratch saving is assumed.

For the supplied model geometry, N=2560, HC=4, D=10240, LR=320, K=10, C=10240, ZV=6144, and HV=48 (prefill.cpp:65-66). In the favorable no-MMQ, compact T-row path, exact source take arithmetic gives:

| T | GDN set | QSA set | MoE set | Region maximum |
|---:|---:|---:|---:|---:|
| 8,192 | 1,180,698,624 B | 1,120,979,712 B | 1,087,671,808 B | 1,180,698,624 B |
| 12,288 | 1,771,046,912 B | 1,634,831,104 B | 1,631,505,920 B | 1,771,046,912 B |
| 16,384 | 2,361,395,200 B | 2,148,682,496 B | 2,175,340,032 B | 2,361,395,200 B |

GDN is eight aligned takes and evaluates to 144128*T + 2048 B. Thus the 8,192→16,384 region alone grows exactly 1,180,696,576 B (1,126 MiB). QSA also grows with T; all other chunk-shaped takes in bytes_needed() also grow or change with T. The 1,126-MiB region delta is therefore a strict lower bound on total additional prefill request, not the full P(16384)-P(8192). It excludes runtime allocator rounding/fragmentation and any extra graph or pinned-host allocations. The old T6144/T8192 arithmetic in R162 is a cross-check of these same take formulas; R178 recalculates the values above against the current production source lines and does not borrow R136's older noncompact totals. Since the compact flag's effective value was not supplied, this lower bound must not be reported as the measured run's exact allocation.

Against the supplied 714 MiB READY free, dropping the whole 281-MiB GPU cache would expose at most 995 MiB before reconstruction. That is 131 MiB short of the region-only lower bound for T16384; it is further short of the actual total request growth. This arithmetic does not prove T16384 impossible: some additional independently owned allocation would have to be releasable, and the runtime allocator may report a different usable amount. It does prove that “release the current cache” alone is not enough to claim T16384 admission. T32768 requires strictly more still. Any proposed admission must calculate full Prefill::bytes_needed(g, ss, T), then account for independent init() allocations, device allocation limits and current free bytes on the target, with a hard fail before prompt consumption if the request cannot fit.

## What is live, what can be rebuilt, and what cannot be dropped

The session is allocated at session_bytes(g, o.max_context, K) before prompt processing (src/core/session.cpp:58-131, src/program/generate.cpp:3494-3519). It includes QSA state and KV, GDN recurrence/convolution state, shared decode scratch and PLE history. This is sequence state, and graph/session consumers keep its addresses. Preserve it across prefill and decode; relocating or sizing it for a shorter context violates the full-context condition.

The expert cache is separately owned. Its current 281 MiB is the clear candidate GPU residency to free for a phase transaction, provided its source remains authoritative in host RAM. Save the slot-to-expert map, ranking/profile/adaptation metadata, and current cache identity; the expert payloads can be reloaded from the retained ExpertSource instead of copied into a second RAM snapshot. Do not discard the source's host-resident or mapped expert backing as part of freeing VRAM. A half-cache policy preserves only the retained slots; it frees less than 281 MiB and needs an explicit saved map for which experts survived. This configuration's host/device residency maps (host_res, d_res) and dispatch views are passed to Prefill and decode (generate.cpp:4676-4680, 10129-10168); after reconstruction, refill slots, publish a coherent new device map and refresh every view that captured the old base, slot offsets, count, or map.

The persistent decoder graphs are not an obvious pre-prompt reclamation pool in this native standalone case. Native packs skip session_capture and session_capture_token; the verifier captures lazily on its first run, which follows prompt completion. MTP is different: it owns draft weights, its own K/V, device work buffers and graph executables (src/core/mtp.cpp:197-227, 268-360), and Prefill invokes its KV-update callback per chunk. Its prefill graphs may be captured while the prompt is being consumed (:920-945, 1060-1145). The MTP weights and state must stay live to preserve the current speculation path; its prompt graphs are also needed during Prefill. Destroying/rebuilding MTP wholesale would require reloading its model and restoring or recomputing its draft KV through the full prompt. That is a separate, unmeasured reconstruction design, not a presently proven free-byte source. Main's no-batch/no-pipeline setup removes batch-slot and pipeline-window allocations from this current ledger.

The Prefill object owns its own buffers when borrow == nullptr; it also owns queues/events, stager workers, host staging, PLE staging and other lifetime state. release() drains its compute and copy streams and joins the stager before freeing owned buffers (prefill.cpp:539-560). In the present implementation it is destructor/reset cleanup, not a validated reusable public phase API: fields are not cleared for repeated teardown. A phase swap therefore needs an explicit idempotent retire and fresh-Impl/re-init transition. It must happen only after the final chunk and MTP callback have completed, the Prefill streams have drained, and every staging worker has joined. Retiring Prefill scratch after the prompt helps restore decode residency; it does not provide memory for the earlier larger chunk allocation.

For a fresh native standalone prompt, verifier capture graphs are not yet built. If a future path reaches the boundary with a cache-dependent capture already live, those graphs must be destroyed before the cache allocation they reference is released and recreated only after cache storage/map metadata is stable. Verifier::run captures window/commit graphs at first use (src/core/verify.cpp:1437-1468); its init copies cache slot offsets to device memory (:429-440). A device sync alone cannot fix stale pointer snapshots.

## Minimum candidate architecture and safe overflow rule

The least stateful candidate is one full phase transaction for standalone generation:

1. Before Prefill::init, reach a global quiescent point; release the entire 281-MiB cache allocation and any actually existing cache-address graph owners, retaining source weights, profile and logical cache-map metadata in RAM. Keep the 262,144-context SessionState, main KV backing/page map, PLE state, MTP weights/state and the exact native input stream alive.
2. Admit a fixed larger T only if measured READY free plus the identified released allocations covers the complete Prefill request, independent initialization buffers, allocator headroom and any graph allocations still needed during chunk execution. Do not lower max_context, change KV format/resident cells, trim logical prefix, borrow stale cache slots, or silently fall back to a smaller context.
3. After the last prompt chunk and MTP KV callback, drain Prefill's compute/copy work, join the stager, retire only Prefill-owned storage, re-open/refill the cache from RAM source, restore the intended profile/adaptive selection, publish the new host_res/d_res, refresh dispatch and verifier snapshots, and recapture only consumers whose addresses changed. Enter decode only after the transaction is complete.
4. If the full allocation or restoration fails, fail the request before decode with a clear error. Do not continue with a partially restored map, a smaller context, stale captures, or missing MTP KV. For persistent service, require the same quiescent between-request boundary and rebuild a fresh Prefill owner before the next prompt.

On current evidence this is a candidate lifecycle, not a recommendation to implement or a 16K fit claim. Known reclaimable cache bytes alone do not cover the first doubling. No already-captured native decode graph has been established as reclaimable in this fresh standalone timing window; no other buffer with a measured size large enough to close the deficit was identified. Main should first obtain a source/receipt-backed allocation ledger for the exact request, especially separately allocated main output/hit buffers, MTP prefill graphs/buffers and allocator free-space changes. Only then decide whether saving/rebuilding extra decode state is worth the cost.

## Minimum CPU correctness discriminator

Before GPU work, exercise a host-only fake owner transaction with owned-Prefill and cache-borrowed variants. Required cases: success with all 262,144 context positions and the same KV resident/map limits; refusal to retire while a prefill callback, copy, stager worker, verifier, or batch consumer remains live; cache refill success republishes a map whose slot IDs point to the intended experts; refill/allocation failure leaves decode disabled and never republishes stale residents; exact pointer-generation invalidation causes all cache-dependent hit/verifier snapshots to be refreshed; repeated retire is idempotent and a fresh Prefill can be constructed; overflow/allocation failure leaves max_context, KV format, resident count, page map and prefix unchanged. This fixture checks the host transaction contract only. It cannot establish device quiescence, graph/runtime behavior, numerical parity, physical allocation fit, or performance; those require the main workstream's appropriate checks.

On two RTX 3090s the author reports fresh 8K/37K/119K prompt prefill changing 99.9→223.7, 88.1→212.6, 81.3→206.5 tokens/s, with roughly 2.8 seconds fixed release/restore cost and longer restore for fuller cache. The author later found short cached-prefix followups lost time and added pending-token gating. That is a potential alternative only if the measured shortage is cache contention rather than workspace capacity. https://github.com/ggml-org/llama.cpp/discussions/28248
