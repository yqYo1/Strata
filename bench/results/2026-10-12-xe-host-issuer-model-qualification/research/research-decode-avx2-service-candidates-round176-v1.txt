# R176 — AVX2 decode service candidate screen

Date: 2026-10-12 (Asia/Tokyo). Read-only source and primary-source review. No Git command, source edit, import, AST/code execution, build, test, inference, service, process/device/GPU query, profiler, or cleanup was performed. This report is the only new artifact.

## Decision

No genuinely new AVX2 kernel or fusion candidate is justified by the inspected evidence. Current source already provides AVX2 multi-row kernels and runtime dispatch for IQ3_S, IQ3_XXS, IQ2_S, IQ4_XS GU, and IQ4_NL Down, with a distinct generic Q2_0 path. The real pack is mixed across layers, but a pool batch has a uniform native format; heterogeneity is across batches/layers, not within one batched kernel call. A new candidate that is merely “add AVX2 multi-row IQ3_S,” “fuse heterogeneous GU/Down formats,” or “rebalance row tasks” would duplicate existing implementation or prior reports.

The actionable gap is service attribution for current actual decode: there is no joined request/window/layer record showing format pair, CPU-owned expert and token-row counts, selected kernel branch, worker CPU service, phase wall envelope, and whether that work delays physical decode. Existing phase clocks are pool-lifetime counters and their GU/Down spans include queue waits; they do not separate compute from scheduling or establish CPU memory-bandwidth saturation. The exact quiet 64K cold 16-token result (~7.64 tok/s) is a cold, short observation and is not a warmed-adoption result. Preserve the 256K and RESTORE constraints.

## Best next discriminator for Main

Use existing route/job/pool data first, without adding per-task clocks. For each completed observer-off decode request, retain exact context/state class, emitted tokens, verify windows and MTP acceptance; per window and layer record `(gu_type, down_type)`, routed CPU expert count, CPU-owned `nt` histogram, selected resident/helper/CPU route, and GU/quant/Down existing wall deltas plus CPU dispatch and physical decode. Preserve denominator and zero-window behavior. These counters can establish which actual format and NT cohorts recur and whether CPU work changes with decode latency; do not label logical blob bytes as DRAM traffic, and do not sum overlapping host/device intervals.

If this leaves a concrete question, the next bounded diagnostic is the already-specified R284 design: fixed preallocated per-worker records around real row fragments, worker thread-CPU and wall spans, active host-drainer service, whole GU/Down phase envelopes, and pre-publication/done/re-park waits. Calibrate observer-off versus clocks-on separately. Interpret CPU thread-time as scheduled service, not memory traffic; call it bandwidth-bound only with suitable memory-controller counters. If worker service ends before the physical decode tail or reduces without improving decode, stop kernel/scheduler work and keep the cause unresolved.

There is therefore no candidate-specific Main CPU microbenchmark to nominate this round. If future joined data shows one uncovered pair/branch, the minimum useful component comparison is current dispatch versus the proposed branch on the exact actual packed expert layout and activation representation, NT=1 and the observed NT cohorts, identical pool worker/host-drain policy, output parity and paired samples. It must retain build flags and runtime ISA gates. A component win is only a screen. Any selected change still requires at least three observer-off matched model decode repetitions per arm, with identical actual context position and fresh-versus-RESTORE state, route/cache policy, emitted-token count and MTP behavior; report individual sample rates and correctness. Do not infer an outcome from CPU peak specs or another CPU's tokens/s. A 32K/64K result does not qualify full 256K capacity; preserve the physical 262,144-token and RESTORE lifecycle constraints.

## External implementation and author-source screen

- KTransformers' official CPU-path documentation describes runtime AMX/AVX dispatch by arithmetic intensity and AMX's tile-resident multiply/accumulate to reduce movement. Its decode path cited in the official guide selects AVX-512 for short-token work. Those AMX/AVX-512 branches are unavailable on the specified 5600X; they do not reveal an uncovered AVX2 packed-IQ kernel. The KTransformers author paper/blog discusses CPU/GPU task scheduling and token-count-dependent service, useful as measurement design context only. [KTransformers AMX path](https://github.com/kvcache-ai/ktransformers/blob/main/doc/en/AMX.md), [KTransformers author paper](https://madsys.cs.tsinghua.edu.cn/publication/ktransformers-unleashing-the-full-potential-of-cpu/gpu-hybrid-inference-for-moe-models/SOSP25-chen.pdf), [author implementation writeup](https://www.lmsys.org/blog/2025-10-22-KTransformers/).
- llama.cpp's CPU quantized dot kernels and shared chunk pool are known AVX2-compatible building blocks, but the packed types/activation layouts and single-token dot contract differ from this native expert's grouped rows. Current Strata already derives from ggml CPU quant code. Without an exact-format uncovered branch and parity/service evidence, transplanting code is not a candidate. [llama.cpp x86 quantized dots](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cpu/arch/x86/quants.c), [CPU pool chunk claims](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cpu/ggml-cpu.c).
- ik_llama's public documentation includes CPU MoE placement and AVX2-capable backend context; the located Qwen3 MoE issue reports a Ryzen 7 5800X AVX2 comparison but not a transferable kernel-level measurement or implementation proof for these GGUF type pairs. It suggests checking exact branch dispatch and actual layout, not importing an unsupported result. [ik_llama parameters](https://github.com/ikawrakow/ik_llama.cpp/blob/master/docs/parameters.md), [Qwen3 MoE issue](https://github.com/ikawrakow/ik_llama.cpp/issues/1699).
- Intel LLM Scaler's official repository is a vLLM-oriented serving stack and offers no inspected AVX2 CPU-expert kernel or matching native GGUF layout. It contributes no candidate here. [Intel LLM Scaler](https://github.com/intel/llm-scaler).

These sources establish patterns and boundaries only. No external speed figure is transferable to Ryzen 5600X or Strata's routed decode workload.
