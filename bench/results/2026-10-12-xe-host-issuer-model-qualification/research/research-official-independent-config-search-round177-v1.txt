# R177 — official pristine independent settings search: actual degrees of freedom and bounded holdout plan

Date: 2026-10-12 (Asia/Tokyo). Read-only source/history research. No code edits, imports, AST inspection, tests, builds, runtime/GPU/process queries, Git commands, service actions, or cleanup. This report authorizes no GPU execution and claims no new performance result.

## Decision for Main

The open TODO is a real selection problem once the source/runtime path is qualified. The independent search space is much smaller than the full CLI: one prefill geometry axis (requested chunk), one first decode axis (pool worker count), then at most one conditional decode-work axis (speculation width). Cache, reserve, KV residency, profile, prefill lending/ring, and CPU/GPU miss service are coupled admission or policy choices; hold them fixed in the first two screens, and only open a separate policy comparison if a specific limitation is observed. On the supplied B570 host, positive PCIe fractions are ineligible, and current pristine v0.1.43 has no stock parameter shown to make its long-prefill host-USM polling handoffs safe. Therefore the search is finite and concrete but remains behind the existing safety gate.

Use three comparison arms on the same frozen model and exact prompt token IDs: (1) the installer-produced stock `auto` configuration, (2) one matched explicit recipe applied unchanged to both engines, and (3) each engine's own independently selected prefill and decode settings. Select each phase on a fixed 32K+ selection workload, freeze the chosen tuple, then run held-out fresh-process repetitions on the exact same model and exact same prompt/token IDs. Preserve phase outcomes separately. Decode needs at least three held-out independent processes with every value, median, and range. This validates the chosen setting on the target workload; it does not establish general optimality beyond it.

Installer-generated standard config must be preserved as its own baseline. In setup.py v0.1.43 the usual Qwen runtime config includes `--expert-profile ... --expert-cache auto --prefill auto --spec 4 --spec-min-p 0.5 --mtp ...`; setup can add a calibrated worker count on hybrid CPUs. This differs from compiled engine defaults (e.g. no `--prefill` means token path; default `--spec-min-p` differs). Therefore label arm 1 **installer stock config/auto**, not “all CLI flags omitted.” Record exact generated args and effective INFO/resolution. Source and setup can be read without executing setup.

Current independent phase dimensions are thus: prefill chunk geometry under one pinned residency/borrow/ring policy; decode pool size under pinned cache/KV/MTP policy; optional speculation width as a subsequent decode-only question. Cache policy is the main shared cross-phase resource choice and must not be bundled into either initial screen. The GPU-card safety issue is not in this parameter space: R169 identifies host-polled volatile sequence words in Stager and PLE upload allocations; changing chunk/ring/stream/worker/PCIe/spec settings does not establish the missing host/device synchronization contract.

## Minimum finite selection and held-out comparison plan

**Precondition:** the existing Main-owned source/runtime gate must establish safe normal >=32K prefill and decode, including the actual selected prefill kernels and both Stager and PLE handoffs, on the exact B570, driver/runtime and compiler. R169's source finding blocks stock pristine v0.1.43 at the supplied `HOST_USM=1, ATOMIC_HOST_USM=0` capability. A config sweep cannot be used to discover safety by trial-and-error, and no failure status or smaller chunk is a safety qualification. This report does not relax that gate.

1. Freeze binary/source identity, model pack/native shards/profile/MTP and their hashes, tokenizer, one exact prompt-token sequence of at least 32,768 IDs, generation token count/sampling, device/runtime/driver, context, KV format/residency, process warmup, complete allowlisted environment, and machine state boundaries. Use fresh independent processes and a counterbalanced order with a repeated baseline between candidates. Record individual results, no averages alone.
2. **Three externally interpretable arms:** (a) installer stock auto configuration exactly as generated for the engine; (b) a matched recipe passed unchanged to both engines, starting with historical `prefill=8192, cache=128, workers=5, pcie-frac=0, spec=4, spec-min-p=0`; (c) settings selected independently for each engine by the phase screens below. The historical matched recipe is a comparison control, not a prior optimum. Keep model/data/sampling/output and all common controls fixed. If the three arms' effective geometry/cache differs, retain those facts and mark the comparison as requested-setting matched but not effective-geometry matched.
3. **Prefill selection on the fixed selection prompt:** hold all decode controls fixed and use one fresh-process screening sample each for (P0) installer stock auto, (P1) fixed 4096, (P2) fixed 6144, (P3) fixed 8192. This is four finite rows; the matched historical arm may serve as P3 only when it has the same other controls and remains a separately labeled arm. Interleave P0/candidates/P0. A candidate is eligible only after complete prompt completion, health/fault check and declared numerical/output correctness gate. If two requests resolve to the same actual chunk/ring/cache geometry, collapse them as duplicate effective candidates. Choose the highest fresh prefill throughput among eligible rows, subject to cache/VRAM headroom and unchanged quality. Add exactly one `auto:16384` row only if source admission logs show the policy is eligible and P0/P3 evidence plus measured remaining expert-stream work justify the added chunk; stop there. Record PP times and exact batched positions separately from the terminal prompt token and decode.
4. **Decode selection:** hold the selected prefill and prompt state fixed; use the same MTP artifact, KV/context/cache policy, output length and sampling. Compare fresh-process auto workers, explicit 5, and (only if auto==5 or topology/evidence gives a reason) explicit 3. Deduplicate identical effective worker geometry. Do not change affinity, host-core placement or host-worker participation in this screen. Select by median decode tokens/s among correct, healthy samples, with no output/quality regression and with actual `pool_workers`, drafted/accepted windows, cache and KV values recorded. Keep prefill wall separate. If worker count does not matter or is inside noise, retain auto as the less fragile setting; do not expand a grid. If the independent target is decode dominated and worker rows show no improvement, one separate spec-width question may test 2 vs 4 (or 4 vs 6 only where source/artifact supports it) while holding every other value fixed.
5. **Held-out validation:** freeze each engine's selected phase tuple before opening validation samples. Run the default(auto), matched, and independently selected arms against the same exact prompt/model again in a fresh process/order not used for selection; use at least three independent held-out decode processes per arm and record each sample, median, range and output/fault/correctness status. Keep prefill selection and held-out prefill results separate; a single held-out prefill sample can validate completion, but at least three fresh-process prefill samples are preferable if claiming an observed speed difference. The exact same prompt/token IDs is intentional for paired setting comparison; it does not support claims about other prompts or contexts.
6. Choose prefill and decode independently. A winner on prefill is not automatically the decode configuration, and a decode winner is not a whole-request winner. Report prefill tok/s, decode tok/s, time-to-first-token/full request only as distinct metrics with every per-process sample. Never subtract one phase from overlapping timers. If effective cache, prefill ring, actual KV residency or output differs, report a policy/quality difference rather than a pure setting speedup.

Fairness method is consistent with llama.cpp's primary `llama-bench` practice of separating prompt processing from generation, holding a test shape, repeating each test and retaining per-repetition samples/standard deviation in JSON; this is method precedent, not a Strata performance oracle. The prescribed minimum three decode repetitions is the project TODO's lower bound, and all individual values remain necessary for variance assessment.

## Unknowns and stop conditions

- Actual accepted settings and performance for this exact v0.1.43 binary have not been measured. A source default or setup config does not imply an effective runtime value.
- Exact host-USM device handoffs remain unresolved for the supplied B570. The source has no stock parameter that replaces their volatile polling with a supported event/atomic contract.
- Effective auto chunk/cache/residency and pool-worker resolution depend on runtime free VRAM, prompt context, profile, borrowing, device ID, host topology and environment. Record logs and INFO rather than infer them.
- Installer default config can inject a calibrated pool-worker number on hybrid CPUs. On this Ryzen 5 5600X, verify the actual generated argument vector; do not assume its presence or absence from the generic code path.
- An apparent win within sample noise is unresolved. Keep the simpler stock policy unless held-out individual values support a change; do not widen the search without a bottleneck-based hypothesis.
