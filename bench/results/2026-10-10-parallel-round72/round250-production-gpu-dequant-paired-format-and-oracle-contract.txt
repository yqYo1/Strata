## Finding

The production native prefill caller dequantizes a layer's packed experts to FP16 only in its ordinary per-expert branch: `lay.native && !use_mmq && !fused_l` in `sycl/src/prefill/prefill.cpp`. It dispatches the layer's loaded `(f.gu_type, f.d_type)`, not a single model-wide type. Before allocation, `generate.cpp` checks each loaded layer with `native_expert_supported(...)`; that checks a GU role list, a Down role list, the generic dequant switch, and the exact block/dimension divisibility. A fixture or benchmark that assumes every native expert is the 384-fixture's IQ2_S/IQ4_NL pair does not represent this caller.

At the standard geometry `H=n_embd=2560`, `FF=n_ff=640`, all runtime-valid role pairs are the Cartesian product below with the format-specific block divisibility constraints (which all listed types meet at these dimensions):

- GU formats: `16 IQ2_XXS`, `17 IQ2_XS`, `18 IQ3_XXS`, `21 IQ3_S`, `22 IQ2_S`, `23 IQ4_XS`, `29 IQ1_M`, `42 Q2_0`, `12 Q4_K`, `13 Q5_K`, `6 Q5_0`, `2 Q4_0`, `3 Q4_1`, and `8 Q8_0`.
- Down formats: `20 IQ4_NL`, `42 Q2_0`, `7 Q5_1`, `6 Q5_0`, `2 Q4_0`, `3 Q4_1`, and `8 Q8_0`.
- `14 Q6_K` is an additional GU format only in a build compiled with opt-in `STRATA_Q6K_EXPERTS`; this macro also admits it in the dequant dispatcher. Type `23 IQ4_XS` exists in the generic switch and Down grouped-kernel list, but it is **not** a valid Down role at `FF=640`: its role block size is 256 and `640 % 256 != 0`, so `native_expert_supported` rejects it. Type `20 IQ4_NL` is valid Down but not a GU role. Generic dequant cases such as `11 Q3_K` do not become an admitted native expert role because they are absent from both GU and Down grouped role macros.

Thus the standard build's source-eligible pair set is 14 × 7 = 98 role pairs at H=2560/FF=640; the opt-in Q6_K build adds 7 more. This is a source contract, not evidence that every combination occurs in the current loaded pack. The exact active per-layer pairs must be read from `expert_layout().fmt[l]` and joined to the root-owned current-pack metadata census. The dispatcher also has generic `is_iq(t)` and `dq_dispatch` cases outside these role lists; that larger switch is not a caller eligibility list.

The existing 384-selected-expert CPU capacity fixture metadata covers exactly `(GU,Down)=(22,20)` / `(IQ2_S,IQ4_NL)`, H=2560, FF=640, with 1,971,200 packed bytes per selected expert (1,049,600 GU + 921,600 Down). It is a real selected-weight CPU service cohort and a useful actual-data GPU dequant subset; it is neither the model's `n_expert` nor a complete per-layer type-pair census or GPU dequant measurement. R240/R244 explicitly preserve that distinction. No expert/model payload was read for this audit.

For each routed expert in the ordinary native branch, the call is:

1. `iq_dequant_gu_f16(f.gu_type, blob_dev, blob_dev + f.up_off, f.n_ff, f.n_embd, dq_gu[q], m.cs)`.
2. `iq_dequant_f16(f.d_type, blob_dev + f.down_off, f.n_embd*f.n_ff, dq_d[q], m.cs)`.
3. The current FP16-input GU oneMKL GEMM, SwiGLU, then the current FP16-input Down oneMKL GEMM consume those same output matrices.

The `q = j % DQ` ring has `DQ=2`. Each GU slot is `1280*2560` FP16 values (6,553,600 B) and each Down slot is `2560*640` FP16 values (3,276,800 B); two pairs of slots reserve 19,660,800 B = 18.75 MiB in the Prefill workspace. They are maximum production-geometry scratch, not 384 full-expert outputs. Per expert the complete dequant outputs are 4,915,200 half values / 9,830,400 B: GU interleaves gate/up into `[2*FF,H]` (3,276,800 values / 6,553,600 B), and Down is `[H,FF]` (1,638,400 values / 3,276,800 B).

The GU wrapper requires `n_embd%256==0` and an `is_iq` type. With H=2560 its ND-range is two parity groups × `n_ff*(n_embd/256)` groups × 32 local work-items: `2*640*10=12,800` groups / 409,600 work-items. Each group decodes one 256-value block into the interleaved gate or up output. The Down flat wrapper requires `n%256==0` and `is_iq`; at `n=H*FF=1,638,400`, it has 6,400 groups / 204,800 work-items, each group writing 256 contiguous half values. Both wrappers check the device's `sycl::aspect::fp16`. These launchers use local size 32; neither declares a subgroup-size requirement, and this is distinct from subgroup requirements in the optional native grouped matmul kernels.

Role type/shape admission is concretely `gu_qk(gu_type)>0`, `d_qk(d_type)>0`, `is_iq(gu_type)`, `is_iq(d_type)`, `H%gu_qk==0`, `FF%d_qk==0`, `H%256==0`, `(H*FF)%256==0`. The native expert layout/source contributes its own per-layer `gu_type`, `d_type`, `up_off`, `down_off`, row bytes, total bytes and geometry; the startup GGUF check validates tensor type, shape, payload size, metadata offsets, and file bounds against that layout. A copied blob must preserve the canonical `[gate | up | down]` role segments.

The logical packed input extent for a pair is metadata-defined:

`B_GU = 2 * FF * (H / qk(GU)) * block_bytes(GU)`

`B_D = H * (FF / qk(D)) * block_bytes(D)`.

For the 22/20 fixture these are 1,049,600 B and 921,600 B respectively. Every pair has the same FP16 output extents above at the fixed geometry, but different packed bytes, decode instructions, lookup behavior and block strides. `B_GU+B_D+9,830,400` is a source logical input-plus-output extent for a full isolated pair, not a measured physical memory transaction rate. Exclude host copy/H2D and later GEMM input reads from the *dequant-only* denominator; report those separately if the whole expert service is measured.

## Exact numerical oracle and current ambiguity

The unchanged generic GPU implementation is the production baseline: `dq_dispatch` switches each 32-lane group to `dq_iq2_s`, `dq_iq4_nl`, etc.; the block decoders calculate FP32 values from the GGUF blocks and store FP16 output. Candidate-versus-baseline admission must compare every output half's 16-bit representation, across both GU roles and Down, for each admitted actual pair. Do not use a checksum-only gate, samples, max error, or tolerance where the claim is preservation of current dequant output.

Use the pinned GGML C reference as an independent decode oracle: `ggml_get_type_traits(type)->to_float` / the corresponding `dequantize_row_<type>` routine produces FP32 values from each original packed row. Independently convert each FP32 oracle value to a binary16 expected bit pattern using the pinned `ggml_fp32_to_fp16_row` contract or a bit-exact independent RNE encoder. This gives two separate checks: generic GPU vs independent expected bits, and candidate vs generic GPU bits. Preserve and report each separately. The generic baseline comparison alone can show that a candidate preserves existing behavior; it cannot prove that the baseline's conversion is the intended GGML result.

The current decoder uses `sycl::half(v)` in `store_run<half,8>` and `cvt<half>(v)`/`sycl::vec::convert<half, automatic>` in other run forms. The spelling does not pin emitted conversion rounding or half-subnormal behavior. R166/R168 note the host and device constructor source paths differ and the host helper's subnormal conversion is not a portable target observation. Therefore the qualifier must include values that exercise zero/signed zero, ties, subnormals, normals and overflow; emit the selected backend/device, relevant FP compiler options and `half_fp_config` values as capability evidence; and retain the three-way outcome `generic==independent`, `candidate==generic`, and `candidate==independent`. A shared generic/oracle mismatch is a baseline-contract issue, not a candidate-only regression and not a pass. No current source-only audit proves emitted device conversion semantics.

For the 22/20 pair, the pinned GGML references are `dequantize_row_iq2_s` and `dequantize_row_iq4_nl` in `ggml/src/ggml-quants.c`, block layouts in `ggml/ggml-common.h`, and the binary32-to-binary16 routine in `ggml/src/ggml-impl.h` / row wrapper in `ggml/src/ggml.c`. The GPU implementation's fixed-format decode formulas correspond to those GGML decoders; its final half conversion remains target behavior to qualify. For other active pairs, call the exact GGML type trait corresponding to each per-layer role, not a hard-coded 22/20 reference.

## In-order queue and lifetime contract

The production path uses a dedicated in-order compute queue (`m.cs`) and in-order copy queue (`m.copy`). For a streamed expert, the copy queue writes the device ring slot and records `m.copied[slot]`; compute submits a barrier waiting for that event before calling `compute`. Within `compute`, both dequant kernels, gather and both GEMMs are submitted in program order to `m.cs`. Immediately after the two dequant submissions, it records `m.used[slot]` on the compute queue; the copy issuer can recycle the packed source slot after that event because the dequant commands have finished reading the blob. The GEMMs no longer need the packed blob; they consume `dq_gu[q]` and `dq_d[q]`. The two-slot dequant scratch is also consumed by queued GEMMs before a later same-queue command reuses its slot. This is an asynchronous lifetime chain; do not add per-expert host waits or free/rewrite blob/output storage before completion.

A diagnostic that uses one queue may simplify source ordering but must still use an in-order queue, preserve one source blob and its GU/Up/Down slices until both dequant launches complete, keep each output slot live until the end event/wait, and drain the queue before any USM free/destruction. A diagnostic that has copy and compute queues must explicitly preserve the copy-event wait on compute and a terminal compute event before source/ring reuse. Keep the actual caller's queue, staging event dependency, DQ ring choice and packed extent fixed; do not introduce cross-queue compute, fusion, alternate subgroup requirements, or host synchronization into the timed path. Dequant has no internal work-group barrier; its only synchronization dependencies are queue/event/lifetime edges around separate kernels.
