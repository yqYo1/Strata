R290 — XeStrata grouped FP16 XMX GEMM eligibility on Arc B570
Date: 2026-10-10

Read-only Git metadata commands confirmed the assigned revision/worktree; there was no Git mutation. The XeStrata rootmain and eval-b570-20261010 are pinned by task to pristine source commit `39bdadcc9e2b89b1e3c8be7bb2a603b04fa0e197`; task says the eval tree is the same source and root is building its icpx main. Decision
The XeStrata FP16 grouped GEMM path is an architecture-relevant candidate for the B570 because the target is Intel Arc B570 (Xe2) with XMX, not NVIDIA. Intel's specification lists Xe2, 144 XMX engines, and 10 GB GDDR6. The relevant XeStrata branch is its Intel-only XMX kernel, dynamically gated by the runtime's FP16/f32-accumulator matrix-combination report, a reported subgroup width of 16, and a kernel-bundle compile probe for its large-GRF mode. If those checks pass in the actual icpx/Level Zero environment, `xmx_gemm_grouped` is the expected non-MMQ fallback; no Tensor Core port is relevant. This is candidate eligibility, not proof the kernel compiles or runs on the installed B570 driver/compiler, fits current D's compact layout, or improves the 32K request.

The correct comparison is not Xe2 XMX against NVIDIA or against a different prompt speed. Compare the Xe grouped path on the B570 against current D's compact fallback, which calls `Gemm::f16` once per expert and uses the oneMKL-backed path when enabled. The Xe fork's own B70 experiment measured grouped GEMM against per-expert oneMKL, but used a different card and a 26,292-token IQ3_S prompt; it cannot predict the B570 result or current seven format pairs.

Correction record
The separate [R288 correction](./round288-correction-after-r290.txt) leaves R288 immutable and corrects two material errors: B570 was called an NVIDIA card; and the R288 full T*K GU/H memory figures were attributed to D's compact fallback. In this R290 comparison, D compact uses T-sized Xs/GU/Hh planes and still uses a T*K Dm plane. XeStrata's viewed allocator uses full T*K extents for Xs/GU/Hh/Dm. Do not carry the R288 NVIDIA/Tensor Core conclusion or full-K GU/H sizing into the B570 decision.

What the candidate actually does

- `src/prefill/prefill.cpp` lines 1775–1801 partitions expert routes, prioritizes a separate resident fused-dequant path for eligible resident experts with `cnt <= kIqGemmTileRows`, then appends other GPU experts in ID order. Its grouped dequantized XMX path is for the latter non-MMQ experts; the small resident expert `iq_gemm_grouped_f16` route is a distinct fused dequant GEMM kernel and must not be called the same candidate.
- Lines 1904–1910 gather the FP16/BF16-like activation rows into expert-contiguous Xs and copy cumulative expert boundaries to device. Lines 2103–2129 dequantize a group of `g_expert_group` expert weights into DQ buffers, then call `Gemm::f16_groups` for gate/up and down, falling back to `xmx_gemm_grouped` when the oneMath grouped helper declines. SwiGLU consumes the grouped F32 GU output and writes a uint16 Hh output for down GEMM. This route has F32 GEMM accumulation/output; the between-projection intermediate is already stored in half.
- `Gemm::f16_groups` in `src/prefill/gemm.cpp:259–277` uses oneMath per expert only when `gemm_path(f16)` is DP4a. With matrix engines, it returns false, so the call site takes the grouped kernel. On an Intel B570 with the XMX gates satisfied, this is therefore not a grouped oneMKL benchmark. The grouped kernel vs. D's oneMKL per-expert loop is the relevant A/B.
- `xmx_gemm_grouped` at `src/kernels/xe/xmx_gemm.cpp:324–347` validates shape and weight stride, selects `mma_gemm_grouped` only if forced/required or XMX is not usable, selects grouped DP4a when XMX is unavailable, otherwise launches the Intel XMX `GroupedKernel<128,256,3>` with FP16 inputs/weights and F32 accumulators. `GroupedKernel` indexes `bounds[ex]`, derives `rows`, and grids to the caller's `max_rows`; the kernel skips tile rows beyond each expert's `rows` and offsets both activation and output bases to that expert's absolute row boundary.

B570 hardware path and compile/runtime gates

Intel's product specification says the Arc B570 is Xe2 and lists XMX engines and 10-GB GDDR6: [Intel Arc B570 specifications](https://www.intel.com/content/www/us/en/products/compare.html?productIds=241676,241598.html). This establishes why the Xe2 XMX source is relevant. It does not establish what this installed runtime reports. `xmx_gemm.cpp:207–264` requires (a) a 16-lane subgroup in device info, (b) a reported FP16×FP16→FP32 joint_matrix combination satisfying 8×16×16, and (c) successful compilation of a kernel requesting 256-GRF mode. `STRATA_NO_XMX` forces fallback. The grouped-kernel functor requests `grf_size<256>` and subgroup size 16 at lines 129–179. The capability check does not key on product name, vendor string or PCI ID, which is the right device-selection pattern. A generic scalar kernel-bundle probe is helpful but is not a launch receipt for the actual grouped kernel.

This kernel's tile body has no explicit SYCL local_accessor/LDS allocation. It uses joint_matrix operands/accumulators, L1 prefetch hints and work-group strips; its critical target-specific constraints are the 16-lane subgroup and 256-GRF request. Do not infer that an XMX device can execute it from the engine-count marketing value alone. If the FP16 matrix combination, subgroup or GRF compile is absent, source falls back to `mma_gemm_grouped` when available or DP4a; that fallback is a different experiment and must be recorded as such. Official SYCL matrix-extension documentation is maintained by Intel LLVM at [sycl_ext_oneapi_matrix](https://github.com/intel/llvm/tree/sycl/sycl/doc/extensions/experimental/sycl_ext_oneapi_matrix); XeStrata's source performs its own runtime reporting and compile check.

Grouped shape and bounds constraints

The current source geometry is N=2560, K=10 routes/token, expert FF=640; group dequant extents are `GU_ELEMS=1280*2560` and `D_ELEMS=2560*640` uint16 values per expert (`prefill.cpp:181–182`). Gate/up GEMM is N=1280, K=2560; down is N=2560, K=640. Both N and K satisfy XMX's `xmx_gemm_ok` multiples (N≥16, N%16=0, K≥32, K%32=0). Dequant group strides are multiples of 64 bytes. These geometry checks do not prove device pointer alignment, safe `bounds` contents, capacity, or stream ordering at runtime.

The caller relies on cumulative monotonically nondecreasing boundaries, `bounds[0]=0`, `bounds[G]` within gathered Xs/Y extents, each group row count ≤ `max_rows`, valid expert weights in each DQ slot, and no empty/tail out-of-range writes. `GroupedKernel` itself does not validate boundary monotonicity or bounds-array length on the device. The host builds boundaries from `m.off` and `m.cnt`; the last element is `rows_gpu` after CPU rows are removed. A candidate qualifier must assert these invariants on CPU for actual route rows and compare boundary values sent to device. Include `max_rows` around 1, 127/128/129, and at least one multi-tile tail, not just full 128-row tiles; production expert counts are sparse and may be much smaller than 128.

The same in-order compute queue matters. The caller queues activation gather/bounds transfer, computes expert gate/up, queues SwiGLU, then down GEMM, and only then continues/reuses the DQ group slot. Expert staging uses a copy queue: the compute stream waits for each slot's `copied` event; after dequant reads a staged blob it records `used`, which the copy stream waits on before overwriting the staging slot. A grouped kernel changes the GPU work from per-expert products to a multi-expert launch but must preserve these producer/consumer dependencies, DQ-slot lifetimes, and output-row write ownership. The grouped path's asynchronous launch is safe only on the caller's same ordered stream; if the call is moved to another queue/graph, an explicit dependency must replace that assumption. Check both first and tail groups, resident-vs-staged experts, copy overlap, and group size 1 and default 16.

Memory difference from current D compact fallback

The D compact target is the exact branch audited in R287: `Xs=T*N` uint16, `GU=T*1280` float, `Hh=T*640` uint16, while `Dm=T*K*N` float remains full routed-row storage. Per expert, it gathers at row 0 and writes GU/Hh scratch at row 0; it then writes Dm at the expert's full grouped output offset until route combination. Its compact MoE bound is 132,772 B/T including maps, shared expert, and full Dm. The reusable workspace region is the maximum of its phase sets, not the sum of GDN/QSA/PLE/MoE; separately allocated DQ, KV, expert slots/staging, runtime and model weights still compete for VRAM.

XeStrata `prefill.cpp:759–768` allocates Xs at `T*K*N` uint16, GU at `T*K*1280` float, Hh at `T*K*640` uint16, and Dm at `T*K*N` float for the viewed non-fused path. When an MMQ layer is present it additionally allocates q8 Xq, float H, and q8 Hq; these are not part of the grouped XMX fallback's base shape. With T=32,768, only the four always-reserved Xs/GU/Hh/Dm planes total 6.64 GiB of capacity (1.56 + 1.56 + 0.39 + 3.13 GiB), versus 3.48 GiB for the corresponding four D compact planes (0.16 + 0.16 + 0.04 + 3.13 GiB). This is a roughly 3.16 GiB allocation-capacity increase before shared maps and other buffers. The phase region may be allocated at the maximum of phase sets; this is not a claim that all other phase arrays add on top of it. In addition, Xe's group-of-16 dequantized weights use about 150 MiB (`16*(1280*2560+2560*640)*2`), versus the current D's two-slot dequant ring about 18.75 MiB. At 64K these linear prompt workspaces double; do not assume the fork can retain D's 64K compact fit on 10 GB. A source-based size is a capacity, not an allocation receipt or peak residency measurement.

Evidence, scope and measured claims

`bench/results/2026-10-02-xmx-gemm/README.md` describes an Intel B70 and IQ3_S, 26,292-token prompt, `--max-context 32768`, `--prefill auto`, `--kv int8`, `--expert-cache 10000`, 4 generated tokens. It reports prompt 1,053.5/1,051.9 tok/s on oneMKL and 1,020.5/1,015.7 on XMX G=16 (about 3.3% slower); generated IDs match for its 24 output tokens, while logits differ by up to 3.1. Separate expert microbenchmarks on that record say oneMKL one-call-per-expert 16.2 ms/layer; grouped G=1 31.8, G=4 16.6, G=8 12.9, G=16 10.6, G=32 9.4. The record explicitly notes the model/context, hardware and run count. These establish that the architecture has been exercised on B70 and that group size trades launch/dequant costs for larger storage and bandwidth; they do not predict B570 throughput, a different model’s routed rows, or current D quality. The later 2026-10-09 record is also B70/RTX4070 with IQ2_XS and smaller microkernel shapes; it is not the B570 32K current-workload control.

Actual D's route join at `/home/yayoi/.local/state/strata-sycl/post-reboot-tuning-20261007/actual-prefill-census-capacity-join-v1.json` has seven active format pairs and 93,505 GU plus 93,505 down calls for a fresh 32,768-token diagnostic, but marks `performance_eligible=false` and `full256k_qualified=false`. Pair counts `(GU,down)` are 18/20: 27,283 calls; 18/42: 5,801; 21/20: 17,634; 21/42: 2,005; 22/20: 29,271; 22/42: 9,662; 23/20: 1,849. Pair totals show route coverage, not that each pair is accepted by Xe's dequantizer, takes its XMX route, or is speed-critical. Before any result, reconcile all seven exact `(GU,down)` IDs against `native_fmt`, the `iq_dequant_gu_f16` and `iq_dequant_f16` supported-type switches, and (where considering the separate resident-fused route) `iq_gemm_grouped_ok` in this pinned source. The Xe branch's `iq_gemm_grouped_ok` format list is separate from the F16-dequant/XMX branch's supported inputs. Do not assume a single format's parity qualifies all pairs.

Safe qualification boundary before the main raw fork run

There is no existing single small test in this pinned fork that covers all of: grouped XMX FP16 GEMM with real expert bounds and CPU-reference-qualified output limits; GDN; copy/compute queue event order; graph capture/replay; and the actual 32K layout. Existing checks cover components only:

- `gdn_parity --selftest` (CTest, `CMakeLists.txt:659–661`) compares recurrence/state, convolution and norms with its CPU double reference and explicit tolerances/invariants. It qualifies its synthetic shapes, not the 32K prompt or GEMM.
- `qsa_prompt_attn_parity [context=32768] [queries=2048] [reps=5]` (`src/kernels/qsa_prompt_attn_parity.cpp:4–15`) exercises synthetic 32K attention and has an FP64/FP32 reference, but does not run MoE GEMM, GDN, staging, or graph layout.
- `native_expert_parity` accepts real GGUF shards/layer IDs and compares CPU/GPU expert routes with ggml dequantization; it does not call `xmx_gemm_grouped` or verify the new grouped bounds path. Existing `device_selftest` checks allocation/alignment/capacity but the Xe docs say its readback is not numerical qualification.
- `--gpu-stages` and `--gpu-only-full` are source-described decode graph measurement modes, print and exit, and are not prompt-prefill tests. Native-pack token capture is separately gated off in `generate.cpp:4788–4795`; do not cite decode graph coverage as proof the 32K prefill is captured/replayed. The generic graph registry source has no matching CTest graph-pipeline test.

Therefore the safest first action is to run those existing component qualifiers before the candidate, then add/execute a narrow grouped-GEMM qualifier before a full 32K raw fork comparison. This requires no full-context run and should use the B570 build's actual runtime report. Seed it from real current 32K input's selected layer(s), exact weight formats, actual gathered Xs and `bounds`; first one group and max_rows around 1/127/128/129 plus actual tail; compare each F32 output against both a pinned CPU FP64 accumulation reference over the same dequantized FP16 operands and current D's per-expert oneMKL FP32-output path. Establish and freeze max-absolute, relative/RMS, non-finite and downstream logit/task bounds before opening the main raw fork run. A dequantized-weight synthetic GEMM selftest is useful for first launch/shape/queue validation, but it is not enough to establish real-format correctness or 32K routing.

If the grouped probe passes, next run the actual 32K prompt through the fork with a one-token output and a conservative explicitly selected prefill chunk that passes the measured 10-GB memory reserve. Use identical token IDs, pack, KV, context, CPU share, cache/ring settings, graph/capture mode and CPU-reference-qualified output checks in current D and fork arms. Keep `--max-new 1` for this qualification; generation throughput is a separate CPU decode measurement (target 70 tok/s) and must not be mixed with the user's prefill objective (1000 tok/s at actual input/64K). Then repeat the same input/model at ≥32K for the comparison, and qualify 64K only after capacity and quality evidence. A 256/512-token warmup may qualify startup but cannot stand in for the real 32K layout. Any lower-precision storage is a separate non-bitwise experiment: use R289's quality protocol and accepted local quality margins, not a byte-hash requirement or a claim of no degradation.
