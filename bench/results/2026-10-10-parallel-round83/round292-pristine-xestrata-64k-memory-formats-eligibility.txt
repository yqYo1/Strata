R292 — pristine XeStrata 64K prompt memory and format eligibility
Date: 2026-10-10
Scope: read-only source audit of `/home/yayoi/ghq/github.com/MistVVK/XeStrata/.worktree/eval-b570-20261010`, pinned commit `39bdadcc9e2b89b1e3c8be7bb2a603b04fa0e197`. The prompt length under review is 64K, processed as 8K chunks. This report records source-level capacities and route eligibility; it is not a build, runtime memory sample, performance measurement, or proof that a 64K session fits a particular GPU. No source or result status was changed.

Finding
The prefill's large activation/intermediate scratch is chiefly sized from chunk T, not from the total prompt length: `Prefill::init` sets `m.T = chunk`, `Prefill::run` advances `c0` by `m.T`, and each iteration uses `T=min(m.T,n-c0)` (`src/prefill/prefill.cpp:615–620, 1170–1174`). Thus a 64K prompt with an 8K chunk reuses the chunk buffers eight times. This does not make total session memory 8K-sized. QSA/KV pages, RoPE tables, pooled index rows, GDN recurrent state, and parts of session state are allocated from `max_cells` / layer geometry in `src/core/session.cpp` and `src/core/layer.cpp`, separately from Prefill's chunk allocation. `qsa_set_bytes` also has a capacity-dependent selection-score term (`max_blocks`) even though its token-row terms use T. Total fit therefore remains model-, KV-mode-, context-capacity-, resident-cache-, device-, and backend-dependent.

Chunk-owned device memory outside the shared activation/scratch region
- A fixed GEMM scratch allocation is 32 Mi FP16 elements = 64 MiB (`prefill.cpp:532, 699–702`).
- With the default expert group G=16, the FP16 gate/up and down dequant buffers are 157,286,400 bytes (150 MiB), independent of T (`:180–182, 772–775`). `bytes_needed` includes these, confirming they are outside the shared region (`:1020–1023`).
- The resident-MMQ path additionally allocates fixed group buffers for streamed-all chunks T>=2048, or a 32-slot MMQ ring for smaller chunks (`:558–565, 776–786`). These do not grow with T, though their byte size depends on the largest supported expert blob/matrix in the model.
- The expert staging ring is another allocation. `STAGE=8` below `STREAM_ALL_MIN=2048`; at 8K, `ring_slots(T)` is selected from configured/pinned-share defaults, with a 384–512 high-pinned-share target, capped by one eighth of reported device memory and by `RING_MAX=1024` (`:64–68, 140–164`). If the default low-pinned-share branch applies it starts at 96. Each slot is MAXBLOB-sized. Therefore “ring 8” describes the small-chunk staging mode, not the 8K chunk's ring allocation.
- `bytes_needed(g,ss,chunk)` counts the same allocations as init and returns 8 MiB alignment slack (`:1000–1041`). It is a source calculation, not observed device free memory.

The common region is the maximum, not sum, of GDN scratch, QSA scratch and MoE scratch because the attention half runs before the MoE half and reuses that region (`:534–538, 735–754`). Most row buffers in those sets scale with chunk T. On the fallback path, MoE scratch contains T×K×N FP16 activations `Xs`, T×K×1280 FP32 `GU`, T×K×640 FP16 `Hh`, and T×K×N FP32 `Dm` (`:596–611, 755–769`; N=2560, K=10 at `:60`). At T=8192, these four alone total 1,887,436,800 bytes (1.758 GiB); other router/shared buffers add to that set. If MMQ is available, `Xq`, `H`, and `Hq` are also present, and the max-set calculation can be larger. These capacities explain the chunk-size effect but cannot be summed with all attention buffers: the code intentionally overlays the three scratch sets.

Across total prompt length, session state is distinct and capacity-based. `session_bytes` includes per-layer GDN state, QSA state, QSA buffers, page tables, pooled/indexer state and other buffers, and `session_init` carves those allocations from `max_cells` (`src/core/session.cpp:57–75, 78–123`). QSA K/V slot counts derive from `max_cells` pages; RoPE cos/sin tables are proportional to `max_cells` (`src/core/layer.cpp:614–667`). For streamed KV, `Prefill::take_stage` allocates host staging pools from `n_pages × heads × page_size × head_dim` with byte width determined by KV format (`prefill.cpp:470–495`). Consequently, 64K still increases or determines persistent state even when prefill scratch stays near the 8K chunk size. Whether this state is resident, host-streamed, quantized, or elastic changes the device/host split; no single GPU-fit conclusion follows from this audit.

Seven census GU/down format pairs: source eligibility screen
The joined actual-prefill census names these seven pairs: 18/20 (27,283 calls), 18/42 (5,801), 21/20 (17,634), 21/42 (2,005), 22/20 (29,271), 22/42 (9,662), and 23/20 (1,849). Counts identify observed work in the census; they are not timings.

- CPU native-format detection is generic: `native_fmt` requires ggml-cpu dot-product traits on both weights, activation quantizers for each dot type, and whole-block geometry, then computes row/storage sizes (`src/kernels/cpu/native_expert.cpp:34–70`). Thus the seven pair IDs are not by themselves proof that a particular bundled ggml-cpu build accepts each pair; inspect its runtime traits or build result before claiming CPU eligibility.
- Xe grouped IQ GEMM's `in_iq_gemm` includes all seven IDs (18,20,21,22,23,42); grouped geometry requires N and K multiples of 128 (`src/kernels/xe/iq_kernels.cpp:1519–1525, 1638–1663`). For this model, N=2560 and the GU/down K dimensions 1280/640 meet that condition. The fused native expert gate/up predicate accepts IQ GU IDs except 20; the down predicate accepts 20,23,42. All seven census pairs satisfy that fused pair predicate, subject to its separate runtime layout/launch conditions (`:1666–1676`).
- Both IQ F16 dequant entry points require `is_iq`; dispatch has cases for every census type. `iq_dequant_gu_f16` additionally requires n_embd divisible by 256, satisfied by N=2560 (`:1296–1318, 1596–1600, 1621–1635`). The general fallback branch calls the GU and down dequantizers before grouped multiplication (`src/prefill/prefill.cpp:2103–2114`).
- Eligibility is route-specific: a fused resident-expert route, grouped IQ GEMM, and CPU `native_fmt` have different gates. In particular, generic ggml CPU trait availability cannot be inferred from the SYCL dispatch switch. Also, the census confirms calls in the present source/workload only; it does not prove every route is selected at runtime or correct on another backend.
