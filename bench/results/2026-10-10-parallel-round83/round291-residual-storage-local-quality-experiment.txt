## Pinned sources and proposed experiment

The current Strata prefill source is D, `/home/yayoi/.local/state/strata-sycl/post-reboot-tuning-20261007/prefill-gemm-service-only-v1/prefill.cpp`, SHA-256 `1cf7e911a555e8611c1368a4d18d4ba81c95027bb8de77f89ad65ac64b05fc3c`. The comparison source is XeStrata at `/home/yayoi/ghq/github.com/MistVVK/XeStrata/.worktree/eval-b570-20261010`, pinned by the task to pristine commit `39bdadcc9e2b89b1e3c8be7bb2a603b04fa0e197`; its `src/prefill/prefill.cpp` SHA-256 is `919c696192311066055077bdd0fc74769bfb50854e3437b6b387732acf6d532e`.

The concrete candidate is **BF16 storage for the host-backed inter-layer four-branch residual rows in D's explicit `run_layer_major` prefill mode**, with F32 as the compute format on both sides of each storage boundary. At the end of a layer, after the normal F32 residual update has completed, round each `R[token, branch, channel]` once to BF16 for persistent host storage. Before the next layer consumes the same rows, expand them back to F32 in the existing per-chunk `m.R` compute buffer. This changes only the value preserved from one layer to the next; it leaves GEMM accumulators, GR read/write arithmetic, GDN recurrent state, expert buffers, KV, routing and final prompt state types untouched. A parallel FP16 arm is useful to distinguish exponent range from mantissa precision, but BF16 is the first candidate because its FP32-like exponent range avoids FP16's 65,504 finite maximum.

This experiment deliberately targets `STRATA_PREFILL_LAYER_MAJOR=1/2` with `STRATA_PREFILL_LAYER_MAJOR_R_GPU=0`, the host-backed path. D selects that path at lines 2436–2444; by default `gpu_tokens` is zero (2720–2721). `run_layer_major` keeps each token's `D=HC*N=4*2560=10,240` float residual row across the complete layer loop: it sets `hand_in_` to `rows.data()` for the next layer (2822–2827), writes the completed layer's chunk into `rows` with `transfers.activation` (2832–2845), and reads host-backed rows into the F32 scratch `m.R` before layer computation (3101–3113). The host vector is currently `std::vector<float>` of `(n-gpu_tokens)*D` (2750); a configured GPU prefix is separately allocated as `float` rows (2736–2749). The row represents the four GR branches, not the GDN's separate recurrent matrix/history state.

The ordinary chunk-major path is materially different: it keeps `m.R` as F32 chunk scratch of `T*D` and processes all layers on each chunk before moving on (the chunk loop begins at 3077). It has no full-prompt cross-layer residual array to halve. Converting that active scratch would require changing kernels' compute/storage interfaces and is not the isolated boundary proposed here. The previous rejected layer-major run in R285 combined layer-major scheduling, a full GPU residual allocation, and cache leases; that failure remains real, but does not test this BF16 host-row storage change in isolation.

## Exact capacity and transfer opportunity at 64K

For an actual 65,536-token input and the source's `D=10,240` values per token:

| Host-backed residual store | Bytes per token | 65,536 rows | Change |
|---|---:|---:|---:|
| Current F32 | 40,960 B | 2,684,354,560 B = 2.50 GiB | — |
| Candidate BF16 | 20,480 B | 1,342,177,280 B = 1.25 GiB | −1.25 GiB host RAM |

These values are capacity arithmetic, not an allocation receipt. They assume 65,536 prompt rows and no GPU-resident prefix. With `g` rows placed in `device_rows`, the host saving is `(65,536-g)*10,240*2` bytes; the optional GPU-resident prefix separately saves `g*10,240*2` bytes if stored BF16. The host-only candidate does not lower the prefill F32 compute scratch or the DMoE/GDN/QSA arena, and it should not be credited with any VRAM saving. It may allow the host row store to fit with 1.25 GiB less RAM.

For all-host rows, each inter-layer boundary currently copies one full prompt of F32 rows GPU→host and then host→GPU for the next layer: 2.50 GiB each direction, 5.00 GiB of payload per boundary. A BF16 row store reduces this to 1.25 GiB each direction, 2.50 GiB combined, a nominal **2.50 GiB less PCIe payload per layer boundary**. For `L` layers the total opportunity is `2.50*(L-1) GiB` across the prompt, subject to chunk/tail sizes. With a GPU prefix `g`, the saving applies only to host-backed rows: `4*(65,536-g)*10,240` bytes per layer boundary across both directions. These figures count bytes; they do not predict elapsed time or prove the PCIe copy is the bottleneck.

The transfer estimate depends on converting *before* the GPU↔host copy. Converting to BF16 on the CPU after downloading the current F32 rows would halve retained host memory but leave D2H traffic unchanged. The useful implementation shape is a BF16 host-USM row store with an F32→BF16 pack operation at layer end and a BF16→F32 unpack operation into `m.R` before the next layer. D already creates pinned host-USM handoff buffers for inter-stage rows (`m.hand[2]`, allocation at 1076–1081; end-of-stage copy at 5284–5318), but those are F32 stage handoffs and are not the `run_layer_major` row vector. Replacing a pageable `std::vector<float>` with a full 1.25-GiB host-USM allocation may add pinning pressure; a `malloc_host` pointer's device accessibility and a pack/unpack kernel's throughput must be checked on the target. This review does not assume either. If using an extra device-side BF16 transfer tile instead, count `T*D*2` bytes of new VRAM (240 MiB at `T=12,288`) against the target reserve. Reuse/aliasing that tile would need a separate liveness proof.

The corresponding XeStrata implementation point is its explicit two-buffer layer-stage handoff, not a persistent full-context row store. In Xe `Prefill::init`, each `m.hand[b]` is allocated with `sycl::malloc_host(chunk*D*4)` when a successor stage exists (lines 631–633); each finished chunk copies `m.R` to one handoff buffer and syncs (2279–2291), and the next stage uploads that host pointer into its F32 `m.R` (1179–1183). At a 12,288-row chunk, the two F32 handoff buffers reserve 960 MiB total; BF16 buffers would reserve 480 MiB, saving 480 MiB of pinned host capacity. At 65,536 rows, the in-order chunk schedule has five full 12,288 chunks and a 4,096-token tail; per handoff boundary the same F32 payload totals 5.00 GiB across device→host plus host→device and the BF16 payload totals 2.50 GiB, saving 2.50 GiB. This is a stage-split-only result; it is not evidence that the B570's ordinary single-stage prefill uses the handoff path or that its conversion kernels are already present.

Both D's `STRATA_PREFILL_DUMP_R_ALL` and Xe's dump hook show an existing round-to-nearest-even float→BF16 conversion for diagnostic output. They first copy F32 rows to host and then convert only the final residual for a file; they do not supply the pack/unpack data path, do not reduce PCIe bytes, and do not establish quality for repeated inter-layer rounding. Relevant D locations: host row allocation 2750; host/GPU residual row read and write 2826–2843, 3101–3113; diagnostic BF16 dump 5338–5353. Relevant Xe locations: `m.hand` allocation 631–633, upload 1179–1183, output handoff 2279–2291, BF16 dump 2300 onward.

## Local teacher-forced quality comparison is source-supported

The current Strata generator contains a teacher-forced log-probability hook. `src/program/generate.cpp` SHA-256 is `aa58f73711d3ad9b2020a3d9f54b98610b3aa070abe8da0cbd56ba3f42b2b76a`; its `STRATA_LOGPOS=<path>` path records the prompt's own next token for every verifier window (5610–5624). `Verifier::window_logprobs` in `src/core/verify.cpp` SHA-256 `7334ccf8bf602dbec17cf560ba93e57fc4823b8a458ef0194793cd7b7a29a816` writes per-position target log-probability, argmax/top log-probability, agreement, and the configured extra-token mass (1533–1577); `STRATA_LOGPOS_TOPK` adds the top-K token IDs and log-probabilities. The matching interface contract is documented in `include/strata/core/verify.hpp:133–141`.

This is sufficient to obtain reproducible paired next-token NLL from fixed token IDs, including a teacher-forced code answer or retrieval answer appended after a long fixed context. The repo's [UNSLOTH_Q4.md quality comparison](https://github.com/yqYo1/Strata/blob/main/docs/UNSLOTH_Q4.md#quality-against-llamacpp-on-the-same-file) documents using this hook with top-20 probabilities for code completion, ordinary text after a 16K prompt, perplexity, top-k overlap and KL-style comparison. That historical IQ3_S/0.1.32 result is a methodology example, not a quality prediction for BF16 residual storage or the current Qwen3.8-Flash-Next prompt.

For this candidate, first establish the current F32-store `run_layer_major` control with the same layer-major mode, 64K token IDs, model pack, system state, seed, chunk size, and flags; do not compare the BF16 layer-major arm directly to chunk-major and attribute all differences to storage. Then change only the row storage dtype. Include a matched ≥32K comparison as well as the actual ~64K input; preserve the separate full-262,144 lifecycle gate. For code, teacher-force fixed reference completions to compare per-token NLL/top-K/KL, then separately generate under fixed decoding settings and run the same unit tests. For retrieval, teacher-force the expected answers and also score exact needle/multi-key retrieval after the same long context. Report individual examples and position-binned token results; set acceptance margins from repeatability of the current F32 layer-major control before opening candidate results. Intended quantization means byte-identical residuals/logits are not the acceptance metric. `STRATA_LOGPOS` copies full window logits to host, so collect these quality traces in a separate run from timing and keep only the compact metric report plus the bounded current comparison evidence under `docs/ARTIFACT_RETENTION.md`.

Qwen Team's primary technical report is architecture-matched qualitative support: it says FP8 storage of the four-branch residual state halves bytes versus BF16 “with almost no loss in quality,” and warns that sparse residual writes can look fine on pretraining metrics yet degrade after post-training. It does not give a numeric FP8-storage quality delta, protocol, context, or confidence interval. It therefore motivates this residual-store experiment but does not qualify BF16 as near-zero in this engine. See [Qwen Team, *On the Design of Qwen3.8-Next Architecture*](https://arxiv.org/html/2608.30320v1), §2.2 inference efficiency. Keep the evaluation boundary narrow: this trial changes GR residual storage once per layer, not MoE `GU`/`Dm`, GDN recurrent `ss.gdn_state`, KV, or GEMM accumulation.

## Minimal implementation experiment boundary

1. First qualify the existing F32-storage layer-major path as a control against the current accepted chunk-major path. If layer-major itself fails correctness/lifecycle gates, stop; it cannot serve as a valid quality baseline for the storage change. If it passes, add a host-backed BF16 row store only to D's explicit layer-major path, preserving its F32 `m.R` scratch and all existing F32 compute. Initially set GPU-resident rows to zero so host bytes and transfer bytes are both explicit; leave ordinary chunk-major unchanged.
2. Encode each completed non-final layer chunk directly into a device-accessible BF16 host-USM row range; next layer decodes that range into the F32 scratch before any GR/GDN/QSA/MoE operation. Keep the current two-way layer/chunk order and completion waits. Use round-to-nearest-even, preserve NaN/Inf payload behavior deliberately, and record range/underflow/overflow counts. Do not enable the existing in-place path for this candidate.
3. Compare BF16 storage against the exact F32-storage control first, then FP16 as a separate treatment. At the first changed layer/token, record residual max/percentiles and absolute/relative/RMS error; retain finite-value and state checks. Complete 32K and ~64K teacher-forced NLL/code/retrieval comparisons before evaluating throughput. If this path is chosen for 64K, separately demonstrate the required full 262,144-token lifecycle and memory reserve.

The earlier layer-major failure remains an unresolved rejection of that combined run; this report makes no claim the isolated BF16 storage change repairs or reproduces it. No source files were changed. Root owns subsequent implementation and all GPU qualification.
