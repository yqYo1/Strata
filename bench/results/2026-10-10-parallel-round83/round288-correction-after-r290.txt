Correction to R288 — hardware identity and compact MoE buffer extents
Date: 2026-10-10
R288 remains immutable. This correction is a separate read-only report; no implementation, build, test, GPU, profiler, or cleanup was performed.

1. Hardware identity: current target B570 is an Intel Arc B570, Xe2, with Intel XMX engines and 10 GB graphics memory. It is not an NVIDIA GPU. The R288 passages that describe the B570 as “RTX B570,” assign it a Ryzen-vs-NVIDIA Tensor Core path, and conclude an NVIDIA Tensor Core port is needed are wrong. B570 has an Intel Xe2 XMX target. Whether the fork can use a particular SYCL/XMX kernel still depends on its build target and runtime-reported matrix combination, subgroup and kernel-build capability; the product name alone is not a runtime capability receipt. XeStrata's own docs state that Xe2 uses its `xmx_gemm`, and its `mma_gemm` joint_matrix implementation targets Arc A and NVIDIA matrix engines, so the Xe2-specific XMX grouped path is directly relevant to investigate on an Intel B570. Intel's product page identifies B570 as Xe2, lists 144 XMX engines, and 10 GB GDDR6: https://www.intel.com/content/www/us/en/products/compare.html?productIds=241676,241598.html.

2. Compact D memory: R288's 179,200 B per token arithmetic (GU + Dm + MMQ H, each sized at T*K) does not describe current D's compact fallback branch. D `moe_bufs(T,...,compact=true)` at `prefill.cpp:1020–1022` returns `GU=T*1280` float elements, `H=T*640` float elements, and zero Xq/Hq; compact eligibility requires `mp.any == false`, so the conditional H/Xq/Hq allocator is not entered. The compact allocator at `1341–1350` sets Xs to `T*N` uint16, GU to this compact extent, Hh to `T*640` uint16, and Dm to `T*K*N` floats. The actual compact native fallback branch gathers one expert's `ne<=T` rows into Xs row 0, writes GU row 0, converts SwiGLU to Hh row 0, and writes each down product into Dm at grouped route offset (`4970–5003`). R287's scoped compact MoE bound is 132,772 B/T, including maps, shared expert buffers and full Dm; use that for this branch. MMQ/noncompact and fused branches have different extents and must not be conflated.

3. R288's `T=12,288/32,768` figures for GU and H as T*K capacity apply only to the ordinary noncompact MMQ layout, not the compact fallback used by D's relevant target. Dm remains T*K*N in compact mode, so its 102,400 B/token capacity remains relevant; it shares the reusable region with attention/GDN/PLE and is not added to all their maxima. See R287 and R290 for detailed branch/liveness analysis.

These corrections do not alter the R288 record's source observations; they narrow the applicability of its device and memory conclusions. No speed result or B570 qualification follows from this erratum.
