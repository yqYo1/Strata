# R286 — current native CPU service and capacity fixture join

Date: 2026-10-10 (Asia/Tokyo). Read-only reconciliation of the closed `(GU22,Down20)` CPU capacity fixture with cached decoder sources W0141 and current W495, plus retained hardware controls. No source change, build, test, model run, GPU action, profiler/PMU collection, process/service query, Git operation, environment dump, or cleanup was performed. Only this report was written.

## Finding

The CPU capacity fixture is eligible as a component control only when a current decoder call has all of these properties: actual loaded layer pair `(gu_type,d_type)=(22,20)`, `H=2560`, `FF=640`, a CPU-owned expert job, the same `nt` bucket, the same relevant dispatch branch/ISA settings, and the same direct or five-worker-plus-host pool mode. Default pool task value `0` is a row-partition policy (18 partitions for five workers plus host), not an NT value. It neither implies a single-token call nor changes an expert job's NT.

For the Ryzen 5 5600X AVX2 configuration, the source routes `(22,20)` NT1 through GGML's single-token dot functions; NT2–4 can use Strata's custom AVX2 `iq256_gu_rows` for GU22 and `iq4nl256_down_rows` for Down20. The capacity fixture measures that exact pair with actual packed expert weights and synthetic prequantized activations. It does not measure current W495 route frequency, production activations, worker CPU-time shares, or physical memory traffic. NT3/4 capacity values cannot be weighted into ordinary decode until those actual NT cohorts are recorded; the closed route histogram R282 reached NT2 only.

Neither the measured six-core FP32 FMA rate of 0.81822 TFLOP/s nor the separate 36.869 GB/s host RAM-read control is a meaningful roof for these integer/table-lookup kernels. A hypothetical division can be calculated, but it compares unlike operations and unobserved traffic. The first relevant production-normalized service measure is per-worker thread CPU time around the exact native row-kernel call, grouped by `(request,window,layer,role,format,NT,branch)` and divided by the actual CPU expert-token row count; pair it with wall envelope and separately counted pool waits. R284 defines that instrumentation contract. Existing default task-0 phase clocks are elapsed wall spans and have no NT join.

## Exact production branch eligibility

In W0141 `native_gu_rows` (`src/kernels/cpu/native_expert.cpp:125–176`), default `native_gu_mt_min` is 2 (`:106–123`). On the target Zen 3 CPU, with AVX2 and without AVX-512 or `STRATA_NO_IQ256`, NT1 falls through to `traits(IQ2_S)->vec_dot` for both gate and up rows; NT2–4 take `iq256_gu_rows` (`:154–173`). `STRATA_IQ_MT_MIN`, `STRATA_NO_IQ256`, ISA support, and CPU selection can alter this, so source eligibility is not a runtime branch receipt.

In W0141 `native_down_rows` (`:178–206`), IQ4_NL NT1 falls through to its GGML `vec_dot`; NT2–4 take `iq4nl256_down_rows` only when AVX2 is enabled, `STRATA_NO_IQ4NL` is absent, and default `mt_min=2` is met (`:180–203`). Q2 Down uses a separate pool branch and is not this fixture. The target current host recorded as Ryzen 5 5600X / Zen 3 has AVX2 and no AVX-512 in the capacity/R231 source receipts. The four capacity rows therefore cover NT1 and NT2–4 as two kernel families, not four NT variants of one kernel.

W495 `expert_pool_dispatch_multi` first classifies each routed token/top-k entry, then deduplicates only CPU-owned misses by expert and increments `ExpertJobMulti.nt` once per such row (`sycl/src/core/expert_source.cpp:2583–2693, 2718–2735, 2745–2798`). Its `NativeFmt` is per loaded layer. A current call is not fixture-eligible if it is GU18/21/23, Down42, another geometry, a non-CPU route, NT outside 1–4, a changed ISA/override, or a fallback implementation not matching the fixture. Actual per-layer GU/Down pair and NT frequency are not present in existing default task-0 receipts.

At `pool.cpp:716–718`, `phase_tasks()` returns `3*(n_workers + host_works)` for `tasks_=0`; with the measured five workers and host this is 18 row partitions. At `:627–661`, the pool splits flattened output rows into expert-local subranges and calls native GU / Down for the fragment's expert. This maps task-0 timing only when the same pool topology, host participation, and row-partition policy are used. GU, caller-side FF quantization, and Down remain separate phases at `:759–787`. Existing `ms_multi_gu`, `ms_multi_q`, and `ms_multi_down` are elapsed wall spans around phases and barriers; they are not summed worker service or per-NT timings.

## Arithmetic and bytes supported by the source

The fixed shape supplies exact dense-equivalent dot-work counts. One MAC is defined here as one multiply-accumulate over one input dimension; dense-equivalent FLOPs count a MAC as two operations. This is a normalization convention, not the native instruction count. SwiGLU, activation quantization, integer decode/reduction, and other scalar/vector operations are not included in the MAC totals.

For one expert-token at H=2560, FF=640:

- GU has two `FF × H` products: `2 × 640 × 2560 = 3,276,800 MAC`, or 6,553,600 dense-equivalent FLOPs.
- Down has one `H × FF` product: `2560 × 640 = 1,638,400 MAC`, or 3,276,800 dense-equivalent FLOPs.
- GU+Down totals 4,915,200 MAC, or 9,830,400 dense-equivalent FLOPs per expert-token.

NT multiplies the number of output vectors but does not multiply the per-job unique packed weight extent. Per expert job, logical weight bytes are GU 1,049,600 B (gate 524,800 + up 524,800), Down 921,600 B, combined 1,971,200 B. The exact data extents are in the selected payload manifest/receipts and R229; they are logical packed extents. Their FP32-sized logical equivalents are `2×640×2560×4 = 13,107,200 B` for GU, `2560×640×4 = 6,553,600 B` for Down, and 19,660,800 B combined. These FP32 equivalents do not materialize in the native path and do not describe its runtime resident set.

|---:|---:|---:|---:|---:|---:|---:|
| 1 | 3,276,800 | 1,638,400 | 4,915,200 | 9,830,400 | 1,971,200 | 1,971,200 |

The last column is arithmetic amortization over tokens in a grouped job; it is not per-token measured DRAM traffic. For a cohort per timed round, multiply the per-job operation counts by `logical_jobs` (8 or 192), not by both cohort sizes. Aggregate packed payload extent is independent of NT: hot-eight is 15,769,600 B (15.039 MiB); streaming-192 is 378,470,400 B (360.938 MiB). FP32-sized equivalents are 157,286,400 B (150 MiB) and 3,774,873,600 B (3.516 GiB), respectively. Hot/streaming labels specify selected active-set extents; they do not certify cache residency, a DRAM miss for every packed byte, or cold-start disk behavior.

The fixture's intermediate FF quantizer produces Q8_0 activation data of 680 B per active token for `FF=640` (R229); it has no packed-weight-byte or MAC denominator. The pool does this quantization serially between GU and Down. Keep it out of GU/Down MAC rates and include it only in a separately measured complete-service total. Input activation quantization into GU's input format is another caller-side stage outside the direct `GU` measurement.

## Hardware control comparison: why the simple roofs fail

The separate FMA control reached 818.22 GFLOP/s aggregate on six physical cores; it is a register-only FP32 FMA loop with twelve independent YMM accumulators and no loop spills. The RAM control reached 36.869 GB/s on its selected read-stream loop. These are valid controls for their own loops and host, not CPU roofs for IQ2_S/IQ4_NL.

For scale only, the deliberately naive FMA division `19,660,800 dense-equivalent FLOPs / 818.22 GFLOP/s` is about 24.03 µs per expert-token. This is not a lower bound or utilization estimate: native IQ2_S/IQ4_NL do packed index/sign/scale decoding, byte table lookups/shuffles, integer dot/reduction and floating accumulation; `2 MAC = 2 FLOPs` is only a dense-work convention. Much of the operation count does not execute as FP32 FMA, and the FMA loop's occupancy and dependencies do not match these kernels.

Likewise, `1,971,200 logical packed bytes / 36.869 GB/s` is about 53.46 µs per full expert job if one imagines every packed byte fetched once at the control's rate. Dividing by NT gives 53.46/26.73/17.82/13.37 µs per expert-token for NT1/2/3/4 under the additional ideal assumption that one job's unique weights are fetched once and shared across all rows. Neither assumption is measured: the control has its own access pattern, the packed extent is not memory-controller bytes, cache reuse changes physical requests, and grouped kernels can reread or retain blocks differently. Do not compare those invented values to the pool timings, infer an L3/DRAM fraction, or label the native service memory-bound.

No AVX2 FMA peak calculation improves this comparison. The measured FMA loop is more useful as evidence that six-core register FP math is available on this host; it does not bound integer table lookups, vector integer dot, dependent loads, or their scheduling. The RAM stream establishes a host read control, not sustained kernel transaction bandwidth. Current records mark PMU access unavailable, so there is no same-interval cycle, instruction, cache-miss, or memory-controller-byte counter to refine these limits.

No external quantized-kernel blog or other engine is used to transfer a performance claim. The NT2–4 implementations here are Strata's own `iq256_gu_rows` and `iq4nl256_down_rows`; another engine would be relevant only if the exact compiled function, format, NT, dispatch, and architecture matched. NT1's fallback is pinned GGML `vec_dot`, but no separate GGML benchmark is needed to establish the current branch or normalize its production service.

## First normalizable production component

R284's smallest useful next measurement is the first attributable service metric, not a generic roofline: around each actual `native_gu_rows` / `native_down_rows` fragment in `pool.cpp::drain`, capture current-thread CPU-time delta and steady wall delta after the fragment's expert `e`, `[r0,r1)`, and `mjobs_[e].nt` are known. Join each observation to request/window/layer, role, exact `NativeFmt` type, NT, and actual selected branch. Count CPU expert jobs and expert-token rows once at the dispatcher after it constructs `jobs_multi`. For each exact cell, report total worker+host thread CPU ns divided by the observed expert-token rows (ns/CPU-expert-token), each worker's wall-call sum, earliest-to-latest phase kernel envelope, and separate active-drain/wait/quantization spans. Preserve the actual default `tasks=0` topology and report absent NT cells as absent.

This produces a same-request component service rate that can be compared to matching fixture components without confusing a fixture median with a production ceiling. Validate disabled-path parity and clocks-on overhead; use timer-off timings for performance conclusions. It still cannot distinguish integer execution from cache/DRAM effects without valid same-interval hardware counters. For an available PMU later, the first useful counters would be cycles and retired instructions on the exact branch interval, followed by CPU-family-validated L3/memory-controller events with enabled/running coverage. No existing receipt has those counters.
