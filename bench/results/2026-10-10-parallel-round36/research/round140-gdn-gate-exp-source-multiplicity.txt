R140 — source-level native-exp multiplicity in prefill GDN recurrence

Scope and status

The private root-v5 probe source was used only to confirm the candidate expression boundary; its manifest is `152b74e534845dff7f8ea17f9422530f59fcde48b8fac8f2b40ce63be784987f`.

Current shapes and counting convention

The frozen constants are `HV=48`, `HK=16`, `S=128`; `RG=4`, `RPG=32`, `CB=32`, `NCB=4`. Thus there are 393,216 gate scalars for `T=8192`, and 24,576 gate scalars per token. I count source-level work-item evaluations of the recurrence's `native::exp` expression separately from unique mathematical gate values and SIMD/subgroup instruction issues. A single scalar expression in a SYCL work-item is not proof of a particular emitted instruction count: compiler uniformity analysis, vector lowering, common-subexpression handling, device compiler and SFU implementation can change the machine-level work. These counts are dispatch geometry and source expressions only.

In all kernels below, the input to the recurrence expression is one log-gate scalar per `(t, head)`; all work-items assigned to a head/token use that same scalar. The current producer computes one log-gate and beta per `(t, head)`. Its softplus path already evaluates `native::exp(v)` for `v <= 20`; a same-buffer factor producer would add a separate `native::exp(loggate)` after the existing log-gate expression (one extra exp expression per active gate), then store factor instead of log-gate in the same FP32 slot. It would not remove the producer's existing softplus exp. For full `T=8192`, this is 393,216 extra producer exp evaluations and no increase to `m.gate` scratch: it stays `T*HV` FP32 = 1,572,864 bytes (1.5 MiB). `m.beta` remains the same size. Gate-plane bytes written/read and allocation size do not change; only its meaning changes. The recurrence's `gate` loads also remain in place (or stage into existing local memory); this factor does not remove those source loads.

Legacy recurrence work-item expression counts for `T=8192`

- **Serial/scalar `gdn_rec_kernel`:** launch is one work-group per head with local shape `(RG,S)=(4,128)`, 512 work-items. Each work-item executes the `native::exp(gate[t*HV+head])` source line once per token. Count: `48 * 8192 * 512 = 201,326,592` work-item evaluations. That is 512 evaluations of each of 393,216 distinct gate values. Each head group has 16 SG32 subgroups; if the source maps directly to subgroup-wide exp instructions, that would be 16 exp issue sites per head/token, but compiler/hardware lowering is unverified.
- **Columns, non-pipelined `gdn_rec_cols_kernel`:** grid has `HV*NCB=192` groups; each group covers one head and one 32-column tile with `(RG,CB)=(4,32)`, 128 work-items. Four CTAs per head, each 4 SG32 subgroups. Every work-item executes the same exp expression once/token. Count: `48 * 4 * 128 * 8192 = 201,326,592`; again 512 evaluations per distinct gate. A direct SG32 mapping would issue 16 subgroup exp instructions per head/token across the four independent CTAs, subject to compiler/runtime lowering.
- **Columns pipeline `gdn_rec_cols_pipe_kernel`:** launch geometry and per-token exp expression multiplicity are identical to columns non-pipeline. The pipeline stages one raw `ng` gate per work-item for the next token, broadcasts it through local variables `cg`/`ng`, and computes `native::exp(cg)` in each work-item. It therefore has the same 201,326,592 source evaluations and 512 per unique gate; staging overlaps input loads but does not deduplicate the gate exp across columns or row groups.
- **Key-head/tuned `gdn_rec_kh_kernel`:** launch geometry is `HK*NCB=64` CTAs, 128 work-items each; `VPK=HV/HK=3` value heads per key head. The stage loop copies one raw gate per token and each of the three value heads into its existing `sg[buffer][token][j]`; the compute loop then executes `exp(sg[...][j])` for each `j=0..2` in every work-item. Count: `16 * 4 * 128 * 3 * 8192 = 201,326,592`, again 512 exp evaluations per unique `(token, value-head)` gate. Per CTA/token it has 3 scalar exp expressions per work-item, versus 1 for the columns routes. The one-time staging/buffering does not constitute reuse of the exponentiated gate across the CTA's 128 work-items.
- **SYCL SG32 quad-pipeline (`gdn_rec_quad_pipeline_sg32_kernel`):** the admitted SYCL quad variant dispatches this pipeline with the same `HV*NCB` groups and `(RG,CB)` local shape as columns pipeline; it has one `exp(cg)` per work-item/token. Count is 201,326,592. The separately written CUDA/HIP `gdn_rec_quad_kernel` is backend-specific and not the SYCL SG32 quad dispatch. Its source shape is `HV*(S/QCB)` CTAs, `QTH=128`, `QCB=32`, also giving four CTAs/head and 512 work-item exp evaluations per head/token. Keep those backend-specific consumers outside a SYCL-only representation switch unless that backend is deliberately supported and qualified.

Therefore, for each of these current 48-head recurrence shapes, source-level counts are identical despite different data staging: 201,326,592 recurrence exp evaluations versus 393,216 distinct gate values (512:1 work-item expression multiplicity). At the SYCL subgroup level, serial/columns/pipeline/quad geometry suggests 16 subgroup-wide source expression instances per head/token if lowering preserves the uniform evaluation; key-head has the same total subgroup geometry (`16 key-head groups * 4 column CTAs * 4 subgroups * 3 expressions = 768` per token, equal to `48*16`). These are not claims about emitted SFU instruction count or throughput. The source count falls by 200,933,376 recurrence expressions if all consumers switch to reading the factor directly; producer gains 393,216 factor-exp expressions. Nominally, that removes 511 of 512 recurrence work-item exp expressions per gate (99.8047% of the recurrence-side source expression count), but the comparison must not be advertised as an SFU or speedup percentage.

What changes and what does not

The direct scalar/columns routes currently load the same gate scalar independently in each work-item. The columns launch repeats that across four CTAs; key-head stages each value head's gate once per block/token into its existing ping-pong shared buffer, then each work-item still exponentiates its local staged scalar. A factor path substitutes the loaded/staged value and deletes the consumer exp expression. It does not by itself reduce the existing consumer gate loads, input staging, or recurrence state work. It adds the producer exp and writes factor in the existing gate store; it does not add a scratch array, global pass, or new buffer traffic. If materializing a separately rounded log-gate store/reload were required for equivalence, that could require another pass or storage and would invalidate this same-buffer/source count premise; no such method is presumed here.

Which routes make this worth measuring

Source multiplicity is large across all actual shapes, including the default pipeline, but unique mathematical values are only one per gate. It is plausible that repeated work-items make this a worthwhile discriminator for serial, columns, and key-head pipelines; source does not show whether native exp is the bottleneck, how efficiently identical lane inputs are lowered, or whether producer work dominates. Key-head reduces raw gate-load repetition through staging but not the exp expressions; direct columns/serial routes repeat loads too. This distinction argues to compare current production dispatch modes separately rather than infer a universal benefit. The ordinary wrapper defaults to the pipeline unless selector/environment precedence chooses serial, columns, key-head/tuned, or qualified quad; actual selected route and exact environment must accompany any result. The selector must preserve those existing choices and bind every selected kernel to the same encoding.

Closed timing evidence and the smallest useful discriminator

R104's closed 32,768-token / 2,048-token-chunk quad-vs-legacy fixture reports all paired service samples slower for quad, with ratios 1.675–1.718 in legacy-first order and 2.878–2.961 quad-first; the measured interval includes repeated candidate-only bundle/device admission per chunk, recurrence/norm submission, and queue drain. It has no device event timestamps and cannot isolate recurrence exp or compare gate representations. R106 explains the bounded useful discriminator: preserve the same in-order queue and current recurrence wrapper, keep host admission/submission/wait durations separate, and capture returned recurrence and norm events then read SYCL command start/end only after the existing successful drain. The source snapshot's ordinary recurrence path has a parallel-for event available at its launch point; the qualified quad wrapper has a submit event. No closed report found here provides a clean, gate-generation-plus-recurrence factor-vs-baseline event comparison. R87's 727 vs 788 tok/s B70 note is a combined tuned-keyhead result, not an isolated GRF or gate-exp timing comparison.

Smallest useful actual-device discriminator, if the primitive first passes: use the existing private primitive screen to establish bitwise identity, then perform a narrowly scoped instrumented A/B for the exact production gate producer plus recurrence on the same device/compiler/input/dispatch, collecting producer, recurrence, and norm event durations, as well as host wrapper/admission/submit/wait intervals. Start with the currently selected production dispatch and one alternate that has materially different geometry (e.g. default pipeline vs serial or key-head) only if it is currently selectable and covered. Keep gate-generation plus recurrence as the primary combined interval; producer-only or recurrence-only values explain a result but cannot replace the combined measure. Avoid hardware-counter assumptions and avoid projecting this synthetic stage result to full model throughput. Use the production kernel bodies and exact encoding pair, unchanged FP flags, no competing GPU/build work, complete state/output parity, clean async drain, and paired/counterbalanced samples. If event profiling is unavailable, record that and do not replace it with host wall time under a device-time label.

Decision boundary

The source arithmetic says a factor implementation would exchange one producer exp per gate for 512 recurrence work-item exp expressions per gate in these shapes, leaving scratch footprint and recurrence loads unchanged. This supplies a quantitative reason to measure the hypothesis after numerical admission, but compiler lowering, target throughput, actual dispatch, and producer-plus-consumer timing remain unresolved. Do not claim a reduction in issued SFU instructions, milliseconds, speed, or model performance from these source counts.
