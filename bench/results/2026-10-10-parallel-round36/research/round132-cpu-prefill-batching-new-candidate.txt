## Strata callsite and what already exists

The CPU AVX2 source already implements the basic token-batch sharing this question might otherwise propose. In `row_dot<TY,NT>` it decodes a quantized GU weight block once, then reuses that decoded block across the `NT` activation rows. IQ2_S is type 22 in the `Fmt32` decoder. For Down type 20, `iq4nl_rows<NT>` unpacks the nibble block and computes absolute weights once per weight block, then applies it across the `NT` Q8_0 activations. The `native_gu_dispatch` and `native_down_dispatch` paths select these multi-token AVX2 kernels at their configured minimum NT (default minimum 2 in the inspected source); NT1 uses the existing GGML path. This is existing code, not a missing weight-decode reuse factor.

The production caller narrows applicability further. The frozen `sycl/src/program/generate.cpp` calls `drive_pool` from the general layer path, including prefill's per-layer/per-position loop (`:5146`, `:12757+`). That adapter calls `expert_pool_dispatch`; in the pinned `sycl/src/core/expert_source.cpp`, this function explicitly fails when `expert_layout().native` is true, with the message that the single-token expert path does not take a native IQ pack (`:2430+`). The native batched path is `drive_pool_multi` → `expert_pool_dispatch_multi` → `run_split_multi_native`; it is attached to verifier-window execution (`generate.cpp:1015-1020, 7145-7163, 12464`). That function is bounded by `MAXT` and describes its arrays as verify-window tables (`expert_source.cpp:2542-2555`). Therefore its native NT histograms and the MTP/split bound in R32 are decode/verification data, not CPU prefill data.

R5 separately examined cross-chunk expert-major prefill. It found that preserving the existing routed-rank FP32 combine order while deferring expert outputs costs a 25-GiB contribution plane at 262144 tokens; retaining dense FP16 expert matrices is a different 4.6875-GiB-per-layer device-residency tradeoff, with unknown headroom. That is neither a small batching tweak nor new evidence for the requested CPU AVX2 route. R12's `width*nt` weighted dynamic task partition is already a distinct scheduler hypothesis, but it was written for verifier/decode work and explicitly requires per-worker tail evidence. Neither report establishes the same cost distribution or caller for prompt prefill.

## External implementation and implementer-lead screen

- **SGLang CPU prefill.** The maintainers' CPU roadmap says its optimized target is Intel Xeon with AMX; its prefill task calls out duplicated weight reads at large input M. The implementation PR uses 2D thread blocking, L2 cache blocking, AMX INT8 and FP8-to-BF16 dequant caching. It targets BF16, INT8 W8A8 and FP8 W8A8 GEMM/MoE, not the unchanged IQ2_S/Q8_K and IQ4_NL/Q8_0 blocks on Ryzen AVX2. It is an implementer lead for large-M blocking, but not a transfer candidate for this row-kernel path. Sources: [SGLang CPU roadmap #8281](https://github.com/sgl-project/sglang/issues/8281), [CPU prefill optimization PR #8750](https://github.com/sgl-project/sglang/pull/8750).
- **vLLM CPU / SGL kernels.** The reviewed `csrc/cpu/sgl-kernels/moe.cpp` labels the fused path AMX. The current CPU extension build description places the SGL CPU MoE sources in the AVX-512/AMX source set, not the AVX2 source set. Its W8A8/BF16-style grouped GEMM cannot be assumed to preserve the Strata quantized weight bytes or to run on Zen 3. No format-preserving IQ2_S/IQ4_NL AVX2 kernel was found. Sources: [vLLM CPU MoE source](https://github.com/vllm-project/vllm/blob/main/csrc/cpu/sgl-kernels/moe.cpp), [CPU extension source selection](https://github.com/vllm-project/vllm/blob/main/cmake/cpu_extension.cmake). These branch URLs are discovery references, not pinned Strata evidence.
- **Intel LLM Scaler.** Its own README identifies Arc Pro B60/B70 as the target and describes the LLM Scaler vLLM stack, INT4/FP8 online serving and platform/model integrations. It is a GPU-oriented deployment distribution, not an AVX2 CPU quantized MoE implementation. Source: [Intel LLM Scaler](https://github.com/intel/llm-scaler).
- **llama.cpp IQ panel.** The pinned llama.cpp IQP implementation from commit `85c55223caf0a2ad0d1d88e5a73ab3fe36107867` decodes grid-IQ weight panels and has an 8-token minimum for the per-expert panel route; R30 describes its 8-row × 8-token tile. It does support IQ2_S bytes and leaves the persistent model format unchanged, so it is the closest row-kernel analogue. But it is already R30's candidate, not a new lead. R32 ruled it out for the configured MTP decode path (individual expert NT at most 2). The present task asks about prefill, but the actual pinned Strata CPU path does not route native IQ packs through prefill. There is no prefill-specific per-expert NT>=8 evidence to reopen it. The panel also has temporary conversion/packing cost and changes reduction grouping; it does not apply to Down20 IQ4_NL. Sources: [pinned IQP implementation](https://github.com/ggml-org/llama.cpp/blob/85c55223caf0a2ad0d1d88e5a73ab3fe36107867/ggml/src/ggml-cpu/iqp.cpp), [pinned CPU caller/eligibility](https://github.com/ggml-org/llama.cpp/blob/85c55223caf0a2ad0d1d88e5a73ab3fe36107867/ggml/src/ggml-cpu/ggml-cpu.c), and the prior [R30 candidate screen](https://github.com/ggml-org/llama.cpp/commit/85c55223caf0a2ad0d1d88e5a73ab3fe36107867).
- **KTransformers implementer report.** Its AVX2 MXFP4 change converts activation rows once to match a fixed weight emission order and amortizes decoded weights across four token accumulators. This is a different MXFP4 block/layout and the author reports Zen 2, so the activation permutation does not map to dynamic IQ2_S grid indices or Strata's present per-row dot. R104 already excludes this as an NT1 candidate. Source: [KTransformers commit 9481291](https://github.com/kvcache-ai/ktransformers/commit/9481291).
- **ik_llama.cpp.** The author discussion explains that its IQK 2–5 bit formats use 4/8/16/32-entry tables that fit AVX2 `pshufb`. Those formats encode weights differently; IQ2_S's indexed 1024-entry grid is not a same-byte small-LUT substitute, and Strata's IQ4_NL already uses a small 16-entry shuffle table. Source: [ik_llama.cpp discussion #8](https://github.com/ikawrakow/ik_llama.cpp/discussions/8).
- **ncnn-MoE-Runtime.** Its CPU path covers Q2_K–Q8_K and MXFP4, uses expert grouping, and offers optional packed sidecars with added memory. Its README also describes exact-input coalescing. These are useful runtime mechanisms but the quantized formats differ; exact-input result reuse would need a byte-identical activation collision for the same expert and no such route/input evidence exists in Strata. Packing changes representation/resident memory and is excluded. Source: [ncnn-MoE-Runtime README](https://github.com/crafcat7/ncnn-MoE-Runtime).
- **FastLLM.** The docs expose CPU/NUMA/disk expert placement, separate MoE dtype, and chunked prefill controls. The material located was placement/runtime configuration rather than a pinned Zen 3 AVX2 IQ2_S or IQ4_NL row/batch implementation. It does not provide a transferable kernel factor. Sources: [FastLLM README](https://github.com/ztxz16/fastllm/blob/master/README_EN.md), [Qwen4-Exp guide](https://github.com/ztxz16/fastllm/blob/master/docs/qwen4_exp.md).

## Decision and minimum next evidence

No genuinely new kernel, activation-reuse or route-cost scheduling candidate is supported for this Strata CPU prefill path. The existing per-row multi-token kernels already share each decoded weight block across their current NT rows; R17's activation reuse, R12's `nt`-weighted scheduling, R30's IQP panel, R5's cross-chunk expert-major design, and the R104/R117/R123 NT1 screens are all previously considered proposals or do not apply to the pinned prefill caller. R59's decode exposure and NT1-vs-NT2 dispatch comparisons cannot be relabeled as prefill evidence.

The smallest next discriminating step is an immutable source/call-graph admission check for a CPU prefill path that accepts native IQ packs and submits multiple prompt-token rows to `ExpertJobMulti`. The supplied production snapshot instead shows the general per-token callback and an explicit native-pack refusal; absent an updated source identity proving otherwise, do not prototype an NT8 panel or an `nt`-weighted prefill scheduler. If a future callsite is added or found, the first controlled comparison should be a single-layer, actual-weight CPU prefill slice at 32K with a per-layer/per-format/per-expert NT histogram, selected-dispatch receipt, same activation quantization, worker work/tail distribution, and unchanged GGUF bytes. Reopen IQP only if real prefill jobs reach its >=8-token threshold; include its transient panel conversion in timing and check its numerical/order contract against the established gates. Compare end-to-end prefill separately from decode. Adoption would still require the >=32K model comparison and then a full physical 262144-token lifecycle/capacity pass; neither is established here.

No speed, model correctness, valid-domain, or adoption claim is made.
