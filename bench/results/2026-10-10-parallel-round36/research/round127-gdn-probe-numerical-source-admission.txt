## Findings: fixed geometry, indexing, guards, and comparisons

No arithmetic/indexing or buffer-bound defect was found in the corrected source by inspection. The probe fixes `HV=48`, `HK=16`, `S=128`, `MaxT=8192`; `N=393,216` elements at maximum length. It owns eleven shared-USM buffers: input `ab` of `2*N`, `dt`/`a` of 48 each, and eight `N` output buffers. Including 22 guard regions of 16 floats, the static expression `(2*N + 8*N + 96 + 22*G)*sizeof(float)` is a valid aggregate upper bound and is below 16 MiB. Each individual allocation is also bounded below 16 MiB (`ab` is 2*N floats, every other allocation is at most N floats, plus guards).

Every output is reset to a quiet-NaN canary before each case. After all case stages, `guards(active)` checks the leading guard and every index from `active` through the trailing guard; thus it checks the entire inactive tail, not just the last guard. Input extents are initialized and guard checked; `ab` is bit-snapshotted and checked unchanged, as are `dt` and `a`. The ordered lengths contain 15 cases: `0,1,3,5,15,16,17,127,128,129,8191,8192,3,8192,8192`, so empty/tail, 128 boundary, maximum length, and large-small-large/reset reuse are represented. All active outputs are compared for every case.

The comparison loop checks five independent relations per active index: baseline/candidate loggate, baseline/candidate beta, and candidate factor against scalar, SG16, and SG32 reference readers. It therefore entails 7,970,640 comparisons if all cases complete (sum of lengths 33,211 × 48 × 5). The rolling 64-bit fingerprint covers all eight output arrays for each full-size case and requires the three repeated 8192 cases to match. This is a repeatability check, not a golden hash or proof for other inputs. The terminal receipt does not itself assert the expected count or `full_seen`; for an auditable clean run, the owner should verify `cases=15`, `comparisons=7970640`, exactly three `FULL_REPEAT_HASH` records with the same value, all `CASE_PASS` records, and successful process exit plus the existing async/error/flush checks.

For the SG readers, each workgroup is exactly 128 work-items. With required subgroup size `SG`, the flattened index `workgroup_id*128 + subgroup_id*SG + lane_id` covers each local index exactly once because the supported sizes 16 and 32 divide 128. The global range is rounded up to a multiple of 128 and the `i<active` guard prevents padded lanes writing. This is a sound isolated lane/index check under the stated queue/device contract.

## Expression equivalence and layout limits

The baseline producer preserves the parent expression at line 468: `v = ab[...] + dt[h]`; `gate[i] = (v > 20.0f ? v : sycl::log1p(sycl::native::exp(v))) * a[h]`. The candidate computes the same right-hand expression into a `const float loggate`, writes that value to `gate`, and immediately computes `native::exp(loggate)`. Baseline and candidate beta expressions match the parent sigmoid helper at lines 84–86. The probe appropriately compares gate and beta bits as well as the later factor bits. It deliberately does not force a volatile or explicit store/reload for candidate `loggate`, so it tests the proposed same-kernel materialization behavior rather than assuming an intermediate global roundtrip.

This is not a production-layout or recurrence proof. Production launches the gate kernel as a 3D `nd_range` with local extent `(1,1,256)` and computes its index from dimension 2. The probe uses 1D workgroups of 128 for the producers and readers. It reproduces the flattened `t,h` address and math expressions, but not the production WG256/3D mapping, its occupancy/resource behavior, or the consumer's full workgroup context and surrounding recurrence. Its SG16/SG32 readers are separate one-output-per-index kernels; the production consumers use `native::exp(gate[t*HV+head])` inside larger 3D workgroups and recurrence operations. Any same-kernel candidate must still be checked in each real serial/columns/pipeline/keyhead/quad/recurrence context and on actual reachable inputs; this probe can only be a necessary scalar/indexing screen.

## Input labels and interpretation

The deterministic input pattern is correctly described as synthetic. `domain()` maps the flattened index back to `h` via `i % HV`, then to the selected 16-value class. Default classes 0–7 include finite values around zero and the `v=20` branch with adjacent binary32 values. Classes 8–13 are marked artificial finite boundaries and include large positive and negative values; `v=80..104` take the `v>20` branch, while the negative boundary inputs exercise the producer's `native::exp(v)` and the resulting consumer gate can exercise small/subnormal/underflow-side `native::exp`. Optional classes 14–15 are artificial `+Inf` and quiet NaN. Labels are consistent with the generated classes and the README explicitly says none is an observed model range.

The one misleading phrase is the runtime label `plausible_synthetic_not_observed_model`: “plausible” is not supported by this source-only generator and can be mistaken for a model-domain claim. Rename it to an unambiguous label such as `finite_synthetic_domain_unverified`; keep `artificial_finite_boundary` and `artificial_nonfinite` as synthetic-input classifications. These classes describe construction only. They do not establish whether any value is within the Intel `native_exp` implementation's valid range or reachable in Strata. A mismatch in an artificial/unknown-domain class should remain a numerical-screen mismatch and keep the optimization unqualified, but must be reported as such; it is not by itself evidence of a production model failure or proof of non-reachability. Do not broaden the comparison tolerance to make it pass. Resolve applicability only with the device/compiler contract and separate real-input provenance.

## Build-option comparison and proof gap

The corrected probe CMake sets C++20 and IntelLLVM, compiles with `-fsycl -fp-model=precise -fsycl-default-sub-group-size=32 -fsycl-device-code-split=per_kernel`, and links with `-fsycl -fsycl-device-code-split=per_kernel -Xsycl-target-backend=spir64 -cl-fp32-correctly-rounded-divide-sqrt`. These intended JIT flags align with the immutable parent CMake's JIT path: per-kernel split at compile and link, subgroup default 32 at compile, `-fp-model=precise`, and the same spir64 backend divide/sqrt option at link. Probe additionally requires WG128 by its launch and device check; parent gate producer's production launch uses WG256/3D. The probe omits parent warning suppressions, which do not change FP semantics. The AOT `spir64_gen` path is not selected by this probe.

CMake's fast-math rejection inspects only `CMAKE_CXX_FLAGS`; by itself it does not audit configuration-specific `CMAKE_CXX_FLAGS_RELEASE`, toolchain-injected flags, `CXXFLAGS`, SYCL device-program compile options, or all backend/link options. The README correctly assigns this to root. No closed `compile_commands.json` was supplied with this immutable three-file probe snapshot or in the R126 report inspected here, so I cannot verify the resolved command/environment. Root should preserve and inspect the actual closed compile database and verbose link command, plus inherited SYCL options, for each translation unit; verify that `-fp-model=precise`, per-kernel split, subgroup 32, and the JIT `spir64` divide/sqrt backend option actually reach the probe and that no fast/relaxed option overrides them. This is an audit requirement, not a reason to add arbitrary flags.
