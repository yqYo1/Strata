# R142 — MoE prefill route-transfer candidate screen

Date: 2026-10-10 (Asia/Tokyo). Read-only source and external implementation review. No source changes, Git operations, builds, tests, runtime/model/payload access, GPU/profiler work, or cleanup.

**Decision: one narrowly scoped candidate merits a controlled comparison; no speedup is established.** Extend the existing GPU route-grouping count/scan/place path from fused MoE execution to the long-prompt, non-fused MMQ branch. That branch currently transfers the full route-ID array GPU→host, waits, constructs expert order plus `slot`/`src` maps on CPU, and uploads both maps. GPU grouping can construct the maps in place and return only per-expert counts for CPU scheduling. This removes route-metadata transfers and CPU O(TK) map construction; it does not reduce expert-weight streaming or its bytes. The extension is not a claim that grouping itself is new: GPU grouping already exists for a separate fused path.

## Current seam and candidate

At `prefill.cpp:4027`, the fused path invokes `fused::group(ids, T*K, K, n_expert, scratch, slot_dev, src_dev, queue)`. Its implementation in `moe_fused.dp.cpp:997+` zeroes expert counts, counts routes, scans counts and places each route into expert-contiguous rows while writing inverse `slot` and token-row `src` maps. Reusable scratch size is `group_bytes(n,E) = tiles_at(E) + (ceil(n/64)+E)*sizeof(int2)`; at the representative current shape `T=8192`, `K=10`, `E=512`, this is 22,576 bytes. That is small per-chunk scratch; the existing `slot_dev` and `src_dev` arrays are already sized for `T*K` and are reused. No full-context route buffer is needed.

By contrast, `prefill.cpp:4077–4201` in the non-fused path copies all `T*K` IDs to host memory and waits, builds `cnt/off/fill`, expert ordering, and route maps on the CPU, then copies the full `slot` and `src` arrays back (or uses mapped host buffers for those same transfers). A possible narrow implementation would call GPU grouping at this point, copy only the `E` counts to host, and retain its device `slot/src` outputs. Host code can still construct active-expert ordering and MMQ batch bounds from counts. This preserves the synchronization needed for host-side scheduling, but reduces its payload from O(TK) route IDs plus two O(TK) maps to O(E) counts. The host O(TK) loops and fill vector disappear only if the new path does not reconstruct equivalent route data on CPU.

Scope it initially to one-GPU, large streamed-MMQ prefill with ordinary expert ordering. Keep existing host grouping for peer/multi-GPU placement (the host path assigns peer rows as separate contiguous groups), resident-row-sort mode (it coherently reorders maps), and any unsupported/fallback schedule. Do not enable for fused-native execution, which already uses the GPU group kernel. The MMQ and combine consumers must be checked to ensure the generated maps define a consistent permutation; atomic placement may change row order within an expert, so byte-for-byte `slot/src` equality is not the oracle. Verify per-route expert identity, map inverses, MMQ outputs, combined outputs/logits and model state instead.

## Transfer bound and trade-offs

For `T=8192`, `K=10`, 32-bit entries, the host path moves 327,680 bytes of route IDs D2H and 655,360 bytes of `slot/src` H2D, totaling 983,040 bytes per MoE layer per chunk (0.9375 MiB). As an arithmetic scenario only, if 48 MoE layers each process four such chunks, this is 180 MiB of route metadata per request; at 32 chunks it is 1.40625 GiB. These are derived byte counts, not observed transfer counters, and depend on actual `T`, `K`, active layers and chunk count. The candidate does not save expert blob reads, weight staging, activation traffic, or any transfers required to fetch experts. It adds GPU count/scan/place work and a small counts copy; the CPU wait remains. At short prompts or low route volume, it may lose.

The source has `STRATA_GROUP_COPY` mapped-host handling for the existing host algorithm. That changes how the same route arrays are copied; it does not remove their CPU grouping or full-array data movement and is not the proposed change. Existing fused grouping is also not evidence that the non-fused MMQ extension wins. No retrieved B570 long-prefill trace attributes time or actual dispatch to this branch.

## External implementation screen

- The [vLLM XPU Xe2 grouped-GEMM source](https://github.com/vllm-project/vllm-xpu-kernels/blob/main/csrc/xpu/grouped_gemm/xe_2/grouped_gemm_xe2.hpp) is a current primary-source example of GPU-side expert row counts and tiled per-expert work scheduling. It supports using a small host count summary to schedule expert batches, but its W4A16/BF16/FP8/MX formats do not establish behavior or performance for Strata's native IQ2S/IQ3S kernels. R136 already screened this source as a kernel-format mismatch for a new IQ GEMM, so this report uses it only as route-scheduling precedent.
- The [SGLang Expert Pack implementation](https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/layers/moe/expert_pack.py) and [LMSYS/SGLang SSD Expert Pack author post](https://staging.lmsys.org/blog/2026-08-29-sglang-ssd-expert-pack) describe offline contiguous expert packing to enable direct-I/O and streaming. That does not provide a new candidate here: Strata already has a file expert source with direct-I/O support, while arbitrary GGUF tensor placement requires conversion/format handling and adds a packaging path outside this route-metadata question. Its reported CUDA route/cache results are not B570 or native-IQ evidence.

## Minimum discriminator for root

If selected, compare baseline and candidate on the same B570 long prompt (first >=32K, then the full physical 262,144-token lifecycle), same model/file format, chunk size, cache/ring settings, and one-GPU schedule. Keep non-fused MMQ dispatch fixed and record per layer/chunk: host grouping time, actual D2H/H2D route-metadata byte counts, GPU group-kernel duration, counts-copy duration and wait, active experts/row histogram, expert source and streamed weight bytes, MMQ time, and end-to-end prefill. Correctness must cover route/map invariants and output/logit/state comparisons through the complete context lifecycle. Reject if total prefill does not improve beyond run variation, if the group kernel erases transfer/CPU savings, if any route or output/state mismatch occurs, or if scratch exceeds the existing per-chunk budget. No runtime timing was performed for this screen.
