## External evidence and fit

- [ik_llama.cpp discussion #8](https://github.com/ikawrakow/ik_llama.cpp/discussions/8), especially the author’s explanation and AVX2 Ryzen-7950X table, describes a potentially fast route for *different* IQK quant types: replace large group codebook lookups with tiny nonlinear per-quant tables that fit in SIMD registers. It reports AVX2 model prompt/decode timings for IQ2_K/IQ3_K versus IQ2_XS/IQ3_S. This is a useful general lead but not a drop-in IQ2_S/IQ4_NL/Q8_K kernel: it changes stored quant type and quantization representation (quality/format scope explicitly excluded), and is a format redesign, not a single source-local NT1 optimization. The published machine is Zen 4 Ryzen 7950X, not 5600X.
- [ik_llama.cpp discussion #5152](https://github.com/ikawrakow/ik_llama.cpp/discussions/5152) discusses vectorizing sign expansion for IQ2_XS on AVX2. That applies to a different format path; Strata’s IQ2_S already forms a 32-byte sign vector with its bit-selector routine. It supplies no evidence that the same change improves current IQ2_S code or escapes current pressure. Reworking this path would also overlap the screened decoder/sign alternatives.
- [ncnn-MoE-Runtime README, Qn_K CPU weights](https://github.com/crafcat7/ncnn-MoE-Runtime/blob/main/README.md#qn_k-cpu-weights) documents direct AVX2 bit-decode dot kernels for Q2_K–Q8_K and optional lazy packed-weight sidecars. The README explicitly cautions that repacking costs resident memory and is not assumed to help single-token decode. The covered storage formats are Qn_K and MXFP4, not Strata’s IQ2_S/IQ4_NL. No source-pinned, 5600X NT1 result or matched bottleneck is provided, so neither repacking nor kernel transfer is admitted.
- [SGLang CPU optimization roadmap #8281](https://github.com/sgl-project/sglang/issues/8281) targets Intel Xeon/AMX CPU backend work, including AWQ INT4 and prefill blocking; it does not document a Zen 3 AVX2 IQ-format NT1 kernel. Its scope does not map to this path.
- [vLLM CPU MoE implementation](https://github.com/vllm-project/vllm/blob/main/csrc/cpu/sgl-kernels/moe.cpp) and [Intel LLM Scaler](https://github.com/intel/llm-scaler) focus on conventional INT8/FP8/INT4/Intel platform serving paths. The discovered material provides no exact IQ2_S/IQ4_NL/Q8_K Zen 3 single-token expert microkernel or transferable decode factor. Branch links were used only for discovery; no mutable upstream code is treated as a pinned implementation result.

## Source-local disposition

The frozen source already implements IQ4_NL multi-token lookup with an AVX2 `pshufb`-style small-table path (`iq_avx2_rows.inl`, `iq4nl_rows`), and the expert dispatch admits it for NT1 only through the multi-token threshold. This removes the apparent “small LUT in SIMD registers” opportunity for the requested NT1 path: applying a multi-token strategy to one token is not externally supported by the sources found and has no exact linked pressure evidence here. Q8_K activation quantization was just reviewed in R115; this search found no distinct verified NT1 fix for it.

For IQ2_S, R103’s exact linked control/candidate comparison already establishes the remaining scalar `iq2s_grid` loads. The attractive external small-table method changes quant formats; using AVX2 gathers or a different table-index strategy would restate screened/rejected candidates. The exact R103 candidate has no repeated stack-index reload or observed accumulator spill to target. No remaining external result identified a new factor tied to a measured Strata bottleneck.

Therefore nominate **no source change** from R117. A future candidate needs a new source-pinned AVX2 implementation for one of these exact formats and an exact linked/previously measured Strata pressure target. Preserve model quantization and ordered FP operations. Any later single-factor experiment must first state integer decode equivalence and exact FP order/rounding obligations, then validate NT1 correctness against the pinned reference; only after correctness and codegen gates should actual-weight timing be interpreted. No performance inference is made here.
