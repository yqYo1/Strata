Normative behavior that determines the contract
------------------------------------------------
Khronos SYCL reference says queue `wait()` blocks until all enqueued tasks complete and reports synchronous errors; `wait_and_throw()` also waits and routes unconsumed asynchronous errors to the queue/context handler. A synchronous submission exception is reported at the failing API call; prior successful submissions are still queued and may still be executing. `sycl::free(ptr, queue/context)` is explicitly non-waiting: freeing while commands using the allocation are enqueued or in flight is undefined behavior. The queue/context used to free must match the allocation's context. The async handler may run from `wait_and_throw`, `throw_asynchronous`, event `wait_and_throw`, or destruction when unconsumed errors remain, so destruction is not a substitute for an explicit recorded drain. Level Zero puts responsibility on the application not to destroy an executing queue; queue synchronization/fences establish completion, not host-process wall time.

Minimal source-level gates
--------------------------
1. Create one explicit SYCL queue bound to the selected Level Zero device, with `sycl::property::queue::in_order` and a user async handler. Keep handler state alive longer than queue destruction. The handler must be non-throwing and thread-safe: rethrow each `exception_ptr` only to extract/log its diagnostic, append a durable error record under a mutex (or atomically set a sticky failure plus preserve messages), then return. Because a recording handler consumes async errors, success depends on checking its sticky error list after `wait_and_throw`; the call itself may return normally despite the handler having observed an error.
2. Use checked, nonzero dimensions and overflow-safe byte calculations before allocation. Check every `malloc_device`/`malloc_host`/`malloc_shared` result for null. Allocate all input, baseline log-gate, baseline decay, candidate factor, beta, output, status, and guard buffers from this queue/context (or matching context). Keep host source vectors and all USM allocations immutable/alive until final completion. Initialize guards/status before any kernel submission. Only read device allocations after a completed queue wait, through explicit copy to host or supported shared USM.
3. Track every successful submission immediately (at minimum a `submitted_any` bit and successful event/count list); never mark a stage submitted before `submit` returns its event. A submission is successful only if the host call returned. If a later submit throws synchronously, report the failed stage but enter drain handling because earlier submissions remain live. Do not run the compare/readback stage if setup or producer submission failed. Do not overwrite inputs, reuse slots, free USM, destroy the queue/context, or let an allocation-owning destructor run while submitted commands could still reference them.
4. Normal completion path: after all intended producer, reference consumer, candidate, and readback submissions succeed, call queue `wait_and_throw()` inside a catch boundary. A successful return plus an empty sticky async-error record is the required device-side completion/error gate. Only then inspect every output/status/guard and compare (i) immutable source input hashes or exact input bits before/after, (ii) baseline log-gate bits, (iii) beta bits, (iv) baseline and candidate factor bits, and (v) guard tails. Print a single final complete receipt only after those checks and checked output close/flush succeed. A clean receipt requires normal process exit code 0, exact expected submit/test counts, no synchronous exception, no async handler records, successful `wait_and_throw`, all numerical and guard checks passing, and one complete parseable terminal record. No receipt, partial output, mismatched count, timeout, signal, nonzero exit, exception, or absent clean terminal record means incomplete/failed/indeterminate, never pass.
5. Failure cleanup path after any partial submission: synchronously drain the same queue with `wait_and_throw()` before any USM release or reuse, recording both the original submission error and every drain/async error. If the drain returns normally, the queue is complete and buffers may be freed (run remains failed). If drain throws but returns control, preserve the error and establish completion separately before freeing; SYCL async error delivery and completion are distinct questions. If drain hangs, device is lost, or completion cannot be established, do not free/reuse buffers or destroy an executing queue in that process. Avoid throwing destructors that silently free in this state; use an explicit owner whose cleanup is permitted only after a confirmed completion state. End the run as indeterminate and retain the one required diagnostic. A process-level forced termination may be necessary operationally, but must not be described as safe device cancellation or as a clean cleanup.

What a root wall-time kill means
-------------------------------
A wall-time supervisor observing its limit proves only that the host-side deadline expired and it requested/caused process termination. It does not prove the kernel stopped, that Level Zero completed or canceled submitted command lists, that device lost/recovery happened, that USM became safe to reuse, that an async handler ran, or that no partial output was written. Even observing that the process exited after a signal proves process exit, not device completion. Therefore a killed run is not a clean pass and provides no valid basis to reuse those buffers inside a surviving process. No reset, unbind, service restart, or recovery script invocation is authorized or recommended by this report; parent owns any separate diagnosis. A timeout/recovery script's exact behavior must be audited from its immutable committed version before describing the signal it sends.

Narrow auditable observation contract
-------------------------------------
For later root execution, require the runner to preserve the exact command/environment/debug Level Zero variables; record start time, child PID, deadline, each output line and whether the child exited normally or was signaled; and retain stderr plus the final receipt only when it is a completed run. The probe itself should emit stage-start/submitted/completed markers and the final receipt after `wait_and_throw` and bit/guard checks, with allocation dimensions and byte counts. The runner must distinguish (a) exit 0 + clean receipt, (b) normal nonzero/exception with drain-complete receipt, (c) timeout/signal with no completion receipt, and (d) runner/driver failure preventing an observation. Only (a) is clean completion. This is an admission contract, not permission to launch or recover the GPU.
