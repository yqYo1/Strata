# R144 — non-fused MMQ GPU grouping interface audit

Date: 2026-10-10 (Asia/Tokyo). Source-only audit of the fixed WPROBE609a270d tree. No edits to code, build, tests, runtime/model/GPU/profiler use, Git operations, or cleanup. This report resolves R142's proposed handoff before any source implementation.

## Finding: feasible with a small interface addition, not with the current public call as-is

`fused::group` currently returns `void` (`include/strata/prefill/moe_fused.hpp:49`, `sycl/src/prefill/moe_fused.dp.cpp:997`). It internally constructs a `Tables` view over caller scratch: `cnt[E]`, `off[E+1]`, `fill[E]`, `ts[E+1]`, then aligned `tiles` (`moe_fused.dp.cpp:69–78`). It zeroes `cnt`, launches count, scan, then place kernels on the queue (`:1003–1074`). `count_kernel` counts valid `[0,E)` expert IDs into `cnt` (:148–184); `scan_kernel` writes exclusive prefix `off[e]`, initializes `fill[e]=off[e]`, and writes total `off[E]` (:246–265); `place_kernel` atomically allocates each route's row in its expert range and writes `slot[i]=row`, `src[row]=i/k` (:268–284). Thus counts and offsets do exist on GPU, but neither is published to the caller; a new caller cannot safely infer the private scratch layout from `void*`.

Minimal private API: add `GroupTablesView group_with_tables(...)` (device pointers `counts`, `offsets`) and retain the current `group(...)` as a wrapper that calls it and discards the view. The view is valid only while the supplied scratch is not reused. The non-fused MMQ call should enqueue the group on `m.cs`, enqueue a D2H copy of exactly `E` `int32_t` counts to `m.cnt.data()`, and wait on that copy event before the host reads them. Do not expose or copy all scratch. Host can reconstruct `m.off[0]=0; m.off[e+1]=m.off[e]+m.cnt[e]`; `off[E]` is `T*K`. The returned `offsets` pointer is useful to a debug oracle but is not needed for the production host schedule. This keeps the scratch ABI encapsulated while publishing precisely the summary the host needs.

The queue contract is workable: `Prefill::init` rejects a non-in-order compute queue (`prefill.cpp:1055`); group kernels and the count copy can therefore be enqueued on `m.cs` in order. Waiting for the count-copy event drains the preceding route and group work on that queue. Host must not read counts before that event completes, and scratch / `slot_dev` / `src_dev` must not be reused until group placement and the count copy finish. After the wait, the existing MMQ work is enqueued on the same queue. Do not use the separate expert-copy queue for grouping or count publication.

One existing fault semantic needs preservation. The host currently rejects any invalid ID with `prefill: routed id out of range` (`prefill.cpp:4118–4122`). GPU `count_kernel` silently ignores invalid IDs and `place_kernel` writes `slot[i]=0` without a `src` row (`moe_fused.dp.cpp:167–170, 277–283`). For the new branch, after the count copy, sum counts in a checked wide integer and require `sum == T*K`; since every valid route contributes once and invalid IDs contribute zero, mismatch detects invalid IDs before any consumer uses the incomplete map. Return the existing error string. Require `T*K <= INT32_MAX`, `k>0`, and supported `1 <= E <= 1024` before calling `group` (it exits on unsupported E rather than returning an error). Guard multiplication and `group_bytes` arithmetic before allocation/use.

## Host scheduling and expert-source reconstruction

For a one-GPU path with no resident-sort transformation, expert row intervals must be the ascending-expert prefix sum represented by `off[e]`. Host `order` is already formed as ascending expert IDs with `cnt[e] > 0` (`prefill.cpp:4164–4169`). The MMQ primary path consumes `m.cnt`, `m.off`, and this order to build `bounds_host` and `bounds_dev` (`:4207–4234`); per-expert fallback gathers rows from `src_dev + off[e]` (`:4791–4795`). Constructing `order` from copied counts and recomputing `off` therefore suffices; `ids_h` is unnecessary on this eligible branch. Preserve the existing `rows_local=T*K`, `n_order`, `MMQ_GROUP` partition/bounds creation, and identity `m.ids_identity` table. This leaves the existing `stage_one(order[j])` / resident-pointer / `ExpertSource` / Stager / transfer-event code untouched (`:4580+`), so resident-vs-RAM-vs-file blob choice, ascending order, ring lifetime and batch formation remain the same. The candidate changes route metadata creation only; it does not pick expert sources or change expert-byte transfers.

The current `MoeBufs` allocation is enough for a temporary scratch overlay on ordinary non-compact MMQ: `moe_bufs(..., fused=false, compact=false)` provisions `T*K*1280` floats for `GU` (`prefill.cpp:1015–1025`), while `group_bytes(T*K,E)` is the count/off/fill/tile workspace (`moe_fused.dp.cpp:965–969`). At this source shape the workspace is much smaller, but implementation must compare checked `group_bytes(T*K,E)` against the actual allocated `GU` byte span; do not rely on a guessed size. Group finishes before the host waits on counts; after that wait MMQ's gate/up product reuses `m.GU` as destination (`prefill.cpp:4761–4765`). This is safe only because the same in-order queue prevents overlap. It requires no new allocation or context-sized route array and does not raise `bytes_needed`/borrowed-region capacity. For a borrowed allocation, use only the already-carved `m.GU` span and retain its owner/lifetime unchanged. Do not write expert-cache slots or `ids_identity` with scratch.

Physical 262,144-token context is processed through the allocated `m.T` chunk buffers on `Prefill::run`/`run_impl`; do not size scratch by request length. Require `group_bytes(T*K,E) <= GU_capacity` for every current chunk. Any failed guard, unsupported shape, non-MMQ layer, scratch shortfall or overflow must select the original host grouping path before writing maps. For small per-chunk `T*K`, use the original route path until the B570 crossover is measured; do not invent a threshold from this audit. The eventual opt-in selector should require a long request and a measured minimum chunk route count, default off, and preserve a cheap in-code fallback for the last short chunk.

## Exact eligibility seams

The exact callsite is `prefill.cpp:3992–4017`, inside `Prefill::run_impl` after router IDs are produced and before the existing host grouping branch. Start only when `use_mmq` is true, `fused_l` is false, candidate explicitly enabled, the whole request and current chunk pass the measured long/chunk threshold, capacity guards pass, and this is the regular single-GPU non-compact path.

- **Fused vs non-fused:** `fused_l` already selects GPU grouping at `:4017–4027`, including fused native-IQ when `fused_nat` is true. Leave that code untouched. Candidate is only the `else` route path where `use_mmq && !fused_l`; `!use_mmq` / FP16 fallback and compact work stay on the old grouping implementation.
- **Native IQ vs MMQ:** `lay.native` alone does not decide the candidate. Native-IQ fused layers (`fused_nat`) are excluded because grouping already runs on GPU. A native layer that actually falls through to `use_mmq && !fused_l` can use the same mapping interface, but keep it behind the opt-in and admit only after its native gather/MMQ checks pass separately. Initial measurement can start with non-native Q2 MMQ to isolate routing. Do not accidentally route an unsupported native format into fused kernels.
- **Peer and helper:** `no_peer` is based on `!core::peer_portable()` (`:3999–4001`), and peer MMQ builds a distinct local/peer row layout and `order_peer` (`:4124–4154`, `:4240+`). Exclude `m.pp != nullptr`, peer-enabled operation, stage-helper/handoff (`hand_in_`, `helper_`, `next_`, or split stage bounds), even when a peer happens not to receive rows. This keeps ordinary ascending expert offsets and avoids changing the peer's contiguous row block.
- **Resident sort:** `mmq_resident_sort_rows` reorders `off`, `order`, `slot`, and `src` together and requires `ids_h` (`:4174–4177`). Call the existing `mmq_resident_sort_eligible` predicate before selecting GPU grouping and stay on host path if it returns true. A mere request that is not eligible need not disqualify it, but the production gate should use the predicate result, not duplicate a simplified approximation.
- **CPU verifier / CPU expert path:** This seam is the GPU prompt `Prefill::run_impl` route, not `core::verify`/verify kernels or a CPU verifier oracle. The per-layer non-MMQ fallback (`!use_mmq`) remains on its current host grouping route. Do not add grouping behavior to verifier/decode code or claim CPU path coverage.
- **Layer-major and borrow:** `run_layer_major` requires full single-GPU compact FP16 and rejects peer/helper paths (`:2381–2399`); exclude it. Normal borrowed buffers are not intrinsically disqualifying: the candidate only overlays the existing MMQ `GU` span, but must prove its capacity from the carved allocation. Compact layouts are excluded. No new heap/device allocation is necessary.

## Mapping invariants and numerical acceptance

Atomic placement intentionally changes within-expert row order from the host's increasing route index. The map contract remains: for every route `i`, if `e=ids[i]`, then `off[e] <= slot[i] < off[e]+cnt[e]` and `src[slot[i]] == floor(i/K)`; every expert row in `[off[e],off[e+1])` appears once; `off[0]=0`, `off[e+1]-off[e]=cnt[e]`, and `sum(cnt)=off[E]=T*K`. These are the route-map oracle. For diagnostic runs, validate them against the original IDs using a separate correctness-only path; do not charge this extra full-ID diagnostic copy to candidate timing.

The source's fused API explicitly says order within expert is not fixed and no output depends on it (`include/strata/prefill/moe_fused.hpp:46–50`), but that contract applies to fused kernels, not automatically to MMQ. In the non-fused MMQ route, `src_dev` selects activation rows for row quantization (`moe_mmq.hpp:25–28`, `moe_mmq.dp.cpp:143–145`), bounds group expert intervals, and `ids_identity` scatters product rows; `slot_dev` then maps each route output into `Dm`. Each route's per-expert GEMM is a row product with the same expert weights and activation, and `moe_combine_kernel` uses `slot` while retaining route-k order `0..9` and the same FMA chain (`kernels.dp.cpp:1893–1917`). This supports the inference that a consistent row permutation should preserve each route result and combination association. It is not a formal MMQ bitwise guarantee: exactness depends on the MMQ backend having no cross-row reduction or order-sensitive shared fixup. The implementation admission oracle must compare MMQ products after inverse permutation by route and combined MoE output; demand bitwise equality first. If a backend exhibits a difference, locate whether the operation is genuinely order-sensitive. Do not waive output/logit/state changes as a harmless route permutation. Also compare final full-context state and generated logits/tokens at the physical context limit.

## Minimal source-only implementation handoff and next measurement

Implementation handoff (not performed here): (1) add the private `GroupTablesView` API above while retaining the legacy wrapper; (2) add a private route-grouping selector helper with explicit reason counters and checked chunk/request eligibility; (3) in the selected MMQ branch, enqueue group, enqueue/wait only the `E*4` count copy, validate sum, rebuild host `cnt/off/order`, and reuse all existing bounds, source scheduling and MMQ consumers; (4) otherwise execute the exact host path. Do not add allocation or alter peer/resident-sort/fused behavior. Add a debug-only map invariant oracle before performance admission.

Root's minimum discriminator should separate: selector/admission reason by layer and chunk; GPU group kernel time; counts D2H bytes/time and event wait; old-path route-ID D2H and `slot/src` H2D bytes; host grouping and host `cnt/off/order/bounds` construction time; active expert count and row-count histogram; `rows_local`, MMQ batch/bounds count and max rows; resident/RAM/file expert source, expert DMA bytes and copy wait; GU/D and total prefill time. Hold model, prompt, chunk, cache/ring/source and warm state fixed. Compare baseline/candidate at >=32K and then the full 262,144-token lifecycle, with repeated runs and per-route output mapping checks. Admit only if counters prove this branch ran, correctness passes, end-to-end prefill improves beyond run variation, and scratch/capacity fallback works for short final chunks and all tested layouts. This audit contains no B570 timing or hotspot claim.
