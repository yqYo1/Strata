# R131 — exact IGC v2.41.5 single-kernel capture controls

Date: 2026-10-10. Read-only inspection of the installed IGC package/library and version-pinned Intel IGC source documentation. No compiler, disassembler, executable, runtime, SYCL, device/GPU query, build, test, profiler, model/payload, Git action, source edit, or cleanup was performed. No active owner output was read.

## Finding

The installed release IGC exposes the known shader-dump controls, and Intel's documentation at the exact v2.41.5 tag explicitly marks the core dump switch, custom output directory and regex file filter as available in Linux Release builds. Thus release-vs-debug is not a blocker for requesting normal shader dumps or using those settings. The exact names are `IGC_ShaderDumpEnable`, `IGC_DumpToCustomDir`, and `IGC_ShaderDumpRegexFilter`.

However, the docs do **not** establish a hard single-kernel selector: the regex is described only as filtering dump *files* by regex, without documenting which filename field it matches, a kernel-name mapping, or whether it suppresses compilation of other kernels. The docs also identify `*_options.txt` as options passed to `clBuildProgram`; they do not establish that a Level Zero SYCL JIT module-create path emits this sidecar or that it records all SYCL/ZE build options. No IGC flag documented here caps aggregate output bytes. Accordingly, exact one-kernel selection, a ≤5 MiB aggregate, and a matching Level Zero/SYCL JIT-options record are not proven by the installed-artifact evidence alone. A broad first capture is not a safe way to discover the naming convention under the stated bound.

## Exact names, values and release/debug boundary

Intel's v2.41.5 `configuration_flags.md` says flags use environment names `IGC_<flag>=<value>` and specifically shows `IGC_ShaderDumpEnable=1`. The shader-dump instruction page documents the following:

- `IGC_ShaderDumpEnable=1`: request standard shader dumps. It says the default destination is `/tmp/IntelIGC`.
- `IGC_DumpToCustomDir=<path>`: route dumps to a custom directory; its parent directory must already exist.
- `IGC_ShaderDumpRegexFilter=<regex>`: configuration table says “Only dump files matching the given regex.” No regex grammar, field, anchoring, or named-kernel guarantee is specified there.
- Avoid `IGC_ShaderDumpEnableAll=1`: it dumps all LLVM passes and forces recomputation of analysis passes. It is available in Release but creates much broader output than the minimum normal dump.
- Avoid debug-only switches such as `IGC_ShaderDumpEnableG4`, `IGC_ShaderDumpEnableIGAJSON`, `IGC_ShaderPassDisable`, and `IGC_ShaderDisplayAllPassesNames` for this purpose. The Release table marks the first two and pass-display/disable controls with `-` (requires a debug build). `CompileOneAtTime` is also a debug-only shader-debug control and its doc says it produces no valid binary, so it cannot provide the desired matching kernel artifact.

The table's status legend is explicit: `-` means requires debug build; `Available` means available in release builds; `Diagnostic` requires a special build option. The three controls above are all `Available`.

## Documented dump products and qualifications

At v2.41.5, `shader_dumps_instruction.md` says normal IGC runtime shader dumps include `*.spv`, `*.spvasm`, LLVM IR checkpoints (`*_beforeUnification.ll`, `*_afterUnification.ll`, `*_optimized.ll`, `*_codegen.ll`), `*.visa.ll`, `*.visaasm`, `*.asm`, and `*.isa`. It separately lists `*_options.txt` as “Options passed to `clBuildProgram`” and `*.cos` as patch tokens exchanged between IGC and Intel Compute Runtime. The docs describe `*.visaasm` as vISA assembly, `*.asm` as kernels in assembly form and `*.isa` as kernel binaries.

These product names demonstrate the content types IGC's documented shader-dump mechanism can produce in its documented runtime path. They are not proof that the installed Level Zero SYCL JIT uses every product path, that one `.spv` is per kernel rather than per module, or that `*_options.txt` records the Level Zero build flags. In particular, the documented `clBuildProgram` wording is OpenCL-facing. Treat the SPIR-V/options products as conditional until the exact SYCL/Level Zero runtime route is confirmed from its own output or a narrowly recorded module-create build-flags receipt. Do not relabel a full device image or offline build artifact as the matching JIT module without a verified identity link.

## Bounded owner recipe if a target-specific filename is already known

If root has a previously evidenced, unique IGC dump filename token for the one required GDN kernel, a future owner-approved run can be configured before the process's first JIT compilation as follows:

1. Use one fresh, empty, owner-controlled custom dump directory with its parent already created; set `IGC_DumpToCustomDir` to it. Do not use the shared default `/tmp/IntelIGC`.
2. In the one fresh process, set `IGC_ShaderDumpEnable=1` and `IGC_ShaderDumpRegexFilter` to an anchored/escaped expression matching only the verified target filename token. Keep `ShaderDumpEnableAll` off. IGC reads these settings at process/JIT initialization; do not change the variables after compilation starts.
3. Arrange the owner's normal per-kernel device-code split and submit only the necessary producer or consumer kernel under the already settled PCI admission. Do not turn on module-wide/pass-all dumping or any API trace.
4. The owner must verify immediately that the directory contains only the intended kernel's required SPIR-V, matching vISA/ISA, and a provably matching options receipt; compute aggregate bytes and hashes before retention. Enforce the existing 5 MiB retained-artifact ceiling in the owner controller. If the file naming cannot be matched in advance, unexpected kernels appear, the required metadata is absent, or the total exceeds the ceiling, stop/retire under the existing artifact-retention rules; do not expand into an all-kernel capture.

This is a conditional recipe, not a proven exact recipe for the current installed Level Zero SYCL path. In the reviewed evidence there is no previously verified v2.41.5 filename token for a generated kernel and no hard output-byte limit. If those prerequisites cannot be met without a discovery capture, then the bounded single-kernel Level Zero/SYCL capture remains unsupported/unverified. The safe resolution is to retain the R130 implementation gap rather than invent a flag or create an unbounded capture.

The immutable root-v3 probe snapshot has distinct source kernel types `BaselineProducer`, `CandidateProducer`, `GroupReader<SG>`, and `ScalarReader`; this identifies source-side candidates only and does not prove the IGC filename convention or one-to-one dump identity. Any future file regex must be rooted in an observed/pinned IGC filename, not guessed from a C++ kernel type.

## Confirmed / inferred / unresolved

**Confirmed:** installed IGC version and core library hash above; exact environment variable spellings occur in that binary; Intel's exact-tag release documentation marks three needed controls Release-available; custom directory parent must exist; default dump destination and product list as documented; regex is described as a file filter.

**Inferred only:** that the dump facility can receive the exact SYCL/SPIR-V JIT invocation in the current Level Zero backend; that a given `.spv`, vISA and ISA file trio all belong to one kernel; that filename regex can select a C++ named kernel; and that an options sidecar is produced for `zeModuleCreate`/SYCL JIT.

**Unresolved:** exact installed `.14` driver + oneAPI 2026.1.1 + IGC 2.41.5 Level Zero dump naming and filter semantics; whether its options sidecar exposes the exact SYCL/JIT flags; an aggregate output cap; and verified ≤5 MiB single-kernel artifacts. No capture was run or created.
