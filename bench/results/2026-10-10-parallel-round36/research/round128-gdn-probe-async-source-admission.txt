Ownership findings in probe source
----------------------------------
The queue is declared after `Errors errors`, and its async-handler lambda captures that object by reference. C++ reverse destruction order therefore keeps `Errors` alive through queue destruction. `Errors::collect` is `noexcept`, sets an atomic sticky error first, bounds stored diagnostics to eight, and catches failures while allocating/logging messages. In the ordinary path this is suitable: every submitted stage calls `wait_and_throw()` and then checks the sticky flag before continuing; the handler can consume an async error and still return, so that separate flag check is essential. Async diagnostics beyond the bounded message list are represented by sticky failure/overflow state.

The `Buffer` type allocates `malloc_shared` using the same queue later passed to `sycl::free`, is noncopyable, checks null before use, and holds the queue pointer. Buffers are constructed after the queue and thus destroyed before the queue; the handler's `Errors` remains alive after both. Shared USM is host-initialized/checked only before submissions or after `stage()` has returned from its queue-wide `wait_and_throw()`. Each case resets all result buffers only after the preceding stage completed. In the intended single-threaded, one-in-order-queue path, this prevents host/device overlap and keeps allocations live until consumers finish. The extent calculation is bounded (`MaxT=8192`, HV=48; compile-time assertion accounts for all `n+2G` allocations and remains below 16 MiB).

Per-stage `action()` exceptions, including synchronous submission exceptions, and `wait_and_throw`/sticky async errors are caught and exit via `std::_Exit(2)`. This deliberately skips all stack unwinding and `Buffer` destructors when submitted work may have failed or may still reference the USM. It is a safe anti-premature-free choice for this process; it is not an assertion that `_Exit` cancels GPU work or returns a queue-completion signal. Earlier stages have fully drained before each new stage begins, but the failing stage may have accepted some commands before a later command-group submission throws. The process's terminal state is indeterminate for device completion unless the wait completed successfully; root must classify code 2 as failed/incomplete and must not reuse or free these device-side endpoints in a surviving process.

For ordinary host-side errors outside `stage()` (allocation failure, output/flush failure, numerical mismatch, changed input, or guard failure), prior submitted stages have returned only after successful `wait_and_throw()` plus a clean error check. Normal unwinding frees buffers using the same queue/context, which is safe with respect to in-flight device uses. Allocation failure while constructing a `Buffer` is before any submission; a failed constructor does not invoke that object's destructor and the base is null if allocation returned null. A `sycl::free` failure from the implicitly `noexcept` destructor would terminate instead of yielding a normal failure receipt; runner must require normal exit code 0 in addition to a pass marker. No current source path was found that normally throws after submission but before `stage()`'s drain or its `_Exit(2)` branch.

Concrete limits / gaps
----------------------
- The C++ source emits no explicit build ID or pinned source hash at runtime; root must bind the executable to the captured source/CMake compile configuration externally.
- `gpu_selector_v` selects a GPU but source admission is by Level Zero backend, Intel vendor, device-name substring `B570`, shared-USM aspect, subgroup sizes 16 and 32, and work-group size >=128. It reports device and driver strings, but it does not pin/record the PCI BDF or prove uniqueness if multiple B570s exist. Root should record its intended device identity and ensure the selected one matches; a different selected GPU fails the current checks rather than falling back to CPU/OpenCL.
- `stage()` emits/flushed `STAGE` before `action()`, then on a submitted-stage failure logs `SUBMITTED_STAGE_FAIL` and calls `_Exit(2)`; it does not emit `TERMINAL,fail` on this path. The caller must accept a missing terminal record with exit 2 as a failed submitted-stage run, never as clean completion. The exception branch flushes `std::cerr`; if that diagnostic write itself fails, exit 2 still fails closed but detail may be missing. The async handler records only eight human-readable messages plus an overflow marker.
- Host exceptions after successful stage drain print `TERMINAL,fail` and return 1, with RAII freeing all buffers. A pass marker is printed before `main` returns; only observed normal process exit 0 confirms destruction/unwinding also returned normally.
- The source prints actual case/comparison counts but does not assert them against fixed expected totals at terminal. Root must enforce 15 `CASE_PASS` records, `cases=15`, `comparisons=7970640`, and three `FULL_REPEAT_HASH` records with identical values (the three 8192-token cases), plus an intact output capture and process exit 0. Require every expected stage-start/completion progression or equivalent accounting; absence of `TERMINAL,pass` is not a pass. A case pass is emitted only after its stage waits, bit comparisons, guard checks, and immutable input checks complete.
- Default finite values include synthetic, not measured model, inputs. Optional nonfinite mode is explicitly artificial. Neither establishes reachable model-domain coverage.
- The CMake file forbids a few relaxed math flags but is not a complete auditor of arbitrary inherited/link/JIT options. README correctly leaves exact inherited compiler/backend options to the root owner. The probe does not validate per-recurrence kernel contexts, generated production code, repeated state evolution, physical 262144 context, or performance.

Root process observation contract
---------------------------------
The minimum pass receipt is a single captured run with: exact immutable executable/source/CMake identity and compile/link/JIT configuration; intended B570 identity and driver version; exact diagnostic environment; process PID, start/end time and whether it exited normally or by signal; stdout/stderr file status; normal exit code 0; exactly 15 completed cases and expected comparison count; three equal 8K fingerprints; exactly one final `TERMINAL,pass` with the stage-one-only scope; no `SUBMITTED_STAGE_FAIL`, async error, unexpected stderr error, missing/truncated log, guard/input failure, or timeout. The run must also respect root's externally imposed bounded wall time and output/resource caps: the source contains no deadline/watchdog or resource limiter, and SYCL `wait_and_throw()` has no wall-time bound. `debug-run.py` is not a supervisor: it extracts the Python block from the adjacent `recover-xe.sh`, calls `diagnostic_environment(os.environ)`, and `os.execvpe`s the requested executable in the same process. It adds flushed UR/Level Zero tracing/validation environment settings and tracing layer while preserving caller settings; it does not capture environment, impose time/output/resource limits, record status, or kill a stalled child.

If the process exits via `_Exit(2)`, signal, or runner timeout, record the failing stage and available diagnostics, mark the endpoint state unknown, and retain only the designated diagnostic evidence. Do not claim device cancellation, safe USM reuse, or completed cleanup. If root has independently established a fully drained queue and the process returns a normal numerical/guard failure (code 1), its RAII cleanup is within the source's safe path. Exit 0 plus complete receipt is the only clean source-level screen pass. This is still necessary-only evidence and cannot authorize model timing/adoption by itself.

`recover-xe.sh` is separate: `debug-run.py` imports only its diagnostic-environment function and execs the child; it does not call the script's CLI/recovery path. The shell script defaults to inspection; actual reset/rebind operations are gated behind explicit `--apply` and its safety checks. This report neither recommends nor invokes recovery. A kill from an external runner does not imply that recovery is needed or that the driver reset/canceled the queue.
