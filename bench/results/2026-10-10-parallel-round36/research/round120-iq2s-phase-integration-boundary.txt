## Small call graph and the seam

The production CPU path in the frozen caller snapshot is:

`expert_source.cpp` quantizes each routed token's layer input with `native_quant_act`, stores pointers to activation and destination rows in per-expert `ExpertJobMulti`, then calls `run_split_multi_native` (lines 2730, 2799). `ExpertPool::drain` mode 5 invokes `native_gu_rows` on disjoint output row ranges (CPU snapshot `pool.cpp:653`). `native_gu_rows` asks `native_gu_dispatch(f.gu_type, nt)` and routes to GGML, AVX-512 IQ, or AVX2 IQ (`native_expert.cpp:125-194`). The current AVX2 wrapper enters `iq256_gu_rows` (`iq_avx2.cpp:493-495`); `gu_rows` calls the row dot once for Gate and once for Up, then forms the existing SwiGLU result (`iq_avx2_rows.inl:155-164`).

The isolated NT1 direct/index helpers reside under `sycl/tools/native-service-calibration`; they are not production call targets. If later runtime evidence justifies integration, the narrowest seam is a new explicit dispatch arm in the Gate/Up route (`native_gu_dispatch` → `native_gu_rows`) for IQ2_S/type 22, `nt==1`, on an AVX2/FMA-capable caller, forwarding each Gate/Up row to a productionized exact dot. Keep `native_down_dispatch` and `native_down_rows` untouched. Do not place an NT1-only function in the generic row path so that NT2+ can accidentally select it. Keep GGML as fallback when the feature is off, type/layout/ISA is ineligible, or the call is not NT1. Avoid routing by `NativeFmt::d_type`; the relevant pack type is `gu_type`.

`native_gu_dispatch` currently chooses by `(type, nt)` and CPU feature/environment state; it is the Gate/Up-vs-Down selector, not a prompt-phase selector. `native_down_dispatch` is a separate expert subphase. The dispatch API does not carry a `PREFILL`/`DECODE` request-class value. Thus a global change for IQ2_S NT1 here would apply to every caller that reaches this native CPU path. To preserve independently selectable prefill and decode policy, thread an explicit request-phase policy from the engine-level owner to the native job/dispatch decision (or use separate caller-supplied policy objects); keep a default-off policy per request class. Do not reuse `nt`, `native_gu_mt_min`, or the GU/Down phase flag as a proxy for prefill vs decode. The whole snapshot shows `ExpertPool` construction and decode-side `run_split_multi_native`; `prefill.hpp` declares `set_cpu_pool`, but the captured prefill source does not contain a call to it. Verify actual target-revision callers before deciding whether any prefill path reaches this CPU seam.

## Static eligibility and preserved fallback

The actual-cohort shape is `H=2560`, ten `QK_K=256` IQ2_S blocks per row, with one Q8_K activation of the same `n_embd` extent. `NativeFmt::gu_row` and `up_off` define Gate/Up row starts and the source blob is validated before pool use. The existing AVX2 row adapter casts each supplied activation to `block_q8_K`, uses `n/QK_K` blocks, and calculates both rows independently. A helper shaped like R116's standalone ABI (`n, block_iq2_s*, block_q8_K*`) must be adapted behind the validated production row path; it must not be called on arbitrary GGML strided rows or use the separate Down role. `nt==1` means one activation pointer and one output pointer; for multi-token jobs, the current `row_dot<TY,NT>` reuses decoded data across tokens, so those calls must retain the established NT-specific kernel/fallback. The NT1 helper is not a multi-token substitute.

Gate and Up output must preserve the existing dot-result FP order and final scalar expression. The R116 linked contract requires keeping separate scale multiplication and the ascending per-block FMA accumulation/reduction tree if exact output bits are required. Correct integer index mapping alone is not enough. AVX2 execution requires the checked AVX2/FMA CPU capability path; the AVX2 translation unit must not be entered based on format alone. On CPUs where AVX2 is unavailable, retain GGML. For AVX-512 CPUs, the current `Iq512` choice at eligible NT values and existing default GGML at NT1 remain the baseline; an AVX2 NT1 candidate must not silently suppress either path unless a separate policy explicitly requests it and evidence qualifies it. Existing `STRATA_NO_IQ256`, `STRATA_NO_IQ512`, and multi-token threshold behavior should remain orthogonal. `STRATA_NO_Q8K_AVX2` governs activation quantizer choice, not weight-dot dispatch; exact quantizer byte parity and MXCSR conditions remain a correctness gate.

## Pointer ownership and lifetime at the call

`ExpertJobMulti` is assembled in the decode-side caller from stable expert blob pointers, per-token activation buffers, and output-row pointers. Native activation storage is owned by the expert-source decode state; job pointer arrays and output rows remain caller-owned. The synchronous `run_split_multi_native` call drains and waits for the worker tasks before returning, and worker mode 5 only writes its assigned `[r0,r1)` rows. Therefore a future dot must consume these pointers synchronously, retain no activation/row pointer past the pool wait, and write only the supplied row interval. It must not stash a pointer to worker-local scratch, the temporary activation pointer list, or per-call output storage in static/cache state. Any new dispatch policy value must be copied into the submitted job/batch (or immutable pool configuration) so workers do not read a mutable request setting while a batch is in flight. This lifetime account is from separate frozen snapshots and must be rechecked on the target revision.

## Minimal gates before adoption

1. First close the exact source/linked qualification already outstanding: match the candidate/helper/table against its pinned source; confirm production trait ABI and row layout, exact linked symbols and ISA selection; pass release and sanitizer extent checks; prove activation-byte parity under the recorded rounding/MXCSR contract; compare Gate, Up, and finished FF values bitwise against the production baseline across the admitted actual-weight cohort. The archived actual-cohort pass is synthetic-activation and does not substitute for these target-binary gates.
2. With one fixed real model and fixed decode settings, compare baseline and candidate under repeated sessions that enter decode at context length at least 32K. Use identical prompts, seeds, routes where available, and session/lifecycle setup; include multiple repeated decode windows per run and independent repeats. Require unchanged token/logprob behavior under the project's existing correctness policy, no changed route inputs caused by prior-token divergence, no output/state faults, and no persistent allocation or lifetime failures. Record exact model/build identity and the selected NT1/NT>1 expert cells. This establishes a decode use case, not the physical maximum-context boundary.
3. Separately exercise physical-context boundary/lifecycle cases on the same real model: a prefill covering exactly 262,144 positions; a boundary case split at the physical end (262,140 + 4) and at least one repeated/resumed lifecycle with boundary-adjacent chunks; and a distinct 262,143-token prefill followed by one decode step ending at 262,144. The 262,144-position prefill cannot itself be followed by a decode token without exceeding capacity. Compare baseline/candidate intermediate state hashes and first-difference locations at the established engine boundaries, selected IDs, final output/logprobs, and save/restore or repeated-session behavior. Require normal completion and zero unexplained divergence before considering timing. R21 records prior instability at the 262140+4 boundary (first run passed; repeat after an intervening 32K comparison diverged), so one pass is insufficient: isolate any mismatch and reproduce cleanly before adopting any performance path.

Only after these correctness and lifecycle gates pass should a separately owned timing round test the NT1 dot and full decode service. No timing or model performance claim follows from this static review or from the current linked-code artifact.

## Decision

There is a small, clean *potential* dispatch seam for IQ2_S NT1 Gate/Up, separate from Down and with existing fallback. It is not yet an admitted production candidate: the isolated helper is not integrated, phase identity is absent from the dispatch signature, source snapshots differ in revision, and linked/correctness/runtime gates remain. If the user's desired PREFILL/DECODE independence is required, carry that choice explicitly from the request-level owner; do not let a generic `nt==1` rule collapse it. Proceed to implementation only after the root's timing and correctness evidence makes this exact cell worth pursuing.
