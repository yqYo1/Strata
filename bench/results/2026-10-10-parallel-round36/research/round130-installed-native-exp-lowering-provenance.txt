## What the versioned source establishes

The installed `sycl/detail/builtins/native_math_functions.inc` device-side macro implements `sycl::native::exp(x)` by calling `__spirv_ocl_native_exp(x)`. That is a frontend mapping to the OpenCL extended instruction in SPIR-V; it is not proof of later IGC algorithm selection or native machine code. The closed compiler build uses SPIR64 and embeds/loads SYCL device code, while the Level Zero driver and IGC are separate installed components. Intel's oneAPI guide describes runtime JIT from SPIR-V to device binary; IGC's VISA guide describes JIT finalization from virtual ISA to native GEN instructions. Those pipeline descriptions explain why an installed header or the host executable's imports alone cannot settle the final native sequence.

I checked the exact IGC release lead: the installed IGC packages are 2.41.5 and Intel's public release list contains tag `v2.41.5` (release URL below). I did not find a version-pinned public implementation source for the final `native_exp` lowering or its flags in the checked source lead. The guessed `IGC/BiFModule/Implementation/Math/native_exp.cl` location is absent at that tag; the adjacent ordinary `exp.cl` implementation is not evidence for `native_exp`. Therefore I do not transfer an algorithm, input interval, error bound, or denormal policy from `exp`, a different IGC release, or an unpinned public compiler tree. Khronos specifies `native_exp` as OpenCL extended-instruction opcode 83 and leaves accuracy/input range implementation-defined; this describes the contract boundary, not this installation's implementation.
