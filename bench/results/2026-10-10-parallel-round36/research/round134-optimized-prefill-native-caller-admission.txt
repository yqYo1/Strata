# R134 — optimized long-prompt caller and native expert admission

Date: 2026-10-10. Read-only audit of immutable production source and the committed report registry. No implementation, build/compiler/disassembly, test, executable, runtime, profiler, GPU/device query, model/payload access, Git operation, cleanup or active source/output inspection was performed. Decision: **R132's refusal is specific to the general CPU single-token callback, not all prefill native-expert execution.** The optimized long-prompt caller can dispatch native IQ per-expert, multi-token work, but that implementation is on the GPU; the source does not show a native per-expert multi-token CPU prefill caller. Native CPU multi-token remains wired to verifier windows.

## Caller graph and native path

`generate.cpp` invokes `prefill.run(...)` for the batched prompt at lines 11801–11804. Its separate per-position generation path calls `drive_pool` once per layer/position; the source explicitly notes at 12757–12761 that prefill also traverses that loop. That general callback reaches `expert_pool_dispatch` in `expert_source.cpp`. At 2435–2440, it checks `expert_layout().native` and refuses with “the single-token expert path does not take a native (IQ) pack.” This establishes a native refusal for that callback, not for every expert path in `Prefill::run`.

The optimized prompt caller is directly in `Prefill::run` (`prefill.cpp`, beginning line 2332). For routed MoE layers, lines 3985–4013 derive `fused_nat`: it requires an MMQ or fused-only layer, `stream_all`, no peer device, native pack layout, and `fused::native_supported(gu_type, d_type)`. `fused_l` selects either ordinary fused quantized experts or that native fused case. On long chunks the source's guard errors if a fused-layout buffer would otherwise be used by a layer not served by the fused path. When selected, lines 4017–4027 quantize the layer activations and group the `T * K` routed rows by expert on device. Lines 4034–4050 build batches of expert pointers from the resident cache or streamed stage ring; lines 4058–4065 call `fused::experts_native(...)` for native formats, otherwise `fused::experts(...)`. Thus each expert kernel receives the layer's `T*K` rows, with routing/grouping and output rows on the device; this is a multi-token prompt route, not the CPU `ExpertJobMulti` pool.

The header `moe_fused_iq.hpp` lines 1–12 documents this as the opt-in native-GGUF fused int8 prompt path. It lists gate/up IQ2_XXS, IQ2_XS, IQ2_S, IQ3_XXS, IQ3_S, IQ4_XS and down Q2_0/IQ4_NL; unsupported pairs/layers retain MMQ or FP16 paths. The native admission function at `moe_fused_iq.dp.cpp:1361–1367` additionally requires native support not explicitly disabled (`STRATA_PF_FUSED_NATIVE=0` disables it), request via the fused setting, covered format pair and supported device. The kernel entry at 1396 onward dispatches native GPU kernels by format. This is a conditional route, not a universal property of all native packs or every long prompt.

By contrast, `expert_pool_dispatch_multi` at `expert_source.cpp:2549–2569` prepares multiple activation rows and native activation quantization for a verify window; lines 2785–2800 aggregate entries into `ExpertJobMulti` per expert and call `run_split_multi_native` when the pack is native. `generate.cpp:12464` supplies its callback to `ver.run(...)`. That is the native multi-token CPU path proven by source. There is no call from the optimized prompt branch to `expert_pool_dispatch_multi` or `run_split_multi_native`; the optimized branch's `experts_native` is a SYCL/GPU kernel entry.

## Conclusion and runtime limits

The broad claim “native IQ expert work is verifier-only” is too broad for this snapshot: under the documented opt-in and layer/device gates, optimized long-prompt prefill has native IQ per-expert multi-token **GPU** execution. The narrower claim “native multi-token **CPU** per-expert work is only wired to verifier windows” is supported by the inspected caller graph. General per-token `drive_pool` refusal alone cannot adjudicate the optimized prompt route.

Static reachability does not prove which branch ran in a measured 32K request, its exact chunk/layer coverage, or actual kernels executed. To establish that for the closed model result would require an already-retained run configuration/summary with the fused environment settings and per-layer route evidence (or a bounded future caller counter); none is asserted here. No new candidate is admitted: this finding corrects scope and identifies a GPU route, not a CPU prefill batching candidate or a measured speed/correctness result.
