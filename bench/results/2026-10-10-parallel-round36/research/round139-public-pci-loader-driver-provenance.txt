# R139 — public PCI loader API and driver lookup provenance

Date: 2026-10-10. Static source/API/library-metadata review plus the supplied closed identity-refusal receipt. No compiler, build, test, executable, runtime/API call, GPU query, profiler, payload/model, Git action, source edit, cleanup, or ACTIVE runtime file was used. This review is not a new runtime result.

## Finding

The initial failure was caused by querying a public standardized device API through the driver's vendor/experimental extension-name resolver. Those are different dispatch paths. The closed run's `ROOT_CAUSE.json` records that installed driver `26.31.39395.14` advertised PCI extension 1.0, but `zeDriverGetExtensionFunctionAddress(driver, "zeDevicePciGetPropertiesExt", ...)` returned `ZE_RESULT_ERROR_INVALID_ARGUMENT` (`2013265924`). The process exited 1 after 0.2417 seconds, before app USM allocation or any kernel stage; ownership closure was clean, and the post-cursor kernel interval was complete with no new driver entries. This was an identity/startup refusal, not a numerical failure or device-reset event. The 48,748-byte stderr trace remains represented by the closed receipt; I did not reread the raw trace.

This distinction matches the Level Zero API surface. In the pinned upstream loader `v1.32.0` DDI header (the loader component version attached to upstream compute-runtime release `26.31.39395.13`), `ze_pfnDevicePciGetPropertiesExt_t` has the exact `(ze_device_handle_t, ze_pci_ext_properties_t*)` signature and `pfnPciGetPropertiesExt` is a member of `ze_device_dditable_t`, alongside the other device calls. The same header declares `zeGetDeviceProcAddrTable` as the exported entry used to provide the device table. The driver extension table/API is separate: the driver DDI has `zeDriverGetExtensionFunctionAddress`, while the Level Zero driver API documentation describes it as retrieving function pointers for vendor-specific or experimental extension functions. The PCI properties specification documents `zeDevicePciGetPropertiesExt` as the public device API and demonstrates calling that function directly with the `ze_device_handle_t`. The original name lookup therefore asked the driver-extension resolver for a function whose public ABI is the device-table PCI entry. The advertised PCI extension property establishes PCI extension support/version; it does not guarantee that the same symbol name is retrievable through the vendor/experimental resolver.

The installed loader metadata is consistent with this public path: `libze_loader.so.1.32.0` exports `zeDevicePciGetPropertiesExt`, `zeDriverGetExtensionFunctionAddress`, and `zeGetDeviceProcAddrTable`. Installed `libze_intel_gpu.so.1.17.39395` exports `zeGetDeviceProcAddrTable` but has no dynamic export named `zeDevicePciGetPropertiesExt`. This is expected for a loader-dispatched public API, not proof of a missing driver implementation: the device DDI table supplies the driver-side function pointer under `pfnPciGetPropertiesExt`.

The public header prototype is also unchanged and matches the loader DDI function signature.
