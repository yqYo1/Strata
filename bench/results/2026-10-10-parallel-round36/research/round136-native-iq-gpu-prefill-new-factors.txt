# R136 — native IQ GPU prompt kernels: new factor screen

Date: 2026-10-10. Read-only source and external implementation screen. No source edit, Git operation, build/compiler/disassembly, test, runtime, profiler, device/GPU query, model/payload access, cleanup, or active source/output inspection was performed.

**Decision: no new candidate admitted.** The frozen source already contains the central transferable idea from other MoE GEMM implementations: group routed rows per expert, tile by expert/row, decode quantized weights into a local tile, and reuse that tile across multiple routed rows in an integer matrix operation. The nearest new Intel/Xe2 grouped GEMM references handle BF16/FP16 or blockwise INT4/FP8/MXFP4, not Strata's native GGUF IQ2/IQ3 codebooks and scales. Their tile policies are not evidence that an analogous IQ kernel is faster or numerically preserving. Existing reports already cover quantized-weight reuse, output staging, XMX alternatives, shared-prefix/transfer changes, per-format lookup, and row/tile-size tuning. There is no retained B570 per-layer trace or timing showing this optional native GPU branch executed in the original >=32K result; consequently no measured hotspot can be assigned to it.

## Frozen implementation and route

Production references below are from immutable snapshot `gdn-gate-consumers-cd353f30`, revision `cd353f30a47dfd42818aace6f464bd227084e779`, manifest SHA-256 `1ac15ccad1b17ca2913f17abdf40a4989f567a39568cb27bf74721af9572dcfb`. The relevant pins are `sycl/src/prefill/prefill.cpp` SHA-256 `f3c9bb38b46cdc111e9e663cc606d655f60f07c05873aff5499d51895e886c77`; `sycl/src/prefill/moe_fused_iq.dp.cpp` `1717285bc25ad7742cd10a9077682ffeed7ee8b98e485b0a52157be337940998`; `include/strata/prefill/moe_fused_iq.hpp` `84d0c99ace277a53deb5d091b2a0a5137fdc390f834815b43e8a5a910f42b4c8`; and shared fused API `include/strata/prefill/moe_fused.hpp` `2809428405209d177a5ded160f62707f21eb344e85c84de8837b2b86ea938f65`.

The prompt selector at `prefill.cpp:3992–4013` admits `fused_nat` only for a native format layer with a compatible MMQ/fused-only plan, streamed large chunk, no peer, and `native_supported` device/format/opt-in result. In that branch, `:4024–4027` quantizes layer activations once and creates GPU expert groups from the layer's `T*K` route IDs. `:4034–4050` constructs each batch's expert blob pointers from resident or streamed slots. `:4058–4065` calls `experts_native` for the native case. These are precise reachability gates; they do not prove any particular measured request selected them.

In the frozen SYCL translation, `moe_fused_iq.dp.cpp:587–607` uses a workgroup-local decoded weight buffer, per-weight scales, a four-stage activation tile and the native format codebook. The common `native_kernel` is launched with workgroup size `THREADS` (512) and required subgroup size 32 at `:1271–1288` (the 2-WW launch is likewise `:1309–1337`). It handles each group tile through the expert row list (`:634–640`), loads the `src` activation-row mapping into local storage (`:676–695`), decodes IQ weights via `convert` (`:428–559`, `:697–707`) and applies them over routed rows with int8 matrix dot operations and FP scale/FMA reconstruction (`:727–815`). Gate/up is followed by SwiGLU and per-row int8 H quantization (`:817–859`), then the down kernel consumes H. The source uses a SYCL `local_accessor` for this tile and a DPCT experimental matrix abstraction outside the HIP-specific implementation (`:223–264`, `:1257–1288`). No CUDA/HIP-specific proposal is presumed portable to B570.

Some current-source measurements are explicitly RTX 5070 only: the comment at `moe_fused_iq.dp.cpp:1343–1357` compares 64/128 routed-row tile shapes at 2K/3.5K/8K and selects based on average rows per expert. It provides no B570 ≥32K phase attribution. The source also deliberately pipelines next-stage activation/weight loads and notes that decoding before products regressed on the RTX 5070 (`:809–815`); changing that schedule would repeat a screened experiment.

The arithmetic and route constraints are already quite specific. `moe_fused_iq.hpp:5–12,35–39` states that grouping is on GPU, expert blobs are pointed to directly (no gather), input rows come from `src`, and the kernels perform gate/up, SwiGLU/int8 H, then down into routed output slots. The comment at `moe_fused.hpp:46–50` leaves row order within expert unspecified but requires the `slot` map to scatter results to the combine's rows. A candidate must preserve every token/expert pair and that slot mapping, exact supported IQ codebook/sign/scale reconstruction, the kernel's int8 activation and H quantization, FMA/dot order, router coefficients in combine, and sequential layer/chunk state.

## External implementation screen

- The vLLM XPU kernels repository is the closest current Xe2/SYCL grouped-GEMM reference. Its public Xe2 source entry `csrc/xpu/grouped_gemm/xe_2/grouped_gemm_xe2.hpp` includes a `MoEGEMM` that computes each expert's row count/tile range and dispatches a tiled GEMM, while its Xe2 policy has data-type-specific tile choices. The public interface describes W4A16 with 4-bit weights and block scales and caller activation between GEMM1 and GEMM2 (`include/sgl_kernel_ops.h`, `moe_grouped_mm_nt_xe20_w4a16`). Release notes describe native Xe2 grouped-GEMM routes for MXFP8/block-FP8. These are relevant architecture examples, but they don't decode IQ2/3 grid/sign codebooks and their BF16/FP16/FP8/INT4/MXFP formats use different reconstruction and rounding. The use of subgroup size 16/GRF-specific Xe2 policies in the project also cannot be copied into Strata's required subgroup-32 workgroup without a different layout and full correctness/performance admission. Sources: [Xe2 grouped GEMM implementation](https://github.com/vllm-project/vllm-xpu-kernels/blob/main/csrc/xpu/grouped_gemm/xe_2/grouped_gemm_xe2.hpp), [Xe2 kernel policies](https://github.com/vllm-project/vllm-xpu-kernels/tree/main/csrc/xpu/grouped_gemm/xe_2), [operator signatures and format contracts](https://github.com/sgl-project/sgl-kernel-xpu/blob/main/include/sgl_kernel_ops.h), [vLLM XPU release notes](https://github.com/vllm-project/vllm-xpu-kernels/releases).
- MachX's C++/SYCL implementation and B70 reports were already screened in R118. Its reported Q8_0 MoE paths and row-grouped prefill work use a different weight representation/engine and another Arc Pro model; neither gives an IQ kernel change for Strata's current path. Source/report: [MachX](https://github.com/Red-Weasel/machx-inference-engine); prior finding in `round118-external-prefill-next-candidate.txt` (SHA-256 `c8720358302161ef837b22b39bca4c4292da87a326e92e8321cbd408b88670ab`).
- Existing related candidate screens and decisions: R132 (`round132-cpu-prefill-batching-new-candidate.txt`, SHA-256 `7faee162ac2d9610d320992af262f6c73fe775eb53670c221ee2ae9e0b51d63c`) concludes no CPU batching candidate; R134 (`round134-optimized-prefill-native-caller-admission.txt`, SHA-256 `a8fb8f5164579271853667957abc74d506378b0ab9986e8ed08897057cad3dcf`) identifies this conditional GPU route and notes that source reachability is not observation of a 32K run. The existing XMX GEMM audit found the standalone FP16 joint-matrix alternative was 4–5x slower than dequant + oneMKL on its reported Intel card and lacked MoE route integration; see `prefill-xmx-existing-code-audit.txt` in the committed report set. R108–R110 already cover the same-buffer gate-exp/fusion idea and its unresolved numeric admission. R132 and earlier CPU reports cover per-token-weight reuse and CPU multi-token kernels; they do not establish a new change for this GPU kernel.

## Candidate disposition and next evidence

I found no distinct source-local factor to recommend from these leads. Grouping/tiled expert scheduling, quantized-weight reuse across token rows, per-format lookup/decode, SwiGLU/H intermediate, stage overlap, and row-tile size already exist in this implementation or previous reports. Replacing IQ with W4A16/FP8/MXFP or materializing/retaining a format-wide converted pack would change the implementation/data representation and violate the requested format-preserving, bounded scope. A full XMX/oneMKL rewrite duplicates the existing XMX audit and still needs gather/activation/slot integration.

No controlled >=32K experiment is proposed for a nonexistent candidate. If a future independent result or owner audit admits one B570-specific factor, first use the same ≥32K prompt and existing native-prompt setting with a closed, bounded per-layer record of native vs MMQ/fallback selection, native GU/D launch count, expert row-count/tile histogram, and separated GU/D/other-prefill times. That verifies both caller execution and whether the putative phase is material. Only then compare baseline vs one changed kernel factor with identical input, route IDs where capture is permitted, chunk/ring/cache conditions, numerical state/logit checks and the full physical-context lifecycle required by the project. No claim about 32K runtime selection, hotspot, speed, or adoption is made here.
