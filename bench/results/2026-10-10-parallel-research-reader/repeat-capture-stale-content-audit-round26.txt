## Root cause in the code path; remediation status

The stale test parses one file, changes a payload float, and calls `compare_requests(path, manifest, None, path, manifest, None)`. `compare_requests()` opens the path twice with the manifest's pinned identity, then pairs the same record from the same manifest. Since the manifest's left and right `payload_sha256` values are identical, the equality fast path at `if a['payload_sha256'] == b['payload_sha256']: continue` skips reading either current payload. The final `fstat` checks compare each descriptor to the identity freshly returned by `open_private`, not to an independently revalidated content digest. This makes it possible to return equal for stale parsed evidence when the manifest's expected identity passes. The parser already records a full-stream digest in `manifest['file_sha256']`, but the comparator never checks it. More fundamentally, stat identity is metadata provenance; it cannot substitute for rechecking the bytes that the parsed metadata and payload hashes describe.

Commit `ae8e3d66` improves the round24 ledger bounds/CLI ingestion, path normalization, and independently transcribed producer fixture oracle. In the reviewed committed `compare_requests()` it still opens both files, skips on equal stored payload digests, and does not rehash the current whole file against `file_sha256`. The stale test body is unchanged and there are no deterministic stale-payload or stale-header tests under unchanged identity. Therefore that commit does **not** close the reported test failure. The requested content verification/test additions appear outstanding in this reviewed commit; this is a source finding, not an inference about any later uncommitted work.

## Minimal sufficient content check

Before trusting any equality-based payload skip, stream-hash each opened descriptor from offset zero through exactly its pinned size in bounded chunks and require the result to equal the corresponding manifest `file_sha256`. Reject early EOF, extra bytes, digest mismatch, or identity change during the hash. Then restore/use explicit `lseek` offsets for the record comparison and retain the current final identity checks. That check validates every parsed header and payload against the complete bytes that produced the manifest, including when the left/right payload digests happen to be equal. Do not hash by `Path.read_bytes()` or load a complete 128-MiB file into memory. Any returned comparison must remain structural comparison only; it cannot clear the original C numerical rejection or qualify lifecycle/adoption/performance.

Add deterministic tests that isolate content from metadata: parse a valid small capture; change a payload word, then separately change a header field; make identity reads appear unchanged/pinned for the comparison (for example, mock the identity helper only around the compare call); require `CaptureError` in both cases even though the old in-memory left/right payload digests are equal. Also keep an unmutated control to show that equal content still compares successfully. These falsify precisely the risk that stat checks alone passed without relying on filesystem timestamp behavior. A separate mutation-during-compare test may verify final identity checking, but is not a substitute for the static stale-header/payload cases.

The manifest stores a full-stream digest only after a complete parse, so both complete manifests should carry `file_sha256`; comparison should fail closed if that field is absent or malformed. The exact scope is the two capture descriptors supplied to `compare_requests`; verifying current bytes against parser-produced digests makes stored row metadata/payload hashes internally anchored to those bytes, assuming the in-process manifest itself is trusted. It does not authenticate a caller-forged manifest or establish producer freshness. O_EXCL creation, owner/controller ledger, orderly producer shutdown and close-error sentinel remain separate provenance requirements.
