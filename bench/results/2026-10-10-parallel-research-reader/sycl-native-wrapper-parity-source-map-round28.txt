## Actual SYCL source resolution and flags

`sycl/CMakeLists.txt` defines `strata_resolve()` and checks for a SYCL-side copy before falling back to the repository root. In the CPU library:

- `src/kernels/cpu/native_expert.cpp` resolves to the shared root source. H’s `native_gu_dispatch`/`native_down_dispatch` and wrapper calls are therefore the actual host resolver used by SYCL; no separate SYCL implementation shadows them.
- `src/kernels/cpu/iq_avx2.cpp` resolves to `sycl/src/kernels/cpu/iq_avx2.cpp`, whose wrapper includes the root IQ AVX2 implementation. Compile properties are attached to this SYCL-side translation unit, so linking the root-only target would not verify this compilation route.
- `q2_avx2.cpp`, `expert.cpp`, `iq_avx512.cpp`, and the other listed CPU sources resolve to the root copies where no SYCL override exists. The Q2 route is thus the shared CPU implementation.

A correct added target should be declared in `sycl/CMakeLists.txt` after `strata_kernels_cpu` is defined. Resolve the harness source there (it falls back to root `src/kernels/cpu/iq_avx2_parity.cpp`) and link it to **only** `strata_kernels_cpu` and its transitive CPU/ggml dependencies—not `strata_kernels`, `strata_engine`, or `native_expert_parity`. The library itself links `ggml-cpu` and `ggml-base` when `STRATA_NATIVE_EXPERTS=ON`. The SYCL directory globally applies `-fsycl` and `-fsycl` link options to C++ targets, so “CPU-only” here means no GPU engine/kernel library, no GPU API calls, and no GPU device run; the executable may still carry the toolchain’s SYCL host runtime linkage.

## Format-safe synthetic inputs and independent references

The generic parity harness already supplies the strongest reusable input contract:

- Its expert dimensions are `H=2560`, `FF=640`, matching `native_fmt()` on the model’s native expert rows.
- GU types under review are 18 (IQ3_XXS), 21 (IQ3_S), 22 (IQ2_S), and 23 (IQ4_XS). Down types are 20 (IQ4_NL) and 42 (Q2_0).
- `fill_blocks()` initializes deterministic encoded bytes per ggml block and writes a small positive finite FP16 scale in the block’s leading scale field. The remaining IQ/Q2 code bits are bounded bitfield/codebook indices. Use `native_fmt()`/ggml’s `ggml_type_size` and `ggml_row_size` instead of hand-computing row offsets; these shapes are whole blocks.
- `Acts` builds finite activation vectors and calls `native_quant_act`/`native_quant_h`, matching the actual ggml activation type for the selected weight format. The Q2_0 direct path additionally needs the production `act_quant_any()` result (`ActQ`), as the pool does. Do not pass arbitrary byte arrays as Q8 activations or inject `-128`: the earlier intrinsic audit found a distinct conditional `vpsignb(-128)` behavior, while normal native finite-input quantizers cap the signed values at ± 127.

The wrapper test must exercise these actual paths (not only direct variant helpers):

- For each GU format 18/21/22/23 and NT 1–8, call `native_gu_rows()` from the linked SYCL CPU library. An independent expected result can use `ggml_get_type_traits_cpu(type)->vec_dot` with the same quantized Q8_K activation for gate and up, then apply the fallback’s SiLU expression `(g / (1+exp(-g))) * u`. Keep the established numerical tolerance for the optimized multi-token path, and compare H against T bitwise for the same tuple/settings.
- For Down type 20 and NT 1–8, call `native_down_rows()` and compare to ggml CPU `vec_dot` using the same produced activation.
- For Down type 42 and NT 1–8, call the actual pool-level direct `q2_rows_any()` with production `ActQ` activations; `native_down_rows(type42)` is not the engine’s Q2 route. The existing parity source has an independent double reference from Q2_0 block scale/code values and `ActQ.scale/q`; retain its numerical tolerance and add H/T wrapper-output comparison.

The current root `iq_avx2_parity.cpp` already validates the raw IQ AVX2 variants and the IQ4_NL/Q2 row implementations at NT1–8, but it only calls `native_gu_rows()` in the `check_engine_width()` helper when the effective threshold is 1. It does not call the production Down20 wrapper over widths, nor does its ordinary CPU parity path exercise Q2 through `q2_rows_any()`. A new SYCL-specific mode should add the production-wrapper calls/hash output rather than treating raw-kernel parity as resolver parity. The resolver is the system under test: compare H’s actual outputs with the frozen T build under separately launched environment profiles; do not write a parallel copy of the resolver predicates as the expected oracle.

Use the real Ryzen 5 5600X’s detected AVX2/no-AVX512/no-AVX-VNNI capabilities. Test NT1–8 and the already identified threshold/settings boundary cases in separate processes because the dispatch settings are function-local statics. Do not fake CPU feature bits or claim the AVX-512 resolver path was qualified. Histogram row/job totals remain a separate request-level integration gate because a tiny wrapper target does not instantiate the production pool’s routed jobs.
