## Whole-file content verification

`verify_manifest_file(fd, pinned, manifest)` now checks the size is an exact integer within the 128-MiB cap, seeks to offset zero, hashes the entire pinned size through `CHUNK_BYTES` reads, rejects early EOF, checks the descriptor identity against the open-time pinned stat, and compares the digest to `manifest['file_sha256']`. `compare_requests()` invokes this for both open descriptors **before** entering the record loop and before the equal-`payload_sha256` fast path. Since the reader's stream digest covers each header and payload in byte order, this closes the original stale-header and stale-payload shortcut for a completed, parser-produced manifest. It retains record-level rehashing when payload digests differ and the final stat-identity checks.

The new tests cover separate stale payload and stale header mutations, each with both same-path and separate-right-file compare arrangements. They make `file_identity()` return the previously pinned identity for matching dev/inode during comparison, so these cases specifically falsify digest verification independently of timestamp behavior. The existing stale-manifest case remains as an ordinary filesystem test. Together with the root-reported five stale-content passes in v2, this is the right focused CPU falsification; commit 4a's tests still need actual execution.

The check is intentionally bounded but costs one full streaming pass over each capture per comparison. For two approximately 133.5-MB owned capture files, a pair check reads both complete files (about 267 MB total), including unexamined control intervals, because each manifest digest covers its complete stream. Each file remains within the 128-MiB cap and the check does not materialize payloads in memory. It is a useful correctness cost for the exact stale-byte question; it is not timing evidence for a future model run.

## Ledger contract and test correction

The v2 case that called a deeply nested JSON array “malformed” was a bad test premise: such an array is valid JSON. The fixed reader now decodes with a duplicate-object-key hook and requires exactly five GEN interval objects, then validates their order, contiguity, bounds and full file extent. A deeply nested non-ledger fails schema validation even if JSON decoding itself succeeds. A duplicate key is rejected explicitly. `read_ledger()` remains descriptor-pinned and private, reads at most 64 KiB plus one byte, and checks identity/length after reading. The mutation fixture now uses `utime()` on its private file to guarantee an observed timestamp change, and its report correctly narrows the claim to rejection of an observed identity change.

This is the precise trust boundary: the ledger is trusted only as a private, closed controller artifact after the producer has exited orderly; the reader detects a change observed by its pinned metadata check and requires the exact schema. Neither that check nor the whole-file digest makes a concurrently hostile writer impossible. The whole-file check authenticates current bytes against the parser-produced digest at the time of its pass; a writer changing bytes after that pass is outside the stated closed-producer workflow. An immutable/sealed-file or locking design would be needed for a hostile-writer guarantee. Do not describe the metadata mutation case as proof that every same-size concurrent write is detected.

The reader now explicitly constrains paths to text strings and rejects empty/root paths; the added bytes-path case exercises that API contract. It pins the wire schema separately by requiring `repeat_capture.hpp` SHA-256 `1db25fde8987a4f778d9cba2a5dfdc811dc4f0e36778b9e6b34a779fdc7bd509` in the CPU fixture setup.
