# R179 — Existing actual-kernel event seam for bounded SYCL profiling

Date: 2026-10-12 (Asia/Tokyo). Read-only source/report review plus primary-source web check. Only this report was written. No source edits, imports, AST work, tests, builds, profiler/runtime/model/GPU/process queries, Git operations, cleanup or subagents.

## Decision

The `finish(stream, event, label)` seam receives the actual `sycl::event` returned by the kernel submission, so a fixed-capacity host collector could retain copies of selected actual events without adding per-expert marker or barrier submissions. However, **the current production queue cannot provide profiling timestamps for those events**: Runtime constructs plain in-order compute/transfer queues without `sycl::property::queue::enable_profiling`; SYCL rejects `get_profiling_info` on an ordinary event from such a queue. Holding and querying the existing event therefore does not meet the requested collector contract on current configuration.

If exact kernel event durations are still needed, the smallest viable bounded experiment is a diagnostic-only Runtime queue construction mode with `enable_profiling`, selected before queue construction, then a preallocated fixed-capacity collector that copies only chosen events at `finish(stream,event,label)` while a finite chunk/layer capture window is active. It adds no per-kernel marker/barrier command and no extra wait. It still changes queue profiling mode and adds host event-handle copies, so it is not assumed low-overhead until paired measurement. The ordinary mode must construct the same in-order queues and execute the same command/wait sequence as today.

Do not enable `enable_profiling` unconditionally or query a direct event on the current queue and treat an exception as data. Do not substitute profile-tag marker timing, a queue-wide timer, or per-expert marker events for actual event durations. Existing profiling-tag / event-timing implementations are reusable for queue-boundary timelines but do not provide this actual-kernel-event collector under current queue properties.

## Profiling API blocker and event meaning

Khronos SYCL reference documents that an event is returned by command-group submission and is copyable with common reference semantics. It also documents that `get_profiling_info` may block if command completion has not happened, and throws `sycl::errc::invalid` if the submitting queue was not constructed with `enable_profiling`. Queue property documentation says this property requires profiling information to be captured and rejects construction when `aspect::queue_profiling` is unavailable. Intel's optimization guide demonstrates event `command_start` / `command_end` timing on a profiling-enabled queue and distinguishes host submission, device start and device completion. [SYCL event reference](https://github.khronos.org/SYCL_Reference/iface/event.html), [SYCL queue reference](https://github.khronos.org/SYCL_Reference/iface/queue.html), [Intel oneAPI GPU kernel launch guide](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2024-1/kernel-launch.html).

The pinned source LLVM implementation enforces the same precondition in `event_impl::checkProfilingPreconditions()`: unless the event is a profiling-tag event or its associated queue enabled profiling, the getter throws `invalid`. This confirms why a retained current event is not presently queryable. The oneAPI profiling-tag extension is a different contract: on an in-order queue it returns a lightweight tag event with submit/start/end times for a queue boundary. It does not make an ordinary kernel event from the same non-profiling queue queryable. [Intel LLVM profiling-tag extension](https://github.com/intel/llvm/blob/sycl/sycl/doc/extensions/experimental/sycl_ext_oneapi_profiling_tag.asciidoc).

With an eligible profiling queue, retain raw `command_submit`, `command_start` and `command_end` for each selected actual event after its existing natural drain. `command_end - command_start` is inclusive duration of that command action. `command_start - command_submit` can be reported as submit-to-start queue/launch delay only after the source/toolchain path validates these timestamps as ordered and same-domain; label it as an event-level delay. Do not compare raw event timestamps to `steady_clock`. The SYCL spec says same-backend event values share an implementation-defined timebase; they are not host wall timestamps.

For multiple selected events, report each duration and, if all selected event starts/ends share the same backend domain, the selected-set envelope `max(end)-min(start)`. The sum of per-event durations is inclusive and may exceed makespan when commands on independent queues overlap. The selected-set envelope excludes unselected work and cannot establish the full request's or hidden physical critical path. Neither event duration nor envelope measures physical PCIe transfer bytes, DRAM traffic or link utilization.

## Smallest bounded diagnostic shape, conditional on queue qualification

1. Read the diagnostic enable flag once before Runtime queue creation. When off, preserve today's queue property list, event calls, queue commands, explicit waits, math, output and control flow at every kernel site. When on, construct the same owned in-order queue with `enable_profiling` only if the device advertises `aspect::queue_profiling`; otherwise report `PROFILE_UNAVAILABLE` before a timed request. This property is global to the queue's submitted commands even though the collector retains only a chosen subset.
2. Give one finite named capture window a fixed set of allowed labels/layers or a fixed `K` event slots, plus metadata (label, layer/chunk ordinal, backend/queue identity). Do not allocate/grow a vector in the kernel dispatch path. `finish(stream,event,label)` copies the actual event into the next available slot only while the capture window is open. Stop at the predetermined endpoint; overflow sets `capture_overflow=1` and invalidates completeness rather than silently dropping an event. Do not add start/end markers or per-expert marker events.
3. Read timestamps only after a naturally required successful chunk/request drain. Do not add `queue.wait`, `event.wait`, a barrier, polling, or synchronization just to make timestamps available. Query each selected retained event once for each raw field needed, then release its retained copy after the report is durable. Keep event-query time outside the measured request wall endpoint. No new event/timestamp work is allowed when the flag is absent.
4. Query failures are profiling failures, not successful zeroes and not queue completion. Preserve the exact query status/error and omit a normal timing record for the affected window. Do not retry the kernel, alter fallback, or reuse state. A failed existing completion boundary keeps the existing fail-stop/cleanup path; do not query events or release queue-owned state after unknown completion. Check asynchronous error handling at the existing drain boundary. Collection failure after confirmed drain must not rewrite successful model correctness/normal-close status.
5. Suppress direct event queries during graph capture/replay paths without replay-owned actual event handles, and mark skipped coverage. Keep captures strictly bounded in duration and event count; persist compact per-event rows/raw timestamps and summary only. Do not retain full profiling timelines after the attribution question closes, per `docs/ARTIFACT_RETENTION.md`.

The collector is not reusable unchanged from the old diagnostic worktree. Its `SyclServiceOps` / `ExpertServiceLedger` retains real copy events and reads `command_submit/start/end` only after completion, but it first admits a queue via `has_property<enable_profiling>() && aspect::queue_profiling`; those are copy/transfer lanes on a profiling-enabled queue, not the current direct kernel events on Strata's non-profiling compute queue. The old diagnostic's prefix also adds queue profiling and transfer-specific event collection. Reuse the delayed-query/error-boundary pattern, not its queue admission or scope as proof that the present kernel event is queryable. The older prefill phase timer emits explicit queue markers and therefore does not satisfy a no-added-marker design.

## Host fixture discriminators and measurement gate

Before device/model use, a host-only fixture should distinguish the API and accounting contract with an injected event/profile facade:

- Collection disabled: no event copies, timestamp calls, profile-specific output, queue-property change or command/wait additions; identical accounting/output defaults.
- Enabled on a fixture queue marked non-profiling or without the capability: admission fails as `PROFILE_UNAVAILABLE`, no timestamp query and no normal timing summary.
- Bounded capture at exactly `K` selected events: copies and timestamps correspond to the same original event identity and label; no synthesized event ID is accepted. A `K+1` event produces overflow/incomplete status and no apparently complete summary.
- Event query throws before any timestamp, on a middle field, or after successful completion: retain field-specific failure and do not convert it to zero, claim completion failure, retry work or change result status.
- Existing queue drain failure / async error: no timestamp extraction, no normal report, preserve fail-stop and release ownership.
- Graph-capture active: explicit skipped coverage and zero profile-query attempts.
- Boundary fixture: raw timestamps and per-event inclusive durations; overlapping events show sum can exceed the selected-set envelope. No host-clock subtraction or PCIe interpretation.

For owner-run qualification, use the same binary recipe, model, prompt/context/chunk settings, warm state and output/correctness/fault gates in counterbalanced observer-off and bounded-observer-on arms. Keep individual samples and request wall/throughput separate from event durations. Compare the observer-on change against matched observer-off repeat variation; if the event-enabled mode changes physical decode beyond the control's noise band, treat the event numbers as diagnostic-only and do not infer quiet throughput or critical-path shares from them. Capture only the named bounded sample; stop and preserve incomplete status on slot overflow, profiling-query errors or failed normal-close/fault checks. Do not invent a fixed acceptable overhead percentage without the predeclared workload's measured paired variation.

## Existing source/report reuse and limits

The prior committed reports R106 (quiet GDN event-profile clock/error contract), R178 (existing-counter seam) and the old `diag-sycl-prefill-service-events-20261010` tree were read. R106 already requires a preexisting profiling-enabled queue, query after the existing successful wait, event and host clocks remain separate, and profile-query failure cannot become a successful timing or completion failure. R178 covers reuse of existing counters and unrelated CPU cohort evidence; it does not make current kernel events profile-enabled. Existing old-tree copy service receipts and profiling-tag integrations do not identify a current actual-kernel-event collector. No existing implementation reviewed satisfies this exact seam and queue-property constraint.

Main supplied the current completed diagnostic status: 64K plus 32K model diagnostics passed normal quit/full-output/runtime/fault gates; prior pinned-direct 32K host-issuer baseline was 97,728 events, logical 199,990,579,200 B, submit 9.331112483 s, wait 0, prompt 93.4338 s, with observer-off 94.2567 s. These are owner-provided context, not measurements performed or reclassified by this review. The prior tag-timed 146.7 s is a separate observer-on result and cannot be subtracted into exclusive critical path.

No GPU outcome, driver-specific event timestamp precision, queue-profile overhead, actual throughput effect, event query reliability for the supplied binary, or graph replay collection was tested. Current-source capability and query behavior need qualification by Main before any implementation claim. OneAPI guide distinctions between device action time and host/launch scheduling are primary-author implementation guidance; they do not establish a hardware service rate or guarantee exact timer overhead.
