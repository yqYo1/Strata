## Exact `Prefill::bytes_needed` arithmetic

`Alloc::take` in `src/prefill/prefill.cpp` charges each take as `A(p)=ceil((p+256)/256)*256`, including 256 bytes of per-take alignment guard. `bytes_needed()` follows `init()`'s device carve sequence and adds a fixed 8 MiB capacity margin. With the retained recipe's compact no-MMQ fallback, `K=10`, `N=2560`, `HC=4`, `D=10240`, `LR=320`, `C=10240`, `ZV=6144`, `HV=48`, `E=512`, group 16, max context 262144 and selection/attention batches 256/32, every T-row payload in this table is 256-byte aligned. The current shared region uses `max(GDN,QSA,MoE)`; the three views overlap by phase and must not be added together.

The row-shaped takes outside that shared region sum exactly to `155,568*T` bytes: `emb, R, xn, xn16, lo, lo16, gated, inj, mixed, mixed_bf, mixed_h, bo, steps_dev, ple_emb`. The fixed takes outside it sum to `232,830,464` bytes, including 32 Mi FP16 GEMM scratch, FP16 group-16 GU/D buffers, both expert-bound tables (compact path), PLE norm, and the fixed 8 MiB `bytes_needed` margin. The 16 device expert-stream slots add `16*A(MAXBLOB())` bytes; this is fixed across these three T values. Thus the full exact source request is:

    P(T) = 155,568*T + max(GDN(T), QSA(T), compact_MoE(T))
           + 232,830,464 + 16*A(MAXBLOB()) bytes.

Therefore each 4096-row increase adds `637,206,528` bytes of other row buffers plus `590,348,288` bytes of GDN shared-region demand: exactly `1,227,554,816` bytes (`1,171.0 MiB`) for 8192→12288 and again for 12288→16384. The total 8192→16384 request grows by `2,455,109,632` bytes (`2,342.0 MiB`). These deltas include every T-dependent take inside `bytes_needed`, not only the largest scratch set. They exclude the fixed ring, so the value of `MAXBLOB()` cancels exactly. The fixed 8 MiB margin also cancels in deltas.

`bytes_needed()` is a counted carve size, not a complete runtime VRAM reservation. `init()` adds a separately allocated `tok_dev` of `4*T` bytes, plus independently allocated resources described below. For this owned-buffer recipe, the 8 MiB alignment margin is not itself carved or allocated; it is headroom in `bytes_needed()`'s capacity answer. The GPU delta from `tok_dev` is 16,384 bytes per 4096 rows. Including it, the known device request deltas become 1,227,571,200 bytes (8192→12288), 2,455,142,400 bytes (8192→16384), before any runtime allocator/page rounding. With an 8,192 baseline, 714 MiB ready plus the entire 281 MiB cache is an optimistic maximum of 995 MiB = 1,043,333,120 bytes. Under that supplied free-space bound, 12288 remains short by at least **184,238,080 bytes** (about 176 MiB), and 16384 by at least **1,411,809,280 bytes** (about 1,347 MiB). These are optimistic arithmetic deficits, not measured allocator results; fragmentation, separately growing owners and allocator rounding can only change the actual admission threshold.

For completeness, if compact scratch had not been effective, MoE would add `103,680*T` to the compact MoE set (the route-sized Xs/GU/Hh difference); its values would be 1,937,018,368 / 2,905,525,760 / 3,874,033,152 bytes, dominating the region. The full source-ledger model is therefore `fixed session + model/output/hit/MTP/graph owners + P(T) + tok_dev(T)`, with the owner-specific formulas above. It is not valid to subtract the prefill phase's `P(T)` from decode usage and call the difference free: session, main KV, MTP state/weights, hit buffers, output buffers and any live MTP graph consumer remain. `Prefill::release()` drains the compute/copy streams, cancels and joins the stager, destroys events and frees only its owned allocations (`prefill.cpp:539-560`). It is teardown/reset behavior; no validated reusable phase-retire API exists. Retiring Prefill after the last chunk returns Prefill-owned bytes for decode, but cannot help admit that chunk in the first place.

## Capacity decision and next source boundary

The measured reclaimable cache upper bound plus supplied ready free still leaves a source-derived 12288 shortage of 184,238,080 bytes after accounting for the additional `tok_dev`. The existing GDN row-bounded idea, if implemented with the R155/162 seam and B=512, would shrink the T12288 region only from GDN 1,771,046,912 B to max(QSA, compact-MoE)=1,634,831,104 B: 136,215,808 B saved. It would leave 48,022,272 B short even before runtime headroom. This also shows why the compact T-row MoE result cannot be retold as the missing 12288 capacity answer. No retained source or allocation receipt identifies another safely reclaimable, separately owned buffer of at least that remaining amount. The exact evidence-supported deficit remains 184,238,080 B against the optimistic full-cache release; no minimal source change can be claimed to make 12288 fit on current evidence. Freeing additional MTP state, hit/output storage, or captured graphs is not an established option and would change decode/speculation or violate consumers' lifetimes.

Do not lower `max_context=262144`, alter INT8 KV/resident-cell policy, remove prefix state, or infer endpoint execution from this arithmetic. Keep the full-context endpoint overflow behavior and pre-consumption hard refusal: a future admission must compare complete `bytes_needed` plus init's separately allocated buffers, all concurrently live owners, allocator headroom and target device limits, and fail before consuming the prompt if it cannot allocate. No T12288/16384 fit or quality result is claimed. The 353.577 tokens/s six-sample T8192 report remains the only applicable throughput summary; this ledger makes no performance projection.
