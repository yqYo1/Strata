# R178 — Existing-counter serve seam and minimum route evidence

Date: 2026-10-12 (Asia/Tokyo). Read-only source/report review; primary-source web checks. This file is the only new artifact. No source edits, imports, AST work, tests, builds, runtime/model/GPU/process queries, Git operations, cleanup, or parallel agents.

## Decision

Serve can report per-request deltas for the already-existing native CPU-pool phase clocks and packed-blob-byte counter without adding per-task timers or changing scheduling. A prior code-only implementation already does this on the W0141 source line; Main should review and reuse that implementation pattern, not repeat the counter instrumentation. It does not provide the second discriminator needed to choose a kernel or scheduler optimization: exact per-request CPU route/format/NT/expert-count cohorts. Current retained receipts and output expose only aggregate per-request misses/entries/hits/PCIe and static model format census, not their joint histogram.

There is no supported basis here to select a new AVX2 kernel, worker policy, cache, or memory-layout optimization. The next useful source change, if Main needs route attribution before its next controlled decode comparison, is a small bounded request-local histogram at the existing completed-job construction point, then one request-end summary. Keep the physical decode result as the optimization outcome. The existing phase clocks include pool scheduling and barriers; they are neither worker CPU service nor a critical-path decomposition.

## Minimum bounded route addition and contracts

At the existing `expert_source.cpp` job-construction loop, each completed `ExpertJobMulti` already has its exact `nt`, and the dispatcher knows the layer and `lay.fmt[layer]` pair. Aggregate before dispatch into request-owned integer bins keyed by layer and NT: distinct CPU jobs per NT, plus CPU token rows per NT. Layer maps directly to the static `(GU type, Down type)` pair, so request-end output can include pair, layer, NT, jobs and rows without storing per-expert identity. Retain the existing aggregate total fields for reconciliation: sum of jobs should match `multi_misses`; sum of rows should match `multi_entries` for the same request/scope. Keep route class (native/Q2_0/generic, CPU vs VRAM/PCIe/helper) explicit where relevant; a CPU job histogram alone does not describe GPU/remote shares.

The allocation should be fixed before the request starts or reused from the dispatcher, bounded by model layer count and `MAXT + 1`; no vector growth, strings or per-task records in the hot dispatch loop. The current source's model metadata supplies `n_layers`, while NT has the hard `MAXT` bound. The design has `O(n_layers * MAXT)` integer bins; use checked/saturating increments with an overflow flag, preserve integer counts, and emit that flag. Do not infer a request total bound from the 96-job pool batch cap: it batches a potentially larger set. The caller invokes pool work synchronously and `run_phase` waits for workers to finish; sample/emit only after every decode window callback and the final successful `ver.wait_commit`, as the existing request output does. Preserve one record per request, explicit zero-window output, failure/cancel status, window denominator, and pool/stage identity. If a path can own more than one independent pool, emit per-pool scope or explicitly sum only after snapshotting all of them.

The existing `int64_t multi_bytes` lifetime accumulator has no source overflow guard, and request delta subtraction is unsafe if it wraps; do not present it as overflow-safe. A review should keep the current signed counter limitation visible or use a checked unsigned/request-local delta in a future implementation. `double` phase totals can lose precision at large lifetime values. Counter collection should remain diagnostic-gated where possible, and the output path should format a fixed bounded number of layer/NT bins and flush once per request, not one line per expert/task. Existing early error returns do not reach the successful request-end report; represent that as missing/failed coverage, never as zero work.

This route histogram counts scheduled CPU-owned jobs/rows, not how many tasks each worker claimed, worker CPU time, memory-controller traffic, or the overlap/tail relation with device work. Do not add per-task timers until the aggregate shows a specific cohort and physical decode correlation worth investigating. If that later step is needed, R284 is already the named bounded worker-clock design; it must be separately calibrated against the clocks-off physical decode result.

## Remaining hardware/service gap and conditional candidate

`multi_bytes` counts logical expert blob extent submitted. It cannot yield DRAM transactions, cache hits, bandwidth, or PCIe reads, and phase sums cannot yield worker service or an exclusive CPU critical path. Intel PCM is not suitable on the AMD 5600X: its official project describes Intel processor coverage. AMD uProf is the relevant primary lead: its guide says system metrics can use Core, L3, Data Fabric and UMC counters and documents memory-bandwidth collection. Availability and the exact events on this machine still need host qualification; no hardware query was made. [Intel PCM scope](https://github.com/intel/pcm), [AMD uProf overview](https://docs.amd.com/r/en-US/57368-uProf-user-guide/Overview), [AMD uProf memory collection examples](https://docs.amd.com/r/en-US/57368-uProf-user-guide/Linux-and-FreeBSD).

For implementation comparison, llama.cpp's upstream CPU pool and quantized-dot source demonstrate an established CPU threadpool/quantized row-kernel architecture, but its row/dot contract does not identify an uncovered custom IQ format in this engine. vLLM's official CPU backend/kernel docs and SGLang's EP guide cover different expert formats, CPU backends, or multi-device EP/all-to-all; no matching 5600X packed-IQ CPU-offload service result or directly transferable kernel was found. These are architecture references only, not candidate speed claims. [llama.cpp CPU pool](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cpu/ggml-cpu.c), [llama.cpp quantized CPU kernels](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cpu/arch/x86/quants.c), [vLLM MoE kernel features](https://github.com/vllm-project/vllm/blob/main/docs/design/moe_kernel_features.md), [SGLang expert parallelism](https://github.com/sgl-project/sglang/blob/main/docs/docs/advanced_features/expert_parallelism.mdx).

One conditional layout candidate is to reorder/pack the active CPU expert-blob region by measured decode frequency and physical-core access pattern, but only if the new route histogram shows a stable hot subset and AMD hardware counters show that repeated cold-weight fetches reach DRAM while worker service correlates with physical decode tail. The project already keeps frequently used expert blobs resident in system RAM and builds per-layer CPU job lists, so a repack has no demonstrated gain today. First compare the existing resident layout with an offline reordered layout on the exact model, preserve expert IDs/format parity, and keep the physical decode/context/correctness gates. If bandwidth is not near a measured sustainable limit, or CPU phase completion precedes the decode tail, stop this candidate and investigate another measured component. No candidate is selected by this report.
