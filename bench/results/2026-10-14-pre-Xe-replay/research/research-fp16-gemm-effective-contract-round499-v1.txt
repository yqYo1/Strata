# R499 — 旧・現FP16 GEMMの実効契約

日付: 2026-10-14 JST。読み取り専用のソース・ビルド記録・公式oneMKL文書調査。GPU、build/test、profiler、cleanup、Git変更は行っていない。Mainの進行中ベンチにも触れていない。禁止指定の `prefill-gemm-only-contract-root-v1/record.json` は読んでいない。

## 結論

旧1eb89482の選択済みFP16経路と現在の `src/prefill/sycl/gemm.cpp` は、同じ引数形状が有効な限り、GEMMの数学的な契約が一致する。旧column-major呼び出しの `N,T,K,trans,nontrans` は、現row-major呼び出しの `T,N,K,nontrans,trans` と同じ `Y[T,N] = X[T,K] * W[N,K]^T` を表し、α=1、β、半精度入力、FP32型の出力、`ld` による出力行strideも一致する。旧計算mode `mm_default` はDPCT adapter上で oneMKL `compute_mode::unset` に解決される。現呼び出しもoneMKL既定 `unset`。両方ともoneMKL 2026.1の動的SYCL BLASを使い、旧リンク記録は `libmkl_sycl_blas.so.6` と逐次threadingライブラリを示す。

従って、transpose/row-majorの書き換えで数学的に別の結果を計算している証拠はない。一方、oneMKLは内部アルゴリズムや加算順序を公開契約にしていないため、同じ oneMKL versionでもrow-majorとcolumn-major経由のshape dispatch・kernel選択・結果の末尾bitが同一とは言えない。FP16入力/FP32出力というAPI型組は出力とscalar型を確定するが、それだけで内部accumulationが厳密にFP32か、どのGPU kernelを選ぶかを保証しない。実効accumulationの契約差は確認できず、実行時kernel dispatch差は未計測である。

## 選択された経路と呼び出し

- 旧ビルドreceipt `main-pre-Xe-1eb-build-root-v2/record.json` はsource revision `1eb89482a4afd20277ae0405780ed4f8eb98eb20`、ggml `3cf03257`、oneAPI compiler/MKL `2026.1`、`-O3 -std=c++20 -fsycl -fsycl-default-sub-group-size=32 -fsycl-device-code-split=per_kernel -fp-model=precise -qmkl=sequential` を記録する。compile databaseに `sycl/src/prefill/gemm.dp.cpp` と `sycl/src/prefill/prefill.cpp` がある。旧CMakeの実targetはこれらを選び、MMQ実装/stubは非実装として `mmq::built()==false`。R495が環境変数・dispatchとともに訂正した通り、実測経路はMMQでなくFP16 fallback。
- 旧 `prefill.cpp` はMoEのIQ weightsを `iq_dequant_gu_f16` / `iq_dequant_f16` でFP16 scratchへ展開し、compact設定ではtoken rowsを `Xs`/`Hh`へgatherする。その後expertごとに `Gemm::f16(Xs, dq_gu, GU, ne,1280,N)` と `Gemm::f16(Hh, dq_d, Dm+o0*N, ne,N,640)` を呼ぶ。これは旧測定でdenseと呼んだ全行FP16 GEMMの経路で、GU/DownのMoE呼び出しでも使われる。旧native `Gemm::native` もIQ weightsをFP16 scratchへ小分けにdequantして `f16` を呼ぶ。呼び出し側で標準INT8 MMQを選択していないことが根拠。
- 現主の `mmq_plan()` は `STRATA_PREFILL_MMQ=0` でMMQを無効にし、expertごとの同じFP16 dequant/gather/`f16` GU/Down呼び出しへ入る。現 `native()` は出力列をscratch単位で分割し `f16` を呼び、`Y+r` とldを保つ。今回の対象はこのoneMKL GEMM選択であり、MMQ・fused MoEの性能やCPU expert経路の評価ではない。
- 旧ビルドのsource resolverは `sycl/src`をrootより優先し、旧の選択sourceは `.tools/pre-xe-1eb-source-v1/sycl/src/prefill/gemm.dp.cpp`。現primary pinは `src/prefill/sycl/gemm.cpp` SHA256 `0fe1904787462a4156185bc08b2076e047f9cf51d9517ede4c8f482fa76c5410`、現backend pinは `cmake/sycl_backend.cmake` SHA256 `562a394fd5ad9357faa1509ae2d26aaba8d6b9f5ab6671120bf111d8a3ec9a51`。
- 比較対象の速度は旧fork 1ebの32K FP16 dequant+oneMKL測定中央値449.674 t/s（pooled 449.698）と現root-native 118.x t/s。ただしそれぞれのchunk、MTP/split、実入力なども異なり、単独GEMMの原因をこの差から推定しない。

## 引数を展開した同値性

| 意味 | 旧DPCT/oneMKL column-major | 現 oneMKL row-major |
| --- | --- | --- |
| 論理出力 | `Y[T,N]` | `Y[T,N]` |
| GEMMの次元 | `m=N,n=T,k=K` | `m=T,n=N,k=K` |
| 左入力 | `W[N,K]`をcolumn-major viewでtranspose、`lda=K` | `X[T,K]` nontrans、`lda=K` |
| 右入力 | `X[T,K]`をcolumn-major `K x T` nontrans、`ldb=K` | `W[N,K]` row-majorをtranspose、`ldb=K` |
| 出力 | 同じY先頭、column-major `N x T` view、`ldc=ld` | 同じY先頭、row-major `T x N`、`ldc=ld` |
| scalar・型 | α=1.0f、β caller値、half×half→float（またはbf16×bf16→float） | α=1.0f、β caller値、half×half→float（bf16 methodも同形） |

双方とも各有効要素について `Y[t,n] = 1 * sum_k(X[t,k]*W[n,k]) + beta*Y[t,n]`。`ld`は出力のtoken-row strideで、列数Nより大きい時のpadding領域はBLASの対象外。旧f16は`ld<=0`をNに置き換えるだけで、現は`ld<=0`をNにし、`ld<N`を拒否する。実call sitesでは既定ld=Nまたはそれ以上なのでこの入力検証差は通常経路の契約差ではない。現は範囲/overflowとnon-null/spanを追加検証する。β=0ではoneMKL仕様上Cは初期化不要、β≠0では既存Cが入力。MoEの上記callはβ=0。

行列tailはK方向の端数を含めてBLASのK値だけを読む。MoEのactivationとdequant weightは各行K要素が連続し、X/W strideはK。出力は `T`行について各 `N`列だけ書き、ld paddingは保持する。`native()`がNを出力列tileに分けた時も、旧・現とも出力baseを列rへずらし同じldを渡す。BLAS GEMM自体に行列tailを過読する規定は見つからない。oneMKLは通常のGEMM呼び出しに対する内部vector loadの範囲を公開していないので、padding/pointer boundaryの完全な物理load証明はAPI記述だけではできない。

## 数値mode、descriptor、scalar pointer、dispatch

旧 `Gemm::init_external/init` はDPCT descriptorを作成してqueueと `math_mode::mm_default` を設定する。1ebの `dpct/blas_utils.hpp` では `mm_default` は `deduce_compute_mode(...)=unset`。f16 GEMMに渡す `compute_type::f32` もこのadapterでは `compute_mode::standard` でなく `unset` に落ちる（f32 enumで明示分岐がなく、tf32指定でもない）。adapterはalpha/betaのホストfloat pointerを `get_value()` して値にし、oneMKL scalar-by-value overloadに渡す。よって旧はCUDA/cuBLASのdevice/host pointer-mode stateをoneMKLへ移植した状態ではない。現もoneMKLのUSM APIへfloat alpha/beta値を直接渡し、compute mode omitted＝`unset`、scalar pointer mode/descriptorsは持たない。現在のコードで特別なmath-mode、pointer-mode、fixed workspaceを適用している証拠はない。oneMKLの `MKL_BLAS_COMPUTE_MODE` 環境変数は未記録。defaultのままならalternate modeは有効でないという公式説明だが、今回の測定プロセスの実環境状態はreceiptに値がないので断定できない。

FP32出力の型表記から、内部積和がどの精度・順序かを推定しない。旧DPCT `f32`は名前に反して`unset`へ写る。現の`unset`も同じmode指定である。公開oneMKL資料は標準precisionとalternate modesの選択を説明するが、Arc B570の2026.1実装がFP16×FP16→FP32をどの命令/accumulatorで行うか、row/column interface間で同じkernelへ正規化するかは公開契約でなく、本調査では観測していない。

oneMKL 2026.1自体は旧/現で同じ。legacy sourceのcolumn-major interfaceから現在のrow-major interfaceへ変わったため、同じ行列計算でもライブラリ内部がtranspose対称性をどこまで正規化し、同じalgorithm/dispatchへ落とすかは非公開。shapeごとの選択kernel差はこの比較で残る最も具体的な潜在速度要因。oneMKL verboseでmodeは記録できるが、必ずしも選択内部kernel名・全dispatch要因までは得られない。

## Compiler・group/subgroup・dense/MoEへの関係

旧compile databaseのGEMMとprefill TUは同じ `-O3 -fsycl -fsycl-default-sub-group-size=32 -fsycl-device-code-split=per_kernel -fp-model=precise -qmkl=sequential`。oneMKL dynamic librariesはruntime linkであり、これらTU-local flagsはoneMKL内部device binariesのcompile設定を変えない。現CMakeでは`strata_prefill`に `-fno-fast-math -ffp-contract=off`、`MKL_LINK=dynamic`, `MKL_THREADING=sequential`を指定し、runtime public flagsに `-fsycl-id-queries-range=size_t` を付ける。現primary build recordはこのrange flagが110 consumer全てに付くことを証明するが、提示されたreceiptはwatchdog/lifecycle build由来で、現ベンチbinaryの全compile command/oneMKL verbose dispatch証拠ではない。

旧と現の両方でoneMKL threadingはsequential、MKL動的BLASを使用。旧はTUへ`-qmkl=sequential`も伝搬。SYCL subgroup32と`per_kernel` device code splitは旧compiler/CMakeの全kernel TUへ適用された。現backendはグローバルsubgroup32/device splitを付けず、必要なSYCL kernelの多くがsource attribute等でsubgroupを指定する。これらはアプリ側のkernel生成/JIT/module負荷には関わるが、oneMKL libraryの外部GEMM kernelを直接compileし直す設定ではない。従ってoneMKL GEMM内のsubgroup変更原因と見なす根拠はない。

FP16 GEMM TU自体はBLAS呼び出し・event処理を行い、積のdevice kernelはoneMKL libraryが供給する。Compiler math flagsはライブラリ内の積和順序を制御しないが、周辺のSYCL dequant/gather/SwiGLUや他のdense/MoE計算の生成コードには影響し得る。現の`-fno-fast-math -ffp-contract=off`はFP16 GEMM wrapperを含むprefill targetに適用、旧の`-fp-model=precise`もprefill TUに適用なので、wrapperや同一TU内の周辺浮動小数演算に完全な旗一致はない。ただしMoE weightsをFP16へdequantした後のGEMMはoneMKLで共通実装・同じAPI型/modeであり、これらcompiler flagsだけから速度差または数値差を帰属できない。

Denseへの具体的適用は、prefillのBF16 weight projectionが旧 `Gemm::bf16` から同型のcurrent `Gemm::bf16`へ流れる点。形式はBF16×BF16→FP32で、同じtranspose algebra。旧・現のactivation処理、native weight dequant/routeや他のprojection実装は別途差があり、全denseの速度をこのFP16契約だけで説明しない。MoE FP16 fallbackは上記GU/DownのFP16×FP16→FP32を直接使うため、row/column internal dispatchの影響があれば多数expert GEMMへ積み重なる可能性はある。MMQを有効にした別設定ではそのMoE GEMMの呼び出し数・型自体が変わる。

## 未確定と一要因の候補

未確定は (1) oneMKL 2026.1 B570でrow-majorとcolumn-major callが選ぶ内部kernel/dispatch、(2) 実ベンチで`MKL_BLAS_COMPUTE_MODE`が未設定だったか、(3) `unset`の実効accumulation命令・順序、(4) 長いtailを持つ特定output stride/feature-splitで内部loadがどう実装されるか。最初の3項はコンパイルrecordや公開APIだけでは決まらない。現在/旧の1回ごとの実際のlibrary dispatch logは保存されたreceiptからは得られない。

**優先候補:** Mainの現在32K比較が完了した後、production sourceを変えずにisolated GEMM probeで同じoneMKL 2026.1・同じbinary/compiler flags・同じデバイスで、同一FP16 operand/output bufferについて (A) 現row-major `(T,N,K,NTRANS,TRANS)` と (B) 旧式column-major `(N,T,K,TRANS,NTRANS)` の一要因A/Bを行う。MoE実shape `(ne,1280,N)` / `(ne,N,640)`の実際の`ne`分布、padding/ld、β=0と必要ならβ=1を対象にし、correctness、GPU kernel時間とAPI/queue時間を分離して記録する。`MKL_VERBOSE=1`でmode情報も固定・保存する。ここでBがrepeatably fasterなら、現wrapperにlegacy column-major呼び出しだけを試験的に戻す単一差分が、旧速度回復を検討する根拠になる。dense BF16 shapesも同条件で別系列として確認する。優位差がなければGEMM orientation仮説は後順位にする。

この小probeは旧449.7 t/sの再現にも、GEMM全面置換の判断にもならない。1ebとcurrentには少なくともsource family、compiler flags、SYCL kernels、prefill scheduling/configuration差が同時にある。上記一要因を終えてもend-to-end benchmarkへ戻し、prefillとdecodeを別に評価する。
