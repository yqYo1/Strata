# FP16 MoE grouped GEMM runtime and quality review — R496

Date: 2026-10-14
Scope: read-only source and contract review; candidate only. No implementation, build, test, GPU, profiler, cleanup, or Git mutation was performed. The concurrent benchmark was left untouched.

## Finding

A grouped oneMKL GEMM experiment remains a plausible host-submission optimization, but the existing evidence is too narrow to accept or reject it on model quality. Keep the existing per-expert path as default. A future isolated candidate should compare the same active experts, shapes, inputs, stream ordering, and output layout, then pass a practical numerical and model-quality gate. Do not require bitwise FP32 output identity or identical generated text. The earlier group-of-four probe differed in FP32 output by at most 7.62939453e-6, with no nonfinite values; this is a small local delta, but it does not by itself establish end-to-end quality.

Current `src/prefill/sycl/gemm.cpp` submits one `oneapi::mkl::blas::row_major::gemm` per call with FP16 operands and float output. `finish(stream,event)` preserves asynchronous operation for an explicit stream; with a null stream it waits. The non-MMQ MoE expert path in `src/prefill/prefill.cpp` invokes this twice per expert (gate/up and down), on the same compute stream. A grouped API could reduce host/API submission overhead, but must preserve the stream dependencies and output offsets of both phases. Actual device-kernel fusion or speedup is not guaranteed by the grouped API contract. In the cited prior probe, four-expert Down grouping was about 2.85% faster than separate calls (0.477624 ms vs 0.491666 ms median); group-of-two cases were mostly slower. These are probe-specific timings, not model-wide evidence.

## oneMKL contract and caveats

Intel oneMKL 2026.0 documents a USM grouped `gemm_batch` interface with `group_count`, per-group `group_size`, per-group dimensions/leading dimensions/scalars and pointer arrays; the total batch count is the sum of group sizes. It returns a SYCL event and accepts dependencies. The regular GEMM reference documents half inputs with float output. See [gemm_batch](https://www.intel.com/content/www/us/en/docs/onemkl/developer-reference-dpcpp/2026-0/gemm-batch.html) and [gemm](https://www.intel.com/content/www/us/en/docs/onemkl/developer-reference-dpcpp/2026-0/gemm.html).

The public signature and output type do not promise a particular internal accumulation order or bitwise agreement with individual GEMMs. oneMKL's compute-mode and numerical-reproducibility material describes precision/reproducibility options and explains that BLAS results can differ with summation order; use only a mode explicitly documented and supported for the target device if a precision requirement is adopted. Do not infer FP32 accumulation solely from float output. See [compute modes](https://www.intel.com/content/www/us/en/docs/onemkl/developer-reference-dpcpp/2026-0/compute-modes.html) and [numerical reproducibility](https://www.intel.com/content/www/us/en/docs/onemkl/developer-reference-dpcpp/2026-0/numerical-reproducibility.html).

Keep host-side pointer arrays and all shape/scalar metadata alive and unchanged until the returned event completes. The API material establishes an asynchronous event/dependency contract, but does not clearly specify an earlier host-metadata consumption point; retaining metadata through completion is the conservative lifetime rule. Device input/output buffers must likewise remain valid through completion. Chain the returned event into subsequent work or preserve the current in-order stream semantics; do not host-wait after every expert merely to simplify lifetime.

The oneMKL 2025.1 known-limitations page states that recording oneMKL operations with SYCL Graph is unsupported. Treat a grouped call as graph-incompatible unless the exact deployed oneMKL version documents and verifies support: [known limitations](https://www.intel.com/content/www/us/en/docs/onemkl/developer-reference-dpcpp/2025-1/known-limitations.html). This matters if the call site is ever moved into a captured graph; no graph behavior should be inferred from ordinary stream execution.

## Quality gate for any future candidate

Replace the old bitwise equality gate with layered practical checks:

1. Preserve exact structural correctness: no NaN/Inf; correct active row ranges, expert ordering, output strides/offsets, beta behavior, and stream dependencies; run the existing memory/state/fault checks unchanged.
2. Compare individual and grouped results on real routed FP16 activations and weights, separately for gate/up and down, across representative expert row counts and batch/prefill shapes. Record absolute and scale-normalized RMS and percentile/max error, including near-zero outputs; report route/top-k changes where routing is in scope. The 7.63e-6 prior max is evidence only for that probe, not a universal tolerance.
3. Compare fixed prompt sets through the full model using logits/distribution deltas, top-1 flip rate and task-quality measures. Require no material quality regression under a declared evaluation budget; generated strings need not match exactly because tiny numerical changes can alter later token trajectories. Establish numerical limits from representative baseline variation and task needs rather than choosing an arbitrary tolerance from the old probe.
4. Measure end-to-end prefill latency and host submission cost on the same binary/configuration, across enough repetitions and expert-count/row-count regimes to detect regressions. Adopt only if the gain is repeatable and meaningful after metadata construction and event chaining costs. Keep per-expert fallback for shapes where grouping loses.

## External efficiency context (not SYCL performance evidence)

PyTorch's Triton MoE write-up explains the common motivation: grouped/persistent kernels can amortize launch overhead and improve utilization when many small expert GEMMs are present ([PyTorch](https://pytorch.org/blog/accelerating-moes-with-a-triton-persistent-cache-aware-grouped-gemm-kernel/)). NVIDIA reports grouped GEMM benefits for its CUDA/cuBLAS workloads ([NVIDIA](https://developer.nvidia.com/blog/introducing-grouped-gemm-apis-in-cublas-and-more-performance-updates/)). These support investigating host submission overhead, but neither establishes oneMKL/SYCL speedup or quality on this machine.

## Decision

No code change now. Retain per-expert GEMMs as production path; consider a guarded grouped candidate only after the revised practical quality gate and representative latency measurements pass. Exact-output identity is not required, but the current small probe alone is insufficient to claim negligible quality impact.
