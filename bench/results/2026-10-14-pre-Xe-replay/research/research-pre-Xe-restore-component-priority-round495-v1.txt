In the old binary, `mmq_plan()` therefore has `any=false` and `fallback=true`. The measured environment explicitly has `STRATA_PREFILL_COMPACT=2`, does not request old prompt XMX, and the fallback code enables `compact_prefill()` / `compact_hc_prefill()`. The MoE loop dequantizes each expert's native IQ block weights to FP16 with `iq_dequant_gu_f16` / `iq_dequant_f16`, gathers routed rows into compact scratch, then calls `m.gemm.f16()` for GU and Down. `Gemm::f16` dispatches through the migrated `dpct::blas::gemm` interface to oneMKL SYCL BLAS. The tracked `moe_mmq.dp.cpp` code is a dormant source candidate in this configured build, not the measured route. This is consistent with the old build record's comment that fused int8 kernels were not built.

The old mixed layout supplied for this review is 48 native expert layers: GU has 20 IQ2_S, 17 IQ3_XXS, 10 IQ3_S, and 1 IQ4_XS; Down has 39 IQ4_NL and 9 Q2_0. The old fallback supports those types by dequantizing them through the GGUF type routines before FP16 GEMM. The old 32K throughput receipt binds the executable and flags, but does not include a layer-by-layer dispatch log; the route conclusion above is from the exact selected CMake target and source guards, not per-layer profiler counters.

## Current root route for those formats

The accepted stock binary records source revision `5bf0742913584a343975ea7f792c97cefac488fe`; its selected current `prefill.cpp`, `moe_mmq.cpp`, `moe_fused.cpp`, and `native_mmvq.cpp` gates were checked alongside current HEAD and have the same route/format facts described here. Current `cmake/sycl_backend.cmake` compiles `src/prefill/sycl/moe_mmq.cpp` and `moe_fused.cpp`. `mmq::supported(type)` delegates to current `native_mmvq_supported(type)`. That switch includes all formats in the supplied inventory: IQ2_S (type 22), IQ3_XXS (18), IQ3_S (21), IQ4_XS (23), IQ4_NL (20), and the engine's Q2_0 encoding (42). Thus the current format-aware MMQ path can cover every listed GU and Down type. The build defines MMQ support; unless `STRATA_PREFILL_MMQ=0` is set, the current plan attempts MMQ for each layer whose pair fits the 1280-row GU / N-row Down shapes.

Current native fused support also covers this inventory in source: `gu_covered()` accepts 16, 17, 18, 21, 22, 23, including the four GU formats above; `d_covered()` accepts IQ4_NL type 20 and Q2_0 type 42. `fused::native_supported()` additionally requires `STRATA_PF_FUSED=1` (`requested()`), the native-fused enable not be disabled, and device support. `fused_ring()` requires every native layer's pair to be covered so it can safely choose the reduced fused workspace. With the supplied mix, there is no format-level reason to reject any of the 48 pairs. The current stock record summary does not preserve the launch's effective `STRATA_PF_FUSED` value, so classify the actual stock run's MMQ/fused path as unknown until its narrowly scoped launch receipt is checked. Under an absent `STRATA_PF_FUSED`, native fused is not requested and MMQ is the expected current route. Do not infer fused was active merely because CMake built it or `STRATA_PF_FUSED` is enabled by default for the non-native Q2_0-pack path.

This route evidence creates useful comparison arms: old FP16-dequant + MKL + compact, current native MMQ, and current native fused (opt-in). They are materially different expert implementations even though the current tree supports the same format coverage.

## Workspace and chunk feasibility

`compact=2` and current MMQ/fused do not simply stack. Old compact mode is admitted only when `mmq_plan().any` is false and there is no conflicting diagnostic/XMX path. Current source has no equivalent compact selector. Its MMQ plan requires full `T*K` routed rows (`K=10`) for float GU/H and Q8_1 activation buffers. Current fused uses a separate reduced buffer layout, but the `fused_layout()`/ring decision owns that layout and keeps a small-chunk MMQ tail; compact's one-row-per-token MoE scratch is not used alongside MMQ/fused.

Source formulas give a meaningful capacity warning for 8192-token chunks, but not a proof of failure. At `T=8192`, the old compact MoE GU/H buffers are approximately `T*(1280+640)*sizeof(float)`, about 60 MiB, plus compact FP16 X/H buffers of about 50 MiB. Current MMQ GU/H buffers are `T*10*(1280+640)*sizeof(float)`, about 600 MiB. Its activation quantization buffers are approximately 225 MiB for Q8_1 at width 2560 and 90 MiB at width 640, before route tables, padding, shared/QSA/GDN workspace and allocator slack. These source-derived figures put the current full MMQ expert workspace roughly 0.8 GiB above the old compact workspace at T=8192; they are not measured peak allocations. The current 128-slot cache is also 268.6 MiB versus the old run's 325 MiB, leaving about 56 MiB less nominal VRAM headroom. Fused mode can shrink buffers substantially if its complete route is eligible.

Therefore `--prefill 8192` must be treated as a request, and the actual accepted chunk and complete `bytes_needed`/init allocation are authoritative. Preflight each candidate's actual allocator plan using the same 262144 context, int8 KV, 32768 resident cells, 128-slot cache and staging settings. If current MMQ cannot admit 8192, record its maximum admitted actual chunk and do not compare it with the old 8192 result as a matched run. Check current fused separately: if every layer is covered and the reduced layout fits, it may make 8192 feasible. Never force a smaller workspace than the layer route needs; the current source has explicit guards against the too-small fused-layout failure mode.

## Restoration priority

1. **Recover active old compact workspace semantics as a current-source candidate, gated to the FP16 expert fallback.** This is the highest-priority memory/control restoration because it is a real old measured setting and plausibly explains why the old build admits an 8192 chunk. Preserve old allocation/counting parity: the sizing pass and carving pass must use the same sequence; compact rows must be bounded by T; use the full current MMQ buffers whenever any MMQ layer is selected; use the fused buffer contract when fused is selected. Make the chosen route visible in startup diagnostics. Do not port the old MMQ files as part of compact restoration.
2. **Benchmark current native MMQ against the old-equivalent fallback at a common admitted chunk.** In current root, `STRATA_PREFILL_MMQ=0` selects the dequant-FP16/GEMM fallback (confirm its actual current defaults); compare it with MMQ at identical 4096 chunks first, same full context/KV/cache, inputs, API/client and output count. Then repeat at 8192 only if both allocator plans admit it. This separates kernel family from chunk capacity. A current-source fallback without compact is an intermediate arm, not an exact reproduction of the old memory plan.
3. **Evaluate current native fused only after route admission is established.** Add explicit `STRATA_PF_FUSED=1`, retain native-fused support, ensure every actual GU/Down pair passes the fused gate, and compare to MMQ with the same chunk and ring. Run both at 4096 first. If the fused buffer plan admits 8192 while MMQ does not, compare each at their maximum admitted chunk only as a capacity/tuning result, not as a kernel-only A/B. Keep native MMQ available as fallback for unsupported combinations and small/non-streaming chunks.
4. **Restore old compact-layout attention behavior separately from MoE kernel routing.** `STRATA_PREFILL_ATTN_LAYOUT=1` was set in the old measured environment, but its independent speed contribution is unknown. First measure compact MoE workspace with current QSA attention untouched; then evaluate the layout-1 query/merge arrangement as a separate option. Do not bundle it with MMQ→fused or chunk changes.
5. **Keep decode components low priority for this regression boundary.** The old matched later decode median was 16.182 tok/s versus control 16.262 with overlapping ranges; its composite run is evidence for the prefill setup, not for a decode win. Restore CPU quantization or verify scheduling only as a separate decode A/B with sufficient generated output.

The old compact path's main value for this specific question is bounded workspace and avoiding FP32 per-route scratch; the current MMQ/fused routes may still be faster at equal chunk. Source availability alone is not an adoption result. Preserve all numerical, fallback, tail-padding and full-context safeguards when implementing an opt-in candidate.

## Core and server changes to preserve

Treat 1eb as a donor for inference components, not as a replacement build. Keep the current server/API/CLI entrypoint and all current root runtime protections while isolating prefill candidates. The 1eb integration carried all twelve changed common server files byte-for-byte from the pinned v0.1.41 upstream and retained SYCL server support; its server test report recorded 593 tests (585 pass, eight skip). Those functions remain required in the user's intended upstream sync, but they are independent of the MoE GEMM experiment and should not be discarded when restoring `prefill.cpp` code.

Likewise, retain current root support for large `size_t` global ranges, native model loading, request/cache/state lifecycle, and its watchdog/callback lifetime behavior. The old full-context receipts qualify old 1eb behavior only. Any transplanted prefill path must keep queue drain before freeing staging/workspace, real event completion before pinned-buffer reuse, graph retirement before cache/pointer release, typed KV access and tails, canonical QSA spare/capacity bounds, and host-verdict-before-visible-speculative-output. Keep current server runtime compatibility and the API's prompt-cache/RESTORE behavior; validate those separately after any integration. Do not revert `generate.cpp`, the whole SYCL overlay, or shared server files to gain a prefill result.
