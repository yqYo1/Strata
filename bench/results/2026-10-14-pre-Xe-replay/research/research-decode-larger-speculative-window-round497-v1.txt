# R497: larger speculative windows and CPU expert-weight reuse

Date: 2026-10-14 (Asia/Tokyo). Read-only source/history review and public web review. No repo edits, Git mutations, builds, tests, model runs, GPU/profiler work, cleanup, or private-environment scan. This report is the only file written.

## Finding

The compiled old 1eb source and current source both permit verifier windows through T=8; there is no hidden four-token hard ceiling in these two trees. T counts the current token plus T-1 drafts. Thus T=4 means three speculative proposals, while T=8 means seven proposals. The practical first experiment is a measured sweep over T=4..8, with MTP and suffix proposals separated. Going beyond eight is not a safe parameter tweak: verifier and CPU expert buffers, graph captures, policy arrays, and commit state are statically bounded at eight.

Larger T can improve CPU expert weight reuse only when multiple rows route to the same CPU-served expert. Current dispatch deduplicates experts per layer/window, then runs each distinct expert once with a multi-token activation/output list. This reuses the expert blob across those rows. It does not reuse one expert across different layers, and it does not reduce expert traffic when the rows route to distinct experts. Existing source comments say a four-row window has around 3.05x one-row's CPU-miss union, or only about 1.31 rows per distinct miss on average (4 / 3.05). That is evidence of some reuse, but not enough to assume that doubling the window halves RAM traffic. The real test is the per-layer distribution of distinct CPU experts and rows per expert, joined to measured pool time and end-to-end decode time.

The high historical acceptance counts do not by themselves justify T=8. The 46/51 RESTORE result is 90.2% accepted drafts, while fresh 64-output work was 41/66 = 62.1%. Those are different session states and must remain separate. Current stock's three lookup-derived samples reported 41, 61, and 45 proposed rows. Those are proposal counts, not acceptance counts or visible output counts, and cannot establish acceptance without the matched accepted counts and verify-step totals. In all cases, accepted draft count excludes the target correction/bonus token, and final visible output is truncated by `max_new`/EOS; neither proposed nor accepted rows equal visible output tokens. vLLM makes the same distinction in its per-request fields: accepted draft tokens, proposed draft tokens, verify steps, and mean emitted tokens per step are separate metrics [vLLM acceptance metrics](https://docs.vllm.ai/en/latest/features/speculative_decoding/acceptance_metrics/).

A 70 tok/s target is not implied by any acceptance ratio. It needs an end-to-end speed result on the target workload. Longer windows can spend more time in sequential MTP drafting, CPU expert work, verification, and state commit; the winner depends on all of those costs.

## Source limits and work shape

- `include/strata/kernels/verify_kernels.hpp` sets `kVerifyMaxT = 8` in both current source and commit `1eb89482a4afd20277ae0405780ed4f8eb98eb20`. `include/strata/kernels/cpu/expert.hpp` likewise sets `MAXT = 8` in both. The CLI's `--spec T` is the whole verify window, not the number of new drafts: `generate.cpp` documents it as one last/current token plus `T-1` drafts.
- Verifier initialization rejects `max_t > kVerifyMaxT` or CPU `MAXT`. It allocates/captures around `max_t`; `run(T,...)` rejects T above the initialized cap. Current expert dispatch also rejects `n_tok > MAXT`; it permits at most 128 routed entries, while this model's ten expert IDs per token gives at most 80 at T=8. Current MTP load checks `max_t <= kVerifyMaxT`; its draft array capacity is `max_t-1`.
- MTP drafts are autoregressive. `MtpDrafter::draft` launches a graph for the first draft and then one graph per subsequent draft step, synchronizing its stream after every step. T=8 therefore adds up to four serialized draft steps over T=4 (seven rather than three drafts), before the verify pass. `--mtp-max-t` can cap MTP depth independently of verifier T; current default suffix behavior can enlarge the verifier window while limiting MTP depth. Do not conflate “larger verifier T” with “deeper MTP.”
- In current `generate.cpp`, the suffix drafter can propose up to `o.spec - 1` tokens; default suffix drafting is enabled. When no explicit MTP cap is supplied with suffix enabled, parser logic can preserve an MTP cap while raising verifier capacity (up to eight). Therefore record the **effective** `o.spec`, `o.mtp_max_t`, chosen source (MTP or lookup), and actual T histogram, not only command-line `--spec`.
- At each layer, `expert_pool_dispatch_multi` quantizes each row's activation, resolves each routed expert, and puts CPU misses in one `ExpertJobMulti` per distinct expert ID. `ExpertJobMulti` carries up to MAXT activations/output rows. `run_split_multi_native` uses one blob for that job across its rows. CPU jobs only cover CPU misses; resident-GPU/PCIe/peer placements are separate. The old verifier header's recorded miss-union ratios are 1.75x/2.4x/3.05x for T=2/3/4, matching the key tradeoff: larger T reuses dense target weights, but increases the union of CPU misses.
- The CPU expert's weight bytes dominate this question. The session's 982,272,000 B per proposed row is a **logical selected-weight accounting**, not observed DRAM traffic and not a directly additive bandwidth measurement. A repeated expert's one blob is read/unpacked for multiple rows; unique experts still add traffic, while cache-line reuse and OS/NUMA behavior can change physical reads. Report unique expert bytes and pool wall time separately; do not present the logical figure as measured RAM bandwidth.
- QSA and KV are also window-width dependent. Verifier captures one T-row target pass; QSA indexer append and decode attention take row groups; K/V for all proposed positions are written. The canonical indexer state is not committed until acceptance is known: `commit(n_keep)` restores the saved index tail, appends accepted keys, replays only accepted GDN state, and advances PLE history. The code explicitly protects the case where a rejected key occupies a block/spare slot still needed by the accepted path. A larger window must keep this snapshot/restore and full-capacity spare behavior intact; it cannot simply expose speculative state early.
- The root `Verifier` uses a host `PoolMultiFn` boundary and captured GPU work; the actual configured current/old resolver must still be used when validating a particular binary. Do not substitute the CUDA root-source description for the configured SYCL Arc path. The limits above are also stated in the current and old root API, but their runtime relevance depends on the selected source resolver.

## Public evidence and implications

The official vLLM guide explicitly frames speculative decoding as most useful for medium/low-QPS, memory-bound workloads, says results depend on model, traffic, hardware, and sampling, and recommends reproducible local measurement. Its method table describes both MTP and suffix as candidates, not universal wins [vLLM guide](https://docs.vllm.ai/en/latest/features/speculative_decoding/). The current vLLM MTP docs describe a recursive MTP draft chain and verification, consistent with the serial draft-step cost here [vLLM Speculators MTP](https://docs.vllm.ai/projects/speculators/en/latest/user_guide/algorithms/mtp/).

A public MTP case study on an MI50 with partial CPU offload measured target verification at 9.76 ms for one token and 14.8 ms for two (+52%), despite the model being memory-bound; its MTP case later measured +14.5% throughput and 97.7% code acceptance. This is useful evidence that CPU-offloaded verification is not free and acceptance alone is insufficient, but it is a different model, engine, GPU, and workload [Sebastian Haas case study](https://sebastianhaas.dev/research/case-studies/mtp-speculation/). Another consumer-GPU report measured Qwen3.6 MTP at 66.0 versus 31.9 tok/s on one R9700, but it explicitly says its 2.07x result was a short-prompt case and captures long-context acceptance separately; this is not transferable to the Arc/CPU-offload target [Local AI Frontier MTP measurements](https://localaifrontier.com/blog/speculative-decoding-mtp-measured/).

The adaptive-draft-length literature and systems documentation agree on the relevant rule: optimal depth depends jointly on conditional acceptance and round cost; fixed acceptance averages can hide poor later positions, and longer blocks stop being nearly free as verification saturates [vLLM guide](https://docs.vllm.ai/en/latest/features/speculative_decoding/) [adaptive draft-length analysis](https://www.tmls.nyc/research/adaptive-speculative-decoding). This machine adds the especially important CPU-miss-union and per-expert reuse costs.

## Safe experiment and adoption gates

First establish an unchanged-T=4 baseline on the exact 32K fixture and 64 visible-token target with the same binary, process state, expert residency, CPU worker count, prompt/cache state, and environment. Keep first-use vs later reads separate. Preserve the current MMQ setting being measured; the parent run's MMQ0 long sequence should finish before any competing execution.

Then run one-factor windows T=5,6,7,8. For MTP-only, disable suffix (`--suffix-draft 0`) and explicitly set `--spec T --mtp-max-t T --spec-min-p 0`; keep all other settings fixed. This avoids current suffix parser expansion/cap ambiguity. A separate suffix test can hold MTP depth at 4 (`--mtp-max-t 4`) and allow lookup to propose the longer window. Do not combine these into one headline. Record effective configuration and T/source histograms from startup and the completed request.

For each sample retain: visible output count and exact token/hash comparison against the same canonical greedy output; proposed MTP and lookup rows; accepted MTP and lookup rows; verify-step histogram by T and accepted-prefix length; per-position conditional acceptance; MTP draft milliseconds/count; verify milliseconds; commit milliseconds; CPU expert-pool milliseconds; per-layer CPU-miss unique-ID count; per-unique-expert row-count histogram (1..8); bytes of unique CPU expert blobs logically dispatched; GPU/PCIe/peer hit rows; and end-to-end tok/s. Keep first post-prefill window distinct because native path starts with T=1.

Accept a larger fixed MTP depth only if it improves paired end-to-end decode confidence across the target fixture set, without regression in correctness, full-context lifecycle, fault handling, or visible-output equivalence. Accept an adaptive rule only if the logged controller decisions show gains in held-out fixtures and do not overfit the two high-acceptance RESTORE/fresh cases. Never infer benefit from acceptance rate alone. Avoid T>8 until a deliberate source change raises every verifier, graph, CPU job, MTP, state-snapshot, ABI and test bound together; such a change is out of scope for this report.
