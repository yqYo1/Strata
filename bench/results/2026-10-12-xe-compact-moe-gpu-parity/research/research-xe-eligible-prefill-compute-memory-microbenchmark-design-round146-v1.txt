# R146 — source-matched compute/memory microbenchmark design for eligible Xe prefill work

Date: 2026-10-11 (JST). Static source and documentation review only; no build, test, import, device/process query, profiler, inference, GPU execution, Git mutation or cleanup. No performance result is claimed.

## Decision

Do not add a synthetic square-GEMM roofline test. The useful next experiment is a bounded, three-part harness built around the exact native prefill shapes and dispatches: (1) source IQ → FP16 GU/Down dequant, (2) the resulting grouped FP16 products with the same expert row partitions, and (3) a joined full eligible MoE group with compact row partitions. Run an isolated host-to-device transfer case only for genuinely staged experts, and report it separately. This separates host-link transfer, quant/dequant service, grouped GEMM service, scratch/cache behavior, and launch/partition overhead without treating any dormant route as measured.

The pinned candidate is `perf-xe-prefill-row-bounded-scratch-20261011`, HEAD `39e395a103af36323262cdc0dbaea27cba81f3e4`, parent `0740b43488d812117f021ccbe4bd0e15d223f955`. The candidate's compact fallback forms row-bounded groups, gathers only those rows, then invokes `Gemm::f16_groups` or `xmx_gemm_grouped` for GU and Down; noncompact fallback uses the full expert group. IQ grouped dequant APIs (`iq_dequant_gu_group_f16`, `iq_dequant_down_group_f16`) and individual wrappers are already present. Candidate's row partitioning is not proof of the executed GEMM backend: record the actual path string and acceptance/fallback counters. `Gemm::f16_groups` can return false after prior per-expert work, so count attempted and accepted calls separately and reject mixed/partial cases from comparison.

## Minimal harness and case matrix

Implement one opt-in C++ benchmark entrypoint in the owning tree only after the main agent accepts this design. Reuse production allocation, queue, route shapes, and kernel entrypoints; avoid copying alternate implementations into the harness. Freeze and receipt source revision, compiler/build flags, runtime/device, model pack and per-role format, route flags, memory allocation kind, clocks/power mode if available, and command. The baseline arm must preserve the frozen dispatch settings (notably FUSED=0, MMQ=0, preload=0); no `--native-bf16` is implied by old samples. Include only route arms that the source predicates and run receipts establish as eligible.

For each actual (format pair, residency, layer/chunk, GU or Down, `m_e`, M/N/K, leading dimensions, group position) tuple in the 32K census, run:

1. **Dequant-only:** identical production IQ blob pointers and output layout, measuring group GU and Down calls separately; compare grouped API to individual wrappers only when both accept the exact type/shape. Record source bytes, FP16 output bytes, calls, fallback/decline reasons, output hash/checksum and numerical comparison against the production reference. This is the direct way to characterize unpack/dequant work; it does not compare IQ direct-to-product since FUSED0 excludes that path.
2. **Product-only:** use the identical FP16 scratch contents produced by the reference dequant case, same X/H rows and exact group boundaries. Run GU, SwiGLU/intermediate, and Down as distinct kernels/intervals; mark whether `f16_groups` or `xmx_gemm_grouped` actually accepted, and record inner selected implementation (oneMKL, joint matrix/XMX, DP4a) from existing supported runtime evidence. Include production compact split and unsplit cases only for matching routed rows and same total experts. The split test asks whether smaller row subsets reduce padded work enough to repay extra launches/gathers, not whether a synthetic geometry is faster.
3. **Joined group:** invoke the production dequant → gather → GU → SwiGLU → Down chain with real census routing/format/residency distribution. Capture separate stage intervals, dependencies, event counts, scratch bytes/allocations and end-to-end group wall. This confirms stage timings compose in the actual sequence. Run only the smallest complete request/chunk that preserves dispatch and routing semantics; don't extrapolate model performance from isolated cases.
4. **Staging-only (conditional):** for a nonresident expert, separate host packing/staging duration and H2D copy event from device-side dequant. Use the real packed byte count and allocation mode. Avoid a fabricated HostUSM/USM comparison: host allocation/copy mechanics must match the production path. Report current copied bytes and measured transfer interval, never infer current H2D time from the historical 6.446834 GB/s HostUSM number.

Each case has a correctness gate before timing: dequant outputs match the production/reference tensor within the existing format-specific tolerance; GU/Down outputs match reference, and final group output agrees within current prefill tolerances. Preserve output max absolute/relative error and mismatch count. Include expert row conservation (`sum(m_e) = routed rows`), exact row-boundary checksum, accepted/fallback counts and completion/fault state. A case is ineligible if it silently uses another path, drops rows, reuses stale scratch, or cannot show completion.

## Timing, cache and bandwidth method

Use the production SYCL queue with profiling enabled only for the diagnostic arm. Retain returned events through query and completion. Collect event command-start/end for each device operation, host steady-clock submit time and submit-to-completion wall separately; attach predecessor/successor events where dependency is known. An event interval proves that command's device execution, not whole oneMKL wrapper time or critical path. Intel's oneAPI guide distinguishes host submission, device execution and host-offload transfer, and warns profiling intervals omit host/device transfer time: https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2024-1/kernel-launch.html and https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2024-2/using-the-timers.html.

Compile/JIT/preload and allocation are outside steady-state kernel samples but record their separate wall costs. Prewarm each exact kernel/shape until the runtime reports completion, then collect at least 5 warmup invocations and 20 timed repetitions per shape (or a shorter fixed deadline if the caller's run budget requires it; declare that budget before execution). Use deterministic seeded order, randomized across dequant/product/compact cases in each block; synchronize only at block boundaries and when a result must be checked. Preserve all individual samples and report median, p10/p90 and count; abort on any timeout, error, failed event or correctness regression. Run quiet joined endpoint samples before and after the instrumented set to estimate profiler/instrumentation perturbation. Keep GPU profiling to one serial arm, with no concurrent inference/build/test.

Separate cache-hot repeat from streaming regime explicitly. Cache-hot repeats may reuse one exact source/output set and must be labeled reuse/cache-resident; they answer repeat-service latency only. Streaming regime rotates through disjoint, initialized buffers whose combined read/write working set exceeds the documented device cache capacity by at least 2x; if capacity is not published/verified for the exact product/driver, report actual bytes and call it “larger rotating working set,” not DRAM streaming. A larger footprint alone does not prove all bytes reached GDDR. For DRAM attribution, use supported VTune GPU metrics on the exact B570/device/software stack and preserve metric availability/status; correlate task intervals with device memory read/write and L3 bandwidth/miss metrics. VTune documents Arc metrics for host-to-GPU, L3 and system-memory bandwidth, while Intel's GPU analysis guide cautions to inspect dependencies and distinguish L3-bound/stalled time: https://www.intel.com/content/www/us/en/docs/vtune-profiler/user-guide/2025-4/gpu-metrics-reference.html and https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2023-0/gpu-analysis-with-vtunetm-profiler.html. If target counters are unsupported or unavailable, do not label logical bytes as measured DRAM traffic; keep throughput as logical-bytes-per-observed-time with cache state named.

Report distinct quantities: packed source logical bytes, FP16 scratch bytes written and later read, actual copy bytes, API-reported device memory transactions/bandwidth (if supported), L3 bandwidth/miss ratio, event durations and critical-path wall. Avoid a DRAM floor from `logical bytes / 380 GB/s`: that is a ceiling-derived quotient, not a guaranteed floor because cache hits and transaction amplification are unknown. Avoid any FP16 compute roof unless a verified relevant FP16 peak for this exact product is sourced. B570 INT8 TOPS cannot stand in for FP16 throughput. HostUSM 6.446834 GB/s remains isolated historical evidence only.

## Decision interpretation

- Large staged-byte counts plus copy/staging intervals overlapping the exposed chain support a transfer-focused follow-up; copied bytes alone do not prove link-bound service.
- High device memory-read/write with low cache reuse on the same phase supports a memory-pressure hypothesis; high L3 traffic with low external-memory traffic indicates cache bandwidth/reuse may dominate. Check supported counter definitions and device support before interpreting.
- Long dequant device intervals with modest product time support focusing on decode/materialization; compare only same IQ type, source bytes, group size and output layout.
- Long product intervals with active XMX/compute metrics and low memory pressure support a compute/tile hypothesis; capture the actual product path and all relevant utilization metrics. Runtime path names and high utilization do not alone establish saturation.
- Compact-vs-full-group improvements must include gather cost, additional launch count, padded `ceil(max_rows/128) × ceil(N/256)` workgroups and unchanged output correctness. Compare only the same routing and census row counts.
- If profiling shifts the before/after quiet endpoint materially, retain the profile as diagnostic attribution only; use quiet request samples for performance claims.
