# Xe layer-major full-context live-RAM capacity contract (round 147)

Date: 2026-10-12 (Asia/Tokyo). Read-only source and receipt audit. No build, test, GPU/runtime query, process inspection or Git mutation. This is a capacity/liveness contract, not a fit or full-context qualification.

## Decision

Correct the machine description first: the campaign receipt reports MemTotal 134,986,948,608 B (125.716 GiB), and representative pre-run MemAvailable 97,499,279,360 B (90.79 GiB), not a 64-GB machine. The default expert arena is 47,962 MiB (46.838 GiB) of owned, loaded host storage. Corrected full-context INT8 host KV is 6,643,777,536 B (6.1875 GiB). A single layer-major FP32 residual plane is 2.49996 GiB at 65,535 rows and 9.99996 GiB at 262,143 rows. The old 57/115/459-GiB figures are cumulative transfer traffic and must not be booked as simultaneous allocations.

The capacity interpretation therefore does not rule out layer-major on a nominal 64-GB machine; however neither this arithmetic nor the available-memory sample proves a fit. The sample is before model load, and it does not include phase-aligned process RSS, pinned-host allocations, cgroup limit, other applications, memory pressure, or all session owners. Full 262,144-token qualification remains false/unresolved. Preserve the exact context boundary; do not cap prompt length at 262,143 to make the residual plane fit. The current generation route batches `n_prompt-1` then processes the last prompt token through the single-token path. At a 262,144 prompt, the plane needs 262,143 batched rows and session/KV capacity must still represent the final token at position 262,143. Zero output room at this boundary is acceptable; do not silently truncate the prompt.

For each owner below distinguish (a) address-space reservation, (b) pages/storage committed or pinned, and (c) resident set at a particular instant. Anonymous expert-arena allocation is written during load, which commits its pages; pinned host KV allocation is actual pinned backing, not a cost-free mapping. The optional Linux mmap expert branch reserves a file mapping and lets the page cache populate/dismiss pages dynamically; it is neither permanently resident nor zero-cost. `STRATA_ARENA_MMAP` defaults off. Shared-arena reuse, if selected, changes ownership but is not evidenced by this campaign receipt.

Main known-owner subtotal (arena + INT8 host K/V + one plane) is about **50.885 GiB at 64K** and **63.025 GiB at full context**, before other host model/session/runtime/application owners. The 64K calculation uses 65,536 KV cells but 65,535 batched residual rows; full uses 262,144 KV cells and 262,143 batched rows. Values are rounded and not measured allocations. Do not subtract these totals from MemAvailable to claim free headroom: MemAvailable was measured before loading and process/cgroup scope may differ.

For a chosen chunk size `T`, existing PLE host storage is `2 × T × N × 4` bytes (two pinned buffers or two pageable vectors), with `N=2,560` in this build; it does not scale with prompt length. A further pair of layer handoff buffers, when allocated, is `2 × T × D × 4`, `D=HC×N=10,240`. The prefill's other host vectors (token ids, step records, route/slot/source IDs, PLE row indices, expert counts/offsets) scale with `T`, `K`, and expert count. `Prefill::bytes_needed()` is a device workspace query, not a complete process-host-RAM query; its counted region includes streamed staging data but not the prospective residual plane or full process/session accounting.

## Non-host owners and overlap constraints

R142's per-layer expert bank holds all native expert blobs for the active layer across token chunks, and it is provisioned in addition to the existing decode/profile cache; its planned footprint is GPU memory. Existing tail cache slots currently loaned to chunk scratch cannot also be assumed available for that bank. Device VRAM fit requires its own phase-aligned receipt. On the host, the source arena remains live while that bank is copied; source/pack reads, PLE and transfer staging may overlap. Do not add cumulative H2D/D2H traffic to live RAM, but do count any simultaneously retained source buffer or copy buffer if implementation introduces one.

The residual plane is pageable in R142. Making it pinned would change the pinned-host total and may fail even when pageable allocation succeeds. Do not automatically provision two planes for optional rollback or ping-pong: they are separate design choices, and two planes would add another 2.49996/9.99996 GiB at these boundaries. Failure rollback/checkpoint behavior remains a correctness requirement, but no second plane is justified by the current proposal itself.

## Capacity proof still required

No current evidence establishes exact simultaneous process RSS or pinned bytes for an accepted 64K or 262,144 prompt run. A qualifying proof must use the actual selected model/config and process memory limit, record before/after and phase-aligned host available/commit/RSS/pinned values, and name overlap for: arena/source, QSA host pools, residual plane, PLE/handoff buffers, session, MTP, snapshots, other model mappings and runtime. Report reserved virtual bytes separately from committed pages and RSS. At full context, retain the 262,144-cell session/KV and final single-token pass even if generation has no output capacity. Until that evidence exists, the result is **capacity plausible but unqualified**, not rejected by a 64-GB label and not proven to fit.
