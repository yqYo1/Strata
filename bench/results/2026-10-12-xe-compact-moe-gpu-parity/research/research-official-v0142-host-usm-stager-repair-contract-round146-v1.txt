## Exact dataflow and allocation contract

### Expert Stager ring

`Prefill::Impl::Stager` owns `kRing` host buffers, default 16 and environment range 2–256 (`prefill.cpp:347-380`). `done_seq` is allocated using `sycl::malloc_host<uint64_t>(kRing, dpct::get_in_order_queue())` (`:362,385`); each `buf[i]` is also host USM when pinning succeeds (`:395-406`), otherwise a pageable vector fallback. `done_seq` is initialized by the host (`:387`). The GPU's copy queue copies an expert from a buffer to `m.stage_dev[sl]` (`:2577-2587,2645-2654,3855-3857`) and `issued_one` queues a device `fill<uint64_t>` to `done_seq[j % kRing]` (`:503-507`). The worker waits for issue order, then polls the corresponding value through a volatile host load before it may overwrite that pinned source buffer (`:440-450,509-510`). The producer's `ready`/`issued`/`active` and claim-generation variables are CPU-to-CPU atomics; they are not the host/device capability problem (`:366-375,441-488`). Stream/event barriers for the destination slot (`:2564-2565,2588; :2656; :3859`) are a distinct device-buffer ownership protocol and should remain intact.

The worker's producer operations have three forms: direct `memcpy`, `ExpertSource::copy_blob`, and `GgufExpertSource::read_into` (`:451-461`). The caller receives the completed host buffer through `wait(j)` (`:491-495`), enqueues DMA, and calls `issued_one`. This ordering permits host fill of a source slot to overlap prior DMA from other slots, but the individual source allocation remains borrowed by the asynchronous transfer until completion.

### PLE double buffer

`ple_emb_host[2]` is pinned host USM where allocation succeeds and otherwise pageable storage (`:697-705,1041-1056`). After the SSD/host gather completes, the compute queue copies `ple_emb_host[ple_buf]` to device `ple_emb` and queues a device fill of the host-USM sequence slot (`:2305-2325`). Before the host producer refills the older buffer for the next chunk, it polls `ple_done_seq` with a volatile host load (`:2341-2365`). `ple_done_seq` is host USM from `malloc_host<uint64_t>(2, queue)` (`:701-705,1061-1065`). PLE page/previous-token state and its device buffers remain owned by the session; this sequence flag only protects reuse of the host staging allocation.

### Capability and language contract

SYCL 2020 says host USM can be accessed by a device, but concurrent host/device access and atomic modification require `aspect::usm_atomic_host_allocations`; `aspect::usm_host_allocations` alone grants device access, not that concurrency guarantee ([SYCL 2020 spec, aspects](https://registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html#sec:device-aspects), [USM kinds](https://registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html#sec:usm-kinds)). The spec also says a device-side `sycl::atomic_ref` must be used for safe device atomic access; it is not used in host code. For a host/device atomic handshake, when the atomic-host-USM aspect exists, device `sycl::atomic_ref` and host `std::atomic_ref` operations on the same object are guaranteed atomic relative to each other, with system-scope ordering requirements ([atomic references and host/device atomics](https://registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html#sec:atomic-ref)). `volatile` is not such an atomic operation or a memory-ordering protocol.

Level Zero's host-allocation capability matrix is likewise explicit: concurrent host/device access and concurrent atomic access are separate optional capabilities; concurrent access does not itself guarantee coherency/consistency, and concurrent atomics on allocations lacking `CONCURRENT_ATOMIC` are undefined ([Level Zero access capabilities](https://oneapi-src.github.io/level-zero-spec/level-zero/latest/core/PROG.html#access-capabilities)). A host-capability tuple without `CONCURRENT_ATOMIC` cannot justify the existing concurrent volatile handoff. Neither cache hints nor volatile casts upgrade the allocation's capability.

SYCL specifies `event::wait()` blocks until the event and dependent events complete; `event::get_info<command_execution_status>() == complete` has synchronization equivalent to wait. Queue `wait()` blocks until all queue commands complete and provides host-thread forward-progress delegation ([SYCL event and queue synchronization](https://registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html#sec:event-class)). The spec's event-status example also notes that without flushing, whether an event is marked complete can be implementation-defined; any polling variant must ensure the queue is submitted/flushed. These guarantees establish a portable synchronization design, not that this specific Level Zero adapter is free of the historical event-wait liveness bug already recorded by the source comments (`prefill.cpp:498-502,701-703`).

## Smallest safe source repair options

### Recommended initial admission path: capability-independent queue-completion handoff

Provide a conservative synchronous host-USM path for devices without `usm_atomic_host_allocations`; do not execute the current volatile protocol. Preserve the host buffers' ownership and the existing `m.copy`/`m.cs` destination-event ordering.

For the Stager, disable the asynchronous worker's autonomous slot refill in this mode. Have the submitting/launching host thread prepare the next expert into the selected host slot (using the existing three source forms and preserving their error behavior). Before refilling a slot previously used as a DMA source, call `m.copy->wait_and_throw()` on the host thread; only after it returns may the host mutate that buffer. Then enqueue the H2D copy and keep the existing copied/used event ordering for the device destination. The first `kRing` distinct slots may be prepared while earlier distinct-slot copies proceed; at wrap, queue wait establishes source lifetime before slot reuse. A first implementation may use one pinned slot and wait after every copy for the clearest proof, then expand to ring slots if validated. In either version, no GPU command writes a host completion counter and no host thread concurrently polls one. The queue wait may reduce staging overlap, but progress and ownership are defined. The `Stager::finish`, cancellation, and destructor must still join workers/finish active host reads before freeing buffers (`:414-424,512-517,2552-2555`); for safe mode there must be no worker left with access to a synchronously-owned slot.

For PLE, remove the device-written sequence/poll and keep `ple_gather` from refilling a host slot until a host-side wait on `m.cs` completes the prior upload from that slot. The conservative implementation can wait on `m.cs` before launching the next asynchronous gather into the old buffer; a narrower event wait is a later optimization only after reproducing this adapter's known event-host-wait issue. Preserve the double-buffer ownership, the `ple_next` future join/error path, and pageable fallback. Free no buffer until its upload and gather have both completed. The PLE path remains active and semantically unchanged; this is not equivalent to disabling PLE.

This is the lowest-risk source route for the recorded B570 capability because it uses standard host blocking synchronization rather than unsupported concurrent accesses. It can preserve producer/consumer progress at queue granularity and can overlap work on distinct host buffers, while avoiding a CPU/GPU polling dependency. The previous source comment reports a Level Zero v2 adapter hang when a host thread waited on a specific queue event (`:498-502,701-703`); use queue-wide waits for the initial repair and explicitly test queue-wait liveness on the target runtime. If even queue waits reproduce a backend hang, route admission remains blocked pending a different tested backend/runtime implementation; do not restore volatile access.

### Faster optional path: actual atomics, only when capability permits

A future optimized path could retain worker polling only if it is a real system-scope atomic handshake and the runtime reports `aspect::usm_atomic_host_allocations`. Device writes must use `sycl::atomic_ref<uint64_t, ..., sycl::memory_scope::system>`; host reads must use `std::atomic_ref<uint64_t>` on the same correctly aligned object with release/acquire ordering around the payload DMA completion signal. Capability and required alignment/type support must be checked; exceptions and allocation failures route to the queue-completion fallback. Apply this separately to `done_seq` and `ple_done_seq`. Do not gate the existing volatile code on the aspect: that would still be non-atomic. This option has more implementation and validation risk than the initial fallback, and the hardware's host-USM atomic absence means it does not help this B570 route.

A SYCL event-per-slot completion handoff is another spec-conforming possibility: retain the event returned by each copy or a barrier after it, then prevent host-buffer reuse until that event is complete. However, the official source explicitly records prior host event waits hanging on the Level Zero v2 adapter. An event-based worker path is therefore not the minimum admitted repair for this host/runtime; it needs an adapter-level stress fix/validation first. Event status polling also needs a flush/submission contract and error/async-exception handling. Do not claim the spec's event semantics alone dismiss the implementation history.

## Invariants and unresolved details

1. Host source buffer write/read ownership is exclusive: host fills before DMA enqueue; no host rewrite until a queue/event completion establishes the DMA's last read. Queue and event objects belong to the same context/device and remain alive through waits.
2. Device completion flags are removed from the fallback path. If retaining them in an atomic path, each flag's host and device accesses are atomic operations on one object, with system scope, correct order, supported alignment, and checked lifetime.
3. The destination ring's `copied`/`used` barriers, expert source ordering, `issued`, ready-generation rules, and all existing compute/copy dependency edges stay in place. Do not conflate completion of the host source DMA with completion of an expert kernel's use of the destination stage slot.
4. Early returns and exceptions drain or cancel both source reads and queued DMA before releasing the pinned/pageable host slots; PLE's future is joined before buffers are freed. A failed source read must retain its current explicit error/zero policy, never publish a success completion prematurely.
5. Queue-wide waits may serialize more work than necessary. That is a performance cost to measure after correctness, not a reason to weaken the ownership proof. Runtime event-host-wait history remains a specific liveness risk until reproduced and resolved.

Unresolved from source alone: whether `m.copy->wait_and_throw()` from the selected host thread reliably drives all pending copy work under the exact B570 runtime/adapter; the exact wait placement's effect on chunk scheduling; cancellation/error drainage under injected async failures; and the minimum safe queue-wait granularity that preserves useful overlap. No source-only report can settle those runtime properties.
