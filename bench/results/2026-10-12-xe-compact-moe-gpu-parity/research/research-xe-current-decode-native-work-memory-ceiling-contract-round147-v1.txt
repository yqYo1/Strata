# R147 — current cold-decode native work and CPU/RAM ceiling contract

Date: 2026-10-12 (JST). Read-only audit of the immutable XeStrata source snapshot, prior decode/capacity/Zen3 evidence and primary hardware/memory references. No build, test, model/runtime/GPU/process query, profiler/PMU action, Git operation, source edit or cleanup. No new decode result or hardware roof is claimed.

## Decision

The next decode question is a same-request work join, not an inference from 16 output IDs, configured MTP width, routed-token count, or expert parameter totals. The 64 OFF/ON cases closed PASS at 16 IDs and LP5 exactness qualify correctness for those cases; their length does not validate decode speed. The available fresh-first quiet32K result (four OFF/four ON samples) has OFF mean 7.8578 output tokens/s and 12.2% CV, based on 16 generated IDs, MTP4, 144 cache slots, pool5, with hard CPU share 0 and PCIe 0. It is a short, high-variance endpoint and gives no per-pair CPU job or resident-GPU work denominator. Keep it separate from restored decode, correctness-only 64-run rows, and all task-6/capacity diagnostics.

At the frozen candidate `perf-xe-prefill-row-bounded-scratch-20261011`, HEAD `39e395a103af36323262cdc0dbaea27cba81f3e4`, the native decode source defines enough structure to count work exactly, but not to claim its physical service:

- Each layer's `NativeFmt` carries loaded `gu_type`, `d_type`, activation types, `n_embd`, `n_ff`, bytes per GU/Down row, offsets and total expert blob bytes. Derive format/layout/extent from the loaded per-layer entry and its actual source, not a presumed uniform pair or model-wide parameter count.
- In a verifier window, `expert_pool_dispatch_multi` classifies each routed `(token, top-k slot)` as primary-GPU resident, PCIe staged, helper/peer GPU or CPU. It deduplicates CPU-owned rows by expert into one `ExpertJobMulti`; `nt` is that job's CPU-owned rows in this window. It then invokes `run_split_multi_native`. Thus one CPU job reads one expert blob extent logically, while its GU/Down row arithmetic grows with `nt`. GPU-resident rows do GPU work; they are not CPU jobs. An MTP window can compute rows later left uncommitted, so attempted/speculative work and emitted tokens must be separate.
- In ordinary `T=1` decode, dispatch is the single-token path, not the multi-token `ExpertJobMulti` route. With MTP4 the verify-side rows/windows have a different job-NT distribution and may mix committed and uncommitted inputs. A configured width of four is not evidence that all windows have four rows, that the CPU jobs have `nt=4`, or that all drafts are accepted.
- `blob()` / `prefetch()` expose source blobs and can affect file/page-cache readiness. A cold/fresh-first decode after a prompt is not automatically a cold OS page cache or cold DRAM read. “Resident” must name the GPU expert-cache owner and slot state; host source residency and CPU cache residency are separate questions.

The 5600X has six cores, twelve threads, 32 MiB L3 and up to 4.6 GHz boost, with AMD listing memory speeds up to 3200 MT/s. This yields a *conditional specification arithmetic ceiling* of 51.2 GB/s only if the host has two active 64-bit channels at 3200 MT/s: `2 × 8 B × 3.2 GT/s`. The installed channel/rate population is not in the closed evidence. Earlier controls measured 36.869 GB/s for a selected host RAM-read loop and 0.81822 TFLOP/s in a six-core register-FMA loop; neither bounds IQ integer/table-lookup decode. The old native CPU fixture has actual packed 22/20 weights and synthetic quantized activations, with service medians by NT and direct/pool mode. It is useful only for matching `(pair, NT, branch, build, topology)` capacity comparisons, not an upper bound or production decode rate. The first defensible ceilings must be re-measured/qualified against actual loaded RAM configuration, exact current CPU jobs and a sustained >L3 STREAM control. STREAM measures a particular large-array stream, not Strata's IQ service; it cannot establish the bytes Strata fetched from DRAM.

## Minimum matched evidence to close the work question

Use one bounded diagnostic on the same fresh-first request definition, model pack, prompt, output length, binary, cache size, MTP, pool and environment as a longer quiet performance cohort. Preserve the clean, diagnostic-off decode wall result for any performance statement. On the diagnostic request collect these bounded numeric keys, without token content or raw tensors:

1. **Request and speculation accounting:** run/source/model-pack/device identity; fresh vs restored state and exact prompt positions actually consumed; emitted output IDs count; verifier windows; for each window `T`, `K`, offered drafts, effective accepted prefix, committed input rows, uncommitted verifier rows, draft-source path and fallback; separate MTP draft, verify and ordinary one-token decode calls; request correctness, completion and failure state. Include any suffix/lookup draft contributors if active. Averages over 16 visible IDs cannot stand in for attempted model work.
2. **Per-layer route and layout:** every layer's loaded `(gu_type,d_type)`, activation types, `H/FF`, `gu_row/d_row`, offsets and blob bytes; for each verifier window retain routed-row counts and distinct expert jobs by final owner (`resident GPU`, `CPU`, `PCIe`, peer/helper), with per-job CPU `nt=1..MAXT`. Ordinary `T=1` rows must have their own bucket. Cross-check rows total `T*K`, distinct jobs, `multi_entries`, `multi_misses`, `cache_hits`, `offload_entries`, cache-refused counts, staged/copy calls and ownership. Pair GU and Down by the actual layer; do not combine marginal totals as if they were a paired layer census.
3. **Work normalization:** for a native geometry, report actual role FLOPs/MAC convention per CPU job from its loaded dimensions, e.g. dense-equivalent MACs `2*n_ff*n_embd` for the two GU matrices and `n_embd*n_ff` for Down per routed token; mark these as shape work, not native instruction counts. Report logical packed blob bytes once per distinct CPU expert job (`NativeFmt.bytes`), and actual routed rows separately. Report source types: mapped/file/pinned host blob, host cache if known, GPU resident blob, and actual H2D/PCIe bytes/copies if the selected path transfers. `pool.multi_bytes` is submitted logical blob extent; `prefetch` and logical blob bytes do not equal physical RAM reads or DRAM transactions. Preserve Q8/intermediate-activation quantization and caller plan/job stages as separate work.
4. **Current CPU service join:** for actual worker fragments, key by `(request, window, layer, role GU/Down/FF-quant/input-actq, exact format pair/type, nt, branch, expert job, row range, worker/host slot)`. Count submitted jobs and routed expert-token rows before pool submission; in `pool.cpp::drain` collect per-fragment wall and calling-thread CPU-time deltas around the actual native row calls. Keep worker CPU-time sum, worker wall-call sum, phase envelope, active drain, pool waits, host/caller quantization, and dispatch planning distinct. Existing GU/quant/Down phase wall spans include pool barriers and host drain; they overlap request/GPU work and are not CPU-busy time. Record the actual selected branch (GGML fallback vs format-specific AVX2/etc.) at dispatch if naming it; do not infer from type/ISA flags alone.
5. **RAM ceiling controls:** capture installed DIMM/channel/trained data rate and relevant affinity/host participation. Run a pinned six-physical-core STREAM Copy and Triad with arrays each materially larger than L3 (prefer >=4× L3), warmup, correctness, compiler/flags and every sample, under the same worker affinity/host-drainer policy. Report this separately as an attainable streaming memory control. Do not call the old 36.869 GB/s read-loop result a ceiling. Physical bytes during Strata CPU kernel service require CPU-family-valid memory-controller/cache PMU data on that exact interval; current local evidence says perf access is blocked (`perf_event_paranoid=4`, no effective CAP_PERFMON) and prior profiler attempts are inadmissible/failed. Unless that access state changes by an authorized means, label physical traffic/cache split unknown and stop short of a DRAM-bound claim.

Need a larger same-request decode sample than 16 outputs to estimate speed credibly; predeclare output budget and enough independent quiet process blocks to show the sample distribution. Keep output target and MTP policies identical across arms. The diagnostic's added clocks/counters must be default-off, bounded and checked against an otherwise identical quiet run for perturbation; do not use instrumented latency as the speed result. Retain individual samples, prompt/work identity, exact output/correctness and close status.

## Exact counts and conditional ceilings

For each native CPU expert job `j` with loaded dimensions `H=n_embd`, `F=n_ff`, and `nt_j` rows:

- logical packed input is `B_j = NativeFmt.bytes` once per distinct expert job (not multiplied by NT); separate its GU+Up and Down extents using `2*F*gu_row` and `H*d_row` only after validating actual layout/offsets;
- dense-equivalent GU work is `2*H*F*nt_j` MAC; Down is `H*F*nt_j` MAC. These are stable algebraic work counts, not decoded-instruction counts, FLOPs to compare with FMA peak, or bytes transferred;
- CPU work exposure totals `jobs[pair,NT]`, `Σ nt_j`, and each role's job-fragment rows; preserve which verifier rows were committed/uncommitted but do not divide one grouped job's service or packed bytes by an assumed accepted fraction;
- GPU resident calls/rows need separate `owner=resident_gpu` denominators and actual selected GPU path/time if one exists. A zero hard-CPU-share setting means ownership may differ from model source layout; only the per-request ownership census confirms this.

A defensible memory plausibility bound is available only as a conditional check: for a validated matching CPU cohort, `logical packed bytes / measured STREAM GB/s` is the hypothetical time if every logical byte were fetched once from RAM at the benchmark's sustained rate. This is neither an actual DRAM lower bound nor a ceiling for the decode kernel: CPU-cache hits reduce DRAM reads; line fetches, repeated lookup, page faults and other working data can increase them; IQ decode instructions and dependent lookup latency remain outside the stream model. A physical DRAM service estimate requires actual memory-controller bytes and same-interval bandwidth; the RAM transfer ceiling plus those bytes can bound the memory component, but CPU/RAM operation times may overlap and cannot simply be summed into request wall. A CPU compute bound likewise requires actual instruction/µop work and a matching measured service ceiling for that emitted function/NT; 0.818 TFLOP/s FMA is not suitable. Use matching actual-weight component service fixture rates as component capacity controls only, not as an inferred current request limit.

Examples from the old `(22,20), H=2560, F=640` fixture are useful for the formula and its limit, not current work: one expert job has 1,049,600 logical packed GU bytes plus 921,600 Down bytes; combined dense-equivalent work is 4,915,200 MAC per expert-token. Previous capacity medians differed by NT and direct-vs-five-worker pool mode. They used synthetic prequantized activations and only this pair, so cannot be multiplied into a new request absent the exact current pair/NT/job histogram and same branch/topology. Do not assume all current IQ layers use 22/20.

## Existing evidence: use and limits

- Existing counters in this snapshot include request-level `ExpertDispatch` fields (`multi_misses`, `multi_entries`, `cache_hits`, `cache_refused`, `offload_entries`, `ms_plan`, `ms_actq`, `ms_jobs`, `ms_run`) and `ExpertPool` `ms_multi_gu`, `ms_multi_q`, `ms_multi_down`, `multi_bytes`. They establish coarse route/phase exposure. They do not retain an exact per-request join of layer pair × CPU job NT × source/residency × service branch × physical traffic. `Drive::routing` records route IDs for optional trace, but the record is not a packed-byte/NT/service ledger.
- The decode pool component records establish that GU, caller FF quantization and Down phases execute and that CPU pool timing is host elapsed. R204 explicitly warns they overlap and are non-additive. R282 records task-6 route histograms but no time/bytes per job; they do not qualify default task-0 decode.
- R206 specifies 5600X nominal and conditional RAM spec ceilings; R231/R286 have 22/20 CPU capacity medians and the 36.869 GB/s and 0.81822 TFLOP/s controls. They are fixture/control measurements only. R95 records current local perf-counter access unavailable and no admitted PMU result. R260 gives the ownership/job construction seam; R284 gives the minimal worker-clock measurement contract. R310 warns that logical bytes and separate H2D controls are not production traffic/time.
- CPU-only source pins at the current immutable snapshot: `src/core/expert_source.cpp` 7915f5ceb462a5c14655bbe585408f72ef9abd581b95ed14f08d9533d20f2edc; `src/kernels/cpu/native_expert.cpp` 39c7b9e66c52edb7b42d5dd65e5c317bf322e23f1ab24f6b300640abffc989d3; `src/kernels/cpu/pool.cpp` c114539980d496ea69c17fee2ddaf1b7229668afe07586142f572d96cb8a7036; `src/program/generate.cpp` c9b60ef079694302dfa1f8099ddffd5375d7dae503f6edec454c1d7de3d941ee; `include/strata/kernels/cpu/native_expert.hpp` 67976a240c8209694bcf6c11578f466276413f7f136f9d97d10e8ef5501062be; pool header eaa55d450538d6572de06ca0eed374606af04461ca54a39f0007ad5b310ff954.
