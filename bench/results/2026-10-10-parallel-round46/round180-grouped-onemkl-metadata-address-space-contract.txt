## What the API documents, and what it leaves open

The oneMKL 2026.0 `gemm_batch` USM group declaration takes pointers to each metadata array (`transa`, `transb`, `m/n/k`, `alpha/beta`, `lda/ldb/ldc`, `group_size`) and pointer lists (`a`, `b`, `c`), returns a `sycl::event`, and describes A/B/C as arrays containing the pointers to the matrices. It says the returned event is the event to wait on to ensure computation is complete. The docs do **not** say whether the host call copies every metadata/list element before returning, or whether asynchronous work later reads those host addresses. Nor do they expressly define the USM allocation kind for the arrays of metadata or the outer A/B/C pointer-list arrays. [oneMKL 2026.0 `gemm_batch`](https://www.intel.com/content/www/us/en/docs/onemkl/developer-reference-dpcpp/2026-0/gemm-batch.html)

The oneMKL DPC++ BLAS introduction does explicitly require USM-API vector and matrix inputs to refer to memory allocated by a DPC++ USM allocator and device-accessible; ordinary `malloc`/`new` memory cannot be used for those inputs. That is a clear rule for pointed-to matrix storage. It does not explicitly classify the pointer-list storage or the metadata arrays as vector/matrix inputs, so it does not settle their address-space contract. Do not infer that host stack/heap metadata is guaranteed accepted or synchronously copied from their raw-pointer C++ types alone. [oneMKL DPC++ BLAS introduction](https://www.intel.com/content/www/us/en/docs/onemkl/developer-reference-dpcpp/2023-0/introduction-to-the-intel-oneapi-math-kernel.html)

SYCL USM rules say each allocation is tied to a context; accesses must use that same context. Host, device and shared USM have distinct accessibility. USM support and each allocation kind are optional per device and queryable through device aspects. In particular, a USM pointer used by device code must be device-accessible; plain `malloc`/`new` does not become device-accessible unless `usm_system_allocations` is supported, which still is not an explicit oneMKL metadata-array promise. [Khronos SYCL USM reference](https://github.khronos.org/SYCL_Reference/iface/usm_basic_concept.html)

The installed DPCT helper is useful implementation evidence, but not a portable guarantee. At lines 377–415, `gemm_batch_impl` creates a `matrix_info_t` with ordinary `std::malloc`, passes its transpose/scalar/dimension/leading-dimension/group-size members to oneMKL, and submits a host task dependent on the returned event to free that block. It forwards caller A/B/C pointer-list storage directly. Thus this local compatibility layer retains its own ordinary-host metadata until completion, which suggests it deliberately does not assume immediate consumption; it does not demonstrate that caller pointer lists may be stack/heap allocations, or that the oneMKL public contract guarantees either address-space choice. The facade is `void` and hides the returned event, so a new implementation needing explicit retirement should call the event-returning oneMKL overload (or retain everything through a known queue drain).

Device scope also matters. Intel oneMKL 2026.0's BLAS functionality table marks all BLAS-like extensions supported on CPU and Intel GPU. This is not a claim of support on arbitrary SYCL GPU backends: the 2026.0 docs and 2026 release requirements identify Intel GPUs, while API errors include `unsupported_device`/`unimplemented` in the oneMKL specification. The installed signature/header alone cannot establish target-runtime support for this exact precision/device/driver. [oneMKL 2026.0 BLAS functionality](https://www.intel.com/content/www/us/en/docs/onemkl/developer-reference-dpcpp/2026-0/blas-functionality.html), [2026 system requirements](https://www.intel.com/content/www/us/en/developer/articles/release-notes/onemkl/2026.html)

## Conservative sufficient two-entry layout

For each GU or down group, allocate a small, stable metadata record and pointer lists with `sycl::malloc_shared` in the same `sycl::context` as the `m.cs` queue. Before using this path, require `device.has(sycl::aspect::usm_shared_allocations)`; check every allocation result. This is a conservative policy that makes these host-written arrays accessible to both host and device even though the public docs do not require or explicitly guarantee that particular storage choice. It avoids depending on ordinary host arrays being copied.

For `group_count = 1`, allocate these arrays, initialize them once for that call, and do not modify them before completion:

* One-element metadata arrays: `transa[0]=trans`, `transb[0]=nontrans`, `m[0]`, `n[0]=ne`, `k[0]`, `alpha[0]=1.0f`, `lda[0]`, `ldb[0]`, `beta[0]=0.0f`, `ldc[0]`, and `group_size[0]=2`.
* Two-element pointer lists: `a[0..1]`, `b[0..1]`, and `c[0..1]`. The list allocations are shared USM; the addresses stored in the lists point at the existing device-accessible A/B/C matrices.
* The A/B/C matrix allocations remain their existing device-USM allocations. Validate each allocation belongs to the queue's context and each output span is disjoint. The metadata/pointer-list USM allocations and all matrix buffers must remain allocated and unmodified until the batch completion event.

Use the exact R178 values. GU uses `(m,n,k)=(1280,ne,2560)`, `(lda,ldb,ldc)=(2560,2560,1280)`, A entries `dq_gu[q0/q1]`, B entries at `Xs + o0_i*2560`, C entries at `GU + o0_i*1280`. Down uses `(m,n,k)=(2560,ne,640)`, `(lda,ldb,ldc)=(640,640,2560)`, A entries `dq_d[q0/q1]`, B entries at `Hh + o0_i*640`, C entries at `Dm + o0_i*2560`. Same queue/context, noncompact mode only; preserve `compute_mode::unset` and the current FP16/FP16/FP32, alpha/beta and transpose semantics.

Obtain the `sycl::event` directly from the oneMKL call. Do not overwrite or free any metadata array, pointer-list array, A/B/C allocation, or referenced view until `event.wait_and_throw()` completes. Free all USM allocations with `sycl::free(ptr, queue.get_context())` only after completion. For reuse across same-queue operations, either retire on that event or keep the storage pinned through an existing `wait_and_throw` on the same queue; queue ordering alone does not protect host arrays from host writes. On a submit or async failure, fail the run, keep ownership until a completion/error boundary establishes safe retirement, and do not retry the accepted pair as scalar work. If there is no returned event because submission throws, conservatively drain the queue/error boundary before freeing; do not infer that an exception proves no work was accepted.

If this device lacks shared-USM support, this proposed layout is not qualified. A host-USM metadata layout could be considered only after checking `usm_host_allocations` and confirming the oneMKL implementation supports it; a device-USM metadata layout needs an upload/ordering plan and could be overkill for these tiny arrays. Do not silently fall back to ordinary heap/stack storage. The oneMKL `gemm_batch` return event plus existing event behavior supports the completion boundary; there is no new scratch-workspace requirement.

## Minimal root-owned qualification gate (proposal only; not run here)

Add a standalone two-entry API fixture in the same build configuration/device/runtime as production. Use nonidentical, nontrivial A/B inputs, disjoint C spans, and the USM-shared metadata/list layout above, with A/B/C matrices in device USM allocated from the same context. Check allocation types/context with SYCL pointer queries where applicable. Submit once, retain all allocations, wait on the returned event with `wait_and_throw`, and compare each result against the already accepted scalar `gemm` path using the existing pre-registered numerical limits; also assert the two entries landed in their intended output spans. This proves the conservative address-space layout and target precision/device path. It does not claim stack/heap arrays are supported.

Keep the exact batch API, dimensions, types, default compute mode and scalar values fixed. Treat unsupported API/device, absent required USM capability, bad allocation, event failure, wrong output assignment, or out-of-policy numerical error as gate failure. Do not loosen criteria to pass or retry after accepted work. A separate ordinary-host-array experiment is unnecessary for production if the all-USM sufficient layout passes; if the project wants to make a portability claim for ordinary metadata/list arrays, obtain an explicit vendor contract or run a separately approved, backend-specific test and label that result as empirical only.

The gate is API/correctness qualification only, not a runtime or performance claim. Continue to require the already stated production proof: matched real-model comparisons with at least 32,768 actual batched positions (ordinary CLI prompt at least 32,769), repeated independent decode adoption, and full physical 262,144 / 262,143+1 / 262,140+4 lifecycle tests. Keep same-backend event submit/start timing separate from host `steady_clock`, and retain the current fixed numerical criteria. No gain or adoption result is established here.
