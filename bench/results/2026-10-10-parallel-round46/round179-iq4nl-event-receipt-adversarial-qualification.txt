## Finding: parity does not validate event attribution

An exact-bit parity pass shows that generic and private kernels produced the expected outputs for the tested inputs. It does not prove that a timing sample came from the corresponding launch. A result can falsely pass if the collector counts caller attempts rather than successful submissions, drops a receipt but uses the surviving vector length as its denominator, duplicates a receipt, tags a generic event as private, shifts metadata by one call, captures a queue-tail/sentinel event, overwrites an old slot on capacity overflow, leaves a nested scope active, or queries event timestamps from the wrong queue/backend. These are independent of numerical parity.

R177's direct-event sink remains the smallest scoped mechanism: retain the actual `sycl::event` returned by the one submit in each existing void wrapper, with no duplicated kernel body and no per-expert wait. This follow-up qualifies the sink's own accounting and failure paths; it does not redesign or implement that sink.

## Bounded two-layer gate

Use a pure host gate before any GPU work, then a small owner-supervised valid-device diagnostic. The host gate validates sink/state-machine behavior and expected call plans. The device diagnostic verifies real returned-event identity, direct wrapper metadata, and timestamp availability on the admitted queue. Keep the existing exact-bit parity and host-origin async-error gates intact; this additional gate can reject timing, never soften a correctness check.

### Host-only synthetic gate — before any queue submission

1. **Expected plan and capacity preflight.** Construct a plan of bounded call records with unique scope ID and expected order/arm/queue tag/type/n/pointer tuple. Allocate capacity before installing the active scope. If expected count exceeds capacity, fail scope admission before any wrapper call; assert zero submit-attempt counter, zero receipt serials, zero stored events, and no `STAGE` recording a device submission. For a test capacity of one and a two-call plan, the expected result is this preflight rejection. Capacity must never be implemented as a wrapping index or silent overwrite.

2. **Nested-scope rejection and restoration.** Install an outer scope, attempt to install an inner one, and require explicit rejection before submissions. Assert outer sink identity, next serial, capacity, and receipt count are unchanged and still active; destroy the outer scope and assert TLS returns to its original null/prior value. This detects a nested scope that shadows the intended sink, leaks its pointer after destruction, resets a serial, or fans a single command into both scopes. If implementation chooses save/restore with nested support instead, define that forwarding rule and test exactly one receipt per command; do not leave behavior implicit.

3. **Collector metadata adversaries.** Through a host-only validator entry point, inject synthetic metadata tuples to confirm the gate rejects duplicate serials, a gap, wrong arm tag, wrong queue identity, changed type/n or source/destination pointer, out-of-order planned calls, excess records, and zero records for a nonzero expected call count. Compare against an independently constructed expected-call list, not a count derived from the sink itself. Keep event identity out of this test; it proves the parser/collector detects metadata corruption, not GPU launch identity.

4. **Pre-submit validation rejects.** For the private wrapper, reuse its current host-only invalid cases with a scoped sink and null stream; its argument guards precede queue resolution/submission. Require the expected exception, zero successful-submit count, and zero receipts. The generic wrapper's invalid branch calls `std::exit(1)` before queue lookup/submission, so it cannot be tested inline: either verify the source ordering or run that invalid call in a sacrificial child process whose output parser rejects any receipt marker and requires the expected exit. Do not use a valid-device call to test an invalid pre-submit argument. This gate proves invalid arguments never receive kernel-event receipts; it does not qualify valid queue/capability failures.

5. **Injected recorder/query state failures.** Before GPU admission, drive the sink's no-throw capture callback with a forced “drop next receipt” condition and verify it only sets a sticky incomplete flag; it must not throw across the post-submit hook or increment the stored-event count as though it succeeded. Drive the timestamp-query wrapper with a synthetic exception after the host state is marked complete; require “sample invalid,” not a performance row or pass, while the cleanup decision remains safe because completion was already established. These are host state-machine tests. They do not simulate a SYCL runtime event-copy or profiling exception.

Host-only tests are not proof that an actual queue returned an event or that the device supported profiling. They can establish capacity, scope, receipt-validator, and post-completion error-state logic without touching a GPU.

### Valid-device diagnostic — root-owned GPU/device action

On the already qualified B570 root device, with the exact runtime/compiler and current worktree/build receipt, first record device identity, selected queue pointer, backend, in-order property, `has_property<sycl::property::queue::enable_profiling>()`, `aspect::queue_profiling`, and `info::device::profiling_timer_resolution`. If the actual queue lacks profiling property or the device lacks the aspect, reject timing before any DQ submissions. A property on some other/default queue is irrelevant: these APIs accept `void* stream`, and the event is profiled according to the queue that submitted that command.

Use a very small planned series on one submitting host thread. Submit a pre-guard command and retain its event, invoke the existing generic and private wrappers in independently planned order under the receipt scope, then submit a post-guard command and retain its event. Use the same in-order profiling queue and no per-call wait; perform the existing single drain after the whole series. The guard commands are diagnostic identity sentinels, not performance samples. Count each attempted wrapper call separately from each successful return and from stored receipts. The exact plan should call generic and private at least once with known valid type-20 inputs and dimensions, and assert one-to-one expected receipts by serial, arm tag, queue, arguments, and scope.

At each instrumented submit site, the returned event must be passed directly to the sink. A static review of that exact line is necessary because queue-tail APIs cannot prove which helper submitted an event. At runtime, require each captured event to compare unequal to both pre/post guard events and check non-strict profiling order `pre.end <= captured.start <= captured.end <= post.start` on the same in-order queue, with equality accepted. This detects substitution with adjacent known events and obvious reordering. It cannot alone detect a substitution with a different unrelated event whose time happens to lie in the bracket; static proof that the sink receives the local submit return plus tuple/serial matching closes that gap. Do not infer equality of timestamps means event identity.

To validate **lost capture after accepted work**, arm a one-shot test hook that deliberately drops the receipt after one real wrapper has returned from `submit` while leaving the helper's command accepted. The helper/hook must not throw or wait. Continue to the same batch drain, then assert: actual successful-return/attempt count includes the command; receipt count has the deliberate gap; the sticky loss flag invalidates the entire timing batch; both input/output allocations remain alive through a successful completion drain and correctness readback; cleanup occurs only after completion; no timing pass or terminal-success marker is emitted. This proves the harness does not turn an accepted but unmeasured kernel into a fabricated sample and does not unwind live USM. It is a capture-path fault injection, not a device fault.

To validate a **profiling-query exception after known completion**, complete the ordinary queue drain first and set an explicit `known_complete` state. Then inject an exception at the profiling-query adapter (or, separately, record an actual backend query exception). Require the whole timing batch to be rejected, the query error recorded, event references safely released, and normal post-completion cleanup to proceed. Do not route that exception through the “completion unknown” fail-stop path: a failed read of timestamps after completion does not make already completed work live again. If completion establishment itself fails before the query phase, preserve the existing no-unwind/fail-stop policy. The injected query exception validates the handler path only; it does not prove the runtime can or cannot throw from real profiling queries.

The device diagnostic must report no timing pass unless every expected receipt is present exactly once and all profile reads succeed. Preserve all existing numerical output, canary, input immutability, and terminal checks; the event test supplements those checks. A sink capture or profile read failure invalidates timing even when numerical parity passes.

## Timestamp contract: allow quantized zero-duration observations

The current Khronos SYCL 2020 specification provides these usable constraints:

- `command_submit`, `command_start`, and `command_end` are 64-bit nanosecond timestamps. Events on the same backend share a timebase. The device descriptor `info::device::profiling_timer_resolution` reports device timer resolution in nanoseconds. The specification does not promise a particular timestamp accuracy; `command_start` is encouraged to be close to start, but no specific accuracy is guaranteed.
- Ordering is non-strict: `command_start >= command_submit` and `command_end >= command_start`. Equal values are allowed. A measured service interval of zero is therefore a valid reported observation at the available timestamp granularity; do not filter it, reject it, coerce it to one tick, or impose an unsupported positive-duration rule. Record resolution and raw timestamps so zero observations remain visible. A coarse/zero-heavy result may lack enough resolution to establish a difference; handle that through repeated paired samples and uncertainty, not by silently deleting zeros.
- `command_start` queries can block until a command is running or complete; `command_end` blocks until it is complete. Query only after the planned drain anyway, so timestamp collection does not become hidden per-expert synchronization.
- Event profiling data requires the profiling property on the queue that submitted the event. The device must support `aspect::queue_profiling` for this property; constructing an unsupported profiling queue is specified to throw. Admission must check the actual queue's property and record the device aspect/resolution before DQ launches. Timestamp query errors invalidate the measurements.

Use `service_ns = end - start` and `queue_ns = start - submit` from the same event/backend. Measure host wrapper-call time with `std::chrono::steady_clock` and report it separately; the SYCL specification defines no correlation between that host clock and the device event timebase. Never subtract host and device timestamps.

Primary reference: [Khronos SYCL 2020 specification, current revision](https://registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html) — `queue::submit` return-event contract (§4.6.5.2), `aspect::queue_profiling` and `enable_profiling` (§4.6.3/§4.6.5.5), device timer resolution (§4.6.4), and event profiling descriptors (§4.6.6.5). The same source specifies in-order queue guarantees and states that execution order among submissions from multiple threads is determined by the runtime (§3.9.3), so per-thread serials alone cannot claim a global shared-queue order.

## Another implementation's concrete lesson

PETSc's SYCL device-context source keeps a queue and host `steady_clock` time, and comments that its timer is not the right way to time device execution. It shows an event `submit`, `wait`, and `command_start`/`command_end` query as the SYCL method, then states that its wrapper cannot control the input queue or retain the launch event, so it falls back to host time. This supports two specific admission requirements here: retain the actual returned event at the submit site, and separately prove the submitting queue has profiling enabled. It is not a correctness suite: the source example does not test receipt loss, one-to-one call metadata, query failure, equal timestamps, or accuracy, so none of those are borrowed as a passing test pattern. [PETSc SYCL device context source](https://petsc.org/release/src/sys/objects/device/impls/sycl/syclcontext.sycl.cxx.html#L113)

## Result interpretation and limits

The host-only gate validates sink admission, scope isolation, metadata accounting, and safe invalidation branches; it cannot establish the actual returned-event identity, device timer behavior, or GPU profiling property. The valid-device diagnostic validates those actual queue/event properties for the exact small run; it does not establish a model speedup, route frequency, all-path production correctness, full 262,144-token physical KV, or adoption. Root has already recorded the legal host-task/control cases as passed; this design must not reinterpret that async-boundary pass as an event-receipt pass.

An isolated DQ component result remains a component measurement. Any real-model performance comparison must use at least 32,768 actual batched prompt positions, with actual direct helper-call receipts and generic/private routing held constant. Decode remains repeated and independent. No arbitrary minimum useful gain threshold is imposed; a small measured gain may matter, but it still needs a correct event mapping, uncertainty accounting, and the requested end-to-end evidence.

No new performance candidate or implementation is proposed here. R177's no-ABI-change, compile-guarded event sink remains pending separate implementation and qualification. Numerical parity, host-task async handling, static image inclusion, and timing are separate gates.
