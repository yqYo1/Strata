# R181 — distinct Intel small-row FP16 MoE GEMM candidates

Read-only source and public implementation/documentation review, 2026-10-10. No source edits, builds, compilers, tests, runtime/model calls, device queries, profiler, Git, cleanup, or access to the active implementation worktree were used. There are no runtime or performance claims here.

## Result

Two bounded component hypotheses remain distinct from R149's adjacent equal-M oneMKL `gemm_batch` pairing and R171's IQ4_NL vector-store/private dequant work. They both keep the current FP16 weights/activations and FP32 results as the starting contract. Candidate A is a shape-bucketed SYCL*TLA FP16 GEMM backend for measured small M. Candidate B is fusing the interleaved SwiGLU epilogue into the gate/up GEMM. Neither is proven faster or fully target-qualified. Do not promote either beyond an isolated exact-shape component comparison unless its applicable requirements below are met.

A public Intel AutoRound/ARK API also documents FP16/BF16 grouped GEMM across experts with unequal token counts; vLLM-XPU and SGLang-XPU ship Intel MoE/grouped-GEMM kernels. These establish that the broader implementation family exists, but grouped execution is adjacent to R149's already reviewed batching scope and those APIs/kernels do not establish that Strata's streamed IQ experts, weight layouts, precision contract, or small M regime can reuse them. I do not list this as a new candidate.

## Candidate A — small-M bucket to a BMG-tuned FP16 GEMM

**Hypothesis.** Some observed `ne` buckets may be poorly served by the existing oneMKL launch path; a compile-time tile-specialized SYCL*TLA GEMM could improve the device service time for the exact skinny-M matrices while keeping FP16 inputs and FP32 accumulation/output. This is a backend/tiling experiment, not a cache of opaque oneMKL algorithms and not R149's equal-row expert batching.

**Source and eligibility.** Intel's SYCL*TLA repo describes a SYCL/CUTLASS header-only GEMM framework with hierarchical tiling and mixed-precision FP16 support. Its current hardware table explicitly lists Arc B580 (Xe2) and its build docs name target `intel_gpu_bmg_g21`; its CI matrix records DPC++ 2025.3+ for Xe2. That is strong family/toolchain evidence but does not explicitly list Arc B570. Therefore B570 support is plausible, not documented by that table; source/build availability does not prove the exact kernel instruction path, matrix shape, or driver is supported on this B570 system. The installed oneMKL 2026.1 version is known from R178 but says nothing about TLA being present in this build. The candidate would add a dependency/integration path unless the needed headers are already available to the root-owned build.

The exact call-site mapping is straightforward only for a component probe: compare one expert's current `Gemm::f16` against a TLA FP16×FP16→FP32 kernel with same transpose, leading dimensions and beta=0 semantics at GU `(M=ne,N=1280,K=2560)` and down `(M=ne,N=2560,K=640)`. Candidate dispatch should be based on a small number of immutable M buckets selected from a measured real routed-row histogram, retaining oneMKL fallback for every other M and all unsupported cases. Do not invent a representative M such as 160; obtain it from a real >=32768-position model trace first. Fixed model dimensions do not make `ne` fixed.

**Why not already covered.** R149 assesses whether adjacent experts with the same `ne` can be submitted together through the existing oneMKL batch API. This tests an alternate per-matrix implementation for an already measured M bucket. R178 reviews that batch API's lifetimes, not a TLA GEMM. R174 audits an existing direct-IQ `joint_matrix` kernel that dequantizes quantized weights inside a workgroup and notes a 4–5× slowdown on a different card; this candidate instead consumes the already dequantized FP16 matrices and tests a different tiled GEMM implementation. It does not reuse or endorse that IQ kernel. Prior result and applicability records include R146 (compiled native fallback, not MMQ/fused), R149, R153, R174, R178, and R176; none supplies B570 TLA measurements for the two FP16 shapes.

**Smallest gate.** First obtain the actual per-expert `ne` histogram on a >=32768-position run using root-owned instrumentation, without using a guessed M. Then run an isolated component comparison for only the most frequent eligible noncompact M values, for both exact shapes, with identical resident FP16 input/weight buffers and FP32 output. Keep oneMKL as control. Record oneMKL and TLA device start/end service on the same production backend/queue when available; record host submission separately. Validate every output against the existing full-precision baseline and existing parity criteria, including finite checks; no tolerance relaxation. Reject on unsupported B570/compiler/driver configuration, correctness difference outside existing criteria, or no repeatable service reduction. This component gate proves nothing about routed model performance. Only after that could a model gate compare same backend end-to-end for >=32768 actual batched positions and confirm repeated-decode independence.

## Candidate B — fuse gate/up interleaved SwiGLU as a GEMM epilogue

**Hypothesis.** In the active route, gate/up emits `ne×1280` FP32 GU, then a separate `swiglu_interleaved` reads GU and writes `ne×640` Hh. A custom GEMM with a matching fused epilogue could avoid one device submission and the FP32 GU write/read, while preserving FP32 accumulation and FP32 Hh. The current oneMKL GEMM and the elementwise operator are separate calls; no fusion currently occurs in this SYCL fallback.

**Evidence and limits.** SYCL*TLA describes fused epilogues as a supported framework feature, and vLLM-XPU describes its kernel library as SYCL/DPC++ and lists activation and grouped GEMM operations. This supports the general implementation technique, not a claim that a ready-made TLA SwiGLU epilogue exists or that the required output transform is supported. A new epilogue would need to implement Strata's exact interleaved layout and activation formula. The projection is a single packed GU weight with 1280 output rows arranged for gate/up pairing, so the mapping must preserve the exact pair convention in `swiglu_interleaved`; it cannot assume two independent projections or reorder output lanes. Keep current FP16 A/B, FP32 accumulator and FP32 output H. Do not fold down GEMM into this candidate or change weight conversion.

**Why not already covered.** R149's batch proposal preserves the separate current per-expert GU GEMM, SwiGLU and down-GEMM sequence and aims at call grouping; it does not fuse the elementwise operation. R174's IQ4NL/XMX kernel replaces the multiply with dequant-from-packed-weights and had adverse different-card evidence; this proposal would use the already materialized FP16 matrix and changes the GU epilogue boundary only. R171 changes the private IQ4NL dequant store and is separate. No report in the registry's R146/R149/R153/R171/R174/R176/R178 scope covers a fused GU epilogue.

**Smallest gate.** At one actual noncompact M from the model histogram, compare existing `Gemm::f16` plus `swiglu_interleaved` against an opt-in single fused GU+SwiGLU component. Use the same already-dequantized FP16 W and activation X. Compare both FP32 GU (before fusion's epilogue, if exposed in a diagnostic arm) and final FP32 Hh against the existing implementation, with exact lane mapping, finite checks and existing numerical criteria. Measure device service for GEMM, SwiGLU and their sum, plus fused-kernel service and separate host submission; no per-call host waits. Stop if correctness criteria fail or saved elementwise service does not exceed added fused-kernel cost. This is still only a synthetic/isolated component result. If it survives, use the established >=32768-position model gate and preserve the physical 262144 lifecycle requirements for any later adoption.

## Other-engine and official-source cross-check

- Intel SYCL*TLA documents the technology, FP16 support, B580/Xe2 validation, target naming and version matrix: [SYCL*TLA README](https://github.com/intel/sycl-tla), [SYCL*TLA 0.9.3 release notes](https://github.com/intel/sycl-tla/releases/tag/v0.9.3). Its public feature/API evidence establishes that a tiled FP16 prototype is a real SYCL option; it does not supply timings for these `M×N×K` shapes or qualify Arc B570.
- Intel AutoRound's ARK README explicitly lists `ark.moe_gemm` as XPU FP16/BF16 activations and weights, accepting per-expert token counts for unequal expert sizes, built with `ARK_SYCL_TLA=ON`: [ARK MoE API](https://github.com/intel/auto-round/blob/main/auto_round_extension/ark/README.md#2-moe-mixture-of-experts-grouped-gemm). This is closest dtype evidence for a variable-M grouped route, but differs from R181's individual GEMM/epilogue candidates and from Strata's streamed, per-expert dequant scratch. It is not evidence of drop-in integration or faster service.
- Intel's vLLM-XPU kernel project says its operations are written in SYCL/DPC++ and lists grouped GEMM and activation operations; the current project requirements name oneAPI 2026.1: [vLLM-XPU kernels README](https://github.com/vllm-project/vllm-xpu-kernels). The release notes identify native Xe2 grouped-GEMM paths for MXFP8 and block-FP8, which demonstrate active architecture-specific expert GEMM work but those quantized formats do not match Strata's current FP16 buffers: [v0.1.13 release notes](https://github.com/vllm-project/vllm-xpu-kernels/releases/tag/v0.1.13).
- SGLang's official XPU kernel library has a build-time `USE_MOE` option for MoE group GEMM; SGLang's XPU docs describe an Intel Xe2 W4A16 MXFP4 grouped kernel. These are useful implementation checks but not current dtype/weight-layout matches: [SGLang XPU kernels](https://github.com/sgl-project/sgl-kernel-xpu), [SGLang XPU platform/MXFP4 notes](https://github.com/sgl-project/sglang/blob/main/docs/docs/hardware-platforms/xpu.mdx).
- Intel's current oneMKL DPC++ reference describes asynchronous BLAS routines and supported scalar types; R178 additionally checked the installed 2026.1 `gemm_batch` signatures. No public oneMKL material located in this review presents a user-selectable persistent FP16 GEMM plan/algorithm object that could be cached at the Strata call site. Therefore “cache oneMKL algorithm descriptors” is not a supported candidate from this evidence. Use a public algorithm control only if a separately pinned API proves it exists in the installed version.
- Intel's oneAPI GPU Optimization Guide documents XMX acceleration for supported datatypes/compiler combinations ([Intel optimization guide](https://cdrdv2-public.intel.com/824351/oneapi_optimization-guide-gpu_2024.2-771772-824351.pdf)). That is consistent with the existing oneMKL FP16 path already being eligible for XMX; it does not establish a further flag or algorithm to switch on. It should not be used to infer a performance win.

## Avoidance and decision

This report does not restate R149 equal-M batching, the R146 route-map replacement, direct packed-IQ4NL output/vector stores (R163/R171), direct-IQ joint-matrix integration (R174), or event/dispatch measurement protocol (R176–R178). Those are already explicitly audited. It does not recommend migration to vLLM/SGLang, quantization changes, reduced precision/tolerances, a CUDA/HIP port, or batching advice as such.

Priority is B (fused gate/up epilogue) only if the component setup can preserve existing FP32 results and the saved launch/data movement is measurable; otherwise stop. A (TLA small-M GEMM replacement) is a lower-priority toolchain/backend trial because oneMKL is already production-qualified, B570 eligibility is unproven from TLA's public hardware list, and no exact-shape timing evidence was found. If root has no measured expert-M histogram and service breakdown yet, defer both until those records exist. Current disposition: hypotheses only, no runtime or performance claim, no adoption.
