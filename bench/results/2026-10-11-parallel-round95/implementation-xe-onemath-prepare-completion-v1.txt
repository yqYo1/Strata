Ownership and completion decisions:
1. TrialStorage is constructed before allocation, and owns the private in-order queue plus initially null
   X/Y pointers. Each malloc_device result is checked immediately. A null allocation throws DeviceError,
   and a throwing second allocation still leaves the first pointer owned by the scope. No trial product
   dereferences a null pointer. Allocation failures are not misclassified as unsupported math backends.
2. The queue handler retains a shared atomic<bool>, not a shared plain bool. It records actual asynchronous
   exception text to stderr and makes the sticky failure flag visible with release/acquire operations.
   The handler does not clear a prior error or modify backend policy. Shared ownership outlives queue
   handler copies, including queue teardown; the flag's member precedes the queue in construction order.
3. Each phase submits an in-order terminal barrier, then calls the existing Runtime::wait on that event.
   The snapshot Runtime::wait accepts an event without requiring ownership of the private queue, tracks
   the wait in the existing watchdog, calls event.wait_and_throw, and checks the Runtime's sticky errors.
   Runtime::finish(queue) cannot be used here: it explicitly refuses a queue outside the engine streams.
   queue.throw_asynchronous then delivers any remaining private-queue error, and the sticky atomic flag
   is checked. This follows the engine's existing terminal-barrier completion pattern without polling,
   spin, retries, unchecked q.wait, or changing the watchdog deadline.
4. Any terminal-barrier submission/wait/async-delivery exception, or a reported private-queue async error,
   prints the phase/error, flushes stderr and calls std::_Exit(1). It does not throw through TrialStorage,
   free either trial pointer, destroy the queue, return a fallback result, reset the flag, or retry a wait.
   An error is never used as proof of GPU completion. The existing Runtime watchdog also fail-stops if
   its monitored wait exceeds the existing deadline (120 seconds in the snapshot).
5. TrialStorage's destructor always performs a terminal checked completion before freeing non-null X/Y.
   This includes normal return, unsupported backend/type fallback, and unwind from a synchronous
   allocation/fill/product exception. If the cleanup drain fails, fail-stop occurs before free/queue
   destruction. A free exception also fail-stops rather than unwinding through remaining storage.
   There is no catch followed by an unchecked wait that authorizes release.

Fallback versus execution failure:
  The FP16 and BF16 oneMath product calls have separate synchronous oneapi::math::exception catches.
  FP16 rejection keeps the existing Trial::why -> Backend::blas=false route; BF16 rejection keeps the
  existing Trial::bf16=false -> own BF16 route. Both pass through checked completion first, because
  even a synchronous exception could follow an earlier accepted submission. A failed or asynchronous
  completion never returns either fallback Trial. A non-oneMath synchronous exception propagates via
  the future after safe scope cleanup; BF16 no longer turns an arbitrary std::exception into a quiet
  unsupported-type result. The product helper and all operational Gemm math/dispatch below prepare
  are byte-unchanged. The trial remains a 16x16 FP16 product followed, on FP16 success, by BF16, with
  the same zero inputs and FP32 output. No warmup repetitions or policy knobs were added.

Future / static lifetime:
  Using Runtime::wait requires the captured Runtime to outlive the async worker. Gemm::prepare now
  creates a function-local JoinTrials guard after Runtime::get, before publishing any async future.
  The Runtime instances belong to the function-local runtimes vector in the snapshot; its destructor
  is registered before this join guard. The guard therefore runs first during normal static teardown,
  while the Runtime/watchdog, g_backends and g_mutex are alive. It waits for every still-valid shared
  future under g_mutex. Workers use only their captured Runtime and private trial scope and never take
  g_mutex, so this wait does not hold a lock the worker needs. A settled future already finished worker
  cleanup before ready.get returned; clearing it does not leave an active trial to join later.
  future.wait here joins the worker; it is not a GPU completion check or a claim that its Trial succeeded.
  Worker exceptions remain stored for ready.get, and the worker's storage cleanup itself still has to
  finish the checked drain. A future-join exception is fail-stop. No background worker relies on
  g_backends' later shared_future destructor to keep an already destroyed Runtime alive.
