## Finding

A new, testable K=640 candidate is to write each decoded IQ4_NL FP16 weight directly into the existing XMX packed-B layout in local memory. The frozen `xmx_gemm_iq` path already decodes quantized weights into a row-major local `stage` tile, transposes them into a second local `packed` tile, then loads FP16 B tiles with `joint_matrix_load`. For the native IQ4_NL Down shape, the loader can skip both the intermediate row-major tile and the local transpose: each native 18-byte block supplies 32 quantized values for one output row and one K interval, so the loader can decode each low/high nibble pair, round its scaled values to FP16, and place that pair at its final packed-B address.

The primary expected benefit is a reduction in local-memory traffic and capacity, plus one fewer full-tile rearrangement/barrier sequence. It does not remove quantized-byte reads or nonlinear decode, and it does not reduce global weight traffic. It also does not inherently reuse weights across multiple M tiles: doing that requires keeping the packed tile resident while computing multiple activation tiles, trading occupancy and accumulator state against fewer decodes. No gain is claimed before measuring the candidate against oneMKL and the existing XMX route under the actual routed-M distribution.

## Frozen arithmetic and matrix contract

R201 records the selected native Down matrix as `N=2560`, `K=640`, with 51,200 native 18-byte blocks and 3,276,800 packed bytes. Each output row therefore contains 20 consecutive 18-byte blocks (360 bytes), each block representing 32 values. The local IQ4_NL decoder reads the stored FP16 scale as float, multiplies it by one of the 16 signed nonlinear codebook values, then converts/stores the result as FP16. Its block helper maps low nibbles before high nibbles. The current XMX IQ path can take a whole K slab when K is not a multiple of 256, provided `NT*K` is divisible by 256 and K is divisible by 16; with `NT=16`, K=640 satisfies those conditions. It uses FP16 A and B operands, FP32 accumulator matrices, and FP32 output.

The new loader must preserve those steps in that order for each weight: `scale_half -> float`, `code -> exact signed IQ4_NL integer`, FP32 multiplication, then FP16 round-to-nearest-even. It must place the resulting exact FP16 bits into B; multiplying the unrounded FP32 dequantized value by A would violate the contract. Do not replace the IQ4_NL nonlinear table with a signed/affine nibble mapping.

K=640 is exactly 40 K=16 XMX steps, and the Q blocks align as 20 groups of 32 values. No K tail is needed for this admitted shape. A first specialization should reject other K values, `N` values not divisible by the output tile, and unsupported device/compiler combinations instead of quietly applying incomplete tail logic. The design retains FP32 accumulation and output, but the joint-matrix reduction order and implementation may differ from oneMKL; the established local GEMM numerical policy still governs acceptance. Exact equality of final FP32 outputs is not asserted.

## Loader mapping

Use one work-group per 16-output tile (`NT=16`) and preserve the existing required subgroup size 16 / eight-subgroup work-group only after runtime and compiled-image qualification for this device. For a native row `n` within the tile and block index `b in [0,20)`, block base K is `32*b`. Within its 16 packed bytes, byte `j` contains the low code for K=`32*b+2*j` and high code for K=`32*b+2*j+1`. After codebook lookup and FP16 rounding, store the two halves at:

`packed[(k >> 1) * (NT * 2) + n * 2 + (k & 1)]`

where `k` is the global row-local K index in `[0,640)`. This is the same packed-B address equation already used by the frozen kernel. It yields one collision-free address for each `(k,n)` and lets the unchanged B load consume 16x16 tiles with stride `NT*2`.

The source bytes are interleaved by block, so the loader reads a scale from the block header and the 16 quantized bytes from that same native block. Avoid assuming 16-byte alignment or issuing wide reads across a block/row boundary: row starts advance by 360 bytes, which is 8 modulo 16. Scalar or safely bounded byte/half loads avoid crossing the row allocation. Each block's 32 decoded values are wholly within one output row; no padding, repack, global temporary, or permanent per-expert copy is required.

With 16 output rows, the final packed B tile is `640/2 * 32 = 10,240` halves (20 KiB). The existing route allocates both a row-major stage tile and packed tile for this shape, each 10,240 halves (40 KiB combined), before A-tail and accumulator scratch. The direct writer can remove the stage tile, reducing that pair to the packed tile alone. This capacity estimate is arithmetic from the frozen layout, not a device allocation report. Local-memory occupancy and compiler register use remain unknown.

All lanes in each subgroup must execute each joint-matrix load/MAD collectively and in convergent control flow. The work-group must place a local-memory barrier after all subgroups finish writing B and before the first joint-matrix load; no subgroup may begin reading while another still writes. If the loader uses subgroup-local barriers or reductions, they must be uniform too. For the fixed production N=2560, every 16-row output tile is full. M tails must continue to zero invalid A rows before matrix load and suppress invalid output stores as the frozen kernel already does. The exact block count, source bounds, and output offsets need a standalone boundary checker before any runtime dispatch is enabled.

## Reuse and work scheduling tradeoff

The frozen kernel's outer M-chunk loop restages weights for every M chunk. A direct packed writer preserves that behavior and isolates the no-transpose benefit. A second, explicitly separate variant can retain one packed B tile while computing `R` consecutive 16-row activation tiles, reducing decode work by approximately `R` for the same output tile. That increases the work-group's live FP32 accumulator matrices (one per resident M tile), extends one work-group's lifetime, and can reduce scheduling parallelism. It may help only when M is large enough and the device has spare occupancy; at low routed M, it adds no reuse and could lose. Compare small `R` values as separate candidates and report local-memory/register use plus actual concurrent workgroups. Do not choose R based on guessed top-k or a fixed routed-row count.

A grouped persistent design that loads a B tile once and distributes it across several independent work-groups is not proposed: ordinary local memory is work-group scoped, and such a design would require a different global cache or cooperative launch contract with extra synchronization/lifetime costs. Likewise, pre-repacking all experts into normalized arrays would add persistent memory and load/initialization costs and would fail the direct-native-loader question.

## Numerical and correctness gates

The first gate is the block loader alone against the frozen generic IQ4_NL dequantizer. Exhaust all 16 code values under scales chosen to distinguish sign, exponent, subnormal/zero, rounding ties, overflow boundaries if reachable, and low/high nibble positions; compare output FP16 bits. Exercise the first and last block of each row, adjacent row starts (including the 360-byte stride), and the first/last native block of the 16-row tile. This is a proposed test matrix, not a test performed here.

Next qualify the complete `M x 2560 x 640` operator for M=1, values around 16-row boundaries, and M values from an actual caller census. Compare exact decoded FP16 weight bits separately from final GEMM outputs; preserve FP32 accumulators and FP32 output and apply existing GEMM parity criteria without loosening tolerances. Verify each output once, no invalid-M row writes, no input reads outside 51,200 blocks, correct K order, and no early local read. Check sanitizer/fault handling through the owning queue boundary before production use. The R164 helper finding about asynchronous error propagation remains relevant: a later GEMM must not be treated as proof that a specialized submit succeeded, and no generic replay should occur after partial acceptance.

Only after the operator passes should a root-owned component comparison measure matched M values, resident input/weights, warm and cold order controls, and device-service time separately from host submission. Include the current oneMKL dequant-plus-GEMM route and existing XMX path as controls, count all conversion/decode work, and report the actual device/compiler/image. The model-level comparison still requires the real caller census and existing full-model acceptance limits. Type-20 pack metadata and a synthetic operator result do not establish production calls or speedup.

## B570 and ESIMD limits

The existing XMX path is a `joint_matrix` path, not proof that an ESIMD implementation is already legal or efficient on the owner’s B570 setup. Intel's XMX guide says joint-matrix operations are subgroup-scoped, requires XMX hardware for its example, and describes the `load`, `mad`, and `store` operations and tuning choices. That supports the proposed tile construction in general, but not target qualification for this exact compiler/driver/device/data type. The SYCL 2020 specification describes round-to-nearest-even as the default floating conversion mode for floating types; Intel's compiler reference also documents `float2half_rn`. The kernel should nevertheless use an explicitly round-to-nearest-even conversion primitive or prove generated conversion behavior, then compare bits with the source path.

No use of Intel ESIMD `dpas` intrinsics is needed for this first design; reuse the existing joint-matrix interface and target gate. If a separate ESIMD implementation is pursued later, its required subgroup/work-group aspects, supported operand/accumulator combinations, local-memory behavior, and emitted lowering must be qualified independently. The Intel llm-scaler reference from R201 is useful for IQ4_NL codebook and nibble ordering only: its normalized weights, K=640 fallback, FP32 weight multiply, and FP16 output still make it a non-drop-in source. This report does not reopen that eligibility survey.

## Newness and disposition

The specific new candidate is a native 18-byte-block IQ4_NL loader that writes the existing packed XMX B operand directly, preserving FP16 weight-rounding bits while avoiding the row-major SLM tile and transpose. This is distinct from R201's external GEMV ABI survey and from the existing frozen XMX implementation's generic `dq_dispatch -> stage -> packed` flow. It is a source-level architecture hypothesis with a clear byte-level address formula and an immediate correctness oracle. It has no compiled-image proof, target qualification, runtime result, or measured benefit. Keep all production route/defaults unchanged until the loader, operator, error boundary, real route census, and model-level gates pass.
