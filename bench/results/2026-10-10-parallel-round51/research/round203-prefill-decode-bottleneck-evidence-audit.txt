# R203 — Prefill and decode bottleneck evidence audit

Date: 2026-10-10 (Asia/Tokyo). Read-only reconciliation of closed model measurements, phase receipts, host counters and component-profiler records. Only this report was written. No source edits, builds, tests, model/GPU/profiler runs, device or live-process inspection, Git operations, service actions or cleanup were performed.

## Finding

The strongest current conclusion is a coarse prefill one: native expert-copy activation on the v0.1.41 route coincides with a substantial increase in 32K prefill throughput in a quiet same-day A/B sequence, while independent helper measurements show only a small host-wall change for one IQ4_NL dequant helper. This supports prioritizing transfer/staging and the surrounding MoE schedule for phase attribution. It does not establish PCIe saturation, transfer as the sole cause, or the fraction of request time spent on transfer.

For decode, the qualified baseline is about 16.47 tok/s for the first decode after fresh prefill and 21.69 tok/s for restored repeats. Native-copy decode repeats are about 22.16 tok/s baseline versus 21.89 tok/s with native copy enabled; the paired interval crosses zero. There is no demonstrated decode gain or regression from that candidate, and no closed CPU hot-path profile that identifies a decode kernel/task as the bottleneck. Existing host accounting does show the CPU copy-worker sum, GPU-wait host time and submission time, but those are overlapping counters. Their sum is not the request wall and cannot identify exclusive CPU or device service.

The detailed phase receipt is still an older v0.1.40.2 diagnostic. It shows `host grouping`, `gemm down`, `gemm gate/up`, `dequant` and `gather` as the largest measured phase-attributed intervals in that 32K run. The timer uses consecutive compute-queue event markers and charges queue idle gaps to the phase being waited on. These figures are useful for coarse ranking only; they are not pure kernel times and are not current v0.1.41 estimates. No existing closed real-model report joins current native MoE GU/down wrappers to their internal oneMKL device commands.

The production route represented by current v0.1.41 receipts is native MoE IQ-to-FP16 dequantization followed by oneMKL FP16-input, FP32-compute/output GEMM. MMQ and fused flags are false. R201 found no eligible direct IQ4_NL GEMM replacement; its external ESIMD GEMV is a format reference only. Do not treat a source candidate, event count, kernel name, or standalone helper result as evidence of model call share or performance.

## Phase and profiler receipts

The only retained real-model fine phase record found is `owned-dd5-phase-v2-v01402-code32k-diagnostic-r1/record.json` (SHA-256 `89ad8649fdd397d41f89ac6120ff5c3c44fd811aa153357f8968f86312a56567`). It is a v0.1.40.2 diagnostic with `STRATA_PREFILL_TIMING=1`, state/head dumps and trace/loader/validation logging. Four request phase reports have aggregate compute-queue timeline values 323,519.1, 316,043.1, 317,166.9 and 315,664.8 ms. Across those reports the intervals range approximately as follows: host grouping 79,809–80,621 ms; GEMM down 83,026–83,584 ms; GEMM gate/up 56,931–57,399 ms; dequant 39,167–39,613 ms; gather 22,323–22,529 ms; copy wait 4,682–4,830 ms; QSA projection 3,537–3,600 ms; QSA indexer 2.5–9.8 ms; QSA selection 2,629–2,664 ms; QSA attention 10,619–10,647 ms. All are phase-attributed queue timeline intervals. In particular, `host grouping` can include compute-queue idle time while CPU work is being grouped; GEMM labels are not isolated kernel elapsed times. QSA marks also cover more than the named primitive (projection includes KV/QKV/output work; attention includes dispatch/transform). The run cannot rank current v0.1.41 kernels, supply a full-context profile, or give additive CPU/GPU time accounting.

The earlier round-30 audit records a different 262,140-input full-context run with no `STRATA_PREFILL_TIMING` phase report. It reported 830,132.7 ms first prompt and 759,945.9 ms repeat, with repeat math gate false. Those are failed diagnostic wall observations, not clean performance or QSA evidence. No retained full-context phase receipt closes this gap.

For oneMKL MoE attribution, R190 is a plan, not a result. It explains that the wrapper’s host stopwatch includes dispatch and later completion, while the oneMKL return event only guarantees completion and its interval is not documented as the whole library operation. No accepted result presently joins the return event to internal GU/down kernels and dependencies. The suggested bounded unitrace trace with ITT operation labels and an ordered host ledger remains the right first discriminating profile if the owner proceeds. It must retain ambiguous commands as unattributed and keep kernel-duration sum, device span, event interval, host submit and host wait as separate fields.

The IQ4_NL event-receipt probe has successful synthetic kernel launches and profiling queries, but its later host-wall source audit (R197) defines a separate inclusive host measurement, not GPU timing. Another real event-profile sample was rejected: its exact-event `command_start - command_submit` was -1,333 ns, violating SYCL’s same-backend ordering contract if the returned descriptors were faithfully associated. R198 gives a plausible cached-submit clock mechanism from public SYCL source but cannot establish that the installed v2 binary followed that path. Preserve the failure; do not clamp, offset-correct, or reuse it as valid service timing. The native IQ dequant service fixture has only synthetic component counts and does not sample model routes.

No completed VTune CPU hotspot or decode pool phase receipt in the audited closed set identifies an active decode function’s exclusive share or critical path. VTune/gprofng research reports define protocol and limitations, not recorded production profile results. CPU task timing remains unmeasured as a causal bottleneck.

## Double counting and causal interpretation rules

- The phase timer’s consecutive compute-queue marker intervals are queue-timeline attribution. Gaps while the host is preparing work can be charged to the currently open phase. They are not per-kernel execution, and other copy-queue active intervals may overlap them.
- `expert_submit_host_ms`, `group_gpu_wait_host_ms`, `host_copy_worker_ms`, group CPU time and whole request wall are different scopes. The worker value sums workers; submit and waits can overlap GPU execution; GPU wait is not GPU service. Do not add these to each other or the wall.
- Native-copy on/off is a whole-route intervention. It supports the claim that this route change is associated with faster 32K prefill under this specific sequence. It does not identify whether the gain came from DMA, host scheduling, different queue submission behavior, or interaction among them. There is no PCIe utilization/saturation measurement here.
- Per-event intervals, sums of overlapping kernels, cross-queue span and wrapper host wall are distinct quantities. Never report their sum as operation wall or infer exclusive time without a dependency graph and consistent clock domain.
- Aggregate arithmetic extents from the unregistered R200 caller census are source/accounting bounds, not measured bytes transferred, time, or verified active expert counts. R200 itself notes that chunk/expert identity, async completion proof, and application prompt-to-batched-position provenance remain incomplete. R201’s external kernel screen supplies source-format eligibility reasoning, not local B570 performance.

## Prioritized next measurement plan (not executed)

1. **Close the current real prefill phase ranking first.** On the serially qualified v0.1.41 baseline and an actual model prompt with at least 32,768 batched positions, emit the existing coarse phase receipt in a separate diagnostic process. Keep its profiling/logging overhead and phase semantics explicit; compare its phase labels to a quiet, fresh-process request without claiming the diagnostic timings are the quiet timings. If the practical question is 262,144 physical positions, keep that as a separate full-context control with the required tail and state/correctness checks. Record input/batched positions, build/source identity, all switches, per-request wall and raw phase values. This resolves whether the old v0.1.40.2 ranking remains representative before any phase optimization is selected.

2. **Attribute the native IQ/oneMKL prefill route.** Use R190’s bounded one-run ledger and ITT + PTI unitrace software trace for a selected actual MoE layer/chunk in a separate diagnostic process. Join each existing GU/down wrapper call to trace commands only through explicit event/dependency evidence or proven queue order; otherwise mark it unjoined. Do not add per-expert waits, alter queue policy, or mix profiler runs into clean throughput samples. Record event completion, optional same-event action timestamps, each attributed kernel/copy interval, device envelope and host timing separately. This distinguishes dispatch/grouping, dequant and GEMM internal work and supplies the missing causal map for the observed native-copy prefill movement. Existing event-profile inversion remains failed and does not support a corrected timing estimate.

3. **Measure decode’s host critical path with lightweight counters before another candidate sweep.** Take one fresh first-decode and one restored decode request from separate lifecycle-qualified processes; instrument the already active CPU pool phases with per-task/per-worker start/end, queue wait, dispatch count, work amount, and layer/task identity, then compute the host critical path without summing worker durations. Preserve request wall and generated-token count. Avoid profiler collection in the clean comparison. The existing `decode-pool-phase-critical-path-round7` source plan is a measurement proposal, not evidence; VTune collection research is not a profile. This will discriminate CPU pool imbalance/dispatch from device-side or other waits.

4. **Only if those receipts show a specific residual candidate, repeat its whole-model comparison with independent process blocks.** Keep fresh prefill, fresh first decode, and restored decode separate. Meet the >=32,768 actual-batched-position floor and full physical 262,144 lifecycle/tail qualification before considering adoption. Continue to treat CIs spanning zero as unresolved rather than equivalence; require no correctness/fault regression. Do not select CPU-grain, copy scheduling or GEMM changes from external results alone.
