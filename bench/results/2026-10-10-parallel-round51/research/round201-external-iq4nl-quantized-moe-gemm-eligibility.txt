# R201 — external quantized MoE GEMM eligibility for IQ4_NL Down on B570

Date: 2026-10-10 (Asia/Tokyo). Read-only review of the immutable Strata source identity supplied by the owner (`2ab09413117044d7499ac6acc6c12db404024f9d`) and primary external code/docs. No source change, build, compiler, test, profiler, inference, device/service query, or Git operation was performed. External code was inspected at immutable GitHub commit URLs recorded below. No external performance number is transferred to Strata.

## Disposition

One new, format-specific external implementation is worth preserving as a component reference: Intel llm-scaler’s shared SGLang ESIMD IQ4_NL/IQ4_XS GEMV. It spells out the canonical 16-entry nonlinear IQ4 lookup, decodes low nibble before high nibble, applies the FP16 per-32 scale in FP32, and has an M-specialized form that reuses decoded weights across multiple input rows. That is closer to Strata’s exact quantized format than ordinary signed/affine INT4 MoE kernels.

It is not an eligible drop-in Down GEMM for this model and supplies no B570 performance evidence. Its current `iq4_gemv_M_host` explicitly falls back to one separate GEMV submission per row when K is not divisible by 256; Strata Down has K=640. The implementation expects deinterleaved `[N,K/2]` packed weights and `[N,K/32]` scale arrays, whereas Strata holds native interleaved 18-byte IQ4_NL blocks. It produces FP16 outputs and performs float dot-products over weights dequantized in FP32, while Strata’s current path first rounds each `scale * code` weight to FP16 and then uses FP16 inputs with FP32 GEMM accumulation/output. Therefore adopting it as-is changes both required layout and arithmetic/rounding. An adapted direct matrix kernel would be new work and must be compared against the current exact route.

The Intel llm-scaler fused prefill INT4 MoE is a separate non-candidate: its source decodes linearly signed/two’s-complement or Marlin-shuffled nibble values with per-group scales, uses DPAS, and stores FP16 intermediate/output. It does not implement IQ4_NL’s nonlinear codebook. vLLM-XPU’s newer grouped Xe2 paths are likewise documented for MXFP8/block-FP8, not GGML IQ4_NL. FlashInfer’s documented FP4 MoE/GEMM is CUDA/CUTLASS-family code and uses other formats/architectures. These do not satisfy the requested source format or target.

No B570-eligible replacement is admitted. The useful new evidence is a precise external IQ4_NL ESIMD arithmetic/layout reference and a sharply bounded follow-up question: whether an adapted K=640 direct IQ4_NL down kernel can keep enough rows resident/reuse decoded weights while preserving Strata’s FP16 weight-rounding and FP32 GEMM contract, without adding a weight-repack cost. This is a hypothesis only; no speed gain is claimed.

## Pinned Strata contract and route limits

The supplied immutable native path uses IQ4_NL type 20 Down with orientation `2560 output × 640 input`, 1,638,400 values, 51,200 18-byte blocks, and 3,276,800-byte materialized FP16 matrix. Type-20’s table has 16 nonlinear signed integer codes; it is not a linearly mapped signed nibble. The present route dequantizes IQ weights to FP16, then invokes oneMKL FP16-input / FP32-output-and-compute GEMM. R171 records the active `dq_iq4_nl` order as `float(d) * integer_code`, then FP16 conversion/store. R181 records the production MoE shapes and runtime M (`ne`) as data-dependent routed rows.

Installed metadata showing 39 of 48 layers with Down type 20 is format eligibility, not a call census (R186). The direct native call is conditional on positive routed expert rows, selected noncompact/native route, and the loaded layer layout; actual selected experts and successful helper returns are required to establish calls. No external kernel supports the conclusion that this model’s Down path executes any particular candidate. The usual validation floor remains at least 32,768 actual batched prefill positions; full-physical-context and repeated-decode requirements remain those already recorded in the registry. Do not use a GEMV microbenchmark or a fixed guessed `ne` as model evidence.

The local `xmx_gemm_iq` helper is already in Strata source, accepts IQ4_NL and uses workgroup-local FP16 dequant plus FP16 `joint_matrix` products with FP32 accumulators. Its call-path/performance gap is already documented by `prefill-xmx-existing-code-audit.txt` and R174. R174 is a compiled-image qualification plan, not a B570 slowdown measurement; registry correction explicitly disallows attributing a 4–5× result to it. R181’s TLA small-M FP16 GEMM and fused GU+SwiGLU candidates are distinct, conditional FP16-buffer hypotheses. R171’s packed-LUT/OpenCL screen and current fixed-type dispatch work are also distinct. This report does not repeat or promote those candidates.

## New primary implementation: llm-scaler IQ4_NL/IQ4_XS ESIMD GEMV

At Intel `llm-scaler` commit `0bf3789b9b1548b5d5078a8deaba214b59f12f04` (commit date 2026-10-09), `sglang/custom-esimd-kernels/csrc/xpu/esimd_kernels/iq4_GEMV.h` identifies itself as a shared canonical IQ4_NL/IQ4_XS GEMV and defines input `[M,K]` FP16, packed weights `[N,K/2]` uint8, scales `[N,K/32]` FP16, and FP16 `[M,N]` output (lines 1–14). Its code gives the 16 entries `{-127,-104,-83,-65,-49,-35,-22,-10,1,13,25,38,53,69,89,113}` and constructs the lookup through eight immediate bit planes, with the top plane contributing -128 (lines 23–38). Packed bytes are unpacked low nibble then high nibble, interleaved into element order, multiplied by FP32-converted FP16 scales, and returned as FP32 dequantized weights (lines 41–59). This is credible evidence for the canonical nonlinear table and a codebook implementation pattern; it is not evidence that Strata’s compiler currently emits an efficient lookup or that the pattern is faster than its signed-byte table.

The single-row GEMV forms FP32 products of those FP32 weights and FP16 activations, sums in FP32, then casts final output to FP16 (lines 73–119 and 122–158). The `M` kernel shares each decoded weight tile across M input rows, but still stores each row/output as FP16 (lines 199–245). Its host dispatch uses M tiles 16, 8, 4, 2, or 1 only when K is divisible by 256; otherwise it loops over M and calls the single-row host path separately (lines 248–299). Strata’s K=640 triggers this fallback. The source contains no output mode retaining FP32 accumulators/output, and its order does not round each dequantized weight to FP16 before multiplication.

A further integration mismatch is structural: the file documents that SGLang normalizes raw GGUF blocks before this kernel into separate packed-weight and scale tensors. Strata’s native input is block-interleaved `(half d, 16 packed bytes)` for every 32 weights. At K=640 per Down output row, the source kernel’s normalized layout occupies 320 packed bytes plus 20 half scales (360 bytes), versus 20 native IQ4_NL blocks ×18 bytes = 360 bytes. This equal byte count does not mean zero-cost compatibility: bytes and scales are at different addresses/order, so the direct kernel needs either an up-front repack or a modified block-addressing loader. If retained weights for many experts are repacked, memory use and initialization/loading time must be charged; if repacked on demand, that cost and lifetime must be included. The external source provides neither a native-Strata-layout path nor an end-to-end ownership/lifetime recipe for Strata’s scratch buffers.

## Related external candidates screened

**llm-scaler/SGLang fused INT4 prefill.** At the same pinned commit, `sglang/custom-esimd-kernels/csrc/moe_prefill/moe_prefill_int4.sycl` fuses expert-sorted gate/up and down projections with routing/activation work. Its gate/up weights use IPEX K-major, Marlin-shuffled uint32 storage, per-group FP16 scales, nibble unshuffle, and signed `nibble - 8` values (lines 108–145, 197–243). Its Down section uses the same linear unshuffle/decode pattern and DPAS (lines 266–369). It allocates/consumes routed expert ranges, processes M in tiles, and emits FP16 output (lines 270–313, 375–395). The top-level full-int4 call composes top-k, gather, up, down, then weighted accumulation (lines 925–963). Its algebra is not IQ4_NL: replacing the nonlinear table with linear signed values changes every code except any coincident entries. It also has an explicit FP16 accumulation path (`simd<fp16,...> acc`) rather than Strata’s current FP32 accumulation/output. Copying its linear INT4 DPAS recipe would be an invalid quantization and precision substitution. The sibling `moe_batch/int4_nmajor_gemm.h` explicitly describes implement_zp two’s-complement nibbles (lines 3–18, 115–150), so it is not a nonlinear IQ4_NL kernel either.

**vLLM-XPU kernels.** The current repository README says kernels use SYCL/DPC++ and oneDNN, lists grouped GEMM and FP8/MXFP4 quantization, and requires oneAPI 2026.1. Release notes identify Xe2 grouped paths for MXFP8 and block-FP8. This is valid evidence for contemporary Intel XPU grouped GEMM engineering, but no IQ4_NL format reader or GGUF block mapping was found in the screened tree. The grouped-GEMM interfaces are relevant only as a framework comparison; they do not provide the missing table, weight layout, or Strata rounding compatibility.

**llama.cpp SYCL.** The backend supports IQ4_NL and its SYCL conversion path dequantizes GGML formats, as R171 already records. The current SYCL `mmq.cpp` is a generic quantized matrix-multiply implementation with different internal tile/activation quantization contracts; no new standalone, production-ready direct IQ4_NL MoE Down kernel matching Strata’s `M×2560×640` FP16/FP32 contract emerged beyond the already-reviewed code. CUDA MMQ and other CUDA/HIP implementations are not evidence for B570 SYCL legality or speed.

**FlashInfer.** Its own primary README describes CUDA-oriented backends (CUTLASS/CuTe/TensorRT-LLM) and FP8/NVFP4/MXFP4 MoE formats. Those formats, layouts, instructions and device targets do not establish a direct IQ4_NL implementation for Intel SYCL, so no candidate is transferred.

## B570 SYCL/XMX legality and arithmetic gates

Intel’s B570 product specification says Xe2 microarchitecture and 144 XMX engines, device ID `0xE20C`. That proves hardware XMX presence. Intel’s 2025.2 GPU optimization guide’s characteristics table lists Arc B580 with subgroup sizes 16 and 32 and XMX/DPAS, but does not list B570. A family-level inference that B570 can execute a particular DPC++ `joint_matrix`/ESIMD DPAS combination is not qualification of this card, driver, compiler, or data type. The specific local `xmx_gemm_iq` uses required subgroup size 16, and Intel’s joint-matrix guide says all lanes in the subgroup must participate convergently. Any extension to that kernel must preserve uniform collective control and query exact runtime combinations for FP16 A/B, FP32 accumulator, tile shape and target. ESIMD DPAS code has its own required aspects, supported subgroup/workgroup and compiler-lowering constraints; source syntax alone is not proof of legal execution. The llm-scaler ESIMD files do not claim validation on Arc B570. Do not imply a CUDA/HIP implementation or an XMX-present datasheet settles these gates.

For a direct operator to match the current local reference, it must consume the exact IQ4_NL 16-code lookup and nibble/block order, convert stored scale to FP32, compute `float(scale) * float(code)`, round that weight to FP16 as current dequant does, multiply by FP16 activations, accumulate/output in FP32 under the same required GEMM numerical criteria, and retain the current output tensor layout. DPAS hardware modes that accumulate in FP16 or integer, fold scales differently, bypass the FP16 weight rounding, or change reduction ordering are separate approximate kernels and must pass the existing numerical parity policy; no tolerance relaxation is implied. Exact output equality may not be required for GEMM by local policy, but this review has no result showing any alternative meets that policy.

An M-aware kernel must dispatch from actual per-expert routed-row counts, including tiny M and tails. K=640 requires 40 DPAS K=16 steps or 20 IQ4 groups if recast to those tilings; output N=2560 is divisible by the external GEMV’s four-row scheduling and by common N tiles, but that superficial divisibility does not solve the weight ABI, FP32 accumulator/output contract, per-M dispatch fallback, or occupancy. With one routed row, current IQ4 GEMV is nominally a vector reduction and may be worth a microbenchmark only after accounting for conversion/repack. At larger routed M, tile reuse and XMX may make a true direct GEMM more promising. No actual `ne` histogram or candidate performance sample is available, so selecting one dispatch point here would invent workload coverage.

Any integration must keep packed model weights, per-expert routing indices, activation rows, output scratch and asynchronous queue operations alive through their known completion boundary. Repacked weights cannot be freed or reused while accepted kernels may still read them; async faults cannot trigger replay after partial acceptance. If one kernel processes experts in a grouped grid, each group’s offsets and zero-row behavior must be proven and bounds checked. Do not add per-expert synchronization merely to establish safety. R178/R190 retain the separate existing concerns about batched GEMM pointer-array/scratch lifetimes and event attribution; an external sample’s queue design does not resolve Strata’s wrappers.

## Novelty, remaining gate, and source pins

The new finding versus R171 is the exact Intel llm-scaler shared IQ4_NL ESIMD codebook and multirow GEMV, not a generalized INT4 or CUDA recommendation. The new finding versus R181 is a low-level format-specific vector GEMV reference, not its FP16 oneMKL replacement backend or fused SwiGLU epilogue. It remains held because its present M fallback is especially mismatched to K=640, it requires normalized weight arrays, and it has incompatible output rounding. No external direct matrix kernel currently clears all constraints.

If a later root-owned exploration pursues it, the minimum useful first gate is a host/device component design that proves a single-block IQ4_NL loader exactly matches all 16 table values, nibble order, scale conversion and FP16 weight bits; then test the exact `N=2560,K=640` matrix multiply at M values sourced from an actual >=32K route census. The comparison should use resident packed model input and resident activations, current oneMKL as control, the existing FP32 output/compute contract, repeatable device-service records plus host submission separately, and full numerical checks. Include repack cost/memory if used. Only a qualifying component result may justify an opt-in full-model run; it does not itself establish prefill benefit. Preserve existing full physical 262,144+tail controls and independent repeated decode for any later adoption decision. No arbitrary gain threshold is introduced.
