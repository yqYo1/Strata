## Eligibility and path selection

`sycl/include/sycl/ext/oneapi/experimental/profiling_tag.hpp` dispatches by device aspect, not queue profiling property. If `aspect::ext_oneapi_queue_profiling_tag` is present, `submit_profiling_tag(queue)` submits a `CGType::ProfilingTag`, even on a queue without `enable_profiling`. If that aspect is absent, the extension falls back to `ext_oneapi_submit_barrier()` only when the queue has `enable_profiling`; otherwise it throws `errc::invalid`. Thus a native tag's profiling eligibility is an explicit exception to the normal `enable_profiling` precondition; it is not a general relaxation for arbitrary events.

The scheduler marks the returned event as a profiling-tag event before submission. `event_impl::checkProfilingPreconditions()` accepts this flag without `MIsProfilingEnabled`. For this event, `command_submit` is fetched from the UR event; ordinary events on a non-profiling queue still fail the SYCL precondition. The extension's existing unit tests exercise supported native tags on default and in-order queues, and fallback behavior on unsupported devices (default queue throws, profiling queue uses a barrier). These are mock-UR tests, not physical-device checks.

For a native tag, scheduler code issues `urEnqueueTimestampRecordingExp`. On an out-of-order queue it brackets the timestamp record with a marker/barrier sequence; in-order queues take a simpler path. The tag is therefore an ordered marker in the queue stream, not a timestamp attached to or duration measurement of the preceding copy. Tag events also require a real returned UR event to query later; the scheduler's discarded-event path passes a null event output. Do not expect profiling queries to work on an event that has been discarded.

## What the inspected adapters expose

The Level Zero v2 adapter treats a timestamp-recording event as profile-queryable even when the queue's ordinary profiling flag is off. Its timestamp recorder captures a device global timestamp before appending `zeCommandListAppendWriteGlobalTimestamp`; the latter writes the end timestamp on the command list. Timestamp queries return the captured start-side value for queued/submit, while start/end/complete return the recorded end timestamp in the timestamped-event branch. This is a point marker, not an operation start/end interval: `command_start` and `command_end` on the tag do not bound useful work. Batched queues can defer submission of the command list, so the gap between the two values can include batch-submission delay; the adapter source comments explicitly describe that behavior. The non-timestamped ordinary event path requires event profiling enabled and queries Level Zero kernel timestamps.

The Level Zero legacy adapter has the same explicit “profiling enabled or timestamped” gate and returns its captured global start and recorded end timestamp for timestamped events. Adapter-specific details differ; avoid assuming every backend shares Level Zero's timestamp implementation.

The native CPU UR adapter shown in this tree does not implement `urEnqueueTimestampRecordingExp` (`DIE_NO_IMPLEMENTATION`). Its event profiling values are populated by queue profiling's host-side `tick_start`/`tick_end` only when the queue reports profiling enabled. Its device does not establish the native profiling-tag aspect in the sources inspected, so extension dispatch would use the profiling-enabled barrier fallback there; a source audit cannot establish which adapter a future executable selects. In particular, do not infer native CPU support for native timestamp tags from the Level Zero path.

## Strata event distinction

`src/core/gpu.cpp::copy_async_after` submits a handler `memcpy` and stores the resulting `sycl::event` in `done->ev`. It uses the supplied prior event as a dependency; it does not create a timing event. `event_record` separately stores `submit_profiling_tag(queue)` (when selected by the runtime) or a barrier into an `Event`. `event_elapsed_ms` requires `Event::timing` and computes the difference of `command_end` values for two separately recorded tags; it does not query memcpy start/end. In `prefill.cpp`, `m.copied[]` events are created with the default `timing=false`, and the async-copy calls store the actual copy event there; they are then used as cross-queue dependencies. They are not timing-tag events and are not currently a per-copy profiling ledger. The API's “copied event” meaning must not be conflated with the distinct timing marker.
