The question is whether an opt-in full-stream route-zero branch can omit H2D for a nonresident expert once `cnt[e] == 0`, with the existing expert compute and float arithmetic unchanged. The source's current full-stream plan is built at chunk entry, before that chunk's layer routers run. Therefore it cannot decide active experts then. At each layer, routing IDs are copied to host and synchronized, `cnt` and expert-row prefixes are built, and `order` is formed in increasing expert ID for experts with `cnt>0` (prefill.cpp around 2080-2148). Only after that does the layer create/consume its MoE rows. A route-aware producer must receive this layer's counts after that synchronization; a chunk-start producer cannot know them.

## Actual compiled path and narrow opt-in seam

For `T >= STREAM_ALL_MIN` with `m.ring > STAGE` and a source, `stream_all` builds `seq` across `[LB, LE)` with each nonresident expert in increasing layer then expert order, assigning a host-stager job to transient/unpinned blobs and `job=-1` to pinned blobs (`prefill.cpp` around 1403-1441). The ring size is clamped to at least 16; normal large chunks use the configured/computed ring. It launches the issuer before layer execution (default enabled), and initially issues up to one ring. Each issue maps sequence ordinal `idx` to slot `idx % ring`; `copy_async_after` submits a copy-queue command that depends on the slot's last `used` event, then installs its completion as `copied[slot]`. The inline path uses the same sequence and ring mapping through `issue_until`; the threaded path writes `a_issued` after each submission, waits for `a_consumed + ring`, and is joined/drained by guards before the chunk-owned sequence/count/transfer vectors retire (around 1452-1556, 2909-2919).

After route grouping, the streamed consumer walks that layer's sequence while visiting active `order` experts. `release_to(e)` advances past intervening nonresident IDs: it flushes any pending native dequant batch or MMQ group, waits until the threaded producer published the entry, records a compute-stream `used` event and advances `consumed`. For selected nonresident experts it waits on `copied[slot]`, consumes the blob, and returns the slot immediately for ordinary dequant; native batched dequant and grouped MMQ delay slot release until the batch/group flush has finished reading. Resident experts use their cache pointers. This same schedule is duplicated in the non-MMQ Q2 and native branches (around 2518-2557 and 2786-2820).

Smallest safe experimental change: retain the all-entry sequence and its ordinal/slot mapping, but add a per-entry `copy_needed` bit populated **after the layer's route synchronization** from `cnt[e] != 0`; make the opt-in issuer/inline issuer acknowledge zero entries without `stager->wait`, `copy_async_after`, `issued_one`, DMA/transfer counters, or `stage_live` changes. The consumer's skipped-entry release must still advance its sequence ordinal and `consumed` protocol, but a zero-copy entry has no `copied` dependency and no current-blob reader. Do not blindly record `used` into a slot for a zero entry: it may alias an older ring incarnation. Model slot state by last actually submitted copy and its last-reader event, and only mark/replace that state for a slot that has an outstanding copied blob. The next actual copy to that slot still depends on its prior `used` event. Keep the existing flush-before-release rule so native dequant/MMQ readers have completed before their physical slots can be recycled.

Because the threaded issuer currently runs before this count bit exists, the simplest opt-in qualification should use inline issue (`STRATA_PREFILL_ISSUER=0`) and call route-aware issue as each layer reaches its post-router consumer. That isolates the scheduling contract and avoids a mutable-mask data race. If retaining a threaded experiment, use a per-layer producer: publish an immutable active mask only after route grouping; then start the producer, join it before that mask/sequence/layer tables change, and retain the existing checked compute+copy queue drains on success and every failure/unwind. Do not mutate a chunk-wide mask while the current producer may read it. This per-layer producer loses some existing next-layer prefetch opportunity; its timings could not alone characterize the current threaded policy. A more complex future producer could be fed immutable per-layer route sets, but later layers cannot be populated until their routers run.

Sequence cardinality remains all nonresident entries in this initial experiment, so ordinal and fairness are unchanged. A later optimization may construct compact active-only sequences, but then `seq_start`, routed-ID lookup, ring ordinal, `a_issued/a_consumed`, `native_hold`, and `release_to` all need one shared mapping; filtering independently in producer and consumer is unsafe. Do not sort by route count or quant type: `order` and row-prefix order are increasing expert ID; leaving it intact preserves each expert's token rows, grouped quant/dequant membership, and downstream per-row accumulation order. The optimization removes only transfer/staging work for an empty expert. It must not alter router calculations, route IDs/counts, quantization, activation arithmetic, dequantization of active experts, expert products, or shared-expert/combination order. Float outputs and state still need the existing correctness gates; no bitwise equivalence is asserted here.

## What zero-route can skip and what it cannot

A zero-count nonresident entry can safely skip its blob fetch/stager copy, H2D submission, copy-completion wait, native weight dequant/gather, and expert GEMM, because it owns no routed rows. It cannot skip the router, route-ID transfer/synchronization, host count/prefix construction, the ordered slot-release walk (or an equivalent mapping), or the expert rows/weights of any active expert. It also cannot skip a copy merely because it is zero-count at chunk setup: the decision only exists after that layer's route counts are available. It does not imply that the layer's entire MoE can be skipped: shared expert and downstream combination still execute. These are source-level possibilities only, not claims of link or time savings.

The active native model layout has seven GU/Down type pairs across 48 layers: 18/20 (14 layers), 18/42 (3), 21/20 (9), 21/42 (1), 22/20 (15), 22/42 (5), and 23/20 (1). The per-layer `blob_bytes`, offsets and native format must remain authoritative; do not infer a common copy extent or dispatch order from quant type. The direct consumers use `NativeFmt` layer fields and per-layer exact blob extent. No alternate dequant or conversion path belongs in this experiment.

## Dependency model and primary SYCL reference

Pinned implementation `src/core/gpu.cpp:242-253` submits `handler.depends_on(*after->ev)` when the prior slot event exists, then `handler.memcpy(dst,src,bytes)`, and stores the returned event in `done`. Thus event edges express the slot reuse dependency and copy completion dependency; merely advancing a host ordinal does not make a queued copy complete. The current consumer adds `stream_wait_event(m.cs, copied[slot])` before reading a copied blob, and records `used[slot]` after its last asynchronous reader. The ring's safe reuse proof is this event chain plus queue ordering and ownership, not host iteration order alone.

The Khronos SYCL reference documents that `handler::depends_on(event)` requires the represented action to complete before the command group executes and that `handler::memcpy` copies `numBytes`; the queue shortcut `memcpy(..., depEvent)` is equivalent to a command group with `depends_on` followed by `handler::memcpy`. Primary references: [SYCL Reference: command-group handler](https://github.khronos.org/SYCL_Reference/iface/command-group-handler.html), [SYCL Reference: queues and memcpy dependencies](https://github.khronos.org/SYCL_Reference/iface/queue.html), and [SYCL 2020 specification](https://registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html). These semantics support the event-edge description; they do not establish a specific backend's physical-copy behavior or performance.

## CPU-only fixtures that can expose schedule/lifetime defects

Factor a pure schedule model (no SYCL or project runtime) that takes sequence entries `(layer,expert,blob_bytes,copy_needed,job_kind)`, ring size 16, route `order`, and a fake set of completion/last-reader events. Test:

- All-zero, one-active, alternating active/zero, first/last expert active, and active entries on both sides of ordinals 15/16/31. Assert no copy/stager job for zero, exact active-copy set, monotonically correct `issued/consumed`, and no active slot reuse before the previous reader event.
- Distinct unequal `blob_bytes` on adjacent synthetic layers; verify each copy uses its layer's exact size and that a zero entry never overwrites the prior slot's pending state.
- A zero gap while `native_hold` spans an active group boundary, and a zero gap with grouped MMQ enabled. Require flush before returning any held ring slot; assert every held slot's `used` event follows its last fake reader.
- Inline and deterministic threaded-fake schedules must yield identical active copy order and slot/event edges. Gate producer progress with condition variables at ring capacity, at a zero entry, and at a simulated submit failure. Assert stop wakes the producer, join happens before sequence/mask/stager storage destruction, checked drains happen after no producer can submit, and failure cannot publish partial transfer counts.
- Invalid/out-of-range IDs and route-count inconsistencies fail before producer start; every valid active expert appears once in `order`, and every zero-count nonresident sequence item is acknowledged once. Include resident entries (not in the transfer sequence) and empty layer sequence.
- Preserve the exact seven production type-pair tags above as table-driven blob-size fixtures using the existing source layout metadata captured in the test—not a generic fixed-byte blob. These test heterogeneous extents and ordering without loading a model.

These fixtures test algorithmic schedule and host lifetime only. They cannot qualify SYCL event destruction, queue behavior, DMA, active mask publication in the compiled implementation, or numerical correctness; those require implementation-specific validation by the main workstream.
