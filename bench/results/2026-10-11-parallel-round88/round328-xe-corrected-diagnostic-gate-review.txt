Diagnostic shape and bounds
The controller derives argv and environment from the older owned receipt, replaces argv[0] with the v4 linked executable, and sets issuer mode OFF. It checks actual /proc executable identity/hash and exact environment equality after READY. The prior environment key set includes UR/Level Zero loader/validation logging controls; this report intentionally records no values. Note that the controller currently serializes the complete target environment into record.json and every direct-owner command entry, so the eventual run should not put secrets in that environment or expose the raw receipt.

The prompt is built from 8,144 fixture IDs plus the final 49 IDs: 8,193 total prompt tokens, of which 8,192 are batched positions. Validation requires prefill progress at 4,096 and 8,192, one completed request with one generated token, a fresh-state marker, one T/LP5 pair, finite values, and token-domain checks. It makes no ability, quality, or performance claim. READY must advertise context 262,144; effective context/KV/expert/pool/spec settings are checked, and reported free VRAM must be at least 512 MiB before GEN.

The direct owner bounds the model wall time at 210 seconds; protocol waits are 120 seconds for startup lines, 90 seconds per request line, and 30 seconds for final exit. It polls for a new dump while the process is owned. On failure it records the exception and uses pinned pidfds to close its own session; it does not retry. The final pass predicate requires a completed request, closed owner, successful kernel and post-model health gates, unchanged boot, and no recorded error. The post-model integer health probe is only run after request completion; an incomplete/failed request does not trigger another GPU diagnostic. These are useful stop/no-extra-GPU safeguards.

Unresolved diagnostic and failclosed gaps
1. Level Zero/UR logs are captured but not made an auditable pass/fail input. The owner stores raw stdout and stderr with caps and hashes; run_root.py parses stdout into protocol lines and only rejects lines starting with ERR while waiting for a response. Other text is tolerated and the validator selects expected protocol prefixes. Stderr is not inspected. There is no requirement that the expected loader/runtime trace be present, no compact per-chunk log-progress record, and no classification gate for Level Zero/UR error markers. Therefore a successful T/LP/DONE transcript plus clean kernel gate could still pass when an error-level UR/Level Zero record was emitted to stderr or as a tolerated stdout line. The full raw logs are available under the owner output directory, but the receipt alone gives their filenames, byte sizes and hashes, not their contents or whether logging advanced through each chunk. This is the main observability gap for the requested first reproduction: it weakens the ability to tell where the second chunk progressed and makes the runtime logging configuration informational rather than a failclosed check.
2. The kernel interval check is intentionally useful but narrower than “all new kernel/runtime errors.” It keeps messages mentioning the device BDF or word xe, then tests only the helper's FAULT regex. The historical R309 CAT18/fault-response/UR40 incident strings include a CAT memory error and failed fault response; those two kernel categories are covered by the current regex. UR40 / UR_RESULT_ERROR_OUT_OF_RESOURCES itself is not checked in captured model stderr, and a new relevant Xe message outside the regex is retained as a device entry but does not fail the gate. Thus this gate catches known kernel fault/reset signatures; it is not a general Level Zero/UR error gate.
3. Health success has no freshness bound. The R3 receipt passed on the current boot at 2026-10-10 17:35:11–17:35:12 UTC, with one exact integer-health round and an empty post-probe kernel interval. At this review time (17:58:47 UTC) it is about 23 minutes 35 seconds old; the v4 link completed at 17:42:42 UTC, about 7 minutes 30 seconds after the health probe. run_root.py requires same boot and passed/inactive status, but does not cap health age or require a new health observation immediately before the model. Same-boot identity prevents cross-reboot reuse, not intervening degradation. This is a bounded-staleness admission gap, not evidence that the device degraded.

Decision
The controller is strongly bounded on process ownership, request shape, no-retry behavior, READY/VRAM admission, and mandatory post-model health for a completed request. It is not ready to launch against the currently edited source tree because v4 source pins no longer match; that is an effective prelaunch failclosed result. After the stated v5 qualification and link update, the first-debug evidence still needs an explicit Level Zero/UR log presence/progress and error-classification gate, and a documented maximum age for the health receipt. Until those are resolved, any eventual output should remain a diagnostic/fault result and must not be treated as a performance comparison.
