Finding: a caught Stager worker exception permanently poisons the reused Stager instance

`Stager::work` catches an exception from `event_sync(dma_done[b])` or the source copy at prefill.cpp:315–326, stores it in `Stager::failure`, marks the current job ready/failed, and cancels the Stager. Outer cleanup joins the workers. On a later run using the same Prefill/Impl, `Stager::start` at 342–356 resets `cancelled`, `failed`, jobs, and `issued`, but never clears/replaces `failure.first_`. Every later `Stager::wait` calls `failure.rethrow()` at 364, so it throws the old exception even if the new worker operation succeeds. If the next generation has no waitable job, `StagerDone::complete` still calls `failure.rethrow()` at 1324. This is fail-closed (no false success), but it is a concrete recovery/reuse defect: after a transient worker exception, future requests on the same Prefill fail until release/reset reconstructs the Stager. Recovery must explicitly reset the failure state only after prior workers and queues are quiescent, or mark the Prefill terminal and make that lifecycle contract explicit. This finding concerns the Stager Failure member, distinct from the per-run issuer_failure, which is freshly constructed at 1369.

Failure-flow checks

- Issuer submission/event failures are now converted to exceptions by `publication::require`. The issuer lambda catches all at 1416–1420, captures the first exception, publishes stop, and cancels the Stager. `wait_issued` checks failure and stop before accepting `a_issued > k` (publication.hpp:26–36); `give_back` rechecks failure (prefill.cpp:1430–1434). The normal chunk joins and rethrows at 2325–2328. A producer exception therefore cannot be masked by an already-advanced issued counter at these consumer gates.
- The issuing thread's plain `stage_live`/`used_of` metadata is published before the release-store to `a_issued` (1402–1414); consumer acquire-load in `wait_issued` precedes its use. Ring reuse is handed back with consumer release-store `a_consumed` and producer acquire-load (1391–1397). `skipped_entry` flushes queued group readers, waits for producer publication, then records the reuse event and updates slot metadata (2210–2217). I found no unsynchronized access in these specific handoffs.
- Stager waiters observe worker completion with `ready` release/acquire. Worker catch records the exception before publishing `ready`; failure is read under the Failure mutex. Cancellation sets the terminal high value in `issued` and notifies waiters (373–376). `publish_staged` uses monotone compare/exchange, so a racing normal `j+1` cannot lower that sentinel (publication.hpp:38–45). The sentinel is far above this sequence's expected job indices. These changes close the prior lost-wakeup/false-publication pattern in this helper.
- Worker `active` is decremented after either success or catch, and `finish` prevents more claims and waits for active workers (prefill.cpp:301–329, 378–384). Stager destruction calls finish, signals quit, joins every worker before destroying its events/buffers (281–289). The issuer RAII guard cancels, joins, then drains (1373–1385). In ordinary in-scope return/exception unwinding, declaration order destroys the issuer guard before the chunk StagerDone guard; a joinable issuer is not destroyed directly. I found no joinable-thread destruction or cancellation deadlock in those paths.
- Normal completion checks both stream drains in `StagerDone::complete` before finish and rethrows worker failure (1315–1325); the outer completion also checks the stream sync around 2343–2347. Submission/check failures caught by the outer run handlers return false (2465–2474). The exceptional RAII destructors intentionally ignore drain return values (1327–1334 and 1378–1383), and catch handlers also ignore best-effort drain results (2467–2473), but those paths are already unwinding an error and return false; this does not turn the observed error into success. It does mean cleanup cannot report a secondary drain failure separately.
- `Stager::start` itself does not join/finish an earlier generation. Current call sites rely on prior layer/chunk completion/guard cleanup to establish quiescence. The worker-failure path's cleanup does so. The stale Failure state above remains the specific reuse bug found.
