# R365 — Xe e32 full-path measurement controls

Date: 2026-10-11 (Asia/Tokyo). Read-only source, report, registry, and official-document audit for the current Xe e32 handoff worktree. No build, test, compiler/runtime or device query, GPU execution, profiler execution, process/service query, Git operation, cleanup, or source edit was performed. The only write is this report. `prefill-gemm-only-contract-root-v1/record.json` was not read.

## Decision

The evidence supports a controlled, staged measurement plan, not choosing a kernel or transfer optimization by intuition. Use two evidence lanes: (1) quiet end-to-end runs with timing/profiling controls off to establish actual latency and output status; (2) separately labelled diagnostics to locate service and wait. Run the exact same source/input/config under `free` and `contrib-llvm` (`STRATA_ONEMKL=OFF` vs `ON`) because the principal dense prefill GEMMs switch from XeStrata's own kernels to oneMath/oneMKL. Keep prefill, decode, and whole-request wall as separate results. Never add phase counters to derive a request critical path.

R344 already proposed `--hw-bench`, `--kernel-bench`, and the source phase timers. R365 updates that plan against the current `fix-xestrata-e32-host-handoff-20261011` source: the concurrency protocol is now refused by source and the verify path is segmented by queue completion; small-chunk prompt CPU expert sharing is disabled. This source difference changes what a future production run measures. It does not establish runtime correctness, pass the whole model's safety/quality gate, or authorize using VTune/unitrace to probe a rejected/pristine route. The current B570 safety/ownership gate and full-context/restore qualification still control any model execution.

## Current source entries and route semantics

**Build arms.** `CMakeLists.txt:31-55,100-118,474-498` declares `free`, `contrib` (the contrib-llvm build mode), and `contrib-icpx`; on Intel GPUs the `contrib` arm's `STRATA_ONEMKL=auto` enables oneMKL when an Intel card is found, while `free` forces it off. `src/prefill/gemm.cpp:145-170` reports the selected `Gemm::path()`: oneMath (oneMKL) for supported dense products, with XeStrata's own kernels for the rest; otherwise the own kernels handle dense products too. The source/docs state that `STRATA_NO_BLAS=1` forces own dense kernels in contrib-llvm. `STRATA_NO_XMX=1`, `STRATA_NO_BF16_MMA=1` and `STRATA_NO_INT8_MMA=1` are real kernel-path controls; they test alternatives and must be separate labelled arms. Do not claim a no-XMX or no-BF16 run disables oneMKL—`STRATA_NO_BLAS` is the explicit backend bypass. `--kernel-bench` prints `Gemm::path()` and has default, no-XMX and no-BF16-MMA sweeps in `tools/bench.py:306-327`; these are synthetic kernel runs, not a production request. Capture effective CMake cache/build identity and the `Gemm::path()` line for each arm; source tree equality alone does not prove the two binaries used different backends as intended.

**Prompt phases.** `STRATA_PREFILL_TIMING=1` is present in `src/prefill/prefill.cpp:1094-1130,1159,2450-2465`. It reports the prompt's ordered compute-stream marker timeline by phase, request wall, host staging, chunk setup, chunk waits, after-chunk work and PLE. Its marker-to-marker intervals may charge host lookahead/staging gaps to the preceding phase; they are queue timeline buckets, not exclusive kernel execution. The R212 audit specifically found that a large Down-labelled marker interval can include host delay before its following mark. Do not convert it to oneMKL busy time or sum it with request wall. It does not yet provide a complete production H2D/D2H bytes-and-service ledger or a kernel dependency graph.

**Decode/CPU pool.** `STRATA_DECODE_TIMING=1` exists at `src/program/generate.cpp:9031-9046,9778-9797`; it reports request windows, average T/tokens per window, decode wall, verify (GPU-reach wait, per-layer host, staging), commit/emit, draft and before-window/adaptation time, plus CPU expert/entry, VRAM-hit and PCIe-expert counts. `--stats` (`generate.cpp:657,10840-10905`) adds verify wait/pool/host/commit, CPU GU/quantize/Down pool times, dispatch plan/ActQ/jobs/run, residency/file tier, and MTP stats. These are useful, existing controls, but their durations are host stopwatch spans around concurrent work: GPU-reach wait is not pure GPU time; pool-call/GU/Q/Down spans can overlap device execution; dispatch `plan/actq/jobs/run` are nested cumulative sections, not four serial pieces of total decode wall. Expert byte extents and PCIe expert counts are logical counts, not physical RAM/PCIe traffic. Do not sum them, subtract them from total wall, or call the remainder launch overhead.

`STRATA_VERIFY_PROFILE=1` enables device-side stage stamps only if `gpu_stamp_available()` finds a device-scope clock (`src/core/verify.cpp:346-365,1261-1290`; report at `generate.cpp:10840`). It prints ticks per window by GPU phase, not milliseconds absent a calibrated clock conversion. The known B70 source docs say it lacks this clock; no current B570 runtime query was made here, so eligibility is unknown. `--stage-timing` reports kernel-count shares, not elapsed time. `STRATA_POOL_TRACE=1` is a very chatty one-line-per-layer/step progress log, not a duration measurement. `STRATA_TRACE=1` reports startup free VRAM and chunk progress, not a profile. There is no `--quiet` CLI switch in the current generate help; the quiet baseline means leave timing/trace env vars unset and omit `--stats`/profiler, while preserving the stdout tokens and measured wall externally.

**Current B570 safety logic.** Current `include/strata/core/gpu.hpp:41-48` hard-returns `false` from `host_handoff_concurrent()` because the live Xe control protocol uses volatile accesses and a capability report cannot validate that protocol. `src/core/verify.cpp:410-425` therefore selects segmented, queue-completed windows by default; `session.cpp` refuses token graph paths when the protocol is unqualified (`:843-844,917-918`); and `prefill.cpp:137-142,1781` forces CPU prompt sharing off until concurrent host-USM access is qualified. This source-level safe routing is different from the pristine official source refused by R352/R354 and from the earlier conditional host-USM overlap in R351. It is not an observed validation of the e32 model path. Keep any measurement on the current corrected source and its enforced safe route; do not pass `--no-capture`, `--no-token-graph`, a profiler, a visibility probe, or an env override off as evidence that a refused concurrent handoff is safe.

## Measurement order after the existing gates permit execution

1. **Pin conditions before measuring.** Use identical pack/hash, prompt token IDs/hash, output count, context size, cache/adaptive/MTP settings, device, queue policy, worker count, environment and compiler/runtime/driver for both arms; record all effective options and `Gemm::path()`. Use fresh sessions without restored/prompt-cache state. Run on an idle device, never alongside builds or other GPU work. For each size, record exact request tokens, batched prefill positions, the last prompt-token step, generated outputs and end-to-end wall: the source routes the final prompt token through decode, so “32K prefill” is not necessarily exactly 32K batched positions. Choose matched >=32K and >=64K actual input sizes, then keep prefill and a fixed decode output count as separate report rows.
2. **Establish clean wall first.** With timing/profiler/trace controls off, perform a small repeated series for each build arm and size, sequentially, after identical runtime warmup. Keep every sample, median/range, output/state/correctness status and process/build identity. Record fresh-request prefill wall, decode wall and whole-request wall independently when source/harness exposes them; never derive one by subtracting overlapping counters from another. Quiet series alone answers “did it get faster?”.
3. **Take hardware/shape references without production phase claims.** The existing round53/54 B570 suite is already a strong effective reference; do not repeat it simply because the build changes. It measured seven samples per cell and three fresh processes, serially, with Direct Submission and Level Zero v2 copy offload disabled. Across process medians: six-core 512 MiB RAM read 36.87 GB/s, non-temporal logical copy 37.58, cached copy 22.95; host-USM H2D 6.447 GB/s and D2H 5.643; pageable H2D 4.605 and D2H 5.295; VRAM queue-copy 330.07 GB/s in logical read+write bytes. Synthetic oneMKL FP16-input/FP32-output GEMMs: large M=8192 GU 52.69 TFLOP/s and Down 41.61; small M=8 hot GU 1.92–2.70 and Down 1.22–1.48 across processes. These are effective test rates, not physical memory-controller counters or production demand. Host RAM arrays were 512 MiB, not evidence of a 64-GiB bandwidth sample. Encoded external PCIe Gen4x4 is 7.8769 GB/s/direction by spec arithmetic, not a measured installed-link or sustained request rate. The existing hardware results use oneMKL for the dense GEMM; they do not establish the free build's own-kernel ceiling. After build identity is complete, `--hw-bench` can be repeated only if the compiler/runtime/link changes plausibly change copy service; preserve all bursts, not fastest-only output. `--kernel-bench` should be run independently under free and contrib-llvm with path labels and relevant `STRATA_NO_BLAS` control; its dense BF16 and expert products are synthetic (expert M=64 and first-layer format/type), so collect actual pack format and production row histogram before applying a result to live prefill.
4. **Run separate timing diagnostics.** On same-size fresh inputs/configs, one diagnostic pass with `STRATA_PREFILL_TIMING=1` (decode timing/profile off) gives the prompt phase view. A separate pass with `STRATA_DECODE_TIMING=1` and `--stats` (prefill timing off) gives decode/CPU pool sections. If device clock support is proven, `STRATA_VERIFY_PROFILE=1` can be a third separately labelled pass; it is not part of latency. Preserve the full diagnostic output, effective input/positions, queue/wait status and exact backend path. Compare each timed pass to its matched clean-run distribution to quantify perturbation; diagnostics are never substituted for quiet latency. `STRATA_POOL_TRACE` is only for one bounded fault-progress reproduction, not the normal profile series.
5. **Join the missing causal evidence before selecting optimization.** The present source counters cannot answer all requested questions. Add an opt-in, bounded diagnostic receipt on the post-gate branch: (a) phase-level software wall spans around prefill chunk setup, submit, explicit queue wait, transfer completion, oneMath call, head/output, and layer boundaries, all on one host steady clock; (b) exact transfer copy bytes/counts by direction/source with queue events only at existing completion seams (not one event/mark per expert); (c) exact routed job histogram `(phase/layer, native format, NT=1..4, unique expert jobs/entries)`; (d) per-pool-worker active CPU duration plus completion-tail and barrier/park duration, aggregated at request end instead of per-job logs; (e) oneMath returned event/kernel spans if the backend exposes them. Pair these with request wall and a trace/dependency DAG. For critical path, use interval union and predecessor/consumer relations; never add workers' inclusive CPU time to GPU intervals. If implementing these counters would add synchronizations, event marks, or change copy order, treat it as a distinct perturbed diagnostic run and validate it against the quiet series. Candidate per-kernel GPU hardware counters are optional and strictly gated by enumeration/permission; a missing group is unavailable, not zero.

## What distinguishes bottlenecks

- **GPU arithmetic/dense GEMM:** current `Gemm::path()` plus `--kernel-bench` by backend and shape, then production prefill phase spans and actual oneMKL kernel/activity trace after the safe-route gate. A large marker bucket alone does not prove compute saturation.
- **CPU expert service or RAM:** same-request `(format, NT, layer)` job demand, `ms_run`/worker tail and worker active/parked time; compare to the recovered effective RAM reference, not to `packed bytes ÷ RAM GB/s` as if those were DRAM bytes. Existing counters lack physical memory-controller bytes and per-worker wait/tail.
- **PCIe/host staging:** exact bytes and actual event/service spans by source and direction joined to the prefill/decode critical path. `h2d/d2h` HW probes and decode PCIe-expert count alone cannot show transfer demand, overlap, or exposure. Sysman PCI/VRAM counters are device-wide and require separately established support/permission; do not change observation settings here.
- **Host control/launch/rendezvous:** host submit-to-completion/wait spans plus dependencies that show the GPU had no queued useful work. `ms_wait`, `ms_host`, and cumulative pool dispatch intervals are not a launch-gap sum. An idle gap must be observed on the exposed critical path before choosing host-control optimization.
- **Attention/context cost:** `qsa indexer`, `select`, and `attn` prefill phases and verify-profile attention ticks distinguish its direction; compare 32K and 64K fresh cases with same other settings. The phase timers still include queue-gap attribution; need matching kernel activity or targeted returned events before claiming an attention-kernel ceiling.

## VTune, PTI/unitrace, LLVM22 boundary

The source tree's `docs/DEVTOOLS.md` documents VTune 2026.4 `gpu-hotspots` for Xe and metrics-discovery, but also records that VTune XPU-Offload and unitrace stalled the engine in prefill for minutes; it directs them to small programs/probes, not the engine. No profiler should be used to bypass the rejected official/pristine path or the independent current host-USM gate.

Official docs show broad technical applicability, but do not close exact stack compatibility. VTune's SYCL cookbook lists the oneAPI DPC++ compiler and Intel Graphics; its 2026.4 release notes say GPU Hotspots/XPU Offload fixed reused Level Zero command-list and SYCL-graph tracing, while explicitly excluding native graphs. PTI `unitrace` README supports SYCL/Unified Runtime XPTI tracing (`--chrome-syclrt-logging`, `--chrome-ur-logging`), with UR described as the newer successor to the SYCL Plugin Interface. None of these primary sources certifies this custom intel/llvm v7.1.1/LLVM22 runtime build, the exact XeStrata Level Zero graph form, or the local driver and model execution. Hence: VTune GPU Hotspots is a conditional isolated diagnostic candidate after a standalone microprobe proves collection and output completeness; it is not currently admitted for the engine. Do not treat old `SYCL_PI_TRACE` assumptions as proof for the Unified Runtime path; unitrace's UR/XPTI tracing is the documented modern interface, but the local prior stall still blocks a production engine run until separately qualified. `STRATA_VERIFY_PROFILE` is an existing built-in alternative only if B570 device clock is available and validated. Do not alter `observation_paranoid`, driver settings, or runtime flags to make a profiler work.

Primary references: [VTune SYCL GPU profiling cookbook](https://www.intel.com/content/www/us/en/docs/vtune-profiler/cookbook/2025-0/profiling-dpc-application.html); [VTune 2026 release notes](https://www.intel.com/content/www/us/en/developer/articles/release-notes/vtune-profiler/current.html); [PTI unitrace README](https://github.com/intel/pti-gpu/blob/master/tools/unitrace/README.md). The first says SYCL profiling uses oneAPI DPC++; current release notes describe Level Zero command-list/graph coverage and native-graph exclusion; PTI documents UR/XPTI options and does not state a particular LLVM 22 runtime qualification.
