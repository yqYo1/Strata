## Conclusion

The specific `--spec 4`, `prompt=C-1`, `max_new=1` direct MTP-overrun example in R362 does not execute in the ordinary standalone caller. The request passes initial `prompt+max_new<=C` admission, but the non-native token loop emits the first output and breaks at `produced.size() >= o.max_new` before setting `spec_pos`; the speculative block is skipped. The native path enters the speculative block with a one-row first window, emits the one output, and short-circuits `mtp.draft()` once the output budget is exhausted. Neither path reaches `draft_first` or a post-commit MTP draft for this one-output example.

For ordinary standalone generation with **effective MTP depth four** (`max_steps=3`) and default `STRATA_MTP_CATCHUP_ALL=0`, the current MTP candidate writes are also bounded by the accepted prompt/output budget whenever the helper is reached. The verifier can still refuse an admitted edge request because it checks the full fixed window rather than shortening it; that is an early-termination defect distinct from a physical MTP cell overrun.

A real standalone counterexample remains reachable for a wider MTP depth, and another is reachable at depth four when `STRATA_MTP_CATCHUP_ALL=1`. The MTP helper still has no logical-capacity guard, so arbitrary/future callers are unsafe independently of these normal-call proofs.

## Standalone entry state and invariant

Parser admission requires positive `max_new` and `prompt + o.max_new <= C` (`generate.cpp:2347-2351,2901-2905`). Let `N` be prompt length, `M` the parsed `o.max_new`, `C=max_context`. Thus `N+M<=C`. `produced` starts empty, `tok=tokens[0]`, `pos_start` is zero unless batched prefill starts later, and `spec_pos` starts at zero (`generate.cpp:5409-5412,11603-11611`).

For a non-native pack, the token loop processes through the last prompt cell `N-1`. It appends the first output there; if that reaches the requested count it breaks before assigning `spec_pos=pos+1` (`generate.cpp:11987-12002`). If another output is requested and speculative decoding is enabled, it sets `spec_pos=N`, leaves `tok` as the just-sampled first output, and exits the prompt loop. The spec block itself is gated by `spec_pos>0 && produced.size()<o.max_new && !ended` (`12012-12013`). When entered, it initializes `p=spec_pos`, `x=tok`, and `first_window=false`, then invokes `draft_first(o.spec, ..., cell=p-1)` before the first verifier `p+T` check (`12227-12250,12321`).

For a native pack, the prompt token loop sets `spec_pos=pos_start` and exits before token work; `pos_start` is the last prompt position for the ordinary full-prompt path. It starts with `p=N-1`, `x=tokens[N-1]`, `first_window=true`, so first verifier width is forced to one (`11738-11740,12227-12228,12288-12289`). After that window it emits the first generated token. If the output budget remains, it calls `mtp.draft(T=1,p=N-1,a=0)`; if not, the `produced.size()>=max_new` disjunct skips the call (`12412-12426`).

After first output in either ordinary route, the state relation is `p = N + produced_count - 1`: non-native starts the speculative loop with `p=N, produced_count=1`; native advances from `(N-1,0)` after its first one-row window to `(N,1)`. Each later verified window accepts `a+1` outputs at most, advances `p` by `a+1`, and increments produced by the same amount (`generate.cpp:12412-12426,12431-12435`). If output remains, the draft call is made only after the emit loop and after the count has been updated. `draft_first` is the one exception to that post-commit ordering, but is called only on the non-native path after one output has been produced and while the original budget still has room.

## MTP row arithmetic and effective depth

`MtpDrafter::draft()` has no check against `st_.max_cells`. It optionally changes catch-up `T` to `a+1` when `STRATA_MTP_CATCHUP_ALL` is false, writes catch-up row cells `p..p+T-1`, then writes candidate row cells `p+a+j` for `0<=j<max_steps`, where `max_steps=min(max_t_-1,max_drafts_)` (`mtp.cpp:1534-1564`). A candidate row's cell and exclusive step are stored in the MTP staging arrays. `draft_first()` writes residual rows, makes a repeated-token vector, and delegates to `draft(T, ..., cell, a=0)` without an extent check (`mtp.cpp:1955-1970`).

The parser may transform a requested width: with default positive `--suffix-draft`, raw `--spec 4` becomes verifier width 6 and sets `mtp_max_t=4`; MTP proposal depth remains capped at three. With `--suffix-draft 0`, raw/effective spec 4 has three MTP candidates. `--lookup-chain` may widen the verifier window up to eight while preserving its MTP cap. `--spec 8` stays at eight, and MTP depth can be seven (`generate.cpp:2268-2279,12264-12265`; MTP load/cap setup at `3973-3985`). The proof below uses actual `max_steps`, not just the user-facing raw `--spec`.

### Why effective spec4 with default catch-up does not overrun candidates

For non-native `draft_first`, the first call occurs only when `M>=2`; hence `N<=C-2`. Its seed cell is `N-1`, and with three candidate rows the maximum is `N+1<=C-1`. With native input, after its first one-row verify the same `p=N-1` seed gives the same bound. Default catch-up only processes `a+1=1` row on these first calls.

For a post-commit draft with three candidates, the last candidate is `p+a+2`. The helper is skipped if `produced_new>=M`. If called, `produced_new=produced_old+a+1<M`, so `a<=M-produced_old-2`. Using `p=N+produced_old-1`, the last cell is at most `N+M-1<=C-1`. In the special “one output remains after this round” case, `p_next=p+a+1<=C-2`; equivalently the draft base `p+a=p_next-1<=C-3`, so `j<=2` reaches at most `C-1`, as Main suspected. Default catch-up only writes through `p+a`, also in range. This is a source-level algebraic bound for the existing standalone caller and the effective three-candidate depth; it does not add a guard to the public helper.

### Reachable wider-depth candidate overrun

Use `C=32`, `N=30`, `M=2`, `--mtp`, effective `--spec 8` and `--spec-min-p 0`. Parser admission passes exactly (`30+2=32`). For the native route the first verify at `p=29,T=1` emits output one; the post-commit call is `mtp.draft(T=1,p=29,a=0)`. For the non-native route, after emitting output one the prompt loop sets `spec_pos=30`; the pre-loop `draft_first(T=8,cell=29)` delegates to `draft(T=8,p=29,a=0)`. With default catch-up-off, either call uses seven candidate rows, cells `29,30,31,32,33,34,35`. Cells 32–35 are outside the logical extent `[0,32)`. In the non-native route this happens before its later `p+T` verifier check; in the native route the first width-one verifier passes and the MTP draft overrun follows immediately. The ring slots do not enlarge `max_cells`; the later verifier refusal cannot undo earlier out-of-range MTP staging/submission. The chosen zero probability threshold ensures the current draft path asks for all seven outputs; finite positive thresholds can shorten the executed step chain, but the host row records are still staged up front.

### Reachable effective-spec4 overrun with catch-up-all

Use a non-native pack, `C=32`, `N=30`, `M=2`, `--mtp --spec 4 --suffix-draft 0`, and `STRATA_MTP_CATCHUP_ALL=1`. This is admitted and produces one prompt-loop output, leaving one output requested. `spec_pos=30`, so `draft_first(T=4,cell=29)` runs before verifier admission. Catch-up-all leaves `T=4`; its catch-up rows are cells `29,30,31,32`. The fourth staged cell is outside `[0,32)`. The later verifier window at `p=30,T=4` would be refused (`30+4>C`), but only after the MTP call. This is a different mechanism from excessive draft depth: even with three candidate rows (cells 29–31), the unchecked full-window catch-up writes cell 32. With default suffix lookup enabled, raw `--spec 4` is widened to six verifier rows while MTP depth is still four; catch-up-all then stages still more rows, so it does not remove this edge case.

## Excluded edge examples and distinct failure

- **`N=C-1, M=1`, non-native:** after the final prompt position creates the one allowed output, the `produced>=o.max_new` break occurs before `spec_pos` is set. The spec block and `draft_first` are not reached.
- **`N=C-1, M=1`, native:** first window is one row at `p=C-2`; it emits the one output. The draft conditional sees the exhausted output budget and skips `mtp.draft`. No direct MTP out-of-range position is reached.
- **Effective spec4, catch-up-off:** the valid `N=C-2,M=2` request reaches an in-range initial three-row draft at cells `C-3..C-1`, then the fixed verifier window fails `p+T<=C` before a post-commit draft. It can terminate early despite initial prompt/output admission, but that is not proof of an out-of-range MTP cell.
- **`--spec-oracle` without MTP:** oracle-proposed window rows do not invoke `MtpDrafter`. With MTP enabled the standalone window construction selects the MTP drafts; the oracle does not change the MTP position arithmetic (`generate.cpp:12328-12331`).
- **`--spec-follow`:** the speculative-block entry tests the original `o.max_new`; the local follow-clipped `max_new` is set inside the block before `draft_first`, but `draft_first` is outside the `while (produced < max_new)` loop and is not separately gated by the clipped value (`generate.cpp:12012,12029-12033,12248-12250`). A shorter follow file therefore does not make a risky initial `draft_first` unreachable if the original budget exceeds `produced`.
- **`first_needed()`:** this is a lower-bound optimization for MTP prompt K/V lookback, used in `Prefill::draft_kv`/`MtpDrafter::prefill` to skip old cells (`mtp.hpp:153`; `prefill.cpp:1323`; `mtp.cpp:1353-1354,1415,1493`). It does not bound the upper cell in `draft()` or `draft_first()`.

## Serve and other callers

Ordinary text `GEN` admission rejects unless `n+max_new+8<=C` (`generate.cpp:9497-9500`). Serve starts at `p=n-1`, `produced_n=0`, with a one-row first window. It emits and commits accepted tokens, increments `produced_n`, then calls `mtp.draft` only if output remains; next position advances by `a+1` (`10345,10362,11220-11223,11243-11255`). The same invariant is `p=n-1+produced_n`. The MTP candidate depth is at most seven, hence candidate maximum after a draft is bounded by `n+max_new+3<=C-5` when any output remains. If catch-up-all is enabled, its span is the just-verified `T` rows and the source already checked `p+T<=C` before verifier execution. The eight-cell request margin covers the standard verifier cap of eight. It blocks the standalone minimal examples before execution.

Suffix lookup can raise verifier width, but `S` is capped at `kVerifyMaxT=8`; lookup-chain adds only verifier proposal rows within the same `p+T<=C` check. The MTP's own proposal depth remains capped by `S_mtp-1`, while catch-up-all uses only the already-bounded verified window. The optional two-GPU pipeline uses `chain_launch`, not ordinary `draft`; its `n_out` is at most seven. It is launched only when another output remains. If `p_next=p+a+1` is the next position after the committed prefix, the largest chain row is `p+a+6=p_next+5`; the request margin leaves this inside context. Batch MTP is still narrower: each slot has one proposal, commits two rows only when `sl.produced+2<=sl.max_new && sl.p+3<=C`, and otherwise retains one (`generate.cpp:3995,8840-8847`). These are caller safeguards, not a general helper invariant.

## Limits

This is source arithmetic, not a runtime observation. It identifies logical cells equal to or greater than `C` that the current helper can stage and submit; it does not predict whether a particular backend faults, wraps, or accesses a mapped allocation beyond the logical page-table contract. It does not resolve the runtime host-USM admission barriers in R352/R354/R362, qualify numerical behavior, or make any performance claim. The safe effective-spec4 proof applies to the audited standalone caller with the stated admission, output-count, and default catch-up conditions; the helper remains generally unguarded.
