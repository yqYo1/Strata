Main's stock 4096-chunk GPU measurement remains active and was not approached. No build, test, runtime, GPU, profiler, Git operation, cleanup, source/product change, or broad environment/log scan was performed. Only this report was written. ## Finding

The concrete decode-capacity candidate is to release `Prefill`'s owned device workspace after a serve request has finished all prompt chunks, checkpoints, cache refill, and any prompt-side MTP K/V work, then lazily initialize that prompt object before the next request needs a batched prompt. In the current serve path, `sp` and each split-stage `sp` live for the entire server loop. The normal prompt completion refills borrowed expert slots but does not call `sp.reset()`. When `--no-prefill-borrow` is selected, `Prefill::init` allocates its carve from owned device buffers; those remain attached to the long-lived `sp` through decode and between requests. This is an avoidable decode-time VRAM hold if a request-boundary reset/reinit can preserve callbacks, queue ordering, stage state, and next-request behavior.

With normal borrowing and a profile, the prompt workspace instead occupies a calculated tail region of the expert cache only while reading batched prompt chunks. Before a verify window reads, those slots are refilled with the same expert blobs, the residency table is restored, and the hit path sees the full expert cache. Borrowing therefore removes a separate persistent VRAM reservation and does not require moving decode graphs, MTP weights, KV/session state, or live decode weights to RAM. Its costs are prompt-side temporary cache capacity and refill transfer/time. It is the preferred capacity path when exact slot geometry admits it; `--no-prefill-borrow` remains a distinct prefill/decode arm, not a universal improvement.

The 70 tok/s goal is not supported by a single bandwidth ceiling from current data. The 982,272,000 B/top-10-row figure is logical selected expert extents, not actual DRAM reads. The 128-slot cache's reported 268.60 MiB occupied weights and the stock 1.9% lookup hit rate describe only one aspect of serving; neither alone establishes the CPU traffic, VRAM room, or critical path. MTP acceptance and split grouping change bytes and time per emitted token, so they must be measured together with actual miss ownership and timings.

## Actual prefill borrow and allocation lifecycle

In `src/program/generate.cpp`, `Options::no_prefill_borrow` defaults false and `--no-prefill-borrow` flips it true (around lines 362–364, 1255). The admission predicate is `pf_borrow = !no_prefill_borrow && !expert_profile.empty()` (2499). The cache-sizing code accounts a rough chunk-based prefill reserve only when `!pf_borrow`; the exact serving loan later uses `Prefill::bytes_needed(g, session, chunk)`, not that estimate (2493–2509; 4269–4340). In serve, the no-split `sp` borrows from the tail of `xcache`; each layer-split stage borrows from the tail of its own cache. The planner walks back from the last cache slot until its actual byte extent fits `bytes_needed`, and requires at least a 128-slot floor (`fits_one`, around 4305–4339). Sized per-layer slots use offsets and real byte extents; total cache GiB or nominal slot count alone is insufficient to prove a loan fits.

With no profile, `--no-prefill-borrow`, or too few lendable slots, the prompt path uses its own device buffers. `Prefill::init` carves GEMM scratch/workspace plus the rest of the chunk buffers from the borrowed region if supplied, otherwise via owned allocations (`src/prefill/prefill.cpp:181, 665–779`). The serve object is initialized once before the request loop (`generate.cpp:4480–4491`). Request-level `lend()` temporarily marks resident entries in the actual tail range not resident; `refill_issue()` copies the exact layer/expert blobs back to the same slots, `refill_wait()` waits for queued fills and clears the lent list, then the source uploads the restored residency table (`generate.cpp:5653–5705, 5710–5760). After prompt reading, `refill()` is called before the first verify window (`5817–5859`). Thus borrowed slots are free for prompt buffers only during the prompt phase; they are again expert cache during decode. Short requests can lend fewer slots than the configured maximum; the loan is based on that request's prompt size.

`Prefill::reset()` calls `release()`, which synchronizes compute/copy queues and frees `Impl::owned` device buffers, then installs a fresh `Impl` (`src/prefill/prefill.cpp:541–565`). The standalone generate path already resets after its only prompt and before token generation (`src/program/generate.cpp:6347–6349`). The serve path currently resets only during failed initialization/chunk retry (`4546–4549`), not on ordinary request completion. That is the narrow existing lifecycle seam: after prompt and refill have completed, between request prompt processing and decode, owned workspace can be released; before a later request's `sp.run`, setup can lazily init again and rebind the current `WeightTable`, geometry, `SessionState`, cache/residency table, streams, stage links and `on_chunk` callbacks. For borrow mode, re-init/relayout must reacquire a currently valid tail loan and refill it before verify. Do not reset while a stager, callback, queue, checkpoint, or borrowed cache range still references the object.

In decode, retain `Verifier` live arrays/graphs, MTP weights and its needed draft state, model tensors, session/KV, expert-cache arena and residency pointers. The user's lifecycle constraint is compatible: if live decode graph/weights can be restored from their canonical host copies/RAM, do not add a VRAM→RAM eviction step merely to reclaim prompt-only workspace. Test the full 256,144-token usable-context configuration under the existing admission/safety checks; a lifecycle memory saving is not permission to lower safety headroom or shrink requested context.

## Phase memory model

Let `V` be usable device memory, `D` fixed decode-live allocations (weights, verifier capture/arrays, MTP, session/KV, runtime, stacks/scratch), `C` resident cache bytes, `P` prompt workspace required by the selected chunk (`Prefill::bytes_needed`), and `R` explicit/allocator/driver reserve. Then:

- Borrowed prompt: `V >= D + C + P_borrowed_overlap + R`, where `P_borrowed_overlap` is storage carved from the tail of `C`, so count it once as `C` in physical capacity; during prompt the number of usable expert slots falls by the admitted tail loan, then refill restores `C`'s expert contents before decode. The loan must fit exact tail bytes and leave the required 128-slot floor per participant.
- Own-buffer prompt (`--no-prefill-borrow`): `V >= D + C + P_owned + R` while prompt workspace lives. In current serve lifetime, `P_owned` can also remain through decode and later requests because `sp` persists. After a safe request-boundary `reset`, decode capacity becomes `V >= D + C + R`; the next prompt temporarily returns to the own-buffer inequality.
- Safe cache expansion enabled by workspace release: at most `ΔC <= P_owned_released`, further limited by free physical VRAM and `R`, per-layer slot sizes/quota, headroom required to allocate/touch/fill cache, and correctness/graph ownership. Do not promise that every released byte can become a useful resident slot; 128 nominal slots currently occupy 268.60 MiB and have low 1.9% stock lookup hit rate. A byte increase must be allocated from profile-ranked pairs, with actual layer-specific sizes and hit/byte evidence.

`--no-prefill-borrow` has two separate effects that must not be collapsed: it reserves additional VRAM for workspace during prompt, and in serve today it keeps that workspace alive beyond prompt. Borrowing avoids the second arena but temporarily removes tail cache slots from prompt residency and incurs refill H2D. Compare these modes separately for prefill throughput/quality and decode throughput/capacity. Do not assume borrowing wins prefill or that no-borrow improves decode.

## 70 tok/s roofline equations (unknowns stay explicit)

At 70 visible tokens/s, wall budget is `1000/70 = 14.286 ms` per visible output token. For a speculative verify window of width `T`, let `a` be accepted draft tokens and let `m = a + 1` be target outputs made visible/committed by that iteration when no EOS/max-output truncation applies. Then `m` is not `T`, offered drafts, target-evaluated rows, or lookup rows. Across a request, use exact `N_visible / N_windows`; EOS/correction/bonus behavior and the final partial window belong in that denominator.

For window `j`, derive CPU miss bytes from actual IDs and ownership:

`B_CPU,j = Σ_(layer, group, expert) blob_bytes(layer, expert) × I[expert is a distinct CPU-served miss in that group]`.

Dedup happens per expert job within a dispatch group. For split ON, R500 says ordinary T=4 work uses two groups of two: CPU-miss sets are deduped independently in each half; repeated experts across halves may be read/unpacked twice, while each CPU phase can overlap the other group's device mixer/router phase. Split OFF uses one group of four, allowing wider within-group expert reuse but removing that cross-half overlap. Split setting can also alter QSA/verify row shapes and launch count. Therefore it changes both `B_CPU,j` and the critical-path schedule; it cannot be priced as merely a bandwidth multiplier. The matched `--spec-split` toggle is a separate decode adoption axis.

Let `D_j` be actual physical RAM bytes attributable to CPU expert reads (including blob fetch, unpack/activation and any relevant cache-line traffic only as observed), `H_j` actual H2D bytes, `W_j` actual VRAM→host bytes, `BW_RAM` attained CPU memory bandwidth, `BW_H2D(shape,kind,batch)`/`BW_D2H(...)` measured for the matching direction/shape, `t_CPU,j`, `t_GPU,j`, `t_sync,j`, and `t_other,j` exclusive intervals after accounting for overlap. A useful lower bound on per-visible-token wall time is based on the measured interval union/critical path, not a sum of nested timers:

`T_wall/token = (union_j critical_path_intervals) / N_visible`.

For a simplified non-overlap bound only, `T_wall/token >= max(ΣD_j/BW_RAM, ΣH_j/BW_H2D, ΣW_j/BW_D2H, ΣCPU_compute, ΣGPU_compute, Σsync, Σother) / N_visible`; actual phase overlap may raise or lower component exposure, but the max terms remain resource-service bounds when bytes and attained bandwidths are measured consistently. `BW_RAM` is unknown here, so leave `ΣD_j/BW_RAM` symbolic. Do not substitute logical `B_CPU` for `D_j`.

For optimistic transfer-only arithmetic (not a prediction): a full 982,272,000 B logical row at 70 rows/s implies 68.76 GB/s of *logical selected payload*. If one hypothetically transferred that entire payload H2D, measured 256 MiB ordinary-host→VRAM 2.25 GB/s would take 436.6 ms/row; Host-USM→VRAM at 2.73 GB/s takes 359.8 ms/row. Actual inference does not necessarily transfer those host expert weights to VRAM: CPU misses are computed on CPU, resident GPU hits are already in VRAM, and distinct/cache-reused IDs reduce or alter requests. Expert-copy shape-specific batch8 5.30–5.49 GB/s would take ~179–185 ms for 982 MB if transferred in that exact shape; this is a counterfactual scale check only. At a 14.286 ms whole-token budget, 2.25 GB/s permits at most 32.1 MB of ordinary-host H2D even if all token time were copies; at 2.73 GB/s, 39.0 MB. Other decode phases reduce the allowed exposed copy bytes. Use copy bytes/time per visible token from the real request before drawing an H2D conclusion.

MTP/acceptance traffic conversion should be computed as observed values:

`logical CPU bytes / visible output = Σ_j B_CPU,j / N_visible` (logical dispatch extent only);
`physical DRAM bytes / visible output = Σ_j D_j / N_visible` (only if counted/measured);
`mean rows per visible output = Σ_j T_evaluated,j / N_visible`;
`accepted-draft fraction = Σ_j accepted_j / Σ_j offered_j` (proposal acceptance only).

A high acceptance fraction can reduce verifier iterations per output, but autoregressive MTP drafting and split group work have their own costs; it does not imply the same ratio for CPU bytes or wall time. Count the correction/base target row and visible truncation explicitly. R497's historical 41/61/45 lookup-derived rows are target-evaluated rows and cannot be used as MTP proposals or acceptance counts.

For CPU theoretical context only, AMD lists up to 3200 MT/s on the 5600X. Assuming two 64-bit channels at that rate gives 51.2 GB/s peak; dividing 982,272,000 logical bytes by that peak yields 19.2 ms, already above the 14.286 ms goal budget. This comparison is not a physical floor or impossibility result because logical blob extents are not necessarily DRAM reads, weights can hit cache/LLC, route IDs deduplicate, CPU and GPU work can overlap, and the actual configuration/attained bandwidth are unknown. Measure CPU memory-controller traffic and matched bandwidth before any DRAM-bound verdict.

The most useful source change boundary is the existing `Prefill::reset()` / serve request boundary: release owned prefill workspace after prompt/refill completion and lazily reinitialize before the next batched prompt, preserving MTP K/V state, conversation/session/KV, checkpoints, verifier graphs, cache addresses, callbacks and stage lifetimes. Do not evict live decode weights or graphs into RAM during the request. Test the full usable context and allocator reserve, normal refill completion, repeated request/prompt-cache cases, output/head/state/logprob/MTP checks, and no new faults.

For roofline attribution, the next measurement should report per request: visible outputs; MTP offers/accepts and target rows/windows; T/group histogram; per-layer distinct CPU misses by group and actual blob extents; cache hits/misses by bytes and provider; CPU pool GU/activation quant/Down wall and worker activity; device event durations/waits; H2D/D2H bytes and matching shape-specific durations; VRAM free watermark at model/cache/graphs/prefill/request boundaries; and a timestamped CPU/GPU/copy interval union. A separate low-overhead CPU DRAM counter plus matched memory-bandwidth measurement is required to fill `BW_RAM`. Keep clean throughput samples distinct from instrumented diagnostics.

No inference change or adoption is proposed by this report. Prefill borrow/workspace lifetime is its own capacity/prefill decision; verifier split, MTP depth/acceptance, CPU expert kernels, and cache admission are separate decode decisions. Each requires matched, correctness-gated evidence.
