# R500 — pre-Xe decode dispatch: selected source-path comparison

Read-only source audit of the selected 1eb89482 pre-Xe snapshot and current-primary source pins. No source, build, test, Git, GPU, profiler, cleanup, or network operation was performed. The prohibited `prefill-gemm-only-contract-root-v1/record.json` and unrelated broad logs/environment data were not read. This report adds decode dispatch details to R489–499; it does not claim causality from unlike historical timing runs.

## Measurement boundary and identity

The old reference is the selected, Git-archive-verified source at `P/.tools/pre-xe-1eb-source-v1`, revision `1eb89482a4afd20277ae0405780ed4f8eb98eb20`. Its accepted tuned measurement was 32,768 input / 64 output, MTP4, `--spec-split`, five pool workers, chunk8192, context262144, INT8 resident KV32768, cache128/325 MiB, two processes plus six later reads; the later-read decode median was 16.182 and pooled 16.635 tok/s. The old source build receipt is the permitted `main-pre-Xe-1eb-build-root-v2` receipt. The accepted current stock evidence is actual 32,049 input / 24 output, MTP4, `--no-spec-split`, chunk4096 and resident KV32768; median decode 3.4 tok/s. Current stock comparison has MMQ1 118.5 prefill / 3.4 decode, while MMQ0 175.3 / 2.8. R491 and the pre-Xe README correctly say the workloads, source/compiler, chunk and verify grouping differ. These values identify a gap to investigate, not a measured decode regression or a component attribution.

Current source files inspected match the permitted current compiled-source pins in `bench/results/2026-10-14-primary-model-baseline/receipts/main-primary-watchdog-lifecycle-build-root-v4/record.json.gz` for `src/core/verify.cpp`, `src/core/expert_source.cpp`, `src/kernels/cpu/native_expert.cpp`, `src/kernels/cpu/pool.cpp`, and `src/program/generate.cpp`. That receipt proves the source pins and 110-consumer size_t range compile-flag contract for its lifecycle build; it is not the stock run's per-TU compile database. Do not treat it as such. R491 additionally establishes current stock `STRATA_IQ_SINGLE_EXACT=1`; old accepted environment has no such opt-in. Historical/current compiler and runtime differ (old Intel oneAPI/icpx 2026.1; current Clang 22/libsycl 9 per recorded stock metadata).

## Decode dispatch differences, ordered by expected value to isolate

1. **Verifier split changes expert work shape and overlap (highest priority).** Both generators pass `o.spec_split` into Verifier; the accepted old CLI enabled it and current stock disabled it. In old `sycl/src/core/verify.cpp`/resolved overlay, `record_window` uses two groups when split is on, unless batch-rec path forces one group. For an ordinary four-row speculative verify this is two groups of two. Current `src/core/verify.cpp` uses two groups for `split_ && T>=2`, so this stock comparison's split-OFF four-row window is one group of four. The old two-group schedule interleaves A's CPU expert phase with B's device mixer/router phase and vice versa (documented around old `record_window`); current one group offers no such cross-group overlap. Both still synchronize before host-visible completion: group/layer completion uses event waits, and the final verify waits for compute/copy streams. Therefore the candidate is CPU/GPU overlap and group-local batching/launch count, not omitted synchronization. Split can also change QSA/attention row shape and launch count, as R491 noted. It is a concrete likely decode lever, but the historical 7% study cited in source is not enough to explain a 4–6x cross-workload difference.

2. **CPU-miss batching is deduplicated within a group/window and is consequently different under split.** Old/current `expert_source.cpp` collect distinct CPU-miss expert IDs for `n_tok*k`, build one `ExpertJobMulti` per expert and attach every routed token activation/output to it, then call `run_split_multi_native` (native layout) or `run_split_multi` (quantized S2 path). This multi-token ABI and per-expert dedup structure are materially shared. With split ON, each 2-row group plans and launches its own set of distinct experts; an expert reused across the 4 rows cannot share a single group job across both halves. Conversely, each half's CPU phase may run concurrently with the other half's device work. Split OFF gives a larger four-row batch for each expert but loses that cross-half overlap. Which wins depends on route overlap, cache hits, CPU misses and dispatch; retained stock summary does not report the actual per-layer group job histogram or phase timings. Collect those from a permitted future matched run before preferring one mode.

3. **Q8_K activation quantizer has a concrete old-only fast path (high priority, clean component candidate).** Old `native_expert.cpp::native_quant_act` calls `q8k_quant_avx2` for Q8_K activation when AVX2 is usable and `STRATA_NO_Q8K_AVX2` is absent; its source comment estimates the ggml scalar path at roughly 3 us per token/layer. Old `native_quant_h` similarly has the Q8_K route for down activations. Current `native_expert.cpp` directly calls `traits(type)->from_float` for both, without the AVX2 quantizer branch. The recorded CPU is Ryzen 5 5600X with AVX2; old accepted environment did not disable it. This can recur across layers and verify tokens, so it is more concrete than a generic kernel-family concern. The old parity source says the fast path writes the same Q8_K bytes. A same-current-binary CPU-only dispatch comparison or bounded engine diagnostic should establish call count/time before adoption; no number here attributes end-to-end latency.

4. **IQ row selection and the IQ_SINGLE_EXACT override differ (medium priority; numerical path must be controlled).** On AVX2-without-AVX512 CPUs, old `native_gu_rows` chooses the multi-token IQ AVX2 route for `nt >= mt_min` (default 2), with GGML `vec_dot` below that; AVX2 support is explicitly checked before calling AVX2-compiled code. Current stock pins `STRATA_IQ_SINGLE_EXACT=1`; current `native_gu_rows` additionally dispatches `iq256_single_gu_rows` for `nt==1`, AVX2 and no AVX512, before falling back to ggml. That branch does not exist in the old snapshot. Old has an AVX2 path for the Q8_K quantizer; current source has IQ single-exact and also routes its AVX2 TU based on the compile/runtime feature controls. `mt_min` remains 2 by default in both. This distinction can affect the common NT1 CPU-miss case and output rounding/acceptance; it must be measured with fixed activations/route and numerical parity, then separately with stock generation. `STRATA_IQ_SINGLE_EXACT` is intentionally not equated with old `IQ_MT_MIN=1`; they select different functions and are not interchangeable.

5. **Pool task granularity is slightly different, probably secondary at default settings.** Old multi-token pool uses `mtasks_=3*(workers + host_participant)` for GU and Down phases. Current introduces `phase_tasks(rows)` and caps task count to row count; with configured/default tasks=0 it still requests three tasks per participating thread, capped at available rows. Native multi-token paths also batch distinct experts above `kMaxSplitMulti`. Thus five workers alone does not prove equal partitioning, but the default policies are close and the row cap only matters when task count exceeds rows. There is no source evidence that pool task count alone explains the speed gap. The old SYCL CMake's `STRATA_NATIVE_POOL_TASK_FACTOR` default is 0; current CLI `--pool-tasks` default is 0. Avoid confusing a nonzero compile-time factor or explicit CLI tasks with the measured default.

6. **AVX compile and execution contracts differ in gating, not clearly in generated row-kernel flags.** Old CMake builds `iq_avx512.cpp`, `iq_avx2.cpp`, `kq_avx2.cpp`, and `kq_avx1.cpp`; AVX2 files are TU-local `-mavx2 -mfma -mf16c`, and runtime `cpu_avx2_ok()` gates their use. Current root CMake also isolates AVX2/AVX512 sources and uses TU-local AVX flags; current `native_expert.cpp` has removed some explicit AVX2 guards for the AVX2 IQ/KQ selection, though this host supports AVX2. This suggests no obvious old-only compile-optimization advantage for the IQ row TU itself. Main should use exact stock compile commands before asserting compiler flags: the permitted current receipt gives source pins and the size_t contract, not this benchmark's compile database. Old global SYCL flags (`-fp-model=precise`, subgroup32, per-kernel split) apply to device translation units, not the CPU pool's AVX2 code, so they are poor direct explanations for CPU expert row throughput.

## Dispatch family boundary

This report concerns native packed experts on CPU during verify. The measured old 1eb build's MoE prefill was FP16 dequant + oneMKL and had no active MMQ/fused TU, as corrected in R494/495/499. It is therefore wrong to explain old decode with `moe_mmq`/fused prefill dispatch. For the current stock arms, MMQ1 versus MMQ0 changes prefill route; R494's comparison explicitly says decode shifted alongside potentially different prompt state/draft acceptance, so those decode medians are not evidence that MMQ dispatch is a decode kernel. Current no-split MTP4 decoding still has batched verify and native CPU expert work.

The selected old and current host `verify` / `expert_source` dispatches are code, not the upstream CUDA generator nor an Xe engine import. The lookup-row warning from R497 is unrelated here; no proposal count is inferred from lookup rows.

## Priority and next evidence

For a future Main-controlled matched stock-client run, the cleanest decode-first sequence is: hold model/binary, input/output target, chunk, resident/cache geometry, route conditions and CPU worker topology fixed; toggle only `--spec-split`; record generated output IDs, drafts offered/accepted, per-window T/group count, CPU-miss distinct jobs per group, pool GU/quant/down phase times, and device group/event times. Then compare old-only Q8_K activation quantization and current IQ_SINGLE_EXACT separately, with bit-parity where required. A second controlled knob is pool task cap only if phase rows show underfilled/overfilled task partition. Do not bundle those changes, change MMQ/prefill, or use short prompts to explain long-prompt decode.

Without such measurements, the source-derived ranking is: (1) split grouping and overlap, (2) Q8_K activation quantizer, (3) IQ NT1 exact dispatch, (4) verify-group-local expert dedup effects as part of split, (5) pool task cap. These mechanisms are specific and testable; none is demonstrated as the cause of historical16.6 versus current2.8–3.4 tok/s. The historical configurations remain non-comparable and the gap remains unresolved.
