## Candidate ranking

1. **First recovery arm: enable the existing compact HC alias and request an 8,192 chunk, with allocator admission as the gate.** This is the smallest concrete step and needs no source port. The active `src/prefill/prefill.cpp` already parses `STRATA_PREFILL_COMPACT=2`, computes `compact_hc_prefill()`, aliases `emb/mixed/bo` to one compact base image, and allocates the reduced HC scratch through the same count/carve helpers (`take_compact_base`, `take_compact_hc`, `hc_set_bytes`, `bytes_needed_impl`, `carve`). With `STRATA_PREFILL_MMQ=0`, `mmq_plan()` takes the FP16 fallback and permits compact, subject to its existing NaN/XMX conditions. R498's proposed Xs/GU/Hh changes are a separate un-applied allocation reduction and are not needed to test this existing alias. Use an explicit current-binary arm at compact=2, first compare at 4,096, then request 8,192 only if `bytes_needed` and actual initialization admit it at the same 262,144 context/KV/cache. Record the *accepted* chunk and allocation result; a requested chunk is not evidence of admission. Do not infer residency changes from old 325 MiB logical cache versus current 268.60 MiB occupied figures.

2. **Highest-value source candidate after the config arm: restore old attention layout/query order as an opt-in variant on the current QSA fallback.** The measured old source reads `STRATA_PREFILL_ATTN_LAYOUT` values 1–4 and dispatches `qsa_decode_attn_batch_variant`; the old measured value 1 maps to `launch_chunk_variant<KV_MODE, 32, true, false>`: 64-cell split retained, transposed query/lane mapping, eight 32-lane subgroups, followed by the same split merge. Current active prefill has no layout reader or variant call and invokes fixed `qsa_decode_attn_batch` when prompt attention does not handle the geometry (`src/prefill/prefill.cpp` around the QSA attention section). Current `decode_attention.cpp` fixes the work-group mapping and performs a separate merge; it does not expose the old variant. This is a repeated per-QSA-layer path and a plausible PP candidate, but there is no isolated measurement proving layout 1 caused the old result. The minimum implementation is an opt-in current `qsa_decode_attn_batch_variant(..., variant=1)` with explicit current `size_t` indexing and bounds, leaving current prompt-attention selection, fixed fallback, scratch layout, and default dispatch intact. Adapt the mapping to current `QsaShapes`/queue interfaces; do not transplant the old kernel wholesale or change query arithmetic. Compare variant 1 against current fixed fallback at equal chunk and inputs before considering the other old variants.

3. **Chunk/capacity is a co-equal tuning variable, not proof for a kernel change.** Old used 8,192 and current stock uses 4,096. R495 source estimates show compact workspace bounded by one routed row per token while MMQ uses `T*K` rows and Q8_1 buffers; those estimates are not allocator results. Current stock run's smaller accepted chunk can materially affect streaming/reuse and throughput. Keep MMQ disabled for the old-equivalent FP16 arm, run `compact=2` at the common 4,096 chunk first, then test 8,192 only after complete allocator admission and successful execution. Do not package chunk and attention-layout differences as a kernel-only result.

4. **Keep queue and in-order contracts; do not restore old scheduling wholesale.** The old path explicitly rejects a non-in-order compute queue, uses a separate copy queue, records DMA events before host staging-ring reuse, waits at slot retirement, and drains/joins the stager on release. The current runtime `queue_for()` likewise rejects non-in-order queues; current prefill retains a separate copy path and explicit event/queue retirement. This preserves the required order/lifetime model. The current source also has host issuer/stager, batched expert route, layer/chunk scheduling and explicit queue drains; no receipt here isolates a faster old queue schedule from these mechanisms. Keep synchronization/lifetime behavior unchanged while comparing attention or compact settings. Avoid changing in-order status, queue count, event elision, issuer threading, or batch order absent a mechanism-specific matched result.

5. **Gather/dequant/transfer scheduling remains lower priority for the MMQ=0 arm.** The measured old route is compact routed-row gather plus IQ weight dequantization to FP16, then oneMKL GEMM; R495 confirms the native MMQ/fused source was not in its executable. Current MMQ=0 also selects the FP16-dequant/GEMM fallback. MMQ group-gather is irrelevant while MMQ is disabled; it changes another route. Current and old `prefill.cpp` both have host staging, ring slots and streamed expert walks, while the current route has additional explicit group/gather scheduling for MMQ. Do not attribute speed from these code-shape differences without stage timings. If the compact+attention arms leave a large gap, the smallest next diagnostic is to separate host copy/stager wait, expert gather/dequant, GEMM, and QSA time on the same workload, then change one schedule at a time. No broad transfer rewrite is justified by source inspection alone.

6. **Native conversions and GEMM orientation are already bounded by R499/R498; no new conversion patch is selected.** Old active FP16 fallback dequantizes each expert's IQ blocks into FP16, gathers compact activations, and calls `Gemm::f16`; current MMQ=0 follows the same broad representation. R499 establishes API/descriptor/scalar equivalence limits and says row/column algebra alone cannot establish internal oneMKL dispatch. R498's Xs/GU/Hh compact conversion/alias proposal is not applied and is excluded by this review's requested scope. There is no source-only basis to alter BF16/FP16 conversion order or BLAS orientation now. Keep those experiments behind the isolated probe previously recommended by R499.

7. **Do not regress current launch range or subgroup contracts to mimic the old `globalSG32` shape.** Old layout 1's local work-group is 8×SG32 and its global dimensions encode queries/chunks differently; it is not merely a `global_range` knob. Current SYCL CMake requires and propagates `-fsycl-id-queries-range=size_t` for large context launches, and active kernels use explicit work-group/subgroup sizes per kernel (including subgroup 32). Preserve the current large-range compiler contract. Only the QSA layout candidate above should vary query/work-group ordering; do not make a source-wide SG32/global-ID rewrite. Compiler/compiler-flag differences remain confounders between the old oneAPI 2026.1.1 build and current binary.

## Concrete next boundary

After Main's current model/check work, the smallest useful recovery sequence is: (A) current stock settings at a common 4,096 chunk with MMQ=0, compact off; (B) same binary/inputs with compact=2; (C) if allocator admits, B at 8,192; then (D) only after A/B/C, add current QSA fallback layout-1 as a separate opt-in source arm and hold the accepted chunk fixed. Reuse the same stock client protocol for official speed claims and preserve actual token/output counts; historical exact 32,768/64 comparison remains a separate lane. Keep decode, MTP/split, cache residency, build/compiler and other runtime differences separately recorded. This is a component prioritization, not an adoption or recovery result.
