## Finding: threaded skip has a real host-generation race when event reuse is enabled

The threaded producer (`prefill.cpp:1618–1640`) waits for capacity using an acquire load of `a_consumed`; for its slot it reads `stage_live[sl]` and, if live, reads non-atomic `used_of[sl]` to select a used event. It then queues the wait/copy, records `copied[sl]`, writes `stage_live[sl]=true`, and release-stores `a_issued=idx+1`. The normal routed consumer calls `wait_issued(k)` before it reaches `compute` and its `used_of` write. The skipped-route path in `release_to` (`2541–2549`) currently flushes an open group, records a used event, writes `used_of[sl]=sl`, advances `consumed`, and gives capacity back, but does not call `wait_issued(k)` first.

This is a real C++ data race in that threaded route, not merely an unproven event-generation concern: on later ring generations, producer `used_of[sl]` read and consumer skip `used_of[sl]` write are ordinary accesses from distinct host threads, with no happens-before edge. `a_issued` only publishes producer work to consumer. `a_consumed` only publishes released capacity from consumer to producer; the producer's capacity acquire can occur before the consumer's subsequent mapping write and does not wait for the current producer's mapping read to finish. Device queue ordering can establish that an unrouted skipped blob has no GPU reader and that copies to a slot are ordered, but it cannot order these C++ host accesses.

`stage_live` is written and read by the issuer thread itself after initial setup; the consumer does not mutate it in the reviewed run path, so this particular field has no analogous producer/consumer conflict. The event wrapper's optional `sycl::event` is mutex-protected in compat, so the wrapper state itself is not an unsynchronized C++ object. However, the event generation selected through `used_of` still needs the host handshake: an event mutex cannot make an independently racing mapping index or a logically stale event selection correct. `copied` is written before the producer's `a_issued` release; consumer `wait_issued` acquire makes that event generation visible before wait submission. `used` must be recorded before the consumer publishes the mapping/capacity for its next generation.

When `copy_events` is false, short-circuit evaluation skips both the producer's `used_of` read and its used-event wait. Thus this exact field race is absent in the explicit same-queue/no-cross-queue-event mode. Current expression is `!same_queue || m.copy != m.cs`: absent `STRATA_SYCL_PREFILL_SAME_QUEUE`, `same_queue` is false, so events are enabled even when queues alias; explicit `SAME_QUEUE=1` suppresses them only while `m.copy==m.cs`; a separate queue forces them on regardless. Therefore the hazard applies to the default event-enabled same-queue path as well as the separate-copy path, and is not eliminated by same-queue device ordering alone. Host `used_of` synchronization is independent of whether a device cross-queue wait is needed.

## Route-by-route ordering

- **Normal streamed issuer / ordinary routed entries:** Producer publishes each copy/event and its stage state before release-storing `a_issued`. Consumer acquire-waits for the exact index before observing `copied` and before it records `used`/writes `used_of`. Consumer then release-publishes `a_consumed`; producer's acquire capacity loop orders future slot reuse after that release. This closes both sides of the generation handoff, provided mapping is written before the capacity release.
- **MMQ group gather:** Each streamed routed entry gets `wait_issued(k)` before entering the group. `flush` waits for the last group's copied event, gathers all group source blobs, records one `used` event on the last slot and writes `used_of` for every gathered slot to that last slot, in that order. At group close `give_back(consumed)` publishes the consumed prefix. That group-last compression is valid for the host map only if every producer has completed its read of each slot's previous `used_of` before the group consumer rewrites it; routed entries have that edge. The last event covers device reads because the one in-order copy queue ordered the group's DMA submissions and compute waits for the last copied event.
- **Skipped entries, including skip after an open MMQ group:** The existing `flush()` correctly closes the open group before releasing the skipped slot, but it is not a producer acknowledgment for this skipped index. The skip then writes its own `used_of` without waiting for issuer publication. This is the missing host edge. It also applies when `used_of` for the skipped slot had been mapped to a prior group's last slot in an earlier chunk: the producer must first finish reading that old mapping; the consumer can then install the new self mapping for the skip generation.
- **Fused batched route:** It waits for `k-1` before the batch's last copied event and records used/mappings for the streamed batch after queuing `experts(_native)`, then gives back the prefix. This is the equivalent batched producer acknowledgment and mapping-before-capacity order. It does not repair the distinct ordinary streamed skip path.
- **Inline issuer:** It is one host thread; `issue_until` and the consumer execute serially. This producer/consumer C++ race does not occur in issuer=0. Device queue/event lifetime still follows its separate queue contract.
- **Old retained snapshot:** The old `release_to` likewise writes `used_of` and gives back without `wait_issued`; later routed entries do call `wait_issued(k)`. It contains the same structural gap. This report does not claim old snapshot execution had a particular observed failure.

## Minimal deadlock-free ordering

A naked `wait_issued(k)` immediately before the skip's used-event record/mapping write closes the immediate read/write race in the currently bounded design, and the source bounds show it will not deadlock today: `stream_all` requires `m.ring > STAGE`; `ring_slots()` returns at least 16 for such a non-STAGE ring; `MMQ_GROUP` is 16; a full group flushes on its 16th routed entry, so before an intervening skipped entry can flush an open group, at most 15 consumed group entries can be withheld from `a_consumed`. Without group gather, routed entries return capacity individually. Hence at the skip, `k` is at most `a_consumed + 15`, while a ring of at least 16 admits producer index `k` (`issuer waits only when idx >= a_consumed + ring`). Still, this proof depends on those current ring/group bounds.

The robust minimal ordering is to publish a flushed prefix before waiting for the skipped generation, then acknowledge that generation before rewriting the host mapping:

1. If `gg_nslots > 0`, call `flush()`; it queues the grouped reads, records the last-slot used event, and installs all group mappings.
2. In threaded mode, release-store the already-consumed prefix (`a_consumed.store(consumed, release)`) so the producer can advance if it had reached its ring limit. This prefix is safe because every earlier source read has already been queued and its used event/mapping installed. In inline mode no publication is needed.
3. Call `wait_issued(k)` and acquire-observe the producer's release store for this skipped index. This ensures it has finished reading the slot's prior `stage_live`/`used_of`/event generation before the consumer changes that mapping.
4. Record the skip's used event, write `used_of[sl]=sl`, then advance `consumed=++k` and publish that new capacity using the existing `give_back(consumed)`.

This order cannot wait for the skipped copy to be consumed by compute: the skip has no blob reader. It waits only for producer host publication/read completion; copy-vs-copy reuse remains ordered on the single in-order copy queue, and the later copy's wait on the newly recorded used event provides the normal slot-reuse edge. Publishing the prior prefix before `wait_issued(k)` removes dependence on the ring>=16/group<=16 arithmetic and avoids the deadlock pattern where a producer is blocked at the capacity limit while the consumer waits for an index it has not yet permitted. The event order is `record used` → `write used_of` → release `a_consumed`; on the producer side, prior mapping read → release `a_issued` → consumer acquire `wait_issued` → mapping rewrite → capacity release → producer acquire before any future reuse. This produces a two-way generation handshake and is race-free under the existing one-producer/one-consumer ownership.

This is a source-proven proposed ordering, not an applied fix or a tested result. No active source or benchmark was changed. R504 does not alter or qualify CUDA/HIP behavior. It does not change the status of the R8 stock measurement: that configuration has `stream_all=false`, so it cannot exercise this threaded path.
