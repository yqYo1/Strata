# R171 — unitrace post-PASS host SIGSEGV teardown source review

Date: 2026-10-12. Read-only review of closed R171 health evidence and pinned PTI source commit `6c0d6b0b80c6dbac4b5902d9d5ade1c75b9e9033`. No runtime, tests, builds, GPU/process queries, Git mutation, or workspace edits were performed.

## Result boundary

The closed record `xe-unitrace-v711-health-root-v2/record.json` records a completed `unitrace-health` command with exit code `-11`, no owned survivors, and elapsed 0.4529 s. Its stdout contains `H2D 65536 complete`, `KERNEL 16384 complete`, `D2H 65536 complete`, exact `PASS`, and a device timing summary of 41,040 ns. The trace was saved and the stderr includes normal timing/kernel-submission reports plus a final timeline path. Thus failure happened after the health program printed PASS and after unitrace had produced its reports, during process shutdown or a late asynchronous teardown path. This localizes the crash window; it does not identify the faulting instruction, prove which destructor ran last, or establish a GPU hang. The record's before/after kernel journal collection found no new kernel messages in the interval. The actual run environment did enable loader debug logging and Level Zero validation/parameter validation, as recorded in the command environment.

## Source findings

`tools/unitrace/src/tracer.h` has `UniTracer::~UniTracer()` call `ze_collector_->DisableTracing()`, flush reports if needed, then `ze_collector_->Finalize()`, before destroying the Chrome logger. `ZeCollector::Finalize()` itself calls `FlushData()` again, then (on non-Windows) calls `zelTracerDestroy`, clears the global collector pointer, and performs metric teardown only when metric-query mode is enabled. The double flush is intentional/idempotence-sensitive: `Flush()` sets `data_flushed_`, but the destructor still explicitly finalizes the collector. The current run uses device timing and kernel submission, not the counter/metric-query mode, so the metric-query-only context destroy path is not a leading match.

The strongest source-level teardown candidate is the interaction between Chrome trace thread-local buffers and `ChromeLogger` destruction. `ChromeLogger::Flush()` flushes buffers and closes JSON, but its destructor later iterates the global `trace_buffers_` set and invokes `TraceBuffer::Finalize()` on every registered buffer. `TraceBuffer` is a `thread_local` object; its destructor also takes the logger mutex, flushes if needed, frees its buffers, and erases itself from `trace_buffers_`. This creates two distinct teardown owners for the same TLS object (explicit finalization by logger versus TLS destruction) with global-set bookkeeping. The atomic finalized flag and recursive mutex appear intended to make the overlap safe, and the process is single-threaded in the health source, so this is only a credible ordering/race target, not a demonstrated bug. A more specific lifetime concern to audit is whether `trace_buffers_` remains valid when TLS destructors execute after ChromeLogger/static state teardown, and whether all buffer flush/finalize operations are safe after the logger itself has been flushed or destroyed. The current explicit `UniTracer` destruction order puts ChromeLogger destruction after ZeCollector finalization, but it does not by itself prove TLS teardown ordering across worker/runtime threads.

PTI's ZeCollector also uses `thread_local ZeDeviceSubmissions local_device_submissions_` and a global set of pointers to those objects. `FlushData()` takes the global submissions mutex, finalizes and erases all entries; each TLS destructor takes the same mutex, sweeps if not already finalized, then erases itself. The `finalized_` exchange and mutex are explicit synchronization, making a simple double-delete theory weak. Still, late TLS destruction racing global collector teardown is another source boundary to inspect if a native backtrace points into submission bookkeeping.

R169 already reviewed event-cache and immediate-list teardown. Its source-level concern is destruction of cached profiling events after a nonblocking poll if work remains outstanding. Here the health explicitly waits after H2D, kernel, and D2H, and reports all stages complete before PASS. That makes the known pending-event lifetime gap a poor fit for this completed path, though it cannot exclude an unrelated PTI/driver defect. R170 found the historical ZeLogger thread-local string teardown UAF fixed upstream by v1.31; the configured system loader reports v1.32.0. This specific old bug is therefore not a leading explanation, subject to the prior caveat that the installed binary was not independently lineage-matched by hash.

## Discriminating next step and mitigation direction

The most useful next evidence would be a host core dump/backtrace from a separately admitted reproduction, with symbols/build IDs for unitrace, PTI, loader, validation layer, UR, and driver. Preserve the crash's signal metadata and exact frames; the current status `-11` alone is not a stack. If policy permits a later controlled run, compare a host-only unitrace invocation (no SYCL/GPU initialization) with the smallest Level Zero-initializing invocation, then change one teardown dimension at a time: Chrome kernel logging off/on, validation off/on, loader logger off/on, and an explicit `UniTracer::Flush()`/controlled normal exit if a harness can call it. A host-only test of `ChromeLogger` plus several worker threads that create/use/destroy `TraceBuffer` TLS buffers and then destroy the logger can exercise the identified ownership boundary without GPU work; run it under ASan/TSan in a separate source build only after the owner authorizes build/test work. This is a proposed discriminator, not an experiment performed here.

Source mitigation should wait for a backtrace or a reproducer. If the TLS/logger boundary is implicated, make ownership single-sided: provide an explicit shutdown that stops/joins producer threads, finalizes their TLS buffers while the logger and registry are alive, clears registry membership, then destroys the logger; make TLS destructors idempotent against an already-retired registry without dereferencing a destroyed global. If the trace instead points into `zelTracerDestroy` or validation/loader teardown, use the exact frame and upstream source history to select a narrower fix. Do not infer that disabling a diagnostic option is a repair from one successful run.
