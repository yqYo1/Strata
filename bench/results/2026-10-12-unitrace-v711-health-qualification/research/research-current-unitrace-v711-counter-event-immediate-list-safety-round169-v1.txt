# Round 169 — counter event / immediate-list safety for the current tiny health target

Date: 2026-10-12

## Scope and result

This is a read-only source/specification audit of the exact `health.cpp` target and the frozen PTI/unitrace source at commit `6c0d6b0b80c6dbac4b5902d9d5ade1c75b9e9033`, against the LLVM worktree based on `504366f4b82ff00bbac7b0c956635eed8bc599d8` plus 17 local patches. No tests, builds, runtime, GPU, process, Git mutation, or cleanup were performed. The health controller is expressly out of scope.

The inspected health source has a newly created SYCL in-order queue, performs H2D, one integer kernel, and D2H, and calls `wait_and_throw()` after each operation. The checked-in UR-v2 source provides both an older append route and the newer `urEnqueueKernelLaunchWithArgsExp` route. The SYCL scheduler path in this toolchain calls `urEnqueueKernelLaunchWithArgsExp`; UR-v2's immediate in-order queue manager reaches `zeCommandListAppendLaunchKernelWithArguments` on the selected new path. Thus PTI's matching `WithArguments` hook is material for the health kernel, alongside the ordinary `zeCommandListAppendMemoryCopy` hook for transfers.

The core ordering conclusion is favorable for this bounded health flow: PTI changes only the append's signal-event pointer when it instruments a counter-based application signal on a registered in-order list; it preserves the application wait list and `pNext`, then appends a signal for the saved application counter event after the profiled operation on that same in-order immediate list. The application event therefore still denotes completion of that operation and later queue work remains ordered. PTI does not put timestamp flags or a changed extension chain onto the application's counter-based event pool.

This is not a proof of universal no-hang behavior. PTI can assert/abort on internal Level Zero failures, and its final polling is not a blocking drain for pending immediate-list work. The current health's explicit waits are the condition that makes cache-event reuse and teardown consistent with the lifetime requirement. A failed or timed-out wait, a path that exits with immediate work outstanding, an unrecognized list, or a non-in-order list remains outside that favorable conclusion.

## Descriptor, pool flags and extension-chain handling

UR-v2's event-pool builder starts a normal `ze_event_pool_desc_t`, sets host-visible and profiling flags only when the requested event properties require them, and, for driver counter-based events, links a `ze_event_pool_counter_based_exp_desc_t` into `pNext`. It sets `IMMEDIATE` when the pool is for immediate lists and `NON_IMMEDIATE` otherwise; if interrupt-based sync is enabled, the counter descriptor chains to the Intel event sync-mode descriptor. The corresponding queue initialization sets `ZE_COMMAND_QUEUE_FLAG_IN_ORDER` when driver counter-based events and the in-order driver-list policy are both enabled (`unified-runtime/source/adapters/level_zero/context.cpp`, around lines 200–220, 408–450).

PTI's `OnEnterEventPoolCreate` first leaves IPC pools alone, then walks the original `pNext` chain. If it sees `ZE_STRUCTURE_TYPE_COUNTER_BASED_EVENT_POOL_EXP_DESC`, it returns without allocating/replacing a descriptor and without adding `HOST_VISIBLE` or `KERNEL_TIMESTAMP`. Therefore the caller's descriptor, flags, and full counter/sync-mode chain reach the original `zeEventPoolCreate` intact. On successful create PTI tracks that pool; `OnExitEventCreate` tracks events created from it. Pool/event destroy callbacks erase those tracking entries after successful destroy. This matters because the Level Zero counter-pool extension is deprecated in recent spec versions but remains the extension this pinned UR-v2 source uses; PTI does not try to merge mutually sensitive profiling flags into it.

For its own timing events, PTI uses a separate `ZeEventCache`: a regular pool with `HOST_VISIBLE | flags_`, where the collector supplies the kernel-timestamp flag, no counter-based `pNext`, and 1,024 events. Events have host signal/wait scope. Releasing a used cache event first occurs after PTI has observed completion; it destroys that event and creates a replacement at the same pool index before returning the replacement to the free list. These events are private to PTI and are not exposed to the application's wait lists.

The app's `pNext` for WithArguments is passed through unchanged by UR. PTI's callback only swaps the `phSignalEvent` value as described below; it does not replace the `pNext` chain. The regular AppendMemoryCopy callback likewise leaves its source/destination/size and wait list unchanged and uses the common preparation path for signal-event handling.

## Signal/wait and in-order behavior

`PrepareToAppendKernelCommand` finds PTI's registered command-list record, including its `in_order_` bit derived from `ZE_COMMAND_QUEUE_FLAG_IN_ORDER`, and checks the supplied wait list without altering it. If the signal is null, PTI obtains a private timestamp-capable cache event and supplies it as the signal. If the supplied signal is marked as counter-based:

- On an in-order list, PTI saves the original application event in `ze_instance_data.in_order_counter_event_` and substitutes a private timestamp event for the append.
- On a list not marked in-order, PTI reports that counter events cannot be instrumented there, sets `instrument_ = false`, and returns without substitution. The original append then proceeds without PTI timing instrumentation.

After a successful append, the common kernel/memory recording path sees that saved application counter event and, for an in-order list, calls `zeCommandListAppendSignalEvent` on the same list to signal it. The result is an operation signaled by PTI's private timestamp event, followed by a signal of the original application event. The application's later command wait list remains byte-for-byte the original pointer/count/handles. Since the application queue is in-order and the extra signal is appended immediately on that same list before the caller returns, the application event is not signaled early; it is signaled after the completed operation. An in-order queue's subsequent commands remain ordered even if they have no explicit wait event.

For a health call whose output event is null, PTI's private signal event is the only event added. For an output event backed by a counter pool, the two-event arrangement above preserves the event's completion meaning. The extra append does add a command and host-side overhead, so this instrumentation must not be treated as transparent timing.

The Level Zero spec defines an immediate command list as an implicit queue; it supports synchronous completion of append calls and does not require the app to create a signal/wait pair for in-order sequencing. It also allows counter-based events to be signaled from a command list, and explicitly exempts them from the ordinary signal-event device-access rule. Waiting on a counter event retains the peer-access requirement. In this single-device B570 health path, the extra counter signal is on the same device/list as the application's operation; no cross-device case is claimed.

## Reset, destroy, timestamp query, completion and teardown

- PTI intercepts application `zeEventHostReset` and `zeEventDestroy`. Before the real operation, it queries status; if already signaled, it processes PTI commands associated with that event. Destroy of an unsignaled event removes collector-side associations. This cleanup does not make destruction of a device-referenced event legal; the Level Zero spec still requires the application to ensure the device is not referencing an event before destroying it.
- Completion processing calls `ProcessCommandSubmitted`. For an event which carries a timestamp, PTI queries the kernel timestamp only after `zeEventQueryStatus` reports success; then it releases the private event. `ZeEventCache::ReleaseEvent` destroys/recreates that event slot, so its safety depends on the completion observation happening first. Failed append paths release the acquired cache event because the failed append did not queue it.
- The spec allows host status queries and host reset, and `zeEventQueryKernelTimestamp` requires an event from a pool with kernel-timestamp support. PTI's private pool satisfies that requirement. The spec says timestamp `duration` is undefined for events created from kernel-timestamp pools when those events are used as signal events, while also saying such events still report correctly as signaled for other event APIs. PTI relies on the timestamp fields and status, not an application-facing duration for the private event.
- `OnExitCommandListDestroy` polls submitted commands and then removes command-list metadata. For an immediate list, `DestroyCommandList` does not block waiting for pending commands. `FlushData`/`Finalize` call `ProcessAllCommandsSubmitted`, which also only queries current event status; they do not wait until all pending immediate-list events become ready. The cache destructor then destroys cached events and pools. The spec says event destroy requires that the device no longer references the event. So source inspection exposes a real lifetime hazard for any process path that exits or destroys its immediate list before its work completes; the finalizer alone is not a drain.
- For this specific health source, `wait_and_throw()` follows every H2D, kernel, and D2H operation, and the queue is in-order. A successful last wait establishes completion for that queue's prior work; status/query hooks can process and release the corresponding events before teardown. The source's `TransferLifetime` guard also exits immediately instead of unwinding host buffers if queue completion cannot be confirmed. Consequently, normal successful health completion satisfies the ordering/lifetime precondition by application waits. It does not make a failed wait or forced process termination safe; those remain a failed gate, not evidence of a hang-free completed run.

## Failure and GPU-hang interpretation

There is no source-level cycle introduced by the normal path: the operation itself waits only on the app's original prerequisites; PTI's timestamp event does not become an extra wait prerequisite; and the app's original counter signal is appended after the operation on an in-order list. The health waits for the queue's completion after each stage. This rules out a straightforward PTI-created self-dependency in this narrow single-queue sequence.

There are still credible failure modes. `PTI_ASSERT` covers cache event/pool creation, `zeDeviceGetGlobalTimestamps`, appending the preserved counter signal, and timestamp/event status operations. Those errors can terminate the process. Level Zero may report device lost/reset, synchronization-object errors, or unknown errors; a tool timeout does not prove a GPU hang. If health wait fails, its guard uses `_Exit(74)` and the process can leave in-flight device work, so do not label that outcome a normal teardown or retry it in the same session. The event-cache immediate-list teardown gap above also means that only a successful, fully waited health run can be accepted as clean lifetime evidence.

No dynamic observation in this report establishes that the installed driver takes every expected callback on this exact run, that the queue manager chose WithArguments at runtime rather than the supported fallback on the actual device, or that a driver has no internal hang bug. Source selection logic says the new branch is chosen when support is reported and it is not disabled; the closed environment identifies the forced v711 adapter but does not prove those runtime branch conditions. Keep the claim at source-path qualification until a later explicitly admitted trace observes the callback/API identities. This report does not extend to model graphs or other launch types.
