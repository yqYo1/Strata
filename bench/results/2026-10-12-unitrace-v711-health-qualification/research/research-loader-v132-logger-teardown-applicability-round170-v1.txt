# R170 — Level Zero loader logger teardown fix applicability to installed v1.32.0

Date: 2026-10-12. Read-only upstream source/release audit. No runtime, tests, builds, GPU/process queries, Git mutations, or workspace edits were performed. Existing report index and private reports were searched first; no earlier audit of this specific upstream ZeLogger teardown issue was found. The existing installed-loader provenance report is `round130-installed-native-exp-lowering-provenance.txt`.

## Finding

The `ZeLogger` thread-local-buffer use-after-free was introduced alongside the replacement custom logger in upstream v1.30.0 and fixed in upstream v1.31.0 by PR #483, merged as commit `fd1706e` (squashed commit shown in the PR; its commit page is `d2cb9bb`). The v1.31.0 release notes explicitly list the fix. Upstream v1.32.0 is later than that fixed release. Therefore the fix is already included by version in a loader built from the upstream v1.32.0 source; it is not a v1.34.0-only fix. The installed `/usr/lib/x86_64-linux-gnu/libze_loader.so.1.32.0` identified in the prior provenance report is expected to contain the fix if it corresponds to upstream v1.32.0. Version string alone does not prove the exact installed binary's source ancestry or rule out downstream modifications; this read-only audit did not match its binary hash to a distro build or inspect its disassembly.

The proposed logging configuration does not exclude the historical failure mechanism: the PR describes log calls occurring during process-exit teardown, and `ZEL_ENABLE_LOADER_LOGGING=1` enables loader logging. Console output changes the sink; `debug`/`trace` select more messages. There is no upstream statement found that these settings are required for the defect, or that validation specifically triggers it. It is justified to say enabled loader logs can exercise the affected logger path; it is not justified to claim that validation is necessary, that every validation run triggers the race, or that the environment settings alone reproduce it. On a genuine upstream v1.32.0 build this specific old use-after-free is fixed even when logging is enabled. This conclusion is about this logger defect only, not general validation/logger teardown safety.

## Evidence

- Upstream merged PR #483: <https://github.com/oneapi-src/level-zero/pull/483>. The PR says: “Replace the thread_local std::string line/tid buffers with POD thread_local char buffers, so log calls that arrive during exit teardown no longer write into freed memory.” It also adds a standalone ASan regression test. It was merged June 18, 2026.
- The PR identifies merge commit `fd1706e`; its included commit is `d2cb9bb`, “Replace the thread_local std::string line/tid buffers with POD thread_local char buffers, so log calls that arrive during exit teardown no longer write into freed memory.” Files changed include `source/utils/ze_logger.cpp`, its header, and `test/ze_logger_teardown_unit_tests.cpp`.
- Upstream release notes: <https://github.com/oneapi-src/level-zero/releases>. The v1.31.0 entry names PR #483 and the logger teardown use-after-free fix. The v1.32.0 release entry is later (tag commit `d3b3efb`) and its changelog lists other changes, with no separate logger fix required to establish that the fix arrived in v1.31.0.
- Upstream changelog: <https://github.com/oneapi-src/level-zero/blob/master/CHANGELOG.md>. v1.30.0 introduces the custom logger replacing SPDLog; v1.31.0 lists the ZeLogger teardown fix. This gives the supported affected/fixed upstream version boundary: custom logger introduced in 1.30.0; fix released in 1.31.0. No narrower patch-version boundary is stated in the sources inspected.
- Upstream README logging documentation: <https://github.com/oneapi-src/level-zero/blob/master/README.md>. It documents `ZEL_LOADER_LOG_CONSOLE=1` with `ZEL_LOADER_LOGGING_LEVEL=trace` for loader debug tracing and marks older `ZE_ENABLE_LOADER_DEBUG_TRACE` deprecated. It supports interpretation of console/level as output/filter settings, not a separate fix switch.
- Prior installed-file provenance report: `/home/yayoi/.local/state/strata-sycl/post-reboot-tuning-20261007/research-20261009/round130-installed-native-exp-lowering-provenance.txt` records the loader path and SHA-256 `b764efda507f173560fa6055d433dd5c76140180b4a7c532e1cea813cde67363`. That establishes which local file was previously hashed, but this report did not independently map that hash to pristine upstream v1.32.0 source.

## Practical conclusion for current source decision

For the installed loader labeled `1.32.0`, upstream release evidence places it after the fix; do not treat this particular ZeLogger bug as an identified blocker for logging/validation qualification solely because v1.34.0 exists. Preserve the binary-lineage caveat above if an absolute claim about the installed bytes is needed. No runtime or test was run to qualify this machine's actual teardown behavior.
