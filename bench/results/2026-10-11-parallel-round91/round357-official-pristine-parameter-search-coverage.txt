## Decision

The earlier long-prompt measurements did more than exercise stock defaults: they explicitly requested `--prefill 8192`, `--expert-cache 128`, `--pool-workers 5`, `--pcie-frac 0`, MTP/speculation 4, and related flags; v0.1.40.2 and v0.1.41 also set the recognized `STRATA_PREFILL_FIRST=0` and `STRATA_PREFILL_RING=8` environment controls. But the retained official/pristine records examined here do not show an independent parameter search for the B570/5600X/128-GiB environment. They repeat a single requested recipe. Requesting non-default values, comparing versions at the same request, and optimizing a local fork are three different kinds of evidence.

The bounded record scan found two v0.1.40.2 pristine 32K clean runs with the same argv/environment and two v0.1.41 pristine 32K clean runs with the same argv/environment. v0.1.41 pure read the 32K fixture at actual chunk 6144 and actual cache 144 slots in both processes, despite requesting chunk 8192/cache 128. v0.1.40.2 used actual chunk 8192/cache 144 with requested cache 128. These establish successful historical workloads and requested-vs-admitted geometry; they do not establish that any setting was selected by a parameter search. The archive does not prove that no other experiment ever existed outside the inspected retained corpus.

There is no v0.1.42 GPU performance result to optimize yet. The R352/R354 audits refuse the current official B570 path for long all-component prefill and normal CPU-pool generation because the runtime receipt lacks the required concurrent host-USM access contract for live host/device polling. Keep v0.1.42 performance unmeasured until the source route or actual capability/runtime contract passes that gate; parameter search cannot make an inadmissible handoff safe.

## Main-owned search once admitted

After the exact pristine source/runtime tuple passes both generation and prefill access gates, run a small staged search on the same 32K input, model, expert profile, output budget, and system state; repeat the selected configuration at 64K as a separate validation point. Keep pristine source and keep the recipe limited to variables proven supported by that source.

1. **Prefill screening:** hold decode settings fixed; compare requested chunks 4,096/6,144/8,192 (and auto only if its actual selected chunk is recorded), then screen `FIRST=0` versus its documented default and `RING=4` versus `8`; keep the row only if actual progress reaches the requested geometry, cache admission is recorded, correctness passes, and prefill tokens/s improves. Test `KV_PREFETCH` and `KV_STAGE_OWN` as separate binary factors only after one-factor results identify a plausible bottleneck. Record prefill and final prompt-position work separately if the engine reports them.
2. **Decode screening:** freeze selected prefill settings; independently compare supported pool-worker counts (for example 3/5), PCIe CPU/GPU share (0 and one nonzero supported value), expert-cache admission (requested values that fit, recording actual slots), KV residency (32K/64K at the matching context), and speculation widths (e.g. 2/4) one axis at a time. Maintain exact numerical/quality checks and free-VRAM/RAM gates; never tune through a rejected access path.
3. **Selection and validation:** use screening runs for choice, then run at least three independent quiet process launches of the selected configuration, with multiple fresh reads within each process. Report process-level decode samples, spread, and the within-process read samples separately. Also retain an explicit baseline-default measurement, an unchanged-request cross-version comparison if desired, and the per-version tuned result as separate rows. Do not call repeated requests in one process three independent decode samples. At 64K, validate the chosen point and its correctness independently rather than assuming 32K admission or performance extrapolates.

No search was executed in this round. The next decision is source/runtime eligibility, then an official-only measurement plan; the local tuned settings do not fill that gap.
