# Round 355 — Xe MTP output and QSA mapped-metadata caller reachability

Date: 2026-10-11 (Asia/Tokyo). Read-only source audit. I inspected the stable `generate.cpp` plus `mtp.cpp`, `layer.cpp`, `session.cpp`, `verify.cpp`, and `prefill.cpp` paths and compared the MTP findings with R350/R353 and registry v113. No project command, test, build, GPU/runtime/process operation, source edit, or Git mutation was performed. The report is the only artifact written.

## Finding

The B570 capability receipt summarized in R353 allows host-USM access but reports no `CONCURRENT` or `CONCURRENT_ATOMIC` capability. Under that capability, ordinary `--mtp --spec 4` generation reaches an unsupported CPU/device overlap in `MtpDrafter::draft`: after launching the draft graph, the CPU spins on mapped `h_out_`, then reads mapped `h_out_` and `h_prob_` while the graph may still be writing those same host-USM allocations. `volatile`, an atomic fence, `stream_idle`, and a final stream synchronization do not make the earlier concurrent accesses legal. This is a live production caller, not just a dormant helper: non-native generation calls `draft_first(o.spec, ...)` before its first verify window (`generate.cpp:10594-10599`) and calls `mtp.draft(...)` after each accepted verify/commit (`10777-10790`); native generation also calls `draft_first`/`draft` in its speculative loop (`9713-9716`). With `--serve --batch-mtp`, slot admission and each active slot call the same `draft_first`/`draft` implementation (`9926-9934`, `7438-7445`).

The failure is independent of the authoritative MTP KV ownership cleared in R353. The mapped output arrays are separate from the KV host pool. In the normal serial path, a successful `draft()` does finish with `stream_sync(cs_)`, so subsequent metadata staging and KV lifecycle work are ordered after a completed prior draft. That late completion cannot legalize the earlier CPU polling/reads. A rejected verify row is handled by `mtp_catchup_all()` / `T = a + 1` before the next MTP draft; that controls which KV rows are appended, not mapped-output ownership.

The narrow safe fallback is to keep token/probability outputs in device memory and serialize each draft step: launch the round/step graph, wait for its completion, copy the output row(s) to CPU storage and wait for that copy, then read the token/probability and decide whether to launch the next step. Do not poll an output mapped to host USM unless the active device reports the required concurrency capability. This gives up early-step overlap but leaves the current chain semantics and probability cutoff intact. Apply the same contract to any future chain path that exposes mapped outputs. `chain_outputs_ready()` / `chain_poll()` currently read only after corresponding event completion, so their event-gated reads are not the same overlap; however, the pipelined-window entry is rejected when host handoff concurrency is unqualified (`Verifier::capture_all`/`prestage`, `verify.cpp:1440-1447, 1840+`), and it is not the normal B570 route.

## MTP record lifetimes and the full-context probe

`draft()` fills persistent mapped `h_tok_`, `h_step_`, `h_pos_`, `h_row_`, and optional `h_force_` before graph launch (`mtp.cpp:1042-1059`). The function's normal successful exit synchronizes `cs_` (`1110-1118`), and `idle()` also synchronizes before snapshot/slot transfer (`895-901`). In the target-only generate route this makes the next draft's record rewrite occur after the prior MTP graph has finished. Prompt prefill normally uses device-side temporary records on the Xe/CUDA path and synchronizes when `sync` is true (`939-1001`); the mapped-record branch, when explicitly selected, waits after each launch before it overwrites the persistent mapped records (`1003-1021`). Conversation slot copying calls `mtp.idle()` before saving/restoring draft KV (`generate.cpp:7296-7305, 7331-7341`). Thus I found no additional overlapping CPU/GPU reuse of these MTP input records in the serial normal path or full-context probe.

The exact-full-context diagnostic does not reach `draft()` or the output poll. Its dedicated branch requires `--max-new 0`, exact full extent, one GPU, native/MTP, fixed prefill, and excludes serving/batch (`generate.cpp:2456-2479`). Its callback builds bounded successor IDs with the explicit terminal probe and calls `mtp.prefill(..., true)` plus `stream_sync(mtp.stream())` for every completed target chunk (`1306-1322`). It forces `STRATA_MTP_PREFILL_SYNC=1` (`2475-2479`), which selects the mapped persistent-record loop; that loop waits after each graph launch before the CPU rewrites its records (`mtp.cpp:1003-1021`). The graph capture helper synchronizes capture finalization (`794-805`), but capture records work and is not graph execution; the callback's later `graph_launch` is the actual execution and its completion wait is the ownership boundary. The existing `probe::successors` path supplies 262,143 real next-token rows and one tagged terminal probe (`generate.cpp:1296-1319`, building on the R350 design). No one-past `tokens[262144]` read or post-context prediction is implied. The probe's separate snapshot/poison/restore route device-quiesces around capture and restore (`1324-1395`); it does not call the MTP output polling path.

## QSA `host_step` / `host_pos` reuse

`qsa_layer()` writes each state's persistent host-USM `host_step` and `host_pos` and then submits either mapped-read kernels or asynchronous copies from those addresses (`layer.cpp:1038-1050`). For the production split-token `session_loop` path used by ordinary generation, the loop performs `stream_sync(cs)` before `stage_token()` rewrites all QSA records (`session.cpp:589-594`), and synchronizes again before returning (`775`). The one-token direct `session_token` path calls `qsa_layer` through `block_layer`; its normal top-level `put_input` synchronizes the device before each token (`generate.cpp:4828-4851), except when the explicitly experimental `--stream-token` option is selected. That explicit async combination needs its own completion proof before host staging is reused.

There is a separate source-level reuse gap in the benchmark/replay APIs `session_replay()` and `session_replay_full()`: both call `stage_token()` and enqueue graph launches without draining the preceding replay (`session.cpp:275-313`). The `--graph-only` generate caller launches a warm pass, device-syncs, then launches 20 replay calls and performs only one device sync after the loop (`generate.cpp:5096-5117`). The next call rewrites mapped source bytes after the previous replay enqueue, so the device may still be reading the same host-USM allocation. `session_replay_full()` has the same contract but its current GPU-only timing caller synchronizes after every invocation (`generate.cpp:5136-5151`). By contrast, `session_replay_stages_per_layer()` ends in a stream synchronization before returning, so its repeated benchmark calls are drained. A graph capture itself does not run kernels or copy nodes, but replay does. Add a queue completion before staging in the unsynchronized replay API or make every caller wait before its next call; retain a final completion for result use. The benchmark's identical position-0 values do not remove the host/device access overlap.

## Remaining work and ownership

Main should own the implementation and qualification. The blockers are (1) remove the MTP output polling/read overlap when host/device concurrency is false, preserving an early-exit-free serialized fallback, and (2) add a completion boundary before each QSA mapped-source rewrite in the replay API, plus qualify the opt-in `--stream-token` direct path. The ordinary `session_loop` token path is already serialized at the staging boundary. No change is indicated to R353's authoritative KV findings.

Useful tests for Main: a Xe no-concurrent-host-USM `--mtp --spec 4` greedy generation and probability/min-p path that proves outputs are read only after their completion/copy; equivalence to the serialized target result and correct draft count; replay with positions changing across repeated calls and a queue delay, checking QSA positions/state against a fully serialized run; test the direct `--no-capture` route and explicitly cover or reject `--stream-token`; and retain the full-context probe check that terminal successor construction stays in-bounds and mapped-record prefill waits before reuse. Do not treat the full-context storage probe as a draft-quality test.
