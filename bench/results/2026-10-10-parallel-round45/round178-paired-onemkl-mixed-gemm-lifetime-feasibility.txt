## Conclusion

**The pair is feasible in the normal native-IQ direct path for noncompact execution, but it is not safe to implement by simply accumulating raw pointers and calling the existing `Gemm::f16` twice later.** The actual route has the right resources and dimensions: `DQ=2` FP16 GU/down dequant slots, per-expert route rows and output spans, and an in-order compute queue shared by Prefill and the Gemm descriptor. The installed oneMKL group `gemm_batch` API supports `sycl::half × sycl::half -> float` with float scalars and an asynchronous completion event. A group of one with two entries exactly represents two equal-row-count expert products.

Two explicit implementation obligations remain. First, caller-owned pointer arrays and per-group metadata must remain alive until their use is known complete. The current DPCT `gemm_batch` facade is `void`; it does not return the oneMKL event to its caller. Second, preserve the current queue order across both dequantizations, both GU products, each intervening SwiGLU, both down products and the next pair's dequantization. Neither is a hard oneMKL type/workspace blocker, but both need an explicit test-only paired implementation and an event/lifetime policy. Do not ship this path based only on signature compatibility.

## Exact active operation

The production native direct route calls `Gemm::f16(X, W, Y, T=ne, N, K)` separately for GU and down after dequantizing an expert into `dq_gu[q]` and `dq_d[q]` (`prefill.cpp:4778–4829`). `ne` is that expert's routed row count, and `order` contains only nonempty experts. For the pair candidate, require adjacent active experts with exactly equal positive `ne`; do not pad or issue a zero-row entry. The same `N/K/ne` and same leading dimensions are shared in each oneMKL group.

`Gemm::f16` defines `alpha=1`, defaults `beta=0`, and dispatches through column-major `gemm(op(A)=A^T, op(B)=B)`: A is the dequantized row-major weight matrix W, B is the activation rows X, and output C is FP32. It passes `real_half` for A and B, `real_float` for C, and `compute_type::f32` (`gemm.hpp:40–42`; `gemm.dp.cpp:750–788`). In this DPCT mapping the half/half/float combination resolves the oneMKL group to `sycl::half, sycl::half, float, float`; `compute_type::f32` falls through to mode `unset` for this non-complex data type, rather than selecting an alternate TF32/BF16 mode (`dpct/blas_utils.hpp:866–890`, 1205–1210). Preserve those exact dtypes, scalar values, mode/default semantics, transpose and strides. FP32 output is explicit; do not describe `unset` as a new explicit accumulator guarantee or change the math mode for the pair.

The two products for each paired set are distinct batches because their K/N shapes differ:

* GU group: `m=N=1280`, `n=ne`, `k=2560`; `transa=trans`, `transb=nontrans`; for each expert `a[i]=dq_gu[q_i]`, `b[i]=Xs + o0_i*2560`, `c[i]=GU + o0_i*1280`; `lda=2560`, `ldb=2560`, `ldc=1280`, `alpha=1`, `beta=0`.
* Down group: `m=N=2560`, `n=ne`, `k=640`; same transposes; `a[i]=dq_d[q_i]`, `b[i]=Hh + o0_i*640`, `c[i]=Dm + o0_i*2560`; `lda=640`, `ldb=640`, `ldc=2560`, `alpha=1`, `beta=0`.

These are the column-major views of the existing row-major `X[ne,K] * W[N,K]^T` operation. The output pointer-array entries must be disjoint. In noncompact layout, `o0_i=m.off[expert_i]` and each active expert owns a distinct `ne` row span in Xs/GU/Hh/Dm, so equal row count does not cause overlap. In compact mode `scratch_row=0` and `Xs/GU/Hh` are a single reused T-row region; two experts' pointers would alias. **Exclude compact mode** unless new separate buffers and a new measured lifetime proof are added.

## API support and precise limitation

The installed Intel oneMKL 2026.1 `blas/usm_decls.hpp` declares the USM pointer-array group overload returning `sycl::event`, including the mixed type `gemm_batch<sycl::half, sycl::half, float, float>` (around lines 808–823 and type instantiations at 878 onward). It takes arrays for transpose, `m/n/k`, alpha, A pointers, `lda`, B pointers, `ldb`, beta, C pointers, `ldc`, `group_count`, `group_size`, compute mode and optional dependency events. Intel's DPC++ reference lists the same mixed precision and says the returned event signals completion; group arrays contain `group_count` sets of dimensions and scalar parameters, with matrix pointer arrays sized to the total batch count. Thus a single group with `group_count=1`, `group_size[0]=2`, and the dimensions above is representable. Pointer-array form is the safer first implementation than strided batching: the GU/down DQ buffers are separate ring allocations, and pair order can start in slot 1 then slot 0, so a positive forward stride must not be assumed. A strided variant could be considered only after verifying every A/B/C pair's actual stride and ordering. [oneMKL 2026.0 `gemm_batch`](https://www.intel.com/content/www/us/en/docs/onemkl/developer-reference-dpcpp/2026-0/gemm-batch.html)

The repository DPCT pointer-array `dpct::blas::gemm_batch` supports `real_half,real_half,real_float,real_float` (`dpct/blas_utils.hpp:1205–1210`) and forwards to `gemm_batch_impl`. That helper builds a heap `matrix_info_t`, calls oneMKL group `gemm_batch` with group_count 1, then adds an in-order host task dependent on the returned event to free `matrix_info_t` (`dpct/detail/blas_utils_detail.hpp:372–417`). This covers the helper's own metadata lifetime. It **does not return the event**, and it does not put the caller's A/B/C pointer arrays into `matrix_info_t`; the caller must supply a separate lifetime policy for those arrays. The oneMKL documentation does not specify how long the host pointer-array storage itself is consumed, so do not assert that stack arrays are safe after return. Conservative safe design is to call the event-returning oneMKL overload directly and retain all arrays/metadata until its event completes, or to retain the DPCT-call arrays through the existing compute-queue drain before reuse/free. The direct call should be tested against installed headers and compiler as part of root-owned implementation; this report did not test it.

The `GEMM_SCRATCH` reservation is 32 Mi FP16 elements and `GEMM_WS=0` (`prefill.cpp:848–849`), but `Gemm::f16` does not reference `scratch_` or `workspace_`; it passes matrix buffers directly to oneMKL. The per-expert DQ ring is separate: `dq_gu[2]` each hold `1280*2560` half values and `dq_d[2]` each hold `2560*640` half values (`prefill.cpp:1372`). No additional dense weight or GEMM scratch is required for a two-entry batch. This makes the existing resources sufficient; the reserved 64 MiB GEMM scratch is not a proof of batch lifetime and should not be counted as new workspace for this path.

## Pair scheduling and buffer/event lifetime

A safe isolated scheduler for the normal direct path is:

1. Read the existing host route order/counts and form only adjacent pairs `(e0,e1)` where both are nonempty and `m.cnt[e0] == m.cnt[e1] > 0`. Preserve order exactly; send an odd final expert or unequal neighbor through the existing scalar path. Keep MMQ/fused, non-native and compact paths on current dispatch.
2. For a pair, enqueue both experts' existing GU/down dequantizations into `dq_gu[q0/q1]` and `dq_d[q0/q1]` on `m.cs`. Preserve expert source slots. Once each compressed blob has been read by its dequant commands, the normal ring `used` marker can release its staging slot; do not extend blob lifetime unnecessarily.
3. Submit the GU group on the same `m.cs` queue. In current `Prefill::init`, `m.gemm.init_external` configures its descriptor with `strata::q_of(stream)`, the same queue stored as `m.cs`, so the normal path has in-order sequencing. No extra event dependency list is required in that same-queue case. If a future implementation sends any stage to a different queue, explicitly depend on both dequant completion events before GU and on both GU/SwiGLU completion events before down.
4. Enqueue two normal interleaved SwiGLU operations for the now-disjoint GU output spans. Then submit the down group on the same in-order queue. The group outputs are separate Dm row spans, and beta remains zero.
5. Keep pair pointer arrays and dimensions/scalars in stable storage until the down group's event completes. Because the same in-order queue orders the GU group, SwiGLU work and down group before the next pair's DQ reuse, the returned down event also certifies earlier pair operations. The synchronous host scheduler may append retained metadata records to a per-chunk list and release them at the existing `m.cs->wait()` boundary; alternatively return/store events and retire each record only after its event is complete. Do not overwrite host arrays on the assumption that a device queue command orders CPU stores. DQ device buffers and Xs/GU/Hh/Dm regions must remain allocated and unmodified until their consumers' queue work completes; same-queue ordering handles subsequent writes only if all users remain on that queue.
6. If a batch submit is accepted and later errors, report the error through the existing outer synchronization/error boundary and fail the run. Do not retry those entries as scalar GEMMs after partial/accepted batch work; the outputs may already be partially written. A scalar fallback is appropriate only before any batch command is accepted (for ineligible pairs or an immediate pre-submit unsupported condition).

An implementation that cannot retain one pair's arrays through a completion boundary, cannot keep both expert route spans disjoint, or mixes queues without explicit dependencies is not safe. There is no oneMKL workspace blocker; the critical gaps are local wrapper event visibility and caller-owned metadata lifetime.

## Smallest correctness/service gate before integration

Use a synthetic native IQ4_NL fixture only to provide the same valid dequantized weights/activations for two logical experts. Exercise the exact active dimensions, both pair entries, and non-identical expert inputs/weights so swapped pointer order cannot pass unnoticed. Compare each scalar `Gemm::f16` output against its corresponding batch output, then run separate SwiGLU and down products and compare final Dm per row. Include equal-ne adjacent pair, unequal-ne ineligible neighbor, odd singleton, zero-count expert, and last pair in a chunk. Exercise disjoint noncompact row offsets and make compact-mode rejection explicit. Check finite outputs, maximum absolute/relative errors against the existing pre-registered numerical acceptance criteria, and route-row placement. Do not require bitwise identity unless the measured backend demonstrates it and the existing contract requires it; identical data types do not imply batch and scalar paths use the same reduction schedule.

For the service discriminator, warm both scalar and pair APIs with the same GPU and oneMKL/driver version; run matched alternating batches on the same queue and buffers. Measure oneMKL event durations and host submission time separately, drain after a batch (not after each expert), and also measure full MoE layer service/wall with the candidate enabled. No oneMKL promise states that a group batch maps to fewer device launches or runs faster; a successful `gemm_batch` call is not itself a speed result. Record equal-ne pair frequency from an actual >=32768 batched-position production A/B run before claiming model relevance; source alone cannot predict routes. Keep fallback/default behavior unchanged and no speed/adoption/full-KV claim unless measured.
