## Source shape and requirement

The generic `iq_dequant_f16(int t, ..., void* stream)` at `iq_kernels.dp.cpp:4318–4343` validates its arguments, resolves the queue through `strata::q_of(stream)`, then calls `queue->submit(...)` once. That submission contains one `parallel_for` with range `n/256` groups and local size 32, instantiating `dequant_flat_kernel_c7cec2` and calling the runtime-type `dequant_flat_kernel(t, ...)`. The private `iq_dequant_f16_prefill_iq4nl(...)` at 4297–4315 is compile-guarded; after type/null/size validation and fp16 capability check it calls `queue->submit(...)` once, with one `parallel_for` at the same geometry and `dq_iq4_nl<sycl::half>`. Both functions return `void` and currently discard the `event` returned by `submit`. Both end in a `check()` which source shows is a no-op placeholder (`const dpct::err0 e = 0`). The parity fixture calls these existing APIs directly (`prefill_iq4nl_parity.cpp:160–161`); duplicating the lambda in a benchmark would create an avoidable kernel-identity/body drift risk.

The desired measurement needs the exact event object returned by the existing `queue::submit` for each wrapper invocation. It must preserve the `void` APIs and kernel lambda bodies, avoid one wait per expert, and have no event-capture behavior in the default-off production build.

## Smallest viable design: private compile-guarded, thread-local receipt sink

Add an internal test-only receipt interface behind a distinct compile option, for example `STRATA_SYCL_PREFILL_IQ4NL_EVENT_RECEIPT`, that is legal only with the existing private-dequant and async/parity qualification options. Compile the queue submission source and the qualification harness with the receipt define in the dedicated test configuration; leave it off in the normal configuration. Do not expose the interface from public kernel headers and do not change either public `void` signature.

Under that define, keep one internal `thread_local` pointer to a test-owned receipt sink and a small RAII scope type in a private header, with its accessor defined once in the instrumented library so test and kernel translation units share one TLS instance. The test creates the scope on the thread that calls the existing wrappers. The two wrappers keep their present argument/capability checks and the exact same `parallel_for` lambda, but bind the result of that one existing `submit` to a local `sycl::event` and report it only if a scope is active. The event reported is the direct `submit` return; there is no queue-tail guess, second submission, or reconstructed event. Outside an active scope the compiled test variant only performs the inactive-sink check. In a build without the receipt define, preprocess to the existing direct `queue->submit(...)` expression and retain the current default-disabled path. A test-only preprocessor wrapper around the single call expression can preserve one lambda body if direct spelling is preferred; avoid copy-pasting the lambda into separate instrumentation branches.

The sink should be preallocated before any command submission, with fixed capacity sized for the planned component batch (or a bounded sample capacity for caller attribution). Each receipt should include the moved/copied `sycl::event` plus stable host metadata: a monotonically increasing call serial, arm tag (`generic` or `private`), queue pointer/identity, `type`, `n`, `src` and `dst` values, and scope/run ID. Those fields let the collector prove one receipt for every expected wrapper call and pair the correct event with dimensions and arm. Compare receipt counts and keys against independently counted calls after the ordinary batch/chunk drain; reject the timing result on any missing, duplicate, overflowed, or mismatched receipt.

Thread-local routing separates simultaneous host caller threads without a global mutex in the expert loop. Use nested-scope save/restore (previous sink pointer) in the RAII type; either reject nesting before submissions or define explicit parent forwarding. Do not silently fan out a single call as two receipts. For this isolated one-thread component test, the simplest rule is to reject nested measurement scopes and use one submitting thread. SYCL specifies that the runtime determines execution order when multiple threads submit to the same queue, so per-thread serials do not define a cross-thread queue order. A future multi-thread caller probe may retain per-thread streams and merge by explicit IDs after drain; it must not pretend those IDs alone recover actual queue submission order.

## Accepted-submission exception and lifetime contract

The event is available only after `queue::submit` accepts/returns. SYCL specifies a synchronous exception if command enqueue fails, but the wrapper has no returned event to prove identity if `submit` itself throws; treat that as a failed/unknown measurement and let the harness's existing fail-stop boundary protect any potentially submitted work. Any receipt-vector growth, string formatting, logging, lock acquisition, or exception escaping after a successful return would create a post-submit failure window. In particular, dynamically allocating a vector node or building labels in the receipt hook could throw while the kernel remains queued. The hook must therefore be `noexcept`, use preallocated bounded storage, and make overflow/capture failure a sticky “measurement invalid” flag rather than throw back through the void kernel API. The caller then reaches its already-planned queue drain and rejects the run; it must not free input/output USM or claim timing because a receipt was lost.

The SYCL header in the pinned compiler declares event copy/move assignment as defaulted but does not declare it `noexcept`. Do not assume event retention cannot throw. Catch failures inside the no-throw recorder, mark the receipt stream incomplete, and continue into the normal batch completion/error boundary. In the isolated harness, any other exception before completion is known must use the established unknown-completion fail-stop policy (no USM unwind). If the normal queue drain completes and capture had failed, USM is safe to clean up but the sample is discarded. For production-call instrumentation, do not add a new throw or wait in the expert helper; report capture loss through preallocated state and validate it at the existing chunk boundary.

The collector and retained event objects must remain alive through completion and timestamp queries. Keep their storage, test input, output allocations and queue scope alive until the planned batch drain and readback complete, then release events before destroying their queue if practical. A failed receipt alone is not permission to reclaim potentially live buffers; cleanup follows known completion, otherwise fail-stop applies. No event should be retained indefinitely: bound samples and clear them after query/drain.

## Event semantics and correct timing quantities

Khronos SYCL 2020 says `queue::submit` returns the event representing the submitted command group. The specification's profiling descriptors are nanosecond timestamps sharing an implementation-defined timebase for events on the same backend. `command_start` may block until the command is running or complete; query all timestamps only after the batch's already-required completion point. Compute per-call service as `command_end - command_start`, and queue delay as `command_start - command_submit`. Record host `std::chrono::steady_clock` duration around the wrapper call separately as submit-call latency. Do not subtract host clock values from SYCL/device timestamps or label `command_submit - host_start` as queue delay. The command-submit event timestamp is produced during/after the command-group function and before `queue::submit` returns, so host wrapper latency and device queue delay are different quantities.

The existing `device_ext::create_queue_impl` attaches `sycl::property::queue::enable_profiling()` to queues, and its in-order factory adds the in-order property; `create_queue(true)` also installs the existing exception handler. This supports the intended production-owned queue path at source level. The test must still record `has_property<enable_profiling>()`, backend and in-order status on the exact queue passed to each API, because the wrappers accept arbitrary `void*` queues and `strata::q_of(nullptr)` maps to the default in-order queue. A queue lacking profiling makes event timestamp queries invalid; receipt capture remains possible, but the timing run must fail its admission rather than silently fall back.

References: [Khronos SYCL 2020 queue::submit and returned event](https://registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html#_queue_class); [Khronos SYCL 2020 profiling descriptors and timestamp timebase](https://registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html#_profiling_information_descriptors); [Intel LLVM SYCL event API declaration](https://github.com/intel/llvm/blob/sycl/sycl/include/sycl/event.hpp) (current upstream source is implementation evidence only; the installed local header is the one reviewed for the pinned compiler).

## Alternatives and blockers

- **Return an event from either kernel API:** rejected because it changes the public function type/ABI, contrary to scope.
- **Add a separate test facade that calls the existing void wrapper and then asks the queue for its last event:** cannot prove it got the exact command. Another host thread or queue submit can intervene; a wrapper-internal `check()` or runtime action could also alter what “last” means. `ext_oneapi_get_last_event()` describes queue state, not a receipt tied to this function invocation.
- **Duplicate the generic/private kernel body in the test:** rejected because it would measure a copy that can diverge from production helper code and violates the no-duplicate-kernel-body constraint.
- **Unconditionally assign `auto e = queue.submit(...)` in ordinary builds and ignore it:** avoids ABI changes but modifies the default-off production helper's object lifetime and host code path. Do not choose this when preserving the default path is required.
- **Use a global sink or an unbounded vector callback:** global state races across concurrent callers; an unbounded vector can allocate/throw after submission. Prefer the compile-guarded TLS sink plus bounded preallocated collector.
- **Use per-expert event waits to avoid retention:** invalidates the existing asynchronous schedule and changes the measured work. Record events while submitting and query after normal drain instead.

There is a practical build-isolation tradeoff. The source to be instrumented is compiled into `strata_kernels`; defining the receipt option on that static library in a dedicated qualification build is simple and default-off. That build may also link a test-enabled application target, so the receipt branch exists in those test-build objects even when no scope is active. Normal production builds with the option off remain unchanged. If absolutely no instrumented kernel object may be linked into the application in the qualification configuration, a separate instrumented `strata_kernels` variant is possible but substantially duplicates CMake target construction; it is not the smallest change and should be justified by an explicit artifact-isolation requirement.

## Prior-work avoidance and measurement limits

R176 already establishes the measurement sequence, queue profiling property, per-batch deferred query, component-vs-real-caller distinction, and prohibition on per-expert synchronization. This report only resolves the missing mechanism for retaining the exact event from the two existing `void` APIs, plus its exception/lifetime and threading constraints. The actual 84-case exact-bit parity result, isolated host-task error-boundary result, and prior production integration review do not establish event capture or timing correctness. The production experiment remains withheld; no speedup, call count, model result, full-262144 result, device-fault result, or adoption is claimed here.

A component-only direct-helper measurement can answer isolated DQ service cost. Any claim about prompt/model benefit still needs a real batched prompt at least 32,768 positions and actual per-call/call-count receipts, with generic/private routing otherwise held constant. There is no arbitrary minimum gain threshold; decide admission based on measured uncertainty and the requested outcome. Do not infer service savings from host submit-call latency or total DQ phase timing.
