## What the current ordinary path does

`Prefill::run` in current `prefill.cpp` selects `run_layer_major` only when `STRATA_PREFILL_LAYER_MAJOR` is set to `2`, or to `1` with multiple chunks; otherwise it calls `run_impl` (lines 2436–2444). Thus a run with that override explicitly disabled follows ordinary chunk-major execution, subject to its selected `m.T` and any surrounding borrowing/transfer settings. A `--prefill 12288` request alone is not proof that `m.T` stayed 12,288: startup may shrink a fixed chunk when its admission calculation does not fit, and it can size to the actual prompt segment. The current caller initializes Prefill with `o.prefill_chunk`, passes `n_batched` to `run`, and has its own borrow/lend and fixed-fit decisions (`generate.cpp` 11672–11770). The parent run must retain the log evidence of selected chunk and fallback status.

`run_impl` sets each chunk length to `min(m.T, n-c0)` (with a separate optional first-chunk setting), iterates `c0` in increasing prompt order, computes absolute position `p0=pos0+c0`, and invokes each layer in order for that chunk (`prefill.cpp` 3021–3025, 3064–3074, and layer loop near 3616). PLE rows are formed using the carried two-token history and prompt tokens, then `prev` advances through the chunk; the final `ss.ple_prev` is saved after the walk (3026–3034, 3240–3245, 5331–5332). GDN uses the layer's existing recurrent/convolution state, projects the current T rows, applies `gdn_conv`, then `gdn_recurrence` for T rows (3760–3783). QSA generates per-position step records; it appends indexer rows for the chunk, and scores/selects query batches against the completed prefix plus the current incomplete block (3246–3257, 3870–3910). K/V is appended at absolute `p0` for the T positions before attention consumes it (around 3848–3870). These paths make token order and state carry causal: chunk-major's intended semantics require the same positions, prior state and layer order across chunk boundaries.

The allocation and batching source accepts a general positive T rather than requiring a power of two or a 256-token multiple. Sizing/carving uses `size_t`/64-bit extents; `T_max` is set from the supplied chunk (1051–1055, 1116–1117), and the shared region uses `max` of HC/PLE/GDN/QSA/MoE scratch sizes (1292–1305). QSA score/attention loops and prompt-attention batch cap use `min` for the final short batch (prompt_attn_batch at 923–931; selection batch loop around 3895–3910). PLE's compact sizing comment explicitly retains original GEMM row counts “including an odd final chunk” (877–884). No source evidence reviewed here establishes every allocation or kernel safe at 12K in every build; the source count and current run's allocation log remain needed. 12,288 equals 48×256 and 12×1024, but that arithmetic is only a convenient divisibility fact, not a correctness proof.

A 12,288 fixed chunk also does not divide typical conditioning lengths evenly because the generation path batches prompt positions `[0, n_prompt-1)` and leaves the final prompt position to the token loop (`generate.cpp` 11672–11682 and 11770–11809). For a 32,768-token prompt this means `n_batched=32,767`, nominal chunks 12,288 + 12,288 + 8,191. For a 262,144-token prompt it means 262,143 conditioning tokens: 21 full chunks (258,048 tokens) plus an 4,095-token tail, then the final prompt token is processed by the token loop. Tail handling is part of the correctness gate; a 32K run does not qualify full-context occupancy or the full-context tail.

Chunk boundaries preserve the intended position/layer/state order in `run_impl`, but they can change batched operation shapes and numerical accumulation. Current code documents QSA score tensor-core math as “FP32-level, not bitwise” (around 3900), and a chunk can alter projection/GEMM row grouping and kernel/batch selection. This makes numerical sensitivity a plausible test concern, not an explanation for a large mismatch. Current source review cannot establish whether 12K ordinary chunk-major matches the accepted 8K baseline; the complete state/head/output numerical gate must answer that.

## What the previous 12K rejection establishes

It reported 63/66 main-state parts different, all 248,320 first-head floats changed (max absolute 0.8735668659, RMS 0.1801613686; both argmax were 40), first generated ID changed at zero-based index 2 (baseline 3286, candidate 22903), and MTP counters 38 accepted / 75 offered versus the 8K reference's 43 / 66. It had no clean timing result. The status is rejected correctness, not a hang or an accepted alternative. The later exact-word health check passed; that does not reverse the math result.

The old README describes its comparison as changing compact-HC chunk from 8,192 to 12,288 at constant 32,768 input, but its complete treatment also used full GPU residual rows and the layer-major route with cache and MTP payload leases/restores. That differs from current normal chunk-major `run_impl` with no layer-major setting. Its earlier binary/source baseline also predates the current W HEAD. The rejection therefore proves that that combined old configuration did not pass its 8K mathematical gate. It does not show that current ordinary chunk-major 12K fails, identify chunk boundaries/GEMM rounding/lease behavior as the cause, or show a correction. Conversely, it cannot be used to waive parity testing for the current ordinary path.
