# R278 — Returned oneMKL event duration and shape-roof contract

Date: 2026-10-10 (Asia/Tokyo). Read-only source and primary-reference audit. No build, test, device/GPU/process query, profiler run, Git operation, source edit, cleanup, or service action was performed. This report is the only file written.

## Conclusion

`Gemm::f16_event` provides a valid oneMKL completion dependency when its returned event completes. Neither the public oneMKL contract nor the checked SYCL event contract says that the event's `command_start..command_end` timestamps enclose all internal oneMKL work. They do not establish that the timestamp pair represents the full routine, nor do they specify that it corresponds only to a final internal command. For the installed implementation, the choice requires operation-level observation on the same software, device, queue and shape. Until that evidence passes, `returned_event_ms` is correctly named as a returned-event duration, not a full GEMM service interval, exclusive GPU busy time, or throughput denominator.

A production-shape harness is feasible for the distinct `(role,T,N,K,ldy)` classes present in a bounded routed request. Testing every theoretical `T=1..6495` is a different and much larger sweep; neither the tiny T=7 canary nor a few synthetic M points covers that shape roof. Even an exact shape sweep would not itself prove production call attribution or a request critical path. PTI coverage and dependencies must be reconciled separately.

## Contract and exact source path

The pinned caller is `diag-sycl-prefill-service-qualification-20261010/sycl/src/prefill/gemm.dp.cpp`, `Gemm::f16_event` at lines 787–802. On the Intel oneMKL USM path it validates dimensions and queue identity, then calls DPCT `blas::gemm` with `(N,T,K)`, transpose/nontranspose, FP16 inputs, FP32 output/compute, and writes one event to `returned_event`. It makes no internal commands visible to the caller. The actual native expert caller in the private GEMM-only source passes `T=ne`, `N=out`, `K=inner`, `ldy=out`; GU uses `(N,K)=(1280,2560)` and Down `(2560,640)` for the current model geometry. `ne` is route data, so the tested M set must come from the exact route, not token count or a chosen synthetic point.

Intel's USM GEMM reference describes the output event as one “to wait on to ensure computation is complete.” That is a completion guarantee, not a timestamp-envelope guarantee. SYCL describes `command_start` and `command_end` as timestamps for the action associated with an event's command group. The public oneMKL reference does not document which command-group action its library event represents when a routine internally submits multiple operations. The supported conclusion is therefore bounded: waiting on the returned event establishes routine completion; duration interpretation beyond the associated event action remains to be measured for this implementation. [Intel oneMKL USM GEMM reference](https://www.intel.com/content/www/us/en/docs/onemkl/developer-reference-dpcpp/2025-2/gemm.html), [SYCL 2020 event profiling contract](https://registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html#sec:event-profiling).

## What current evidence establishes

The saved B570 small-device qualification called the same wrapper once at `T=7,N=11,K=13,ldy=17`. It checked all output floats and padding, event completion, and monotone submit/start/end timestamps. The returned action span was 8,750 ns in that run. Its stdout explicitly says “not internal kernel coverage”; the trace summary did not show GPU kernel entries. It establishes wrapper/output behavior and that the three profiling fields were queryable for that small case. It says nothing about production algorithm dispatch, internal command count, or complete operation-span coverage.

The private GEMM-only ledger source is pinned in the parent handoff (header SHA-256 `7d473f68dcfdb48660c50cff0e75c6191e5b3339ed95901a1aa4286f38bbff06`; caller SHA-256 `1cf7e911a555e8611c1368a4d18d4ba81c95027bb8de77f89ad65ac64b05fc3c`). When enabled, the ledger checks queue profiling admission and queue identity; keeps bounded pending events; checks completion when folding; queries submit, start and end for each folded event; validates monotonicity; reconciles expected GU/Down route pairs; then accumulates shape and `(chunk,layer,role)` totals. It stores shape identity and sequence bounds but not individual event IDs or timestamp triples in its report. Thus it can establish internally consistent counts and aggregate returned-event durations after a valid full request, but it cannot join one production event to a PTI operation set.

For `E` retained/folded GEMM events, the present lane performs `3E` profiling timestamp queries, plus completion-status queries during fold and the existing queue admission checks. It has caps of 65,536 events and 16,384 shape/coverage buckets. A single chunk with 48 layers and up to 512 expert pairs per layer gives the existing worst-case bound of 49,152 GEMM calls and 147,456 profiling timestamp queries; role coverage is 96 buckets. The theoretical row roof has at most `2 × 6495 = 12,990` role/row classes, below 16,384 if each role's other shape fields remain fixed. This arithmetic only shows the ledger's nominal event and bucket capacities for that bounded case. Multi-chunk requests can exceed the event or coverage caps; every planned request must be preflighted, and any cap hit or dropped record invalidates the aggregate. PTI's event buffer is a separate cap and must be sized and checked independently.

The report's aggregates (`returned_event_ms`, `submit_to_start_ms`, host submit/stager/ring wait fields) are different clocks and scopes. Summing returned-event durations is not a critical-path calculation when internal helper operations, queue gaps, or overlapping work are not represented. A positive gap between consecutive event endpoints is not “idle”; it may contain queueing, other work, or an unclassified command. Do not subtract event intervals from host-call, staging, or copy intervals without an explicit common-clock correlation.

## Shape qualification and analysis boundary

The finite next discriminator is an isolated harness using the same `f16_event`, oneMKL/DPCT binary and profiling-enabled queue as production, with the exact `(role,T,N,K,ldy)` histogram harvested from a bounded native route. It should run one case per distinct observed class with exact USM types/layouts and descriptor parameters; setup, initialization, warmup, and output checks must sit outside each target window. A separate bounded PTI capture needs a visible begin/end marker, target operation visibility, complete queue/engine and host-device-flow records, explicit event-buffer sizing, and a measured SYCL-to-PTI clock mapping with uncertainty. Keep all internal GEMM/helper/copy operations attributed to each call; names or matching durations alone do not establish attribution. PTI documents `--device-timeline` and `--kernel-submission` for device intervals and `--chrome-kernel-logging` for device events plus host-device interactions/dependencies; the trace must also demonstrate that the target and markers are actually visible. [Intel PTI-GPU unitrace documentation](https://github.com/intel/pti-gpu/blob/master/tools/unitrace/README.md).

For each isolated shape and repeat, full-span qualification requires: correct output; completion; valid timestamps; all target-caused device operations visible and attributed; and returned-event start/end covering the first-to-last associated operation within measured cross-clock uncertainty. A pass applies only to those tested shape classes and that pinned B570/runtime/library/queue configuration. If completion passes but operation visibility or interval coverage fails, keep the event as a completion token and do not promote its duration to full-routine time.

A later actual-prefill trace is still needed to show transfer of the isolated result to native route calls. The current ledger has no per-call timestamp/event-ID receipt, so a unique one-to-one PTI join requires either a single-call isolated window or a bounded opt-in sequence receipt with `(chunk,layer,expert,role,T,N,K,ldy)`, thread/queue identity, call order, completion and timestamps, joined through verified flows. Do not insert a production queue marker per GEMM without separately accepting and quantifying that scheduling change. Aggregate per-role/per-M totals are useful for route/shape distribution and exploratory ratios, but they cannot prove per-call PTI coverage.

Even with complete operation coverage, distinguish three quantities: individual operation intervals; their union/first-to-last envelope and dependency critical path; and exclusive hardware busy time. PTI kernel intervals can overlap across engines/queues, so summing durations can double-count. A complete event envelope can include gaps and is not exclusive busy time. A FLOP count divided by returned-event milliseconds may be retained only as an explicitly labeled event-duration quotient after the event's full-operation meaning is qualified; an “achieved GEMM FLOPS” or model service rate additionally needs an uninstrumented, independently measured denominator and correct workload count. The PTI capture is for command coverage, not a clean speed result.
