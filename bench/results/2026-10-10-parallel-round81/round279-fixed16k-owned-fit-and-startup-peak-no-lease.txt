## Owned-workspace calculation

For the recorded compact-HC layout, the relevant source geometry is `N=2,560`, `D=10,240`, `HC=4`, `LR=320`, `K=10`, `NE=512`, `C=10,240`, `ZV=6,144`, `HV=48`, `DQ=2`, 8 ring slots, and `MAXBLOB=2,662,400 B`. `Prefill::bytes_needed_owned` calls the same sizing sequence as `init`, but rounds every `Alloc::take` to a 2 MiB page and adds 8 MiB alignment slack. This is the engine's conservative estimator, not measured Level Zero allocation granularity. `init`'s `accounted bytes` instead sum 256-byte-aligned requests and are not the allocator's physical commitment.

The shared region is the maximum of HC, PLE, GDN, QSA and MoE terms. Here compact PLE is largest: `T * ((3*10240 + 2560 + 4)*4 + 2560*2 + 4096) = T * 142,352 B`. At 8K/16K/32K it is respectively 1,166,147,584 / 2,332,295,168 / 4,664,590,336 B before the outer allocation's page rounding. The full 262,144 context sets `m.max_blocks = 262144/4 + 2 = 65,538`; the corresponding QSA score table remains below this PLE region at all three chunk sizes, so it does not replace the shared-region maximum. The current source returns the same fixed geometry and QSA/GDN carve as the prior offline count; the changed context-sized QSA term does not change the winner.

## Does the 1,565 MiB baseline admit fixed 16K?

No, under the observed same-owner set and without a new lease. The OFF32K stderr records the 8K layout first (`1,861,857,536 accounted`, `1,166,147,584 shared`) and then `1,565 MiB VRAM free with everything loaded`. Thus the free reading already includes the 8K workspace. Replacing it with the 16K workspace costs about 1,672.5 MiB of source-accounted additional requests, exceeding the observed free amount by about 107.5 MiB before fragmentation or first-use allocations. The source's own 2 MiB/page estimator gives a 1,672 MiB increment and a 107 MiB shortfall. A 32K replacement exceeds the reading by about 3,452.5 MiB on the accounted count.

The server startup path confirms that this is a real initialization peak: its persistent `Prefill sp` is initialized in `init_prompt_paths` before the `free with everything loaded`/`READY` block. The prompt workspace is not a per-token temporary that the server frees after every completed request; it remains available for later requests and is reset only in the startup fallback path after an unsuccessful initialization. The user-visible free sample follows Prefill setup, and later startup objects remain live. R275's CLI statement that `Prefill` initialization precedes `mtp.bind` is not proof of server startup order; the server is the relevant caller here.

The server's existing `own_fits` check runs before prompt-path init, uses `Prefill::bytes_needed` and keeps a 512 MiB headroom when MTP is enabled. It does not use the owned-page estimator. On an explicit fixed request that fails this test, the normal server path steps down through `{6144,4096,3072,2048,1536,1024,512}` rather than guaranteeing the requested 16K. Therefore an `INFO`/`READY` context value is not evidence that fixed 16K was selected. The current 8K success is the only observed selected/allocated chunk here.

## Other allocations and possible narrow levers

`STRATA_KV_STAGE_OWN=1` and streamed int8 KV make `take_stage` allocate a fixed pool outside the counted `Alloc`; with 262,144 context cells, 12 QSA layers, 2 KV heads, page size 4, and int8 K/V plus scales, the pool is 264 MiB. It is allocated during Prefill init and is already represented in the post-init free reading, so it is not another 16K delta; however, the `bytes_needed` preflight also skips it and cannot certify this peak by itself. `GEMM_SCRATCH` is included in the workspace count (32 Mi uint16 elements = 64 MiB); current `GEMM_WS=0`. The server reserves 512 MiB for later/window/head/BLAS allocations when MTP is enabled. The retained free reading follows window-buffer and draft-head logs (64.5 MiB and 212.9 MiB), but it does not measure all first-use oneMKL/runtime allocations or desktop/other-process variation. Keep at least the source's 512 MiB admission headroom and treat further margin as unmeasured.

The closest existing memory knobs are `--kv-resident` and `--expert-cache`; both change residency/caching, not tensor math, but can change transfer/service behavior and require the same numerical and performance gates. Lowering `--kv-resident` from 32,768 to 16,384 saves about 198 MiB of device-resident int8 QSA K/V plus scales (`16,384 * 12 QSA layers * 1,056 B/cell/layer`); host KV and the fixed stage pool remain. The current 128-slot expert cache is about 325 MiB; reducing it to 64 slots frees roughly 162.5 MiB. Together they add only about 360 MiB, still below the roughly 620 MiB needed to cover the 16K increment plus the existing 512 MiB headroom. Lowering those settings further could alter hit/stream behavior materially and has no retained qualification evidence. Do not call this a safe-fit recipe.

`Prefill::reset()` is public and drains/frees the object's workspace. It could reduce idle residency if a caller resets after a successful prompt and before a later phase, but the current server has already paid the startup allocation peak before READY; freeing after the first prompt cannot make the first fixed 16K init fit. Reinitializing on every request also changes allocation/reuse behavior. The existing MTP draft release callback is reached on the layer-major route only after Prefill init; it cannot create the startup headroom for that init. R275's external pre-init MTP lease remains a future design, not an existing option or proof of fit.

## Decision and limits

Do not claim fixed 16K is admitted by the current 1,565 MiB post-init free sample. The direct source-count delta already exceeds it, and the server's own admission check preserves another 512 MiB; a future fixed request may step down. 32K is well outside this no-lease envelope. Reconsider only after a serialized, source-supported ownership change or materially smaller cache/KV residency is measured, and record actual selected chunk, exact allocation/high-water/free sample, later scratch, and full-context correctness. The OFF32K state/output parity result is not a 16K fit test or a 262,144-token prompt qualification.
