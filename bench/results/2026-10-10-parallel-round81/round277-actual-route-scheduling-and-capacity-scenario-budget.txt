## 16K/32K chunk-growth deduplication bounds

The current census line for each layer/chunk stores marginal counts by exact `M` and source, but not expert IDs. Neither `record.json` nor `census.jsonl` records which expert occupies each bin. Thus exact cross-chunk ID intersections and the exact new per-M histogram are not recoverable from these retained artifacts. I did not infer IDs or run a new inference. The following are rigorous occupancy bounds from each layer's measured active-expert counts and the 512-expert universe, not the often-assumed exact halving:

For one merged group of chunks with active expert sets `A_i`, merged expert calls equal `|∪A_i|`, bounded by `max(|A_i|) <= |∪A_i| <= min(512, Σ|A_i|)`. For copied IDs, apply the same bound to the subset with census `source=3` (stager-RAM), holding each chunk's recorded source label fixed. Each expert blob size is layer-specific but equal for all experts in that layer, so its copied-byte bound is the copied-ID bound times that layer's recorded `blob_bytes`.

Here GB is decimal. Corresponding conditional payload times are 14.89–15.60 seconds at the independent 6.4468 GB/s pinned/USM attained probe, 20.84–21.84 seconds at 4.6052 GB/s pageable probe, and 12.18–12.77 seconds at the 7.8769 GB/s encoded Gen4x4 line-rate ceiling for 16K; for 32K, 7.50–7.80, 10.50–10.92, and 6.14–6.38 seconds. These are payload÷rate scenarios only. They are not active-copy durations, actual request time, guaranteed candidate savings or upper/lower wall-time bounds. Submission, memory-source mix, caching and overlap remain unmeasured in a clean matched run.

Rows are conserved because chunking changes grouping, not router selections or prompt length. The merged call count changes the mean M to 320.1–333.3 at 16K and 640.0–661.6 at 32K. It does not multiply every existing M by two or four. For example, if one expert has 14 rows in the first 8K chunk and 9 in the next, its merged M is 23; if absent in the second chunk, it remains 14. Since IDs are missing, the exact result distribution is unknown. The current 8K per-chunk maximum M values are 4,889 / 5,722 / 5,713 / 6,495. Thus merged max M is at least 6,495; conservative same-layer upper bounds from these marginals are 12,208 for a 16K pair and 22,476 for the 32K group. Exact per-M bins require recording `(layer, expert_id, chunk, rows, source)`; the present histogram cannot support an exact M-conditioned GEMM/dequant budget.

The packed-byte bounds also assume the joined source labels remain meaningful in the combined schedule and each copied ID is loaded once per merged layer group. A new cache/admission plan can alter resident/staged classification. So the bounds describe reuse available from the recorded routes, not an assertion that the future planner will copy those exact bytes.

## Keep the 50.292 GB and 190.241 GB cases distinct

The **190.241 GB** number is the actual caller-accounted copied payload across four 8K chunks. It must not be replaced by the distinct/full-pack case. Summing `512 × blob_bytes` once for each of the 48 actual layers gives **50,292,326,400 B (50.292 GB; 46.838 GiB)**, the logical payload for a full all-expert pass over the model pack once per layer. It is a useful one-pass scale and is the upper end of the 32K route-union byte bound, but it is not the copied payload of the measured 8K run.

The current layer-major implementation keeps one full layer's packed expert cache and processes every current chunk through that layer before advancing. It therefore already avoids repeated packed-weight loads across chunks for that layer, at the cost of loading every expert in the layer, including experts not routed in the prompt. It still performs route/dequant/GU-GEMM/SwiGLU/Down-GEMM work per chunk; it does not concatenate `M` across chunks. For this pack the single layer cache is sized with 512 uniform `MAXBLOB` slots: 1,363,148,800 B (1.2695 GiB). The one-pass actual packed blob payload over all layers (50.292 GB) is not the cache allocation size and is not the current route's 190.241 GB.

The isolated seven-pair O2 AOT expansion fixture's medians, weighted by the **actual current format-pair call counts**, total 10.743 seconds (10.333–10.828 using process-median ranges). This is a device-resident packed-weight capacity-equivalent for existing calls, not production time or exposed critical path. It cannot be multiplied by the new lower call count as a forecast: merged M changes GEMM/dequant cost and the fixture is not an M-conditioned production build. The current census's 919.192 GB expanded-output count is also not H2D input and must not be added to the 190.241 GB copied payload or this isolated service figure. Do not add packed-copy and dequant scenarios as if serial; their actual operations may overlap.

## Schedule choices and the 10,240-float residual

**Chunk-major plus larger chunks** is the direct route-consolidation experiment. The normal path runs each token tile through all layers and keeps its residual on the device chunk workspace; it does not need a full-prompt residual spill plane. With IDs joined, 16K/32K can combine each expert's rows across adjacent chunks, reducing routed call count and reloading each repeated staged expert once within that larger layer/chunk. The bounds above show meaningful call/copy reuse potential, but only an exact merged-M receipt tells the shape mix. Workspace is chunk-scaled and source-side admission/correctness/performance for 16K or 32K is unproven. Keep fixed chunk sizing distinct from `auto` when no cache borrowing is disabled: R275 documents the auto fallback.

**Existing layer-major, group width one**, has a different trade: it loads all 512 packed blobs for each layer once and reuses them across 8K tiles. It does not reduce the 93,505 expert route/GEMM call count or merge M. It holds a host residual plane between layers. Correct residual width is `D=10,240` FP32 values per token (four streams × 2,560), not 2,560. For this request the batched prefix is `n=32,767`; its plane is `n×D×4 = 1,342,136,320 B` (1.249962 GiB). A host spill after each of the 47 layer boundaries writes this plane D2H and the next layer reads it H2D: 58.748 GiB each direction, 117.496 GiB combined logical residual traffic. For a 262,144-token prompt, the batched prefix is 262,143 and the plane is 10,737,377,280 B (9.999962 GiB); 47 boundaries imply 469.998 GiB each direction. These are host↔device residual extents from the source schedule, not DRAM measurements or time forecasts. Current layer-major additionally requires resident QSA K/V and has other live session, workspace, cache and runtime objects; it is not qualified at full context.

**Adjacent-layer group-major** is a bounded middle order: keep `g` neighboring layers' experts resident, process tiles in increasing token order through the group, spill residual only between groups, then retire the group after its consumers complete. The causal GDN/QSA order can be preserved only if each layer still sees tiles chronologically, the PLE prefix advances once, group slot maps are disjoint and stable, and queue fences precede cache reuse. R263 marks this as a design, not an implementation. It reduces residual boundary crossings relative to layer-major width one, not relative to chunk-major (which has no full-prompt spill). For 48 layers, groups of 2 and 4 leave 23 and 11 boundaries:

This grouped schedule does not, by itself, combine M across tiles; with 8K tiles it retains the same per-expert route/dequant/GEMM call totals. Each group must hold its weights simultaneously: R47's metadata budget gives exact packed payload peaks of 2.3071 GiB for width 2 and 4.5288 GiB for width 4; current uniform `MAXBLOB` slots reserve up to 2.5391 and 5.0781 GiB. These are group-cache sizes, not free-memory readings. At full context the resident-QSA subtotal alone is 6.4375 GiB before base weights, GDN/PLE, Prefill, cache, graphs and workspace; width 4 is not admitted by nominal device capacity even when the subtotal is combined only with that QSA value. Width 2 still has no demonstrated simultaneous-allocation margin. At 32K the numerical run's 1,564 MiB startup-free reading is not a post-Prefill/group-cache peak and proves neither fit nor failure after a different lease/order.

Chunk growth and layer grouping can be composed, but their budgets must not be double-counted: if a group retains the packed weights across its tiles, the group has already removed repeated weight fetches like layer-major. Enlarging tile M may then reduce route/dequant/GEMM calls, but will grow per-chunk workspace; it does not further reduce the same within-group packed-weight fetch below one per expert. Conversely, layer-group residual savings do not imply a lower routed-call or expanded-output count.

## Capacity and decision

The independent H2D probe gives 6.4468 GB/s attained for pinned/USM and 4.6052 GB/s for pageable transfer; the encoded Gen4x4 external-link figure 7.8769 GB/s is a physical line-rate ceiling, not achieved application bandwidth. The measured 10.743-second expansion capacity-equivalent and transfer payload scenarios are separate lanes. No valid sum is a request-time estimate because copy, DQ, GEMM, host route preparation and waits can overlap. The failed combined profile supplies no clean overlap intervals; the separate GEMM-only run is the next discriminant. The current `mean M=168.2` must not be used to interpolate the O2 shape fixture into a candidate 16K/32K GEMM estimate.

The most direct architecture question is whether chunk consolidation exposes less repeated staged payload and fewer calls without exceeding owned-workspace capacity. It can plausibly change work materially (bounds above), while preserving the current no-full-residual-plane path. The alternative layer-major path can lower packed reads to a full one-pass pack but adds up to 117.5 GiB of logical residual traffic for 32K under width one and requires resident KV. A grouped order trades the same full residual backing for fewer group boundaries, at the cost of 2.3–4.5 GiB exact group expert payload before other simultaneous owners. None is shown to improve end-to-end wall time.

Before a timing claim, retain an ID-level `(layer, expert, chunk, M, source)` census for an already-authorized same-input run, join it to merged schedules, and record exact merged-M histograms, source bytes, and successful copy/compute completion intervals on the qualified queues. Keep a separate clean application-wall sample. Fixed 16K/32K workspace allocation and capacity, and complete full-262,144-context state/final-token/decode gates remain mandatory. Do not turn the current ON/OFF numerical pass, route census, isolated capacities or group-byte arithmetic into a performance, fit or full-context claim.
