# R280 — GEMM returned-submit clock rejection and safe denominator

Date: 2026-10-10 (Asia/Tokyo). Read-only audit of the closed GEMM-only run and primary specifications/source. No runtime, device/GPU/process query, build, test, Git operation, source edit, retry, or cleanup was performed. Only this report was written.

## Disposition

Keep the 32K GEMM-only timing result rejected. The request itself completed normally and passed its numerical/state checks; the event-measurement lane failed its timestamp-order contract. This is an invalid measurement, not an invalid numerical result and not a GPU hang. Do not relax the `submit <= start <= end` guard, clamp negative deltas, apply a guessed offset/tolerance, discard failing calls, or retry the same 32K flag run.

The closed receipt is `owned-prefill-gemm-only-code32k-diagnostic-r1/record.json` (SHA-256 `dd929ca6c954163f0116ce0492dbfbdb316d727761e1cbc31f27f39eda3826da`); its stderr is `debugger/inferior.stderr` (SHA-256 `7e088e1d04f3eed3ed59f981bf3711c581c27938c58ee5f489d6c62175a3aa6c`). Preserve both unchanged. The record reports a normal exit (`exit_code=0`, no signal), cleanup `forced=false`, no surviving inferior/debugger, no new GPU-fault messages, and a passed math gate: 64 generated outputs, exact first-head/IDs/log-probs/MTP/state-part comparisons, and all 66 live-state parts equal. ## Contract and timestamp-path audit

SYCL 2020 specifies 64-bit nanosecond profiling values on an implementation-defined timebase; events on the same backend share that timebase. It defines `command_submit` as the queue-submission time, `command_start` as action start, and requires `submit <= start <= end`. Therefore, for faithful descriptors from the same event/backend, a negative `start-submit` is a contract failure. A constant epoch offset would cancel when comparing those two values; ordinary host/device cross-clock calibration cannot make the negative delta valid. [Khronos SYCL 2020 event-profiling contract](https://registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html#sec:event-profiling).

The source trail identifies where a discrepancy could arise, but does not prove which branch produced this receipt:

- The pinned public SYCL candidate at commit `fbccb466cc122c294a6c746dcf0d37e45ff70f3c` caches `command_submit` in `event_impl::setSubmissionTime()` by sampling `Device->getCurrentDeviceTime()`; its device implementation calls `urDeviceGetGlobalTimestamps`. The public SYCL getter later returns that cached value for `command_submit`, while it obtains `command_start` through the event profiling API. The same candidate documents that its *submitted executable-command-buffer* estimated submit clock can lead actual start, and clamps it only for events marked as coming from that submitted-command-buffer path. This is evidence that an estimated/cached submit sample can be ahead, not evidence this oneMKL returned event is such an event or that this public commit matches installed `libsycl`.
- The public current `intel/llvm` Level Zero v2 `event.cpp` candidate handles ordinary `command_start` by querying `zeEventQueryKernelTimestamp`, masking the returned global kernel-start counter and converting it with the device timer resolution. Its direct UR queued/submit query branch returns zero and comments that submit is instead captured by `urDeviceGetGlobalTimestamps` before enqueue. In the SYCL route above, that upstream cached value, not the UR event getter's zero, supplies `command_submit`. This is a public current-branch candidate, not an exact oneAPI 2026.1 source pin. Prior R196 records that the shipped compiler/UR source-revision mapping remains unestablished.
- The Level Zero specification says `zeDeviceGetGlobalTimestamps` returns synchronized host/device global timestamps. It also says kernel timestamp events use finite-range counters that can wrap, requires `kernelTimestampValidBits` and timer resolution for correct conversion, and warns not to infer temporal order across kernel-event timestamps from raw values around wrap. It explicitly distinguishes kernel timestamp events from `zeCommandListAppendWriteGlobalTimestamp`; that warning does not by itself prove `zeDeviceGetGlobalTimestamps` and event `global.kernelStart` are different domains. The public UR v2 candidate applies mask/resolution conversion for event START/END; its END helper handles a wrap from the event's own start and documents limited wrap handling. The closed receipt contains only converted nanoseconds, not raw counters, bit widths, source route, or clock-correlation samples, so it cannot adjudicate wrap or domain mismatch.

The installed Level Zero package is recorded as `26.31.39395.14`; the published Intel `.14` NEO source tag and package source provenance were established in R271/R276, but installed shared-library byte identity was not. The `.14` event entry point delegates `zeEventQueryKernelTimestamp` to the event implementation; the source computes profiling values from timestamp packets and includes overflow handling. The `.14` device entry point delegates `zeDeviceGetGlobalTimestamps` to its device implementation. That source and the Level Zero specification document separate stages; they do not identify this UR/SYCL event's cached-submit branch or explain these two observed deltas. Do not attribute a root cause to NEO, UR, SYCL, driver, oneMKL, or event identity from this audit alone.

A bounded search of official Intel issue records did not identify a primary issue or release note that reproduces this exact ordinary oneMKL returned-event `submit > start` case or confirms a matching fix. The relevant evidence here is the specification, pinned/public source candidates, the release-tagged NEO source path, and the closed-run receipt; unrelated issue reports are not evidence for this failure.

## Safe next denominator

For the next useful measurement, keep the current failed receipt untouched and avoid another 32K run with the same submit-query lane. Use a bounded harness built from the actual route's observed `(role,T,N,K,ldy)` histogram and the production queue/USM layout. Record exact call/shape counts and compute the nominal operation count as `sum(2*T*N*K)` from those calls. For a timed batch, use one host monotonic clock at both ends: start immediately before the first timed GEMM submission; stop only after the defined batch-completion wait returns. Keep allocation, initialization, warmup, and output comparison outside that interval; retain output/correctness and queue-async-error checks. Do not query `command_submit` or use the rejected values in the denominator.

If the same in-order queue and last returned completion event demonstrably cover all earlier calls, one final `wait_and_throw` gives a bounded host-wall completion denominator. Otherwise wait on every retained completion event after submitting the batch, and state that the measurement includes host wait overhead. Report it as **batched host-wall completion time / host-wall operation rate for this exact shape mix**, not pure device time, exclusive GPU busy time, or model service rate. The returned-event dependency contract supports completion; it does not turn host wall into device-only service.

Run PTI separately as an operation-coverage diagnostic for a finite set of those same real shapes. Preserve operation IDs, host/device flows, queue/engine IDs, timestamps, and collector-loss checks; establish any SYCL/PTI clock mapping with markers and measured uncertainty. PTI can test whether the event's `start..end` covers all attributed internal oneMKL operations without depending on `submit`, but instrumentation perturbs execution, so it is not the clean denominator. If event-to-operation attribution or full internal command coverage does not pass, retain host-wall batch latency and call it an end-to-end host-wall result only. This follows R278's existing event-envelope fence; it does not promote `end-start` alone to full GEMM service or achieved FLOPS.
