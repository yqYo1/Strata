## Current shared region and 16K owner arithmetic

In current `prefill.cpp`, `init` makes one `region` allocation of `max(hc_set_bytes, ple_set_bytes, gdn_set_bytes, qsa_set_bytes, moe_set_bytes)` at lines 1274–1305. The alternatives are later carved over the same base at 1316–1370. `bytes_needed_impl` uses the same max at 2025–2030. The compact PLE bound is `T * ((3*HD + N + 4)*4 + N*(bf16x2?4:2) + 4096)` (894–901), where `HD=NG_HC_DIM=10,240` and `N=2,560`. In the W compact-HC/BF16 layout counted by R279 that is 142,352 B per row. At T=16,384 it is 2,332,295,168 B before the outer `Alloc::take` alignment; R279's entire 8K-to-16K accounted Prefill increase is 1,753,743,360 B (1,672.5 MiB).

R279's retained same-owner post-8K free sample is 1,565 MiB. The 16K workspace delta alone is about 107.5 MiB larger than that reading, before keeping the MTP-enabled server's 512 MiB headroom. R279's “about 620 MiB” is the amount to recover for that 512 MiB reserve under this conditional arithmetic. The 1,565 MiB sample and source-size counts are not a 16K allocation receipt.

## Exact compact PLE scratch planes and liveness

The native batched PLE path is conditional: Prefill requires PLE ready, the stage to include layer 1, `STRATA_PLE_BATCH` not disabled, native postops enabled by the CLI (`--native-ple-postops` or the native-everything preset), and a supported key projection weight (`prefill.cpp` 3001–3012). Non-native/per-token PLE calls `ple_block` with `ss.ple.scratch` at 3662–3674; that path does not consume the three large PLE arrays in `m.region`. Current `ple_set_bytes(T, compact)` reserves the PLE bound whenever `compact` is true, without checking which PLE path will actually run.

For the native batched route, the three HD FP32 arrays in each PLE subbatch are precisely:

| Current array | Producer | Consumers and death point | Can it be dropped/reused? |
|---|---|---|---|
| `key` (`nb*HD` floats) | Key GEMM writes projected key; first `rms_rep_kernel` normalizes it in place. | `gate_kernel` reads normalized key and query norm. After that kernel completes, no later operation reads key. | It is a candidate backing for `gated`, because its last read is before the broadcast that produces `gated`; retain the same storage through all queued consumers. No recomputation or changed arithmetic is needed. |
| `qn` / `query_norm` (`nb*HD` floats) | First RMS writes normalized `hidden` (here `m.R`). | `gate_kernel` reads the normalized hidden against key. It is then overwritten by RMS of `gated`; `conv_residual_batch_kernel` reads the resulting normalized gated values for current-token convolution, and `history_batch_kernel` reads them to commit history. | It stays live across both uses and must be separate from key/gated while those phases overlap in the ordered command stream. Retiring it would require a distinct schedule/recompute or an alias proof not present here. |
| `gated` (`nb*HD` floats) | `broadcast_batch_kernel` writes `value * gate`. | RMS reads it to produce `qn`; then conv/residual reads it again while updating `hidden`. Its final use is the conv/residual kernel. | Alias its backing with `key` only after `gate_kernel` has finished reading key. It cannot be released at the broadcast point; the conv/residual reader is later. |

The other PLE scratch is `val` (`nb*N` FP32, key/value projection output read by broadcast), `gate` (`nb*4` FP32, gate output read by broadcast), `e16` (`nb*N/2` uint16, reused for the key then value GEMM input), and optional `e16_lo` (the second BF16X2 input). These do not replace an HD plane. The current caller carves `key`, `qn`, `gated`, `val`, `gate`, and the one/two e16 buffers from `m.region`; each carve rounds to 256 bytes (3622–3647).

The postops kernel order in `native_ple_postops_batch` is: in-place key RMS; hidden RMS into `query_norm`; gate reduction reading key+query_norm; broadcast writing `gated`; gated RMS into `query_norm`; conv/residual reading query_norm+gated and updating `hidden`; history commit reading query_norm (394–514). The source already relies on same-pointer key RMS input/output and exact hidden in-place residual. The proposed extra cross-kernel storage reuse is narrower: broadcast may overwrite the key allocation only after gate has consumed it. There is no simultaneous kernel argument alias between key-read and broadcast-write.

The ordinary caller passes `main_cs`, which `generate.cpp` binds to `dpct::get_in_order_queue()` (2912–2922, then Prefill init/run at 11726/11770); `strata::q_of` documents null as the default in-order queue. GEMMs and these postops use `m.cs`. Thus the gate kernel is enqueued before the broadcast that would reuse its storage, with no host-side wait needed. The existing region remains live for all PLE work, and later attention/MoE uses it only after PLE in the same layer's compute-queue order. If this routine is moved to an out-of-order/different queue, or the PLE work is split across queues, the alias is invalid absent an explicit event/barrier edge from the gate reader to the broadcast writer. The normal host PLE row gather is asynchronous, but `ple_land` joins its future, enqueues the PLE embedding copy on `m.cs`, records completion for host-buffer reuse, and layer 1 then enqueues GEMMs/postops on the same queue (3176–3238, 3620–3647); it does not permit releasing `m.ple_emb` before queued work drains.

PLE history is outside these temporary planes. `conv_residual_batch_kernel` writes each `hidden` row in place; after it, `history_batch_kernel` writes the nine-row `ss.ple.hist` from the final normalized rows and the prior history for a short T (262–290, 495–514). With multiple subbatches, the next subbatch must see the history update from the previous subbatch. The host-side two-token `prev`/`ss.ple_prev` maintains n-gram row identity separately: it advances over tokens in order and commits at the end of `run_impl` (3026–3034, 3240–3245, 5331–5332). The proposed storage alias changes neither predecessor IDs nor session history layout/order. Keep both states and current PLE row gather intact.

## One source-supported candidate and its actual ceiling

**Candidate:** in compact native-batched PLE only, back `gated` with the dead `key` plane. Keep the exact seven existing kernels and their order; do not fuse, recompute, change GEMM math/row grouping, or move history updates. Centralize the PLE per-row bound and use `2*HD` instead of `3*HD` for this exact alias in both `ple_set_bytes`/`bytes_needed_impl` and the runtime's `SB` denominator. Keep the current 4,096-B-per-row conservative extra and the optional e16_lo term. Require the native-postops route, same `m.cs`, and `SB == T` (or the baseline's exact same SB) before taking the alias; otherwise use unmodified carve/size. Add an explicit batch-function alias contract: `gated==key` permitted only on an in-order queue with gate-before-broadcast ordering. The contract must not be generalized to the single-token API, whose writable-span validator presently rejects overlapping outputs except its documented exact aliases.

Updating both sizing and `SB` is necessary to avoid accidentally changing PLE/GEMM row shapes. `SB` currently is `min(T, region_bytes/per_token)` at 3631–3635. If only the max-region size shrank but the old 142,352-B denominator remained, `SB<T` could split the 16K PLE chunk into multiple calls, changing GEMM M and when `ss.ple.hist` is committed. With the proposed bound `((2*HD+N+4)*4 + N*(bf16x2?4:2) + 4096)`—101,392 B/row for the counted single-BF16 plane, or 106,512 B/row when the optional `e16_lo` plane is active—and the compact MoE region below, the full T remains admissible as one subbatch, preserving its existing GEMM row shape.

The 640 MiB figure is only the raw retired plane: `16,384 * 10,240 * 4 = 671,088,640 B`. It is **not** the shared-region or total-workspace saving because that region is a maximum. With the current compact fallback MoE carve, `moe_set_bytes` is approximately 132,772 B per row (source expression at 1018–1030 and 1340–1355: logits, route arrays, compact Xs/GU/Hh, Dm, gates, shared output and SG; aligned count at 16K is about 2,175,340,032 B). After one D plane is retired, the PLE bound is approximately 101,392 B per row (106,512 with BF16X2), so MoE becomes the next maximum (GDN is about 107,264 B/row, HC lower; the context-sized QSA score plane remains below these at 16K as R279 recorded). The region therefore falls from 2,332,295,168 B to about 2,175,340,032 B, a net source-count saving of roughly 156,955,136 B / 149.7 MiB, plus/minus outer 256-byte alignment. Other per-chunk allocations are unchanged.

Under R279's conditional same-owner arithmetic, that saves only about 149.7 MiB against the 16K workspace increment. It may put the increment roughly 42 MiB under the historical 1,565 MiB free reading, but leaves about 470 MiB less than the 512 MiB MTP guard, with no margin for allocator/runtime/desktop variation. It cannot by itself preserve the existing admission headroom, and no source arithmetic certifies allocator fit. Therefore do not treat this as a replacement for the MTP lease or as authorization to allocate 16K. It could be a small independently useful workspace reduction if it preserves parity.

## Exact block and qualification boundary

The candidate is blocked from implementation/adoption until the caller's actual option and loaded PLE weights prove the native batch branch is active, the matching W/B source and binary are reconciled, and a reviewer confirms the in-order dependency contract is part of the public batch API. The native postops path is opt-in; ordinary per-token PLE does not execute the `key/qn/gated` planes, so the alias itself does not apply there. In that branch, source shows PLE uses session-owned `ss.ple.scratch`; a future sizing change could omit the unused PLE shared-region term, but it would have the same MoE ceiling and is a separate branch-specific edit.

Before any use, preserve operation args and first run a state/head/output parity gate against the accepted same-source, same-GEMM, same-PLE-route baseline. Compare complete `ss.ple.hist` and `ss.ple_prev`, all main state parts, all first-head floats, IDs/logprobs and MTP accounting; test at fixed 16K and its short tail, then the intended full-context `n_prompt-1` conditioning tail and final-token path. Include subbatch shape evidence (`SB`), exact region bound/max, selected chunk/no fallback, output correctness, and phase-aligned allocation/free readings. If `SB` differs, queue is not the same in-order queue, or any parity bit changes, reject the candidate. Run performance only after the numerical gate; do not retry the failed GEMM timing.

No ownership or cache/KV changes are proposed. The server's 512 MiB headroom and full-context occupancy/repeat/restore/clipped-tail/refusal/later-valid gates remain mandatory and open.
