# R282 — Decode CPU capacity versus current service: dispatch join and proof gaps

Date: 2026-10-10 (Asia/Tokyo). Read-only audit of current source W495, the actual cached v0.1.41 base worktree, closed decode-pool/route receipts, closed native CPU capacity receipts, and primary optimization references. This is not a new inference or performance run. No build, test, GPU/device/process/service/profiler/PMU action, Git operation, source change, or cleanup was performed. Only this report was written.

## Finding

The current source already routes each verifier window's actual CPU-missed native expert rows into one `ExpertJobMulti` per distinct expert. Each job's `nt` is the number of CPU-owned routed rows for that expert in that layer-window. The pool runs gate/up, caller-thread intermediate quantization, and Down in separate stages. In the default Ryzen 5 5600X AVX2 configuration, NT1 generally takes GGML's per-token dot path; NT2 and higher may take Strata's existing AVX2 multi-token kernels for IQ2_S GU and IQ4_NL Down. This is an important distinction: the acquired `NT=1..4` fixture capacity is not one interchangeable CPU service rate.

The closed task-6 route diagnostic does retain a per-type/per-NT dispatch histogram, and its actual route cells reach NT2, not NT3 or NT4. For GU22 it reports NT1 GGML and NT2 `iq256`; for Down20 it reports NT1 GGML and NT2 `iq4nl256`. The corresponding same-record GU/Down pool-phase values are host elapsed intervals, not worker compute. The route instrumentation does not cross-tab the two roles into per-layer `(GU type, Down type)` pairs, and does not attach time, bytes actually read, task fragments, worker CPU time, or wait/tail to the histogram. It is a task-6 diagnostic build with `performance_eligible=false`, `full_lifecycle_passed=false`, and `adopted=false`, not a current default production result.

Accordingly, the evidence now says more than “MTP averages cannot identify NT”: a closed diagnostic directly records NT1/NT2 job and token counts. But it still cannot join a particular `(22,20)` pair's NT cells to that cell's service time in the current default request, nor prove whether CPU execution, memory hierarchy, pool submission/waits, or another callback span is the exposed limiter. The 36.87 GB/s CPU RAM read and 0.818 TFLOP/s register-FMA results are separate operation controls, not roofs for packed IQ kernels. The R280 whole-GEMM returned-event lane remains invalid; no clock relaxation or rerun is warranted here.

Relevant frozen file hashes are W495 `sycl/src/core/expert_source.cpp` `5cc617c9887e80175f5325957b02cd034ac1f7ce7a5fb310cda5492e1e25d5f1`; cached-base `native_expert.cpp` `694e86a623889ed03c5157d68f70651692eee9d265d7c2f99d44877ada37a146`; `pool.cpp` `f789078f1e14b6cf72bec5cacc2802d358ad82cbd7bf890f344a4a4a32158611`; and `sycl/src/core/expert_source.cpp` `3109bfa4a54cf64f7cf7088fc510370dd49d25d628349324873c8030f52ee028`.

In `expert_pool_dispatch_multi`, the code classifies every `(token, top-k entry)` into a route kind. Only negative `kind` entries become CPU jobs; GPU-resident, offloaded, peer, or remote entries do not. If there is any CPU work, it quantizes the relevant input activations, gathers exact CPU-miss expert IDs for source prefetch, deduplicates entries by expert through `job_of`, adds each CPU token row to that expert's job, and increments `nt` and the CPU-entry counter. It then invokes `run_split_multi_native` with the layer's actual `NativeFmt` and the number of distinct CPU jobs. This is the correct unit chain:

`route entries → CPU-owned entries → distinct CPU expert jobs → job.nt → row work → pool phases`.

For the 5600X source path, `native_gu_rows` defaults `mt_min=2`; NT1 falls through to the GGML `vec_dot`, while eligible IQ types can use AVX2 at NT≥2. `native_down_rows` similarly uses GGML for IQ4_NL NT1, and the AVX2 `iq4nl256_down_rows` path for IQ4_NL NT≥2 when enabled. Q2_0 Down uses its separate `q2_rows_any` branch. Thus phase `GU` or `Down` alone does not identify one kernel. The per-request route histogram is useful precisely because it records selected format, NT and dispatch branch; it must be joined with the actual per-layer pair before using the 22/20 fixture.

`run_split_multi_native` dispatches one row phase over `nb * FF`, does native intermediate activation quantization serially on the caller, then runs a row phase over `nb * H`. Its phase clocks wrap `run_phase`, which includes worker park/wakeup, queue publication, host draining, completion wait and re-parking. The dispatcher's outer CPU interval also includes planning/jobs and peer/remote completion. These counters are elapsed host spans, not the sum of per-worker active time. `phase_tasks` chooses either the automatic `3 * (worker_count + host participation)` count or the configured limit; a task is a contiguous flattened output-row range and not an expert-token unit.

## Capacity comparison and denominator fence

The closed actual-weight native CPU capacity fixture is exactly GU22/IQ2_S plus Down20/IQ4_NL at H=2560, FF=640. With five workers plus the host, complete pooled service per expert-token is 90.978 µs at NT1, 54.215 µs at NT2, 42.931 µs at NT3 and 38.738 µs at NT4 for the 192-ID streaming fixture. Those are fixture medians across disjoint selected cohorts and three processes per cell; activations are synthetic/prequantized. The direct fixture and pooled fixture use their own declared service interval. This is not an online model-route sample and not an instruction or DRAM roof. The NT1 and NT2 branches differ from each other and NT3/NT4 have no exposure in the current R6 route receipt.

The separate hardware controls on the Ryzen 5 5600X / Arc B570 report 36.87 GB/s for the selected host RAM read stream and 0.818 TFLOP/s for a six-core register FP32 FMA control. The former says nothing about this IQ lookup kernel's physical transactions; packed bytes per window are a submitted logical extent, not DRAM bytes. The latter does not bound integer byte-shuffle/dot/dequant instructions. Dividing expert blob bytes by the stream rate or dense-equivalent MACs by FMA throughput would create a false service model.

The 70-token/s goal means 14.286 ms for the entire request critical path per emitted token. The historical pool0 request's roughly 68.5–75.3 ms/window divided by its average accepted outputs is a descriptive rate for that diagnostic only; it does not isolate or predict current W495 performance. The aggregate `CPU` callback is host time and phase counters are nested; neither can be compared to that target as if it were exclusive CPU compute.

## Proof presently available, and remaining joins

| Question | Retained evidence can establish | It cannot establish |
|---|---|---|
| Which CPU work was exposed? | Current source has explicit route kinds, per-format dispatch and `nt`; the R6 diagnostic records selected role/type/NT/job/token counts and branch. | Current W495 default-request histogram, per-layer GU/Down pair cross-tab, or service time for each type/NT cell. |
| How much elapsed callback/phase time? | Per-request CPU dispatch wall; per-window GU, serial FF quantization and Down phase wall; whole request/window wall and emitted tokens. | Worker CPU busy time, worker wait/spin, park/wakeup cost, task claims, work tail, or which NT/type paid a phase duration. |
| Is CPU compute the bottleneck? | A large host CPU callback is on the verifier host boundary in the closed diagnostic; GU/Down phase spans are correspondingly visible. | CPU instruction cycles or active-time fraction, or proof that the elapsed callback is dominated by math rather than barriers/other host work. CPU PMU was not admitted (`perf_event_paranoid=4`, no effective `CAP_PERFMON`); VTune software sampling and gprofng clock sampling were previously rejected by local evidence. |
| Is CPU memory the bottleneck? | Separate streaming/copy controls and submitted logical bytes. | Actual CPU kernel physical read/write bytes, cache misses/latency, controller saturation or whether each packed blob came from LLC, DRAM or page cache. No same-interval PMU/uncore counters exist. |
| Is submission or device work the bottleneck? | Host dispatch and GPU-reach-wait/stage fields in the whole-window log. | Valid GPU internal operation timing for the rejected R280 GEMM event lane; no timestamps should be recovered by offset/clamp. The CPU callback still includes its synchronization and peer/remote completion. |
| Does MTP group work enough for fixture cells? | R6 explicitly records NT1/NT2 cells for that diagnostic; native fixture supplies NT1–4 controls. | Current ordinary W495 job mix, NT3/4 frequency, committed-versus-discarded CPU rows, or a tok/s gain from changing speculative depth. Average MTP acceptance does not provide this histogram. |

The smallest service join is one matched clean default request receipt that binds, for each `(request, window, layer, NativeFmt pair, NT, selected kernel)`, CPU job count, expert-token row count, GU/Down output rows, exact source bytes, selected variant, CPU owner, and task partition to elapsed service; pair it with per-worker CPU-time/active/wait/tail and the physical request denominator. Preserve accepted prefix so discarded suffix work is separately counted. If the current closed dispatcher histogram can be extended on the same source/binary without changing route behavior, keep its existing correctness and counter reconciliation gates; do not extrapolate the R6 task-6 values into task-0 W495.

To distinguish memory from execution, the next proof would require counters collected over the same admitted kernel intervals: per-worker cycles and retired instructions, model/CPU-family validated cache events, physical memory-controller bytes, event enabled/running coverage, affinity/frequency, and comparison with exact source branch. R95/R206 record that the local perf/PMU gate was unavailable, so do not attempt to replace it with blob-byte arithmetic or a RAM stream result. Without that capability, paired direct-versus-pool service and worker CPU time can still distinguish active service from scheduling exposure, but not instruction throughput from cache/DRAM limitations.

## One conditional source-level candidate

If a clean service join first shows that the actual CPU critical path is dominated by the **NT2 IQ2_S GU plain-AVX2 kernel's grid lookup work**—rather than by callback waits, memory-service saturation, FF quantization, or Down—then the narrowest new kernel candidate is to evaluate the existing gathered `iq256_gu_rows` specialization for that exact GU22/NT2 cell against the current plain variant. The route receipt says the tested build had `gu256=1`, default gather setting `-1`, and variant `scalar:0` for all observed cells; source retains the alternate gathered implementation and a setting to request it. Keep it an isolated paired CPU capacity comparison on identical blobs/activations, both intended-hot and streaming cohorts, with correctness gates, followed only if it wins by an engine-level request comparison. Do not apply the override globally, and do not call it a speedup before measurement. This is narrower than generic prefetch, compiler or row-tile proposals and is contingent on proving the selected NT2 kernel's active service matters. The Zen 3 AMD Family 19h guide is the primary architecture reference for designing the instruction comparison; the upstream GGML/llama.cpp x86 quant source is a primary implementation reference for quantized dot paths. Neither source supplies a performance result for this Strata variant or this 5600X. [AMD Family 19h Software Optimization Guide](https://docs.amd.com/v/u/en-US/56665), [GGML x86 quantized CPU implementation](https://github.com/ggml-org/llama.cpp/tree/master/ggml/src/ggml-cpu/arch/x86).

If the joined evidence instead shows that task barriers dominate or memory transactions saturate, this candidate is ineligible and the next action should target that demonstrated mechanism. Prior R9 already covers the cross-window decoded-weight side cache; R12 covers NT-weighted scheduling; R224 covers NT4 emitted spills; R213/R244/R258 cover CPU roof and NT eligibility; none is being restated as a new generic optimization here.
