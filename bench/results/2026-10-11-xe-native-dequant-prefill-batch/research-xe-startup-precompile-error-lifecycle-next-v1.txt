## Fixed-commit execution order and diagnosis

In the `git show` snapshot, `src/program/generate.cpp` invokes `Runtime::get().preload_kernels()` beside model loading, before model execution and before `READY`. It then performs `Gemm::prepare()` / `Gemm::settle()` before the prompt. This is free mode with native batch disabled, but neither fact disables the runtime preloader. `Gemm::prepare()` is guarded by `#if STRATA_ONEMATH`; in a free build it is compiled as a no-op. It is therefore not the evident source of the three background compile records in this run.

The fixed commit's `src/core/device.cpp` implements `Runtime::preload_kernels()` as a background `std::thread` which iterates every `sycl::get_kernel_ids()` result and calls

`sycl::get_kernel_bundle<sycl::bundle_state::executable>(context_, {device_}, {id})`.

The call can trigger online device compile/link (JIT). Its `catch (const std::exception&)` increments `skipped` with the comment “none for this device, or a shape it does not run”; the exception is discarded. `STRATA_TRACE` emits only final built/skipped totals if the whole loop completes. `preload_stop_` is checked between IDs, so an in-flight bundle build is not cancelled. `Runtime::~Runtime()` sets the flag and joins the preloader before draining queues and stopping its watchdog.

This is an indiscriminate startup compilation sweep, not a model-selected warmup: SYCL specifies that `get_kernel_ids()` returns IDs for all kernels defined in the application. The call asks for executable bundles for all of them, including code paths never entered in this process. Intel's own DPC++ design note describes the exact class of problem: applications can define thousands of kernels and use only a small subset, and device-specific kernels unused at runtime can fail JIT on a different device; the documented mitigation is device-code splitting, including per-kernel modules. Therefore it is confirmed that the fixed-commit preloader speculatively JIT-compiles beyond the selected native-batch-off model path.

That does **not** prove that each of the three named failing specializations is unused. `PromptAttnMma` is a prompt-attention kernel family; its name and log show that it was compiled, but this run stopped before GEN and does not reveal whether a real prompt of its shape would select it. The `Kernel<2,...>` variants likewise require their owning wrapper and runtime dispatch to determine actual reachability. Native batch off only says the optional grouped-dequant batching mode is off; it cannot be used to label unrelated joint-matrix kernels dead. No source callsite-to-build-log mapping is claimed beyond the names captured in the module logs.

The fixed commit's `sycl::async_handler` records the first asynchronous queue exception under a mutex. `Runtime::wait()` calls `event.wait_and_throw()` and then `check_async()` rethrows that stored exception. The preloader's `get_kernel_bundle()` failure is a synchronous exception from a host API call and is caught locally by the preload thread; it is not delivered through the queue async handler. Thus the existing asynchronous error slot does not by itself propagate this preload failure to startup/request control. The source currently disguises every caught build failure as “not for this GPU” in the aggregate count and proceeds.

## Safest selection and error-propagation options

1. **Best first app-level isolation:** disable the global all-kernel background sweep for this run/configuration and let normal request dispatch trigger JIT only for kernels actually selected. Record the first real operation that fails and fail that request/process through an ordinary C++ error path. This directly tests whether the failures are unused and prevents compilation of unrelated template variants before GEN. It may move JIT latency to first use; it is a diagnostic candidate, not a performance claim. Since the current per-run compile error is in named joint-matrix kernels, a production fallback should be chosen only for an operation whose wrapper already has a correct alternate path.

2. **If eager preparation is retained:** derive an explicit active-kernel manifest only after model format, dtype, backend and shape dispatch are known. Separate “unsupported/incompatible for this device” from `errc::build`/module compilation failure; retain kernel name/id, device, requested format/shape and exception text. Never silently count a compiler build failure as a normal device skip. Join the bounded preload phase before advertising READY if readiness promises compilation status, or label it optional and publish its failure to the actual operation that requests that kernel. Do not keep a detached fire-and-forget compiler thread whose errors can be followed by GEN with no failure state.

3. **Bundle filtering has a limit:** SYCL supports `get_kernel_bundle(..., kernelIds)` and image selectors, but the specification allows a returned device image to contain additional kernels beyond the requested IDs because images may group kernels. So ID filtering alone is not proof that one problematic specialization cannot be compiled along with a wanted one. Intel DPC++ documents `-fsycl-device-code-split=per_kernel` as a way to make per-kernel modules; first verify the actual binary's device-image grouping/build flags and compatibility with external device functions before relying on it. Per-kernel splitting narrows compile coupling; it does not make an actually selected failing kernel work.

4. **Matrix capability selection:** use the existing source-level `mma_usable()`/`gemm_path()` dispatch to reject joint-matrix shapes the device reports it cannot run, and retain the existing DP4a/other fallback where it is valid. This is useful for hardware/shape incompatibility, but it is not sufficient for this failure: the error is an unresolved backend compiler builtin, not evidence that the device lacks matrix capability. A safe capability gate for this compiler/runtime tuple would need a small, isolated probe through the same representative kernel wrapper/type/shape, followed by `event.wait_and_throw()` and the runtime's async check before setting the capability flag. The probe must separate FP16 and BF16 and must never claim success from merely constructing a queue or obtaining a device. An unsupported matrix route may then fall back only if its existing alternate preserves the required result contract.

5. **Error exit and cleanup:** add a first-failure channel for the preloader (status plus kernel identity and exception text), stop scheduling new IDs after a required-kernel failure, and have the main thread observe it at a defined startup/request boundary. Catch exceptions inside the worker; never throw across a `std::thread` entry point. For an optional failure, publish “unavailable” for only that optional path and select a checked fallback. For a required failure, return a normal nonzero engine status while owning the main thread. On shutdown, request cooperative stop, join all background compiler/helper threads, then perform checked queue drains and destroy runtime state. The existing service protocol has `QUIT` to leave the serve loop; `STOP` cancels a request and is cleared when the next request begins, so it is not process shutdown. A test controller should send QUIT and wait for normal close before considering a signal escalation. The supplied SIGTERM/longjmp tail is not a safe cleanup proof and this report cannot diagnose the longjmp source.

The shortest useful follow-up is not another broad compilation run: after Main closes the active ownership window, compare (a) existing all-ID preload with (b) preload disabled, without GEN at first, and inspect only whether the three build failures disappear before readiness. Then, only if model execution is requested and safe, record the first selected real operation, active kernel name, path/shape/dtype, compile/submit/wait result, fallback decision and normal QUIT status. Do not suppress a required-kernel compile failure as SKIP, and do not relabel a generic health/READY result as matrix correctness.

## Relevant prior findings

R323 already notes that queue helpers can defer asynchronous errors until a checked wait and that errors need to stop producers, wake waiters, and be joined before cleanup. R327 distinguishes a reported operation error from unconfirmed device completion and warns against freeing live buffers on failed drains. Those apply if a real launched operation fails; they do not explain this specific pre-READY `get_kernel_bundle` compile path, whose host API failure is synchronously caught by a detached preloader thread. R8's reset/lazy Prefill path can avoid allocating prompt buffers when unused, but it does not filter `get_kernel_ids()`.

## Official sources and transfer limits

- Khronos [SYCL 2020 specification, kernel IDs and bundles](https://registry.khronos.org/SYCL/specs/sycl-2020/pdf/sycl-2020.pdf), §§4.11.6–4.11.7: `get_kernel_ids()` returns all application kernel IDs; requesting an executable bundle can invoke online compile/link and throws `errc::build` if that fails; ID-filtered bundles may still include extra kernels from a grouped image. Primary normative source.
- Intel/LLVM [Compiler and Runtime Design](https://github.com/intel/llvm/blob/sycl/sycl/doc/design/CompilerAndRuntimeDesign.md), “Device code splitting”: describes unused, device-specialized kernels failing on a device and offers `-fsycl-device-code-split=per_kernel` / `per_source`. Primary compiler design documentation; it establishes a supported technique, not that this binary used a particular splitting setting or that the fix will address the builtin.
- Khronos [SYCL 2020 specification, queue waits and async handlers](https://registry.khronos.org/SYCL/specs/sycl-2020/pdf/sycl-2020.pdf), §§4.6.6 and 4.13.1: `wait_and_throw` completes submitted commands and delivers unconsumed asynchronous errors to the handler; async handlers apply to errors detected after the initiating host call returned. This distinction supports treating synchronous bundle build exceptions separately from queue async failures.
- Intel/LLVM [Get Started Guide](https://github.com/intel/llvm/blob/sycl/sycl/doc/GetStartedGuide.md), AOT requirements section: describes Intel GPU AOT compiler/ocloc availability. AOT can move compilation to build/deployment, but would need a qualified exact device/compiler path and does not justify enabling AOT by assumption here.
- C++ working draft [`std::thread` destructor](https://eel.is/c++draft/thread.thread.destr): a still-joinable thread destructor terminates. Primary standard wording; reinforces explicit join for normal teardown.

These sources were opened during this investigation. No kernel-lowering fix is proposed or evaluated; that work belongs to the separate compiler investigation.
