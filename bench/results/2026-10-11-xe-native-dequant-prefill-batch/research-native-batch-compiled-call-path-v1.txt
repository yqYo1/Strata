Selection path and gaps
In the candidate snapshot, the branch at `prefill.cpp:2097-2102` enables batching only when `STRATA_PREFILL_NATIVE_DEQUANT_BATCH` exists and `strtol(...,10) != 0`, `lay.native` is true, and `use_mmq` is false. The existing per-expert native calls remain the fallback at `2349-2358`; candidate ON accumulates pointers then invokes grouped APIs in `native_flush` (`2128-2155`). The API header at commit b72640ff declares both group entry points and a fixed `kIqDequantGroup=16`; CMake in that commit compiles `src/kernels/xe/iq_kernels.cpp` into `strata_kernels` under the Xe backend (`CMakeLists.txt:381-384`). No evidence here says this caller snapshot was integrated into that binary.

The caller selector itself has no `G<=64`, `hold<=16`, particular architecture, occupancy, type whitelist, or chunk-size test. G is independently clamped to 1..64 by `Prefill::set_expert_group` (`prefill.cpp:1024`); q is `(j-nf)%G` (`2342`). Safety limits are enforced downstream: the pending array has 16 entries and flushes at 16 (`2103-2105`, `2344-2348`); destination rebasing supports q windows within G (`2135-2139`); API rejects invalid slot bounds or dimensions/capacities/alignment/source overlap and refuses unsupported IQ types or devices whose work-group dimensions are below 256 (`iq_kernels.cpp:1682-1719`, `1724-1732`, `1751-1759`). The API accepts GU and Down independently, so a rejected axis falls back independently (`2140-2155`). A true result is normal submission, not completion, as documented by the committed header; source slot markers are recorded only after both axis calls (`2156-2165`).

This means the relevant eligibility is not simply "native pack": caller opt-in plus native/non-MMQ reaches the grouped attempt, but actual grouped admission additionally depends on the API's per-axis supported type, geometry, span/capacity and device work-group checks. Failures preserve individual wrappers in source. `!use_mmq` is a notable deliberate exclusion: the grouped dequant-to-FP16 experiment cannot be selected on the MMQ path even if `lay.native` is true. No condition in this path uses chunk token count. `f.n_ff`, `f.n_embd`, row-byte geometry and blob/destination bounds are checked at flush time, so invalid layouts throw before API submissions rather than causing a soft grouped refusal.

Window bounds in the actual producer/consumer loops
The API's hard maximum is 16, and the caller's `nd_blob` / `nd_slot` arrays are exactly 16. A native batch cannot exceed 16 entries (`2103-2105`, `2344-2348`). The unchanged expanded-weight GEMMs require a flush at each expert-group boundary / final tail (`2362-2364`), so each window is also bounded by the remaining contiguous q slots in G; G itself can be up to 64. Rebasing lets successive <=16 windows fill one G<=64 dequantized group before the existing GEMMs (`2135-2139`). Thus API capacity is not the limiting factor for G>16; caller lifetime/ordering and group tails can make windows shorter.

Routed path uses `STAGE=8` (`prefill.cpp:67`) and lookahead `STAGE-1=7` (`2380-2383`). Before `stage_one` stages a nonresident expert into `stage_next`, the loop scans pending slots; if that exact slot remains held by an unflushed dequant window, it flushes before the original staging path can wait for/reuse the slot (`2384-2391`, with reuse wait in `2201-2229`). Therefore the safe window is the contiguous pending run only until its earliest held slot is next needed by staging. For a fully streamed run with all eight slots occupied, the source schedule revisits slot 0 while processing the first staged expert, so the first held-reuse flush can occur after one expert; the same rolling overlap can force very short windows. This is a source-derived bound/example, not a measured histogram. If the upcoming entries are resident, they do not consume `stage_next`, so batching can continue until another held-slot collision, the 16-entry ceiling, a q/G boundary or end-of-order. No universal routed minimum window >1 is established.

Full-stream path tracks `nd_consumed` separately from the producer-consumed prefix. It flushes before a wait if `k-consumed >= m.ring` (`2425-2430`), and immediately after a batch reaches the full ring distance or 16 entries (`2361`). If the configured ring is 16, producer publication therefore bounds held pending streamed entries to at most 16 and aligns with the API ceiling. Any skipped entry calls `native_flush` before publishing that skipped slot (`2409-2419`); layer end also flushes (`2447-2449`). These mechanisms can make windows shorter than 16 when route-ID gaps/skips intervene. The source's ring implementation can choose much larger rings normally (`146-166`), so "ring16" here is specifically the requested/configured case, not a general full-stream default.

Relation to the 32K 269 t/s reference
The committed `RESULTS_JA.md` in `bench/results/2026-10-11-xe-native-dequant-group-v2` explicitly identifies `269.159t/s` as an earlier 32K diagnostic reference and says the production prefill caller was still unapplied; the new API's component measurements are not end-to-end prefill results. Consequently that throughput is neither a batch-ON result nor a batch-OFF paired baseline for this candidate. It cannot establish that grouped calls are selected, that routed windows are large, or that this optimization improves full prefill. No speed inference is made here.

Conclusion
The gap is caller qualification and window-size observation, not the group API's nominal slot limit. At present the committed source proves an optional API with independent admission checks; the caller snapshot proves the intended opt-in wiring and lifetime flush points only. For a future run, group-call length per flush (or exact per-window count histogram) is needed alongside per-axis admitted/refused totals to distinguish routed ring reuse from API refusal and group-tail effects. That evidence must come from the applied source/build and measured run; this source-only review does not claim any performance outcome.
