# Xe JIT, SIGTERM, and checked-longjmp lifecycle

Date: 2026-10-11
Scope: read-only review of the fixed Strata source, recorded run/health receipts, compiler source proof, recorded runtime-library hashes, and static symbols/strings in installed library files. Official LLVM/glibc source and public issue reports were browsed. No process execution, shared-library loading/import, test, GPU query, build, debugger attach, service action, source/Git mutation, or cleanup was performed. The only new file is this report.

## Finding

The record establishes a sequence, not a cause: the failed model run encountered synchronous Level Zero module-build errors while its background SYCL preloader was active; the controller then sent owned SIGTERM; the process later produced 2,241 lines of `*** longjmp causes uninitialized stack frame ***: terminated` and was recorded with exit `-11` (SIGSEGV), not the ordinary shell-style SIGTERM status. The child was reaped and its session was empty. Those facts establish process termination and the order recorded by the controller; they do not prove that SIGTERM itself caused the longjmp warnings, identify the signal that invoked a longjmp, or prove that the compiler thread executed cleanup.

The warning string is glibc's x86-64 `____longjmp_chk` diagnostic. Its implementation checks whether the saved jump target's stack relationship is safe (and checks alternate-stack bounds) before falling through to `__fortify_fail`. This makes an invalid/stale/out-of-scope jump target, stack corruption, or incompatible signal/recovery path plausible mechanisms. The message alone does not say which caller supplied the jump buffer, whether it was stale, or what earlier event caused it. In this process the record does not include a core/backtrace resolving the warning to a caller.

There are two concrete reasons to investigate the compiler signal-recovery path while retaining uncertainty:

1. At the exact recorded Intel LLVM source commit, LLVM `CrashRecoveryContext` uses thread-local recovery state and a saved `setjmp` environment; its POSIX crash signal set is `{SIGABRT, SIGBUS, SIGFPE, SIGILL, SIGSEGV, SIGTRAP}`. It is explicitly designed to `longjmp` out of those crash handlers. **SIGTERM is not in that list.** Thus stock LLVM's `CrashRecoveryContext` implementation at this commit does not by itself explain handling the controller's SIGTERM. Another handler/path (including IGC), a different signal during teardown, or a stale recovery context would need evidence.
2. The local installed IGC candidate library has static evidence of signal/longjmp machinery: `libigc.so.2.40.13+0` exports `_Z13signalHandleriP9siginfo_tPv` and has undefined references to `__longjmp_chk`, `_setjmp`, and `sigaction`; `libigdfcl.so.2.40.13+0` exports the same handler name and LLVM `CrashRecoveryContext` symbols. This is suggestive of a path worth resolving. However, `libigc` and `libigdfcl` are not listed among the failed run's `observed_libraries`, so these host-installed files and hashes are not proof that those exact files were mapped in the failed process or that their handler caught this event. Static symbol presence also does not reveal which signals are installed or when the handler is active.

A public OpenVINO report describes a similar *class* of symptom: an IGC compile-time SIGSEGV followed by the same glibc checked-longjmp warning, with a reported `libigc` `signalHandler` in the stack. That report is a different stack (OpenVINO, IGC 2.34.4) and its author proposes a signal-handler/longjmp explanation; it is not evidence for this run's IGC version, signal chronology, or root cause. It makes the hypothesis credible enough to test, not established.

The fixed Strata snapshot `fa3e20e842fbed6986a69bade8afe3edabedee07` was inspected with `git show`. `Runtime::preload_kernels()` owns a joinable `std::thread`; it enumerates all kernel IDs and makes a synchronous executable-bundle request per ID. The stop flag is checked between IDs, not inside an in-flight `get_kernel_bundle()` call. `Runtime::~Runtime()` sets the flag, joins the preload thread, then calls `finish()` and joins its watchdog. The inspected project source contains no SIGTERM/sigaction registration and no `setjmp`/`longjmp` call. Consequently, the application has a cooperative path to join a compiler worker during ordinary teardown, but that code does not intercept a default SIGTERM or make an in-flight backend compile cancellable.

## How QUIT can be tested as mitigation

A protocol-level `QUIT` followed by normal close is a sound *mitigation experiment* because it allows the application to leave its serve loop through its ordinary control path and run C++ teardown, including the joinable preloader, instead of forcing a signal while JIT may be on the worker stack. It is not yet a proved fix for the observed warning. The preloader only notices its stop flag between synchronous builds, so a QUIT-triggered destructor can wait until the current bundle request returns; if the backend hangs, the join may hang too. If `QUIT` is only received by a separate stdin thread while main is blocked elsewhere, its actual effect must be verified in the protocol/lifecycle trace. Do not escalate to SIGTERM until the QUIT attempt has either exited normally or met a bounded timeout and its active child/compiler state is recorded.

For a discriminating follow-up, retain the same input, executable hash, compiler/driver environment and JIT trigger, and record two independent outcomes: (A) ordinary QUIT during active preload, wait through destructor/join and capture final preload status; (B) only if A proves no in-flight worker remains or the bounded policy explicitly requires escalation, signal termination. A clean A with no checked-longjmp diagnostics would support “signal-time interruption of active compiler state is avoidable by orderly shutdown”; it would not prove the original source of the warnings. If A still produces the warning, the SIGTERM-interruption hypothesis weakens and a compiler/driver fault or unrelated cleanup handler becomes more likely. If A blocks, that establishes join waiting but not a crash-recovery cause.

## Minimum additional evidence for causal separation

Main should capture this from the next owned run; this investigation did not attach a debugger or generate a core:

1. One core/backtrace from the **first** checked-longjmp warning, with signal number/name, timestamp, TID, PC, and module/build-id mapping for every frame from `__longjmp_chk` through its immediate caller, signal handler, and into IGC/LLVM/SYCL. Later repeated warnings add little unless they have a different caller.
2. For that same process, the signal disposition/handler address for SIGTERM, SIGSEGV, SIGABRT, and SIGBUS (or equivalent `sigaction` audit before and during JIT), plus proof of which DSOs were mapped at the moment: `/proc/<pid>/maps` snapshot or core `NT_FILE` notes, file build IDs/hashes. This resolves whether local IGC/`libigdfcl` candidates participated and whether SIGTERM was caught or left default.
3. A monotonic event trace for controller send, first warning, child wait status, and session teardown. Preserve the raw terminating signal/status (`WIFSIGNALED`, `WTERMSIG`, core-dump bit), not just a negative wrapper exit code. This distinguishes direct SIGTERM from a later SIGSEGV/SIGABRT or wait/translation artifact.
4. If `__longjmp_chk` is confirmed, the caller's saved jump-buffer provenance and stack mapping/stack pointer at `setjmp` and `longjmp`, or an equivalent debug-symbol trace. This is the minimum needed to decide stale/out-of-scope jump target versus a correct jump blocked by stack-check conditions.

An ordinary QUIT control run needs only the same event trace, final preload built/skipped line or explicit worker completion marker, normal wait status, and absence/presence of the first warning. Do not retain repeated stack copies once one representative causal stack has been recorded.

## Official source and analogous reports

- Intel LLVM [`CrashRecoveryContext.cpp` at commit `504366f4b82ff00bbac7b0c956635eed8bc599d8`](https://github.com/intel/llvm/blob/504366f4b82ff00bbac7b0c956635eed8bc599d8/llvm/lib/Support/CrashRecoveryContext.cpp) documents in code that the POSIX handler is for synchronous signals, enumerates ABRT/BUS/FPE/ILL/SEGV/TRAP (not TERM), stores `setjmp`, and invokes `longjmp` from `HandleCrash`. This is the exact compiler-source revision associated with the toolchain receipt.
- glibc [`____longjmp_chk.S`](https://github.com/bminor/glibc/blob/master/sysdeps/unix/sysv/linux/x86_64/____longjmp_chk.S) contains the exact warning string and stack/alternate-signal-stack validation before `__fortify_fail`. This explains the diagnostic mechanism, not its caller in this incident.
- OpenVINO issue [#36326](https://github.com/openvinotoolkit/openvino/issues/36326) reports an IGC compile SIGSEGV followed by the same glibc warning, includes `signalHandler` frames from IGC, and describes the author's longjmp-recovery hypothesis. It is a report on IGC 2.34.4/OpenVINO and was closed “not planned”; it is analogous evidence, not confirmation for the current B570 run or IGC 2.40.13 candidate.
- Intel LLVM issue [#22853](https://github.com/intel/llvm/issues/22853) reports reproducible SIGSEGV during first Level-Zero V2 JIT compilation with persistent SYCL cache on other Xe2/Xe3 systems. It is a different failure path and says nothing about this longjmp; it establishes only that runtime JIT can itself be a crash site and needs a core for attribution.

## Decision

Do not attribute the 2,241 messages to SIGTERM, LLVM CrashRecoveryContext, or IGC based on current evidence. The exact glibc diagnostic and installed IGC signal/longjmp symbols make a compiler-side signal-recovery path plausible; LLVM's pinned POSIX CrashRecoveryContext explicitly excludes SIGTERM, and the recorded process exit is `-11`, so there is an unresolved signal/termination chain. Prefer cooperative QUIT and normal worker join as the next bounded shutdown experiment because it avoids injecting a termination signal into an active JIT stack, while recognizing that join cannot interrupt a stuck synchronous compiler call. The first warning's core stack, actual mapped DSOs, signal dispositions, and raw wait status are needed before any stronger causal claim.
