Native grouped dequant: how much 32K prefill headroom can existing data support?
Read-only evidence synthesis — 2026-10-11

Scope and provenance

Read the v129 committed registry, current v2 RESULTS_JA and structured component-analysis receipt, the compact count/timing/route-census fields from `xe-source-llvm-census32k-root-v3/counts/record.json`, the fixed API implementation at commit `b72640fff05098f1762cb3bf9c427a5f8d7db31c`, optional prefill source snapshot SHA256 `c2c78fd15c0d5667256a2eeed8d8a72a5951612a74d4995ec7d1ba30daed2492`, and the named R reports below. Did not read the large model API logs, full env receipts, or prohibited `prefill-gemm-only-contract-root-v1/record.json`. No GPU/runtime query or execution, test, build, profiler, source edit, cleanup or Git mutation was done.

Provenance note: while first selecting compact fields from the count `record.json`, one read-only helper serialized the first 10 KB of the whole parsed JSON; that output began with environment fields before truncation. This was an accidental broader display than intended. Subsequent reads were limited to explicit timing/census fields. No additional environment dump or prohibited record was opened.

The question is an upper bound on current prefill improvement from grouped native dequant, using the old model run plus the standalone component result. Current evidence supports a dispatch-count ceiling and a conditional arithmetic screening estimate. It does not support an end-to-end performance upper bound or an attributable percentage of the 32K wall time.

What the two measurements actually cover

The census run is a 32K diagnostic: 32,768 prompt tokens, 32,767 actual batched positions, six chunks, ring16; 121,742.1 ms prefill and 269.1591 t/s, with 16 generated tokens. The run records 136,846 normal-return native GU wrappers and 136,846 Down wrappers (273,692 total), plus 144,639 logical expert H2D requests and 295,956,300,800 requested bytes. Of those bytes, 45,968,076,800 are routed and 249,988,224,000 are full-stream. The source record marks completion validation and GPU execution inference false for the transfer census; byte counts are logical requests, not physical PCIe traffic or service time. The request timing is diagnostic, not a quiet baseline.

The v2 component comparison is a separate 640×2560 service experiment over seven GU/Down format pairs, n=1/8/16. For n=16 it has six samples per arm and four timed repetitions per sample (ABBA blocks), with checked queue completion measured separately from host enqueue. The seven n=16 checked-completion medians, individual/group, are 4.624/3.797, 3.725/3.318, 4.387/3.616, 3.603/3.180, 8.405/3.785, 3.542/3.115, and 5.318/4.604 ms. Each pair improves in this standalone n=16 test by 1.123×–2.221×; its separate tag intervals also improve 1.132×–1.855×. These times are for a repeated resident-input component, not times observed inside the model prefill.

The analysis receipt explicitly says the prefill caller is not applied and no model was executed. The 32K wrapper/H2D totals therefore describe the individual-call path. They cannot be retrospectively treated as a batch-ON result. Component numbers cannot be added to, subtracted from, or multiplied by 121.742 seconds to claim measured model latency.

Two useful but limited bounds

1. Host call-count ceiling from API shape. Each grouped GU call and each grouped Down call launches one `parallel_for` over up to 16 experts (the ND-range's expert dimension is `group.n`). Thus, if all 136,846 expert pairs formed contiguous full groups and both axes admitted, calls would fall from 273,692 individual API returns to at most `ceil(136846/16) × 2 = 17,106` grouped API returns, a 93.75% reduction in wrapper-call count. This is an ideal arithmetic maximum, not expected windows or a 93.75% latency reduction. Partial tails, skips, ring-slot lifetime, group boundaries and independent axis refusals add calls. The component API's boolean success means normal submission, not completion.

2. Conditional service extrapolation for scale only. Each structured n=16 component sample times four repetitions × 16 logical GU/Down pairs. Dividing the paired checked-completion median difference by 64 gives a per-logical-pair saving of 6.36–72.19 microseconds across the seven format pairs. If (a) every one of the model's 136,846 pairs ran as an isolated n=16 group, (b) its type behaved like one of these synthetic measured pairs, (c) the resident-input component latency transferred unchanged to production, and (d) all such elapsed intervals were serial and exposed on the prefill critical path, the extrapolated saving would be 0.87–9.88 seconds. The upper endpoint assigns every model call to the single most favorable measured pair (22/20); it is about 8.1% of the 121.742-second diagnostic wall. Equal weighting of the seven pair measurements gives 2.50 seconds, but model format-call weights have not been joined, so this is not a model estimate.

Those assumptions are intentionally severe and not established. In particular, checked-drain component completion includes queue completion and host/driver waits absent between every model wrapper call; production overlaps expert copies and compute; the component input residency, group length mix, type weights and matching critical-path intervals are unmeasured. So 9.88 seconds is only a conditional scale illustration, not a defensible hard upper bound. Amdahl's expression makes the missing fraction explicit: if `f` is the fraction of current prefill critical-path time attributable to this exact service and `S` its transferable speedup, then total speedup would be `1 / ((1-f) + f/S)`. Neither `f` nor a production-transferable `S` is currently known. From current data alone, the justified range for realized benefit still includes zero.

Why the call total and 296 GB do not resolve the fraction

The dequant counter measures successful individual API wrapper returns. It gives neither duration nor GPU occupancy. The H2D counter sums logical source blob extents submitted for transfer; it does not say how much of that traffic lies on the critical path, overlaps dequant/GEMM, reaches PCIe, or stalls a group window. The full-stream H2D component dominates the byte total (about 84.5%), but its share of bytes is not its share of prefill time. Prior R267/R365 explicitly distinguish conditional transfer budgets and marker/phase totals from verified serialized critical-path service. No bottleneck fraction should be inferred from the byte ratio or wrapper count.

The standalone n=1 results also make a 16-slot assumption risky: group was faster in only 4/7 host-only pairs and 3/7 tagged pairs; host individual/group ratios span 0.686–1.155, and tag ratios 0.083–1.287. At n=8, host improves in 6/7 pairs and tag intervals in 7/7, but those are not the model's observed flush lengths. Grouping every call in a full 16-slot run cannot be assumed from `ring16` alone.

Smallest missing observation to decide whether the bound is relevant

The exact source report `research-native-batch-compiled-call-path-v1.txt` already derived the lifetime window rules: pending windows are capped at 16; group boundaries and skipped experts force flushes; a fully streamed routed `STAGE=8` path can flush after one expert for held-slot reuse; full-stream ring16 permits up to 16 but skips shorten windows. It already asked for a per-window length histogram plus per-axis admission/refusal. The candidate source also already has per-layer/chunk aggregates `gu_admitted`, `gu_declined`, `down_admitted`, `down_declined`, `gu_covered`, `down_covered`, fallbacks, total `flushes`, `held_reuse_flushes` and `released_slots` (`prefill.cpp:2107-2164, 2451-2459`). These totals still omit the distribution of `nd_n` at each flush. Repeating that generic proposal would add nothing; the useful refinement is to make the count receipt joinable to the exact `chunk_offset`, `layer`, route mode, and `(gu_type,down_type)` already present in the transfer/census row, and to record `window_n=1..16` counts separately for successful GU, refusal/fallback, and Down. Keep reason counters for held-slot reuse, ring-pressure, skip, group-tail and max16. This supplies the missing actual-format weighted window mix without per-window log spam.

The narrow next run should use an already qualified, source-pinned batch-on caller and the existing strict 32K comparison protocol, paired with the unchanged batch-off arm. Record quiet end-to-end prefill wall in repeated matched runs; check exact selected outputs/health/fault status, route counts and H2D request counts remain equal. A bounded diagnostics-only run can emit the window histogram and existing per-axis totals. No test or model run is proposed or performed here.

For phase attribution, current `STRATA_PREFILL_TIMING` groups a compute-stream mark-to-mark interval under labels including `dequant`, `wait copy`, `gemm gate/up`, `gemm down` and `host grouping`; code comments explicitly charge inter-mark GPU idle gaps to the preceding phase. Candidate `native_flush` is not a separate phase. This diagnostic can show whether the broad dequant interval changes, but cannot say it is exclusive GPU service. The smallest additive host-side timing is one accumulated `steady_clock` duration around calls made inside `native_flush`, emitted once per chunk/layer alongside the window summary; do not add a per-expert event or drain. It is comparable to the component's host-enqueue metric and quantifies dispatch/validation CPU time, not GPU execution. Pair it with a matched quiet ON/OFF wall measurement and existing coarse phase diagnostics; report the attribution limitation. If the existing timer is used, preserve its overhead line and keep that diagnostic separate from quiet latency.

Comparison against existing R work

- `research-native-batch-compiled-call-path-v1.txt` already documented the exact missing window histogram and per-axis counters, plus why the 269.159 t/s reference cannot establish a gain. This report adds a quantitative conditional extrapolation from the structured n16 component data, the maximum call-count arithmetic, actual old-path H2D split, and the join keys needed to weight windows by format/chunk/layer.
- `implementation-xe-native-dequant-prefill-batch-v1.txt` already describes ring-slot safety, held reuse, 16-entry flushing, and a staged qualification plan. Its expected diagnostics were proposed source behavior, not an executed batch-on observation.
- `round365-xe-e32-critical-path-measurement-controls.txt` already warns that phase totals/copy counters are not an exclusive critical path and proposes broader phase, transfer and worker data. The narrow instrumentation here adds only batch window length/reason and one aggregate native-flush host duration; it does not repeat the full system profiling plan.
- v129 registry reports 508 committed research reports and the two v2 component/byte controller reports; they confirm component qualification, not caller application or model speed. `RESULTS_JA.md` itself states no new model prefill, decode, full-context or RESTORE performance qualification.

Decision

Existing evidence can state a 16× ideal maximum reduction in native host wrapper calls and an unweighted conditional 0.87–9.88 s service extrapolation if the component measurements transferred perfectly and were serially exposed. It cannot state an actual percent saving or an end-to-end upper bound. The high-value minimum is a real `window_n`/reason histogram joined to per-axis admission and format/route metadata, plus quiet paired ON/OFF 32K wall. Add one aggregate `native_flush` host clock only if distinguishing CPU submission from coarse dequant/wait phase time is necessary; it does not replace the paired wall result. Do not choose an optimization or claim savings before those observations.
