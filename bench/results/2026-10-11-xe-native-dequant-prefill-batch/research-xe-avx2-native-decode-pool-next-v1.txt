## Cross-implementation comparison

**llama.cpp / GGML CPU.** The upstream CPU pool uses a shared atomic chunk cursor for matrix-multiply chunks. This validates dynamic claiming as a common pattern, but Strata's reports already identify dynamic atomic row claiming; copying that mechanism is not a difference. Its IQ decoder baseline is also the source of Strata's NT=1 fallback and is not an alternative decoder. Primary references: [GGML CPU threadpool](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cpu/ggml-cpu.c) and the pinned [IQ quantized AVX2 kernels](https://github.com/ggml-org/llama.cpp/blob/3cf03257f219afbe7334045ff7c6a06ac68c627d/ggml/src/ggml-cpu/arch/x86/quants.c).

**KTransformers AVX2 grouped MoE.** Implementer commit `9481291` describes an AVX2 MXFP4 path that transforms activation rows into the fixed decoder order, amortizes decode across token groups, and falls back for large per-expert batches to bound per-thread FP32 staging. Its author reports EPYC 7452 / DeepSeek-V4-Flash / MXFP4 results. The transfer idea—batch shape can change whether weight decode should be amortized, and scratch capacity can require a fallback—is already represented by the prior R30 IQ row-panel screen. It does not create a new IQ3_S path: its fixed MXFP4 permutation and BF16 activations differ from Strata's indexed IQ grids and Q8 quantized activation data. Its measurements do not predict 5600X performance. Source: [commit and implementation details](https://github.com/kvcache-ai/ktransformers/commit/9481291).

**vLLM and IPEX-LLM.** The vLLM sources surfaced by this search describe expert parallel placement/load balancing or grouped GPU kernels, not a Ryzen-local quantized IQ row pool. IPEX CPU LLM examples focus on conventional weight-only INT8/INT4 and dense operators; no matching IQ3 decoder/pool implementation was located. These are not evidence for porting their batching or scheduling policy into this exact AVX2 path. References: [vLLM CPU backend docs](https://github.com/vllm-project/vllm/blob/main/docs/getting_started/installation/cpu.md), [vLLM expert parallel/load-balancer docs](https://github.com/vllm-project/vllm/blob/main/docs/serving/expert_parallel_deployment.md), [IPEX CPU LLM examples](https://github.com/intel/intel-extension-for-pytorch/tree/main/examples/cpu/llm).

**Other code and author material.** Hugging Face's experts interface distinguishes `batched_mm` (duplicate expert weights per token) from grouped expert matmul; it documents an operator/data-layout choice, but does not identify a better AVX2 IQ row kernel for this pool. KTransformers R104 and llama.cpp R30 are the closest prior implementer material and have already been screened. References: [Transformers expert interface](https://github.com/huggingface/transformers/blob/main/docs/source/en/experts_interface.md), [KTransformers AVX2 implementation commit](https://github.com/kvcache-ai/ktransformers/commit/9481291).

## Decision: no new kernel or scheduler delta established

The external comparison plus registry reconciliation yields no unreported, source-supported 1–3 implementation changes for this target. In particular, it does not support another row-order rewrite, generic batch/task knob, static worker affinity, different chunk scheduler, or AVX2 panel proposal. Those overlap with prior reports, and external implementations use different packed formats, batch regimes, hardware, or execution layers. That is a no-new-candidate finding, not a claim that the current kernel or pool is optimal.

The remaining unknown that can still change the decision is narrower: during actual verify windows, does variable `ExpertJobMulti.nt` make one or more current equal-row tasks the tail, or are the phase intervals mostly useful balanced row work (or hidden behind GPU work)? R12/R86 already define NT-weighted boundaries and task-tail diagnostics; without actual worker-tail evidence, implementing the weighted policy again would be premature.

## Minimum useful counter, if the owner asks for one

Use the already-existing clean request/window wall outcome and GU / FF-quant / Down phase elapsed counters, then add only a compact per-phase-batch tuple:

`(layer, NativeFmt, nt=1/2/3/4+ counts, task_count, per-worker claimed rows, per-worker row-call thread-CPU ns, last-finish minus first-finish ns)`.

Aggregate over a fixed number of completed windows; do not store task timelines or per-row events. This is the minimum discriminator for the only surviving pool question: phase wall alone cannot distinguish useful row work from queue/barrier/tail, and row counts alone cannot show NT-skewed service. The `nt` bins and phase counters are already part of prior proposals; the incremental minimum is per-participant row-call CPU and finish skew, not the extensive per-wakeup/per-expert-ready telemetry from R57. Thread CPU is a participant-work proxy including code in the timed row call, not a hardware cycle or pure matmul counter. Keep this diagnostic instrumented and separate from clean decode throughput; compare emitted tokens over request wall time. Do not infer that CPU pool time is on the critical path merely because its phase total is large.

Decision use: if rows/NT are balanced and worker finish skew is small, do not pursue weighted boundaries. If repeatable skew tracks NT while pool phase wall and clean output rate move together, a single equal-vs-NT-weighted boundary comparison becomes justified. If per-worker row-call CPU is balanced but physical decode remains slow, the pool scheduler is not selected by this counter; phase decomposition and wait/GPU overlap must direct the next question. No performance gain is predicted.
