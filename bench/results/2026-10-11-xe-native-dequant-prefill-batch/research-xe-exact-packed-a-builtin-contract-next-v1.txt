# Exact PackedA builtin origin and contract

Date: 2026-10-11
Scope: source, receipt, report and official documentation review only. No build, compiler invocation, GPU query, test, profile, model or service operation was performed. No source, Git state, or run artifact was modified.

## Finding: the name is synthesized by IGC

The undefined symbol is not a C++ template name emitted directly by the SYCL header. SYCL 7.1.0-pre (commit 504366f) lowers this `joint_matrix_load` API call to the SPIR-V `OpCooperativeMatrixLoadKHR`; the SYCL header calls `__spirv_CooperativeMatrixLoadKHR` for the Intel GPU device path. IGC v2.41.5 then resolves cooperative/joint matrix loads in `JointMatrixFuncsResolutionPass::GetMatrixFuncName` and constructs the internal load builtin name. Its source explicitly maps a row-major load of matrix A to the `PackedA` family, adds the `SG16` tag when `platform.hasExecSize16DPAS()` is true, appends matrix rows, columns and element bit width, obtains the following `8` from `getNumRowsPerWI(desc)`, appends the pointer address-space token (`_local`), and uses the fixed load signature suffix `_v8i8_pi32_i32`. These fields reproduce the observed name:

`__builtin_spriv_OpJointMatrixLoadINTEL_PackedA_RowMajor_SG16_16x16_i16_8_local_v8i8_pi32_i32`

The exact source is the official [IGC v2.41.5 JointMatrixFuncsResolutionPass.cpp](https://github.com/intel/intel-graphics-compiler/blob/v2.41.5/IGC/Compiler/Optimizer/OpenCLPasses/JointMatrixFuncsResolutionPass/JointMatrixFuncsResolutionPass.cpp), especially `GetMatrixFuncName`. The compiler’s source-level API is defined in [`matrix-unified.hpp` at the exact DPC++ base commit](https://github.com/intel/llvm/blob/504366f4b82ff00bbac7b0c956635eed8bc599d8/sycl/include/sycl/ext/oneapi/matrix/matrix-unified.hpp); the extension describes `joint_matrix_load` and its pointer/stride contract in the [same commit’s SYCL matrix specification](https://github.com/intel/llvm/blob/504366f4b82ff00bbac7b0c956635eed8bc599d8/sycl/doc/extensions/experimental/sycl_ext_matrix/sycl_ext_oneapi_matrix.asciidoc). SPIR-V’s [KHR cooperative-matrix load contract](https://github.com/KhronosGroup/SPIRV-Registry/blob/main/extensions/KHR/SPV_KHR_cooperative_matrix.asciidoc) leaves supported combinations to client APIs, accepts a pointer with scalar/vector pointee, and defines row-major stride in pointee elements. The SYCL overload rejects private memory but permits local memory. Thus the error occurs after a valid API path has become an IGC internal builtin reference; it is not a frontend error about the source overload.

### `SG16` does not mean subgroup size 16

IGC v2.41.5 appends `SG16` based on `hasExecSize16DPAS()`, not by reading the source `sycl::sub_group` width. Its source comment describes this as a distinct load family for the SIMD16 DPAS platform lane contribution. Therefore `Kernel<2>`’s source shape can have subgroup size 32 while IGC still emits an `SG16` builtin on a platform that has that DPAS capability. The `S2` / `SG32` disagreement is naming-layer confusion, not evidence that IGC misread the kernel’s subgroup size.

### Strong source mapping to `mma_gemm.cpp` `Kernel<2>`

At XeStrata commit `b72640fff05098f1762cb3bf9c427a5f8d7db31c`, `kShapes[2]` is `16x16x16`, subgroup 32, `packed=false`. `built<2>()` is true on the non-AMD target because its predicate returns true for shapes with subgroup size at least 32. For this shape, `FR` is false, so `Kernel<2,E>::operator()` reaches the ordinary A-load branch and calls `joint_matrix_load` on its local-accessor-backed, row-major `16x16` matrix A. `E` is half or bfloat16, both 16-bit elements. This exactly matches the logged `Kernel<2,half,...>` and `Kernel<2,bfloat16,...>` names and the IGC-generated dimensions, element width and local address-space suffix. This is a strong source mapping, not a captured per-call IR/SPIR-V proof.

`PromptAttnMma` is also a candidate: the same fixed source uses `joint_matrix<sub_group, half, use::a, T16, T16, row_major>` and loads A from local-accessor-backed `pp` at `src/kernels/xe/qsa_prompt_attn.cpp` lines 654–659. The log lists that kernel too. The strongest fully matching template and 16x16 type evidence is `Kernel<2>`; no full IR/module dump was collected to assign every occurrence.

This corrects the earlier report’s tentative characterization: `Kernel<2>` is not excluded by the `SG16` token. The token is inserted later by IGC based on platform capability. `mma_gemm.cpp` SHA-256 is `540a4366709b8a2caf43aae36bbaeefd21bf4290d5555557077c463754da2238`; `qsa_prompt_attn.cpp` SHA-256 is `6b5bb8c4b38245299bda06f2bce4fe785c4b4cc82dca7986389459cf8ff054b6`.

## What the source proves—and what it does not

The IGC pass constructs a call to a named builtin after inspecting the matrix type, operation layout and pointer address space. The normal local load path is explicitly named `_local`; IGC’s pass also exposes alternative load/store lowering modes through `JointMatrixLoadStoreOpt` (0 subgroup, 1 block read/write, 2 optimized block, 3 2D block) in its [configuration reference](https://github.com/intel/intel-graphics-compiler/blob/v2.41.5/documentation/configuration_flags.md). The official [KHR cooperative-matrix specification](https://github.com/KhronosGroup/SPIRV-Registry/blob/main/extensions/KHR/SPV_KHR_cooperative_matrix.asciidoc) does not mandate hardware support for a particular 16x16 half local load. The failed build says this generated internal builtin was undefined while creating a module. Together, this points to a missing or mismatched backend implementation/provider for this generated specialization as the immediate failure class. The inspected public sources do not prove whether IGC should have a builtin implementation for this exact specialization on this device, whether it was omitted by a build/configuration choice, or whether a compiler/driver interface mismatch led to the unresolved reference. No public exact-symbol defect or fixed commit was identified.

The DPC++ header and its SPIR-V output establish the front-end contract, but the exact internal symbol is synthesized later by IGC. `IGC_JointMatrixLoadStoreOpt=0` or `1` remains only a diagnostic candidate; none of the modes was tested, and no mode is established here as a fix. The safe avoidance path remains build-time exclusion of all affected local joint-matrix specializations with a separately validated non-matrix fallback. A runtime branch alone may still leave the failing specialization registered for background JIT compilation.

## Provenance limits and next useful evidence

The failed log excerpt and exact source/API mapping strongly identify a candidate call site and the internal-name construction. We did not capture the actual failing module’s SPIR-V, post-IGC LLVM IR, or builtin-library symbol index; therefore the origin of every repeated instance and the missing definition/provider are not proven from a single artifact. The next decisive artifact would be an IGC shader dump of this exact module with its SPIR-V, `*_beforeUnification.ll`, post-joint-matrix-resolution IR, and builtin link diagnostics, together with the actual IGC component version or the driver package build identity. A reduced single `16x16` half/bfloat16 matrix-A row-major local load would isolate whether the problem is tied to this specialization. These actions were not run here.
