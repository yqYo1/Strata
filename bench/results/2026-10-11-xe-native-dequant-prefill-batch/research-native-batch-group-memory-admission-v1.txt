Group-dependent VRAM allocation
Source constants at `src/prefill/prefill.cpp:190` are `GU_ELEMS=1280*2560` and `D_ELEMS=2560*640`. With `n_embd=640`, `n_ff=2560`, each FP16 expert's dequantized GU storage is 6,553,600 bytes = 6.25 MiB and Down storage is 3,276,800 bytes = 3.125 MiB. They are separate allocations of `G*GU_ELEMS` and `G*D_ELEMS` only when `mmq_plan().fallback` is true (`prefill.cpp:800-802`; same accounting in `bytes_needed`, lines 1048-1051). Combined this is 9,830,400 bytes = 9.375 MiB per G slot, ignoring allocator rounding (the owning `Alloc.take` alignment/slack and final +8 MiB are separate).

These are arithmetic estimates from exact element counts, not observed allocation sizes. They explain the old source comment "157 MB at 16" (`prefill.cpp:800`). The 16 API entries do not determine this allocation size: a G=64 GEMM group retains 64 expert slots while the dequant API fills them in <=16 windows.

Conditional coexistence with MMQ buffers
`mmq_plan` is global across model layers (`prefill.cpp:599-621`): `any` means at least one layer takes MMQ; `fallback` becomes true if MMQ is off, no native layout is present, or any layer does not meet MMQ's type/layout admission. `carve` allocates `dq_gu` and `dq_d` based on global `fallback`, separately from the `if (mp.any)` block (`800-815`). Therefore a mixed model with `mp.any=true` and `mp.fallback=true` retains both the G-scaled FP16 group buffers and the MMQ workspaces. The MMQ path's per-layer `use_mmq` selection cannot release those group allocations; the fallback layers need them, and allocation occurs before route-level selection. The candidate batch itself is enabled only in a non-MMQ layer, but that does not change this buffer topology.

If MMQ is enabled and every layer is covered, `fallback=false`: `dq_gu/dq_d` are null, so varying G from 1 to 64 adds no group-buffer VRAM. MMQ's own storage remains: for `T>=STREAM_ALL_MIN`, `MMQ_GROUP*gu_max + MMQ_GROUP*d_max` bytes for packed group buffers; below that threshold, `MMQ_RING*MMQ_SLOT()` bytes for its packed ring. Shared quantized activations/temporary rows and identity/bounds also remain when `mp.any`. The MMQ workspace depends on each layer's packed matrix byte sizes, not the FP16 G. Conversely with MMQ disabled, `fallback=true`, `any=false`: G group buffers remain and the MMQ-only workspace block is omitted. The exact mixed-model MMQ bytes cannot be inferred from only n_embd/n_ff and MoE count; actual layer type histogram and `max_blob` are required.

G clamp and timing of the setting
`Prefill::set_expert_group(g)` clamps requested values to 1..64 (`prefill.cpp:1024`); there is no rounding to 8/16. `generate.cpp:5540` calls this setter before `lend_slots`/`Prefill::bytes_needed` calculations used for request borrowing (`5555-5565`). However the earlier startup expert-cache reserve is calculated around `4160-4187`, before this setter call. On a single GPU the `prefill_mib` term there is the fixed approximation `160 + (prefill_chunk*680)/1024`, independent of G (`4164-4170`). On a multi-GPU path it calls `Prefill::bytes_needed` (`4166-4169`) while the setter has not yet installed the user's requested G, so the static default G=16 is used. Thus the startup cache-sizing reserve does not account for G>16's additional 150/450 MiB in the single-GPU case, and in the multi-GPU case it sees the default group size rather than the requested group size. Later borrow/lend estimates do use the clamped G. This is a concrete pre-run admission gap for large G if buffers are allocated outside borrowed cache slots.

`Prefill::bytes_needed` mirrors most of the carve allocation order and includes the group arrays iff fallback, MMQ workspaces iff any, streamed ring slots, stage buffers and an 8 MiB alignment slack (`prefill.cpp:1028-1069`). `init` separately allocates `tok_dev` as `4*T` bytes before that counted region (`664-669`); it also creates streams/events and host/stager state. For a strict standalone VRAM floor, include `bytes_needed(g,ss,T)` at the effective G, plus `4*T` for token IDs and any other independently owned device allocations not included in the counted carve; then retain the existing 512 MiB free guard and account for concurrent owners/cache/session/MTP/BLAS allocations. `bytes_needed` is a deterministic source-side estimate of its counted allocations, not a promise that an observed device allocator will grant them.

10 GiB / old startup INFO evidence
The earlier R306 corrected admission report records a Xe 8K setup with `--expert-cache 144`, 281 MiB cache, and startup `INFO` `vram_free_mib=50`; the request did not reach generation because the owner required 512 MiB free. It also records only 29/144 cache slots filled before READY. This is an observed old-counts/startup record, not a measurement of the current candidate or a guarantee for an actual 10 GiB card. The 462 MiB shortfall to the existing 512 MiB gate is already larger than the G16-to-G64 increment of 450 MiB; with G64 counted in a future actual startup the cache sizing/free result could change, so do not simply subtract 450 MiB from that INFO or claim pass/fail. It does show why an INFO/free gate must be evaluated after correctly charging current fixed allocations and cache.

The v20 source has `INFO` fields for current free VRAM, cache slots/cache MiB and arena size (`generate.cpp:7088-7103`); it does not report G, `bytes_needed`, selected prefill chunk or whether buffers will be borrowed. The 10 GiB total alone is insufficient to derive usable free VRAM: prior allocations, cache sizing, context/KV state, MMQ buffers, reserve, borrowing and other processes matter. The model data `n_embd=640,n_ff=2560,48 MoE` determines the per-slot arithmetic above, not total peak VRAM. `cache144` is a startup cache count, not a stable amount available for additional allocations; borrowed mode can carve buffers from cache slots and therefore changes cache capacity/hits rather than making the same bytes disappear.

Admission proof that can be done before a run
1. Parse and record the exact requested G, clamp it with the source rule, and ensure sizing uses the resulting effective G before any cache reserve. Reject invalid/nonpositive/overflowing values rather than silently calculating a different group.
2. Pin model geometry (`n_embd`, `n_ff`, expert/layer counts), the actual layer type/MMQ admission map, max blob and chunk/ring settings. Compute the existing `bytes_needed` formula at that exact G and include separately allocated `tok_dev` and owner-reserve terms. For fallback geometry, the exact group delta from G16 is `(G-16)*9.375 MiB` for these dimensions; for fully MMQ-covered models it is zero. In a mixed model both this delta and actual MMQ workspace must be included.
3. For non-borrowing, compare that full count to the contemporaneous pre-allocation free bytes after cache, model state and other fixed allocations, retaining the 512 MiB post-admission floor. For borrowing, verify each device cache can lend enough tail bytes/slots under its actual size layout and count the resulting lower cache separately; a borrowed fit does not add those bytes to free VRAM.
4. At startup, emit and validate INFO including effective G, effective prefill chunk, borrow/own policy, MMQ/fallback plan or its sufficient summarized byte counts, cache bytes/slots and current free VRAM. INFO alone is a snapshot; a runtime allocator check is still needed at the actual allocation boundary. No values in this report establish the 10 GiB setup's current outcome.

Conclusion
G has a real 9.375 MiB/slot cost only where the existing fallback group allocations are present. G64 reserves an estimated 600 MiB there, 450 MiB more than G16. Mixed MMQ coverage retains this group allocation alongside MMQ workspaces; full MMQ coverage removes the G-dependent buffers. The requested G is clamped to 1..64 and reaches later borrowing math, but the earlier cache reserve is calculated before that setter and is G-blind on single GPU. Existing `bytes_needed` can support an exact source-side preflight once called with the effective configuration, but it must be incorporated before cache admission and supplemented for separately owned allocations and allocator headroom. No build receipt, historical INFO line or arithmetic estimate proves a new runtime admission result.
