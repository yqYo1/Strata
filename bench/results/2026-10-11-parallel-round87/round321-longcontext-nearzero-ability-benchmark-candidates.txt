# R321 — Practical long-context benchmark candidates for near-zero ability loss

Date: 2026-10-11
Status: read-only benchmark and prior-report review. No dataset, model, or source-code download; tokenization, implementation, test, build, inference, GPU/process query, Git operation, or cleanup was performed. This report selects benchmark candidates and a test contract; it is not evidence that FP16/BF16 storage has acceptable quality.

## Decision

Use a paired, staged suite at exact 32,768- and 65,536-token input lengths, with independent cases for (1) repository code review, (2) long retrieval/composition, and (3) factual answers whose fixed references are multi-token continuations. Make a small 50-case-per-family screen to reject obvious regressions, then use at least 300 independent task cases per principal ability family and context length before claiming a one-percentage-point-or-smaller regression rate. Three hundred is a statistical floor for a binary regression event, not a universal sample-size guarantee for continuous code-review scores; the latter needs a variance-based paired confidence interval and may require thousands of examples.

The 262,144-cell question is a separate physical capacity/lifecycle gate. A clean 64K quality result says nothing about physical cell 262,143, state restoration at the boundary, or 256K task quality. Do not combine that gate with the 32K/64K ability score.

## What the reviewed local evidence rules out

- R291/R294/R297 establish that STRATA_LOGPOS covers verifier-window inputs, not the long batched Prefill path. It cannot by itself score all continuation tokens after a 32K/64K candidate Prefill. A valid teacher-forced comparison must preserve the real batched prefix path, capture the first full-vocabulary logits after the final prompt token, score the first reference token there, force it into the state, and score every later fixed token. Assert complete target-position coverage. This remains distributional evidence; it is not a generated-answer ability score.
- R296's historical 262,144-cell result is from a separate older binary and is not current-source qualification. Any capacity run must obey the exact binary's admission rule and assert last-cell access and full lifecycle.
- The current 65,536-token fixture (clean64k-task-fixture-root-r3/manifest.json, fixture SHA-256 5284d8fa53d1ef28f6ba916a629faf901c890bc0c669bf986ee04ed72aa2c3ff) is a historical corpus prefix with a 49-token suffix reused from the 32K fixture. Its manifest says the body may cut source code, the historical lineage overlaps, the full chat template was not rendered, and it is not independent quality data. Exclude it from the benchmark and do not use its 49-token suffix as a multi-token quality set.
- R289/R299 report no quantified public result for simple reduced-precision storage of these exact Strata intermediates. Qwen's qualitative GR-residual claim, recurrent-state codecs, weight/activation quantization, and KV-cache results are not evidence for an uncalibrated transient or residual store in this engine.

The LongBench v2 503-question set is a useful optional held-out realism check because it covers documents, multi-document QA, code repositories, long dialogue and structured data with multiple-choice ground truth. Its choices are generally one short letter, however, so it cannot replace the factual multi-token continuation suite. A 503-item aggregate-only result also does not support one-percentage-point confidence separately for each of its six task categories.

For the code-review choice, SWE-PRBench is the closest available labeled task-size match: its paper reports 350 human-labeled pull requests, three frozen context configurations, and an LLM-as-judge score validated against human review. ReviewBench is operationally convenient and has a stable official evaluator, but only 219 total tasks. Neither benchmark by itself naturally produces 32K/64K input prompts. Adding repository context creates the relevant long-context stress but changes the benchmark configuration; retain the base configuration as a short-context control and name the extended set as a local derivative. Use LongCodeBench's 32K/64K contexts for code comprehension and repair, not as a substitute for review judgment.

RULER is preferable to a single needle demo because it exposes task complexity and exact answer keys while controlling position/length. Do not rely on one-key retrieval alone. The official repo's generated synthetic tasks intentionally test retrieval, multi-hop tracing and aggregation; its published results also show task scores falling with context length for several Qwen3 variants, reinforcing the need for matched 32K and 64K measurements rather than assuming a 256K window implies unchanged ability.

## Small screen versus near-zero qualification

Predeclare the operating meaning of “near-zero” as no more than **1 absolute percentage point of additional task regressions** at each length, with a one-sided 95% confidence bound. This is an evaluation target for this plan, not a result or evidence that a storage candidate meets it.

- At 50 independent baseline-correct tasks per family/length, zero new regressions gives a one-sided 95% binomial upper bound of about 5.8% (1 − 0.05^(1/50)). That is a practical screen for large damage only. A 50-item pass cannot support “near-zero.”
- At 300 independent baseline-correct tasks, zero new regressions gives a one-sided 95% upper bound of about 0.994%. At 350, it is about 0.85%. This uses the task as the sampling unit; 32K and 64K are separate length-specific denominators. If fewer than 300 items are correct in the FP32 control, continue sampling until 300 baseline-correct items are available or report that the 1pp gate is underpowered. Keep all cases in the overall accuracy comparison; this conditional regression bound supplements, rather than replaces, paired accuracy.
- For continuous per-task metrics (review macro-F1, rubric score, document NLL), 300 examples may not be enough. Estimate the SD s of paired per-task differences from a blinded FP32 repeat/control pilot, and size a one-sided 5%/80%-power paired test as n ≈ ((1.645 + 0.842)·s/δ)^2, where δ=0.01 on a 0–1 score. For s=0.10, this is about 618 independent items; for s=0.20, about 2,470. Use a cluster bootstrap by PR/document for confidence intervals. If the resulting upper bound does not fit within the predeclared −1pp margin, call it inconclusive, not pass.
- For paired accuracy use an exact McNemar interval/test on candidate-vs-control discordant task outcomes. For factual QA with multiple labels per item, score the item once using exact fields/evidence; don't inflate n by counting answer tokens, facts, needles, or repeated token windows as independent observations.
- A practical first wave is 50 per ability family/length: 300 long prompts across two lengths and three families, before any teacher-forced trace. The near-zero wave uses the full 350-PR review set, 300 cases for each RULER family at each length (1,800 retrieval prompts), and 300 factual-QA items at each length (600 prompts), then increases task-level sets whenever paired-score confidence intervals remain wider than the target. This is not a tiny run, but it is materially smaller and better targeted than running every benchmark task; a smaller set cannot honestly certify a 1pp loss bound across these abilities.

## Paired protocol required for the precision candidate

1. Freeze the reference and treatment binary/source, model pack and hash, runtime/driver, all prefill/decode flags, chunk size, sampling seed, prompt IDs, and tokenized user-facing prompts before inspecting candidate results. Only the target storage format may differ. Run FP32 control and candidate on the same exact token-ID sequence; do not compare one to chunk-major and the other to layer-major or alter the system prompt.
2. Use the current Qwen tokenizer source/assets recorded by the R3 manifest as the starting identity: tools/strata_tokenizer.py SHA-256 9b0327e25aa62754406a924db6cc137e6edb1d93c7af76a4f3d14a8920ea72c8, vocab.json 4ba64f0332abcfb0b600b7df1537d1e836e68009d5fb7cdb77339738dc6365c4, merges.txt 4ba698529766c7a2f5052083ea10cdf2485577f5237a332ee291054eb11e3332, and token_type.json 5088c8c298fc06af8382ddb3b76c888703ac2634e82263b97eedcc2ad202738b. Pin the chat template too (chat_template.jinja SHA-256 12827f24b742ea4e80cdc12dbcf9622227056b9f797252a3149263d4f9aaadce). These are asset identifiers from the old fixture manifest, not proof its body is a valid prompt. Render every new question through this one template, then hash the rendered UTF-8 and exact token-ID list. Assert both arms have identical IDs and exact input lengths 32,768 or 65,536.
3. Keep the prompt question/source marker and assistant prefix identical and at the same final position. Stratify supporting evidence over position bins; don't duplicate the answer passage, append artificial decimal-token tails, cut through code, or generate filler by repeating the old 32K/64K fixture. Pad only with frozen, unique, semantically plausible context from the relevant repository/doc corpus. Avoid answer leakage and ambiguous references. Verify each factual question is answerable from its short source passage with the fixed expected answer before it is surrounded by the long context.
4. For actual generated ability, use deterministic greedy decoding (temperature=0, top_k=1, fixed seed), a fixed maximum output length (128 tokens is sufficient for the short review/QA schemas), and the same EOS/stop strings from the same model template in both arms. Do not stop at an arm-specific newline or task score. Record truncation, malformed output, EOS position, parser result, exact match, expected findings/tests and denominator for every case. For generated code repairs, preserve the same sandboxed unit-test command.
5. Separately evaluate distributional change on reference answers. Preserve real batched Prefill for the long prefix; use the corrected first-logit + forced-reference-token + verifier-window contract from R296/R297. Record per-target token NLL, top-1/top-K identity, and KL/JS only when exact target coverage is asserted. Aggregate uncertainty by independent document/task, not token. Report distribution shifts as a diagnostic table; do not count them as demonstrated ability loss or use stable NLL alone to assert task quality.
6. Run each length as its own sample stratum. Report per-item paired control/treatment outcomes, length- and position-specific deltas, the predeclared confidence intervals, and all failures. Do not combine 32K and 64K into one denominator to hide a 64K-only regression. Timing runs remain separate from quality hooks and full-logit traces.

All prompts must include the exact same rendered chat template, model/system instructions, stop policy and context-token placement in both arms. The benchmark answers, labels, unit-test commits, and context assembly manifest need their own source/answer hashes. Keep full successful traces out of long-term artifacts after compact results and hashes are verified, following docs/ARTIFACT_RETENTION.md.

## 262,144-token capacity is a different test

Use one source/binary-pinned physical-boundary case to establish admission and capacity: exact token IDs, actual prompt plus generation slack allowed by the running source, physical 262,144 allocated cells, final prompt-conditioning token, last admitted cell index 262,143, and a short continuation/state check after the last cell. Include fresh/repeat/restore lifecycle if that is the target service path. The prompt must not exceed the version-specific admission predicate; older direct-GEN success cannot be transferred to a new generator or BGEN route. A test ending at 65,536 proves no property of full 262,144-cell occupancy, and a capacity pass makes no claim that ability is unchanged at 256K. A separate full-quality 256K set would need its own independent benchmark and sample-size plan; it is not selected here.

## Sources reviewed

- [NVIDIA RULER repository](https://github.com/NVIDIA/RULER) and [RULER paper](https://arxiv.org/abs/2404.06654): synthetic examples at exact sequence lengths with retrieval, multi-hop tracing and aggregation.
- [LongCodeBench repository](https://github.com/Zteefano/long-code-bench) and [paper](https://arxiv.org/abs/2505.07897): LongCodeQA and LongSWE-Bench; repository documents 32K/64K configs and repo-context task construction.
- [SWE-PRBench paper](https://arxiv.org/abs/2603.26130): 350 human-annotated pull requests and three frozen context configurations. This is an arXiv preprint; use its released labels/harness as a candidate, not the author's headline scores as Strata evidence.
- [GitHub ReviewBench repository](https://github.com/review-bench/ReviewBench): 25-task public test subset, 219 full tasks, human-reviewed gold findings. Its test subset is too small for the proposed near-zero claim.
- [LongBench official repository](https://github.com/THUDM/LongBench), [LongBench ACL paper](https://aclanthology.org/2024.acl-long.172/), and [LongBench v2 paper](https://arxiv.org/abs/2412.15204): fixed public QA/code tasks and ground truth; v2 has 503 items and six categories, with short multiple-choice answers.
- Anthropic's implementer write-up, [Prompting Claude's long context window](https://www.anthropic.com/news/prompting-long-context), describes source-specific question wording, filtering out questions missed on the short source passage, constructing long contexts from distinct passages, and testing answer locations/lengths. These are useful harness-design lessons, not claims about Strata.
- R291, R294, R296, R297, R299 and R301 in research-20261009/ define the candidate data-path, the teacher-forcing hook limitation, the separate full-context lifecycle, published precision-evidence limits, and required quality gates. These reports remain controlling for this selection.

## Recommendation

For a first practical screen, choose 50 each at both 32K and 64K from (a) long-context review cases, (b) RULER direct retrieval/multi-hop/aggregation, and (c) source-grounded QA with multi-token reference answers. If the screen stays close, expand to at least 300 baseline-correct independent items per family and length and size continuous metrics from the paired pilot SD. Keep a 1pp one-sided 95% target explicit; if the available tasks or interval cannot support it, the outcome is inconclusive. Do not take the old fixture's correctness or its historical suffix as a quality pass, and do not substitute NLL/top-K stability for generated ability. The 262,144-cell check remains a distinct capacity/lifecycle qualification.
