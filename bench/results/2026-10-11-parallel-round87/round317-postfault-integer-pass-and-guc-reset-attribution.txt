## Receipt and scope

Evidence: `/home/yayoi/.local/state/strata-sycl/post-reboot-tuning-20261007/postfault-status-health-root-r2/record.json` (closed; `passed=false`), with its referenced helper/source hashes and complete retained kernel interval. The original V8 receipt remains `FAILED/incomplete`; its faulting inferior was PID 2791225, and it recorded a real CAT18 engine memory fault, unsuccessful `-ENOENT` fault response, and engine reset. R2 verifies the known original inferior/debugger owners were gone before the new diagnostic, on the same boot. Its initial dump node/data metadata and final metadata are identical (`devcd1`); the old dump was not cleared or replaced.

The new diagnostic was deliberately narrow: a fresh `zeDeviceGetStatus` returned success before context creation; it then created a new Level Zero context/queue, allocated 64 KiB, completed one H2D, one 16,384-word integer kernel, and one D2H, and matched all 16,384 expected words. The health utility returned success after matching; the outer controller finalized the receipt as failed on the kernel interval gate. The record has `status_success=true`, `integer_exact_words=16384`, and `CPU_argument_gate_passed=true`. It executed no model, retry, userspace recovery, or userspace reset. These are positive results for that single data path only.

The scoped kernel interval was captured from a journal cursor immediately before launch and retained all 199 relevant BDF/xe entries. It includes: one G2H timeout (`fence 26233`, action printed as `3003`, `done no`); one `GuC PC query task state failed: -ETIME`; one `Schedule disable failed to respond, guc_id=0`; 30 `Check job timeout` messages, 31 `Timedout job` messages, and 32 each of `trying reset`, `reset queued`, `reset started`, and `reset done`. The timed-out-job lines say `guc_id=0 ... in no process [-1]`. The interval also has an unexpected engine-class warning and a `get_ctx_timestamp` stack trace. No new CAT18/fault-response line was present in this interval. The receipt's aggregate health gate failed on the new GuC PC failure and records `kernel_gate_error=RuntimeError('new fault or dump identity change')`; the dump identity and boot were unchanged. The health result is therefore a **failed post-fault health gate with a successful one-round data check**, not a clean device-health pass. It must not be summarized as “no reset”: the journal contains 32 reset sequences.

## Kernel meaning, with the source-version limit

The installed release string is `7.0.0-38-generic`; the exact vendor source, patch set, module build ID, and source-to-binary mapping are not available in this read-only evidence. The following is interpretation against the browsed upstream Xe source, not proof that the installed module has identical code. The upstream code snapshots are linked below so this source limit is visible.

- The Xe GuC CT source's blocking send/receive path waits for its matching G2H fence. If it remains incomplete at the wait timeout, it logs `Timed out wait for G2H, fence ..., action ..., done no`, removes that fence, and returns `-ETIME`. Thus the R2 G2H line means the host driver did not observe the expected GuC-to-host completion for that control message in time. It does not say what device work caused the missing response. In upstream `xe_guc_pc.c`, the “query task state” helper waits for SLPC/GuC PC to be in RUNNING state, sends a blocking GuC CT task-state query, and logs the query error if that send fails. The matching timestamp and action are consistent with that helper, but installed source and exact callsite remain unproven. [Upstream Xe GuC CT source](https://codebrowser.dev/linux/linux/drivers/gpu/drm/xe/xe_guc_ct.c.html#L1217), [upstream Xe GuC PC source](https://codebrowser.dev/linux/linux/drivers/gpu/drm/xe/xe_guc_pc.c.html#L167)
- In upstream Xe submission code, `Check job timeout ... not started` is printed when the timed-out scheduler job has not been marked started; it is not evidence that this job ran a long GPU kernel. The later timeout handler logs the queue's GuC ID, job/LRC sequence, flags, and process name/PID if the associated VM file has those fields. It initializes those process values to `no process` and `-1`; the displayed text therefore means no process metadata was available to that log path at that moment in that source version. It does not identify the creator, submission time, or whether the queue/job originated in V8, the new health process, or driver cleanup. `guc_id=0` is the queue identifier printed by the driver, not a PID or proof of ownership. [Upstream timeout check and handler](https://codebrowser.dev/linux/linux/drivers/gpu/drm/xe/xe_guc_submit.c.html#L1128), [upstream timeout logging](https://codebrowser.dev/linux/linux/drivers/gpu/drm/xe/xe_guc_submit.c.html#L1371)
- Upstream Xe logs “Schedule disable failed to respond” when the queue scheduling-disable acknowledgement does not arrive within its wait. That timeout path requests an asynchronous GT reset. The receipt then has repeated Xe `trying reset`, `reset queued`, `reset started`, and `reset done` records. This is positive evidence the kernel driver ran its reset path; `reset done` is a driver log milestone, not a subsequent end-to-end health qualification. The R2 controller's `reset_executed=false` means it did not invoke a userspace reset tool. [Upstream Xe schedule-disable/reset path](https://codebrowser.dev/linux/linux/drivers/gpu/drm/xe/xe_guc_submit.c.html#L1337)
- Upstream submission source contains a FIXME that CAT/IOMMU fault-message storms can cause schedule-disable messages to be lost and says that case triggers a GT reset. This is a possible general mechanism, not attribution here: R2 has no new CAT18/fault-response entry, the older CAT18 remains in a separate failed receipt, and installed source/firmware/runtime behavior are not pinned. [Upstream Xe timeout path and FIXME](https://codebrowser.dev/linux/linux/drivers/gpu/drm/xe/xe_guc_submit.c.html#L1337)
- Xe's coredump documentation says its data is a snapshot of the first hang and subsequent hangs do not replace it until userspace releases the dump or its timer expires. R2's unchanged `devcd1` metadata therefore preserves the identity of the pre-existing dump; it cannot prove there was no new kernel reset/hang in the interval. No dump data was read. [Linux Xe device-coredump documentation](https://docs.kernel.org/6.16/gpu/xe/xe_devcoredump.html#snapshot-at-hang)

## Can the old queue be separated from the new tiny diagnostic?

No. The sequence is temporally inside the new receipt's journal window and overlaps the diagnostic, while the first logged timed-out sequence is reported as not started and later lines repeatedly report queue 0 with no process/PID. That is consistent with a stale queue/job whose owning userspace process had exited, but it does not prove that story. The receipt has no per-queue creation/close trace, submit-to-seqno mapping, context/VM identity, fence-to-process mapping, or contemporaneous per-process engine trace. Nor does it show that the single tiny SYCL command itself caused those Xe jobs. Its success markers only prove the host saw successful completion and exact returned values for that one allocation/kernel/copy sequence; they do not resolve the separate driver/GuC events. Since the dump was unchanged and the interval has reset events, neither unchanged dump metadata nor “no new CAT18” separates old teardown from new work.

The helper's fault regex is a coarse classifier, not the record. It matches a limited vocabulary (`page fault`, `fault response`, `timestamp stuck`, `wedg`, `engine reset`, `gt reset`, `guc.*timeout|timed out|failed`, `memory.*cat`, `device.*lost`). It catches the GuC PC query failure but misses important wording in this receipt, including `Check job timeout`, `Timedout job`, `Schedule disable failed to respond`, `trying reset`, `reset queued/started/done`. The complete 199-entry capture is why reset activity remains visible even though the classifier did not enumerate those messages. Future gates must classify the complete scoped interval and explicitly treat Xe timeout/reset lifecycle messages as failure; absence of CAT18 alone is insufficient.

## Finite source gap and admission requirements

A finite host/source-only gap remains: obtain the exact vendor kernel package source revision and patch set for `7.0.0-38-generic`, then map the installed `xe` module build ID/hash to that source. With that mapping, inspect the exact shipped versions of `xe_guc_ct`, `xe_guc_pc`, `xe_guc_submit`, timeout/reset helpers, and GuC action definitions to confirm message and action-code semantics. This can clarify whether the observed strings/code path match upstream. It cannot reconstruct the lost per-queue owner history or establish the cause of this event. No live host query was made or is needed to state that limitation.

Future admission to a larger diagnostic must be separately authorized and start only after the existing failed results are preserved and the unresolved reset/health status has an explicit disposition. Its gate should require a new status success, exact data result, and a bounded BDF-scoped kernel interval with **no new GuC CT timeouts, job timeouts, schedule-disable failures, reset attempts/completions, fault responses/CAT errors, or dump-identity change** across the whole probe. Retain the complete interval and per-command timestamps, not only a regex summary. If any such event occurs, preserve the failed status and stop: no automatic retry, model run, reset, rebind, service startup, or dump clear. Only after a clean gate should separate staged runtime/model qualification be considered. This is a proposed admission standard, not authorization to run it.

Decision: R2 proves that one fresh status call and one 64 KiB exact integer round succeeded, but its own kernel-health gate failed. The 32 logged Xe reset cycles and related queue timeouts prevent admitting even a tiny health pass, much less a model or larger diagnostic. Cause and old-vs-new queue ownership remain unresolved.
