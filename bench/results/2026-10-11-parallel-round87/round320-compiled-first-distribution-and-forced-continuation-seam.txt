## Actual candidate path and indexing

In this source, `n_batched` is `n_prompt - 1` by default (around 11682); `prefill.run(o.tokens.data(), n_batched, 0, err)` executes that prefix at 11770. The generator sets `pos_start = n_batched` and `tok = o.tokens[pos_start]` at 11809. For a prompt of `P` IDs, this leaves `o.tokens[P-1]` for the ordinary token loop. That loop calls `session_token`/`session_loop` at `pos`, which advances the main `SessionState` (including its KV and recurrent state), then `run_head` at about 11964. Thus at `pos=P-1`, after consuming the final prompt token, `d_logits` is exactly the first continuation distribution `p(c0 | prompt)`. This is the candidate's first relevant head row, not a Prefill callback.

The default prefill shape is essential to the experiment: require the selected candidate chunk path, `n_batched == P-1`, and no `--prefill-until` split that sends a suffix of the prompt through the token path. Keep all storage/chunk arms identical except the intended candidate flag. The ability mode should reject or explicitly report `native_pack`, which skips this plain loop (`if (native_pack) { spec_pos = pos; break; }` at about 11830) and routes its final prompt token through a verifier window instead. Supporting that separate architecture requires a matching one-row verifier hook; it must not silently claim to use the direct token-loop seam.

After `run_head`, ordinary code reads logits only if `!o.stream_token || o.check_logits || emit_logits` (about 11969). It then samples via `sample_tokens`, copies `d_next`, appends the sampled ID, and chooses the next token from the prompt or the sample (about 12019–12100). `--dump-logits` can expose the row, but it does not force a reference continuation. Therefore a minimal ability-only CLI/API is an opt-in token-ID file (e.g. `--ability-follow PATH`) consumed only in this plain token loop. On the scoring run, force a host logits readback at each needed position, score the target ID, and use that same supplied ID as `next` for the following input. Do not invoke the sampler in this branch. This gives the exact flow: score c0 at pos P-1; feed c0 at pos P; score c1; continue through the last requested target. It uses one common generator-owned `SessionState`/KV rather than reconstructing a suffix state.

A numerically stable host score matches the verifier's existing method: for logits row z, compute `m=max(z)`, `lse=m+log(sum(exp(z_v-m)))`, and `logp(target)=z_target-lse`; `Verifier::window_logprobs` does this at about 2443–2495. Reuse that calculation/format or keep the ability hook's row calculation equivalent. Emit absolute predictor position, target ID, target log-probability, top ID/top log-probability and optional top-K IDs/log-probabilities. The existing verifier helper cannot itself be called from this plain-loop head row, because it owns verifier-window `head_logits_`; the missing integration is the generator hook, not another Prefill-side quality assertion.

## Ownership and scope

The generator owns input IDs, `pos`, `tok`, `SessionState`, the main model KV/recurrent state, PLE predecessor updates, and the logits returned by `run_head`. The ability hook should be the sole owner of the forced sequence cursor and of replacing the sampled `next` with the next fixed target. It must not advance `pos` or mutate KV separately: the next ordinary loop iteration consumes the forced ID once through existing `session_token`/`session_loop`. This avoids a duplicate/missing last-prompt token and keeps position/KV changes aligned.

For the minimal target ability run, require MTP and speculative decode off (`--mtp` absent, `--spec=0`), and do not enter the `Verifier` path. The prompt's MTP draft KV is optionally populated by `prefill.on_chunk` only when MTP is bound; with MTP disabled, there is no secondary MTP state to advance. The verifier's KV/window state and `commit` logic belong to the speculative branch, not this direct hook. This restriction is acceptable for a target ability comparison and makes clear what the result covers. If a later experiment explicitly needs MTP, it needs a separate hook that feeds the same fixed IDs to the drafter and advances its KV; if it needs verifier execution, it must force a one-token verifier window at each continuation position and commit exactly that input. Neither should be implied by a direct-loop result.

Existing `--spec-follow` is not that hook. Its documentation calls it an argmax replacement for speculation (`--spec` required); in the ordinary path the last prompt token has already been sampled and pushed to `produced` before verifier mode begins. The speculative `follow` cursor is initialized from `produced.size()`; that first already-sampled c0 is therefore outside forced continuation coverage. It substitutes IDs in verifier output and counts argmax disagreements, but it does not log every fixed-target log-probability. `STRATA_DUMP_FIRST_LOGITS` is a diagnostic one-row dump in the first speculative window, not paired scoring or forcing. `STRATA_LOGPOS` remains the R294 verifier-window-only path.

## Default timing and full-boundary checks

Make the new mode opt-in and inactive for ordinary generation: no continuation-file open/parse, extra host logits transfer, log-softmax work, output file, or token override when absent. When enabled, the host readback/scoring is deliberately an ability-evaluation run and must not be used as a timing measurement. The existing default sampler and timing path should be byte-for-byte behaviorally unchanged when the option is absent; the candidate's performance run remains a separate invocation.

Validate input before doing any model work: continuation IDs are nonempty when requested, each ID is in `[0,n_vocab)`, the requested number fits the configured generation and context bounds, and the token-file length is the declared score length. Define `P` as the prompt length and `N` as the number of target continuation IDs. A full score needs predictor positions `P-1 ... P+N-2`, so require `P+N-1 <= max_context`; its final predictor position is `P+N-2`, and the last forced continuation token itself need not be consumed to score it. Log `P`, `N`, first/final predictor positions, max-context, chunk, and selected Prefill path. Assert exactly N output rows and target IDs equal the supplied sequence at offsets 0 through N-1, with no duplicate or skipped position. At physical capacity, explicitly distinguish a 262,144-cell model allocation from a request that would need a predictor at position 262,144: the latter is out of bounds. A valid end-boundary score has final predictor position at most 262,143. Also assert the last prompt token was processed once, first target row is at P-1, and any stop/EOS logic cannot truncate a fixed continuation before coverage completes.

This identifies a narrow, plausible harness seam in the actual compiled source. It is not implementation guidance for modifying Prefill itself, a proof that the host-backed/chunked storage path ran, or evidence that BF16/FP16 changes preserve ability. No file other than this report was written.
