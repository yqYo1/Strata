## What the compiled server path actually does

In the compiled generator, MTP loads before the expert cache (around lines 3931–3954); the target native output head is loaded separately. The serving prompt setup selects/checks the chunk and initializes its long-lived `Prefill` object in `init_prompt_paths` (around 6693–6777), before `READY`. `Verifier::init` and `mtp.bind` follow Prefill initialization (around 7085). Release/restore callbacks are installed later (around 7607), and the consuming callbacks are on the layer-major route. This differs from treating the non-server one-shot decode path as the server's prefill admission path.

During a prefill chunk, `sp.draft_kv`/`mtp.prefill` uses the dense MTP projections and its K/V/recurrent state. It does not use the decode-only MTP expert payload or MTP draft head. The verifier is also not called by that chunk callback. The server nevertheless retains its initialized Prefill workspace across requests. Existing callback release is too late to change the initial `sp.init` admission, and its existing restore point is inside Prefill execution while its workspace is still live.

This means the useful lifecycle seam is not just “suspend before the one prefill call.” To retain a decode-only lease across server prompt execution and avoid the restore/workspace overlap, a server change needs a request-level cycle: suspend before owned Prefill initialization, run/drain prompt, retire/reset Prefill before restoring decode weights, then suspend again and reinitialize owned Prefill before the next prompt. That requires replacing or explicitly managing the current persistent workspace lifecycle, exact fixed-chunk admission behavior, and the shared MTP user's cancellation/error/concurrency boundary. The pinned generator shows no ready-made server lease scope that provides those guarantees. Therefore this report does not recommend moving only the existing callback or applying the R275 one-shot ordering to the server.

## Capacity implication, not an admission result

R279's retained same-owner evidence is an 8K workspace with 1,565 MiB free after startup, and its source-accounted 16K increment over 8K is 1,672.5 MiB. Preserving the server's 512 MiB admission guard yields a 619.5 MiB shortfall before a lease. Releasing the inspected 896 MiB MTP expert/head map would leave an arithmetic margin of 276.5 MiB after that increment and guard (`896 - 1672.5 + 1565 - 512 = 276.5`). This is only the arithmetic scenario: it assumes the entire map is actually released, no additional fixed costs, and comparable free-memory conditions. It does not account for fragmentation, first-use/runtime allocations, physical commitment, device/desktop variation, or prove 16K fit. Expert-only release is 680 MiB and leaves just 60.5 MiB by this arithmetic, making the head portion relevant to a robust candidate but still not a fit claim.

## Minimal future implementation seam and gates

A real server candidate must introduce an explicit serialized lease owner spanning all uses of the shared MTP object. It must make the owned Prefill workspace request-scoped (or equivalently reset/reinitialize it at safe boundaries), perform complete queue drain and graph retirement before unmap, preserve dense MTP and session state, and restore/verify exact bytes at the original addresses before final prompt-token verification or any draft/decode graph replay. It must rebuild the required prompt/decode graphs after restore. Cancellation, partial suspend, reset failure, partial restore, verification failure, and next-request recovery need a fail-closed policy; the current generic callback does not supply this boundary. Bind/head eligibility and all graph aliases must be proven against the linked implementation before counting the head bytes.

Next evidence should first close linked `libstrata_core.a` member/source identity and confirm the release flag is enabled and the full snapshot covers the exact expert/head payloads. Then implement only the owner/lifecycle boundary, add CPU transition/failure tests, compile the actual generator/MTP/Prefill translation units under the recorded flags, and qualify fixed 8K no-borrow parity before attempting fixed 16K. A 16K attempt must record actual selected chunk, mapped release/reallocation, every transfer, init and reset/restore peak/free/high-water values, graph recapture, and the existing correctness gates through the final prompt token and subsequent decode. Keep the full 262,144-context state/output qualification; no accepted 32K route result substitutes for it.

Decision: exact compiled-generator evidence confirms that MTP decode experts and draft-head rows are unused by prompt K/V, and provides a plausible conditional 896 MiB map lease. It also confirms that current server ownership/admission timing cannot use the old one-shot callback proposal safely. No safe server implementation or larger-chunk fit is established by this report.
