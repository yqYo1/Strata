## Completion and mapped-output ownership

The v4 implementation closes the original MTP host handoff hazards described in R353/R355: completion becomes pending before asynchronous submission, waits are checked across the MTP compute and side streams, failure is sticky, and unknown completion prevents later reuse/free. Draft-step graph execution calls `wait_step(j)` before reading mapped `h_out_[j]` and `h_prob_[j]`. The chain path does not treat an early event as permission to read one element while later steps can write other elements of the same allocation: `chain_outputs_ready()` calls `complete()` and then `chain_poll()`, and `chain_poll()` performs a checked whole-chain completion before copying the mapped arrays into the public chain buffers and clearing `chain_live_` (`mtp.cpp:1360-1375`). Both `prepare_chain()` and `chain_launch()` enforce `host_handoff_concurrent(cs_)`; `chain_outputs_ready()` also checks it. `chain_poll()` has no duplicate capability check, but the only state it can poll is established by the gated launch, and that capability is static for this process/device.

The persistent prefill host token staging (`pf_host_`) remains alive across asynchronous uploads; per-call vector-backed copy inputs use the checked-copy path that retires their source before return. Public operations are guarded by the completion state, and failed/unknown async work takes the fail-stop cleanup path. The implementation report and the helper test source were reviewed; tests were not run here.

## Actual caller qualification

**Pipelined prompt prefill.** At `generate.cpp:8557-8558`, the caller uses `mtp.prefill(..., false)` and records a corresponding MTP stream event after the prefill. The producing verifier's final residual rows are exposed only after `v.done()`/`pl_finish` has completed the stage work (`verify.cpp:2578-2586`). Before the same-parity stage verifier is reused, its launch waits for that MTP event (`generate.cpp:8545`). MTP copies the token inputs into persistent `pf_host_` before returning, so the caller's local `nx` vector may expire safely. `pl_drain()` services both verifier parities, synchronizes both stage streams, then synchronizes the MTP stream (`generate.cpp:6075-6095`); checkpoint/park/serial transitions use this drain invariant. The non-pipelined verifier path synchronizes its compute and copy queues before returning (`generate.cpp:1609-1616`); ordinary MTP prefill uses its default synchronous path and waits for each chunk (`prefill.cpp:1151-1157`). The full-context probe's exact callback is invoked only after target prefill has completed and explicitly synchronizes the MTP stream; R356 separately audited that path.

**Chained decode and borrowed residual source.** `chain_launch()` stages `src_R_` to `window_R_` using `copy_async` on the MTP stream before launching its graph (`mtp.cpp:1257-1265`, `1290-1348`). The pipeline sets this pointer from `V1(A).final_R(0)` at `generate.cpp:9491` and `9514`. The source-producing `A` has already reached `s1_done`; the caller's stage service calls `done()` and `pl_finish()` before setting that state (`generate.cpp:9284-9296`). The source rows are therefore ready before MTP enqueues its copy. The MTP chain remains live until checked completion; the pipeline polls/drains it before accepting the verdict and before another chain/source is scheduled (`generate.cpp:9316-9340`, `9438-9445`). The verifier parity buffers alternate, and a given parity is not reused for a later source until this verdict/drain progression has passed. The pipeline's end-of-path `pl_drain()` also synchronizes MTP. This qualifies the borrowed pointer lifetime in the actual caller; it does not rely on a per-step event to authorize mapped output reads.

**Native direct-token path.** The direct `--stream-token` producer completes sampling-token readback by synchronizing `token_stream` before using the host result. The persistent QSA metadata rewrite is additionally gated: if host handoff concurrency is unqualified, it takes `device_sync()` (`generate.cpp:4847-4858`). The corresponding output read uses `copy_async` followed by checked `stream_sync(token_stream)` (`generate.cpp:10358-10369`). These guards are part of the reviewed stable root hash.

**Snapshot, restore, and KV state access.** The running snapshot source path is taken after the server's request/drain boundary; `conversation_snapshot_sources()` captures the authoritative state synchronously, and restore uses bounded synchronous host-to-device writes (`generate.cpp:7853-7860`, `7930-7943`; R353/R356 describe the callee-level copy contract). The parked-conversation restore has the same boundary and returns fatal on partial transfer before decode (`generate.cpp:8317-8324`). `mtp.kv_restore(resume)` occurs before request prompt reading (`generate.cpp:8427`); its failure is intentionally fail-stop via exception rather than a structured request error. Raw `kv_state_rw` has two current consumer families: `Prefill::draft_kv` calls `mtp.idle()` before its direct QSA append and synchronizes its own queue before returning (`prefill.cpp:885`, `1009-1018`); the full-context probe snapshots, poisons, verifies, and restores state on synchronized direct paths and does not poll MTP draft outputs afterward (R356).

## Failure propagation and limits

The regular decode callers check `mtp.draft()`/`mtp.draft_first()` false returns and report the error (`generate.cpp:10599`, `10786`). `set_draft_sampling`, `set_draft_history`, and `kv_restore` throw on failure and have no local structured-error conversion at their call sites (`generate.cpp:8820`, `9717`, `10470`, `8427`); the exception escapes the request/main execution and fails the process. That is fail-stop behavior, not graceful API recovery.

The static review supports completion/ownership safety and caller ordering for the paths above. It does not qualify unsupported hardware/driver host-USM concurrency, a fresh LLVM runtime, compiler behavior, performance, or numerical behavior. Those remain with the root's planned build/runtime/tests. Chain launch also does not sentinel-initialize every `h_out_` slot before execution; this is a possible fault-detection enhancement, not an observed ownership race, and the chain path is capability-gated.
