# R214 — Production GEMM and expert-copy event-capture contract

Date: 2026-10-10 (Asia/Tokyo). Read-only implementation-feasibility audit on the immutable SYCL/DPCT source at commit `185fa78098bee4be01ac81ad4f791673d24246f3`, plus primary oneMKL, SYCL, and Intel PTI documentation. No implementation, build, test, inference, GPU/process query, profiler run, Git operation, service action, or cleanup was performed. Only this report was written.

## Finding and recommendation

The least disruptive route is an opt-in, bounded event ledger in the existing prefill instrumentation, then one short `unitrace` capture as an independent host/device timeline check. Do not infer actual GEMM service from the `gemm down` phase total. The current copy timer already retains `sycl::event` plus logical byte count and layer behind `STRATA_PREFILL_TRANSFER_TIMING`; its copy queue is created with profiling enabled under that flag, and it queries events after the prefill work has already waited. This is a real capture path, but it currently emits aggregates, has no expert/copy identity or per-copy row, and does not itself show host API or staging waits.

The GEMM seam is clear: `Gemm::f16` calls DPCT `dpct::blas::gemm`; the DPCT overload is `void`, and `dpct::detail::gemm_impl` calls `oneapi::mkl::blas::column_major::gemm` but discards the returned event. The oneMKL USM GEMM API returns a `sycl::event` whose completion represents the routine. Thus no caller-returned GEMM event exists today; a phase marker around the call cannot substitute for one.

I recommend adding a nullable event output only along the existing half-input / float-output oneMKL path, then collecting that event at the two native fallback call sites (GU and Down). Keep the current `Gemm::f16` invocation and output behavior exactly as-is when the event-audit flag is absent. Do not add waits, queue barriers, replay, or a second GEMM call. Make the capture SYCL/oneMKL-only; if a backend or fallback cannot provide the event, report `unsupported` and do not combine it with event-qualified samples.

## Event fields, service definitions, and validation

For each returned GEMM and expert-copy event, retain `command_submit`, `command_start`, and `command_end` after the program’s existing completion synchronization. Derive:

- oneMKL routine event span: `command_end - command_start`;
- queue delay after submit: `command_start - command_submit`;
- preceding same-queue gap: current `command_submit - previous command_end`;
- copy event byte rate: logical copy bytes divided by that event’s start-to-end span;
- overlap: interval intersection between copy and compute events on the same backend timebase.

These are event-level operation spans and logical byte rates, not proof of exclusive kernel-busy time, physical PCIe payload, or DRAM traffic. A returned oneMKL event guarantees the routine’s completion, but the library may implement the routine with internal work; use PTI kernel events when a kernel-level decomposition is needed. SYCL specifies that profiling timestamps from events sharing a backend use a common timebase, so differences can join the compute and copy queues. Host `steady_clock` values remain a separate clock; do not directly subtract them from event timestamps.

Validation must happen only after the existing compute/copy completion waits and thread joins: confirm exact queue/device/context identity, every retained event is complete, drain async queue errors without adding a wait, query profiling fields with exceptions caught, enforce `submit <= start <= end`, ensure nonnegative/nonzero durations where expected, check queue-clock monotonicity, reconcile submitted/retained/queried rows and expected role/copy counts, sum bytes with overflow checks, and mark any missing/unsupported/failed query or cap hit invalid. This preserves the current scheduling and arithmetic. The report parser should independently verify full `(request, chunk, layer, expert, role)` coverage and recompute byte totals and rates.

For host starvation, retain host call begin/end and measured stager/ring waits keyed by the same request-local sequence. Compare those with per-event queue gaps and `command_submit` values; host/device cause attribution should be cross-checked against PTI’s host-device trace, not inferred by subtracting the independent host and device clocks. Do not insert a host wait to make a timeline easier to read.

## Independent PTI/unitrace check

Intel PTI `unitrace` documents host API timing, per-kernel queue/submit/execution timing, per-device command timelines, and Chrome/Perfetto traces that include host-device interactions and dependencies. A short, isolated, already-authorized diagnostic can be wrapped with `unitrace --kernel-submission --device-timeline --chrome-kernel-logging --chrome-call-logging` (or a small `--start-paused` collection window if the harness can bracket only the diagnostic request). Retain engine/queue identifiers; use the narrowest relevant capture window and a documented event-buffer limit. This can show whether the long Down-labelled interval contains one long GEMM kernel, multiple kernels, queue holes, and `zeMemCopy`/other copy commands, while the source ledger supplies exact routed-expert IDs and byte counts.

PTI is not yet qualified on this exact B570 driver/runtime stack. First verify on the exact binary that the oneMKL dispatches and `queue::memcpy` operations are visible, timestamps are valid, and capture does not alter correctness/fault status. If filtering cannot preserve copy commands or host interactions, use a short bounded trace without filters and reduce it to a compact event table; do not keep a full timeline beyond its named question. The PTI trace is a diagnostic cross-check, not the source of truth for expert bytes.

## Decision rule

Use the merged event ledger and PTI cross-check to answer two separate questions: (1) are actual per-shape GEMM service spans themselves large, or is the phase label dominated by gaps before the next compute-queue marker; (2) do copy intervals overlap GEMMs, and do staging waits or late submissions leave the compute queue idle? Reordering/overlap work is supported only if dependency-aligned traces show avoidable host gaps or underlapped copy/compute while event-level GEMM/copy service remains adequate. A hardware/data-volume limit is supported only if service intervals account for the critical path under valid clock/coverage checks and the actual request’s shape/route distribution. The R212 phase total alone does not choose between these.
