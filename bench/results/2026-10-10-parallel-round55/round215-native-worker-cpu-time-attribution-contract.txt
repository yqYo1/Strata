# R215 — native worker CPU-time attribution insertion contract

Status: read-only source/report contract. No implementation, build, test, profiler, model, GPU, process query, Git command, service action or cleanup was performed for this report. The only new artifact is this report.

## Question and boundary

The next useful CPU attribution is a same-request measurement that separates native kernel service on each pool thread from wall time spent synchronizing, and joins those timings to the actual native format, token group size (NT), and number of expert jobs. It must work if PMU access is unavailable. It is not a kernel proposal or an adoption decision.

The source review used the pool-timing snapshot at `perf-sycl-decode-pool-phase-timing-v0141-2026-10-09`, commit `7d0105f2a942ac72ca20fef69d4c2e7960653de3`, and the caller-census snapshot at `perf-sycl-iq4nl-caller-census-20261010`, commit `0961c16d3c5b7f1191f4df139ea3e7b7a2c7859f`. The latest closed evidence is round54, registry v77, archived under `bench/results/2026-10-10-parallel-round54/`.

The pool0 request there had `--max-context 262144` capacity but consumed 32768 actual prefill positions; it is not a full-262144-position input. Its restored per-window host CPU phase spans were 145.04/145.81 ms, with GU 104.159/104.009 ms, activation quantization 0.363/0.330 ms and Down 40.493/41.448 ms. These are nested phase wall spans, not exclusive worker busy time. GU type 22 is dominant, but the aggregate Down span includes type 20 and other formats/NT groups; it cannot be described as “IQ4_NL time.” The host stream tests were approximately 37 GB/s RAM read, 37.6 GB/s non-temporal copy and 23.0 GB/s cached copy, all logical workload rates rather than memory-controller traffic. Round54 hardware records still show `perf_event_paranoid=4`; the prior R95 record found no effective CAP_PERFMON. Treat PMU/uncore access as unavailable until a new closed receipt proves otherwise.

## What the pinned code already measures

`src/kernels/cpu/pool.cpp` has host wall accumulators for `run()` at `run_split`/`run_split_multi_native` and existing GU, quantize and Down wall spans (`ms_multi_gu`, `ms_multi_q`, `ms_multi_down`). These span `run_phase`/the quant loop and include host barriers, scheduling and phase work. `run_phase` calls `wait_parked` before publication, `wait_done` after host draining, then `wait_parked` again; those barriers do not yet have separately accumulated durations. `drain` claims row tasks with one shared atomic head. Native mode 5 walks GU rows and applies SwiGLU; mode 6 walks Down rows. A claimed row task can cross expert boundaries, so the whole task does not have one NT value.

The caller-census snapshot already adds an opt-in native dispatch exposure histogram in `pool.hpp`/`pool.cpp`: `native_histogram_begin()` resets per-request cells; `native_histogram_add()` runs once per completed GU/Down phase and aggregates expert jobs, tokens, output rows, format, NT, eligible and selected dispatch; `native_histogram_report()` prints those cells after the request. `generate.cpp` brackets a decode request with begin at the `DecSnap ds0` boundary and report after `ver.wait_commit`, adjacent to `ds1`. It explicitly labels the histogram “exposure only, not time/traffic/worker imbalance.” Reuse those exact actual-job count cells. Do not add a second type/NT/expert counter or infer a worker's selected implementation from a histogram cell whose hybrid variant is unresolved (`-1`).

The separate SYCL prefill IQ4NL caller census in `bench/results/2026-10-10-iq4nl-caller-census-source-host-contract/` counts routed prefill Down calls and payload/output extents. It does not measure native CPU worker time and does not replace this pool instrumentation. The existing histogram above is a native-pool dispatch exposure helper in the caller-census snapshot.

## Clock interpretation and collection mechanics

On Linux, `clock_gettime(CLOCK_THREAD_CPUTIME_ID, ...)` measures CPU time consumed by the calling thread. It excludes time that the thread is descheduled or asleep, but includes time while it is scheduled and stalled on memory. It is not an instruction-retirement counter, memory-bandwidth counter, or physical DRAM traffic counter. Therefore pair it with `steady_clock` spans: CPU time estimates scheduled execution service, while wall duration includes descheduling and preemption. A memory-bound kernel can have high CPU time and still make little progress while stalled. On Windows use a documented thread CPU-time equivalent (`GetThreadTimes`) and the same wall clock; do not silently substitute process CPU time.

Allocate fixed-size per-worker storage before starting pool threads. Each worker writes only its own padded record; the host-drainer uses a separate record. No shared `fetch_add`, lock, vector growth, allocation, printing or cross-worker write occurs in `drain`. The host reads records only after `wait_done` and the final `wait_parked` acquire boundary; request reset/report occurs only after the preceding request has completed. Use the existing publish/wait handoff for immutable request enablement. Do not add branches that select work, change `claim`, reorder jobs, alter `done_`, split row ranges, or write clocks to the shared head. Diagnostic state is default-off and frozen at initialization; the off path must make no clock calls and preserve baseline arithmetic, claims and scheduling.

Per-call sampling has a cost, so first record call count and measure clock/helper overhead in a standalone host-only calibration. Compare diagnostic-disabled, counters-only and clocks-on diagnostic cohorts with otherwise identical inputs. Set a predeclared overhead ceiling; if clocks-on exceeds it or changes phase/request behavior materially, coarsen sampling or report that the requested attribution is too perturbative. Never present timed-diagnostic wall throughput as clean model speed.

## Required validation before any hardware attribution

1. Static review confirms clock calls are only in the explicit diagnostic path; arrays are bounded from pool worker count and have no hot-path allocation/locks/shared atomic increments. Test Linux clock failure/unsupported behavior and Windows thread-time implementation, with invalid timing records marked unavailable rather than zero.
2. A host pool test with known jobs across multiple types and NT=1..MAXT verifies exact exposure counts, rows, calls, worker/host ownership, phase wait classification and report reconciliation. Include empty phases, single-worker, host-drain-enabled and host-drain-disabled paths, task ranges crossing expert boundaries, all supported native dispatch branches and bounded overflow/error paths. Require no lost or duplicated jobs and exact output parity with instrumentation off/on.
3. A paired instrumented diagnostic run validates generated IDs/logprobs, all existing correctness gates, request count/window totals, `sum(worker+host phase jobs) == histogram jobs`, and `sum(worker kernel CPU) <= sum(active-drain CPU)` within clock resolution/defined boundaries. The equality checks must use actual format/NT cohorts; do not average away absent NT values. Compare timer-off model wall receipts separately for perturbation.
4. Cover actual NT1, NT2, NT3 and NT4 production cohorts where present; if a closed request has no cohort for an NT, report it absent, not calibrated. Keep GU types and Down formats separate; type 22 dominance does not establish IQ4NL dominance. Preserve the actual prefill-position count and context-capacity distinction.
5. Recheck PMU permissions only from a closed, recorded environment receipt. If unavailable, report worker CPU-time and wall attribution as the answerable evidence and leave instruction/cache/uncore-traffic causes unresolved. Do not derive physical traffic from packed-byte extent or the RAM stream probes.

## Limits and decision

This insertion contract can identify which worker/host thread spent CPU time in each native format/NT call, whether wall lag comes from scheduling, active drain or barriers, and which worker completed last. It cannot determine retired instructions, cache misses, memory-controller traffic, whether a memory stall is latency- or bandwidth-limited, or prove a CPU architectural ceiling without an accessible and valid PMU/uncore collection. It also does not establish that a kernel change, task-order change, or CPU/GPU overlap change would improve clean end-to-end throughput.

Round213's NT1 Down20 service calibration (80.5–84.6 microseconds/job in its actual-weight/synthetic-activation fixture) remains NT1-only component evidence. The round54 host/GPU test receipt and pool0 diagnostic remain bounded to their stated workloads; no full 262144-position model input, full native NT2–4 service qualification, physical RAM traffic, PMU result, or optimization/adoption decision follows from this report.
