# R226 — bounded read-only PLE storage-capacity probe contract

Date: 2026-10-10 (Asia/Tokyo). Read-only design audit of the frozen PLE reader and the existing CPU-only probes. This report proposes a bounded host-storage control matching the actual 90-byte row, 4 KiB direct-I/O page grouping, reader limits and counter semantics. No benchmark, test, build, model/inference, mount/device/process query, Git operation, cleanup or source edit was performed. The only write is this report. No SSD throughput or capacity result is claimed.

## Finding and frozen pins

The frozen direct reader is not an io_uring implementation. On POSIX, `DirectFile` opens the original GGUF with `O_RDONLY | O_DIRECT`, allocates 4 KiB-aligned buffers, and runs one blocking `pread` per worker thread. Its implementation defaults to 64 I/O threads (`STRATA_IO_THREADS` clamps to 1–64); the public header comment still says 16 on Linux and is stale for this pinned implementation. `PleReader` queues aligned jobs in a fixed slot slab, default `max_inflight=256` and two 4 KiB pages per slot (2 MiB), plus a default 1,048,576-row, 90-byte set-associative row cache (~90 MiB of row data plus keys/metadata). Thus 256 is the reader's maximum outstanding job slots, not an achieved disk queue depth: active blocking `pread`s cannot exceed its worker count. The existing stats do not report active/peak `pread` concurrency.

The default IQ4_NL table extent is 320,001,536 × 90 = 28,800,138,240 bytes (about 26.82 GiB). Direct mode uses the GGUF parser to validate the tensor file offset, then destroys that mapping before reopening the shard with O_DIRECT. A token requests 16 rows (1,440 logical bytes). A 32,768-position chunk asks for 524,288 rows / 47,185,920 logical bytes (45 MiB) before exact row-cache hits, page reuse and row straddles. The maximum one-page-per-row direct payload for that chunk is about 2 GiB; the real job count is data-dependent. A PLE row begins at a potentially unaligned 90-byte stride. `PleReader::issue` checks the row cache, groups misses by aligned first 4 KiB page, extends a job to 8 KiB if a row crosses a page boundary, deduplicates rows sharing the same job start page, and sorts each ticket's jobs by file offset before queueing. These are the shapes the storage controls must preserve.

## Minimal read-only controls

All controls must use the existing original PLE shard, open read-only, and stay within its validated tensor byte extent. The data file, extent hash, token fixture hash, table-data file offset/row count, `ROW_BYTES=90`, OS/filesystem, kernel, I/O engine, storage identity and driver/firmware must be pinned in the eventual receipt. These facts are not available in the closed PLE timing summary; do not fill them in by guess or by querying the current machine during this audit. Use the existing bounded process-owner pattern when a future run is separately authorized. The available `B/run_gdn_gate_factor_probe_v2.py` owner is hard-pinned to a different GDN workspace and workload, so it is not a ready-to-launch PLE runner.

1. **Sequential direct-read reference.** Use fio against the PLE shard with `rw=read`, `readonly=1`, `direct=1`, `ioengine=libaio`, `bs=1M`, `numjobs=1`, and `iodepth=1` as the base sequential rate; optionally repeat at `iodepth=16` only as a separately labeled asynchronous control. Set `offset` to the first 4 KiB boundary at or after the tensor file offset; set `size` to a 1 MiB multiple wholly inside the tensor extent (at most a small prefix/tail is omitted). This keeps the sequential arm within table data and satisfies direct-I/O offset/length alignment. Use a single finite pass over the table extent, not a write, trim, raw-device or whole-disk sweep. Fio's read-only option prevents accidental write/trim jobs. This is a best-case contiguous storage reference; its large requests do not resemble production's sparse page-batched work.
2. **Uniform random 4 KiB direct-I/O reference.** Against the same table-containing file extent, use `rw=randread`, `bs=4k`, `direct=1`, `ioengine=libaio`, and one job at requested depths 1, 16 and 64. Fix and report the random seed and selected extent; keep it a finite fixed number of reads or a bounded duration, and never let offsets escape the file. Record fio's achieved I/O-depth distribution and latency percentiles, not just the requested `iodepth`. This is a generic scattered-read reference, not a PLE prediction: it lacks 90-byte row collisions, 8 KiB straddlers, source-sorted per-ticket order and the application row cache. Fio documents that a synchronous engine ignores `iodepth > 1`, and that `libaio` may fail to reach requested depth unless direct I/O is used, so the achieved-depth output is an admission condition.
3. **Source-derived PLE page-batch replay.** Prefer the actual CPU-only `ple_read_probe` / `PleTable::gather_batch` path over a hand-written random offset loop. Generate the 16 row IDs per token from a pinned deterministic token fixture through the frozen `ngram_rows`; choose the already-qualified bounded prompt/chunk lengths. This probe uses the same reader and decoder, with no model or GPU. For a distinct lower-level capacity reference, emit one fio-compatible read-only I/O trace from the `PleReader::issue` jobs after cache misses, page grouping, 4/8 KiB length calculation and per-ticket sort; store the token fixture hash, trace hash, job count, 4/8 KiB counts and per-ticket boundaries. Validate every trace record is a read, 4 KiB aligned, and falls within the file. Replay with fio's `read_iolog` and `readonly=1`, preserving offsets and lengths, at target queue settings; verify achieved depth. Since fio's libaio engine is not the current pool of blocking `pread` workers, call that replay a device-side trace control and use the real reader below for the application result. If a full trace has no continuing replay consumer, discard it after the compact receipt records its hash and distributions; retain only with a named owner, budget and review point.
4. **Actual-reader thread/depth sweep.** Keep source rows, ticket/chunk boundaries, table and build constant. Compare `STRATA_IO_THREADS=1,16,64` at fixed `max_inflight=256`; then, at fixed 64 threads, compare slot caps 16, 64 and 256. Include the exact production default (64 threads, 256 slots) as its own row. The probe's existing CLI does not expose `max_inflight` or `cache_rows`; future usage should exercise the frozen `PleTable` API with explicit `PleIoOptions` or make a narrow diagnostic extension. Do not substitute `generate` inference for this CPU-only control. Because source stats lack a high-water counter, instrument or otherwise record actual outstanding blocking reads before claiming an achieved application queue depth. Report worker count, slot cap and measured active-read high-water separately.
5. **Row-cache isolation.** Run one separate process with `cache_rows=0` for the cold row-cache arm, and a second arm with the production 1,048,576-row cache. In the cached arm, run the same deterministic chunk twice within the same table/process and report first-pass and repeat `cache_hits`, `dedup_rows`, reads and bytes separately; reopening the table resets the row cache. Set `keepalive_ms=0` for this capacity probe. Production `generate` enables keepalive by default (100 ms, up to its window); those idle one-page reads are separately accounted as `keepalive_reads` and can contaminate block-device deltas if left on. Do not drop global OS caches. `O_DIRECT` is intended to bypass the page cache for the table reads, but does not flush the SSD controller or device cache.

The current `PleIoOptions` defaults are 256 slots, 1,048,576 cache rows and a separate I/O worker. The `ple_read_probe` currently selects only `direct|mmap`; its `PleIoOptions` default keepalive is off. `ple_full_context_probe` supplies a useful existing integrity pattern: build a direct-reference embedding and compare every output byte for a fixed row sequence against the tested direct or mmap arm. For the bounded probe, keep that reference to the exact rows/outputs under test; do not allocate or lock a second full table. Require identical output bytes, finite values, normal exit, stable fixture/output hashes, and unchanged file size/identity before and after. An mmap comparison validates row-offset/decode behavior but its cache residency is a different storage mode, not an SSD-rate arm.

## Counters, order and interpretation

Capture one sample per run, with a warm-up clearly marked and at least three measured repeats per control. Alternate or pseudorandomize control order (for example, sequential / PLE replay / random / random / PLE replay / sequential) to reveal drift without pretending repeated O_DIRECT reads are physically cold. Record CPU/model/OS/software/build metadata, wall time, bytes, request distributions, alignment, row-cache settings, thread/slot settings, power/thermal notes if already available, and all per-sample validity results. Do not include only medians: preserve individual finite samples. No cache-drop, filesystem tuning, power-state manipulation or writes are part of this design.

For the actual reader, preserve these separate quantities:

- requested logical row payload (`requests × row_bytes`; 90 B rows);
- `ReaderStats.reads` and `ReaderStats.bytes` (successfully submitted read jobs and completed bytes; each job is normally 4 KiB and can be 8 KiB for a straddling row);
- cache hits and `dedup_rows` (same-ticket rows sharing an already queued page job);
- reader issue/submit/wait time, per-read latency samples and P50/P99;
- fio bytes and achieved QD for the reference arms;
- before/after block-layer read sectors/bytes, merged-read count, read-complete count, and in-progress/active-time fields for every identified backing layer.

`PleTable::io_report()` prints rows, row-cache-hit percent, reads, MB from `ReaderStats.bytes`, read P50/P99, collect-blocked time, submit time, cache size/capacity, and keepalive count when present. It currently omits `dedup_rows` and achieved concurrency. `PleTable::bytes_read()` instead counts logical gathered row payload, not physical direct-read bytes. A future receipt should surface the full `ReaderStats` counters so that the page-work reconciliation is falsifiable.

For Linux block counters, take quiet before/after snapshots of the actual volume/device-mapper/partition and underlying block device(s) once their mapping is separately documented. Convert the kernel's sector counters to bytes using 512-byte sectors, detect resets/reattach, and retain device major/minor with each snapshot. Reads can merge in the block layer; system-wide counters can include unrelated I/O; these counters show traffic delivered through the observed block layer, not SSD NAND or necessarily data read from flash. A controller cache, virtualization layer, RAID, network filesystem, or other stacked device changes the meaning further. If device deltas do not reconcile with `ReaderStats.bytes` within the known merge/straddle/keepalive and background bounds, label them inconclusive. Do not subtract an estimated idle background rate.

Interpret outcomes narrowly: sequential rate is a contiguous best case; fio uniform-random 4 KiB is an unordered scatter reference; fio replay of the exact source-derived page job trace is a host-independent queue-depth control; only the actual `PleReader` pass includes its cache, job construction, submission and collect behavior. Compare reader `bytes` with block-layer bytes and actual foreground wait before discussing storage exposure. `read_us_sum` sums job issue-to-completion latencies and can exceed wall time under concurrency; PLE gather wall includes CPU hash, batch construction, decoding, submission/collection and overlap. Neither divided by logical payload yields SSD bandwidth. Even a close block-counter match is not proof of physical media transfer or a hardware capacity ceiling.

## Documentation consulted

The source-specific detail above comes from the frozen implementation rather than another engine's implementation. R221 already reviewed a B70 NVMe-reader implementer's staged/O_DIRECT path, which is not a matched control for this table or its storage. No other inference-engine implementation adds a more concrete control here. Primary documentation used for the proposed probe: [fio documentation](https://fio.readthedocs.io/en/master/fio_doc.html) (direct I/O, achieved depth and I/O replay); [Linux `open(2)` O_DIRECT documentation](https://man7.org/linux/man-pages/man2/open.2.html) (alignment rules vary by filesystem/kernel; `statx(2)` may expose them); [Linux `statx(2)`](https://man7.org/linux/man-pages/man2/statx.2.html) (`STATX_DIOALIGN`); [Linux block I/O statistics](https://cdn.kernel.org/doc/html/latest/admin-guide/iostats.html) (cumulative block-layer counters and merges); [Linux block-stat sector units](https://kernel.org/doc/html/v5.12/block/stat.html) (512-byte sectors); [io_uring interface documentation](https://www.man7.org/linux/man-pages/man7/io_uring.7.html). The last source describes an alternative asynchronous interface; the pinned reader currently uses thread-pool `pread`, so an io_uring benchmark would be a separate implementation comparison, not a substitute for the actual PLE path.
