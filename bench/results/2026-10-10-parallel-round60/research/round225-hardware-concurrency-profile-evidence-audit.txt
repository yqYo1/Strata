# R225: Hardware-concurrency PTI evidence audit

Date: 2026-10-10
Scope: read-only audit of the closed synthetic hardware-concurrency run and existing profile. No benchmark, build, test, profiler, process, hardware, or device query was run. No run status or source artifact was changed. The raw trace was not copied into this report.

## Result

The closed PTI trace supports the narrow statement that, in this one profiling-perturbed synthetic run, 144 8 MiB H2D copy commands and 3,168 GEMM commands were observed, and their device execution intervals did not overlap in the trace. The trace's two PTI lane labels both resolve to `L0 Compute Engine<0,0>`; this is a reported queue-group ordinal/index label, not a measurement of physical engine occupancy or exclusivity. The separate clean, non-profiled repetitions show a modest but variable Down wall-time benefit for concurrent host submission. These observations are compatible: the concurrent path can reduce host-side wait/submission time while the device commands still execute sequentially. That mechanism remains an inference, not a measured cause.

This is a synthetic independent-buffer control, not a production model run. It does not establish production routing, model speedup, engine saturation, or a causal role for the copy-offload flag.

## Independent trace and source reconciliation

An offline parser read the already-closed raw trace and compact table and checked the analyzer's joins. It found 3,330 `gpu_op` events, 16,516 `cpu_op` events, and 6,660 flow keys. Event IDs were unique. Each GPU event had one host/device flow pair for H2D and one for D2H; both device flow anchors coincide with the GPU command start in this trace. For H2D, the host flow anchor joins exactly one CPU API event by process, thread, and timestamp. The records therefore link the device operations to host append calls; they do not provide a complete high-level SYCL/oneMKL dependency graph or an independent measurement of queue waits.

The exact operation names contain:

- 144 `zeCommandListAppendMemoryCopy(H2D)[8388608]` device events, totaling 1,207,959,552 logical bytes;
- 3,168 `gemm_*` device events;
- 18 other setup/validation device events.

The archived source's loops account for those target counts: copies are six shapes × two passes × three copy-enabled modes × four copies; GEMMs are four small shapes × two passes × three modes × 128 and two large shapes × two passes × three modes × 8. The joined host records include 3,171 kernel append calls and 159 memory-copy append calls, consistent with the operation mix plus other setup/validation work. The exact target operation-name counts and source loop arithmetic independently agree.

The trace was collected with `--chrome-kernel-logging --chrome-call-logging -d` in a single profiling-qualification process. Its receipt reports complete/passed, normal exit code 0, empty session, no recorded errors, cleanup completed, and no survivors. No visible kernel fault or device coredump is recorded. The trace is explicitly marked `profiling_perturbation=true`; it is excluded from the clean timing summary and is not performance evidence.

## Overlap and timing precision

Recomputing intervals from the complete compact table gives zero copy/GEMM intersection over all probe phases. The union durations are 188,535,878 ns for the target copy intervals and 175,603,167 ns for GEMM intervals. The closest cross-role interval gap is 5,084 ns. Since this zero intersection includes warmup, solo, serialized, and concurrent phases, the concurrent subset also has zero observed overlap. This supports only “no overlap observed in this trace,” not a claim that overlap is impossible or that one engine was saturated.

PTI's `UniTimer::GetEpochTimeInUs` converts its nanosecond counter to integer microseconds plus the remainder multiplied by 0.001; JSON serialization prints six fractional digits. The resulting timestamp representation has a nominal 1 ns grid, but that is not a clock-calibration or accuracy bound. The 5.084 µs minimum observed gap is larger than a conservative 1 µs serialization guard, on this trace's shared timebase. Do not infer sub-nanosecond accuracy or a general clock-error bound.

## What the engine label establishes

Both PTI lanes are rendered as `Thread 1107780 L0 Compute Engine<0,0>` despite different thread IDs (`4259518335` and `4259518334`). The target copies and 3,167 GEMMs appear on the first lane; one GEMM appears on the second. PTI source forms this string from the Level Zero engine name plus group ordinal/index. Its collector classifies a group from its flags (checking COMPUTE before COPY), then uses the group ordinal and queue index. The Level Zero specification defines the ordinal as the queue-group-property position, the index as a queue within that group, and flags as supported capabilities. Thus the defensible reading is “same PTI-reported ordinal-0/index-0 queue-engine slot, labeled Compute.” The label alone does not show that copy support is absent: a group may support both capabilities, and PTI's classification order can label it Compute. The profile receipt does not retain the complete group-property flags or `numQueues` values.

Primary references: [Level Zero command-queue API](https://oneapi-src.github.io/level-zero-spec/level-zero/latest/core/api/apis/command_queue.html) and [Level Zero device API](https://oneapi-src.github.io/level-zero-spec/level-zero/latest/core/api/apis/device.html). PTI source excerpts are pinned to the commit above; the profile's `pti-source-meaning.json` carries the source-path and line mapping.

## Clean repetitions and compatibility with zero overlap

The three clean fresh processes have seven samples per cell. Down M80 median-of-process medians are 8.489 ms serial and 7.515 ms concurrent; the per-process serial/concurrent ratios are 1.130, 1.186, and 1.069. Down M160 medians are 8.781 ms serial and 8.223 ms concurrent; ratios are 1.118, 1.068, and 1.047. The gain is present in these three process summaries but varies across processes. Keep it as a small observed wall-time difference, not a stable universal speedup. GU changes are small.

The benchmark source explicitly waits for copy completion before GEMM submission in the serial path; the concurrent path submits copies and then GEMMs without an inter-queue wait. Sequential device execution and less host-side waiting/submission idle time can coexist, so the clean wall-time change does not contradict the zero-overlap profile. The trace did not measure the host-side causal gap well enough to prove that explanation. PTI logging also perturbs execution, which is why its timeline is not used to explain the clean timing magnitude.

The experiment uses independent host-USM-to-device-USM buffers and synthetic operations. It does not exercise the production ring, model routing, or the exact production shapes/dependencies; no production throughput or cause claim follows.

Separate the concurrent and serial probe batches, then align host append and explicit wait/synchronization calls with their device intervals. This requires no GPU run and can test whether the already-observed wall-time difference is compatible with reduced host wait/submission gaps. Preserve the recorded flags and do not repeat a synthetic benchmark or run an offload A/B for this question.

Keep the R223 serial build/small-event admission gate and do not broaden to a retry sweep. This would test whether the same queued operation pattern appears in production; it still would not by itself establish general speedup.
