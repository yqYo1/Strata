## Finding

The source defines a distinct, defensible inclusive host-wall measurement for the submitted helper batch. In `batch`, after plan checks and the progress announcement, `steady_clock::now()` brackets the loop of 64 wrapper calls, their per-call clock reads and receipt-hook event retention, followed by one normal `queue.wait_and_throw()`; the end timestamp is taken only after that call returns. The resulting `host_wall_ns` is the elapsed host monotonic interval from immediately before the first wrapper call through normal return from the planned queue drain. `host_submit_window_ns` ends just before the wait; `host_wait_ns` covers the wait call. The separately logged `host_submit_ns` values bracket each wrapper call only. These fields are not device timestamps, and no event profiling query or device clock is used.

The batch must also pass wrapper-return accounting, receipt accounting and tuple checks, event-object pairwise-distinct checks, sticky async-error checks, and post-completion numerical/input/guard readback before it logs `HOST_BATCH ... result=PASS`. A normal wait return establishes the completion boundary before potentially throwing validation/readback work. An exception during the wrapper loop or wait calls the fail-stop path and avoids unwinding potentially live allocations. If later checks fail after known completion, the sample is rejected. This is coherent source-level provenance and fault accounting for an instrumented helper-batch wall metric, conditional on a qualifying runtime record; it does not validate a host run or prove every failure mode is observable.

## Scope and interpretation

The metric includes wrapper dispatch and submission overhead, two host clock reads per helper, receipt-hook work, runtime/driver scheduling observed while submitting, the in-order queue drain, and host return latency. It excludes the pre-batch progress print/flush and plan validation, post-wait receipt/event validation, per-call logging/flush, D2H copies, numerical checks, and full-cohort readback. Each cell has one 64-call submission batch and one DQ wait, then a separate readback wait. The reportable interval is therefore neither per-kernel service nor end-to-end cell time. It is specifically inclusive host-observed batch latency under this instrumented exact-event-receipt path. The per-call `host_submit_ns` readings are nested inside that interval and must not be added to it.

The queue admission deliberately requires Level Zero, in-order, and profiling disabled, as well as the pinned B570 root device and PCI address. This avoids dependence on the known invalid device profiling sample and does not repair or supersede it. Exact events are retained from the existing helper hook for identity and metadata after queue completion; no `get_profiling_info`, event status/timestamp query, or timestamp subtraction appears in the fixture. Event retention itself adds overhead to the measured path. The metric therefore cannot be treated as the uninstrumented helper's latency without a separate same-protocol control, which this source does not provide.

The fixed measured design has four cells: generic/private helper crossed with same-address/rotation64 address regime. Each has 64 calls, `n=1,638,400`, two alternating output slots, and 64 distinct allocated input views. Eight blocks each run one of four Williams orders: 0132, 1203, 2310, 3021, then repeat the same four orders. Across those four orders, each cell occupies each within-block position once and each directed within-block predecessor pair occurs once; the second set repeats this. It is not randomization, and only four order variants are sampled. The cross-block predecessor is recorded continuously but the sequence is not balanced across arbitrary block transitions. Position/predecessor fields and block IDs permit inspection of observed sequence or drift patterns, but do not support broad claims about order independence or arbitrary order interactions.

Each cell follows two warm passes over all inputs and both helpers. After every batch, including each measured cell, the fixture reads both complete outputs and all 64 complete input allocations to host and waits; these copies are outside `host_wall_ns` but condition queue and memory history before the next cell. The same-address and rotation64 labels thus describe access addresses under this repeated readback cadence. They establish neither coldness nor cache residency, cache level, nor equivalent cache state. Identical packed input bytes mean this is not a data-content comparison.

For correctness, input packing and an independent scalar RNE oracle cover the full workload; prephase and final replay exercise both helpers across all 64 addresses, and readback checks the full output allocations and input immutability/guards. During a 64-call cell, only the last occupant of each of the two output slots survives; the batch checks those two complete output arrays, not a separate result for every timed call. The source labels this limitation, while the full replay supplies separate all-input coverage. Do not describe each individual timed call as independently numerically checked.

The optional CMake target is explicitly OFF by default and requires the private dequant, event receipt, parity and public `ze_loader` options. CLI rejects absent/invalid mode before queue construction; `--host-only` runs host checks without a queue. This supports isolation at source/configuration level, not proof that a particular binary was built from these pins or that its execution passed.

## Limits and conclusion

I found no source-level timer-boundary, completion-order, event-attribution, or lifetime defect that invalidates the named inclusive host-wall interval under a successful batch record. The timer uses one monotonic host clock at both endpoints; it needs no host/device epoch correlation. The exact wrapper return is retained by the existing receipt hook and then checked against the plan. Completed batches reset retained events before continuing; fail-stop covers ambiguous submit/wait completion. Validation after the wait keeps rejected batches from becoming passes.

Interpretation remains narrow: instrumented direct-helper component wall latency with this exact batch size, schedule, receipt overhead, warmup, queue, and full-cohort readback cadence. There is no arbitrary speed threshold implicit in this protocol. A useful result should retain per-batch wall/submit/wait fields, per-call submit durations, fixed block/order/position/predecessor metadata, and rejection accounting, and report distributions or paired cell contrasts rather than promote one favorable cell. It cannot support a pure device-service claim, an uninstrumented path estimate, a general cache claim, production expert-copy/ring-wrap behavior, full model prefill/decode speedup, or adoption. The user's model-level bar (at least 32,768 actual batched prompt positions, full physical 262,144-token lifecycle plus tail controls, and independent decode evidence) remains outside this fixture.

The new host-wall protocol is therefore a legitimate separate fallback measurement contract after the rejected device-profile result, provided the owner verifies the pinned build and qualification records and preserves that failed device-profile outcome as failed. This source audit itself does not establish compilation, qualification, runtime correctness, measurement values, speedup, or model-level benefit.
