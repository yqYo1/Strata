# R194 — UR Level Zero v2 submit/start profiling-clock contract

Date: 2026-10-10 (Asia/Tokyo). Read-only source and primary-document investigation following the clean component-service rejection. Scope is the reported oneAPI 2026.1 / UR 0.12.0 Level Zero v2 runtime and the independent legitimacy of host-wall timing. No source/build/test/device/process/GPU action was taken. The live fixture was not read. No attempt was made to infer or subtract a clock offset.

## Facts established by specifications and installed headers

SYCL 2020 revision 12 section 4.6.6.5 defines every event profiling value as a uint64 nanosecond timestamp on an implementation-defined timebase. Events on the same backend share a timebase, so their differences are meaningful. `command_submit` is the timestamp when the command group is submitted to its queue, and must occur after the command-group function returns but before that call to `queue::submit` returns. `command_start` is device action start and is required to be greater than or equal to `command_submit`; equality is expressly allowed. The spec says implementations should approximate action start but gives no accuracy guarantee. Thus two values queried on the exact returned event, from one backend, can be subtracted without host/device clock correlation; a negative start-minus-submit violates the SYCL ordering contract, independent of the timestamp's absolute epoch. (Khronos primary source: https://registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html#_event_profiling_information)

Installed oneAPI 2026.1 headers bind the SYCL descriptors directly to `UR_PROFILING_INFO_COMMAND_SUBMIT` and `_START` (`include/sycl/info/event_profiling_traits.def`). `ur_api.h` exposes `urEventGetProfilingInfo`; the event profiling API says profiling is unavailable when the associated queue was not created with profiling enabled. The installed header's experimental `urEnqueueTimestampRecordingExp` separately specifies its own semantics: QUEUED/SUBMIT mean time of the call to that API; START/END mean device-recorded time. Do not confuse that special timestamp-recording event contract with normal kernel event profiling.

The Level Zero core API describes `zeEventQueryKernelTimestamp` as returning global and context kernelStart/kernelEnd from the event's device clock; timerResolution and kernelTimestampValidBits are required to convert ticks and account for wrap. The programming guide states the kernel timestamp counter is finite-width, can wrap, and ordering should not be inferred across timestamps from coincidental raw values; wrapping must be handled using valid bits. It also warns `zeCommandListAppendWriteGlobalTimestamp` has a similar but distinct mechanism and the two kinds of timestamps must not be assumed equivalent. The newer Event Query Kernel Timestamps extension explicitly offers a synchronized host-domain timestamp result, marks synchronized support with a capability flag, and says querying it has performance cost. That is an explicit separate API route; it does not license offset-correcting normal SYCL profiling values. (Primary sources: https://oneapi-src.github.io/level-zero-spec/level-zero/1.0.4/core/PROG.html and https://oneapi-src.github.io/level-zero-spec/level-zero/1.14.33/core/EXT_EventQueryKernelTimestamps.html)

## Contract adjudication of the observed failure

The clean run's supplied sample is `submit=301019766336958`, `start=301019766335625`, `end=301019766364687`: start-submit = -1333 ns. If these are the normal SYCL profiling `command_submit` and `command_start` descriptors for the exact captured event and their adapter values faithfully describe those descriptors, this is invalid by SYCL's same-backend ordering guarantee. It does not call for guessing a clock offset: a constant epoch offset cancels in same-timebase subtraction. Plausible implementation mechanisms to investigate are descriptor misrouting (e.g. one value from pre-enqueue host/device-global query and the other from kernel event timestamp without valid correlation), bad timestamp unit/conversion/mask/wrap handling, stale/wrong event or metadata association, or an adapter/driver reporting a backend-order violation. These are hypotheses only; this report cannot distinguish them because exact installed v2 source and the actual fixture are unavailable here.

The event's `end > start` and successful receipts/completion do not cure the failed ordering check. Keep the sample/run failed and reject the entire timing batch under the already frozen rule. Do not silently swap fields, use absolute values, clamp a negative queue delay to zero, add tolerance, or calibrate/subtract an inferred offset. Root's R179 source gate remains pertinent: exact local submit return and static binding plus independent receipt metadata and validity accounting are necessary to rule out attribution errors; guard-event brackets alone are supplemental.

For a future diagnosis, request the frozen actual9c28 fixture/source and exact build/runtime receipt, then pin its adapter source to the shipped 0.12.0 revision (or obtain vendor confirmation) and trace both descriptor routes and their units/counter width. A clean rerun is not needed to conclude this sample is invalid; any future diagnostic run is a separate owner-controlled qualification.

## Host-wall metric

A separately labeled host-wall measurement is legitimate without correlating clocks if it uses one host monotonic clock for both endpoints and describes exactly the interval measured. For example, `steady_clock` immediately before the wrapper loop through return from the batch completion wait measures host-observed wall latency for that instrumented service batch, including submit overhead, waiting, runtime/driver scheduling, and any intervening host work in the bracket. A per-call host duration from before `queue.submit` through return measures host submit-call latency only. Neither is the pure device service time, and neither should be presented as event `end-start` or device queue delay. Keep boundaries, completion operation, work count, and instrumentation/logging state explicit; comparisons need the same protocol and condition. The C++ standard defines `steady_clock` time points as never decreasing and advancing at a steady rate relative to real time. The documented host metric remains usable even when profiling timestamps fail, provided its own clock reads and completion/receipt checks are intact; it is an independently named observation and cannot rehabilitate the rejected device-timing result or claim model-level speedup. (Primary source: https://eel.is/c++draft/time.clock.steady)

## Evidence classes and uncertainty

- **Fact:** installed headers connect the SYCL profiling names to UR descriptors; SYCL mandates same-backend same-timebase and SUBMIT <= START; L0 documents finite-width event counters and offers a distinct synchronized-timestamp extension.
- **Fact:** public current L0 v1 source uses different-looking routes for START and comments on a pre-enqueue global timestamp for SUBMIT; it is not the exact installed v2 source.
- **Fact from supplied closed-run record:** one sample violates the expected ordering by 1333 ns after successful return/receipt accounting; no timing cells accepted and no new GPU fault reported.
- **Inference:** if this is a descriptor-faithful exact-event sample, it is a backend/runtime/driver contract failure; likely areas are source/time conversion or event association, not an unknown cross-clock epoch offset.
- **Uncertainty:** without pinned v2 0.12.0 source, the exact timestamp origin/path and any relevant upstream fix cannot be identified. This report does not access the changing fixture or runtime binary internals.
