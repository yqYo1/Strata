# R224 — emitted IQ2_S GU code versus Zen 3 CPU capacity

Date: 2026-10-10 (Asia/Tokyo). Read-only audit of the frozen native CPU source and its already-built host calibration binary. Question: what does NT2–4 actually emit for IQ2_S gate/up on the 5600X-class AVX2 route, and what can that tell us about a CPU ceiling that packed RAM-stream capacity cannot? No executable was run; no build, test, profile, PMU, inference, GPU/device/process query, Git/service operation or cleanup was performed. The only write is this report.

## Finding

The source's reuse claim is real but bounded. For each 82-byte IQ2_S block, each 32-value half decodes grid values, signs and scales once, then shares those decoded weight vectors across NT activation dots. Each token still loads its own Q8_K activation vector, applies sign and byte-pair multiply/adds, updates integer accumulators, and contributes a separate FP accumulator. Thus NT grouping can amortize decode work while the arithmetic and a long per-token dependency chain remain. It does not reduce packed weight extent or turn the operation into a simple bandwidth-only kernel.

The closed AVX2/AVX/FMA binary provides an actionable register-pressure warning: its out-of-line NT4 `row_dot_any<22,4>` function stores three YMM vectors to the stack and feeds them back as memory operands to FP FMAs inside the block loop. The NT3 specialization uses only a 0x28-byte frame for scalar/pointer temporaries and shows no corresponding YMM accumulator stack traffic in its emitted function. This makes NT4 spill traffic a credible CPU cost in this exact compiler/build; it does not establish that spills dominate service, or give cycles/token. NT2 is inlined into the large runtime dispatch function, so its wrapper frame is not a clean measure of spills in its inner loop.

The current build has AVX-VNNI disabled (`STRATA_AVXVNNI=0`) and uses 256-bit AVX2, FMA and F16C. On default dispatch, source gates the gather path to Intel AVX-VNNI-capable CPUs, so Zen 3's default is the plain AVX2 decode. `STRATA_IQ256_GATHER=1` can override that; this binary contains gathered code too, but the closed build record does not contain an executed runtime setting. Accordingly, this is an audit of the available specialization and its default source route, not a record of a particular calibration run's selected variant.

- The `iq256_gu_rows_v` NT dispatcher subtracts one from the NT value and indexes a jump table. Its NT2 case begins at `0x448039`, NT3 at `0x4475d8`, and NT4 at `0x447b2d`. The NT3 and NT4 cases call the named plain specializations at `0x499910` and `0x499fd0`; NT2's loop is inlined in the dispatcher.
- NT3 helper disassembly (`0x499910–0x499fd0`) allocates 0x28 bytes and uses it for addresses, bounds and result pointers. In the inspected helper range, no YMM vector is loaded from or stored to that frame.
- NT4 helper disassembly (`0x499fd0–0x49a780`) allocates 0xa8 bytes. At `0x49a090`, `0x49a096`, and `0x49a09c`, it stores `%ymm5`, `%ymm4`, and `%ymm3` to stack offsets `0x40`, `0x60`, and `0x80`; the block-loop FMAs at `0x49a315`, `0x49a330`, and `0x49a34b` use those stack slots as memory operands. The second loop body repeats this pattern at `0x49a400–0x49a694`. This is direct evidence of vector accumulator spills/reloads in this specialization, not an estimate inferred from frame size.
- Integer dot sequence in the NT3 helper includes `vpsignb`, `vpmaddubsw`, `vpmaddwd` and vector integer accumulation (`vpaddd`); float block accumulation uses `vfmadd*ps`. IQ2_S decode also has byte/bit extraction and shuffles (`vpsrl*`, `vpshufb`, masks/ORs), while the plain grid/sign lookup path uses scalar table loads and assembles vectors. The source's separate gather specialization emits `vpgatherdq`/`vpgatherdd`, but that is not the default Zen 3 route.

These instructions show the *kind* of CPU work and the NT4 register-pressure issue. I did not count dynamic instructions or claim an exact cycle cost. Static code presence alone does not tell whether execution is limited by instruction throughput, dependent-load latency, cache misses, or memory bandwidth. NT3's absence of the same obvious spills does not prove it is faster than NT4 at any service shape.

## What RAM capacity does and does not answer

R220 records the production GU geometry: H=2560, 640 gate plus 640 up rows, ten 82-byte IQ2_S blocks per row, and 1,049,600 logical packed-weight bytes per expert GU job. A selected 8-expert hot set is about 15 MiB, intentionally below the Ryzen 5 5600X's nominal 32 MiB L3; R220's 192-ID streaming cohort exceeds 64 MiB for GU. These are logical extents and intended residency geometries. They do not measure cache residency, DRAM bytes, or a CPU service roof.

The source decodes 80 IQ2_S halves per output row (10 blocks × 8 halves). At NT2–4, each decoded half still feeds two to four distinct activation vectors and integer dot chains. NT4's emitted spills add stack traffic to those chains. A RAM-stream bound that divides logical packed bytes by a nominal RAM rate therefore cannot predict CPU-side decode, sign/multiply-add, accumulator dependency, or spill costs. Conversely, a hot-cache result bounds the DRAM contribution but still combines all of those CPU operations and the cache hierarchy; it is not an isolated instruction ceiling.

AMD's Family 19h optimization guide is the primary Zen 3 resource for instruction behavior and optimization rules. LLVM's `znver3` scheduling-model change is useful as a second, implementer-maintained resource model. They can guide static analysis or `llvm-mca` hypotheses, but neither is a measured Strata kernel result; model predictions must not be relabeled as the kernel's achieved throughput. Sources: [AMD Software Optimization Guide for AMD EPYC 7003 / Family 19h](https://docs.amd.com/v/u/en-US/56665), [LLVM AMD Zen 3 scheduler model](https://reviews.llvm.org/D94395).

## Smallest discriminating next comparison

Keep the host-only calibration's correctness gate and exact same selected GU22 blobs, inputs, affinity and compiler build. Measure separate direct-call NT2, NT3 and NT4 service on (a) the already-described eight-expert intended-L3-fit set and (b) the existing >64 MiB cohort, with warmup followed by the established 25 rounds per cohort. Preserve individual rounds and report per expert job and per token-group; do not divide full job service by NT and call that per-token timing. Add NT1 only as the fallback/control path, clearly labeled as GGML rather than grouped AVX2.

Record the actual per-thread gather variant, NT dispatch, worker CPU placement, clocks/temperature if available from the already-authorized diagnostics, CPU thread time and wall time. Do not force gather selection for the comparison; separately label any explicit gather override as a distinct implementation. No current PMU is needed for this first discriminator. A larger NT4 penalty in both hot and streaming cells is consistent with CPU work/register pressure; a streaming-only penalty suggests a cache/memory-system contribution; a pool-only change points toward worker scheduling or tail effects. Those patterns remain diagnostic, not proof of a specific execution bottleneck. The exact disassembly predicts that NT4 spill traffic deserves measurement priority, but cannot establish that NT4 service is slower than NT2/3 before measurement.

If the direct hot-cell result still cannot separate decode dependency from execution throughput, the smallest next analytic step is to isolate the emitted NT2–4 inner-loop machine code and feed it, with the pinned compiler and a representative fixed trip count, through an AMD Zen 3 scheduling model (for example LLVM `llvm-mca -mcpu=znver3`). Treat that as a lower-bound/resource-pressure model only: it will not model real IQ lookup cache latency, thread contention, or actual memory-system behavior. A measured, pinned-CPU single-core direct-call cell remains the service evidence.
