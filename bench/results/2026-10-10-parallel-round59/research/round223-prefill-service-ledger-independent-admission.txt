## Finding

The normal SYCL path is narrowly instrumented and source-bounded. It preserves the original `Gemm::f16` declaration/body and adds an opt-in `f16_event` entry point which forwards the same half/half/float oneMKL GEMM arguments and returns the oneMKL event. The compute ledger admits the actual `m.cs` queue by profiling property and device aspect, checks GEMM descriptor queue identity, and rejects unsupported multi-GPU mode. The copy queue is the existing in-order queue; its profiling property is requested only when either transfer or service timing environment variable is present. Environment presence enables the corresponding instrumentation even for value `0`; both absent leaves the main service/copy lanes off and does not change the original GEMM call or submit additional device commands.

I found one conditional fail-closed gap: if a diagnostic run reaches a compute queue without profiling enabled, `services.admit(cs)` marks the service ledger invalid, but `expert_product` still calls `Gemm::f16_event` for each selected native expert GEMM. `record()` then marks/drops the records, while the later `fold()` still queries all three profiling timestamps for every retained event even when `valid` is already false. A runtime that cannot provide those timestamps can reach `fatal("profiling_query_failure")` and `_Exit`, instead of rejecting diagnostic admission before workload submission and preserving the original non-event GEMMs. This is conditional; the supplied base/runtime evidence says the default production compute queue is profiling-enabled, so it is not evidence of failure on that exact queue. It should be resolved or explicitly qualified before reusing this opt-in path with another queue configuration. The copy lane has the analogous record/fold behavior if copy queue profiling admission fails, although this implementation requests copy-queue profiling whenever the diagnostic is enabled.

The issuer join/read boundary is safe in this source. The issuer is started at `prefill.cpp:3494`; each chunk joins it at lines 5212–5217 before `transfers.fold_copy(false)` at line 5322. Thus the apparent concern that the main thread reads the copy ledger while the issuer mutates it is not a source defect. `fold_copy(false)` polls already-completed events after the existing compute wait and does not wait the copy queue. Final required copy folding follows the existing copy-queue wait. Activation and device-residual events are produced/folded on the compute thread after its existing synchronization.

The ledgers fail closed on dropped/capped records, mismatched expected GU/Down identity or row count, missing/duplicate roles, timestamp errors/reversal, incomplete/unknown events, queue change, async delivery failure, arithmetic overflow, and reconciliation failure. Cap overflow invalidates the lane, discards further records while keeping the latest returned event for a completion check, and suppresses aggregates. Failure paths use `_Exit` rather than unwinding model storage while completion is unknown. One routine diagnostic bound is conservative but useful: a chunk with 48 layers and at most 512 active experts/layer yields at most 49,152 expert GEMM events and 24,576 expected pairs; caps are 65,536 events/pairs. A single run with no intermediate callback therefore stays below those per-chunk limits. Records are reserved only after admission and only for enabled lanes. The expected-pair map is bounded by 65,536; shapes and chunk/layer/role coverage each cap at 16,384 entries.

The 256K-position coverage does not automatically fit the coverage bucket. `coverage` is cumulative across chunk folds; folds retire pending events but preserve aggregate maps. At a 512-token chunk size and 48 layers, expert GEMM coverage can reach 512 × 48 × 2 = 49,152 chunk/layer/role buckets. The 16,384 cap will invalidate that run’s service ledger and suppress its aggregates (after retaining at most 16,384 coverage entries); it will not claim partial telemetry as complete or grow unbounded. At 4,096-token chunks the corresponding maximum is 64 × 48 × 2 = 6,144 buckets, below this cap. These are source-derived ceilings, not claims about the configured production chunk size or actual routing. Event capacity applies to one outstanding fold interval; the request-wide bucket cap is what limits the cumulative 256K case.

The output is similarly bounded by the number of buckets, with at most four per-lane query/reversal diagnostics and one receipt per lane. A valid run can print up to 16,384 shape plus 16,384 coverage entries per lane; an overflow-invalid run prints no aggregates. This prevents request length from creating an unbounded event timeline, but a worst-case valid report can still be large. The output has no source-side byte cap; the root’s diagnostic runner should retain its existing output budget and treat truncation/nonzero exit as invalid, not as complete coverage.

## Routed geometry and event meaning

Expected GEMM pairs are registered from each layer’s actual local `order` vector, using the actual routed `m.cnt[expert]` row count and chunk position `p0`. The event path records one GU and one Down per expert with roles, N/K/ldy, and the same rows. Existing oneMKL fallback math is preserved: column-major `trans/nontrans`, `m=N`, `n=T=ne`, `k=K`, alpha 1, beta 0, FP16 inputs and FP32 output. MMQ/fused paths and unsupported multi-GPU modes are rejected from qualified coverage rather than silently combined. The digest (`expert_id_sum`/`xor`) is not a full expert identity trace; retained coverage aggregates include chunk/layer/role, shape/rows/calls, and source/ring where relevant. Per-call identities are not emitted as a full timeline.

The reports correctly limit interpretation to a returned routine/copy event. A oneMKL returned event establishes completion, not that `command_start..command_end` covers all internal kernels. The ledger therefore does not qualify a full GEMM service interval, physical copy traffic, exclusive kernel busy, or actual overlap; R216’s exact-B570 PTI check and actual request route/shape coverage remain required before such claims. The source also deliberately avoids using cross-event submit/end gaps as idle time.

## Evidence and qualification limits

The committed handoff records eight changed source-file hashes and says the original CPU contract v1 failed because its fixture invalidated the expected identity before submitted identity; that failed receipt is retained. Root corrected only the fixture, added an independent expected-identity negative case, raised the per-event cap from 32,768 to 65,536, and added bounded event reservation. The committed v2 receipt is reported as 26 passing actual-header host cases, including 49,152 events and 24,576 pairs. Those are committed receipt claims, not tests rerun in this audit. No SYCL build/recompile, small-device returned-event check, model route histogram, internal oneMKL coverage, async hardware fault qualification, or 262,144-position run has yet been established by this source-only handoff. Consequently the ledger remains implementation-ready but unqualified for runtime results or performance interpretation.

The immediate admission correction is to prevent event-aware submission when profiling admission fails (fall back to the original `f16` once and mark coverage unsupported, or reject the diagnostic before model work), and avoid querying profiling timestamps for an already-invalid/unadmitted lane while still completing/draining submitted work safely. Then run the root-owned serial SYCL compile and small event qualification before any model trace. Keep the 256K coverage-cap invalidation explicit in any full-input result; either qualify with the actual bucket count or choose a justified cap from actual route/chunk counts before admitting coverage.
