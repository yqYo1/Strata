## What the source says about the compared memory lifetimes

For fixed type 20 and `n = 2560 * 640 = 1,638,400` values, the existing generic and private wrappers submit one asynchronous kernel to the supplied queue with the same `n/256 = 6,400` groups and local size 32. The generic wrapper selects `dequant_flat_kernel<sycl::half>` at runtime; the private wrapper calls `dq_iq4_nl<sycl::half>`. Both write 3,276,800 bytes (3.125 MiB) of FP16 output. Their current APIs return `void`; the existing call's exact event is not currently retained. Use R177's compile-guarded receipt only if and when its separate root-owned implementation and qualification are complete. Do not substitute queue-tail events or duplicate either kernel body.

The direct prefill caller keeps two output workspaces (`dq_d[DQ]`, `DQ=2`) and chooses `q = j % DQ`, so output storage is reused every other expert. In the streamed path, expert blobs are copied into `stage_dev[issued % m.ring]` on `m.copy`; if a live ring slot is reused, the copy queue waits on the compute queue's recorded `m.used` event. The consumer uses the same ring-addressed blob and inserts a compute-queue barrier on the matching `m.copied` event before reading the bytes. In the non-streamed path, `blob_dev` can instead name a resident expert allocation. Thus a compressed source address may repeat after a ring wrap while each intervening expert can use different weight bytes; the DQ output address repeats on a two-slot cadence. Exact ring size/mode depends on the run and must be recorded from runtime receipts. A direct-helper microbenchmark has no expert-copy queue, ring wrap, staging schedule, routed-row count, or DQ/GEMM overlap. Its address-reuse result cannot be called a prefill-cache result.

The pinned source layout allocates `n_embd * n_ff` FP16 DQ-down elements and the direct call uses the above shape for the model geometry identified in R176. The source baseline also selects native IQ-to-FP16 plus oneMKL down GEMM; current MMQ/fused stubs are false in the pinned source context. This remains only a direct helper component, not model evidence.

## Cache facts and why “cold” is not a valid label

Intel's public B570 product material identifies 18 Xe-cores and 380 GB/s graphics memory bandwidth; Intel's B570 product specifications identify 10 GB GDDR6. They do not publish a B570 cache-capacity number in these sources. Intel's 2025.2 oneAPI optimization guide lists 18 MB L3 and 256 KB/core L1 for its B580 example, and explicitly says the table gives one specific model per microarchitecture and that models/SKUs can differ. It is not evidence for a B570 cache size. Do not infer that a 32- or 64-buffer working set is larger than B570 L2/L3, and do not use an undocumented cache capacity to call a cohort “cold.” Intel also says these cache controllers cannot be queried through SYCL device info in that guide.

Use labels `same-address reuse`, `32-address rotation`, and `64-address rotation`. Rotating 32 or 64 preallocated, distinct, valid packed-input addresses reduces repeated use of the same address and makes the tested input working set about 28.125 or 56.25 MiB respectively (32/64 × 921,600 bytes, using MiB). Adding the two 3.125 MiB output slots gives 34.375 or 62.5 MiB. This is below the stated 96 MiB component budget, but says nothing about cache residency, cache-set conflicts, compression, allocator placement, or the effective cache available to this process. If 64 buffers cannot be allocated and admitted within the predeclared budget, record the resource limit and do not relabel a smaller cohort as 64.

Use byte-identical copies at distinct, aligned GPU addresses for the cohort so input values and work are held constant while address reuse changes. Avoid filling or flushing a guessed “cache-size” buffer: that would add another workload and still would not prove a B570 eviction. This experiment asks whether repeated access to one address differs from cycling a bounded set of addresses under this harness. It does not identify a particular cache level or prove DRAM traffic.

## Smallest pre-registered plan

Use one process, one exact in-order profiling queue, one submitting host thread, and the same binary/options for all arms. The four cells are a small 2 × 2 comparison:

- generic wrapper, same input address;
- private wrapper, same input address;
- generic wrapper, 64-address rotation;
- private wrapper, 64-address rotation.

Before timing, allocate all 64 packed input views, initialize each to the same valid IQ4NL bytes, allocate exactly two FP16 output slots, and allocate canary margins. Record addresses, byte sizes, alignment, hashes, allocation kind and queue identity. Verify that the views are distinct and do not overlap. Keep all input/output allocations alive through the last queue completion and all output reads. No allocation, host/device copy, output readback, logging, event timestamp query, or wait occurs inside a timed submission window. The 32-address series can be a predeclared secondary sensitivity check if needed; do not choose 32 versus 64 after inspecting the timing winner.

First run the existing independent-oracle qualification for each of the 64 input views through both wrappers, with both output slots exercised. Require exact expected-output comparison, input immutability, output canaries, one planned call/one receipt for each successful submit, and the full R179 metadata and event-identity checks. This is a correctness prephase and its time is discarded. It also populates both input cohorts and both kernel paths before service measurement. Warm both wrappers and all cohort addresses with a fixed, recorded number of extra untimed calls, then drain once. The warm-up is a stated harness condition, not proof that every cache level is resident. Record the count and report any first-use/JIT behavior separately; do not mix it into steady-state samples.

For each measured batch, submit 64 calls with no interleaved work: in the same-address cell use one input address 64 times; in the rotating cell use the 64 addresses once each, permuting their order between batches so no address is repeatedly chosen as the first cohort member. Alternate the two output slots on every call, matching the production workspace cadence. Save the expected input index, output-slot index, arm, sample ID and serial per call in preallocated metadata. Retain only the actual wrapper-returned event. Do not query profiling timestamps in the loop and do not wait per call. At the end of each 64-call batch, perform exactly one planned queue completion wait/drain, then query every expected event and reject the entire batch on any submit/receipt mismatch, loss, duplicate, queue/metadata mismatch, timestamp error, or missing sample. A same-queue drain is required before timestamp reads. Record raw submit/start/end timestamps and timer resolution; allow a quantized zero service duration as specified by R179.

Pair the four cells into a block and pre-register balanced order. Across eight blocks, rotate all four starting positions and include each cell both early and late; use a fixed seed and preserve the generated order before running. For example, use these four cell orders, then repeat them once: [G-same, P-same, G-rot64, P-rot64], [P-same, G-rot64, P-rot64, G-same], [G-rot64, P-rot64, G-same, P-same], [P-rot64, G-same, P-same, G-rot64]. This balances cell position and prevents a fixed first arm from collecting all the earliest device state. It does not make state identical across cells. For each service contrast, report paired block differences, order-stratified results, a paired bootstrap confidence interval, and difference versus block index. Preserve all valid samples; report zeroes and any excluded batch with its pre-registered reason rather than filtering inconvenient observations.

The 64 calls within a cell share one queue batch so timer collection and drain are amortized and each batch has one known completion boundary. Event retention remains bounded at 64. Do not change to per-call waits if launches are too small to resolve; if timestamps are mostly quantized to zero or paired differences are inconclusive, report the component as unresolved at this timer resolution and stop or pre-register a larger batch/repeat count in a later run.

Keep device event service (end-start), queue delay (start-submit), host wrapper-submit elapsed time, per-batch host wall time, and completion/drain time as separate quantities. Only service is the kernel service observation. Do not subtract host and device clocks. A run with event instrumentation must also report its instrumentation mode. If an uninstrumented harness comparison is later done, that is a distinct result and must use the same input rotation, warmup, batch order, and workload.

## What order balancing does and does not control

Alternating and rotating cell order controls a simple monotonic drift or “first arm wins” effect better than running all generic samples and then all private samples. Prewarming both kernels and all inputs removes the most obvious one-time first-touch difference. It does not guarantee equal data-cache state at the start of each timed call: the A address is revisited 64 times, while B sees different addresses. That is the intended address-reuse contrast. Nor does it guarantee equal instruction-cache state: generic dispatch and fixed IQ4NL code can have different compiled instruction footprints, and prior cells may evict or warm different instruction lines. A balanced order averages these first/last and immediate-predecessor effects; report per-order results so a large predecessor effect is visible. Do not claim it eliminates instruction-cache effects or prove equal cache state.

Do not insert dummy kernel traffic to “equalize” instruction caches. Do not query undocumented B570 cache counters, flush with arbitrary memory traffic, pin clocks, or force sleeps. The practical inference is bounded: a stable generic/private difference within each input regime supports a component service difference under those two address-reuse conditions. A difference that changes with regime reveals sensitivity to input address reuse for this component harness, but still cannot identify L2 versus L3/DRAM or reproduce prefill streaming.

## Correctness and safe failure boundaries

R179 remains the admission gate. Before the first device submission, validate the independently expected call plan and preallocate receipts/metadata to full capacity. Receipt hook must be non-throwing and bounded. A dropped or failed receipt invalidates the batch without unwinding accepted work. Do not count wrapper attempts as successful submits, and do not count a final surviving output as proof for every timed call.

The prephase validates every input/cohort with both kernels against the independent oracle, source immutability, and output canaries. During timing, check successful submission count against the immutable plan; receipt serial/arm/queue/type/n/pointer tuple against every planned call; sticky overflow/drop state; event timestamps; and input bytes/hashes plus canaries after known completion. Because two output slots are overwritten repeatedly, only the last occupants in those slots remain available for a post-batch or final output comparison. Such a comparison validates those occupants only. It does not validate each earlier timed invocation. If full output correctness for every input is needed after measurement, perform an untimed replay of every cell/cohort input with the oracle and clearly label it as post-timing replay; do not attribute that replay to the timed samples. Never modify the timing loop to read or synchronize every output.

Separate three error cases. (1) Pre-submit validation/admission failure: no kernel was accepted; reject and release unsubmitted resources. (2) Accepted work followed by known successful queue completion, then an async handler or profiling-query error: mark the batch invalid, keep records until the completion boundary is established, release retained events and allocations safely, and report the error. A query exception after successful completion is not an unknown-live-work condition. (3) Completion cannot be established, including a wait/drain failure with uncertain outstanding work: do not unwind device allocations or event-backed state that queued work may still reference; use the established owner fail-stop path and preserve the diagnostic. A mere receipt loss is not itself proof that completion failed: still reach the planned drain. No retry may convert an accepted-but-unmeasured batch into a pass.

## Limits and next evidence

This is a protocol for exact generic/private helper service under a direct, valid-buffer workload. It cannot prove model-level wall improvement, warm or cold cache capacity, DRAM bandwidth, GPU cache hit rate, ring-reuse effects, first-token latency, MMQ/fused eligibility, or the overlapped fraction. Any production claim still requires the exact caller and per-call receipts, actual routing counts, and a real model comparison of at least 32,768 actual batched prompt positions as R176/R179 specify. Full physical 262,144-token lifecycle and repeated independent decode remain later separate evidence. No minimum useful gain, altered precision/tolerance, retry, or adoption rule is introduced here.
