## What the returned event promises, and what it does not

The public oneMKL DPC++ reference documents the ordinary USM GEMM return as an “Output event to wait on to ensure computation is complete.” The corresponding grouped pointer-array `gemm_batch` documentation states the same completion guarantee. The current browsed Intel reference is version 2026.0; its signatures and return-value wording are the documented contract for that revision. The [2026.0 `gemm` reference](https://www.intel.com/content/www/us/en/docs/onemkl/developer-reference-dpcpp/2026-0/gemm.html) and [2026.0 `gemm_batch` reference](https://www.intel.com/content/www/us/en/docs/onemkl/developer-reference-dpcpp/2026-0/gemm-batch.html) both distinguish USM/pointer event-returning overloads from buffer overloads returning `void`.

That completion guarantee is sufficient to use the event as a dependency/lifetime fence: after successful wait/completion, the GEMM output is ready and inputs/outputs may be retired according to ordinary SYCL lifetime rules. It does not state that `command_start`/`command_end` on that event enclose every device command or kernel used internally by the library. The oneMKL public API does not specify a kernel decomposition or profiling-window mapping.

SYCL profiling descriptors describe the action associated with the event's command group. `command_start` is when that associated action started on device; `command_end` is when that associated action finished. A queue must have `property::queue::enable_profiling`, and queries may block for that action to run/complete. Timestamps share a timebase among events on the same backend. See the [Khronos SYCL event reference](https://github.khronos.org/SYCL_Reference/iface/event.html) and the [SYCL 2020 specification](https://registry.khronos.org/SYCL/specs/sycl-2020/pdf/sycl-2020.pdf). Consequently, if a library implements GEMM as multiple device commands and returns an event on a final kernel or terminal dependency/barrier, the return event can correctly certify the whole operation while its `command_start`–`command_end` interval measures only that associated final action. This is a permitted possibility implied by the distinction between completion-fence semantics and command profiling semantics; it is not evidence that the installed oneMKL build actually does this for these shapes.

Three separate claims must be kept separate:

1. **Completion:** the documented oneMKL returned event can be waited on to ensure the operation computation is complete.
2. **Profiling availability:** querying the returned event is possible only when the event's queue was created with profiling enabled; the actual target device/backend must support queue profiling (`sycl::aspect::queue_profiling`), the event must carry available profiling data, and query errors must be handled. Neither the source queue construction nor the task-provided platform version proves that this specific B570 driver/runtime supports event profiling. Check `has_property<enable_profiling>()`, `device.has(queue_profiling)`, timer resolution, and real query success on the owning queue in the root-owned diagnostic.
3. **Whole-operation service window:** neither oneMKL's completion wording nor SYCL's per-associated-action profiling wording promises that `event.command_end - event.command_start` is the sum or wall span of every kernel/copy/command internal to GEMM. Current public closed-source implementation details do not settle whether the installed build returns an event whose profiled action spans all work. Treat that relationship as unknown until measured/traced on the exact installed build and target.

The task context identifies the intended stack as oneAPI/oneMKL 2026.1 on Arc B570, but this read-only source bundle contains no installed binary/package manifest or live device/backend query that independently pins that runtime, driver, event profiling capability, or B570 support. Intel's oneMKL product page lists Arc graphics generically, which establishes product-family support, not this exact API/event-profile combination on B570. The browsed public Developer Reference currently available for this audit is 2026.0, one minor release behind the supplied installed-version description. Do not silently treat the two as identical; first confirm exact 2026.1 documentation/release behavior in the root-owned qualification context. The [Intel oneMKL product specification](https://www.intel.com/content/www/us/en/developer/tools/oneapi/onemkl.html) lists Arc graphics generically; the [oneMath support table](https://github.com/uxlfoundation/oneMath#support-and-requirements) distinguishes Intel GPU plus Intel oneMKL backend and Intel DPC++ compiler from other GPU backends, but neither public source names B570 profiling qualification.

## Smallest safe timing discriminator

Before using GEMM event elapsed times to rank grouped GEMM, TLA, or fused epilogues, run one root-owned, opt-in, isolated diagnostic on the exact Arc B570 + driver + compiler/runtime + oneMKL build and actual queue/shape. Keep the normal async route and error/lifetime path; do not add per-expert waits or mix host-clock values with device timestamps.

1. Retain the exact GEMM return event in a diagnostic-only path, check the profiling queue/device gates, wait/drain once at the existing safe batch boundary, and query its timestamps. Keep the event alive until profiling queries finish. No event wait is inserted between experts.
2. In the same run, collect a short actual device command/kernel trace for that same queue and call, or bracket the call with a pre-event and a post-marker on that same profiling queue, with the post-marker explicitly dependent on the GEMM completion event. Compare the GEMM event's profile interval against the same-backend device trace or marker interval. A marker span is an envelope that includes queue gaps/marker cost; it is not pure GEMM service. A trace can reveal whether the GEMM event is a tail action and what earlier commands it depends on.
3. Keep host submit-to-drain latency in a separate host-clock column if operational latency matters; never subtract it from or combine it numerically with SYCL device timestamps. Preserve successful/failed result status and existing asynchronous error propagation. Release buffers and temporary state only after the completion chain is known complete; on unknown-completion errors, retain the existing safe failure behavior.
4. Record operation identity, shapes/group count, event ID/provenance if the tool provides it, queue/device/backend, profiling timer resolution, each kernel/command's same-domain start/end, event timestamps, trace/marker envelope, errors, and version/driver metadata. If a profiler is unavailable, the profile query fails, or the trace cannot correlate the event and commands, report the event span as **not established to cover whole GEMM service**; do not use it as the prioritization metric.

This discriminator is a contract check, not a performance win gate. After its result, later optimization ranking should use repeatable same-backend actual-device service samples and the already-required actual-model route histogram and model qualification. This audit does not repeat R178 resource-shape feasibility or claim any speedup.
