## Existing path and concrete data layout

`prefill.cpp` allocates selected-attention scratch from the requested batch and chooses a prompt tensor path when `qsa_prompt_attn_batch` accepts the geometry. Otherwise it uses the decode-attention kernel in batches; `STRATA_PREFILL_ATTN_LAYOUT` selects variants 1–4, while `STRATA_PROMPT_ATTN_OLD` forces the old fallback. Static source inspection cannot establish which path a particular full-model B570 run actually takes.

The fallback has `HD=256`, `G=12` query heads per KV head, 64 selected cells per CTA (`CHUNK=64`), and one `(query, KV-head, 64-cell chunk)` CTA. With the model's selected-width bound of 2,051 from the earlier QSA audit, this is up to 33 chunks per query/KV head followed by `attn_merge_kernel`. Variant 1 is `(SG=32, TRANSPOSE_Q=true, QUERY_FAST=false)`; variant 4 is `(SG=16, TRANSPOSE_Q=true, QUERY_FAST=true)`. The dispatch supports FP16 KV (`KV_MODE=0`), INT8 codes with FP16 group scales (`KV_MODE=1`), and Q4/hybrid variants. The active representation must be confirmed from the run's pool pointers and receipt.

For `KV_MODE=1`, `load8_q8` loads eight adjacent signed-byte codes and one FP16 scale at `row * (HD / KV_Q8_GROUP) + d0 / KV_Q8_GROUP`, converts that half to float, and multiplies each code. In the V pass, each dimension lane independently loads the same half scale for its dimension group before multiplying its own code. For 256 dimensions, there are four 64-dimension scale groups per row. In the V pass, each 16- or 32-lane subgroup covers dimensions within one scale group; in the K path, eight adjacent lanes each handle eight dimensions covered by one scale. That makes subgroup scale broadcast a plausible instruction-count reduction. Hardware may already coalesce or cache the redundant reads, so the source pattern alone does not establish a memory-bandwidth bottleneck.

The current code requires the SYCL fp16 aspect. The proposed scale path is only eligible for the existing INT8-code/FP16-scale mode and the layouts where the corresponding dimensions are aligned to the subgroup grouping. It does not apply to FP16 KV mode 0, Q4 modes, or a different shape. No B570 subgroup-16/32 execution, joint-matrix behavior, cache capacity, residency, or speed is established by this static audit.

## Candidate: subgroup reuse of identical Q8 KV scales

**Implementation sketch.** Add an experimental mode-1 branch that has one lane in each same-scale lane group load and half-convert the scale, then uses `sycl::group_broadcast` (or an equivalent supported subgroup shuffle) to distribute that already-converted float. Start with V only: for each selected cell, every subgroup handling one aligned 64-dimension group uses the same scale, while their int8 code loads remain distinct. A later K variant would broadcast within each eight-lane group of eight dimensions in `load8_q8`. Keep the exact half-bit input and the same half-to-float conversion and code-times-scale operation; no scale reconstruction, changed quantization, changed reduction, or altered softmax is part of this candidate.

Intel SYCL*TLA's Xe rearchitecture notes explicitly identify broadcasting scales/zero-points as a subgroup-layout operation and describe subgroup reorder/broadcast patterns as a way to remove redundant data movement. This is a transferable primitive, not evidence that this Strata kernel is bandwidth-bound or that B570 gains. [Intel SYCL*TLA Xe rearchitecture](https://github.com/intel/sycl-tla/blob/main/media/docs/cpp/xe_rearchitecture.md) (primary implementation documentation; current `main`, inspected 2026-10-10; the report does not pin a Git object for this public page).

This is smaller and more constrained than importing full SYCL*TLA FlashAttention. SYCL*TLA documents FP16/BF16 dense FMHA examples and hardware-specific Xe atoms, whereas this kernel consumes per-query selected cell IDs, FP32 queries, mixed KV formats, and head dimension 256. Direct replacement would need sparse gathers and new shape/format support and has no established exact Strata mapping. The current source already has an opt-in prompt tensor path and a 64-cell split/merge path; the new candidate here is specifically scale reuse within its existing Q8 path, not a new attention algorithm.

**Why the external evidence argues for measurement first.** A llama.cpp author reported on an Arc Pro B70 that its SYCL Flash Attention prefill path declined from 595 to 227 tokens/s as KV depth rose from 8K to 32K; at 16K it was roughly half the no-FA result, while decode was largely unaffected. This is Qwen3.5, a different runtime, B70 rather than B570, and an FP16 KV path, so it is not a Strata prediction. It is strong evidence against assuming that a generic Xe2 FlashAttention port automatically fixes long-context prefill. [llama.cpp issue #21862](https://github.com/ggml-org/llama.cpp/issues/21862) (author report; build `75f3bc9`, oneAPI 2025.3, B70, posted 2026-04-13).

Intel LLM Scaler issue #738 reports FP8 KV prefill penalties growing from about 2% at 8K to 19% at 96K on two B70s, with a hypothesis that repeated FP8-to-FP16 conversion per attention tile is expensive. That implementation stores FP8 and runs XMX without FP8 math; Strata's Q8 path uses signed integer codes and per-64-dimension half scales. The issue therefore does not justify caching expanded KV here. Its useful lesson is to distinguish representation-conversion work from scale/code loads and measure the actual critical path. [Intel LLM Scaler issue #738](https://github.com/intel/llm-scaler/issues/738) (Qwen3.8-27B-FP8, `0.26.0-b2`, 2× B70; author results, posted 2026-09-30).

## Other screened transfers and disposition

- SYCL*TLA FlashAttention (Intel, current project) uses Xe-specific matrix/copy atoms for dense FP16/BF16 query-key-value tiles. Strata's active QSA selection creates distinct sparse IDs per query, FP32 Q, 256-wide heads and a mix of Q8/Q4/half KV. Porting the dense kernel would require a gather/layout bridge and no exact matching call path was identified. Treat it as a future implementation reference only if actual phase evidence warrants a new kernel.
- SGLang's Intel XPU documentation establishes an Intel-optimized attention backend and page sizes 32/64/128, but does not demonstrate the Strata QSA selected-ID interface or the current 256-wide mixed-format layout. It is not evidence of direct runtime or kernel eligibility. [SGLang XPU backend documentation](https://github.com/sgl-project/sglang/blob/main/docs/docs/hardware-platforms/xpu.mdx) (primary project docs; current `main`, inspected 2026-10-10).
- The recent llama.cpp SYCL QSA sparse-attention patch is single-token decode only. It compacts selected rows then re-enters dense attention, notes finite-count slack beyond its nominal top-k, and warns that unordered atomic compaction changes floating-point sum order. It does not cover prefill, and is not a candidate for bypassing Strata's existing selected attention or exact ordering. [llama.cpp discussion #28695](https://github.com/ggml-org/llama.cpp/discussions/28695) (author patch notes, base `22397c31`, 2026-09-10).
- KV quantization, attention sparsification/eviction beyond the model's own IDs, QSA tile-union, arbitrary query/selection overlap, and expanded-KV conversion caches are excluded here: they either change representation/participants or repeat already-registered candidates.

## Disposition

One source-grounded, exact-math candidate survives the novelty screen: explicitly reuse the same half scale across subgroup lanes in the existing INT8 KV attention path. Its possible benefit is reduced redundant scale-load instructions, not established bulk bandwidth reduction. Require root's actual mode/path receipt and exact outputs before timing; full-context lifecycle correctness remains independent and mandatory. No candidate is proven eligible or beneficial on B570, and no result in this report changes the current full-context, runtime, or adoption status.
