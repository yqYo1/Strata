# R183 — fused GU/SwiGLU epilogue eligibility and FP16 contract

Read-only source and public implementation/documentation review, 2026-10-10. No source edit, Git operation, compiler/build/test, model/runtime call, device query, profiler, cleanup, service/reset, or access to the active implementation worktree was used. This report makes no runtime or performance claim.

## Finding

The arithmetic and lane dependency are feasible: Strata's GU output is already physically interleaved, and IntelLabs' Xe-Fuse provides a public Xe20/SYCL-TLA pairwise epilogue visitor that exchanges adjacent N lanes and computes SwiGLU while the GEMM accumulator is in the epilogue. The common paired-column layout problem is therefore already solved by Strata's current output ordering. A one-off custom SYCL*TLA epilogue can represent the intended operation without changing the FP16 input/weight types or FP32 activation calculation.

There is no ready-made, qualified drop-in for this route. Xe-Fuse's current SwiGLU example intentionally writes the same result to both lanes at full N width; its source says N-to-N/2 compaction is future work. Strata needs one result per adjacent pair, stored in a half-width FP16 row, with its exact saturating round-to-nearest conversion and `native::exp` behavior. That needs a custom epilogue/store extension and exact shape/stride/backend qualification. Xe-Fuse is explicitly marked active development/not production-ready. SYCL*TLA publicly lists Arc B580/Xe2, not B570; family membership is not evidence that the actual B570/compiler/driver combination is supported.

Separate the architectural answer from qualification: there is no cross-tile arithmetic dependency if the current even/odd output pairing is preserved, but arithmetic equivalence to oneMKL's rounded FP32 GU, the selected Xe layout's pair mapping and stores, B570 support, and any service-time change remain unqualified. Do not adopt from these source examples alone.

## Source/API eligibility and exact blocker

Intel's [SYCL*TLA repository](https://github.com/intel/sycl-tla) describes a CuTe/CUTLASS-style SYCL GEMM framework with FP16 and epilogue support, and lists its tested hardware as Data Center GPU Max, Arc B580/Xe2, and Crescent Island/Xe3p in the [hardware compatibility table](https://github.com/intel/sycl-tla#hardware-support). The current table does not list B570. This makes it a plausible custom-kernel substrate, not proof of B570 qualification. The general TLA epilogue model permits custom device-side operations on GEMM results; the published [efficient GEMM/epilogue guide](https://github.com/intel/sycl-tla/blob/main/media/docs/cpp/efficient_gemm.md#epilogue) describes per-thread register results plus inter-thread exchange for coalesced stores and custom operations.

IntelLabs' [Xe-Fuse README](https://github.com/IntelLabs/Xe-Fuse/blob/main/README.md) lists composable SwiGLU visitors, FP32 accumulator/compute template parameters, and MoE expert GEMM epilogues. Its exact [pairwise visitor source](https://github.com/IntelLabs/Xe-Fuse/blob/main/include/xe-fuse/visitors/xe_pairwise_compute.hpp) documents the Xe DPAS CLayout as `(16, M)` with each subgroup lane owning one N column, and uses `shuffle_xor(..., 1, 16)` to exchange `(2k,2k+1)` partners. Its `SwiGLUFn` uses float values and `gate / (1 + sycl::exp(-gate)) * up`. This is concrete source evidence for a feasible adjacent-pair mechanism on the described Xe20 mapping, not generic permission to assume an arbitrary SYCL*TLA tile or epilogue has that mapping. A Strata specialization would have to select and verify the actual Xe20 epilogue layout and ensure pair boundaries never cross an unsupported lane/subtile boundary.

The ready kernel in [Xe-Fuse's GEMM+RMSNorm+SwiGLU source](https://github.com/IntelLabs/Xe-Fuse/blob/main/include/xe-fuse/kernels/gemm_rmsnorm_swiglu.hpp) defaults A/B/D to BF16, uses FP32 accumulation/compute, assumes both operands RowMajor, and constructs output at full `N`. Its header says both even and odd lanes write duplicate SwiGLU values for Phase 1, with N-to-N/2 contraction reserved for Phase 2. Therefore neither the default dtype/layout nor output addressing matches Strata as a drop-in. Although TLA advertises FP16 support and the Xe-Fuse template parameterizes ElementA/B/D, that establishes type expressibility only: the route still needs W's exact transpose/stride, X stride, compact half-width output, and custom saturating final conversion. The shown visitor uses `sycl::exp`, while Strata uses `sycl::native::exp`; preserve Strata's operation on the first bit-contract gate rather than accepting the example's math change. The Xe-Fuse README labels its project active development and not intended for production use.

A relevant implementer write-up, FAL's [“Crafting Efficient Kernels with Epilogue Fusion”](https://blog.fal.ai/crafting-efficient-kernels-with-epilogue-fusion/), explains why ordinary half-concatenated gate/up columns require cross-fragment/tile communication, then solves it by permuting packed weights so each gate/up pair is N-adjacent. Strata already expects and consumes interleaved pairs (`2*k`, `2*k+1`), so its layout meets that prerequisite without the FAL packing change. The post is CUDA/CUTLASS-specific and does not qualify an Intel implementation; its transferable evidence is the pair-local layout requirement, not a portable kernel or performance result.

Other-engine cross-checks support the existence of the building blocks while showing why names in a kernel list are insufficient. [vLLM-XPU's current kernel list](https://github.com/vllm-project/vllm-xpu-kernels#supported-kernels) exposes SiLU-and-mul/SwiGLU activation and grouped GEMM as separate operation categories; that documents separate ops, not a fused FP16 epilogue with Strata's mapping or saturation. [SGLang's XPU kernel library](https://github.com/sgl-project/sgl-kernel-xpu) documents a `USE_MOE` group-GEMM build option; its existence does not establish this specific FP16 interleaved SwiGLU epilogue. Xe-Fuse is the specific Intel-side source found here for a paired SwiGLU GEMM epilogue, and its contraction/type/qualification gaps above remain.

## Minimal qualification gate

1. **Activation/cast gate, before GEMM fusion.** Feed the same already-rounded FP32 GU rows to the existing interleaved kernel and a standalone candidate pair visitor/store for the measured M. Match every Hh element bit-for-bit against the existing `native::exp`, exact pair order, saturation, NaN, signed/overflow behavior and RTE half conversion. Include values around the saturation and half-rounding boundaries. This isolates pair mapping and FP16 output semantics; no guessed `ne` is needed for this component, and its result does not prove GEMM fusion.
2. **Exact-shape fused GEMM gate.** Only after the real model route histogram includes a measured noncompact `ne`, compare the baseline oneMKL GU+SwiGLU with a candidate FP16 X/W, FP32 accumulator/compute GEMM whose epilogue computes the same formula and stores compact FP16 Hh. Use exact `M=ne,N=1280,K=2560`, actual W/X strides, output row stride 640, and the current noncompact path. Keep the same physical W layout. Compare FP32 GU where candidate diagnostic output permits and compare final Hh using the project's already-established numerical criteria fixed before the run; no relaxed dtype/tolerance. The candidate's FP32 accumulation does not by itself prove identical rounded GU to oneMKL: a different implementation/reduction can change FP32 results, so any difference must pass the existing criteria. Reject on pair/stride/cast mismatch, unsupported B570/compiler/driver, numerical failure, or no repeatable device-service improvement. Keep device-event timing separate from host submission. Do not insert per-expert waits or retry after accepted work.
3. **Model relevance gate.** There is no arbitrary representative M. First obtain an actual per-expert `ne` histogram from at least 32768 actual batched positions. Only then assess a model run and require repeated-decode independence. Later adoption still needs the existing full physical 262144-token lifecycle gate. No model speed claim follows from either component gate.

No SIMD width or tile shape is recommended: the useful pair-exchange evidence above is tied to the cited XeFuse visitor's specified Xe DPAS CLayout. The exact TLA build/layout, B570 support, compact-store extension and numerical contract must be demonstrated in the root-owned qualification work before any engineering decision.
