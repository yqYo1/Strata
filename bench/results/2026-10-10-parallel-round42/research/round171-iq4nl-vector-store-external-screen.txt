# R171 — external implementation screen for IQ4_NL to FP16 dequant

## Disposition

No new evidence-backed optimization is admitted beyond the fixed-format dispatch experiment. Current production code already has the most obvious safe store optimization: each work-item builds eight half values and stores them as one 16-byte `sycl::vec<half,8>` at an offset aligned to that run. The IQ4_NL direct helper reuses the same `dq_iq4_nl` arithmetic and `store_run`; it changes dispatch only. The remaining obvious external match is a packed codebook lookup in llama.cpp's OpenCL IQ4_NL GEMV, but that code is fused into a different GEMV algorithm and does not establish a benefit for this SYCL dequant-to-oneMKL path. Its packed-half table is larger than Strata's current signed-byte codebook, and its dot-product multiplication order is not a bit-preserving replacement for the standalone dequant output. I found no primary-source Intel SYCL/oneDNN example that demonstrates a new exact, lower-cost IQ4_NL full-matrix dequant or the same native-down GEMM layout on Arc B570.

This is a no-candidate screen, not a claim that the current path is optimal. R163's exact-bit fixture and the root's separate direct-dispatch comparison remain the gates for that existing experiment; neither is external evidence for this screen.

## Fixed local mapping and current build

In the active kernel source, `dq_iq4_nl` maps each 32-value block to four work-items: `il = tid % 4` selects one 8-value run; `ib = tid / 4` selects one of the eight IQ4_NL blocks in the flat 256-value group. `il < 2` uses low nibbles; `il >= 2` uses high nibbles; `d` is converted from the stored half to float and multiplied by the integer codebook value before the output half conversion. `store_run<half,8>` converts all eight values to half and writes one vector store. The direct helper calls this same function; it does not change codebook values, nibble order, scale, arithmetic order, or output layout (`sycl/src/kernels/cuda/iq_kernels.dp.cpp:2378-2391, 2490-2507, 4295-4315`). Thus an external table/layout idea would need to beat already vectorized stores and preserve exact FP16 bits across the unchanged `d * codebook[nibble]` then half-round sequence.

The source configuration matters for comparisons. `sycl/src/prefill/moe_fused_stub.cpp` returns false from `fused::built()`, `available()`, and `enabled()`, and `sycl/src/prefill/prefill.cpp` supplies `mmq::built()==false` when `STRATA_PREFILL_MMQ` is not compiled in. `sycl/CMakeLists.txt` resolves only `gemm.cu`, `kernels.cu`, and `prefill.cpp` for `strata_prefill`, then links `moe_fused_stub.cpp`; it does not add the migrated `moe_mmq.dp.cpp` there. So the currently selected build's ordinary production route is the native IQ packed blob → FP16 dequant → oneMKL FP16/FP32-output GEMM, not CUDA MMQ or the fused INT8 path. That is the correct local route for this screen; the mere presence of MMQ/XMX code elsewhere is not evidence of execution.

The flat type-20 Down geometry remains R163's corrected `2560 output rows × 640 input columns`: 1,638,400 values, 6,400 flat groups, 51,200 18-byte IQ4_NL blocks, and 3,276,800 FP16 output bytes. The downstream `Gemm::f16` passes the FP16 Down matrix to `dpct::blas::gemm` with transposed weights, FP16 inputs, FP32 output/compute (`sycl/src/prefill/gemm.dp.cpp:750-783`). Changing the dequant output to a different packed/row arrangement would alter oneMKL's input layout and would need an explicit performance case; none of the reviewed external sources demonstrated this native Strata shape or driver path.

## External implementation findings

- **llama.cpp OpenCL IQ4_NL GEMV, primary implementation.** Its [`gemv_noshuffle_iq4_nl_f32.cl`](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-opencl/kernels/gemv_noshuffle_iq4_nl_f32.cl) stores the 16 codebook entries as eight `uint32_t` words, each containing two FP16 values, and defines `IQ4_NL_DEQUANT` using indexed word load, shift and `as_half`. The same file performs subgroup broadcasts and accumulates dequantized weights multiplied by activations. This is a credible implementation precedent for packing a small LUT in a fused IQ4_NL dot-product kernel. It is not a demonstrated optimization for Strata's current format: the OpenCL kernel's FP16 pair table uses 32 bytes, while Strata's table is 16 signed bytes; its kernel fuses scale, codebook, activation and accumulation, so its arithmetic does not isolate Strata's FP16 dequant; and its subgroup/layout target differs. A packed table candidate could preserve code values if every codebook entry's half representation is converted exactly back to float and the multiplication order remains `d * code`, but no evidence shows this wins against a compiler's constant lowering of Strata's smaller table. Admitting it without that evidence would be speculative.
- **llama.cpp SYCL conversion implementation, primary implementation.** [`ggml-sycl/convert.cpp`](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-sycl/convert.cpp) dispatches an IQ4_NL dequant entry and uses SYCL work-group launches for dequant conversion; its generic converter processes paired values per work-item in a 32-item group. It provides no observed B570 timing or operation-count evidence for Strata's 8-half run. The local kernel already coalesces those eight outputs into a vector store, so copying a different thread mapping from the general converter is not an established improvement.
- **Intel/IPEX-LLM and oneDNN screen.** The inspected route ends in oneMKL GEMM after an explicit dequant. I found no directly applicable primary source showing that oneDNN/oneMKL can consume GGML IQ4_NL's block layout/codebook as a native down GEMM operand on this single-device SYCL path. Standard INT4/NF4 GEMM implementations use different scales, codebooks, or fused arithmetic and cannot establish bitwise equivalence or better B570 performance here. No alternate matrix reorder/layout candidate is supported by the reviewed source set.

## What remains unproven and minimum gate

No source-level review can show the emitted SLM/constant-table access, vector-store instruction, register cost, or occupancy on this compiler/device. No external result supplies the missing B570 timings. If the packed-LUT idea is reconsidered, first establish at codegen level that the current signed-byte lookup is a material cost and that packed lookup actually reduces instructions or memory operations without increasing spills. Then compare synthetic all-nibble/all-lane cases with the independent scalar oracle and compare every `uint16_t` FP16 output against the generic type-20 path for actual Down matrices. Build the candidate under the private opt-in only. Measure cold first call separately from warmed calls, dequant event time, the two oneMKL GEMMs/MoE phase, and total prefill on the same >=32K request and the same chunk/cache schedule. Keep byte readback outside the timing run. Reject on any exact-bit mismatch, output/layout issue, material code-size/register regression, or no repeatable end-to-end prefill gain.

For the already proposed fixed-type dispatch, continue to require R163's exact output gate and root's actual production call receipt. A branch count proves selection, not savings. No gain, cost attribution, or adoption is concluded here.
