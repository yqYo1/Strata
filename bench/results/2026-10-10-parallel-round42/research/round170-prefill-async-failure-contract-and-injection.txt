## Current source chain and what the empty `check()` means

`sycl/src/kernels/cuda/iq_kernels.dp.cpp` has a no-op `check()`. Therefore its check after `iq_dequant_f16_prefill_iq4nl` does not report a queued error at the call site. This is not the same as an application with no asynchronous error reporting: `dpct::device_ext::create_queue(true)` attaches the existing `dpct::exception_handler`, which calls `strata::rethrow_sycl_errors`. That handler prints the batch and rethrows the first exception. Production `Prefill::run_impl` has existing `m.cs->wait()` synchronization before chunk callbacks and at the tail; object `release()` later calls `wait_and_throw()` on its compute/copy queues, and device/server shutdown also calls `queues_wait_and_throw()`.

The practical gap is **delayed and poorly owned reporting**. `queue::wait()` blocks for queued completion and reports synchronous errors, but does not dispatch unconsumed async errors to the configured handler. Thus a run can pass its `wait()` and hand results to a callback while the async exception is still unreported. Later `release()` or shutdown can invoke the handler. `Prefill::~Prefill()` calls `release()` with no local catch. If `wait_and_throw()` reaches a throwing handler there, the exception escapes the destructor; under C++ non-throwing destructor/function rules this calls `std::terminate` (and throwing during stack unwinding also terminates). The inherited empty kernel `check()` does not disprove eventual reporting; it makes clear that the owning queue/run boundary must perform it in time.

`strata::rethrow_sycl_errors` throws from the handler after logging. SYCL specifies that an async error passed to a handler is consumed and will not be sent again at a later handler invocation. Therefore, after a host boundary has caught a delivered async exception, a later release wait should not rediscover that same error. This supports a clean teardown after a caught, completed async error, but says nothing about a separate error on another queue, a wait/device-loss error, or an error not yet delivered.

## Established SYCL and Level Zero contract

- SYCL `queue::wait()` and `queue::wait_and_throw()` both perform a blocking wait for all previously submitted commands to complete; both can report synchronous errors. `wait_and_throw()` additionally passes unconsumed asynchronous errors to the queue/context async handler. `throw_asynchronous()` dispatches those errors without a blocking wait. References: [Khronos SYCL queue reference](https://github.khronos.org/SYCL_Reference/iface/queue.html), [SYCL 2020 spec queue operations](https://registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html).
- Asynchronous error instances are considered consumed once passed to an async handler and are not reported on subsequent handler invocations. The handler is invoked by `wait_and_throw`, `throw_asynchronous`, event `wait_and_throw`, or destruction when unconsumed errors remain. A default handler can terminate the process. References: [Khronos async-handler reference](https://github.khronos.org/SYCL_Reference/iface/async_handler.html), [SYCL 2020 spec error handling](https://registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html).
- An uncaught exception thrown from a `host_task` becomes an asynchronous error; `host_task` is run by the runtime on the host regardless of the queue's associated device. It follows dependency ordering, and the event completes once its callable returns (including exceptional completion being reported as async error). That provides a practical, non-GPU-fault injection source. Reference: [Khronos SYCL host-task reference](https://github.khronos.org/SYCL_Reference/iface/host-task-basic.html), with an async-handler example that throws from host_task in the [SYCL async-handler reference](https://github.khronos.org/SYCL_Reference/iface/async_handler.html).
- Level Zero `zeCommandQueueSynchronize(..., UINT64_MAX)` waits until completion or device loss and can return `ZE_RESULT_ERROR_DEVICE_LOST` or `ZE_RESULT_ERROR_DEVICE_REQUIRES_RESET` (among other errors). Level Zero requires the application to ensure a queue is no longer executing before destroying it. References: [Level Zero command-queue synchronization](https://oneapi-src.github.io/level-zero-spec/level-zero/latest/core/api/apis/command_queue.html), [Level Zero queue programming/destruction rules](https://oneapi-src.github.io/level-zero-spec/level-zero/latest/core/PROG.html).

A normally returning SYCL queue wait is a completion receipt for the commands it covers; that receipt does not mean each command succeeded. For the recommended asynchronous host-task injection, the host task itself ran and the earlier queue work was covered by the queue wait before error delivery. By contrast, an API/driver failure such as device-lost/reset-required or a timeout means there is no successful completion receipt from this path. Treat submitted buffers/queues as potentially active until a separate successful completion signal is obtained; do not infer safe reuse/free from the fact that an exception was caught. Level Zero explicitly distinguishes successful completion from device-lost and not-ready results. A wait that returns an exception is not, by itself, an application-level license to free if the root cause means the backend did not positively establish completion.

## Smallest opt-in production boundary

Use the existing host synchronization; do not add a wait after every expert and do not retry the generic dequant after the private submission. Track whether the private IQ4_NL path was selected/submitted during this `run_impl` call. At every existing compute-queue wait that immediately gates externally consumable output (the chunk callback/handoff boundary) and at the existing tail when no earlier callback boundary covers it:

1. Keep the existing blocking `m.cs->wait()` so completion is established at the same point and with the same scheduling boundary as before.
2. Only when the opt-in private path was exercised, immediately call `m.cs->throw_asynchronous()` to dispatch any queued async error to the existing rethrowing handler. Catch it locally, preserve a concise `err`, return `false`, and skip the callback/handoff. Catch/translate synchronous errors from the existing wait at that same boundary as a run failure too; do not allow the old broad `run_impl` catch to call `std::exit(1)` for this candidate failure.
3. Because the throwing handler consumes the async error when invoked, a subsequent release wait will not redeliver that same exception. Keep the existing teardown wait for queue completion and other queues, but do not suppress unrelated teardown errors. Confirm this behavior with the injection case below before treating the destructor path as safe.

This reuses the one already-existing blocking wait. `throw_asynchronous()` is a nonblocking dispatch after the wait has established completion, which separates the completion receipt from error delivery and avoids an extra per-expert synchronization. It also ensures the current queue's error is known before output is handed to a callback. If API compatibility prevented `throw_asynchronous()`, `wait_and_throw()` at the same existing boundary is a viable alternative under its blocking-wait contract, but the completion/error distinction is less explicit to the owner when a driver wait itself fails. Do not implement both paths as duplicate waits.

This candidate gate only covers the queue and run boundary it drains. It does not automatically account for independently failing copy/KV/successor queues, exception paths that bypass the boundary, or a backend wait that cannot establish completion. Preserve failure attribution, no-retry behavior, and all existing queue ownership/lifetime requirements.

## Practical injection design

Use a one-shot opt-in test mode disabled by default, for example an explicit command-line diagnostic mode or a dedicated test environment setting. Once, after the first successful private IQ4_NL submission on the same in-order `m.cs` queue, enqueue a valid SYCL `host_task` whose callable sets a persistent atomic marker and then throws a known `sycl::exception`. Do not submit malformed GPU work, corrupt a kernel, manufacture an invalid pointer, or provoke a device reset. The host task is an ordinary legal SYCL command; its intentional exception travels through the queue's actual async-handler delivery route.

At the existing run boundary, the ordinary `wait()` must return after the host task and all prior queue work are complete; then `throw_asynchronous()` must invoke `dpct::exception_handler`/`strata::rethrow_sycl_errors`, whose thrown exception is caught by the local opt-in run gate. The gate records failed run status, returns false before `on_chunk`/stage handoff, and never invokes generic fallback. The marker, exception count, gate result, callback count, private submission count, generic retry count, and completion state should appear in a bounded receipt. Teardown should then explicitly drain/release the same queue and object; the already-consumed injected error must not reappear from the same handler during `release()`/destruction. A zero exit from the fault test is only correct if its harness expects the request to fail and confirms the run returned failure without callback delivery, then confirms teardown succeeded and no async error remained. The normal request path remains default-off and does not enqueue host_task work.

A small harness can exercise the exact factored run-boundary helper without a model by submitting a tiny **valid** command before the host task on a queue constructed with the same async handler. For the full ownership gate, later run the one-shot mode through a model-backed prefill request, because only that covers the actual `Prefill::run` callback/handoff and `release()`/destructor chain. Keep both gates separate: the harness validates SYCL callback and boundary code; the production request validates routing and object teardown.

### What this injection proves and cannot prove

If observed as designed, it exercises a genuine SYCL asynchronous error generated by an uncaught host-task exception, the configured handler's rethrow path, the run-boundary error translation, no-callback/no-retry outcome, and subsequent teardown after a successful completion wait. It does not simulate a GPU kernel fault, Level Zero device-lost/reset-required result, kernel hang, driver crash, memory fault, device command partial execution, or a queue wait that cannot complete. It also cannot establish the exact point at which a real device fault would be detected or whether every production backend routes it through the same exception type. No device reset or recovery claim follows from this test.
