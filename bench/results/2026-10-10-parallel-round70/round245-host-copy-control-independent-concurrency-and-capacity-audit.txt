Concurrency and lifetime audit
The harness is a separate C++ pool and does not instantiate live `Stager`. For each 16-slot batch, main sets a generation and an atomic work index; each worker claims distinct slot indices and writes only that slot's destination/result plus its own assignment count. A worker publishes departure while holding the same mutex used by main's completion wait; main waits until every worker departs before reading results or checking outputs. Main verifies generation/job tags and every full payload, then checks source/destination canaries and destination hash, and only then acknowledges the generation. The next batch rejects an unacknowledged prior generation. Therefore no destination slot is overwritten while a worker still copies or while main checks the previous contents. Pool joins before final source validation and before arena destruction. Normal receipt says complete/pass, `active:false`; controller records normal exits, reaped direct children, no survivors, and the same boot ID for owned commands.

No concurrency or source/destination lifetime counterexample was found in the inspected code/receipt. The principal deliberate difference is material: batch workers stop at each 16-copy barrier while main performs full verification and acknowledges; that is a synthetic host acknowledgment, not the live asynchronous DMA completion/reuse protocol. It makes this a valid bounded burst-copy control, not a replica of live overlap or streaming cadence.

Byte verification, counts, and accounting
The control allocates a 64-byte-aligned ordinary RAM arena with 192 deterministic source blobs and 16 destinations, each 1,971,200 payload bytes plus a 64-byte tail canary. Each completed job gets a full `memcmp` against its source and FNV-1a64 over the full destination before reuse. All sources receive a final full hash/canary validation after pool join. The worker-byte identity is not merely a probabilistic hash: the full byte comparison is checked first. The expected source hashes are generated by the harness itself; no separately recorded external golden corpus was used. That limits independent corpus validation, but does not weaken the source-to-destination byte-equality result.

Independent arithmetic over the retained structured receipt finds 104 sample records: 12 timing processes × 8 records (1 warmup + 7 samples) and 4 qualifier processes × 2 records (1 warmup + 1 qualifier). Their counts reconcile to 19,968 fully checked copy jobs and 39,936 source/destination tail-canary checks. The 84 timed rows each have 12 positive batch durations; the receipt's batch-wall sum matches those durations, and worker copy-span sum matches the 192 per-job spans. Rates recompute from 378,470,400 payload bytes divided by summed batch-wall nanoseconds, in decimal GB/s. Logical read+write rate is exactly twice payload rate. Total checked payload over all records is 39,360,921,600 bytes. Verification/hash/canary work occurs outside the timing windows, between bursts, and changes cache state; the numerator and denominator do not include those scans.

Capacity finding and valid comparison
For three workers, the median of three process medians is 13.743331 GB/s payload (12.943454–13.946056 range of process medians), or 27.486663 GB/s under the declared logical read+write convention. Four workers yield 13.667247 GB/s; six yield 13.710849 GB/s. Their process-median ranges overlap substantially. In this control there is no measured benefit from increasing worker count past three; this supports not increasing threads on the basis of a generic “more memcpy threads” assumption.

The separate hardware report defines H2D as a 256 MiB host-USM transfer, 6.447 GB/s one-way payload, with host-inclusive completion. Comparing the same one-way payload-rate denominator gives 13.743331 / 6.447 = 2.13174. For the representative 1,971,200-byte payload, dividing by those independently measured rates gives conditional quotients of about 0.143 ms for this three-worker plain-RAM copy control and 0.306 ms for the separate H2D control. This demonstrates operation-level headroom for the synthetic copy arm relative to that H2D control, and justifies prioritizing measurement of the actual transfer path before raising Stager worker count. It does not prove actual Stager copies finish in 0.143 ms, that H2D and copy are serial, or that the production bottleneck is H2D. The payload denominators are comparable; the memory semantics, request size, completion protocol, and overlapped schedule are not.

Concrete gates before any production conclusion
1. Attest the actual route/source arm and the per-expert bytes: resident direct pointer versus `copy_blob`, GGUF `read_into`/assembly, file-transient path, pinned-source bypass, and actual mixed blob sizes. The control is uniformly 1,971,200-byte resident ordinary-RAM source; no disk/read-into/cache-fault behavior is included.
2. Attest allocation outcomes for the live host ring (`sycl::malloc_host` success versus pageable fallback) and source/destination placement/alignment. The benchmark is not pinned or SYCL host-USM memory, so it cannot transfer its copy rate directly to either allocation type.
3. Attest worker defaults for the exact production run: source uses 32 threads for file-transient input; otherwise, absent override, `max(2,min(4,hardware_concurrency()/4))`. The host has 12 online logical CPUs in metadata and the expected resident-RAM default is three, but the synthetic controller explicitly sets 3 and does not query/attest `std::thread::hardware_concurrency()` or the production source type. Taskset pins the control to physical CPUs 0–5; it is not evidence that production had the same affinity.
4. Record live stager ready-wait/host-copy spans against exact matching H2D issue-to-completion events, ring-slot reuse acknowledgments, and the DMA queue timeline. Preserve overlap and per-job dependency structure rather than dividing all bytes by one isolated rate. Pair with actual selected-route expert histogram and phase timing; the control contains no route, DMA, dequant, GEMM, or inference.

No optimization, bottleneck, actual-model speedup, physical DRAM rate, or production stager capacity conclusion follows from this control alone. The three-worker result is useful as a conservative plain-RAM host-copy capacity reference; it is not a hard upper/lower bound for the SYCL staging implementation.
