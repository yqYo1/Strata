## Finding

I found no valid-row EOF defect in the active Linux direct reader for the admitted 90-byte table. It does not clip the requested job or pad the buffer. It submits a page-aligned 4 KiB or 8 KiB read, records the actual returned byte count, and copies/caches a row only if that row's complete byte range is within the returned prefix. Consequently the final valid rows are accepted when the read reaches EOF partway through the requested page, while any short read that omits even one requested byte causes `collect` to fail. Bytes left in the reused slab beyond the OS return length are never copied to an output row or inserted into RowCache.

This is a source-level safety proof, not a successful actual-shard I/O result. The R239 offline census enumerated the valid row domain and geometry but issued no reads. R230 already identified the generic short-EOF behavior; this pass adds the exact final 4 KiB and preceding-page 8 KiB job extents for this file, checks the loaded production parser's overflow/extent guards, traces row fan-out/cache/error handling, and calls out the remaining direct-API extent assumption.

## Exact last-page geometry

For the admitted IQ4_NL table, tensor row 0 is at file offset 192, row width is 90 bytes, row count is 320,001,536, and the tensor end/file EOF is 28,800,138,432. The EOF remainder modulo 4,096 is 3,264; the last aligned page starts at 28,800,135,168 and the nominal full-page request extends 832 bytes past EOF.

- Last valid row ID 320,001,535 begins at 28,800,138,342 (offset 3,174 within the final aligned page) and ends exactly at EOF. Its 4 KiB job starts at 28,800,135,168. On an unmodified file a Linux `pread` can return 3,264 bytes rather than the requested 4,096. The use bound is `3,174 + 90 = 3,264`, so the complete row is inside the returned bytes and passes the reader's check.
- A valid boundary-straddling row at ID 320,001,499 begins at 28,800,135,102, offset 4,030 within its first page (28,800,131,072). Its grouped job is 8 KiB and nominally ends at 28,800,139,264, also 832 bytes past EOF. The actual available prefix from that job start to EOF is 7,360 bytes; the row ends at offset 4,120 in the returned buffer. The check passes. Any other valid row fanned into that same page job also ends at or before EOF, so its `in_page + row_bytes` is no greater than 7,360.

The two requests are not shortened to their on-table extent before submission. The 832-byte overrun is only a requested buffer tail: POSIX file I/O transfers no data past EOF. In the Linux/OpenZFS environment described in R230, the request may have a direct portion and an ARC-served EOF tail; that storage-path detail does not change the application's returned-byte guard. The `pread(2)` API defines a successful return as the number of bytes actually read, so the caller must use that count rather than assume a full request ([Linux `pread(2)` manual](https://www.man7.org/linux/man-pages/man2/pread.2.html)).

The general proof is simpler than enumerating the census: for a valid row, `at = table_offset + row*rb`, `first = floor(at/PAGE)*PAGE`, and the requested use bound is `in_page + rb = at - first + rb <= table_end - first <= file_size - first`. A regular-file read may return a short prefix at EOF, but all valid uses whose bytes lie within that prefix pass. A truncation that cuts any requested row makes its bound exceed `c.bytes` and fails closed. This relies on the file staying unmodified between validation and reading; if it shrinks, the same guard rejects affected rows.

## Read completion, fan-out, and cache behavior

`PleReader::issue` skips invalid row IDs by writing zeros; for a valid miss it computes the absolute row interval, chooses the aligned first-page key, and requests 4 KiB or 8 KiB depending on whether the row crosses a page. Rows with the same first-page key share one `Job`; a straddler raises that job's length to 8 KiB. Each requested row retains its own `Use{row,in_page,dst}`. The algorithm intentionally deduplicates by first page, so an 8 KiB straddler can overlap another job keyed by the next page; it does not merge overlapping byte ranges.

On POSIX, a negative `pread` result is `ok=false`; any nonnegative result, including a positive short read or zero at EOF, is `ok=true` with its exact byte count. On Windows, `STATUS_END_OF_FILE` is also marked as a successful completion with its transferred-byte count. `PleReader::finish` handles either platform the same way: after an I/O completion it adds the returned bytes, validates *all* uses in the job (`in_page + row_bytes <= c.bytes`) before copying any of them, then copies each row and inserts it into RowCache. Thus one truncated use prevents the whole job's fan-out from being copied or cached. A zero-byte EOF completion cannot satisfy a nonempty valid use and fails.

Cache propagation is safe under that ordering. Same-ticket duplicate row uses are fanned out from the one page read; cache insertion occurs only after every use passes the byte-bound check, and duplicate cache inserts do not replace a valid resident row. On a later ticket, `RowCache::find` can serve the row and copy its 90 bytes directly to the caller buffer. No cache path reads from the DirectFile slab or creates a partially populated row. Out-of-range rows are zero-filled and are not cached.

On failure, `finish` latches a reader-wide error, cancels unsubmitted queued jobs while decrementing their tickets' pending counts, clears the failed job's uses, decrements its ticket and returns its slot. Already-in-flight jobs are drained; independently successful jobs may still populate their own output rows/cache before the failed ticket completes, but `collect` returns false because the global error is latched. The production `PleTable::gather_batch` checks `reader.collect` before decoding any of the ticket buffer and returns false; verifier and prefill callers propagate that false. The legacy `PleTable::gather` void API instead logs and returns an all-zero embedding on direct-read error, but no active production verifier/prefill caller found in this source uses that API. `wait_prefetches` discards individual collect errors during synchronization/teardown, but the underlying reader error remains latched: a matching-prefetch `gather_batch` returns false when it collects, and a mismatch path's subsequent ordinary collect also fails. This is fail-closed for the production bool-returning gather path, though it can defer where the prefetch failure becomes visible.

## Parser extent and API boundary

The active `PleTable::open` path validates the PLE GGUF tensor shape/type, checks `n_rows <= UINT64_MAX / row_bytes` before multiplication, checks `data_start <= file_size`, then uses subtraction-based bounds (`t.offset <= have` and `need <= have - t.offset`) to prevent overflow and out-of-file extents. For a one-tensor shard it also requires tensor offset zero and exact table fill. In direct mode it closes the parse mapping before opening `PleReader` and passes the validated absolute offset and extent. For the admitted stand-alone shard these constraints establish `table_end == file_size == 28,800,138,432` without reading tensor data.

One narrower hardening gap remains in the public `PleReader::open` itself: its local check is `table_offset + n_rows * row_bytes > file.size()` and is not overflow-checked there. The active production caller has already validated the multiplication/addition in `PleTable::open`, so the frozen path's last-row proof does not rely on unsafe arithmetic. A different caller invoking `PleReader::open` directly with adversarial values could wrap that expression and bypass its extent check despite the API comment's validated-input precondition. A low-risk follow-up, if root chooses to harden the generic API, is to reject `n_rows > UINT64_MAX / row_bytes`, then reject `table_offset > file.size()` or `n_rows*row_bytes > file.size()-table_offset` before storing the extent. This is not evidence of an admitted production-table failure.

## Existing tests and remaining qualification

Existing test source is relevant but was not run here. `direct_file_async.cpp` checks aligned reads and a 4 KiB request at a synthetic 17-byte EOF returning exactly 17 bytes; `ple_reader_test.cpp` checks first/last rows, duplicates, straddlers, cache hits, multiple in-flight tickets and delays against synthetic files. The latter's edge ticket includes `N-1`, but its selected straddler rows are taken from the beginning of the table rather than deliberately selecting the final 8 KiB short-at-EOF job. Existing R233's 65,536 pread samples all returned full lengths and were not an EOF qualification. These tests support the generic mechanism but do not prove current-device behavior for this admitted shard.

No root action is required to resolve an observed source defect. If an additional finite CPU qualification is desired before relying on this source proof, make a dedicated synthetic sparse file with the exact `(table_offset=192, row_bytes=90, n_rows=320001536, file_size=28,800,138,432)` geometry, write deterministic sentinels only in the target pages, and exercise the ordinary `PleReader` 4 KiB final-row job plus the 8 KiB row-320001499 boundary job. Require the expected short byte counts (3,264 and 7,360), exact sentinel output, successful `collect`, correct cache hit on a second ticket, and unchanged output guards. In separate truncated-file arms, cut EOF into each requested row and require `collect=false`, no cache insertion for that job, no decode, no normal success marker, and clean close after queued/in-flight work drains. Keep this CPU-only, serialize it with other I/O/build/GPU work, and do not call it actual-shard I/O or full-context inference qualification. The existing API test could be extended to include these two end-boundary cases, but no source change is recommended solely from this audit.
