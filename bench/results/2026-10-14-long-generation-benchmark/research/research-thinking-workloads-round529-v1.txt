## Assessment

The current v3 completion gate has the right shape for the user's requirement: actual `usage.completion_tokens` must be at least 1,024 and may extend to 8,192, and at least 512 visible answer characters must remain after thinking (`tools/long_generation_bench.py:6-13,45-60`). The 1,024 value is an eligibility floor, not the requested output size or an upper limit. Do not change it into a fixed 1,024-token cap. A request that uses 7,200 tokens thinking before producing answer text is not proof of a model fault or of a useful completed long-output sample; record it as a thinking-only/partial output at that observed point. The task handoff says the native later ended with SIGXCPU under an incorrectly interpreted aggregate CPU budget. Keep that process failure separate from output behavior and GPU-fault status; it supplies no completed speed sample.

The v3 prompts are poor first-line realistic workloads for the user's purpose, though for different reasons. The 80-test module requires mechanically repeated exact forms (`long_generation_bench.py:15-25`), so it can overstate local regularity and may burn output on a synthetic artifact. The Japanese story asks for several voices, three motives, the same event from multiple viewpoints, a contradiction and resolution, diverse sensory/technical details, and novelty (`:28-40`). That combination forces open-ended planning before prose and is likely harder to complete with a substantial body under an 8,192-token total cap. This is a workload-design inference, not a measured acceptance or quality claim. The prior in-repository v1 screen is especially clear about why its old 1,152 cap cannot be reused: both requests had 1,152 completion tokens and zero visible answer characters (`screen-v1.json`). That result is historical v1 evidence only; it does not establish v3 behavior.

A load-bearing control is reasoning effort. The official Qwen3.8-Flash-Next chat template revision shown on Hugging Face (uploaded 2026-08-26, commit label `34567a4`) sets `reasoning_effort` to `xhigh` when thinking is enabled and no effort is provided, then adds an instruction to think carefully and consider alternatives (`chat_template.jinja:310-318`). The v3 client explicitly enables thinking and sends `reasoning_budget_tokens: 0`, but does not pass an effort (`tools/strata_bench.py:274-276`). Strata defines request budget zero as no reasoning-token budget (`serve/server.py:1740-1750`), and the service's shared default is not inserted if the request already contains `chat_template_kwargs.enable_thinking` (`serve/server.py:1933-1939`). If the active loaded template matches the cited official revision, this combination means thinking is unbounded up to the overall completion cap and defaults to xhigh. It is a plausible contributor to thinking consuming most of a small completion; it does not by itself explain any individual long reasoning trace. Record and hash the template actually loaded by the benchmark before drawing a causal conclusion. A matched `enable_thinking=true` low- or medium-effort condition is a useful follow-up if the intended question permits effort to vary; it must get its own workload identity and must not be mixed with xhigh results. Thinking remains on in either condition.

The requested 262,144-token setting is not exercised by the current v3 sample gate. The request is calibrated around 33,792 input tokens, eligibility only requires at least 32,768, and the precheck needs about 42,496 context tokens (`tools/strata_bench.py:254-276`, `tools/long_generation_bench.py:9-10`). The official model launch examples advertise 262,144 context, but this benchmark is a 32K-input decode workload on a server configured with a larger maximum, not a 262K-context result. Keep those claims separate.

## Ranked workload proposals

1. **Six-turn coding-agent issue triage with deterministic tool results — best match to the agent-history request.** Use a small frozen fictional repository issue: a reproducible bug report, a few relevant source excerpts, a failing-test excerpt, and a config note. Across six user/assistant turns, have the agent inspect/search, read, compare evidence, receive a deterministic tool result, answer one bounded follow-up, and deliver a final diagnosis plus a patch plan. At least two turns should return actual tool results; replay the model's assistant messages and tool results in the next request. Keep tool outputs relevant and bounded. Each turn can have a 2,048-token maximum as in the unapplied proposal, but that is a per-turn maximum, not a 12,288-token target. Enable thinking for every turn and record the exact effort. This tests long-lived history and useful work without a creative-writing planning burden. Count sessions, not six correlated turns, as independent repetitions; retain per-turn prompt/reuse/usage/draft rows and a session aggregate. The task must be frozen enough that runs can be compared, while actual assistant/tool-call text remains part of each run's history.

   Important proposal correction: a real tool-agent turn may correctly finish with `tool_calls`. Treat that as a valid intermediate transition only when its tool call parses, the expected deterministic tool result is appended, and the six-turn state machine continues. Require a normal final answer on the final turn. Requiring every turn to have only a normal `stop`/`length` finish would reject successful tool use. Preserve the assistant tool-call message and tool result with their roles/IDs, rather than simulating tool use as another ordinary user message. Qwen's official concepts guide documents multi-step tool calls and tool results in the conversation structure; its function-call guide recommends a structured tool protocol for reasoning models instead of stopword-based ReAct parsing.

2. **Evidence-grounded maintenance memo — best single-request natural sustained-answer candidate.** Supply a frozen, relevant 32K-token evidence bundle from a fictional repository or incident packet: a bug report, selected source/config excerpts, test output, and a short change log. Ask for a concise but substantial engineering memo with a diagnosis, evidence with file/record references, alternatives, a recommendation, unresolved questions, and next steps. Bound the number of evidence items and sections, but let each section explain the evidence; ask for a complete memo and conclusion rather than an outline. This has an answer body that is directly useful and checkable without requiring a plot, multiple characters, or many simultaneous stylistic constraints. A 512-character body gate is a presence check only; quality and evidence support need separate review. It is a candidate for ordinary variable prose, not a promised weak-MTP case.

3. **Structured migration/incident register — controlled regular-output candidate.** Provide 30–50 distinct source records with IDs and short factual descriptions; ask for one useful row per record in a fixed Markdown/CSV schema such as ID, affected component, user impact, action, and unresolved question. This is a real transformation task with predictable formatting, a substantial final body, and a row-count/content check. It is more natural and less trivially periodic than writing 80 copies of one unit-test shape. Classify it as a *regular-format hypothesis* only; record observed agreement before naming it high acceptance.

4. **Keep the Japanese story as an optional creative-writing workload, after simplifying it.** If Japanese creative writing is part of the actual target workload, reduce it to one place, one or two characters, one central problem, and a clear resolution; remove the simultaneous multiple-POV/voice/knowledge and contradiction constraints. Use it as a distinct open-generation workload, not as the only low-agreement arm and not as an agent test. The reported 7,200-token thinking-only observation makes it a poor first task for confirming body emergence under the current xhigh/unbounded-thinking request.

Prefer relevant 32K evidence over the current unrelated generated word list where long-context handling is part of the claim. The present prompt explicitly tells the model that the word list is irrelevant (`tools/strata_bench.py:266-273`): that measures decode after a long irrelevant prefix, not realistic synthesis over a long working set. If preserving this calibration prompt for comparability, label it as a separate synthetic-prefix decode workload and do not call it the agent-session workload.

## Experimental handling

- Keep thinking enabled and pin `enable_thinking`, exact `reasoning_effort`, reasoning budget, sampling, model/quant, loaded template hash, server/config, input/request hash, context and output cap in the run identity. Do not compare an xhigh run to a low/medium run as though only the prompt changed. The model template is an upstream default, not proof of the template actually loaded by this Strata build.
- Treat `max_tokens` as a hard cap only. The 1,024 minimum and 8,192 maximum must stay separately recorded. Keep every request with actual `usage.completion_tokens`, visible content length/hash, reasoning length/hash, finish reason, offered/accepted counters, engine timing, request order and failure status. A missing usage count cannot be replaced by stream-piece counts for eligibility (`tools/long_generation_bench.py:45-73`; R528 comparability report).
- Separate performance eligibility from task completion. A valid engine-timed request with 1,024–8,192 actual completion tokens and at least 512 body characters can be a generation-performance sample even when it hits the cap; label `finish_reason=length` as cap-limited/truncated and do not call the task complete. `finish_reason=stop` is necessary but not sufficient for task success. For an agent, a valid intermediate tool call is neither a final answer nor a failed sample. Define task-specific checks separately from throughput.
- Retain short/EOS-before-floor, thinking-only, cap-truncated, malformed-tool-call, missing-usage/timing/draft, and process-failed samples with reasons. Do not rerun a short or unhelpful output until a favorable one appears. If infrastructure retry is necessary, declare its criteria and maximum attempts in advance, keep all failed attempts, and report the retry denominator. Alternate workload order and use independent sessions for replication; do not treat six turns from one history as six independent samples.
- For speed summaries, include all predeclared eligible samples and show all attempted/eligible/ineligible counts by cause. For agreement, use `sum(accepted)/sum(offered)` plus each request's ratio; zero offers means undefined. Report speed-eligible rows that lack enough draft offers separately from agreement-eligible rows. Keep the current >=256 offered-draft condition if maintaining continuity with v3; do not change it after seeing results. A workload label such as “regular” or “varied” is a hypothesis, not a measured regime.
- Record process exit independently from request samples. SIGXCPU is a CPU resource-limit termination, not a GPU fault or normal run completion. Distinguish aggregate CPU-seconds (`RLIMIT_CPU`) from wall-clock deadlines, preserve completed request rows when a later request or process fails, and do not publish a completed-session/rate summary for an interrupted parent process. The task handoff says the previous native process reached SIGXCPU after a mistaken wall-time interpretation; that is a failed run boundary, not evidence about MTP speed or correctness.
- Preserve the stated MTP scope. Current root server counters can reflect proposal agreement rather than end-to-end speedup; prior R527 notes the serving path's source selection and end-of-output counter edge. The active screen pins suffix drafting off per Main's correction. Still, acceptance observations alone do not prove speedup, output quality, completion, or equivalence to another model/configuration. No prompt should be described as high/low until replicated measured counters support its predeclared threshold.
