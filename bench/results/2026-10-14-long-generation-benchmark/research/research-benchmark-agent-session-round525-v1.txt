## Formal upstream benchmark and agent-session semantics

`bench.sh` is a thin launcher: it changes into its checkout and `exec`s `.venv/bin/python tools/strata_bench.py "$@"` (`bench.sh:1-10`). The supported `--long` flag selects an about-32,768-token prompt; `Suite.run()` runs warm-up, short chat, 4K, 16K, agent, optional concurrency, then 32K (`tools/strata_bench.py:401-411,834-848`). Thus the standard comparison command is the unchanged `./bench.sh --long --runs N` on each matched binary/configuration. It includes all standard suite cases and writes the stock community result. It is not equivalent to calling only the long prompt code path, and `--long` itself does not lengthen decode (`LONG_MAX_TOKENS = 24`, lines 55-62 and 281-302).

The formal agent case is a six-request, five-file-reading conversation sequence (`AGENT_TURNS = 5`; loop is `range(AGENT_TURNS + 1)`, lines 55-62 and 320-338). It sends a system message and an initial user task; on each later turn it appends a roughly 1,500-word project-file body as a user message, then resends the complete message list to `/v1/chat/completions`. After each request, the benchmark appends the model's actual answer as the next assistant message (lines 304-338). Therefore it has model-generated assistant history, unlike `agent_turns_bench.py`, whose successive snapshots contain prewritten assistant tool-call messages and fixed tool outputs (`tools/agent_turns_bench.py:115-128`). The formal benchmark's sequence does not actually execute tools or append tool-role results. Describe it accurately as a scripted file-review agent conversation with model-generated answers, not a tool-executing agent or an arbitrary real user session.

The history is scripted but not byte-identical across repetitions: each system prompt gets a per-run nonce (`Suite.tag`, `:229-234,320-324`), each run rereads whichever eligible files exist in the checkout (`:304-318`), and later request bodies include sampled model answers (`:326-338`). Temperature is zero, yet prompt/output token counts may still differ slightly as documented in the report (`:131-136,783-786`). For paired A/B acceptance tests, matching the source checkout is necessary but not enough to make the whole conversation body identical. Hash each serialized request if exact prompt identity is needed; for controlled acceptance comparisons, a single frozen prompt/body is simpler and more diagnostic than extending this adaptive history.

Each of six agent turns has `AGENT_MAX_TOKENS = 64` as a per-request cap (`:55-60,320-338`), not a session-wide 1024-token target. Short-answer instructions ask for one or two sentences (`:323-324,329`), so actual aggregate completion can be far below 384 tokens. The formal report currently displays "up to 64" per turn and a session-level decode summary; raw per-request records retain turn index, actual completion count, prompt/reused/read counts, decode rate, prompt rate, TTFT, prompt/decode milliseconds, and MTP `drafts_offered`/`drafts_accepted` (`:178-201,330-338,364-368`). The table does not aggregate or gate by cumulative generated-token budget (`:711-716`).

The standard suite's `--think` toggles reasoning off only when absent; when enabled, the request omits the disabling parameters, allowing configured/default reasoning (`:128-139,740-741,842-844`). The client treats both `content` and `reasoning_content` as first-piece activity but stores only normal `content` in the transcript (`:128-175`). The server usage's `completion_tokens` is the correct total-output measure for a budget that includes thinking; in this fork, the server's generation loop totals completion tokens across generated events before publishing usage (`serve/server.py:2245,2463,2548-2598`). Do not count visible content characters/tokens alone. Preserve the thinking setting/effort in result metadata because it changes both total completion work and what history is replayed.

The formal case's `cached_tokens`/`prompt_n` feed cache hit, reread and new-input statistics (`:178-201,354-368`). These counters characterize the actual configured server behavior, not a guaranteed cache hit or a proof that the full prefix was reused. Keep total prompt tokens, cached/reused tokens and newly read tokens as distinct fields; do not call `prompt_n` total context. A report should preserve per-turn values and session aggregates. Existing `drafts_offered` and `drafts_accepted` counters can support MTP acceptance rates, but a ratio must be computed from summed counts (`sum(accepted)/sum(offered)`), alongside each request's raw counts; averaging per-request ratios weights tiny and large draft samples equally. A zero/missing offer count makes acceptance undefined, not zero.

## Minimal compatible extension seams

Keep `bench.sh --long` and its existing `tools/strata_bench.py` report path/meaning as the standard suite result. The smallest compatible addition is to the suite's agent section: add a separately labeled pair of fixed acceptance workloads and additive CLI/result metadata, preserving the existing agent case and JSON schema's current fields. A split helper such as `run_agent_acceptance()` called next to `run_agent()` is less invasive than changing the formal agent's six-turn semantics. Reuse `chat()`/`digest()` so existing HTTP handling and timings continue to populate prompt, completion, reasoning-inclusive completion, MTP offer/accept, finish/error and latency evidence. Add explicit request-body identity/hash, workload label, target/cap, actual completion budget state, and content/reasoning counts only if the API exposes them; leave the standard conversation's `sessions` and its summaries intact.

For high/low acceptance, define the workload by the prompt and expected MTP acceptance regime, not merely by an arm name or `--think` flag. Use the same model, server/config, thinking effort, decoding settings, per-request context, and exact input bytes for the comparison arms. The high case should make continuation predictable from the supplied context; the low case should make the continuation difficult to predict while remaining a meaningful generation task. Document the exact prompts and their hashes. The response content need not be identical across candidate engines if stochastic settings are used; deterministic decoding and fixed seed make the acceptance comparison more interpretable. Record correctness/termination and output digest separately from throughput.

A nominal `max_tokens=1024` is a maximum, not proof that 1,024 tokens were generated. For the requested approximately 1,024 total generated tokens **including thinking**, accumulate returned `usage.completion_tokens` over the workload, not visible text alone. Keep each generation request bounded and persist every request's actual total and MTP counters; if using multiple turns, pass the remaining target as the next cap and stop after reaching the target or a defined overshoot tolerance. Prefer one request with an explicit 1024 cap if the intended MTP workload can produce a sufficiently long continuation in one request; if one response commonly ends early, use a deterministic continuation protocol and state that the sequence is a multi-request workload. Do not artificially truncate or silently discard overshoot rows. Predeclare an acceptance band (for example, 900–1,100 actual completion tokens) and mark runs outside it as incomplete for the 1024-token acceptance comparison while retaining their raw results. Record reasoning-inclusive usage as the controlling count and separately note whether thinking was enabled and its configured effort.

Minimal output evidence per workload/run: request hash, workload label, arm/config/binary identifiers, think/effort, seed/sampling parameters, context and effective input/reused counts, per-request `completion_tokens`, cumulative completion tokens, finish reason, output digest and correctness result, elapsed/engine decode timing, `draft_n`, `draft_n_accepted`, acceptance ratio from summed counts, errors, and process/run order. The stock report can summarize medians/ranges, but individual raw rows must remain in `results.json`. Distinguish warm-up from measured requests and do not mix stock `--long` prefill samples with these acceptance decode samples.

## Suggested acceptance checks before speed interpretation

1. Run the unchanged `./bench.sh --long --runs 3` (or the predeclared replication count) as the standard result for each arm. Preserve the generated result folder and individual 32K prompt rows; gate on actual prompt token count, successful completion and recorded config. The standard prompt case's 24-token output is a prefill reference only.
2. Run a separately named agent-session result with the existing six-turn conversation intact. Confirm all turns' cumulative `completion_tokens`, actual prompt/reused/read values, the thinking setting, and raw draft counters are present; report cache as observed by that server and not inferred from chronology. An approximately-1024 aggregate across this short-answer scenario should not be claimed unless the actual usage total passes the predeclared token band.
3. Run each fixed high- and low-acceptance workload for the target budget in paired/alternating arm order, with fresh-process repetitions if process startup/cache state is part of the criterion. Require each accepted sample to land in the predeclared actual completion-token band including reasoning, complete normally, pass the workload's correctness check, meet the context gate, and provide nonzero draft offers before computing acceptance. Preserve failed, short, over-budget and no-draft cases, but exclude them from only the corresponding eligible-sample statistic with explicit counts/reasons.
4. Keep phases separate: stock 32K prompt/prefill, standard agent session, and high/low acceptance are distinct claims. Do not infer one from another, and do not pool their token rates or draft ratios.

These are source-level recommendations, not run results. No upstream or fork performance numbers were measured in this research.
