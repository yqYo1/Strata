## Selected server path

The configured root build target is the root `src/program/generate.cpp` (`CMakeLists.txt:430`); the server starts the resident `strata --serve` engine and sends its `GEN` protocol (`serve/server.py:392-398`). This audit follows that `--serve` request loop around `src/program/generate.cpp:5228-5237, 5260-5265, 5408-5416, 5863-5880, 5902-6006`, not the separate CLI generation loop at lines 6761 onward. The source tree alone does not prove which binary a running process loaded; the main run’s build/binary receipt remains the authority for that.

For each server GEN request, the engine initializes `draft_offered` and `draft_accepted` at zero (`generate.cpp:5873-5875`). Its first verification window is explicitly T=1 (`:5863-5865,5873,5908`), so this window contributes zero offers and accepts. Later it chooses a verification window T. The normal MTP proposals come from `MtpDrafter`; its chain is limited by configured max drafts and probability floor (`src/core/mtp.cpp:826-877`). Verification accepts the matching prefix `a` (`generate.cpp:5950-5952`), then increments offers by `T-1` and accepts by `a` (`:5965-5967`). These are proposal-token counts, not counts of windows. The wire `DONE` record carries accepted then offered as decimal integers (`:6152-6159`); the matching server parser reads those fields with `int()` (`serve/server.py:608-619`).

The GEN path also has suffix lookup (`generate.cpp:5235-5236,5913-5919`). When the online `DraftPolicy` chooses a suffix window, that window replaces the MTP candidates after confirming its first candidate agrees with MTP (`:5916-5919`; policy rule at `src/spec/draft_policy.cpp:55-81`). The counters nevertheless add generic `T-1` and `a` without labeling the proposal source (`:5950-5952,5965-5966`). Therefore API `draft_n`/`draft_n_accepted` are a combined verified-proposal agreement measure if suffix lookup is enabled, not a pure MTP-only metric. The source default enables suffix lookup (`generate.cpp:432-438`); CLI normalization can grow the verify window and cap MTP separately (`:1628-1634`). Confirm the actual launched `--suffix-draft`/MTP settings before naming the reported ratio “MTP acceptance.” If suffix lookup was explicitly disabled, the denominator refers to MTP proposals only.

There is a boundary effect at EOS and `max_new`: counters are updated for the full verified prefix before the engine emits tokens up to `max_new` or through the first EOS (`generate.cpp:5965-5975`). The request stops at EOS or the generation cap (`:5983-5984,6003-6006`); it can count accepted candidates after the emitted EOS, and a final accepted prefix can extend beyond the output cap. Thus `accepted/offered` is exact agreement over verified offered candidate positions but may include candidates not included in the visible completion. First T=1 itself does not bias the ratio because it adds neither numerator nor denominator. A sufficiently long response makes this edge contribution small; a short or truncated response can make it material.

## API timings, completion accounting, and benchmark digest

`StrataEngine._parse_done` stores counts as integers from the request’s own `DONE` (`serve/server.py:608-619`). `Service.run` saves these raw counts in per-request history and aggregates totals (`:2415-2426`); `request_timings` maps them to `draft_n` and `draft_n_accepted` only when the engine reported offers (`:2478-2495`). OpenAI streaming attaches the request completion usage and those timings to the final chunk (`:2647-2655`). Engine decode throughput uses engine-generated tokens and decode milliseconds (`:2485-2495`), while client TTFT is measured separately in `tools/strata_bench.py:147-188`.

The new screen’s `chat()` captures each final usage/timing object, normal `content`, reasoning text, finish reason, stream completion, and SHA256 of the exact serialized request (`tools/strata_bench.py:131-188`). `digest()` carries raw draft counts, engine decode timing, completion usage and finish status (`:191-217`). For screen eligibility, completion usage must be present as an exact Python `int` and be within 1024..8192; booleans and floats fail `type(generated) is int` (`tools/long_generation_bench.py:45-58`). Draft counters similarly require exact ints and `0 <= accepted <= offered`, with at least 256 offers (`:67-73`). This rejects missing, malformed, or inverted counters. A zero-offer count cannot pass; when calculating a general ratio outside this gate it is undefined, not 0.

The v3 workload declares thinking enabled, a 33792 target input estimate, minimum actual input 32768, maximum output cap 8192, minimum completion 1024 including thinking, and at least 512 visible body characters (`tools/long_generation_bench.py:6-13,45-60`). It explicitly sends thinking on and `reasoning_budget_tokens=0` (`tools/strata_bench.py:274-276,300-307`). The server interprets zero as no positive reasoning limit (`serve/server.py:1739-1750`) and returns total generated `completion_tokens` including thinking; the separate reasoning count is supplementary (`:2461-2464,2647-2654`). The visible body gate correctly checks `raw["text"]`, not reasoning characters (`long_generation_bench.py:54-55`). Thus the gate addresses the prior concern that a completion-token cap is only a maximum and thinking may consume it before any answer body appears.

Context is not tested at 262144: eligibility checks only actual `usage.prompt_tokens >= 32768` and zero prefix reuse (`long_generation_bench.py:56-60`). The suite’s context precheck is `33792 + 8192 + 512 = 42496` tokens. It allows a context smaller than 262144 and does not establish full-context behavior. `strata_bench.py:254-256` skips only if configured context is below that value. The actual prompt is calibrated approximately; the reported usage gate, not the target, establishes whether the run had at least 32768 input tokens. It does not require the request to reach the 8192 output cap; it requires at least 1024 actual completion tokens, which may end naturally at EOS. The result records per-request request hashes; run-number tags make requests distinct across repetitions (`strata_bench.py:270-276`). This is a screen of new, independent requests, not repeated byte-identical prompts.

For eligible requests, the suite reports each row’s accepted/offered and ratio, plus pooled `sum(accepted)/sum(offered)` and statistics over per-request ratios (`tools/strata_bench.py:291-307,883-894`). It does not silently include ineligible runs in these summaries. Classification is predeclared: at least three eligible runs each, regular code >=60% per run, varied prose <=40% per run (`long_generation_bench.py:76-87`). It explicitly describes this as observed draft agreement, not MTP speedup or task correctness (`strata_bench.py:891-894`).

## Interpretation for new real requests

At greedy decoding, accepted/offered is a direct empirical agreement fraction between the selected proposal source and target model’s verified next-token sequence for the candidate positions that were actually verified. The integer validation and API propagation are sound for that scoped interpretation. It is useful for comparing proposal agreement under the same model, server configuration, prompt type, and generation settings.

It is not a general “MTP quality” score unless suffix lookup is disabled or separately attributed. With lookup active, the source API merges MTP and suffix candidates. Even pure MTP ratios are affected by probability-based window length, request output stopping, and the model/prompt distribution. The cap/EOS accounting can include un-emitted accepted positions. Therefore acceptance from these real requests is a reliable agreement metric only when reported with the actual proposer configuration and caveat; the screen is not a speedup proof. The current benchmark does not claim quality qualification (`quality_qualified: false`, `strata_bench.py:300-307`), and its candidate prompts do not guarantee strong/weak acceptance regimes (`long_generation_bench.py:1,76-87`).
