## CPU budget recommendation

`RLIMIT_CPU` is CPU time in seconds for a process, not elapsed time. Multi-threaded CPU work can consume multiple CPU-seconds in one wall second. This screen used `--pool-workers 5` and the capped native process averaged roughly `9300 / 2320 = 4.0` CPU-seconds per wall second before the signal. Thus the observed cutoff is consistent with the equal wall/CPU cap; it occurred well before the 9,000 s benchmark timeout or 9,300 s owner wall deadline.

Set the CPU soft limit from both the wall budget and the work’s bounded CPU parallelism. For this screen, a defensible starting rule is:

`cpu_soft = ceil(wall_seconds * min(effective_cpu_slots, configured_cpu_parallelism) * 1.10)`

where `effective_cpu_slots` uses the process affinity and any cgroup CPU quota, and `configured_cpu_parallelism` is derived from engine/server worker settings (here at least the 5 configured pool workers plus the host/main execution slot). With 5 pool workers plus one host slot and a 9,300 s wall budget, that rule gives at most 61,380 CPU seconds; the exact bound should be limited to the actual effective slot count. Record the inputs and computed limit in the run receipt. Keep the separate wall timeout as the absolute elapsed-time bound. The existing owner also has finite RSS, log, artifact, process-population, and closure checks; those remain independent bounds.

The formula is intentionally per process: `RLIMIT_CPU` is not a shared CPU-second pool for every descendant. Each process inherits limits, and a process with threads can spend CPU in parallel. If the desired policy is a strict aggregate CPU budget across the whole owned session, use a session/cgroup aggregate counter and owned shutdown path as a separate limit; do not describe the inherited `RLIMIT_CPU` as an aggregate tree cap. A soft/hard gap materially larger than one CPU second would allow orderly closeout only if the workload handles `SIGXCPU`; otherwise the default signal action still terminates at the soft limit. Keep the bound finite and record both values.

## Termination and status truth

Python documents `RLIMIT_CPU` as processor time and says it sends `SIGXCPU` when exceeded. Linux man-pages state the default `SIGXCPU` action is process termination; if caught/ignored, Linux sends it again once per CPU second until the hard limit causes `SIGKILL`. `direct_owner.py:221-224` configures a one-second soft/hard gap and does not install a signal handler in the child. The observed `engine-exit.json` `exit_code=-24` is therefore a signal termination; it is not a successful exit code. The wrapper's server exit code 0 only means its own shutdown completed; `run_server_job.py:175-183` correctly requires both native and server exit 0 and records failure otherwise. Keep `passed=false` and `complete=false` even though `direct_owner.py` successfully observed/reaped the owned session. These fields answer different questions: workload completion versus process ownership closure.

The returned HTTP error included the engine's unexpected exit, and the client retained an incomplete stream-piece count, but that fallback is not authoritative completion usage. The screen correctly leaves `generated_tokens` ineligible without normal completion usage. Any future checkpoint must preserve a distinct terminal reason (`normal`, request error, timeout, signal/resource limit, owner wall stop) and must never promote a partial output into a usage-backed complete sample.

## RequestJournal patch audit

Captured `proposal.patch` SHA256: `1097092118954f84525de4a82dadec5893b9a6447f85201a1e6fd700da99c670`. The patch adds useful core behavior: fsyncs each compact JSONL row, chains rows with `previous_sha256` and a row digest, atomically replaces/fsyncs state, writes `start` before the request and a result after return, and leaves completion false if the suite is interrupted. Its request rows retain summary values and output/reasoning digests rather than full text. This supports recovery after abrupt death better than only writing the final results object.

**Medium: concurrent in-flight state is inaccurate.** `RequestJournal.append()` serializes appends with a lock, but `journal-state.json` stores one scalar `pending`. Every `start` overwrites it, and any `result` or `interrupted` clears it (`proposal.patch:89-102`). Under concurrent client requests, a completion for A can clear B’s still-pending status; multiple starts collapse to the last one. JSONL rows preserve enough history to reconstruct unmatched starts, but the state summary cannot be trusted as a live pending count. Store a pending map keyed by a stable request ID and remove only that request on terminal row; derive/verify it from the hash chain when reopening.

**Medium: interrupted requests lack their request identity at the durable start boundary.** The start row contains phase/run/turn only (`proposal.patch:126-134`). The exact serialized request hash is added to the result only after `chat()` returns. A kill between start and result leaves an unresolved marker but not the request hash or effective parameters that would identify the attempted body. Add the canonical request SHA256 and non-secret parameters (model, max tokens, thinking/reasoning settings, timeout) to the start row before sending bytes; do not store prompt text or secrets.

**Low/medium: signal and timeout provenance is split across files, and no recovery verifier is wired in.** A caught `KeyboardInterrupt` is returned from `chat()` and then causes `request()` to raise after logging the sample; the suite-level handler marks state interrupted. An external `SIGKILL`/default `SIGTERM` leaves the last durable state as `running` with a pending start, which is appropriately incomplete but does not say why. A caught transport error can be logged as a result and the suite may later mark its journal complete even though an individual request failed; this should mean “all scheduled work returned,” while row eligibility and run `passed` remain separate. The wrapper hashes the finished journal and records state but does not verify row sequence, each row hash, last index/hash agreement, or pending reconstruction. Add a small read-only verifier at collection: validate monotonic indices, previous-hash links, canonical row digests, final state head, and pending IDs; report mismatch as corrupt/incomplete. Keep the owner/outer receipt’s signal, timeout, and closure evidence as the authority for cause.

A direct `SIGXCPU` to the native engine does not itself interrupt Python’s streaming client. In this run, it became a request/engine error. If the benchmark client itself receives an external signal, the proposal’s initial durable `start` row survives; an in-memory partial stream does not. That is acceptable for compact result retention if marked unresolved, but do not claim partial token/body evidence is preserved. The existing `RequestJournal` has no signal handler, which is preferable to unsafe work in a handler; rely on atomic per-event persistence and classify an unresolved start as interrupted from the owner’s terminal evidence.
