# R544 — Thinking-enabled benchmark request and terminal-gate review

Date: 2026-10-15 JST. Source-only review of the current `tools/strata_bench.py`, `tools/long_generation_bench.py`, the burst client, and the OpenAI server/template path. I followed the census and long-generation registries and their prior-report chain, including R525–R530 and the Main corrections, then focused on current request construction, response parsing, eligibility and process-exit behavior. I did not inspect current or closed run files, models, private environment/session data, the excluded record, or any process/service; I ran no test, build, benchmark, profiler, GPU, Git mutation, reset or cleanup. No new performance result or output-quality claim is made.

## What the current source actually sends

With `--think`, the ordinary benchmark client's `chat_body` explicitly sets `enable_thinking=true`, `preserve_thinking=true`, `reasoning_effort=xhigh`, and `reasoning_budget_tokens=0` (`tools/strata_bench.py:132–145`). The server treats a zero reasoning budget as no separate reasoning-token limit (`serve/server.py:1739–1750`); thinking and visible answer share the requested `max_tokens` cap. The local template defaults enabled thinking to xhigh as well, but the ordinary client's xhigh is explicit.

| Workload | Request cap and source meaning |
|---|---|
| Short chat | 100 total completion tokens per request, thinking included when `--think` is set (`strata_bench.py:59,489–503`). |
| 4K / 16K prompts, optional 32K prompt | 24 total completion tokens; this measures prompt work/TTFT, not long decode (`:60,507–524`). |
| Agent-style history | Six sequential requests, each capped at 8,192 total completion tokens with `--think`; assistant body and `reasoning_content` from each response are resent in later turns (`:61–62,547–570`). |
| `--clients N` burst | 128 total completion tokens per request. With `--think`, the burst client sends `enable_thinking=true` and budget zero, but relies on the served chat template's default effort rather than explicitly sending `reasoning_effort=xhigh` (`:65,624–648`; `serve_load.py:24–31`). The checked-in template defaults that to xhigh (`chat_template.jinja:58–70`). |
| Long-generation v4 | Always thinking-enabled, independent of the suite's `--think` flag; 16,384 total completion-token cap, actual input gate 32,768, target input about 33,792, body gate 512 characters and at least 256 observed offered drafts (`long_generation_bench.py:6–13,45–75`). The client keeps the base request's explicit xhigh/budget-zero settings, while its override drops `preserve_thinking`; this is a single user-turn request so there is no previous assistant reasoning to preserve (`strata_bench.py:401–431`). |

The benchmark's configured context value of 262,144 is a server maximum, not a 262K-input workload. Long-generation uses a target near 33.8K input and checks actual `usage.prompt_tokens >= 32,768`; its preflight requires `target + 16,384 + 512 = 50,688` tokens of context (`strata_bench.py:403–408`). The server independently validates the actual rendered prompt and output cap against remaining context, with its context slack, and rejects an oversized request unless fit mode is enabled (`serve/server.py:2145–2206`).

Warm-up calls are discarded from speed summaries. The two-point calibration calls omit `think`, so they explicitly disable thinking and request one token; they estimate prompt token/word slope only (`strata_bench.py:467–487`). Their rows are journaled, but calibration counts do not enter chat, prompt, agent or long-generation decode summaries. Long-generation also separates `speed_eligible` from agreement eligibility: it can summarize a valid engine-timed output with too few drafts for an MTP category, but `eligible`/classification additionally requires valid counters and 256+ offers (`long_generation_bench.py:45–75,82–88`).

The server's OpenAI stream maps parser reasoning events to `delta.reasoning_content` and answer events to `delta.content`; its final chunk carries total `usage.completion_tokens` (the server's `n`, including thinking) plus engine timings when present (`serve/server.py:2244–2464,2602–2655`). `chat()` stores the two text channels separately and the long-generation body check uses only normal `content`, while its usage check uses total completion tokens (`strata_bench.py:148–202`; `long_generation_bench.py:48–58`). The six-turn history replays both channels in assistant messages; the local template reads `message.reasoning_content` and reconstructs the previous `<think>` block (`strata_bench.py:569`; `chat_template.jinja:114–121`).

## Remaining concrete gate issues

1. **A capped agent turn can be counted as complete.** `digest.stream_complete` accepts both `finish_reason=stop` and `length` (`strata_bench.py:230`), and `agent_turn_complete` requires only that the stream ended, usage and prompt counts are positive, and `output_chars > 0` (`:253–261`). At the 8,192 total-token cap, a response with a nonempty but unfinished answer body is therefore appended to the next turn and can contribute to `complete_sessions`, cache statistics and session summaries. The six-turn gate does not require a normal stop or a minimum/body-completeness check. This is a concrete completion-label false pass if thinking consumes most of the cap and leaves only a fragment. Keep the timing sample if desired, but a capped turn should remain visibly truncated and should not make the *task session* complete without a separate continuation/completion rule.

2. **Standard chat/prompt rows accept less than a completed, usage-backed SSE response.** `digest.ok` means only “no client error and at least one content/reasoning chunk”; it does not require `[DONE]`, a final `finish_reason`, or actual `usage.completion_tokens` (`strata_bench.py:205–231`). `digest` falls back to the number of nonempty SSE chunks as `generated_tokens` when usage is absent (`:208,231`), but `run_chat` and `run_prompt` include rows using only `d["ok"]` (`:489–529`). The reported unit then says generated tokens even though the fallback is chunks. In addition, malformed `data:` JSON is silently skipped (`:171–174`), so a partly damaged stream can retain a first chunk and be summarized if iteration closes without a transport exception. The strict long-generation gate avoids the usage/terminal fallback by requiring integer completion and prompt usage, a terminal marker plus stop/length, body length, and an engine clock; the base short-chat/prompt path has no equivalent gate. `serve_load.one` is looser still: it records no finish reason or `[DONE]` state and leaves SSE chunk count as its token count unless a usage event arrives (`serve_load.py:24–56`). Its burst results should remain explicitly best-effort on terminal accounting.

3. **Long-generation exit status is not a uniform signal for classification qualification.** The classifier requires at least three complete runs (`long_generation_bench.py:78–88`), but `main` returns nonzero for an unqualified class pair only when `suite.runs >= 3` (`strata_bench.py:1282–1286`). For `--long-generation-only --runs 1` or `--runs 2`, if all attempted samples pass individual eligibility but the pair cannot satisfy the minimum-run rule, the command writes `classification.qualified=false` and exits zero. This may be a useful pilot-execution exit, but it is a false pass if callers interpret the exit code as “the requested strong/weak screen qualified”; the minimum-run condition needs to be explicit in the exit contract or a separate execution-success status must be used. Runs 3+ already return failure for an unqualified pair.

## Truncation and MTP interpretation

Long-generation intentionally accepts `finish_reason=length` as a valid *performance and observed-agreement* sample, provided the usage, body, input, freshness, engine-clock and draft-count gates pass. It writes `quality_qualified=false` and the classifier scope says observed draft agreement only (`strata_bench.py:451–458`; `long_generation_bench.py:50–75,86–89`). This is a reasonable separation: cap-limited output may be useful for throughput/agreement, but the row does not establish that either the 80-test module or the Japanese story was completed correctly. The 512-character gate detects that some answer body escaped the reasoning channel; it does not establish task completion or quality. Preserve `finish_reason` in any comparison and do not present pair qualification as output-quality qualification.

The source's offer/accept counters are verifier agreement counts, not a count of candidates visibly emitted. The serving loop adds `T-1` offered and `a` accepted before it caps emitted tokens or stops on EOS (`src/program/generate.cpp:5965–5975`); as R527 already records, the final verified window can contribute accepted positions beyond the visible output boundary. Under the current spec-4/suffix-off screen, at most the final window's un-emitted tail changes that boundary. Thus the regular-code/varied-prose labels are valid only as observed MTP agreement over verified proposals under this thinking-enabled model/config; they are not an emitted-token speedup or a prompt-intrinsic “strong/weak” property. Current classification requires every row in each arm to be eligible, at least three runs, regular-code rates >=60% in every run and varied-prose <=40% in every run; it reports agreement only (`long_generation_bench.py:78–89`).
