## Where counters come from and their meaning

In fork `src/program/generate.cpp:6761-6846`, each speculative round verifies a window of size `T`; drafts offered for that round are `T-1`, and accepted drafts are `a`, the matching prefix before the first mismatch. The first native-pack window is forced to `T=1`, so it contributes a round but zero proposals. The loop stops at the request output cap or EOS, and the final verification may have a smaller realized contribution because generation stops at the cap. Fork lines 6875-6888 report totals, accepted/offered ratio, mean accepted drafts per round, and a histogram of accepted drafts. Thus `accepted/offered` uses draft proposals as denominator; `accepted per round` uses all rounds and includes the initial zero-proposal round. They answer different questions. Avoid calling the latter an acceptance rate.

The engine protocol's per-request `DONE` reports generated count, accepted drafts, and offered drafts (`src/program/generate.cpp:6152-6159`). `serve/server.py:2478-2495` converts these to API timings (`draft_n`, `draft_n_accepted`) and computes decode throughput from engine generated tokens over engine decode time. `tools/strata_bench.py` in upstream already preserves these per-request fields in `digest()` (`:178-201`), but does not use a long-output request in its suite. Its streaming client counts `completion_tokens` from usage where available (fallback stream-piece count is not a token count); `--think` is supported by omitting the explicit reasoning-off overrides (`:128-175`). Extend report/JSON rows to retain the raw offered and accepted counts and compute the ratio only when offered > 0; do not combine samples' percentages unweighted. The `timings` are engine request aggregates, while wall time/TTFT have different boundaries.

Thinking is generated completion. Upstream `chat()` sends `max_tokens` and temperature zero; when `think=False`, it explicitly sets `reasoning_effort=none` and `enable_thinking=false` (`:128-139`). With `--think`, these overrides are omitted and the model's normal thinking behavior is used. Fork server `Service.prepare` returns a single `max_new` budget for the generated response (`serve/server.py:2145-2206`); request-level thinking budgets are separately validated by `reasoning_budget` (`:1739` onward) and can constrain internal thinking. Use an explicit ample reasoning budget only if the deployed service config applies one; record the effective setting. Do not treat `max_tokens=1024` as 1024 visible answer tokens. If the intent is about 1K generated tokens total, request a cap around 1152 or 1280, track actual `completion_tokens`, and require a predeclared actual-count floor (for example 900) for inclusion. EOS, refusal, or short answer may still end early; retain and label those runs as short-output/ineligible rather than silently rerunning until a favorable length. Keep the benchmark request's total context plus cap within configured context.

## Workload design

Use two deterministic, natural instructions with a shared request shape, temperature 0, same thinking setting, same max output, same system message and repeated independent request tags. Avoid token forcing, logits bias, constrained decoding, artificial draft injection, or changing model math. Those can directly manipulate MTP predictions and cease to represent normal generation.

- Candidate high-copy workload: ask for a substantial continuation of a repetitive, machine-readable but naturally useful artifact, such as a Markdown glossary where every entry has the same fields and a fixed schema, with many entries and consistent formatting. Provide a short seed set and ask it to continue with new terms, not copy a supplied 1K-token answer. A second candidate is a long, regular code file with repeated declarations or table rows. These may provide regular local continuations, but that is a hypothesis only; inspect actual output and offered/accepted counters before calling it high-acceptance.
- Candidate low-copy workload: ask for a detailed, varied narrative analysis of a novel scenario with several independent evidence points, counterarguments and a synthesis, requiring distinct paragraphs and examples. Do not make it contradictory or ambiguous merely to lower draft matches. A naturally varied prose answer may produce lower draft agreement, but the prompt cannot guarantee this; classify it only from measured proposal counts and rates.

Both should ask for enough substance to continue through most of the cap without explicitly commanding padding or repetitive filler. Set a modest sample count per workload (at least 5 independent requests for screening, more for a stable comparison), and interleave/alternate workload order to reduce thermal/order bias. Keep exact prompt bytes or canonical request-body SHA, source revision, MTP configuration, server/model identity, and every row's finish reason, actual input/output tokens, timing, draft counts, and output digest. The currently frozen stock suite starts/reuses a single server for its suite, so its measurements are warm-process; label any new test accordingly unless the implementation intentionally adds separately supervised fresh-process arms. Do not mix prompt-prefill duration into decode throughput.

Thinking-enabled comparisons should be a separate matched condition, not mixed into a non-thinking average. Thinking can change both output length and token-distribution/task behavior. If desired, run each workload with thinking disabled and enabled as a 2x condition, holding every other field fixed. Record `reasoning_effort`, `enable_thinking`, effective reasoning-budget setting and actual total completion tokens. For the benchmark goal described here, the primary condition can simply be thinking on; the non-thinking pair is optional diagnostic context.

## Suggested integration and decision rules

A compact opt-in `--long-generation` suite section in upstream `tools/strata_bench.py` is the natural integration point; keep `bench.sh` as its existing thin wrapper. Add a fixed cap constant or explicit CLI option and named prompt definitions, then reuse `chat()` and `digest()` so request handling, streamed usage, MTP counters and timing fields remain consistent. Preserve old formal benchmark defaults/results. The output report should show each independent row, median/range of engine decode tok/s, actual generated tokens, TTFT, offered and accepted draft totals, pooled accepted/offered ratio, per-request ratio, accepted drafts/round if the engine provides it, and finish/correctness status. Upstream API currently exposes totals but not the accepted-per-round histogram; do not imply that histogram is available via HTTP without additional instrumentation.

Require all of the following before describing a workload as high or low acceptance: nonzero and substantial offered count; actual output meeting the declared floor; successful finished response; and repeat observations whose individual rates support the classification. Define categories by observed rate thresholds before running, or report rates continuously without categorical labels. Use per-request counts and a pooled ratio `sum(accepted)/sum(offered)`; also report median per-request ratio to show spread. Zero-offer rows have undefined acceptance rate, not zero. Present speed with individual samples and a robust summary, not a single best run. High/low describes MTP proposal agreement for that measured model/config/prompt/decoding setup, not a reusable property of the prompt alone.

For MTP speed attribution, a useful comparison also needs a matched no-MTP arm with the same model, input, output cap, sampling and server conditions, plus output/correctness comparison appropriate to the changed generation path. Greedy temperature zero reduces sampling variation but does not establish universal bit identity. Report observed outputs and checks; do not require or claim universal output bit-identity across speculative and non-speculative paths. Keep correctness/quality outcomes separate from speed. No result from the proposed workload should be treated as an official `bench.sh` score unless the suite itself records it as such and the report identifies the exact modified upstream revision.
