# R209 — default decode pool dependencies and conditional 70 tok/s budget

Date: 2026-10-10 (Asia/Tokyo). Read-only analysis of two closed, same-sequence 32,768-actual-batched-position diagnostics (default-auto baseline and pool-counter build with `--pool-tasks 0`), pinned v0.1.41 source and prior closed reports. The baseline and telemetry records are separate processes on the same boot and have matched input/output/checkpoint evidence. Both explicitly exclude their timed requests from clean throughput; neither is a scheduler candidate or performance-eligible run. This report makes no performance or Amdahl claim. No source edits, builds, tests, GPU/model/profiler runs, live process/device inspection, services, Git operations or cleanup were performed.

## Result

The latest same-route diagnostics expose two useful quantities for each verification window: `CPU` dispatch host elapsed and existing GU / feed-forward quantization / Down pool-phase elapsed. On the fresh-first request they are respectively 138.41 ms/window and 98.911 / 0.332 / 39.147 ms/window; the three phase spans sum to 138.390 ms/window in this one receipt. On the two restored requests CPU dispatch is 145.04 and 145.81 ms/window; GU / quant / Down spans are 104.159 / 0.363 / 40.493 and 104.009 / 0.330 / 41.448 ms/window. All are host-observed intervals. The pool phases include work-completion and park barriers, task publication/claiming, and can overlap GPU activity. Their near-equality to CPU dispatch here does not make them exclusive CPU busy time, GPU service, or a decomposition of physical wall.

This makes pool scheduling and phase-architecture work both reasonable hypotheses to discriminate, but it does not show which is on the exposed critical path. The logs do not report per-worker busy time, task claim distribution, cache misses, DRAM bytes, GPU kernel service or a dependency-resolved overlap graph. Packed expert-blob bytes are logical extents submitted to pool jobs. They do not measure physical RAM traffic. There is no safe path from these numbers to a clean speedup bound.

## What 70 tok/s would require

For 64 visible decode outputs, 70 tokens/s allows at most `64 / 70 = 0.9143 s` of decode wall, or 14.286 ms per emitted token. If the same MTP grouping persisted, this is 33.862 ms per 27-window fresh-first request window and 36.571 ms per 25-window restored request window. These are request-wall budgets divided by observed window counts; they are not independent per-phase allowances and they change if MTP acceptance/window count changes.

Keep the clean throughput references separate from this diagnostic. R203 reports a clean baseline mean of 3,886.9 ms / 16.47 tok/s for fresh-first and 2,951.2 ms / 21.69 tok/s for restored continuation. Against that clean baseline, 70 tok/s would require reducing the 64-output decode segment by about 2.973 s (76.5%) fresh-first or 2.037 s (69.0%) restored. These are arithmetic target gaps against R203's clean samples, not claims that a proposed change can supply them.

For scale only, the telemetry diagnostic's 4,816.4 ms fresh-first request would need 3,902.1 ms saved (81.0%) to meet the target; the baseline partner's 5,039.9 ms would need 4,125.6 ms (81.9%). Mean of the two pool0 restored times is 4,380.0 ms, needing 3,465.7 ms (79.1%); the baseline partner mean is 4,551.95 ms, needing 3,637.7 ms (79.9%). These runs are explicitly validation/phase diagnostics and are not clean speed measurements.

A deliberately restrictive conditional calculation helps size the question without answering it: if CPU dispatch were one fully exposed, serial interval per window, removing the entire logged CPU interval with no change in GPU execution or overlap would remove 3.737 s from the fresh-first windows and 3.636 s from restored windows. That hypothetical ceiling nearly matches but falls short of the diagnostic fresh-first gap (3.902 s) and exceeds the restored gap (3.466 s). The assumption is unverified; GPU work may overlap these host intervals and dispatch changes may alter queue idle. Therefore this arithmetic is not an Amdahl fraction, a strict achievable bound, or evidence that CPU work is/is not sufficient. It only says a pool-only hypothesis should be tested against physical request wall rather than inferred from the host span.

## Safe scheduling and architecture constraints

The frozen pool implementation at `src/kernels/cpu/pool.cpp` (SHA-256 `f789078f…`) provides concrete dependencies:

- `run_split_multi_native` batches distinct experts to fit its split buffers, launches the GU row-range phase, waits for that phase, serially quantizes each expert/token FF intermediate into the activation type used by Down, then launches and waits for the Down row-range phase (`:759–787`). Down cannot consume an intermediate before its paired GU results and FF quantization exist.
- `run_phase` waits for workers to be parked before publishing a batch, lets workers and optionally the caller drain row-range tasks, waits for all tasks to finish, then waits for workers to park again (`:688–697`). The task worker maps row intervals across expert output rows; a task range can span expert boundaries (`:665–684`). Counters include these barriers and scheduler overhead. They contain no per-worker active time or task-work histogram.
- `expert_source.cpp` constructs per-layer unique expert jobs from routed tokens, assigns the token activations/output rows and calls the native pool (`:2765–2797`). The next transformer layer depends on prior layer outputs; verifier/draft progression and MTP acceptance determine which tokens and windows proceed.

Thus the safe scheduling search space is within independent row/expert work of one layer's current phase, while preserving exact job coverage, one writer per output range, the GU → activation-quantization → Down dependencies, phase completion before scratch/output reuse, output-combine semantics, and per-layer order. Reducing phase barriers or overlapping per-expert GU/Q/Down is an architectural pipeline change: it needs explicit completion/lifetime edges and unchanged numerical formats/rounding, not just a changed task order. Reordering across layers, across verifier windows, or across MTP draft/acceptance boundaries would change data dependencies or the amount of work and cannot be treated as a scheduler-only test.

Byte/work claims must remain at the right level. The latest decode receipt gives actual per-window logical blob extents, while R207's corrected prefill receipt gives about 190 GB logical queued expert bytes for a different 32K prefill request. Neither is a measure of cache misses or DRAM traffic. R206's dimensions/formulas are hardware- and format-level work estimates; it explicitly lacks same-request default route counts and memory transactions. Consequently no current bound says how many packed bytes, quantization operations, row operations or cycles an architectural change could remove from physical service. A design can safely claim a reduction only in a named logical operation/extent proven by the same-run route ledger; it cannot translate that into milliseconds until traffic/service and overlap are measured.

A valid next comparison should keep the current default-auto task mode and output/MTP path fixed, use at least 32,768 actual batched positions, and retain separate fresh-first and restored samples. Join each request's physical decode wall, 27/25-style window count, CPU dispatch, GU/Q/Down spans, exact pool logical bytes, MTP counts, output/logprob/state result and binary/source identity. If the candidate changes window count, accepted drafts or the byte/job denominator, classify it as a different-work comparison and do not use its apparent speed as a like-for-like scheduler effect. Add per-worker or GPU timing only after a specific unanswered dependency question remains; validate timer ordering, and record physical memory transactions separately before claiming a DRAM-bound architecture case.
