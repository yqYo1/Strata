## Decision-relevant result

The board's advertised PCIe interface is not the installed path. Intel lists B570 as 10 GB GDDR6, 380 GB/s memory bandwidth and PCIe 4.0 x8. The closed post-reboot topology record instead shows the GPU attached through an external PCIe 4.0 x4 path, with every external ancestor x4. Its 128b/130b encoded link ceiling is 7.8769 GB/s before packet and software overhead. A separate older Strata note calls about 6 GB/s an effective transfer rate, but the inspected closed topology receipt says application bandwidth was not remeasured and contains no raw transfer benchmark. Treat 6 GB/s as a prior planning observation, not a current validated ceiling. The GPU leaf's 2.5 GT/s x1 sysfs reading is explicitly cautioned against in that topology record; it is not the upstream path measurement.

The strongest real workload result remains a coarse whole-route prefill contrast: native expert-copy-on was associated with 20.36% higher pooled 32K prefill throughput than baseline in a quiet same-day sequence. It does not establish PCIe saturation or isolate copy service from CPU grouping, queue behavior or their interaction. No accepted current device-DRAM bandwidth, actual staging-byte total, or real-model oneMKL internal-kernel share was found. Thus the present evidence cannot choose scheduling versus an architectural kernel change by ceiling comparison. It does justify measuring staging and GEMM demand separately before making that choice.

## Workload geometry and arithmetic bounds

R203's quiet v0.1.41 workload used a configured 32,768-token prompt, four 8,192-position chunks, 48 layers and 128 expert slots. Its prompt accounting says 32,767 positions were batched and the final input position was handled separately. Consequently it is a close 32K reference but does not satisfy a strict future requirement of at least 32,768 *batched* positions. The four chunks times 48 layers give 192 layer-chunk opportunities per request; they are not 192 identical calls and do not reveal routed experts.

For the observed native Down matrix shape `N=2560`, `K=640`, one expert matrix has 1,638,400 values. For a type-20 IQ4_NL block (32 values in 18 bytes), this is 51,200 blocks and exactly 921,600 compressed bytes per expert matrix. Expanding to FP16 writes 3,276,800 bytes. One Down GEMM for an expert receiving `M_e` rows performs `2 × M_e × 2560 × 640` nominal multiply-add FLOPs. Across a layer-chunk, use `R = Σ_e M_e` and `F_down = 3,276,800 × R` FLOPs. Actual `R`, expert identity/count per chunk, and type-20 dispatch count were not captured in the closed census. Do not substitute a guessed top-k or assume all experts are active.

The following are conditional scale calculations, **not measured route totals**. Earlier installed-pack metadata recorded type-20 Down in 39 of 48 layers, but current loaded-pack identity and per-chunk runtime calls are unproven. If all 512 experts in each of those 39 layers were type-20 eligible and actually called in all four chunks (a deliberately loose combinatorial ceiling), that would be 79,872 DQ calls: 73.610 GB compressed Down payload and 261.725 GB FP16 output writes. At 380 GB/s, the output writes alone have a 0.689 s ideal bandwidth floor; reading the compressed payload too raises the simple byte floor to 0.883 s. If the GEMM rereads every expanded matrix from GDDR, another 261.725 GB gives a 1.571 s floor. These floors assume sustained peak bandwidth, count only Down, and do not account for cache reuse, actual call distribution, other MoE projections, activations, QSA, synchronisation, or any compute time. They are not predicted request time.

For a single type-20 Down matrix, 0.9216 MB of compressed payload divided by the Gen4 x4 encoded ceiling is about 117 microseconds; at the provisional 6 GB/s figure it is 154 microseconds. This is only the serialization time for those Down bytes. A staged expert blob also contains other tensors, and the DQ input bytes are not evidence that those same bytes were transferred once per DQ call. Likewise the 3.2768 MB expanded matrix is a destination extent, not observed DRAM traffic; if each GEMM consumes it from external memory, its ideal read floor is another 8.62 microseconds at 380 GB/s. Cache residency may change that. Do not add overlapped host worker sums, GPU waits, copy-queue activity and request wall.

R200 explicitly limits its byte arithmetic to returned type-20 Down helper extents: `staging_bytes=UNOBSERVED`; no physical memory transactions, staging transfers, cache state, timing or async completion are measured. Its aggregate records also lack chunk/expert identity. R186's pack metadata is not a runtime pack identity. These boundaries prevent the scenario above from becoming an actual transfer lower bound.

## What the closed measurements establish

R203 reports baseline fresh prefill at 79,613.2 ms mean / 411.59 tok/s across six independent processes. In the quiet same-day native-copy sequence, native-copy-on pooled throughput was 20.36% above baseline; off was effectively at baseline (-0.02%). This is intervention-associated whole-request evidence, not an isolated PCIe measurement. Host accounting in the same request class reports copy-worker time summed across workers of 10,124.8 ms, group GPU-wait host time of 29,353.9 ms and whole wall of 72,853.2 ms. These scopes overlap or represent different work; they are not additive shares, nor does dividing worker time by wall yield a PCIe service estimate.

The only retained detailed phase report found in R203 was from v0.1.40.2 under diagnostic tracing, not the current route. It ranks coarse queue-timeline intervals, with queue idle gaps attributed to the open phase; it cannot identify current device kernel time. R205 also found current marker samples can be invalid (including inverted/wrapped timestamps). Do not use those intervals as ceilings or clamp them. The Intel joint-matrix guide describes XMX programming, but it supplies no B570 runtime rate for this route: [Intel joint matrix optimization guide](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2024-1/joint-matrix.html).

## Bounded measurement that can resolve the choice

The root owner should run the next comparison on the serially qualified v0.1.41 configuration, preserving current correctness gates. Require at least 32,768 actual batched positions and record prompt/tokenizer/model-pack/build hashes, actual chunk extents, 48-layer geometry, per-layer/per-chunk unique routed experts, Down type and returned DQ calls. Record the exact expert blob bytes queued, copies completed, and cache hit/miss/reuse counts; do not infer staging bytes from Down tensor extents. Keep individual request samples and compare against a quiet fresh-process control.

First obtain an independent transfer roofline with preallocated pinned host buffers and device buffers, large enough repeated transfers to amortize setup, separate H2D and D2H, multiple byte sizes, and enough repeats to report every sample plus median. Verify completion before buffer reuse and count only bytes whose copy completion succeeded. Compare effective payload rate to 7.8769 GB/s, not the board's x8 label. Keep host staging/copy time and device wait distinct.

Then measure device-memory and GEMM ceilings separately. Use an explicit streaming read/write working set larger than the last-level cache for sustained device-memory bandwidth, with validated event ordering and a long enough steady interval; retain both event durations and independent wall/device-span values. Independently benchmark the exact oneMKL FP16-input/FP32-output shapes and M histogram observed from the route census, including actual K=640 and N=2560 Down plus the real gate/up shapes, under the same driver/oneMKL build and allocation regime. Report M=rows per expert, number of calls, warm/cold weight cases, correctness, and per-sample latency/throughput. A generic peak TOPS number, one large GEMM, or sum of overlapping kernels cannot stand in for the production shape distribution.

Use a timer only after its timestamp domain and monotonic ordering are validated on the actual backend; reject failed, missing, wrapped or `end < start` samples without repair. Keep the R205 invalid intervals excluded. Join any command-level trace to host call IDs and dependencies; preserve unmatched commands as unattributed. Do not run trace-heavy timing as the throughput control.

Interpretation: if measured H2D bytes/rate and transfer wall approach the validated transfer roofline while GEMM and device-memory measurements leave headroom, test queue/stager scheduling first. If staging stays far below the link ceiling and the observed GEMM shapes consume a large fraction of measured device memory/compute service, focus on GEMM/dequant architecture. If neither dominates, keep host grouping, allocation, launch gaps and overlap as separate hypotheses. The existing 20.36% route change is enough to motivate this attribution, not enough to decide it.
