## Decision-useful result

There is one useful, narrow CPU service datum for the actual IQ4_NL Down20 format: the closed NT1 native-service calibration reports 25-round medians of 0.0805–0.0846 ms per Down20 expert call on actual host-resident weights with fixed synthetic activations. It is a measured NT1 component service interval, not a CPU instruction ceiling, not physical DRAM bandwidth, and not a bound for the decode route. In reciprocal terms that corresponds to about 11.8–12.4 thousand serial fixture calls/s; its 921,600-byte logical weight extent per call divided by the interval is about 10.9–11.4 GB/s of logical packed extent. Both reciprocal rates are derived descriptions of that fixture timing, not application throughput or memory-controller rates.

The hardware evidence does not identify the CPU-side limiter. Round53 has effective host stream measurements (single-thread read 26.9 GB/s and NT copy 30.8 GB/s; six-core dependent read 37.7 GB/s and NT copy 37.6 GB/s). These show that the host can sustain those particular stream kernels; they are neither absolute memory ceilings nor comparable measures of IQ lookup/dot service. Conversely, packed bytes and dense-equivalent MAC counts do not expose the actual memory transactions or retired instructions. A useful CPU roof for native IQ4_NL needs a service distribution from the actual NT mix plus worker activity and counters on that same kernel interval.

The closed matched pool0 request is diagnostic evidence, not that roof. Its restored decode CPU dispatch spans are 145.04 and 145.81 ms/window; GU is 104.159 and 104.009 ms/window, FF quantization 0.363 and 0.330 ms/window, and Down 40.493 and 41.448 ms/window. At 25 windows for 64 tokens, the 70 tok/s budget is 36.57 ms/window. The reported CPU phase spans exceed this arithmetic budget by roughly fourfold, but are nested with GPU work and include waits/dispatch; Down also aggregates formats and NT groups. They are not exclusive worker-busy time, not all IQ4_NL, and not exposed request critical-path service. They motivate attribution, but do not decide scheduling versus architecture.

## Exact work and dispatch contract

For the inspected native pack geometry, type-20 IQ4_NL Down is `N=2560` output rows by `K=640` input values. Each weight block covers 32 values in 18 bytes (FP16 scale plus 16 packed nibbles): 20 blocks or 360 packed bytes per output row, hence 921,600 logical packed weight bytes per expert job. Dense-equivalent dot work is 1,638,400 multiply-accumulates per activation row; for an expert with `NT` grouped rows it is `1,638,400 × NT` MACs. That is a normalized work count, not the literal instruction count or a claim that a MAC maps to one CPU instruction. The Q8_0 activation vector is 680 bytes per token and the FP32 output is 10,240 bytes per token; the activation is shared across output rows. Cache reuse and line fetches mean none of these logical extents determines physical DRAM traffic.

The frozen native dispatch defaults to `mt_min=2`. For IQ4_NL Down at NT1, the wrapper calls GGML's single-row `vec_dot_iq4_nl_q8_0`; for NT≥2 on AVX2-capable CPUs it selects Strata's IQ4_NL AVX2 multi-token routine unless the explicit disable setting is present. If the AVX2 gate is unavailable, dispatch returns to GGML. Therefore the measured NT1 Down20 arm characterizes the existing GGML NT1 route. It does not characterize the grouped NT2–4 custom route, which is a different kernel with a different decode reuse pattern.

Pinned GGML x86 AVX2 source handles two blocks per iteration, unpacks the low/high nibbles, maps them through `pshufb`, performs signed byte dot/madd operations, converts integer partials to FP32 and scales/accumulates. The grouped Strata routine decodes IQ codes and prepares absolute weights once per block, then applies each activation row's signed Q8 values and accumulates; it has separate NT1/2/3/4 instantiations. This has a clear instruction-versus-data hypothesis: NT1 pays lookup/unpack per row-block; NT2–4 should amortize that decode across grouped activations, while still doing dot products and reading each token's activation. It does not establish which part dominates in the running binary. The host service v3 fixture excludes input quantization and uses synthetic activations, so its FF quantization and complete service are not model input preparation or route-conditioned inference timings.

The NT1 calibration evidence is precisely limited. Four fresh processes, 25 samples per arm/cohort, six distinct pinned CPUs, and 384 selected actual IQ3_S expert blobs were used; the aggregate selected blobs total 756,940,800 bytes, while each train/holdout cohort working set exceeds L3 capacity. This makes the fixture useful for repeated resident-weight service outside a whole-cohort L3 fit. It does not prove each weight load reached DRAM, nor represent cold first-touch, 32K/full-context routes or the online mixture of NT1–4. Correctness checks cover byte-exact NT1 GU and Down20 versus independent GGML, production quantizer bytes, guards, repeats and pool partition/results. NT2–4 correctness/performance are not qualified by this run. All pool fit/holdout gates failed; its 14.8–17.5 ms per 192-job cohort durations cannot be divided by jobs and called per-expert latency.

## How the evidence bears on scheduling versus architecture

Scheduling can change when expert rows are assigned, wait/barrier time, core occupancy, and which working sets overlap. It cannot remove the same routes' IQ4_NL value lookups, dot products or logical weights by changing order alone. NT grouping is a work-sharing dimension already in the source, but there is no NT2–4 service measurement in the cited calibration and the same-request counters do not expose per-expert NT or per-worker active time. “Architecture-bound” would require evidence that IQ4_NL worker execution is exposed on the critical path and near a measured instruction/cache/memory roof. “Scheduling-bound” would require evidence that the same work is materially delayed by idle workers, barrier/dispatch or tails, and that reducing those spans reduces physical request wall. Current pool-phase sums establish neither condition.

Do not compare the 40.5–41.4 ms aggregate Down span from the current diagnostic with the 80.5–84.6 µs type-20 NT1 component median to infer a number of type-20 calls: the request Down span combines types and NT values, while its host phase interval is nested with GPU execution. The ~3 GB/window expert-blob figure is logical submitted extent, not DRAM traffic. Multiplying the type-20 extent by an older route census or treating it as one read per call would also invent current-run call and transaction counts. The source-level 39/48 layers eligible for type 20 is eligibility, not proof those layers made a Down20 CPU call in this particular request.

## Smallest decisive CPU measurement, after current owner runs close

The next useful packet is one format-aware CPU-service study, not another generic stream benchmark or a kernel rewrite:

1. On the same frozen build/host and actual IQ4_NL expert-weight cohort, measure direct Down20 calls at NT1, NT2, NT3 and NT4 with the exact production row code and real routing-derived M/NT counts. Keep input preparation, direct kernel service, pool batch wall, pool CPU dispatch, worker-active spans, wait/barrier spans and tail-to-last-worker separate. Run both a repeated cohort and a rotated working set with total selected bytes well beyond LLC; report sample distributions and correctness per cell. The current NT1 synthetic-activation calibration remains a valid control, not a substitute for the grouped cells.
2. In a separate counter arm over exactly those kernel intervals, collect actual cycles and retired instructions per worker plus model-specific memory-controller read/write bytes and cache-level events if available. Tag counters by phase/worker and retain enabled/running or multiplex-coverage, affinity, ISA, compiler flags and source/binary identities. Compare bytes/call to 921,600 logical bytes only as a diagnostic: the difference is expected if blocks hit cache or line traffic differs. Compare cycles/instruction counts to the exact AVX2 code path and a measured frequency; do not use dense FP FLOPs as the CPU compute roof for this integer lookup kernel.
3. Keep a standard large-array STREAM result as a system-wide sustainable RAM comparison, with arrays comfortably larger than cache and exact run rules; keep it separate from the kernel's physical-byte measurement. The current round53 read/copy probes are useful baselines but not STREAM qualification or maximum-bandwidth proof.
4. Relate these components back to the same clean, matched default model requests only after per-format NT histograms and per-worker busy/wait/tail data exist. The diagnostic's CPU phase and physical request wall remain distinct denominators. If PMU/DF counters cannot be collected under the current host policy, report that gate as unavailable and do not replace it with blob-byte arithmetic.

A credible result could say either “this exact production-style IQ4_NL NT cell runs at X service under Y residency and Z worker concurrency” or “controller bytes / core instruction counters account for the interval.” It still would not by itself be a universal CPU peak or a full-model tok/s result.

## External measurement methods and transfer limits

The upstream GGML IQ4_NL author’s implementation discussion reports that a CPU SIMD lookup table was faster than polynomial decode, and upstream’s AVX2 `vec_dot_iq4_nl_q8_0` provides the exact table-lookup style present in the NT1 fallback. Its benchmark notes pair quantized-dot microbenchmarks with model `pp`/`tg` measurements, but their Ryzen 7950X and thread counts are not transferable to this 5600X or Strata MoE. This is useful implementation evidence, not a service estimate. [GGML IQ4_NL PR and benchmark notes](https://github.com/ggml-org/llama.cpp/pull/5590)

A recent independent `llama-roofline` implementer tool illustrates the right comparison for dense single-stream decode: measure a sustained read ceiling, measure actual backend throughput across models and thread counts, and fit performance against resident bytes. Its own methodology treats the measured bandwidth ceiling as a lower bound, says quant formats can sit below it due to unpacking, and explicitly flags MoE as outside its dense roofline because only routed experts are read. That makes it a helpful measurement method but also an explicit warning against applying its dense `bytes/model` equation to this MoE expert-pool schedule. Its IQ4_NL format comparisons are on Gracemont, not this host. [llama-roofline method and caveats](https://github.com/manunicholasjacob/llama-roofline)

STREAM's reference run rules require each array to exceed four times the aggregate last-level cache used (or one million elements, whichever is greater), so its result is not a small-array cache benchmark. [STREAM reference and run rules](https://www.cs.virginia.edu/stream/ref.html)

AMD uProf documents core PMC, IBS, L3 and Data Fabric counters, and says event availability depends on the processor-specific PPR and may be reduced by OS/BIOS reservations; this is the correct class of source for investigating instruction and memory-system limits on AMD. The guide's headline Zen3 metric table is for EPYC, however; it cannot supply event encodings or a prequalified ceiling for this Ryzen 5 5600X (R95 identifies family 19h model 21h). Any future event set must be checked against the matching desktop-family PPR, then passed through the local host’s access gates. [AMD uProf hardware sources](https://docs.amd.com/r/en-US/57368-uProf-user-guide/Hardware-Sources), [AMD uProf guide](https://docs.amd.com/r/en-US/57368-uProf-user-guide)

Intel VTune's Memory Access guide is a clear description of what a useful memory diagnosis looks like: measure achievable DRAM bandwidth, view time-correlated memory-controller (uncore) read/write traffic, and correlate that with core events/code sections. But VTune is not being nominated as an available instrument here: the local R16/R74 records report its software sampling blocked by ptrace scope, and Linux perf access was recorded at `perf_event_paranoid=4` without effective `CAP_PERFMON` in R95. Existing gprofng clock sampling failed independently. No permissions, profiler, sysctl or services were changed. [Intel VTune Memory Access overview](https://www.intel.com/content/www/us/en/docs/vtune-profiler/user-guide/2024-0/memory-usage-view.html)
