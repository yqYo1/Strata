## Assessment

The committed fix closes the R251 schedule mismatch by resolving the outer prefix's first-chunk length against the same temporary `layer_cache` that each subsequent `run_impl` sees. Its outer `all_cached` predicate is now `layer_cache.slots() >= g.n_layers * g.n_expert`, matching `run_impl`'s `m.cache->slots() >= m.g->n_layers * m.g->n_expert` after `m.cache = &layer_cache`. The first-chunk decision expression, `m.T`, and `n` fallback match the unchanged inner `chunk_len(0)` logic. For layer counts above one the temporary cache normally fails the full-model cache test, so an unset `STRATA_PREFILL_FIRST` yields the full `m.T` first chunk both outside and inside. For a one-layer geometry, both predicates see the same threshold and still agree.

The added runtime guard in `run_impl` rejects a chunk when `c0 < G && c0 + T > G`, before the chunk's residual input upload or later output callback. With the fixed shared first-chunk schedule, the prefix rounding formula makes every partial `G` a cumulative chunk end. If an unexpected divergence nevertheless occurs, the guard prevents the crossing chunk from forming either its negative host input offset or negative host output offset. It can reject only when execution reaches that chunk: the residual allocations, expert layer-cache setup/load, and any earlier complete chunks may already have occurred. It is a bounds backstop, not an allocation preflight or rollback of earlier work.

## Independent boundary and span check

I checked the committed formulas and guard against the archived exact-extraction harness and receipt, rather than rerunning tests. The harness contains the original and fixed outer calculation, unchanged inner `chunk_len`, the actual guard expression, and a span oracle. It builds separate optimized and UBSan host executables, then runs each with `STRATA_PREFILL_FIRST` unset, `0`, `256`, `1`, `8192`, and `-1`. Each process covers 8,064 combinations: 14 prompt lengths (from 1 to 262,144 including 262,143), six `T` values including `T=257` and several short-tail cases, six original cache-capacity values around the `48*512` threshold, and 16 requested-prefix values including below-zero, exact boundaries, around `F`, around `T`, `n-1`, `n`, and above `n`.

The receipt records 12 clean fresh processes and 96,768 case evaluations total (the 8,064 matrix is repeated across six environment values and two build modes; these are not unique configurations). Both builds pass. For unset `FIRST`, the old calculation creates 416 invalid row spans in each process and the copied new guard rejects those 416 before the crossing residual span; the fixed calculation has zero invalid spans. With explicit `FIRST`, old and fixed outer `G` agree and the fixed spans remain valid. The named `n=32,768`, `T=8,192`, full-original-cache, requested-8,192 example gives old `G=256` and fixed `G=8,192` when `FIRST` is unset.

One receipt field needs careful reading: `named_unset_original_first_host_offset` is computed as `-oldG` in every process. It is a negative offset for the actual attempted first host span only in the unset-`FIRST` counterexample, where the first chunk is host and crosses old `G`. Under explicit `FIRST`, the named first chunk can instead be wholly GPU-resident; the arithmetic field is then not an observed invalid host pointer/span. The report README explicitly preserves this correction.

The matrix is broad and exercises exact extracted arithmetic, but it is finite, and the regression is a separate CPU program with stub geometry/cache objects—not a call through the compiled production `run_layer_major`/`run_impl`. It checks address ranges arithmetically without forming an invalid pointer, which is appropriate for the old case. It does not prove every environment mutation, allocation exception, queue failure, or production cache lifecycle.

## Counterexample screen

For positive `n` and initialized positive `m.T`, the resolved first length `F` is exactly the actual first chunk: `F=first` only when `0<first<m.T && n>2*first`, otherwise `F=min(m.T,n)`. If `G=n`, the code bypasses partial-prefix rounding and the complete tail is GPU-owned. If `G<n`, it maps requests below `F` to zero; otherwise `G=F+floor((request-F)/m.T)*m.T`. Thus `G` falls at `F` or a subsequent full-chunk end. Remaining tail rows stay host-side. An exact full-prefix request is the only way to include a short final tail in the GPU plane. I find no formula counterexample for negative, zero, one, equal-`m.T`, greater-than-`m.T`, near-`n`, or over-`n` `FIRST`/prefix values in the source: `atoll`, the clamp, the fallback and the same condition in the inner loop make those cases align, subject to the fixed process environment.

The host-offset bounds then follow for each legal full chunk `[c0,c0+T)`: if `c0+T<=G`, it is GPU-owned; otherwise no split guard has fired, so `c0>=G`, and host offset `c0-G` is nonnegative with end `(c0-G)+T <= n-G`. The callback's host output uses `row-G` on a chunk that is wholly host-owned, so it has the same bounds. For mixed in-place mode, GPU chunks set `m.R` to their persistent device row start; input and output compare equal and skip D2D copies. Host chunks set `m.R` to the existing scratch and preserve the host upload/download path. In the all-GPU in-place case, `F<=m.T` rows reuse the pre-existing `m.R` workspace and new device allocation is `(G-F)*D*sizeof(float)`; when `F=n` for a single short chunk this is zero new rows, with that chunk fully backed by scratch. Mixed mode sets `reused_tokens=0` and allocates all `G` persistent rows, so its host suffix still has the original full `m.T` scratch available.

The CPU harness validates the prefix and host spans but does not simulate actual scratch/device pointer capacities or pointer alias behavior. Source arithmetic supports these extents; device allocator success and real alias correctness remain untested.
