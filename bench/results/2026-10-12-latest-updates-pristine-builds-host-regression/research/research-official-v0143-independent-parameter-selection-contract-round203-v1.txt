## Decision and current gate

The upstream parameter-audit TODO's independent selection and held-out validation remain open. The old 32K recipes were explicit recipes, not a sweep or best-setting proof. R185/R367 already proposed broad conditional matrices; this report narrows those proposals to this actual 6-core B570 PC and separates resource controls by which phase they affect.

Do not execute the batched-prefill selection lane until the exact pristine B570 runtime/allocation path is separately admitted. R169 found the v0.1.43 prefill staging ring polling device-written `done_seq` in host USM (`sycl/src/prefill/prefill.cpp:388-393, 505-524`) and a distinct PLE upload completion word polled from host USM (`:1075-1082, 2330-2362`). Neither chunk size, ring size, pinned mirror budget, ordinary arena/RAM mode, nor compiler choice removes those handoffs. R202's `STEPPED=1, PIPE=0` serializes the verifier window/pool handoff only; it does not serialize batched prefill's stager or PLE polling. Thus `--short-read 65536` can support a **window-route** long-prompt evaluation after R202's decode-path gate, but it cannot be counted as a batched-prefill/chunk experiment.

The conservative B570 window baseline from R202 remains `STRATA_VERIFY_STEPPED=1`, `STRATA_VERIFY_PIPE=0`, `STRATA_VERIFY_NO_HOST=0`, `STRATA_VERIFY_DEVICE_PLAN=1`. For the primary CPU-pool selection, pin `--pcie-frac 0` and one expert source/residency mode so every nonresident expert is served consistently. This does not prove device execution safe; it is a route candidate pending the R202 execution gate. Do not describe an ordinary concurrent polling/volatile handoff as safe or fast on B570 based on parameter settings.

## Controls, their effects, and constraints

**VRAM and resident cache.** The B570 has 10 GB decimal (9.31 GiB) nominal VRAM; earlier machine evidence records 128 GiB system RAM and a Ryzen 5 5600X (6C/12T), while actual free VRAM/RAM at model load remains run-specific. Source default `--vram-reserve-mib` is 700, and `--expert-cache` without a profile is off; with a profile, a zero request becomes auto (`generate.cpp:553-556, 3361-3372`). `--expert-cache auto` sizes from free memory after session/KV/other allocations and reserve. Numeric `--expert-cache N` is a request/budget in units of the largest expert blob, not a promise of N installed slots. Native per-layer admission can yield an actual slot count different from N (`generate.cpp:4381-4415`). The profile and `--expert-cache-per-layer` change which experts are resident/hit, thus both CPU-pool demand and VRAM residency; freeze them in all chunk and worker comparisons. Report `INFO expert_slots`, cache MiB, primary equivalents and actual free VRAM, as well as profile identity.

Intel's Arc notes advise leaving about 1.5 GB VRAM free on `xe` (`docs/INTEL_ARC.md:135-141`), whereas the generic code reserve defaults to 700 MiB. Treat the documented 1.5 GB as a conservative starting headroom constraint, not an optimized reserve. Keep an explicit reserve fixed for a candidate series. Change reserve only as a separately gated admission study, because it directly changes cache size. Never derive a slot count from the product's 10 GB figure alone.

**Host expert source and RAM.** For the pool-served baseline, use one frozen source mode. Without `--stream-experts`, the engine reads a resident expert arena (or `--mmap-experts`' file-backed tier); with `--mmap-experts --resident-cpu-experts --expert-profile`, it can keep the cache complement in RAM, with optional bounded `--resident-budget-gib`. These choices change RAM residency, page-cache/disk traffic and sometimes pinning, not just a worker knob (`generate.cpp:913-918, 4150-4245, 6330-6428`). The default resident arena size and PLE/model footprints consume RAM; the owner-supplied 128 GiB is a capacity figure, not a free-memory guarantee. Keep RAM source policy fixed during cache, chunk and worker screens; log actual arena/resident/mirror bytes, available RAM, and file-read/warm state.

For the alternative streaming route, `--stream-experts` requires a native pack plus `--native`; nonresident experts can be mirrored in pinned host memory up to `STRATA_MIRROR_MIB` (default MemAvailable minus 4 GiB), with `--pcie-frac` controlling the share the GPU reads (`generate.cpp:4153-4167, 4767-4816`). If misses remain unmirrored, `NO_HOST=1` is refused; do not rely on it to service missing experts (`:4836-4843`). On `xe` without `--stream-experts`, the source explicitly defaults PCIe share to zero; a positive explicit value warns that pageable host access faulted/hung an Arc, so keep it zero for the pool baseline (`:2554-2569`). A later mirror/CPU share comparison is a separate route and requires pinned-mirror residency/capability qualification; it must not be mixed into the worker screen.

**Pool workers.** `--pool-workers 0` means source-derived automatic worker count from detected topology; a positive integer overrides it (`generate.cpp:469-477, 891-902, 4245-4260`; `src/kernels/cpu/pool.cpp:437-467`). On the known 5600X, a plausible small CPU selection is auto (0), 3, and 5, but the actual topology available to the process and effective `INFO pool_workers` are authoritative; do not assume 5 is best from the six-core count. By default the host thread also joins the drain. Keep host participation (`--no-host-worker` absent), affinity (`all`), host-core placement and fetch-thread count fixed for the worker screen. Under stepped serial serving, the GPU segment waits for pool work to finish, so worker count can change exposed CPU service time directly; there is no normal CPU/GPU overlap to assume with `PIPE=0`. A lower worker time alone is not proof of higher end-to-end tokens/s.

**Prefill chunk and `--short-read`.** Batched prompt path is selected with `--prefill CHUNK` (native pack required); source default is chunk 0/token path. `--prefill auto` is an admission policy whose default ceiling is 8192. `--prefill auto:16384` and `auto:32768` (or `STRATA_PREFILL_AUTO_MAX`) open those ceilings, still bounded by context and memory. Auto chooses from a candidate list including 256, 512, 1024, 2048, 3072, 4096, 6144, 8192, 16384, 32768, subject to cache/ring admission; it is not an exact fixed chunk (`generate.cpp:564-571, 1790-1798, 5973-6010, 6571-6604`). Fixed numeric requests can be reduced to fit a cache loan or own-buffer VRAM. The own-buffer fallback list is 6144, 4096, 3072, 2048, 1536, 1024, 512 (`:6781-6831`); request lengths are rounded to a 256-token grid and capped by the configured chunk (`:5914-5919`). Record requested, resolved and actual chunk/ring; deduplicate trials that end up at the same geometry. Battlemage chooses no borrowing by default at max context <=32768 and borrowing above it, unless explicitly overridden; `--prefill-borrow`/`--no-prefill-borrow` must be pinned for matched comparisons (`:2166-2203`).

`--short-read N` is a serve-mode threshold: a fresh text part up to N tokens is read through verifier/decode windows instead of batched prompt path; default 64, zero disables this route (`generate.cpp:666-669, 810-811, 1853`). At N=65536, a single 32K fresh text part will generally route through those windows, so changing `--prefill` does not test batched chunk performance. Log per-part short-read decision and actual batched position count. It is a route selector, not a chunk or speed control. For a true batched-prefill screen, use `--short-read 0` and wait for a separate prefill-safety admission. For the serial window/decode screen, retain the R202 threshold and keep chunk settings fixed/irrelevant.

Other prefill controls (`STRATA_PREFILL_RING`, `STRATA_PREFILL_STREAM_MIN`, `STRATA_PREFILL_STREAM_ALL`, `STRATA_RING_BYTES`, `STRATA_PREFILL_LEND_PCT`, borrow mode) change ring memory, streaming lookahead, cache loan and sometimes which experts are streamed. They are coupled to chunk and expert source. Keep them at the exact selected config/default values in the first chunk screen; only test an additional one after logs show a ring/cache or staging bottleneck, and only after the prefill safety gate. Do not copy ring slot counts from another pack: each ring slot reserves that pack's whole expert blob (`prefill.cpp:101-180, 195-228`).

**Compiler and fixed work.** The target existing official build is Release icpx 2026.1, JIT (`STRATA_SYCL_AOT` empty), not the Xe LLVM 7.1.1 toolchain. Do not pool measurements or flags across those compiler/backend configurations. No broad all-kernel eager preload was found in the official v0.1.43 SYCL tree (R169); selected kernels still require actual JIT acceptance. Separate process start/model and profile load, first-use JIT, graph capture/warm-up, prompt conditioning, terminal prompt-token work, generation, and teardown in timing records. Keep whether persistent JIT cache is enabled/disabled identical across every arm; Xe2 docs warn `SYCL_CACHE_PERSISTENT=0` due a first-compile crash. Do not count startup/JIT as prompt or decode throughput, and do not discard it from whole-request user latency.

## Minimal independent selection matrix after the relevant admission gates

Use one frozen exact prompt with **at least 32,768 prompt tokens**, same tokenizer, model/pack/PLE/profile/MTP file hashes, context and sampling. Set max context the same across arms and large enough that the prompt fits. For batched input, report the engine's `n_prompt-1` batched positions plus the final prompt token handled separately; do not call a nominal 32K input 32K batched positions. Use a separate held-out prompt-ID sequence of at least 32K tokens for validation. Keep all run order, runtime/device selector, CPU topology, warm/cold policy, and background load controls constant. Screening results choose settings only among actually admitted and correctness-passing candidates.

**Lane A — batched prefill, conditional on prefill safety admission:** keep decode fixed and use `--short-read 0`, one source/residency mode, one profile/cache policy, fixed KV/context, fixed reserve, borrowing policy, and ring controls. Screen the installer-style `--prefill auto` as a distinct policy against requested fixed `4096`, `6144`, and `8192`. Fixed values bracket a useful 32K chunk range and historical requested/effective geometry; they are candidates, not presumed winners. Add `auto:16384` only if 8192 is admitted and actual PP/cache data gives a reason. For each candidate do one fresh-process screening run on the same exact ≥32K prompt, recording requested/effective chunk, cache slots/MiB, ring slots/bytes, VRAM/RAM headroom, PP per-chunk progress and ms/tok/s, PLE/stager status, correctness and errors. If multiple requests collapse to one effective chunk/ring, count them as one setting. Do not screen a lower chunk as a workaround for host-USM synchronization.

**Lane B — serial verifier/decode resource selection, conditional on R202's window-route execution gate:** use `STRATA_VERIFY_STEPPED=1`, `STRATA_VERIFY_PIPE=0`, host pool enabled; pin source mode, profile/cache budget, mirror policy, `--pcie-frac 0`, prefill route, KV/context, `--spec 4` and draft artifacts. Use ≥32K prompt context/state for every candidate but select decode time on the same fixed generation-length range. Screen `--pool-workers 0`, `3`, `5` with one fresh process/sample each; if auto and an explicit value report the same worker topology, collapse duplicates. Record actual worker count and CPU placement, CPU-pool drain, segment wait, per-window and generation throughput, actual misses/hits, output IDs/logits quality gate, failures, and startup/JIT separately. If source build has no MTP file and `--mtp` is absent, label MTP disabled; do not conflate default suffix lookup (`--suffix-draft`, default 3 when eligible) with MTP. Pin the suffix setting too if wanting the same draft route.

**Selection repeats and held-out check:** after one-factor screening, select at most one chunk policy and one worker count. For the chosen decode tuple, collect **three independent fresh-process decode samples** with identical restored/constructed ≥32K context, exact output count, and all artifacts/controls fixed; retain all three, median and range. Use a held-out ≥32K prompt not used to select settings and run the frozen tuple through the same correctness gate; ideally take three fresh-process held-out decode samples too. If a valid identical restored state is not available, rebuild the matched context in each process and record prefill/context-build separately, never mix that time into decode-only rates. Repeat the chosen batched prefill tuple on held-out input as a separate prefill validation only after Lane A is admitted. The final claim is “selected among these tested candidates on these prompts/configurations,” not globally optimal.

Do not combine worker count with cache size, host-RAM mode, mirror budget, PCIe share, KV type/residency, reserve, ring or chunk in one arm. If cache policy materially changes hit/miss ratio, run a later dedicated screen: the current installer/profile `auto` policy versus one feasible fixed cache budget, each with its actual post-admission slot count/bytes logged. If testing source tier (arena, file mmap, resident CPU copy, or pinned streaming mirror), treat each as a separate execution mode and report it as such; do not compare it as a worker-only optimization. Preserve full individual timings and correctness/fault outcomes per `docs/ARTIFACT_RETENTION.md`.
