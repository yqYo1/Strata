## Finding: a supported safe-control-flow candidate exists, but it is a slow verifier-window qualification arm

A normal **text-only** 32,768-token request can avoid the batched-prefill Stager/PLE completion-word loops by using the already-supported `--serve --short-read 65536` path, and can avoid concurrent decode doorbell access by enabling the existing segmented verifier path. Candidate settings for either source tree:

```text
engine args: --serve --spec 4 --short-read 65536
environment: STRATA_VERIFY_STEPPED=1 STRATA_VERIFY_PIPE=0
```

Leave MTP absent/off, server batch and `--pipeline-windows` off, and use the normal CPU expert pool. Ensure `max_context` exceeds prompt plus output. This deliberately processes fresh text through the verifier in small windows; it is not the fast batched-prefill route and must not be labeled as a batched-prefill performance comparison. The value 65536 leaves room for server-created prompt segments and covers a 32K fresh prompt. The source has no B570 capability check on `STRATA_VERIFY_STEPPED`; the handoff ordering is device-independent, but execution on B570 remains to be qualified.

### Reachability proof: the long prompt bypasses batched prefill

In official `sycl/src/program/generate.cpp`, `--short-read` is a documented `--serve` option (default 64; option help near line 810, parse near 1853). `windows_ok(a,b)` rejects only a segment longer than the configured maximum (near 9840). The request loop branches on that predicate: `win ? read_windows(at,to,...) : read_part(...)` (around 10303–10313). `read_windows` advances through windows of `S=o.spec` and calls `ver.run(...)` (around 9985); `--spec 4` provides a nonzero width, without requiring an MTP file. With no MTP, the main model still verifies and commits each window; MTP drafting/prompt prefill is guarded by `use_mtp = !o.mtp.empty()`.

The unsafe official prompt waits are reachable only in `Prefill::run`: Stager's `done_seq` is `malloc_host` and host-polled by `buffer_free` after asynchronous DMA (official `sycl/src/prefill/prefill.cpp:388–393, 513–523`); PLE upload writes `ple_done_seq` from the queue and polls it before the next chunk reuses the other buffer (`:1078–1080, 2341–2362`). The `read_windows` branch does not call `sp.run`/`Prefill::run`, so neither word is written or polled for this request. PLE remains enabled and is supplied through verifier windows instead of being ablated. Text-only matters: source refuses the windows route for prompt segments carrying image embedding rows; image requests must use the batched route and remain outside this candidate.

This also answers the nearby knobs: `STRATA_PREFILL_CPU_SHARE=0` is a Xe batched-prefill CPU/GPU split control, not a no-poll control; it neither makes the official sequence word safe nor changes verifier CPU-miss service. `--prefill-until` and ring sizes affect the batched route only. No batched route is selected for the covered prompt segment here.

### Reachability proof: stepped verifier serializes host/device access

Both source trees recognize `STRATA_VERIFY_STEPPED=1` in `Verifier`; official `sycl/src/core/verify.cpp:101, 1734–1737, 2041–2189`. The non-all-resident stepped route submits a segment, drains its queue with `cs_->wait()`, then reads the host sequence/payload and runs the CPU pool; it writes the plan/flag words while the device queue is idle and submits the dependent segment afterward. It does not spin the device on a host flag while the host changes that flag, and the host does not poll a device-written sequence while its segment runs. The source explicitly describes this ordering at `verify.cpp:218` and uses ordinary host USM for buffers only accessed between kernels when stepped mode is on (`:225–238`). Set `STRATA_VERIFY_PIPE=0` so the serial segment path is explicit and the optional helper-thread/early-segment overlap is absent (option comment at `:101–102`). Keep `STRATA_VERIFY_EAGER` unset; eager execution is a separate route. The CPU pool remains enabled, so nonresident routed experts are computed and combined rather than omitted.

Thus `HOST_USM=1` suffices for the sequential host-USM payload/flag transfers; no atomic host USM is requested. `ATOMIC_HOST_USM=0` blocks the concurrent volatile/atomic-polled protocol, but is immaterial after ownership is sequenced by queue completion and the next segment submission. No-pool/no-capture is neither needed nor an acceptable substitute: source says that combination is a GPU-only floor whose routed misses contribute nothing (`generate.cpp` around 5245–5257 in official; Xe around 4796–4808).

### PLE, host data and object lifetime

The window path gathers the PLE rows into verifier-owned host staging, then serves the window through its segmented queue boundaries; it does not execute the batched double-buffer `ple_done_seq` protocol. The CPU pool consumes the verifier's host payload only after the segment drain. The next segment that reads pool output/flags is submitted after host work and the publication fences. The verifier's mapped buffers and the model's expert source remain owned for the full window/request; teardown occurs after outstanding window/commit work is drained. This is the supported sequential-ownership pattern. It is different from arguing that `volatile` alone makes an overlapping host/device poll safe.

MTP off removes the draft-head path and its extra state; it does not disable the main verifier. Conversely, `--spec 0` selects ordinary token-graph/session decode and does not route decode handoffs through the segmented verifier; it is not a safe substitute. `--no-pool` without an all-device-expert implementation omits routed misses. The 32K setup must therefore retain `--spec 4`, the CPU pool, and the explicit stepped verifier setting.

## Difference between pristine official and Xe

- **Official v0.1.43:** the default/large-chunk batched prefill still has the unsafe Stager completion word and the cross-chunk PLE completion word. The candidate above avoids both by selecting `read_windows`; it does not qualify the batched-prefill route. Official has no `preload_kernels`, `get_kernel_ids`, or `STRATA_PRELOAD` reference under `sycl/src`, so there is no all-ID preload to disable. On-demand selected-kernel compilation/execution is still unqualified.
- **Xe0.1.42:** batched-prefill staging uses queue events (`event_sync(dma_done[b])` before staging-buffer reuse) and PLE upload uses `event_sync(ple_copied[other])`, rather than the official `done_seq`/`ple_done_seq` host polling words (`src/prefill/prefill.cpp` around 220–240, 255–300, and 1070–1090 / `ple_land`). The decode doorbell remains a separate problem: `session_run_token` polls host `h_seq` and writes `h_flag`, while captured token graphs/device kernels wait on the flag (`src/core/session.cpp:909–947`, `src/core/layer.cpp` doorbell allocation/reset). It is still covered by the segmented-verifier candidate when `--spec 4` is used. Xe also unconditionally calls `Runtime::preload_kernels()` during startup (`src/program/generate.cpp:2847`; implementation `src/core/device.cpp:255–276`) and has no `STRATA_PRELOAD`/CLI disable. No configuration claim can turn off that global compilation request; whether it succeeds on the target compiler remains an independent execution gate.

## Pristine vs qualification boundary

This is a source-supported existing-option candidate, not a claim that the default pristine server configuration is safe: its default short-read limit is only 64, so a fresh 32K text segment normally takes `read_part` and the batched prompt path. It is also not a performance candidate; the long prompt becomes thousands of serial main-model verifier windows and may take many minutes. A B570 run under the candidate would qualify only the exact text prompt, one-GPU, serial verifier-window control flow and generated output. It would not qualify the 32K batched-prefill optimization or its speed.

If the requested result specifically requires a **batched-prefill** 32K benchmark, current official has no parameter-only way to sequence its two host-polled completion words while preserving that route. That question is a separate code qualification: replace the staged-DMA/PLE sequence polls with queue/event completion (Xe's event synchronization is an adjacent reference), then validate allocation and buffer lifetimes. Do not mislabel the verifier-window candidate as that result.
