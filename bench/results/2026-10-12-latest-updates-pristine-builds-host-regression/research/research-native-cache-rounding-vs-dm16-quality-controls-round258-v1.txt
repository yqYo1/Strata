# R258 — Native CPU/GPU cache rounding versus Dm16 quality controls

Date: 2026-10-12 (JST). Read-only source and closed-artifact review for WN `0691bcdf`; upstream reference U `7695859`. No test, import, execution, build, GPU/process/device query, Git operation, cleanup, or source change was performed. No new numerical result or quality conclusion is claimed.

## Finding

The remaining numeric question is **route precision when an expert moves between CPU and GPU**, not whether cache residency changes the mathematical weights. On the mixed pair IQ3_S GU / IQ4_NL Down, the CPU consumes the original quantized weights with ggml CPU dot products and quantized activations. The ordinary GPU fallback decodes weights to FP16, feeds FP16 activations to grouped GEMM, and accumulates product output in FP32. A direct/fused GPU branch can decode IQ values locally instead of materializing the same FP16 weight matrices, so the selected route must be recorded. These distinct representations and accumulation orders can shift near-tie logits even when the quantized expert weights are identical.

Three minimal comparisons are sufficient to localize the remaining rounding sources before any quality decision:

1. **GU activation and product boundary, IQ3_S.** For identical routed rows and exact expert blob, save the FP32 input activations, CPU quantized activation bytes/type, and GPU FP16 activation words. Compare dequantized activations to the same FP32 input, then compare CPU IQ3_S GU outputs with GPU GU outputs before SwiGLU. Report max/percentile/RMS error, nonfinite counts, and the CPU/GPU accumulation path and row count. This isolates the initial activation encoding plus dot/dequant/product arithmetic. CPU `NativeFmt` gets the activation type from ggml's `vec_dot_type`; the source comments identify Q8_K as the activation format for i-quant rows. GPU's regular route uses Xs in FP16; fused resident IQ GEMM is a separate path and must not be mixed into this arm.
2. **SwiGLU/Down activation boundary, IQ4_NL.** At the same rows, compare post-SwiGLU FP32 `H` before CPU quantization against CPU's actual IQ4_NL activation encoding (ggml trait; Q8_0 for IQ4_NL) and GPU's FP16 H buffer. Then compare CPU IQ4_NL Down output and GPU Down output before Dm storage. This isolates the extra quantization at the intermediate activation boundary from the different Down dot implementation. Keep GU/Down row ordering and exact expert identity fixed.
3. **FP32 expert contribution and final combination.** Compare each selected expert's completed FP32 Down contribution before any storage conversion, then the route-weighted FP32 MoE sum in the exact route-rank order, followed by final logits for the same teacher-forced positions. Preserve pre-store values on both CPU and GPU; do not insert Dm16. This establishes whether local expert deltas compound or cancel in the actual combine, and supports paired full-logit/KL/top-1 analysis. The current cache run's Exact16/LP5 observation is a trigger for this broader comparison, not a substitute for it.

For each arm, pin identical token IDs, routing/bounds, layer, expert IDs and weights. Record CPU ISA/dispatch, NT, CPU activation quantizer, GPU fused/MMQ/native-dequant flags, cache-resident versus streamed state, and the selected product backend. The supplied R255 histogram can weight prompt CPU work by layer/type/NT after its completeness gates pass, but counts do not supply numeric parity or timing.

## Rounding map in WN0691

- `native_expert.cpp::native_fmt` obtains GU and Down activation types from each GGML weight type's `vec_dot_type`; `native_quant_act` and `native_quant_h` materialize those formats. Native IQ CPU products preserve the packed IQ weights and use ggml/Strata AVX kernels or ggml's dot path, depending on type, NT and CPU ISA. IQ3_S GU's i-quant CPU activation path is Q8_K; IQ4_NL Down uses Q8_0. The intermediate is passed through float/SwiGLU then quantized again for Down.
- The regular GPU fallback in `prefill.cpp` gathers FP16 activations, dequantizes IQ weights into FP16 scratch, and calls grouped FP16-input GEMM with FP32 outputs. The product's accumulator/output being FP32 does not undo FP16 input/weight rounding. A fused resident IQ-GEMM path is separately gated and uses local IQ decode with FP16 activation input; it is not numerically interchangeable by assumption with the dequant-to-scratch route.
- Device dequant output parity is not CPU/GPU product parity. R159 shows GPU grouped dequant outputs at widths 1/8/16 match the individual GPU path byte-for-byte for seven pairs including (21,20), but both share the same GPU conversion/store behavior. It did not compare CPU expected half bits for those whole matrices or CPU GEMM output. Its independent RNE converter audit is not a complete CPU-versus-device route comparison.
- Dm16 is a later, independent storage roundtrip. In WN, Down products are FP32 when written to `Dm`; the combine consumes those contributions and accumulates weighted routes in FP32. Dm16 would round after the FP32 Down result, before the combine. Measure CPU/GPU route differences with full FP32 Dm first; only then, if pursued, evaluate a Dm16 writer-store-reader arm against that same FP32 baseline. Mixing the two would confound activation/weight/product precision with storage rounding.

The current official cache128/512 diagnostic was reported by Main to differ on 16 generated IDs and LP5. That supports only an observed exact-16 output/LP5 difference between those run arms. It does not show a quality regression, a precision pass, full-logit deltas, or that CPU/GPU rounding alone caused the changes: cache residency can change which experts execute on which device, while request/profile/cache conditions may also differ. The official record itself scopes the result to “Exact16 reported tokens/LP5 only” and disclaims full-logit, quality, RESTORE and optimal-speed claims.

## Existing evidence and non-duplicates

- **Old cache-on/off report:** the committed 2026-09-27 cache-parity README compares Q2_0 on an RTX 5070 for three short teacher-forced prompts, with CPU-only versus GPU-cache execution; it reports token agreement, median KL and text perplexity. It supports the general fact that route changes can move near-tie predictions without deciding which route is more accurate in that sample. It is not the target WN mixed IQ3_S/IQ4_NL pair, current B570/compiler, current profile/cache policy, or the requested 32K/64K quality check. Do not repeat it as though it covered this target.
- **R159 GPU dequant evidence:** seven pairs including (21,20), GU/Down at 640×2560, grouped widths 1/8/16, six ABBA samples per pair/width and complete byte comparisons. It closes grouped-vs-individual GPU dequant output equivalence for sampled inputs; it does not close CPU activation/product parity or independent device-half conversion parity.
- **R255 histogram:** source-audited CPU prompt job/row/NT attribution by layer and format pair. It describes which CPU work could be weighted in a future comparison; it has no numeric sample and does not observe GPU output or correctness.
- **R251 Dm16 eligibility:** source confirms a post-FP32-store Dm16 candidate on an eligible compact fallback and identifies its writers/reader, but no capacity, numerical, or quality result. It is specifically not evidence for the current CPU/GPU route delta.
- **R239 / R301 precision reports:** define persistent-storage candidates and quality gates, but do not qualify this route's FP16 activations, half-dequant weights, Q8 activation formats, or mixed CPU/GPU expert products.

No primary paper or other-model “nearly lossless” result can certify this model, these expert formats, this compiler, or its user tasks. No full-vocabulary comparison or task-quality acceptance has been performed; no quality margin is defined by these artifacts. The 16-ID/LP5 observation alone must not be called degradation or accepted precision.
