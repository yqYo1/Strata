## Decision

The failure signature is mechanically comparable only at the outer contract: both engines admit a profile pair to an ExpertCache slot, copy the pair's per-layer blob extent, then synchronously read back a slot and compare it with source bytes. Official v0.1.43 has a *different* arena transfer/registration implementation from Xe. Its usual arena is an ordinary `mmap`/anonymous mapping; SYCL's translated `cudaHostRegister` call is a literal no-op in source, while the code reports the full arena registered and derives a device alias by casting the host pointer. Cache fill/readback instead call DPCT queue `memcpy` directly from/to that host pointer. There is no official `prepare_for_device_copy` piece splitter at the Xe large-allocation boundary.

Thus the Xe slot-84 byte-0 failure is not enough to predict the same failure in the official path, and the official source does reveal a distinct host-pointer/registration assumption that must be qualified by the official runtime. No source-only conclusion can identify which side of a future official byte mismatch is wrong, prove the host-pointer transfer valid on a given adapter, or claim official startup passes.

## Native per-layer slot mapping

For 48 layers and 144 actual sized slots, `layer_slot_range` uses `q = 144 / 48 = 3`. Layer 28 owns slots `[84, 87)`, so slot 84 is layer 28's first slot if this is the same 48-layer / 144-slot setup. The per-layer list is constructed as three entries of each layer's own `lay.blob_bytes(l)`, in layer order. `open_sized` builds 256-byte-aligned cumulative offsets; `admit` uses the layer's cursor to allocate inside its range. The profile-fill loop passes that layer's byte count to `fill_slot_blocking`; startup `verify_slot` resolves the same first profile pair through `slot_of` and compares its source bytes after a blocking D2H read.

This mapping is internally consistent for the reported values. It does not show the failing profile pair without opening its profile, which this review did not do. Also, the available compact official IQ3_S layout fixture (`tests/data/native_experts/iq3_s.txt`) identifies layer 28 as type pair 21/20 with a 2,329,600-byte blob. In that fixture, 2,662,400 bytes is the 23/20 blob size (the 22/20 entries are 1,971,200 bytes). Therefore the Xe diagnostic's `of 2662400` must not be attributed to official IQ3_S layer 28 / pair 22/20 based only on slot number; actual pack/layout/profile identity is required to join those claims. The compact test fixture is not proof of the model input used in the Xe run.

## Arena size, chunk boundaries, and registration behavior

Official `ArenaExpertSource::open` creates one arena of `lay.total + lay.max_blob` bytes. The extra maximum-blob tail allows whole-slot copies starting at any expert. For the official IQ3_S fixture the logical total is 50,292,326,400 bytes; the arena request adds its largest blob (2,662,400 bytes). Layer bounds are passed to `PinnedArena`; the loader writes into those layer bases in 8 MiB file-read chunks. That 8 MiB is host file loading, not GPU cache-transfer chunking.

In the default no-cap path, official `PinnedArena` substitutes zero for `cudaHostRegister`, enters the `e == 0` branch, sets `registered_bytes = bytes`, and later forms each device alias by using `base + offset` directly. This bookkeeping does not correspond to an actual imported/registered region in this SYCL source. If the whole registration fails in a real implementation or a registration cap is selected, its fallback loops over layer bounds; it still has no `max_alloc_bytes()` piece splitter and does not cut at each expert boundary. The deferred per-layer registration worker is Windows-only and its SYCL replacement is also a no-op.

Xe's `PinnedArena::register_pieces` instead queries `max_alloc_bytes()`, cuts the mapping into pieces no larger than that limit, and accepts expert-start cuts so an expert blob does not straddle piece registrations. It calls `sycl::ext::oneapi::experimental::prepare_for_device_copy` per piece before the load, retains those exact piece extents, and creates the device-copy alias through its GPU/runtime wrapper. The runtime's piece count (the reported five pieces in the Xe setup) depends on that device's maximum allocation and the exact boundaries; official source has no corresponding five-piece mechanism. This comparison explains a structural divergence, not the root cause of the Xe failure.

## Fill and verification path distinction

- Official serial path (`srcp == ArenaExpertSource`): `blob()` returns a pointer into the resident arena. `ExpertCache::fill_slot_blocking` calls `dpct::get_in_order_queue().memcpy(dst, host_blob, n).wait()`. `verify_slot` performs a separate blocking queue memcpy from the cache to a `std::vector` and `memcmp`s it against the same arena pointer. This has queue completion before comparison, but no explicit SYCL import/register of the ordinary mapping at the call site.
- Official pipelined profile fill is only selected for `GgufExpertSource`, non-per-layer mode. It reads into `sycl::malloc_host` ping-pong batches, queues per-blob copies, waits the queue, then optionally validates every slot. It is not selected by the `ArenaExpertSource` default path or by the per-layer case described here.
- Xe's `fill_slot_blocking` routes through `strata::gpu::copy`, while its arena has prepared piece imports. Xe `verify_slot` likewise reads back synchronously and compares source bytes. The fact that the Xe run's verifier reached a byte mismatch rather than a copy error does not prove the official `dpct queue::memcpy` path has equivalent pointer semantics.

The startup verification is useful: a byte-0 mismatch proves the readback bytes differ from the source bytes passed to the comparison. It cannot distinguish stale/incorrect source bytes, H2D transfer corruption, wrong cache destination/pointer, or D2H/readback corruption. The official `verify_slot` uses the same style of source comparison, so an official failure would require preserving the source identity and exact fill/verify pointer/extents to localize it.
