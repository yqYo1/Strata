# R226 — first-chunk compilation and cache fairness for latest engines

Date: 2026-10-12 Asia/Tokyo. Read-only source/runtime-documentation audit for pristine XeStrata v0.1.42, adopted Xe integration `0691bcdf5af63a85b3b25650f367d3276db64035`, and official SYCL v0.1.43 where useful. No build, tests, imports/AST, Git, process/service, model/GPU, cache mutation/cleanup, or benchmark was performed. Main's active official v0.1.43 32K run was left alone.

## Decision

The source contains substantial pre-first-prompt kernel preparation: an asynchronous pass requests executable SYCL bundles for every registered kernel ID on the selected device; oneMath GEMM preparation is called and settled; and speculative verification setup executes several device-side tuner/calibration paths before reporting `session is up`. This makes the first prompt a poor proxy for “all compilation happens on the first chunk.” It does not prove that the first prompt has no lazy compilation. No source path measures a decomposition of first-chunk elapsed time into compilation, cache loading, memory paging, clock state, or model computation. Treat any such attribution as unmeasured until instrumentation separates it.

The supplied pristine Xe diagnostic is a normal-QUIT/no-fault 32,768+16 run, but it used instrumentation and `SYCL_CACHE_PERSISTENT=0`; the reported cumulative prefill times were 61,698, 95,088, 124,768, and 150,548 ms, with engine prefill 150,580.2 ms and decode 1,536.8 ms. The successive cumulative increments are 61,698, 33,390, 29,680, and 25,780 ms. These samples show a slower first recorded chunk in that run; they do not identify JIT as the cause and do not make a winning claim. Persistent cache off only excludes disk-cache reuse; Intel documents the per-context in-memory cache separately, enabled by default.

## What source prepares before prompt timing

Xe v0.1.42 and adopted integration call `Runtime::preload_kernels()` alongside model loading (`generate.cpp`, Xe about line 2847; integration about 2924). The runtime launches a background thread over `sycl::get_kernel_ids()`, requesting `get_kernel_bundle<executable>(context, {device}, {id})` for each ID. It counts exceptions as “not for this GPU”; with `STRATA_TRACE` it reports built/skipped totals on completion. This is compile-ahead work for the registered, device-compatible SYCL kernel IDs. The request is asynchronous. In `generate.cpp`, explicit `wait_preload()` sites are tied to PCIe split and pre-prompt memory-rate measurements; a supplied `--pcie-frac` path bypasses that calibration. Thus source alone does not prove the preload thread has finished before first prompt in every configuration. No elapsed-time counter isolates its work.

The source separately prepares oneMath prefill GEMM and settles it before prompt execution (Xe `generate.cpp` near 2860; integration near 2937). This is library preparation, not proof every eventual matrix shape/module has been instantiated. The first real prompt still exercises shapes and branches that generic preloading or a library prepare call might not cover.

When `--spec` is active, `Verifier::tune_device` is called during startup before the `session is up` message, and the verifier's init path also calls it before recording the first graph. It invokes `gdn_step_tune`, `fetch_blobs_tune`, and BF16 multi-row GEMV tuning for selected dimensions. These are real GPU work, not a no-op JIT warm-up: the source creates scratch, builds command graphs, launches candidate forms over window sizes, waits, and stores selection choices. The BF16 tuner tries both forms for T=2..8 per shape; GDN trials three forms per verify window when not forced; the fetch tuner tries work-group counts. This can trigger compilation before the prompt, warm device clocks, and consume startup time. It is not an end-to-end prefill warm-up and does not cover every prefill kernel/configuration.

The SYCL cache key includes device image, specialization-constant values, device identity/version/driver, and build options. A different specialization value or compile option may therefore require a different compiled entry even if an image ID was previously requested. External library code may also have its own loading/caching behavior. This prevents a source-only claim that “all possible kernels/shapes are compiled” from the all-ID loop.

## Cache semantics and fair comparisons

Intel's oneAPI DPC++ documentation distinguishes the per-context in-memory program/kernel cache from the persistent on-disk device-code cache. `SYCL_CACHE_PERSISTENT=0` disables persistent caching; it does not disable the in-memory cache (`SYCL_CACHE_IN_MEM`, default `1`). Persistent caching is default off unless enabled/configured. `SYCL_CACHE_DIR` selects its root; the docs say a persistent cache hit is qualified by image, specialization values, device and build-options keys, with device identity including driver version. Sources:

- Intel LLVM, “A brief overview of kernel and program caching mechanism”: https://intel.github.io/llvm/design/KernelProgramCache.html
- Intel LLVM, “Environment Variables” (including `SYCL_CACHE_TRACE`): https://intel.github.io/llvm/EnvironmentVariables.html

For a defensible cold-process comparison, keep engine/model/request settings, instrumentation, driver/compiler, and cache policy fixed; record whether persistent cache is disabled or use a separate empty `SYCL_CACHE_DIR` per engine/binary; use a fresh process for each sample; and report startup preparation separately from request prefill. Persistent-off gives a fresh process no on-disk compiled image reuse, while still permitting compilation and in-memory reuse during that process. Do not call it “no JIT.” For a warm-compiled comparison, first populate the same engine's persistent cache with the exact binary, device/driver, build options and route, then start fresh measured processes with that cache enabled. Do not compare Xe's empty/off state with official's populated/on state. Cache tracing is useful in a separate diagnostic run; keep it out of timed runs unless the same instrumentation overhead is intentionally measured on both sides.

In addition, an explicit same-process warm-up can prime in-memory entries, but it must execute the same relevant prompt/verifier kernel route and then reset session/model state before timing. That measures a warm-process condition, not a cold process. Report both as separate estimands. The current instrumentation-enabled diagnostic must not be mixed with uninstrumented samples unless both engines use equivalent instrumentation.

`STRATA_GDN_STEP`, `STRATA_FETCH_GROUPS`, and `STRATA_MMVF_ROWS` are algorithm/dispatch controls, not cache switches. The first two can bypass particular tuning selection when forced; `STRATA_MMVF_ROWS` forces dispatch choice but the BF16 tuning function still runs its measurements. Changing them changes selected forms or startup work, so they should be held equal across comparisons and recorded. No safe source knob was found that simply disables lazy JIT while preserving every route. `STRATA_TRACE` reports preload counts but is diagnostic instrumentation, not a wait barrier.
