## Admission decision

The route is representable in source for a single text segment of at least 32,768 positions, provided the CLI uses separate option and value arguments. The literal strings `--short-read65536`, `--spec8`, and `--suffix-draft0` are **not** accepted option spellings: parser dispatch compares the complete argument to `--short-read`, `--spec`, and `--suffix-draft`, then reads the next argv element. Use `--short-read 65536 --spec 8 --suffix-draft 0 --no-spec-split`. This is a material admission issue: do not assume shell or CLI prefix matching. Source lines in `sycl/src/program/generate.cpp`: 1825, 1853, 1855, 1907. No `--key=value` branch was found for these options.

With that normalized argv, `short_read=65536` admits an eligible text-only segment of 32,768 tokens to `read_windows`; the threshold applies per serve segment, not necessarily the whole request. `spec=8` requests the existing maximum verifier width; `suffix-draft=0` prevents the default suffix-draft rule from turning requested spec into a different effective spec. `no-spec-split` keeps one verifier group of up to eight rows rather than two smaller groups. At 32,768 positions and full eight-row groups the arithmetic ceiling is 4,096 calls; a short final remainder can add the corresponding smaller call only when total length is not divisible by eight.

The requested env route `STRATA_VERIFY_STEPPED=1`, `STRATA_VERIFY_PIPE=0`, `STRATA_VERIFY_NO_HOST=0`, `STRATA_VERIFY_DEVICE_PLAN=1` is consistent with the R208 mixed-residency host-service path: stepped queue segments, inline host pool at misses, and device planning for resident routed experts. It does not make the separate batched-prefill stager/PLE host polling safe; this candidate must actually take the short-read window route. Keep `--pipeline-windows` off. The device-plan bit is optional for window sizing and changes resident-plan construction, so pin it across comparisons.

`--kv int8 --kv-resident 32768` is syntactically admitted for a single-GPU route: zero means all KV resident; the source only rejects negative values here, then passes the requested resident-cell count to QSA allocation. Source help documents a 20,480-cell minimum when streaming, so 32,768 exceeds that minimum. It does not prove that 32,768 is enough for this model/context or will fit 10 GB VRAM; actual allocation, context, max-context, and INFO/free-VRAM gates remain decisive. Also freeze `--max-context` and output allowance: they affect KV/QSA and other allocations. An optional `--native` or native-dense path is not required to select `read_windows`; native dense is a different tensor implementation/admission axis and must not be silently enabled in one arm. If selected, verify its files/shard coverage and PLE compatibility separately and compare correctness.

## Independent decode tuning boundary

The only clean first-order independent decode parameter in this route is CPU expert-pool worker count (`--pool-workers`): compare source automatic (0, then record actual INFO count) with a small physical-core candidate such as 3 and 5 on the known 6-core/12-thread Ryzen 5600X. These are candidate points, not predicted winners. Keep affinity, host participation, source/residency/profile, cache slots, PCIe fraction, KV, context, MTP/speculation, sampling and prompt fixed. Explicitly record effective workers. `STRATA_FETCH_THREADS` tunes file prefetch, not compute workers; no official `--pool-tasks`/`STRATA_POOL_TASKS` knob exists. Under PIPE=0, don't assume host compute overlaps GPU work. Cache/PCIe/residency/native flags alter which misses reach the pool and are separate route axes, not worker settings.

Keep `--spec 8`, suffix-draft 0, MTP state and inputs fixed across worker comparison; the verifier window width is not a decode-worker optimization. If a later width study is justified, treat it as a separate quality/work-shape arm: draft acceptance and window count can change, so token/s alone is not like-for-like. `--no-spec-split` remains the one-group route from R208. No simultaneous change to `--kv-resident`, `--expert-cache`, `--pool-affinity`, `--no-host-worker`, PCIe fraction, native dense, profile or prefill settings should be attributed to worker count.

## Critical-path quantities and limits

Source gives logical work formulas, not physical traffic or time estimates. In `src/kernels/cpu/pool.cpp`, each batched native pool batch of `nb` distinct CPU-served experts exposes `nb*FF` GU rows, serially converts/quantizes `nt*FF` intermediate values per expert/token, then exposes `nb*H` Down rows. `FF` and `H` are model dimensions, `nt` is the routed token count, and batches are bounded by split-buffer capacity. The CPU source's logged `multi_bytes` is `n * f.bytes` per drain: logical expert-blob extents requested by jobs, not cache-miss bytes, RAM reads, DRAM transactions, or PCIe bytes. For a verifier group with at most T=8 rows and top-K=10, the fixed route planner's upper table bound is 80 routed entries; actual unique misses/expert jobs and their `nt` must be taken from runtime counters, not assumed equal to 80.

With stepped serving and no helper pipeline, the dependency to preserve per pool batch is: queue segment completion / miss-group handoff, GU row work, activation quantization, Down row work, completion before output/scratch reuse, then next dependent transformer-layer/window work. The routed pool service and the next-layer output dependency form the critical path; exact exposed duration depends on which experts are resident, CPU jobs, GPU segment queue work, and actual scheduling/overlap. The source supports counting windows, unique jobs, logical `n*f.bytes`, `nb*FF` and `nb*H` row work, and `nt*FF` quantization values. It does not support a numerical latency lower bound without measured service rates, route counts, and overlap. Do not turn those quantities into RAM bandwidth, physical DMA, or a guessed ms floor.
