## Prompt-route arithmetic and logical blob-volume bounds

Official `read_windows` consumes the prompt's first `n-1` positions and later decodes the final prompt token (`generate.cpp:9964-10014, 10363-10365`). Here `n=32768`, so 32,767 prompt positions enter routing. `--spec 8` makes a full verifier window T=8; therefore 4,095 full windows plus one T=7 tail = 4,096 windows. `verify.cpp:823` gives G=1 under `--no-spec-split`; `expert_source.cpp:2540-2564` fixes a window to at most 128 entries and defines 10 routed experts per token. The actual request has 48 expert-bearing layers and cache q=3/layer per R228's source/layout arithmetic and the receipt's 144 total slots.

For one layer-window, 8 rows × 10 routes gives 80 routed row-expert incidences. Each row selects 10 distinct experts, so the union across the window has at least 10 and at most 80 distinct experts. With only 3 resident cache entries, nonresident unique jobs are therefore bounded 7..80 per layer-window. This is a conditional, source-derived set-size bound: it assumes the same 3-per-layer static cache and no peer/remote/adaptive placement. The actual profile overlap is unknown. Across 48 layers and 4,096 windows, this yields 1,376,256..15,728,640 CPU expert jobs (unique layer-expert jobs per window), and 11,009,712..15,728,160 routed row-expert assignments executed on CPU (at least seven misses per token/layer, at most ten). It does not measure CPU instructions or worker utilization.

Using `S=98,227,200 B` as the sum of one aligned expert blob per layer, the source-blob logical extent associated with 8-window misses is bounded:

`4096 windows * [7,80] distinct misses/layer/window * S = [2,816,370,278,400 B, 32,187,088,896,000 B]` (about 2.56–29.27 TiB in binary units).

This is a repeated CPU source-blob work-volume estimate. It is not PCIe traffic: the selected official route serves misses in the CPU pool (`expert_source.cpp:2711-2784`), and a blob pointer may be served from mapped/file cache or host RAM. Counted logical expert extents do not prove bytes fetched from storage or DRAM.

For the comparison route, a 32,767-token batched request with T=8192 makes chunks 8,192 + 8,192 + 8,192 + 8,191 (four chunks). `prefill.cpp:115-121, 2460-2465` sets stream-all at 1,024 tokens by default when `m.ring > STAGE` and the expert source exists; the conditional must be checked for any future arm. In that path the source enumerates each layer's nonresident experts once in the chunk's sequence (`prefill.cpp:2519-2555`) and issues each entry through a ring/copy stream (`:2680-2691`), so repeat use of an expert within that chunk does not imply a second blob issue. Per chunk/layer the union of routes is at least 10 and at most 512; subtracting three cached experts gives 7..509 nonresident experts. Across four chunks and 48 layers:

`4 chunks * [7,509] misses/layer/chunk * S = [2,750,361,600 B, 199,990,579,200 B]` (about 2.56–186.26 GiB of logical blob extents).

Under the artificial minimum-overlap case (same ten experts every row, three of them cached), both paths have seven misses per processing unit and 8-window repeats the same logical source set 1,024 times more often: 4,096 windows versus four chunks. This is a lower-bound construction, not a claim about the prompt's actual routing. At the other extreme, chunk unions can cover nearly all experts, while windows cap at 80 per layer/window. Actual volume must be calculated from per-window/per-chunk distinct nonresident pairs and each layer's exact `blob_bytes(layer)`, not inferred from token count or total route frequency.

For batched8192 those logical extents are candidates for host-to-device staging. They are not actual DMA bytes: pinned-vs-pageable source, actual copy submission/completion, copy-engine behavior, routing, profile hits and driver staging decide that. For read_windows the corresponding blobs feed CPU jobs directly. Do not compare these two logical quantities as if they represented the same hardware transfer.

## Scheduling bounds and cache-512/auto sensitivity

With 4,096 T=8 windows, stepped `PIPE=0` and 48 layers, the same per-layer serve hook gives 196,608 service boundaries. R230's source-derived segment counts remain 97 graph submissions/window when `STRATA_VERIFY_SPLIT` is enabled/default, or 49 when disabled; the baseline receipt does not set `STRATA_VERIFY_SPLIT`, so do not assign it either count without the inherited environment receipt. Disabling that split removes kind0 graph segments, not kind1 per-layer serve boundaries. The bounds above imply 1.376M..15.729M distinct CPU expert jobs spread over those boundaries; each boundary schedules 7..80 jobs under the assumptions. A service boundary still costs a queue drain and host flag/plan path even if future residency reduced its CPU job count; it is not equivalent to one CPU job.

The current pool summary has 5 workers (receipt) and host participation depends on `ExpertPool`'s `host_works` setting; R230 source says up to 6 participating compute threads when five workers plus host participation are enabled. This is a concurrency ceiling, not a lower bound on active threads or a throughput prediction. CPU task scheduling upper/lower seconds cannot be computed without per-job service measurements and route placement. Total routed FFN row work is invariant across path selection: 32,767 × 48 × 10 = 15,728,160 routed row-expert pairs; the 8-window cache/miss split only assigns some pairs to GPU-resident experts versus CPU misses. No FLOP count is asserted here.

R228's per-layer formula yields q=3 for cache 128, q=13 (624 slots) at a full cache-512 request, and a data-dependent q for `auto`. A larger cache can reduce CPU expert jobs and host-source reads in the window route when its added resident pairs overlap repeated routed experts; it cannot eliminate the 48-per-window serve protocol, and effectiveness depends on route frequency and cache identity. In batched8192, increasing residency can reduce the nonresident set staged per chunk, but R228 source notes chunk routes can cover nearly all 512 experts, making q=13 only a small possible reduction in that high-union case. Neither `cache 512` nor `auto` is an established performance win; auto's capacity depends on the actual allocator/free-memory receipts. Keep one cache policy change per fresh process and keep route, prompt, KV, profile, workers and graph/split settings fixed (R228/R230).

## Can retained logs, trace, or sysfs measure it?

Current receipt proves the observed route, prompt span, total prefill/decode times, READY cache and normal closure; it has no per-window miss/CPU-job/blob-byte histogram and no H2D byte counter. Existing code has aggregate counters (`Drive::cpu_ms`, `multi_misses`, `multi_entries`, cache hits, and dispatch `ms_plan/ms_actq/ms_jobs/ms_run` at `generate.cpp:1003-1015`, `expert_source.cpp:2811-2822`). Its normal summary is decode-round scoped (`generate.cpp:12495-12511`); it cannot be reassigned to the earlier prompt interval after the fact. The retained receipt omits such a prompt summary.

`STRATA_USAGE_DUMP` is an optional total routed-frequency map emitted at `generate.cpp:12512-12528`; it loses which distinct misses repeated per 8-row window or 8192-token chunk, and it is not a byte or transfer counter. `STRATA_POOL_TRACE` emits and flushes multiple records per dispatch (`expert_source.cpp:2570-2576`), so a prompt could produce millions of lines and alter the measured path. It is not a suitable production-run probe. Read-only host `proc`/sysfs snapshots can show aggregate scheduling/memory/device occupancy where exposed, but they cannot attribute DDR/page-cache reads or PCIe bytes to expert pairs, nor distinguish DMA service from CPU blob use. Tracefs/driver profiling is excluded during Main and aggregate counters would still need source attribution. No RO trace/sysfs observation is justified while the current measurement is active.

Minimal future source-only measurement, after Main closes and only in an separately admitted fresh process: add a bounded request-scope aggregate at the existing `expert_pool_dispatch_multi` call. Snapshot/reset around each prompt `read_windows` part and `Prefill::run` chunk. Accumulate by mode, layer, and T: window/chunk count; routed row entries; distinct resident hits; distinct CPU misses (`njobs`); CPU miss row assignments (`multi_entries`); logical miss bytes (`njobs * expert_layout().blob_bytes(layer)`); and the existing inclusive dispatch/pool/service time fields. Emit one compact summary per request/route plus optionally a small fixed histogram of misses per layer-window. For batched path, additionally count each stream sequence entry and its actual submitted copy extent separately from `logical_bytes`; for windows, do not call CPU blob bytes PCIe. Snapshot boundaries must not wait on or add GPU work. This is a proposed instrumentation contract only; no source was changed and no live run should receive it. Existing verification of correctness/health/normal closure stays authoritative.

## Decision and limits

Use the official43 timing as the measured `read_windows8` baseline only. The source supports a substantial reduction in repeated logical expert work when grouping route-identical rows into large chunks, but route overlap unknowns span orders of magnitude and the 8-window implementation computes CPU-side while batched8192 stages active misses to GPU. Cache512/auto may preferentially reduce repeated CPU scheduling for window route; with 8192 chunks it can lower staged sets when hot routed pairs remain resident. Source arithmetic cannot establish how much, whether CPU/GPU compute is the bottleneck, or if either route is faster on this B570. Do not promote the Xe42 timing, T8192 heldout source case, theoretical logical bytes, sysfs counters, or decode counters as measured official43 transfer or exclusive CPU time.
