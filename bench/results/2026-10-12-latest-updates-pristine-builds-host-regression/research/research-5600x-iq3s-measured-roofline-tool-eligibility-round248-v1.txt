# R248 — Ryzen 5 5600X IQ3_S CPU roofline tool eligibility

Date: 2026-10-12. Read-only audit of WN `sync-xe-v0143-nonfinite-20261012` at the supplied identity `@0691bcdf`, existing CPU benchmark/test source, prior reports, and external references. No commands that build, test, execute a model, query a device/process, profile, run Git, clean up, or edit source were used. No measurement was performed. Main owns the running serial official-model work; this report makes no recommendation to interrupt or modify it.

## Finding

There is no existing single executable that gives a measured roofline for the exact CPU work performed by the production IQ3_S route, including host-pool scheduling. The best available minimal evidence is a three-part readout with distinct scopes:

1. `strata --hw-bench` measures a standalone CPU RAM read rate (one thread and all physical cores), separate H2D/D2H, and optionally SSD. It is a hardware ceiling, not expert-kernel throughput. The source reads a working set of `min(4 GiB, physical RAM / 8)`, pins one thread per selected physical core, and reports only the best of three passes. On a 5600X-class 125.7-GiB host, this is a 4-GiB read set. Its source does not retain the three individual timings. Do not rerun this merely to duplicate the already-recorded six-core reference: R53/R54 measured a 512-MiB RAM read test on the B570/5600X host; R365 reports a seven-sample/three-process aggregate of 36.87 GB/s. That is a useful historical effective bandwidth, not a physical controller counter. R245's separate 13.743-GB/s result was an ordinary-RAM copy control, not a read-bandwidth result.
2. The existing CPU-only `iq_avx2_parity --bench --dispatch --pairs iq3_s/iq4_nl --nt 1,8 --mb 256 --reps 5` is the closest kernel roofline. The benchmark fixes H=2560 and FF=640; `native_fmt` builds the GGUF row layout, the selected pair is active in the installed Qwen 3.8 IQ3_S pack, and 256 MiB synthetic expert blobs exceed the Ryzen 5 5600X's official 32-MiB L3. The methods include the production engine dispatch and GGML token-by-token reference. `Acts` constructs and quantizes activations before timed regions, so output is kernel-only and excludes activation quantization, pool scheduling, file/mmap reads, and GPU work. `--nt 1` models single-row expert math; `--nt 8` is an upper reuse case for an eight-row verifier window. These are not a production `read_windows8` distribution or an 8,192-row CPU run. The generated blocks have valid IQ3_S/IQ4_NL syntax, but are not a real shard's bytes.
3. The actual model run's existing `--stats` production output separates pool scheduling/service from the kernel-only microbench. In the decode section, `verify window` prints mean distinct CPU experts and routed entries per layer, while `pool multi` prints gate/up, activation-quantize, and down milliseconds and the total CPU pool-call time per round; `dispatch` separates plan, activation quantize, jobs, and run time. The final `--stats` pool lines also report total pool milliseconds per actual position and wait-park/drain/re-park phases. These counters let Main report measured CPU work and scheduling on the real route, without adding a profiler or another run. However, current production summary does not emit the prompt `read_windows8` per-layer histogram keyed by `(layer format, expert NT, distinct CPU jobs)`; prompt pool timing is aggregated. Thus current existing outputs cannot weight the microbench by the actual prompt's CPU expert groups. Do not manufacture that histogram from total routed rows or `STRATA_USAGE_DUMP`.

Use the already available production result if it contains `--stats` and the needed decode section. The first two are standalone references only if Main needs a fresh value after the serial run is closed; `--hw-bench` also opens the GPU path for copy measurements and should be run only in the separately authorized quiet post-run window. No further probe is needed if the existing R53/R54 hardware reference suffices. No existing-only measurement supports an exact production `read_windows8` CPU roofline without the missing prompt job histogram. A future minimal instrumentation change would emit a compact per-layer count at the point immediately before `run_split_multi_native`: layer, GU/down type pair, `njobs`, sum of job `nt`, and per-NT bucket counts, then correlate with the already available `ms_multi_gu`, `ms_multi_q`, `ms_multi_down`, and `ExpertPool` wait/drain/re-park totals. That is a source change and outside this task.

## Format, shape, and accounting boundaries

`iq_avx2_parity.cpp` declares `kH=2560`, `kFF=640` and uses the active representative pair IQ3_S/IQ4_NL. `native_expert.cpp` derives row size from GGML format traits and selects Q8_K for the IQ3_S GU activation and Q8_0 for the IQ4_NL Down activation. IQ3_S blocks are 256 values / 110 bytes; IQ4_NL blocks are 32 values / 18 bytes. From those source layouts, one expert's GU weights are 2 × 640 × 10 × 110 = 1,408,000 bytes and its Down weights are 2,560 × 20 × 18 = 921,600 bytes, totaling 2,329,600 bytes (2.22 MiB), excluding alignment. The input activation buffers are 2,920 bytes/token for Q8_K (10 × 292 bytes at H=2560) and 680 bytes/token for Q8_0 (20 × 34 bytes at FF=640). For an expert with NT rows those buffers are per row; they do not multiply the expert weight payload by NT. The microbench constructs them outside its timing, making weight/kernel service and activation conversion separate quantities.

The production native pool groups duplicate routed IDs inside each verifier window into one job and increments that job's `nt`; its pool executes GU, per-job intermediate quantization, then Down. `--stats` currently reports actual decode `CPU experts distinct / routed per layer`, so decode has a valid routed-work denominator. For an eight-row prompt verifier window, a CPU expert can have NT 1 through 8 depending on row overlap and placement. The existing microbench only samples NT endpoints and does not imply all experts get eight rows. `native_expert_parity` can read real GGUF expert blobs for correctness but has no timing mode. `pool_test` and `expert_multi_test` exercise legacy Q2_0 kernels, not the active IQ3_S/IQ4_NL native path.

The 8,192-token batched prefill is not a CPU matrix-size counterpart. In the current source, that route's expert products are batched/staged for the GPU; the CPU performs routing/issuing and source staging, rather than 8,192-row IQ3_S GEMM. The CPU AVX2 native expert contract and `ExpertJobMulti` are limited to `MAXT=8`. Do not benchmark or report `--nt 8192` for CPU, and do not use `--kernel-bench` GPU results as a CPU roofline. The batching arm's distinct CPU question is issuer/host staging, already covered separately by R246 and not a CPU expert kernel result.

A useful, finite CPU-only kernel command after the current run closes is:

```text
<free-WN0691-build>/iq_avx2_parity --bench --dispatch --pairs iq3_s/iq4_nl --nt 1,8 --mb 256 --reps 5
```

Record the executable/source hashes, `iq_avx2_parity`'s printed CPU name and `avx2`/`avx512` bits, selected variant, and `STRATA_IQ256_GATHER`, `STRATA_NO_AVXVNNI`, and `STRATA_IQ_MT_MIN` environment values. For a default Ryzen 5 5600X dispatch comparison, leave those variables unset as they would be in the serial control; the executable checks the CPU features itself. The Ryzen 5 5600X is a six-core/twelve-thread Zen 3 desktop CPU with 32 MiB L3 and DDR4-3200 support per AMD's [official product specifications](https://www.amd.com/en/products/processors/desktops/ryzen/5000-series/amd-ryzen-5-5600x.html). Confirm AVX2 and AVX512 availability from this executable's actual CPUID output, not from model-name assumptions. Do not include `STRATA_FORCE_AVX2=1` unless an intentional forced-dispatch comparison is separately labeled.

For kernel parity, the finite companion gate is:

```text
<free-WN0691-build>/iq_avx2_parity
```

It tests deterministic random IQ blocks across widths and checks custom rows against GGML's dot reference (relative error limit 1e-5), but it is only a kernel parity gate. It does not establish model-level quality. Any worker/policy change still needs identical-request output/quality and full fault/correctness checks against the closed serial official baseline. Do not treat a kernel-only rate multiplied by routed bytes as a model prediction; compare only after matching the actual format and NT histogram, and keep activation quantization, job construction, pool scheduling, and route count as separate terms.

## External implementer evidence

An implementer article on [running a 200-GB DeepSeek MoE on one RTX 3090](https://ai.thesatyajit.com/articles/big-moe-one-3090) makes a useful distinction between CPU arithmetic service and memory bandwidth: it reports a model-derived 0.20-ms CPU-expert constant and 66-GB/s implied expert-byte rate, then explicitly reasons that its EXL3 decoder is CPU-limited on 22 Zen 3 cores. Those constants are not a measured 5600X or IQ3_S rate: the model, EXL3 format, CPU core count, and GPU differ, and the article describes the byte rate as arithmetic from a configured per-expert constant. It supports measuring arithmetic and pool service separately from DDR bandwidth, not reusing its number.

The earlier [KTransformers AVX2 MXFP4 implementation report](https://github.com/kvcache-ai/ktransformers/commit/9481291) reports grouped MXFP4 measurements on dual-socket EPYC 7452 and a different model/format. This supports grouped decode as a useful design in that workload, but not direct performance transfer to Strata's IQ3_S blocks, IQ4_NL Down, Ryzen 5600X, or `read_windows8`.

## Decision

Do not repeat R53/R54's hardware sweep or R245's host-copy control, and do not claim they measure IQ3_S service. If the active run already retained `--stats`, consume its actual route and pool counters first. If Main still needs a CPU-only kernel reference, the single target command above supplies per-expert GU/Down timing at NT1 and NT8 with the active representative shape and kernel dispatch. Keep its output labeled synthetic one-thread kernel-only. The missing prompt-side CPU `(format, NT, job-count)` histogram remains the precise blocker to converting that timing into an actual `read_windows8` CPU work ceiling. A batched8192 CPU GEMM ceiling is inapplicable because that branch delegates the expert matrix work to the GPU.
