# Pristine Xe v0.1.42 initial expert-cache slot-84 mismatch (R220)

Date: 2026-10-12. Read-only comparison of pristine Xe v0.1.42 and the qualified Xe host-issuer-ledger source, plus compact startup receipt/log and earlier R303-R305/R154-era evidence. No payload/profile read, retry, GPU/model/build/test/import/AST, Git/process query, cleanup or source edit. The report ranks hypotheses; it does not identify a confirmed runtime or driver defect.

## Observed failure and exact check

The new pristine startup receipt is an ordinary failed startup: `engine.stderr` records `ExpertCache::verify_slot: slot 84 differs from the arena at byte 0 (of 2662400)`, stdout contains no READY, owner closure observes child exit 1, with no forced cleanup. Parent's kernel/fault and devcoredump review says no Xe fault/dump. The same log says the expert source was a 46.84-GiB native IQ3_S arena, “one mapping registered for device copies in 5 pieces,” loaded at 1.67 GiB/s; `--expert-cache 128 --expert-cache-per-layer` was converted into 144 physical slots, three per layer. It reached the immediate profile-fill verification, before READY and before any GEN.

`generate.cpp:4273-4295` derives per-layer sizing from each layer's actual packed `blob_bytes`, and `ExpertCache::open_sized` (`expert_cache.cpp:366-390`) makes 256-byte-aligned slot offsets. Per-layer admission (`:432-461`) gives each layer a contiguous quota; slot 84 is the first of layer 28's three slots under the logged 48-layer / 3-per-layer geometry. This is an index interpretation, not a claim about the private `profile[0]` pair: its identity was not opened. The failing 2,662,400-byte extent equals the reported check length; the checker logs only the first differing index, not either byte value or the mismatch hash.

At `generate.cpp:4446-4471`, the startup loop resolves a profile pair's source blob, calls **blocking** fill for that exact layer's blob length, then resolves `profile[0]` again and verifies its assigned cache slot. `fill_slot_blocking` (`expert_cache.cpp:485-502`) uses `gpu::copy`; `verify_slot` (`:531-568`) synchronously copies that same slot to host and memcmps it against the same source pointer. Xe `gpu.cpp:232-234` waits on the compute-queue copy event for both directions. Thus this is not an uncompleted queued-fill check. A reported mismatch means one of the copied/read-back bytes differed at comparison time. It does not by itself reveal whether H2D, D2H, or the underlying source/destination access was wrong.

## Ranked source-supported hypotheses

1. **Prepared anonymous mapping / device-copy registration visibility (leading, unconfirmed).** The startup log identifies the exact path relevant to R304: a single anonymous mapped arena, prepared for device copies in five pieces, then host-populated by the native loader, with no mlock. `PinnedArena` (`pinned.cpp:94-121`) overmaps and aligns the `MAP_PRIVATE|MAP_ANONYMOUS|MAP_NORESERVE` region, calls `prepare_for_device_copy` for each piece before loader population, and later `ArenaExpertSource::open` passes layer pointers into `load_experts_gguf` (`expert_source.cpp:2422-2565`). `blob()` returns a stable pointer into that arena (`:2718+`). The source therefore has the prepare-before-host-write ordering, and the device copy reads directly from this prepared mapping. R304 already establishes this is permitted by the public API contract, not caller UB; an implementation/page-population/import visibility problem remains a coherent hypothesis. The immediate slot byte mismatch is consistent with a bad H2D source view, but no returned bytes were recorded, so it does **not** prove stale pages/COW or driver behavior.

2. **Host-to-device cache copy or device cache/readback path.** Both copies report success: otherwise `fill_slot_blocking` or `verify_slot` returns an operation error rather than a memcmp mismatch. A success status does not prove correct content. A transfer implementation could read the wrong registered host backing, or a destination/readback addressing/cache issue could produce different bytes. The current receipt has no source/destination pointer identities, a bounded byte fingerprint, or independent post-copy hash, so it cannot distinguish this from (1).

3. **Wrong source blob/layout or profile-to-slot mapping.** The startup path validates native expert layout metadata, forms contiguous layer bounds, loads the GGUF role slices into the packed arena, and derives `blob_offset`, `blob_bytes`, profile lookup, slot size, fill length, and verify length from the loaded layout. `open_sized`'s layer-major quota list and `admit`/`slot_of` are internally consistent for the logged geometry. Also, the verifier compares the cache against the same `ArenaExpertSource::blob()` mapping used for the fill; a static wrong source value alone would be copied consistently and should still pass. This makes a simple metadata/slot-size arithmetic mismatch lower-ranked for this exact self-check. It cannot be fully excluded without independently checking the profile pair, host pointer/offset and bounded source bytes, or finding concurrent mutation/corruption. No source in the audited startup interval intentionally mutates the arena after loading; the loader joins its workers before `open` returns.

No source evidence supports interpreting “byte 0” as “all-zero destination,” “first piece failed,” or “layer 28 is generally corrupt.” It only says index zero is the first differing byte in one tested extent. One pair was checked; no multiple-slot or piece-specific result exists.

In `src/core/expert_cache.cpp`, fill, blocking copy, readback, and slot methods are unchanged. The diagnostic branch adds profile length and duplicate-pair rejection in `read_expert_profile` (`:61-96`); those checks do not change this transfer path. `device.cpp` differences inspected are an architecture-tag include removal and a kernel-preload environment switch, not the copy path. Therefore that qualified tree does not currently supply an independent source fix for the pristine startup mismatch; any branch-only instrumentation should not be mistaken for a correction of H2D/registration semantics.

R303 already described the generic mismatch and declined to localize it. R304 already reviewed the API contract and the prepare-before-populate concern. The new useful evidence is this exact pristine v0.1.42 receipt, its five-piece/46.84-GiB arena and 144-slot configuration, and source-tree equality of the relevant pinned mapping implementation to the diagnostic tree. R305's static host-USM lifetime review remains a source argument only; it does not establish a host-USM startup pass. No earlier conditional proposal is upgraded to a confirmed cause.

## Minimal safe CPU/synthetic discriminators for Main

- Add/run a CPU-only pure-layout fixture (no source/profile/model payload): use 48 synthetic layers with distinct blob lengths and quota 3; assert `open_sized` offsets equal the 256-byte prefix sum, each layer maps to exactly `[3*l,3*l+3)`, and admit/slot_of returns the same slot through the first pair, including layer 28/slot 84. Generate distinct in-memory `(layer, expert, offset)` byte patterns, copy exactly `blob_bytes(layer)`, and check every byte and guard region. This can clear ordinary geometry/index/length arithmetic but cannot emulate a GPU transfer.
- Add a host-only synthetic registration-partition fixture for the `register_pieces` interval-selection arithmetic with `max_alloc` much larger than every synthetic expert, and independently with an expert at/over the boundary. Assert adjacent non-overlapping coverage of `[0,capacity)`, every expert source extent lies within one registered piece when promised, and final padding treatment. This validates bounds/cut selection, not Level Zero import behavior.
- For any future actual device localization, keep `verify_slot` enabled and record only source kind, profile layer/expert and layout offsets, device/cache slot and resolved offsets, source/dest pointer classes, copy event status, and a small fixed byte prefix plus SHA-256 before H2D / after D2H (not a tensor dump). A separately admitted fresh `STRATA_ARENA_HOST_USM=1` run is the narrow comparison already outlined by R304/R305; it changes host allocation/import path and therefore supports, but does not uniquely prove, the mapping hypothesis. This report requests no retry or GPU action.
