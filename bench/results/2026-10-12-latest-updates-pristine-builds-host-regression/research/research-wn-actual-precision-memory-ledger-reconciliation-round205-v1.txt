## Source geometry and accounting rules

Current Xe source declares N=2,560, HC=4, D=10,240, LR=320, K=10, C=10,240, ZV=6,144, HV=48; the model geometry has SSM state size 128, 48 value heads, convolution width 10,240, 36 GDN layers and 12 QSA layers. QSA has two KV heads, head dim 256, index block 4 and top-k width 2,048, so the persistent prefill selection cap is 2,051 cells. Main prefill allocates one reusable workspace region of `max(GDN scratch, QSA scratch, MoE scratch)`, because the attention and MoE halves run sequentially. The region is reused across layers and is not a sum of those three sets.

`Alloc::take<T>` charges each take `round_up(payload + 256, 256)`; `Prefill::bytes_needed` follows the source take sequence and then adds 8 MiB alignment slack. My table gives unrounded payload sums for clarity, so the source-request total is slightly higher. `bytes_needed` also includes the external stage/ring, 150 MiB of group FP16 expert dequant buffers in the fallback case, PLE embedding storage, token/step arrays and other workspace. Source path: `src/prefill/prefill.cpp`, especially `gdn_set_bytes`, `qsa_set_bytes`, `moe_set_bytes`, `carve`, and `Prefill::bytes_needed`; persistent state comes from `src/core/session.cpp` and `include/strata/plan/plan.hpp`.

## Exact persistent GDN and saved-state sizes

For one GDN layer, persistent recurrence is `(128,48,128)` FP32 = 3,145,728 B. Conv history is `(3,10,240)` FP32 = 122,880 B. The total is 3,268,608 B/layer. All 36 layers therefore request **117,669,888 B (112.2 MiB) per full-model sequence**, independent of whether the context is 8K, 64K or 262K. This is fixed session state, not an evictable expert cache and not part of the chunk-sized prefill workspace.

If only the recurrence matrix changes to FP16 while convolution history stays FP32, the source-size saving is 56,623,104 B (54 MiB) per sequence. If both recurrent and convolution state are halved, the saving is 58,834,944 B (56.1 MiB). No such change exists in the inspected source: `GdnBuffers::state` and `conv_state` are `float*`; prefill and verifier pass the session's `float*` recurrent state to the recurrence path. The kernel loads and stores state elements in global memory (`src/kernels/xe/native_gdn.cpp`), so FP16 storage could reduce per-step state bytes in principle, but source byte savings are not an observed bandwidth or latency gain.

The verifier uses the session's same `ss.gdn_state` pointer. Its device arena has window-sized per-layer temporary `qkv_L`, `h_L`, `gate_L`, and `beta_L` arrays, plus QSA/attention, expert-part, logits and PLE scratch. It does **not** carve a second full GDN recurrent-state array. It does allocate small tail/history snapshots (`tail_snap_`, `hist_snap_`) for indexer/PLE rollback, not a copy of the 112.2-MiB GDN state. Verifier scratch scales with its configured `max_t`, not Prefill's T=8192; no verifier maximum was supplied here, so its total is not represented as an 8192-row request.

A saved conversation checkpoint copies the GDN bytes into host-side checkpoint storage: one full-layer checkpoint therefore adds another **117,669,888 B of host memory**, not GPU memory. Each retained checkpoint can add another such copy. Disk save similarly serializes running state. A session save or verification snapshot must not be counted as a duplicate full GDN allocation on the GPU. Conversely, an independently live second sequence has its own persistent device state.

MoE counts assume the pure FP16 fallback because that is the path with `Xs`, `GU`, and `Hh`; the build/model's actual MMQ selection is not inferred. The compact option is an explicit conditional path and is only admitted for pure fallback on the required ordered queue. Source mode and chunk settings must be recorded in any actual receipt.

The base row arrays + PLE embedding + GEMM scratch + expert group buffers + one shared region already total about **3.20 GiB** in fallback/no-compact and **2.50 GiB** in fallback/compact, before step arrays, guards, stage/ring slots, other owners, runtime allocations and any other process. Those are requested workspace payload subtotals, not an admission guarantee or a measured VRAM delta. Actual `Prefill::bytes_needed` further depends on `ring_slots(T)`, `MAXBLOB`, expert group size, active MMQ/fallback branch and session context. If MMQ is active, fallback `Xs/Hh` and group dequant storage are different/absent, MMQ has its own Xq/H/Hq buffers, and compact mode cannot be presumed effective.

## Context and 10-GB fit relevance

Persistent GDN state is context-independent. QSA KV and indexer storage are separate and context-dependent: at 64K with ordinary FP16 K/V, the 12 QSA layers' K/V payload alone is about 1.50 GiB (24,576 B per token); indexer pooled-key payload adds about 96 MiB, before page/allocation metadata. INT8, Q4, streaming and elastic modes change which bytes are on the GPU versus pinned host memory. These cache bytes must not be mixed into the transient prefill region or counted from a nominal full-context logical extent without reading the effective QSA state mode.

The largest directly source-supported *capacity* reduction among the named work buffers is compact MoE row-bounded scratch: 810 MiB from the shared set at T=8192, if its guards and fallback route apply. A separate FP16 `Dm` storage experiment has a 400-MiB theoretical workspace saving and may halve the write/read payload for those rows; it is an arithmetic/quality intervention and is unimplemented. Halving `GU` would save 200 MiB in the non-compact fallback shape. By comparison, halving only persistent recurrence saves 54 MiB per sequence; its value is session-count capacity and potentially repeated decode memory traffic, not a reliable fix for a several-hundred-MiB Prefill allocation gap. Hh is already FP16. Router logits are just 16 MiB and also control expert choice.

This ordering says nothing about which buffer is the measured bottleneck or whether any candidate crosses B570's fit boundary. The 10-GB label is physical capacity, not usable budget; actual owners include weights/cache, expert staging/cache, QSA state, Prefill/Verifier arenas, runtime overhead, page rounding and competing display allocations. Need an actual B570 allocation/owner ledger to establish free bytes, the largest allocation, or a successful T8192/64K request. No bandwidth estimate is made from Intel's theoretical 380 GB/s, and no transfer/quality gain is claimed from requested capacity.

## Quality evidence boundary

R204's DAMP paper result supports considering FP16 *recurrent-state storage* as a test arm on a related Qwen GDN hybrid; it does not validate this WN source's GDN recurrence, its model pack or 262,144 cells. At most, current source inspection says a state-size change would affect persistent `ss.gdn_state`; it leaves the much larger chunk-sized MoE Dm/GU and attention workspace separate. A 64K allocation/context record is not a quality benchmark, and it does not prove full 262,144-cell use or quality. Retain FP32 state until a correct-format counterfactual is implemented and tested on this exact model; do not frame that conservative default as a published universal requirement.
