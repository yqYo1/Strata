## Contract in one sentence

`logit_bias` is a sparse, request-scoped map from **actual tokenizer token ID** to finite FP32 additive logit penalty, with exactly `-100` denoting a hard ban; expand it to a dense `n_vocab` bias only for the final target-head sampler, apply it before penalties and filtering on every supported non-batched target pick, and clear/replace its storage only after the prior reader on the owning final-stage queue has completed. It is vocabulary-sized, independent of context length, and must not alter the configured 262,144-token context/KV geometry.

## Exact minimal source boundary

The safe W337 source has no `logit_bias` implementation. `db0bb964` is the smallest upstream feature concept, but a raw cherry-pick is not the correct delivery: it was authored against a different source state, and its API serializes each bias with `:g` (six significant digits), which can round a finite value such as `-99.9999999` to the hard-ban spelling `-100`. R172 v2 changed the transport formatter to `.17g` and supplies safer request-buffer ownership. Preserve W337's existing three request-accounting changes in `serve/server.py`; graft the narrow hunks around them.

## Validation and hard-bound semantics

Python receives sparse API values and must bound IDs with the loaded tokenizer's `len(tok.tokens)` when available; the native parser independently bounds IDs by the loaded output head's `n_vocab`. Do not use `max_context`, request token count, vocab subset size, or the 262,144 context ceiling as a substitute for vocabulary validation. Native protocol parsing must reject duplicate keys/IDs, bad delimiters/trailing text, integer overflow, embedded NUL, non-finite values, `|bias| > 100`, and an all-vocabulary ban. HTTP forms are an object `{ "id": number }` or list `[[id, number-or-false]]`; list `false` is the hard-ban shorthand, while JSON booleans as numbers (including `true`) are rejected. Exactly the numeric value `-100` maps to `-infinity`; a nearby finite penalty must stay finite even if conversion to `float` rounds its stored payload to finite `-100.0f`. That requires the parser to compare the parsed `double` against `-100` before FP32 conversion and the HTTP/native text round-trip to use enough precision (`.17g`), not `:g`.

The configured context remains 262,144 and no context-dependent buffer is introduced. The dense table costs `4*n_vocab` bytes when a nonempty bias is first used, plus host staging; it is not `4*n_vocab*context`. At Qwen vocab 248,320 this is **993,280 bytes (0.947 MiB) of device payload per final-head verifier**, plus host state/event/runtime overhead. The no-bias request remains null and allocates no device bias table. A pipelined second verifier may own a second such allocation. Because this is added to a model that can be near a VRAM admission edge, include those exact per-verifier bytes in any admission/accounting, but do not change context, KV, verifier window, or context allocation formulas to make it fit. This source arithmetic does not prove full-context GPU fit.

## Queue and pointer lifetime requirements

A bias pointer is device-USM in the final stage's device/context and is read by asynchronous sampling kernels outside the captured forward graph. Before replacing or clearing it, the prior readers on that stage's actual `cs_` queue must finish. A newly uploaded host source must remain alive until its copy is known complete. On submission or completion uncertainty, keep the source alive, mark the owner unusable, and fail the request/stop reuse; do not recycle storage or retry while a possible copy still references it. Destructor teardown must drain the owning compute/copy queues before destroying the graph, event, device array, or host source. W337 provides `gpu::copy_async`, event/wait helpers, `Runtime::wait`, and fail-stop owner-aware `gpu::free`; do not assume an ordinary `copy()` on a different queue orders against `cs_`. R172 v2's `LogitBiasState` seam (injectable drain/prepare/upload/complete operations) is suitable for isolated CPU lifetime tests, but that candidate is source-only and not qualified.

The upload can be lazy and persistent per final verifier: keep dense host state for equality/clear semantics, update the existing device allocation only when changed, avoid allocation/copy for null/empty or unchanged values, and drain before mutating a buffer that a previous request may still read. `set_sampling` must bind the owned pointer after every sampling-parameter replacement. No per-request device pointer may be saved into a graph or a mapped MTP parameter block.

## Sampling and run-path coverage

The bias is **additive before** repeat/frequency/presence penalties, top-k, top-p, min-p, temperature, and pick. Greedy must receive it too; gating only on `temperature > 0` is incorrect. Hard-ban `-infinity` must bypass penalty arithmetic so negative/zero repeat penalties or `+infinity` raw logits cannot resurrect the token. Ordinary top-k may reread bias along with logits during each candidate-selection round; the large-vocab split path needs the bias in stage 1 before candidate reduction. These are existing target sampler routes, not model-expert algorithms.

Supported: single-request `GEN` and `GENI`; regular `Verifier::run`; pipelined `Verifier::pl_finish`; each target-head sampling call reached by the normal model variants using that engine. In a layer split, only the terminal/head verifier reads the pointer; earlier stages forward the setup call but allocate no table. Coupled MTP drafts remain unbiased proposals and target verification is biased. Deliberately unsupported in the minimal unit: continuous `--batch` / slot sampling, because current server and native contract reject it before mutation. Do not add bias into `sample_rows` while batch is rejected; if batch support is later desired, it becomes a separate per-slot ownership/protocol change. Raw-logit/logprobs calculations stay unchanged.

## CPU/mock tests vs GPU correctness

The meaningful CPU/mock checks are narrow and necessary but insufficient:

- `python3 -m unittest serve.test_logit_bias` covers both forms, ID/value validation, capability and batch rejection, 17-digit boundary transport, effective defaults/clear, HTTP rejection before SSE/generation, and supported fake-engine request serialization. It makes no GPU or model claim.
- CMake's `logit_bias_test` / `ctest -R '^logit_bias_test$'` covers native parsing including actual-vocab and precision boundary, plus request state equality/change/clear and injected drain/allocation/submission/completion ownership failures through a host fake. It does not exercise a real SYCL queue.
- Existing `serve.test_server`, `serve.test_parallel`, and `serve.test_request_accounting` are useful unaffected-regression coverage; retain the W337 request-accounting tests while adapting `server.py`.

The separate GPU correctness gate is the existing `sampler_parity` target extended for: unchanged no-bias path; greedy positive bias and hard ban; finite near-`-100`; penalty ordering and ban immunity; ordinary and split large-vocab sampler paths; clear/change persistence; and unchanged raw logits. After that, only a newly owned bounded full-engine/API validation can establish one real model request, A→empty→B reset, `GENI`, MTP target verification, captured-window warming then changed bias, and memory fit. No GPU numeric or quality result is established by the upstream source or prepared parity fixtures. Do not launch the pristine unsafe long-context host-USM/PLE route as part of this feature review.

One concrete source-level GPU sampler issue remains open before claiming hard-ban correctness: the R172 sampler audit found no-candidate reduction paths initialize/convert an empty `-infinity` candidate set to token ID 0. The API correctly rejects a request that explicitly bans every vocabulary token, but an admissible bias can still leave every *effective* model logit at `-infinity` (or all unbanned logits non-finite); if token 0 is banned, the fallback can violate the ban. A GPU-side fix must surface a no-candidate/error result or otherwise guarantee a permitted ID; it must not silently return zero. This is not testable by the CPU/mock protocol fixtures.

## Recommendation

Port the API/parser, native request protocol, final-head sampling path, owned device-state lifecycle, MTP pointer clearing, and matching CPU/mock/parity tests as one minimal feature. Keep the 262,144 context and all CPU/expert inference algorithms fixed. Use `.17g` and the R172 queue-owned staging discipline rather than the six-significant-digit upstream formatter or unsynchronized per-request upload. Resolve the empty-effective-candidate sampler case before marking bans correct. Then do the CPU tests first; GPU parity and real-model/API validation are separate, pending owner-controlled gates. This report is static source evidence only; it does not validate R172 candidate correctness or authorize execution.
