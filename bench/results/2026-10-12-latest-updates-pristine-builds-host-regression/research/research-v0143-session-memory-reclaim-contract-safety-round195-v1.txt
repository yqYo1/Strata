## Finding: one concrete cgroup v2 undercount of protected usage should be fixed

The official sampler credits clean inactive cache against every cgroup `memory.max` and `memory.high` budget, but does not inspect `memory.min`. The kernel's official cgroup v2 documentation says that usage within a cgroup's effective `memory.min` boundary is not reclaimed under any conditions (and the effective protection is constrained by ancestor minima). A cgroup can therefore report clean `inactive_file` that is not available for a new SAVE allocation while it is protected by `memory.min`; `reclaimable_cache()` may credit that amount and `combine()` can overstate room under that cgroup's max/high. If the overstatement crosses the SAVE peak-plus-floor preflight, the subsequent allocation can fail or trigger cgroup OOM rather than being refused before capture.

Relevant official source: `src/core/conversation_memory.cpp` parses only `memory.max`/`memory.high` and `memory.current` in `scan_levels`; `reclaimable_cache()` subtracts dirty/writeback from inactive file but has no protected-min adjustment; `combine()` uses `current - credit` for each limit. The official helper then acts on that allowance in `include/strata/core/session_save_reclaim.hpp` and the SAVE handler. Kernel source: [cgroup v2 memory interface documentation](https://docs.kernel.org/admin-guide/cgroup-v2.html#memory-interface-files), specifically `memory.min` effective boundary and `memory.stat` definitions; the page also says `memory.high` throttles and applies heavy reclaim pressure while `memory.max` is the hard limit. This is a source-level accounting gap, not a runtime observation.

Before porting this sampler as “safe available RAM,” account for the protected `memory.min` usage at the relevant ancestors when calculating reclaimable credit. The safe conservative fallback is to remove the protected portion from the cache credit (or give no cache credit where the effective protection cannot be determined). `memory.low` is best-effort protection and may cause additional reclaim pressure; it is a performance conservatism choice rather than the hard non-reclaimable condition that makes the min omission unsafe. No such v2 concept applies to the v1 branch.

## Other sampler contract review

- **Ancestor limits:** the v2 scan obtains the process path from `/proc/self/cgroup`, constructs visible mount-root-to-process directories, and takes the minimum remaining room across each finite `memory.max` and `memory.high`. `memory.current` is hierarchical and the kernel docs explicitly define it as the cgroup plus descendants. The v1 branch follows the `memory` controller path, checks `memory.limit_in_bytes` against `memory.usage_in_bytes`, and skips the near-2^63 v1 unlimited sentinel. This is directionally consistent with Linux's hierarchical accounting contract. V1 `memory.use_hierarchy` is documented as enabled by default and disabling it deprecated. One documented boundary remains: a container cannot see an ancestor outside the mounted/visible hierarchy; the code only accounts the deepest visible group, as its header states.
- **MemAvailable:** the parser requires exactly one decimal `MemAvailable: <n> kB` record, rejects malformed/duplicate/overflowing values, and converts with a checked `*1024`. The source returns unknown if MemAvailable is unavailable, so native admission fails closed. This matches use as a host-availability floor term; it does not count swap as RAM.
- **Inactive-file credit:** for v2 it clamps `inactive_file` to that cgroup's `memory.current`, subtracts `file_dirty` and `file_writeback` with saturating-to-zero behavior, and fails to zero credit if an applicable field is malformed. For v1 it uses hierarchical `total_inactive_file`, `total_dirty`, and `total_writeback`; the kernel v1 docs define `total_<counter>` as the hierarchical counter and state that inactive-file includes reclaimable file/LazyFree pages. Subtracting all dirty/writeback from the inactive estimate is conservative because those totals may include pages outside the inactive subset. The `memory.min` protection finding above is the exception to the current “clean inactive means reclaimable” assumption.
- **Explicit operator cap:** `--memory-limit-mib` wins over `STRATA_MEMORY_LIMIT_MIB`; when the operator cap is active and cgroup scanning is unusable, `sample_host_memory` returns unknown instead of relying on host `MemAvailable`. If cgroup root usage is not visible, it uses `MemTotal - MemAvailable` as the measured usage basis, which can conservatively charge unrelated host usage against the cap. The cap conversion has input range checks before MiB-to-byte conversion. `conversation_memory_admit` avoids subtraction underflow by checking `available >= floor` first and avoids addition overflow by checking `allocation <= available - floor`.
- **Missing/unreadable cgroup data without an explicit cap:** the official implementation intentionally warns once and falls back to MemAvailable. This is fail-open relative to an invisible container limit, even though explicit operator cap is fail-closed. It is a documented compatibility fallback, not a parser arithmetic defect. A deployment that must never exceed a hidden ancestor limit needs to set `--memory-limit-mib`; whether to change the default fallback is a product policy decision. Treat this as a residual operating boundary, not proof that hidden ancestors are covered.
- **Rounding and size arithmetic:** `/proc/meminfo` kB conversion checks `UINT64_MAX/1024`; cgroup files are parsed as unsigned decimal with overflow detection; high/max/current bytes remain byte-granular. `conversation_memory_admit` is safe at `UINT64_MAX`. SAVE peak arithmetic uses saturating add/multiply (`session_save_peak_bytes`), and an unknown/overflowed size becomes `UINT64_MAX`, which prevents reclaim and admission rather than guessing. Native diagnostics floor bytes to MiB, while the Python retry helper adds a two-MiB margin to compensate for down-rounded need/floor values; psutil remains retry scheduling telemetry, never the native admission authority. The live admission is a sample, not a reservation: concurrent outside allocations can race it, as the header documents.
- **v1 usage accuracy:** kernel v1 docs call `memory.usage_in_bytes` a fuzzy/approximate value and recommend memory.stat combinations for a more exact figure. The official sampler uses this interface. This is an inherent sampled guard with a 2560 MiB default floor, not mathematically exact accounting; test around the boundary and keep the explicit floor. No source proof here shows the documented fuzz can exceed the built-in reserve, so this review does not recommend a change solely from that caveat.

## Reclaim helper and SAVE selection review

`session_save_reclaim()` chooses `session_deepest_checkpoint(chain)` first and computes `session_save_peak_bytes` for that exact selection. It does nothing when the probe is unknown, the size saturates, or current room already meets the peak plus floor. Under known pressure it reclaims in order: optional retained/reuse KV buffers (`take_reuse`, not authoritative live/device state), oldest evictable parked conversations (the cache excludes entries holding pins), then non-pinned non-selected checkpoints. It re-probes after every release and stops as soon as admission fits. The reverse erase/index update preserves the selected checkpoint and deterministic first-deepest tie. `session_save_checkpoints()` runs only afterward and recomputes the same selection before copying one checkpoint; the SAVE handler's expensive live-state capture and KV source creation follow the admission. This preserves copy selection and avoids freeing the data being serialized. The core helper's `bad_alloc` test and helper cases cover pinned/selected preservation, exact same selected ids/storage, no mutation on unknown/no-pressure/overflow, one-at-a-time stop, and final refusal before copying.

No helper-level defect was found in this order or preservation logic by static inspection. W337 already has the safer lifetime/protocol side that must be retained when integrating: one native SAVE/RESTORE exchange, strict `SERR` parsing; malformed/out-of-step response kills/ends the process; `FATAL` during RESTORE is fatal and prevents unsafe in-place continuation. W337 has no native reclaim helper and its SAVE sampler is MemAvailable-only; do not port the official helper by replacing W337's fatal RESTORE path or treating Python psutil as native RAM authority.

The cgroup ancestor parser, v1 sentinel, max/high min-combination, clean/dirty/writeback credit, unreadable/malformed cgroup fallback, explicit-cap failure behavior and overflow paths therefore lack deterministic source-level test cases in that test file. No tests were run in this review. Add fixture-driven pure tests before treating those branches as qualified; in particular cover a nonzero effective `memory.min` with inactive-file credit, and explicit-cap unknown/fail-closed versus no-cap fallback.

## Primary kernel references

- [Linux kernel cgroup v2 documentation](https://docs.kernel.org/admin-guide/cgroup-v2.html#memory-interface-files): `memory.current` includes descendants; `memory.min` hard protection; `memory.high` throttle/reclaim boundary; `memory.max` hard limit; `memory.stat` file dirty/writeback and LRU-state definitions.
- [Linux kernel cgroup v1 memory documentation](https://docs.kernel.org/admin-guide/cgroup-v1/memory.html): `memory.limit_in_bytes`, `memory.usage_in_bytes`, `memory.stat` counters and hierarchical `total_<counter>` definitions; usage-in-bytes fuzz caveat; hierarchical accounting is on by default and disabling it is deprecated.
