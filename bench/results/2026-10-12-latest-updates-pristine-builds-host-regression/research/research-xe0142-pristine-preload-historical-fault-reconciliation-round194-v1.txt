# R194 — Xe 0.1.42 all-kernel preload and historical B570 startup failure

Date: 2026-10-12 (Asia/Tokyo). Read-only source and retained-evidence reconciliation. No build, tests, compiler, AST/import, runtime/GPU/device/process query, model run, Git mutation, or cleanup. This report classifies the old failure stage and assesses source-path overlap; it does not assert that pristine Xe 0.1.42 is universally unsafe.

## Finding

Xe da3d's `Runtime::preload_kernels()` is the same eager compilation operation implicated by the historical B570 startup failure: it enumerates `sycl::get_kernel_ids()` then calls `sycl::get_kernel_bundle<bundle_state::executable>(context_, {device_}, {id})` for each ID. In Xe da3d this sweep is unconditional; the explicit-zero `STRATA_PRELOAD_KERNELS=0` guard present in W337 and in the historical disabled candidate is absent. It starts beside model loading before request work. The requested host-handoff options (`--serve --spec 4 --short-read 65536`, `STRATA_VERIFY_STEPPED=1`, `STRATA_VERIFY_PIPE=0`) do not gate that call. `wait_preload()` joins the thread before selected host memory probes, but does not suppress, filter, or make the preload optional.

Accordingly, an unpatched da3d executable built and run with the same B570 stack would repeat the same source-level all-ID bundle-build requests. The historical receipts tie the failure to LLVM 7.1.1-based host/runtime artifacts and Level Zero loader/driver identities, but the failed process did not retain mapped IGC/FCL provenance. A current da3d binary/toolchain runtime tuple has not been built or executed in this audit. Therefore identical failure is a credible, specific risk when reusing those components, not an established result for da3d's exact binary/provider tuple. The prudent distinction is: do not claim the unpatched route is safe based on unrelated host-handoff flags; also do not label the latest release categorically unsafe without its exact mapped compiler/provider and failure evidence.

## What failed, at which layer

The retained `xe-native-dequant-prefill-model-root-v3/n64-g16-off/record.json` binds the failing process to base source `b72640fff05098f1762cb3bf9c427a5f8d7db31c` plus a recorded working diff (`a46c5894…`), and to a successfully built, byte-identical host executable in v21; the 37 recorded source pins match the fixed fa3 source. The preload implementation itself was not changed by that prefill-only source diff. The controller recorded three `ZE_RESULT_ERROR_MODULE_BUILD_FAILURE` events before `GEN`, with Level Zero build logs reporting an unresolved device compiler symbol:

`__builtin_spriv_OpJointMatrixLoadINTEL_PackedA_RowMajor_SG16_16x16_i16_8_local_v8i8_pi32_i32`

The logs identify attempted `Kernel<2, bfloat16>`, `Kernel<2, half>`, and `PromptAttnMma<0,0>/<1,1>/<1,2>` specializations. This is evidence of synchronous executable-bundle module compilation/link failure during the background preload sweep, not a failed production kernel dispatch. The process reached `READY`, but no `GEN` was recorded; model output/correctness and whether any of those named templates are needed by a real prompt remain unresolved. The preload catches `std::exception` per ID and increments `skipped` while discarding the exception in the loop. A background compile failure therefore does not itself become a reported request error through the queue async handler.

After the controller detected startup errors, it sent `SIGTERM`. The child record ended with exit code `-11`; the retained stderr then emitted repeated `*** longjmp causes uninitialized stack frame ***: terminated` warnings. This is a separate post-controller-signal host process crash/teardown symptom. The chronology and signal record do not localize its crashing instruction or prove SIGTERM itself caused it. Neither event is evidence of a GPU system fault: the captured evidence has no failed model-kernel dispatch or `ZE_RESULT_ERROR_DEVICE_LOST` result, and related health checks report no new kernel-health fault. Avoid merging the provider's module-build error and later host SIGSEGV-like termination into one causal diagnosis.

The earlier diagnostic named the failure “compile/build failure” at the Level Zero module-build stage. It did not produce evidence that the model launched the affected kernels. Source reachability review says preloading all registered IDs can request kernels outside the selected request path; it cannot establish that every failing template is unused. Conversely, the module-build failures do not prove the GPU or all selected device code is unusable.

## Provenance comparison and its limits

Historical failed run environment points `PATH` and `LD_LIBRARY_PATH` to the private `intel-llvm-v711` install. The installed compiler receipt identifies Intel LLVM tag v7.1.1 / source commit `504366f4b82ff00bbac7b0c956635eed8bc599d8`, with version string DPC++ 7.1.0 prerelease based on clang 22.1.0. Captured mappings in the failed model include that tree's `libsycl.so.9.0.0-0` (SHA-256 `74243bafb2766fd1a038cf80fd62632b4aad9ecfdc0d3ce8711e4515a93d7008`), `libur_loader.so.0.12.0`, UR Level Zero adapter v2 `0.12.0`, `/usr/lib/.../libze_loader.so.1.32.0`, and Intel GPU driver `/usr/lib/.../libze_intel_gpu.so.1.17.39395`. These pin the high-level DPC++/SYCL/UR/Level Zero stack used by that process. The failed-run allowlisted maps did not include the dynamically loaded `libigc.so`/`libigdfcl.so`; its exact compiler-provider copy/hash in that process cannot be asserted from those receipts.

The later disabled-preload v6 64-token OFF/ON pair shares host executable SHA-256 `7c8a86f9…`, LLVM/SYCL source base fa3e20e, and the only tracked behavior change is the explicit preload-zero guard. It uses the same private LLVM 7.1.1-based toolchain and visible Level Zero loader/driver identities. Its expanded mapped-library receipt identifies `/usr/local/lib/libigc.so.2.41.5` and `libigdfcl.so.2.41.5` for the successful disabled run, but that does not retrospectively prove those were the provider mappings in the earlier failed process. Both preload-disabled n64 arms completed, generated 16 tokens, matched exact IDs/T/LP5, had no startup/pre-GEN errors, normal QUIT, process exit 0 and passing strict integer health. That qualifies only this 64-token selected path with the preload sweep skipped. It is not evidence that any of the previously failed registered specializations is fixed or that a 32K/64K request works with preload enabled.

The current `da3d426` worktree is source-only in this review. Its `src/core/device.cpp` hash is `2c089ad5e93432226ac3fffddf073c01238a11bff7e564401cf5422d84f74128`; W337's is `3e7523a2947af7c82d41fc9a7653f4f9aad0fa3cbb062999de19553659e0ec27`. The key source difference is that W337 retains the explicit `STRATA_PRELOAD_KERNELS=0` early return; Xe da3d does not. Both sources retain the same per-ID executable-bundle call and broad `std::exception` catch. The separate v7.1.1 source receipt identifies the compiler build and installed library bytes, not the compiler/provider libraries loaded by an unrun da3d binary.

## Latest startup flow and flags

Xe da3d `src/program/generate.cpp:2847-2850` calls `preload_kernels()` immediately after remote preflight and before normal model execution. For multi-GPU it repeats this per split device. Source policy then invokes `wait_preload()` around lines 1935/1948 before memory-rate / PCIe-split calibration so preload work does not perturb those measurements. This wait is not a bypass. It makes completion of the attempted all-ID pass explicit at those probe seams; the worker still catches failures as skips and emits only aggregate built/skipped counts when tracing is enabled.

`--serve`, speculative width, short-read prefix length, `STRATA_VERIFY_STEPPED`, and `STRATA_VERIFY_PIPE` affect later generation/verifier paths; there is no source conditional linking them to `preload_kernels()`. They cannot prevent startup from enumerating IDs. Setting `STRATA_PRELOAD_KERNELS=0` works in W337, and the committed historical source patch shows a minimal five-line early guard at `Runtime::preload_kernels()`; latest Xe da3d has no equivalent. Its omission is directly inspectable without execution.

## Decision and bounded evidence boundary

A source-only comparison establishes that the exact *class* of source operation that produced historical module-build errors remains in latest Xe da3d, under an unconditional startup invocation. This does not prove da3d itself fails under its exact build/provider stack, nor whether a filtered/selected path would dispatch any implicated template. The historical later `-11`/longjmp symptom is not evidence to attribute to the all-ID compile call. The toolchain receipt and mapped Level Zero files make an environment-matched recurrence test meaningful only under owner-controlled gating; they do not compel a test or authorize a GPU run in this scope.

For any later evaluation, the source-level first guard is the preload behavior, not the verifier/serve flags: either apply a reviewed explicit skip/control before the unconditional call, or instrument and qualify a selected-kernel preload manifest/error channel. Skipping the sweep leaves first-use JIT active and may move compilation failure into an actually selected operation; it is not a repair. If pristine enabled preload must be evaluated, preserve a closed source/binary/runtime/provider identity, separate compiler/module-build errors from launched-kernel faults and host teardown signals, and capture normal process shutdown. The current records justify neither a categorical “safe” verdict nor a claim that a system GPU fault is inevitable.
