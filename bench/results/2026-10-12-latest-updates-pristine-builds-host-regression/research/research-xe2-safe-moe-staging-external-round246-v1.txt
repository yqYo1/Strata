# Xe2 safe MoE staging and CPU/GPU split: external evidence screen (R246)

Date: 2026-10-12. Scope: external implementer/vendor evidence relevant to one Intel Arc B570 (Xe2, 10 GiB) plus Ryzen 5 5600X, mapped onto the integrated Strata Xe source at `sync-xe-v0143-nonfinite-20261012` (`@0691bcdf`). This is a read-only research report; no build, inference, GPU query, profile, runtime, source edit, or cleanup was performed. Main owns the serial B570 campaign; no run or setting was changed.

## Finding

No external implementation is presently a safe, directly adoptable MoE staging or CPU/GPU partition for Strata's active IQ3_S/GGUF path on this single B570. The public results use different weight formats, model/shape regimes, or hardware/software stacks. They can inform a bounded experiment, but cannot establish a speedup, safe copy-engine policy, or useful Ryzen share here.

The only source-local staging candidate worth preserving is the already-implemented optional threaded issuer for the `stream_all` batched-prefill route (`STRATA_PREFILL_ISSUER=0` forces inline; default is threaded). Its producer is bounded by ring slots and waits on the prior reader event before refilling; it copies in the same order and has stop/failure propagation and queue drains. The host issuer timing record explicitly says `performance_eligible=0`, `overhead_calibrated=0`; this is measurement scaffolding, not evidence of a win. More importantly, ordinary Xe `host_handoff_concurrent()` is false (`include/strata/core/gpu.hpp:48`), which disables concurrent host/GPU sharing and means `cpu_share_on()` cannot enable the proposed dual-compute split. `STRATA_PREFILL_ISSUER` only affects `stream_all`; it does not change the official read-window path. Therefore the issuer is eligible only for a matched, isolated A/B if a separately authorized campaign selects the batched stream-all route, with correctness and end-to-end prompt timing, and is not a candidate to toggle during the running Main campaign.

The existing compact-MoE scratch path (`STRATA_PREFILL_COMPACT_MOE_SCRATCH`) is similarly conditional: source restricts it to a pure FP16 fallback, no MMQ and no `DBG_NAN`, and requires the in-order queue. It compacts active groups before grouped F16 GEMM. The active IQ3_S/MMQ path does not meet that gate, so external grouped-GEMM results do not justify enabling or generalizing it. This is not a new candidate; it overlaps the already-screened Dm16/compact-fallback topic in R239/R301.

## External evidence and fit

- [vLLM XPU kernels release notes](https://github.com/vllm-project/vllm-xpu-kernels/releases) document Xe2 grouped GEMM enablement for MXFP8/block-FP8 in v0.1.13. That is a useful Xe2 implementation reference but not Strata's fused GGUF IQ3_S expert weights or current MMQ route. Treat as a porting/shape reference only, not a ready kernel substitution.
- [vLLM XPU kernels issue #509](https://github.com/vllm-project/vllm-xpu-kernels/issues/509) reports an Arc Pro B70 Xe2 experiment: scanning/compacting 256 expert groups to eight did not improve single-token decode end to end; reducing eight to two experts had a reported 1.37x prefill and 1.07x decode on a different Qwen3.6 setup. The author identifies graph-replay fixed cost. This is evidence against assuming expert compaction wins decode just because it reduces work; model, kernel, prompt, quantization, and card differ, so the ratios are not forecasts for Strata.
- Intel's [LLM Scaler repository](https://github.com/intel/llm-scaler) targets Arc B60/B70 and describes later vLLM/oneDNN integration and quantized Hugging Face-oriented paths. It establishes that the hardware family is actively targeted, but does not demonstrate the Strata GGUF IQ3_S storage path, the Ryzen 5600X host split, or a matched end-to-end result.
- Intel ARK's [XPU README](https://github.com/intel/auto-round/blob/main/auto_round_extension/ark/README.md) describes grouped MoE GEMM for Battlemage with FP16/BF16 activations and weights; low-bit GEMM is marked work in progress. It is not a directly usable IQ3_S kernel.
- [SGLang CPU backend roadmap issue #8281](https://github.com/sgl-project/sglang/issues/8281) discusses CPU prefill/thread blocking and Xeon AMX, including duplicated weight reads at large M. Hybrid CPU MoE offload/pipeline is roadmap discussion, not demonstrated Ryzen 5600X + B570 implementation or evidence that this single-GPU Strata path benefits.
- [SGLang expert-parallelism documentation](https://github.com/sgl-project/sglang/blob/main/docs/docs/advanced_features/expert_parallelism.mdx) describes grouped GEMM and batch-overlap schemes in a largely CUDA/NVIDIA context. It is not single-GPU Xe2 evidence. Expert parallelism is not equivalent to a safe CPU split on this backend.
- Intel's [SYCL environment variable reference](https://github.com/intel/llvm/blob/sycl/sycl/doc/EnvironmentVariables.md) documents the legacy `SYCL_PI_LEVEL_ZERO_USE_COPY_ENGINE` option. A global runtime copy-engine selection is not equivalent to a queue-local dependency/ownership proof and gives no performance or correctness guarantee for Strata's existing queue/event graph. Do not set it as an optimization based on the documentation alone.

## Decision and bounded next step

Do not adopt an external kernel, enable a copy-engine environment override, or infer a Ryzen share from these sources. Do not change the active Main campaign. If Main later chooses a separate batched `stream_all` experiment, the existing issuer toggle is the only source-grounded staging A/B in this screen: compare inline and threaded on the same prompt/weights/chunk, record correctness and end-to-end prefill wall time alongside the existing issuer timing fields, and keep the active official read-window result as its own baseline. Do not treat issuer host timings or transfer counts as PCIe bandwidth or exclusive CPU time. For current IQ3_S/MMQ and official read-window, no new safe external CPU/GPU split candidate is supported.
