Disposition

The proposed ordering is directionally sound: the new property receipt is required in `common.admit` before the qualified owner import and run-root creation; the property helper selects the unique SYCL Level Zero GPU at the fixed BDF, queries ZE properties from that same native handle, refuses the wrong vendor/root/device ID and nonzero relaxed-limit setting, and emits only after its queries succeed. The source contains no explicit context, queue, allocation, copy or kernel call. The explicit ban on reading the tainted inherited receipt is guarded in both `common.sha` and `common.load`, with an adversarial parser fixture. These checks keep the property-only path separate from model startup.

The packet is not ready for Main execution as written. The critical gap is that the controller validates fields asserted in a receipt but does not bind most fields to the property helper's actual output or to a build of the pinned helper source. The CPU fixtures mostly test dictionaries, not a real receipt-to-CAPS admission path. The source also has no matched 128-slot run, so it cannot support a causal 128-versus-512 performance comparison.

Required fixes before the property result can admit model startup

1. **Bind measurement fields to the actual helper output and binary build.** `common.validate_capacity` at lines 175–198 validates a JSON dictionary; `common.cache_capacity` at lines 201–215 checks that some closed command has the expected helper argv and environment. Neither parses/cross-checks that command's stdout against `proof` fields. It does not require the helper build command, exact compiler executable/hash/flags, or a build receipt connecting the pinned `health_caps.cpp` bytes to `property_binary`. A different binary or edited receipt could supply threshold-passing numbers while the successful command emitted different data. Require an anchored compile receipt with exact command/environment/compiler/provider and source/output pins, plus the property invocation's exact one-line `CAPS` stdout. Parse it strictly and derive every receipt field from that line; require no contradictory or unexpected output.

2. **Pin the property source in the qualified source closure.** `health_caps.cpp` is outside `policy.CODE` (seven Python files), as the source contract notes. `manifest.json` contains its SHA, but `common.admit` never checks that manifest. `common.cache_capacity` compares the receipt's `property_source` to the file's current hash, which proves consistency with that receipt, not the Main-reviewed source version. Add a separately reviewed, immutable `health_caps.cpp` SHA to qualification/controller review and require both the build receipt and property result to match it. Also bind the actual property binary's source/build receipt, not only its current file SHA and command path.

3. **Anchor the accepted native device ID independently.** `validate_capacity` at lines 186–191 accepts any integer `expected_native_device_id` in range so long as the helper-reported `native_device_id` equals it. `cache_capacity` then constructs the command-line expected ID from that same receipt field. There is no independent expected-ID field in qualification for the selected B570 identity. A self-consistent but wrong Intel root GPU at the BDF would pass this relation. Record Main's accepted native ID in a separate reviewed device/identity receipt or qualification field, and require both the command and observed ID to equal that pin. Do not infer or guess it.

4. **Validate all properties the helper emits and the basic total-memory bound.** `health_caps.cpp:63–85` emits `sycl_global_mem_size` and all six USM booleans. `validate_capacity` only type/range-checks the two max-allocation values and `usm_device_allocations`; it ignores global memory and the other USM values. Thus unresolved strings or contradictory values in those fields are not rejected. Require `sycl_global_mem_size` to be a measured unsigned integer and at least the requested single-block bytes (a necessary total-capacity check), and require each emitted USM property to be an actual bool. Keep the contract clear that this says nothing about current free memory, successful allocation, zero-touch, residency or model fit. Also note `sycl_properties_status=0` in the helper is a synthesized success marker: SYCL `get_info` returns values or throws; it does not return that integer status.

5. **Put a bounded owner around the property compile and run.** `cache-capacity-receipt.pending.json` has no budget fields, and `common.cache_capacity` does not check command `wall_seconds`/CPU limits. `Owner.closed` checks normal anchored completion but not requested CPU/wall caps. The property helper is not accompanied by a property-only launcher source, so the `MAIN_REVIEW_TODOS` promise to run it under the lock/current health/fault gates is still procedural, not enforced here. Main should use a finite short wall/CPU/RSS/output budget, record it in the actual receipt and require it at admission; retain sameboot, current health and fault checks before/after. Do not treat the enumerating property query as an allocation test.

6. **Bound receipt identity reads before hashing/parsing.** `common.identity` at lines 39–44 accepts any absolute regular-looking path and calls `sha` before `load` enforces B-directory containment and 16 MiB size (`load`, lines 30–35). `sha` at lines 16–20 has no size limit or descriptor identity/no-follow checks. A malformed Main path can therefore trigger an unbounded file read before the intended private bounded-receipt rejection, and `identity` followed by `load` has a path-swap window. Constrain receipt paths and sizes before hashing, and hash/read/parse one no-follow descriptor with stable fstat checks. Retain the explicit excluded-record guard before any open.

CPU fixture coverage and limits

There is no `controller_cpu.py` in this packet: the fixture file in the seven-file closure is `controller_cpu_fixtures.py` (SHA-256 `bff6265c259b514935766cb112fd2021d8ea31cdc3367b3421208a5fe29972b2`). Its `parser_cases` at lines 16–47 rejects missing/pending receipts and tests synthetic exact-threshold/undersize/root/ID/attempt/relaxed/device-USM values by calling `validate_capacity` directly. It does not exercise a valid `cache_capacity` file receipt, property command output, source/binary/boot/provider pins, or global-memory/other-USM cases. Add CPU-only cases for those binds, strict CAPS parsing and failure before owner import/root creation.

The fixture's return values at lines 134–135 deliberately leave `owned_mock_quit_passed` and `invalid_pending_process_passed` false; the pending-process function overwrites the admission result only when run with `--invalid-pending-output`, and the mock function only when given `--owned-mock-output` (lines 206–215). A parser-only invocation cannot be used as the complete CPU receipt. Main's CPU qualification checks all four flags (`common.admit`, lines 109–111), so execute and receipt-pin parser cases plus both bounded optional fixtures. The fixture child commands specify wall 20 s and CPU soft/hard 30/31 s via `Owner.run` (fixture lines 160–163 and 196–198); the parent fixture process itself has no source-level deadline/RLIMIT and needs an external bounded launcher.

For model runs, `run_root.py:117–123` passes `cpu=controller_wall * max(1, len(os.sched_getaffinity(0))) + 60`; `direct_owner.py:221–230` applies that as per-process `RLIMIT_CPU=(cpu,cpu+1)`. This is an affinity-scaled per-child limit, not a session-wide cumulative CPU cap. At a 3,600 s controller wall cap the soft CPU limit is `3,600 × affinity_count + 60` seconds for each child; descendants inherit individual process limits. The wall deadline and session RSS cap still bound the campaign, but the report must not call this an aggregate CPU budget. If Main needs an aggregate CPU hard limit, add session-level accounting or state explicitly that wall time is the governing limit. The capacity receipt's property-command budget must be separately bounded; the model-run CPU formula does not bound it.

Cache-setting comparison fairness

`policy.argv_for` at lines 78–89 requests `--expert-cache 512` with the fixed profile and `--expert-cache-per-layer`; the sequence at `policy.py:22` has only official startup then official model. Both use 512. The source contract says the candidate differs from the 128 base only in that switch, but this controller contains no 128 arm or pinned 128 result. It can produce one instrumented 512 run, not a paired capacity/performance effect. To compare settings, run a reviewed matched 128 control with the same executable/source/provider, input IDs, profile, cache/residency knobs, environment, health state and route validation; counterbalance or repeat process order and report startup/allocation and timed results separately. Otherwise label any outcome as a 512-setting sample without comparative speed or quality claims.

Further, `protocol.info` at lines 65–85 records a single aggregate `expert_slots` count (bounded by 48×512) and fixed settings; it does not prove how many distinct experts were populated or each layer's resident set. R224 already found that pristine official v0.1.43 accepts duplicate `(layer, expert)` profile pairs and can count repeated successful fills while reusing a slot. The packet itself correctly warns not to infer populated unique experts from slot count (`SOURCE_CONTRACT.txt:38–40`), but its structured protocol does not validate a profile fill/readback ledger. For any statement that 512 raised *effective* resident capacity, record distinct per-layer pairs, successful fill/readback and route reuse/miss evidence, or limit the claim to the requested/configured cap. R224: `research-current-integration-profile-fill-and-slot-identity-round224-v1.txt`, SHA-256 `aa84834d2e506460da13f9103e76d49c5d52a3a889a3a6806a9f55293585c99b`.
