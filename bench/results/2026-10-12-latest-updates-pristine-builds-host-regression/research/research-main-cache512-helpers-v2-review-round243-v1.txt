Disposition

The substantive v1 correctness gaps called out by R236 and v1 handoff are corrected in the v2 source: the negative pending child is required to remain a normally reaped exit-1, the parser enforces global memory as well as both max-allocation thresholds, and the resolver parses the exact retained CAPS stdout and links it to source, binary, compiler and invocation evidence. I found no parser acceptance path for foreign device identity, malformed numeric fields, unreported output, or a different compile source/output under the pinned manifest.

One material source-provenance race remains in the Main wrapper: it validates the helper manifest and source files once, then `runpy` executes each helper by pathname over multiple independently locked steps. Neither the per-step helper source pins nor the resolver bind those current helper bytes back to the wrapper's expected manifest. A helper file changed after the initial check but before a later step can therefore be executed and yield receipts that the resolver accepts under the original manifest reference. This is conditional on an intervening file change, not an observed change. The wrapper also does not apply a hard CPU/wall limit to its own Python controller; subprocesses are bounded, but in-process validation work is outside those child limits. Treat the latter as finite-ownership hardening, not a demonstrated false PASS.

Previously identified gaps that v2 fixes

- R236's CAPS/proof mismatch: `resolve_step.py:41-45` parses `capacity['caps_stdout']`, reads the separately pinned property stdout artifact and requires byte equality plus equivalent strict parsing. Lines 60-61 require the receipt's every parsed field to match.
- R236's missing compilation provenance: `resolve_step.py:46-56` closes the property build and original build receipts, equates source and binary pins across build/property receipts, pins the installed compiler, and requires the exact compile argv including the reviewed `health_caps.cpp` input and property binary output. Lines 57-59 also require exact property invocation argv and expected environment. Query mode (`property_step.py:111-116,128-140`) requires the pinned compile receipt/binary and validates the actual CAPS output before marking the capacity receipt complete.
- R236's missing independently reviewed device identity/global-memory checks: `caps()` (`cache_support.py:163-184`) requires exact keys, fixed BDF/backend/vendor/native ID/normal relaxed limits, canonical uint64 values and `sycl_global_mem_size >= 1,276,953,600`, in addition to both max-allocation limits. All USM output fields must be binary booleans; only root-device and device-USM capabilities are required true by design.
- v1 expected-negative-child status: `cpu_step.py:30-32` explicitly requires each inner invalid-pending command to be strongly closed with exit code 1. The outer fixture command remains successful only after it has asserted the negative child and mock receipts (`cpu_step.py:22-40`). This preserves the expected failure instead of turning it into a PASS exit status.

Findings

1. **P1, conditional correctness/provenance race: helper source files are checked only before the whole wrapper sequence, not before each execution.** Main checks the v2 manifest/source-pins and each helper file once at `latest-update-main-cache512-qualification-v1.py:26-31`. It then executes `H / name` through `runpy` at lines 42-48 for CPU, compile, query, and resolver. These are separate phases: each `CacheRun` releases `owned-v0141-measurement.lock` on finish (`cache_support.py:142-153`), so the lock does not span the sequence. Per-step `CacheRun` captures whatever helper `.py` hashes are present at that step start and checks for changes only against those captured values at finish (`cache_support.py:119-126,147-150`); it does not compare them to `manifest.json`. The resolver validates original cache-controller source pins, not the v2 helper source hashes (`resolve_step.py:34-40,69-80`). Its `controller_review` check compares `controller_source_pins` to the original seven-file packet pins and does not verify the review's `helper_manifest` against every v2 helper byte (`resolve_step.py:35-40`). Consequently, if (for example) `property_step.py` or `resolve_step.py` changes after wrapper startup but before its `runpy` invocation, the changed code can run, record its changed local helper pins, and still produce a resolver PASS while the wrapper/manifest records the original manifest hash. The source does not establish that mutation occurred; this is a reachable inter-stage mismatch under concurrent source modification. Fix by revalidating the exact helper file set and each manifest hash immediately before and after every `runpy` stage and requiring the review/step receipts to carry that exact manifest hash and expected per-file hashes. For stronger TOCTOU resistance, execute the reviewed immutable bytes from a protected snapshot rather than relying on check-then-open pathnames.

2. **P2, finite-ownership hardening: Main's controller process itself has no hard resource cap, and some admission work runs outside `CacheRun.Owner`.** `CacheRun.run` caps each owned child and bounds each helper's command wall (`cache_support.py:98-103,131-140`), but those limits do not cover Python work in the controller process. `CacheRun.whole_wall_seconds` is stored as metadata and checked only when starting a later child (`cache_support.py:118-123,131-135`); `finish()` has no elapsed-wall check or controller CPU cap (`142-153`). Main runs the helpers in-process with `runpy` and its `wall_seconds=1200` is informational; its only elapsed check is before a stage (`latest-update-main-cache512-qualification-v1.py:36-44`). The resolver also calls `common.admit(q, ...)` directly in that unowned controller process (`resolve_step.py:69-77`), in addition to running the admission in an owned child at lines 65-67, so source and binary identity hashing can consume controller CPU/wall without an Owner limit. This can delay or exceed the stated overall cap without producing a false PASS; every command that runs remains bounded, and the resolver repeats the Main admission in an owned child. To make the whole-step ownership claim literal, apply a parent CPU/wall limit to the wrapper or move unbounded validation work into an owned bounded child and enforce elapsed time in `finish()`.

3. **P2, descriptor-identity hardening (not a newly demonstrated correctness failure): receipt and file pins still use path-based hash/stat/read sequences.** `cache_support.sha` now caps individual regular-file reads at 512 MiB (`cache_support.py:32-37`) and `load` caps private JSON receipts at 16 MiB (`48-53`), fixing R236's unbounded-read concern. `exact` then hashes a pathname and separately stats it (`60-68`), while `load` checks a resolved pathname/size and separately opens it for `read_text`. A path replacement or symlink-target swap between those operations can make the verified bytes differ from the bytes parsed/used. The known excluded credential path is rejected before read. This requires concurrent filesystem mutation and is not evidence of a bad v2 receipt; it remains a trust-boundary hardening item from R236 rather than a reason to reject the static helper logic by itself. A single no-follow descriptor with stable pre/post `fstat`, bounded read, and hash-then-parse of that same byte buffer would close the race.

Review checklist by requested area

- CPU negative-child handling: source checks exactly exit-1 with anchored normal closure; not promoted to an outer success without checking the inner command. Correct statically.
- Pure CAPS parser: exact single newline/line and exact key set; duplicate/unknown/missing keys fail; canonical unsigned integers are range-checked; booleans accept only `0`/`1`; fixed native identity and global/max allocation thresholds are enforced. Fixture cases cover representative malformed and threshold values. No reachable permissive parse found.
- Compile-to-property binding: source and binary pins are equated; build command exact; compiler identity linked to original installed compiler pins; property invocation exact; output file hash and parsed receipt output agree. Correct under the pinned-receipt/no-concurrent-mutation trust assumption.
- Resolver derivation: capacity proof is derived from actual stdout and checked again by original `common.admit`; the new qualification is written only after those checks. No trust on a free-standing capacity dictionary found.
- Ownership: child processes have finite wall/CPU/RSS/output caps, and child CPU limits are clamped below the parent's hard limit (`cache_support.py:98-102,131-140`). The main controller and direct admission pass remain outside those child caps as described in finding 2. The exclusive lock is held per helper stage, not across the complete wrapper sequence (`cache_support.py:108-116,142-153`).
