## Decision

For a bounded first B570 run with experts served by the host, use the source-supported serial stepped verifier route: `STRATA_VERIFY_STEPPED=1`, `STRATA_VERIFY_PIPE=0`, and `STRATA_VERIFY_NO_HOST=0`; keep the wrapper's `STRATA_VERIFY_DEVICE_PLAN=1`. Do not infer that the wrapper's normal `NO_HOST=1` default can safely handle cache misses. This route deliberately serializes each segment, device queue completion, CPU-pool service, copies, and flags. It trades throughput for an explicit completion boundary and avoids the ordinary concurrently-polled host/device doorbell sequence. It is a source-based candidate, not a runtime safety certificate or the recommended performance path for Xe.

## Selector and adapter setup

- Use the Level Zero backend and pin the intended GPU with `ONEAPI_DEVICE_SELECTOR=level_zero:<index>`. The oneAPI runtime selector controls backend/device selection; setup writes a selector only for multiple Intel GPUs and preserves a user's explicit selector (`sycl/setup_intel.py:280-294`). Level Zero ordinal order was observed to match sysfs on tested machines, but the docs explicitly say another machine may differ. Therefore do not assume index 0 names the B570 without a previously captured device inventory. The existing build itself cannot establish which device the runtime will choose.
- Keep ordinary Unified Runtime adapter discovery. Do not set `UR_ADAPTERS_FORCE_LOAD`: UR documents that it disables other adapter discovery and is for development/debugging. The Linux preload filter uses `ONEAPI_DEVICE_SELECTOR` to avoid loading irrelevant adapters by default. No source evidence requires forcing an adapter when the Level Zero selector is set.
- Run in the configured Intel oneAPI environment (or the existing `strata-sycl.sh` development image). The wrapper removes a prior named container, passes `STRATA_`, `ONEAPI_`, `UR_`, `IGC_`, `SYCL_`, and `ZES_` variables, and defaults to `DEVICE_PLAN=1`, `NO_HOST=1`, `STAGER_THREADS=12` (`sycl/serve/strata-sycl.sh:10-42`). A value of 0 suppresses the corresponding wrapper setting; it is not passed to the engine. Thus explicitly set `STRATA_VERIFY_NO_HOST=0` to enable host misses and leave `STRATA_VERIFY_DEVICE_PLAN=1` active. For Xe2, set `SYCL_CACHE_PERSISTENT=0`; the official Intel docs record a persistent-cache crash during the first JIT compilation (`docs/INTEL_ARC.md:135-141`, Docker default `sycl/tools/Dockerfile:8`).
- Do not carry over the A-series debug workaround keys `IGC_EnableDPEmulation=1`, `OverrideDefaultFP64Settings=1`, `NEOReadDebugKeys=1` to this icpx B570 run. The setup code emits them for Alchemist/i915, whose docs describe a hardware FP64 limitation; docs report native FP64 on the B70, and distinguish B-series from A-series. These keys are not a substitute for the correct runtime/driver and were not justified for B570 by this source audit (`sycl/setup_intel.py:194-202`, `docs/INTEL.md:684-707`). Do not add undocumented IGC/NEO overrides.

## Why the stepped route is the right bounded candidate

The wrapper default `STRATA_VERIFY_DEVICE_PLAN=1` does not itself mean the verifier is all-resident. `ar_on()` is exactly `all_resident_ && !ar_off_` (`sycl/include/strata/core/verify.hpp:339`); `device_plan_` is separately enabled for non-all-resident layers when `DEVICE_PLAN` is present (`sycl/src/core/verify.cpp:701-729`). On a window with misses, `g_stepped && !ar_on()` selects the segmented doorbell capture (`verify.cpp:1734-1738`) and `stepped_run` at execution (`verify.cpp:2041-2045`). Device-plan can cover resident hits while the pool serves actual misses (`verify.cpp:1453-1459`); it does not turn a missing expert into a resident one.

With `PIPE=0`, the helper-thread branch is disabled (`verify.cpp:2090-2119`). At each serve the main thread waits for `cs_` to drain, checks the sequence/payload, runs the CPU pool, waits for the copy queue and its host function, then raises flags before subsequent graph work (`verify.cpp:2066-2137`). The payload is explicitly read only after segment drain (`verify.cpp:1687-1718`). This serial ordering is the meaningful distinction from ordinary polling, where host reads/pool service can overlap a running graph (`verify.cpp:2180-2205`). The code itself documents the stepped mode as an Arc A-series mechanism; applying its ordering as a conservative B570 fallback is an inference from the generic SYCL route, not a claim it has been validated on B570.

Two details matter:
1. `NO_HOST=0` is essential if there are cache misses. Before generation, source counts unmirrored misses and refuses them when `NO_HOST` is enabled (`generate.cpp:4836-4843`). The ordinary B70 `NO_HOST=1` configuration is documented for a full VRAM cache or misses covered by the host mirror; it does not provide CPU fallback for experts in neither location (`docs/INTEL.md:242-249`).
2. `SPEC=4` does not require loading an MTP drafter. `use_mtp` is `!o.mtp.empty()`; with no `--mtp` the MTP load path is skipped (`generate.cpp:3968-3985, 6454`). The suffix/prompt lookup drafter is separately enabled by default for eligible `spec>=2` requests (`generate.cpp:2268-2280, 12289-12300`); if the intent is “no drafts at all,” add `--suffix-draft 0`. For the requested “MTP disabled” contract, `--spec 4` with no `--mtp` satisfies it. In serve mode `--short-read 65536` sets the maximum fresh prompt tokens passed through decode windows instead of batched prompt path; parser default is 64 (`generate.cpp:810-811, 1853`). It is a route switch, not a promise that an input of 65,536 tokens exists.

## Bounded first-launch / 32K evaluation contract

1. Preserve exact model/checkpoint, native pack, expert profile/cache, PLE input, data paths, and all existing correctness settings from the intended config. Use the real oneAPI runtime environment and pin the verified B570 Level Zero selector; no A-series FP64 overrides. Use a workload that intentionally has both resident hits and cache misses, with sufficient RAM/mirror/pool configuration. If there are no misses, the CPU-pool path has not been exercised.
2. First admit one single-request greedy generation with a short prompt and small output cap (e.g. 8 generated tokens), `--spec 4`, no `--mtp`, `--short-read 65536`, and the stepped/serial environment above. Require clean model load, graph capture/warm path, a completed verifier window, no pool refusal or runtime exception, and correct token/logit behavior against the established same-model reference. Do not interpret graph capture as a device kernel launch: the SYCL port captures verifier graphs at startup by default (`generate.cpp:12260-12272`), while a JIT build compiles device code on first actual use. The docs estimate about 47 seconds of first-run JIT compilation in their documented build context (`docs/INTEL.md:229-230`); allow for that separately from generation timing.
3. Only after step 2 passes, run the same single-request greedy check at a 32,768-token context using the established prefill settings, keeping max new tokens small. Record exact prompt-token count, cache residency/miss counts, selector, model/pack hashes and runtime/compiler versions, output IDs or correctness digest, error status, and elapsed phases in the retained run report. Preserve failure diagnostics according to `docs/ARTIFACT_RETENTION.md`. This contract calls for a bounded correctness/capability evaluation; it makes no performance claim and does not call the segmented path optimal.
4. If the selected adapter/device, compiler/runtime tuple, or actual run configuration differs from the existing receipt, refresh that capability receipt before interpreting results. In particular, a previous v0.1.42 B570 receipt reported `HOST_USM=1`, `ATOMIC_HOST_USM=0`; it does not certify this v0.1.43 executable or its selected Level Zero allocation route. A pass under this route would be evidence for this exact serialized workload only.

## What source cannot certify

No source read proves that the current host's Level Zero adapter selects the intended B570; that the driver/runtime loads cleanly; actual USM allocation attributes/coherence at queue completion; graph capture/submit/execute support; kernel JIT and device image compatibility; XMX/native kernel functionality; available VRAM, pinned memory, RAM, file/model correctness, numerical parity, timeout sufficiency, or the resulting 32K correctness/performance. Those require the explicitly staged runtime evaluation and its recorded artifacts. A runtime capability bit such as atomic host USM is not required to claim the source ordering is serialized, and the source ordering alone does not certify actual host/device memory behavior.
