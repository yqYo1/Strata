# R189 — Full-context INT8 KV: host backing, VRAM residency, and chunk admission

Date: 2026-10-12. Read-only source and retained-report reconciliation. No runtime/device query, model run, build, test, Git operation, or cleanup.

## Finding

In the supplied immutable source W, `--kv-resident 32768` with 262144-cell context selects main QSA streaming (`kv_mode=1`) when the main-off override is absent. The full-context INT8 K/V copy is allocated as pinned host memory and device-mapped; only the configured resident pages' INT8 arrays occupy ordinary device VRAM. The phrase “262144-cell KV = 6.64 GB” cannot be used as a VRAM allocation. There is also a source arithmetic conflict: the current W architecture is 48 layers with QSA every fourth layer (12 QSA layers), and its exact INT8 format computes 3.09375 GiB of full main host KV, not 6.1875 GiB. The latter value appears in retained R147/R179 summaries, but R179 explicitly calls it an earlier receipt, not remeasured; I cannot reconcile it to current source geometry and row formula. Preserve it as an unresolved historical figure, not as current W's VRAM or pinned-host allocation count.

For current W's stated geometry (QSA heads=2, head dim=256, page size=4; 48 layers, 12 QSA), one INT8 KV cell is 1,056 B per QSA layer: 1,024 code bytes for K+V plus 32 bytes of FP16 scales. With main `kv_resident=32768`, its device KV pools are 396 MiB across 12 layers. The full logical host backing is 3,321,888,768 B (3.09375 GiB) plus small per-layer allocation padding. The pool is not 6.64 GB on the GPU.

The MTP draft has a separate host mirror and a short device ring when host pinning succeeds. A requested 32768-cell attention window gives an 8192-page-slot baseline at four cells/page, but `MtpDrafter::init` actually sizes its ring as `window + 4*max_t + 64` cells and rounds up to pages. Its device KV is therefore about 33 MiB for 32768 slots, slightly larger with write-ahead cells; its host mirror still covers all 262144 logical cells (about 264 MiB). If draft host pinning fails, the source discards the ring attempt and allocates a fully resident 262144-cell draft KV pool instead. The available sanitized record summary does not report whether that fallback happened, so actual draft VRAM ownership remains unconfirmed.

`kv_plan` in `src/core/layer.cpp` has `pages=ceil(max_cells/page_size)`. For main QSA, `kv_resident=32768` is raised only to the 20480-cell minimum, rounded to page slots; with `page_size=4` this is 8192 slots. If fewer than the 65536 context pages, the mode is 1. `qsa_state_bytes` and `qsa_state_init` allocate K/V arrays for `p.slots`, but allocate the `page_table` and residency map for the full logical pages. For mode 1, `qsa_state_init` makes one `gpu::alloc_host(bytes)` allocation per QSA layer, obtains a device pointer to that pinned memory, and carves full-capacity host K/V arrays from it. Its size is `pages * kv_block_bytes + 4*256`. For INT8, one page is `4 cells * 1,056 B = 4,224 B`; 65,536 pages yield 276,824,064 B per layer plus 1,024 B padding. Twelve layers yield 3,321,888,768 B plus 12,288 B padding (3.093761 GiB). That is pinned host backing, device-addressable for kernels, not an additional normal VRAM copy of every cell.

The mode-1 K/V arrays themselves allocate `p.slots * page_size * n_head_kv * head_dim` codes for each of K and V, plus one 16-bit scale per 64 values for each head/plane. At 8,192 slots, this is `32768*1056 = 34,603,008 B` per QSA layer and `415,236,096 B = 396 MiB` for 12 layers, before small alignment/arena overhead. The full-context page table costs 256 KiB per layer (3 MiB total); map metadata is bounded by 8,192 slots. `kv_stream.hpp` says append always writes the logical-position host row and writes a VRAM slot only if the page table maps that page. On selection, `kv_stream_resolve` may change page-to-slot mappings and copy selected pages from host into the resident pool. Thus the host mirror remains full-context even if any given cell is absent from VRAM at a later point.

For the draft, `MtpDrafter::init` computes `ring = window + 4*max_t + 64` for a shorter-than-context window, forces the draft format to ordinary INT8 even under K8V4, and calls `qsa_state_init` for one separate state. Mode 2 maps page `b` to `b % n_slots`; `n_slots=ceil(ring/page_size)`. The draft also allocates a full-context pinned host mirror when it can pin it, despite its small device ring. If `qsa_state_init` fails in mode 2 because the host mirror cannot be pinned, the caller frees the failed ring state and retries in mode 0, which puts the entire context's draft INT8 KV pool in device memory. The emitted “no pinned RAM left ... keeping it in VRAM” message is the source-described fallback; it is not present in the sanitized R179 setting summary.

## What the retained measurements do and do not show

R179's read-only ledger cites a 32K, T8192 passing record with effective context 262144, main `kv=int8`, `kv_resident=32768`, 144-slot/281 MiB cache, no Prefill borrowing, and 714 MiB reported free. Its raw model record is not re-opened for this round. The sanitized summary does not include main `kv_mode/n_slots`, draft `kv_mode/n_slots`, host-pin success, or a per-owner VRAM delta. It therefore does not prove main streamed mode was effective or that the draft avoided the mode-0 fallback, although the current W settings predict mode 1 and mode 2 respectively when their guards and allocations succeed.

R353 provides a separate source-level ownership audit: with page size four it derives 65,536 logical pages and 8,192 main resident slots at 32768 cells; it confirms full logical host backing and distinguishes MTP's ring/host mirror. It did not run the supplied current W or measure its allocator. R147/R149 record full-context host KV arithmetic of 6.1875 GiB, and R179 repeats that historical number while explicitly saying it was not remeasured. Current W's model geometry and Q8 `bytes_per_cell` imply half that main host payload for 12 QSA layers. The gap is likely an older geometry/count or a doubled K/V accounting in the historical estimate, but I cannot establish which from the retained sanitized sources. Do not substitute either historical host estimate for actual current-process pinned bytes.

The retained 714 MiB READY/free figure is an aggregate at a named workload/startup point in the model summary, not an owner-by-owner VRAM receipt. It can support only the R181 arithmetic screen. R181's source-derived T8192-to-T10240 incremental Prefill request, including `tok_dev`, is 613,785,600 B (585.35 MiB), leaving nominally about 128.6 MiB against 714 MiB if the point and owners match. T10240 has a largest individual Prefill GDN region of about 1,475,872,768 B. These values show why admission is tight, but do not prove it will allocate: `Prefill::bytes_needed` aggregate accounting, a largest individual take, later owners, fragmentation, runtime pages and device per-allocation maximum are different constraints. The 144-slot cache is live and cannot be assumed reclaimed with `--no-prefill-borrow`.

Existing heavy device owners include the main 396 MiB streamed KV pool (source-derived), context-sized QSA indexer pooled rows, the one shared full-length RoPE table, the separately sized Prefill workspace, the cache, and MTP weights/arena/draft state. For current W, the main QSA pooled indexer is `(262144/4+2)*128*4` bytes per QSA layer, about 384 MiB over 12 layers; it is device session state and varies with `max_context`. The shared RoPE tables are 64 MiB at 262144 cells. MTP's weights/arena and the 281 MiB cache remain live during the prefill admission point; R179 has no exact current-process byte breakdown for all those owners. Do not attribute all pressure to KV or assume freeing the 6.64GB historical number from VRAM.

## Would a 64K max_context benchmark reduce GPU KV?

A 64K prompt run while preserving `max_context=262144` changes no full-context KV allocation. That is the appropriate same-capacity benchmark if full-context/output admission is part of the question.

If `max_context` itself is lowered to 65,536 while keeping main resident policy at 32768 and draft window at 32768, main QSA remains mode 1 because the 64K context still exceeds the resident limit. The main 8,192-page-slot device KV pool therefore stays 396 MiB. Its pinned host mirror shrinks from 3.09375 GiB to 0.7734375 GiB, a source-derived reduction of 2.3203125 GiB. The separate one-layer draft host mirror shrinks by about 198 MiB (from about 264 MiB to about 66 MiB), while its ring pool remains determined by window plus write-ahead cells and does not become a smaller context-sized allocation. A change in available host pinning could alter whether the draft falls back to full device residency; current mode logs are required to exclude that path.

Lowering max context also shrinks context-shaped GPU metadata/workspaces, so the answer is not “only host RAM.” Under current source dimensions it reduces the 12 main QSA `idx_pooled` arrays by 288 MiB, their page tables by 2.25 MiB, the single shared RoPE pair by 48 MiB, the Prefill QSA block-score array by 48 MiB, and the standalone QSA `cell_scores` array by 0.75 MiB: about 387 MiB source-derived device reduction, excluding small fixed structures/runtime allocator effects and the MTP page-table delta. It does not reduce the 396 MiB main resident KV pool or fixed 32768-cell draft ring. A reduced-context run therefore has materially different GPU admission and cannot be reported as the same 262144-capacity benchmark.

## Remaining ownership gap

Before any claim about actual WVRAM ownership, the same qualified READY/startup receipt needs to record, per main QSA layer and draft state: `kv_mode`, `max_cells`, `n_pages`, `n_slots`, format, host pointer present/bytes, and actual host-pin success/fallback. Record free VRAM at the same stages as R179 (before/after session, MTP, cache and Prefill init) plus largest individual allocation. The source-derived figures above predict the split; only those owner-bound records can close actual allocation residency. The raw `B/prefill-gemm-only-contract-root-v1/record.json` was not read.
