# Pristine controller v2 post-READY diagnostic gates (R218)

Date: 2026-10-12. Read-only review of `protocol.py`, `run_root.py`, and `common.py` in `/home/yayoi/.local/state/strata-sycl/post-reboot-tuning-20261007/latest-update-pristine-model-controller-source-v2`, with narrow reads of the pinned pristine official v0.1.43 source and the qualified direct-owner implementation where control flow required it. No import/AST, project execution, tests, build, lint, GPU/model/process run, Git operation, cleanup, or implementation edit.

## Result

I found no reachable false PASS in the requested cases of mixed compile/runtime UR or ZE diagnostic lines, a partial stderr line crossing READY, or an unsuccessful QUIT/owner close. I found a reachable **delayed diagnostic detection** during model GEN: the replacement `io.poll()` enforces deadlines, byte/RSS/artifact limits, progress sampling, and devcoredump absence, but does not run the post-READY stderr scanner. The scanner runs after READY/source guards, after DONE, again after the owned engine command has exited, and before final PASS. Therefore a post-READY stderr runtime error during a long GEN remains undetected until DONE or another termination condition; the controller may keep the request running until its 1,800-second whole-run limit. It will not yield PASS if the error text is present by final scan, but it does not stop promptly at the error.

## Checks that close the requested false-PASS paths

`protocol.diagnostics()` first gathers lines matching fault, fatal, compile, or error patterns, then extracts every UR/ZE error enum from each relevant line. Startup exemptions require the line to contain one or more enums and **all** enums to belong to `BUILD_ENUMS`; a build enum beside any unrelated UR/ZE enum is severe. A plain `[ERROR]` beside only recognized startup build enums is reviewable at startup, but any such line after READY is severe. `CL_BUILD_PROGRAM_FAILURE` is likewise allowed only at startup review; post-READY it is severe. Thus compile words do not mask another enum on the same line, nor do startup build exemptions carry across the READY boundary. This matches the code comment and stated contract.

READY handling reads the current stderr file and records the start of the final partial line (`rfind(b'\\n') + 1`) as `ready_stderr_offset`. The pre-READY snapshot ends before that fragment; the strict post-READY scanner starts at that offset, so a diagnostic whose prefix was written before READY and whose enum suffix arrives after READY is reconstructed from the saved fragment plus later bytes. `post_ready_diagnostics()` reads through EOF on each call, including an unterminated final line (`splitlines()` retains it). The owner bounds stderr/log growth, and reads are additionally capped at 64 MiB. No line-straddling false negative was found in this design.

The final result is gated beyond diagnostic parsing. A protocol `ERR` raises immediately; after DONE, the request and final diagnostic checks run; then `normal_quit()` sends QUIT and waits for child exit/drained stdout. The direct owner requires exit observation, an empty anchored session, and successful child reap. Only after `run('engine', ...)` returns does `model_normal_close` become true, and `passed` additionally requires complete/inactive state, no errors or primary failure, all strong commands with exit code 0, final kernel gate and unchanged boot. A QUIT send that fails, an exit deadline, trailing protocol, surviving session process, or forced cleanup prevents PASS. The receipt's `quit_send_outcome='sent'` means the nonblocking pipe writer loop completed the entire command; `quit_exit_outcome='exit observed'` is assigned only after the owner observes exit. Those two fields are then corroborated by the owner closure evidence.

## Reachable detection delay during GEN

Inside `run_root.py`, the GEN protocol loop calls `io.line(remaining)`. The owner `Interactive.line()` invokes the installed poll callback while waiting for protocol stdout. That callback does not inspect the current stderr contents; it only samples progress every 30 seconds and stops on a devcoredump. The stderr scanner is called only after the request loop reaches DONE (or the request fails), and then after the child exits. If a runtime error is printed to stderr while the engine continues emitting valid-looking progress/output, there can be a potentially long gap before the gate rejects it. This is a delay, not a persistent PASS path, assuming the diagnostic text remains in the retained stderr log. A useful fail-fast hardening is to check `post_ready_diagnostics()` from the installed poll callback, with a bounded scan strategy; retain the after-DONE and post-exit scans to cover races around shutdown.

The official source provides a corroborating control-flow distinction: `generate.cpp` prints selected-request failures as `ERR ...` on stdout (e.g. around 8854, 8868, 9039, 9082), and verifier failures return false through that path. The controller catches those protocol lines immediately. Runtime/driver diagnostics may instead be stderr-only, so they depend on the delayed stderr scan. This audit does not claim every runtime error emits an enum, `[ERROR]`, or `ERR`.

## Unavoidable source-level observability boundary

The controller explicitly requires Main review of Xe's ignored intermediate event-return limitation (`common.admit()` checks `ignored_intermediate_event_errors_reviewed`). That review gate does not make ignored failures observable. A source call whose return status is discarded can fail without producing a recognized stderr message, stdout `ERR`, device fault, or malformed/nonfinite output. In that case the controller's finite output/LP5 structural checks may still accept the result. This is not a newly discovered defect in the three controller files; it is the already disclosed pristine-source limitation. Consequently a controller `passed` record means the enumerated diagnostic, protocol, identity, and closure gates passed, not proof that no unreported async/event failure occurred or that outputs match an independent full-logit reference.

## Scope of evidence

This review inspected source text only. It did not synthesize fake logs, execute Python, validate a runtime, or prove every vendor runtime's stderr spelling. It found no new mixed-enum, partial-line, or QUIT closure false-PASS example. The one actionable delta is periodic post-READY stderr scanning during the active GEN wait; currently rejection is eventual at DONE/closure rather than promptly at the error.
