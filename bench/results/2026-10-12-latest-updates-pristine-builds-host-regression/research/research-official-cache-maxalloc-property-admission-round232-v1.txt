Main's official FULL32K remains active; no GPU/runtime/device/process query, build, test, import/AST, Git, cleanup, or source edit was made. This report proposes the smallest additional B570 observation for deciding whether a larger official expert-cache allocation deserves a startup trial. It supplies no live hardware values and no fit/performance result.

## Decision

Preserve the existing bounded `health.cpp` six-record protocol unchanged. Add a distinct, one-shot source/binary such as `health_caps.cpp` that only selects the required BDF and reads device properties; it creates no SYCL context/queue, allocates no USM, submits no copy/kernel, and prints one bounded `CAPS` receipt line. Do not append property fields to the integer-health stdout: its owner currently checks the exact six non-`LIBRARY` records (`STATUS`, `QUEUE`, `H2D`, `KERNEL`, `D2H`, `PASS`). The retained `xe-source-llvm-small-health-v3/health.cpp` is SHA `399487d9d62837c75d52ffe3c9c39b1d3eba69853ec5d06e5a20907a31c06ec2`; its successful v3 root record is closed/passed, but it validates only one 64 KiB device allocation and 16,384 integer words under that record's pinned source-built runtime. It says nothing about a 1.2 GiB cache allocation or the current official executable/runtime.

The new receipt should report the requested BDF, Level Zero backend, ZE vendor/device/root identity, `ze_device_properties_t.maxMemAllocSize` in bytes, SYCL `info::device::max_mem_alloc_size` for the same selected `sycl::device`, SYCL `global_mem_size`, and `device.has(...)` for `usm_device_allocations`, `usm_host_allocations`, `usm_atomic_host_allocations`, `usm_shared_allocations`, `usm_atomic_shared_allocations`, and `usm_system_allocations`. Include a field for each checked result/error; reject duplicate/missing/mismatched target identity or any failed query. Explicitly record that allocation/kernel attempts were zero. Use a fixed-size one-line key/value receipt with no library dump or per-device enumeration.

Selection must copy the known working health helper's fixed `0000:05:00.0` input and unique SYCL PCI-address match. Only after one unique Level Zero `sycl::device` object is selected, obtain its native handle with `sycl::get_native<sycl::backend::ext_oneapi_level_zero>(selected)` and call `zeDeviceGetProperties` on that same handle. Do not enumerate independent ZE handles and match an ordinal, do not use a tile/subdevice as a substitute, and fail closed unless ZE properties also identify Intel vendor `0x8086`, the expected B570 device ID from the accepted identity receipt, and a root (non-subdevice) device. Query SYCL max-allocation and USM aspects on the same `selected` object. This paired observation answers two different questions: the SYCL layer's advertised limit and the underlying L0 device handle's reported limit. Keep both, even if equal; do not substitute one silently for the other.

## Cache threshold this observation resolves

R228 pinned official v0.1.43 at revision `7695859aa13afb248bdb4d36f9b2e95707db079d`, found that native `--expert-cache N --expert-cache-per-layer` builds one contiguous sized block, and found no source query of B570's maximum single-allocation limit. Under its pinned metadata and full requested quota:

| Arm | Effective slots | One contiguous cache block requested |
|---|---:|---:|
| Existing N=128 baseline | 144 | 294,681,600 B (281.03 MiB) |
| First candidate N=512 | 624 | 1,276,953,600 B (1,217.80 MiB) |
| Deferred N=1024 challenger | 1,296 | 2,652,134,400 B (2,529.27 MiB) |

The immediate new discriminator is whether both advertised max-allocation values are at least the exact one-block request for N=512 (1,276,953,600 B). If either is lower, do not attempt the manual full-quota 512 arm; keep the baseline and return to source/allocator semantics before considering another arm. If both exceed it, this passes only a necessary property gate: the current free-room cap, allocator/driver state, other startup allocations, graph/workspace room and cache zero-touch still decide whether startup succeeds. It is not proof of capacity. Do not use the N=1024 comparison as the first allocation trial. Auto/per-layer remains data-dependent; its actual selected contiguous byte count must also be compared against both recorded max-allocation values before claiming the candidate was within the reported cap.

The source cache and model figures must come from the same pinned layout/routing receipt as the eventual startup arm. The earlier READY free estimate in R228 (4,177 MiB) is historical campaign input, not a current free-memory receipt. It cannot be combined with today's property query to claim space.

## Values that must stay distinct

- **Maximum single allocation:** `maxMemAllocSize` is a device-property limit for an individual allocation. For this cache, compare it to the one contiguous cache `malloc_device` request, not to the largest individual expert blob and not to a sum across separate per-layer allocations (the official implementation uses one block).
- **Total/global physical capacity:** ZE `zeDeviceGetMemoryProperties` reports properties for each physical local-memory type. SYCL `global_mem_size` is a device-wide capacity property. Neither is a current free-space number.
- **Current usable/free:** L0's optional `ze_device_usablemem_size_ext_properties_t.currUsableMemSize` is described as transient available usable memory, includes client-allocatable plus L0 internal allocation room, and explicitly cannot guarantee future allocation success. Avoid adding this optional extension to the minimum sidecar; preserve the main program's actual `free_at_sizing`/free-room and post-allocation reserve receipts. If collected in a later optional diagnostic, label it `usable_now` and never call it guaranteed free. The runtime's `UR_L0_USE_RELAXED_ALLOCATION_LIMITS` can also change allocator behavior, so capture its explicit value/environment; do not infer the normal limit from a run with it enabled.
- **Requested/allocated:** report the exact cache byte request from startup and whether `malloc_device`/zero-touch succeeded. An allocation success is evidence the actual attempt worked in that state; the property query alone is not. A requested size or virtual allocation is not the same as committed physical residency.
- **Resident experts:** record populated, unique `(layer, expert)` entries or slots from the cache fill/residency receipt. This is software cache content and does not mean all VRAM is free, nor does `--expert-cache 512` denote 512 physical slots in the per-layer formula. At N=512 the source full-quota arithmetic yields 13 per layer, 624 total. Do not label allocated block bytes as resident expert bytes unless the fill receipt establishes those contents.

Optional `currUsableMemSize` is a worthwhile secondary value only if its extension struct is supported by the actual installed Level Zero headers/driver and the root owner wants a contemporaneous device-wide free-ish view. It is not needed to answer the narrow `maxMemAllocSize` question, and not worth making the minimal query depend on optional extension availability.

## USM interpretation and relaxed-limit exclusions

The cache's USM requirement is `sycl::aspect::usm_device_allocations`; its absence rejects a device-USM cache route. The health microprobe's successful 64 KiB `malloc_device` is an empirical check of a tiny allocation on its own runtime, not a replacement for the aspect bit or an upper-size qualification. Host and shared USM aspects are useful contextual receipt fields, but are not prerequisites for the cache's `malloc_device`. `usm_atomic_host_allocations` is a separate concurrency capability: its value cannot be inferred from `usm_host_allocations`, from success of the device-USM cache, or from the small copy/kernel PASS. An absent host-atomic aspect does not reject this device cache allocation, and a present bit does not by itself qualify every host-USM marker algorithm or arbitrary pointer's concurrent atomic behavior.

Do not set `UR_L0_USE_RELAXED_ALLOCATION_LIMITS=1`, attach a relaxed-allocation `pNext` descriptor, or treat a relaxed-limit run as evidence that a normal allocation fits the reported property. The current Unified Runtime Level Zero adapter reference documents the environment variable, with default 0. L0's older experimental `ZE_RELAXED_ALLOCATION_LIMITS_EXP_FLAG_MAX_SIZE` is deprecated and says allocations may exceed `maxMemAllocSize`; the current extension has replaced it. Changing this knob masks exactly the normal max-allocation gate R232 is intended to measure. Do not confuse this with allocation cache-bias flags or command-list relaxed ordering; those are unrelated.

## Concrete bounded measurement guard for Main

1. Wait for the currently owned official FULL32K process to close normally. Do not run a second diagnostic against the B570 while that run is active. First preserve/close its result and verify no owned GPU process or outstanding device work remains under the existing owner/lock protocol.
2. Only after that closure, use the existing exclusive measurement lock and the sameboot/current-health and device fault pre/post checks already required by Main. Pin the new source and binary hashes, the exact compiler/runtime/adapter/driver and explicit environment. In particular preserve the fixed Level Zero BDF selector and record `UR_L0_USE_RELAXED_ALLOCATION_LIMITS=0` or unset as the actual inherited state; no relaxed limit, profiler, logging/selector change, extra queue or GPU workload.
3. Compile/run a separate property-only helper under the existing health owner's fixed command wall/RSS/CPU/process bounds. Its sole GPU-adjacent operations are selected-device enumeration and bounded property queries; no queue, context, memory allocation, free-memory trial, transfer or kernel. One attempt only, no retry/reset/rebind/recovery. Require exactly one well-formed bounded CAPS record, stable boot/device/source/runtime identity, successful query statuses, and no new fault/dump events in the owned kernel interval. Stop and preserve evidence on any timeout, query failure, exception, identity mismatch or new fault.
4. The next candidate must remain a distinct full startup run after the baseline: with exact 512/per-layer bytes and both reported max limits above the request, launch the regular official controller only when Main's usual READY/free-reserve gate permits. Require actual single-block allocation and zero-touch success, exact effective q/slots, post-allocation reserve and populated-unique residency receipt, unchanged `read_windows` route and outputs, normal closure and kernel health. A failed normal allocation is a failed sample; do not retry with relaxed limits, and do not recast the property-only pass as cache fit. `auto/per-layer` follows only as its own fresh-process arm, with its actual selected request/max comparison recorded.

This guard protects the existing six-line protocol and gives Main one new, decision-relevant observation: the root B570's per-allocation limit, paired with the SYCL advertised value and exact USM aspects for the same selected device. It does not alter R228's cache recommendation or R230's window split/worker matrix.

Primary specifications:

- Level Zero [`ze_device_properties_t`](https://oneapi-src.github.io/level-zero-spec/level-zero/1.18.31/core/api/apis/device.html) defines `maxMemAllocSize` as the maximum memory allocation size; [`zeMemAllocDevice`](https://oneapi-src.github.io/level-zero-spec/level-zero/1.18.31/core/api/apis/mem.html) says a device allocation request must be no larger than that value.
- Khronos SYCL [`device info/aspects reference`](https://github.khronos.org/SYCL_Reference/iface/device.html) defines `max_mem_alloc_size`, USM capability aspects, and what atomic host/shared aspects mean. [`USM overview`](https://github.khronos.org/SYCL_Reference/iface/usm_basic_concept.html) distinguishes device, host and shared allocations and cautions that shared host/device concurrency may be unsupported.
- Level Zero [`usable-memory extension`](https://oneapi-src.github.io/level-zero-spec/level-zero/1.18.31/core/api/extensions/device.html) calls `currUsableMemSize` transient and not a guarantee of future success; [`memory properties`](https://oneapi-src.github.io/level-zero-spec/level-zero/1.18.31/core/api/apis/device.html) are per physical memory type.
- Unified Runtime's [Level Zero adapter reference](https://oneapi-src.github.io/unified-runtime/core/LEVEL_ZERO.html) documents `UR_L0_USE_RELAXED_ALLOCATION_LIMITS` and default `0`; the [Level Zero experimental memory reference](https://oneapi-src.github.io/level-zero-spec/level-zero/latest/core/api/experimental/mem.html) marks the old `MAX_SIZE` relaxed flag deprecated and says it permits allocations above `maxMemAllocSize`.
