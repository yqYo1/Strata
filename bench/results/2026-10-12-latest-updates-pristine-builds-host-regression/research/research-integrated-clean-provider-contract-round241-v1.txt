R241 read-only source audit: integrated source6 clean-provider and phase-health contract

Scope and method

Read source6 `common.py`, `policy.py`, `run_root.py`, and `protocol.py`; Main's `latest-update-main-integrated-provider-health-v2.py`, `latest-update-main-integrated-phase-v2.py`, and `latest-update-main-integrated-admission-v4.py`; the v4 qualification and the explicitly approved `latest-update-main-integrated-provider-health-xe-timed1-off-root-v1/record.json` and its `integer-health.stdout`; R236 and report-registry-v156. This was a static/source and retained-receipt review. No source was executed/imported, and no runtime/GPU/process/model/query/build/test/profile/Git/cleanup action was performed. The prohibited tainted record was not opened.

Disposition

The clean branch is exact-map constrained: source6 accepts the clean 7-library health identity only for `timed*` and `heldout*` phases, verifies it is precisely the debug 8-library map with only the pinned validation-layer library removed, and checks that the health receipt's probe command and environment match the clean phase policy. The actual approved timed1-off receipt contains seven mapped libraries and its recorded integer-health argv/environment agree with the source-generated clean policy. I found no source path in this contract that accepts a different library set, path, or hash as an equivalent clean provider once the Main-reviewed qualification and its pinned clean receipt are held fixed.

That conclusion is conditional on Main's reviewed qualification/receipts. Receipt booleans such as `main_reviewed` are asserted fields, not cryptographic signatures. Also, source6 trusts `mapped_libraries` in the pinned clean receipt; it verifies command identity and environment, but does not itself reparse the corresponding stdout artifact and derive the map again. Main's health-v2 source does derive the map from the probe output, hashes each unique path, and records the source and command evidence. This is a layered-provenance limitation, not an observed provider mismatch in the approved receipt.

Findings: exact clean/debug split

It then requires the debug map minus clean map to equal exactly `/usr/lib/x86_64-linux-gnu/libze_validation_layer.so.1.32.0`, and every remaining path/hash pin to match. It compares the receipt's full environment to `environment('xe', False, phase='timed1-off')` and requires a recorded command with exact `[health_binary, BDF]` argv and that environment. Later it pins all health-library files (`common.py:163-173`).

The retained v4 qualification is `passed`/`main_reviewed`; its debug map contains eight paths and its clean map seven. The only removed entry is the validation layer above. Source control of phase selection is unambiguous: `common.py:238-244` only substitutes `clean_health_libraries` when phase starts with `timed` or `heldout`; `policy.py:48-80` makes the same phases disable tracing, validation, parameter validation and verbose loader logs. Debug and startup retain the 8-library detailed environment. Thus a timed/heldout run cannot use the debug map by silently inheriting it: the fresh health receipt equality at `run_root.py:45-58` requires exact selected map and exact phase environment.

Main health-v2 source at lines 24-31 obtains this phase environment from the pinned source6 policy. Lines 80-85 parse the native probe's six protocol lines, require library output lines, deduplicate emitted paths, require the SYCL library and forced adapter, hash each observed path, and store the resulting map. The recorded command's actual stdout is kept in the command evidence. The approved clean command stdout has the expected six success lines and lists precisely the seven mapped unique libraries above (the file repeats loader lines as expected for map events). This is observed retained evidence; the correspondence is generated by Main source and was not independently re-executed here.

Fresh-health and Owner gate ordering

`run_root.py:37-42` verifies the qualification/receipt hashes and calls `admit` plus `phase_health` before Owner import. Lines 43-61 then check the actual qualified Python interpreter and a closed fresh health receipt: current boot, exact engine, Main-reviewed marker, exact health binary and phase-selected library map, device/kernel/reset/retry constraints, expected protocol, exact health command argv/environment, low device-use cap, and age no greater than 120 seconds. At line 62 it hashes the Owner immediately before import (lines 63-66). It creates a run root only after acquiring the lock, checking an exact successful-prefix namespace, and (except startup) checking the predecessor and reviewed startup diagnostic/provider identity (lines 69-93). Therefore a stale/debug/mismatched clean health receipt fails before Owner import or model launch in the source order.

Per-run source and provider identities are rechecked in `source_guard` (`run_root.py:139-165`), while actual pre/post health is run under the selected phase environment; the observed map must equal the selected pin set and each path's current SHA (`run_root.py:176-186`). The final record cannot pass without normal anchored child closure, clean fault gate and same boot (`run_root.py:424-444`). These gates support the source-level ordering claim; this audit did not observe a source6 model campaign result.

After all five pairs, each second arm performs a token/log-probability comparison (`run_root.py:419-423`). The final heldout-on path additionally closes all 11 receipts and requires exactly five completed neutral comparisons before writing the compact summary (`run_root.py:445-466`). It deliberately leaves `main_reviewed=false` on that summary, so Main review is still a separate final barrier. No final all-pairs result was reviewed in this audit.

Residual trust boundary

The fresh-health admission checks its recorded command argv and environment and exact `mapped_libraries`, but does not recompute the map from `fresh['evidence']['integer-health']['stdout']` or cross-check that stdout against the command-log artifact hashes itself (`run_root.py:45-58`). The pinned Main health-v2 generator does perform this derivation (`latest-update-main-integrated-provider-health-v2.py:80-85`), and the retained approved clean receipt carries source/command evidence, so this gap did not produce a mismatch in the reviewed 7-library receipt. For a stronger local receipt contract, the source6 gate could parse the bounded health stdout evidence, require its exact protocol and emitted path set, and bind it to the command-log stdout digest before trusting `mapped_libraries`. Source6 also does not require `clean['main_reviewed'] is True` in `common.admit` itself (`common.py:117-132`), although the qualification and fresh per-run receipt are Main-reviewed and the actual q4 qualification path pins the clean receipt. These are trust-model hardening points, not evidence that the approved receipt is foreign or mismatched.

The q4 admission script (`latest-update-main-integrated-admission-v4.py:72-115`) copies health binary/library identities from the reviewed runtime pin and derives `clean_health_libraries` directly from the clean receipt before writing the pinned qualification. It closes the receipt at lines 110-114. It does not add a separate independent signature to the receipt; source6 relies on the Main-reviewed/pinned qualification boundary described above.
