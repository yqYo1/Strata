## Source-level overhead and synchronization

Against W337, WN adds one raw-logit scan kernel launch per recorded verify window when `STRATA_NAN_GUARD` is unset or nonzero. The default is on (`src/core/verify.cpp:2260–2265`). The launch is in `record_window()` directly after greedy `sample_tokens()` and before the window capture ends (`:1252–1260`, capture at `:1318–1331`). It is therefore a graph node replayed with the window, not a host launch issued separately after every graph replay. It adds one node per window graph and scans every active row's full `n_vocab` logits before the existing queue completion. The ordinary verifier already calls `stream_sync(cs_)` after the graph and before reading mapped outputs/flags (`:1612–1620`); with the guard, that same completion naturally includes the scan. No additional blocking wait/synchronization call is introduced on this path. Kernel helper `done(stream, ...)` only waits when `stream == nullptr`; this call passes `cs`, so it does not wait (`src/kernels/xe/verify_kernels.cpp:43–45, 1137–1158`).

The scan's exact source-level work is: read `T * V` float logits (`4*T*V` bytes), launch `T * 16` work-groups (16 fixed scan blocks per row, up to 8 rows), and write `T * 16` 32-bit flags (`64*T` bytes, maximum 512 bytes for 8 rows). `kVerifyMaxT=8` and `kNonfiniteBlocks=16` are defined in `include/strata/kernels/verify_kernels.hpp`. For a 248,320-token head, each row's scan reads about 0.947 MiB; a one-row neutral decode window reads about 0.947 MiB and writes 64 bytes of flags. The verifier maps a fixed `8 * 16 * 4 = 512` byte flag buffer during setup (`verify.cpp:271`); it does not allocate flags per window. Host reduction reads at most `64*T` bytes after completion (`nonfinite.hpp:10–16`, `verify.cpp:2287–2305`).

There is no separate output readback or device-to-host copy for the guard: the mapped flags are ordinary host-USM, read only after the queue/event has completed. The scan does extend device work on the decode critical path and delays the existing `cs_` completion by its runtime. It is small in storage but its scan cost scales linearly with active rows and vocabulary; source inspection cannot establish its latency or percentage effect against model decode.

The pipelined verifier has an extra nonblocking `event_query(ev_done_)` in `pl_finish()` when the guard is on (`verify.cpp:2643–2650`), after the usual `done()` check already queried the event (`:2632–2641`). This is a defensive readiness assertion before reading mapped flags, not a blocking sync. It is one additional host query per finished pipelined window; no `stream_sync` or event wait was added by the guard. This small host-side check should be distinguished from the scan's real device critical-path work.

Official v0.1.43 uses the same default-on pattern: a single `logits_nonfinite_rows()` call after sampling inside captured `record_window()` (`src/core/verify.cpp:1794–1796`), and one CUDA kernel over `(16 blocks, rows)` (`src/kernels/cuda/verify_kernels.cu:857–876`). It performs the same source-level scan and flag count. The Xe WN therefore follows the official mechanism here. The immutable W337 source has no `nan_guard_on`, `logits_nonfinite_rows`, or `note_nonfinite` path; the WN overhead relative to W337 is additive, not an existing baseline behavior.

## Measurement arm for Main

Use the same WN binary, model, sampling, warmup, prompt bytes/token IDs, context setting, and output length in fresh processes with `STRATA_NAN_GUARD=0` and `STRATA_NAN_GUARD=1` (also record default-unset if validating the shipped default). Choose a prompt ending at at least 32K context while leaving room for at least 3 generated decode tokens. Keep the run profile-free; collect prefill/TTFT and decode token timing separately, plus total wall time, using the existing bench/report fields if available. Run repeated paired arms in alternating order and report each sample and median, along with prompt token count and at least three decode tokens. This estimates scan cost separately from prefill and prevents a one-token startup result from being presented as decode throughput. The report makes no measured performance claim.
