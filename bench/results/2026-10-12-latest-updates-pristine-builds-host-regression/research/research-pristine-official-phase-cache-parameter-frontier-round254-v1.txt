## Finding

Official `--expert-cache 128` and `--expert-cache 512` do not mean 128 or 512 actual resident experts in the native per-layer mode. Each is a byte budget expressed in units of the largest native blob. With the per-layer flag, the source divides the lesser of that budget and current free VRAM after reserve by the sum of all layers' rounded blob sizes, then grants the same quota `q` to each layer. Closed source arithmetic gives `q=3` / 144 total slots for 128 and `q=13` / 624 slots for 512 when the full respective budgets fit. Free memory can lower either result. The supplied official profile has one unique ranked pair per possible layer/expert, so the resident set is the first `q` ranked entries *in each layer*. These capacities and profile entries are not a runtime allocation, hit-rate, or speed result.

The shared device cache and residency table serve prompt `read_windows` verifier windows (including an eight-row window when `--spec 8` selects that case) and subsequent decode. A larger cache therefore changes route placement and CPU/PCIe miss work in both phases. The windowed prompt does not run a separate cache or prefill cache policy. In that path it uses the verifier's existing residency map; ordinary batched Prefill's tail-slot loan is a separate route and should not be attributed to `read_windows8`.

The built-in cache is not an LRU that silently replaces entries as requests run. Startup fills the profile once. `ExpertCache::admit` assigns free slots and returns not-resident when the layer range is full; it does not evict an existing pair. Startup checks a profile slot by reading it back and comparing with its source blob. The default fill does not individually read back every slot; `STRATA_VERIFY_COMPLEMENT` is an optional all-slot byte checksum, which still is not an ID-to-slot proof. If adaptive swaps are enabled, decode has a separate explicit replacement process: a selected victim is copied back from its GPU slot to a host exchange buffer, the candidate blob is copied from its source into that slot, then the source's complement map and device residency table are updated after completion. This is a deliberate, counted route change with asynchronous-copy ordering, not the static cache's default eviction behavior.

## Phase behavior and settings that can change it

**Startup / cache construction.** `--expert-cache N` determines the native profile-cache budget; `--expert-cache-per-layer` changes its allocation shape to a uniform per-layer quota. `--expert-profile` determines ranking and therefore the selected resident pairs. Under R244's reviewed exact profile, 128 and 512 choose top-3 or top-13 entries per layer if q reaches those values. An allocation can be capped by the current `free_room`; `INFO expert_slots` and the actual quota/fill lines, rather than the argument, identify what was admitted. Profile fill reads/copies each admitted packed expert from its stable source to the device cache and performs a one-slot readback check. The readback is a startup validation cost, not a per-request weight transfer.

**Serial prompt `read_windows` / `read_windows8`.** For each verifier window, the same `d_res`/`host_res` map resolves each routed expert. Cached rows execute from the GPU blob already in its cache slot. Nonresident rows are classified to the CPU expert pool or the configured PCIe route; therefore changing `q` changes how many prompts' rows are GPU-resident and the mix of CPU/PCIe work. The window's route/row count is also a separate determinant: `--spec 8` groups up to eight rows, and the same cache quota does not imply each expert gets eight rows. The adaptive-swap code explicitly avoids adapting while `in_prompt_read`; for this serial prompt mode, profile membership stays fixed through the windows. `DONE`'s hit/file-source deltas in the reviewed official source are decode-scoped, while `PP` and `--stats` boundaries have different aggregation; do not treat the process summary as a complete prompt-vs-decode per-layer attribution (R249).

**Batched Prefill, only if selected.** `--prefill N/auto` selects a different chunked path. With borrowing enabled (default), `plan_lend` can loan the cache's tail slots to temporary prefill buffers, subject to chunk/slot and lend-percentage rules. The associated resident experts are temporarily marked missing; they can then be streamed/read for the prompt. After prefill, the exact borrowed slots are refilled from their original profile experts, the cache is synchronized, and the residency table is restored before later verifier windows/decode. `--no-prefill-borrow` keeps those scratch buffers separately allocated for the session, which changes device-memory pressure and can reduce the cache quota/fit. `--prefill auto` jointly chooses chunk and lend volume; a change in cache size can alter both. None of this applies merely because the serial `read_windows` loop processes prompt tokens in windows. Keep the prompt route fixed when comparing 128/512.

**Decode and adaptive replacement.** The same cache table continues into decode, so cache size changes its GPU hit fraction and CPU/PCIe miss work. Source defaults are `--adapt-swaps 96`, `--adapt-every 4`, decay 0.7, and minimum gain 1.5 (actual argv may override them). Decode counts route use and can swap up to the configured number of experts at an adaptation boundary. Victims are copied from device to exchange storage; incoming expert blobs are fetched from the source and transferred into the slots. Until transfer completion, pending pairs remain nonresident; after completion the exchange map, `host_res`, and device residency map are updated. These operations change subsequent decode's weight-source path, miss count, and transfer activity. `--adapt-swaps 0` disables that dynamic tier, leaving the initially filled per-layer set static. `--pcie-frac`, `--pcie-mode`, host-pool settings, source/RAM tier and profile are additional route controls and must remain fixed in a cache-size comparison.

## U versus WN source comparison

The quota formula, profile-backed fixed residency, per-layer admission and explicit decode adaptation are present in pristine U and WN. Relevant source behavior is consistent at this boundary. WN adds strict duplicate `(layer,expert)` rejection in `read_expert_profile`; U validates profile format/geometry/ranges but does not reject duplicates generally. R244 found the supplied profile has all 24,576 unique pairs, so this difference does not change the reviewed 128/512 candidate sets for that exact profile. WN also includes later Prefill/native-kernel and nonfinite-related changes; those can change the chosen prompt implementation and numerical/performance behavior independently of cache quota. The two revisions are not a controlled cache-only A/B unless the selected prompt/verify route and all other selectors are matched. Do not use a WN-prefill route result to infer an upstream U effect from the cache knob alone.

## Smallest useful candidates after the current owner run closes

No value is selected as optimal. Use the closed cache-512 record as control only if it is complete and its route/health/correctness gates pass. Do not rerun it as a new baseline.

1. **`--expert-cache 128 --expert-cache-per-layer`** with the same profile, verifier window, source mode, fixed reserve, CPU/PCIe policy, and other arguments as cache512. This is a one-factor quota screen (nominal 3 slots/layer versus 13/layer when the full budget fits). Record actual q, slots, bytes, fill count/readback, and prompt/decode residency counters. Decode must be measured again: the lower quota changes the same shared residency table, which changes the experts and rows dispatched to CPU/PCIe after the prompt. Prompt-only timing cannot predict that decode distribution or the cost of its changed misses.
2. **`--adapt-swaps 0`** against the current recorded adaptive setting, holding cache512 and all else fixed; use this only if the closed control confirms adaptation was enabled (default is 96 per 4 rounds). This keeps prompt `read_windows8` policy unchanged because the source suppresses adaptive ticks during `in_prompt_read`, while making decode static rather than evicting/refilling profile entries. Decode must be measured again because the source set and weights loaded per window diverge after the first completed adaptive swap; CPU/GPU route counts, D2H/H2D swap work, and output can all change. If the control already specified zero swaps, this candidate is a duplicate and should be dropped rather than rerun.

Do not combine these two first: cache quota alters the resident population that adaptation chooses from. Do not add `--pool-workers 3` or `--expert-cache auto` as new candidates here; R245 already screened them as separate possibilities. Do not use `--no-prefill-borrow` as a `read_windows8` candidate: it only applies if the independent batched Prefill path is selected. If the owner wants to compare batched Prefill, make that a different route experiment with explicit chunk/lend/refill receipts and a decode retest after the slots are restored.

For either screen, use a fresh process from the same starting profile and prompt, keep route-affecting flags fixed, record effective cache quota/fill and per-phase timings/counters, verify that all prompt tokens were processed by the intended path, and rerun decode from the corresponding resulting prompt state. A candidate that changes cache membership cannot borrow the other arm's cache or continue its decode state. Retain output/logit, runtime-error/fault, progress, and normal-close checks. Existing `DONE`/`PP`/process-lifetime `--stats` boundaries are not interchangeable; report prompt and decode separately without deriving device time by subtraction.
