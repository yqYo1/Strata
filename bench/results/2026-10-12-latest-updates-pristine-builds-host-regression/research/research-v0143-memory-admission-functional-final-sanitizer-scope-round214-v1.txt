## WN versus official U and platform/macro selection

Official U's `conversation_memory.cpp` credits clean inactive-file cache to each visible cgroup level and also retains root cache credit for the operator-cap term. WN changes this materially: the only cgroup credit is attached to a fully parsed, canonical, unique, exact, non-root process leaf that has no child directories; all visible ancestors and the operator cap use raw charged usage. It rejects partial path resolution, duplicate/malformed membership and symlink/unknown child cases for purposes of leaf credit. This is a conservative visible-hierarchy policy: parent limits can report less room than might be reclaimable if parent cache were credited, but nested `memory.min`/`memory.low` descendants do not make parent cache look available when reclaim is directed at that parent. The leaf's own min/low are not subtracted; targeted Linux reclaim ignores the reclaim target's own protection. Hidden ancestors, cgroup changes after sampling and kernel reclaim outcomes remain outside this estimate. R200's earlier noncanonical-membership finding is closed in this snapshot: `group_dirs()` gates exactness on leading `/`, no trailing `/`, no `//`, and the fixture now checks those malformed forms (`conversation_memory.cpp:181-209`, `memory_guard_test.cpp:373-381`).

The memory sampler is OS-selected, not an XE/SYCL-selected implementation: `sample_host_memory()` has `_WIN32` handling (`GlobalMemoryStatusEx`, min of physical and commit availability) and a `__linux__` path that reads MemAvailable and cgroup controls (`conversation_memory.cpp:301-334`). `STRATA_ENABLE_XE` in CMake enables the Xe runtime; `STRATA_BACKEND="xe"` is a compile definition. The sampler itself has no `STRATA_ENABLE_SYCL`, `STRATA_ENABLE_XE` or `STRATA_BACKEND` conditional, so there is no silent alternate XE memory-probe branch to enable or omit. WN's existing `build/free/compile_commands.json` is stale relative to the v0.1.43 source (it records upstream `0.1.40.2` / `e8ca9af`), so it cannot prove which current dirty-tree sources have been compiled. Do not cite that cache as current-build proof. Main's current build receipts and validation results, if any, are the authority for actual compilation.

No native memory authority is absent from the reviewed API path: `set_memory_limit_bytes()` feeds the process-wide cap, `available_host_bytes()` delegates to the native C++ sampler, and the generation/server SAVE and parking paths call that native admission before copying. Python `psutil` in `serve/session_save_retry.py` is only a wait/retry scheduling predicate after a native typed refusal; it never overrides native admission. The flag is real and opt-in; `--memory-limit-mib 0` means no explicit cap, while a positive value constrains native admission. Invalid negative, malformed or overflowing CLI/environment values are rejected (`generate.cpp:2351-2370, 2502-2515`). A bad/missing cgroup sample falls back to MemAvailable when there is no operator cap, but remains unknown (and refuses admission) with an explicit cap (`conversation_memory.cpp:301-320`). A valid zero available-byte reading is known zero, not unknown; `memory.max`/`memory.high = max` and the v1 near-2^63 sentinel are unlimited. Fixture cases cover zero usage/headroom, unlimited v2/v1, malformed values, unknown usage, and explicit-cap fail-closed behavior (`memory_guard_test.cpp:62-249`).

## Leaf credit, parents and operator cap

For a known v2 tree, the scan keeps each visible finite `memory.max` and `memory.high` term, using the tightest remaining room. Cache credit is calculated only for the exact child-free process leaf and clamped to current usage after subtracting dirty/writeback (`conversation_memory.cpp:79-115, 146-175, 212-244`). If the leaf is incomplete, malformed, ambiguous, root-only, symlinked or has descendants, its credit is zero. No ancestor receives the child's credit. Cgroup v1 is similarly limited to the exact child-free memory-controller leaf; its hierarchical total counters and near-2^63 unlimited limit are handled separately.

For `--memory-limit-mib`, `combine()` uses raw visible-root current, or MemTotal-minus-MemAvailable if root current is unavailable; it uses no cache credit (`conversation_memory.cpp:246-281`). Bad/unusable cgroup accounting under an explicit operator cap returns unknown rather than guessing; with no cap, the legacy MemAvailable fallback remains. Tests specifically cover nested parent tighter-than-leaf limits, root/operator cap raw usage even with valid leaf/root cache, root namespace not being credited, `max`, malformed control values, cap ties, missing root current and unknown MemTotal (`memory_guard_test.cpp:75-153, 340-415`). This protects admission from over-crediting protected descendant cache at ancestors; the consequence is conservative under-admission, not guaranteed maximal reclaim.

The no-child predicate is a sampled filesystem observation, not a lock. A child can be created or the task moved after it is checked; an ancestor can also be hidden above a cgroup namespace/mount. Therefore the implementation comment is correct to call the reading an estimate and not a reservation. No source fixture can prove what a real kernel will reclaim on a 125.7-GiB host under concurrent cgroup changes.

## SAVE allocation ownership and re-probe

The opt-in `session_save_reclaim` helper selects the same deepest/pinned checkpoint the file path will serialize, estimates its peak with saturating arithmetic, and does nothing for initially unknown telemetry or an unknown/overflowed size. If pressure is known, it releases reconstructible retained/reuse KV buffers, then oldest evictable parked entries, then non-pinned checkpoints except the selected one. It probes after each step and stops at the first observed sufficient reading. The selected checkpoint's index is adjusted while erasing from the back; pins remain. This matches the allocation ownership rule: reclaim only unpinned host cache/checkpoint copies, never live device state or the selected checkpoint (`session_save_reclaim.hpp:16-55`; `session_save_reclaim_test.cpp:44-117`).

The native SAVE handler computes current live-state sizes with overflow checks, invokes optional reclaim before `session_save_checkpoints`, then supplies a fresh `sample_host_memory()` probe to that helper's admission callback; only after successful admission does it construct snapshot sources and capture the live state (`generate.cpp:7944-8016`). The peak estimator includes write buffer/small vectors, twice the selected checkpoint, live state/tokens/images and a K/V source directory (`conversation_file.cpp:1140-1157`). K/V payload is streamed from authoritative pools into the output; it is not first copied as an unbounded full-host snapshot. The next admission sample occurs before the expensive snapshot copy. This remains a time-of-check/time-of-use race with unrelated allocations; it is not a reservation, and a later allocation/write can still fail.

One narrow non-safety limitation: if the initial probe reports pressure, one reclaim action is taken, and the next probe becomes unknown, `done()` treats unknown as terminal and returns with that first release already made (`session_save_reclaim.hpp:25-34`). The final SAVE admission probe then refuses because the reading is unknown. This can discard one recoverable cache despite failing to prove that it helped; it does not permit an unknown sample to authorize the SAVE or trigger more eviction. Existing helper tests cover initially unknown/no-pressure/overflow and known re-probe progression, but not “known pressure, one reclaim, then unknown.” A deterministic test could document this bounded behavior or the helper could roll it back only if rollback is safe; no change is recommended in this audit.

## Retry deadline after telemetry

The current Python retry helper checks the 30-second deadline before telemetry and again after telemetry and process-identity checks immediately before another `engine.session_file()` attempt (`serve/session_save_retry.py:64-80`). The focused host test explicitly advances fake monotonic time to the deadline inside `available_mib()` and asserts that no retry SAVE is dispatched (`serve/test_session_save_retry.py:72-84`). It also tests zero/bad telemetry, process replacement/death, retry limit and FIFO serialization (`:95-159, 206-240`). This closes the earlier R199 observation that the deadline was not checked after the availability probe. A tiny scheduling interval still separates the final monotonic check from the Python call and stdin write; strict “never write after the exact deadline under arbitrary scheduler suspension” would require a boundary in/around command writing, but the telemetry-delay case requested here is now covered.

## 125.7-GiB / 262144-context boundary

A host reporting 125.7 GiB total does not report 125.7 GiB currently available. The native guard uses MemAvailable, visible cgroup limits and optional operator cap, with a configurable floor. The full-context diagnostic separately requires exactly 262144 supplied tokens and physical context capacity; it estimates snapshot plus two checkpoint allowances plus 1 MiB, keeps a minimum 2560-MiB RAM floor, checks `available_host_bytes()` before prompt processing and rechecks after the 262144 rows before snapshot capture (`generate.cpp:1282-1307, 1336-1362`). It tracks complete target/draft chunk coverage and a terminal storage-probe row. It then validates snapshot bytes, poisons/restores, and verifies restored K/V state. Source explicitly says the terminal row is a storage probe and makes no prediction-quality claim (`generate.cpp:1308-1317, 1345-1359`). This is a useful storage/capacity diagnostic if executed and recorded, but it is not a SAVE-handler proof, an allocation guarantee, or a quality/generation run. No 262144 run or 125.7-GiB fit was established in this source-only review.

## CPU and host-only sanitizer coverage

The source includes meaningful, nontrivial CPU-only fixtures for the new memory semantics:

- `memory_guard_test` supplies fake meminfo, `/proc/self/cgroup` and cgroup filesystem trees. It covers nested parent high/max limits, operator cap behavior, v1/v2, dirty/writeback deductions, malformed/duplicate/overflow values, missing/partial/ambiguous paths, child directories and symlinks, zero/unlimited values, and explicit-cap unknown versus no-cap fallback. This is much stronger than a real-files smoke test, but it cannot exercise kernel reclaim, namespace visibility or the admission race.
- `session_save_reclaim_test` injects availability and intercepts allocations to test selected checkpoint identity/storage, pin preservation, no allocations in the reclaim helper, one-step-at-a-time eviction, initial unknown/no-pressure/overflow and final refusal before checkpoint copying. It does not call the real OS memory probe or allocate pressure on the host, and it omits the post-reclaim-unknown transition noted above.
- `test_session_save_retry.py` uses a fake clock, fake process and HTTP/FIFO harness. Its post-telemetry deadline regression is directly meaningful for retry dispatch policy; it does not test actual `psutil` or native C++ memory measurements.

CMake names the pure CPU targets explicitly (`CMakeLists.txt:784-788`). `STRATA_SANITIZE` instruments project host code through `-Xarch_host`; the Xe device image is not instrumented (`CMakeLists.txt:154-169`). A host ASAN/UBSAN pass can detect host memory errors in the C++ parser/helper/handler code that was actually built, but cannot certify device memory, real cgroup reclaim, cgroup races, process-level allocation headroom, 262144-context fit or full SAVE success. No test/build was run as part of this review; report only source coverage, not a pass result.
