## Conclusion

The new cache-512 capacity does **not**, in the reviewed `read_windows`-8 setup, select a different class of host/device synchronization or introduce a path that needs concurrent atomic modification of host or shared USM. It adds resident `(layer, expert)` slots and can make more individual window groups fully resident, but both the 128 and 512 configurations use the same partial-residency `device_plan` / stepped serve path. A fully resident, zero-doorbell verifier graph is not selected by either candidate: source checks residency of every expert in every verifier layer, whereas the source-derived full-quota cache sets are 144 (3/layer) at request 128 and 624 (13/layer) at request 512, out of 24,576 possible pairs. At request 512, actual q/effective slots still depend on the startup free-room cap; the run’s startup receipt must be used for the realized count.

The target receipt reports `usm_host_allocations=true` and `usm_shared_allocations=true`, but both `usm_atomic_host_allocations` and `usm_atomic_shared_allocations` are false. These results exclude concurrent host/device atomic access to those allocation kinds. They do not prohibit ordinary host-USM device reads/writes when the host and device take turns and the program synchronizes between phases. The SYCL reference explicitly requires turn-taking for host-USM accesses, warns that shared USM host access during a kernel is undefined when atomic-shared/concurrency capability is absent, and says host/device concurrent atomic modification is enabled by the atomic aspects ([USM basic concepts](https://github.khronos.org/SYCL_Reference/iface/usm_basic_concept.html), [interaction with host code](https://github.khronos.org/SYCL_Reference/iface/interaction-with-host-code.html)).

For the specified serial setting (`STRATA_VERIFY_STEPPED=1`, `STRATA_VERIFY_PIPE=0`, `STRATA_VERIFY_NO_HOST=0`, `STRATA_VERIFY_DEVICE_PLAN=1`, pool workers 5, PCIe fraction 0), the verifier’s host sequence/plan/flag cells are ordinary host-USM buffers, and device kernels still publish/read them. The important source property is the ordering: the GPU’s segment completes before the host inspects its sequence and payload; the host runs the CPU pool and raises plan/PCIe/continuation flags before submitting the next graph segment. `PIPE=0` avoids the optional helper-thread path that can overlap host pool service with GPU execution. Thus the host and GPU do not concurrently access those cells in this path. `volatile` itself is not synchronization and does not justify concurrency; the queue/graph boundaries are the relevant ordering. This static audit finds no new cache-512-specific unsupported host/shared atomic dependency. It does not certify driver correctness or replace the current startup/model/fault/output gates.

The approved property observation is a capability/property result, not a cache-fit or model-run result. In the Main-reviewed, passed, same-boot receipt, the property-only CAPS helper reports ZE and SYCL max-allocation size `10,132,807,680` bytes, global memory `10,666,115,072` bytes, and device-USM support. Its exact 512 candidate request field is `1,276,953,600` bytes, below both reported maximum-allocation values. The receipt says relaxed allocation limits were unset. That passes the necessary per-allocation-property comparison only; it does not prove the cache is available, fits with the rest of the process, or leaves required VRAM reserve. The CAPS counters are zero for allocation, queue/context, copy and kernel operations. The same root receipt separately records two integer health workloads, so it is incorrect to describe the *whole receipt* as a zero-GPU-work run. It records no model execution or model launch attempt.

## What changes between 128 and 512

R244 verified that the supplied STRP profile has 24,576 distinct ranked pairs, one per possible `(layer, expert)`. With native per-layer admission, the first `q` ranked profile experts are filled in each layer. R228’s source arithmetic gives q=3 / 144 logical slots / 281.03 MiB for the full 128 budget, and q=13 / 624 slots / 1,217.80 MiB for the full 512 budget. These are conditional full-budget results; actual startup memory may cap either quota. R244 also confirms that when q=13, the resident set is each layer’s first 13 profile IDs, not the first 624 global profile entries, and that the q=3 set is each layer’s first three.

The cache is device memory. `ExpertCache::open_sized` uses one contiguous device allocation for the rounded per-layer slot extents (`sycl/src/core/expert_cache.cpp:708–730`). The verifier receives the device residency table and cache base/slot offsets. In its constructor (`sycl/src/core/verify.cpp:704–722`) it sets `all_resident_` only if **every expert ID** is resident for every layer in that verifier stage. Neither a 144- nor 624-slot cache can satisfy that condition for a 48×512 model. With `STRATA_VERIFY_DEVICE_PLAN=1`, `device_plan_` is enabled whenever the all-expert condition is false (`:723–729`), at either cache size. Larger q changes `d_res` lookup results and miss counts; it does not turn this non-all-resident window into the zero-doorbell graph.

For each layer/group, the device plan kernel routes top-k expert IDs through the residency table, writes GPU-resident expert pointers into its plan, and marks whether the group is fully resident. The verifier then uses the same `wait_flag_ge_or` plus conditional plan-copy path for both cache sizes (`verify.cpp:1448–1466`). On larger q, it is plausible that more particular windows/groups have all their routed top-k experts resident. For such a group the GPU can set the device-only `skip_` marker and avoid waiting for/copying a host plan. That is an existing `device_plan_` subcase, not an all-stage residency mode and not a newly introduced shared-host atomic. The serve point and its sequence/continuation protocol remain. Only the startup and per-window route/residency receipts can establish how often it occurs in the actual prompt/decode.

The CPU pool remains needed for nonresident routed rows (`STRATA_VERIFY_NO_HOST=0`, `--pool-workers 5`). It can have zero jobs for a particular fully resident group; that does not by itself remove the group’s stepped serve boundary. Avoid equating “all experts routed in this group are resident” with “the whole verifier is all-resident” or “the window has no host/GPU handoff.”

## Concrete marker and memory audit

**Window staging allocation.** `verify.cpp:218–239` documents the stepped contract, and `mapped()` selects `sycl::malloc_host` when stepped mode is on and `STRATA_VERIFY_HOST_UNCACHED` is not enabled. It aliases the mapped device pointer to that host-USM allocation; the verifier allocates `h_seq_`, `h_flag_`, `h_flagA_`, `h_flagB_`, `h_plan_`, payloads and output through this helper (`:535–560`). The task’s environment uses the normal stepped defaults, so these are host-USM cells accessible to device kernels, not shared-USM allocations. The false `usm_atomic_host_allocations` bit means system-scope atomic modification of these host allocations cannot be assumed safe under concurrent host/device access; it does not revoke host-USM device access (`usm_host_allocations=true`) when access is serialized.

**GPU doorbell writes.** `sycl/include/strata/sycl_doorbell.hpp` implements the default `sys_store` and `sys_load` with uncached annotated-pointer reads/writes plus system fences (lines 46–98). A fallback using system-scope `sycl::atomic_ref` is present under `STRATA_DOORBELL_ATOMIC_LOAD` / `_STORE`. The pinned official `compile_commands.json` entries for `elementwise.dp.cpp` and `verify.cpp` have no such `-D` definitions; the source pin and production executable hash are in the property receipt. Thus the recorded official build selects the non-atomic default path. The window publisher stores route payload and sequence/tag data through `sys_store_mapped` / `sys_store` (`sycl/src/kernels/cuda/elementwise.dp.cpp:637–708`); it does not atomically modify host-USM payload/sequence objects. GPU command completion precedes the host’s volatile sequence and payload reads at the stepped serve point (`verify.cpp:2066–2074`). `volatile` makes accesses observable to the compiler but would not make a concurrent access safe by itself.

**Host plan/flags and device waits.** The host writes its fallback plan and flag A only after the preceding GPU segment is drained; it waits for copy completion, raises flag B, then writes the continuation flag before the next segment is submitted (`verify.cpp:2084–2134, 2140–2146`). Device kernels waiting on flags use `strata::sys_load`; for this configuration the waited-on segment begins only after the host has raised those flags. The `PIPE=0` condition selects the direct pool branch, not the branch that starts a helper thread and launches the plan-copy/VRAM segment while pool work remains in flight (`:2090–2122`). `STRATA_VERIFY_SPLIT` may still form split segments, but with PIPE disabled the host completes the serve and raises its flags before those next segments are submitted.

**GPU-local/device-only atomics.** `resident_plan_kernel` can use an atomic on its work-group-local `s_bad`; its optional adaptive usage counter uses `sycl::memory_scope::device` and a device-global usage pointer (`sycl/src/kernels/cuda/verify_kernels.dp.cpp:2080–2140`). The per-group `skip_` is allocated with `sycl::malloc_device` (`verify.cpp:748–765`) and accessed by GPU kernels (`verify_kernels.dp.cpp:2233–2350`). These operations do not use host or shared USM. Device USM is supported by the receipt. They remain subject to their normal device-side correctness; they are outside the two reported host/shared atomic aspects.

**Queues and drains.** `cs_->wait()` and `copy_->wait()` in the stepped serving loop are host-side queue completion operations, not a host/GPU marker-poll protocol. They establish the points where host code resumes after device operations. The queue drains do not imply that every other mode is safe; the safety here depends on the exact stepped control flow and `PIPE=0` settings. Likewise the host-only `std::atomic` pool state and the direct synchronous `ExpertPool` callback are CPU-thread coordination, not GPU atomics on host-USM cells.

**The excluded batched markers.** R238’s separate batched-Prefill audit identified two different volatile host-USM completion-marker families: PLE `ple_done_seq` and the Stager’s `done_seq`. PLE double-buffer completion is polled between multi-chunk Prefill chunks; staged expert-copy completion is polled by Stager for nonresident batched expert misses. The active `read_windows` verifier path executes window graphs and invokes its CPU pool at stepped layer boundaries; it does not execute `Prefill::run` for the long prompt. `prefill.cpp` may still be initialized for the application, but these two polling loops are tied to the batched Prefill work/streaming route, not to the cache-hit plan branch in verifier windows. Cache 512 does not switch `--short-read` or chunk size and does not expose those R238 multi-chunk polls in the specified window route. Keep the R238 route exclusion: no inference from this audit should be used to permit long batched Prefill or large chunks on the same unsupported atomic-host/shared device. R238 remains SHA-256 `53f93651bcbdd3d986c27f1c5c8be81634982f5f4f1b39892ecd1fc5a7890904`.

## What remains unproven and what the run must retain

The old cache-128 full-32K PASS demonstrates that the owner’s complete run checks passed for that particular run; it is not proof that every accessed host-USM cell was race-free or that an unsupported capability was never used. The static source contract provides the no-overlap argument for the exact stepped path, subject to the compiled binary/source/environment matching the recorded values. A result at cache 512 must still establish the actual q and slots, successful device allocation and fill, same `read_windows` window size/stepped markers, CPU miss route and job counts, unchanged PCIe/MTP/context controls, output/correctness, normal closure, and pre/post kernel fault gates. The property receipt alone cannot establish any of these run outcomes.

Record whether actual cache quota is 3 or 13 (or a lower free-room-capped value), aggregate slots, requested/effective allocation bytes, and the run’s full source/binary hashes. Preserve Main’s `read_windows` route and serial control environment. A 512 startup/allocation failure is a failed arm; the property maximum is not a substitute fit receipt. No recommendation is made to weaken checks or alter the verifier protocol.
