# R196 — v0.1.43 cgroup protection versus targeted reclaim

Source-only reconciliation of R195. This report does not alter R195, W337, source, tests, or the report registry. No tests, builds, compiler/AST/import/runtime/GPU/model/process queries, Git mutations, or cleanup were performed. No runtime qualification or OOM outcome is claimed.

## Result

R195's specific claim that the sampler is unsafe because it ignores the *target cgroup's own* `memory.min` is incorrect for targeted cgroup reclaim. Linux explicitly ignores the target memcg's own min/low protection when reclaim is targeted at that memcg. Thus, for a target cgroup with no protected descendants, its own clean inactive-file cache is not made unavailable by that cgroup's own min/low setting during reclaim targeted at its `memory.high`/`memory.max`.

There is a narrower, still concrete accounting concern: when a limit target has descendants, its `memory.stat` inactive-file counter includes subtree pages, while targeted reclaim at that target continues to honor protections on descendant cgroups. v0.1.43 assigns the entire cache credit to each target limit. If a descendant's clean inactive cache is protected by effective `memory.min` (or is currently protected by `memory.low`), the parent-target credit can exceed what that targeted reclaim can reclaim. This is a conditional source-level admission overestimate. It does not establish that an allocation fails or that runtime OOM occurs.

## Source basis

Official Strata source is immutable commit `7695859aa13afb248bdb4d36f9b2e95707db079d` at `/home/yayoi/ghq/github.com/Niko1221/Strata/.worktree/bench-upstream-v0143-pristine-20261012`; immutable W337 is `337255086026f6eef21a861c297183d05a5f7a22` at `/home/yayoi/ghq/github.com/yqYo1/Strata/.worktree/diag-xe-host-issuer-ledger-20261012`.

In official `src/core/conversation_memory.cpp`, `reclaimable_cache()` reads v2 `inactive_file` and subtracts `file_dirty` and `file_writeback`; `scan_levels()` walks visible cgroup directories from mount root to the process cgroup, reads each level's `memory.current`, `memory.max`, and `memory.high`, and attaches that level's cache credit to every finite limit at that level. `combine()` computes `room = limit - (current - credit)`, then uses the minimum room across the limits. It does not read `memory.min`/`memory.low` or traverse the limit target's descendants as separately protected reclaim candidates. The v2 `memory.current` value is subtree-inclusive.

The Linux cgroup v2 documentation says min is hard protection up to the effective boundary, low is best-effort protection, and a cgroup's protection is limited by ancestor settings and overcommit. It also explicitly makes protection relative to the reclaim target: the target's configured min/low is ignored; protection configured on a descendant applies to reclaim targeting an ancestor, capped by the intermediate ancestors' values. See [memory.min/low and high/max semantics](https://docs.kernel.org/admin-guide/cgroup-v2.html#memory-interface-files) and [Reclaim Protection](https://docs.kernel.org/admin-guide/cgroup-v2.html#reclaim-protection), especially lines 1279–1286 in the current rendered documentation.

The current upstream kernel header implements the target special case directly: `mem_cgroup_protection(root, memcg, ...)` returns zero min/low when `root == memcg`; `mem_cgroup_unprotected(target, memcg)` returns true when `memcg == target`. See [`include/linux/memcontrol.h`](https://raw.githubusercontent.com/torvalds/linux/master/include/linux/memcontrol.h), `mem_cgroup_protection()` and `mem_cgroup_unprotected()` (around lines 514–595 in the current file). That supports rejecting R195's unconditional own-min objection. It does not mean the target's descendants are unprotected.

The same kernel implementation's `memcg_vmstats` distinguishes “Aggregated (CPU and subtree) page state” from “Non-hierarchical (CPU aggregated) page state”; `memcg_stat_format()` emits `memory.stat` through the aggregate `memcg_page_state()` accessor. Thus v2 `inactive_file` in a parent can include descendant pages. See [`mm/memcontrol.c`](https://raw.githubusercontent.com/torvalds/linux/master/mm/memcontrol.c), around lines 632–639, 752–765, and 1633–1656. For v1, Strata explicitly uses `total_inactive_file`, and the v1 interface defines `total_<counter>` as hierarchical; the same target-versus-descendant distinction should be kept if v1 reclaim credit is ever used for such analysis.

The v0.1.43 SAVE reclaim helper (`include/strata/core/session_save_reclaim.hpp`) only frees Strata-owned reconstructible cache/checkpoints and re-probes the sampler. It does not call kernel `memory.reclaim` or otherwise control kernel reclaim target selection. This report concerns the sampler's preflight estimate for potential kernel reclaim by subsequent allocations, not an assertion that the helper itself reclaims protected kernel pages.

## Concrete conditional over-credit example

Let `A` be a visible ancestor with a finite `memory.high` or `memory.max`; process cgroup `B` and sibling `C` are below `A`. Suppose `A.memory.current = 2.0 GiB`, its limit is `2.2 GiB`, and its subtree `inactive_file` is `0.7 GiB` with no dirty/writeback deduction. `C` uses `0.8 GiB`, has effective `memory.min = 1.0 GiB`, and contributes `0.6 GiB` of that inactive-file cache. Let the remaining `0.1 GiB` of inactive cache be reclaimable from unprotected descendants.

The sampler attaches all `0.7 GiB` to A's limit: apparent charged usage is `1.3 GiB`, so it reports `0.9 GiB` of limit room. But when reclaim is targeted at A, A's own protection is ignored while C's descendant protection remains in force. At most the unprotected `0.1 GiB` of these cache pages is represented as reclaimable in this simplified example; the `0.6 GiB` under C's effective min cannot be treated as available for A-targeted reclaim. A SAVE needing `0.5 GiB` can therefore pass this ancestor-room term even though the reclaimable-credit model overstates it by `0.6 GiB`. Other ancestor/leaf limits, host MemAvailable, concurrent allocations, reclaimability subtleties and allocation behavior can still change the final result. The arithmetic demonstrates a conditional sampler-accounting error, not a reproduced SAVE failure or OOM.

A parallel `memory.low` example is weaker: the docs define low as best effort and allow reclaim from low-protected cgroups when no unprotected reclaimable memory is available. A conservative preflight should treat low-protected descendant cache as unavailable when it cannot know the reclaim competition state, but should describe this as possible pressure/under-reclaim, not a hard invariant equivalent to min.

## Conservative correction and source-level cases

Do not subtract the target's own configured min/low wholesale from its cache credit: that applies the wrong reclaim target semantics and can needlessly refuse saves. Instead, define credit relative to each finite limit's target. A safe, conservative v2 policy is to give a limit target zero subtree cache credit whenever its descendant protection/cache composition is not known. A more precise policy may credit the target's own local clean inactive-file pages while excluding descendant cache that could be protected. It must handle effective protection, not just compare each configured min/low number independently: ancestor caps, overcommit, `memory_recursiveprot`, and unknown/unreadable descendants affect the effective boundary. If those conditions cannot be resolved from visible files, fail closed for that target's cache credit. With the existing path-only scan, the least complex safe change is likely zero credit for protected/unknown subtrees, with no credit restored unless descendant state is fully accounted.

Fixture-driven pure-source cases to add before relying on the credit as SAVE admission evidence:

1. A single cgroup target with `memory.min > 0`, no descendant cgroups, and clean inactive cache: targeted-reclaim model must not remove the target's own cache credit solely because of its own min. This guards against the over-broad R195 fix.
2. Ancestor A with child C below its effective min and inactive cache in C: A's target-specific credit must exclude C's protected cache; demonstrate the numeric case above.
3. Ancestor A with a low-protected child: conservatively exclude that child's cache credit unless the model establishes that unprotected reclaimable memory is exhausted; label this best-effort/pressure behavior separately from hard min.
4. Min/low overcommit and ancestor cap, plus `memory_recursiveprot` behavior where applicable: assert conservative fallback rather than assuming configured child values equal effective protection.
5. Missing, malformed, unreadable, and hidden descendant state: no optimistic descendant cache credit for that target. Keep existing explicit-cap unknown/fail-closed behavior covered separately.
6. A target with only unprotected descendants and clean inactive cache: retain the credit that the precise policy can justify; dirty/writeback remain deducted.

These fixture cases validate parsing and arithmetic only. A runtime claim about the kernel's actual protection behavior or whether SAVE reaches OOM requires a separately authorized kernel/cgroup integration experiment with recorded kernel version, hierarchy, protection settings, competing reclaimable memory, allocation/result, and relevant cgroup events. No such experiment was run here.

## R195 correction

R195's statement, “A cgroup can therefore report clean `inactive_file` that is not available ... while it is protected by `memory.min`,” is too broad because it does not qualify whether that cgroup is the reclaim target or a protected descendant. The assertion that the sampler “does not inspect `memory.min`” and therefore necessarily has a concrete defect is not established for the target's own usage; kernel targeted reclaim ignores that target's own min/low. The more precise conditional finding is the protected-descendant case described above, since parent `memory.stat` cache credit can aggregate those descendant pages while parent-target reclaim honors their protection. R195's recommendation to subtract target min from cache credit should therefore be withdrawn; use per-target descendant-aware credit or a conservative zero-credit fallback when the protected subtree cannot be resolved.

R195's other findings are outside this reconciliation and remain neither revalidated nor changed here. In particular, this source analysis proves neither runtime OOM nor SAVE qualification.
