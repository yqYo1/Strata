## Determination

There is no transition-time destruction/reuse of the prefill workspace in this source route. Serve constructs one `Prefill sp`, initializes it before READY, and keeps it alive for subsequent prompt and decode work. With `--no-prefill-borrow`, `lend_first` remains negative; `lend()` and final `refill()` are no-ops. `sp.run()`'s own buffers and staging ring remain allocated and owned while verifier graphs run. This avoids a free-while-graph-reuses-prefill-addresses hazard at the transition, but retains sizeable prompt-only VRAM allocations during decode; the fit ledger must include that overlap. It does not free prompt workspace to make decode allocations fit.

For a fresh exact 32,768-token request, batched conditioning covers `n-1 = 32,767` positions; in one uninterrupted text segment `Prefill::run` processes chunks 8,192, 8,192, 8,192, and 8,191. Serve can split the positions at prompt/cache/message/turn boundaries, so those exact four sizes assume no reused prefix and no internal prompt cuts. The final prompt token at `n-1` is not part of that batched count: after `prompt done`, the first verifier window feeds it. `--short-read 0` sends every positive-length eligible fresh text part through `read_part`/`sp.run`; it does not send those prompt segments through verifier windows.

`--prefill-experts 16` controls grouped prompt expert work, not verifier window size. With no MTP, suffix draft off, and no lookup chain, the first verifier window is forced to T=1 and subsequent decode iterations also use T=1; greedy and those flags do not cause a 16-row decode. Thus “first 16 decode tokens” means sixteen serial one-token verifier windows. The native serve path still requires `--spec >= 2` for its verifier capacity, but actual T remains one here. Under default `STRATA_ONE_TOKEN_COMMIT` behavior, each T=1 forward graph self-commits its fed input; the subsequent `ver.commit(1)` does not launch the commit graph and only advances the PLE history if active. The first such fed input is the last prompt token, and `outv[0]` is the first generated token.

## Transition ordering and ownership

- `Prefill::run` uses `m.cs = main_cs`; it finishes with `stream_sync(m.cs)` before returning. It also obtains the final PLE gather future before uploading rows, records `ple_copied` on `m.cs`, waits on the alternate prior upload before reusing that host buffer, updates `ss.ple_prev`, and does not hand an unfinished chunk to decode. No MTP callback is installed in the selected configuration.
- The prefill streamed-expert copy stream `m.copy` is private and distinct from both `main_cs` and the verifier's streams. A 8,192-token chunk satisfies `T >= STREAM_ALL_MIN` (2,048). `ring_slots(T)` clamps the ring to at least 16, greater than `STAGE=8`; with a non-null expert source, `stream_all` is therefore selected. Default `STRATA_PREFILL_ISSUER` enables its host issuer thread. The verifier's captured decode graphs and resident expert-cache addresses are separate allocations; prefill owns its stage ring and chunk scratch, and the source/cache/WeightTable outlive the request. Prefill does not free or repurpose those allocations at `prompt done`.
- Cross-queue device ordering within prefill uses `copy`-queue `copied` and compute-queue `used` events. A selected expert's compute consumer waits on its copy completion before reading the staging slot; the copy issuer attaches a dependency on the slot's last `used` event before refill. PLE host-row reuse similarly waits on the previous `ple_copied` upload. At the end of `sp.run`, `m.cs` is synchronized but `m.copy` is not globally drained. Some final lookahead/unselected expert copies may remain queued. Their destination is still-live prefill-only `stage_dev`; their Stager buffers, events, and source owners remain alive, and later prefill reuses the same in-order copy queue. The decode verifier does not read those staging buffers or cache slots, so the absence of a prefill-copy drain at this boundary is not by itself a transition UAF or missing decode-weight dependency. It does mean the prompt phase is not a complete transfer-queue quiescence point.
- `Verifier::run(T=1)` has its own queue. With segmented mode, each segment is submitted, `cs_` is synchronized before the CPU reads the GPU sequence/control words, CPU plan writes are published with the existing fences/store path, and its copy stream is synchronized/flag B checked before the next graph segment launches. At final window completion, compute and expert-copy work are waited before the next operation. The prior prompt compute queue had already completed on the host before this verifier call, so the shared `SessionState` changes have a host-ordered phase boundary; no additional event between `Prefill::main_cs` and `Verifier::cs_` is necessary for completed prompt work. `STRATA_VERIFY_SEGMENTED` affects verifier handoffs only; it does not alter the prefill issuer or ring protocol.
- The `Weights`, output head, cache, verifier graph, session arrays, and Prefill allocations are long-lived owners. Since the source keeps `sp` alive through decode and does not rebuild/free the verifier graph at the boundary, no captured decode graph points into recycled Prefill scratch. Shutdown/reset is a separate lifetime point. `Prefill::release()` destroys the Stager before its explicit compute/copy stream sync and ignores both sync return values; pageable Stager fallback vectors therefore still rely on the older conditional teardown concern in R326. That is not a prompt-to-first-token free in the selected serve flow, because `sp` is not released there.

## Applicable unresolved host-publication race

A source-level conditional race already identified in R311 remains reachable in this exact shape; `--no-prefill-borrow`, segmented verification, MTP absence, and G=16 do not disable it. The 8K chunk selects `stream_all`; the issuer is on by default. It reads `m.stage_live[sl]` and `m.used_of[sl]` to choose the `used` event while `a_issued`/`a_consumed` limit its ring window. The selected-entry consumer path calls `wait_issued(k)` before reading/using the copy; however the `release_to()` skipped-entry path records `m.used[k % ring]`, writes `m.used_of[...]`, then release-stores `a_consumed` without first waiting for the issuer to finish that entry. An issuer that already acquired the earlier ring-window value can overlap the plain `used_of` access and the `Event.ev` read/write. The later `a_consumed` release cannot order an access that already passed the acquire gate. It can occur when the streamed sequence has an unresident expert that the chunk's routed `order` skips; the source does not establish whether or where a specific model/request has such a skip. This report does not claim the race occurred in any run. R311 is prior source evidence; R216's useful delta is that the requested 8192/no-borrow profile satisfies the exact `stream_all` and default threaded-issuer selector, so those earlier controls do not remove the conditional concern.

The verifier's published flag path is different: segmented `stream_sync(cs_)` brackets host reads of device-updated sequence state; CPU plan publication follows the host writes/fences, and the next graph segment is not launched until the verifier's transfer queue completes and the expected flag is visible. No new ordering gap was found there for this serial T=1 route. As in R199/R315, several Prefill calls that submit copies, record/wait events, or sync the copy queue ignore Boolean failure results; this is a failure-handling/qualification gap, not evidence of a missing successful-path edge or a fault in the target machine.
