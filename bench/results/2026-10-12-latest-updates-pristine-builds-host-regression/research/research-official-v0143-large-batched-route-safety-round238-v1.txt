R238 — pristine official v0.1.43 large-batched prefill route audit

Scope and disposition

Read-only source audit of the supplied pristine official v0.1.43 tree at revision `7695859aa13afb248bdb4d36f9b2e95707db079d`, centered on the 32,768-token generation case changing from the safe 8-row `read_windows` path to `--short-read 0 --prefill 8192`. Consulted registry v155 and prior R217/R219/R228/R230/R232/R237 reports. Did not open the prohibited `B/prefill-gemm-only-contract-root-v1/record.json`, read model/profile payloads, run/import/AST source, build, test, invoke Git, inspect processes, query or use the GPU/runtime, profile, clean artifacts, or alter source. This report is source-only; it does not qualify fit, synchronization, correctness, or speed.

**Decision:** the parameter choice is valid for selecting batched prefill, but the multi-chunk route is not admitted on a device without supported concurrent host-USM atomics. At 32K it is four chunks, and the second and later chunks reach the PLE completion-marker poll. Routed nonresident unpinned experts can also reach the Stager `done_seq` volatile poll. These source paths remain even with the commonly suggested stream-all, issuer, PLE arithmetic, first-chunk, copy-engine, or queue settings. Do not replace the `read_windows` baseline with this route for the current run. A successful allocation or a “hung prompt fixed” workaround is not evidence that the marker access is supported.

Route and chunk count

`generate.cpp` parses `--short-read` as an independent integer and accepts `--prefill N` as the explicit native prompt chunk. In service routing, `can_read_windows` rejects when `b-a > req_short_read` (`generate.cpp:9838-9844`), so `--short-read 0` does not route a nonempty long prompt through verifier windows; the batched prompt setup at `:11620-11699` then processes the conditioning positions. It sets `n_batched` to `n_prompt-1` (unless explicitly cut by `--prefill-until`), calls `Prefill::init(..., o.prefill_chunk, ...)`, then `prefill.run(..., n_batched, ...)`. Thus for a 32,768-token prompt and `--prefill 8192`, the work is 32,767 positions, in four chunks: 8192 + 8192 + 8192 + 8191. It is not one 32K allocation or one chunk. The normal verifier width 8 has 4,096 windows for the 32,767 conditioning positions (with a final partial window); those are a different route and allocation regime.

For this 128-cache context, source defaults do not make an 8192 chunk a stream-all route: `g_nonres_share` is set from nonresident coverage; stream-all defaults on only below 10% nonresident (`prefill.cpp:219-227`), whereas a small 128-slot cache is far below that. `ring_slots(T)` consequently returns `STAGE` (8) unless stream-all is explicitly forced; `m.ring` is the ring for the chunk and `stream_all` requires `m.ring > STAGE` (`:189-227, 2464`). Forcing stream-all changes the route and allocates a much larger staging ring, but does not remove the poll discussed below. Do not assume the nominal `--prefill 8192` implies a 384-slot ring.

New allocation scale and order

`Prefill::bytes_needed_impl` mirrors the `init` carving order (`prefill.cpp:1851-1917`); `bytes_needed_owned` rounds each separately owned allocation to 2 MiB pages and treats the expert ring as one allocation (`:1856-1860`). It is a source sizing function, not a device allocation receipt. The allocation list below separates exact fixed and directly computable terms from geometry-, cache-, driver-, and environment-dependent terms. The exact full peak cannot be recovered from the prompt length alone: QSA state/capacity, native expert `MAXBLOB`, MMQ plan and format, `--no-prefill-borrow`, memory pinning, and existing model/KV/cache allocations affect it.

The front of the device carve has a fixed 64 MiB GEMM scratch (`GEMM_SCRATCH=32 Mi elements of uint16`, hence 67,108,864 bytes) followed by 32 MiB GEMM workspace (`GEMM_WS=33,554,432 bytes`). Next come the chunk-linear activations: FP32 embedding/residual/hyper-connection/intermediate arrays, FP16/BF16 projection/output arrays, recurrent/attention working arrays, and a shared region sized as `max(GDN(T), QSA(T, state), MoE(T, native-format))`. The main dimensions in this source are `N=2560`, `D=10240`, `HC=4`, `LR=320`, `K=10`, `C=10240`, `ZV=6144`, `HV=48` (`:99-100`). `bytes_needed_impl` counts these terms in sequence (`:1872-1900`); BF16x2 low-part arrays depend on `bf16x2`/device mode. The QSA selection scores and attention scratch include state/context terms and cannot be assigned a fixed number here without the exact session state.

Next come two fixed dequantization slots: each reserves `uint16[1280*2560]` and `uint16[2560*640]`, total 37,683,200 bytes (35.94 MiB). If MMQ is enabled for the formats, it adds T*K identity rows, group-bound tables and max-format group buffers. The device expert staging ring follows: for routed-only mode it is at least 8 * `MAXBLOB`; for forced stream-all on the native pack the source ring default is 384 * `MAXBLOB` (capped at 512), unless overridden. The final chunk-linear device buffers include PLE embedding `float[T*N]`, the norm constant, and the KV stage pages (`take_stage`). Source line `:1906-1915` counts these.

Chunk-specific exact examples at T=8192: each FP32 `T*N` array is 83,886,080 bytes (80 MiB), and two pinned PLE embedding host buffers of that extent total 160 MiB (`:1060-1083`). Each `T*D` FP32 allocation is 320 MiB; `T*HC` is 128 KiB; a `T*D` uint16 projection image is 160 MiB; `T*LR` float is 10 MiB and its uint16 image 5 MiB. Each `T*N` uint16 image is 40 MiB. These are individual terms, not a sum: several are conditionally carved, and `xn` is only allocated under the GR-unfused option. At T=8 the same per-token terms are exactly 1/1024 as large. The 8192 case also allocates sizeable host-side arrays: PLE row vectors of `T*PLE_N_HEADS` per buffer, `steps_host`, ids/slot/src/counter/offset vectors, plus the Stager's pinned host blob ring (default 16 * `MAXBLOB`, independently of the device staging ring). These are not all represented by the single device `bytes_needed` total.

For owned pages, a change from T=8 to T=8192 increases a linear FP32 `T*N` term by 83,804,160 bytes (79.992 MiB), a `T*D` FP32 term by 335,216,640 bytes (319.6875 MiB), and a `T*N` uint16 term by 41,902,080 bytes (39.996 MiB), before 2 MiB rounding per allocation. The separate PLE host buffers rise by 159.84375 MiB. If routed ring stays at 8 slots, its GPU blob-ring extent is unchanged by T; forcing stream-all raises it from 8 to 384 slots, an extra `376*MAXBLOB` bytes. R228's selected native layout reports maximum blob 2,662,400 B; only if that exact layout/source is the one in this run, those ring values would be 21,299,200 B (20.31 MiB) versus 1,022,361,600 B (975.12 MiB). Confirm actual loaded layout and ring in the owned receipt rather than transferring that layout number blindly.

`--no-prefill-borrow` avoids carving the region out of expert-cache slots but reserves owned device buffers; it does not avoid the preceding model/cache/KV allocations or guarantee device fit. Without that switch the source can borrow cache tail slots if the planner admits them (`generate.cpp:11634-11674`); the T=8192 `bytes_needed` / `plan_lend` decision and actual borrowed bytes then need to be recorded. R228's 128-cache sizing arithmetic and headroom is a separate source-derived candidate and does not establish the much larger owned-buffer fit. With the 128 cache fixed as requested, do not mix in R236/R232 cache-512 or max-allocation changes.

Host/device lifetime and synchronization blocker

The GPU side allocates two pinned PLE row buffers and host-side row vectors for double buffering (`prefill.cpp:1060-1083`). At the end of each chunk, `ple_land` queues the upload and a sequence-marker fill into mapped host USM; if another chunk follows, it waits in a host loop on the *other* marker (`:2327-2362`). With four chunks this cross-buffer poll is reachable after chunk two and three. `STRATA_PLE_BATCH=0` toggles the PLE arithmetic block (`:2179-2189`), but does not disable this upload/double-buffer lifetime or marker poll. Likewise `STRATA_PREFILL_FIRST=0` only disables the short first chunk (`:2190-2203`); it does not turn four chunks into one.

The MoE route groups token/expert IDs on the host after a queue wait, then writes/copies grouping tables and enqueues kernels (`:3318-3445`); that handoff itself is ordered. However, nonresident unpinned expert staging uses the Stager's host-pinned `done_seq` written by copy/fill commands; Stager threads poll it via `*(volatile const uint64_t*)` in `buffer_free` (`:364-365, 506-523`). Routed-only batching still has staged misses and can reach `issued_one`/poll sites (`:2580-2603, 2654-2671`). R219 documents why disabling stream-all/issuer does not remove the routed-only staged-miss path. The SYCL spec aspect absent on this discrete device precludes concurrent host/device access of shared USM; no general guarantee makes these volatile host marker polls valid. The source has not replaced them with queue/event completion.

Existing workaround behavior

- `STRATA_COPY_ENGINE=0` makes the custom Level Zero copy queue factory return null; `Prefill::init` then creates an ordinary separate queue (`copy_queue.cpp:74-77`, `prefill.cpp:988-993`). It does not remove Stager marker polling, nor does it necessarily put copies on the compute queue. Do not describe it as a safety fix.
- `SYCL_UR_USE_LEVEL_ZERO_V2=0` selects the legacy adapter and makes the custom copy engine factory decline its queue (`copy_queue.cpp:96-99`). Official `docs/INTEL.md:582-585` records historical v1, 256-buffer, and per-phase-sync success for the former queue-event deadlock. This predates/references that event-wait failure, while current v0.1.43 source deliberately polls host-USM sequence markers. A historical workaround for one deadlock does not qualify the current poll under the target aspect; it also changes the runtime globally.
- `STRATA_PREFILL_SYNC=1` waits at timing marks (`prefill.cpp:1988-1990`), and may diagnose a stalled phase; it is a debug mode and does not replace the two explicit volatile marker loops. It can change timing.
- `STRATA_PREFILL_ISSUER=0` removes the stream-all host issuer thread (`:2621-2628`), not Stager or the PLE queue marker.
- `STRATA_PREFILL_STREAM_ALL=0`, `STRATA_PREFILL_RING`, and `STRATA_STAGER_RING` affect expert selection/ring depth; they do not eliminate all marker reads. Increasing ring depth only delays reuse; it is not a proof that a workload never wraps.
- The official v0.1.43 tree has no `DirectSubmission=0`, `direct-submission`, `copy-offload-disable`, or `nativeV2` option/identifier in the inspected source/docs. The source's explicit adapter selector is `SYCL_UR_USE_LEVEL_ZERO_V2`; its copy-engine queue deliberately uses an immediate command list for the copy-only queue (`sycl/include/strata/copy_queue.hpp:8-14`). Do not claim a generic external variable suppresses the source-level markers without verifying runtime documentation and the actual inherited environment.

Minimal prelaunch gates

1. Keep the owned 32K `read_windows` baseline intact and close it normally before any same-GPU allocation probe. No parallel model/GPU/process activity.
2. If a later experiment considers this candidate, first obtain a source/runtime owner-reviewed admission that addresses **both** PLE `ple_done_seq` and Stager `done_seq` host polling with a supported synchronization design, or proves by bounded source/route receipt that neither poll is reachable for the exact entire prompt. The current 128 cache and general 32K routed set do not prove the latter.
3. Before a run, pin exact source/binary/model/profile/runtime/device identities and cache-128 settings; capture actual `MAXBLOB`, `T`, effective chunk count, ring/stager sizes, owned versus borrowed bytes, existing cache/KV/context memory and all linear allocation inputs. Obtain measured device free memory/max allocation from the approved existing receipt; formulas and product VRAM labels are insufficient. Preserve sameboot/fault/reserve gates and use one serialized fresh process.
4. Do not interpret successful init as run qualification. Require the exact route/correctness/quality checks, all four chunk commits, no sync errors/faults, first decode transition, complete normal closure, and separate prompt/decode measurements. A timeout/hang is a retained failed sample; no retry/reset or flag-only recast.

Evidence limits

This audit derives the route, lifetimes, and allocations from source. It supplies no actual free-memory, allocation, timing, route, output, quality, driver-fault, or 32K run result. The source comments' historical throughput and the R219 conditional one-chunk candidate are not transferable results for this four-chunk route. If a separate one-chunk long prompt is evaluated, it must explicitly use a chunk covering all conditioning tokens and satisfy R219's full resident/source-pinned predicate; it is a different candidate and still needs actual route evidence.
