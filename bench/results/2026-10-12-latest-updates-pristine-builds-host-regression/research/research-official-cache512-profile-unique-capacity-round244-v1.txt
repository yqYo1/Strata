## Finding

The supplied official profile is not a repeated-pair profile. It is a 196,632-byte little-endian `STRP` v1 file with header `(version=1, layers=48, experts/layer=512, slots=24576, ranked_pairs=24576)`. Its ranked-pair segment contains 24,576 in-range pairs and 24,576 distinct `(layer,expert)` identities: exactly one ranking entry for every possible expert. This direct examination supersedes the generic duplicate-profile concern in earlier R224/R236 source-only reviews for this particular input file; it does not make the official reader validate uniqueness on other profiles.

The packet's campaign keeps `--expert-cache-per-layer` and changes only the cache request from 128 to 512. Official v0.1.43 translates that value into a byte budget of `requested_slots × largest_expert_blob`, then computes a per-layer quota `q = floor(min(byte_budget, free_VRAM_after_reserve) / sum_48(rounded_layer_blob_bytes))`; it opens `q` blobs for each layer (up to 512 experts/layer) and sets actual slot count to `48×q` (`generate.cpp:4942-4965`). Thus a 512-slot-equivalent byte budget can yield 624 effective slots if actual free room allows `q=13`; 624 is the maximum in that case, not guaranteed by the argument. The packet correctly requires actual startup `INFO expert_slots` and explicitly says not to predict 624. Under a reduced free-memory cap, q and the effective set can be lower.

The profile has 13 unique ranked experts in each layer, so all 624 entries in the per-layer top-13 set are distinct. The first three are simply the first three IDs of each row below, a 144-pair subset. Official fill scans the whole profile ranking, calls `admit`, and in per-layer mode skips an expert once that layer's assigned range is full; it fills the first `q` ranked experts for every layer, not the first `48q` global entries (`generate.cpp:5134-5190`). If actual `q=13`, the effective set is exactly the first 13 IDs listed per layer. If `q=3`, it is the first three. These are different from simply taking the first 512 pairs in the file.

The profile already supplies the identity needed to describe the candidate sets, while runtime output must confirm which candidate size was actually admitted. The official fill calls `ExpertCache::admit` and copies each accepted pair's blob into its slot; it verifies the profile's first pair by one blocking readback. In this profile the first pair belongs to layer 28, so with per-layer admission its assigned slot is layer 28's first slot (for q=13, slot 364), not slot 0. The current diagnostic text `pre-filled N of N slots ... slot 0 verified` is therefore misleading: the call verifies `slot_of(profile[0])`, not necessarily physical slot 0. It proves the count filled and that the first-ranked pair's assigned blob round-tripped, not that every blob was individually read back. Optional `STRATA_VERIFY_COMPLEMENT` computes a checksum over every resident slot's bytes, but that checksum does not include layer/expert IDs (`generate.cpp:5191-5239`). The per-layer quota log reports the first layer's range size; `INFO expert_slots` is the authoritative aggregate actual slot count. Do not describe a count of slots as independent per-pair readback.

## What the upcoming run can prove, and bottleneck counters

For startup, preserve the actual stderr lines with `R4.2g PER-LAYER: each layer owns q slots`, `profile ... ranked pairs, built for 24576 slots`, `pre-filled N of N slots from the profile ... slot 0 verified`, plus stdout `INFO ... expert_slots=N ... expert_slots_primary=N ... vram_free_mib=...`. The quota line plus INFO establish actual quota and aggregate slots; the fill line establishes successful fill count and that the first-ranked pair's assigned slot round-tripped (despite the misleading “slot 0” wording). The current controller binds/records the INFO line but its protocol does not inspect the other stderr fill lines. If the upcoming report wants a direct runtime effective-count claim, archive these few lines in the actual run receipt. If all-slot byte verification is enabled with `STRATA_VERIFY_COMPLEMENT`, preserve its `expert cache checksum ... (N slots)` line too, while noting it hashes slot+blob size+contents, not pair identities.

For the official model request, the packet sends one fresh `GEN 16` with no reuse and requires `RESUME 0`, `REUSED 0`, exactly one `DONE`, 32 token/LP5 outputs, and the full 32,767-token prompt. Official v0.1.43 uses serial `read_windows`, with one `PP 32767 32768 ...` boundary in this controller; retain `PP`, `DONE`, and source trace `strata trace: read 32767 tokens (windows) in ... ms`. `PP` gives elapsed prompt window and tok/s. `DONE` retains prompt/decode engine wall timings, cache hits/lookups, RAM/file blob reads and logical file MB, actual prompt tokens read, and offloaded routed entries. The controller also stores measured `prefill_to_REUSED`, `decode_REUSED_to_DONE`, TTFT, and whole-GEN host-wall boundaries. These are the shortest existing records for actual route cost and hit/miss outcome.

Use them as separate evidence, not interchangeable counters. `DONE` file MB and expert blob counts are source-level logical reads; OS read bytes / major faults from the `file tier I/O this request` diagnostic are physical storage activity. `experts streamed` and `experts ... by DMA` are expert event counts, not DMA bytes or bus bandwidth. Prefill host phase timings, PP wall interval, and GEN wall time overlap or include different work; do not sum phase timings and label the result critical path. Existing breakdowns useful if present include one-shot prefill `experts streamed / by DMA / host ms / resident / CPU`, and `--stats` decode lines for CPU expert-pool time, pool wait/drain/re-park, R4 hits/lookups/admitted/refused, `DONE` offload counts and file-tier counters; the served route's protocol receipt is primary for the packet as written.

## Comparison and limits

Official v0.1.43 `read_expert_profile` reads the STRP header and ranked list, validates version, geometry, list length and pair range, but does not detect duplicate pairs (`src/core/expert_cache.cpp:72-139`). `ExpertCache::admit` returns an existing slot for a duplicate identity (`:638-655`); the official fill loop then fills that same slot again and increments `prefilled`, so a malicious/repeated profile could make a slot count exceed unique resident pairs. This file itself has no duplicates, so that failure mode does not reduce its candidate uniqueness.

The integrated WN source `sync-xe-v0143-nonfinite-20261012` has added a `seen[layer×expert]` check to `read_expert_profile` and rejects a repeated pair before returning the ranking. Its behavior is stricter for arbitrary profile inputs; for this exact profile, both sources accept it and see the same 24,576 unique pairs. This is a source comparison only; no code was changed.

The packet remains `SourceOnlyUnverified`, with pending property/startup/model receipts. The source files and profile analysis do not establish actual q, successful cache allocation, fill count, readback, request route, or measured speed. Latest report registry v156 includes earlier capacity and controller-source records but no completed result for this new cache-512 actual run. No claim is made that 624 slots will be admitted or that cache512 improves performance against a matched 128 run.
