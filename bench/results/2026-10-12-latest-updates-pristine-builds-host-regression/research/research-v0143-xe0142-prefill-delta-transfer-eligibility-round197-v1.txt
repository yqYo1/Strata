R197 — upstream prefill delta and transfer eligibility
Date: 2026-10-12
Scope: compare only new source changes in upstream SYCL `61b3fb5..7695859` and XeStrata `e32b8b..da3d426`, against current safe W337/WN prefill production call sites. Primary-source review only. No compile, AST, import, test, build, runtime, GPU, process query, Git mutation, cleanup, or scratch file was used. No implementation or performance result is claimed.

Decision
--------
One newly eligible source candidate is the upstream fused IQ expert dequantization call for the **non-batched native-expert prompt path**. It replaces the adjacent gate/up and down dequantizer submissions with one ordinary 32-lane SYCL kernel submission for the same FP16 outputs. The current W337 source has matching production call sites and can take an equivalent implementation without changing the batched-prefill scheduler, expert placement, grouped XMX kernel, queue handoff, or oneMath backend. It is a candidate for a bounded A/B patch, not a parameter-only speed change already available in W337.

The source states that the fused kernel writes the same two FP16 arrays byte-for-byte and saves one launch per expert; its comments estimate about 24,500 launch boundaries per 4K prompt. That estimate is the upstream author's stated result, not an independently checked value and not a B570 measurement. Do not claim a B570 speedup until a matched run shows one. Keep the candidate out of the `native_batch` path: that branch already uses its separate batched dequantization path and does not invoke the adjacent single-expert calls.

Delta screen
------------
The only new upstream files directly establishing this candidate are `sycl/include/strata/kernels/iq_dequant_expert.hpp` and the kernel addition in `sycl/src/kernels/cuda/iq_kernels.dp.cpp`; the call switch is in `sycl/src/prefill/prefill.cpp`. Although the implementation filename is under `cuda/`, the separate `sycl/` CMake project compiles the `.dp.cpp` SYCL migration. This candidate is a normal SYCL kernel path, not a CUDA/HIP launch or a grouped XMX specialization.

The Xe `e32b8b..da3d426` delta changes `src/prefill/prefill.cpp` (among other things, `bo`/`emb` allocation accounting, CPU-share gating and stager/PLE helper behavior) and adds a device-architecture tag in `src/prefill/kernels.cpp`. It does not add a combined IQ expert dequantizer. Xe's current `src/prefill/prefill.cpp` retains separate native `iq_dequant_gu_f16(...)` and `iq_dequant_f16(...)` calls. W337 has the same pair at three production call sites in `src/prefill/prefill.cpp`; two non-batched paths reach it for the safe long-prefill recipe when `--native-batch 0` is held. Thus the fused algorithm transfers conceptually to both safe W337/WN and Xe source, but only the upstream delta provides an implementation to adapt.

Other changes were screened and set aside for this request:

- Upstream `STRATA_COPY_ENGINE` moves expert DMA and its completion notification to a Level Zero copy-only queue, but `Stager::buffer_free()` still polls `done_seq` through a volatile host pointer. It is outside the requested safe handoff subset and is not the proposed transfer.
- Upstream `STRATA_KV_WIDE_HOST` changes host KV writes in the DPC++ kernel. It is not the new Xe delta's implementation, and promoting a new device-written-host-storage path is not needed to test the dequant launch reduction.
- Xe's new `STRATA_PREFILL_CPU_GATE` adaptively disables CPU sharing based on wall-time comparisons. The source's own comment reports a throughput decrease with the gate on (B70 844→833 tok/s and RTX 4070 296→283 tok/s for the cited 1K IQ3_XXS runs), so it is not a supported speed candidate for B570. Its event policy and CPU-share choice are also a separate route change.
- Xe's `bo`/`emb` alias is an allocation/capacity aid already in the R180/R181 alias family; it is not repeated here as a new speed proposal. Xe's source comments say the planner continues counting that storage unless explicitly enabled.
- The new upstream `xmx_moe.dp.cpp` changes Xe2 subgroup/tile geometry. It is excluded: it changes grouped kernels and has separate image/dispatch/resource admission questions. No grouped XMX tile is proposed.
- Upstream's Battlemage `STRATA_SYCL_GEMM_STAGE` default reflects a measured oneMKL staging result in the upstream SYCL project. W337's and Xe's current `src/prefill/gemm.cpp` already submit oneMath products directly and do not contain that `staged_gemm` source path, so toggling it is not a transferable setting change.

Production path and mechanism
-----------------------------
In W337 `src/prefill/prefill.cpp`, the one-expert native path sets `gu16 = m.dq_gu + q * GU_ELEMS` and `d16 = m.dq_d + q * D_ELEMS`, then calls `iq_dequant_gu_f16(f.gu_type, blob_dev, blob_dev + f.up_off, f.n_ff, f.n_embd, gu16, m.cs)` followed by `iq_dequant_f16(f.d_type, blob_dev + f.down_off, f.n_embd * f.n_ff, d16, m.cs)` (current source around 2489–2495 and 2770–2776; another near 2277–2285 is the native-batch drain path). Both are enqueued on `m.cs`; the subsequent slot-use event and product submission remain after both. Xe da3d426 has an analogous per-expert pair around `src/prefill/prefill.cpp:2245–2249`.

The upstream fused API receives the two independent GGML IQ types and source pointers plus the shared expert shape, then writes gate/up rows in the exact interleaved order of `iq_dequant_gu_f16` and down rows in the exact flat order of `iq_dequant_f16`. Its kernel maps work-group IDs below `gu_wgs` to the gate/up routine, with parity selecting gate or up, and later work-group IDs to down; the work-group size is 32. It uses no explicit SLM/local-memory allocation and does not create an alternate grouped GEMM tile. Argument validation requires both types to be IQ, `n_embd % 256 == 0`, and `(n_ff*n_embd) % 256 == 0`; the target source's `native_expert_supported` predicate already requires the same shape/type family for this route. The upstream call site is guarded by its established native-format route.

Port shape for W337/WN should add a distinct `iq_dequant_expert_f16` function in the existing Xe `iq_kernels.cpp` / header API, implement both output regions inside one queue kernel using the already used type-dispatch helper, then replace only the two single-expert submissions in the non-batched branch. Keep both destination allocations, `slot` event ordering, all subsequent products, and the native-batch drain unchanged. A temporary opt-in switch such as `STRATA_PF_DQ_FUSED=1` would permit one-variable A/B; default off until parity is established. Do not set it in current W337 because that source has no such option.

Safety and resource boundary
----------------------------
This transfer does not touch Prefill's host completion protocol, the verifier's volatile doorbells, cache lending, pinned expert-copy notifications, PLE gather/upload, or queue ownership. It submits the dequant operation on the same `m.cs` stream that currently orders the two operations and the later GEMM/event. One submitted kernel remains ordered before the existing `m.used[slot]` record and before product use. It adds no staging pointer, allocation, cache slot, host thread, or inter-kernel host poll. It therefore fits the existing event/queue-safe W337/WN candidate's boundaries at the cited call sites.

The work-group count in the upstream kernel is the sum of the original gate/up and down launch domains; it guards integer multiplication/addition for `gu_wgs` and `d_wgs`, and dispatches only after IQ type/shape checks. The upstream helper's per-superblock decode work is unchanged; kernel launch geometry for all blocks becomes one contiguous ND-range. Do not copy that exact geometry into W337 without adapting it: W337/Xe's existing GU and flat kernels launch 256 work-items per work-group (eight 32-lane subgroups, each processing a distinct superblock), whereas upstream's corresponding migrated kernels use 32 work-items per work-group. A Xe port must preserve its helper's lane-to-superblock mapping and bounds, then validate resource and output behavior on B570. No source artifact proves that a B570 can compile every shipped IQ type combination or that combined launch duration does not hit a watchdog. Those need build and runtime validation by Main. This is a much smaller admission question than a new matrix tile, but it is not waived by source arithmetic.

Validation boundary for a future patch
---------------------------------------
1. First establish exact byte parity for each supported `(gu_type,d_type,n_ff,n_embd)` used by the shipped native packs: compare the complete old and fused `dq_gu` and `dq_d` arrays on identical input bytes, including tail/partial block handling and failures. The upstream source claims exact parity but the W337 target version must independently meet it.
2. Exercise the existing prefill call site with native pack, `--native-batch 0`, PLE active, the current safe B570 settings, and the same short-read/stepped handoff options as the control. Hold the full context, expert cache/profile, pool, chunk, prompt IDs and output settings fixed. Require call-site evidence that the paired path was taken, byte-exact dequant arrays where a diagnostic is available, exact full output/logit/state parity from the established oracle, no async/device faults, and preserved startup/context refusals.
3. Only after correctness passes, run interleaved fresh-process prefill samples with the switch off/on, same exact prompt and model hashes. Separate startup/module-load time from prompt prefill; report per-sample status, number of eligible expert dequant pairs, and end-to-end prefill time. Do not infer speed from launch-count arithmetic or apply this result to MTP batched dequantization / the native-batch path without separate evidence.

Documents checked
-----------------
The kernel uses the standard SYCL `nd_range` / `parallel_for` execution form (Intel's DPC++ compiler documentation describes `-fsycl` as enabling SYCL program compilation and documents using the C++ driver for SYCL sources). That supports treating this as a SYCL implementation route, but does not certify this exact code on the installed LLVM 7.1.1 or B570. oneMath's primary project description defines its role as the portable math API/backend layer for domains such as BLAS, LAPACK, RNG, DFT and sparse BLAS; packed IQ decode/dequantization is not a oneMath BLAS operation. No oneMath API/backend change is needed or implicated by this candidate. No CUDA/HIP path is used.
