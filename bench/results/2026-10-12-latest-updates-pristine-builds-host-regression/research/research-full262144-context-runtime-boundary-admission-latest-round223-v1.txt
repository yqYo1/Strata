## Determination

A zero-output request cannot prove the requested boundary through the current public request route: `max_new` must be at least one, and the serve parser rejects `n + max_new + 8 > max_context`. At context 262,144 this makes a direct one-token request with 262,144 prompt IDs fail admission. Setting the engine capacity to 262,208 (or relying on the extra 64 cells allocated for some workspaces) would test a different capacity and hide the boundary.

The source-supported controlled alternative is the batch admission protocol: start with `--batch 1 --max-context 262144 --kv int8 --kv-resident 32768 --prefill 8 --spec 8`, submit `BGEN 0 10 ...` with 262,135 prompt IDs, then let the admitted slot continue through its fixed ten generated rows. `BGEN` rewrites the initial prompt request as `GEN 1`, so the normal guard sees `262135 + 1 + 8 = 262144`; after the first token it retains the caller's `max_new=10` for slot continuation. The first request consumes the final prompt input at position 262,134; the ten slot windows then consume positions 262,135 through 262,143. The last produced token is an output; it does not imply a cell at position 262,144. The route must be confirmed from `BADM`/`BT`/`BDONE` and verifier position receipts. A shortfall due to EOS, error, cancellation, or early slot termination is not a full-context pass. The batch path checks EOS independent of the standalone `--stop-eos` switch, so use an explicit nonmatching `--eos-ids` sentinel (the CLI accepts a parsed integer list) or another verified way to prevent premature EOS for this controlled probe; record the actual argv and confirm all ten rows ran.

This route is a controlled response at the full context boundary, not a 262,144-ID input with zero output and not a teacher-forced correctness test. If the requirement is specifically to submit 262,144 prompt IDs, source changes to admission policy or a dedicated harness will be required; no current user request option accepts that exact direct-GEN pair with max_new >= 1. The older full-context R296 historical receipt used a different binary/source version and cannot be reused as current proof.

## Addressing and route constraints

For a fresh 262,135-ID prompt, the native generation split is `n_batched=n_prompt-1`: conditioning positions are 0..262,133; the final prompt token is processed by the first single-token verifier step at position 262,134. This avoids counting the generated output as an unconsumed prompt token. In the batch-admission route, the 10 subsequent verifier rows must be the contiguous positions 262,135..262,143. The required invariant is exactly 262,144 unique committed input positions `[0,262144)`, with no gap, duplicate, wrap, or row at 262,144.

The configured `--short-read 65536 --spec 8` controls window routing/capacity; it does not grant context capacity. At 262K, the served text may be divided at internal request/message/turn boundaries and by the ordinary Prefill chunk size. Record every actual `[start,end)` chunk/window and the final prompt-to-slot transition. Do not infer that one 65,536 window spans the full request, or that `--prefill 8` means a single eight-token full-context job. A useful route receipt is the ordered compact interval list plus actual final verifier row, PLE/KV commit status and request completion status.

The official serve path's prefill window choice is guarded by `windows_ok` and otherwise sends a segment to native Prefill. R215 establishes that the verifier path can drain the final commit before decode; R216 identifies a Xe prefill-stream issuer hazard for its own 8K/no-borrow shape. These do not prove an arbitrarily long prompt's route or transfer-owner safety. In particular, use the current board's atomic-host-USM finding and current exact source/build: a context boundary test does not cure an unsafe prefill handoff. The official and Xe routes have different source trees; qualify each separately. No claim is made that the selected high-throughput prefill settings are safe or fast on either engine.

## KV, storage, integer and slot bounds to assert

- Keep engine `max_context=262144`, INT8 KV, resident-cell target 32768, and KV-growth disabled/fixed. Verify at startup and after request that the primary and any secondary QSA/MTP states actually use the requested type, mode and cell limits; do not infer them from argv. No MTP is needed for this boundary probe.
- The session/KV primary pool must hold 262,144 cells while resident KV remains capped at 32,768; distinguish host spill, resident VRAM cells, page-table entries and any elastic/growable pool. The source initializes session state with `max_context`; the extra 64-cell workspace/table allocations are guard/scratch capacity only, not permission to address beyond `max_context`.
- Use 64-bit host arithmetic for `n`, `max_new`, `p`, `p+T`, row counts, byte sizes and interval endpoints. Check before addition/multiplication and before narrowing to kernel position types. 262,144 fits signed 32-bit, but byte offsets and cell×head×page strides still need checked `size_t`/`uint64_t` arithmetic. Assert `0 <= p`, `T > 0`, `p+T <= 262144`, every row maps to the expected page/cell, and the largest valid cell is 262143.
- For expert slots, validate per-layer slot range, per-slot byte capacity, aligned offset plus byte length within the arena, source pair identity, and residency remap after any borrow/refill. Keep the earlier R221 correction: slot 84 corresponds to layer 28 only under the cited 48-layer/144-slot layout; the `of 2662400` diagnostic denominator is global `blob_` maximum, not the failing expert's actual `nb`. The compact IQ3_S fixture's layer 28 is 21/20 at 2,329,600 bytes; do not label the prior synthetic mismatch an actual identity mismatch or use the global denominator as slot length.

## Compact evidence and pass/fail gates

Avoid full K/V tensors, raw sessions, or per-token full logits. Retain a compact, reproducible record containing: exact source and executable hashes; build receipt; GPU/driver/runtime and `usm_atomic_host_allocations`; model and pack hashes; full argv/env; exact prompt ID count/hash and EOS/sampling controls; context/KV mode and observed effective capacity; memory high-water by host, VRAM, pinned-host and any cgroup limit; prompt chunk/window interval list; final commit/position; slot IDs, per-layer slot extents and residency summary; first and last KV cell checksums per layer (include cell 262143), aggregate state/KV hash before/after; output IDs/count; `DONE`/`BADM`/`BT`/`BDONE` and error/fault status; and restore/reset status if restoration is part of the test. Keep one small failing diagnostic with the first divergent layer/cell and error if a fault occurs. Hashes are evidence of repeatability, not a substitute for a semantic or byte-level comparison when a mismatch is being localized.

Pass gates are: startup reports exactly the requested context/KV configuration; the request is admitted without raising context or growing KV; all expected input positions were committed exactly once through 262143; no premature EOS; cell 262143 has valid nonzero/expected state and K/V on every relevant layer; page/slot bounds and resident-cap limits hold; no sync/runtime faults; deterministic repeat produces the same compact hashes and output under fixed sampling; and peak memory remains within the declared host/VRAM limits. A mere `READY 262144`, a successful prompt parse, a nonzero output, or a 262144-sized allocation does not prove last-cell consumption.

Run one boundary-adjacent control (e.g. prompt 262134 with the same output budget) and the exact boundary protocol on each engine, each in fresh processes. Preserve every sample including admission failures. Only after all correctness and fault gates pass, repeat the exact-boundary arm for timing; report prefill throughput, first-token latency and decode separately. At least five independent cold-process samples per configuration are needed for a timing decision; keep timing secondary to address and state evidence. This investigation made no such runs.

## Evidence basis and limitations

The prior R296 report documents an older direct-GEN full-context lifecycle receipt and explains why its binary/source guard differs from later sources. R147's accounting says full-context capacity is plausible but unqualified and distinguishes 262,143 batched residual rows from the 262,144-cell KV pool. R215/R216 describe narrower transition/lifetime contracts, not this full-context acceptance. The v0.1.43 tree inspected here rejects a direct zero-output path and gates prompt length with an eight-token reserve. The BGEN protocol is the practical current-source route to write the final position while retaining a small controlled response. Actual context fit, complete layer writes, no-growth behavior, slot mapping, correctness and throughput remain runtime gates.
