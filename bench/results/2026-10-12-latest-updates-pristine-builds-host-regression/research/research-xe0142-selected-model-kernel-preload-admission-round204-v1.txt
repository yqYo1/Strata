## Selected-family inventory and admission implications

- **Dense native quantized projections / native expert decode:** Xe `NativeDense::eligible` admits projection names and a bounded GGML type set; native pack token embedding/head and native expert tables are separate. `native_mmvq` quantizes FP32 activations to Q8_1 and dispatches source-GGML quantized type IDs (including 18, 21, 22, 23; it is not a BF16/FP16 GEMM). For expert decode, `native_expert_grouped` is a q8_1 activation / float-output pipeline. On this pack, only the four gate/up and two down IDs listed above can be model-selected. The source contains type-specialized normal and optional fused G/U/down kernels; mode/local-memory conditions determine which specialized IDs launch. Types outside those six IDs are unselected for this pack's native-expert workload, but source selection alone is not enough to infer a failure is harmless if one of those IDs fails.
- **Native BF16 decode projections (requires `--native` preset or explicit flag):** `layer.cpp::project_bf16` chooses `bf16_gemv_fp32_mmvf` with FP32 activations and BF16 weights when `native_bf16` is enabled; otherwise its fallback is BF16-activation `bf16_gemv` or `bf16_gemv_split`. The native path is used by projections eligible in the native preset (SSM/router/indexer) and the `native_bf16_extra` flag enables PLE/shared-expert scalar projections. The multirow verifier has `bf16_gemv_fp32_mmvf_multi` (2–8 rows; 1 row delegates to single-row) and optional auxiliary form. These BF16/FP32 MMVF families are selected by the native flags and current row count, not by the all-ID preload result. Source lineage comment in `src/kernels/xe/bf16_gemv.cpp` explicitly identifies GGML-CUDA `mmvf` at llama.cpp 3cf03257.
- **Native dense FP16 input/weights and FP32 output (conditional):** `NativeDense` reads eligible quantized tensors in their GGUF quantized form via native MMVQ; it does not turn them into FP16 GEMMs. Separate packed `dense.bin` BF16/F16/F32 forms are used by canonical and projection paths. FP16 PLE convolution inputs/weights and QSA KV/attention storage are distinct kernels. Treat the exact native dense tensor type list as pack/GGUF metadata-derived; it cannot be inferred from expert type IDs.
- **32K+ batched BF16 dense prompt products:** the BF16 tensors remain BF16 in the pack. Xe `Gemm::bf16` first tries the configured oneMath backend, then the selected XMX matrix kernel when `xmx_gemm_ok`, else `gemm_rows` (DP4a/portable row kernels). If the GPU has only FP16 matrix engines, `bf16_through_f16` may convert BF16 X/W in bounded slices and use the FP16 product path; it is disabled with `STRATA_BF16_TC=0`, for accumulation/single-output cases, or if temporary allocation fails, after which the BF16 route continues. So a failed, unselected half/BF16 matrix specialization during preload is not proof this BF16 product path cannot run; conversely a failure of the actually selected oneMath/XMX/row path can surface at first use. Existing code does not consult the preload skip counter to choose a fallback.
- **Native expert prompt / FP16 fallback versus MMQ:** for batched prompt work, `prefill.cpp` chooses `mmq_plan().layer[l]` when the plan says this layer/type/device uses the integer path: it quantizes activations to Q8_1 and gathers native expert groups. Otherwise it gathers row activations in FP16. For resident experts, `fuse_res` further requires default-on `STRATA_PREFILL_FUSED`, no MMQ for the layer, native format/cache/residency, FP16 XMX, bounded per-expert rows, and supported grouped shapes; then `iq_gemm_grouped_f16` consumes the model's IQ blocks directly, dequantizes in its FP16 tiles, and executes grouped FP16 GEMM. Other experts go through the normal staged/dequantized prompt route. `iq_mmq_usable` checks device matrix shape, local-memory/workgroup limits, and (except AMD WMMA) accumulator-layout parity before opting into the int8 matrix path. These are source-level pre-dispatch capability gates, not a catch-and-retry after an actual selected kernel compile/launch failure.
- **QSA prompt attention:** `qsa_prompt_attn_batch` gates the FP16 matrix family on selected KV pools, device matrix engine/shape and local memory; the default FP16 K/V pool selects `PromptAttnMma<kF16,kF16>` (`<0,0>`). The `<1,1>` family corresponds to INT8 K/V, and `<1,2>` to INT8 K + Q4_0 V; they are not needed by the default FP16 KV route. If the FP16 matrix route is unavailable or its normal preconditions fail, caller retains the portable FP32 attention kernel; Q4_0-specific modes have their own gates. `STRATA_VERIFY_SEGMENTED=1` does not select a different `PromptAttnMma` specialization. If Main's actual runtime selects FP16 KV + the matrix path, `<0,0>` is a selected-path admission requirement, not an ignorable optional ID.
- **`mma_gemm::Kernel<2, half/bfloat16>` family:** source's `kShapes[2]` is the 16x16x16, 32-lane non-packed shape, i.e. the NVIDIA-style shape. Selection is by `shape(q, bf16)` scanning device-reported matrix combinations and fitting resource limits; it is not selected just because the ID appears in the global preload sweep. On an Intel device that selects shape 0 or 1, shape 2 is not used by this `mma_gemm` dispatch. Do not generalize that conclusion to an unspecified GPU without the actual device-reported selected shape. The XMX path separately carries `GemmKernel` specializations; a driver log naming `Kernel<2,...>` must be mapped to the exact compiled TU/kernel ID before being classified.

## Preload failure scope / source fallback boundary

`device.cpp::Runtime::preload_kernels()` still enumerates all registered `sycl::get_kernel_ids()` and independently requests executable bundles. A caught `std::exception` is only counted as skipped; the ID and diagnostic are discarded, and `wait_preload()` only joins. There is no selected-path manifest, per-kernel error state, compile-time admission map, or later automatic fallback keyed to a failed ID. Consequently, the main path can safely ignore a failed ID only after it is proven unselected by the exact executable/device/configuration and no first-use code path can issue it. Conversely, once a selected call is attempted, ordinary device/queue exception behavior applies; a preload skip must not be interpreted as evidence of a GPU reset, nor as proof that the selected specialization is available.

Practical allow-list criteria for Main's qualification: bind to the actual device's `mma`/XMX shape and BF16/FP16 capability; the actual `--native`/native dense toggles and model-pack metadata; selected KV format; selected expert MMQ/fused/dequant route and actual layer types; and whether long-prompt work reaches QSA prompt attention and the verifier under the supplied short-read/segmented options. For the B570 historical receipt, `Kernel<2,...>` is a candidate shape-2/non-selected family if the current device scan confirms shape 0/1; `PromptAttnMma<0,0>` remains relevant for default FP16 KV, while `<1,1>`/`<1,2>` are alternative-KV families. The source cannot validate the current device scan; Main's owned actual startup/request evidence must close that part. Do not convert an unselected-specialization omission into a GPU fault or into a clean selected-path qualification.
