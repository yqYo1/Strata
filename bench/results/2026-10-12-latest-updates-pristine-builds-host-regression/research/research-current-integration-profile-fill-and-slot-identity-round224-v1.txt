## Finding

The currently adopted integration has the v0.1.43 per-layer continue repair: a saturated layer is skipped while later ranked pairs are scanned until `prefilled == want`; global mode still breaks on the first refusal. Its actual loop is `src/program/generate.cpp:4466-4501`. The old R222 finding that this specific integration accepts duplicate profile pairs is stale: the currently selected `src/core/expert_cache.cpp` rejects duplicate `(layer, expert)` pairs in `read_expert_profile`. R222's pristine Xe/official conclusions on duplicate acceptance remain accurate. The duplicate rejection is material: it prevents repeated fill calls from reusing one claimed slot and incrementing the startup `prefilled` counter while another distinct pair/capacity slot remains unfilled.

## Profile admission and slot mapping

All three readers use the `STRP` version-1 profile header with model layer/expert geometry, declared slot/ranked counts, then bounded `(uint16 layer, uint16 expert)` pairs. They reject incompatible version/geometry, too many pairs, truncation and out-of-range IDs. They do not require end-of-file immediately after the declared list. Current integration additionally tracks a `seen[layer*n_expert+expert]` bitmap and rejects any duplicate before the cache fill can begin (`src/core/expert_cache.cpp`, `read_expert_profile`; error identifies pair index and pair). Pristine Xe and official v0.1.43 accept duplicates.

The cache maps each `(layer, expert)` to one `residency_` slot. `admit` returns the existing slot for an already-resident pair; a new per-layer pair receives `layer_next[layer]++` within that layer's contiguous range; a full layer returns `kNotResident`. Global mode assigns `next_free_` in order. Slot identity is therefore established by the residency table and allocation path, not by profile rank after admission. For per-layer mode, rank order decides which distinct experts enter each layer, while physical slot IDs are grouped by layer. The current integration and pristine Xe use the same `q=slots/n_layers` range rule with remainder in the last layer; no cross-layer or global alias was found in the inspected `admit`/`slot_of` mapping.

At startup the integration chooses `want=min(profile.size(), xcache.slots())`; with per-layer admission it scans the entire profile (`scan=profile.size()`) and continues on a layer-quota refusal, stopping after `want` successful fills. With global admission, `scan=want` and first refusal breaks. This agrees in substance with official v0.1.43's per-layer scan/continue repair and differs from pristine Xe v0.1.42, whose loop breaks on first `kNotResident` and can leave later layers' ranges empty. No implication about current profile distribution follows without reading the actual profile payload.

Duplicate handling changes counters and fill behavior. In pristine Xe/official, a repeated pair can return the same slot, cause another copy into it, increment successful-fill accounting, and consume one unit of `prefilled`; thus that loop may stop before filling `want` distinct experts. In per-layer mode the repeated pair does not advance layer capacity. This is bounded underfill, not an alias to a different pair, because the repeated copy names the same pair and slot. Current integration refuses the malformed/redundant ranking up front. Consequently, for the current integration's accepted profile, each successful `prefilled` count corresponds to a distinct admitted pair, assuming source reads and slot fills succeed.

## Implications for repeated 32K and full 262144 use

The profile scan/cache allocation occurs during startup, once for the process; it is not repeated per request. Per-layer fill policy does not itself vary with prompt length. No-eviction cache residency and the slot map persist across requests. A later request may use a previously unprofiled pair as a cache miss and potentially admit/fill it if that layer still has capacity; a repeated 32K request therefore does not replay the profile scan, but its routed expert set and cold-miss behavior need runtime evidence.

For full 262144 context, these source facts alone establish neither memory admission nor correctness. The profile reader permits a partial ranking; cache capacity is bounded by actual allocated slots, and `want` is capped to that capacity. A full-length prompt can create different QSA/session memory and routing demand, but does not change the profile loop's slot identity. Verify startup effective slot count, profile accepted length, per-layer residency map, fill success/readback, request route and all memory admission using the exact model and runtime before making a safety or performance claim. `verify_slot` readback of one selected fill is not proof that every filled slot's bytes were compared or that the full prompt is correct.
