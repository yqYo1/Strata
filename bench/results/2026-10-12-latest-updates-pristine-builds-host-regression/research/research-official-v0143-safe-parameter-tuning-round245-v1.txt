# R245 — safe cache-auto and CPU-worker candidates for official v0.1.43 window mode

Date: 2026-10-12 Asia/Tokyo. Read-only source and report analysis for pristine official v0.1.43, requested revision `7695859aa13afb248bdb4d36f9b2e95707db079d`. This is a candidate-eligibility note, not a setting selection or performance result. No project command, test, build, compiler/runtime/device/GPU/process query, profile/session read, Git operation, cleanup, or source edit was performed. The active Main campaign must finish and close under its owner/lock protocol before any additional B570 sample.

## Decision

Keep the serial `read_windows` path and the current admitted configuration as the control. Do not infer from a larger cache or worker count alone that 32K prompt conditioning or generation will improve. Source establishes plausible, distinct candidates:

1. A fresh-process `--expert-cache auto` candidate under the same expert-source mode and admission policy as the control. It is eligible only after recording actual free VRAM at sizing, selected/effective slot count, sized bytes, successful allocation and zero-touch, post-touch reserve, populated unique `(layer, expert)` pairs, and the unchanged `read_windows` route. Auto is data-dependent. It is not source-guaranteed to fit, to keep the default reserve, or to help this prompt.
2. A fresh-process `--pool-workers 3` candidate against the recorded effective five-worker control, with all other values fixed. Positive worker counts are literal; with the default `host_works=true`, the serving host also takes jobs, giving up to four rather than three total compute participants. This is eligible as a controlled screen, not an assumed optimum. Existing R230 already proposed 3 versus 5; this report does not reopen the broad worker/split matrix.

Do not combine cache and worker changes in the first comparison. They interact: a larger cache can change which routed experts miss to CPU, which changes the work available for the pool. Preserve the already-safe window route (R237/R238 boundaries) and defer any batched-prefill or large-chunk settings. R238's large batched route exclusion is unchanged.

The immediate practical constraint is experiment freshness: the present Main run is active, and a recent pristine controller packet identifies a cache-512/worker-5 configuration. If that is the current owned arm, do not repeat it as a new baseline. After its closure, use the actual closed Main record as control and run only a not-yet-sampled candidate. If cache auto was already sampled there, do not repeat it; choose the worker arm only if it is still untested and the owner’s quality/fault gates passed. This avoids spending another full 32K run on a duplicate condition.

## Why cache auto is a candidate, not a promise

In pristine `sycl/src/program/generate.cpp` (SHA-256 `8112c1808dc317e89d9635ad1b6e46b080fc16e67a0b2f63923d5231f355fa07`), auto sizing occurs after weights and session allocations. Around lines 4269–4312 it reads current free bytes, subtracts the configured VRAM reserve and owned prompt/pipeline buffers, accounts for bound draft-head bytes, and caps the resulting maximum-blob slot estimate by profile length. With native `--expert-cache-per-layer`, the later sizing branch around 4388–4418 uses current free-room and the summed 256-byte-rounded per-layer blob sizes to select a uniform quota, then creates one cache slot for each layer/quota position. Consequently the final slots and bytes cannot be known from the nominal card capacity or an earlier READY free-memory observation.

The allocation loop around lines 4499–4557 explains the safety benefit and limits of auto. It opens the cache, zero-touches the full range, waits for the queue, and re-reads free VRAM; when the reserve is short it closes and shrinks the cache. Auto may also try a smaller allocation after open failure (up to the source’s bounded retry policy). The code comment gives the reason: an untouched allocation can overstate actually resident capacity, especially on WDDM. A successful auto startup still needs the normal run’s readiness, reserve, route, numerical, fault, and closure checks. A retry/shrink is a real change in effective cache size and must be recorded; it must not be summarized as the requested auto value alone.

`sycl/src/core/expert_cache.cpp` (SHA-256 `48959dd9ae6c96b96f58c0f30878823accd1ecc1bdbcea0e6d908f267a13f6fa`) lines 708–730 show `open_sized` sums 256-byte-rounded per-slot extents and passes that sum through one contiguous allocation path. In `generate.cpp`, source sizing and residency filling are separate: requested slots do not prove populated unique experts, and populated entries do not prove a particular prompt’s hit rate. Auto can lower the amount of CPU miss work only when the additionally resident pair set overlaps this prompt’s routes. It does not remove the `read_windows` layer service/segment handoff or reduce computation for routes that remain CPU misses.

R228 provides prior source-derived comparison context for the same 48-layer native layout: manual per-layer 128 yields 144 logical slots and 281.03 MiB at full quota; 512 yields 624 slots and 1,217.80 MiB; the 1,024 challenger yields 1,296 and 2,529.27 MiB. These are source arithmetic, not this machine’s measured free memory, actual allocation, residency, hit rate or performance. R232 further requires the single-allocation property ceiling to be compared with an exact manual allocation request before attempting a manual large allocation. Auto does not make the property result, current free-space receipt, or normal allocation success interchangeable.

## Why a worker count change is separate

The pool is the project’s own pinned CPU `ExpertPool`, not a SYCL CPU device executor. `generate.cpp` lines 4245–4259 constructs it with `pin=true` and `host_works=!no_host_worker`, then prints effective worker count, assigned logical processors, host processor, and whether the host drains jobs. The option parser stores positive `--pool-workers N` literally (line 1748); constructor source in `src/kernels/cpu/pool.cpp` (SHA-256 `4b9b8ec1eeaabca0524a3a4aef39907ad90583e798d1e03a2ae1f6318e9105bc`) selects exactly N worker threads for positive N and pins them to detected worker processors. `ExpertPool::run` calls `drain` on the host when `host_works` is true (around line 695). The constructor’s actual effective count and topology receipt matter more than the option string.

On a six-physical-core Ryzen 5 5600X context supplied by prior project records, the existing five-worker form with host participation can engage up to six compute threads. Three workers plus host can engage up to four; this leaves cores available for the GPU host/driver and other work, but it can also reduce CPU expert throughput. No evidence here chooses between those outcomes on the current 32K serial route. The project header (`include/strata/kernels/cpu/pool.hpp`, SHA-256 `5f7e7ee3f48ce6505ad25975c320310e647551df3304a87052ce3c7e2b414936`, lines 99–105, 139–151) documents the physical-core pinning and host participation. It also contains historical measured bandwidth examples on a six-core machine; those characterize a separate memory benchmark/host-loop placement, not current Qwen routing, this prompt’s CPU miss mix, or a measured worker-3 comparison. Treat them only as motivation to test, not a throughput forecast.

Intel’s oneAPI guide describes thread-count and affinity controls for its OpenCL CPU-device execution path and warns that its CPU work-group thread count should not exceed hardware threads to avoid oversubscription ([Intel oneAPI CPU-core execution guide](https://www.intel.com/content/www/us/en/docs/oneapi/programming-guide/2024-2/control-binary-execution-on-multiple-cpu-cores.html), lines 288–305). That guidance is not a direct prescription for this application: this path uses its own `ExpertPool`, so use the application’s reported pinning/effective count and do not alter `DPCPP_CPU_NUM_CUS` or other runtime controls as a substitute. The documented concern supports measuring actual topology and contention; it does not prove that six project participants oversubscribe a six-core machine, particularly when the pool is the only active CPU workload.

## Minimal evidence plan after current campaign closure

For each candidate that has not already been sampled:

- Start a distinct fresh process, preserve the same pristine official binary/source/compiler/driver/runtime, model/pack/profile hashes, full prompt token sequence, seed/sampling, context/KV, source mode, reserve, route controls, `read_windows` eligibility, `--spec`, and all unrelated arguments/environment. Record full argv/environment and whether the process is warm/cold under the same policy.
- For cache auto, record the source's initial free/reserve calculation; prefill/pipeline/draft deductions; requested and effective slots; exact contiguous allocation bytes; whether any retry/shrink occurred; zero-touch completion; post-touch free/reserve; cache fill status; unique resident pair count; and actual CPU miss/hit counters for prompt and generation separately. Preserve the actual route/window size and fail the A/B comparison if it silently falls back to batched Prefill.
- For workers 3, record the startup-reported worker count, pinned logical processors, host core, host participation, actual CPU-miss jobs and pool drain/segment-wait times. Compare prompt and decode separately; the cache and route must be identical to the control.
- Retain the existing owner’s output/logits correctness, device/runtime error and fault checks, request progress, normal-close requirement, and individual timing samples. Any failure remains a failed sample; do not tune around it or substitute a later success. If the control’s setup/allocation differs, first establish matched records rather than attributing the result to the parameter.

A candidate is useful only if startup succeeds with recorded headroom and unchanged route, output/correctness and health gates pass, and the corresponding phase has enough measured CPU miss work to explain any observed change. One screening sample can admit/exclude; it cannot select a generally best setting. A selection claim needs repeated independent samples and a held-out prompt per the existing R203/R367 campaign contract. There is no source basis here to change the current production defaults.
