# R192 — Xe da3d Prefill policy eligibility on the B570 64K/T8192 source path

Date: 2026-10-12 (Asia/Tokyo). Read-only source and retained-record audit. No project execution, tests, build, compiler, AST/import, runtime/device/GPU/process query, model run, Git operation, or cleanup. This report distinguishes static eligibility from observed effects.

## Finding

The latest Xe da3d policies are not a common set of immediately effective optimizations for the present B570 64K/T8192 production path. The source-level embedding-plane alias (`bo = emb`) already saves one actual allocation in `carve()`; its accounting switch only changes the planner's reported bytes and has no runtime data-path effect. `cached_share()` selects the special file-staging profile only when expert blobs are transient file-backed reads, so it is inapplicable to experts served from the existing pre-pinned/native mirror. The opt-in CPU-share gate is a different policy: it can affect eligible nonresident expert layers when CPU sharing is available, but no retained B570 64K receipt proves its flag was set, its layer arms were taken, or a benefit. The auxiliary-CPU scheduling policy is host scheduling and needs route-specific measurement; no same-input B570 evidence establishes a gain.

Do not carry over any upstream RTX/B70 measurements as B570 results. The retained 64K/T8192 reports establish a candidate configuration and source arithmetic, but do not establish the exact model source tier, per-layer dispatch, page-cache fraction, CPU gate state, or performance of these policies in that production run. For source eligibility only, current W337 has a default CPU-share guard on devices without concurrent host handoff; R351 documents B570's host-USM concurrency limitation, which makes concurrent CPU/DMA sharing especially inappropriate on that source class.

## Path-by-path applicability

### Embedding output plane alias and accounting

In Xe da3d `src/prefill/prefill.cpp`, `carve()` allocates `m.emb` at line 783, then assigns `m.bo = m.emb` (line 790); the actual output-plane allocation is already absent. `bytes_needed()` around lines 1060-1064 still counts the legacy `bo` extent unless `STRATA_EMB_REUSE_ACCOUNT=1`. Thus the environment switch can lower the *planner estimate* by `T*N*sizeof(float)`; it does not alias another buffer, change compute, reduce the already-carved arena, or affect page cache. At T=8192 it is planner accounting only, not another 256 MiB of physical savings: the allocation is already shared. R181's lifetime analysis supports the alias for Runtime-created in-order streams under its guards, and notes that a caller-provided stream must be verified. The current B570 W337 source has separate `m.emb` and `m.ple_emb` allocations (lines 783 and 874); it does not contain the Xe `bo` reuse implementation. Therefore Xe's established `bo` alias is not evidence that W337 already aliases the distinct PLE embedding plane. An actual `emb`/PLE alias candidate is a separate code change and parity/lifecycle qualification, not a setting to apply to W337.

Verdict: no compute-speed or physical-memory benefit from flipping Xe's accounting variable on the Xe binary; a planning report benefit only. Do not infer that the separate W337 PLE-plane proposal has been adopted or qualified.

### `cached_share()` / RAM-vs-file stager profile

Xe's `Prefill::init` scans `src->transient(l,e)` to identify file-like sources. Only if at least one such blob exists and `STRATA_STAGER_THREADS` is unset does it consult `STRATA_STAGER_SSD` or `src->cached_share(256)` (around lines 694-713). A cached share of at least 90% turns off the SSD profile; otherwise file profile remains. That source distinction matters: page-cache probing is not a general optimization for every source that happens to have host data.

W337 exposes distinct source kinds. `ArenaExpertSource` in `expert_source.cpp` can serve model expert blobs from its contiguous registered/pinned arena; `FileExpertSource` handles GGUF/mapped file blobs and cache-complement paths. For a blob already reported `pinned()`, Xe Prefill calls `blob()` and uses the source's mapped host address directly (Xe `prefill.cpp` around 1339-1344); it does not first load the expert through the transient-file Stager. The prompt's pre-pinned mirror therefore bypasses `cached_share()`'s file-vs-RAM profile decision for those experts. A warm OS page cache can matter for a file-backed GGUF expert that still answers `transient()`, because transient classifies the source access method, not whether a particular page is resident. It cannot improve or change already resident mapped/pinned mirror reads through the file-stager heuristic.

Tier caveat: the retained R148/R150 material does not identify the actual current run's per-layer native-pack expert tiers or report all `transient/pinned/resident` flags, and the sanitized T8192 contract expressly leaves actual loaded type/residency to the run receipt. It is therefore not justified to label the whole B570 model “pinned/native” or “file/page-cache” from the prompt length or candidate command. Resolve per layer/expert from a closed receipt: source kind; transient, pinned, resident/VRAM status; bytes returned by blob/file source; copy/stager counts. A tiered model can have both behaviors in different cohorts. For all-pinned-mirror cohorts, cached-share and SSD profile are inert; for transient GGUF cohorts, cache sampling may apply, and requires new closed-run evidence of actual warm fraction, selected profile and timing.

Verdict: first classify actual source tier. Do not apply or interpret page-cache policy as if it governs the pre-pinned arena path.

### CPU-share gate and adaptive arms

Xe da3d's `STRATA_PREFILL_CPU_GATE=1` is opt-in and enters only where CPU sharing may be considered and `cpu_share_env()<0` (auto). It alternates early layer arms until it has ratios, then probes the opposite arm periodically, recording events/deciding whether the CPU share is worth using (around lines 1773-1805). Its source comments cite four interleaved 1K IQ3_XXS rounds on B70 (844→833 tok/s) and RTX 4070 (296→283 tok/s), both regressions; those are source-comment historical claims, not B570 64K measurements. Gate has no authority over explicitly forced CPU-share settings, and cannot help if source predicates make CPU sharing unavailable.

W337 defaults `cpu_share_on()` to `cpu_share_env()!=0 && gpu::host_handoff_concurrent()`. R351's retained B570 capability record says host USM has RW/ATOMIC but no CONCURRENT, and explains that concurrent CPU reads and GPU DMA reads from disjoint experts of the same host-USM layer allocation remain unsupported at allocation granularity. R351 recommends disabling CPU share for that host-USM source path. This is separate from the ordinary registered mapping path, whose contract must be identified before generalizing. Consequently the CPU gate is not a license to opt back into concurrent B570 host-USM sharing. It also isn't a setting that improves an all-native/pinned or all-resident route when there are no eligible CPU-share layers.

Verdict: eligible only after actual source allocation class and device gate are known; keep B570 host-USM concurrency restriction. No B570 64K/T8192 result establishes benefit. A valid experiment must hold source/tier, prompt, cache, chunk, and all other controls fixed, record gate enabled/effective arms/CPU rows/host allocation class, and compare closed A/B timing after numerical/lifecycle qualification.

### Auxiliary CPU scheduling

Xe's auxiliary CPU selection/pinning changes where host worker/stager threads run; it does not change GPU kernels or source tier. Its applicability follows the workers actually used: transient blobs use staging threads; unpinned blobs can be copied by the stager; native CPU-share workers require eligible CPU rows. A fully pre-pinned arena streamed directly to GPU can leave these copy-worker settings with little or no relevant work, while a page-fault-heavy file route may have substantial host staging. No retained record reviewed here compares auxiliary-CPU scheduling on the B570 exact 64K/T8192 workload, with the actual model route and timing attribution. Avoid moving affinity based on another GPU/CPU's source comments.

Verdict: host-side candidate only for a receipt-proven active worker route, not a GPU-kernel optimization. New controlled B570 run required; absent worker activity, it is inert.

Neither reports a B570 measurement of the four policies above. R148's 745 MiB OFF and 1,286 MiB ON figures are historical startup-free figures, not T8192 physical admission, and the compact-on 2.793 GiB is source-requested Prefill ownership only. Do not use those numbers as evidence that cached_share, CPU adaptation, or worker affinity helped.

Source supports a useful decision split, not a result: (1) existing pre-pinned/native mirror: page-cache profile is bypassed for those blobs; (2) file-backed transient blobs: cached-share policy can select staging profile; (3) host-USM with B570 missing CONCURRENT: CPU sharing must remain off under R351; (4) eligible separate registered-mapping or pageable routes: classify with their own backend contract and actual CPU-share eligibility; (5) auxiliary worker affinity matters only if those workers are active. A fresh closed receipt is needed to state which cohorts actually dominate the production T8192 path.

## Decision

Treat `STRATA_EMB_REUSE_ACCOUNT` as correcting an overestimate only in Xe's planner, not a production optimization. Treat `cached_share` as file/transient-only and inapplicable to already pre-pinned mirror reads. Treat CPU share as capability- and tier-gated, with no B570 64K evidence and a host-USM no-concurrency restriction. Treat auxiliary CPU placement as unqualified host scheduling. The retained evidence justifies no default change or speed/capacity claim. Next useful evidence is a compact source/tier/path receipt from the exact closed B570 64K/T8192 run (including mode/pin/fallback and thread/gate flags), followed by a matched experiment only for controls shown active.
