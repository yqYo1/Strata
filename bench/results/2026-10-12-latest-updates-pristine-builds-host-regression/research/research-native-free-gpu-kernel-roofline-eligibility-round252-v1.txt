# R252 — Native free-build GPU roofline eligibility and missing measurement

Date: 2026-10-12 (JST). Read-only synthesis of committed B570 reports and source-path contracts for source-built LLVM 7.1.1 free mode. No build, test, executable/script/import, GPU/process/device query, profile, Git, cleanup or source edit was performed. The supplied current property values `normalmax10132807680` and `host/sharedAtomicFalse` are treated only as given inputs; they do not establish XMX/joint-matrix support, a memory bandwidth, or permission to use a shared-host path.

## Finding

Do not repeat native IQ3_S grouped-dequant width/parity or the selected-layer generic IQ expansion capacity run. Those already have qualified B570 evidence. The one useful missing roofline quantity is **true device-command time for the free-build grouped FP16×FP16→FP32 expert GEMMs at the fixed MoE geometry and actual routed-row boundaries**, alongside host submit/completion wall. Existing `--kernel-bench` is synthetic timing for dense BF16 and an optional first-layer MMQ expert case; it neither times the native IQ dequant APIs nor proves the free-build grouped XMX/own-FP16 GEMM path. Historical B570 dense GEMM capacity numbers used oneMKL and do not establish free-mode own-kernel behavior. The old B70 XMX grouped benchmark is another card and workload.

This gap is narrower than “GPU roofline”: measure one exact grouped expert product cell with event timing and path receipts. Unless an exact supported external-memory counter is available and correctly attributed, report logical operand bytes per device interval only. Do not call that DDR/GDDR bandwidth or infer saturation from product specifications.

## What is already measured

1. **Native grouped IQ dequant component:** R159 and its v2 addendum record B570 free-mode results on LLVM 7.1.1 plus 17 patches. All seven active GU/Down type pairs were compared at 640×2560 for group widths n=1,8,16; six ABBA samples per arm/pair/width, four repetitions/sample, 252 timing samples and 105 complete-byte comparisons. Grouped and individual paths matched complete output bytes and guards. The component was marked performance-eligible, but its endpoint is host submission plus completion, not an isolated kernel event; it was not a model-speed result. At n=16, individual/group median ratios ranged 1.123–2.221. The N=64 and N=2049 receipts add production caller admission evidence and weighted average widths, not individual width histograms or quiet performance claims. Do not rerun this matrix.
2. **Actual-blob generic dequant:** R261 audits a separate completed 3-process selected-blob GPU run. It covers seven pairs, including IQ3_S GU, using 32 distinct actual pack blobs per pair/sample, device-resident input, one GU and one Down wrapper per blob, and one terminal wait. Pair wall medians span 75.876–207.700 μs/expert. It is O2 standalone wrapper, host submit-through-completion, no event-only kernel service, with no cold-cache proof and no production routing. This is already a valid generic expansion control, not a free LLVM 7.1.1 production-build ceiling and not an XMX GEMM result.
3. **Dense/grouped GEMM controls:** R365’s B570 synthetic large-M and small-M FP16-input/FP32-output GEMM rates are oneMKL. They are useful operation-specific references but not the free build’s own FP16 implementation. The older XeStrata B70 grouped-MoE report in R290 is not transferable to the B570/current runtime. `--kernel-bench` results cover synthetic dense BF16 (and optional MMQ expert work); they are not this native FP16-dequant plus grouped dense GEMM route.
4. **Production branch distinctions:** ordinary native prefill may dequantize IQ blobs to FP16 and call per-expert `Gemm::f16`; an alternate branch can use grouped products or fused/MQM dispatch depending on source/version and runtime gates. Merely seeing `native IQ3_S`, `Gemm::path()`, or a `--kernel-bench` line does not prove which native route was selected. The exact source build and its effective path must be recorded. Free mode disables oneMKL; where `Gemm::f16_groups` is used, the free build returns to the project’s own grouped kernel. XMX eligibility is a separate runtime question.

## Existing tool eligibility

- `strata --kernel-bench` is a finite, reproducible diagnostic command, but it does not answer the question above. Its dense BF16 arm is not FP16 expert GEMM; its optional MMQ arm is not native IQ dequant plus dense grouped products. The source review in R368 also found that this timing-only tool lacks an output reference gate and ignores the sync return in its timing helper. It can be retained as a smoke/capability timing only, after independent correctness and completion evidence.
- `dequant_bench` is a useful allocation/launch scaffold but its documented existing fixture uses random packed bytes, a mismatched Down shape, and incomplete output hashing/oracle coverage. It does not produce native grouped GEMM roofline data. R250 explicitly says it is insufficient as-is.
- `xmx_gemm_bench` is not a substitute for the real grouped route unless its exact build/runtime branch, input rows/bounds, output correctness, event completion and selected kernel are shown to match. Source existence alone does not make it a valid roofline command.
- Consequently, there is **no existing valid one-command benchmark** for the requested free-build native grouped FP16 expert GEMM event service. Re-running any of the above under different labels would not fill that gap.

## Smallest new measurement, if later authorized

Add (or use an already-existing reviewed harness only if it proves these same conditions) one bounded diagnostic arm in a separate quiet period, never concurrent with model inference/build/tests:

- Freeze the free build to the exact LLVM 7.1.1 source commit `504366f4b82ff00bbac7b0c956635eed8bc599d8` plus the recorded 17 patches. Record full source revision and hashes, compiler/link receipts, Level Zero runtime/driver and GPU identity, effective free/oneMath configuration, binary hash and all route controls.
- Use production H=2560, FF=640, standard expert GEMM dimensions GU `[1280,2560]`, Down `[2560,640]`, FP16 input/weights and FP32 accumulation/output. Source weights from exact valid IQ3_S/Down-pair blobs already in the fixture, dequantize and correctness-check before timed product samples. For the first discriminating shape use one routed expert with `m_e=8`; also cover `m_e=1` as the decode/small-row endpoint and one grouped launch with actual `bounds` copied from a closed production census. Do not invent that census from mean widths. If the closed histogram is available, select its common observed shape and one actual tail; preserve every expert’s exact row count and boundary.
- Measure GU, SwiGLU/intermediate, and Down separately only as needed to keep product intervals unambiguous; the core requested metric is the GU and Down product command events. Save per-sample event start/end, host submission and submit-to-completion, warmup/repetition counts, selected kernel/path, group size and row bounds. Preserve raw samples and report median/p10/p90. Keep dequant, host staging/H2D, and queue idle gaps outside the kernel-event denominator and report them in separate columns. If only wrapper-to-completion can be measured, label it that way, not kernel time.
- Run on device USM inputs/outputs. Do not use host/shared USM for an overlap experiment: `sharedAtomicFalse` is not a concurrency/lifetime qualification. Keep any packed-weight staging transfer as a separate explicitly timed control. The supplied `normalmax10132807680` is an allocation property only; account buffers against the actual free-memory receipt and do not treat it as bandwidth or total allocatable capacity.
- Establish the exact XMX selection first. For Xe2 grouped XMX, source gates include reported subgroup 16, a supported FP16×FP16→FP32 joint-matrix combination at the expected 8×16×16 shape, and successful compile probe for 256-GRF mode; source also retains alternate fallback routes. Record each property/report and actual selected branch. If any gate is unavailable, label the measured fallback (DP4a/joint_matrix fallback/other) and do not call it the XMX roofline. Dequant kernels have their own workgroup/FP16 acceptance and are not certified by GEMM matrix capability.
- Correctness gate before performance: compare product output for the same dequantized operands, activation rows and exact expert bounds to the current per-expert free-build reference; verify queue completion/error status, all output elements under the established tolerance, non-finite counts, row conservation, bounds and guard regions. The timing tool itself is not a parity test. Any changed grouped ordering requires de-permuted output comparison.
- Report logical bytes only as logical bytes (FP16 weight/activation reads and FP32 outputs), unless a supported B570 external-memory counter has its event definitions, support status, coverage and attribution recorded. Keep VRAM-copy, H2D, host RAM and vendor 380-GB/s figures separate. They are different operations or specification values.

If source modification is disallowed, stop at eligibility: no current built-in command closes this gap, and `--kernel-bench` is not a valid substitute. No code or command was run in this audit.

## Device-property interpretation

The supplied max-allocation value and `host/sharedAtomicFalse` do not say whether the exact device exposes subgroup 16, a joint-matrix tuple, FP16, device USM or 256-GRF compilation, nor whether memory counters are available. The required property packet for this one experiment is the selected device/driver, FP16 and device-USM aspects, subgroup sizes, max workgroup/work-item dimensions, joint-matrix combination report for FP16×FP16→FP32, and the exact-kernel 256-GRF compile result. For native grouped dequant also record API acceptance and its 256-work-item launch constraints. For host-to-device transfer measure a separate actual copy event; no allocation maximum, host-atomic flag or logical expert size establishes transfer or external-memory bandwidth.
