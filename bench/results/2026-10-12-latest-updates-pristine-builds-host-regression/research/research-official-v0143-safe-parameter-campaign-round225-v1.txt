## Decision

Keep the qualified long-prompt route: `--short-read 65536 --spec 8 --suffix-draft 0 --no-spec-split --prefill 8`, with `STRATA_VERIFY_STEPPED=1 STRATA_VERIFY_PIPE=0 STRATA_VERIFY_NO_HOST=0 STRATA_VERIFY_DEVICE_PLAN=1`, and the supplied fixed context/KV/profile/cache/PCIe/adaptive/native settings. The 32K and 64K requests must actually select `read_windows`; route logs and final commit wait are acceptance evidence. This route avoids the known Prefill Stager/PLE host-USM polling issue by not taking batched Prefill for those eligible text segments.

The best source-backed candidates are small, single-variable changes inside the stepped verifier route: first remove non-service graph split points (`STRATA_VERIFY_SPLIT=0`) while preserving the layer service boundary; then compare resident device planning; then tune CPU pool participation/workers for miss service. Keep verifier width at its existing maximum eight. No currently known environment-only change makes general multi-chunk native Prefill safe when the board reports no host-USM atomics. Therefore the safe campaign can improve the current window path and cold decode, but cannot yet claim a faster batched-prefill route.

## Parameters to keep fixed or reject

- **Prefill chunk, stream and issuer knobs:** R207/R219 identify reachable raw volatile `done_seq` polling for a nonresident unpinned Stager job and `ple_done_seq` polling when a later Prefill chunk reuses PLE host buffers. `STRATA_PREFILL_STREAM_ALL=0`, `STRATA_PREFILL_ISSUER=0`, `STRATA_PLE_BATCH=0`, or a larger `--prefill` chunk do not independently remove those markers. Multi-chunk batch arms remain unadmitted on this atomic-host-free discrete GPU absent a supported queue/event rewrite or a strict, runtime-proven one-chunk/no-Stager-job predicate. Keep `short-read=65536` as the route selector for these 32K/64K intervals; changing the threshold can route more text through verifier windows or expose unsafe batching, not accelerate the existing eligible windows by itself.
- **Speculation width:** `--spec 8` is already the maximum T. With no MTP and suffix draft 0, the specified decode outputs are still serial T=1 windows; raising `--spec` cannot help. Preserve `--no-spec-split`; `--spec-split` changes graph/work grouping and adds potential per-layer service work, and historical “exact, ~7% slower” help text is not a B570 measurement.
- **Verifier safety modes:** `STRATA_VERIFY_EAGER=1` suppresses segmented capture (`capture()` returns without segments) and forces normal `record_window()` execution; it is not a safe replacement for `STEPPED=1`. Keep `STRATA_VERIFY_PIPE=0` in the first campaign; enabling pipe adds concurrent helper/pool behavior and CPU placement as a confound. `STRATA_VERIFY_NO_HOST=1` is unsafe for a miss-bearing window because the device waits on a host plan that will not be supplied. `STRATA_VERIFY_LEAN` is ineffective in the selected route: lean requires both no-host and non-stepped execution. The current device-plan setting is useful only while `NO_HOST=0`.
- **Debug and measurement flags:** leave `STRATA_VERIFY_DEBUG`, `STRATA_VERIFY_TRACE`, `STRATA_VERIFY_PROFILE`, and `STRATA_VERIFY_NODES` unset for timed arms. DEBUG allocates per-layer residual buffers and inserts per-layer copies; PROFILE allocates timestamp counters/stamps and changes shared-expert stream selection; TRACE writes ring breadcrumbs; NODES enumerates graph nodes at capture. Use those in separate diagnostic passes, never compare their times with uninstrumented runs. Keep the normal cache `verify_slot` startup content check enabled; it is a one-time transfer/correctness gate and is not a steady-state throughput optimization. Do not disable it to improve reported generation rate.
- **oneMKL threads:** pristine `sycl/CMakeLists.txt:237–238` applies `-qmkl=sequential` to the Prefill target. Intel’s oneMKL guide says this compiler option selects/links the sequential threading layer. An `MKL_NUM_THREADS` sweep is therefore not an admitted CPU pool tuning axis for this build; leave it fixed and confirm the exact built executable’s compile/link receipt before any claim about a rebuilt variant. Do not change build threading mode as part of this source-only campaign.

## Independent prefill/decode adoption

For 32K and 64K requests on the selected safe route, eligible text is processed by `read_windows`, not by `Prefill::run`. Therefore `--prefill 8` is a required/fixed serve setting but is not the size of those verified windows. Track actual `read_windows` counts and committed positions; a chunk log showing Prefill ran indicates a changed route and invalidates the comparison. The safe arms above can improve window submission, resident dispatch, or CPU miss-service; they do not make the multi-chunk native Prefill route safe.

The CPU worker sweep affects any host expert service in both prompt and decode. Isolate decision-making by reporting `PP`/prompt interval, first-token latency and post-prompt decode separately; there is no source knob here that changes CPU worker count only for the decode phase. If prompt time remains dominant after the safe graph/planning arms, the needed next step is an implementation change replacing concurrent host-USM marker polling in Prefill with supported queue/event synchronization, then separate correctness/fault admission before a Prefill performance campaign.

## Primary external evidence

Intel’s [SYCL GPU atomic guidance](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2024-2/atomic-operations.html) states that atomics on host-allocated USM are unsupported on discrete GPU and concurrent host/device access to one shared-USM location is unsupported; this supports excluding the raw marker-poll path. Intel’s [SYCL application optimization guide](https://www.intel.com/content/www/us/en/docs/oneapi/programming-guide/2024-0/optimize-your-sycl-applications.html) recommends finding the actual host/device bottleneck with profiling and does not predict a winning Strata flag. Intel’s [oneMKL `-qmkl` compiler-option documentation](https://www.intel.com/content/www/us/en/docs/onemkl/developer-guide-linux/2026-0/using-the-qmkl-compiler-option.html) says `-qmkl=sequential` links the sequential threading layer.
