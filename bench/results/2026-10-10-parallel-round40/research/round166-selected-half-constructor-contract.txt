## Installed oneAPI 2026.1 implementation

Installed compiler root inspected: `/opt/intel/oneapi/compiler/2026.1/include`.

`sycl/half_type.hpp` SHA-256 `6321bb1d428814c964685275374204f0eae94f7153bbcd38a4bb071b7d177fce` contains an explicit compile-time branch at the `half(float const&)` constructor:

- Host compilation (`!__SYCL_DEVICE_ONLY__`) initializes storage with `float2Half(rhs)`. That routine decodes float bits itself, maps sufficiently large finite values to half infinity, handles NaNs as a quiet half NaN, performs ties-to-even rounding for normal-range mantissas, and preserves sign. Its subnormal branch shifts the significand directly without rounding discarded bits. Thus this host implementation is not full binary32-to-binary16 RNE for subnormal results: it truncates them toward zero (and values below its exponent cutoff become signed zero). The source comment's nearest/tie-even description appears only inside the normal-range branch. This distinction matters for host-side constructor fixtures.
- Device compilation (`__SYCL_DEVICE_ONLY__`) initializes storage as `Data(rhs)`, where the device representation is the compiler's native half type; the header contains no software conversion algorithm or explicit rounding selector for this branch.

Consequently the selected implementation has different host/device source paths. Header presence establishes this conditional source lowering, not the actual emitted instruction or effective target behavior. For the selected Intel Arc target, LLVM's normal FP conversion model and the OpenCL SPIR-V environment point toward an `fptrunc`/`OpFConvert` style conversion with RNE by default; however, without compiler output the precise lowering is not proven, and without target/runtime FP-control evidence, half denormal preservation/flush behavior is unresolved. SPIR-V's OpenCL environment says FP-to-FP `OpFConvert` defaults to RNE absent an explicit rounding decoration; it also permits denormal FP16 inputs/results to be flushed depending on implementation mode. LLVM's `fptrunc` default-environment semantics are IEEE-correctly-rounded absent controls that change behavior. These are conditional standards expectations, not proof about this build's generated SPIR-V or device mode.
