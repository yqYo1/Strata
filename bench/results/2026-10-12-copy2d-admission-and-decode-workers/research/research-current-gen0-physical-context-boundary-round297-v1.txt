# R297 — GEN=0 and the physical full-context boundary
Date: 2026-10-12 (Asia/Tokyo)

## Finding

On combined HEAD `9b03c18b643e974e5475f68a2a9d2f26ea9613b0`, the ordinary `--serve` `GEN` route cannot prove or perform an exact-capacity, no-output read of all 262,144 input cells. `GEN 0 ...` is explicitly rejected: `context_bounds::admission` requires `outputs > 0`. With one requested output, admission requires `prompt + 1 <= max_context`, so at capacity 262,144 the largest prompt is 262,143 IDs. That leaves the physical last cell (zero-based cell 262,143) unconsumed. `ckpt=0`, spec-4, suffix-draft-0 and no MTP do not alter this contract. A guessed `GEN 0` is not a valid workaround and should not be used as a boundary test.

The existing `--full-context-probe` is not an applicable workaround for the requested recipe: its parser requires MTP, a full 262,144-ID prompt, and max-new zero, then runs a special MTP row/capture/restore diagnostic. R356 reviews that opt-in path as source-qualified for its own MTP diagnostic; its behavior cannot establish no-MTP decode or no-output semantics. Historical `GEN 262140 IDs + max_new=4` receipts also belong to an older binary/source; they do not change the current admission check.

Therefore there is no safe supported command in the requested current no-MTP/spec-4/suffix-0 recipe that simultaneously processes all 262,144 physical input cells, emits no output, and stays within current bounds. The minimal actionable qualification is a dedicated no-MTP, zero-output input-drain mode (or an equivalently bounded harness mode) that explicitly runs the final prompt row at position `cells-1`, disables sampling/output, commits that row, drains/waits all relevant queues, and reports committed-cell coverage. Admission must validate the full prompt span before any enqueue; each Prefill span and verifier row must retain their current physical-capacity checks. This report proposes a test contract, not a source change or execution.

## Source trace

Audited source hashes:

- `src/program/generate.cpp`: `b27fd104b79007814a3eedc8f575d390eeefc986bc82ff01225c6d5b6a4d5ca9`
- `src/prefill/prefill.cpp`: `ececd50d16cb9f41b20a5890a461ca2dad33873693ac9a6d5d0ec499bbaa9183`
- `src/core/session.cpp`: `d914f75a19022edd29f6fec0fd4df85f1b24b09d56bf014744be79d12e914ab6`

The command parser in `generate.cpp:8116-8175` recognizes `GEN`, parses `max_new`, and accepts `ckpt=0` as disabling checkpoint writes/continuation behavior. It does not make `max_new=0` legal. After IDs are parsed, `generate.cpp:8282-8285` calls `context_bounds::admission(max_context,n,max_new)` before prompt processing; a false result prints `ERR prompt (...) + max_new (...) exceeds the context (...)` and continues without scheduling that request. The helper at `include/strata/core/context_bounds.hpp:19-21` requires positive outputs and a bounded `span(cells,prompt,outputs)`. Thus the checked combinations are 32,767 + 1 <= 32,768 and 262,143 + 1 <= 262,144; exact-capacity prompts paired with any positive output count fail. `GEN 0` fails even if the sum would fit.

The current serve prompt logic (`generate.cpp:8769-8827`) reads known prompt IDs in windows `[a,b)`; each window forms `win[t]=cur[q+t]`, the successor `nxt[t]=cur[q+t+1]`, runs `ver.run(T, ..., q, ...)`, then commits `T` rows and advances `pp_reached=q`. The main decode path begins at `p=n-1`, with `x=ids[n-1]` (`generate.cpp:9115-9120`). Therefore the last prompt ID is intentionally reserved for the first verifier window, rather than included in the prior prompt windows. Decode-window processing is guarded by `produced_n < max_new` (`generate.cpp:9781`); a zero-output request would not execute that final row even if the admission guard were bypassed. This is the important distinction: `ckpt=0` changes checkpoint retention, while the prompt-final row is reached only through the output-producing verifier route.

The standalone `generate` path has the same split: batched Prefill handles `n_prompt-1` conditioning tokens (`generate.cpp:10383`), then the token loop starts at the last prompt position, executes the layer/head/sample work, and checks the generated count after sampling (`generate.cpp:10625-10640`). It is not a no-output consumer either. `Prefill::run` independently rejects any input span outside physical capacity via `publication::valid_span(n,pos0,ss.max_cells)` (`prefill.cpp:1224-1229`); this bounds the batched region but does not add a route for the withheld final row. Verify batch rows independently check `pos[t] >= 0` and `pos[t]+1 <= slot.max_cells` (`verify.cpp:1937-1970`), with `context_bounds::verifier_window` refusing a row at `pos==cells`.

SAVE/RESTORE (`SAVE`, `RESTORE`) serializes or reloads the current conversation state and its token/KV/checkpoint ownership. It does not consume a token or move the final prompt row through inference. The no-MTP recipe also has no MTP-specific KV state to use as evidence. Current session position/state hashes can demonstrate a restored prior state, but not that a fresh run executed row 262,143 unless the new input-drain path reports coverage tied to this request.

## Minimal boundary qualification contract

Keep the intended setting fixed: max-context 262,144; no MTP; spec 4; suffix draft 0; int8 KV; 32,768 resident cells; no KV growth; `ckpt=0`; and a fixed, bounded-vocabulary prompt fixture. Use a deterministic token sequence with a recorded source, exact count, IDs/hash, and a small, reproducible task-formatted tail. Do not fabricate 262K natural-language tokens by repeating a tiny chat suffix and call it representative.

1. At 32,768 cells, separately assert admission behavior for zero outputs (must reject today), 32,767 IDs plus one output (must admit), and 32,768 IDs plus one output (must reject before enqueue). Under the current code, this is only an admission/last-row boundary check; it does not qualify an exact 32,768-input no-output drain.
2. At 262,144 cells, repeat with 262,143 IDs plus one output and 262,144 IDs plus one output. The former is the current legal max prompt but can only establish through cell 262,142 as a prompt input; the latter must reject before enqueue. `GEN 0` at either size must reject.
3. To qualify all physical inputs, add the explicit no-output drain mode. Assert zero sampled/emitted tokens; monotonically contiguous processed positions `[0,262144)`; final processed position 262,143; no attempted row at 262,144; successful completion and synchronization of main and any auxiliary queues; `pp_reached`/committed-row count 262,144; plus a state/KV/checkpoint fingerprint and SAVE/RESTORE round-trip comparison against the captured post-drain state. Run the same contract at 32,768 first. A DONE line reporting prompt length or `pp_reached` alone is insufficient unless the diagnostic proves the final verifier/session row actually ran and committed.
4. After the boundary request, issue a positive-output request and verify it is rejected without enqueue if no context remains; separately SAVE/RESTORE the exact full session if the product contract intends such a state to be restorable. State clearly whether a full session is terminal-only or can be resumed after truncation/eviction; do not treat cached conversation length as physical row evidence.

The no-output drain mode needs explicit ordering: validate token IDs and checked span arithmetic first; allocate/prepare; process batched span `[0,cells-1)`; process the final input token at `cells-1` through a non-sampling verifier/session row; commit exactly one row; wait on its commit and every queue touched; only then capture state or save. A failure before the final commit is partial, not a pass. The existing input-loop structure cannot silently be relabeled as this mode because it conditions the final prompt row on a positive output count.
