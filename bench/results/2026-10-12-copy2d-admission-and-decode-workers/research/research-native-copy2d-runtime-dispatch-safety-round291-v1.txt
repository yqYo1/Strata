## Answer for Main's first cohort GPU qualification
On the audited LLVM 7.1.1 / UR 0.12.0 Level Zero v2 source, a SYCL `ext_oneapi_memcpy2d` with Host-USM source and Device-USM destination does **not** take the native Level Zero 2D path: the v2 context explicitly reports `UR_CONTEXT_INFO_USM_MEMCPY2D_SUPPORT=false` with a TODO. SYCL's `MemoryManager::copy_2d_usm` therefore decomposes the region into `height` separate `urEnqueueUSMMemcpy` operations, each receiving the supplied dependency list, followed by a queued `urEnqueueEventsWait` that returns the group completion event. For cohort height 2–16 this means 2–16 H2D copy commands plus the event join, not one native region command. Because the source pointer is host-USM, this does **not** fall back to a GPU kernel.

Thus the first Main run must not be labeled or accepted as a native Copy2D cohort unless it first establishes that the exact context reports the 2D capability and that the runtime actually dispatches `urEnqueueUSMMemcpy2D`. On the audited v2 implementation the capability is false, so the safe outcome is to skip native qualification and keep the existing one-row Strata copy path. A separate, explicitly labeled fallback characterization is a different test and does not qualify the optimization.

The extension's compile-time feature macro and the public method's existence only establish that the API is present. The runtime-native capability check is internal to SYCL (`handler::supportsUSMMemcpy2D`) and the public API offers no corresponding `queue`/`device` query. If Main cannot obtain the `UR_CONTEXT_INFO_USM_MEMCPY2D_SUPPORT` value from the same selected SYCL context through its current adapter/interop layer, it should remain fail-closed (native cohort disabled). If capability is true, a small-buffer UR trace or equivalent runtime dispatch receipt should confirm one `urEnqueueUSMMemcpy2D` before a model-integrated run; returned SYCL event timing alone cannot distinguish the native path from per-row fallback.

## Dispatch paths in source
1. `sycl/include/sycl/ext/oneapi/memcpy2d.hpp:36-58` classifies pointers. Host+host uses a host task. If either pointer is host (including Host-USM) it creates the `Copy2DUSM` special command; only device/device considers `supportsUSMMemcpy2D()` there and can use a fallback kernel.
2. `sycl/source/detail/memory_manager.cpp:926-993` is the later, decisive runtime branch. If context query `UR_CONTEXT_INFO_USM_MEMCPY2D_SUPPORT` is true, it calls one `urEnqueueUSMMemcpy2D`. Otherwise host-involved transfers run a loop from 0 to `Height`, enqueueing one linear `urEnqueueUSMMemcpy` per row with the same dependency handles, then enqueue an event-wait command. This hidden fallback is why the public extension call succeeding cannot be used as proof that the adapter executed native 2D.
3. In the audited v2 adapter, `unified-runtime/source/adapters/level_zero/v2/context.cpp:233-235` returns false for the capability, marked “currently not implemented.” Therefore the source-backed active route for this package family is step 2's row decomposition.
4. If capability is true (or a caller bypasses the SYCL capability gate and invokes UR directly), `queue_immediate_in_order.hpp:305-317` dispatches to `command_list_manager::appendUSMMemcpy2D`; `command_list_manager.cpp:574-590` creates zero-origin source/destination regions and routes to `appendRegionCopyUnlocked`; `:191-219` calls `zeCommandListAppendMemoryCopyRegion` with source/destination pitches, region width/height, wait handles and one signal event. This is a native Level Zero region-copy API submission, not a row loop or GPU kernel in the adapter source. It proves one region-copy API command was appended; it does not prove which physical engine services it, that the engine is DMA-only, or that the copy overlaps compute.

The region conversion narrows row pitches, width, height and origin coordinates to `uint32_t` (`unified-runtime/source/adapters/level_zero/helpers/memory_helpers.cpp:42-79`). The cohort wrapper must precheck every field before narrowing, as the existing source audit says. UR's raw-USM handle uses size zero (`command_list_manager.cpp:583-584`), and the route does not establish the complete rectangle's allocation bounds. Keep Strata's exact single-allocation, extent, overflow and lifetime proofs even if a runtime advertises native support. The extension also rejects command-graph association synchronously (`memcpy2d.hpp:21-25`); the graph path is not eligible.

## Event lifetime and error behavior
The Main wrapper passes all live per-slot reader events in the `std::vector<sycl::event>` dependency argument. In the native path these become the UR wait list and then Level Zero wait-event handles for the one region operation. Keeping the Strata `used` events alive until the copy's returned event completes matches the caller's slot-reuse contract. The one returned event is a suitable completion for every row only when the native operation actually ran and all row readers are dependencies.

The fallback path changes event ownership internally. `MemoryManager::copy_2d_usm` owns one returned UR event per row in `OwnedUrEvent` objects until it enqueues the join at line 991, then destroys those owners as the function returns. In UR v2, `wait_list_view` turns the supplied event handles into raw Level Zero handles (`command_list_manager.cpp:49-94`); immediate-queue `appendEventsWait` appends `zeCommandListAppendWaitOnEvents` (`:1084-1103`). The v2 event's `release()` sends pooled events to `event_pool::free`, which calls `event->reset()` and puts the same object back on the free list (`event.cpp:180-190`, `event_pool.cpp:46-56`); `reset()` calls `zeEventHostReset` (`event.cpp:157-165`). The code inspected does not show a completion check before a fallback row event is returned/reset/reusable. Level Zero documents that the application must ensure the device is not currently referencing an event before destroying it, and the event is still supplied as a wait dependency of the enqueued join. I cannot conclude from this source-only audit whether this runtime's event-pool contract and driver semantics make this immediate recycle safe; that deserves a focused fallback lifecycle test, particularly if post-join events can be reused on the same queue. This is a source-inferred unresolved risk, not an observed failure. Do not rely on hidden fallback as a harmless implementation detail or change internal events into caller-owned ones without verifying the runtime contract.

For the native path, the caller-held `used` events avoid that specific internal per-row event fanout. Runtime capability false is not itself a native-path correctness failure: SYCL's documented/source implementation attempts to preserve correctness by falling back. It means native command-count qualification is absent; on a per-row fallback, Strata's own service event metadata may describe the final SYCL join rather than each internal row command, so that event must not be reported as evidence of one-copy execution.

## Known unequal-pitch hazard and scope
The cohort uses `srcPitch=width` and `dstPitch=MMQ_SLOT`, so its native candidate has unequal pitches. An open ALCF/Aurora reproducer report for `zeCommandListAppendMemoryCopyRegion` describes GPU SIGSEGV with unequal source/destination pitches on an Intel multi-tile GPU; it notes the related SYCL fallback-to-row-copies behavior and reports “Fixed with 1146.78.” That report is not a B570 reproduction and does not establish a defect in the installed 7.1.1/v2 runtime. It is direct evidence that unequal-pitch region copies have had a driver-sensitive failure mode, and supports preserving a runtime-capability gate and per-row fallback. Do not bypass a false capability bit to force the region command. [ALCF report and reproducer](https://github.com/argonne-lcf/AuroraBugTracking/issues/30).

I found no public primary report in the reviewed material that establishes a B570 hang for this exact call. Level Zero's programming guide says event wait DAG cycles can deadlock and must be prevented by the application, but that's a general dependency rule, not a report that this cohort hangs. No event or command hang was reproduced here.

## Minimal release gate
- Confirm the selected adapter/backend and query the `UR_CONTEXT_INFO_USM_MEMCPY2D_SUPPORT` value on the exact queue context. Query failure, unknown adapter, or false means native cohort is ineligible; keep the existing 1D path.
- If true, use a separate small-buffer preflight first. Retain evidence that the actual UR call is one `urEnqueueUSMMemcpy2D` (not N `urEnqueueUSMMemcpy` calls), with expected width/height/pitches and all reader dependencies; verify contents and padding only after checked completion, and propagate async errors.
- Keep source and destination allocations plus all caller-owned dependency events alive through the returned event. Do not use graph capture. For capability-false fallback characterization, separately retain row-command counts and validate whether pooled row events are reset/reused before the join has completed; if safe completion cannot be shown, don't exercise the extension fallback in this feature's path.
- Treat offload queue flags as hints only. They do not change native-vs-row dispatch and do not prove physical copy engine selection. The R276/R283 reporting limits remain in force.

No additional host packing/temporary scatter technique is recommended: it would add allocation and a device scatter step, while the current Level Zero source reports native 2D unsupported. The only previously source-backed candidate remains native Copy2D when the exact runtime advertises and demonstrates it; all other rows remain the existing fallback. This does not claim speedup.
