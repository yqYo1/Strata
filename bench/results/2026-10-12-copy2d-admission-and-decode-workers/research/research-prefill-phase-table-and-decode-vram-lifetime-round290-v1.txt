# R290 — Prefill-phase allocations and decode VRAM lifetime

Date: 2026-10-12 (JST). Read-only source audit of curated combined HEAD `9b03c18b643e974e5475f68a2a9d2f26ea9613b0` at `/home/yayoi/ghq/github.com/yqYo1/Strata/.worktree/sync-latest-updates-20261012`. Prior reports R279, R284, and R316 were consulted as boundaries; this report does not repeat their scratch-size or alias proposal. No source edit, tests, build, AST/import, GPU/process/service operation, Git mutation, or cleanup was performed. No candidate worktree was accessed.

## Decision

The recipe cannot make useful VRAM by moving the embedding table to RAM: for a native IQ pack it is already in mapped pinned host memory, with a device alias for GPU reads. With `--mtp` absent, MTP decode experts, draft head, draft KV, and MTP graphs are not loaded/bound, so there is no MTP lease to release. The target output head is a real device allocation and can be hundreds of MiB, but current captured verifier graphs reference its address; verifier windows also run during prompt processing on the path selected by `windows_ok`. There is therefore no safe source-level “free head around every prefill” switch.

The only plausible unchanged-math experiment is an explicit mutually-exclusive phase lifecycle for the *batched* prompt route: drain outstanding work, retire verifier graphs/arena and device head before initializing/running a large owned Prefill workspace; then drain and reset/free Prefill before re-uploading/formatting the head and rebuilding Verifier graphs before any verifier-window or decode use. It must retain main model weights, session/KV state, native embedding and its mapping. It is a substantial lifetime refactor, not an allocation tweak. Because the service can choose verifier windows for some prompt segments and batched Prefill for others, it needs a route-aware serialized transition and cancellation/RESTORE recovery. It has no numeric fit guarantee without measurements. A 64K chunk is four times the T-proportional workspace of 16K while the 262,144-cell context's QSA/session state remains; this audit cannot claim either fits.

## Recipe interpretation and startup/admission order

The source accepts `--expert-cache auto` or an integer: parsing is `(v == "auto") ? -1 : atoi(v)`. If “free” means literal `--expert-cache free`, it becomes zero slots, not auto/free-memory sizing; if “free” is shorthand for an external configuration, its actual cache size is unspecified. The no-borrow flag is explicit and causes the prompt path to allocate its own buffers. For a fixed chunk the service initializes `sp` at startup; it does not halve that fixed chunk on its own when no borrow is available. A failed init reports that the chunk's device buffers do not fit. Auto-chunk mode has a separate small-chunk fallback and is not evidence for a fixed 16K/64K chunk.

Startup order in this source is materially important:

1. `session_bytes/session_init` allocates the main session for `max_context` and builds QSA state; the 32K resident setting still records 262,144 max cells and allocates the host backing for streamed cells.
2. Native embedding is loaded into pinned host RAM. Native dense weights and the main output head are loaded; the head and `d_logits` are allocated before expert-cache sizing. The source comments explicitly place the head before the cache so the cache fits around it.
3. Expert-cache auto sizing subtracts reserve for prefill and other allocations. With no borrow, the single-GPU estimate uses `160 + chunk*680/1024` MiB for prefill; this is a planning estimate, not `bytes_needed` high-water. The prompt's own chunk buffers are then allocated by `sp.init` in the serve setup.
4. The serve path initializes `sp` before initializing the `Verifier`. The verifier is initialized with `max(o.spec,o.batch)`, then the process reports ready. The graphs/arena/head are thus resident along with Prefill for serving.

One effective-setting caveat: `Options::suffix_draft` defaults to 3. When `--spec 4` is supplied, `--mtp` is absent, and no explicit `--mtp-max-t` prevents the default path, the source's suffix-draft setup sets `mtp_max_t=4` and raises effective `o.spec` to 6 (`min(spec+2,8)`). The verifier is allocated for effective `spec`, not the command-line spelling. `--suffix-draft 0` changes that route; a task/run labeled “spec4” must record effective startup INFO/argv before its verifier bytes are assigned. This is not MTP: there is no MTP model load or bind.

## Bounded source result and safe candidate boundary

The only high-value potential VRAM exclusion among the named allocations is the target head plus verifier-owned buffers during batched prefill. It is not currently safe to free only the weights: captured graphs retain the pointer. It is not generally safe to free verifier buffers because `windows_ok` can route a prompt part through the verifier, and those windows also evaluate the head. The service initializes Prefill and Verifier once and keeps both for multiple requests; `NativeHead` has no restore API. The existing `Prefill::reset()` supports the other half of a request-scoped lifetime, but a correct change needs explicit owners for both phases and for all early returns.

A narrow test candidate can keep arithmetic and the conservative synchronization boundary unchanged:

- Serialize a request-phase gate (the recipe is single-request/non-batch). At the transition to a batched-only prompt part, wait for all relevant compute/copy work, destroy verifier graphs/arena, release the device output head and any truly unused direct-token buffers, then construct/run the owned Prefill workspace. Keep session, mapped host embedding/KV, dense weights, cache and all model values unchanged.
- At the end of the batched prompt, drain the Prefill compute/copy/stager work and call `Prefill::reset()` before re-uploading/reformatting the exact head bytes, allocating verifier workspace and recapturing the verifier graph. Do this before any verifier-window prompt part, final prompt-token work, or decode.
- If a request interleaves batched and window parts, perform a safe phase transition for each part or decline the optimization for that request. Cancellation, failed Prefill reset, partial head upload, failed graph recapture, and RESTORE must fail closed and leave no graph with a dead pointer.

This candidate must not use shared-host atomics as a new progress/lease signal. Preserve `host_handoff_concurrent == false` behavior and existing queue ordering; phase changes are host-side serialized transitions after explicit stream/device drain. It does not alias or overwrite session state, KV, captured session-layer weights, or mapped embedding. A simpler first experiment may conditionally skip the small direct-token scratch in service mode, but its VRAM return is under 1 MiB and does not justify a large-chunk claim.

## 64K, full context, RESTORE and first-use limits

- T=64K increases T-proportional prefill workspace and pinned PLE upload staging fourfold versus T=16K. The full-context QSA score/index shapes remain configured for 262,144 cells; they do not fall because the chunk is 16K or 64K. With no borrowing, fixed chunk init either fits its owned allocations or fails. There is no source-only way to assert 64K fits the user's free card.
- `--kv-resident 32768` reduces the main QSA device K/V page pool, but creates/retains authoritative full-context pinned K/V and mapped page tables. It is a persistent model-state tradeoff, not a decode-only temporary buffer that can be evacuated for prompt scratch. The session's graph addresses, QSA index state and full-context RoPE remain live.
- RESTORE of a saved session changes/repopulates persistent session/KV state; it does not retire Prefill or verifier storage and does not free the output head. With MTP absent, the serve source explicitly turns off parked conversation-cache and `--conversation-save` behavior because those images require draft-layer K/V; that mode cannot qualify MTP-backed conversation RESTORE. Any other supported session restore must be tested after the phase transition with full 262K geometry and 32K resident K/V, then verified through the first verifier/decode use.
- First-use GEMM/library/kernel allocation and graph capture may have a different peak from steady state. The source prepares some GEMM/runtime resources before allocation sizing, but it does not supply a receipt for this exact recipe/card. Measure cold start and warm start, `Prefill::init` high-water, after Prefill reset/head restore/verifier capture, first prompt, first post-RESTORE window, and subsequent decode. Record selected/effective spec and chunk, actual expert-cache slots, allocator failure/fragmentation, host pinned bytes, and native head tensor type/bytes. No inference/runtime was run here.

## Minimum evidence for an implementation decision

1. Resolve the run's actual cache parameter (`auto` or integer, not ambiguous “free”), effective `spec` after suffix/lookup defaults, actual GGUF output tensor type/shape, device, and `Prefill::bytes_needed`/separate allocations.
2. Prove a phase owner can destroy every verifier graph that references the head and complete every queue before free; show no host/shared-atomic dependency was added and no cross-request overlap can enter the transition.
3. Compare the unchanged prompt token sequence/logits in baseline and phase-swapped runs through full 262,144 context, at fixed chunks 16K and then 64K. Include short prompt, multi-chunk, window-route, mixed route, cancellation, first use, and session RESTORE; no quality or correctness inference from allocation-only success.
4. Record total/free/high-water before and after each phase. A successful Prefill allocation while head/verifier are absent is insufficient: prove the intended post-prefill phase also fits when the head and verifier are rebuilt, and that repeated requests do not leave stale graphs or lost K/V.
