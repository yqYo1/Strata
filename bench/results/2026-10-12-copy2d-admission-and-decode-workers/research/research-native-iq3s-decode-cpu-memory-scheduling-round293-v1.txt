## Exact current path

`expert_pool_dispatch_multi` quantizes one input row once per layer (`expert_source.cpp:1917–1928`), then groups repeated routed expert IDs into one `ExpertJobMulti` (`1957–1979`) and runs the native pool (`1983–1991`). For `n_tok=1`, every distinct CPU job has `nt=1`; a CPU miss is not equivalent to one pool task or to one active expert for every layer. Current exact model CPU/GPU ownership and per-layer GU/Down formats must come from the request's route/job histogram.

On the target's AVX2-without-AVX-512 path, default `native_gu_mt_min` selects the custom AVX2 kernel at NT1 for all eligible GU formats except IQ2_XXS, unless `STRATA_IQ_MT_MIN` or the disable switch changes the branch (`native_expert.cpp:95–112, 115–142`). IQ3_S therefore does **not** fall through to ggml-cpu's scalar one-token dot under the stated default setup. Down is dispatched separately: IQ4_NL has its own AVX2 path; Q2_0 has the q2 path. The two should not be merged into an “IQ3_S expert kernel” attribution.

The actual job work is split into GU rows, serial per-job intermediate quantization, and Down rows. The native pool partitions a flattened `n_experts × FF` / `n_experts × H` row range into equal contiguous task slices; each slice may cross expert boundaries. Dynamic workers claim these fixed slices. GU and Down are separate phase barriers, and host elapsed phase spans include wake/park, publish, host drain and completion (`pool.cpp:325–379, 381–390, 470–506`). Parent's worker/tasks experiment is the right owner for those controls; this audit does not suggest a worker count or generic task sweep.

For IQ3_S type 21, one row is 10 × 110 = 1,100 packed bytes. At H=2,560 and FF=640, GU contributes `2 × 640 × 1,100 = 1,408,000 B` per expert job. If paired with IQ4_NL type 20, Down row bytes are 20 × 18 = 360, hence 921,600 B; whole blob is 2,329,600 B. These are logical packed extents, not DRAM reads. The per-token Q8_K input has ten 292-byte blocks (2,920 B). Existing independent Gate and Up row traversals each reload that activation stream for all 640 rows: 3,737,600 B of logical activation loads/expert; the paired loop loads it once for both: 1,868,800 B. This is a 1.87 MB/expert reduction in repeated logical activation loads/instructions. Given the 2.9 KB activation working set and six-core Zen 3 32 KB L1D, most repeats may already hit L1; the defensible target is load/uop pressure, not DRAM traffic. The weight stream remains 1.408 MB and both matrix decodes remain required.

The AVX2 code's block loop handles 10 Q8_K blocks per row, with IQ3_S codebook/sign/scale decode and integer dot, then fp32 FMA accumulation; `native_expert.cpp` and `iq_avx2_rows.inl` describe this loop. Existing AVX2 comments report about 5 GB/s/core for the codebook-heavy multi-token kernel, but that is historical/comment context, not a measured ceiling for this request/CPU/branch. Do not translate blob bytes or dense-equivalent MACs into service time. R206 documents the lack of a current physical-traffic/PMU service measurement for this CPU.

## Candidate: paired NT1 IQ3_S Gate/Up activation loads

Current source locations: `src/kernels/cpu/iq_avx2.cpp:477–486` validates exact shape and chooses scalar/gather decode; `517–525` reads `STRATA_IQ256_PAIRED_GU` and dispatches the optional path. The loop is `src/kernels/cpu/iq_avx2_rows.inl:36–70`. This is narrower than a new scheduler or converted-weight cache and can be isolated using the existing runtime switch. It avoids expanding the 110-byte IQ3_S block representation and avoids a cross-window cache's multi-MiB-per-expert footprint/pollution risk documented in `cpu-hot-expert-predecode-cache-round9.txt`.

A source-level operation-order review supports intended exact arithmetic: for each matrix, the block, subgroup, half, SIMD integer accumulation and fp32 FMA sequence is unchanged; Gate and Up still have independent accumulators and the same final horizontal sums; SwiGLU expression is unchanged. Paired execution interleaves independent Gate/Up work, which shares activation loads and may raise register pressure. Therefore it is a no-math-change scheduling/load-reuse candidate, but still requires byte-for-byte row-output parity and full request correctness, including finite checks, before performance interpretation. Keep it disabled by default unless both correctness and performance gates pass.

Minimal discriminator after Main closes its run: select only production-exposed `(GU=21, NT=1)` expert jobs from the same qualified runtime route; compare paired switch unset vs `=1` with identical binary/source, pool workers/tasks, route, prefetch/gather environment, input/state, and request. First use a small CPU fixture with actual type-21 packed rows and the production quantizer to check every output float bit and nonfinite count; then compare phase/component time and clean `REUSED→DONE` request wall in alternating fresh processes. Keep worker/task as fixed to Main's chosen arm. Record CPU job count/type/NT and whether tasks touch these rows. If the route has little type-21/NT1 service, stop: the candidate cannot affect enough work. If the GU component improves but request wall does not, treat it as hidden/overlapped work. Do not add pool counters or profiling axes here.

## Scheduling and memory alternatives reviewed

- **Cross-expert cache/predecode:** Prior R9 quantified IQ3_S magnitude/sign predecode at 512 B per 256-weight block, 4.65× source size, before additional scale vectors; this can grow a full expert into multiple MiB. It avoids per-window codebook decode but not weight bytes or dot work, may enlarge L2/DRAM traffic and is not justified without repeated-hot-expert evidence. Not ranked over the paired path.
- **Expert-affine row ownership / per-expert static blocks:** The current flattened row slices are contiguous and dynamic; no observed worker-tail/cache counter shows that an expert-boundary crossing harms locality. Static expert ownership can strand work under variable job NT and loses the current dynamic tail balancing. A changed scheduler is not supported by the current evidence.
- **More task/worker tuning:** Already owned by Main; no duplicate recommendation here.
- **Q8 activation quantization:** Already quantized once per token/layer, not once per expert (`expert_source.cpp:1923–1924`). Sharing it across duplicate routes is already implemented; don't suggest it again.

## External primary implementation context

KTransformers' primary AMX design says it fuses expert matrix work into large tasks, shares activations, partitions weights into cache-sized blocks and dynamically distributes fine-grained work. It also explicitly says the AMX kernel is weak at decode's low arithmetic intensity and selects lighter AVX-512 kernels for decode (`[AMX design](https://github.com/kvcache-ai/ktransformers/blob/main/doc/en/AMX.md)`, especially sections 1–4). This makes shared activations and task/cache scope a credible design concern, but KTransformers preprocesses weights for AMX and supports Xeon Sapphire Rapids+; it is not an implementation to transplant to the Zen 3 AVX2 IQ3_S path and its published throughput is not transferable.

llama.cpp's primary CPU backend uses a shared atomic `current_chunk` with per-thread state in its CPU threadpool (`[ggml-cpu.c](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cpu/ggml-cpu.c)`). That is a general chunk scheduler, not evidence that replacing Strata's epoch/head task claims or flattened row ranges improves this model. The current Strata pool already dynamically claims task indices; the meaningful untested structural opportunity here is paired GU data access, not introducing another atomic queue.
