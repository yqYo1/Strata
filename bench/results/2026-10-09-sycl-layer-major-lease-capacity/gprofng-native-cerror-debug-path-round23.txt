Installed debug/logging path: not enough in this release artifact

Upstream gprofng's collector header documents `SP_COLLECTOR_DEBUG=4` as the collector debug-trace setting and defines trace levels through 4; it also declares `__collector_dlog`. The 2.42 dispatcher source uses `TprintfT(DBG_LT2, ...)` for selected `__real_*` pointer addresses and has debug diagnostics around timer operations. This is a useful source-level path when built with DEBUG support. It is not evidence that this installed release library will emit those records.

Static inspection of the installed `/usr/lib/x86_64-linux-gnu/gprofng/libgp-collector.so` found the string `SP_COLLECTOR_TRACELEVEL`, but no `SP_COLLECTOR_DEBUG`, no resolver diagnostic strings such as `__real_timer_create`, no `timer_create @%p` / timer return formats, and no corresponding timer failure format. It does export `__collector_dlog`, timer wrappers, and their GLIBC symbol versions. The debug function's presence alone does not prove that debug call sites/environment parsing were included. On this installed binary, setting `SP_COLLECTOR_DEBUG=4` cannot be relied upon to reveal resolver branches, timer return/errno, or interval values; the relevant parser/diagnostic strings are absent. `SP_COLLECTOR_TRACELEVEL` is a different setting and its presence alone does not establish the requested timer diagnostics. I did not run a collector to test these settings, consistent with scope.

Therefore the zero-change user-facing setting path is not established for this installed ELF. This is the precise delta from round 19's general recommendation to use a debug collector build: the default installed library's static contents do not provide a demonstrated runtime switch for the needed fields. GNU `collector.h`'s comment (`SP_COLLECTOR_DEBUG=4`) is conditional source guidance, not proof about this Ubuntu binary.

Minimal isolated instrumentation if the root later authorizes it

A one-off diagnostic build of the collector source, placed outside the installed package and selected only for a single owned native experiment, can answer the remaining question without global preload or package changes. Keep all emitted records in that experiment's existing `log.xml` using `__collector_log_write` as bounded `<event kind="comment">` records; no standalone trace file, unbounded polling log, or environment dump is needed. Add an explicit diagnostic opt-in (for example a narrowly named `STRATA_GPROFNG_TIMER_DIAG=1`, checked before output) and emit at most these records:

1. At each successful branch in `init_interposition_intf`, record function name, resolver branch/version string (`GLIBC_2.34`, fallback version, or unversioned dlsym), pointer value, `dladdr` object path and base. Include whether the libc `RTLD_NOLOAD` handle was found and which lookup handle (`RTLD_NEXT`/`RTLD_DEFAULT` or libc handle) was used. Keep object paths XML-escaped; do not print arbitrary target environment values.
2. Around the internal collector-only create, arm, query, and disarm calls (`collector_timer_create`, `collector_timer_settime`, `collector_timer_gettime`, and the call in `__collector_ext_itimer_set`), record input clock ID, notification mode/signal/TID, interval seconds/nanoseconds, exact function pointer, immediate return value, and `errno` copied immediately after the call. For gettime, record returned `it_value` and `it_interval`; at helper return, record `itimer_period_actual`. Restore the caller-visible `errno` after writing each diagnostic so logging does not alter behavior.
3. Use only numeric and escaped bounded fields, and avoid logging timer IDs as pointers unless their type is explicitly formatted. Keep user application wrapper calls out of these records: they can intentionally reject SIGPROF timers and are a different path.

The existing experiment `log.xml` is the appropriate compact destination because timer initialization failure is already recorded there as `cerror 9`; these records would sit beside the actual failure evidence. The diagnostic should be local to the diagnostic build and single experiment, without changing `/usr/lib`, global `LD_PRELOAD`, package state, sysctls, or system timer settings. A normal release collector build should not silently expose these extra records. If round 18's upstream debug calls are confirmed present in a separately built DEBUG collector, setting `SP_COLLECTOR_DEBUG=4` is a less invasive alternative, but still inspect the emitted log and verify it includes the required fields before deciding it suffices.

A compact decision gate after that capture: if the pointers resolve into the expected target libc and the calls report failures, the per-call errno/local inputs identify which operation to investigate; if pointers resolve elsewhere, the resolver object/version becomes the lead; if calls all succeed and gettime returns a positive period but `itimer_period_actual` is nonpositive, then inspect helper state/order. Until then, no syscall policy, libc defect, timer API incompatibility, or collector source defect is established.
