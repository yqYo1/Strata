The helpers in `src/kernels/cpu/native_expert.cpp` preserve the original function-local cached flags, thresholds, branch order and selection predicates; `native_gu_rows` and `native_down_rows` then invoke the same kernels with the same format, blob, activations, row range and output pointers. The pool's Q2 direct path is classified before the native wrappers using the same `q2_native_kernels` predicate as `drain`; the AVX-512-versus-AVX2 label follows the same predicate as `q2_rows_any` (`src/kernels/cpu/pool.cpp:635-660, 778-805`; `src/kernels/cpu/expert_layout.cpp:348-352`). Selected labels come from the same resolver used in the worker wrapper, so a supported format at `nt=1` can be eligible while counted as `ggml`. ## Important caveats before trusting output

- **The histogram reports job exposure, not literal row-kernel calls.** It adds one expert job, `nt` routed tokens, and `FF` or `H` output rows per expert (`pool.cpp:785-812`). A job can be split across flattened tasks and cause multiple wrapper calls, but the counts intentionally do not include task intersections. Thus `selected=iq256` means all output rows for that job map to the IQ256 wrapper branch, not that the report counted every fragment invocation or measured how long it ran. Reconcile expert totals across GU/Down and `sum(nt)` with CPU job/entry counters before interpreting it.
- **The hybrid variant guard is conservative and appropriate.** On non-hybrid CPUs the classifier uses `iq256_variant()` and removes the gather bit for formats without a gathered decoder. On hybrid CPUs it reports `worker-unresolved:-1`; this avoids claiming the caller's per-core gather decision for workers. `Iq256` branch identity itself remains resolvable, because it depends on process-cached ISA/threshold/flags. Down IQ4NL records only the VNNI bit. The header separately reports variant capabilities and the effective gather setting (`pool.cpp:801-843`). These distinctions should remain explicit in downstream reading; capability bits are not a report of variants actually used.
- **Disabled histogram is quiet, but the resolver refactor is not disabled.** The `STRATA_NATIVE_DISPATCH_HISTOGRAM` static toggle prevents begin/reset, job walks, and report output when off (`pool.cpp:762-776,816-818`; `generate.cpp:10404,11304`). However, moving branch selection into `native_gu_dispatch` / `native_down_dispatch` changes the always-used wrapper control flow even with collection disabled. The predicates and math are statically equivalent, but any per-fragment call/branch overhead or optimizer/codegen change is unmeasured. Keep the implementation unadopted until root completes parity and clean timing checks; “histogram off” is not a byte-for-byte baseline executable.
- **Enabled attribution perturbs existing timing boundaries.** The GU histogram walk occurs after timestamp `b` and before the caller's FF-quantization timestamp `c`, so it inflates the existing `ms_multi_q` interval even though it does not quantize. The Down histogram walk is after timestamp `d`; both walks are inside `run_split_multi_native`, so its enclosing dispatch/host elapsed timing may include them. The final report formatting happens after `decode_ms` is sampled and commit wait succeeds. The implementation report identifies the GU→quant timing contamination; callers must also keep outer host/request timing from the enabled diagnostic separate from clean performance evidence (`pool.cpp:859-875`; `generate.cpp:11296-11305`).
- **Reset/report scope is one `ExpertPool` object's successful serve decode interval.** `generate.cpp` calls begin at the per-request decode snapshot and report after the final commit wait; it reports accumulated exposures over all native CPU jobs in that request, including repeat layer/window use, not unique experts. It skips the report on earlier error returns. A later request begins by clearing the fixed array. No worker-side counters or synchronization were added (`generate.cpp:10401-10405,11299-11305`; `pool.cpp:770-776,816-846`). If future request execution becomes concurrent on the same pool, this mutable request array would need ownership/serialization; current serial request scope is assumed, not enforced by the histogram methods.
- **The print cap is fixed but not tiny in the theoretical type space.** The array has `2*65*(MAXT+1)` cells, with type 64 and nt 0 overflow buckets. The output is one record with nonempty cells only; current model types and nt values should occupy far fewer than 1,170 cells. Add a practical byte bound if these diagnostics are later exposed to untrusted/high-variability input; no expert IDs or raw event traces are emitted. `uint64_t` counts are ample for a normal decode request, but no saturation/overflow check exists (`pool.hpp:291-303`, `pool.cpp:827-845`).

## Default settings and static initialization

`native_histogram_enabled()` is a function-local static that reads `STRATA_NATIVE_DISPATCH_HISTOGRAM` once. An unset or zero value leaves `native_histogram_active_` false; the added `begin()` and `report()` calls return without touching the array or walking jobs. If enabled, counters reset once at request decode start. Environment/ISA dispatch settings keep their original lazy-static behavior in the shared decision helpers; the histogram's calls after phase completion use the same cached values as actual dispatch. The report queries GU type18's normal threshold, GU type21's IQ3S threshold, and Down type20's threshold; the same call sequence also captures CPU-effective branch enables. Since these settings are process static, a changed environment after first dispatch is intentionally not reflected. The target's non-hybrid Ryzen gather choice is exact from the caller; the implementation conservatively avoids that claim on hybrid systems.
