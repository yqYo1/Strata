## What the current GU scheduler and kernel actually do

`ExpertJobMulti.nt` is each expert's count of routed window tokens (`include/strata/kernels/cpu/pool.hpp:57-66`). In `run_split_multi_native` the native pool makes a GU phase with `mrows=nb*FF`, quantizes every token's FF intermediate serially on the caller, then a Down phase with `mrows=nb*H` (`src/kernels/cpu/pool.cpp:759-793`). Here `nb` is the current expert batch, `FF=640`, `H=2560` for the reviewed Qwen geometry. `phase_tasks()` returns the configured task count clipped by rows; the receipt's `--pool-tasks 6` therefore gives six tasks in these large phases. Boundaries are equal intervals in flattened expert-row space: task i owns `[mrows*i/mtasks, mrows*(i+1)/mtasks)`. The worker walks across expert boundaries, calls the row kernel for the intersection, and increments one shared atomic completion count per task (`pool.cpp:627-667, 699-735`). This is dynamic claiming of six broad ranges, not one task per expert and not one task per token.

That flattening hides useful cost structure. Each expert's range has the same row count, but its kernel processes `nt` activations per row. The native IQ3_S GU multi-token path decodes the same row's gate/up weights across all tokens, while the scalar fallback calls the dot product separately for each token (`src/kernels/cpu/native_expert.cpp:125-177`; AVX2 dispatch in `src/kernels/cpu/iq_avx2.cpp:465-496`). The multi-token path has a threshold (`native_gu_mt_min`, default 2), so per-row cost is not necessarily a linear `nt` multiplier: weight decode is amortized for multi-token groups. `STRATA_IQ3S_MT1` can also change the one-token kernel/rounding choice on a narrow CPU configuration; it must remain fixed during any comparison. The report must therefore model actual dispatch and `nt`, not equate submitted blob bytes or rows with work.

GU and Down also have different work maps. GU has 640 rows per expert and two projections (gate and up); Down has 2,560 rows and dispatches according to the layer's `d_type` (`native_expert.cpp:180-202`, `pool.cpp:638-664`). Some formats have an nt-batched multi-token Down kernel; others use per-token dot products. Serial FF quantization sits between the two pool phases and is currently a separate measured interval. Do not force GU and Down to share task boundaries or infer their costs from each other.

## Concrete candidate: measured-dispatch weighted tiles, only if the trace shows a tail

Round 12 already proposed `nt`-weighted boundaries; this audit narrows that proposal to the real kernel behavior. If worker-tail telemetry shows imbalance, retain the current output rows and kernel calls, but form a small row-tile list separately for GU and Down. Estimate each tile with a measured lookup for `(phase, actual kernel dispatch, nt bucket, rows)` rather than `rows*nt`: distinguish the one-token fallback from the nt-batched IQ3_S GU path and distinguish each Down dispatch. Give tiles to the existing atomic queue in descending estimated cost, or choose prefix boundaries by cumulative measured cost while retaining dynamic claims. The estimator may combine dispatch time, completed rows, and observed `nt`; it must be calibrated on these exact kernels and fixed machine/build. This is a conditional scheduling experiment, not a claim that weighted scheduling will help.

For GU, task boundaries may split at whole output rows; each row's packed weight begins at its own `gu_row` byte offset, so splitting a row interval does not require changing quant blocks or arithmetic. For Down, keep whole output rows as well, preserving the existing row kernel and one writer per token/output row. Keep each task's expert-local `(r0,r1)` contiguous and keep `nt`, activation pointers, format dispatch, FF activation quantization, and each row's accumulation order unchanged. Avoid a token-major schedule that invokes the row kernel once per token: it would discard the multi-token weight-decode reuse this path was designed to obtain. A finer row-tile count is only useful if its extra atomic claims and bookkeeping cost less than the observed tail; do not increase tile count by default.

Before implementing, add one bounded diagnostic to a root-owned comparison: for each phase and expert, record `nt`, selected kernel path, row count and tile IDs; per worker record claimed tiles, useful row work, phase start/end and final idle-tail interval. Keep this alongside per-request GU/quant/Down and whole CPU-pool time, plus physical decode latency. Use multiple fresh requests and compare current equal ranges against exactly one measured-dispatch policy with all flags, inputs and worker count held fixed. First confirm numerical parity of all heads, all 66 live-state parts, logprobs and MTP. Only continue if the measured phase tail tracks this cost estimate and the policy lowers the whole CPU critical path and physical decode latency beyond run-to-run noise. If worker finish times are already close, stop; do not introduce a more elaborate scheduler.

## External implementation references and limits

SGLang-JAX's EPMoE describes expert groups with token-count-derived group boundaries for grouped matrix multiplication; this supports representing variable group sizes explicitly, but is Pallas/TPU and not evidence for this AVX2 CPU pool ([SGLang-JAX EPMoE/GMM](https://github.com/sgl-project/sglang-jax/blob/main/docs/architecture/06-layers-and-attention.md#6521-epmoe--grouped-matrix-multiply)). llama.cpp's CPU pool uses shared atomic chunk claiming, a mechanism Strata already has; it is not a reason to replace the current queue ([llama.cpp CPU pool](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cpu/ggml-cpu.c#L3022-L3027)). KTransformers' CPU/GPU MoE study examines changing tokens per expert and reports results on a different multi-core Xeon/AVX-512 system; it motivates measuring actual expert counts, not transferring its speed claims ([SOSP 2025 paper](https://madsys.cs.tsinghua.edu.cn/publication/ktransformers-unleashing-the-full-potential-of-cpu/gpu-hybrid-inference-for-moe-models/SOSP25-chen.pdf)). No external result predicts this Ryzen 5 5600X, IQ3_S, or current build.
