## Finding

Most new `return false` sites are structurally routed through the existing `run_impl` and layer-major cleanup scopes. The notable new lifetime gap is narrower: the local host vector used as the asynchronous copy destination is freed if both the event wait and the fallback queue drain throw.

In POSIX `RepeatCapture::record` (`repeat_capture.hpp:65-70`), `host` is a local `std::vector<uint32_t>`. The code enqueues `queue.memcpy(host.data(), device, size)`, waits with `wait_and_throw()`, and on *any* exception calls `queue.wait()` then rethrows. If the fallback `queue.wait()` itself throws a synchronous/backend error before completion is established, that exception leaves the catch block and stack unwinding destroys `host`, even though the copy's use of its destination may not have retired. The prior drain-contract review established why a failed queue finish cannot be assumed to mean completion; the new observation here is that the backing allocation at risk is this newly introduced local vector. The existing `KvDrain` cannot extend its lifetime: it does not own `host`, and it runs only after the exception has left `record()` and destroyed its local objects.

This is an unproven rare backend-failure path, not an observed runtime fault. But the current catch path does not prove the destination survives an unclassified failed fallback drain. Do not label it fixed merely because normal event completion or normal `queue.wait()` is safe.

A concrete source-level correction is to keep the copy destination in an owner that outlives the call and can quarantine it when completion is unknown. On a fallback drain that returns normally, rethrow the original event error and release the vector normally. If that drain throws without a backend-specific completion guarantee, move the vector into a process-lifetime poisoned/quarantine owner (never reuse/free it while the process continues), mark capture/session poisoned and stop further queue use. A fail-stop that terminates without stack unwinding is another conservative option; a generic catch followed by ordinary local destruction is not. If the SYCL backend has a documented distinction proving the copy completed before the thrown event error, classify that result explicitly rather than treating every exception alike.

## Other new failure paths and caller ownership

- **Shape, budget, open, and allocation errors:** These happen before the host-vector copy is submitted. They can return through the capture lambda as `false`; already submitted compute work is still present, but no new readback destination is referenced. In layer-major mode `run_impl`'s function-scope `KvDrain` fences retained compute on an early return; outer `run_layer_major`'s `Restore` scope then fences compute/copy and finishes Stager before restoring callbacks, cache/residency, residual pointers and mode. Temporary `device_rows`/`layer_cache` outlive `Restore` by declaration order. In direct/non-retained mode, `KvDrain` still drains its selected/default stream. This mirrors the existing early-return structure and I found no new path that bypasses these guards.
- **`wait_and_throw()` before memcpy:** This call is outside the local `try` around event wait, but the capture lambda catches its exception and returns failure. No command has been submitted using this host vector yet. The event-wait specification treats asynchronous error reporting as a blocking wait; a synchronous/backend wait failure remains a general retirement uncertainty for the existing queue-owned compute buffers, already covered by R7/R8. It does not expose `host` to an outstanding memcpy.
- **File writes:** Serialization begins only after the copy event wait succeeds. A file-write exception can leave a truncated record, as the report already documents, but it does not leave a device access to `host`; the vector can safely be destroyed. File failure is surfaced by the capture lambda and early-return fences.
- **`std::vector` allocation failure:** The vector is constructed before queue submission, so a `bad_alloc`/`length_error` creates no outstanding readback using its storage. The capture lambda treats standard exceptions as diagnostic failure. If constructing/assigning `err` itself allocates and throws, the function-level exception path runs instead; the same outer fences apply, subject to the pre-existing destructor failure behavior.
- **Windows stub:** The explicit enabled-on-Windows `record()` throw occurs before any queue work by the stub. It is safe with respect to host destination lifetime and goes through the same existing cleanup path.
- **Queue drain failure in existing RAII:** `KvDrain`/`Restore` destructors can still terminate if waits throw. This is inherited from the base cleanup design and was analyzed in rounds 7–8; I do not count that generic condition as a new finding. For the new capture return, successful cleanup fences are sufficient to retire run_impl/layer-major backing. A failed fence is not a recoverable return and must not be made to look safe by catch-and-free.

`run_impl` capture returns (`prefill.cpp:3655`, `3870`, `3887`, `3932`, `3947`, `4117`, `5220`) are ordinary `false` returns inside its existing function-try-block. That unwinds local `StagerDone`/future scopes before `KvDrain`; `run_layer_major` immediately returns on a failed layer run, invoking `Restore`. `Prefill::run` then calls its existing `drain_pipeline` even when the layer-major call fails (`2335-2348`). Therefore no new capture-specific bypass of the caller's restoration or pipeline drain was found. This is source structure only; if one of those inherited drain destructors throws, cleanup still fail-stops as previously documented.

## CPU mock boundary

A CPU-only fake can validate the newly introduced control-flow contract without pretending to validate a SYCL queue. A source-level test seam could substitute a copy/wait provider and file sink, then inject: shape/budget/open errors before submission; host allocation failure; successful copy; async event error followed by successful drain; event error followed by a drain that reports unknown completion; and partial-write failure after successful copy. Assert that every non-copy error submits no readback; successful fallback drain preserves the primary error and releases the host vector after retirement; unknown completion quarantines the destination and prohibits subsequent capture/use; and file-write failure marks the record incomplete after the queue has retired the buffer. Also assert outer failure order: stop/join local issuers, retire applicable queues, then restore temporary layer/cache/callback state.

Such a mock can verify branching, allocation ownership and no-free-on-unknown-completion in the proposed abstraction. It cannot prove Intel SYCL's event/queue exception semantics, that a real backend failure leaves a command in flight, actual host-memory registration behavior, kernel completion, or that production queue routing matches the fake. A CPU test cannot establish GPU numerical validity or restoration of real graph consumers. Root's actual uniform build and CPU format/error tests remain the owner-controlled validation and are outside this audit.
