Installed ELF and libc facts

The installed package versions are binutils `2.42-4ubuntu2.10` and libc6 `2.39-0ubuntu8.9`. Installed `/usr/lib/x86_64-linux-gnu/gprofng/libgp-collector.so` SHA-256 is `1429fb2ca32905affd9a425efdb04d392efdf26d7118bf33c52281dfb3be614e`. The collector has DT_NEEDED `libc.so.6`, exports interposed `timer_create` entries for GLIBC_2.0, 2.2, 2.2.5, 2.3.3, 2.17, and 2.34, and exports its `setitimer` wrapper. It does not have ordinary undefined dynamic relocations for timer_settime/gettime/delete; those functions are obtained dynamically. The installed glibc 2.39 exports `timer_create`, `timer_settime`, `timer_gettime`, and `timer_delete` at GLIBC_2.34, with compatibility entries (e.g. 2.3.3/2.2.5). Therefore the active collector's 2.34 selection has an ABI-version match on this host, while its old-version fallback symbols also exist. Merely seeing old timer versions in the library is not evidence of a mismatch.

Upstream binutils 2.42 `gprofng/libcollector/dispatcher.c` has `init_interposition_intf()` resolve timer functions using `dlvsym` for the newest known GLIBC symbol versions and fallback versions; it chooses `RTLD_NEXT` when it finds the real `setitimer` there, otherwise `RTLD_DEFAULT`, and uses `dlsym` as a final fallback. `collector_timer_create`, `collector_timer_settime`, `collector_timer_gettime`, and timer deletion then invoke the resolved `__real_*` pointers via `CALL_REAL`, avoiding the collector's own exported application interposers for its internal timer. Public source links: [GNU sourceware binutils 2.42 dispatcher.c](https://gnu.googlesource.com/binutils-gdb/+/refs/tags/binutils-2_42/gprofng/libcollector/dispatcher.c) and [GNU sourceware binutils 2.42 profile.c](https://gnu.googlesource.com/binutils-gdb/+/refs/tags/binutils-2_42/gprofng/libcollector/profile.c). An independently browsable public source mirror is [binutils 2.42 dispatcher.c](https://raw.githubusercontent.com/rosco-m68k/binutils-2.42/master/gprofng/libcollector/dispatcher.c); it is not Ubuntu's downstream source package and is cited as a mirror, not as proof that Ubuntu applied no patches.

Why the same timer can pass libc controls and fail gprofng

1. **Different function pointer / loader scope is the main unresolved class.** The raw matrix called the process's ordinary libc symbols; gprofng reaches libc through `dlopen("libc.so.6", RTLD_LAZY|RTLD_NOLOAD)`, `dlsym(RTLD_NEXT, "setitimer")`, and versioned `dlvsym` selection relative to `RTLD_NEXT` (or fallback `RTLD_DEFAULT`). Another object in the target's global lookup scope could interpose one of these names or versioned timer symbols, or gprofng could select a different resolution scope than a direct helper. The smoke receipt does not retain the target environment's complete `LD_PRELOAD`/loader state, and the normal XML does not identify the resolved object/address. No evidence currently shows such an interposer exists; this is a falsifiable lead, not a finding.
2. **Initialization failure is collapsed before it reaches XML.** `profile.c::open_experiment` calls `__collector_ext_itimer_set(p)` and emits only `itimer could not be set` when the returned interval is <=0. `__collector_ext_itimer_set` returns a stored `itimer_period_actual`; it initializes to zero and is only overwritten from `collector_timer_gettime` after successful timer creation and arm. `collector_timer_create` logs errno only through debug output on -1; `collector_timer_settime` likewise. `collector_timer_gettime` returns -1 if its real call fails. Thus the single cerror 9 can represent real `timer_create` failure, real `timer_settime` failure, or a `timer_gettime` failure that made the returned interval negative. It is not proof that create or arm specifically failed. If `timer_gettime` succeeds but reports zero interval, then actual also remains zero; a 10 ms setting makes that unlikely absent a wrong timer ID / bad pointer / wrong implementation. The later disarm result is ignored by the initial-period calculation.
3. **The collector's own wrappers intentionally behave differently for application calls.** Upstream 2.42 `gprofng_timer_create` rejects an application SIGEV_SIGNAL/SIGPROF timer with EBUSY, and `_setitimer` reserves ITIMER_PROF/ITIMER_REALPROF (the SIGPROF paths). These rules do not apply to the collector's own setup because it calls `CALL_REAL` on its resolved function pointer. A test that invokes the interposed public wrapper under `LD_PRELOAD=libgp-collector.so` is not equivalent to the raw matrix: a SIGPROF `timer_create` should be intercepted/rejected by design. A useful collector-specific diagnostic must distinguish its internal call through `__real_timer_*` from public application entry.
4. **glibc symbol versions are supported in the installed pair.** Binutils 2.42's resolver attempts GLIBC_2.34 first; libc 2.39 exports that entry. The installed collector itself exports each old/new wrapper version; it is not statically linked to an unavailable timer ABI. A version-resolution defect remains possible only in the actual dynamic lookup/namespace or initialized pointer, not simply because “binutils 2.42 is old” or “libc is newer.”
5. **The source's return contract loses the failing call's errno.** A failed timer create returns the previous stored period, initially zero; failed arm similarly leaves it zero; gettime failure can set it to -1. All become the same XML cerror. This is enough to explain why the raw matrix narrows the fault but does not identify it.

ABI and initialization-order checks

The `timer_create` symbol wrappers are versioned and delegate application calls to `gprofng_timer_create(real_func, ...)`. Collector-internal setup first checks whether `__real_timer_create` is null, calls `init_interposition_intf()` if needed, then makes the actual timer call through the selected pointer. `init_interposition_intf()` resolves timer_create alternatives at GLIBC_2.34, 2.17, 2.3.3, 2.2.5, 2.2, then unversioned `dlsym`; timer_settime/gettime/delete use their supported version chains then unversioned fallback. The installed ELF exposes the expected wrapper versions and local libc has the preferred 2.34 symbols. If all resolution failed, a null internal function pointer would normally cause a fault rather than cleanly return timer errno; the smoke instead reached protocol DONE and collector exit 0, so a wholesale missing-pointer explanation is low confidence. Partial/wrong-scope resolution to a valid but unsuitable function remains possible.

The `gprofng_timer_create` helper in the 2.42 source uses an old-style function pointer declaration (`int (real_func) ()`) before forwarding the three POSIX timer arguments. Binutils 2.43/2.44 source changes this to an explicit prototype. On x86-64 SysV, the function is passed the same integer and pointer arguments in the same registers, and `timer_create` itself retains its stable C ABI; the older declaration is not, alone, evidence of the observed failure. Runtime ABI divergence would require a wrong function pointer or different object, not simply this source prototype. The installer's actual Ubuntu patch set was not available in the local sources; sourceware upstream should not be represented as exact Ubuntu source provenance.

The setup uses a SIGPROF timer and later installs/dispatches SIGPROF handling. The raw matrix demonstrates signal delivery to ordinary helper handlers, but cannot establish interaction between a collector-installed handler, target Python/runtime signal claims, the pause SIGUSR2 toggle, and timer startup. In the retained XML, the `cwarn id=213` value 12 is the separate SIGUSR2 pause-signal warning; it is not evidence about timer creation. The recorded error arises at clock module initialization before a `<profile>` schema/frame payload exists.

Root-owned harmless native target: diagnostic points

Root plans to run a no-model native collector target. To localize this without another raw API matrix:

- Under a debug collector build or temporary root-owned debug instrumentation, record for each internal `__real_timer_create`, `__real_timer_settime`, `__real_timer_gettime`, and disarm call: selected pointer, `dladdr` object path, selected GLIBC version (or fallback), immediate return and errno, input clock/event/tid/timer ID, requested timespec, returned `it_interval`, and final `itimer_period_actual`. Record the values only around the collector's internal `collector_timer_*` helpers, not around application wrappers.
- At resolver initialization record `dlflag`, whether `libc.so.6` NOLOAD succeeded, which `dlvsym` branch succeeded for each function, and whether pointers are null. This specifically distinguishes the valid ordinary-libc matrix from a wrong symbol scope or missing/incorrect function pointer.
- Compare the native target's collector log for `profile ptimer` and nonempty frame data with its normal exit. A collector process exit 0 and a completed target protocol are not a profile pass. Do not substitute a public SIGPROF timer call from inside the target as a probe: the wrapper intentionally reserves it.
- If pointers map to the expected libc 2.39 exports and all three calls return success/positive 10 ms, but the module still returns <=0, inspect `__collector_ext_itimer_set` stored-state/return ordering next. If pointer resolution is unexpected, test only a root-owned diagnostic change that pins the intended libc resolution; do not globally alter preload order or runtime state as a “fix.”

No profiling target or model is approved by this audit. The raw timer matrix rules out generic ordinary-user Linux timer support as the leading explanation. The next evidence needed is the collector's actual internal resolved addresses, per-call errno/results, and returned interval. No specific kernel incompatibility, glibc bug, or collector source bug is established.
