## Review result

The physical row slicing and score-width logic appear internally consistent for the current source path. For a chunk `[p0,p0+T)`, capture is enabled only on intersection with `[98304,98336)`, row pointers are offset by `(capture_first-p0)*width`, and row captures use the intersection length. `steps_host` is prepared from `qsa_step_fill` before device upload; `n_bid` is then the same host-side value used to compute the batch's `active` bound. Scores are copied synchronously after their batch score kernel and before scratch reuse, with exactly `n_bid+1` entries and a `<=m.max_blocks` check. Selected IDs use the corresponding per-row `kStepWidth`, checked against `m.cap`; step words are copied from that row's device step record. These avoid reading score padding. K/V/indexer/query/output row widths match the source allocation layouts in this path. The in-order queue copy/wait also makes each captured edge complete before host serialization.

Two concrete issues need correction or explicit bounds before treating the implementation as portable and request-attributable:

1. `repeat_capture.hpp` unconditionally uses POSIX-only headers and calls/flags (`unistd.h`, `geteuid`, `open`, `O_NOFOLLOW`, `O_CLOEXEC`, `O_NONBLOCK`, `fstat`, `write`, `close`). This source is compiled into the SYCL prefill translation unit, while Strata supports Windows as well as Linux. The Windows build cannot compile this header as written. Add an OS-specific implementation behind a small private-file sink interface (Windows `CreateFile` with no-follow/reparse-point and owner/ACL checks, bounded append/write/close), or explicitly compile the diagnostic implementation only for supported POSIX builds with a harmless disabled Windows implementation. Keep the enabled path's private regular-file and size guarantees equivalent.

2. The singleton mutex serializes records only within one process. The file format has no request/capture identifier, and record ordinals restart at zero on each process while append mode accepts existing files. If multiple request executions share a process, their records can interleave record-by-record; identical `p0,T,layer,phase` records cannot reliably be assigned to requests. The prose delegates request transitions to a controller, but the binary itself cannot establish that association. Add a caller-supplied capture/request ID to every record and a defined begin/end marker, or make the capture instance explicitly scoped to one serialized request and reject concurrent use. For reproducibility, require a fresh file (`O_EXCL` creation) or encode the starting byte offset and process/run ID; otherwise stale appended records are accepted as part of this run. A mutex does not provide cross-process serialization if two processes are pointed at the same path.

The buffer lifetime handling on asynchronous copy failure is sound in principle: the copy event is waited, and the catch path drains the queue before the local host vector leaves scope. `queue.wait_and_throw()` before the copy can fail without any copy using the destination. File write failure propagates as a diagnostic request failure, and partial records are explicitly considered incomplete. The destructor can only report close failure to stderr; a close failure after an otherwise successful request is therefore not reflected in the request result or a machine-readable completion marker. A final completion record/status or controller-side checked close is needed if successful-looking output must be distinguishable from a close failure.

## Budget and useful limits

For one capture of 32 physical rows, the three R snapshots over 13 layers cost `13 * 3 * 32 * 10240 * 4 = 49,152,000` payload bytes. At QSA layers 3, 7, 11, the K/V/indexer inputs cost `3 * 32 * (512+512+128) * 4 = 442,368` bytes. Query, q-indexer and attention output add `3 * 32 * (ZV+512+ZV) * 4`; with this source's `ZV=1280`, that is 1,179,648 bytes. Score payload is `4 * sum(n_bid(row)+1)` over the 96 captured QSA rows. Around the recorded pooled block 24582, this is about 9.44 MB. Device steps and IDs add `4 * sum(kStepCount+width(row))`, small relative to scores. Thus the expected total is about 60.3 MB decimal / 57.5 MiB per complete capture, approximately 120.6 MB / 115 MiB for two, plus 128-byte headers per record (roughly tens of KiB). This fits the 128 MiB cap with roughly 13 MiB margin if the stated 32-row, three-layer QSA schedule and widths apply. The exact request-sequence total is not proven by source inspection; larger active score widths, retries/repeated prefill calls, pre-existing file contents, or concurrent captures can exhaust it. The code correctly counts the existing file size and each record, so the controller must use a fresh file and preserve the explicit budget-failure result.

The fixed `[98304,98336)` window does not show an earlier transient difference outside the window. Capturing R at layer boundaries and the selected QSA edges can localize a repeat divergence but does not establish its cause if all captured values agree. Synchronous copies and queue drains can suppress timing-sensitive faults or alter issuer overlap; captured parity cannot prove ordinary unsynchronized-run parity. No request identifier, binary parser validation, or capture parity was tested.
