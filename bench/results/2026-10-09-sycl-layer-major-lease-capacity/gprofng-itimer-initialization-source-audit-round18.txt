Exact installed collector behavior and source mapping

Static inspection identifies `/usr/lib/x86_64-linux-gnu/gprofng/libgp-collector.so`; `dpkg-query` reports binutils `2.42-4ubuntu2.10`. The library exports the collector timer entry points, wraps `timer_create` symbol versions through GLIBC_2.34, and has a `setitimer` interposer. Its local disassembly of `__collector_ext_itimer_set` matches the upstream 2.42 source control flow below. The public upstream copy is [binutils 2.42 `dispatcher.c`](https://raw.githubusercontent.com/rosco-m68k/binutils-2.42/master/gprofng/libcollector/dispatcher.c) and [2.42 `profile.c`](https://raw.githubusercontent.com/rosco-m68k/binutils-2.42/master/gprofng/libcollector/profile.c). The installed binary's local symbols/disassembly and diagnostic strings corroborate the relevant control flow; the public source mirror is not the Ubuntu downstream source package itself. The Ubuntu binary's local symbols/disassembly are the exact installed-artifact evidence.

In 2.42 `dispatcher.c`, `collector_timer_create` constructs a `sigevent` with `SIGEV_THREAD_ID | SIGEV_SIGNAL`, `SIGPROF`, `sigev_notify_thread_id = gettid()`, and calls the real libc `timer_create(CLOCK_THREAD_CPUTIME_ID, ...)`. `collector_timer_settime` turns the requested interval in microseconds into a periodic `itimerspec` in nanoseconds and calls the real libc `timer_settime(timerid, 0, ...)`. `__collector_ext_itimer_set` creates the timer, arms it, queries the actual interval only on successful arm, then disarms it; if creation or arm fails while the stored actual period is still zero, it returns zero. This helper does not itself fall back to `setitimer`.

In `profile.c`, clock-module `open_experiment` parses the `p:` collector parameter, creates its thread-local key, calls `__collector_ext_itimer_set`, and logs exactly `itimer could not be set` and returns `COL_ERROR_PROFINIT` when the returned period is <=0. That is the narrow source path explaining the observed generic error. The error text does not preserve `errno` or distinguish `timer_create` failure from `timer_settime` failure: the dispatcher debug trace prints `errno` internally, but the normal XML cerror does not. On the failure path the collector returns the prior `itimer_period_actual` (initially zero), which explains why an underlying errno is not visible in the receipt.

The 2.42 `setitimer` interposer is a different interface. It forwards non-`ITIMER_PROF`/non-`ITIMER_REALPROF` calls and query calls to libc; it reserves `ITIMER_PROF` (SIGPROF) and `ITIMER_REALPROF` for gprofng, logs an override warning, and returns `-1`/`EBUSY` for an application's attempt to set either timer while collecting. Likewise, its `timer_create` wrapper rejects application timers using `SIGEV_SIGNAL` with `SIGPROF` using `EBUSY`, while passing other application timers through. These protections do not explain the collector's own initial POSIX timer setup: its internal path calls the resolved real timer function with `CALL_REAL`.

Linux API contracts and incompatibility evidence

The Linux man-pages specify `CLOCK_THREAD_CPUTIME_ID` as a timer clock (since Linux 2.6.12), and `SIGEV_THREAD_ID` as a Linux-specific signal notification aimed at a thread ID (`gettid`) in the caller's process. `timer_create` returns failure for invalid clock/event/thread ID (`EINVAL`), resource pressure (`EAGAIN`/`ENOMEM`), unsupported timer clocks (`ENOTSUP`), among other documented cases. `timer_settime` returns `EINVAL` for an invalid timer ID or invalid timespec and `EFAULT` for bad pointers. The collector's computed 10 ms request for `-p 10m` is normalized (positive seconds/nanoseconds), so a malformed interval is not supported by current evidence. `CLOCK_THREAD_CPUTIME_ID` plus `SIGEV_THREAD_ID` is an intentional valid Linux configuration, and Linux 7.0 is far newer than the API's documented introduction; this does not rule out a particular kernel config, seccomp policy, libc binding issue, or collector defect.

A separate `setitimer(ITIMER_PROF)` control has different semantics: it counts total process user+system CPU time across threads and sends process-directed SIGPROF. It is not equivalent to gprofng's per-thread POSIX CPU timers. A successful setitimer control would narrow the issue to the POSIX/per-thread path or collector binding, but would not prove gprofng's normal setup works. It must not be proposed as an automatic fallback because the collector reserves the interface and different timer semantics change sample distribution.

The Linux `timer_create(2)` documentation states timer count is limited by `RLIMIT_SIGPENDING` and documents errors/clock support; `timer_settime(2)` enumerates invalid ID/timespec and pointer errors. The gprofng user guide documents `-p` as a per-thread clock sample rate (10 ms default, here 10 ms explicitly) and does not describe a need for PMU access or ptrace. Therefore `perf_event_paranoid=4` and Yama `ptrace_scope=1` do not, by themselves, explain this launched-target timer initialization error.

Competing hypotheses (not established)

1. A seccomp filter, container policy, or other syscall mediation rejects the POSIX timer operation. Distinguish `timer_create` versus `timer_settime` and inspect the immediate errno; do not infer this from the kernel release.
2. The exact `CLOCK_THREAD_CPUTIME_ID` + `SIGEV_THREAD_ID` combination fails under the current kernel/runtime despite the documented Linux support, or the collector's `sigevent` data/target TID is incompatible with that runtime. A control matrix varying clock and notification target will isolate this.
3. The timer syscalls succeed in an ordinary process but gprofng's `LD_PRELOAD`/symbol-version interposition chooses an unexpected real libc entry point or the target's runtime changes signal/timer state during startup. Installed library symbol versions show wrappers exist, but no runtime binding trace was taken; this remains a hypothesis.
4. A timer resource limit or process-level policy blocks creation. `timer_create` documents `RLIMIT_SIGPENDING` as a timer-count bound, but there is no evidence of exhaustion in this short smoke.
5. Application signal use may conflict with SIGPROF after startup; however, it is not currently evidenced as the cause of the `itimer could not be set` cerror, which is emitted while the collector initializes its timer. The logged SIGUSR2 warning is a distinct signal.

Harmless root-owned probe that distinguishes the branches

After the separate protocol final-BYE drain race is fixed, use a tiny standalone CPU-bound C helper (no model, GPU, service, ptrace, PMU, privileges, or system setting changes) and have it record each syscall return value and `errno` immediately. Run controls separately in disposable child processes, using the same ordinary user/container launch context as the failed smoke:

1. `clock_gettime(CLOCK_THREAD_CPUTIME_ID)`; then create/disarm/delete a timer with exactly the collector's clock (`CLOCK_THREAD_CPUTIME_ID`), event (`SIGEV_THREAD_ID | SIGEV_SIGNAL`, SIGPROF), current `gettid`, and timer value (10 ms). Keep an SA_SIGINFO handler and a bounded CPU loop long enough to confirm one expiry only if create+arm succeeds. Report the exact failing operation/errno; always disarm/delete and exit.
2. Matrix controls change one variable at a time: thread CPU clock with ordinary `SIGEV_SIGNAL`; monotonic clock with `SIGEV_THREAD_ID`; monotonic clock with `SIGEV_SIGNAL`. These identify whether failure tracks the CPU clock, thread-directed notification, or all timer syscalls. Record `timer_create`, `timer_settime`, `timer_gettime`, and `timer_delete` results separately.
3. In a separate child only, try `setitimer(ITIMER_PROF)` for a short CPU loop and disable it before exit. Treat this as a legacy-interface control, not a gprofng workaround or equivalent-success criterion.
4. Finally launch only that tiny CPU helper under the same `gprofng collect app -p 10m` setup (unique disposable `.er`, no model) and record the normal collector exit, full XML cerror/cwarn, whether `profile ptimer` and nonempty frame data exist, and helper protocol. If the raw libc exact-control succeeds but the collector launch still logs cerror 9, focus next on collector symbol/interposition/runtime binding; do not claim root cause without evidence that localizes which call failed.

Do not use `strace`/ptrace attachment, alter `ptrace_scope`, change sysctls, raise limits, or infer a complete profile from target READY/DONE or collector exit 0. Keep the failed receipt/status intact; a successful helper smoke would qualify only the collector path, not validate profiling the Strata model or the protocol supervisor.
