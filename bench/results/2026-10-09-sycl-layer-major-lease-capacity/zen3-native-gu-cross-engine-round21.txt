## What the current Strata CPU path already fuses

The path is under the SYCL tree's CPU engine, not the generic CUDA `src/` path: `sycl/src/core/expert_source.cpp` collects missed experts into `ExpertJobMulti` entries and calls `ExpertPool::run_split_multi_native` (`:2782–2797`). In `src/kernels/cpu/pool.cpp`, native multi-token GU traverses flattened expert/output rows in mode 5 (`:631–654`), and `native_gu_rows` selects the format-specific row kernel. For the generic AVX2 IQ row kernels, `src/kernels/cpu/iq_avx2_rows.inl:31–57,154–165` decodes a weight block once, loops across `NT` activation rows, computes each token's dot, then applies sigmoid-gate times up in the same row function. Gate and Up remain two distinct weight rows/calls (`:162–164`); the shared activation is reused temporally, not held in one SIMD load across both dots. `native_gu_dispatch` in `src/kernels/cpu/native_expert.cpp:106–160` uses the AVX-512/AVX2 format path subject to CPU and flags and normally leaves `nt=1` to ggml (`native_gu_mt_min`, default 2). On the Ryzen 5 5600X target, treat IQ3_S `nt=1` as fallback unless the process's explicit IQ3S/dispatch flags actually select the AVX2 row path. Q2_0 has a separate pool branch, not this IQ row dispatcher (`pool.cpp:638–650`).

This matters when comparing other engines: Strata already merges the per-row Gate, Up, and SwiGLU result in one pool task. A proposal that merely fuses graph nodes or removes a second operator dispatch may not map to a missing cost here.

## New kernel hypothesis: verify high-NT register pressure before changing the NT tile

`row_dot<TY,NT>` keeps `accf[NT]` live across all weight blocks and creates `acci[NT]` for each block (`iq_avx2_rows.inl:34–55`). At `NT=8`, the source-level arrays represent sixteen YMM accumulators before the decoder's `g/sgn/sc`, Q8 activation `yv/ys`, and integer multiply temporaries. x86-64 AVX2 provides sixteen architectural YMM registers. This does not prove generated spills: the compiler can shorten lifetimes, spill selectively, or recompute values. It does make a spill check particularly relevant for NT=6–8 on this AVX2 CPU, separate from the paired-Gate/Up fusion pressure noted in R17.

Conditional experiment: only if the built histogram shows material native work at NT≥5, inspect the exact GCC/Clang-generated NT specializations and measure per-format row kernels for NT=1…8. If NT=6–8 show repeated spills in the block/token inner loop, compare the existing specialization with a token-chunked version (for example, two 4-token passes for NT=8). Keep each token's block order and scalar reduction order identical. The chunked variant necessarily repeats weight decode for each token group, so it trades fewer live accumulators/spills for extra codebook work; it can easily lose, especially for IQ3_S's scalar grid decode. Require exact native output parity and a repeatable reduction in isolated GU row time before considering a full-run comparison. A source-level register count alone is not evidence to change the kernel.

For the microbench, use the production pack's actual GU format and dispatch variant for each tested NT, not an IQ3_S-only synthetic. Record compiler/build/flags, cycles or time per row, retired instructions, spill loads/stores if available, and repeat samples. Also run the existing native parity comparison. On full inference, compare identical fresh requests and all established output/state/logprob/MTP gates; log whole decode latency and CPU phase counters with the known overlap qualification. Keep CPU affinity, worker count and CPU frequency policy fixed. Stop if no repeatable high-NT spill or no row-time win.

## Secondary scheduling/layout check: a narrow false-sharing edge

The current native pool splits phase rows using `g0=mrows*i/mtasks_`, `g1=mrows*(i+1)/mtasks_` and maps each interval back to an expert and row (`pool.cpp:631–637`). With Qwen's 640 Gate/Up output rows per expert, a task edge can split an expert at a row index that is not a multiple of 16. Each output element is a float, so adjacent workers can then write different words in the same 64-byte cache line of `SplitBufMulti::ff[t]`. This is only a possibility at task edges, not evidence of a bottleneck; there are at most `mtasks_-1` phase boundaries and most row work is inside the quantized dot. The histogram's expert/NT counts do not detect line sharing or worker completion tails.

If root later has per-worker task/tail telemetry and the CPU's coherence counters show material HITM/cache-to-cache traffic, test the same six tasks with edges rounded to 16 output rows within expert buffers, accounting for any resulting imbalance. Keep row math and ownership disjoint; do not increase task count by default. Compare cache-to-cache/HITM events and worker tails on the same CPU; test multiple exact-routing requests. If no coherence traffic or tail is visible, close this hypothesis without touching the scheduler. This is a new, low-priority falsifier, not a recommended change.

## Cross-engine implementations and limits

- **ik_llama.cpp fused MoE (closest CPU precedent).** Its merged PR #229 describes a graph-level `up`, `gate`, activation and product fusion. The author says the separate `mul_mat_id` calls repeat expert lookup, activation quantization and barriers; on CPU the DeepSeek-Lite run showed about 3–4% prompt and 1–2% token-generation gains. That is the author's result on a different model/build and not a Ryzen 5600X estimate. Strata's current native row path already combines the two projections and activation per output row, so the missing transferable unit may be reduced shared-input work, not another outer op fusion. [PR #229](https://github.com/ikawrakow/ik_llama.cpp/pull/229)
- **ik_llama Qwen IQ4_XS context.** The author reports a custom IQ4_XS Qwen3-30B-A3B run on Ryzen 7950X plus RTX 4080 and enables runtime repacking and fused MoE for CPU experts. This confirms that IQ4_XS and CPU expert fusion coexist in one practical configuration; it is Zen 4, a different model and code path, and the post does not isolate the fusion contribution. The reported numbers must not be mapped to the 5600X. [Qwen3 early comparison](https://github.com/ikawrakow/ik_llama.cpp/discussions/357)
- **S-MoE paired Gate/Up row dot (GPU analogy).** Its Metal kernel assigns a SIMD group to output rows, stages the input once, and describes `qrow_dot2` sharing `x` and a scale/offset sum across two dots. Its reported ~17% is an M4 Pro GPU microbenchmark with its own Q2/Q4 formats and layout. The reuse pattern is conceptually relevant, but Strata CPU's activation loads are likely cache-resident and its quantized row kernels have different dequantization math; this is supporting prior-art context for R17, not a Zen 3 speed claim. [S-MoE Metal kernels](https://docs.s-moe.com/v1/internals/metal-kernels.html)
- **Vec-LUT/vlut.cpp cache-aware tiling.** This work targets ternary I1/I2 formats and a converted LUT-centric weight layout, with cache-aware streamed lookup for parallel/batched inference. It shows that table layout and cache blocking can dominate when a kernel's LUT working set is large. Strata's IQ2/IQ3/IQ4 packed blocks and codebooks are different, and the active native model files are not in that layout; adopting the method would require a format-aware repack and correctness proof, not a loop-only tweak. It is a follow-up research lead only if measurements show codebook misses or decode overhead. [vlut.cpp design and supported layouts](https://github.com/OpenBitSys/vlut.cpp)
- **AMD Zen 3 constraints.** AMD's Family 19h guide is the proper microarchitecture reference for Zen 3; the 5600X product page identifies its Zen 3 generation and six-core/12-thread class. Use AVX2 assumptions, not AVX-VNNI or AVX-512. The guide is branded for EPYC 7003, so cache topology, memory channels and clocks still need the actual desktop CPU configuration. [AMD Family 19h optimization guide](https://docs.amd.com/v/u/en-US/56665), [Ryzen 5 5600X product page](https://www.amd.com/en/products/processors/desktops/ryzen/5000-series/amd-ryzen-5-5600x.html)

First establish from the root-built histogram how many jobs, tokens and rows each format/dispatch receives at every NT. It can prioritize which row specialization to inspect, but it does not prove selected worker execution time or load imbalance. If NT≥5 exposure is negligible, do not investigate chunking. If exposure is material, obtain compiler output for the actual AVX2 build and compare only the affected specialization with an identical-parity microbench. Keep the F16/activation format, per-layer expert formats, runtime flags, routing window, task count and affinity unchanged. A full inference run is warranted only after a component improvement survives repeat measurements and then must clear all established numerical gates. The reported 111.7–116.7 ms GU counters do not establish that this component is the end-to-end bottleneck.
