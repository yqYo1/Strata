## Active path identified from source and run evidence

The retained run environment sets `STRATA_PREFILL_ATTN_LAYOUT=1`; prompt chunks are 8,192 tokens and `STRATA_PREFILL_ATTN_BATCH` is absent, so source default is 32. The run messages contain no `prompt attention on XMX` notice. On the SYCL branch `qsa_prompt_attn_batch()` tries the opt-in prompt XMX helper and otherwise returns false; the prefill caller then dispatches the decode-attention variant. I therefore audit the run's reported/default decoder fallback, not an XMX kernel. The environment receipt does not explicitly include `STRATA_PROMPT_ATTN_XMX`; the missing XMX notice is the retained runtime evidence, and no XMX-use claim is made.

With INT8 KV, this path is `qsa_decode_attn_batch_variant(..., variant=1)` → `dispatch_chunk_variant<1>` → `launch_chunk_variant<KV_MODE=1, SG=32, TRANSPOSE_Q=true, QUERY_FAST=false>` → `attn_chunk_kernel<1,32,true,false>` plus `attn_merge_kernel` (`sycl/src/prefill/prefill.cpp:4026-4065`; `sycl/src/kernels/cuda/qsa_decode_attn.dp.cpp:817-847, 618-647`). It is one query × one KV head × one 64-cell selected-ID chunk per work-group, with eight 32-lane subgroups. `STRATA_PREFILL_ATTN_LAYOUT=1` selects this decoder layout variant; it does not select XMX.

At the first localized row, prompt chunk `p0=98,304`, row `t=24` is cell 98,328. The shape contract is page size 4, pool block 4, top-k 2,048 cells, and width `min(n_kv, 2051)` (`include/strata/kernels/qsa.hpp:94-139, 282`). Thus this query has `n_kv=98,329`, `n_bid=24,582`, width 2,051, and attention uses 33 chunks: 32 full chunks and a final three-cell chunk. The final cell is the only valid cell of the current partial four-cell block. This is a particularly useful causal-tail plus partial-attention-chunk probe. At the maximum query, 262,139, the selection remains width 2,051 and the final attention chunk likewise contains three cells.

For cap 2,051, `qsa_decode_attn_scratch_floats()` allocates 204,400 floats per query (33 × 24 × (256+2), plus 64 slack floats); the 32-row batch scratch is 26,163,200 bytes. `qsa_set_bytes()` and the actual carve use the same helper (`prefill.cpp:912-922, 1327-1335`; `qsa_decode_attn.dp.cpp:849-851`). Each per-query scratch stride reserves accumulator, max, and sum arrays for 33 × 24 heads. Layer-major chunk size is divisible by 32, so every attention batch in this run is full-sized; the scratch is reused between calls.

## Active-kernel audit: close hypotheses and checked cases

1. **Per-query scratch/lane or merge issue, conditional on identical attention operands.** In the active variant, `attn_chunk_kernel` offsets Q/IDs/steps and all three scratch planes by `query_index * scratch_stride`; the variant launch's group coordinates make query index, KV head, and chunk independent. For each nonempty slot it writes `part_m` and `part_l` for all 12 heads and `part_acc` for all 12 × 256 outputs. The merge launches after the chunk kernel on the in-order compute queue, picks `kvh=head/12`, `head_in_group=head%12`, and writes each output dimension once (`qsa_decode_attn.dp.cpp:130-180, 314-355, 572-595, 839-847`). The offsets and stride fit the helper's allocation on inspection. If pre-attention Q/IDs/K/V operands are identical but merged attention differs, the active lane/barrier path is the next useful target; current source review found no obvious duplicate-writer or uncovered-output interval.

2. **Partial last chunk or stale `part_acc`, strongest narrow kernel check at cell 98,328.** For the 2,051-cell row, chunk 32 has `n_here=3`. The kernel initializes every `srow[0..63]` to a valid row or -1, places -FLT_MAX in score slots for invalid cells, exponentiates only cells below `n_here` with a valid row, and loops over values only for `c<n_here`. All three cells in this chunk are live; its max/sum/accumulator must be compared. For queries with no cells in a later chunk, the early return writes `part_m=-FLT_MAX` and `part_l=0` for all 12 heads while leaving `part_acc` untouched; the merge explicitly skips a slot whose max is -FLT_MAX. That reuse is intentional and statically guarded, not an uninitialized read on this path. At the target long row, no chunk is empty. Keep a direct assertion/check for all 33 slot markers and final-three-cell accumulators in the debug comparison rather than proposing scratch zero-fill.

3. **Tail, causal width, and cell-to-page address.** The selector's current partial block has weight one at row 98,328, and its +1e9 score bias forces the current tail cell into the selection when `n_kv%4 != 0` (`qsa_select.dp.cpp:32-74, 109-113`; `qsa_step_fill` in `qsa.dp.cpp:1082+`). The selected IDs are cell IDs. The attention kernel reads `page_table[cell/4]`, then addresses `[page][kv_head][cell%4]`; for this fresh identity stage, cell 98,328 is page 24,582, slot zero. Width 2,051 is strictly below `n_kv`, so there is no suffix ID consumption; output accumulation loops only over the row width and valid mapped rows. No source-only off-by-one or physical-row overrun is apparent at this location. Host/stage correctness is covered by the other round14 audit; this report does not reassign that ownership question.

4. **Lane/subgroup reduction and query transpose.** Variant 1 has required subgroup size 32. `TRANSPOSE_Q` writes source dimension `d` to shared index `(d%8)*32+d/8`, then each lane reconstructs its eight consecutive query values while `load8_q8()` reads the matching eight INT8 key codes and one half scale. The per-lane eight-product sum is reduced with XOR offsets 16,8,4,2,1; the 32-lane max and sum use the same subgroup helper. Cell scores are written by lane zero; barriers separate query/row staging, score/probability reuse of `sp`, and accumulator reads. Static review did not find an uncovered score lane, use-before-barrier, or subgroup-width mismatch in the selected variant (`qsa_decode_attn.dp.cpp:21-50, 131-180, 214-313`). If an operand-identical replay still changes, compare per-head/per-chunk `part_m`, `part_l`, `part_acc`, then merged attention to isolate this arithmetic/reduction path.

The saved state only proves persisted QSA KV/indexer bytes for ordinals 0–1 are equal. The earlier QSA layers' transient `q`, selected IDs and attention outputs are absent. Their selection can differ while the persisted KV/indexer arrays remain equal; if so, that difference can alter later hidden rows and explain ordinal 2's first persisted KV difference. This is the highest-value reason to keep attention in the investigation. Conversely, if IDs differ, selection is upstream of this selected-attention kernel; if Q/IDs and selected K/V match but attention differs, the variant kernel becomes directly implicated.

Record hashes for equal ranges and the first differing element only. Use the same immutable stage/selection operands when replaying the attention kernel, and add any queue wait/hash only in the debug path. No full prompt dump or ordinary-path synchronization is needed.

Interpretation: different Q/IDs/selected bytes means the mismatch precedes this kernel; equal operands but different last-slot or merge data means active kernel or scratch lifetime; equal merge but different projected residual moves the boundary downstream. For early short-width rows, separately verify the -FLT_MAX empty-slot markers if needed, but do not prioritize them over the observed saturated-width row.
