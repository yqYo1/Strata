## Controller ownership and VTune control

The proven controller `run_owned_upstream_v0141_full256k_v2.py` uses `OwnedGdb` plus a PTY: the controller reads/writes raw protocol bytes on the PTY master, while GDB owns the inferior and its stdio. Do not attach VTune to that inferior: the software Hotspots collector uses ptrace-based access and a tracee has one ptracer. Use a separate baseline launch owned by VTune, with no GDB in that process tree.

VTune CLI supports launch-paused collection and independent result-directory actions: start `hotspots` with `sampling-mode=sw`, `-start-paused`, `-duration=unlimited`, unique `-result-dir`, and `-data-limit=64`; issue `-command resume`, then after the profiled request `-command pause` or `-command stop` against that same result directory. A stop terminates the collection, and a pause leaves the target running; neither is the engine shutdown protocol. The engine must separately receive `QUIT\n` after the request is complete and the collection has been stopped/paused. Then wait for the VTune launcher and target to exit normally. Do not send QUIT before the response's `DONE` and captured 64th `T`/`LP` pair.

**Raw stdio is the unresolved integration detail.** The installed CLI config/docs confirm target-launch collection and control actions, but do not establish that the VTune CLI's standard streams form a clean byte-transparent channel to the target. Its own messages may share inherited streams. Therefore the existing Python line parser must not simply be pointed at `Popen(vtune, stdin=PIPE, stdout=PIPE)` without proving stream separation. A safe controller must own a dedicated target stdin/stdout transport (e.g. explicit inherited FIFO/FDs or a PTY relay) while sending VTune control commands through separate short-lived subprocesses with stdout/stderr redirected to bounded logs. Before any model run, statically review that relay and validate stream isolation on a harmless target; if a transparent target channel cannot be demonstrated, do not run the model under VTune. Record raw target stdout separately and never parse VTune diagnostic text as protocol.

The launch must start paused before model initialization. Wait for engine `READY`, reproduce the canonical 32K control state, issue `RESTORE <qualified-session-path>` and require `RESTORED ...`; only then resume collection and immediately issue the exact 64-token control request. After `DONE`, pause/stop collection, send engine `QUIT`, and wait. This excludes model load, prefill, and restore from samples. Keep it as diagnostic evidence; software sampling perturbs execution and is not a speed comparison.

## Numerical and process gates

Use only the baseline binary/hash and the same model, MTP, pack, environment, and serve arguments recorded in r2. Reuse the r2 `control32k-before` fixture and its `control32k.session.bin` (written by `SAVE` and verified by r2), not regenerated prompt text. Start a fresh engine and issue `RESTORE` on that saved 32,831-token state, then submit the exact 64-ID continuation from `resume32k-reference`; the control prompt is 32,768 tokens and `max_new=64`; compare every generated token ID, every per-token five-entry `LP` record, four reported head samples, decode/state checks, and MTP offered/accepted counters against the qualified r2 record. The r2 baseline records 64 generated IDs and MTP counts `[46, 51]`. Require restored position/resume and `RESTORED` receipt to match the saved session before sampling. If any exact result differs, stop collection, `QUIT`, preserve the failed record and raw streams, and do not call the sample a baseline profile.

Controller record should include resolved VTune and engine argv, executable/build/receipt hashes, boot ID, monotonic times, result directory, every VTune command/exit code, READY/RESTORED/GEN/DONE protocol offsets, raw stream hashes, request/LP/ID/MTP comparisons, and PID plus `/proc/<pid>/stat` start ticks for the VTune launcher, target, and every discovered descendant. Discover descendants recursively from `/proc` and refresh while active; PID alone is insufficient because it can be reused. Bound total wall time with a finite supervisor deadline (baseline controller used 10,800 seconds, protocol timeout 5,400 seconds); use a smaller explicit 64 MiB cap for VTune data and 64 MiB combined text logs. Flush receipt/events frequently. On a protocol, collector, numerical, timeout, or size failure: stop collection if possible, request `QUIT` if the target is alive, wait a short fixed grace period, then signal only recorded live processes whose start ticks still match (TERM, then KILL after another fixed grace period). Record each signal and final identity/state; never blanket-kill by executable name or process group. Preserve a terminal failed receipt and all bounded evidence, and confirm the complete process tree has exited before another run.

## Host and collector limits

The local VTune 2026.4 `config/analysis_type/hotspots.cfg` explicitly rejects software sampling if neither TPSS nor ptrace is available and rejects limited ptrace scope. The existing system state recorded in round 13 is `perf_event_paranoid=4`, `kptr_restrict=1`, with no root authorization; do not change sysctls or permissions. Software Hotspots is the plausible user-mode path because it samples with a timer and can expose active user-space stacks/hot functions; it cannot explain PMU cycles/cache misses/bandwidth, blocked-thread wait time, kernel execution, or GPU time. If its ptrace preflight fails, stop without trying hardware Hotspots, root, kernel sampling, or attaching to the GDB inferior. AMD host support and stack quality remain unvalidated here; treat collection as exploratory, not authoritative.
