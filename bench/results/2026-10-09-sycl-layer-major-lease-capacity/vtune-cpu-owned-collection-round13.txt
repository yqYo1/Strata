# VTune CPU hotspots collection design — round 13

## Finding

Do not attach VTune to the currently GDB-owned engine. VTune 2026 software Hotspots is the viable non-root sampling mode to investigate, but it is not a second read-only observer: Intel documents a Linux agent embedded in the target, timer interrupts/signals (usually SIGPROF), and the local 2026.4 Hotspots configuration explicitly checks ptrace availability and rejects a restricted ptrace scope. The existing `OwnedGdb` keeps its inferior under GDB/MI control. Linux ptrace has a single tracer per tracee; an attach attempt risks conflict with the debugger, independent of hardware PMU access. Given `perf_event_paranoid=4`, `kptr_restrict=1`, no root permission, and the prohibition on changing sysctls, avoid hardware/driverless PMU collection and do not alter system settings.

## Collection design for root after the active gate closes

Run only when the full 12-request correctness controller has completed and all owned measurement processes are gone. Use the existing exact binary/source (`6cdf81078128488e5797afb9e92824b7ebe51124`, binary SHA `66d5bee60f4bbdb6f710b395ae11a1e6e14a61e04db417bcd6092d4f7956377e`) in a separate profiler-owned diagnostic process. Have VTune launch it with software Hotspots in paused mode; do not attach to a live PID. Example shape (same already-qualified engine arguments, private unique result directory):

```sh
/opt/intel/oneapi/vtune/2026.4/bin64/vtune \
  -collect hotspots -knob sampling-mode=sw \
  -start-paused -data-limit=64 -return-app-exitcode \
  -result-dir <private-run>/vtune-result -- <same frozen strata argv>
```

Keep the run paused while model initialization and READY occur. Restore the already-qualified 32K state, wait for protocol confirmation, then use VTune’s documented control action to resume this result (`vtune -command resume -r <private-run>/vtune-result`) immediately before the controlled decode request. Stop collection promptly after its completion (`vtune -command stop -r ...`); graceful-stop the engine through the same protocol and wait for both VTune and its launched target to exit. Use the controller’s finite wall deadline and a 64 MiB VTune data cap. The report format and `-start-paused`, `-data-limit`, `-return-app-exitcode`, result-dir, resume, and stop actions are in the installed CLI message files and Intel 2026.0 CLI docs. This avoids sampling the large model initialization and yields samples from the requested CPU decode interval. It is a new normal launch under VTune, not a resume/attachment of the GDB-controlled process; the exact target output, LPs, MTP and full-state comparison still gate correctness.

A necessary constraint is that the agent itself may use ptrace to initialize the user-mode collector. The local config checks for this, so the profiler-launched process should be its own child (and therefore subject to the local Yama policy as a child), rather than asking VTune to seize an unrelated target. If even that collection fails its ptrace check, stop; do not change `ptrace_scope`, privileges, or attach the profiler to the live debugger inferior. Intel’s software collection uses per-thread timer samples rather than PMU events, and it has higher overhead (about 5% at the default 10 ms interval per the guide). Use it for function/control-flow and active-thread hotspot triage, never as a clean speed result. It cannot establish hardware cycles, cache-miss/bandwidth causes, kernel time, GPU time, or exact wait/critical-path durations. With `perf_event_paranoid=4`, hardware event-based Hotspots is unavailable to this non-root run; `kptr_restrict` also makes kernel-symbol investigation unsuitable.

## Target/profile details and limits

Static inspection of the actual ELF shows it is not stripped and has `.symtab`, but no `.debug_info` or `.debug_line` section. `nm -C` resolves names including `ExpertPool::run_split_multi_native`, `native_gu_rows`, `act_quant_any`, and `expert_pool_dispatch_multi`. A software Hotspots report can therefore be useful at function/symbol level; do not promise source-line attribution. Do not rebuild with debug flags for this collection because the request is to profile the frozen tested binary. The installed binary is `/opt/intel/oneapi/vtune/2026.4/bin64/vtune`; installed versions span 2026.0–2026.4. Intel’s release/system requirements say general non-PMU software collection supports compatible non-Intel x86-64 CPUs, while EBS is Intel CPU-specific, and caution that non-Intel instructions may not be analyzed correctly. Interpret AVX2 samples as statistical attribution and verify readable call stacks; do not treat VTune’s AMD instruction-level diagnosis as authoritative.

The target already has a diagnostic `STRATA_DECODE_TIMING` line and phase counters, but phase sums include host dispatch/synchronization and overlap GPU work (round 7). Keep those counters alongside the VTune sample window; do not add them arithmetically or infer phase wall from sampled percentages. User-mode samples only show statistically sampled active instruction paths; a hotspot view is not a replacement for per-thread completion-tail timings or physical request wall time. Do not tune based on a profiled throughput sample.
