# CPU MoE heterogeneous expert work — round 12

## Decision

Do not add a scheduler or kernel yet. The current pool already uses a dynamic atomic queue; changing task count alone is not a new mechanism. One distinct, testable candidate remains: make each queued row range reflect per-expert `nt` work, then compare its worker-tail distribution against the current equal-row ranges. First establish whether the measured CPU phase is on the critical path and whether `nt` creates a material tail.

## What this code does

Reviewed candidate T (`src/kernels/cpu/pool.cpp`) and `src/core/expert_source.cpp` statically. `expert_pool_dispatch_multi` groups CPU misses by expert and constructs one `ExpertJobMulti` per distinct expert (`expert_source.cpp` around 3310–3351); each has a variable `nt` token count. For each native pool batch, `run_split_multi_native` fixes one `NativeFmt`, runs GU, quantizes FF activations serially on the host, then runs Down. The queue assigns dynamic claims, but each claim is a contiguous, equal-sized interval in a flattened row space: GU rows are `nb*FF`; Down rows are `nb*H`. The worker walks across expert boundaries and each expert’s row kernel processes its entire `nt` token group. Thus current work per row is not necessarily constant when `nt` differs. Format is uniform within this batch; format heterogeneity is between layers, not between its experts.

The current timing record supplied by root passed all four 32K mathematical comparisons, but it is diagnostic evidence, not a speed/adoption result. The reported last-request CPU time is about 140.4 ms/window; plan (~0.16 ms) and job-build (~0.08 ms) are small nested counters, not additive independent costs. Do not infer from those figures alone that row scheduling is the bottleneck: phase counters include dispatch/synchronization and CPU intervals overlap GPU work. The previous round-7 report’s separate GU/quant/Down timings came from a different baseline and must not be joined to this request as if they were one sample.

## Candidate: `nt`-weighted task boundaries, with dynamic claiming retained

For each phase, form a prefix-work map over experts: each expert contributes its phase row width (`FF` for GU, `H` for Down) multiplied by its `nt` (and optionally calibrated per-format/per-kernel cost only if observations show meaningful differences). Partition the cumulative estimate into the configured number of row ranges, while preserving contiguous rows within an expert and current output ownership. Workers still claim tasks dynamically through the existing queue, so fast workers can take more work; only task boundaries/weights change. This targets an unequal cost per row caused by different token multiplicities, rather than another blind granularity sweep. Keep the serial quantizer unchanged and treat the two phase row spaces independently; GU and Down have different dimensions and no direct producer-consumer range identity.

A close upstream analogue is the CSR-style group-size schedule in SGLang-JAX’s EPMoE documentation: expert token counts define variable group boundaries, and the grouped matrix operation handles groups without padding. That is Pallas/TPU, not a CPU AVX2 quantized kernel; it supplies a design precedent only, not a performance prediction ([SGLang-JAX architecture, EPMoE/GMM](https://github.com/sgl-project/sglang-jax/blob/main/docs/architecture/06-layers-and-attention.md#6521-epmoe--grouped-matrix-multiply)). vLLM’s EPLB documents skewed token counts and logs average/max expert load, but balances experts across EP ranks, not workers inside one CPU pool; changing expert placement or routing is inapplicable to this exact local computation ([vLLM EPLB](https://github.com/vllm-project/vllm/blob/main/docs/serving/expert_parallel_deployment.md#expert-parallel-load-balancer-eplb)). llama.cpp’s CPU graph pool uses a shared atomic `current_chunk` for matmul chunks (`ggml_threadpool_chunk_add` in `ggml/src/ggml-cpu/ggml-cpu.c`); that supports dynamic chunk claiming as a known mechanism, but Strata already has this property ([llama.cpp CPU pool source](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cpu/ggml-cpu.c#L3022-L3027)).

### Preconditions and risks

- First capture per-expert `nt`, per-phase row dimensions, task boundaries, and per-worker task completion/tail for real verify windows. If `nt` is nearly uniform or the queue drains evenly, stop here; no new scheduler is justified.
- Work estimate `width*nt` is only a first approximation. IQ3_S, IQ4_NL, and Q2_0 dispatches can have different cost per operation, but each pool batch has one `NativeFmt`; gather a per-layer calibrated model only if measured per-kernel work/row differs. Avoid tuning against theoretical FLOPs.
- Finer or irregular boundaries add metadata and can split work into tasks too small to amortize claim/barrier cost. Preserve format/block row alignment and each output row’s single writer. Do not reorder arithmetic inside a row or alter token routing.
- Small decode batches may leave fewer than five useful ranges. Weighted partitioning cannot create parallelism where routed jobs/rows do not provide it.

### Root-owned comparison

Use exact same restored 32K inputs, fixed MTP/configuration and the existing qualified baseline/candidate pair. Compare current equal-row partitioning with one `nt`-weighted policy; do not simultaneously sweep worker counts or task count. Capture per-window distributions of `nt` (including min/median/max and count by 1/2/3/4+), `nb`, GU/Down row ranges, tasks/worker, per-worker useful time and finish time, pool GU/quant/Down, wait/plan/jobs, CPU time, and physical decode time divided by emitted tokens. Record identical measures across multiple fresh windows/requests and distinguish debug-counter-instrumented runs from clean speed samples. Preserve all-head, 66-state, LP, and MTP comparison gates. Try 256K only after 32K shows a stable critical-path gain and after confirming the full-context capacity path.

Proceed only if equal-row tasks show repeatable `nt`-correlated worker-tail imbalance and weighted boundaries shorten whole CPU-pool time and physical decode beyond run noise. If CPU-work falls but decode does not, it was overlapped and is not a useful optimization. If phase counters are high but per-worker finish times are balanced, seek elsewhere (kernel throughput, memory bandwidth, GPU/host wait) rather than another scheduler.

## Other implementations and limits

KTransformers’ SOSP’25 study explicitly varies tokens assigned to each expert and reports CPU MoE throughput by token count, while noting CPU memory bandwidth and thread synchronization limits; its measurements use a 36-core Intel Xeon, AMX/AVX-512, DeepSeek-V3 and different quantization, and cannot predict 5600X IQ3_S results ([paper](https://madsys.cs.tsinghua.edu.cn/publication/ktransformers-unleashing-the-full-potential-of-cpu/gpu-hybrid-inference-for-moe-models/SOSP25-chen.pdf), §2.2). This reinforces measuring at actual `nt`, not transferring their performance numbers. vLLM’s skew/load-balancing approach changes expert-to-device placement and may affect routing/runtime; it must not be applied to alter selected experts or outputs in this exactness-sensitive local decode path.

Other recurring ideas—generic task-count/grain sweep, serial quantization parallelization, row splitting, format weights without cost observations, identical GU/Down worker-range affinity, and expert-token regrouping—are already covered by prior reports or corrected in the root round-11 review. No new code, build, test, GPU, profiler, or service work was performed here.
