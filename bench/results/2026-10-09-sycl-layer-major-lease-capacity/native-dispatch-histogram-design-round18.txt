## Call path and what a histogram can truthfully count

`expert_pool_dispatch_multi` builds `ExpertJobMulti` entries for CPU-missed experts with each expert's exact `nt`; the native path calls `ExpertPool::run_split_multi_native` (`src/core/expert_source.cpp:2782-2796`). For each expert batch, the pool sets GU rows to `nb*FF`, runs six configured flattened row tasks in the current `--pool-tasks 6` diagnostic, quantizes FF activations on the caller, then sets Down rows to `nb*H` and runs Down (`src/kernels/cpu/pool.cpp:759-793`). Worker tasks may split one expert's rows into multiple fragments, but every fragment for that expert has the same format and `nt`. There is no per-expert format or `nt` counter in the existing receipt.

A request-scoped histogram can be formed on the same caller that owns `mjobs_` by iterating the expert jobs once at each existing GU/Down phase boundary. Use fixed-size counters keyed by phase, GGML format, exact `nt`, and dispatch label; accumulate over layer/window calls and print one bounded summary with the existing opt-in request timing output. Count experts, routed token rows (`nt`), output rows (`FF` for GU; `H` for Down), and, if useful, the number of task/expert intersections computed from the same flattened bounds. Do not log expert IDs, each task execution, every row, timestamps, or per-thread samples. A per-request delta line avoids the pool's process-lifetime counters being mistaken for one request. Because pool methods already return only after the phase drain completes, this adds no worker barrier or queue operation. Caller-side classification adds a small loop over the already-built jobs and fixed counters; it does not require per-row/per-task clocks or atomics.

The classifier must report two different facts:

- **Format/ISA eligible:** a row kernel supports this format and the CPU/build exposes the required ISA, without yet applying branch precedence or disable/threshold flags.
- **Selected path:** the exact branch that `native_gu_rows` / `native_down_rows` or the Q2 wrapper will take after runtime flags, `nt` threshold, ISA checks and branch order. Do not call an eligible expert a row-kernel execution if the wrapper falls through to ggml.

For unambiguous selected-path labels, use a small pure dispatch-decision helper shared by the host histogram and the existing wrapper, or otherwise mirror every branch predicate in one reviewed function. The row-kernel bodies and math remain untouched. Include a resolver consistency check in the CPU-only unit/parity validation before relying on counts. This is important because a separate hand-maintained histogram predicate could silently drift from dispatch.

## Exact dispatch inputs to capture

The format and `nt` alone do not determine the selected branch. Record resolved process settings and CPU/build capabilities once with the request: `STRATA_IQ_MT_MIN` (default 2), the special `STRATA_IQ3S_MT1` rule, `STRATA_NO_IQ256`, `STRATA_NO_IQ512`, `STRATA_IQ256_GATHER`, `STRATA_NO_AVXVNNI`, `STRATA_KQ256`, and `STRATA_NO_IQ4NL`, along with usable AVX2/AVX-512/AVX-VNNI and whether the CPU is hybrid. Several are read into function-local statics, so use the values actually resolved by the process, not a later fresh `getenv()` interpretation (`native_expert.cpp:106-161,178-199`; `expert_layout.cpp:202-267`). This is a compact settings header, not environment dumping.

For the reviewed pack, GU formats are IQ3_XXS type 18, IQ3_S type 21, IQ2_S type 22, and IQ4_XS type 23 across 48 MoE layers. The native GU decision order is: the opt-in Q4_K `KQ256` branch for type 12 and `nt>=2`; otherwise the IQ512 path if its support/CPU/enable predicates pass; otherwise the IQ256 path if its support/CPU/enable predicates pass; otherwise ggml's `vec_dot` fallback. For the four actual pack formats, the special Q4_K branch is irrelevant, but keeping it in the shared resolver prevents the general native path from being misclassified. The IQ row-kernel threshold is `native_gu_mt_min(type)`; default is 2, with the IQ3_S one-token special case gated by multiple flags. Therefore a type can be ISA-eligible but select ggml at `nt=1`.

When IQ256 is selected, also label the implementation variant: scalar decode, gathered decode, and VNNI combination as applicable. `iq256_variant()` uses `STRATA_IQ256_GATHER` when explicitly set; when unset it calls `cpu_gather_fast_here()`, and VNNI depends on compiled support and CPUID (`iq_avx2.cpp:383-384,458-463`). On the current Ryzen 5 5600X target, which is non-hybrid and lacks AVX-VNNI, the default selector has one consistent scalar/gather answer for host and workers; explicit `STRATA_IQ256_GATHER=1` can change it. On hybrid CPUs the default gather choice can differ by worker core, so a caller-only resolver cannot claim exact per-core selected variant without worker-local observations. In that case, report ISA eligibility and the unresolved per-core variant separately rather than treating caller's core as every worker.

Down needs its own branch classifier. `pool.cpp` sends native Q2_0 Down through `q2_rows_any` directly; this is outside `native_down_rows` and selects its AVX-512 or AVX2 implementation from CPU support (`pool.cpp:651-656`; `expert_layout.cpp:348-352`). Other native formats call `native_down_rows`, where Q5_1/Q8_0 may take opt-in KQ256, IQ4_NL type 20 may take the AVX2 multi-token path when `nt>=mt_min` and `STRATA_NO_IQ4NL` is absent, and all remaining cases use ggml's dot (`native_expert.cpp:178-202`). Histogram labels must keep Q2, IQ4_NL and generic fallback distinct. Do not infer Down from GU type or count FF quantization as either phase.

## Bounded collection and validation gates

Keep the histogram opt-in and request-scoped. A fixed array keyed by the small known GGML type set (or bounded type id), `nt=1..MAXT`, phase and a small enum of selected branches is sufficient; no unbounded map keyed by expert, no text row trace, and no profiler dependency. Resolve settings once, add counts only on the caller's already-executed per-request job walk, and print a single line/compact record after request completion. If classification uses task intersections, derive those intersections from `mrows`, `mtasks_`, and the same `[mrows*i/mtasks_, mrows*(i+1)/mtasks_)` ranges as `drain`; this verifies the number of dispatched fragments without adding worker-side updates. The histogram counts dispatch exposure and workload shape; it is not elapsed time.

Before interpreting it, the root-owned check should verify that for each completed phase the sum of histogram expert counts equals the number of CPU expert jobs, GU and Down job counts match, and the sum of `nt` equals the CPU-routed entry count for those jobs. Validate branch labels against the shared decision helper for every format/`nt` pair and runtime flag combination in existing host parity/CLI coverage; keep `STRATA_IQ_MT_MIN`, gather, ISA-floor and disable flags explicit in the receipt. Then run the opt-in summary on several already-controlled fresh 32K requests and ensure it does not alter all-head/state/LP/MTP comparisons or protocol completion. The report should stay compact and once per request.

A histogram still cannot show which branch consumed the most time, whether an eligible SIMD path was actually invoked on a worker if variant selection is core-dependent, whether six equal tasks left a worker tail, whether CPU work was hidden by GPU work, or whether it changed physical decode latency. Do not derive a weighted scheduler from counts alone. A branch's large row/token count only establishes exposure. To establish a bottleneck later requires an independently qualified attribution method or a controlled isolated kernel comparison plus clean end-to-end timing. The current rejected profiler attempts do not authorize a substitute profiler or altered host settings.
