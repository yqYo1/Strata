## Conclusion

The latest closed model-root-v4 attempt establishes the runtime tuple at `ready_before_gen`: `libigc.so.2.41.5+1788943183` (SHA-256 `40badd8f1ee80ac844a8947f5e91e5654fbcd851caefe343b0e5ec4ce4d1b123`), `libigdfcl.so.2.41.5+1788943183` (`ece8bcd533a44cc1684c1f24eeeca3302e4d19307a806fad5f1b83171f9fc1c3`), and `libopencl-clang2.so.22.1` (`02ba9fb0f16b7f02c012095c46f8053c4bc20f9b5bde3028eedff6dcfed94bfe`). The receipt shows READY and GEN, then `RuntimeError('aggregate owner log cap')` after GEN: `complete=false`, `passed=false`, `model_normal_close=false`. It is not a successful computation and says nothing about whether the builtin was fixed. The prior startup error excerpt remains the evidence of the unresolved call; the current receipt fixes the prior missing IGC/FCL mapping provenance.

The narrowest verifiable provider distinction is a **bundle boundary inside IGC core**, not a demonstrated version mismatch: IGC v2.41.5’s source builds the OpenCL builtin module, embeds its `OCLBiFImpl.bifbc` as `_igc_bif_BIFBC_122`, and the mapped `libigc` ELF has both `_igc_bif_BIFBC_122` and `_igc_bif_BIFBC_122_size` symbols (bundle size `0x1327ccc`). The mapped `libigdfcl` separately has `DT_NEEDED libopencl-clang2.so.22.1`; `libigc` itself has no such dependency. Thus the source says the candidate provider is packaged with the exact mapped IGC core, while OpenCL Clang is a separate front-end dependency. Static `strings` found no literal failing symbol in any of these three binaries, which is inconclusive for embedded/compressed/bitcode content. This narrows the unresolved case to whether that exact function exists in the embedded IGC BIF bundle and whether the failing module’s link path consumed it. It does **not** prove either omission or failed selection.

## Source-to-binary boundary

The official [IGC v2.41.5 BiFModule CMake](https://github.com/intel/intel-graphics-compiler/blob/v2.41.5/IGC/BiFModule/CMakeLists.txt) unconditionally adds the prerelease Matrix subdirectory. Its OpenCL BiF build globs `PreRelease/*.cl`, builds the builtin bitcode, and depends on the BiF cache/build-pack target. The [Matrix generator CMake](https://github.com/intel/intel-graphics-compiler/blob/v2.41.5/IGC/BiFModule/Languages/OpenCL/PreRelease/Matrix/CMakeLists.txt) runs `IBiF_matrix_generator` post-build. Its [README](https://github.com/intel/intel-graphics-compiler/blob/v2.41.5/IGC/BiFModule/Languages/OpenCL/PreRelease/Matrix/README.md) identifies `IBiF_matrix.cl` as hand-coded implementations and the generator as the compile-time generator of matrix loads/stores; the generated header is not checked into source and is generated when IGC is built. The official [Linux BiF CMake](https://github.com/intel/intel-graphics-compiler/blob/v2.41.5/IGC/BiFModule/linux/CMakeLists.txt) embeds `OCLBiFImpl.bifbc` under `_igc_bif_BIFBC_122` in a static BiF library. These sources, plus the mapped `libigc` ELF symbols, show the provider’s packaging locus and confirm the overall bundle exists in that binary. They cannot show the exact specialization’s presence in its contents.

Static `readelf -d` on the mapped files showed `libigdfcl` needs `libopencl-clang2.so.22.1`; the exact `libigc` and `libigdfcl` build suffixes match. The process mapped the `/usr/local` 2.41.5 files, not the installed Ubuntu `/usr/lib/.../libigc.so.2.40.13+0` alternative. The mapped ELF `SONAME`s are `libigc.so.2` and `libigdfcl.so.2`. There is no evidence here that the failed link selected the distro 2.40.13 library or an unintended OpenCL Clang SONAME. Static package/ELF facts cannot establish which provider object was attached to the module link.

## Discriminator and limits

The single high-value discriminator would be an exact function-symbol inventory of the actual `OCLBiFImpl.bifbc` embedded in this mapped `libigc`, compared with the unresolved post-resolution module reference and its link diagnostics. If the bundle lacks the generated local PackedA definition, the build’s provider composition/generation is implicated; if it contains the definition but the module link still reports it missing, the provider selection/link path is implicated.
