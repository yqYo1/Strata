# Native prefill batching and the first decode after a 32K prompt

Date: 2026-10-11. Read-only source review, scoped to the supplied published source worktree at HEAD `0740b43488d812117f021ccbe4bd0e15d223f955`, its prefill-to-token transition, and prior committed reports/receipts. This adds the decode interpretation to earlier native-batch call-path and service-bound reports. No run, source edit or performance inference was performed.

## Main source finding: the recorded knob is absent from published source

A full text search of the production `src/` and `include/` source at the supplied published worktree found no read of `STRATA_PREFILL_NATIVE_DEQUANT_BATCH`. The recorded OFF/ON values in the 32K v6 receipts (0/1) are environment evidence, but alone they do not prove that this named switch selected different code in that source tree.

The production prefill file does contain a distinct setting, `STRATA_PREFILL_GROUP_GATHER`. In the streamed expert caller it enables grouping only when `stream_all && use_mmq && lay.native` and the group fits the API maximum. Its `flush` waits on the final streamed copy, calls `gather_native_group`, falls back to the existing per-expert gather on refusal, and marks held ring slots used after the gather. This is not the same switch or candidate path as `STRATA_PREFILL_NATIVE_DEQUANT_BATCH`: the earlier candidate review describes the latter as native format with `!use_mmq`, and grouping GU/Down dequant calls. The 32K census records MMQ disabled across all 288 layer/chunk rows, so the published `STRATA_PREFILL_GROUP_GATHER` branch would be ineligible there.

The historical candidate implementing `STRATA_PREFILL_NATIVE_DEQUANT_BATCH` is separately archived under the batch source candidate and its patch. Its branch changes the prefill native GU/Down gathering/submission work only; it does not alter attention, KV math, decode MoE dispatch, MTP policy, token sampling, decode kernels or cache hit/refill policy. The 32K receipts pin fa3 plus an uncommitted source diff and mark `source_uncommitted=true`; their recorded `c5cfa...` prefill source pin differs from the published worktree's current `src/prefill/prefill.cpp` hash `c2f624...`. Therefore the 32K OFF/ON records cannot be relabeled as measurements of the published HEAD's behavior. Main should keep the historical candidate provenance and published source provenance separate, and resolve the exact source/binary relationship before using the knob as a causal treatment.

## What can carry over into the first decode

In the generate path, `Prefill::run` synchronizes its compute, expert-copy and KV-copy streams before returning. It also drains any pipeline successor. Once it returns, the driver refills any cache slots lent to prefill, synchronizes queued refill copies, restores the residency table, then starts the token loop. The 32K diagnostic argv uses `--no-prefill-borrow`, so that specific run configuration should have no lent-slot refill work. The `Prefill` object itself remains alive through the token loop; its destructor calls `release`, which synchronizes its streams and frees its owned buffers/events at scope exit. There is no prefill-specific cache-recovery or decode graph-selection branch keyed by the native-batch variable in the published source.

Even if the historical prefill candidate actually changes grouped submission, the first decode immediately after prefill can differ indirectly. The prefill path has just driven GPU clocks, temperature/power state, device cache contents and host/driver scheduling; source-level batching can change the timing and spacing of that work. Prefill workspaces also remain allocated while the token path runs. Where a run lends cache slots, the explicitly timed refill before token decode is another carry-over path; that does not apply to the supplied `--no-prefill-borrow` configuration. Persistent SYCL caching was disabled in the recorded controller environment, but that does not eliminate GPU data-cache, filesystem page-cache, thermal, clock or host scheduling state.

These are state/carry-over effects around the prefill-to-decode boundary. They do not show that a decode kernel or decode dispatch improved. The existing 32K pair has one short generated sequence per arm (16 tokens) and one prefill followed by that decode. Its ON decode time of 2258.7 ms versus OFF 2599.6 ms is a single diagnostic observation per arm with a different prefill history. Both records explicitly set `performance_eligible=false`; the delta is not evidence for a decode-kernel change or decode-side adoption. A faster prefill can also change the waiting interval before the first decode, so a separately measured prefill duration does not remove this confound.

## Minimum decision and next measurement

Keep prefill and decode decisions separate. First resolve whether the historical `STRATA_PREFILL_NATIVE_DEQUANT_BATCH` implementation is present in the exact binary/source pair being tested. For the current experiment, use the balanced v2 pair plan already owned by Main and require at least three independent closed OFF/ON pairs (the current v2 proposal has four). Preserve every pair and correctness/fault result. Report prefill phase time separately from the post-prefill decode interval.

If the question is whether prefill batching affects *the first 16 decode tokens after this 32K prompt*, the minimum useful measurement is those same at-least-three independent matched pairs, with identical model/input/settings and a complete 16-token output in each arm. Record each arm's decode aggregate plus its first-token and remaining-token timings if the controller can capture them without changing the decoder; keep pair ordering balanced. Label the result only as a post-prefill carry-over comparison. Since the decoder code and dispatch are unchanged, even a repeatable difference would describe the cold decode state induced by the preceding prefill path, not justify adopting a decode kernel.

If a future change actually modifies decode math, dispatch or cache policy, test that change directly under an identical prefill/setup and decode state. Use at least three independent matched measurements, same decode token sequence/context and cache/residency policy, strict output/logprob and health/fault checks, and separate first-token cold versus subsequent-token/steady-state results. No extra measurement beyond the 32K pairs is needed to make a decode-kernel adoption decision for the current prefill-only change, because no decode code change is present to adopt.

## Evidence status and limits

Confirmed by source text: the production knob-name mismatch; the separate `STRATA_PREFILL_GROUP_GATHER` condition and gather/slot-release path; synchronization at the end of `Prefill::run`; cache refill before the token loop when slots were lent; and scope-exit release of prefill-owned resources. Existing receipt evidence confirms 32K OFF/ON environment values, strict finite PASS, 16 outputs, performance ineligibility, and no-prefill-borrow argv. The related prior reports already cover the candidate's prefill-only call path, ring/window lifetime, and need for quiet paired prefill measurements; this report does not repeat their window-size or component-performance analysis.

Not confirmed: that the batch flag is consumed by the exact binary used by the diagnostic receipts; any decode-kernel speed effect; a causal carry-over effect; stable first-token latency; or the result of the proposed balanced v2 campaign. The current source review is not a runtime result or adoption qualification.
