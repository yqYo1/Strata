## Why this differs from the unresolved startup specialization

The earlier error came from the runtime's background preload path that enumerates all registered kernel IDs and requests executable bundles, including candidates which model dispatch may never call. `STRATA_PRELOAD_KERNELS=0` suppresses that sweep, but does not disable JIT for kernels actually submitted later. Therefore the v6 PASS establishes that the selected runtime work for this n64 diagnostic could compile, execute, drain and produce the expected strict16/T/LP5 outputs with this mapped stack. It does not establish that every registered specialization compiled, that the old reported `Kernel<2>`/`PromptAttnMma` source entries were selected, or that every occurrence of the failing internal builtin was resolved. The receipts contain no chosen MMA shape index or per-kernel launch list; they cannot label an individual kernel from the former preload error as unused. The best supported distinction is between *the actual n64 path completed without all-ID preloading* and *the full set of registered images remains unqualified*.

The receipts also differ from the earlier failing build binary and source-diff identity. The successful v22 build and v6 model run share their exact new host executable and the explicit-zero preload change. This resolves the prior source/runtime map gap for the successful run, but does not prove a particular module image or template was used.

## Source conditions that can be reached at longer input

`mma_gemm.cpp` selects the first supported shape in fixed order S0 `(8,16,16,SG16)`, S1 `(8,8,16,SG8)`, S2 `(16,16,16,SG32)`, subject to reported matrix combinations and `groups_layout_fits`; a later `by_shape` dispatch instantiates that selected kernel. The shape decision is device/type/layout based, not selected by input length. Thus longer T does not by itself imply a new shape, and n64 success does not certify all S0/S1/S2 variants. The model receipts do not log the selected index. `Kernel<S>` still uses local joint-matrix A loads; S2’s `packed=false` field describes that kernel’s B/layout family and is not enough to rule out the IGC internal `PackedA` lowering discussed in the earlier reports.

A distinct T-dependent branch is `mma_gemm::k_slices`: it returns one slice for `T<64`; at `T>=64`, it may split K only if the product has fewer than twice the reported compute-unit count in tiles and enough K. The 63-position v6 prefill cannot exercise that split path. A 2049-token prompt has 2048 batched positions and crosses the T threshold; whether the split actually occurs depends on the per-layer matrix tile counts/device CU value. The split reuses the selected `Kernel<S>` specialization and adds a reduction path; it is not evidence that another S index is selected.

The more important sequence-length boundary for sparse attention is in `qsa_selection_width`: `min(n_kv, idx_top_k + idx_block - 1)`, with `idx_top_k=2048` and `idx_block=4`, so width is `min(n_kv,2051)`. For 2049 input tokens, the latest query has `n_kv=2049`, still identity selection. The first positions with sparse width occur at `n_kv>=2052`; a 2049-token request therefore does not yet reach that sparse-selection regime. A 32K prompt does. It uses six prefill chunks at the 6144 chunk size and has query rows at nonzero starting positions; within them selection IDs are capped at 2051 and become sparse. This expands work/data and chunk-loop exposure, but the selection-width change is data/branch behavior, not by itself a new matrix-template specialization.

`qsa_prompt_attn_batch` can launch `PromptAttnMma` only through its portable branch when `!xmx_available(f16)`, valid QSA geometry/IDs/steps/page table and positive cap hold, the device reports `(16,16,16,SG32)`, local memory suffices, and the pools match the supported format. For the model's INT8 KV, the relevant local MMA choice is `launch_mma<kI8,kI8>` when its K/V pools/scales exist; if the enabled PTX path is built and its local-memory requirements pass, a PTX alternative may be chosen instead. `STRATA_PROMPT_ATTN_OLD` or a false API return falls back to decode attention. These gates are independent of the observed n64 finish; the v6 receipts do not expose their values. At 32K the same format/geometry gates may remain true while query positions/data differ, so a successful n64 request does not qualify the long-context QSA path.

## Evidence required for the next boundary

For 2049 OFF, distinguish input prompt length 2049 from QSA sparse threshold: source predicts 2048 batched positions and identity QSA selection through the last position. To claim the new T>=64 split was selected, the run must capture selected shape, tile count, CU count, and computed `ns>1`; the receipt's strict completion alone proves correctness of the resulting requested calculation, not which shape/slice branch ran. For 32K, also require evidence of all six chunk starts and QSA selection width/format, plus normal QUIT, strict before/after health and complete output checks. Continue to keep context capacity, actual visited positions, and full-context qualification separate.
