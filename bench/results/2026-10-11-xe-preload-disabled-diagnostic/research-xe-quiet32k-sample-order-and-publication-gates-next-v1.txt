## Review concerns and limits

The controller defines same-index pairing correctly but does not set or enforce the execution order of the planned campaign. Main must orchestrate it. A fixed OFF-then-ON order for every index would confound the arm comparison with position in the campaign, device temperature/clock drift and caches shared across sequential processes. Each arm is a fresh process, but first-use JIT/driver and filesystem cache state can still differ between early and later observations. `SYCL_CACHE_PERSISTENT=0` and independent processes do not establish that all first-use/cache effects are absent. The engine phase timer excludes mapping polls and the implementation note acknowledges observation CPU/I/O/cache costs are not calibrated. The controller therefore captures meaningful phase observations but cannot by itself remove campaign-order effects or make them a performance qualification.

The minimum design change is to make Main's resolved qualification manifest state the full sample order, with at least three distinct index pairs and balanced/counterbalanced OFF/ON arm order across pairs (or an explicitly stated fixed order if Main chooses to treat order as a limitation). Store the planned order in every record and reject an arm run if it does not match that plan. If warm-up is chosen, specify the same finite warm-up procedure for both arms and exclude it from samples; otherwise label the campaign as cold/first-use-sensitive and retain order for analysis. Do not add automatic retries or silently discard outliers. Preserve prefill and decode as independent outcomes, with all per-pair values available to Main before any aggregate decision.
