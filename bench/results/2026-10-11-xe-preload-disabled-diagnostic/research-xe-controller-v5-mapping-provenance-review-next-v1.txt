## Assessment

The capture is substantially more useful than the earlier runtime-only library census. At `READY` before `GEN` and after completed `GEN`, it records selected `/proc/<pid>/maps` rows, resolved path, opened-file device/inode/size/timestamps, full-file SHA-256, ELF GNU build ID, and an `original_runtime` classification. It now includes candidate IGC/FCL/OpenCL-Clang/IGA/GMM libraries separately from SYCL/UR/ZE/UMF runtime libraries, and rechecks identity at repeated points. It fails closed for deleted or mismatched selected files, unsupported ELF layouts, missing/multiple distinct GNU build IDs, and exhausted budgets. These are valuable safeguards.

The strongest remaining caveat is semantic: this is a bounded sample of selected file-backed mappings, not a complete process library map, and the map rows are read once before the selected files are opened and hashed. PID/start-time checks establish that the same process identity persists; they do not establish that every saved mapping row remains mapped throughout the potentially long hash pass. The capture also discards a partially built snapshot when any selected path fails and its generic failure labels do not say which path or stage failed. Thus a failure is visible and the run remains failed, but the detailed per-file cause may be hard to act on.

## What the capture proves and how

- It reads at most 2 MiB of maps text, requires at most 8,192 lines, and selects at most 64 absolute-path entries by basename: core `libsycl`, `libur_`, `libze_`, `libumf`; additional `igc`, `fcl`, `opencl-clang`, `iga`, `igdgmm`, `libc.so`, and `ld-linux` names. Deleted selected mappings fail instead of disappearing silently. Other mapped DSOs are not reported, so `additional_process_mappings` means “additional selected matches,” not all extra libraries.
- It preserves every raw six-field mapping row for a selected path, including address range, permissions, file offset, device, inode and pathname. Rows are grouped per pathname. For each path it resolves the pathname, opens the canonical target read-only with `O_NOFOLLOW`, compares every maps-row inode/device against `fstat`, hashes the opened file, parses its ELF64 `PT_NOTE` segments, then checks before/after fd stat and current canonical-path stat for matching device, inode, size, mtime and ctime. The row-to-opened-file identity match makes the hash/build-ID attribution meaningful at the maps-read instant and prevents silently hashing a replacement file.
- The parser accepts ELF64 in either byte order, requires 56-byte program headers and at most 256 of them, caps aggregate PT_NOTE payload per file at 1 MiB, and accepts GNU type-3 build IDs of 1–128 bytes. It requires one distinct GNU build-ID value. This is adequate for the expected Linux 64-bit shared-library set, but it intentionally rejects other ELF forms and unusual/no-build-ID DSOs.
- `mapped_identity()` compares the current `/proc/<pid>/stat` start ticks to the direct child identity before/after capture and around file reads; the run-level record also has boot ID. The owner helper anchors the unreaped session leader and uses pidfds for owned processes. The mapping helper itself does not use a pidfd and checks start ticks, not state/executable or session fields. Start ticks strongly reduce PID-reuse risk, but the mapping helper can accept a same-start-time zombie; `/proc/<pid>/maps` could then be empty and the generic function would mark an empty file set complete. The READY path subsequently validates the expected runtime set, which catches this there; the after-GEN capture has no analogous nonempty/core-set assertion.

## Races and parser/path edge cases

1. `/proc/<pid>/maps` is opened and read once. The code then hashes files sequentially, checking process start ticks but not rereading maps or confirming each row still exists. If the process `dlclose`s/unmaps a selected library or changes mappings between the maps read and the end of hashing, the snapshot is a valid identity check for the original point-in-time row/file pair but not proof the file remained mapped at snapshot completion. The before-GEN/after-GEN phase tags make the intended sampling point clear; they do not close this within-snapshot race. For an actual loaded-library claim, a final maps recheck and selected-row dev/inode comparison would strengthen it.
2. `/proc/<pid>/maps` encodes whitespace and some special path characters with octal escapes. `split(None, 5)` correctly retains the remainder as one path field, but the code does not decode those escapes before `Path.resolve()`. Ordinary system library paths have no such characters; a selected library in a path containing escaped whitespace can fail strict resolution. This should be reported as a bounded-capture failure, not silently normalized to a different pathname.
3. `resolve(strict=True)` and file open occur after the initial map read. The opened fd and row dev/inode checks make replacement races fail closed; final `stat_identity(canonical)` also detects many changes to the named file. An in-place content change while hashing should normally alter mtime/ctime and fail the final stat comparison. This is stronger than hashing the path alone.
4. The ELF reader checks class/endian, program-header entry size/count, per-read file bounds and note-size limits, but not every ELF header invariant (for example ELF version, machine, or extended program-header count). Unsupported/malformed files fail by validation/`struct`/I/O error. This is acceptable for evidence gathering if those errors retain stage/path detail.

## Budgets, deadlines and I/O cost

The per-path ceiling is 512 MiB; there are at most 64 selected paths; map text is capped at 2 MiB/8,192 rows; aggregate note data per ELF is 1 MiB; aggregate mapped-file reads across snapshots are capped at 4 GiB. The full file is read once to hash it and then header/program-header/PT_NOTE bytes are read again with `pread`, and the same mapping-read budget is shared by `ready_before_gen`, `after_gen`, and a possible after-GEN retry. That makes the actual byte budget bounded and visible but can exhaust sooner than the sum of unique file sizes suggests. A retry after a partially consumed failure may immediately fail the same aggregate budget.

Each hash chunk and each note/header read calls `mapped_identity(..., poll)`. In model interaction, `poll` invokes the owner's process/resource/deadline checks and the GPU-dump check, so long sequential captures are charged to the diagnostic's 500-second model wall and 900-second whole-run wall budgets. A single blocking filesystem/proc read, `stat`, or path resolution is not interruptible by those checks; the 1 MiB read chunks bound ordinary file reads, and the target paths are local system libraries, but there is no separate snapshot deadline. Reading and hashing these libraries during a diagnostic can add CPU/storage contention and warm file cache; the run is explicitly diagnostic and `performance_eligible=false`, so its timing should not be treated as a clean performance sample.

## Failure retention and control-flow behavior

`capture_maps()` first records `{complete:false, requested:true}`. The detailed `mapping_snapshot()` object remains local until every selected file and the final process identity check succeeds. If anything fails, no partial `files` dictionary, last pathname, maps row or parser stage is copied into the record. The exception still propagates as `primary_model_failure` with a `model_failure_phase`; generic messages such as `mapped path inode/device identity`, `stable mapped file stat`, or `one ELF GNU build-id` identify the failed check, but not the path that failed.

At READY/pre-GEN, a capture failure is preserved as the primary failure, then the handler attempts cooperative QUIT and bounded exit. At/after completed GEN, an incomplete after-GEN snapshot triggers one retry; if that also fails, `unavailable_error` records the retry exception. It then sends QUIT and waits, preserving the provenance failure rather than converting the run to success. This is a good fail/close policy and avoids signal-based teardown for a completed request. Successful snapshots are saved to `mapping_snapshots`; original runtime entries go to `observed_libraries` with identity consistency enforced across phases; selected compiler/driver extras go to `additional_process_mappings`. The original runtime comparison keys intentionally omit `mapped_rows`, allowing load address/segment rows to differ between phases while keeping path/hash/stat/build ID stable.

Actionability would improve if failure handling retained a bounded partial result and fields such as `failed_path`, `failed_stage`, and the generic reason before re-raising. Also distinguish structural completion from “expected runtime mapping set present,” and reject an empty/zombie after-GEN snapshot. These are review recommendations only; no change was made.
