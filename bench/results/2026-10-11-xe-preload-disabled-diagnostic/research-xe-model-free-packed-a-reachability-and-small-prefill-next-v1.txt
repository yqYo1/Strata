# Model-free reachability of the PackedA local-load JIT failure

## Scope and provenance

Read-only source review at the local fa3e20e842fbed6986a69bade8afe3edabedee07 source revision (commit author yqYoi; this is the yqYo1/Strata work, not a claim about MistVVK upstream). Relevant source files were read with `git show` from the local immutable object. No build, test, GPU query, profiling, service change, Git mutation, or source edit was performed. This note addresses route reachability only; it does not change the earlier provider-gap conclusion.

## Existing no-model routes

`tools/test_prefill_dense_gemm.cpp` (`prefill_dense_gemm_parity`) invokes the production `strata::prefill::Gemm` API for synthetic FP16 and BF16 inputs, including a one-row case `(T=1,N=32,K=32,ldy=32)` and five larger/tail shapes. It requires `STRATA_NO_BLAS=1` and `STRATA_MMA=1` at the target's CMake configuration (target definition in root `CMakeLists.txt` around lines 618–634); at runtime the own XMX route still requires hardware eligibility and the `xmx_gemm_ok` alignment/stride predicate. The test prints `xmx_gemm_ok`, own path and production path, but those strings do not identify the chosen shape index. The fixed `mma_gemm.cpp` chooser tries S0, S1, then S2; `Kernel<2>` is only instantiated/launched when that chooser selects S2. In the reviewed source S2 is the packed-A local-fragment joint-matrix specialization. Thus this existing test can reach the failing mechanism conditionally, but its current output cannot prove S2 was selected. `mma_shape_is(q,m,n,k,sg)` invokes the same chooser and is the narrow source-level shape witness; a small harness should report the exact successful tuple / chosen index alongside each test call before claiming target-kernel coverage.

The dense test's terminal proof is stronger than a launch: it checks each production `Gemm` completion (`stream_sync`), downloads and checks outputs/guards, drains the device before releasing allocations, and only then prints `... OK`. If the runtime raises the strict build error, the test must exit nonzero before `OK`; if the completion drain itself fails, its fail-stop path deliberately exits before releasing storage. A `FAIL` or process exit alone says the probe did not pass; preserve the error and determine whether the failed phase was module build, launch, or drain.

`src/kernels/qsa_prompt_attn_parity.cpp` is another model-free route: it synthesizes FP16/INT8/Q4 KV pools and calls production `qsa_prompt_attn_batch`; the defaults are context 32768, 2048 queries, five repetitions. The route returns false when shape/pools/device gates fail; on Intel's `!xmx_available(f16)` branch, eligible FP16 pools call `launch_mma<kF16,kF16>`, which constructs `PromptAttnMma` and its local joint-matrix loads. Successful coverage therefore needs the correct device/format/local-memory and joint-matrix shape predicates, and a true API return is not itself completion when a non-null stream is supplied. The parity test subsequently calls `par::sync`, reads outputs, compares numerical checks, and prints `FAILURES: 0`; those checks plus process success distinguish completed execution from mere submission. Q4 may explicitly SKIP on a device without a supporting route, so a skip is not coverage.

## Actual prefill and small-N distinction

In `src/prefill/prefill.cpp` QSA prompt attention is attempted once per prompt chunk unless `STRATA_PROMPT_ATTN_OLD` is set; a false return falls back to `qsa_decode_attn_batch` in groups of `m.attn_batch`. This is a real fallback that avoids `PromptAttnMma` for that attention call. But it is not selected just because N is small: the return decision is based on QSA head/pool/device/local-memory gates, not a documented small-N threshold. With the environment override it is deterministically bypassed. The small-N dense path is also not guaranteed to avoid `Kernel<2>`: row count T alone does not establish chooser index, and the chooser evaluates device shape and layout eligibility. Avoid claiming any small-N prefill completed under the JIT failure unless the run's strict completion evidence exists.

The test binaries initialize the shared runtime before their target call; startup/eager module compilation can fail first. Therefore a failure before target-specific output is not evidence that a parity route exercised the exact kernel. The decisive observation is a run that records the selected S2 witness (or the QSA eligible branch/target launch), reaches its checked completion and correctness gate, and records the strict build error status if it does not. For production prefill, require the request-level strict drain and successful completion, not just token/launch progress.

## Minimal useful test conditions and interpretation

For dense coverage, use the existing one-row, aligned `(1,32,32,32)` FP16 case, disable BLAS, enable MMA, and record `mma_shape_is`/same chooser's selected index for that exact call. If it selects anything except S2, the unresolved S2 specialization was not tested. For the attention path, use synthetic FP16 pools and the parity executable's `new_run`, record that `qsa_prompt_attn_batch` selected its Intel MMA branch, then require sync, output checks, and zero failures. Do not use an API `true` alone as proof of completion.

The specific unresolved JIT symbol is `__builtin_spriv_OpJointMatrixLoadINTEL_PackedA_RowMajor_SG16_16x16_i16_8_local_v8i8_pi32_i32`; previous investigation located it in packed-A local joint-matrix lowering. This review found source paths that can instantiate the affected load, not a model-free route already proven to complete on the failing installation.
