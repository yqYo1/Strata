## Findings

The protocol close cases are sound for the two specified safe points. The controller does not send GEN until after READY, INFO/settings checks, process executable/argv/environment identity checks, startup mapping validation, and a final severe-runtime-error scan immediately before the only GEN write (`run_root.py` lines 537–569). READY is emitted after engine/model initialization and INFO, then the engine enters its input loop. At the top of that loop it tests `line == "QUIT"` and breaks before testing/parsing `GEN` (`generate.cpp` lines 7134–7136, 7753 onward, 7994 onward). Therefore, after READY and before any GEN has been attempted, a gate failure can send QUIT while the engine is idle in its input loop. The controller’s exception path does this only when `ready_seen` and `not gen_send_attempted` hold (`run_root.py` lines 591–624).

After `DONE`, the request loop has completed and the engine returns to the between-request input loop. The normal path captures the after-GEN map, sends QUIT, waits for process exit, and only then validates the output/trace/coverage evidence (`run_root.py` lines 571–589, 628–658). A post-DONE provenance/capture failure also qualifies for QUIT because `request_done_seen` is set before after-GEN capture; the exception path will attempt a bounded QUIT and exit wait (`run_root.py` lines 578–581, 603–623). It never starts a second GEN.

An exception after GEN has been attempted but before DONE is intentionally outside those graceful-close cases. The controller preserves the original failure and lets the process owner’s bounded failure cleanup act instead of injecting a potentially ambiguous command into an active or partially written request. That is the appropriate protocol boundary.

The failed-gate status is preserved. The interaction catches the primary exception in `primary_model_failure`; even when graceful QUIT succeeds and the interaction returns, `run()` checks this field and raises, causing the top-level receipt to record an error. Final `passed` requires `complete`, the kernel gate, unchanged boot, no active child, and no `error`/kernel-gate error (`run_root.py` lines 591–624, 685–704). Post-DONE output/runtime/mapping validation errors also propagate after normal process close, preventing a clean QUIT from turning failed evidence into PASS.

Ownership and cleanup remain bounded by the separately pinned V5 owner. It records the direct process identity including start ticks, pins process handles with pidfds, applies finite interaction/send/exit deadlines, and on unsuccessful close scans before terminating the pinned process. Its cleanup path uses bounded SIGTERM then SIGKILL waits and records cleanup, which makes the close gate fail. The controller’s graceful QUIT temporarily restores the owner poll callback before sending, so PID/start and resource checks remain active. No numeric-PID-only cleanup was identified in this reviewed path.

## Error-gate limits

The gate is strict for protocol `ERR` lines and for the explicit `ERROR` regular expression. That expression covers UR/ZE result errors, `[ERROR]`/`[FATAL]`, GPU completion unconfirmed, terminate/assertion/CAT/fault/out-of-resources strings. It is not a universal classifier for every compiler/runtime diagnostic: for example, an otherwise unadorned `error:` line does not match by itself. Startup and pre-GEN checks read the stderr file at discrete points, so an unrecognized or late-written diagnostic could escape those scans; final full stdout/stderr validation still runs after process exit. This is a bounded limitation of the diagnostic classifier and timing, not evidence of such an escaped error in this source review. Main should retain the current strict known-signal gate and inspect any new concrete diagnostic string before broadening it.

## Shutdown work with preload disabled

The opt-out controls only the background kernel preload sweep. With `STRATA_PRELOAD_KERNELS=0`, `preload_kernels()` returns before starting its preload thread; it does not bypass runtime initialization, other kernel-bundle checks, or queue drains. Before READY, device selection calls `get_kernel_bundle` for `ProbeKernel`, and the runtime constructor performs event/barrier measurements with queue waits (`device.cpp` lines 37–50, 185–219). Thus a startup failure or wait can still happen before READY, where no QUIT is safe or useful; the owner’s finite process deadline/cleanup is the applicable boundary.

On QUIT, the engine breaks the serve loop, optionally saves parked/live conversations only when `--conversation-save` enabled a disk store, calls `save_profile("exit")`, and returns (`generate.cpp` lines 10078–10110). The reviewed controller argv does not supply `--conversation-save` or `--expert-profile-save`; the profile save lambda is a no-op when `heat` is empty. With a completed generation, however, adaptive/profile state may make that final profile operation relevant. The controller’s `io.exit(30)` / failure `io.exit(10)` and owner deadlines contain this work.

Runtime/object teardown can still perform synchronous GPU work. The preload-disabled candidate’s `Runtime::finish()` enqueues a barrier and waits on the compute queue, transfer queue, and each engine stream; `Runtime::free()` calls `finish()` before freeing USM (`device.cpp` lines 336–357). The per-runtime watchdog observes blocking waits, with a 120-second hang threshold that terminates via `_Exit(1)` (`device.cpp` lines 116–125, 319–334). Therefore graceful QUIT can still spend time draining or terminate on a stuck driver wait; it is not a guarantee of immediate exit. The owner’s finite exit and cleanup limits remain essential. These shutdown statements establish source paths only; they do not predict whether this particular process will hang or whether any candidate kernel is reachable.

## Evidence boundary

This review establishes protocol ordering, error-gate behavior, identity/cleanup design, and concrete possible shutdown work from the pinned source. It does not establish that the controller or candidate was executed, that READY/QUIT occurred in a live run, that mappings or compiler provenance are complete, or that preload opt-out fixes any runtime/compiler failure. It does not amend any receipt, registry, or prior result status.
