## Finding: prompt-owned buffers survive into decode

The local `Prefill prefill` is constructed at `generate.cpp:10118`. For a batched prompt, the caller optionally loans expert-cache slots (`:10130-10171`), initializes prefill (`:10172-10180`), binds MTP and installs `on_chunk` (`:10181-10197`), calls `prefill.run` (`:10202`), refills all loaned slots and synchronizes the cache (`:10206-10224`), then proceeds to the token loop (`:10249+`). There is no `release()` or `reset()` at that boundary. The object remains in scope throughout token generation and releases at function exit/destruction.

`Prefill::release()` (`prefill.cpp:535-556`) cancels the stager, synchronizes its compute and copy streams, destroys stager/events/CPU buffers and copy stream, then frees each pointer in `Impl::owned`. `reset()` calls full `release()` and replaces the implementation (`:532-533`). This is a complete teardown, not a prompt-buffer-only method on a still-initialized object. Queue drains matter: `Prefill::run` can overlap a successor-stage run; it waits/drains that pipeline before returning, and callbacks run within that prompt phase. A caller-boundary reset after successful run and cache refill is the earliest plausible boundary in this path. No one should clear `owned` or free individual `region` members while their queues, callbacks, stager, or successor stage could still refer to them.

## T-scaled scratch versus decode state

At `T=6144`, source `carve()` allocates prompt arrays including FP32 `emb[T,N]`, residual `R[T,D]`, `xn[T,HC]`, `lo[T,LR]`, `gated[T,D]`, `inj[T,HC]`, `mixed[T,N]`, `bo[T,N]`; conditional BF16 remainder arrays; int32 steps/route tables; and PLE embedding rows. `D=10240`, `N=2560`, `HC=4`, `LR=320`, `K=10` are source constants (`prefill.cpp:~40`). The large shared `m.region` is sized to `max(gdn_set_bytes, qsa_set_bytes, moe_set_bytes)` and carved into alternate GDN/QSA/MoE views. Other allocations include fixed 32M-element uint16 GEMM scratch, expert dequant/group scratch, MMQ storage and the expert staging ring, plus (for streaming KV) an identity table and KV staging pool. These are prefill buffers; the attention/MoE/GDN views share the same region by design and are not all simultaneously live.

The state needed after prefill lives in other owners: main `SessionState` QSA K/V/indexer tables, GDN recurrent/conv and PLE history; expert cache and host residency map; MTP K/V/session state, dense projections, expert/head weights and decode graphs. `Prefill::draft_kv` temporary views borrow `m.region`, but the active callers are the prompt callback; it waits its queue before returning. Its MTP K/V outputs are persistent MTP state, distinct from the scratch. Therefore the source does not identify a decode-required `Prefill::Impl` arena. Existing MTP draft/decode does not call `Prefill::draft_kv`.

The implementation does not make a generic release-safe promise for retained aliases. In borrowed mode, `Alloc::take` carves from the expert-cache span without adding those pointers to `Impl::owned`; the loan is refilled before the caller reaches decode. Those borrowed views alias cache backing and must not be treated as owned allocations. In no-borrow mode, all `Alloc::take` device buffers are individually recorded in `owned`. The C++ source audit did not prove absence of all backend graph-capture or external recorded-pointer references for every allocation, nor did it inspect every RESTORE/checkpoint consumer. A release change must check the target's capture/recorded-pointer contract and checkpoint path before resetting. Do not infer that model allocations, session/KV state, or CPU workspace are reclaimed by freeing Prefill.

## Byte census and 262,144 physical context

A scalar maximum owned-byte total for current `T=6144` cannot be stated as a measured fact from this source-only audit. `Prefill::bytes_needed(g, ss, T)` mirrors the device carving sequence and adds 8 MiB alignment slack (`prefill.cpp:1028+`), but the result depends on model geometry, `ss.max_cells`/QSA `max_blocks`, selected KV stage representation and page count, MMQ/fallback plan, BF16X2 setting, expert group, `MAXBLOB`, ring override/pinned share/device memory, and borrowed versus owned mode. `init()` also owns allocations outside that byte-planner sum (e.g. token IDs, identity table, per-ring events, host/pinned PLE and route buffers, stager, optional handoff/CPU pool buffers). Thus planner bytes are not a complete host+device process census or a measured physical high-water mark. Existing R numbers do not fill this gap: round 273's 1,861,857,536 B / 1,166,147,584 B shared-region figures are for a different snapshot and `T=8192`; round 6's 2,116 MiB is a supplied run accounting value from a different tree, not independently derived here. Neither can be scaled to 6144 or attributed wholly to reclaimable device bytes.

The physical context limit `262144` affects QSA `max_blocks` and, for streamed KV, page counts/staging bytes; it is not the Prefill chunk length. Source uses `n_batched=n_prompt-1` and leaves the final prompt token to the ordinary token path. A fixed `T=6144` live allocation census for the target run requires the exact `SessionState` geometry, KV mode/page count, MMQ and ring configuration and allocation-mode receipt. Those inputs and an allocation-level high-water receipt were not present in the read sources. Record that as an open byte-census item, not as zero or a guessed 6144/8192 ratio.

## Does `release()` alone buy decode residency?

No, not for the decode interval in the observed call sequence: destruction at scope exit is after the token loop, so it cannot make capacity available to expert cache or decode graphs during generation. Moving a release/reset immediately after `run()` and successful cache refill would return the Prefill-owned device allocations before decode in the no-borrow case, subject to backend allocator behavior; it would not release session state, model weights, cache, MTP state/weights, verifier resources, or CPU-side session/workspace allocations. It would also destroy the initialized Prefill implementation, requiring a lazy `init()` before any later prompt that reuses this generation path. In borrowed mode it must not free cache storage and must respect the completed refill/lease; the active borrow is not separately owned.

This is a plausible reclaimable capacity category, not proof that additional expert-cache or graph residency can be admitted: there is no measured free-byte delta, no graph allocation request or failed admission to compare, and no runtime allocator evidence. Decode graph capture/warmup and graph aliases may be established later in the loop; exact capture timing and pointer use were not exhaustively audited for every graph. A proposal should retire/reset only after the complete prompt operation, callback/successor work, and loan refill; then verify no captured graph or recorded pointer references Prefill allocations before capture/replay. Keep checkpoint/RESTORE, multi-stage, error/cancel, later-request re-init and borrowed-cache behavior as explicit unresolved gates.

## Evidence limits and decision

Static source proves the workspace remains live through token-loop entry and that `release()` would free the owned set after queue drain. It also proves the MTP batching scratch is prompt-only, while the updated MTP K/V/session state is persistent and must remain. It does not prove the amount physically returned, the exact current 6144 maximum, whether a particular decode graph/cache allocation then fits, or an improvement in throughput. No recommendation should claim those outcomes until a same-host phase-aligned allocation/free-memory receipt and correctness checks exist. Existing layer-major cache/draft release hooks are separate: they execute inside that prompt path and restore their resources before `run_layer_major` returns; they do not establish post-prompt workspace release.
