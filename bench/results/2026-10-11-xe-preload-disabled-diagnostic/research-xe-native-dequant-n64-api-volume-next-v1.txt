## Why the API log is large for a small prompt

There are three sources of work/log volume, with different dependence on prompt length.

1. **Runtime and model initialization are present even at n=0.** The process environment captures API logging from process start, before `READY`. Serve initialization loads the model and expert profile/cache, initializes the prompt/verification/MTP state and queues, and performs GPU allocations/uploads and runtime/module operations before printing `INFO`/`READY`. The immutable source places the `READY` print after these steps (`generate.cpp` around 5718 onward and 7086–7135). The preload opt-out bypasses the separate background kernel-preload sweep only; it does not bypass model loading, device usability/kernel-bundle checks, runtime queue setup, or work done by the initialization path. The receipt has no byte/time offsets at `READY`, so it cannot quantify how much of the 64.6 MB came from startup.

2. **The input causes fixed-depth MoE work, even at 64 tokens.** With the recorded explicit `--short-read 0`, `windows_ok` treats the limit as explicitly given, so a 64-token part is not sent to speculative verify windows (`generate.cpp:1118–1125, 8488–8497, 8934–8951`). `--batch` is absent, so `read_part` calls one `Prefill::run` for this part (`generate.cpp:8760–8762`). Each prompt pass still visits the model's MoE layers, builds routing for `T*K` rows per layer, and processes each selected nonresident expert through the production path. The source counts actual routed expert rows and active experts per layer (`prefill.cpp:1835–1909`), then the current OFF path invokes one GU dequant wrapper and one Down dequant wrapper per selected non-fused expert (`prefill.cpp:2344–2363`). There are 48 MoE layers. Thus call volume is driven by 48 layer visits and the distinct selected experts per layer, not by a single operation proportional to 64 alone. The actual n=64 route and wrapper counts were not recorded, so this source-based mechanism is not an observed call total.

3. **The diagnostic environment makes every call expensive to log.** The receipt records `UR_ENABLE_LAYERS=UR_LAYER_TRACING`, `UR_LOG_TRACING=level:info;flush:info`, `UR_LOG_LOADER`/`UR_LOG_LEVEL_ZERO` at debug with flush, `ZE_ENABLE_VALIDATION_LAYER=1`, `ZE_ENABLE_PARAMETER_VALIDATION=1`, and Level Zero loader logging at trace with success printing, plus `STRATA_TRACE=1`. The UR tracing layer emits API entry/return lines, while the loader and validation controls add their own messages; flushing each line magnifies log bytes and wall overhead. Engine `STRATA_TRACE=1` is separately documented in source as one line per request step (e.g. `request`, `read ... tokens`, `refill`), not one line per device API (`generate.cpp:7050–7055, 8463, 8962–8967`). The dominant detailed-volume mechanism is therefore the broad UR/ZE diagnostics across both initialization and prompt execution, but the receipt did not segment bytes by API family or phase. Treat 64.6 MB as logged output under this instrumented environment, not a normal runtime cost.

The two traced sources cannot currently be separated numerically: stdout proves `READY` then `RESUME 0`, but the retained receipt has only total stderr bytes/hash and the log cap occurred before `PP`. A future bounded trace analysis would need byte offsets/counters at READY and prefill boundaries; reading the entire trace is unnecessary.

## What existing census/component reports add

The 32K source-LLVM caller census (`xe-source-llvm-census32k-root-v3/counts/record.json`, summarized in `research-native-batch-prefill-service-bound-v1.txt`) measured 136,846 successful individual GU wrapper returns and 136,846 Down returns over 32,767 actual batched positions, six chunks, 48 MoE layers. It also counted 144,639 logical expert H2D requests and 295,956,300,800 logical requested bytes. These counts are for that 32K OFF arm, not n=64; the receipt explicitly does not prove GPU completion inference, physical PCIe traffic, or service time. It illustrates why a trace can grow with active experts across layers, but must not be scaled down linearly to assert n=64 calls.

The same component report reports a theoretical full-window maximum of 17,106 grouped API returns versus 273,692 old individual wrappers if all 136,846 expert pairs form 16-wide groups and both axes always admit: 93.75% fewer wrapper returns by arithmetic. It is a call-count ceiling, not expected caller behavior or a latency claim. Partial windows, skips, lifetime-driven flushes, and independent GU/Down refusal/fallback change this. The component n=16 results are separate: host submit was often shorter for the group API, while checked enqueue-plus-drain medians were substantially slower for several type pairs (for example GU18/Down20 individual 4.419 ms vs group 159.993 ms under that fixture's full checked interval). Those component data require caution about group-length distribution and cannot predict model latency.

The candidate caller's available ON counters distinguish `gu_admitted`, `down_admitted`, declined calls, covered experts, fallback experts, flush count, held-slot reuse flushes and released slots. They identify actual admitted group calls and coverage only if the observer source is applied and validated; aggregate flush counts do not report the distribution of window sizes. Existing reports already proposed a per-window-size histogram. Do not repeat that as though it were a new discovery.

## One observation required for the ON adoption decision

The decisive measurement is **quiet, paired end-to-end prefill wall time for the same qualified prompt with batch OFF and ON**, captured from the request's prompt-read start through its successful `PP` completion, with actual batched positions and full output/health/fault gates. Use the normal long-run environment with the detailed UR/ZE trace layers absent; the n=64 trace-cap run cannot serve as either arm or timing sample. The measured quantity is the complete `Prefill::run`/prompt-read interval, not loader time, trace-write time, component enqueue time, a profiler phase, or a calculated API-call ratio. Keep existing prefill time diagnostics separate because queue-mark phases charge intervening idle gaps and perturb timing.

For that same request, the minimum count attached to this timing is the **successful dequant submission count, split by axis**:

`OFF: native_dequant_gu_calls + native_dequant_down_calls`

`ON invocation count: gu_admitted + gu_declined + gu_fallback_experts, and down_admitted + down_declined + down_fallback_experts; submitted-launch count: gu_admitted + gu_fallback_experts and down_admitted + down_fallback_experts`, with per-axis covered experts and flush counts reconciled.

This count explains whether batching actually replaced individual submissions; it is not a substitute for the PP wall. Require identical OFF/ON selected route and H2D request census, exact outputs/health/fault gates, source/binary/runtime identity, and successful completion. Accept ON only if the quiet paired process-level PP wall improvement is repeatable with an interval excluding zero and no correctness, count, transfer or fault regression. If the count falls but PP does not improve, do not adopt. If grouped call admissions are poor or the grouped arm regresses, stop and inspect the route/window mix before any further component or kernel work. Do not use 64.6 MB log bytes or the 50-second log-limited lifetime as a denominator.

This choice is deliberately narrower than new tracing instrumentation: the caller census already has OFF wrapper counts and ON per-axis group/fallback counters; the missing adoption evidence is a completed quiet paired ON/OFF request with the exact call-count join. A bounded diagnostic may retain the already designed window histogram if Main needs to explain a negative result, but it is secondary to the decision measurement.
