Why the separate host metric is needed
At base prefill.cpp:1779, kPfHostGroup is recorded BEFORE host routing data
preparation/copy and the checked compute stream_sync at1798. PfTimer.fold at1799
then queries the completed timestamps on the host. fold keeps the last mark as
the next interval's first endpoint; host work after that retained mark and before
the next marker can land in the host-grouping queue interval. Therefore the
phase labeled host grouping includes the fold's host API work, not just routed
pair grouping. Dequant similarly can include host/submission/transfer gaps between
its surrounding marks. This patch moves none of those boundaries and does not
subtract host costs from phase totals or relabel the fractions as GPU service.

Minimal optional implementation
PfTimer now holds two per-run host steady-clock accumulators:
  mark_host_ms: entry after the enabled guard through completion of event creation
    when needed, vector/phase bookkeeping, the existing event_record/require and
    used increment. Uses the already existing Clock=steady_clock and ms_since.
  fold_host_ms: entry after the enabled guard through all existing elapsed queries/
    require calls, phase accumulation and retained-marker swaps/used reset.
    Enabled no-op folds with fewer than two marks are timed/counted as well.
No elapsed phase/query or arithmetic is changed. No new GPU Event, recording,
wait, stream synchronization, kernel, polling, thread or queue operation is added.
The two Clock reads per enabled successful call and local counter bookkeeping
are the only added instrumentation before the final single stderr line.

The metrics are host wall DURING these CPU API wrappers, not CPU cycles or thread
CPU service time. They include possible API blocking, scheduler descheduling,
allocation/vector work and local bookkeeping; they do not isolate bare runtime
calls. The measured boundary excludes the accumulator update after the ending
Clock read and the final report formatting. Clock/counter instrumentation itself
has cost and can perturb a timer-on queue timeline; there is no calibration or
claim that this cost is fully measured, zero, or safely subtractable from phases.
Existing host staging/chunk counters can overlap these observations. Do not add
all host/phase metrics as disjoint shares or subtract mark+fold from the GPU
timeline to manufacture exclusive work/service totals.

Counters and interval-versus-endpoint semantics
  marker_calls: every PfTimer.mark entered while on, counted once per call.
    It is not the number of distinct retained Event objects or unique endpoints.
  new_events: successful actual production event_create calls when the vector
    needs another Event wrapper; reused markers do not increment it.
  fold_calls: every fold entered while on, including used<2 no-op calls.
  completed_intervals: incremented ONLY after the existing production
    publication::require(event_elapsed_ms) succeeds for that adjacent mark pair.
    It is the number of successfully completed helper intervals, including a
    permitted zero interval under the unchanged helper, not raw endpoint calls.

For a work-bearing fold with used=U at entry, its existing loop queries U-1
adjacent intervals and retains one last mark. Actual gpu.cpp event_elapsed_ms
invokes two command_end get_profiling_info calls on a successful normal pair:
one on each endpoint. A middle Event can therefore be queried as the end of one
interval and the start of its neighbor. No endpoint/UR/Level Zero getter counter
is added or printed by this patch. Do not interpret completed_intervals as that
underlying API count; source-level two-getter behavior is not a measured driver
call count, because the runtime may cache/implement queries differently. Failed
getters can stop the helper before reaching its second endpoint, and failures
are never represented in an emitted completed summary.

Failure and completion safety
All existing event_create/event_record/elapsed require checks remain in place.
Completed interval count increases only after require, so a failed query throws
through the original Prefill::run failure path instead of becoming a successful
count/timeline. Every work-bearing fold still follows its original checked stream
completion. If any inner or final fold query fails, control exits before the
existing phase reports AND the new overhead summary. No destructor or catch emits
partial overhead, a completed result or a second fold. Call timing which throws
need not finish its local accumulator because that entire PfTimer is discarded.
Existing issuer/stager cancellation/join/drains, catch queue drains and fail-stop
completion policy are untouched. Timings are never used to authorize buffer
release or infer completion. Earlier completed calls' local counters are discarded
with a failed run; no apparently complete summary is published for that query failure.
The report branch follows the same final stream_sync and successful final fold.
The preexisting optional later GDN-hash diagnostic can still fail after a phase
report; Main must retain final run/process status. This patch does not redefine
the existing report as proof of all later optional diagnostics/model operations.
