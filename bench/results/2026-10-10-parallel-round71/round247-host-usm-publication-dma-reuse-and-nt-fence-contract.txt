R247 — production host-USM publication, H2D use, ring reuse, and NT-store fence contract
Date: 2026-10-10
Scope: read-only review of frozen production SYCL source, its queue/event helpers, and primary SYCL, Level Zero, C++ and AMD/x86 ordering references. No hardware/runtime query, build, test, GPU work, code change, or optimization adoption.
Frozen source: `/home/yayoi/ghq/github.com/yqYo1/Strata/.worktree/diag-sycl-prefill-service-events-20261010`, commit `495369cf4dc6e6da564095a1c26504dd3694e3f2`.

Finding
For the current ordinary `memcpy` path, I found a coherent host publication and H2D source-lifetime chain; I found no definite undefined behavior or unsupported SYCL API in the reviewed path. Host USM allocation and the copy queue are made from the same DPCT device context, the producer publishes completed bytes with a release atomic, the issuer consumes that publication with acquire before enqueuing H2D, and the ring source is not reused until the H2D event reports complete. Shutdown also waits the copy queue before freeing the Stager. This does not prove performance or exact backend behavior on a live run.

Allocation and context compatibility
In `sycl/src/prefill/prefill.cpp:391-418`, `Stager::init` obtains pinned host output with `sycl::malloc_host(blob_bytes, dpct::get_in_order_queue())`; a failed allocation (or `STRATA_FORCE_PAGEABLE`) switches that slot to a `std::vector` pageable buffer. In this DPCT layer, `device_ext::create_queue_impl` constructs every queue with its `_ctx` (`sycl/include/dpct/device.hpp:692-703`), and `create_in_order_queue_with_profiling` also passes `_ctx` (`:625-635`). The host ring allocation queue is `device_ext::in_order_queue()`; prefill's `m.copy` is created through `dpct::get_current_device().create_in_order_queue_with_profiling(...)` (`sycl/src/prefill/prefill.cpp:1107-1118`), hence both queues have the same device context when called for the same current DPCT device. `Stager::device` captures that device id and each worker calls `dpct::select_device(device)` (`:434-440`); device selection is thread-local (`device.hpp:754+`) and does not change the allocation's context. Host-side `sycl::free(buf, dpct::get_in_order_queue())` uses that same context (`prefill.cpp:425-430`). The release path selects `Impl::device` (`:800-804`), waits queues before `stager.reset()` and frees (`:807-832`). The ordinary fallback is an allowed host pointer source to queue memcpy; its lifetime is protected by the same completion handshake.

This is source-level context compatibility, not runtime proof that every slot allocated successfully as host USM. In particular, `sycl::malloc_host` success versus pageable fallback was not attested per slot for a production run. The exact `sycl::queue` backend/context and actual allocation type remain a production-evidence gate.

CPU publication and host-to-device access
The worker's `Stager::work` writes the buffer through `read_into`, `memcpy`, or `copy_blob`; on a successful copy it executes `ready[j].store(1, std::memory_order_release)` (`prefill.cpp:456-481`). `Stager::wait` observes that flag with `load(std::memory_order_acquire)` before it returns the source pointer (`:507-514`). A release/acquire pair that reads the release value establishes the C++ host-thread synchronizes-with/happens-before edge for preceding ordinary writes; the issuer then calls `transfers.copy`, which calls `q->memcpy(dst,src,bytes)` on the `m.copy` queue and returns its event (`prefill.cpp:2321-2347`, `4748-4765`). The source remains immutable from worker completion through that queued H2D read.

The selected H2D operation also publishes device ordering: `transfers.copy` enqueues the memcpy to device staging on `m.copy`; `dpct::sync_barrier(m.copied[sl],m.copy)` records a barrier after it (`prefill.cpp:4762-4769`; `device.hpp:986-1004`). Compute submission later waits on the corresponding `m.copied` event before dequant/compute (`prefill.cpp:4972-4986`). Therefore the device consumes the copied packed expert only after its H2D command in the copy queue. For host source reuse, `issued_one` retains the exact H2D event and generation, then release-stores `issued`; the worker acquire-waits until its previous ring occupant has at least been issued, then polls completion of the retained event for that ring slot (`prefill.cpp:443-455, 483-528`; `sycl/include/strata/event_completion.hpp:26-53`). A non-complete or failed status is not treated as an acknowledgment; timeout exits rather than overwriting a possibly live source. At whole-object teardown `Prefill::release` waits `m.copy->wait_and_throw()` before destroying Stager buffers. Thus the source lifetime covers both the async command and the full queue shutdown.

SYCL requires USM passed to explicit memory commands to be accessible to the queue device and from the same context; host USM is host-accessible and device-accessible. Its specification warns that host/device accesses to host allocations must be synchronized. Level Zero similarly requires memory used by a copy command to be accessible to the command-list device and describes events/fences as completion/coherency primitives. Those API requirements match the source's queue-context and event ordering. Pageable fallback is deliberately a distinct performance path, but source queue memcpy accepts a host pointer; actual fallback path completion remains covered by the returned event.

Non-temporal stores: required additional proof
The existing release/acquire pair is sufficient to publish ordinary C++ stores between the CPU worker and issuer. It is not by itself evidence that hand-written streaming stores have drained their write-combining buffers before a host-to-device DMA starts. AMD's AMD64 Architecture Programmer's Manual Vol. 5 says `MOVNTQ` is weakly ordered and calls for `SFENCE` (or another sufficient fence) for strong ordering relative to other stores and shared data. AMD Vol. 1 describes SFENCE as ordering memory writes. Intel's optimization manual and DPC++ compiler guide give the same fence requirement for streaming stores. So an explicit NT implementation would need a CPU-store fence after the final NT store to a blob and before the release `ready.store`; if publication is batched, the fence must precede every ready flag covered by that fence. The issuer's acquire then preserves host-thread order before the `q.memcpy` submission. The existing queue event is still required for device command completion and slot-reuse safety; SFENCE does not replace it.

Glibc 2.39's public x86 `memmove-vec-unaligned-erms.S` source includes SFENCE after its 2-/4-page NT bulk loops before the final temporal tail and return path. That is useful source evidence that a selected glibc NT memcpy path is fenced before returning in that implementation. However the target process's exact installed glibc build, IFUNC target, and active copy-size branch were not inspected under this task's restrictions; R245 metadata reports glibc 2.39 for the synthetic control, not a contemporaneous production process attestation. The frozen C++ source calls `std::memcpy`, but it does not itself prove the emitted call reaches that exact glibc implementation or that the NT branch is selected. Consequently: do not add another fence on the assumption glibc omitted one, and do not assert that the actual production call currently uses the glibc branch based only on generic x86 source. If the source-level candidate replaces libc memcpy with explicit NT intrinsics, make the fence explicit and validate the compiler output plus host-USM-to-device visibility on the actual backend.

Exact invariant and remaining evidence gates
- Keep the current queue/context relation, release/acquire publication, copy-queue ordering, returned-event generation tracking, completion-before-reuse, and queue wait-before-free unchanged. No source-supported reason was found to weaken these edges.
- For any explicit NT experiment, limit it to CPU architectures/features with a supported streaming-store implementation, keep a temporal-tail path, execute SFENCE before readiness publication, and byte-check through actual H2D/device consumer before slot reuse. Do not rely on C++ release ordering as the hardware WC-store drain.
- On target, record each ring slot's actual allocator kind and allocation queue/context, plus selected source arm and worker count. Validate host-written NT bytes read correctly by the actual m.copy queue on the supported GPU/backend. Record completion event status/sequence for each tested slot and prove reuse happens only after completion; retain errors as failures, never as a release signal.
- Verify the exact target libc/IFUNC or use the application's explicit NT path; if relying on glibc, confirm the installed source/build and selected copy implementation. R245's ordinary-RAM result and R243's generic dispatch analysis do not establish SYCL host-USM visibility or selected NT behavior.
