API
protocol.validate(lines, *, n_prompt, batched_n, chunk_limit, max_generated, physical_context, vocabulary, output_requirement, require_lp5).
All expectations are mandatory. n_prompt>=2; batched_n must equal n_prompt-1; positive caller-supplied chunk_limit; max_generated1..4096; explicit physical_context2..INT32_MAX (the source device-cell capacity limit); n_prompt<=physical_context; vocabulary5..INT32_MAX. Counts/keys otherwise canonical nonnegative signed-int64 decimal, with bool rejected as an expectation integer. No universal chunk size, model vocabulary, physical context, captured-PP inference or performance default.
output_requirement exactly positive or exhausted_zero. require_lp5 explicit bool. Positive mode requires actual positive bounded output and positive decode time. A normal stop before requested maximum is accepted as bounded early EOS, including stop exactly at maximum. No requirement that all requested tokens be generated is applied to stop. LP5 required mode demands exactly one full LP line per token; false mode demands no LP lines. Output identity/probability correctness versus an independent reference remains outside this parser.
exhausted_zero is an explicit hypothetical caller contract requiring n_prompt==physical_context, generated0, finishlength, no decode counters and no output/LP lines. Decode time may be zero. It is never the default and does not establish output capability or whole-model quality.
Important source boundary distinction: current GEN initializes p=n_prompt-1 and context_bounds.hpp verifier_window allows physical_context-p positions. Thus this source can have one final verifier position when the prompt equals physical_context; the observer does NOT claim that this binary must produce zero then. Positive output is bounded by physical_context-batched_n, and length must reach min(max_generated, that capacity). Caller-declared zero at physical262144 is accepted solely as the explicitly requested zero-output contract, with actual zero observed, never invented when a different capture is obtained. Main must pin the prospective caller/source contract before treating a zero-output run as its expected case. There is no full262144 actual qualification here.

Fresh request grammar and order
RESUME 0
PP <exact end> <n_prompt> <nonnegative finite cumulative ms> <nonnegative finite reported rate> repeated once for each expected batched chunk
REUSED 0
T <vocabulary ID>, followed immediately by LP <selected logprob> <id:logprob> repeated exactly5 times when require_lp5 is true
DONE <generated> <prompt> <prompt ms> <decode ms> <length|stop> <drafts accepted> <drafts offered> <reused> <cache hits> <cache lookups> <RAM blobs> <file blobs> <file MB> <read_n> <offloaded>
Each line has exact single-space field count and no additional tokens. Strict whole-request stdout, with no startup, unrelated text, ERR, cancellation, batch lines, YIELDED, lookup-chain appended fields or second request. No diagnostic filtering silently removes recognizable or extra lines. Malformed/truncated/missing/duplicated/out-of-order PP/RESUME/REUSED/T/LP/DONE fail. Identical token values repeated legitimately are allowed, but added output lines must agree with requested and DONE counts. One final newline or CRLF capture-reader handling accepted; embedded CR/LF, blank request lines, extra final blanks and nonstandard separators rejected.
Chunk count is computed as ceil(batched_n/chunk_limit), checked<=1024 before generating any starts/ends. Starts are index*chunk_limit; exact ends min(start+chunk_limit, batched_n), including tails. No per-token range exists. Progress identity, order, declared prompt count and all ends must match caller expectations. PP cumulative timing must not regress. DONE prompt time positive and cannot precede final rounded PP time by more than0.55ms (PP rounds to integer and DONE to0.1ms). PP rate and file MB are descriptive reported fields; no throughput estimate or PCIe service claim is inferred.
DONE generated must equal parsed output count; fresh prompt/reused/read_n must equal n_prompt/0/n_prompt. Accepted drafts<=offered. Source increments accepted by the verified window before the EOS-sensitive emission loop; a valid earlyEOS can therefore have accepted>generated. The earlyEOS fixture explicitly retains8 accepted/12 offered with3 emitted outputs, and that case is accepted. Cache hits<=lookups; combined lookups+offloaded and RAM+file reads checked int64. File MB cannot be positive without file read count; a rounded0.0MB with positive reads is allowed. Zero-output contract requires accepted/offered/cache/reads/offloaded all0. No unsupported universal proportionality between cache counts, offload counts, source reads, generated tokens or unique experts is imposed without model/source geometry. Unknown negative/noncanonical/overflow count values fail.
All numeric floats have anchored decimal syntax, finite values and legal signs. Timings/rates/file MB nonnegative; logprob values nonpositive. LP5 IDs are canonical in vocabulary, unique, exactly5, sorted by nonincreasing logprob. Selected logprob cannot exceed maximum; if selected token appears among top5 its logprob agrees within0.000001. Printed top5 exp(logprob) mass<=1.000003 accounts for six-decimal source rounding. Positive log probabilities, NaN/infinity/overflow floats, duplicate IDs, bad ranks or impossible probability mass fail.
