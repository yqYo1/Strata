## Clock contract

SYCL event profiling is a separate clock from the fixture's `std::chrono::steady_clock` host interval. The SYCL 2020 specification defines `command_start` and `command_end` as 64-bit nanosecond timestamps from an implementation-defined timebase. It guarantees that events sharing a backend share a timebase; it does **not** say that this timebase is host steady-clock time. Therefore:

- Use each individual returned event's `device_elapsed_ns = command_end - command_start` only as its device event/action elapsed time. Save the raw start and end values as well as their difference and identify the event/kernel.
- Recurrence and output-normalization events are submitted to the same existing in-order queue/backend, so their timestamps can be interpreted in that common SYCL profiling timebase. Do not compare either timestamp value to host `Clock::now()` or subtract one from the other to build admission/wait estimates.
- The host `service_seconds` remains exactly its existing interval: host steady-clock starts immediately before the public wrapper (thus including admission) and ends after `q.wait_and_throw()`. Capture that end before issuing any profile queries. Querying/formatting timestamps must not extend or be folded into the host service interval.
- Do not add recurrence and norm event durations and label the sum “service”, “wait”, or a decomposition of host service. The host can enqueue norm while recurrence executes. Device-event time omits host admission and portions of launch scheduling; host service also contains wait, wrapper and host submission. Event-duration sums are a separate device-side observation.
- SYCL defines event values as per-backend, so keep any comparison to events collected from this same backend. Do not combine SYCL event timestamps with another backend or raw host timestamps. Level Zero raw kernel timestamp APIs have their own timer-resolution, valid-bit and wrap/domain rules; there is no need to bypass SYCL for this diagnostic. No host/device synchronization extension or raw Level Zero timer query is proposed.

The event is the returned `sycl::event` from a queue command-group submission. The immutable source submits one recurrence kernel command group and one norm kernel command group per wrapper. A test-only output/event sink at those two launch sites can retain the return values (`q.submit` for quad recurrence; the `parallel_for` return event for recurrence/norm). The source can keep the current named kernel bodies, launch ranges, arithmetic, order, queue properties and explicit bundle binding unchanged. The event's `command_start/end` describes the associated action (e.g. kernel invocation), not a device-side timestamp around any work-group or subgroup barrier.

## Availability requirements and error layers

The queue already has the `enable_profiling` property in the completed quiet run. SYCL says that constructing a queue with this property requires capture of profiling information; it also says construction must throw `feature_not_supported` if the device lacks `aspect::queue_profiling`. The current timing code intentionally reuses the queue created by Strata and only inspects `has_property`. A diagnostic must not construct a replacement queue or change queue properties/environment just for profiling. If this run's existing queue says it lacks the property, skip event queries and report `PROFILE_UNAVAILABLE: queue_property_absent` before any claim about event timing.

The SYCL event API says querying unavailable profiling information before completion can block; after the already existing `q.wait_and_throw()` it should not block waiting for command completion. It specifies `sycl::errc::invalid` if the queue that submitted the event did not have profiling enabled. Event information may still fail because a backend/runtime operation is unavailable or the device is lost; Unified Runtime exposes a distinct `UR_RESULT_ERROR_PROFILING_INFO_NOT_AVAILABLE` and `UR_RESULT_ERROR_DEVICE_LOST` among event-query results. Those are diagnostic-query failures, not an admission denial or a submission retry signal. The standardized SYCL-level API presents SYCL exceptions rather than requiring the application to depend on UR codes, so record available SYCL error category/code and message; do not assume every adapter maps UR statuses identically.

`wait_and_throw()` is the asynchronous-error synchronization boundary in this fixture. The SYCL spec says it delivers unconsumed async errors to the queue/context `async_handler`; it does not require a user-supplied handler to throw rather than record/handle an error. The immutable source snapshot does not include the Strata queue-construction/async-handler implementation, so this review cannot prove that a returned `q.wait_and_throw()` means the handler reported no error. Before relying on it in the instrumentation, the root-owned runner must verify its existing async handler is fail-closed for this disposable test or make it latch/report async errors and check that latch after the wait. Do not replace or mutate production queue error handling in this report. Any async error observed at the completion boundary invalidates the diagnostic and must never permit candidate fallback/retry on the same state.

## Safe status and termination split

Keep submission/completion safety exactly separated from profiling observation:

1. Inside the existing `gpu_stage` fail-stop scope, submit the recurrence and norm; retain their events; then call the existing `q.wait_and_throw()`. A pre-submit admission denial remains the existing candidate-denied result; it has no submitted recurrence/norm events to query. Once submission starts, any recurrence/norm submission exception or error from this completion/async-error boundary remains `FAIL-STOP completion_unknown=true` (exit 2 / no host unwind / no USM free). Do not broaden fallback or add a legacy retry. An async fault latch set by a returning handler is also a failed completion result; stop before using outputs or events.
2. Only after that scope returns successfully, stop `Clock` exactly where current code does. At this point the prior queue work is drained and the timed host endpoints have survived to completion. The event profile query must be in a separate scope **outside** `gpu_stage`; otherwise the existing generic catch will incorrectly label a read-only timestamp failure `completion_unknown` and `_Exit` before safe cleanup.
3. In the profiling-only scope query `command_start` and `command_end` for each retained event, after completion. Keep query outcomes in a separate profile-status field. Validate `end >= start` and use integer subtraction before converting to seconds. If either recurrence or norm profile lookup fails, do not convert the arm into `Denied`, rerun it, or let it fall back. Abort the profiling diagnostic as `PROFILE_UNAVAILABLE/PROFILE_QUERY_FAILED`, never print its normal `TIMING_SUMMARY ... pass`, and do not claim an event breakdown. As queue work has already completed successfully, let `Buffers` unwind normally: its destructor performs the existing final `wait_and_throw()` then frees owned USM. Return a diagnostic-specific nonzero result only after this teardown. If that final drain or release fails, preserve the existing fail-stop/failed teardown behavior.
4. If the event query error indicates device loss or any exception leaves uncertainty about queue/USM usability, still do not fallback or reuse the events. The normal final drain/free must either close successfully, or take its existing fail-stop branch. The query failure can never be relabelled as a successful measured event time.
5. Emit profile status/timestamps only after the service stopwatch has stopped and only outside device timed intervals. Keep existing bitwise comparisons/digests and successful-exit gates. If failure occurs before a chunk's parity comparison, the record must not claim the full paired correctness gate passed.

This split keeps an unavailable SYCL profile from being confused with an uncertain submitted command. It also makes the error report honest: `wait_and_throw`/async-handler failure means no result and fail-stop; a timestamp-read failure after successful drain means no event result but can follow orderly cleanup if the final drain/free succeed.
