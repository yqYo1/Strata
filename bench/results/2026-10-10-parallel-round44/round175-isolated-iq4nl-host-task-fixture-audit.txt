## Source finding

The fixture isolates a completed host-origin asynchronous error on the same in-order Level Zero queue as the private IQ4NL kernel. It first executes the pre-existing `q.wait()` and only then calls `iq4nl_completed_boundary(q, err)`, which invokes `q.throw_asynchronous()` and translates standard/nonstandard handler exceptions to an error string and `false`. DPCT's handler is installed via `create_queue(true)`; `dpct::exception_handler` calls `strata::rethrow_sycl_errors`, which logs all passed exceptions and rethrows the first. The installed SYCL API declares `throw_asynchronous()` to report outstanding async errors through that handler. These sources support the intended source-level flow; they do not prove the runtime consumes a one-shot error exactly once or that the later drain succeeds. The fixture explicitly requires both properties at runtime.

The fixture has strong positive-path lifetime ordering. The host `input`, `output`, `marker`, queue, and device `src`/`dst` remain in scope through all queued commands. The host task captures `marker` by reference, and normal success does not destroy it until after `destroy_queue`. Input and output readbacks use the same queue, with `wait()` and explicit `throw_asynchronous()` before validation. Device buffers are freed only after the later `wait_and_throw`, readbacks, and async deliveries complete. The queue was created as an owned, registered queue with async handler; after the explicit terminal drain, `destroy_queue` removes it from the owning device. No marker/source/output use-after-free was found on the full successful control or fault path.

## Error and partial-initialization paths

- **Unknown completion after possible submission:** The try block starts before upload submissions. On any exception while `completed == false`, the catch calls `iq4nl_unknown_completion`, which flushes `FAIL_STOP,...completion_unknown,no_USM_unwind` and `_Exit(2)`. This intentionally avoids unwinding/freeing device USM and host-captured state when completion cannot be established. `q.wait()` has its own catch that takes the same fail-stop path. A synchronous submission failure before work was actually accepted can therefore also fail-stop conservatively; that is not a UAF.
- **Known-completion failure after the primary wait:** After `q.wait()` returns, `completed` is set true before the async boundary call and later assertions. If async delivery returns the expected `false`, marker/count checks pass, and later `wait_and_throw` succeeds, the fixture reaches orderly readback/free/queue teardown. If a completed-boundary error is unexpected, an assertion fails, or a later `q.throw_asynchronous()` throws after `completed` was set true, the catch rethrows to `main` without freeing buffers or destroying the registered queue. Completion is already known on the paths where the flag is true, so this is a leak/fail-process-exit path, not a use-after-free or unknown-completion path. The owner device retains the queue in its registry until process teardown. No `CASE` or `TERMINAL` success marker is then emitted.
- **Queue construction and identity failures:** `create_queue(true)` precedes `identity(q)`, and identity must pass before any USM allocation. If identity fails, `run` unwinds without explicit `destroy_queue`; the registered queue persists until process exit. No fixture command or USM buffer has yet been submitted/allocated, and the marker has not been constructed. This is a bounded process-lifetime queue leak, not pending-work UAF.
- **Partial allocation failure:** `src` and `dst` are both allocated before `require(src && dst)` and before entering the guarded `try`. If exactly one allocation succeeds, the thrown allocation error bypasses all explicit cleanup and queue destruction. No queue command has yet been issued, so the successful allocation is safe to reclaim but leaks until process exit; the registered queue also remains. If both fail, the same queue leak occurs without a USM leak. This does not create a use-after-free, but a scoped cleanup guard would improve failure hygiene.
- **Other cleanup exceptions:** `sycl::free` and `destroy_queue` are after the guarded body and have no local catch/RAII. The expected successful path is ordered and should reach them after all work is complete, but source alone does not characterize exceptional cleanup API behavior. A failure there returns no terminal pass, though no pending command is expected at that point.

The error paths favor process termination or process-exit reclamation rather than unsafe live-buffer unwind. The principal static deficiency is resource cleanup on known-complete pre-terminal failures and partial initialization, not an identified asynchronous use-after-free. A parser must never treat the fault case's expected `boundary_ok=0` as a full pass unless all later drains/readbacks, buffer frees, both queue teardowns, and the final terminal record also complete.

The input is read back and byte-compared with the original, checking guards and active bytes. The `marker` is an independent host atomic and must be 0 for control and 1 for fault. Calls/retries/callback counts are asserted: exactly one private call and zero generic retries in both cases; callback count one for control and zero for fault.

The private helper call uses type 20 and `n=256`, satisfying the private API's documented contract. It passes a device input and output slice derived from distinct allocations, with active pointers offset inside guard regions. The fixture submits exactly one private kernel per run and, only in the fault run, one throwing `host_task` after it on the same queue. Thus its source layout tests a single host-origin asynchronous exception ordered after the candidate operation; it does not test a device-kernel fault, a host task failing before/while the private command completes, recovery/reuse after failure, production prompt callbacks, or actual model data.

## Queue registration and teardown scope

`create_queue(true)` selects an in-order queue in the configured non-USM-none path and registers it in `device_ext::_queues`; `true` selects the DPCT exception handler. `destroy_queue` validates that the pointer is an owned non-default queue, erases its shared pointer from the registry, and nulls the caller pointer. The fixture's successful path calls `wait_and_throw()` at `later_drain`, then performs and drains two readbacks with further `throw_asynchronous()` calls before freeing USM and destroying the queue. Consequently, a successful run does not rely on global default-queue synchronization to complete this fixture-owned queue: it explicitly completes and tears it down. A process-level/device-wide queue drain is not present in this standalone fixture and must not be inferred. Error paths with incomplete work intentionally `_Exit`, while known-complete failures can leave the queue registered until the short-lived process exits.

The helper's `iq4nl_wait_boundary` is not called by this fixture; this fixture tests the narrower contract that an existing wait returned successfully before calling `iq4nl_completed_boundary`. Its fail-stop wrapper is exercised only if the fixture's own guarded submissions/waits throw while `completed` is false; fault injection is an async host-task exception expected after a successful wait, so that path should be caught as a completed-boundary error, not classified as unknown completion.
