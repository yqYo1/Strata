## Production queue can provide SYCL event profiling

The queue factory in `sycl/include/dpct/device.hpp` constructs queues with `sycl::property::queue::enable_profiling()` unconditionally in `create_queue_impl` (around 692–705), adding the requested property such as `in_order`. `init_queues()` creates the default compute queue with `in_order` (around 681–686); `in_order_queue()` returns that queue (around 562). `strata::q_of(stream)` uses the supplied queue or this in-order queue (`sycl/include/strata/sycl_queue.hpp:13`). Thus the default production compute queue has both properties; no queue replacement or profiling property change is needed for the default path. This is a source-level conclusion; the eventual process should still record `has_property<enable_profiling>()` and `has_property<in_order>()` on the actual queue passed to Prefill, since stages/custom queues could differ.

SYCL event profiling returns device timestamps for `command_start` and `command_end`; queries may block until the command reaches running/complete. Timestamp differences on a backend share a timebase. To avoid per-expert waits that would alter the schedule, collect returned events as commands are already enqueued, do not query timestamps in the expert loop, drain at the existing chunk boundary, and read timestamps only after that drain. [Khronos SYCL 2020 event profiling](https://registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html#_profiling_information_descriptors)

The two helper implementations currently call `queue.submit(...parallel_for...)` on the same queue. The private helper's kernel is `prefill_iq4nl_flat_kernel`, range `n/256` groups with local size 32, and invokes `dq_iq4_nl<sycl::half>` (`src/kernels/cuda/iq_kernels.dp.cpp:4295–4315`). The generic helper submits `dequant_flat_kernel_c7cec2` with the same `n/256` and local size 32, passing runtime `t` to `dequant_flat_kernel` (`4318–4344`). Both perform an asynchronous submit; the local `check()` currently does not wait or surface an asynchronous error. The production caller executes the helper per nonempty expert in the direct native layer path, with private dispatch only for env-enabled type 20 (`src/prefill/prefill.cpp:4799–4810`).

## Stage 1: one-DQ component measurement before any long prompt

The cleanest first answer is a root-owned, isolated, synthetic microbenchmark that calls the two existing helpers directly in one compile-option-ON executable: generic `iq_dequant_f16(20, ...)` versus `iq_dequant_f16_prefill_iq4nl(20, ...)`. It should use identical valid type-20 packed input, device buffers, queue, output layout, and `n`; validate both output arrays against the same independent oracle before timing. The fixed-format size to request for the intended native down matrix is `n = f.n_embd * f.n_ff`; where the inspected type-20 layout is 2560 output by 640 input, that is 1,638,400 values (6,400 256-value blocks). Record the actual passed dimensions rather than assuming every GGUF layer has that shape. Existing parity fixtures prove arithmetic only; they do not report these timings.

For each call, capture the `sycl::event` from `queue.submit` (a test-only return/receipt change at the submit boundary is sufficient), plus host steady-clock time immediately around submission. Do not insert `wait()`/`wait_and_throw()` after each call. Do a small untimed warm-up for both, alternate or randomize the measured order in batches on the same in-order queue, collect enough repetitions to characterize run-to-run noise, then drain once per batch and query the event timestamps. Keep separate values for device kernel service `(end-start)`, host submit call time, and queue delay `(start-submit)`; never call all three “kernel time.” Also retain per-batch wall time, output-check status, and counts. Timestamp event creation/retention has a cost of its own; use the smallest event set that gives stable results and report it. This method does not add queue commands or per-expert waits, but it does retain event objects and is still instrumentation; validate the uninstrumented harness-level wall result too.

Use one compiled ON binary and compare the generic and private direct wrappers within it to pin compiler, host code, runtime, and build options. This is a component test, not a production prompt result: it omits production routing, per-expert blob transfer, host grouping, actual MoE rows, oneMKL down GEMM, and layer/chunk pacing. It answers whether the two kernels have a measurable service-time difference for one down matrix, and whether the host submit path changes. It does not establish a prompt speedup.

Report cold-JIT and steady-state separately. The first call may trigger module/kernel creation or device JIT; its host call latency and event submit/start gap can include cold effects, but the event's `start..end` duration alone does not include compilation. Do not mix a first-use sample with warm kernel measurements. For steady state, warm both kernels in the same process before measurement. If measuring cold starts later, use separate fresh processes and explicit cache policy/state receipts; do not delete shared caches as an unrecorded cleanup action. Intel documents separate JIT and AOT paths; cold-image compilation is a different cost from running the already-built kernel. [Intel compiler/runtime JIT/AOT design](https://intel.github.io/llvm/design/CompilerAndRuntimeDesign.html#ahead-of-time-aot-compilation)

## Stage 2: small real-caller attribution, only if Stage 1 is positive

If the component result shows a stable saving, run a short production-caller prompt using the same compile-ON binary twice, with runtime option 0 (generic type-20 path) and 1 (private type-20 path), fresh processes and identical input/model/device/cache conditions. Do not enable MMQ/fused or another dispatch path; retain the source-supported direct path configuration and receipts from R169. Record prompt token count, chunk and layer boundaries, actual private/generic type-20 calls, `n` for each, and bypass counts. No actual production call count can be established from source alone: it depends on runtime nonempty routed experts per layer/chunk. Count it; do not substitute top-k times prompt length or an assumed constant.

The existing `STRATA_PREFILL_TIMING` has queue event marks around phase `kPfDequant`, and reports `kPfGemmD`, host, and transfer phases (`prefill.cpp:2120–2186`, marks around 4702/4747 and 4825–4829). It is useful to put the candidate in context, but it does not isolate private Down dequant: the dequant interval starts before the expert's GU and Down dequant operations and ends at a later phase mark, so it can include both dequant kernels and host/queue gaps. Do not report that phase as the private kernel's own duration. The timing code marks event barriers and folds them at layer/chunk synchronization; keep its existing mode identical across A/B and report it as phase attribution, not a per-call microbenchmark.

For any production short run, add only counters for every qualifying call plus a bounded, deferred sample of returned events if needed; query the sample after the ordinary chunk/layer drain. Do not add synchronization after individual experts. Compare aggregated `kPfDequant`, `kPfGemmD`, host chunk/sync, and transfer phases with the isolated event measurements. If an in-production per-call event probe materially changes aggregate wall/phase values versus the same run without the event probe, report the observer effect and discard it as a quantitative production measure. The source contains existing expert-wait controls (`STRATA_PREFILL_SYNC` is explicitly per-mark synchronization); do not use `STRATA_PREFILL_SYNC` or any per-expert wait setting for performance comparison.

## Bound the possible end-to-end effect and stopping rule

For observed actual private calls `i`, define component benefit `delta_i = generic event duration_i - private event duration_i`; also compare host submission time separately. A conservative gross device-work upper bound is `max(0, sum(delta_i))`. Divide by the same A/B short-prompt wall time for a loose upper bound on fractional prompt benefit. This is optimistic because DQ work can overlap with copies/host preparation, and changes in dispatch can move bottlenecks; measured short prompt wall time is needed to tighten the bound. Compare the aggregate against the observed down-GEMM, transfer, total MoE, and prompt-wall costs. Source cannot supply actual `i` counts, per-call timings, model-route sparsity, or the overlapped fraction; those are the exact unknowns to measure.

Pre-register a noise-aware gate before collecting results: if the paired steady-state private-vs-generic service delta is not positive beyond its confidence interval, reject and stop—do not spend the full-model run. If positive but `sum(delta_i)/short_prompt_wall` has a one-sided upper bound below the team's declared minimum useful prompt improvement, reject the full-model run. If no minimum is already set, choose and record one before Stage 2 rather than inventing it after seeing numbers. A positive component result with unknown route counts is not enough to proceed to the 32K model run; Stage 2 must provide the actual count and gross upper bound first. A full-model run is then justified only if the upper bound remains large enough to be practically relevant; the subsequent long run tests end-to-end benefit rather than discovering component kernel cost.

## Artifact and interpretation requirements

Keep the timing artifact compact: code/command and source hashes, compiler/runtime/driver/IGC versions, queue property receipts, target/device, dimensions, exact runtime/build options, cache warm/cold state, event counts, output correctness, per-arm samples and summaries, and a table of `device service`, `submit latency`, `submit→start`, production call count, existing phase totals, and wall. Preserve each sample and decisions under the repository's measurement-retention instructions; do not retain duplicate timelines.

This plan establishes that event profiling is supported by the current default production queue construction and gives an asynchronous way to isolate the DQ command without per-expert waits. It does not establish that a profiler has succeeded, that event instrumentation is free, that private DQ saves time, how many experts are routed by the target model, or any full-model speed result. Avoid PTI/VTune as the first measurement route: the narrow event path is already present in source and does not depend on the previously rejected system-profiler setup.
