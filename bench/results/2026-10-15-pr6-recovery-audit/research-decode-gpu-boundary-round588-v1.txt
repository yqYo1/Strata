# R588 — normal verifier GPU-boundary wait の実範囲

2026-10-15 JST。読み取り専用のsource/runtime契約調査。許可された本報告だけを書いた。製品変更、build/test、GPU/service実行、Git、cleanupはしていない。Mainのactive GPU format run/logには触れていない。旧完了receiptのみ参照した。禁止されたB、`prefill-gemm-only-contract-root-v1/record.json`、private Codex/home/envscanは読んでいない。

## 結論

固定4096 FP32 normal decodeの `GPU boundary wait` は、実GPUだけが動いていた時間ではない。`Verifier::run` が次のSYCL graph segmentをlaunchした後、`cudaEventSynchronize(layer_done_)` が戻るまでのhost wall時間である。このeventは互換層がgraph全体を一つのin-order queue submissionとして発行したSYCL eventにbindされる。したがって区間は、そのsubmissionに属するdevice executionに加えて、queue submit/driver/runtime scheduling、event完了通知、CPU側 `event.wait_and_throw()` とerror checkの時間を含む。既存計時にはdevice eventのGPU timestampがなく、区間をGPU active timeやexclusive kernel timeには分解できない。

一方、明示的なCPU expert `pool(...)` 呼出しとcopy queue drainはこのtimerの外にある。`ms_wait` のstart `a` はprogress通知前、end `b` はSYCL layer event synchronizationの後。pool後の `ms_pool` は別に足し、`cudaStreamSynchronize(copy_)` はその加算後に呼び、完了後に次segmentをlaunchする。よって記録済みの7.713/6.886秒は「verifier graphごとのevent completionまでのwall累積」であり、CPU pool時間や明示copy-stream drainを加えた値ではない。ただしruntime/driver・queue/protocol待ちを含むので「GPU演算wait」と断定できない。callback実行の可能性を厳密に除外するには、実際に発行されたgraph node/host taskをtraceで識別する必要があり、timerだけではそれも証明しない。

旧ledgerは34603 input、MTP4/max128、W55/R217でboundary 7.713 s、CPU pool 8.363 s、verify caller 22.346 s。二回目はW50/R197でそれぞれ6.886 s、7.186 s、15.316 s。出力列が42番目から異なり、accept/verify量も異なるため差をwarm graph効果へ帰属しない。48×Wの計算値は記載しない。既存値はaggregate marginalsで、別scopeの和・引き算やkernel時間への変換に使えない。

## 実source経路とruntime契約

* `src/core/verify.cpp:59-73` は `STRATA_SYCL_VERIFY_NATIVE_CAPTURE` を読む。通常値は`small`、ただし固定normal ledgerは明示`0`。その実行では `begin_verify_capture()` はcompat `cudaStreamBeginCapture` を選び、native recordingを有効化しない。これは「SYCL graphを使わない」という意味ではない。`src/sycl/compat.cpp:21-40,433-465` では通常captureがoneAPI `command_graph`をnon-native propertyで記録し、native modeのみ `enable_native_recording` を付ける。`src/core/verify.cpp:1024-1040,1044-1073` は実SYCL経路でwindowを多segmentに切り、各segment graphをinstantiateする。normal receiptには `STRATA_SYCL_VERIFY_NATIVE_CAPTURE=0`、故にcapture modeを切り替えて診断する必要は今の証拠から出ない。
* `include/strata/sycl/launch.hpp:44-62` はopaque streamをin-order `sycl::queue`として扱い、null streamを除いてnon-in-order queueを拒否する。`Runtime::make_queue()`もin-order propertyを必ず付ける (`src/sycl/runtime.cpp:78-89`)。`src/core/verify.cpp:399-415` はseparate `copy_` と `cs_` queuesを作る。従って各queue内のsubmissionは順序化されるが、copy_とcs_間には暗黙の順序はない。copy_の依存完了はhost側 `cudaStreamSynchronize(copy_)` で成立させ、その後に次のcs_ graph segmentをlaunchする。
* 通常の `graph_launch_with_completion()` は `src/sycl/compat.cpp:478-519` で `q.submit` し、`graph->last`への依存後 `h.ext_oneapi_graph(graph->value)` を実行し、そのsubmit eventを `layer_done_`へ保存する。`cudaEventSynchronize()` (`:394-399`) はそのeventに対して `runtime_for()->wait(*event)`、すなわち `event.wait_and_throw()` とruntime error check (`src/sycl/runtime.cpp:112-115`) を行う。このためtimerは単なるdevice timelineではなくhost blocking completion span。
* `src/kernels/sycl/sequence.cpp:37-47` のmapped-flag spin waitとGPU global-timer stampはSYCLでthrowする。verifyはmapped-flagをGPU上でpollする経路ではなく、layer event completion後に `reached_`をhostで進め、poolがplan/resultsを用意した後に次segmentを進める。このためCUDA側のdevice-spin予算や48×windowの推計をSYCL normal pathのGPU仕事として使えない。
* pool callbackの明示呼出しはevent同期の後 (`verify.cpp:1290-1301,1333-1349`)、copy streamのDMA/host callback drainはpoolの後 (`:1371-1389`)。GPU shared/hit graphはpool callback中に独立してlaunchし得る (`:1338-1344,1360-1369,1551-1568`)。これがevent waitで実行中かどうかはcompletionイベントの区間と別であり、graph/queueのactual traceで判断する。

normal receiptは `UR_L0_V2_FORCE_DISABLE_COPY_OFFLOAD=1` と `EnableDirectSubmission=0` を含む。Intel LLVMの公式environment-variable表ではcopy-offload変数はqueueのcopyをdedicated copy engineへoffloadする実装動作の制御。DirectSubmission設定も同じfrozen runtime recipeに記録されている。現source/runtime契約からこの二つを戻す理由は得られず、今後も固定して比較する。これらは実装/driverの実行経路を固定する設定であって、GPU faultや今回timerの原因が実証済みという意味ではない。仮に比較する場合も別armとしてMainが管理する必要がある。

具体的なhang defect、data race、UBはこのsource reviewで特定していない。二queueを跨ぐ依存はhost drainで明示され、graph completionもchecked event waitを通る。GPU native captureを有効にすると結果や速度が変わるという証拠もここにはない。既知のfailure hook `STRATA_TEST_VERIFY_STALL` は明示的テスト注入で、通常unset (`verify.cpp:148-153`)。

## 次に有用な最小のactual decode profile

新しいsource-level原因仮説は出なかった。最も情報量が高い次の一手は、clean route/CPUformat測定と直列化せずMainが選ぶ別のnormal actual-decode diagnostic processで、**完了する一つの実MTP verifier windowだけ**をprofilingすること。process全体・全requestのtraceは提案しない。

Windowの開始直前から最終segmentとcopy streamが成功drainするまでの一回を、bounded ITT taskで選ぶ。範囲内で既存位置の `graph_launch_with_completion`, `cudaEventSynchronize(layer_done_)`, `pool(...)`, `cudaStreamSynchronize(copy_)`, next segment launchを低量ITT task/annotationでtagする。`fetch_dma`の`cudaLaunchHostFunc` callback本体もtaskとして識別する。これはcallback内容を記録する計測ラベルであり、新しいwait/eventやsequence変更は追加しない。traceで同じVerifierのnative PID、B570、cs_/copy_ queue、window IDを関連づけ、各graph-launchからcompletion-event同期までのhost durationと、対応するdevice event kernel/copy execution intervals、queue gaps、copy queue/callback intervalsを別々に出す。device lane上の全activity coverageがない限りgapを「GPU idle」と呼ばない。host/device flow IDだけでcopy方向を決めず、allocation/APIとaddress rangeでendpointを照合する。

Collectorは固定済みPTI/unitrace provider revision `6c0d6b0b80c6dbac4b5902d9d5ade1c75b9e9033`を再利用し、再buildしない。`--start-paused --chrome-kernel-logging --chrome-call-logging --chrome-itt-logging --pid --tid`を使う。PTI READMEは`PTI_ENABLE_COLLECTION=1/0`による範囲収集、host/device/ITT collectionを記載する。いまのsourceにはwindow選択付きITT gateはないため、Main側でdefault-offの狭い診断hookを加える必要があるなら、そのhook自体を先にレビューして完了後に実施する。環境変数をSYCL runtime初期化後に設定して発効すると仮定しない。`--chrome-sycl-logging`やUR traceは、まずこのLevel Zero+ITT captureでqueue/event対応が不足した時だけ別process候補とする。

R576のbounded trace budgetをdecode用にも保守的な上限として流用する: 64 MiB total trace/output、300 s、8 GiB owner RSS、host threadあたり65,536 events、単一window、超過または欠落はincompleteとして止める。stdout/stderrとtrace directory合算bytesをownerがhard monitorし、後の計測手順・retention lockはMainが管理する。既存oneAPI validation/loader warning flagsはnormal receiptどおり固定し、collectorをperf比較には使わない。profile有無で発生したwall差は診断runの影響として別記する。raw timelineから同じwindowのcompact device/service、host API、queue gap、callback、event completeness、identityのみを抽出してhashし、raw削除可否はartifact retention手順でMainが判断する。

unitraceの`--device-timeline`/`--kernel-submission`は補助出力に留める。unitrace READMEのtimestamp表示がGPU clockとhost monotonicを同じdomainと保証しない。過去資料ではUnitrace `UNITRACE_SystemTime=1`によるCPU header checkのみqualifiedで、GPU traceのRAW clock joinは未証明のまま。従って本profileはGPU-duration内部比較とhost-side call durationの独立列までとし、GPU/host absolute timestampをjoin・合算しない。現在の証拠はRUN実行を許可しておらず、本報告は提案のみ。
