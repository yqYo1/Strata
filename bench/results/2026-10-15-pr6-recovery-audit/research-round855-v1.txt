# R855 — Convolution mapping, reuse, and workspace crossover

**Classification:** knowledge collection. **Question:** when does 2-D CNN convolution benefit from explicit im2col plus GEMM, implicit GEMM indexing, or a direct spatial kernel with output/input-window reuse? This is algorithm guidance, not a Strata or Arc prediction; no local build, benchmark, profiling, or implementation was done. Scope metadata for R798/R805/R811/R813/R832/R835/R839 shows adjacent coverage of GEMM tiling/layout, descriptors, MoE, pipelines, stencil reuse and bank layout; this report addresses convolution mapping and workspace.

## The mapping choice

Let input be `N×H×W×C`, filter `K×R×S×C`, output `N×P×Q×K`, element size `e`, and forward convolution use stride `(u,v)` and padding. The GEMM view has `M=NPQ`, `N_g=K`, `K_g=CRS`. Explicit im2col writes an `M×K_g` activation matrix: `B_col = e·N·P·Q·C·R·S` bytes, before filter packing. For stride-one 3×3 this is near nine times the input bytes, apart from borders. It takes a transform write and then GEMM reads that workspace; a third reorder may be needed if GEMM's output layout is not the consumer's. The advantage is a regular, independently tuned matrix kernel and straightforward data reuse across output channels. Its costs scale with output positions and filter area, including padded zeros, and the workspace must coexist with other live buffers.

Implicit GEMM generates the same logical activation tile while loading it, using coordinate decoding, pointer increments, and validity predicates instead of storing the full lowered matrix. CUTLASS documents the mapping from output-row `M` back to `(n,p,q)` and filter-channel `K_g` back to `(c,r,s)`; it describes building the tile in shared memory for Tensor Core GEMM. cuDNN calls this a variant of direct convolution: it retains ordinary convolution inputs and weights and does not create the global virtual matrices. It saves global traffic and peak workspace but pays address and boundary work in the main loop; unsupported alignments, small `M`, or awkward tails can reduce vectorization and matrix-engine occupancy. CUTLASS's documented high-performance case favors NHWC, 128-bit alignment, and channel/filter counts divisible by 32. This is an implementation constraint, not a universal convolution requirement.

Direct spatial/output tiling assigns neighboring outputs to a block or lane group, retains input-window fragments and weights in registers/shared memory, and accumulates output tiles. It can reuse an input value among filter taps or adjacent output positions without writing im2col. A simple thread-per-output kernel instead repeats loads and address calculations, so “direct” alone does not guarantee reuse. Some direct algorithms split reduction dimensions and write partial outputs for a later reduction; that trades input staging for output scratch and another launch. Boundary predicates, small output grids, channel reduction length, and thread-block count govern whether the kernel feeds enough work to the GPU.

## Algorithm comparison

| Mapping | Temporary bytes and global passes | Reuse and arithmetic | Boundaries, launches, and applicability |
|---|---|---|---|
| Explicit im2col + GEMM | `B_col` workspace, plus optional packed weights/output. At least one full lowering write and one GEMM read of `B_col`; ordinary input read and output write remain. | Reuses each lowered patch over output channels through GEMM; regular dense matrix tiles can use fast matrix units. Arithmetic remains `2·N·P·Q·K·C·R·S` FLOPs. | Typical two device kernels (lower, GEMM), possibly a reorder; host descriptor/allocation/setup is additional and source benchmarks often exclude it. Padding materializes invalid zeros unless specialized. Best case: large dense matrices and enough work to repay workspace; weak case: small batch/tiny output, memory cap, or small `K`/`M`. |
| Implicit GEMM | No global `B_col`; tile-sized shared/register storage only. One main compute launch, or an extra offset-precompute launch in a precomputed-index variant. | Same multiply count as direct convolution. Reuses weight and activation tiles within GEMM; avoids global duplication, but coordinate arithmetic and predicates are paid during loads. | Masks invalid coordinates at edges; strides change virtual addresses and may break load regularity. CUTLASS Turing example relies on NHWC/alignment and per-tile GEMM. Good for dense, matrix-friendly channel counts; ragged or small dimensions can underfill tiles. |
| Direct spatial tile (cuConv example) | No input-lowering matrix, but the cited 3×3 implementation writes `N·K·P·Q·R·S` FP32 partial-output values, then reads/reduces them; two launches. | Direct convolution operation count. Reuses a filter row in shared memory and maps spatial reads for coalescing; does not depend on dense GEMM throughput. | Its NCHW layout makes X-contiguous reads coalesced for suitable patch widths; row crossings can cause extra transactions. Small input grids can win through parallel blocks; larger reductions/channels expose low arithmetic-unit utilization and partial-output traffic. |
| Winograd `F(2×2,3×3)` family | Transform input/filter, compute in transformed domain, inverse-transform. Fused variants combine work; nonfused variants use extra kernel passes and scratch. Exact scratch depends on tile packing and implementation. | Fewer multiplications for 3×3: `F(2,3)` uses 16 products for 4 outputs versus 36 direct products. Adds/transforms and different rounding replace some multiplies. | Only a bounded small-filter comparator here. Edge tiles and transforms cost more for small total work; scratch can be large. oneDNN documents FP32-only Winograd and shape/stride/group restrictions in its v3.0 guide; it warns accuracy can be lower than direct. |

## Exact cases and measured evidence

Jordà et al.'s cuConv v1 paper reports single-precision, NCHW forward convolution on Tesla V100-SXM2 with CUDA 9.2/cuDNN 7.1; stride is one and padding is `(R−1)/2` on each side. They report GPU-kernel execution times, mean of nine executions, not host-call latency. Shape notation below is `(H=W, batch, R=S, K, C)`; the two 3×3 tests are exact source cases:

* `(7,1,3,384,192)`, output `1×384×7×7`: cuConv direct partial-product + sum kernels take 57.79 μs; cuDNN Winograd takes 111.03 μs fused and 105.63 μs nonfused; implicit-precomputed-GEMM totals 203.45 μs. Here the direct family wins. Its calculated im2col workspace is 84,672 FP32 elements = 338,688 B (0.323 MiB), while cuConv's partial output is 9·1·384·49 FP32 = 677,376 B (0.646 MiB). The direct result is not workspace-free.
* `(13,1,3,384,384)`, output `1×384×13×13`: direct takes 466.68 μs; fused Winograd 232.35 μs, nonfused Winograd 327.55 μs, and implicit-precomputed-GEMM 389.08 μs. Direct loses as the output/reduction work grows. The lowered input estimate is 584,064 FP32 values = 2,336,256 B (2.23 MiB); the direct partial-output scratch is the same byte count here because `C=K`.

These cases do not prove input size alone caused the crossover: implementations differ, and reported timings exclude host setup. The authors attribute the small case's result to exposing more block-level parallelism; the larger direct case shows about 50% compute and memory unit utilization despite 86% occupancy. Thus output-grid exposure and instruction utilization matter alongside workspace.

For a 1×1 contrast, cuConv case `(7,1,1,256,832)` is also FP32/NCHW/same-padding (padding is zero); direct takes 58.56 μs, versus 128.13 μs implicit GEMM and 107.29 μs implicit precompute plus GEMM. But the same paper records 1×1 counterexamples: `(14,1,1,1024,256)` takes 73.86 μs direct versus 47.87 μs implicit GEMM, while `(27,1,1,256,64)` is 22.53 μs direct versus 19.20 μs implicit GEMM. The authors link the first loss to 1,024 direct blocks and their setup/termination overhead; the matrix paths use 224/32 blocks. This warns against treating “no transform” as low latency independent of launch granularity.

Explicit lowering's evidence is separate. Zhou et al. (arXiv v1, 2021) measure cuDNN explicit im2col plus GEMM against cuDNN implicit im2col on V100, CUDA 10.2/cuDNN 7, FP16, batch 64. Across AlexNet, ResNet, VGG16, YOLO, and DenseNet, explicit im2col is 28% slower on average; its GEMM time is nearly the same as implicit, so the measured gap is transform time. Their table reports VGG16 lowered-input memory of 311.80 MB versus 34.65 MB original maps (9.0×). The paper omits per-layer layout/padding for this plot; its batch-64 network aggregate is not a per-shape result and cannot be combined with cuConv FP32 cases. It shows materialization can lose while GEMM remains strong, not that explicit im2col always loses.

## Break-even and hardware limits

A compact model is `T_exp ≈ T_setup + T_lower + 2·B_col/BW_eff + T_GEMM`; the `2B_col` term is the global write and later GEMM read, excluding original input/filter reads. `T_impl ≈ T_GEMM,useful/u + T_addr + T_predicate + T_tile_load`, where `u` captures matrix utilization and `T_addr` includes coordinate decode. `T_direct ≈ T_FLOPs/F_direct + T_redundant_loads/BW_eff + T_partial_write/read + T_reduce`, less spatial overlap when a tile retains input and weights. Direct wins when saved materialization/launch cost exceeds its lower effective math rate and any partial-output traffic. Implicit wins when matrix-engine utilization and reuse repay index/predicate work. Track peak live workspace, not just total traffic: explicit has roughly `B_col` live; direct split-reduction has its own `N·K·P·Q·R·S·e_acc` live; implicit GEMM has only the chosen tile and staging buffers.

For a systolic reference, Zhou et al. validate a TPUv2 cycle simulator against cloud TPUv2 measurements (mean error 4.87% on convolution microbenchmarks), then evaluate implicit channel-first im2col. Their synthetic `N=8,C=8,H=W=128,K=128,R=S=3` case needs multi-tile packing to fill a 128×128 array; simulator workspace rises linearly as tile count grows while performance gains diminish. This is simulator/design evidence, not a measured direct-versus-im2col TPU comparison. Systolic underfill can motivate concurrent spatial/filter tiles, while duplicated on-chip activations consume capacity. TPU/GPU results do not predict Arc.

Winograd's multiplier reduction is useful for small 3×3 filters, but its transforms add work and change summation/rounding. Lavin and Gray benchmarked GPU Winograd on VGG for batches 1–64; cuConv's exact examples above show transform kernels taking a large share when total work is small, while its larger shape favors Winograd. oneDNN explicitly warns of possible significant accuracy loss and restricts its documented path to FP32, ungrouped 3×3 stride-one convolution. Reduced products are not a free precision-preserving speedup.

## One future experiment design (not run)

Compare the three mappings on one GPU with a single FP32 NCHW forward implementation and identical `same` padding/stride-one outputs for shapes `(1,192,7,7)→384, 3×3`, `(1,384,13,13)→384, 3×3`, plus `(1,832,7,7)→256, 1×1`; add a batch-32 arm for each shape to expose launch amortization. Use identical accumulation/output contracts and correctness checks. Record end-to-end call wall time, each kernel's device time, host submission/setup time, launched kernel count, actual peak scratch, total global bytes read/written, achieved math utilization, and repeated individual samples. Explicitly time lowering separately and its consumer GEMM; for implicit and direct, report the corresponding main-kernel interval. This isolates materialization from compute without conflating bytes, launch cost, padding, or batch.
