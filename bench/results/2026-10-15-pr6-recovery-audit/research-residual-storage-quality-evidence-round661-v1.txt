# R661 — external quality evidence for lower-precision inter-layer residual storage

Date: 2026-10-15 JST. Read-only source and public-A-artifact review. No build, test, GPU, process, Git, cleanup, private B, active ON log or environment inspection was performed. No work-in-progress proposal was read. Only this report was written.

## Finding

The nearest direct external result remains the one already identified by R569: the Qwen authors' Qwen3.8-Next architecture paper. It is unusually relevant because it discusses the exact Qwen3.8-Flash-Next gated residual (four branches), and says residual values are kept in a narrow range by GR, gated-attention and GDN gates; the authors report inference residual-state FP8 storage uses half the bytes of BF16 with “almost no loss in quality.” The paper also says residual state supports FP8 storage at inference. This is credible positive evidence that low-precision residual **state** is viable in this architecture family and is stronger than generic “framework supports half” claims.

It is not a quantitative FP16/BF16 result and does not match the current Strata boundary closely enough to establish quality. In the cited result the paper does not identify the FP8 encoding/scaling/rounding, checkpoint weight dtype/quantization, evaluation prompts/tasks/context length, quality metric, measured delta, or whether each stored state is restored to FP32 before the next operator. It does not say that only storage is narrowed while all arithmetic and accumulations remain FP32. The byte comparison is FP8 versus BF16; Strata's experimental change is 4-byte FP32 residual storage to 2-byte FP16, with FP32 arithmetic restored at each consumer. These are different format and comparison baselines. FP8's unspecified exponent/scale behavior prevents assuming that its success implies FP16's narrower exponent range is safe, even though FP16 has more significand bits than common FP8 formats.

**Direct evidence for FP16 or BF16 boundary-only storage with FP32 arithmetic in Qwen3.8-Flash-Next or a comparably close Qwen3-Next/HC MoE model: none found.** The Qwen author result supports investigation, not “near-zero loss” for Strata's change.

The Qwen3.8-Next paper further cautions against treating one metric as the full quality outcome: its introduction describes other residual/architecture changes whose pretraining metrics and downstream quality diverged. That is a reason to check task quality as well as numerical deltas, not evidence that FP16 storage will harm or preserve quality.

## Reconciliation with existing A evidence

R569 already named the Qwen3.8 paper as the strongest external evidence and specified that it did not establish Strata's precision, model checkpoint, hardware, or layer-by-layer storage boundary. R573 set a separate paired quality gate; this report reuses that distinction rather than treating a numerical screen as acceptance. R580's placement-divergence report concerns an FP32 GPU-prefix versus host-tail mismatch and remains a separate unresolved route/copy question. It does not qualify lower-precision storage.

The current A registry describes the FP16-storage implementation as having passed small mechanics tests while synthetic cumulative residual relative-L2 was about 9.73% and first-logit KL about 0.027 nats; it marks natural quality/performance unqualified (`research-index.json`, `layer_major_fp16_storage`). The post-hoc saved-value screen (`saved-residual-precision-screen-v1.json`) reports one-cast FP16 relative-L2 `0.00021125` on 5,539,840 sampled final-layer scalars at 541 positions, with no cast nonfinites and one underflow-to-zero. That is a representation error for a **single post-hoc cast of already-produced FP32 values**, not the accumulated effect of 47 inter-layer round trips. Neither number is a capability-loss rate, benchmark score, or “quality degradation percentage.” Keep those distinctions and their recorded FAIL/PASS statuses intact.

Main supplied this round's boundary condition: current FP32/b1 matched IQ ON10041 has been measured. This report did not read its raw logs. It is a useful source/configuration anchor for a candidate comparison but says nothing about the quality of FP16/BF16 storage until a paired residual-storage arm is run.

## Application to the Strata condition and remaining evidence

The relevant candidate is exactly: keep GR/MoE/GDN/QSA and all operators/accumulations in FP32; after each non-final layer's residual result, store the inter-layer row in FP16; restore it to FP32 once before the next layer consumes it. This causes repeated rounding across the 47 boundaries. The last-layer callback remains FP32. The Qwen paper's result is about residual state storage but leaves open whether it used this boundary-only round-trip pattern; it cannot establish that condition by itself.

Before any quality or support claim:

1. Keep the same IQ checkpoint, source revision, prompt token IDs/template, sampling, context length and fixed FP32/b1 baseline as the measured matched arm. Run FP16 and BF16 as separate arms; do not pool them under “16-bit.” Verify exact store/restore behavior and finite/overflow/underflow counts by layer, branch and position. Keep performance/capacity results separate from quality.
2. Measure numerical impact after all layer-boundary round trips on natural histories: paired full-vocabulary KL, target-token NLL delta, top-1/top-2 and margin-conditioned flips, plus residual error at sampled layer/position boundaries. Include first/middle/final prompt positions and chunk, prefix/tail, host/GPU transitions. A one-cast residual screen cannot substitute for this.
3. Use independent held-out task examples and long-context retrieval at increasing lengths, including the configured 262,144-position boundary before making a full-context claim. Report paired category/length results and uncertainty. Reuse R573's sample-size and acceptance protocol; do not promote matching generated IDs or a small KL/NLL difference alone to broad quality qualification.
4. Preserve the paper's “almost no loss” wording only as an attributed, qualitative FP8 result on the Qwen authors' setup. There is no published numerical acceptance margin from that passage to reuse here.
