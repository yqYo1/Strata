# QSA indexer batching dependency contract (R680)

Read-only review of the configured root SYCL layer-major prefill route. No source edits, proposals, tests, builds, compiler, GPU/process inspection, environment mutation, private-B inspection, Git mutation, or cleanup were performed. This report does not qualify a new kernel, performance result, quality result, or 262,144-token physical run.

## Why batching is a concrete candidate

The long-window profile supplied for this review reports about 415,284 QSA indexer-append GPU calls and about 1.917 s of device service for that category, among about 1,017,611 device operations. The same supplied summary reports 140.105 s GPU busy union and 98.266 s visible GPU gaps. These are diagnostic observations, not clean throughput: the capture includes restore and one generated token, and profiler service, visible gaps, API time, and request wall time are different measures. The v1 compact report exceeded its declared output budget and is explicitly failed; do not use it as a validated grouped-kernel analysis. The v2 compact reanalysis is pending, so the profile call attribution remains provisional.

The source has already exposed a batch API, but it does not batch device work. `src/prefill/prefill.cpp:2146-2165` calls `native_qsa_indexer_append_batch(raw,T,p0,...)` once per QSA layer and prompt chunk by default. In `src/kernels/sycl/native_qsa_indexer.cpp:173-190`, the API validates once, then loops `i=0..n-1` and calls `append()` once per row; `append()` submits its own one-work-group SYCL kernel (`:79-85`). Thus low-level submissions still scale with rows. With 12 QSA layers and exactly 34,603 appended rows, the source-derived count is `12*34,603 = 415,236` append-kernel submissions; the supplied provisional trace says 415,284 (48 higher), a difference not reconciled here because its compact v2 is pending and its window also includes restore/decode activity. A real one-submit-per-QSA-layer-per-chunk kernel would be 12*9=108 append submissions for nine chunks (or 216 if a separate finalization launch is required), versus roughly 415K today. These are launch-count arithmetic only, not predicted speedup. The current path submits the other selector, top-k, and attention kernels separately and is not replaced by this candidate.

## Exact current order and causal contract

For each chunk, `src/prefill/prefill.cpp:1652-1660,1784-1788` chooses `T=min(chunk,n-c0)` and `p0=pos0+c0`, creates one `QsaStep` row per token, and uploads those rows on the prefill queue. For each QSA layer, source order is:

1. Project/normalize/rotate Q, K, V and project indexer K/Q (`prefill.cpp:2102-2145`). `m.idx_raw` is the raw indexer-key matrix `[T,128]`; `m.q_idx` already contains the query-side normalization/rotation.
2. Append all `T` indexer keys before any query selects or reads the indexer (`:2146-2165`). Default calls the native SYCL append-batch API; `STRATA_INDEXER_PER_TOKEN` routes each row through the single-cell API. The production input is `m.idx_raw`, row `t` corresponds to cell position `p0+t`, `pos_base` is currently zero, and each layer has its own `QsaIndexerBuffers` (`:2148-2163`). The existing queue is in-order, so the current serial submissions make every state write visible to the next position and later selector submissions without a host sync between rows.
3. For each selection microbatch, `qsa_block_scores` and `qsa_block_topk` consume the updated layer's `idx_pooled`/`idx_dead`, the query rows, and each query's own `steps` (`:2166-2181`). The selected IDs then feed prompt attention with this chunk's KV pools/page table (`:2267-2277`). The queue order is append -> scores -> top-k -> attention. Do not move the selection or attention before all pooled keys needed by the chunk have been committed.
4. After the final layer work for a chunk, `run_impl` completes the queue before delivering the layer-major `on_stage_chunk`/`on_chunk` callbacks (`src/prefill/prefill.cpp:3079-3090`, also mapped in R667). The MTP/draft callback consumes final-layer residuals and next-token IDs; a batch append must not return an error asynchronously or let any indexer state outlive its buffers/callback boundary.

The causal safety comes from per-query steps, not from withholding future chunk keys from memory. `qsa_step_fill` defines each query's `n_kv=pos+1`, `n_bid=n_kv/4`, and `width=min(n_kv,idx_top_k+idx_block-1)` (`include/strata/kernels/qsa.hpp:127-135,138-160`). The selector reads a query's own `n_kv/n_bid` and only scores blocks `b<=n_bid` (`src/kernels/sycl/qsa_select.cpp:26-63`); its top-k weights complete blocks by four cells and the incomplete tail by `n%4`, emitting only those IDs (`:72-142`). Below the selection limit, `n==width` returns the identity `[0,n)` (`:92-95`). The current prompt-attention call receives the query's selected-ID count and resolves those IDs through the layer's page table (`src/kernels/sycl/prompt_attention.cpp:123-153,344-404`). A batched indexer may produce future pooled rows before selection, provided it preserves per-query `steps`, score masks, tail count/bias, selected IDs, and same-queue dependency.

## State transition a true device batch must reproduce

The fixed geometry is 128 key components, four-token blocks, 64 rotated components; `QsaState` allocates a three-row FP32 tail, a 128-value `dead` spare, pooled block keys plus spare rows, and `block_pos` (`include/strata/kernels/qsa.hpp:96-116`; `src/core/layer.cpp:537-552,610-615`). The current native device transition at `src/kernels/sycl/native_qsa_indexer.cpp:79-155` is the bit-level oracle:

- At position `pos`, each component first rounds `raw[d]` to `sycl::half`, expands it to float, and writes `tail[(pos%4)*128+d]` only for slots 0, 1, and 2 (`:87-96`). This half-rounding must not be dropped or moved after the pooling average.
- Positions other than zero return unless `pos%4==3`. Position zero is the one-cell seed: it repeats the rounded row four times, so its mean is exactly the rounded input, then writes both `dead` and `pooled[0]` (`:97-104,148-150`). A fresh zero-based batch containing multiple blocks must make the correct dead seed visible to all later block work; independent work-groups cannot assume a global barrier inside one ordinary SYCL kernel.
- For each completed block at slot 3, the exact reduction order is `tail[0] + tail[1] + tail[2] + incoming`, then `fma(.25,sum,0)`. It performs the current 128-value FP32 RMS reduction, `rsqrt(ss/128 + eps)`, multiplies by `gamma`, and rotates the first 64 lanes at position zero or `pos_base + 4*(pos/4)` (`:99-147`). Keep the same float conversion/reduction order if bitwise parity is required; one changed pooled key can change a near-tie top-k route (R581/R593).
- A completed block writes its key to `pooled[block]`; position zero sets `dead`; any other completion copies the existing `dead` spare into `pooled[block+1]`; and nonzero completion records `block_pos=pos_base+4*block` (`:148-154`). Tail positions do not update pooled rows, dead, or block_pos. The globally visible tail after a chunk must be the final block's first three half-rounded input rows, including when a chunk ends after slot 3; that state is reused by a later chunk or restored session.

The simplest safe parallel shape is independent block work plus explicit single-writer/finalization rules, not one work-group per token racing on `tail`, `dead`, adjacent pooled rows, or `block_pos`. Blocks in one call can write distinct completed keys, but every work-group must not write the shared tail/block_pos. The spare-row copies also overlap the next completed block's key row if every block writes them. Handle fresh `pos=0` dead initialization before groups consume it, or compute the same seed without a race; ensure only the final completed block publishes the spare row when it is actually the terminal spare. A separate small finalization kernel is a viable correctness-first option, still reducing a chunk to one or two launches. These are source-derived constraints, not a prescribed optimized implementation.

`pos0` and `pos_base` are distinct. The native API's `p0` is the relative cell index and its `base` is the sequence's first absolute position; `base` must be nonnegative/divisible by four, and `base+capacity` must fit `int32` (`include/strata/kernels/native_qsa_indexer.hpp`; `native_qsa_indexer.cpp:38-56,173-183`). Do not derive RoPE position from the chunk-local row. A nonzero `p0` that begins in a partial four-cell block must continue from valid previous `tail/dead/pooled` state; a zero-initialized state at arbitrary `p0` is not a valid history. The fixture should seed the prefix rather than silently treating nonzero `p0` as a new sequence.

At maximum logical capacity, `C=262,144` means 65,536 four-cell blocks and final cell position 262,143. A call over `[262,140,262,144)` closes block 65,535 and writes key row 65,535 plus spare row 65,536; `capacity/4+1` pooled rows cover that highest index (the state allocation includes the spare capacity, `qsa_state_bytes` pooled sizing at `layer.cpp:545-552`). Guard final writes and preserve signed position/capacity checks. A final query has `n_kv=262,144`, `n_bid=65,536`, `n%4=0`; its extra incomplete-block candidate has zero cell weight in top-k. Never modulo the block/page to fit a smaller scratch. Full physical-context correctness remains a separate end-to-end gate.

## Snapshot, RESTORE and MTP boundaries

The full QSA state is per layer; do not share its `tail/dead/pooled/block_pos` between QSA layers. Conversation snapshot stores the QSA K/V plus pooled indexer rows (`include/strata/core/conversation_cache.hpp:41-49`; `src/core/conversation_snapshot.cpp:40-56,143-174`) and validates/restores them with the same K/V/indexer geometry. The running checkpoint additionally saves each QSA layer's tail, dead and block_pos (`src/core/conversation_state.cpp:154-169`); restoring a checkpoint writes these states and seeds the moving pooled spare from `dead` at the restored prefix (`:172-192`). For streamed mode, the saved host K/V is authoritative and restore resets the map before later selected-block resolution (`src/core/conversation_snapshot.cpp:200-215`). A candidate therefore needs exact end-state parity not only for attention output, but for pooled rows and the moving tail/spare so a later `RESTORE` or resumed append sees the same state.

MTP's prompt callback is installed as `Prefill::on_chunk` and pairs final residual row `i` with prompt token `i+1` (`src/program/generate.cpp:6435-6441` standalone; serve path `:4961-4966`). Preserve the existing callback order and queue completion after QSA attention and final-layer residual computation. Do not cause MTP to observe chunk output while the indexer batch still has queued writes or while the final layer is incomplete. In layer-major execution, intermediate per-chunk checkpoint callbacks are an existing separate concern: R608 records that earlier QSA layers may already hold the full range when the final-layer callback reports a shorter prefix. This batching candidate must not claim to fix or qualify that checkpoint schedule; keep current callback policy and require the existing RESTORE gates.

## Minimal falsifiable fixture and priority

There is already a useful but insufficient baseline in `src/kernels/qsa_parity.cpp:1380-1454`: it compares eight cells, two completed blocks, and none/linear/YaRN scaling with `memcmp` over pooled/dead/tail/block_pos. Today both sides use the same one-cell append operation because the batch API itself loops; it does not validate a new parallel kernel or chunk-split partial state.

A minimal candidate fixture should clone state and compare a genuinely batched kernel against sequential single-cell appends, with exact `memcmp` of tail, dead, every valid pooled row, and block_pos after each checked batch. Include: fresh `[0,1)` seeding; several cells and multiple blocks in one call; split calls ending/starting at slots 1, 2, and 3; a nonzero `p0` continued from a seeded prefix; `pos_base=100` with the documented cell-to-RoPE mapping; final incomplete block; none/linear/YaRN scaling; invalid/overflow range rejection; and final physical indices 262,140..262,143 with guard canaries for row 65,536. For each position, feed cloned step rows through current block-score/top-k and require exact selected-ID equality, especially n=1/3/4/5 and n=2,051/2,052 (identity-to-top-k boundary). A snapshot save/restore continuation should preserve the same next pooled/key/ID state; keep an MTP callback only after the final chunk fence. The full 262K allocation/run, output parity, quality and speed tests are later gates, not part of this proposed small fixture.

Priority is high enough for a narrow kernel candidate because source proves one kernel submission per token despite the batch API, and the provisional profile reports the corresponding call volume. Keep the implementation default-off until the independent batch-vs-sequential state fixture, causal selected-ID check, RESTORE continuation and later end-to-end matched measurement pass. The existing shared-QSA quality and long-prefill correctness gates still apply. No performance prediction is made from ~1.917 s append service or ~98.266 s visible gaps: batching targets dispatch volume only, while output math, QSA selection/attention, GDN, MoE, transfers, CPU work and waits remain. Re-evaluate the complete `AppendLaunchKernel` and device interval totals only from the compact v2 analysis after its hash/count checks pass.
