# R637 — bounded wave scratch の region alias と同時生存 owner

2026-10-15 JST。R633/R636、R621–R623、および既存の Prefill scratch/owner 調査を先に読み、現行 SYCL source の `Prefill::carve`、layer-major residual、FFN/GDN/QSA/MoE、MTP callback を照合した。読み取り専用。source、build/test、GPU、process、Git、cleanup、benchmark raw は操作していない。新規作成は本報告のみ。

## 結論

**R633 の retained subtotal をそのまま全て別々の新 allocation として加算する必要はない。ただし `m.region` 全体をfree scratchとみなして wave state を置くこともできない。** `carve` はGDN、QSA、MoE scratchの最大サイズを一つの `m.region` として確保し、三つの内部配列配置を同じbaseから重ねる。現行の一chunk処理では attention 完了後にMoEを行うため成立する。wave causal prepassでは、前chunkから保持したroute/prepared dataと、現在chunkが使うQSA/GDN scratchが同時liveになり得る。したがってwave retentionには別のlive領域が要り、regionを再利用できるのは、先行データを別ownerへ保存済みで、該当scratchの全queue accessがchecked drain済みの区間に限る。

容量算術だけでも、full context 262,144、chunk 8,192、現QSA geometryでは `m.region` のQSA枝は約1.644 GB、MoE枝は約1.088 GBで、QSA枝が最大となる。QSA `sel_ids` と `Qf` がそれぞれ約1.00 GiB、384 MiBを占める。一方、2-chunk waveの正確なroute-slot `Dm` は1.5625 GiB、4-chunkは3.125 GiBであり、どちらも既存region容量を超える。2-chunkでは `Dm`だけでもregionより約31.9 MiB大きく、expert tile workspaceも別途同時liveに必要。従ってこの最大chunkではregion単体への全wave `Dm` overlayは成立しない。

ただし、既存chunk-sized allocation分を再利用し、wave bufferを単一拡張arenaまたは少数ownerへまとめれば、R633の *全* subtotalを新規bytesとして二重計上する必要はない。FP32 `Dm`の増分は既存C-row planeとの差、prepared/route/shared/injectionも既存chunk buffersとの差として算定する。さらに `Rstore` の同一rowを入出力bankとして安全に使う設計が成立すれば、別FP32 R planeは回避できる。ただし保存Rを上書きする時点と、FFN後の `gr_write` に必要なattention段階値の保持は新しいchecked ownership contractであり、現行callbackが保証するものではない。

すべての値はsource shapeから計算した論理容量である。GPU allocatorのlive free、`m.region`内の実際の同時live bytes、fragmentation/headroom、wave arenaの実fitは未測定であり、容量式から採用可能性やfree VRAMは結論しない。

## 既存のcarveとphase lifetime

`Prefill::carve(T)` は `m.region_bytes = max(gdn_set_bytes(T), qsa_set_bytes(T,...), moe_set_bytes(T,...))` を一回の `o.take<uint8_t>` で確保する。その後、同じ `base` と `region` capから独立した `Alloc a`, `b`, `c` を作り、各々GDN、QSA、MoE pointerを配置する。この三配置は相互にaliasする。sourceコメントにもattention halfとMoE halfは順次実行され、最大の一領域を共有するとある。これは一chunk pathのpeak accountingで、複数chunkのretained stateと現在chunkのscratchを重ねる計画ではない。

wave prepassはchunk順でattention/GDN/QSA/PLEとFFN preludeを進める。QSAの `Kc/Vc/Qf/q/idx/attn/sel_ids/sel_scores` またはGDN buffersは、現在chunkのdevice work完了まで必要。一方、前chunk分の `mixed_h`、shared result/gate、route IDs/weightsとexpert outputsは後続wave workまで保存する。したがって、例えば2-chunk waveのchunk 1をQSA処理するとき、chunk 0のprepared dataを同じ領域へ上書きできない。FFN prelude中のroute/activation scratchにも同じlive overlapがある。sourceの `m.region` pointerやbyte countからこの追加bufferとの実際のfree subspanは示されない。

wave expert phaseではQSA/GDN scratchは使われないので、その時点で `m.region` を再配置し直す候補はある。しかしそこにwave `Dm`を置くなら、同時に必要なexpert microbatch workspace (gathered X, GU FP32, H/`Hh`, Down input)、route-map lookup、combine入力も差し引く必要がある。単にattention終了後に全 `m.region` を `Dm` と呼び替えるのは不正確。regionを拡張した場合も、QSA phaseではQSA scratchとretained stateが重なるので、必要capは両者の和または別領域の合計で評価する。

## Source byte geometry

layer-major admissionは `n<=262144`, `chunk<=8192`, `N=2560`, `D=HC*N=10240`, `K=10`, `NE=512`, QSA `idx_block=4` を要求する。max logical cell数262,144では `max_blocks=262144/4+2=65,538`、`cap=qsa_selection_width(kTopkMaxCells)=32,771`。`sel_ids`は `T*cap*4`、`sel_scores`は `256*max_blocks*4`、`Qf`は `T*12,288*4` bytes。これらは `qsa_set_bytes` の実source operands。

C=8,192時のsource-counted region arms:

| Overlay branch | payload + `Alloc::take` padding | 主な大きさ |
|---|---:|---|
| QSA set | 1,644,273,525 B (1.531 GiB) | `sel_ids` 1,073,840,128 B、`Qf` 402,653,184 B、`sel_scores` 67,110,912 Bなど |
| compact FP16 MoE set | 1,087,675,378 B (1.013 GiB) | `Dm` 838,860,800 B (800 MiB)、`shared` 83,886,080 B、`Xs/GU`各41,943,040 Bなど |
| GDN set | smaller than these two for this geometry | `gdn_set_bytes(T)` の同じcounting allocator |
| chosen `m.region_bytes` | 1,644,273,525 B | 三枝の最大値 |

数字は `Alloc::take` が各 item に `(bytes+256+255)&~255` のpaddingを加えるsource arithmetic。`m.region`がこのサイズで確保されることはsource count上の事実だが、これを同じ時間帯にfreeな容量と扱えない。active QSA/GDN bufferとの重なりとqueue workがある。

FP32 route-slot `Dm=W*K*N*4=102,400*W` bytesである。`W=min(q*C, prompt rows in this wave)`。上限contextでは次の通り:

| Chunk C | q | W rows | Dm logical bytes | Existing C-row Dm | Dm delta vs C-row |
|---:|---:|---:|---:|---:|---:|
| 4,096 | 2 | 8,192 | 838,860,800 (800 MiB) | 419,430,400 (400 MiB) | 400 MiB |
| 4,096 | 4 | 16,384 | 1,677,721,600 (1.5625 GiB) | 400 MiB | 1.171875 GiB |
| 8,192 | 2 | 16,384 | 1,677,721,600 (1.5625 GiB) | 838,860,800 (800 MiB) | 800 MiB |
| 8,192 | 4 | 32,768 | 3,355,443,200 (3.125 GiB) | 800 MiB | 2.34375 GiB |

R633's all-retained plane subtotal for exact output slot order is `117,940*W` bytes: `Dm`, FP16 `mixed_h` (5,120 W), shared FP32 (10,240 W), HC `inj` (16 W), scalar `sg` (4 W), and four 32-bit per-route tables (160 W). It is 966,164,480 B (0.900 GiB) for C4096×2, 1,932,328,960 B (1.800 GiB) for C4096×4 and C8192×2, and 3,864,657,920 B (3.600 GiB) for C8192×4. IDs/weights/slot/src are a conservative four-array layout; an implementation could recompute some maps from retained IDs/weights at extra host work, but exact slot mapping must survive through `moe_combine`.

Those are **gross live payload**, not all-new allocation bytes: C-row `Dm`, `mixed_h`, shared/gate/injection and route buffers already exist in current carve, though most are inside the aliased region and cannot all remain live after expansion without a layout change. The logical incremental growth from C to W for the per-token planes is approximately `(q-1)*C` times each plane size, before alignment and microbatch. A complete capacity plan must also add the current chunk's QSA/GDN or expert tile workspace during the phase that overlaps it. Thus neither `m.region_bytes` alone nor `gross subtotal` alone is the correct allocation delta.

## What can be borrowed or reused, with gates

- **One region allocation, not three concurrent scratch sets:** current QSA/GDN/MoE scratch arrays can keep using one shared region in their ordinary sequential phase lifetimes. New wave retention may be laid into a re-planned region after sizing peak overlap; only buffers whose last device/copy-queue reader/writer has completed can be overlaid. A host-side phase transition alone is not a fence. On the configured layer-major route `m.copy==m.cs`; use checked `cudaStreamSynchronize(m.cs)` after all relevant operations and before repurposing bytes. On failure/cancel/drain error, retain owners and invalidate the wave; do not reclaim aliases by restoring C++ fields.
- **Existing C-row MoE arrays:** the first C rows of `Dm`, `mixed_h`, `shared`, `sg`, `inj` and route arrays can be part of wave storage after changing shape/stride/accounting. Count only their incremental W−C capacity as growth. Since `Dm` and the other MoE arrays are currently aliases inside `m.region`, an enlarged contiguous region or explicit new owners are needed; pointer reuse without updating capacity and strides overruns the existing allocation.
- **Expert decoded weights:** current `dq_gu[DQ]` and `dq_d[DQ]` are separate top-level allocations outside `m.region`; at `N=2560,n_ff=640`, one GU+Down pair is 9,830,400 B (9.375 MiB), and DQ=2 is 19,660,800 B total. A serial expert loop can reuse the existing pair; a bounded ref microbatch only needs Xs=`B*N*2`, GU=`B*1280*4`, Hh=`B*640*2` plus existing B-sized intermediate workspace. `B<=C` avoids making expert tile workspace W-sized even though an expert may have up to W routed rows; split that expert's references into microbatches while retaining its decoded pair. A parallel two-expert/two-queue pipeline would need explicit additional weight-pair and queue ownership, not presumed free capacity.
- **Interlayer `Rstore`:** existing plan owns `n*D*4` bytes FP32 by default, 10,737,418,240 B (10 GiB) at n=262,144, split GPU prefix/host tail. It already holds each layer's input/output residual between passes; it is not spare total capacity. A safe in-place strategy can reuse each row as output only after its prior-layer input has no further readers. To defer the FFN after attention while preserving the original input, the wave also needs the post-attention residual (40,960 B/row), or a replayable decomposition (saved attention `bo` and `inj`, then reconstruct after rereading the untouched input). Do not charge a new FP32 R plane if an in-place row lifecycle is explicitly proven and the row can be overwritten with the post-attention value after input consumption, then reloaded for delayed FFN; but this changes the residual-bank state/callback boundary and needs a checked schedule. Conservative design lacking that proof adds `40,960*W` bytes: 320 MiB / 640 MiB / 640 MiB / 1.25 GiB for the four rows above. The existing FP16 residual option is not assumed; it changes saved boundary precision and does not provide the needed FP32 wave history contract.
- **MTP callbacks:** `on_chunk` receives final-model FP32 residual `m.R` only after chunk queue sync; layer-major wrapper defers user chunk callbacks until final layer. `draft_kv` consumes those final rows and may advance draft QSA state. `on_stage_chunk` is delivered only at the final request boundary in this full-model route. A wave prepass's advanced GDN/QSA/PLE state paired with incomplete residual/FFN output is not a valid callback/checkpoint point. Keep callbacks withheld until every wave expert product, combine, HC write and residual commit succeeds; then deliver chunks in original order. MTP may need wave output rows to be loaded from committed residual store because `m.R` is only C rows. Any upload/borrow must survive a checked same-queue completion. This matches R633/R621 callback boundary, not a new MTP optimization.

## Bounded microbatch scratch and MTP overlap

The routed expert path currently gathers each expert's rows into `m.Xs`, runs GU into `m.GU`, SwiGLU into `m.Hh`, then Down writes `m.Dm` for original route slots. These are chunk-sized source buffers (`m.Xs`: C*N FP16; GU: C*1280 FP32; Hh: C*640 FP16); their current storage is in the aliased region. A wave can keep `Dm` W-sized while using only B rows of these temporaries, but then the expert loop must carry a stable expert-ref list and output offset into the wave slot plane. It cannot let the next microbatch overwrite earlier Dm rows. `moe_combine` requires route-slot-ordered Dm entries and combines shared/gate after all per-row route slots are available.

MTP is downstream callback work, not concurrent with current routed expert compute in the ordinary route. To bound peak, do not call MTP during causal prepass and do not hold its draft callback owners concurrently with region retirement. After final output commit, invoke `on_chunk` for each row block in ascending order as the current contract requires; if callback processing causes its own workspace or state to stay live, account it as an additional peak owner. Existing `MtpDrafter::prefill` upload/scratch and expert-retirement work are not part of `m.region`; prior owner-retirement reports found no generic release API and do not establish extra headroom.

## Admission arithmetic and boundary

Maximum context affects persistent row stores and QSA state, while wave row capacity is bounded by `min(n_remaining,q*C)`, not n alone. At full context, Rstore alone is 10 GiB FP32 (or 5 GiB if explicitly FP16); it is already existing layer-major owner. The max wave retained payload numbers above do not include row-store bytes, the active expert cache, the existing 32 MiB GEMM scratch/workspace allocations, QSA/KV stages, resident model/session data, or allocator reserve. The source `run_layer_major` admission reserves 512 MiB GPU and 8 GiB host headroom for its known residual/cache owners; any wave extension must include all incremental device/host owners in checked aggregate admission before session state advances.

No actual live-free measurement was requested or performed. The R594/R599 1,662,831,872 B `Impl::owned` accounting is not free memory and cannot be added as a hypothetical reclaim unless a separate checked retirement implementation actually releases it. Likewise source arithmetic for the 1.644 GB region does not prove that capacity is free at a later point, that a larger arena fits, or that allocation succeeds at 262K.

## Required lifetime/fence boundary for a prototype

1. Before reusing any region subspan, establish that QSA/GDN/prelude kernels and copies no longer read/write it; on current admitted route use checked same-queue drain. Region aliases are not independently retireable owners.
2. Give every wave buffer an explicit owner, W/B capacity, row stride and phase tag. Retained data stays live across subsequent chunks; only scratch whose last consumer has completed may alias it.
3. Keep original residual inputs alive until their attention/preparation consumers finish. If reusing Rstore in place, prove per-row source completion and replay/reload requirements; otherwise reserve the complete post-attention FP32 R wave plane in the checked budget.
4. Preserve exact router decision, weights and per-token route slot mapping. Keep Dm output slot lifetime through unchanged `moe_combine`; do not use expert completion order as reduction order without a separate numerical gate.
5. Check each submission and the drain even after submission failure; on drain failure retain all wave/region owners and reject future continuation until reset/RESTORE policy establishes coherent session state.
6. Publish MTP/public chunk and checkpoint callbacks only after final residuals are coherent. MTP callbacks run in original position order; no callback at the partial causal-prepass boundary.
