# R632 — decode expert-cache 128/192/256 capacity screen の source readiness

2026-10-15 JST。R624/R625/R626、R584/R594/R607/R608とcompact decode ledgerを読み直し、現行root SYCLのCLIからcache、resident route、Verifier/MTPまでをread-onlyで追跡した。新規計測なし。既存reportは変更せず、新規ファイルは本報告だけ。build/test/GPU/process-control/Git/cleanup、活動中benchmark rawの読取りは行っていない。対象はSYCL/native single-device Qwen3.8-Flash-Next IQ3_Sの現在の`--expert-cache 128 --expert-cache-per-layer`、MTP4 decodeである。

## 結論

容量screenはCLI上、`--expert-cache`の値だけ128→192→256にし、`--expert-cache-per-layer`、profile、MTP/KV/context、Prefill、CPU poolなどを固定して行える。ただしこれは「既存128 slotsへ64/128個を単純追加」するarmではない。現行のlast-layer remainder partitionを同じtotal数から再計算するため、slot数だけでなく層ごとのquotaとprofileから入るexpert集合を変える。特に128→192では最終層47のquotaが34から4へ30減り、他47層は各2増える。容量増によるhit上昇と最終層の大幅なresident入替えを一緒に測る。R607のappend-only `+128/+256` CPU route ceilingはこの配置変更のhit予測に流用できない。

現行sourceはper-layer native cacheの正確なbyte arenaを起動時に一括確保する。explicit 128/192/256で不足した場合はauto-sizeへfallbackせず、allocation拒否/失敗で起動を止める。`ExpertCache::open_sized`のfree queryはarena要求byteを確保できるかを見るが、explicit armの700 MiB reserveは保証しない。R584の700 MiB reserveはsweepの安全条件として維持し、cache確保後・profile fill後・MTP/Verifier/Prefill準備後の実free値を確認する。192/256が入らない時にPrefill/cache退役案で続けず、そのtierを拒否する。

既存出力で新observerを作らず比較できる量は、実slot数、MiB丸めのcache量、request hit率、CPU/GPU/other ownerの集計、層ごとのCPU jobs/rows、MTP窓とCPU serviceである。exact arena bytesは出力に整数byteでは現れず、起動時の実slots・層ごとの`expert_layout.blob_bytes`・現行partitionから計算してreceiptに記録する必要がある。hit率とaggregate route countersは実動作screenには足りるが、現在profileのexpert ID別適合や各新容量の理想hit率を決めるものではない。

## CLIからMTP verifierまで

1. `generate.cpp` parserは`--expert-cache N`をtotal slotsとして読み、`--expert-cache-per-layer`は独立bool。`--expert-cache 0`にprofileが付く場合はauto扱いになるため、capacity armでは明示的な正数128/192/256を使う。`auto`/0を含めると別の容量選定policyの比較となる。
2. `--expert-profile P`は起動時のranked pair列を読み、current model/routingへの頻度計測ではない。R584ではprofileはshape-compatible 48×512 full rankingだが、model weightsやroute corpusへ結び付くfingerprintではない。比較では同一profile file hashを固定する。per-layer modeのstartup fillはprofile全体を走り、各layerのquotaを満たした後のpairをskipし、各層上位rankを初期cacheに入れる。
3. `native_pack && expert_cache_per_layer`では各layerの`blob_bytes(layer)`から同owner layerサイズのslot列を作り、`open_sized`へ渡す。各slotは256-byte alignされたoffsetを持つ単一arena。`ExpertCache::layer_slot_range`は`q=S/48`, `lo=l*q`; 最終層だけ`S`まで拡張する。`admit`は層ごとのcursorを使い、adaptive replacementも同層内のslotを交換するためraw capacityは維持される。cacheはexpertの元packed blobを層所有slotへcopyする。native Q8_1のSYCL hit arithmeticへroute ownerを移すのであって、`--expert-cache`変更でIQ3_S weightsを新しいQ8 weightへ再量子化する処理ではない。
4. CacheはVerifier/MTP setup前に開き、profile fill後にVerifierの`VerifyHits`へ`base`, `slot_off`, `blob`, `n_slots`を渡す。`Verifier`は各Tのgraphを初回実行時lazy captureし、native hit graphやper-layer planはcache slot pointer/offsetを使う。capacity変更は**fresh process startup時だけ**行う。起動後close/reopen/resizingや同じVerifier内のcache差し替えは既存graphのpointer lifetimeを壊し得る。armごとに別processを使い、active adaptive refill/eventを跨いでcacheやenvironmentを変更しない。
5. MTP draft model/cacheは`--expert-cache`対象のtarget `ExpertCache`とは別owner。target VerifierがMTP proposalsを同じ窓で検証し、target cache residency変更がtarget logits/accepted A/Verifier T distributionを変える可能性がある。そのためMTP4/spec/min-p/normal-or-coupled modeは固定し、`W,R,D,A,C,E`, MTP acceptance/draft cost、CPU rows/service、decode E/wallを同じreceiptで読む。draft cacheのhitやMTP graph準備をtarget-cache hitとして数えない。

## Per-layer geometryとexact arena bytes

現packのread-only `native_experts.txt` layout metadataに保存された48層blobサイズは全て256 B倍数で、countsは以下。これはweight tensorを読まずに算出したlayoutで、GPU allocation receiptではない。

| 1 expert blob bytes | 層数 |
| ---: | ---: |
| 1,510,400 | 5 |
| 1,715,200 | 3 |
| 1,868,800 | 1 |
| 1,971,200 | 15 |
| 2,176,000 | 14 |
| 2,329,600 | 9 |
| 2,662,400 (layer 47) | 1 |

Sum over one slot in all 48 layers is 98,227,200 B. Since aligned already, `arena(S)=q*sum(blob_bytes_by_layer)+r*blob_bytes_by_layer[47]`, where `q=S//48`, `r=S%48`.

| `--expert-cache S` | current quota layers 0–46 / layer 47 | exact arena bytes | MiB | delta from 128 |
| ---: | ---: | ---: | ---: | ---: |
| 128 | 2 each / 34 | 281,651,200 | 268.604 | — |
| 192 | 4 each / 4 | 392,908,800 | 374.707 | +111,257,600 B / 106.104 MiB |
| 256 | 5 each / 21 | 533,734,400 | 509.009 | +252,083,200 B / 240.405 MiB |

At 192: layers 0–46 each gain two slots, layer47 loses 30, total +64. At 256: layers 0–46 each gain three, layer47 loses 13, total +128. Because profiles are layer-conditional, the entries selected at layer47 and all other layers can change. The same `--expert-cache` arg controls total count, but neither resident map nor per-layer hit opportunity changes monotonically by implication. `balanced-layer-cache-v1` would use a distinct quota rule (128 = 32 layers×3 + 16×2) and source diff; do not apply it or conflate its byte table with this legacy screen.

## Admission, fallback and async lifetime

For this single-GPU explicit setting, `open_sized` creates offsets and passes summed arena bytes through `ExpertCache::open`; that performs a free-memory precheck for `want` and then one `cudaMalloc`, zeroing, and pinned staging allocation. If `cudaMemGetInfo` reports fewer bytes than `want`, or allocation/init fails, `generate` returns an error. The retry-and-shrink loop is conditional on `auto_cache`; explicit `--expert-cache 192/256` does not silently fall back to 128/less. Its check is only `free >= want`, not `free >= want + configured reserve`. Startup free-after-allocation/serve `INFO vram_free_mib` and low-free warning are evidence, but a successful arena `cudaMalloc` alone does not prove later MTP/Verifier/Prefill allocations fit without paging or failure. Preserve the established reserve and reject any tier that consumes it. If Main wants an exact full-system safety margin, use existing phase memory marks/free query receipts at the startup boundaries; do not change cache after graph capture.

With a profile and batched Prefill, `pf_borrow` defaults on unless `--no-prefill-borrow`; Prefill uses tail slot offsets until exact `Prefill::bytes_needed(chunk)` fits, retains 128 nonloan slots, streams any loaned experts during prompt, refills their same slots, and publishes residency before decode. Since the tail geometry changes with S, record actual borrow `first`, slot count, bytes, refill/publish success and free-after-prompt. Keep `--prefill`/chunk and borrow flag fixed. A lower final-layer quota may cause the loan to cross layer boundaries differently; do not infer equal prefill traffic from equal chunk setting. Cache/scratch retirement proposals remain unapplied and must not serve as admission fallback.

Adaptive replacement defaults to active (`adapt-every=4`, swaps normally 96); it updates same-layer residents asynchronously and only publishes a swap when transfer completion is observed. For a first static capacity screen, set `--adapt-swaps 0` identically across 128/192/256 to remove this source of time-dependent resident identity. If the production/default adaptive policy is the eventual target, evaluate it as a separate matched triplet after static screen. Never alter the cache/process environment after SYCL/runtime init. Existing fill is blocking and startup verification reads back one profile slot; the rest of startup cache validity is supported by per-fill error checks, not a whole-arena readback. Cache live swaps and Verifier graphs are async owners; no same-process capacity changes.

## Which existing evidence suffices

No new observer is needed for the first screen. Existing successful serve request output provides:

- `INFO ... expert_slots_primary ... expert_cache_primary_mib ... vram_free_mib` for actual primary slot count and floor-MiB arena report; startup `expert cache N slots, X.XX GiB` and `pre-filled ... slots` cross-check requested/admitted count. Use exact arena arithmetic above to supplement rounded bytes.
- `decode expert cache hit rate: hits/lookups` by request. R624/R584 note PCIe-served misses are excluded from this ratio; read joined ledger owner classes for CPU/VRAM/other owner totals instead of treating `1-hit rate` as CPU share.
- The retained MTP4 decode ledger contains W/R/D/A/C/E, per-layer/T CPU jobs, CPU rows, route-entry counts, owner totals, unique jobs/nt and CPU thread service. It can show aggregate or per-layer route movement and whether CPU work fell; it does not retain expert IDs in that compact receipt. The `cpu-gpu-cache-opportunity-v1.json` is one 34,603/128 request's CPU-owner hindsight ceiling, not a new-capacity result or ID-disjointness guarantee.

Exact per-expert profile hit fit, current GPU-resident ID overlap with CPU route histogram, future route ceiling, physical DRAM/H2D bytes, GPU kernel saturation, and whether CPU work moved onto the GPU profitably are unknown from these outputs. Do not add a new tracing observer to this first capacity comparison; if aggregate owners indicate a promising arm, later authorized diagnosis can decide whether IDs or bounded device trace are necessary.

## Implication for 70 tok/s and acceptance

The retained normal MTP4 first 34,603-input/128-output receipt has 36.734 CPU thread-seconds (GU 25.533, Down 11.102, quant 0.099), 101,036 CPU rows /104,160 routed entries (97.00%), decode loop 25.544 s, GPU-boundary host wait 7.713 s and pool callback wall 8.363 s. The wait/callback/run timers overlap; they cannot be summed as exclusive time or described as GPU kernel time. CPU thread service is concurrent resource-seconds. At unchanged work it is 36.734/128=0.28698 CPU s/output. Sustaining 70 outputs/s would require ~20.09 CPU thread-seconds each second; with the configured 5 workers+issuer (six participating threads on six physical cores), the same CPU service cannot exceed 6 thread-seconds per wall-second. Conditional on unchanged route/service, the simple CPU-service screen is ~20.9 output/s, and 70 requires CPU service to fall below 0.0857 CPU s/output (~3.35× reduction). This is not a hardware/model bound because GPU ownership, route mix, MTP acceptance, work/output and CPU kernel cost can change. It does show why a small hit-rate gain or 192/256 capacity alone cannot be assumed to reach 70.

R607's appendix numbers describe **append-only** additions preserving the original 128 map: +128 slots gave a hindsight 10.05% CPU rows under legacy appended quotas (and 12.20% global ranking), +256 gave 19.07% (20.08% global). Capacity screen 128→192 adds only 64 net slots and repartitions the 128 residents; 128→256 adds128 net but still repartitions them. Neither equals the appendix policy. No exact candidate CPU-row savings or CPU seconds can be calculated for these new profile-selected maps from aggregate current counters. Read actual hit and route-ledger owner counts after each arm.

Acceptance is clean end-to-end emitted tokens/s plus unchanged correctness/quality gates, fresh fault result, actual arena/remaining VRAM, and route/service evidence. GPU cached experts use native Q8_1 arithmetic while the CPU path uses IQ arithmetic; values may differ at rounding/tie boundaries. This capacity-only experiment does not requantize Q8 weights, but new resident routes can change logits/tokens and consequently MTP acceptance/work. Use the existing predeclared numerical/quality comparison, not token identity alone, and keep the R624 original automatic 24,576-row numerical gate status unchanged.
