## Official SYCL joint-matrix contract

The primary source is Intel's [oneAPI joint_matrix extension specification](https://github.com/intel/llvm/blob/sycl/sycl/doc/extensions/experimental/sycl_ext_matrix/sycl_ext_oneapi_matrix.asciidoc), specifically its device restrictions for `architecture::intel_gpu_bmg_g21` and neighboring Intel GPU architectures. It states:

- `joint_matrix_load` stride is measured in elements between rows for row-major layout. For the listed Intel GPU architectures including BMG-G21, `stride * sizeof(T)` must be a multiple of 8 and no greater than `2^24` bytes.
- The load base pointer must be 4-byte aligned.
- The offset overload additionally restricts `row_index` to a multiple of `4 / sizeof(T)` (for 16-bit values, a multiple of 2). This kernel calls the pointer-plus-offset overload with a pre-offset pointer and the one-stride overload; it does not pass a `row_index` argument.
- Matrix parameter support is device-dependent. The extension specifies queries such as `matrix_params` / `matrix_combinations`; source-level template shape alone does not establish support on every device.

The current QK operand is `joint_matrix<sub_group, half, use::b, 16, 16, row_major>`. It receives `kv + k*CH + cell` with stride `CH=32`. For half, the stride is 32 elements = 64 bytes, so it satisfies the documented byte-stride rule and limit. Its required base-pointer alignment must also hold. Current pointer offsets are even half-element offsets (`k` increments by 16 and `cell` is 0 or 16), so they preserve 4-byte alignment if the local-accessor base is 4-byte aligned. The API requirement itself is clear; the compiler/device allocation's base alignment must be verified or guaranteed when making a changed local layout. The current successful model path shows this existing compiled shape ran in that environment, but does not establish arbitrary device support or alignment for a new allocation layout.

This specification is experimental and the online `sycl` branch can evolve. Before treating its exact wording as the installed compiler's contract, Main should pin the actual compiler revision and check its bundled extension implementation/spec copy. The hard API constraint should not be replaced by a claim that a device will silently optimize a nonconforming pitch.

## Candidate-only pitch arithmetic and layout obligations

Current candidate K gather writes the logical matrix tile as `kv[dim * CH + c]` after reading consecutive INT8 dimensions. QK loads treat that storage as 256 rows by 32 columns: the 16x16 B matrix at each load starts at `k*CH + cell`, where `k` traverses 0,16,...,240 and `cell` is 0 or 16. The same `kv` local accessor is reused later for V in `[cell, dimension]` order; PV loads then use `kv + k*HD + dim`, with stride `HD=256`. K and V consumers therefore have distinct strides/layouts even though they share the allocation.

For a padded K pitch `P`, a correct candidate-only layout would allocate at least `HD*P` half elements; write the QK tile at `kv[dim*P+c]`; and change every QK B pointer to `kv + k*P + cell` with joint-matrix stride `P`. It must leave V stores and PV pointer/stride at their existing contiguous `[cell,dimension]` layout. The padded row gaps must never be consumed as K cells. This is a whole-set update: changing only the gather or only the load stride corrupts the logical operand.

| K pitch | Byte stride for half | Documented BMG-G21 stride rule | K workspace vs current 256x32 | Assessment |
|---:|---:|---|---:|---|
| 32 | 64 B | Pass | 16 KiB | Existing layout/control |
| 33 | 66 B | Fail: not divisible by 8 | 16.5 KiB | Reject for this joint-matrix path |
| 40 | 80 B | Pass | 20 KiB (+4 KiB) | Legal stride candidate, subject to allocation base alignment and runtime checks |
| 48 | 96 B | Pass | 24 KiB (+8 KiB) | Legal stride candidate, subject to allocation base alignment and runtime checks |

For 40 and 48, all existing QK starting offsets `k*P + cell` remain multiples of two half elements: `k` is a multiple of 16, and `cell` is 0 or 16. Their byte offsets are therefore divisible by 4 relative to the base. This proves offset preservation conditional on the base itself being 4-byte aligned. Pitch 33's starting offsets also happen to remain 4-byte aligned for this particular `k`/`cell` set, but that does not cure its documented invalid 66-byte row stride.

The allocation grows only by the stated K padding delta because the existing accessor is already reused for V. Padded slots are not initialized by the K fill unless explicitly written; correctness requires consumers never read them. On the V reuse, PV accesses stay inside the first `CH*HD` elements with stride 256. No source/API evidence predicts the resulting SLM bank pattern, occupancy, transactions, or speed. The increase in local allocation can affect group residency depending on hardware/compiler allocation; no physical-bank count or occupancy is inferred here.
