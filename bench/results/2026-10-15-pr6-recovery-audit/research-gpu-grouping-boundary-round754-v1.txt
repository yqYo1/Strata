# R754 — GPU-local MoE grouping boundary in compact FP16/MMQ=0 prefill

2026-10-16 JST. Read-only source research. No source, build, test, runtime, device, profiler, process, environment, service, or Git state was changed. Only this report was written. The active Main-owned CPU wait diagnostic was not inspected or disturbed. No XeStrata source or derived material was read or used.

## Finding

The current compact FP16, MMQ=0, layer-major resident-bank path has a real host-controlled MoE boundary on each layer/chunk. The GPU router produces `T*K` expert IDs. The normal path copies those IDs into mapped host-visible storage (or ordinary host staging), synchronizes the compute queue, and then the CPU computes per-expert counts, offsets, per-ID slot positions, source-row indices, and the active expert order. It uploads the slot and source maps before entering per-expert dequant/GEMM work. The expert numerical operators remain submitted to the GPU queue; the host performs routing/grouping/index preparation and determines their calls and row counts.

This makes GPU-local grouping a credible way to remove a repeated device-to-host ID dependency and its matching map upload. It would not, by itself, remove the host wait or the host-controlled per-expert GEMM loop: the host currently needs `cnt[e]` to pass `ne` to oneMKL GEMM and `order` to select each expert's resident weight pointer. A GPU-produced grouping buffer followed by a host copy of counts/order would still require completion and host inspection. A small kernel that computes counts alone therefore does not make the execution device-driven.

The next decision should wait for Main's active CPU attribution. The present source and geometry identify a removable boundary and its theoretical work scale; they do not establish that grouping accounts for the observed CPU time or improves the critical path if moved.

## Current route and dependencies

For the configured compact route, `prefill.cpp` selects the non-fused host-grouping branch. `grp_mapped` is true when mapped pinned allocation succeeds; `copy_i32(grp_dev, ids, ...)` is a device kernel that writes the mapped host alias. The following `cudaStreamSynchronize` is the required dependency before CPU reads the IDs. The non-mapped fallback uses D2H copy plus the same synchronization.

CPU work then proceeds in a strict chain:

1. Clear 512 counts; scan the `T*K` IDs, validate range and compact row bounds, and increment counts.
2. Prefix counts in expert order to make `off[e]` ranges.
3. Initialize `fill` from offsets; scan IDs again to write `slot[i]` and `src[slot[i]] = i/K`.
4. Upload the slot and source maps; make active `order` by ascending expert ID and positive count.
5. For each expert, resolve its resident bank slot, enqueue two format dequantizations, gather compact rows, call the first FP16 GEMM with `ne=cnt[e]`, run SwiGLU, and call the second GEMM with the same `ne`.

In this configuration the bank has all 512 expert weights resident, so per-expert weight staging does not add a dependency. It does not remove the CPU need to select the correct resident pointer or the two GEMM dimensions. Each iteration uses the CPU `order`, `off`, and `cnt` values. The ID scan order is token-major then top-k index; the current slot assignment consequently preserves that order within each expert. A replacement must preserve deterministic row ownership and stable token order, bounds/error handling, and the accumulation/state behavior of the existing combine path. Atomically scattering IDs without a stable ordering rule is not equivalent evidence.

Relevant active source: `src/prefill/prefill.cpp` around lines 2580–2604 (ID exposure and wait), 2610–2660 (counts, offsets, slot/source construction and upload), 2663–2667 (active expert order), and 3029–3063 (compact row gather and the two per-expert GEMMs). `src/prefill/sycl/postops.cpp` around lines 232–247 implements device `copy_i32` and row gather. `src/prefill/layer_major.inc` around lines 360–390 builds and uploads the full layer bank. Existing source comments and this report concern the normal compact route; MMQ and fused paths have different contracts and are not evidence for this boundary.

## Workload scale from corrected geometry

Use the corrected API geometry in `own-prefill-cpu-investigation-v1.ja.md`: 78,453 API input rows produce 78,452 batched rows; chunk size 8,192 gives nine full chunks and one 4,724-row tail. At 48 layers this is 480 layer/chunk MoE boundaries. Every boundary routes `T*10` IDs.

- Total logical routed IDs: `48 * 78,452 * 10 = 37,656,960` int32 values, or 150,627,840 bytes (about 143.6 MiB).
- In the mapped grouping route, logical ID writes from the device to mapped host storage are 150,627,840 bytes; slot and source map writes back to device are each the same size. Combined logical movement is 451,883,520 bytes (about 430.8 MiB).
- These are source-derived logical payload sizes, not PCIe/Level Zero/device-counter measurements. Mapped-memory kernels may use a different physical path than explicit copies. No transfer counter was collected here.
- The two CPU scans touch the routed-ID sequence, about 75.3 million ID visits across the request, in addition to count/offset initialization, prefix work and vector allocation/order construction. This is operation geometry, not measured CPU cycles or time.
- There can be at most `480*512 = 245,760` expert iterations. Under a uniform-routing arithmetic estimate, expected count is about 160 rows per expert in an 8,192-row chunk and about 92.3 in the tail; the probability of a zero count is negligible in that idealized model. Actual router distributions are unmeasured, so 245,760 is an upper bound, not a measured count.
- If all experts are active, the host submits 491,520 oneMKL GEMM calls (two per expert iteration), plus up to 491,520 format-dequant calls, 245,760 gather calls and 245,760 SwiGLU calls. These are source-level API submissions inferred from the loop geometry, not low-level GPU kernel-launch counts; oneMKL can use an implementation-dependent number of kernels.
- The existing layer-bank upload remains separate work: 48 layers each prepare/copy 512 expert blobs. GPU-local routing does not remove this serial source-copy preparation or its upload path.

## Architecture boundary

**Grouping/index-map offload, with CPU orchestration retained.** A device implementation could produce a stable expert-major assignment and slot/source maps while expert weights remain resident. However, to keep the present per-expert oneMKL path, the host still needs counts, active order, and completion before using those outputs and issuing GEMMs. This may remove the two full ID scans and their logical ID/map roundtrip, but not necessarily the queue synchronization, CPU loop, or GEMM submission overhead. One possible boundary is to produce compact per-expert counts/order in a device buffer and read only that metadata; this still has a host-visible completion point and requires careful stable slot generation. Exact feasibility, metadata format, and whether it shortens the critical path are unmeasured.

**Fully device-driven expert execution.** To avoid host inspection and a host-side 512-expert GEMM loop, execution needs an operation whose runtime can consume device-resident counts/order and expert weight descriptors directly. That means a persistent/indirect expert scheduler or a custom batched/grouped matrix path capable of varying row counts and selecting the resident expert matrices. Ordinary host-side oneMKL GEMM calls cannot take a device-resident `ne` or dispatch themselves from a GPU list. Issuing fixed-size GEMMs for all experts would need masking/padding and can multiply row work substantially (e.g., `T` rows per expert instead of roughly `10*T/512` under uniform routing); this is not a drop-in way to eliminate the boundary. This class of change is a much broader numerical and performance component, and no implementation is recommended here.

## Decision and limits

This is a source/geometry investigation only. It does not recommend implementing either architecture before the current CPU diagnostic attributes time outside the queue wait. If that measurement shows substantial host grouping time, the first concrete proposal should state exactly which scans/maps and bytes it removes, what host-visible metadata and synchronization remain, how stable token order and error bounds are preserved, and how it keeps the resident-bank GEMM interface. If CPU time is primarily queue waiting or source-copy preparation, moving grouping alone may leave the dominant work untouched.

No measured device counters, CPU stack attribution, new performance sample, numerical comparison, or 262,144-context result was produced. Any eventual design must preserve shared state and physical 262,144-context correctness. Long-prefill CPU time, end-to-end throughput and critical-path behavior remain unknown pending Main's owned diagnostic.
