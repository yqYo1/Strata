## Direct1 interpretation

The current Direct1 diagnostic does not add XeStrata code. Commit `84374f68` adds `qsa_decode_attn_batch_layout` and an opt-in `TransposeQ` branch to the extant decode fallback. The branch maps query lanes with `(dim % 8) * 32 + dim / 8`, while retaining the existing K lane ownership and dot-product structure. The normal API calls layout 0; prefill's explicit diagnostic setting selects layout 1. The checked-in Oct. 4 prompt-attention commits and Oct. 15 own fallback-layout recovery provide the direct ancestry. Therefore the current Direct1 measurement can be treated as testing an own-fork implementation under this policy, subject to normal measurement limits; it is not a new XeStrata-derived optimization. This is a provenance conclusion only and does not itself qualify its performance or recommend adoption.

## Dependencies and deployment-path exposure

The project build is configured for SYCL and routes these kernels through the own SYCL source tree. Existing GGML/quantized expert formats and GPU APIs are dependencies used by the engine; their presence does not by itself establish copied XeStrata source. The layer-major candidate uses the existing native expert layout/cache, prefill callbacks, and SYCL queue/copy compatibility layer. Its code ancestry should be traced through the listed own commits and base hashes, rather than inferred from a shared dependency or a matching optimization name.

There is a separate toolchain-location issue. The saved compiler/runtime receipts and environment in the recovery audit identify the active DPC++ installation under a XeStrata worktree path, for example `.tools/intel-llvm-v711/install` beneath `/home/yayoi/ghq/github.com/MistVVK/XeStrata/.worktree/fix-xestrata-e32-host-handoff-20261011/`. R611 records compiler output as DPC++ 7.1.0 pre-release, Clang 22.1.0, LLVM revision `504366f4b82ff00bbac7b0c956635eed8bc599d`; it also explicitly says this is not Intel oneAPI 2026.1. Environment snapshots show this path in `PATH`, `LD_LIBRARY_PATH`, `CPLUS_INCLUDE_PATH`, and `UR_ADAPTERS_FORCE_LOAD`. This is evidence about where compiler/runtime artifacts were installed and how the build was launched, not evidence that own kernel source originated in XeStrata. It does create an operational path dependency: reproducing the saved build environment may require that external worktree-local installation to remain available. The present audit did not run or alter the toolchain.

## Limits

This audit inspected the own repository's source, history, reports, and saved environment records. Per the task constraint, it did not inspect XeStrata implementation source, compare kernel bodies against it, or copy external source. Thus provenance labels are based on documented ancestry, commit timing, and source reports; “unknown” remains the right classification where that evidence is absent. No conclusion here is a legal determination.
