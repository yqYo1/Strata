# R959 — Work-group split-barrier contract in the Xe2 K loop

**Classification:** decision support. **Question:** what requires or permits the single `ScopeWorkgroup` split-barrier pair around each K32 tile in the current B570 register-fragment loop? **Answer:** the pinned Intel split-barrier contract makes this a work-group execution rendezvous, and the current uniform kernel satisfies its convergence rule. With the helper's default `SemanticsNone`, it is not a memory fence. The visible copy/reorder/DPAS path exposes per-work-item and subgroup fragments rather than an explicit cross-subgroup buffer handoff, so available source does not establish that this pair is needed for data correctness. Pinned TLA material does describe its work-group scope as loosely synchronizing subgroup progress, which is a scheduling rationale. Neither that rationale nor the source inspection proves that the pair can be removed: the instantiated helper/backend path and its generated code are not fully contracted or inspected here.

## Contract and evidence

| Question | Exact contract or source evidence | Limit for this loop |
|---|---|---|
| What does the pair synchronize? | TLA's one-scope overload forwards `scope` as both SPIR-V execution and memory scope to `ControlBarrierArriveINTEL` and `ControlBarrierWaitINTEL`. Intel's extension defines arrive as marking arrival while continuing, and wait as waiting for other invocations to arrive. For `Execution=Workgroup`, every invocation in the scope must execute the same dynamic instance of each instruction or behavior is undefined. | This requires all work-items in each work-group to converge on both calls, on each K iteration. It does not by itself require a work-group barrier for the tile's math. |
| Does it order memory? | The helper defaults `memory_semantics` to `SemanticsNone` (zero). The SPIR-V extension says `Memory` is ignored when `Semantics` is `None`; the arrive and wait instructions provide release/start and acquire/end memory effects only when non-None semantics are supplied. | This exact call is a control rendezvous, not an acquire/release handoff for local or global memory. A hidden producer/consumer memory dependency would need its own valid synchronization contract; this pair cannot supply that fence. |
| Are loop calls converged? | The adapter uses local ranges of 64 or 128 items, selects subgroup size 16, and rejects nonpositive K or K not divisible by 32. `k_tile_count` and the K-loop condition are work-group uniform. The bounded prefetch branch is also uniform; there is no lane-specific early return around the pair. | The source meets the extension's work-group uniform-control requirement for the admitted shapes. The 4- and 8-subgroup policies do not alter that requirement. |
| What does the data path show? | `get_block_2d_copy_A/B` selects TLA Xe 2D copy atoms; the traits pass a descriptor payload to the selected load op and place values in register fragments. `partition_sg_fragment_*` creates subgroup fragments; `reorder` dispatches on layouts/types to an Xe fragment reorder; `XE_DPAS_TT<8,float,Input>` supplies the DPAS MMA atom and `cute::gemm` accumulates the K tile in the FP32 C fragment. | Same-item program order must make each load result available before its reorder and DPAS use. Subgroup fragment layouts and the DPAS atom indicate the visible math/data exchange is per item or subgroup. This is not proof that every instantiated helper/compiler lowering has no cross-subgroup communication or scratch. |
| Is prefetch a data dependency? | The loop prefetches the next in-range A/B tile while current fragments compute. TLA describes `XE_PREFETCH_2D` as a cache hint, with no register destination. | It does not complete a copy into a fragment or establish producer/consumer visibility. The range guard protects the hint's coordinate; it does not make the pair a prefetch-completion barrier. |
| Does source establish actual lowering or speed? | TLA's companion calls the barrier a loose synchronization of subgroups and describes the register-fragment loop. | This design description is not a formal no-hidden-storage promise for these two shapes, nor evidence of the selected device binary, Level Zero behavior, or barrier cost. No speed claim follows. |

The barrier is dynamic per loop iteration. `barrier_arrive` precedes the copies and `barrier_wait` follows reorder and GEMM. The arrive is nonblocking: it does not first stop fast subgroups before they issue the copy. The wait prevents an invocation from leaving that dynamic barrier until all work-group invocations have arrived, loosely keeping subgroups within the same K phase. This is consistent with the TLA explanation of scheduling intent and can limit phase skew. It is not equivalent to a blocking pre-copy rendezvous followed by a memory-publishing barrier.

For the visible fragment dataflow, the essential dependencies are: a copy operation must finish writing each work-item's fragment before its reorder reads it; any subgroup lane exchange in reorder must be valid and converged for that subgroup; and the converted A/B values must be ready before the DPAS instruction consumes them. The per-item accumulator is cleared before the loop, then accumulates successive tiles in FP32. These dependencies are principally same-item or subgroup scoped. TLA APIs and source describe this dataflow, but source ordering alone cannot prove that the backend implements a block load synchronously or that a helper never uses hidden staging. If an instantiated helper needs scratch or cross-subgroup exchange, its own contract may add a requirement; a `SemanticsNone` work-group pair still would not publish that scratch by memory ordering.

SYCL 2020 revision 12 gives `group_barrier` its standard work-group coordination and memory-ordering role. This kernel does not call `sycl::group_barrier`; its proprietary TLA helper calls the SPIR-V split-barrier builtins. Do not import SYCL's standard barrier memory semantics into this helper. The SPIR-V extension is the directly applicable contract for these calls; the standard SYCL convergence rule is useful context, not a substitute for that extension's exact behavior.

## Counterevidence and limits

Evidence against a data-correctness requirement is the source's explicit absence of a `local_accessor`, the TLA API's subgroup register-fragment types, the TLA companion's register-reorder description, and DPAS's per-subgroup SIMD16 atom. Evidence against concluding “therefore unnecessary” is that the same public helpers receive full tiled-mma geometry, source headers contain other conditional/helper paths, and compiler-generated spilling or scratch cannot be inferred from source names. The `ScopeWorkgroup` calls might also be required by a TLA scheduling or backend contract beyond the general SPIR-V instruction contract. The reviewed public material does not say that this exact copy/reorder/MMA instantiation requires that pair for correctness, nor does it promise that it is redundant.

The SPIR-V rules require collective convergence for a work-group-scoped pair but do not require the kernel to choose work-group scope if a narrower scope suffices for its dataflow. Conversely, changing scope could violate an unreviewed helper contract or change execution scheduling. The current source and references therefore support a contract classification, not a change recommendation.

The scope is the active B570/BMG G21 adapter only: K32, subgroup size 16, compact policy 4 subgroups/64 items and wide policy 8 subgroups/128 items. Input and output storage are BF16 or FP16 (two bytes); the MMA atom consumes native 16-bit inputs and uses FP32 accumulation fragments. No result here extends to other Xe generations, tile geometries, formats, or kernels. Any later native comparison must keep the process environment fixed after runtime/provider initialization and use separately owned processes or an explicit parameter. Preserve the physical 262144-context, buffer/descriptor bounds, allocation lifetime, guard, and fault requirements; this local GEMM contract review proves none of them. Existing M160/M8192 submit-through-completion timings are not split-barrier service times or evidence of a barrier bottleneck.

## Narrow Main-owned evidence gate

The remaining uncertainty is concrete and bounded: inspect the actual configured compiler's emitted SPIR-V and device code for both tile policies and 16-bit input formats. Confirm the arrival/wait execution scope and semantics, copy completion behavior, reorder instruction path, DPAS lowering, and any compiler/helper-generated SLM or scratch and synchronization. Preserve the compiler/runtime/device identity and immutable environment. Then validate the unchanged current kernel across both policies and BF16/FP16 with correctness, allocation bounds, output guards, fault/lifetime checks, and the existing physical-context gate. That evidence would settle the helper/backend contract and applicability. It would not by itself measure barrier cost; any later timing comparison is a separate Main-controlled experiment. No removal, weakening, or adoption decision is made here.
