## Intended dependency graph and the reuse question

In the failing test, 200 producer jobs share a 128-slot host ring and an eight-slot device-weight ring. For host slot `h`, producer job `j >= 128` waits until the main thread has submitted job `j-128`, then synchronizes `host_done[h]` before overwriting that host buffer. Main observes `ready[j]`, queues host-to-device copy, records `host_done[h]`, and publishes `issued`; it also records `copied[d]`. Before reusing device slot `d`, the copy queue waits for its prior `used[d]`; the compute queue waits for `copied[d]`, submits GEMM, and records the new `used[d]`.

For a slot generation, the intended order is therefore:

`old compute use -> copy-queue wait(old used) -> H2D -> host_done and copied -> compute-queue wait(copied) -> GEMM -> new used`.

The host producer is an additional branch: `old host_done -> CPU overwrite -> ready -> H2D`. This graph is acyclic as written. The test also uses acquire/release atomics for `issued` and `ready`. In the compatibility layer, `cudaEventRecord` submits a barrier and replaces the event state's `optional<sycl::event>` under its mutex; `event_of` copies the currently recorded event under the same mutex; `cudaEventSynchronize` waits on that copied event. Given the test's order—publish `issued` only after recording `host_done`, and do not submit a host slot's next payload until its producer has completed the wait and published `ready`—the source does not show a clear event-generation overwrite window for this case. A ring/event reuse defect remains possible if runtime event binding differs from these assumptions, or if an overlooked ordering edge exists, but a host data race, lost wakeup, or dependency cycle is not established by inspection.

The production `Stager` follows a similar host-DMA lifetime contract: it waits for `dma_done[j % kRing]` before copying into a reused pinned buffer, and the issuer records that event after queuing DMA. The new receipt stops in the standalone two-queue test before reaching production staging; it is not evidence that the production stager or BF16 data is involved.

## What the public contracts say

The Unified Runtime API describes `urEventWait` as waiting for listed events to finish. It separately defines `urQueueFlush` as issuing previously enqueued commands to the device, without guaranteeing completion, and defines an enqueued wait-with-barrier as a queue command whose following work is held until its dependencies complete. These contracts distinguish submission from completion, but the public text does not tell us whether the exact installed Level Zero V2 adapter's host-wait path flushes any pending queue work, or how it maps the SYCL queue's barrier events.

Level Zero's command-queue specification says execute submits command lists in received order across calls (including calls from different threads); queue synchronization blocks the host until completion. Its event specification explicitly permits concurrent host threads to call `zeEventHostSynchronize` and says the implementation should be lock-free. Those are API-level concurrency expectations, not proof that this exact adapter/runtime/driver sequence makes progress. Intel's immediate-command-list guide identifies Arc B Series as Level Zero V2-only and immediate-list-only. The local receipt pins that adapter family for B570, which makes a regular-list batching/flush explanation less direct; it does not expose whether UR V2 still has an event/wait/queue-progress defect or show the internal calls made by the installed binary.

An Intel LLVM issue reports a superficially similar `urEventWait -> zeHostSynchronize` hang in a Level Zero V1 workload, while its author reported that L0 V2 passed that separate workload. It is useful mainly as a caution: this stack signature locates the host waiter but does not identify the producer of an unsignaled event. Its app, hardware, adapter and old software revision differ, so it is not causal evidence for this failure.

## Ranked hypotheses (not findings)

1. **UR/Level Zero V2 cross-queue progress or host-wait path.** This best matches the observed location and the fact that `pipeline(q,true)` is the first two-queue arm; the one-queue arms were not reached in this run. Candidate mechanisms include a missing/late queue issue, a cross-queue dependency that never becomes visible, or host wait on an event whose signaling submission did not progress. The receipt has no UR call trace at the hang, queue state, or event-generation IDs, so “V2 bug,” “flush bug,” and “driver hang” remain unproven.
2. **Strata compatibility/test event-generation or ring-control bug.** The event wrapper deliberately replaces a reusable event's stored SYCL event, and the test has independent 128- and eight-slot generations. A wrong generation snapshot or a missed `issued`/`ready` transition could strand workers. Mutex and acquire/release ordering plus the per-slot order above weaken the obvious race story; inspection did not find a concrete cycle. The V1 pass followed by one V2 timeout is compatible with a timing-sensitive project bug but proves neither timing sensitivity nor cause.
3. **Test workload/library boundary rather than its event DAG.** The compute operation is oneMKL GEMM and the cross-queue arm changes dimensions as well as queue topology. A hang in or around library submission could prevent the `used[d]` signal and indirectly block copy reuse. The main thread's sampled `sched_yield` frame does not show its exact loop condition, and workers wait on `host_done`, so neither oneMKL nor an event edge can be singled out. Numerical checks completed first; numerical correctness is not implicated by this stop.

## Narrow next diagnostic for Main

If Main chooses to investigate, use one Main-owned, separately supervised process against the pinned test and same pre-start runtime environment. Add bounded progress records at the producer's entry/return from each `host_done` wait and at main-thread `used` wait, copy submission, `host_done`/`copied` record, GEMM submission, and `used` record; include job index, host/device slot, and event generation. Emit at slot wraps and when progress stalls, not on every poll. Preserve the 200/128/8 wrap geometry initially, since reducing below the ring boundary would remove the suspected mechanism. Set a short finite deadline (for example 60 seconds), a 64 MiB raw-log ceiling, and a fresh kernel-fault boundary; terminate and reap only that owned child on deadline. Keep the current environment immutable after runtime initialization. The last paired “submitted/signaled” markers can separate a project-side missing edge from a wait entered on a correctly published event; if all producer-copy markers advance but the waited event does not, that narrows the next Main-owned experiment to queue issue/progress. A future controlled copy/barrier-only arm can then remove oneMKL while preserving the same cross-queue/ring edges. This is a proposal only; no reproduction or runtime verdict was produced here.

## Limits and references

Not proven: GPU hardware hang, driver fault, Level Zero V2 defect, missing flush, event reuse race, oneMKL defect, or causality from the process-lifetime registry edit. No model inference ran in this failing test. V1's single pass does not qualify repeatability; V2's timeout does not qualify a correctness regression in BF16 or native16. The fresh-fault scan was empty and the driver dump was absent; this rules out only those captured signals, not every hardware/runtime failure mode.
