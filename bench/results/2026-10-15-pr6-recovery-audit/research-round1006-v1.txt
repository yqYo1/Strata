The pinned `native16.cpp` `combine` maps `d` from BF16, multiplies it by FP32 `w`, and executes ten `sycl::fma(w, d, v)` operations in each token's original `slot[t*10+k]` order, skipping negative slots. It then evaluates `store(v + load(shared[i]) * sigmoid(sg[t]))`: the shared BF16 output is widened, sigmoid sees an FP32 scalar HC gate, product/add are written as ordinary FP32 expressions, and the final result is BF16-converted once; compiler contraction/fast-math settings and generated instructions would be needed to establish whether the multiply and add remain two roundings in the built kernel. The HC residual update is a later operation, `store(fma(load(b_o), 2*sigmoid(inj/HC), load(r)))`; it is not part of the combine sum. The planned expert-major schedule changes the sequence in which routed expert terms reach a token's accumulator. It does not change the real-number sum, but may change FP32 rounding before the shared epilogue. The contract receipt separately warns to preserve the FP16 mixed bank for expert/shared GEMM input and BF16 mixed producer for router/scalar shared gate; converting one rounded bank into the other is another, independent input-quantization change.

## What can be bounded

Let `p_i = fl32(w_i * d_i)` denote the exact real product of the already stored FP32 weight and widened 16-bit expert result; a fused path computes each `w_i*d_i + s` with one FP32 rounding, rather than first rounding the product. Under round-to-nearest, normal finite values, no overflow/underflow, and standard IEEE operations, the serial FMA result has a conservative absolute forward-error scale of about `gamma_10 * sum(abs(p_i))`, where `gamma_n = n*u/(1-n*u)` and FP32 unit roundoff `u=2^-24`; `gamma_10 ≈ 5.96e-7`. Comparing two independently ordered serial FMA reductions gives a safe coarse scale `2*gamma_10*sum(abs(p_i))` (not a tight or empirical bound). A tree can have a different error profile and dependency depth; Higham's analysis treats recursive and pairwise summation separately, and pairwise summation is well suited to parallel execution. None of these bounds is relative to the final sum when cancellation makes it near zero: the condition number `sum(abs(p_i))/abs(sum(p_i))` can be arbitrarily large.

Input representation error is separate from reduction error. For a normal value rounded to nearest, BF16's significand precision gives relative rounding at most `2^-8` (about 0.390625%); FP16 gives `2^-11` (about 0.048828%). Subnormal, zero, overflow and NaN cases need absolute/format-specific treatment, and the bounds do not apply across overflow. In this combine path, expert outputs are already BF16, so summation order does not select their quantization; a proposed FP16-vs-BF16 producer change does. Weights are FP32 in the pinned contract. If a future candidate moves the multiply into a lower-precision format, this model is insufficient and product rounding must be included explicitly.

Let `q = fl32(fl32(shared_bf16) * sigmoid(gate_fp32))` for the source's non-fused shared multiplication, and `z = fl32(sum_fp32 + q)`. BF16 output uses round-to-nearest conversion `R_BF16(z)`. Two distinct FP32 values produce identical BF16 output whenever they lie in the same BF16 rounding interval; a sufficient condition for an output known to be distance `m` from its nearest BF16 midpoint is `abs(delta_z) < m`. For example, around `+1`, adjacent BF16 numbers are spaced `2^-7 = 0.0078125`; an FP32 result `1.0000` and `1.0010` both round to BF16 `1.0` (their difference is 0.001, and neither crosses the `1.00390625` midpoint). If both branches are exactly `1.0` the stored outputs are, of course, equal regardless of their unobservable inner path. This explains how many outputs can match bitwise despite different FP32 sums, but it says nothing about what fraction of actual tokens/columns fall in a bin: that is a measurement question.

## Executable mathematical counterexamples (illustrative only)

These are small self-contained C++-like snippets defining the operations; they are not run here. `fmaf` models one correctly rounded FP32 fused multiply-add. The final `bf16_rn` is a round-to-nearest-even conversion, including IEEE special values. Zero-filled terms make each example K=10.

```cpp
float route_order(float p[10], int order[10]) {
  float s = 0.0f;
  for (int j = 0; j != 10; ++j) s = fmaf(1.0f, p[order[j]], s);
  return s;
}
uint16_t epilogue(float routed, uint16_t shared_bf16, float gate) {
  float q = bf16_to_f32(shared_bf16) * (1.0f / (1.0f + expf(-gate)));
  return f32_to_bf16_rn(routed + q);
}
```

Cancellation counterexample (all inputs/products are binary32 exactly representable; BF16 expert output may be `1`, weights carry the values): `p={1, 2^-24, -1, 0,...}`. Order `[0,1,2,...]` evaluates `fma(1,1,0)=1`, then the half-ulp-at-1 term rounds away in the FMA tie, then subtracts 1, giving `+0`. Order `[0,2,1,...]` cancels first and produces `2^-24`. The exact real sum is `2^-24` in both. With shared BF16 zero and any finite gate, epilogue sigmoid contributes zero; BF16 results are respectively +0 and the nonzero BF16 value `2^-24`. Relative error against the exact result is 100% for the first order, while absolute error is only `2^-24`. Thus a low average absolute error or FP32 diagnostic-relative percentage cannot replace near-zero and task-level measures.

A second, larger but still finite illustration uses `p={2^24,1,-2^24,0,...}`. In the displayed serial order the `+1` is exactly a halfway case at `2^24` and rounds away under ties-to-even, yielding zero after cancellation; order `[0,2,1,...]` yields one. The expert outputs can be BF16 `1` and FP32 weights `2^24, 1, -2^24`; the example therefore does not require nonrepresentable input values. These are adversarial to cancellation, not evidence that normal router weights/expert outputs reach these magnitudes.

Overflow counterexample: let terms be `{FLT_MAX, FLT_MAX, -FLT_MAX, 0,...}`. One order overflows its second partial sum to `+Inf`; adding the negative finite term leaves `+Inf`. Order `{FLT_MAX,-FLT_MAX,FLT_MAX,...}` remains finite `FLT_MAX`. BF16 epilogue then yields infinity versus a finite BF16 value. Such an expert/output-weight combination is extreme, but it shows a finite exact final sum does not prevent order-dependent intermediate overflow. Runtime/task acceptance should separately count nonfinite values; clamping would silently change the stated contract.

NaN: with any quiet NaN input term, ordinary IEEE FMA propagation yields NaN independent of where it appears in this short sum, but payload/signaling behavior and which exceptional operation first occurs need not be bit-identical across implementations. A BF16 NaN stays NaN on final conversion. The pinned local code explicitly assigns a NaN for an out-of-range positive slot; preserve route bounds/error handling, and compare NaNs by classification/count rather than payload unless payload is a deliberate contract. `+0/-0` can also differ by order even when ordinary numeric comparison calls them equal.

## Reduction choices and counterevidence

| Method | Numeric / scheduling property | What it does not establish |
|---|---|---|
| Per-token slot loop with ten FP32 FMAs | Fixed sequence for fixed route-slot array and compiler contract; one accumulator, serial dependency. This is the pinned local native16 behavior. | It is not exact real arithmetic, and fixed order does not make it more accurate in every cancellation pattern. |
| Expert-ID major deterministic scatter, one writer per token/column or stable per-expert stage | Can be reproducible if each destination receives a defined sequence, e.g. ascending expert ID, plus fixed FP32 FMA and same stored operands. Lowers/changes route output storage and order. | Stable order is not route-slot order or a proof of smaller task error. Many-token parallelism does not itself specify per-destination order. A token with repeated expert IDs needs explicit duplicate handling. |
| Unordered FP32 atomic scatter | Correctly prevents lost updates, but addition order follows execution/scheduling; GPU atomic order can vary between runs, so both bitwise reproducibility and a fixed numerical trajectory are not guaranteed. | Atomicity is not deterministic reduction, and it does not preserve the slot-order source contract. CUDA documentation is only a general accelerator example, not B570/SYCL feature evidence. |
| Pairwise/tree reduction | Parallel depth near `log2(K)`; summation error often improves over long naive serial sums and is analyzed by Higham. For K=10 it is a changed tree and need not beat a particular FMA order on every input. | A tree must be fixed to be deterministic; products may be rounded separately or fused at leaves, changing another rounding boundary. Generic numerical analysis does not prove model equivalence. |
| Accumulate shared term first vs after routed sum | Same exact real sum, different rounded path. Existing snapshot adds shared product after ten routed FMAs; expert scatter initialized from shared output would inject it before the first routed addition unless it keeps a separate routed accumulator. | Do not collapse this difference into “same FP32 precision”; test the placement. |
