# R779 — Memory transactions and translation limits in irregular gathers

2026-10-16 JST. Bounded public-source knowledge collection. This report compares memory-transaction efficiency, cache/page working sets, subgroup mapping, prefetch, and added concurrency for resident irregular gathers. No product source was inspected or changed; no build, test, GPU, profiler, process inspection, Git operation, environment change, cleanup, or service action was performed. No XeStrata source or derived material was used.

## Finding

A low measured bandwidth number does not identify a PCIe limit or even prove that peak DRAM bandwidth is the relevant ceiling. A resident gather can be slow with low external bandwidth because one SIMD instruction fans out to many cache-line requests, translation misses serialize or queue, target loads depend on earlier index loads, or too few independent requests exist to cover latency. Conversely, it can be bandwidth-bound if its transactions are efficient and enough concurrent misses reach device memory. These causes need separate probes.

For each gather stage, distinguish (1) useful bytes per memory transaction/cache sector, (2) cache misses and repeated target-line/page reuse, (3) distinct virtual pages and translation misses, and (4) dependency stalls and outstanding independent requests. Coalescing addresses (1); cache-aware tiling may improve (2); page-local ordering/working-set reduction targets (3); prefetch or more independent work can help (4) when the needed addresses are known early. These are related but not interchangeable. In particular, adding work-groups can hide latency while leaving transaction count unchanged or increasing TLB/cache contention.

## Three approaches and their tradeoffs

**Bucket or tile for reuse.** GraphCage is a substantive graph example: PageRank pull gathers source-vertex values from CSR edges, while its push and traversal kernels have different access and active-frontier patterns. Its throughput-oriented cache blocking (TOCAB) partitions data so the active vertex-value range fits in GPU L2, limits repeated partial-sum traffic, and coordinates blocking with load balancing. On an NVIDIA GTX 1080 Ti, the authors report reduced L2 misses/DRAM transactions and average PageRank speedups over Gunrock of 4.0× (pull) and 3.6× (push); in SpMV, where matrix values have no reuse opportunity, the coalescing/load-balance method is more effective than cache blocking. The key transferable result is conditional: block only where a reusable target working set exists and can fit. Naïve blocking can repeat writes/partial-result work; too-small blocks multiply reduction overhead, while too-large blocks lose cache fit. In their Twitter case, conventional blocking made many repeated accesses and did not improve cache behavior; GraphCage’s size sweep chose 256 vertices for its own cache and data. Those figures describe its graph benchmark and CUDA/NVIDIA machine, not Arc/SYCL. [Chen, *GraphCage*](https://arxiv.org/abs/1904.02241)

**Redistribute lanes or order indices for coalescing.** In a subgroup, coalescing improves when lanes request nearby addresses in the same cache line(s). If the kernel has a free permutation, a page/line bucket can collect requests, load adjacent fields together, then restore output order. This costs index classification, temporary storage, synchronization, and possibly a scatter; it pays only if each line supplies multiple requested values, duplicates can be merged, or the layout can be reused. Sorting a set of distinct one-value-per-line requests does not reduce its total unique line count by itself. The IRU paper demonstrates the possible upside of changing lane-to-data mapping: in GPGPU-Sim configured as a GTX 980, its proposed hardware reorder unit improves average graph coalescing from four to three L1 accesses per memory instruction and reduces simulated L1/L2 accesses; it also delays the first target load while accumulating/reordering indices. It is evidence for a mechanism, not a software feature or measured commodity-GPU result. A portable SYCL path could use subgroup operations and an explicit bucket/permutation, but cannot assume cross-subgroup or device-global redistribution is free. The Intel guide says the work-item-to-hardware mapping is implementation-dependent; valid subgroup sizes must be queried, and an explicit subgroup size only sometimes helps. [Segura et al., *Irregular Accesses Reorder Unit*](https://doi.org/10.1007/s11227-022-04621-1); [Intel, *Sub-Groups and SIMD Vectorization*](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2025-2/sub-groups-and-simd-vectorization.html)

**Reduce page working set or prefetch.** Address translation is a distinct fan-out: lanes on different cache lines can also touch different virtual pages. Shin et al. report that 45–77% of eligible memory instructions in their irregular workload suite had page-walk requests interleaved with other instructions; their SIMT-aware page-walk scheduler improved modeled irregular workloads by 30% over FCFS, with little effect on regular workloads. Their reported scheduler results use a heavily extended gem5 model (8 CUs, 64-lane wavefronts, 512-entry GPU L2 TLB, eight page walkers and DDR3), not an Arc device. The paper’s sensitivity study shows the gain falls as TLB size or walker count increases: with both increased, the gain is 5.3%. This is useful evidence that translation locality and translation service capacity can limit performance separately from raw data bandwidth, but it does not establish that software can control the page walker. [Shin et al., ISCA 2018, *Scheduling Page Table Walks for Irregular GPU Applications*](https://doi.org/10.1109/ISCA.2018.00025)

At software level, group requests that reuse the same page before moving on, compact/remap the target data, or process one cache-fitting target tile at a time. GraphCage’s graph-size and frontier sensitivity illustrates when this works: tiny active frontiers may already fit in cache, so extra blocking is wasted; sparse/irregular social-graph frontiers may benefit; frequent block reductions can erase the gain. Reducing unique pages per active batch can plausibly improve TLB reach, but a compact allocation is not automatically page-local if indices still scatter across it. On Arc, actual device page size, TLB capacity, and a directly observable GPU translation counter were not established by this research. Do not infer those from CPU TLB counters or generic OS page size.

Prefetch is narrower than a page-locality fix. Intel’s SYCL guide recommends it only if execution has high scoreboard stalls while memory bandwidth is not full, and enough independent instructions exist between prefetch and use. The standard `global_ptr::prefetch` example prefetches a future contiguous index, not unknown future gather targets; its documented implementation fetches at most 32 bytes per work-item and only to L3. Intel’s documentation also scopes support details to Data Center GPU Max and later products and warns that prefetch can regress performance. B570 support/cache effects therefore need direct confirmation. Prefetch cannot be assumed to prefetch page-table entries or cure high transaction fan-out. [Intel, *Prefetch*](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2025-2/prefetch.html)

## Discriminating experiment

After the active measurement boundary is closed and a real resident gather is identified, run one bounded same-kernel experiment with identical index count, useful bytes, result order, allocation residency, and data values. Compare: baseline; a cache-line bucket/subgroup remap; a page-bucketed or compact-target layout; a small target-tile reuse path; and baseline with a small sweep of independent work-groups. First count exact address/line/page distributions from the input and record scratch bytes and added passes. Keep any sort/bucket preprocessing inside end-to-end timing unless the same map is demonstrably reused across calls. Validate identical output and retain a bounds/fault check.

For every arm, record full gather-path time, kernel time, useful bytes, transactions or memory-read bytes where the current Intel tooling exposes them, L3 misses, EU/scoreboard stalls, active subgroup/occupancy, and the actual profiler/device/runtime versions. Intel VTune documents GPU memory-read/write bandwidth, GPU L3 misses, and EU stall metrics; these can show transaction/cache pressure or memory waiting but are not direct proof of TLB misses ([VTune GPU Compute/Media Hotspots Analysis](https://www.intel.com/content/www/us/en/docs/vtune-profiler/user-guide/2025-1/gpu-compute-media-hotspots-analysis.html)). If available, record a GPU translation metric separately. Otherwise, create a page-footprint sweep that holds the number of distinct cache lines and accesses constant while placing those lines across progressively more pages, with the actual page size documented; repeat hot-page and cold-page orderings. Treat the timing response as indirect translation evidence, since cache-set and allocation effects remain. Do not claim a PCIe bottleneck from low bandwidth or a TLB bottleneck from latency alone.

Interpretation: a coalescing win should lower requests/bytes per useful output and persist without requiring more page reuse; a cache-tile win should reduce L3 misses/DRAM bytes and be strongest when targets recur within the tile; a translation win should track the controlled page-footprint change with similar cache-line counts; a latency-hiding win should improve time and raise useful memory throughput with more independent work while per-item transactions stay similar. A regression from bucketing/prefetch points to sort, scratch, barrier, scatter, cache pollution, or serialization cost. If counters are unavailable, report the mechanism as unresolved and keep the result as a timing comparison only.

## Applicability limits and sources

The Arc B570 question is a hypothesis until its own resident gather and full dependency path are measured. PageRank/SpMV, simulated GTX 980 IRU, modeled page walks, and Intel Data Center GPU examples differ in memory hierarchy, page mappings, subgroup width, cache policy, and driver. SYCL makes subgroup and prefetch operations expressible, but does not make page sizes, line transactions, TLB behavior, or prefetch support portable. The sources are design/evidence for discriminating experiments, not a prediction of B570 speedup or a product change proposal.

Sources used: Shin et al. (ISCA 2018) page-walk study; Chen (2019) GraphCage; Segura et al. (2023) IRU simulation study; Intel oneAPI GPU Optimization Guide 2025.2 (SYCL subgroups, memory system, and prefetch); Intel VTune Profiler 2025.1 GPU metrics documentation.
