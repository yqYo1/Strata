R849 — Establishing actual JIT kernel resource use on Intel SYCL / Level Zero
Decision support | Read-only research | 2026-10-16

Question and boundary

The question is how to distinguish what typed attention declares from what the current JIT-compiled kernel actually asks the Intel runtime to allocate. The 6354/B570 component and 129-model work is closed after nine clean 39K processes; the natural-32K numerical screen remains active. On the closed B570 run, BF16-only had a 394.9 tok/s median and typed QSA 384.8 tok/s; the attention interval changed from 33.9610 s to 36.2963 s, but that interval is nonexclusive. Those measurements make the resource question concrete, but do not identify its cause. Source-declared SLM of 44,500 B versus 32,336 B is not compiled resource evidence. This report compares three evidence routes and gives one bounded Main-only capture; it makes no code or optimization proposal. Prior review metadata places R817 on AOT extraction/ISA interpretation, which leaves the JIT dynamic-resource question open; R847 concerns event timing, not resource allocation. R847’s collection body remains unread.

Field interpretation and dynamic local memory

Keep four different quantities separate. “Registers” is a compiler's architecture-specific register allocation count; on this stack UR's optional `NUM_REGS` is the direct field to try, while Level Zero's public kernel-properties structure has no register count. “Private memory” in SYCL/UR is a minimum per-work-item amount and can include language/runtime private storage; Level Zero describes compiler-allocated private bytes per thread. “Spill memory” is compiler-allocated spill storage; the Level Zero contract does not state the aggregation unit, so a nonzero value is a compiler resource signal, not a total device allocation. “Local memory” is per work-group on L0; UR calls it local memory required by the kernel. Neither public description promises a static-only value or documents the exact alignment and device-granule rounding.

A local_accessor's extent is supplied on the host when its accessor is created for the command group, but its concrete local-memory argument size is not part of compiler-time static SLM metadata. Its argument size and each argument's alignment are applied when the runtime binds the local arguments for a particular submission. The final aggregate can then include inter-argument padding and implementation/hardware rounding. Thus source or `.ze_info` can describe static requirements and argument layout; they cannot establish the effective dynamic total for a launch. Read the Level Zero property from the exact kernel handle after all dynamic local arguments have been set for that submission, or record the adapter's actual launch argument sizes and alignment. If the existing property route reads before binding, it may report only static/incomplete SLM. The public API alone does not prescribe the rounding formula; pin the deployed compute-runtime source when explaining a rounded result. Do not hard-code a guessed 1 KiB or other alignment.

No resource-property value predicts occupancy. Even a confirmed GRF count and SLM bytes need device limits, allocation granularity, subgroup/work-group size, compiler spills and dispatch dimensions to model resident groups; runtime scheduling and concurrent work still affect what actually runs. The useful result here is exact compiled resource metadata plus the actual launch geometry, not an occupancy claim.

Bounded Main-only recipe

1. After the active natural-32K screen reaches its allowed checkpoint, run only the existing successful tiny typed-attention fixture at frozen revision 6354 and the qualified B570 component configuration. Keep input, expected output and optimization options unchanged. Record executable/source hashes, device/runtime versions and actual UR kernel name. Use one fresh owned process and keep its environment immutable from before `exec` to shutdown.
2. Before `exec`, create one private mode-0700 directory and set `IGC_ShaderDumpEnable=1`, `IGC_DumpToCustomDir=<existing-directory>` and `IGC_ShaderDumpRegexFilter=<escaped exact kernel name>`. Add `IGC_ElfDumpEnable=1` and `IGC_DumpZEInfoToConsole=1` only if the installed library accepts them. Upstream v2.41.5 docs list these flags, but do not prove support in local `libigc.so.2.41.5+1788943183`; require a nonempty matching dump or mark support unproven and stop that branch. Do not assume master-only flags.
3. Set a finite deadline and 64 MiB total dump/log budget. Keep only the matching kernel artifacts and the fixture's one-run property/result record. If capped, mark incomplete. Do not clear shared caches or alter optimizations; if a cold compile is needed, use an owned private cache set before process start.
4. For the same execution, capture the existing `Runtime::compute` and compatibility-queue property paths separately, recording path, kernel name, group dimensions, runtime local-accessor sizes and query results. Distinguish unsupported from zero. Read L0 values from the dispatched kernel handle after local arguments are bound. If the existing fixture cannot expose post-bind properties or module identity without source edits, leave those claims unresolved.
5. If existing interop exposes the corresponding Level Zero module, extract `zeModuleGetNativeBinary`, hash it, enumerate names and match `ze_kernel_uuid_t.mid/kid`. Compare its ZE metadata with the IGC output from that compile. Without the module handle, call the IGC file compiler evidence only. Record raw L0 local/private/spill bytes, subgroup/work-group requirements and optional UR register count beside exact module/kernel IDs. No profiler or model run is needed.

Acceptance and residuals

The decisive evidence is a successful query on the exact dispatched Level Zero kernel, tied to the same module UUID/name and (if exposed) a hash of that module's native bytes; dynamic SLM is captured only after its local arguments are bound. An IGC dump with matching name, PID/run and compile identity corroborates the compiler artifact but is weaker runtime linkage. Source declarations, perf medians, total attention time, estimated register pressure, or a kernel-name match alone do not prove actual allocation. Existing 6354 measurements and the BF16/typed-QSA delta identify the reason to measure; they remain separate from this read-only resource report.
