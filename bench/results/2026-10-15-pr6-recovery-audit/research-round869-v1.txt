# R869 — Direction-optimized single-GPU BFS frontier representation and switching costs

**Purpose:** Knowledge collection. This is algorithm literature, not a Strata proposal, implementation, or validation. The report concerns level-synchronous BFS for unweighted graphs and excludes sparse triangular dependency scheduling, destination reduction, and generic compaction surveys.

## Findings

Top-down push and bottom-up pull trade work over opposite sets. For frontier `F`, unvisited set `U`, and directed outgoing/incoming degrees, the useful first-order push work is `E_F = Σ(v∈F) d_out(v)`: expand only active sources, test destinations against visited state, and enqueue new vertices. The input is naturally a compact queue/list; a visited bitmap or labels support membership. Pull instead visits each `u∈U`, tests its incoming neighbors against membership in `F`, and stops on the first match. Its actual edge checks are `Σ(u∈U) k_u`, where `k_u` is the inspected prefix length through the first frontier neighbor, or all `d_in(u)` edges if none is found. A bitmap makes each membership test constant-time and avoids looking up a sparse frontier list for every neighbor.

**Analytical estimate, not a measured TEPS model:** If each neighbor independently belongs to `F` with probability `p` and neighbor order is random, expected pull inspections for a vertex of in-degree `d` are `Σ(i=0..d−1)(1−p)^i = [1−(1−p)^d]/p` (limit `d` as `p→0`). This makes the crossover degree-sensitive: when `p d` is small, pull nearly scans every incoming edge of every unvisited vertex; when `p d` is large, early exit sharply shortens the scan. A handful of high-degree frontier vertices can make actual `E_F` much larger than `d_avg |F|`, while hubs with many frontier neighbors can make pull terminate quickly. Correlated graph structure, neighbor order, visited fraction, cache behavior, and destination overlap violate the independence assumption. Frontier density alone is therefore an incomplete switch signal.

The crossover must include representation costs. A vertex bitmap uses `ceil(|V|/8)` bytes, versus roughly `|F| × index_width` bytes for an ID queue; this storage comparison is analytical and omits allocator/metadata overhead. Queue-to-bitmap can mark `F` in `O(|F|)` after a bitmap clear, but a clear is `O(|V|/word_size)` unless epochs or another valid initialization scheme avoid it. Bitmap-to-queue requires enumerating set bits or scanning/compacting `O(|V|/word_size)` words. Beamer reported conversions as typically small because its switch occurs while the frontier is still small, but also found frontier conversion and `m_f` calculation non-negligible; that is CPU-specific evidence and cannot be assumed for a GPU launch/scan path. GraphBLAST reports operand reuse to avoid sparse-to-dense conversion in its direction-optimized implementation. It stores CSR and CSC for speed, with a one-format option that saves memory at a performance cost; its v1 cost heuristic uses `d|F|≈|E_F|`, assumes `|E_U|≈|E|` early in scale-free BFS, and switches around `|E_F*|>|E|/10` (back below the same estimate). The authors explicitly note exact `|E_F|` requires prefix sums and counting dense `U` adds a GPU launch. [GraphBLAST arXiv v1, §§4.1, 4.3, Table 9](https://arxiv.org/pdf/1908.01407v1).

Graph layout adds a one-time or amortized cost beyond per-level switching. CSR/outgoing access makes push direct; CSC/incoming access makes pull direct. For symmetric undirected graphs one representation contains both arcs, but directed inputs need a transpose or a separate incoming index. Beamer estimates the inverse graph can nearly double directed graph storage. GraphBLAST provides both CSR and CSC, while TurboBFS targets one compressed representation and omits Boolean value arrays to reduce its memory footprint. Whether transpose construction, matrix conversion, and initial frontier conversion are included in a published benchmark must be recorded explicitly; the cited TurboBFS report does not make that timing boundary clear. GraphBLAST and Gunrock explicitly exclude host/disk transfer, so their timings are traversal-side results rather than end-to-end graph ingestion.

## Counterevidence and applicability

The best case for pull is a low-diameter, scale-free wave: a large frontier makes push inspect many edges whose targets were already discovered or are simultaneously reached by several parents, while pull often finds a parent quickly and writes each target once. Beamer’s CPU study says its hybrid saved edges both by skipping the transition-level push expansion and by early exit; its tuned online heuristic was often within 10% of an offline oracle. But edge-count reduction is not time reduction one-for-one: Beamer measured conversion and frontier-degree accounting overhead, and remaining pull accesses had worse spatial locality. Higher-effective-diameter Flickr and Wikipedia had smaller speedups and more redundant pull work in the tail; the authors say repeated pull after the first dense level checks edges redundantly. Their paper’s principal benchmark is shared-memory CPU, so the α/β values are historical reference points, not GPU prescriptions.

GPU evidence likewise cuts both ways. Gunrock’s direction optimization helped its small-degree/large-diameter group on average, but its text says the gains on road-network and bitcoin graphs were smaller because there was less concurrent discovery. In TurboBFS, top-down was best on 7 irregular cases, bottom-up on 5, and hybrid on 6; different CSC/COO variants won the rest. Thus graph family labels do not fully predict direction winner. Degree distribution, actual frontier-neighbor overlap, edge orientation, adjacency locality, and input/output format all affect it. For low-degree road/mesh graphs, pull’s full scan over a huge unvisited set can overwhelm early exit; however a sufficiently broad level or favorable GPU occupancy can still amortize it, as Gunrock’s group result illustrates.

Push can create multiple candidate entries when active parents share children; atomic first-claim prevents duplicate visits but adds contended writes, while idempotent discovery plus filtering may trade atomics for redundant queue traffic and expansion. Gunrock documents both atomic and idempotent/filter paths. Pull assigns each target to itself and avoids concurrent parent claims, though it still pays bitmap probes and per-row early-exit divergence.

## Evidence limits and novelty

These studies vary corpora, GPU generations, direction variants, and timing boundaries; their absolute TEPS are not comparable (Beamer CPU, Gunrock K40c, TurboBFS Titan Xp, GraphBLAST K40c/Titan V). Gunrock gives aggregate forward-versus-hybrid results but no mode-specific conversion times. TurboBFS reports mode winners and rates but leaves undirected-edge counting and setup inclusion ambiguous. GraphBLAST is cited at arXiv v1 only for input-sparsity and direction claims. This adds BFS frontier crossover as a distinct topic beside fan-in reduction, SpTRSV readiness, format conversion, and irregular gather/cache. No source measures Strata or Arc/SYCL.
