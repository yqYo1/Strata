# R665 — Teacher-forced prefill NLL math and API contract audit

Date: 2026-10-15 JST. Static read-only audit of public A `prefill-teacherforced-nll-v1` source diff, README, source pins and fixtures, with current root sequence API/consumer context. No patch application, build, test, compiler, Python compilation, GPU, Git, process, cleanup, root edit, private B, live-run or environment inspection. Only this report was written.

## Finding

The proposed formula is a numerically stable FP32 log-sum-exp for finite logits: each row computes a maximum, sums `exp(logit-max)` in FP32, then calculates `(max-gold)+log(sum)`. It never materializes a rounded probability before taking its logarithm. NaN/Inf logits and invalid target indices produce NaN, which the host writer refuses to publish as a complete artifact. The supplied fixture has a double-precision oracle for every valid output and explicitly checks NaN for every invalid row. This is appropriate source coverage for the math, but remains an unrun fixture and does not qualify the implementation.

## Math and fixture coverage

`row_target_nll` validates rows/vocabulary and checked byte counts, uses a 256-lane workgroup per row, reduces nonfinite status and the maximum, then reduces FP32 exponentials. The `m-l[id]` term is formed before adding `log(sum)`, avoiding the avoidable loss from `log(softmax_probability)` when the target probability is tiny. A finite input whose correct NLL exceeds FP32 range becomes nonfinite and is rejected by the writer, as the proposal documents.

The current fixture's ten rows cover ordinary logits; a large common offset; a gold token whose probability underflows in naive FP32 probability space; the non-power-of-two vocabulary tail (259); a very large finite logit range; NaN, positive infinity and negative infinity; and negative/upper-bound targets. It computes the CPU oracle for every valid row, asserts NaN for rows 5–9, tests zero rows and vocabulary 1, and uses assertions. No fixture row tests logits containing mixed `+Inf` and `-Inf` simultaneously, but the implementation's finite-status reduction rejects either independently, so this is an incremental test case rather than a source defect. The tolerance is `2e-5 + 2e-6*abs(oracle)`; it is a reasonable numerical fixture tolerance, not bitwise parity.

The fixture checks null/negative dimensions, zero vocabulary, integer byte-count overflow, misalignment, output-input aliasing, null stream, and non-in-order queue before enqueue. The wrapper also checks all spans through `validate_spans`, rejects non-USM pointers in the selected queue context, and requires an explicit in-order queue. It does not and cannot infer the actual allocation extent from raw pointers: `validate_spans` proves pointer non-nullness, alignment, address arithmetic and alias separation only. Actual readable/writable extents remain a caller contract. The production caller appears to allocate `n_batched*4` bytes for both gold and NLL arrays and passes one-row offsets; the fixture's full allocations match its supplied extents. The new declaration should state this caller-owned extent obligation explicitly, and the GPU fixture should include at least one genuinely undersized USM allocation negative case if the runtime allocation registry can expose it. Do not describe the current wrapper as checking allocation bounds.

## Indexing and ordering at the consumer

The writer's `n_input` denotes the full prompt input. It stores every input token and expects exactly `n_input-1` records in position order; record `p` uses `tokens[p+1]` as gold. `generate` sets `n_batched` to the full prompt's initial batched region and rejects a short `--prefill-until`, so this represents all next-token predictions made by that initial full prefill. Each callback row points into `R_rows[p-p0]`, runs the same `lm_head_mix` and `NativeHead::run` sequence, and sends gold/NLL row `p0+t` to the same main in-order stream. A single checked chunk readback follows the row launches. The wrapped previous callback still runs, and completion metadata is published only after full prompt/MTP restore and checked owner retirement. The ordering and extent arithmetic are internally consistent by source inspection.

One limitation is intrinsic to the API: `rows` and `vocab` are `int`, so byte products are checked against `INT64_MAX/4`, but an otherwise arithmetically valid enormous `rows` can still request an impractical `rows*256` ND-range. The production caller uses `rows=1` per row, and configured input size caps the count; no concrete production overflow follows. If this entry is intended as a general public kernel API, a documented practical row/launch bound or an allocation/launch test is still needed.

## Paired metric scope

`compare_nll.py` requires complete artifacts, matching exact native-int32 token bytes, matching vocab/head/type/scope metadata, full coverage and valid gold IDs/NLL values. It reports all-token mean NLL delta, min/max per-token delta and relative perplexity change; it hardcodes quality, physical-262144 and RESTORE qualification to false and requires external recipe/source/binary/model/environment/chunk/residual dtype/placement/MTP/driver/fault/retirement pins. This is a useful paired screening metric for the exact initial prompt and the initial-prefill prediction distribution. It can reveal a broad loss shift hidden by sparse selected logits or greedy-token agreement.

It does not establish general model quality: it evaluates one conditioning token sequence, one initial prefill path/configuration and only the gold-token log probability per position. Mean NLL can hide localized regressions; comparing arms with different residual precision/placement, prompt/chunk behavior, or model identity invalidates attribution even when token bytes match. Keep per-position records and the external recipe pins, then use task/retrieval and full-context gates as separate evidence. No quality or speed outcome is claimed here.

## Gate summary

No concrete math, row-index, gold-offset, queue-order or consumer coverage error was found in the proposed source. The concrete contract omission is that the API documentation and fixture do not establish/check actual caller allocation extents; source currently relies on caller-owned spans, as the production allocation does. Add that explicit contract and test an undersized allocation where supported before claiming extent checking. All source remains unbuilt and unrun; numerical correctness, runtime behavior, paired data and quality gates remain unverified.
