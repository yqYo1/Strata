# R669 — long-prefill profile route for current layer-major FP32

2026-10-15 JST. Read-only profiler/source review for the current Strata SYCL path, with the requested priority on >600K-token and then 1M-token prefill follow-up. No source edit, build/test, compiler, GPU/profile run, process/service inspection, Git mutation, cleanup, or private environment/log access was performed. This report is the only new file.

## Recommendation

The present fixed official unitrace `--device-timing` summary is the quickest trustworthy coarse inventory, but it cannot answer which work is on the long-prefill critical path: it spans process startup, prefill, and generated tokens, and reports aggregate operation durations. The 34,603-input/128-output profile is a useful kernel census, not a prefill timeline. Its 167.176 s sum is neither prefill wall nor GPU-busy union; overlapping operations can be counted more than once, and it cannot be subtracted into startup/prefill/decode.

For the next diagnostic, retain that low-volume official summary as a reference and use one bounded, phase-scoped official unitrace Chrome activity capture around the actual `run_layer_major` call. A default-off diagnostic hook must select the prefill phase in-process and use the pinned unitrace collection control (`--start-paused` with one documented control mechanism); put phase start after prompt setup, immediately before layer-major work, and pause after its final checked drain/callback, before generation. One emitted ITT task should mark this entire region. Do not reuse `STRATA_PREFILL_TIMING`: `run_layer_major` explicitly rejects it, and its legacy `PfTimer` uses CUDA events and ignores event creation/record errors. `STRATA_PREFILL_PHASE_AUDIT` is tensor/state capture, not a timer; it copies selected layer-26 values and imposes audit storage/I/O.

Use device-lane execution intervals to compute the union of busy time on the selected compute queue, and separately preserve sum of durations by operation/kernel. Use queue/host records and copy endpoints to distinguish queued/submit gaps, blocking host waits, copy service, and host work. Do not label unobserved gaps GPU-idle. Do not join absolute GPU and host timestamps or add their durations: R576's GPU clock-domain validation remains open, and R588 explicitly keeps host-call durations and device durations separate. Report prefill wall from the owner's monotonic bracket around the same call; it is a separate wall interval, not a GPU duration.

This is the fastest trustworthy *critical-path diagnostic*, not a clean speed measurement. If the full 48-layer capture exceeds the established budget, retain the failure as incomplete and ask for a reviewed next capture; do not silently cap/roll over and claim completeness. The prior R576 whole-prefill ceiling is 512 MiB total, with a 300 s diagnostic deadline, 8 GiB owner-session RSS limit, and 65,536-event per-host-thread buffer. Monitor the aggregate provider plus owner log budget and stop on the predeclared limit. Preserve only compact receipt fields and verified hashes after extraction; retire raw timeline once the open profile question is answered under `docs/ARTIFACT_RETENTION.md`.

## Why not the alternatives

* **Fixed `--device-timing` summary:** use it to identify high-count/high-sum kernels and verify coarse operation counts on the same 34,603/128 run. Its checked profile labels itself complete startup+prefill+decode and explicitly disclaims phase-specific device timing or busy-union. A one-token output reduces decode contamination but still includes startup and cannot prove where the prefill work falls.
* **Whole-process Chrome timeline:** source-role/kernel intervals allow interval union and queue-gap inspection, but include unrelated startup and generation. For this long, many-chunk workload it also spends the finite trace budget on activity outside the question. A phase gate is the useful narrowing step; whole-process output should not be the default.
* **New aggregate in-engine phase observer:** no trustworthy current layer-major timer exists. Adding SYCL event profiling would require profiling-enabled queues and explicit event lifecycle/error handling; forcing queue drains at every phase would serialize work and perturb the pipeline. A host-only aggregate can report call/wait service spans but cannot identify device service or GPU busy union. Therefore it is not a substitute for provider activity. If the phase-gated provider cannot be made to emit complete records, the best fallback is a small checked host-wall observer around the whole prefill plus existing coarse device summary, clearly marked as marginal evidence only—not a custom phase-by-phase GPU timer.

## Source and route checks

The current route is narrowly gated in `src/prefill/layer_major.inc`: `STRATA_PREFILL_LAYER_MAJOR=1` and `n > m.T` select it; admission requires the SYCL engine, full 48-layer single-GPU route, native compact FP16 expert source, explicit `STRATA_PREFILL_MMQ=0`, no peer/stage/hand-off/reentry/legacy observer, and a same queue. The checked wrapper drains at entry, expert upload, boundaries, and exit. Input over 600K uses many outer layer passes and chunk passes; measure the actual admitted request, exact effective rows/chunk, and actual `n_batched`, rather than treating 600K nominal prompt tokens as the model's prefill row count. For standalone generation, source uses `n_prompt-1` conditioning rows.

`STRATA_PREFILL_TIMING` is rejected by layer-major admission (`layer_major.inc`). The legacy `PfTimer` in `prefill.cpp` is CUDA-event-based; `cudaEventCreate` and `cudaEventRecord` results are unchecked, so even on a path where admitted it is not a reliable failure-reporting observer. The `Layer26PhaseAudit` name is misleading for timing: it copies selected state/route tensors to bounded raw/text files for a numerical boundary audit, at one layer, and performs checked queue copies.

The current official record is `model-device-profile-v1.json`, whose scope explicitly includes startup, prefill and decode. Its summary keeps operation duration sums and provider metadata; it does not contain a native prefill-only region, operation-interval union, or exclusive wall decomposition. Its companion validator checks the existing summary format and totals but cannot reconstruct the missing phases. R576 documents pinned PTI/unitrace controls, event budget, trace-retention plan and open timestamp-domain limitation; R588 reinforces keeping host and device times separate.

## Minimal collection contract for Main

1. Keep diagnostic and clean-throughput owners separate. Use one exact >600K request first, then 1M only if needed; the experiment owner pins model/input hashes, source/binary/provider receipts, actual chunk/admission values, immutable inherited runtime environment and one short output. The user priority is prefill; do not add decode tuning to this profile.
2. Start unitrace paused, collect only from the ITT-marked start of `run_layer_major` until its final checked completion, then pause before decode. Use one documented pause/resume mechanism; do not mutate arbitrary process environment after SYCL/provider initialization. Ensure the actual unitrace build accepts the flags and can collect the ITT region before admitting the run.
3. Require provider records for the native PID, Arc B570, selected queue/lane, full interval coverage, matched flow/operation identity, and device event order. Match copies by allocation/source/destination evidence, not a `Flow_H2D` name. Reject incomplete records and incomplete queue/lane coverage for busy-union claims.
4. Extract (a) monotonic prefill wall, (b) device execution-duration sum by kernel/op, (c) same-queue interval union and overlap, (d) submitted/queued/execute spans, and (e) separately measured host call/wait spans. Keep host and device columns unjoined until actual trace timestamp-domain qualification exists. Do not infer PCIe bandwidth from requested bytes or profiler direction labels alone.
5. Compare diagnostics-off/on wall only to quantify observer perturbation. Neither the trace nor observer-enabled wall is a clean performance result. Keep raw timeline only until compact evidence is checked and hashed, then follow the documented retention manifest/lock policy.
