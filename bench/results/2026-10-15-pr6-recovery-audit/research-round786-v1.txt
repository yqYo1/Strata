# R786 — Atomic fan-in strategies for skewed GPU graph aggregation

**Purpose:** knowledge collection. **Question:** for graph and scientific aggregation with degree skew and changing frontier density, when should destination-owned pull, edge-centric atomic push, subgroup/work-group aggregation, or destination-segmented reduction win, and what counterexamples favor simpler methods?

This is public-source research only: no local inspection, measurement, or Strata proposal. It focuses on destination fan-in, local duplicates, and reduction order, outside R759 scheduling/scans, R763 residency, R778 storage conversion, and R779 transaction/page behavior. Other hardware does not establish Arc/SYCL performance.

## The crossover depends on two distributions

Let `F` count edges emitted by active sources and `g(v)` count updates to destination `v`. Frontier density controls visited edges; the tail of `g(v)` controls contention. They differ: skewed source degrees need not create hot destinations, and subgroup duplicate rates also depend on edge order and lane mapping.

PageRank-like sum aggregation and BFS discovery share fan-in but differ in semantics. PageRank must include every incoming contribution for each computed rank, so a pull traversal generally reads all in-edges even if only a few sources changed, unless the update is formulated incrementally. In BFS, pull can stop after finding one active predecessor; atomic push often uses a compare-and-swap or idempotent state update rather than a floating-point sum. Do not transfer a BFS direction-switch threshold to a PageRank reduction.

## Strategy comparison

| Method | Sparse frontier, weak destination skew | Sparse frontier, strong skew | Dense frontier, weak skew | Dense frontier, strong skew |
|---|---|---|---|---|
| Edge-centric push with global atomics | Strong baseline: visits only `F`; modest fan-in | Can serialize at hot addresses; still attractive if active edges rarely target the same hot bins | Often competitive if atomics are native and destinations spread | Likely worst atomic case; every contributor queues at hot locations |
| Destination-centric pull (CSC / incoming adjacency) | Often loses for sum: scans inactive in-edges; can win for BFS if a hit ends the row | Avoids cross-work-item destination atomics; long rows need parallelization and can become stragglers | Natural when work is close to all edges; each destination has one owner | Avoids atomics but a few long rows still need tiled/tree work; balance is not automatic |
| Subgroup/work-group local combine, then global update | Usually overhead when most lanes have distinct keys | Useful only where the same subgroup/work-group actually contains duplicate destination keys; reduces atomics per local unique key | Potentially useful if local duplicate groups remain dense | Can remove many updates, but key matching, scratch, barriers, and local-capacity limits matter |
| Destination-segmented reduction | Sorting/reordering can dwarf a small `F` | Attractive if a segment can be formed cheaply or reused; stable ordering is possible | A destination-major layout avoids atomics but still reads all needed edges | Avoids global atomic serialization; large segments may need multiple tiles and a merge pass |

These are hypotheses, not rankings. Pull changes ownership and traversal. Existing incoming-adjacency order makes destination ownership cheap; sorting dynamic push output into segments adds records, workspace, and passes. Existing CSC or sorted keys changes the cost.

### Push and pull

Atomic push scales with active edges and needs no per-edge records, making it a sparse-frontier baseline when skew is low and atomics are native. Relaxed order fits an accumulator with no publication dependency; it does not remove hot-address serialization or fix floating-point ordering.

Enterprise's GPU BFS study [3] reports severe out-degree skew: on YouTube, 330 vertices (0.03%) account for 10% of edges; on Wiki-Talk, 96 vertices (0.004%) account for 20%. It switches to bottom-up traversal near BFS's explosion level, using frontier hub count as a signal. This is evidence for density-aware BFS ownership, not a PageRank in-degree hotspot: pull also reads status/bitmap data and may inspect inactive edges while the frontier is sparse.

### Local aggregation

A subgroup can combine equal keys before issuing one atomic per local unique key; a work-group can extend this with local memory or a small table. Benefit ranges from the active lane count (all keys equal) to none (all unique). Global skew is insufficient: shuffled edges may hide duplicates from each subgroup. A larger local table adds coordination, capacity, collision, and occupancy costs.

Khorasani's CUDA thesis [4] on Warp Segmentation/Collaborative Task Engagement assigns warp lanes across irregular CSR adjacency segments and locally reduces by vertex. It reports 1.29–2.80x over virtual-warp-centric processing and up to 1.51x over the best fixed sub-warp width. This shows local segmented combination can repair SIMD underfill, not that destination-key atomics improve on a current SYCL GPU; duplicate keys per subgroup remain unmeasured.

### Segmented reduction and accelerator evidence

Destination-ordered contributions permit one owner/tree per segment and one write. Static incoming CSR/CSC avoids per-iteration sorting. Dynamic lists need temporary records, sort workspace, and passes; splitting long segments adds partial sums and a merge. Fixed replay requires a fixed tree/order because library reduction may choose another.

AccuGraph's cycle-accurate FPGA simulation [5] found pure atomic protection added 45% average overhead versus 16-edge parallel updates, especially for Orkut; its Xilinx accelerator reported up to 3.14x over single-chip ForeGraph. This is specialized-hardware evidence, not GPU performance. Its degree-aware accumulator also has finite width and incurs synchronization for million-edge vertices.

NVIDIA Warp's current guide [6] replaces atomics with temporary records, destination sorting, and reduction. Its RTX 4090 / CUDA 12.4 graph-capture microbenchmark reports 1M writes to one output at 1.46 ms (ordinary atomic) versus 0.193 ms (run-to-run sort/reduce). With 65,536 random outputs, it reports 0.020 versus 0.201 ms; stricter GPU-to-GPU order took 172 ms for the hot case. This synthetic CUDA test shows sorting can win under extreme contention and lose badly for cold destinations; it is not a graph-kernel result.

## Reduction semantics and portability

SYCL 2020 revision 12 [1] provides `atomic_ref`, `reduce_over_group`, and kernel reduction variables, but no universal combination order. Floating addition is non-associative, so tree/order changes can alter low bits. Atomics protect individual accesses without choosing which racing work-item contributes first. A fixed local tree may repeat on one build/device but is not automatically bitwise portable; specify and validate the required order.

Intel's 2025-2 oneAPI guide [2] recommends hierarchical reduction over a one-bin global atomic and notes floating atomics may be emulated on some devices (its examples include older Gen9/Iris Xe). It shows SYCL built-in and work-group-local reductions, but is not a cross-vendor guarantee: check device support and benchmark the actual type, address space, scope, and key distribution. Relaxed ordering cannot remove contention or make addition associative.

BFS `min`/CAS, integer counts, and floating PageRank sums have different contracts. Integer addition is exact absent overflow; floating results may meet tolerance while differing bitwise. Check convergence and task metrics. AccuGraph's error-tolerance argument is algorithm-specific.

## One discriminating experiment

Use real and generated graphs, holding `|V|`, `|E|`, values, and active-edge count fixed while varying frontier fraction (0.1–100%), fan-in (uniform, Zipf, one-hot), and edge order (grouped/shuffled). Rewire destinations while preserving source out-degrees to vary fan-in, and compare push atomics, CSC pull, subgroup keyed combine then atomic, and destination sort plus segmented reduce. Time complete paths including clear/sort/scratch/launch, plus kernel-only time. Record `F`, max/p95 `g(v)`, subgroup duplicate rate, remaining atomics, scratch/local-memory bytes, individual timing samples, and repeat/bitwise stability. Check integer work exactly and FP32 against a high-precision reference, then validate convergence or BFS tree correctness.

Report a crossover surface over active-edge count, fan-in, and local duplicate rate. Falsifiers matter: atomic push may win despite skew if atomics are cheap; pull may win while sparse if layout costs are low; segmented reduction may win only when sorting is amortized. No Arc claim follows without target-runtime measurement.
