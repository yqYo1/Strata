# R569 — layer-major残差をFP16/BF16で保存する品質gate

2026-10-15 JST。read-only調査。指定された本報告ファイルだけを書いた。製品source、build/test/GPU、process/service、branch/commit、active log、fixtureの重い数値処理は行っていない。Mainが進行中の実行には介入していない。除外指定のprivate contract record、環境変数、Codex private log/sessionは探索していない。数値ベンチが必要な提案は実施せず、source・既報・一次資料から評価条件を整理した。

## 結論

FP16/BF16化の最も近い根拠は、モデル作者のQwen3.8-Next設計論文である。著者はGR、gated attention、GDNのgateが残差への書込み幅を制限することを理由に、残差branchをFP8で保存し、BF16比で残差trafficを半分にし「quality loss is almost zero」と報告している。論文冒頭も推論時に残差stateがFP8 storageを支援すると記す。これは本モデルと残差stateに直接関係する前向きの根拠で、一般FP16推論の類推より強い。

ただし、論文はFP8方式とStrataの現行layer-major scratch round-tripを同一視できるほどの条件・数値を提示していない。報告箇所には比較したcheckpoint/weight quantization、FP8 variant/scale・rounding実装、精度評価セットの全結果・誤差分布が示されず、IQ3-native checkpoint、FP16/BF16のどちらか、B570/oneAPI、層ごとに1回書戻すこの配置を直接評価した結果ではない。論文自身、別の「sparse writes」はpre-training lossとbenchmarkではほぼ影響が見えなかったのにpost-training後の品質が明確に悪化し、採用しなかったと記す。このため「作者がFP8を通した」ことは低精度保存の検証可能性と試験の優先度を上げるが、ここでの採用判定にはならない。

現状のMain briefingでは、既存FP32のlayer-majorで513 input/512 batched、257/255 chunkのcontrol/GPU-prefix/host-onlyが比較され、全248,320 logitsとsampled residualのbitwise一致、fresh fault 0が報告されている。これは新しい配置がFP32保持なら同じ演算結果になる根拠であり、FP16/BF16で層間丸めを加えた結果ではない。別に34,602 batched rowsのnatural history pairでは248,320 first logitsと541 residual positionsがbitwise一致しているが、quality・RESTORE・full-256K・bench.sh performanceの資格ではない。R567/Main correctionどおり、34,602 rowsのFP32 residualは1,417,297,920 B、host-onlyを47層間往復する量は133,226,004,480 B。16-bit保存ならそれぞれ708,648,960 B、66,613,002,240 Bとなる算術で、対象バッファとその往復量は半分になる。全体prefill時間が半分になるという意味ではない。

## 既報との接続

R540 (`research-prefill-intermediate-storage-round540-v1.txt`) は、別のMoE Down出力DmをFP16/BF16で一度丸める候補と、GDNの未使用FP32 y重複bufferを削る候補を扱った。別bufferの判断、24 prompt/1pp例が screeningに過ぎず、独立なzero-harm pair 299件で初めて片側95%上限がおよそ1%になるとのMain correction、そしてtarget model品質は未測定との制限を再利用する。Dmは今回のlayer-to-layer GR residualではないため、その誤差・容量予測をここへ移さない。

R547/R567はowner/lifetimeとVRAM admissionを扱い、R567/Main correctionでは34,603入力行と今回のnative対象34,602 batched rowsを区別し、MTP expert/Verifier/cacheのsource上の解放余地を実測freeと混同しないよう訂正している。本件はその未解決free budgetに絡むresidual **storage format**だけを扱う。decode cache、GDN recurrent state、QSA KV/indexer、MTP cacheや演算全体のdtypeは変更しない。

現rootのlayer-major plan (`include/strata/prefill/layer_major_plan.hpp`) は現在 `row_bytes = width*sizeof(float)` と `float[]` host rowsを前提にしている。`layer_major.inc` は非最終層の各chunk出力をGPU/host residual storeへコピーし、次層ではそこを `hand_in_` としてFP32演算へ戻す構造である。よって本提案はこのscratchの保存表現だけを狭めるもの。FP16とBF16は別候補とし、各層の残差更新後に一度だけFP32→storage cast、その層の次consumerでstorage→FP32復元して現在の計算を行う条件で比較する。host tailとGPU prefixに別のrounding回数を持たせない。last layerのcallback/checkpoint、token/window state、weight/cache/state ownerはFP32 armと同一に保つ。

## 一次資料と適用できる範囲

- Qwen Team, [On the Design of Qwen3.8-Next Architecture: Evaluation, Efficiency, and Training Stability](https://arxiv.org/abs/2608.30320), §2.2 “Inference Efficiency”, lines/HTML section around 384–390 and abstract/introduction. Paper says widened residual traffic dominates GR inference cost; sparse writes looked nearly unchanged on pre-training loss/benchmarks but degraded clearly after post-training and were rejected; its FP8 residual-state experiment reports half the BF16 residual bytes with almost no quality loss. This is an architecture-author, same-family residual-state experiment. The report's own data supports both exploring reduced residual storage and testing downstream/post-training behavior, not a numeric Strata FP16/BF16 threshold.
- [Qwen3.8-Flash-Next official repository README](https://github.com/QwenLM/Qwen3.8-Flash-Next/blob/main/README.md) describes GR as four residual branches with dynamically gated reads/writes, and points to the design report. This supports architecture identity, not quality equivalence.
- [Intel format documentation](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-deep-learning-boost-new-instruction-bfloat16.html) and [NVIDIA TensorRT accuracy considerations](https://docs.nvidia.com/deeplearning/tensorrt/10.x.x/inference-library/accuracy-considerations.html) state the standard representation tradeoff: FP16 has 5 exponent and 10 mantissa bits; BF16 has 8 exponent and 7 mantissa bits. FP16 preserves more significand precision; BF16 has wider exponent range and coarser significand. This predicts a trade-off, not which wins for this residual distribution. Do not infer conversion safety, overflow/underflow rate or a threshold by inspecting scalar source types/ranges; measure saved/round-tripped values across the real histories and positions.

The Qwen paper is the only directly relevant quality evidence found in this pass. No author model card, official implementation note, or other implementation report was found that publishes an FP16-vs-BF16 layer-major residual round-trip comparison for this IQ3 checkpoint and this storage boundary. The paper's phrase “almost no loss” has no numeric margin in the cited section and must not be restated as a measured tolerance for our target.

## Required precision and conversion checks

First compare three arms from the same source revision and immutable prompt/history: current FP32-storage control, FP16-storage, BF16-storage. Keep all math, attention/cache format, chunk sequence, expert cache, output callbacks and seeds fixed. Run formats separately; never use an arm that stores FP16 then BF16 or packs/unpacks twice. The production consumer should see exactly one storage rounding per layer boundary and one FP32 restoration before the next layer's unchanged operators. Include unit-level representative values only as implementation checks; acceptance must come from model histories.

At every boundary exercised, check actual cast/restore path and byte accounting: finite/NaN/Inf, overflow, subnormal/underflow-to-zero counts; absolute and relative RMS, p99, p99.9 and maximum error; errors by layer, row, branch/channel, token position and GPU/host location. Record exact cast semantics/rounding mode and verify C++ half/bfloat conversion agrees with any device conversion. Include odd row counts, chunk tails, the 257+255 two-chunk case, a 512-row complete prefix, a prefix/tail transition, and final partial chunk. Compare direct saved bytes against a reference pack/unpack oracle so a duplicated conversion or byte-offset error cannot masquerade as numerical loss. Verify the next-layer FP32 values are restored once, including host→device and device→device cases; no change to accumulation precision or residual operator is allowed in this experiment.

Numerical output comparison should reuse exact serialized prompt IDs/template and full history, including thinking mode. At selected rows spanning early/middle/final positions and each context length, record target-token log-prob delta, candidate/reference KL over logits, top-1 and top-2 IDs, top-1 margin, and top-1 flip rate. Stream full-vocabulary comparisons through the evaluator; retain compact per-position summaries rather than giant logit dumps. Add final logits and last-layer residual comparisons. Token equality is diagnostic only: a token flip can occur at a tiny margin, while a consistent distribution shift can be harmful before any greedy flip.

## Bounded quality gate and useful minimum

Use a staged gate so a cheap screen cannot be reported as final quality:

1. **Boundary correctness.** Run 513 rows split 257/255, plus 512-row prefix and host-only placements. Verify exactly one cast/restore per non-final layer, correct span bytes/offsets at chunk and store boundaries, all finite outputs, and matched control histories. The existing FP32 bitwise result is the oracle for unchanged layout. This stage finds wiring and conversion bugs; it is not a quality sample.
2. **Natural-history numerical screen.** On the already relevant 34,602-row fixed thinking-template history, run paired FP32/FP16/BF16 all the way through all 48 layer transitions. Sample logits at fixed positions across the full history, especially near the beginning, at chunk/prefix-tail boundaries, and near 34,602; collect KL/logprob/top-margin metrics as above. Repeat with host-only and a GPU-prefix placement where the same row sequence gets the same selected 16-bit representation. This measures accumulated rounding in the actual route. One natural prompt remains a screen, not broad-task evidence.
3. **Long-context retrieval.** For each surviving format, use fixed multi-needle retrieval questions with needles at early, middle, late, and near-window-end positions; exercise 32K/64K (practical screen), then the configured 256K boundary (262,144 actual context positions) before claiming support for full-context use. Use identical prefixes/questions and compare exact retrieval success and answer evidence. Include questions that require combining early and late facts, not only a single needle. Report each length/position separately; a 34K pass does not establish 256K behavior.
4. **Task non-inferiority.** Use fixed independent items balanced across retrieval/document QA, coding, reasoning/math and ordinary instruction; use multiple fixed seeds for generative tasks and paired scoring. A 24-prompt set is a screening pass only (R540 already corrected this). To support a “less than 1 percentage-point harmful-pair rate” statement using the prior R540 binomial/independence calculation, require at least 299 independent paired binary task outcomes with zero harmful candidate-only regressions for a one-sided 95% upper bound near 1%. Repeating seeds on the same prompt does not create independent examples; diversify prompt/item identities. If any pair is harmful, increase sample size and compute a paired confidence interval instead of claiming the zero-event bound. Predeclare success labels, blind scoring/rubric, and per-category reporting before looking at outputs.

For continuous quality, compare teacher-forced continuation NLL/perplexity on fixed held-out continuations under identical histories, and summarize both aggregate and per-category/length changes. Use paired bootstrap over independent prompts for confidence intervals; set a provisional acceptance criterion of the candidate's upper 95% bound for relative PPL increase ≤0.5%, while no individual length/category has a clear regression. This 0.5% is a proposed engineering gate carried forward from R540, not a published guarantee from Qwen or an empirically validated threshold for this target. Calibrate baseline repeatability with repeated FP32 runs first; do not let baseline noise inflate the allowed margin. Report mean and tail KL/logprob changes and top-margin-conditioned flips even when PPL passes.

Keep natural quality and numerical behavior paired on the same input IDs. Once one format clears the 34K screen, the minimum useful broad decision is the balanced independent task set above plus retrieval at 64K and 256K. If runtime budget forces staging, label 24 items/34K as screening and defer adoption; don't lower the evidence bar by counting correlated tokens or repeated seeds as independent tasks. FP16 and BF16 require separate full candidate/control results. No format should be selected from exponent-range intuition alone.

## Capacity, traffic and performance gates

For 34,602 rows, 10,240 scalars/row, and 48 layers, the provided FP32 plan uses 1,417,297,920 B residual capacity; FP16/BF16 representation would use 708,648,960 B for the same full set. If all rows are host-only, the provided 47 inter-layer write/read transfers total 133,226,004,480 B in FP32 and nominally 66,613,002,240 B in 16-bit storage. These are exact logical payload calculations from the task geometry, before allocation padding or conversion work. A mixed prefix/tail saves only the fraction actually assigned to those stores. Report actual allocated bytes, host↔device transfer bytes, GPU prefix rows, conversion scratch, and observed free VRAM separately. The 512 MiB safety reserve and full 512-expert temporary cache remain part of admission; precision halving does not prove the candidate fits or that all 34K rows can be on GPU.

Only after correctness and quality pass, compare clean paired end-to-end prefill runs with identical prompt, chunking, context/KV format, cache and device settings. Keep host tail, full-GPU prefix and the intended mixed plan separately visible. Record prefill and decode separately, each clean sample and order, same-device faults, memory high-water/free values, conversion/copy timings and actual residual bytes. A smaller residual allocation/transfer is useful evidence, not a speed claim; a quality-preserving format is adopted only if the capacity or end-to-end benefit is material and repeatable against run variation. Do not infer that halved residual traffic halves total prefill time.

## Decision

The author evidence is encouraging and directly relevant to the model family: test a 16-bit residual-storage variant. It does not tell us whether FP16 or BF16 wins in this quantized Strata route or provide a defensible numeric adoption margin. Keep current FP32 as the equivalence oracle. Evaluate FP16 and BF16 separately through one-rounding-per-layer storage with FP32 restored compute, then require the numerical, retrieval, broad task and memory/performance gates above. Until those results exist, mark both formats as candidate-only; do not alter global inference math, persistent states, KV formats or defaults.
