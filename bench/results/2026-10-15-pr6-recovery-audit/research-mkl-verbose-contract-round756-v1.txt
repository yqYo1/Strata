# R756 — oneMKL 2026.0 verbose contract for the 2026.1 GEMM check

2026-10-16 JST. Read-only documentation/source research. Only this report was written. No compiler, build, test, runtime, device query, profiler, process or environment query/change, Git operation, cleanup, or source edit was performed. No XeStrata implementation/helper/test/archive source was read or used. This report narrows R753 to the exact official verbose contract and a bounded owned diagnostic proposal; it does not report new runtime evidence.

## Finding

Intel's Linux oneMKL Developer Guide marked 2026.0 (dated 2026-04-28) documents GPU verbose output for BLAS, including DPC++ applications. A verbose call-description ends in a GPU index such as `GPU0` when the call executes on a GPU. The index field is empty when the function executes on the host CPU. Thus, if the installed oneMKL 2026.1 emits a verbose-enabled line for the matching GEMM call, the suffix distinguishes that call's reported execution target. The line format may change between releases; verify the installed output, and match the function and argument dimensions rather than treating an unrelated line as evidence.

This is a per-call execution-target signal. A `GPU0` suffix does not show that the call had no CPU preparation, data copies, queue waits, dispatch work, or CPU polling. It does not establish behavior for unlogged calls, other type/shape/device combinations, or the whole model. An empty device field on the corresponding GEMM line is the documented host-execution signal for that call. Missing GEMM lines are inconclusive: the function may not be verbose-enabled, output may be incomplete, or the call may have been interrupted before the line was printed. In particular, Intel documents that GPU verbose output only covers verbose-enabled functions and that interrupted calls do not print their call line. Therefore, do not turn absence of a GPU suffix or absence of any line into proof of fallback.

The 2026.0 guide defines `MKL_VERBOSE=1` as verbose enabled without timing for GPU applications; `=2` enables synchronous timing. `=1` is the appropriate first target-attribution mode because it avoids the documented synchronous-timing behavior, though verbose output still has overhead. `=2` makes kernel execution synchronous, blocks later work behind prior kernels, and includes possible transfers/copies in overall time; it is unsuitable for a clean performance sample and unnecessary for the execution-target question. Timing output is not proof of the CPU/GPU split.

Intel also documents `mkl_verbose(int)` modes 0/1/2 with the same meanings, and says function calls take precedence over the environment setting. That state is global, not thread-local; changing it concurrently across threads has undefined results. A serial diagnostic could use the API to scope logging to selected calls, but only if no other thread can call oneMKL during toggles. This is more intrusive and easier to misuse than an owned process started with `MKL_VERBOSE=1`. Do not mutate the process environment after runtime/provider initialization. For a small capture, set the environment in the native child's environment before `exec`, and leave it immutable throughout that process. Separate owned processes with different inherited settings if comparing `=1`, `=2`, or off. Do not switch environment values in one process.

## Minimal owned evidence proposal

The source reviewed in R753 uses `oneapi::mkl::blas::row_major::gemm(queue_for(stream), ...)`: FP16 (`sycl::half`) or BF16 (`oneapi::mkl::bfloat16`) inputs and FP32 output. The existing component test in `tests/sycl/gemm.cpp` covers both data types and realistic GEMM dimensions, but it loops multiple beta settings and then makes hundreds of pipeline GEMM calls. Running that unchanged with verbose enabled is broader than needed and can produce many records. A bounded Main-owned diagnostic should invoke the existing GEMM component path in a finite, serial, single-process capture, selecting one FP16 and one BF16 call for each shape family Main considers representative (including the larger routed-expert shape if that is the target). Capture the version line, detected GPU line(s), and only the matching GEMM lines with dimensions, type, and ending device field; record which intended calls were observed and whether output was complete. Keep the raw output within the repository's 64 MiB per-job diagnostic budget and retain the compact extracted lines/results, not a redundant full success trace. If a tiny selection cannot be made without editing the existing test, a small purpose-built owned harness is preferable to retaining hundreds of repeated lines.

Run the diagnostic outside the clean performance cohort and without concurrent GPU work. Start it with `MKL_VERBOSE=1` set in the child's inherited environment, before `exec`; do not change that environment after initialization. Record binary/source identity, compiler and runtime/driver/library versions, device, exact dimensions/type, output completeness, and correctness status. First confirm that the runtime actually emits verbose GEMM lines under the installed 2026.1 library; do not substitute 2026.0 documentation for this check. One representative line per type and shape establishes only those calls. If matching output has `GPU<n>`, conclude that those calls were reported as GPU-executed; if the device field is empty, conclude host execution for those logged calls. If expected calls are missing, report inconclusive and investigate instrumentation coverage/output, without treating the missing lines as negative proof.

`tests/sycl/gemm.cpp` has parity checks against FP32 accumulation for multiple beta values and shapes. If Main builds/runs it, preserve its original pass/failure status and validation; verbose attribution is an additional observation, not a reason to weaken or replace correctness checks. The focused verbose capture and any clean performance measurement must be separate processes because output instrumentation affects execution.

## Limits and relation to R753

R753 already establishes the source-level call shape and that no runtime fallback observation has yet been made. This report adds the exact current (2026.0) official output discriminator and the environment/timing/global-state constraints. Neither the previous report nor this one establishes what the installed 2026.1 library does on B570 for any specific call. The result also cannot quantify CPU time or establish that CPU is on the critical path. Keep host-side grouping, staging/copies, synchronization, and busy polling as separate candidates unless their own measurements attribute them.

Do not use `libmkl_sequential` presence to infer host execution: that library name concerns oneMKL's threading layer and does not identify dispatch for this SYCL GEMM call. Likewise, do not conflate device-side software emulation with host CPU fallback. No claim about either is made by the verbose index alone.
