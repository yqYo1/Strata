# When programmable processing-in-memory wins after the full data path is charged

**Knowledge collection; no local-system claim.** Question: which workload and placement patterns retain benefit after host↔DPU transfers and setup? This compares PrIM's experimental characterization with the later DIMES offload-aware study; PIMulator explains mechanisms only. Machines, baselines, workload samples, and timing boundaries differ, so the speedups are not one continuous experiment.

## Evidence boundaries

PrIM (2022) ran real UPMEM hardware with 640 DPUs at 267 MHz and 2,556 usable DPUs at 350 MHz, comparing an Intel Xeon E3-1225 v6 CPU and NVIDIA Titan V GPU. The larger system had about 160 GB of DPU memory; each DPU has a 64 MB bank and 64 KB WRAM scratchpad. Most inputs exceed WRAM, so kernels move MRAM data through WRAM by DMA. In headline CPU/GPU comparisons, PIM time covers DPU execution plus inter-DPU synchronization, while CPU and GPU are kernel-only; GPU host-device transfers are excluded. PrIM separately measures host↔DPU copies, but these do not enter the headline speedups. ([PrIM, arXiv v7 / IEEE Access 2022](https://arxiv.org/abs/2105.03814))

DIMES (2023) revisits 11 PrIM workloads on two Xeon Silver 4215 CPUs, 128 GB conventional DRAM, 20 PIM modules and 2,543 usable 350 MHz DPUs. Plotted UPMEM runs use 2,304 DPUs with 16 tasklets; the initial CPU baseline uses four threads. It adds CPU↔PIM transfers to kernel time and repeats with CPU code at `-O2`. The plot includes transfers to and from PIM, but does not itemize launch/dispatch or state whether all CPU-side result aggregation is included. DPU allocation and program loading are separate measurements, not part of plotted latency. No single bar combines transfer, setup, host scheduling and all postprocessing. A separate 44-core Xeon Gold 6152 comparison is kernel-only. ([DIMES 2023 paper](https://ess.cs.uos.de/static/papers/Friesel-2023-DIMES.pdf))

Table sizes are from PrIM’s scaling table; DIMES does not publish aggregate byte counts for every plotted case. Adding transfers often cuts apparent speedup by about an order of magnitude: RED, SCAN, SpMV and VA become slower than the four-thread CPU; BS, SEL, TRNS and UNI are marginal; GEMV, HST and TS still beat that baseline before CPU optimization is equalized. At `-O2`, only HST and TS “excel in all scenarios” at one to two orders of magnitude; GEMV, SEL and UNI are only slightly faster in some cases. The larger Xeon Gold further narrows PIM advantage. DIMES summarizes the overall resource-aware result as nine of eleven workloads performing best on a conventional server CPU.

## What placement and setup change

The evidence favors enough work per staged byte, small results, regular partitioning across DPUs, and reuse of an existing allocation. HST updates counts over an image and returns compact partials; TS performs similarity work over a series input for its queries. DIMES identifies both as compute-intensive survivors after transfer. This is not proof that every histogram or time-series application wins: bins, query count, skew, reuse, CPU implementation and bytes moved affect the balance.

UPMEM is not a transparently shared DRAM pool. DIMES explains that memory-controller interleaving spreads physical addresses across ordinary and PIM ranks, while UPMEM requires placement in a particular DPU bank. The SDK mediates placement and applications copy from host to PIM memory. Within a DPU, MRAM data is staged to WRAM; DPUs cannot directly share, so cross-DPU reductions and scans send partials through the CPU. PrIM measured transfer direction and granularity effects: for 32 MB per bank, one-DPU CPU→DPU bandwidth is 0.33 GB/s versus 0.12 GB/s DPU→CPU; parallel transfers across 64 DPUs reach 6.68 and 4.74 GB/s. These figures are specific to its host/SDK generation.

DIMES separately measures configuration. Allocating 2,304 DPUs takes 1.6 seconds; each rank allocation adds about 44 ms. Loading a maximum-size program takes up to 10–20 ms. The authors attribute allocation latency largely to serial rank allocation and blocking reset; code load is limited by instruction-by-instruction control-interface waits. These costs can swamp short one-off kernels, but the paper says they are negligible for persistent applications that keep the DPU allocation/program and receive new data. A sound reading is therefore conditional: HST and TS retain an observed transfer-inclusive advantage when startup is amortized, but the paper does not report an all-in elapsed-time result that adds setup to each HST/TS invocation. It also ran measurements on an idle server and warns that CPU and memory-controller contention raises latency.

## Mechanism evidence: measured platform versus simulator

PIMulator (2024) is an architecture study, not another measured end-to-end UPMEM comparison. Its cycle-level uPIMulator model uses 350 MHz, a 14-stage in-order DPU, 64 MB MRAM and 64 KB WRAM. The authors validate against real UPMEM: 710 single-DPU points show 98.4% correlation and 12.0% mean absolute error; 387 multi-DPU points show 83.6% correlation and 26.9% error, with larger error when host-mediated inter-DPU communication is prominent. The simulator models CPU↔DPU communication as a fixed-bandwidth channel tuned from hardware profiling, not by simulating host CPU instructions. It therefore helps explain mechanism, but its projected architecture changes are not hardware results or fully charged application latencies. ([PIMulator, arXiv v3](https://arxiv.org/abs/2308.00846))

Its simulations explain why arithmetic intensity and local memory both matter. A scalar DPU can become compute-bound on kernels that would be described as memory-bound on a CPU/GPU, because its simple in-order pipeline and instruction scheduling leave limited compute throughput. In a simulated 16-way SIMT GEMV, vectorization alone reaches 2.6× the modeled baseline; address coalescing raises that to 4.6×. The paper attributes the gap to MRAM read bandwidth, not a lack of parallel work, and simulates larger bandwidth as a remedy. It also models the 64 KB WRAM capacity constraint: statically staging data can overfetch for some access patterns, while cache-like demand fetching can help there; carefully orchestrated staging wins for other patterns. These are architectural counterfactuals. PIMulator does not establish that a changed DPU, cache or bandwidth design would deliver those speedups on existing UPMEM hardware.

Together, the three studies identify distinct gates. The PrIM hardware characterization establishes that many kernels scale across DPUs when the data is partitioned evenly and communication is limited. DIMES shows that this is insufficient when each invocation must copy a large changing input and collect outputs, or when a full CPU baseline is much stronger. PIMulator helps explain why data staging, scratchpad capacity, simple DPU execution and host-mediated coordination set the next limits, but its simulation cannot replace those system measurements.

## Transferable evaluation checklist (inference, not a UPMEM result or Strata recommendation)

For a GPU/ASIC offload study, report separate latency layers: kernel; device execution plus transfers in both directions; first-use configuration/compilation/allocation; and repeated application latency with explicit persistence and reuse assumptions. Identify where every input and output resides before and after the operation, include host packing/partitioning and result reduction, and state whether setup is paid once, amortized, or charged per call. Give byte counts, output sizes, reuse/query counts, partition balance, local-memory capacity and transfer granularity. Compare optimized CPU and accelerator implementations on named hardware with resource counts, compiler settings and equivalent work; include both a latency-sensitive baseline and any throughput-oriented multi-core baseline. Preserve a favorable full-boundary example and a counterexample, with timing inclusions stated for each. Keep simulated mechanism evidence visibly separate from measured platform results.
