## Proved address effects; not measured traffic

At the first K gather iteration, linear local IDs 0–31 cover `c=0..31, dim=0`; the source address is `row[c]*256`, so adjacent work-items select different rows with a 256-byte row pitch. IDs 32–63 cover the same cells at `dim=1`, etc. Per-lane one-byte K-code requests therefore do not follow the contiguous 256-byte dimension of any one row. They may still be served by cache or compiler transforms; the source does not prove memory transactions, cache misses, or wasted bytes.

For a cell-major flattened index `j`, `c=j/HD`, `dim=j%HD`, adjacent IDs traverse adjacent dimension bytes in one row. Each 128-ID group spans 128 consecutive code bytes; the full 256-byte row is covered in two such groups. This changes source-load lane ownership from row-scattered bytes to contiguous dimension bytes. Selected rows remain indirect and can still scatter across the pool. K scales (`ks[i]`, lines 149–152) are a separate 32x4 access and should remain unchanged in the first comparison so the code gather is isolated.

That K source remap must transpose values back to the matrix consumer's logical `[dim,cell]` tile. Directly writing `kv[dim*32+c]` from lanes whose adjacent IDs advance `dim` makes adjacent half stores 32 half-elements (64 bytes) apart for fixed `c`. This is a plausible SLM bank-conflict pattern, not a proven device transaction: Intel documents device-dependent SLM bank counts and serialization for distinct addresses in one bank. A padded pitch or tiled transpose may alter that pattern, but either adds layout/consumer work and needs compiler/device confirmation. The existing K matrix pointer and stride are line 165; any pitch/layout change must update every affected load and retain the same logical K operand. The already contiguous V gather is a useful unchanged control, not a second expected coalescing win.

No transaction count or speedup follows from the address arithmetic. The relevant output is an actual profile of global-load sectors/transactions and cache behavior, plus local-memory conflicts and matrix service, for this own kernel/device. A cell-major experiment is worthwhile only if the Direct-path profile attributes meaningful time or poor load efficiency to K gather.

## Bounds, barriers, SLM, and occupancy constraints

The active tile always has 32 row slots. `count` is clamped to `[0,cap]` at lines 123–124; `c0` advances by 32; only `c0+tid<count` reads an ID (lines 126–131). A negative cell or negative page leaves `row=-1`, and both gather paths write zero for that row (lines 127–138, 143–148, 210–214). The current kernel does not locally check an upper bound on the `cell` ID before indexing `page_table[cell/page_size]`; the normal selection/page-table contract therefore remains a precondition. Do not widen vector reads across the per-row 256-code boundary or across invalid rows. Mode-1 vectors must preserve exact INT8-to-half code values and the existing 4-group scale multiplication.

All work-items initialize their assigned gather outputs, including invalid-cell zero fills. A barrier after row resolution (142) precedes K/scale reads; the barrier at 153 precedes QK matrix reads. Matrix work is subgroup-conditional but its following group barrier (187) is uniform. V/value-scale writes precede the barrier at 216 and subsequent PV consumers. The `count` loop is group-uniform. Keep these control-flow facts: no early return for inactive lanes, no barrier under subgroup-only control, and all lanes must complete the transpose before matrix loads. Official joint-matrix operations are subgroup collective operations and must be called in converged subgroup control flow; current subgroup guard around the four QK subgroups already has each participating subgroup converged.

The current `kv` local accessor is `CH*HD` half values = 16 KiB (lines 67–72). A 128-work-item group and these local accessors are subject to device local-memory admission; `matrix_available` checks a lower-bound formula and device matrix support (lines 315–341), not actual compiler register use or achieved occupancy. Source alone cannot establish register count, spills, allocated SLM after lowering, resident work-groups, or occupancy. Any added staging/padding must be counted against this check and measured after compilation; no build was run here. Preserve current barriers and local-memory contract before interpreting performance.
