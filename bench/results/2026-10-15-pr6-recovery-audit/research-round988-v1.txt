## Production hook association and coverage

`Trace` binds to the passed stream's queue and requires an in-order queue, profiling property, Level Zero backend, and GPU (`src/sycl/command_profile.cpp:89-98`; `launch.hpp:48-58`). The request creates it for `m.cs` (`layer_major.inc:366-369`). The existing layer-major admission requires `m.copy == m.cs` (`layer_major.inc:100-107`), so the selected map uploads and kernels share this queue. `observe_impl` checks the stream pointer against the bound pointer (`command_profile.cpp:167-180`). This is a plausible queue/event association for the current one-thread window2 path; it is a caller-level association, not an independent inspection of each event's queue/context.

The two submission seams are narrow and clear: `finish(stream,event)` passes the actual returned event to the hook before its existing null-stream wait (`launch.hpp:61-65`), and nonzero `cudaMemcpyAsync` captures the event returned by `queue(st).memcpy` (`compat.cpp:255-263`). In the current tags, source inspection found the expected one-event path: both ordinary and parallel-IQ dequant launches call `finish` (`src/kernels/sycl/iq.cpp:26-46, 79-101, 179-205`); gather and native16 elementwise/combine/write use `for_each`/`finish` (`postops.cpp:239-248`, `native16.cpp:116-159`); local GEMM and vLLM-returned GEMM events both reach `finish` (`gemm16.cpp:185-247, 281-315`). Both route-map copies use the compatibility hook. The current tagged scopes therefore cover the intended command event for every call site reviewed; no new wait, marker, or per-command drain is introduced.

Coverage starts late in the window. `LayerMajorCoarseProfile::moe` begins at `moe_window.inc:81`, while the command `Frame` begins only after norm/projections, router, shared-expert work, D2H route readback plus its drain, and CPU route grouping (`moe_window.inc:84-110, 114`). The collector tags the two H2D route-map copies, dequant, gather, GU, SwiGLU, down, combine and residual writes (`moe_window.inc:119-183`). It does not capture the earlier window commands or route readback, the CPU grouping interval, or the coarse marker barriers. Its sampled service cannot be summed to reconstruct the complete coarse MoE interval or full request. That boundary should be in the diagnostic interpretation.

A completeness gap remains: `Group.eligible` is incremented only when a hooked event is observed; the destructor emits groups only when eligible is nonzero and only checks `selected` for those groups (`command_profile.cpp:110-117, 167-180`). There is no expected-per-phase event/call count or required nonempty-phase check. A missing hook for a whole phase is indistinguishable from a valid zero population, and can still yield `complete=1`. Source inspection covers the present call sites, but the diagnostic's `complete` bit alone does not prove all intended phases were hooked. The synthetic test currently does not close this gap (see below).

## Current window2 strata and representativeness

The bins are correctly implemented as `1–15`, `16–31`, `32–63`, `64–127`, `128–255`, `256–511`, `512–1023`, `1024+` (`command_profile.cpp:25-30`). `Frame::consider` retains the four lowest deterministic FNV ranks per bin keyed by `job.global_row`, and the four lowest expert ranks for dequant (`:35-50, 139-146`). Tags reuse the same selected jobs for gather/GU/SwiGLU/down, while dequant is selected by expert (`:147-159`). Empty bins do not spuriously fail, matching R979's correction (`:110-117`). Counts are actual hooked event counts per phase/bin; for current wrappers one event per tagged operation was confirmed above. `eligible/selected` can be used as an expansion factor for a within-bin sample mean, but the code does not compute a weighted request total or uncertainty. The choice is deterministic, its seed/ranks and job IDs are not emitted, and the counters alone do not provide a randomized sampling receipt; do not present a weighted extrapolation as confidence-bounded.

This is materially different from R978's five-chunk/8K model. `run_moe_window` accepts a pair of chunks (rows greater than 8192 and at most 16384; `moe_window.inc:5-8`); for the 39K, 8192-capacity input there are two paired window calls (first rows 0 and 16384) and one partial tail handled by the existing path. Across 48 layers that is 96 dedicated window calls. `Trace::begin` records only first_row 0 and layers 0, 15, 31, 47 (`command_profile.cpp:124-132`), so the four captured frames are four first-pair windows out of 96, not five request-wide chunks or all windows. It misses the row-16384 pair and tail, and four fixed layers cannot establish all-layer representativeness. This is accurately labeled `selected_first_windows` in output (`:118-120`), but the output does not report request-wide window coverage; use Main's separate owner/window census if stating coverage.

A reproducibility defect affects the selected job strata: `Frame::consider` ranks `global_row`, but `Meta` stores expert/rows/shape only (`command_profile.hpp:9-13`), and `Frame::tag` receives `row` without copying it into the record (`command_profile.cpp:147-161`). Sample lines print no row/job ID (`:104-108`). When an expert is split into two 8192-row jobs, equal-size records for the same expert cannot be distinguished or mapped back to the selected packed-route offset. The diagnostic therefore cannot independently verify the lowest-rank job selection from its own emitted records. Preserve the source route identity in a future revision or mark this validation gap; no code change was made here.

## Fixed bounds and lifetimes

The fixed collector has 4 frames, 160 pending `sycl::event` handles, 640 numeric records, and a `static_assert(sizeof(Impl) <= 128 KiB)` (`command_profile.cpp:18-19, 64-78, 89-91`). The 160 cap is distinct from opaque runtime/backend event storage; it is not a hard whole-process memory bound. A current one-frame upper count is 141 records if the reviewed one-event-per-call contract holds: 32 selected jobs × 4 job phases =128; 4 selected experts ×2 dequants =8; two uploads + one combine + two writes =5; total 141. Four such frames are 564, below 640; the 160 per-frame event ceiling leaves 19 slots. The separately planned 256 KiB serialized-output budget is not enforced by a byte counter in this source; output is streamed with `fprintf` in the destructor (`:99-123`).

Retirement ordering is sound in the production request path. Each selected `Frame` keeps handles until the existing checked `cudaStreamSynchronize(m.cs)` after both HC writes (`moe_window.inc:181-191`); status is checked before timestamp queries, then handles are cleared only after all queries complete (`command_profile.cpp:182-212`). The `Trace` is owned by `MoeWindowContext`, declared before the outer `DraftUploadGuard` lease (`layer_major.inc:366-369, 405-419`; owner at `prefill.cpp:438-448`), so early return/cancellation destroys the frame and clears TLS, then the lease drains before the request owner releases remaining handles. If both checked drains fail, the existing guard aborts with owners live. A profiling query failure marks the trace incomplete and retains handles until outer retirement, without changing inference success; this is reasonable for a diagnostic, provided incomplete traces are rejected by the consumer.

One fixture-only ordering flaw is present: in `tests/sycl/command_profile.cpp`, `Pending` is constructed before `trace` (`:33-37`), so on an exception after event capture `trace` is destroyed before `Pending` performs its fallback drain. The normal path explicitly drains and resets the trace afterward (`:72-80`), but the fixture's error path does not keep event owners through its cleanup drain. This should be corrected before treating failure/cancel fixture behavior as lifetime-validated.

## Default-off behavior and test truthfulness

`requested()` reads an immutable startup environment value once and defaults off (`command_profile.cpp:80-88`). When off, production allocates no `Trace` and submits no extra GPU command, event, barrier, wait, or timestamp query. The hot-path delta is still nonzero: `finish` and every nonzero compatibility async copy take a thread-local `active` branch (`launch.hpp:61-65`, hook header `:8-10`), and window2 still calls `Frame::tag`/constructs tag scopes around all jobs even when `command_trace` is an empty frame (`moe_window.inc:114,119-183`). These are CPU-side checks/calls; the candidate has no source measurement of their default-off CPU cost. The synthetic default-off fixture proves functional output/guards, not zero overhead or binary-equivalence. Measure off/on in separate fresh processes, with environment fixed before runtime initialization; do not switch arms in-process.

The synthetic arithmetic is internally consistent: 64 jobs, eight per row bin; 4 selected jobs per bin gives 32 selected jobs. It submits 384 per-job kernels (six kinds ×64), plus combine and two writes =387 kernels. Selected records are 128 job-phase events +8 dequant events +2 copy events +1 combine +2 writes =141; total observed eligible events are 389 after adding both uploads. However, line 80 prints the literal `expected_profile_records=141`; the test never reads actual `Trace::records`, `complete`, or phase counters (there is no accessor), and it will still print `case status=PASS` if on-mode profiling is incomplete while tensor/guard checks pass (`tests/sycl/command_profile.cpp:71-81`). Thus 141 is a correct expectation, not an asserted result. Also the CMake target is `EXCLUDE_FROM_ALL` and has no `add_test` registration (`cmake/sycl_backend.cmake:153-170`); it needs an explicit target build and explicit run in both modes. The existing 25-event calibration is a distinct test and does not validate this collector's sampling counters.

## Timestamp contract, interpretation, and gates

The primary reference is Khronos SYCL 2020 Specification Revision 12, source commit `b3bcc5d5cc83217d14ebbb904e353c5a0d17f52b` (2026-08-06). Its event profiling section defines 64-bit nanosecond timestamps on a shared per-backend timebase; `command_submit` is before `queue::submit` returns, `command_start` is action start, and `command_end` is action end. It says `command_start`/`command_end` queries can block until running/complete and makes no timestamp-accuracy guarantee. The queue property requires profiling capture; device `profiling_timer_resolution` is in nanoseconds. Source: [Khronos SYCL 2020 Revision 12 at pinned source commit](https://github.com/KhronosGroup/SYCL-Docs/commit/b3bcc5d5cc83217d14ebbb904e353c5a0d17f52b) and [official registry HTML](https://registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html). Applicability: normative generic API semantics used to interpret these fields; it does not qualify this UR/Level Zero driver's accuracy or service metrics. License/provenance: Khronos copyright with a conditional license to use/reproduce the unmodified specification; this report only paraphrases semantics and copies no spec code/text. Counterevidence: Khronos disclaims accuracy/completeness/reliability and the spec gives no timestamp accuracy guarantee, so Main's B570 calibration is required and only qualifies its tested queue and command set.

Accordingly, `end-start` is backend-reported action service for the returned event; `start-submit` is submit-to-start delay, not host CPU time. Neither is EU occupancy, useful FLOPs, cache/DRAM/PCIe traffic, physical bandwidth, or whole-window busy time. `steady_clock` is used only to measure query wall duration, not subtracted from device timestamps (`command_profile.cpp:193-207`), which is correct. The collector logs sample sums and group counters, not a total service estimate; aggregate sample durations can overlap only if the actual backend event semantics/queue violate the assumed in-order sequence, and in any event they omit most request commands. It reports `hardware_busy=UNMEASURED` (`:118-120`).

Before interpretation: explicitly build/run `sycl_command_profile_test` off and on; make its on-mode outcome assert actual completeness and 141 records/counters, and its error cleanup retain the trace through the checked drain. Then verify the current 39K request's four selected frames, actual phase populations, queue/runtime identity, timestamp order/granularity and owner/fault closure, with off/on in separate processes and intact request/correctness checks. Use only this bounded four-frame result as sampled evidence; it does not answer full-request command service without a justified layer/window expansion. Keep clean unprofiled model speed and inference adoption separate. Main's current build and these execution gates remain outside this source-only report.
