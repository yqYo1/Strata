# R828 — Block-scaled activation streams with local 16-bit decode

**Purpose:** knowledge collection; read-only research. **Retrieved:** 2026-10-16. This report compares two implemented FP8 activation representations as compact storage/transport streams whose consumer may locally unpack values to FP16 or BF16. It does not assess model weights, KV caches, native FP8 matrix arithmetic on Intel BMG, or a Strata implementation. No source was copied, adapted, built, tested, benchmarked, or loaded; no GPU or process inspection was performed.

## Increment beyond the existing precision work

The research index and retention metadata already cover saved-residual FP16 (R569), model-quality gates (R573), native-16 framework state and producer/consumer boundaries (R782), and typed low-precision GEMM interfaces (R783). R782 and R783 were inspected only at the relevant interface/quality sections. R825 addresses direct-16 GEMM rounding, while R826 isolates a native16 AOT image; neither compares sub-16 activation streams, their scale metadata, or decode materialization. The active native16 pipeline remains a distinct producer/consumer implementation and has not been replaced by this report. The new evidence here is about encoded activation tensors that remain one byte per value plus scale metadata until a device decodes them. This is a reusable storage/transport comparison, not an inference precision decision.

## Design A — Transformer Engine MX-style block scaling

OCP MX v1.0 defines a 32-element scaling block and an 8-bit E8M0 scale for MXFP8. Its named MXFP8 payload is E5M2; the spec does not name E4M3+E8M0 as MXFP8. Transformer Engine (TE) implements an MXFP8 quantizer that accepts an FP8 dtype and partitions values into groups of 32. Its current source declares `SCALE_DIM_X` and `SCALE_DIM_Y` as 32, reduces each block’s magnitude, derives an E8M0 exponent scale, multiplies by the inverse scale, then converts to the FP8 payload. Where a TE recipe chooses E4M3, describe that as TE’s E4M3 block-scaled variant rather than the OCP-named MXFP8 format. The implementation source is CUDA and contains an `__CUDA_ARCH__ >= 1000` kernel guard; its implementation proves a Blackwell-oriented CUDA path, not a portable kernel for other GPUs.

For a `[rows, hidden]` activation, rowwise data has a scale for each 32 adjacent hidden values: logically `[rows, ceil(hidden/32)]`. Columnwise scaling reverses which dimension is grouped, with logical scale shape `[ceil(rows/32), hidden]`. TE’s tensor model can retain rowwise, columnwise, or both orientations, and can optionally swizzle scale storage for GEMM. A standalone rowwise stream should not allocate a second columnwise payload unless a later consumer needs that orientation: two data layouts erase much of the storage reduction. GEMM-swizzled padding is a physical-layout choice and must be included in capacity/transport counts, not replaced by logical scale counts.

Scaling is current-data, block-local amax rather than a learned calibration table. A large value sets the scale for its entire block; the inspected path has no outlier side stream that preserves that value separately. Smaller neighbors can therefore lose relative resolution or underflow sooner than with a smaller block. The source explicitly computes an E8M0 scale and casts scaled values to the chosen FP8 type, but the wrapper does not promise a framework-independent rounding/overflow contract for every compiler/device. That exact cast and scale conversion should be recorded for any separate implementation.

The quantizer has an actual tensor-storage boundary: `MXFP8Tensor` carries FP8 rowwise/columnwise data and inverse scales, and `dequantize()` returns a plain tensor through TE’s `_FromMXFP8Func`. That API is a materialization point; a model operator that consumes quantized operands directly can instead avoid the expanded output. TE’s fused cast path can also include an activation operation and update scale/data in the same kernel. These are real framework boundaries, but the CUDA code does not establish that its conversion kernel can run on a GPU without compatible FP8 support.

## Design B — TorchAO dynamic rowwise Float8Tensor

TorchAO v0.18.0 provides an independent `Float8Tensor` storing `qdata`, a scale tensor, a block-size description, and the original activation dtype. `from_hp()` defaults to `torch.float8_e4m3fn` with `PerRow()` granularity; for `[tokens, hidden]`, this is one dynamic scale per token row, not a group every fixed number of features. Its generic path chooses a scale from the current high-precision tensor and converts to FP8; optional high-precision lower/upper bounds can constrain scale selection. The tensor supports a standalone `dequantize(output_dtype=...)` API returning an ordinary tensor, while linear/matmul handlers can pass qdata and scales to a native scaled-matmul implementation without first materializing all values.

This row scale has lower metadata overhead than one scale per 32 values, but one unusually large feature affects the whole hidden row. There is no separate outlier payload in the examined Float8Tensor path. The quantization primitive clamps the scaled value before casting; its `_RoundToFloat8` wrapper delegates conversion to `tensor.to(float8_dtype)`. It documents that older PyTorch versions did not saturate finite FP8 overflow, which is why the quantizer clamps first. The high-level wrapper does not specify a portable device rounding mode. Unlike a fixed learned calibration, its normal path derives scale from each current tensor; supplied bounds can serve as an explicit range constraint but are not evidence of a task-calibrated scale.

TorchAO’s `dequantize()` calls `_dequantize_affine_float8` with a requested output dtype. The affine primitive is defined as a copy-conversion followed by scale multiplication, so eager execution has a full output tensor boundary and may use more than one operation. Compilation could fuse those operations, but the Python tensor API alone does not establish fusion. A fused consumer would load FP8 values and row scales, apply the scale while converting locally, then consume FP16/BF16 values in registers. That path requires a consumer implementation that accepts the encoded representation; it is a port hypothesis, not a guarantee that TorchAO will dispatch such a fallback on a target without FP8 arithmetic.

## Logical bytes and decode break-even

For FP16/BF16 input storage, the reference payload is 2 bytes per value. An unpadded OCP-style 8-bit payload with one E8M0 byte per 32 values is `1 + 1/32 = 1.03125` bytes/value, 48.44% fewer logical bytes than 16-bit storage. A rowwise FP8 payload with one 4-byte scale per row of width `H` is `1 + 4/H`; at `H=2560` this is 1.0015625 bytes/value, 49.92% fewer. Those figures exclude row padding, alignment, extra orientations, headers, scratch, and allocation granularity. They are storage arithmetic, not measured bandwidth or memory-fit results.

For a transfer of `N` values, the ideal transfer-time budget is `(2 - compact_bytes_per_value) * N / measured_PCIe_bytes_per_second`. Compression wins only if encode work, scale calculation, metadata movement, synchronization, and local decode together cost less than the saved transfer time. If activation values originate on the host as FP16/BF16, encoding them there adds host work; if they originate on the GPU, sending them through the CPU merely to quantize would likely remove the intended benefit. Measure both directions when the actual path requires them.

On GPU memory, a direct 16-bit producer store plus consumer read transfers about 4 bytes/value. If the producer writes the compact stream directly and the consumer unpacks inline, the corresponding payload traffic is about 2.06 bytes/value for 32-value MX scales, before scale-cache effects: roughly 1.03 bytes on store and 1.03 on read. Rowwise FP32 scales are about 2.003 bytes/value. By contrast, a separate unpack kernel reads the compact stream, writes a 2-byte/value half tensor, and the consumer reads that half tensor; this adds another full-sized write/read pair after the compact read. If encoding itself is a separate pass, also count the original 16-bit result write, the read for amax or range scan, the quantization reread, the compact write, and any partial-scale scratch. A single GPU queue or nominally fused API is not proof that those passes were eliminated. Record bytes, kernels, peak live buffers, scale scans, transfers, and synchronization over the complete producer-to-consumer path.

## Applicability, quality, and Intel boundary

The current Intel SYCL joint-matrix extension table includes FP16, BF16, integer, and TF32 combinations for BMG G21/G31; it does not list an FP8 joint-matrix combination. That API table does not prove no lower-level hardware path can exist, but it supplies no native FP8 contract. Neither OCP MX format publication nor TE’s SM100 CUDA implementation can be used to infer native FP8/MX arithmetic on BMG. TorchAO or another runtime offering an FP8 configuration for an XPU likewise does not identify whether a given device uses native arithmetic, software decode, or another backend. Until a specific Intel device/compiler/runtime/kernel combination is verified, treat BMG use as compact activation storage followed by local unpack into the already-qualified FP16/BF16 consumer type.

Quality evaluation must inspect the encoded/decode values and the task. At tensor boundaries, retain a fixed FP16/BF16 reference and report max/mean absolute and relative errors, RMS error or SQNR, cosine similarity, NaN/Inf/zero/underflow/saturation counts, and error percentiles per row and per 32-value group. Include naturally occurring outlier rows and rare branches rather than only Gaussian synthetic tensors. For model effects, teacher-force the same long inputs and compare full-vocabulary log-probability/KL and negative log likelihood, top-token margins and rank changes at multiple layers, then score independent tasks or a predeclared task set. Token identity under greedy decoding is a useful observation but cannot expose probability shifts that leave the selected token unchanged; generated text alone also mixes decode randomness with precision change. Keep long-context and physical-context checks separate from short synthetic tensor tests. No acceptance threshold is inferred here.
