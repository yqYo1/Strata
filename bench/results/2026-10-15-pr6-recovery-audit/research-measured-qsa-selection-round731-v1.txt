## Current own-source path and scale

For the 78,453-token run, the source cursor produces ten chunks of at most 8,192 rows per layer. There are 12 QSA layers and 120 QSA layer/chunk intervals. QSA geometry is four indexer heads × 128 dimensions, pooling block 4, top-k budget 2,048 cells and selected width `min(n_kv, 2,051)`. The long-path capacity is `max_cells/4 + 2` score blocks; per-query steps carry the actual `n_kv`, block index, and width.

The current native indexer uses `native_qsa_indexer_append_batch` once per QSA chunk. With the default batch plan this submits completed-block append, final tail/spare update, and boundary/finalize work as three ordered queue commands; this has already removed per-token append submission from the normal prefill route. Do not propose another generic append-batching change. `append_completed_blocks` still computes one pooled row per completed group of four input rows, with FP16 input rounding, FP32 pooling/norm, RoPE and spare/tail contracts. The final phase updates partial tail and completed-block spare state.

Selection runs in 256-query batches (`sel_batch=256`). Each batch submits one `qsa_block_scores` kernel and one `qsa_block_topk` kernel. With 8,192 rows this is 32 batches per chunk, 64 selection-kernel submissions per QSA layer/chunk, or 7,680 across this 78K request, in addition to 360 native-indexer commands. These are source-derived submissions, not profiler counts. The current in-order queue is passed as a non-null stream, so `finish()` does not host-wait for these kernels. The queue interval still includes host work/gaps and cannot identify CPU submission as the cause without the finer observation.

`qsa_block_scores` launches one 32-lane subgroup for every query × active block. Each lane accumulates four adjacent dimensions for each of four indexer heads; each head then has a fixed XOR subgroup reduction, ReLU, and sequential head sum. The incomplete final block reads `dead` and receives the existing `+1e9` priority when it contains cells. For high context, one query evaluates up to 65,536 blocks at physical 262,144 tokens; across a late 256-query batch that is up to 16,777,216 query/block subgroups. The actual per-query `n_bid` predicate removes blocks beyond that query's prefix. The score launch's `active` bound comes from the batch's final query.

`qsa_block_topk` launches one 256-work-item group per query. When width equals `n_kv`, it writes identity IDs. Otherwise it partitions the `n_bid+1` scored blocks across 256 workers, performs 32 serial one-bit radix threshold rounds with a group reduction each round, then counts greater/equal weights, scans tie budgets and emits cell IDs. Each complete block has weight 4; the final block has weight `n_kv % 4`. Equal score keys are resolved by lower block/cell index, and output IDs are ascending. At the 262,144-token bound, the last query has at most 65,536 score blocks and the per-worker scan partition is at most 257 blocks. Top-k width remains 2,051 after saturation; storage capacity is 32,771 IDs. The launch uses checked capacities and step bounds; it does not enumerate every context cell in the top-k loop.

## Conditional ranking

1. **Only if the finer profile identifies `qsa_block_scores` service or repeated pooled-key loads as material:** test an own-source query-tiled scorer. A concrete first shape is a group containing four query subgroups for the same block: cooperatively load that block's 128-float pooled key once to local memory, let four subgroups apply their distinct query rows and preserve the current per-head lane products/reduction, and use `dead` only for each query's own incomplete block. This targets reuse of the identical completed pooled key across adjacent query rows without changing the selection algorithm. It adds a local-memory stage/barrier and may lose to existing cache reuse or occupancy; profile global transactions, local-memory stalls, registers/SLM and end-to-end score-kernel duration before keeping it. The score tile must not cross query-dependent `n_bid`/tail semantics. At high context, bound active blocks and 256-query batch exactly as today.

2. **Only if the finer profile isolates `qsa_block_topk` reductions as material:** compare exact four-bit radix selection against the current 32 one-bit rounds. Each of eight rounds would histogram 16 next-digit bins over the same per-worker block range, combine the 16 counts across the group, and choose the digit containing the remaining weighted-cell rank; the final greater/equal budget and ascending-ID emission must preserve current output. This is a concrete reduction-count hypothesis (eight digit rounds instead of 32 threshold reductions), not an assumed speedup. It adds per-work-item histogram state and group aggregation. Preserve the sortable float-key transform (NaNs lowest, signed zero canonical), weighted tail count, ties by ascending block/cell ID, the width-equals-n identity path, and all output bounds. Reject if local storage/register cost offsets fewer collectives or if any selected ID differs on exact and near-boundary ties.

3. **Only if the finer profile attributes the indexer phase itself, and separates append kernel service from submission gaps:** inspect the three existing native append phases separately. A candidate worth testing is fusing the final tail/spare update into completed-block append only for full-block-aligned chunk ends, with the partial-tail path retained. This can remove one ordered launch only for aligned boundaries, but the finalizer currently establishes a global ordering boundary after all groups have read old tail and written pooled rows. Fusion must prove single-writer ownership, preserve the block+1 dead spare and `block_pos`, and handle chunk starts/ends modulo four across the physical 262,144 limit. If the current event says only host submission or append is a small share, this is not justified; a launch-count reduction alone is not a speed claim.

These rankings are conditional on stage attribution, not an assertion that any of the three stages dominates. The current device-batched indexer and batched block score/top-k route are already active. Do not reopen generic device batching, attention tile geometry, or unrelated tensor-core advice.

## Numerical, ordering, and qualification gates

For any score-kernel restructuring, first compare all score outputs with the current FP32 path and require exact selected-ID parity for the same inputs/steps where the existing contract expects it. A changed floating reduction tree can move a score across the 2,051-cell boundary even if average score error is small; no BF16/FP16 approximation is implied. For top-k restructuring, scores remain byte-for-byte inputs to selection, and ID output must be exact, including equal keys, NaNs, signed zero, partial final blocks and the full-width identity case. Preserve step validity, `active <= blocks`, `n_kv <= capacity`, `n_bid=floor(n_kv/4)`, output cap 32,771 and signed 32-bit cell IDs. Do not widen beyond the model's physical 262,144-token contract or use wrapped block/cell arithmetic.

A candidate must pass focused component parity on boundary lengths around multiples of four, selection-width saturation, radix ties and invalid/empty cases, then actual long-model selected-reference comparison, fault/teardown and RESTORE gates. Physical 262,144-context behavior is separate. Only repeated independent clean full-prefill samples on the same exact request/configuration can support a speed or adoption claim. This source report itself makes none.
