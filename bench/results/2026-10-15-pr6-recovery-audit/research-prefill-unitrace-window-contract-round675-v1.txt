# Named unitrace session window for long-prefill diagnosis (R675)

2026-10-15 JST. Read-only audit of PTI source at pinned revision `6c0d6b0b80c6dbac4b5902d9d5ade1c75b9e9033` and prior reports. No tests, build, compiler, GPU, provider/app process, environment probe, Git mutation, cleanup, or source change was performed. No profile was collected and no performance claim is made.

## Decision

The planned `--start-paused --session NAME` plus external `--resume/--stop NAME` is an official Linux temporal-control route in the pinned unitrace and does not depend on ITT. Main's actual collector has `BUILD_WITH_ITT=0`, so omit `--chrome-itt-logging` and do not expect ITT task labels. The named session avoids application `setenv`/`unsetenv` after SYCL/provider startup and is a practical, source-free way to collect one bounded *request window*.

It cannot produce a pure prefill trace. Resuming before one long `GEN` and stopping after `DONE` encloses the whole request: request handling/token setup, prefill, the one generated token's decode/sampling/output work, and any traced Level Zero activity between those points. The external controller has no prefill marker or acknowledgment that collection began/stopped on an exact application boundary. Treat the result as a single-request device/host activity census with prefill-dominant workload, not prefill-only attribution or a prefill tok/s measurement. One generated token limits decode volume but does not make it zero.

This is a useful low-intrusion diagnostic if the single-request trace fits the already-owned 64 MiB aggregate output ceiling; stop/mark incomplete at the ceiling, with no rollover. The old 512 MiB whole-prefill exception from R576 was a proposal, not an admitted budget. R669 v2 requires Main to confirm current owner limits before a run. The named session removes the need for an ITT-linked source hook for request-level collection; it does not solve exact prefill boundaries, prove trace completeness, or qualify clock/performance.

## Control semantics and limits

- Pinned README documents Linux-only temporal control: a named alphanumeric session with `--start-paused`, then `unitrace --resume NAME`, `--pause NAME`, or `--stop NAME` from another process. The named session controls every process attached to that session. It is distinct from spatial controls (`PTI_ENABLE_COLLECTION`, `__itt_pause/resume`), which need app hooks; ITT flags are compiled out in this collector. See README lines 909-1000 and CLI option guards in `unitrace.cc:318-329,403-424`.
- In source, the launcher creates the temporal shared-memory state and sets it paused before launching the instrumented child (`unitrace.cc:1139-1163`). The external commands write `TEMPORAL_RESUMED/PAUSED/STOPPED` (`unicontrol.h:121-153`). The child consults that state at collector control checks (`unicontrol.h:330-383`), not at Strata's HTTP/request or prefill boundaries. The controller's printed "resumed/stopped" confirms the control-state write, not an application-thread acknowledgment or exact first/last collected event. The first subsequent provider interception observes a transition; an already-running request is not paused by `--pause`.
- On stop, the child notices the state at a later collection check and invokes `OnSessionStopped`, which flushes the Chrome logger (`tracer.cc:246-274`; `unicontrol.h:356-365`). This does not wait for Strata's serving request or GPU queue. `--stop` is not a synchronous trace-file-ready acknowledgment. The parent has stop handling and waits for its instrumented children (`unitrace.cc:1323-1417`); normal `QUIT`, followed by child exit and checking the final trace file is closed/valid, is the conservative close procedure. A stop with no later interception may rely on process teardown's final buffer flush (`chromelogger.h:1897-1941`).
- Session names become Linux shared-memory names under `/uctrl` (`utils/shared_memory.h:25,63-79`). `shm_open` uses mode `0666` (`:88-124`); the name is therefore a control rendezvous, not an authentication secret. Use a fresh unpredictable alphanumeric name, one owned session at a time, and no unrelated attached process. Reusing an existing name may reuse/reset an extant mapping (`:88-103`); stop unlinks it while existing mappings stay valid (`unicontrol.h:143-152`). Avoid concurrent sessions/launchers with the same name and check the controller's session messages/results. The state enum is plain shared storage, not an explicit request/ack protocol; source does not provide a per-transition generation or child acknowledgment.
- `--chrome-event-buffer-size` is an event count per host thread, not a byte cap or completeness proof (`unitrace.cc:339-340`). `--output-dir-path` likewise is not a cap. The existing owned recipe's finite limits are guardrails; require an owner-side aggregate byte monitor, wall/RSS limits, and explicit incomplete status if a cap trips.

## Trace contents and interpretation

Use the proposed pair `--chrome-call-logging --chrome-kernel-logging`; both are supported under Level Zero/OpenCL compile guards even with ITT disabled (`unitrace.cc:318-329`). Keep device engine/thread lanes enabled; do not pass `--chrome-no-thread-on-device` or `--chrome-no-engine-on-device` (`:331-337`). Use JSON output unless the owner has validated another parser.

In the pinned Chrome JSON emitter:

- Device command slices are `ph:"X"`, `cat:"gpu_op"`, `ts` and `dur` in microseconds, with `args.id` holding the command id (`chromelogger.h:992-1032`). Kernel names carry kernel/shape metadata. Memory-command names append the requested byte count in brackets when available (`ze_collector.h:1161-1190`); this is requested operation size, not measured PCIe/wire traffic.
- Device `pid` is a synthetic device-process track, not the native process PID. Device thread metadata names include device model/PCI address and, with default options, engine ordinal/index plus source host thread (`chromelogger.h:168-292`). The host event remains under native host pid/tid. Thus use emitted metadata and event IDs to join lanes; never equate device pid with native PID. A lane is an engine/track attribution, not a serialized command-queue handle.
- Host Level Zero API calls are `ph:"X"`, `cat:"cpu_op"`, `ts`, `dur` in microseconds, and the API symbol/name (`chromelogger.h:1059-1118`). This can expose call durations such as `zeCommandListAppendMemoryCopy`, `zeCommandQueueSynchronize`, and `zeCommandListHostSynchronize` when the provider intercepts them. It does not expose HTTP/server/tokenization spans, and the generic API event does not include queue pointer, source/destination addresses, or copy-size arguments. An append API duration is CPU-side call time, not device copy execution.
- `chrome-kernel-logging` emits GPU memory copy operations as device events too. `mem_size_` becomes the bracketed size in the operation name; the copy endpoint addresses are not emitted. Level Zero host-call flow events (`ph:"s"/"t"`, `Flow_H2D_<kid>_<rank>` / `Flow_D2H_<kid>_<rank>`) and `gpu_op.args.id` reuse command IDs for causal matching (`chromelogger.h:1034-1053,2136-2199`). These flow category labels show the provider's flow relation, not a proof of payload direction or PCIe transfer. Do not infer copy direction, pinned-vs-device memory, or wire bytes from the flow label or M2D/D2M-style command name alone.
- For copying, report separately (1) host append-call wall/duration, (2) GPU copy operation execution duration and requested size if present, and (3) operation ID/flow association. The trace alone cannot prove allocation endpoints or actual transferred bytes because it has no allocation address/range map. Require separate allocator/source evidence before making endpoint/bandwidth claims; otherwise leave them unresolved.
- `gpu_op` durations can be summed across matched GPU events, but that sum double-counts overlapping engines/queues. Merge intervals on each device engine lane for lane-union time; merge across all visible lanes for visible-device activity union. Their difference is observed overlap, not useful-work percentage. PTI lane metadata does not expose the application queue handle, so do not label this *same queue* unless source/another independent record ties the measured lane to the queue. A no-event gap across all visible lanes is not proof that the GPU was globally idle if activity collection/identity is incomplete.
- Host `cpu_op` Level Zero API durations are not CPU busy time. Report visible API-call spans separately from the native request wall and provider device intervals. A request-window remainder is unattributed; it can include Python/server work, CPU tokenization, scheduling, synchronization, untraced runtime calls, and trace boundary/clock uncertainty. Do not call it host-idle or GPU-idle without the needed coverage.

The Level Zero collector converts device ticks using sampled host/device global timestamps: `PrepareToAppendKernelCommand` reads `zeDeviceGetGlobalTimestamps` (`ze_collector.h:3505-3608`), and `GetHostTime` maps kernel start/end relative to that pair into the host timestamp origin (`:2745-2769`). JSON then applies `UniTimer::GetEpochTimeInUs` and `GetTimeInUs` for both host and GPU slices (`chromelogger.h:1113-1118,1024-1027`). This supports a common host-normalized microsecond timeline in source, including cross-engine lane comparison. It is not empirical validation of actual GPU clock calibration/ordering/error for this Arc/B570 profile. Require ordered/overlapping host/GPU timestamps to pass sanity bounds and preserve the R669 v2 clock qualification status as false until a representative trace proves the join. Never treat the configured `UNITRACE_SystemTime=1` switch alone as proof of GPU-to-RAW accuracy.

## Narrow operational use and performance evidence

A bounded diagnostic sequence is: launch the pinned collector around the owned native `--serve` with `--chrome-call-logging --chrome-kernel-logging --session <fresh-name> --start-paused`; wait for the server's ready signal; externally resume once; issue exactly one long `GEN` request; after its `DONE`, externally stop; send normal `QUIT`; wait for clean native/unitrace exit and verify the trace file finalized, event identity and completeness. Ensure the request client is outside the unitrace-owned process tree/session; the named session controls all attached children. Record that `READY` and `DONE` are application-level request brackets, not profiler acknowledgment or prefill boundary markers. Do not run multiple generation requests in this window.

The resulting trace can answer whether the request's observed execution is dominated by kernel duration, copy activities, host Level Zero calls/waits, visible lane overlap, or unattributed intervals. It cannot directly assign events to a named prefill stage, distinguish prompt/decode without additional trustworthy markers, or produce a qualified prefill-only wall. Use the normal clean request receipt's prefill start/end and actual prompt token count for prefill tok/s; retain the diagnostic trace only for attribution. Run the clean performance cases at 32,768 and 65,536 actual input tokens as separate measured workloads, targeting >600 tok/s then 1,000 tok/s. These values are token rates, not input lengths. Record the configured 262,144 physical context separately; a 32K/64K request does not establish correctness at the physical context limit.

If the requirement is a prefill-only trace, the external session is insufficient. Needed evidence is a default-off in-process prefill-boundary controller that works with the exact `BUILD_WITH_ITT=0` binary without mutating process environment after runtime initialization, plus a verified stop/flush/trace-close handshake and representative completeness/overhead/clock tests. No such hook is asserted by this report; a future root source change is not required for the one-request diagnostic.
