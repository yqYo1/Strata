# R667 — Current long-prefill execution order and data movement

Date: 2026-10-15 JST. Read-only trace of current root `Prefill::run` / `run_impl`, `run_layer_major`, its planner, and standalone `generate` integration. AGENTS.md and ARTIFACT_RETENTION.md were reviewed. Prior R620/R622/R658 and the research index were consulted to avoid repeating expert-mix, deferral, and allocation conclusions. No build, test, compiler, GPU, process, Git, cleanup, private-B, live-log, environment, or root-source operation was performed. Only this report was written.

## Finding

The selected long route is a layer-major *orchestration* around the unchanged per-chunk `run_impl` math. For exact `STRATA_PREFILL_LAYER_MAJOR=1` and `n > Prefill::chunk()`, `run_layer_major` visits one model layer at a time. At each layer it copies all 512 packed expert blobs into a temporary 512-slot device cache, drains that upload, then runs the entire prompt in chunks through that layer before replacing the cache with the next layer's blobs. Within each chunk the order remains token embedding/residual load → that layer's first hyper-connection → QSA or GDN → second hyper-connection/router/shared expert/routed experts/combine → residual write. At the end of each nonfinal layer, final FP32 residual rows are saved to a persistent device prefix or host tail. The next layer reloads each chunk from that store.

For C=4096, FP32 residuals and requested `R_GPU=4096`, the planner keeps exactly the first 4096 residual rows in device memory when the prompt has more rows, and stores the rest in host RAM. With D=hc*n_embd=4*2560=10240 floats per row, each saved row is 40,960 bytes (40 KiB); the host tail is copied device-to-host at each nonfinal layer boundary and host-to-device when the next layer consumes it. This is a substantial repeated transfer path for long prompts. Its byte count is source arithmetic, not an observed link rate or a claim about achieved throughput. The source establishes plausible speed ceilings and costs; only a clean measurement can decide whether this path reaches 600 tok/s or approaches 1000.

## Selection and admission

`Prefill::run` selects the candidate only for exact value `STRATA_PREFILL_LAYER_MAJOR=1`, a live implementation, and `n > impl_->T`; short prompts and the default-off route call `run_impl` directly (`src/prefill/layer_major.inc:3-14`). This preserves the existing chunk-major route for short prompts. The layer-major candidate is SYCL-only and rejects split/stage/peer/hand-off/vision/reentry, missing native source, noncompact MoE, anything other than explicit `STRATA_PREFILL_MMQ=0`, and distinct copy/compute queues (`:16-57`). It also checks the supported 48-layer Qwen geometry and session/KV range (`:45-110`). Thus the following route is not a generic description of all prompt execution.

`LayerMajorResidualPlan::make` uses width `D=hc*n_embd`, row size `D*4` for FP32, and rounds any requested nonterminal GPU-row count down to complete chunks (`include/strata/prefill/layer_major_plan.hpp:78-117`). With C=4096 and request 4096, it chooses `gpu_rows=4096`; for `n>4096`, bytes are `gpu=4096*40960=167,772,160` (160 MiB) and `host=(n-4096)*40960`. The planner's `span` assigns a complete chunk based on its starting row, offsets host data relative to `gpu_rows`, and rejects a chunk crossing the stores (`:120-133`). Missing/`auto` R_GPU is a different mode: for FP32 it chooses the largest complete prefix within available budget (`:34-45,96-110`); it should not be conflated with an explicit 4096-row prefix.

Admission reserves 512 MiB of reported free VRAM after the additional layer cache and 8 GiB of available RAM after the host residual, upload slab, staging row and residency maps (`src/prefill/layer_major.inc:127-153`). This is an allocation check and reservation, not proof that physical free memory or OS paging equals the calculated amount. The temporary cache is 512 slots of aligned `layout.max_blob` stride (`:130-132`); `upload` is a host slab of that same aggregate size and `rows` holds the host residual tail (`:144-162`).

## Outer layer pass: packed expert lifetime

The outer loop initializes a temporary per-layer residency table, calls `m.src->copy_blob(layer,e,upload+e*stride)` for **all 512** experts, then calls `layer_cache.fill_slot(e, upload+e*stride, m.copy, ..., blob_bytes)` for all 512 (`src/prefill/layer_major.inc:292-320`). A checked drain follows before the table publishes each expert as resident (`:316-320`). Since copy and compute streams must be the same queue in this candidate (`:36-43`), the fill operations are ordered on that queue and the drain establishes the upload boundary. No streaming-ring issuer or Stager job owns these blobs. This source lifetime is one full packed layer in device cache at a time; the source copy buffer itself is reused to stage each expert and is not the per-expert dequantized-weight cache.

The wrapper then sets `stage_lb_=layer`, `stage_le_=layer+1`, points layer-major residual input at the GPU-prefix/host-tail stores for every layer after layer zero, resets PLE's previous-token pair for replay, and invokes `run_impl(tokens,n,pos0,err)` for this one layer (`:329-384`). It drains again before the next outer-layer iteration (`:383-395`). The same temporary 512-slot cache is overwritten with the next layer only after the prior layer's full chunk sequence and callbacks have completed. In the configured FP32 compact fallback, routed experts are **not** dequantized once and kept across chunks: `run_impl` uses two FP16 dequant scratch slots (`q=j%DQ`), runs `iq_dequant_gu_f16` and `iq_dequant_f16` for each active expert in each chunk, then reuses those scratch slots (`src/prefill/prefill.cpp:2808-2899`). The layer-major route reuses packed device blobs across chunks; it does not implement R622's deferred expert-major dequant/GEMM reuse.

## Per-chunk math and work ordering

`run_impl`'s chunk loop computes `T=min(m.T,n-c0)` and `p0=pos0+c0` (`src/prefill/prefill.cpp:1652-1660`). On layer zero it uploads token IDs and gathers embeddings in one batch when the embedding format/tokens permit, falling back to per-token `embed_row` otherwise; it broadcasts embeddings into four residual streams (`:1661-1746`). For later layer-major passes, it instead loads `m.R` from the corresponding persistent residual span. FP32 GPU-prefix spans use D2D; FP32 host-tail spans use H2D (`:1663-1695`). There is no FP16 pack/unpack in the stated route.

The per-chunk QSA step records are constructed from absolute positions and uploaded before the layer work (`:1784-1791`). At layer 1, optional PLE rows are gathered on an async host thread, uploaded to the device just before use, and the following chunk's gather is started into the alternate host buffer. The PLE table gather waits on that future; the upload is ordered on the compute queue and a recorded event is synchronized before refilling a host buffer that an earlier upload may still read (`:1747-1782`). PLE's recurrence/history work is only at layer 1. Each layer is then processed as two hyper-connection halves (`:1970+`): half 0 computes the normalized/mixed input and runs its attention path; half 1 computes the other input and runs MoE. GR writes update `m.R` after each half (`:2998-3024`).

For a QSA layer, the route projects K/V/Q and the indexer tensors, appends the chunk's indexer rows, scores/selects cells for each query batch, then executes batched prompt attention when available or its decode-attention fallback (`src/prefill/prefill.cpp:2110-2300`); KV append and staged host/staging-pool movement occur within this QSA path (`:2100-2290`). For non-QSA layers, half 0 runs GDN projections, gates, convolution and recurrence, then output projection (`:2018-2104`). These state updates are per layer and advance over the chunk sequence before the wrapper advances to another model layer.

At half 1, the code computes router logits for T rows, routes each row to K=10 experts, and computes the shared expert and scalar gate (`src/prefill/prefill.cpp:2300-2417`). It copies route IDs device-to-host and calls `cudaStreamSynchronize(m.cs)` before host-side counts, offsets and expert order are formed (`:2416-2508`). Under the selected candidate, `use_mmq` is false because admission requires explicit MMQ=0 and `mmq_plan().any` is rejected; `compact_moe_fp16()` is required, so each expert's activation rows are gathered into compact FP16 input storage. All routed expert IDs in the active layer map to the just-uploaded resident slots. The old `stream_all` condition is explicitly false when `m.layer_major_active` (`:1792-1798`); its all-layer streamed ring path is not used. The fallback `stage_one` rejects a missing layer-major residency entry instead of staging it (`:2712-2741`), while the ordinary `!stream_all` expert loop computes resident experts directly (`:2901-2918`).

For each expert in ascending expert-ID order with a positive route count, the SYCL/native path dequantizes that expert's packed GU and Down matrices into scratch, records no ring-slot release (resident path), gathers its compact activation rows, runs FP16 GEMM for GU, interleaved SwiGLU, then FP16 GEMM for Down into that expert's output rows (`:2808-2899`). `moe_combine` applies the original slot/weight mapping and adds the shared expert output (`:2967-2969`); the second GR write produces the layer's final chunk residual (`:2998-3018`). This is still per-chunk MoE work: the active experts and their weights are not combined across chunks.

## Residual prefix/tail and synchronization

For every nonfinal model layer, the final residual callback checks ascending chunk order with `LayerMajorChunkCursor`, determines `plan.span(row,count)`, and stores the residual. FP32 device-prefix rows are D2D; FP32 host-tail rows are D2H, followed immediately by the wrapper's checked compute/copy drain before the next chunk/pass can reuse the source scratch (`src/prefill/layer_major.inc:343-381`). On the next layer, the same chunk loads from D2D or H2D into `m.R` before the unchanged FP32 operations (`src/prefill/prefill.cpp:1663-1695`). The last model layer does not save an interlayer copy; its final FP32 residual is delivered to the caller callback (`layer_major.inc:352-355`).

The candidate requires `m.copy==m.cs` and opens a checked outer lease. Entry, each layer boundary, expert upload, each interlayer residual store, each full layer pass, and final exit drain the compute queue (the separate copy drain aliases it) (`src/prefill/layer_major.inc:232-244,311-320,374-399`). With the selected same-queue setting, ordinary expert-ring copy events are unnecessary for dependencies; all expert upload, compute and residual work are serialized by the in-order queue. The layer-major branch does not use the chunk-major expert ring's `copied/used` waits. PLE still has its host-future and alternate-buffer event described above. There is also an explicit stream sync after copying route IDs for CPU grouping in each chunk; that host dependency remains even though expert weights are already resident. These are real synchronization points and plausible throughput costs; none is a measured fraction of wall time in this report.

If C=4096 and the prompt is 34,603 model input tokens, standalone generation passes `n_batched=n_prompt-1`, so the prefill count is 34,602 predictions' conditioning rows; that yields nine chunks (eight 4096-row chunks and one 1834-row tail) if that is the exact prompt length (`src/program/generate.cpp:6361-6370`). There are 48 outer layer passes and 48*9=432 chunk/layer executions. With an explicit GPU prefix of 4096 rows, the first chunk is saved/reloaded D2D and the other eight chunks use the host tail. For this example the host tail is 30,506 rows = 1,249,525,760 bytes. Across 47 nonfinal layer boundaries, source code requests one D2H store and one later H2D reload per host-tail row: `2*47*1,249,525,760 = 117,455,421,440` bytes (about 117.5 GB decimal). Re-evaluate exact count from the actual input receipt before using this illustration as a run estimate; it is byte accounting only, not measured transfer traffic or time. For a 262,144-row input with C=4096 and the same prefix, 64 chunks execute per layer; host tail is 258,048 rows (10,569,646,080 bytes) and the analogous 47-boundary two-way copy request is approximately 993.5 GB decimal. The final layer's output is not copied into the interlayer store.

## Final-layer callbacks, MTP, and return to decode

For a chunk with a caller callback, `run_impl` synchronizes the compute stream after the final model-layer work, then calls `on_stage_chunk` followed by `on_chunk(m.R,T,p0,err)` (`src/prefill/prefill.cpp:3079-3090`). The outer wrapper suppresses intermediate-layer callback delivery to the caller; it installs its saved callback only for the last outer layer (`src/prefill/layer_major.inc:334-355`). Thus the user callback runs once per logical input chunk, after all layers' residual for that chunk has been reconstructed by sequential layer passes, not after every intermediate layer pass.

In standalone `generate`, `n_batched` is normally `n_prompt-1`; the final prompt token is left for the token/verify path (`src/program/generate.cpp:6361-6370,6532-6555`). If MTP is enabled, `prefill.on_chunk` builds the next-token IDs and first tries `prefill.draft_kv`; if that path is inapplicable it falls back to `mtp.prefill` (`:6430-6441`). `draft_kv` is a prompt K/V callback, not routed target-model work. Any optional target-head/logit callback is installed later as an outer wrapper around the existing MTP callback (`:6443-6493`): it uses the final residual, then calls the saved previous callback, so the target-head work precedes MTP KV work for that chunk. The outer layer-major candidate's last-chunk `on_stage_chunk` delivers the final checkpoint before `on_chunk` and sets `ss.ple_prev` to the final input pair (`layer_major.inc:334-355`).

MTP expert detach/restore is conditional on exact `STRATA_PREFILL_RELEASE_MTP_EXPERTS=1`, exact layer-major mode, a long prompt and the supported native single-GPU MTP4 case. The wrapper drains/destroys MTP decode graph readers and frees only routed MTP experts before calling the whole prompt; after `prompt.run` returns (success, false, or exception), it restores those experts before returning/rethrowing (`src/program/generate.cpp:119-172`; implementation `src/core/mtp.cpp:438-509`). Therefore final-layer MTP/KV callbacks and layer-major temporary-owner retirement complete before MTP expert restore begins. If release is off, the prompt simply calls `prompt.run` and there is no detach/restore. After the initial prefill, standalone generation reports prefill stats, refills any separately lent cache slots, resets/frees the prompt workspace, then starts token generation (`generate.cpp:6510-6555`). This keeps decode on its initialized weight/cache layout; the layer-major temporary expert cache is a prompt owner only.

## Other routes and performance hypotheses

The ordinary `run_impl` route is chunk-major: outer loop is over chunks, inner loop over all layers (`src/prefill/prefill.cpp:1652`, layer loop `:1928+`). It may use a resident cache plus an 8-slot staging ring or the `stream_all` all-expert issuer depending on `m.layer_major_active`, ring size, T, and source availability (`:1792-1798,2712-2965`). These paths overlap host staging/copy and compute differently and must not be described as the selected layer-major 512-slot-per-layer route. Short prompts remain here even with the opt-in set because `n<=chunk` (`layer_major.inc:10-14`).

Bounded hypotheses from source only: the current long route can pay for all 512 packed blob source copies and cache uploads on each of 48 layers, synchronous host route-ID readback/count/order per chunk, repeated per-chunk expert dequantization, and host-tail D2H/H2D movement at every interlayer boundary. It avoids routed expert weight loads during the layer's chunk sequence once that layer's packed cache is populated, and retains the caller's initialized decode workspaces/cache instead of repurposing them. Larger chunks can reduce the number of chunk/layer passes, route readbacks, and repeated active-expert dequantizations, but require larger live chunk scratch and change the amount of layer-major data parallelism; threshold/chunk tuning is deferred per user direction. Increasing GPU residual prefix can reduce host-tail traffic but consumes GPU memory reserved for decode and does not itself prove a higher rate. Neither hypothesis states a fix, tuning recommendation, >600 tok/s result, 1000 tok/s prediction, nor quality result.
