## 結論

現在の実装はnative MTP4 verifierの実Tごとに、48層のroute owner、CPU unique expert jobsとそのtoken rows、job `nt=1..4`、native GU/quant/Downのissuer/worker CPU thread-time、pool task/row/phase completionを一つのdecode requestへ結び、既存のverify/dispatch timing・counterと整合検査する。Mainがこれを実際の32K以上のdiagnosticで得れば「CPUに何件/何行/どの形式が来たか」と「CPUがどれだけ実行資源を消費したか」を見分けられる。CPU worker合計CPU時間は並列サービス量であってwall-critical-pathではない。現時点でこの新observerのMTP4実model出力を確認できる証拠はなく、数字は未知のままにする。

既存形状とモデル幾何からのスクリーニングでは、TG70に対してCPUの役割は十分大きくなり得る。R488の長文短出力中央値相当の1.875 verifier rows/outputなら、70 output/sで131.25 routed rows/s、全expert有用演算は約619.3 GFLOP/s。既存の6-core FP32 FMA control 0.818 TFLOP/sの約75.7%だが、これはpacked IQ integer-dotを測った値ではなく、CPU全量担当と仮定した比較に過ぎない。cache lookup entryの約97.94%がmissでも、CPUが計算するrowsの率はentry率とは異なり、ledgerの `cpu_rows/R` が答える。CPU unique packed weight bytesはT=4でroute overlapによりかなり変わり、素朴な論理上限でもRAM read controlを超えるとは限らない。従って現証拠は「70可能」も「不可能」も示さず、CPU/GPU/QSA/KVのどれがlimiterかは決めない。

### Conditional TG70 arithmetic

Metadata and current fixed geometry: 48 layers, top-k10, hidden2560, FF640, native one-expert-per-layer blob total 98,227,200 B, per expert-token useful routed GU+Down work 9,830,400 FLOP, complete routed row 4,718,592,000 FLOP (R481 corrected `decode-work-model.json`; R570 restates bytes/semantics). These are operation counts/logical packed extents, not traffic or timing.

For one joined receipt define `rho=R/E` (actual verifier token rows per visible output, honoring EOS/max-new), `q=cpu_rows/R` (share of routed token rows assigned to CPU), `Bcpu=owner[o=CPU].logical_blob` (packed bytes, once per distinct CPU expert group), `W=windows`, `A/D` accepted/proposed drafts. Then:

* TG70 rows/s = `70*rho`; full routed expert arithmetic = `70*rho*4.718592 GFLOP/s`. At R488-like rho=1.875 this is 131.25 rows/s, 619.315 GFLOP/s total. CPU routed arithmetic estimate = total × `q`, and GPU-cache-hit arithmetic estimate = total × `(1-q)` only if owner accounting confirms CPU+GPU cover all rows and any other owners are zero. The measured miss *entry* percentage is not q because repeated expert routes become one CPU job that can evaluate multiple rows.
* CPU logical packed expert-weight bytes/s = `70*Bcpu/E`; CPU logical FLOPs/s = `70*9,830,400*cpu_rows/E`. `Bcpu/E` depends on owner and distinct groups, whereas CPU compute depends on rows. Their quotient captures weight reuse: `cpu_rows / CPU_jobs` is average job nt; `job_nt` histogram separates reuse of a fetched blob from repeated row arithmetic. Neither `Bcpu` nor source RAM/file counters measures DRAM bytes; they also do not establish LLC reuse/cachelines.
* If every routed row were CPU-owned, total useful FLOP demand at rho1.875 is ~619.3 GFLOP/s, ~75.7% of the prior 0.818 TFLOP/s FP32 FMA control. At q=0.98 this simplistic multiply gives ~607 GFLOP/s. The mixed quantized integer dot/dequant/SwiGLU/Down path differs from the FMA control and additional work competes for cores, so this is not a ceiling/pass verdict. It identifies CPU work as large enough that a directly measured service/critical-path split matters.
* For a T=4 window the logical distinct expert payload bound per all-owner route window is 98.227–392.909 MB, or 24.557–98.227 MB per verifier row, depending on recurrence of IDs inside a layer. Applying R488-like rho and 70/s gives a rough 3.22–12.88 GB/s per-row equivalent if every unique expert were CPU-served. The CPU fraction and route type sizes lower/change this; unique IDs across layers are distinct, while duplicates are only within a layer/window. This range straddles below the 36.87 GB/s read control; it cannot prove RAM-bound or RAM-safe because the control/request traffic are not comparable. At the contrary no-reuse entry accounting, 98.227 MB/row ×131.25 rows/s ≈12.90 GB/s before miss weighting (≈12.63 GB/s at 97.94% miss); this is *not* CPU actual traffic and must not be used instead of `Bcpu`.
* 70 output/s leaves 14.286 ms/output total decode wall. Normalize all measured role CPU ns, caller spans and existing wall deltas by E for descriptive per-output values. Keep their overlap explicit. The sum of worker CPU ns may exceed decode wall by concurrency factor; `(decode wall - sum CPU time)` has no valid pure-wait interpretation.

These bounds exclude shared/dense expert, MTP draft, router, QSA/GDN attention, KV streaming, dispatch, activation quant, scheduler, GPU work and sync. QSA context-prefix scoring and host-KV reads from R488 can be substantial co-limiters. The clean end-to-end 70/s gate must remain independent of diagnostic output.

## Current-root route and what joined output separates

`expert_source.cpp:65-160` creates joined state only if both exact env values equal `1`, after prompt handling; only Linux SYCL, ordinary single-stage native pool, loaded MTP, capacity4, suffix0, split off and no peer/remote route passes eligibility (`decode_route_ledger.hpp:15-28`, constructor at expert_source.cpp:90-120). The `generate.cpp:6000-6014` snapshot starts immediately before request decode after prompt. First verifier T is explicitly1, later T follows MTP probability policy (`generate.cpp:6016-6038`). Every successful `ver.run` dispatches layer callbacks and then calls `verified`; commit and emitted rows are recorded at `generate.cpp:6060-6096`. `wait_commit` is separately timed and must succeed before complete close (`6130+`, scope header:45-58).

`expert_pool_dispatch_multi` deduplicates expert IDs per layer/window, classifies route `kind`, makes one `ExpertJobMulti` per unique CPU miss with its actual `nt`, and increments per-token-row multi_entries (`expert_source.cpp:2060-2187`). The ledger `record` maps `kind=-1` CPU, `kind=0` VRAM, and other owners separately; it sums group count, route entries, GU/down/blob logical extents, CPU jobs/rows and nt histogram (`decode_route_ledger.hpp:120-167`). `complete()` cross-checks per-layer callbacks against W, rows against R×layers, job rows against cpu_rows, route entries against R×layers×k, owner totals against source counters, and pool task expectations (`200-255`). Those are useful validity joins; they are not physical traffic measurements.

Pool service hooks bracket actual native GU, intermediate quant and Down work with thread CPU clocks, divided by issuer slot0 and worker slots1..5 (`src/kernels/cpu/service_budget.hpp`, called from pool.cpp; receipt aggregation `decode_route_ledger.hpp:292-311`). Thread CPU time counts time executing on CPU; associated wall spans and pool done/park boundaries are concurrent. `native_phase` reports planned/completed task/rows and completion/park counts; phases are not native phase elapsed ms (`footer native_phase_ms_not_available=1`). Existing snapshots expose `ver.ms_wait/pool/host/commit`, `dispatch ms_plan/actq/jobs/run`, pool ms_multi_gu/q/down, and explicit run/commit/draft spans (`generate.cpp:5986-6004`; emitted as index-based deltas at ledger `322-327`). These are overlapping scopes, not additive wall buckets.
