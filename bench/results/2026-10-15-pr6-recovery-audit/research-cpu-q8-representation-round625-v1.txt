# CPU expert GU: Q8 versus lossless signed-byte cache representation — R625

2026-10-15 JST. Read-only investigation of the Ryzen 5600X/AVX2 CPU route, prior CPU predecode/cache fixtures and retained live-route LRU receipt. Only this report was written. No source change, build, test, benchmark, GPU/model/service/process operation, Git command or cleanup was performed. New calculations are explicitly arithmetic scenarios; no cache is implemented or recommended for production.

## Decision

A RAM-side reuse cache has three materially different representations:

1. **FP16 weights**: two bytes per GU weight. This is not the low-memory option and still converts quantized weights to approximate half values. R603's measured cold-fill/amortization evidence concerns its integer-byte expanded fixture, not a separately measured FP16 cache implementation. If the cited “FP16 GU cache” means a two-byte-per-value cache, the retained evidence still argues against it: it has at least twice the payload of byte expansion and no better saved kernel service has been measured.
2. **True Q8 requantization**: convert each original IQ weight to a new signed 8-bit quantization and scale. This can use near one byte/value plus scales but changes weight values and output numerics. It must pass model-level quality evaluation; it is not a lossless optimization.
3. **Lossless signed-byte code expansion with original IQ metadata**: the existing R595/R603 fixture. It stores the original signed codebook integer in a byte and preserves original D/subscales exactly. It does not quantize decoded FP32 weights. The integer payload can reconstruct the same IQ code and original scale metadata; a kernel can retain current Q8_K activation quantization and integer dot structure. It costs ~3.35–3.40 MB per GU expert for this fixture because each original 256-value block also carries D and scale metadata.

Only option 3 has both a local correctness fixture design and measured cold-fill/warm-service pairs. Its model-level case remains rejected for request-cold synchronous fill at the measured 8 GiB request LRU. Raising RAM allowance to 20–48 GiB might reduce eviction, but the observer retained no LRU replay results over 8 GiB, and larger capacity cannot cure a poor cold-fill ratio without measured cross-request persistence. One concrete next screen, if Main chooses to spend more work here, is a **20 GiB maximum, live-admitted, nt1-only persistent-cache trial** with exact lossless bytes and two identical deterministic requests, and an automatic packed fallback. Do not begin with 48 GiB or true Q8 requantization.

## Current CPU path and its already-present reuse

`native_expert.cpp:32-68` obtains each format's activation dot type and bytes from GGML traits; `:71-76` quantizes FP32 GU input with `traits(gu_act)->from_float` and Down input separately. IQ GU formats use a Q8_K dot activation; the exact type depends on the original GGML `vec_dot_type`, so preserve the current trait-derived activation and Q8_K block scales. The codebook representation is on the weight side, not an alternate activation format.

For supported IQ types, `native_gu_rows` chooses AVX-512, then AVX2 multi-token code only when `nt >= mt_min` (default 2); otherwise it falls through to GGML, except the opt-in `STRATA_IQ_SINGLE_EXACT` helper at `native_expert.cpp:79-134`. The current AVX2 `row_dot<TY,NT>` decodes each packed weight block once per row, then loops over all `NT` activations reusing the decoded magnitude/sign/scale vectors (`src/kernels/cpu/iq_avx2.cpp:202-228,324-335`). Thus within-call reuse for nt2–4 is already present. A cache's additional value is only across later jobs that reuse the same `(layer, expert, GU format)`; it cannot claim the existing nt sharing again.

The actual AVX2 dot applies sign to the Q8_K activation bytes with `_mm256_sign_epi8`, performs magnitude×signed-activation using `_mm256_maddubs_epi16`, multiplies the subscale lanes via `_mm256_madd_epi16`, sums int32 lanes and applies block D×activation D using FP32 FMA before horizontal reduction (`iq_avx2.cpp:202-228`). A lossless expanded representation must preserve code magnitudes/signs, IQ subscales, block D, activation Q8_K bytes/scales, int32 saturation/overflow behavior, per-format half order and float reduction/FMA placement. R598's fixture explicitly checks the special `-128` activation behavior; sign-swapping the weight instead of the activation is not interchangeable for that case.

## What the bounded reuse evidence actually says

The one actual model request receipt is `cpu-gu-reuse-long-v1.json`, summarized in `cpu-gu-reuse-summary-v1.json`. It records 34,603 prompt tokens plus 128 generated outputs and an ordered CPU job stream from one request. R607's distinct 9,816 routed `(layer,expert)` pairs and 68,781 CPU jobs are an aggregate census, **not enough to infer LRU reuse**. The relevant evidence is the separate v2 observer's replay of that actual job order with its explicitly modeled serial demand LRU; it is still a simulation, not a production expanded cache or measured hit-time result.

For its `nt1_only` policy (the only policy corresponding to measured expanded speed; nt2–4 completely bypass it), the request-cold simulated LRU reports:

The summary's 8 GiB `existing_exact` service calculation makes the result more concrete than hit rate: current hit savings total ~4.31 CPU thread-seconds across formats, while overwrite refills cost ~6.76 seconds; modeled net is **−3.36 thread-seconds**. On a request-cold mapping, first-touch fills cost ~33.63 seconds and net is **−36.37 thread-seconds**. Individual values from `cpu-gu-reuse-summary-v1.json`: type18 9,544 hits / 7,968 fills, 2.20 uses per fill; type22 10,117 / 8,541, 2.18 uses/fill; type21 4,969 / 4,294, 2.16 uses/fill. The R603 warm savings were ~91–110, 53–76, and 133–169 microseconds per expert call respectively; cold fill was ~1.6–2.3 ms/expert and overwrite refill ~0.3–0.5 ms/expert. The arithmetic break-even is about 13–31 uses after a cold fill or 3–7 uses after an overwrite refill; the actual observed request's ~2.16 uses/fill misses both for most fills, consistent with negative service estimate.

This evidence does **not** predict 20 or 48 GiB hit rates. The observer supports fixed 256 MiB/1/4/8 GiB policy instances, and the retained summary has no larger-capacity replay. Its compact receipt does not contain the full chronological job trace needed for arbitrary offline LRU replay; the exact per-expert `nt` counters lose order. Reconstructing LRU hits from 9,816 unique pairs or a frequency histogram would be invalid. A new observer/replay on an actual ordered route or a bounded new request would be required. Even if more capacity raises hit rate, it has to increase uses-per-fill enough to cover prepare and memory-bandwidth cost, not merely reduce misses.

The separate `cpu-gu-reuse-small-v1.json` is an observed small model run in another source/build path with the observer OFF in one request and ON in a separate request. It confirms that the diagnostic was run in an actual serving shape and that a complete request can emit bounded accounting; it is not a controlled cache-hit performance comparison or an expanded-cache fixture. The v2 CPU mock validates observer policy mechanics (including isolated nt1 behavior and accounting) but is synthetic. Neither means a CPU cache was allocated. `cpu-predecode-probe-v1` is the actual representation/dot correctness and timing fixture: it exercises block reconstruction, raw-dot and GU/SwiGLU comparisons, edge activations, and 1/16/64 expert timing, with cold first-touch separated from overwrite refill. Its timings are single-CPU fixture results, not model-level cache timing.

## Memory shapes: FP16, lossless byte and true Q8

Model dimensions are H=2560, FF=640, and each GU has gate and up matrices, so one expert contains `2*640*2560=3,276,800` weights (`include/strata/kernels/cpu/expert.hpp:34-36`; R595). For comparison:

| Representation | Payload per GU expert before metadata/alignment | Relative to one byte/value | Numeric contract |
|---|---:|---:|---|
| FP16 expanded values | 6,553,600 B = 6.25 MiB | 2.00× | Rounding/underflow may alter IQ-dequantized FP32 values and dot; quality/parity needed. |
| Q8 signed values | 3,276,800 B = 3.125 MiB, plus block scales | 1.00× | If requantized from decoded weights, values and scales change; approximate. |
| R595/R603 lossless expanded codes | 3,404,800 B (IQ3_XXS/IQ2_S) or 3,353,600 B (IQ3_S) | 1.04× / 1.02× | Signed codebook bytes plus original D/subscales; exact code/metadata reconstruction, subject to the same dot arithmetic. |

For the local lossless fixture, each block is `[original D:2][signed integer codebook bytes:256][raw subscales:8 or 4]` (R598 README and `cpu-predecode-probe-v1/probe.cpp:36-76`). This is slightly larger than simple Q8 because it preserves the original per-half/scale structure. R595's earlier 3.125 MiB signed-byte figure omitted this metadata; R598/R603's later fixture size is the correct planning payload. A true Q8 weight cache can be smaller only by reducing/packing scales or using its own quantization block scheme, not by calling the lossless bytes “Q8”.

A 20 GiB payload-only budget holds about 6,300–6,420 GU entries; 48 GiB holds about 15,100–15,400, depending on format. Metadata, allocator/page overhead, temporary conversion buffers and reserved headroom reduce those counts. For comparison, 48×512=24,576 possible layer/expert GU identities and the one retained request touched 9,816 distinct pairs, but those counts alone do not tell how many entries are useful in a recency cache or fit the actual mixed-format bytes.

Do not claim `120 GB model + 50 GB packed files + 20–48 GiB cache` either fits or fails by addition. The model's mmap-backed experts can share physical file-cache pages with the packed source; process RSS includes anonymous, shared and file-backed pages; MemAvailable, cgroup limits, page cache, model/session/KV owners, resident complement, other processes and allocator reserve all matter. R595 reports ~54.2 GB peak session RSS and public IQ3_S expert RAM around 54.8 GB, but the receipts did not provide simultaneous MemAvailable and anonymous-vs-file RSS at the candidate admission boundary. Preserve an explicit live 8 GiB available-RAM floor, then cap cache by a live query after all model/session owners: `budget=min(requested, MemAvailable - 8 GiB - other planned allocations - metadata)`. Reject if nonpositive; never infer free RAM from model file size, RSS alone or “128 GiB installed”. A 20–48 GiB cache is a conditional envelope, not a demonstrated fit.

## Q8 requantization versus lossless code preservation

**True Q8 requantization** would first recover each IQ weight value `D × subscale × signed_grid`, choose a new block scale, round/clamp to signed 8-bit, and store that integer plus new scale. It potentially converts expensive IQ grid/sign extraction into a direct byte dot. Compared with current IQ-weight × Q8_K activation, both operands are signed-byte families; AVX2 still needs signed-weight sign handling or a mathematically equivalent dot. An implementation must define accumulation scale combination and avoid signed `-128` traps and `maddubs` pairwise saturation changes. This is a model arithmetic change: quantization error is introduced once in weights, potentially per decoded layer/expert, and recurrent activation/logit effects can accumulate. No local Q8 weight-requant quality or throughput measurement was found. Required gate: per-format weight reconstruction error distribution and worst cases; GU raw dot/GU+SwiGLU error on actual activations; per-layer residual/logit changes; prompt and generation perplexity/logit divergence/top-k flips; and held-out code/instruction/long-context task noninferiority. Exact token equality need not be required, but project must set quality thresholds against baseline run variance. A Q8 kernel microbenchmark alone cannot establish “almost no capability loss”.

**Lossless signed-byte code expansion** uses the current IQ decoded integer magnitude/sign and stores the original block D/subscale bytes. The current Q8_K activation quantizer and per-block float scaling can remain unchanged. Its numeric goal is exact integer code reconstruction and matched dot arithmetic; any changed SIMD order must still be separately checked. It avoids weight re-quantization error but not the increased memory traffic, cold fill or cache working-set cost. The local fixture's byte inverse demonstrates the intended encoding and tests fields; it does not qualify a persistent model cache or all concurrent worker/lifecycle cases.

**Original IQ integers plus relocated scale/sign data** is a useful lower-byte candidate distinct from either expanded representation. Keep original grid indices/code bits (or a more SIMD-friendly compact packing) and move only the repeated scale/sign metadata into aligned per-row/per-group arrays. This may remove some scalar unpack and improve vector loads while staying close to packed payload size; it is not proven faster. It still needs format-specific layout, no weight quantization, raw-dot equivalence, cache-line/DRAM accounting, and nt2–4 comparison against existing packed in-call decode reuse. The per-call decoder already reuses its decoded vectors across nt activations, so for multi-token jobs a second representation must beat that optimized path. R598 suggests testing a narrow table/bit-sliced or scale-rearranged path if actual codebook/sign decode is material; no present receipt says that CPU lookup instructions dominate system wall time.

## Bandwidth and amortization: a falsifiable screen

Logical payload estimates for a full GU expert from fixed dimensions and current block sizes:

| Format | Packed GU read payload | Lossless expanded read payload | Extra logical bytes per full GU call | Expanded/packed |
|---|---:|---:|---:|---:|
| IQ3_XXS (18) | 1,254,400 B | 3,404,800 B | 2,150,400 B | 2.714× |
| IQ2_S (22) | 1,049,600 B | 3,404,800 B | 2,355,200 B | 3.244× |
| IQ3_S (21) | 1,408,000 B | 3,353,600 B | 1,945,600 B | 2.382× |

These are logical weight operand extents (`1280 GU rows × 10 QK_K=256 blocks × block bytes`), not measured DRAM bytes. Actual residency/cache lines and row subset/nt reuse affect traffic. Yet cache-hit penalty needs a high bar on a streaming CPU: at the R603 measured saved service of 91–110 us (type18), the added expanded bytes require roughly 19.5–23.6 GB/s *incremental effective bandwidth* to pay for themselves; type22 at 53–76 us requires 31–44 GB/s; type21 at 133–169 us requires 11.5–14.6 GB/s. Formula is `extra logical bytes / saved CPU service`. These thresholds are not predicted bandwidth or speed; they are a direct falsification test against the local measured savings.

R579's separate host read control was 36.87 GB/s, not model-attained DRAM bandwidth. R595/AVX2 comments report about 5 GB/s per core for its codebook-lookup-bound route on a different Zen 3 5700X3D and ~25 GB/s host stream under that measurement. These numbers are neither interchangeable nor proof for a 5600X model workload. If the actual selected cache hit reads full expanded GU from RAM, the measured per-hit service saving must beat the additional traffic at the observed concurrent memory bandwidth. Under page pressure, the additional 1.02–3.24× logical working set may drive more DRAM and page faults; a warm 64-entry synthetic cohort is not enough.

At 8 GiB actual-order replay, cumulative fill payload is 70.61 GB for 45,433 nt1 jobs and net overwrite service is negative. The model's CPU job mix makes the codebook benefit plausible, but the measured fill/write and extra read costs presently refute synchronous request-cold adoption. A larger resident cache could reduce refills only if its exact ordered trace shows higher reuse per admitted fill; to beat measured refill costs, each re-fill lifetime should exceed format-specific 3–7 uses, and to pay a first-touch cold fill it needs 13–31 uses. Because current 8 GiB entry lifetimes averaged only ~2.16 uses, an enlarged-capacity replay must show a pronounced lifetime gain and matched CPU wall improvement. Do not multiply the 9,816 distinct pairs by token counts to invent hit rates.

## Minimal next experiment (single candidate) and stop rules

If this branch is continued, one bounded candidate is: **lossless signed-byte representation, nt1-only, 20 GiB hard maximum, persistent across two identical model requests, with live admission and packed fallback**. Keep nt2–4 on the current packed multi-token route; do not quantize to Q8 or widen SIMD arithmetic in the same trial. Restrict source coverage to the existing supported IQ GU types 18/21/22. Before allocation, measure MemAvailable/cgroup headroom, anonymous/file/peak RSS, and all long-lived model/KV/session/cache owners; admit 20 GiB only if 20 GiB plus an 8 GiB available-RAM floor and metadata/temporary owners fit. Otherwise refuse and do not silently shrink into a misleading run. Preserve the packed source as truth and ensure CPU workers have completed the current batch before an entry can be rewritten/evicted.

Run the same prompt twice under the same binary/settings and pinned route inputs where possible. Capture request 1 cold fill, CPU jobs/hits/misses/refill distances and wall; retain the cache for request 2, capture its reuse, hits/fills/bytes and wall. Since actual token generation could alter later route sequence, compare per-request real route receipts rather than assuming identical IDs. The cache key must include source/model generation, layer, expert and type; worker jobs need an entry lease until pool parking; clear it on model/source replacement. Measure MemAvailable and RSS through both requests, plus CPU service, thread and wall time, file/anonymous RSS, major/minor faults, physical memory bandwidth if available, and output quality. This tests whether persistence amortizes cold fill; it does not authorize 20 GiB on current evidence.

Falsifiable go criterion: for every enabled type, actual per-entry lifetime must exceed the measured cold/refill break-even (18/22/21 respectively: cold 24/31/18 conservative calls, refill 5/7/4 calls from R603 report, or recompute a stricter threshold from individual same-run samples); request 2 must show a reproducible end-to-end decode-wall improvement beyond paired variation after accounting for request-1 cost if user-facing first-use matters; CPU service must fall without higher system memory pressure/faults erasing wall benefit; and numerical outputs, errors, generated work, cancellation/RESTORE and cache-owner lifecycle must satisfy the existing gates. Stop if the nt1 ordered 20 GiB replay fails thresholds, if fill work remains net negative after request 2, if only thread-time improves while wall does not, or if admission cannot retain 8 GiB live headroom. Do not jump to 48 GiB on a higher hit-rate hypothesis. For true Q8, require a separate quality threshold decision before even this runtime experiment.
