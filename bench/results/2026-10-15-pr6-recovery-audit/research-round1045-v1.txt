# Round 1045 — unitrace MemoryCopy labels and measurement boundary

## Scope and novelty

This analyzes Intel `pti-gpu` revision `6c0d6b0b80c6dbac4b5902d9d5ade1c75b9e9033`, pinned by `own-qsa-gemm-unitrace-direct-v7`. R875/R880 already established timing sums are not bandwidth or critical-path evidence; its QSA corrections are outside scope. This adds classifier edge cases and a payload/source join recipe. The package is unrun; prior sums do not establish a current bottleneck.

## Exact endpoint labels

At this revision `ze_collector.h` defines endpoint suffixes H, D, M, S as allocation-property buckets, then maps them into distinct names for `zeCommandListAppendMemoryCopy`, `...MemoryCopyRegion`, and `...MemoryCopyFromContext` ([enum and names, pinned source](https://github.com/intel/pti-gpu/blob/6c0d6b0b80c6dbac4b5902d9d5ade1c75b9e9033/tools/unitrace/src/levelzero/ze_collector.h#L272-L450)). In `GetMemoryTransferType`, `zeMemGetAllocProperties(context, ptr, ..., nullptr)` is called separately on source and destination. The mapping is `ZE_MEMORY_TYPE_HOST` or `HOST_IMPORTED` → H (0), `DEVICE` → D (1), `UNKNOWN` → M (2), and `SHARED` → S (3). When both query successfully the packed suffix index is `(src << 2) | dst`; if destination type remains unset, it returns the source bucket alone. The collector asserts query success, so a failed allocation-property query is not converted to M: the assertion can terminate the process. [Classifier and standard copy path](https://github.com/intel/pti-gpu/blob/6c0d6b0b80c6dbac4b5902d9d5ade1c75b9e9033/tools/unitrace/src/levelzero/ze_collector.h#L5013-L5138).

`H2D` means HOST/HOST_IMPORTED source and DEVICE destination queries, not “RAM bytes physically traversed PCIe”; `M2D` means UNKNOWN source and DEVICE destination. Level Zero says an allocation unrelated to the supplied context queries successfully as UNKNOWN, so a pointer from another context can yield M2D even if backed by device memory. Ordinary `malloc`/`mmap` is not proven HOST: accepted UNKNOWN can yield M2D, while a failed query triggers the collector assertion. Unregistered-pointer behavior is driver-specific. Host-imported allocations fold into H. See the [official `zeMemGetAllocProperties` contract](https://oneapi-src.github.io/level-zero-spec/level-zero/latest/core/api/apis/mem.html#zememgetallocproperties) and [external-map contract](https://oneapi-src.github.io/level-zero-spec/level-zero/latest/core/EXT_ExternalMemMap.html).

`S2D` is a Shared-to-Device query; on discrete GPUs H2D or S2D could mean RAM-to-device, but shared placement varies. M2D could likewise be RAM-to-device with UNKNOWN source. D2D could be peer transfer or local copy. Even H2D does not prove external PCIe traffic: host-accessible/unified placement, peer paths, staging/offload, migration, caches or driver behavior can change physical traffic. The classifier asks allocation type, not physical residency/route; no label counts wire bytes.

`MemoryCopyFromContext` has a specific classifier limitation: `OnExitCommandListAppendMemoryCopyFromContext` passes the provided source context and pointer but passes `nullptr` as destination context to `AppendMemoryCommandContext`. The classifier therefore only obtains a source type and returns that type as the suffix index; the generated names use the `...FromContext(H2H/D2H/M2H/S2H)` family. Those suffixes do not classify the actual destination pointer/type and are not full endpoint pairs. The command list's context is found separately for command recording, but is not used as destination allocation-query context in this path. [Callback and context append implementation](https://github.com/intel/pti-gpu/blob/6c0d6b0b80c6dbac4b5902d9d5ade1c75b9e9033/tools/unitrace/src/levelzero/ze_collector.h#L3920-L3940) [callback](https://github.com/intel/pti-gpu/blob/6c0d6b0b80c6dbac4b5902d9d5ade1c75b9e9033/tools/unitrace/src/levelzero/ze_collector.h#L5260-L5290).

There is a second exact source caveat for `MemoryCopyRegion`: its exit callback initializes `bytes_transferred=0` and only multiplies that value by `region->depth`, so it remains zero. Width and height are not used. Its name retains the H/D/M/S endpoint classification, but the stored displayed size is not region payload. Do not use that path's `[...]` size as bytes. [Region callback](https://github.com/intel/pti-gpu/blob/6c0d6b0b80c6dbac4b5902d9d5ade1c75b9e9033/tools/unitrace/src/levelzero/ze_collector.h#L5230-L5255).

## What the aggregate measures

`--device-timing` collects one command's `execute_time = kernel_end - kernel_start`, plus call count, min and max; its table columns are Calls, Time, percent, average, min and max. This is the device timestamp-derived start/end service interval, converted to host nanoseconds. It excludes time before device start: queue append and submit-to-start delays are separate fields in the submission table (`append_time = submit - append`, `submit_time = start - submit`). It is not end-to-end dependency latency; upstream event waits / queue delay before start do not enter this command's execute duration. A started command's reported interval can still include device-side service behavior internal to that interval, so it should not be paraphrased as pure link serialization time. [Timing aggregation and tables](https://github.com/intel/pti-gpu/blob/6c0d6b0b80c6dbac4b5902d9d5ade1c75b9e9033/tools/unitrace/src/levelzero/ze_collector.h#L1000-L1025) [command completion timestamps](https://github.com/intel/pti-gpu/blob/6c0d6b0b80c6dbac4b5902d9d5ade1c75b9e9033/tools/unitrace/src/levelzero/ze_collector.h#L2768-L2805) [table columns](https://github.com/intel/pti-gpu/blob/6c0d6b0b80c6dbac4b5902d9d5ade1c75b9e9033/tools/unitrace/src/levelzero/ze_collector.h#L1478-L1580).

The aggregate does **not** report total payload bytes or bytes/sec. The command key includes `mem_size`, and verbose command-name rendering appends the size in brackets for positive-size memory commands; separate sizes therefore appear as separate rows. But the timing table has no byte-sum column, and multiplying row size by Calls is only a logical requested-size estimate if each call was captured and the size field is correct. Standard MemoryCopy receives the API's `*psize`; MemoryCopyRegion has the zero-size bug above. Even standard `psize` is requested command payload, not verified physical PCIe bytes. [size in command name](https://github.com/intel/pti-gpu/blob/6c0d6b0b80c6dbac4b5902d9d5ade1c75b9e9033/tools/unitrace/src/levelzero/ze_collector.h#L1160-L1190) [standard callback](https://github.com/intel/pti-gpu/blob/6c0d6b0b80c6dbac4b5902d9d5ade1c75b9e9033/tools/unitrace/src/levelzero/ze_collector.h#L5110-L5135).

## Bounded attribution and evidence needed

For bounded attribution: inventory every copy-producing Level Zero/runtime callsite (not only expert-weight uploads), recording source function/operation tag, logical object, requested bytes, pointers, allocation owner/context and device. Correlate each append with its command instance/timeline event and allocation queries; keep per-instance requested size, not aggregate-derived size. Tag higher-level wrappers for operations hidden inside libraries. Join to dependency/timeline evidence, sum only the selected logical operation, and separate overlap from critical-path delay. H2D/M2D can also be scratch, metadata, activation/state, initialization or library traffic.

A PCIe bottleneck claim additionally needs the device/route, evidence selected copies constrain request critical path, exact logical payload by operation/direction, and independent same-interval link bytes/utilization or a controlled payload-rate baseline. Show attained traffic near measured route capacity and material request-time impact. Topology is only capacity context; device copy service is not PCIe utilization. Without link evidence and dependency attribution, conclude only that copy commands/service intervals were observed.
