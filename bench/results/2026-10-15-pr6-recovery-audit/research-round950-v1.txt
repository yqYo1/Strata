Classification: knowledge collection. Date: 2026-10-17 JST. ## Portable typed-storage contract

The current declaration is `template<int Count> struct alignas(4) MatrixTile { BFloat values[Count]; };`. The kernel allocates one object of each tile type through `local_accessor<MatrixTile<...>,1>`, indexes its actual `values` array, then uses `address_space_cast<local_space, decorated::no>` before matrix loads. This keeps the storage element type BF16 from producer through consumer. It does not manufacture BFloat objects by aliasing uint32 storage, and the cast describes the local address space; it is not a lifetime or alignment fix by itself.

Core SYCL 2020 revision 12 defines local_accessor storage as a per-work-group array of DataT elements, with subscript returning a reference to an element. For implicit-lifetime DataT, it says that the accessor implicitly creates those objects with indeterminate values. The outer `MatrixTile` is written as an aggregate with an array member and no custom constructor/destructor. C++20's implicit-lifetime class rules include aggregates; the pinned WG21 N4917 draft records this class of type. Consequently a local_accessor of this aggregate is a typed-object design, subject to the device supporting the element type. The indeterminate initial values are safe only because every matrix operand element is written before its first matrix load: Q is populated for all heads/dimensions; the transposed K tile and later V tile cover the whole K/V array; and each probability row is written before the PV load. The work-group barriers between producers, consumers and tile reuse remain part of that proof.

The alignment argument is independent of element size. `alignas(4)` requires each complete MatrixTile object to start at an address suitable for at least 4-byte alignment. To pass that guarantee to `.values`, its member offset must be 0 mod 4. The wrapper has one ordinary first member, and the Q specialization also asserts that wrapper size equals the member-array byte size. Still, current assertions do not explicitly check standard-layout status and member offset for each of the Q, KV and probability specializations. A compact source-visible strengthening is to assert `is_standard_layout`, `offsetof(MatrixTile<N>, values) % 4 == 0`, `alignof(MatrixTile<N>) >= 4`, and the expected `sizeof` for all three instantiated N values. This makes the pointer-base derivation explicit instead of leaving it implicit in the type shape and one specialization's size check. `sizeof(BFloat)==2` establishes a two-byte element step; it does not imply 4-byte alignment of an allocation or a pointer.

## Xe2 matrix contract and current offsets

The pinned Intel joint_matrix extension specification at commit `17c6a87c9a5dcd3a85187ded445a695bdf1faf1a` lists BMG G21 and G31, and specifies for these Intel GPU architectures: matrix load/store base pointers must be 4-byte aligned; `stride * sizeof(T)` must be a multiple of 8 and no more than 2^24 bytes; for the 16-bit row-index overload, row_index must be a multiple of 2. The current calls use the pointer-plus-stride overload, not row_index. The same specification lists BF16 A/B to FP32 accumulator including 8x16x16; Strata queries the device for its supported combination before dispatch. This is an Intel experimental extension contract, not a portable guarantee of core SYCL, and the specification warns that extension interfaces can change.

Assuming the BF16 element size of 2 bytes, current call offsets are multiples of 16 elements (32 bytes) and current row strides are 32 or 256 elements (64 or 512 bytes). Q loads use `qtile + head*256 + d`, with d stepped by 16 and head row width 256. K loads use `kv + d*32 + cell`, with d stepped by 16 and cell 0 or 16. Probability loads use `probability + head*32 + c`, with c 0 or 16. V loads use `kv + c*256 + dim_base + j*16`, where c is 0 or 16 and dim_base/j offsets are multiples of 16. Thus each computed pointer preserves the aligned base if the tile member base is aligned; strides are far below the byte maximum. This arithmetic is a source-level proof conditional on the typed-object base, not a claim derived from sizeof alone.

## Safe staging alternatives

1. **Separate aligned real-array local accessors (current).** Each operand gets its own 4-byte-aligned MatrixTile object and one flat, genuine BFloat array. This has the clearest pointer and bounds story: each matrix operand is wholly inside one array object; no subarray-crossing pointer arithmetic or type punning is needed. It is core-SYCL local_accessor storage. The cost is three typed local allocations/accessor arguments, with backend allocation packing and rounding left to the compiler/runtime.

2. **One aligned operand bundle in one local_accessor (portable typed alternative).** Define one `alignas(4)` aggregate containing three real arrays, `q[16*Dim]`, `kv[Cells*Dim]`, and `p[16*Cells]`, and allocate that aggregate as one local_accessor element. Keep all loads pointed into the individual member arrays. Assert standard-layout, each member offset modulo 4, exact offsets/size, and that all field extents remain within the object. Here the Q extent is 8192 bytes and KV extent 16384 bytes, so the next member offset remains 4-aligned; the probability extent is 1024 bytes. This preserves typed BFloat object arrays and total operand payload, while changing the local accessor count and compiler-visible aggregate layout. It is source-safe only with the explicit offset assertions; it has no established Xe2 codegen or speed advantage.

A third typed route, when intentionally tied to DPC++, is the pinned `sycl::ext::oneapi::group_local_memory_for_overwrite<MatrixTile<...>>` extension. Its specification returns a local-space multi_ptr to a constructed object, requires Group=sycl::group and a trivially destructible T, and says the allocation lasts through the work-group. It therefore avoids raw-byte reinterpretation but is not portable core SYCL; all work-items in the group must call it consistently, and the same explicit barriers are still needed. The current `is_trivially_copyable` assertion is not as readable as an explicit `is_trivially_destructible` assertion for this extension constraint. It is a different allocator/API route, not proof of different alignment or resource behavior.

## Compiler, resource and evidence limits

The Intel extension notes that users may select a slower joint_matrix load/store implementation with `IGC_JointMatrixLoadStoreOpt=1` when its listed restrictions are not satisfied. That note is compiler/backend evidence that load/store lowering has architecture-sensitive constraints; it does not license misaligned pointers, show that the fallback is active by default, or predict this kernel's lowering. The matrix extension is experimental, and documented shape support/runtime queries alone do not prove successful BMG G21 execution. Local memory allocations all count toward work-group local-memory usage: bundling typed arrays does not reduce their payload. The current source's 28,160-byte logical total and +4,096 admission margin are source accounting, not measured allocation rounding, occupancy or an SLM/codegen result.

Keep three evidence levels separate:

- **Source guarantee:** declared alignment, verified field offset and actual object lifetime/type, plus offsets/strides that satisfy the pinned Intel rule. Static assertions can make this review repeatable.
- **Device-codegen claim:** the exact DPC++/IGC build lowers these local-space pointers into legal aligned Xe2 matrix loads rather than a different path. Verify the emitted device IR/backend representation and compiler diagnostics for the exact target; source syntax and a generic successful compile do not establish this.
- **Empirical runtime proof:** the exact built binary runs on the target BMG G21 device/runtime and passes the existing BF16 correctness, fault and context-boundary gates. A separate device-side address check for each matrix base, if supported by that compiler/address-space model, can validate the observed addresses; completion alone does not show which lowering ran. R950 performed no such check; Main owns native builds and tests.

The existing matrix math and rounding contract stays BF16 for Q/K/V/probability, with its existing FP32 accumulators, score/reduction/online state and barriers. This report makes no numerical-format or performance adoption decision.
