# Native16 GPU route-map consumer contract source audit

分類: decision support（source contract only）  
調査基準: personal Niko1221/Strata source worktree `verify-moe-window`、依頼指定の immutable commit `af99f294`。ソースの編集、Git、build、test、GPU/profile/process作業は行っていない。  
レポート予算: 18,000 bytes。  
結論の範囲: GPU上で安定route mapを作る案について、現在のcustom native16 GEMM adapterが消費できる契約、または変更が必要な契約を比較する。性能・採用の判断ではない。

## 要約

現状のMoE window経路はGPUでrouter logitsとtop-k IDsを計算するが、その後IDをhostへ読み戻し、hostで全routeを検査して安定slot map・source row配列・expert job列を作る。`run_moe_window` はその配列を同一queueへ全量uploadし、host側job loopからexpertごとのdequant/GEMM/gather等を順にsubmitする。従って、既存経路の契約は「checked readback後に確定したhost job数/各jobのexpert・row範囲・M寸法をhost launch制御が保持する」であり、route mapそのものやdevice descriptorをnative16 adapterへ渡す契約ではない。

`STRATA_SYCL_PREFILL_NATIVE16_BACKEND=vllm` で選ばれる実コードもGEMM専用である。`Problem` は `t,n,k,ldy,beta` とX/W/Yポインタをhostから受け取り、`beta0()` はひとつのGEMMをenqueueしてeventを返す。`gemm16.cpp` のwrapperは実際にはそのeventを `finish()` してから戻る。route・expert数・jobs・複数dispatchのdevice descriptorを受け取るAPIはない。よって現在のAPIに適合するのは正確なhost scalar/job dispatchであり、fixed upper-bound dispatchまたはdevice descriptorsは別consumer/kernel/queue contractを設計する場合の候補である。

GPU上のresidual windowは残差tensorのhost-tailを除き、attention後の2 chunkをbankへD2D storeしてからwindow FFNを行う。一方、router ID readback、host grouping、全route upload、host expert loopは残る。残差配置のall-GPU化だけではMoE制御のhost-tailを除かない。

## Source contract

### Producer, host visibility, and map invariant

1. `run_moe_window` is eligible only for a 2-chunk window (`rows > T`, `rows <= 2*T`, `T=8192`), active native16/layer-major mode, same compute/copy stream, and existing scratch/cache/residency. In this invocation each window has at most 16,384 rows.
2. For each 8,192-row part, normalization/projections/router are launched through the caller's `m.cs`. Router IDs are written to device `ids_slots`; weights remain in `weights`. Then `owner.ids` is resized to `rows*K`, device IDs are copied D2H, and `cudaStreamSynchronize(m.cs)` is checked. Only after this checked visibility boundary does `MoeWindowRoutes::build(rows, owner.ids.data(), owner.ids.size())` execute on CPU, inside the `host_group` profiling scope.
3. `build()` requires `rows` in `[1,16384]`, exact `rows*10` IDs, IDs in `[0,511]`, no duplicate expert within a token, and no expert count above `rows`. It creates counts/offsets, stable source-row order and slot map in original token/slot order, and expert-major jobs split at 8192 rows. Since each token routes exactly 10 times, route mass is exactly `rows*10`; `offsets.back()` checks this invariant. Each job's `global_row` addresses both a contiguous source segment and the matching down-output destination segment.
4. Job sequence is ascending expert, then ascending expert-row segment. It does not assume equal expert load: exact host `counts` define how many jobs exist. With 16,384 window rows and max job size 8,192, each expert can contribute zero, one or two jobs; total jobs and their exact M values vary with the router result.

### Uploads, queue, owners, checked completion

After build, two full `rows*K` int32 planes (`slot_map`, `source_rows`) are uploaded H2D to the compute stream. Both host vectors live in `owner.routes`, a `shared_ptr<const MoeWindowRoutes>`; the header deliberately exposes no mutation/move of a published plan. The upload comments and control flow retain this shared owner through final checked drain. Each upload is tagged as one profile upload of `rows,K,4`, but that is source metadata, not a performance measurement.

For each host job, caller uses `job.expert` to look up its resident weight slot (`host_res`), dequantizes that expert's GU and Down weights into shared device scratch, then submits gather, GU GEMM, SwiGLU and Down GEMM using that job's exact `job.rows`/`job.global_row`. The exact route source range and output range are checked against full `rows*K`/Down plane before enqueue. Expert scratch is reused only after preceding same-queue job consumers. After all jobs, one combine consumes the full Down plane, original device IDs and weights, shared expert outputs and shared gate; `write` produces the two residual-window pieces.

The code checks queue completion at three relevant boundaries: (a) after router D2H readback before host map construction; (b) after both final HC writes before marking the window complete; and (c) caller's outer layer-major checked lease, whose failure path retains the request context and owners rather than freeing them after an unchecked timeout. On success only, `routes.reset()` follows the checked final drain, so both DMA source buffers and device readers have retired before releasing vectors/reusing arenas. The vLLM adapter's `Native16BackendState` stores a `shared_ptr<Runtime>` before a borrowing `Gemm adapter`; member declaration order makes Runtime outlive the adapter. The adapter itself borrows the caller runtime/queue and registers no scratch/route data. `vllm_submit` binds it to the queue from `queue_for(stream)`, and rejects a different queue address after binding. It checks Intel AOT device/architecture, constructs one `Problem`, calls `beta0`, and caller invokes `finish(stream,event)`. Its queue/device USM checks and input/output span validation protect a GEMM call, not the map uploads or host job plan.

The active adapter exposes a `Problem` for exactly one compact X[T,K] by W[N,K] to Y[T,ldy] operation. Its guards require positive dimensions, beta=0, legal fp16/bf16, N divisible by 64, K divisible by 32, bounded surface extents, and validated device allocations. The launch has tile count derived from scalar T/N; T can be 1/3/17 logically (M itself need not be padded). It returns one SYCL event. The outer `gemm16.cpp` wrapper uses host scalar arguments to dispatch and finishes that event before returning; caller `run_moe_window` therefore has serialized checked GEMM completion through that wrapper, in addition to final stream drain. This is a GEMM consumer, not a route scheduler.

### Exact map and combine relationship

The device map is indexed in original token/slot order. `slot_map[i]` tells combine where routed output for original route `i` was scattered in expert-major storage; `source_rows[p]` identifies the original token row for that expert-major slot. Stable order preserves deterministic per-expert row ordering and exact mapping. Combine later walks original IDs/weights with the slot plane, so it sums expert outputs using the original route slots and weights. The route map is not interchangeable with just per-expert counts: counts alone cannot gather source tokens or restore each route's original slot at combine. Nor may expert job order be sorted independently of its source/destination row offsets.

## Dispatch alternatives and evidence

| Option | Fits current contract? | Required contract / unresolved work |
|---|---|---|
| Exact host counts and job scalars | **Yes; current implementation.** | Router IDs must first be host-visible and fully checked. Host plan carries the variable job list, exact expert/M/global offsets, and host residency slot selection. Caller submits jobs; current adapter receives only one job's scalar dimensions and tensor pointers. Route map arrays remain uploaded device inputs for gather/combine. Correctness depends on keeping immutable host upload owners through checked drain. This is the only verified current option. |
| Fixed upper-bound launches | **Not exposed by current adapter.** | A finite host loop can submit a preselected maximum number of slots, but each active slot still needs expert and row range. Padding empty jobs requires a no-op/guard convention and fixed target weight/address semantics. Current `beta0` gets one scalar `Problem`, performs no device-indirect M/expert lookup, and validates an exact job rectangle; caller's expert dequant scratch is shared/reused. A practical variant could submit up to max 1,024 job commands (512 experts × at most 2 row segments for 16,384 rows), but without per-slot descriptors or host-known job fields it cannot choose the correct expert weights or output span. It may avoid dynamic host branching only if descriptor-driven kernels are added; mere fixed host loop still requires host map/count data. Launch overhead/speed is unmeasured. |
| Device descriptors / device-side job loop | **Architectural option only; no present API.** | A descriptor needs at minimum active/expert ID, expert-row start/count, global source/Down offset, and either weight source/slot or an expert-major staging plan; device route map needs count/offset/slot/source data or a way to derive them. A host-launched kernel could read device descriptors and guard inactive jobs, but the current vLLM dense adapter accepts no descriptors and launches a single GEMM with host-fixed dimensions and weight pointer. Variable expert weights and reused dequant buffers require serialization or distinct per-job weight staging; combine must wait for all successful jobs and know every valid output. A GPU map producer does not by itself enable GPU command submission: standard host-side queue API still needs host launches unless using a deliberately supported command-graph/indirect mechanism, whose support and limits are not established by these four files. Device descriptors could remove ID D2H and host grouping only after such a redesigned consumer is implemented and checked. |

Fixed upper bound and descriptor options are alternatives, not proofs of a faster schedule. Device descriptor design could reduce route metadata transfers but add descriptor generation/storage, guards, device-side scan/prefix work, dependency edges, more weight residency or serial expert service. A no-readback design could return a bounded count to host, but retains a visibility/wait tail. Dynamic launch count is a control-flow fact, not proof of a latency bottleneck.

## Residual placement versus host tail

`prefill.cpp` selects `window_piece` only when consecutive residual spans are device spans. It checks topology, stores each attention result into the request bank with D2D copy and a checked stream synchronize, then calls `run_moe_window` once both pieces are ready. The helper validates the bank and operates on 16-bit device storage. This keeps that residual window out of host RAM and gives FFN both pieces together.

It does **not** remove these host operations: copy all routed IDs D2H and synchronize; CPU `MoeWindowRoutes::build` and its validation/prefix/scatter; upload both complete route planes; iterate variable jobs on the host; select resident expert slots from `host_res`; perform per-job host-side submit/control and error/cancellation checks. Thus the window remains host-tail-dependent at MoE routing/scheduling even while residual input/output stays GPU-resident. Source profiling labels identify host grouping/submission scopes but do not attribute thread CPU computation separately from wait/polling, establish a CPU latency bottleneck, or establish any speed.

## Conditions for a follow-up implementation decision

This report is source-level design support only; no recommendation to adopt a route-map or launch redesign. A later candidate should be schedulable only when all applicable evidence is available:

1. Pin the actual configured build entrypoint, backend setting, binary/compiler/runtime/provider and exact source snapshot; recheck that the adapter selected is this custom implementation, not a generic library assumption.
2. Provide current profiler evidence with required events qualified, and a source-pinned per-window host compute, submission, queue-wait, transfer and device-service census. The indexed round997 evidence leaves a profile incomplete (508/532 events) and `hardware_busy=UNMEASURED`; no performance-based route scope is schedulable from that evidence.
3. For a device-map design, specify descriptor layout, producer/consumer queue ordering, exact ID/count/offset invariants, bounds, source/destination ranges, expert weight residency, map lifetime, checked asynchronous failure/drain, cancellation behavior, and the point at which owners may be released/reused.
4. Preserve exact route-slot and combine order, two-window alias/live-range rules, recurrent/session state, physical context correctness, and native16 numerical gates against the actual SGLang/vLLM execution path required by AGENTS.md. Demonstrate error-path owner retention and checked retirement; source comments or a GPU queue alone do not establish arithmetic placement or safety.
5. Only after those gates, run serialized whole dependency-path comparisons that include route producer, transfer/visibility, dispatch, expert weight service, combine, window writes and drain. Retain individual samples and failure status per `docs/ARTIFACT_RETENTION.md`; no isolated GEMM or launch-count result substitutes for whole-path latency.
