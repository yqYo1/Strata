# Low-precision bandwidth kernels beyond GEMM: implementation patterns and measurement

## Scope and relation to earlier precision work

This note adds instruction, memory-layout and resource evidence to the earlier R569/R764/R782/R783 work on low-precision boundaries and typed producers/consumers. It concentrates on normalization, pointwise gating and residual update kernels, where each output uses few arithmetic operations per input byte. It does not recommend adopting any implementation or claim a Strata speedup. The two implementations below are external design references: Intel's vLLM XPU kernels at release v0.1.15, commit `1c7cbeee1cd0c1481d48f5031f679a47f3f0ef45` (repository Apache-2.0), and AMD ROCm AITER v0.1.25, commit `c53e9b3f4285c36ea785e614ce5cf8b04c78b3bd` (the RMSNorm file declares MIT). No source is copied here.

## What the implementations show

**Intel/SYCL RMSNorm plus residual.** The vLLM XPU layernorm implementation chooses a vector width of eight for 16-bit values when its pointer alignment, hidden width and row strides satisfy the vector path's constraints; it drops to a scalar path when they do not. That is a useful concrete lesson: the vector path is a shape-and-layout specialization, not a promise that every tensor with a 16-bit dtype is vectorized. It also packs rows for small hidden widths to expose enough parallel work. Its fused residual path adds into `scalar_t`, stores that residual, reduces squares in FP32, then reads the residual again for normalization and output. Thus storage precision and reduction precision are separate choices, and the add's intermediate rounding is part of the implementation's numerical behavior. The kernel uses a required subgroup size of 32 and Intel-specific work-item facilities; neither is a portable default for another SYCL implementation or device. See [the pinned layernorm source, vector path and fused residual code](https://github.com/vllm-project/vllm-xpu-kernels/blob/1c7cbeee1cd0c1481d48f5031f679a47f3f0ef45/csrc/layernorm.cpp#L2913-L2947) and [the reduction and second pass](https://github.com/vllm-project/vllm-xpu-kernels/blob/1c7cbeee1cd0c1481d48f5031f679a47f3f0ef45/csrc/layernorm.cpp#L3182-L3283). The repository's license at that revision is [Apache-2.0](https://github.com/vllm-project/vllm-xpu-kernels/blob/1c7cbeee1cd0c1481d48f5031f679a47f3f0ef45/LICENSE).

**Intel/SYCL gated activation.** The same revision implements a vectorized `act_and_mul` path: each work-item loads packed gate and up values, applies the activation and product, and stores a packed result. Its launcher chooses up to 16 bytes per work-item (eight BF16/FP16 values), reduces the width until the hidden dimension divides evenly, caps work-group size, and loops for larger rows. This illustrates how to fuse a pointwise activation with its following multiply without an intermediate tensor or an extra launch. The source comments report higher memory-bandwidth utilization, but omit a reproducible device, workload, baseline and measurement method; treat those numbers as author comments, not transferable performance evidence. Check emitted device code for vector loads/stores and the intended math; source-level vector types alone do not prove the compiler generated them. See [the kernel](https://github.com/vllm-project/vllm-xpu-kernels/blob/1c7cbeee1cd0c1481d48f5031f679a47f3f0ef45/csrc/activation.cpp#L2130-L2189) and [its dispatch/vector-width logic](https://github.com/vllm-project/vllm-xpu-kernels/blob/1c7cbeee1cd0c1481d48f5031f679a47f3f0ef45/csrc/activation.cpp#L2725-L2759).

**AMD ROCm/Triton RMSNorm with residual.** AITER's blocked kernel processes row tiles in a loop, marks vector alignment with `tl.multiple_of`, masks incomplete tiles, adds the residual, stores it in the input dtype, casts the stored value to FP32 for the sum of squares, and later reloads the residual for normalization. This is a concrete alternative to Intel's explicit C++ vector path: block/tile and mask expressions tell the compiler about alignment and bounds, while compiler output still needs inspection. The row reduction creates a data dependency: normalization cannot finish until the row statistic exists. A fused kernel can remove a launch, but it may still write and reload residual values; a version that keeps the entire row live instead pays in register footprint. The source is at the pinned [AITER RMSNorm implementation](https://github.com/ROCm/aiter/blob/c53e9b3f4285c36ea785e614ce5cf8b04c78b3bd/aiter/ops/triton/_triton_kernels/normalization/rmsnorm.py#L2891-L3067). Its file header identifies MIT licensing.

Together these examples warn against treating "FP32 accumulation" as one uniform rule. A reduction may need FP32 while tensor storage stays 16-bit; however, whether the reduction sees a rounded 16-bit residual or the pre-store FP32 sum changes results. Pick and document the intended boundary, then compare against the retained FP32 reference. For sigmoid/SiLU gating, likewise test whether activation math is computed in FP32 and where the result is narrowed. The source examples show alternatives, not evidence that their rounding matches a particular model's tolerance.

## Transferable layout and resource rules

Contiguous 16-bit data makes pairs of values occupy the same bytes as one FP32 value, but vectorization helps only when addresses, strides and dimension tails line up with the compiler's legal access widths. Misaligned row starts can split transactions even when the base allocation is aligned. Use a fast aligned/divisible specialization plus a correct masked or scalar tail path; exercise offsets, odd widths and nontrivial row strides. For each path, inspect disassembly for actual packed memory operations, conversion instructions, predicates and extra address arithmetic. Count memory sectors/transactions as well as load/store instructions: a wider instruction is not automatically fewer memory transactions if the addresses cross boundaries or lanes request scattered sectors.

Intel's 2024.2 GPU Optimization Guide explains the portability boundary especially clearly: standard SYCL relies on compiler vectorization across work-items, while ESIMD exposes explicit vectors and block load/store messages. Its examples show that vector widths can be legalized into several ISA instructions, and that larger vectors or block messages can reduce address/payload overhead but consume general-register-file capacity. ESIMD is Intel-specific, so its block-message advice is a target-specific option rather than a portable SYCL recipe. See [Optimizing Explicit SIMD Kernels](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2024-2/optimizing-explicit-simd-kernels.html). AMD's [CDNA2 register-pressure lab note](https://gpuopen.com/learn/amd-lab-notes/amd-lab-notes-register-pressure-readme/) describes the analogous tradeoff on that architecture: more live values can lower occupancy or spill to scratch. Hardware limits differ, but the reasoning transfers.

This tile-oriented approach has a compiler-design basis beyond LLM inference. Tillet, Kung and Cox's original Triton paper centers statically shaped tiles and tile-level optimization, a useful way to expose regular blocked work without hard-coding every thread mapping. It is a programming-model argument, not evidence that a given tile size, vector width or memory path wins on a target device; generated code and counters still decide that. See [Triton: An Intermediate Language and Compiler for Tiled Neural Network Computations](https://www.eecs.harvard.edu/~htk/publication/2019-mapl-tillet-kung-cox.pdf).

For a normalization row, increasing values held per work-item or keeping a full row live may cut reloads and expose more vector work. It also raises registers per thread, may reduce concurrent resident work-groups, and can trigger spills. Conversely, a small tile may increase loop/control work and reloads. Sweep tile size, work-group size, subgroup choice where supported, and vector width as a coupled design; do not select width eight solely because it is 16 bytes for half values. For pointwise gate/up kernels, fusion is especially promising because there is no cross-element reduction: values can usually flow from packed loads through activation and multiply directly to the output. For RMSNorm plus residual, source-level byte accounting for two-byte values is roughly 4B of input/residual reads, 2B residual write, 2B residual reread and 2B normalized output write per element. A two-kernel add-then-normalize can have similar source-level traffic. Fusion may save launch and intermediate scheduling overhead without reducing bytes; cache behavior decides external-memory traffic. Keeping all values live may remove the reread at the cost of registers. Measure which mechanism changed.

## A focused measurement protocol

Use a fixed device, driver/runtime, compiler and source commit; record them with exact dtype, dimensions, strides, pointer alignment, work-group/subgroup, vector width, and kernel specialization. Compare scalar, widths 2/4/8 (and architecture-legal wider variants), fused versus split residual/RMSNorm, and fused versus split gate/multiply. Include aligned/divisible cases and awkward tails/offsets. Give each arm a fresh owned process or immutable explicit parameter; warm up before timing, use repeated samples with randomized arm order, and report median plus spread. Time both kernel-only work and the caller-visible sequence so launch savings are visible.

For Intel collect device-kernel time, EU/SIMD activity, register/spill evidence, cache/DRAM bytes or sectors, occupancy and synchronization; save compiler reports and device assembly for representative specializations. On AMD, record VGPR/SGPR, scratch, occupancy and ISA plus equivalent memory/timing counters. These counters explain whether time changed because of fewer transactions, better packing, occupancy, spills, math or launch count. Don't infer bandwidth from nominal bytes alone: report estimated source traffic and measured memory traffic separately. Numerical checks should cover maximum and relative output error, residual state, reduction statistics, tails and repeated-layer drift against FP32; test FP16 and BF16 independently. First establish the same rounding boundary for each compared arm. This method distinguishes a real vectorized bandwidth improvement from a scalar fallback, a cache effect, a launch-only win, or a precision change.
