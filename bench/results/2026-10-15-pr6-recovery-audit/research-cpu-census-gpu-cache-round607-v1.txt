# Round 607 — CPU expert census as an upper bound for added GPU cache slots

2026-10-15 JST. Read-only offline analysis of the retained CPU GU reuse census and reviewed cache/prefill proposals. Wrote only this report. No source edit, build, test, GPU/server operation, Git operation, or cleanup was performed. The census JSON is complete, inactive, passed, and has zero fresh faults. Its exact expert histogram is decoded and aggregated below; no benchmark was run.

## Finding

`cpu-gu-reuse-long-v1.json` records one 34,603-token prompt / 128-token generation at 262,144 context, 48 layers, top-10 routing, `--expert-cache 128 --expert-cache-per-layer --adapt-swaps 0`, with no prefill borrowing. Its complete route ledger reports 68,781 CPU GU jobs and 101,036 CPU token-expert rows out of 104,160 route entries. Thus 97.0008% of route entries in this request were CPU-owned. `expert_counts_base64` decodes to exactly 98,304 bytes arranged as `[layer][512 expert IDs][nt 1..4]`; byte sum is exactly 68,781 jobs and the `nt`-weighted sum is exactly 101,036 rows. It has 16,296 nonzero `(layer, expert, nt)` cells and 9,816 distinct routed `(layer, expert)` pairs.

This histogram gives an observed CPU-owner opportunity set for this one request. It does not reveal IDs or recurrence for GPU-owned routes, other prompts, or other generated tokens. Ranking its CPU-owned expert pairs can therefore estimate how much of these observed CPU jobs/rows an added GPU cache might displace under a fixed route. It cannot establish the optimum over all experts, a future hit rate, time saved, GPU capacity admission, or model-level speedup. In particular the reported CPU rows are work counts, not elapsed-time savings.

The current 128-slot cache is a total of 128 slots, partitioned as 47 layers × 2 plus the last layer × 34. For the row-count upper bound, I ranked only the 9,816 observed CPU-owned pairs by their exact CPU rows and summed their observed job and row counts. Mixed layer formats mean the bytes for those IDs are different from a fixed average-slot estimate.

The table is an ideal static assignment ceiling on the observed CPU-owned route only: each added slot holds one distinct `(layer, expert)` pair chosen with hindsight from this request, and every recorded CPU event for that pair is assumed to execute on GPU after admission. It ignores cache setup, prefill loans, capacity pressure, pointer/graph work, concurrency and changed outputs. The “total slots” column means the existing 128 residents remain present; no slot is replaced. Bytes are raw full-expert blobs for the selected pairs, grouped by their layer's actual format. The seven per-expert source sizes in this model are 1,510,400 / 1,715,200 / 1,868,800 / 1,971,200 / 2,176,000 / 2,329,600 / 2,662,400 B; these are all 256-byte aligned. This payload sum is not a live allocation receipt or a guarantee that a requested GPU arena fits.

## Per-layer quotas versus global ranking

The preceding global ranking may spend slots wherever the highest CPU row counts occur. To show the effect of retaining a per-layer partition, I separately allocated each increment by the legacy quotient/remainder pattern: `q = floor(N/48)` additions to each layer and the remainder to the final layer. This appends to the current per-layer residents rather than recomputing a total-size partition that could shrink a layer. Within each layer, slots go to that layer's highest row-count CPU experts. This rule preserves all current slots, but its last-layer remainder is deliberately the legacy layout's skew, not a claim that the skew is desirable.

Global ranking gains only 2.15, 1.01 and 1.26 percentage points of observed CPU-row coverage at +128/+256/+512 slots over this per-layer schedule. Even this small gap depends on optimizing the chosen CPU rows; it does not establish that global placement is worth a more complex owner map. The balanced-layer proposal changes how a total capacity's remainder is partitioned (and its exact bytes), while the table above is an append-only quota model explicitly preserving the current 128 residents. They are different capacity plans and should not be conflated.

For the 128/256/512 additions above, the aggregate sizes happen to be near R594's rough 260/520/1,040 MiB ladder, but selected bytes vary with layer-format mix. R594's retained source-layout arithmetic gives the existing legacy 128 arena as 281,651,200 B (268.60 MiB), and its proposed balanced 128 layout as 260,044,800 B (248.00 MiB); neither value is a live allocation measurement. The older R594 admission arithmetic concerned total capacities, while this report's rows concern additions on top of the current 128 slots. In particular +512 means 640 total slots and lies outside R594's 512-total-slot screen. It is a route-coverage calculation only, not an admission recommendation.

## CPU cache and predecode are separate levers

This GPU-cache ceiling answers: if additional full experts are resident on GPU, how many observed CPU-owned routing jobs/rows might change owner? It does not model their GPU execution time, H2D cost, asynchronous refill or numerical effect. A GPU cache entry holds the expert payload used by the GPU path; it may reduce CPU work by routing those expert rows to GPU.

The CPU GU predecode proposal instead materializes a transformed representation in host RAM while the expert remains CPU-owned. It does not remove CPU jobs or rows and does not consume GPU expert-cache slots. R603 found the `nt=1`, 8-GiB observer policy at about 54% hit, yet request-cold fill/refill service outweighed the warm-kernel savings in this 128-output workload; that evidence does not support synchronous request-cold predecode adoption. The 54% CPU-cache hit statistic is not GPU-cache hit rate and cannot be used to infer the GPU slot table above.

## What a capacity experiment would still have to prove

The route histogram can select a candidate ordering for a later static capacity experiment, but changing capacity affects memory owners and pointers. Admission needs a fresh exact `open_sized` byte count and live free/total query after the model, KV/session, MTP, Verifier, graphs and runtime owners exist, with a declared reserve. R594's phase-specific margin and approximate ladder are not substitutes for startup or decode-boundary admission; retiring Prefill scratch after a request cannot enlarge an already-open cache. Preserve the existing 128 entries as the baseline invariant and reject any candidate whose plan shrinks a layer or cannot retain their exact `(layer, slot, expert)` residency.

If testing a close/reopen or resized cache, first drain every GPU queue, pending adaptive refill/copy, prefill loan and active graph reader. Preserve the exact source profile and slot mapping, refill and verify every payload, then refresh host/device residency maps and all Verifier hit pointers. Any captured T-specific graph that copied cache addresses must be retired and recaptured before decode; a pointer table update alone does not repair captured addresses. On uncertain drain, free, refill or recapture, fail before decode and retain uncertain owners rather than continuing with a partial cache. No adaptive policy should be mixed into the first capacity comparison; the census request used `--adapt-swaps 0`.

RESTORE and checkpoint state belongs to the session and host snapshots, not to a GPU expert slot. It must survive a cache plan unchanged, while every cache expert and graph pointer must be valid after restore and before any resumed decode. The physical 262,144 context and its host-backed KV fallback remain required; cache growth or Prefill retirement cannot shrink that correctness condition. Validate fresh prompt, repeated prompt, RESTORE hit/miss, full physical context, cancellation/failure boundaries and numerical/quality behavior independently. Finally measure individual CPU and GPU work plus clean same-work end-to-end wall samples. The CPU route ceiling alone supplies no speed claim.
