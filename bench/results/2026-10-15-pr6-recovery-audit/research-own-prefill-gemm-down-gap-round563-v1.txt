## Finding

The principal FP16 MoE route and its compact scratch behavior are already present in the current root path. The exact 1eb donor and current root both run the same per-active-expert sequence: native GU/Down dequantization into two rotating FP16 buffers, compact activation gather into row zero, FP16 GU GEMM, SwiGLU, then FP16 Down GEMM writing at that expert's global route-row offset. Both issue separate GU and Down GEMMs per expert. I found no missing donor batching or reduced-call Down implementation in these two routes.

A real, narrow implementation difference remains in how GEMM is described to oneMKL:

- Donor `sycl/src/prefill/gemm.dp.cpp:750-784` calls the DPCT BLAS API in column-major form: `trans, nontrans`, dimensions `(N,T,K)`, weights W first, activations X second, leading dimensions K/K/ldy.
- Current `src/prefill/sycl/gemm.cpp:18-29,96-100` calls oneMKL row-major form: `nontrans, trans`, dimensions `(T,N,K)`, X first, W second, leading dimensions K/K/ld. These describe the same row-major output bytes (Y=XW^T), including the same FP32 accumulation and FP32 output. For the current MoE call sites, `ld=N`; compact scratch changes row offset to zero but does not pad rows.
- The descriptor/orientation can select a different oneMKL implementation for some shapes, but source does not establish that it does. R524 already specifies an orientation A/B probe; it remains unmeasured. This is the clearest exact donor-to-root GEMM hypothesis, rather than proof that the donor GEMM is missing.

The native-format dequant path is already equivalent by source: donor `sycl/src/prefill/prefill.cpp:4777-4803` and current `src/prefill/prefill.cpp:2777-2808` call `iq_dequant_gu_f16` and `iq_dequant_f16` on the same format metadata and blob offsets; both rotate `q=j%DQ` with `DQ=2`. Both write Down into `Dm + o0*N`. The root applies stricter compact-request eligibility and explicit range checks, but these do not change the admitted computation. Both use per-expert `ne` shapes, with compact X/GU/Hh scratch at row zero; both preserve global Down accumulation order through the route CSR offset.

Queue behavior also does not show an obvious lost wait optimization. The donor DPCT GEMM submits asynchronously on its stream. Current `finish(stream,event)` is a no-op for the nonnull prefill stream; it waits only for a null stream (`include/strata/sycl/launch.hpp:47-63`). Current prefill requires the in-order queue and routes GEMM, dequant, gather, and SwiGLU through that queue. The returned oneMKL event is not used to introduce a host wait. Donor/current ownership and event bookkeeping differ elsewhere for safety: donor waits via `dpct::sync_barrier` on the used slot; current records a CUDA-compatible event only when `copy_events` is active. Do not remove current queue, slot, issuer, copy, or completion protections to mimic older bookkeeping.

## What the timing and counts establish

The committed diagnostic `bench/results/2026-10-14-primary-routed-fp16-census/long-phase-summary.json` covers a fresh 34,560-batched-token, nine-chunk compact FP16 run. It reports 90,297 active-expert calls for each of GU and Down and 16,588,800 rows each. The source-observed call distribution has median `ne=12`, p90 428, p99 3,245; 55.13% of calls have `ne<=16`, while these account for just 1.386% of rows. That is a strong exposure signal for small-shape launch/submission overhead, not an estimate of the percent of Down time spent on small calls.

The same record reports 61.535 s in the Down phase marker interval, 32.529 s in dequant, 6.004 s in GU, 5.273 s in gather, and 75.519 s accumulated host staging time. These phase intervals are queue-marker buckets rather than exclusive device-kernel times. R521 (`research/research-down-stager-phase-attribution-round521-v1.txt:13-19`) explains that a host submission gap and previously queued copy can land in the currently open Down interval, while host staging overlaps the GPU timeline. Therefore the 61.5 s cannot be divided by 90,297 to claim per-GEMM service, nor can the 75.5 s be added to phase time. The one-request comparison reports 207.576 s diagnostic wall versus 201.618 s reference prefill (2.95% observed difference), but is not a variance study or formal stock throughput result.

The compact-MoE recovery report records formal stock benchmark medians 187.5 tok/s OFF and 194.2 tok/s ON for the same new binary, with three requests per process arm. It explicitly leaves quality, full-input/RESTORE qualification, adoption, and independent decode regression unresolved. The report also states prior same-client 343.8 tok/s and adjusted 449.7 tok/s were not recovered; those historical numbers have different binary/source and protocol boundaries. These observations make the old result relevant to preserve, but do not identify GEMM orientation, layer order, or any individual component as the cause of the gap.
