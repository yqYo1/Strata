# R807 — Decision support: adapting Intel vLLM Xe2 native 16-bit GEMM

## Decision question and evidence boundary

This review inspected `vllm-project/vllm-xpu-kernels` at requested revision `6b30c9b92cc525c32729df988b5f918e7c5661a5`, then compared its Xe2 grouped-GEMM path with Strata's `src/prefill/sycl/gemm16.cpp`. It seeks a small adaptation for direct 16-bit inputs, FP32 accumulation, and direct 16-bit output, including FP16 to BF16; it is source review only.

The closest source candidate is the low-level `xe_gemm` in `csrc/xpu/grouped_gemm/xe_2/gemm_xe2.hpp`, launched through `MoEGEMMLauncher` in `grouped_gemm_xe2_interface.hpp`. It is a genuine typed-input matrix path: `XE_DPAS_TT<8, float, ElementA>` feeds a float accumulator fragment, and the output tensor has an independent `ElementD` template parameter. The current public vLLM 16-bit dispatch does not expose mixed output: its wrapper selects same-type A/B/D and casts the D pointer as `ElementA`. Thus FP16-in/BF16-out is a plausible narrow instantiation seam in the kernel, but is not an existing public or verified vLLM contract.

## What the kernel actually does

The device code tiles A `[M,K]`, B `[N,K]`, and D, using CUTE identity coordinates and `local_tile`. SYCL-TLA block-2D copy/prefetch loads A/B into fragments; each K step uses workgroup barrier arrival, fragment copy/reorder, `cute::gemm`, and barrier wait before reuse. The float accumulator is reordered to D's store layout and written through block-2D copy. This is a direct 16-bit producer/consumer path, not an FP32 tensor plus cast kernel.

The launcher builds `XE_DPAS_TT<8,float,ElementA>` and a `TiledMMA`. The default policy is `256x256x32` with subgroup layout `8x4x1`; small-M includes `16x64x32`. It requests subgroup size 16 and Intel `grf_size<256>`. K and per-expert M tiles use ceil division; the 16-bit host checks require N%8 and contiguous A/B/D, with no K multiple check. Current N/K multiples of 128 meet those restrictions; ragged T still matters.

The grouped helper maps workgroups over padded N and expert-M tiles, reads device `rows_per_expert`, and uses an atomic counter plus one local integer/barrier to fetch more tiles. This handles ragged per-expert M. The Torch wrapper zeroes the counter and selects policy from average M. A dense single GEMM can use a direct M/N grid and avoid the expert walk, counter, and row-count buffer.

## Smallest viable standalone adaptation

Start with only the Xe2 low-level tile path. The Strata adapter takes the existing queue, resident `A[T,K]`, `W[N,K]`, output `Y[T,ld]`, dimensions, and input/output kinds. Instantiate same-type A/B, float accumulation, independent half/BF16 D; apply beta/bias before one output conversion. The core has `ElementD`, but the public wrapper aliases D to A, so mixed instantiation and rounding correctness are gates, not established support.

For dense GEMM, grid `ceil_div(T,tile_m) x ceil_div(N,tile_n)` and call the tile function directly. Omit the expert loop, atomic counter, FP8/4-bit paths, Torch tensors, and Python bindings. A is row-major `(T,K)`; view existing W bytes as row-major `(N,K)` without transposing; construct D with row stride `ld`. A small launcher/template shim is still needed because CUTE/SYCL-TLA provides the copy, MMA, reorder, prefetch, and policy machinery.

Only add grouped scheduling for a concrete routed consumer. Its device helper does not call Torch, but a plain wrapper must provide row counts and initialize/lifetime-manage the atomic counter on the same queue. For dense T=1..8192, the direct grid has the smaller contract; no dynamic-scheduler speed claim was measured.

Minimal headers to inventory are `sycl/sycl.hpp`, Intel `grf_size_properties.hpp`, `cute/tensor.hpp`, `cute/atom/mma_atom.hpp`, `cute/util/compat.hpp`, `cutlass/numeric_types.h`, and the Xe block-copy/MMA definitions they include. `gemm_xe2.hpp` also includes tensor-ref, event-manager, clock, and reference-GEMM headers not visibly used by `xe_gemm`; an extraction should trim after review. The policy header uses `XE_STORE_2D` but lacks SPDX; resolve its history before copying. The vLLM root license is Apache-2.0, while marked Xe2 files are BSD-3. Keep actual source notices and attribution; new adapter follows Strata's license. SYCL-TLA is also BSD-3 and header-only, so it is a material license/dependency boundary.

Pinned vLLM CMake enables `CUTLASS_ENABLE_SYCL`, `SYCL_INTEL_TARGET`, `intel_gpu_bmg_g21` when Xe3p is off, and C++20 Xe2 targets. The source targets Intel DPC++/SYCL and Xe2/BMG, not generic SYCL. Qualification must use only the approved official LLVM under `Xe.tools`; no build was run. Current Intel docs list Xe2/BMG and DPC++ 2025.3+ validation and describe `XE_DPAS_TT` as DPAS/inline-vISA, but are not pinned to this CMake dependency revision; exact header/compiler compatibility remains a compile gate.

## Bounded initial qualification outline (not run)

1. Freeze against both immutable commits; extract only the 16-bit core/policy, and record source hashes, notices, build flags, and binary identity.
2. One compile/correctness fixture: T `{1,15,16,17,160}`, then `8192`; workload N/K multiples of 128; FP16→FP16, BF16→BF16, FP16→BF16; FP32 accumulation plus one rounding, beta if required, `ld>N` canaries, input immutability, finite output, and queue completion.
3. Verify block-2D base/stride alignment before timing. Intel's design note gives 64-byte base and 16-byte stride requirements plus width restrictions. If W/D cannot meet them, use a safe copy/store or reject that tuple; this review did not inspect allocator alignment.
4. After correctness, compare same-binary/queue/input semantics with oneMKL and current code. Time conversion, packing, launch and sync; separate host submission/wait from device time and retain samples. GEMM correctness does not establish model quality.

The supplied R803 snapshot is the numeric motivation, not a finding from this source inspection: old custom GEMM medians were 2.252697 ms versus 0.200878 ms at T=160,N=1280,K=2560, 0.9202 ms versus 0.147919 ms at T=160,N=2560,K=640, and 42.263487 ms versus 1.399792 ms at T=8192,N=1280,K=2560, with similar direction for BF16 inputs. It identifies a large component-level difference for those tuples; it does not identify a vLLM layout winner or prove which part of Strata's kernel causes the slowdown. Whole-model BF16 quality and the reported long-input slowdown remain separate adoption gates.
