# R762 — mapped host-USM kernels versus explicit queue copies

2026-10-16 JST. Bounded, read-only research. This report is the only file written. No product source was changed; no build, test, GPU run, profiler, process inspection, Git operation, environment/service mutation, or cleanup was performed. I read the requested instructions, retention policy, research index, R751–R760 reports and the R757–R760 Main review. No XeStrata material was read or used.

## Finding

The choice is between two different ways to cross the same host/device boundary, not between “zero traffic” and “traffic.” With host USM, the device can access host-resident storage directly; with device USM and `queue::memcpy`, data is moved by an explicit command into or out of device-local buffers. Direct access avoids a copy command and extra device allocation, but it still transfers data remotely on a discrete GPU. A copy command adds submission/completion work, while allowing contiguous bulk movement into the local buffers used by later kernels. SYCL and Level Zero do not promise which method is faster or that a `memcpy` will use a particular DMA engine.

For the supplied route, the mapped `copy_i32` path writes route IDs to host USM for CPU grouping, then reads the CPU-produced `slot` and `src` maps from host USM back into device buffers. Across the actual 78,452-row, 48-layer, 10-chunk diagnostic, the three logical arrays total 451,883,520 bytes over 480 boundaries (about 430.8 MiB). This is a payload calculation, not PCIe traffic measured by a counter. The 0.16536 CPU seconds for grouping plus map-copy submission exclude the earlier queue wait and later map consumption/completion; they do not bound the complete boundary cost. The same run recorded 167.9548 CPU seconds in explicit waits and 37.3482 seconds unclassified, so the payload alone does not establish a CPU or transfer bottleneck.

## Contracts and hardware evidence

**Portable SYCL contract.** Host USM is allocated in host memory, remains there rather than migrating, and may be remotely read or written by a device. Host-USM support is optional, allocations are limited by pinnable host memory on many systems, and host/device access must be synchronized. `queue::memcpy` enqueues a command and returns its event; USM pointers do not create implicit dependencies, so the application must preserve the required queue/event order and wait before host reads or buffer reuse. The spec does not define cache-line or PCIe transaction sizes, cache policy, DMA-engine selection, or a relative performance rule. See SYCL 2020 rev. 12 §§3.8.1, 4.8.3.3, and 4.6.5.3.

**Intel and Level Zero specifics.** Intel's GPU guide describes `malloc_host` memory as remaining on the host and being accessed remotely via PCIe/fabric, and describes device allocations as local memory with explicit copies for host transfer. This supports the placement distinction for the Intel GPU context, but it is not a B570 link-counter measurement. The current DPC++ environment reference says `UR_L0_V2_FORCE_DISABLE_COPY_OFFLOAD=1` keeps copy operations on the engine behind their original queue instead of offloading eligible copies to dedicated copy engines; it marks this as a V2 development/debug variable whose semantics can change. Preserve the existing setting in every arm. A Level Zero memory-copy command accepts host, device, or shared memory subject to device/context accessibility; command-list start order does not itself guarantee completion order. Thus call it an explicit queue copy in results, and call it DMA only if the run's actual path establishes that.

**Coalescing and batching are hypotheses to measure.** A linear `int32` index mapping can give adjacent GPU lanes adjacent addresses, which may let the hardware combine accesses. Actual `copy_i32` lane mapping, alignment, transaction widths, cache treatment, and remote-memory bandwidth for Xe2 are not established here. CUDA's discrete-GPU guidance says mapped pinned access can be useful for one-time, coalesced accesses; its CUDA-specific claim that such memory is not GPU-cached must not be transferred to Xe2. An NVIDIA performance blog measured direct pinned-system-memory reads on A100/V100 and found strong dependence on grid-stride versus random access and 128-byte alignment. Its results show why access pattern matters, not what this Arc will do. Intel's general offload guide recommends reducing transfer count and batching small transfers, but it does not imply that commands can be merged across this CPU dependency: each boundary needs its IDs on the host before that boundary's maps can be formed.

## Novelty relative to R757–R760

R757 already separates ordinary `new[]` from host-USM allocation policy, allocation/setup cost, call time and wait time; R760 records the mapped route and corrected logical-byte total. This report narrows the next comparison to mapped-kernel loads/stores versus explicit bulk copy commands over the same host-USM staging and device-local endpoints. It adds the contract limits around visibility, coalescing, transaction assumptions and the current copy-offload safety setting. It does not reinterpret prior timings or propose that changing the grouping algorithm will remove the host dependency.

## Bounded exact-map experiment

Replay the fixed route-ID fixture for the same 78,452 rows, 48 layers and 10 chunks (nine 8,192-row chunks and the 4,724-row tail), covering 480 boundaries. Use two clean, separate processes with identical binary, device, prompt/route fixture, queue, warmup and environment, including `UR_L0_V2_FORCE_DISABLE_COPY_OFFLOAD=1`; set environment before process start and do not change it after runtime initialization.

- **Mapped arm:** at each boundary, keep the current three `copy_i32` operations: publish device IDs into a persistent host-USM staging region, wait before the CPU reads them, run the unchanged CPU grouping/reference, then pull `slot` and `src` from that host-USM region into the existing device-local map buffers.
- **Explicit-copy arm:** keep the same device-resident ID fixture and host-USM staging region. Use one `queue::memcpy` from the device IDs to host staging, wait before identical CPU grouping, then two bulk `queue::memcpy` commands for `slot` and `src` to their existing device-local consumer buffers. Keep the same boundary dependency and completion point. The safety setting remains enabled, so do not assume these commands use dedicated copy engines.

Measure enqueue CPU/wall, ID-copy completion wait CPU/wall, CPU grouping, map-copy enqueue, completion through a small map consumer, whole boundary sequence, call counts and logical bytes. Record event/queue waits separately; a queue drain can include prior queued work. Compare five paired clean-process repetitions with arm order alternated. Check every boundary's counts, offsets, expert order, `slot` and `src` byte-for-byte against the CPU reference, plus bounds and a small consumer result. A route fixture benchmark excludes model routing/GEMM and cannot qualify full prefill throughput or physical 262,144-context correctness.

Preload at most 160 MiB of device fixture IDs (the full logical ID stream is about 144 MiB), and reuse at most 1 MiB of host-USM staging for one maximum 8,192-row boundary: 327,680-byte IDs plus two 327,680-byte maps. Reuse device-local map destinations. Check host-USM support/allocation before timing; abort that arm cleanly on allocation failure. Keep all source, destination and staging allocations alive and unchanged until their final copy/kernel event completes; host reads/writes happen only after the matching event or queue wait. Do not free, recycle, or concurrently touch them while device work may use them. Do not batch across route boundaries in this experiment. If the explicit arm improves submit time but not full boundary time, that is not a performance win; if neither arm changes full boundary time materially, stop this transfer-path branch absent new attribution.
