# Xe2 joint_matrix schedules for transposed BF16 data and recurrent state

**Classification:** knowledge collection; read-only research  
**Research date:** 2026-10-18  
**Hardware context supplied by Main:** Arc B570 (Xe2, 10 GiB), about 6 GB/s measured host-link traffic; long prefill; BF16 activation storage with FP32 local accumulation/carry. No build, test, benchmark, profiler, GPU job, process inspection, Git command, or product edit was performed for this report.

## Executive synthesis

joint_matrix exposes the logical matrix shape and row/column-major memory view, but it does not prescribe lane-to-element ownership, prove a transpose is free, or prove XMX executed usefully. For GDN's 128x128 recurrent state, the update is dominated by elementwise decay plus a rank-one outer product and a query/state reduction; that is a much poorer automatic fit for XMX than dense GEMM. The strongest candidate to compare is a subgroup-owned 16x16 FP32 state fragment, grouped by output-column stripe so one work-group owns all eight row tiles needed for a local output reduction; compare its per-token synchronization and register footprint with independently scheduled tiles plus scratch/reduction and with chunked kernels that spill state between chunks. Treat direct col_major loads, explicit SLM transpose/staging, and repeated cached loads as separate arms; source evidence supports each as plausible, not a winner on B570.

## Facts and transfer limits

Intel's current B570 specification identifies Xe2, 18 Xe-cores, 144 XMX engines, 10 GB GDDR6 and 380 GB/s local-memory bandwidth. Intel's 2025.2 optimization guide uses the B580 as its representative Xe2-HPG model: 20 Xe-cores, 8 Vector Engines per core, 8 hardware threads per Vector Engine, subgroup sizes 16/32, up to 128 KiB SLM per core and 128 KiB per work-group, with 128/256 GRF modes. B570 has fewer cores than B580, and the guide does not publish a B570-specific GRF/SLM table. Use those numbers as a Xe2-HPG starting point, not as proof of B570's exact runtime properties. Query the actual device and compiler output.

The oneAPI joint_matrix interface is experimental. Its standard collective scope is one subgroup; all subgroup members must enter matrix operations in converged control flow. Each device/compiler pair supports specific type/shape combinations, so query matrix_combinations and test the installed runtime path. An immutable Intel LLVM documentation commit adding BMG-G31 support is 08e06d3ae73bd7a94a313c2e3bc31734cedc263a; its table distinguishes hardware targets rather than promising the same shape set for every SKU. B570's actual target code and advertised BF16 combinations still need Main's runtime check. Intel's 2025.2 guide says the matrix path has no emulation fallback; a SYCL matrix aspect or shape failure must select a non-matrix path before launch.

For a transposed operand, joint_matrix_load(..., stride, layout::col_major) describes a logical column-major tile with the stride measured between columns. This permits treating a physically row-major [N,K] buffer as logical [K,N] without first materializing a full transpose. It does not guarantee coalesced device transactions, zero rearrangement, or an efficient B570 lowering. joint_matrix fragments are subgroup-shared objects whose element distribution is implementation-defined; do not write a lane-index mapping based on CUDA WMMA or infer ownership from a source-level tile. joint_matrix_copy explicitly permits a same-shape copy across element types and uses, which makes BF16-to-FP32 fragment conversion an API-level option; its exact cost and rounding behavior on this toolchain still require inspection and a numerical gate. The SYCL extension's joint_matrix_apply is element-wise; coordinate-aware callbacks are Intel-specific.

A useful local reference is src/prefill/sycl/gemm16.cpp: the existing own BF16/FP16 GEMM stages a 16x32 A panel and a 32x32 B panel in work-group local memory, then four 16-lane subgroups load 8x16/16x16 fragments; B uses a column-major view over its [N,K] staging layout. Its two work-group barriers per K panel protect stage/read reuse. This is evidence of an existing transpose-view/SLM pattern in Strata GEMM, not a GDN implementation or proof that SLM is best for recurrent state.

## State-tile schedules to compare

The given 128x128 state has 16,384 elements: 32 KiB in BF16 or 64 KiB in FP32. A 16x16 fragment is 1 KiB in FP32; there are 64 such fragments per head. An 8x16 fragment is 512 B; there are 128 per head. These are logical working-set sizes, not register-allocation or occupancy measurements.

**A. Subgroup-owned matrix fragments with direct vector/SIMD recurrence.** Give one subgroup a 16x16 state tile and retain it as FP32 across the token loop; use BF16 storage at the prescribed boundary, then copy/widen to FP32 for local carry. Apply the state decay and rank-one update using vector/SIMD arithmetic over the fragment. For a coordinate-aware callback, row/column indices can select the K and V elements, but repeated pointer loads or gathers may become the bottleneck. This approach uses joint_matrix as a compact distributed tile and owner map without claiming the GDN recurrence itself maps to XMX DPAS. It keeps the numerical state local and avoids padded K work. Its risks are callback lowering, repeated gate/vector loads, live-range pressure over long loops, and how to compute q*S partials without crossing work-group boundaries.

**B. XMX rank-one outer update.** A BF16 A*B with FP32 accumulation can form an outer-product update, but the legal BMG BF16 combinations have reduction K at least 16 in the documented shapes. A rank-one update therefore either pads 15 K lanes with zeros or performs additional packing/repetition. The matrix engine might still win on throughput, but operand construction, padding, barriers, FP32 gate placement, conversion, and an extra accumulator can erase the gain and increase GRF use. Keep a SIMD-FMA arm: it performs only the useful per-element update and preserves FP32 gate/state math. This is a hardware-efficiency hypothesis, not a measured result.

**C. Direct transposed load versus SLM staging.** Direct-load the selected logical view from the device allocation and let caches serve repeated use. In the staging arm, cooperatively load the source tile, transpose/repack into SLM, barrier, then load the matrix fragment; measure the extra source read/write, barriers, padding, and SLM allocation against actual reuse. For one head/column stripe, a full 128-element BF16 K vector is only 256 B and a 16-element BF16 V stripe is 32 B; across many state tiles these are reused, but they may already be served from L1. An SLM staging win is most plausible when several subgroups in the same group reuse the same transposed panel enough times to amortize staging. R815 in Intel's SYCL*TLA is a counterexample to “cache every broadcast value in registers”: its BMG Xe2 256x256 epilogue tile duplicated each row/column broadcast value 16 times, causing 12–22 spills; replacing the full-tile register cache with small direct loads (reported L1-cached) removed the spills and improved its four GEMM cases 4.8–8.3%. That is transferable evidence against replicated register caches, not a GDN or Strata performance claim.

**D. Owner map and output reduction.** A concrete persistent candidate is one work-group per value-head and 16-column stripe. Eight subgroups own the eight 16x16 row tiles spanning the 128x16 FP32 state stripe. That is 48x8 = 384 work-groups per layer, with an 8 KiB logical FP32 state stripe per group; K/query vectors are reused across the stripe, and each group can reduce its row-tile contributions for those 16 output columns locally. This avoids an inter-work-group state dependency and a full per-token partial-output array. The costs are an intra-group reduction/barrier for each token if output is produced immediately, replicated K/query reads across the eight column stripes, and eight live matrix fragments per group. Compare 16- and 32-lane subgroups and legal 8x16/16x16 BF16 shapes; the larger subgroup may reduce hardware-thread demand but Intel warns it can increase per-subgroup register pressure.

A tile-per-work-group grid gives more independent groups and avoids per-token group synchronization, but a q*S output needs a reduction across row tiles. If eight row partitions each write 128 FP32 partials for every token/head, scratch alone is T*48*8*128*4 bytes: 1.5 GiB at T=8192, before the merge. That is a deliberately simple upper-cost model; a fused/streamed reduction can shrink it, but then ownership or synchronization returns. A one-work-group-per-head design that keeps all 64 FP32 tiles live has a 64 KiB logical state and up to 1024 work-items at subgroup size 16; it reduces inter-group state coordination but risks high group resource use and still needs output reduction across subgroups. The alternative stripe owner map is a middle point worth measuring.

## Persistent versus split crossover

Separate two meanings of “persistent”: keeping each state tile in FP32 over several tokens, and keeping one program resident to schedule several tiles. They have independent resource costs. A chunk-persistent state stripe saves repeated state loads/stores and launch control while keeping local FP32 carry; longer chunks increase loop duration, barrier count, and live ranges. Splitting into shorter recurrence kernels increases launch count and round-trip state traffic but can shorten live ranges, expose more work, and give the scheduler more load balance. Writing BF16 state between chunks is allowed only if it matches the adopted numerical boundary; otherwise preserve FP32 carry in scratch (whole-state FP32 is 3 MiB per layer across 48 heads, so each chunk boundary reads and writes about 6 MiB). This is device-local traffic; the supplied PCIe rate does not price this traffic.

A useful whole-path comparison is: persistent time = launch + per-token update/load/reduction + final state/output; split time = chunk launches + per-token math + per-boundary state traffic/conversion + partial/reduction work. Test chunk lengths that Main's existing long-prefill path can support, using the same inputs/state, and include transpose/preparation, state carry, output reduction, synchronization, and launches. Do not select from isolated DPAS throughput or occupancy estimates alone.

## CUDA/Triton analogies and evidence limits

CUDA WMMA documents that fragment element-to-thread mapping is unspecified and architecture-dependent; the transferable rule is to keep fragments opaque at subgroup scope and cross APIs via memory or documented cooperative operations. CUDA's per-thread register and per-block shared-memory budgets are an analogy for cost accounting, not Intel resource numbers. Triton's official persistent matmul tutorial describes the same general trade: persistent programs can coordinate work and pipeline loop iterations, but replace dynamic block scheduling with a mostly static schedule, which can lose load balance and underperform when the grid is small or uneven. Its implementation uses NVIDIA Hopper/Blackwell features, so its TMA/WGMMA/TMEM mechanisms are not Xe2 candidates. The relevant transfer is the crossover question, not code or tile sizes.

No source establishes a Strata speedup, B570 matrix throughput for GDN, exact dynamic SLM rounding, occupancy, or actual joint_matrix availability in Main's installed driver. SYCL*TLA is an Intel public project with a BSD-3-Clause license and CUTLASS ancestry; it was consulted as a design/performance reference only, and no source was copied or adapted. XeStrata was not consulted.

## Main retrieval/measurement checklist

1. Record B570 device ID, DPC++/IGC/NEO versions, target architecture, ext_intel_matrix, runtime matrix_combinations, and supported subgroup sizes. Probe BF16 A/B with FP32 accumulator and all candidate shapes.
2. For exact candidate kernels, retain compiler warnings/resource report and native disassembly; collect per-thread spill/private bytes, GRF mode, actual work-group local arguments and driver allocation, subgroup count, and work-group size. R1057/QSA static-SLM metadata is not a substitute.
3. Compare tile size 8x16 versus 16x16, subgroup 16 versus 32, direct global column-major view versus SLM transpose/reuse, SIMD-FMA recurrence versus XMX rank-one MMA, and persistent stripe versus chunk-split schedules. Gate each on output, final-state, bounds/fault and physical-context requirements before timing.
4. Use Main's serialized GPU process only; measure the full long-prefill dependency path and record input T, chunk length, state bytes, scratch, barriers, launch count, per-stage samples and whole-prefill throughput. No result should be promoted from matrix microbenchmark timing alone.
