## R1005 decision-support report

The scope was well chosen and its substantive source audit is useful. It separates the BF16 mixed stream for router/scalar shared-gate projection from the FP16 mixed stream for expert/shared matrix inputs; tracks the BF16 expert-down output, FP32 routed accumulation, shared-term placement and final BF16 store; and calls out the separate FP32 HC update. It appropriately limits claims to the local snapshot, records the missing `native_proj16` implementation boundary, and refuses to infer SGLang/vLLM model equivalence, numerical adoption or performance. The full-window gate lifetime and route-slot versus expert-major summation-order concerns are directly relevant to the candidate in the index. Novelty is concrete compared with the index’s R1004 metadata: it makes the dual-stream and gate-source correction explicit and turns them into component-level counterexamples and tests.

Two corrections are required before using it as a planner record:

1. The spec says `Gemm::f16_out16 x_f16=true`; that signature is wrong. In the pinned `gemm16.cpp`, `f16_out16` has FP16 input by definition and its boolean is `output_bf16`. `true` selects BF16 output. R1005’s prose reads the call correctly, but the spec phrase must not be copied into an index or implementation description.
2. R1005 says the old planner’s `shared_gate` plane is `W` floats. The pinned `moe_accum_plan.hpp` contradicts this: its `shared_gate` payload is `J*4` bytes, with `J=8192` (8,192 FP32 entries); `shared_gate_input`, `shared_up_input` and `shared_hidden` are also chunk-sized payloads. The separate existing `moe_window.inc` uses a `W*4` shared-gate allocation with `W=16,384`. The contract is right that a 65,536-row candidate using the current final combine needs the BF16-derived scalar gate available for every window row (262,144 bytes), or an explicitly different bounded schedule that preserves those values and their lifetimes. Correct R1005’s sentence attributing a `W`-sized gate to the old planner; this is a material admission/layout issue, not a formatting defect.

The report’s remaining limits are stated well: an immutable local source pin is not a matching SGLang/vLLM execution contract; source expressions and local GEMM accumulator type do not prove every device instruction or reduction order; the routed combine order changes under an expert-major fold; and the report does not qualify owner retirement, 262144-context behavior or performance. The source-only follow-up is not a substitute for those Main-owned gates.

## R1006 knowledge-collection report

This report fits its assigned collection role and should remain held from Main’s normal working context. It adds useful quantitative framing beyond the index’s R1004 metadata about summation-order differences: a conservative `2*gamma_10*sum(abs(p_i))` comparison scale for two serial FP32 FMA orders under stated normal finite round-to-nearest assumptions, BF16-bin masking, cancellation/overflow examples, and a prospective metric set that separates reducer differences from routing, input conversion, shared epilogue and task quality. It correctly labels the examples as illustrations, distinguishes deterministic ordering from unordered atomics, cites generic rather than matching-model evidence, and says actual adoption must use the validated model path and task outcomes. Its finite retrieval trigger and `schedulable_now=false` are appropriate: the report itself says no exact upstream branch/backend/kernel or concrete comparison fixture is established.

Corrections and limits for later retrieval:

- The text calls the shared multiply “non-fused” while also saying compiler contraction and generated instructions are needed to know whether multiply/add fuse. The source expression `v + shared*sigmoid(gate)` establishes neither separate rounding nor fusion; describe it as a source-level expression until the selected build/kernel is inspected.
- Some adversarial examples describe the values as being carried by weights, including negative weights. That is useful arithmetic evidence but may not be reachable through a normalized top-k router. When a concrete model comparison exists, construct the same signed products through expert outputs with valid nonnegative route weights, or label the example explicitly as outside the route domain. The report does disclaim that examples are not evidence of model reachability.
- The BF16 spacing statement “around +1” gives the upward spacing; below 1 the adjacent spacing differs. The illustrated upper midpoint and rounding result are correct, but the prose should specify the direction.
- The local source and framework commit pins are recorded, and Higham’s paper has a DOI. The official framework and vendor document references would be easier to retrieve with exact file/section paths or direct canonical links. This is a traceability improvement, not a reason to retrieve or re-run this collection now.

These are precision/traceability corrections, not a basis for rejecting the collection’s general mathematical points. The exact local source pin is MIT-licensed project source; the report describes vLLM/SGLang references as docs-only Apache-2.0 and NVIDIA material as reference material. No copied implementation or XeStrata-derived proposal appears in the reviewed text.
