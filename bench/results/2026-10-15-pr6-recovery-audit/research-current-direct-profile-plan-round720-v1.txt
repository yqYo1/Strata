## Interpretation limits of the timer

`PfTimer` in `src/prefill/prefill.cpp` records CUDA-compatibility events at phase boundaries on `cs`; under the configured SYCL path, `cs` is the in-order SYCL queue. `fold()` accumulates elapsed time between adjacent marks at existing host-sync points. Host delay before the next mark, including a late CPU submission, can therefore lengthen the preceding phase interval. The phase totals are not exclusive service time, and adjacent entries must not be summed as independent work. Event creation and recording return values are not checked. Timer output is diagnostic only, and a missing/zero bucket is not proof that the phase did no work.

The host line reports three limited spans: setup of each expert chunk's plan, host time blocked at the existing per-chunk callback synchronization, and host work after that sync (draft callback/progress). `stats_.ms_experts_host` is the existing aggregate staging-consumer time. These are host wall spans, not CPU thread service and not a complete breakdown of expert `Stager::wait`, source reading, queue submission, or all host work. In particular, the timer does not provide an exact CPU issuing-gap duration or prove copy completion time.

For the current hypotheses:

- A large `wait copy` interval is evidence that the queue-side interval around that marked stage is long; it does not isolate staging-worker service, H2D execution, or the CPU's blocking wait. Compare it with `host staging` and existing copy counters before attributing it.
- Large `host grouping` or phase intervals that stretch across late submissions may point to host issuance pressure, but the timer does not timestamp CPU route/gather/submit calls individually.
- `gather`, `dequant`, `gemm gate/up`, and `gemm down` buckets rank broad marked regions. They do not report per-kernel service, occupancy, memory bandwidth, SLM conflict rate, or whether a particular matrix kernel is compute-bound.
- If QSA attention is large, the bucket cannot distinguish its subkernels, data movement, or queue starvation. Existing Direct1 comparison controls the layout, but this timer alone does not validate why that layout is faster.

`STRATA_PREFILL_ROUTED_FP16_OBSERVE=1` is a separate host observer that records route shapes and requested copy payload/call counts only when its strict FP16/MMQ admission conditions pass. It does not record elapsed time per call or successful physical DMA bytes; the current FP32 path is not its intended admitted case. Do not enable it for this measurement or interpret a declined receipt as evidence about the current route. Other settings such as `STRATA_PREFILL_ATTN_LAYOUT` report dispatch counts, not execution time. `STRATA_PREFILL_PHASE_AUDIT` captures numerical/state evidence and is not a timer.

## What the existing provider paths can answer

The saved Main unitrace build is PTI revision `6c0d6b0b80c6dbac4b5902d9d5ade1c75b9e9033`. Existing `--device-timing` produces per-operation device duration aggregates; paired `--host-timing` and Chrome call/kernel collection can add host Level Zero API calls and device kernel/copy intervals. `model-device-profile-v1/v2.json` used only `--device-timing`, returned whole startup+prefill+decode device sums and a complete aggregate within 64 MiB, and explicitly cannot provide phase attribution, overlap/interval union, or prefill-only wall. Operation sums can identify expensive kernel families after mapping their names through source, but cannot distinguish the same family in prefill versus startup/decode.

Chrome `--chrome-call-logging --chrome-kernel-logging` can show host Level Zero API duration, visible device operation durations, per-engine lanes and overlap. API durations are CPU call times; they do not measure CPU work between calls. Copy traces may expose requested byte size and causal flow IDs, but not copy endpoint addresses/ranges or proof of PCIe wire bytes. Provider device lanes are not the native queue handle; overlapping device-lane unions are not automatically same-queue critical path. The historical provider recipes that can retain raw Chrome traces used a 2 GiB trace allowance for the 34,603-token request, while the current owner budget is 64 MiB text/file and 512 MiB total. The prior 513-token component alone emitted 135,949,669 bytes / 806,125 events. Thus a detailed Chrome trace of the 78,453-token run is not admissible under the current budget and is not the minimal next capture. Do not raise the limit or assume a truncated trace is complete.

`UNITRACE_SystemTime=1` only changes the timer source used by the collector. Existing CPU-header sampling does not validate actual Arc GPU timestamp correlation. Keep GPU/host clock correlation unqualified unless the representative trace passes the explicit bounds/ordering check. `UR_ENABLE_LAYERS=UR_LAYER_PARAMETER_VALIDATION` in saved environments is a validation layer, not a profiler; `UR_LOG_*` only configures diagnostic logs. Do not turn validation/logging layers on for this profile because they change the execution environment and do not answer timing questions.

VTune is not a candidate: the retained `vtune-visibility-v1/v2` records concern a standalone synthetic probe and include collection failures (the v2 failure is missing/unreadable VTune user-data directory, with zero journal entries). ## Follow-up decision gates

First record the two timer lines, actual prompt rows/chunks, exact environment/source/binary, fresh fault state, and unprofiled 303.2 tok/s diagnostic receipt identity. If the timer run changes output/rows, has timer errors, misses expected phases, breaches owner limits, or materially exceeds the existing same-case timing spread, retain it only as noncausal diagnostic evidence.

Use the resulting profile to pick one question. If MoE `wait copy` dominates, the next instrument should separate consumer wait from host submission/stager service without adding per-expert logging; existing aggregate staging data is not enough. If host setup/grouping dominates, use a bounded host-call census around source, route, gather and submission, with no new waits. If gather dominates, establish actual operation and memory traffic before considering a gather change. If matrix phases dominate, measure actual call-shape distribution and kernel duration; this event timer cannot establish SLM behavior or XMX occupancy. If QSA dominates, isolate its existing operation family with the already saved attention-profile method. Do not start parallel profiler/kernel experiments from this report.

Do not run a detailed PTI Chrome request-window profile under the current 64 MiB provider cap. A later request-window trace would include prefill plus restore, request overhead and one decode token, would not have an exact prefill boundary, and could not alone establish copy endpoints or same-queue identity. It needs a new approved retention budget and Main-owned cap monitor before any collection. The existing `--device-timing` aggregate profile remains a useful coarse fallback if the in-engine timer is unavailable, but it is weaker for the current stage-level question.
