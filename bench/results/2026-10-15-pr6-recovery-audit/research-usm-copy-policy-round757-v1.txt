# USM and ordinary-host copy policy research (round 757)

Date: 2026-10-16 JST  
Scope: bounded, read-only literature/code-policy research for the next ordinary-host versus USM host-transfer comparison. No GPU/compiler/build/test/profiler/process/environment/Git activity was performed. No source code was read, copied, or proposed.

## Existing measurement context

The current `own-prefill-host-attribution-v2.ja.md` reports the 78,452-token long-prefill diagnostic: 217.1 caller CPU seconds / 223.6 wall seconds; explicit GPU waits account for about 168.0 CPU seconds. Of the remaining 49.15 CPU seconds, 4.857 is source-slab preparation, 0.165 host grouping, 6.784 GEMM-call time and 37.348 unclassified. The current `bank.upload`/`rows` source is ordinary `new[]` memory passed through compatibility `cudaMemcpyAsync` to `queue.memcpy`. These facts motivate separating host-copy call CPU from subsequent GPU wait/transfer time; they do not establish pageable-memory staging as the cause of the residual.

## Findings

1. **What the V2 safety setting means.** Intel's current DPC++ [Level Zero environment-variable reference](https://intel.github.io/llvm/EnvironmentVariables.html) labels these as development/debug variables with changeable semantics. It describes `UR_L0_V2_FORCE_DISABLE_COPY_OFFLOAD=1` narrowly: copies otherwise eligible for dedicated copy engines are kept on the engine behind their original queue. It is not a pinning, host-registration, synchronous-copy, or staging switch. Thus the captured `=1` is a valid safety/scheduling condition to preserve in both arms; it does not identify whether a host pointer was staged or whether the CPU waited in `queue.memcpy`. The docs say the V2 adapter applies on Xe2+ or when explicitly selected, while the old adapter applies on older hardware or with V2 disabled. The ordinary Level Zero UR reference lists general `UR_L0_USE_COPY_ENGINE` and other controls, but this does not establish equivalence to the V2-specific toggle. **Do not infer that enabling copy offload is safe or useful here**: the provided production setup has an explicit reason to retain its safety setting, and this research did not test a change.

2. **Host pointer vs USM host allocation is a real contract difference.** The [SYCL 2020 specification](https://registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html) permits host pointers for explicit `handler::memcpy`; queue `memcpy` enqueues that operation and returns an event. USM host allocation is separately optional and is queried through `aspect::usm_host_allocations`. A host-USM allocation remains in host memory, is device-accessible, and is generally remotely accessed; it is not a device-local upload buffer. Intel's [data-transfer guide](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2024-1/optimize-sycl-data-transfers.html) recommends `malloc_host` when the application controls the allocation and that pointer is used in a transfer API. It also describes explicit import/release for externally allocated ordinary memory, but those APIs are experimental. A fair timing must therefore distinguish allocation/registration setup from repeated transfer submission and completion; amortizing setup is meaningful only if the same allocation is reused in production.

3. **Pinning has cost and limits; docs give no universal size ceiling.** The SYCL spec says host-USM total size is limited by pinnable host memory on most systems; the exact amount is platform-dependent. Intel's FPGA-focused pre-pinning guide emphasizes that pinning is expensive and scarce and recommends doing it outside the main compute loop. This is directionally useful, but its explicit FPGA/BSP throughput examples and support claims do not establish Arc Xe2 performance or limits. The UR [USM Host Alloc Register extension](https://oneapi-src.github.io/unified-runtime/core/EXP-USM-HOST-ALLOC-REGISTER.html) is explicitly experimental, intended to register external host allocations for device access without copies, and requires adapter support discovery. It does not prove the installed Arc adapter supports this API, nor that registration is cached automatically for current `new[]` calls. No official source found in this bounded search gives a portable maximum `malloc_host` size or promises allocation caching for repeated independent allocations.

4. **Async API names do not bound host CPU work.** SYCL queue `memcpy` returns an event representing an enqueued command; this is asynchronous at the execution model level, but the SYCL spec allows implementation-specific scheduling and says queue commands may not start until a host blocks on completion. Level Zero's `zeCommandListAppendMemoryCopy` likewise appends a copy and requires pointers be accessible in the device context; its contract does not promise zero host work in the append call. Neither contract guarantees that a runtime/driver will avoid pageable-memory registration, staging, copy preparation, command submission, or bookkeeping in the caller. Nor do these documents establish that any such operation is occurring in this run. In particular, `std::memcpy`/page faults on the CPU inside the compatibility call must be observed with a CPU-region bracket or stack attribution; a high caller CPU total dominated by explicit GPU wait cannot answer that question.

## Applicability and unknowns

The V2 definition applies if this process actually selected Level Zero V2; current hardware (Arc B570) is Xe2 class, so the official docs indicate V2 is the normal adapter on this family, subject to the installed runtime/version. Record the actual runtime and adapter version from the run receipt rather than assuming docs equal installed behavior. The old adapter's corresponding controls are distinct and must not be treated as a proxy. This research did not inspect installed runtime source or perform experiments, so it cannot tell whether current `queue.memcpy` copies ordinary pointers directly, stages them, caches registrations, blocks in call, or transfers asynchronously after return.

## Measurement implication for the pending comparison

Use two persistent, equivalently sized source regions and keep the same queue, destination, transfer sizes/order, safety environment and wait placement: ordinary `new[]` host source versus a supported SYCL `malloc_host` source. Report setup/allocation time separately from each transfer-call CPU and wall time, then event/queue completion CPU and wall time; retain bytes and call counts. Keep every source/destination allocation alive and unmodified until its corresponding copy event completes, then free through the matching SYCL allocator or ordinary owner. Avoid conflating “CPU busy while waiting” with time spent in the memcpy call. A warmed repeated-call arm can expose registration/cache effects, but should be labeled separately from first-use cost. Do not add a third import/register path until installed adapter support is positively queried and its lifecycle and cache behavior are defined.
