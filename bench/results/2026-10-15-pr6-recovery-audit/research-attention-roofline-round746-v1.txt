# R746 — Mode-1 Direct prompt-attention source roofline

2026-10-16 JST. Read-only arithmetic and source review. The only write is this report. No toolchain, build, test, GPU/process/runtime, environment, service, cleanup, or Git action was performed. No XeStrata source, helper, test, or archive was read or used; XeStrata was used only as the explicitly permitted performance-numbers reference. The R714 attention-layout analysis and the R692/R711 capacity arithmetic were read first to avoid repeating their proposals or capacity conclusions.

## Case and measured boundary

The existing Main diagnostic is the 78,453-token actual-input, C8192, mode-1 INT8 K/V, Direct=1 case. Its profile records 78,452 QSA query rows per each of 12 QSA layers, 120 matrix chunks, 941,424 total QSA queries, 120 matrix chunks, zero fallback chunks, and an attention queue-span sum of 69,692 ms. The cap is 2,051 selected cells, but each query's selected width varies; the cap is not the width for every query. The 69,692 ms is a sum of queue-timestamp spans across these calls, not exclusive device busy time and not an isolated kernel-time measurement. The surrounding model's QSA selection sum is 17,945.8 ms. Neither span should be interpreted as a clean performance sample or as a per-kernel attribution.

The current JIT receipt is a diagnostic for the exact mode-1 Direct source specializations, captured on an nq=256 component case. Its ZEInfo reports SIMD16, 128 GRFs, DPAS present, and 4,096 B static SLM for each specialization. UR tracing reports 13 local arguments totaling 44,496 B, local size 128, global size 65,536 for the component launch, and device `LOCAL_MEM_SIZE` 131,072 B. These are resource observations for the component diagnostic; they do not establish dynamic SLM use, occupancy, active EU count, spill traffic, or resources for every actual-model shape. No spill count is proved by the present receipt.

## Source-defined work and ceilings

In `prompt_attention.cpp`, mode 1 uses HD=256, CH=32, WG=128, four K scale groups, and four V scale groups. One work-group handles one query row and one KV head; the two KV heads are separate work-groups, each covering the corresponding 12 query heads. Each selected-cell tile runs a QK DPAS phase and a PV DPAS phase. QK computes the high and low FP16 pieces of Q separately; PV does the same for the probability/value product. Each `joint_matrix_mad` is an 8x16x16 FP16-input/FP32-accumulate operation, or 4,096 FLOPs when counting an FMA as two operations.

Per 32-cell tile and per KV-head work-group, the source executes 128 QK DPAS operations and 128 PV DPAS operations: 256 total, or 1,048,576 source-level FLOPs. This includes 16 rather than 12 query rows in the matrix tiles, so four rows are inactive padding, and it includes separate hi/lo passes. The corresponding ideal single-pass attention arithmetic for 12 query heads, 32 cells, and HD=256 would be 393,216 FLOPs. The source tile therefore issues 2.67 times that ideal arithmetic count; this ratio describes source-issued DPAS work, not useful FLOPs or achieved hardware utilization.

For a query with selected width `s`, the loop issues `ceil(s/32) * 256` DPAS operations per KV head. Across the 78,452 rows and both KV heads, the exact source-work expression is `2 * 256 * sum(ceil(s_i/32))` DPAS operations. The width histogram is absent from retained evidence, so a single actual operation count cannot be recovered. At the maximum `s=2,051` for every row, the upper bound is 2,610,882,560 DPAS operations and 10,694,174,965,760 FLOPs. Dividing this deliberately conservative all-at-cap work by 69.692 s gives at most 153.45 GFLOP/s of source-issued work divided by queue-span sum. This is not a measured achieved rate; actual issued work is lower because widths vary, and queue spans are nonexclusive. There is no useful nonzero lower bound from the retained width data.

The mode-1 global payload for each active selected cell and KV head is 512 B of K/V INT8 codes plus 16 B of K/V FP16 scales, 528 B total. At the cap for every query, that is at most 169,915,734,912 B logical payload across both KV heads. Rounding every query to the source's 32-cell tile gives a more conservative 172,318,248,960 B bound on tile payload; out-of-width rows skip the source code/scale loads, so this rounded value is an upper bound, not a traffic measurement. At Intel's advertised 380 GB/s B570 memory bandwidth, these two byte counts imply idealized transfer floors of 0.447 s and 0.453 s respectively. Compared with 69.692 s of queue spans, they do not support a DRAM-bandwidth-only explanation at the all-cap assumption. Actual selected widths, cache behavior, address-sector efficiency, repeated cache-line fetches and other traffic are unknown; the advertised bandwidth is a product specification, not a measured sustained rate.

There are seven work-group local-memory barriers in each 32-cell tile (row/score readiness, K/scale readiness, QK completion, V readiness, V-scale factors, hi/lo probability readiness, and PV completion), plus one before the loop. Thus 2,051 cells lead to 65 loop iterations and 455 loop barriers per work-group, before accounting for the other work in those iterations. The kernel also repeatedly writes/reads local score, K/V, scale, probability hi/lo, and query tiles. The 4,096 B ZEInfo SLM number cannot by itself explain this scratch footprint: UR's 44,496 B local-argument total is a separate report, and the mismatch means the resource presentations must not be collapsed into one occupancy figure. Static GRF/SLM metadata alone does not determine whether DPAS is compute-limited, whether local-memory/barrier stalls dominate, or whether subgroup/EU slots are idle.

Intel's B570 specification gives 18 Xe-cores, 144 XMX engines, 2.5 GHz graphics clock, 203 INT8 TOPS and 380 GB/s memory bandwidth. It does not give a B570-specific FP16 DPAS peak in the cited product specification. Older Intel Xe architecture throughput tables describe Xe-HPG-era hardware, so applying those rates to this Xe2 B570 kernel would be an unverified architecture transfer. Accordingly this report does not convert the work count into an asserted percentage of FP16 peak. The INT8 TOPS figure is not a valid peak for this FP16-input/FP32-accumulate source path.

## Smallest useful next measurement

One bounded, same-binary profile of the existing actual 78,453-token Direct=1 pass should add only the counters needed to partition the 69.7 s queue-span evidence: per-dispatch selected-width histogram and elapsed time; XMX/DPAS active cycles; EU active/occupancy and dependency-stall breakdown; global bytes and sector/cache efficiency; SLM traffic/conflicts and barrier wait. Keep selection/kernel intervals separate and report whether each counter is a device-active count or a timestamp span. These measurements discriminate the main cases: high DPAS utilization with low memory/barrier stalls supports compute pressure; low DPAS utilization with high global-byte/sector waste supports global-load inefficiency; low DPAS utilization with high SLM/barrier stalls supports local scratch/synchronization overhead; low active EUs or low resident work-groups supports subgroup/occupancy underfill. If the profiler cannot provide those counters, a short fixed-width kernel-only sweep (32, 256, 1,024, 2,048 selected cells, replaying identical captured rows) can establish scaling and tail cost, but cannot alone distinguish memory from subgroup stalls.

No implementation or performance recommendation follows from this arithmetic. The earlier rejected padded-K and K-mapping arms remain rejected, and the existing default mapping stays the comparison reference pending evidence.
