# R805 — Intel GPU matrix operand layout and lowering evidence

Purpose: `knowledge_archive`; read-only. This report compares low-precision GEMM B layouts and records the compiler/runtime evidence needed to separate data movement from matrix arithmetic. It is not an implementation proposal or result. Main should defer reading it until an owned measurement opens a concrete layout decision; it does not select a tile, library, or backend.

## Decision scope and known local boundary

The provided motivating note pins `src/prefill/sycl/gemm16.cpp` to `9c1a2020`: weights `[N,K]`, with `BM16/BN32/BK32/WG64/SG16`. This is an example, not proof of measured shapes or a GEMM bottleneck. The whole-model BF16 result, active coarse profile, and untested R803 source benchmark establish neither component cost nor codegen. No Arc performance claim is made.

Viewing those bytes as logical `B[K,N]` yields a column-major view with element stride `K`. `col_major` specifies addressing, not register ownership or emitted conversions. Intel’s older XMX example instead assumes VNNI-reordered B and uses Intel-specific `layout::packed`; it is not a portable efficiency guarantee. A third path stages a transient transpose in SLM or converts within subgroup registers. None is selected by API documentation alone.

## Candidate paths and crossover questions

**Direct column-major B.** Keep `[N,K]` weights; pass logical `B[K,N]`, `col_major`, stride `K`. This avoids a pack pass and buffer, making it worth checking for low reuse or small operations. But a compiler may materialize gathers/lane moves, and the tag reveals neither global access efficiency nor conversion cost. Check per-device B-col-major type/shape legality, exact pointer/stride support, and the loaded binary.

**Persistent VNNI/packed B.** Convert weights on load and reuse the packed form. Intel’s BF16 sample assumes VNNIed B, declares Intel `layout::packed`, and uses a doubled element stride. This historical XMX pattern does not define VNNI for every dtype/generation. For `R` uses it pays only when `Tpack + R*Tpacked < R*Tdirect`. Repacking per call, changing weights, retaining both copies, padding, transfers, residency, and model-load latency can erase the benefit. Replacing original weights is viable only if all consumers and reload paths accept packed data.

**Per-tile SLM transpose or subgroup shuffle.** Load a tile, then rearrange it on chip. Work-group SLM enables cross-subgroup sharing but costs local traffic, barriers, bank behavior, and finite capacity. Subgroup shuffles avoid that scratch exchange when data stays subgroup-local, but add lane communication and register/live-range pressure. A pointer overload does not prove `joint_matrix_load` supports or efficiently consumes local memory; check the installed release and binary. Compare only if direct-layout codegen or device metrics expose a repeatable conversion cost.

Packing’s plausible case is stable, reused weights with a cheaper packed load/DPAS sequence; one-shot or frequently replaced B is the countercase. SLM needs tile reuse to repay local traffic/barriers; tails, low occupancy, capacity, bank conflicts, GRF growth, and spills can reverse it. Li et al.’s 2009 CUDA GTX 280 study varied shared-memory transpose for bank conflicts alongside tile/thread shape. It supports treating layout as a measured variable, not transferring its hardware or results to XMX.

Address behavior is shape- and ownership-dependent. At a fixed K index, adjacent output channels in raw `[N,K]` are `K` elements apart, while a K walk inside one channel is contiguous. Whether lanes issue coalesced transactions depends on which axis they own and on the backend’s block-load lowering. VNNI packing rearranges data for a specific operand convention; the guide’s pointer arithmetic alone does not specify every interleave, tail, or alignment case. Keep K/N tails and any padding traffic explicit. A direct col-major load could already lower well; a packed load could still add conversion or residency cost.

## Compact contract table

| Layer | Documented contract | What it does not prove |
|---|---|---|
| SYCL `joint_matrix` | Experimental; A/B row/column-major, accumulator dynamic. Only `sycl::sub_group`; collective construction/ops require converged control flow. Load stride is in elements. Query `device::matrix_combinations` / `matrix_params`. | Pointer alignment, lane mapping, col-major cost, or current support for Intel `layout::packed`. |
| Intel packed example | Guide 2023.1 XMX BF16 example assumes VNNIed B, uses Intel `layout::packed` and doubled offset/stride. | Cross-release/device/dtype/tail/local-memory support or a complete pack permutation/alignment contract. |
| IGC vISA `DPAS` | `D=C+A×B`; B (`Src1`) has a special GRF layout. BF16/HF16 inputs match; N is 8/16, with platform depth/type limits. Dst/Src0/Src1 are GRF-aligned; Src2 has depth-derived DWORD alignment. | SYCL pointer alignment, or proof that source `joint_matrix_mad` becomes DPAS. |
| SLM / lifetime | Work-group scope; capacity/banks are device-dependent; same-bank different-address accesses serialize. Query local capacity; use converged barriers around producer/consumer/reuse. Matrix collective remains subgroup scope. | That SLM input is legal/cheap for a given matrix load or all devices share one bank layout. |
| Compiler/runtime | DPC++ may JIT from SPIR-V or compile AOT. Resolve the actual compiler, adapter, and binary. UR exposes host tracing and Level Zero/OpenCL/native-CPU adapters. | Queue identity or successful API calls prove GPU matrix arithmetic. Host API spans alone do not time device work. |

IGC documents `DPAS.bf.bf.8.8`; its GRF alignment applies to compiler operands, not the user pointer. Check repeated DPAS and adjacent conversion instructions in the executed binary plus timing/counters. A legal API query proves neither selected adapter nor native XMX execution.

Use multiple evidence layers for attribution. Source/API legality and typed device IR establish intent; the exact binary loaded by the runtime establishes the selected lowering; ISA structure establishes whether DPAS coexists with extra permutes, local-memory traffic, or barriers. Neither instruction counts nor code size measures dynamic cost, so pair them with device duration and available memory/matrix/occupancy counters. A JIT compile made by an offline tool is only comparable if target, options, driver/compiler, and resulting code match the run. UR tracing brackets host runtime calls; instrument device duration and host thread CPU/wait separately. A queue on a GPU says where submission was directed, not where a fallback or all math ran.

## One prospective discrimination protocol (not run)

Wait for a source/binary-pinned true-16 fixture and active profile to identify one actual `(M,N,K)`, strides, dtype, accumulation, and reuse count. Hold math, tile, launch, output, and correctness fixed; compare direct column-major B with once-packed persistent B for that tuple only. If disassembly shows a conversion, a later SLM/shuffle pair may isolate it; do not sweep shapes or tiles.

For both arms preserve source/toolchain/device, adapter, IR, and the actual JIT/AOT binary. Record vISA/native DPAS repeat/depth, accumulator dependency chains versus independent DPAS chains, B-side conversion instructions, SLM/barriers, GRF/spills, reference correctness, pack and residency costs, device and whole-call times, host thread CPU versus wait/poll, transfers, and available matrix/memory/stall counters. This separates math dependency limits from operand-layout work. Freeze environment before runtime initialization; use clean owned processes and retain individual samples/fault receipts per `ARTIFACT_RETENTION.md`. Compare `Tpack + R*Tpacked` with `R*Tdirect` including real invocation and residency costs.

Math limitation needs device time/counters showing matrix work without dominant conversion, memory, or occupancy cost. Layout limitation needs repeated conversion/conflict/spill evidence plus a penalty that disappears in the matched packed arm without changing math or correctness. If counters are unavailable, say so; source alone cannot identify the bottleneck. Separate CPU spent in waits from compute/submission. Intel’s no-emulation/fallback statement applies only to its XMX example; UR and AdaptiveCpp also document CPU routes, so identify the selected route. A GPU queue is not proof of native matrix execution.

## Limits and retrieval gate

DPAS GRF rules do not predict layout cost. AdaptiveCpp/OpenSYCL calls its Intel-GPU generic path experimental and documents separate CPU OpenMP paths; this does not establish Intel matrix-extension support or fallback behavior.
