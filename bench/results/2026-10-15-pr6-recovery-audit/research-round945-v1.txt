# Round 945: BF16-prefix QSA tiles and operand reuse

Classification: decision support. Scope: source-level scheduling and storage choices for the current BF16-prefix QSA attention path. This is a design comparison, not a performance result or an implementation proposal patch.

## Finding

The strongest potential reuse is across adjacent query rows, not another split of the 12 query heads. Keep all 12 real heads (plus the current four padded rows) together for each KV head, but experimentally schedule a pair of adjacent queries through one workgroup and share each gathered K/V tile across the pair. This only merits a Strata candidate if the current weighted-cell selector rows have high overlap and if exact per-row membership and causal tails can be preserved. The vLLM same-model tile-union report is a useful external lead, not evidence for Arc B570.

A lower-integration comparison is a 64-cell K staging window with two ordered 32-cell score/softmax/PV substeps. It can reduce row-index and K-staging synchronization without changing the current 32-cell FP32 online-state update boundary. Neither option changes BF16 operand formats: Q/K/V and P stay BF16; Q is scaled then BF16-rounded before QK; score, max, normalizer, alpha and output accumulators stay FP32; output is rounded to BF16. The SGLang contract is the priority check. Reordering keys or changing the reduction tree still requires comparing outputs against that model path.

## Current local dataflow

`src/kernels/sycl/qsa_bf16_prefix.cpp` first launches a transient pack over live logical rows. It consults the logical-to-physical page table before reading K8/V8 codes or FP16 per-64-dimension scales, dequantizes in FP32, rounds K and V to BF16, and writes separate dense `[row,256]` K and V scratch arrays. The attention kernel resolves each selected cell to a logical packed row. K is copied into a workgroup-local `[dimension,cell]` transpose; V is copied in `[cell,dimension]` order. The header documents zero fill for padding/unmapped pages and caller-owned scratch lifetime. This pack plus attention is the 21.5123-second profiled attention envelope.

The current attention grid is one 128-work-item group for each query and each of two KV heads. It requests subgroup size 16, so each group has eight subgroups. The local query tile is 16×256 BF16: twelve real query heads and four padded rows. QK uses four subgroups, each producing an 8×16 score tile; the two N tiles and sixteen K steps cover 16 padded rows × 32 cells × 256 dimensions. PV uses all eight subgroups: each owns eight heads × 64 output dimensions as four FP32 8×16 accumulators. The 32-cell BF16 K/V tile is reused across the head groups, so another head split would repeat data movement.

Current local storage sums to 28,160 bytes: Q 8 KiB, shared K/V staging 16 KiB, P 1 KiB, scores 2 KiB, row indices 256 B, per-head statistics 192 B and diagnostic flags 64 B. Each 32-cell loop maps IDs and pages, stages/transposes K, computes QK, updates FP32 online softmax and BF16 P, stages V, then computes PV. The prefix route packs K/V once before attention; `qsa_bf16_attention_late_flags.cpp` is a useful layout comparator but instead dequantizes selected K/V inline and reduces diagnostic flags at the end. `src/prefill/sycl/qsa_native16.cpp` selects the math route; its header retains BF16 I/O and the local FP32 operator boundaries. None of these source facts alone establish which resource limits the measured run.

At maximum width 2,051, the current tile takes 65 loop iterations. The clean long-prefill summary reports 445.4 tok/s for `bf16-prefix` versus 406.1 for `bf16` and 393.4 for current, across three processes per arm. These are whole-prefill results, not a tile attribution. The separate instrumented 39,262-token profile reports wrapper 89.2009 s, QSA 27.4816 s, attention including prefix pack 21.5123 s, selection 3.88812 s, and MoE 20.1915 s. Queue intervals are nonexclusive and include submission gaps; no PMU counters were collected. Do not turn these intervals into XMX, cache, VRAM, or utilization percentages.

## Bounded alternatives and discriminating observations

**1. R=2 adjacent-query tile-union (highest upside, conditional).** Group two consecutive rows only within one prefill chunk and KV head. Preserve each row's actual selected-cell set, its width, page validation and causal tail; build a stable union plus per-row membership and gather each union K/V tile once. Maintain separate Q, max, normalizer, alpha and FP32 PV accumulators for the two rows. Keep the existing 16-head mapping and BF16 Q/K/V/P conversions. This changes scheduling and may change the order of FP32 updates, so compare against the pinned SGLang BF16 path and retain the old path as control. Do not substitute SGLang's compressed-block IDs for Strata's weighted-cell IDs.

The vLLM Qwen3.8-Flash-Next tile-union report describes R=2 sharing and reports 87–94% Jaccard overlap on 8K selector dumps. It first overstated kernel gain against a stale baseline, then corrected its comparison to about 1.5× kernel time improvement and about 2.9% TTFT on GB10 after build/selection overhead; its maintainer discussion calls out complexity and weak end-to-end return. These are author-reported CUDA/GB10 results from an unmerged design, not Arc or Strata measurements. For Strata, count actual adjacent-row intersection and union width from the same input/IDs, then time union-build plus attention as one component. A small `union/(width0+width1)` with lower whole-component time despite extra row math supports selector-gather reuse as a useful path. Low overlap, expensive union construction, register spills, or no component gain rejects it. Without counters, a timing gain does not prove reduced physical VRAM traffic.

**2. Stage 64 cells, retain 32-cell recurrence (lower-risk control).** Keep M=16 heads and subgroup mapping unchanged. Stage up to 64 row IDs and the transposed 64×256 K slab once; compute both 32-cell QK score halves into a 16×64 FP32 score tile. Then run the existing online max/normalizer/PV sequence first for cells 0–31 and next for 32–63, reusing the 16×32 BF16 P buffer and staging V 32 cells at a time. This preserves the current per-32-cell online update and PV order while reducing repeated row/page resolution and K staging. At width 2,051 it changes 65 outer iterations to 33, but QK/PV multiply work and logical selected-cell bytes remain the same. Estimated local storage is 46,848 B if P stays 16×32; admission must query the actual device and the candidate needs register/occupancy inspection. Its extra SLM may cost more than the saved barriers and ID work.

If this candidate lowers same-input component time with unchanged selected-cell count, output boundaries, and requested logical bytes, the saved fixed loop/synchronization/indexing work is implicated. If time rises as SLM grows, occupancy or spills are plausible, but counters are needed to establish that cause. If neither candidate improves while matrix-multiply issue is unchanged, an ALU/XMX limit remains possible; if traffic/cache misses dominate, R=2 is more promising than 64-cell staging. Current receipts cannot distinguish those cases.

## Contract, counterevidence, novelty, provenance

Pinned SGLang QSA source groups the 12 query heads into a padded M=16 tile, selects BLOCK_N by shape/device configuration, scales and rounds Q to its dtype before QK, maintains online FP32 max/normalizer/accumulator, and rounds probabilities to V dtype for PV. Pinned vLLM QSA also uses M=16 and FP32 online state but scales its BF16 QK scores after the dot, so it is not the numerical substitute for the selected SGLang contract. SGLang demonstrates the existing head reuse and online algorithm; neither stock kernel proves cross-query reuse on this engine.

Prior R568 already considered 8-head×64-cell scheduling and rejected splitting the current head tile because it rereads KV in a second workgroup and adds matrix work. The staging comparison here keeps M=16 and stages K once, with 32-cell recurrence boundaries retained; the query-union option changes the query axis and is new relative to that head-only study. R928/R931 already map SGLang's path and numerical boundaries; R935 supports the BF16 component candidate but not this scheduling change. R939's physical initialization, R941's BF16 numerical threshold corrections, and R944's MoE/GDN review do not settle these tile choices. This report adds the query-sharing alternative, a recurrence-preserving N64 control, and a path to distinguish their evidence.

Intel's versioned oneAPI GPU optimization guide says SLM allocation and register use affect workgroup occupancy and that higher occupancy is not by itself a performance guarantee. Its B580 table is not B570 measurement; query actual device limits. Intel's 2025 joint-matrix guide describes the API's matrix load/mad/prefetch operations and XMX mapping, while the Intel joint-matrix technical blog presents the API as a way to fuse custom dataflow. These references support feasibility only, not the target compiler's lowering or local speed. Source-level `joint_matrix_mad` calls do not reveal utilization; no Arc PMU evidence was available.
