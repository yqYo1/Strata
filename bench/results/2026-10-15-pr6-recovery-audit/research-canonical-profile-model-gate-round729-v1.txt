`parse_profile()` does not rely on `complete=1`: it requires 50 profile lines, version/status/schema strings, twelve wall values and six queue/sample values per layer, 48 ordered layer rows plus aggregate, QSA/GDN per-layer sample geometry, aggregate counts `[470,120,360,480,48,470]`, exactly 12 QSA and 36 GDN layers, and expected upload/input/store requested bytes. Its wall denominator excludes teardown.

One concrete lifecycle assertion gap remains: dense output fields include `session_recapture`, but the gate never checks that field (it validates positions 0–6 and verifier at 8, skipping 7). The receipt records the phases as raw parsed tuples, so a reviewer can recover the value if they read the full receipt, but `passed=true` would not establish any expected session-graph recapture state. Qualification should state whether recapture is expected for this exact no-token-graph workload and validate that value, or explicitly leave it as an unqualified observation. This is not evidence that recapture occurred or caused a problem.

Parser robustness is otherwise a modest schema-hardening opportunity, not a demonstrated wrong count: row parsing checks required fields by later indexing but does not reject extra/duplicate keys or require one exact key set. A malformed line with duplicate keys would be last-value-wins under `dict(re.findall(...))`; ordinary output is generated by the pinned formatter and the line/count/shape checks constrain it. I found no concrete count or byte arithmetic mismatch. The aggregate sample vector ordering agrees with the formatter’s interval enum (`input,QSA,GDN,MoE,upload,store`).
