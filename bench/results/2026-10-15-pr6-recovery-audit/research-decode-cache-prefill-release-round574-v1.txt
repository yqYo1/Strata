# Round 574 — persistent decode cache と native hit graph の prompt 中一時退役

2026-10-15 JST。読み取り専用の現行 root source 調査。唯一の書込先はこのレポート。製品source、build/test/GPU、git/cleanup、service は触れていない。過去調査とMain review、MTP-only retirement proposalを読み、既知の「close/reset APIがない」「MTPのKV-only promptはrouted experts不要」は繰り返さず、target decode cacheとSYCL hit graphの再構成・caller境界を特定した。速度、GPU free増加量、restore/recapture時間、正しさは測定していない。

## 結論

対象を **1 GPU / persistent target `ExpertCache` 128-slot tier (~260 MiB) と `ExpertDispatch::native_hit_graphs`** に限る場合、実装の核は小さくできる。`ExpertCache::close()` →同じ`ExpertCache` objectに`open()`/`open_sized()` →同じprofile順に`admit`/fill → `host_res`・device residency table再公開、という既存操作がある。native hit graphも一度 drain後 `native_hit_graphs.reset()` してから既存`expert_hit_prepare_graphs()`を呼び直せる。しかし現行のdestroyはunchecked destructor相当であり、Verifierがcache pointerをcaptured graphに保持するため、この順序を安全と証明するAPIはまだない。

**retire order:** (1) prompt区間へ入る時点でVerifierの全window work/segments graphsを成功確認つきでretireし、window実行者を止める。(2) main `ExpertDispatch` hit callbackとそのhost pool/callbackの実行終了、`main_cs` queue drainを確認し、`native_hit_graphs`をretireする。(3) host/device residencyを全missへ切替え、prefill readerがcache slotを参照しないことを確認。(4) そこで初めてcacheをclose。Restoreはcache確保→profileの同一順序で全slotを再充填→completion確認→host/device residencyをpublish→Verifierの`VerifyHits`値とDispatchのcache base/off値を更新→native hit graphs再capture→decode/next short-windowを許可する。

Verifier destructor/re-init案はserveの最小策ではない。serveのVerifier arena内の`final_R`をMTP通常/coupled `round_exec`がborrowしている。Verifier graphだけを退役し、Verifier arenaと`final_R` addressを維持すれば、MTP graphsのreader lifetimeを変えずに済む。`Verifier`にはそのgraph-only APIもhits-update APIもないので追加が要る。sessionの普通のper-layer `pre/post` graphsはtarget cacheをcaptureしない。SYCLではtoken graph (`TokenGraph`/`session_capture_token`) 自体が明示unsupportedで、このretirement対象に含めない。

## 現行source resolverと所有関係

configured SYCL targetは cmake/sycl_backend.cmake:95-113 のroot `src/core/{expert_source,expert_cache,verify,mtp,session}.cpp`、root `src/prefill/prefill.cpp` + `src/prefill/sycl/*.cpp`、実entrypoint root `src/program/generate.cpp` を選ぶ。別の旧`sycl/src`やXeStrata engine、Niko root CUDA generatorを実装根拠にしていない。

- `ExpertCache` (include/strata/core/expert_cache.hpp:76-105, src/core/expert_cache.cpp:288-305) はdevice `base_`に加えresidency map/slot offsets、SYCL blocking stagingを持つ。`close()`はそれらを破棄するが、queue drainやcudaFree結果を報告する一時退役APIではない。再開に必要な既存部品は`open`/`open_sized`, `admit`, `fill_slot_blocking`または`fill_slot_queued`+`sync_queued`, `verify_slot`, `slot_of`, `device_slot`。常にprofile全件が128 slotsに収まるとは限らないので、startupと同じ`min(profile.size(), slots)`条件/順位で復元する。
- `ExpertDispatch` (include/strata/core/expert_source.hpp:218-296) はcache object pointerと複数のdevice-side cache/hit buffersを持ち、SYCL `native_hit_graphs`は`shared_ptr<NativeHitGraphs>`。`expert_hit_prepare_graphs()` (src/core/expert_source.cpp:2270-2360) は `hit_out`, `native_hit_ptr/meta`, `d_dst`, `mixed`, `hit_scratch`, mapped `host_plan`をcaptured graphへ固定し、runtimeにrouteされたcache slot pointerをmetadata経由で読む。再capture前に呼ぶべき既存のretireはcleanupの`drive.d.native_hit_graphs.reset()` (src/program/generate.cpp:7276) だけ。`NativeHitGraphs::~NativeHitGraphs` はexec destroyとhost plan freeの戻り値を捨てる。従って成功を確認するproduction retirement APIはなく、単純 `.reset()` をfault/async failure後のfree証明には使えない。
- `Verifier::init()`は`VerifyHits` (`d_res`, `cache_base`, `slot_off`, `n_slots`)を値コピーする (src/core/verify.cpp:239-260)。SYCL `Verifier::capture(T)`はT別`segments_[T]`と`work_[T]`をlazy captureし、work側はresident GPU hit/cacheを使う (src/core/verify.cpp:1044-1072); それらは同じraw cache base/offを捕捉する。全てのTについて`segments_`と`work_`をretireした後でないとcacheをcloseできない。Verifier destructorにはgraph destroyとstream syncはある (src/core/verify.cpp:215-236)がarenaもfreeしてしまう。再利用したい`final_R_all()`はMTP normal/coupled graphsがborrowするため、destructor/reinitは余計な切離しが要る。必要最小追加口はactive window/commit/copy streamsのchecked idleを証明してwindow graphsを全T destroy/resetするgraph-only retire、cache restore後`hits_`を書換える更新口で、`arena_`, streams, events, final_Rを維持するもの。`commit_exec_`は`record_commit`のstate/KV commit用でcache expert pointerを読まないため、少なくともcacheから切離す目的だけなら維持できる。
- `MtpDrafter::bind()`は`window_R_`を参照設定し、round graphをlazy captureする。`capture_round()`がcaptured `round_exec_[T]`とcoupled対をcacheし続けること、`MtpDrafter::idle()`はstream syncのみでgraph destroyしないことは既報MTP proposalの通り。本案はVerifier arena/addressを維持するのでMTP normal/coupled graphsもそのままreaderとして生かせる。MTP experts675MiBの開放/再uploadは別Sol候補で、ここでは再実装しない。
- `session_graphs_free()`は`SessionGraphs`のexecs/posts/routes/sharedをdestroyできるが、それらはlayer pre/postのoperatorsであり、通常のSYCL hit callbackを別途`session_loop`から呼ぶ構成。target cache baseをdirect captureするのは`TokenHits`を持つtoken graph側だが、SYCL `session_capture_token()`はunsupportedでreturn errorする。従ってsession `pre/post` graphをcache退役のために捨てる必要はない。

CUDAの公式Runtime API文書は`cudaGraphExecDestroy`、`cudaGraphLaunch`とgraph capture後のinstantiationを記載する: https://docs.nvidia.com/cuda/cuda-runtime-api/cuda_runtime_api/group__CUDART__GRAPH.html 。ここではAPIの存在だけを参照し、同期済みSYCL compatにおけるdestroy失敗時の保持保証やfree VRAM量は文書から推論しない。

## prefill境界と、実装で外せない追加条件

`generate.cpp`のstandalone経路ではprefill setup/`Prefill::run`が先、Verifier生成とMTP bindは後 (src/program/generate.cpp:6321-6350, 6731-6747)。そのため、cache retirement/restoreを単一prompt区間に置き、decode/Verifier初期化前に必ずrestoreするならVerifier window graphsのretireは不要な場合がある。ただしSYCL `native_hit_graphs`はsetup時にcaptureされている (src/program/generate.cpp:3524-3531)ので、main streamをdrainしてretire/再captureする必要がある。

serveは反対に、`Verifier::init()`と`mtp.bind(..., ver.final_R_all())`をrequest loopに入る前に行い (src/program/generate.cpp:4735-4744)、`read_windows()`ではVerifierを使い、batched promptは`sp.run()`を使う (src/program/generate.cpp:5635-5685, 5850-5872)。`sp.run()`区間だけ両モードを切り替えるならVerifier graph retirementが要る。区間直前にVerifier graphsをclearし、batched segment成功後/short-read `read_windows()`/decode前にcache復元とhits更新を完了させる。short read windowsを先に読むprompt分割やcheckpoint restoreもあるため、request全体の先頭/末尾で一度だけretireする前提にはできない。serveは次のrequestへ同じVerifier/MTP/Prefill ownersを持ち越すので、成功・失敗・STOP/取消すべてで状態を明示する必要がある。

現行serveの`Prefill`はデフォルトでcache tail slotsをbuffer loanにする。`Prefill::init()`は`cache`, `host_res`を保持し、`borrow`を指定するとdevice buffersをそこへcarveする (include/strata/prefill/prefill.hpp:58-73, src/prefill/prefill.cpp:714-830); `run_impl`は`host_res>=0`かつ`cache`のとき `cache->device_slot()` へアクセスする。cacheをcloseするなら、**borrowed Prefill buffersも同じ区間に使えない**。`--no-prefill-borrow`相当でstartupからown buffersを割当て、host_resをall-missとして公開するか、Prefillがcache leaseを明示的に解除できる新APIが必要。`Prefill::relayout()`はborrowed専用であり、closed cache pointerに対する救済APIではない。現行serveではloan前に`host_res`のcache-tail slotsを`kNotResident`にし、windows前に同じslotsをrefillしてresidencyを再uploadする既存境界がある (src/program/generate.cpp:4248-4254, 4310-4370, 5770-5850)。全cache retirementではこのslot-lendingを二重に走らせてはいけない。no-borrowのown buffer VRAM fitも明示 admission gateにする。

Sourceから安全な実装境界を作るなら、all-miss publication → graph/callback/queue drain → cache closeの間にreaderが無いことが要る。main `session_loop`中/Verifier window中、pending adaptive refill (`adapt_ev`/`pending`)、prefill stage ring/stager/copy、remote/peer cache paths、別GpuStageを跨ぐ状態でcloseしない。エラーやcancelが起き、checked waitが失敗したときはcache/graph/async host ownersをfreeせずrequest/processを失敗させる。Verifier windowが実行中なら`release_gpu_waits()`はhang recovery用であり健全 retirement/drainではない。ordinary/coupled MTP graphのpointer leaseはVerifier arenaを維持する限り残し、target cache restoreが完了する前にVerifier/MTP decodeを呼ばない。

## restore手順の具体化

1. 対象configを1 GPU、no remote/peer/split/adaptive swap等、最初は全cache ownerが単一のものに限定。request boundary内のprefill区間を選び、serveなら今のwindow/copy/commit operationが無い、Prefill staging/compute queueが完了した正常地点だけ開始する。
2. Serve Verifierのall-T `segments_`/`work_` (または非SYCL `exec_`)をchecked destroyしてvector/handlesをemptyにする。Verifierのstream/event/arena/final_Rは保持。`ExpertDispatch` launch callback/poolが止まり`main_cs`がsuccessfully idleの後、`native_hit_graphs`をchecked destroy/resetし、mapped host_planも戻す。`ExpertCache` statusをdecode-offにしhost/device residency all -1を公開。
3. Prefill自身のdevice buffersはcache slot loan外に所有。source `blob(layer,expert)`はmmap/resident FileExpertSource / arena sourceから復元に使えるが、「必ず全weightsがphysical RAM内」はいえない。buffer chunk/read threadはboundedとし、original source remains alive.
4. prompt完了、全prefill source/copy queues成功drain後、`ExpertCache`を同じslot sizes/bytesで再open。startupの`profile`順、slot assignment、対象blob bytesでrefillし、`sync_queued` success後にslot verificationを行う。失敗時はempty/partial cacheをpublishせず、Verifier/decodeへ進めない。
5. stable `host_res`をprofile mapへ復元し、`d_res`と各stageがある場合その`d_res`へcopy。`ExpertDispatch` cache base/blob/offを再取得。Serve `VerifyHits`の`cache_base/slot_off/n_slots`もrefresh。then `expert_hit_prepare_graphs(drive.d, main_cs, err)`でnative hit graph再capture。Verifier graphは次の`run(T)`でlazy recaptureし、capture前に更新済みhitsを使わせる。prefill中にSPが古いresident mapを読む余地がないことをassert/guardする。
6. graph recapture・profile restore完了をdecode-ready stateとして初めて公開。MTP normal/coupled graphsは維持し、既存のVerifier final_R leaseを変えない。stop/cancel、runtime sticky error、profile read/upload/capture failでは次windowを許さず、free未確定ownerを保持する。

既存sourceで再利用できるのはallocation/fill/profile iteration/graph recaptureの各部品で、state machine、checked graph destruction/drains、Verifier graph-only retirementとVerifyHits update、Prefillへのcache-disconnect、decode-ready gatingは不足している。`ExpertCache::close`のunchecked cudaFreeだけではsafety contractは満たさない。

## 条件付きbyte算術とメモリ計測の読み方

`hc*n_embd=10,240 floats/row`。FP32 residual rowは40,960 B、FP16は20,480 B。

- 64 Ki inputを65,536 rowsと解釈する条件では、全rowのFP16 allocationは1,342,177,280 B = 1,280 MiB = 1.25 GiB。R567の実観測baseline `1,960 MiB free after standalone prompt execution` がMTP675 MiB decode experts/cacheの両方をなお含む時点なら、MTPだけ解放後は理論2,635 MiBでFP16全64K residualを入れる算術余地がある。decode cacheも約260-266 MiB戻せるなら理論2,895-2,901 MiB。この計算はgraph/device allocator/workspace/chunk/conversion/headroom分をまだ差し引かず、FP16の品質許可を意味しない。
- R567の34,602 batched rowsの全RはFP32 1,417,297,920 B ≈1,352 MiB、FP16 708,648,960 B ≈676 MiB。baseline1960 MiBにMTP675+cache260-266を返せたと仮定する場合、FP32 34K full-Rは残り約1,543-1,549 MiBという単純算術で収まる可能性がある。これは34,602 input rowsと最終next-token targetの1-token差を保つ比較である。
- 256K=262,144 rowsはFP16でも5,368,709,120 B=5,120 MiB、FP32は10,240 MiB。上の2.9 GiB級回収だけでは全長residualをGPUに入れられず、host tail/streamedKV pathは必要。64Kの単純算術を256Kへ外挿しない。

基準値1960 MiBはR567の記録では**standalone prompt buffers/execution後**のfree表示で、cache/MTP既存allocationsを含む可能性がある観測値であり、この調査の現在のfree値ではない。別の表示3120 MiBはstandalone prompt buffers解放後、3057 MiBはその後VerifierとMTP bindした後。これらは異なるallocation stateなので混ぜない。特にcurrent auto cache sizingはallocation前freeをそのまま信用せず、cacheを触った後に`cudaMemGetInfo()`し、足りなければ縮小する (`generate.cpp` cache sizing around :3120-3185)。release candidateの数値は少なくともretire前、graph drain後/cache close後、residual allocate/touch後、restore/refill後でそれぞれ記録し、free値が増えた観測を残差確保成功と同一視しない。RAM source reads、restore bytes/time、graph recapture cost、first decode latency、ordinary/coupled correctnessとcancellation/fault statusも未測定。

## 過去候補の位置付けと次ゲート

過去own PR6 / pre-Xe `STRATA_PREFILL_RELEASE_CACHE`系の記録は、候補の機構/名前の参照に限定する。現root resolver/graph owners/PF loanは現在のNiko-root+SYCL統合実装で再確認が必要で、過去tree全体の復元や設定名だけの移植は根拠にしない。R567、R571-573 Main corrections、`mtp-expert-prefill-release-v1/implementation.txt`のMTP-only candidateとの併用は後段の組合せ候補に留める。

次の実装レビューで最低限見るべき点は: serveのbatched prompt直前とshort-window/decode直前を切替える位置、Prefill own-buffer admission、checked graph drain/delete failure時のowner保持、xcache profile-order exact restore、host_res/d_res/Verifier `hits_`の再公開順序、fresh/repeated/cancel/error/request-sequenceでdecode readersが古いbaseを持たないこと。実freeとrestore/recapture時間を同じrun receiptで確認するまで「約260MiB戻る」「速くなる」と結論しない。
