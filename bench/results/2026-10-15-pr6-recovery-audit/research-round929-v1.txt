# R929 — GDN, hyper-connection and PLE forward boundaries

**Purpose:** decision support; source-only algorithm audit. **Inputs:** the four supplied Strata SHA-256 pins matched exactly. I read the current `feature/sycl` layer-major path and its native16, GDN and PLE consumers; no Git command, build, test, process inspection, GPU work, profiler, product edit or XeStrata material was used. ## Finding

The exact SGLang Qwen4-Exp layer is a Qwen3.5-backbone layer: `Qwen4ExpLinearDecoderLayer` inherits `Qwen3_5LinearDecoderLayer`, then adds Qwen4 HC and optional PLE around its linear-attention branch. The model-level order is PLE addition (on configured PLE layers), HC attention read, linear attention, HC combine, HC FFN read, MoE/MLP, then HC combine. The HC reads and writes have distinct learned norm and gate parameters; the same-shaped operations are not interchangeable. The actual Qwen4-Exp GDN dispatch goes through `RadixLinearAttention` and a selected backend, so the model file alone does not guarantee a particular prefill kernel.

Strata's current layer-major native16 route has the same high-level order but exposes more boundaries: BF16 residual storage; a BF16 normalized projection view and FP32 per-stream scales; two output encodings from HC mix (BF16 for resident BF16 projections, FP16 for native quantized projections); FP32/FP16 GDN intermediate tensors and FP32 recurrent state; and an FP32-only PLE block bracketed by full residual restore/pack. Most submissions share the in-order compute queue and need no host wait between each adjacent operation; checked drains at layer/callback boundaries provide lifetime completion. A source launch boundary is therefore an extra dependency/launch, not automatically a CPU synchronization.

## Candidate order and limits

The current measured evidence does **not** rank HC, PLE and GDN service: it records a 105.007 s instrumented host-prefill interval, 60 QSA commands / 33.963 s in a 94.945 s attention envelope, 123,192 GEMM submission scopes, 0.106 s grouping and 69.696 s CPU time inside explicit GPU waits. The attention envelope is not arithmetic utilization, and no GDN/HC/PLE phase split or PMU saturation proof is supplied. The only defensible ordering below is by source-level repetition or bytes touched, not predicted speed; measure before implementation.

1. **Test native16 HC write→next norm fusion first (repeated boundary).** In each layer, the attention combine stores the BF16 residual, then the FFN HC read normalizes that same stored residual. The native16 path uses `native16::write` and `native16::norm` separately, while the FP32 path already has `gr_write_norm_rs` for eligible boundaries. A fused kernel could store the same BF16 values and reduce their *rounded* squares into the next FP32 scales in one launch. Keep the separate path where PLE/control-vector/callback boundaries intervene. Counterevidence: reduction workgroup shape and shared-memory traffic may erase the launch/save; source does not prove fusion faster. Gate on exact BF16 residual bits and exact FP32 scales before measuring.
2. **Remove the layer-1 full restore/pack only with a native16 PLE producer/consumer.** For T=8,192, the BF16 residual is 160 MiB and the FP32 view is 320 MiB; restore plus pack touch about 960 MiB of read/write traffic per chunk (not including PLE scratch). A direct path can load BF16 residual values into FP32 PLE math and round the final residual once, retaining FP32 PLE state and reductions. Counterevidence: PLE runs at one configured layer and table I/O or postops may dominate; the end-to-end bridge cost is unmeasured. Implement both batch and token fallback only after proving identical token-ordered history.
3. **Measure whether HC mix can reuse the normalized projection tensor.** It currently rereads four BF16 residual streams and recomputes scale×weight in FP32 even though `norm` materialized BF16 normalized streams for the down/up/inject projections. This is not an exact reuse today: consuming that tensor would round before the HC weighted mean. Keep the current path unless an operator comparison shows the change stays within the predeclared quality/parity gate and a clean timing wins. The BF16/FP16 dual output itself is not a duplicate to delete: current resident BF16 weights and native quantized weights call different projection contracts.

**One next experiment:** a same-queue, isolated native16 HC boundary A/B at T=8,192 plus short and non-multiple tails. Compare current `write` then `norm` against a fused store-and-norm kernel using identical captured BF16 residuals, injection and norm weights; require exact BF16 residual and FP32 scale equality, then compare repeated device service while attributing submission and wait separately. A win only advances to the ordinary clean 32K+ model comparison and actual physical 262,144-context/RESTORE checks; it is not a speed or adoption claim by itself.
