# Prefill GU/dequant hot-path research — Round 610

Date: 2026-10-15 JST. Read-only investigation for the Niko1221/Strata personal SYCL fork, Arc B570 10 GiB / Ryzen 5 5600X / 128 GiB RAM. Only this report is written. No source edits, builds, tests, CPU/GPU runs, profiler/process/service inspection, cleanup, or Git mutation.

## Finding

The active compact FP16 prefill fallback fully expands each expert's packed native GU and Down tensors into rotating FP16 scratch, then calls oneMKL GEMM. Its actual dequant work is concrete and sizable: the current profile records 91,880 `iq_dequant_gu_f16` launches totaling 22.4007 s and 94,580 generic `dequant<unsigned short>` launches totaling 12.0643 s. The combined 34.465 s is the sum of profiler kernel durations across the full startup/prefill/decode process; it is not exclusive prefill wall time or critical-path time. The request's 34,603 input / 128 output Direct=1 run, profile identities and limitations are recorded in `model-device-profile-v2.json` and `prompt-direct-profile.ja.md`.

Two distinct candidates merit source-level evaluation. The first, higher-value candidate is a packed-native expert product path that decodes weight values directly into XMX/GEMM tiles, avoiding the full FP16 weight materialization. The existing branch has useful building blocks, including a packed native fused expert kernel for a narrower streamed/MMQ case, but the observed fallback does not select it. The second is a format-specialized SIMD unpack kernel for the current FP16 materialization route, parallelizing codebook unpack/dequant across lanes and vectorizing FP16 stores while preserving the same staging and oneMKL GEMM. It is a smaller dispatch-local experiment and should serve as the fallback if the direct packed matrix prototype cannot cover the empirical route shapes safely.

The already-authored R566 GEMM+SwiGLU epilogue fusion is a separate candidate. I do not restate it here. GEMM orientation, grouped-GEMM API reuse, CPU expanded-weight cache, QSA/head tiling and generic GEMM replacement are also outside these two new candidates.

## Actual SYCL dispatch and current cost

The relevant caller is the non-`use_mmq` expert callback in `src/prefill/prefill.cpp:2808-2891`. For native GGUF layers it calls `iq_dequant_gu_f16(type, gate, up, n_ff, n_embd, dq_gu[q], queue)` followed by `iq_dequant_f16(down_type, down_blob, n_embd*n_ff, dq_d[q], queue)`. It then gathers routed activation rows to compact row zero when compact FP16 is enabled, runs `Gemm::f16(X, dq_gu, GU, ne, 1280, N)`, runs `swiglu_interleaved(GU, Hh, ne)`, and runs `Gemm::f16(Hh, dq_d, Dm + expert_offset*N, ne, N, 640)`. `DQ=2` scratch buffers rotate; this bounds scratch residency but does not avoid re-decoding weights at the next call. Same in-order queue ordering is used, with no per-call host wait (`include/strata/sycl/launch.hpp:47-63`).

The profile's source is revision `a4d27df2`; its workload is 34,603 input tokens and 128 generated tokens, 4,096-token prefill chunks, int8 KV, 32,768 resident KV, and normal MTP4. Direct=1 changed attention timing but left GU and generic-dequant totals essentially the same as Direct=0. Both profile arms are instrumented one-process diagnostics, not clean speed comparisons. The measured attention GPU duration changed 44.0661 to 29.8050 s; this is context only and does not establish how much of the 34.465 s dequant duration is on the prefill critical path.

The model is width `N=2560`, expert intermediate `FF=640`; packed GU is two `[640,2560]` matrices (gate and up), and Down is `[2560,640]`. Current half outputs per routed expert call are therefore:

| Object | FP16 elements | Bytes written by current dequant |
| --- | ---: | ---: |
| GU (gate + up) | 3,276,800 | 6,553,600 (6.25 MiB) |
| Down | 1,638,400 | 3,276,800 (3.125 MiB) |
| Combined | 4,915,200 | 9,830,400 (9.375 MiB) |

The routed-FP16 census records 90,297 active expert calls per role and 16,588,800 rows per role for its 34,560-batched-token / nine-chunk case. Applying the dimensions above gives about 887.8 GB of logical FP16 dequant output over those calls (decimal GB). Dividing by the current profile's 34.465 s duration sum gives about 25.8 GB/s of logical output per accumulated kernel-second. This is an arithmetic exposure indicator only: the census and profile are separate receipts, profiler durations are aggregate device-kernel intervals, and logical writes do not prove physical DRAM traffic or process critical-path bandwidth. The packed reads are approximately 1.5–2.2 MB per expert in the recorded seven format pairs; actual traffic can be lower through caches and is not measured here.

Native format support on this model is GU types 18 (IQ3_XXS), 22 (IQ2_S), 21 (IQ3_S), and 23 (IQ4_XS); Down types are 20 (IQ4_NL) and 42 (Q2_0). This is source/model-ledger-derived for the current seven observed format pairs, not all-type coverage. `include/strata/sycl/gguf_decode.hpp` maps these formats to scalar GGUF decoders. `src/kernels/sycl/iq.cpp:19-37,118-145` launches one work item per 256-weight block for GU and one per block for generic dequant; each work item materializes `float values[256]`, invokes the scalar block decoder, then stores the 256 values as FP16. This is exact candidate locality: packed decode, not GEMM orientation, is the code executed by these profiled kernel names.

## Candidate 1 — packed-native decode inside the XMX matrix tile

Use a dedicated native expert GEMM path for current compact-fallback calls so each tile reads packed IQ3/IQ4/IQ2/Q2 blocks, unpacks codes/scales into local/register matrix operands, and multiplies them without writing and rereading a whole FP16 weight matrix. At first, restrict to current model's exact GU/Down format pairs, `N=2560`, `FF=640`, compact mode, one-GPU/no-peer execution, and measured `ne` shapes. Keep the existing FP32 accumulated GU and Down outputs and FP16 SwiGLU boundary. Compare against the current path for GU and Down separately; preserve exact GGUF codebook/scales and treat floating-point order changes as a numerical change requiring explicit gates.

There is a relevant existing path in this fork: `src/prefill/sycl/moe_fused.cpp:284-301,367-411` already has native packed expert handling for GU 16/17/18/21/22/23 and Down 20/42, and decodes 32-element integer units from packed blocks in `unpack<T>` rather than creating an FP16 matrix. Its public caller is restricted by current `fused_nat` dispatch to `use_mmq && stream_all && !peer && native_supported`; the main compact callback above is a separate fallback. Reuse or extend this local format-specific logic only after auditing its Q8 activation quantization, row-grouping, tile accumulation, workspace and output semantics against the FP16 route. It is not an existing exact replacement: it currently quantizes activations and computes the whole grouped layer, and its non-FP32 arithmetic/rounding contract differs from the fallback. This candidate may become an XMX tile kernel instead of reusing the existing integer-dot kernel if quality/shape gates show that necessary.

Independent reference evidence is unusually direct. At pinned llama.cpp commit `a0e6dc7384edb8f5d927155e1d26c10b4a310e6d`, its SYCL backend documents XMX gather paths that dequantize supported packed weights straight into XMX tiles, including IQ3_S, IQ3_XXS, IQ4_XS and multiple IQ2 variants. Its documented gates include selected weight types, supported `joint_matrix` shapes, row-length divisibility and a <=64-token per-expert batch limit; unsupported shapes fall back to standalone dequant plus library GEMM. This establishes an implementation pattern and an eligibility boundary, not performance or numerical parity for Strata's B570 build. IntelLabs/Xe-Fuse at pinned commit `290604bfc6f738d4931bb475d82c1891e8bab67d` supplies XMX/SYCL-TLA GEMM and SwiGLU epilogues, but its published MoE examples do not prove support for these GGUF IQ layouts or this route schedule.

**Exact initial eligibility and gates.** Enable only when `lay.native`, one of the recorded format pairs, `!use_mmq` fallback branch, compact FP16 active, `N=2560`, `FF=640`, peer path disabled, and `1 <= ne <= 64`, plus row/inner divisibility and device matrix-combination admission established by the chosen tile. Log source-level decline reasons in the fixture; do not silently alter fallback selection. `ne>64` stays on the current code at first. The census establishes that small calls are common: `ne<=16` is 55.13% of calls but only 1.386% of routed rows; R563 reports p50=12, p90=428, p99=3,245, max=4,096. Thus this 64-row path needs row-weighted reporting and cannot be credited with covering most arithmetic without the exact histogram below 65. For a later larger-M path, solve batch scheduling/resource limits rather than inferring coverage from the <=64 result.

**Resource implications.** The direct tile avoids at least 9.375 MiB of FP16 weight-output writes and same-sized GEMM operand reads per expert call in logical address space, but it adds integer unpack, codebook/scale loads, XMX operand staging, and register/SLM pressure. Tile size, format-specific lookup tables and concurrent accumulator tiles determine occupancy. The B570 has 10 GiB device memory, but a persistent full expanded-weight cache is not recommended: one expert's expanded GU+Down is 9.375 MiB; the model has 48 layers and 512 experts/layer, so full cache expansion would be roughly 225 GiB. Even 128 expanded experts per layer would exceed 56 GiB. Any persistent subset would compete with the existing packed resident expert cache and buffers; measure bytes and eviction/coverage before considering it. Register and SLM consumption are unknown until compiler/device resource evidence exists.

## Candidate 2 — parallel format-specialized SIMD unpack into existing half scratch

Keep the current `iq_dequant_gu_f16`/`iq_dequant_f16` interface and scratch lifetimes, but add specialized device kernels for the exact active type pair set. Instead of one work item decoding all 256 values through a local float array and then storing them, assign a subgroup or a small lane group to packed subgroups/values: load packed words once, vector-extract indices/signs/scales, table-lookup the IQ grids, apply scale, convert to FP16, and issue aligned/coalesced half stores. For IQ3_S/IQ3_XXS and IQ4_XS, specialize their packed group structure; use separate variants for Q2_0 and IQ4_NL Down. Retain the scalar decoder as fallback for unsupported or irregular types. The caller eligibility can be exactly the current `lay.native && !use_mmq` branch with compact FP16 and the same `N/FF`; unlike candidate 1, this covers every current `ne` because weight dequant dimensions do not depend on routed row count.

This targets the actual `float[256]` decode and serial per-block control work and reduces instruction/temporary pressure; it does not eliminate 9.375 MiB per-call logical expansion. It is lower risk than a new GEMM because it preserves the existing FP16 operands, oneMKL dispatch, queue sequence, and accumulation order. It may still lose if subgroup shuffles/table gathers cost more than the existing scalar block decoder or if large per-item state currently stays in registers. No speed claim is justified from source alone.

**Numerical and layout gates.** Compare every output element against `decode_block` + existing `f16_from_f32` for all supported types, with random and adversarial codebook indices, signs, extreme/zero scales and NaN/Inf source behavior according to the actual GGUF contract. Check unaligned valid block rows only where source layout permits, first/last block, guard bytes and exact row stride. The parallel implementation must keep one logical owner per output, avoid writes crossing block-row padding and preserve the exact per-element FP32-to-FP16 conversion; no reduction/reassociation is required. Then compare dequant buffers and full expert outputs on all seven observed format pairs and empirical `ne` histogram. Record launch count and per-kernel duration without verbose trace; keep clean host-submit and drained device interval separate.

## Comparison, floors and ranking

The current whole-kernel duration sum gives 34.465 s for both current dequant kernels, with a logical output volume of about 887.8 GB if the census's 90,297 paired expert calls are used. The absolute idealized removal ceiling for any dequant optimization is less than that aggregate duration, and end-to-end prefill improvement is strictly lower because GEMM, SwiGLU, routing, copies and other work remain. This ceiling does not assign an exclusive wall-time share. The task's reported 22.4 s GU + 12.06 s generic-dequant figures should be retained as profiling evidence, not modeled as additive critical-path savings. For a direct tile candidate, a more meaningful bound is per-call eliminated traffic (9.375 MiB write plus the later corresponding GEMM read) and coverage-weighted potential; no B570 bandwidth conversion is warranted until physical memory traffic and a same-process device profile are available. Do not multiply by the board's advertised 380 GB/s as if it were achieved bandwidth.

Rank 1: a bounded packed-native tile prototype for `ne<=64`, using the current source's native format decoder and the llama.cpp XMX-gather precedent. It has the largest potential reduction in actual bytes and may cover many launch calls, but resource pressure, quality differences, and row-weighted coverage are unmeasured. Start with a standalone correctness/performance microfixture, then add only if it beats existing `fused_native` and current compact fallback on identical weights and activations.

Rank 2: format-specialized SIMD dequant-to-half. It has lower potential because it preserves full materialization, but straightforward exact FP16 parity and broad `ne` coverage make it the preferred fallback experiment. Compare by format and bytes/sec; accept only if the full-call benefit including launch and downstream GEMM is repeatable.

A third idea, persistent FP16 expert caching, ranks below both and should not be the next implementation: the expanded model exceeds VRAM by an order of magnitude, and existing packed expert residency would be displaced. Full GPU cache, all-GU CPU cache, generic GEMM swap, and grouped GEMM are not supported by the current cost evidence as the next change.

Measure scratch bytes, registers, spills, SLM, occupancy/admission, logical bytes, host submit and completed-batch duration; keep correctness and timing arms separate.
4. Candidate 2 microfixture: compare scalar and SIMD dequant variants for all formats and representative matrix extents; measure duration, register/spill and effective logical output rate. Keep oneMKL and queue setup identical.
5. Only a candidate passing correctness and the microfixture advances to paired clean model prefill and exact first-logit/output checks. Use the same 34,603-token / 128-output job and existing clean benchmark protocol, full input/actual chunk sizes, same binary except opt-in, identical model/cache/MTP settings, OFF/ON separate processes, individual samples, and fresh fault checks. Preserve prefill and decode as separate outcomes. No adoption based on unitrace aggregate alone.
