# R966 — feasibility of a 16K native16 MoE window over 8K causal chunks

## Scope and conclusion

Decision support, source-only. The scope pins `src/prefill/prefill.cpp`, `src/prefill/layer_major.inc`, `src/prefill/sycl/native16.cpp`, `src/prefill/sycl/gemm16.cpp`, `src/prefill/sycl/postops.cpp`, and `include/strata/prefill/layermajor_shape_census.hpp` all match their recorded SHA-256 values (6/6). The assignment labels source revision `2b357a8a14be9e10d5909591cc7f72a15c69046d`; no Git command was used, so this validates content identity, not the revision’s commit metadata. Provenance is the pinned Strata tree itself; no outside implementation, XeStrata material, build, test, or runtime data was used.

A 16K MoE window is feasible as a separate scheduling capacity while GDN/QSA remain two ordered 8K operator calls. There is no causal dependency from a layer’s later-token attention result to that same layer’s earlier-token FFN result. The current routine interleaves attention and MoE, compact-MoE bounds are tied to `m.T`, and callbacks publish each completed 8K chunk. Keep `T_op=8192` distinct from `W_moe=16384`; widening `m.T` is unsafe. The smallest viable boundary is a two-pass layer window: run causal attention and HC write for each 8K piece, save post-attention residual rows in the existing layer-major bank, then prepare/execute MoE for the window and publish ordinary 8K callbacks only when both outputs are final. The dispatcher keeps `n<=m.T` on the original short path (`layer_major.inc:14-29`).

## Current native16 path and invariants

`run_layer_major` admits `m.T<=8192`, and QSA16 validation receives `m.T`; `run_impl` loops in `m.T` pieces. Each piece fills position steps, performs GDN recurrence or QSA append/indexer/select/attention, then HC attention write, HC FFN read, router, shared expert, routed experts, combine and HC FFN write (`layer_major.inc:93-104, 160-195`; `prefill.cpp:1844-1850, 2005-2012, 2304-2343, 2679-2717, 3374-3439`). QSA appends keys and pooled indexer rows before per-query selection; QSA’s completed blocks and current dead tail are distinct. GDN recurrence/conv state and PLE history also advance in token order. Both operator chunks must therefore run at their original positions in ascending order, committing each state update before the next; do not batch QSA/GDN over 16K or change their guards.

Native16 has several different 16-bit tensors. `R16` and `gated_b16` split the old FP32 `gated` reservation; `lo_b16`, `bo_b16`, `GU_b16`, `Dm_b16`, `sgate_b16`, `sup_b16`, and `shared_b16` reinterpret existing FP32 allocations (`prefill.cpp:947-955, 1007-1012`). HC norm keeps FP32 row reductions/scales; `native16::mix` produces BF16 `mixed_bf` for the router and FP16 `mixed_h` for expert GEMMs; injection is FP32 and shared scalar gate `sg` is projected from `mixed_bf` into FP32. Shared expert output is BF16. Expert down GEMMs accumulate locally in FP32 and store BF16 `Dm_b16`; `native16::combine` loads those BF16 values and uses FP32 FMA in token top-k slot order, then adds `shared_b16*sigmoid(sg)` and rounds once to BF16 (`native16.cpp:59-88, 98-123, 141-158`; `gemm16.cpp:206-241`). This native numerical contract is distinct from a wider FP32 expert-output tensor.

Routing currently emits IDs and weights per operator chunk. Host grouping sets `slot_h[i]=p` (logical token/top-k slot to expert-major result row) and `src_h[p]=i/K` (expert row back to token); it uploads `slot_dev` and `src_dev`, while `w` stays in logical slot order (`prefill.cpp:2808-2885`). A window must preserve both maps and weights through combine. For bounded per-expert gather, `src_dev` can be refilled for one expert at a time; it need not hold all window routes. Concatenate IDs on the host (or maintain equivalent expert lists), and form one window-wide slot map after both chunks’ histograms are known.

Callback ownership is a hard boundary. The native16 callback synchronizes the queue, accepts strictly ascending `m.T` row spans, stores intermediate BF16 rows, and restores FP32 only at the final layer; the final stage callback is delivered once after the last chunk. Restore restores borrowed fields and callbacks, not already-updated session tensors (`layer_major.inc:353-383, 543-550, 608-660`). A 16K window must not expose a first-half checkpoint. After MoE/write finishes, issue two normal 8K callbacks in order (or one correctly sized tail callback). A cancellation/fault after causal state advances but before FFN commit is not a completed boundary; failure handling must prevent reuse as a valid checkpoint/RESTORE state.

## Exact window payloads and reuse

The following are raw tensor payload bytes for the expert-compute peak at `W=16384`, with one expert’s `ne<=W` rows in bounded scratch. The source’s compact path currently rejects `cnt[e]>=T`; it must become a window bound that allows equality at `ne=W`. `Xs` and `Hh` must be sized to W rows. Do not expand the QSA/GDN operator shape to achieve this.

| Simultaneously live owner | Formula at W=16384 | Bytes |
| --- | ---: | ---: |
| retained `mixed_h` (FP16) | W×2560×2 | 83,886,080 |
| slot-order expert outputs `Dm_b16` | W×10×2560×2 | 838,860,800 |
| shared output (BF16) | W×2560×2 | 83,886,080 |
| expert input gather `Xs` (FP16) | W×2560×2 | 83,886,080 |
| gate/up `GU_b16` scratch | W×1280×2 | 41,943,040 |
| expert hidden `Hh` (FP16) | W×640×2 | 20,971,520 |
| weights + slot map | W×10×(4+4) | 1,310,720 |
| scalar shared gate + HC injection (FP32) | W×4 + W×4×4 | 327,680 |
| one-expert source map | W×4 | 65,536 |
| **slot-order live payload** | sum above | **1,155,137,536** |

By phase, post-attention residual adds 0 B only when the existing row bank is reused (otherwise +335,544,320 B). After routing/shared preparation, retained mix + shared + weights/slots + `sg` + injection is 169,410,560 B. Slot-order expert peak is the table; combine/output owners total 1,008,271,360 B (`Dm` + shared + maps + `sg` + injection + `bo`, reusing the mixed-input span). The accumulator expert peak is 567,934,976 B.

This is the MoE live payload; session/cache/residual owners and the existing arena are additional. `mixed_h` can be retained in the existing `bo_b16`/embedding reservation only if the two-pass schedule has finished attention: its 8K FP32 backing has exactly 16K BF16 capacity, and combine may overwrite it after the last expert read. The 8K layer-major residual bank can likewise hold post-attention rows in place after that piece’s input has been consumed; final FFN rows overwrite them only after combine. Neither reuse is implemented today. Without residual-bank reuse, one separate BF16 post-attention window costs another 335,544,320 B. Host-resident rows also add a read/write round trip per piece.

The allocation aliases are useful but must be interpreted by storage width. At `T_op=8192`, the actual BF16 `Dm_b16` tensor is 419,430,400 B, while its FP32 `m.Dm` backing reservation is 838,860,800 B. At W=16K, BF16 `Dm_b16` needs exactly 838,860,800 B, so it can occupy that old reservation; this is not an 8K BF16 tensor of that size. Similarly W-sized BF16 `GU`, shared, shared gate and up outputs fit their 8K FP32 backing byte counts. The per-expert `Xs/Hh` compact capacities do not: grow them by 41,943,040 and 10,485,760 B. Extending W-sized `w`, `slot_dev`, `sg`, and `inj` adds 327,680, 327,680, 32,768, and 131,072 B respectively. Total arena growth is therefore 53,248,000 B, excluding host vectors. R965’s exact 8K compact MoE inner count is 1,087,671,808 B versus a 1,180,698,624 B GDN region; this extension leaves 39,778,816 B before the existing region limit. It fits the old 8K region on that source arithmetic, so the top-level 8K arena remains 2,311,569,920 B, but the custom layout, alignment, and actual runtime allocator still require Main’s review. `src_dev` already has 81,920 int entries at 8K, more than one expert’s 16,384; host IDs/maps need up to 655,360 B per W-sized array, with a second expanded host map another 655,360 B if both IDs and slot map are retained.

An alternative uses a W×2560 FP32 accumulator (167,772,160 B) and a reusable BF16 down-output tile for one expert (up to 83,886,080 B), accumulating weighted outputs in expert completion order. Including the other live owners, its payload is 567,934,976 B. It can reuse the old 838,860,800 B FP32 Dm backing by partitioning it into accumulator and BF16 tile; these are simultaneous subranges. For accumulation, per-expert `src_dev` must carry flattened `i=token*K+k` so each output uses `w[i]`; current `i/K` is insufficient. The sum order changes from top-k slot order, so it is not bitwise equivalent. Keep shared addition last and qualify it separately.

For comparison, the same payload formula for the existing compact 8K schedule is 577,568,768 B. Thus the slot-preserving W schedule doubles its retained MoE payload; the accumulator schedule stays near the 8K payload while reducing the result plane. Neither figure predicts latency or free VRAM. Expert-major outputs and shared outputs remain simultaneous until combine; router logits, per-chunk HC projection temporaries and QSA/GDN scratch are phase-local and reuse the arena, while expert inputs/maps and residual owners survive their relevant phase.

## Request and physical-context accounting

For 39,261 rows at `pos0=0`, operator pieces are `8192,8192,8192,8192,6493`; MoE windows are `16384,16384,6493`, and the final callback remains 6,493 rows. The BF16 residual owner is 804,065,280 B. R965 counted a 1,363,148,800 B expert cache, 80,726,784 B BF16 QSA prefix, 2,311,569,920 B 8K arena, and 536,870,912 B headroom: 5,096,381,696 B before model/session owners. This candidate adds no top-level arena bytes under the stated reuse/margin conditions; add host route vectors or any separate residual shadow. The snapshot is not current admission.

At physical `max_cells=262144`, process sixteen independent 16K MoE windows over thirty-two 8K causal chunks. The BF16 full-request residual owner is 5,368,709,120 B across the selected device/host plan. For Mode0 INT8 QSA, K/V codes and scales are 12,672 B per physical cell across twelve layers, or 3,321,888,768 B; the exact twelve QSA state allocations are 3,794,839,072 B including primary RoPE, pooled indexers, page tables, steps and guards. GDN recurrent plus convolution state is 117,669,888 B. These three persistent owners total 9,281,218,080 B before QSA work buffers, session PLE/block buffers, expert cache, prefill arena, weights and runtime headroom. If the BF16 prefix option is enabled, its 2 tensors plus flags add 2,056×262144 = 538,968,064 B. This is an accounting boundary, not a fit claim; the R965 65K-context free-memory observation cannot qualify physical 262K.

## Decision evidence and gate

Prefer the slot-order version first if a 16K window remains within measured allocation/headroom and shows lower whole-request wall time over repeated paired 8K/16K runs. Capture per-window expert `ne` histogram/union, route rows, dequant/GU/down work, and host grouping/route-exchange time; profile GPU completion separately from CPU submission and wait. Include host/device residual bytes and copy/drain time, cache traffic, allocations/high-water and faults. A new shape census must prove `ne<=W`, route conservation, slot/source map bounds, ascending 8K QSA/GDN positions, 262144 endpoint coverage, correct 6,493-row request tail, and two ordered callbacks per full window. Compare same-binary 8K and 16K runs with unchanged short-input/decode path and retain current FP32 diagnostics.

The slot-order candidate must match the 8K native16 reference at router IDs/weights, BF16 expert outputs, combine output and final boundary within its declared rounding contract, with GDN/QSA/PLE state and callback/checkpoint checks passing. The accumulator candidate additionally needs logit/NLL and task-quality evaluation because completion-order FP32 additions differ. Adopt neither from arithmetic alone: require repeated whole-request improvement, no new runtime faults, and actual physical-context memory admission with headroom. The bounded recommendation is a 16K MoE window over two unchanged 8K operator chunks, first retaining native BF16 outputs and slot order; if it does not fit under the measured full owner set, test the accumulator as a separately qualified numerical design.
