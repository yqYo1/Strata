# R783 — Typed-16 prefill producer/consumer kernels

Date: 2026-10-16. Purpose: decision support for a true FP16/BF16-producing prefill path with FP32 accumulation. This was a read-only source/documentation review: no Git commands, product edits, builds, tests, GPU work, profiling, process inspection, or environment changes. Prior context checked: the R674 boundary-storage contract and Main’s R671–675 corrections. This report addresses producer output and its immediate consumer, not another residual-only cast proposal.

## Finding

The best first prototype is an owned SYCL `joint_matrix` kernel for one high-volume prefill GEMM, with FP16 inputs, an FP32 accumulator, direct FP16 output, and a typed-16 consumer. The Intel joint-matrix specification describes an FP16 A/B, FP32 C accumulator, FP16 D output combination on BMG-class XMX devices. It has a clearer precision contract than the oneMKL API and avoids bringing in a PyTorch extension. Gate the path on the running device’s advertised matrix combination and retain the existing FP32-output route as the default/reference.

oneMKL has a documented API signature for 16-bit output, but the public GEMM contract reviewed here does not specify its internal accumulator type. The existing vLLM XPU grouped GEMM source explicitly combines FP16/BF16 output with a `float` DPAS accumulator, but it is a Torch/CUTLASS grouped-MoE implementation, not a drop-in Strata GEMM. Intel LLM Scaler also has genuine typed-16 ESIMD producer/consumer examples; the traced FP16 examples are decode-oriented GEMV/norm paths, not long-prefill GEMM replacements.

## Candidate kernel/API contracts

**Current Strata seam.** `src/prefill/sycl/gemm.cpp:19–33,93–104` accepts 16-bit input and weights, validates a four-byte-per-output `float*`, and calls oneMKL. `Prefill::compute` calls this for the routed MoE gate/up projection at `prefill.cpp:3077`; `postops.cpp:224–230` then reads interleaved gate/up as FP32, computes SwiGLU in FP32, and writes FP16 Hh. Down GEMM consumes Hh and writes FP32 Dm (`prefill.cpp:3078–3083`). Thus there is a concrete intermediate worth changing: the gate/up FP32 buffer is written and read between two already-16-bit endpoints. A `Gemm` call that writes 16 bits followed by the current float-pointer SwiGLU is not enough; the consumer must also accept 16-bit input.

**Existing XPU grouped GEMM.** The public `cutlass_grouped_gemm_xe2_impl` / `MoEGEMMLauncher` path in `vllm-xpu-kernels` is the strongest precedent for a real output-16 GEMM. Its launcher instantiates `XE_DPAS_TT<8, float, ElementA>`; the W16A16 calls pass the same FP16 or BF16 `scalar_t` as both A and D/output. Its grouped interface accepts per-expert row counts and a dense grouped output, and the source describes itself as a BMG MoE API example. This is explicit FP32 accumulation with a typed-16 global store. However, it expects a Torch XPU stream/tensors, CUTLASS/CuTe and the project’s grouped-MoE shape/data layout. Strata currently dequantizes its IQ weights into two rotating FP16 buffers and invokes oneMKL per active expert; retaining/grouping all expert weights and adding the Torch/CUTLASS interface would be a substantial port. Use this as a precision/layout reference, not as a drop-in library or a measured B570 result. The cited interface file carries Intel’s BSD-3-Clause notice; the repository root is Apache-2.0, so any direct adaptation has separate attribution/notice obligations to resolve against Strata’s MIT file policy.

**oneMKL typed output.** The current oneMKL 2026.0 `gemm` table documents `sycl::half × sycl::half → sycl::half` and `oneapi::mkl::bfloat16 × oneapi::mkl::bfloat16 → oneapi::mkl::bfloat16`, alongside FP32-output variants. For the FP16-output overload, alpha/beta are also `sycl::half`; the BF16-output overload uses float alpha/beta. This is a credible low-footprint API experiment because Strata already links oneMKL and uses its FP16-input/FP32-output form. But the table and function signatures specify input, output, and scalar types—not the accumulation type—and offer no `accumulation_type` parameter for these combinations. They therefore do not satisfy the requested FP32-accumulation evidence by themselves. Do not label the candidate FP32-accumulating until the exact oneMKL implementation/backend is evidenced; a queue and a type signature alone do not establish either device execution or the internal accumulator.

**Intel LLM Scaler trace.** The checked wrapper chain for `esimd_gemv_fp16` is Python `ops.py` → registered Torch op in `torch_extension.cc` → `esimd_kernel.sycl::esimd_gemv_fp16` → `GEMV_fp16_host` in `fp16_GEMV.h`. That kernel loads half, widens to `simd<float>`, reduces FP32 partials, then writes `fp16`. The fused norm example is Python `ops.esimd_norm_gemv_norm_fp16` → Torch registration → `esimd_kernel.sycl::esimd_norm_gemv_norm_fp16` → `NormGemvNorm_fp16_kernel`; its RMS statistic and router dot are float, while router logits and normalized MoE input are stored as FP16. The vLLM patch enables that fused path only for a batch of one. These are actual producer/consumer APIs rather than casts, but their single-row/small-batch decode layouts and per-output GEMV work are a poor match for large routed prefill GEMM. The ESIMD extension also depends on PyTorch’s `SyclExtension`, ATen, and XPU stream. The LLM Scaler repository is Apache-2.0. Do not import its wrapper or kernel into Strata unchanged.

**Owned `joint_matrix`.** Intel’s SYCL matrix-extension table separates accumulator type C from output type D and lists FP16×FP16 and BF16×BF16 with FP32 C and 16-bit D on BMG G21/G31 XMX, among other architectures. The extension exposes the matrix multiply-accumulate and store operations needed to keep the accumulator float while storing the result directly in FP16/BF16. It is experimental and shape-specific: query `device::matrix_combinations` and select an advertised tuple/tile at runtime; handle ragged M and strides explicitly. The current Strata GEMM dimensions (`N=1280`, `K=2560`) are multiples of 16, while active-expert M varies, so the final M tile needs a checked mask/pad or a fallback. This is the clearest precision contract, but it still needs a real kernel and exact-device verification; no speed is implied.

## Recommended integration boundary

Start with FP16 on the routed gate/up projection only. Add a separate, default-off prefill kernel entry for A/B FP16 → FP32 accumulator → FP16 GU. Add `swiglu_interleaved_f16` that reads two FP16 values, widens them locally for the existing FP32 sigmoid/product, and writes the existing FP16 Hh buffer. Keep the down projection’s FP32 Dm output, FP32 residual/norm route, current `gemm.f16` overload, and decode path unchanged. This yields a genuine typed producer-consumer pair and preserves the existing implementation as the oracle. It intentionally rounds GU before SwiGLU, so it is a numerical change even though the GEMM accumulator remains FP32. Do not describe it as merely a storage cast.

BF16 is a separate candidate: current compact-MoE activations and dequantized weights are FP16, so emitting BF16 requires an explicit input/weight representation decision as well as a BF16 output and consumer. Both formats use two bytes; there is no source evidence here to prefer BF16 or FP16 for this model. Norm and residual producers should be deferred until their immediate consumers are mapped; the existing `image()`/audit hooks that optionally write 16-bit side buffers do not make the FP32 result a typed producer.

An owned kernel avoids a PyTorch dependency and copied upstream code. If a future source adaptation is proposed, pin the exact source, retain its license and notices, and review the complete diff before integration. New Strata implementation files must follow the repository MIT license; this review does not grant adoption approval for third-party source.

## Constraints and bounded validation

Intel’s B570 product page identifies Xe2/Battlemage and XMX hardware; the joint-matrix spec includes BMG-family combinations. That establishes architectural relevance, not the active B570 driver/compiler’s support for the needed FP16/BF16 C/D tuple. Intel LLVM issue #22926 recorded an empty matrix-combination list on a Battlemage G31 using DPC++ 2025.3.3 even though the spec listed it; the issue was closed after maintainers noted BMG support had landed later in the compiler. It is a version-specific caution, not evidence that this B570 or the indexed DPC++ 7.1.0-pre stack fails. Before dispatch, query and record actual device name, runtime/driver/compiler versions and the exact supported tuple. Fall back unchanged if absent.

A concrete next experiment is a paired, default-off component run on the real long-prefill routed gate/up call shape, `M=ne, N=1280, K=2560`. Compare existing oneMKL FP16-input/FP32-output GU plus current SwiGLU against the joint-matrix FP16-output GU plus typed consumer, using the same preallocated buffers, routed-row order, expert IDs and queue. Cover the active `ne` distribution including 1, tile-boundary M values, and final partial tiles; validate bounds, output finiteness, router/order identity, output max/relative error, and fault-free queue closure. Attribute time to the complete GU→SwiGLU→Down dependency, not GEMM submission alone, and retain the FP32 arm bitwise. If the exact device tuple is absent, stop this candidate and record the fallback rather than attempting emulation. If the component passes, Main should use matched natural long-input controls to measure teacher-forced NLL/task quality and whole-prefill throughput before considering adoption; retain physical 262144-context and RESTORE checks as later release gates. CUDA/HIP remains outside scope.
