# R755 — oneMKL batching and SYCL graph limits for long-prefill expert submissions

2026-10-16 JST. Read-only documentation/source research. Only this report was written. No build, test, compiler, runtime, GPU, profiler, process, environment, service, Git, or cleanup operation was performed. No XeStrata source or derived material was read or used. The active Main diagnostic was not touched.

## Finding

There is a plausible oneMKL submission-coalescing path between today's per-expert GEMM calls and a fully device-driven expert engine: the official DPC++ oneMKL `gemm_batch` API has a USM group form that accepts pointer arrays and groups with per-group dimensions and sizes. In principle, after host grouping has produced `cnt`, `off`, and expert order, experts with equal `ne` can be placed in a group and their corresponding GEMMs submitted in one call per group, per projection. This can lower host-side oneMKL API-call count without padding every expert to `T` rows.

This does not remove R754's CPU-controlled boundary. `group_count`, `group_size[]`, dimensions, and matrix-pointer lists are host call arguments; the documented interface has no device-resident count/list dispatch. The host must still complete/read routing metadata and prepare these arrays. Grouping by exact row count may leave many small groups when the 512 expert counts vary. The effect on library setup, runtime submissions, kernel launches, and critical-path time is unknown. The appropriate conclusion is a measurable candidate for reducing submission overhead, not a GPU-local scheduler.

Descriptor reuse has a narrower role. Dimensions, transpose flags, leading dimensions, and type/layout are stable for a layer-major chunk, and the 512 weight slots are resident; host arrays for those stable fields/pointers could be reused or refreshed. But each request's active expert order, offsets, and row count vary with routing, and weights change by layer. The oneMKL GEMM API documented here is a stateless call interface, not a persistent compiled GEMM plan/descriptor object whose dynamic M values it can read from device memory. Do not assume that retaining host descriptors removes per-chunk host preparation or queue submission.

## Batched-GEMM feasibility and costs

The inspected Strata route issues two `m.gemm.f16(...)` calls for each active expert, with `ne=cnt[e]`; it gathers compact rows into reusable scratch, runs SwiGLU between projections, and writes each expert's down projection to its offset range (`src/prefill/prefill.cpp`, around lines 3029–3063). The oneMKL group interface can represent different group sizes and different M dimensions across groups, and pointer arrays can name noncontiguous A/B/C matrices. Therefore equal-`ne` experts are structurally batchable at the BLAS-call level after their compact inputs and weights are ready.

There are important dataflow changes behind that call reduction. The current loop reuses per-expert scratch because experts run serially. A single first-projection batch needs distinct output storage until all first projections finish; SwiGLU can then cover those rows, followed by a batched down projection. If materialized for all routed rows in a chunk, the two FP32 buffers sized for GU (1280 values/row) and Hh (640 values/row) require `T*K*(1280+640)*4` bytes. At `T=8192`, `K=10`, this is **629,145,600 bytes (600 MiB)**, before pointer metadata or alignment. This is a derived capacity estimate, not a measured allocation. It is a meaningful cost under the documented 10 GiB device-memory ceiling; current scratch is reused across experts and does not imply this extra capacity is free. Batching only subsets could reduce storage but introduce more host batches/calls or intermediate dependencies.

Under the corrected 78,452-row request geometry, R754 estimates at most 245,760 expert iterations over 480 layer/chunk boundaries and 491,520 per-expert GEMM API calls across two projections. Grouping equal M could reduce those BLAS calls, but the count reduction cannot be quantified without actual router `cnt` histograms. It does not automatically remove oneMKL internal kernel count, row gathers, SwiGLU work, host list assembly, or graph synchronization. These source-level counts are not timing evidence.

The inspected local `gemm.cpp` wrapper calls ordinary `oneapi::mkl::blas::row_major::gemm` for each operation and waits via `finish(stream,event)`. It contains no batch API or reusable GEMM descriptor. This is a source observation, not a statement about other active builds or hidden runtime behavior.

## Command graph assessment

Intel's `sycl_ext_oneapi_graph` remains an experimental DPC++ extension. Its dynamic parameters update kernel arguments; dynamic command-groups can change a kernel and its execution range, but the specification limits those command-groups to kernel operations and host tasks. Graph support and mutable update capabilities are backend/device-specific (`aspect::ext_oneapi_graph` / limited-graph capability). Intel's implementation documentation describes graph replay as a command-buffer capability and notes graph partitions and extra synchronization when host tasks occur.

A graph may amortize repeated submission for a fixed topology and stable arguments. This workload's per-expert M, active order, compact offsets, and some addresses vary per routed chunk. Reusing a graph would therefore require either (a) mutable parameters/ranges for the captured low-level kernel nodes, with proof that the actual oneMKL implementation's internal nodes are graph-capturable and updateable, or (b) a fixed maximum-shape/padded execution, which trades CPU submission for extra matrix work and scratch. No official documentation found guarantees that arbitrary oneMKL GEMM calls become a single graph-capturable node or that the current Intel GPU/UR stack supports the required graph updates. A graph capture experiment is not justified as an assumed drop-in optimization; first establish a stable candidate subgraph or use implementation-specific documented support.

A fully static graph containing every operation for all 512 experts would also make the serialized graph large and encode a route that has variable `ne` and active experts. If the graph includes host tasks to inspect counts, Intel's guide says host work must be represented as graph host-task nodes, and compiler docs describe host-task graph partitioning. That inserts a host boundary; it does not make dynamic expert scheduling device-local.

## Recommended decision boundary

Wait for the active source-level CPU attribution to settle. The current actual-model diagnostic attributes 77.6445% of caller CPU seconds to explicit GPU waits and 48.507 CPU seconds outside those waits; the latter is material but does not identify GEMM submission as its source. If later evidence isolates CPU time in per-expert GEMM submission, the smallest candidate is an owned component study of grouped `gemm_batch` over already host-grouped equal-`ne` experts, comparing call counts and complete GPU dependency time while preserving the existing route as reference. Record the real `ne` histogram, host-array preparation, additional output storage, GEMM numerical deltas, and GPU faults. A graph study should follow only if profiling shows repeated stable submissions remain after batching and the actual runtime reports the required graph update support.

Do not treat oneMKL batching as eliminating R754's dynamic-count boundary: it still consumes counts supplied by the host. Do not infer that grouped API calls are faster; their implementation may itself schedule several GPU kernels. No performance, numerical, correctness, hardware-capability, or 262,144-context measurement was made here.
