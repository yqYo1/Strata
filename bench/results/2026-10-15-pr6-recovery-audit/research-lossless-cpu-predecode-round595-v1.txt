# R595 — CPU lossless IQ GU expanded-weight cache feasibility

2026-10-15 JST. Read-only source, receipt, and primary-reference review for Ryzen 5 5600X (Zen 3/AVX2), Arc B570 10 GB, RAM 128 GiB, current native mixed-IQ3_S model. Only this report was written. No source/Git mutation, build/test, measurement, GPU/service operation, or cleanup was performed. Performance discussion is prior receipt evidence or explicitly labeled arithmetic; this round measured none.

## Decision

A bounded CPU-only expanded representation is mechanically possible without model requantization: retain each IQ block's original D and subscales, predecode codebook magnitude and sign into byte lanes, then use an integer dot and the current block-to-FP32 FMA sequence. It is only a candidate. The representation would read about 2.33–3.12 times as many GU weight bytes per cache hit as packed IQ3_S/IQ3_XXS/IQ2_S, so there is no basis to predict it is faster on this memory-sensitive host. Full-model expansion is a no-go; a bounded, lazily populated CPU-GU cache is the sole candidate worth a later isolated fixture.

The required CPU saving is substantial. Existing service receipts assign about 70% of CPU thread-time to GU; GU shares are IQ3_XXS 36.5%, IQ2_S 37.2%, IQ3_S 25.0% (per-GU shares, not total CPU shares). At the observed 36.5 thread-seconds / 128 outputs, even six workers running at full capacity give a CPU-service lower bound near 6.1 seconds, or roughly 21 outputs/s. The 70 outputs/s goal needs several-fold less CPU service or a material work/critical-path change. Worker thread-time is not wall time; this calculation is conditional capacity arithmetic, not a decode speed prediction. See R579 and the exact format service receipt.

## Current format and route

The actual native_gu_rows() path uses type-specialized AVX2 Fmt32 decoding. For each IQ block, IQ3_XXS performs scalar grid loads then forms sign/scale vectors (iq_avx2.cpp:150-161); IQ3_S forms 9-bit codebook indices, loads grid magnitudes, and expands sign/subscale (:164-178). The row dot applies signed Q8_K activations, integer accumulation, block D×activation-scale FP32 FMA in block order, then horizontal reduction (:202-228). The current multi-token kernel reuses a decoded weight block among tokens in that one job; unexplored reuse is across later jobs/tokens that revisit the same (layer, expert, GU) blob. R582/R590 establish the dispatch split: nt>=2 can use the custom multi-token path; nt=1 ordinarily uses GGML unless the existing opt-in exact helper is enabled. Do not count either the exact helper or GPU expert cache as this proposal.

The IQ2_S custom decode costs four scalar 64-bit codebook loads per half plus sign/subscale processing; IQ3_XXS/IQ3_S each use eight scalar grid entries per half. Codebooks are small and likely cache resident, but the current CPU binary has no recorded lookup latency or cache-miss attribution. Expanded bytes remove grid lookup and sign unpack on a hit, but add weight traffic and possibly more cache lines. An L1 codebook lookup being fast is plausible, not measured.

A lossless byte representation can hold one signed magnitude byte per original weight (or separate magnitude/sign bytes if needed by the chosen vector instruction), plus the original per-block/per-group scale metadata and D. No float conversion, fp16 conversion, new quantization, or change to block scaling is needed. However, retaining the current arithmetic order is not automatic: a byte layout and SIMD dot must reproduce existing per-half integer sums, scale application, per-block FMA order, and reduction. If a different SIMD instruction changes integer saturation or reduction grouping, exact equality must be demonstrated. Treat lossless as exact reconstruction of the source integer code and existing scale metadata, then separately gate kernel arithmetic against the current path.

## Source ownership, mmap, and additive RAM budget

FileExpertSource::open() on packed format maps experts.bin read-only with mmap(MAP_SHARED) (src/core/expert_source.cpp:538-559). A native pack without experts.bin maps each GGUF shard named by its native index (:675-745); an expert's gate/up/down blob is assembled from three tensor slices when requested, and stage buffers are reused (:760-777,780-800). The mapped file is the packed source. A decoded cache would be an additional anonymous/owned allocation and must not be charged as if it replaced that mapping. OS file-cache pages, process RSS, and explicitly owned anonymous cache bytes are different counters.

The current source allows a separately owned RAM complement for CPU experts while leaving mmap as a fallback (include/strata/core/expert_source.hpp:441-465); that is an existing raw packed expert copy mechanism, not a license to reserve memory twice for an expanded copy. Current long-service capture reports peak engine session RSS 54,244,605,952 B (~50.5 GiB) (decode-format-service-normal-v1.json) and the comparable phase audit reports 54,207,803,392 B (~50.5 GiB). Public docs give IQ3_S experts at about 54.8 GB RAM (docs/MODELS.md:64-74). RSS is whole-session, includes mmap pages and other owners, and is not free RAM available for this proposal. Current receipts do not provide simultaneous MemAvailable, anonymous-vs-file RSS split, cache working set, or selected resident-complement bytes at the same decode boundary.

Use an explicit initial cap of **8 GiB of incremental expanded-cache owned bytes** as a proposed admission ceiling, with the existing 8 GiB RAM-headroom convention as the reason for starting conservatively. This is not a claim that 8 GiB is free: admission must also check live available RAM after model/session/KV/RSS owners are established and leave at least 8 GiB available after requested allocation. Formula: expanded_cache_budget = min(8 GiB, MemAvailable_at_admission - 8 GiB reserve - other planned incremental owners), refused if non-positive. Report actual allocated bytes and process RSS separately. Preserve that cap until a real 256K/RESTORE run establishes a larger safe budget; never use file-backed mmap size as free RAM and never double-count it as new allocation.

Using the repository's fixed expert dimensions H=2560, FF=640 (include/strata/kernels/cpu/expert.hpp:34-36), GU has 2×640×2560 = 3,276,800 weight values per expert. A signed int8 expansion is 3.125 MiB/expert before scale metadata/alignment; 16 entries are 50 MiB, 64 are 200 MiB. Each 256-weight packed block currently occupies 98 B IQ3_XXS, 82 B IQ2_S, or 110 B IQ3_S (iq_avx2.cpp:150,164-166): per GU row this is 980/820/1,100 B against 2,560 B expanded, or 2.61×/3.12×/2.33× bytes. Extra block metadata can increase expanded-cache size modestly and must be counted in exact planning. Expanding every one of 48×512 expert GUs to signed bytes alone would be 75 GiB, before scale metadata: this excludes a whole-model cache on a 128 GiB PC already running a ~50 GiB RSS session and preserving RAM for 256K/RESTORE. These are dimension-based arithmetic estimates; no actual allocator or model file was inspected in this round.

## Bandwidth-aware benefit bound

R579's current route's logical CPU weight payload is about 1.098 / 0.969 GB per output in its two recorded long samples, equivalent to 76.84 / 67.85 GB/s if sustained at 70 outputs/s. The separate host RAM read control was 36.87 GB/s. R579 explicitly warns that logical bytes are not measured DRAM bytes and the control is not attained model bandwidth. It nevertheless shows why multiplying GU bytes matters.

For a cached expanded weight with actual cache-hit fraction p, its weight-read byte multiplier is 1 + p × (r - 1), where r is 2.33, 2.61, or 3.12 by format; p=1 means 2.33–3.12× and p=0 means packed baseline plus decode cost on every access. This is only a byte-count identity. The existing GPU decode expert cache's 3.0% hit (3,124/104,160 route lookups) is not a prediction for a new CPU decode cache's hit rate. The latter has no per-(layer,expert) reuse histogram yet.

Possible benefit is decoder instruction work removed on a true repeat hit; possible cost is higher CPU memory traffic, cache footprint/eviction, initial expansion work, and synchronization. An upper bound on service saving is the service-time fraction actually served by this cache on hits, at most 100% of the targeted formats' GU CPU service (together the three formats are ~99% of measured GU time), multiplied by an unknown decoder share of those instructions. There is no evidence that decode is the dominant share. Therefore no nonzero speedup lower bound or 70 t/s claim is justified. If extra expanded reads push traffic toward the 36.87 GB/s control, the candidate could lose even with perfect hits. Compare CPU thread service and end-to-end decode wall separately.

## One bounded candidate and later gates

**Candidate: per-ExpertSource bounded lazy CPU GU expanded cache, at most 8 GiB owned, only types 18/22/21.** Cache key is (model/source generation, layer, expert, GU type); one allocation contains only gate+up signed integer codes plus exact metadata. Populate only when CPU GU route is about to consume that expert; a miss decodes from existing packed mmap/blob into the cache and continues. On capacity pressure, evict a least-recently-used entry only after all synchronous pool jobs holding it have returned; use pin/refcount or equivalent checked lease so no worker can observe freed storage. Free the arena on model/source replacement and orderly engine teardown. Do not change GPU cache miss upload: prefill and GPU expert-cache upload always read original packed source bytes. Do not expand Down types or non-IQ types. Keep packed fallback and an OFF-by-default selector.

A small later screen should start with **16 and 64 expert entries** (about 50/200 MiB of code arrays plus scales), using real IQ2_S, IQ3_XXS, and IQ3_S rows. Verify full gate/up outputs bitwise against current same-binary CPU route over valid packed blocks, scales, alignments, tails, concurrent duplicate misses, eviction while jobs are active, source close/reopen, and canaries. The cache fixture must establish hit/miss/eviction counts and producer/waiter ownership under a fixed sequence before any model run. Then collect actual model CPU expanded-cache hit rate and evicted bytes without GPU upload changes; service timing and work must be matched. A fixture win alone does not imply model speed.

Before broader adoption require:
- Measure format×nt×expert reuse and compare CPU service for decode/expansion versus expanded-cache hit; distinguish cold fill from warm hits and use a live-cache working set larger than LLC.
- Run matched clean end-to-end samples using same prompt/output length, generated IDs/work accounting, model build, route settings, and no concurrent build/test/GPU/cleanup. Require lower decode wall beyond run noise and no regression in tokens/work, numerical output/greedy IDs, faults or CPU/RAM pressure. Worker thread-time alone cannot pass.
- Keep prefill GPU upload packed, and verify it against the old path; check prompt wall doesn't pay an unbounded whole-model expansion at startup.
- Exercise cache hit/eviction/lifetime through 256K and RESTORE, repeated prompts, cancellation/error and source teardown. Measure MemAvailable, anonymous/file RSS, peak RSS and cache-owned bytes; retain >=8 GiB live RAM reserve at admission and during the run. Candidate must refuse to admit above its cap and preserve current packed fallback.
- Keep candidate off unless clean decode improves materially and exact current-model route spends enough repeated CPU-GU work in selected formats. Existing exact-helper small differences and old IQ3_S rowpair proposal do not count.

## Prior proposal exclusions

R582 already identified scalar lookup as a possible bottleneck and proposed IQ3_S nt=1 pair/gather approaches; IQ3_S rowpair was subsequently measured slower by 4.13% hot and 25.72% streaming and must stay rejected. R590 proposes IQ2_S nt>=2 gate/up software pipeline as a hypothesis, not a result. This cache is different because it reuses a predecoded expert across later calls and spends additional memory, but it should not proceed unless reuse/working-set evidence exists. R594's GPU VRAM cache admission and prompt-scoped release candidates concern device cache/scratch owner lifetimes; they do not establish CPU expanded-cache RAM headroom.

## External primary-reference scan

- Microsoft T-MAC paper, EuroSys 2025: https://arxiv.org/abs/2407.00088, lines 16–20. It gives a CPU low-bit inference design using lookup-table-based fused arithmetic that deliberately avoids materializing dequantized weights. This is a useful caution against assuming expanded weights win; it is not an IQ2_S/IQ3_XXS/IQ3_S predecode cache and does not transfer a speedup estimate to Strata. Official code overview: https://github.com/microsoft/T-MAC, lines 258–268.
- Upstream GGML declares per-format IQ dequantization entry points including IQ2_S/IQ3_XXS/IQ3_S and distinct quantization types (https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-quants.h, source lines 472–479, 514–528). That establishes an available materialization/reference path, not an inference cache or a claim that float dequantization preserves Strata's integer-dot arithmetic. Current web pages are mutable branch links; record exact fetched commit if a future implementation copies code.
- Upstream IQ codebook layouts and decode functions are in https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cpu/arch/x86/quants.c. The page is the current master source view, with no immutable SHA available in the web response. It provides a primary layout/reference check, not evidence for this bounded cache.
- No primary IPEX-LLM or ik_llama artifact located in this scan demonstrates an exact IQ-family expanded CPU expert-weight cache with unchanged IQ dot semantics. Do not use forum/blog claims or unrelated per-format benchmark numbers as support.

## Status

Candidate only. No code, build, test, cache fixture, service run, GPU upload change, performance result, quality qualification, or adoption. Current no-go conditions: no measured CPU expanded-cache hit/reuse histogram; no proof IQ grid/sign decode is a material CPU-time share; 2.3–3.1× bytes/read per hit; no simultaneous live RAM-headroom/anonymous-vs-file RSS receipt; and no same-binary exact-arithmetic prototype. Preserve packed IQ source, existing CPU fallback, and current default until all gates above pass.
