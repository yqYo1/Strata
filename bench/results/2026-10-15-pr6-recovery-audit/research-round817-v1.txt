## Local toolchain and what is actually installed

The approved official Intel LLVM tree is `.tools/intel-llvm-v711/install` as referenced by R810's manifest. Static build metadata identifies LLVM `22.1.0` at Intel LLVM revision `504366f4b82ff00bbac7b0c956635eed8bc599d8`; the install header reports `__SYCL_COMPILER_VERSION 20260915` and SYCL 9.0.0. No executable was invoked to corroborate those records. The package label `v711` alone is not the compiler identity; Main should record the compiler build output and binary hash in the R810 build receipt.

That install contains `clang-offload-extract`, `clang-offload-bundler`, `llvm-offload-binary`, `llvm-objcopy`, `sycl-post-link`, `syclbin-dump`, `llvm-spirv`, and `spirv-to-ir-wrapper`. A filename search did not find `llvm-objdump`, `ocloc`, or a standalone `iga`/`iga64` executable in this prefix. `llvm-objcopy` can manipulate ELF sections but is not an Intel GPU ISA disassembler. `syclbin-dump` is for the separately defined SYCLBIN format; R810's normal `-fsycl` executable is not declared as a `.syclbin` artifact. A static system filename search did find an `ocloc` executable under the VTune 2026.4 GTPin profiler tree and `libiga64.so` in system library locations, but not a standalone IGA CLI. Neither the external `ocloc` version nor compatibility with this compiler's generated image has been verified. Treat the external ocloc as a candidate tool only.

Intel documents `spir64` as the generic SPIR-V target and `spir64_gen` as Intel GPU AOT. R810's CMake compile/link options select `-fsycl-targets=spir64_gen`, pass `-device ${STRATA_XE2_AOT_DEVICE}`, request the split-barrier, 2D block-I/O, and subgroup matrix-multiply SPIR-V extensions, and set the 256-GRF option. This is a source recipe, not evidence the target variable was set to the intended BMG model in the eventual build or that a runtime loaded that image. Preserve the actual CMake cache, full compile/link commands, and chosen `STRATA_XE2_AOT_DEVICE` (`bmg-g21` or `bmg-g31`) with the build receipt. The Intel target guide calls `spir64_gen` AOT and lists BMG G21/G31 target aliases. A generic `spir64` image instead requires device-side compilation/JIT. A binary containing an AOT image proves it is packaged; runtime dispatch evidence is needed to prove that exact image and kernel were used.

## Bounded extraction and disassembly recipes

These are proposed commands only. Their flags follow Intel LLVM's documented extraction/unbundle examples and Intel's documented ocloc disassembly syntax; exact installed-tool acceptance remains untested. Start only from Main's closed, hash-pinned R810 executable and a separate finite output directory. The container may be the legacy Clang bundle or the newer offload-binary representation, so inspect the ELF section table and extracted labels rather than hardcoding a section name or guessed target label. LLVM describes both formats; `clang-offload-extract` is the documented host-ELF extraction step, and the bundler's `--unbundle` selects a recorded target triple.

**Recipe 1 — extract the AOT payload from the exact ELF.** Required inputs: the R810 executable (or final object/archive actually consumed by the test), its SHA-256, the exact compiler/link command, ELF inspection tools, and the v711 extractor/bundler. Keep the unmodified output from this recipe as evidence, not a replacement build.

```sh
OUT=/path/to/owned-r810-isa-review
mkdir -p "$OUT"
sha256sum /path/to/r810-executable > "$OUT/input.sha256"
readelf -W -h -S /path/to/r810-executable > "$OUT/host-elf-sections.txt"
V711=/path/to/approved/intel-llvm-v711/install/bin
"$V711/clang-offload-extract" /path/to/r810-executable --output="$OUT/offload"
strings "$OUT/offload.0" | rg 'CLANG_OFFLOAD_BUNDLE|spir64_gen|spir64'
# Substitute only the exact target label found above; do not guess it.
"$V711/clang-offload-bundler" --unbundle --type=o --targets='<recorded-target-label>' --input="$OUT/offload.0" --output="$OUT/device-image"
```

The final unbundle command applies only if the extracted payload is in the Clang bundle format accepted by that installed bundler. If the section/header inspection instead identifies a newer llvm-offload-binary container and the documented extractor does not handle it, stop and use the matching v711 `llvm-offload-binary` documented interface; no unverified listing/extraction option is proposed here. If the object is an archive, first identify the exact member linked into the test, then apply the same receipt to that member. Do not conclude from section names alone that the image is native AOT.

**Recipe 2 — disassemble the extracted Intel GPU image.** Required inputs: the device image from recipe 1, the BMG model name recorded in the AOT invocation, and an `ocloc` version verified against the producer/toolchain. The only statically located candidate is outside the v711 prefix, so Main must check its package/tool metadata before use. If it is compatible and the payload is a ZEBin/Intel device binary accepted by that tool, the documented form is:

```sh
OCLOC=/path/to/version-matched/ocloc
"$OCLOC" disasm -file "$OUT/device-image" -device bmg-g21 -dump "$OUT/isa"
```

Replace `bmg-g21` with the exact AOT device (`bmg-g31` if that was compiled). The guide documents `.asm` output for each kernel. If the installed tool rejects the extracted format, preserve the failure and stop; do not recompile source with an approximate offline command and present that as the loaded image. No `IGA` command is offered because the approved prefix has no IGA executable, and the static `libiga64` presence does not establish a usable CLI. No `llvm-objdump` recipe is offered because it is absent and is not a general Intel GPU ISA disassembler.

The host adapter specializes `DenseKernel<Input, Output, Policy>` over four 16-bit input/output pairs—FP16→FP16, FP16→BF16, BF16→FP16, BF16→BF16—and two tiles, 16×64×32 and 128×128×32. Thus there are up to eight entry variants; confirm which are present in the actual image rather than assuming all templates survived linking. The source spells `MMA_Atom<XE_DPAS_TT<8, float, Input>>`, asserts `MMA::ValTypeC` and `ValTypeD` are `float`, casts X/W to `Input`, and Y to `Output`. `xe_gemm_beta0` uses TLA's typed A/B/C block-2D copy helpers, reorder-to-MMA fragments, `cute::gemm`, then reorder and copy the output fragment. These types establish intent only. The mangled kernel entry/demangled template parameters (or a symbol map from the same compile) must identify each `.asm` file; a separate debug build is not a substitute for this exact optimized binary.

## What an ISA finding can establish

For the identified entry, a native DPAS instruction with disassembled or matching device-IR operand typing for HF16/BF16 inputs and FP32 accumulator supports the native matrix path. The DPAS mnemonic alone does not identify C++ template types, the chosen variant, or whether every operation in the kernel used DPAS. Cross-check the assembly operand precision/shape against the pinned IGC DPAS spec and R810's template mapping. For each load and output, decode the 2D block message form and width/type. A direct 16-bit output path requires the final writes to the Y argument to carry the selected 16-bit representation, with any FP32-to-output conversion confined to the fragment/register path and no intervening FP32 global output buffer. A `send` by itself is not proof of 2D block I/O; decode its message descriptor and bind it to the identified kernel's pointer arguments.

Inspect the entire matched entry for scalar/vector fallback arithmetic, conversions around the DPAS, SLM traffic/barriers, GRF use, spill/private-memory traffic, and additional global writes/reads. No DPAS in that entry argues against the intended native-DPAS lowering for that code object; it does not by itself prove CPU emulation or identify another kernel. DPAS present in a static image proves that instruction is available in that image, not that the runtime selected this image or dispatched this entry. Runtime kernel tracing/launch attribution must match the same image hash, device BMG target and symbol. Instruction presence, counts, and static code size do not establish latency, occupancy, memory bottleneck, numerical quality, or task quality. Those require Main-owned runtime trace, device timing/counters, correctness oracle comparisons, and per-sample performance runs. R805's warning applies: queue identity and legal API calls do not prove where arithmetic executed.

## Retention and evidence gate

Use one owned, closed build artifact set. Keep the exact executable or consumed object hash, compiler/revision and IGC/driver identity, CMake cache plus full compile/link commands, target image hash, target label, and a compact per-entry ISA excerpt/resource summary while the native16 code-generation decision remains open. Do not create a duplicate full binary. Cap the raw extraction/disassembly job at 64 MiB total by default; record extracted-image and text sizes before continuing, and stop as incomplete if the cap is hit. If a larger capture is necessary, record a finite replacement budget and its consumer before collection. After verifying the compact proof, retire duplicate extracted containers and full repeated `.asm` output; retain only the image still needed by the named decision, the concise instruction excerpts, hashes, and a deletion manifest with path/hash/reason at the next review. This follows `docs/ARTIFACT_RETENTION.md`; no cleanup was performed here.
