## What the tuning changes

For model geometry `S=128`, `HK=16`, `HV=48`, `C=10,240`, the tuned work-group covers one key head and one 32-column tile, with `4 × 32 = 128` work-items. It computes the three value heads sharing that key head (`VPK=HV/HK=3`), so it loads Q/K once and reuses those rows across the three recurrences. Four column tiles × 16 key heads produce 64 work-groups and 8,192 work-items total. By comparison, the current root path launches 48 groups × 512 work-items = 24,576 work-items; each item carries 32 FP32 state scalars. The tuned item carries 3 × 32 = 96 state scalars, which is why register allocation is central to this version.

The historical tuned launcher requests subgroup size 16 and Intel `grf_size<256>`. The recurrence body retains the original per-state FP32 FMA order. The body stages Q/K, V, gate and beta for eight tokens in two local-memory buffers, then reuses each staged Q/K row for the three heads. It performs two cross-row-group local reductions per token (`rkv` and output `ro`); a work-group barrier protects each reduction, plus a block-transition barrier around the eight-token tile. Its source comment says the CUDA `cp.async` path is disabled for this SYCL build: on B570 the staging copies are ordinary work-item writes followed by work-group synchronization, not asynchronous DMA. The separately launched normalization kernel uses subgroup-32 and its own local reduction.

Source-count comparison for long `T`:

| Path | Groups / work-items | Per-item recurrent state | Local storage per work-group | Synchronization structure |
| --- | ---: | ---: | ---: | --- |
| Current root recurrence | 48 / 24,576 | 32 FP32 values | 784 floats = 3,136 B | 6 group barriers/token at `begin=0` in source, including local Q/K publication, two reductions, and norm partials |
| Historical tuned key-head | 64 / 8,192 | 96 FP32 values | 6,496 floats = 25,984 B | 2 reduction barriers/token plus a block barrier per 8-token tile; normalization remains a separate kernel |

These are source resource/work counts, not measured occupancy, frequency, hardware ceilings, or proof that fewer barriers dominate runtime. The tuned version exchanges less duplicated Q/K and fewer barriers/work-items for roughly 8.3× more local storage per group and 3× as many state scalars per item. The exact launch's resource/occupancy fit must be read from the actual B570 compiled kernel. In the historical build, `SG16 + GRF256` reported zero spill bytes. This does not establish that current LLVM/Clang emits the same allocation or that 25,984 B/work-group is a favorable occupancy point.

## Historical correctness, speed, and fault evidence

The committed register study (`84ba5e56`) compares six `T` values × five designs. Its accepted tuned design preserves every FP32 state bit, FP32 recurrence-output bit, and FP16 normalized-output bit for `T={1,17,257,1024,4096,8192}`; the engine gate declines the variant for `T<256`. Guards/finite checks pass. `gdn_variant_parity` later extends coverage to `{1,17,255,256,257,1024,4096,8192}` under JIT and B570 AOT; both report exact state/output parity, zero guard errors, and zero spill bytes for the tuned kernel. These tests compare to the old GPU pipeline, not an independent CPU oracle, and do not establish today's current-root parity.

The tuning probe isolates several designs. At `T=8192`, the paired-row-group design with SG32/default GRF spills 4,864 bytes and takes 35.493 ms versus the 15.477 ms old control; requesting GRF256 removes reported spills and takes 14.069 ms. The selected key-head design with SG32/GRF256 spills 5,760 B and takes 21.443 ms; SG16/default GRF spills 3,520 B and takes 23.989 ms; SG16/GRF256 reports 0 spills and takes 12.272 ms. The latter changes `T=4096` from 7.285 to 6.165 ms. These are three warmed rounds of five calls per arm, alternating order, in an isolated recurrence probe on Arc B570, compute runtime 26.35.39758.10, oneAPI 2026.1. They are kernel timings, not end-to-end or 32K prefill measurements.

On the same historical JIT model binary, ordinary CLI timings were 13,550.2→13,506.0 ms at 4,096 input tokens (0.33% elapsed reduction) and 17,141.0→17,036.5 ms at 8,087 (0.61%); full 248,320-float first heads and IDs matched. At 8,192, the source-specific GDN phase had shown about a 20.7% reduction in a separate profiled single repeat, while resident prompt wall barely moved. This is consistent with a small total-work share. The current routed census reports a 3.543 s GDN recurrence interval out of 207.322 s GPU timeline (1.71%) on a different 34,560-token workload/config; that is a nonexclusive phase interval, not a causal ceiling for another build. For scale only, even an impossible zero-time recurrence at that observed share has a 1.7% Amdahl upper bound. Neither figure predicts a current-root gain.

No tuned-kernel GPU fault is identified in the retained GDN parity or paired performance records. The current R585 review found no concrete uninitialized read, race, span overrun, queue-order, or alias/lifetime defect in the portable root GDN recurrence. It also explicitly preserves the original automatic-24,576 numerical FAIL; added diagnostic copies/synchronization may suppress a timing-sensitive issue. These are separate observations, not proof that all binaries/configurations are fault-free. The R585 layer-26 difference is first seen in 19 sampled residual rows, with gaps in the recurrent input history; it does not show all layer-26 GDN inputs equal or identify GDN as the first differing operation. A GDN kernel change must not be treated as a diagnosis or fix for that FAIL.

## Barrier, subgroup, SLM, and lifetime audit

The historical tuned `stage(k)` partitions each Q/K, V, gate, and beta local-memory element by a unique linear `p` in its complete extent; tail positions with `t>=T` are skipped and never read because `n` is clipped to the valid token count. `rkv[j][rg][c]` and `ro[j][rg][c]` each have one writer per `(j,rg,c)` before the converged group barrier; the post-barrier reads consume all four row groups at the same `(j,c)`. The output row is written once by `rg=0,1,2` for the three value heads. The unconditional barriers are reached by all work-items; per-token tail size is group-uniform. The host parity test includes a 257 tail and guards around state and outputs. I found no concrete uninitialized consumed local value, SLM write/read race, subgroup-lane dependence, or out-of-range access in this inspected geometry.

The two-buffer reuse is ordered by the prior token's output-reduction barrier before the next block can overwrite the older buffer; within each tile, staged entries are published before recurrence reads. For the actual Intel path `STRATA_GDN_CP_ASYNC` is compile-time 0, so there is no missing async-copy wait to diagnose. This source review does not establish emitted machine behavior, hardware fault freedom, or correctness under a different compiler/runtime. SYCL requires a group barrier to rendezvous all work-items and order surrounding accesses; local accessors are per-work-group storage (Khronos [group barrier reference](https://github.khronos.org/SYCL_Reference/iface/group-functions.html), [local accessor reference](https://github.khronos.org/SYCL_Reference/iface/local_accessor.html)). Intel's current SYCL runtime maps a 256-GRF kernel property to the large-register-file compiler option ([Intel LLVM runtime source](https://github.com/intel/llvm/blob/sycl/sycl/source/detail/program_manager/program_manager.cpp#L2635-L2688)); the historical measured property belongs to oneAPI 2026.1, so verify it on the current configured compiler.

The root recurrence keeps all 512 work-items in every token loop and its barriers are also converged; its local arrays are fully written before reads for active heads. R585 already checked these properties in context. Do not remove an apparently redundant barrier until proving all work-items have completed every read of the local arrays before reuse; the old tuned loop's two barriers are not interchangeable with a textual barrier-count reduction in the root kernel.

## Current-root delta and minimum port candidates

The configured root resolver builds `src/kernels/sycl/fused_gdn.cpp` (`70abf4fd1359477a2e170b54f2172ba148a2ae21306e8145e070ebd0db7d995f`) and calls its `gdn_recurrence` from `src/prefill/prefill.cpp`. It is not the historical overlay. Current recurrence is token-serial per value-head group, has one 512-work-item group/head, 32 FP32 state values/item, 3,136 B SLM/group, six source barriers/token and fused output normalization. It uses current `sycl::exp`, current `sycl::fma(-decay, proj, v)` delta ordering, and current normalized FP32 plus FP16 output. The old selected default in R519 was a distinct 192-group, 128-work-item/head mapping with register-prefetched next token; R519 already proposed evaluating that mapping under current math. The PR #6 *tuned* key-head kernel is a further distinct 64-group/128-item three-value-head mapping and does not drop into the current recurrence by copying its launcher alone.

Two opt-in, same-math current-root comparisons are concrete:

1. **Smallest experiment: large-GRF build property on the existing kernel.** Keep the current 512-item geometry, subgroup-32 contract, arithmetic, all barriers, arrays, outputs, and dispatch. Apply `grf_size<256>` only to this recurrence kernel behind a diagnostic opt-in. Measure compiled private/spill bytes and per-kernel time first. This isolates register-file allocation; historical evidence is adjacent rather than exact because the SG32/GRF256 result was the 2-row-group probe, not today's 512-item kernel. If current compiler rejects the extension or changes generated code unexpectedly, retain the existing path.
2. **Higher-upside port: three-value-head key-head tile with eight-token staging.** Port the historical work distribution and SLM tile, but retain current root's exact decay/delta/output-normalization expressions and current state/layout API. Use subgroup 32 initially because current `xor_sum` for output norm reduces offsets 16,8,4,2,1; the historical recurrence body itself had no subgroup reduction and used SG16, but transplanting that property into current fused norm would be unsafe without a separately proven 16-lane reduction. Keep all work-group barriers converged and preserve two-buffer handoff. Gate only long per-call chunks (`T>=256`), leave the short/current path as fallback, and leave default off. This is a meaningful separate kernel reimplementation, not an import of the old engine. It has 25,984 B SLM/group and 96 state scalars/item from source geometry; hardware limit, residency, spills, and current compiler support must be verified before model tests.

The exact old SG16+GRF256 combination is not a safe minimal current-root port by itself: current root's normalization reduction is explicitly 32-lane, and group count/state layout differ. No candidate is applied or measured on current root, so both remain proposals.
