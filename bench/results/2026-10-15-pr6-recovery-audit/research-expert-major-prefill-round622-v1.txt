# R622 — deferred expert-major MoE batching across prefill chunks

Date: 2026-10-15 JST. Read-only external precedent and implementation review. Only this report was written. No source, build, test, process, GPU, profiler, or Git operation was performed.

## Scope and overlap with prior rounds

Read R601 (`research-profiled-dequant-reuse-round601-v1.txt`) and R620 (`research-current-layermajor-mix-round620-v1.txt`). R601 already proposes a bounded per-layer FP16 decoded-weight LRU across chunk calls and fused dequant-to-matrix-tile as separate candidates. R620 establishes that the configured layer-major path completes all 512 packed expert uploads for a layer before computing its chunk sequence, but does not expose a layer-major route/shape observer. This report does not repeat those candidates or claim the current exact `ne` mix. The question here is a different schedule: for one layer, compute causal attention/GDN and exact router inputs for the whole prefix over ordered chunks, retain/reread the resulting MoE input and routes, then visit each expert once and process all its prefix rows before advancing to the next layer.

The useful outside precedent is *token batching per expert within prefill* and *bounded rounds*. I found no primary source demonstrating this exact complete-prefix deferred schedule for a single-process 10 GiB discrete GPU and this model. Standard batched MoE kernels usually receive all tokens in their current graph/batch; that does not establish that recurrent/causal block preparation can be deferred or that an entire long prefix fits in device memory.

## Closest implementation precedents

### S-MoE: exact layer-major prompt batching, bounded to 64 tokens

The S-MoE maintainer's internals pages document a layer-major prefill for a streaming model: per layer, process a chunk of up to 64 tokens, compute attention and exact routes for all those tokens, form the chunk's expert union, and apply each claimed expert to all matching rows with `smoe_gate_up_batch` / `smoe_down_batch`. The token-batch path uses one dequantization stream per expert and keeps activations in batch planes. Its source description explicitly says the batch kernel falls back when the batch exceeds preallocated buffers. It also says the kernel's current wall-time impact is hidden under NVMe I/O in that system, so it does not establish a speedup for this Strata path.

The same page documents an adjacent kernel idea: decode quantized values in the dot-product epilogue without materializing a full floating-point weight tensor. This is already covered as the fused-dequant candidate in R601; it is not a new candidate here.

Sources: S-MoE maintainer docs, [Layer-Major Batched Prefill](https://docs.s-moe.com/v1/internals/layer-major-prefill.html) (sections “The Inversion,” “Choreography Per Chunk,” and “Token-Batch Fused FFN”) and [Metal Compute Kernels](https://docs.s-moe.com/v1/internals/metal-kernels.html) (section “Token-Batch Fused FFN,” especially the 64-token bound/fallback). These are rolling docs, retrieved 2026-10-15; they do not expose a source commit on the page. Their implementation is Apple Metal/UMA plus NVMe-streamed experts and a different quantized format, not Arc SYCL or an 8,192-row chunk. It establishes that exact routing and grouped expert GEMM are implementable inside a bounded chunk, not that all chunks can be delayed together.

### vLLM and SGLang: grouped expert execution and bounded communication rounds

vLLM's modular fused-MoE design distinguishes contiguous activation input from a batched layout shaped `[num_experts, max_tokens, K]`, accompanied by a per-expert valid-token count. This is direct evidence for an expert-major activation layout and grouped work; it is generic GPU/serving infrastructure and assumes a dispatched batch is already available. It says nothing about preserving recurrent state or delaying one layer's MoE across independently processed prefill chunks.

SGLang's official Expert Parallelism guide decomposes MoE into dispatch, pre-permute, grouped-GEMM core, post-permute, and combine. It also documents its “ant-moving” long-sequence path, which transmits tokens in configured rounds and sizes communication buffers from per-round token count, hidden size, and top-k. This is a useful precedent for limiting the live routing/communication footprint while retaining batched expert work. It is distributed expert-parallel communication and not a host-RAM spool for one local accelerator.

Sources: vLLM official design doc [`docs/design/fused_moe_modular_kernel.md`](https://github.com/vllm-project/vllm/blob/main/docs/design/fused_moe_modular_kernel.md), “Batched” input format; SGLang official guide [`docs/docs/advanced_features/expert_parallelism.mdx`](https://github.com/sgl-project/sglang/blob/main/docs/docs/advanced_features/expert_parallelism.mdx), modular EP framework and “Ant-moving Function.” The URLs point at moving `main` snapshots retrieved 2026-10-15; pages did not expose a pinned commit. The implementations target accelerator-resident or distributed execution (SGLang's example is an accelerator collective buffer), and their grouped GEMMs should not be read as evidence that all 512 FP16-expanded expert pairs fit in 10 GiB.

### llama.cpp: batch-shaped MoE execution and prompt batch sizing under host offload

The llama.cpp `MUL_MAT_ID` implementation contract is an expert-indexed batched matrix multiply: expert IDs select matrices for each batch position. The project also exposes physical prompt `ubatch` size, documenting that increasing it may improve prompt processing while increasing memory use. CPU-MoE flags place expert tensors in host memory, while prefill operations may still be dispatched as batched matrix work. This validates the common technique of amortizing expert work over a token batch and highlights activation-buffer sizing as a control. It does not persist the MoE inputs for an entire request across chunk boundaries or show a per-layer one-dequant lifetime in the current Arc implementation.

Sources: [llama.cpp bare-metal `MUL_MAT_ID` kernel](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-et/et-kernels/src/mul_mat_id_f32.c) (algorithm/input-output contract; moving `master`, retrieved 2026-10-15) and the official [completion README](https://github.com/ggml-org/llama.cpp/blob/master/tools/completion/README.md) (`--ubatch-size`, physical maximum tokens and memory tradeoff). This kernel file is a reference implementation, not proof that its backend is the configured Strata Arc/SYCL path. `MUL_MAT_ID` also does not itself prove packed-to-FP16 reuse; the kernel's quant/backend contract differs by source path.

### MoE offload systems: relevant scheduling, different saved cost

Fiddler is specifically a CPU-GPU orchestration system for constrained GPU memory and reports long-prefill gains in its paper page. KTransformers (SOSP 2025) provides a more detailed primary account of expert offloading, AMX-specialized CPU kernels, dynamic scheduling of imbalanced prefill expert tasks, and CPU/GPU coordination. Its paper states that its “Expert Deferral” is used exclusively during decode, not prefill; deferring routed experts there is a scheduling/behavior trade to overlap adjacent layers, not the exact all-prefix prefill scheme proposed here. It also notes that long prefill has thousands of tokens and is compute-heavy on CPU, so moving work to CPU is not automatically beneficial. These systems address placement, CPU throughput, and offload/synchronization more than repeated GPU dequantization of already GPU-resident packed weights.

DALI's 2026 paper abstract is directly local-PC/offload-oriented. It describes runtime CPU/GPU assignment by workload, residual-based prefetch and workload-aware GPU cache replacement, evaluating across several MoE models and settings. The abstract establishes those techniques and measured phase speedups on its own configurations, but does not claim full-prefix per-expert accumulation. Since this target already has the active layer's packed experts on device, DALI's transfer/cache gains cannot be transferred as a predicted benefit for this proposal.

Sources: [Fiddler author publication page](https://kanzhu.netlify.app/publication/fidder/) (ICLR 2025 metadata and reported speedups; code link `efeslab/fiddler`); [KTransformers SOSP'25 paper](https://madsys.cs.tsinghua.edu.cn/publication/ktransformers-unleashing-the-full-potential-of-cpu/gpu-hybrid-inference-for-moe-models/SOSP25-chen.pdf), especially §3.2 and §4.1 (AMX/dynamic work scheduling and Expert Deferral); [DALI arXiv paper](https://arxiv.org/abs/2602.03495) (paper abstract; local-PC offload). The Fiddler author page points to the project but is not a pinned implementation revision. KTransformers experiments are CPU/GPU hybrid with NVIDIA CUDA/AMX and different model/hardware; DALI's reported results likewise do not establish an Arc/SYCL outcome.

## Tradeoffs for the proposed whole-prefix pass

1. **Potential saved work is specifically repeated decode/materialization.** If an expert is active in several 4,096/8,192 chunks of the same layer, complete-prefix aggregation can decode its packed GU/Down pair once and use that decoded pair against all rows routed to it. Unlike an LRU hit hypothesis, this is a scheduling guarantee for the experts actually visited, but only if the per-layer worklist deduplicates expert IDs across all chunks and the decoded pair stays live for all GEMM sub-batches. The total saving is bounded by repeated active-expert visits and must be measured from exact ordered layer routes; R620 says that current layer-major source does not emit that histogram. R601's per-slot 9.375 MiB and full-layer 4.6875 GiB calculations remain applicable: this schedule should visit one expert at a time (or a small bounded set), never allocate all decoded weights together.

2. **The cost moves to intermediate activation and route retention.** To compute the whole layer's MoE in expert-major order, preserve or spool each token's exact normalized MoE input (or sufficient original tensors to regenerate it), its top-10 expert IDs/weights, and a token-index map; then scatter/accumulate expert outputs back in original token order before passing the full hidden state into the next layer. A straightforward design has O(T·D) activation storage plus O(T·top-k) route metadata for prefix length T and hidden width D. If the input and output planes coexist, it can require multiple O(T·D) planes. A tiled expert computation can cap transient gather/GEMM output workspace, but cannot avoid retaining enough layer state or writing it to host memory/storage. Expert-wise duplication of all routed inputs is an avoidable O(T·top-k·D) expansion; an index list plus one shared activation plane is smaller, with extra gathers.

3. **Host RAM is a possible spill area, with real bandwidth and capacity costs.** A bounded device staging buffer can copy expert-specific rows from host-held layer activations in sub-batches while keeping that expert's FP16 pair live. This trades transient VRAM for host memory traffic and device-link transfers. On a discrete B570, this differs from S-MoE's Apple unified memory and from server studies with pinned host pools and high-end PCIe/NVLink. A design that writes per-layer intermediates to disk would add storage bandwidth and latency and has no direct precedent among the checked primary sources; keep any spool bounded, sequential, and only if host RAM is insufficient. Host RAM must still preserve the project's reserved tail/state memory; it is not free capacity.

4. **It increases synchronization/queue-lifetime obligations.** All causal pre-MoE work must complete in chunk order, routes must be derived from their true states, and each token's top-k weighting/residual/scatter must match the existing path. The expert-major stage then has to consume each activation exactly once per route and finish its output before the next layer begins. This report does not audit Strata's causal state or prove that its QSA/GDN implementation can be split at the proposed point; the parallel source audit owns that question.

5. **Larger GEMMs may improve utilization, but may be capped.** Aggregating a cross-chunk expert's rows turns multiple smaller GU/Down GEMMs into fewer larger GEMMs. Benefits depend on actual per-expert row counts and GEMM overhead; skewed routing may leave very large and very small expert matrices in the same layer. Dynamic shape/padding, gather/scatter overhead, route list construction, extra host traffic, and oneMKL behavior can offset the gain. vLLM/SGLang show grouped execution structures, but their batched layouts and compute platforms are not a performance prediction for Strata's oneMKL FP16 shapes.

## Finding and applicability boundary

The schedule is structurally distinct from R601's cache and has a credible upside: for each active expert, do the packed-to-FP16 expansion once per layer and use the same 9.375 MiB decoded pair for all rows from the entire prefix, using bounded GEMM sub-batches if needed. The closest validated architecture is bounded per-expert token batching (S-MoE, vLLM, llama.cpp); none of those references establishes cross-chunk deferral over a full prefix with Strata's hybrid recurrent/causal stages. Offload literature (Fiddler, KTransformers, DALI) supports workload-aware scheduling and shows that long prefill is a distinct regime, but its gains largely come from compute placement, load balancing, cache hits or transfer hiding. Here all packed experts for the active layer already reside in the device cache per R620, so those gains must not be claimed.

Treat this as a research candidate, not an adoption recommendation. A useful next evaluation, if the source audit confirms a legal cut point, is to obtain exact route counts by layer and chunk; estimate route/input/output retention bytes under the actual prefix and reserve; prototype an expert-at-a-time staged pass with bounded activation gather and existing dequant/GEMM kernels; compare dequant call/bytes, GEMM shapes and end-to-end clean prefill time against the current 4,096/8,192 chunk schedule. Preserve exact routing and numerical behavior and include fresh fault/correctness gates. Stop if legal causal ordering forces replay/recomputation, the route/activation lifetime exceeds host/device budgets, or transfer/gather/scatter cost outweighs fewer dequant launches. No speed or quality result has been measured for this proposal.
