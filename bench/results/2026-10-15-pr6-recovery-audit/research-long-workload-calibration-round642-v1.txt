Question and conclusion

`tools/calibrate.py` does not calibrate the requested workload. It measures short, 128-token, temperature-zero answers with thinking explicitly closed. It then fixes PCIe fraction before sweeping `spec_min_p`, tests workers separately after restarting the engine, and promotes a candidate only after three interleaved default/candidate confirmations. This is a useful machine setup probe, but not an optimization result for 32K+ thinking-on generation, and its short-answer winner should not be copied into the requested operating point.

The project already has a better workload: `tools/strata_bench.py --long-generation-only`, backed by `tools/long_generation_bench.py`. It measures two distinct 32K+ thinking-on tasks, alternating their order, with fresh prefixes, temperature zero, up to 16,384 generated tokens and at least 1,024 actual completion tokens for eligibility. It records engine decode rate and MTP offered/accepted counts. Three eligible runs are required to confirm the declared strong-code (>=60% acceptance each run) and weak-prose (<=40%) categories; those categories do not guarantee a draft regime. `quality_qualified` is explicitly false: having answer text/body and counters is not a task-quality judgment.

The smallest credible optimization is to retain that long workload and first screen the existing per-request `pcie_frac` × `spec_min_p` controls together, then test `pool_workers` in fresh server processes. The current official HTTP benchmark does not expose those tuning keys and does not run a setting matrix. `serve/server.py` does accept `strata_tune` in a request's sampling object for `pcie_frac` and `spec_min_p`; a future measurement invocation can pass them on each otherwise-identical long request. Worker count is startup-only (`--pool-workers`) and must be varied by restarting the engine/server. If no client path forwards `strata_tune`, current tools alone cannot do this long-workload screen without a small benchmark-runner adaptation; do not fall back to `calibrate.py`'s short prompts or to process-environment mutation.

What the current calibrator actually measures

- `tools/calibrate.py`: three short English prompts, fixed `MAX_NEW=128`, `temperature=0`, and prompt serialization ends with `<think>\n\n</think>\n\n`. It measures decode tok/s, not prompt processing, and accepts any generation with more than eight tokens and a positive engine `decode_ms`; it does not require full 128-token length or a particular finish reason. There is no answer-quality check or acceptance minimum.
- It runs the same three prompts twice for warmup, then sequentially samples five PCIe fractions at default `spec_min_p`, sequentially samples three thresholds at the selected PCIe fraction, and compares only that pair against default in three alternating pairs. Initial sweep points get one sample each. Worker counts (default, roughly 2/3 and 1/2) are then tested with one warm-up and two rates per count, each in a newly started engine. Selection is median decode rate and needs >3% gain over default.
- The script explicitly states this tunes decode only. Cache/prefix behavior is inherited from the engine config; it does not capture reused prompt tokens or force a fresh-prefix lifecycle. Repeated exact short prompts can therefore interact with whatever prompt cache the config enables. The short workload is neither a fixed long-context prefill nor long reasoning decode.
- `serve/server.py:655-707` constructs `strata_tune` protocol keys only for valid numeric `pcie_frac` and `spec_min_p` in [0,1]; `generate.cpp:5376-5400` reads them as request-local values, clamps them, then uses them for GPU-vs-CPU PCIe miss assignment and probability-floor verify-window/draft behavior. They are not process environment changes. The current `tools/strata_bench.py` long-generation request supplies thinking and reasoning-budget overrides but no `strata_tune`, so it uses process defaults. `tools/sycl/serve_bench.py` exposes startup `--pcie-frac` but no per-request `spec_min_p`; it is a local native token-protocol bench, not the HTTP long-generation client.
- `pool_workers` is not among server request sampling keys. `generate.cpp` constructs the pinned `ExpertPool` once from startup `o.pool_workers` before serving requests (`:2977`); a change requires a fresh process. This matches `calibrate.py`'s restart behavior. Keep its environment immutable from child creation through runtime lifetime, as required by the project rules.

What the official long workload measures—and misses

`tools/long_generation_bench.py` v4 declares 32,768 minimum input tokens, approximate 33,792 target input, 1,024–16,384 actual completion tokens, and thinking on. The two tasks are an explicitly formatted 80-test Python module (expected strong MTP) and a 4,000+ Japanese-character story (expected weak MTP). The suite warms the server first, then alternates workload order each run. Each request is a fresh prefix; eligibility requires `reused_tokens == 0`, actual input >=32,768, normal stop/length completion, valid engine decode clock, and at least 256 offered MTP drafts. Prompt tokens are approximate until actual usage is checked. Completion usage includes thinking; `reasoning_budget_tokens=0` means no imposed reasoning cap, not thinking disabled.

The standard suite's `request()` sends `temperature=0`; long-generation overrides set `enable_thinking=true` and `reasoning_budget_tokens=0`. Per-run receipts record input/output lengths, reuse, decode rate, acceptance, output/reasoning hashes and actual reasoning-token count. They do not retain full answer text in the compact result. Prompt construction contains a run-number tag and generated background list; a fair settings comparison must replay the *same tokenized input IDs* for every arm, not regenerate new run-tagged prompts for each arm. `MAX_OUTPUT_TOKENS=16384` is only a cap: actual completions vary, so compare only eligible outputs and report actual token counts. The two tasks and three runs establish workload coverage, not semantic correctness. Do not select a setting from acceptance alone or claim optimized quality without the existing task/correctness gates.

Minimal existing-control screen

1. Hold one exact binary/model/pack, context, MTP/verifier capacity and MTP mode, cache size/profile/adaptation, prefill chunk, KV mode, CPU/GPU route baseline, sampler, environment and server lifecycle fixed. Use the official two long-generation prompts with thinking on and zero reused tokens. Preserve 32K+ actual input and >=1,024 output eligibility; capture exact request IDs so every arm gets the same input. Start with the current server defaults as baseline.
2. For `pcie_frac` in the calibrator's existing `{0.0, 0.2, 0.35, 0.55, 0.75}` and `spec_min_p` in `{0.3, 0.5, 0.7}`, run a full 5×3 request-level screen on both long tasks. Use one common input per workload/run block across all 15 settings, alternate/reverse setting order in the next block, and do not change any environment variable. Keep an explicit default pair (including the configured default if outside the grid). This is the minimal way to detect interaction; the present one-axis-at-a-time sweeps can miss that interaction. Treat this as screening only because one sample per cell is noisy and costly.
3. Re-run default and the best one or two screened pairs in at least three paired, interleaved blocks for each workload, using the same request IDs and fresh-prefix condition. Retain every sample, actual prompt/completion tokens, finish reason, TTFT/prompt time, decode tok/s, MTP offered/accepted, output hashes, and error/fault status. A candidate advances only on repeatable end-to-end decode improvement for the intended workload mix and unchanged task/correctness/quality acceptance; strong code and weak prose winners may differ.
4. With `pcie_frac`/`spec_min_p` fixed to the surviving pair, compare the calibrator's worker candidates in separate fresh server processes: default count, rounded 2/3 and half (minimum two), deduplicated. Keep all environment and request IDs fixed; give each process the same startup warm-up recipe and at least three paired long-task samples. Because startup, cache/graph warm state and OS drift can bias restart order, rotate worker-count order across blocks. Recheck the default worker count in the same blocks. This is the only one of the three settings that requires restart.
5. If the final intended setting is a combined tuple, run it against the original default tuple in a final fresh-process paired confirmation; report code and prose separately and their declared decision rule. Recheck the actual 256K context path only if the candidate is intended for that path; 32K admission/fit is not a 256K result. Do not combine cache-capacity or MTP-width changes into this calibration screen.

This sequence uses only existing engine controls and avoids a new online controller. It requires the long-workload caller to forward supported request-local `strata_tune` keys; as written, `strata_bench.py` does not. The HTTP engine serves one request at a time by default, so keep the screen serial (`parallel=1`) to preserve an unambiguous comparison. Separate worker-count processes prevent mutation of the already-constructed worker pool. If exact request replay cannot be arranged, first fix the benchmark harness/replay inputs; changing prompts between settings would confound the screen.

External benchmark-method reference

The upstream llama.cpp SPEED-Bench client measures per-category throughput, latency and speculative-draft acceptance through the OpenAI-compatible server; its documented purpose is comparing draft configurations over diverse prompts ([SPEED-Bench README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/bench/speed-bench/README.md)). Its speculative-decoding guide recommends end-to-end throughput/latency and acceptance measurements and distinguishes acceptance statistics from valid generated output ([speculative decoding guide](https://github.com/ggml-org/llama.cpp/blob/master/docs/speculative.md)). These support measuring acceptance alongside real request speed and workload diversity. They do not validate Strata's thresholds or guarantee transfer across its Arc/SYCL backend.
