## Primary-source lesson and limits

FlashAttention-2's author paper and Princeton NLP explanation support partitioning Q/head work among independent blocks when additional parallelism is useful, and partitioning warps so each owns query rows while K/V remains available to them; the stated goal is reducing shared-memory communication and improving occupancy. They also emphasize that block sizes trade shared memory and registers against occupancy. Intel's oneAPI joint-matrix guide and the Intel LLVM SYCL extension say joint-matrix operations are subgroup-scoped, all work-items in that subgroup must participate without divergence, and legal matrix shapes are device dependent. Those ideas motivate a candidate shape; the FA2 results are CUDA/A100 evidence and do not predict this Arc/SYCL kernel's speed or admission.

Sources: Tri Dao et al., [FlashAttention-2 paper](https://tridao.me/publications/flash2/flash2.pdf), especially §§3.2–3.3 and the block-size discussion; [Princeton NLP author-group explanation](https://princeton-nlp.github.io/flash-atttention-2/); Intel, [Programming Intel XMX Using SYCL Joint Matrix Extension](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2024-1/joint-matrix.html); Intel LLVM, [SYCL oneAPI matrix extension](https://github.com/intel/llvm/blob/sycl/sycl/doc/extensions/experimental/sycl_ext_matrix/sycl_ext_oneapi_matrix.asciidoc). The FA2 warp mapping is a design analogy, not a direct port: this kernel already assigns query-row bands to subgroups for PV, but its K/V loads and score/softmax staging are work-group shared.

## Concrete mode-1 candidate and exact declared bytes

Candidate A is two independent head-tile work-groups for each `(query, KV head)`, each `WG=64` with four 16-wide subgroups, `CH=64`, and the existing 8x16x16 FP16-input / FP32-accumulator matrix contract. It has two variants: tile bases `{0,8}` with live counts `{8,4}` (“8+4”), or bases `{0,6}` with live counts `{6,6}` (“6+6”). Each tile pads to 8 rows. It uses the existing Direct global store (`STRATA_SYCL_PROMPT_DIRECT=1`). Per group, the QK score matrix needs four 8x16 tiles to cover 8 padded heads x 64 cells. For PV, four subgroups each own one 64-wide output-dimension slice for the 8 rows. Q and online-softmax state have 8 rows; probability hi/lo storage is `VG x 8 x 64`. Every group stages its own 64 selected K/V rows.

For mode 1 (`KG=VG=4`) the accessor declaration sum is exactly **53,876 B (52.61 KiB)** with Direct output and **62,068 B (60.61 KiB)** with the local `final` array. The sum includes each declaration once per work-group, not twice for the two tile work-groups:

| Local accessor | Bytes per candidate work-group |
|---|---:|
| `qhi`, `qlo`: 8 x 256 x 2 B each | 8,192 |
| `kv`: 64 x 256 x 2 B | 32,768 |
| `phi`, `plo`: each 4 x 8 x 64 x 2 B | 8,192 |
| `scores`: 8 x 64 x 4 B | 2,048 |
| `ks`, `vs`: each 64 x 4 x 4 B | 2,048 |
| `maxima`, `sums`, `alpha`: each 8 x 4 B | 96 |
| `factors`: 4 x 4 B | 16 |
| `final`: one float for Direct / 8 x 256 floats otherwise | 4 / 8,192 |
| `rows`: 64 x 8 B | 512 |

The 53,876-B figure is only the sum of declared accessors. It does not include compiler/runtime padding, hidden allocation, registers or spills, and is not a device capacity query. Existing `matrix_available` still applies the current 60,880-B mode-1 threshold and checks WG at least 128. A port would have to change the WG condition to 64 and define a new conservative admission rule based on declarations plus implementation evidence; it must not claim that a 53,876-B source sum automatically proves launch safety. At an actual 64-KiB local-memory limit, the declaration sum alone permits at most one such WG resident per compute unit before other limits; occupancy is unknown until device data/compiler resource reports exist.

For coverage planning, the same candidate accessor formula can be evaluated for each current mode (`KG/VG` from source). With Direct enabled it is `43,620 + 256*KG + 2,308*VG` bytes: mode 0 `(1,1)` = 46,184 B; mode 1 `(4,4)` = 53,876 B; mode 2 `(8,8)` = 64,132 B; mode 3 `(4,8)` = 63,108 B. Without Direct, add 8,192 B. These are byte sums, not a proposed mode admission threshold. Thus this head-tile geometry directly addresses the mode-1 ~60-KiB target; it does not put Q4 modes 2/3 below 60 KiB by declaration count.

## Work, traffic and synchronization accounting

For `width=2,051`, current CH32 executes `ceil(2051/32)=65` iterations; CH64 executes `ceil(2051/64)=33`. The last allocation is 29 padded cells/current chunk sequence (2,080 allocated) versus 61 candidate (2,112 allocated). The useful QK and PV work remains 12,601,344 MAC each, 50,405,376 FLOP combined per query. Do not call this candidate's matrix-issued work “useful FLOP.”

A first-order scalar product count for the joint-matrix FP16 hi+lo operands, over two KV heads, is separable:

| Product | Current CH32, 16 padded heads x 2,080 issued cells | Candidate CH64, two WGs x 8 padded heads x 2,112 issued cells |
|---|---:|---:|
| QK matrix operand MAC terms (both hi/lo parts) | 34,078,720 | 34,603,008 |
| PV matrix operand MAC terms (both hi/lo parts) | 34,078,720 | 34,603,008 |
| Combined issued MAC terms | 68,157,440 | 69,206,016 |
| Combined matrix FLOP-equivalent at 2 per MAC | 136,314,880 | 138,412,032 |

These are tile-issued scalar MAC terms from padded heads, rounded cell tiles, and two FP16-part products; they exclude softmax, scale application, barriers and copies. The candidate is about 1.54% higher in this arithmetic envelope only because of the larger final CH64 cell tile. Its total padded head rows remain 16/query/KV head across the 8+4 and 6+6 choices; the head-tile split itself does not increase padded head matrix work relative to the current 16-row tile. The numbers do not predict latency or throughput.

The explicit trade is K/V duplication. The two independent work-groups each gather and stage the same selected rows. At 2,051 cells per query, mode 1 asks for K+V INT8 code bytes `2 KV heads * 2 tensors * 2,051 * 256` = **2,100,224 B/query**, plus four FP16 K and four FP16 V scale entries per row, **65,632 B/query**. Candidate A doubles these requested source bytes to **4,200,448 B** and **131,264 B** respectively (plus repeated row-ID/page mapping and query/step setup). This is requested logical traffic; cache reuse could change physical memory traffic. SLM `kv` bytes are per work-group and are not doubled when comparing a work-group's declared sum, but two groups issue two copies of the gather/stage work.

Per work-group the online loop and its barriers fall from 65 to 33 iterations. There is no cross-group reduction or output merge because each group owns distinct query heads. There are twice as many work-groups, so aggregate barrier instances across the query/KV pair need not halve; concurrency and lower per-group serial loop length may help, while scheduler/launch bookkeeping and duplicated KV loading can erase the gain. The per-head softmax reductions stay independent as required by attention. In 8+4, one tile has eight live heads and the other four; in 6+6, both have six live heads. Both declare/issue eight rows per group, so 6+6 balances live-row non-matrix work without changing matrix padding or gather duplication. It also means two partial Q-scale reductions rather than one shared reduction.

A same-work-group alternative could reuse one staged KV tile while processing both query-head tiles sequentially, avoiding duplicated global K/V reads, but it needs two sets of live FP32 output accumulators (and separate online-softmax state) or an intervening spill/store/reload. That raises per-subgroup register pressure and may defeat occupancy or reintroduce traffic. Treat it as a separate candidate only if profiling shows duplicated K/V requests dominate and the two-accumulator resource cost is acceptable; it is not assumed in Candidate A.

## Numerical contract and index blueprint

Preserve the current mode-specific input interpretation and online attention contract:

- Mode 0: FP16 K/V values; mode 1: exact INT8 K/V codes and four FP16 scales per head/cell; mode 2: Q4_0 code interpretation and eight FP16 block scales; mode 3: INT8 K and Q4_0 V with their distinct 4/8 scale groups. Do not route these through a generic reinterpretation that changes codes or scales.
- K score is still the sum over each K scale group of the FP32 scale times its QK partial, followed by `qdown`. Q is scaled by a power of two, converted to FP16 hi+lo and accumulated to FP32. V probability-times-scale is still normalized per value group, split hi+lo to FP16, multiplied with staged V in joint-matrix FP32 accumulation, rescaled by `factors`, online-softmax `alpha`, and final row sum. Preserve missing-cell zeroing and nonresident selected-row behavior.
- A tile-local `qm`/power-of-two shift is mathematically reversible through that tile's `qdown`, but changes FP16 hi/lo rounding from a single 12-head shared `qm`. If bitwise-like numerical proximity is desired, a common Q scale must be broadcast to both work-groups by a sound mechanism; otherwise explicitly accept a precision-path change and test attention/residual/logits with tolerances. Do not claim exact equivalence from the algebra alone.

Minimal index blueprint for a two-tile dispatch, leaving all unrelated paths intact:

1. `tiles=2`; launch `nq * n_head_kv * tiles * WG` work-items. Decode `tile=index%2`, `kvhead=(index/2)%n_head_kv`, `batch=index/(2*n_head_kv)`. Keep each group's required subgroup size 16, with WG=64 (four full subgroups).
2. Set `head_base = tile==0 ? 0 : (split==8 ? 8 : 6)` and live heads to 8/4 or 6/6. Query source is `query + (batch*n_head + kvhead*12 + head_base)*HD`; quantize local rows 0..7, zeroing local rows `r>=live_heads`. Do not use padded stride 16 for the external query/output layout: global head stride remains 12.
3. For output, only write when `r < live_heads`; destination row is `batch*n_head + kvhead*12 + head_base + r`, with dim from the same `db*64 + j*16 + c` partition. This guards padded rows and prevents inter-tile overlap. In 8+4, tile 1 writes only global heads 8..11; in 6+6 the tiles write 0..5 and 6..11.
4. Reuse selected cell `ids[batch*cap + c0 + tid]`, `steps[batch*kStepCount + kStepWidth]`, page-table lookup and row formula unchanged. Stage the same 64 cells separately per head tile. Tail chunks keep `rows[c]=-1` and zero all K/V/scale/probability entries that may be loaded by the matrix tiles. Preserve bounds checks on `count`, negative IDs/pages and `c0+tid < count`.
5. Keep 8x16x16 joint-matrix operations uniform across all 16 lanes of each subgroup; do not place joint-matrix calls under a lane-divergent head-valid predicate. Subgroup-level work assignment is: all four subgroups cover the 8x64 QK score rectangle as four N=16 tiles; for PV they each own a distinct 64-column output band, with four M=8 rows-by-output tiles per band, and keep all `joint_matrix_*` calls converged.

Audit every `HEADS` use in a diff. Any hard-coded 12 in query group decode, Q load, Q row validity, score row indexing, `maxima/sums/alpha` indexing, `phi/plo` row indexing, PV joint-matrix A pointer, Direct store condition, output base/row, span sizes, and fallback caller must be intentionally classified as either the external per-KV stride (12) or the local tile size/padded 8. Do not replace the global stride with 8/16, or use a flattened output `i` that crosses into the next KV head at row 12. For `n_q=1`, two KV heads ×12 query heads must produce all 24 output rows exactly once.

## Evaluation gates and recommendation

Candidate A is a geometry hypothesis, not a recommendation to adopt. Its CH64 loop and per-WG footprint are promising for mode 1 only if device SLM admits the launch and duplicated KV reads do not dominate. It retains total padded rows and hi/lo matrix products, modestly increases final-cell padding, doubles selected K/V gather requests, and adds one extra tile-scale/online state setup per KV/query pair. No speed estimate or measured result is claimed.

Capture actual device-reported local memory, subgroup/matrix-combination support, compiled SLM/register/spill resources and route/mode counts. Keep this separate from the currently unfinished QSA route observation. Compare CH32 and one head split at equal selected IDs/steps, pool contents, residency/page tables, query count, queue and state. Record individual clean samples and correctness separately; include the existing fallback as an arm only when its route is explicitly forced/observed. Profile requested versus physical traffic before attributing any change to loop/barrier reduction.

Numerical/shape validation must cover all four input modes (FP16, INT8, Q4_0, K8V4), each split variant if retained, `n_q` values 1 and non-multiples for head/batch indexing, empty and all-missing selections, selected nonresident pages, nonidentity page-table mapping, widths around 31/32/33 and 63/64/65 plus partial tails including 2,051, maximum admitted `cap`, and logical position 262,143. For 262,143, distinguish a logical-ID/cap arithmetic fixture from actual selected-page residency and physical computation; no small fixture or logical boundary alone is a full-context pass. Compare attention output, residual and fixed-history logits with declared numerical tolerances; include finite values, infinities/NaNs and zero-scale/empty-row behavior; run the repository's applicable exact-model long-context retrieval/quality and physical near-boundary/RESTORE checks before any adoption. Keep original failures and all individual outcomes per retention policy.

Disposition: retain current CH32 implementation while Main's real route measurement is unresolved. 8+4 and 6+6 are unmeasured opt-in experiments only.
