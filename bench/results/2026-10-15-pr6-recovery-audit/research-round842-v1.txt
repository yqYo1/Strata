# R842 — Replaying repeated GPU command graphs

**Purpose:** knowledge collection; public-source review only (2026-10-16). This compares host-side graph capture, setup, replay and update for repeated workloads made of short GPU commands. It does not establish a Strata bottleneck or adoption case.

## Break-even is a whole-loop cost

Eager asynchronous submission pays host work for each command, but the CPU may submit later commands while earlier kernels execute. A graph pays a capture/build cost and an executable setup cost (often called finalize, instantiate, and sometimes upload), then pays replay submission and graph-side scheduling on each iteration. For R iterations, graphing is worthwhile when `R × (eager iteration time − replay iteration time) > capture + setup + parameter-update + graph-specific staging costs`. These times must share the same measurement boundary. If the eager path synchronizes after every kernel while the graph path synchronizes once per iteration, the comparison mostly measures removed synchronization; it does not isolate graph submission.

A graph is a cached command DAG, not a fused kernel. Kernel nodes still execute as kernels. The principal expected gain is less repeated host/driver work and fewer exposed gaps between device commands. Presenting the DAG at once may also let a runtime optimize scheduling, dependencies or device descriptors, but neither capture nor replay implies less arithmetic or shorter kernel execution. Graphs help when host submission lies on the critical path: small kernels, a repeatable command sequence, enough replays, and a graph spanning the host gaps. A large compute or memory-bound operation can leave almost no host work to recover.

The [CUDA Programming Guide’s graph chapter](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/cuda-graphs.html) separates graph definition from executable instantiation and launch. CUDA supports both explicit node construction and stream capture of existing stream submissions. Capture can be a low-edit path, including compatible library calls; manual construction gives direct control of nodes and edges. In either case, capture/build and instantiate are not free and belong in cold-start or short-lived-workload cost. First launch may also include upload; repeated-launch timing should not silently mix that cost into a steady-state result.

The following measurements illustrate distinct regimes. Reported step times are end-to-end unless the source explicitly calls out a CPU or device metric.

The older V100 result shows why measurements should separate the submission clock from device execution. The kernel is separately measured at 2.9 µs on device; 3.8 and 3.4 µs are effective wall-clock averages including host and device time. The article does not report a graph-versus-eager device-kernel-time comparison. Likewise, the Intel slide’s graph step is not evidence of a faster kernel: its small A770 case removes launch scheduling gaps, while the 192k PVC case remains dominated by device work. As a useful independent model, the A100/CUDA 12.3 study includes graph construction in total time and locates a replay-count crossover, instead of inferring benefit from a low CPU launch number alone.

## Updating parameters and choosing node size

When topology and parameters stay fixed, capture once and replay. When arguments or addresses change but the operation DAG remains the same, CUDA’s `cudaGraphExecUpdate` can carry changed parameters into an existing executable graph instead of rebuilding and re-instantiating it. The [CUDA dynamic-environment example](https://developer.nvidia.com/blog/?p=37199) shows an A100 application with 504 nodes for the small workload and 2,520 for the large workload. Its update path reports section speedups of 16% and 26%; it captures on each of 70 and 1,540 invocations respectively, then updates 69 or 1,539 times and instantiates only three or one times. The article does not identify the exact CUDA toolkit/driver for these results, so those percentages should not be treated as a version-controlled baseline. It also warns that update cost scales roughly with changed-node count: if most nodes change, updates may lose their advantage. Caching separate executable graphs by parameter key avoids updates for frequently recurring shapes, but adds cache memory, key correctness and eviction concerns.

Updates are bounded by graph structure. CUDA graph update requires compatible topology/dependencies; a topology change or unsupported update falls back to fresh instantiation. Updating only a few known nodes avoids comparing unchanged nodes. The [current CUDA guide](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/cuda-graphs.html) says updates take effect on a subsequent launch and distinguishes full-graph from node-level updates. Node-level updates suit a small set of known changes; whole-graph update suits many changes or a graph captured from a library whose nodes the caller does not track.

Node granularity sets both the possible launch amortization and the cost of managing the graph. A graph with only a few nodes cannot remove much repeated submit overhead. A very large graph can cost more to construct, instantiate, upload and retain, and larger parameter changes increase update work. The CUDA 12.3 A100 study found that its roughly 100-node batch was a useful measured point, not a universal target. A different GPU, runtime version, DAG width, node types, or kernel size can shift that point. Keep enough structure to preserve actual dependencies and concurrency; making one giant chain can serialize work that eager streams overlapped.

## Dependencies, pointer lifetime and portability

CUDA stream capture infers ordering from stream order and supported event dependencies. Cross-stream event waits can join streams into one captured graph, but the capture must rejoin the origin stream before it ends; invalid operations can invalidate the capture. Device allocations, copy endpoints, and kernel arguments must remain valid for graph execution. CUDA graph memory nodes have explicit GPU-ordered lifetimes; accesses must fall between allocation and free. These are correctness constraints, not only setup details: an executable graph retains references to the recorded work and may replay long after capture returns.

Intel’s [DPC++ Command-Graph design documentation](https://intel.github.io/llvm/design/CommandGraph.html) describes deferred execution as depending on experimental Unified Runtime command-buffer support and says the runtime reports graph capability through device aspects. That capability is backend- and device-specific. The [experimental oneAPI graph extension](https://github.com/intel/llvm/blob/sycl/sycl/doc/extensions/experimental/sycl_ext_oneapi_graph.asciidoc) offers explicit graph-building and queue-recording APIs: queue recording is easier for existing submissions; explicit construction exposes nodes and dependencies. A recording and execution queue must match the graph’s context and device. Graph-owned allocation pointers are valid only inside their owning graph and must be dependency-ordered after allocation and before free.

SYCL graph update is experimental too. Its extension describes kernel parameter and range updates, and whole-graph updates require topologically identical graphs. Crucially, native recording delegates capture to the backend, where SYCL cannot inspect nodes; the extension explicitly does not support executable graph update for native-recorded graphs. A backend that supports replay therefore need not support update or the full SYCL feature set. In contrast, CUDA Graphs have existed since CUDA 10 and expose a mature CUDA-specific graph API, but remain NVIDIA-specific. SYCL offers a more portable source-level direction, not a promise of equivalent semantics, mutability, runtime maturity or performance on every backend. Query actual device aspects and verify the particular commands and update mode.

**Evidence boundary:** measurements above are tied to their named hardware and software. The IWOCL presentation describes Arc A770 and PVC 1100 only; it establishes no graph support or speed on Arc B570/Xe2. This archive proposes no local implementation or inference change.
