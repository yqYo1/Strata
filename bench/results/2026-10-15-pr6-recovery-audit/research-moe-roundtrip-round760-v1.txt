# R760 — long-prefill MoE grouping and host/device boundary

2026-10-16 JST. Bounded read-only source/documentation investigation. The only file written is this report. No build, test, GPU/runtime/profiler/process/environment/service/Git operation or cleanup was performed. No XeStrata material was read or used.

## Finding

Yes: the normal compact FP16 long-prefill MoE route has a logical GPU→host-visible-memory→GPU grouping boundary once per layer/chunk. Router IDs are exposed for CPU grouping; CPU computes expert counts and row maps; the maps are then made available to device kernels. This is not evidence that hidden activations, router probabilities, or expert math make a CPU roundtrip. `m.ids` is copied/exposed; `m.w` (router probabilities/weights) remains on the device and is consumed later by GPU `moe_combine`. `m.mixed_h`, gathered rows, expert projections and outputs remain device data in this path.

In the default SYCL path, `grp_host` is normally an attempted mapped host-USM allocation, and `grp_dev` is its device alias. A SYCL kernel writes router IDs into that allocation; after a queue synchronization CPU reads them. CPU then writes `slot` and `src` into the same host allocation, and SYCL copy kernels read those maps into device buffers. This is logically a visibility roundtrip, but it is not an explicit D2H then H2D copy pair, and source alone does not tell whether physical fabric traffic, cache/coherency work, or implicit runtime migration occurs. If mapped allocation fails (or the explicit group-copy setting forces the fallback), ordinary host vectors are used with explicit queued D2H/H2D copies. Both branches synchronize before CPU reads the IDs.

## Source path and payload

- Router projection and top-10 routing are queued at `src/prefill/prefill.cpp:2485-2487`; the router writes `m.ids` and `m.w`. Diagnostic audit copies at `:2488-2495` are optional and excluded here.
- `src/prefill/prefill.cpp:854-873` allocates fallback vectors, then normally tries `cudaHostAlloc(...Mapped...)` and `cudaHostGetDevicePointer`. In the SYCL compatibility layer, `src/sycl/compat.cpp:246-253` accepts only host USM and returns the same pointer as its device alias; allocation implementation is `src/sycl/runtime.cpp:150-168` (`sycl::malloc_host`). Allocation policy is an attempted default, not a guarantee: failure selects fallback. `STRATA_GROUP_COPY=1` suppresses this allocation attempt in the shown code.
- At `prefill.cpp:2582-2592`, mapped mode launches `copy_i32(m.grp_dev, m.ids, T*K, ...)`; fallback queues an explicit D2H copy. Both then call `cudaStreamSynchronize(m.cs)` before host access. The mapped copy is a device `parallel_for` (`src/prefill/sycl/postops.cpp:232-237`), not a CPU copy. The synchronization drains the in-order queue's earlier work too, including shared-expert operations queued after routing (`prefill.cpp:2498-2504`), not only router production.
- CPU clears and fills `cnt`, validates IDs, computes offsets, and scans IDs again to write `slot`/`src` (`prefill.cpp:2606-2657`); it assembles active expert `order` (`:2665-2674`). Mapped mode queues device copies from the host alias into `slot_dev`/`src_dev` (`:2658-2663`); fallback queues explicit H2D copies. Expert launch control still uses CPU `order`, `off`, and `cnt`: the per-expert loop obtains `ne=cnt[e]`, gathers rows, and calls two GEMMs (`:3037-3069`). `moe_combine` later reads device `slot` and device `w` (`postops.cpp:249-267`).
- The layer-major outer loop is 48 layers and the chunk size is 8,192 (`layer_major.inc:358-365`, `:412+`). For 78,452 batched rows this is nine full chunks plus a 4,724-row tail: 480 routing/grouping boundaries. Total `T*K` IDs are 37,656,960 int32 values (150,627,840 logical bytes). The mapped route writes that many ID bytes into host-visible storage, then writes one `slot` and one `src` int32 per routed item back through the alias: 451,883,520 logical bytes (about 430.8 MiB) across both directions. The fallback has the same logical payload in explicit copies. These are source-derived payloads, not measured bus traffic/counters.

The completed host attribution is stronger evidence than CPU-utilization inference: over the actual 78,452-row, 48-layer, 10-chunk diagnostic, grouping plus map-copy submission used 0.16536 CPU seconds and 0.16804 wall seconds across 480 calls. Explicit GPU waits used 167.95479 CPU seconds (77.36% of caller CPU); 37.34820 CPU seconds remained unclassified. Thus the grouping boundary exists, but moving grouping alone has little measured CPU-time upside in this run and does not address the dominant observed wait time. The result is diagnostic with trace/validation, not a clean throughput sample or proof of critical-path contribution.

## Safest design boundary

A stable device-side count/scan/scatter can remove the ID exposure and map roundtrip while preserving expert-major order, but by itself it does not remove the host wait: the existing per-expert oneMKL calls need host `ne`, active expert order and host-selected weight pointers. Copying only counts/order back is less data, but still leaves a host completion point. It also does not remove the measured 0.165-second grouping cost unless implemented and qualified end to end.

The smallest low-risk experiment, if later evidence justifies it, is a component-only device grouping implementation that writes stable `slot`/`src` and counts/order, retains current host GEMM orchestration, and compares exact maps/counts plus end-to-end dependency time. That tests eliminated payload without claiming wait elimination. A true no-host-wait path requires device-driven expert execution consuming device-resident routing metadata and weight descriptors (or a fixed padded/masked schedule); this changes the expert compute interface and must preserve row order, bounds/error behavior, output accumulation and state. A fully padded schedule can waste substantial work, so it is not a safe drop-in shortcut.

Official API constraints support this boundary: oneMKL `gemm_batch` accepts host-supplied group sizes/dimensions and matrix pointer arrays, making call coalescing possible only after host grouping; it does not document a device-driven dispatch list ([Intel oneMKL DPC++ `gemm_batch`](https://www.intel.com/content/www/us/en/docs/onemkl/developer-reference-dpcpp/2026-0/gemm-batch.html)). SYCL graph support is experimental/device-dependent; its dynamic command groups are restricted to kernels and host tasks, and host-task nodes may prevent whole-graph submission to the device ([Intel DPC++ graph extension](https://github.com/intel/llvm/blob/sycl/sycl/doc/extensions/experimental/sycl_ext_oneapi_graph.asciidoc)). Graph capture or batched GEMM therefore cannot be assumed to erase this dynamic-count dependency. Neither source documents performance for this model/device.
