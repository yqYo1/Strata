# R631 — QSA stage ownership and incremental-restage premise

2026-10-15 JST. Source-only audit of R630's streamed-QSA incremental staging proposal against current root SYCL source. No build, test, GPU, benchmark/process-control, Git, cleanup, or raw-artifact operation was performed. R630's existing report was left unchanged.

## Finding

R630 correctly identifies repeated prefix staging as a candidate in the **current layer-major execution order**, but its ownership premise is wrong: current `Prefill::Impl` owns one `m.stage`, not one stage per QSA layer. The candidate may still work in layer-major because calls are sequentially layer-major and each QSA layer's whole chunk sequence runs before moving to the next layer. It does **not** work by retaining twelve independent pools, and it must not be generalized to ordinary chunk-major execution.

`take_stage` allocates one pool with the primary QSA shape's full logical page count (`n_pages * n_head_kv * page_size` rows), once during `Prefill::init`; `bytes_needed` repeats the same count-only allocation. In mode 1, `SessionState` separately owns a host backing copy for each QSA layer. `session.hpp` explicitly documents that `qsa_bufs` scratch is shared because the twelve layers do not run concurrently; that shared scratch is separate from the host KV copies. `m.stage` is the only prompt stage pool.

`run_layer_major` iterates layers in ascending order, sets the stage range to `[layer, layer+1)`, and calls `run_impl(tokens,n,pos0,err)` once per layer. Within that call, `run_impl` iterates chunks in ascending `c0` order. The selected `st = ss.qsa_states[qsa_index]` is the current layer's independent state. For streamed KV it queues `kv_stage_from_host(m.stage, st.host, ceil(p0/page_size))`, appends the current chunk to that layer's host backing and the same `m.stage`, then selects/attends from `m.stage` before the next chunk. The run's compute/copy queue is the same (`m.copy == m.cs` is required); the layer-major path also checks drains at layer and pass boundaries. Thus, for a successful uninterrupted pass, the single stage changes owner only at a completed layer boundary, and within that pass its contents can already contain the previous chunk's K/V.

Normal `run_impl` is chunk-major: one chunk is the outer loop and all layers run for that chunk. It uses `m.stage` for every streamed QSA layer in turn, with each layer's distinct `st.host`. Before attention, each subsequent QSA layer overwrites the stage with its own prior history. At the next chunk, the first QSA layer cannot assume its prefix remains in the stage. Incremental prefix reuse is therefore limited to layer-major's order unless stage allocation/ownership is redesigned.

## Invalidation and correctness conditions

`session_zero` calls `qsa_state_zero` for each owned QSA layer. That clears device KV slots and the indexer and resets the streamed residency map; it intentionally does not clear the large host KV backing. It does not clear or tag `m.stage`. So a fresh sequence at `pos0=0` is safe to begin with an empty valid prefix (old physical bytes are irrelevant): skip a zero-byte prefix copy, append each current chunk to stage, and grow the valid-cell prefix only after the relevant writes are successfully ordered. A nonzero `pos0` or restored session starts with no valid stage prefix and must populate from the current layer's host backing before attention.

Conversation checkpoint/snapshot restore writes host/device KV and indexer state outside this `Prefill` stage. A stage-validity cache must be invalidated on any restore, session zero/reset, reinit/relayout/stage reallocation, change of QSA layer owner, sequence generation, or position discontinuity. Current prefill callbacks restore borrowed fields and ranges; they do not roll back session tensors. Layer-major's checked drain/lease keeps temporary owners alive on failed retirement, but an early error/cancel can occur after some stage copy or append has been submitted. On any error/cancel/failed drain, stage validity must be cleared; mark a prefix only after queue ordering and operation success are established. Reusing partially advanced session KV itself remains governed by the caller's existing reset/recovery policy. Never infer stage validity from host bytes merely being present: session zero deliberately leaves stale host data in unwritten ranges.

For arbitrary chunk sizes, the copy covers whole pages `ceil(p0/page_size)`, whereas append writes cells. Reuse should track a contiguous **cell** prefix owned by the current layer and sequence, not a count of completed chunks or pages. Existing page-aligned chunk sizes simplify the initial gate. Partial-page boundaries, short final chunks, nonzero `pos0`, restored state, repeated requests, and failure/cancellation each need explicit gates before broad enablement.

## Copy geometry correction to R630

Current INT8 geometry is `n_head_kv=2`, `page_size=4`, `head_dim=256`. `kv_stream.cpp:runs()` copies four arrays per logical page: K bytes `2*4*256=2048`, V bytes `2048`, K scales `2*4*(256/64)*2=64`, and V scales `64`, totaling **4,224 bytes/page = 1,056 bytes/cell**. This corrects R630's 4,160 bytes/page and 1,040 bytes/cell.

The logical prior-prefix `kv_stage_from_host` payload (not measured physical traffic) is consequently:

| Input | chunk | chunks | prior cells across layer passes | payload at 12 layers |
| ---: | ---: | ---: | ---: | ---: |
| 32,768 | 4,096 | 8 | 114,688 | 1,453,326,336 B (~1.35 GiB) |
| 65,536 | 4,096 | 16 | 491,520 | 6,228,541,440 B (~5.80 GiB) |
| 65,536 | 8,192 | 8 | 229,376 | 2,906,652,672 B (~2.71 GiB) |

At 262,144 cells, one full logical stage/host copy is 65,536 pages × 4,224 = **276,824,064 B** (~264 MiB); twelve per-layer host copies total 3,321,888,768 B (~3.09 GiB), excluding allocator padding. There remains only one stage allocation in the prefill workspace. These payload sums exclude current appends, kernels, metadata, and transaction effects; they predict no wall-time improvement.

## Smallest viable candidate and disposition

A narrowly scoped candidate is feasible for the existing opted-in layer-major route: stage-owner = current QSA ordinal plus request/session generation; valid-prefix starts at zero only for a known freshly zeroed `pos0=0` session, otherwise at zero with an initial host restore required; retain it only through contiguous ascending chunks after successful same-queue append; invalidate on every layer transition and every error/cancel/drain failure, reset, restore, reinit/relayout, or gap. The simple baseline-safe implementation can continue full restage for all unsupported conditions. Chunk-major remains full-restage. No cross-layer or cross-request reuse is justified.

Existing safe optimization opportunity is only the successful same-layer, contiguous chunk sequence in `run_layer_major`: current append already writes to both host backing and `m.stage`, so re-copying pages already present in that stage is redundant in principle. For `pos0>0`, restore the prefix once at pass entry; for fresh `pos0=0`, no prefix copy is needed. Keep the current page-copy path elsewhere. This report establishes source feasibility and corrected byte accounting, not correctness qualification or measured value; do not adopt based on arithmetic alone.
