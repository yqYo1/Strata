# R775 — Transfer granularity and packing for repeated host-to-GPU movement

2026-10-16 JST. Bounded, read-only knowledge collection. This report is the only file written. No product source, build, test, GPU run, profiler, process inspection, Git operation, environment/service mutation, or cleanup was performed. No XeStrata material was read or used.

## Finding

There is no portable segment-count or payload threshold at which packing wins. The crossover depends on per-copy host/runtime cost, transfer efficiency, CPU packing bandwidth, GPU gather/scatter work, setup cost, and reuse. First merge already-contiguous compatible ranges; this removes calls without a staging pass. Pack disjoint ranges when the host pass costs less than the calls and transfer inefficiency it removes. Gather on the GPU when a device-resident source or repeated local-layout reuse amortizes its kernel and memory traffic. Thresholds must be measured on the target dependency path.

Supplied Strata data motivates measuring submission and completion separately, but does not establish a granularity bottleneck: 25.793 seconds of residual copy-call CPU includes unseparated runtime work. An idle 320 MiB transfer measured 6.015 GB/s for ordinary H2D versus 5.095 GB/s for Host USM; Host USM submitted faster but completed slower. Route accounting totals 451,883,520 logical bytes over 480 boundaries, not PCIe-counter traffic. None predicts a packing gain.

## Contracts and crossover model

Core SYCL `queue::memcpy` takes two pointers and a byte count, returning an event; it is a contiguous copy, not a scatter/gather or strided operation. A USM pointer must be device-accessible and from the queue's context. Preserve event dependencies and keep source, destination, and staging allocations alive and unchanged through their final consumer [1].

For logical payload `S`, `N` small copies, and `M` merged contiguous ranges, compare these terms:

- Direct copies: `Tdirect = N × host-call cost + transfer(N, S, layout) + waits/dependencies`.
- Host pack: `Thost-pack = CPU-pack(S) + setup/amortized registration + M × host-call cost + transfer(M, S + any copied gaps) + required unpack`.
- GPU gather: `Tgather = kernel launch + gather from the source + write to local device storage + later use`, plus any host transfer still needed.

These are accounting guides, not additive laws: queued work overlaps and the critical path may include earlier GPU commands. Source element sizes give logical bytes; only a transfer counter can establish link traffic. A scattered gather may fetch more bytes due to transaction granularity and locality. Merging across a gap also adds copied bytes, so do it only when safe and cheaper than the saved calls.

Packing is promising when `CPU-pack + amortized setup + unpack < saved call cost + transfer-time improvement`; gathering when `launch + gather + local write < saved host work/calls + reuse value`. Measure host packing, API-call CPU, wait CPU/wall, completion, and the full dependency path separately; an async return is not completion.

## Strategy comparison

| Strategy | Likely favorable regime | Main costs and failure cases |
|---|---|---|
| Many direct copies | Few ranges; large spans; immediate or partial consumption; data already in consumer layout | Per-command host/runtime work repeats. Tiny transfers can underfill the link and make call cost dominate. |
| Merge compatible ranges | Adjacent spans share direction, ownership, ordering, and lifetime | Removes calls without a pack pass. Incompatible dependencies/layouts prevent merging; copying gaps adds traffic or can overwrite live values. |
| Pack into reusable host staging | Many scattered spans; host packing is cheaper than saved calls/transfer inefficiency, or producer can write packed output directly | Packing reads and writes payload and competes for CPU memory bandwidth/cache. Changing data repays this cost each iteration; a scattered consumer adds unpack cost. Per-transfer allocation/registration may erase savings. |
| GPU gather into device-local storage | Device-resident or efficiently accessible source; coalesced gather; local layout reused; spare GPU capacity | Launch, source reads, local writes and later rereads may exceed savings. Scattered host gathers can amplify remote transactions; a busy GPU is a poor target. |

Intel's guide recommends host USM for application-controlled transfer buffers and describes experimental import/release for external memory, with lifetime safety left to the application. Measure setup separately from reuse; this is not a reason to pin every buffer or evidence of an Arc speedup [2]. Reuse a persistent staging pool only when the workload amortizes it and event completion protects each slot. Host-USM support/limits depend on platform [1, 2].

## Evidence and counterexamples

NVIDIA's CUDA guide recommends batching small copies, even if packing/unpacking is required, and notes host-device bandwidth limits [3]. This motivates testing fixed call overhead; it provides neither a SYCL guarantee nor an Xe2 threshold.

Wu et al.'s GPU-aware Open MPI study compared CPU/per-span copies, GPU pack/unpack kernels, and pipelines for scientific data. On NVIDIA Kepler K40 with CUDA 7.5, GPU packing approached CUDA 2D-copy performance for vector layouts; its pipeline reached 90% of PCIe bandwidth for vector data and 78% for indexed data. Triangular packing reached about 80% of GPU-memory peak because irregular blocks lowered occupancy; caching layout metadata and overlapping its preparation helped reuse [4]. These results show opportunities and shape sensitivity, not SYCL/Arc/H2D/model performance.

Counterexamples: packing a large contiguous transfer adds a host read/write pass without removing calls. Adjacent ranges can be merged directly; one or two calls may be cheaper than packing. If the consumer can use input in place, a staging copy is waste. Whole-prompt batching can delay first consumption when chunks are sequentially dependent, so smaller batches may preserve overlap. GPU gather loses when launch time is exposed, the temporary is written then reread, the GPU is busy, or sparse loads amplify transactions. The Open MPI study also shows irregular occupancy and pipeline sizing can limit parallel packing [4].

## Workload crossovers

| Workload shape | Candidate to measure first | Reason to reject it |
|---|---|---|
| Small total payload, one to a few ranges | Direct copy or exact adjacent-range merge | A host pack or gather launch may cost more than all saved calls. |
| Fixed total payload spread over many tiny spans | Exact merge, then host packing to a persistent stage | Packing is only promising if CPU pack time is below saved call/transfer cost; no threshold follows from the number of ranges alone. |
| Large contiguous payload already saturating transfer | Direct bulk copy | Packing adds CPU traffic without reducing logical transfer bytes. |
| Same immutable layout consumed repeatedly | Pack/gather once, keep the prepared representation, and reuse it | Recomputing the representation or re-registering on each use loses the amortization. |
| Layout changes each iteration, producer is CPU-side | Compatible-range batching; compare host packing against direct calls | Every iteration pays the pack pass. Consider writing producer output straight into staging if this does not add other costs. |
| Device-resident scattered input reused by multiple kernels | GPU gather, or fuse gather into the first consumer | A standalone gather is poor when single-use or when GPU occupancy is already limiting the main work. |

Do not collapse the critical path to nominal link bandwidth. The comparison should retain queue submission mode, pointer type, allocation/setup and registration lifetime, copy count, wait placement, source layout, and consumer dependency. R762 already considered mapped host access versus explicit copies, and R765 separated host-copy submission from possible UR queue-drain behavior; this report does not infer either mechanism from copy granularity.

## One future experiment

After Main closes the current FP32 NLL diagnostic, use its fixed route/map fixture for a bounded granularity benchmark with identical logical bytes and destination contents. Test totals of 64 KiB, 1 MiB and 16 MiB across 1, 4, 16, 64, 256 and 1,024 equal or power-law spans; include the actual ~0.94 MiB map payload. Compare one copy per span, exact adjacent-range merging, CPU packing into persistent staging plus a bulk copy, and GPU gather into reusable device-local storage where the source is device-accessible. Otherwise treat gather as a separate topology case.

Measure one-use and 16-use cases. Record setup/import, CPU pack, call counts/CPU, wait CPU/wall, gather kernel, full dependency time, memory peak, checksums and logical bytes. Report link bytes only if a reliable counter exists. Use persistent allocations with event-correct lifetimes, clean processes for environment arms, and the current copy-offload safety setting. Alternate five paired repetitions; this can reject obvious losers but cannot establish prefill speed. Stop packing if total time fails to beat direct/merged copies, or gather if it adds path time or changes correctness.
