# R577 — layer-major RAM tailの通常host/Host-USM転送調査

2026-10-15 JST。読み取り専用の既存資料・source確認と公式SYCL/UR/Level Zero一次資料の確認。書込先は本報告だけ。製品変更、build/test、CPU/GPU計測、Git操作、cleanup、private excluded record/Codexログ/環境全域調査は行っていない。

## 結論

既存の同じprimary SYCL runtimeを使った比較に、普通の`malloc` host endpointと`cudaMallocHost`経由のHost-USM endpointが両方ある。256 MiB one-wayではHost-USMが速く、通常hostはH2D 2.25対2.73 GB/s、D2H 5.05対5.66 GB/sだった。ただし比較条件は現在の安全設定（Level Zero V2 copy-offload無効、DirectSubmission無効）と同じだが、残差の転送形状・連続往復は同じでない。実expert extentの小コピー比較もあるが1.51–2.66 MBである。従って過去の6.447 GB/sをlayer-major tailに当てはめられず、既存receiptだけで今回の実形状でどちらが有利かは判定できない。

現在のlayer-major candidateは1,249,525,760 BのFP32 host tailを普通の`new[]` rowsに置く。34,602 batched rows、GPU prefix 4,096 rows、48 layersの場合、47境界間のD2H store + H2D restoreは117,455,421,440 Bの論理payload（約109.35 GiB）。この値はR571とMain reviewが整理した算術で、PCIe上の実測trafficでも時間でもない。FP16保存案は対象payloadをほぼ半分にするが、自然入力で累積誤差/品質評価が未完了なので、転送最適化の比較へ混ぜない。

既知の安全baselineは維持する。すなわち`UR_L0_V2_FORCE_DISABLE_COPY_OFFLOAD=1`、`EnableDirectSubmission=0`、`m.copy == m.cs`の同じin-order queue。今回のtransfer ceilingもこのbaselineで行われた。offloadやqueueを変えると別要因が入る。

## 既存測定の再利用可否

`bench/results/2026-10-14-pre-Xe-model-compare/README.ja.md`の旧hardware tableは、Host-USM H2D/D2H 6.447/5.643 GB/sとpageable H2D 4.605 GB/sを記録する。Arc B570/Ryzen 5600X/128 GiB RAM、256 MiB、one-way payload、host-inclusive completion、当時のstack/configurationの値。これらは実モデルrouteの測定ではなく、H2D側では安全設定・current primary runtimeに一致する条件がreceiptから示せないため、現在のbaseline値としては再利用しない。

より近い`bench/results/2026-10-14-primary-transfer-ceiling/RESULTS.md`は同じprimary LLVM/SYCL 9/Level Zero V2 stackと、copy-offload disabled・DirectSubmission disabledで、 ordinary malloc vs Host-USMを同じtransfer helperのallocation/direction armとして比べている。256 MiB burstの3 process mediansはH2D ordinary 2.2487/2.2401/3.0572、Host-USM 2.7293/2.7076/2.7485 GB/s、D2H ordinary 5.0467/5.0490/5.1714、Host-USM 5.6624/5.6630/5.6612 GB/s。各runはwarmup後4連続burst、completionはordered compat event brackets込み。host completion wallとdevice event intervalは別記録で、overlapなし。H2D ordinaryはばらつきが大きく、小差の採否には反復不足とreceipt自身が留保している。

同じreceiptのactual expert extentsは1,510,400 / 1,971,200 / 2,662,400 B。1,971,200 Bのordinary H2Dを8件まとめると5.3031/5.4888/5.4021 GB/s、batch 32では2.5212/3.3371/2.9521 GB/s。これはAPI回数・同時batch・端点サイズにrateが依存する実例だが、残差より約60–100倍小さいコピーである。既存試験はH2D/D2Hを単独armで実施し、residual store→次layer restoreの連続roundtripは試していない。

## sourceと一次情報

Current `src/sycl/compat.cpp`の`cudaMemcpyAsync`はnonzero copyを`queue(st).memcpy(dst,src,bytes)`へsubmitし、そこでCPU `memcpy`、明示staging buffer、またはwaitは実行しない。`src/sycl/runtime.cpp`が作るcurrent queueはin-order。layer-major (`src/prefill/layer_major.inc`) はFP32 host rowsをordinary `new[]` ownerにし、callbackでD2Hを同じqueueへsubmitしてdrainし、次layerでは普通のhost pointerからH2Dをsubmitする。R572/R571 reviewも「shimに明示host memcpyはない。driver内部stagingの不存在は証明しない」と確認済み。SYCL `queue::memcpy`はhost pointerを含むcopy commandをevent付きでsubmitするAPIだが、specの意味はbackendが物理的にどう搬送するかを約束しない。

Intel oneAPI GPU guideはLevel Zeroの`malloc_host`について、allocationはhost上に留まりdeviceからPCI経由でアクセスされ、明示copyを要しないと説明する。これはCPUから読む正しさの説明であり、host-USMに置けばモデルのGPU kernelから大きなtailを直接読む方が速いという根拠ではない。またIntel GPU Optimization Guideの`LIBOMPTARGET_LEVEL_ZERO_STAGING_BUFFER_SIZE`は、非USM host memoryのhost/device copyで一時staging bufferを使うOpenMP Level Zero pluginの機能として説明される。この設定・実装をSYCL Unified Runtime adapterへそのまま適用できない。SYCL/UR shimの明示copyがないことと、Level Zero driverが普通host pointerをimport/pin/stageする有無・粒度は別の質問で、今回読めた公式資料だけではcurrent Arc B570 runtimeの内部動作を確定できない。

Intel DPC++ `EnvironmentVariables.md`はL0 V2が専用copy engineへcopy operationをoffloadでき、`UR_L0_V2_FORCE_DISABLE_COPY_OFFLOAD`はcopyを元queueのengineに残すと説明する。検討中の実測baselineに合わせてこの設定を保つ。SYCL in-order queueはそのqueueへの投入順だけを保証する。CPU側のbuffer上書きはqueue順序に含まれないので、queue copy完了前のhost pointer再利用は禁止。R541/R571/R572のhost ownership所見と現在のchecked drainsを維持する。

- Khronos [SYCL 2020 specification: queue::memcpy](https://registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html) — submission/event/dependency semantics。
- Intel oneAPI [Level-Zero multi-tile memory model](https://intel.github.io/llvm/MultiTileCardWithLevelZero.html) — `malloc_host`のhost residenceとPCIアクセスの説明。
- Intel LLVM [Level Zero adapter environment variables](https://github.com/intel/llvm/blob/sycl/sycl/doc/EnvironmentVariables.md) — L0 V2 copy-offload controlおよびhost USM allocatorの説明。
- Intel [Supported Environment Variables, oneAPI 2026.0](https://www.intel.com/content/www/us/en/docs/dpcpp-cpp-compiler/developer-guide-reference/2026-0/supported-environment-variables.html) — OpenMP Level Zero staging bufferの機能scope。SYCL UR stagingの直接根拠ではない。
- oneAPI Unified Runtime [Level Zero queue adapter](https://github.com/oneapi-src/unified-runtime/blob/main/source/adapters/level_zero/queue.cpp) と [memory adapter](https://github.com/oneapi-src/unified-runtime/blob/main/source/adapters/level_zero/memory.cpp) — 公式実装入口。現行GitHub branchとlocal oneAPI runtimeが同一revisionだとは仮定しない。公開ページの大きなsource fileだけから現在のdevice/driverの内部fallback動作までは判定できない。

## 有限Host-USM staging案のコストと寿命

全host tailをHost-USM/pinnedに変える案は採らない。34,602 rowsだけで約1.164 GiBをhost-USM化し、256KでGPU prefix 4,096を仮定した場合は約9.844 GiBに達する。OS locked-memory上限、常駐RAM、allocator制約と競合する。OS THP/large pagesやfault-inによるCPU側のTLB/page-walk改善は候補だが、それはDMA用host mapping/pinningやPCI転送rateを自動的に改善する保証ではない。

有限stage案はper-chunk上限を明示する。T=4096、D=10,240 FP32 rowsのchunkは167,772,160 B = 160 MiB。prefix境界を越えるtail copyは最大160 MiB、最終chunkは75,120,640 B。1 slotならHost-USM 160 MiB、2 slot ringなら320 MiB（加えて小さなmetadata/event）で足り、1.25 GB tail全体をpinしない。storeではGPU→pinned slot D2Hを成功waitし、その後CPU `memcpy`でordinary rowsへ保存する。restoreではCPU `memcpy`でrows→pinned slot、H2Dをsubmitし、同じslotを次回CPUで書き換える前にcopy-completion eventをwaitする。copy source/destination、eventとallocationは全てそのwait成功まで生かす。

この案は各payloadについてCPU memcpyを一度store側と一度restore側に足す。tail全体ならlogical CPU memcpy量は最大117.455 GBで、CPU trafficは読み書き合計約234.911 GB。過去の37.58 GB/s non-temporal RAM copy値を単純割りした約6.25秒は別CPU microbenchmarkに基づく理論スケール目安であり、通常`memcpy`の実測でも推論critical path予測でもない。current callbackでD2H/H2Dを既にdrainしているため、1-slot stagingはそれを消さずにCPUコピーを追加する可能性が高い。CPU copyをhideする2-slot overlapは、現在のsame-queue・per-callback checked drain制約を変える必要があり、queue/event/lifetime gateを別途レビューする。第一候補に昇格させない。

## Mainが必要と判断した場合の最小component比較

既存transfer-ceiling targetを再利用し、製品コードやactive model jobへ触れずに、主がGPU slotを管理して同じruntime helperで一度だけ以下を測れば判断材料になる。条件は同じArc B570/current compiler-runtime-driver、同じin-order production queue、`UR_L0_V2_FORCE_DISABLE_COPY_OFFLOAD=1`、`EnableDirectSubmission=0`、同じevent/completion計時。普通hostはfault済み`malloc`、Host-USMは同じcompat `cudaMallocHost`。各armへ同一chunk payload 167,772,160 B（最終chunk 75,120,640 Bを別shape）を使う。D2H、H2Dに加え、D2H完了→host-visible data検証/必要最小CPU touch→H2Dの往復armを実モデル順で計時する。単方向はdevice側source/destinationの準備・verifyをtimed region外へ置く。ordinary/USM allocation kindをABBA順で交互にし、各arm 2 warmups後に3 fresh processes × 7 matched samples以上を推奨。全payload guard/hash、各sampleのenqueue span、event duration、host-inclusive completion、median/range、CPU time、bytes/copy countを保存し、異なる区間を足し引きしない。

まずD2H/H2D roundtripの普通host対Host-USMで差が再現しない、またはHost-USMの改善が追加CPU copyと同等以下ならbounded staging案を棄却し、普通host rowsを維持する。USM単方向が速いだけでもstaging案を採用しない。roundtripでHost-USMに再現する明確な利得があり、有限1/2 slotでhost copy込みの同じ順序でも利得が残る場合だけ、CPU-copy込のcomponent prototypeへ進む。さらに候補を採用するには、error時のlease保持、checked event wait、same queue順序、短文guard、長文residual/logit equality、数値/品質、memory admissionを通し、最後に同一入力のclean end-to-end prefill performanceを測る。帯域結果単独ではwhole-model critical-path benefitを示さない。
