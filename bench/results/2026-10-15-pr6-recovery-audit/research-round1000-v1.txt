# Sub-16-bit MoE activation operands: gathered rows と SwiGLU intermediate

## 1. 先に見るべき設計境界

この調査は MoE の expert 入力 (gather 後の A) と、gate/up projection 後に down GEMM へ渡す SwiGLU 出力 (A2) を対象にする。weight checkpoint の量子化、attention/KV、routing、一般の residual 格納は対象外。

指定 source snapshot の `src/prefill/moe_window.inc` では、routing 後に BF16 `mixed` から expert ごとに `gather_rows16` で BF16 `gathered` を作り、それを `f16_out16` に渡す。出力 `gu` も BF16 buffer で、別 kernel の `native16::swiglu` が BF16 `hidden` を作り、down GEMM が読む。大きさは gather `J*N*2` bytes、GU `J*2*FF*2` bytes、hidden `J*FF*2` bytes として arena に予約されている。従って A と A2 は両方とも短命だが、別々の GEMM 境界にあり、同じ scale lifetime/producer fusion ではない。指定のコード形状はこの snapshot のみを記述し、現行 Main worktree の source/hash を再検証したものではない。

アーキテクチャの主な障害は精度形式そのものより consumer の組合せである。Intel SYCL matrix extension の公開 XMX table は BMG-G21 を含み、sint8×sint8→sint32 および uint8×uint8→sint32 を列挙する一方、FP8 matrix type/tuple は列挙しない。BMG の public XMX/VTune data-format list も INT8, INT4, INT2, FP16, BF16, TF32 で FP8 を挙げていない。従って FP8 の直接 XMX consumption は今回確認した公開 API/documentation では根拠がなく、software emulation、vector conversion、または別機能と見分ける必要がある。`joint_matrix` の種類表は device/runtime による optional capability であり、spec の arch list はこの PC の installed runtime が実行可能である証明にならない。特に別 SKU BMG-G31/B70 の公的 issue では `joint_matrix` query が空でも ESIMD XMX DPAS INT8 は動作したとの報告がある。対象カードの正確な `matrix_combinations`/kernel tuple または選択 backend の実行証明が必要。

さらに current path の expert weight operand は activation とは別で、dequantized FP16 matrix を GEMM に供給する。公開 SYCL matrix combinations に INT8 activation × FP16 weight の混合 tuple はない。よって A または A2 だけを INT8 化しても、それだけで DPAS INT8 GEMM にならない。選択肢は (a) producer で低bit保存してから同じ GEMM 前に BF16/FP16 へ戻す（storage/traffic の便益だけが残り、変換コストが加わる）、または (b) GEMM が直接 8-bit activation を消費するための一時的なweight-side conversion/layoutを設けること。後者はモデルweightの恒久量子化ではないが、weight operand の再表現を含むため、本タスクの activation-only 対象から外れる。INT8 activation を GEMM が直接消費できる実装条件を確認するまでは sub-16-bit activation GEMM を推奨しない。

## 2. Scale granularity と lifetime

* **A: gathered expert input.** Scale は gather 後の各 row の K 軸 group ごとに求め、scale と quantized row を同じ gather slot に対応づける案が素直。row 単位一個の scale は簡単だが、hidden K 中の局所外れ値がその row 全体のレンジを決める。K-group scale は局所レンジを保つかわりに absmax reduction 数、metadata load、scale 配置/strideを増やす。scale はその expert's GU projection の完了まで生存すればよく、別 expert/別 row 間で共有しないのが framework source の per-row/group 型に一致する。expert 全体・window 全体の単一 dynamic scale は大きな値一つが他 row を決め、batch/expert構成依存を入れるため不利。
* **A2: SwiGLU output.** gate/up FP32 math を経た後の **出力 A2** を、row ごとに FFN K 軸 group へ scale して down GEMM 用に保存する。GU の gate/up tensor を圧縮しても、down operand にはならない。scale の生存期間は該当 row/group を down GEMM が読むまで。SwiGLU と量子化を同一 producer に融合すれば、FP32 absmax reduction と quantization を一度に行いつつ BF16 A2 の write/read を省ける可能性がある。ただし直接 XMX INT8 consumer がない場合、後段で BF16/FP16 に戻す必要があり、metadata/convert が圧縮メリットを上回る恐れがある。
* OCP MX の規格化例は 32 consecutive values ごとに E8M0 shared scale を使う MXFP8 / MXINT8。別の vLLM/SGLang DeepGEMM path は `block_size` を選択して per-token-group scaleを持ち、代表例は 128。32 は規格由来、128 は backend tuning/config 由来で同一の標準でも同一のハードウェア最適値でもない。Xe2 target の最適 group を示す測定は見つけていない。scale は FP32 (4 byte) なら32要素で12.5%、128で3.125%の追加領域となる。scale を E8M0 1 byte へ変えてよいのは power-of-two scale rounding と受け側の scale format/layout の両方が対応するときだけ。

## 3. Rounding、saturation、precision contract

vLLM の pinned `fp8_utils.py` では SwiGLU+quant fused kernel が clamp 設定時に input を FP32 で clamp 後に input dtype に戻し、SiLU と up の各項も input dtype に narrow してから elementwise multiply する。その後に block absmax と `scale=amax/fp8_max` を計算し、E8M0 使用時は `2^ceil(log2(scale))` に切り上げ、値を scale で割って FP8 range に clamp して保存する。これは scale rounding が saturate を避ける向きに働く具体例だが、行/群サイズと dtype が呼び出しで決まる。vLLM source comment は C++ activation と一致させるための narrowing を明記している。SGLang pinned DeepGEMM path の fallback は gate/up 演算結果を BF16 `down_input` に一度書き、その BF16 tensor を per-token-group FP8 quantize する。一方 `silu_and_mul_contig_post_quant` branch は activation と quantization を結合して直接 FP8 output/scale を生成する。これらは同じ「FP8 down operand」でも BF16 rounding boundary/一時tensor有無が branch 依存であることを示す。

Main の採用基準に合わせ、上記 source の数学は vLLM/SGLang の該当実行 branch との比較候補であり、単独で現在の model/provider の正解契約を確定しない。実装前に選択された framework backend、activation clamp、SiLU/SwiGLU alpha/beta、BF16 narrowing の位置、scale dtype/rounding、FP8/INT8 conversion rounding、saturation (NaN/Inf含む)、累積精度と出力 round point を対応づけること。SGLang の fused path が BF16 write を省くからといって、その省略が現在の Strata BF16 contract と同じ数値になるとは推定できない。INT8 は通常 scale を含む symmetric quantize/dequantize の定義が必要であり、round mode/zero-point/±127または−128端点を固定しない単なる `int8_t` 化では再現できない。

## 4. Hardware/API と framework source の比較

| 候補 | source-level pattern | Xe2 consumer 根拠 | 今回の判断 |
|---|---|---|---|
| FP8 per-token / per-K-group | vLLM/SGLang で動的 A1/A2 quantization、SwiGLU+post-quant融合の実例あり | 公開 oneAPI `matrix_type`/XMX combination table は FP8 tuple を掲載しない。FP8 は scale metadata も必要 | native GEMM operand としては保留。単なる圧縮保存の価値は full-path計測で別途判定 |
| INT8 per-row/group | OCP MXINT8 (K=32, E8M0) など、row/group amax→scale→clamp/round→INT8 | oneAPI table は BMG-G21 に s8×s8→s32 / u8×u8→s32 を列挙。FP16/BF16との混在tupleはなし | native consumer の候補だが activation-only では GEMM operand pair が揃わない。runtime query/actual XMX proof plus paired operand plan が必要 |
| BF16 fused SwiGLU→down GEMM | gate/up output tile から SiLU×up を計算し、BF16 fragment/register を直接 down GEMM の A operand に流す | Xe2 public table は BF16 pair を掲載。既存のtarget GEMM adapterが BF16 A/Bを消費する source evidence はありうるが fused producer/consumer integration は未調査 | 8-bit XMX capability がない/weights変換が不適格な場合の substantive alternative。hidden BF16 temporary の global write/read を省きうるが、register pressure、pipeline/synchronization、weight layout、row batching次第。速さは未測定 |

A の BF16 fused alternative は、grouped GEMM の expert row batch と GEMM output tile を同じ work ownership に揃え、expert GU output を global memory に一度書いた後 `swiglu` kernel と hidden buffer を介す代わりに、tile内で gate/up pairを読み、activationを計算して down GEMM fragment へ渡す設計。A2 側も同様に SwiGLU result を downstream DPAS tileに直接流せる。これは arithmetic と精度形式を変えずに中間materialization一回を除く案であり、「BF16保存をやめてFP32へ戻す」だけではない。条件は expert ごとの可変 row count/尾tileを正しく扱うこと、gate/up dual-output layout と down B matrix tile の整合、必要な BF16 narrowing を維持、accumulator/reductionは現行の必要精度に維持、fused tileの occupancy と出力列順を損なわないこと。fuseによりweight tileの再利用やoccupancyが悪化する可能性もある。現行sourceにこのfused grouped computeがあるとは確認していない。

## 5. Quantization kernel の cost と評価式

producer-side quantize には最低限 K-group absmax reduction、scale計算/rounding、低bit convert + clamp、低bitとscaleのstoreが必要である。consumer-sideには scale decode/乘算、scale tile load/broadcast または accum後のscale補正、padding/stride処理がある。group-sizeを小さくすると局所精度とscale metadataが増し、大きくするとscale計算は減るが外れ値の影響が強くなる。A は gather が既に行う不規則 source load/store に quant/reduction を融合できる可能性がある。A2 は既知の2-way SwiGLU producer と group quant を融合できる可能性が高く、独立 materialized BF16 A2を保った後別quantする二段版より合理的な出発点である。ただしどちらも直接 8-bit XMX consumerがなければ activation-only speed claim にはならない。

適用判断は経路全体で比較する: gather/projection output→quant/reduction→低bit/scale write→consumer load/scale work→dequantまたはXMX GEMM→output conversion。既存BF16 temporary bytesの半減だけでなく、per-expert小M時のscale reduction launch、kernel launch/subgroup reduction、alignment、K尾、metadata traffic、consumer fallbackを含む。測定は各 operand がどの程度実際に外部メモリへ書かれ/読み戻されたかを含む全依存経路を見て、常に同一の layer/window/token/expert分布で個別サンプルを保持する。現時点でこの比較の測定値はない。
