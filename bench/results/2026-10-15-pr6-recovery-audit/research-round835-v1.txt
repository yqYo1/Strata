# R835 — Time-step reuse and halo crossover in GPU stencil kernels

**Purpose:** knowledge collection. **Question:** when should a finite-difference stencil use a one-step spatial tile, sliding-plane reuse, or multiple time steps per tile? The focus is algorithmic time-step reuse and halo cost, separate from R832’s cache-hint distance, producer roles, barrier phase, and load/compute-stage ownership. No Strata or Xe2 performance claim is made.

## Assumptions and reusable model

Assume a Jacobi update on a regular Cartesian grid with fixed coefficients and two ping-pong arrays: a radius-one 5-point 2-D or 7-point 3-D FP32 stencil (4 bytes per value). In-place Gauss-Seidel, per-step adaptive stopping, or a consumer needing every intermediate field change whether fusion is legal or useful. Fusing can also alter floating-point contraction/order, so check the application’s tolerance.

For a square/cubic tile of B interior cells per dimension, radius r, and T fused steps, a rectangular overlap method starts from a `(B+2rT)^d` input footprint. It computes shrinking output regions: `sum_{j=0}^{T-1}(B+2rj)^d` updates to produce `T*B^d` useful updates. This is a screening count for a rectangular halo, not an exact count for every stencil shape; diamond/time-skew schedules can remove some redundant updates but need more coordination. A dense two-buffer local-storage bound is `2*b*(B+2rT)^d`, with element size b, before coefficients, padding, and compiler allocations. Real sliding-plane methods keep less than this full volume.

| Design | Time-step reuse and local cost | Regular large grid | Boundary-heavy or small grid | Crossover signal |
|---|---|---|---|---|
| One-step spatial tile | Load a tile plus one radius-r halo; reuse neighbors within one update. Local capacity follows the staged footprint; no redundant time-level updates. | Good when coalesced loads and one local barrier amortize over many outputs; cache may already capture neighbor reuse. | Simple masked edges and short tails; no deep halo, but many small tiles repeat halo loads. | Wins if traffic is already cached, few steps run, or a temporal working set cannot fit. |
| One-step sliding plane | Sweep a 3-D axis with a `2r+1` register window and reuse an XY plane in local memory; retain no prior time-step output. | Fits long, regular depth; local state is O(Bx*By + r), not a full 3-D tile. | Thin depth, masks, or uneven dimensions shorten sweeps and increase halo/tail work. | Wins when plane reuse is useful but cross-step halo or synchronization costs too much. |
| T-step overlap or time-skew/diamond | Retain dependencies across steps; overlap recomputes expanding halos, while skewed geometry reduces redundant updates but orders tile dependencies. Local state grows with T and competes with active tiles. | Cuts repeated global traffic/launches when a memory-bound kernel reuses the field for many uninterrupted steps. | Physical boundaries, thin axes and few tiles reduce useful interior; boundary values may need reapplication each step. | Wins only when savings exceed extra updates, local-memory pressure, synchronization, and tails. |

## What the designs actually reuse

A one-step tile shares halo/interior values among adjacent outputs for one update. Intel’s SYCL ISO3DFD walkthrough uses ping-pong fields for a 16th-order (radius-eight) 3-D acoustic wave stencil. Its baseline keeps `front`/`back` Z windows in registers, shifts them, and reads one new depth value per sweep step. The SLM variant stages an XY tile plus halo in `local_accessor`; groups still launch for each time level. The buffer is `(Bx+2r+pad)*(By+2r)` floats, not a multi-step volume. Intel cautions that this SLM optimization may not help Gen9 but may help Gen12LP; this is not a portable performance rule.

For radius eight, the two Z windows alone hold 17 FP32 values (68 bytes) per work-item, besides the coefficient array and other live temporaries. This makes the capacity trade visible: register-window reuse reduces repeated depth loads without storing eight time steps, but it can still raise register pressure. The sample’s Z sweep is useful only when enough planes remain after the eight-point front/back prologue and tail; short depth or a small Z extent amortizes that setup poorly. XY SLM also duplicates the radius-eight halo at each workgroup edge, so large workgroups improve the interior-to-halo ratio until local capacity or parallelism becomes limiting.

SYCL makes the workgroup boundary important: `local_accessor` is shared within a workgroup, and every work-item must reach its `group_barrier`. The specification gives no portable grid-wide barrier or scratchpad-capacity/speed guarantee. A plane tile can use group-local staging; cross-workgroup time skew needs separate launches or supported device-specific coordination. Queueing or cache hints do not make that recurrence safe.

Temporal blocking produces T consecutive time levels before a tile writes its result. An overlapped tile reads a T-step halo and repeats work neighboring tiles also need. A skewed/diamond wavefront schedules only required points but adds dependence ordering, boundary complexity, and synchronization. Hybrid 3.5-D designs spatially tile two axes and stream the third, reducing full-box storage at the cost of shape-dependent tuning. AN5D reports tuned Tesla V100 depths around 8–15 for first-order 2-D and 3–5 for first-order 3-D. High-order blocking is feasible, but these are not default depths.

## Halo, storage, and amortization arithmetic

For r=1, B=32, T=4 in 2-D, overlap computes `38^2+36^2+34^2+32^2=4,920` updates for 4,096 useful updates (1.20x). Two dense FP32 arrays require `2*4*40^2 = 12,800` bytes. Ideal global values fall from `2*T*B^2 = 8,192` to `40^2+32^2 = 2,624` (68% fewer), assuming one read/write per output each step and no cache reuse. Effective caching reduces this headroom.

For B=16, T=4 in 3-D, overlap computes `22^3+20^3+18^3+16^3=28,576` updates for 16,384 useful updates (1.74x). The dense two-buffer bound is `2*4*24^3 = 110,592` bytes, about 108 KiB per tile before other live values. At T=8, storage reaches 262,144 bytes and updates 3.32x useful work. This can force smaller tiles, fewer resident groups, or shallower T. Plane streaming stores less, but cannot remove dependencies or boundary costs. Rectangular halos also overstate the radius-one star’s exact dependency shape.

For this 3-D example, the no-cache baseline model moves 32,768 FP32 values per tile (one read plus one write for four steps); the fused tile moves 24^3+16^3=17,920 values, about 45% fewer. A memory-bound device may trade the 74% extra arithmetic for that reduction, but a compute-bound device, effective cache, or footprint that reduces active groups can erase it. Occupancy is part of the crossover. Query local limits, registers, and spills; total scratchpad does not prove useful occupancy.

Boundary share rises as domains shrink: for fixed radius-one edges, `1 - product(Ni-2)/product(Ni)` is 9.1% on 64^3 and 57.8% on 8^3. A 64x64x8 grid has only 70.3% interior cells. Temporal tiles still need valid Dirichlet/Neumann or periodic halos each step. Fixed physical boundaries must not update as interior; time-varying data must be injected into the recurrence. Small domains magnify masks, tile halos, and device underfill; large grids expose more parallel tiles but repeat overlap halos more often.

A useful break-even test compares the measured cost of `ceil(N/T)` temporal tiles, including a short tail, with N one-step launches. Saved DRAM bytes and launches must exceed extra arithmetic, local traffic, barriers, and occupancy loss. If caching already serves repeated reads, fusion mainly adds redundant math and staging. One step, or a global consumer after every step, offers little cross-time value. Repeated memory-bound Jacobi/wave updates with fixed coefficients and a large interior are favorable.

The number of reuse rounds matters independently of tile depth. If the application requests N steps and T is the tile depth, it runs roughly `ceil(N/T)` temporal tiles; a remainder shorter than T still pays setup and boundary cost, and each tile boundary writes and reloads state. A time-skewed schedule also needs enough independent tiles on each wavefront to keep the device occupied. On a small grid, deeper fusion can cut the number of simultaneously runnable tiles even as it saves traffic; on a large regular grid, that constraint relaxes but halo duplication rises with the number of spatial tiles. Periodic wrapping, fixed-value edges and time-varying boundary injection need distinct halo rules, and these rules must be applied at each internally computed time level, not just once at the beginning.

## Measured counterevidence and evidence limits

Maruyama and Aoki measured single-precision 3-D 7-point diffusion on Fermi and Kepler. On Fermi, temporal `TEMP` remained slightly behind the optimized kernel without shared-memory blocking: L1 already served regular reuse, so staging and halos added work. On Kepler K20X, ordinary global loads did not use L1 the same way; shared-memory plus warp specialization and temporal blocking performed better, reaching 287 GFLOP/s and 1.23x over `SHM-WARP`. Cache behavior moved the crossover; this is not a current-GPU prediction.

Their measured stencil replaces an out-of-grid neighbor at a physical edge with the boundary point’s own value, so it assumes a particular boundary policy rather than a general variable-boundary PDE. Each update is 13 single-precision operations and the paper models an ideal two-float memory stream as only 1.625 FLOP/byte, making memory traffic a plausible bottleneck when data misses cache. The Fermi result is thus counterevidence to unconditional staging for a regular grid, while the Kepler result shows that a changed cache hierarchy can expose the benefit again. Neither result predicts a different device or boundary mix.

The A100 EBISU study adds a capacity and metric caution. For 3-D 7-point, workgroup-level overlap reached 151 GCells/s versus 197 GCells/s with device tiling; authors attribute the loss to overlap halos limiting depth. Lazy streaming also hurt when extra on-chip storage reduced depth while global memory remained the bottleneck. Disabling it doubled T=8 to T=16 and raised traffic-inclusive throughput 2.7 to 2.9 TB/s, yet useful throughput excluding redundant halo fell 2.4 to 2.3 TB/s. This loss is for the authors’ A100/CUDA implementation and tested shapes, not SYCL or Xe2.

Start with a coalesced one-step kernel, then test plane/window reuse if within-step traffic remains. Try temporal depth only when repeated steps are available, capacity permits enough concurrent work, and halo fraction is modest. Count useful updates separately from redundant work and include physical edges and tails. R763 surveys overlapped halos; this report adds crossover arithmetic against plane reuse and capacity-aware depth.
