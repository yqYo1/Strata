## What PR#6 actually does and its enabled envelope

At `d0c5dda:sycl/src/prefill/prefill.cpp:1873-1880`, `STRATA_PREFILL_LAYER_MAJOR=1` selects the new traversal only when the input spans multiple chunks by its `n > T` / first-chunk heuristic; `=2` forces traversal for diagnostic runs. With no variable, the original chunk-major `run_impl` runs. The layer-major routine is at `1917-2073`.

The routine rejects anything except a full-model, one-device, compact FP16 route: it refuses layer slices, helper/peer paths, handoff buffers and missing source at 1923-1926; it refuses each primary QSA state whose `kv_mode != 0` at 1928-1932; and it refuses PLE preload at 1934-1936. It opens a private `ExpertCache` sized for every expert (`1944-1946`), resolves every expert blob for one layer, stages/uploads all experts into that cache, waits for the whole layer, then runs the existing `run_impl` one layer across the full prompt (`1998-2059`). Only after that traversal does it advance to the next layer. Thus its cached experts do not coexist with ordinary stream-ring misses: this is a complete per-layer working set, and `kv_mode==0` (all KV pages resident) is a hard admission condition in that implementation.

The timer is applied to all prompt layers; source says cache upload once per layer, and saved benchmark report explains the intended avoidance of fetching the same expert set for each chunk. It preserves each original chunk's layer math and ordering by calling the existing `run_impl` with the same `n` and chunk selection. It saves `ple_prev` at entry and restores it before every layer, so each layer gets the chunk sequence's intended starting PLE history rather than seeing the final layer's state. Its callback wrapper defers the user's final `on_chunk` callback until the last model layer, while intermediate layer residuals are copied to host/device storage and waited before next-layer consumption.

The original cited 453.29→645.85 result is an own-fork historical result, not an XeStrata engine import or a current-source result. The retained `bench/results/2026-10-14-performance-regression-audit/historical-layer-major/README.md` attributes that paired normal-wall result to 32,768 new tokens, 8K chunks, K8/V8 at 65,538 configured cells, warm PLE, all 32K residual rows in VRAM, no timed MTP, three alternating pairs, all six output heads and IDs matching; medians are 72.289 s / 453.29 tok/s original and 50.736 s / 645.85 tok/s layer-major. It explicitly does not establish physical 256K prefill throughput or MTP. Its separate 256K capacity sample requests 262,146 K8/V8 positions with all K/V resident but processes only two input tokens to test allocation; that is allocation evidence, not a full-context behavior/quality/speed check. These results must not be combined as if the 645.85 run was at physical 256K or MTP.

## Queue, source, and lease audit

PR#6 introduces `ExpertTransferTimer::{device_residual,activation,copy}` by submitting `q->memcpy` operations and retaining profiling events (`d0c5dda:prefill.cpp:~400-430,2041-2051`). The residual event is immediately `.wait()`ed before host rows or the next layer's residual input can be reused. This makes each inter-layer residual copy a synchronous boundary; it is safe by serialization intent but loses cross-layer residual-copy overlap. For GPU-resident residual rows, the bytes are device-to-device; for remaining rows, device-to-host. The host vector is allocated before traversal and remains stable through the routine.

Expert uploads pass `m.stager->wait(e)` to the copy queue, then call `m.stager->issued_one(e, m.copy)` (`2017-2022`); both queues are waited and stager is finished before layer execution. This is the key source-buffer lease release. The copy is submitted once per expert into `layer_cache.device_slot(e)`, and the whole copy queue is drained before publishing `residency[layer,*]=expert slot` and before `run_impl` consumes the new layer cache (`2022-2035`). Before the next layer, the previous layer's residency map range is invalidated, all queues/stager are drained, then the next layer's slots are overwritten. On the normal successful path, the per-layer upload source and destination ordering is explicit.

The runtime adapter is important: current and historical adapter copies are queue submissions, and caller return is not host-source completion. Current `src/sycl/compat.cpp` SHA256 is `225e2021b5ce67b3bb58f116a4a15cd5d592a33dbdf2c9837940a3e89155dca7`; it queues `queue(st).memcpy` and discards the event (`R541` records the source anchors). Same-queue command order does not order a later CPU overwrite against an earlier device read of host memory. PR#6's expert stager path correctly uses `issued_one`/copy completion for its staging slots, but the PR still contains the separately identified `draft_kv` upload defect: `tk` and loop-local `bh` are submitted on the in-order queue for each batch and reused on the next iteration, while its one completion wait is after the loop (`d0c5dda:prefill.cpp:1304-1343,1394`; R541). This is conditional on more than one draft batch and does not mean corruption was observed. The canonical 4K-chunk/MTP batched case can take multiple batches. PR#6 timed baseline excluded MTP, so its speed result does not validate that path. Current `feature/sycl` includes later upload ownership fixes (`332cc372`, `16d9d2b9`) and current source includes `draft_uploads.hpp`; preserve those current fixes when recovering any layer-major functionality.

The local `Restore` guard at `1975-1990` waits compute, copy and stager, then restores callbacks, layer bounds, borrowed residual input, cache/residency/timers and residual storage pointers. Declaration order keeps the local layer cache and vectors alive until after `Restore` runs. The intended lease is therefore: do not expose stack/local cache pointers past this call; drain queued work before local owners die; restore the original decode cache and callbacks even on cancellation/error. However, the destructor ignores the outcomes of all three drains and then restores/frees local owners. A failed/sticky runtime wait can therefore make the guard claim retirement without proven completion. `R541` documents the compat adapter sticky-error caveat; `R542` covers graph-captured pointer lifetime; R547/R548 reinforce that failed wait/destroy/free must keep pointees alive. A recovery needs explicit checked completion and an error path that retains all referenced storage when a drain fails; it cannot rely on this unchecked destructor as a safety proof. Also `std::bad_alloc` after some submissions and stager failures need to preserve/retire source/destination leases before return.

PR#6 does not capture the layer-major loop's kernels in a new command graph. It calls ordinary `run_impl`; there are no new persistent executable graphs whose pointers need teardown. It does run around shared session/MTP graph objects and user callbacks owned elsewhere. The source rejects helper/split but does not reject MTP callback ownership. Its local pointers (`m.cache`, `m.host_res`, `m.residual_gpu`, `on_chunk`, `on_stage_chunk`) must be restored before each later decode/graph replay, as the guard intends. The actual current verifier graph/commit/callback contracts are more sophisticated and were changed after this PR; R542 and R548 show that graph executables can capture raw device/host pointers and require explicit successful retirement before their pointees are freed. A port must not conflate layer-major's temporary residual/cache leases with persistent `SessionState`, verifier/MTP arenas or graph-backed state.

## Persistent state and chunk order

PR#6 does not save/restore the full model between layer passes. It advances each layer's persistent state over prompt chunks in ascending token order by reusing `run_impl`. Before each layer, it restores just the two `ple_prev` scalar values captured at entry; layer-specific recurrent, convolution, KV, indexer, pooled, and PLE table effects are advanced in that layer's own persistent state. This design depends on exactly one complete pass over all tokens per layer and normal chunk boundaries, with no interleaving request/session mutation. The `on_stage_chunk` wrapper marks checkpoint-ready only on the last layer and final position, so intermediate progress is not a full model checkpoint; the final callback is the only whole-model boundary. This is consistent with the historical report and should be retained if revisited.

The physical 262,144 boundary was not exercised by the 645.85 throughput run. `run_layer_major` itself clamps `STRATA_PREFILL_LAYER_MAJOR_R_GPU` using `n`, but the products `(size_t)gpu_tokens * D`, `(n-gpu_tokens) * D` and row offsets have no visible checked arithmetic in the routine. It delegates positional/KV bounds to the existing `run_impl`/layer functions and existing session geometry. Current source has downstream positional bounds (for example `qsa_layer` rejects a position outside `st.max_cells`, and caller session uses `max_cells`); a recovered path must retain caller-level `pos0+n <= max_cells` / `max_cells <= 262144` checks, QSA append/page-table semantics, and checked size arithmetic before allocation/copy. No evidence in this audit proves the historical source's whole physical-limit behavior or the current 256K input length; the current native benchmark actual input was only about 33K per Main's task context.

## Later own-fork work, streamed KV, and recovery boundary

There is no later layer-major or KV-streaming implementation currently selected in the root source. Search of current `src/` and `include/` finds no `run_layer_major` or `STRATA_PREFILL_LAYER_MAJOR`; CMake resolves the root `src/prefill/prefill.cpp`. Existing KV streaming is implemented independently in root prefill/session/layer paths: `run_impl` handles stream/ring modes (`prefill.cpp:937,972,2026`) and `src/core/layer.cpp` owns `kv_mode`, page-map reset/append, max-cell bounds and selection state. The old PR's blanket `kv_mode != 0` rejection means there is no direct “enable layer-major with streamed KV” toggle.

The historical compact/layer-major report and later primary-source audits add useful decisions but not a current adaptation: `historical-layer-major/README.md` documents GPU/host residual split, state-byte equality for selected 257/4096/8087-token cases, normal/long MTP checks, AOT comparison and 256K *allocation-only* capacity; R448/R452 state primary retained the streamed ring and recommends an admitted resident cache slice with the ring as miss/fallback. R548/R547 independently map graph/workspace leases and MTP references. None of these commits a current layer-major source route or demonstrates streamed-KV layer-major correctness. In particular the 256K allocation sample is not a 256K prefix parity/performance proof, and the older full-state/MTP results are tied to their recorded source/binary/recipes, not automatically today's `src/`.

A partial resident-prefix/cache slice could be reconsidered without wholesale replacement: retain primary's chunk-major stream/ring path for cache misses and streamed KV; admit only a bounded set/prefix of complete layer experts when enough VRAM exists, with an explicit reserve and source/cache lease, and fall back exactly to current ring behavior otherwise. But PR#6's benefit comes from avoiding repeat loads across *all* chunks while keeping one layer's full 512-expert cache. A partial subset only helps on repeated hits for those experts and will not reproduce the 453→645 result. For an actual streamed-KV experiment, the right initial design is likely layer-major traversal over each layer while the existing stream append/attention contract still handles its K/V (if the same layer state can advance across chunks without requiring resident pages); source must prove page map eviction/identity, logical cell lifetime, causal selection, host staging and stream reuse order. No such adaptation was found. If attention's stream ring holds only current pages and a layer revisits early chunks later, it may be impossible to reproduce the original layer's causal context unless the stream mechanism retains the required full logical history or can reload it; this needs precise source tracing before coding.

Concrete blockers before replay or port:

1. Resolve exact target/source ancestry and benchmark recipe for the historical PR and its later own-fork descendants. The existing receipt has different 65,538 context, no timed MTP, FP16-only, full resident KV and an older source/binary.
2. Decide whether a new route must support current all-resident KV only or streamed KV. If streamed KV is required, design and source-prove page/append/attention semantics first; simply remove the `kv_mode` guard is unsafe.
3. Port the layer traversal into the actual root source without deleting current root-only features/fixes (including MTP upload ownership, QSA attention selection, current staging/error handling, callbacks, session/service support). Reject unsupported modes explicitly and dispatch opt-in only.
4. Use checked arithmetic for all residual/cached layer byte sizes and enforce the actual `max_cells`/262144 input limit; prove allocation admission accounts for model/cache/session/runtime reserve rather than only `free_bytes` at one point.
5. Replace unchecked restoration/destructor waits with checked, monotonic lease retirement. Keep staged host blobs alive until their copy event completes, keep cache entries valid until all consuming kernels finish, and preserve local residual rows until their D2H/D2D copy completes. On any submission/wait/free error, retain pointer owners and fail the request safely.
6. Inventory callback and graph references from the actual serving/MTP/verifier path. Complete or detach borrowed residual pointers before temporary buffers die; ensure successful graph/queue retirement before freeing captured pointees. Preserve full persistent session state and only checkpoint at the final layer/final chunk.
7. Main-owned validation needs to separate: small source/model-free ownership checks; exact-state/logit parity at odd/even chunk sizes; KV page/stream boundaries; MTP normal and RESTORE/continuation; all-owner/fault checks; near and full physical-bound inputs; then repeated matched B570 performance. Any such execution remains outside this read-only task.
