# Prefill-time head owner deferral audit (R672)

Status: source-only review. No build, test, compiler, GPU, runtime/process, environment, Git mutation, cleanup, or source change was performed. No free-memory or latency delta was measured. This evaluates an owner-lifetime idea only; it does not establish that the memory is currently available or that releasing it improves prompt speed.

## Finding

There is a plausible standalone-only prefill window in which neither the target output-head weights nor MTP's duplicate draft-head weights are read by the ordinary layer-major prompt computation. For the reported current Q6_K dimensions (n_embd=2560, vocab=248,320), their packed weights total 744,699,900 bytes (about 710.3 MiB): 2,100 bytes/row × 248,320 for NativeHead, plus 2,100 × 106,299 for the MTP indexed draft head. This is an upper bound on releasable weight payload, not a measured VRAM-free delta; MTP logits/map, verifier arenas, embeddings, Prefill buffers, and allocator overhead remain.

This is not a low-risk one-line defer. Startup currently couples head load, MTP bind, verifier initialization, auto-cache reservation and decode graph lifetimes. The idea is materially more attractive for a fresh standalone prompt than for a warm serve process. No evidence here supports a speedup or adoption.

## Source trace

- `src/program/generate.cpp:2997-3004` loads `NativeHead` before cache sizing when `--native-head-gguf` is selected. At `:3039-3041`, automatic expert-cache sizing reserves MTP `bind_bytes`; the nearby comment explains the draft head/logits are allocated later. The canonical model table skips `output.weight` for this option at `:2143`, so an absent native head cannot silently fall back to that table's target head.
- `NativeHead::load` in `src/core/native_head.cpp:12-65` reads `output.weight` from the retained shard path and uploads packed weights plus a small Q8 scratch allocation. Its object retains device allocations, not a host copy of the tensor. The destructor frees them; there is no unload/reload API. `generate.cpp` retains `native_head_shards`, so a later explicit reload can reread GGUF, but it incurs a fresh file mapping/read and host-to-device copy.
- Main prompt layers use the configured layer-major residual path and do not invoke the target output head. The opt-in selected-prefill-logits callback at `src/program/generate.cpp:6473+` is an exception: it explicitly runs the target head for selected rows. Any head deferral must disable or schedule that diagnostic separately.
- Prompt MTP is K/V-only. `MtpDrafter::record_forward` appends each row's K/V and returns at `src/core/mtp.cpp:~742` when `full == false`, before the full head projection and sampling code at `:~808-824`. Both batched `Prefill::draft_kv` and the token fallback therefore do not read `head_logits_`, `dhead_`, or target head weights for their prompt work. The serve callback at `src/program/generate.cpp:4961-4978` and standalone callback at `:6431-6450` run this after each completed prompt chunk, inside the prompt callback/timing path.
- Today `MtpDrafter::bind` is not K/V-only: `src/core/mtp.cpp:625-650` saves a borrowed `NativeHead*`, allocates full-vocabulary draft logits, maps the subset and gathers duplicate packed rows from the loaded target head. Later full draft graphs read the borrowed target head (or duplicate rows), the subset map, logits and sampling buffers (`:808-824`). Its prompt graphs (`:896-903`, `:1120+`) are separate and K/V-only. The drafter destructor retires all of these graphs and allocations together (`:122-150`); there is no narrow draft-head detach API.
- The target `Verifier` stores a borrowed `NativeHead*` (`src/core/verify.cpp:239-248`) and uses it for full-window output logits (`:970-992`). It lazily creates window graphs on `run` (`:1204+`); destroying and reinitializing the verifier before first decode can replace the pointer, but the destructor also frees its full verifier arena and host staging (`:215-235`). A long-lived verifier must not be destroyed while a window, completion callback, or async commit is active. The existing `wait_commit` contract is in `include/strata/core/verify.hpp:126-133`; it covers the asynchronous commit, not an arbitrary unfinished window.
- The post-prompt ordinary target path also requires the head: `src/program/generate.cpp:3761+`. Thus a standalone implementation must restore it before first target sampling/verifying. The model shard descriptor survives but the head tensor is not held in a reloadable host allocation.

## Memory arithmetic and boundaries

The calculation above assumes the current output tensor is Q6_K (210-byte blocks of 256 values), so a 2,560-wide row is exactly ten blocks = 2,100 bytes. The dimensions used are output.weight shape `[2560, 248320]` and the current indexed draft vocabulary size 106,299. These are source/model-configuration arithmetic, not allocator telemetry. NativeHead's Q8 scratch is only `native_q8_1_bytes(2560,1)` and is negligible beside weights. MTP's FP32 logits (`max_t × vocab × 4`), subset IDs/inverse map, target/MTP verifier workspaces and `NativeEmbed` are not included in the 744,699,900-byte figure and cannot be called reclaimed by dropping just the packed heads.

NativeEmbed is not a good prompt-window target. `NativeEmbed::load` (`src/core/native_head.cpp:108+`) normally pins/maps the packed embedding host payload; only the fallback owns a device allocation. The global embed is consumed at layer zero by `src/core/layer.cpp:1013+`, and by verifier/MTP layer-zero paths (`src/core/verify.cpp:501+`, `src/core/mtp.cpp:681+`). Releasing it across prompt computation would reintroduce host traffic or require a replacement source; no safe large GPU allocation is established here.

## Standalone versus warm serve

For one standalone request, a possible sequence is: initialize prefill/MTP K/V state without draft-head resources; run the full prompt and its K/V-only MTP callback; retire/drain prompt graph readers; bind/load the output head and draft subset; initialize/reinitialize Verifier with the new head pointer; then begin generation. This is blocked by current APIs because `mtp.bind` requires the loaded head and allocates head resources as part of bind, while `NativeHead` has no checked unload operation. Splitting MTP bind into K/V and decode-head phases, adding checked head release/reload, and accounting deferred bytes in auto cache sizing are prerequisites. The existing auto-cache estimate is made before prompt allocations and explicitly reserves MTP bind bytes; omitting that reserve would risk later allocation failure/paging. `Verifier::init` itself allocates a large arena, so deferring the head alone does not defer verifier memory unless verifier initialization is also moved.

For warm serve, this is substantially less attractive. `serve` binds MTP and initializes the verifier before requests (see `generate.cpp:4773-4801`), then reuses the engine. To retire the packed weights for each long prompt it would need to drain all relevant streams/completions, destroy every verifier graph and verifier arena, retire MTP full draft graphs while preserving the MTP K/V prompt state/graphs, release both owners, then reload/rebind and lazily recapture before decode. It would pay repeated GGUF-to-device transfer, arena churn, and graph capture per request. Any RESTORE/prompt-cache continuation must preserve session K/V and recurrent state while these owner changes occur. The current code has no request-scoped head-retirement protocol or state-continuity test for this sequence. A warm serve might benefit only if the head is already absent at engine startup and stays absent until after each prompt, which still entails repeated reloads.

## Decision

Keep this as a bounded standalone architecture candidate, not an immediate patch or a serve optimization. The strongest blocker is the ownership/API coupling: MTP bind gathers the duplicate head and verifier retains a borrowed pointer, while startup cache admission assumes those decode resources. A future prototype should first add explicit split-phase MTP bind and checked release/reload owners, then prove (1) no outstanding graph/callback/event can read freed storage, (2) prompt K/V and target outputs match across normal, chunked, RESTORE, repeated-request and 262144-context paths, and (3) actual free VRAM rises by the predicted packed-head bytes. Only then is an end-to-end long-prompt timing comparison meaningful. Short-input decode should remain on its current path.
