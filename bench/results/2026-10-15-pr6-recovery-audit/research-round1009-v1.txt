## Mechanisms: different layers

| Method | Work reduced | Dynamic sparse-job behavior | Main tradeoffs |
|---|---|---|---|
| **Command batching/list** | Fewer API submissions; kernel boundaries remain. | Host still constructs/appends each expert command unless one generic kernel consumes device descriptors. | Host encoding/argument updates, list close/submit and reuse; doesn't remove route readback, grouping or variable job creation. |
| **Command graph** | Replay recurring DAG without rebuilding/re-submitting each node. | New routes can be payload to a generic node, or parameters/shape keys can select among supported fixed structures. Arbitrary runtime topology is not implied. | Capture/instantiate/update cost, fixed dependencies, shape coverage, pointer/storage lifetime; SYCL graphs are nonstandard/experimental. |
| **Indirect/grouped descriptors** | One launch covers multiple heterogeneous jobs/tiles. | Device descriptors carry expert, shape/rows, offsets, tile count, output range and tail mask. Assignment may be static or ticketed. | Descriptor production/transfer, bounds/masks, weight locality, shape compromise and load imbalance. Level Zero indirect launch changes grid dimensions; it does not generate arbitrary commands or per-job kernel/arguments. |
| **Persistent scheduler** | Fixed worker grid repeatedly claims jobs/tiles, avoiding host dispatch per task and often balancing irregular jobs. | Fits a finite, already-ready queue; generic consumer loops to queue end. | Atomic/ticket contention, indirection, register/occupancy cost, stragglers, locality and coarse cancellation. No portable global barrier/spin-progress assumption. |

They can be composed, but overheads add: a graph launching a persistent scheduler still has the long-kernel resource/cancel profile; grouped GEMM still has grouped schedule and kernel shape compromises. Determine whether host job construction, API gaps, or device imbalance is material before choosing.

### Transferable grouped-GEMM evidence

NVIDIA CUTLASS grouped GEMM is a single persistent launch over multiple problems. CTAs loop over tiles; a device scheduler maps tile indices to individual problems. `kDeviceOnly` distributes problem-range lookup across a warp; another mode precomputes problem starts on host. This makes explicit the trade: remove repeated host launches by adding device scheduling and descriptors. The docs explain that variable K makes tile durations unequal and show sorting improved a GA100 grouped benchmark by about 30%; that is vendor/workload-specific counterevidence to assuming a generic grouped loop is automatically balanced, not a Strata speed estimate.

cuBLAS grouped GEMM is the library-owned alternative: one host API call supplies arrays of heterogeneous problem parameters. NVIDIA's 2024 original blog shows up to 1.2x against its naive batched baseline in one case. It still requires host descriptor construction and compatible vendor library support; it does not imply oneMKL or SYCL offers the same interface. These CUDA examples are design analogies only, not port sources or Arc evidence.

## API legality and data lifetime

**SYCL standard.** SYCL 2020 standardizes queues, events and USM dependencies, not command graphs, batched command lists, indirect device launch or device enqueue. Commands must be ordered on an in-order queue or through explicit events. Host route/descriptor vectors and copy sources must remain valid/unchanged until their copy completes; device descriptors, weights and outputs must remain allocated until last dependent command completes. Keep queue/context alive through that retirement. An enqueue return is not completion; event/wait completion is the retirement point, while errors still require the configured async error path and checked drain.

**Level Zero.** Core `zeCommandListAppendLaunchKernelIndirect` reads indirect group counts from device-visible memory. `zeCommandListAppendLaunchMultipleKernelsIndirect` takes host-specified `numKernels` and kernel handles, with indirect launch arguments/counts in device-visible arrays. It batches a bounded known kernel set; it is not arbitrary device-generated topology. The v1.18.31 spec requires kernel/events, list and allocations to be accessible/created in the same context and launch arrays visible to that device. Mutable command list is an explicitly experimental extension: mutations target pre-encoded command slots and declared fields/kernels; it is not an unlimited append-from-device facility. Exact adapter/driver support must be queried.

**Graph analogues.** Intel `sycl_ext_oneapi_graph` remains experimental and backend-dependent; graph update concerns supported parameters while retaining graph structure/dependencies. Native recording has additional backend-specific requirements documented in R990. CUDA host graph update similarly changes supported node parameters without changing topology. CUDA device graph launch allows device control flow, but its graph structure is fixed at host instantiation; graph must be uploaded, and a device graph cannot be relaunched from device while its previous device launch is active. Conditional nodes select predeclared subgraphs. HIP provides capture/replay/update APIs with version/platform differences. None of CUDA/HIP semantics proves SYCL or Strata support.

**Forward progress and cancellation.** SYCL 2020 rev. 12 §3.8.3.4 gives work-items weakly-parallel progress; stronger progress is implementation-defined, and barrier progress is guaranteed only within a work-group. A persistent queue can safely have independent workers claim from a finite prefilled array and exit; do not rely on another group running to publish work, or use a global spin barrier. For dependent stages, end the kernel and order the next kernel with queue/events. Bound descriptor count and check overflow/completion.

There is no general portable preemption of a running persistent kernel. A cancel flag may stop future claims, but already claimed jobs can write. Drain while retaining owners, then discard partial output/state and only then recycle memory. Chunk boundaries preserve host stop checks and checked completion points. On failure, do not publish partial session/shared state or allow RESTORE to consume it. Keep checked route ranges, absolute token base and valid tail masks; a graph/job cap must not narrow the required physical 262,144-context path.

## Conditional relevance to the bounded helper

If complete-path attribution shows host submission per expert job dominates, a fixed-capacity descriptor array plus generic GPU consumer is conceptually a closer fit than a graph node per unpredictable job. But if host still reads IDs, builds/validates descriptors, uploads them, and synchronizes inside each backend GEMM call, the device scheduler leaves much of that cost intact. If job shapes/kernels are specialized and topology repeats, list batching or a small set of shape-keyed graphs might be cheaper and preserve tuned kernels; keep eager fallback for uncommon tails. If submission is not material, added scheduling logic is extra cost/risk. No mechanism is selected here.

Future Main-owned comparison should count per real window: host grouping/descriptor time, calls/submits, list/graph update cost, waits/poll separate, route bytes/readback, launch/kernel counts, device gaps/durations, job/M/tile skew, live scratch and complete-path latency. Use fixed inputs/routes/weights; include zero jobs, skew, partial chunks, cancellation, async failure and full-context correctness. Fewer submissions or a faster isolated GEMM does not establish end-to-end improvement.

**Finding:** graphs amortize repeated fixed topology; batching amortizes host submission but retains host command creation; descriptors/grouped kernels and persistent workers move variable job selection onto device at a scheduler/descriptor cost.
