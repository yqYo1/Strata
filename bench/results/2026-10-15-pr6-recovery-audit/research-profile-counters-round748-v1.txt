## Finding

There is no presently usable non-root route to collect the requested counter set on this host. The best official candidate is Intel PTI `unitrace` with its Level Zero Metric API query mode (`--metric-query`, optional `--group`). PTI documents per-kernel query collection and metrics such as `XVE_INST_EXECUTED_XMX_ALL_UTILIZATION[%]`, `XVE_STALL[%]`, `XVE_INST_EXECUTED_SEND_ALL_UTILIZATION[%]`, `XVE_ACTIVE[%]`, GPU memory byte counts and L3 byte counts. Intel documents that BMG/Xe-driver metrics collection for non-root users requires ` /proc/sys/dev/xe/observation_paranoid` set to `0`. Its current read-only value here is `1`; the user is in `render`, and `/dev/dri/renderD128` is render-group accessible, so GPU compute access alone does not satisfy the separate observation gate. No permission or service change is proposed.

The PTI metrics pathway is therefore a capability candidate, not a collection proof or a runnable command for this turn. Prior unitrace work used tracing without PMU metrics (`unitrace-gemm-collection-v1.json` explicitly says “no model/PMU metrics”), so it does not establish counter availability on this installed stack. Existing VTune GPU-Compute collection failed because VTune 2026.4 could not recognize this machine microarchitecture (`vtune-visibility-v2.json`); do not retry it as a counter route. XPU-SMI's official documented EU-array telemetry is system/device telemetry and cannot attribute the requested signals to one prompt kernel. PTI's `--stall-sampling` is documented only for Data Center GPU Max and later, not Arc B570. No per-kernel SLM-traffic or barrier-wait metric is promised by the PTI generic metric examples; availability would have to be proved by enumerating this device's metric groups, which is disallowed here and would still be gated by the sysctl.

## What each available signal would and would not answer

- XMX instruction-pipeline utilization is the closest documented PTI metric for executed XMX/DPAS activity; it is utilization, not necessarily an architectural instruction count or active-cycle count. Confirm the device's exact metric name, scope, and units before interpreting it.
- `XVE_STALL` is a broad EU stall fraction, not the requested dependency-stall breakdown. PTI's generic metrics do not establish a B570-specific dependency reason counter.
- `XVE_INST_EXECUTED_SEND_ALL_UTILIZATION` and global/L3 byte metrics can show send-pipeline and aggregate traffic pressure. They do not directly report global-load sector efficiency or per-kernel cache/DRAM bytes unless this device's metric set exposes explicit byte counters and unitrace associates them with the exact kernel instance.
- The cited public PTI metric set does not establish SLM read/write traffic, bank conflicts, or barrier-wait cycles. Without a named B570-exposed metric, do not infer these from SLM source traffic, compiler metadata, or broad stall percentage.
- `XVE_ACTIVE`/EU activity is useful to characterize device activity, but does not by itself provide occupancy/resident work-groups. ZEInfo `numGRF`/static SLM and local argument size are not dynamic occupancy measurements.

The required separation is consequently incomplete even if PTI became runnable: public docs support likely XMX, broad stall, send/utilization, and aggregate memory signals; they do not guarantee the exact B570 counters or complete SLM/barrier/dependency breakdown. The local metric list/API enumeration is the only safe way to prove exact availability, and it was not executed.

## Current host and prior evidence

- Current read-only metadata: `/proc/sys/dev/xe/observation_paranoid` = `1`; user belongs to `render`; `/dev/dri/renderD128` is group `render` and mode `0660` with ACL marker. No permission was changed.
- Prior actual collection: unitrace trace succeeded on an independent GEMM probe, but its receipt explicitly qualifies it as no model/PMU metrics. It does not establish a prompt-attention counter profile.
- Prior VTune visibility report: `vtune-visibility-v2.json` records the error “VTune Profiler cannot recognize the processor” / analysis inapplicable to the current microarchitecture. This is an actual failed route, not a reason to repeat it.
- Current prompt-attention evidence (`prompt-jit-resources-status-v1.ja.md` and R746/R747 corrections) is static compiler metadata plus source arithmetic. For actual 78,452 batched queries, source says 120,787,680 32-cell tiles, 30,921,646,080 `joint_matrix_mad` calls and 126,655,062,343,680 source-issued FLOPs across 12 layers and two KV heads. These counts are not device execution, occupancy, traffic, or stall measurements. The recorded 69.692 s summed QSA queue spans are nonexclusive and include 12 layers; they are not isolated kernel time.

## Minimal next discriminator without PMU counters

Do not label an alternative timing run as occupancy or stall measurement. For the candidate discussed in R736 (WG64 with two 8-head tiles), the minimum independent discriminator is a source/ISA and component-timing comparison against the current WG128 kernel:

1. Keep the current mode-1 Direct=1 source specialization and input fixed; pin the own-source diff, compiler/runtime/driver hashes, launch geometry, and exact JIT kernel symbol. Build each arm separately and capture only exact-symbol ZEInfo plus matching final ASM/ISA. Map the 8-head split and source barriers/loads/mads to emitted instructions. Compare static GRF, explicit SLM/private metadata, instruction counts and matrix/send instructions; never translate those fields into occupancy or dynamic traffic.
2. Run the existing component harness in separate clean owned processes, same input and repetitions, after Main releases its exclusive GPU lock. Preserve individual times and correctness/fault checks. Use the component duration only to test whether WG64/two-head tiling changes end-to-end prompt-attention component time; do not claim which hardware stall caused a change.
3. If component timing is neutral/slower, close the candidate. If it is repeatedly faster and correct, advance only to a clean long-prefill comparison. No adoption follows from static ISA or component timing alone.

This is the smallest independent test that can discriminate the next 8-head-tile candidate without pretending to observe occupancy. It should be scheduled only after Main's running cohort closes; this research itself made no such run.
