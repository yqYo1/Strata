# R653 — source review of the checked adaptive-event proposal

Date: 2026-10-15 JST. Read-only review limited to `checked-adaptive-event-v1/`, its pinned root inputs, and relevant checked-cleanup, SYCL compatibility, and generate call paths. No existing report/index or code was changed. No test, build, `py_compile`, GPU/native process, Git operation, cleanup, private B tree, log, or environment data was read. Only the new report was written.

## Finding

The proposal is a narrow fail-stop around the two primary adaptive-refill event records: serve and standalone. In the success case it invokes the same `cudaEventRecord` once and returns without adding synchronization or changing pending/publication logic. In the failure case it prints the event status and current SYCL detail, then reaches `_Exit(EXIT_FAILURE)` through the existing cleanup helper. That prevents normal return to either caller, subsequent pending publication/consumer work, and C++ owner destructors. Static review found no concrete blocker in that scoped design.

This conclusion is limited to a single SYCL primary with no stage or peer adaptive path. The serve code still has unchecked stage-event records and the peer path is outside this diff. The proposal identifies these as unqualified/out of scope; it does not make multi-GPU or CUDA/HIP claims.

## Evidence

- All root pins match the current files, including `generate.cpp`, `compat.cpp`, `checked_cleanup.hpp`, `verify.cpp`, `expert_source.cpp`, the index and cited R650 review. Artifact hashes match the proposal files. `reconstruction.json` names the exact `generate.cpp` base SHA and expected proposed SHA. I reconstructed the described include insertion and two callsite replacements in memory without writing files; the resulting hash matches the declared proposed SHA `fd0613c67ec58473f75d6d8b5bcaa55c1b61aaa819d85b079d3c81143f3fb35b`.
- The helper returns directly after one successful record call (`files/include/strata/sycl/checked_adaptive_event.hpp:8-13`). On nonzero result it calls the supplied detail callback immediately, emits scope/code/detail and flushes stderr, then calls the existing `cleanup_fail_stop` (`:14-28`). Its try covers both record and describe callbacks and both standard/nonstandard exceptions also end in the same fail-stop. The existing helper prints the owners-retained message, flushes, and calls `_Exit`, with no stack unwinding (`include/strata/sycl/checked_cleanup.hpp:8-15`).
- SYCL `cudaEventRecord` wraps barrier submission inside `attempt`; a thrown SYCL exception becomes a nonzero CUDA-compatible code while `fail()` stores `detail` and `detail_code` thread-locally (`src/sycl/compat.cpp:47-75,364-379`). `cudaGetErrorString` returns that same-thread detail when codes match (`:589-605`), and the proposal performs no intervening runtime call before retrieving it. The proposal does not clear or replace the original detail with `cudaGetLastError`.
- The diff wraps the serve primary record at the end of the refill enqueue loop and the standalone primary record, under `STRATA_ENABLE_SYCL`, while preserving each original direct call under `#else` (`source.diff`, hunks at 5124/6922). The served source clears the victim's host residency and records the incoming pair in `pending` before recording the event; `apply_pending` later waits/queries that event before moving pending slots into `host_res` (`generate.cpp:5055-5079,5110-5128`). Standalone has the analogous order (`:6850-6864,6911-6925`). Thus on record failure the incoming slot is still unpublished, and `_Exit` prevents reaching a later consumer or ordinary return/destructor path. Success retains the original event and publication order.
- The fixture includes the exact proposal header. Its success subprocess expects `RPCDDD` (record, publication, consumer, then three owner destructors); status-77 failure expects `RE`, and record-exception failure expects `R`. Failure assertions require exit status 1, the retained-owner diagnostic, original injected detail for the status case, and no publication/consumer/destructor markers (`cpu_fault_fixture.cpp:14-43`). This checks helper control flow and failure diagnostics with fake callbacks, not actual runtime/event/DMA behavior or caller integration. `assert` must remain enabled as README states.
- Scope boundary: serve additionally records each `st->adapt_ev` when `st->adapt_live` (`generate.cpp:5129-5133`) and uses `peer.adapt` on the multi-GPU route (`:5138-5144`); standalone has a separate primary loop. These remain unchecked in the proposal. The normal single-primary configuration has peer disabled by default (`generate.cpp:373-378`) and no secondary stage; the proposal is appropriate only under that restriction. Enabling a peer or staged split requires separate event-failure handling and qualification.

## Fixture gaps and unqualified behavior

The fixture does not exercise real SYCL event registration, queue/barrier failures, an in-flight DMA, host-res updates, pending-vector code, or actual source/cache owner objects; publication and consumer are explicit pipe markers. It tests a record callback exception but not a throwing describe callback, although production's actual `cudaGetErrorString` callback is a C API and the helper catches either exception source. The next review/build boundary must still verify the fixture with assertions enabled, compile the integration, and separately qualify native behavior before enabling positive adaptation. The patch does not address H2D submission failures, peer/stage records, ignored device-map upload errors, short exchange commit counts, or any failed-event hardware ownership guarantees beyond process-level fail-stop. It makes no performance, quality, physical-context or RESTORE claim.
