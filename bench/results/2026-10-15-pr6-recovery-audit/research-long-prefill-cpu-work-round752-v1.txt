# R752 — Long layer-major prefill: host work and GPU work

2026-10-16 JST. Read-only source review at the requested base `617647659f21487ff3bf61fa1fd4ba87ba2520bf`. Only this report was created. No build, test, runtime, process inspection/control, profiler/attach, GPU query, environment change, cleanup or Git operation was performed. XeStrata implementation/helper/test/archive source was not read or used. Main's GPU comparison was left untouched. R751 was read first; its Level Zero busy-wait discussion is not repeated here.

## Finding

The requested layer-major path is explicitly a SYCL GPU path guarded by `STRATA_ENABLE_SYCL` and an explicit layer-major request. In the described configuration (native expert source, `STRATA_PREFILL_MMQ=0`, one device, same in-order queue, compact FP16 experts), source shows substantial host work around device kernels: copying each layer's 512 expert blobs into an upload slab, setting up layer/cache/residual metadata, synchronously uploading the layer cache, and regrouping MoE rows after routing IDs are copied back. These are real host-side operations and plausible contributors to a hot main thread. The source does not establish their share of the observed 5-second CPU sample.

No CPU implementation of router softmax/top-10, dense projections/GEMM, QSA selection/indexing, or expert matrix math is selected by the inspected layer-major route. Those operations dispatch SYCL kernels or oneMKL SYCL GEMM on the GPU queue. The source does not show a host task or a CPU-device fallback in this route. Therefore CPU utilization alone does not support claiming numerical fallback/emulation. R751's unresolved stack attribution still applies.

## Path selection and shape

- `src/prefill/layer_major.inc:3-17`: `run()` selects `run_layer_major()` only when `STRATA_PREFILL_LAYER_MAJOR=1`, the implementation exists, and request length exceeds chunk capacity `m.T`; otherwise it calls the ordinary `run_impl()` path.
- `src/prefill/layer_major.inc:20-47`: SYCL build required. It rejects non-native source, anything other than explicit MMQ=0/fallback plan, noncompact expert layout, peer/stage/handoff/reentry and distinct copy/compute queues. `src/prefill/layer_major.inc:49-60` enforces supported model/session geometry and `m.T <= 8192`.
- With actual input 78,453 and `T=8192`, the residual/chunk cursor has 10 chunks (nine full 8,192 chunks and a 4,125-row tail). The outer layer loop is 48 layers (`layer_major.inc:346`); `run_impl` is called for each individual layer after that layer's expert preload (`layer_major.inc:398-410` and subsequent dispatch). This means repeated layer-level execution and a 48-layer expert preload, while each layer's chunk loop totals 78,453 rows.
- `src/sycl/runtime.cpp:12-22,26-28` enumerates only SYCL GPU devices and checks USM aspects; `src/sycl/device.cpp:10-16` exposes that list through the core device API. No CPU device is added as a fallback by this resolver. `src/sycl/runtime.cpp:59-76` binds queues to the selected device; compute is in-order with profiling and transfer is in-order. User-provided `ONEAPI_DEVICE_SELECTOR=0/1` can change enumeration/selection, but there is no “fall back to CPU” branch here. Device 0 versus 1 should therefore be interpreted as selecting among GPUs admitted by the runtime, subject to the actual environment/device list (not independently queried in this read-only task).

## Host numerical work, staging, and transfers

1. **Per-layer expert source preparation (largest explicit bulk CPU-data path).** `src/prefill/layer_major.inc:356-367` clears a `48*512` residency vector over the selected layer, loops over all 512 experts, and calls `m.src->copy_blob(layer,e,upload+e*stride)` serially on the main thread. This is CPU-side source resolution/copy into a single host upload slab. The exact bytes depend on the current native pack's per-layer `layout.blob_bytes(layer)` and alignment stride; no pack byte receipt was part of the request. The loop handles `48*512=24,576` expert blobs across one full prompt, before considering tensor chunk work. `ExpertCache::fill_slot()` is then called for all 512 experts (`:368-381`) and its queue drain completes before the layer is published as resident (`:386-389`). This is host preparation plus H2D, not expert math on CPU.
2. **Layer control and host metadata.** `layer_major.inc:129-160` scans token IDs for range validation, plans residual placement, computes byte counts, allocates the host upload slab/residual rows and initializes a 24,576-entry residency table. `:346-356` checks cancellation and resets 512 residency values each layer. These are CPU control/initialization tasks; token validation is O(78,453), and the per-layer residency clear totals another 24,576 int entries. No model arithmetic is implied by these tasks.
3. **MoE routing-result grouping.** In `src/prefill/prefill.cpp:2484-2486`, the router projection and `route()` are enqueued before expert handling. Unless a diagnostic observer is enabled, `:2580-2604` copies `T*10` expert IDs D2H when not mapped, synchronizes the queue, then on CPU clears expert counts and iterates all `T*10` IDs to count assignments and validate bounds. It builds expert offsets, a fill vector, and walks those IDs again to create slot/source row mappings (`:2638-2653`); it also constructs routed expert order vectors (`:2661-2667`). In this layer-major mode all 512 experts were published resident, so no streamed upload issuer is required. For a full 8,192-row chunk the IDs comprise 81,920 int32 values (327,680 bytes) per layer; over 48 layers and the entire 78,453 rows this is 37,657,440 IDs (150,629,760 bytes) logically examined/copied if the non-mapped route is used. The configured `Direct1`/other grouping mapping can affect actual D2H/H2D mechanics; the source supports both mapped and explicit-copy branches. Host grouping is genuine numeric/index bookkeeping, not a CPU expert GEMM fallback.
4. **Small device-control data and input.** QSA setup reads device step metadata through `steps_host` to derive active selection extent (`prefill.cpp:2311-2323`), while actual scores/top-k remain device operations. Host row/slot grouping tables are copied to device when mapped grouping is unavailable (`:2654-2660`). These are transfer/control costs. The user's QSA device-batch setting and selector 0/1 can alter QSA launch paths; neither option changes the SYCL GPU-only device resolver above.
5. **Layer-major residual and weight traffic.** `layer_major.inc:145-160` computes the residual plan and allocates host rows plus optional device rows/staging. The configured FP32 residual is 78,453 rows × 10,240 floats = 3,213,434,880 bytes (about 2.99 GiB) total logical activation storage. At `R_GPU=32768`, the plan requests 32,768 rows in GPU storage; if the planner places all remaining rows on host, that host portion is 45,685×10,240×4 = 1,870,233,600 bytes (about 1.74 GiB). This is storage sizing, not proof of bytes copied per boundary; actual transfer behavior is governed by the cursor/boundary path and no trace was collected here. FP32 live layer computation remains unchanged.

## Numeric operators and execution location

- **Dense/native projections and router logits:** `native_proj` and `bf16_proj` (`src/prefill/prefill.cpp:1376-1387`) validate native/resident weights and call `Gemm`. `src/prefill/sycl/gemm.cpp:18-29,89-127` sends BF16/FP16 products to oneMKL row-major GEMM on `queue_for(stream)`; quantized native weights are dequantized with `iq_dequant_f16(..., stream)` then passed to the same GEMM. No host matrix multiplication is present in these functions.
- **Router softmax/top-10:** `src/prefill/sycl/postops.cpp:313-324` dispatches canonical 512-expert routing to `native_router_top10_multi(...,&q)`; generic routing uses `router_top10(..., stream)`. The SYCL implementation is selected in this build. The router call at `prefill.cpp:2484-2486` follows the device GEMM. It does not copy logits to CPU in the normal path. Explicit phase-audit copies at `:2487-2494` are optional diagnostic behavior and not part of the supplied no-audit configuration.
- **QSA index and selection:** `prefill.cpp:2291-2308` invokes the native batched QSA indexer for the normal mode; the per-token alternative is selected by presence of `STRATA_INDEXER_PER_TOKEN`. At `:2311-2331`, block scores and top-k selection are launched through kernel APIs, with `qsa_block_topk_prefill` on the layer-major SYCL path. `src/kernels/sycl/qsa_select.cpp:203+` implements the latter. These are not CPU `std::sort` operations on the production route; the `std::sort` seen in `prefill.cpp:2333-2351` is inside the optional `STRATA_SEL_OVERLAP` diagnostic branch, which is not in the described setup. Selector 0/1 comparisons should be interpreted as device kernel variants, not proof of host fallback.
- **Attention/GDN/PLE and elementwise post-ops:** Calls in `prefill.cpp:2203-2217, 2250-2289, 2427-2462` dispatch projections, GDN recurrence/convolution, QSA score/attention, and KV work on `m.cs`. `src/prefill/sycl/postops.cpp` uses `queue_for(stream).submit(...)` / `parallel_for` (for example lines 52-91 and 93-120) for row normalization/mixing; these execute device kernels. QSA block top-k and index kernels are under `src/kernels/sycl/`.
- **Expert projections:** The given config requires compact FP16, native source, `MMQ=0`; the selected per-expert path at `prefill.cpp:3029-3063` calls `iq_dequant_gu_f16` / `iq_dequant_f16` with `m.cs`, then `m.gemm.f16`, `swiglu_interleaved`, and another `m.gemm.f16`. The dequant and GEMMs use GPU queue operations. CUDA-only/fused or MMQ alternatives are disabled by the layer-major precondition, so their presence in the larger source file is not evidence those paths run.

## Waits and evidence limits

`layer_major.inc:282-296` drains compute and copy streams on entry; `:346-350` drains at layer boundaries; `:368-384` submits and drains the full 512-expert upload for each layer. The outer synchronous queue waits can block or poll inside the SYCL/UR/Level Zero runtime. R751 already explains that a Level Zero wait can consume CPU by busy polling; the present source review cannot attribute the measured main-thread CPU to that wait path. Per-chunk MoE grouping also intentionally synchronizes to obtain routed IDs (`prefill.cpp:2580-2604`). Source locations identify candidates, not the observed sample's call stack or time share.

The reported 5-second measurement (native main thread 0.9976 core, other threads zero; no call stack) is compatible with either host-side source/grouping work, a runtime synchronization path, or a mixture. It does not distinguish them. There is no evidence here that unsupported types are silently emulated on CPU: the selected path explicitly requires supported native layout/weights, and SYCL GEMM rejects types without a valid IQ row size (`gemm.cpp:102-112`). A missing/unsupported type would raise/fail rather than route to a CPU numerical fallback in the inspected code.

The largest explicitly quantifiable input-scaled host work is the serial per-layer blob copying (24,576 source blob copies, byte total pack-dependent) and MoE ID grouping (up to 37.7M routed IDs logically handled over this request; exact transfer path depends on mapping). The largest storage/traffic scale is the 3.21 GB FP32 interlayer residual, with requested GPU residency of 32,768 rows and the remainder planned through host storage. Component CPU time and actual transfer bytes require measurement and cannot be inferred from source or aggregate CPU percentage.
