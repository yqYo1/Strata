## Finding and minimum design

A minimal *screening/throughput* comparison is two independent server launches of the official long-generation-only client, one with the shipped profile and one with the prepared CPU-history-first profile, each using the same model/config except profile path, the same 128-slot per-layer cache, `--adapt-swaps 0`, pool 5 with host participation, and three repetitions:

```sh
python3 tools/strata_bench.py --config <baseline-config.json> --long-generation-only --think --runs 3 --out <baseline-results-dir>
python3 tools/strata_bench.py --config <candidate-config.json> --long-generation-only --think --runs 3 --out <candidate-results-dir>
```

`bench.sh --long-generation-only --think --runs 3` is documented as the Linux entry point, but `bench.sh` is absent from the tracked worktree and not resolvable in this environment. The checked-in client equivalent above is auditable. The public v4 suite record shows the applicable engine flags: same native IQ3_S model/pack, max-context 262144, int8 KV with 32768 resident, expert-cache 128, `--expert-cache-per-layer`, pool-workers 5, pcie-frac 0, adapt-swaps 0, MTP4, greedy, prefill4096, no-prefill-borrow, reserve700 MiB. Pool host participation is the default (`host_works = !no_host_worker`); leave `--no-host-worker` absent. Compare only profile path as the intentional variable. Do not use cache auto or raise capacity: same 128 per-layer quota preserves equal arena bytes (281,651,200 B) and isolates the profile ordering. Confirm startup log says exactly 128 filled slots, per-layer geometry, expected source/profile hash, active GPU/model, and that the two launches have matching effective argv and cache bytes.

The client synthesizes the same fixed versioned regular-code and varied-prose prompt for each run number, including deterministic filler generated from `long_prompt`; it alternates workload order on odd/even run indices. It sends temperature 0, thinking on, 16,384 output cap, reasoning budget 0, a fresh request prefix, and needs actual input >=32,768 and generated output >=1,024 tokens. Thus the two arms can share client source, prompt version and run-number inputs exactly. Keep the result folders distinct and preserve their client JSON, server/native startup logs, and durable individual request rows. The `--compare` switch is a report formatter, not an A/B runner.

For a valid paired result require three eligible rows per workload in each arm; each row has normal completion, nonzero engine decode clock, zero reused prompt tokens, sufficient input/output/body, and >=256 offered MTP drafts. The built-in strong/weak MTP classification requires regular-code acceptance >=60% in every run and varied-prose <=40% in every run, separately in both arms. Report per-run and median engine decode t/s, prompt tokens, completion tokens, accepted/offered drafts, output/reasoning hashes and chars. Run a fixed order or interleave whole process arms (A/B/A/B/A/B) across six independently started arms, counterbalanced by replicate; no concurrent service/GPU use. A simpler A then B can support a first screen but confounds arm with thermal/driver time drift. Do not pool output from different prompt versions or remove ineligible runs silently.

## Cache evidence and acceptance

The client stores HTTP body hashes and timing/draft fields but does not itself store expert hits. The native serve source prints per-request `decode expert cache hit rate: ... (hits / lookups)` and startup reports cache slots/fill. Its server log excerpt retains lines matching expert cache/slots/VRAM/hit, but truncates to 80 matches. Preserve complete bounded server logs and correlate each hit line to the immediately preceding request completion in the client request order; verify one completion+hit row for each of six long requests. If that mapping is missing or ambiguous, report aggregate or incomplete hit evidence, not per-prompt hits. Compare actual hits/lookups and rate per matched request as the primary profile-fit observable; verify total looked-up routes agree with engine behavior, and verify no adaptive swaps occurred. `adapt-swaps 0` is supported explicitly and is required because normal adaptive refill would change the initial profile-dependent placement during decode.

This is only a pilot. The official client explicitly marks `quality_qualified: false`; minimum body length and output hash establish neither correctness nor task quality. Retain outputs (within existing artifact policy) and independently check the Python module parses/runs with all 80 expected methods/values and the Japanese story meets its requested content/length. Compare both arms for failures and completion, not just token/speed. Because cached GPU expert arithmetic can differ slightly from CPU output, exact output hash equality is not a correctness gate. Before adoption, require numerical/task-quality acceptance defined by the owner plus repeated clean performance samples with diagnostics/logging disabled, while maintaining same fixed cache capacity. Treat prompt prefill rates and decode rates separately.

## Independence and provenance limits

The preparation JSON pins candidate bytes by SHA-256 `d97b2f483b00341001883537ea4848049b26944c0d14f668b5c43aa88a7a5456`, candidate size 196,632 B, training input hash, and a closed CPU-census receipt hash. R651 states candidate ordering uses only the training receipt's first request recurrence, ranks CPU-owned counts, then falls back to the current prior ranking. The official workload source has visibly different task instructions (integer unit-test module and Japanese story with a named harbor town) and its versioned fresh prompt IDs differ from the training provenance. However, the retained public preparation receipt gives only the training input hash, not its original prompt body/token IDs; the historic producer did not pin the prior profile contents. Therefore exact byte/token-level independence of the training input from the held-out prompt cannot be proven from the reviewed public source/receipts. It is reasonable to call these task families different, but label independence as source-level only unless a non-private, bounded training-prompt receipt is provided and checked.

The training record contains no GPU-owned expert IDs/counts. R649's route-hit bounds remain conditional: GPU-owned frequencies are unknown, not zero, and historic profile content at training time was not pinned. The new pilot can directly observe current per-request total GPU-cache hit counts for both arms, but the default official output does not expose per-expert IDs or route histograms, so it cannot establish why the candidate fits or derive a general route ceiling. A candidate win on these two held-out workload families does not imply general route coverage. Do not present hindsight coverage numbers from the training request as expected held-out hits.
