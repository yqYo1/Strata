# Round 977 — Small-row MoE kernels for the actual GGUF path

## Decision

The actual optimized profile supports a bounded new candidate: for expert pieces with `M=1..15`, fuse GGUF weight decode into the existing 16-bit matrix operation, keep the current full-dequant path from `M=16` upward, and preserve the existing router, activation, combine, and FP32-accumulation boundaries. This is a candidate screen, not a speed adoption. The current source and active pack define an exact per-format decode and the profile shows that these tiny pieces account for half of expert-piece calls but less than one percent of routed rows; no available result says how much of their logical scratch traffic reaches device memory or how much XMX service they consume.

The second viable design is a persistent grouped version of the same direct-decode operation. It could cut per-expert submissions further, but it needs a device-resident expert/count/row-offset schedule and a bounded live set for streamed weight pointers. The profile's host grouping work is only 82.6 ms CPU time, so begin with direct-decode; grouping is justified if an exclusive kernel trace shows launch/submission cost remains material after the small-M data movement is removed.

## What the census establishes

The request contained 39,262 tokens; the batched work counted 39,261 over five 8,192-token chunks, including a 6,493-token tail. Across 48 MoE layers, the closed optimized arm counted 59,614 nonzero expert-piece calls and 119,228 MoE GEMMs. Pieces with 1–15 routed rows account for 30,543 calls (51.23%) and 135,562 rows (0.719% of the 18,845,280 routed rows per GEMM kind). Pieces with 1,024–8,192 rows account for 14,154,159 rows, so this is a selective small-M path, not a replacement for the hot-expert path.

In the recorded active branch, `STRATA_PREFILL_MMQ=0` disables the existing Q8_1 MMQ route. `compute()` in `src/prefill/prefill.cpp` calls `iq_dequant_gu_f16` and `iq_dequant_f16` for the complete expert matrices, then submits GU and down through `f16_out16`; compact mode gathers only that expert's 16-bit input rows. The SYCL GEMM contract takes FP16 inputs/weights, accumulates and applies beta in FP32, and rounds once to its 16-bit output; this active call requests BF16 output. A candidate must preserve the exact existing GGUF-to-FP16 weight decode, the input bits, the BF16 rounding after GU/down, SwiGLU semantics, and FP32 local accumulation. Do not replace these with Q8 activations or a new weight/KV quantization.

For the active dimensions, one expert's combined GU and down weights contain 4,915,200 FP16 values, or 9,830,400 logical output bytes. Multiplying that by the 30,543 small calls gives 300,249,907,200 bytes of possible FP16 dequant writes; the receipt's total 586,029,465,600 bytes uses the same “once per nonzero expert-piece” derivation. Joining each layer's small-row histogram to `native_experts.txt` gives 62,723,174,400 compressed expert-blob bytes associated with the small calls if each call reads its full blob once. These are logical payload/workspace figures, not DRAM, cache, or PCIe counters. The fused candidate would still read/decode the packed weights, but could avoid writing and then rereading the 9.83 MB FP16 matrix scratch per small piece.

The same receipt counts 123,156 total GEMM submissions (2.398 s CPU, 2.752 s host wall), of which it does not split the 119,228 MoE GEMMs from other calls. Host grouping is 240 calls and 82.6 ms CPU. The 58.05 CPU seconds in compatibility waits and 36.77 seconds in route-exchange inclusive timing are not MoE GEMM service; the latter has only 4.1 ms attributed outside waits. Queue intervals include host gaps. Thus grouping is not supported as a CPU-grouping fix; neither device saturation nor a slow XMX kernel is established. The profile's single 459.5 tok/s diagnostic, whole-card samples, requested upload bytes, and PCIe link report do not qualify performance or hardware service.

## Design comparison

**A. Per-expert small-M direct decode + GEMV/GEMM (recommended first screen).** Add a branch at `ne<=15` in the current `compute()` loop. Each GU/down kernel decodes quant blocks as it consumes them, rounds decoded weights at the same FP16 boundary as `iq_dequant_f16`, and accumulates in FP32 to the same BF16 output. Keep existing SwiGLU and compact route ordering. At M=1 or 15, each output tile can load an expert's compressed weights once and reuse them across the rows; no full weight output scratch is needed for that piece. The existing large-M scratch remains allocated for the fallback path, so this does not by itself free VRAM. It keeps the present host route and weight-staging order and needs no additional full-expert VRAM. It still issues work per expert, so it cannot by itself prove a launch-cost win; use device and host timings separately.

**B. Grouped persistent small-expert direct-decode kernel.** Build a descriptor for each small expert (`M`, source-row offset, destination-row offset, weight slot/pointer); one GU launch and one down launch can schedule the active small experts for a layer/chunk, with the current per-layer format pair specialized at compile time. If one group covers each layer/chunk, the upper-bound launch target is 480 projection launches across 48 layers × 5 chunks, rather than 61,086 small-piece projection submissions, plus activation/combine work. A 16-byte descriptor is about 0.49 MB for all 30,543 small calls; route rows add 0.54 MB if their 4-byte indices must be copied separately. These are estimates, and existing device route maps may avoid those copies. Current staging uses eight slots; the largest expert blob is 2,662,400 bytes, so a 16-slot raw-weight window adds 21.3 MB (20.3 MiB) over eight slots. An eight-expert group avoids that growth but needs more waves. Grouped scheduling also risks tail imbalance and scheduler overhead; preserve actual M per expert instead of padding all jobs to 128 rows.

The current Strata MMQ route is a useful but ineligible near-miss: it groups up to 16 experts and directly consumes supported quantized formats, but quantizes activations to Q8_1 and writes FP32 outputs. The fused native route also groups on the GPU but uses integer activations. Its presence, or the `STRATA_SYCL_MMQ_XMX=1` setting in a run where `STRATA_PREFILL_MMQ=0`, is not evidence for a new 16-bit-contract kernel or for active XMX service. Keep the packed-IQ/XMX history distinct from this direct-decode proposal.

SGLang's current Triton runner uses pre-permute, grouped GEMM, and post-permute stages; vLLM exposes backend and per-quantization support tables for grouped/batched expert kernels. Intel's `vllm-xpu-kernels` advertises grouped GEMM and FP8/MXFP4 quantization, but none of these sources establish direct consumption of this model's GGUF IQ formats. Use their scheduling interfaces as design references only. The NVIDIA cuBLAS grouped-GEMM blog reports a 1.2× result for MoE decode batches 8/64 with FP16 on NVIDIA, not this prefill, format, or device. CUTLASS documents persistent device-only scheduling when descriptors are device-produced, while warning that scheduler work matters more for low-intensity groups; that generic scheduler lesson transfers, its CUDA code does not. SGLang, vLLM, and vLLM-XPU are Apache-2.0; CUTLASS is BSD-3-Clause. No external code was copied or adapted.

## Bounded first screen and gates

Run only after Main has serialized the build/GPU slot. First, compare current and candidate component kernels for all seven active type pairs at M={1,15,16,127,128,8192}; use deterministic weights/inputs and device-completion timing, with a small fixed number of warm-ups and repeats, not full-model profiling. Verify decoded FP16 weight tiles bit-for-bit against the existing decoder, then compare GU/down BF16 outputs and intermediate values under the current FP32-accumulate/output-rounding contract. Include a grouped representative histogram with up to eight live streamed slots, and one 6,493-token tail fixture with bounds/canaries. M=1 and 15 must avoid padding/overrun; M=16 must take the unchanged path; M=127/128 must cross the current compact/wide tile boundary correctly; 8,192 must retain the hot path. Stop on any changed route, expert, SwiGLU, output slot, NaN, or bounds result.

The screen must separately record host submit CPU/time, kernel count, exclusive per-kernel device duration, actual DPAS/XMX instruction or utilization evidence, and device/cache/DRAM read/write bytes. Record peak live VRAM while the process is active and staged/upload bytes; do not substitute logical bytes, inclusive phase markers, board power, or `vram_free` at readiness. If direct decode wins only in a synthetic case but the real group shows no lower exclusive time or service bytes, do not extend it. If correct, take a matched full-model comparison only after a clean repeatable 39K cohort, per-model quality/NLL gate, no new faults, and physical 262,144-context/RESTORE checks; the paired packed failure remains failed.
