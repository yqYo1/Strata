# R628 — 32K layer-major censusに基づくMoE GEMM dispatch候補

2026-10-15 JST。読み取り専用のsource・保存済みcensus・過去R601/R619/R620/R622照合。唯一の新規出力は本報告。公式bench.sh full OFF armは実行中のため、そのprocess/artifactを読まず、build/test/GPU/process/Git/実装を行っていない。性能向上は主張しない。

## 結論

候補は二つまでに絞る。

1. **小ne向けnative GPU MMVQ/GEMVを既存FP16 oneMKL GEMMの代替armとして検証する。** 新しいkernelをまず書く前に、既存SYCL `native_mmvq`を使うpilotを別のnative single-GPU opt-in経路で小さいne範囲だけ試す。ne=1/4/8/16の閾値を段階的に比べ、FP16 GEMMへfallbackする。ne≤16は呼び出し数の過半を占めるが行は約1.37%なので、対象は小M GEMM/host dispatch負担であり、総演算量やbytesを大きく減らす案ではない。MMVQはQ8_1に量子化したactivationを使い、現在のFP16 activation × FP16-dequantized weightのoneMKL経路と数値が異なる。独立品質ゲートに通らなければ棄却する。
2. **現行chunk内のnative MMQ grouped expert routeを、layer-majorでも安全に使えるか評価する。** `MMQ_GROUP=16`、`gather_native_group`、grouped `mmq::Product`を持つ既存chunk-major経路を候補部品とする。これはexpert別GEMM dispatchをgroup単位へまとめられる可能性があるが、現行long layer-major admissionは`STRATA_PREFILL_MMQ=0`を必須にしている。単純なflag変更で適用可能とは扱わず、chunk内groupの実形状/順序、bytes、数値、queue/event lifetimeを再確認する。grouped MMQはFP16 oneMKLと異なる計算経路なので品質・速度の結論を移植しない。

同一neのexpertsをoneMKL grouped GEMMへ渡す経路は現行sourceに見当たらず、現censusだけでも機会を数えられない。これは新たなthird candidateにはしない。R601のcross-chunk decoded-weight LRUとfused dequant-to-XMX、およびR622のwhole-prefix deferred expert-majorは既報の別案として重複提案しない。

## Censusの根拠と範囲

`selective-iq-model-assessment-v2.json`は、request input 32,089、batch prefix 32,088、configured chunk 4,096、48層の正確なissuer `ne` censusを保存し、`issuer_exact_ne_verified=true`、`hardware_cache_residency_measured=false`を記録する。native request自体は既存receiptを再利用したもので、このassessmentは`GPU_executed=false`。census validationはcomplete/passだが、`original_status_preserved`はfailed/incompleteを明示している。したがって新しい実行・clean timing・hardware cache measurementと解釈しない。資料上のcensusは8 chunks/layer、32,088 rows、82,878 GU callsと82,878 Down callsを集計する。

集計結果:

| 項目 | 32K census |
| --- | ---: |
| GU / Down issuer calls | 各82,878 |
| GU / Down routed rows | 各15,402,240 |
| active callsの平均ne | 185.84 |
| active callsの中央値ne | 11 |
| ne≤16 | 46,003 calls、55.51%; 210,579 rows、1.37% |
| ne=1 | 13,300 calls、16.05%; 13,300 rows、0.086% |
| GU type 18 | 30,380 calls、36.66% |
| GU type 21 / 22 / 23 | 17,421 / 34,365 / 712 calls |
| Down type 20 / 42 | 67,746 / 15,132 calls (81.74% / 18.26%) |

`ne`は各layer/chunkのrouter groupingから実際のGU/Down issuerへ照合されている。保存summaryは8 chunksを層ごとに集約するため、同じne値のexpertが同じchunkに何個あるか、expert sequence、per-chunk GEMM batch機会は復元できない。Censusのconfigured resident=512はそのlayer's temporary cacheが512 expertsを配置した事実で、GPU hardware cache/DRAM hit率ではない。

## 現行sourceの正確な経路

Configured resolverはSYCL時にroot `src/prefill/prefill.cpp`, `src/prefill/layer_major.inc`, `src/prefill/sycl/gemm.cpp`, `src/kernels/sycl/iq.cpp`, `src/kernels/sycl/native_mmvq.cpp`を使う。`STRATA_PREFILL_LAYER_MAJOR=1`のlong pathはsingle-GPU/native/compact FP16/MMQ=0などを検査し、48 layersを順に処理する。各layerの512 packed expert blobsをtemporary layer cacheへuploadしてから、そのlayerのchunksを実行する。GDN, QSA, PLE, attention/state orderingは`run_impl`の既存block sequenceにあり、この調査の候補はMoE issuer境界だけに置くべき。

Current fallback compute (`src/prefill/prefill.cpp`, compute lambda) はactive expertごとに、同じin-order `m.cs` queueへGU `iq_dequant_gu_f16`、Down `iq_dequant_f16`、compact rows gather、GU `m.gemm.f16(..., ne,1280,2560)`、SwiGLU、Down `m.gemm.f16(..., ne,2560,640)`を発行する。SYCL `Gemm::f16`はoneMKL row-major GEMMを呼ぶ。dequantとGEMMも同一in-order queue上なので順序を持つ一方、非null streamの`finish()`は各eventをhost waitしない。scratch `q=j%DQ`再利用、source residency、adaptive/ring event関係を跨ぐ別queue導入やbuffer reuseは、completed-read lifetimeを保たなければならない。

Layer-major pathは現状MMQを明示的に拒否する (`STRATA_PREFILL_MMQ=0`必須)。Chunk-major `prefill.cpp`には既存`MMQ_GROUP=16`、native group gather、1 grouped GU product + 1 grouped Down productの部品があるが、同じくMMQ経路はquantized activations/packed weightsを使う。これをlayer-majorでonにするのは単なるdispatch selector切替ではなく、layer-major admission、workspace/metadata sizing、group tail、cache-slot release event、Q8 activation quantizationとoutput scatterのsource reviewを要する。

`src/kernels/sycl/native_mmvq.cpp`はmodelのtype 18/20/21/22/23/42を支援し、`native_mmvq`はQ8_1 activation spanとnative packed weightsを受け取る。従ってsmall-ne pilotで使えるexisting compute familyではある。しかしcurrent MoE input `Xs`はFP16; Q8_1 conversionが必要で、current FP16 GEMM contractから異なる丸め/activation errorが入る。GUはconcatenated gate/up layoutを現kernelのoutput mapに正しく繋ぎ、SwiGLU後のDownも同様にする必要がある。Callをひとつのnative routineに置換できるとも、dispatch count自体が減るとも推定しない。まず同じinput/weightsのmicrobenchmarkとnumerical comparisonsを取る。

また`STRATA_SYCL_PARALLEL_IQ_DEQUANT=1`という既存opt-inはGU type 21/22/23およびDown type20/42をparallel-decode pathへdispatchする。type18 GUは除外され、「slower」とsource commentに記載されている。これはdequant内部work mapping変更で、82,878 per-role GEMM/issuer callsやlogical bytesを減らすものではない。現censusでカバーされるtypeの大きさを示す参考armであり、候補2件へ追加しない。Process environmentはexec前に固定し、runtime init後のenv切替をしない。

## 候補の評価に必須の観測・gate

**1. Small-ne MMVQ/GEMV selector**は、ne閾値ごとに該当call数/rows、GU/Down別のlaunches・input conversion bytes・weight bytes・output bytesを記録する。ne≤16の大半がrows 1.37%という集計はhost/kernel dispatch latencyの可能性だけを示し、speedupの根拠ではない。same packed blob/X rowsについて current FP16 dequant + oneMKL output と MMVQ outputをcompare; Q8_1 activation quantization dahil differences. Route/activation precision, accumulation, output mapping and first/last logits plus quality metrics need approval thresholds set before performance timing.

**2. Grouped MMQ**はper-chunk serialized expert list/ne histogram, exact active experts, group boundaries (up to 16 and max rows/workspace limit), padded or zero-tail bytes, gather bytes, active outputs and idle group slotsを取得する。既存per-layer censusのlayer-total histogramはこの情報を含まない。もしsame-ne grouped GEMMを実装候補として再検討する場合も同じper-chunk evidenceが先に必要。Grouped-product countは`ceil(experts/16)`を全layer aggregateへ当てて算出してはならず、real chunk boundariesとgroupsize constraintsで再生する。

両候補でmetadata/admissionは実際の48層format pair・row stride・`up_offset/down_offset/blob_bytes`・actual `ne`・slot/residencyに結合する。現在logical GEMM dimensionsは記録できるが、oneMKL内部tile/padding bytesはsourceから不明であり計測扱いしない。Host census counters/dispatch数はlogical call accountingで、GPU operation duration, busy time, bytes on link/DRAM, end-to-end critical pathではない。

32K pilotは現在のofficial OFF resultと同じmodel/input/profile/cache/KV/residual/MTP/device configurationで一候補だけをonにした別runとし、元OFF armと混ぜない。正しさ/qualityがpassした後、diagnosticsなし・複数matched clean samplesでprefill whole-request wall timeとdecode別時間を測る。64Kはcontext/host-tail and chunk-tail effects、longer route sequence、admission/free-memory differencesがあるため独立baseline/candidate pairとし、32Kのne histogramやhit/grouping結果を外挿しない。Mainのfull OFF benchが閉じる前はbuild/test/GPU作業を開始しない。

## 適用しない候補の理由

- R601's bounded decoded-weight LRUはcross-chunk repeated expert sequenceが必要で、current 32K layer-major histogramにexpert identity/orderがない。R601は既に候補として監査済み。
- R601's fused dequant-to-XMXはformat/shape-specific kernelとstrict FP16 rounding/equivalence proofを要し、call-count problemを解く候補ではない。
- R622's whole-prefix expert-major deferral moves activations/routes and changes scheduling across chunks; it is much broader than issuer dispatch reduction. QSA/GDN/PLE must remain ordered; 32K aggregate census does not authorize it.
- `STRATA_SYCL_PARALLEL_IQ_DEQUANT` changes decoder execution but leaves dispatch counts intact; type18 GU (the largest distinct single GU role share, 36.66%) is explicitly not admitted by that optimization.

ここで選んだ二候補も仮説段階であり、source application, measured speed, output quality, memory admission, or adoptionを意味しない。
