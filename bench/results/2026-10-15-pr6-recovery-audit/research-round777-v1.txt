# R777 — attributing QSA queue intervals to kernel execution

2026-10-16 JST. Purpose: decision support. This is a public-documentation and existing-record review only: no profiler, device query, build, test, process inspection, source edit, or performance measurement was performed. No XeStrata implementation source was used.

## Evidence pins and question

The historical QSA receipt is `qsa-subprofile-model-v2.json`, SHA-256 `4e1764503030726b7bf310aed7501f790a03da1db0af28e1523cf4317a9b49d3`, with analysis `qsa-subprofile-analysis-v2.json`, SHA-256 `ad5cba01b8dbf8cc5be6de21494bd429681e7f672d3756b758f9a7ac1c5951d4`. That closed run used binary SHA-256 `f01e8bd5c9e22f7984594b3928dcefade19b50fb72918c0506986bf25db51241`. Its approximately 69.9 s QSA-attention and 24.4 s selection values are queue marker intervals. The applied observer brackets whole QSA sections with events; the spans include marker submission, host gaps, and any interval between device commands. As R733 records, they are nonexclusive and are not kernel execution or occupancy measurements.

The later build receipt `own-dense-prefill-nll-build-v3.json` identifies current binary SHA-256 `3770ee3c5a85d891c0dd6552ae31d296107b23f44385d13860fc310205712971` and compiler file SHA-256 `1290881b4e12a5e002e5b0de0787f85328ee5fe19f253a54be1cdd97dc2f26eb`; the assigned spec pins the current source snapshot. This build receipt does not pin a loaded runtime map. The available library mapping receipt belongs to a different native binary (`0e62c5fa74cb6a077aef5c5977617e6d74fbd8c2c712ac8f80f3445946289a36`). Its recorded UR adapter and Level Zero versions therefore cannot be represented as versions loaded by the current binary. The spec says installed runtime/IGC files were stable before the live control, but that is not new per-process proof. Any future claim about exact current-stack support must capture the current process's loaded library hashes and the profiler build/version alongside the binary identity.

The selection question is narrower than a general profile: separate each QSA kernel's device execution from its queueing/submission delay and from visible gaps, while associating the kernels with the QSA phase that produced them. PTI documents the needed per-instance timeline without requiring app source changes. Direct source events provide the cleanest same-backend timestamps and exact labels, but require an instrumentation change. Existing phase spans alone cannot make that separation.

## Method comparison

| Choice | What it establishes | Phase association and timebase | Cost, volume, and failure modes |
|---|---|---|---|
| Existing source QSA spans | Barrier-to-barrier elapsed interval per observed QSA section; preserves section order and the current fixed-size output. | Exact source phase and chunk labels, but no per-kernel boundaries. The whole interval is inclusive of device gaps and host submission delays. Summing overlapping spans or treating a share as exclusive is invalid. | Already present; no new source or queue change. Small bounded records. Cannot answer the per-kernel question even if the existing observer passes. |
| PTI `unitrace --device-timing` plus `--kernel-submission` | Device-timing summarizes kernel execution; submission mode summarizes time spent queueing, submitting, and executing. | Kernel/shape totals do not retain the order or phase of each instance. Useful to identify candidate symbols only, not to split the specific QSA intervals. | No Strata source or queue changes. Compact output. Shape aggregation, missing instance order, and profiler version/build mismatch are the main limits. |
| PTI `unitrace --device-timeline --include-kernels-file` | Per kernel instance, reports queueing, submission, device start, and device end timestamps; a selected kernel-name list can reduce scope. This can expose execution spans and the visible gaps between successive instances on a lane. | Name/shape identifies a kernel instance, not the application phase that called it. PTI's existing request-window control captures a bounded request, not an exact prefill boundary. Overlaying PTI's host-normalized trace timestamps on source event timestamps requires a validated cross-clock join; the prior PTI review has not qualified that join for this device. | Lowest-intrusion candidate for the requested discriminator: no app source edits, barriers, new drains, or broad API-call logging. Timeline output grows with included instances; apply kernel filters and the 64 MiB raw-text budget. Filter substrings can include similarly named kernels, and an incomplete/clock-invalid trace is not a result. |
| PTI `--chrome-device-logging` (or `--chrome-kernel-logging`) | A timeline of individual device events; the kernel variant also records host-device interactions and dependencies. | Device-only events do not identify the host phase. Kernel logging adds flow context but no application phase marker; exact QSA association still needs a symbol-to-callsite map or a validated marker join. | Higher trace volume than timing summaries. Device logging omits host calls; kernel logging adds dependency data, but neither is general Level Zero call-duration tracing unless call logging is separately enabled. Filter and externally bound the request; keep collection within the artifact cap. |
| Direct SYCL event records at QSA dispatch sites | `command_submit`, `command_start`, and `command_end` for each exposed event separate submission, device-start delay, and execution on the same backend timebase. Existing event-profiling queues can provide this without extra barrier commands. | Strongest exact phase association if each dispatch stores a small source phase/chunk tag with its event. Differences from submit to start are queue/dependency/scheduler delay, not proof of CPU work; gaps between end and the next submit are visible intervals, not necessarily CPU idle. | Requires source work and access to the returned event for every target dispatch. Read profiling fields only after the existing checked retirement/drain because querying an unfinished event can block. Hidden library work that returns no event remains unobserved. Bound event storage/output and fail closed on missing timestamps. |

Intel PTI's pinned `unitrace` README documents `--device-timing`, `--kernel-submission`, `--device-timeline`, kernel-name inclusion, and separate device/kernel trace modes. It describes `--device-timeline` as per-instance timestamps for queueing, submission, start, and end; inclusion filters reduce overhead and analysis work, but it supplies no quantitative overhead guarantee. The source-free timing path uses the Level Zero collector and does not request metric queries, so it does not depend on the separate PMU metric route. Do not infer occupancy from timing spans.

The Khronos SYCL event reference defines 64-bit `command_submit`, `command_start`, and `command_end` timestamps on an implementation-defined timebase, with timestamps from events on the same backend sharing a timebase. It also says profiling info requires an `enable_profiling` queue and a query may block until the event completes. `command_start` is encouraged, but not guaranteed, to be close to the action's actual start. This supports direct per-event measurement where Strata has the event; it does not prove that every internal library dispatch exposes one or that the installed UR-v2 backend's timestamps meet a device-specific error bound.

## Recommendation and minimum evidence

For the first discriminator, use PTI's `--device-timeline` with `--kernel-submission` and a file of source-mapped QSA kernel names, in a single externally controlled long-request window. Avoid `--chrome-call-logging`, metric collection, new queue drains, and per-kernel barriers. This is less invasive than changing each dispatch site and yields the per-instance intervals needed to distinguish device service from visible queue/lane gaps. Treat `--device-timing` alone as a summary check, not the answer. Use `--chrome-device-logging` only if the text timeline lacks a needed event relationship; it has greater trace volume and does not solve phase labels by itself.

Before interpreting the output, require four items: (1) current exact binary hash plus loaded SYCL/UR-v2/Level Zero/driver/IGC file identities and the unitrace version/build feature record; (2) a source-to-kernel-symbol map for this binary that identifies which QSA callsite launches each included symbol and whether that symbol is unique to QSA; (3) expected instance counts/shapes from the pinned input and QSA section geometry, with all requested events present; and (4) if assigning PTI timestamps by overlaying them on existing barrier spans, a measured, bounded cross-clock alignment check against those same boundaries. If the source map proves each included kernel name is unique to the QSA callsite, phase association can use symbol plus shape/count and does not need a clock overlay. If names are shared or ambiguous, PTI alone cannot prove phase membership; then the least sufficient escalation is a default-off observer tagging the returned SYCL events at QSA submission sites, read only after existing checked drains.

Interpret `command_end - command_start` as event execution duration. Interpret `command_start - command_submit` as submission-to-start delay, not pure host submit time. A gap between one event's end and the next start is a visible interval on the observed queue/engine; it may reflect host scheduling, dependencies, runtime/driver work, or profiler coverage gaps. These timing records cannot say how much was useful work, prove GPU-idle state outside complete lane coverage, or establish a CPU bottleneck. The queue phase sums remain nonexclusive and should be retained beside per-kernel timings rather than converted into exclusive percentages.

## Bounded future experiment

After Main pins current loaded-library evidence and confirms unitrace's actual installed build, collect one long request with unitrace started paused under a fresh named session. Resume immediately before the request and stop after its completion; retain `--device-timeline`, `--kernel-submission`, and only the mapped QSA kernel include file. Keep one request, no metric mode, no API-call logging, a finite wall deadline, and the existing 64 MiB aggregate diagnostic cap; mark a cap-triggered output incomplete. Record exact binary/runtime/profiler hashes, request/input identity, source symbol map, event counts, lane timestamps, and any clock-alignment error. This is attribution evidence only, not a clean prefill speed or model-quality result. After the compact summary is checked against the receipt, remove the raw timeline under the retention policy unless a named open question still needs it.
