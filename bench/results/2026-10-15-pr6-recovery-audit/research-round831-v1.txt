## Findings, ordered by severity

### 1. The product prefill route is not activated in the reviewed source (confirmed)

`Prefill::Impl::native16_active` is initialized to `false` at `src/prefill/prefill.cpp:483`. Searching that translation unit finds no assignment to it. `Prefill::init` calls `native16::requested()` at lines 943–947 but discards the return value; all native16 prefill dispatches are guarded by `if (m.native16_active)` or `typed_qsa` derived from it. This includes `native_proj16` at lines 2327–28, 2361–64, 2640–41, 2680–83, and the expert `f16_out16` calls at 3263–80. Thus the compiled adapter and direct-call evidence do not show that `Prefill::run` reaches the vLLM route in this tree. `Gemm::init_external` only checks the configured backend/device (`gemm.cpp:46–64`, `gemm16.cpp:273–79`); it does not set this flag. If the route is meant to be enabled by the native16 request, initialize the flag from the validated immutable setting and keep the existing default-off gate. No execution was done to qualify that change.

### 2. `native_proj16` can generate calls the vLLM backend rejects when it splits output rows (conditional contract bug)

`native_proj16` at `src/prefill/prefill.cpp:1442–56` chooses `block = gm.scratch_elems()/k`, dequantizes `count=min(block,n-r)` rows of weights, then calls `f16_out16(x, scratch, y+r, rows, count, k, true, n)`. The vLLM adapter's public contract in `include/strata/prefill/gemm.hpp:52–54` and validator in `src/prefill/sycl/vllm_xe2/native16.cpp:41–45, 172–75` require `count % 64 == 0`, `k % 32 == 0`, `ldy % 8 == 0`, and 64-byte aligned spans. The helper does not round `block` down to a legal output width. For example, its current 32 Mi-element scratch divided by `k=6144` yields `block=5461`; if a real projection has `n>5461`, the first call fails the N multiple and the next `y+r` also has a 2-byte offset not divisible by 64. That is a deterministic pre-submit rejection for that geometry, not an asynchronous lifetime issue. I did not establish that a current model projection reaches this split; weight-shape evidence is required before calling it an observed model failure. Round each nonfinal block to a multiple of 64 and verify the final count before dispatch, or reject that projection before dequantization.

This helper also passes an offset output pointer while retaining the original row stride `ldy=n`. The adapter validates `yb=t*ldy*2` bytes from that offset (`native16.cpp:51–58`), a full strided rectangle, whereas the logical touched extent for this submatrix is `(t-1)*ldy+count` elements. This stricter extent can reject a tightly sized standalone output allocation for later column blocks even though the kernel's stores stay within the logical matrix. The current prefill views are carved from FP32 reservations and therefore have additional byte capacity; `m.bo_b16` is backed by FP32 `m.bo` (`prefill.cpp:941–52`), and the QSA typed views similarly reuse FP32 reserves (`978–87`). The expert destinations are also oversized FP32 reserves (`994–1001`). I found no source proof of an actual out-of-bounds store here. Preserve the full-span API contract, but test/validate submatrix offsets against exact allocation extents if `native_proj16` is meant to use this adapter.

### 3. Expert GU/down call geometry is compatible, including partial token counts (source-confirmed)

The fallback expert path calls GU with `(T=ne,N=1280,K=2560,ldy=1280)` and down with `(T=ne,N=2560,K=640,ldy=2560)` at `prefill.cpp:3263–65, 3279–80`. `ne` is the selected expert's routed row count and is not rounded to the backend tile M, but the adapter accepts arbitrary positive `T`; it uses `groups_m=ceil(T/BM)` and the kernel masks logical rows (`vllm_xe2/native16.cpp:51–70, 137–53`). Both N and K satisfy its divisibility requirements. GU input/output row offsets use `scratch_row*N`; down output uses `o0*N`, at line 3280. These are row offsets, unlike `native_proj16`'s column offset. The adapter's full output span is `ne*N*2` bytes from each offset pointer; the source reserves GU as at least `T*K*1280` FP32 elements in the normal noncompact path (`prefill.cpp:702–08, 998–1000`) and Dm as `T*K*N` FP32 elements, so the typed 16-bit expert writes have room for this span. Native GU dequantization builds the interleaved 1280-row matrix before that call (`3237–41`); it is followed in-order by `swiglu`, then the down product. These are shape/offset conclusions only, not execution evidence.

## Ownership and retirement graph

There is no ownership cycle in the reviewed graph. `DeviceArena` owns a `shared_ptr<Allocation>` (`include/strata/core/device.hpp:98–100`); `Allocation` owns a `shared_ptr<Runtime>` (`runtime.hpp:84–89`). The device-span map stores `{bytes, shared_ptr<Runtime>}` only (`runtime.cpp:17–28`), not an `Allocation` or `DeviceArena` back-reference. Compatibility `allocations` owns `unique_ptr<Allocation>` (`compat.cpp:56–60`). The registry's strong owner therefore keeps runtime/context state alive while a registered pointer exists, but does not keep that pointer allocated. `runtime_for_device_span` locks the map, checks the requested range and queue context/device, and returns the entry's Runtime (`runtime.cpp:168–85`). `Allocation::release` drains, frees, then erases that base while holding the registry lock (`239–52`). Move construction/assignment transfers the same pointer and does not add/remove its key (`226–37`); no double-delete path is evident. Allocation-constructor registration failure frees the just-allocated pointer before rethrow (`210–22`).

`Gemm` has no move operation: copy is deleted and the user-declared destructor suppresses an implicit move (`include/strata/prefill/gemm.hpp:21–26`). Its vLLM state is declared before the raw `handle_`, `stream_`, scratch and workspace fields (`75–90`), so reverse member destruction drops those trivial borrows first and then `out16_backend_`. The state declares `runtime` before `adapter` (`gemm16.cpp:26–32`), so reverse destruction destroys the adapter before releasing its Runtime. `Gemm::~Gemm` frees scratch only when it owns it (`gemm.cpp:42–45`); `init_external` marks scratch external and stores the borrowed stream (`46–64`). No duplicate scratch release is apparent for the prefill path: `Alloc::take` records separately allocated scratch in `m.owned` or carves it from the caller's borrowed region (`prefill.cpp:199–219, 912–20`), while `Gemm` has `external_==true` and does not free it again.

For the actual caller, `generate.cpp` creates `main_stream` with `cudaStreamCreateWithFlags` at 2576–81 and passes it to `Prefill::init` at 6759–61. Compatibility stream creation wraps `Runtime::make_queue` in a registry-owned `unique_ptr<sycl::queue>` (`compat.cpp:304–12`). Thus this stream is an additional in-order queue owned by the compatibility stream table, not `Runtime::compute()`. `Prefill::release` synchronizes `m.cs` before freeing its owned buffers (`prefill.cpp:592–608`); `relayout` also drains before rebinding scratch (`1050–76`). `Gemm::f16_out16` returns through `finish(stream_, event)` (`gemm16.cpp:281–315`); for the non-null production stream `finish` intentionally does not wait (`launch.hpp:60–63`). Subsequent GEMMs and native16 consumers remain ordered on that same queue, and the Prefill retirement path is the owner-side drain.

## Remaining lifetime risks (not proven failures)

`Gemm` and the adapter borrow the queue and allocation owners; the adapter header explicitly requires both to outlive submitted work and asks callers to serialize owner retirement (`vllm_xe2/native16.hpp:20–25`). `Gemm` does not retain the queue object or allocation objects. The real Prefill caller keeps the compatibility queue alive in its global stream registry and drains it on release, so I found no current stale queue/runtime pointer on that path. A standalone caller that destroys the queue, Gemm, or a registered owner before completion violates the documented contract and can leave `stream_`/adapter references stale or free live USM; the validation lookup does not pin the allocation after it unlocks.

There is a narrower domain check: both `runtime_for_device_span` and adapter `check_device` compare SYCL context and device equality, not `Runtime` object identity (`runtime.cpp:181–83`; `native16.cpp:73–96`). The adapter initializes its state from X's original registered Runtime (`gemm16.cpp:83–90`) and separately validates W and Y. The actual engine route uses `runtime_for(0)` for arenas and queues, so I found no mismatch there. If two distinct Runtime objects produce equal contexts for the same device, however, a queue created by one can pair with allocations tagged to the other; the queue's async handler captures the creator's separate `Errors`, while adapter `runtime_.check()` checks the X owner's errors. Source alone does not establish that such equal-but-distinct contexts occur in the configured runtime. Either enforce owner identity in the registry/adapter or retain this as a focused source/runtime question before relying on sticky-error checks across independently constructed Runtime objects.

Finally, `Runtime::wait()` waits only its `compute_` and `transfer_` members (`runtime.hpp:21–24`, `runtime.cpp:112–31`); `make_queue()` queues are not registered with Runtime. `Allocation::release()` therefore cannot drain arbitrary extra queues by itself. `compat::cudaFree` compensates by `wait_all()` over registered streams before removing an allocation (`compat.cpp:89–112, 132–48`), and Prefill explicitly drains its queue. Static compatibility maps are declared in order `streams` then `allocations` (`compat.cpp:55–60`), so at exit allocations destruct before queues. The leaked process-lifetime `DeviceRegistry` (`runtime.cpp:22–28`) makes those late erases safe and addresses the older proven function-static destruction bug; it is not a shared_ptr cycle. If process exit occurs with an allocation still used by a custom queue and without the explicit compat free/drain path, `Allocation` teardown's `Runtime::wait()` alone does not cover that queue. This is a conditional teardown/concurrency risk; no current failing exit or double-free was proven. `Prefill::release` ignores sync/free statuses, which merits Main's attention on failure paths, but `compat::cudaFree` retains the allocation when its checked `wait_all()` fails rather than deleting it.
