# R649 — independent audit of profile/cache route bounds

Date: 2026-10-15 JST. Static arithmetic and source review only. I reviewed the bounded closed CPU census receipt, its derived bounds JSON and recipe, the current 196,632-byte public profile, the four corresponding implementation files, and prior cache-census reports. No test, `py_compile`, build, benchmark, GPU/native process, Git operation, cleanup, or candidate/product edit was performed. No model weights or broad private logs were read.

## Finding

The reported arithmetic and its conditions are internally consistent. I found no correction needed to the result values. The important distinction from R607 is that R607's “additional slots” preserved all 128 old resident slots and appended capacity, while the R649 192/256 cases reconstruct a new total per-layer partition. Those new totals can evict old residents from the last layer; the bounds account for the reduced resident set instead of treating added slots as append-only.

## Cross-checks

- The input receipt hash is `17ddf01d…43cb1`; its closed/passed state and empty fresh-fault list are asserted by the recipe. The actual command records `--expert-cache 128`, `--expert-cache-per-layer`, current profile path, `--adapt-swaps 0`, and `--pcie-frac 0` (`cpu-gu-reuse-long-v1.json:2512-2557`). - The current profile is exactly 196,632 bytes, SHA-256 `8f59b4aa…975baf`, and has the expected 24-byte header plus 24,576 unique in-range `(layer,expert)` pairs (`analyze_profile_cache_coverage_v1.py:25-39`). I independently matched the source receipt's pins to current `src/core/expert_cache.cpp`, `include/strata/core/expert_cache.hpp`, `include/strata/core/expert_slot_sizes.hpp`, and `src/program/generate.cpp` (`cpu-gu-reuse-long-v1.json:2576-2577,2688,2765`).
- The source's per-layer slot rule is `q=slots/48`, with the final layer taking the remainder (`expert_cache.cpp:310-319`; `expert_cache.hpp:127-134`). Thus 128 total slots mean 2 slots on layers 0–46 and 34 on layer 47; 192 means 4 per layer, including 4 on layer 47; 256 means 5 on layers 0–46 and 21 on layer 47. The analysis recipe's legacy partition matches that rule (`analyze_profile_cache_coverage_v1.py:76-85`). In `generate.cpp`, per-layer startup fill admits ranked profile pairs only until each layer's range is full (`:3290-3318`), so taking the first quota pairs per layer from the ordered profile is consistent with the current admission/fill path.
- The per-layer bounds use known CPU rows for selected pairs plus GPU rows only for baseline resident IDs retained in the new set. If all old residents in a layer remain, all its observed GPU rows are a valid lower as well as upper bound; if some remain, 0-to-all GPU rows is conservative because original GPU IDs/counts were not retained; if none remain, they contribute zero. These disjoint CPU/GPU owner classes avoid double-counting. For the 192 and 256 shipped-profile partitions, this yields 4,617–5,263 and 5,268–5,914 route rows, respectively, over 104,160 total rows. Fractions 4.43–5.05% and 5.06–5.68% match the report after rounding. These are conditional route-hit bounds, not speed predictions.
- Hindsight CPU ranking under the same legacy 128 quota selects 128 pairs while preserving each layer's quota. Each selected slot's byte size depends only on its layer, so the exact same per-layer slot counts must have the same arena bytes as the original 128 layout: 281,651,200 B. The JSON reports that exact equality, with 10,159 CPU rows for legacy-quota hindsight. The separate global top-128 hindsight set uses 12,325 CPU rows and 266,342,400 B; it is an uneven placement and same-request hindsight, not a held-out result. It is correctly separated from the same-quota comparison.
- The historical CPU-census producer pinned the profile path/source but did not pin the profile contents. The recipe and derived JSON say historical profile identity is unproven and all reconstructed-residency bounds are conditional on the current profile having been present then (`analyze_profile_cache_coverage_v1.py:10-13,27-31,122-130`; JSON `historical_profile_content_identity_proven=false`). Zero overlap between current-profile legacy residents and observed CPU IDs is a consistency check only. Current profile SHA does not retrospectively prove its contents during the old run.

## Explicit clarification versus earlier reports

R607's tables modeled **incremental append** of 128/256/etc. slots while preserving the old 128 residents. R649's current-profile rows instead model **replacement/repartition at the requested total**, which is why the last-layer resident quota falls from 34 to 4 or 21 at total sizes 192 and 256. These plans and their hit bounds are not interchangeable. R624's proposed future capacity sweep remains a measured-run requirement; R649 supplies no VRAM admission, hit performance, physical traffic, numerical quality, held-out fit or speed result.
