The progress text is a stage label, not a program counter. `Prefill::run` chooses `run_layer_major` for a long prompt when `STRATA_PREFILL_LAYER_MAJOR=1` (`src/prefill/layer_major.inc:3-14`). The log explicitly says `layer-major candidate`; that wrapper loops model layers and calls `run_impl` once per layer (`:279-363`). Each layer pass then loops prompt chunks. At each chunk it emits the layer heartbeat immediately before layer work (`src/prefill/prefill.cpp:1976-1980`). Thus the watchdog identifies entry into layer 27's first chunk. It does not show whether execution reached GDN/QSA, host route grouping, a library call, a queue wait, or the post-layer residual callback. The recent phase-audit found no concrete scratch/source-lifetime violation and did not reproduce the old layer-26 numerical discrepancy; it does not cover this liveness event.

## Ranked source mechanisms and discriminators

1. **A host thread blocked in a synchronous queue/oneMKL/SYCL boundary, with an earlier queued dependency still outstanding.** This is the highest-value first split because `run_impl` enqueues many GDN/QSA and native GEMM operations on the same compute queue, while `Gemm::native` repeatedly enqueues IQ dequant then FP16 GEMM (`src/prefill/sycl/gemm.cpp:102-130`). The per-layer routed host grouping explicitly copies routing IDs back and calls `cudaStreamSynchronize(m.cs)` before CPU grouping (`prefill.cpp:2412-2424`); several QSA and layer-major callback boundaries also synchronize/drain. These are real blocking boundaries, but source alone does not show which one was active. The configured layer-major path uploads each layer's 512 expert blobs into a retained slab and drains before publishing residency (`layer_major.inc:287-307`); it disables the normal stream-all and stager/issuer route, so an active staged-copy worker is not the leading explanation here. A simultaneous all-thread stack plus thread identity is the decisive first evidence: a request thread in `cudaStreamSynchronize` / runtime wait points to an outstanding queue dependency or device/library completion; a stack inside an actual SYCL/oneMKL call localizes the host-side boundary. A bounded UR/Level Zero API begin/end trace with thread IDs can then distinguish a long module build or submit from a wait, but the API trace alone cannot explain host work between calls.

2. **CPU-side route construction or model-state/input preparation that is slow or waiting.** With `layer_major_active`, the route uses host grouping rather than the streamed-all expert path. A blocked request stack in `std::fill`/grouping, host memory allocation, source access, or a lock would separate this from a queue wait. The current pool snapshot excludes a worker still computing a claimed job at report time, but it does not prove the request thread was idle or exclude a host wait on another object. The issue is unlikely to be PLE at this reported layer: PLE is enabled only for the layer-1 pass (`ple_on` requires `LB <= 1 && 1 < LE`; `prefill.cpp:1621,1980`), and the log labels layer 27. Similarly, the layer-27 first-chunk marker occurs before its operation sequence, so prior-layer input/output persistence or QSA/GDN state is context, not evidence of a state bug. A stack in host grouping or a repeated identical `futex`/syscall wait across bounded snapshots would promote this mechanism; active CPU ticks and successive stacks changing through grouping would instead indicate long host work.

3. **A long first specialization/module compilation or memory-manager path.** This remains possible because native IQ projections and oneMKL calls may invoke JIT/runtime work, and the same layer-major sequence is repeated per request. It is lower-ranked than a generic queue/host boundary: the same binary already completed two 32K requests and the layer is a later model layer, so this is not a simple process-cold first-use event. Repeated prompts can still encounter a distinct shape/specialization or allocator path. Require a sampled stack in compiler/module creation or a bounded API trace with a clearly long `zeModuleCreate`/module-build interval on the same thread. Do not infer compilation from a quiet kernel log or long elapsed time alone.

## Minimal next capture

For the owner-planned single bounded reproduction, preserve the existing 480-second watchdog and capture one timestamped, symbolized **all-thread** snapshot when the prompt thread enters the established stall window; include thread IDs/names and the named prefill layer/chunk. The trigger must be independent of the reporting watchdog if invoking its abort path would terminate before the capture. Pair this with the planned fixed, flushed markers around the actual blocking source boundaries: (a) entering/leaving the per-layer host route-ID copy + `cudaStreamSynchronize` and finishing host group construction, (b) entering/leaving each GDN/QSA block and each native `Gemm::native`/oneMKL submission with layer, chunk, operator, shape, and host elapsed time, and (c) layer-major callback/residual copy and checked drain. Keep records bounded and make the markers report phase transitions rather than every kernel. This will map the stack to a source operation and show whether the host progressed between samples.

If that snapshot lands in a SYCL/oneMKL submission, the minimum follow-up is a separate single-run, capped UR/Level Zero API trace for module creation and command submission, with timestamps and thread IDs. If it lands inside a queue synchronization, correlate the wait's queue and latest submitted operation; do not call it a GPU hang without a queue/device completion or fault finding. If it lands in host grouping/lock/source code, instrument only that exact operation on the next run. Do not enable broad timeline profiling for this question.

The R475 recommendation was a bounded fixed failure marker plus read-only per-thread `/proc` counters because it addressed a SIGABRT/stack-smash and explicitly avoided stopping a live GPU-owning process. R613 ended via owner stop after a watchdog abort path, has no recorded stack-smash message, and the owner is preparing an isolated debugger snapshot shim. The R475 `/proc` plan remains useful only as a low-perturbation fallback if that planned snapshot cannot be safely bounded; attaching a debugger to the already-running process is outside this review.

## Comparison with prior watchdog signature

R473 concerned a 60-second first-layer heartbeat timeout in an XMX-enabled diagnostic with persistent SYCL cache disabled, followed by `*** stack smashing detected ***`; the related 105.36-second fixture made watchdog-threshold collision plausible but did not prove JIT. R613 instead used Direct-0, made two successful 32K requests first, reported layer 27 after 480 seconds, and records no stack-smash text in the retained tail. There is no evidence these are the same failure mechanism. In both cases the progress marker was emitted at layer entry, and neither it nor `release_gpu_waits ... finished 0 ms` establishes device completion. Current R613's explicit “no active verify spin waits to release; prefill/device drain not assessed,” clean fault review, and later same-binary recovery further limit conclusions to a request-local prefill stall/abort; they do not prove or exclude a host bug, runtime wait, compilation, or transient device condition.

Disposition: retain this as a distinct unresolved liveness event pending a source-mapped host snapshot. No code defect, GPU hang, JIT cause, memory-pressure cause, fix, or performance conclusion is established.
