# R605 — Mode1 INT8 prompt attention CH64 split の最小安全設計

2026-10-15 JST。読み取り専用のソース監査。唯一の書き込みは本レポート。製品ソース、build、test、GPU、server、Git、cleanupには触れていない。

## 対象と結論

対象ソース `src/kernels/sycl/prompt_attention.cpp` は SHA256 `97b1b9e4020b532bfabd5db2245224cfda52bbc793e5891f0e8bbbcb374763e4`。最終の Mode1 Direct route は `launch<1,true,false>` である。R600、R568、R564、MainのR567–568 review、`matrix-direct-probe-v1/implementation.txt`、`prompt-direct-profile.ja.md` と現行ソースを読んだ。

**8+4 head split・CH64・Direct専用の実装は、既存の意味を保った限定的な実験kernelとして設計できる。** query scaleを各WGで独立にtile内計算してはいけない。従来と同じ12-head全体から共通のpower-of-two scaleを各WGが再計算し、各WGは担当するquery行だけ量子化する。softmaxのchunk幅を32から64に変えるためFP32の総和順序とhi/lo roundingは同一にならず、bitwise同等とは言えない。数式上のattention、選択ID、scale/code解釈、hi/lo積、FP32 accumulator、row ownershipは保てる。従って判定は「source設計上は実装可能、数値完全一致は不可、許容差付きの正しさ・実機resource・性能は未検証」である。

初回パッチは Mode1 + Direct=true にだけ新しいgeometryを選ぶ明示opt-in分岐とし、現在のCH32経路を別kernel instantiationのまま残す。CH64を既定化したり4つのKV modeへ広げたりする根拠はない。Direct=falseなら従来CH32を使う。R600後に得た34K128 real-int8 Direct比較（両方108回、same IDs/work、fault 0、44.066 s→29.805 s）はDirectを単独評価する材料であり、CH64の速度・安全性を示すものではない。

## 現行kernelの実際の協力範囲

`HEADS=12`, `CH=32`, `WG=128`（19行）、subgroup sizeは16（84行）。work-groupは1 query × 1 KV headを処理し、gridは `queries * n_head_kv * WG` work-items（82–83行）。従って2 KV heads×12 query headsを1つのWGで処理する。`q` はそのKV headに属す12 query vectorsの先頭（91–92行）。WG内subgroup番号 `0..7` から `hb=subgroup/4`、`db=subgroup%4` を作る。

QKでは4 subgroup（`subgroup<4`）がそれぞれhead band 8行×cell band 16列を処理する。各headはK scale groupを順に処理し、各16-dim sliceでQhi×K、Qlo×Kの二回のjoint-matrix MADを同じFP32 accumulatorへ加算する（154–185行）。従って8-row×16-cell joint_matrix tileで、CH32の2 cell bandsを覆う。P計算はheadごとに32 cellsを昇順に走査し、最大値・`exp`・sumを更新する（188–205行）。

PVでは全8 subgroupが使われ、`hb=0/1` の8-head bandと `db=0..3` の64-output bandを担当する。各subgroupは4つの8×16 accumulatorを持ち、probability hi/lo×Vを二回ずつMADする（235–266行）。Direct=trueの場合は正規化後にglobal outputへ書き、`final` stagingと最後のbarrier/copyを省く（269–290行）。Mode1では `KG=VG=4`。QおよびPはFP16 hi/lo、INT8 codeはFP16へ正確に変換、FP16 per-64 scaleはFP32で適用し、matrix accumulatorsはFP32である（28–64行）。

`matrix_available` は subgroup16、matrix combination (fp16,fp16,fp32,8×16×16)、work-group上限と現在のmode別local-memory下限を確認する（315–342行）。ソースの `local_accessor` 総量とdevice/compiler実allocationは別物。Unitrace propertiesのstatic SLM 4096 Bをこの動的accessor量やoccupancyに読み替えられない。

## 提案する最小geometry

最初は **8+4** splitだけにする。`WG=64`（4 subgroup×16）、`CH=64`、local row数8とし、2 WGが1 query × 1 KV headの異なるquery headsを担当する。8+4ならtile0はglobal heads `[0,8)`、tile1は`[8,12)`、後者のlocal rows 4..7は無効として全てzeroにする。6+6は別のgeometry選択・検証を増やすため初回には入れない。

work-group indexを以下で展開する。

```text
index = group_linear_id
head_tile = index % 2
kvhead = (index / 2) % n_head_kv
batch = index / (2 * n_head_kv)
head_base = head_tile * 8
live_heads = head_tile == 0 ? 8 : 4
```

Gridは `nq * n_head_kv * 2 * 64` work-items。最大 `nq=65535`, `n_head_kv=2` で約33.6M work-items、64-bit `size_t`の積は安全。work-group indexからの出力・query strideは引き続きexternal `n_head=24`, per-KV `HEADS=12` を使い、8はlocal tile strideだけに使う。

```text
q_group = query + (batch * shapes.n_head + kvhead * 12) * HD
out_row = batch * shapes.n_head + kvhead * 12 + head_base + local_row
```

QKとPVのsubgroup割当ては4 subgroup全てで次のようにする。

```text
subgroup = local_id / 16       // 0..3
cell16 = subgroup * 16         // QK: four 16-cell bands cover CH64
output_band = subgroup         // PV: four 64-dim bands cover HD256
```

QKは各subgroupが同じ8-row query tileをロードし、`scores[8*64]` の担当cell bandだけを書き込む。PVの各subgroupは `output_band*64 + j*16` の4 output tilesを処理する。`hb` は常にlocal tile0で不要になる。`joint_matrix` shapeは現行の8×16×16、QK/PV共にFP16 A/B・FP32 accumulatorを維持する。

### 共通Q scale

現行は12 query heads全体（3072値）から `qm` を取り、同じpower-of-two `qup/qdown` を12行すべてに使う（94–103行）。WGごとに担当8/4行だけから`qm`を取ると、半精度hi/lo分解が変わる。各split WGで同じ`q_group[0..12*HD)`を走査して現行と同じwork-item分担・work-group reductionを行い、共通の`qup/qdown`を得る。その後、local `qhi/qlo[8*HD]` には `q_group[(head_base+r)*HD+d] * qup` を保存し、`r<live_heads` の範囲だけ実queryを読み、pad行は0にする。`head_base`は8/0で、どちらのWGも`qm`の参照範囲は同じである。これにより有限Qでtileごとのscale起因の丸め差を避ける。共通scale reductionをWG64化後も従来と同じ順序/NaN挙動と主張せず、有限値fixtureで現行との差を確認する。

## local accessor量とadmission

mode1 + Direct=trueで、source declarationを8 local rows/CH64へ置換した場合のpacked logical bytesは以下。alignment・compiler spillを含まない。

| accessor | 計算 | bytes |
|---|---:|---:|
| qhi/qlo | 2×8×256×2 | 8,192 |
| kv | 64×256×2 | 32,768 |
| phi/plo | 2×4×8×64×2 | 8,192 |
| scores | 8×64×4 | 2,048 |
| ks, vs | 2×64×4×4 | 2,048 |
| maxima/sums/alpha | 3×8×4 | 96 |
| factors | 4×4 | 16 |
| final Direct dummy | 1×4 | 4 |
| rows | 64×8 | 512 |
| **total** |  | **53,876** |

Indirectなら `final` が8×256 floatsとなり、追加8,188 bytesで **62,064 B**。したがってCH64初回はDirect-onlyが妥当。現行host guardのmode1閾値60,880 Bは候補Directのdeclared sumより大きいので、そのguardは保守側に維持できる。ただしこれは実allocation測定ではなく、kernelのコンパイル、実local allocation、register/spill、device admissionの証明にはならない。candidateだけのためにhost閾値を低くしない。`max_work_group_size>=128` の現行確認もCH32分岐に影響を与えず維持し、splitの64要件を別確認するか、既に128を満たしたdevice上だけcandidateを許可する。

## barrierとjoint_matrix収束監査

CH64 loopでは `count` が同じquery/KV/tileの両WGで共通なので、2つのwork-groupそれぞれの全work-itemが同じ `c0` 回数を通る。次の全WG barrierをtile-local branch/early returnの内側へ移動してはならない。

- loop前（現125行）: Q tileと初期softmax stateをpublish。
- row/score準備後（142行）: `rows` とゼロ初期化scoresをpublish。
- K/scale stage後（153行）: joint-matrix QKが `kv` / `ks` を読む前にpublish。
- QK出力後（187行）: 全score store完了後にsoftmaxが読む。
- V/scale stage後（216行）: softmax更新、`vs`、V tileをpublish。
- factors算出後（223行）: probability scaleをpublish。
- phi/plo変換後（234行）: PVがhi/lo tileを読む前にpublish。
- PV更新後（267行）: 次chunkがscores/kv/phi/ploを再利用する前に前chunkの全読出しとacc更新を完了。

Direct-onlyならfinal-store barrier/copy（286–290行）は不要。joint_matrix constructor/fill/load/MAD/applyの全てを各subgroupの全16laneでconverged control flowから呼び続ける。`subgroup<4` は新WGでは全subgroupが真になるが、条件を残してもgroup-uniform。head validityは `joint_matrix_apply` のelement callback内部のstore条件で処理し、joint_matrix call自体を `local_row<live_heads` のwork-item分岐に置かない。pad Q/score/P/Vは明示zero、`rows=-1` でsoftmaxから除外する。これにより無効4 headが結果をglobal outputへ書かない一方、subgroup matrix collectiveは全laneで揃う。

Intel oneAPI matrix extensionは `joint_matrix` collective操作のconstructor、load/store、MAD、fill、elementwise operationsがsubgroup全work-itemのconverged control flowで実行されること、組合せがoptionalでmatrix combinations queryで確認すべきことを明記している。既存の `[[sycl::reqd_sub_group_size(16)]]` とmatrix-combination probeは維持する。

## FP32順序と意味の境界

CH64は数学上同じ選択セル集合に対するonline softmaxだが、現行演算順をそのまま保てない。

- QKの各cell/dim内では4 scale groupsを順に処理し、各groupでhi MAD→lo MAD、そのFP32結果に `scale * qdown` を加える順を保てる。CH変更でK-dimの順序やscale順を変えない。
- ただしCH32のsoftmaxは32 cells単位に `l` を昇順加算し、各chunkで `sum=fma(old_sum,alpha,l)`。CH64は64 cellsで一つの`l`を作るので、FP32足順とonline-update境界が変わる。
- `factors[g]` は現行32-cell tile内のmax `abs(Vscale)`。CH64では64 cellsのmaxになる。scaled probability `p`, FP16 `phi/plo` rounding、PV hi/lo MADとrescale境界が変わる。
- PV accumulatorは各CH32 tileごとに `acc = alpha*acc + part*down`。CH64では一つの64-cell joint tileで`part`を作るため、FP32更新回数は半分になる。

よって安全な主張は「同じselected IDs、code/scale解釈、softmax数式、二成分hi/loのmatrix積を保つ。浮動小数丸め差はあり、現行とのtolerance比較が必要」。bitwise parityを必須gateにしない一方、source auditだけでtolerance PASSにもならない。Direct store indexingはhead write coverageを個別確認する。

## context 262144 とindex/stride

論理cell ID `262143` はsigned int32に収まる。`cap=262144`、1 queryあたりids spanは `cap*4=1,048,576` bytesで、host側`checked_count(nq,cap)`を通る。`c0`と`tid`をint32のまま足しても、最終tailの最大 `262080+63=262143` でありINT_MAXを超えない。`batch*cap+c0+tid` は `batch` がsize_t、checked spanが先に検査されるため64-bit address arithmeticとなる。gridやoutputは最大query数65535と24 heads×256を含めても64-bit積で収まる。

CH64へ拡張してもrow mappingは変えず、`cell<0`を先に扱い、そうでなければ `page_table[cell/page_size]`、`row=(int64(page)*n_head_kv+kvhead)*page_size+cell%page_size` を使う。ページ内offset・global head strideの置換はしない。`cell=262143`が有効かつ安全である条件は caller がIDを実context内に制限し、page tableに `floor(262143/page_size)` を含む有効範囲を用意すること。kernel自体は正の`cell`上限を `QsaShapes` から検査せず、page-table長やpool容量もAPIで受けない。これは現行契約/呼出側の境界であり、splitで新たな保証を得るわけではない。small fixtureで262143を使う場合は高logical pageを小さいvalid physical pageへmapし、実pool allocationとtable範囲をfixture側で確保する。大きなcontext数をIDの数値だけで検証済みと扱わない。

## 実装差分の擬似コード

既存kernel本文は保存し、`launch_mode1_ch64_split<Direct>`（初回は`Direct=true`のみ）を追加するのが低リスク。Mode1のみに限定すればKG/VG=4、INT8 code/scaleの意味も固定される。dispatchでは明示的な新env opt-inがあるときだけ新launcherへ進み、それ以外は旧 `dispatch<1>` のまま。Direct=false candidateは作らない。

```cpp
constexpr int C64 = 64, R8 = 8, WG64 = 64;
submit parallel_for(nd_range(nq * 2 * n_head_kv * WG64, WG64),
                    [[sycl::reqd_sub_group_size(16)]]) {
  decode batch, kvhead, tile; head_base = tile * 8;
  // group-wide same range as old 12-head qm; same qdown/qup
  qm = max_abs(q_group[0 .. 12*HD));
  qhi/qlo[0 .. 8*HD) = split_hi_lo(q_group[(head_base+r)*HD+d] * qup)
                        for r< (tile==0 ? 8 : 4); pad others to zero;
  initialize maxima/sums for 8 rows;
  barrier;
  for (c0=0; c0<count; c0+=64) {
    stage 64 selected rows, using same page lookup; tail/unmapped => row=-1;
    zero scores[8*64]; barrier;
    stage K codes and four scales; barrier;
    // each sg 0..3 handles one cell16 band; preserve scale-group and hi/lo MAD order
    QK joint_matrix operations; barrier;
    per-row max/exp/l/sums update over cells 0..63 in ascending order;
    stage V scales and V codes; barrier;
    factors over 64 cells; barrier;
    split scaled P into phi/plo; barrier;
    // each sg owns one 64-dim band; 4 accumulators, same hi then lo MAD
    PV joint_matrix operations and online FP32 update; barrier;
  }
  normalize each 8x16 accumulator element;
  joint_matrix_apply(..., [&](r,d) {
    if (r < live_heads)
      out[(batch*24 + kvhead*12 + head_base+r)*256 + d] = value;
  });
}
```

実際の差分はlocal shapesで`16→8`, `32→64`, `WG128→64`, `scores/maxima/sums/alpha/phi/plo`のrow extent、QK subgroup mapping、PV `hb/db` mapping、query/output row indexing、launch gridをcandidate instantiationだけに適用すること。outputの`24`/per-KV `12`は現行external stride。全ての`HEADS`および数値定数をlocal row countへ機械置換しない。count validation、negative IDs/page、empty row、K/V mode selection、host span validation、finish/error path、current routeを変更しない。

## 最小正当性確認セット（設計。未実行）

1. **全24 output rows coverage:** `nq=1` と `nq=3`、既知出力を返すsynthetic INT8 data。全出力と前後guardを検証し、24 headsの各elementが一回だけ書かれ、tile間重複・穴がないことを確認。`nq=3`はbatch decodeも検査する。
2. **split-scale bug検出:** tile0のheadに最大abs Q、tile1のheadに小さいQを置いたcaseと逆向きcase。共通12-head scaleを使うcandidateが基準CH32の注意出力に近いことを確認する。tile-local qmを誤用すると差が出る設計になっている。
3. **tail / row handling:** widths/count `0,1,31,32,33,63,64,65,2051`、特に63/65/2051の部分CH64 tail。負ID、page=-1、非identity page、zero scale、all-missing。空/欠落rowがゼロでsoftmax除外されること、部分tileのpadding読みがないことを確認。
4. **long logical index:** `cap=262144`、selected ID `262143` を有効なpage-table entryとbounded physical poolへmapした1-query fixture。さらにinvalid/out-of-range ID契約をcaller fixture側で拒否するか、明文化された上限を確認する。これはfull physical 256K residency/RESTOREの証明ではない。
5. 各shapeで既存CH32 Directと全24×256 outputsを比較し、有限値・guards・独立FP64 referenceを確認する。既存 `STRATA_TEST_PROMPT_MATRIX` tolerance `1e-5*(1+abs(ref))` を初期比較閾値として使えるが、候補値がこのgateを通過した結果はまだない。実際のmodel logits/greedy IDs、long-context retrieval/RESTOREは別の上位gateとして Main が必要性を判断する。
