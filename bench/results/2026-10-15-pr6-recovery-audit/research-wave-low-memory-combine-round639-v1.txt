# R639: Lower-memory wave MoE combine under ordered-FMA semantics

Date: 2026-10-15
Scope: read-only design research. No source, build, test, GPU, process, Git, or cleanup action was taken.

## Finding

The current SYCL combine has an explicit numerical order that rules out a generic scatter-add as an equivalent replacement. For every output scalar, `moe_combine` initializes `v=0`, applies valid routed contributions in top-k slot order `k=0..9` using `sycl::fma(weight, routed_value, v)`, then adds the shared contribution. Any memory-saving schedule must retain that per-token sequence, including skipped slots, and retain shared-after-routed ordering.

The present expert-major wave path materializes routed outputs for the full wave (`W × K × N` FP32), then combines. R633's per-expert GEMM microbatching bounded the GEMM scratch but did not remove that full-wave `Dm`; R637v2 also corrected the accounting to avoid treating aliased regions as simultaneously free. The basic memory floor is therefore clear: there is no free full-wave output buffer to alias. Existing `m.bo` is only the current chunk's output buffer. Any proposal must explicitly budget a new accumulator or reduce/defer the retained routed values.

Primary local source: `src/prefill/sycl/postops.cpp` (`moe_combine`, approximately lines 248–267) and the route preprocessing / expert stage in `src/prefill/sycl/prefill.cpp` (approximately lines 2413–2484 and 2800–2898). Line numbers can move; inspect the current worktree before implementation. Reports reviewed: R621, R622, R623, R628, R633, R636, R637v2 and R638; also `layermajor-wave-census-v2`.

## Candidate schedules

### 1. Token-output-tiled expert-major wave

Keep the current route table and wave prepass, but compute and combine output tokens in tiles of `B` rows. For a tile, run experts and write only `B × K × N` routed values (or use existing `m.Dm` capacity when `B` is bounded by the configured chunk), combine with the unchanged slot loop, then commit its `B × N` output before reusing the tile. The routed-output footprint becomes `B × K × N × 4` bytes instead of `W × K × N × 4`; it can be reduced by `W/B` while retaining one expert evaluation per active expert per wave if the execution structure supports all tile writes from a single expert pass. If expert passes are repeated for each tile, dequant/GEMM work repeats by `ceil(W/B)`; this is the principal tradeoff. A concrete mapping must show how an expert's wave rows are visited across output tiles without re-reading/recomputing its weights unnecessarily.

This is distinct from R633: that report bounded expert input/GEMM microbatches but left full `W × K × N` `Dm` intact. Tiling the *output retention and combine* is the new part. It appears the lowest-risk exact-order direction if shared/gate/router state for the wave can stay resident and a tile can be retired safely.

### 2. Rank-major / slot-outer accumulation

Use one `B × N` FP32 accumulator, initialized to zero. For each slot `k=0..9`, visit experts and their rows whose route belongs to slot `k`, compute that route's down projection, then update the destination token accumulator with `sycl::fma(weight[t,k], y, acc[t,n])`. After slot 9, apply the shared term and store. This makes the routed-output plane unnecessary (up to 10× less output retention at equal row extent), and fits the existing chunk `m.bo` if `B` is a normal chunk. It directly preserves the required FMA sequence.

The likely cost is repeated expert work: an expert active in several slots may be dequantized / projected once per slot rather than once per wave. Before pursuing it, census active expert counts by slot and the per-expert slot multiplicity for representative q2/q4 wave sizes. Existing `layermajor-wave-census-v2` only records aggregate counts/union and does not retain slot IDs, so it cannot establish this cost. No runtime benchmark has been run for this proposal.

### 3. Route-precedence DAG and SCC-bounded retention (diagnostic first)

For each token, add directed edges from each valid route expert to the next valid route expert in slot order. If the wave's expert dependency graph is acyclic, process experts in a topological order, scattering each expert result into one token accumulator. Every token's predecessor contribution is then complete before its successor, so its FMA order is exact while each expert is still evaluated once.

For cycles, condense the graph into strongly connected components (SCCs), then process SCCs topologically. Contributions crossing between SCCs can be accumulated when their source is emitted. Only outputs whose ordering constraints remain within the current SCC need be retained; the peak intra-SCC route count, rather than all `W × K` routes, bounds the required temporary output plane. If the graph is one large SCC, this offers little or no reduction. Correctness requires edges from each consecutive valid slot pair (skipping invalid slots consistently); duplicate expert IDs must preserve repeated FMA operations in their original sequence. This is an exact dependency argument, not a claim that observed graphs are sparse.

Recommended bounded diagnostic: in the existing optional observer, consume the host route IDs while they are available, form a 512-node adjacency bitset (32 KiB), and report per wave/layer/q only compact summaries: edge count, SCC count, maximum SCC size, intra-SCC route count, and per-slot active-expert counts. Do not persist raw IDs or tensor/session captures. Census-v2 as reviewed does not currently retain the edge/slot information required. Record observer bytes and owner under the repository's artifact policy before extending it; the existing report describes a small bounded observer, but capacity must be checked against its actual cap.

## Scale of the retention target

For `K=10`, FP32 routed output costs `W × 10 × N × 4` bytes. At `N=4096`, this is 160 KiB per token; at `N=8192`, 320 KiB per token. Illustratively, for `W=8192/16384/32768`, that is respectively:

| W | Dm at N=4096 | Dm at N=8192 | one FP32 output accumulator at N=4096 / 8192 |
|---:|---:|---:|---:|
| 8,192 | 1.25 GiB | 2.50 GiB | 128 / 256 MiB |
| 16,384 | 2.50 GiB | 5.00 GiB | 256 / 512 MiB |
| 32,768 | 5.00 GiB | 10.00 GiB | 512 MiB / 1.00 GiB |

These are arithmetic sizing examples, not measured wave sizes or allocated bytes. They show that slot-major whole-wave accumulation alone still requires a large `W × N` output plane. Chunking it to `B` rows is essential if the accumulator is to fit the existing output chunk. For a genuine tile `B`, multiply the one-accumulator figures by `B/W`; likewise multiply Dm by `B/W` if only tile outputs are retained.

## Lifecycle and correctness constraints

- The prepass's mixed/shared/router data and route metadata remain live until their consumers finish; Rstore and other region aliases cannot be counted as free output storage (see R637v2 correction).
- A tile's output storage is reusable only after the ordered combine and all dependent same-queue writes have completed. Do not infer that a delayed callback or host polling makes it safe to overwrite. R638 notes MTP already batches E-9 by chunk, borrows `R_rows`, and still needs storage for delayed callbacks; moving a callback is not itself a memory or speed win.
- Keep routing-slot weights and offsets tied to the original token/slot. Preserve invalid-slot behavior and shared-after-routed addition. Test numerical results against the unchanged path on the same route table before considering speed.
- Do not switch runtime environment variables in-process for comparisons. Use separate processes or explicit test parameters, consistent with `docs/ARTIFACT_RETENTION.md` and AGENTS.md.

This is a structural precedent only. The referenced `master` URL is moving, and its documented strategy does not establish this fork's route-slot FMA order or a numerical contract.

## Recommendation

First add or adapt a compact route observer to obtain slot multiplicity and SCC statistics on representative q2/q4 waves. Then prototype a chunk-sized output tile with unchanged combine order and explicit storage-lifetime accounting. Use the census to decide whether rank-major slot passes or SCC scheduling can reduce repeated work enough to justify implementation. Do not select any candidate on presumed graph sparsity, and do not adopt generic scatter-add for a bitwise/order-sensitive comparison. No candidate is validated or recommended for production based on this research alone.
