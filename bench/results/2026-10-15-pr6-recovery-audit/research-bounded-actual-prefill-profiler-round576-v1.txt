# R576 — bounded actual-prefill GPU service attribution

Date: 2026-10-15 JST. Read-only design review for the current configured root SYCL path and the already-qualified PTI/unitrace provider. No source/build/test/GPU/profile run, Git mutation, cleanup, process/service inspection, or private environment, secret, or agent-log access was performed. The only new artifact is this report.

## Decision

For the first actual-model collection, add a default-off diagnostic gate that collects **one complete MoE layer-chunk from the same 32K+ prefill**. If that trace is complete, useful, and stays inside budget, add one or two preselected layer-chunks in later, separately bounded runs. This tests the actual route/shape path with one contiguous capture window and only one pair of boundary fences. It can show whether that layer-chunk's `gemm down` phase consists mostly of Down device kernels, copies/dequant/gather, or same-queue gaps; it cannot reconstruct the exact 61.535 s all-layer bucket by scaling up one sample. If it is necessary to cover route variation across all request chunks, the gate may select one layer across chunks, but collection must pause/resume for each disjoint layer-chunk window in execution order; it must not leave collection on between chunks, where it would record unrelated layers. That version adds a fence pair per selected window and should be admitted only if the one-window result stays within overhead and event budgets.

If the decision requires a whole-request sum that can be compared directly with 61.535 s, a whole-prefill trace is ultimately required. That should be a separate explicit exception run with a hard **512 MiB total trace/output cap**, prompt/input fixed to the already-qualified 32K+ case, immediate offline extraction and raw-trace retirement after checks. This is a ceiling, not a prediction that a full trace will fit. If the owner cannot enforce the cap or the validator cannot prove completeness, stop with `incomplete`; do not retain a partial trace as a qualified result. A kernel-name filter is not a safe substitute for this full capture.

VTune Ryzen/XPU collection remains rejected and must not be retried. Reuse only the existing PTI source/provider revision `6c0d6b0b80c6dbac4b5902d9d5ade1c75b9e9033` and pinned binary. Do not rebuild/reinstall PTI. The historical external-UTC gate remains false. The old synthetic hot-GEMM trace (739 device events) proves only its operation mapping and same-kernel descriptor groups; it is not whole-model evidence.

## Why a bounded layer capture is implementable

The current CMake resolver selects `src/prefill/prefill.cpp` plus `src/prefill/sycl/{gemm,postops,blob,moe_mmq,moe_fused}.cpp` through `cmake/sycl_backend.cmake`; the historical CUDA source/layout is not the configured engine. In the currently audited native compact-FP16 MoE branch, a routed expert goes through native dequant, optional compact-row gather, GU GEMM, SwiGLU, then Down GEMM. The queue passed to these operations is the non-null compute queue. The SYCL `Prefill::init` path aliases copy/compute queues for this route; `queue_for` requires an in-order SYCL queue, while `finish(stream,event)` intentionally does not wait for a non-null queue. Thus host-return/phase-marker intervals are not GPU service intervals, but one queue's submitted order is a usable join key once all queue work is fenced at the diagnostic window boundaries. Khronos SYCL 2020 defines in-order queue commands as executing in submission order, with no ordering promise across distinct queues.

R575/R575 Main review corrected the phase attribution: the Down phase marker is followed by the next expert's Dequant marker, so later expert dequant/gather/GU service should not simply be charged to the preceding Down phase. Host lookahead/stager work, host submission gaps, and queue waits can still occur between those markers. Existing `STRATA_PREFILL_TIMING` is explicitly a queue-marker accumulator that charges the time between marks to the earlier phase. It does not expose exclusive device service. The one-layer trace should keep those concepts separate:

- **Device service:** sum device execution intervals for operations matched to the target layer's Down role. Because the selected compute queue is in-order, its own operations should not overlap. Show any other queue/engine activity separately.
- **Queue gaps:** time between consecutive device operations on that queue. Call these *same-queue gaps* unless every device engine/lane is covered and idle; a queue gap alone does not prove the GPU was globally idle.
- **Host wait/submission:** Level Zero host API intervals and already-planned aggregate host counters for routed Down submission, `Stager::wait`, host copy submission, and worker memcpy/service. Do not convert `Stager::wait` duration to GPU service.
- **Copies:** classify each copy by its actual source/destination allocation ranges and allocator API; a profiler's `M2D`/`D2M` label alone is not proof of physical pinned-H2D bandwidth.

No additional in-stream wait should be inserted between expert phases. Add one queue drain before collection is enabled to clear earlier work and one drain after the selected layer's last chunk has been submitted; disable collection only after that tail fence. The trailing fence's host wait should be reported as a collection-boundary drain, not charged to an expert role. These fences perturb the diagnostic run and make it unsuitable for throughput qualification.

## PTI collection controls and output

The pinned upstream `tools/unitrace/README.md` at the existing provider revision documents:

- `--chrome-kernel-logging` for device activity plus host/device interactions and dependencies; `--chrome-call-logging` for Level Zero/OpenCL host calls; `--chrome-itt-logging` for ITT-instrumented application regions. Keep default device thread and engine/queue lanes enabled, and request `--pid --tid`.
- `--start-paused` plus in-process `PTI_ENABLE_COLLECTION=1/0` toggles on Linux and Windows, or ITT `__itt_resume()`/`__itt_pause()`. ITT pause/resume takes precedence if both mechanisms are used. Use one control mechanism only. For this design, use the documented env toggle around the selected layer and ITT named tasks for its source-role labels; the agent binary must accept the flags in the pinned build before a collection is admitted.
- `--include-kernels`/`--exclude-kernels` filters are substring filters on kernel names. They cannot select a model layer, expert role, chunk, or source call site. Excluded kernels are not counted in total device time. A GEMM-only filter would omit copies, dequant, gather, SwiGLU, and other queue work, so do not use it for this attribution.
- `--device-timeline` (`-t`) prints each kernel/command's queued, submit, execution-start, and execution-end timestamps. `--kernel-submission` (`-s`) is an aggregate summary of append/queued, submit, and execute intervals, not a source-role timeline. Use the Chrome/Perfetto timeline as the primary joined evidence; `-t` may be an optional cross-check if it stays within the same budget.
- `--chrome-event-buffer-size` is a count of events **per host thread**, default unlimited; it is not a file-byte cap or a documented completeness guarantee. `--output-dir-path` is only a destination. Neither provides a hard output budget.

## Minimal source and collection recipe

A small diagnostic-only source patch is required to select a layer/chunk range and to label source roles. Keep its default disabled; gate it with a dedicated, exact opt-in environment switch and target layer/chunk values. Place the selector at the root `Prefill` routed-layer/chunk loop in `src/prefill/prefill.cpp` (near the existing routed FP16 observer and phase marker definitions around `PfPhase`, and the streamed `compute` lambda around the current native compact-FP16 branch). Do not instrument the 90K expert calls with printf, per-expert files, queue queries, extra events, or waits. Add low-volume ITT task labels at the existing role boundaries—copy/stager, Dequant+Gather, GU+SwiGLU, Down, and combine—with layer/chunk in the enclosing task. Retain the existing default-off routed observer and add only aggregate Down host-call count/duration bins (`ne<=16`, `17..428`, `>428`) and the planned `Stager::wait`, memcpy-submit, and worker-service totals. These CPU aggregates are corroboration only; they are not GPU critical-path attribution.

For the first run:

1. Use the same model, input, chunk size, source resolver, queue topology, memory mode, and 32K+ request as the unprofiled main result being diagnosed. Select one exact MoE layer-chunk; do not replace the model path with the standalone GEMM binary.
2. Drain the selected in-order compute queue, enable collection for this one contiguous layer-chunk, mark source roles, and collect the existing Level Zero/SYCL-runtime-independent timeline (`--chrome-kernel-logging --chrome-call-logging --chrome-itt-logging --start-paused --pid --tid`). Avoid `--chrome-sycl-logging` unless the first trace cannot resolve queue/submission behavior: it adds SYCL and UR layers and event volume, while this target is the actual Level Zero device work plus its host/API handoffs.
3. Immediately after the selected layer-chunk has submitted its final queue work, fence that same queue, close the source task, disable collection, and continue the exact model invocation normally. For a later all-chunks sample, repeat steps 2–3 around each matching disjoint layer-chunk; never keep collection enabled across intervening layers. Keep any asynchronous staging worker evidence under the existing observer's lifetime rules; do not detach workers or read slots after teardown.
4. Require native child PID/start-ticks from the owner receipt; host API and ITT rows must belong to that native process. Device-lane PID is commonly a provider-assigned lane PID and need not equal the native PID: match device rows through the recorded host-to-device flow/operation IDs, Level Zero context, actual device metadata, and the selected queue/lane. Require Arc B570 metadata and the expected operation/copy/kernel sequence. Do not assume a category named `Flow_H2D` establishes payload direction; R487 showed those flow labels indicate causal flow. Match actual allocation APIs (`zeMemAllocHost`/device/shared and/or corresponding UR USM allocation calls) to source/destination address ranges for every included memory copy. Reject an event set that cannot distinguish the compute queue from another queue or prove its copy endpoints.
5. Run with `UNITRACE_SystemTime=1` in the unitrace environment and record `CLOCK_MONOTONIC_RAW` immediately before provider/native launch and after native exit in the wrapper. Qualify this run only if the *actual GPU trace in this mode* is shown to use the same RAW domain: trace event times are ordered, agree in units/conversion with those wrapper RAW bounds, and fall within them (allowing a documented launch/exit bracket). The existing 32-sample CPU-header check proves only that the pinned header selects RAW under this setting; it does not qualify a GPU trace. Do not shift old trace timestamps or turn them into UTC.

## Budgets, checks, and rejection

For the initial one-layer collection, set an owner-enforced **64 MiB total trace/output ceiling**, 300 s wall deadline, 8 GiB owner-session RSS ceiling, and a finite `--chrome-event-buffer-size` of 65,536 events per host thread. These are collection limits, not PTI completeness semantics: continuously monitor aggregate output bytes, stop the owner before the hard cap, and mark the receipt incomplete if stopped. If the captured layer needs more than 64 MiB, raise the ceiling only in a reviewed, explicit next-run record; do not silently roll over. For the whole-prefill exception, the sole larger ceiling is **512 MiB total output**. State file cap and cleanup/compaction owner before starting. Immediately extract compact per-role counts, device durations, same-queue gaps, matched copy bytes/durations, ITT boundary IDs, event counts, PID/device/queue identity, RAW-bound test, and hashes; then retire the raw timeline under the artifact-retention lock/manifest once that compact evidence is verified.

Set a prospective instrumentation-overhead budget of **5% of the matched unprofiled prefill wall** (or the larger measured baseline repeatability band, declared before collection). Compare the same workload/settings with profiling disabled/enabled; if the profiled wall exceeds that budget, the trace can still be diagnostic only if it is complete, but timing must be rejected as a representative service estimate. No overhead for this provider/this source path has been measured, so 5% is an admission threshold, not a claim.

Reject or label the collection incomplete if any of these occur: raw-domain gate fails; native process identity or B570/queue identity is missing; allocation/copy endpoints cannot be matched; selected layer/chunk tags or expected role sequence are absent; event IDs/flows have gaps or duplicate/missing host-device associations; same-queue order check fails; one of the event/file/RSS/wall caps trips; runtime/provider error or device fault occurs; source change perturbs output/correctness; observer changes paired wall beyond the declared overhead budget; or collection pauses before the last queued work's fence. A trace with missing events cannot be repaired by a lower byte threshold or kernel filters. Preserve original collection result status; this diagnostic does not qualify product performance, whole-model latency, quality, or adoption.
