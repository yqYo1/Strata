# R685: long-prefill workspace aliasing contract

Read-only source review for C=8192 layer-major prefill. No source changes, build, test, GPU work, runtime/environment or process scan, Git mutation, or cleanup was performed. Byte arithmetic below uses the existing B570 model geometry N=10,240, HC=4 and T=8,192 from `prefill-capacity-plan.ja.md`; it is a design calculation, not a memory or performance measurement.

## Existing capacity point

The C8192 planning row with one active K8V8 KV layer, all 12 indexers resident and 256K FP16 hidden rows has a deficit of 161,033,920 B after the modeled 512 MiB driver reserve. `carve` currently makes four separate `float[T*N]` allocations for `emb`, `mixed`, `bo`, and `ple_emb`. One is 83,886,080 float elements, or **335,544,320 B**. The earlier expression `2*83,886,080 B` would confuse element count with byte count for these FP32 arrays. If two allocations can safely share one slot, the saving is 335,544,320 B and the modeled residual becomes 174,510,400 B. Four-to-one reuse would save 1,006,632,960 B. These deltas are conditional on the alias being implemented in both `carve` and `bytes_needed`; they are not evidence that the full capacity case fits in an actual run.

The allocation order and sizes are explicit in `src/prefill/prefill.cpp:845-860,924-926`; `bytes_needed` separately counts the same standalone arrays in `:1247-1260`. `GEMM_SCRATCH` is 32*2^20 **uint16 elements**, 67,108,864 B, and `GEMM_WS` is 33,554,432 B (`:585-586,831-834,953-955,1247-1255`). The SYCL CMake resolver compiles `src/prefill/sycl/gemm.cpp` rather than the CUDA/HIP `gemm.cu` (`cmake/sycl_backend.cmake:111`; `CMakeLists.txt:427` is the non-SYCL path). SYCL `init_external` accepts but ignores the workspace byte count, stores `workspace_`, and the SYCL GEMM paths never read/write `workspace_` (`src/prefill/sycl/gemm.cpp:41-58,81-88,89-125`). Thus this source has a separate **32 MiB allocation-removal candidate** for the SYCL-only resolver. It is not a candidate to overlay live buffers; CUDA/HIP still gives cuBLAS the workspace. Removing it alone leaves 127,479,488 B of the stated C8192 deficit.

## Candidate lifetimes on the supported long path

`run_layer_major` requires full single-GPU compact FP16, native source, explicit `STRATA_PREFILL_MMQ=0`, no peer/stage/hand-off/vision/reentry and `m.copy == m.cs` (`src/prefill/layer_major.inc:36-43`). It loops one full model layer at a time; each `run_impl` pass traverses chunks, and final residual callbacks synchronize `m.cs` before invoking observers (`src/prefill/prefill.cpp:3079-3088`). SYCL `queue_for(stream)` requires an in-order queue, and GEMM/kernel calls use that stream (`include/strata/sycl/launch.hpp:55-62`; `src/prefill/sycl/gemm.cpp:47-54,89-125`). The serial queue plus the listed last-read/first-write edges is the basis for the following alias proposal; a bare pointer-size match is insufficient.

| Buffer | First write for a chunk | Last relevant read | Earliest safe next occupant, on eligible layer-major path | Review |
| --- | --- | --- | --- | --- |
| `emb` | Embedding gather or row upload to `m.emb` (`prefill.cpp:1716-1744`) | `gr_broadcast(m.emb, m.R, ...)` (`:1746`) | The first layer-0 `gr_mix` write to `m.mixed`, after broadcast on `m.cs`; or the later `ple_land` H2D into `m.ple_emb` | Can share one FP32 slot with `mixed`, and with `ple_emb`, subject to route gate and same-queue ordering. On nonzero layer-major passes it is not written because residual rows feed `R`. |
| `mixed` | `gr_mix` / `gr_mix_r` writes F32 output each HC half (`:2056-2058`) | The MoE FP32 activation quantization (`:2366-2367` fused, `:2512-2514` MMQ). The compact FP16 expert path instead gathers `mixed_h` (`:2880-2886`); no later use of F32 `mixed` appears in that path. | In attention half, after its projections have consumed `mixed_h`/`mixed_bf`, the attention output projection can write `bo` (`:2075-2087` or QSA `:2103-2107,2299-2301`). In FFN half, after activation quantization, `moe_combine` can write `bo` (`:2967-2969`). | `mixed`/`bo` is a plausible phase alias under the serialized single-device route. `mixed` must remain disjoint from simultaneous `mixed_bf`, `mixed_h`, and `mixed_bf_lo` outputs/inputs. |
| `bo` | Attention output projection (`:2085` or `:2301`), then FFN `moe_combine` (`:2969`) | `gr_write[_norm_rs]` consumes it into `R` (`:3011-3015`). Optional phase audit reads it before that write, synchronously through its audit path. | Next half's or next layer's `gr_mix` may overwrite the shared slot only after the corresponding `gr_write` has been queued earlier on the same in-order `m.cs`. At layer 1 the PLE upload can occupy it after layer-0's FFN `gr_write`; PLE is consumed before layer-1 attention writes `bo`. | Plausible member of the same serialized slot, but this proof depends on both attention and FFN `gr_write` ordering and on callbacks/observers not retaining `bo`. |
| `ple_emb` | `ple_land` copies gathered host rows to device on `m.cs`, immediately before layer 1 (`:1755-1768`); gather itself is asynchronous on a host future (`:1638-1649`) | Layer-1 batched PLE uses `m.ple_emb` in postops (`:1990-2025`), or token path calls `ple_block` (`:2028-2035`). | After PLE's last use in layer 1, the layer-1 attention `gr_mix` can overwrite the slot. The host's opposite PLE buffer is independent and only refilled after the matching upload event completes (`:1770-1779`). | Plausible with the shared slot only if the upload remains ordered after layer-0 consumers and before layer-1 PLE consumers. Host gather lifetime does not extend a device read of the old slot, but the upload source event must remain intact. |

The strongest source-supported candidate is a single shared `T*N*4` slot for all four arrays **only behind the already narrow layer-major eligibility**. Their operation phases serialize as: embedding write/read; attention/FFN mixed write and its projections/quantization; `bo` write and residual read; PLE landing and layer-1 read before that layer's `bo` phase. For `mixed` and `bo`, this repeats in each half: attention `mixed` is consumed by projection before attention `bo` write, and attention `bo` is consumed by residual write before FFN `mixed` write; FFN `mixed` is consumed by activation quantization before `moe_combine` writes FFN `bo`, which is consumed by residual write before the next layer's `mixed` write. This is a plausible source-order proof, not a claim of tested alias correctness. Implementing only one pair such as `emb`/`ple_emb` is a lower-risk 335,544,320 B experiment and already exceeds the stated deficit.

## Buffers that must stay distinct, and boundaries that invalidate a broad change

`mixed_bf` and `mixed_h` are both written from the same GR-mix operation while the resulting projections use them (`:2056-2058,2075-2078,2103-2107,2321-2339`). They cannot overlap each other or the shared F32 slot during that phase. `mixed_bf_lo`, when enabled, contributes to separate GEMM accumulations and stays live through those projections. The same goes for GR input/output temporaries and `R`: `gr_write` reads `bo` while updating the persistent residual, so aliasing the candidate slot with `R` would destroy the source/destination state. The attention and MoE `region` is a separately sized max-of-sets scratch, not part of this four-buffer lifetime argument (`:866-905`).

The `on_chunk` callback can call `Prefill::draft_kv`, including on the final layer-major pass. `draft_kv` carves its temporary embedding, residual and K/V projections from `m.region`, uses the passed final `m.R` rows, and synchronizes `m.cs` before returning (`prefill.cpp:965-1045,1115-1148`; callback after stream sync at `:3079-3088`). It does not use `emb`, `mixed`, `bo`, or `ple_emb`, so that final-layer MTP reuse does not invalidate the proposed four-buffer slot. It does reinforce that the slot must not alias `R` or `region`, and that callback execution must finish before the next chunk overwrites any retained row data.

Do not apply a static alias to every `Prefill::carve` user without route-specific admission. Short prompts (`n <= T`) and ordinary chunk-major prompts continue through `run_impl` rather than layer-major (`layer_major.inc:8-14`). That route can carry `PeerPrefill`: an independent peer stream copies `m.mixed` with `cudaMemcpyPeerAsync` after an event from `m.cs` (`prefill.cpp:2536-2550`), and peer/stage modes have different lifetime edges. The layer-major route explicitly rejects these modes, but a generic `carve` alias would not inherit that restriction automatically. A safe implementation should preserve the separate layout as the fallback and reject/fall back unless the exact layer-major/same-device/same-queue capability is active; `bytes_needed`, owned allocation and request `relayout` must agree on which layout is selected. A compact-MoE-FP16 request alone is not proof of layer-major eligibility (`compact_moe_fp16()` only controls the MoE scratch shape at `prefill.cpp:645-660`).

PLE's two host buffers and future can outlive an early-return site until their destructor waits, so no design may repurpose `ple_emb_host`, `ple_rows`, or the host staging used for upload. The device `ple_emb` candidate is reused only after a checked same-queue last read. If later code moves `ple_land` earlier, introduces an out-of-order queue, adds a peer consumer without a completion event, or lets a callback retain one of these buffer pointers, this proof fails. The `m.copy == m.cs` layer-major condition provides current scope; a new layout that omits or bypasses it must be separately validated.

## Byte-saving options and a negative fixture

For `C=8192`, N=10,240:

| Change candidate | Conditional device bytes released | C8192 planning deficit after candidate |
| --- | ---: | ---: |
| One safe pair among the four FP32 arrays shares a slot | 335,544,320 | 0; 174,510,400 B nominal remainder |
| Two additional arrays share that slot (four-to-one total) | 1,006,632,960 | 0; 845,599,040 B nominal remainder |
| Omit SYCL-only dead 32 MiB `GEMM_WS` allocation | 33,554,432 | 127,479,488 B still short |

There is an additional transfer-side saving with modest conversion work rather than more aliasing: existing layer-major FP16 boundary storage applies `to_f16` before a host-backed boundary store and `from_f16` on the next layer (`layer_major.inc:359-369`; input path `prefill.cpp:1672-1689`). For a host-backed row, the per-boundary store plus reload is 2 * 40,960 * 4 = 327,680 B in FP32 versus 2 * 40,960 * 2 = 163,840 B in FP16, saving 163,840 B per token per boundary while adding conversion. For 47 boundaries and 256K tokens that is a logical request-length reduction of 2,018,634,629,120 B (1,880 GiB); this is an arithmetic upper bound for rows that actually use host-backed spans, not a claim that all transfers hit PCIe or that FP16 quality passes. The existing capacity plan already labels long FP16 boundary quality unqualified. A future recompute/late-materialization design could likewise trade arithmetic for fewer stored/transferred rows, but no source in this review establishes a correct recomputation schedule or its net cost.

A useful unrun counterexample fixture should expose both positive and negative contracts. In a tiny serialized in-order model, fill distinct logical phase values, enqueue embedding gather/broadcast, layer-0 attention and FFN, PLE host gather/upload plus layer-1 PLE read, then the next chunk's embedding; compare each consumer's checksum against an unaliased reference and use a partial final chunk. Include an `on_chunk` that runs a mock `draft_kv` on a distinct `region` and reads final `R`. The negative case should deliberately move PLE landing before the embedding broadcast, or delay an independent peer-stream copy of `mixed` while overwriting the shared slot; it must either detect the clobbered checksum or reject alias admission. Also assert aliasing is disabled for `n<=T`, peer/stage/handoff, `m.copy!=m.cs`, and noncompact/fallback layouts. This fixture design is a proposed adversarial test, not code or test evidence.
