# GPU MoE dataflow choices after the BF16-prefix attention milestone

Decision support for a future resource-bottleneck measurement; no speed or adoption claim. This review updates the routed-expert case against the native16 path and current attention/prefix work. It does not repeat the dense projection-bank analysis in R684–689. Earlier MoE/dequant reports R566, R601, R610 and R621 already cover device GEMM alternatives, dequant reuse, host grouping and deferred-layer hazards; R621's FP32 route-output sizing must be revised for the now opt-in BF16 MoE output path.

## Current path and geometry

The fixed model geometry in `src/prefill/prefill.cpp` is N=2,560, HC=4, D=10,240, top-K=10 and 512 experts; `layer_major.inc` validates 48 layers and expert FF width 640. At each layer boundary, layer-major copies and uploads the layer's 512 packed expert blobs into the quantized expert cache. For each input chunk (up to 8,192 rows), routing/group construction produces per-expert row counts and row offsets; the host builds the active expert order and moves route maps. The expert loop gathers rows, dequantizes each selected expert's gate/up and down matrices to the existing FP16 scratch ring (two slots), submits gate/up GEMM, SwiGLU, then down GEMM. It writes per-route results to Dm and combines them after expert work. Some fused/MMQ/native paths already do GPU grouping for supported pack formats, but the opt-in native16 path still has the per-expert `m.gemm.f16_out16` calls. These are distinct paths, so a grouped prototype must state which format and precision mode it exercises.

This design keeps chunk streaming and its current overlap opportunities. It also repeats expert dequantization for each chunk even when the quantized layer cache retains that expert. The older 123,192-GEMM/5.643-host-CPU-second profile and 0.106-second grouping observation in the task are scoped historical measurements, not a current bottleneck attribution; separate submission, polling and host grouping before choosing a target.

At two bytes per value, one BF16/FP16 expert's gate/up matrix is 1,280×2,560×2 = 6,553,600 bytes (6.25 MiB), and its down matrix is 2,560×640×2 = 3,276,800 bytes (3.125 MiB). The combined bank entry is 9,830,400 bytes (9.375 MiB). Therefore 16/32/64/128 experts require 150/300/600/1,200 MiB respectively; all 512 experts of one layer require 5,033,164,800 bytes (4.6875 GiB). A 48-layer full-model BF16 bank would be 225 GiB and is not a plausible resident design. BF16 and FP16 have the same byte cost; the current dequant scratch is FP16, while native16 MoE input/output storage is BF16. Changing the bank's rounding point or format needs comparison against the actual SGLang/vLLM execution contract.

For a deferred wave containing all 262,144 context rows, the BF16 expert input (`T×N`) is 1.25 GiB; the ten per-route Dm outputs (`T×K×N`) are 12.5 GiB; and a BF16 shared-expert output is another 1.25 GiB. The shared scalar gate costs 1 MiB. Minimum route IDs plus FP32 weights cost 20 MiB; retaining explicit source-row and slot maps as well raises routing control to about 40 MiB. Thus a straightforward full-wave buffer set is about 15.02–15.04 GiB, excluding temporary expert activations. At the current 8,192-row chunk, the same live tensors cost 40 MiB mixed input + 400 MiB Dm + 40 MiB shared output, or roughly 481 MiB with route maps and gate. This is why a wave limit is material. These are logical BF16 payloads; the existing Dm allocation is sized as FP32 storage and aliases its first half as BF16 under native16, so a new deferred path needs its own checked capacity and lifetime plan.

## Dataflow candidates

| Candidate | What it changes | Main costs and constraints |
|---|---|---|
| Per-expert GEMMs (current baseline) | Keep chunk → active expert order, dequantize each selected packed expert into the two-slot FP16 ring, then issue its two GEMMs and SwiGLU. | Lowest persistent expert-bank storage and keeps existing streaming; repeats dequant work across chunks and can submit many small expert GEMMs. Current quantized cache can avoid repeated source reads/upload while resident, but it does not by itself avoid repeated decode. Keep this as the measured control. |
| Device-driven grouped dispatch over quantized cache | Keep packed weights and chunk streaming. Build route counts/offsets on device, dispatch work by expert and row tile, and fuse or batch weight decode with GEMM work. | Can remove CPU route compaction, descriptor copies and per-expert launch control. A naive CTA-per-row-tile decoder may decode the same expert matrix repeatedly; a cooperative expert work unit must reuse decoded tiles. IQ formats need exact block-scale/lookup decoding; generic BF16/FP16 grouped GEMM cannot consume raw GGUF IQ blobs. Preserve format coverage and compare full host+device dependency path. Existing fused paths demonstrate only format-specific precedents, not a generic native16 implementation. |
| Full one-layer BF16/FP16 bank + expert-major chunks | Dequantize the current layer once into 512 typed matrices, then reuse those matrices while processing several chunks. | Requires 4.6875 GiB per active layer in addition to source/cache and live buffers. It eliminates repeated decode but converts/streams more bytes than the packed source, may compete with residual/KV allocations, and a blocking full-bank conversion can lose streaming overlap. Every chunk still reads expert weights; if the bank exceeds cache, repeated 4.69-GiB weight traffic per chunk remains. FP16 versus BF16 bank precision needs task-level comparison. |
| Partial bank + bounded wave, expert/chunk interchange | Keep E selected experts typed at a time (150 MiB–1.17 GiB for E=16–128), process them across several retained chunks, then advance the expert window. | Bounds bank size and can amortize decode within a wave. Needs a wave of pre-MoE inputs/routes and shared output; retaining all route-slot Dm costs 12.5 GiB at full context, 400 MiB per 8K chunk, or 1.5625 GiB per 32K wave. A smaller wave reduces memory but also reduces reuse. If a partial bank is loaded once per route slot to avoid storing Dm, it can repeat bank/decode traffic up to K=10 times; retaining Dm trades that traffic for memory. |

The layer/chunk interchange is feasible only with phase lifetimes made explicit. The recurrent GDN/QSA state, indexer, and PLE mutations must still advance in original token/chunk order; attention/GDN/normalization prelude for later chunks cannot run with stale prior-layer inputs. A layer-scoped deferred design can finish the prelude sequentially for a bounded wave, retain BF16 `mixed_h`, router decisions/weights and either the shared output plus gate or enough input to recompute them, then run the expert schedule and finalize the wave before the next layer consumes it. Callbacks/MTP outputs stay after finalization and in their original chunk order. Route output must either remain in per-slot Dm until the existing slot-ordered FP32 weighted combine, or the new schedule must prove equivalent accumulation/rounding. Current native16 output rounds each expert down result to BF16, then combines route slots in FP32 and writes BF16. An expert-major order that accumulates by expert ID changes that order; do not assume it is numerically interchangeable.

The route-output storage can be reduced if scheduling guarantees slot order: process one top-K slot across experts, accumulate its BF16 route results with the existing FP32 FMA sequence, then advance to the next slot. This needs only one route's temporary output plus a per-token FP32 accumulator (T×N×4: 2.5 GiB at full context, 80 MiB at 8K) rather than all K Dm slots, but partial banks may then be revisited for every slot. That is a distinct dataflow/traffic trade and must be measured with the prescribed SGLang/vLLM numerical comparison.

## Available facilities and the smallest probe

The checked SGLang Qwen4-Exp path delegates to its Qwen2-MoE sparse block and implementation registry; the pinned vLLM Qwen4-Exp model extends the Qwen3-Next sparse MoE block, with its checked wrapper under NVIDIA. These establish architecture-level routing/expert structure, not an Arc Xe2 grouped kernel. The current official `vllm-xpu-kernels` tree is a more direct Intel reference: it has route/remap/gather helpers and an Xe2 grouped GEMM path for BF16/FP16 and selected quantized formats. Its input is flattened token×top-K rows with per-expert row counts; it does not accept Strata's packed IQ2/IQ3 blobs as raw matrix operands and does not provide a persistent BF16 bank. The repository is Apache-2.0; check any CuTe/TLA or other vendor dependency file's own license before copying or adapting source.

Local `src/prefill/sycl/gemm16.cpp` is a native Intel GPU dense GEMM with 16×32×32 work tiles, not a route-aware grouped operation. The optional vLLM-native adapter in that file is also a dense `Problem` interface. oneMKL `gemm_batch` has a grouped pointer-array API with per-group dimensions and group sizes, so a host can describe unequal expert row counts as many groups; its API does not guarantee one device kernel or a speedup, and Strata still needs route packing, typed weight pointers and the intervening SwiGLU/down path. oneDNN matmul can serve as a low-level dense/batched primitive, but it does not encode sparse top-K expert routing or variable per-expert row counts; equal-M padding/packing and dispatch glue remain. Neither API alone performs GGUF IQ dequantization.

Smallest useful independent probe: one layer, one actual long-prefill chunk, one recorded native pack and route map. Keep the current quantized layer cache and existing dequant formulas; create grouped descriptors for the real per-expert M values and try the available oneMKL grouped API (or the already licensed/checked Xe2 grouped kernel only for its supported typed format). Start with existing per-expert FP16 scratch and outputs so the first comparison isolates grouping/dispatch from bank precision. Record total elapsed path, GPU kernel/event count, route/group preparation CPU time, polling CPU time, bytes decoded/written/read, peak live bytes and exact output/error against current native16 and the required SGLang/vLLM path. Reject a host-side group list that merely moves the same number of launches, and do not infer a full-wave benefit from a one-chunk result. Only after that probe shows where cost moves should a separate bounded-wave partial-bank trial compare E and wave size, including Dm retention versus slot-ordered accumulation. No such experiment or adoption is claimed here.
