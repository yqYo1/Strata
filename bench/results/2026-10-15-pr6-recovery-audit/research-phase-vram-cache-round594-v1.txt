## Findings

The 1,662,831,872-byte Prefill allocation (`Prefill::Impl::owned`, reported as `accounted=1662831872`) survives the prompt call and remains owned by the long-lived serve `Prefill` object during decode. `Prefill::release()` frees those buffers; normal serve initializes `sp` before entering its request loop and does not release/reinitialize it between prompt and decode. This is real potential decode VRAM occupancy, but no decode-boundary `cudaMemGetInfo` receipt currently quantifies its share of decode pressure. Do not call the number a measured decode-time free-memory delta: some allocation may be shared with, or contain persistent session/pinned owners, and only the device allocation breakdown can settle that.

The receipt's live phase values are more useful for prompt admission: immediately before MTP expert detach, free VRAM was 2,229,817,344 B (2,126.5 MiB); after its checked 675 MiB detach it was 2,937,610,240 B (2,801.5 MiB). In the same long prompt, layer-major reported a temporary full-layer cache of 1,363,148,800 B (1,300 MiB), FP32 residual-on-GPU of 167,772,160 B (160 MiB), and a 536,870,912 B (512 MiB) headroom allowance. Their sum is 2,067,791,872 B (1,972 MiB). Simple remaining arithmetic is therefore about 154.5 MiB before MTP detach or 829.5 MiB after it, while preserving the observed 4,096 GPU residual rows. These are phase-specific observations and explicit allocations, not a decode-time free value or an allocation guarantee.

The existing 128-slot cache reports 3.0% hit rate (3,124 / 104,160 lookups) for the long request. R584's corrected partition is 47 layers × 2 slots plus one layer × 34 slots. The roughly 260 MiB cost in prior reports is an estimate for that cache; exact `open_sized` bytes depend on actual per-layer blob sizes and padding. A first-order ladder is 128 ≈260 MiB, 256 ≈520 MiB, 384 ≈780 MiB, 512 ≈1,040 MiB. Relative to the current 128, the approximate additions are 0, 260, 520 and 780 MiB. Under the after-MTP-detach phase observation, subtracting those deltas from the 829 MiB prompt margin leaves about 829, 569, 309 and 49 MiB, respectively. Without MTP detach, only the current 128-slot size retains the observed 4,096-row FP32 prompt allocation plus the stated 512 MiB headroom; a +260 MiB tier already exceeds that arithmetic margin. The 512 candidate is borderline even under detach and should be refused unless a fresh live query and exact allocation accounting leave the required reserve. A 1,024-slot tier is outside this budget. None of these figures establishes startup cache admission: explicit cache open checks current free bytes against the requested arena, and the startup free point has not been reported for these candidates.

Treat this as an admission screen, not a speed ranking. A useful static screen is 128 → 256 → 384, then 512 only if live admission leaves the same reserve and 4,096-row R allocation. At the approximate increments above, the post-detach arithmetic margin becomes 829.5, 569.5, 309.5 and 49.5 MiB for 128/256/384/512. At each step query free/total after all persistent model, session/KV, MTP and decode graph owners are established; record exact requested and allocated cache bytes; then query before and after layer-major temporary allocations. Do not use the MTP-detached prompt number for decode admission because MTP experts are restored before decoding. The 128 baseline has a measured low hit rate, but R584 shows only aggregate owner marginals and no expert-ID route histogram, so neither higher capacity's attainable hit rate nor the profile's fit to the current route is known.

## Adaptation screen

`--adapt-swaps 0` is the right first arm for every admitted size: it gives a fixed profile placement and removes asynchronous refill/pending-map publication from the cache-size comparison. Current defaults are `--adapt-every 4`, `--adapt-decay 0.7`, `--adapt-swaps 96`; swaps only replace experts within a layer, require a missing expert's decayed usage to reach 2 and exceed the victim by 1.5, and are submitted asynchronously. Capacity does not increase with adaptation, and the configured maximum is not a swap count that will necessarily occur. After static capacities are screened, one bounded dynamic arm at the selected size can compare `--adapt-every 4 --adapt-swaps 16` against zero swaps; this caps churn well below 96 while retaining the existing cadence. Record actual swaps, pending-refill waits and per-request hit counts. This is a proposal for a later measurement, not a result. Cache retirement/reopen must reject or drain while a refill is pending; no `adapt` worker, `adapt_ev`, or pending slot publication may outlive the cache arena.

The exact decode-format receipt attributes CPU work to IQ3_XXS 36.5%, IQ2_S 37.2%, IQ3_S 25.0%, and IQ4_XS about 1.2%, with 97% of routed entries CPU-owned. It has no format × `nt` service time. Therefore cache admission is a plausible lever for the observed 3% hits, but it cannot be credited with the 97% CPU service or predicted to improve decode elapsed time without route-ID counts and a clean same-work decode comparison. Cached SYCL experts use native Q8_1 arithmetic while CPU experts use Q8_K; generated IDs need not be bitwise equal across placements. Evaluate numerical/quality tolerance independently from work-normalized performance and elapsed wall time. Report W/R and CPU service separately from loop elapsed; the two repeated requests' loop times differ despite similar owner/service counts.

## Up to two component proposals

1. **Release Prefill-owned device scratch between prompt and decode, then recreate before the next prompt.** `Prefill::Impl` owns the chunk allocation through `m.owned`, including the logged 1.6628 GB accounting, while `run_impl` uses `region` as a reused union for attention/MoE/GDN scratch. It is not an MTP `window_R_` buffer. The MTP normal/coupled graphs borrow `Verifier::final_R`; keep that address and all MTP dense/head/KV/coupled owners intact. In serve, `sp.on_chunk` also performs batched MTP prompt-KV work and conversation checkpoint/progress handling; selected-head collection (when enabled) consumes the chunk's R synchronously under a checked queue lease. Retire only after the final `on_chunk`, every prefill copy/stager event, and callback work has completed. Before another prompt, reinitialize the same chunk geometry and restore all callbacks/peer-stage wiring; do not clear persistent KV, GDN, conversation snapshots, or MTP KV. `Prefill::release()` currently synchronizes but does not return a checked status, so a safe component needs an explicit checked release/recreate boundary and fail-stop behavior if queue retirement or recreation fails. A failed recreate must stop before batched prompt execution, never fall through with stale pointers. By itself this leaves existing cache capacity unchanged; it can free decode-time headroom, or accompany a separately admitted larger startup cache, if the bytes remain free at the decode boundary. No source-only amount or speedup is qualified. Exercise fresh prompts, prompt-cache/RESTORE hit and miss, short-read `read_windows`, cancellation/error and the physical 256K host-KV fallback before adoption.

2. **Reintroduce the old prompt-scoped decode-cache retirement only as an optional, exact-layout transaction.** The preserved `STRATA_PREFILL_RELEASE_DECODE_CACHE=1` candidate already details the required owner protocol but is explicitly `UNAPPLIED_NOT_BUILT_NOT_TESTED_NOT_RUN_ON_GPU`. Its potential decode-cache memory is about 260 MiB at 128 slots; during prefill it is replaced by a 1.3 GiB layer-major cache, so this transaction alone frees prompt memory rather than making cache capacity coexist with the layer cache. As preserved, it restores the same 128-slot layout; increasing that target requires a separately reviewed target-layout planner and new exact restore receipt. Preserve existing 675 MiB MTP detach behavior unchanged and compose outside it: verifier's all-T cache-reading graphs and native hit graphs need checked retirement; keep verifier arena/final_R for MTP coupled readers; detach Prefill's cache-tail borrow (candidate requires `--no-prefill-borrow`); publish all-miss maps before close; refill in exact profile/slot order, verify bytes, refresh `host_res`/`d_res`, dispatch and VerifyHits pointers, recapture before decode. Do not close across active adaptive copies, lookahead, callbacks, remote/peer/split paths or any unfinished graph/queue owner. Reject unsupported settings before mutation, and on destroy/drain/refill/recapture failure retain uncertain owners and fail-stop before decode. Do not silently drop to a smaller or partial cache, discard a restored conversation, or disable 256K host backing. RESTORE, prompt-cache checkpoint resume, short prompt chunks, repeated requests, normal/coupled MTP, full physical 256K and failure/cancel paths must qualify independently. The candidate's strict readback and recapture costs count toward prompt time. It makes no performance/quality claim.

These proposals target different owner lifetimes and can be evaluated separately. A future implementation should begin with the simpler scratch boundary while keeping 128 static cache, then evaluate exact cache-capacity steps; cache retirement is a separate higher-risk prompt-path change. Do not combine them in a first causal comparison.

## Other memory and transfer distinctions

The decode KV setting remains `--max-context 262144 --kv int8 --kv-resident 32768`: R587's logical device-resident payload is 396 MiB, while the 256K host backing is 3.094 GiB payload (plus allocation slack). It is separate from expert cache and Prefill scratch. The 95.85% KV block hit and 223.3 MiB logical RAM-read figure in the service receipt do not imply wire bytes or an expert-cache opportunity. The 675 MiB MTP expert detach is observed at the prompt boundary and is restored for decode; it does not add to decode capacity. Conversation checkpoints are host-RAM state, with `conversation-cache-mib=0` in the current phase receipt; RESTORE changes which prompt rows are recomputed, not ownership of Prefill's device scratch. `on_chunk` is a real reader during prompt execution and can run draft-KV, selected-head and checkpoint work; its completion is part of the retirement boundary.

No external SGLang/vLLM/IPEX-LLM memory-reuse reference was needed: current configured source and actual retained phase receipts directly establish the owner/liveness facts, while third-party designs would not establish Strata's pointer or queue lifetimes. No candidate is implemented, measured for speed, quality-qualified, or adopted by this report.
