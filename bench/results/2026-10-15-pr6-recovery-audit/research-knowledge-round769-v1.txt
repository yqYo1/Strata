# R769 — Chunk residency and bounded overlap for long prefill

2026-10-16 JST. Bounded public-literature research only. The previous R763 survey already covered general GPU residency and transfer-reduction patterns; this report narrows to one-window versus two-window scheduling, queue dependencies, scratch headroom, and lifetime. No source, build, test, GPU, profiler, process, Git, environment, cleanup, or service operation was performed. No XeStrata source or derived material was read, copied, or used.

## Finding

A second device window is useful only if there is a ready next chunk, a distinct free destination, and a transfer path that can progress while the GPU computes the current chunk. It can overlap loading chunk i+1 with compute of chunk i; it cannot make a causal/recurrent compute for chunk i+1 independent of state produced by chunk i. The candidate schedule therefore needs an event DAG that separates “next input copied” from “next compute may start.” A host `wait()` after every copy or layer can drain earlier GPU work and erase the intended overlap. Neither SYCL events nor the Intel guide guarantee that a particular device has a separate copy engine or that concurrent transfers will be faster.

For the supplied 78,452-row diagnostic, the baseline is 48 layers, 8,192-row chunks, FP32 residuals, and 32,768 resident rows. Existing results report 165.704 caller-CPU seconds in explicit GPU waits and a 131.610-second inclusive route interval that contains earlier work; neither value is copy-only latency. A separate idle 320 MiB component measured 6.015 GB/s ordinary H2D versus 5.095 GB/s host-USM H2D. Those are non-overlapped transfer results, so they do not predict copy-engine throughput while kernels are running. This makes an end-to-end dependency-path test necessary before treating extra buffering as a performance option.

## Three schedules and their costs

**1. Sequential one-buffer.** Allocate one 8,192-row scratch window, fill or copy it, wait for readiness, compute, and reuse it only after its last consumer. At the current hidden width of 10,240 FP32 values per row, this window is 8,192 × 10,240 × 4 = 335,544,320 bytes (320 MiB). It is the lowest-scratch schedule and has simple ownership. Copy and compute on one in-order queue, or an explicit host wait before reuse, serialize the stages; if input staging is host-side, that work may still run while the device computes, but the H2D copy cannot overwrite a buffer still being read. This is an appropriate control and can win where copies are short, transfers are not on the critical path, or GPU memory is nearly full.

**2. Resident 32K prefix plus one scratch window.** Keep the configured 32,768-row prefix resident (1,342,177,280 bytes, 1.25 GiB for the same FP32 row shape) and process one additional 8,192-row window at a time. If scratch is separate from the configured prefix, the hidden-state subtotal is 1.25 GiB + 320 MiB = 1.5625 GiB. The likely advantage is reuse of already-local prefix/state and avoiding its repeated host-to-device movement; it does not follow that the extra window creates overlap. With a single scratch slot, the next transfer must wait until the slot's current consumer releases it. This schedule keeps working-set scope bounded and may be preferable if prefix reuse is material but double-buffer headroom is not available. Do not assume the configured 32K row count includes or excludes any allocator-specific scratch without measuring the actual live allocations.

**3. Bounded two-window overlap.** Keep the same prefix and add two 8,192-row slots, alternating them: while slot A is consumed, copy an already available next input into free slot B; only launch B's compute after both B's copy event and the prior causal/state event are complete. Two scratch windows are 640 MiB; prefix plus these windows is 1.875 GiB under the separate-scratch assumption, an incremental 320 MiB over schedule 2. Use a transfer queue and compute queue in the same SYCL context, explicit `depends_on` event edges, and one completion event per slot. Submit the next copy before waiting for current compute; avoid a queue-wide drain inside the chunk loop. A final wait and waits before reusing an occupied slot remain required. Add no more slots until measurements show the two-slot producer/consumer rhythm is transfer-starved rather than compute- or memory-bandwidth-bound.

## Dependencies and failure modes

The portable SYCL contract returns events for `queue::memcpy` and kernels. An `in_order` queue acts as if each command depends on the previous command in that queue, so placing every copy and kernel in it may serialize more than the data dependencies require. Different queues have no implicit cross-queue ordering; express copy-to-kernel, previous-state-to-next-kernel, and last-consumer-to-slot-reuse dependencies explicitly. The Intel guide's overlap example traces copy-ins for upcoming independent iterations overlapping compute, but says this depends on hardware resources and copy engines. It does not establish overlap on this Arc B570 or under the current build/runtime. (Khronos, [SYCL 2020 revision 12](https://registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html) and [queue reference](https://github.khronos.org/SYCL_Reference/iface/queue.html); Intel, [oneAPI GPU Optimization Guide, 2024.1: host/device overlap](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2024-1/overlap-data-transfers.html).)

An event boundary is not permission to free or mutate its storage. Keep host input staging unchanged until its H2D event completes; keep a device slot intact until the final kernel reading it completes; for D2H, keep the destination valid and do not read it before completion. On cancellation, allocation failure, or asynchronous error, preserve both slots until queued work has retired or the queue has been safely drained. This matters with a causal pipeline: a slot can be copied early but its compute may remain blocked on the prior chunk's attention/recurrent state, so prematurely reusing the slot or treating “copy finished” as “chunk finished” races correctness.

Two common schedules suppress overlap: waiting after every H2D copy before submitting the compute, and waiting after every compute before submitting the next H2D copy. A global `queue.wait()` can also include preceding attention/GDN/GEMM work, so its wall time cannot be charged to the newest copy. The current diagnostic's long explicit waits and route-inclusive boundary are exactly the type of evidence that must be partitioned by event and dependency before attribution; they do not themselves establish removable transfer latency.

Extra queues or buffering can regress. Intel's 2024.1 multi-queue guidance reports that distinct contexts can repeat input transfers and JIT compilation; shared-context queues avoid that duplication but can increase the simultaneous live memory footprint. Bhatotia et al.'s non-LLM Shredder pipeline (FAST 2012, NVIDIA Tesla C2050) measured 30% transfer/compute overlap but only a 15% total-time reduction with double buffering; four pipeline stages gave 2× rather than the ideal 4× because stage costs differed. Their paper also reports higher pinned-memory allocation cost and warns that excessive pinned pages can increase paging. It is evidence that overlap is conditional and staging has costs, not a prediction for SYCL or B570. Reguly et al. found a stronger counterexample in out-of-core stencil work on NVIDIA P100: prefetching improved performance above 16 GB, but low reuse in CloverLeaf and overlap gaps between OpenSBLI loop chains still failed to hide movement; driver page migration/prefetch performance dropped under oversubscription, and on IBM+NVLink the oversubscribed case was consistently worse. The transferable point is that residency headroom, reuse, and dependency shape determine whether a pipeline helps; the reported GPU/driver results are not B570 evidence. ([Intel multi-queue guidance](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2024-1/multiple-queue-submission.html); [Shredder paper](https://www.usenix.org/legacy/events/fast12/tech/full_papers/Bhatotia2-5-12.pdf); [Reguly et al., *Beyond 16GB: Out-of-Core Stencil Computations*](https://arxiv.org/abs/1709.02125).)

## One bounded experiment

After the current measurement boundary is closed, compare the three schedules on the same actual 78,453-token API request (78,452 batched rows), 48 layers, 8,192 chunk, FP32, 32,768-row resident prefix, binary, device, and runtime settings. Keep one-buffer as the control; schedule 2 isolates prefix reuse; schedule 3 adds only the second scratch slot and event-based copy/compute queue split. Use separate clean processes and alternate order. Do not change storage dtype, kernels, model math, or copy-offload environment between arms.

For each arm, record individual end-to-end prefill samples; per-chunk copy submit and event-completion intervals; compute and boundary event intervals; explicit wait CPU/wall time; number of whole-queue drains; peak live VRAM/free headroom after model/KV allocation; and allocations/lifetimes for prefix, scratch, staging, and output. Attribute overlap from an actual device timeline or event intervals, not queue names. Compare each output against the existing FP32 path and preserve existing fault/cancellation checks. Confirm all slots retire on normal and error paths. The 78K run is only a scheduling screen; preserve the separate physical 262,144-context correctness requirement before adoption. Stop at two slots if full prefill does not improve repeatedly, if compute time rises enough to erase masked copy time, if peak memory loses required headroom, or if explicit drains/lifetime complexity prevent stable overlap.

## Provenance and limits

Sources were official Khronos/Intel API and optimization documentation plus two primary non-LLM GPU pipeline studies. Intel's cited pages are version 2024.1 (dated in the guide) and provide general guidance; confirm the actual compiler/runtime, context sharing, and B570 copy-engine behavior in any future implementation. Shredder used a 2012 Tesla C2050/CUDA storage pipeline; Reguly et al. studied stencil codes and P100/Knights Landing-era systems. Neither study is evidence for Qwen recurrence or current Arc performance. The linked papers are research evidence, not reusable implementation templates: no code was used, and their publication links do not establish a license to copy code. Any later source proposal needs independent provenance and repository-license review. This collection is not an inference, correctness, capacity-admission, or performance result.
