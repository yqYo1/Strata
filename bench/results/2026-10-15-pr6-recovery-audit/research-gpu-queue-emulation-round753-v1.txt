# R753 — oneMKL GPU queue, possible host fallback, and software emulation

2026-10-16 JST. Read-only research. Only this report was written. No build, test, runtime, device query, profiler, process control, environment change, service action, Git operation or cleanup was performed. No XeStrata implementation/helper/test/archive source was read or used. The current clean GPU cohort was left untouched.

## Finding

The concern is plausible enough to distinguish experimentally, but current evidence does not establish that oneMKL GEMM is executing numerically on the host. Strata's reviewed SYCL prefill GEMM calls `oneapi::mkl::blas::row_major::gemm(queue_for(stream), ...)`; BF16 and FP16 inputs both accumulate/store to FP32 output. The runtime path reviewed in R752 selects SYCL GPU devices only and binds its queues to those devices. This rules out Strata choosing a SYCL CPU device in that resolver, but it does not, by itself, prove the oneMKL implementation never computes on the host internally.

The oneAPI oneMKL architecture specification explicitly says that a computational routine's computation is done on the hardware device(s) associated with its queue, possibly with host assistance, unless specified otherwise. It also says an implementation that does not support the routine on the specified device may either compute on the host or throw. Thus host fallback is permitted by the generic specification for an unsupported operation/device; it is not proof that Intel oneMKL's current BLAS GEMM uses that fallback for Strata's queue, data types, shapes, or installed version. Conversely, GPU-only queue selection and presence of SYCL/GPU libraries do not rule out all host participation or unsupported-case fallback.

Intel's 2026.0 DPC++ oneMKL GEMM reference documents both exact signatures relevant to this source: `sycl::half × sycl::half -> float` and `oneapi::mkl::bfloat16 × oneapi::mkl::bfloat16 -> float`. This establishes API/type support in that reference version, not a guarantee about every Intel GPU, device capability, shape, or installed 2026.1 implementation. The 2026.1 release notes report the product release and general changes, but I found no 2026.1 release-note claim resolving host fallback for these exact GEMM paths.

The linked library names also do not settle where this call computes. Intel describes `libmkl_sycl_blas` as the BLAS SYCL domain library. Intel describes `libmkl_sequential` as a oneMKL threading layer; “sequential” refers to oneMKL's CPU threading mode in its standard linking documentation. Intel's 2026 guide lists SYCL BLAS linking with a SYCL-domain library plus interface, threading, core, and runtime libraries, and says SYCL can use supported threading libraries. A link dependency indicates available code/linkage, not that this particular SYCL queue call dispatched to CPU. Nor does the name `sequential` itself prove CPU GEMM fallback.

“Software emulation” also needs a precise meaning. Compiler/device support for emulated or synthesized floating-point behavior can execute as part of a GPU-targeted kernel and does not imply the host CPU executes the matrix multiply. For example, Intel documents `-fsycl-fp64-conv-emu` as partial emulation for FP64 conversion-only kernels, applied to device-specific compilation and requiring a GPU with that capability. That is not evidence about BF16/FP16 GEMM, but it illustrates why emulated device instructions and CPU fallback are separate claims. I found no official evidence that Strata's exact BF16/FP16 oneMKL GEMMs use CPU software emulation.

## What would distinguish the cases

Intel oneMKL verbose documentation says GPU BLAS call-description lines identify the GPU (`GPU0`, etc.); when the function executes on the host CPU, the device-index field is empty. That gives a direct library-level discriminator for verbose-enabled BLAS calls. `MKL_VERBOSE=1` enables GPU verbose without timing; `=2` enables synchronous timing and can perturb execution. The verbose reference is older (2024.x), and actual availability/format in the installed 2026.1 runtime has not been checked. The 2024.2 Intel feature announcement says verbose support covers GPU BLAS and reports function, parameters, GPU device and time. Treat verbose as a diagnostic suggestion for Main to evaluate in an owned run, not as evidence collected here.

A bounded Main-owned diagnostic could correlate each existing GEMM call with the verbose device field and with sampled host stacks/thread CPU during the same prefill interval. A host field on a matching GEMM line would support oneMKL host execution for that call. A GPU field would establish GPU targeting for that logged call, while leaving ordinary host-side setup, transfers, queue synchronization/busy polling, and other CPU work as separate possible CPU consumers. Aggregate process CPU percentage or library presence alone cannot make this attribution. Any verbose timing run should be separate from clean performance samples because Intel documents synchronous timing and output overhead.

The previously documented CPU evidence remains consistent with multiple mechanisms: R751 found a main thread at about one core for the observation window and official Level Zero docs describe default host busy polling; R752 found explicit serial expert-blob copies, routed-ID grouping, staging/control and queue synchronization in the layer-major route. Neither report provided a stack tied to the hot interval. This report adds a standards-level possibility, not a new attribution.

## Settled facts and unresolved questions

Settled from source/docs:

- Strata's inspected GEMM source calls oneMKL SYCL BLAS GEMM on the provided queue, for BF16 or FP16 inputs and FP32 output.
- The reviewed Strata device resolver admits GPU devices only; it does not select a SYCL CPU device as fallback.
- The oneMKL specification permits host computation or an exception when a routine is unsupported on the queue's device.
- The 2026.0 Intel GEMM reference lists both FP16/BF16-to-FP32 combinations; this is API support documentation, not per-device execution proof.
- `libmkl_sycl_blas` names the SYCL BLAS domain; Intel describes `libmkl_sequential` as a threading-layer selection. Link presence is not dispatch evidence.
- Software emulation in device-targeted code does not, by itself, imply host CPU numerical execution.
- Intel oneMKL verbose documents a GPU index for GPU-executed calls and an empty device-index field for host CPU execution, with version and instrumentation limits above.

Still unresolved for this machine/build/workload:

- Whether any current prefill GEMM call falls back to the host for the installed Intel oneMKL 2026.1 components, selected Intel GPU, data pointers, types and shapes.
- Whether oneMKL device kernels use a software-emulated instruction path for any relevant operation, and if so, whether it materially affects runtime.
- How much of the main thread's CPU time belongs to GEMM host dispatch/fallback, host preparation/grouping, or Level Zero/SYCL waiting.

No library-presence inference, source-level queue inference, or 2026.0 documentation should be presented as proof of the current 2026.1 hot path. No intervention is recommended from this research alone.
