# Round 930 — CUDA/SYCL expert-granularity and shared-expert audit

**Purpose:** decision support. **Scope:** read-only source audit; no code, builds, tests, profiler runs or performance claims. Strata’s pinned inputs and the captured `hardware-resource-profile-v1.json` match all four task SHA256 pins. The upstreams are algorithm references only: no source or patch is proposed for copying.

## Finding

The best supported MoE target is the dependency around route exchange. In the actual 39,262-token run (four 8,192-token chunks and one 6,493-token chunk), Strata computes router logits and top-10 ids/weights on the GPU, then copies ids to host and calls `cudaStreamSynchronize` before host grouping. Across 240 layer/chunk exchanges, the recorded region spans 52.433 s; host grouping itself is only 0.108 s. The same run records 69.696 s of explicit GPU-wait CPU time, with just 0.012 s of route-exchange CPU time outside wait intervals. This makes device-side grouping plus device-consumed row lists a concrete dependency experiment, but the 52.433 s region also retires preceding queued work; it is not 52 s of proven removable route overhead.

The CUDA references show the same useful pattern: keep top-k ids, expert sorting/alignment and padded row metadata on device, then let grouped GEMM kernels consume expert-sorted token indices. They do not establish that a generic BF16/FP16 fused MoE kernel can read Strata’s mixed GGUF IQ blobs or beat its native IQ-to-FP16 path. The current layer-major validator requires compact FP16-row mode, explicit `STRATA_PREFILL_MMQ=0`, and the fallback expert route; because that mode also disables `stream_all`, this benchmark is not the existing all-experts fused streaming branch. It loads the 512 experts of the current layer into the layer cache, drains the upload, and then runs the routed rows; it does not require all model weights resident.

At 8,192 tokens × top-10 there are 81,920 routed rows per full chunk. Uniform routing would average 160 rows per expert, but actual per-expert counts and padding loss must be measured. Preserve router ids/weights and ordering, the interleaved IQ gate/up and down formats, BF16 hidden/output storage with FP32 router/reduction accumulation, shared-expert gate semantics, and 262,144-position state correctness. No 600 tok/s qualification or adoption conclusion follows from this audit.

## Candidates and next discriminator

1. **Keep route metadata and grouped projection device-side.** Prototype a grouping contract that emits per-expert counts/bounds and stable source-row ids from the existing GPU top-10 result, then feeds the next existing expert operation without D2H ids, host prefix sums or H2D slot/src maps. Retain per-layer 512-expert cache placement and bounded scratch; do not allocate converted copies of all experts or change the current layer-major offload budget. This targets the only large MoE-specific measured region, but its benefit is unknown until queue retirement and first-projection time are separated.
2. **Reduce per-expert launch/materialization only after the first discriminator.** Compare a fused interleaved SwiGLU epilogue or an IQ-aware indexed-row grouped kernel against the current `dequant -> row gather -> gate/up -> SwiGLU -> down` chain. It must cover every active IQ type pair, keep the raw GGUF encoding and expert offsets intact, and use the same BF16 output / FP32 accumulation boundaries. Do not infer benefit from the total 123,192 GEMM submissions; that count is not MoE-attributed.

**One discriminating experiment for Main:** on an owned copy of one 8,192-token routed layer, produce device grouping metadata from the existing ids, compare its ids/weights/row mapping and final BF16 MoE output against the current host oracle, and separately time (a) router-ready→group-metadata-ready, (b) metadata-ready→first expert GEMM, and (c) full MoE completion. Keep the expert cache placement and IQ bytes identical, avoid profiler logging in timing samples, and follow with the 262,144-position shared-state/correctness gate before any full-prefill speed decision. This separates removable host dependency from kernel execution and avoids assuming the busy waiting thread is the bottleneck.

## Evidence limits

The profile reports 33.963 s of QSA launch service in a 94.945 s long-attention envelope, 77.31% compute-command coverage of that envelope, 123,192 all-engine GEMM submissions, 5.643 s GEMM submission CPU time, 4.846 s source-copy CPU time and 52.349 s route-exchange CPU time, mostly within GPU waits. These scopes do not attribute GEMM or compute time to MoE, prove arithmetic-unit saturation, or isolate all queue gaps. The clean prior 403.0 tok/s median is not this instrumented run; the separate Qwen3.5-9B throughput is not a model-to-model speed ratio. No performance gain, precision qualification, offload-capacity increase, or 262,144-context correctness result is established here.
