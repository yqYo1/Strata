# R633 — bounded expert-major chunk waves

2026-10-15 JST. Read-only review of a bounded 2/4 chunk wave that preserves causal passes but batches MoE expert work across neighboring chunks. Reviewed R621/R622/R623/R627/R628/R631 and the audit registry before searching external code and project reports. No code, tests, build, GPU, process, Git, cleanup, or current benchmark raw data were touched. Only this report was added.

## Disposition

This is a distinct, smaller candidate than R621/R622's whole-prefix deferred schedule: for each current layer, run each 2 or 4 consecutive chunks' causal attention/GDN/QSA and FFN prelude in order, retain the wave's prepared MoE inputs/routes, run expert-major work over only that wave, write completed chunk outputs, then advance to the next wave. It preserves the current layer-major architecture and does not carry wave activations/routes across the full prompt. It is a credible **bounded design to prototype**, not a speed recommendation. A first study should compare 2 chunks; 4 chunks has twice the retention. No local route-identity histogram currently tells us whether experts repeat across each candidate wave.

R622 already proposed full-prefix deferred MoE and reported its large live-state costs. R633 does not repeat that proposal: it asks whether 2/4 chunk windows capture enough repeated-expert work to amortize dequant/GEMM while bounding the pending outputs. R601's decoded-weight LRU and fused dequant-to-XMX are also separate already-reported ideas; a wave schedule yields exact within-wave opportunities from one captured route set, but does not establish cross-wave cache hits. Current layer-major puts the active layer's packed expert blobs in a temporary GPU cache already (R620/R628); any benefit here is fewer repeated packed-to-FP16 dequant operations and larger per-expert row GEMMs, not fewer host-to-GPU expert transfers.

## External implementation evidence

The strongest direct code precedent found is Anemll's Flash-MoE layer-major executor. Its repository describes a per-layer prompt slab: capture exact top-k IDs/weights for all slab tokens, deduplicate expert IDs across the slab, gather the matching rows per expert, process a possibly large expert ref range in bounded micro-batches while keeping that expert's weights loaded, then scatter weighted outputs. `--moe-prefill-batch` bounds the dedup window and `--moe-prefill-micro-batch` bounds each expert's compute call. This is the right structural analogue for a two/four-chunk wave, although its source tree is a different llama.cpp/Metal/sidecar path and does not prove Strata's state or numeric contract. The detailed [project design and executor description](https://github.com/Anemll/anemll-flash-llama.cpp/blob/master/docs/flashmoe-layer-major-dedup-single-sidecar.md) explicitly points to `build_prefill_selected_plan()` and `compute_prefill_moe_tensor()` in `src/llama-context.cpp`; inspected [current source](https://raw.githubusercontent.com/Anemll/anemll-flash-llama.cpp/master/src/llama-context.cpp) has the corresponding slab and expert-ref planning logic. The retrieved moving `master` source was not pinned to a commit, so this is implementation precedent, not a reproducible version comparison.

A second relevant implementation is the public `jagoff2/qwenllama` fork for Qwen Flash-Next. Its README describes streamed expert prefill with bounded GPU arena slots, explicit pre/post fences, pinned host staging, and QSA query chunking. It reports a layer-granularity streamed path and identifies future per-expert/grouped streaming as future work; it does not implement the exact cross-chunk expert-wave schedule. Its value here is ownership/fence design in a close model family, not an existing wave algorithm: [repository source/design](https://github.com/jagoff2/qwenllama).

The author discussion [llama.cpp #28363](https://github.com/ggml-org/llama.cpp/discussions/28363) links the patch/evidence repository `zhaoyilun/moe-working-set-16gb` and describes a staged prefill experiment. The author's later gate update describes a router-post barrier, per-layer unique-expert packing, shared VRAM windows, and grouped MMQ, with a hard negative 262K admission result. This resembles a bounded router-to-expert barrier and is useful discovery evidence. It is an individual report, not upstream source or transferable performance evidence. The follow-up explicitly says full expert bucketing/grouped GEMM was still in progress; do not present its prefill numbers as a measured result for this wave candidate.

Upstream `llama.cpp`'s [MUL_MAT_ID reference kernel](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-et/et-kernels/src/mul_mat_id_f32.c) shows the baseline grouped-routing contract: each `(slot,batch)` selects an expert matrix and produces one output at the corresponding slot/batch. This validates batched expert-indexed work but does not itself show shared-expert deduplication or cross-chunk reuse. Its source is a moving `master` snapshot, and the reference backend is not Strata's Arc/SYCL backend.

These examples support bounded batched expert execution and explicit buffering. They do not show an equivalent QSA/GDN model, per-chunk activation reuse, Strata's exact output reduction, or an Arc B570 speedup. SGLang/vLLM grouped GEMM and CPU-offload/cache material in R622 remains supporting context, not a stronger direct precedent for this particular single-device staged wave.

## Causal schedule and wave interface

Current `run_layer_major` is layer-outer, chunk-inner. `run_impl` performs attention half (including GDN recurrence or QSA append/index/attention), then FFN preparation (`mixed_h`, router IDs/weights, shared expert and gate), routed experts, combine, and final hyper-connection write for each chunk. GDN/QSA/PLE must remain in ascending token order. The next token chunk's layer input is already stored in the preceding layer's residual bank, so current-layer FFN output does not feed current-layer attention for a later chunk. A wave may therefore run its causal/preparation segments in order, defer that wave's routed expert work, then finish/write the wave before starting the next wave. Do not interleave chunks across model layers, defer the attention-state updates, or claim this is legal for the ordinary chunk-major route.

After preparation, the wave must own or address: FP16 `mixed_h` input rows; router IDs and FP32 weights; a stable mapping from each `(token, top-k slot)` to its exact output row; shared FP32 result and shared gate; the four HC injection values per token; and the routed expert outputs until combine completes. The previous-layer residual bank is the input source and can become the next-layer output bank only after every input row in that wave has been consumed and all final outputs have been stored. The per-chunk device residual `m.R` cannot substitute for that layer-wide bank.

A workable executor groups wave route references by expert, gathers each expert's rows from wave `mixed_h` in a bounded row micro-batch, dequantizes the packed expert once per wave, runs GU, SwiGLU and Down, and scatters FP32 Down outputs into the original route output slots. Then it runs the unchanged combine in original chunk/token order, applies `gr_write` with each token's saved injection, and writes completed residual rows to the layer-major bank. The activation staging/gather order is flexible; exact router decisions, weights, per-token slot IDs and top-k holes must remain attached to original tokens.

## Reduction-order result

For the configured Arc route, `src/prefill/sycl/postops.cpp::moe_combine` starts FP32 `v=0`, walks `k=0..9`, performs `sycl::fma(w[token,k], Dm[slot[token,k]], v)` for nonnegative slots, then adds `shared[i] * sigmoid(sg[token])`. The current per-expert route loop creates `Dm` rows through a host `slot`/`src` mapping; expert ID order is not the top-k slot order. It must not be replaced by “accumulate each expert into the token sum as its GEMM finishes” if preserving current arithmetic order is the goal.

If each wave's expert results are written as FP32 into the same per-token route-slot positions and the existing combine is invoked unchanged, **the ten-way reduction order can be preserved**. The individual GEMM's row result is still FP32 from the configured FP16-input oneMKL path. Shape changes from separate chunk GEMMs to a larger multi-chunk GEMM may choose a different oneMKL kernel/reduction implementation, so bit identity is not guaranteed; test route outputs, combined output, residual and logits. If outputs are accumulated in expert-major completion order, the reduction order changes and requires an explicit quality gate. This is R621/R623's exact slot-order constraint, applied to bounded waves rather than restated as a full-prefix plan.

## Wave memory arithmetic

Use `N=2,560`, top-k `K=10`, HC=4 and configured FP16 `mixed_h`. Let `C` be current chunk size, `q` wave width in chunks, and `W=q*C` (last wave may be shorter). If the first candidate retains exact route outputs on device until unchanged combine, the unavoidable dominant planes are:

- `Dm`: `W*K*N*4 = 102,400 W` bytes.
- `mixed_h`: `W*N*2 = 5,120 W` bytes.
- shared FP32 result: `W*N*4 = 10,240 W` bytes.
- HC injection: `W*HC*4 = 16 W` bytes; shared gate: `4 W` bytes.
- four 32-bit per-route arrays for IDs, weights, slot destination and source token: at most `W*K*4*4 = 160 W` bytes, plus O(NE) counts/offsets.

Combined retained payload above is `117,940 W` bytes (about 0.900 GiB at W=8,192); it excludes the existing full residual bank, current layer/chunk operator scratch, expert decoded-weight pair, routing projection temporaries and any extra alignment. Route metadata may live in host memory rather than device memory, but transferring it and result planes has a cost. Intermediate GU/hidden workspace need not scale with W if per-expert rows are processed in a fixed micro-batch; decoded FP16 weights can remain the existing per-expert pair (R601 source calculation 9,830,400 bytes / 9.375 MiB) while all wave refs for that expert are consumed.

| Chunk C | Wave q | W rows | Exact-order `Dm` alone | `mixed_h` + shared + inj/gate + 4 route arrays | Listed retained subtotal |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 4,096 | 2 | 8,192 | 838,860,800 B (0.781 GiB) | 127,303,680 B | 966,164,480 B (0.900 GiB) |
| 4,096 | 4 | 16,384 | 1,677,721,600 B (1.562 GiB) | 254,607,360 B | 1,932,328,960 B (1.800 GiB) |
| 8,192 | 2 | 16,384 | 1,677,721,600 B (1.562 GiB) | 254,607,360 B | 1,932,328,960 B (1.800 GiB) |
| 8,192 | 4 | 32,768 | 3,355,443,200 B (3.125 GiB) | 509,214,720 B | 3,864,657,920 B (3.600 GiB) |

This is a source-shape lower bound for retained planes, not admission or speed. R623's notional 1.663 GB budget for all new device allocations is exceeded by `Dm` alone for 4,096×4 and 8,192×2/4; whether that old budget applies to a new wave is a fresh admission question, and actual free-VRAM and resident-cache receipts control. The 4,096×2 case leaves only ~0.76 GB under that illustrative budget for other new device allocations. It is the smallest credible exact-order probe, but not established to fit. If `Dm` spills to host, at least one wave's routed output plane must return to the device for GPU combine; a 2×4,096 wave already means about 0.781 GiB of output H2D, potentially erasing dequant/GEMM savings. Do not claim a cheap host spill without measuring traffic and overlap.

The current 4,096-chunk route has `Dm` capacity for one chunk. A 2/4-wave implementation cannot merely reuse its pointer: allocation/accounting, source/destination strides and map indices must all be wave-sized, while transient per-expert workspace should remain explicitly capped by the chosen ref micro-batch. If the route is reworked to slot-ordered passes to reduce `Dm`, expert dequant may repeat across rank slots and offset the benefit; that is a different candidate and changes scheduling again.

## RESTORE, checkpoints and callback timing

`run_impl` currently synchronizes then calls `on_stage_chunk(done)` and `on_chunk(R,T,pos0)` at a completed chunk boundary. The layer-major wrapper deliberately suppresses intermediate public callbacks: its wrapper calls the saved stage callback only after the final layer's final chunk, and calls the saved chunk callback on completed output chunks from the final layer. This ensures callbacks observe a coherent complete-model output/state boundary. A wave's causal prepass advances GDN/QSA/PLE, but before deferred experts/combine/HC write its residual/output bank does not yet represent that same prefix. Invoking a checkpoint/RESTORE capture at this intermediate point would pair advanced session state with incomplete layer residuals. Therefore keep the current whole-request checkpoint callback boundary for the first version; do not publish wave checkpoints. MTP `on_chunk` may be delivered for each completed chunk after wave expert work and final residual writes, but must use the original position order, live owner buffers and checked queue completion.

Failure or cancel after a wave's causal prepass leaves recurrent/KV state partially advanced, just as any failed layer-major prompt can. Do not permit a subsequent decode, checkpoint save, or wave continuation from that state unless the caller's reset/discard/RESTORE policy has re-established a coherent prefix. On failure, cancel further issuer work, checked-drain every queue using activation/route/output owners, retain owners if retirement cannot be proved, invalidate the wave, and return failure. On a successful wave, commit layer output rows and callbacks only after all expert products, combine and residual write have completed. The current `layer_major.inc` lease/callback restoration is relevant precedent; the current code does not roll back session tensors by restoring borrowed C++ fields.

## Evidence needed before implementation priority rises

1. Capture ordered route IDs per layer/chunk from an existing source-safe trace or a new owner-reviewed observer; compute each 2/4 chunk union, repeated refs per expert, and expected dequant calls/GEMM rows. R628's aggregate `ne` histogram cannot reconstruct expert identities or cross-chunk union; R621/R622 whole-prefix proposals lack this bounded-wave measurement too.
2. Resolve actual `Dm` storage and full-live device/RAM admission for the current machine and target context, including overlapping `Rstore`, workspace and decode cache. A successful arithmetic subtotal is not headroom.
3. Prototype only a narrow 4,096×2 wave with unchanged FP16 activation and per-route FP32 output slots; check causal state, exact route mapping, `Dm` values, current `moe_combine` slot order, final residual and logits before timing.
4. Validate partial last waves, nonzero `pos0`, session reset and RESTORE identities, MTP callback sequence, cancellation/fault before and after wave completion, and checked owner retirement. Preserve current end-of-request checkpoint behavior until a wave-boundary checkpoint format can capture a coherent model state.
5. Compare clean end-to-end layer-major prefill at same settings only after correctness/admission; report dequant counts, expert row-count shapes, measured transfer bytes, per-wave time and total prefill wall. If route union is weak or memory/transfer overhead dominates, retain the current chunk path.
