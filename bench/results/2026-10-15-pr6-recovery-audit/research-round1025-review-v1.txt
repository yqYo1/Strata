## Operational digest

1. R1024 matches the pinned scorer and describes the FP32 source order, per-query bounds, dead row and tail bonus correctly.
2. Its four-query SLM candidate must name a single producer subgroup; four subgroups writing the same 512-byte SLM row would race and retain the duplicate global loads.
3. The candidate must pad a final 1–3-query tile without reading absent step/query rows, while all 128 work-items still cross the barrier.
4. Reuse the pooled row only when the block is complete for every populated query; route mixed dead/live blocks through per-query key selection or a no-reuse edge path.
5. R731 already proposed the four-query SLM topology; R1024 adds useful operation-order and mixed-tail detail, not a new topology.

## Source and technical review

R1024's central source description is accurate for the supplied snapshot. `qsa_select.cpp:9-16` validates query/capacity geometry and resolves the active block limit. `:149-183` launches exactly one required SG32 per query/block; the subgroup-uniform step predicate skips blocks above each query's `n_bid`; `b==n_bid` selects `dead`; each lane accumulates four adjacent dimensions; the XOR reduction uses offsets 16, 8, 4, 2, 1; lane 0 applies ReLU per head, sums heads in order, adds the partial-tail `1e9f` only after those sums, and writes `scores[qi*blocks+b]`. The call site in `prefill.cpp:2531-2547` batches up to 256 queries, sets `active` from the last query's `n_bid+1`, and invokes scorer then selector. Those facts support the report's arithmetic, inactive-column, capacity, and physical-context gates.

R1025-C1 — SLM producer ownership is missing from candidate A. A 128-item group has four SG32 subgroups, each with lane IDs 0..31. If every subgroup follows the unchanged lane load and writes `lane*4+[0..3]` into the same 128-float SLM row, the four groups duplicate each global load and issue concurrent writes to each same SLM element. The [C++ working-draft data-race rule](https://eel.is/c++draft/intro.races) treats conflicting unsynchronized writes by different threads as a data race even when they store equal values. Make one designated subgroup (or a non-overlapping set of work-items) the sole producer for the 512-byte pooled row, then have all work-items cross the barrier before the four consumer subgroups read it. Only this mapping can realize the stated three-of-four logical-load reduction.

R1025-C2 — The report handles differing `n_bid` among valid queries, but does not state the partial-query-tile rule. The pinned call site permits `nb=min(256,T-t0)`, so the final batch can contain 1–255 rows; grouping by four can leave one to three absent query slots. Those subgroups must not read `steps` or query memory for `qi>=nq`, and their work-items must still participate in the unconditional group barrier. A common pooled row is safe to reuse only when `b<n_bid` for every populated query in that tile. At `b==n_bid` for one query and `b<n_bid` for another, use separate per-query key selection/load or a no-reuse path. Preserve each valid row's own tail bonus and output bound.

R1025-C3 — The stated source arithmetic order is correct, but the source text alone does not establish the baseline binary's contraction behavior. The `dot += key*query` sequence may be contracted or transformed according to the pinned compiler flags/target. An exact-bit candidate gate is appropriate, but record the toolchain/flags and compare against the same source-pinned FP32 binary; inspect candidate codegen if score bits move. Do not describe a source-order match by itself as proof of bitwise equivalence.

The vector-load candidate is properly conditional. Offset alignment follows from lane/head/row strides being multiples of four floats, but the supplied snapshot does not prove the base alignment of pooled, dead, and query allocations. Confirm each base before using an aligned vector operation. A compiler may already issue an equivalent load; no change in codegen or event means reject. The multi-block-per-subgroup sketch is correctly deferred: it reuses query values only if the compiler does not already retain them, while serializing score work and extending live ranges.

The occupancy and register caveats have primary documentation support, with an applicability limit. Intel's 2025.2 [Thread Mapping and GPU Occupancy guide](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2025-2/thread-mapping-and-gpu-occupancy.html) describes work-item/subgroup/work-group mapping, hardware limits, and how work-group size and SLM affect concurrent work-groups; it explicitly warns that higher occupancy does not always mean higher performance. The 2023.1 [Registerization guide](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2023-1/registerization-and-avoid-register-spills.html) covers live ranges, unrolling, pressure and spills. The 2023.0 [Sub-groups and SIMD Vectorization guide](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2023-0/sub-groups-and-simd-vectorization.html) describes block access for contiguous subgroup accesses. These are general Intel guidance, not measurements or codegen proof for this Arc B570 scorer.
