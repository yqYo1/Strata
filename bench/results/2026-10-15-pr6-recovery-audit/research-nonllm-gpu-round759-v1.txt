## Context and boundary

The current long-prefill evidence supplied for this research is 78K tokens and 223.6 s wall time: CPU expert-row grouping 0.165 s, explicit GPU waits 168 s, source copies 4.86 s, GEMM submission 6.78 s, and 37.35 s unclassified. A repeated clean prompt-prefill cohort is 349.3 tok/s versus 339.2 tok/s baseline. Those categories do not identify the unclassified work or prove a specific critical path. In particular, the small measured grouping duration alone does not justify moving it to the GPU; any replacement must include added kernels, synchronization, and downstream consumption. The prior R753–R756 reports already bound questions about library execution attribution, host grouping dependencies, batching, and command graphs; this report adds algorithmic analogies, not a new attribution.

## Transferable evidence

**Balance work by items processed, not by irregular segment count.** Merrill and Garland's merge-based CSR SpMV partitions the combined row-offset/nonzero streams into similarly sized tiles. It avoids preprocessing and provides a bound on work per processing element despite skewed row lengths. Earlier GPU sparse work likewise treats row-length variability as a source of load imbalance and adapts rows per compute unit. The transferable idea is to split long and short expert segments by total routed rows / bytes, then keep a bounded queue of such tiles, instead of assigning one indivisible task per expert. This can reduce tail imbalance if measured expert sizes are skewed. It does not establish that this is useful for this model: the actual expert histogram, GEMM efficiency at smaller M, and scheduling overhead must be measured. [Merrill & Garland, SC'16](https://mgarland.org/papers/2016/spmv/); [Greathouse & Daga, SC'14](https://doi.org/10.1109/SC.2014.68).

**Use prefix/partition primitives to build stable work maps, but account for global dependency.** Decoupled-lookback scan is a single-pass GPU prefix-sum design intended to avoid multiple full-array passes and an intervening global scan launch. Onesweep applies related single-pass lookback ideas to radix-sort histograms/prefixes. These papers demonstrate techniques and results on their evaluated NVIDIA hardware; they are not portable performance predictions or proof that an equivalent inter-work-group protocol is safe or profitable under this SYCL/Level Zero stack. A conservative transferable design is hierarchical: work-groups count local rows, produce block totals, scan a small totals array, then scatter stable local positions. It costs explicit stages but has simple boundaries and can be compared with CPU grouping. A single-pass lookback variant should be considered only with a documented forward-progress and memory-ordering argument for the target implementation. [Merrill & Garland, decoupled lookback](https://mgarland.org/papers/2016/scan/); [Adinets & Merrill, Onesweep](https://arxiv.org/abs/2206.01784).

**Aggregate tiny work only when metadata stays resident and the consumer can use it.** Persistent-kernel literature for irregular task graphs keeps a bounded set of GPU workers alive, consuming multiple queued tasks to avoid repeatedly launching a kernel and returning to the host between waves. Multi-GPU irregular scheduling research similarly emphasizes keeping communication control on the device and aggregating small transfers when links are constrained. This supports measuring a resident queue or batched expert scheduler as a candidate when host submission is demonstrated to dominate. But the current MoE caller needs per-expert counts/order for oneMKL GEMM dimensions and weight selection; a GPU-produced queue followed by a host readback preserves that boundary. To avoid that round trip, the numerical consumer must accept device-resident descriptors and variable work, or use a fixed-capacity scheme whose padding cost is counted. R754 already notes this fundamental boundary. [Task Management for Irregular-Parallel Workloads](https://escholarship.org/uc/item/9r15d4zk); [Chen et al., SC'22](https://escholarship.org/uc/item/9j6337h7).

**SLM is a scoped scratchpad, not a free cache.** Intel's optimization guide describes SLM as work-group managed storage local to an Xe-core, with lifetime limited to the group. Its histogram example distributes initialization, uses atomics for shared-bin updates, and synchronizes before consumption; it explicitly calls out barrier cost and recommends testing group sizes. SYCL group barriers order memory and synchronize work-items only in that group. Thus SLM is plausible for a small per-group histogram/tile metadata or stencil halo reused several times; it cannot provide a device-wide barrier or hold all 512 expert counts as a globally synchronized structure. Global prefix phases need kernel dependencies or a carefully justified atomic protocol. More SLM can also reduce concurrently resident groups, so evaluate useful work per group and whole-device throughput rather than assuming that data moved into SLM is faster. [Intel oneAPI GPU guide: SLM](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2023-0/shared-local-memory.html); [Intel guide: histogram and SLM barriers](https://cdrdv2-public.intel.com/790956/oneapi_optimization-guide-gpu_2024.0-771772-790956.pdf); [Khronos SYCL barriers](https://github.khronos.org/SYCL_Reference/iface/barriers-and-fences.html).

Stencils and sparse kernels share a further lesson: stage only data with concrete reuse. A stencil halo has neighboring work-items repeatedly consume the same loaded values, while sparse gather can have little or no reuse and SLM staging can merely add copies and barriers. For MoE routing, expert IDs/counts may be reused by scatter, gather, and combine, but only if those consumers share a lifetime and representation. Keep descriptor arrays on-device across stages where possible; quantify scratch bytes and lifetime against the 10 GiB capacity. Do not stage expert weight data into SLM absent a fit/reuse calculation: the expert bank is already GPU-resident, and SLM is work-group scoped.

## B570 transfer limits and testable next steps

Intel lists Arc B570 as Xe2 with 18 Xe-cores, 144 XMX engines, 10 GB GDDR6, and 380 GB/s specified bandwidth. These are product specifications, not sustained bandwidth or occupancy measurements for this application. Intel's guide table reports 128 KiB SLM per Xe-core for B580; do not silently substitute this as a measured or guaranteed B570 work-group limit. Query/build facts belong to a later owned device experiment. NVIDIA CUDA papers establish algorithm ideas on their tested devices; wave width, atomic behavior, forward progress, compiler lowering, SLM mapping, and kernel launch/synchronization costs can differ. [Intel Arc B570 specifications](https://www.intel.com/content/www/us/en/products/sku/241676/intel-arc-b570-graphics/specifications.html); [Intel Xe GPU architecture guide](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2025-2/intel-xe-gpu-architecture.html).

Suggested measurable experiments, if Main's current CPU attribution warrants them:

1. Record actual routed-row histogram per expert and layer/chunk, including empty/small/large counts and stable-order correctness. This determines whether row-count task assignment is genuinely imbalanced.
2. In a component-level, same-input study, compare current CPU-built stable maps against a hierarchical device count/scan/scatter. Time the entire dependent sequence through the first consumer, including ID visibility, maps, launches, and any readback. Preserve current implementation as the numerical and fault reference; include route-order and bounds checks.
3. If counts are highly skewed, compare fixed-size row tiles / bounded device queue against whole-expert tasks. Record tile underfill, atomics/contention, queue overhead, per-expert M distribution, and downstream GEMM shapes; reject a scheduler that increases total dependency time even if its grouping kernel is faster.
4. For any small SLM histogram, sweep a few work-group sizes and SLM allocations against register/global-memory versions; record compiler resource output if available and complete-workload timings. Validate barrier convergence and exact stable maps. No device-wide spin barrier.
5. Promote only a candidate that improves repeated clean end-to-end prefill samples and passes numerical, capacity, fault, and 262,144-context checks. A component speedup or GPU queue alone is not adoption evidence.

Evidence limit: no new B570 measurement, capability query, implementation proposal, performance estimate, or causal CPU attribution was made here.
