# Tile-local attachment lifetime and external-memory traffic in tile-based rendering

**Round:** R868 · **Purpose:** knowledge collection · **Retrieved:** 2026-10-16  
**Question:** When do render-pass structure and attachment lifetime keep framebuffer data tile-local, and when do consumers or hardware limits require external-memory traffic?

## Finding

Tile-local reuse follows from the overlap of three conditions: the next operation can legally consume the current attachment within the same render pass; the producer-consumer dependency fits the API’s attachment model; and the implementation can keep the live attachment set resident for the tile. Load/store and lifetime declarations tell the implementation which old and new values matter. They do not, on Vulkan or Direct3D 12 generally, guarantee that a driver will merge passes or keep every byte on-chip. Apple documents tile memory as a device feature; its scope remains Apple GPU and Metal. A persistent consumer, unsupported access pattern, synchronization boundary, or excessive working set can change the physical path even when the API describes a render pass.

## API contracts versus hardware choices

In the Vulkan 1.4.365 specification (2026-10-02), render-pass attachments define format, sample count, and the treatment of contents at first and last use. `LOAD` preserves prior contents, `CLEAR` initializes them to a known value, and `DONT_CARE` leaves the initial contents undefined. `STORE` writes rendered contents within the render area to memory; `DONT_CARE` allows those contents to be discarded. These are content-validity and access contracts. They do not require a physical DRAM transaction when a cache, compression, or tile store can satisfy the operation. Conversely, marking data dead does not make an illegal later read valid.

The `STORE_OP_NONE` distinction needs care. The mutable Vulkan Tile Based Rendering guide says it can avoid a write without logically discarding current contents, suggesting use before a later non-subpass pass. The normative spec is narrower: `NONE` performs no store access only when the current pass did not write the attachment; if it did write values, it behaves like `DONT_CARE`. Therefore, a later pass that needs the values written now requires `STORE` (or an appropriate resolve/store path). The guide is useful architectural advice, not a replacement for the API contract.

A Vulkan render pass can describe multiple subpasses, their attachment uses, and their dependencies. An input attachment reads at the corresponding pixel/sample location; a subpass dependency expresses execution and memory ordering. The specification says this advance description gives implementations an opportunity to optimize transfers, and that framebuffer-space dependencies may be merged into tiled rendering. It is not a guarantee of merge. The Vulkan guide calls merging implementation-dependent and points to `VK_EXT_subpass_merge_feedback` as a way to inspect an implementation’s decision. Dynamic rendering with local-read support expresses some similar local dependencies, but still does not promise a specific cache residency. Explicit barriers, a dependency requiring broader ordering, or a consumer that samples arbitrary neighboring coordinates can prevent the simple same-pixel reuse case.

Direct3D 12 makes the distinction explicit too: render-pass metadata exposes beginning/ending access and dependencies so a display driver can minimize loads/stores, but Microsoft says the performance benefit depends on driver support; the runtime may map the API onto the existing surface. D3D12 also assigns ordering and resource-state responsibilities to the application. Its preserve/discard/resolve declarations are useful contracts, not a universal promise that a render pass becomes a hardware tile pass.

| Strategy | Lifetime and API intent | Idealized attachment traffic | Main boundary or failure case |
|---|---|---|---|
| **Merged render pass / subpasses / local reads** | Keep an intermediate live between same-pixel producer and consumer subpasses, then discard it after last use. Declare input attachment/local read and the needed dependency. | Zero external traffic for the intermediate if the implementation actually retains it; final persistent output still has to become visible to its consumer. | Merge is a driver choice. A non-framebuffer dependency, unsupported access, too many live attachments, or a wider-neighborhood consumer can force a split or spill. |
| **Separate passes with store then load** | End one pass with valid contents for an external consumer; begin the next with `LOAD` if it needs the prior pixels. | For an uncompressed attachment of A pixels, B bytes/sample, and S samples: approximately `2 × A × B × S` for one full store plus one full reload. | Required for later sampling/compute, cross-frame history, or other persistent uses; caches/compression may alter physical bytes but do not remove the lifetime dependency. |
| **Transient / lazily allocated attachment** | Mark a temporary framebuffer attachment transient; use lazy allocation if supported; clear or declare undefined input as appropriate and discard at last use. A later subpass can consume it before that lifetime ends. | Ideally zero backing allocation and zero external load/store for the transient value; any final persistent output still stores. | Not suitable for a consumer after the render pass. A lazily backed resource can incur backing if accessed, and the feature is not uniformly supported. |
| **MSAA resolve at pass end** | Keep multisample data live through rendering, resolve into a single-sample target, and discard multisample contents if they are no longer needed. | Ideal inline path writes about `A × B` bytes for the resolved output, not `A × B × S` for the samples. | If the unresolved samples must persist, both sample storage and resolved output are needed; a later external resolve can add a full sample read and output write. Resolve support and residency are implementation/format dependent. |

## Traffic model (arithmetic, not bandwidth measurement)

Let `A = width × height` covered pixels, `B` be bytes per sample, and `S` be sample count. The first-order raw payload for a full attachment load or store is `A × B × S`; clear-at-start or undefined-at-start needs no read of old pixels, and a discard store needs no valid-result write. An intermediate that is stored after one pass and loaded in the next therefore contributes roughly `2ABS`. A direct MSAA resolve into a persistent one-sample target contributes roughly `AB` output bytes while the `ABS` sample surface can be discarded. If samples are stored, later read for resolve, and a resolved output is written, the rough sum is `2ABS + AB`. If both samples and resolved output must persist, count their stores separately (`ABS + AB`), plus any subsequent reads.

For 1920×1080 RGBA8 at 4× MSAA, `A=2,073,600`, `B=4`, and `S=4`: one raw multisample image is 33.18 MB (31.64 MiB); a store-plus-reload is 66.36 MB (63.28 MiB); adding a resolved-image write gives 74.65 MB (71.19 MiB). The inline resolve’s ideal output is 8.29 MB (7.91 MiB). These are byte-count examples, not observed bandwidth, timing, or power. They omit partial coverage, compression, metadata, caches, alignment, depth/stencil packing, and implementation-specific transaction behavior. Arm’s 2021 Mali guide gives its own 1440p/60 4× example for comparison, explicitly presenting arithmetic for a naive DRAM round trip and an inline resolve, not a universal result.

## Capacity, consumers, and compression boundaries

Tile size is hardware-managed and generally opaque to portable Vulkan applications. The Vulkan guide notes that formats, attachment count, and MSAA sample count all increase the per-pixel tile working set; fixed on-chip capacity can then lead to smaller tiles or less efficient execution. More simultaneously live G-buffer planes and higher sample count therefore narrow the merge opportunity. A real implementation may choose different tile sizes, split work, or move data through external memory. API descriptions do not expose a portable capacity threshold, so no cross-vendor byte cutoff can be inferred from the sources here.

Later consumers determine the needed lifetime. Deferred lighting that reads a G-buffer at the same pixel can fit a later subpass; transient/lazy allocation can still be useful if all consumers finish before the pass ends. A blur, post-process, or other kernel that samples neighboring pixels may need a completed image visible outside the attachment interface and thus a stored image plus later read. Temporal history and a drawable also outlive a pass or frame and need persistent contents. Cross-frame reuse, external sampling, and explicit synchronization are counterexamples to assuming that a transient attachment can simply remain in tile memory. A driver may retain cached data opportunistically, but the application must still meet the declared API lifetime.

Lossless framebuffer compression changes physical traffic for eligible persisted surfaces; it does not erase the store/load lifetime or make a transient resolve unnecessary. Arm’s issue-10 guide says AFBC is automatic when supported, but may be unavailable or trigger runtime decompression. On documented Mali paths, shader `texture()`/`texelFetch()` accesses can use rendered AFBC textures, while `imageLoad()` or `imageStore()` can trigger decompression. The guide also limits image shape, sample count, tiling, format, and usage flags; specifically, transient-attachment usage prevents AFBC on pre-Valhall GPUs. Thus a transient allocation that saves a tile-memory round trip may trade away compression for a later persistent read, depending on generation. The byte model should treat compression as a physical-traffic modifier to measure on a named device, not as an assumed ratio or substitute for avoiding unnecessary stores.

Apple’s TBDR documentation provides a concrete, vendor-specific example: fragment and tile stages share local imageblock/tile memory, and tile shaders can combine rendering with computations on that data. This supports the general lifetime model but is not evidence that another GPU, including an Intel compute device, has the same tile storage or graphics pass-merging behavior. Arm’s bandwidth-efficient graphics deck describes Mali-T600 with 16×16 tiles and 128-bit pixel data; those historical parameters illustrate why per-tile working-set capacity matters, not a portable limit. Neither source licenses transfer of Mali or Apple raster behavior to Intel SYCL compute.
