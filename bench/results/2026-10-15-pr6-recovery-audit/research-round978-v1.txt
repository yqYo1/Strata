# Round 978 — Minimal event-service attribution for the measured MoE path

Decision support, source/read-only. Recommendation: after Main’s active build and serialized validation are finished, add a default-off, bounded event collector to one fresh diagnostic request. Keep the current as-is window candidate and both paired receipts unchanged. Use actual returned SYCL events, sample by MoE shape and phase, and read `command_submit`, `command_start`, and `command_end` only after the existing checked chunk drain. This separates reported command service from device-side submit-to-start delay while avoiding a wait per command. It does not measure execution-unit occupancy or physical memory traffic.

## Evidence and measurement boundary

The new input declares six artifact hashes. I read each referenced file and all six SHA-256 values match `orca-actual-profile-wave976-978-v1.json` (SHA-256 `a83b4458…a419a9334a`). The matched optimized receipt is `own-qsa-bf16-prefix-tilepack-profile-census-bf16-prefix-optimized-r0-v2.json` (SHA-256 `03559f30…da92b2558`); its compact summary is `optimized-profile-after-packed-stall-summary-v1.json` (`88972514…ab4e65`). The paired tilepack receipt remains `passed=false, complete=false`; the optimized profile is a single diagnostic and the summary says `performance_adopted=false`. This is not a clean speed comparison.

For 39,262 prompt tokens (39,261 batched), the optimized profile reports 84.324 s wall and 78.694 s issuing-thread CPU. Its wait wrappers account for 58.052 CPU seconds / 58.243 wall seconds over 5,601 calls, predominantly 1,328 compatibility waits (58.048 CPU seconds) and 4,257 event waits (0.004 CPU seconds). Outside-wait CPU is 20.642 s: existing spans attribute 4.895 s to source copying, 4.955 s to upload submission, 2.398 s to GEMM submission, 0.083 s to host grouping, and leave 6.542 s unclassified. `route_exchange` is 36.775 s inclusive CPU but only 0.004 s outside its nested waits. Thus the long route interval is a wait boundary, not CPU grouping time. Likewise, CLOCK_THREAD_CPUTIME_ID charged inside a blocking API can include driver polling; it is not a measure of GPU work. Do not repeat the earlier inference that the wait share (formerly 77%) is GPU-compute share.

The coarse profile’s MoE, QSA, and upload queue intervals are respectively 20.186 s, 24.714 s, and 8.469 s. Their own header explicitly calls them nonexclusive and includes host submission gaps. They locate queue phases, not busy time. The shape census reports 59,614 expert chunks and 119,228 MoE GEMMs (GU and down), 18,845,280 routed rows per GEMM kind, and 185.257 TF logical GEMM FLOPs. Its 586.0 GB “logical dequantized weight write” estimate is explicitly not physical VRAM traffic. CPU accounting has 123,156 `gemm_submit` calls, a broader count than the MoE-only census; keep those populations distinct.

The previous host-attribution v3 report already found that its inclusive route wait did not measure route-transfer service and that its 25.793 s of host residual-copy API time did not prove CPU math. The round-947 review digest accepts round 945 with caveats, records no counter proof, and says the later main reconciliation does not confer timing/adoption status. Existing queue-marker limits remain applicable; the new opportunity is narrower: this source path returns actual per-command events that the old marker profile discarded.

## Production event path

The measured receipt selects `STRATA_SYCL_PREFILL_NATIVE16_BACKEND=vllm`, `STRATA_SYCL_PREFILL_NATIVE16=bf16`, `STRATA_SYCL_PREFILL_NATIVE16_VLLM_TILE=auto`, and `STRATA_SYCL_PREFILL_SAME_QUEUE=1`. In `src/prefill/sycl/vllm_xe2/native16.cpp`, `Gemm::beta0` returns the `sycl::event` from the selected `q.submit`. `src/prefill/sycl/gemm16.cpp`’s `vllm_submit` preserves that return, and `Gemm::bf16_out16`/`f16_out16` receive it, call `finish(stream_, event)`, then discard it. `include/strata/sycl/launch.hpp::finish` waits only for a null stream, so the observed explicit same-queue path can retain selected handles without adding waits. The SYCL prefill setup assigns `m.copy = m.cs`; validate the actual stream is nonnull and is the profiled in-order queue before enabling a collector.

`src/sycl/runtime.cpp` constructs the compute queue with both `in_order` and `enable_profiling`; the separate transfer queue is in-order but unprofiled, and `make_queue` defaults to unprofiled. The measured environment’s same-queue setting means `m.copy = m.cs` in the prefill setup, but the collector must test the concrete queue used by each command rather than assume this setting in a future run. SYCL requires profiling capture for a queue with `enable_profiling`, and the reference says timestamps from one backend share a timebase. It also says querying `command_start`/`command_end` can block until running/completion and gives no guaranteed timestamp accuracy. Therefore read them only after a successful existing drain, validate `end >= start >= submit`, and mark any query error or unfinished event as an incomplete diagnostic. [SYCL event profiling reference](https://github.khronos.org/SYCL_Reference/iface/event.html), [queue profiling and in-order semantics](https://github.khronos.org/SYCL_Reference/iface/queue.html).

Tap points should follow actual submits, not insert timing markers: (1) retain the event in `gemm16.cpp` just after `vllm_submit` and before `finish`; tag layer, chunk, expert, GU/down, `ne`, `N/K`, and chosen tile. (2) In `src/kernels/sycl/iq.cpp`, tap the returned event in both the ordinary `iq_dequant_gu_f16`/`iq_dequant_f16` path and `parallel_iq_launch` if that branch is selected. (3) In the current compact-FP16 path, tag the `gather_rows16` launch in `src/prefill/sycl/postops.cpp`, the `native16::swiglu` launch, and `native16::combine` in `src/prefill/sycl/native16.cpp`. (4) If upload command time is needed, tap the `queue(st).memcpy` event inside `src/sycl/compat.cpp::cudaMemcpyAsync`, record direction/bytes, and only accept it if that queue advertises profiling. Existing source-copy and upload-submit CPU spans already measure host preparation/submission; add only aggregate issuing-thread CPU spans around the dequant, gather, and activation wrappers if current `unclassified` CPU still prevents a decision. Do not add a timer or output per expert.

`include/strata/sycl/cpu_wait_profile.hpp` measures non-overlapping host regions with `CLOCK_THREAD_CPUTIME_ID`, separately subtracting explicitly wrapped waits. `LayerMajorCoarseProfile::chunk_retired` is called after the successful existing `cudaStreamSynchronize` at chunk retirement. Its `retired` method reads queue marker elapsed time only after completion; those marker deltas still span host gaps between commands. The new collector should use that same successful retirement point to query retained per-command events, not call `cudaEventElapsedTime` or introduce new barriers.

## Capture options

| Option | What it separates | Main limitation |
| --- | --- | --- |
| Retain every MoE GEMM event, query at chunk retirement | Per-GEMM reported service and submit-to-start delay | About 23,846 GEMM handles per 8K chunk (119,228 total), before dequant/post-op/copy handles; backend storage is opaque and this is unnecessary event pressure. |
| Bounded stratified events, query at chunk retirement | Same per-command measures across shapes/phases while bounding retained events | Samples estimate populations; representativeness and query completeness must be recorded. |
| Focused replay of selected shapes/layers | Good control for timer resolution, call-site mapping, and instrumentation calibration | Replays can alter expert mix, queue backlog, source/copy concurrency, and host submission gaps, so they cannot answer whether the actual request was front-end or service limited. |

Choose the bounded sample as the minimum useful next measurement. For each of five chunks, sample at most 256 GEMMs: the eight receipt row bins (`1–15`, `16–31`, `32–63`, `64–127`, `128–255`, `256–511`, `512–1023`, `1024+`), both GU and down, four samples in each of four layer quartiles. Use deterministic reservoir selection within each `(chunk, layer-quartile, kind, row-bin)` stratum; store total eligible and selected counts. This gives at most 1,280 GEMM events, roughly 1.1% of the census population, spread across the observed shapes rather than the first experts only. Estimate weighted totals with actual `eligible/selected` counts; report per-bin distributions and uncertainty, not an unweighted sum of sample durations.

Add at most 32 dequant samples per chunk (GU and down, four in each layer quartile), and 16 each for gather, SwiGLU, and combine (four per layer quartile). Sample at most 16 weight-upload copies across the request, four per layer quartile. These caps total 336 phase samples per chunk plus up to 16 upload samples in the same chunk; set a hard cap of 352 event references. Store `submit/start/end` timestamps and compact phase/shape tags for no more than 1,760 sample records across the five chunks. A 40-byte packed numeric row is about 70 KB; cap fixed host records at 128 KiB and the serialized diagnostic at 256 KiB. The runtime does not guarantee the memory cost of its opaque event resources, so the explicit 352-handle ceiling is a separate guard, not a claim of a hard backend-memory bound.

Own the fixed collector beside the request’s existing layer-major profile state. Keep event handles only until the already successful chunk retirement; query status and three timestamps, fold the numeric row into the fixed request table, then clear the handle immediately. Add no new event pool, marker, wait, per-kernel drain, dynamic vector growth, or per-call logging. On an early error, failed drain, missing stratum, cap overflow, profiling exception, or unexpected queue, set `complete=false`; do not query unfinished events or claim a sample. Keep the existing owner/queue/allocation cleanup ordering intact, and release remaining handles only after that owner’s normal checked retirement.

The submit-to-start interval is device-side queue/runtime delay, not a direct host CPU span. `command_end - command_start` is the backend-reported service interval for the command, not execution-unit occupancy, useful FLOPs, cache traffic, or PCIe bytes. Since all event timestamps for a backend share a timebase, selected same-queue `next.submit - previous.end` can expose an idle gap only where it is positive; a negative value means submission was already queued before prior completion. Never subtract these device timestamps from `steady_clock` or thread CPU timestamps without a separately validated cross-clock mapping. Level Zero exposes timestamp valid bits/resolution and warns about finite timestamp width/wrap for its native timestamp events; stay at the SYCL level for this first pass and record the selected device/backend/runtime and SYCL profiling timer resolution. [Unified Runtime event profiling](https://oneapi-src.github.io/unified-runtime/core/api.html), [Level Zero timestamp event API](https://oneapi-src.github.io/level-zero-spec/level-zero/latest/core/api/apis/event.html), [Level Zero timestamp limits](https://oneapi-src.github.io/level-zero-spec/level-zero/1.4.8/core/PROG.html).

## Qualification before interpretation

First run a small, separately owned calibration on the same profiled queue with a bounded sequence of representative short/long kernels and copies, one final checked drain, and post-drain queries. Record device `profiling_timer_resolution`, backend, driver/runtime versions, queue properties, and a no-op or very short command distribution. Reject zero/negative or coarsely quantized values for a claim about short GEMMs; SYCL explicitly does not guarantee accuracy. Verify all timestamp order constraints, no query blocks after the drain, and that profiling failures are surfaced. This calibration is not a throughput comparison.

Then build the collector as default-off against the same pinned candidate source; do not mutate the live window. Run it in a separate process after Main’s serialized work, with the same 39,262-token input digest, 8,192 chunk, queue/backend flags, and shape-census controls. Require the census, number of chunks, command populations, all selected/eligible counts, checked retirements, async error status, and fault/ownership checks to agree with the receipt. Compare a collector-off and collector-on diagnostic in separate processes to estimate observer perturbation; preserve correctness and original receipt statuses. If the chosen upload queue lacks profiling, mark upload timing unavailable instead of adding a barrier or silently profiling another queue.

Interpret only after the weighted service estimates and device-side queue delays agree across strata and the per-request coarse intervals reconcile within expected missing-operation/marker bounds. If estimated selected-command service is a small part of the 20.186 s MoE envelope while submit/start gaps and the existing CPU phase spans dominate, investigate front-end/transfer preparation next. If service estimates dominate, identify which command family and shapes account for it before changing kernels. Even then call the result a device-command-service bottleneck candidate: without OA/PMU or vendor counters it cannot establish EU utilization, memory-bandwidth saturation, or hardware-busy percentage. Repeated clean, unprofiled request-level measurements and a controlled intervention are still required to call an optimization adopted.
