# R974 — GPU MoE window fixture audit

## Scope and provenance

This is a static audit of the Main-authored sycl_moe_window_test fixture and the production route planner, gather, combine, runtime, and upload-lease APIs it calls. It extends the earlier engine source audits by reviewing the new test’s independent expected path and its asynchronous lifetime; those earlier decisions did not audit this fixture. The supplied source identity is commit 370c9976. All seven requested SHA-256 values matched the listed files; no Git commands, edits outside this report, builds, tests, GPU work, profiler, or process inspection were performed.

The fixture is an EXCLUDE_FROM_ALL executable linked to strata_prefill (cmake/sycl_backend.cmake:139-141). It invokes the production MoeWindowRoutes::build, gather_rows16, and native16::combine; its own kernels generate inputs, a synthetic per-expert witness, and the oracle. It deliberately does not execute the model, router, GEMM/dequant, state, or engine window entrypoint. I used only the pinned Strata files and the official [SYCL 2020 specification, revision 11](https://registry.khronos.org/SYCL/specs/sycl-2020/pdf/sycl-2020.pdf) for the host-pointer rule for queue::memcpy. I did not treat the compiler noted by the previous syntax receipt as an implementation reference.

## Findings

### P2 — Final-output oracle can mask a wrong route; add a pre-combine route witness check

The expected result is independent of the planner’s source map, slot map, offsets, and jobs: oracle_ids is copied from the original ids at tests/sycl/moe_window.cpp:110-112, and expected output at lines 139-146 loops over those IDs. This is meaningful coverage of the complete route-to-combine result. However, the comparison happens only after ten weighted BF16 expert values have been accumulated in FP32 and rounded back to BF16 by production combine (src/prefill/sycl/native16.cpp:148-157). A wrong source/slot/job can therefore escape if its weighted change is hidden by accumulation or final BF16 rounding. The per-gather check at fixture lines 132-135 does not close this gap: it computes the expected input row from the same device src entry that the gather consumed. It checks gather indexing relative to that map, not that the map identifies the original token.

The map oracle is independent, but the synthetic arithmetic intentionally is not: both producer and expected paths call the fixture’s input_bits, weight, witness, and shared_bits helpers (lines 58-68, 132-146). This is suitable for routing checks, not an independent check of those helpers or the model’s expert arithmetic.

The negative-source and negative-slot controls are useful mutation checks, but only prove that the selected in-range substitutions for the two salts change the final output when run. negative-source sets src[0] to another valid row (line 114); negative-slot changes one slot to another valid route position (line 115). Neither control proves that every planner or split error is observable after reduction.

Required before treating this as a broad mapping oracle: add a GPU check over every original (token, k, column) before combine. Use original[token*K+k] to derive the expected expert and source row from the original input pattern, read d[slot[token*K+k], column] only after checking the slot is in [0,routes), and compare it directly with the expected synthetic witness. Keep the final-output oracle as a separate combine check. This exposes a wrong gather source or expert job before weighted reduction can conceal it. It still tests only the synthetic witness, not GEMM math.

### P2 — “Negative” map cases do not exercise invalid sentinels or source bounds

The production gather kernel treats negative source rows as zero but has no upper-row bound (src/prefill/sycl/postops.cpp:239-247); native16 combine skips negative slots and turns slots at or above down_rows into NaN (src/prefill/sycl/native16.cpp:151-157). The current fault controls stay within valid ranges, so they test output sensitivity rather than these malformed-map behaviors. That is safe for the current planner-produced map, but a positive source value beyond rows could cause an out-of-bounds device read before the output oracle runs. Canary checks cannot detect an out-of-bounds read; they guard writes around allocations.

If coverage of invalid map values is intended, add separate cases that validate malformed maps before any gather/combine read (or extend an appropriate checked gather entrypoint with an explicit source-row extent). Keep those separate from the current in-range mutation controls. No malformed source is currently generated by this fixture, so this is a coverage limit, not evidence that the current run submits invalid memory accesses.

### P3 — The route shapes are strong, but some case labels overstate direct assertions

hot8193 and hot16384 use ten distinct experts for every token. The planner check at fixture lines 82-86 asserts ten counts equal to rows and exactly twenty jobs, so these cover 8192+1 and 8192+8192, including ne == window. Per-job source and destination spans are checked before enqueue (lines 124-130), and output writes use the planner’s global_row offset (line 135). The balanced formula covers all 512 experts exactly 320 times at 16384 rows; tail16383 is one row short of the maximum, and single has ten distinct experts. Those latter shapes do not assert their expected counts/job totals directly, but the full output oracle and canaries can still expose many omission/overlap errors. Two salts vary routing and operands on every invocation.

The fixture uploads a full source and slot plane once and gathers from src + job.global_row (lines 110-112, 124-135), matching the current engine path in src/prefill/moe_window.inc:111-115,138-146. It does not test router readback or real expert math. The witness check does exercise the actual 16-bit gather and actual native16 combine implementations, so the split destination and gather sequence are not purely host simulations.

Representation and alias ordering are consistent for this witness: mixed starts with finite FP16 bit patterns, gather copies those 16-bit values, witness decodes them as FP16 and writes BF16 into down, and native16 combine decodes shared/down as BF16, accumulates with FP32 weights/FMA, then stores BF16. The oracle mirrors these conversions and final rounding. The shared gate is zeroed, so both paths use the exact factor 0.5. mixed is reused as combine output only after the per-job gather and witness commands have been enqueued; the Runtime compute queue is in-order, so those reads precede the output writes. This tests the overwrite ordering without claiming it tests the engine’s GEMM producer.

## Lifetime, queue, and false-pass controls

I found no async lifetime or queue-domain bug in the fixture’s current control flow. Every Allocation is constructed before the armed DraftUploadGuard; no work is queued until after all buffers and the host ids/route plan exist (moe_window.cpp:75-106). The source vectors and MoeWindowRoutes remain alive through rt->wait(). The runtime’s compute queue is in-order, and all fixture commands plus production gather/combine use that same queue and runtime (runtime.hpp, launch.hpp, runtime.cpp:97-120). Device allocations are made by that runtime; explicit validate_device_span checks cover the mixed tensor, each source slice, and each Down destination slice before gather (moe_window.cpp:127-130). The remaining combine pointers are also interior spans of buffers allocated from that same runtime.

SYCL permits host pointers as either side of queue::memcpy; the specification requires a USM pointer, when used, to be accessible to the queue’s context/device. The pageable std::vector upload sources are therefore valid pointers, and their lifetime extends past the checked drain. They may affect transfer behavior, but not correctness here. The scalar mismatch readback remains live until the blocking drain at lines 148-149. Each guard readback’s stack observed array remains live through its rt->wait(); a failed read drain calls fail-stop before that host destination unwinds (lines 43-52).

On ExpectedStop, stack unwinding destroys the armed lease while all buffers, ids, and the plan still live. Its destructor drains before the catch marks the case stopped (DraftUploadGuard in draft_uploads.hpp, fixture lines 101-105 and 149-152). An async error makes Runtime::wait() throw; the guard retries the sticky runtime check and fail-stops rather than releasing possible DMA/kernel owners. This may terminate without a normal fixture diagnostic on device failure, but cannot turn that failure into PASS. The same applies to failed canary readbacks. The canaries are real 256-byte device regions, poisoned before use and checked after completed copies; they protect writes at both ends of each allocation, not arbitrary interior overruns or reads.

## Execution priority and limits

When Main schedules GPU execution, run independent processes in this order: traced smoke first to expose queue/oracle problems cheaply; single, unwind, negative-source, and negative-slot next; hot8193 to validate the split boundary before maximum-sized allocations; then hot16384, balanced16384, and tail16383. Each invocation already runs salts 1 and 37. The maximum case allocates about 839 MB for Down alone, about 168 MB for mixed/shared, and about 42 MB for gathered, before other buffers and runtime overhead, so do not use it as the first diagnostic. Capture a timeout/hang receipt separately if a case stalls; do not let a single trace include all large cases.

The existing receipt is syntax-only (moe-window-fixture-syntax-v1.json: passed, no code generation or GPU execution). No executable, route case, invalid-map case, model GEMM, state, physical-context, or performance claim is validated by this audit. The fixture is a meaningful synthetic production-kernel smoke test, with the pre-combine witness check above needed before treating it as a strong general route/gather/combine correctness oracle.
