## Route and storage ownership

The typed route is startup opt-in `STRATA_SYCL_PREFILL_NATIVE16_QSA=1`, and requires native16 BF16. Long layer-major preflight rejects unsupported devices, old attention mode, nonzero K mapping, non-text positions, streamed/host-mirrored, rotated, Q4 or hybrid KV. It validates each QSA owner’s actual `n_pages` logical table and `n_slots` physical pool bounds before work ([`layer_major.inc`](../../../src/prefill/layer_major.inc), lines 45–48, 153–189). In `Prefill`, typed QSA projects Q/K/V to BF16, fuses K and Q norm/RoPE, appends BF16 K/V to the existing INT8 pools with FP16 scales, calls the explicit BF16 attention entry, then gates to the existing FP16 output projection; IDs, steps, selection, and the old FP32 API remain separate ([`prefill.cpp`](../../../src/prefill/prefill.cpp), lines 2349–2444, 2583–2605, 2631–2643). Typed scratch is overlaid on the existing QSA FP32 reservations; the owner comment says there is no new allocation (lines 483–489, 975–986).

The public typed API contract is BF16 Q/output, INT8 K/V plus FP16 scales, FP32 score/softmax/matrix accumulation, selected-ID semantics and bounded page extents ([`qsa_prompt_attn.hpp`](../../../include/strata/kernels/qsa_prompt_attn.hpp), lines 45–69). The registry checks are about truthful live allocation extents and queue context, not a requirement of 16-bit storage.

## Source differences and static accounting

The retained FP32 and typed attention entries both launch one work-group per `(query, KV head)`: `queries * 2 * 128` work-items, WG=128, SG=16, 12 query heads plus 4 padded rows, and 32 selected cells per online-softmax tile. Batch/head addressing and `steps[batch*kStepCount+kStepWidth]` are unchanged. New code explicitly rejects out-of-range logical and physical pages before forming a row; that adds per-ID integer checks but protects owner bounds. It does not add work-groups or a second attention launch ([`prompt_attention.cpp`](../../../src/kernels/sycl/prompt_attention.cpp), old lines 75–101, 146–161; typed lines 503–526, 565–581).

| Area | Retained FP32 | Typed QSA |
|---|---|---|
| Q/output global I/O | `[24,256]` FP32: 24,576 B each | `[24,256]` BF16: 12,288 B each. Q is read twice in both paths (max pass then tile fill), so source-level Q reads are 49,152 vs 24,576 B/query; output writes halve too. |
| Q operand preparation | One work-group max reduction for the 12 heads, one shared scale, then FP16 hi+lo Q tiles | BF16 widens to scalar FP32 for range/nonfinite checks, then one scaled FP16 tile. Each WG computes max and bad reductions per head for 16 rows: 16 subgroup max plus 16 subgroup bad collectives, versus the old single work-group max reduction. One more pre-loop barrier; both paths use seven work-group barriers per 32-cell tile. |
| P and accumulators | FP16 hi+lo probabilities; FP32 joint-matrix accumulators, score/softmax rows | One FP16 probability component; same FP32 joint-matrix accumulators, score/softmax rows. This changes rounding/math, not just storage. |
| Source-declared local storage | For old `Direct=true`, about 44,500 B/work-group from its local arrays | 32,336 B/work-group (`BF16_SLM` static assertion). About 12,164 B less than old direct source accounting; compiler allocation, spills, occupancy and timing are unmeasured. |

The new per-head power-of-two scale handles BF16’s wider exponent range before FP16 matrix input; finite/nonfinite and BF16 output-rounding behavior are explicit format/numerical choices. The one-part FP16 Q/P path is **not** forced by BF16 global storage. FP32 score, normalizer and matrix-accumulator state remain separate local arithmetic; neither FP32 accumulation nor its reductions should be confused with global tensor storage. New `scales_bad` also performs a work-group max reduction for each selected-cell tile (lines 590–600), while the old path accepts its loaded scales without that diagnostic.

**Launch counterevidence:** with a non-null engine stream, `finish()` does not wait (`launch.hpp`, lines 44–63). Typed QSA’s K norm/RoPE, append, Q norm/RoPE, attention and gate are five source-level helper launches; the FP32 route’s separate K RMS/RoPE, append, Q split/RMS/RoPE, attention and gate are eight, before projection GEMMs. Actual GEMM partitioning is shape-dependent. The typed source therefore does not support a claim of more QSA launches or an extra host synchronization. It does add complete allocation-owner checks: typed validation calls `validate_device_span` for output plus seven inputs (eight spans) at each attention call and is also called during preflight for every QSA state (`prompt_attention.cpp`, lines 706–742, 750–753; `layer_major.inc`, lines 170–188). This is host validation work, not device arithmetic.

## Bugs, provenance and limits

I found no definite source bug or undefined behavior in the typed kernel. The ID/count/page path bounds logical and physical pages before use (lines 569–581), and the output store covers only 12 real heads (lines 689–699). This is inspection, not a syntax, runtime or numerical check. R818’s source review ([own-native16-qsa-source-review-v1.ja.md](own-native16-qsa-source-review-v1.ja.md)) records the FP32 local reductions, new span ownership, page semantics and remaining accuracy gates; the older R787 attention review ([own-native16-attention-main-review-v1.ja.md](own-native16-attention-main-review-v1.ja.md)) records the original one-part Q/P precision trade. R822/R824 metadata concerns generic low-precision norm/activation bandwidth, not typed QSA; its reviewer explicitly held retrieval pending a named measured hotspot. The older QSA subprofile measured FP32 attention at 69,909 ms of nonexclusive queue interval for 941,424 queries, but that was a different 78,453-token diagnostic and is no typed-QSA attribution.

One directly relevant primary design: `vllm-project/vllm-xpu-kernels` commit [`08bf8ed99bdf2c41bc9ccd7393c56b4adc3e5b4a`](https://github.com/vllm-project/vllm-xpu-kernels/commit/08bf8ed99bdf2c41bc9ccd7393c56b4adc3e5b4a), the Intel Xe2 chunk-prefill path. Its BF16 instantiation explicitly uses `bfloat16_t` for Q/K/V/O and `XE_DPAS_TT<...,float,ElementQ>` at [`chunk_prefill.hpp`](https://github.com/vllm-project/vllm-xpu-kernels/blob/08bf8ed99bdf2c41bc9ccd7393c56b4adc3e5b4a/csrc/xpu/attn/xe_2/chunk_prefill.hpp#L266-L285) and lines 439–455. The kernel’s typed aliases and subgroup scheduler are in [`chunk_prefill_kernel.hpp`](https://github.com/vllm-project/vllm-xpu-kernels/blob/08bf8ed99bdf2c41bc9ccd7393c56b4adc3e5b4a/csrc/xpu/attn/xe_2/kernel/chunk_prefill_kernel.hpp#L89-L118) and `get_grid_shape` / `get_block_shape` at lines 209–215; its mainloop keeps score/output fragments and online softmax separate from global element types ([`chunk_prefill_mainloop.hpp`](https://github.com/vllm-project/vllm-xpu-kernels/blob/08bf8ed99bdf2c41bc9ccd7393c56b4adc3e5b4a/csrc/xpu/attn/xe_2/collective/chunk_prefill_mainloop.hpp#L169-L198), lines 552–681). This supports separating BF16 storage from FP32 matrix/softmax math, not Strata’s selected-cell mapping, local one-part precision, or performance. The cited source is under the Intel XPU `xe_2` / `vllm_xpu_xe2` path; that establishes the Xe2 family, not a particular board’s support or performance, and it is not portable evidence for another GPU. The [pinned repository README](https://github.com/vllm-project/vllm-xpu-kernels/blob/08bf8ed99bdf2c41bc9ccd7393c56b4adc3e5b4a/README.md#L147) declares Apache-2.0, while the cited kernel files carry BSD-3-Clause headers. No source was copied or adapted.

Until Main separates those costs on the measured input, the 2.56% whole-path regression does not identify a kernel cause or justify an adoption decision.
