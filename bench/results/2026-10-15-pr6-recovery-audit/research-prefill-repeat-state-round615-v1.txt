R615 repeated 32K prefill state and lifetime source audit
2026-10-15

Scope and result

Read-only source audit of the first, second and third repeated 32,089-token prompt in the same native process, with prompt-cache=0, conversation-cache=0, direct=0, ordinary graphs enabled, native verify capture disabled, and samequeue=1. No source changes, builds, tests, target-process actions, GPU actions or Git operations were performed. The failure facts and the important R613/R614 corrections are taken from `prompt-direct-bench-full-0-failure.ja.md`; the checked-in receipt's older interrupted encoding is not treated as different run evidence.

No source defect explaining a first/second/third-request divergence is confirmed. The selected repeated-call path has request-local temporary residual/cache owners, restores borrowed orchestration fields, and performs checked queue drains before releasing them. Persistent process state is expected in the GEMM object, SYCL runtime, oneMKL/JIT caches, allocation arenas, and expert pool, but source does not show a request-indexed state branch or an observed stale reference. Therefore a warm-process specialization/allocation or runtime interaction remains possible but unproven. The same-binary new-process success weakens a persistent GPU-failure explanation; it cannot distinguish process-local host/library state from timing or transient device behavior.

Configured source path

`bench/results/2026-10-14-primary-native-runtime/effective-build-flags.json` records `STRATA_ENABLE_SYCL=ON`, CUDA/HIP off, and compile commands with `-DSTRATA_ENABLE_SYCL=1`, `-fsycl`, and oneMKL headers. `cmake/sycl_backend.cmake:103-120` is the selected resolver: it builds `strata_engine`, and `strata_prefill` from `src/prefill/prefill.cpp`, `src/prefill/sycl/gemm.cpp`, `postops.cpp`, `blob.cpp`, `moe_mmq.cpp`, and `moe_fused.cpp`, then links the `strata` executable. This rules out treating CUDA `gemm.cu` or CUDA root-only paths as the failing prefill implementation. The benchmark config records `STRATA_SYCL_PREFILL_SAME_QUEUE=1`; `prefill.cpp:1541-1546` reads it once in a function-local static and sets `copy_events` false only when both stream handles are identical. The environment must therefore be fixed before the first prefill call, as it was in the owned recipe.

Repeated-request path and reset boundaries

`src/prefill/layer_major.inc:3-14` selects layer-major for `STRATA_PREFILL_LAYER_MAJOR=1` and `n > impl_->T`; it falls back to ordinary `run_impl` for short prompts. The request reaches `run_layer_major` with a full-model layer range and one layer at a time (`:16-40`, `:279-363`). The layer-major branch rejects legacy diagnostic switches that could add state or alter timing (`:67-73`). On every call it creates a fresh `ExpertCache`, upload slab, residual storage, residency map and guards (`:143-207`), then uses those local owners for the layer walk. Before publishing a layer's expert residency, it copies source blobs into the owned upload slab and drains the queue (`:287-307`). It also drains at entry, every layer boundary, after each run_impl pass, and at final exit (`:219-231`, `:303-307`, `:353-364`, `:377-385`). The callbacks are cleared after their checked per-layer boundary; the `Restore` destructor restores stage bounds, handoff pointer, cache/residency pointers, layer-major fields and callbacks (`:199-218`, `:370-372`).

That establishes good lifetime ordering for a normally returned layer-major call. It does not mean model/session tensors are transactional: `Restore` explicitly only restores borrowed C++ fields, while GDN/QSA/KV and residual state are mutated as inference proceeds (`:188-193` comments; `run_impl` receives `SessionState&` at `prefill.cpp:1530-1535`). A failed prefill can leave partial session tensors. That is a confirmed property, but not a confirmed cause here: the observed watchdog abort ends this native before its next API request, and no source evidence says a later request reused the partially updated session. Do not infer that prompt-cache=0 resets all tensors; the exact server/session reset call and this run's request lifecycle must be paired before making that claim.

The regular layer loop emits `progress_at("reading the prompt (batched): layer", l, p0)` at `prefill.cpp:1976-1980`, before layer work. The recorded layer27/chunk0 therefore pins entry to that loop only; it does not identify GDN, QSA, GEMM, host route grouping, or the later callback. At the routed MoE boundary, host route IDs are copied and `cudaStreamSynchronize(m.cs)` is called before CPU grouping (`:2418-2424`). This is a real blocking boundary and remains a plausible localization point, but no retained progress fact says the third call reached it.

oneMKL/GEMM and persistent process state

`Gemm::native` validates the dimensions and scratch, then serially queues IQ dequant and FP16 GEMM for each output-row block (`src/prefill/sycl/gemm.cpp:102-132`). `multiply` submits oneMKL row-major GEMM on `queue_for(stream)` (`:18-29`). `finish(stream,event)` in `include/strata/sycl/launch.hpp:60-63` waits only when the stream is null; the prefill supplies its non-null in-order queue, so a call normally returns after submission, with completion ordered by the in-order queue and collected at explicit `cudaStreamSynchronize` boundaries. This makes the routed copy/sync and layer-major drains meaningful host-blocking sites. Source alone cannot tell which one was active at the watchdog.

The same `Impl::gemm` is initialized against caller-owned scratch once per prefill initialization (`prefill.cpp:827-832`); it is not re-created per prompt. The SYCL runtime queue/device and vendor oneMKL/JIT/module caches are process-scoped or library-managed. That means first-call warmup can differ from subsequent calls, and request 3 can encounter accumulated allocator/cache state. It does not establish unbounded cache growth, stale buffers, or compilation at layer27. In particular, no request-specific cache invalidation or module reset is visible in this path. Requiring a source-level `sycl::queue` reconstruction between requests would contradict the designed shared native process.

Worker-pool boundary

The CPU expert pool is also reused across calls. `ExpertPool::run_split_multi_native` publishes batches through `run_phase(5/6)`, updates the descriptor pointers for each batch, and sets `mode_=0` on return (`src/kernels/cpu/pool.cpp:672-705`). Pool synchronization contracts say parked workers precede writes and completion alone is insufficient without the parked boundary (`include/strata/kernels/cpu/pool.hpp:190-209`); R613's 18/18 done and 5/5 parked snapshot is consistent with this completed-batch boundary. Descriptors `mjobs_` and `nfmt_` remain stored as raw pointers after return, but the next `run_split_multi_native` replaces them before publishing another split phase. Source evidence does not show workers dereferencing those fields while parked. Their persistence is a lifetime condition worth preserving, not a demonstrated dangling dereference. This snapshot also cannot exclude the main request thread waiting elsewhere.

Verified eliminations and remaining uncertainty

- No temporary layer-major upload/residual/cache owner is released before the surrounding queue drains on normal completion; the RAII guard aborts if it cannot prove retirement (`layer_major.inc:219-230`, `:377-385`).
- samequeue=1 removes the auxiliary copy-event path only when copy and compute streams alias; it does not remove the explicit queue synchronization or prove the outstanding work completed during the stalled call.
- oneMKL and IQ dequant reuse stable scratch; scratch block count is checked and spans validated before enqueue. No concrete under-sized scratch or request-specific shape-cache defect was found (`gemm.cpp:102-132`).
- The persistent GEMM/runtime/pool lifetime is real; stale state across calls is not established. The documented partial SessionState mutation on an interrupted inference is real; reuse of that mutated state by a later request is not established.
- The watchdog's layer marker is emitted before work, and the pool being parked does not locate the request-thread stall. The source cannot discriminate host grouping, runtime submission, queue completion, allocator/JIT, or transient device delay.

Disposition

No code fix is supported by this audit. Keep the failure classified as an unresolved request-local prefill liveness event; same-binary recovery means a persistent GPU hang is unproven. The next source-directed capture should map the already planned owned all-thread snapshot to the queue submit/wait or host grouping boundary, with layer/chunk/operator markers around `Gemm::native`, the route-ID copy/sync, and layer-major drains. Preserve environment immutability from exec through provider initialization. This report does not recommend another generic stack plan; it identifies the exact source boundaries against which Main's prepared capture can be interpreted.
