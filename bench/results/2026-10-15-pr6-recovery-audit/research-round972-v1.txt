## Work that stays the same

Attention, token/step preparation, PLE/GDN/QSA state work, and the 8K operator limit stay on the original per-piece path. The candidate runs attention once per piece, stores its BF16 residual in the bank, then does the two pieces' FFN work. It does not rerun attention. Its `run_moe_window` loops by 8K at lines 84-101 for HC norm/mix/injection, router, shared expert and scalar gate. These per-row projections and shared-branch arithmetic are still done twice, with the same 8K projection shapes as baseline. The number of HC writes is also still two (lines 149-151 versus baseline per-piece write at 3427-3430). The candidate combines one 16K window rather than two 8K pieces, but still combines W*K=163,840 route slots.

Layer-major's 512-expert-per-layer source copies and uploads remain unchanged (`layer_major.inc:482-538)); the window does not reduce expert H2D payload or CPU `copy_blob` calls. Both arms use the already populated GPU expert cache when both residual spans are GPU-resident. RAM-side pieces and GPU/RAM mixed pairs do not enter the window: the selection requires both consecutive spans to be device spans, otherwise the existing 8K path runs (`prefill.cpp:1880-1888)). Those fallback pieces get no window savings.

## Route exchange, host work and syncs

For a full (W)-row pair, one int32 route plane is W*K*4=655,360 bytes. Candidate reads IDs D2H once (655,360 B), then uploads one slot plane and one source-row plane (655,360 B each): **1,966,080 B** of route metadata total. Baseline does two 8K exchanges and uploads the same two planes per piece: the same **1,966,080 B** total. So batching halves host transfer/API submissions, not route-map bytes.

In the ordinary non-fused baseline route path, each 8K piece issues one ID readback (mapped mode uses a `copy_i32` kernel into the pinned mapped group buffer; fallback uses D2H `cudaMemcpyAsync`) and then `cudaStreamSynchronize` before host grouping at lines 2808-2810. It submits two slot/source copies per piece at 2880-2884. Candidate issues one `cudaMemcpyAsync` D2H plus one sync at `moe_window.inc:103-105`, and two H2D map copies at 113-115. With baseline mapped grouping, that changes six small copy-kernel submissions per pair to three CUDA copy calls; with baseline vector fallback, it changes six memcpy calls to three. These are API/launch counts, not transfer timings.

Host route work is not eliminated. Baseline counts routes then constructs slot/source maps for each half; candidate's `MoeWindowRoutes` counts and constructs the same total 163,840 slots once for the window. It adds a pairwise duplicate-ID validation loop: exactly W*45=737,280 integer comparisons (`moe_window_routes.hpp:61-90`). Candidate allocates window-sized source/slot vectors in a new route owner each window and frees them after the final drain. The ID vector itself is retained by the request context. One transfer-policy concern: all three candidate host planes are `std::vector<int32_t>` storage (`prefill.cpp:439-445`, header 82-84), not pinned. Baseline's common `grp_host` alternative is `cudaHostAllocMapped` (`prefill.cpp:874-889`). Candidate source-level call counts therefore do not prove overlapped DMA; pageable staging or blocking work can offset a saved submission. Its `source_H2D_bytes` counter increments only for source rows, not the equally large slot-map upload (`prefill.cpp:156`); report total map bytes separately.

Per two pieces, explicit `cudaStreamSynchronize(m.cs)` call sites are:
- **Intermediate GPU-bank layer:** baseline has two route drains and two callback store drains. Candidate has two post-attention bank-store drains, one router-ID drain and one both-HC-writes drain. Both are four syncs per pair. Candidate moves one wait earlier and joins the FFN phase, but source counts do not show a net sync reduction.
- **Final layer with callbacks:** baseline has two route drains and two BF16-to-FP32 callback bridge drains (four). Candidate keeps the two callback bridges and adds two post-attention bank-store drains, one route drain and one window FFN drain (six total). It adds **two explicit syncs per pair** on this path. The final layer is currently window-eligible; `window_piece` has no `LE == g.n_layers` exclusion. It also requests two unnecessary-for-next-layer D2D attention-to-bank copies of 167,772,160 B each (320 MiB aggregate). Consider leaving the final layer on the 8K path unless measuring the final callback consumer shows a benefit that pays for those copies and waits.
- **RAM or mixed placement:** fallback keeps the baseline route and per-piece callback drains. An intermediate RAM store transfers 167,772,160 B per full piece D2H; a two-piece pair transfers 320 MiB. The candidate does not consolidate it.

The per-pass and per-layer drains are shared by both implementations; they are excluded from the pair counts above. `chunk_retired()` after the checked drain queries/reads elapsed events; it does not add a stream synchronization (`layermajor_coarse_profile.hpp:65-83`). Debug-only syncs are outside these normal-path counts.

## Dequant, gather, GEMM and logical data volume

For every active expert, baseline calls both native dequantizers once per 8K piece (`iq_dequant_gu_f16`, `iq_dequant_f16`, lines 3261-3263). Candidate's `loaded` expert guard calls each once per expert in the union of the two pieces (`moe_window.inc:117-133`). Thus it saves exactly one dequant pair per expert present in **both** pieces. Each pair writes 6,553,600 B of FP16 GU plus 3,276,800 B of FP16 Down, 9,830,400 B total. If all 512 experts are active in both pieces, that is 512 fewer dequant pairs and 5,033,164,800 B (about 4.69 GiB) less logical dequant-output traffic. If the same ten experts have `ne == W` (all tokens choose that same top-10 set), it saves ten pairs and 98,304,000 B (93.75 MiB). Each layer's original quantized blob upload is unchanged. These are source tensor writes; actual DRAM traffic may be lower or higher due to caching and kernel implementation and must be measured.

For an ideal balanced distribution across all 512 experts, the window count is 320 rows per expert and each half is 160. Baseline issues 1,024 expert jobs (512 per half), hence 2,048 `f16_out16` API calls (GU and Down each); candidate issues 512 jobs and 1,024 calls. Each call retains the same matrix dimensions but changes row (M): baseline GU ((160,1280,2560)) and Down ((160,2560,640)); candidate ((320,1280,2560)) and ((320,2560,640)). Candidate avoids the repeated GEMM weight read for those overlapping experts at source level, with cache effects unproved.

For the concentrated top-10 case, each expert has 8,192 rows in each piece and 16,384 per window. The candidate's 8,192 job cap splits each expert into two jobs (`moe_window_routes.hpp:20-21,91-96`): **20 jobs and 40 GEMM calls**, same as baseline. The shapes remain (M=8192); this extreme gets the dequant saving but no expert GEMM call or weight-reuse reduction.

A separate launch cost can negate the balanced GEMM benefit. Baseline's default non-compact fallback gathers all (T K=81{,}920) source rows into `Xs` once per piece (`prefill.cpp:2925-2927`), so two gather calls. Candidate unconditionally gathers once for every job (`moe_window.inc:135-146`): 512 calls for balanced routing, or 20 for the concentrated top-10 case. Total gathered FP16 payload is unchanged at (W K N 2=838{,}860{,}800) B (800 MiB), but candidate turns two large gathers into many small gathers. Baseline compact mode is explicitly opt-in and effective only under its fallback conditions (`prefill.cpp:680-694)); if enabled, baseline also gathers per expert per piece, and the comparison changes to 1,024 versus 512 calls in the balanced case and 20 versus 20 when concentrated. The candidate does not enable compact mode. Measure gather launch cost before treating the fewer GEMMs as a batching win.

Candidate repeats invariant range validation inside job loops: it validates the full `mixed` span once per job and the same `dq_gu[0]`/`dq_d[0]` spans once per active expert (`moe_window.inc:126-142`). Per full balanced window this is 3,090 span-validation calls: 18 fixed view/backing checks, 3 per active expert, and 3 per job. Hoisting the two dequant-scratch checks and the full mixed-span check would remove 1,536 + 511 = 2,047 repeated checks, leaving source/down per-job checks. These are host API/check calls, not proven synchronizations. Candidate also builds one combine job over (W\times K) and saves one combine launch versus baseline's two; both process the same number of rows. No source basis establishes that this wins on device.

## Main priorities and finite measurement

1. Keep the existing opt-in and 8K/RAM fallback. First record, per paired layer, both 8K `ne[e]` arrays, their overlap, job count, and gather/GU/Down call shapes. This tests the actual workload without borrowing aggregate histograms (the candidate rejects the old chunk census).
2. Before performance runs, hoist invariant span checks and route map buffers to pinned/mapped storage or an explicitly measured staging path; report slot and source bytes together. Add an explicit final-layer decision: compare the current two-copy path against the retained 8K route for the same final callback workload.
3. In one dedicated process per arm, run the same 16K+ prompt/config once with window off and once on, holding model/cache, chunk, placement, native16 and numerical configuration fixed. Capture one owned trace plus source counters for copy/kernel/GEMM submissions, requested bytes, per-job M and shapes, `cudaStreamSynchronize` call site counts, and host submit versus wait time. Collect device DRAM read/write and H2D/D2H bytes plus per-kernel time for attention-store copy, route exchange, gather, dequant, expert GEMM, combine and HC write. That separates launch, transfer, and compute limits instead of inferring DRAM cost from event intervals. Do not use overlapping/non-exclusive event totals as component timing.
4. After correctness and the trace, take three paired wall-time samples for the actual long prompt with exclusive ownership. Keep GPU-only pair, RAM fallback, and final callback results separate; include actual route-count distributions and source/manifest/binary/config receipts. Do not synthesize a speed claim from the balanced or `ne == W` arithmetic examples.

## Decision

Source proves fewer route-exchange submissions, one-time dequantization per overlapping expert, and fewer expert GEMM calls only where per-expert window rows stay below the job split threshold. It does **not** prove reduced transfer bytes, fewer explicit syncs on intermediate layers, fewer gather launches in default mode, or a device speedup. The default per-job gather count, pageable route arrays, repeated span validation, and final-layer extra copies/syncs are concrete cost risks to settle before adoption. The candidate remains unqualified for codegen/link, GPU execution, queue/DMA behavior, fit, physical context, RESTORE, and speed.
