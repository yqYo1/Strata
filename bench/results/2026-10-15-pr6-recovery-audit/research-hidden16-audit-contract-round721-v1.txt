# R721 — production boundary-audit contract for 16-bit hidden storage

Date: 2026-10-15 JST. Source reviewed at `5942f1853f006b0df45e15fd4f1c60bc37b7b3b3`. Read-only source/evidence audit. The Main native GPU run remains pinned to its own source; this report does not inspect or affect it. No product edits, build, test, GPU/model run, process/service action, Git mutation, XeStrata source access, or private B path. This report is the only new artifact.

## Finding

The live production boundary audit correctly validates the current FP16 pack/store/restore mechanics for sampled rows, including mixed GPU-prefix and host-tail placement when the selection straddles that boundary. It does not qualify FP16 quality against an FP32 control. Current BF16 is rejected before the production path; the audit itself is also not dtype-generic. The present FP16 production path is admitted only when the phase-audit environment option is off: that audit explicitly requires FP32.

This is chiefly a measurement-contract limit, not evidence of a current FP16 data-path defect. No natural-long-input FP16 store/restore quality fixture has been run. Existing small and long receipts establish narrower claims described below.

## Admission and typed path

At this revision, `LayerMajorResidualDtype` and its parser in `include/strata/prefill/layer_major_plan.hpp` represent FP32 and FP16; BF16 text is rejected. In `src/prefill/layer_major.inc`, setting `STRATA_PREFILL_PHASE_AUDIT` with a non-FP32 residual dtype is rejected. This is an explicit diagnostic restriction, not a general FP16 production-admission ban: the separate boundary audit receives `plan.dtype == fp16` and supports the FP16 path.

The boundary audit constructor receives a boolean `half`, rather than a precision enum. Its current FP16 caller is correct. This interface cannot safely represent BF16: passing true would apply FP16 conversion/packed-word semantics and label the storage FP16. BF16 therefore needs a typed audit interface and format-specific compare/restore rules before admission; widening only the parser or planner would create a misreported or miscompared audit path. Current parser rejection fails closed.

## Store, restore, and placement audit

`layer_major.inc` plans dtype and placement, allocates a shared staging buffer for the FP16 host-tail case, and installs the producer callback. For each non-final chunk, the callback snapshots selected source rows, converts FP32 `m.R` to FP16, and writes either the GPU span or a packed host-tail staging span. The host-tail packed bytes are copied device-to-host and the queue is drained before the store audit reads the host destination. In `prefill.cpp`, the next layer reads its span; host rows are staged host-to-device, and `from_f16` restores FP32 `m.R` before the input audit. The final callback remains FP32.

For each selected row, `LayerMajorBoundaryAudit` records the source FP32 output and retains its expected typed round-trip. It checks actual stored FP16 packed bytes against the expected packed representation, then checks the next-layer restored FP32 input against that expected round-trip. The store and input comparisons are bitwise/equality checks for the represented sample, and records identify GPU versus RAM placement. Thus a selection containing rows on both sides of `gpu_rows` exercises both arms. The default sparse row list does not guarantee it straddles every possible prefix boundary; configure explicit boundary rows from the run's actual `gpu_rows` and chunk geometry.

The audit writes raw selected FP32 source rows at every layer, usable for offline cross-run layer/position comparisons. Its FNV-style digest is a locator, not a substitute for those bytes. Per-run exact comparisons prove that observed bytes match that run's expected conversion and restoration. They do not compare candidate outputs to a paired FP32 run, estimate quality loss, or establish full-row coverage. Source records with no expected value also are not a candidate-vs-reference numeric metric.

## What the extant fixtures establish

`boundary-audit-small.ja.md` records separate FP32 audit-off, FP32 audit-on, and FP16 audit-on runs on a 513-token input, 512 batched rows, chunk sizes 257+255. For both audited dtypes, sampled output/store/input records across 48 layers passed the within-run comparisons; the sampled/first logits and generated IDs matched the same-dtype old control. This is a small mechanics and diagnostic-coverage result, not an FP16-vs-FP32 quality result, and does not qualify long-context or full physical 262,144 context behavior.

`boundary-audit-long-pair.ja.md` records 34,603 input tokens / 34,602 batched rows, chunk 4096, with FP32 residual storage in both fixed-4096 and auto-24576 placement arms. Each run's sampled source/store/input checks passed. The placement-pair comparison first diverged in selected raw source output at layer 26, row 24575; auto's numerical FAIL remains. These are FP32 placement results, not an FP16 mixed-placement fixture.

R706 (`research-hidden16-quality-round706-v1.txt`) remains the relevant quality contract. It already distinguishes the small synthetic FP16 mechanics result, a one-conversion post-hoc screen, and 19 correlated selected-logit samples from a dense all-token quality evaluation. The NLL harness in that report is unapplied/unrun. R699 (`research-prefill-fp16-partial-capacity-round699-v1.txt`) covers capacity/placement planning, not quality qualification. No existing fixture combines natural long input, actual FP16 storage, fixed GPU prefix plus host tail, and paired FP32 candidate-quality consumers. The existing long raw-row consumer can help localize cross-run drift, but it needs paired same-token runs and a declared comparison recipe.

## Defect, unsupported harness, and unverified claims

- **Current source defect:** none found in the reviewed FP16 conversion/store/restore boundary contract. This source audit cannot establish race freedom or prove all rows/layers beyond recorded coverage.
- **Unsupported today:** BF16 planner/parser/storage/audit path; phase audit with reduced-precision storage; a dense all-token NLL consumer (the existing selected-logits callback samples at most 64 positions).
- **Unverified:** natural-input FP16 task/quality impact; repeated FP32 baseline spread; FP16 quality for actual long partial GPU-prefix/host-tail storage; full 262,144-context correctness/RESTORE. The synthetic and sparse reports do not close these gaps.
- **Future integration hazard:** adding BF16 admission without replacing the audit's boolean format selector and adding BF16 packing/restoration would make the audit's type label and expected bytes wrong. Do not infer BF16 readiness from the generic two-byte planner capacity.

## Minimum boundary for the next evaluation

Keep today's FP16 mechanics audit and its fail-closed FP32 phase-audit restriction intact while adding a separate quality fixture. Use the exact natural 34,603-token input and same chunk, fixed GPU-prefix row count, host tail, binary/configuration, and output consumer across repeated FP32 controls and FP16 candidate processes. Explicitly select rows before, at, and after the actual placement boundary for audit coverage. Bind the external recipe and token IDs to each receipt. Consume all 34,602 teacher-forced predictions for NLL; use a small predeclared raw residual/logit sample only for localization. Compare candidate effects against FP32 repeatability, treating the 19 selected positions as correlated diagnostics, not independent samples. Preserve FP32 as the reference and do not admit BF16 until its typed planner, pack/restore route, audit semantics, and fixture are separately implemented and reviewed.
