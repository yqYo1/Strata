## Status and what the pending profile can establish

The canonical1/profile1 FP32/R_GPU=32768/Direct1 profile named by Main is not present in the audited evidence yet. This report therefore makes no MoE bottleneck, speed, or adoption claim. Layer-major stores/uploads one layer of 512 experts, drains that upload, then processes chunks; at the target settings this is a layer loop over 48 layers and C=8192 chunks. The fact that experts are resident removes per-routed-expert H2D streaming from this route; it does not eliminate host route readback/grouping or per-expert command submission.

A coarse `moe` wall bucket can establish whether the whole MoE region merits finer attribution, but by itself cannot distinguish host-side route grouping/submission, native dequant kernels, GEMM service, queue gaps, shared-expert work, or combine. Only pursue candidates below if the actual profile and a bounded follow-up distinguish the relevant cost. Record whole-prefill wall as the acceptance measure; phase markers alone are not exclusive service time.

## Current own-source execution granularity

- Layer-major path is explicitly restricted to full-model single-GPU native-source compact-FP16, `STRATA_PREFILL_MMQ=0`, same queue, and 48-layer/Qwen geometry. It uploads all `NE=512` layer blobs and drains before publishing their residency map: `src/prefill/layer_major.inc:316-358`.
- Router executes for each chunk, then the ordinary MoE branch copies routed IDs to host and synchronizes the compute queue before forming per-expert counts, prefix offsets, source rows and slots. Experts with nonzero counts are ordered by expert ID: `src/prefill/prefill.cpp:2450-2453,2546-2634`. This is a real host synchronization and CPU work boundary even though all experts are resident. Grouping preserves route-entry order within each expert and combines by global offset `o0`; do not reorder outputs or change the sum path casually.
- For each routed expert, `compute` uses two rotating dequant slots (`q=j%DQ`, DQ=2), expands native GU/up and Down separately to FP16, gathers that expert's `ne` input rows to compact row zero, submits GU as `(M=ne,N=1280,K=2560,ld=1280)`, applies interleaved SwiGLU, then submits Down `(M=ne,N=2560,K=640,ld=2560)` writing to `Dm+o0*2560`: `src/prefill/prefill.cpp:2995-3029`. `ne<=T`; current C=8192 bounds each compact row count to the chunk, not to all `T*10` routes.
- `Gemm::f16` is one row-major oneMKL `gemm` call per projection. On this non-null in-order queue, `finish` does not host-wait; it returns after enqueue, while queue order carries dequant -> GEMM -> post-op -> Down: `src/prefill/sycl/gemm.cpp:18-30,96-100`; `include/strata/sycl/launch.hpp:44-63`. Thus 2 GEMM submissions plus dequant/gather/postop submissions per expert are possible source-level granularity; this is not a count or timing from the pending profile.
- The layer-major admission's explicit same-queue requirement means a proposed auxiliary queue needs dependency/lifetime proof and whole-path evidence. Do not infer overlap from async API names.

## Conditional implementation candidates

### A. Narrow grouped oneMKL Down GEMM for repeated tiny exact shapes

This is the least invasive submission-count candidate, and R575 already scoped substantially the same idea. Do not restart it broadly. Consider it only if the current run's actual routed-call census shows enough *same-layer, same-chunk, same-ne* groups and a separate measured host-submit component shows submission cost exposed on the critical path. Candidate site is current `m.gemm.f16(...Hh..., ...dq_d[q]..., Dm+o0*N...)` at `prefill.cpp:3024-3029`, with a new current wrapper beside `gemm.cpp:96-100`.

Use the documented USM pointer-array `oneapi::mkl::blas::row_major::gemm_batch` group API for one exact shape per call (e.g. small `ne` bucket, with a minimum group size such as four); its group members may have independent A/B/C pointers and each output pointer must preserve its existing `o0`. Official oneMKL DPC++ 2026.0 docs describe the USM Group API and pointer arrays, plus `sycl::half` inputs with FP32 output: https://www.intel.com/content/www/us/en/docs/onemkl/developer-reference-dpcpp/2026-0/gemm-batch.html (published 2026-04-28; group API and datatype contract). The queue and every pointer-array / matrix owner must remain valid through the returned event. Keep per-expert fallback.

Hard constraints: each Down weight expands to `2560*640*2 = 3,276,800` bytes. Existing `dq_d[2]` cannot retain four expert matrices, and each expert's Hh is produced only after its own GU and SwiGLU. A real implementation must account for bounded additional device storage or a safe dequant/compute schedule, host pointer metadata, output offsets, batch event lifetime, and C=8192 admission. Do not hide those costs in existing scratch. This only reduces API calls; it does not reduce GEMM FLOPs or the bulk of dequant work.

Reject if exact-shape group frequency is low; if extra storage breaks C=8192 admission or lowers the feasible residual prefix; if dequant/metadata/retention consumes submit savings; if output parity/fault checks fail; or if repeated whole-prefill wall does not improve beyond run variation. R575 records the previous broad census at 34,602 rows with `ne<=16` representing 55.13% of calls but 1.386% of rows, and a synthetic R496 four-way Down case about 2.85% faster while most two-way cases regressed. These are historical data from another request/configuration, not current frequency or speed evidence. Prior report SHA256: `e83911d2a588225554069488c4f036e62b263e93f0f1535e2f62e3d9c46c7a61`.

### B. Own-source IQ3_S direct grouped/fused GPU path (larger research candidate)

If the coarse/follow-up evidence says GPU dequant/materialized-weight traffic or repeated per-expert launches dominate, investigate a Strata-authored specialized path for the actual IQ3_S expert format. Reuse only the fork's public local data/layout contract and its own IQ dequant reference. Candidate design: build a compact per-layer-chunk descriptor from the already-authoritative IDs/counts/offsets (expert slot/blob pointer, `ne`, source-row range, output offset), then launch a grouped device kernel over active experts and row tiles. The kernel can decode packed IQ3_S weights as it consumes them and compute GU/up, SwiGLU, and Down into each expert's existing global output span, avoiding full FP16 weight materialization and reducing host-to-runtime launch count. It could first be split into direct-dequant GU/GEMM and direct-dequant Down kernels if a single fused implementation would exceed resource or numerical limits.

This is an algorithm proposal, not a claim that a custom kernel beats oneMKL. ABI/layout constraints to resolve before source work: exact IQ3_S block and scale decoding/row strides for both GU and Down; orientation and dimensions above; `WeightLayout` layer offsets; per-expert count/offset and source-row order; compact `Xs` row-zero semantics; independent `Dm + o0*N` outputs; FP16 materialization rounding currently consumed by FP16 GEMM; accumulation order/dtype; and same-queue event ownership through final combine. Resident cache slot pointers are valid only for the active layer. Preserve the current route as a fallback and keep numerical, route-ID/logit, fault, C=8192 admission and whole-prefill gates separate.

Do not start from an external engine implementation. No non-upstream implementation source has been used here. Any later implementation-reference use first needs a provenance/license check; a paper or official API establishes an algorithm/API, not reusable code. This candidate is justified only if attribution identifies packed dequant or launch-count cost; reject it if source-level cost is small, if existing FP16/oneMKL remains faster in matched whole-path trials, if numerical/task quality or route decisions fail, or if resource use defeats the C=8192 workload.

## Attribution required before selecting either candidate

Use the pending coarse profile first. If MoE is not a material part of end-to-end wall, stop. If it is, add a bounded aggregate observer or qualified device activity collection that separates: host route-ID copy/sync + CPU grouping duration; per-chunk expert count and `ne` histogram; dequant and gather command counts/host-submit duration; GU/Down oneMKL call counts and host-submit duration by role/shape bin; aggregate queue/device activity for those regions; shared expert and combine; and whole-prefill wall. No per-expert host waits, event queries, large logs, or timed MKL verbose output; these would perturb the path. A host submit timer is not GPU service, and the current queue-marker intervals can include host gaps. Retain individual process samples and correctness/fault status under the existing artifact policy.
