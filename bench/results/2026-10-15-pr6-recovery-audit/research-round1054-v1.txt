## Exact API and storage contract

Deployed entry is `prefix_batch_impl<33,false,false>` (`Cells=32`, workgroup 128, subgroup 16). One typed tile is reused as K `[d][cell]`, then V `[cell][d]`; math, BF16 bits, score stride, softmax and FP32 state do not change. Barriers publish `rows`, K, scores/probabilities, V and PV in order. Padding is outside the corresponding loads; preserve barriers and object reuse.

Pinned experimental oneAPI docs at Intel LLVM revision `fbccb466cc122c294a6c746dcf0d37e45ff70f3c` define row-major stride in elements and BMG constraints: `stride*sizeof(T)` multiple of 8, at most `2^24` bytes, pointer 4-byte aligned. With 2-byte BFloat, pitch must be a multiple of four elements, at least row width, at most 8,388,608 elements; each pointer offset must be even. This code uses direct pointers, not the offset overload.

For K pitch 36, producer destination is `kv[36*d + cell]`, with `0<=d<256`, `0<=cell<32`; QK consumer calls use starts `kv+36*d0+c0`, `d0=0,16,...,240`, `c0 in {0,16}`, stride 36. The producer's contiguous `i=tid+n*128`, `d=i/32`, `cell=i%32` mapping still covers each logical element once. For each 16x16 load rectangle, its exclusive maximum linear offset is `(d0+15)*36+(c0+15)+1`; across all loads the maximum is `255*36+31+1 = 9,212` BF16 elements (last used index 9,211). Row padding is not part of the logical matrix.

For V pitch 260, producer destination is `kv[260*cell+d]`, with the same logical bounds; PV consumer starts are `kv+260*c0+d0`, `c0 in {0,16}`, `d0=dim_base+16*j` for `dim_base in {0,64,128,192}`, `j=0..3`, stride 260. The maximum 16x16 rectangle ends exclusively at `31*260+255+1 = 8,316` BF16 elements (last index 8,315). Both pitches satisfy the extension: K row bytes 72, V row bytes 520; both are multiples of 8 and far below `2^24`. With the existing `alignas(4)` typed base, `MatrixTile.values` at offset zero and all listed starts even BF16 indices, every passed pointer is 4-byte aligned. No store-to-matrix API is used; producer destinations are ordinary element assignments.

The present 8,192-element object is too small. One shared typed array of `max(256*36,32*260)=9,216` BF16s (18,432 bytes) covers both; maxima 9,211 (K) and 8,315 (V) fit. Preserve `MatrixTile<N>` standard-layout/trivial/alignas(4), values offset 0 and `sizeof==2*N`, changing its extent. SYCL local accessors create implicit-lifetime objects with indeterminate values; each producer writes every consumed element before its barrier. Padding need not be initialized under the logical matrix API contract; physical transaction width is unmeasured.

Recompute payload: score-stride-33 rises 28,224→30,272 bytes (+2,048); existing `local_mem_size >= payload+4096` admission becomes 34,368 (32-stride: 34,304). This source threshold does not prove compiled allocation/residency. K/V reuse one object; do not sum two tiles.

Coherent 40/264 alternatives have 80/528-byte rows, need 10,240 elements (20,480 bytes), and score-stride-33 payload/admission 32,320/36,416 bytes. Minimum legal pitches are 32/256; 34/258 fail (68/516 bytes). Legal pitch does not legalize odd offsets. Do not use `IGC_JointMatrixLoadStoreOpt=1`; docs describe only a slower fallback, not this design's correctness contract.

## What the pitch may change; what it does not prove

Padding changes row-start modulus (72/520-byte rows versus 64/512) and might alter lowering, SLM conflicts or address work. No B570 bank map, native load shape, conflict/cache counter or occupancy is measured. Current pitches may already load efficiently; padding may add address work without removing conflicts; +2 KiB may reduce active workgroups at a resource threshold. 40/264 increases that risk. Prior timing does not identify the mechanism.

## Smallest useful Main-owned experiment

1. Preserve `<33,false,false>`, compiler/runtime, launch and inputs; compare 32/256 against one immutable 36/260 selector. Derive every producer/consumer address from its pitch; prove alignment, offsets, extent and recomputed admission before execution. Try 40/264 only if 36/260 passes correctness and admission.
2. Run existing small fault/guard cases (duplicates, invalid/tail rows, empty/partial tiles, K-to-V reuse) and bit-compare with baseline. Then repeat the 8,192-query/50,331,648-output component, six rotated samples per shape/arm, with concentrated and scattered rows. Preserve physical-context and known strict numerical-failure gates; this address change does not resolve them. Bounds/domain/fault/bit failure stops the candidate.
3. A repeatable component win only then warrants paired real-model long-prefill samples (same model/tokens/cache/warm/environment/runtime) at 32K or longer. No component-to-model extrapolation or default change; physical-262144, RESTORE and quality gates remain Main's.
