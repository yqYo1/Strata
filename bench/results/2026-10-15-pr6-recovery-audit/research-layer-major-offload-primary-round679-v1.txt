# Primary research: layerwise prefill KV offload for Strata's hybrid model (R679)

Date: 2026-10-15 JST. External primary-source and author-source review, read-only. No source/proposal changes, tests, builds, compiler, GPU, process, environment mutation, private-B inspection, Git mutation, or cleanup. Only this report was written. The sources establish design precedents and their boundaries; they do not establish Strata admission, correctness, speed, or adoption.

## Current capacity case and question

The current capacity plan uses the real B570's 10,666,115,072 B (9.9336 GiB) total and assumes decode-only allocations are absent during long prefill. The model has 48 layers: 12 QSA layers and 36 GDN layers. At 262,144 tokens, the existing FP16 residual-storage option costs 5 GiB for the full hyperconnection-width hidden bank; current operator and recurrent work remain FP32. Full-resident K8V8 QSA state costs 3.5342 GiB including indexer/page/RoPE state. The maximum single-layer weight bank is 1.3413 GiB, and the explicit Prefill workspace is 1.2908 GiB at C=4,096 or 2.4184 GiB at C=8,192. The capacity metadata has a distinct one-active-QSA full-context owner of 377,753,104 B, with remaining KV+hidden budgets of 1,421,781,232 B (C4) and 210,988,016 B (C8) after reserving the full FP16 hidden bank. These are checked arithmetic under the plan's stated reserves, not an allocation result. (`prefill-capacity-plan.ja.md`; `prefill-capacity-metadata-v2.json`, cases `layout=one_layer_bank`.)

The question is whether prefill can keep all hidden rows on GPU while only the currently processed QSA layer's full-range KV occupies its reusable device slot, writing completed QSA state to host RAM once per QSA layer. This trades a one-time per-layer KV spill for avoiding repeated hidden-bank store/restore between all 47 inter-layer boundaries. The hybrid layout matters: the 36 GDN layers have recurrent state rather than QSA KV, and their state/order remain separate GPU/session owners. The capacity plan's all-state K8V8 sum must not be treated as an active-buffer size.

For traffic scale, K8V8 code plus scales are 1,056 B per token per QSA layer. At 262,144 tokens, one QSA layer's K/V payload is 276,824,064 B (0.2578 GiB); across all 12 QSA layers it is 3,321,888,768 B (3.09375 GiB) of one-way D2H writes. The complete all-layer QSA state in the plan is 3,794,839,744 B (3.5342 GiB), including indexer/page/RoPE overhead. The exact traffic depends on which of those auxiliary structures the design retains, moves, or rebuilds; the 3.09375 GiB figure is K/V codes and scales only.

If all 5 GiB of A16 hidden storage were instead host-backed and copied at each of 47 boundaries, its logical store+restore volume would be `5 GiB * 47 * 2 = 470 GiB` (504,658,657,280 B). The plan's current resident-hidden alternative avoids that transfer. Separately, the existing layer-major schedule loads each layer's 512 packed expert blobs once: `native_experts.txt` reports 50,292,326,400 B across 48 layers (46.84 GiB) of packed expert source, with 1.3413 GiB the largest active layer bank including canonical/native dense tensors. These byte totals describe distinct paths and lifetimes. They do not predict elapsed time: transfer contiguity, queue waits, link throughput, attention compute and runtime overhead still matter. R571/R577 already show why residual byte totals and component bandwidth do not establish end-to-end benefit; R621/R622 already cover deferred-MoE scheduling and its larger retention burden, so that proposal is not repeated here.

## Closest direct precedent: layerwise KV buffer reuse

The most relevant source is the vLLM team's [RFC for layerwise KV cache offload](https://github.com/vllm-project/vllm/issues/33398), authored by vLLM contributors in 2026. It proposes assigning one physical KV tensor to multiple layers: load a layer's prior KV before its forward, compute/update it, offload it, then reuse the slot for the next layer. The RFC explicitly says one buffer minimizes memory but serializes load/store and compute; multiple buffers permit overlap only if transfer time is covered by another layer's compute. It recommends estimating per-layer compute and KV load time before deciding buffer count. This is a close architectural match for QSA layers, but its RFC discussion is not a Strata implementation or B570 performance result.

The follow-on [vLLM Ascend design document](https://docs.vllm.ai/projects/ascend/en/v0.30.0rc1/developer_guide/Design_Documents/layerwise_and_sparse_kv_cache_offloading.html) describes a concrete layerwise prefill path: logical layers map to fewer physical device KV buffers, a host KV pool holds the full history, completed layer/block ranges are saved in larger transfers, and a physical slot is reused only after its save and every reader completes. It keeps indexer caches in device memory and treats sparse decode as a separate path with hot top-k buffers. That gives two transferable principles: make the reusable physical buffer explicit and gate reuse on completion for that slot; keep full-history KV backing separate from per-layer scratch. Its backend uses Ascend NPU, Memcache and (in joint mode) MemFabric, and its decode path targets sparse-attention GLM-style models. Those mechanisms and reported scale do not transfer directly to Arc SYCL.

The vLLM maintainers' later [layerwise-and-sparse KV RFC](https://github.com/vllm-project/vllm/issues/48203) makes the boundary clearer. Its prefill part uses two to four reusable KV buffers and proposes layer/block transfer after attention; its sparse decode part is distinct, retains indexer data and fetches selected KV rows into a hot buffer. The RFC uses GLM-5.2/DeepSeek-family sparse attention, including top-k history. It is an open design thread with model-specific implementation work, not evidence that Strata's hybrid QSA/GDN path already supports this layout. The Ascend docs note their own hybrid KV layouts are unsupported. Here, Strata has 12 QSA layers plus 36 GDN recurrence layers, and the existing SYCL QSA state/indexer/page-table/RoPE geometry has to be retained correctly. An ordinary dense-transformer cache pool cannot represent or retire the GDN state.

## Related systems and what they do establish

**FlexGen/FlexLLMGen.** The authors' [FlexGen paper](https://arxiv.org/abs/2303.06865) and [project README/code](https://github.com/FMInference/FlexGen) formulate placement of weights, activations and attention KV across GPU, CPU and disk and use a block schedule to reuse weights and overlap I/O with computation. The project explicitly targets throughput-oriented batched generation, and its examples expose separate offload percentages for parameters, attention cache and hidden states. This supports treating placement and lifetime as a joint schedule rather than as a single allocation. Its experiments are primarily dense OPT with large batch sizes, 4-bit compression and an NVIDIA T4/large DRAM/SSD setting; it neither validates Strata's QSA layer-only staging nor predicts single-request prefill on B570. The useful lesson is scheduling/placement discipline, not its throughput numbers or compression accuracy.

**DeepSpeed ZeRO-Inference.** The DeepSpeed team's [ZeRO-Inference design write-up](https://www.deepspeed.ai/2022/09/09/zero-inference.html) provides evidence for layerwise weight fetch/prefetch from CPU/NVMe and for modeling transfer/compute overlap. Its own result says CPU weight prefetch did not improve its tested short decode sequences, while NVMe prefetch helped by overlapping NVMe-to-CPU and CPU-to-GPU transfers. The official [KV-offload model support notes](https://github.com/deepspeedai/DeepSpeedExamples/blob/master/inference/huggingface/zero_inference/model-support.md) describe a CPU KV buffer and copying a layer's prompt KV after projection, potentially on another GPU stream while attention work continues. That is a concrete ownership/queue pattern to study. It modifies selected Hugging Face dense transformer models; its CPU/GPU attention choice and streams do not establish correctness for Strata's SYCL QSA, in-order queue, page/indexer state or GDN recurrence. R577 separately documents Strata's current same-queue ordering and copy-lifetime constraints.

**vLLM connector author's transfer study.** Or Ozeri and Danny Harnik (vLLM Team at IBM Research) wrote an [author blog on KV offload transfers](https://vllm-project.github.io/2026/01/08/kv-offloading-connector.html). It explains that transfer fragmentation reduces effective block size, that a contiguous all-layer block layout improved DMA throughput in their connector, and that custom GPU-copy kernels can interfere with compute. Crucially, the post states that vLLM's connector was not optimized for hybrid models at publication, and its measurements use NVIDIA H100/CUDA. The transferable point is to measure exact copy granularity and interference and retain distinct completion ownership; no reported bandwidth should be applied to B570.

I screened Intel's [llm-scaler vLLM README](https://github.com/intel/llm-scaler/blob/main/vllm/README.md). It describes an Intel multi-GPU vLLM distribution, prefix caching, LMCache and disaggregated transfer examples, but I found no concrete per-layer, one-active-QSA prefill KV pool there. It is therefore not evidence for this design. Generic vLLM prefix-cache offload is also a different lifetime: it saves completed requests for reuse; layerwise prefill offload reduces the live KV footprint of the request currently being computed.

## What can transfer, and what remains specific

Transferable design ideas are narrow: (1) make host backing and a small, explicit number of reusable device KV slots separate owners; (2) record completion per physical slot and do not overwrite until D2H readers/writers and host publication finish; (3) consider two slots only if a measured per-layer compute window can hide the copy and the extra slot fits the actual budget; (4) batch layer KV into large contiguous ranges and measure the actual K/V plus scale layout; (5) keep request-level “KV saved” completion separate from the event that releases a device slot.

Strata-specific obligations remain: preserve ascending token order inside each QSA layer and each GDN layer; keep all 36 GDN recurrence/convolution states and PLE history correct; preserve QSA K/V, indexer pooled rows, page tables, shared RoPE and K8 scale layout; commit all 12 QSA host-backed states before decode handoff; maintain the 5 GiB FP16 boundary-hidden bank on device with existing FP32 operators; retain a host owner for every saved layer until decode restoration/consumption is resolved. The 262,144 context check must exercise the actual physical final row, not just allocate a logical maximum. A correct isolated prefill allocation does not prove the later decoder can restore/consume the saved state. The K8V4 capacity row remains hypothetical and outside the demonstrated configured SYCL append/gather route.

## Actionable architecture candidate

The closest small candidate is an opt-in **one-slot QSA KV spill** layered onto the existing ascending layer-major pass. Keep the full FP16 residual bank in its planned GPU placement. At each of the 12 QSA layer boundaries, after the final chunk and a checked queue completion, copy that layer's complete K/V codes and scales into its permanent host backing, publish completion, then reuse the same device KV slot for the next QSA layer. Keep indexer/page/RoPE storage either in a separately budgeted persistent GPU owner or include its own exact save/restore path; do not silently discard it. Leave GDN state untouched. Defer any two-slot transfer overlap until a one-slot implementation's transfer and compute spans and full-context budget are measured. At C=8,192, the capacity plan leaves only 210,988,016 B after its one-active-QSA reservation; the 377,753,104 B second full-context QSA slot exceeds that remainder even before any changed allocator overhead, so a second slot is not within the current plan.

The first review gates should be: source map each active QSA/GDN owner and queue consumer; validate a lossless K/V/indexer/page-table round trip for every QSA layer at short, chunk-boundary and 262,144 physical positions; compare logits and residual fingerprints against all-resident K8V8; inject copy failure/cancellation and prove no slot or host backing is reused early; check aggregate available RAM and the project's reserve before mutating session state; and define how decoder state is restored before declaring a completed request usable. Only then is a clean matched prefill-time comparison meaningful. These checks are proposals for a later gate; none was run here.
