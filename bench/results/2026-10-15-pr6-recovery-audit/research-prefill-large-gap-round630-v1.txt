# R630 — 長文prefill差の上位候補と順序

2026-10-15 JST。PR #6監査/R560以降の報告と、現行root SYCL sourceを読み直した。新規計測、build/test/GPU/process/Git操作はしていない。進行中official `bench.sh` full OFF runとそのraw artifactには触れていない。目的は64K実入力で1,000 tok/s（約65.5秒）の見込みを断言することではなく、残る時間差に関係し得る二点を、既存の安全・数値・長文gateで試す順に絞ること。

## 結論

PR #6の645.85 tok/s (32,768 input, 8,192 chunk, context 65,538, K8/V8 fully resident, all residuals GPU-resident, warm PLE, no MTP, one output) と、現行32K正式runの約172秒は同条件比較ではない。後者は約186 tok/sに相当するが、source resolver、設定、workload/timer、runtime safety environmentが異なる。645.85との比率から原因や64K速度を導けない。PR #6でも1,000 tok/sは達成していない。64Kで1,000 tok/sを狙うなら、まずshape・resident state・callback込みの同条件baselineが必要。

上位候補は次の二件。

1. **現行rootでchunk 4,096対8,192を、同じsafe configで分離比較する。** PR #6は8,192、現在のformal設定は4,096という明瞭な差があり、64Kではchunk数16対8となる。per-token attention/indexer/GDN/MoE算術を減らす変更ではなく、chunk境界ごとのsetup/dispatchとQSA history restageを減らす仮説である。8,192はper-chunk scratchを倍にするため、residual GPU prefix・expert/cache admissionが変わらないよう実値を固定・記録する。
2. **QSA streamed mode-1の履歴KV restageを、連続chunk内では一度だけにできるか検証する。** 現行`run_impl`は各QSA layer/chunkで、現在chunkより前の全pageをhost backingからfull-logical-range stage poolへ戻す。各QSA layerには専用stage poolがあり、同じprompt内では直前chunkまでのpageが既にそこにあり、current appendも同じpoolへ書く。fresh `pos0=0`の連続実行では、前段stageを次chunkで再利用して全prefix再コピーを省ける可能性がある。現行の`session_zero`、RESTORE/checkpoint、position gap、partial failure/cancel、request再利用でstage内容が古くならない明示的なvalid-prefix/generation gateが必要。まずsource/lifetimeレビューとexisting page/residual/checkpoint gatesを通し、default-offの狭いfresh-sequence比較だけを検討する。

GDNの新規候補やMoE dense projection orientation/kernel案はここでは追加しない。GDNの既報current-root tuned runはkernel-level改善に対しCLI wallで約0.33–0.61%だった。Current `Gemm::f16` row-majorと歴史donorのcolumn-majorは同じ論理`Y=XWᵀ`を記述し、R566 orientation probeはsynthetic per-call差が小さく、model-qualifiedでない。時間差の主因として選ぶ根拠が足りない。

## Candidate 1: chunk length at fixed current config

Try only after the current full OFF arm closes, with one current-root binary and identical actual token IDs, model/profile/cache, max-context 262,144, INT8 KV/resident policy, layer-major mode, expert count, MTP4, warm PLE, strict-safe environment, compiler/runtime/driver, and output/timer protocol. Compare 4,096 vs 8,192 chunks on the same 32K and then independent 64K input; make each arm a fresh process and keep `STRATA_*` process environment immutable after exec.

Useful exact geometry, not a speed claim:

- 32,768 tokens: 8 chunks at 4,096 vs 4 at 8,192. 64K: 16 vs 8. This halves chunk boundaries; it does not halve per-token QSA, GDN, dense projection or MoE arithmetic.
- One FP32 residual chunk (`D=10,240`) is `T*D*4`: 4,096 → 167,772,160 B (160 MiB); 8,192 → 335,544,320 B (320 MiB). 64K full residual storage is 2,684,354,560 B (2.5 GiB); all-resident capacity requires actual admission, not arithmetic alone.
- Current layer-major planner subtracts a 536,870,912 B GPU headroom and a 8 GiB RAM headroom and checks a new 512-layer-expert temporary cache. Record actual `residual_gpu_rows`, host bytes, cache bytes, free/total memory and chunk buffers. If chunk doubling changes residual prefix or triggers allocation/cache fallback, it is no longer a chunk-only arm.

Use existing checks: exact output/selected-logit/state and QSA/GDN/PLE parity at tails; current host-stage and MTP callback lifetime; full physical 262,144-cell boundary/RESTORE path; then clean official `bench.sh` per-request samples. Do not use phase-audit/profiler timings as product throughput. A current CH64 QSA attention candidate exists in R564; this round does not reintroduce it as a new candidate.

## Candidate 2: avoid repeating QSA host-to-stage copies

Actual root path is `src/prefill/prefill.cpp` (`st.kv_mode==1` branch around current QSA append/attention), `src/prefill/sycl/*`, and `src/kernels/sycl/kv_stream.cpp`, not the historical overlay. `src/core/layer.cpp` selects a mode-1 resident slot count from `--kv-resident`; full logical pages remain separately allocated in host backing. `Prefill::take_stage` allocates a prompt stage pool for `n_pages` (the full logical range), not only the resident slot count. Current `run_impl` calls `kv_stage_from_host` for all prior pages on each chunk before append/current attention. The per-layer QSA history and identity stage pool must retain the current topological order; GDN recurrence and QSA indexer/KV state stay unchanged.

For actual SYCL INT8 shape, `kv_block_bytes()` is the sum of two K/V heads × page size 4 × (256-byte K + 256-byte V + 8 bytes of FP16 scales per head) = 4,160 B/page, or 1,040 logical bytes/cell. Current model has 12 QSA layers. The sum of prior chunk-start cells for a fresh prefix is `C * m*(m-1)/2` (all tested starts align to page size 4); multiplying by 1,040 B × 12 gives this source-level logical H2D payload through `kv_stage_from_host` alone:

| Input | chunk | chunks | prior cells replayed across QSA-layer passes | logical stage payload |
| ---: | ---: | ---: | ---: | ---: |
| 32,768 | 4,096 | 8 | 114,688 | 1,431,306,240 B (~1.33 GiB) |
| 65,536 | 4,096 | 16 | 491,520 | 6,134,169,600 B (~5.71 GiB) |
| 65,536 | 8,192 | 8 | 229,376 | 2,862,612,480 B (~2.67 GiB) |

This excludes current-chunk append writes, route/query/indexer traffic, allocator padding and physical transaction effects. It is neither measured DRAM traffic nor wall time. For fresh `pos0=0` the previous-history stage is initially empty; current append writes each new page to host backing and stage, so the next consecutive chunk appears to need no rewrite of earlier pages. For `pos0>0` or RESTORE, earlier pages must be restored once from host, and reuse must be invalidated when session/host generation changes. `stage` must be per QSA owner; a device pool for one layer cannot be reused as another layer's history. All host-copy and current append/write/read work must remain ordered on the production in-order queue, and no stage storage may be overwritten before QSA attention has consumed it.

The current batch census/profiler summary's M2D 29.275 s and D2M 12.633 s are sums of profiler operation durations across startup, prefill and decode capture; event intervals can overlap and do not isolate this stage copy. R601's `iq_dequant_gu_f16` 22.413 s, generic `dequant` 12.073 s, and 44.066 s prompt-attention kernel bucket are likewise profiler service sums, not exclusive wall components. They signal areas to examine but cannot be added, subtracted from the 172 s clean sample, or used to predict transfer savings. Existing phase-QSA intervals (~49.455 s in a diagnostic run) also are nonexclusive.

Before implementing incremental staging, reuse existing page-boundary/schedule/262,144/RESTORE fixtures and add a source-level gate proving the stage-valid-prefix invariant for every QSA layer and all fail/cancel exits. First compare one small all-resident and one streamed chunk-sequence for page/table/residual/logit parity; then 32K/64K fresh-prefix current benchmark arms. Test nonzero pos0, incoming RESTORE, repeated request, short-tail chunk and failure/cancel before enabling beyond fresh sequences. If current layer-major path already runs only after checked drains, do not add per-chunk global synchronization; rely only on established in-order queue and existing completion fences. Default stays full restage unless correctness and clean end-to-end improvement both pass.

## QSA, GDN and dense projection relevance

The current QSA score selector (`qsa_block_scores` + top-k) is a custom SYCL path, not oneMKL GEMM; `qsa_block_scores_tc()` currently returns false. At a 4-cell index block, it scans a causal count of approximately `sum(floor((i+1)/4)+1)` block candidates per query. With four 128-wide score heads, that is about 68.7 billion MAC (~0.137 TFLOP at 32,768) and 274.9 billion MAC (~0.550 TFLOP at 65,536), a roughly 4x source-shape growth for 2x input. This is arithmetic from geometry, before masking/reduction efficiency; not device time. Prompt attention itself caps selected width near `idx_top_k + idx_block - 1 = 2,051` cells, so its selected-cell logical operand upper bound grows approximately linearly with query count. R564's ~2.17 MB/query at 2,051 selected cells implies ~71 GB at 32,768 and ~142 GB at 65,536 for that operand set, not unique physical bytes from DRAM. These shapes reinforce that 64K is not a linear extrapolation of 32K throughput.

Current root has custom QSA prompt matrix and selection paths. Historical QSA/XMX settings or implementation are not active merely because the old source is reachable; R564 already evaluates a CH64 attention geometry hypothesis and R589 a separate block-score GEMM proposal. Neither is newly proposed here. The actionable distinct current source hypothesis is repeated history staging above.

Current root fused GDN differs from historical tuned GDN mapping, but R592's same-root CLI pair moved only 0.33% at 4K and 0.61% at 8K after a larger recurrence-probe gain; R592's measured/source phase share was small and nonexclusive. GDN is not selected as one of the two large-gap explanations. Do not change QSA/GDN/PLE math or ordering as a side effect of chunk/staging changes.

Current dense/Native projection route uses `Gemm::native`/BF16/FP16 with root `src/prefill/sycl/gemm.cpp`; the per-expert MoE route is not missing oneMKL entirely. The old donor's column-major and current row-major descriptors encode the same output, and R566's isolated descriptor probe was small and not model-qualified. No source evidence here supports a dense-projection kernel as a primary cause. MTP4 is a separate workload difference: current callback (`Prefill::draft_kv` or fallback `mtp.prefill`) executes from `on_chunk` before the prefill interval completes; PR #6 had no MTP model. Preserve MTP4 in official product arms and report its prompt callback time/counters separately if available. A no-MTP diagnostic can measure its added workload but is not a production-equivalent result.
