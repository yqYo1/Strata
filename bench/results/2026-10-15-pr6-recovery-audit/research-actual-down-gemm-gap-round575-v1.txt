# R575 — actual routed Down GEMM interval and component-probe gap

Date: 2026-10-15 JST. Read-only source and retained-evidence review for the configured Strata root SYCL path. This report is the only write. No product edits, build, test, GPU/profiler, process/service inspection, cleanup or Git mutation was performed. The private environment/receipt paths were not accessed.

## Conclusion

The 61.535 s `gemm down` phase bucket is not evidence that 90,297 Down GEMMs each took 682 us, nor does it contradict the synthetic hot-GEMM measurements (about 85.9 us at `ne=428`, 150.9 us at `ne=1490`, 370.3–378.1 us at `ne=4096`). The bucket is a queue-marker interval accumulated across the routed expert walk. Its marker is placed just before each Down GEMM, while the next marker is commonly the next expert's wait/dequant/gather/GU sequence or the layer's combine. Delayed host submission of that next marker leaves GPU-idle and queued work in the preceding Down interval. The marker bucket therefore mixes current Down GEMM execution with boundary wait/submission effects. Adjacent phase totals are also not exclusive, and the 75.519 s staging consumer accumulator overlaps the device timeline.

Source does not establish a missing/slow per-call initialization or a changed GEMM descriptor in the actual route. The external GEMM scratch and 32 MiB workspace are carved/initialized once per prefill layout. In compact FP16 mode, the route reuses two FP16 GU and two FP16 Down dequant buffers; each active expert is dequantized, gathered to the compact row-zero activation scratch, run through GU GEMM and SwiGLU, and then sent to Down GEMM. The actual Down operands are `[ne,640]` and `[2560,640]`, output is FP32 at `Dm + o0*2560`, and `ld=2560`. The same non-null in-order queue carries the sequence; `finish(stream,event)` does not host-wait for each GEMM. This is the path the component measurement partially represents, but the hot component has no native packed source/dequant, gather, expert routing, Stager wait/copy, preceding GU/SwiGLU submissions, or across-expert host gaps.

The most actionable code candidate is a narrowly gated same-layer batch for repeated tiny Down shapes (`1 <= ne <= 16`), with a per-expert fallback. It would retain each tiny expert's SwiGLU output and dequantized Down weights long enough to issue one grouped `gemm_batch` for several experts with identical dimensions and separate `Dm + o0*N` output pointers. It must be staged only after the expert's GU/SwiGLU is ready and before combine. This could reduce API submissions on the 55.13% of active calls that contain only 1.386% of routed rows. It cannot explain the 61.5 s bucket or account for most arithmetic. Treat this as a bounded host-call optimization hypothesis: R496's group-of-four synthetic Down case improved 2.85%, while most group-of-two cells regressed; that evidence does not establish a tiny-M benefit. Stop if exact-shape group frequency is low, metadata/dequant/retained-buffer cost consumes the saved submits, output parity/fault checks fail, or the paired whole-prefill result does not improve beyond run variation. Do not revisit descriptor orientation: the 64-group screen selected the same device kernel for both descriptors.

## Evidence and actual operation path

The retained census is the 34,560 batched-token, nine-chunk compact FP16 request: 48 MoE layers, 432 layer-chunks, 90,297 active expert calls per role, 16,588,800 routed rows per role. The observed active-call `ne` percentiles are p50=12, p90=428, p99=3,245, max=4,096. Calls with `ne<=16` are 55.13% of active calls, but only 1.386% of rows; the row-weighted median is 1,490. These counts distinguish call exposure from work exposure. They do not determine the time weight of any shape.

In current `src/prefill/prefill.cpp`:

- `Prefill::carve` takes one 32 Mi-element FP16 GEMM scratch and one 32 MiB workspace before the MoE region; the layout carves them once. `dq_gu[2]` and `dq_d[2]` are separate persistent scratch arrays, also carved once; `q = j % DQ` rotates the two slots. There is no per-expert allocator in this call chain.
- In the non-MMQ route around lines 2824–2850, each active native expert's packed GU and Down blobs are dequantized to FP16 on the compute queue. The current stream slot is marked used after those kernels have consumed the blob. Compact FP16 then gathers activation rows to `Xs` at row zero; GU computes to compact `GU`, `swiglu_interleaved` writes compact FP16 `Hh`, and Down GEMM writes to the expert's global routed-row offset in `Dm`.
- `src/prefill/sycl/gemm.cpp` calls row-major oneMKL `gemm(nontrans, trans, T, N, K, ..., ld)` and `finish()` is a no-op for the caller's non-null prefill stream. For the actual Down call `T=ne`, `N=2560`, `K=640`, `ld=2560`, and beta defaults to zero. `src/prefill/sycl/postops.cpp` computes interleaved SiLU(gate)*up into FP16 `Hh`; it is upstream preparation for Down, not part of the GEMM component result.
- `Prefill::init` aliases the copy and compute queue for SYCL. Stager preparation runs on host workers, but copy/dequant/gather/GEMM are ordered on the same in-order queue. The source contains `wait_issued` and optional copy-event boundaries in the streamed route. A wait for an expert's staged blob can be charged to an open phase marker depending on where the next compute marker is submitted.

The measurement boundary is consequently narrower in the component probe: hot, preallocated FP16 X/W/Y buffers with no native source-format rotation or dequant; no gather or preceding GU+SwiGLU; one shape and role at a time; repeated calls followed by batch queue drain. Its `ld` now matches the actual Down shape. R563's descriptor difference (donor column-major description versus current row-major description) has been screened: the actual-stride v2 test reports the same device kernel name and geometry in all 64 shape/stride/orientation combinations. Its timing differences do not justify changing the production descriptor.

## What the 61.535 s marker bucket means

The marker implementation in `src/prefill/prefill.cpp` records phase events on the compute queue. Each elapsed interval is charged to the phase of its first marker. In the expert loop, the Down marker is immediately before `m.gemm.f16(...)`; the next Down marker for the next expert is reached only after the host has returned to the loop, prepared/queued that expert's work and passed its own wait/copy/dequant/gather/GU/SwiGLU path. The marker interval can therefore include time between marker submissions and queue-idle gaps after the Down command. Lookahead copies queued before a marker also obey same-queue order and can drain during a later marker interval. The bucket is useful to identify an expensive region of the run, but not to attribute its duration exclusively to Down service.

The 32.529 s dequant and 5.273 s gather marker intervals have the same marker-boundary limitation. The 75.519 s host staging figure is an accumulated consumer-side stage duration that includes waiting for Stager work and submitting H2D, and overlaps the device timeline; it must not be added to phase totals. The run also has 6.004 s in the GU marker interval and 5.273 s in gather. A phase accounting split needs host-boundary timing or a separate device activity attribution; simple byte divided by nominal link bandwidth is not a physical lower bound for this route and is not used here.

The synthetic samples do establish that one hot Down GEMM at the cited shapes is much shorter than 682 us, and actual `ne` often takes values outside the three highlighted shapes. They do not establish the actual sum of Down service across 90,297 calls: the full call histogram and each shape's paired actual-path work, cold dequant, staging and queue gaps are not represented by the few cited timings. In particular, multiplying 90,297 by one representative duration would be invalid. The 61.5 s value must not be used as a target GEMM time or divided into per-call service.

## Candidate and rejection conditions

### Gated same-shape tiny Down batch

Implementation point: the non-MMQ branch in `src/prefill/prefill.cpp` around the per-expert `m.gemm.f16(...Hh..., ...dq_d[q]..., ...Dm+o0*N...)` call and the oneMKL wrapper in `src/prefill/sycl/gemm.cpp`. Keep the current path as fallback. Within a layer, form groups only from active experts whose exact `ne` matches and is in 1..16. The group plan should be derived from the already authoritative `m.cnt`, with output pointers preserving each `o0`; each member must first finish its own GU and SwiGLU production on the same in-order queue. Hold FP16 Hh and each member's FP16 Down dequant result until the grouped event completes; the current two rotating Down buffers cannot be overwritten before that event. Host pointer arrays/metadata and device buffers remain alive through event completion. Group only when at least four same-shape members are available; otherwise use the existing call. Avoid per-expert waits.

This is a real code change, not a claim that grouped GEMM is intrinsically faster. It targets host-call count for a highly call-heavy but row-light part of this histogram. The scratch cost must be explicit: each held Down matrix is `2560*640*2 = 3,276,800` bytes, while four tiny Hh outputs require at most `4*16*640*2 = 81,920` bytes. The workspace currently reused by the two scratch slots is not four independent Down weights, so the proposal needs bounded additional storage or a scheduling arrangement that safely retains the corresponding dequantized weights. Include that allocation in the real prefill capacity accounting. The same-layer exact-shape group count, host metadata build time, dequant time, submission time, queue-drain wall and formal prefill wall are all required to accept it. R496's 4-expert synthetic result and R566's generic grouped API discussion are prior evidence; they neither qualify this small-M gate nor justify a broad all-shape batching rewrite.

Reject the candidate if tiny same-shape groups are uncommon in actual layer-chunks; if staging/copy or other queued work, rather than host calls, dominates after attribution; if held weights force a memory-fit/chunk regression; if grouped output error changes routes/logits beyond the predeclared practical gate; or if model prefill does not improve repeatably. The best possible gain is bounded by the tiny-call portion and cannot close the full marker-bucket gap alone.

### Marker-observer correction for attribution (diagnostic, not an optimization)

Before attributing any model speed change to Down, add aggregate host duration/count fields to the existing opt-in routed FP16 observer at the exact host call boundary for Down GEMM submission, with bins for `ne<=16`, `17..428`, and `>428`; add the matching GU call counters only as a control. Do not add a wait, event query, per-expert log or route ID. In the same bounded request, separate consumer `Stager::wait` time from host `cudaMemcpyAsync` submission and worker memcpy/service if those counters are already in the R521 plan. This identifies whether host-side work is exposed in the bucket; it does not measure GPU service or critical path. If this observer changes paired unprofiled wall beyond baseline variance, discard its timings as causal evidence. Prefer an admitted existing device activity collector only if its clock/overhead limitations are already qualified; do not use the old external UTC alignment or unsupported VTune path.

## Retained decision boundary

- R563's source comparison: current compact per-expert sequence, DQ=2, global output offset, and same async queue are already present; it found no missing donor batching. R564 Main review corrected/limited its claims and identified the need for a diagnostic orientation probe.
- R566's actual-shape discussion distinguishes hot synthetic GEMM from the native-format model path and lists GU+SwiGLU fusion and generic grouped GEMM. This report does not repeat the GU+SwiGLU fusion proposal. The tiny Down batch above is a narrower gated candidate with explicit scratch, frequency, host-call and rejection conditions.
- R496 found group-of-four synthetic Down about 2.85% faster and most group-of-two cases slower. Use only as a reason to keep batching conditional; it is not current-model speed evidence.
- `gemm-orientation-screen-v2.ja.md` and `unitrace-gemm-evidence-v1.json` qualify actual `ld=N` for the descriptor comparison and show the same kernel selection in 64 groups. The profiler validation is not clean timing evidence.
- No direct quantized-XMX Down, dequant-weight cache/reuse, expert tile batching across nonmatching shapes, alternate orientation, or two-queue overlap is proposed. They have no current demonstrated benefit here; two-queue overlap was previously observed to stall at realistic expert shapes, and the current FP16 path already dequantizes each expert once into rotating scratch before GEMM.
