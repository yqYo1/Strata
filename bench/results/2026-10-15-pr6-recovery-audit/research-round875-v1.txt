# R875 — Separating memory, synchronization and matrix limits in QSA prompt attention

Decision support, read-only; evidence and documentation checked 2026-10-16. This report answers what the current source and already exercised unitrace path can separate without another device run. It does not classify the kernel as memory-, barrier- or compute-bound.

## Pinned source and workload

The supplied index hash and all source hashes matched revision `63326f98c36656cf3a3e1adcc54c3c25a02aa6ee`: `prompt_attention.cpp` SHA-256 `5fa7927e611b8cb746e1d11bd70a8e2aae3c66a48b02a93eb55e86eb9bf0076f`; `qsa_prompt_attn.hpp` `e5ed40cde930e09265b6b4b4ba27ae1118444fed8078d39689a08692dca0e230`; `qsa_decode_attn.hpp` `3745db42a1a1fa84a40a5040352a9d5f16f735ae431389b8617dd6cd11bfdd14`. Both closed, passed R861 diagnostics bind to engine SHA-256 `6334491b623ead7b83c7ff5aaee84583294b3ecd4b12c6d06b77d1fe7e7a691d`; neither is a clean performance sample. Target: BF16 Q, int8 K/V Mode 1, actual 39,262-input prefill, context/KV resident 65,536 and chunk 8,192. `STRATA_SYCL_PROMPT_SOFTMAX_SUBGROUP` selects `launch_prompt_bf16<false>` (baseline) or `<true>` (cooperative softmax). Each query/KV-head workgroup has 128 threads, 16-lane subgroups and 16 padded query-head rows (12 active), processing up to 32 selected cells per iteration. Local receipts consulted: paired `own-prompt-softmax-long-diagnostic-{0,1}-r0-v1.json`, `own-prompt-softmax-qualification-v1.ja.md`, the old-source `own-current-device-profile-summary-v1.json`, R748 `research-profile-counters-round748-v1.txt`, plus `own-host-transfer-component-v1.ja.md` and the historical `ATTAINED_CAPACITY_AND_DECISION_BUDGET.md`. The cell-major comparison was slower by 11.28% and does not identify this kernel’s bottleneck.

For each valid row, one KV-head workgroup loads 256 INT8 K codes, 256 V codes, four FP16 scales per tensor, a 4-byte ID and a 4-byte page-table entry: 536 source-request bytes before Q, step, output and padding. This logical estimate is not L3/DRAM traffic; caching and transactions change physical bytes. K is staged once and reused across 12 active heads, then the local tile is overwritten by V. Resident KV loads are not per-row PCIe transfers; weight/residual transfers elsewhere can overlap or delay the kernel and need separate copy intervals.

## Source phase to metric map

| Phase | Global inputs and reuse | Math/state and workgroup barriers | Useful observation |
|---|---|---|---|
| Setup / width | Reads BF16 Q and `steps[batch*kStepCount+kStepWidth]`; scales Q into one FP16 local tile. No cell IDs yet. | Initializes FP32 maxima/sums and joint-matrix accumulators; one barrier before the loop. | Timing alone includes setup. Occupancy/resource metadata is launch/build dependent. |
| Resolve 32 IDs | Lanes `tid<32` read ID and page table, validate page and store row addresses reused for K and V. | Clears scores; barrier before K/scales. | No traffic counter means no conclusion about ID/page-table cache efficiency. |
| Stage K and QK | Reads K codes and four FP16 scales per row; local K serves active heads. | Four 64-dimension groups; FP16 Q×K `joint_matrix_mad`, FP32 accumulation/scaling; barrier after scores. | Per-instance GPU/L3 read bytes and XMX versus send activity separate traffic from matrix work, if exposed. |
| Online softmax | No K/V global reads in this phase; reads/writes local FP32 score and recurrence state. | Baseline has `tid<16` scan 32 scores serially per head. Cooperative arm has each subgroup lane handle cells `c` and `c+16`, with subgroup max/sum reductions. Both update FP32 max, sum and alpha. | Compare the two exact symbols’ per-kernel duration and ALU/XMX activity. A broad stall percentage does not identify reduction or barrier wait. |
| Stage V / form P | Reads V codes into the reused tile; V scales were loaded with K scales. Four factors are reduced. | Forms one bounded FP16 probability part per value group; barriers separate V load, factor and P writes. | Global/L3 bytes aggregate the kernel; source/ISA mapping is needed for phase attribution. |
| PV / finish | Reuses local V and P; no additional selected-ID lookup. | Four output-dimension blocks accumulate P × V through FP16 joint-matrix products into FP32 state, rescale by online-softmax alpha, then write BF16 output. One barrier after PV in every tile. | XMX utilization/instruction mix versus measured DRAM/L3 bytes can support or reject dominant resource hypotheses; neither alone gives a critical path. |

Seven workgroup barriers occur per 32-cell iteration (after score clearing, K/scales, QK, V, factor reduction, P formation and PV), plus one before the loop. This makes synchronization measurable, not proven expensive: overlap, resident groups and barrier wait are not source facts. The softmax variants differ in reduction work; R861 has no clean timing or counters here.

## What the tools can resolve

PTI unitrace documentation (`master`, read 2026-10-16) separates timing from counters. `--device-timing` reports command/kernel time and properties; `--kernel-submission` splits queue, submit and execute; `--device-timeline` timestamps them; `--chrome-kernel-logging` adds device events, host/device interactions and dependencies; `--chrome-call-logging` traces host Level Zero/OpenCL calls. These can show copy intervals, QSA gaps, queue overlap and waits, but not bandwidth. Copy payload sizes are not guaranteed in trace events; pair intervals with existing exact byte records, or mark bytes unavailable.

The qualified direct-model receipt proves unitrace timing was exercised, but its source package configures host/device summaries only and excludes timeline, metric and filter controls. Its receipt binds an older source/binary. A native-only timeline needs a separately qualified path binding documented options to the owned backend child; no undocumented `UNITRACE_*` variable can be assumed. The package was not changed or run.

Unitrace documents `--metric-query` (`-q`) per kernel instance, `--metric-sampling` (`-k`) time-based samples, `--group` selection and `--metric-list`. Generic examples name `GPU_MEMORY_BYTE_READ/WRITE`, `L3_BYTE_READ/WRITE`, XVE send/XMX/ALU/control activity, `XVE_ACTIVE`, `XVE_STALL`, `XVE_THREADS_OCCUPANCY_ALL` and `XVE_BARRIER_MESSAGE_COUNT`. Query can attach metrics to a prompt instance; sampling may miss short calls. Use one group per pass. Generic metric names do not prove B570 support. Barrier-message count is not wait time, and broad `XVE_STALL` gives no barrier reason; synchronization needs a supported barrier-stall or instruction-level signal.

R748 records the unprivileged counter route blocked (`/proc/sys/dev/xe/observation_paranoid=1`); no enumeration/query was attempted. No non-root route or B570 SLM-wait metric is established. PTI stall sampling is documented only for Data Center GPU Max and later, not Arc B570. VTune previously could not recognize this host’s microarchitecture; do not retry. Its 2026.1 GPU Compute/Media Hotspots guide (Preview) documents task time, occupancy and source analysis, but not host support; memory-bandwidth analysis also requires sampling drivers. VTune is unavailable evidence here. Its metric catalog lists candidates such as XVE Barrier Stall, SLM bandwidth/bank conflicts and thread occupancy, but the host visibility failure prevents using them.

## Keep resource quantities separate

The old whole-process profile’s 33.966 s over 72 launches is a nonexclusive service sum, not current R861 kernel time or critical path. Its 4,096-byte SLM property came from source `6354f0b4ff3731466795410e11ca9ef785c9d326` / binary `85643f3926bb9d212945659cb7ddb264e101ca9b2d5fa8f19430e945140ad191`, the earlier FP32-Q path and a kernel-create snapshot before local-argument settings. R861’s BF16 launch requested 32,336 local-argument bytes: Q 8,192 B, K/V 16,384 B, P 4,096 B, scores 2,048 B, scales 1,024 B and other state 592 B. These are different builds/captures; do not add them, treat either as physical SLM or infer occupancy. `BF16_SLM+4096` is only a support gate.

Capacity figures are context, not utilization. The 2026-10-16 idle-queue copy component measured 320-MiB ordinary H2D at 6.015 GB/s and host-USM at 5.095 GB/s; USM shortened submission but slowed whole H2D. Results depend on size and allocation. A 2026-10-10 sheet gives PCIe Gen4×4 ideal encoded payload 7.877 GB/s/direction and older attained H2D 6.447 GB/s; vendor VRAM bandwidth 380 GB/s differs from 330 GB/s logical copy. The 36.87 GB/s RAM read result is a separate six-core test. None is current prompt utilization. Use trace intervals with exact payload bytes; keep them separate from PCIe wire, L3/DRAM traffic and summed service.

## Minimal serialized profile plan and decision boundary

After the active clean cohort closes, collect one timing trace per R861 arm with pinned source/binary and the same 39,262-input workload, placement and runtime. Fix environment before exec (`STRATA_SYCL_PROMPT_SOFTMAX_SUBGROUP=0` or `=1`) and preserve separate process ownership. Prepend `unitrace --follow-child-process 1 --chrome-kernel-logging --chrome-call-logging --kernel-submission --device-timeline --device-timing -v` to the exact owned native argv from the R861 receipt. Leave this trace unfiltered to keep other kernels, copies, dependencies and gaps; identify `launch_prompt_bf16` in the result. Join copy intervals to existing exact H2D/D2H byte records. This is an instrumented dependency profile, not a speed comparison. A counter pass needs a separate process per arm and one supported `--metric-query --include-kernels launch_prompt_bf16` group per pass, but current evidence says it is unavailable.

Favor global-memory pressure only if per-instance memory/L3 bytes and measured bandwidth approach matching device capacity with send activity/cache misses; low rates and high hits weaken it. Favor a PCIe dependency if measured payload rate nears matching H2D/D2H capacity and copies overlap QSA or end at its dependency edge; no nearby copies or long gaps weaken it. Favor XMX saturation if XMX activity nears a supported maximum with high matrix instruction activity and low memory pressure; low XMX use rejects it. Synchronization needs supported barrier-stall time localized to tiles, low memory/XMX pressure and a repeatable arm difference; a message count or broad stall percentage is insufficient. Without counters, trace can establish timings, recorded bytes, overlap and dependency gaps, not bandwidth, occupancy, XMX saturation or barrier-wait cost.
