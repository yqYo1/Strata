The normal default suite order, thinking default, calibration and workloads remain unchanged. Opt-in mode runs only the existing short chat warmup (24 output tokens) and three default fresh long requests (24 output tokens each), with thinking explicitly enabled through the existing chat_body path. No calibration, 4K/16K cohorts, agent, long-generation or concurrent requests run. `--prefill-tokens` accepts only 32768 or 65536, defaults to 65536 in this mode and rejects use outside it. Mixed suite scopes and nonpositive runs reject before config discovery/server startup. Explicit `--think` is harmless. Existing `--compare` may consume saved results; `--compare-only` is incompatible with the execution scope.

Measured bodies use the existing Suite.prompt_for / long_prompt / chat_body / workload-ID / request-journal mechanisms. Construction uses a 25%-oversized target and fixed rate/overhead constants (1.1/40) independently of calibration or any server responses. The fixed workload ID plus run index determines each distinct input exactly; changing the run index changes the fresh prefix. Neither undersized nor oversized/failing bodies are silently repaired, retried or reinterpreted. Construction estimates are explicitly separated from actual server counts. A known context must accommodate the oversized target plus 24 output and 256 headroom before even warmup; tokenization can still exceed an estimate, in which case the request or actual headroom gate fails.

Every measured response must complete normally at the stream/usage layer, report integer `usage.prompt_tokens` AND integer `timings.prompt_n` each >= the requested minimum, report explicit zero reuse (all available usage/timings reuse counters must be zero), report 1..24 actual completion tokens and finite positive engine prompt_per_second, and fit actual prompt + 24 + 256 within known context. Missing prompt_n is a failure; this mode never substitutes usage-minus-cache for the read counter. A nominal 32K result of 32089 fails the 32768 gate. Existing generic digest remains unchanged for ordinary workloads. Ineligible returned samples are journaled before terminal failure and are excluded from summaries.

Metadata records mode, requested minimum, construction plan/version/constants, actual prompt/read/reuse counters and their sources, completion count, thinking request, observed reasoning and any reported reasoning-token count. Thinking enabled is the sent request setting; observed reasoning is recorded separately, without asserting that empty reasoning proves the server honored or ignored that setting. Body SHA256 and actual workload provenance remain in the journal/results/comparison identity. Agent files are not traversed for this scope.

The existing renderer has a mode-specific report showing individual counts and reasoning observation, and generic summary/table helpers accept absent chat/agent/client cohorts. On returned errors or invalid bounds, results.json and README plus the durable journal/state retain the failed response and prior samples, complete=false/qualified=false. On Python interruption or transport exceptions, completed samples and any returned interrupted response are saved atomically in results.json with an incomplete report before rethrowing; the journal preserves the request start and interrupted/result evidence. Uncatchable termination or storage failure cannot guarantee a final report; the already-fsynced journal remains the durable prefix. No full API bodies/outputs are retained, only bounded per-request counters/hashes and errors.
