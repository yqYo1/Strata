This is a proposed arm, not a capacity guarantee: it adds exactly one chunk over the established R32768 arm. For HC4x2560 FP32 residuals, the row is 40,960 B, so R32768 occupies 1,342,177,280 B (1.25 GiB), R40960 occupies 1,677,721,600 B (1.5625 GiB), and the increment is 335,544,320 B (320 MiB). It does show that the old R32768 path was sensitive to runtime drift; R40960 costs a further 320 MiB. The canonical arena release is a source-visible logical saving, but its net usable bytes during the actual run have not been measured. ## Current allocation and rejection contract

`LayerMajorResidualPlan::make` uses row bytes `HC*N*storage_bytes`; for this path `4*2560*4 = 40960`. Explicit decimal R is rounded down to a whole chunk except `R==n`, which keeps the exact full length. Values above `n` and malformed values reject. A device chunk may not straddle the device/host boundary. For FP32 there is no FP16 tail staging. It validates `gpu_bytes <= gpu_budget`; insufficient explicit R throws `requested layer-major GPU residual prefix plus staging exceeds free VRAM with headroom`. Automatic mode instead chooses the largest complete chunk prefix that fits; neither mode retries an explicit request at a smaller R.

Before plan construction, `run_layer_major` reads current free VRAM and requires `free_gpu >= cache_bytes + 512 MiB`; then it passes `free_gpu - cache_bytes - 512 MiB` as the residual budget. `cache_bytes` is the extra 512-expert layer cache (1,363,148,800 B for this workload's source layout). It admits host RAM separately for host residual tail, upload cache/slab and maps with an 8-GiB allowance. After admission, it creates host upload/tail and maps, opens the layer cache, allocates the FP32 device residual prefix, then proceeds with layer uploads and chunk execution. Thus increasing R changes residual placement/ownership and host-tail size only; FP32 values, layer operations, chunk math and their inputs are unchanged. That does not itself prove identical results; the selected reference comparison remains required.

A fail-closed explicit-R rejection occurs before these residual/cache allocations and before layer computation. Allocation-time failures also return false under the checked outer lease, which drains before owners are destroyed. Do not silently lower R or convert to another dtype. Record the admission line and native outcome for the chosen value; a failure is an unqualified/rejected arm, not an invitation to retry an unplanned value.

## Canonical/native owner ordering and lifecycle headroom

The generator prepares the canonical active-layer bank and persistent pool, then prepares the NativeDense bank while the original full canonical arena and native packed owners still exist. Those allocations must fit simultaneously before any owner can be withdrawn. Graph/verifier readers are then retired; native originals are freed on entry to its bank, and `CanonicalDenseBank::enter` withdraws table pointers and frees the original canonical arena. The layer-major free-memory query and its residual admission happen only after this phase has completed, so it sees the canonical release if the actual integration/run reaches that point.

The layer-major residual, expert cache and host owners are local to `run_layer_major`; they are destroyed when that call returns, before the outer generator transaction restores the full model. Restore first allocates every NativeDense original packed owner while the native bank remains allocated; only after all allocations/copies succeed does it free that bank. It then allocates the original canonical arena while the canonical active bank and persistent pool remain allocated, uploads the retained RAM snapshot, republishes references, rebinds PLE and retires the bank/pool. Therefore the restore allocation does not overlap the local layer-major residual/cache allocation, but it does need headroom for the full native owner set plus the canonical bank and persistent pool while the full canonical arena is allocated. During prepare, original owners and both destination banks coexist. The 512-MiB layer-major cushion is not proof of either prepare or restore peak capacity.

Relevant component receipts report canonical full arena 1,538,035,200 B, active-layer bank 32,284,672 B and persistent pool 82,821,120 B. Those component receipts passed allocation/transition/restore fault arms, but they explicitly make no full-model runtime/admission claim. Their successful component restore does not establish that generator prepare, a long prefill, and full restoration fit together. The capacity document's ideal combined-layer/context table also excludes the current decode/cache/head/MTP serving configuration and is not a measured free-memory receipt for this run.
