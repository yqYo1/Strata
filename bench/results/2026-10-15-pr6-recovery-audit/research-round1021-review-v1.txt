## R1019 — 64-cell QSA tile

The source accounting is correct. The current kernel declares 28,224 B of local payload for `Cells=32, ScoreStride=33`; the templated 64-cell candidate declares 47,936 B for `Cells=64, ScoreStride=65`, a 1.70x increase. These totals follow the actual Q/KV/probability, score/state, row and bad-head accessors. The kernel’s matrix-admission check separately requires payload plus 4,096 B (52,032 B for the candidate); neither figure proves residency, compiler allocation, occupancy, or speed.

The corrected source geometry is also right: current QK and PV each make 64 `joint_matrix_mad` API calls per KV-head/tile; both heads make 128 per phase. QK’s 256-dimension loop is real. PV instead has four accumulator fragments and `Cells/16` reduction fragments, so it has no such dimension loop. With 64 cells and the proposed 2 head bands × 4 cell bands, QK and PV each make 128 calls per KV-head/tile. The report correctly calls these API/source counts, not executed instructions or cycles. The 8 × 16 × 16 shape keeps the total padded MAC count per selected cell unchanged; the per-tile API-call count doubles while the long-sequence tile count can roughly halve. Five explicit barriers remain per tile. Serial max/sum/probability work per tile grows from 32 to 64 cells. These are tradeoffs, not a speed prediction.

The SLM arithmetic and subgroup coverage agree with `qsa_bf16_prefix.cpp` and the prepared candidate excerpt. In particular, the candidate still gives one query and one KV head to each workgroup, covers 16 padded query rows, and writes all 64 score columns through eight QK subgroups. Row pitch 65, 64-element row IDs, BF16 operands/probabilities, and FP32 score/online state are included. The bounds discussion preserves missing and partial cells, page/live-cell checks, padded heads, NaN/scale behavior, and physical-context gates. The numerical section correctly warns that per-tile BF16 probability rounding changes with the grouping and that the actual selected SGLang/vLLM execution path must be pinned before using it as a numerical gate.

No factual correction is required to R1019. It appropriately uses the main correction receipt for the earlier PV-count error, keeps the prior subgroup/tilepack and cross-query work out of scope, and labels the old attention/GDN/MoE queue intervals non-exclusive. Its Qwen3.5 SGLang/vLLM links are mutable model-wiring references only; they do not identify the exact Qwen3.8-Flash-Next runtime backend or establish a matching numeric contract. The report says this, so index the reference as a retrieval lead only. The separate QSA64 proposal manifest says it is unapplied, uncompiled, and unqualified; this review did not elevate it. Source and header hashes in the wave manifest match the current workspace.

## R1020 — expert upload overlap

The ownership argument for reusing the existing slab is sound: each layer’s 512 H2D submissions are checked-drained before residency is published and before `run_impl`; compute then reads the separate GPU cache. A synchronous next-layer `copy_blob` after that layer’s compute therefore cannot overwrite a host buffer still read by its previous H2D. The current resolver split is also accurate: `generate.cpp` selects `FileExpertSource` for `--mmap-experts` and `ArenaExpertSource` otherwise. The base source’s `blob()` pointer can expire on the next blob call; the File source has separate copy paths, including direct-read thread-local scratch on Windows. The report correctly rejects retaining an unleased blob pointer for DMA and notes that `pinned()` alone is not a lifetime lease.

The performance timing needs a stronger conclusion than the report gives. In the current layer-major route, `m.copy == m.cs` is a precondition. `run_impl` synchronizes `m.cs` immediately before each chunk callback and synchronizes both `m.cs` and `m.copy` before returning. For each non-final ordinary chunk, `on_chunk16` (or `on_chunk`) then enqueues the residual store and calls the checked layer-major `drain()`, which synchronizes those same queues. In the MoE-window route, each attention-bank piece is synchronized before the window callback, `run_moe_window` synchronizes after its writes, and the final bridge callback drains again. Thus, when `run_impl` returns for a non-final layer, current-layer GPU work is already retired; the outer pass drain is a second check. Copying layer L+1 between return and that drain is memory-safe, but the inspected source exposes no GPU tail for it to overlap. Treat option A as **no-go under the current ordering** and do not spend a new build/GPU comparison on it unless a future source path demonstrably returns with relevant commands still pending.

The recorded source-copy interval (about 4.7 s in the assignment; a nearby completed receipt reports 4.8407 s CPU and 4.8465 s wall across 48 layer copies) measures host copy work. It establishes neither hidden GPU time nor speedup. Since current callback drains remove the proposed overlap window, those values remain on the serialized layer path. A worker started after upload drain and before `run_impl` is the only described option that could overlap source copying with current GPU execution, but the generic `ExpertSource` contract does not grant universal concurrent `copy_blob`/`warm` safety. `RouterLookahead` can own an asynchronous `warm()` thread, and the direct-read File path may allocate per-thread scratch; a worker stack and TLS scratch also defeat a strict no-extra-RAM claim. Hold this option. The API needs an explicit capability/lifetime/resource contract before any worker proposal, and this review does not recommend one. The same applies to direct DMA: require a stable, DMA-capable pointer lease through checked completion, not just `pinned()`.

Destruction ordering is adequately covered at the design level: an asynchronous worker must join before source/slab owners can die, then the existing checked queue lease must prove DMA retirement; failure paths must not release live storage. One useful citation is absent from R1020: C++ [data-race rules](https://eel.is/c++draft/intro.races) directly support its warning that a thread-safe join and object lifetime do not make concurrent calls on a shared source safe. The report already cites the [join synchronization rule](https://eel.is/c++draft/thread.thread.member) and [object lifetime](https://eel.is/c++draft/basic.life); this is a reference-completeness note, not a reason to change its conservative conclusion.

The generic [SYCL queue](https://github.khronos.org/SYCL_Reference/iface/queue.html) and [`handler::memcpy`](https://github.khronos.org/SYCL_Reference/iface/command-group-handler.html) pages support only general queue and endpoint semantics. The local layer-major path uses the CUDA compatibility calls shown in source, so those documents do not prove this route’s completion or host-slab reuse behavior. R1020 states this limit. The [Intel joint-matrix extension](https://github.com/intel/llvm/blob/sycl/sycl/doc/extensions/experimental/sycl_ext_matrix/sycl_ext_oneapi_matrix.asciidoc) is an experimental, mutable branch document; its collective rules and supported-shape query API support R1019’s legality checks, not this compiler/B570’s lowering or performance. The [Intel optimization guide](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2024-1/joint-matrix.html) is general background. Both Qwen source links point to mutable `main` branches and are not runtime pins.
