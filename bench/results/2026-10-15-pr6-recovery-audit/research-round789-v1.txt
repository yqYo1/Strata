# R789 — HC4 BF16 residual-combine mapping and fusion choices on Intel Xe2

Date: 2026-10-16 JST. Purpose: decision support for the current native-16 long-prefill work. This is a read-only source and documentation review; no Git, product edits, builds, tests, GPU work, profiler use, process inspection, cleanup, services, or environment changes were performed. Main’s assignment pins the active implementation source at `662e3a1e` and identifies HC4, N=2560 per stream, and 8192-row chunks. I inspected only the relevant live-tree kernel and call seams; this report makes no speed claim and proposes no third-party code reuse.

## Geometry and current dataflow

The four residual streams are laid out row-major as `[T, HC, N]`, with `HC=4`, `N=2560`, and `D=10240`. The active `native16::write` in `src/prefill/sycl/native16.cpp` assigns a flattened item to each `(row, stream, feature)`. It loads one BF16 `bo[row, feature]`, one BF16 old residual, and one FP32 injection scalar; it computes the gate/FMA locally in FP32 and writes BF16. Thus each new MoE output is consumed once for each of the four streams. The adjacent `native16::combine` separately materializes one BF16 `bo[row, feature]` per row-feature. The next HC normalization is also a separate kernel: `native16::norm` groups work by `(row, stream)`, reduces the 2560 BF16 values in FP32, then writes the 16-bit normalized activation. These are source observations, not measured costs.

For one 8192-row chunk, `R16` is 160 MiB, `bo` is 40 MiB, and `XN16` is 160 MiB. A standalone residual write logically reads and writes 160 MiB of residual and reads the 40 MiB `bo` four times (160 MiB of feature values), before any cache reuse. Separate normalization reads the newly written 160 MiB residual and writes `XN16`. A `combine`→`write` boundary also materializes `bo` once (40 MiB) and reads its feature values four times (160 MiB) in the following kernel. Those are tensor-byte counts, not DRAM traffic: caches may serve repeated reads, and they do not predict kernel time. All row and stream boundaries are aligned to 16- and 32-element feature groups because N=2560 and D=10240.

## Standalone mapping alternatives

**Flat 1D, one item per residual element.** This is the simplest reference mapping and is already used by `write`. With flattened row-major indexing, consecutive work-items touch consecutive BF16 residual values and contiguous `bo` values within each stream’s N-wide span. It needs little per-item state, has no group barrier, and makes the BF16 conversion explicit at the store. Its costs are integer index reconstruction and four logical `bo` reads across the four stream ranges. Since the spans are aligned and `bo` is only 40 MiB per chunk, repeated accesses could be cache-friendly; without counters there is no basis to claim that the read count becomes four DRAM reads. Retain this as the correctness and timing baseline.

**2D row-by-feature tile with a stream loop.** Map a work-item to `(row, feature)` and have it consume the shared `bo` value once, then update the four residual streams in a fixed stream loop. A work-group such as one row by a feature tile keeps adjacent lanes on adjacent `feature` values; each loop iteration then stores a contiguous segment at `row*D + stream*N + feature`. This reduces launched work-items by four and can reuse the `bo` scalar in a register. It does not reduce the four residual reads or stores, and it repeats the four gate calculations per feature. A sequential stream loop can keep live ranges small; unrolling all four streams may expose more instruction-level parallelism but also keep more gates and residual values live. A mapping with lanes varying over `stream` while holding `feature` fixed would instead stride residual addresses by 5120 bytes and defeat the intended coalescing, so do not treat a 2D range alone as proof of good lane order.

SYCL specifies that the rightmost dimension varies fastest when a multidimensional range is linearized, but subgroup composition and scheduling are implementation-defined. Intel’s 2025.2 guide describes its compiler’s subgroup-to-SIMD mapping as device-dependent and shows contiguous subgroup accesses as the vectorized memory pattern to aim for. Therefore, prefer `(row, feature)` with feature as the rightmost dimension as a design hypothesis, then verify the actual device/compiler subgroup sizes and generated access pattern. The Intel guide’s subgroup-size examples are general guidance, not a guarantee for a particular B570 driver build. [SYCL 2020 specification, §§3.7.2 and 3.11](https://registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html); [Intel oneAPI GPU Optimization Guide 2025.2, “Sub-Groups and SIMD Vectorization”](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2025-2/sub-groups-and-simd-vectorization.html).

**Typed-16 vector stores.** A second axis is to have each item process two or four consecutive features per stream, widen BF16 inputs into FP32 values, perform each residual FMA in FP32, then narrow directly to BF16 output. The values per item must still be distributed so subgroup lanes cover a contiguous feature interval; a scalar loop over adjacent values per item can make lanes access separate, strided segments. Intel’s guide demonstrates subgroup-oriented vector loads/stores and warns that wider vectors can increase register use. For this kernel, alignment is favorable: N and D are divisible by two and four, and the stream starts are multiples of 5120 bytes. But a vector type or packed store is only a source-level intent. Check alignment for every base pointer, compiler lowering, masked tails for non-8192 final chunks, and register/spill data. Keep each element’s conversion after its FP32 combination; never reinterpret the BF16 allocation as an FP32 tensor. [Intel oneAPI GPU Optimization Guide 2025.2, “Sub-Groups and SIMD Vectorization”](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2025-2/sub-groups-and-simd-vectorization.html); [“Optimizing Register Spills”](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2025-2/optimizing-register-spills.html).

## Fusion choices and constraints

**Fuse the producer, `combine`→`write`.** This is a clear storage boundary: the FP32 weighted expert sum plus shared branch becomes BF16 `bo`, then the HC update reads that BF16 value and rounds the residual to BF16. A fused producer can compute the expert sum once for `(row, feature)`, explicitly round/widen it through the same BF16 conversion, then update and store the four streams. That removes the 40 MiB `bo` write and the next kernel’s four logical 40 MiB reads if the intermediate is no longer needed elsewhere. The stream loop preserves contiguous feature stores. The hard part is that `combine` gathers ten routed rows and weights per output feature; fusing this work into an output kernel that also reads and writes four residual streams enlarges the live set, can complicate register allocation, and couples MoE routing/output layout to HC storage. Keep the same order of the ten FP32 FMAs, shared addition, BF16 rounding, and residual FMA if exact BF16 behavior is required. Do not remove the BF16 round-trip as an “optimization”: that would change the value consumed by all four HC streams. Use this as a later candidate only if profiling shows the materialized `bo` path matters.

**Fuse the consumer, `write`→next `norm`.** This is the cleaner initial fusion candidate when there is no intervening residual reader or writer. One work-group per `(row, stream)` can update the 2560 residual values, round each updated value to BF16 locally, reduce its squares in FP32, and then store both the persistent BF16 residual and BF16 normalized activation using the resulting FP32 scale. This preserves the required residual tensor while removing the next kernel’s residual reread and one launch. The current norm uses 256 work-items per `(row, stream)`, ten feature values per work-item, a subgroup reduction, and a small local partial array; a fused kernel can begin from that geometry rather than inventing a new cross-row reduction. It will keep updated values alive through the reduction or recompute them for the final stores. Keeping them live saves arithmetic but raises register pressure; recomputing can reduce registers at the price of repeating gate and FMA work. The exact order matters: first form the residual with the FP32 FMA, narrow to BF16, widen that rounded value for the FP32 norm sum and normalization, then store the same BF16 activation. Normalizing the unrounded FP32 temporary would skip the mandated storage boundary. The source has an existing FP32 `gr_write_norm_rs` fusion precedent, but its FP32 path does not establish correctness or speed for native BF16.

Fusion should be judged as a whole dependency path, not by isolated launch duration. The SYCL fusion study reports that fusion can remove intermediate memory movement, but also describes live-value internalization and register spilling as tradeoffs and finds fusion legality sensitive to work-item mapping. Its prototype has restrictions on fusing kernels with different ND-ranges, which is relevant here because current `write` and `norm` have different decompositions. It is not a Strata or Xe2 performance result. [Pérez et al., “User-driven Online Kernel Fusion for SYCL,” ACM TACO 20(2), 2023](https://doi.org/10.1145/3571284). Intel’s work-group guidance likewise ties work-group/subgroup choice and register use to utilization; neither maximizing work-group size nor fusing by itself guarantees faster execution. [Intel oneAPI GPU Optimization Guide 2025.2, “Thread Mapping and GPU Occupancy”](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2025-2/thread-mapping-and-gpu-occupancy.html).

The target card matters. Intel lists the Arc B570 as Xe2 with 18 Xe-cores, 144 Vector Engines, and 380 GB/s graphics-memory bandwidth. The guide’s architecture table uses B580 as its Xe2-HPG example, with a different core count. Treat its occupancy and subgroup advice as starting points; query the actual device/compiler subgroup support and inspect the compiled kernel before selecting work-group sizes or assuming SIMD16/32 block operations. Product bandwidth is a specification, not achieved kernel bandwidth. [Intel Arc B570 specifications](https://www.intel.com/content/www/us/en/products/sku/241676/intel-arc-b570-graphics/specifications.html).

## Recommended next experiment

Run one owned 8192-row component sweep with identical BF16 inputs, routed-slot table, weights, injection values, and queue ordering. Compare: (A) current flat 1D `write` followed by `norm`; (B) row×feature tiles with a four-stream loop; (C) the same tile with subgroup-contiguous vector-width 2 and 4 stores; and (D) fused write→norm using the current 256-item, 32-lane reduction decomposition where the residual is truly consumed next. Add producer `combine`→`write` fusion only as a separate arm if the component counters show the intermediate path is relevant. First require identical BF16 residual and normalized output bits, identical FP32 row scales or a documented mismatch, finite-value checks, and fault-free queue closure. Then compare paired clean-process timing for the complete producer→write→norm dependency, not just stores. Record actual subgroup width, generated memory instructions, register count/spills, occupancy, memory counters, and toolchain/driver/device versions. No performance winner should be inferred from source structure alone.
