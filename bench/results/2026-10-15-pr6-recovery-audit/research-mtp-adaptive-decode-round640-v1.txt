Question and conclusion

A bounded acceptance/cost controller is a plausible decode candidate for Arc, but this audit cannot claim it will help. The source already supports dynamic verify-window sizes and a drafter-confidence cutoff. It does not currently use observed target acceptance to choose the MTP width. This is a useful distinction: current `--spec-min-p` is an open-loop cutoff on the drafter's own per-token probability; the existing `DraftPolicy` learns accepted tokens and round cost for each observed T, but uses that estimate only to decide whether suffix lookup should replace the MTP window. There is a concrete minimal candidate: select the MTP window cap for the next round using measured `accepted + 1` per-round yield divided by full round wall time per T, with bounded choices, warmup and hysteresis. First compare fixed widths; only implement if same-input measurements show a stable best width varies between workloads and online adaptation beats the best fixed width across the combined workload set.

The supplied first regular-code sample (3,346 emitted tokens at 9.8 tok/s; 2,382 accepted of 2,895 offered = 82.3%) is consistent with strong acceptance for that run, but it is one arm/run and contains no same-workload width sweep. It cannot establish that 4 is optimal, that 2/1 is faster on weaker prose, or that throughput should be adapted. The varied-prose sample is still running; this review neither reads nor predicts it. No strong/weak conclusion is warranted yet.

What “width” means in this tree

`--spec T` and MTP's `max_t_` are verify-window rows, not draft-token count. A T-row verify window includes its target row; it can contain at most T−1 proposals. In a no-suffix MTP4 configuration (`o.spec=4`, absent a smaller `--mtp-max-t` cap), MTP proposes at most 3 drafts. `--mtp-max-t` is a verify-window cap. When suffix drafting is enabled and `--mtp-max-t=0`, startup expands `o.spec` by up to two for lookup windows, then caps the MTP width at the original value; thus the loaded verifier/MTP buffer capacity can exceed `S_mtp`. Keep both actual `o.spec` and `S_mtp` explicit in every arm. Therefore:

| Proposal depth | Verify T | Current MTP4 support |
| --- | ---: | --- |
| 0 proposals in the window | 1 | Yes, as a target-only verify window; MTP still runs afterward to prepare the next proposal chain. |
| 1 proposal | 2 | Yes |
| 2 proposals | 3 | Yes |
| 3 proposals | 4 | Yes; this is the MTP4 ceiling. |
| 4 proposals | 5 | No under MTP4; requires `max_t_ >= 5` and verifier capacity 5. |

A true target-only/no-MTP baseline is `--spec 0` (MTP is ignored/cleared when `--spec < 2`), not a T=1 window inside an MTP-enabled loop. For a matched MTP4 static-cap sweep, pass `--mtp-max-t=4` (which also prevents suffix startup expansion) or set suffix off; otherwise the expanded `o.spec` and `max_t_` alter allocated capacity and graph eligibility. At T=1, the verifier consumes one target row, while `MtpDrafter::draft` is still called after the verify and produces the next chain. `set_max_drafts(0)` is not a “zero draft” control: `draft()` unconditionally executes its first round and emits `drafts[0]`; `max_drafts_` only limits later step graphs. A controller that wants a no-MTP mode must explicitly skip drafter execution and use the ordinary one-token target path; changing this boundary is a distinct candidate from selecting T=1.

Existing variable behavior and state constraints

- `src/program/generate.cpp:6017-6035` (serve) and `:6964-6977` (standalone) already make T dynamic. With `--spec-min-p > 0`, they increase T while the previous chain's stored MTP probabilities meet the threshold. `MtpDrafter::draft` also stops adding later steps when its own prior draft probability falls below `min_p` (`src/core/mtp.cpp:1140-1191`). This can cut work but is not calibrated against target acceptance. Default `spec_min_p=0` keeps the configured MTP cap.
- `strata::spec::DraftPolicy` (`src/spec/draft_policy.cpp:24-103`) already tracks per-T cost EMA and MTP committed-token EMA (`accepted+1`) and estimates lookup yield by match-length bucket. `choose(t_mtp, lookup_k, match)` takes `t_mtp` as given and returns lookup only when expected yield/ms beats that MTP baseline; it does not select among MTP widths. `observe` is called after verify, commit, emission and the subsequent draft; its `round_ms` covers that whole interval. In serve the policy is process-wide and learned over the process; a future adaptive MTP policy must decide deliberately whether its state is per-request, per-workload bucket or process-wide. Mixing regular code/prose, context lengths and normal/coupled sampling can erase useful signal.
- `MtpDrafter::draft(T, ...)` separates catch-up input rows from draft-chain ceiling internally: the round graph catches up T verifier rows, but the later-step loop runs to the loaded `max_t_` / `max_drafts_`, not T (`mtp.cpp:913-992,1140-1191`). Thus after a small verify window it can still generate candidates for a larger next window. This supports adaptive candidate depth without resizing MTP buffers. However the caller currently does not pass `n_drafts`, and outer T selection uses the probability vector only when `spec_min_p` is enabled; any acceptance-driven cap must keep the number of produced drafts and next verify T in sync, including drafts zeroed after early stop.
- Verifier buffers are allocated for loaded maximum T; `Verifier::run` accepts `1 <= T <= max_t_` and lazily captures per-T graphs (`verify.cpp:240-288,1044+,1208+`). MTP allocates scratch by `max_t_`, has per-T round/prefill graph handles plus per-step ordinary/coupled handles, and lazily captures variants as used (`mtp.hpp:145+, mtp.cpp:895-992`). Dynamic choices within the existing cap do not resize the borrowed `Verifier::final_R_all()` or rewrite the MTP K/V state layout. Newly exercised T/step/coupled shapes still create graph executable owners and retain them until retirement/destruction; first-use capture/instantiate/upload time and VRAM must be measured, particularly in the tight full-context case. MTP expert release retires all four decode graph families and lazily recaptures them after restoring expert bytes; it is hard-gated to `max_t_ == 4` (`mtp.cpp:444-470`). A max-T=5/four-draft experiment would not qualify for the current MTP release path.
- The first serve decode window is deliberately T=1 (`generate.cpp` `first_window` path); that produces the first target token and feeds the initial MTP chain. It is startup work, not a sample of a steady-state adaptive T=1 policy. Standalone's first-window path differs: it may call `draft_first(o.spec, ...)` before the loop (`:6937-6944`). Do not compare or pool first-window statistics with steady-state rounds without labeling them.
- On each loop, verifier accepts a prefix `a`, commits `a+1` target rows, emits up to `a+1` outputs (possibly EOS/max-new truncated), updates `p += a+1`, and then drafts the next chain (`generate.cpp:6070-6110`; standalone `:7005-7063`). Rejected/unaccepted speculative rows must not advance the target sequence. MTP's K/V catch-up and generated draft K/V can write positions beyond the committed target prefix; future draft/verify must overwrite/catch up the live positions before reading them. A variable-width policy must preserve this and ensure stale speculative tail rows are never interpreted as accepted state. Do not change commit, output, `p`, sampler history, or target token rules to adapt width.
- Serve restore first restores the target checkpoint/session, then calls `mtp.kv_restore(resume)` for ring KV and sets the current `prompt_len` before reading the resumed prompt (`generate.cpp:5669-5671`). Draft state must remain consistent for new `n`, resumed prefix, prompt reread, session zero, and snapshot RESTORE; an adaptive policy must not checkpoint a width-dependent hidden cursor or reuse a previous request's acceptance state as session state. The first target position and MTP K/V cell alignment (R_i paired with token i+1) remain unchanged.
- At 256K, `max_context`, actual filled target KV, MTP `--mtp-window`/KV mode, host/resident pages and graph memory jointly constrain the request. Source supports the runtime shape abstraction but supplies no full 256K adaptive evidence. In particular, widening to five rows can add Verifier buffers and newly captured MTP/Verifier graphs, while the release-experts helper becomes ineligible above max_t 4. Existing 32K or startup allocation evidence does not clear this memory gate.

Concrete candidate and minimal evidence gate

Do not start with an online controller. First use existing static controls on the same deterministic request to measure no-MTP `--spec 0`, then MTP verify widths 2, 3 and 4 (one, two and three proposal tokens; keep `--spec 4` fixed and set `--mtp-max-t` to the respective width for MTP arms). The first window remains T=1 in every serve arm. Keep model/pack/binary, exact prompt/history, context and actually filled KV mode, expert cache and resident map, CPU pool, sampler/seed, stop/max-new, suffix setting, min-p, coupled mode, and all environment settings fixed. Run regular-code and varied-prose separately, with repeated clean performance samples and the existing correctness/task-quality checks. Do not use debug observer runs as performance runs or cite only acceptance-rate averages.

For diagnosis, retain per-window `(T, a, draft_count, per-position acceptance, MTP probability prefix, round wall, draft wall, verifier/commit wall, CPU route/service)` plus emitted tokens and exact request/source identity. The R624 report's compact MTP4 observer records W/R/D/A/C/E and acceptance aggregates by T but has no per-depth acceptance histogram or full round-ms-by-T series; the observer v1 artifact is unapplied, and its proposal must not be treated as current runtime evidence. `DraftPolicy` internally has MTP yield/cost EMAs but does not expose a per-T receipt. If the fixed sweep supports adaptation, add the smallest bounded counters needed for calibration; use separate owned processes/runs, no same-process environment arm switching.

Then use only a short fixed candidate set such as T={2,3,4} for MTP4, plus an explicit no-draft mode only if true MTP-off is in scope. A controller can choose the next verification width from measured expected committed tokens per full-round millisecond, with minimum observations per T, warmup, hysteresis, a decay/reset policy at request/workload boundaries and a hard configured cap. Reuse of `DraftPolicy`'s EMA is a promising code-level starting point, but its present pre-prior (`1 + 0.7*(t-1)` tokens and shape-scaled cost), lookup comparison and process-global lifetime should not be silently reused as a validated MTP policy. Compare adaptive against both best fixed width and fixed MTP4 on the same complete workload mix. Acceptance alone is not the objective: target verification cost, CPU expert service/rows, sequential MTP graph steps, cache hits, committed/emitted tokens and total decode wall all change with T.

Retain exact target sampling behavior for both normal and `STRATA_SPEC_COUPLED=1` paths. Check deterministic target-only versus spec compatibility under the project's existing equality/numerical/quality gates, and ensure the controller never consumes rejected draft rows. Include token-zero/first-window, EOS and max-new truncation, forced rejection, accepted-prefix rewind, increasing and decreasing width, reuse after a second request, checkpoint restore/resume, `STRATA_CKPT_REREAD`, snapshot save/restore, ring and full KV modes, max-context boundary and genuinely filled 256K. Keep current adaptive expert-cache residency fixed during this first comparison so cache changes do not alter targets/acceptance independently. Main owns any implementation and all build/test/GPU measurements.

External primary references and transfer limits

- EAGLE-2's paper says draft-token acceptance is context-dependent and its calibrated draft confidence can guide a dynamic tree: [arXiv paper](https://arxiv.org/abs/2406.16858). It is evidence for the general confidence premise in EAGLE, not proof that this MTP head's logits estimate target acceptance.
- Current vLLM docs describe adaptive verification for model drafters including MTP. They use per-position survival estimates from a confidence head or an online logistic estimator recalibrated against target verification, combined with a measured shape-cost budget ([vLLM adaptive verification](https://github.com/vllm-project/vllm/blob/main/docs/features/speculative_decoding/adaptive_verification.md)). This is the closest concrete algorithmic analogue. Its global batch scheduling, captured-graph, device-decided query-length and CUDA assumptions do not transfer directly to this single-stream Arc/SYCL target; the transferable part is calibrated survival plus measured cost, not its GPU budget implementation.
- SGLang's current adaptive-drafting documentation uses accepted length EMA, warmup, update interval, hysteresis and prebuilt runtime/graph tiers, but limits the documented feature to EAGLE/EAGLE3 with top-k 1 ([SGLang adaptive speculative decoding](https://github.com/sgl-project/sglang/blob/main/docs/docs/advanced_features/adaptive_speculative_decoding.mdx)). Transfer the conservative controller pattern only; the algorithm itself is not an Arc MTP implementation.
- llama.cpp documents MTP and `p_min`/maximum draft controls and recommends end-to-end benchmark comparison ([llama.cpp speculative decoding](https://github.com/ggml-org/llama.cpp/blob/master/docs/speculative.md)). These controls illustrate fixed cap/probability-threshold behavior; they do not establish acceptance-driven adaptation in Strata. Its Qwen3.8 256K community report shows a sharply non-monotonic MTP depth curve and reports higher-context graph-memory cliffs on a different NVIDIA/llama.cpp stack ([personal 256K write-up](https://piszczek.pl/blog/qwen38-27b-256k-50-tps-24gb-gpu); [thread and reported measurements](https://github.com/ggml-org/llama.cpp/discussions/27290)). Treat that as motivation to measure each Arc shape and memory margin, not as a performance prediction.
