# R766 — Register live ranges, rematerialization, and DPAS tile resources

2026-10-16 JST. Bounded, read-only literature and retained-report review. This is the only file written. No source/product edit, build, test, GPU/runtime/profiler/device query, process inspection, environment/service change, Git operation, cleanup, or XeStrata material was used. Public sources below are cited for their findings only; no code was copied or adapted.

## New finding

The useful tuning target is a compiled resource threshold on the actual hot kernel, not the smallest source-level SLM sum or register count. Intel’s SYCL guide recommends moving loads closer to their uses, shortening live ranges, selectively recomputing cheap values, and checking loop-unroll factors: unrolling can expose instruction scheduling but also keep more temporaries live and spill. For a tiled DPAS kernel, an extra in-flight tile can hide load latency, but also holds more matrix fragments/accumulators and staged data concurrently. Whether overlap wins therefore depends on the compiler’s resulting SIMD/GRF/spill/SLM allocation and the measured dependent phase, not the source tile request alone. The final software-pipeline sentence is a resource-based inference, not a measured Xe2 result. [Intel, *Optimizing Register Spills*](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2025-0/optimizing-register-spills.html)

Two public measurements illustrate why a lower resource number is not automatically higher throughput:

- Intel Advisor’s QuickSilver example on a Data Center GPU Max 1550 reports the first kernel call falling from 9.003 s to 6.030 s after reducing SIMD width 32→16; the guide then reports 1,408 B of spills disappearing and 5.763 s after enabling large GRF mode. This is a useful counterexample to “wider SIMD always wins,” but it is one documented kernel/sample on Max 1550, not Arc B570 evidence or a repeatable benchmark. [Intel Advisor cookbook](https://www.intel.com/content/www/us/en/docs/advisor/cookbook/2024-2/use-gpu-roofline-to-identify-optimization.html)
- AMD’s MI200/ROCm 5.4 LBM example reports 102 VGPRs, four waves/SIMD, and no spills. Replacing `pow(x,2)` with `x*x` reduced usage to 100 but did not change occupancy; moving an independent store earlier reduced it to 96 and crossed the documented threshold to five waves/SIMD. The example shows that a small reduction can have no residency effect until it crosses a hardware allocation boundary. Its VGPR thresholds do not transfer to Xe2. [Fanfarillo and Curtis, AMD GPUOpen lab notes](https://gpuopen.com/learn/amd-lab-notes/amd-lab-notes-register-pressure-readme/)

## DPAS, SLM reuse, and limits

Intel’s XMX guide says one subgroup can issue multiple DPAS operations and shows blocking across M/N/K (256×256×32 outer tiles, 64×32×32 per subgroup); its example favors large GRF for that GEMM. That supports testing a small tile/pipeline-depth matrix when the kernel is underfeeding XMX, but not importing those PVC dimensions or GRF settings to Xe2. Intel’s GRF guide explains the trade: on Data Center GPU Max, small mode exposes 8 threads/XVE and large mode 4, and its unroll-off/on cases favor different modes. The command-line mode is documented for PVC, not as a B570 control. [Intel, *Programming Intel XMX Using SYCL Joint Matrix*](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2025-0/programming-intel-xmx-using-sycl-joint-matrix.html); [Intel, *Small Register Mode vs. Large Register Mode*](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2025-0/small-register-mode-vs-large-register-mode.html)

SLM pays when a work-group reuses staged data enough to offset load/setup and barrier costs. Intel’s guide gives a bank-conflict example with 1/16 of nominal bank bandwidth and notes barrier cost grows with group size; these are programming-model examples, not B570 measurements. SLM is work-group scoped and device limits vary. A smaller request can enable another resident group only if SLM was the active residency limit; it does not remove a GRF/SIMD limit, improve a memory-bound access pattern, or prove additional active work. Conversely, shrinking a tile can duplicate loads and barriers. [Intel, *Shared Local Memory*](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2025-0/shared-local-memory.html)

## Application to the retained QSA evidence

The retained baseline is JIT SIMD16/128 GRFs. The source’s local arrays request 44,500 B; the runtime/UR local-argument request is 44,496 B. The compiler’s separate static SLM field is 4,096 B, so none of those values is itself an occupancy result. The pending heads8 source estimates 31,092 B per group but remains uncompiled and untested. Prior R747/R749 review already found that heads8 keeps the same source DPAS count while splitting work across two groups and duplicating K/V gathering and group barriers; this report does not restate its geometry as a speedup proposal. Lower per-group SLM could help only if it changes a real residency/pressure threshold and the extra duplicated work does not cost more.

This also resolves the “rematerialize cheap values” question narrowly: shortening a scale/index/predicate lifetime or recomputing it can be useful if compiler output shows a spill or threshold-sensitive register pressure. It is not useful merely because the expression is cheap; recomputation can add instructions, dependencies, or reduce reuse. Neither current QSA receipt nor the pending source estimate proves that registers or SLM cap active work.

After Main closes its current measurement boundary, compare the existing baseline prompt-attention kernel with the already reviewed heads8 candidate on the same fixed QSA input and B570/runtime. Hold mode, Direct path, matrix types, K/V contents, cell cap, queues, and all other settings constant. First record exact JIT SIMD, GRFs, spill/private-memory bytes if reported, static SLM, local-argument request, group size, and barriers; keep static SLM and UR argument requests as separate fields. Run a short fixed-input component timing with alternating clean-process arms and exact output/guard comparison. If available counters are still blocked, report occupancy as unknown rather than deriving it from the byte delta. Only if the component completes correctly and improves its whole-kernel time, do a clean, same-workload long-prefill screen (78,452 batched rows, 48 layers, C8192, FP32 residual/GPU32768) with separate clean processes; compare full-prefill throughput and faults, not just QSA time. Keep diagnostic/validation runs separate from speed samples. Reject the candidate if lower source/requested SLM does not survive compilation, if duplicated K/V/barrier cost erases the kernel gain, or if the full phase regresses. This screen is not the 600/1000 tok/s milestone and does not replace physical 262,144-context correctness before adoption.
