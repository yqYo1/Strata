## Why strict qualification is held

Pinned official [`QueryKernelCommandMetrics`, lines 2274–2313](https://github.com/intel/pti-gpu/blob/6c0d6b0b80c6dbac4b5902d9d5ade1c75b9e9033/tools/unitrace/src/levelzero/ze_collector.h#L2274) drops a failed first `zetMetricQueryGetData`/empty-size outcome without reporting its numeric status. The second call's return status is assigned but **not checked** before retaining the buffer when its size is unchanged. A CSV row or exit zero therefore cannot prove every internal metric API succeeded. The offline decoder cannot reconstruct an unreported status. Lines 2590–2635 emit a generic calculate-metrics warning on decode failure without the exact status. The per-sample output loop also assigns, rather than appends, the row string, losing earlier rows if `num_samples>1`; the proposed parser rejects any sample index other than 0 and requires exact per-kernel dispatch counts, but that is not general multi-device qualification.

These are source findings, not observed failures on this host. The controller preserves every emitted native/API/validation message byte-for-byte and rejects warnings/errors, missing rows and unknown files, but it explicitly cannot meet the stronger requirement to preserve **every internal API error**. Main was notified through Orca before completion. No unauthorized collector patch/build, undocumented control or trace was added. A separate Main-reviewed solution for exact status observation is the unresolved qualification gate; no manifest boolean, diagnostic success, root/sysctl change or model run resolves it in this package.
