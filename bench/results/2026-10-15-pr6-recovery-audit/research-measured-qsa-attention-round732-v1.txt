## Current kernel path and exact shape bounds

At HEAD the mode dispatch in `src/kernels/sycl/prompt_attention.cpp:344-405` identifies mode 1 from INT8 K and V pools, uses `KG=VG=4` scales, and chooses the Direct specialization when the fixed process environment value starts with `1`. The caller is `src/prefill/prefill.cpp:2400-2427`; its `matrix_used` boolean is the actual admission result, with fallback to decode attention if refused. The profile's recorded runtime route/call counts should be checked alongside the finer profile before attributing these intervals to the matrix kernel.

Current QSA geometry from `include/strata/kernels/qsa.hpp:110-145,279-346` is 24 query heads, 2 KV heads, head dimension 256, page size 4, index top-k 2,048 and selection granule 4. Thus the maximum selected width/cap is `2048 + 4 - 1 = 2051`. For each query at context position `p`, the width is `min(p+1,2051)`. With 78,453 prompt positions starting at zero, the source-derived total is 158,804,828 selected query-cell visits per QSA layer; nearly all later positions are at the 2,051 cap. The model's 12 QSA layers and 10 chunks per layer give 120 observed coarse QSA intervals. `qsa_prompt_attn_batch` launches one work-group per (query, KV head), so an 8,192-query chunk has at most 16,384 groups, each with 65 CH=32 loop iterations at the cap. These are source-derived workload counts, not fine-profile kernel counts or timings.

Per selected query-cell, the mode-1 source requests 256 INT8 K bytes + 256 INT8 V bytes + four FP16 K scales + four FP16 V scales (1,056 logical bytes across the two KV heads). Applying that to the source-derived widths gives 167,697,898,368 bytes (156.1 GiB) per layer and approximately 2.01 TB (1.83 TiB) across 12 QSA layers. This is the requested source payload; page indirection, cache reuse, sectors/transactions, bytes reaching memory, and staging copies are not measured by this arithmetic. It is not an observed bandwidth.

The matrix work per selected cell is bounded from the active source shape: 12 query heads × 256 dimensions × K/V products, with hi/lo FP16 decomposition for Q and probabilities, i.e. approximately 12,288 multiply-adds (24,576 floating operations if counting an FMA as two operations) per selected query-cell across both KV heads. At the source-derived selected widths this is approximately 23.4 trillion multiply-adds (46.8 TFLOP by the same convention) across the full 12-layer prompt. This is arithmetic implied by the algorithm and workload shape, not a measured instruction count, achieved throughput, or roofline. The Direct=1 path uses `final[1]` local floats versus `final[16*HD]` for non-Direct, while retaining the same attention math; no new local-output tiling is implied by that flag.

At each capped query/KV-head work-group, the kernel performs 65 serial CH=32 loop passes over at most 2,051 selected cells. It has a 16-KiB `kv` local tile (`CH*HD` halfs), plus mode-specific local query/probability/score/scale state. Matrix admission checks subgroup 16, a device-local-memory lower bound, work-group size and an FP16/FP32 joint-matrix combination. That check does not establish compiler registers, spills, actual allocated SLM, resident groups or occupancy. No device bandwidth or instruction roofline can be inferred from the source or coarse profile.

## Candidate decision and gates

The only untested own attention mapping candidate that remains concrete from R725 is a mode-1 K-only cell-major cooperative gather: adjacent lanes read adjacent dimensions from one selected row, then cooperatively transpose into the existing logical `[dimension, cell]` K tile consumed by joint-matrix loads. Keep current V gather, scales, row IDs, selection, CH=32, WG=128, Direct=1, matrix work, output and arithmetic fixed. This may improve contiguous K source ownership, but sparse row resolution remains and the transpose may increase local-memory conflicts, barriers or register/SLM cost. The current V gather is already cell-major and contiguous. No tiling reuse, query-head regrouping, double buffering or arithmetic change is justified before the finer component evidence; these carry duplicated traffic or resource risks and cannot be ranked from the coarse QSA interval.

The precise existing component fixture is `src/kernels/qsa_prompt_attn_parity.cpp` (SHA-256 `7a9d1dc41c12854a5c4536dcbe347a95544b29f880339c7f5fdaa8ba47e833c2`), wired as `qsa_prompt_attn_parity` by the existing build. Its INT8 format covers the widest 2,051 selection, selected recent/older cells, page-table indirection and compares output against the prior prompt path and FP64 reference. For a lane-remap comparison, extend/use this fixture with explicit all-256-dimension and all-32-slot coverage, a partial final chunk, invalid-row zero fill, and exact same pools/IDs/steps/page table, with mode 1 and Direct=1 fixed before process/runtime creation. Require parity at existing tolerances and prove identical logical K operands and unchanged scale application before any model run.

Before implementation, wait for the already-pending fine profile and require actual mode, Direct route, matrix-vs-fallback counts, query/chunk shapes, selected-width histogram, and separated attention versus KV staging evidence. To admit the K-only mapping trial, require Direct-path evidence of poor K-load sector efficiency or material K-gather service; then inspect compiled load/store lowering, global sectors/cache behavior, local-memory bank conflicts, barriers, registers, spills, SLM allocation and active work-groups. Reject the mapping if its source-load improvement is absent or local transpose/resources lower occupancy or raise service cost. These are gates for evidence, not measurements already collected.

After component parity/resource gates, use a matched own-engine component profile first, then the fixed 78,453-token / C8192 / R32768 / FP32 / K8V8 / Direct1 model route with the existing selection and fault/quality/RESTORE/262,144-context qualifications. The current R730 instruction to defer extra residual-prefix experiments until the closed R32768 profile is respected; this report recommends no concurrent change to Main's run or settings. Do not interpret the one instrumented wrapper result as a clean speed baseline or call the kernel a bottleneck until the finer profile closes.
