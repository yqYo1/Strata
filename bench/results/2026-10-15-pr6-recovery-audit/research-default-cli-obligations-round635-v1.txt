## Finding

Current `origin/main` (`beddab2fd6b61631d73b39b7484bc9a585ebe1de`) is an ancestor of current `feature/sycl` (`4c89454f147693982a45aceebd033681b19d797f`), but ancestry does not make the engine/API trees functionally equivalent. Current root CMake declares project/engine version 0.1.38; `origin/main` declares 0.1.39. The current build's actual SYCL resolver compiles the root `src/program/generate.cpp` into `strata`, via `cmake/sycl_backend.cmake`; it does not compile the main branch's engine instead, and it does not use the historical `sycl/src/program/generate.cpp` experimental subproject. Thus the service can expose 0.1.39-era controls that have no implementation in the current native SYCL engine.

The concrete functional blockers are (a) multi-request batch protocol and (b) elastic VRAM runtime control. The current service files are byte-identical to `origin/main` for `serve/server.py`, `serve/responses.py`, `serve/runconfig.py`, and the focused Responses/runconfig/parallel/VRAM tests. The service features therefore exist, but the current engine does not satisfy every engine contract they call. The older R447 report correctly identified these dependency clusters, but its claim that the dedicated Responses/runconfig paths were absent no longer describes the current tree; they now exist and match `origin/main`.

## Resolver and engine boundary

- Top-level `CMakeLists.txt` is integrated for this fork and declares `project(strata VERSION 0.1.38 ...)`, defines `STRATA_VERSION`, and when `STRATA_ENABLE_SYCL=ON` includes `cmake/sycl_backend.cmake`.
- `cmake/sycl_backend.cmake` creates `add_executable(strata src/program/generate.cpp)` and links the native `strata_prefill` and `strata_spec` targets. This is the current shipping engine entrypoint for the SYCL setup adapter.
- `tools/setup_intel.py:build_commands()` selects `STRATA_ENABLE_SYCL=ON` and builds target `strata`; its `cli_flags()` inventories flags from root `src/program/generate.cpp`, and `validate_config()` refuses unsupported configured flags. It separately refuses `parallel > 1` while the native generator source lacks the BGEN port. This is useful setup-time protection, not a substitute for the runtime server/engine protocol.
- `serve/server.py` is shared with main and starts the configured engine from the config, builds CLI arguments, and implements request/API wrappers. It does not select an alternate SYCL-specific server. Its config path can therefore request service features whose engine side must either exist or be explicitly rejected.

This matches AGENTS' requirement to trace the configured SYCL build's real source resolver and keep shared CLI/API obligations distinct from engine imports. CUDA/HIP code is neither needed nor proposed below.

## Non-inference work already present versus still open

The R447 inventory is the feature inventory, not a present-tense absence list. Current `serve/` contains `responses.py`, `runconfig.py`, `test_responses.py`, `test_runconfig.py`, `test_parallel.py`, `test_vram.py`, and UI routes for Responses, settings and parallel/VRAM status; these key files compare byte-for-byte equal to `origin/main`. In other words, they are already imported at the service boundary. The unresolved gap is contract mismatch with the actual native engine, particularly because identical wrappers still emit engine flags/protocol that the current C++ target lacks.

Main's `serve/server.py` reports optional `effort_position=end` as requiring `--tail-role-token`; current generator has the parser and checkpoint call, so this is an example where an old version number masks already-present behavior. Conversely, the batch wrapper's matching implementation is not proof that BGEN is supported: exact root parser and serve loop show the engine does not have that command language. The VRAM endpoint is mounted but gets a valid `ERR expected GEN...` response from the engine instead of a `VRAM ...` response, while a startup `vram_elastic=true` config attempts to start an engine with an unknown argument.

R447 also listed setup compatibility, docs, status/metrics, session parking/restore, draft/profile tools, and error diagnostics. This round does not classify all of those as integrated by file presence. The setup files differ from main, and shared docs are adapted for SYCL. For promotion, reuse R447's per-feature tests and compare current setup/config behavior to the engine's true supported flags. The two concrete engine mismatches above can be fixed without replacing prefill, decode, CPU, QSA, expert cache arithmetic, or other pinned benchmark source.

## Decision for the next default boundary

Do not use ancestry-only merge or the shared service files as evidence that current `feature/sycl` can replace `main` for all advertised settings. Before changing the fork's default, Main should choose one of two reviewable outcomes for each contract:

1. implement/test complete SYCL behavior; or
2. reject/disable the feature in SYCL's server, setup/config conversion and user-facing capability metadata, while retaining supported shared APIs and truthful error behavior.

At minimum, close the batch wrapper/native-protocol mismatch and the separate `vram_elastic` config conversion/API mismatch. Also rerun the focused Responses/runconfig/parallel/VRAM tests against mocks plus the configured engine's supported-options/protocol tests; a mock-only pass is not enough to declare the engine contracts supported. Keep CUDA/HIP implementation and validation outside this work.
