# v2 source lifetime and input audit

No concrete new undefined behavior was established in the reviewed v2 driver and fixture. This is source reasoning, not runtime qualification or exoneration of its linked kernels/runtime.

- In-order queue orders dequant, GEMM and memcpy operations without missing cross-queue dependencies in this file. oneMKL arguments have row-major A=ne by k, B=n by k with transposed B, C=ne by n, valid leading dimensions k/k/n. GU oracle interleaves each gate/up row to match n=2*rows; Down n=rows.
- Seven allocations fit the registry reserved for eight. Guard bases and host staging are heap-owned, and Runtime has deleted destructor. Successful drains precede frees. Exceptions call _Exit without unwinding device owners/staging or freeing unknown-completion allocations. Allocation-failure leaks are intentionally process-exit scoped. The async handler captures the intentionally retained Runtime and uses a sticky fault plus synchronized first exception.
- Every Guard payload and guard is byte-initialized before upload; packed w/u and x/reference payloads are then fully populated. Dense/y/expected poison initialization is intentional, overwritten before their relevant correctness reads; in dequant mode y/expected remain poison and are compared only as bytes. 0xa5a5a5a5 represents a finite float on this platform; no uninitialized C++ object reads were identified. Reference and candidate GEMMs use beta=0, so no prior C payload is required by the BLAS contract.
- Device USM is never host-dereferenced. Staging downloads drain before host reads. Cold verification precedes warmup; all trial work drains before later downloads/frees. Success-path queue deletion follows a drain and USM retirement. The asynchronous handler is noexcept and survives teardown because its owner is retained.
- Product type conversion/half storage follows the existing uint16_t device-payload convention; full strict-aliasing/device-library qualification is not proven by this local audit. Linked kernel indexing, provider teardown and implementation internals need their own source/stack evidence. No driver blame is inferred from an empty stderr or later reset.
