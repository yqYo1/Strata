# R637 v2 — bounded wave scratch の region alias と同時生存 owner

2026-10-15 JST。R637 v1のQSA selection width転記を訂正し、`qsa_real_shapes()`、SYCL attention scratch式、現layer-major admission、`Prefill::carve`の全三scratch branches、compact/MMQ/fused dispatchを読み直してsource計算した。読み取り専用。source/build/test、GPU、process、Git、cleanup、benchmark rawは操作していない。v1は書き換えず、訂正版の本報告のみ新規作成。

## v1の訂正

v1の `cap=32771`、`sel_ids≈1 GiB`、`m.region≈1.644 GB` というQSA算術は誤りであり、取り消す。実source `qsa_real_shapes()` は `idx_top_k=2048`, `idx_block=4`; `qsa_selection_width(kTopkMaxCells,s)=min(32768,2048+4-1)=2051`。`sel_ids` bytes/rowは従って `2051*4=8204` である。正しいsource-counted `m.region_bytes` はC=4096で607,128,320 B、C=8192で1,180,698,624 B。v1の値を根拠にしない。Mainが提出後に冒頭の値を本表のmaxと一致させた。

## 結論

**R633のretained subtotal全体を別々の新allocationとして足す必要はないが、既存`m.region`をwave bufferのfree arenaと見なすこともできない。** `carve`はGDN/QSA/MoEの三branchを各々countし、最大枝一つのregionを確保し、三者のpointer配置を同じbaseへ重ねる。一chunk pathはattention後にMoEを実行するため成立する。wave causal prepass中は、先行chunkから保持したprepared inputs/routesと、現在chunkのQSA/GDN scratchが同時liveになる。MoE work中もwave Dmとexpert microbatch scratchが同時liveとなる。従って旧region内の全bytesを保持データに流用できる時点は、該当scratchの最後のdevice/copy queue accessがchecked drainされた後であり、次chunkのQSA/GDN中ではない。

現geometryではC=4096時はQSA branchが最大でregionは607,128,320 B (約579 MiB)、C=8192時はGDN branchが最大で1,180,698,624 B (約1.099 GiB)。wave全体のexact-order FP32 DmだけでC4096×2は800 MiB、C8192×2は1.5625 GiB、両×4は1.5625/3.125 GiBとなり、**Dm単体でも既存regionより大きい**。microbatch scratchやwaveの他planeも同時に要る。regionをW-rowに再carveし、既存C-row planeとの差だけをnew bytesとして計上する方式や別ownerへの集約は可能な設計案だが、実際の同時live capacityはそのpeak sumで再計算する必要がある。

sourceから`region`の割当容量・overlaid pointer geometryは計算できる。GPU allocatorのlive free、既存ownerとのfree overlap、fragmentation/headroom、wave allocation fit、性能は未測定で、ここからfree VRAMやadmission successは結論しない。

## 現行admissionとdispatchを固定

`run_layer_major`は`n<=262144`, `T=m.T<=8192`, `N=2560`, `HC=4`, `D=10240`, `K=10`, `NE=512`, `n_ff=640`、single GPU、`m.copy==m.cs`、native source、明示`STRATA_PREFILL_MMQ=0`、`!mmq_plan().any`, `m.compact_moe_fp16`, full-model admissionを要求する。`compact_moe_fp16()`は`STRATA_PREFILL_MOE_COMPACT_FP16=1`、MMQ fallback/no `mp.any`、native format geometry、`STRATA_DBG_NAN`なしを必要とする。このadmission内では`mp.fallback=true`, `fp16_moe_rows(T)=T`, `moe_bufs={T*1280,T*640,0,0}`。`fused_layout`には`mmq_plan().any`が必要なので、ここでは`STRATA_PF_FUSED`やring設定に関わらずfalse。よってMMQ group/fusedの小さいworkspace branchではなく、compact FP16 fallback branchを数える。

QSA shapeは`qsa_real_shapes()`の`idx_top_k=2048`,`idx_block=4`,`n_head=24`,`idx_dim=128`; layer-majorは`cap=2051`。最大session context262,144の`max_blocks=262144/4+2=65,538`。`sel_batch=256`,`attn_batch=32`。SYCL split-attention scratchは`ceil(cap/64)*n_head*(HD+2)+64` floats: `ceil(2051/64)=33`, `33*24*258+64=204,400` floats。これにattn_batchと4 bytes/floatを掛けるので26,163,200 bytesである。

## Count-only allocator padding

`Alloc::take<T>(n)`はpayload `x=n*sizeof(T)`に対して `((x+256+255)&~255ull)` bytesをcountする。これは`x`を単に+511するのではなく、256-byte boundaryへ切り下げた式で、paddingは256..511 bytes。今回のC=4096/8192の全配列payloadは256-byte alignedになるため、**各takeはpayload+256 bytes**。GDN 8 items、QSA 11 items、compact fallback MoE 14 itemsとして枝別padを加えた。下記はcount-only source arithmeticである。

### GDN branch

source `gdn_set_bytes` operandsは `T*C`, `T*ZV`, `T*2*HV`, `T*HV`, `T*HV`, `T*C`, `T*ZV` floatsと`T*ZV` uint16。`C=10240`, `ZV=6144`, `HV=48`なので32,960 floats + 6,144 uint16 = 144,128 payload bytes/row + 8×256 padding:

| Chunk T | Payload | Padding | `gdn_set_bytes(T)` |
|---:|---:|---:|---:|
| 4,096 | 590,348,288 B | 2,048 B | 590,350,336 B |
| 8,192 | 1,180,696,576 B | 2,048 B | 1,180,698,624 B |

### QSA branch

source `qsa_set_bytes` arrays per row: `Kc,Vc` each 512 floats; `Qf` 12,288 floats; `q` 6,144 floats; `idx_raw` 128 floats; `q_idx` 512 floats; `attn` 6,144 floats; `attn_h` 6,144 uint16; `sel_ids` 2,051 int32. This totals 125,452 payload bytes/row. Fixed-context arrays are `sel_scores=256*65,538*4=67,110,912 B` and `attn_scratch=32*204,400*4=26,163,200 B`, total fixed 93,274,112 B. ## Wave Dm and retained-plane arithmetic

For wave rows `W=min(q*T, rows_remaining)`, exact combine-slot output requires `Dm=W*K*N*4=102,400*W` bytes. Current carve already has C-row `Dm`; `mixed_h` (FP16, 5,120 B/row), shared FP32 (10,240), `sg` (4), FFN HC injection `inj` (16), and route data/mapping also have chunk-sized storage, though most MoE arrays are inside `m.region` aliases. R633's conservative four 32-bit route arrays cost 160 B/row. Thus its gross retained subtotal remains 117,940*W bytes for Dm + mixed_h + shared/gate + inj + four route arrays. This subtotal is not the allocation delta: at minimum subtract existing C-row capacities and count the change in peak region/standalone layout; do not double-charge the first chunk's buffers.

| Chunk C | q | W max rows | Dm wave | existing Dm C-row | Dm growth | R633 gross retained subtotal |
|---:|---:|---:|---:|---:|---:|---:|
| 4,096 | 2 | 8,192 | 838,860,800 B (800 MiB) | 419,430,400 B | 419,430,400 B | 966,164,480 B (0.900 GiB) |
| 4,096 | 4 | 16,384 | 1,677,721,600 B (1.5625 GiB) | 400 MiB | 1,258,291,200 B | 1,932,328,960 B (1.800 GiB) |
| 8,192 | 2 | 16,384 | 1,677,721,600 B (1.5625 GiB) | 800 MiB | 838,860,800 B | 1,932,328,960 B (1.800 GiB) |
| 8,192 | 4 | 32,768 | 3,355,443,200 B (3.125 GiB) | 800 MiB | 2,516,582,400 B | 3,864,657,920 B (3.600 GiB) |

Dm alone exceeds the whole source-counted `m.region` in every row. Exact Dm overage above that region (before microbatch or other wave planes): C4096×2 =231,732,480 B; C4096×4=1,070,593,280 B; C8192×2=497,022,976 B; C8192×4=2,174,744,576 B. Those are comparisons of capacity, not runtime fit. The active MoE microbatch scratch must be added to Dm at expert time; during causal prepass the QSA/GDN scratch and retained earlier rows coexist.

At n=262,144, bounded wave payload is set by q*C, not by full n. The existing FP32 interlayer residual plan is already `n*D*4=10,737,418,240 B` (10 GiB), partitioned between device and host; it is not extra wave headroom. An independent post-attention FP32 R plane would cost `40,960*W`: 320/640/640/1,280 MiB across the four table rows. This can be avoided only under an explicit in-place row lifecycle that overwrites an input row after its last read and reloads the post-attention value for delayed FFN write. Without that proof, retain the R plane in the checked wave plan.

## Reusable workspaces and unavoidable overlap

- `m.region` is one allocation with three same-base layouts, not three scratch sets and not a lease-free arena. During a successful ordinary chunk, GDN or QSA runs first and compact FP16 MoE after; their internal scratch phases can alias. Wave retention changes that phase graph. A host phase label is not a fence: current layer-major requires `m.copy==m.cs`; before alias reuse, checked synchronization must prove all prior queue readers/writers finished. On failure/drain error, owners stay live and the wave is invalid.
- Existing C-row buffers can be grown/re-laid as W-row wave owners; their first-C capacities reduce incremental bytes. Since most of those buffers are aliases inside region, they cannot all be treated as independently live storage while retaining current QSA layout. Recompute full peak overlap for the new carve; use a few explicit owners if clearer than an expanded region.
- Current compact expert dequant pair is outside `m.region`: `dq_gu` is `1280*2560*2=6,553,600 B`, `dq_d` is `2560*640*2=3,276,800 B`, total 9,830,400 B per pair; `DQ=2` reserves two alternating pairs (19,660,800 B). Serial expert-wave execution can reuse them. `B<=C` microbatch scratch can stay bounded at `Xs=B*N*2`, `GU=B*1280*4`, `Hh=B*640*2`; split an expert's W refs into B-row tiles while keeping output row offsets into W-sized Dm. A two-expert concurrent pipeline would need additional decoded pairs and independently proven queues.
- `Rstore` existing capacity is not automatically disposable. In-place per-row reuse may avoid a separate R plane only after all input consumers finish; the current residual callback runs only after the complete chunk's FFN and final HC write. Wave code would need an earlier private row-store boundary with its own validation.
- Keep exact router IDs/weights and mapping needed for slot-order `moe_combine`. The four route arrays are a conservative 160 B/row; an equivalent compact map/reconstruction is possible but is a separate CPU bookkeeping design. Do not change combine order as a storage shortcut in this audit.
- MTP `on_chunk` sees final model FP32 residuals after queue sync; `on_stage_chunk` is gated to final request completion in this full-model route. MTP/draft state must not run at the causal prepass boundary because GDN/QSA/PLE may already be advanced while FFN output/residual is unfinished. After all wave products, unchanged combine and HC writes complete, deliver `on_chunk` in original position order; reload each final C-row block from committed residual store as needed. Stage/checkpoint callback remains at the coherent request boundary. Count any persistent callback workspace separately; existing report owner studies do not show that it is concurrently free.

## Admission boundary and evidence limits

Current layer-major setup reserves 512 MiB GPU headroom and 8 GiB host headroom for the known cache/residual/optional observations. Any wave plan must checked-add the incremental or separately-owned wave buffers before GDN/QSA/PLE state advances, including overlap with the selected phase scratch and active expert/cache allocations. Full-context residual 10 GiB, QSA session/KV stage, model weights and existing 32 MiB GEMM scratch/workspace remain other owners. R594/R599's 1,662,831,872 B `Impl::owned` is retained owner accounting, not free memory; no safe retirement is inferred here.

No GPU query or allocation test was run. Source branch byte counts are not live-free VRAM. Region arithmetic does not prove full-context admission, actual co-liveness implementation, host availability, allocator success or speed.
