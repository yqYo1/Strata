# R740 — QSA threshold count-round mapping

2026-10-16 JST. Read-only source and evidence review in the own Strata fork. Only this report was written. No source edits, build, test, process, service, GPU, environment, cleanup, or Git mutation was performed. Existing worktree changes were left untouched. The prohibited credential record was not opened. No XeStrata implementation source was inspected or used.

## Decision

This is a distinct, source-plausible experiment: in only the 32 threshold-count rounds in `qsa_block_topk`, assign score indices cyclically (`b=t; b<nb+1; b+=256`) instead of giving each work-item its current contiguous interval. It preserves the count, key transform, threshold decisions and collectives in exact integer arithmetic, while making each loop iteration's active local IDs address consecutive score keys. That is a source-address improvement hypothesis, not proof of coalescing or reduced memory transactions. The final greater/equal passes, exclusive scans, and ascending-ID emission must continue using the current contiguous `[lo,hi)` partition.

A focused component comparison is meaningful alongside the source-only radix4 candidate because it tests a different lever: address layout with all 32 threshold rounds/reductions retained, versus fewer radix rounds with histogram/reduction overhead. The two candidates are not redundant; neither can be assumed faster. Compare baseline, cyclic-count, and the independent radix4 proposal on the same pinned scores and exact build/device, with identical output checks and per-kernel timings. If only one candidate is affordable, prioritize a count-mapping arm only if compiled transaction data or selector service indicates the repeated threshold score reads are costly. Keep source-only status distinct from component performance and full-prefill qualification. No implementation or measurement is recommended from this review alone.

## Source and prior screening

The audited file hash matches `src/kernels/sycl/qsa_select.cpp` SHA-256 `45084756ca5e8e36085dae46581049c81366a45cdfde23e8c6f38defbba0c809` (the R731/R738 immutable source pin). In the top-k kernel, `chunk=ceil((nb+1)/256)`, `lo=t*chunk`, and `hi=min(nb+1,lo+chunk)` define a contiguous partition. The 32-round loop independently scans that partition and calls one work-group `reduce_over_group` after each round. The later `gt`/`eq` scans and output pass reuse that partition. `eqstart`, `chosen` and `offset` are group exclusive scans; emission walks increasing `b`, which gives ascending cell IDs.

R731 records the current 32 one-bit rounds and suggests a conditional four-bit radix alternative. R738 develops that alternative into a weighted MSD prefix histogram and its component fixture/work bounds. Neither report screens cyclic addressing in the existing one-bit count rounds. The current registry lists R731; R738 is present as the named unregistered report. The prior census registry has a QSA score-kernel grid-stride proposal, but it changes the separate score producer's launch/traversal mapping, not `qsa_block_topk`'s threshold-count reads, so it is not this screen. Git history for the selector shows its original addition only; it supplies no recorded cyclic-count trial. The existing `own-qsa-select-radix4-v1` snapshot is explicitly source-only with build, correctness and performance all UNRUN; it is a different candidate and has not screened this mapping.

## Equivalence and bounds

For each round, the candidate would count exactly the same predicate, `order(sc[b]) >= candidate`, over exactly `b=0..nb`, adding the same `weight(b)` (`4` for completed blocks, `n%4` for the final block). Only which work-item accumulates each term changes. Partial sums and group sums are integer; under the existing supported int32 `n` contract the complete weighted count is at most `n`, and each local partial is nonnegative and no larger than that total. Thus changing the partition does not introduce floating-point reassociation or count overflow. Keep `order(float)` byte-for-byte: all NaNs map to key 0, both signed zeros canonicalize to one key, and other finite/infinite values retain the existing sortable transform. The threshold choice therefore remains exact for nonfinite scores and ties, provided every candidate score slot is visited once per round.

The kernel's early returns depend on per-query step fields shared by all work-items in its group. For a valid row, each work-item can finish its own scan before the same fixed 32 group reductions; no data-dependent branch may skip a collective. Different cyclic loop trip counts are safe because the loop itself has no group collective and reconverges before the reduction. Keep the identity and zero-width paths unchanged. Keep every final greater/equal accumulation, exclusive scan, and emission in the original contiguous partition: cyclic emission would interleave block ranges across work-items and would break the current ascending-ID segment ordering unless a new ordering step were added.

For the specified actual batch, there are 78,452 selected queries from 78,453 input tokens; the last input token is handled elsewhere. The maximum selected-row `n=78,452` is divisible by four, so `nb=19,613`, `B=nb+1=19,614` score slots including a zero-weight spare, and output width is capped at 2,051. The current contiguous partition has `chunk=77`; it assigns 77 entries to 254 work-items, 56 to one, and none to one. Cyclic scanning distributes 19,614 entries as 77 to 158 work-items and 76 to 98. Both execute exactly 32×19,614 = 627,648 threshold key visits for a maximum-length row, then leave the separate two final scans unchanged. These are source-level visits, not measured cache/DRAM traffic.

At the physical `n=262,144` boundary, `nb=65,536`, `B=65,537` (the final spare has zero weight), and width remains capped at 2,051. The contiguous `chunk=257` partition gives 257 entries to 255 work-items and 2 to one; cyclic scanning gives 257 to one work-item and 256 to the other 255. Both visit 32×65,537 = 2,097,184 keys per maximum row. The cyclic map's more even trip counts at this bound do not imply lower time; maximum-latency work-item, subgroup formation, occupancy and memory behavior need measurement. `b`, `nb+1`, and partition products are held as int64 in the source. The cyclic index must also be int64 (or otherwise proven not to wrap); with current `n<=INT_MAX`, `b+=256` remains safely bounded. The supported physical-context case is much smaller, but should remain a separate correctness boundary.

## Address and experiment interpretation

At source level, a cyclic round maps simultaneous local IDs `t` to adjacent `scores[qi*blocks+t+256*k]` for each iteration `k`, covering a contiguous prefix/tail with a masked final iteration. A contiguous round maps local ID `t` to `t*chunk+j`; for fixed `j`, neighboring IDs are separated by `chunk` (77 for the actual maximum row, 257 at physical context). This makes the cyclic form a reasonable memory-access hypothesis. It does not establish the target's actual subgroup width/layout, compiler scheduling, memory transaction count, cache hits, or GPU speed. SYCL defines the local linear ID, but does not specify the hardware subgroup execution order or global-memory transaction formation. Intel's oneAPI GPU Optimization Guide discusses locality and memory-use patterns; Intel's separate compiler documentation describes adjacent-access coalescing for Intel FPGA devices, so that FPGA-specific behavior is not evidence about this Arc GPU. Inspect generated device code/resource reports and profile global/L1/L2 transactions and selector kernel service on the actual configured GPU before making a performance claim.

The cyclic scan retains 32 full key-read passes and 32 group reductions, with the same theoretical score-byte request count as baseline. It changes lane-level address shape and work distribution only; it does not reduce total source loads, launch count, score-buffer capacity, or final emission cost. Cached repeated reads can make transaction savings much smaller than the source pattern suggests. The radix4 candidate instead changes threshold work to eight digit rounds with weighted histograms and more per-round reductions; it also keeps final contiguous emission. A three-arm component comparison (baseline/cyclic/radix4) can attribute any gain to those distinct mechanisms. A factorial combined cyclic+radix4 arm is only useful after each standalone arm has a clear result, because the radix candidate's histogram has a different repeated-read pattern and may interact with cyclic scanning.

A minimal component fixture should compare every output ID byte-for-byte with the baseline and an independent cell-order oracle. Include all-equal scores and threshold ties spanning work-item boundaries; NaNs, infinities, signed zero and adjacent float keys; `n%4` values 0–3 including the zero-weight spare; widths below/equal/above `n` and the cap boundary; mixed row lengths in one 256-query group; the actual max `n=78,452`, and separate physical-boundary cases through 262,144. Check output length, uniqueness, ascending order, bounds, and guards. Compare source and compiled transactions, registers/spills, occupancy and isolated selector time in matched runs. Whole-prefill clean samples are needed for any end-to-end claim; queue intervals alone are not a kernel timing.
