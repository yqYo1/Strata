## Current lifetime and exact storage cost

In `src/prefill/prefill.cpp`, `DQ=2`; `Prefill::carve` allocates two `dq_gu` slots and two `dq_d` slots. At the fixed model shape each slot is `1280*2560` FP16 GU elements plus `2560*640` FP16 Down elements: 9,830,400 bytes (9.375 MiB). The two-slot working set is 19,660,800 bytes (18.75 MiB). `q=j%DQ` rotates these buffers in the active-expert loop. The native path launches GU and Down dequantization for that expert, then compact activation gather, FP16 GU GEMM, SwiGLU, and FP16 Down GEMM. `src/kernels/sycl/iq.cpp` decodes each packed block to FP32 `values[256]`, then stores `f16_from_f32` bits; both the gate/up and generic output paths use this conversion. The non-native blob path has a separate packed 2-bit decoder in `src/prefill/sycl/blob.cpp` and also uses the project's FP16 conversion helper.

The compute path uses the same in-order SYCL queue. That ordering and the per-expert sequence currently keep the two slots safe; any cache hit/eviction must prove the dequant write and all GEMM reads have completed before storage is reused. Source layout is chunk outer, layer inner for the current path, so a cache kept through chunks must be layer-keyed and survive the intervening layers. In the layer-major candidate, the schedule is layer outer and chunk inner; a small cache can then serve one layer across its nine ordered chunks and be drained/reset at the layer boundary. Its key must include layer, expert, source format/offset and generation, not just the expert number.

A full 512-expert FP16 weight layer would require 512 x 9,830,400 = 5,033,164,800 bytes = 4.6875 GiB, before metadata, alignment, model allocations, prompt scratch, KV staging or allocator slack. It is not a viable assumption on a 10 GiB card already carrying the base model/session and layer-major packed-expert cache. A bounded single-layer tile is materially smaller: 8 entries = 75 MiB, 16 = 150 MiB, 32 = 300 MiB (decimal per-slot values rounded to MiB). Those figures cover both GU and Down together and do not include other live memory. The full-context path also keeps a 256K host tail; no cache admission may consume the RAM budget reserved for it or reduce its backing. The source/report evidence for phase order also requires QSA causal history and GDN recurrent/convolution state to advance in ascending chunks within each layer; layer-major reuse cannot reorder phases around those dependencies or move MoE work ahead of deferred GDN/QSA work.

## At most two candidates

### 1. Bounded per-layer FP16 decoded-weight cache across chunks

Reuse the exact existing native dequant result for the same expert in the same layer across chunks, with an 8- or 16-entry LRU (75 or 150 MiB) resident only for the active layer. On the first miss, dequantize into a cache entry; on later hits, issue GEMMs against the retained FP16 pair. Keep the existing two DQ scratch slots for misses and leave all formats on the existing decoder/conversion path. This is a source-level proposal, not a demonstrated hit rate. It is attractive only if an exact layer/expert/chunk route trace shows that the bounded recency window captures substantial later-chunk work after warm-up. A popularity histogram without sequence order is insufficient; a repeated expert may be separated by enough other expert IDs to miss a small LRU.

Before implementation, derive the candidate hit rate and byte/work savings by replaying the actual per-chunk expert sequence under 0/4/8/16/32 entry capacities, with exact native format, shape, resident/streamed source, and order. Report unique IDs, repeat distance and misses, plus counts/rows by `ne`; do not count the first-chunk fill as avoided work. Admission must query live free VRAM after base model/session, MTP, KV and the actual 512 packed-expert layer cache are established, preserving the required reserve and 256K host tail. Start at 8 entries and refuse admission if the measured remainder is insufficient. Enforce checked per-layer cache ownership and queue completion before eviction/layer transition; preserve FP16 bit patterns and existing GEMM accumulation. Require exact dequant-output comparison for every supported format and stride, guards, attention/GDN/MoE/residual and first/final-logit checks, unchanged IDs/faults, then paired clean whole-request samples. If measured cross-chunk LRU reuse is low or alloc/free pressure impairs residency, reject the candidate. The profile's 91,880 call count alone is not an upside estimate.

### 2. Exact native dequant directly into an XMX/GEMM tile

Replace the intermediate full FP16 weight write/read with a fused packed-block decode feeding the matrix multiply tile, for a narrowly selected native format and actual expert sizes. This can avoid materializing 9.375 MiB per expert and may reduce global-memory traffic. It is a much larger kernel and numerical-contract change: the decoder must preserve each GGUF format's scale/code interpretation, row stride, and the current `f16_from_f32` rounding before matrix use. It must reproduce the current FP32 accumulation and route output layout, including tails and mixed resident/streamed expert sources. A simple claim that the fused kernel “does not dequantize” is misleading if it repeatedly decodes packed blocks for each output tile or loses packed-weight reuse across many routed rows.

Primary reference: upstream llama.cpp's official SYCL backend documents XMX gather paths that dequantize supported quantized weights directly into XMX tiles for MoE `MUL_MAT_ID`; it also sets explicit type/shape masks and falls back to standalone dequantization for unsupported types/layouts and selected batch/row shapes ([SYCL backend guide](https://github.com/ggml-org/llama.cpp/blob/master/docs/backend/SYCL.md)). The official Intel joint-matrix extension describes hardware/shape combinations as optional and device-specific ([oneAPI matrix extension](https://github.com/intel/llvm/blob/sycl/sycl/doc/extensions/experimental/sycl_ext_matrix/sycl_ext_oneapi_matrix.asciidoc)). This establishes that fused dequant-to-tile is a real implementation family, not evidence it is faster or numerically compatible for Strata's formats, B570 compiler/runtime, `ne` distribution, or current oneMKL path. No direct IPEX-LLM source reference matched this model's GGUF IQ format/row contract, so it is not a candidate donor.

A Main-owned screen should first select one format with the largest profiled service and enough actual row work, then establish per-format/per-shape operation count, logical source bytes, and active `ne` distribution. Compare against current dequant+oneMKL on identical packed blocks and X rows; require bitwise equality of the FP16 dequantized values and the existing GEMM's result within its established numerical contract, plus output guard, tail, finite, exact-logit/greedy and fresh-fault gates. Profile actual kernel duration and memory traffic separately from clean request timings. Stop if the device lacks the required matrix combination, fallback coverage becomes broader, repeated tile decoding outweighs saved writes, or any exact conversion/GEMM contract fails. Do not import the donor backend wholesale.

## Disposition and references checked

The only safe near-term reuse hypothesis is the small, single-layer decoded-weight LRU, conditional on actual ordered cross-chunk reuse and a live VRAM admission calculation. The fused XMX route has larger upside but needs a format-specific prototype and strict equivalence proof. Neither is implemented, measured for speed, or adopted. No extra candidate is proposed for “full 512 FP16 residency.”
