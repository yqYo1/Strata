Date: 2026-10-15 JST. Read-only source and retained-report audit for the long-prefill recovery. No test, build/compiler, GPU, process/service, private environment/log, cleanup, or Git mutation was performed. Historical source was read with `git show` at the named implementation commit; current source is the configured root path. No source was changed.

## Finding

Both implementations use the same outer traversal: for each of 48 layers, load that layer's 512 expert blobs, then run the complete prompt through the existing chunk implementation for that layer, preserving token/chunk order; store each non-final layer's residual rows for the next layer; only after all chunks finish advance to the next layer. The layer-major idea itself is therefore not missing from current root. The material differences are its admitted shapes, expert source/upload/lifetime implementation, residual residency policy, KV support, current features and safety contract. The historical 645.85 tok/s does not show that the present root path reaches that rate or that any one of these differences caused the gap.

Processing order, both:

```text
for layer in 0..47:
    load/publish that layer's expert set
    reset layer's chunk cursor and PLE previous-token state
    for chunk in prompt order (size T, final chunk may be short):
        run_impl(chunk, layer range = [layer, layer+1])
        for non-final layer: save this chunk's FP32 residual rows
        on final layer: deliver normal prompt callback/output
    retire this layer's pass before next layer
```

The shared order avoids reloading expert weights once per prompt chunk. It does not reduce the model's per-token work. `run_impl` owns QSA/GDN/PLE/MoE math and within-layer chunk details in both versions.

## Source comparison

Historical source: implementation commit `f263d87d44aa671d056c33e6c6b6b0635fc25b8c`, `sycl/src/prefill/prefill.cpp`, `Prefill::run`/`run_layer_major` around lines 1870–2075. Mode `STRATA_PREFILL_LAYER_MAJOR=1` selected reuse when multiple chunks; `=2` forced it for diagnostic equivalence. The routine required full single-GPU compact FP16 and native source, and rejected any `kv_mode != 0` plus PLE preload. It allocated one `ExpertCache`, filled all experts for a layer with staged jobs, waited, marked residency, then called `run_impl(tokens,n,pos0)` once for that layer. Its `on_chunk` copied residuals into either the configured GPU prefix or host tail; the callbacks are chunk-ordered. The host-tail callback waited for the copy before the next layer could read it. The final layer forwarded the ordinary saved callback. Each layer restored the original PLE token pair before replaying the prompt.

Current configured root source: `src/prefill/layer_major.inc`, `Prefill::run` and `run_layer_major` (dispatch at file start; layer loop and callbacks in the later portion). `STRATA_PREFILL_LAYER_MAJOR=1` uses layer-major only when `n > T`; unlike the historical `=2`, there is no forced-short diagnostic mode. It checks one full model/device, no PP/peer/stage/hand-off/vision/reentry, explicit `STRATA_PREFILL_MMQ=0` with the expected fallback, matching compute/copy queue, model geometry, position/context/chunk limits, a complete native source table, uniform mode-0 resident or mode-1 streamed KV, and idle stager. It pre-admits an additional 512-expert cache plus 512 MiB GPU headroom and host storage plus 8 GiB RAM headroom; opens an uninitialized cache; copies source blobs into an owned upload slab on the caller thread; uploads each expert and drains before publishing residency. This avoids retaining transient source pointers or stager jobs across a layer pass.

Current code calls `run_impl` for each whole prompt/layer as well. It resets `ss.ple_prev` to the request's initial pair before each layer and commits the final pair after the last layer. Each stored residual range is FP32 by default and selected by `LayerMajorResidualPlan`: a GPU prefix and host tail may be chosen from free-memory admission; exact rows/bytes are logged at runtime. FP16 storage is separately experimental and unqualified. Unlike the historical simple `m.cs->wait()/m.copy->wait()` restore, the current route drains both queues at entry/layer/pass/final boundaries and holds owners under `DraftUploadGuard`; inability to prove retirement aborts rather than unwinding live buffers. This is a meaningful safety/lifetime difference and may add synchronization cost, not a measured speed delta.

Current root admits streamed KV mode 1 as well as fully resident mode 0 when all 12 QSA layer stores have compatible full-logical-range host and stage storage. The shared `run_impl` handles the current streamed path, including per-chunk prior-page host-to-stage work. Historical layer-major refused streamed KV outright. Thus current configured 32K/64K contexts with resident INT8 prefix plus streamed tail do not follow the historical K8/V8 all-resident condition. Current mode also rejects the `STRATA_PREFILL_PRELOAD_PLE` option; PLE compute remains in the shared prompt pass. A separate MTP prompt callback can run at each chunk boundary as part of `run_impl`'s caller callback; current server/standalone generation installs batched `draft_kv` then fallback `mtp.prefill` (`src/program/generate.cpp` around 4961–4978 and 6435–6441). Historical timed PR6 condition loaded no MTP model, so had no draft-KV callback work.

## Historical result and mismatches

R560's retained receipts report three paired PR6 samples, median 645.85 prompt tokens/s (32,768 input, 8,192 chunk, four chunks). Its timed configuration was context 65,538; INT8 K/V all resident; 128 expert slots; warm PLE; five workers; PCIe fraction zero; no prefill borrowing; no timed MTP; one generated output. It changed compact scratch mode and layer-major together; all 32,768 FP32 residual rows were requested on GPU. The comparison's own matching logits/output fingerprint and three alternating pairs support that result for its stated setup. It is not a 256K prompt run, current-root run, MTP4 run, streamed-KV run or 4K-chunk comparison. R560 also records that measured executable/build provenance is incomplete for byte-identical rebuild.

The current formal setup described by R630 uses the actual root resolver, 4,096 chunks, maximum context 262,144, INT8 KV with 32,768 configured resident cells, layer-major path where enabled, MTP4 prompt work, and current safe runtime controls. A 32K prompt may fit within resident KV capacity but still uses the current mode-1 streamed implementation; 64K necessarily crosses the 32K resident prefix. Current FP32 residual placement is admission-selected, not guaranteed all-GPU. The PLE preload switch is refused in layer-major, while PLE's normal per-layer prompt computation remains. These settings and work differ from PR6 in several correlated dimensions.

| Dimension | PR6 timed path | Current root path | Consequence for comparison |
| --- | --- | --- | --- |
| Outer traversal | Layer-major, full prompt once per layer | Same outer traversal, full prompt once per layer | Core ordering is shared. |
| Chunk | 8,192 (4 chunks at 32K) | Formal path 4,096 (8 chunks at 32K; 16 at 64K) | Fewer chunk boundaries may reduce setup/staging overhead; doubled chunk buffers can change admission. No causal speed attribution. |

| PLE/MTP | Warm PLE; no MTP callback | Normal PLE pass; current MTP4 callback may do draft KV at chunk boundaries | Current timed prefill includes callback work when enabled. |
| Safety/timer | Historical executable/configuration and CLI timer | Current root queues, checked drains, safe environment, prompt timer/callback path | Both route and measured interval need exact receipts; no cross-run ratio isolates one factor. |
