# Round 599 — retire owned Prefill scratch between prompt and decode

2026-10-15 JST. Read-only configured-root SYCL ownership review. The only write is this report. No source, Git, build, test, GPU, service, profiler, or cleanup action was taken. I read `AGENTS.md`, `docs/ARTIFACT_RETENTION.md`, this audit's `research-index.json`, R594, R574, and the reviewed MTP expert-release v2 proposal before tracing current root source. No external design was needed: the relevant question is whether Strata's own queued work, captures, and owners survive a proposed boundary.

## Decision

The owned Prefill allocation can in principle be retired after the final successful batched prompt segment, because its residual and scratch are consumed synchronously through the end of `Prefill::run`; decode continues from `SessionState` and Verifier-owned buffers. Current code does not yet provide a safe repeated lifecycle. `Prefill::release()` ignores queue-sync/free errors and leaves a populated `Impl`; calling `init()` again on that same implementation can reuse stale pointers and append duplicate `owned` entries. `reset()` replaces the implementation, but invokes the same unchecked release. Therefore the smallest sound architecture is an opt-in checked `retire/recreate` API (or equivalent checked `reset`) that drains and releases only Prefill-owned resources, preserves the persistent `SessionState`, `ExpertCache`, MTP and Verifier, and cannot return to prompt/decode after an uncertain drain/free. Recreate lazily before the next batched segment with the exact current chunk and buffer layout; do not allocate a second permanent prompt arena.

R594's `accounted=1,662,831,872 B` is 1,585.6 MiB (about 1.55 GiB) attributed to `Prefill::Impl::owned`. It is a source/log accounting value, not a measured `cudaMemGetInfo` delta or guaranteed reclaimable amount. R594's phase observations and cache-size estimates remain the only byte evidence. The 256/384 cache tiers add approximately 260/520 MiB over the 128 tier; if exact fresh admission permits those additions, scratch retirement would leave a nominal net decode-space difference of about 1,325/1,065 MiB relative to the existing 128-plus-scratch footprint. This arithmetic assumes all 1,662,831,872 bytes are released and cache-tier deltas match the estimates. It is not an allocation, capacity, latency, or hit-rate result.

A fresh 256/384 cache must be selected and fully admitted before use. Freeing scratch after the first prompt cannot enlarge an already-open `ExpertCache`. Admission must use a live free/total query and exact `open_sized` bytes after persistent model, session/KV, MTP, Verifier, decode graph, and runtime owners exist, with a declared reserve. If Prefill uses cache-tail loans, require the exact chunk's `bytes_needed`, preserve the documented 128-slot floor, and record that those slots are temporarily prompt buffers then refilled before decode. Otherwise account for the full Prefill allocation concurrently at prompt peak. For 256K, use the actual host-backed KV configuration; scratch release does not reduce the 3.094-GiB logical host KV backing or change the physical-context correctness obligation.

## Smallest concrete lifecycle

1. Keep the existing initialized `Prefill` for the current prompt. During serve's request loop, batched segments can be separated by turn/root checkpoints and short verify-window reads (`generate.cpp:5912+`); do not retire at the return of an arbitrary segment if the same request can later call `sp.run()` again.
2. After the final prompt-loop segment, wait for all `Prefill::run()` work and callbacks (already part of normal successful return), complete every borrowed-cache refill and residency upload, and verify no segment remains lent. At this point the code logs `prompt done (slots refilled)` before entering verify/decode (`generate.cpp` around the prompt loop ending after `:5955`). The standalone path has a simpler single `Prefill::run()` followed by decode setup.
3. Add a checked API whose success means all relevant queue operations completed and each free/destroy succeeded. On failure, preserve live owners and stop the request/process; do not continue decode or let destructor retry unknown ownership. Destroy only Prefill's owned allocations and host/event/stager resources; leave caller stream, `SessionState`, cache, MTP, Verifier and their graphs untouched. Reinitialize through a fresh `Impl`, not by calling current `init()` after current `release()`; current `owned` and pointer fields are not reset by `release()`.
4. Recreate immediately before the first next-request batched segment, after RESTORE/checkpoint state has been applied but before any `sp.run()` or `relayout()`. Use current request's exact chunk and actual borrowed slot range/bytes. Keep MTP's Verifier-R binding and all persistent state owners. A no-batched-work request need not recreate scratch. Short `read_windows()` does not require Prefill.

For the first candidate, scope to single-device SYCL, no peer/split path, no external callback that retains Prefill pointers, and static expert cache. Supporting a split requires retiring/recreating each stage in device order after all `next_run` futures and handoffs are complete; supporting peer requires a separate `PeerPrefill` owner audit. Adaptive cache refill must be idle at the boundary. The current report does not claim that default configuration meets these narrowed conditions without runtime gates.

## Required verification gates before implementation adoption

- **Physical 256K:** run actual `--max-context 262144` full physical-context path, preserving host-KV fallback and exact session/page ownership; compare no-retire and retire/recreate on the same source/config. Confirm no lost tail, no page-table or host-pool change, and successful end-of-context decode.
- **Cancel/error:** stop during a chunk and inject only controlled host-side setup/callback failures in an isolated qualification. Assert the request cannot proceed to decode after failed drain/recreate, borrowed slots are either fully refilled or retained as uncertain owners, and no callback reads freed R. Do not create GPU faults for this gate.
- **RESTORE/checkpoint:** cover fresh conversation, incoming live snapshot, checkpoint hit, checkpoint miss, checkpoint save boundary, and a short continuation that uses `read_windows()` only. Compare restored outputs/state to the unchanged path; verify Prefill can remain retired throughout windows and be recreated before a later batch.
- **Normal MTP4:** ensure `draft_kv`/`mtp.prefill` finishes before R release, all normal MTP graphs still use Verifier's unchanged `final_R_all()`, and target/draft KV state plus logits/tokens match the baseline criteria.
- **Coupled MTP4:** same as normal plus sampled coupled round/step graph path; verify coupled state/counter/history and graph handles remain live and no pointer aliases Prefill R.
- **Capacity admission:** test exact static 128/256/384 slot layouts in fresh processes. Record free/total immediately before exact cache allocation, exact requested/allocated bytes, after profile fill, after Verifier/MTP graph creation, after Prefill init/run, after loan refill and after scratch retirement. Require an explicit reserve and refuse the tier if the exact bytes plus reserve do not fit. Preserve all individual receipts; a refused tier is not a failure or a speed result.
- **Repeated request:** same server process with multiple prompts, a restored continuation, a no-batch short turn and a subsequent long batched turn. Check fresh `Prefill` allocations are initialized exactly once per cycle and no prior queue/event/pointer is reused.

These gates establish safety and fresh admission. Performance remains a separate matched same-work measurement; neither this source review nor the 1.55-GiB accounting predicts prefill/decode speed or cache hit improvement.
