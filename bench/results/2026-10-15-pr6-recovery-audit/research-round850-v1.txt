# R850 — Natural 32K dense-NLL FP32 failure: source, lifetime, and control audit

**Decision support; read-only.** The compiled source pin is `6354f0b4ff3731466795410e11ca9ef785c9d326`, recorded in `bench/results/2026-10-15-pr6-recovery-audit/own-vllm-engine-build-v2.json`. The supplied FP32 control receipt hash matches `bf9d6f0036bff3d6c8f49a384ecc03d849453a41e3ab93b2d90fd4c9833a4f18`. The failed result remains failed: `passed=false`, `capture_complete=false`, and formal original ownership closure is false. This audit ran no build, test, GPU job, profiler, process inspection, or driver/service action and changed no source or gate.

## Finding

No concrete source-level use-after-free, out-of-bounds access, wrong queue dependency, or exception path that releases live row/head storage was found in the audited callback. The new failure remains unexplained. Source control appears deliberately synchronous at the important handoffs; that makes a missing event between the NLL head and readback a poor explanation. It does not exclude a stuck queue command, a runtime/device failure, a host-side stall, or an issue in unreviewed compiled details. The CCS reset reported near owner termination does not establish what stalled first or why. Keep the original status and do not treat this run as a healthy qualification.

The successful FP32-a metadata says `n_input=32863`, `rows=32862`, `vocab=248320`, and `callback_ms=316122.344785` (about 5m16s for the NLL callback). FP32-b was terminated at 903.68s after 677 complete records and 4 additional bytes; the 677 target/loss records match FP32-a exactly. This is about 2.06% of rows. The control callback averaged 9.62ms per row, so 677 rows at that average would take about 6.5s, but the failed run has no row timestamps: its prefix may have accumulated quickly before a later stall, or may have been very slow throughout. No per-row timing is recorded in the receipt, and `callback_ms` includes only completed chunk callbacks; it cannot resolve that distinction.

The raw length is suggestive but not a stack trace: 64-byte header + 677 × 12-byte records + 4 bytes = 8192. That fits four bytes of the next record, but `fwrite` is buffered and the process was killed, so the file length cannot identify whether the last in-process phase was projection, stream wait, FP64 reduction, or flushing. No output-progress line is emitted per row. The NLL timer is added only after the current chunk's row loop returns; the completion footer and summary appear only after the whole prompt run succeeds. The existing selected-logit file being empty is expected: NLL wraps the existing callback, executes its full row loop first, and calls the previous selected-logit/MTP callback only afterwards. A failure inside NLL therefore prevents selected-logit work from starting.

## Source and lifetime trace

`generate.cpp:2576-2581` creates `main_stream` and passes its address as `main_cs`. Under the SYCL compatibility header a `cudaStream_t` is `sycl::queue*`; stream creation calls `Runtime::make_queue(true)`, whose queues have the in-order property. `Prefill::init` stores this caller-owned pointer as `m.cs` and, for SYCL, sets `m.copy=m.cs`; `Prefill` destruction only destroys `copy` when it differs from `cs`. Its final-chunk callback is invoked after `cudaStreamSynchronize(m.cs)` succeeds (`prefill.cpp:3480-3504`). In layer-major mode, the last layer forwards its final residual to that callback before the layer-major pass clears its overlay and before the outer native/canonical bank transaction restores full ownership (`layer_major.inc:509-520, 604-621`; `generate.cpp:362-437`). The caller keeps the stream, session, weights, `NativeHead`, and NLL writer alive across the whole prompt call.

The NLL loop at `generate.cpp:6830-6878` accounts for each chunk, then serially processes each token. It copies the `BlockBuffers` pointer bundle, changes only `R` to the row at `rows + t * (hc*n_embd)`, and submits one existing single-token head. `lm_head_mix` reads that FP32 residual and writes the existing GR/mixed scratch; `NativeHead::run` submits the native output projection when loaded, or the canonical `lm_head` path submits its quantization/projection. Both use `main_cs`; the full vocabulary row is copied to `prefill_nll.row()` on `main_stream`. That destination is ordinary host storage, which the SYCL explicit-copy contract permits; the checked stream sync keeps it alive and readable before the guard retires, CPU loss reduction, or file append. The next row cannot reuse the one-row head scratch until then.

At the compatibility layer `queue(st)` resolves the same queue pointer and checks its context; `cudaMemcpyAsync` enqueues `queue(st).memcpy`; `cudaStreamSynchronize` calls `wait_and_throw` and then checks accumulated runtime errors (`compat.cpp:83-87, 255-261, 332-338`). The official SYCL contract guarantees in-order submission order within a queue, not between queues, and defines `wait_and_throw` to wait for queued commands while delivering asynchronous errors ([Khronos SYCL 2020 specification, revision 12](https://registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html)). On the audited path, projection, copy, and wait all use the same explicit queue. No cross-queue event omission was identified.

The guard is armed before any possible head submission, including a partial submit or throw. On an early return it synchronizes before local owners unwind; if that drain cannot be proved, it fail-stops with owners retained (`DraftUploadGuard`, `generate.cpp:6851-6878`). On success, the explicit wait is checked before `retire()`. After the inner `Prefill::run` returns, the outer dense-bank transaction drains the main queue before restoring ownership. These contracts make a straightforward borrowed-row or head-scratch UAF unlikely. The row stride is the declared `(hc,n_embd)` shape; `Writer::chunk` rejects gaps, overlap, and invalid count; the loop is bounded by that count. `ss.block` is carved from the session arena, while prefill `R` comes from a separate prefill allocation or cache loan. The optional scratch alias only overlays prefill `mixed`/`block_out` with prefill embedding scratch; it does not alias the session block arena. No direct row-to-head-scratch overlap is apparent.

This is not all-GPU work. The GR mix, output projection, and D2H copy are queued on the GPU. `target_loss` is CPU FP64: it scans all 248,320 logits for the maximum and scans them again for stable log-sum-exp; `append` validates the target and writes the record on the host. It reports `callback_ms` only after completing every row in that chunk. Thus the callback’s lack of progress output is a source-level observability gap, not evidence that no work occurred.

For this input the exhaustive callback performs 32,862 single-row head projections and transfers/reduces 8,160,291,840 FP32 logit values in total. That repeated output-head work is necessary if the requested artifact is exact NLL for every input position; it is unnecessary for an early precision quality screen. This is a high-cost diagnostic, not a speed cohort. It does not by itself explain why the successful control completed in 316s while the second same-configuration control produced only a partial prefix before its 900s deadline.

## Ranked hypotheses (open seams, not established causes)

| Rank | Mechanism still consistent with the evidence | Smallest safe discriminator and falsifier |
|---|---|---|
| 1 | A row-local command/wait or other callback phase stopped making progress. The queue calls are ordered and checked, but there is no progress state between head submission and callback completion. A single long wait could leave the same 677-record prefix as uniformly slow processing. | First use source-only analysis and the completed control’s per-callback total; do not rerun GPU work now. If a separately reviewed health gate later permits it, repeat the same 32K prefill with only selected logits at position 677 and compute that row’s NLL offline; add a bounded phase observer. A `before-sync` with no `after-sync` marker would localize the wait; a later marker falsifies that explanation. Do not infer cause from the reset timestamp alone. |
| 2 | A host-side reducer or stdio flush stalled after some completed D2H rows. The file prefix and four-byte tail are compatible with the append boundary, and no row-level timing separates CPU reduction, `fwrite`, or device waiting. There is no evidence that this actually happened. | Main can first run a CPU-only microreproducer of `target_loss` and `BasicWriter::append` on a 248,320-value row and explicitly record reduction/append/flush times. In a future healthy-gated diagnostic, publish before/after markers around sync, `target_loss`, and append; after-sync without after-loss implicates the reducer, while after-loss without append completion implicates writing. |
| 3 | An actual compiled pointer/context mismatch or unexpected alias outside the checked path could invalidate the static lifetime argument. The audited source argues against this: `R` and `ss.block` have separate owners, the copied buffer struct changes only `R`, and the main queue stays alive through callback drain. | Resolve by source-only pin verification and extent/owner assertions for `R_rows`, `ss.block`, `d_logits`, and native-head scratch; a CPU mock can exercise guard return/throw/drain branches without a GPU. If those checks agree with this trace, deprioritize alias/owner hypotheses. A GPU reproducer is not justified before a new independent health gate. |

The earlier separate-queue GEMM regression is not evidence that this callback shares its cause: that failure exercised `pipeline(q,true)` with transfer and compute separated, whereas this prefill sets `m.copy=m.cs` and the head/readback path uses only `main_stream`. Its stalled main/worker stacks and absence of case progress remain useful as a warning that a whole-test timeout can hide phase, not as a diagnosis here. The R831 runtime review corrected a prior false claim about `native16_active` and reaffirmed that the compatibility stream is a distinct in-order queue whose caller must drain it. This FP32 case has `native16=0`; the producer callback and drain described above are the relevant path. Earlier clean requests without dense capture and short dense cases do not qualify this 32K exhaustive-NLL callback.

## Safer screen and next diagnostic design

For a future precision screen, use the existing deterministic sparse selected-logit positions across the full 32K input (the 64 positions spaced 512 apart in the supplied recipe), then compute NLL offline from those saved full-vocabulary rows and the immutable next-token IDs. This retains exact per-position logit comparison and a meaningful matched sparse NLL sample while reducing added head calls from 32,862 to 64. Label it sparse; it is not an all-position NLL result and must not silently replace any separately required exhaustive comparator. Keep exhaustive NLL as an explicit later diagnostic only if the all-position statistic is still needed. Because NLL is installed outside selected logits and runs first, a screen using selected logits must omit the exhaustive NLL callback; no code or gate is changed by this recommendation.

A source-only observer proposal is a preallocated fixed-size parent-visible status record containing request identity, chunk start/count, row, monotonic timestamp, and phase (`before-head`, `after-head-submit`, `after-readback-submit`, `after-sync`, `after-loss`, `after-append`). Update at phase boundaries, not with a flushed message for every row. Have the owning launcher consume those records and, if a bounded phase remains stuck, collect one representative stack itself as the child’s actual parent before termination; do not use the sibling debugger arrangement that failed under ptrace policy. Capture identity, timestamps, stack, exit/reap state, and the fault boundary under the retention budget. This proposal is not approval to run another GPU job: require a new reviewed independent health gate first.
