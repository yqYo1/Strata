## Mechanisms from published work

**Fuse by data regime and keep intermediate state in the cheapest tier.** Microsoft’s TQP++ (VLDB 2026) combines relational operators with a map/reduce-oriented fusion scheme and gates execution using runtime data characteristics. Its authors describe tiering aggregation state by `group count × value width`: thread-private registers for small state, shared memory for medium state, then sharded device memory for larger state. The paper presentation also shows overlapping string-pattern windows loaded once per block and reused from shared memory. This is more specific than “fuse kernels”: it makes cardinality and live-state size explicit scheduling inputs. [Microsoft Research paper page](https://www.microsoft.com/en-us/research/publication/tqp-bridging-ml-compilers-and-analytical-query-processing-on-gpus/) and [author presentation, slides 5–7](https://www.microsoft.com/en-us/research/wp-content/uploads/2026/05/TQP.pdf).

Transfer hypothesis: a device-resident route descriptor list could select among a small-row path, a block-local tile, and a bounded overflow path without returning each expert’s count to the CPU. This requires the consumer to read device counts/descriptors; TQP++ does not establish that its graph gates remove all host control roundtrips or that this schedule maps to MoE GEMMs. A 2024 GPU database comparison found four kernels for its fused Crystal/HeavyDB Q21 paths versus 172 for BlazingSQL and 190 for TQP, with intermediate materialization a substantial cost; it also found the fused Crystal path loaded unnecessary data and lacked prompt thread termination. So fusion can save intermediates and still lose locality or useful issue slots. Those results were on the authors’ NVIDIA setup and query, not B570. [Cao et al., PVLDB 17 (2024), §§5.1.2, 6](https://www.vldb.org/pvldb/vol17/p441-cao.pdf).

**Allocate variable output in bounded pages instead of probing twice.** Rui and Tu’s GPU hash join first describes a conventional two-probe plan: count outputs, prefix-scan counts, then repeat the probe to materialize results. Their alternative reserves small pages from a global output pool with an atomic pointer; threads fill local pages and request another only when needed. This removes the second probe at the cost of atomic page reservations and potentially unused capacity. On their Titan X data, direct output improved hash-join time by about 20–25%; the gain fell with larger datasets as reservation atomics rose. Larger pages could waste pool space and increase transfer bytes; the technique did not help their sort-merge path. [Rui & Tu, SSDBM 2017, §3.2.2 and §4.2.5](https://cse.usf.edu/~tuy/pub/SSDBM17.pdf).

Transfer hypothesis: use a fixed-capacity, per-chunk GPU descriptor pool (expert, source row, top-k slot), with block-local reservations and an explicit overflow flag, as a candidate for routing-to-expert handoff. It could avoid a second pass or host-built index only if the subsequent expert consumer can use the descriptors directly. A single global atomic order would not preserve the current stable row assignment; preserve a source/slot key and compare final outputs. Output selectivity and skew matter: a low occupancy descriptor pool may waste space, while a hot expert can serialize reservations. This is not the same operation as the current host-grouping implementation.

**Device-driven producer/consumer worklists.** Ding et al. use NVSHMEM GPU-initiated transfers and two CUDA streams for multi-GPU sparse triangular solve, reporting up to 6.1× over cuSPARSE across their 1–18 GPU tests. This demonstrates device-driven dependency handoff in that CUDA/NVSHMEM environment, not a portable B570 solution. The transferable shape is a bounded device queue of (expert, tile, source-offset) descriptors whose consumer owns the dependency chain; a GPU-generated queue followed by host inspection would retain the roundtrip. [Ding et al., SIAM ACDA 2021](https://epubs.siam.org/doi/10.1137/1.9781611976830.14).

**Recompute halo work to remove a synchronization boundary, but stop at the measured crossover.** Holewinski, Pouchet, and Sadayappan’s GPU overlapped tiling computes a tile plus its dependency halo for several time steps inside one block. Neighboring blocks redundantly compute overlapping cells, avoiding inter-block synchronization between those steps. Their measurements show the trade clearly: on their 2D Jacobi cases, time tiling improved performance only up to an optimum (T=5–6 for the tested configurations); beyond that, global loads stopped falling while redundant instructions kept rising. They also report that 3D stencils fare poorly with this method because halos grow rapidly. [ICS 2012 paper, §§4–5](https://www.cs.colostate.edu/~pouchet/doc/ics-article.12.pdf).

For QSA, the analogous hypothesis is to recompute a small score/predicate from already resident query/key tiles instead of materializing and rereading an intermediate score array. This paper demonstrates a GPU-global-memory/synchronization trade, not PCIe savings; it gives no reason to recompute expensive attention or expert projections. For sparse route/QSA shapes, padding and duplicated arithmetic may overwhelm the saved metadata movement. Measure instructions, bytes, scratch, and the full dependent path together.

**Reuse dependency state for repeated graph updates.** Grapin (PVLDB 2025) targets streaming graphs larger than GPU memory. It adapts dependency-memoized incremental updates to GPU CAS operations and keeps frequently accessed dynamic subgraphs in a fine-grained GPU cache. On its NVIDIA A5000 evaluation, incremental processing reduced transfers by 61%; caching reduced the remaining transfers by another 72% (89% total). This is a counterexample to assuming that recomputing a whole problem is cheaper than retaining compact dependency/cache state when iterations reuse most of the data. It is workload-specific: it uses changing graph snapshots and parent dependencies, unlike a single prompt prefill. [Wang et al., PVLDB 18(11), 2025, §§1–3](https://www.vldb.org/pvldb/vol18/p3854-wang.pdf).

## Strata scale and applicability limits

The dispatch-provided diagnostic is actual 78,452 batched rows, 48 layers, chunk 8,192, FP32 residuals with 32,768 rows placed on GPU: 217.1097 CPU seconds / 223.6063 wall seconds, including 167.9548 CPU seconds in explicit waits. Route IDs plus slot/source maps total 451,883,520 logical bytes over 480 boundaries. At a hypothetical 6 GB/s, moving every logical byte once has a 75.3 ms bandwidth-only floor; mapped host USM is not VRAM, these bytes are not a PCIe counter, and the estimate excludes queue latency, coherence, host work, and dependencies. A full chunk’s three int32 arrays (IDs, slot, source) are 8192×10×3×4 = 983,040 bytes (0.94 MiB); counts/offsets are small beside that. This makes a per-boundary reusable descriptor arena plausible by capacity, not necessarily by speed.

The planned 32,768-row FP32 residual is 32,768×10,240×4 = 1,342,177,280 bytes (1.25 GiB), before weights, KV, runtime, and other workspaces. A 10 GiB card therefore does not imply enough free headroom for whole-prompt materialization or an unbounded output pool. Reserve and measure peak memory before selecting tile sizes. Main’s grouping+map-submission counter is 0.16536 CPU seconds and excludes the preceding wait and map completion; do not infer that this counter or logical bytes dominate latency. A GPU grouping kernel alone still leaves the existing host `ne`/expert selection dependency. A true no-host-roundtrip experiment must include a device-resident descriptor consumer through expert work and combine, or report exactly which host dependency remains.

## One measurable experiment

After Main closes its current boundary-attribution run, compare the current route/map/oneMKL path with one prototype full device-resident descriptor path on the same 78,452-row request, 48 layers, 8,192 chunks, FP32 residual mode, and identical runtime settings in separate clean processes. The candidate should create stable per-expert descriptors and bounded row tiles on-device, consume them through expert projection/activation/combine, and return only at the normal output boundary. Record per-layer/chunk wall and caller-CPU time from routing through combine, map/readback bytes, queue waits/submissions, per-expert row histogram, kernel time, and whole-prefill samples; component kernel time alone is insufficient.

Correctness gate: compare route IDs, expert counts, source-row/top-k ownership, and final FP32 output/logits to the existing path; retain bounds, cancellation, async-error, and full physical 262,144-context validation. If a changed GEMM tile alters rounding, quantify against the FP32 reference without relaxing existing checks. Use no device-wide spin barrier; express producer/consumer dependencies with ordered kernels/events. Keep descriptor/tile buffers alive through their final consumer event and do not recycle them earlier. Bound added scratch to 64 MiB, check actual free/peak VRAM after resident model state, and abort cleanly on descriptor overflow or allocation failure. Treat improvements as unproven until repeated end-to-end results and correctness both pass; do not interpret reduced host bytes or a faster component as an overall speedup.
