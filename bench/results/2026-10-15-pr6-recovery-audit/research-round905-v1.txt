# Round 905 — Metric query pool creation failure

**Classification:** decision support  
**Scope:** read-only audit of the exact recorded zetMetricQueryPoolCreate failure, installed version alignment, context use, plausible OA dependencies, and one bounded next diagnostic. No build, test, GPU job, process inspection, permission change, or package change was run.

## Finding

The failure is specifically the first performance-query-pool creation: zetMetricQueryPoolCreate returns 0x78000004 (ZE_RESULT_ERROR_INVALID_ARGUMENT) after the ComputeBasic event group has enumerated and metric-group activation has returned success. The call’s logged arguments are non-null handles, type=0 (performance), and count=64; the group reports event-based sampling and 83 metrics. The run exits 125 before a query begins or any kernel result is completed. Its status remains failed and unqualified; it is not evidence of a GPU hang, permission fault, bad model kernel, or performance-counter sample.

The installed runtime and loader versions align with their exact local upstream tags. The sharper compatibility concern is below that layer: the compute-runtime 26.31.39395.14 manifest pins Metrics Discovery 1.16.192 and Metrics Library 1.0.234, while the recorded process loaded Metrics Discovery soname 1.16.188 and Metrics Library 1.0.231. Package metadata identifies them as intel-metrics-discovery 1.14.188 and intel-metrics-library 1.0.231. That is a real revision skew to investigate, but neither the manifest nor the failure record proves that it caused this result.

## What can produce this exact result

In the exact compute-runtime tag, the exported entry point forwards the arguments into the Level Zero tools implementation. For the observed performance type, OaMetricGroupImp forwards the context and group to OaMetricQueryPoolImp::metricQueryPoolCreate. That function derives the OA metric source from the device. If a streamer is already active it returns ZE_RESULT_ERROR_NOT_AVAILABLE, which is not the observed code.

Several separate false-return paths are collapsed into ZE_RESULT_ERROR_INVALID_ARGUMENT:

1. createMetricQueryPool() rejects a group unless its sampling type is event based. The captured group has event-based flag 1, so this specific gate appears satisfied.
2. On the normal non-implicit-scaling path, any metricPoolImp->create() failure becomes INVALID_ARGUMENT. For performance pools, this can be an unsupported descriptor type, the event-based group check above, or MetricsLibrary::createMetricQuery() returning false. In the latter, the source returns false when the Metrics Library is uninitialized or its api.QueryCreate() call does not return success. It does not preserve that lower-level status in the Level Zero result.
3. If the Metrics Library query object succeeds, allocateGpuMemory() asks the library for the GPU report size and multiplies it by the pool count. A failed/unavailable parameter query, uninitialized library, or zero report size produces allocation size zero, which returns false and is also mapped to INVALID_ARGUMENT. A null graphics allocation follows an unrecoverable path rather than this normal return.
4. If implicit scaling is active, failure to create any per-subdevice pool is separately mapped to INVALID_ARGUMENT. The record does not establish whether that branch applies to this device.

The count=64 value is not inherently malformed: the exact PTI source initializes performance pool descriptors with the same count of 64, and the Level Zero header describes it as internal slots, not a metric count. However, the exact Metrics Library call receives Slots=64, and the report allocation is multiplied by 64; the record cannot show whether either provider operation accepts that count with the installed library revision.

## Context difference

The receipt logs activation on context 762431288 and pool creation on context 765965576. This matches the pattern in PTI commit 6c0d6b0: unitrace creates a private metrics context, activates the metric group on its device descriptor, then obtains query pools with the context stored against the application command list.

In the exact compute-runtime 26.31.39395.14 OA pool-creation implementation, hContext is forwarded but is not read in OaMetricQueryPoolImp::metricQueryPoolCreate; that method selects the metric source from hDevice. Thus this context split is real, but the reviewed implementation does not use the pool call’s context to create the OA query object. It is not enough to label context mismatch as the cause of this INVALID_ARGUMENT. This source conclusion is version-pinned to 26.31.39395.14 and does not cover behavior after pool creation or downstream kernel/query use.

## Version, OA, and permission dependencies

The runtime/loader pair is consistent with the compute-runtime tag’s Level Zero 1.32.0 dependency. The Metrics Discovery and Metrics Library revisions seen by the process are older than the revisions in that exact runtime tag’s build manifest. Since MetricsLibrary::createMetricQuery() discards the internal QueryCreate status, that skew could match the observed error. It remains a candidate rather than a proven incompatibility; the checked sources do not state a minimum runtime-compatible version range for these independently versioned packages.

Intel’s current Metrics Discovery documentation lists Battlemage support and a Linux 6.11 minimum kernel plus Mesa 24.2 for Xe2-HPG event-based measurements. The receipt’s 7.0.0-38 kernel exceeds that kernel floor, but the Mesa version is not in the receipt. Enumeration and activation succeeded, which shows that this run got through those stages; it does not prove Metrics Library query creation, report sizing, or OA data collection is healthy.

Permissions remain unresolved. Level Zero can report a dedicated insufficient-permissions result, but this driver path can hide a Metrics Library query failure behind INVALID_ARGUMENT. A PTI B580 issue documents the i915/perf_stream_paranoid and xe/observation_paranoid checks and reports a different error, ZE_RESULT_ERROR_DEPENDENCY_UNAVAILABLE; it is a relevant example, not evidence that permissions caused this run. The captured record contains no OA policy value or effective-credential snapshot. Both Metrics Discovery and Metrics Library were mapped into the process, so missing-package-at-load is not a fit for this receipt.

## Smallest useful next diagnostic

Use the existing tiny owned API harness for one bounded, unprivileged reproduction with the same event group and descriptor. Add local diagnostic logging around the exact Metrics Library boundaries: initialization state, GetParameter(QueryHwCountersReportGpuSize) status and returned size, QueryCreate status and slot count, then report whether allocation sizing passed. These are the hidden branch points that the current Level Zero result collapses. If QueryCreate alone fails with 64 slots, repeat once with count 1; keep all other inputs and the process environment unchanged. The result separates a count-sensitive provider rejection from library initialization/report-size failure without running a model or kernel workload.

Alongside it, record the already-installed package versions and read the applicable xe observation policy and effective user identity without changing them. Do not elevate privileges, alter observation_paranoid, grant capabilities, restart services, or reset the device. A nonzero policy value or denied access would make the OA permission route more plausible; an allowed value does not rule out the version-skew or provider-configuration paths.

PTI’s documented time-based metric sampling mode (-k/--metric-sampling) is an alternative collection route to event-based query pools (-q/--metric-query). It is a source-supported fallback to try only in a bounded smoke run after the direct cause is clearer. It uses the same driver, Metrics Discovery/Library stack, and OA access, so it does not bypass a dependency mismatch or permission restriction and is not yet qualified here.
