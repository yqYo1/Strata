## Contract and actual timestamp path

The primary normative reference is SYCL 2020 Revision 12. `command_start` must be greater than or equal to `command_submit`; `command_end` must be greater than or equal to `command_start`. Equality is permitted by those inequalities. The spec promises no particular timestamp accuracy. A zero value is therefore not disproved by the inequalities alone, but it is ambiguous evidence of a usable measurement. Keep separate flags for (a) normative order failure, (b) zero/sentinel or unavailable query, and (c) the collector's stricter service-quality rule. In particular, `end == start` is not a SYCL contract violation; it can still fail the collector's current `end <= start` service gate. Do not silently accept an order violation or relabel a strict collector rejection as a normative failure.

The current upstream Intel LLVM `sycl` source snapshot was inspected only as a reference, not as the installed runtime. Its L0 v2 `event.cpp` path queries `zeEventQueryKernelTimestamp` for command start/end, masks timestamp bits with the device valid-bit mask, converts ticks using the device timer resolution, and adjusts the end for one counter wrap. The same implementation's submit timestamp is captured separately before enqueue through a global-device-timestamp path. Thus `start < submit` can implicate submit/device clock conversion or clock-domain handling even where the start/end pair looks plausible; a timestamp-query wall measurement does not test that relation. The timestamp path does not itself establish that all command kinds produce meaningful kernel timestamps.

The Level Zero Programming Guide says a kernel-timestamp event is signaled by kernel-launch commands and describes start/end as kernel execution timestamps; the API exposes device timer frequency and valid timestamp bits, and wrap handling is a client responsibility. That makes a copy-specific timestamp limitation a concrete candidate: current UR v2 code routes a profiled command event through a kernel-timestamp query, while Level Zero's underlying documented event type is kernel-specific. An unsupported query would normally surface as a query error; the current model report instead says guard rejection after numeric query, so unsupported-with-error alone does not explain it. A successful API call returning zero/stale/inapplicable timestamp data remains possible until the ledger records per-query status and values.

UR v2 also has reusable event pools and a counter-event path. An event handle remains associated with its profiling record and a borrowed event returns to its pool when its UR owner is released. Retaining the SYCL event through the checked drain and timestamp query should prevent ordinary early release in the application; the Main source audit and R991 review found that successful production owner order sound. However, Intel's pinned history contains an explicit earlier fix titled “Fix incorrect profiling timestamps when events are reused,” so stale/recycled timestamp storage is a real implementation failure class, not a speculative API concept. Its relevance depends on the actual installed UR commit and exact event-provider/pool route; neither is known here. Counter-event pooling is not proof that the captured queue events use that path.

The model queue is in-order and profiling-enabled; that ensures ordering/submission context but does not guarantee meaningful timestamps for every operation kind, nor prove every command uses the same Level Zero engine/event implementation. The model's small rejection clusters (all route-map uploads plus full sets of four job phases at only layers 15/31) are more selective than a general timer-resolution problem. They are compatible with command-type handling or per-slot/event reuse, but do not establish either. The 52 ns device resolution makes raw ticks essential: a returned positive duration below one tick merits a conversion/rounding check, while a zero-duration event may satisfy SYCL ordering but is not evidence of resolvable service. Counter-wrap errors usually leave a distinctive mask-boundary pattern in raw ticks; the current adapter has an explicit one-wrap adjustment, and 39K query intervals plus the 25/141 accepted controls are counterevidence to a broad conversion failure, not a substitute for raw values.

Traced versus untraced evidence is also not interchangeable. The 25/141 controls were traced; the model's `STRATA_TRACE` diagnostic did not enable the UR tracing layer. Tracing can perturb host enqueue/batching and event-allocation timing, potentially exposing or hiding a lifetime/reuse race, but it should not redefine the SYCL timestamp inequalities. Compare these modes only in separately owned processes with fixed pre-exec settings. A traced/untraced difference would be a clue, not proof of a performance cause. `start-submit` is not host CPU time, `end-start` is not EU occupancy or device busy time, and the partial four-window sample is not whole-request utilization or speed evidence.

These are hypotheses, not attribution. The easiest first split is by command type and raw/status values. The layer/job pattern then makes event identity/generation and query path the next discriminants if kernels remain affected.

For each rejected event record the three converted `uint64_t` values, each query's return/error status, which guard booleans fired, timer resolution and valid-bit mask, event kind/command type, layer/phase/job, queue identity, and a stable event owner/generation identifier. 2. Use the ledger to select only the failing shapes for a bounded same-queue follow-up: one representative ordinary-host route upload (actual host pointer and size) plus gather/GU/SwiGLU/down kernels. Retain event owners through a checked drain. For each, capture raw native L0 timestamp ticks/status alongside UR/SYCL converted fields when available, and log pool/event generation and engine/queue routing. Keep this a diagnostic, not a model-speed cohort.
3. If raw evidence points to tracing or reuse, compare one fresh-process traced and untraced arm with the same source/binary/commands and fixed environment. Preserve the same query and retention path; do not switch environment variables after runtime initialization. If it points to command kind, compare copy and kernel APIs directly before widening the model sample. Keep correctness/fault closure and performance interpretation separate.

Do not relax start>=submit or end>=start. If the ledger reports `end == start`, record it as contract-ordered but below-resolved service under the current collector rule; a separate policy decision may later distinguish this from a strict ordering violation. Preserve the existing failed result byte-identically and attach the ledger to the follow-up evidence; do not overwrite or reinterpret the original.
