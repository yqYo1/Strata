# R1008 — GPU-local weighted MoE reduction: layout, tiling, and epilogue traffic

Classification: **knowledge collection** (hold body; retrieve for a concrete accumulation decision). Date: 2026-10-17. Budget: 12,000 bytes. Scope: compare layout, cache/scratchpad tiling, and Down-GEMM epilogue fusion for the fixed example. This is mechanism research, not a patch, profile, speed prediction, model numerical decision, or adoption recommendation. No build, test, GPU/profile/process/Git work or product edit was done. No XeStrata material was consulted.

## Fixed contract and evidence boundary

Only the immutable `moe-accum-device-source-v1` snapshot was read. Task-provided SHA-256 pins: `moe_accum_plan.hpp` `96e976e24225e5929e20e69995d22e5d603b10fa565147bebadf2e830a00dd7d`; `moe_window_routes.hpp` `62abedecd553ababefcdabc4c549d75844f848027516293ed028a46fce617379`; `src/prefill/sycl/native16.cpp` `7567f607b4b564c21c8fc4ee21ed41ae7f419a3f0a23a866836f1a85e658627c`; `tests/sycl/moe_accum.cpp` `733d12dbbec19b64baac39f71f64b21899e5550b3d0d282d9904f2e9c0ae2ec1`. The candidate's `moe_accumulate` reads stored BF16 Down, widens it, then computes `fma(route_weight_fp32, down_fp32, accumulator_fp32)`. `moe_finish` combines that accumulator with widened shared BF16 times sigmoid(FP32 gate), then stores BF16. Preserve BF16 rounding before weighting and the intended expert order; moving conversion after weight, replacing FMA with separate multiply/add, or changing reduction tree/order changes arithmetic.

Example: 65,536 × 2,560 FP32 accumulator = 671,088,640 bytes (640 MiB), or 80 MiB per 8,192-row chunk. There are 512 experts, top-10 routes, jobs <=8,192, and each token has at most one row per expert. This guarantees one writer per token/column *within one expert job*; different experts can target the same output, so parallel jobs race with plain stores. A SYCL work-group barrier/CUDA block barrier cannot order different workgroups. Ordered same-queue launches can, but leave repeated accumulator RMW traffic. Metadata says planning/route CPU checks, strict SYCL compile and 3-row GPU smoke passed; 65,536 integration and performance remain unqualified. The helper source alone does not prove full owner lifetime, queue order, or error retirement.

## Dataflow choices

| Choice | Traffic/locality | Ordering and cost/risk |
|---|---|---|
| **Expert-major FP32 RMW (candidate)** | Initialize 640 MiB, then 10 routes/token each read+write the destination: nominally ~12.5 GiB aggregate accumulator traffic, plus Down and route traffic. Down rows are contiguous across N; token destinations are permuted, though each row's N is contiguous. Cache residency is unknown. | Ascending expert launches on one in-order queue give fixed per-output FMA order without atomics. Simple and no huge partial buffer; repeated reads/writes, scattered rows and serialized jobs remain. No evidence this device is bandwidth-bound. |
| **Token/column tile owner** | Load an output tile once, collect contributions, write once: potentially removes repeated plane RMW. But inputs are expert-major and outputs token-major. Owner either gathers up to ten expert rows indirectly (N-coalesced, token-scattered) or uses an expert-to-token staging/transpose (extra scratch writes/reads). `M×N` FP32 tile is `4MN` bytes plus fragments; larger tiles increase register/SLM use and may reduce occupancy. | One owner can replay experts in order and preserve FMA sequence. Barriers coordinate only within its workgroup. Dynamic route maps, masks, tile queues and tails need bounded capacity. Saved output traffic can be lost to gather/staging and synchronization costs. |
| **Private partials + final reduction** | Removes contended writes if experts write disjoint planes. One plane per expert would be 512×640 MiB; one per top-k slot 6.25 GiB. Use expert groups/windowed scratch to bound space, then merge; each extra FP32 plane costs write/read traffic and initialization. | Fixed tree/group merge is deterministic but changes order and likely FP32 results. Exact baseline order requires replaying ordered terms, not pre-summing groups. Atomics avoid scratch but allow scheduler-dependent order and do not preserve baseline. Small jobs can underfill hardware; “reduce later” is incomplete absent scratch bytes, ordering and synchronization. |
| **Fuse weighted accumulation into Down GEMM epilogue** | GEMM's FP32 accumulator is register-local; epilogue can convert to BF16, widen, weight/FMA into FP32 output, eliminating Down plane write/read and one kernel. It does not remove accumulator RMW. Row N stores remain contiguous but token-row starts are scattered. | Must explicitly BF16-round GEMM result *before* weight/FMA. Weighting in FP32 then converting changes arithmetic. Concurrent expert epilogues still race unless atomics/private partials or ordered launches. Custom scatter can hurt GEMM's regular store path or raise register pressure; actual adapter support is unknown. |

Hybrid: route epilogue contributions into bounded per-token-tile bins, then one owner merges in expert order. This regularizes output ownership but adds bin metadata, up to top-10 records/token, capacity checks, synchronization and staging passes. Persistent token-tile owners have similar dynamic work assignment and GEMM-utilization questions. Neither is known to be faster.

## Hardware mechanisms and limits

**Intel/SYCL.** The pinned SYCL 2020 specification defines `local_accessor` and `group_barrier` at workgroup scope, not as a device-wide job-order primitive. Public Intel SYCL-TLA GEMM guidance describes keeping matrix accumulators in registers then exchanging layouts through local storage for coalesced global epilogue stores. Its 0.9.2 changelog lists grouped-GEMM epilogues and SLM/EVT work. IntelLabs Xe-Fuse documents batched MoE GEMM with per-batch SwiGLU epilogues: proof of a possible fusion shape, not B570 or Strata adapter support/performance. Intel's occupancy calculator explicitly treats SLM and subgroup choices as occupancy constraints. On B570, tile size must be based on generated kernel/register/SLM and actual implementation support, not CUDA warp assumptions.

**CUDA/HPC.** CUTLASS documents the common epilogue pattern: matrix-optimized accumulator fragments are rearranged through shared memory for coalesced output stores. CUTLASS 3.x's original NVIDIA engineering blog explains fused epilogues removing intermediate tensor movement; CUDA Ampere technical guidance shows asynchronous global-to-shared staging and pipelining to overlap loads and compute. These mechanisms fit regular GEMM tiles. TMA, `cp.async` and their barriers are architecture-specific and do not transfer as B570 capabilities. None solves token-index scatter by itself.

**AMD / general.** Versioned HIP docs describe LDS and barriers within a workgroup; rocWMMA warns shared-memory use can require explicit workgroup synchronization. This reinforces the local-memory scope limit, not a target port recommendation. Matrix-engine GEMM mainloops favor regular tiles; irregular epilogue scatter can erode that advantage.

## Transferable design checks

1. Fuse at the last producer: remove materialized per-job Down only if its BF16 conversion is retained before weight/FMA. Fusion saves Down tensor traffic/launch, not shared-output RMW.
2. Establish output ownership before parallelizing experts. Unique token per expert is not global uniqueness. Use ordered launches, independent partials plus defined merge, or atomics only if changed ordering is accepted and validated.
3. Count route permutation costs: compare expert-row gather into token tiles against expert-to-token staging. Include route/weight reads, bin metadata, scratch clear/write/read, barriers, masks and drain.
4. Bound `M×N` live tile resources against actual SLM/register/occupancy and spills; generic occupancy aids are not achieved occupancy evidence.
5. State conversion and FMA sequence explicitly: `bf16(a) -> fp32(d) -> fma(weight,d,accum)` preserves the stated Down boundary; `fma(weight,a,accum)` does not. Check rounding mode, subnormal/NaN behavior and compiler contraction.
6. A single fused kernel still has no cross-workgroup barrier. Epilogue fusion cannot silently synchronize experts.

A useful Main-owned comparison, if opened later, pins configured source/compiler/runtime and measures the full dependency path (init, route availability, GEMM, conversion, weighted update, shared epilogue, drain), bytes, launch count, peak allocation, host submission/wait separately, and repeat whole-context timings. Numerical comparator must isolate identical routes/weights, BF16 Down bits, FMA order and final BF16 changes against selected SGLang/vLLM path. No such evidence was gathered here.
