## Evidence and current dispatch

Current `src/kernels/sycl/prompt_attention.cpp` is a separate `joint_matrix` kernel path. `qsa_prompt_attn_batch` selects KV mode from pool pointers, validates the request, checks matrix admission and dispatches mode-specialized kernels. There is no current `STRATA_PROMPT_ATTN_OLD` environment switch in this path; the historical name must not be assumed to select it. R561's `STRATA_PREFILL_ATTN_LAYOUT=1` is a fallback decode-layout selector and leaves this function untouched. The R561 result therefore says nothing about changing this matrix kernel.

The current path uses `CH=32`, `WG=128`, subgroup width 16, accumulator tile 8x16, and K dimension 16. Each work-group handles one query and one of two KV heads. Its 16-row local tiles carry 12 live query heads plus four zero rows. Four subgroups cover two 8-row bands by two 16-cell bands. Per chunk, K is staged and scored, online softmax updates row maxima/sums, V and split probability tiles are staged, then four output dimension tiles update the FP32 accumulator. The loop advances by 32 cells.

The donor at `1eb89482a4afd20277ae0405780ed4f8eb98eb20:sycl/src/kernels/cuda/qsa_prompt_attn_xmx.dp.cpp` is historical implementation evidence, not a ready port. It used `CH=64`, `WG=128` with eight subgroups, 16x16x16 matrix tiles, packed K-transpose and V layouts, a shared K/P local-memory region, and a distinct score/softmax/PV schedule. Its own source comment records that an earlier 16-cell version was three times slower than its FP32 fallback due to staging, barriers and accumulator traffic; v2 moved to 64 cells to reduce per-cell overhead. That is a candidate rationale only: it is not evidence that a current-root CH64 port will be faster or safe.

## Admission calculation and workload arithmetic

`matrix_available` requires subgroup size 16, max work-group size at least 128, one reported FP16×FP16→FP32 combination able to cover 8x16x16, and reported local memory at least `51648 + 2180*KG + 128*VG` bytes. For INT8 K/V mode 1, `KG=VG=4`, so the explicit admission threshold is **60,880 bytes (59.45 KiB)**. Mode 0 threshold is 53,956 B; modes 2 and 3 use `KG=VG=8`, giving 69,088 B. These are source admission thresholds, not a query of the B570's reported capacity or proof a launch compiles/runs. The current mode-1 accessors sum to roughly 57,808 B by declared element counts before any implementation/compiler allocation details; the threshold includes additional allowance. If the device-reported local-memory value falls below the threshold, this source rejects matrix dispatch and returns false for the caller's fallback. No device property was queried here.

For an int8 run bounded by `cap≈2051`, at most `ceil(2051/32)=65` chunk iterations occur per query/KV-head group; the actual count comes from each row's `steps` and may be smaller. At `n_q=4096`, the launch has 8,192 work-groups. Assuming 2,051 selected cells for a deliberately conservative upper-bound illustration, one query's two KV heads read about 2,101,376 INT8 K/V elements (2 heads × K and V × 2,051 × 256), plus 65,632 FP16 scale elements (K/V × 2 heads × 2,051 × 4 groups). This is about 2.17 MB/query of logical source operands before IDs, query vectors, and cache-line/transaction effects, or roughly 8.9 GB over 4,096 queries. This is arithmetic from the shape, not measured physical DRAM traffic.

For each query, the useful score and value products are each 12 heads × 2,051 cells × 256 dimensions: about 6.30 million multiply-accumulates apiece, 12.60 million total (about 25.2 MFLOP/query if one MAC is counted as two operations), or 51.6 billion MAC over 4,096 queries. The same 12-head sharing explains both the opportunity and the limit: K/V rows are loaded/staged once per KV head and reused across its 12 query heads, while each head still requires its own score and weighted-value arithmetic. The 16-row tile pads four heads; matrix issue work can therefore be up to 16/12 = 1.33× the live-row arithmetic before considering other tile waste. Repeated 32-cell chunk setup, barriers, score scaling across four K scale groups, online normalization, FP16 hi/lo probability conversion, and four output tiles are separate costs not represented by the useful-MAC count.

An intentionally broad arithmetic roofline can be stated without claiming achieved performance: the useful workload is about 25.2 MFLOP/query, and the logical INT8+scale operand lower-bound is about 2.17 MB/query at width 2,051. A bandwidth ceiling would be `effective bytes/s ÷ 2.17 MB/query`; a compute ceiling would be `effective FP32-equivalent FLOP/s ÷ 25.2 MFLOP/query`, and the smaller ceiling is only a first-order bound. At 4,096 queries those denominators become approximately 8.9 GB and 103 TFLOP. Neither device rate nor achievable cache/traffic behavior is established by this report, so no numeric time or speedup estimate is justified.

The prior `long-phase-summary.json` records QSA attention at 49,455 ms / 23.85% inside a 207,576 ms diagnostic run. It explicitly labels phase intervals nonexclusive and still lists actual matrix acceptance/decline as unobserved. This is not kernel time, proof the matrix path ran, or a basis for multiplying a proposed kernel speedup into end-to-end PP.

## Candidate for Main's decision

The most defensible matrix experiment is a current-root, mode-1, opt-in CH64 geometry variant that retains the current numerical contract and entrypoint safeguards, paired against CH32 on the same actual selected IDs and widths. Its source-based hypothesis is halving chunk iterations (at width 2,051, 65 to 33), reducing repeated per-chunk setup/barrier/softmax work, and using the donor's 64-cell batching lesson while keeping current-root arithmetic and fallback integration. It is not a recommendation to copy the old kernel wholesale. CH64 doubles several local arrays: current `kv` grows from 16,384 to 32,768 B; `phi/plo` from 8,192 to 16,384 B; score storage from 2,048 to 4,096 B; mode-1 scales from 2,048 to 4,096 B; row IDs from 256 to 512 B. Together with fixed query, final accumulator and other arrays, estimated declared local storage rises by about 29 KiB over the current accessor total, to roughly 87 KiB, before compiler/register effects. Admission must therefore be recomputed from exact declarations/alignment and checked against device-reported local memory; do not silently keep the 60,880-B CH32 gate.

An alternative is retaining CH32 while remapping the same work among subgroups to reduce padded matrix rows or make selected-cell staging more contiguous. This may avoid the larger local-memory footprint, but the current supported target shape is 8x16x16 and any proposed remapping must preserve those joint-matrix constraints. Do not infer support for the donor's 16x16 accumulator or packed B layout from the current `matrix_combinations` check, which only establishes the current 8x16x16 request's capability predicate.

Both candidates must preserve exact INT8 code values and FP16 per-group scale interpretation; the current score path scales each four-group partial after matrix accumulation. Q is scaled and split into hi/lo FP16, both halves are accumulated into FP32 score accumulators. Probabilities and scaled V are also split hi/lo FP16 before FP32 accumulation. The donor's alternate scaling order, exp2 formulation, tile layout, scale folding, Q4 path, or FP16 native mode must not be merged casually. Compare score/attention/residual and first/final logits with declared tolerances, include finite/NaN behavior and empty/missing selected rows, then use exact-model long-context retrieval and task/quality checks; matching output token IDs alone is not a numerical or quality gate.
