# Query-group reuse for sparse selected attention

Classification: knowledge collection; hold for a concrete query-row reuse decision.
Scope: compare exact cross-query reuse of selected KV data for the supplied AMD 5600X / 128 GiB / Intel Arc B570, driver 1.17.39395+14, LLVM 22.1/libsycl 9, forced Unified Runtime Level Zero v2 context. No local runtime, build, test, model, profiler, GPU, process, or Git work was done. This report is a design reference, not a B570 performance claim or a candidate adoption.

## Prior-index boundary and current evidence

I read the shared index metadata and the requested R982 body. The nearest indexed QSA items are R568 (head tiling/SLM), R605 (attention tiling; one query row per KV head), and R731/R732 (selector and attention attribution); their metadata does not establish cross-query selected-ID reuse. The latest subgroup-softmax candidate metadata is separate again. R982 is a held resource-ceiling survey: its reviewed index marks another ceiling capture unschedulable until a specific component/model receipt and same-process device identity exist, and the report measures no achieved B570 ceiling. I do not repeat its resource ladder or treat 160 `max_compute_units` as a hardware-unit count.

Main's supplied QSA row-major/subgroup cohort is a same-binary synthetic component result (median 333.318 to 322.337 ms; correctness and fault gates passed). It tests subgroup normalization inside the existing query/KV workgroup. It supplies no cross-query overlap measurement, selector locality, model speed adoption, or resource bound. The supplied QSA/attention queue intervals include host gaps and do not establish utilization. Keep these results separate from query-row tiling.

For this task, “query group” means multiple query-token rows sharing selected KV within a KV-head path. It does not mean the already-existing reuse across the 12 query heads of one KV head. The supplied dimensions are 2 KV heads, 12 query heads per KV head, head dimension 256, width 2051, and a 32-cell online tile; they do not alone define each query's full selected-ID count, its index domain, page granularity, or real learned overlap. In formulas below, `K_i` is the actual selector count for row `i`; do not assume the 32 tile cells are 32 selections for every grouped row.

## Evidence from the actual Qwen3.8-Flash-Next path

The strongest model-specific analogue is vLLM's QSA tile-union RFC/PR (#55394/#55430). It reports real Qwen3.8-Flash-Next selector dumps at 8K where adjacent query rows had 0.87–0.94 Jaccard overlap in compressed block IDs, then proposes one prefill program per consecutive-row tile and KV head: traverse the exact union once, mask each row to its own selection, and retain row-specific online-softmax state. The RFC's original 2.24x operator comparison used a stale pre-split-K baseline; after correction, the author reported about 1.50x on an 8K selection replay and 1.42x on another chunk, including union-build cost. The author later closed the PR after an active-path breakage was fixed and remeasured: on the cited 29K case, TTFT improved 1.6%, versus 1.0% at 8K and a 0.5% regression at 16K; sort/pack/build glue and added idle consumed part of the kernel gain. The author calculated a 3.78% whole-prefill ceiling from one profile where QSA attention plus index was 12.2% of GPU kernel time. These are NVIDIA GB10 observations, not B570 predictions; selection overlap was model-derived, while some kernel replay used random K/V. The PR was closed, not merged. This is direct evidence that real Qwen selector sets can be highly correlated, plus equally direct evidence that savings can be too small after Amdahl and glue costs.

SGLang's current DSA backend documentation exposes a related exact, opt-in `triton_sparse_mla` prefill union of adjacent query tokens (`--dsa-triton-union 2|4`), with head/tile constraints and CUDA SM90+ eligibility. Its backend disables the union in deterministic-inference mode because batch neighbors and group tails can change an output. This is an implementation reference for the execution pattern, not an Arc port: the documented kernel is NVIDIA-specific and does not establish B570 behavior. vLLM's sparse-MLA utilities also represent selected indices as `[num_tokens, topk]`, making the per-token support relation explicit; vLLM QSA's tile-union RFC consumes compact per-row block IDs before expansion, rather than recovering selection from a dense/expanded cache view.

## Four reusable execution patterns

| Pattern | How it reuses across rows | Cost and limiting case |
| --- | --- | --- |
| Independent row gather (current baseline) | Each row gathers its own set. Existing device caches may reuse sectors naturally; no cross-row data structure, barrier, or ownership change is needed. | Repeated loads/dequantization may remain when IDs overlap. Cache hits can make explicit union staging redundant. This is the control to beat. |
| Fixed adjacent-row union (SGLang / vLLM) | A fixed group of `g` rows forms `U = union(S_i)`. A workgroup gathers each unique entry once and shares it through registers/subgroups or local memory; each row applies its own membership and causal mask. Keep each row's FP32 online-softmax maximum, denominator, and output accumulator. | Build/remap and barriers cost time; a dense `g × |U|` score/value tile may do masked work. Larger groups can reduce workgroup count, raise register/SLM use, and widen the union. The vLLM case's small TTFT gain and loss at one short context are concrete counterexamples to assuming locality always pays. |
| Exact set decomposition / cascaded sharing (QUILT) | For two unique Top-K lists, sort their concatenation with source tags; equal adjacent IDs identify the intersection, and remaining IDs are row-private. Recurse across group sizes so entries shared by only a subgroup are not reloaded by all rows. Prepare segments ahead and pipeline set work with attention. | Sorting, remapping, and segment scheduling are critical because sparse attention has little spare work. Reordering segments changes reduction order. QUILT's optional low-importance tail clipping is approximate and is outside this exact-support reference. Its arXiv results use GLM-5.3/DeepSeek-3.2, not this engine or B570. |
| Bounded affinity regrouping (PageWeaver) | Within a request-local window, GPU search greedily groups rows that add few new pages, then an ID-aware union kernel computes complete outputs into original row slots. Supports stay unchanged; it changes group membership rather than sharing probabilities or softmax state. | Search and permutation cost every call; nonadjacent rows can lose locality. The paper's bitset search scales as `O(N W ceil(B/32))` for N rows, window W and bitmap capacity B. Its H200 study found modest incremental online gains on selected 64K captures, regressions at 8K, and a case where random IDs slowed execution. It uses a bounded bitmap and identity fallback beyond capacity. |
| KV-page-outer incidence inversion (PageWeaver / MSA family) | Build, for each page, the list of query rows selecting it; process the page across those queries, potentially sharing work even for distant rows. | Splits each row's attention over page groups, requiring partial FP32 softmax state and a stable log-sum-exp merge, work lists, workspace and extra launches. The PageWeaver study won on constructed interleaved supports but lost to query-owned Union8 on its examined model captures; one low-overlap case was 1.827 ms versus 1.368 ms. It is a useful alternative when affinity is nonlocal, not a default. |

The first fixed-union form is the most directly comparable held design for this fork: keep query groups request-local and small; form an exact per-tile union; stage bounded portions of it; preserve each row's support, causal position, output owner and independent FP32 recurrence; and keep the current independent path available. Query groups may not cross workgroups if reuse depends on SYCL local memory. A larger group spanning workgroups needs another global synchronization/staging design and its cost belongs to the comparison.

## Locality prerequisite and GPU-only census cost

The needed fact is not “selected IDs look sparse,” but the per-call distribution of exact overlap at the chosen grouping boundary. For each actual query row and KV-head path, record `K_i`, each adjacent-pair Jaccard, `|U|` for candidate group sizes, duplicate multiplicity, selected logical pages, and resulting cache-line/sector identities. Summarize by QSA layer, request/chunk, context length and query position, including tails. Entry overlap and transaction overlap differ: nearby token IDs may share a cache sector without being equal; conversely an exact-ID duplicate may already hit cache. Keep logical selected bytes, union bytes, and measured physical traffic separate.

The census can stay on GPU: consume the selector's existing device-resident IDs, compute group counts/overlap in a diagnostic kernel, and reduce to small histograms/counters in device memory. Do not copy the routing rows to CPU or make an input-dependent host dispatch. A dense bitmap needs `ceil(B/32)` 32-bit words for a B-ID universe: 2051 IDs require 65 words (260 B) per row bitmap, while the full 262144-position domain needs 8192 words (32 KiB) per bitmap. A group-union bitmap can count unique IDs, but per-row overlap needs row masks or set intersections; clearing, atomics, popcounts, sorting, and remapping all have costs. Local sorting scales with the `sum(K_i)` IDs in a tile; a bitonic-sort illustration with 12 rows × 32 IDs pads 384 inputs to 512 and entails about 11.5K compare-exchange elements before data movement and barriers. These are shape-derived work estimates, not B570 timing. Fuse census into union construction when it can directly drive the exact gather; otherwise charge its extra launch and scratch traffic. Keep all IDs on device and compare the full attention call, not census-only time.

For equal-sized sets of K IDs, pairwise Jaccard `J` implies `|A union B| = 2K/(1+J)`. This converts the vLLM 0.87–0.94 observed Jaccard into roughly 46.5–48.5% fewer unique pair loads than two independent gathers, before transaction size, cache hits, union-build, masked compute or synchronization. It must not be transferred to the current fork's selector: its width, compression, top-k budget, token/page identity and hardware path differ. Conversely, a uniform-spread synthetic selector over a large domain predicts little duplicate work; it is a null model only, not evidence that learned QSA selections are uniform.

A fair cost comparison is:

`net = removed repeated KV transfer/dequant + any useful tile gain - union build/remap - masked or padded arithmetic - SLM/register occupancy loss - barriers/launch/gaps`.

A smaller `|U|` is not itself measured bytes saved or faster time. Measure attention device service and full QSA path; do not call queue coverage utilization. Short contexts where each row's support is not saturated, low-overlap tails, and cache-hot IDs may favor the independent kernel. The vLLM RFC reports its union starts helping after selection saturates, while its fixed-row grouping was neutral or negative on other contexts.

## SYCL, memory, synchronization and numerical constraints

`sycl::local_accessor` storage is private to one workgroup and shared by its work-items; `sycl::group_barrier` synchronizes that group. A practical query tile therefore needs one uniform barrier after staging and another before reusing a buffer. Every work-item must reach each workgroup barrier, including masked rows and empty tails. Subgroups alone cannot publish data across workgroups. The SYCL contract does not promise a particular SLM bank geometry or bank-conflict rate. Intel's generic GPU guide describes SLM as a workgroup-managed cache and warns that same-bank access conflicts serialize; neither the guide nor the B580 sibling numbers establish B570's usable capacity or bank mapping under the supplied runtime.

Stage only the live union slice, not a full 262144-token KV window. Capacity is `|U_slice| × bytes_per_actual_KV_entry` plus IDs, masks and scratch, multiplied by the number of in-flight buffers. As a conditional example, one 256-element BF16 vector is 512 B: 64 unique entries occupy 32 KiB, 128 occupy 64 KiB, and 384 occupy 192 KiB per KV path; separately stored K and V would increase this. These are arithmetic examples, not assertions about the fork's physical representation or B570 SLM. Double buffering doubles the staged union footprint. Large unions can spill or reduce active workgroups before memory bandwidth improves; query the actual B570 property and inspect compiled resource use if a Main-owned candidate is ever built.

Reuse K/V only. Preserve each query/head's current FP32 max, sum and output accumulator; no softmax probabilities or normalization state may be shared across different query rows. Keep the existing BF16 operands/storage and FP32 accumulation/reduction boundaries. Exact integer union/membership preserves the selected support, but processing keys in union order can change floating-point reduction order; compare against the selected SGLang/vLLM numerical contract, including causal tails and invalid rows. Do not import QUILT's optional pruning. A regrouped row must still address its original request, logical position and output. Query groups must stay within request boundaries; SGLang's deterministic-mode guard is evidence that batch-invariance requirements may matter even when set membership is exact.

## Held conclusion and evidence limits

Cross-query exact KV reuse is a distinct option from the measured subgroup-normalization change, and real upstream Qwen3.8 selector evidence makes it technically plausible. The highest-value reusable reference is a request-local, exact union of a small set of neighboring query rows with per-row masks and private FP32 online attention state; QUILT cascade and PageWeaver affinity are alternatives if actual sets show heterogeneous or nonlocal overlap. The vLLM experience is the counterweight: an impressive kernel ratio was reduced to roughly 1–2% TTFT by path cost, other contexts regressed, and the PR was closed. There is no captured learned-ID overlap, B570 local-memory/sector result, or current-engine query-group timing in this task, so this remains a held knowledge collection rather than a performance recommendation.
