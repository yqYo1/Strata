## Source facts and measured question

`qsa_block_scores` validates `nq` 1..65535, positive block capacity, and the fixed indexer shape (4 heads, D=128, cells/block=4). It launches `nq*active` work-groups, each exactly one required SG32. Group ID gives `(qi,b)`. Each query reads its own `n_kv/n_bid`; `b>nb` does no work. `b==nb` uses the 128-float `dead` row; earlier blocks use `pooled+b*128`. Query row stride is 512 floats.

Each lane owns four adjacent dimensions `lane*4+[0..3]`. For each of 4 heads it evaluates `k0*q0`, then sequential `+= k1*q1`, `+= k2*q2`, `+= k3*q3`; subgroup XOR adds use offsets 16,8,4,2,1. Lane 0 adds positive head dots sequentially in head order and, only after all four, adds `1e9f` when `b==nb && n%4`. It stores one FP32 score. This is the arithmetic-preserving order; do not reorder products, XOR tree, heads, or tail bonus, nor contract/reassociate multiply-add. Full-row ID oracle, guards, input/repeat/sample FP32 checks pass per task brief; this report adds no validation run.

Case: 256 queries, K=128/head, 4 heads; blocks=`capacity/4+2`, active prefix=`78453/4+1`, SG32/WG32. Repeated/context cohort is Main-owned. Timings do not identify key traffic/cache behavior or support utilization/bandwidth inference.

The current address pattern exposes two possible costs. For a fixed full block, four adjacent query subgroups load the same 128-float pooled row while using distinct query rows. Also, each lane's four scalar accesses cover contiguous dimensions, but each per-d operation has lane stride four floats (16 B). All 32 lanes together cover the 512 B row; compiler lowering is unknown. The kernel source proves repeated logical loads, not redundant DRAM traffic.

## Mappings compared

### A. Four queries, same block, shared key

A 128-item work-group contains four SG32 subgroups; each subgroup scores the same `b` for one `qi`. Lanes write their four key floats into one 128-float SLM row (512 B), then all 128 work-items pass an unconditional work-group barrier. Each subgroup reads its lane's vector and applies the existing head/dot/reduction sequence. No cross-subgroup shuffle is proposed.

For any query with `b>nb`, skip arithmetic/store only after the common barrier; its subgroup still participates in synchronization. Crucially, a short query's `b==nb` reads `dead` while a longer neighbor's same `b` can be pooled. Do not share the pooled row in that mixed case: either use per-subgroup key selection/load after the barrier or take a no-reuse edge path. Tail bonus and output store are per query. This avoids letting a longer neighbor's row change shorter-query semantics.

At best the shared completed key avoids 3×512=1536 bytes of logical global loads per four-query group, before accounting for cache reuse; SLM then services four subgroup reads. This is not a DRAM saving estimate. Cost is one barrier, SLM write/read, four-subgroup state, and a larger work-group that may reduce concurrent groups. The shape is a reuse hypothesis, not a speed prediction.

### B. Existing topology with explicit vector loads

Keep one SG32 per `(qi,b)` and exact accumulation, but load aligned `float4` key at `lane*4` and query at `h*128+lane*4`, extracting components and accumulating in current order. Lane bases and row/head strides are multiples of 16 bytes; verify base alignment for both pooled and dead pointers in the actual caller contract before using a vector type. The shape could turn four strided SIMD scalar operations into a contiguous 16-byte-per-lane operation or reduce address/issue overhead. It may instead compile identically to current code. No barrier/SLM or extra group state; no key reuse across queries/blocks. Keep only if codegen confirms a useful load change and device event improves.

### C. Several adjacent blocks per subgroup (defer)

Loop over 2 (then at most 4) block IDs for one query while retaining the same query values in registers. It reduces query reloads only if cache/compiler do not already do so. Keys still differ; outputs serialize, parallelism falls by loop factor, register lifetimes grow, and each iteration has distinct bounds/dead/tail. Do not implement without counters/code evidence that query traffic or subgroup setup is material; reject if occupancy, spills, or score time worsen.

## Collectives, bounds, and arithmetic gates

All subgroup lanes must call every XOR permutation in converged control flow. Do not branch on lane 0, per-query validity, tail, or `b==nb` around a subgroup collective. In A, all work-items cross the work-group barrier even if query lengths differ. After it, subgroup-uniform validity may skip work; every lane in a subgroup performing XORs remains active. The barrier orders SLM key writes/reads; there is no cross-work-group sharing.

Preserve score stride `qi*blocks+b`, write only through each query's `nb`, and leave future columns untouched. Test bounds for heterogeneous query lengths and 0/partial/full block steps; dead row at `b==nb`; `n%4` 0..3; sentinels; selection ties/IDs; maximum physical 262144 tokens (`nb=65536`), pool capacity and dead spare; size/overflow limits. The spare is not a completed pool row at the maximum. Keep top-k independent and exact. Do not expand physical context based on capacity.

Gate on exact FP32 scores and selected IDs; classify any bit change as compiler contraction/reassociation or mapping error. No reduced precision/XMX contract is proposed (R1022 covers GEMM).

## Resources and falsification

A uses just 512 B explicit SLM/group plus a barrier. Sequential head loads keep query vectors' live ranges short; materializing four heads at once could add 64 B/lane of query vectors plus key/dot state. B can hold one 16 B key and one 16 B query vector at a time; all four head vectors together would be ~64 B/lane. They are payload estimates, not register counts; inspect compiler resource output. Intel documents work-group, subgroup, SLM and register-pressure effects but says higher occupancy is not always faster.

Main-owned falsification: (1) inspect load width, spills, registers, SLM/barrier and subgroup geometry; (2) repeat same-input score-only device events, separating submit CPU, wait CPU and wall; (3) use traffic/cache/stall counters if available; (4) verify exact full-row scores, sentinels, guards and IDs on 256 queries, mixed lengths, dead/tail, physical boundary and ties; (5) repeat/context and whole-prefill gates after the owned cohort. A loses if cache reuse makes saved traffic immaterial or barrier/occupancy erases it. B loses if codegen is already vectorized, time is unchanged, spills appear, or values/IDs change. C stays deferred absent direct query-load evidence.
