# R657 — MTP non-expert decode allocation audit during batched Prefill

Date: 2026-10-15 JST. Static review of current root and public A/research artifacts only. No build, test, process, GPU, Git, cleanup, private B, live ON log, or environment inspection was performed. This report is the only artifact written in this round.

## Result

One additional independent owner is source-separable from the batched Prefill reader set: MTP's draft-output head allocation group, `head_logits_` plus optional `dhead_` and `dvocab_`. `Prefill::draft_kv` and the fallback MTP prompt pass execute K/V-only work and do not read this group. The group is read in `record_forward` only after the `if (!full) return true` boundary, in the full decode forward, for the draft-head GEMM, sampling, probability, and optional token remapping. This is a concrete detach/restore candidate after draining the MTP stream and retiring full decode graphs.

This is an ownership opportunity, not evidence of useful physical VRAM headroom. Source-derived requested bytes are `max_t * n_vocab * sizeof(float)` for `head_logits_`, plus when `draft_vocab.bin` is present `n_dvocab * NativeHead::row_bytes()` for `dhead_` and the file's raw byte count for `dvocab_`. The current model shape and subset file are not read here, so the byte total is not instantiated. No corresponding `cudaMemGetInfo` delta exists in this audit. The source's `vram_` counter increments for the subset head and vocabulary IDs but not for `head_logits_`, so it must not be used as the full owner size.

I found no larger single independent owner that is wholly unnecessary to batched Prefill. The monolithic `dense_` contains both prompt-K/V tensors and decode-only tensors; it remains live because `draft_kv` reads embedding/hidden projections, attention hyper-connection weights, K/V projections and normalization. The shared `arena_` contains both K/V-only and full-forward scratch and is used by the cached prompt graphs; it cannot be detached as a whole. Splitting unused decode-only ranges out of `dense_` or carving the arena would be a new layout/reader change, not release of a currently independent owner. The coupled-sampler device and mapped-host buffers are a second decode-only group, but their smaller and more entangled lifecycle is not the maximal clean candidate: coupled state/history, `dinv_`'s dependence on `dvocab_`, and graph references require a separate transaction. No source-only size evidence justifies claiming it is worthwhile.

## Reader census

- **Needed throughout batched prompt callback:** `dense_` prompt tensors, `state_arena_`/`st_` draft K/V and its ring host backing/page metadata, `arena_` working storage, `pf_dev_`/input records or mapped `h_tok_`/`h_step_`/`h_pos_`, and `prefill_exec_` / `prefill_dev_exec_`. `Prefill::draft_kv` also borrows the current chunk's `R_rows` and its own Prefill scratch region; it computes K/V from those rows and token IDs. The fallback `mtp.prefill` uses the same K/V state and MTP working arena through `record_forward(...,-1,...)`.
- **Not a K/V-only prompt reader:** `head_logits_`, `dhead_`, and `dvocab_`. The sole source reads are the full forward's main/draft head, sampling, and `map_ids` after K/V-only return. For `dhead_`, restoration depends on the still-live borrowed `head_` weights plus the subset IDs; bind currently reads `draft_vocab.bin` into a temporary vector and does not retain a host copy. Any implementation must retain/hash an owned copy of the subset IDs or perform an explicitly checked exact-file reload before publishing the owner.
- **Also decode-only, but not selected:** `cparams_`, `cring_`, `dinv_`, `cscratch_`, `h_cparams_`, and `h_chist_` are used by coupled full-row capture/sampling and setters/history staging, not by prompt K/V graphs. `dinv_` is derived from `dvocab_`; coupled graph arrays consume these owners. Releasing them needs a separate coupled-mode state/history snapshot and restore design. Do not infer a safe free from the fact that the first request is greedy; coupled resources can exist across calls when enabled.
- **Already handled by current expert release:** the 512-expert allocation and the normal/coupled `round_exec_`, `step_exec_`, `round_exec_c_`, `step_exec_c_` graph families. Existing detach synchronizes `cs_`, destroys all four decode graph families, then frees experts. Prompt graphs are K/V-only and remain live. This is distinct from freeing the output-head owner.
- **Never propose freeing as a headroom shortcut:** target/draft K/V and state, `window_R_` (borrowed Verifier residual window used by decode graphs and first draft), prompt graphs, or active callback scratch. `window_R_` is not needed by prompt K/V itself but remains a decode owner and lease; its lifetime is not relinquished by this candidate.

## Minimum candidate contract (not implemented)

On the existing serialized single-device, long layer-major prompt boundary, first synchronize `cs_` and checked-destroy all full decode graph families that may reference the draft-head group. Keep prompt K/V graphs, dense prompt tensors, K/V state, arena, mapped prompt staging, and borrowed `window_R_` live. Detach `head_logits_`, and when present `dhead_`/`dvocab_` as one logical owner group only after all graph destruction and queue retirement succeed. The public API has no internal lock: require that no other MTP call can overlap this transition, as the current expert scope contract does.

After synchronous Prefill callbacks and their queues are retired, restore a fresh logits allocation of the original dimensions; recreate the optional subset mapping and gathered draft head from validated owned subset IDs and the still-live `head_`; then publish pointers/accounting together. If a checked drain, graph destruction, allocation, upload/gather, or completion fails, retain any possibly referenced storage and make the request/decode unavailable (fail-stop is consistent with the existing expert-owner policy). Do not return to `draft`/`draft_first` until expert restore and this owner restore both succeed. Normal and coupled round/step graphs can then be lazily recaptured by the existing paths against restored owners. Preserve subset contents/hash and dimensions exactly; no slot enlargement or alternate head layout is implied.

This proposed head-only boundary does not require changing `draft_kv` or prompt callbacks. A broader dense compaction or coupled-sampler transaction has additional readers/state and is out of this one-owner candidate.

## Prior-art reconciliation

The A `research-index.json` records `mtp-expert-prefill-release-v2` as integrated with bounded correctness results but full-context/performance/quality still unqualified; the existing live expert release is therefore the baseline and is not repeated here. `mtp-prefill-record-lease-v1` is indexed as integrated incremental source, and R578 documents K/V-only prompt graphs versus decode graph readers and queue/restore constraints. R638 already establishes that MTP K/V prompt work is batched in the callback and cannot simply be deferred without keeping residual/token data or recomputing target prompt work. R574, R599 and R626 concern decode ExpertCache release, Prefill scratch retirement, and cache/prefill retirement readiness respectively; none establishes that MTP draft-output head allocations are prompt readers or provides a measured reclaim for this owner. No earlier report is treated as a measurement of this proposed head owner's driver-visible free delta.
