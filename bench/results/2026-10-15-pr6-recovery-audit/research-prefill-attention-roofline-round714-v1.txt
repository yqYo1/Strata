## Source-level access pattern

In `src/kernels/sycl/prompt_attention.cpp`, mode 1 has `HD=256`, `CH=32`, `WG=128`, `KG=VG=4`, subgroup 16. One work-group handles one query and one KV head; its 12 query heads share the selected rows. The current K and V gather loops flatten `i` over `HD*CH`, set `dim=i/CH, cell=i%CH`, read `row[cell]*HD+dim`, then store to local `kv[dim*CH+cell]`. Thus adjacent work-items initially vary `cell` while global source addresses jump by a selected-row stride of 256 bytes for int8 codes (and scale reads use row/group). Each individual selected cell is contiguous across its 256 dimensions, but that direction is not the current adjacent-work-item global-load direction. Later joint-matrix loads consume the transposed local tile `dim*CH+cell`.

This is a code-layout observation, not a measured transaction count. Caches, vectorization, compiler lowering, row-ID distribution, device sector size, and whether global loads combine across iterations are unknown. The selected rows are sparse and may have poor physical locality; a cell-major mapping cannot remove that irreducible row scatter, but may make each row's 256-byte code vector contiguous across lanes, then transpose on-chip into the matrix-friendly K/V layout. It may also introduce extra local stores, transpose/barrier work, register pressure, or lower occupancy. Hence candidate priority is conditional on an instruction/transaction profile showing inefficient K/V gather traffic or gather issue cost on the Direct path.

At mode 1, each active selected cell requests K+V code payload 512 B and 4+4 FP16 scale values 16 B. If all 2,051 positions are active, source arithmetic is 1,082,928 bytes per query/KV head: code payload `2*2051*256 = 1,050,112 B`, scales `2*2051*4*2 = 32,816 B`, total 1,082,928 B per KV head, or 2,165,856 B for two KV heads. This is requested logical payload, not observed DRAM/LLC traffic; if selected count differs, multiply per-cell amounts by active count. Existing R568's selected-row figures and profiles use different exact conventions/cases, so do not substitute these arithmetic values for a trace.

For 2,051 positions the current CH32 loop executes 65 serial iterations per work-group. Each iteration has cooperative row resolution, K/scale gather, barriers, QK joint-matrix work, online softmax, V/scale gather, probability hi/lo conversion, PV joint-matrix work, and barriers. This makes serialized chunk scheduling a second plausible limiter, but R568 already examined CH64/head partitioning and did not measure it; this report does not assert a loop-bound speedup. At the actual Main cap/chunk/selected-width distribution, the profile needs to distinguish gather stalls, matrix issue, local-memory/barrier stalls, and occupancy before choosing between access remapping and tile geometry.

The caller in `src/prefill/prefill.cpp` runs `qsa_prompt_attn_batch` after indexer selection and KV staging, with OLD/fallback route controls. Its boolean return means matrix path admitted, but source presence alone does not prove every long-run QSA call used this kernel. Use the current Main's actual route trace and per-call shapes. Do not use decode attention's `CHUNK=64` as evidence for prompt's geometry or performance.

## Ranked hypotheses

1. **Cell-major cooperative K/V gather plus SLM transpose, mode 1 only.** Reassign cooperative load ownership so adjacent lanes walk adjacent dimensions of one selected row (`row*HD+dim`), with vector/wide loads where the compiler supports them, and write a tiled/transposed local representation matching current joint-matrix B operand layout. Keep cell IDs, K/V values, scale groups, online softmax, CH32 and Direct switch fixed. This is the most concrete novel candidate because the source currently assigns lanes across selected cells for a fixed dimension while each source row is contiguous. Measure requested/global sectors, cache misses, load issue stalls, local transpose cost, compiled registers/spills, SLM, active WGs and full attention call duration. If mapping cannot retain enough rows concurrently without spills or the current source is cache-hit/compute-bound, reject it.

2. **Bounded K-load / matrix overlap within the existing CH32 loop.** Only if profiling shows K gather serializes the QK matrix path, test a two-stage local K/scale buffer schedule that resolves and loads the next selected cells while the current tile's independent work proceeds. Existing SYCL joint-matrix prefetch supports cooperative subgroup prefetch in principle, but arbitrary page-table-resolved rows and int8 decode/scales may not fit that API; a software double buffer would add SLM and synchronization. Start with a minimal diagnostic proving overlap and resource costs, not an assumed FA3-style warp-specialized port. Hopper FA3's TMA/async Tensor Core results do not transfer to Arc/Xe2. This candidate is lower priority than the simple ownership remap because dependencies and extra SLM are substantial.

3. **Only after component profile: adjust number of query rows per work-group or query/KV work-group scheduling.** There are already 12 query rows per KV head per WG and each query is an independent attention result. Fewer rows/group can add parallelism but duplicates selected K/V gather; more rows/group can reuse data but increases live score/probability/output state and SLM/register pressure. R568 covered one split direction (8+4/6+6), so any later geometry should be justified by occupancy/SM underfill from this exact 78K workload and compared against the R568 predicted duplicate-traffic cost. No geometry has a speed ranking from source arithmetic alone.

## Primary implementation references and transfer limits

- FlashInfer authors' [sparse prefill API/source](https://github.com/flashinfer-ai/flashinfer/blob/main/flashinfer/sparse.py) and [paged-KV layout design note](https://github.com/flashinfer-ai/flashinfer/blob/main/docs/design_docs/nvfp4_msa_paged_kv_layout.md) illustrate that sparse/page-aware attention depends on the consumer's exact physical layout and should avoid assuming a dense contiguous cache. CUDA implementation/layout ideas are architectural references, not measured Arc outcomes.
- Intel LLVM's [SYCL joint-matrix extension](https://github.com/intel/llvm/blob/sycl/sycl/doc/extensions/experimental/sycl_ext_matrix/sycl_ext_oneapi_matrix.asciidoc) defines `joint_matrix_prefetch` as a cooperative subgroup prefetch for a logical matrix region. It is a possible building block for candidate 2 only; it does not prove support for this kernel's indirect sparse row gathers, usefulness on the configured Arc device, or overlap.
- The authors' [FlashAttention-2 paper](https://arxiv.org/abs/2307.08691) motivates balancing parallelism, warp/work partition and shared-memory communication. Its CUDA dense-attention results do not predict this selected-row INT8 SYCL path.
- The authors' [FlashAttention-3 paper](https://arxiv.org/abs/2407.08608) describes Hopper-specific TMA/Tensor Core asynchrony and warp specialization. Treat this only as a pipeline design concept; the prerequisites and mechanism differ here.
- Upstream llama.cpp's [SYCL backend documentation](https://github.com/ggml-org/llama.cpp/blob/master/docs/backend/SYCL.md) describes its optional reordered Q8 path and wide loads. This makes wide contiguous load ownership a concrete Xe/SYCL precedent, not proof that its quantization layout or kernel applies to Strata's selected KV layout. The authors' [SYCL sparse-FA discussion](https://github.com/ggml-org/llama.cpp/discussions/28695) is a work-in-progress, opt-in path and is not an adopted reference result.

No personal blog claims are used as performance evidence. No external implementation's reported speed is projected onto this model or device.
