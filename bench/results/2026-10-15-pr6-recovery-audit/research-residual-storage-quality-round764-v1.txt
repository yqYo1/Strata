# R764 — FP16 versus BF16 storage for long-prefill residuals

2026-10-16 JST. Bounded read-only research; this report is the only file written. No product edits, build, test, GPU/profiler/process inspection, environment/service action, Git operation, or cleanup was performed. I reviewed `AGENTS.md`, `docs/ARTIFACT_RETENTION.md`, the audit index, R569/R573/R661–662/R674/R741, the R757–763 reports and Main corrections, and `own-prefill-host-attribution-v3.ja.md`.

## Finding and evidence limits

There is still no direct measured comparison of FP16 and BF16 for this exact operation: store the widened Qwen residual after each non-final layer, restore it to FP32, and keep every live operator FP32 for all 47 boundaries. The index says current FP16 has a small synthetic recurrent screen and selected-position natural-input diagnostics, while the BF16 v2 proposal remains unapplied, unbuilt, and untested. The checked-in selected-logit runner remains tied to the older 34,603-input fixture; the dense teacher-forced NLL proposal is source-only. Therefore neither format has natural-long quality or task qualification here.

The most relevant external result is from the Qwen authors. Their Qwen3.8-Next report says the GR/gated-attention/GDN gates keep residual writes in a narrow range and reports FP8 residual storage at half the bytes of BF16 with “almost no loss in quality” (§2.2, *Inference Efficiency*). It gives a useful same-family reason to test residual storage, but the cited passage supplies no numeric FP16-versus-BF16 comparison, residual-tail histogram, per-layer cast semantics, or matched result for Strata’s IQ3 checkpoint and repeated FP32-restored storage path. The report also documents cases where pretraining loss and downstream results diverge, including sparse-write quality loss after post-training (§1 and §2.2). That is evidence to check task outcomes alongside NLL, not evidence that this storage-only change will regress. [Qwen Team, technical report](https://arxiv.org/html/2608.30320v1); the official model README confirms four gated residual branches [here](https://github.com/QwenLM/Qwen3.8-Flash-Next).

FP16 and BF16 both use two bytes, but encode different errors: oneDNN documents BF16’s 8-bit exponent/7-bit mantissa versus FP16’s 5-bit exponent/10-bit mantissa. BF16 has much wider range; FP16 has finer relative spacing for ordinary finite values. This does not establish the residual distribution or the better format. Measure actual per-layer, per-branch tails and conversion effects, especially finite-to-infinity, subnormal-to-zero, and low-magnitude values; do not use only a final-layer tensor or one post-hoc cast. [oneDNN BF16 data-type reference](https://oneapi-spec.uxlfoundation.org/specifications/oneapi/v1.1-rev-1/elements/onednn/source/data_model/data_types/bfloat16.html).

The latest 78,453-input diagnostic is 78,452 batched rows, 48 layers, C=8192, FP32 residual storage, and 32,768 GPU rows. Its CPU/wall and host-copy timings are attribution evidence, not a storage-quality result or a measured removable-latency bound. A 16-bit bank for 78,452 rows at width 10,240 requests 1,606,696,960 bytes (~1.50 GiB); either 16-bit format uses that same space, and a 262,144-row bank is 5 GiB. These are capacity arithmetic only: all-GPU admission and the time saved by removing host residual roundtrips remain to be measured.

## One bounded matched experiment

After BF16 conversion and boundary plumbing have passed Main’s source/build/mechanics review, run FP32, FP16, and BF16 storage arms in separate owned processes. Keep the checkpoint, exact token IDs/template, native prefill route, C=8192, current 78,452-row length, MTP/KV/cache settings, and placement fixed at `R_GPU=32768`; only the storage dtype changes. Preserve FP32 live arithmetic and final-layer output, with one cast on each of the 47 non-final boundaries and one FP32 restore before the next layer. This isolates format quality from the separate all-GPU placement/capacity question.

First collect compact conversion summaries at every boundary: per-layer and per-branch min/max, p99/p99.9/p99.99 absolute value, absolute/relative cast error, and counts of overflow/nonfinite, underflow-to-zero, subnormal, and signed-zero outcomes. Break out early/middle/late rows, each C8192 edge, and both sides of the actual GPU/host boundary. A benign aggregate histogram cannot hide a single bad layer or branch.

For quality, use a preregistered set of 16 independent long-document contexts (32K–78K tokens) with identical input IDs across arms. Score 64 fixed initial-prefill positions per context—uniformly stratified through the sequence, with positions at chunk edges and the GPU/host boundary included—using full-vocabulary logits and the next input token `x[p+1]` as the teacher-forced target. The current selected-logit hook supports at most 64 positions, but its existing runner does not cover the current 78K input; make a new pinned runner/receipt before launch. Record per-position target NLL via stable log-sum-exp, reference-to-candidate KL, top-two margin and top-1 flips. Report the per-context mean NLL delta and a paired bootstrap confidence interval clustered by context, not by the 1,024 correlated token positions; show each length/position stratum. Repeat FP32 separately to establish its own spread. If the interval is too wide to support a pre-agreed application margin, expand the independent context set; do not invent or borrow an acceptance threshold from prior proposals.

Use a fixed scored retrieval/reasoning/coding subset from those contexts as a separate outcome, with identical prompts, decoding settings, and blinded rubric. Score answer correctness/task criteria rather than requiring identical generated text. NLL, task results, and numeric range are distinct gates. A later all-GPU FP16/BF16 run is a separate placement/performance comparison and must prove the emitted plan has zero host tail/staging and fits actual free-memory headroom. Any claim at the physical 262,144-token boundary also needs a separate admitted full-context correctness/lifetime check; the 78K cohort cannot establish it.

No acceptable loss threshold is established by the reviewed evidence. Treat the 16-context result as a bounded screen, not broad quality qualification; preserve every per-context result and baseline repeat, and make a performance decision only from separate clean end-to-end runs.
