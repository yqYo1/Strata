# R893 — Reconstructing the historical QSA attention route

Decision support; read-only source and receipt analysis, 2026-10-16. Question: which route the PR6 timed environment selects at source level, how that GPU work differs from the currently measured matrix route, and whether an isolated computation candidate can be qualified without carrying forward the historical runtime layer. No source was changed or executed. This report uses the personal fork's pinned PR6 reconstruction and current fork source only; it does not use XeStrata implementation material.

## Finding and confidence

**The timed environment selects the historical QSA decode-attention fallback, variant 4, in 128-query batches, for INT8 K and INT8 V.** It does not select the historical prompt XMX kernel. The source chain is direct: the recorded `STRATA_PREFILL_ATTN_LAYOUT=4` maps to variant 4; `STRATA_PROMPT_ATTN_OLD` is absent; the SYCL `qsa_prompt_attn_batch` wrapper attempts only `qsa_prompt_attn_xmx` and returns false when that helper declines; `STRATA_PROMPT_ATTN_XMX` is absent, whose default is mode 0/false; then the caller invokes `qsa_decode_attn_batch_variant`. The variant switch instantiates `launch_chunk_variant<KV_MODE,16,true,true>`; the `--kv int8` pools select `KV_MODE=1`. Batch size 128 is clamped only by the current query count. These are source-derived route facts for the reconstructed snapshot, not confirmation of the historical binary's emitted kernel.

The timing anchor is the recorded three-pair median, 645.847951 tok/s, for the 32,769-token file / 32,768 batched tokens, four 8,192-token chunks, INT8 K/V, resident capacity 65,538, `R_GPU=32768`, FP32 residuals, layer-major plus compact=2, warm direct PLE, prefill-only, one raw output token and no MTP. The reported input speed is whole-prefill time; it does not measure QSA in isolation or establish which component caused the speed. Treat 6,144 historical attention kernel submissions below as a source-level estimate from 4 chunks × 12 QSA layers × (8,192 / 128) fallback batches × two kernels per call, not as a trace count.

## Route comparison

| Property | Historical variant 4, inferred from env + restored source | Current measured matrix route, source + device trace |
|---|---|---|
| Work assignment | 128-thread workgroup = one query, one KV head, one 64-cell selection chunk; 8 SG16 warps. `TRANSPOSE_Q` changes local query layout; `QUERY_FAST` puts query as innermost workgroup axis. Separate merge kernel per 128-query call. | One 128-thread workgroup per query × KV head; 8 SG16 subgroups, 32-cell tiles processed serially inside the workgroup. One QSA kernel call per input chunk/layer, no scratch merge. |
| Math and precision | INT8 K/V codes are multiplied by FP16 scales widened to FP32; QK uses FP32 scalar products/reduction; scale is `1/sqrt(256)`. FP32 score, per-chunk max/sum and value partials; chunk outputs are FP32-merged with `native::exp` and FMA. | Actual signature is `launch<1,true,false,0,false>(float const*,...,float*)`: float Q, int8 K/V, FP32 output; Q uses high/low FP16 parts, XMX joint-matrix FP32 accumulation, K scales applied after QK groups, V scales are FP32, probabilities use high/low FP16 parts. Online FP32 softmax/accumulation spans the selected rows. Not the separate BF16-native QSA path. |
| Reuse and traffic opportunities | K codes are loaded once per cell/KV head into lane registers and reused over 12 heads. Q (12×256 FP32) is staged in local memory per chunk, so a query is reloaded for each 64-cell chunk. K scale loads repeat by lane within each 64-dimension group; V scale is read inside the per-dimension loop (256 logical scale reads/cell, four unique groups), although cache/broadcast behavior is unknown. V scalar is reused across 12 heads. | Q is loaded once per query/KV-head group into high/low tiles. K is staged once in local memory and reused across 12 heads; V overwrites the same tile and is reused across output heads. Four K and four V scales per row are staged once per 32-cell tile. Source therefore removes repeated scale-load instructions, not proven DRAM bytes. |
| Synchronization and scratch | Three workgroup barriers per nonempty 64-cell chunk (Q/row publication, QK-to-softmax, softmax-to-PV), followed by a second kernel and FP32 partial `[chunks, heads, 256]` plus max/sum scratch. `ceil(cap/64)` determines chunk groups; groups beyond the actual `steps` width return early. | One initial barrier plus seven barriers per 32-cell loop tile. Direct output store avoids the alternate local final tile, copy-back, and its barrier. The 60 long-input instances in the current profile sum to 33.962851 s service; the full attention envelope is 94.944752862 s, with compute-union 73.402613863 s, copy-union 8.648969200 s, uncovered gaps 12.893177792 s, and only 7,993 ns compute/copy overlap. This does not identify XMX, memory, or barrier saturation. |
| Padding | 12 real heads, no 16-row head padding. Inactive cells are masked and skipped for K/V arithmetic; capacity chunks past `steps` still launch and write empty partial metadata. | Joint matrices cover 16 head rows for 12 real heads (four padded rows, 25% of row-tile arithmetic); a partial 32-cell tail is zero-filled but still enters matrix operations. Visible local-accessor requests for this exact direct/mapping-0 Mode1 source are about 44,500 B (Q hi/lo 16,384; K/V tile 16,384; P hi/lo 8,192; scores/scales/state/rows/final remainder). This is source accounting, not compiler storage or occupancy. Historical visible local arrays total about 15,872 B (Q 12,288; scores 3,072; rows 512), likewise not occupancy. |

The key schedule tradeoff is parallelism versus dependency/workspace. Historical splitting exposes more independent cell-chunk workgroups, but repeats query staging and per-batch dispatch and requires a global partial-result merge. Current matrix attention has more local barriers, larger visible SLM, padded head/cell work and a serial tile loop, but uses XMX and carries online state without a second launch or global partial outputs. The source does not establish which path is faster: no historical QSA trace or current PMU/occupancy/stall counters exist, and the workloads/builds are not matched.

## Numerical guards and qualification candidate

The historical route assumes `steps[kStepWidth]` and cell IDs are valid for the supplied capacity/page table. It reads `page_table[cell / page_size]` before checking `cell < 0`, and accepts any nonnegative physical page without an upper bound; a negative or corrupt ID/page can address the wrong row or go out of range. Valid selector output may satisfy these preconditions, but they need explicit current guards/oracles. The current float matrix path guards negative cells and count outside `[0,cap]` but still relies on page-table/allocation invariants; only the typed BF16 validation path accepts explicit logical/physical page bounds. Both routes mask missing pages and return zero for all-missing selections through their softmax/merge logic. Historical chunk-local softmax plus merge changes reduction order versus a single online recurrence; its native exponent and FP32 FMA are not bitwise-equivalent to current XMX FP16 high/low Q/P arithmetic. Neither route is certified by this source review.

A defensible *standalone qualification candidate* is a newly authored SG16 vector streaming kernel that keeps the historical 12-head scalar QK/PV idea but (a) uses the current owned queue, registered spans and checked event retirement, (b) bounds cell/page IDs before dereference, (c) loads each row's four K/V scales once, and (d) maintains online FP32 max/sum/value state to write final outputs without historical per-cap scratch and merge. It targets identifiable excess work—four matrix-padded heads, partial 32-cell tiles, repeated scalar scale reads—and removes launch/scratch dependencies; it may lose to XMX because a longer vector loop and per-thread accumulators can limit throughput. This is a hypothesis to qualify, not a recommendation to adopt or dispatch.

Two bounded experiments for Main: first, use the current exact long-prefill selected IDs/widths and INT8 pools to compare current matrix against that standalone candidate in the same owner-managed queue; report QSA kernel and full dependency time separately, preserving 5×12 long-input shape and current outputs. Second, validate numerical/guard cases against the current FP64 oracle over widths 0, 1, 31, 32, 33, 63, 64, 65, ragged capacity, invalid/missing pages, and finite/Inf/NaN inputs before any performance comparison. Keep both arms outside default dispatch until independent qualification and the long-prefill milestone. Neither experiment uses the old host doorbell/counter/queue protocol or treats source footprints as performance evidence.
