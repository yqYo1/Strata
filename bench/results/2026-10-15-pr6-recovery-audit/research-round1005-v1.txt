Classification: decision support; bounded source-only audit. Snapshot base named by the task: `e4346e75399cfacf6ed26abd45751e9c92387fb4`; no Git command was run, so commit object identity/ancestry was not independently verified. ### Existing window producer and precision boundaries

`run_moe_window` retains the 16-bit residual bank as BF16: `native16::norm` loads BF16 to FP32; its per-channel reduction, scale, and normalization arithmetic are FP32; normalized `xn` is BF16-stored. Down projection and SiLU intermediates are BF16, and the up projection output is BF16. `native16::mix` then reads residual/gated values as BF16, performs scale/weight products and four HC FMAs in FP32, divides by four in FP32, and emits **both** `mixed_bf` (BF16 rounded) and `mixed_h` (FP16 converted, without the explicit finite clamp used by expert hidden). This is the key correction: they are distinct outputs of the same FP32 `v`, not interchangeable aliases.

The router projection consumes `mixed_bf`; route logits/weights and route choices remain FP32, while IDs are int32. The scalar shared-gate projection also consumes `mixed_bf` and writes one FP32 gate scalar per row. Reconstructing that input from `mixed_h` changes the gate input by converting already-rounded FP16 to BF16 and is not a preservation of the current graph. The two shared matrix projections consume `mixed_h` in this source path; preserve the existing FP16 producer for them as well. The shared SwiGLU output (`sh`) and shared down output are 16-bit; final combine interprets shared-down bits as BF16. The pinned five-file set does not include the implementation of the `native_proj16` wrapper, so exact shared projection input/output template selection beyond the stated call-site operands cannot be independently proven from this snapshot.

For routed experts, `gather_rows16` gathers from `mixed` (the FP16 `m.emb` bank). `Gemm::f16_out16(..., true)` receives FP16 input and FP16 dequantized weights, accumulates in FP32 matrix accumulators, then stores BF16 because the bool is `output_bf16=true`. This applies to GU and Down; GU output is BF16. `native16::swiglu` reads BF16 gate/up values into FP32, computes SiLU and multiply, explicitly clamps finite result to [-65504,65504] (NaN is passed through), and converts to FP16 for hidden. Down projection consumes FP16 hidden and FP16 dequantized down weights, writes BF16 expert output. `gemm16.cpp`’s GEMM kernel has an FP32 accumulator and converts the final value to the requested 16-bit output at the store (`Output(value)`); this says nothing by itself about matrix partial-sum order or hardware-specific exactness.

`native16::combine` follows original token route-slot order: for each output feature, starts FP32 zero, applies FP32 FMA of FP32 router weight by BF16 expert-down value for each of 10 slots, then adds BF16 shared-down times sigmoid(FP32 scalar gate) in FP32 and stores BF16 once as `bo`. `native16::write` reads BF16 `bo`, FP32 injection, and BF16 residual; computes scalar gate in FP32 and FP32 FMA, then BF16-stores updated residual. Thus rounding/saturation points include BF16 normalized input, BF16 projection inputs/outputs, paired BF16+FP16 mix outputs, clamped FP16 SwiGLU hidden, BF16 expert-down outputs, BF16 shared-down output, BF16 final MoE sum, and BF16 HC residual write. Router decisions, scalar gate, route weights, expert-sum accumulation and HC write arithmetic are FP32. No claim here that all conversion instructions are identical across compilers/devices.

### 64K expert-major batching and counterevidence

A 64K batched plan can preserve this contract only if it maintains both activation streams for every logical row until their last consumers: BF16 `mixed_bf` for router and shared scalar gate; FP16 `mixed_h` for expert gather and both shared matrix projections. It must compute/store the scalar gate for the full window from the original BF16 producer before its storage is reused. The old plan draft’s `shared_gate` plane is `W` floats, but its `shared_gate_input` and shared projection prep payloads are only chunk-sized `J`; the snapshot manifest itself correctly flags this extent mismatch. At `W=65,536`, scalar gate is 262,144 bytes, not an 8,192-row extent (32,768 bytes). A gate from a single chunk cannot stand in for the remaining rows.

Shared matrix projections may be scheduled after expert jobs if the same row’s `mixed_h` remains live until the last shared projection input read, `shared_gate` was already computed from `mixed_bf`, and combine waits for both all routed Down outputs and all shared outputs. The shared term still joins after the FP32 routed sum, then the final BF16 store occurs once. Putting shared output into an expert-major FP32 accumulator, narrowing it early, or applying it before the routed reduction changes existing arithmetic.

The current two-piece path has `mixed` alias `m.emb` and aliases it as `bo` only after the final expert reads; a 64K schedule must provide a proven new lifetime/layout or preserve that delayed alias boundary. Do not overwrite the only FP16 mixed copy before gather/shared matrix readers retire, or overwrite BF16 mixed before routing/scalar-gate readers have finished. A producer may generate the two formats together, but this does not justify collapsing either format. The plan’s FP32 accumulator is not the hidden state, and an FP16 expert input is not evidence that the original BF16 router/shared scalar-gate input was FP16.

Current window code reuses `m.dq_gu[0]`/`m.dq_d[0]` for each host-dispatched expert, uses shared `gathered`, `gu`, and `hidden` scratch, and relies on same-queue ordering. The new batching must not overwrite dequant weight scratch before that expert’s queued GEMMs have consumed it, nor reuse job output/scratch while an async reader/writer remains. Existing custom vLLM backend call wrapper finishes the returned GEMM event before returning; nevertheless transfers and other kernels remain subject to stream ordering and checked final drain. The provided precision snapshot does **not** include `src/prefill/sycl/vllm_xe2/native16.cpp`; therefore this audit cannot verify its internal output-store code. From the named `gemm16.cpp` call site and local GEMM kernel only, the declared output is BF16 and the kernel stores `Output(value)`. R999 describes the adapter as one-GEMM/event API and reports wrapper finish, but is a separate source pin (`af99f294`) and does not close this missing-file limitation for the `e4346e7` snapshot.

Source preservation is a numerical hypothesis, not proof that changing from route-slot summation to expert-major scatter-add preserves results. The original combines in route-slot order; an expert-ID-order FP32 fold changes addition order even if all expert outputs remain BF16. Also, the snapshot’s production helper is currently two 8,192-row pieces, whereas a 64K schedule has more rows and potentially different GEMM shape/partition behavior. Keep the physical 262,144 context, shared state/order, and normal owner lifetime gates from AGENTS.md; this source audit establishes none of their runtime validity.

## Finite semantic comparisons and counterexamples

Use deterministic inputs/weights/routes and isolate one boundary at a time before whole-model/task validation against the actually selected SGLang/vLLM path. The exact model-path source/branch is not pinned here; source flags or these local Strata snapshots do not establish its contract.

1. **Dual mixed activation and gate dependency:** compare original FP16 `mixed_h` and BF16 `mixed_bf` against a deliberately collapsed path which derives BF16 from FP16. Include values where FP16 and BF16 round to different values and near the BF16 scalar-gate projection’s decision-sensitive outputs; compare router logits/IDs/weights and scalar-gate values independently. Counterexample: a value rounds to `a16` in FP16 then to `b16` in BF16, while direct FP32-to-BF16 gives a neighboring value. Shared scalar gate and router can diverge despite expert gather seeing a valid FP16 operand.
2. **Per-row scalar gate extent:** use a 65,536-row logical window with distinct mixed BF16 rows and distinct shared gate inputs in every 8,192-row region; compare all `W` gate entries against recomputation from original BF16 rows. Assert no chunk-reused or uninitialized tail. Counterexample: gates are only prepared for J rows and reused modulo J; first chunk passes while later shared terms are wrong.
3. **Expert matrix input/output and hidden saturation:** compare FP16 gathered inputs, FP16 dequant weights, BF16 GU store, BF16-to-FP32 SwiGLU, finite clamp then FP16 hidden, FP16 Down operands and BF16 Down store. Include large positive/negative activation, NaN, values around half-format overflow and values near BF16/FP16 midpoints. Distinguish the clamp only at hidden from the unclamped FP16 mix conversion and from GEMM BF16 outputs.
4. **Combine order/shared addition:** retain exact IDs/weights and BF16 per-expert outputs; compare original slot-order FP32 FMA with candidate expert-major order, with/without shared branch, then BF16 store. Include one large positive term plus many small terms permuted across route slots, duplicate/invalid route injection as fault cases, zero routes if API allows, and shared values that lie around the final BF16 midpoint. This detects non-associative FP32 sum and any early/multiple BF16 rounds.
5. **Asynchronous lifetime:** trace ownership in a bounded component fixture only after Main authorizes implementation/measurement: delay or fault queued consumers, attempt cancellation/error around job submission and final drain, and prove `mixed_bf`, `mixed_h`, shared-gate data, weights, scratch, descriptor/upload owners and output planes remain alive until their last checked consumer retires. Compare the `vllm` event-return/finish path separately from local GEMM; API-level event completion is not proof of every surrounding transfer lifetime.
