# oneDNN typed-16 GPU matmul as a Strata prefill option

## Scope and finding

This read-only check asked whether the installed oneDNN path can express BF16 or FP16 inputs, a 16-bit output, and documented FP32 accumulation on the existing SYCL queue, and whether it can keep setup bounded across 512 experts with different row counts. Local package metadata and headers identify oneDNN 3.11.4 at `/opt/intel/oneapi/dnnl/2026.0`, configured with `DNNL_GPU_RUNTIME=DNNL_RUNTIME_SYCL`; `libdnnl.so.3.11` is present. The headers expose the C++ SYCL interop and accumulation APIs described below. This establishes local API availability, not successful primitive creation, selected GPU implementation, arithmetic placement, or speed on the target device.

The clearest documented typed-16 contract is `dnnl::matmul` with same-type BF16/BF16/BF16 or FP16/FP16/FP16 and `dnnl::accumulation_mode::strict`. oneDNN documents `strict` as the default mode and specifies FP32 accumulation for floating-point primitives. This is an unusually direct route to test against Strata's FP32 reference while storing the output in 16 bits. However, the ordinary MatMul primitive still executes once per expert. Runtime M dimensions can avoid making a descriptor per row count, but do not fuse 512 ragged expert calls into one grouped execution. No comparative performance measurement was made; there is no evidence here that oneDNN is faster than Strata's in-progress native kernel or current oneMKL call.

## API guarantees

The oneDNN 3.11.4 MatMul type table lists FP16 source and FP16 weights with FP16 or FP32 destination, and BF16 source and BF16 weights with BF16 or FP32 destination. It does not list FP16×FP16→BF16 or BF16×BF16→FP16, nor does it list mixed FP16/BF16 operands for these native floating-point rows. Keep each trial's input, weight, and destination format consistent. The accumulation-mode guide says `strict` selects the default FP32 accumulation for floating-point primitives; `relaxed` permits some partial sums to be rounded to source/destination precision, while `any` allows a faster supported precision. Therefore an explicit `attr.set_accumulation_mode(dnnl::accumulation_mode::strict)` records the intended contract in the primitive description, even though strict is already the documented default. This is about the accumulation datatype; it does not make the output FP32.

For Strata's current row-major GEMM seam (`src/prefill/sycl/gemm.cpp`), X has shape T×K, the stored expert weight has physical shape N×K, and the requested product is X times W-transpose. The direct oneDNN descriptors can use logical dimensions `{M,K}`, `{K,N}`, `{M,N}` and explicit element strides `{K,1}`, `{1,ldw}`, `{ld,1}`. Here `M` is that expert's token-row count, `K` is input width, `N` is output width, and the last strides preserve the project's transposed weight and padded output layouts without a copy. Use `f16` or `bf16` consistently for X, W and destination; use `DNNL_RUNTIME_DIM_VAL` for M if reusing a primitive across different expert row counts, with K and N fixed per layer family.

The MatMul guide supports runtime dimensions and strides, but warns that withholding shape information can reduce performance and rules out `format_tag::any` when shape is unknown at creation. It also documents regular batching and broadcasting; that is not a ragged grouped-MoE interface. A standard batch descriptor expects compatible batch matrix shapes, so varying expert M values cannot simply be described as one uniform batch without padding or a different API. The separately documented oneDNN 3.13 grouped-memory facility is later than the installed 3.11.4 package and is experimental; it is not proof of grouped matmul dispatch. A read-only search of the installed headers found no grouped-memory identifiers.

## Minimal integration contract

1. Build the oneDNN engine from the same `sycl::device` and `sycl::context` that own Strata's queue using `dnnl::sycl_interop::make_engine(device, context)`, then bind `dnnl::sycl_interop::make_stream(engine, queue)`. The documented C API describes engine creation from a device/context and stream creation from a queue; the installed C++ headers expose corresponding wrappers. This allows execution to share the existing queue rather than creating an independent queue whose work would need additional ordering.
2. Construct the explicit-stride memory descriptors and primitive descriptor once per layer shape and dtype. Set strict accumulation on the primitive attributes. A candidate call is `dnnl::matmul::primitive_desc(engine, src_md, wei_md, dst_md, attr)`, then repeated `matmul::execute(stream, {{DNNL_ARG_SRC, src}, {DNNL_ARG_WEIGHTS, weights}, {DNNL_ARG_DST, dst}})` with memory objects wrapping the current X, resident weight and output buffers. For USM, the interop memory wrapper does not own the supplied pointer; keep allocations alive and avoid reusing a buffer until its asynchronous use has completed.
3. Let the producer, matmul and next consumer share queue order, and carry events/dependencies if work crosses queues. Synchronize where the next CPU decision or host-visible result requires it, not after every expert. The API returns/accepts SYCL events and dependencies, but queue ordering and buffer lifetime still need validation in Strata's execution and teardown paths.
4. Keep the existing FP32 operator/reference for comparisons. FP16 and BF16 are both two-byte storage; this API evidence does not choose between them. Router decisions, reductions and recurrent state retain their existing FP32 requirements unless a separate numerical change is justified.

oneMKL remains the lowest-change path in the current source, and its SYCL BLAS call accepts typed 16-bit operands. The local oneMKL 2026.1 package has headers and `libmkl_sycl.so`, but this check found no implementation source establishing how a selected GEMM accumulates or whether it preserves the needed producer/consumer behavior. A callable typed GEMM signature is not an FP32-accumulation guarantee. Do not infer accumulation precision from the output element type or from the fact that the queue is a GPU queue.

| Route | Useful contract/evidence | Main limitation for the 512-expert case |
|---|---|---|
| Installed oneDNN 3.11.4 | Same-type BF16 or FP16 operands and output; documented strict FP32 accumulation; SYCL engine, queue and USM interop | One execute per expert; dynamic M reduces descriptor variants but may lose shape-specific optimization; no local GPU run |
| Existing oneMKL GEMM | Already called at Strata's row-major SYCL seam; minimal integration disruption | Local API/library presence does not document the selected kernel's accumulation precision or prove device-side arithmetic |
| vLLM XPU grouped GEMM reference | Pinned source has a typed FP16/BF16 grouped route taking per-expert row counts and a queue | CUTLASS/CuTe DPAS specialization for Intel Xe2/BMG, ATen/Torch bindings and workspace design; architecture reference only, not portable Strata code |

## Cache, lifetime and compatibility tradeoffs

The oneDNN C++ overloads available locally include `make_engine`, `make_stream` and memory wrappers; match the runtime/context and queue exactly. The official interop contract allows wrapping a caller-owned USM pointer without transferring ownership. This is useful for avoiding a host copy, but it also means Strata must ensure every source, weight and destination allocation outlives the queued primitive execution. Primitive objects and memory wrappers can be reused only while their descriptors, engine and storage assumptions remain valid. Explicit dependencies are preferable if any producer or consumer moves work to a different queue.

A single runtime-M primitive per (dtype, N, K, relevant stride/layout) can cap host descriptor creation while honoring expert-specific row counts. There will still be one argument setup and primitive execute per nonempty expert, and that cost can dominate when many experts receive few rows. An alternative is cache entries for a small set of exact or bucketed M values, which restores shape specialization at the cost of cache pressure and more descriptor builds. Padding to equal M may enable regular batched execution but adds inactive multiply work and writes; it should be measured, not presumed beneficial. The project's gate is the full dependency path, including CPU expert grouping/index work, queue submission, transfers and synchronization, rather than the kernel interval alone.

The pinned vLLM XPU oneDNN wrapper provides an architecture example for cache management: it obtains the Torch current XPU stream's queue, caches oneDNN engine/stream state, creates primitive plans by matmul shape/strides and related attributes, wraps handles and caps its cache at 512. That route is used for FP8/INT4 helper matmuls, so it demonstrates wrapper structure, not native same-type BF16/FP16 accumulation. The same commit's Xe2 grouped-GEMM header passes `rows_per_expert` and has typed FP16/BF16 elements with float accumulation in a hardware-specific DPAS template. This is better evidence for what a truly grouped variable-M interface looks like, but not evidence it can run on Strata's Arc path or other Intel GPUs. The repository and file headers identify Apache-2.0 and BSD-3-Clause provenance respectively; use it only as a cited design reference, with no source adaptation.

## Validation limits and next experiment

No compiler, library load, device query, build, test, benchmark or profiler was run. The local configuration confirms SYCL support is built into the installed oneDNN package, but runtime primitive creation and execution on this specific device remain unknown. A successful descriptor could still select an emulation or fallback path; verify actual implementation and attribute host CPU time inside waits separately from host computation/submission. oneDNN's documented accumulation setting is stronger evidence than the local oneMKL signature, but numerical comparison must still cover the model's actual activation and weight ranges, not only random small matrices.

A concrete follow-up is a paired GPU experiment in the same inference process using one shared queue: current Strata GEMM and oneDNN strict-accumulation MatMul on the actual routed rows for the up/gate shape N=1280,K=2560 and down shape N=2560,K=640 at T=160, then the high-row-count HC case at 8192. Compare BF16 and FP16 in separate runs; retain the FP32 output reference. Record per-expert M histogram, primitive creation/cache hits, number of executes, CPU time by grouping/setup/submission/wait, queue dependency time, bytes transferred, full producer-to-consumer latency, output errors and faults. First validate output16 and the required error bounds, then decide whether variable-M oneDNN overhead is acceptable against the native grouped kernel. This protocol does not assume either implementation is faster.
