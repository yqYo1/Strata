## Current geometry and exact source counts

Each work-group owns one query and one KV head. There are 12 actual query heads per KV head, but local query, score, softmax, and probability arrays pad to 16. The eight 16-lane subgroups use `hb=subgroup/4` and `db=subgroup%4`: four subgroups cover QK's two padded 8-head bands by two 16-cell bands; all eight cover PV's two padded head bands by four 64-dimension bands. QK issues two FP16 products for each hi/lo query component and K-scale group. PV likewise issues hi and lo probability products. This 16-row padding is unchanged by CH-only candidates and remains 4 padded rows per 12 actual rows per KV head.

At the maximum selected width 2,051, current CH32 uses 65 passes and allocates 2,080 cell slots across those passes (29 padded). Each pass has seven work-group local-space barriers: after row/score setup, after K/scale setup, after QK, after V setup, after factor reduction, after probability preparation, and after PV. Direct=1 has one additional pre-loop initialization barrier; the non-Direct path also has final output staging/barrier work. These are source barrier instances, not measured stall cycles.

Count `joint_matrix_mad` invocations as subgroup-call instances, separately from scalar MAC terms. Each matrix call is an 8x16x16 operation (2,048 scalar MAC terms). For one query/KV-head work-group per pass, current CH32 has 4 QK subgroups × 4 K-scale groups × 4 K panels × 2 hi/lo calls = 128 QK mad calls. PV has 8 subgroups × 4 output tiles × 2 cell panels × 2 hi/lo calls = 128 PV calls. Total is 256 calls/pass, 16,640 calls at 65 passes. Across two KV heads that is 33,280 calls, or 68,157,440 tile-issued scalar MAC terms for QK+PV. The equivalent useful work for 12 heads is lower; this tile count includes padded head rows and cell-tail padding. These are algorithmic source counts, not machine instruction, throughput, or time measurements.

The current Direct=1 declared local-accessor sum is 44,500 B per work-group: qhi/qlo 16,384; kv 16,384; phi/plo 8,192; scores 2,048; ks/vs 1,024; maxima/sums/alpha 192; factors 16; final 4; rows 256. The current matrix admission function separately requires the device-reported local-memory size to be at least 60,880 B for mode 1 and max work-group size at least 128. That threshold is an existing conservative gate, not compiled allocation evidence or occupancy. The source checks subgroup 16 and the FP16/FP32 matrix combination.

| CH16 / WG128 | 129 / 2,064 | 64 | 64 | 33,024 | 67,633,152 | 30,548 |

CH16 reduces declared bytes by 13,952 B and total matrix MAC terms by about 0.77%, but nearly doubles the per-group barrier count at cap: 903 instead of 455. It reduces each PV K loop from two 16-cell panels to one and requires only two QK cell/head tiles per pass. CH64 cuts passes and per-group barriers to 33 and 231, but raises source accessor sum to 72,404 B and matrix MAC terms by about 1.54% from 61 padded final cells and the same 16 padded heads. The existing 60,880-B mode-1 admission floor is not sufficient as a CH64 resource rule; a geometry-specific admission bound and actual compiler allocation evidence would be required before launch. Neither CH16 nor CH64 changes the 16-versus-12 query-row padding.

WG64 cannot simply halve the work-group size while preserving one group per query/KV head. Four subgroups could cover only one 8-row band in QK/PV under the current mapping. A viable isolated WG64/CH32 shape therefore needs two groups per query/KV head, each with eight local padded rows and disjoint live head ranges (for example 8+4 or 6+6). It preserves total padded head matrix work but doubles group count and duplicates selected-row resolution and K/V staging. The per-group Direct=1 declared sum is 31,092 B; this smaller number cannot be turned into a B570 occupancy claim. The split's source correctness requirements are detailed below. R568 already examined the combined CH64/WG64 split and its duplicated-gather cost; it remains an unmeasured proposal and is not evidence for this isolated CH32/WG64 variant.

## Required source changes and correctness contract

For **CH16**, changing the constant alone is incorrect. The QK mapping must change from four subgroups covering two head bands × two 16-cell bands to two subgroups covering the two 8-row head bands at cell offset zero. Leaving the old `subgroup%2` cell offset would make subgroup 2/3 read a cell tile beyond the 16-cell `kv`/score arrays. PV's cell-panel loop must become one panel. All `CH`-sized accessors, `c0` increments, count tails, score/softmax loops, scale/code gathers, and matrix strides must consistently use 16. Zero-initialize every invalid/tail slot before matrix loads and retain uniform barriers. Preserve external query/output stride 12, row-ID/page mapping, scale application, online softmax, and Direct output coverage.

For **CH64/WG128**, QK must cover four 16-cell panels for each of two padded head bands: use eight QK subgroups with `head=(subgroup/4)*8` and `cell=(subgroup%4)*16`; the current `subgroup<4` and `%2` mapping misses half the cells. PV's matrix inner loop then covers four cell panels. Grow all cell-dependent local arrays and `c0` steps consistently; safely zero all 61 tail cells in the final tile and retain row/page bounds behavior. Recompute the mode-1 admission limit for the larger declarations and check actual compiler resource metadata before attempting the route. Do not infer launch safety from source bytes alone.

For **WG64/CH32 with two head tiles**, initially limit the experiment to Direct=1 so the direct stores can be audited without adding split `final` staging. Extend work-group indexing with a tile coordinate; each group owns one KV head and one head tile. Each group uses eight padded local rows, four subgroups, two QK subgroups for that tile's two 16-cell bands, and four PV subgroups for its four output-dimension bands. Guard every output by the tile's live-head count, store to external row `kvhead*12 + head_base + local_row`, and never use local padding as the global head stride. Keep the groups' actual head ranges disjoint and cover all 12 rows exactly once for every batch/query/KV head. To preserve the current FP16 hi/lo input decomposition, compute `qm`/shift from all 12 actual query rows and use the same result in both tiles; a tile-local maximum changes rounding even if the scale algebra cancels. Keep online max/sum/alpha independent per actual row and zero padded local rows. Each group repeats the same IDs, page lookup, and KV gather; do not add a cross-group output reduction. Cover n_q=1 and >1, both KV heads, 8+4 or 6+6 row boundaries, and verify no missing/overlapping outputs. If supporting Direct=0 later, separately resize and reindex its `final` store/copy path.

For all three candidates, preserve empty and partial selections, negative ID/page zero-fill behavior, page-table indirection, cap 2,051, and the physical-context caller contract. Compare all 24 output heads over all 256 dimensions against current mode-1 output for identical inputs/IDs/steps/page tables, plus existing reference tolerances and finite checks. For split WG64, also verify exact output writer coverage before numerical parity. A source-level index proof is not component parity; no geometry candidate was compiled or tested in this review.

## Disposition and decision gates

No geometry candidate can be ranked for speed from this evidence. CH16 is the least resource-demanding source variant and has slightly fewer padded matrix terms, but it doubles barrier/control passes and there is no evidence those saved resources matter. CH64 has fewer serial passes but exceeds the current mode-1 admission floor on source declarations and adds padded matrix work. WG64 lowers per-group declarations but requires two groups, duplicates gather/staging, and changes query scale-sharing semantics unless the common scale is preserved. Treat these as conditional designs only.

Before choosing one, Main should first finish the current source qualification and obtain the actual geometry-independent component route/resource record for the exact C8192, Direct=1, mode-1 workload. Require the matrix/fallback counts and selected-width distribution. Then compile each candidate from a pinned source snapshot with the configured SYCL compiler; record generated matrix lowering, GRF/registers, spills, actual SLM allocation and device admission. Verify component parity, and only then compare isolated component service with identical selections and the same whole-prefill route. Intel's own guide identifies work-group size, subgroup size, registers and SLM as occupancy factors and cautions that higher occupancy does not itself guarantee speed; these factors must be measured for this kernel/device ([Intel GPU thread mapping and occupancy](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2025-2/thread-mapping-and-gpu-occupancy.html)). SYCL `joint_matrix` operations are subgroup group functions and must be reached in converged control flow, which is why each changed mapping must retain full 16-lane participation for every matrix call ([Intel LLVM oneAPI matrix extension](https://github.com/intel/llvm/blob/sycl/sycl/doc/extensions/experimental/sycl_ext_matrix/sycl_ext_oneapi_matrix.asciidoc)).

No 600/1,000 tok/s qualification, kernel bottleneck claim, occupancy, resource allocation, or adoption decision follows from this source accounting or the nonexclusive profile.
