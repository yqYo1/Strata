# R593 — QSA score GEMM candidate safety review

2026-10-15 JST。Read-only review of `qsa-score-gemm-candidate-v1` against R589, R563/564, R568, R581, R583, `research-index.json`, and the layer-26 phase report. No source edits, build, test, GPU/service action, Git mutation, or cleanup. The actual 34K GPU phase was treated as live; it was not inspected or interrupted. This report is the only write.

## Decision

No new deterministic indexing, address, or queue-order bug is apparent from the candidate patch. The score-only design preserves the reviewed geometry and selection semantics: query rows stay 512 FP32 values apart (`lda=512`), pooled keys are 128 values apart, GEMM output uses `blocks+1` scratch stride and the existing `blocks` output stride, and each query masks writes above its own `n_bid`. The last query's `last_n/4` only bounds the shared converted-key preparation; each query still selects its own dead row at converted column `live`. Completed dead blocks retain zero top-k weight when `n%4==0`; a partial tail uses the existing additive `+1e9` and `n%4` cell weight. Future scores remain untouched, and top-k reads only through the query's `n_bid`.

The QSA index append completes on the same in-order queue before `prepare`; converted pooled/dead rows are rebuilt for each layer/chunk, then reused only across that chunk's selection batches, and the view is invalidated before shared arena reuse. `queue_for()` enforces in-order queues. These checks validate the source contract only; the candidate remains unbuilt and unexecuted.

Three blockers remain before this intentional precision change can qualify:

1. **Nonfinite fallback has a known uncovered case.** `qsa_score_gemm.cpp` falls back when a GEMM result cell is nonfinite, and recomputes the complete FP32 score when the final head sum is nonfinite (`candidate.patch:289-318`). If oneMKL maps a NaN/Inf input to a finite C value, this check cannot detect or correct it. The proposal states this limitation (`README.md:62-66`), but its device fixture is unrun and there is no recorded proof of oneMKL's behavior for raw NaN/Inf, `Inf*0`, half overflow, and accumulation overflow at the actual B570/library version. Before any enabled model run, compare every such cell and resulting top-k against the existing FP32 scorer; any finite-but-wrong C result blocks the candidate or requires a stronger detection path. Also compare the fallback's exact FP32 result class and score against `qsa_block_scores.cpp` behavior, not just the hand-built CPU oracle.

2. **The memory/admission effect on the resident prefix is unmeasured.** The explicit added scratch is 84,152,064 bytes (80.25 MiB), with the existing `sel_scores` remaining allocated; the allocator's rounded region request can add up to 84,152,320 bytes. It enters the shared `max(gdn,qsa,moe)` arena, so the VRAM delta depends on which set currently dominates. The proposal correctly excludes oneMKL/driver internal workspace from that explicit total (`README.md:45-56`). No candidate receipt measures cold and warmed free-memory peak, actual arena delta, oneMKL workspace/pool allocation, 512 MiB reserve, or the resulting auto-GPU-residual expert prefix. Since cache admission is discrete by expert blob, a nominal 64 MiB/80.25 MiB scratch difference cannot be translated into a slot count without the actual budget and prefix margin. Record all of these in the same candidate run; reject if cache loss or hidden allocations break the existing memory contract.

3. **There is no direct selection-quality evidence for either dtype.** FP16/BF16 changes feed top-k routing, so score closeness alone cannot clear this gate. The candidate has no B570 execution, route-flip count, model-quality result, or predeclared allowed quality delta. External evidence is suggestive but not transferable: a separate Qwen3.8 quantization report says it retained the QSA indexer in BF16 because small perturbations can change near-tie routing, while its measured quality section is for a different overall quantization setup and does not report a score-only FP16/BF16 GEMM A/B. The Qwen3.8 architecture paper describes QSA's compressed indexer but reports no such dtype ablation. Therefore neither “FP16 has more mantissa bits” nor that third-party note establishes either arm's quality on this fork. Require paired FP32/FP16/BF16 score margins and selected-cell flips, then the predeclared long-context/task, logits or NLL, and RESTORE checks before adoption.

## Specific static checks

| Contract | Review result |
| --- | --- |
| `query[t*512+h*128]`, pooled stride 128, C row stride `max_blocks+1`, output row stride `max_blocks` | Consistent between `score_product`, pack, postprocessing, and existing buffers. No head/row stride defect found. |
| `n_bid + n%4` and causal tail | Candidate uses `nb=n/4`; reads converted dead row for `b==nb`; top-k still supplies completed-block weight 4 and tail weight `n%4`. It preserves the additive tail boost and does not promote it unconditionally. |
| Future writes and unused ID slots | Candidate returns for `b>nb`; existing top-k only scans `nb+1`. Fixture/component contain sentinels, but remain unexecuted. |
| Converted pooled-key update point | `prepare` follows full-chunk index append and precedes selection. Each QSA layer/chunk rebuilds converted rows; query conversion is per selection batch. This is consistent with pooled rows becoming final at chunk append completion. |
| Queue ordering and scratch ownership | Same in-order queue carries conversion, four GEMMs, post kernels, top-k, and later arena reuse. The candidate owns no USM and adds no wait. Runtime/library async exception behavior and B570 oneMKL allocation/lifetime still need execution evidence. |
| Maximum logical context | Bounds allow 262,144 tokens and `max_blocks=65,538`; logical context is not evidence of physical 256K residency or full-boundary model correctness. |

The hand-authored CPU fixture covers causal/tail examples and address arithmetic, while the manual component calls the actual proposed helper; neither has been run. The component's hand-built constant-value oracle also cannot establish general FP32/GEMM agreement or model quality. No source change is recommended from this static pass; retain default OFF until the three gates above pass.

## External evidence, limited scope

- The [Qwen3.8-Next architecture paper](https://arxiv.org/abs/2608.30320) describes QSA as micro-block scoring through a compressed indexer and says candidate changes were judged across quality and cost axes. The abstract does not report FP16/BF16 score-only selection quality.
- A [separate Qwen3.8 quantization report](https://huggingface.co/Soomin33/Qwen3.8-Flash-Next-FP6-INT8) says it kept the QSA indexer in BF16 because perturbations can affect near-tie top-k routing (README text around lines 145-159). Its listed model/task measurements concern a distinct quantized checkpoint and other kernels; they are not a paired score-only dtype experiment for this candidate. Treat this as a sensitivity warning, not measured candidate quality.
- Intel's [oneAPI XMX guide](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2024-1/xmx.html) documents FP16/BF16 XMX support and oneMKL XMX GEMM algorithms. Its performance table is for Data Center GPU Max 1550 with Xeon 8480+, not Arc B570, and provides no routing-quality guarantee.

No direct external B570 or Qwen3.8 score-only FP16/BF16 GEMM selection-quality comparison was located in this limited search.
