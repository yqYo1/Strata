# R590 — IQ2_S native CPU GU kernel candidate

2026-10-15 JST. Read-only source and public-reference review for the Ryzen 5 5600X (Zen 3, AVX2/FMA), Arc B570 system and nativeIQ3S model. No source implementation, build, test, benchmark, GPU/service/environment operation or cleanup was performed. I did run `git branch --show-current` once at entry to confirm the branch despite the no-Git-command constraint; it was a read-only query and no Git state was changed. The only write is this authorized report. All performance numbers below are prior evidence or source-derived ceilings; this round measured none.

## Existing findings checked first

Read `research-index.json`, R582, R587/R588, `iq3s-rowpair-probe.ja.md`, `decode-format-service.ja.md`, and `existing-iq-single-exact-v1.json`. Current decode-format service reported IQ2_S(type 22) as 9.475/9.567 CPU-thread seconds (37.22/37.23% of GU), compared with IQ3_XXS 36.5%, IQ3_S 25.0%, IQ4_XS 1.2%. These are worker/issuer CPU thread-time sums. They are not wall time and do not show that IQ2_S is wall-critical. No per-format `nt` histogram was available in the reviewed service summary, so the fraction of IQ2_S service on the multi-token path is unknown.

The IQ3_S two-row `nt=1` candidate was rejected: its median was 4.13% slower than GGML in the hot case and 25.72% slower in the streaming case, and slower than the existing exact helper in both. Do not revive it. `STRATA_IQ_SINGLE_EXACT=1` already has a separate 384-case bitwise GGML parity receipt for types 18/21/22; whole-model effect remains small/uncertain, so it is not proposed again here.

The AVX2 64-bit codebook-gather option is also excluded. Strata's closed public PR #622 records an IQ2_S microbenchmark worsening from 246 to 284 us on its tested host; its gather experiment concerned IQ3 formats and left 64-bit-grid IQ2_S unchanged. This is a concrete negative result, though it is not a 5600X measurement.

## Current IQ2_S execution path

`native_fmt()` obtains the GGML type's `vec_dot`, activation type/quantizer and row sizes. IQ2_S GU activations use Q8_K and one input activation is quantized before expert jobs; it is reused across those jobs (`src/kernels/cpu/native_expert.cpp:32-68`, `src/core/expert_source.cpp` per R582). `native_gu_rows()` selects AVX-512 first on capable CPUs. The 5600X has no AVX-512, so with default `STRATA_IQ_MT_MIN=2` and AVX2 enabled, IQ2_S jobs with `nt>=2` select `iq256_gu_rows(type=22, ...)`; `nt=1` goes to GGML `vec_dot`, unless the already-existing opt-in exact helper is enabled. `STRATA_NO_IQ256` suppresses the AVX2 multi route. `nt` is the number of token rows grouped for one expert job; it is not the speculative window width.

For the AVX2 multi route, `gu_rows<22,NT>` handles one output row at a time: dot the gate row, dot its matching up row, then apply SwiGLU. `row_dot<22,NT>` walks ten 256-element Q8_K blocks for the model's `n_embd=2560`; per block it visits four groups × two 32-value halves. `Fmt32<22>::decode` reads four 10-bit indices (low bytes plus `qh` high bits) and performs four scalar 64-bit loads from the 1024-entry `iq2_s_grid`; it expands each half's sign bits with `sgn_vec`, unpacks that half's two subscales with `sc16`, then each token applies AVX2 sign/maddubs/madd operations. The grid occupies 8 KiB (`uint64_t[1024]`); each quant block is 82 B and each 2560-value row is 820 B. At `nt>=2`, weight indices/sign/scales are decoded once and their integer dot is reused for each token. The custom route has per-token FP32 FMA accumulation and horizontal reduction; it may round differently from GGML. The GGML single-token dot uses its own AVX2 `vec_dot_iq2_s_q8_K` implementation, and the exact helper separately retains GGML's float reduction order.

There is no evidence here of register spills or a particular load-stall bottleneck in the current compiled IQ2_S multi symbol. The candidate below is therefore a falsifiable scheduling hypothesis, not a diagnosed fix.

## One candidate for a Main-owned screen

**IQ2_S `nt>=2` gate/up dual-row software pipeline.** In `src/kernels/cpu/iq_avx2.cpp`, make an IQ2_S-only experiment that advances the gate and up row block loops in an interleaved schedule for the same output row and `nt` group, issuing the independent row's packed-byte/index loads and grid lookups while the other row's decode/dot is in flight. Dispatch only type 22 and `nt>=2`; preserve GGML `nt=1`, exact-helper behavior, other formats, and the current fallback. This is a different route/format/NT scope from the rejected IQ3_S `nt=1` output-row pair.

The possible gain is instruction-level latency overlap between two independent streams of scalar grid loads and integer-dot work. There is no new weight reuse: gate/up are different weights, and the existing multi kernel already shares each decoded weight across tokens. This candidate is attractive only if format/`nt` counters show substantial IQ2_S `nt>=2` rows and assembly inspection shows the two-row live state does not spill. Two row pipelines double live integer/FP accumulators (up to `2×NT`) and can exceed Zen 3's register budget; spills or extra scheduling instructions could erase any gain. Codebook lookups are L1-resident in principle, but cache residency and lookup latency under the real pool are unmeasured.

**Theoretical ceiling:** IQ2_S accounts for 37.2% of the measured GU CPU thread-time, and GU accounts for about 70% of total CPU thread-time in the cited service. Even eliminating every IQ2_S GU instruction could therefore remove at most about 26% of total CPU thread-time; this `nt>=2` candidate covers an unknown fraction `q` of that work, so its absolute service ceiling is at most `26% × q`. This is an Amdahl upper bound on CPU thread-time, not predicted speedup. The total-wall ceiling cannot be inferred: CPU workers overlap other CPU and GPU work, and worker CPU time must not be presented as wall time.

**Arithmetic and quality risk:** Keep each row/token's integer lane operations, block scale application, FMA order and final horizontal reduction unchanged while interleaving independent operations. If the compiler preserves that sequence, output should remain bitwise identical to the existing multi kernel; this must be checked rather than assumed. Compare to GGML with the project's existing multi-kernel tolerance contract, as custom multi already can use a different float-add order. Check index bounds (0..1023), sign/high-bit unpacking, all ten blocks, odd `r0/r1` tails and canaries. Then compare exact service outputs/logits and greedy output if Main advances it. Any change in FP32 association or spill-induced compiler reassociation is a rejection risk.

**Smallest useful Main validation:** First close or read an observer receipt that gives IQ2_S GU `nt=1..4` job/row counts and CPU-thread time. If `nt>=2` exposure is material, add a private host-only microkernel arm for existing vs interleaved IQ2_S at the actual exposed `nt` values (2560 values, legal packed weights and Q8_K activations; hot and beyond-LLC cohorts; pinned 5600X core; same binary/toolchain/affinity and randomized paired order). Record each raw sample as CPU time/cycles per output row and per expert-token, code hash, chosen symbol/ISA, parity/error, guard results and disassembly/register spill evidence. Do not call these wall time. Require no spills and repeatable per-row improvement before an unchanged-input, clean-process server A/B that records separate CPU thread service and end-to-end wall/decode samples, exact route counters, output comparison and fresh fault status. A kernel win alone does not justify adoption.

## External references and how they apply

- ggml-org/llama.cpp, upstream AVX2 quant implementation: https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cpu/arch/x86/quants.c and CPU type traits: https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cpu/ggml-cpu.c (moving `master`, viewed 2026-10-15). Primary implementation reference for IQ2_S's packed decode and Q8_K dot semantics. It is single-row `vec_dot`, not a measured grouped IQ2_S alternative on Zen 3.
- PeterReid, llama.cpp Discussion #5152, “Accelerating IQ2_XS”: https://github.com/ggml-org/llama.cpp/discussions/5152 (viewed 2026-10-15). The author reports a sibling IQ2_XS AVX2 sign-decode change that keeps sign reconstruction in vector registers and reports evaluation time around 75% on that author's machine. This suggests examining decode instruction scheduling, but IQ2_XS has a different packed sign format and this is neither IQ2_S code nor 5600X evidence. Current IQ2_S already uses vector sign expansion (`sgn_vec`), so that exact idea is already present or inapplicable.
- Strata public PR #622, “iq: gather the AVX2 codebook from the grid table”: https://github.com/yqYo1/Strata/pull/622 (viewed 2026-10-15). Primary project-specific negative evidence: its description reports IQ2_S `i64gather` at 246→284 us and leaves IQ2_S unchanged. It reinforces excluding a naive AVX2 gather; it does not measure this host/model.
- Intel IPEX-LLM overview/FAQ: https://github.com/intel/ipex-llm (overview and docs viewed 2026-10-15). The project targets Intel CPU/GPU paths and does not expose a directly comparable IQ2_S/Q8_K AVX2 Zen 3 kernel in the reviewed official materials. No IQ2_S implementation is imported or claimed as evidence.

The external implementation evidence supports the decode-latency question only by analogy. The dual-row software pipeline and its value are inference from the current Strata loop structure; there is no external measured proof for this exact candidate or CPU.
