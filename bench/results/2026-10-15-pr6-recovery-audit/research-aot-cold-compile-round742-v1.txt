## Finding

`STRATA_SYCL_DEVICE_ARCH=bmg_g21` is a distinct hardware-specific AOT build path, not an environment switch that converts the current generic/JIT executable. In `cmake/sycl_backend.cmake`, an empty architecture leaves the generic SYCL target. A nonempty architecture adds `-fsycl-targets=spir64_gen` to compile and link options; the final link passes `-device bmg_g21` to the `spir64_gen` backend. The optional double-GRF flag defaults OFF. Because the options are PUBLIC on `strata_sycl_runtime`, they propagate through linked SYCL libraries and consumers. The resolver path therefore includes the compile database's per-translation-unit driver command and the final device-link command; confirming only a CMake cache value is insufficient. The driver-selected device backend/OCLOC and its IGC libraries must be captured from the actual verbose build, not guessed from whichever `ocloc` happens to be on the caller's `PATH`.

The closed R742 model receipt uses binary SHA-256 `0e62c5fa74cb6a077aef5c5977617e6d74fbd8c2c712ac8f80f3445946289a36`, matching the recorded R739 generic/JIT build (`STRATA_SYCL_DEVICE_ARCH` empty). It ran the official prefill-only plan: one short chat warmup, then a fresh long prompt. Its environment set `SYCL_CACHE_PERSISTENT=0` and a private `XDG_CACHE_HOME`; it did not record `NEO_CACHE_PERSISTENT`. This is not a cold process/first-use measurement: runtime and model loading occurred before the timed long prefill, and the warmup can initialize the runtime and compile/cache whatever short-path kernels it calls. It may leave long-prefill-only kernels or specializations for first use, but the receipt does not establish which specializations were warmed. The device profile classifies kernels as JIT or AOT; that is useful dispatch evidence, not a per-kernel first-compile timing record.

R742 arm 1 reports diagnostic PP `346.6 tok/s`, wrapper `225088 ms`, QSA attention queue interval `69692.0 ms`, and selection queue interval `17945.8 ms`. These are instrumented, nonexclusive phase intervals from an actual model diagnostic, not cold-compile attribution. The earlier instrumented 309.9 tok/s record had other timing differences and cannot establish a PP gain or a JIT cost. Do not infer compile time by subtracting timestamps or phase totals.

## What first use remains uncovered, and what AOT can change

The current short warmup does not isolate or time a truly fresh process's first use of the long prompt path. Unresolved components include process/runtime and driver initialization, image enumeration/selection, any first-use JIT for long-prefill device images or specialization variants, any residual JIT for kernels not present in a matching AOT image, and cache effects from both the SYCL layer and NEO/IGC. The model receipt does not prove that its private XDG path controlled every cache layer. Current R739 evidence establishes the actual path for one live process, not cache behavior or JIT timing.

A matched `spir64_gen`/`bmg_g21` image can remove IGC's runtime compilation for device images that are actually present, accepted for the installed device, and selected by the runtime. It cannot remove host C++ build/link cost, process and plugin initialization, device enumeration, module/image loading, allocation, first-launch setup, kernel execution, or JIT for absent/generic images and other libraries (including independently generated library kernels). It cannot by itself prove that the live generic executable used AOT or that AOT and JIT kernels are functionally interchangeable. AOT may also change backend compilation choices; static AOT resources are not JIT resource measurements. A clean AOT first-launch wall time would still combine initialization, load and execution with any remaining compilation, so it is not pure compiler time.

## Loader and toolchain version correction

R739's package metadata named `libigc2 2.40.13` and `libigdfcl2 2.40.13`, but that was not evidence of what the model process loaded. The fresh read-only `/proc/maps` receipt `own-qsa-select-model-a1-loaded-libraries-v1.json` records the actual arm-1 native process mappings:

- `/usr/local/lib/libigc.so.2.41.5+1788943183`
- `/usr/local/lib/libigdfcl.so.2.41.5+1788943183`

The same process loaded the Level Zero driver `/usr/lib/x86_64-linux-gnu/libze_intel_gpu.so.1.17.39395`, the Level Zero loader `/usr/lib/x86_64-linux-gnu/libze_loader.so.1.32.0`, and SYCL/UR components from the pinned LLVM install. Therefore package metadata alone is not a version pin for an AOT compiler run or a future JIT capture. Loader search order, embedded RUNPATH/RPATH, `LD_LIBRARY_PATH`, driver discovery and vendor-library selection can choose different IGC/IGDFCL builds. `/usr/local/lib` is particularly material here because it is outside the Debian package path cited in R739. Before any later AOT/JIT comparison, record exact hashes and mapped paths for compiler-resolved backend tools and the process-loaded IGC, IGDFCL, Level Zero driver/loader, UR adapter/loader and SYCL runtime. If the resolver or mapped set is unexpected or differs between arms, stop the comparison and label it a different toolchain/loader stack. The R739 package versions are superseded as runtime-loaded-library claims; retain them only as package metadata.

## Scope and next decision

The configured `bmg_g21` path is technically available in project CMake, but this audit found no bmg_g21 build receipt, AOT image selection proof, qualified AOT fixture or cold JIT timing. AOT is a reasonable hardware-specific candidate to qualify after controlled build isolation, especially to test whether matching prompt kernels avoid runtime compiler work. It is not evidence of a measured cold-compile cost or a whole-prefill speed improvement. First resolve/pin the backend tool and actual loaded-library versions, then require independent fixture correctness and AOT image-selection evidence; only afterward consider a matched clean model arm. Keep full-context correctness, numerical quality, and repeated >600 tok/s long-prefill measurements as separate gates.
