# R981 — Pageable versus host-USM layer upload path

Classification: decision support. Read-only source and literature research; no build, test, GPU run, profiler, process inspection, Git command, or project edit. Report limit: 18,432 bytes.

## Decision

Keep the existing pageable upload as the control. A single host-USM slab is the cleanest first comparison because it changes the source allocation while preserving the expert bytes, per-expert copy calls, cache slots, same queue, and checked drain. The project still has to CPU-copy each source blob into its owned staging slab; host USM alone does not remove that work. The existing profile and public UR/Level Zero source do not establish whether the current ordinary heap source causes internal driver staging, whether a host-USM slab lowers end-to-end time, or whether the GPU copy engine is busy for the whole measured interval.

A bounded double buffer tests a separate hypothesis: CPU preparation of the next layer might overlap GPU execution of the current layer. It does not by itself overlap H2D transfer with compute. The route uses one in-order queue for copy and compute and reuses one device expert cache, so the next layer's upload cannot safely overwrite those slots until the current layer finishes. Do not combine allocation, buffering, and copy-granularity changes in one arm.

## Current path and copy semantics

`src/prefill/layer_major.inc:242-253` admits one `cache_bytes` upload slab, then allocates it with `new uint8_t[]`. For each layer, `copy_blob` copies the source into that owned slab; its comment says a borrowed blob pointer may only live until the next `blob()` call (`:483-495`). The route then issues 512 `ExpertCache::fill_slot` calls with the layer's exact width (`:496-514`). Each call invokes `cudaMemcpyAsync` with the source pointer and exact byte count (`src/core/expert_cache.cpp:358-377`). The route requires `m.copy == m.cs`, submits to the same queue, and performs a checked drain before publishing the layer to compute (`layer_major.inc:511-518`). Layer boundaries also drain before preparing the next layer (`:472-487`).

The slab capacity is 1,363,148,800 bytes (2,662,400-byte stride × 512 slots), even though the current width census totals 50,292,326,400 transfer bytes across all 48 layers. Each host-USM arm should allocate the same one-layer slab capacity and transfer the same exact widths; a second buffer costs another 1,363,148,800 bytes. Filling full stride or introducing a rectangle changes requested traffic and confounds this comparison.

In the SYCL compatibility layer, `cudaHostAlloc` is an owned host allocation, while `cudaHostRegister` explicitly returns not-supported (`src/sycl/compat.cpp:228-244`). The host allocation implementation uses `sycl::malloc_host` (`src/sycl/runtime.cpp:192-209`). `cudaMemcpyAsync` delegates to `queue(st).memcpy` (`compat.cpp:255-261`); it does not implement a CPU `memcpy` stage in that wrapper. The project's `cudaMemcpy2DAsync` compatibility path loops over rows and calls queue `memcpy` for each row (`compat.cpp:272-286`), so a 2D API call alone would not prove a single native rectangle transfer.

The reviewed official UR v2 source at Intel LLVM `sycl` commit `4a08d0453c6b37a6e1eb5f52933f79c734b1149c` forwards `urEnqueueUSMMemcpy` to a queue implementation. Its batched queue appends `appendUSMMemcpy(false, ...)` and only finishes the queue for a blocking request. The command-list manager sends `appendUSMMemcpy` to `zeCommandListAppendMemoryCopy`; it calls host synchronize only for the blocking case. The immediate in-order queue code enables copy offload for its command list. These are submission and queue semantics. They do not prove a particular hardware engine, no driver-internal staging, or a physical DMA for a raw `new[]` source.

Level Zero's copy specification says the operation copies host, device, or shared memory and requires both pointers to be device-accessible; it defines the API operation rather than how an implementation moves bytes. Source data therefore has to remain owned and unchanged until the copy is retired. The layer's existing checked drain is a conservative lifetime boundary. A host-USM candidate should preserve that boundary unless it records and checks an event for each buffer before reusing it.

SYCL 2020 revision 12 describes host USM as host-resident, device-accessible memory that does not migrate to the device, requires SYCL allocation routines for guaranteed host-allocation behavior, and can be limited by pinnable host memory. Intel's optimization guide recommends `malloc_host` when the application controls the source allocation for explicit data movement, while separately describing system-memory import as an explicit lifetime-managed path. This supports testing one owned host-USM slab; it does not imply a speedup. The UR Level Zero reference lists host-pointer-import controls separately, with import disabled by its documented default. The current route's direct `queue.memcpy` source should not be assumed imported or pinned from the adapter setting alone.

The external-memory-mapping Level Zero extension describes page-aligned host memory registration and its lifetime/overlap constraints. This route has a direct compatibility refusal for arbitrary host registration, so it is not a candidate here.

## Comparison by arm

| Arm | What changes | What it can reveal | Costs and limits |
| --- | --- | --- | --- |
| Current ordinary heap slab | Control; `new[]`, same `copy_blob`, 512 exact-width queue copies, same drain | Existing per-layer source preparation, submit CPU, and request boundary | Runtime or driver may stage ordinary host memory internally; public UR source does not expose that detail |
| One host-USM slab | Allocate one slab through the existing owned host-USM path; write source blobs directly into it; retain same stride, 512 copy calls, exact widths, queue, and drain | Whether a device-accessible host allocation changes request wall or submit/wait behavior without altering bytes or topology | Still performs source-to-slab CPU copies and H2D copies; host allocation, first-touch, and pinning cost; pinned-memory limit may be lower than free RAM; the previous 320 MiB screen is counterevidence to a universal gain |
| Two host-USM slabs | Add one bounded producer that copies the next layer into the alternate slab while the current layer computes; enqueue the next layer only after the shared device cache is free | Whether source-copy time can be hidden under compute and reduce layer-boundary idle time | Adds another 1.363 GB host allocation; depends on source-copy overlap being longer than producer/scheduling cost; host memory traffic may contend with the active workload; H2D and compute remain ordered on the shared in-order queue |

For the double-buffer arm, keep `copy_blob` calls serialized through one producer and do not allow borrowed source pointers to escape a call. The alternate slab cannot be overwritten until its own upload completion is checked. Do not submit next-layer copies early into the one device cache while the current layer still reads it. A separate transfer queue or second device cache would be a different design with additional device memory and different ordering, outside this comparison.

## Smallest decision-quality physical measurement

Use one matched, three-arm end-to-end cohort on the same already-used 39K long-input workload that activates the optimized path. Run each arm in three fresh native processes, with the exact same model identity, prompt bytes, build, device, driver/UR v2 selection, and process environment captured before runtime initialization. One workload shape avoids a broad sweep; three independent processes per arm can screen against run-to-run noise. Treat this as a screening result, not adoption evidence. If the cohort is inconclusive, stop before a wider sweep and decide whether the remaining opportunity justifies another Main-owned measurement.

For every arm, require the same 48 layer widths, 50,292,326,400 requested upload bytes, 24,576 logical `fill_slot` calls, successful checked retirement, and unchanged first consuming compute. Keep the current exact-width copy path in all arms. Report complete request wall time from route entry to final checked completion, including per-request allocation and first-touch. Also retain separate CPU/wall totals for allocation, source `copy_blob`, copy submission, queue drain/wait, and compute; attribute caller CPU during wait apart from outside-wait submission.

Record actual native copy-append counts and per-layer source/submit/drain intervals. Where a supported, low-perturbation counter exposes copy-engine activity and transferred bytes, record it for a representative layer; compare that activity with queue/event interval and route wall. If the counter is unavailable, report requested bytes and queue/event times only and leave physical link rate and engine saturation unqualified. A single event spanning many submits can include host submission gaps, so it is not by itself an engine-utilization measurement. Preserve the exact process-level Level Zero/SYCL environment for every arm; do not switch environment variables after runtime/provider initialization.

For host-USM arms, preflight the extra host allocation before submitting model work. Keep the present RAM headroom policy, separately record host-allocation failure/locked-memory limits, and release buffers only after the checked retirement path succeeds. The double-buffer arm must account for an additional `cache_bytes` in the host admission plan; do not create it speculatively after device work is live. On any allocation or copy failure, retain owners until the queue-retirement check proves they can be released. If a selected host-USM allocation cannot be made within the machine's admitted memory limits, record that mode as not feasible on this host and make no fallback-to-measured-win claim.

A model-path win requires lower end-to-end request wall time beyond the existing cohort's variation, with unchanged payload/call counts and no failures. Lower submit CPU alone, a different event interval, or higher measured transfer bandwidth without a request-wall gain is insufficient. If ordinary versus one-slab host-USM remains equal, the two-buffer arm is only justified by evidence that source preparation overlaps current compute; if the double-buffer request wall also stays equal, no upload-path change is qualified.
