# R847 — What event timestamps and a system trace actually time

**Decision support; public-source comparison only.** The documents below are fixed reference points: Khronos SYCL 2020 revision 12 (6 August 2026), Unified Runtime 0.12, Level Zero specification 1.9.3 (including its timestamp extension introduced in API version 1.6), and Intel VTune Profiler User Guide 2025.1 (2 May 2025). These are contract and tool-document revisions, not a claim about the versions loaded by Strata or the capabilities of its current device. No local profiling or runtime inspection was performed.

A command interval, a queue interval, and a request interval answer different questions. Per-command device timestamps tell when a submitted operation began and ended on the device timeline. Host clocks tell how long application work and submit calls took. A system trace relates those lanes and may expose gaps and overlap, but only a request boundary plus causal edges can support an end-to-end critical-path account. None of these quantities, by itself, is “exclusive GPU service.”

## Comparison

| Mechanism and revision | What the timestamps cover | Requirements, clock and costs | Main attribution limit |
|---|---|---|---|
| SYCL event profiling, SYCL 2020 Rev. 12; UR 0.12 event API | SYCL `command_submit` is recorded after the command-group function object returns and before `queue::submit` returns. `command_start` and `command_end` mark the command-group action’s device execution. The UR API additionally names `QUEUED`, `SUBMIT`, `START`, `END`, and `COMPLETE`; `COMPLETE` includes child events enqueued by that command on device. | Construct the SYCL queue with `property::queue::enable_profiling`; its device must advertise `aspect::queue_profiling`. Timestamps are 64-bit nanoseconds from an implementation-defined epoch. SYCL guarantees a shared timebase for events on the same backend, but no fixed accuracy; `command_start` queries can block until running or complete, and `command_end` until complete. UR profiling queries are optional and return not-available if the queue lacks its profiling flag; adapters may also reject unsupported properties. | `submit→start` includes queue backlog, dependency readiness, runtime and device dispatch delay; it does not isolate host submission CPU time. `start→end` omits time before device execution and can still reflect scheduling/preemption. Profiling has implementation-specific cost, and the nanosecond unit is not a precision promise. |
| Level Zero timestamp event and `zeEventQueryKernelTimestampsExt`, L0 Spec 1.9.3 | The base kernel timestamp event returns device clock readings at operation start/end. The extension can return kernel-only device timestamps or synchronized results: `global` follows the device’s free-running active clock in host-time units, while `context` reports the context-active interval. | For ordinary event timestamps, use an event pool created with `ZE_EVENT_POOL_FLAG_KERNEL_TIMESTAMP`; read `timerResolution` and `kernelTimestampValidBits`, and handle counter wrap. The synchronized extension requires device-reported support and a pool created with `ZE_EVENT_POOL_FLAG_KERNEL_MAPPED_TIMESTAMP`. The specification says synchronized queries have a performance cost. | It measures a device operation, not the host call that appended it or request completion. `global` and `context` durations answer different clock questions. Extension support is optional; unsupported feature, not-yet-signaled event, low-power state, permissions, sub-device behavior, and wraparound can prevent or complicate a query. |
| Intel VTune Profiler GPU Offload trace, User Guide 2025.1 | A time-correlated view of CPU execution, SYCL/OpenCL tasks, software queues, and GPU activity over the captured process window. VTune documents clock alignment across CPU cores and GPU into a unified time domain and says GPU Offload instruments code on both CPU and GPU. | Requires a supported Intel GPU/software collection path and working driver/permissions; the 2025.1 analysis explicitly targets SYCL/OpenCL and Intel Media SDK. Collection settings affect what is captured. Instrumenting both sides can perturb host submission and task timing; the guide provides no universal fixed correction factor. | Timeline correlation is not automatically a complete causal DAG. GPU utilization/busyness is an activity view, not a sum of exclusive per-command service. Unsupported APIs, missing symbols, hidden runtime work, or coarse utilization sampling can leave gaps or ambiguous attribution. |

The standard SYCL definitions and the UR names line up at the broad boundary but are not interchangeable implementation promises. SYCL’s profiling epoch is implementation-defined; subtracting same-backend timestamps is defined, while comparing raw device timestamps against `steady_clock` is not. UR 0.12 specifies profiling values as device-counter nanoseconds and makes the `COMPLETE` field broader than one event’s `END`. That is useful when a runtime event owns device-side child events, but it is not evidence that every framework child operation is included. The SYCL spec also notes that implementations are encouraged, but not required to make `command_start` close to the actual device start. In both APIs the submission timestamp is a backend event boundary, not a replacement for recording the host’s `submit()` entry/return times. ([Khronos SYCL 2020 Rev. 12](https://registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html); [Unified Runtime 0.12 API](https://oneapi-src.github.io/unified-runtime/core/api.html))

Level Zero offers a lower-level way to make those boundaries explicit, and can expose a host-synchronized form when the extension is present. The extension’s support flags must be queried from the device; its documentation distinguishes the normal kernel timestamp pool from the mapped-timestamp pool and explicitly warns that synchronized timestamp retrieval costs more. The returned `global` and `context` pairs should not be collapsed into one duration: one tracks wall-clock time while the device is active, the other only time while that context is active. For old or narrow counters, wraparound and resolution matter; a timestamp expressed as nanoseconds after conversion does not imply nanosecond precision. This mechanism still does not show time spent in host preparation, between host submissions, or awaiting the final API response. ([Level Zero timestamp extension, spec 1.9.3](https://oneapi-src.github.io/level-zero-spec/level-zero/1.9.3/core/EXT_EventQueryKernelTimestamps.html))

VTune’s value is the joined timeline: it can show the host issuing work while the GPU is idle or active, and aligns clocks so CPU and GPU activity can be viewed together. But an aligned picture is not, by itself, a dependency graph. Two kernels on different queues can overlap; their event durations each count their own interval, so summing them double-counts the overlap. Conversely, host setup, submission gaps, event waits, transfers, or untraced internal runtime work can make request wall time longer than all reported kernel intervals. A timeline also does not prove that visually adjacent operations depend on each other. The request’s critical path is the longest causal path through host spans, queue commands, transfers and waits, including uncovered gaps on that path—not the sum of all queue or event durations. ([Intel VTune Profiler 2025.1 GPU Offload Analysis](https://www.intel.com/content/www/us/en/docs/vtune-profiler/user-guide/2025-1/gpu-offload-analysis.html))

## Evidence that timing can mislead

Original studies provide concrete counterexamples, although their measurements do not predict a modern SYCL runtime. Tillmann, Karcher, Dachsbacher and Tichy’s 2013 CUDA autotuning study timed an empty-kernel path with start/stop events on a GTX 680: its reported 20-launch averages varied from 0.210 to 0.256 ms across block sizes. They warn that event timing plus unpredictable launch overhead makes short GPU measurements inaccurate and that repeated per-kernel costs accumulate. This is evidence that an event-delimited “kernel” measurement can be dominated by the launch/runtime path on that setup, not a calibration for Level Zero. ([Tillmann et al., *Application-independent Autotuning for GPUs*, ParCo 2013](https://publikationen.bibliothek.kit.edu/1000037784/4204007))

Zhou et al.’s HPCToolkit study (Parallel Computing 108, 2021) reported 1.81× overhead for coarse and 2.23× for fine-grained collection on an Intel Gen9 system running a DPC++/OpenCL PeleC workload; instrumented kernel durations were inflated. The paper also found 28.8 MB of GPU allocation but no measured transfers because transfers were implicit and public API wrapping missed them. Thus a detailed trace may still omit runtime-internal activity, and collection can change both the measured interval and the software path. These numbers belong to that old stack and workload, not VTune 2025.1 or Strata. ([Zhou et al., *Measurement and Analysis of GPU-accelerated Applications with HPCToolkit*, 2021](https://mxz297.github.io/files/PARCO21.pdf))

The current local comparison illustrates the attribution boundary without resolving it. Its closed QSA queue-window figures are 33.9610 s for BF16 and 36.2963 s for typed QSA attention, but the profile labels queue windows nonexclusive and inclusive of host submission gaps. Those values are not exclusive GPU service time, cannot be summed with other queue windows as if each used a separate GPU, and cannot alone establish which device command caused the end-to-end difference. The same report says wait-excluded issuing-thread CPU time is about 19.124 s and 19.193 s respectively; that is not a measurement of pure host computation because runtime work and uninstrumented waits may remain. The numbers support the specific limitation here, not a hardware performance conclusion.

## Minimal Main-only evidence plan

1. In a clean, unprofiled owned process, record a host monotonic timestamp at the chosen request start and at final completion/response readiness. Keep this request wall result separate from instrumented runs. It is the end-to-end interval, including application work, transfers, waiting and all overlap visible to the request.
2. In a separate diagnostic process, give each command a stable ID, queue ID and explicit predecessor IDs. Record host monotonic entry/return around command preparation and queue submission, plus wait entry/return. After the terminal drain, collect each supported event’s submit/start/end timestamps. Report `end-start` per command, `submit-start` as aggregate queue/dependency/dispatch delay, and host API spans/gaps as separate quantities; do not subtract raw host and device clocks.
3. Capture one bounded VTune 2025.1 GPU Offload trace for that same diagnostic request with the request’s start and completion marked. Join task IDs and the explicit dependency list to its CPU/GPU lanes; use VTune’s synchronized timeline for cross-domain placement, and mark missing/unsupported work as unattributed. Build the request DAG and calculate the longest causal path from its host start to final completion. Report event-duration sums, overlap/union, and request wall separately; queue-window totals remain nonexclusive. Compare profiled and clean wall only as a perturbation check, not as interchangeable speed samples.

This plan distinguishes device command intervals, host submission gaps and request critical path with three separate pieces of evidence. If the runtime cannot supply per-command timestamps or the trace lacks a joinable event/dependency identity, the corresponding quantity stays unresolved rather than being inferred from a queue-window total.
