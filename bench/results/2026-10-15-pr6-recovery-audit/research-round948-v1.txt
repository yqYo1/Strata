# R948 — FP32 QSA score-tile layout around SYCL joint_matrix

Classification: decision support. Date: 2026-10-17 JST. Finite question: for the current 16-head × 32-cell FP32 score staging buffer, which SLM address mapping is source-legal and worth one controlled Arc B570/Xe2 comparison? No build, test, device query, GPU/profile/process work, environment change, Git command, cleanup, or product/index edit was performed. The only intended write is this report.

## Current path and exact scope

The reviewed production source `src/kernels/sycl/qsa_bf16_prefix.cpp` matches supplied SHA256 `b55684754231c007877e967375f721cf4d88746b698d2a7a9811d2bcdf578081`. It stages `scores` as `local_accessor<float,1>(16*32)`. Four subgroups each produce a disjoint 8×16 region of the logical 16×32 score rectangle. The FP32 accumulator is exposed by `mi::joint_matrix_apply`; its callback writes `scores[(head+r)*32 + cell+c]`. Then work-items `tid=0..15` each own one head, scan cells `c=0..31` in order for max, scan again in order for `sum += p`, and write BF16 `probability[tid*32+c]`. The online update remains `normalizer = fma(normalizer, alpha, sum)`.

` scores` is scalar staging, not a `joint_matrix_load` operand. The actual load operands are BF16 `qtile` (A) and `kv` (B) for QK, then BF16 `probability` (A) and `kv` (B) for PV. Thus do not change probability layout or stride as part of this question. The matrix accumulator callback stores scores through scalar SLM indexing; it does not call `joint_matrix_store` on `scores`. The BMG G21 restrictions in Intel's matrix extension apply to matrix loads/stores, not this score accessor. For current BF16 operands, the visible strides are 256, 32 and 256 elements (512, 64 and 512 bytes); each satisfies the documented 8-byte stride multiple and current pointers/offsets are 4-byte aligned. Keep all Q/K/V/P as BF16, matrix accumulators and online max/sum/output state FP32, and all current score, max, sum, probability-rounding, and recurrent-update order.

This is narrower than R568's 8-head/CH64 split, which changes work-group geometry, duplicated KV staging and Q scaling, and narrower than R945/R947's adjacent-query union / N64 staging hypotheses. It tests only the in-work-group FP32 score address map. R939/941 review metadata adds no evidence about score SLM. R568 and R947 both say there is no local score-tile measurement or adoption result; their CUDA or Arc-unmeasured claims do not establish a bank model.

## Legal mappings and predicted tradeoffs

**Control: pitch 32.** Keep current `scores[(head+r)*32 + cell+c]` and `scores[tid*32+c]`, 2,048 bytes. It is compact and contiguous over each head's 32 cells. Under the common simple word-interleaved bank model, however, the 16 active scalar lanes reading the same `c` touch word indices `32*head+c`; all have the same residue modulo either 16 or 32 banks. That is a conditional prediction, not a B570 finding.

**First candidate: pitch 33.** Allocate `16*33` floats, write `scores[(head+r)*33 + cell+c]`, and read `scores[tid*33+c]`. The extra element in each row is padding and is never read. Every logical score still has one producer and the same consumer. At each scalar-loop iteration, addresses become `33*head+c`; modulo-16 or modulo-32 word interleaving maps these 16 lanes to distinct banks. This costs only 64 bytes per work-group versus baseline (2,112 score bytes total), has no extra arithmetic in the addressing expressions, and is a clean low-risk hypothesis. It preserves the head-major contiguous 32-cell producer/consumer ordering.

**Alternative: cell-major/head-minor.** Allocate 2,048 floats and map writes to `scores[(cell+c)*16 + head+r]`, reads to `scores[c*16+tid]`. The 16 active head lanes then read adjacent words for each fixed c, which is coalesced under ordinary lane-address reasoning and naturally spreads banks. The indexed callback guarantees each logical matrix coordinate can be addressed, and the map is bijective over all 16×32 scores, so it is functionally legal. It may make callback stores strided depending on the implementation's register-to-lane mapping; that mapping is not specified by the API. Treat as a comparison alternative, not a predicted win.

**Alternative: XOR within the 16-cell half-tile.** Use `scores[head*32 + (cell+c ^ head)]` on callback stores and `scores[tid*32 + (c ^ tid)]` on both scalar passes, with parentheses exactly `(cell+c) ^ head`. For every fixed head the XOR permutes all 32 cells bijectively; because head is 0..15, it stays inside each current 16-cell matrix tile. It has no SLM-byte increase and, under simple 16/32-bank word-interleave, gives the scalar lanes distinct low bank bits. It adds XOR/index instructions on callback writes and twice on scalar reads, so pitch 33 is the better first trial. Do not mix swizzle with changed lane ownership or reduction parallelization in the same experiment.

SYCL `local_accessor` defines a per-work-group local array indexed by elements and exposes its start pointer; it does not promise a physical bank map. Intel's indexed `joint_matrix_apply` contract invokes the callable per element with row/column coordinates; it does not promise which lane owns each callback or which order callback stores issue. All three maps above are bounds-safe and unique if both producer and scalar consumers use the same formula. Keep the four matrix apply calls converged and preserve the barriers around score production/consumption.

## What Intel evidence does and does not establish

Intel's current [oneAPI GPU Optimization Guide 2025.2, Shared Local Memory](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2025-2/shared-local-memory.html) says SLM banks are device-dependent and gives, “at the time of writing,” 16 banks at 4-byte granularity for 64 consecutive bytes. It demonstrates same-bank serialization and recommends access patterns that avoid conflicts. It does not name B570/Xe2 or publish its bank-address hash. Intel's [Arc B570 specifications](https://www.intel.com/content/www/us/en/products/sku/241676/intel-arc-b570-graphics/specifications.html) identify Xe2/Battlemage, but do not describe SLM bank geometry. The old [Intel OpenCL graphics memory guide](https://www.intel.com/content/www/us/en/docs/opencl-sdk/developer-guide-processor-graphics/2019-4/memory-hierarchy.html) explicitly scopes its 16×4-byte description to Gen7.5. Intel's [Gen12LP SLM technical walkthrough](https://www.intel.com/content/www/us/en/developer/articles/technical/iso3dfd-code-walkthrough.html) says Gen12LP improved banking relative to Gen9. These primary Intel sources are counterevidence to carrying one fixed Gen9-era or CUDA 32×4 rule forward to Xe2. I found no public Intel source establishing B570's exact bank width/count/hash; therefore the modular bank arithmetic above is only a test hypothesis.

The [Intel 2025.2 joint-matrix guide](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2025-2/programming-intel-xmx-using-sycl-joint-matrix.html) describes the coordinate callback and subgroup-collective operations. The matching Intel LLVM matrix specification at immutable tag [`nightly-2026-09-27`](https://github.com/intel/llvm/blob/nightly-2026-09-27/sycl/doc/extensions/experimental/sycl_ext_matrix/sycl_ext_oneapi_matrix.asciidoc) lists BMG G21 BF16 A/B to FP32 accumulator combinations including 8×16×16, and requires matrix load/store stride in bytes to be an 8-byte multiple, with 4-byte aligned base pointers. That validates the *shape/operand* context, not the local score layout or generated code. Intel's [SYCL local-accessor specification](https://registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html) defines element indexing and per-work-group storage, not cache-bank placement.

Intel's [2025.2 occupancy guide](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2025-2/thread-mapping-and-gpu-occupancy.html) warns that local allocations can be rounded, affecting resident work-groups, and discusses register pressure/occupancy tradeoffs. Its explicit rounding buckets are for Data Center GPU Max 1550, not B570, so they cannot be applied numerically here. Current declared local payload is 28,160 bytes, including 2,048 score bytes; pitch 33 raises it to 28,224. The source admission guard adds a 4,096-byte margin, so its nominal threshold would need to account for the extra 64 bytes. No B570 local allocation rounding, compiler register count/spills, occupancy, or score-SLM counter is available in this evidence. Since pitch 33 adds only 64 logical bytes, it is unlikely to change a coarse resource bucket in most cases, but that remains unknown and even a small allocation delta can cross a bucket boundary.

## One bounded experiment and decision rule

If Main elects to measure this question, compile one immutable source/binary per layout and compare only pitch32 control against pitch33 on the existing same-input 8,192-query / 32K-cell component cohort. Reuse the exact Q/K/V tensors, IDs, page map, query order, queue, launch geometry, and all chunk/precision settings; do not change the separately running 128-thread probability computation. Use independent owned processes or a compile-time parameter, never runtime environment switching after SYCL initialization. Randomize arm order and take five clean process samples per arm after one warm-up; report each sample, median, and attention-kernel event interval separately from wrapper/QSA/pack envelopes. Collect the same output fingerprints and the established attention/oracle correctness result. A storage-only candidate should preserve exact FP32 score/online arithmetic and BF16 outputs; a difference is a correctness/compiler investigation, not permission to relax the gate.

A pitch33 improvement with matching outputs would justify one follow-up asking whether the observed gain is repeatable and whether it survives the official long-prefill boundary. No gain or a regression would reject pitch33 for this kernel; then retain pitch32 and consider cell-major only if compiler output or a B570-relevant SLM counter gives a concrete reason. Neither outcome alone proves unit saturation or production benefit. Existing measurements are not attribution evidence: the cited same-binary official profile has a wrapper interval of 89.2009 s and attention+prefixpack 21.5123 s (nonexclusive), with no PMU, physical VRAM/PCIe, XMX or SLM bank-counter result. Coalesced-global-K was 16.33% slower on the same 8,192-query / 32K-cell cohort despite matching fingerprints/oracle, so a cleaner-looking memory map is not sufficient grounds to expect a win.
