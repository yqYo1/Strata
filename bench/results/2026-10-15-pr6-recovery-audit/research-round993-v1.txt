The genuinely narrower question here is how those options behave at the *current* `run_moe_window` boundary: the helper uses one decoded scratch pair, decodes when the sorted job's expert changes, and feeds native `f16_out16` calls. A reuse cache can add hits only across separate window calls; it cannot eliminate the one decode already shared by the jobs grouped in a single window.

The helper accepts one or two 8,192-row pieces (`rows > T` through `2*T`) and processes jobs with routed `job.rows` up to its 8,192-row gathered buffer. For a new expert it decodes the entire GU and Down matrices into `m.dq_gu[0]` and `m.dq_d[0]`; then it gathers rows, runs GU GEMM, SwiGLU, and Down GEMM. `f16_out16(..., output_bf16=true)` uses FP16 inputs/weights, FP32 accumulation/beta epilogue, and BF16 output; the actual backend is selected by build/runtime configuration (R977's inspected profile used `vllm`). The `loaded` value is local to this call, so a later window starts cold. This source description does not depend on the unavailable current command-service model result.

For N=2560 and FF=640, the expanded pair is 4,915,200 FP16 values = **9,830,400 bytes (9.375 MiB)**. From the observed GGUF pair types and block layouts in R977, packed GU+Down spans about **1.51–2.66 MB per expert pair** (format-dependent); this is logical input payload, not measured device traffic. The current IQ decoder is not ordinary linear INT4: IQ3 uses indexed codebook vectors with sign bits and block/subblock scale fields; IQ4_NL maps each nibble through a 16-value nonlinear table; IQ4_XS reuses that table but assembles a signed 6-bit scale per 32-value subgroup. A tile decoder must preserve the exact index planes, sign/nibble order, scales, row offsets, and `f16_from_f32` rounding. Using integer dot products or rounding directly to BF16 would be a different arithmetic path.

## Architecture comparison

Let `E=9,830,400` bytes be the full expanded pair, `P` the actual packed bytes for the format pair, `r` the number of separate window uses for one layer/expert, and `Mt` the fused kernel's output rows per live weight tile. Logical traffic below separates unique payload from actual cache/DRAM traffic, which is not known.

| Path | Per-expert work and reuse | Favorable shape/reuse regime | Workspace, numerical, and failure limits |
|---|---|---|---|
| **A. Current whole-expert decode → FP16 native GEMMs** | Reads/decodes packed GU+Down once on a miss/new expert in a window, writes E bytes of FP16 pair, then the XMX GEMM consumes dense tiles for the expert's rows. Within-window row reuse is available without repeating dequant. Across r windows, the decode and E-byte scratch write recur r times; each GEMM still consumes the weights. | Medium/large M can amortize IQ unpack and nonlinear table/scale handling over many rows, while preserving a tuned dense XMX producer/consumer boundary. It avoids a custom matrix kernel and uses the existing exact decoder. | Needs one live decoded pair (E bytes) per sequential slot; current window reuses `dq_*[0]`. The FP16 matrix write and later dense weight loads cost traffic, but neither their physical traffic nor their time is measured. Dense GEMM still tiles K/N and may reload from cache at multiple M tiles. |
| **B. Tile-local fused IQ decode + XMX matrix tile** | Load the packed block(s), reconstruct IQ codes/scales/signs, round each weight to the current FP16 value, and feed the current XMX fragment without writing the full E-byte matrix. With M≤Mt, each weight tile can serve all rows of that expert in one row tile. Without retaining a tile across row tiles, packed reads and IQ decode work can repeat about `ceil(M/Mt)` times; K/N tiling and codebook fetch pattern add more detail. | Small per-expert M that fits one XMX M tile, especially when one-call dequant scratch traffic is poorly amortized. It can remove the full decoded-matrix write and subsequent expanded-weight scratch read for that invocation. | Requires type-specialized IQ unpack/table/scale logic plus tile layout conversion, and more registers/local storage/coordination with DPAS. If the useful rows are padded to an XMX M tile, padding cost matters; for M≫Mt repeated decoding can cost more than expansion. Must retain current FP16 weight bits and FP32 accum/BF16 output; changed product accumulation order remains a numerical gate. No B570 support or speed is proven by another GPU's joint-matrix kernel. |
| **C. Bounded cache of full FP16 pairs for selected experts** | On the first use in its cache lifetime, pay the same packed read/decode and E-byte fill as A; on later window hits skip that decode and fill but keep the GEMM's dense weight reads. Best-case logical saving relative to A over r hits is `(r−1)×(P read + decode + E-byte write)`; it does **not** save the dense GEMM read or MACs. | An expert reappearing in separate windows before eviction, where exact ordered reuse exceeds capacity. Compared with B, cache avoids repeated table decoding across calls and allows the native dense XMX GEMM to consume the matrix for large M too. | Each resident expert costs E bytes: 8 entries = 78.6 MB/75 MiB; 16 = 157.3 MB/150 MiB; 32 = 314.6 MB/300 MiB, before allocator and other live state. Current raw staging uses eight compressed slots (largest single pair 2.66 MB); a decoded cache is a substantially larger separate allocation. A no-hit or one-use expert only adds fill and residency pressure. Cache key/lifetime must be layer+expert+format/source generation and eviction must wait for every GEMM reader. |

A first-order crossover is therefore conditional, not one universal M threshold. B has its cleanest case when one packed weight tile serves the expert's whole small-M piece; its decoder starts repeating after M exceeds the tile's live M. A avoids that custom IQ work and becomes more plausible as M grows, provided the dense XMX path can reuse its matrix tiles efficiently. C is useful only for recurrence *between calls/windows* and retains the exact dense contract; it is weaker than a fused tile for a one-off expert because it does not remove the expansion fill, and weaker than A if it sees no hit. The correct selector needs exact per-type `job.rows`, tile dimensions, and per-layer/expert/window order. The old M≤15 call percentage alone cannot decide.

For IQ-specific work, IQ4_NL's 16-byte codebook lookup is structurally simpler than IQ3's indexed multi-byte vector/sign reconstruction; IQ4_XS adds subgroup scale assembly. A shared “INT4 unpack” shortcut is wrong for both arithmetic and scale meaning. IQ codebook bytes may be reused from constant/cache storage, but random lookup efficiency, gather lowering, and subgroup broadcast cost depend on the actual compiler/device. The current FP16 conversion is part of the data path: cache entries must retain those exact half bits, and a fused kernel must round to those bits before the same FP32 local dot accumulation and BF16 store.

## Primary implementations and transfer limits

- **llama.cpp SYCL XMX gather, pinned source/doc:** `ggml-org/llama.cpp` commit `a0e6dc7384edb8f5d927155e1d26c10b4a310e6d`, [SYCL backend guide](https://github.com/ggml-org/llama.cpp/blob/a0e6dc7384edb8f5d927155e1d26c10b4a310e6d/docs/backend/SYCL.md), [implementation dispatch](https://github.com/ggml-org/llama.cpp/blob/a0e6dc7384edb8f5d927155e1d26c10b4a310e6d/ggml/src/ggml-sycl/ggml-sycl.cpp), license checked at the same commit (MIT). This is the closest architecture precedent: documented IQ4_NL/IQ3_S/IQ4_XS and other IQ gather paths decode eligible GGUF weights into XMX tiles, with type/shape masks and standalone GEMM/dequant fallback. Its documented gates include >64 tokens per expert or unsuitable row lengths falling back; this confirms mixed-M specialization and fallback matter, not that 64 transfers to Strata. Its reported B60/Qwen prompt gain is not evidence for Strata B570. The exact matrix type, packing, M partition, output rounding, current vLLM backend and compiler/device support must be checked before implementation.
- **Marlin:** official author implementation at commit `1f25790bdd49fba53106164a24666dade68d7c90`, [repository README/kernel](https://github.com/IST-DASLab/marlin/tree/1f25790bdd49fba53106164a24666dade68d7c90), Apache-2.0 checked in repository. The first-party description stages/reorders regular GPTQ/AWQ INT4 and group scales offline, asynchronously loads/pipelines them, and dequantizes directly into tensor-core organization. That supports tile-local operand staging and overlap as concepts. It is CUDA/NVIDIA-specific, uses preprocessed linear INT4 and different group scales/zero points, and targets medium-batch weight-only GEMM; none of its format decoder or tile assumptions carry over to GGUF IQ or Xe2.
- **vLLM Machete/CUTLASS W4A16:** vLLM commit `fbc9ba6d303b97d38a3f8b420a90de161b709aff`; [Machete kernel files](https://github.com/vllm-project/vllm/tree/fbc9ba6d303b97d38a3f8b420a90de161b709aff/csrc/libtorch_stable/quantization/machete) and [selection tests](https://github.com/vllm-project/vllm/blob/fbc9ba6d303b97d38a3f8b420a90de161b709aff/tests/quantization/test_cutlass_w4a16.py); vLLM Apache-2.0. The tests explicitly gate Machete to Hopper (SM90) and exercise packed uint4/uint4b8 group-size-128/channelwise cases. This is useful as a licensed CUTLASS W4A16 tile design reference, but its gate itself is counterevidence to porting kernel schedules or expected speed to B570, and its linear quantization is not IQ table decoding.
- **SGLang grouped MoE:** source page pinned to `sgl-project/sglang` `20621aa14bda7726a8a968f326198eac61717fef`, [Triton MoE kernel](https://github.com/sgl-project/sglang/blob/20621aa14bda7726a8a968f326198eac61717fef/python/sglang/kernels/ops/moe/fused_moe_triton_kernels.py), [expert parallelism flow](https://github.com/sgl-project/sglang/blob/20621aa14bda7726a8a968f326198eac61717fef/docs/docs/advanced_features/expert_parallelism.mdx); Apache-2.0 checked in repository. It carries sorted token IDs, expert IDs, M-block padding and WNA16 INT4 tile support; grouped routing is an execution reference, not support for GGUF IQ codebooks or this output rounding. In the Xe2 path, SGLang's separate MXFP4 grouped-GEMM supports OCP E2M1 plus one scale per 32 values; its [XPU docs](https://github.com/sgl-project/sglang/blob/20621aa14bda7726a8a968f326198eac61717fef/docs/docs/hardware-platforms/xpu.mdx) describe staying packed end-to-end. That is useful evidence for an Intel packed-weight architecture class but **not** exact IQ3/IQ4 equivalence: E2M1 is a regular numeric encoding, unlike IQ codebook indices/signs.
- **First-party technical posts:** Intel engineers' [Run LLMs on Intel GPUs Using llama.cpp](https://www.intel.com/content/www/us/en/developer/articles/technical/run-llms-on-gpus-using-llama-cpp.html) (read 2026-10-17) documents their SYCL/oneMKL path; it is useful historical backend context, but predates this B570 path and does not describe IQ XMX fusion. Marlin's first-party [technique summary](https://github.com/IST-DASLab/marlin/tree/1f25790bdd49fba53106164a24666dade68d7c90) (same pin/license) emphasizes simultaneous use of cache, staged loads, compute, and direct tensor-core operand layout; it is a developer write-up, not a Xe2 measurement. Intel's official [SYCL joint-matrix optimization guide](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2024-1/joint-matrix.html) says to block i/j/k for cache locality and feed the matrix unit, but its example's supported combinations are device-specific and explicitly assumes XMX. These are ideas to test in Strata, not source to transplant.

Treat that as toolchain provenance only, not a design/source basis or product measurement.
