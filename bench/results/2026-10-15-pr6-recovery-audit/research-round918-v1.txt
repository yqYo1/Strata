# Read-only GPU traffic telemetry without OA event queries

**Classification:** knowledge collection  
**Scope:** compare Level Zero Sysman PCI and memory snapshots, Linux Xe kernel interfaces, and public Intel monitoring tools for observing PCIe and device-memory traffic.  
**Evidence boundary:** source and documentation review only; no native query, device support test, build, profiler, or tool execution. This report does not establish that any counter works on the Arc B570 in this host.

## What the APIs can observe

Level Zero Sysman exposes snapshot APIs outside the OA metric-query/pool path. The installed Level Zero package is loader 1.32.0, whose official release identifies its headers as spec v1.17.24; the local `zes_api.h` likewise identifies `v1.17-r1.17.24`. Sysman initialization is `zesInit(0)` and must precede Sysman calls. A read-only capability pass would enumerate Sysman devices, match `zesDevicePciGetProperties().address` to the GPU BDF, then query properties/state/stats. PCI traffic is `zesDevicePciGetStats(zes_device_handle_t, zes_pci_stats_t*)`; capability fields are `zes_pci_properties_t.haveBandwidthCounters`, `.havePacketCounters`, and `.haveReplayCounters`. Memory handles come from `zesDeviceEnumMemoryModules`; `zesMemoryGetProperties` reports memory location (`ZES_MEM_LOC_DEVICE` or `ZES_MEM_LOC_SYSTEM`) and subdevice identity, while `zesMemoryGetBandwidth(zes_mem_handle_t, zes_mem_bandwidth_t*)` returns per-handle counters. These are snapshots, not event queries or per-kernel traces. [Level Zero v1.32.0 release](https://github.com/oneapi-src/level-zero/releases/tag/v1.32.0), [Sysman API spec](https://oneapi-src.github.io/level-zero-spec/level-zero/1.16.24/sysman/api.html), [Device API](https://oneapi-src.github.io/level-zero-spec/level-zero/1.19.12/sysman/api/apis/device-2.html), [Memory API](https://oneapi-src.github.io/level-zero-spec/level-zero/1.19.12/sysman/api/apis/memory.html).

The distinction between properties, state, and traffic matters. `zesDevicePciGetProperties` gives the BDF, the fastest port configuration supported by the GPU, and whether PCI RX/TX, packet, and replay counters are valid. `zesDevicePciGetState` reports current link speed/width and status. `zes_pci_stats_t.speed` is the current link configuration; it is not the device's maximum configuration and neither value is attained payload bandwidth. The stats contain RX/TX byte counters summed across lanes, packet and replay counters, and a per-snapshot microsecond timestamp. TX counts include replay bytes. API-defined throughput is derived from two snapshots: `1e6 * (delta_rx + delta_tx) / (current_max_bandwidth * delta_timestamp_us)`. Preserve RX and TX rates separately first: a combined ratio uses a link-capacity denominator, can obscure full-duplex direction headroom, and is not a measure of useful application bytes. RX/TX are direction labels at the GPU endpoint; the mapping expected for host-to-device and device-to-host should be checked against a controlled copy before using that shorthand in a report.

Sysman PCI bytes are endpoint/link-wide. They include every client and every transfer that crosses that GPU link in the interval; the API has no process, queue, kernel, allocation, or copy-command attribution. A host root-port/system PMU counter, where available, is broader still: it can include other devices sharing that root complex. A GPU-local memory counter is a different quantity from PCIe bytes. It describes traffic to/from a memory handle (device-local or system memory as identified by properties), not traffic across the host link, requested copy payload, cache-line requests from one kernel, or per-process VRAM traffic. For multi-module or multi-tile devices, report the handle and subdevice fields; do not sum parent and child observations until their scopes are known to be disjoint.

## Counter windows, wrap, and failure meanings

Both PCI and memory timestamps are only valid for differences between snapshots of the same structure/API clock. The spec warns against subtracting timestamps from different structures or assuming their absolute origin matches another run. Keep a host monotonic timestamp immediately before/after each call to bound when it happened, but calculate byte rates from the corresponding API timestamps. Do not splice Sysman timestamps into a GPU event timeline or compare them numerically to host time.

The PCI spec calls RX/TX counters monotonic but does not define a rollover/reset algorithm in the struct contract. Treat a falling counter, non-increasing timestamp, device reset/rebind, or API error as a discontinuity and begin a new baseline; do not invent a modulo width. `haveBandwidthCounters == false` means the RX/TX fields are not valid (spec says they read as zero), not “the link was idle.” Separately, `ZE_RESULT_ERROR_UNSUPPORTED_FEATURE`, `ZE_RESULT_ERROR_DEPENDENCY_UNAVAILABLE`, `ZE_RESULT_ERROR_NOT_AVAILABLE`, `ZE_RESULT_ERROR_INSUFFICIENT_PERMISSIONS`, `ZE_RESULT_ERROR_DEVICE_REQUIRES_RESET`, and `ZE_RESULT_ERROR_DEVICE_IN_LOW_POWER_STATE` distinguish support, backend, temporary state, and access failures. `ZE_RESULT_ERROR_INVALID_ARGUMENT`/null-handle/null-pointer are call construction errors; they are not evidence that a hardware counter is unavailable. Preserve the exact result and capability flags.

The memory struct is more awkward. `zes_mem_bandwidth_t` reports `readCounter`, `writeCounter`, `maxBandwidth`, and `timestamp`; the published field descriptions call the read/write values total bytes. The same spec text says the counter is a 32-byte transaction count, wraps at `2^32`, and its delta must be multiplied by 32 to obtain bytes. That yields 128 GiB per 32-bit counter wrap. The prescribed one-wrap correction is ambiguous if more than one wrap can occur between snapshots. The local v1.17.24 header also contains the experimental `zes_mem_bandwidth_counter_bits_exp_properties_t` (`validBitsCount`) extension, while the older `zes_mem_ext_bandwidth_t` is explicitly deprecated. Therefore record raw values, API version, extension/valid-bit result, memory handle properties, timestamps, and error codes; do not apply a guessed multiplier or assume a one-second sample is unambiguous. Select a sample interval short enough for the observed bandwidth and valid counter width to permit at most one wrap, then verify the conversion on a driver that reports the capability. `zesMemoryGetBandwidth` has the same meaningful support/access/device-state error families as PCI stats, but there is no PCI-style `haveBandwidthCounters` boolean: successful memory-module enumeration alone does not prove that bandwidth sampling works.

A zero returned after success only means no counter increase over that sampled interval if the relevant capability and conversion are valid. `N/A`, `NOT_AVAILABLE`, `UNSUPPORTED_FEATURE`, permission errors, or PCI capability false must stay distinct from a measured zero. The stopped OA experiment is a separate path: its pool-create `INVALID_ARGUMENT` and later Metrics Library `EACCES`/fixed-GUID-not-found results do not demonstrate Sysman PCI or memory availability, and this report does not retry or reinterpret that experiment.

## What Linux Xe and Intel's tools add

The upstream Xe documentation does not describe a generic sysfs PCIe-byte or VRAM-bandwidth counter comparable to Sysman. Standard PCI sysfs link metadata can show negotiated/current and maximum speed/width, but it is configuration/topology, not observed traffic. Xe sysfs also exposes frequencies and link downgrade state, which can explain a speed change without measuring utilization. Xe's DRM `fdinfo` output is per DRM client: engine busy/cycle statistics plus allocated/shared/resident memory by region. It can identify which client is active or has memory allocated, but does not report the client's bytes transferred over PCIe or memory buses. [PCI sysfs documentation](https://docs.kernel.org/PCI/sysfs-pci.html), [Xe frequency sysfs](https://docs.kernel.org/gpu/xe/xe_gt_freq.html), [Xe DRM client usage stats](https://docs.kernel.org/gpu/xe/xe-drm-usage-stats.html), [DRM usage-stat specification](https://docs.kernel.org/next/gpu/drm-usage-stats.html).

A useful adjacent Xe interface exists in current upstream kernel documentation: `/sys/kernel/debug/dri/<device>/gt<id>/stats`, if the running kernel includes it and was built with `CONFIG_DEBUG_FS=y`. It has cumulative per-GT SVM/page-fault bookkeeping, including page sizes moved CPU-to-device, `SVM_DEVICE_COPY_KB` / `SVM_CPU_COPY_KB`, and copy time. Those counters are aggregated across CPUs and accrue from driver load or an explicit reset. They can help distinguish Xe SVM fault/migration activity from a link-wide rate, but they are not general host-to-device command bytes, not full VRAM controller bandwidth, and not per-process or per-kernel. The interface documents a write-to-reset operation and warns that resetting while active can produce unpredictable intermediate values; a later read-only study should take before/after snapshots and must not reset counters during a workload. The `next` kernel documentation is not proof that the host's installed kernel has this interface. [Xe GT statistics](https://docs.kernel.org/next/gpu/xe/xe_gt_stats.html).

Intel XPU-SMI / XPU Manager illustrates how the Sysman counters are consumed publicly. XPU-SMI 2.0 documents `MEMORY` fields for total/used/free, read/write bandwidth and utilization, and `PCI` fields for maximum/current link generation and width, TX/RX throughput, and replay counts. Its `--loop-ms`/`--loop` options control how often userspace asks for another sample; that cadence is not a guarantee about hardware counter update granularity. The XPUM OpenTelemetry receiver describes GPU IO and memory IO as cumulative read/transmit and write/receive metrics, with rates and BDF/subdevice/memory-location attributes. It is device/component telemetry, not application attribution. The documented target is Intel Data Center and Arc Pro products, not the consumer B570. XPUM itself says availability varies with hardware, firmware, kernel, user-space driver and privileges; its daemon guide states that memory and PCIe bandwidth metrics may require root in its documented deployment. These facts establish a public implementation path and known gating classes, not B570 support or permission advice. [XPU-SMI 2.0 field reference](https://intel.github.io/xpumanager/2.0/xpu-smi/overview.html), [XPUM Sysman metric definitions](https://github.com/intel/xpumanager/blob/main/xpumd/receiver/intelxpu/sysman/documentation.md), [XPUM metric prerequisites](https://github.com/intel/xpumanager/blob/main/xpumd/README.md).

## Application and measurement implications

The same interpretation transfers to non-LLM heterogeneous workloads. For example, high-order stencil codes using CUDA-aware MPI pipeline packing, halo exchange, and unpacking on separate streams; a link-wide RX/TX sample can check whether the full communication phase moves substantial data, while per-call timing and message accounting are still needed to attribute traffic to one halo exchange. The published study is on a non-LLM HPC application and explicitly pipelines those stages; it supports the workload example, not Intel counter behavior. Similar boundaries apply to GPU image ingest, sparse solver migration, and storage-to-GPU staging. [High-order stencil / CUDA-aware MPI study](https://www.sciencedirect.com/science/article/pii/S0167819122000102).

For a future safe prefill observation, first pin the BDF and complete endpoint-to-root topology. The existing hierarchy snapshot reports 2.5 GT/s x1 at GPU `05:00.0` and `04:01.0`, but 16 GT/s x4 on upstream `03:00.0`, `02:02.0`, `01:00.0`, and `00:01.2`; this conflict remains topology-only, not measured utilization or a usable payload ceiling. Prior same-binary 320 MiB ordinary-RAM-to-device-USM copy proxies were about 4.35 GB/s H2D and 3.89 GB/s D2H with the external sampler disabled; older samples were about 6.02/5.54 GB/s, with cause unresolved. Requested copy bytes in a model trace are not wire bytes, and the prior 77.31% compute / 9.11% copy numbers describe only an attention envelope, not whole prefill. These results motivate a separate aggregate traffic source but do not establish it will explain the drift or bottleneck.

If a future read-only capability pass succeeds under existing access, use an owned external observer or existing XPU-SMI process, matched to the device by BDF. Capture PCI and each unambiguously scoped memory handle at a fixed, low-overhead cadence short enough to remain within the resolved memory-counter wrap bound, around one exact prefill boundary. Store raw snapshots, API timestamps, host call brackets, errors/capability flags, user-space driver/runtime/kernel versions, and the observer's polling configuration. Do not run OA event-query collection; do not change permissions, runtime configuration, or device state. Keep these diagnostic samples separate from clean speed samples, and use an observer-off/observer-on matched control to quantify observer cost. Attribute only to the GPU/device or link interval, not the active model/kernel. For exact allocation or kernel attribution, pair with command-level timing and source-proved requested bytes; neither Sysman nor Xe aggregate stats provide that join.

If PCI Sysman counters are unsupported or blocked, the remaining uncertainty is actual GPU endpoint PCIe traffic during the workload. Link metadata and copy-only service-rate proxies do not measure that traffic; a separately supported endpoint/root-port traffic source would be needed. If memory bandwidth is unavailable, GPU-local memory pressure remains unresolved; fdinfo memory usage and SVM migration bytes are not substitutes. Continue to preserve the resource distinctions in [RESOURCE_PROFILING.md](../../../docs/RESOURCE_PROFILING.md).
