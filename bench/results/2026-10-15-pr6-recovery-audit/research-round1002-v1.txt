## Finding

The proposed algorithm is mathematically feasible without an `[n*K,N]` routeDown plane: run the unchanged causal attention/PLE and router-input formation for ordered chunks, preserve each row's BF16 mixed input and unique top-10 IDs/FP32 weights, run each expert once in deterministic expert-ID order in jobs of at most 8,192 rows, and scatter each weighted BF16 expert result into one FP32 `[n,N]` accumulator initialized from the shared expert result. After the expert sweep, recompute or perform the HC injection and write HC output to the original BF16 residual rows. This replaces per-route output storage with a token output accumulator; each route is consumed exactly once. It is a distinct architecture from R621/R622 full-prefix deferral, R633 2/4-chunk waves, and the already implemented 2-piece MoE window: those reports do not answer the proposed FP32 accumulator layout. The full-`n` version is **not admissible in the current measured placement**: its new planes alone require 1,205,022,720 bytes (1.122 GiB) at 78,452 rows, exceeding the diagnostic's 512 MiB headroom by 668,151,808 bytes, before additional live staging or allocator guards. The fixed 262,144 physical-context case requires 4,026,531,840 bytes (3.750 GiB) for the two planes alone, 3,489,660,928 bytes above that same headroom. Do not count releasing the target decode cache: its owner, graph/address contract and preserved state have not been reconstructed for this alternate request lifetime.

## Source-derived live set and capacity

Pinned source explains why this schedule differs from current execution. `src/prefill/prefill.cpp` allocates `m.region` to the maximum of GDN, QSA and MoE scratch; its standard MoE includes `T*K*N` FP32 `m.Dm` (or BF16 through the native16 view). `src/prefill/moe_window.inc` is the existing 16K-window specialization and carves a 998,443,520-byte `m.region` with a BF16 `[16,384*10,2,560]` `down` plane (838,860,800 B payload), bounded expert job gather (8,192 rows), GU and hidden buffers. It routes and combines one/two chunks, not all prompt rows. `m.emb` is only the chunk-sized FP32 reservation; aliasing it to BF16 mixed does not enlarge its backing span. The candidate need not keep all-token shared outputs or HC injection: initialize the FP32 accumulator from each shared result and scalar gate as it is computed, then compute/inject the HC projection at final per-chunk write while the old residual remains in the BF16 bank. This saves those two global planes but still requires mixed + accumulator together. IDs, weights, source rows and slot maps add a few to tens of MiB, plus each expert's <=8,192-row gather/GU/hidden/output tiles and QSA/KV/QSA-prefix/PLE/live workspaces. The concrete candidate thus has a hard lower-bound payload of 1,205,022,720 B at 78,452, and 4,026,531,840 B at 262,144, not counting these additional objects. Existing `m.region` and chunk `m.emb` cannot be presumed free: `m.region` is live for the current max-sized QSA/MoE workspace and `m.emb` is chunk-owned, with launch readers and transfer lifetime. Even treating their full recorded payloads as reusable does not establish a fit; the full-prefix planes exceed the stated 512 MiB slack. A correct admission sheet must name every carve, guard, bank, QSA BF16 prefix, resident KV, decode/MTP object, routing plane and concurrent callback owner, and show addresses/live intervals. Do not merely compare the candidate planes to total VRAM or use unused cache as implicit scratch.

## Placement alternatives

- **Stay at the current 16K/two-piece window:** Already has an exact-size arena and routeDown space, but expert dequant repeats across windows. A no-routeDown window can instead use BF16 `[W,N]` mixed plus FP32 `[W,N]` accumulator, with shared scalar initialization and final HC write in the same bounded window; it may free routeDown bytes but does not deduplicate an expert across the request. This fits only if the source allocator proves overlap against actual dead intervals and all existing QSA/live objects. The present diagnostic says its existing 2-piece window fits; it does not certify this alternate layout.
- **Larger bounded windows (e.g. 32K):** Same asymptotic expert reuse opportunity within the window, with mixed+accum bytes `6*W*N` = 503,316,480 B (0.469 GiB), versus current BF16 routeDown payload `2*W*K*N` = 1,677,721,600 B (1.563 GiB), before routing/shared/job scratch. Can reduce expert visits only when an expert recurs across that window. It is not all-input once-per-expert, and available VRAM remains unproven until a complete live-set carve is calculated. Larger jobs may also change oneMKL GEMM shapes and rounding.
- **All `n=78,452` once per expert:** Avoids 7.482 GiB naive FP32 routeDown, but needs 1.122 GiB for mixed plus accumulator and cannot be placed in current `m.region`/chunk `m.emb`/512 MiB spare as reported. Paging either plane through host RAM needs re-transfer/update across experts; CPU reduction or PCIe traffic cannot be presumed cheaper or compatible with GPU-local math policy. This is a concrete placement blocker unless a reviewed live-range redesign or separately qualified memory source is established.
- **Physical `n=262,144`:** The 3.75 GiB pair-only payload exceeds current slack by 3.25 GiB; complete route tables and other live workspaces add more. No physical-context admission follows from a smaller prompt fitting.

## Numerical, ordering and lifetime contract

Current native16 `combine` is not an arbitrary scatter sum: for each token/column it starts `float v=0`, loops `k=0..9` in that token's original top-k slot order, performs `sycl::fma(weight, BF16_load(down), v)`, then adds `BF16(shared)*sigmoid(FP32 gate)` and BF16-stores `bo`. The subsequent HC write applies the FP32 gate/normalization arithmetic and stores the residual to BF16. A deterministic expert-ID-major in-place FP32 accumulator changes the addition sequence from per-token route-slot order to expert-ID order; one-FP32 accumulation avoids the existing BF16 rounding at every expert output but is not numerically identical by construction. Router routes are unique per token: source route planner rejects duplicates, bounds all 512 IDs, and requires total route mass `rows*K`; preserving the slot map is necessary if exact per-token slot arithmetic is the chosen contract. Same-queue ordering in the existing worker establishes upload/read/write sequence, but the proposed gather, expert scatter, shared initialization and final write must all use the same ordered queue or explicit dependencies.

The existing window has important outer contracts: its context is borrowed through a checked layer-major lease; it keeps immutable route/upload owners alive through checked synchronization; stop checks occur between expert jobs; failed drains return false without releasing owners; and only after the final checked drain does it clear route owners and call `complete_piece` for each original chunk. A full-prefix rewrite must preserve cancellation checks, ownership through every async read, checked lease retirement, callback boundaries, MTP arena reuse only after both bank writes, and “completion” only after final write/drain. Breaking work into 8,192-row jobs bounds transient output, but not the full mixed/accumulator lifetime.

The current public SGLang Qwen3.x MoE model source shows router logits -> top-k -> expert dispatch/combine but is not an immutable, verified Qwen3.8-Flash-Next branch matching this GGUF, and current online source is a moving `main` snapshot. The pinned Strata source explicitly uses BF16 routed activations/outputs, FP32 router weights/gates and FP32 per-route accumulation for native16. It does not establish that a changed expert-major summation order or FP32 accumulator matches actual vLLM/SGLang task quality for the exact model branch. Therefore the revised numerical criterion is a model-path comparison, not rejection just because it differs from an FP32 diagnostic oracle: obtain/pin the exact vLLM or SGLang model implementation and precision/rounding path first; then compare router IDs/weights, per-expert BF16 outputs, combine and final HC residual against it. Keep FP32/ggml references diagnostic. No quality conclusion is possible from this source-only review.

## Smallest useful Main-owned component test and finite next scopes

The first component test should isolate a single MoE window at small rows (including a row count with expert counts crossing a job boundary), use fixed inputs/weights/routes and compare: current route-slot `native16::combine`; candidate FP32 accumulator in expert-ID order; and a candidate that restores route-slot order at final combine. Assert unique IDs, exact route mass, no dropped/duplicate source rows, finite outputs, BF16 rounding points, same-queue write completion, cancellation between jobs, injected checked-drain failure retaining owners, and callback only after both HC write and drain. Use actual pinned SGLang/vLLM model-kernel contract fixtures only after source pinning; no performance claim from the unit. Then Main can separately calculate exact full-live-set arenas for 16K, 32K and `n=78,452`; include 262,144 admission and MTP/decode cache ownership before any implementation decision. Profiling dequant counts and end-to-end clean prefill is a later Main-owned measurement after numerical and memory admission, not a researcher claim.

External architecture precedent is limited: the official [vLLM modular MoE design at commit c67fe497a25d5af10a6ca0be9d18bcdd42cac4f1](https://github.com/vllm-project/vllm/blob/c67fe497a25d5af10a6ca0be9d18bcdd42cac4f1/docs/design/fused_moe_modular_kernel.md) documents grouped/batched expert inputs; official [SGLang EP design at commit a9c97c9f6973c03e778d1fe1e63a6b9f58a55012](https://github.com/sgl-project/sglang/blob/a9c97c9f6973c03e778d1fe1e63a6b9f58a55012/docs/docs/advanced_features/expert_parallelism.mdx) documents dispatch/permute/grouped-GEMM/combine and bounded communication rounds. Both repositories use Apache-2.0; only these descriptions were consulted, no implementation was copied or adapted. They support implementability of grouping, not this model's all-token deferred causal schedule, its numeric order, or B570 performance; see the already reviewed R622/R633 reports in the library. The closest local implementation evidence remains this pinned Strata window. R1002 adds only the all-token accumulator/fit analysis and does not recommend performance.
