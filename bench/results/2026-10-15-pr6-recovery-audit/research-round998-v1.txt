# Round 998 — Exact-stack Level Zero/SYCL profiling clock-domain drift

Classification: decision support. Date: 2026-10-17. Bounded read-only investigation; no builds, tests, GPU/profiler work, process inspection, Git commands, source edits, cleanup, service calls, or additional workers. Report budget: 18,000 bytes. This report is the only file written.

## Executive finding

The new receipts make a submit/start clock-domain or conversion defect more credible than the older “rare aged event” framing, but do not identify one. The model run has 24 numeric rejects among 532 captured events and every one is start < submit; a separate aged stress run has 140/141 valid records, one start < submit, while every pair has positive service of at least 52 ns and short query latency; baseline had 141/141. Data/guards/owner/fault gates passed in the latter two, and model inference/fault checks completed. These are diagnostic outcomes, not qualified complete profiles or performance evidence.

The key interpretation is that the three returned SYCL values are contractually in one backend timebase: SYCL 2020 R12 requires submit ≤ start ≤ end (equality allowed) and says timestamps from a backend share a timebase; no accuracy guarantee is made. Thus a numeric start-before-submit is a real returned-contract inconsistency, not an allowed consequence of “different domains.” A defect in how the implementation maps two lower-level clocks into that promised domain is a plausible mechanism. Keep the full triple rejected and preserve the unchanged acceptance rules.

## Acquisition path and what can be stated

### Normative SYCL result

SYCL 2020 revision 12, §4.6.6.5, defines three nanosecond values relative to an implementation-defined timebase; all same-backend events share that timebase. command_start >= command_submit, command_end >= command_start; equality is legal. The implementation is encouraged to be accurate but gets no specified accuracy. Reference: Khronos [SYCL 2020 revision 12](https://registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html), also pinned docs commit b3bcc5d5cc83217d14ebbb904e353c5a0d17f52b as used by R996. The implementation must supply coherent values despite whatever clocks it uses internally.

### Intel LLVM / UR v2 comparator, not installed-source identification

At immutable Intel LLVM snapshot afcca05be916a6ba0b925a4e088d76c160442be2, unified-runtime/source/adapters/level_zero/v2/event.cpp shows UR_PROFILING_INFO_COMMAND_START querying zeEventQueryKernelTimestamp, taking the global kernelStart, masking with the timestamp mask, and applying the device timer conversion. End independently re-queries the event and adjusts end for valid-bit wrap. The comments in this snapshot say command-submit time is recorded before enqueue with urDeviceGetGlobalTimestamps; the profiling-info switch itself returns zero for queued/submit because submission time is stored at enqueue. This path combines a pre-enqueue sample and a post-execution kernel-event sample, then publishes both as SYCL nanoseconds. Exact pinned source: [v2 event.cpp at afcca05](https://github.com/intel/llvm/blob/afcca05be916a6ba0b925a4e088d76c160442be2/unified-runtime/source/adapters/level_zero/v2/event.cpp), especially profiling query and submit comments around lines 1647–1699.

That code makes at least three testable clock/conversion boundaries: (1) which output from urDeviceGetGlobalTimestamps is retained for submit and how it is normalized; (2) how v2 obtains/caches timerResolution and whether it is “nanoseconds per tick” or “cycles per second”; (3) whether the kernel event global timestamp and device-global timestamp used by submit share a usable origin/epoch after conversion. The pinned event.cpp alone does not resolve (1)–(3); queue/device helper and installed binary source mapping are needed.

Level Zero versioned API documentation matters here. Its zeDeviceGetGlobalTimestamps describes a synchronized host/device pair; current spec specifies hostTimestamp as RAW_MONOTONIC_CLOCK nanoseconds, unaffected by wall-clock changes or software clock adjustments, and the corresponding device tick sample. Device properties select timerResolution units by structure type: legacy ZE_STRUCTURE_TYPE_DEVICE_PROPERTIES expresses nanoseconds per tick; ZE_STRUCTURE_TYPE_DEVICE_PROPERTIES_1_2 expresses cycles/second. The latter conversion is ticks * 1e9 / frequency, not ticks * frequency. A conversion code must pair the value with its property structure/version. Sources: [Level Zero device API v1.19.12](https://oneapi-src.github.io/level-zero-spec/level-zero/1.19.12/core/api/apis/device.html) and [Level Zero guide v1.19.12](https://oneapi-src.github.io/level-zero-spec/level-zero/1.19.12/core/PROG.html). These docs are current, not evidence that driver 1.17.39395+14 implemented every current clarification.

The guide explicitly cautions that kernel timestamp event clocks and zeCommandListAppendWriteGlobalTimestamp values must not be assumed equivalent merely because values fall in the same numeric range. That warning is directly relevant to checking whether v2’s converted start is being compared against a submit timestamp from a second acquisition route. Do not assert that the installed driver violates it: the exact adapter source, helper output and driver behavior remain unknown. Versioned Level Zero API docs (e.g. [v1.16.24 device API](https://oneapi-src.github.io/level-zero-spec/level-zero/1.16.24/core/api.html)) state the property-unit split; R996’s observations already caution that support and behavior have changed by specification version.

### Clock adjustments and age

For a submit value actually sourced from Level Zero’s specified hostTimestamp, wall-clock corrections (NTP step/slew, settimeofday) should not move that RAW_MONOTONIC_CLOCK sample. Therefore “system clock adjusted” alone is weak as an explanation for start < submit; inspect which sample is used and its normalization first. A monotonic host/device calibration can still be stale, discontinuous across runtime/device power-state transitions, or lose coherence with a kernel timestamp source if the implementation maps clocks incorrectly. Device counter wrap is a separate bounded-counter issue handled with valid bits; it typically concerns differences across wrap, and the pinned v2 code adjusts end relative to start. A single start < submit with positive start/end duration does not by itself resemble an end-wrap error.

“20 seconds aged” demonstrates that waiting before the test can coincide with a rare ordering failure, but does not show that the host wall clock changed, that frequency drift accumulated, or that a calibration became stale. The baseline/aged test is only 141 records per arm with one failure in the aged arm; it is not evidence of systematic clock drift or a causal wait threshold. Query wall time being short excludes the prior 1-second query-delay guard as an explanation for this observed aged reject, but says nothing about clock accuracy.

## Can start/end be qualified separately?

Prospectively, yes as a narrow duration submetric, provided the definition and gate are explicit: retain all receipts unchanged; qualify delta = command_end - command_start only for records where each query succeeds, end >= start, timestamps are non-sentinel, and delta is positive and at least the validated timer granularity; record timer units/valid bits and coverage. The baseline/aged microtest meets that narrow numeric predicate for its captured pairs (141/141 and 140/141 respectively) according to the receipt, while the complete triple remains unqualified because aged still has one start < submit. This does not retrospectively turn either triple result into a pass, and a microtest does not qualify all command classes or the model’s required full capture.

The current Level Zero guide cautions that kernel event and global device timestamps are not necessarily equivalent timebases, but start/end both come from one kernel-event query route in the pinned comparator; their difference can be internally useful even when cross-domain placement against submit fails. However, a difference-only qualification is still conditional on the installed provider returning meaningful event timestamps, correct unit/mask conversion, and command-kind semantics. Do not treat the 52 ns receipt guard as a universal specification guarantee; it is a stack-specific reported resolution. Keep full SYCL acceptance (submit <= start <= end) and all current fault, owner, physical-context, completeness gates intact. This is analysis guidance, not an acceptance-policy/code change.

Use a single bounded same-process diagnostic on the already pinned stack and exact failing receipt binary/command shape; no model expansion is needed. For each of one rejected and one neighboring accepted kernel (and one route-map upload only if it remains implicated), capture: UR/SYCL submit/start/end return codes and values; source call/path for submit; zeDeviceGetGlobalTimestamps host and device outputs at submit; native event query status and raw global.kernelStart/kernelEnd; property stype, timerResolution value/units, both valid-bit counts/masks; queue/engine/command kind; event handle plus pool slot/generation and release/reborrow sequence.
