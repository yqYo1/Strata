# GPU special functions: contracts, lowering, and measurement

**Knowledge collection; no hardware work or Strata implementation was performed.** The useful comparison is between three separate things: the API's numerical contract, the compiler's chosen sequence, and the whole kernel's measured behavior. A function named `native`, an optimization flag, or a GPU command duration does not by itself establish the other two.

## Contracts

SYCL 2020 revision 12 defines the ordinary `sycl::exp2`, `sycl::log2`, and `sycl::rsqrt` functions in its built-in math namespace. It does not give one ULP table that applies to every backend. Its informative Appendix C.11 says that built-in math called on the OpenCL backend has the corresponding OpenCL profile's precision; other backends need their own specification. For OpenCL C 3.1.2 (Khronos commit `219be24`, dated 2026-09-17), single-precision full-profile bounds are exp2 ≤3 ULP, log2 ≤3 ULP, and rsqrt ≤2 ULP. Embedded-profile bounds are ≤4 ULP for all three. These are maximum errors relative to the infinitely precise result under the spec's ULP definition; they are not promises of correct rounding. The backend/profile distinction matters when someone reports “SYCL accuracy.” [SYCL 2020 rev. 12](https://registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html) [OpenCL C 3.1.2](https://registry.khronos.org/OpenCL/specs/unified/html/OpenCL_C.html)

`sycl::native::exp2`, `sycl::native::log2`, and `sycl::native::rsqrt` are a separate, single-precision-oriented API (float and supported float vectors). SYCL explicitly delegates their precision requirements and legal input values to the backend. The stated intent is that they may use native device functionality for better performance, while sacrificing accuracy or restricting legal inputs. The OpenCL C contract is concrete about the latitude: native functions may map to one or more native device instructions and will typically be faster, but accuracy and, for some functions, input ranges are implementation-defined. The native exp2/log2/rsqrt entries each specify both an implementation-defined range and maximum error. Native denormal support is also implementation-defined. Thus `native` is an intent and contract change, not a portable instruction selector, ULP limit, argument range, FTZ policy, or speed guarantee. [SYCL 2020 rev. 12](https://registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html) [OpenCL C 3.1.2](https://registry.khronos.org/OpenCL/specs/unified/html/OpenCL_C.html)

For the ordinary OpenCL math functions, special-value behavior follows the spec's C99-derived edge rules and listed additions: exp2(±0)=1, exp2(−∞)=+0, exp2(+∞)=+∞; log2(±0)=−∞, log2(negative)=NaN, log2(+∞)=+∞; rsqrt(−0)=−∞, rsqrt(+0)=+∞, rsqrt(negative)=NaN, and rsqrt(+∞)=+0. NaNs yield NaN where the function is defined. OpenCL requires INF and NaNs but makes single-precision denormal support optional; inputs or results of math operations may flush to zero. Its `-cl-denorms-are-zero` and relaxed-math modes further affect the effective contract. With `native_*`, do not infer these corner results for inputs outside that implementation's legal range: the SYCL/OpenCL native contract does not give the same portable full-domain promise, and native denormal handling is implementation-defined. Signed-zero-sensitive callers need an explicit backend test or a non-native operation with the desired contract.

Fast-math compiler options are a third choice. They apply to a broader expression context than a single `native` call and can permit reassociation, contraction, relaxed range assumptions, denormal flushing, or substitutions. Their spelling is not a cross-compiler contract. For example, OpenCL's `-cl-unsafe-math-optimizations` has its own weakened error table (exp2's bound grows with |x|; log2 retains a narrower accuracy statement), while the exact profile and option combination must be read from the implementation's language version. CUDA's `--use_fast_math` is defined by NVIDIA to imply FTZ, approximate division and square root, and FMA contraction, and to replace standard math calls with corresponding fast intrinsics. Do not read an option name in a build script as proof of which operation or instruction the generated kernel contains. [OpenCL C 3.1.2](https://registry.khronos.org/OpenCL/specs/unified/html/OpenCL_C.html) [CUDA C++ Best Practices Guide 13.1.2](https://docs.nvidia.com/cuda/archive/13.1.2/pdf/CUDA_C_Best_Practices_Guide.pdf)

## What can lower to hardware

A scalar C++ call is only a request at the source level. Depending on the backend, precision mode, type, vectorization, known value range, and compiler version, it can become a direct device instruction; several instructions (range reduction plus polynomial or multiply/add); a library/helper call; or a different expression selected by an optimizer. Broad-domain standard functions often need a more expensive path than their narrower native counterpart. Even similar-looking “approx” APIs can be software-emulated for a type or target: PTX ISA 9.1 documents `rsqrt.approx.f64` as software-emulated and relatively slow, while FP32 `rsqrt.approx` has a hardware-targeted PTX instruction. This is a useful counterexample to equating API name with hardware SFU use.

Base-2 calls make some transformations especially visible. A source `exp(x)` can be represented using `exp2(x * log2(e))`; `log(x)` can be a scale of `log2(x)`. Those expressions may add a multiply/scale, fuse with a neighboring operation, or be recognized and folded into a different function. If `x` is guaranteed inside a narrow range, a compiler may use a cheaper sequence than it can use for unrestricted library semantics; if the promise is absent, it may retain range checks or a helper path. Vector/scalar spelling alone does not settle the mapping either: a vector operation can become per-lane scalar instructions, a vector builtin, or a helper depending on target and compiler.

For OpenCL/SPIR-V, LLVM's SPIR-V builtin table at commit `32dd4e7e8e375cf983ffcf49e72f3abd6158a1b1` maps `native_exp2`, `native_log2`, and `native_rsqrt` to OpenCL extended-instruction IDs 84, 87, and 91. This is evidence of a frontend/backend path into the OpenCL extended instruction set, not evidence that a specific DPC++ build emits one Intel EU instruction. Intel IGC's pinned configuration table (`ed9448a9e138bc8e48b93c89910aacdb637f0a6a`, 2026-09-11) also documents a `log2/mul/exp2 = pow` matcher and a `pow -> exp(log(x)*y)` transform. That establishes that an apparently scalar expression can be rewritten into or out of a math composition; it does not show which path a particular kernel takes. Exact DPC++/IGC/SPIR-V versions and final VISA/ISA are needed to make that claim. [LLVM SPIR-V builtin table at pinned commit](https://github.com/llvm/llvm-project/blob/32dd4e7e8e375cf983ffcf49e72f3abd6158a1b1/llvm/lib/Target/SPIRV/SPIRVBuiltins.td) [Intel IGC flags at pinned commit](https://github.com/intel/intel-graphics-compiler/blob/ed9448a9e138bc8e48b93c89910aacdb637f0a6a/documentation/configuration_flags.md)

NVIDIA's PTX ISA 9.1 (CUDA Toolkit 13.1.2 archive) documents `ex2.approx.f32`, `lg2.approx.f32`, and `rsqrt.approx.f32` as fast approximate instructions. It gives exp2 a maximum error of 2 ULP across the input range; log2 an absolute error of 2^-22 on (0.5, 2) and relative error of 2^-22 for positive finite inputs outside that interval; and rsqrt relative error of 2^-22.9 over positive finite inputs. The ISA spells out signed-zero, infinity and NaN results. The `.ftz` form flushes subnormal inputs and results to sign-preserving zero; the unqualified FP32 forms support subnormals on SM 2.0 and later. PTX is a virtual ISA translated by the driver to target instructions, so these documented PTX properties still do not prove final SASS, instruction issue rate, or a particular chip's elapsed time. CUDA's guide additionally notes that `1.0/sqrtf(x)` is converted to `rsqrtf(x)` only when approximate division and square root are enabled; it recommends calling `rsqrtf` explicitly when that is the intended operation. [PTX ISA 9.1](https://docs.nvidia.com/cuda/archive/13.1.2/parallel-thread-execution/index.html) [CUDA C++ Best Practices Guide 13.1.2](https://docs.nvidia.com/cuda/archive/13.1.2/pdf/CUDA_C_Best_Practices_Guide.pdf)

In PTX's documented corner table, exp2 maps −∞ to +0, both signed zeros to +1, +∞ to +∞, and NaN to NaN. Log2 maps either signed zero to −∞, negative finite values and −∞ to NaN, +∞ to +∞, and NaN to NaN. Rsqrt maps −0 to −∞, +0 to +∞, negative finite values and −∞ to NaN, +∞ to +0, and NaN to NaN. For `.ftz` variants, a subnormal can become signed zero before the operation: this can turn a tiny log2 argument into the zero case or a tiny rsqrt argument into a signed infinity. The unqualified FP32 instructions preserve subnormal inputs/outputs on the documented newer targets. This difference is a concrete reason to compare tail inputs, not just values near one.

## Reduction examples and applicability

Triton's fused-softmax idiom is a max-reduced row, `exp(row - max)`, sum-reduced denominator, then division by that denominator. A pinned Triton issue gives an especially useful observed example: at Triton commit `b2684bf` on an A100, the author supplied a log-sum-exp reduction with BF16 input cast to FP32, then `exp` and `log`; the generated PTX showed `ex2.approx.f32`, without `.ftz`. The author reported that manually using the FTZ form improved that example by about 6% and online-softmax by more than 10%. Those are author-reported measurements from that one compiler/device/kernel, not an independently reproduced result or a Triton contract. They do show why FTZ must be checked in generated code rather than inferred from a high-level flag, and why a normalized reduction can be the right end-to-end workload for comparing variants. Triton's source-level `tl.exp` alone does not promise this exact PTX on another version/backend. [Triton issue #5735, codegen report at commit `b2684bf`](https://github.com/triton-lang/triton/issues/5735)

The max shift in softmax constrains each exponent input to be non-positive, preventing overflow for finite logits and making far-tail underflow a likely accuracy question. The sum is at least one for a non-empty row with a finite maximum, so log-sum-exp avoids taking log of a tiny denominator. The contract to test is still the full reduction: local exp error changes the sum and normalized probabilities, and reduction order/precision can dominate. Replacing exp(x) with exp2(x·log2(e)) or storing a prescaled score can change rounding and may trade one multiplication for a more direct base-2 operation; a source-level algebraic identity is not a bitwise identity. `rsqrt(var + eps)` in layer normalization has a different domain: variance plus positive epsilon is nonnegative, but a very small epsilon, subnormal variance, or output-scale amplification can make FTZ and relative error consequential. Native math is unsuitable if its legal input range does not cover the application's observed domain, if special-value behavior matters, or if small errors perturb branch/routing decisions or persistent recurrences.

A non-LLM counterpart is the all-pairs gravitational N-body kernel in *GPU Gems 3*, which repeatedly computes distance-dependent force from pairwise displacement and includes square root and division in the interaction. This is a natural workload in which a carefully bounded `rsqrt` formulation might reduce scalar math cost, but the cited chapter's code is not evidence that its source used a native rsqrt or that replacing its operations is safe. A softening term keeps the self-interaction finite; the acceptable range/accuracy must be judged for that formulation and the accumulated trajectory, not inferred from an isolated rsqrt ULP bound. This distinguishes a transferable example from a claim about a particular implementation. [GPU Gems 3, “Fast N-Body Simulation with CUDA”](https://developer.nvidia.com/gpugems/gpugems3/part-v-physics-simulation/chapter-31-fast-n-body-simulation-cuda)

## A meaningful discriminator

1. Build two or more arms that differ only in the math choice or documented compiler option. Record compiler/driver/device, backend/profile, flags, generated intermediate code, and exact input domain. Keep process environment fixed after runtime initialization. Do not compare a standard arm with a native arm if the compiler also changes reduction order, fusion, vector width, precision, or launch configuration.
2. Use both representative inputs and boundary probes: powers of two and adjacent floats, values around exp underflow/overflow, log's zero/negative boundary, rsqrt's zero/negative boundary, signed zeros, infinities, NaNs, normal/subnormal boundaries, and values near any documented native input limit. Compare the function result and the consumer's full reduction output. Record ULP away from zero, absolute/relative error near zero, NaN/Inf/sign behavior, normalization-sum deviation, and error distributions or worst cases. A high-precision reference is useful for diagnostics; acceptance must use the task's agreed numerical contract and full output behavior.
3. Inspect the compiler path: source-to-LLVM IR, SPIR-V or PTX; Intel IGC VISA or final device ISA; CUDA cubin/SASS after PTX. Look for instruction count, helper/libcall paths, math opcode and FTZ modifier, vectorization, fusion, register/spill changes. PTX or SPIR-V alone is a lowering observation at that stage, not hardware execution proof.
4. Measure the whole kernel and relevant dependency path with repeated, isolated processes and an identical workload. A GPU event/command interval includes launch, scheduling, reduction dependencies, memory effects, and the operation's latency; it is not SFU utilization. To claim SFU activity, use architecture-specific profiler counters for special-function issue/active cycles and confirm their availability/meaning on that device, alongside instruction mix and disassembly. If no such counter is available, report end-to-end time and avoid an SFU-utilization conclusion. Check for a speed change on the actual normalized reduction, because a scalar instruction can be hidden behind memory or reduction work; conversely one less math instruction can lose if it increases registers, spills, or numerical work elsewhere.

Include short and long rows or batches only as workload regimes in the same controlled comparison, not as interchangeable test cases: very short rows may be dispatch/reduction dominated, while wide rows increase math and memory work and can change occupancy. Normalize any instruction or counter totals by useful elements, and record the exact profiler event definition; an “EU active” or “math pipe busy” number is not interchangeable with an SFU issue counter. If the standard and native variants produce the same final instruction sequence, the API distinction has no demonstrated codegen benefit on that build. If their sequences differ but whole-kernel time does not, the honest finding is “lowering changed, end-to-end effect below this discriminator's sensitivity,” not “the special unit is saturated.”

A defensible choice therefore has two gates: the documented/observed math contract covers the real input domain and produces acceptable complete-output error, and repeated whole-kernel measurements show a gain under matched conditions. Standard math is safer for broad-domain or special-value-sensitive callers; native math is a candidate when inputs are bounded, denormal/special handling is acceptable, the compiler emits a genuinely cheaper path, and the application-level discriminator passes. No B570 bottleneck, Strata speedup, or utilization conclusion follows from these source observations.

## Sources and evidence limits

Eight source entries were used: (1) SYCL 2020 rev. 12; (2) OpenCL C 3.1.2, Khronos commit `219be24fc8947c68ee45b4d25b55a92b8f799f29`; (3) LLVM SPIR-V builtin table, pinned commit above; (4) Intel IGC configuration flags, pinned commit above; (5) NVIDIA PTX ISA 9.1 / CUDA Toolkit 13.1.2; (6) NVIDIA CUDA C++ Best Practices Guide 13.1.2; (7) Triton issue #5735, reporting Triton `b2684bf` / A100; (8) NVIDIA GPU Gems 3 N-body chapter. The Intel source observations are compiler-source evidence, not an Intel GPU measurement; the Triton performance numbers are issue-author reports, not reproduced measurements. This investigation ran no GPU, compiler, profiler, test, or Strata workload.
