# R773 — Chunk-size choices for causal long prefill under GPU memory limits

2026-10-16 JST. Bounded public-source knowledge collection. This report compares prompt-level chunk sizes and short-tail handling; it does not measure or recommend a Strata product change. No product source, build, test, GPU, profiler, process inspection, Git operation, environment change, cleanup, or service action was performed. No XeStrata material was read or used.

## Finding

There is no portable best token count for a causal GPU chunk. Chunk size is an application-level row batch; the library’s internal GEMM tile and a SYCL work-group are separate dimensions. Increasing the prompt chunk can raise the MoE GEMM M dimension, reduce chunk-loop and submission repetitions, and amortize fixed per-chunk work. It also lengthens or enlarges the live row workspace, can create too few or badly quantized GEMM tiles, and makes a padded tail more expensive. Smaller chunks reduce per-window capacity and may be appropriate when memory admission is tight, but can split routed rows into GEMMs too small to fill the device and repeat host/runtime work. Test a few bounded sizes against actual row histograms and peak live allocations.

The current 8,192-row chunk is the existing measured control, not a demonstrated optimum. R769 covered one versus two windows at that size, not smaller or larger chunks. Keep this comparison separate from queue overlap and deferred expert-major accumulation, which changes retained state and may change floating-point combine order.

## Applicability by strategy

| Strategy | Conditions that could justify it | Counterevidence and limits |
| --- | --- | --- |
| Smaller fixed chunks, such as 2K–4K | A high per-row live workspace or a narrow free-VRAM margin makes the current chunk fail admission or displace useful resident data. It can also help where actual expert row counts are already large enough at this batch size and the kernel grid remains well populated. | It multiplies chunk boundaries, state handoffs, GEMM submissions, and repeated preparation. If expert rows become too few to fill M tiles, a smaller chunk can save capacity yet lower GPU utilization. Measure the shapes and library tile schedule. |
| Current fixed 8K | Best comparison anchor for the present engine. It keeps a known path and bounds the row working set while producing larger routed batches than a microchunk. | Its prior speed samples do not establish a local optimum; it can still be too large for a memory-constrained run or too small for launch-heavy expert GEMMs. |
| Larger fixed chunks, such as 16K–32K | Consider only when per-chunk host submission or repeated preparation is measurable on the critical path, expert row distributions show many undersized M dimensions at 8K, and full-workset admission leaves headroom. More rows per active expert can amortize fixed GEMM setup and improve data reuse. | Every row-retained array grows with chunk size, and simultaneously live outputs can raise the peak faster than one residual buffer. More rows do not guarantee more parallel tiles: the grid may shrink or end in a weak wave. Routing skew can still leave hot experts dominant and cold experts small. |
| Small set of admitted sizes selected by workload | Different prompt lengths or routing distributions may justify a small menu when a fixed size wastes capacity on one workload and underfills GEMMs on another. A static sample or prior per-layer histogram may inform a bounded selection. | Dynamic decisions add metadata and CPU/device control. Sparse-accelerator results such as HYTE rely on architecture-specific tile metadata and scheduling; they do not establish a low-cost policy for this SYCL engine. A new size must preserve exact recurrent state and be admitted against actual simultaneous allocations. |

One FP32 residual window at the supplied hidden width (10,240 values per row) costs `chunk_rows × 10,240 × 4` bytes: 2K is 80 MiB, 4K is 160 MiB, 8K is 320 MiB, 16K is 640 MiB, and 32K is 1.25 GiB. These are one-array arithmetic, not allocator or peak-VRAM totals. Per-row state, expert outputs, routing, QSA/GDN scratch, KV, weights, runtime allocations, and aliasing also affect admission. A doubled chunk doubles each row-linear array; retained outputs across chunks raise live data further.

For MoE, useful per-expert M is the realized route count. The uniform estimate `chunk_rows × k / E` hides skew; collect per-layer expert counts and GEMM shapes. A large chunk can still present many small GEMMs, while grouped execution may expose aggregate M. That is an operator-specific effect, not a chunk-size guarantee.

## What literature says about utilization and amortization

Intel’s latest public oneAPI GPU Optimization Guide located for this review is version 2025.2 (dated 2025-07-10). Its SYCL launch discussion separates host submission, device start, and completion, states that submission cost depends on the backend runtime and host, and notes that device start can lag submission. This supports measuring host submission and device execution separately when comparing chunk counts; it does not quantify the installed runtime’s cost. The same guide’s occupancy material ties utilization to available work-groups and resource use such as SLM, registers, and thread contexts, and warns that its work-group examples are device-specific. A prompt chunk’s token count is not itself a work-group size or proof of occupancy. [Intel oneAPI GPU Optimization Guide 2025.2: Kernel Launch](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2025-2/kernel-launch.html), [Thread Mapping and GPU Occupancy](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2025-2/thread-mapping-and-gpu-occupancy.html), and [Considerations for Selecting Work-Group Size](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2025-2/considerations-for-selecting-work-group-size.html).

The NVIDIA GEMM engineering guide provides clear counterexamples to monotonic “larger is faster” or “smaller is safer” rules. On its A100/CUDA setup, larger GEMM tiles were more efficient when enough output work existed, while using smaller tiles exposed more parallelism at an efficiency cost. It also documents tile quantization (masked edge tiles still doing work) and wave quantization (a final partial wave can leave many processors idle); its examples show sharp performance steps around tile and processor multiples. The transferable point is that chunk size changes the matrix dimensions seen by a library, and those dimensions interact with internal tile geometry. Its measured A100 results and CUDA/cuBLAS choices are not B570, oneMKL, or SYCL performance evidence. [NVIDIA, Matrix Multiplication Background User’s Guide](https://docs.nvidia.com/deeplearning/performance/dl-performance-matrix-multiplication/index.html).

Stream-K’s original PPoPP work offers a useful counterexample to fixing underfilled output grids only by enlarging application chunks. It partitions GEMM inner-loop work across processing elements to reduce sensitivity to output-tile quantization; its reported sweep covers 32,824 GEMM geometries and is specific to its GPU implementation and hardware. This suggests checking whether poor utilization is at the chunk-to-GEMM mapping or inside the GEMM schedule before concluding that the prompt chunk must grow. Stream-K splits/reduces GEMM work, so its additional partial results, reduction costs, numeric order, library support, and hardware fit would need separate evidence. It is not a proposal to port that implementation. [Osama et al., “Stream-K: Work-centric Parallel Decomposition for Dense Matrix-Matrix Multiplication on the GPU”](https://arxiv.org/abs/2301.03598).

HYTE’s ISCA 2025 paper provides a sparse-accelerator comparison: it combines offline sampling for an initial tile schedule with runtime tile-shape adjustment for varying local sparsity, and reports results on custom sparse tensor accelerators. Its counterevidence is equally relevant: metadata management is material, sampling and cost models can be inaccurate, and purely dynamic tiling adds complexity. Only the design question transfers—whether routing variability calls for a few static chunk choices or runtime adaptation. HYTE’s hardware gains do not predict performance or implementation cost on Arc/SYCL. [Li et al., “HYTE: Flexible Tiling for Sparse Accelerators via Hybrid Static-Dynamic Approaches” (ISCA 2025)](https://doi.org/10.1145/3695053.3731044).

## Short-tail handling and shared state

For `P` real prompt rows and nominal chunk `C`, process `floor(P/C)` full chunks and one final `r = P mod C` rows when `r > 0`. Prefer carrying the true `r` through the operator path or rounding only to the smallest kernel/library granularity that is needed. If a full-size launch is required, mask every padded row before memory access and ensure padded rows do not write KV, advance GDN/recurrent or PLE state, update positions, contribute to reductions, or become visible at a layer/checkpoint boundary. SYCL 2020 revision 12 requires an `nd_range` global extent to be a multiple of its local work-group extent (or zero); masking or a separate tail launch does not permit padding to enter causal state. [Khronos, SYCL 2020 Specification revision 12](https://registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html).

A dedicated tail path adds one launch/setup cost but avoids full-chunk arithmetic on a small remainder. Padding to the nominal chunk is simple but may waste work; an exact `range` suits some kernels, while GEMM may still round dimensions. Decide from tail frequency, shape constraints, timing, and exact valid-row semantics. For recurrent or causal kernels, preserving the state sequence and absolute positions matters more than padding convenience. Any chunk-size comparison also needs numerical parity checks because a changed GEMM M shape can select another kernel or floating-point accumulation order even if the mathematical token sequence is unchanged.

## One bounded future experiment

After Main’s active measurement boundary is closed, compare 4,096, 8,192, and 16,384 row chunks on the same 78,452-row diagnostic workload, binary, FP32 storage/math, routing, device, and library settings, in separate clean processes with an alternating order. The exact remainders are 628, 4,724, and 12,916 rows, respectively; record whether the implementation executes each tail at its true size, pads only to a lower kernel granularity, or pads to a full chunk. Do not change queue schedule, dtype, placement, kernels, or expert grouping between arms.

For each arm record repeated full-path samples, chunk and kernel counts, host submission CPU time, GPU time, boundary waits, per-layer expert counts/GEMM shapes, transferred bytes, peak live VRAM, and workspace owners/lifetimes. Record output/state and tail parity, faults, and allocation/cancellation behavior. Separate any measured overlap from total time. This 78K screen does not replace the physical 262,144-context correctness/RESTORE gate.

## Evidence limits and sources

This is literature and shape arithmetic, not an Arc B570 measurement, inference-quality result, capacity qualification, or adoption decision. Intel’s 2025.2 guide is the current public guide found and has examples for Intel Xe GPUs; it is not proof of the configured Arc device’s behavior. SYCL’s range contract is portable, while tail-kernel performance is implementation-specific. NVIDIA’s measurements use A100 and CUDA; Stream-K is a GPU GEMM paper; HYTE is a custom sparse-accelerator design. No cited source establishes the best chunk size for causal/recurrent long prefill, Strata’s oneMKL implementation, or 600/1,000 tok/s performance. No source code was used.
