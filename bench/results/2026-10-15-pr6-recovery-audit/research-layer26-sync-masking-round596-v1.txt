# R596 — layer 26 phase-drain同期マスキングとoperand lifetimeの因果候補

2026-10-15 JST。read-onlyで実SYCL source、R583/R585/R586、`boundary-audit-long-pair.ja.md`、
`phase-audit-main-review.ja.md`、small/long-fixed/long-auto phase receipts、`layer26-phase-pair-v1.json`を照合した。
許可された本報告だけを書いた。build/test/GPU/profiler/service/Git/cleanupは行わず、進行中の
`boundary-audit-phase-off-long-auto-v2.json`も読んでいない。

## 結論

b65d5d81のphase診断ONでfixed4096とauto24576の層26・6選択行×11中間tensorがbitwise一致し、
final selected 19 rowsも旧fixed controlと一致したというMain提供の新証拠は、旧b6838d28の
boundary-only/autoでrelative row24575から出た選択差が、同じ観測位置のGDN入力、GDN出力、HC/FFN、
router、host grouping、MoE combine出力のいずれかに必ず残る、という仮説を弱める。ただしこの証拠は
追加captureごとのD2H + 同じcompute queueのchecked drainを含むので、正常経路で起きる同期依存raceを
除外しない。6行の一致から未採取24,575行までのGDN recurrent input/state一致は推論できない。
旧b683 auto境界FAILはそのまま別のFAILとして維持する。

現sourceから、特定のscratch alias違反、invalid async host lifetime、oneMKL queue契約違反は見つからない。
因果候補を残すなら、第一は**層26全chunk中の未観測rowに限るrecurrent入力/状態の先行差または時間依存の非決定差**、
第二は**oneMKL内部dispatch/precisionの未記録変化**である。後者はR583同様、原因を示す証拠はなく、
ordinary compute roundingへFAILを付け替える根拠にもならない。追加drainが6行結果を変える仕組みとして
具体的に残るのは、同期点がhost/GPU間の観測・submission間隔を変えることによる、採取位置外のproducer/consumer
タイミング依存である。現sourceは主要演算とD2Hを同じ明示queueに載せるため、queueが分かれていてevent接続が
欠けるという具体的パスは見つからなかった。

## 実sourceの演算順とlifetime

`run_impl`のlayer-major chunkは`m.cs`上でHC attention norm/down/SiLU/up/inject/mixを進め、
GDN層なら`m.mixed_h`から`qkv`、`z`をnative projectionし、`ab`をBF16投影し、gate生成、
convolution、recurrent state update、`y_h`化、`ssm_out` projection、residual writeを順に発行する。
次に同じ層のHC FFNを実行して`m.mixed_h`を上書きし、router BF16 projectionとtop10を実行、
shared expert、compact routed experts、combineを書き、final residualを更新する。phase captureはこの各境界
で同じ`m.cs`へD2Hを発行して`cudaStreamSynchronize(m.cs)`相当のchecked drainを行う。
GDN/HC/MoE scratch領域`m.region`は同じchunk/layer内で順番に別viewとして使う設計であり、
GDN phaseがMoE phaseより後までliveであるsource上の証拠はない。

Native dense projectionは`Gemm::native`が最大32MiB FP16 scratchを最大行数単位で再利用し、
各weight blockを`iq_dequant_f16(...,m.cs)`、直後に`Gemm::f16`してFP32 Yへ書く。routed compact pathでは
`m.dq_gu[q]` / `m.dq_d[q]`のDQ=2 slotをexpert moduloで再利用し、GU/dequant→GEMM→SwiGLU→DOWN GEMMを
同じqueueに積む。`Gemm::multiply`はoneMKL USM GEMMの返すeventを取得し`finish(stream,event)`へ渡すが、
non-null streamでは`finish`はwaitしない。これはqueue完了を待つ省同期設計であり、呼出し順序と同queueの
in-order semanticsを依存としている。`Gemm::native`のdequant scratchと2-slot expert scratchは、
次の再利用も同じqueueへ順に積まれるため、見えているAPI契約内では前回operationの完了前にhostがscratchを
再利用する形ではない。

oneMKL `Gemm::init_external` / `rebind`が保存する`workspace_`はmultiplyへ渡らず、sizeも未使用。
従ってこの32MiBはoneMKL scratchpadではなく、native weight dequant用scratchである。oneMKL内部の
workspace/allocatorのサイズ・再利用・実algorithm IDはreceiptにない。R583の「memory pressureでvariantが変わる」
仮説は可能性としてのみ残る。現wrapperにFP32 inputsやTF32 mode選択はなく、GEMM入力はBF16かFP16、出力はFP32。

layer-major expert uploadの所有権は、`m.src->copy_blob(layer,e,upload+e*stride)`が各expertを同期的に
owning `std::unique_ptr<uint8_t[]> upload`へコピーし、その後512回の`fill_slot`が同一`m.copy` queueへ
H2D転送、最後の`drain()`で完了を確認する。layer実行開始前にresidency mapを公開し、次層のuploadで
slabを上書きする前にはlayer boundary drainがある。run guardは一時ownersを解放する前にqueueをretireする。
この経路では`m.src`由来pointerを非同期copy完了まで保持する必要はなく、`upload` slabはdrainまで保持される。
`cudaMemcpyAsync` shimは与えられたqueueの`q.memcpy`へ直接forwardし、別copy queueを暗黙生成しない。
このlong-prompt routeは`m.copy == m.cs`をrequireする。SYCL queue memcpyのhost pointerは許可され、
非同期copy完了までsource lifetimeを保つ必要があるという契約と、この所有者・drain順は整合する。

現状で追加drainによる結果変化を想定するなら、global異queue競合やsource buffer早期解放より、
「未捕捉のtoken rowに存在する時間依存問題」か「同じ入力でもlibrary/device経路が変わる非決定差」へ
範囲を限定する。なお`m.mixed_h`はchunk内の全rowを持つが各層で再生成される。selected rowのFFN/GDN入力一致は
全chunkの当該層GDN入力一致を意味しない。`ss.gdn_state`は層別にchunk間を維持する状態であり、phase receiptは
この全状態を保存・比較していない。

## 最小Main比較案（最大2件）

1. **同一b65 binaryのphase drains ON/OFFを境界audit ONで比較する。** Mainが実行中のphase OFF / boundary ON
   auto receiptが閉じた後、phase ON / boundary ONの既存long-auto receiptと同じ34,603 input、chunk4096、
   fixed/auto条件、旧fixed controlのselected logits/headを比較する。boundary D2H/drainは両armに残るので、
   この比較が切り分けるのはphase capture固有drainの追加分だけであり、「drainなしの通常経路」ではない。
   OFFでlayer26差が再現しONで一致するなら、追加phase captureが差を隠す因果証拠は強まる。両方一致なら、
   boundary-only診断でも同期効果が残るためrace不在の証明にはならず、旧b683 failureも維持する。
2. **必要ならphase captureを1か所だけ残すselective drain comparisonを行う。** 現sourceでoperator間scratch再利用の
   対象を最も直接狙う位置として、層26のGDN `y_h` producer (`gdn_recurrence`)→native `ssm_out` GEMM消費と
   層26 compact routed GU/DOWNの2-slot native dequant/GEMM再利用から、Mainがfirst-difference証拠で指した一方に
   1個だけchecked drain/markerを置き、同じb65 binary/同じ入力でその一点ON/OFFを比較する。両方同時に入れない。
   captureでは対象rowだけの値を返すのではなく、その演算がカバーするchunk全rowの出力digestまたは比較可能な
   first-logit/final-head gateを記録し、6 selected rowsだけの繰返しで再び全GDN inputを推論しない。
   drainが出力を切替えれば対象producer-consumer lifetimeを調べる優先度が上がる。差がなければその一点の
   drain-sensitive仮説は弱まる。監査機構を増やす前に比較1の結果を使い、必要なければ実行しない。

## ordinary GEMM丸めとしてquality gateへ進める最低条件

「小さいbitwise差だから普通の丸め」と扱うには足りない。まずphase OFFの長文auto receiptが閉じ、
差が出た場合に以下を満たす必要がある。

* 最初の不一致を同一GEMMの入力/weights、dtype、shape、queue/operand lifetimeが一致した箇所に限定し、
  mismatching bytesがFP16/BF16 GEMMのFP32出力だけであることを確認する。GDN state、mixed inputs、router logits/IDs、
  expert grouping/weights、scratch未初期化やbuffer owner不整合の先行差が残れば丸め差とは言わない。
* phase drainsを外した同一binary/configで少なくとも複数fresh processの通常比較が同じ非致命的差の範囲に収まり、
  routing/selected heads/first logitsと出力の品質gateが別にpassする。oneMKL内部variantが未観測なら
  「GEMM出力の小差と整合」までで、「非決定GEMM由来」と断定しない。
* 既存FAILのoriginal receipt/status/rawを保ち、同条件のnormal path gateで結果を上書きしない。小数値幅だけで
  全context、recurrent state、RESTORE、service品質を合格にしない。

6選択行×11tensorのbitwise一致だけではこの条件を満たさず、全token recurrent input/stateの一致を示さない。

## 公式API契約とsource/evidence pin

* oneMKL 2026.0 GEMM USM APIは`sycl::queue&`を受け取り、optional dependenciesを省略すると明示依存なし、
  返却eventがcomputation完了待ちに使えるとする。row-major GEMMの型表はFP16/BF16入力・FP32出力を掲載。
  [Intel GEMM 2026.0](https://www.intel.com/content/www/us/en/docs/onemkl/developer-reference-dpcpp/2026-0/gemm.html),
  rows 1447–1466 (signature/default deps), 1584–1600 (dependencies and output event), 1338–1360 (precision table).
* oneMKL DPC++ overviewはroutineへ渡すqueueが実行先を指定すると説明する。
  [Intel oneMKL DPC++ BLAS/LAPACK overview 2026.0](https://www.intel.com/content/www/us/en/docs/onemkl/developer-reference-dpcpp/2026-0/introduction-to-the-intel-oneapi-math-kernel.html),
  rows 1257–1279.公開APIは実装内部に別queueがないと保証する文ではないが、その内部queueやevent切断を示す証拠もない。
* SYCL `in_order` queueでは同じqueueへの後続commandがsubmission order上の暗黙依存を持ち、別queueとの順序は保証しない。
  [Khronos SYCL Reference: queue](https://github.khronos.org/SYCL_Reference/iface/queue.html), rows 425–431.
* SYCL command-group `memcpy`はhost pointerまたはqueue deviceからaccessibleなUSM pointerを許し、
  [Khronos SYCL Reference: handler](https://github.khronos.org/SYCL_Reference/iface/command-group-handler.html),
  `memcpy` section; `queue::memcpy`はUSM copyのeventを返す ([Khronos SYCL Reference: queue](https://github.khronos.org/SYCL_Reference/iface/queue.html), `memcpy` section).
  copy sourceの寿命はその非同期operationの完了まで必要で、layer-major slabは最後のqueued fill後のdrainまで存続。
* oneMKL GPU initialization docsはkernel/program cacheと内部memory managerのfast allocation reuseを説明するが、
  memory pressureによるGEMM variant切替は記述しない。
  [Intel oneMKL Initialization on GPU 2026.0](https://www.intel.com/content/www/us/en/docs/onemkl/developer-reference-dpcpp/2026-0/onemkl-initialization-on-gpu.html),
  rows 1265–1278.
