# Long-prefill layer and KV capacity contract (R677 v2)

Date: 2026-10-15 JST. Read-only source and public-artifact audit for capacity arithmetic. This v2 corrects v1's GEMM scratch size and streamed-KV classification; v1 remains byte-identical. No source/proposal changes, tests, builds, compiler, GPU, process, environment mutation, Git mutation, private-B/full-model read, or cleanup. The only new file is this report. This is count arithmetic and source ownership, not a successful admission, performance, or quality result.

## Scope and assumptions

The planning scenario has no decode-only weights resident on the GPU. Reserve the largest active layer's packed experts, that layer's dense/native weights, and its required GEMM scratch/workspace before spending the remaining bytes on session state, KV and residual storage. The layer-major route loads all 512 packed expert blobs for one layer into an extra device cache, completes the layer's prompt pass, then replaces that cache with the next layer (`src/prefill/layer_major.inc:127-162,292-320`; R667). This is the largest streamed expert layer plus the layer's dense/native part; it is not a 512-layer-expert GPU residency assumption.

The small metadata sources consulted are `/home/yayoi/.local/share/strata-sycl/packs/qwen3.8-flash-next-iq3_s/index.txt` and `native_experts.txt`. No GGUF payload was read. `native_experts.txt` describes the packed expert source blobs; at maximum 2,662,400 B per expert, a 512-slot aligned layer cache is 1,363,148,800 B. The metadata file supplies per-layer/per-format blob sizes; it does not itself establish a live allocation. The dense tensor rows in `index.txt` identify canonical tensor shapes/locations, while `src/core/native_dense.cpp:73-188` attaches native dense projection uploads to the corresponding `WeightRef::native_data`. Count the active native dense allocations once, and count the canonical CPU/mapped backing only if it is actually resident in GPU memory. Do not add canonical and native copies as two GPU owners merely because both representations exist in the metadata. Native dense is loaded for supported projections, not a blanket second full-model dense GPU copy (`src/program/generate.cpp:1757-1769,2182-2189`; `src/core/native_dense.cpp:73-188`).

`index.txt`/`native_experts.txt` are configuration inputs for sizing, not evidence that every entry is device-resident. The exact device owner list and any separate runtime allocation still need a live allocator/free-memory receipt. The scenario assumes default fused GR, `STRATA_PREFILL_MMQ=0`, compact FP16 MoE effective, BF16x2 disabled, and the public ring=8 count used by the cited C=4096 log. These are source-count assumptions, not a claim that every future run has that environment.

## Prefill scratch: exact count versus actual carve

`Alloc::take` rounds each allocation independently to 256-byte alignment with 256 guard bytes (`src/prefill/prefill.cpp:191-210`). `Prefill::carve` allocates one shared region of `max(GDN,QSA,MoE)` because those same-base layouts execute in phases; it does not allocate all three branches additively (`:845-887`). With current geometry and full-context QSA scratch, R637 v2 gives:

| Chunk | GDN branch | QSA branch | compact FP16 MoE branch | shared region |
| ---: | ---: | ---: | ---: | ---: |
| 4,096 | 590,350,336 B | 607,128,320 B | 543,837,696 B | 607,128,320 B |
| 8,192 | 1,180,698,624 B | 1,120,979,712 B | 1,087,671,808 B | 1,180,698,624 B |

The public C=4096 run reports `accounted=1,662,831,872` and `shared region=607,128,320 bytes`; its command sets `--max-context 262144 --kv int8` (`boundary-audit-long-fixed-v1.json`, `boundary-audit-long-auto-v1.json`). That observed accounted total is for **streamed KV mode 1**, and includes the full-range one-active-layer stage: 276,824,064 B payload plus four `Alloc::take` guards/padding of 256 B each, or 276,825,088 B. It must not be labeled full-resident accounting. The 4K session mode is also confirmed by the public run's current source route and setup; `take_stage` adds these four buffers only when `q0.kv_mode==1` (`src/prefill/prefill.cpp:526-551`).

Subtracting that exact staged-layer owner gives the following source-derived `carve` accounting for the two modes. C=4096 streamed is the observed log value. C=8192 streamed is derived using R670 v2's actual 1,210,776,832 B C4-to-C8 carve delta. Resident rows are derived by removing the fixed mode-1 stage from each corresponding streamed count:

| KV mode | Chunk | Actual `carve` accounting | Status |
| --- | ---: | ---: | --- |
| Full-resident (`kv_mode=0`) | 4,096 | 1,386,006,784 B | Derived from observed C4 streamed count minus 276,825,088 B stage owner |
| Full-resident (`kv_mode=0`) | 8,192 | 2,596,783,616 B | Derived from C8 streamed source delta minus 276,825,088 B stage owner |
| Streamed full-range stage (`kv_mode=1`) | 4,096 | 1,662,831,872 B | Observed public accounting log |
| Streamed full-range stage (`kv_mode=1`) | 8,192 | 2,873,608,704 B | Derived source count using R670 v2 actual carve delta |

The full-resident C4/C8 rows are arithmetic source-count projections with only the four stage allocations removed; C8 is not a run. Main should confirm the exact carve recount before using these values in a final admission decision.

In both modes, the GEMM scratch is `32*2^20` FP16 elements, not bytes: `take<uint16_t>(GEMM_SCRATCH)` allocates 67,108,864 B (64 MiB), plus the 33,554,432 B (32 MiB) GEMM workspace (`src/prefill/prefill.cpp:585-586,831-834,1253-1254`). The actual carve total also includes chunk arrays, the shared region, two compact-expert FP16 dequant pairs, eight 2,662,400-byte ring slots, PLE chunk buffers and fixed allocations (`:845-932`). In default fused GR `m.xn` is null; that FP32 duplicate is not carved (`:852-856`).

`Prefill::bytes_needed` is a conservative count-only loan size plus 8 MiB slack, not a physical-peak receipt. Do not derive its exact totals from `carve` by adding `xn` and slack: its top-level sequence differs. It counts a chunk-sized FP32 `xn` but only one `T*HC` float allocation in the corresponding segment, while actual `carve` has `grs` and `inj` as two `T*HC` arrays and omits `xn` under fused GR. It also includes `take_stage` only for `kv_mode=1`. The code's count-only `f(T*D); ... f(T*HC)` sequence and the actual named owners are at `src/prefill/prefill.cpp:852-863,1242-1281`. R670 v2's 1,378,548,992 B count-only delta must not be substituted for physical carved bytes; its 1,210,776,832 B actual carve delta is the relevant delta here.

Expert dequantization has DQ=2 small reusable FP16 GU/down pairs (19,660,800 B total), not 512 dequantized FP16 expert copies (`:590-591,918-919`; R667). When MMQ is disabled, MMQ group-conversion buffers are not carved. This scratch accounting is separate from the active layer's packed cache and dense native weights. Any additional oneMKL/SYCL, Level Zero, driver, allocator, or runtime allocations that are not represented by these `cudaMalloc`/`take` counts remain unaccounted and must be covered by measured free-memory headroom.

## Resident KV versus streamed full-range stage

At context `C=262,144`, the model geometry is D=`4*2560=10,240` FP32 residual scalars per row, 48 layers, 12 QSA layers (`include/strata/core/layout.hpp:27-59`; R676). The K8V8 table in R676 counts all twelve QSA states resident, including their indexer rows, page tables and one shared RoPE table:

| Resident format, context 262,144 | All 12 QSA states, KV plus indexing/state overhead |
| --- | ---: |
| K8V8 | 3,794,839,744 B |
| K8V4 | 3,039,865,024 B |

These are full-resident totals, not `Prefill::bytes_needed` scratch. `take_stage` returns without allocation when the primary QSA state has `kv_mode=0`; the twelve persistent states are owned by the session (`src/prefill/prefill.cpp:526-551`; `src/core/layer.cpp:501-552`). In mode 1, `take_stage` instead allocates one full-logical-range staging copy for the currently active QSA layer and the session owns the host backing for every QSA state. At 262,144 context K8V8, the stage has 524,288 rows (`65,536 pages * 2 KV heads * 4 tokens`); K and V codes total 268,435,456 B and their FP16 scales total 8,388,608 B, for 276,824,064 B in that active-layer stage. It is not twelve device copies. The stage is added to prefill `carve`/count-only storage when `kv_mode=1`, while the resident KV is outside that count. Keep this distinction explicit. `take_stage` uses `n_pages * n_head_kv * page_size`, then K/V code bytes and per-64-value scales (`:526-551`).

For the capacity hypothesis using the existing two-byte FP16 layer-major residual-storage option, operators remain on current FP32 `m.R` and current FP32 operator paths; only inter-layer hidden-row storage is FP16. That option is implemented in `include/strata/prefill/layer_major_plan.hpp` and `src/prefill/layer_major.inc`, while its long quality remains unqualified. The FP16 rows cost 20,480 B each, or 5,368,709,120 B (5 GiB) at all 262,144 rows. Combined with full-resident K8V8 state, the post-layer-reservation/non-KV remainder required is 9,163,548,864 B; with K8V4 it is 8,408,574,144 B. Those are arithmetic requirements only, not an adoption recommendation. For a budget `B` already net of all layer weights/workspace, GDN/session owners, shared context-independent allocations and driver/runtime reserve, complete FP16 rows left after full K8V4 state are:

`min(262144, floor(max(0, B - 3,039,865,024) / 20,480))`.

For K8V8, substitute 3,794,839,744 B. If `B` is obtained from a runtime free query after any KV or prefill buffer is already allocated, subtract only newly required owners; do not subtract those existing allocations a second time. No `B` in this formula is inferred from the historical `accounted=1,662,831,872` subtotal.

## Dedicated LM and remaining uncertainty

Releasing a decode-only LM/output-head allocation could increase the prefill budget only as a separate ownership/lifetime hypothesis: establish which exact allocation is resident, show that long prefill does not read it, retire it at a checked boundary, then use a fresh measured free query. The current report's no-decode-only-weights scenario is an input assumption, not evidence that current serving releases an LM allocation or gains its nominal byte count. It does not change the layer-major source allocation formulas.

The largest-layer/cache reservation uses all 512 packed blobs for one layer plus that layer's active dense/native tensors. The observed maximum native packed blob stride is 2,662,400 B and cache sizing is `512 * align_up(max_blob,256)` (`src/prefill/layer_major.inc:127-153`). The 64 MiB FP16-element scratch and 32 MiB GEMM workspace are in the prefill chunk count above; if the reservation is defined as a combined active-layer-plus-kernel-workspace term, do not add those same prefill owners again. Model dense weights, non-Prefill session state, MTP/cache/other shared allocations, native-library internals and runtime allocations are separate and must each be counted once or covered by a fresh free-memory query.

Nothing here shows that a full 262,144 physical input can be admitted, that K8V4 works through the configured SYCL resolver, that FP16 is numerically acceptable for long-layer residual storage, or that any prefill speed target is met. R676 notes that the hybrid K8V4 storage arithmetic has not been confirmed against a working configured-SYCL append/gather route. R674 is a separate future BF16 boundary-storage contract; it does not describe the already implemented FP16 option.
