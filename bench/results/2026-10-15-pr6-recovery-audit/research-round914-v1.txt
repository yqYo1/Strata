# Decision support: separating resource hypotheses for Mode1 QSA without OA counters

**Classification:** `decision_support=true`  
**Date:** 2026-10-16 JST  
**Scope:** bounded, read-only review of the live Mode1 prompt-attention path, its qualified component fixtures and prior controlled results, plus primary Intel/SYCL references. No build, test, device query, runtime, profiler, process inspection, product edit or Git operation was performed. The only new file is this report.

## Current evidence and limits

The current comparison target is `launch<1, true, false, 0, false>`: INT8 K/V inputs expanded into FP16 joint-matrix operands, Direct output, non-native conversion, current KMapping0, and scalar-per-head online softmax. The Main capture reports 60 QSA calls and 33.962851 s summed compute spans, with 77.31% compute / 9.11% copy inside its attention envelope; the pinned timeline receipt also reports 72 calls and 33.965628 s. Reconcile that count/time mismatch and use the actual call-shape/width records before deriving a per-call or workload denominator. These are overlapping service sums, not exclusive wall time or proof of a compute bottleneck. The current profile is instrumented, so its timing is not a clean speed sample.

The same capture reports 28.723 s issuing-thread CPU time outside explicit waits and 69.696 s inside waits. That split does not identify host submission as the cause: wait CPU may be completion polling, and outside-wait time includes more than queue submission. The fresh 252-sample ordinary-RAM copy proxy suggests under one second of plausible extra-thread headroom against a 4.85 s source-copy phase, but is not a live pinned/USM measurement. The unchanged 320 MiB transfer proxy is now 4.35 GB/s H2D and 3.89 GB/s D2H versus older 6.02/5.54; disabling its observer did not explain the drift. The reported sysfs PCIe x1/2.5 GT/s conflicts with attained copy rates and is not a usable ceiling. Keep PCIe and RAM evidence as controls; they do not justify another transfer-only optimization.

The tested OA path did not qualify collection. Its INVALID_ARGUMENT/TBS failures and two EACCES ioctls plus missing metric IDs bound that one path; they do not establish that all counters are unavailable. Main has stopped native-counter retries, so no permission, package or service changes are proposed. The Mode1 property row's 4,096 B local-memory create-time field and 128 register-file-size value are compiled-kernel metadata, not measured launch SLM, residency, occupancy or stalls. Intel's Xe2 capacity table uses B580 as its representative SKU; do not treat it as a B570 runtime query. The B570 product page lists 10 GB GDDR6, 380 GB/s, PCIe 4.0 x8 and 203 INT8 TOPS. That INT8 peak is inapplicable to this kernel's FP16-input/FP32-accumulate joint-matrix work; the bandwidth figure is a specification, not attained throughput. [B570 specifications](https://www.intel.com/content/www/us/en/products/sku/241676/intel-arc-b570-graphics/specifications.html), [Xe GPU architecture guide, 2025.2](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2025-2/intel-xe-gpu-architecture.html).

Source-level workload accounting is useful for denominators only. For selected width `s`, Mode1 requests about `1,056 × s` logical K/V code-and-scale bytes per query across both KV heads, and performs `6,144 × s` useful attention MACs (QK plus PV) across the 12 live heads. At `nq=256`, `s=2,051`, that is 554,459,136 requested bytes and 3,225,944,064 useful MACs. The kernel's hi/lo matrix passes, four padded rows, local staging and barriers add source-issued work; the useful count is not an achieved-work estimate. At 32 selected cells per tile the source has seven work-group barriers per tile, plus one before the loop. Neither source bytes nor barrier count proves DRAM traffic, SLM wait, matrix activity or occupancy. Intel's guide treats SLM as work-group shared storage and explains its size, banking and barrier costs; its examples are design guidance, not measurements of this kernel. [Intel Shared Local Memory guide, 2025.2](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2025-2/shared-local-memory.html), [SYCL thread mapping and occupancy, 2025.2](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2025-2/thread-mapping-and-gpu-occupancy.html), [Intel joint-matrix extension](https://github.com/intel/llvm/blob/sycl/sycl/doc/extensions/experimental/sycl_ext_matrix/sycl_ext_oneapi_matrix.asciidoc).

## Already answered; do not repeat

The current `prompt_k_cellmajor` fixture already exercises Mode1 and has a bounded `nq=256`, `cap=2051`, repeated component benchmark. Main's matched KMapping0/1 component result used 20 repetitions and three independent processes per arm, with full byte-identical output dumps. KMapping1 was 11.279% slower (median 396.634 to 441.371 ms); every ON sample exceeded every OFF sample. Keep KMapping0. This rejects the tested unpadded global-load ownership remap for that component. It does not diagnose cache misses or prove SLM pressure, and rerunning it will not resolve those questions. The padded pitch40 KMapping2 proposal remains a separate source-only candidate and is not a result.

The integrated subgroup-softmax path is also not a new correctness task: existing FP32/BF16 component gates cover the opt-in route, and the current profile used the default-off setting. It changes per-head score/max/sum reduction mapping and FP32 addition order; it adds no local arrays, work-group barriers, K/V reads, or matrix products. It can screen serial softmax service if the exact long clean comparison has not already done so, but any speed effect cannot be labeled a barrier reduction because the seven per-tile barriers remain. Existing long-clean receipts are 32K-prefill records; they are not the current 39K instrumented profile or a substitute for the official matched long-input gate.

The Main-owned HRows8 proposal v2 is a useful *later* work-group split control, not an occupancy measurement or a patch to apply as-is. It is pinned to commit `617647659f21487ff3bf61fa1fd4ba87ba2520bf`, older than the current live source. Its source predicts fewer local bytes per work-group (31,092 B versus 44,500 B declared for HRows16), twice as many groups, unchanged DPAS work, and duplicated query/K/V/scale/page work. Two HRows8 groups have a 62,184 B sum of source declarations versus the baseline's 44,500 B; that sum says nothing about simultaneous residency. If used, re-review/rebase the complete proposal against current sources, then run its smoke, full FP64 fixture and exact cross-process output gates first. The reported local-byte arithmetic is not compiler or runtime evidence.

## Small controlled sequence for Main

Run only after Main's serialized PR6 build/cohort closes. Keep separate owned processes, the exact binary/source/runtime/driver and fixed pre-exec environment; record each sample, clock/warm-up state, query widths/validity, queue, elapsed wall and issuing-thread CPU. No tracing in clean speed runs. Use the same actual token workload for any official long comparison, and keep component results as diagnosis only. Existing component tests can gate numerical equivalence; do not spend a model run on an unbuilt or unqualified candidate.

1. **Test working-set reuse with identical math and values.** The existing Mode1 fixture is a good scaffold, but its current benchmark sets widths 13 and 67 for queries 0 and 1, and its default page mask is not valid for every selected cell. Add a bounded benchmark mode that sets all 256 widths to 2,051 with every selected page resident. Use one selected cohort for all queries in arm A. In arm B, clone every selected K/V code and scale bit-for-bit into disjoint per-query replicas and translate each query's IDs to its own replica. Keep query tensors, selected width, page size, order, count, launch, number of calls and queue unchanged. Both arms then return byte-identical output and do the same logical work. The hot set is about 2.17 MB; the distinct-replica arm requests about 554 MB across the batch. Use three independent paired process runs in alternating AB/BA/AB order, one fixed warm-up plus 20 measured submissions each; preserve individual times and full output comparison. The existing fixture does not test this factor today: it cycles through only 2,113 logical cells, so its 128/256-query benchmark repeatedly reuses a small pool. A strong distinct-set slowdown supports sensitivity to address reuse/working-set locality (cache capacity, transaction locality or TLB effects); it does not measure cache hit rate or prove VRAM bandwidth saturation. No material difference weakens reuse as the explanation for this component shape, not global-load inefficiency in the actual model.

2. **Measure submission grain with the same query rows.** After reconciling the 60/72-call receipt, replay one fixed query/ID/step set with the same total work and addresses: one batch versus a small split such as four batches, all on the same in-order queue with one final drain. The live entrypoint submits one kernel per call and `finish(stream,event)` is a no-op for the supplied non-null queue, so this changes submission count without adding an inter-call synchronization. Choose batch sizes from the captured `nq` distribution where practical; a 256-query microbench is only a command-cost screen, not a 39K model proxy. Compare wall time, CPU time in submission/validation versus wait/polling, and device-span sums/union where the qualified timing capture exposes them. If wall/issuer CPU grows with call count while device-span sum stays stable, submission/control is material in that component; if device spans grow, split-grid scheduling or lost concurrency is involved; if neither changes, submission is unlikely to explain the measured QSA service. This does not allocate CPU time spent in index selection or expert work to QSA.

3. **Only if geometry remains plausible, screen HRows8 after its gates.** Compare current HRows16 with the reviewed HRows8 candidate on the same selected IDs/width histogram and K/V values, with Direct=1, Mode1, KMapping0 and softmax held fixed. Keep launches/call shape fixed and verify full outputs with the independent FP64 oracle before timing. The candidate's lower per-group source state and doubled group count can improve scheduling if per-group resource use limits throughput, while duplicated K/V work can hurt if global/cache traffic is scarce. A win despite doubled requested gathers favors a net grouping/scheduling benefit; a loss is ambiguous between duplicated traffic and lower per-group efficiency. Without valid residency/stall counters this comparison cannot name SLM or occupancy as the cause, and because barriers per group stay unchanged it is not a barrier microbenchmark.

The first two controls preserve matrix operation count and give direct tests of address reuse and call grain. If neither moves service beyond paired-run spread and source-proved selection/call overhead is small, the remaining compute-versus-SLM/barrier split is still **unresolved**. Do not infer XMX saturation from compute command share, published TOPS, copied bytes, property rows or a single saturated CPU thread. Preserve that limit rather than assigning an unsupported “compute-bound” diagnosis. Only a later qualified measurement path providing valid GPU activity/stall evidence, or a new candidate that changes one resource while holding the others constant, can make that distinction.

Any candidate that survives component screening still needs correctness/fault checks and repeated official >=32K long-prefill samples before a performance claim. None of these controls establishes full-model quality, 600/1000 tok/s, physical 262144-context correctness or RESTORE.
