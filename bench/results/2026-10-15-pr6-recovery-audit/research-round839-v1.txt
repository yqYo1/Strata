# R839 — Bank-aware local layouts for tiled GPU kernels

**Purpose:** knowledge collection. **Scope:** bank mapping and local-layout transforms for non-LLM multidimensional tiles. This is a public-source survey, not a device measurement or implementation recommendation.

## Why a layout can serialize

A bank conflict is defined per memory instruction or request: different lanes ask for different words serviced by the same bank, so the bank must issue additional conflict-free transactions. Identical-address reads may be broadcast and are not the same case. A useful scalar model is

`bank(a) = floor(byte_address(a) / bank_width_bytes) mod bank_count`.

For a warp of `W` lanes accessing word addresses `a0 + lane * S`, where `S` is a stride in bank-width words, the bank pattern repeats every `P = B / gcd(B,S)` lanes for `B` banks. If `W` exceeds `P`, lanes revisit banks; for `W=B` and scalar words, each bank receives `gcd(B,S)` distinct addresses. This is arithmetic for the assumed bank geometry, not a performance model for every instruction. NVIDIA’s current guide documents 32 shared-memory banks, successive 32-bit words assigned to successive banks, and serialization for conflicting distinct addresses. AMD’s MI-series guide uses a wave64 and 32 four-byte LDS banks, but additionally gives different lane-group rules for 128-bit reads and writes. A single `bank(a)` formula therefore cannot replace the instruction-specific contract of another architecture.

The transpose makes the phase dependence plain. Take 32 banks of four bytes, 32 lanes, and a 32-by-32 FP32 tile in row-major local memory. A row fill with lane `l` writing `tile[r][l]` sends lane `l` to bank `(32r+l) mod 32 = l`: all banks serve one lane. After transpose, lanes reading `tile[l][c]` use `(32l+c) mod 32 = c`: all 32 distinct words collide in one bank. The data is unchanged; lane-to-element mapping and which axis varies across the warp changed.

## Derived layout comparison

The table holds fixed geometry at 32 banks, four bytes per bank word, scalar FP32, and 32 lanes. The arithmetic illustrates two transforms against the same logical transpose. It does not assert the geometry of an unlisted device.

| Layout strategy | Physical bank mapping for logical `(r,c)` | Row-fill phase: lanes vary in `c` | Transposed read: lanes vary in `r` | Local storage and principal tradeoff |
|---|---|---|---|---|
| Compact row-major, stride 32 | `(32r+c) mod 32` | `l`: conflict-free | `c`: 32-way conflict | 4096 B. No extra address work; one phase serializes. |
| Row padding, stride 33 | `(33r+c) mod 32` | `(33r+l) mod 32`: conflict-free | `(33l+c) mod 32 = (l+c) mod 32`: conflict-free | 4224 B, 128 B more (+3.125%). Linear indexing remains simple, but pitch and alignment change. |
| XOR column swizzle, compact stride 32 | `((32r) + (c XOR r)) mod 32 = c XOR r` | `l XOR r`: a permutation of all banks | `c XOR l`: a permutation of all banks | 4096 B. Avoids padding, but logical neighbors may no longer be physically contiguous; address generation and vector accesses need checking. |

Padding changes row pitch from a multiple of 32 bank words to an odd stride. For a column read, banks become `l+c mod 32`, a bijection. In general, scalar lanes traversing rows with pitch `p` visit all `B` banks when `W=B` and `gcd(p,B)=1`. Choosing `p=width+1` works only when element size and width use the relevant bank words; 16-bit elements, 8-byte banks, vectors, and other bank counts change the equation.

The XOR example remaps low bank-select bits by row: `physical_column = c XOR r`. Varying either coordinate permutes banks, so both scalar phases are conflict-free without increasing the 4096-byte allocation. This assumes the coordinates fit the XOR domain and lane mapping matches the derivation. Other tiles XOR selected bits or pack vectors; “XOR swizzle” is not one universal formula.

## What changes the result

**Bank count and width.** Both are inputs to the index, not minor implementation details. If the number of banks is a power of two, an odd scalar stride visits every bank; stride 2 visits half, and stride 32 on a 32-bank design revisits one. With fewer active lanes than banks, a stride may revisit no bank in that request while leaving banks idle. If `W>B`, some lanes must revisit banks in a scalar request, but instruction-specific lane grouping may alter the serialization. On AMD MI-series, 64 wave lanes share 32 banks and 128-bit LDS operations use specified lane groups; counting one scalar bank per lane can misclassify vector instructions.

**Vector width and element width.** Convert byte addresses to bank-width words first. A lane owning `v` adjacent words has `v` bank positions, not one; depending on instruction lowering, those positions may be serviced as multiple bank-wide subrequests. Padding a row by one FP32 word can fix scalar column loads but shift each row start by four bytes, which can break an alignment assumption for a later vector load. Conversely, grouping adjacent elements per lane can reduce the number of lanes sharing a row segment while increasing each lane’s bank footprint. With 16-bit data, two values can share one four-byte bank word, so element-index arithmetic alone can mispredict packed accesses. Check operation width and that architecture’s conflict rule before claiming a vector pattern is conflict-free.

**Tile shape and lane mapping.** Padding cost is `rows * pad_elements * element_bytes`; its percentage is `pad_elements / logical_columns` for a rectangular tile. A 32x32 FP32 tile grows 3.125%, while a four-column tile padded by one grows 25%. The absolute 128-byte cost in the first example can be enough to cross a per-workgroup shared-memory allocation threshold when the kernel is already close to a residency limit; vendor CUDA documentation explicitly makes resident blocks depend on per-block shared memory and registers. That threshold example is a resource-risk calculation, not a measured occupancy loss. Small tiles can also fail to use all banks even after conflicts are removed. If lanes are reassigned to vary across columns instead of rows, the original compact layout may already serve a phase well, but the other phase changes too. Choose a layout against every local access phase, not a visual preference for row-major storage.

**Address cost and access phase.** Padding is constant-pitch arithmetic. XOR needs coordinate transforms and can make logical neighbors physically noncontiguous, obstructing vector operations. If the tile is touched once, accesses are already conflict-free, or address generation is limiting, remapping cost can exceed the saved serialization. A map that cures one phase may complicate another unless both are designed together. AMD’s MI-series CK-Tile example makes this concrete for 128-bit LDS operations: its `[64,32]` logical data mapped to `[64,4,8]` physical coordinates has conflict-free `ds_write_b128` groups but a two-way conflict for `ds_read_b128`. The post says padding can consume LDS and may not remove all conflicts; its XOR coordinate transform reindexes lanes and data to remove the described read and write conflicts without an extra buffer. These are vendor-described MI-specific instruction rules, not a generic GPU rule or a claim of measured speedup.

## Published measurements and limits

NVIDIA’s transpose article provides a controlled example of a measured padding win. It maps 32x8 threads to a 32x32 FP32 tile, with each thread processing four elements. On Tesla K20c, the coalesced transpose with a compact 32x32 tile measured 97.6 GB/s effective bandwidth; changing the local declaration to 32x33, which removes the 32-way bank conflict, measured 144.3 GB/s. On Tesla M2050 the corresponding numbers were 51.3 and 99.5 GB/s. The article reports ECC enabled and identifies effective bandwidth as twice matrix bytes over elapsed time. These are historical-device results, not a prediction for current GPUs. The article’s other copy and transpose comparisons show that bank repair is only one part of kernel performance.

An original study of configurable hash functions for banked GPU scratchpads reports broader evidence: its software bit-vector mapping improved benchmark speed by 23% on Fermi and 33% on Kepler, reducing bank conflicts by 96% and 99%, respectively. The paper also evaluates bitwise XOR hashes, but its software percentages are for bit-vector mapping, not the exact `c XOR r` mapping above. Its hardware results use Fermi-like GPGPU-Sim, not silicon.

A counterexample to “one layout is conflict-free” is the access-phase asymmetry above: compact row-major serves the row fill at one bank per lane and serializes the transposed column read; the AMD MI example serves its 128-bit write grouping but not its read grouping. A counterexample to blind padding is the 32x4 case: one extra FP32 column raises local storage by 25%, even before considering pitch/alignment or a resource-threshold crossing. Neither proves a benchmark loss from padding; both show why conflict count is not a complete cost model. XOR avoids padding but can add indexing or obstruct vectors. Select the smallest transform that resolves the measured phase while preserving other accesses, then measure the full kernel on the named device.

## Portability boundary

SYCL 2020 `local_accessor` provides device-local storage shared within a work-group but does not prescribe bank geometry or conflict-free layouts. Hardware-specific assumptions need separate evidence. NVIDIA and AMD sources establish only their documented architecture-family behavior; they do not establish Xe2/BMG geometry, implementation details, performance, or support.
