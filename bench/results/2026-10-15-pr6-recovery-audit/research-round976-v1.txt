# Packed QSA non-progress: source boundaries and decision

**Classification:** decision support. **Scope:** read-only review of the wave 976–978 receipts, their indexed predecessors, the measured source pins, and official SYCL/matrix API references. No build, test, replay, hardware query, process inspection, or product edit was performed.

## Decision

The packed run is a real owned-process non-progress failure and must remain failed. Its stack is in `cudaStreamSynchronize` from the native16 layer-major residual-bank callback, after the ordinary end-of-chunk drain has already returned successfully. With the recorded 32,768-row device residual prefix, that callback queues a device-to-device residual copy for rows 16,384–24,575, then drains the same queue. Layer 17 is GDN (`layer % qsa_interval == 1` for interval 4), so the wait is two layers after this chunk's QSA layer 15. On the source's same in-order queue, the previous QSA pack/matrix submissions should already have retired at the successful pre-callback drain. That makes the callback copy/queue retirement the closest source-level explanation; it does not prove the copy or driver is the culprit, and it does not justify attributing the wait to the packed QSA kernel.

No concrete bounds, scratch alias, event-order, or subgroup-barrier violation was found in the inspected path. The packed branch does introduce a distinct experimental matrix layout and local tile rearrangement, so an implementation-specific matrix/queue interaction remains possible, but the stack alone cannot establish it. The current long-prefill MoE tuning can continue with `bf16-prefix-optimized` and the existing shared queue. Keep `bf16-prefix-tilepack` out of that tuning configuration; the current code selects it only through the startup QSA-math setting. No driver-wide investigation is required to make that decision.

## Source path, storage, and ordering

`src/prefill/prefill.cpp:2601-2604` dispatches on the immutable startup selector `STRATA_SYCL_PREFILL_QSA_MATH`. Only the `bf16-prefix-tilepack` branch calls `qsa_bf16_prefix_tilepack_batch`; the optimized row-major arm calls `qsa_bf16_prefix_optimized_batch`. In `src/kernels/sycl/qsa_bf16_prefix.cpp:70-103, 316-322`, both instantiate `prefix_batch_impl` with score stride 33; the distinguishing template argument is `TilePacked=true`. The function first validates the existing query/pool contract and then validates that packed K, packed V, bad-row flags and output are disjoint from each other and from all input spans. It checks the scratch device spans before submission.

For each call, the first `parallel_for` (`qsa_bf16_prefix.cpp:106-134`) gathers resident paged INT8 K/V plus FP16 scales into logical BF16 prefix rows and writes an `int32` bad-scale flag per row. A second kernel consumes those rows in 32-cell tiles, maintaining FP32 online score/normalizer/accumulation. In the packed arm, the local Q, KV and probability tiles are rearranged for pair-interleaved/VNNI matrix loads and the B matrix uses `layout::ext_intel_packed` (`:169-181, 247-279`); the optimized arm keeps row-major tiles. The source uses the same 8×16×16 BF16/FP32 matrix combination and subgroup size for both. The local-accessor payload grows from 28,160 to 28,224 bytes with score pitch 33; `matrix_available` checks the device combination, subgroup 16, workgroup limits and local-memory requirement before submission. I found no obvious out-of-range indexing: the live-page extent bounds `active_rows`, allocation reserves both BF16 tensors and flags through the whole request, and all layers/chunks reuse them serially.

`run_layer_major` allocates this prefix storage as a separate `cudaMalloc` owner for the long-prefill lease, with K, V, and flags at aligned offsets (`src/prefill/layer_major.inc:414-422`). `PrefixBorrow` restores the borrowed field only after the checked lease drain; the lease aborts rather than free temporary owners if drain cannot be proved (`:384-398, 349-355`). This is separate from the measured `STRATA_SYCL_PREFILL_SCRATCH_ALIAS=1` arena optimization. That setting aliases the FP32 `mixed`, `bo`, and PLE input views to `emb` (`src/prefill/prefill.cpp:758-771, 1040`); it does not alias the separate QSA prefix scratch, the residual bank, or the callback destination. Native16's `R16/gated_b16` split also fits disjoint halves of the original `gated` reservation (`:947-955`). The same alias setting is present in both optimized and packed receipts, so it is not the arm delta. The prefill's explicit alias mode is admitted only for an explicit in-order queue and full unsplit single-GPU topology (`prefill.cpp:793-812`); the long layer-major path separately requires `m.copy == m.cs` (`layer_major.inc:74-86`).

For SYCL, initialization sets `m.copy = m.cs` (`src/prefill/prefill.cpp:840-845`). `queue_for(stream)` rejects a queue without `property::queue::in_order`, and `finish(stream,event)` deliberately does not host-wait for explicit streams (`include/strata/sycl/launch.hpp:47-62`), so the pack kernel followed by the matrix kernel depends on ordered submissions to that same queue. The layer-major callback path also shares that queue: `run_impl` first calls `cudaStreamSynchronize(m.cs)` at the chunk boundary and only invokes `on_chunk16` if it succeeds (`src/prefill/prefill.cpp:3502-3525`). At the intermediate-layer callback, `plan.span` chooses the device prefix, then `cudaMemcpyAsync(dst,residual,...,DeviceToDevice,m.cs)` is submitted and `drain()` calls `cudaStreamSynchronize(m.cs)` again (`src/prefill/layer_major.inc:608-638`). `cudaStreamSynchronize` calls `wait_and_throw` on the registered queue (`src/sycl/compat.cpp:332-338`). For row 16,384, count 8,192 and `R_GPU=32,768`, the span is entirely device-resident. The blocked queue wait is at this second drain. There is no queued QSA kernel newly submitted between the successful first drain and this residual-bank copy.

Khronos SYCL 2020 revision 12 specifies that an in-order queue executes its commands in submission order and that `queue::wait_and_throw` blocks for previously submitted commands; it expressly gives no ordering guarantee across different queues. This supports the source reasoning but cannot validate a vendor runtime's internal completion behavior. Intel's oneAPI GPU Optimization Guide, 2024.1 joint-matrix example uses `layout::ext_intel_packed` for a B operand already VNNI-packed and shows a `stride` doubled for pair packing. That makes the source's packed layout a plausible implementation contract, not proof that this exact generated kernel or 2026.1 runtime is correct. The extension is experimental and version-sensitive.

## What could explain the wait, and useful next evidence

Ranked from this evidence:

1. **Callback copy or queue retirement failure is the closest fit.** The last source command between the completed chunk drain and blocked callback drain is the BF16 residual-bank copy. The generic queue-finish stack cannot say whether the copy engine, queue fence, or driver made no progress. The source does not reveal a bad pointer or lifetime: the span is checked, destination storage is owned through the layer lease, and source is not reused until the same queue drains.
2. **An earlier packed matrix submission may be a contributing trigger, but the current evidence does not locate the wait there.** Tilepacked A/B layout, matrix load/MAD implementation, local memory/barrier interaction, or a runtime queue state issue are unique to that arm and remain candidates for a packed-only symptom. Yet the same queue's pre-callback drain returned successfully and the current layer is GDN. The inspected workgroup barriers are outside conditional producer blocks; matrix operations are called uniformly within each participating subgroup. I found no concrete divergent barrier or source-level layout/extent violation to elevate to a confirmed cause.
3. **An allocation/alias fault is less supported.** QSA transient scratch is separately allocated and alias-checked; its lifetime is guarded until queue retirement. The explicit embedding aliases are shared by both arms and are serialized by the in-order queue and chunk drains. A runtime-level invalid USM mapping cannot be excluded from source alone, but there is no receipt evidence for one.

Existing QSA markers already count real dispatches and layer/chunk queue intervals, but their intervals include submission gaps and are nonexclusive. More aggregate queue timing or MoE-shape census will not identify the command that failed to retire. If a future tilepack-specific decision actually needs another diagnostic, keep it to one owned, bounded process and add host-only sequence records at five existing boundaries: before/after QSA pack submission; before/after matrix submission; the successful chunk pre-callback drain; the callback's copy kind/span/bytes and submit status; and the callback drain result. Include layer, chunk row/count, QSA index, active rows, and a monotonically increasing call ID. This would tell whether the last QSA work retired before the copy wait and whether the copy was actually submitted; it still would not identify an instruction in a non-progressing kernel. Avoid adding a marker kernel or a new synchronization edge because that can alter the queue sequence and symptom. Retain only the compact host record and a representative failure stack.

## Decision for ongoing MoE tuning

The sufficient operational gate is explicit: use the completed `bf16-prefix-optimized` setting for the current long-prefill MoE tuning run, keep the `bf16-prefix-tilepack` selector out of its child environment, and keep the environment immutable after runtime initialization. Continue to record that run's independent profile/census as diagnostic data, not adopted speed. The previous tilepack clean samples remain true passes, the new packed profile and pair remain failures, and the post-stop health checks remain recovery evidence. This separates the unadopted experimental QSA layout from the optimized MoE path without requiring a broader driver investigation. Revisit tilepack only if a concrete adoption decision needs it; first target the callback copy boundary shown by this stack.
