# R924 — Subgroup roles and software pipelines for irregular gather plus matrix kernels

2026-10-16 JST. **Knowledge collection; source and literature review only.** The finite question was whether a loader subgroup can safely feed matrix-consuming subgroups inside one SYCL work-group, when overlap is possible without a dedicated transfer engine, and what synchronization, storage, or scheduling costs can erase it. This is reusable architecture knowledge, not a product proposal or B570 performance result. No builds, tests, device/runtime queries, profiling, process inspection, Git operations, product edits, cleanup, CUDA/HIP implementation, or validation were performed. No XeStrata material or implementation source was used. This report is the only new file.

## Current-kernel boundary and prior work

The current `prompt_attention.cpp` source uses `HD=256`, `CH=32`, `WG=128`, and required subgroup size 16: one work-group has eight subgroups. For each selected-cell tile it resolves shared row IDs, gathers K and scales into local memory, executes QK matrix work only for `subgroup < 4`, updates online softmax, gathers V into the same `kv` local tile, then executes PV matrix work in all eight subgroups. Work-group barriers delimit the local-tile handoffs. The matrix extension in use is subgroup-scoped; source-level `joint_matrix` operations are collective within each participating subgroup.

The dispatch context identifies the current Mode1FloatQSA variant as `launch<1,true,false,0,false>` and records 60 calls / 33.963 s for its current attention observation. Treat that as the stated aggregate service boundary only: it is not an isolated kernel measurement, does not establish that gather or synchronization is the bottleneck, and is not whole-prefill throughput. The accompanying 44.5 KB local-argument observation is not an occupancy measurement.

The indexed work already covers adjacent concerns. R714 considered access remapping and a possible next-K overlap; R745 specifically analyzed double-buffering next K against current PV and its added 16 KiB half tile, synchronization, and resource risk; R746 counted source-level work without claiming hardware utilization; R749/R750 reviewed a rejected heads8 proposal; R902 prohibits turning kernel properties into occupancy claims; and R914/R916 distinguish working-set reuse and enqueue-grain tests from hardware-resource conclusions. This report does not renew any of those experiments. Its distinct question is whether idle QK subgroups in the current work-group can stage the *same tile's V* while the other QK subgroups consume its K tile, and what that implies for correctness and actual overlap.

## What SYCL and the Intel matrix interface guarantee

The oneAPI `joint_matrix` extension is experimental and describes `joint_matrix` as a group-shared matrix object. In the extension version reviewed (revision 12, 2024-06-14), the supported scope is `sycl::sub_group`; constructors and operations such as load, fill, multiply-add, and element-wise apply are group functions that must be reached in converged control flow by all work-items of that subgroup. The runtime query advertises legal element types and shapes; support for a family or compiler target is not proof that a particular B570 driver and binary supports the needed combination. A consumer subgroup cannot have some lanes diverted to load data while the rest of that same subgroup execute the matrix collective.

SYCL group functions also impose convergence. `group_barrier` waits for every work-item in its specified group and supplies acquire/release memory ordering for accesses around the barrier. A subgroup barrier cannot publish one subgroup's SLM writes to different consuming subgroups. Thus a loader-subgroup-to-matrix-subgroups handoff through `local_accessor` needs a work-group synchronization edge after the producer stores and before the consumers read; a separate edge is needed before that buffer is overwritten after all consumers finish. Put these barriers outside role-specific branches so every work-item in the work-group reaches them under the same loop conditions, including a partial or empty final tile. Never let an early `return`, data-dependent branch, or role-specific loop skip a barrier or a collective.

Reductions have the same scope discipline. The current query magnitude uses a work-group reduction, so every work-item must continue to participate in that operation; a loader role cannot skip it. The optional softmax uses subgroup reductions and every lane of each participating subgroup must call the same reduction sequence. The QK branch on `subgroup < 4` is subgroup-uniform, so its matrix collectives can remain converged while other whole subgroups do independent work. That structural legality does not promise that the different subgroups issue instructions concurrently.

Intel's GPU optimization guide describes subgroups as SIMD lanes in a VE thread and explicitly says the mapping of work-items/work-groups to VEs is implementation-dependent. The guide's example and SLM discussion warn that work-group barriers are required when synchronization crosses subgroup boundaries and that barriers cost time. This is qualitative execution-model guidance from an older guide, not a B570 timing or mapping guarantee. A source `if (subgroup < 4)` permits distinct roles; it does not reserve a VE for the loader or a matrix engine for the consumers.

## Feasible overlap patterns without assuming TMA

**Same-tile V staging during QK is the most concrete role split.** K and V addresses share the already resolved `rows` array, but K must remain readable while the QK matrix consumers run. A producer therefore needs V storage that does not alias the active K tile. One straightforward representation is a second half tile; in this source shape it adds 32×256×2 = 16,384 bytes of declared local data before compiler or alignment effects. A more compact int8 V staging area could use half that code payload, then reuse the existing half `kv` area to convert after the K readers have finished. That trades local bytes for an extra local read/write and conversion phase. Scales have their own `vs` area and could in principle be populated while QK runs, but only after proving that its prior-tile lifetime has ended. These are storage alternatives to reason about, not implementation claims.

The phase/lifetime edges for such a design are: (1) all work-items resolve and publish `rows`; (2) all work-items stage K and any K scales; (3) a work-group barrier publishes K; (4) QK subgroups read K while loader subgroups gather V codes/scales into distinct V storage; (5) a work-group barrier waits for both QK score publication and V writes; (6) softmax and any V conversion/scaling complete; (7) a work-group barrier publishes the matrix-ready V tile; (8) PV subgroups consume it; and (9) a work-group barrier completes all PV reads before either tile/row metadata is reused for the next iteration. The exact order can be simplified only if source lifetimes prove a dependency absent. Each barrier also waits for the slowest subgroup, so V gathering that outlasts QK remains fully exposed at the handoff.

This schedule can overlap in principle even with ordinary global loads: loader subgroups issue address, page-table, code, scale, conversion, and local-store instructions while other subgroups perform QK. It is software scheduling plus outstanding memory-level parallelism, not an independent data-movement engine. The potential removed from the QK-to-PV dependency path is the portion of V gather/conversion time hidden by QK. No global bytes are removed. It only helps if V work has material exposed latency, QK offers enough independent duration, both phases use compatible hardware resources, and the load stream does not compete enough for memory/issue capacity to slow QK. It can lose when QK is short, page gathers are already hidden, global memory is saturated, QK matrix issue and V address/load instructions contend, the subgroup split gives the producer too few lanes, or the extra live tile reduces work-group residency. Those conditions require component evidence; declared SLM and GRF metadata cannot stand in for achieved occupancy or bottleneck counters.

**Next-tile software double buffering is a separate pattern.** It needs the next tile's row indices and K/V data to be available while current computation runs, which means two buffer lifetimes and a producer/consumer protocol across iterations. R745 already documented this candidate and its storage cost. The current gather is indexed by irregular selected rows and includes page lookup and quantization conversion, so a regular contiguous-copy primitive cannot by itself replace the gather. This report does not recommend repeating R745's candidate or assume its result.

## Asynchronous APIs, hints, and hardware differences

The SYCL reference still documents `group::async_work_group_copy` returning a `device_event` that can be waited on, but marks the API deprecated in SYCL 2020. That contract supplies copy completion ordering; it does not specify a dedicated copy engine, independent issue, or achieved overlap for a particular compiler/backend. The source operation here is an irregular page-table gather plus per-element conversion, not a simple contiguous tile copy. Treat any use of this API as a compiler-lowering question: check the exact DPC++/IGC/runtime implementation, accepted types/address spaces/shape, generated device code, and whether unsupported cases are rejected or lowered to ordinary work-item loads/stores. No evidence reviewed here establishes a CPU fallback or emulation path for this kernel, and none should be assumed. The kernel's gather, conversions, reductions and matrix operations are authored as device-kernel work; queue submission alone does not prove a particular operation uses a hardware engine.

Intel's oneAPI `prefetch` extension defines individual and cooperative prefetches as hints. The note for `joint_prefetch` says it is equivalent in effect to calling prefetch from all group members, with some implementations possibly issuing it more efficiently; `joint_matrix_prefetch` is a cooperative cache prefetch for a matrix-shaped global-memory region. Neither API returns a completion event or writes the target bytes into the work-group's SLM. It therefore cannot replace a V producer plus SLM store/barrier. A prefetch may help only if an indirect address is already known and the target cache behavior is useful; it does not resolve IDs or dequantize values.

The contrast with NVIDIA Hopper is instructive but not transferable as a mechanism. NVIDIA's Hopper guide documents TMA as a dedicated asynchronous engine for 1D–5D tensor transfers between global and shared memory; a thread can issue a transfer while the block executes other work, then synchronize at consumption. Such engines reduce per-thread transfer instructions. The Strata input path is an indirect set of page-table-resolved selected rows, not one regular tensor slab, and the reviewed Intel/SYCL sources do not establish a B570 TMA-like per-work-group transfer engine. TMA results and code should not be ported as if the same facility existed.

For a non-LLM GPU/HPC comparison, Bauer, Cook, and Khailany's SC'11 CudaDMA paper describes software-emulated asynchronous DMA using specialized warps, producer/consumer synchronization, and shared-memory buffers on NVIDIA Fermi, for SGEMV and scientific stencil/finite-difference workloads. Its lesson is that role specialization can expose memory-level parallelism without a dedicated copy engine, but the roles still issue ordinary GPU instructions and require explicit full/empty lifetime handshakes. Its evidence is not portable performance evidence: more DMA warps sometimes oversubscribed memory; double buffering could be slower than single buffering; and benefit decreased at high compute intensity as coordination/MLP needs changed. The paper uses PTX named barriers, which are not a portable SYCL recipe. It is an architectural comparison only; no implementation code was copied or adapted.

## Retrieval and decision limits

The best future consumer for this report is a concrete Main decision after a fine QSA profile shows whether V gathering is on the critical dependency path while QK has independent work. If that evidence appears, compare the baseline against one opt-in same-tile V-role experiment while keeping the work-set, queue grain, chunk shape, matrix configuration, and whole-prefill measurements fixed by Main. Gate first on correct buffer ownership/lifetimes and supported runtime matrix combinations; measure issue/wait and local-memory effects as well as component latency; then separately evaluate long-prefill, numerical quality, RESTORE, and physical-262144-context requirements. A kernel-only gain would not establish a whole-prefill gain.

No B570 capability, actual subgroup concurrency, async-copy lowering, SLM occupancy, memory bandwidth, barrier stall, matrix utilization, bottleneck, speedup, or inference adoption is established here. The report contributes a safety model and conditional schedule only.
