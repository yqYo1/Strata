# R935 decision support: BF16 QSA component result and the next gate

## Decision

Yes. The closed 8,192-query comparison supplies enough evidence to ask Main to run a full long-prefill candidate gate for this independently authored BF16 QSA path, behind an explicit opt-in. The 0.765% lower component latency than the FP32 arm is small, but it is repeatable across three clean processes and is larger than the observed between-process spread; the 7.701% improvement over the older typed-BF16 path is also repeatable. This is a reason to measure the complete model path, not to select the candidate for production. The component result gives no model tok/s, output-quality, RESTORE, full-context, or production-path evidence.

The appropriate comparison remains the existing FP32 QSA route versus this candidate on the same long-prefill workload. Keep FP32 available as the diagnostic and control route. The old typed-BF16 result is useful counterevidence about that particular older implementation, but it does not show that BF16 operands are intrinsically faster: the candidate changes multiple details of the matrix path, operand conversion and local online state at once.

There is a reason to spend a full-model gate on QSA even though the measured delta is only 0.77%: the R931-reviewed R928 profile measured 33.962851 seconds of QSA attention commands in a 39,262-token input, within 105.006826 seconds of instrumented host prefill. That profile is from an earlier route and is an aggregate, not a prediction for this candidate or an attribution to one operation. It makes QSA worth measuring in the complete dependency path; it cannot be multiplied by this component percentage to promise a model gain. Earlier synthetic working-set and command-grain results also do not explain this new delta or identify physical traffic, utilization, or a bottleneck. The BF16 result stands on its own matched completion-time evidence.

## What the closed cohort establishes

`qsa-bf16-matched-bench-summary-v1.json` contains three independent processes per arm and ten timed repetitions per process, with the arms interleaved in the recorded order. The per-process medians were:

| Arm | Three process medians (ms) | Median (ms) | Comparison |
|---|---:|---:|---:|
| New BF16 operands / FP32 online state | 627.165, 627.525, 627.346 | 627.346 | — |
| Existing FP32 path | 632.445, 632.001, 632.184 | 632.184 | BF16 latency −0.765%; 1.0077× inverse-latency speed |
| Existing typed-BF16 path | 679.691, 679.607, 679.715 | 679.691 | BF16 latency −7.701%; 1.0834× inverse-latency speed |

The candidate process-median range (627.165–627.525 ms) does not overlap the FP32 range (632.001–632.445 ms). The summary reports process-median standard deviations of 0.180 ms for BF16 and 0.223 ms for FP32; their median difference is 4.837 ms. That supports a stable component timing signal in this harness, although only three process medians per arm are available and the small percentage does not predict an end-to-end gain. The typed path is slower by 52.344 ms at the median; that stronger result is about these two kernels and this fixture, not BF16 arithmetic generally.

All arms ran the same 8,192-query, cap-2,051 frame with 16,384 workgroups and 2,113 cells. They shared identical Q/K/V, scale, table, selector-ID, and step fingerprints and the same 673,565,908-byte allocated footprint. The harness used two warmups and ten timed repetitions per process. The 8,192 × 2,051 selector IDs were the same ordered, unique deterministic sequence for every arm (`selected_set=shared_ordered_unique`); they were supplied to attention, not produced by the runtime selector. Main reports that all nine owned receipts closed PASS, with exact frame and allocation fingerprints, no fresh faults, and no remaining owner process. Preserve the receipts and their existing statuses byte-identically.

The timing clock covered host enqueue followed by `rt->wait()`. Median enqueue wall time was about 0.09 ms in each arm; nearly all of the observed 627–680 ms was in the wait interval. The measured thread CPU time during that interval was also nearly the full wall wait, consistent with a host thread polling for completion. So there is little evidence that submission overhead explains the between-arm gap, but the harness does not split GPU service time from host polling or establish which GPU work accounts for it. Read this as stable host-observed completion latency for one QSA component, not as measured GPU arithmetic utilization, memory traffic, or device service time.

The three-process medians are interleaved across arms, which reduces simple clock-order bias, but each arm still comes from separate processes and only 30 timed samples. There is no paired per-run estimate or formal confidence interval. The non-overlapping process-median ranges and the nearly identical results across each arm are enough to justify the next gate, not enough to rule out behavior changes under a live model's memory pressure, other queue work, or prompt/state conditions. The harness intentionally allocates all arms' backing buffers in every process to equalize pressure. That is a comparison control, not a model-faithful live working set; the production path will have a different mix of active query/output storage and cached state.

The exact shared selector IDs make the comparison useful: they hold ID production and selected-cell order constant, so differences arise in the attention consumer path under the matched frame. They do not validate selector correctness or cost, demonstrate parity with SGLang's block-plus-tail selector, or show that a model produces this particular ID distribution. Likewise, equal allocation fingerprints control the harness footprint; this is not proof that a live full model has the same residency, transfers, cache reuse, or lifetimes.

## What the oracle proves and leaves open

Only the new BF16 arm was compared with the BF16-operands/FP32-online scalar contract oracle; the FP32 and typed-BF16 arms retain earlier qualification and were not compared to it (`compared=0` in their receipts). The oracle checks all 24 heads and 256 dimensions for four complete queries—0, 1, 2, and the last query—for 24,576 output values total. It finds all finite, with maximum absolute error 6.103515625e-05 and maximum budget ratio 0.976287919023. The candidate output is bit-repeatable over the full final frame, guards and input bytes remain unchanged, and the smoke/diagnostic checks pass. This is meaningful evidence that the matrix kernel implements the stated BF16 operand boundary on the fixture.

The scalar oracle is independently written and does not reuse the GPU tiling or matrix-fragment reduction. It computes the scaled BF16 Q and dequantized BF16 K/V contract, keeps online max/normalizer/weighted accumulation in FP32, rounds probabilities and output to BF16, and permits a BF16-spacing allowance for reduction-order differences. The maximum observed error is near the stated budget, so this is a contract check with an explicit tolerance, not bitwise agreement. It covers four queries rather than every query's numerical output, does not compare against a reached SGLang output, and says nothing about whole-model logits, generated tokens, task quality, recurrent/shared state, or RESTORE. The deterministic full-frame output hash is useful for repeat checks, not an accuracy metric.

A separate component case exercised `cells=262144`, cap 2,051, one query, guards, and input integrity. It establishes a component bounds case only. It does not exercise all layers, selector and cache producers, full-model scheduling, persistent state, the full 262,144-token physical endpoint, RESTORE, or the entire model lifetime graph. PASS here cannot replace those gates.

## Contract comparison and provenance

R931's reviewed QSA sections (13–17 and 21–29, applying R928-C1 through C6) identify the pinned SGLang Qwen4-Exp sparse-attention contract as a source-level reference. At immutable SGLang commit `877be2974aa151a984e52822c028276c2b1e9303`, `sparse_attn.py` loads Q in its tensor dtype, multiplies Q by the attention scale and `1.4426950408`, then casts the scaled Q back to that dtype before the QK dot. The online maximum, normalizer, and value accumulator are FP32; probabilities are cast to the value dtype for the second dot. The prefix pack path casts K/V to Q's dtype. This means FP32 online accumulation does not imply FP32 Q/K/P operands and does not require a high/low FP16 product path.

The candidate follows those key operand boundaries when the framework's actual query dtype is BF16: it starts with BF16 Q, multiplies by the fixture's scale (`0.0625`) and log2 conversion factor, and rounds Q to BF16 before QK; it rounds P to BF16 before the V dot; and it keeps online max, normalization, and matrix accumulators in FP32, with BF16 output. Those are the reasons the candidate merits a full gate under the current numerical policy.

There are material differences to test at model level. Strata's candidate still reads its INT8 K/V cache with FP16 per-64-dimension scales, decodes each operand, then rounds the decoded K/V to BF16 before the matrix operation. SGLang's reached source path uses Q-dtype K/V (and the prefix pack casts to Q dtype); that is not the same cache representation or quantization history. The candidate also uses a 32-cell online step, a serial per-lane probability sum, and an explicit FP32 FMA for the normalizer update. The source contract uses its own Triton reduction/tiling order. Both preserve FP32 online state, but they need not produce identical rounding. The component oracle validates the candidate's own operator contract; it does not establish that Strata's K8V8 decode-plus-BF16 rounding is numerically equivalent to the framework's storage path.

No local evidence establishes which SGLang model configuration, query dtype, prefix/no-prefix branch, or backend was reached on this PC. The source contract is a reference only; do not report this as a tested SGLang CUDA comparison. Before using framework alignment as a numerical claim, Main should record the actual model/config dtype and reached attention branch. No vLLM source claim is needed for this narrowly scoped Qwen4-Exp question.

## First Main-owned experiment and gates

The first discriminating model experiment should be one explicit-opt-in, matched BF16-QSA-versus-existing-FP32-QSA full long-prefill comparison on the same committed model, prompt, context, chunking, and runtime settings, starting with the official `bench.sh` long32K+ workload. Run arms in separate owned processes with the same input/state fixture and capture individual complete-prefill samples. This tests whether the component signal survives projection, selection, other layers, transfers, and the full dependency path. Record total prefill tok/s and wall time, per-layer candidate dispatch/call coverage, and any component timings only as supporting attribution; do not infer an end-to-end result from the QSA delta. Follow with repeated clean-process samples before considering a speed claim. Do not change selector semantics in this first discriminator.

Keep the adoption gates distinct:

1. **Numerics and task quality:** record the actual SGLang dtype/branch contract if available; compare candidate and baseline model outputs/logits or logprobs on matched prompts, then run the relevant task-quality checks. Preserve the existing FP32 route as diagnostic evidence. Do not add exact FP32/ggml parity as a separate adoption requirement if the candidate follows the validated framework contract; record deviations and the agreed tolerance prospectively. A passing four-query component oracle is not a model-quality pass.
2. **RESTORE, state, and lifetime:** exercise save/restore and resumed long-prefill using the candidate, checking that query/output buffers, selector IDs, page mappings, K8V8 scales, and shared/persistent state remain valid until all queued consumers complete. Compare resumed results with the matched baseline under the same numerical policy. The component harness's synchronous completion and buffer checks do not prove model-path cross-queue or restored-state lifetimes.
3. **Fault and ownership:** for each owned model run, capture fresh before/after fault evidence, exact process identity/start time, normal exit, cleanup and no-survivor state; retain progress and fault findings with the run receipt. A no-fault component receipt is not a model-run fault check.
4. **Physical 262,144-context correctness:** separately run the whole model at the exact physical context limit, through selector, KV/cache, QSA, state, and completion paths, with bounds/guards and lifetime checks. The one-query QSA component case is not a substitute. Keep this correctness gate even if the 32K+ speed/quality gate passes.
5. **Performance decision:** require repeated clean official full-prefill samples with the candidate actually dispatched and all phase measurements retained. The candidate must improve the complete long-prefill path without unacceptable quality or lifecycle regressions. Keep it opt-in until those gates close; do not use this component timing to change production selection or short-input/decode dispatch.

The competing choice—keep FP32 as the only selected route—remains reasonable if the full model gains disappear or numerics/state gates fail. The existing typed-BF16 route is not supported by this timing cohort. An opt-in full prefill gate is the evidence-based next step because the new route is faster in a stable matched consumer test and follows the important SGLang BF16 operand/FP32-state boundaries, while its model-level benefit and storage-path numerical behavior remain unproved.

The full-frame hashes reinforce this boundary: the BF16 candidate repeats with hash `16890872196701900771`, while the FP32 arm repeats with `8236143855088747333` and typed BF16 with `12376158063389020593`. Those distinct hashes are expected because the arithmetic and output dtype differ; they show deterministic per-arm outputs, not candidate parity or quality. The benchmark does not include indexer work, real selector computation, model-layer scheduling, or downstream consumers. A live full prefill may expose a regression from extra conversions, incompatible hidden-state consumers, queue placement, or a changed residual boundary even while this isolated matrix consumer remains faster.
