# R811 — Xe2/BMG 2D block load, store, and prefetch contracts

Purpose class: **knowledge collection**. Main body read: **not required now**; retrieve only when a concrete 2D block-I/O implementation or safety review is active. This is documentation/source research, not an implementation proposal. No build, test, device query, profile, runtime, performance, or model-quality work was run; all such results are **UNRUN**. The supplied native16 GEMM slowdown is context only and was not reproduced or analyzed here.

## Question and source boundary

The question is what a later owner must establish before using Intel Xe 2D block messages for BF16/FP16 GEMM operands and output tiles on Xe2/BMG, especially for ragged dimensions and a K-prefetch loop. The pinned SYCL*TLA snapshot is the exact `intel/sycl-tla` commit `87f6850680a580654b9ea2c80dbc01aeb36ad231` (2026-08-10). It is useful for concrete CuTe/TLA setup and assertions, but its documentation describes PVC-origin 2D messages, and its helper checks do not prove every BMG hardware minimum. The Intel LLVM ESIMD API reference was pinned to `intel/llvm` commit `b29c1834fc5795c9748173a1b3ab48e3d75abd28`, the `sycl` branch head observed 2026-10-15. Treat those ESIMD requirements as the public API contract; the TLA snapshot is an implementation contract for that snapshot, not a substitute for capability detection on the runtime device.

## Separate message geometry from allocation geometry

Intel LLVM names `BlockWidth` in **elements**, `BlockHeight` in **rows**, and `X` in element coordinates. The same API names `SurfaceWidth` and `SurfacePitch` in **bytes minus one**, and `SurfaceHeight` in **rows minus one**. Thus for element size `b`, logical row width `W`, row count `H`, and physical row stride `P` elements, a matching descriptor uses `(W*b)-1`, `H-1`, `(P*b)-1`; the operation's tile width remains an element count. Zero width or height cannot be passed by blindly subtracting one into the unsigned descriptor fields: the caller must skip or reject an empty operation first.

The dimensions in a descriptor describe the surface visible to this message. They do not discover the allocation size, prove that the pointer names a live allocation, or authorize an operation past the allocation. The allocation must contain every address that the descriptor and pitch can reach. If rows have padding, logical width and physical pitch are distinct. TLA's `Xe2DTraitsBase` forms width from the tensor's X-mode shape, height from its Y-mode shape, and pitch from the Y-mode stride, then builds the payload with each quantity minus one. For outer modes it may advance the base pointer while retaining those 2D extents. A caller using a view, submatrix, or outer-mode offset must verify that every adjusted base still has the full described surface behind it.

Pinned TLA documentation states a 64-byte-aligned base, 16-byte-aligned stride (with a note that some PVC cases accept 4 or 8), 4-byte-aligned width, width/pitch limited to 2^24 bytes, and height limited to 2^24 elements. The pinned traits helper's optional assertions are not identical: they check base `%64`, width `%4`, pitch `%4`, and width/height/pitch `<= 0xFFFFFF`; when it adjusts an outer-mode base, it checks that added byte offset `%64 == 0`. The code does not assert a 16-byte pitch. Keep this docs-versus-helper gap visible: 16-byte pitch is the conservative documented guard, while relying on only four-byte pitch for BMG needs direct validation. These assertions are debug-only behind `CUTE_ENABLE_XE_BLOCK_2D_ASSERT`; they are not runtime bounds protection.

## Message shape and clipping contracts

The ESIMD `load_2d` API is gated by the device's `has_2d_block_io_support` descriptor. It disallows simultaneous transpose and VNNI transform, caps a message at 2048 bytes, limits height to 32, and sets width/count limits by message element size and mode. For plain 8/16-bit loads, block width is at least 4/2 elements and width times block count is at most 64/32; block count is 1, 2, or 4. Plain 32/64-bit loads allow at least 1 element and width times count at most 16/8, with count 1 or 2/1. Transformed 8/16-bit loads have narrower width ranges (4–16/2–16) and heights 4–32/2–32. Transpose load is documented only for 32/64-bit values. `store_2d` has a separate, tighter 512-byte message limit, height at most 8, and per-element width maxima 64/32/16/8 for 8/16/32/64-bit values. `prefetch_2d` has no transform or transpose parameter, requires cache-hint properties, and uses the plain width/count limits and 2048-byte cap. These are API restrictions, not proof that every supported tuple is efficient or enabled on a particular BMG driver.

The pinned TLA Xe rearchitecture page describes hardware 2D messages as bounds checked, says out-of-bounds global accesses are removed, and specifically says out-of-bounds **loaded** elements are filled with zero. The LLVM API description does not spell out the edge result for any 2D operation; its store signature has no mask and its prefetch signature has no mask or result. Therefore the safe claim is limited: TLA documents zero-fill for OOB loads, and describes general OOB access suppression; no independently explicit API statement here defines store edge behavior or what an OOB prefetch does. Do not use an unverified store-clipping assumption as a tail mask, and do not use prefetch as a bounds guard. A future tile prefetch should be issued only when its origin is in range unless a BMG-specific contract has been established.

## Three Strata mappings to check

| Operand/output | Descriptor mapping | Concrete hazard and conservative action |
|---|---|---|
| Activations `[T,K]` | X=K, Y=T; width `K*b`, height `T`, pitch `stride(T)*b`. | With BF16/FP16, ragged odd K gives a two-byte-multiple width that may fail TLA's four-byte width check. For 8-bit values K must make width a multiple of four. Pad the actual row storage with initialized zeros or use a scalar/other tail path; do not describe nonexistent padding as the surface. A last K tile may zero-fill on load only if the logical surface dimensions are correct and runtime behavior is qualified. |
| Weights `[N,K]` | X=K, Y=N; width `K*b`, height `N`, pitch `stride(N)*b`. | The same K alignment applies; ragged N is a row tail. Plain/TLA tile height is bounded and hardware load clipping is documented only for load results. If a `[N,K]` source is physically transposed or X is not unit-stride, this atom is not a general gather; use a supported reorientation or another path. For 16-bit DPAS-style transformed load, observe the narrower VNNI shape limits. |
| Output allocation `[T,ldY]` for logical `[T,N]` | X=N, Y=T; width `N*b`, pitch `ldY*b`; height T. | `ldY` is the physical row stride, not automatically the logical writable width. Store has no per-element mask. If the message extends past N, writing padding is valid only when those locations are allocated and intentionally writable; otherwise use an exact-width/padded-output strategy or a separately verified tail store. A tensor whose shape is `[T,ldY]` describes the padding as part of its surface. |

For all three, base alignment applies after pointer offsets as well as at allocation start. In a higher-rank tensor, check each batch/expert/slice offset preserves the required base alignment. Padded extents must also obey pitch ≥ logical row bytes and must remain inside the allocation; the latter two are caller-side invariants, not established by TLA's shown assertions. The 2D X dimension must be the contiguous dimension. TLA supports outer dimensions through additional strides/base offsets, but that does not turn the inner copy into an arbitrary-stride gather. Its documented atom families are regular 8/16/32/64-bit load, VNNI load for 8/16-bit, transpose load for 32/64-bit, store for 8/16/32/64-bit, and prefetch; do not infer unsupported transposed 16-bit loads from the regular-load family.

## K prefetch distance and boundary cases

The pinned TLA example defines prefetch distance in K tiles and warms up by issuing `prefetch_dist` prefetches before entering the K loop. That shape is not proof safe for a short K: with `k_tile_count = ceil(K/BK) < prefetch_dist`, unconditional warmup forms future coordinates beyond the K tile range. The ESIMD API gives prefetch no predicate and the references reviewed here do not state its OOB effect. Bound warmup to `min(prefetch_dist, k_tile_count)`, and issue each later prefetch only when its tile index is below `k_tile_count`; if zero K is a legal input, skip descriptor creation and the 2D operations altogether. This is a conservative caller rule, not a claim that the hardware faults for an OOB prefetch.

A future owner should write boundary cases before trusting a specialization: base alignment at 64-byte boundary and at +2/+4 offsets; width and pitch just below/at/above the four-byte boundary and the selected conservative 16-byte pitch; surface byte width around the TLA `0xFFFFFF` assertion and row count around its matching height bound; every legal and adjacent-illegal block width/height/count for each used dtype/mode; `T` or `N` smaller than tile height; `K` equal to 0 (if accepted), 1, one less than a K tile, exact tile, one more than tile, and K-tile-count `D-1`, `D`, `D+1` for prefetch distance D. Use canaries around ragged output rows and around the allocation end; compare valid load-tail elements against zeros and output elements against a scalar reference. Test a padded view and an outer-mode offset whose byte stride is not 64-aligned. These are proposed checks only; none were executed in this collection.

## Unresolved facts and novelty

The most useful incremental point is the exact mismatch between the pinned TLA documentation and its debug assertions, combined with the distinction between a logical surface width and physical pitch for padded rows. R798's indexed metadata covers general 2D geometry; this report narrows the question to the current pinned CuTe/TLA payload construction and the current LLVM ESIMD API, rather than repeating a general geometry survey. It does not read or restate the bodies of R782/783/798/805/807.

Still unresolved: whether BMG's minimum pitch is 4, 8, or 16 bytes for each actual load/store format; whether store OOB coordinates are suppressed at the exact LLVM/TLA device path; what prefetch does at an OOB edge; whether every API-legal 2D tuple is supported by the configured BMG runtime/driver; and whether descriptor width can intentionally include padding without changing logical output semantics. These require versioned device/compiler evidence and targeted owner-run tests. The pinned documentation does not prove runtime capability, numerical suitability, safety under an incorrectly described allocation, or performance.
