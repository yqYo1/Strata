## Finding

A supported route exists to save the actual IGC output produced when the Intel runtime JIT-compiles this application's SPIR-V: enable IGC shader dumps in the child process before `exec`, direct them to an owned directory, and select the exact kernel using IGC's documented regex filter. The IGC dump products include the input SPIR-V, final `.asm` and `.isa`; `ShaderDumpEnableRAMetadata` adds register-allocation metadata. This can establish the machine instructions/lowering, allocated GRF/register mode, and compiler-reported spill/scratch values for the actual JIT compilation. It is diagnostic instrumentation and cannot be used for timing comparisons.

This code's `h.parallel_for(nd_range, [=](sycl::nd_item<1> it) ...)` has no explicit kernel-name template type (`src/kernels/sycl/prompt_attention.cpp`, launch body); the kernel name is compiler-generated and varies with `launch<Mode,Direct,Native,KMapping>` specialization. Do not write a guessed regex such as `prompt_attention`. Obtain the exact `OpEntryPoint`/`OpName` from the SPIR-V image used by the matching executable, correlate its mangled lambda name to this source and specialization, then set `IGC_ShaderDumpRegexFilter` to that exact name. IGC’s own dump also records its input SPIR-V and output file names, which provide a cross-check between entry point, compiled ISA and launch specialization.

The IGC files are the primary resource capture. For an explicit driver-level compiled ELF/ZeInfo record (especially to read the final SLM/local-memory allocation), the installed NEO runtime exposes the `DumpZEBin` debug variable; upstream describes it as dumping Zebin (ELF) files. Its exact output naming/location and usefulness for this Level Zero/SYCL path have not been exercised here. Treat this as an optional, bounded confirmation: enable only in a separate follow-up if the filtered IGC output does not expose the per-kernel SLM size. Use `ocloc disasm -file <captured-ELF> -device bmg-g21 -dump <owned-dir>` only on that captured live ELF. Do not substitute an AOT Zebin. If neither IGC metadata nor the driver ELF exposes the actual SLM allocation, record that gap; source-level local-accessor bytes do not prove runtime allocation. A Level Zero `zeKernelGetProperties` result (`localMemSize`) from the same exact kernel handle would be an independent API confirmation but needs explicit application-side instrumentation and was not tested or proposed as an already available log.

## Unrun capture recipe

Run only after Main closes the current model/profile process and has a planned separate, owned child process using the exact executable, model, source build and short input that actually dispatches the prompt-attention path. Do not inject variables into an already initialized runtime or the shared server. Make two fresh, immutable-environment child processes if the kernel identity is not already recoverable from the exact executable's bundled device image. Do not treat either process as a timing sample.

1. Pin and hash the exact executable and source receipt first. Create a new mode-0700 output root with a finite byte budget; use a private working directory. To identify the generated kernel name, capture only the device image(s) actually used in a first short process with `SYCL_DUMP_IMAGES=2` (official DPC++ behavior: dumps used device image binaries and reports paths to stderr). This is SPIR-V input capture, not machine-code evidence. Keep the total dump to the ARTIFACT_RETENTION default 64 MiB raw text-log budget plus a separately declared binary-image budget; choose 64 MiB for images too, stop on the first exceeded limit, and mark the capture incomplete. Alternatively, if the exact executable contains the image, use the installed IntelLLVM `clang-offload-extract` on that pinned ELF offline and avoid the first GPU run.
2. Disassemble the extracted SPIR-V with an installed official SPIR-V decoder (`llvm-spirv -to-text` from the pinned translator or `spirv-dis`) and retain only the exact entry point/name evidence and image SHA. Match the mangled `OpEntryPoint` to the lambda inside `launch` and record its template specialization. There may be several mode/direct/mapping specializations. Keep only the symbol(s) for the actual dispatch under review.
3. In a second fresh process, use the same executable/model/workload and set all collection variables before `exec`. Set `NEO_CACHE_PERSISTENT=0` so the driver cannot silently serve an old persistent native image; a fresh process also starts with an empty in-process JIT cache. No library or GPU runtime should be initialized before these variables are set. Direct IGC dumps to the empty, pre-created directory. Set a regex for the exact entry point obtained in step 2 (the variable takes a regular expression; verify a harmless broad matching test against retained names before the expensive run, or abort if naming conventions do not match). Example skeleton only; `<...>` paths/arguments are placeholders and this command was not run:

   ```sh
   IGC_ShaderDumpEnable=1 \\
   IGC_ShaderDumpEnableRAMetadata=1 \\
   IGC_DumpToCustomDir=/private/owned/r739/igc \\
   IGC_ShaderDumpRegexFilter='<escaped exact SPIR-V kernel symbol>' \\
   NEO_CACHE_PERSISTENT=0 \\
   /path/to/pinned-strata-child <short reproducible prompt-attention workload>
   ```

   Keep standard output/error bounded under the 64 MiB per-job log ceiling. Preserve exit/health/fault status, timestamps, stdout/stderr hash, effective environment, all produced file names/sizes/hashes, executable/source/compiler/runtime/driver hashes, and the exact entry-point-to-IGC-dump mapping. IGC shader dumps are expected under the configured custom path; upstream's default is `/tmp/IntelIGC`. `DumpToCustomDir` requires its parent directory to exist. Do not use `IGC_ShaderDumpEnableAll`.
4. From the filtered IGC output, retain the kernel's `*.spv`, `*.asm`, `*.isa`, and RA metadata, plus small options/metadata files needed to prove the exact specialization and compiler options. The official dump guide identifies `.asm` as kernel assembly and `.isa` as kernel binary. Inspect actual final register/GRF, spill/private scratch, SLM/work-group metadata fields only where the output explicitly labels them. Record absent fields as unknown. Static spill allocation does not establish dynamic spill traffic, occupancy or speed.
5. If SLM allocation is absent, close the run and decide whether a second narrowly filtered attempt with `NEOReadDebugKeys=1 NEO_DumpZEBin=1` is justified. The NEO `DumpZEBin` flag's installed strings/source description support this as a candidate driver capture, but do not assume a path or output volume. First use a throwaway controlled short child only after the exact output location and naming are established from official matching-version documentation/source; set a separate 64 MiB artifact cap, and stop/mark incomplete at the cap. Run the installed `ocloc disasm` only on the runtime-captured ELF; do not make an AOT image and label it JIT. If the driver dump writes all kernel ELFs or unexpectedly writes outside the private output root, stop and preserve an inventory before any cleanup.
6. Commit compact results/hashes and a deletion manifest per `docs/ARTIFACT_RETENTION.md`; remove successful bulky intermediates only after confirming the run is closed and recording the needed evidence. Never use IGC dumps for clean speed samples. Repeat only if the first receipt has missing SLM evidence or the target symbol was not captured.

## What this will and will not establish

A matching process-specific IGC `.spv` → `.asm`/`.isa`/RA receipt is direct evidence of what this installation's IGC JIT compiled for that SPIR-V kernel, in that executable, on the BMG-G21 JIT route. A runtime-dumped Zebin, if supported and captured, can provide the final native image/metadata for OCLOC disassembly. The exact code path and `OpEntryPoint` association are necessary because the C++ lambda is unnamed and template-instantiated.

It will not report measured spill traffic, occupancy, active resident groups, throughput, performance impact, why pitch 40 changed the n=1 total, or whether prompt attention is the bottleneck. It is not a clean performance run. If compiler/runtime cache prevents a fresh compile, if the IGC filter misses the generated symbol, or if no actual JIT compilation occurs, there is no new compiled-resource result. Do not reinterpret R734 generic AOT as proof of JIT resource use.
