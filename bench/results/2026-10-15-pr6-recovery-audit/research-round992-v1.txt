## Exact call path and what a check proves

At `moe_window.inc:3-24`, window entry rejects unsupported mode/queue geometry, checks bank arithmetic/range, and validates bank, residual, region, and embedding allocation spans. `take` validates ten reserved region views (`:27-48`); `prepare` validates four temporary views (`:49-63`). Prep views intentionally alias the Down reservation, used before expert Down writes, so a future view system must encode phase/lifetime aliasing rather than assert that every view is globally disjoint. The route-map owner is built after ID readback/sync and its host vectors are uploaded at `:102-124`; both route buffers stay owned through all readers and the checked final drain (`:186-191`).

For each active expert, `:128-149` obtains the current residency slot and device blob, then checks that blob plus the same two dequant scratch spans. The blob check is expert-specific; the two scratch checks are invariant across experts in this window. Each job checks its dynamic row/index bounds and checks the same full `mixed` view plus job-specific `source` and `down` subranges (`:151-158`). The fixed 16K window has a maximum 8K expert job; actual active-expert/job distributions are not in the supplied source/build receipt.

Each job submits two `f16_out16` calls (GU and Down, `:164-174`). In the own backend, `gemm16.cpp:249-270` recomputes geometry, calls `validate_spans` (alignment, null and integer-overflow guards plus writable-output-vs-input alias checks), obtains/checks the in-order queue, validates all three actual allocation spans, and checks cached matrix support before submitting. In the optional vLLM path, `gemm16.cpp:77-105,281-297` calls `queue_for` and adapter `beta0`; `native16.cpp:34-70,168-184` recomputes bounds/shape/launch geometry, validates 64-byte base alignment and output aliasing, checks all three registered allocation spans and calls `runtime_.check()` before enqueue. For these fixed shapes both N/K divisibility sets are satisfied; dynamic `job.rows` and exact derived extents still need validation. The backend's immutable device feature probe is cached in `out16_support_` (own) or `has_fp16_` (vLLM constructor); it is not a repeated hardware query on every call.

`runtime_for_device_span` (`runtime.cpp:168-189`) validates nonnull/nonzero, overflow, then locks the process-lifetime registry, finds the containing registered allocation, checks full subrange bounds and exact queue context/device, and returns its Runtime. It does not return or retain the allocation owner. `validate_spans` (`launch.hpp:15-43`) checks power-of-two alignment, nonnull and address arithmetic, and output/input disjointness; it does not prove allocation identity, capacity, kind, or queue domain. The registry does. `compat.cpp:334-340` implements stream sync with `queue.wait_and_throw()` and then the sticky Runtime error check. Non-null `finish(stream,event)` observes event ownership but does not wait (`launch.hpp:61-65`); calls therefore remain asynchronous and rely on the in-order queue and later checked drain. Window requires `m.copy == m.cs` (`moe_window.inc:5-7`), so the checked lease drains the queue used by the window. Layer-major `DraftUploadGuard` drains before its owners are released and aborts with them live if retirement cannot be proven (`layer_major.inc:374-419`). `Restore` restores borrowed C++ fields; its comment explicitly says session tensors are not rolled back (`layer_major.inc:374-376`). Cancellation/error can leave session state partially advanced, so caller invalidation/checkpoint reload remains mandatory.

## Source-count estimate (not timing)

Let `E` be active experts and `J` route jobs in one paired window. The window helper alone performs `18 + 3E + 3J` `validate_device_span` calls: 18 fixed/base-view checks, three per active expert (blob plus two repeated scratch checks), and three per job (mixed, source, Down). Each of the two matrix calls per job additionally performs three `validate_device_span` lookups and one `validate_spans` call. Thus current own and vLLM paths both add `6J` allocation lookups and `2J` matrix shape/alias-validation calls, for `18 + 3E + 9J` total registry lookups across the helper and GEMMs.

At a *calculated balanced proxy* of 512 experts, 512 jobs and 320 rows/expert across a full 16K window (not an observed route census), that is 3,090 helper lookups plus 3,072 GEMM lookups = **6,162 registry lookups**, alongside 1,024 `validate_spans` executions (3,072 pointer-validity/alignment/overflow tests and 2,048 output-vs-input overlap comparisons). A concentrated top-10 case with 20 jobs gives 228 total registry lookups and 40 matrix validations. These count API/source operations, not cycles, wait time, or speedup. The live 39K collection does not supply E/J per window; collect the actual histogram before attaching a model-specific count.

A narrow in-place hoist that retains the existing validator but validates each stable dequant scratch once per window and `mixed` once per window removes `2(E-1) + (J-1)` repeated lookups: 1,533 in the balanced proxy. Blob identity and dynamic job subranges remain checked. Other potentially repetitive work is separated below; a caller must not simply disable the public GEMM checks for raw pointers.

## Concrete alternatives and limits

**A. Immutable allocation-backed tensor views/capabilities (preferred design to prototype).** Mint a capability when the actual Strata `Allocation` owner is established. It carries/ref-counts the allocation identity and owner, allocation base/size, USM kind, Runtime/context/device, and allocation generation; a typed view carries checked offset/extent, alignment, shape/stride, access role, and a phase/alias class. `subspan` uses overflow-safe offset arithmetic and proves `offset <= bytes` and `length <= bytes-offset`; it derives the exact pointer from the retained base. The GEMM entry accepts these views (or a private checked overload), checks the dynamic shape and the relevant input/output alias relation, then dispatches without re-locking the global address map for already-validated views. The allocation capability must pin the exact owner through the final `wait_and_throw`; a bare `{ptr,size,context}` cache or `shared_ptr<Runtime>` is insufficient. This keeps pointer identity, whole-allocation range, context/device, and matrix alias proofs while removing repeated registry discovery. Keep job-index and row-count validation per route map; keep the two-window prep/Down phase boundary explicit.

Scope: region/embedding/scratch/bank views can be formed once for the layer-major allocation epoch, with the residual offset/length freshly derived for each window. Expert views can be prepared for one layer/cache epoch, or minted under a per-expert slot lease after the current `(layer,expert)->slot` mapping is read. The current `ExpertCache` says it does not evict, but its cache object can still be replaced/reopened; cache lifetime and mapping identity must be held through the window. If future streaming/eviction is added, a lease must prevent overwrite until the last queued GEMM retires. Route-map host vectors are ordinary host allocations, not members of the device-span registry; their owner must still survive H2D completion.

**B. Epoch-scoped registry resolution (less invasive, weaker unless pinned).** Add an allocation-generation/epoch to registry entries and resolve candidate pointers to `(allocation id, generation, base offset, allocation size, context/device)` once at request or window setup. Memoize all typed views in that epoch; for each job, validate a small offset/extent against the cached parent instead of locking/searching the map. Re-resolve per expert when residency/slot mapping changes. Invalidate on `Allocation::release`, move, cache replacement/reopen, scratch rebind, arena resize, or epoch end. A snapshot alone is unsafe: an allocation may be freed and the same virtual address reused between lookup and enqueue (ABA). The current registry map lock protects lookup/update only during the lookup; the returned Runtime is not a lease. Require either a pinned owner/generation that prevents reuse or exclusive epoch ownership that forbids mutation/free through queue retirement. Compared with typed views this reduces API churn but leaves raw-pointer APIs able to bypass the epoch; use only behind an internal scoped launch context.

**Keep per launch/window:** input-derived rows, job global index bounds, signed/size arithmetic, actual matrix geometry and output stride, and writable output non-aliasing against the actual inputs. These depend on route job/shape/pointers. They can move into view construction only if the view carries the computed shape, and the launch still checks that supplied shape matches its view. Keep backend-required alignment (2 for own GEMM, 64 in the pinned vLLM adapter) and all fixed-device capability requirements. Queue context/device and in-order property are immutable for one live queue, so a queue lease could avoid repeating property queries; it must retain the actual queue and preserve vLLM's exact bound queue identity. Do not hoist sticky async-error state: device failures may arrive after any earlier matrix check. Keep synchronous enqueue errors and the later checked drain, which surfaces asynchronous errors and prevents freeing owners early. If queuing moves across queues, explicitly add dependencies and include every queue in checked retirement.

## API/runtime contract and counterevidence

[SYCL 2020 revision 12](https://registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html) says USM queries are host-only; `get_pointer_type` returns allocation kind for a pointer inside a valid allocation in a context, and `get_pointer_device` gives its associated device. SYCL separately requires that device USM use the same context for kernel and explicit memory operations; wrong-context access is undefined. These queries alone do not give a full byte extent or retain allocation lifetime. The [Unified Runtime 0.12 USM allocation-info API](https://oneapi-src.github.io/unified-runtime/core/api.html) exposes type, base pointer, size and device, which could support initial resolution, but querying metadata is not a lease against free/reuse. UR's `urUSMFree` contract waits for previously enqueued commands using the allocation; Strata still needs its stronger owner/check-failure policy before release. [Level Zero 1.19.12 `zeMemGetAddressRange`](https://oneapi-src.github.io/level-zero-spec/level-zero/latest/core/api/apis/mem.html#zememgetaddressrange) returns base and size for the containing allocation, and `zeMemGetAllocProperties` reports kind/device. These are queries, not a pin; cached results must still expire before unmap/free/reuse. (The project calls through SYCL/UR; this report does not assume direct Level Zero calls are enabled in the runtime.)

For a mature-runtime comparison, NVIDIA CUDA Driver API 13.4 `cuMemGetAddressRange` also returns containing allocation base/size ([official API](https://docs.nvidia.com/cuda/cuda-driver-api/cuda_driver_api/group__CUDA__MEM.html)); it warns that the query may return earlier async errors. CUDA stream-ordered `cudaFreeAsync` makes the key invalidation boundary explicit: after the free is enqueued, later access or querying pointer attributes is undefined ([Runtime API](https://docs.nvidia.com/cuda/cuda-runtime-api/cuda_runtime_api/group__CUDART__MEMORY__POOLS.html)). NVIDIA engineers' first-person [stream-ordered allocator article](https://developer.nvidia.com/blog/using-cuda-stream-ordered-memory-allocator-part-1/) describes reuse only after allocation/use/free dependencies are ordered. This analogy supports owner/epoch pinning and exact retirement; it does not imply Strata SYCL USM has CUDA stream-ordered allocator behavior. CUDA APIs/docs are a contract comparator only; no external implementation code was copied.
