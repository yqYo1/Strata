# R1030 — QSA head-parallel scorer source audit

Classification: decision support; immutable-snapshot source review only. The four eight-lane head groups reproduce the original SG32 reduction tree at the source-operation level, subject to compiler preservation of FP32 operation order. No confirmed score-mapping, convergence, or in-range-address bug was found. Two contracts matter if adopted: this private entry rejects the public API's `active=-1` default and eagerly reads every launched pooled row before per-row checks.

## Main decision digest

- New lane contributions `l,l+8,l+16,l+24` combined as `(p0+p2)+(p1+p3)` implement old XOR16 then XOR8; XOR4/2/1 complete the same tree. The head roots at lanes 0/8/16/24 are accumulated in baseline head order.
- Each work-group handles one 8-query tile and one block. Row guards precede absent-row `steps`/query access; each row's skip predicate is uniform, so continuing lanes converge at every XOR/select collective.
- At context 262144, `nb=65536`; with explicit `active=65537` the last score uses `dead`, no tail bonus applies, and later score columns are untouched. Physical context remains a caller contract.
- API difference is confirmed at source level (`active=-1` throws); it is a defect only if this is used as a drop-in public scorer. Eager loads are in-range when `active<=blocks`, but require all `[0,active)` pooled rows initialized and immutable through completion.
- Exact bits depend on no contraction/reassociation or equivalent optimizer proof. No build flags/device code were available here; the old scorer remains the independent full-bit reference.
- More live key/partial state is plausible; no physical bandwidth, GRF occupancy or speed claim follows from source. Main owns all such measurements.

## Arithmetic identity and compiler condition

The original scorer (`qsa_select.cpp`, `qsa_block_scores`) maps one SG32 to a query/block. Per head, lane `i` starts at product `4i`, adds dimensions 1..3 in order, then XOR partners at offsets 16,8,4,2,1. Lane 0 adds positive head roots 0..3 and applies the tail bonus last.

Candidate lane `32h+l` maps head `h` and `l=0..7`. Each `part[j]` is the old lane `l+8j` four-product sum. Old XOR16 forms `(p0+p2)` and `(p1+p3)`; XOR8 adds them as `(p0+p2)+(p1+p3)`, then candidate XOR4/2/1 finish the tree. Head roots at `h*8` are selected uniformly; head additions and tail bonus match baseline. Each corresponding operation has the same operands/order, not merely the same real-number sum.

Under separate FP32 multiply/add and preserved parentheses, this correspondence extends to finite values, signed zeros and intermediate overflow/Inf. Opposite infinities can form NaN at corresponding nodes. It does not establish cross-compiler NaN payload/signaling identity. FMA or reassociation can change rounding, finite bits, signed zero, overflow and NaN formation. Manifest says Intel LLVM v711/clang22.1, contraction off; snapshot docs say the SYCL build disables it. Intel documents `-ffp-contract=off` as disabling fusion, but no candidate build command, IR, or device code was available to verify flags or other relaxed-math settings. Full-bit parity remains Main-owned.

## Control flow, bounds, and inputs

**Collectives.** Kernel geometry is `ceil(nq/8)*active` work-groups, each 32 lanes with required subgroup size 32. Each group decodes one tile/block and all lanes loop rows 0..7. `qi>=nq` is checked before `steps` or query pointer use. For present rows, loaded `n,nb` and predicate `n<0 || nb!=n/4 || nb>=active || b>nb` are identical across lanes; a continued row executes all XOR4/2/1 and all four select calls. No lane-specific branch surrounds a collective or barrier exists. SYCL 2020 specifies same-mask XOR exchange and selected local-ID exchange; masks and `h*8` IDs here are uniform and in range.

**Rows and writes.** Key choice is row-specific: `b==nb` reads `dead`, `b<nb` reads pooled. `b>nb` skips. Only lane 0 writes `scores[qi*blocks+b]`; each valid row's tail bonus is added only at `b==nb` when `n%4!=0`. Columns beyond `nb` remain unchanged. Padded query rows never read their step/query records. `n=0` follows baseline behavior at `b=nb=0` and uses the dead row without bonus.

**Extent.** Validation matches baseline query/capacity/shape bounds except active semantics: candidate requires `0<active<=blocks`, while baseline accepts `-1` as `blocks`. Bounded grid/index arithmetic fits signed 64-bit. `validate_spans`/`checked_count` guard alignment, nullness and declared spans, not ownership, initialization or lifetime. Candidate does not independently enforce physical `n<=262144`, as baseline does not. At max context and `active=65537`, `nb=65536`; b=65536 is the dead-key sentinel, exact-multiple `n` has no tail bonus, and later columns are not stored. The caller must provide physical capacity and pool span.

**Read/lifetime obligation.** Before row checks, the candidate loads `pooled[b*128 + (l+8j)*4 + d]` for each lane's 4x4 `common` values. This occurs for absent slots, invalid steps, `b>nb`, or all-dead rows. With `active<=blocks` it is in-range, not OOB, but widens input requirements: all `[0,active)` rows initialized and immutable through completion. Snapshot docs state this for the adjacent public entry; this private entry is absent from the header. The fixture initializes the pool; R1029 proves ordered zeroing only for its engine caller.

Pinned `launch.hpp` says explicit in-order streams may return before completion; retain inputs, outputs and queue/runtime through completion. The fixture drains its queue and retains allocations, so no lifetime failure is demonstrated.

## Findings and priorities

1. **Contract choice:** preserve the public `active=-1` behavior if drop-in compatibility is required; otherwise keep the positive-active restriction explicit at the private caller and test it. This is a real source-level API difference, not a demonstrated engine failure (the fixture supplies explicit active).
2. **Input contract:** document/test full `[0,active)` initialization, immutability and queue lifetime if arbitrary direct callers are in scope. Treat eager read as a coverage/API obligation, not an uninitialized/OOB bug on the evidenced initialized engine path.
3. **Decision evidence:** retain old scorer as independent full-bit/full-ID oracle, including cancellation-heavy, signed-zero, overflow/Inf and NaN diagnostic classes. Main should inspect actual compiler output/resources and repeated scorer results before adopting; no source-level bandwidth, occupancy or speed estimate is made here.

- Khronos, [SYCL 2020 specification §§4.17.3.3–4](https://registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html): subgroup XOR permutation and value selection contracts. It supports convergence reasoning, not this scorer's floating-point reassociation.

- WG21, [C++ expression preamble](https://eel.is/c++draft/expr.pre): arithmetic and exceptional values; not a portable guarantee of exact device NaN payload behavior.
