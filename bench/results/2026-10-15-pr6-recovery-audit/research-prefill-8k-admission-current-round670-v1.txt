# Current-root 8K prefill workspace and residual admission — round 670

Date: 2026-10-15 JST. Read-only audit of current `Prefill::init`/`carve`/`relayout`, `bytes_needed`, layer-major residual admission, and public Main reports. No build, test, compiler, GPU, process, private B/live log/environment, cleanup, Git mutation or root-source edit was performed. No in-progress proposal was read. The public memory figures below are prior Main evidence, not a new query or an admission result.

## Decision

For the compact FP16 MoE fallback and 262,144 context, moving chunk 4,096 to 8,192 adds **1,210,776,832 bytes (~1.13 GiB)** of actually carved, simultaneously live device workspace, assuming the same QSA dimensions, stream mode and other settings. This is not the sum of three scratch families: attention/QSA, GDN and MoE alias one `region`; only `max(gdn,qsa,moe)` is live and allocated. The remaining increment is the other per-chunk buffers outside that region.

The previous public post-MTP-expert-release free query was 2,423,623,680 B. After the layer-major route's additional 512-expert cache (1,363,148,800 B) and fixed 512 MiB reserve (536,870,912 B), the arithmetic budget for the GPU residual bank is 523,603,968 B. At 40,960 B per FP32 residual row, this supports at most 12,783 raw rows before chunk rounding. Therefore:

- C=4,096 can admit a fixed 12,288-row prefix (480 MiB) by that bound.
- C=8,192 can admit one complete 8,192-row prefix (320 MiB), but not two (640 MiB).
- A matched chunk-only pair must set the same effective prefix in both arms. `R_GPU=4,096` at C=8,192 is rounded down to zero, so the proposed `C=4,096/R_GPU=4,096` vs `C=8,192/R_GPU=4,096` is not a chunk-only comparison. `R_GPU=8,192` in both arms yields 8,192 rows in both, if runtime free memory remains at least the bound required for 320 MiB plus the fixed layer cache/headroom.
- The old “all prompt residuals in VRAM” layout cannot be restored from the cited free bound while preserving the current additional layer cache and 512 MiB reserve. A 32K prompt requires about 1.25 GiB of residual storage alone; the public 523.6 MB budget is short by about 819 MB even for exactly 32,768 rows (and ~837 MB for the 33,213-row batched portion of a 33,214-token prompt). Full 262,144-row residual residency would require 10 GiB just for the FP32 bank. These are arithmetic checks, not measured physical admission.

Minimal safe configuration to **screen 8K chunking** while retaining the current full context/session geometry is the existing long route with `--max-context 262144`, C=8,192, FP32 storage, layer-major active, and `R_GPU=8,192` in both 4K and 8K arms. Keep MTP4, KV type/resident policy, compact-MoE/MMQ mode, input IDs, cache, runtime environment and all other settings fixed. Record actual layer-major `free_gpu`, cache bytes and `residual_gpu_rows`, and require the same prefix in each arm before comparing speed. This does not reproduce PR6's all-resident residual layout or prove full 262K input correctness. To request all residual rows for one known prompt, the process would need `R_GPU` equal to that call's exact batched `n` (the planner treats `requested == n` specially and may retain the partial last chunk); the current public budget fails that request. Do not disable the 512 MiB reserve or assume a cache reduction gives the whole deficit back.

## Actual chunk workspace liveness

`Alloc::take` rounds each allocation independently to 256-byte alignment with a 256-byte guard allowance (`src/prefill/prefill.cpp:189-213`). `Prefill::init` lays out the 32 MiB-element GEMM scratch, 32 MiB GEMM workspace, and `carve(T)` in its borrowed workspace or its owned allocations (`:728-836`). `relayout` synchronizes the streams, rebinds the GEMM buffers, and re-carves the caller's borrowed block for the new chunk (`:938-961`). The same allocation sequence is intended to be used by `bytes_needed` (`:1247-1281`). Fixed-size expert-dequant scratch, stage ring, KV stage backing and identity table are not multiplied by chunk size.

For the current compact fallback (`STRATA_PREFILL_MMQ=0`, compact FP16 active, `gr_unfused()` false, no BF16x2 additions), R637's source-derived count table gives:

| Chunk | GDN set | QSA set | Compact MoE set | One shared region (`max`) |
| ---: | ---: | ---: | ---: | ---: |
| 4,096 | 590,350,336 B | 607,128,320 B | 543,837,696 B | 607,128,320 B |
| 8,192 | 1,180,698,624 B | 1,120,979,712 B | 1,087,671,808 B | 1,180,698,624 B |
| Increase | 590,348,288 B | 513,851,392 B | 543,834,112 B | **573,570,304 B** |

Only the rightmost increase is allocated. Adding the three set increases would double/triple count mutually reused scratch. At 4K the QSA set is largest; at 8K the GDN set is largest, so the single allocated region changes its controlling member.

The other chunk-scaled arrays in `carve` add 637,206,528 B between 4K and 8K. Thus the actual dynamic carve delta is 573,570,304 + 637,206,528 = **1,210,776,832 B**. The non-region amount comprises token embedding, residual/work tensors, QSA step records, and PLE embedding rows among others; fixed DQ buffers and ring slots contribute no delta. `m.xn` is null unless `gr_unfused()` is enabled (`:852-856`). However `bytes_needed` unconditionally counts a `T*D` FP32 `xn` allocation (`:1257`) while `carve` conditionally omits it. For this fused-GR configuration, the count-only **borrow/loan request** therefore overcounts the 4K→8K difference by 167,772,160 B; it predicts 1,378,548,992 B more borrowed space, rather than the 1,210,776,832 B actual `carve` increase. This discrepancy affects cache-slot/borrow selection even though it is not live `m.xn` storage. With `gr_unfused=1`, that extra storage would be live and the larger increment would apply.

The 4K/8K actual carved sizes, excluding chunk-invariant owners such as GEMM buffers, are 1,285,464,064 B and 2,496,240,896 B respectively under these assumptions. They are not full `bytes_needed()` totals, which also include constant GEMM, ring, streamed-KV stage and slack allocations. With a borrowed region, the workspace occupies the end slots of the decode ExpertCache while the prompt runs; with no borrow, init allocates it as owned buffers. `--prefill` chunk selection/`lend_slots` and relayout govern the first case. Thus a larger chunk may reduce usable decode cache capacity even when it does not directly lower the `cudaMemGetInfo` result. The per-request 512-expert layer cache is a separate allocation made by `run_layer_major`, not part of this shared chunk scratch.

## Residual-prefix admission and public bounds

`LayerMajorResidualPlan::make` uses `D=4*2560=10,240` FP32 values/row (40,960 B). For any explicit nonterminal `R_GPU`, it rounds down to a multiple of `chunk`; the exception `requested == n` includes an exact partial final chunk. For `auto`, the available whole-chunk prefix is `(budget/40,960/chunk)*chunk` after the extra layer cache and 512 MiB headroom have already been subtracted (`include/strata/prefill/layer_major_plan.hpp:78-117`).

Public Main review `main-review-round655-656.ja.md` reports a completed prior full-OFF long run with 1,715,826,688 B free before the existing MTP expert detach and 2,423,623,680 B after it: measured driver free delta 707,788,800 B. Its layer-major log recorded C=4,096, FP32, requested R_GPU=4,096, a 1,363,148,800 B temporary layer cache and the 512 MiB reserve. The source check is `free_gpu >= cache_bytes + gpu_headroom`, then `gpu_budget = free_gpu - cache_bytes - gpu_headroom`, then a separate residual `cudaMalloc`. This evidence was for a 33,287-row request under that closed process, not 8K chunks, not a repeated admission sample, and not 262K prompt rows. It does not prove the 8K workspace fits in a different process or that the same post-detach free query will recur.

The previous MTP expert release is already integrated and is the source of that measured +707,788,800 B free delta. Do not count its requested 707,788,800 B a second time. The public R655 arithmetic gives 523,603,968 B remaining for residuals after temp layer-cache/headroom. At C=4,096, auto can choose 12,288 rows (480 MiB), the next multiple 16,384 would exceed budget. At C=8,192, auto can choose one chunk (8,192 rows, 320 MiB), and not two. Explicit `R_GPU=8,192` is consistent with that arithmetic. Runtime admission still queries fresh free memory and can fail if other allocations differ.

To request all 32,768 rows at 8K chunk, the FP32 residual allocation is 1,342,177,280 B. The planner's minimum free query is then 3,242,196,992 B (1,363,148,800 cache + 536,870,912 reserve + 1,342,177,280 residual), 818,573,312 B above the public 2,423,623,680 B query. For 33,213 batched rows, residual is 1,360,404,480 B and the minimum query is 3,260,424,192 B, 836,800,512 B above that evidence. If request length changes, the all-resident request must be recalculated against the exact `n` passed to `Prefill::run`; no blanket fixed row setting guarantees all rows for every prompt length.

There are two separate admission stages. The chunk workspace is established at initialization: with no borrow it must be separately allocated; with a borrow it is carved from cache slots and reduces decode-resident capacity during prefill. The residual prefix is planned later inside `run_layer_major`, after any MTP expert release, against fresh `cudaMemGetInfo`. The cited 2.424 GB is from that later point, after the base chunk workspace/session/cache already exist; it cannot prove that increasing the chunk workspace by 1.211 GB will fit at startup. Reconfiguration must capture both the chosen chunk/borrow and the later layer-major free/cache/residual plan in the same process. A cache loan with 128 slots cannot assume the full C=8,192 buffer block fits; `lend_slots` must find enough tail bytes while retaining its 128-slot minimum, otherwise the chosen chunk is reduced or a separate owned-buffer path must pass its own memory check. No test of those paths was run here.

## Minimal route that stays within current correctness bounds

A source-only prefill candidate setup, without adding another engine or altering decode layout, is:

1. Keep maximum context/session geometry at 262,144, INT8 KV and the current 32,768 resident-cell policy; keep layer-major mode, FP32 residual storage, compact MoE fallback and MMQ=0; keep MTP4 prompt callbacks and the current safe runtime controls.
2. Set chunk to 8,192 and use an explicitly matched `R_GPU=8,192` prefix for a chunk-size screen. Also run the 4,096 arm with that same 8,192-row prefix so the residual placement is identical. If borrow is active, verify the planner actually retained 8K and record borrowed cache slots; if no-borrow, confirm init's full workspace allocation succeeded before measuring.
3. Preserve 262,144 context capacity and existing full-context/RESTORE gates. Do not call a 32K/64K prompt at 262K capacity a physical 262K prompt test. Full-input physical 262K at C=8,192 is a distinct, currently unadmitted memory case.
4. Only try `R_GPU=exact_n` (or `auto` that demonstrably selects all rows) if the fresh layer-major free query is at least `1,363,148,800 + 536,870,912 + n*40,960` B with all other allocations fixed. Existing public evidence is below this bound for the 32K workloads above, so it does not qualify old PR6 all-GPU residency.

This configuration distinguishes chunk granularity while retaining current long-prefill model, KV and MTP work. It is the smallest honest prefill-only screen; the requested “8K/all-VRAM” historical layout is not currently justified by the cited capacity. Lowering cache slots, changing KV storage, removing the 512 MiB reserve, or dropping MTP would change a separately material dimension and is not a demonstrated safe route to recover that deficit. The all-VRAM shortfall is not a proof that no future capacity solution exists; it is the present evidence boundary.
