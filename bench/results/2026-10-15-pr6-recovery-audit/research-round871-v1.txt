# R871 — Two-chunk routed-output capacity in the configured SYCL prefill

Decision support, static source audit at supplied snapshot `16f9eefa216f9f6d2f1fd5c18980612e7d6b656a`. All thirteen supplied source hashes matched. The only additional caller file read was `src/prefill/layer_major.inc`, hashed before use (`e2def3bbd248c06c25ff2fce7ebc0ce49aecfcb0e418115196da8bb4b99960b1`). No build, test, device work, performance inference or code change was made. The configured target is `src/prefill/prefill.cpp` plus the listed SYCL GEMM/native16/postops/MoE files (`CMakeLists.txt:35-55`, `cmake/sycl_backend.cmake:118-121`), not the CUDA generator path.

## Decision

The one-chunk `Dm` allocation has enough *bytes* for two chunks of 16-bit routed down outputs in one contiguous expert-major plane: its current FP32 reservation is 838,860,800 B, and two 8,192-row top-10 output planes at N=2,560 also total 838,860,800 B. This is an exact payload fit, not proof that the current workspace safely holds the 16,384-row operation: routes, weights, hidden inputs, shared-gate scalars, injection, attention residuals, and callback ownership remain one-chunk objects or need explicit lifetime/reuse changes.

There is also a format correction. The compact flag name does not imply that `Dm` currently stores FP16. With native16 disabled, `Gemm::f16` writes FP32 `Dm` (`gemm.cpp:102-106`). With native16 enabled, `f16_out16(..., true)` selects BF16 output; `native16::combine` reads BF16 (`gemm16.cpp:281-298`, `native16.cpp:21-22,141-158`). Thus no current route writes FP16 expert outputs to `Dm`. The same two-byte capacity arithmetic applies to the current BF16 output plane, but this is not evidence for FP16 output numerics or adoption.

The same output flag is used for native16 GU and shared projections; those planes are BF16, while routed/shared SwiGLU hidden `Hh`/`sh_h` is stored as FP16 (`prefill.cpp:2680-2689,3263-3270`; `native16.cpp:125-139`). “Two-byte” therefore describes capacity only, not interchangeable encoding.

## Current reservations and lifetimes

`Alloc::take` reserves `round_up(raw_bytes + 256, 256)`; each aligned raw allocation therefore carries a 256-byte guard (`prefill.cpp:199-219`). Values below are raw typed payloads for T=8,192, K=10, N=2,560, FF=640, E=512. MiB is 2^20 bytes. Compact mode is enabled only when requested exactly as `1`, MMQ is inactive/fallback, debug-NaN is off, and native shapes fit; it selects compact `Xs`, `GU`, and `Hh` scratch sizes but leaves `Dm` at T×K×N FP32 elements (`prefill.cpp:676-692,702-730,991-1008`).

At one chunk, top-10 routing produces exactly `T*K=81,920` routed rows; source checks each compact expert count against T and uses prefix offsets over active experts (`prefill.cpp:2807-2815,2841-2855,3250-3283`). Two chunks therefore have 163,840 output rows total and at most 16,384 rows for any expert under the per-chunk bound. `native16::combine` consumes exactly `rows*10` routes and performs each token’s ten weighted additions in slot order before adding the shared result (`native16.cpp:141-158`). A single-window caller must retain that mapping and reduction order; changing to expert-order accumulation is a separate numerical change.

The current allocator deliberately overlays GDN, QSA, and MoE scratch: `m.region_bytes = max(gdn_set_bytes, qsa_set_bytes, moe_set_bytes)` and the three `Alloc` views restart at the same base (`prefill.cpp:620-639,714-730,960-1008`). Summing all three as concurrent storage would be wrong. For compact T=8192, the MoE view’s 14 guarded reservations total 1,087,671,808 B; the C8192 compact receipt `qsa-device-batch-clean-1-r1-v1.json` (SHA256 `3e238b25baef4cc95bd108c30bb06066ec3a9b32b8db4ecbc4d0e7e849313f6d`) reports a shared region of 1,180,698,624 B and all prompt chunk allocations accounted at 2,588,395,008 B. These are allocation extents, not spare capacity or a live MoE-only peak; the larger region is already owned by the phase maximum, and full model/session/KV memory is outside that logged chunk figure. Nonexclusive unitrace totals do not attribute service or speed to MoE.

## Reuse and order boundary

(a) **Current chunk:** router and CPU grouping finish for one T; each expert reuses compact `Xs`, `GU`, and `Hh`, while its down result remains in its expert-major `Dm` span until one combine. Shared output, `sg`, injection, and `R` remain live to combine/write. (b) **Two chunks serialized:** complete combine and HC write for chunk one, then reuse the same buffers for chunk two. This is safe storage reuse but leaves no two-chunk `Dm` window; its first result is already consumed. (c) **One 16K output window:** the `Dm` byte extent fits, but only if the producer retains or reconstructs both chunks’ route maps and per-row inputs/state until all required expert outputs and combines finish. Compact `Xs`/`Hh` can be reused with two separate calls per expert, not with one 2T-row call. Shared outputs fit their native16 alias, while FP32 `sg` and `inj` and the current input/map arrays do not.

Current order is layer-major over 48 layers, with `run_impl` walking positions in chunks no larger than 8,192; the layer-major admission rejects larger T and split/peer topology (`layer_major.inc:78-97,429-429,604-607`; `prefill.cpp:1840-1845`). Within each chunk it runs PLE’s token-ordered history update, then GDN recurrence or QSA selection/attention in position order, then router, shared expert, routed experts, combine, and HC write (`prefill.cpp:2207-2259,2314-2337,2468-2491,2583-2605,2657-2695,3352-3359,3405-3423`). The causal state math need not be reordered to form a 16K output plane: the two 8K state passes could remain ordered. But no current producer-consumer interface splits the layer at that boundary. To defer FFN across chunks, do not advance GDN/QSA/PLE twice, do not overwrite the first chunk’s mixed inputs before gather/shared use, and do not publish intermediate attention residuals through `on_chunk`/checkpoint or to the next layer. Current callbacks commit the chunk only after final FFN write; `on_stage_chunk` is accepted only after the last request chunk in the last layer (`prefill.cpp:3425-3427,3480-3503`; `layer_major.inc:500-520,565-607`). The residual bank could be an in-place row owner only after a source-backed proof of old-input retirement, row precision, placement, and host/device transfer cost.

Layer-major currently excludes peer/split execution. Elsewhere peer/MMQ code partitions local and peer rows and copies peer output into `Dm`; its layout is not evidence that the single-GPU contiguous alias remains valid (`prefill.cpp:2818-2838,3000-3066`). Shapes, flags, and queue topology therefore matter. Compact FP16 is an existing opt-in for per-expert FP16 input/hidden scratch; it neither creates a 16K window nor changes output format (`prefill.cpp:676-692,3250-3283`).

## Decision boundary

A source-level answer is **yes for the `Dm` two-byte payload extent alone, no for current full-window safety**. Before calling it a candidate, a separate source change would have to define the 16K route/slot map, shared gate and injection lifetime, residual/intermediate owner, and extended combine bounds while preserving the slot-order reference and state/callback sequence. The current T=8,192 guards stay relevant to the two causal passes; do not simply relabel them T=16,384. Numerical accuracy/quality, performance, FP16 versus BF16 choice, and default adoption remain unanswered gates. R701/R702 already covered generic grouping/superchunk proposals; this update is only the exact two-chunk capacity, alias, and phase-liveness result.
