## Contract and exact extents

The live source still matches SHA-256 `fa505d02e2b24f7cb6948033921fa697c8aeb58e6f4df6d873f13e5a7918e36b`. The independent `candidate.cpp` differs from it only by pitch-templating the shared K/V tile size, local payload check, K/V producer destinations and matrix-load strides/pointers, plus a fixture entry point selecting the five variants. The existing thread ownership, BF16 payload bits, matrix dimensions/operations, FP32 online-softmax state and arithmetic, and barriers remain unchanged. The candidate’s static assertions establish `sizeof(BFloat)==2`, a standard-layout/trivially-copyable `MatrixTile<N>` with `alignas(4)`, values at offset zero, and exact `2*N` byte size.

The pinned Intel experimental `joint_matrix_load` API defines stride in elements between row-major rows. For BF16 on its BMG restrictions, each stride in bytes must be a multiple of 8 and no more than `2^24`; each direct base pointer must be four-byte aligned. Every proposed pitch is a multiple of four BF16 elements, and every actual pointer offset is even BF16 elements, so the aligned tile base makes every K/PV load pointer four-byte aligned. This uses the direct-pointer overload, so the separate offset-overload `row_index` rule does not apply.

For QK, each subgroup load is 16x16 from `kv + d0*KPitch + c0`, with `d0=0,16,...,240`, `c0=0 or 16`, stride `KPitch`. The K producer writes every logical coordinate `[d][cell]` to `kv[d*KPitch+cell]`, `d<256`, `cell<32`; it writes zero for missing/invalid rows. For PV, each load is 16x16 from `kv + c0*VPitch + dim0`, with `c0=0 or 16`, `dim0=(subgroup%4)*64+16*j`, `j=0..3`, stride `VPitch`. The V producer writes every logical `[cell][d]` to `kv[cell*VPitch+d]`, `cell<32`, `d<256`, again zero-filling invalid rows. Thus one typed tile is reused; it is not two simultaneous K/V allocations.

The max-index values are inclusive; each value fits within the listed single-object extent. Row padding is outside the logical 16x16 loads and no producer/consumer indexes it. No padding initialization is required by the matrix API’s logical load contract; physical transaction width is not established here. Barriers still publish rows, K, QK scores, V, and PV in order, and the final PV barrier protects the next tile’s K overwrite. The existing `local_mem_size >= LocalPayload + 4096` admission therefore evaluates to the table’s threshold for score stride 33 (and 34,304 B for pitch 36/260 with score stride 32). It is a source-side fit guard, not proof of compiler allocation, residency, or occupancy.

## Evidence limits, next gate, provenance

The current service binding attributes 120 attention calls / 37.077867 seconds to the 78K prefill but leaves cache, SLM banks, barriers, and occupancy unresolved. The closed K-staging component run compared global K producer schedules, not local pitch: span-256 regressed 10.35–29.48%, while span-4 was mixed; its 50,331,648 output bits matched. Neither result predicts the SLM-pitch result. Changed row-start modulus may affect lowering or SLM conflicts; the extra 2 KiB for 36/260 may also add address work or reduce residency at a resource threshold. No B570 bank map, physical transaction behavior, generated load sequence, or pitch speed is measured. The 40/264 alternative adds more local storage and should be considered only after the 36/260 correctness/admission gate.

Main’s smallest useful sequence is a fixed `<33,false,false>` baseline against one immutable pitch selector under the same build/runtime/inputs; first validate duplicate, invalid/tail, empty/partial, K-to-V reuse, bounds/fault behavior, then compare all output bits on the 8,192-query component with six rotated samples per shape and both clustered/scattered rows. Only a repeatable component win warrants paired real-model long-prefill samples. Preserve physical-262144, RESTORE, and quality gates. The old packed candidate remains closed.
