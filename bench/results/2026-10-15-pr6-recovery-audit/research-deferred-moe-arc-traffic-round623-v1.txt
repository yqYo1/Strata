# Deferred expert-major MoE on the configured Arc/SYCL route: type, traffic and wave sizing — R623

Date: 2026-10-15 JST. Read-only source and retained-report audit for the configured Arc B570 10 GiB path. The only write is this report. No source edit, build, test, GPU, process/service inspection, Git operation or active-artifact inspection was performed. Values below are arithmetic scenarios from source shapes, not measurements or speed/quality results.

## Corrected implementation identity and R621 corrections

The configured resolver is explicit: `cmake/sycl_backend.cmake:111-114` builds `strata_prefill` from `src/prefill/prefill.cpp`, `src/prefill/sycl/gemm.cpp`, `src/prefill/sycl/postops.cpp`, `blob.cpp`, `moe_mmq.cpp`, and `moe_fused.cpp`, and links oneMKL SYCL BLAS. `prefill.cpp` is shared orchestration; its `cuda*` compatibility calls resolve to the SYCL runtime in the configured build. The CUDA-only `src/prefill/kernels.cu` is not the configured combine implementation.

R621 got the activation byte width right but named its type incorrectly. `m.mixed_h` is **FP16**, not BF16: `carve` allocates it as `uint16_t` (`src/prefill/prefill.cpp:856-858`), and `gr_mix_r` passes it as the separate `half` output (`:2052-2054`). In SYCL `postops.cpp`, `image` writes `half[i]=hf(x)` while `hi[i]=bf(x)` (`:22-50`); `mix` writes the FP16 `half` output at `:93-124`. Separately, `m.mixed_bf` is BF16 and feeds router/shared-gate projections. The routed expert gather reads `mixed_h`, then invokes `Gemm::f16` for GU and Down (`prefill.cpp:2874-2889`). SYCL `Gemm::f16` is oneMKL row-major GEMM with `sycl::half` input, transposed weights, FP32 output and a finish on its queue (`src/prefill/sycl/gemm.cpp:18-29,96-100`). Thus no BF16-to-FP16 cast should be charged to an expert-major design if it retains `mixed_h` bits. The activation storage remains `n*N*2` bytes as R621 counted.

The actual Arc MoE combine is `src/prefill/sycl/postops.cpp:248-267`, not `kernels.cu`: it initializes FP32 `v=0`, visits route slots `k=0..9`, skips negative slots, applies `sycl::fma(weight, Dm[slot], v)`, then adds `shared[i]*sigmoid(sg[t])`. This matches the ordering concern identified in R621. The FP16 expert products are accumulated into FP32 oneMKL output rows before this combine. An expert-outer schedule may change the ten-way reduction order if it accumulates by expert; token IDs need not stay identical per user direction, but numeric drift must be measured against a declared capability-quality floor. Bitwise identity is not the only possible acceptance criterion.

## Where the retention point sits

Current layer-major order is layer outer, chunk inner (`src/prefill/layer_major.inc:279-313,362-373`). Inside each chunk, PLE and the attention HC half execute, then FFN HC normalization/mix produces FP16 `mixed_h` and BF16 `mixed_bf`; router and shared paths consume those (`src/prefill/prefill.cpp:1980-2054,2300-2335`). GDN/QSA state is updated in the attention half (`:2061-2086,2087-2298`); chunks must remain ascending per layer. The following chunk's layer input already lives in the preceding layer's residual bank, so deferring current-layer experts until after all current-layer chunk prepasses does not inherently make its GDN/QSA input depend on current-layer FFN output.

For deferred processing, preserving every input row in FP16 `mixed_h` and its BF16 router input is sufficient for recomputing some small pieces, but not all output-dependent parts. A low-risk layout should retain the exact router IDs/weights and an expert-to-original-route-slot mapping; the current mapping is created by host grouping (`prefill.cpp:2413-2484`) and `slot_dev` is read by combine. It must also retain the four-stream FFN HC `inj` values until final `gr_write` (`:2989-3013`). The shared expert output (FP32 N-vector per token) and shared gate (one FP32 per token) can either be retained or recomputed after restoring/sending the activation; retaining avoids another projection pass. The old layer input cannot be overwritten in the residual bank until all prepasses have consumed it. Once a row's attention and FFN preparation is captured, the existing interlayer `Rstore` may serve as the output destination for that row after expert results and HC write finish; it cannot serve as both previous-layer input and new output while one remains needed. Existing `LayerMajorResidualPlan` only describes the interlayer bank (`include/strata/prefill/layer_major_plan.hpp:78-133`).

PLE history advances tokenwise at layer 1 in the current chunk traversal (`prefill.cpp:1980-2034`); `ple_prev` is advanced in ascending prompt order (`:1781`) and layer-major resets it at each pass, committing final values only after the completed traversal (`layer_major.inc:123-125,311,378`). Keep both orders and state semantics. Defer public `on_chunk`/MTP and `on_stage_chunk` until each chunk has final `Dm`/combine/HC output; current final output callbacks occur after queue synchronization (`prefill.cpp:3070-3079`). Cancel/failure after GDN/QSA/PLE mutation remains a failed partially advanced session unless the outer RESTORE/discard path handles it; saved owners need checked queue retirement. Existing layer-major lease and callback restore are in `layer_major.inc:193-231,279-385`.

## Exact logical byte and PCIe-transfer scenarios

Definitions for this table: prefix `n` is 32,768 / 65,536 / 262,144 tokens; width N=2,560; K=10 selected experts; `mixed_h` FP16 = 5,120 B/token; each FP32 expert product = 10,240 B per route; one FP32 N-wide accumulator/output = 10,240 B/token. “GiB” is bytes divided by 2^30. All entries exclude transport framing/alignment and other operators.

| Prefix | One FP16 activation copy (n*N*2) | Ten routed FP16 activation rows H2D if expert-major input is gathered anew from host (10*n*N*2) | Ten FP32 expert outputs (n*K*N*4) | Those ten outputs D2H then H2D for GPU slot-ordered combine |
|---:|---:|---:|---:|---:|
| 32K = 32,768 | 167,772,160 B (0.15625 GiB) | 1,677,721,600 B (1.5625 GiB) | 3,355,443,200 B (3.125 GiB) | 6,710,886,400 B round trip (6.25 GiB) |
| 64K = 65,536 | 335,544,320 B (0.3125 GiB) | 3,355,443,200 B (3.125 GiB) | 6,710,886,400 B (6.25 GiB) | 13,421,772,800 B round trip (12.5 GiB) |
| 262,144 | 1,342,177,280 B (1.25 GiB) | 13,421,772,800 B (12.5 GiB) | 26,843,545,600 B (25 GiB) | 53,687,091,200 B round trip (50 GiB) |

The host-gather/H2D column is a worst-case straightforward expert-major implementation: each expert's routed FP16 X rows are gathered from the host prefix owner and uploaded, so each token's activation is transferred ten times in aggregate. It is avoidable if the whole wave's activation is resident in VRAM while every expert is processed; that is the key benefit of chunk waves. For a *whole-prefix* 262K activation resident at once, the 1.25 GiB FP16 X owner alone is below a 10 GiB physical-card size but exceeds the cited 1,662,831,872 B (1.548 GiB) potential-release accounting amount once added to other needs. Full `Dm` at 25 GiB cannot be resident. If exact combine order is preserved by round-tripping all `Dm`, the 50 GiB traffic is vastly larger than the data that would be moved for the one-time dequant; it defeats an Arc-traffic rationale even before timing. CPU-side slot-ordered combine could avoid H2D of `Dm`, but then must move 25 GiB D2H and send at least the combined FP32 N output (0.3125 / 0.625 / 2.5 GiB at the three prefix sizes) back for device HC write, plus shared/gate unless combined there too. These are alternatives and bounds, not measured transfers.

The prefix-wide retained payload for a host-backed exact-order route also includes IDs plus weights: `n*10*8` = 2.5 MiB / 5 MiB / 20 MiB, before stable slot maps/alignment. Shared FP32 is `n*N*4` = 0.3125 / 0.625 / 2.5 GiB. Gate FP32 is only `n*4` = 128 KiB / 256 KiB / 1 MiB. HC injection is four FP32 values per token (`inj`, `n*HC*4`) = 512 KiB / 1 MiB / 4 MiB. The FP16 `mixed_h` is 0.15625 / 0.3125 / 1.25 GiB. `m.mixed_bf` need not be retained if router IDs and weights are already stored; if router is recomputed, retain the BF16 router input too (same width/byte count as `mixed_h`) and pay a router pass. If shared values are retained, no need to preserve all shared projection scratch.

## FP32 accumulation instead of 25 GiB route-slot Dm

Relaxing bit identity makes a compact FP32 accumulation candidate possible: allocate one N-wide FP32 result per token, process experts in expert-ID order, and add `route_weight * expert_output` to each assigned token. This replaces the 10*N FP32 route-slot matrix with one N FP32 accumulator, a 10-way reduction in output storage and combine traffic. Per prefix it is 0.3125 / 0.625 / 2.5 GiB instead of 3.125 / 6.25 / 25 GiB. Keep the accumulation in FP32 and apply the shared term after the routed sum. The order differs from current route slot k order and may alter final bits; no source result bounds how much. Alternative accumulation in FP16/BF16 is materially riskier and not proposed.

A sufficient evaluation would compare across representative prompts and task sets: intermediate per-layer routed sum and final residual max/ RMS error and nonfinite count; final-position and prompt-wide logit KL or normalized logit error; top-1 agreement/rank changes on prompt positions; greedy continuation agreement on held-out prompts; and task-level outcomes that exercise code generation, instruction following and long-context retrieval. Because the user permits non-identical token sequences when capability loss is negligible, judge against predeclared noninferiority limits for those task metrics and a baseline variance estimate, not exact token equality. No threshold can be chosen from source; it must be owned by the project quality decision. The model has no measured R623 error distribution, so “almost no capability degradation” is not yet demonstrated.

Do not multiply token output difference directly into a capability claim. Softmax/logit sensitivity and downstream autoregressive divergence can amplify small numeric changes. Conversely, token-sequence disagreement alone is not proof of meaningful capability loss. Measure both local numerical drift and held-out task outcomes.

## Bounded 2/4-chunk waves vs the 1,662,831,872-byte figure

The 1,662,831,872 B value is **not free VRAM**. R594/R599 identify it as `Prefill::Impl::owned` accounting (1.55 GiB) retained beyond prompt in the serve object, with no decode-boundary measurement establishing how much is safely reclaimable. It can be discussed only as a hypothetical ceiling if a future approved, fully drained retirement actually releases the entire allocation. It is not an allocation promise, and retiring it during prefill would remove buffers that this same run needs unless replacements are included.

For a wave of W rows, logical allocations are: FP16 X=`W*5120`; IDs+weights=`W*80`; exact route-slot Dm=`W*102400`; one FP32 accumulator=`W*10240`; shared=`W*10240`; sg=`W*4`; HC inj=`W*16`. Current chunk scratch already allocates `T*K*N*4` Dm plus chunk-bounded Xs/shared/sg/inj (`prefill.cpp:845-899`). An incremental planner could retain existing current-chunk allocation as baseline and account only growth beyond it, but the saved prefix inputs must remain resident concurrently with Dm/accumulator/shared or be copied repeatedly.

| Existing chunk C | Wave size | X FP16 | Exact-order Dm | One FP32 accumulator | Shared FP32 | Dm plus X + accumulator + shared + inj (metadata excluded) |
|---:|---:|---:|---:|---:|---:|---:|
| 8192 | 2 chunks = 16,384 | 80 MiB | 1.5625 GiB | 160 MiB | 160 MiB | about 2.0 GiB |
| 8192 | 4 chunks = 32,768 | 160 MiB | 3.125 GiB | 320 MiB | 320 MiB | about 4.0 GiB |
| 4096 | 2 chunks = 8,192 | 40 MiB | 0.78125 GiB | 80 MiB | 80 MiB | about 1.0 GiB |
| 4096 | 4 chunks = 16,384 | 80 MiB | 1.5625 GiB | 160 MiB | 160 MiB | about 2.0 GiB |

The rightmost combined estimate includes both exact-order Dm and the one-accumulator comparator; those are mutually exclusive designs. Exact Dm + X + shared + inj alone is about 1.797 GiB for C8192/wave2 and 0.898 GiB for C4096/wave2; for wave4, about 3.594 GiB and 1.797 GiB respectively. These figures include the logical saved activation, but omit ids/weights, slot/source maps, active dequant GU/Down, existing QSA/GDN scratch, temporary expert tile Xs/Hh/GU, queue reserve, model/session/KV and allocator overhead.

Against 1,662,831,872 B as a *hypothetical additional budget*, exact-order C8192/wave2 Dm alone is 1,677,721,600 B, already 14,889,728 B over; including other tensors moves further over. C8192/wave4 and C4096/wave4 are also impossible under that notional budget. C4096/wave2 (8,192 rows) uses exact Dm 838,860,800 B; with activation, shared, inj and routing metadata the incremental payload is approximately 1.0 GiB, so it is arithmetically within that notional 1.548 GiB envelope. It still needs a real live-free query, 512 MiB reserve, layer expert cache, all current device owners and a safe plan for persistent prompt scratch. For the one-accumulator reorder, C8192/wave2's accumulator is only 160 MiB; X+accumulator+shared+inj is around 0.391 GiB, and C8192/wave4 about 0.781 GiB, before the same omissions. C4096 waves are smaller. Thus reordered accumulation has much more room for a two/four-chunk device wave, but still requires an actual measured admission and quality gate.

The current prefill scratch has `m.Dm` capacity exactly `T*K*N` FP32, so at T=8192 its logical Dm is 800 MiB and at T=4096 it is 400 MiB (`prefill.cpp:890-899`). The 1.663 GB owned total includes other persistent/chunk owners; it is not spare headroom to add on top. The 8192/two-wave Dm requires doubling the existing 800 MiB route matrix to 1.5625 GiB for a single 16K wave, an incremental 800 MiB if other current allocation is unchanged; the rest of the wave owners also need added capacity. An allocation planner should report both total and delta relative to the live existing carve, plus measured free VRAM at the correct boundary. Do not claim the reported total can simply be reclaimed wholesale.

All 512 decoded FP16 weight pairs for one layer would be `512*9,830,400=5,033,164,800 B` (4.6875 GiB), so they cannot coexist on a card with only the notional 1.55 GiB released budget. One expert pair is 9,830,400 B (9.375 MiB) and can fit as a bounded active tile. A wave can preserve the prepared activations and accumulator on device, run experts one at a time, then retire the wave. It can avoid ten route copies of activation and Dm PCIe traffic, but repeats expert dequant once per wave. Whole prefix with 32 chunks at C=8192 and wave2 would have 16 waves; wave4, 8 waves. At C=4096, 64 chunks produce 32 or 16 waves. For 32K/64K, respective wave counts are `ceil(n/(C*wave_chunks))`: e.g. C8192 gives 2/4 waves for W=2 and 1/2 for W=4; C4096 gives 4/8 waves for W=2 and 2/4 for W=4. Any dequant saved fraction is therefore bounded by observed per-expert recurrence across waves; no route histogram in R620 establishes it.

## Proposed review order and disposition

1. Use the real Arc implementation and FP16 expert input contract above. Do not change activation representation as part of the first schedule experiment.
2. Compare two alternatives: (a) exact per-route-slot FP32 outputs with bounded chunk waves and current slot-ordered `postops.cpp` combine, (b) one FP32 routed accumulator with expert-major addition order. Keep `Rstore` ownership and HC `inj` lifetime explicit. The first protects current arithmetic but retains a larger Dm tensor; the second is the plausible low-VRAM design and requires the quality experiment.
3. Prefer an 8192/2 wave or 4096/2 wave only after the real free-memory receipt and complete buffer liveness calculation. With the notional 1.663 GB budget, the former misses the budget on Dm alone; the latter fits arithmetic payload but remains unqualified. Four-wave C8192 and C4096 exact-Dm cases exceed that notional budget. Reordered one-accumulator cases look much more plausible for 2/4 chunk waves, subject to validation.
4. Record actual H2D/D2H bytes at ownership boundaries. A design that sends each expert's routed FP16 inputs from RAM separately costs 10x the one-copy activation volume. A design that spills exact `Dm` off-device costs up to 50 GiB round trip at 262K. Either could erase dequant gains; source math cannot determine crossover. Keep waves and per-expert work on device where admitted, and avoid serialization only when ownership remains bounded.
5. First correctness/quality experiment should compare current Arc route with the reordered FP32 accumulator on fixed prompt content and task suite, report local errors/logits and noninferiority outcomes, and retain cancellation/RESTORE/MTP/checkpoint behavior. Then paired end-to-end tests must measure dequant, host packing, transfer bytes, PCIe time, wave refill and total wall time. R621/R623 do not claim success or choose a user-facing quality threshold.
