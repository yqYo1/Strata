## Main finding

The shipped profile is structurally compatible with the current 48-layer, 512-expert model shape, but the repository cannot establish that its ranking matches this model's present decode route. Its header says version 1, 48 layers, 512 experts, 24,576 ranked pairs, 24,576 slots; file size is 196,632 bytes and mtime is 2026-10-02. SHA256 is `8f59b4aa8873209dff11c11e37bcda9529a1335b724a1afeea37bf6388975baf`. The reader checks the layer/expert dimensions and ranked-pair bounds, but does not bind a profile to model weights, tokenizer, route corpus or model revision; it also currently ignores the version field. Matching dimensions establish shape compatibility only.

The file is a ranking, not a frequency histogram. In the `STRP` layout the ranked pairs are followed by a dense 48×512 table of rank indices (`-1` when absent), despite an old header comment calling this a frequency table. `tools/make_profile.py` confirms the table maps each pair to its rank. No per-expert frequency can be recovered from the profile. The limited file read is consistent with this format and the exact size.

The current evidence is compatible with keeping profile/cache optimization open. The fixed FP32 MTP4 ledger has two 34K requests at 128 emitted tokens: CPU owned 97.00% and 96.94% of route entries, with mean CPU job `nt` 1.469 and 1.510. These are aggregate owner and job-size marginals, not expert IDs. They do not show which profile ranks were routed, which individual experts were GPU-owned, or an attainable hit rate for a different placement. The measured `--expert-cache 128 --expert-cache-per-layer`, pool-5-plus-host configuration remains a point on the sweep, not evidence that the cache is optimized. The 10 GiB card's free VRAM differs between first and repeated requests; the prior receipt records only 2,312 MiB free after MTP return on the second request, and its FP16 residual + 1.3 GiB cache + 512 MiB reserve arithmetic does not fit. Any sweep must preserve physical 256K host fallback and query actual free memory at each request boundary.

## What the CLI and source actually do

`--expert-profile P` loads a startup ordering. `--expert-cache N` is the total slot count; it does not mean N slots per layer. `--expert-cache-per-layer` partitions that total among model layers (for 128 total slots across 48 layers, roughly two or three slots per layer, subject to the helper's allocation and slot sizing). In SYCL native-pack mode, per-layer slot sizes use the owning layer's blob size. The startup fill walks the profile ranking and admits each layer's highest-ranked pairs until that layer's quota is full. With global admission, the list is instead truncated by total slots/byte capacity. The file's ranked list is therefore usable for initial placement, including under per-layer admission.

The CLI has profile collection/reordering paths, but no direct expert histogram or histogram-output switch:

* `--dump-routing PATH` on a one-shot engine run writes routed expert IDs and weights for each layer and position. `tools/make_profile.py TRACE... --reorder --out PATH` can rank those observed IDs ahead of the base profile. Since the shipped base already ranks every pair, passing traces without `--reorder` leaves its order unchanged. This is a full routing trace, not a bounded histogram; it should not be used for a long request without an explicit byte cap and retention plan.
* `--expert-profile-save PATH` is serve-only. It saves between requests and on QUIT when enabled, and requires adaptive swaps plus an input profile. It accumulates the adapt tier's `usage` into `heat`, then writes resident pairs first, remaining pairs by accumulated heat, prior rank and pair index. It is a convenient learned ordering, not a raw histogram export: residency is given priority, the heat is decay-weighted, and no counts are emitted.
* `--expert-cache-per-layer` only changes admission/slot ownership. It does not disable or replace adaptive swaps. Defaults in the current CLI are `--adapt-every 4`, `--adapt-decay 0.7`, and `--adapt-swaps 96`; the live swap code considers missing experts with decayed usage at least 2 and swaps when a candidate exceeds a resident's usage by 1.5. Swaps remain within a layer and are submitted asynchronously, then published when the refill event completes. For a static-placement comparison, explicitly set `--adapt-swaps 0`; for the existing dynamic policy, keep its normal values and record the setting. A run with an unknown setting cannot be described as static.

The native route path already has the routed IDs at `expert_pool_dispatch_multi`. It increments `d.usage[layer,expert]` before classifying each entry into VRAM hit versus CPU miss. The joined decode ledger then records layer/T, owner totals, CPU unique jobs, CPU `nt` marginals and logical byte totals; it intentionally does not preserve IDs. Its owner percentages and `job_nt` distribution therefore cannot be joined after the fact to the 24,576 profile pairs. The 34K records' route distribution cannot be reconstructed from these compact receipts, and no missing expert frequencies are inferred here.

## Minimum evidence to decide profile fit and a static hit ceiling

For the first useful pass, add an opt-in counter to the existing eligible decode observer at the existing issuer-side route classification point. Keep it disabled by default, allocate only for the bounded diagnostic, and have no pool-worker writes or per-entry atomics. The update can follow the existing issuer-side `usage` increment; accumulate each routed occurrence (not unique jobs) into a `uint64_t[layer][expert]` counter. That is 24,576 × 8 = 196,608 bytes (192 KiB), plus a small header. Emit one compact binary counter file only at successful observer close, bounded at 193 KiB, with source/config/request IDs and a hash in the receipt. The counter should distinguish decode requests, so two 34K requests are independently reviewable. This reveals the current route histogram and permits an exact static hit ceiling for the observed route under the actual per-layer slot quotas and measured cache byte budget. Keep any prompt histogram separate; decode-only counts answer the current decode question.

To compare actual ownership and the counterfactual static ceiling in one run, retain two per-expert owner counters (GPU-cache and CPU) at the point each route entry receives its owner. This is 384 KiB total (two 192 KiB arrays) and remains fixed-size. This identifies which routed IDs currently go to each owner, including dynamic cache state over the whole request. For no peer/remote configuration, the two classes cover the expected route; otherwise add explicit owner classes or reject the receipt. Preserve the existing ledger completion checks and mark histogram overflow/incomplete output as unusable.

The static ceiling calculation is: for each layer, use the captured counts to rank experts, then take at most that layer's actually admitted slot count, respecting the same blob-byte budget. Divide the summed captured occurrences in those slots by all captured route occurrences. Also calculate the current profile's hit share from the same counts and slot plan. This reports an observed-route upper bound for fixed per-layer capacities, not generalization to other prompts, and it is an entry hit fraction rather than a token/job fraction. Compare a profile generated on one bounded request with a separate held-out request; the current two requests have different generated IDs starting at position 42, so they are distinct samples but not clean performance pairs.

The two arrays do not show swap timing or predict the best adaptive policy. If adapt-policy comparison is needed after static ranking is understood, collect a second bounded, one-byte-per-route owner/ID stream with window and request boundaries, capped at 1 MiB for at most 300 emitted tokens; write it only from the existing issuer/observer, never workers. Its purpose is replaying observed windows through a candidate swap rule, not preserving full API text or prompt routes. On cap/overflow, stop the diagnostic capture and mark it incomplete; do not silently sample and call the result exact. Alternatively, compare existing adaptive on/off arms empirically without claiming a simulated dynamic optimum.

## Bounded configuration sweep and guardrails

Run settings as a serial diagnostic after permission for actual measurement, keeping model, prompt/context, MTP4, pool 5 plus host participation, one device, resident-RAM complement and the host-tail 256K path fixed. Keep the cache count total and settings explicit. A practical first ladder is 128, 192, 256 total slots with `--expert-cache-per-layer`, each under the same 700 MiB reserve and a fresh `cudaMemGetInfo` admission recorded after persistent owners are established. Test the existing full-profile ranking with adaptation disabled first (`--adapt-swaps 0`); then compare the same accepted capacity with the existing adaptive setting enabled. Do not run all sizes if the live query plus reserve cannot admit the next one. Use `--expert-cache auto` only as a separately recorded placement decision because first/repeated request allocations can select different slot counts. `--expert-profile-save` is optional for a later held-out learned-order check and should target a dedicated artifact, never overwrite `data/expert-profile.bin`.

For every request, record free/total VRAM before cache allocation, after fill, after the 34K prompt/prefill owners, after any MTP detach/restore, before the first decode window, and after close. Use the actual live cache bytes from startup output, not `slots × max blob` as a claim of exact bytes. Preserve the per-request FP16/FP32 residual decision and host fallback. In particular, repeated-request free VRAM of 2,312 MiB after MTP return is the binding prior observation; don't size from the first-request free value or assume returning MTP's 675 MiB makes FP16 residual, cache and reserve coexist. A 256K residual remains host-backed/streamed under this capacity. Judge each placement from complete route/owner counts, output correctness, fresh-fault status, and clean repeated end-to-end decode samples with diagnostics disabled for performance acceptance. This investigation did not authorize or perform that measurement.

No external engine reference is needed: the current CLI, `make_profile.py`, the startup cache fill, adaptive swap implementation, and the retained native ledger directly answer the source questions. No TG70 hit estimate or DRAM-bandwidth extrapolation follows from the current evidence.
