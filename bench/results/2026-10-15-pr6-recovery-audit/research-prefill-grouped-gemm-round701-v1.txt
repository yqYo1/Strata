# R701 — SYCL long-prefill grouped/batched MoE GEMM再評価

2026-10-15 JST。指定された現在source、既存report/index、保存済みprofileをread-only確認し、oneMKL公式仕様と実装例を調べた。唯一の新規書込みは本report。コード変更、build/test/GPU/process起動、environment/Git操作、cleanupはしていない。mainのserial clean測定には介入していない。指定されたprivate `prefill-gemm-only-contract-root-v1/record.json`、Codexログ、home内の探索対象外データは読んでいない。

## 結論

今回の調査で、実装を再開できる新規grouped-GEMM候補は見つからなかった。前提となるoneMKL APIは実在し、必要なFP16×FP16→FP32出力と可変行数/別ポインタを表現できる。しかし、同一shape群を一括で渡すためのweight/activationの同時保持と前処理が必要で、APIが実際にGPU command/launchを減らすことや現在の実行時間を短縮することは仕様から分からない。既報R496/R566/R575はgrouped GEMM案とscratch/lifetime/実経路評価をすでにカバーしており、同じ提案を繰り返す理由はない。

新たな判断材料は、oneMKL 2026.1環境にある仕様上の対応範囲と、今回のprofile値の読み方を確定したことに限る。API prototypeは評価用sourceとして保持できるが、現状は採用候補ではなく、Mainが別途実測ゲートを開かない限り再提案しない。

## 現行経路と固定条件

`src/prefill/prefill.cpp` のlong layer-major MoE fallbackは、layer内のactive expertsを順に処理する。expertごとにpacked GGUF weightをFP16へdequantし、compact時はactivation rowをgatherし、GU GEMM、SwiGLU、Down GEMMを同じSYCL in-order queueへ積む。Qwen expert形状はN=2560、FF=640、top-k=10、512 experts。各expertのrouted row count `ne` は異なる。DownのCは`Dm + o0*N`にあるexpert固有のglobal row rangeへ書く。`src/prefill/sycl/gemm.cpp` はrow-major oneMKL GEMMを呼び、実モデルのfallbackはFP16×FP16 input / FP32 output。`include/strata/sycl/launch.hpp:60` の`finish(stream,event)`はnon-null streamならhost waitしない。したがって現在のoneMKL呼出し数がそのままCPU wait回数ではない。一方、oneMKL側submission内部のhost work/syncはこのno-op finishからは判断できない。

32K censusのne分布は別の34K request条件で、`ne<=16`がactive callsの55.13%でもrouted rowsは1.386%に過ぎない（R575）。R628は、layer/chunk単位のhistogramを失ったlayer-total censusから、同shape group数は復元できないと指摘している。今回の指定profileはC8192/34603 batched-inputであり、旧censusの値をそのまま適用できない。

## oneMKL/oneMath/oneDNNのAPIと制約

Intel oneMKL DPC++ `gemm_batch` USM group APIは一回のAPI呼出しで複数GEMMの配列を受け、各groupについてtranspose、m/n/k、alpha/beta、lda/ldb/ldc、group sizeを指定し、各GEMMのA/B/C pointer arrayを渡してeventを返す。公式type tableに`sycl::half × sycl::half -> float`（alpha/beta float）がある。従って現FP16 operandsとFP32 accumulation/outputの型契約はAPI上表現可能である。A/B/C pointerは各operation別にでき、Cのexpert別`Dm+o0*N`を指せる。寸法/leading dimensionはgroup単位なので、`ne`の違うexpertsは同じgroupに混ぜず、ne別groupに分ける必要がある。各group_sizeを1にすれば異なるneを全て一API callに載せる形式自体は可能だが、各operationが異なるshapeのままで計算効率が上がる保証はない。

Strided APIは共通shapeで行列を一定strideに置く形式で、異なるne、非等間隔の`o0`出力、個別weight ownershipを持つ現routeに直接は合わない。Buffer APIはstridedのみ。pointer-list向けのUSM APIが候補だが、APIが受け付けることとArc B570で効率的な単一/少数kernelへlowerすることは別である。oneMKL仕様は戻りeventを示すが、同API内部がone kernel/少数kernelで処理するとは約束していない。Intel配布の`gemm_batch.cpp`例もAPI利用例で、Arc B570/2026.1上のcommand-count証明ではない。現行oneMKLのgroup API実装がhost loopとして各gemmを個別にsubmitするか、grouped device kernelになるかを公開一次資料から確定できなかったため、「host loopなら除外」という条件に照らし、ここを未解決の必須評価ゲートとする。

oneMathはoneMKL-compatible APIの選択/dispatch層として別hardware backendを使う余地はあるが、oneMKL2026.1上で同じArc target routeに実装優位がある証拠は確認できなかった。oneDNNの公開MatMul APIはMoEのper-expert variable-M pointer-list/group APIではなく、Strata sourceにも現在oneDNN MoE GEMM pathはない。いずれも現oneMKL経路の差し替え案としては候補にしない。

配列・pointer所有権の設計を仮に評価する場合、A/B/CのUSM allocationはqueueのcontext/deviceに適合し、実行event完了まで解放・再利用しないことが必要。C pointer間の重複は独立operation前提を壊す。host側のA/B/C pointer arrays、各groupのshape/ld/alpha/beta/group_sizeも、APIが同期的にコピーしたとの実証がなければ戻りevent完了まで保持する。API docsは配列引数を示すが、そのhost memoryをいつ内部copyするかまでは lifetime契約として説明していないため、event完了保持が保守的な扱いとなる。現在の`dq_gu[2]`/`dq_d[2]` rotating scratch、compact Xs、Hhをそのまま使うと、異なるexpertsのGEMM入力とdequant weightsをgroup submission時点で同時に揃えられない。buffersを追加するか、producer/completion scheduleを変える必要があり、memory capacity、GU→SwiGLU→Down順序、weight cache-slot releaseを同時に守らなければならない。

公式 oneMKL docsの`dependencies`でevent依存を指定可能だが、現行はin-order queue順序に依存し、group入力を完成させてから同queueへsubmitする形が最小の移行になる。別queue化はR502/R566の既報二queue停滞とevent契約に反する別変更なので、この候補に含めない。API submit数が減っても、同一in-order queue上のgroup全体が同一event境界になることでlater dependent workが遅れればcritical pathは改善しない。

## 同一API方式と実測の境界

既報の結論との重複を避けるため、今回新たに測るべきものは提示しない。既報がすでに述べる必要条件を、採用可否の簡潔なgateとして再掲する。

- 実際の現profile条件でlayer/chunkごとにne histogramと同shape群数を算出する。別requestの32K histogramをC8192に外挿しない。
- 製品のoneMKL 2026.1/Arc B570で`gemm_batch`が本当にcommand-list/kernel launchを減らすことを、API/command traceまたは一次実装sourceで判定する。内部host loopで通常GEMMを個別submitするなら候補終了。
- batched pointer/group plan構築、retained FP16 operands/weights、gather/dequant、event後のstorage releaseを含む同じworkload境界で、current GEMM-per-expert routeと比較する。単にC++ call countが減っただけでは採用根拠にならない。
- C8192 capacity/admission、FP32 output/parity、same queue order、physical262144 correctness/RESTOREなど既存のMain gatesを維持する。GPU clean serial workloadを使い、active runへ割り込まない。

## profileから言える上限

指定した`main-prefill-window-profile-review.ja.md`が示す旧実収集はrequest span 238.371 s、GPU compute union 100.154 s、copy union 39.950 s、GPU busy間gap 98.266 s、CPU wait union 75.817 s（うち75.147 sはGPU busyと重なる）。API totalは988,382 `zeCommandListAppendLaunchKernelWithArguments`、`zeModuleCreate` gap重複19.316 s、launch API gap重複9.745 s。これらは旧収集のprofile値で、新しいclean binaryの性能見込みではない。

grouped GEMMが最も楽観的に縮め得るのは、実際にまとめられるGEMM submissionsによるhost/API gapの一部であり、全98.266 sのgapや全988,382 launchesではない。profileではGEMM固有のhost-gap寄与が分離されていないので、改善可能時間の数値上限を専門的に狭められない。極端に緩い絶対上限でもrequest spanを超えないだけで、役に立つ推定値ではない。GPU compute100.154 sは有用な仕事を含み、grouped形式が演算を消す根拠はなく、丸ごと削減対象ではない。Main reviewは旧238.371 s窓もclean throughput/pure-prefill intervalと区別している。よってこれらからspeedupや600/1000 tok/s達成時期は推定しない。

## 既報との照合・参考実装

R496はoneMKL grouped APIとgroup-of-four synthetic Downの+2.85%例を既報化し、多くのgroup-of-two条件は遅く、compact pathのactivation/dequant scratch再利用はgroup入力を同時に保てないと指摘済み。R566は同shape grouping一般、metadata/scratch追加、oneMKLがfusion/speedupを保証しない点を記載済み。R575は小neの同shape Down groupingを条件付き候補として絞り、実ne別group頻度、retained Down-weight bytes（各3,276,800 B）、metadata/dequant/submit/drainの合計、capacity gateを明示済み。R628は正確なchunk-level censusなしではshape groupsを復元できず、small-ne呼出しの多さを演算量・性能効果に読み替えないと記載済み。従って本reportではこれらを新提案として扱わない。

他実装から得られるのは戦略の参考のみである。SGLangの公式設計資料はMoE dispatch/pre-permute/core/post-permute/combineを分け、DeepGEMM/CUTLASS等の専用backendでgrouped GEMMを使う。vLLM XPU kernelsにはCUTLASS/Xe2 grouped GEMM backendがある。これらは自前専用kernel/異なるXPU量子化backendの実例であり、oneMKL batch APIのcommand削減証明ではなく、Strata IQ2/3→FP16 dequant経路にも直接移植できない。作者ブログは、expertごとに異なるMの小GEMMを単純launchする時のlaunch overheadが動機で、固定shape batched GEMMとMoEのvariable-shape grouped GEMMを区別している。Intel LLM ScalerはIntel GPU上のvLLM framework製品を指すが、今回確認できる公開overviewだけからoneMKL grouped GEMM route/Strata型の実行形は確認できない。いずれの別GPU測定も本機の期待性能に流用しない。
