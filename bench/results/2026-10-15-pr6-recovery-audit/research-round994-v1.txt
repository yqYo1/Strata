An important exact invariant is (c_e \le R): duplicate IDs within one token are refused, so any expert appears at most once per row. A full-count expert therefore needs two 8192-row jobs; a small count needs one. For a maximally skewed legal route (the same ten experts on all rows), that is 20 jobs. For a broadly distributed route, up to 512 first jobs are possible. The helper reserves capacity for 1024 jobs; with 512 possible first jobs and total (M), no more than 19 experts can require a second job, giving a 531-job mathematical bound for this exact (M). These are shape-derived bounds, not an observed route distribution.

## Alternatives and fit to the maps

### Hierarchical histogram, prefix, stable scatter

A work-efficient portable shape is a tile histogram followed by a hierarchy of scans and a scatter. Reusing R761's 64-ID tiles gives (S=\lceil M/64\rceil=2,560) tiles. Each histogram row has 512 int32 bins (2 KiB local histogram); global tile-bin scratch is (S E 4 = 5,242,880) B (5 MiB). A `bad[S]` vector, 20 blocks of per-expert totals/offsets, expert counts/offsets, and a status word bring the illustrative scratch total to about **5,298,184 B (5.05 MiB/window)**. The core work is (O(M + E S)); this version zeros/writes 1,310,720 bins, then scans the tile prefixes, block totals, and 512 expert totals. It must still validate IDs and route mass and enforce (c_e\le R).

For exact stability, each tile's occurrences of an expert need a stable local rank (R761 used comparisons against earlier IDs in the 64-entry tile, at most (M(64-1)=10,321,920) comparisons at this window size). The scatter then writes:
- `slot_map[i] = F[e] + tile_prefix[tile,e] + local_rank` for flattened (i=tK+k);
- `source_rows[p] = i/K` at that same packed position (p).

This reproduces the host helper's expert-major stable layout directly in the existing device arrays and leaves `weights[t*K+k]` untouched. The compare-based rank is simple and deterministic but can cost more than the histogram/scan work; local subgroup ballots or tile-local scans are alternatives, with subgroup-width and code-generation behavior to qualify on the actual SYCL device.

A 64-ID tile limits each local histogram's traffic but not its hot-bin contention: in a skewed legal route, ten experts can occupy every tile. Local histograms avoid a single global atomic per occurrence but repeatedly initialize 512 bins even when only ten are active. The `E*S` term doubles R761's 8K estimate for this 16K window. At physical context 262,144, 16 windows process 2,621,440 route records and 20,971,520 tile-bin entries per MoE layer (80 MiB of 32-bit bin values per full histogram write pass); current route-control transfers total 30 MiB/layer across those windows. With one window in flight, the 5.05 MiB scratch is reused 16 times rather than retained at context scale. These are algorithmic bytes, not measured B570 traffic or timing.

The map destinations can be the existing `ids_slots` and `source` views. In the stable scatter, each work-group must load its entire tile's IDs before writing `slot_map` over the input ID view; no later phase may need original IDs. Histogram scratch is live through scatter, then dead before the first down-job output. `source_rows` is live through the last gather, and `slot_map` through combine; the current final checked drain is the existing release point. The region allocator is exactly consumed at `used == 998,443,520`, so this cannot be added after the current arena. It needs a separately validated allocation or a proven temporary overlay in the dead `down` region between router preparation and the first down output. Concurrent windows multiply scratch by their in-flight count; full physical context does not itself require 16 simultaneous map allocations.

### Expert-key sorting / segmented runs

A second path sorts the (M) route records by expert, then identifies runs to form counts and offsets. A **stable** sort over expert keys preserves original flattened order within each expert; alternatively sort a composite ((expert,i)) key to make tie order explicit. Emit `source_rows[p]=i/K` and inverse `slot_map[i]=p` while walking sorted records. Run lengths directly yield the current 8K job split, with no histogram table. This costs (O(M\log M)) for comparison sorting or a small fixed number of radix passes over the 9-bit expert key, plus sorting temporary storage and run extraction. A key/value pair needs at least two (M)-element arrays (640 KiB each at int32); practical stable device sorts commonly need additional buffers, and exact scratch size depends on the implementation. Stable tie order matches the helper exactly; an unstable sort can still preserve FP combine order only if its inverse map is complete, but it changes deterministic maps and violates the current helper's explicitly stable output contract.

This path treats hot experts as ordinary sort keys and avoids the histogram's repeated 512-bin rows, but it still moves/sorts every route and needs temporary key/value storage. It is most attractive when sort support is already qualified and (E S) histogram traffic is high; neither condition is established here. For any sort, a per-token duplicate check remains necessary to preserve the current refusal contract. Padding every expert run to a block size is not a free substitute: it changes job lengths and can exceed the exact (M)-row source/Down capacity unless all views and combine masks are enlarged or redesigned.

### Atomic cursor scatter

A histogram/scan can first establish each expert's base, then a global per-expert atomic cursor can assign positions as IDs are scattered. That removes stable local ranks and may simplify work, but route order inside each expert becomes scheduling-dependent and skew concentrates atomics on ten counters. If the inverse `slot_map` is written consistently, the final combine still reads expert outputs in original (k=0..9) order; therefore expert-row permutation alone need not change the FP32 accumulation sequence. It does change the currently tested deterministic maps, and any missing, duplicate, or mismatched slot/source write corrupts routing. Keep this as a distinct relaxed-map-contract candidate, not a drop-in implementation of the present stable helper.

## Host dispatch and synchronization boundaries

All device phases can be enqueued in order on the existing stream/queue or linked by explicit events. Histogram, scan levels, expert-prefix construction, and scatter still require **device-wide phase boundaries** between kernels; work-group barriers only synchronize a group. A multi-pass kernel DAG avoids a grid-wide spin barrier and does not assume unscheduled work-groups make forward progress. The exact number of scan kernels depends on the chosen hierarchy (R761's bounded-block design used histogram, segment-prefix, block-prefix, expert-prefix, scatter); these are queue dependencies, not host-blocking drains.

The current CPU consumer iterates the actual jobs, looks up each expert's host residency slot, dequantizes that expert, and passes the runtime `job.rows` to oneMKL GEMMs (`:125–175`). Therefore a GPU-built map alone does **not** remove the first host-visible synchronization: host dispatch still needs counts/job shapes before issuing those calls. One candidate copies only 512 counts plus a status word (2,052 B), computes offsets/jobs on host, and waits once before dispatch. Copying offsets too would be 4,104 B. Either retains a first checked drain and the final HC-write drain: **two host-blocking boundaries per window**, but replaces the 640 KiB ID return and 1.25 MiB map uploads with a few KiB of metadata. No CPU route scatter or full ID readback remains, though CPU job construction and host dispatch remain. If counts are instead used to build device job descriptors, the existing host oneMKL API still requires host-known dimensions; R768 correctly leaves device-only oneMKL group metadata unverified.

Reducing that to the existing **single final checked drain** requires changing the consumer too: for example, a fixed upper-bound device dispatch that guards inactive jobs and consumes device descriptors, or a qualified indirect launch/custom device GEMM path. This entails a new route-to-dequant/GEMM scheduling design, not only route-map construction. Do not introduce a global work-stealing queue or a spinning inter-work-group barrier as a shortcut. Error status must prevent invalid IDs or counts from reaching gather/GEMM; with a device-only consumer it must be checked or propagated before unsafe indexing, with asynchronous faults still reported at the final checked drain.

## Upstream and primitive evidence; provenance limits

- **vLLM**, Apache-2.0, source pinned to commit `026f6ab2689397e64c1f53a5ac57d37c4dc46b67`: [`csrc/moe/moe_align_sum_kernels.cu`](https://github.com/vllm-project/vllm/blob/026f6ab2689397e64c1f53a5ac57d37c4dc46b67/csrc/moe/moe_align_sum_kernels.cu). The alignment path uses CUB block scans and atomic placement and emits block-padded expert rows/IDs. It demonstrates an established CUDA alignment path, but it does not produce Strata's exact unpadded source/inverse maps, and atomic placement is not a stable token-slot ordering.
- **SGLang**, Apache-2.0, source pinned to commit `a126e8d640c707f855e8da31f906035883f4ff70`: [`python/sglang/kernels/aot/csrc/moe/moe_align_kernel.cu`](https://github.com/sgl-project/sglang/blob/a126e8d640c707f855e8da31f906035883f4ff70/python/sglang/kernels/aot/csrc/moe/moe_align_kernel.cu). Its current CUDA implementation counts into shared bins, pads each expert count to a configured block size, then uses per-expert atomic placement for flattened route indices. The native path is useful implementation evidence for histogram + prefix + scatter, and a counterexample to assuming stable order or exact unpadded capacity.
- **oneDPL**, official oneAPI Specification 1.3-rev-1, [Parallel API](https://oneapi-spec.uxlfoundation.org/specifications/oneapi/v1.3-rev-1/elements/onedpl/source/parallel_api) and [Parallel Range Algorithms](https://oneapi-spec.uxlfoundation.org/specifications/oneapi/v1.4-rev-1/elements/onedpl/source/parallel_api/parallel_range_api.html), retrieved 2026-10-17. That API contract does not establish a no-host-fallback path, B570 support, scratch size/lifetime, queue completion behavior, or performance.
- **Khronos SYCL 2020**, [barrier and fence reference](https://github.khronos.org/SYCL_Reference/iface/barriers-and-fences.html) and [SYCL 2020 spec](https://registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html?from=20423&from_column=20423), retrieved 2026-10-17. - **NVIDIA CCCL/CUB**, source pinned to commit `38671dcfbed77c287817282c6411bb615179dfb9`, [DeviceRadixSort header](https://github.com/NVIDIA/cccl/blob/38671dcfbed77c287817282c6411bb615179dfb9/cub/cub/device/device_radix_sort.cuh), and [DeviceScan documentation](https://nvidia.github.io/cccl/unstable/cub/api/structcub_1_1DeviceScan.html), retrieved 2026-10-17.
