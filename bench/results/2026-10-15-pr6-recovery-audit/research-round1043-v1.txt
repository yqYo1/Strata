## Current schedule and invariant contract

The exact path is `prefix_batch_impl<33,false,false>` through `qsa_bf16_prefix_optimized_batch`; workgroup=128, required subgroup=16, hence eight subgroups. Grid has one group per query and KV head (two KV heads). Each group stages 16 query-head rows (12 real, four padded) and processes selected IDs in Cells=32 chunks. Rows absent through invalid/out-of-live-range IDs or unmapped pages are `-1`; score and V staging use zero for missing rows, while online softmax excludes their scores. This is selected-ID attention, not a contiguous causal scan: preserving the ID order, live-cell and page-table checks, zero/missing semantics, and status propagation is mandatory.

The tensor contract is BF16 Q/K/V, BF16 probabilities (round each probability before PV), FP32 XMX score/PV accumulators and FP32 online max/normalizer/alpha; final output is BF16. Score and probability/online-state association changes can alter results. The already-existing subgroup-softmax variant changes FP32 sum association and is a prior experiment, not a fresh recommendation. Prefix matrix groups 0–3 each do an 8x16 score tile for 16 padded head rows by 32 cells; groups 4–7 do no score GEMM. In PV all eight subgroups participate; each owns eight head rows and a 64-dimension output slice, with four FP32 8x16 accumulators. All work-items reach each workgroup barrier; subgroup-specific matrix branches are uniform per subgroup. The five barriers in each chunk fence rows, K staging, score output, V staging/softmax dependency, and PV accumulator reuse. There are also one-time initialization and post-initialization fences.

## Static SLM and matrix work

The source's local payload includes Q `[16,256]` BF16, KV `[Cells,256]` BF16 (reused K then V), probability `[16,Cells]` BF16, FP32 scores `[16,ScoreStride]`, 16 each of max/normalizer/alpha, `Cells` int64 row IDs, and 16 integer head flags. It excludes implementation/compiler padding and any hidden allocation. Formula: `2*(4096 + 256*Cells + 16*Cells) + 4*(16*ScoreStride+48) + 8*Cells + 64` bytes. At C=16/32/64 with matching score stride, totals are 18,304 / 28,160 / 47,872 bytes. Current stride33 adds 64 B over stride32 (28,224 vs 28,160). These are source sums, not actual per-SM occupancy limits or measured allocation. Matrix shape remains M8,N16,K16. Full tile work pads 12 heads to 16, so one quarter of M rows are mathematically padded; source masks output for padded heads, but whether the device suppresses any hardware work is unproved. Cells 16/32/64 keep N work exactly filled in groups of 16; score has respectively 1/2/4 16-cell tiles per head tile, PV likewise. No proposal here increases the real-head fraction absent a different M mapping.

## Bounded alternatives and counterevidence

1. **C16, 128 work-items / 8 subgroups.** Halves KV/probability/score working storage versus C32 (18.3 KB vs 28.16 KB) and retains full N=16 matrix columns. It doubles chunk iterations and the five per-chunk barriers (plus repeated online update and V gather); total mathematical matrix work and padded-head fraction are unchanged. This is a plausible occupancy/latency trade if local-memory allocation is a real residency cliff, but can lose through extra barrier and loop overhead, repeated row/ID work, and a longer dependency chain. It preserves sequential cell-ID and per-chunk online update order, but changes chunk boundaries, so `sum` partitioning and `exp2`/FMA online rounding can change even though BF16 storage points remain.

2. **C64, 128 work-items / 8 subgroups.** Could halve chunk/barrier count, but grows static local payload to 47.9 KB and multiplies row IDs/score storage. An allocation that crosses a local-memory residency threshold can cost more resident groups than the saved barriers; larger FP32 score state and more live work can also raise registers. It does not increase mathematical XMX work or improve real/padded ratio; 4 score subgroups still serve 16 head rows. More per-chunk work could amortize loop/ID overhead if many cells are selected, but can be a net loss at short widths or under high occupancy pressure. Chunk-size change alters online FP32 rounding as above.

3. **64-work-item group with 4 SIMD16 subgroups.** Source mapping could retain the four score subgroups with no subgroup idle during QK; to preserve PV coverage it must either give each subgroup twice as many output-dimension tiles/accumulators (eight rather than four FP32 8x16 accumulators) or split/reduce output ownership. First option halves threads while roughly doubling per-thread accumulator ownership and likely raises register demand; second adds a cross-subgroup reduction or another launch and changes FP32 accumulation order. The local payload remains the same if data layout unchanged. It may relieve workgroup scheduling overhead but may reduce resident workgroups from register pressure, and cannot be assumed better without compiler resources. All work-items still must converge at group barriers; any narrower mapping must re-derive `tid` loops and collective participation. This is not a simple `Workgroup=64` substitution.

4. **Overlap staging with compute / fewer fences.** A double-buffered K/V tile could in principle stage the next selected-ID rows while current tile softmax/PV consumes the other buffer, but doubles much of the 16.4 KB current K/V area (additional ~16,384 B for a second C32 BF16 tile) and requires a proven async-copy or cooperative overlap path. Ordinary group barriers cannot be removed while consumers may read a buffer being written; buffer phase and all-work-item convergence must be explicit. K next-tile copy can overlap current score-to-softmax work only if that work is mapped to work-items that also perform the copy without violating SLM ordering. No source establishes useful overlap or XMX lowering here; extra live buffers/indices may reduce occupancy. The present compute path is synchronous `joint_matrix_load/mad/apply`, so no asynchronous XMX pipeline should be presumed.

Splitting one query/KV head across workgroups over ID ranges could increase group count, but exact online attention then needs a second-stage merge of partial `(m, l, O)` states, and output ownership/status handling. That adds scratch/launch/global traffic, changes merge arithmetic and rounding, and would no longer be a barrier-only schedule change. In-kernel workgroup barriers cannot synchronize groups. Treat as a separate algorithm, not an unqualified scheduling tweak.

## Prior work and evidence limits

The index already records R1013's source accounting and explicit redundancy with R568 (head-tile/SLM), R605, and R954/R955 subgroup-softmax; its report is held for Main. The current index says the tilepack cohort median was 459.1 tok/s row-major versus 459.3 dense16/VNNI, not adopted due to inconclusive difference/high variance and an overlapping job; a later profile attempt was preflight-refused while a foreign CPU benchmark remained active. Do not retry or recommend the packed path as a default. Its source path also changes operand layout, which this question does not need. The index's old device profile and FP32 shared/diverse sensitivity evidence are older configurations; they do not supply current BF16 barrier stalls, register/SLM allocation, XMX use, occupancy, cache/DRAM traffic, or physical bandwidth. Overlapping phase durations do not imply 77% GPU use or saturation. The existing strict 256K numerical-reference failure is unresolved; no relaxed gate or numerical qualification follows from this analysis.

## Prerequisites for any Main-owned measurement

First finish the active score-GEMM cohort and establish the exact runtime selector/source/build identity for `prefix_batch_impl<33,false,false>` plus the retained baseline. Then capture same-path generated device code and per-kernel compiler resources (GRF/register, spills/private memory, local memory) before claiming a likely occupancy cliff. Main should choose one alternative at a time, preserve selected-ID/order, malformed-ID/page and padded-head behavior, BF16 probability rounding and FP32 state; check strict numerical references including physical 262144 context and retain the existing unresolved failure as a blocker. Run isolated paired repeats with whole dependency-path attribution (including staging and synchronization); do not infer XMX participation, occupancy, cache/DRAM, or bandwidth from source or phase overlap. Any changed chunk size must be evaluated for numerical-order differences under the actual SGLang/vLLM execution contract, without relaxing existing gates.
