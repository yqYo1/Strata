## Findings

**No concrete out-of-bounds or double-advance defect was found for the admitted <=65,536-row accumulation window.** The candidate path has distinct planes for FP32 routed accumulation, per-route weights/maps, HC injection, per-chunk gathered/hidden/down/shared scratch, W FP32 shared gates, and the BF16 producer input. `MoeAccumPlan` bounds and rounds every plane with guard reservation; the caller checks the actual region span, every typed view, mixed allocation, residual bank, embedding scratch, and writable/input overlap before submission (`moe_accum_plan.hpp:35-89`; `src/prefill/moe_window.inc:15-56`). For 65,536 rows the gate is 262,144 bytes, matching its writes and final `rows`-wide reads (`moe_window.inc:77-92,143-151`). Temporary preparation storage in the legacy mode-2 helper overlays its Down plane only before expert outputs exist; that is a separate layout (`moe_window.inc:187-228`).

The mode-8 producer/consumer chain is internally consistent in source. Each 8,192-row slice reads the saved BF16 residual bank, computes HC norm/down/up/injection, then writes BF16 router logits/FP32 route weights, the original BF16-derived shared scalar gate, and contiguous FP16 mixed rows (`moe_window.inc:76-92`). It never derives the scalar gate from the FP16 sibling. Router IDs are read back only after a stream drain, validated on host, then the stable expert-major inverse-slot and source-row maps are uploaded; `job_weights` maps sorted route positions back to original route weights (`:93-106`; `native16.cpp:184-195`). Every expert job is at most 8,192 rows, gathers from the saved FP16 mixed stream, computes GU/SwiGLU/Down, and accumulates BF16 Down outputs into FP32 (`moe_window.inc:109-134`; `native16.cpp:197-218`). The final per-chunk shared projections consume the FP16 stream; the FP32 accumulator plus BF16 shared output and retained FP32 scalar gate become BF16 BO, and HC write updates the BF16 residual from FP32 injection (`moe_window.inc:143-151`; `native16.cpp:221-229,117-124`).

The no-atomic update preconditions are represented in code: route-plan construction validates every ID is in [0,511], rejects duplicate expert IDs within a token, and forms stable per-expert rows; a job partitions one expert’s rows into non-overlapping <=8,192 segments (`moe_window_routes.hpp:75-112`). The device update additionally checks the inverse slot and `source == slot/10`, setting status bits on invalid mappings (`native16.cpp:207-218`). `accumulator_routes` requires the matching inverse plan and an in-order queue (`:170-175`); jobs and kernels are submitted serially on `m.cs`. Thus each job’s work-items write distinct token/column cells, and separate jobs cannot overlap concurrently on this queue. The order is ascending expert, with FP32 FMA updates. It differs from original route-slot accumulation order and remains a numerical change; this audit makes no quality or backend-contract claim.

**Scheduler/callback flow:** `run_impl` marks a window only over complete residual chunks on the device; it extends the range no farther than request end, GPU prefix, or owner maximum, enforces contiguous piece order, and stores each attention result in the bank before continuing (`src/prefill/prefill.cpp:1883-1900,3510-3535`). A window piece runs one half of the ordinary layer loop; the source identifies this as the same causal attention/PLE body, while the helper does FFN only (`prefill.cpp:2321-2326`; `moe_window.inc:76`). After each window FFN, the checked HC write drain precedes stage callbacks and per-piece completion. At the final layer, completion restores each bank piece to the existing FP32 callback interface; a layer-major cursor rejects duplicate/out-of-order callbacks and checks complete coverage (`prefill.cpp:3538-3545`; `layer_major.inc:603-625,683-695,725-738`). Source therefore shows one attention/PLE traversal per original chunk and one FFN per grouped window. The helper does not re-run attention, PLE, recurrent append, or token gather.

Windows are bounded to 65,536 rows for accumulation by admission and the helper guard, while final partial chunks are consumed with `min(T, rows-at)` in preparation, shared epilogue and write loops. Examples: an 8,193-row resident request becomes an 8,193-row accumulation window with one full plus one one-row chunk; a 70,000-row request is capped into a 65,536-row window and leaves the remainder to the ordinary path. At physical context 262,144, layer-major residual spans remain a whole-chunk device prefix followed by host tail; window admission requires both opening chunks to be device spans and the end is capped at `gpu_rows`. Later host-tail chunks therefore use existing chunk processing rather than a window. Final output callbacks are counted over the whole request, not just windows (`layer_major_plan.hpp:90-136`; `prefill.cpp:1883-1900`; `layer_major.inc:255-273,737-743`). This establishes source bounds/scheduling only; physical-context execution and RESTORE remain unverified.

Mode 0 remains the default; values 0/2/8 are accepted. Mode 2 keeps its original <=16,384-row helper/factory and mode-2 route limits; mode 8 is enabled only by the explicit request, native16, 8,192 chunk, scratch-alias, single-stage topology, no-prefix-checkpoint and GPU-window conditions. If the VRAM budget cannot admit mode 8, the code leaves accumulation disabled and reports effective mode 2 (`prefill.cpp:455-463`; `layer_major.inc:45-59,262-280,498-508`). Existing mode-2 per-window shared gate remains its own W-sized layout. No source evidence here proves runtime behavior or full compatibility on device.

**Lifetime and error path:** the mixed/device residual allocations and `MoeWindowContext` live outside the checked `DraftUploadGuard`; the guard drains compute and copy queues before restoration/free, and aborts if it cannot prove retirement (`layer_major.inc:286-297,384-435,757-758`). Host IDs and the immutable route owner are context members. Both route uploads, kernels, status readback and BO/HC writes share the in-order compute stream. A failed route readback/drain returns false before map construction; the status host destination is initialized to all ones and retained by the context, and failed async copy or synchronization cannot be mistaken for status-zero success (`moe_window.inc:93-105,136-142`). Error exits after submissions leave context and allocations live through outer retirement; failed retirement aborts with owners still alive. After a successful HC write drain, the route owner is reset before callbacks/MTP can reuse shared scratch (`:143-160`; `layer_major.inc:392-435`; `prefill.cpp:3533-3545`).

## Caveat and remaining source-proof gaps

Mode-8 fallback is demonstrated for the explicit VRAM/headroom budget test, but not for every late admission failure. `make_contiguous` is called after `accumulation_rows` is selected and may throw if `m.region_bytes` cannot hold its planes; that exception reaches the outer layer-major error return rather than retrying mode 2 (`layer_major.inc:262-273,772-778`). Likewise, if `cudaMalloc` of the mixed slab fails after the free-memory estimate, the request errors instead of downgrading (`:487-493`). These are conditional robustness gaps, not proven failures for this fixed 8,192-row arena and not a claim that the plan does fail: the snapshot does not record a computed plan-vs-actual-region admission result or an allocation-failure fallback case. If the intended contract is “mode 8 whenever request is 8, else transparently use mode 2,” add/record a preflight fallback decision for these cases.

Still unverified, and must stay separate from this source result: actual engine build completion and full-engine integration; runtime SYCL/oneMKL/vLLM dispatch and async error behavior; a fresh model run, numerical/task quality, performance, full physical-262144 correctness and RESTORE; preservation of mutable session/recurrent state under cancellation; and failure injection proving outer lease retirement for each submission/copy failure. The candidate itself only checks cancellation at preparation/job/finalization loop boundaries, so cancellation can stop between those boundaries after some attention work has already advanced state (`moe_window.inc:77-80,110-112,143-145`; `prefill.cpp:1883-1886`). Cancellation returns failure and does not roll back session state; callers must treat that state as invalid or restore it. The source proves neither that caller policy nor fault-path behavior.
