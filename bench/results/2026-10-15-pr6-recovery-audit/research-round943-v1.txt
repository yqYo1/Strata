# R943 — Chunked recurrent scans and hardware dataflow beyond LLMs

**Scope.** Compare stable ways to parallelize recurrent updates across long sequences, with attention to what transfers from signal processing and fixed dataflow hardware to a Gated Delta Network (GDN) long-prefill path. This is a source review, not a Strata benchmark or an implementation proposal. None of the cited speedups establish performance on this engine, GPU, sequence length, or model checkpoint. No source code was copied.

## Recurrence and boundary contract

A useful starting form is the affine update

`h_t = A_t h_(t-1) + b_t`.

For two adjacent updates represented by `(A1,b1)` then `(A2,b2)`, their composition is `(A2 A1, A2 b1 + b2)`. Composition is associative over exact arithmetic, although it is generally not commutative. This gives a legal prefix-scan operator. It does not imply that every recurrence has a small or cheap summary: a scalar or diagonal `A` has a compact summary, while a dense `d × d` state map requires a dense summary and can erase the benefit of scanning.

A low-rank update also need not have a low-rank sequence summary. For example, if each transition is a scalar decay times identity plus a rank-one correction, composing transitions introduces cross terms; the rank of the accumulated correction can grow with the number of steps. This is why a per-token rank-one delta rule does not justify scanning a fixed-size list of rank-one factors as if composition remained rank one. WY-style chunking exploits the specific structure and bounded chunk, rather than claiming the entire history has a constant-size summary. The same caution applies to covariance and control recurrences: a structured update may have exploitable factors, but the closure and storage cost of its composed map must be derived first.

The chunk boundary must carry the exact state needed to continue the next chunk, with the model's agreed state dtype, gate convention, and rounding points. For a GDN head, the recurrent memory is a matrix, with token updates involving both a gate and a delta-rule correction. A scalar affine pair is therefore not a valid drop-in summary for the full head update. The GDN paper derives an extended WY representation that reorganizes the chunk's dependent rank-one updates into a chunkwise parallel form. It uses within-chunk query/key interactions and matrix multiplications, while passing a boundary state between chunks. The reformulation exposes parallel work; it does not remove the chunk-to-chunk dependency.

The related SSD/Mamba-2 formulation is instructive but not interchangeable with GDN. Its chunkwise decomposition separates within-chunk causal interactions from inter-chunk recurrent state, turning much of the token work into matrix operations. GDN adds selective delta corrections, so its particular WY derivation and numerical path must be used rather than assuming that an SSD kernel implements the same recurrence.

## Three dataflow choices

| Approach | Dependency and work | Data movement and synchronization | Fits best / loses when |
|---|---|---|---|
| Blocked affine summaries and prefix scan | Local recurrences produce one summary per block; a scan composes summaries; each block applies its prefix carry. A work-efficient tree has linear total combine work and logarithmic scan depth, compared with the extra work of all-prefixes-at-every-level schemes. | Summaries are compact only when the state map is compact. A hierarchical GPU implementation needs local scans, block summaries, a scan of those summaries, and carry propagation, commonly across kernel/event boundaries. Materializing every token's full state defeats the purpose. | Attractive for scalar, diagonal, or otherwise structured SSM/IIR updates, many independent streams, and long inputs where serial depth is material. It can lose on short sequences, few streams, small batches, expensive dense summaries, or when launches and global carry traffic exceed saved serial work. |
| Chunked WY / SSD-style matrix formulation | Retains recurrence between chunks but evaluates a chunk's internal interaction in parallel using causal matrices and GEMMs. Chunk length controls parallel depth and matrix reuse. | Requires chunk-local operands and usually scratch for intermediate interactions/state. Pairwise within-chunk work and storage grow with chunk length (often quadratically in the token tile); GEMM/tensor-matrix units can make this efficient, but scratch traffic and launch cost remain. | A strong candidate for GDN prefill when there is enough sequence and head work to amortize setup and matrix operations. Small chunks underfill matrix hardware and repeat boundary/launch overhead; large chunks increase quadratic work, temporary storage, and register/local-memory pressure. It is not automatically good for decode or short input. |
| Register / shared-local-memory (SLM) producer-consumer tile | A workgroup owns the live recurrent state and advances it over a token tile, while lanes cooperate on projections, reductions, and outputs. Token order within an owner remains serial unless paired with a scan or chunk transform. | Keep the live state in registers where feasible; stage only the current tile in local memory and use workgroup barriers for producer-consumer handoff. This avoids writing expanded per-token state to device memory. Double buffering can overlap stages, but consumes local memory/registers and may reduce occupancy. Inter-workgroup dependencies need a later kernel/event or a separate summary/carry phase; a workgroup barrier cannot synchronize all workgroups. | Useful for short tiles, low launch budgets, or as the local kernel inside a chunked method. It loses when each workgroup carries too much state, spills registers, waits at barriers, or there are too few independent sequence/head owners to fill the device. |

These are composable choices. A common structure is: summarize each chunk, scan chunk summaries, then run a fused local tile kernel using each chunk's carry. The extra pass is justified only if it exposes enough independent work to pay for summaries, scratch, launches, and the changed floating-point order. A single-pass lookback scheme can reduce passes on some GPU designs, but depends on forward progress, memory-ordering, and scheduling assumptions; it should not be assumed portable to a general SYCL device.

## Lessons from non-LLM workloads and fixed dataflow

Recursive image filters have the same basic tension: an IIR recurrence constrains pixel order, while naive independent tiles lose information at tile boundaries. Chaurasia et al. show divide-and-recombine transformations inspired by prefix scans and use producer-consumer locality across pipelines of filters. The transferable idea is to derive a boundary summary and schedule dependent stages near their consumers, rather than materializing every intermediate image/state. Their results are for image-filter pipelines and their compiler's transformations; their reported speedups do not predict GDN speed. The author manuscript is marked CC BY-NC-SA, so it is a design reference only here.

The classic recurrence-to-systolic-array literature makes the hardware tradeoff explicit: recurrence equations can be mapped to pipelined processing elements with local state and regular neighbor communication. This is useful for thinking about bounded state movement and deterministic schedules. A fixed ASIC can dedicate wires and registers to one dataflow; a GPU must share registers, local memory, and execution slots across workloads. Prefix networks also trade depth against fanout, wiring, area, and switching. A shallower tree is not necessarily a lower-energy or easier-to-route design, and this fixed-hardware literature is not evidence that a software scan wins on a GPU.

Merrill and Garland's GPU scan work is relevant to the global boundary problem: hierarchical device scans aggregate block results and propagate prefixes while managing synchronization and redundant work. Its main lesson is architectural: the local scan primitive is only one stage; cross-block summary propagation is part of the algorithm and can dominate. It studies generic scan, not a GDN state algebra or a one-kernel solution for arbitrary recurrence.

## Numerical stability and precision

Associativity is exact-arithmetic algebra, not a floating-point guarantee. A parallel tree changes multiplication/addition order relative to a serial token loop; a chunked WY formula also changes where products and sums round. Therefore, bitwise equality with a serial FP32 path is not a reasonable general adoption rule by itself. The relevant comparison is the validated inference contract of the actual same-model path, including storage formats, accumulation and reduction precision, normalization, gate/beta computation, state persistence, and the points where values are rounded or cast.

For decaying scalar recurrences, long products of gates may underflow; rewriting terms as ratios of cumulative products can also magnify error if those products are tiny. Chunk-local rescaling or log-domain accumulation can help in some formulations, but each changes the arithmetic path and needs a proof for the represented recurrence. For GDN, gates and delta corrections interact with a matrix state; do not assume that an SSM's scalar-decay stabilization automatically applies. Retain the required FP32 local accumulation/reductions and persistent state where the model contract requires them, even if hidden-state storage is reduced to 16 bits. Compare BF16 and FP16 by range, rounding, and measured behavior rather than byte width: both use two bytes, but their exponent and mantissa tradeoffs differ.

A sound chunked design should state what crosses each boundary: state layout and dtype, gate/cumulative-decay representation, tail handling, and whether the chunk output is computed from the incoming state or a zero-state contribution plus a carried contribution. Check finiteness and drift over increasing chunk counts, not only one chunk. Preserve the physical context limit, state lifetime, and fault/bounds behavior as independent gates. Do not let a numerical pass excuse changed persistence or out-of-range access.

## SYCL transfer and fallback requirements

SYCL 2020 group algorithms provide subgroup/workgroup scans and explicitly warn that results are nondeterministic when the operator is not associative. The affine pair operation is noncommutative but associative in exact arithmetic; its combine order must therefore be implemented as a generalized prefix, not reversed under the assumption that scan means commutative sum. Floating-point reassociation still needs the tolerance and state contract described above.

A portable scan design should query/use the selected group's actual size and supported local-memory capacity, use group collectives and barriers only within their defined scope, and separate device-wide carry propagation into kernels or queue events. It must not rely on a vendor tensor-core extension for correctness. A matrix-accelerated path may require an optional backend-specific matrix extension; keep a scalar/vector or ordinary-matrix kernel for devices without it. The device requirements should be explicit: workgroup scan support, local memory if staging tiles, enough registers/local memory for the live state, and matrix acceleration only for the optimized WY path.

The CPU fallback should be an explicit host implementation of the same recurrence and chunk-boundary convention. It may parallelize independent heads/sequences, but a single recurrence stream remains serial unless it uses the same mathematically valid summary method. Label timings as CPU fallback rather than implying the GPU performs that arithmetic. The API should select the backend from discovered capabilities and preserve a deterministic fallback route; it should not silently claim successful GPU execution when a matrix extension or required group feature is absent.

## Public same-family implementation references and limits

The public SGLang integration and vLLM Qwen gated-delta path are useful to anchor the target algorithm family and backend split. In SGLang v0.5.20, the attention backend documentation lists CPU GDN prefill/decode support as well as Triton paths across several device families; the repository's Qwen integration is pinned in the project audit at commit `19ece249fac1407953aa54389c3af8fe91bf951f`. In vLLM, the pinned Qwen4Exp model path at commit `fa75d3456d60a5ffe923818c4b495295675b38e1` invokes `QwenGatedDeltaNetAttention`, whose shared kernel source identifies the Qwen3-Next/Qwen3.5 GDN family. That shared source includes CPU routing and FP32 conversions around one FlashInfer state/gate/beta path. These facts establish available implementation choices and boundaries, not which branch ran for a specific input or whether its arithmetic matches this fork. Architecture names/checkpoint variants differ across sources; confirm a model's actual resolver and dispatched kernel before treating a path as same-model numerical evidence. SGLang and vLLM source repositories declare Apache-2.0; use them as checked references, not as a basis for copied code here.

## Decision guide and unresolved evidence

For a scalar/diagonal recurrence, first compare a serial fused tile against blocked affine summaries: the latter is promising only when prefix depth saved exceeds summary traffic and synchronization. For a GDN matrix recurrence, prioritize a chunkwise WY implementation or another proven GDN-specific transform; do not compress it into scalar scan pairs. Keep chunk-local work fused enough to avoid writing the per-token state history, then measure the complete dependency path including summary generation, carry scan, local computation, transfers, and launches. Sweep chunk size only with the same numerical contract and tail path. Retain a simple serial/local path for short work where scan and GEMM setup dominate.

Evidence still needed before selecting among them on this engine: observed source dispatch for the target model, per-stage whole-path timings, actual CPU time outside GPU waits, launch and synchronization cost, local-memory/register pressure, and numerical comparisons against the chosen SGLang/vLLM contract across long sequences and chunk boundaries. The literature supplies transformations and failure modes, not these measurements. No source here establishes a throughput result, 256K correctness, or RESTORE behavior for Strata.
