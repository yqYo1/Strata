# R744 — IGC RA metadata format and runtime resource evidence

2026-10-16 JST. Read-only research. I did not build, test, run GPU/toolchain/profiler commands, control processes, mutate environments, clean files, or change Git. I inspected only the specified Strata reports, capture recipe/receipt, and the first 64 bytes of one captured RA artifact. I did not inspect the protected prefill record or XeStrata source.

## Finding

The captured `.ra_metadata` is a binary product. The first listed 717,580-byte file begins `01 00 00 00 f9 19 00 00 01 00 00 00 ff ff ff ff ...`; this is observation only. Intel's public IGC configuration documentation promises that `ShaderDumpEnableRAMetadata` adds an RA Metadata file, but the public documentation/source reviewed here does not specify its serialization, field IDs, versioning, or a supported standalone decoder. I found no primary-source schema/parser that can safely assign meanings to offsets in this blob. `read_text()` failing is expected for binary data and provides no format clue. Do not reverse-engineer offsets or interpret the header as GRF, spill, SLM, or scratch numbers.

For useful kernel resources, prefer human-readable final compiler/runtime outputs from the same actual JIT process, and label each value by provenance. IGC `ShaderDumpEnable` gives the shader dumps (including VISA/GenISA and final assembly/ISA products depending on this build); `DumpZEInfoToConsole` emits ZEInfo; `ElfDumpEnable` saves ELF. The current receipts establish that v1 used the exact-symbol regex and captured 11 `.ra_metadata` files plus `SIPKernelDump.bin`, but did not capture asm/ISA. The planned v2 broader bounded regex should recover the matching human-readable artifacts. It must match one intended mangled kernel and then correlate basename, specialization and SPIR-V entry point; `.*symbol.*` may also match other artifacts/specializations, so count/name/hash the output and retain only matched kernel evidence.

## What can be extracted, with limits

- **Compiler register mode/count:** Record `grf_count` from the matching kernel's ZEInfo if emitted; it is a compiler-reported kernel property. Cross-check against final ISA declarations/comments only when this IGC build prints an explicit count. Do not infer a count from the `.ra_metadata` header or from kernel SIMD width. GRF count/mode alone is not occupancy.
- **Actual SLM allocation:** Query the exact live `ze_kernel_handle_t` with Level Zero `zeKernelGetProperties`; `ze_kernel_properties_t.localMemSize` is the direct runtime property for the kernel handle. Record bytes, kernel identity and when queried. This is the strongest direct route if the app can expose the already-created handle. Otherwise, take the per-kernel SLM field from captured ELF/ZEInfo only if the exact version's output names and units are explicit, and cross-check with the Level Zero query. Do not infer SLM bytes from local-accessor source declarations or hardware dispatch encoding.
- **Scratch/private-memory requirement:** Capture the exact kernel's ZEInfo and retain explicit per-kernel private/scratch fields only when the emitted key and unit are visible. A SYCL `kernel_device_specific::private_mem_size` query (where supported by this runtime) is a useful API-level cross-check, but should be recorded under that API name rather than silently relabeled as scratch traffic. A private-memory requirement is not a dynamic spill-byte count or memory-traffic measure.
- **Spills:** Use final VISA/GenISA text to identify explicit spilled declarations and final ISA to identify explicit spill/fill operations, if present in these outputs. Report counts/bytes only when the output gives them unambiguously; static source/spill declarations do not quantify executed spill traffic. The binary RA metadata is not a substitute without an Intel-published decoder/schema.
- **Occupancy/performance:** None of the above proves occupancy, active waves, throughput, spill traffic at runtime, or performance. Those require separate runtime/performance evidence. In particular do not turn GRF count or SLM size into an occupancy estimate without the device scheduling limits and exact execution conditions.

## Bounded capture recommendation

For Main's new immutable child-process capture, keep all IGC and NEO variables in that child environment before `exec`, preserve actual mapped library paths/hashes, exact executable/image/kernel identity and the receipt's byte caps. Add the documented `IGC_ShaderDumpEnable=1`, `IGC_ShaderDumpEnableRAMetadata=1`, broad-but-symbol-anchored regex, and supported `IGC_ElfDumpEnable=1` / `IGC_DumpZEInfoToConsole=1` only if the active loaded IGC accepts them; mark each artifact type present/absent rather than treating a set flag as proof it worked. Avoid broad pass dumps and retain only per-kernel artifacts plus SHA-256, sizes, paths, selected field/value/unit/source, and tool/runtime version. ELF/ZEInfo may contain many kernel records; filter the output offline by exact symbol, with the raw console excerpt retained only if needed to validate parsing.

Use the app's already-held kernel handle for `zeKernelGetProperties.localMemSize` if instrumentation can be added in a separate reviewed build; do not use a second independently compiled kernel as if it were the exact captured dispatch. If adding application instrumentation is out of scope, ELF/ZEInfo is the minimal diagnostic route and must be described as compiler/driver metadata rather than direct handle-query evidence. Preserve the old capture as historical evidence; do not mutate it.
