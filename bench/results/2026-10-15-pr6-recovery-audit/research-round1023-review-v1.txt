The caller therefore invokes qsa_block_scores, which consumes FP32 pooled/dead keys and FP32 query, computes four 128-element FP32 head dots, applies ReLU per head, sums them, applies the existing partial-tail bonus, then writes scores. It skips columns beyond each query's own n_bid. The distinct top-k kernel follows immediately and retains the existing selector mapping. The measured QSA selection interval starts before this loop and ends after it; it includes score and top-k. The reported roughly 15.8 s queue interval is nonexclusive, so it cannot establish scoring share, GPU busy time, hardware utilization, or a bound speedup.

Any dense GEMM proposal still needs an explicit per-query dead-tail mapping: a shared W cannot substitute the dead key at a different n_bid for every query by itself. One viable shape is a dedicated dead-key row/column scored for all query-head rows, then a post-kernel gathers that query's dead score into its n_bid column and applies +1e9 only when n_kv%4 is nonzero; a separate per-query dead dot is another option. The pooled score at that position must not survive as the tail score. The current top-k reads only through each query's n_bid, but the candidate must keep future columns out of all consumed outputs.

The producer audit confirms q_idx is a float reservation with shape [T,512]; indexer q/k projections write float destinations, followed by FP32 RMS norm and RoPE. The native16 QSA opt-in changes attention Q/K/V paths but not the indexer projection. idx_raw and the pooled/dead index keys remain FP32 at this score boundary. A BF16 score arm is therefore an added score-input rounding stage, not evidence that the existing producer has become BF16.

## GEMM API clarifications

R1022 accurately describes the optional vLLM-shaped out16 route's central limits, but the report should distinguish its layers and the existing FP32-output path:

- The public Gemm bf16_out16/f16_out16 surface accepts compact X[T,K] and W[N,K] rows, with one input format for both operands and independently selected FP16/BF16 Y[T,ldy]. It exposes output stride only; there is no ldx or ldw. Flattening q_idx's four consecutive 128-wide heads yields X[4*nq,128] without a transpose, but q_idx still needs FP32-to-16 conversion. The pooled key matrix also needs conversion or a separately maintained packed view.
- The default own out16 backend accepts N and K multiples of 16. The optional vLLM adapter is stricter: beta=0, N%64=0, K%32=0, 64-byte bases, ldy>=N and ldy%8=0. At max physical context, max_blocks=65,538 and a 64-aligned logical N is 65,600. K=128 satisfies both routes. The adapter has no caller-provided scratch/workspace and no ldx/ldw; it requires registered device allocations and validates a live full Y[T,ldy] span. Its Problem object borrows the runtime and queue; the direct adapter returns an event and owners must survive until drain. The public Gemm out16 wrapper calls finish before returning, so the wrapper is synchronous.
- The adapter itself accepts BMG G21/G31, but the current Gemm wrapper's vLLM route guard restricts entry to BMG G21 AOT. Do not generalize the adapter's architecture check to the integrated entrypoint.
- FP32 accumulation does not preserve the old FP32 scorer's rounding location: out16 stores each of the 4*nq head dots to 16-bit before a later ReLU-and-sum epilogue. The current fused output API cannot expose its FP32 accumulator to that epilogue.
- This limitation belongs to the out16 route. Existing Gemm bf16()/f16() methods return FP32 output through the prior library route; R589 already investigated the broad score-only FP32-output GEMM idea and packing/stride issue. R1022 is additive because it analyzes the newer local AOT adapter's alignment, output rounding, full rectangle, and lifetime constraints plus a fused alternative. Do not index its general GEMM feasibility as a wholly new candidate.

For the one-shot vLLM-shaped matrix M=4*nq, N=65,600, K=128, Y alone is 134,348,800 bytes (128 MiB) at nq=256. The existing FP32 selector matrix is 67,110,912 bytes (about 64 MiB); the matrix output is therefore about twice that footprint before conversion/epilogue scratch. A full BF16 pool pack is about 16 MiB, and the query pack about 256 KiB. These are candidate bounds, not an observed allocation or peak; layer-major shared-arena reuse, query tiling, and key-pack lifetime may change the net reservation. The report's concern about maximum-context headroom is warranted.

## Scope, novelty and numerical applicability

R1022 is substantive and source-specific. It compares the scalar fallback, a packed native16 GEMM with a separate epilogue, and a fused subgroup matrix design; it accounts for query/head packing, N alignment, partial/dead/future columns, selector stride, output rounding, memory, queue/owner lifetimes, and explicit no-go conditions. The central decision—split score and top-k timing before spending a build or GPU run—is sound. The fused 8-query/4-head by 32-key tile is a hypothesis only; the report correctly says shape legality, convergence, BMG lowering, and speed remain unproved.

Novelty relative to R589 is bounded rather than wholly new: R589 already covers score-only GEMM feasibility, K=128 shape, key/query conversion, top-k/route quality gates, and cost inclusion. R1022 adds constraints from the current out16/vLLM adapter and a fused alternative. Its strongest retrieval value is the adapter geometry and owner/output footprint section. Avoid describing the score-only GEMM idea itself as first introduced here.

The precision discussion follows the active reference policy. BF16 Q/K plus FP32 dot is an approximate scorer until a specific SGLang/vLLM runtime contract for this checkpoint is identified; FP32/llama.cpp bit identity is not a required adoption criterion. Selected-cell changes are neither presumed harmless nor automatically disqualifying. The official current SGLang and vLLM Qwen3.5 source pages are family references only: as fetched 2026-10-17 their model files contain no “indexer” match, and their mutable main URLs provide no exact local Qwen3.8-Flash-Next kernel, dispatch, activation dtype, or rounding contract. The report accurately limits that inference. Pin immutable upstream revisions and identify the actual reference runtime/selected kernel before a future numerical-contract study.

Intel’s experimental matrix specification supports the convergence and device shape-query caveats; its status is explicitly experimental and backend/type/shape support is queried per device. Intel’s 2024-1 guide states that XMX requires XMX hardware and offers no emulation/fallback. These sources support design constraints, not this kernel’s legality or performance. The report names direct URLs and repository licenses, but SGLang/vLLM and Intel LLVM links use mutable main/sycl branches rather than immutable revisions. This is acceptable for the report’s narrow source-availability and API-contract caveats; pin commits before using any model or compiler source as an adoption contract. No external source code was copied.
