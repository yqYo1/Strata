# Round 911 — OA metric-set registration and the pool-create failure

**Classification:** decision support  
**Scope:** read-only source trace of the new metric-pool diagnostic through the pinned Metrics Library, Metrics Discovery, compute-runtime, and upstream Xe OA kernel paths. No build, test, runtime, device, profiler, process, permission, package, or Git operation was run. The report is source analysis, not a new collection result.

## Finding

The new evidence makes a failure during Metrics Library context/TBS initialization the leading source-consistent explanation for the pool error. The seven library messages include the failed `m_Tbs.Initialize()` and `m_Kernel.Initialize(m_ClientData)` checks, plus a condition requiring either an active or internal metric-set ID. In the pinned compute-runtime path, a failed Metrics Library initialization makes `MetricsLibrary::createMetricQuery()` return before its `api.QueryCreate()` call; the performance pool then maps that `false` result to `ZE_RESULT_ERROR_INVALID_ARGUMENT`. Thus, if these messages came from the recorded pool call as the receipt indicates, query creation with 64 slots was not reached. This supersedes count=64 as the first diagnosis to pursue, but does not identify the failed syscall.

The `Paranoid mode check failed: Paranoid mode is not available` warning is not itself a return failure. Metrics Library 1.0.231 selects `/proc/sys/dev/xe/observation_paranoid` for XE2-HPG, reads the value, logs when it is nonzero, and unconditionally returns success from that check. The receipt records this value as `1` and the native process had `CapEff=0`; those facts fit the kernel permission gate, but the run did not record the actual `DRM_IOCTL_XE_OBSERVATION` errno. The failure remains unqualified.

## What creates the kernel ID file

`zetContextActivateMetricGroups` returning success is not proof that a configuration was registered in the driver. In compute-runtime 26.31.39395.14, the ordinary OA path defers activation until `zetMetricStreamerOpen` or `zeCommandQueueExecuteCommandLists`; the captured call is followed directly by pool creation, with no queue or command list. The registered ID file is a kernel product: userspace sends `DRM_IOCTL_XE_OBSERVATION` with operation `DRM_XE_OBSERVATION_OP_ADD_CONFIG`; the Xe driver creates the per-GUID metrics directory and read-only `id` attribute.

There are two userspace routes to that ioctl:

1. **Metrics Library bootstrap.** During `ContextCreate`, `KernelInterface::Initialize` calls `TbsStream::Initialize`. The 1.0.231 implementation first reads `/sys/class/drm/card%d/metrics/2f01b241-7014-42a7-9eb6-a925cad3daba/id` (the root-device query GUID also used by Metrics Discovery). If no usable ID is available, it calls its `CreateMetricSet()` fallback. On XE2-HPG that builds a one-register dummy OA config and sends `DRM_XE_OBSERVATION_OP_ADD_CONFIG`; then it tries to open the TBS stream. If both the active and fallback IDs are invalid, the `Enable()` condition shown in the log fails and context creation propagates failure.
2. **Metrics Discovery group activation.** For an actual event metric group, compute-runtime's `createConfiguration()` first requires Metrics Library initialization, then calls `IMetricSet::Activate()`. Metrics Discovery locks the group and sends its query register configuration through `SendPmRegsConfig()` to the XE `AddOaConfig()` implementation, which sends the same `ADD_CONFIG` operation under the query GUID. Only after that operation succeeds is there a usable kernel ID for Metrics Library to read; `Deactivate()` releases the group lock after configuration creation.

This order matters. The successful context-level activation API in the receipt only deferred the group. Pool creation asks Metrics Library to initialize before the source path can call Metrics Discovery `IMetricSet::Activate()`. Therefore a bootstrap config/read failure can prevent the real group activation from ever being attempted. The generic `Cannot get kernel metric set` warning identifies a failed read of the library's configured ID path, but the source does not print an errno when `open()` fails. The paired “active or internal ID” condition is consistent with both lookup and bootstrap creation failing; it does not say why.

## Version boundary and current-source check

The diagnostic maps `libigdml.so.1.0.231` (SHA256 `8f4ffe4a856c441d4c85bd7d7de6ad7672c59812fe4655d2a8843c32eba97075`) and `libigdmd.so.1.16.188` (SHA256 `c8908112387576f28023c28cc0be0f456de93af8e99b3bc5259e09e0fa876cd9`); package metadata labels Metrics Library `1.0.231` and Metrics Discovery `1.14.188`. I traced the official Metrics Library commit `74eac4065c178a2d459b9fba3acbf38a2fef4dc3` and the Metrics Discovery `1.16.188` tag commit `bb0f72f1258a44549d2a1281301ecb18753d0c06`, selected by the loaded SONAME. These are source references, not proof the mapped binaries were built from those exact sources. Compute-runtime package 26.31.39395.14 maps to upstream commit `050536ff3b6f830199ec99cff8ffcac3d804c40a`; its manifest requests Metrics Discovery 1.16.192 and Metrics Library 1.0.234. The version skew is real, but neither source set establishes a supported-version range or that skew caused this failure.

I checked the directly related current Metrics Library change, commit `6faaeee013218d8491d3c5b21a184622b8d2ad87` (2026-10-14). It refactors config discovery to enumerate the shared metrics directory and track config IDs/index nodes; it still initializes TBS and uses Xe `ADD_CONFIG` for its fallback. That difference is not evidence of a fix for the recorded denied-or-missing operation and does not justify an update recommendation. The current Metrics Discovery commit `a68a52bdecc1e12e37511e59580317d1184ff757` changes metric-description/device-ID sources, not the Xe config-add path.
