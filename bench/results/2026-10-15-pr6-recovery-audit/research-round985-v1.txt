# Round 985 — Small-M quantized MoE alternatives after the actual window gain

Classification: knowledge collection. This is a source-based design comparison, not an implementation proposal, benchmark, or performance claim for the B570. No project source was copied or adapted.

## Reused evidence and boundaries

I used only the indexed metadata and the relevant R977 sections (“What the census establishes”, “Design comparison”, “Bounded first screen and gates”), the R979 review digest, and the R973 review digest for R971/R972 corrections. R977 is `research-round977-v1.txt` (index SHA-256 `f44aa648b6520ca771d0585f85009ad9611cb37cd2a9bd9ce5a054ae6d682d9a`). R979’s retrieval record says its original bodies remain held; its digest confirms that the earlier matched window comparison closed and identifies the small-M screen as a conditional next implementation question. R973’s digest is `research-review-round973-v1.ja.md`; its source-count correction is material: removing two invariant scratch-span checks per expert saves 1,022 repeat checks across 512 experts, and hoisting the mixed-span check saves 511, for 1,533 total rather than 2,047. The report’s content should be retrieved by Main only if a later design question selects it.

R977’s measured census covers one 39,262-token request (39,261 tokens across five 8,192-token chunks, with a 6,493-token tail) and 48 MoE layers. Expert pieces with M=1–15 make 30,543/59,614 calls (51.23%) but contribute only 135,562/18,845,280 routed rows per GEMM kind (0.719%). The average M in that range is 4.44. The hot 1,024–8,192-row pieces contribute 14,154,159 rows; any small-M path is selective.

The active compact configuration has `STRATA_PREFILL_MMQ=0`. The current per-expert path decodes the GGUF matrices to FP16, uses FP16 GEMM inputs and weights, accumulates/applies beta in FP32, rounds to BF16 output, then applies the existing SwiGLU/routing semantics. Preserve the decoded FP16 bits and FP32 local accumulation as the current comparison contract. R977 counts 119,228 MoE GEMMs and 123,156 total GEMM submissions (the latter also includes non-MoE calls); host grouping is 240 calls/82.6 ms CPU. Its 58.05 CPU seconds in compatibility waits and 36.77 seconds in route-exchange inclusive timing are not MoE service time.

The current staging cache has eight raw-weight slots; the largest expert blob is 2,662,400 bytes. A 16-slot raw window would add 21.3 MB over eight slots. One decoded GU+down expert pair is 4,915,200 FP16 values = 9,830,400 bytes (9.375 MiB). R977’s possible expanded FP16 writes are 300,249,907,200 bytes (279.63 GiB (binary units) for this workload) for the small pieces and 586,029,465,600 bytes for all nonzero pieces. Its 62,723,174,400-byte association between small calls and expert blobs assumes a full blob read for every call. These are logical counts, not DRAM/cache/PCIe observations.

Using those matrix counts, the small-piece arithmetic is about 1.33 TFLOP for the 39K request: 135,562 rows × 4,915,200 GU+down weight elements × 2 FLOP/MAC. All routed expert GEMMs account for about 185.3 TFLOP by the same model. If “A6B” means roughly six billion active parameters per token, a separate rough whole-model estimate is 2 × 6B × 39,262 = 471.1 TFLOP. That total includes attention and other operators and does not describe dequant work or memory traffic. In particular, the 0.719% expert-row share is not a 0.719% estimate of time or physical bandwidth.

The handoff reports a clean, separate-process window comparison at 39K with a 5.95% median throughput gain. The diagnostic MoE interval fell from 20.18 s to 16.78 s, but includes host gaps and is not a utilization or exclusive-device-time measurement. This closes the earlier comparison prerequisite; it does not qualify any alternative below.

## Three alternatives and likely crossover

| Alternative | Work moved or reused | Shape where it could win | Main cost or failure mode |
|---|---|---|---|
| A. Direct low-M quantized compute | Decode packed GGUF blocks while each small expert GEMV/GEMM consumes them; avoid full decoded-weight scratch for that call. Keep current per-expert routing and FP16 weight rounding, FP32 accumulators, BF16 output. | M near 1–4, where a conventional GEMM has little row reuse and per-call dequant plus expanded scratch is a large fixed cost. Can also suit M≤15 if one output tile reuses each decoded weight across those rows without duplicate decode. | It still launches work per expert unless grouped separately; IQ unpack/lookup and scale work may dominate, and register/local-memory pressure or poor occupancy can negate the removed scratch traffic. It does not reduce quantized blob reads by itself. Existing R977 data does not say how many of the 30,543 pieces have each exact M. |
| B. Selectively materialized and reused BF16 weights | Decode only experts that recur across chunks into a resident 16-bit matrix once, then reuse that matrix for several small pieces. Route-overlap/candidate selection is across the same layer and prompt chunks; do not materialize all experts. | A given expert appears in at least two separated small pieces (r≥2) during a cache lifetime, particularly when direct decode repeats expensive format work and the resident matrix can be reused without staging churn. Use the actual expert overlap counts to decide. | BF16 is not the same numerical payload as current FP16 decode. Both formats are two bytes, so BF16 gives no storage/transfer reduction versus FP16. A one-off M≤15 call only adds materialization. Resident full pairs cost 9.83 MB each (8 pairs=75 MiB; 16=150 MiB), compete with current raw slots and other live allocations, and each GEMM still reads the expanded matrix. |
| C. Grouped/ragged dense computation | Construct descriptors for active small expert pieces and run a grouped/persistent dense kernel for each projection; preserve each expert’s actual row count and weight pointer. A hybrid can keep direct IQ decode or feed the grouped kernel selectively materialized weights. | Many small pieces coexist within one layer/chunk; the average is about 127 M≤15 jobs per layer/chunk (30,543/(48×5)). R977’s idealized single-launch-per-projection-per-layer/chunk target is 480 small-piece projection launches versus 61,086 separate projection submissions. | A fixed M tile wastes rows. With the aggregate average M=4.44, a 16-row tile has only 27.7% live rows before considering other padding; a 128-row tile has 3.5%. Small groups may not saturate the GPU, descriptors/scan can consume the savings, and eight raw slots bound how many weights can be live. Grouping alone does not eliminate dequant scratch writes/reads. |

For B, a shape-preserving FP16 materialized cache is the fair first comparison. Converting decoded FP16 weights to BF16 changes the quantized value before accumulation; current instructions also say FP16 and BF16 have equal two-byte storage and format choice must follow task/numerical/performance evidence. Treat BF16 as a separate numerical arm only if the actual reference path for this model uses that storage/decode contract and its output-quality gate accepts it. A cache can still be useful with FP16, but that is not evidence for BF16.

The simple logical traffic crossover for B versus the existing scratch path is repeat-driven. For r uses of one expert, the current path writes one 9.83 MB decoded pair on every use, then GEMM reads it on every use. A persistent exact-FP16 cache writes once and still reads it r times; the best-case logical expanded-scratch write saving is (r−1)×9.83 MB, before accounting for cache fill/eviction/copies. It saves neither the r GEMM reads nor necessarily DRAM traffic. Direct computation can avoid both expanded write and read for each use, but pays the decode and packed-weight traversal inside each matmul. Hence direct compute is favored as M shrinks or expert repetition falls; materialization is favored as per-expert reuse rises and decode/register cost is high; grouped dense is favored as active job count per layer/chunk rises while descriptor overhead and M padding stay low. Cache residency and physical traffic are unmeasured.

The previous window mode already combines two pieces and can avoid repeated dequantization for experts present in both pieces. Any new cache hypothesis should count only additional reuse beyond that path, split by layer, exact M, expert ID, chunk, and GEMM kind; do not credit it with the window’s existing reuse again.

## Design references and transfer limits

* **vLLM Triton fused MoE:** `vllm/model_executor/layers/fused_moe/fused_moe.py`, Apache-2.0, pinned to vLLM main commit `5be4266f5c7c10c69e4be5f3ec01d6a1d8bae9a1` (read 2026-10-17): https://github.com/vllm-project/vllm/blob/5be4266f5c7c10c69e4be5f3ec01d6a1d8bae9a1/vllm/model_executor/layers/fused_moe/fused_moe.py . Its W4A16/W8A16 Triton path unpacks and scales weight tiles in the K loop before `tl.dot`; the main fused kernel uses sorted token IDs/expert IDs and aligned blocks, with an explicit small-batch block-count adjustment. This is a precedent for fusing dequant with matmul and routing tiles, not evidence that GGUF IQ block layouts, exact FP16 decode rounding, BF16 outputs, or this SYCL compiler will match. Its supported weight formats and hardware-specific execution are different.
* **SGLang runner:** `python/sglang/srt/layers/moe/moe_runner/triton.py`, Apache-2.0, `main` page read 2026-10-17 (the page did not expose a full commit SHA): https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/layers/moe/moe_runner/triton.py . `TritonRunnerCore` carries sorted-token, expert-ID, and post-padding metadata into its fused MoE kernel sequence, and its quant-info interface includes INT4/INT8 WNA16. The expert-parallel docs describe dispatch → pre-permute → grouped-GEMM core → post-permute/combine: https://github.com/sgl-project/sglang/blob/main/docs/docs/advanced_features/expert_parallelism.mdx . This is a useful current execution/scheduling reference; it runs PyTorch/Triton/CUDA or HIP paths and does not establish the Strata engine contract.
* **Triton grouped GEMM tutorial:** `08-grouped-gemm.html`, Triton main docs read 2026-10-17: https://triton-lang.org/main/getting-started/tutorials/08-grouped-gemm.html . It represents each problem with pointer and shape/stride descriptors and schedules tiles over a group. The example uses large fixed tile sizes (64/128), so it is a counterexample to assuming a generic grouped GEMM automatically fits M≤15; exact ragged handling or a lower-M specialization needs evaluation. The Triton repository is MIT-licensed: https://github.com/triton-lang/triton/blob/main/LICENSE .
* **CUTLASS grouped scheduler:** official guide, current page read 2026-10-17: https://docs.nvidia.com/cutlass/latest/media/docs/cpp/grouped_scheduler.html . A persistent kernel schedules tiles from many GEMM problems in one launch. Its own guidance says host-precompute versus device-only scheduling matters most for low-intensity groups because scheduling then forms a larger fraction of runtime. That warning transfers; CUDA code, launch costs, architecture performance, and the documented scheduler are not an SYCL implementation reference. CUTLASS is BSD-3-Clause: https://github.com/NVIDIA/cutlass/blob/main/LICENSE.txt .
* **Intel/SYCL matrix path:** Intel DPC++ `sycl_ext_oneapi_matrix.asciidoc` on `intel/llvm` branch `sycl`, read 2026-10-17: https://github.com/intel/llvm/blob/sycl/sycl/doc/extensions/experimental/sycl_ext_matrix/sycl_ext_oneapi_matrix.asciidoc . `joint_matrix` is optional, supports only device-specific type/shape combinations, and exposes a runtime `matrix_combinations` query. The Intel ESIMD example shows packed 2/4-bit DPAS operands, but assumes PVC in its code and uses regular integer packing, not nonlinear GGUF IQ blocks: https://github.com/intel/llvm/blob/sycl/sycl/doc/extensions/supported/sycl_ext_intel_esimd/examples/dpas.md . An LLVM issue reports that on a Battlemage/Xe2 setup, `joint_matrix` reported no matrix hardware while ESIMD DPAS was functional; this is a counterexample, not proof about this B570/LLVM/driver: https://github.com/intel/llvm/issues/21741 . So neither an XMX-capable ISA nor a `joint_matrix` call or SYCL queue proves the selected kernel emits XMX/DPAS or keeps arithmetic on that path. Verify runtime combinations and generated instructions on the owned build.
* **Intel vLLM XPU grouped GEMM:** vllm-xpu-kernels `v0.1.13` (release commit `07d44bc`, Apache-2.0), https://github.com/vllm-project/vllm-xpu-kernels/releases/tag/v0.1.13 . The release documents native Xe2 grouped-GEMM paths for MXFP8/block-FP8 and a regression fix; its code path is a valuable Intel/SYCL/Level-Zero design precedent but operates on supported FP8 formats, not Strata GGUF IQ weights. A repository issue reports a B70 decode experiment where compacting 256 expert groups to 8 lowered an isolated group-scan microbenchmark (232→94 μs) but did not remove a much larger 5–6.6 ms fixed MoE decode cost; a later reported end-to-end change was only 5.2%: https://github.com/vllm-project/vllm-xpu-kernels/issues/509 . This is a decode/B70 report, not a B570 prefill result, and argues for an exclusive component timing plus whole dependency-path measurement.
* **Original grouped-GEMM engineering blog:** NVIDIA’s cuBLAS grouped-GEMM overview reports 1.2× over naive batched loops for FP16 generation MoE at batch sizes 8 and 64, on NVIDIA: https://developer.nvidia.com/blog/introducing-grouped-gemm-apis-in-cublas-and-more-performance-updates/ . It is evidence that grouping can help when launch/shape structure fits, not an expected gain for these 39K prefill shapes. Its GPU, API and M regime differ.

Repository licenses were checked at the source repositories or release: vLLM, SGLang, and vllm-xpu-kernels Apache-2.0; Triton MIT; CUTLASS BSD-3-Clause; Intel LLVM uses Apache-2.0 with LLVM exceptions. These are provenance records only; no borrowed source or license text is part of this report or the active project.

## Minimal decision-quality screen if Main selects one

After serialized Main-owned work and exact source/build pinning, first reuse the existing expert-piece census to make a per-layer/per-chunk distribution table: exact M bins 1–15, M≥16, expert ID across chunks, quant format pair, cache-slot reuse, and whether window=2 already combines the occurrence. Then benchmark the existing FP16 decode→GEMM, direct-decode kernel, a selective exact-FP16 cache arm, and a grouped/ragged arm on the same sampled live descriptors. The first decisive cohort should cover M={1, 2, 4, 8, 15, 16}, one representative for each of the seven format pairs, and an aggregate histogram replay; add no full model run until component gates select an arm.

For each arm, report exact input bits and independent oracle/bounds/fault outcomes; host descriptor/build CPU time separately from device command time; launch count; exclusive per-kernel duration; packed bytes read, decoded scratch bytes written/read, actual cache fill/reuse/eviction, and peak live VRAM. Establish whether the actual generated kernel emits the intended matrix instructions and record achieved service/counters; a compiler flag or kernel name is insufficient. Test residency and transfer placement independently from arithmetic, and include the normal GEMM→SwiGLU→down→combine dependency path. A useful win is a repeatable reduction in the selected limiting cost without violating the established numerical/state/lifetime/context gates. Do not treat logical byte counts, tile occupancy estimates, launch-count reduction, or this source survey as hardware utilization, speed, or adoption evidence.

## Limits

R977 and the handoff contain no exact distribution within M=1–15, no per-expert cross-chunk reuse histogram, no DRAM/cache transactions, no exclusive kernel times for these alternatives, and no achieved B570 resource or XMX ceiling. This report does not determine a tile, dispatch threshold, cache size, kernel architecture, numerical adoption, full-model speed, or physical 262,144-context/RESTORE correctness. The 8-slot cache and 480-launch target are source/report estimates to re-check against the frozen current engine path before any experiment.
