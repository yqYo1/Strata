# R778 — Sparse storage-format crossovers under skew and reuse

2026-10-16 JST. Bounded public-source knowledge collection. I read the project instructions, artifact policy, index, R759/R763/R773, and their Main corrections. This report focuses on storage and conversion break-even. No source code, product, build, test, GPU, profiler, process, environment, service, Git, or cleanup action was involved. No Arc performance claim follows.

## Crossover model

Formats change index/data bytes, padded work, reductions, and conversion or permutation cost. For a stable pattern, a first-order break-even is

`R > (T_convert + T_permute + T_setup) / (T_CSR - T_candidate)`

`R` is reuse count before the pattern changes; the denominator must be positive. Count restoration, vector reordering, allocation, and transfers. A changed pattern incurs conversion again; changing values alone may reuse indices but requires updating packed values. Holding both representations can exceed memory capacity. Credit persistent reordered data only if later operators consume it. This accounting model is a screening tool, not a timing result.

## Format and workload comparison

| Format | Uniform row lengths | Heavy-tailed / highly skewed rows | Changing sparsity and repeated use |
|---|---|---|---|
| COO | Easy tuple assembly; one row and column index per nonzero, no row-pointer build. Adds row-index traffic and usually needs atomics/reduction for output rows. | Per-nonzero assignment balances long rows, but atomics can contend and accumulation may be nondeterministic. | Useful for incremental entries or short reuse. Sorting or duplicate consolidation may still be needed; keep COO if the consumer accepts it. |
| CSR | Compact values/column IDs plus one row pointer per row; no padding. Strong default for balanced rows and supported consumers. | Storage stays compact, but row-assigned work can leave lanes idle behind long rows. | Often wins when patterns change, APIs accept CSR, or conversion repeats. Row lengths are directly available. |
| ELL / blocked ELL | Coalesced regular slots; near-uniform short rows limit padding. Blocks can exploit dense subblocks and matrix-matrix reuse. | Global ELL pads to the longest row. Blocking helps only when nonzeros cluster within blocks; otherwise zero slots and block indices erase gains. | Packing and possible output restoration must be amortized. Repacking each changing pattern recurs. |
| SELL-C-σ / sliced ELL | ELL slices of `C` rows limit padding locally, with slice metadata and a row permutation. For uniform rows, it adds preparation with little padding saved. | Sort within `σ`-row windows to group lengths. Larger windows can reduce padding but increase reorder distance and conversion work; each slice still pads to its longest row. | Reuse pays while structure stays fixed. Restore outputs or preserve a consistent permutation downstream; pattern updates generally require repacking. |

A useful structural comparison is storage slots. For `m` rows, `n` nonzeros, index width `b_i`, and value width `b_v`, CSR uses about `n(b_i+b_v)+(m+1)b_i`; COO uses `n(2b_i+b_v)`. ELL uses `m*k_max*(b_i+b_v)`, so padding inflation is `m*k_max/n`. SELL substitutes per-slice maxima times `C`, plus slice/permutation metadata. These estimate bytes, not time; coalescing, reductions, and kernel quality can reverse the ranking.

## What measurements say, and where they stop

Bell and Garland’s CUDA study is a counterexample to “uniform means ELL always wins.” ELL storage and work degrade as row lengths spread. Their HYB stores typical entries in ELL and exceptional tails in COO. On a GTX 280, ELL held 99.4% of nonzeros for Wind Tunnel but 45.4% for the highly variable LP matrix; HYB was strong on some unstructured matrices and worst on LP. COO was a relatively stable fallback. This is old CUDA evidence, not a current forecast.

SELL-C-σ limits the padding cliff by sorting bounded row windows before slicing. Its study covers Sandy Bridge, Xeon Phi, and Tesla K20 and identifies slice height `C` and sort scope `σ` as tuning dimensions. It suits moderate skew where a few long rows hurt global ELL, but small `σ` may leave outliers together and large `σ` costs more to prepare or undo. Output mapping and downstream consumers must honor the permutation.

A Ginkgo evaluation tested COO, CSR, ELL, and HYB on over 2,800 SuiteSparse matrices with V100 and Radeon VII GPUs (CUDA 9.2/HIP 2.8). No format won all problems: CSR was fastest on about 30%, while HYB generalized better under modest allowed slowdown. Dense-row cases were excluded from ELL because conversion could be virtually impossible. ELL access changes helped Radeon VII more than V100, showing architecture sensitivity. These 2020 SpMV results do not predict other kernels or current devices.

For SpMM, do not transfer SpMV rankings unchanged. A wide dense right-hand side lets CSR reuse each nonzero across columns and coalesce dense accesses. Yang, Buluç, and Owens report CSR-based kernels with 31.7% geometric-mean speedup and up to 4.1× on 157 SuiteSparse datasets, without format conversion. They warn conversion to and from a specialized layout can cost more than SpMM and requires duplicate storage. Results use K40c/CUDA 8 and omit transfer time; they show an optimized consumer may remove the need to convert.

Conversion cost is representation-specific. CSR5 reports CSR-to-CSR5 conversion as low as a few SpMV operations and gains on tested CPU, NVIDIA, AMD, and Xeon Phi systems, even for some workloads with tens of iterations. “Conversion is always too expensive” is false, but this is not a SELL measurement. Measure sorting, transfer, extra live storage, kernel, and restoration for actual reuse counts.

## Changing patterns and API constraints

Changing values alone differs from changing sparsity. If indices and the SELL permutation remain valid, refresh values in packed order and amortize index preprocessing. A changed entry count/location can require new CSR pointers and repacked slices. COO accepts appended triplets, though consumers may need sorting, duplicate reduction, or conversion. Reuse helps only if it amortizes those costs within memory capacity. Output restoration touches the vector and may disrupt the next input. A square iterative method may need a consistent row, column, and vector permutation, not only sorted rows.

Current library contracts narrow viable choices. Intel oneMKL SYCL 2026-0 lists CSR as the default supported format, with COO, CSC, and BSR only for specified routines; sparse GEMM supports CSR/COO, while conversion is documented for CSR↔COO. It recommends device USM for performance but assigns data movement to the caller. Therefore an ELL/SELL experiment may require a custom kernel or external implementation rather than a direct oneMKL format switch. NVIDIA cuSPARSE 13.4 documents COO/CSR/CSC/BSR/Sliced-ELL for SpMV and Blocked-ELL for SpMM. Its Blocked-ELL SpMM support is architecture/type/operation constrained, and its performance notes favor power-of-two and larger block sizes. These are CUDA/NVIDIA contracts, not SYCL portability guarantees. [Intel oneMKL SYCL Sparse BLAS 2026-0](https://www.intel.com/content/www/us/en/docs/onemkl/developer-reference-dpcpp/2026-0/overview-of-intel-oneapi-math-kernel-library.html); [NVIDIA cuSPARSE 13.4 documentation](https://docs.nvidia.com/cuda/cusparse/)

## One concrete future experiment

Use one scientific matrix set with three classes: nearly uniform rows, heavy-tailed rows, and a sequence changing row counts and column positions. Compare CSR, COO, ELL/blocked ELL only under bounded padding, and SELL-C-σ over a small `C`/`σ` grid. Hold operation (SpMV or SpMM), precision, dense layout, and output semantics constant. Include a pattern-static/value-changing case and a native COO/CSR path for changing patterns. Use `C` values 16/32/64 and `σ` windows 32/128/512 as a bounded screen, not claimed optima; define class membership from row-length histograms before timing.

Record row-length percentiles/max, padding ratio, actual packed slots, index/value bytes, conversion, transfer, restoration, peak memory, kernel and end-to-end time for reuse counts 1, 2, 4, 8, and 32. Check reference results, duplicate handling, and permutation restoration. Report the first `R` where full-pipeline time beats CSR, or no crossover/capacity failure. This is experiment design, not a Strata proposal or performance claim.
