# R671 — GPU-local routing at the layer-major FP16 GEMM boundary

2026-10-15 JST. Read-only source/reports review for the current configured SYCL layer-major prefill route. Priority follows the user's correction: improve long-prefill throughput toward >600 then 1,000 tok/s on 32,768/65,536-token prompts under a 262,144-cell context limit; the request is to keep route/group work local to the GPU where possible, even if that adds GPU work, rather than repeatedly moving route rows through CPU memory. No source edit, build, test, compiler, GPU, process/service, private environment/B/log, Git mutation, or cleanup was performed. This report is the only new file.

## Finding

The present route is **CPU-dependent for exact oneMKL dispatch shape**. The router produces `ids[T,10]` and weights on the GPU. Then `prefill.cpp` copies all IDs to host and synchronizes the same compute queue. The CPU validates IDs, builds the 512-bin `cnt`, 513-entry `off`, and ascending active-expert `order`; it fills `slot[T,10]` and `src[T,10]`; those arrays are then written back or through a mapped host allocation. The active-expert loop passes each `cnt[e]` as scalar `ne` to `Gemm::f16`, which calls oneMKL row-major GEMM with `M=ne`. Host code also needs each `off[e]` to point at the expert's compact row range and uses `order` to select that expert's resident weight slot. These are the fields at the router-to-GEMM boundary that prevent GPU grouping alone from retaining the current per-active-expert oneMKL call shape.

The smallest precision-preserving GPU-local change is to reuse the existing GPU grouping algorithm (`fused::group`) for count/prefix/scatter, add an explicit way to expose its 512 counts (and invalid-ID status), copy only those small controls to host, and keep the current host loop that issues exact-M FP16 oneMKL calls. This keeps route IDs, offsets, source-row assignment, and slot mapping on the device; it returns only the counts needed for host `M`, rebuilds `off` and ascending `order` from those counts, and removes the full `ids` readback plus `slot/src` uploads. It still has one queue-completion point per chunk because host oneMKL dispatch cannot use a per-expert `M` read from device memory. It preserves the current packed weights, llama.cpp IQ-to-FP16 dequantization, FP16 input path, FP32 GEMM outputs, SwiGLU and `moe_combine` route-slot accumulation; it adds GPU histogram/prefix/scatter work instead of CPU-per-row routing work. This is a source-level candidate, not a speed result.

## Exact current route and compiled entry points

`cmake/sycl_backend.cmake` is the configured source list. It compiles `src/prefill/prefill.cpp`, `src/prefill/sycl/gemm.cpp`, `postops.cpp`, `moe_mmq.cpp`, `moe_fused.cpp`, `src/kernels/sycl/native_router.cpp`, `native_mmvq.cpp`, `native_iq_esimd.cpp`, and `native_mmq_xmx.cpp`. The active layer-major wrapper in `src/prefill/layer_major.inc` requires `STRATA_PREFILL_LAYER_MAJOR=1`, a multi-chunk prompt, native compact FP16, explicit `STRATA_PREFILL_MMQ=0`, single GPU/full model, and the same in-order compute/copy queue. Its `layer_major_active` flag makes `stream_all` false, so the current prefill's existing fused/MMQ streamed route is not selected. QSA/GDN/PLE state sequencing and all surrounding model math remain owned by the existing per-chunk `run_impl`.

Within `run_impl`, half 1:

1. `route()` dispatches 512-expert routing to `native_router_top10_multi` (`src/prefill/sycl/postops.cpp`, `src/kernels/sycl/native_router.cpp`). It selects ten distinct expert IDs per token by repeated max with the selected logit masked to negative infinity, and writes `ids` plus normalized weights on `m.cs`.
2. The current host branch copies `T*K` IDs to `ids_h` (`grp_host` mapped storage, or `ids_host` with D2H), then calls `cudaStreamSynchronize(m.cs)`. The host loops IDs to validate and construct `m.cnt[512]`; then builds the prefix `m.off[513]`, fills `slot_h/src_h`, copies those arrays to `m.slot_dev/m.src_dev` when they are not mapped, and builds `order` in ascending expert-ID order. This is all visible around `src/prefill/prefill.cpp:2434-2508`.
3. For the compact FP16 fallback selected by layer-major admission, the loop processes each active `e` and uses `ne=m.cnt[e]`, `o0=m.off[e]`. It dequantizes the packed native expert to the existing two FP16 scratch buffers; gathers `ne` rows from `m.mixed_h` using `m.src_dev+o0`; calls `m.gemm.f16(..., ne, 1280, 2560)` for GU; applies `swiglu_interleaved`; then calls `m.gemm.f16(..., ne, 2560, 640)` for Down into `m.Dm+o0*N` (`:2860-2899`). `src/prefill/sycl/gemm.cpp` passes `T` directly as oneMKL GEMM's row count `M`; this is a host scalar call, not a device-side bound. `moe_combine` later reads `m.slot_dev` alongside the original `m.ids`/weights and accumulates the ten routed slots in input `k` order (`:2967-2969`, `src/prefill/sycl/postops.cpp:248-263`).

Therefore `cnt` is needed on the host to pass exact `M` and skip zero experts; `off` is needed to form the source/output slices; `order` is only a compact active-expert scheduling list and can be recreated by scanning counts in ascending expert ID; and `slot/src` are required by the unchanged gather/combine data layout, but need not be CPU-built. GPU grouping cannot eliminate the host decision about exact `M` while preserving this oneMKL call path. A CPU return of the count vector remains necessary unless the GEMM/compute interface changes.

## Minimal GPU-local candidate with current FP16 arithmetic

Reuse the compiled `strata::prefill::fused::group(ids, T*K, K, 512, scratch, slot_dev, src_dev, cs)` implementation from `src/prefill/sycl/moe_fused.cpp` strictly for routing metadata, not for its expert arithmetic. That function already runs the GPU count histogram, prefix/scatter, and 64-row tile-list construction. It writes device grouping tables, `slot`, and `src` from the routed IDs without host copies. Its internal `finish(stream,event)` does not wait for a non-null stream; it submits on the given in-order queue, so subsequent same-queue work remains ordered.

The current compact MoE `m.GU` allocation is `T*1280` FP32 values, or `5,120*T` bytes. It is much larger than the `fused::group_bytes(10*T,512)` table/list scratch calculated below (about 17–23 KiB for the current chunk range), so source inspection shows a plausible temporary alias for group scratch before later GU GEMM writes, without increasing chunk buffers. The lifetime is safe only if all grouping, count-copy, and any scatter consumers are on the same checked queue lease and no later GU operation can overwrite scratch before grouping completes. Alternatively carve a dedicated small region to avoid aliasing. The group function currently keeps its count table private inside scratch and silently ignores invalid expert IDs; its API would need an explicit count-output/access contract and checked invalid-ID count/status. Do not reach into its undocumented scratch offsets from prefill. Validate `sum(cnt)==10*T`, every `0<=cnt[e]<=T` (router guarantees distinct top-10 IDs), and invalid count zero before any oneMKL dispatch.

Then issue one count-table D2H copy (`512 * sizeof(int32_t) = 2,048 bytes`) and one `m.cs` completion wait. Rebuild `off` from counts on host and scan `e=0..511`, dispatching only positive `cnt[e]` in the same ascending order. Leave `ids`/weights on device; leave `slot_dev/src_dev` from GPU grouping. Each expert still uses the same `m.src_dev+off[e]` gather, the same packed resident blob, same IQ dequant-to-FP16, same `Gemm::f16` M, same activation/output precision, and same unchanged combine. The atomic scatter may put a token's routed rows for one expert in a different internal row order, but `slot[original_pair]` points back to the corresponding row and each GEMM output row is independent; verify output and intermediate parity before treating this as exact. `moe_combine` order itself remains unchanged.

This path still returns **counts** to the CPU. It makes the GPU do the per-route histogram and scatter and minimizes host/device roundtrips without pretending that oneMKL can consume dynamic device-side M. It also preserves one synchronization per chunk. The old D2H IDs transfer is replaced by 2 KiB counts; `slot/src` no longer need host writes or explicit H2D copies. Current mapped-buffer mode already avoids an explicit slot/src copy but still copies/reads IDs on the host; those mapped host writes may be device-visible through system memory and must not be described as zero physical traffic or PCIe bytes without endpoint evidence.

## Why existing fused and grouped-MMQ product paths do not preserve this arithmetic

* **Existing direct fused experts** (`fused::group`, `fused::experts_native` in `src/prefill/sycl/moe_fused.cpp`) are the closest full GPU-local route. `group` gives device counts/offsets/slot/src; `experts_native` reads each native packed blob directly and launches from the device tile table, with at most 128 expert pointers per host launch. However `quantize_act_native` converts FP32 activations to int8, and its GU epilogue rounds hidden activations to int8 before Down. The current layer-major route uses BF16 router input, FP16 gathered expert activations and FP16-dequantized weights through oneMKL. Fused changes the arithmetic and precision. It is also currently selected only for `use_mmq && stream_all && no_peer && native_supported`; layer-major rejects MMQ and disables `stream_all`. Reusing its **group function only** avoids this precision change; routing the expert products through `experts_native` would require a separate numerical/quality decision.
* **Existing grouped MMQ** uses `mmq::Product` / `NativeMmq` through `moe_mmq.cpp` and `native_mmvq.cpp`. It keeps packed quantized weights and uses Q8_1 quantized activations; it is not FP16-dequant × FP16 oneMKL. `Product.n` (experts in this group), `total_rows` and `max_rows` are host launch parameters. Device `bounds` select each expert's actual range, but kernel grid sizing uses host `max_rows`; `native_mmq_xmx.cpp` only compacts its launch grid when a matching `host_bounds` array is supplied and `experts<=16`. The prefill caller currently constructs each group and bounds on CPU. The layer-major admission explicitly requires MMQ disabled. Merely exposing device bounds or removing that guard does not make variable-M oneMKL or exact FP16 semantics.
* **A custom exact GPU workqueue/product kernel** could remove even the 2 KiB count return, but that is no longer metadata reuse. It must consume each expert's packed type/layout and exact current dequant/FP16 behavior, run variable row counts from a device worklist, preserve `slot` association and output rounding, and retain checked queue/lifetime/failure handling. Existing SYCL `native_mmvq` is quantized Q8_1 native-weight dot-product code, not a drop-in exact oneMKL FP16 grouped GEMM. No compiled variable-M FP16 grouped API with device-resident shape bounds is present in the configured prefill sources reviewed here. A fixed `M=T` or `M=10*T` for all 512 experts would avoid count readback but execute large amounts of zero/padded work; it also needs GPU-per-expert packing and output slots. That is a separate experiment, not the minimal candidate.

## Bounded storage and grid estimates (logical source bounds only)

For a chunk of `T` rows, routing top-10 creates `n=10*T` route pairs. Existing device arrays each have `n` int32 slots for `ids`, `slot`, and `src`; route weights are `n` FP32 values. The GPU-local grouping table `fused::group_bytes(n,512)` reserves an aligned table prefix plus at most `ceil(n/64)+512` `{expert,row}` tiles. Each `Tile` is two int32 values (8 B). The bound follows because the total number of expert rows is `n`, and each expert contributes at most one ceiling-rounding tile per expert. Counts, offsets, tile IDs and `slot/src` remain bounded by chunk size, not full logical context.

| Configured chunk | Route pairs `10*T` | Max tiles `ceil(10*T/64)+512` | Group scratch upper bound | Count return | Existing `ids` D2H | Existing `slot+src` explicit H2D if not mapped |
|---:|---:|---:|---:|---:|---:|---:|
| 4,096 | 40,960 | 1,152 | 17,424 B | 2,048 B | 163,840 B | 327,680 B |
| 8,192 | 81,920 | 1,792 | 22,544 B | 2,048 B | 327,680 B | 655,360 B |

The group scratch bound is `tiles_at(512) + (ceil(n/64)+512)*8`, where the compiled source's aligned table prefix is 8,208 B. It is a required upper bound, not the expected realized tile count. Grouping work is bounded by one histogram update per route pair, one prefix/scheduling pass over 512 experts (plus the tile-list generation loops), and one scatter update per route pair. Expert computation remains the existing active-expert GU/Down GEMMs; no speed or compute ratio is inferred.

For a 32,768-token input, the current batched path has 8 chunks at C=4,096 or 4 at C=8,192; for 65,536 tokens, 16 or 8 chunks; a full 262,144-row context is 64 or 32 chunks. Actual standalone batched rows can be `prompt_tokens-1`, so use the receipt's actual batched count for final bookkeeping. Across all 48 layers, the full-context chunk upper schedule is 3,072 group operations at C=4,096 or 1,536 at C=8,192. At ten route pairs per input row, full-context total is at most 2,621,440 pairs per layer (2,621,430 if the standalone batched count is exactly 262,143), while resident per-chunk buffers remain those in the table. A 2 KiB count return at each chunk totals 6 MiB over 48×64 chunks or 3 MiB over 48×32 chunks. The old IDs return is 480 MiB over a full 262,144-row route at either chunk size, before any separate slot/src movement. Those are logical payload calculations, not measured host-link traffic, physical PCIe bytes, timing, or a throughput prediction.

The large per-chunk `ids/slot/src/weights` already exist in `carve(T)`. For the compact FP16 branch, `m.GU=T*1280` floats provides 20 MiB at C=4,096 or 40 MiB at C=8,192; the grouping scratch above is only about 17–23 KiB. This estimates a possible alias capacity only. Verify exact `Alloc` extents, pointer alignment, no overlap with live scratch, and checked queue ownership in any implementation. Do not allocate a whole-context route list: the current chunked `run_impl` can bound the metadata per chunk and the user has specified a 262,144 context ceiling.

## Relationship to prior candidates and decision gates

R621/R622's deferred expert-major schedule was a different whole-prefix transformation. It retains layer-wide activations/routes/shared outputs and, to preserve current route-slot accumulation order, up to 25 GiB of full-context FP32 expert outputs, in addition to other owners. It is not needed for this narrow per-chunk routing change and is not re-proposed. R628 already contrasts small-ne MMVQ and grouped-MMQ alternatives with current FP16 oneMKL; its quality/dispatch caveats remain applicable. R667 records the current host readback/synchronization path; R668 sets current chunk-only long-prefill comparisons at 32K and separately 64K. No new decode optimization or >600K/1M-input proposal is made here.

Before implementation, Main should decide whether reducing this synchronization's CPU/transfer cost remains relevant after its current owned clean prefill-only baseline. If pursued, first validate GPU grouping's count and invalid-ID status against the current CPU reference on all tails, slot/src association, `sum(cnt)=10*T`, `cnt[e]<=T`, offset coverage, repeated expert/token handling, output/intermediate parity, queue errors, and source/hash provenance. Then time it only in separate owner-serialized diagnostic/clean processes at the same 32,768 or 65,536 input, 4,096/8,192 chunk, context, KV, residual placement, MTP4 and cache settings. Report clean prefill tok/s and decode separately. Target thresholds (>600 then 1,000 tok/s) remain measured gates, not expectations. Preserve faults, completeness and cleanup receipts under the artifact-retention policy.
