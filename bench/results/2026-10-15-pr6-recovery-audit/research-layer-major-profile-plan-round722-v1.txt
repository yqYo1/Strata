## What this capture answers

The existing aggregate reports device operation duration summaries across the instrumented process. It can show which recognized kernel/operation families have the largest accumulated device durations in this actual run, after operation names are mapped to the current pinned source. This can triage whether attention, GEMM, dequant/gather-related kernels, or visible device copies merit a more focused question. Compare the operation counts and durations as separate fields and preserve the total request/prefill wall from the existing owner receipt.

It does not isolate the 48-layer prefill phase from initialization, restoration or the one output tail in a process-wide profile. It does not provide event order, compute/copy overlap, a same-queue critical path, host CPU issuance gaps, Stager wait duration, source/destination copy endpoints, or measured PCIe traffic. Operation-duration sums may overlap across queues/engines; they are not exclusive fractions of the request and must not be added to claim whole-request service. It reports no SLM occupancy/bank conflicts or XMX utilization, so it cannot decide whether SLM gather or matrix hardware is the limiting resource. Missing activity is not proof of idle time. Existing API timing is likewise not CPU busy time.

`--chrome-call-logging --chrome-kernel-logging` would add Level Zero API and device event intervals that can expose visible lane overlap, but the trace is a different, much larger data product. The previous 513-token component emitted 806,125 events and 135,949,669 bytes. The 34,603-token request trace had 8,066,326 events and required the recorded 2 GiB trace allowance. This workload is 78,453 actual tokens, and its current owner has a 64 MiB per-file/default raw-log cap. Therefore detailed Chrome collection is not a feasible default follow-up under the current budget. A request-window capture also brackets restore/request/output rather than an exact prefill boundary; temporal `--start-paused`/`--resume` controls do not acknowledge application or layer-major boundaries. Use a detailed window only after a concrete question needs it, a current-code pin set and parser are reconstructed, and a finite reasoned budget is recorded before collection.

Prior event/window reports establish that PTI Chrome can record host Level Zero API spans, GPU operation intervals, flow IDs and requested copy sizes. The trace does not expose API queue pointers or copy allocation ranges; the flow category is not proof of physical copy direction. Device lanes are not automatically the application's same queue. Preserve the historical GPU clock-domain qualification as unresolved; `UNITRACE_SystemTime=1` alone does not qualify GPU timestamps. VTune remains unsuitable: R576 rejects retrying the prior Ryzen/XPU collection, while the retained visibility failures did not collect model-path GPU activity. The saved `UR_ENABLE_LAYERS=UR_LAYER_PARAMETER_VALIDATION` and `UR_LOG_*` settings are validation/logging, not profiling; keep the existing environment unchanged and do not add layers for timing.

Map only the largest relevant device operations to current source and use their counts plus the unchanged native receipt to name the next single question.
