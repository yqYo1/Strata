## Findings

The 1,440,161,792 B (1.3413 GiB) largest combined layer is a sound **header/payload-accounting result**, not an observed residency peak. `measure_prefill_capacity_v1.py` reads GGUF headers and the pack/native indexes, groups payload by layer, and uses `canonical + native + packed experts`; metadata-v2 records all 48 layers, names/types/shapes/byte counts, source/input hashes and the max at layer 47. Its alternative separate-bank reservation is explicitly `max(experts) + max(canonical+dense)` = 1,505,173,376 B because those maxima occur in different layers. It does not count embedding/output metadata rows with zero payload or CPU PLE lookup tables as GPU layer payload. This supports the receipt’s stated one-combined-bank assumption; a real loader must actually reuse one bank and not keep the current full canonical owner. It is not a host RSS, transfer, or allocation measurement.

The scratch fixture proves narrower things than “maximum prefill workspace.” The source `prefill_scratch_allocation_fixture_v2.cpp` initializes actual production `Prefill` owners, allocates the owned C8192 region, borrows the exact carve, relayouts C8192→C4096, checks end canaries, and rejects a one-byte-short loan, null/out-of-order queue and split topology. It sets session metadata for max_cells=262144 but runs no model, tensor math, KV-state initialization, inference or physical 262144 producer. Receipt scope correctly says this. In particular, the C8192 `accounted=2,588,395,008 B` is an observed production carve; C4096 `accounted=1,503,447,296 B` is observed during relayout. The full-resident workspace used in the budget is source arithmetic derived from the streamed carve by removing the unused one-layer KV staging allocation and token buffer as described in the receipts; it is not another full-resident GPU run. The layer payload and workspace were never simultaneously allocated by this fixture. The capacity table is therefore a conservation model plus component gate, not a measured simultaneous peak.

The workspace accounting includes FP32 live `R`, chunk embedding/PLE buffers, FP16 activation/dequant buffers, dense-dequant, expert scratch/rings, and the shared maximum GDN/QSA/MoE region with guards. The scratch sharing assumption is explicitly default-off / candidate in the reports; its exact active status must be stated with any budget. The `gemm_reserved_workspace` item is part of the historical source ledger; the later SYCL no-workspace review says production SYCL GEMM does not use the external pointer, removes 33,554,688 B and reports clean C8192/4096 runs. Avoid applying that delta twice. Current metadata-v2 does not contain an empirical maximum for driver/oneMKL/runtime allocations; 512 MiB runtime headroom and 16 MiB small-owner allowance remain policy placeholders.

The source formula for each full QSA owner has all the relevant terms. For 262,144 cells, page size 4, heads=2, head dim=256, index dim=128 and 12 QSA layers:

- K8/V8 cell pool is 1,056 B/cell/layer: 1,024 int8 codes + 32 B FP16 scales. K8/V4 is 816 B/cell/layer: K codes/scales plus Q4_0 V rows/scales.
- Per-layer state additionally includes K/V pool alignment, int32 page table, indexer tail (3×128 FP32), dead row (128 FP32), pooled index rows (`context/4 + 2`, 128 FP32 each), block position, step/count/status, and position vector. The K8V4/current hybrid form is not accepted by the current layer-major streaming path.
- One shared RoPE table (cos+sin, 256 B/cell) is counted once for all QSA layers, not once per layer. Thus the receipt’s full-resident formulas include page/index/RoPE terms, rather than KV codes alone. For K8V8 and K8V4 the recorded expressions are respectively `14476*C+43200` and `11596*C+43200` B for C divisible by 4.
- A streamed mode adds residency-map owners. The full-resident formula used by the capacity table has no streamed map. A future active-QSA-only implementation must specify whether the active layer is full resident or streamed and add/remove the exact map/pool owners accordingly.

The layer-major residual is one rolling prefix store, not 48 saved copies. Its row is HC=4 × hidden=2560 × 2 B = 20,480 B/token in FP16 (5 GiB at 262,144); conversion to/from the FP32 compute residual happens per chunk. Source `LayerMajorResidualPlan::make` also reserves one FP16 chunk on GPU when a host tail exists: 80 MiB at C4096 or 160 MiB at C8192, then rounds the device prefix down to a full chunk. This staging allocation is separate from the persistent prefix bank and must remain in a partial-GPU hidden budget. The residual used by current kernels is still FP32 (`R`/live chunk), already represented in workspace; A16 only reduces the boundary store. A16 quality and full-context range are unqualified by this storage accounting.

## Active-QSA-only owner boundary

The ideal “only the current QSA layer’s cache/indexer on GPU” scenario can remove 11 layers of KV pool plus each old layer’s page/indexer owners from the GPU peak. It does not remove the single shared RoPE table, the currently active layer’s complete state, the common chunk workspace, all GDN recurrent state, PLE history, current-layer weights, or decode/restore requirements. Source currently allocates all QSA state descriptors and arenas from the session and keeps the full indexer tails/dead/pooled state in `QsaState`; the capacity scenario is an ownership redesign, not a toggle proven by current source.

Current mode-1 KV streaming is not equivalent to the proposed scheme: its host mirror covers KV cells, while the per-layer indexer/page state is still part of the GPU QSA state. A layer-retirement design must persist/restore indexer tail/dead/pooled/block_pos and page mapping along with the KV; preserve common RoPE ownership; and ensure decode sees all layers again. It must also account for host copies and transition peaks, and define synchronization before retiring an active owner. The current scratch fixture’s metadata-only 262K session does not exercise any of this.

## Concrete owner corrections / unverified allowance

1. Main’s `prefill-no-workspace-review.ja.md` identifies one precise omitted lookahead owner: layer-major processing reads the next layer’s `hc_attn_norm` in half 1. If norms are extracted into a persistent all-layer owner, this needs one extra 40,960 B norm; the resident layer’s two norms already counted in its 81,920 B must not be double-counted. The all-layer HC norm payload is 3,932,160 B; incremental amount versus those two active norms is 3,850,240 B. This is not demonstrated as allocated from the 16 MiB small-owner bucket.
2. `main-review-round707.ja.md` confirms the three non-layer canonical tensors `output_hc_down/norm/up` sum to 13,148,160 B. They are not part of any layer’s 1.3413 GiB maximum. In a canonical dense-bank implementation they must either stay in a separately budgeted persistent owner or be loaded on the relevant final/output path. The capacity table’s 16 MiB allowance can numerically contain this payload but is an unitemized assumption, not proof of the owner being included. Output/head/MTP retention is excluded by scenario, but these canonical HC tensors are used for model output and cannot silently disappear if the requested prefill includes that boundary.
3. PLE projection pointers in `ss.ple.w` borrow canonical weight storage, per round 707 review. Freeing the full canonical arena invalidates them unless they are composed from active layer data or moved into an explicitly budgeted private/persistent owner. The current bank proposal README describes such a retained PLE/HC/non-layer pool; it is a proposal, not the capacity-table’s measured implementation.
4. Input token IDs, GPU token buffer and per-chunk embedding are accounted as separate workspace items; CPU embeddings and the large PLE lookup mapping are deliberately outside VRAM. Their host resident/locked footprint, page-cache policy, and overlap with a GPU layer bank were not measured in the capacity receipt, so no system-RAM maximum can be inferred from the VRAM budget.
5. The 512 MiB runtime and 16 MiB small-owner budgets remain unverified. The alias receipt notes an unexplained 830,853,120 B difference between free-memory observations after retiring an owned slab and the initial query; it is not established as a persistent Strata owner or a universal runtime requirement. Do not convert that one observation into a fixed runtime deduction without attribution.
