# R1022 — QSA block-score の native16 GEMM / joint-matrix XMX 実現性

分類: decision_support（read-only source / primary-source review）  
対象: Main 指定 source basis `b280c259`（production source `f2d0ef42` と同一との指定）。実装・計測・採用の証明ではない。  
結論: GEMM 化は「APIがあるから容易」ではない。現在の isolated BMG native16 API は K軸と重みの row-major 形を満たすものの、N=block数の64倍数化・入力pack・16-bit出力からFP32 scoreへの戻しが必要で、FP32 per-head ReLU/sum を同じ行列カーネルに残せない。新規 fused tile は出力中間物とpackを減らせる可能性があるが、subgroup joint-matrix の収束制約と未確立のtail処理を引き受ける。今は実装に進まず、先に selection interval を scalar scoring と top-k に分けるべき。

## 実経路と実数

`src/prefill/prefill.cpp` の長prefill QSAは、`indexer.q_proj` を `bf16_proj(..., m.q_idx, ..., m.mixed_bf_lo)` で出力し、その後 `rms_rows` と RoPE をFP32の `m.q_idx` に適用する。`native16::qsa` opt-inでもこのindexer経路はtyped16化されず、q_idxの producer/projection residual correction から norm/RoPE後までFP32。pooled keyは `native_qsa_indexer_append_batch` が `idx_raw` の4-token平均、RMS norm、位置RoPEで更新し、FP32の `st.idx_pooled` / `st.idx_dead` に保つ。したがって候補のBF16 Q/K packはproducerをBF16に置き換える案ではなく、既存FP32境界の後で丸めてscore専用に使う追加stage。

selectionは `t0 += m.sel_batch` のquery batchごとに `active = last_query.n_bid + 1` を算出し、`qsa_block_scores_tc(...)` を試し、SYCL実装がfalseを返すため `qsa_block_scores(...)` に落ちる。そのkernelは1 subgroup/query-blockで、4 headそれぞれのFP32 dot、各headごとのReLU、4値の合計を行う。最後の `b == nb` は `dead` を読む。`n % 4 != 0` のtailには+1e9を足し、block選択後のtop-kが実セルIDに展開する。スコアとtop-kは別kernelであり、既存`qsa_block_topk_prefill`はmapping0/radix/cyclic選択を維持する。新経路はtop-kや出力順序の責務を変えるべきでない。

ここで `nq` はselection batch query数、head数4、D=128、`N`は1 queryで比較するblock数。physical 262144 contextで理論上 `n_bid=65536`、score対象はcompleted blocksとtail spareを含む最大65537。pool容量は`max_cells/4+2`で、dead spareを含む。actual `sel_batch`, `m.max_blocks`, `m.cap`, layer-majorの最大query/selector boundsは構築時値を使い、最大物理容量と各queryの実step値を混同しないこと。indexerの規約上、queryごとに`nb=n/4`が異なり、future queryのためにappend済みpooled rowがあってもそのqueryの`b>nb`は無効。tailは完成pool rowではなくdeadを使う。

診断 `moe-window10-first-model-pair-v1.json` のQSAselection約15.8秒は、明記通りNONEXCLUSIVE queue intervalでscoring+top-kを含む。これはXMX向けmatrix仕事の比率、GPU実行時間、utilizationのいずれも示さない。既存FP32経路は保持し、先にscore-only device intervalとtop-k-only interval、host submit CPU時間、wait中のthread CPU時間、wallを分ける。実測無しにmemory-bound/XMX-boundを決めない。

## 選択肢A: pack + 現在のnative16 GEMM + FP32 epilogue

Public `include/strata/prefill/gemm.hpp` のSYCL `bf16_out16`/`f16_out16` は `X[T,K] . W[N,K]^T` の格納意味で、native matrix accumulationはFP32だがYは指定した16-bit dtypeに一度丸めて出す。isolated adapter `src/prefill/sycl/vllm_xe2/native16.{hpp,cpp}` はcompact row-major `x[T,K]`, `w[N,K]`, `y[T,ldy]` を受け、transpose/packingなしの `W[N,K]^T` 解釈。beta=0、N%64=0、K%32=0、ldy>=Nかつ8倍数、registered device allocation/64-byte alignment、BMG G21/G31 Level Zero、in-order queueを要求しfallback無し。ここではQはTLA adapterを通るnative16 GemmのX、pooled KはW。既存K=128なのでK条件を満たす。Qの連続`[query,4,128]`を`[4*query,128]`として扱え、per-query explicit transposeは不要だがFP32→BF16 packは要る。pooled `[block,128]`は要求W形そのもの。poolはGPU上FP32なので一回または増分のBF16 packが要る。

自然な一回の積はM=4*nq, N=round_up(max_query_blocks,64), K=128で、出力 `[4*nq,N]` の16-bit dots後、GPU epilogueがBF16/FP16→FP32化し、4 headを個別にReLUしてFP32合計し、tail+1e9を追加する。しかしnative16 APIはaccumulatorをkernel内epilogueへ公開せずYを16-bit storeする。このrounding境界は元のFP32-per-head-dot→ReLU→sumと異なる。`qsa_block_scores_tc`の宣言にあるCUDA 3xTF32 FP32-level accuracyはSYCL stubの契約でなく、BF16 routeに精度を移植する根拠にもならない。fused final-score output16ではさらにReLU前head dotsが先に丸まるため、score orderも変わり得る。

GEMM score matrix自体は2 bytes/elementで、`[4*nq,N]`をそのまま確保すると現行`[nq,max_blocks]` FP32 score領域に対するbyte比は約2倍（N paddingを除く）。4-head reduction後にFP32 scoreへcompactする必要がある。selectorは`m.max_blocks` strideで読むため、paddingを含むGEMM Yを直接selectorへ渡すにはstride対応変更が必要。GEMMは矩形上限まで全query×blockを計算するが、stepごとのvalid blockは異なり、無効row/未来blockをscoresへ書かずに済む既存kernelと異なる。queryを小さなtileに分けてもcapacity、zero-fill/skip tail、`dead`の差替え、同期、再利用pool packの所有者・leaseが残る。262144上限ではN=65600の丸めが候補で、実際の`nq`/sel_batchとallocation limitsを照合する必要あり。現APIはfull Y rectangleのlive allocationとint extent制限も課す。

判定: API利用可能性はあり、事前pack済み共通key matrixと高いquery再利用があれば測定対象。ただしscore dominatesが実証される前はno-go。現在のnative16 matrix APIだけではFP32 score epilogueとの一段融合を実現せず、現経路より余分なpack/kernel/帯域と2倍級中間領域を足す。

## 選択肢B: 新規fused joint_matrix tile

概念tileを8 queries × 4 headsでM=32 rows、32 block keys×128でN=32、K=128、BF16 Q/K load、FP32 accumulatorとする。1 tileでQ[32,128]×K[32,128]^Tを計算し、各row内の4 head-dotをReLU+FP32 sumしscoreを出す。block dimensionをtile=32とすると自然なblock×query reuseを持つ。現行row-major Kが joint_matrix の許すlayout/strideで直接loadできなければVNNI/packed stagingが要る。SYCL joint_matrix仕様では演算は`sycl::sub_group` collectiveで、全work-itemが収束したcontrol flowでload/mad等を実行する必要がある。supported M/N/K/type/device combinationはdevice query対象で、experimental APIかつ非互換変更可能。Intel guideはXMX hardware必須、fallback/emulation無しと明記する。8×4のconceptual tileは性能保証でも合法shapeの保証でもない。

安全なmappingではqueryごとにvalid blockが異なり、block端のtileでは一部outputをmaskする。joint_matrix collective内でquery/blockごとに分岐してはならず、全work-itemがmatrix操作に参加した後、store時のvalid maskまたは別edge pathで出力を制御する。`nb`の最後のcellは`pooled`ではなく`dead`を読む。`n%4` tail bonusは4 headのReLU合計後に加算する。queryごとのlength、zero/partial context、`n=262144`、dead spareを含むpool capacityをguardする。現selector strideに合わせてscoreを出すには、row-major query×`m.max_blocks`を維持するかcompact-to-selector変換を行う。4headのrow reductionとReLU/sum順序を保ち、複数subgroupが一つのjoint_matrixに参加する前提は置かない。

判定: API制約に合わせてfused implementationを新規設計する候補ではあるが、現状は概念比較のみ。優位性は追加pack/intermediateを省くことに限られ、XMXで実際に命令発行されるか、tileがoccupancy/traffic上得かはBMG compiler・device matrix query・実測を要する。新たなnative codeのprovenanceはStrata独自実装として記録し、Intel experimental spec/examplesを参照元として記録すること。

## 数値契約: BF16は採用済み契約ではない

現sourceの`q_idx` producerは `bf16_proj` (補正input `m.mixed_bf_lo`も渡す) の後、FP32 normとRoPE。pooled keyもFP32 mean/norm/RoPE。scoreはFP32 per-head dot, `ReLU` each, FP32 sum。この正確な実行をBF16 Q/K + FP32 dotで同じく再現するわけではない。丸めはscore入口で増え、FP32 dot/加算順は既存subgroup kernelの積4項/ lane、xor reductionとは変わる。

SGLang/vLLMの現在公開Qwen3.5 model実装はmodel-family参考として存在するが、ローカルQwen3.8-Flash-Next checkpointのconfig/weight実装や実行選択を証明しない。上記モデル実装の公開コードだけではこのforkの独自indexer `pooled mean→RMS→RoPE→4-head ReLU dot→sum` が同じ呼出順/roundingであると確認できなかった。SGLang/vLLMのmodel config, runtime dispatch, selected kernel, activation dtypeと入力値まで照合されるまでは「BF16 Q/KはvLLM契約」と断定せず近似案とする。FP32/llama.cppとの差だけを理由にrejectする必要はない。次のquality gateではvalidate済み同family SGLang/vLLM execution contractを先に固定し、その契約とscore/top-k/選択cell差を比較する。FP32 routeは診断対照として保持。選択ID差は自動的に無害でも自動的に失格でもない。QSA attention出力、自然prompt NLL/teacher-forced loss、生成品質への影響を決める実測が必要。

## Gates と最大2つの次実験

0. Mainが実行中のmode10 clean cohortを閉じるまではGPU作業を重ねない。QSA64 component arm後、現binaryの短いselector subprofileでscore-only vs top-k-only device event、host submit CPU time、wait中CPU時間、全体wallを分ける。15.8s intervalからscore占有を推定しない。これは候補を選ぶ判断実験で、実装は不要。
1. scalar scoreが測定上の重要部分である場合のみ、**一つ目**のcomponent comparisonを選択: pack costを含むcurrent native16 GEMM arm。FP32 referenceを保ち、正確な`sel_batch`, max `nq`, N rounded capacity, Y/scores scratch peakを見積り/測定する。score errors, per-query top-k cell overlap/order, finite/tail/partial/dead/empty/full262144 checks、owner/immutable selector capacity/lease/drainを条件にする。end-to-end scoring+epilogue+top-kは別計測し、pack costも償却させず含める。
2. GEMM armが16-bit output round/traffic/capacityで不適、またはscore sectionを省ける余地があり、明確な利益仮説が残るときだけ**二つ目**として新規joint_matrix fused tileのsource/build/component screenをMainが計画。device-supported matrix tuple確認、BMG compiled entry/codegen evidence、mask/tail/dead handling、bounds/lease/fault、numerical and model-quality gatesを満たすまでactive selectionへ繋がない。

No-go: selection score sectionがtotal costで小さい、pack+matrix+epilogueが元score kernelより遅い、max-context peakがowner budget超過、producer/reference/partial-tail semanticsを保てない場合。いずれかの新規案にXMX utilization数値は存在しない。
