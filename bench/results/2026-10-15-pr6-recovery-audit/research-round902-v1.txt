These mappings follow the pinned [PTI `ze_collector.h` at commit `6c0d6b0b80c6dbac4b5902d9d5ade1c75b9e9033`](https://github.com/intel/pti-gpu/blob/6c0d6b0b80c6dbac4b5902d9d5ade1c75b9e9033/tools/unitrace/src/levelzero/ze_collector.h) (the task pins its SHA256 as `6ee0130e2b03918a5e4bb5d310dacb94e5ba06bf67c21a23d3134dc406aa9122`). `OnExitKernelCreate` queries `zeKernelGetProperties`, copies the fields above, and attaches the experimental register-file extension. PTI prints zero for private/spill sizes and prints “unknown” for the register field only when that extension returns zero. PTI obtains the JIT/AOT label from the module's tracked compilation classification. The Level Zero specification defines `maxSubgroupSize`, `localMemSize`, `privateMemSize`, and `spillMemSize` as kernel properties, with local memory described per thread group and private memory per thread ([Level Zero kernel API](https://oneapi-src.github.io/level-zero-spec/level-zero/1.19.12/core/api/apis/kernel.html)).

The row therefore establishes a **compiler/driver-reported 4 KiB local-memory property and a 128-unit register-file-size property for this compiled kernel object**. The 4 KiB local value is below the published Xe2/Battlemage per-work-group limit discussed below. The 128 value is consistent with the regular 128-GRF-per-thread option Intel lists for Battlemage. Neither comparison is an occupancy result: this property table contains no active work-group count, measured register use, or resource-limited stall count.

## Why 4 KiB is not the whole SLM story

Level Zero calls `zeKernelGetProperties` properties invariant. Its API separately specifies that an SLM kernel argument's byte count is supplied as `argSize` through `zeKernelSetArgumentValue`. In the pinned PTI source, the property query is in the successful kernel-create callback; it happens before later argument binding. The collector tracks group-size changes and uses the current group size when adding launch records, but the properties table does not print that size, and this header does not track local-argument sizes. Thus 4,096 B should be read as the create-time `localMemSize` value, not as a complete per-launch sum that is known to include local-accessor arguments set afterward.

The matching SYCL `launch` source declares local accessors for query tiles, key/value storage, scales, scores, reductions, and row indices. A previous source-level estimate put the visible local arrays near 44,500 B. That estimate and 4,096 B measure different things: the former totals source declarations under assumptions about shapes and overlap; the latter is the captured Level Zero property. Without the actual sizes supplied for local arguments, device allocation rounding, and compiler lowering/lifetime reuse, do not add them, substitute one for the other, or treat either as measured physical residency. In particular, source-declared bytes do not show whether all arrays are simultaneously allocated or whether their ranges can be reused.

Intel's Xe GPU architecture guide lists for its Xe2/Battlemage row **128 KiB SLM per Xe-core, 128 KiB maximum SLM per work-group, maximum work-group size 1,024, and supported subgroup sizes 16 and 32**. The same table lists 128/256 GRFs per thread in regular/large register mode, 512-bit register width, and eight hardware threads per vector engine ([Intel Xe GPU architecture guide, 2025.2](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2025-2/intel-xe-gpu-architecture.html)). Intel identifies B570 as Xe2 with 18 Xe-cores and 144 vector engines ([B570 specifications](https://www.intel.com/content/www/us/en/products/sku/241676/intel-arc-b570-graphics/specifications.html)). This is useful published family-capacity evidence; the captured run did not query the B570 runtime's local-memory-size or work-group-size device properties, so do not relabel the guide's family row as a same-run device query.

A naive division of 128 KiB by the reported 4 KiB would yield 32, but that is not a defensible resident-work-group ceiling. The denominator may omit launch-time SLM arguments; the numerator is an architectural per-group/per-core capacity, not a promise that the full pool is schedulable for this kernel; and allocation granularity, reservations, per-EU/thread limits, and register allocation interact. Intel's SLM guide also describes SLM as core-local and work-group-shared, and warns that the work-group allowance is device-dependent and may depend on work-group size ([Intel Shared Local Memory guide](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2024-0/shared-local-memory.html)). Exact B570 partitioning and allocation rounding were not established by these sources or this capture.

## What remains unknown

1. **Effective work-group shape.** The property row omits the configured local size and the actual group size used for each launch. The API's required group-size fields, when present, are compile requirements; PTI separately observes `zeKernelSetGroupSize`, but that value is absent from this row. The source's subgroup-size request and `SIMD 16` do not supply the work-group size needed to reason about per-group thread count.
2. **Dynamic SLM total.** The row gives no per-launch local-argument byte sizes. It does not resolve whether the source estimate is the physical allocation, whether any local objects have disjoint lifetimes, or how the compiler/runtime rounds or reserves SLM.
3. **Register allocation and residency.** The 128 extension value names the register-file size used, not the live register count. The record does not identify actual work-groups resident per Xe-core, per-EU allocation granularity, thread/slot limits, or whether SLM or registers constrain scheduling. Zero private/spill values are compiler/driver metadata for this JIT kernel object, not occupancy counters or a guarantee for every input or other compiled specialization.
4. **B570 runtime limits and counters.** Published Xe2/Battlemage capacities do not reveal the exact runtime values or the collector's query-validity for this run. No physical GPU metrics were collected, so there is no measurement of active occupancy, resource stalls, or an SLM/register bottleneck. The PTI row is adequate for narrowing the question, not deciding it.

## One next diagnostic question

For this exact JIT Mode1 QSA kernel and a named launch shape, do actual `zeKernelSetArgumentValue` local-memory sizes plus the configured work-group size, when compared with valid B570 resource/occupancy counters, show residency limited by SLM or by the 128-register-file mode? Record per-launch dynamic SLM sizes, actual local size, runtime `local_mem_size`/work-group limits, and counter validity/denominators in the same component-scoped collection after collector qualification; do not change source or GRF/SLM flags on the strength of metadata alone. Counterevidence already exists: the reported 4 KiB is far below Intel's published 128 KiB per-work-group Xe2 limit, and 128 is the regular mode in Intel's table. If launch-time SLM remains modest and counters show several active work-groups without resource stalls, the SLM explanation weakens; if dynamic local arguments are large or valid counters show a low SLM-limited residency, it strengthens. This diagnostic would answer the resource question only; it would not qualify whole-prefill speed, RESTORE, numerical quality, or physical 262144-context correctness.
