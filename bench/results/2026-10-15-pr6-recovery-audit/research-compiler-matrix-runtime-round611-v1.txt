## Decision

The pinned llama.cpp note is a worthwhile reason for one controlled compiler-stack experiment after the current Direct0 and Direct1 official benchmark processes have both closed. It is not evidence that Strata should switch compilers or that this Qwen model will gain 3.1x. The note reports Arc B570 prompt processing at 1331 versus 434 tokens/s, but does not identify the model, prompt length, batch/chunk, arithmetic mode, llama.cpp source commit for the compared binaries, full build flags, benchmark command or raw samples. Its page is pinned at documentation revision `a0e6dc7384edb8f5d927155e1d26c10b4a310e6d`; that pins the claim text, not the benchmark implementation or the compared source/binaries. The paired builds are called “same code” but the note does not show that the oneDNN/oneMKL versions, compiler flags, runtime/UR/driver, AOT/JIT mode, or library dispatch were held constant. I did not fetch the unavailable revision into the local mirror.

The claim bundles a compiler/toolkit update with an updated CI/build environment. It does not establish compiler code generation as the cause. It also cannot establish a gain on Strata’s Qwen3.8-Flash-Next 32K-prefill / 64K-context / 70-token-generation target. Current Strata code uses a different set of kernels and dispatches than llama.cpp.

## Is the compiler/matrix path new?

There is a distinct possible experiment: compile the existing Strata kernels with packaged oneAPI 2026.1, holding the source and current oneMKL 2026.1 fixed. This asks whether compiler-generated code on this card improves. It is not a new XMX or joint-matrix implementation. Current source already has a native XMX MMQ kernel (`src/kernels/sycl/native_mmq_xmx.cpp`) and Intel `joint_matrix` prompt attention (`src/kernels/sycl/prompt_attention.cpp`). The live Direct0/1 comparison is already testing the latter’s existing output-store option on one binary. Do not re-run that source experiment under a new compiler until both current benchmark arms close. R566 already covered the per-expert FP16 GEMM path, FP32 accumulation, oneMKL grouped-GEMM possibility, and a separate fused GEMM+SwiGLU proposal; changing compiler is orthogonal and does not make grouped GEMM new. R589 separately proposed QSA block-score FP16/BF16 oneMKL GEMM; it is not evidence for this prompt-attention or MoE route.

Keep these causes separate:

- **Compiler code generation:** changed DPC++/LLVM version may emit different kernels for existing SYCL/joint-matrix source.
- **oneMKL dispatch:** the current MoE projection calls oneMKL. Keep oneMKL headers, library build and version at 2026.1 across the first comparison. A changed MKL build/dispatch is a separate variable.
- **oneDNN dispatch:** no oneDNN API appears in Strata’s current `src/`, `include/`, `cmake/` source paths reviewed here. The llama.cpp note says its CI moved to the unified toolkit because oneDNN packaging changed, so an upstream llama.cpp result may include a oneDNN/library-path difference irrelevant to Strata’s direct code path. Do not attribute that result to joint_matrix or oneMKL.
- **SYCL / Unified Runtime / Level Zero:** the alternate packaged compiler may require its matching SYCL and UR runtime. If current and new compilers cannot be supported against the same runtime, a compiler-plus-runtime result is a toolchain-stack comparison, not a compiler-only measurement. Do not force mixed runtimes without first proving supported link/runtime compatibility.

R454 records a concrete header/API difference between the open-source SYCL install and `/opt/intel/oneapi/compiler/2026.1`: Intel’s `sycl::ext::intel::math::ha::exp` overload is present only in the latter. Treat that as a source-compatibility gate, not as permission to alter math. Also recheck `joint_matrix`/`joint_matrix_apply`, device linking, ABI, floating-point flags, kernel acceptance and runtime/UR loading under the alternative compiler. Matching a version string alone is not validation.

## Proposed bounded experiment (after Direct0 and Direct1 close)

1. Freeze one exact source tree/snapshot and its hashes, model/token input and build options. Make two independent out-of-tree builds; leave the existing official-benchmark binary and build tree untouched. Arm A rebuilds with the recorded custom LLVM DPC++ compiler/runtime. Arm B uses installed oneAPI 2026.1 `icpx`/`icx`. Use identical Release, C++20, SYCL, source-specific FP flags, ILP64, target architecture setting (empty unless the baseline recipe proves otherwise), CMake feature options, oneMKL 2026.1, model, input, launch arguments, and safe runtime environment.
2. Before timing, save both compiler `--version` outputs and binary hashes; inspect each compile command; prove which `libsycl`, UR, Level Zero and oneMKL DSOs each process actually loads; confirm no runtime cache cross-contamination; run the same bounded CPU/device correctness and matrix-admission checks with fresh fault checks. Compare prompt-attention and representative MoE/GEMM output fingerprints before the full-model arm. Keep failed build/runtime/correctness results as failures.
3. If the oneAPI compiler cannot use the exact same supported SYCL/UR runtime and oneMKL, label Arm B “2026.1 compiler+runtime stack”. It is still useful as a practical stack comparison, but it cannot isolate compiler code generation. A later factorial compiler/runtime test is warranted only if Intel documents/supports the cross pairing and the loader evidence proves it. Never attribute a bundled stack delta to compiler alone.
4. For performance, wait for both frozen-binary Direct arms to finish, then run owned separate clean processes using the same official long benchmark recipe and fixed prompt/model fingerprints. Compare Arm A vs B in balanced order with individual samples (at least three full runs each), no profiler/tracing, same Direct setting first. Report prefill and generation separately, throughput and total wall time, output/logit or quality checks, all settings and faults. If source Direct0/1 affects the component under study, then after the compiler baseline add the 2×2 compiler × Direct0/1 comparison; do not fold the current live Direct result into a compiler comparison. Require an improvement outside run variance and no correctness, fault, generation or quality regression before any adoption decision.

Recommendation: schedule the identical-source compiler/stack A/B only after the active official arms close. It is the one new experiment justified by the upstream note; make no compiler or matrix-kernel change from the 3.1× number itself. If the compiler/runtime and oneMKL versions cannot be separated, document the outcome as a stack comparison and limit the conclusion accordingly.
