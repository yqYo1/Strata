## Exact contract audit

**Element type and storage.** `PaddedK` is a standard-layout, trivially copyable aggregate with one `sycl::half[10240]` member. In the installed headers, `sycl::is_device_copyable` defaults to `std::is_trivially_copyable` (header `include/sycl/detail/is_device_copyable.hpp`, lines 29–44), so the proposal's trait assertion is consistent with the implementation. The object has `sizeof(PaddedK) = 10240 * sizeof(half)` if the accompanying static assertion passes; the expected 20,480 bytes depends on `sizeof(sycl::half)==2`, which is a compile-time check in the proposal. The C++ standard-layout first-member property puts `values` at offset zero; `alignas(4)` raises the object's alignment to at least four, and the element array therefore begins at that aligned address if the local allocation honors the element type's alignment. A one-element local accessor is in range when `kv[0]` is used.

The Khronos SYCL Reference's [local accessor/container contract](https://github.khronos.org/SYCL_Reference/iface/accessor-concept.html) states that a local accessor owns its elements, that its range is set at construction, and that accessing outside the range is undefined. The proposal constructs range one for `PaddedK`, then addresses its member array; it does not index past the accessor's one element. The installed Intel header `include/sycl/accessor.hpp` defines one-dimensional `local_accessor::operator[](size_t)` as returning a reference to the requested element (around lines 2282 and 2306). This supports the member access shape. The source-level assumption is that the implementation's local allocation meets `alignof(PaddedK)` as required to store an object of that type; header inspection alone does not verify device allocation lowering.

**Address-space conversion and matrix overload.** Installed `include/sycl/multi_ptr.hpp` (around lines 1367–1377) declares `address_space_cast<Space,DecorateAddress>(ElementType*)`, returning `multi_ptr<ElementType,Space,DecorateAddress>`. `include/sycl/ext/oneapi/matrix/matrix-unified.hpp` (around lines 238–267) has the `joint_matrix_load` overload accepting a `multi_ptr<T,Space,IsDecorated>` and statically disallows only private-space sources. Thus, if `&kv[0].values[0]` is accepted as the parameter type, the cast result has the exact multi_ptr shape consumed by the existing matrix-load calls. The Khronos [address-space reference](https://github.khronos.org/SYCL_Reference/iface/address-space.html) specifies that `address_space_cast` produces a multi_ptr with the requested address-space and decoration, returns null for a runtime-incompatible address, and requires a diagnostic for an incompatible deduced source address space. Here source and destination are both intended to be local, which are compatible.

There is an implementation detail to verify at compile time: the local accessor's reference is address-space decorated by the installed accessor implementation, while Intel's `address_space_cast` implementation routes local-space destinations through `__spirv_GenericCastToPtrExplicit_ToLocal` (installed `include/sycl/detail/address_space_cast.hpp`, lines 63–80). The standard API contract permits the compatible local-to-local request, but the header body alone does not establish how this exact input decoration is normalized by the v7.11 compiler frontend/backend. This is a compile confidence limit, not a demonstrated defect. A simpler direct `kv.get_multi_ptr<decorated::no>()` cannot expose the nested member-array start, so the cast has a clear purpose; a compile diagnostic or IR issue would need to be resolved before runtime qualification.

**Pointer arithmetic and bounds.** The QK B tile has 16 rows and 16 columns. For each `k` from 0 through 240 in steps of 16 and `cell` equal to 0 or 16, the pointer offset is `k*40+cell` half-elements. Its byte offset is `(k*40+cell)*2`, divisible by 4 (indeed by 32 for these loop values). Row-major stride 40 is `40*2 = 80` bytes, a multiple of eight and less than `2^24`. The largest accessed element is `(240+15)*40+(16+15) = 10231`, below array element 10240. The K gather writes only `dim*40+c` for dimensions 0..255 and live cell columns 0..31, so its maximum write index is also 10231. Columns 32..39 are padding and no enumerated QK matrix tile includes them.

Intel's primary [oneAPI joint_matrix extension](https://github.com/intel/llvm/blob/sycl/sycl/doc/extensions/experimental/sycl_ext_matrix/sycl_ext_oneapi_matrix.asciidoc), in the BMG-G21 restrictions, says row-major stride is measured in elements, `stride*sizeof(T)` must be a multiple of 8 and at most `2^24`, and the base pointer must be 4-byte aligned. It also restricts `row_index` for the separate offset overload; this proposal uses the pointer-plus-stride overload and does not pass `row_index`. Pitch 40 and the offsets above meet those documented requirements. The extension separately makes matrix shape/type support device dependent; preserving the existing runtime matrix-support gate does not itself prove target support or execution success.

**K/V reuse and synchronization.** The QK reads occur after the K gather's existing work-group barrier. The existing barrier after QK completes before the V loop overwrites the same underlying allocation through `kvp[i]`; another barrier occurs before the PV matrix loads. Reusing the first 8192 half elements for V is within `values[10240]`. The K padding is irrelevant after the QK barrier, and V overwrites every element in the contiguous range read by PV. No new barrier or divergent barrier was introduced. Matrix calls remain under `subgroup < 4`, a condition uniform for all 16 lanes in each participating subgroup; the surrounding work-group barriers remain unconditional. The logical fixture extends a CPU index proof, but it does not test the actual SYCL object lifetime, compiler lowering, or device visibility.
