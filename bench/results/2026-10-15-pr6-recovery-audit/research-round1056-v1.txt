## What DumpZEBin captures

In pinned NEO source `724697d73af22685918fcad4575c6bc267589ca`, `DumpZEBin` defaults false. Level Zero `ModuleImp::initialize` calls `dumpFileIncrement(blob, ..., "dumped_zebin_module", ".elf")` after successful single-device binary decode, only when decoded format is Zebin and the flag equals 1. This captures the module input blob at that point; it is not an args/AUB/memory dump and does not itself compile a source kernel. A second call site exists in the Zebin decoder for archives, so one input may reach repeated dump sites depending on path. `dumpFileIncrement` checks for an existing name, then selects base `.elf`, `_0.elf`, `_1.elf`, etc., and writes in the current working directory unless `ForceLoggingDirectory` redirects it. The existence check plus write is not an atomic reservation; parallel calls can race. A dedicated empty cwd, one owned process, bounded output, and post-capture count/size/hash checks are the right controls. The full blob can contain more than the target kernel; cap and inventory before disassembly.

`zeKernelGetProperties` is a Level Zero kernel-object query, not a `.ze_info` static field. In the pinned NEO implementation it returns descriptor properties and `getSlmTotalSizePerThreadGroup(privateState.slmArgsTotalSize)`. Thus it includes dynamic local-argument sizes already supplied to that *kernel object*. For local args, NEO computes offsets, aligns each following local arg to its `requiredSlmAlignment`, adds its size, then rounds the accumulated dynamic end up to 1024 bytes. The descriptor combines that dynamic total with compiler inline SLM according to its allocation mode: compiler-resolved adds inline bytes; runtime-adjusted uses nonzero dynamic total, or inline size when no dynamic args were set. Query before setting args is a different state from query after setting them. Keep both timestamps/state and do not call either value physical allocation or residency.

The API defines `localMemSize` as local memory used by each thread group; pinned NEO maps it to the descriptor total above. The later dispatch encoder aligns/programs SLM separately. On BMG, use the matching installed runtime's actual command encoding/release helper and queried `localMemSize`; do not infer its rounding from `ze_info`, or transplant XeHPG/Xe3 tables across architectures. Even an encoded SLM size is a per-workgroup request, not proof of concurrent resident workgroups: occupancy also depends on hardware limits, registers, threads, barriers, other resources, and scheduling. The source tree here is commit `724697d...`, explicitly not established as the deployed 1.17.39395+14 driver source. Treat these details as a testable implementation reference until version/build provenance is matched.

## Bind ELF entry to the measured service

The dumped file is useful only after binding its kernel symbol to the exact source and dispatch. Preserve the complete ELF and hash; list its `.ze_info`, kernel symbols, and `.text` sections. Locate the mangled native kernel and demangle it, then compare the lambda/template identity with the source-pinned `prefix_batch_impl<33,false,false>` implementation and dispatcher. Confirm the owning model process, selected environment, device target (`BMG`), loaded module/kernel name, and callsite; require one matching kernel entry and no alternative/fallback entry for those 120 calls. A similarly named AOT image, warmup/decode kernel, fixture build, or cache binary is not a binding. Main's one-process capture must itself establish that this ELF came from the measured engine/build; a filename alone cannot.

Read `.ze_info` as static compiler metadata: target, SIMD width, GRF mode/count where emitted, spill/scratch bytes, inline SLM, and kernel symbol. It can distinguish the presence of a native `dpas`/`dpasw` instruction from scalar/vector multiply-add lowering in that exact binary. Count/inspect the relevant QK and PV instruction region; one DPAS elsewhere is not evidence that both matrix products use it. If ISA shows no DPAS for the relevant products, describe that binary as non-DPAS lowering. If DPAS exists, it proves selected instructions, not sustained utilization or speed. Record SIMD, GRF, scratch/spill metadata per kernel; zero spill metadata is not proof of zero traffic from all private-memory mechanisms, and a GRF count is not occupancy.

Static `.ze_info` does not know runtime local argument sizes. Compare it with (a) properties immediately after kernel creation and before args, (b) properties after all kernel args have been set for the actual launch, and (c) launch geometry. Capture per-kernel identity with every value. For the local pitch candidates, source payloads 28,224 and 32,320 B plus current source admission slack are not guaranteed equal to compiler inline SLM or property result; dynamic arguments, alignment, and static compiler allocations may change totals. Record both raw property values and the runtime-encoded SLM value only if obtainable from matching version/runtime evidence. None is direct measured SLM-bank traffic or a count of concurrently resident groups.

## Bounded interpretation recipe and limits

Main already owns the `DumpZEBin=1` launch with immutable safety keys, dedicated cwd, and 30 MiB cap. After it closes, preserve the source/build/runtime hashes, dump names/sizes/hash, process and module identity, and API properties before/after args. Disassemble only the retained ELF with the installed `ocloc`/IGA path; record tool version, exact command, target, and output hash. Use `ocloc` only against captured ELF, not to recompile another source binary and then claim it is the running kernel. Review the symbol's `.ze_info` and ISA sections and annotate DPAS vs scalar lowering, SIMD/GRF/spill, static SLM, and runtime localMemSize in separate columns. If module dumps exceed the cap, capture is incomplete and no absence claim is valid. The installed ELF strings may establish that the debug key name is present, not implementation version, default behavior, or deployed source identity.

Official Level Zero Kernel spec defines `ze_kernel_properties_t.localMemSize` as per-thread-group local memory and documents `zeKernelGetProperties`; use it for API semantics, with runtime-specific implementation caveats: https://oneapi-src.github.io/level-zero-spec/level-zero/1.19.12/core/api/apis/kernel.html. NEO source paths above explain the pinned implementation. Intel's compiler docs describe SYCL offload/device binaries and the `ocloc` backend relationship, but command syntax and supported inputs vary by installed tool build: https://intel.github.io/llvm/design/CompilerAndRuntimeDesign.html. IGA disassembly is native ISA inspection, not an execution profiler: https://github.com/intel/opencl-intercept-layer/blob/main/docs/kernel_isa_gpu.md.

Alternatives/counterevidence: use a Level Zero API shim/targeted instrumentation to log kernel properties after each `zeKernelSetArgumentValue` and the launch association; it may perturb timing and needs a separate validated build. `zeKernelGetProperties` can give reliable API-visible localMemSize without a dump, but cannot establish ISA or runtime binding by itself. Existing API timing and source binding establish attention service but cannot distinguish issue bandwidth, cache, barriers, SLM banks, occupancy, or preemption. Native disassembly and resource descriptors narrow candidates; only a later controlled measurement can test whether a resource transition explains the 60% result. Do not infer causality from 28,224→32,320 B, a cliff, DPAS presence, or one property value alone.

Evidence limits: no native ELF was opened or disassembled for this report; no build, GPU, profiler, process, or setting action was performed. Local 724697d source was read-only reference, not verified installed source; current runtime capture, ELF-to-call binding, BMG rounding in deployed build, and physical occupancy remain Main's evidence gates. No XeStrata code, helper, test, or proposal was consulted.
