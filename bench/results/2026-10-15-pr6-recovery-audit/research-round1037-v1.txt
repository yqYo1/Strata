# R1037 — native Xe2 QSA score GEMM with FP32 output

## Decision

The adapter architecture makes a narrowly typed FP32-output route plausible without changing the existing FP16/BF16 routes: the current kernel already declares FP32 C/D accumulator fragments and sends that fragment through TLA's public D-copy helper into a destination tensor whose element type selects the global store representation. A direct `float*` D tensor with a corresponding 4-byte row pitch and rectangle validation is the natural extension. However, the checked public material available in the repo does not prove that this pinned TLA revision's `get_block_2d_copy_D` instantiation accepts a 32-bit destination and emits a legal block-2D d32 store for the QSA geometry. Treat that as a finite source/build/lowering qualification gate, not as an established capability or a reason to redesign the independent 16-bit API.

Prefer a distinct typed F32-output entry (e.g. `fp16_f32_out` and `bf16_f32_out`, sharing internal templates) over changing existing `Storage`/`Problem` representation. Keep `f16_out16` and `bf16_out16` signatures, 16-bit output contract, dispatch, and decode route unchanged. The current public `Problem::y` is `uint16_t*`, and `Storage` has only fp16/bf16: widening `Storage` and interpreting the same pointer as either 2-byte or 4-byte data silently changes that ABI contract and makes rectangle byte sizing and validation dependent on an enum. A separate overload/entry with an explicit `float*` output makes type, span size, store width and callsite intent visible. Implementation is not part of this audit.

## Geometry and guards for QSA

For QSA, M=`nq*4` is 4..1024 by multiples of four; N panels are multiples of 64 through 8192; K=128; row stride is 8192. Existing tiling rounds workgroup counts up (`ceil(M/BM)`, `ceil(N/BN)`), while tensors expose actual logical M/N, explicitly avoiding padded caller allocation (`native16.cpp:41-70, 142-152`). This is the right tail model for M<16/128 and N=64 under the respective tile policies, provided the pinned 2D surface suppresses out-of-range accesses as the adapter comments intend. M tails and N-panel tails need canary validation; current input geometry rules require N%64, K%32, and `ldy>=N`, `ldy%8` (`native16.cpp:41-50`). QSA's N and K meet those constraints; M is deliberately ragged relative to tile M.

For F32 output, y bytes and output pitch must be recalculated using `sizeof(float)`: full rectangle `M*ldy*4`, byte pitch `ldy*4`, and surface width in bytes `N*4` or the logical row width accepted by the exact helper. At maxima, M=1024 and ldy=8192 yields 32 MiB; it fits the current signed-int full-rectangle cap, while output width/pitch must separately satisfy TLA surface limits and d32 alignment rules. Do not retain the current `yb=...*2` or `ld*2` bounds for F32. Input X/W remain 2-byte rectangles and retain their existing overflow, K/N, surface, and signed-int checks. Since `validate_spans` currently receives the whole output span and 64-byte alignment, use the F32 rectangle length and maintain disjoint-output/input checking; `validate_device_span` must still confirm each complete rectangle belongs to live device USM on the queue (`native16.cpp:51-58, 168-176`). The element-type pointer must be `float*`, without routing F32 through `uint16_t*` aliasing.

The safety wrapper remains material: positive dimensions, beta zero, checked multiplication, logical surface bounds, launch extent, registered device span, runtime/device/context identity, in-order queue, BMG architecture, subgroup and workgroup requirements, and queue/allocation lifetime (`native16.hpp` class contract; `native16.cpp:34-96, 165-176`). Reuse those invariants; add output-specific byte arithmetic and any stricter store-atom limits. The API returns the event without wait/copy/fallback; its allocations and queue must outlive queued work and owner destruction must be serialized (`native16.hpp`).

## API/dispatch and isolated link consequences

The lowest-risk surface is two explicit typed entries sharing `enqueue<I,float,Policy>` (or an equivalent F32 output overload), with FP16 and BF16 input dispatch selecting the same `Input` instantiations as today. Keep `Storage` and `Problem::y` as-is for the two existing 16-bit methods; no changes to beta semantics, route selector, or decoder. F32 callsites provide `float*` and the QSA physical stride. This creates compile-time AOT specializations for the supported input × tile combinations, adding native entries/image bytes and potentially changing compile time/resource use; none of those costs is quantified here. It does not inherently require new translation-unit topology: CMake already compiles native16 into an object, completes that component's `spir64_gen` image in a separate `-fsycl-link` step, extracts its host slice, and passes both host objects directly as final link inputs (`cmake/sycl_vllm_xe2_native16.cmake:23-65`). Any new F32 entry must be included in that same isolated AOT object/image and host extraction path. Do not inject relocatable native device IR or change generic engine JIT settings. Verify the resulting executable includes/resolves the new entry and that its device image is the one dispatched; the existing “UNQUALIFIED” status means current docs do not establish a new F32 specialization.

Alternative: extending `Storage` to fp32 and making `Problem::y` untyped/void is fewer named methods but a less safe public C++ ABI and more runtime type validation. Keeping `uint16_t* y` and adding an output enum value is not acceptable: it misstates the pointee type and makes byte extent easy to under-validate. Alternative: retain existing 16-bit GEMM then convert to F32 in another kernel. This is a straightforward fallback if d32 block-2D output is not supported, but costs an extra read/write pass and temporary 16-bit output; no performance claim can be made without measurement. A typed F32 path is preferable only if source/build confirms legal store behavior and Main's serialized qualification finds it correct and useful.

## Finite qualification gates for Main

1. Pin/source review: at the documented TLA revision, inspect only the exact D-copy helper/copy atom/2D store headers named by the 207-header index. Confirm the destination element type selects a supported d32 store, its legal block width/pitch/base alignment and tail mask semantics; cite exact pinned files/lines/hashes. If public code leaves this indeterminate, mark it unresolved and use a distinct F32 kernel epilogue/ordinary SYCL stores or the conversion fallback as a separate design question.
2. Compile/AOT/link review: compile the exact 2 input formats × relevant tile(s) × float output specialization through the existing isolated component. Check diagnostics, final link, entry count/symbol identity and exact runtime image dispatch. Inspect generated ISA/artifact to establish FP16/BF16 operands, FP32 accumulation and F32 store; do not infer from template types alone.
3. Memory/fault matrix: canaries around output and row padding; M=4/12/16/20 and 508/512/516 boundaries as applicable, N=64 and 8192, all QSA N panel boundaries; `ldy=8192`; validate only logical output elements and ensure padding/input canaries unchanged. Exercise misalignment, overlap, undersized/unregistered/non-device spans and disallowed queue/device before enqueue; ensure rejected calls enqueue nothing. Drain before releasing owners; serialized fresh fault checks.
4. Numerical and integration: compare full score matrices against the accepted FP32 reference with explicit absolute/relative bounds and downstream top-k/routing stability; include long contexts and relevant prompt boundaries. Run existing 16-bit API/decode regression as a preservation check, then end-to-end serialized QSA route with source/entry attribution. Measure whole dependency path against current path, recording samples and environment under artifact-retention rules. No quality, speed, or production adoption conclusion follows from this source audit or the small transport trace.
