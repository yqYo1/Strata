# Round 618: layerwise checkpoint v2 source contract audit

Read-only audit of `layerwise-checkpoint-capture-v2/FINAL.md`, generated candidate source, fixture, and archived research-index plus Main R608/R609-610 reviews. No build, test/fixture execution, GPU/process, Git operation, implementation, cleanup, or measurement was performed. This report assesses source contracts only; the proposal itself says all runtime, RESTORE, numerical, physical-256K, and performance qualification is NOT_RUN.

## Findings

No confirmed source-level defect found in the reviewed v2 candidate's stated core contracts. That is a static-review result, not acceptance: candidate has not been compiled or run, and important failure modes remain unproven below.

- **Reread with old checks:** v2's `layerwise_capture_enabled` requires `reread_to <= 0` (`layerwise_checkpoint.hpp:20-23`). At the real caller, `reread_to` is initialized then set to resume while the retained checks remain; reread starts at zero (`proposed/src/program/generate.cpp:5646-5694`). It remains positive for the outer segment loop, whose gate receives it on each segment (`5935-5950`). Thus both the reread segment and later root/turn/final segments bypass the new append-only transaction. The source path supports the FINAL's claim that old checks are preserved for the entire reread request. The nonempty-old-check regression in the fixture is only authored, not executed. There is no evidence here of actual `STRATA_CKPT_REREAD` or RESTORE success.
- **Actual candidate C++ fixture exists:** `cpu_contract_fixture.cpp:1-8` includes the candidate `layerwise_checkpoint.hpp`, with assertions mandatory; it is more useful than Python-only modeling. Its two stub headers replace real session sizing/validation and provide toy tag buffers (`fixture_stubs/strata/core/conversation_snapshot.hpp`). Fake copies and lifecycle calls exercise candidate transaction code but do not validate actual core geometry/pointers, queue behavior, or model state. Fixture is NOT_RUN.
- **Position coherence / ownership:** Candidate enforces sequential layer and chunk-prefix progression (`layerwise_checkpoint.hpp:153-156`), maps each GDN/QSA component by owning layer, and takes PLE history only at layer 1 (`163-185`). Actual hook is called from the single-layer layer-major run after stream synchronization (`proposed/src/prefill/prefill.cpp:3070-3101`); owning layer is checked. This addresses R608's mixed-prefix mechanism in source. Restore's PLE previous IDs are derived from the checkpoint IDs, and QSA pooled dead-row reconstruction remains in existing restore code (`src/core/conversation_state.cpp:179-191`). Neither establishes real tensor-value coherence or RESTORE parity.
- **MTP, refill, publication and unwind:** Caller scopes callback borrowing after the transaction owner and before callback install (`proposed/src/program/generate.cpp:5957-5965`). Guard restores the previous callback from its destructor (`layerwise_checkpoint.hpp:31-43`); checked copies are synchronously retired and unretirable queues fail-stop (`proposed/src/prefill/prefill.cpp:3081-3097`). It waits for prompt wrapper/MTP expert reattachment, then refills loans, checks cancellation, and commits (`generate.cpp:5997-6010`). Commit validates old chain and pending masks before noexcept moves and swap (`layerwise_checkpoint.hpp:199-231`). Static ordering supports intended atomic publication and callback restoration on ordinary C++ unwind. Real exceptions at each boundary, MTP reattachment, slot refill, and next-request recovery remain untested; fail-stop queue retirement deliberately has no graceful unwind.
- **MTP completion marker:** `prompt()` requires all 48 layer bits (`layerwise_checkpoint.hpp:187-197`); caller invokes it only after `run_prompt_with_mtp_experts` returns (`generate.cpp:5967-5972`), which is the intended post-MTP hook point. The fixture models that ordering, but cannot show native draft KV/restore correctness.
- **LRU / duplicate events / atomicity:** `begin()` previews old and fresh positions, updates existing positions' use stamps, applies `conv_cache::eviction_victim`, allocates state only for final fresh survivors, and preallocates publication (`layerwise_checkpoint.hpp:103-151`). `commit()` maps old/fresh owners and swaps only after validation (`199-231`). This appears to retain root-pinned policy subject to actual helper behavior and caller event schedule. Fixture oracle is independently written and includes old checks, duplicate boundary events, and LRU, but is unrun and uses a small synthetic chain.
- **Overflow / admission:** Candidate bounds cap at 262144, model geometry, input IDs, positions and schedules before payload allocation; `add`/`mul` guard signed-range overflow, and next-position arithmetic saturates (`layerwise_checkpoint.hpp:17-25,49-64,86-102`). It estimates preview and 2x fresh payload plus metadata against available memory with 8 GiB reserve, then checks actual vector capacities (`85-151`). This is conservative source accounting, not proof of allocator peak, reclaim, RAM telemetry, or successful full-context operation. Existing `conversation_memory_admit` rejects unknown availability, consistent with fail-closed admission.
- **Full 256K scope:** Source allows `cap <= 262144`, checks `end <= ss.max_cells`, and geometry/session state for whole 48-layer model. This preserves a logical path to a 262144 context. No physical allocation, near-end prefill, batched n-1 boundary, page/slot fallback or subsequent legal decode was run; neither the fixture's logical positions nor CLI capacity establish physical-256K support.

## Prior v1 issues and disposition

The archived Main reviews identify the actual v1 hazards: final-layer whole-session callback could pair earlier-layer state from segment end with a shorter final-layer prefix; PLE is owned by layer 1; save before expert restoration/refill was too early; and old checks were retained during reread. V2's one-layer callback, owner-specific piece capture, layer-1 PLE capture, explicit post-wrapper/refill commit, and whole-request reread gate address those source-contract concerns. The prior no-actual-C++-fixture gap is improved by the new candidate-header fixture. These are qualified source dispositions only, not evidence that v1 caused a historical GPU failure or that v2 works in execution.

## Material missing evidence

The authored C++ fixture, ASan/UBSan variant and Python oracle have not been run. No integrated-header build, configured SYCL build, real restored-vs-reread state comparison, target/draft KV or output parity, real cancellation/exception tests, queue fault tests, allocator peak measurements, or physical 262144-context run exists in this audit. Host simulations cannot be cited as actual RESTORE success. No speed/adoption conclusion follows.
