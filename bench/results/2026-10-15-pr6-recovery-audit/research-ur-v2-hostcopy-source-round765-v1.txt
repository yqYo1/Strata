# R765 — UR v2 host-copy submission and pointer-registration path

2026-10-16 JST. Bounded read-only source research. This report is the only file written. No product source, build, test, GPU run, profiler, process inspection, Git operation, environment/service mutation, or cleanup was performed. No XeStrata code or derivative was read or used.

## New finding and version boundary

The 78K diagnostic's 25.7935 caller CPU seconds in host residual copy calls (input 9.4307 s, save 16.3627 s) still cannot be called CPU math, physical transfer time, or removable latency. The newer evidence separates those API call regions from their completion waits, but an asynchronous return does not guarantee a short host call.

The existing receipt names a toolchain directory `intel-llvm-v711` and forces `libur_adapter_level_zero_v2.so.0`; it does not record an immutable LLVM source revision or binary-to-tag provenance. Official Intel LLVM release `v7.1.1` resolves to commit `504366f4b82ff00bbac7b0c956635eed8bc599d8` and is the closest open-source release to oneAPI DPC++ 2026.1, using `sycl-rel-7_1`; the release itself warns this does not guarantee feature or bug-fix parity. That makes v7.1.1 a useful source snapshot for the `v711` label, not proof that the installed library was built from that tag. I separately examined the `intel/llvm` `sycl` head at `b29c1834fc5795c9748173a1b3ab48e3d75abd28` (2026-10-15); it is newer than v7.1.1 and is not evidence about the installed binary.

## What the versioned UR v2 code shows

At v7.1.1, `ur_command_list_manager::appendUSMMemcpy` calls `zeCommandListAppendMemoryCopy` and calls `zeCommandListHostSynchronize` only when its `blocking` argument is true. The v2 batched queue invokes it with `false` for a nonblocking copy. However, before appending, that queue checks its issued-command limit; when reached, `markIssuedCommandInBatch` calls `queueFinishUnlocked`, which submits the active batch and calls `zeCommandListHostSynchronize(..., UINT64_MAX)`. Thus a copy requested as nonblocking can encounter a host-side drain on this specific batched-queue back-pressure path. The source does not establish that Strata used a batched queue for this run; “in-order” alone does not identify immediate versus batched submission.

For the ordinary nonblocking path, UR itself submits the pointer pair to the Level Zero append call and does not show a CPU memcpy or staging loop in this function. That still leaves possible host work inside the driver append, runtime bookkeeping/locks, or queue-mode back-pressure. The source and API contracts do not prove any of those occurred here. In particular, the previous 131.610 s route-publication interval includes a queue wait that drains earlier GPU work, so it is not pure map-copy latency or time a faster host pointer would necessarily remove.

Pointer import is a separate operation in the v7.1.1 `usm.cpp`: `urUSMImportExp` checks adapter support and allocation type, imports an otherwise unknown host pointer, and has a paired `urUSMReleaseExp`. It is not shown as an automatic step in `appendUSMMemcpy`. The newer `sycl` head adds explicit `urUSMHostAllocRegisterExp`/unregister: it requires the driver external-memory-mapping extension, page-aligned pointer and size, maps the existing address through `zeMemAllocHost`, and unregisters through `zeMemFree`. Neither source promises that ordinary `new[]` pointers are automatically imported, that import registrations are cached across unrelated allocations, or that `malloc_host` storage is device-local. SYCL permits host pointers for `handler::memcpy`; its returned event represents the queued operation, whose completion still needs to be measured separately.

Intel's own compute-benchmark inventory gives a useful measurement precedent: `AppendMemCopy` measures CPU time inside the Level Zero append call and distinguishes ordinary non-USM, mapped, imported, and USM placements for both source and destination. `UsmCopyImmediateAfterKernels` explicitly warns that its append interval can include waiting for prior kernels; its total interval runs from the first kernel append through synchronization. Its staging-buffer case is materially different: it says the ordinary host pointer is never passed to Level Zero. This supports measuring pointer kind, call CPU, and full completion as separate values; it supplies no Arc B570 performance result.

## Falsifiable next experiment

Replay the recorded residual H2D input and D2H save sizes and call counts with the same queue, device-USM endpoint, copy-offload safety setting, and bytes. Use persistent ordinary `new[]` and `sycl::malloc_host` endpoints; first-use allocation/setup is its own measure, and a warm phase reuses the same addresses. For each direction and size, record the copy-call CPU and wall time, event wait CPU and wall time, end-to-end copy time, bytes, and queue submission mode. Keep the memory alive and unchanged until its event completes; validate copied bytes. Run each environment arm in its own process, without changing environment after runtime initialization. Include an idle-queue case and a matched case with known prior GPU work so append-side queue back-pressure is visible rather than mistaken for pointer setup.

Interpret the result narrowly: if USM lowers call CPU but not complete-copy or model wall time, it changes host submission cost without demonstrating a prefill latency gain. If the gap appears only on first use, registration or first-touch setup is a hypothesis, not proof of an automatic pin cache; compare reused addresses with fresh allocations before naming a cache. If the call gap appears only with prior GPU work, investigate queue-mode draining/back-pressure. If repeated call and completion times match across pointer kinds, this A/B provides no evidence that changing the host allocation improves these transfers. Keep the prior 600/1000 tok/s prefill milestone separate; the old clean 349.3 vs 339.2 tok/s cohort is not this diagnostic.
