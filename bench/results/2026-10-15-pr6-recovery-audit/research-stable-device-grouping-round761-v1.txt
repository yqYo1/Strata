# R761 — bounded stable device grouping for compact prefill MoE

2026-10-16 JST. Bounded, read-only source and public-documentation research. This report is the only file written. No build, test, GPU/runtime/profiler/process/environment/service/Git operation or cleanup was performed. No XeStrata material or implementation was read or used.

## Finding and novelty

For the single-GPU, compact-FP16, MMQ=0 route, stable grouping can be specified as five ordinary kernels: segment histogram, per-expert scans within bounded segment blocks, scan of block totals, expert-prefix scan, and stable scatter. Every global dependency is a kernel boundary on the existing in-order queue; work-group barriers stay local. There is no device-wide spin barrier, look-back protocol, or assumption that unscheduled work-groups make forward progress.

R754/R759 already suggested hierarchical count/scan/scatter in general; R760 corrected the mapped-memory and timing interpretation. The added result here is a concrete 64-route/128-segment-block decomposition for T=8192, its exact scratch/operation budget, stable-rank rule, and validation and lifetime constraints. It is a proposal, not an implementation or performance claim. The prefix operation is a standard parallel primitive (Blelloch, CMU-CS-90-190); no external implementation is adapted.

## Algorithm and ordering invariant

For one chunk, flatten the router's token-major, top-10 ID array exactly as the current CPU loop does: `i=t*K+k`, with `K=10`, `E=512`, `N=T*K=81,920`. Let `e=ids[i]`. The current CPU algorithm scans `i` in increasing order, so rows for each expert are ordered by token then top-k position. It assigns `slot[i]` to that expert-major row and writes `src[slot[i]]=i/K`. `gather_rows16` consumes `src` at `off[e]`, while `moe_combine` uses `slot[i]` to recover each routed output row. Reproducing both maps bit-for-bit preserves this routing-to-expert mapping.

Use 64 consecutive IDs per segment: `S=ceil(N/64)=1280` segments. Group 128 segments per scan block: `G=ceil(S/128)=10` blocks.

1. **Histogram:** one work-group per segment cooperatively loads up to 64 IDs, validates `0<=e<E`, zeros a 512-bin local histogram, increments it for valid IDs, and writes `H[segment,e]`. A 512×int32 local histogram is 2 KiB. Invalid IDs do not index the histogram; the group writes `bad[segment]=1` (otherwise zero).
2. **Segment-prefix pass:** for each expert and each of the 10 blocks, exclusive-scan its 128 segment counts. Replace `H[s,e]` with the count of expert `e` in earlier segments of that block, and write that block's total.
3. **Block-prefix pass:** for each expert, exclusive-scan its 10 block totals, replacing them with block offsets; write total `C[e]`. Flag `C[e]>T`, preserving compact-FP16's per-expert row bound.
4. **Expert-prefix pass:** exclusive-scan `C[0..511]` in expert order into `F[0..512]`, with `F[512]=N`. This pass also checks `sum(C)==N`, `C[e]<=T`, and whether any `bad[segment]` is set, then writes a status word. The host checks status before any expert GEMM.
5. **Scatter:** for each valid route `i`, compute its stable local rank `r` by counting equal IDs earlier in its 64-ID segment. Then `p=F[e]+block_offset[block,e]+H[segment,e]+r`; write `slot[i]=p` and `src[p]=i/10`. A pairwise rank within 64 has at most 64 comparisons per route (5,242,880 upper bound for this chunk; about half that when only preceding positions are compared). It is deterministic even when histogram atomics update in any order.

The scan uses only work-group scans and barriers. The SYCL reference defines group-barrier ordering and in-order queue dependencies; separate kernel passes therefore provide global phase boundaries without a global barrier. If these passes move to different queues, explicit event dependencies are required. [Khronos SYCL barriers](https://github.khronos.org/SYCL_Reference/iface/barriers-and-fences.html), [SYCL in-order queue property](https://github.khronos.org/SYCL_Reference/iface/queue.html#syclpropertyqueuein_order), [Blelloch, *Prefix Sums and Their Applications*](https://www.cs.cmu.edu/afs/cs.cmu.edu/project/scandal/public/papers/CMU-CS-90-190.html). These sources establish primitive semantics, not B570 performance.

## T=8192 operation and byte budget

- Input IDs are 81,920 int32 values (327,680 B). There are 1,280 segment histograms × 512 experts = 655,360 int32 values.
- New device scratch: `H` 2,621,440 B (2.5 MiB); `bad` (1,280 per-segment flags) 5,120 B; 10×512 block totals/offsets 20,480 B; `C` 2,048 B; `F` (513 offsets) 2,052 B; status 4 B. Total **2,651,144 B (about 2.53 MiB)** per in-flight chunk. This excludes existing `ids`, `slot`, and `src` buffers (327,680 B each) and host-side count/order storage.
- Histogram work: 81,920 local increments, 655,360 local-bin zero stores, and 655,360 global histogram stores. The segment-prefix pass scans 512×10×128 = 655,360 count entries; block scans consume 5,120 entries; the expert-prefix scan consumes 512. Scatter writes 81,920 slots and 81,920 sources.
- Logical global traffic for `H` is 2.5 MiB histogram writes + 5 MiB scan reads/writes + 0.3125 MiB scatter lookups = **7.8125 MiB/full chunk**. Including two ID reads and the two output maps gives about **9.0625 MiB/full chunk**, before small metadata. These are algorithmic bytes, not measured memory-controller traffic. At 78,452 rows, the nine full chunks plus the 4,724-row tail across 48 layers yield about 4.07 GiB of logical device traffic with this layout; actual controller traffic is unmeasured.
- For `T<8192`, use the actual segment/block counts and mask the last segment; retain the 8192-row capacity checks. Size arithmetic must be checked before allocation.

On Arc B570 this design uses modest bounded scratch and standard SYCL local memory, but 2 KiB local-atomic histograms, 64-ID local ranks, work-group limits, compiler lowering, and the five-kernel launch cost are unmeasured. Do not infer speed from nominal device bandwidth or the theoretical byte count.

## What remains on the host; what could disappear

The compact caller still needs `cnt[e]` to pass `ne` to each oneMKL GEMM, `order` to choose each expert's weight pointer, and `off[e]` for the gather/output ranges. A device count/scan therefore still needs a host-visible completion before the existing per-expert GEMM loop. Copying `C` and `F` back costs 4,100 B per chunk (plus status); host can still build ascending nonzero `order`. It removes the need to expose all `T*K` IDs and return host-built maps, but does not remove the host count/order dependency or its synchronization. oneMKL's documented grouped GEMM still takes host group sizes/dimensions and matrix-pointer arrays; it is a separate way to reduce API-call count, not device-driven dispatch. [Intel oneMKL `gemm_batch` group API](https://www.intel.com/content/www/us/en/docs/onemkl/developer-reference-dpcpp/2026-0/gemm-batch.html).

The 78,452-row diagnostic covered 48 layers and 480 boundaries. It recorded 217.1097 s caller CPU / 223.6063 s wall, 167.9548 s CPU inside explicit waits, 4.85694 s source-copy CPU, 6.78437 s GEMM-submit CPU over 239,458 calls, 0.16536 s host-group/map-submit CPU, and 37.3482 s unclassified CPU. Main's correction is essential: the 0.16536 s region excludes the earlier route wait and map-copy completion. The queue wait drains prior queued work, and mapped host USM is not VRAM. Thus the grouping timer is neither full boundary latency nor evidence that the wait is caused by grouping. Do not attribute the 167.9548 s to busy polling or claim GPU grouping removes it. At most, the measured host-group interval bounds CPU work in that exact region; new GPU launches and metadata handling add work, and total latency benefit is unknown.

The route currently exposes 451,883,520 logical bytes across the 480 boundaries (IDs plus slot/src maps). The candidate replaces that host-visible payload with about 1,969,920 B of count/offset/status return data and device-local map writes. This is a logical payload comparison only: mapped-USM physical transfers/coherency were not measured. The CPU wait remains until returned counts/offsets are ready for oneMKL. Removing that wait requires changing the expert execution interface to consume device-side variable counts and weight descriptors, beyond this grouping component.

## Safe component comparison and limits

If Main's route-boundary attribution still justifies a trial, gate a single-GPU compact-FP16 path off by default and compare it against the current CPU reference on identical routed IDs. Measure from completed route production through host count/order availability, map readiness, and the first gather/GEMM consumer; include all kernel submissions, metadata copies, waits, and queue drain overlap. Record each phase separately without adding profiling waits that change ordering. Compare `cnt`, `off`, `order`, every `slot`, and every `src` exactly; test empty experts, tail chunks, invalid IDs, duplicate-heavy routes, and `cnt[e]>T` rejection. Keep existing cancellation/error behavior and async error propagation.

Reuse scratch only after its last queued consumer completes. Keep `H` through scatter; keep `C/F` until host validation/order setup; keep `slot/src` until gather and `moe_combine` have consumed them. One in-flight chunk needs about 2.52 MiB new device scratch; overlap requires one such allocation per in-flight chunk and explicit capacity accounting. Restrict the first comparison to one GPU: multi-GPU `on_peer` scheduling changes expert offsets and needs a separate stable rebasing design. Preserve shared state and require the physical 262,144-context correctness gate before any adoption. No implementation, correctness result, B570 capability query, or performance claim was produced here.
