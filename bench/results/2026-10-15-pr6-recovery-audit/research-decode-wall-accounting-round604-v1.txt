# R604 — decode wall の既存計測値の意味と次のhost timing

2026-10-15 JST。読み取り専用調査。唯一の書き込みはこの報告。コード編集、build/test、GPU/server/profiler実行、Git、cleanupはしていない。先行R590–603、`research-index.json`、`model-device-profile.ja.md`、profile v1/v2、decode ledgerとそのsourceを確認し、重複するCPU候補提案やdecode profiler案は追加しない。対象は既存decode時間の会計と、次の公式`unitrace --host-timing`が答える範囲に限定する。

## 1. `existing_ms` indexのsource mapping

`generate.cpp`のdecode開始時に`DecodeLedgerSources`が17項目をsnapshotする。最初の14項目は`verifier/dispatch/pool/window`累積時計のrequest前後差、最後の3項目は`ExpertPool::phase_ms()`値の差である。ledgerは0値の差を出力しない。`decode_ms`は別途`generate.cpp`でdecode loop開始からmax outputまでを囲み、final `wait_commit`より前に止める。

| index | source / 出力名 | 開始・終了の意味 | 解釈上の重なり |
|---:|---|---|---|
| 0 | `ver.ms_wait` | `Verifier::run`で各layer graph segmentをlaunchし、`cudaEventSynchronize(layer_done_)`完了までに積算したhost wall | GPU event completionまでのhost wait。GPU実行時間そのものではなく、queue/runtime/driver/event waitを含む。`dt_run`の内側。 |
| 1 | `ver.ms_pool` | layer event後のCPU `pool(...)` callback滞在wall | verifier内のcallback範囲。CPU workerの並列CPU serviceとは別時計。`dt_run`の内側。 |
| 2 | `ver.ms_host` | stage/plan/host-visible results・flags等のVerifier host work。`Verifier::run`中、pool呼出し前のhost区間を含む | `dt_run`内。項目0、poolと並べて差し引ける排他時間とは限らない。 |
| 3 | `ver.ms_commit` | `Verifier::commit`内部のcommit操作wall | `dt_commit`内に入れ子。 |
| 4 | `drive.d.ms_plan` | expert-source layer callback内のplan/route準備 `c0..c1` | `dt_run`とpool callback側の広い時計に内包。 |
| 5 | `drive.d.ms_actq` | activation quant staging `c1..c2` | 同上。 |
| 6 | `drive.d.ms_jobs` | job assembly/lookup等 `c2..c3` | 同上。 |
| 7 | `drive.d.ms_run` | expert source callbackの残り `c3..c4`。内部でCPU pool、copy/peer完了等を含み得る | `dt_run`/`ver.ms_pool`に内包される広いcallback周辺値。kernel serviceではない。 |
| 8 | `pool.ms_multi_gu` | poolのGU段の`run_phase` wall | index 15 drain/CPU serviceを含むGU worker実行時間と重なり得る。 |
| 9 | `pool.ms_multi_q` | activation quantのpool側wall | index 15やCPU quant serviceと重なり得る。 |
| 10 | `pool.ms_multi_down` | poolのDown段の`run_phase` wall | index 15 drain/CPU serviceを含むDown worker実行時間と重なり得る。 |
| 11 | `dt_run` | `generate.cpp`の各windowで`ver.run()`呼出し全体 `tw0..tw1` | index 0–10の複数scopeを包含するVerifier window wallの累積。内訳和ではない。 |
| 12 | `dt_commit` | `tw1..tw2`: `ver.commit`, token emission/stdout flush等 | index 3を包含。draft開始前までの外側window区間。 |
| 13 | `dt_draft` | `tw2..tw3`: 次draft準備と`mtp.draft()`等 | decode loop内のdraft側wall。独立したGPU kernel serviceではない。 |
| 14 | pool `wait_park` | `ExpertPool::run_phase`: startから全workerがparkedとなるまでの積算wall | 0差ならreceiptには出ない。各phaseに属する同期区間。 |
| 15 | pool `drain` | `run_phase`: tasksを発行して`done_`完了するまでの積算wall | worker処理中にhostが待つ壁時計。service CPU時間を含む/重なる。CPU serviceを引いてidleにできない。 |
| 16 | pool `repark` | `run_phase`: work完了後、workerが再parkするまでの積算wall | 0差ならreceiptには出ない。同期区間。 |

Rationale: `generate.cpp:5986–6004,6058–6110,6127–6135`; `verify.cpp:1245–1275,1340–1388,1645–1670`; `expert_source.cpp:2286–2304`; `pool.hpp:179–185`; `pool.cpp:640–705,735–765`; `decode_route_ledger.hpp:31–33,404–416`; `expert_source.cpp:75–84`。`pool.ms_multi_*`はworkerのCPU serviceではなく経過wall、joined `service ... cpu_ns`はissuer/worker thread CPUの合計で並列実行される。caller `final_wait_ns`は`decode_ms`停止後の`wait_commit()`を別計測し、end-to-end decode_msへ足し込まれていない。

## 2. actual 128-token仕事から確実に言えること

Structured actual receipt `decode-ledger-fp32-fixed-normal-v1.json` の最初の34603-input/128-output requestはnormal completion、55 windows、R=217 verifier rows、D=162 proposals、A=76 accepted、C=131 committed、E=128 emitted、68,781 CPU expert jobs/101,036 CPU rows/104,160 routesで完了した。CPU worker/issuer serviceはtotal 36.734 CPU-thread seconds (GU 25.533, Down 11.102, quant 0.099)。この値は同一requestの`decode_ms=25.544s`に対しても加算/差引きできず、CPU秒の方がwallより大きいことは複数slotで並行serviceを積算した結果と整合する。

同じworkと128 generated IDsに結びつくprofile v2 actual receiptも55/217/162/76/131/128を記録し、同じ34603-token promptで完了。`model-device-profile-v2.json`のprofiler付き`decode_ms=37.678s`とledger service sum 34.689 CPU-thread seconds (Mainのprofile summary表現ではおよそ35.6 thread-s)は、同じ仕事に対する異なる時計であり、差を「idle」やGPU待ちとは呼べない。Profile v2ではprefill attention 108 callsのdevice durationが44.066から29.805秒へ減ったが、このdevice-duration和はprefill phase serviceでありdecode wallに含めたりdecode speed gainに使ったりしない。

長いactual ledgerで目立つ既存時計は、first request: index0 boundary wait 7.713s、index1 pool callback 8.750s、index7 source callback 8.363s、index8 GU 5.568s、index10 Down 2.605s、index11 whole verifier run 22.346s、index13 draft 3.183s、decode loop 25.544s。index15 pool `drain` 8.362sはindex8–10のjob-stage wallが走る期間と重なり、index1/7/11ともscope上は重複する。これらを足してdecode時間にしたり、CPU serviceまたはkernel durationを引いて残差をidleと呼ぶことはできない。二回目のactual 128出力はindex0=6.886s、index1=7.500s、index11=15.316s、decode=16.996sだったが、出力列は42番目から異なり、W/R/D/Aも50/197/147/81でfirstと別仕事である。差をwarmup効果や性能改善と決めない。

Profile v2側の対応時計はindex0=9.409s、1=16.122s、2=0.870s、7=14.848s、8=10.164s、10=4.463s、11=33.904s、13=3.751s、decode=37.678s。プロファイル中のオーバーヘッド/時計差を測ったclean対照はない。従ってこの増分を原因に結びつけない。確かな結論は、(a) requestに大きなverifier event-completion waitとCPU pool callback wallがあり、(b)両者は`dt_run`内で時間的に並ぶが独立のexclusive区間とは未確定、(c)CPU serviceは大きい並列資源量だがwall-critical-pathではない、(d)同workのdevice profileはdecode区間専用kernel timelineを提供していない、まで。

## 3. 次の最小測定案と限界

最小案はMainが進行中の所有済みGPU測定を閉じた後、同一current binary/normal MTP4 actual 128-token requestを一度だけ公式unitrace `--host-timing`付きで実行し、receiptに該当引数、同一work identity、通常終了/fault、個別API summaryを保存すること。これはhostから見たLevel Zero/OpenCL API呼出し時間のAPI別summaryを出し、queue submit/execute、event wait/synchronize等のhost APIに大きな累積時間があるかを検証できる。測定されたhost API実行区間がdecode側の既存timerで疑われるsubmission/completion経路に整合するか、という仮説の優先順位付けに使う。

ただし`--host-timing`単独のprocess aggregateではstartup/prefill/decodeを別request phaseに分けず、特定のVerifier windowや`existing_ms index`へ結び付けない。API呼出しwallはその呼出しのhost実行時間で、対応するdevice kernel duration/queueのGPU idle/CPU workerのcritical pathを示さない。非同期submit APIに短い時間があっても、後続event wait/device executionが短いとは限らない。Device timelineとのhost/device timestampの安全な共通clock join、queue gapのGPU idle判定、CPU scheduling/off-CPU原因、各source timerの排他的wall partitionも検証できない。従って値が大きければhost API/service経路を次に掘る材料、値が小さければAPI host overhead仮説を弱める材料になるが、どちらの結果もdecode wallの内訳/idle秒を確定しない。

R588が記録した一回のnormal verifier window内でhost API callと対応GPU activityを別々に選別する手順は、unitrace `--host-timing` aggregateだけでは満たせない。そこでhost timingを最初の小さいスクリーニングとし、必要ならMainが別途、選択window付きのbounded Chrome/ITT+kernel traceを計画する。新たな実験はこの調査では実行していない。
