## Finding

The v2 proposal applies byte-for-byte to the current five existing source files: all five `base_sha256` values in `decode-host-phase-observer-v2/source-hashes.json` match `sha256sum` of current `decode_service_budget.hpp`, `verify.hpp`, `expert_source.cpp`, `verify.cpp`, and `generate.cpp`. Their exact hashes are, in that order: `2d5cf6626d8e64829fa459a7ff6904f611bd4f98a7bcde598551ab34de88178e`, `1f8f43ed9f7278ce260a2681b70f3dbfa18b07ff87a90ddb520a60406fb92787`, `2b252e49025178349f327eb54205e1a19b2deb0724945a8deb6a8ec72bf04ae5`, `640e0270be833ddff0218331a7db18043605af3ced2682787f6b06abdcf6316c`, `d4048082aae24f4afc6c841309b0d0f63f2303085880d92da1cc7ebe4e83e80c`. The new observer header is the sole added file. This establishes patch-base compatibility only; the proposal is still unapplied, uncompiled, untested, and unqualified against b1 binary/runtime behavior.

Source shape matches the narrowly declared target: Linux SYCL, ordinary single-GPU full-layer verifier, native single-stage MTP4 decode with joined ledger/service observer. The owner is request-local in `DecodeServiceBudgetScope`; its pointer is borrowed by the verifier only in the ordinary issuer path, and no worker or host-task callback receives it. In `verify.cpp` the host window is stack-scoped around `Verifier::run`, while the pool callback is measured by the issuer around synchronous `pool(...)` and launch bookkeeping. The CPU pool's own joined-service CPU ns remain a different, overlapping sum; the observer does not read/write from pool workers. Normal close explicitly calls `host_phase_borrow.detach()` before `decode_service.finish()` (`generate.cpp` proposal lines 6286–87), satisfying the observer's `attached == false` completion check. On early return, reverse destruction order destroys the borrow before the service owner (the borrow is declared after the service scope at `:6006–11`); the owner survives until close. This is a sound source-level lifetime pattern.

The measured leaves form an exclusive **host issuer timeline** by changing phase at one shared steady-clock boundary. `RunTotal` is their parent and must never be added to its leaf totals. `LayerEventWait` is host time waiting for a graph completion event: it can contain GPU execution and driver/runtime waiting, so it is not GPU event duration or idle. `PoolCallback` covers the issuer's synchronous callback plus plan publication and shared/hit graph submission; CPU worker service may overlap this interval and GPU graph work may overlap portions of it. Do not add pool CPU thread-seconds, GPU device duration, `ms_wait`, `ms_pool`, or `RunTotal` to these leaves or subtract them to infer idle. Copy stream sync and next-graph submission are separate leaves after the callback. `FinalReadout` is inside the verifier call. The observer does not measure verifier commit/emit, MTP draft, final request `wait_commit`, prompt/prefill, or full end-to-end decode; compare `RunTotal` to the joined request's decode wall with that scope difference explicit. Quantile values are base-4 intervals, not exact p50/p95. Its marginals intentionally do not provide per-window cross-products of T/layer/phase.

`DecodeServiceBudgetScope` is freshly constructed per request, with a new observer allocated only when the joined ledger is requested and eligible; its sequence and counters begin at each request boundary. Static environment reads occur before request instrumentation. Set joined and host-phase variables in the child environment before `exec`, keep that environment immutable, and compare OFF/ON only in fresh owned processes. Every request must have a complete joined route/service receipt and a host close receipt whose request sequence, attempted/verified windows, output bounds and conservation checks agree. Early/error exits should yield incomplete diagnostics, not successful phase data. OFF must have no observer allocation, clock reads or phase output. The observer's `Other` residual, capture, staging, waits, callbacks and sync leaves are only eligible if the ordinary verifier envelope holds; unsupported T/multistage/peer/remote/multi-GPU cases should be rejected, not blended.

## Meaning of the supplied workload contrast

The supplied OFF long-generation rates (regular-code 9.8/9.7/9.8 tok/s versus varied-prose 6.2/6.4/4.6 tok/s) show an observed workload/run difference only. Their prompts, generated token counts, draft acceptance, and per-window T distributions can differ; the prior suite says acceptance alone does not explain speed. The current host observer could locate issuer-side wall categories for a matched individual request, but cannot make those outputs equivalent or prove why these rates differ. Matched input/body IDs and full per-request work identity (prompt/output token IDs, W/R/D/A/C/E, T histogram, model/context/settings) remain essential. Do not inspect or compare the active ON run here.

## Smallest next Main step and remaining gate

Keep the running matched-IQ ON job untouched through its owner/receipt close. At the next permitted measurement boundary, first have Main apply the already reviewed v2 patch only after its source pins are rechecked, run the proposed CPU contract and ASan/UBSan borrow fixtures, then perform the configured SYCL build. The smallest meaningful GPU smoke after those gates is **one fresh owned ordinary-G1 MTP4 request with a bounded normal 128-output decode**, host observer ON and the joined route/service observers ON in the same immutable child environment. Verify observer OFF and ON are in separate fresh processes with observer env set at exec; compare identical request body/work identity, one joined receipt plus one host receipt, complete=true, route/ledger conservation, normal process closure and fresh faults=0. This establishes that the proposed observer is actually wired into the present b1 build and has correct lifetime/receipt behavior. It does not measure the long-generation speed split or qualify performance. If smoke is complete, the next diagnostic would be the same already-eligible code and prose requests with actual input hashes and clean client timing in separate uninstrumented processes; observer-enabled timing must remain diagnostic and excluded from clean tok/s.

There is no source-pin blocker: current hashes exactly equal the proposed base. The remaining blocker is that the feature exists only under `decode-host-phase-observer-v2/files/`, not in current `src/`/`include/`, so no current b1 native can emit its phase receipt. Main must qualify the patch/build before any ON measurement can use this observer; the observed OFF/ON clean rates alone cannot substitute. The existing observer itself also cannot provide a decode-host/GPU-idle partition: it records host wall around async waits/callback scopes and lacks a device timestamp join by design. Use it for where issuer time is spent, not for idle attribution.
