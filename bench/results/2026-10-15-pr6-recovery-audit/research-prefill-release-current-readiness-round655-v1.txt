# R655 — current-root readiness for prefill GPU residual headroom

Date: 2026-10-15 JST. Read-only source and public-A-artifact review. No test/build/GPU/`py_compile`/runtime process/Git/cleanup was run. No private B tree, active ON logs or environment were read. Only this report was written.

## Decision and smallest useful next candidate

The smallest relevant mechanism is already in the current root: the opt-in MTP expert release around long batched Prefill. No source application is needed for that mechanism. It releases one exact 707,788,800-byte MTP expert allocation after draining its graph stream and destroying normal/coupled expert graphs; Prefill then queries live free VRAM and uses the remainder for the FP32 residual prefix. It restores MTP before returning to decode. The actual free delta and 262,144-context FP32 rows remain runtime questions, not source facts.

At the next GPU-free boundary, the minimal candidate is one controlled fixed-workload comparison using this existing MTP release path, fixed static cache/configuration, and FP32 residual storage (unset or exact `STRATA_PREFILL_LAYER_MAJOR_R_DTYPE=fp32`). Capture the four existing free-memory phase markers and `layer-major`'s actual `residual_gpu_rows/gpu/host` plan. Keep the MTP feature and all other settings constant in each arm except its existing opt-in switch. Do not use FP16. If this does not create a useful FP32 prefix, do not apply the stale decode-cache transaction until it is rebased and reviewed.

## Source reconciliation

- Current root already has `run_prompt_with_mtp_experts` in both serve and standalone long-prompt call paths (`src/program/generate.cpp:119-173,5926-5930,6496-6502`). The integration source snapshot in `mtp-expert-prefill-release-v2` matches current root: `src/core/mtp.cpp` is SHA `2a9d44b9…8a05669`; `src/program/generate.cpp` is `d4048082…e83e80c`; MTP header is `c0201a81…1aeaad62`. The index marks this mechanism integrated, with earlier bounded cases but no full-context, general quality or performance qualification (`research-index.json:933-938`).
- The wrapper activates only for exact `STRATA_PREFILL_RELEASE_MTP_EXPERTS=1`, long input `n > prompt.chunk()`, exact layer-major mode, SYCL, and its supported single-GPU native MTP4/no split-peer-remote guard (`generate.cpp:122-136,5926-5930`). It records free/total bytes before detach, after detach, before restore and after restore (`:137-162`). FP32 is the default layer-major residual storage; the planner rejects unrecognized values and FP16 is an explicit separate mode (`include/strata/prefill/layer_major_plan.hpp:48-55`).
- `MtpDrafter::detach_prefill_experts` checks device/config/state, synchronizes `cs_`, destroys every normal and coupled round/step graph before freeing `experts_`, then nulls the pointer and decrements its requested-byte accounting (`src/core/mtp.cpp:438-470`). The target/draft KV and dense storage remain live; the borrowed Verifier `window_R_` is intentionally retained. Restore first drains Prefill, reuploads from the retained immutable host source in bounded views with checked stream completion, and publishes `experts_` only after successful completion (`:473-493`). The scope fail-stops if not successfully closed (`:496-509`). The wrapper restores on normal, false/cancelled return and C++ exception before decode can resume (`generate.cpp:151-171`). This path does not release the ExpertCache or Verifier graph owners.
- The released MTP device allocation is a real native `cudaMalloc` owner of 707,788,800 requested bytes (512 native blobs); successful `cudaFree` is required before its owner/accounting is cleared (`mtp.cpp:338-347,392-419,463-467`). That byte count is not a promise of an equal `cudaMemGetInfo` delta; the wrapper's phase queries are the evidence for any actual available-memory change.
- The live Prefill planner runs inside `Prefill::run_layer_major`, after the wrapper has detached MTP experts. It calls `cudaMemGetInfo`, subtracts the extra one-layer cache and fixed 512-MiB headroom, makes the residual plan, and separately allocates `plan.gpu_bytes` with `cudaMalloc` (`src/prefill/layer_major.inc:127-150,255-285`). Therefore the MTP release can affect the FP32 GPU-row plan. The planner still retains the full-context residual tail in host storage as needed; it does not imply a full GPU-resident 262,144-row residual.

## Readiness blockers in the other existing proposals

- `decode-cache-prefill-release-v1` is the direct additional way to free the resident decode ExpertCache while long Prefill runs, but its current-root base pins are stale in four sources: `include/strata/core/expert_source.hpp` (`c95de4…` pinned vs `38bbbad2…` current), `src/core/expert_source.cpp` (`ed0c10…` vs `2b252e…`), `src/prefill/prefill.cpp` (`cc2120…` vs `aca7a3…`), and `src/prefill/layer_major.inc` (`5b0bf9…` vs `1a79f1…`). The other base pins match. A wholesale application is therefore not authorized by its base hashes; its layer-major copy would also replace newer current arithmetic/lifecycle changes. The proposal restores exactly the saved original slots, offsets, arena bytes and profile map; it does not enlarge decode cache. Its graph teardown/recapture, host/device map transition and same-cache restore make it materially larger than using the already-integrated MTP release. It remains an unapplied, unbuilt source candidate.
- `checked-prefill-retire-v1` addresses Prefill-owned scratch after prompt completion, not an unused decode allocation during Prefill. Its `src/prefill/prefill.cpp` base pin is `a01c39…`, while current root is `aca7a3…`. More fundamentally, `layer_major.inc` obtains the FP32 device residual allocation during the Prefill call; retiring Prefill scratch afterward cannot increase the free memory seen by that already-completed residual plan. Its 1,662,831,872-byte `Impl::owned` figure is historical source/accounting, not a measured driver-free delta or guaranteed reclaimable amount (`research-prefill-scratch-retire-round599-v1.txt`; `research-prefill-retire-cache-readiness-round626-v1.txt`).
- The MTP release candidate’s initial source snapshot has already been integrated into current root; it is not a patch awaiting application. Existing bounded integration results do not establish that the current run received a larger FP32 prefix or that full physical context, RESTORE, answer quality or speed passed. Keep the present FP32 default and preserve the prior FP16 automatic-row numerical failure status.

The single unresolved gate for the smallest candidate is an actual fixed-workload free-memory/residual-row comparison under the current root, followed by full physical-context and RESTORE correctness. If the MTP-only FP32 plan remains insufficient, the decode-cache proposal requires a careful rebase before any build/test; no code change is made by this review.
