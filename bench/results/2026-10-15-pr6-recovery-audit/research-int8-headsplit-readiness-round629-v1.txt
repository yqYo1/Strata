## Actual call and dispatch contract

The configured SYCL source is `src/kernels/sycl/prompt_attention.cpp`, called
from `src/prefill/prefill.cpp` after QSA selection. `qsa_prompt_attn_batch`
selects Mode 1 only for INT8 K and INT8 V (`p.k_q` and `p.v_q`, with no Q4
pointer taking precedence); K8/V4 Mode 3 and Q4 Mode 2 are separate routes.
The head-split candidate is nested only in `dispatch<1>`, only behind exact
`STRATA_SYCL_PROMPT_DIRECT=1` (the dispatch also checks `direct[1]=='\0'`) and
exact `STRATA_SYCL_PROMPT_HEAD_SPLIT` values `32` or `64`. Other values leave
the current Direct path in place; Direct off and other KV modes do not select
this candidate. The values must be fixed in each native process at exec. The
candidate does not change public entrypoint arguments or selection, append,
copy, or fallback code.

`steps[batch*kStepCount+kStepWidth]` is the actual per-query active selection
count consumed by the attention loop. The public real geometry has
`idx_top_k=2048`, `idx_block=4`; `qsa_selection_width(n_kv,s)` is
`min(n_kv, idx_top_k+idx_block-1)`, so it tops out at **2051**, not 262144.
Prefill sizes the attention ID capacity from
`qsa_selection_width(kTopkMaxCells,s)`, likewise 2051. `max_cells=262144` is
the logical KV context/page-table range, not this kernel's active selection
count. At 262144 context the physical pool can contain many pages, while each
QSA attention call still consumes at most 2051 selected IDs. The 44.066-second
profile is consistent with 12 QSA layers times nine 4096-token prefill chunks,
but does not expose each call's widths or residency.

This distinction fixes the earlier fixture gap. Its `cap=262144`, logical ID
262143, active width 65 reaches a high page-table index but does not reach the
last CH32 or CH64 loop tile. A *production-reachable maximum-count* fixture is
`nq=1, cap=2051, step_width=2051`, with logical cell 262143 in the final ID
slot (index 2050). For `page_size=4`, this uses logical page 65535, offset 3.
Map only `page_table[65535]=2` into a five-physical-page toy pool; all other IDs
can be negative. With two KV heads the backing row count is
`5*2*4=40`; the terminal cell resolves to physical rows 19 and 23 for KV
heads 0 and 1. INT8 K/V arrays each need 40*256 codes; their FP16 scale arrays
each need 40*4 entries. Q remains `[1,24,256]`; `steps` has four int32s; IDs
has `cap` int32s. This tests high logical indexing, exact max active count,
nonidentity page mapping, and the final partial chunk while keeping physical
allocation small. It does **not** test 256K physical residency or consumption.
A synthetic ID list also does not prove the production selector emits that ID;
record the test as kernel addressing/capacity coverage only.

For CH32, a 2051 count runs chunks starting at c0=0..2048 (65 iterations); for
CH64 it starts at c0=0..2048 (33 iterations). Both last chunks contain only
three selected positions. The new maximum-count fixture therefore addresses
the real reachable loop tail. By contrast, a synthetic `step_width=262144`
would traverse 8192 chunks for CH32 or 4096 for CH64 and would be outside the
real selector contract. Negative IDs still run the full matrix/softmax loop;
they mask loads and contribute zero but do not make this a cheap large-count
test. Such a case is unnecessary for production-reachable coverage and should
be separately named, budgeted, and reported as an artificial API-bound stress
test if ever desired. It must not be called an actual prompt shape or full
physical-context test.

## Data movement and numerical contract

Mode-1 KV layout is codes `[page][kv_head][page_size][256]` and FP16 scales
`[page][kv_head][page_size][4]`, one scale per 64 values. The current attention
kernel reads selected IDs, resolves logical page through the page table, then
loads codes and four scales per cell directly into local tiles. It does not
call the selected-row gather or copy K/V into an intermediate global FP16
buffer. K code conversion to FP16 is exact; FP32 scales are applied to each
QK scale-group partial. V code conversion and four per-cell scales are folded
into the probability side before hi/lo FP16 staging. Q and probability retain
hi/lo terms; matrix accumulation and online softmax state are FP32. No single-
half or Q4 interpretation belongs in this Mode-1 experiment.

The prefill caller still appends the chunk's K/V first, potentially through
the established host/device staging path, builds selection IDs and `steps`,
then calls the attention kernel. The head-split candidate reuses those exact
pointers, `cap`, `QsaShapes`, stream, page mapping, pool contents, and output
stride. It is not a replacement for KV append, indexer, top-k, or streaming.
The external output remains `[batch][24 heads][256]`; tile 0 writes heads 0..7,
tile 1 writes heads 8..11, with the same `kvhead*12` stride. Do not use local
8-row extent as external head stride. There are two KV heads per query. Current
Mode-1 uses `KG=VG=4` scale groups.

CH32 keeps the 32-cell softmax update order, K dimension and scale-group order,
hi MAD then lo MAD, score scaling, V-factor computation, P hi/lo split, PV
MAD/rescale order, FP32 accumulation, and final denominator. Its two head
workgroups each recompute the same max over all 12 heads to preserve the shared
Q scale. This duplicates that max scan and repeats selected row mapping and
K/V loads per KV head across the two head tiles; it trades traffic and workgroup
count for independent scheduling. CH32 all-output bitwise equality to current
Direct is a source-based expectation and the required comparator gate, not an
executed fact. CH64 changes the online-softmax/PV chunk boundaries and is not
bitwise-equivalent by contract; retain its fixed `1e-5*(1+abs(reference))`
tolerance against both baseline and independent FP64 oracle. Never relax a
failed numerical result to make it pass.

## Device and resource facts

The active model profile proves the old Mode-1 matrix route passed its existing
admission: subgroup size 16 is reported, max workgroup is at least 128, the
FP16/FP16 to FP32 matrix combination covers 8x16x16, and the reported local
memory passed the current threshold of 60,880 B. This is an inference from the
source's admission guard plus the recorded actual kernel name; the receipt does
not give exact queried values. It does not certify head-split launch resources.

Candidate source uses a 64-work-item workgroup with four 16-wide subgroups and
8x16x16 matrix tiles. Declared local accessor sums are 31,088 B at CH32 and
53,872 B at CH64. The current host admission remains stricter: local memory
>=60,880 B, workgroup limit >=128, subgroup16 and matrix shape. Keep that gate
unchanged for the first source experiment. Previous profiler reports list
4,096 B static SLM for the current selected kernel. That is not dynamic
local-accessor total, head-split allocation, spill, occupancy, or a device
capacity value. No retained evidence provides exact B570 `local_mem_size`,
subgroup list, matrix-combination record, or compiled candidate resource data.
Before the first candidate launch, Main should record those actual device
properties and inspect candidate kernel-name, dynamic SLM/register/spill
information where available. The current route makes the probe useful; it is
not proof that the new kernel compiles, launches, or avoids spills.
