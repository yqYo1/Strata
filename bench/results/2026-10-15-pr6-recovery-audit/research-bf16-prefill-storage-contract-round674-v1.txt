# BF16 layer-major residual storage contract (R674)

Read-only implementation contract for a future boundary-storage-only BF16 mode. Source anchors refer to the current SYCL tree. No source/test/fixture/proposal edits, build, test, compiler, GPU, process, private-B/live-log/environment inspection, Git mutation, or cleanup was performed. This report does not claim measured quality, capacity admission, or performance.

## Required runtime semantics

Keep the current algorithm exactly: each non-final layer produces the same FP32 `m.R`, stores each residual scalar once as BF16, then the next layer restores that stored BF16 value exactly to FP32 before running its existing operators. No operators, accumulation types, weights, KV/state, final-layer callbacks, or chunk/layer order change. This is a lossy recurrent boundary cast at each of 47 inter-layer boundaries, distinct from the existing FP32 and FP16 arms.

The active layout is width `D=4*2560=10,240` FP32 scalars per row. BF16 rows are 20,480 bytes, equal in size to FP16 rows. Therefore storage is 640 MiB at 32,768 rows, 1.25 GiB at 65,536 rows, and 5 GiB at the full 262,144-row boundary. At `R_GPU=4096`, the device prefix is 80 MiB and the rest is host storage. With an 8,192-row chunk and a host tail, the one reusable device staging chunk is at most 160 MiB. These are checked-layout arithmetic, not evidence that the GPU or RAM admission succeeds. The 32K/64K cases are intended performance lengths; 262,144 is a separate maximum-context correctness/physical-admission bound. The 600/1000 tokens/s goals are not input lengths and have no measured BF16 result.

`layer_major.inc` must treat BF16 as a 2-byte storage format in the same planner path as FP16: retain checked products/offsets, complete-chunk GPU prefix and exact final partial-chunk handling; reserve staging for every 2-byte host tail; use one serial queue for host H2D -> exact BF16-to-FP32 restore -> unchanged layer operators -> BF16 pack -> host D2H. Device-resident rows pack in place to the device store. Neither arm may double-round, expose a half-sized store to an FP32 memcpy, or route BF16 through FP16 conversion. The last layer remains FP32 and is not packed.

## Conversion contract and backend caveat

Use `strata::kernels::bf16_from_f32` and `f32_from_bf16` from `include/strata/kernels/bf16_bits.hpp` for the boundary conversion. Forward conversion is round-to-nearest, ties-to-even (RNE), with the tie decision using retained bit 16. Restore is exact: BF16 is the upper 16 bits of FP32, so restoration shifts the payload left 16 without additional rounding.

Bit behavior matters. Preserve signed zero and signed infinities. All BF16 subnormals map exactly to FP32 subnormals; FP32 values below the BF16 half-min-subnormal rounding threshold become signed zero. BF16 has FP32's exponent range, but values near the largest finite BF16 may still RNE-round to infinity. NaNs must remain NaNs, preserve sign and retained payload bits, and set the BF16 quiet bit. The shared helper implements that explicitly and is exhaustively checked by `src/kernels/bf16_bits_test.cpp` against ggml's rule for all 2^32 FP32 bit patterns, including all NaNs; all 65,536 BF16 patterns are also round-tripped.

Do not assume the existing `strata::prefill::to_bf16` is an equivalent residual primitive. The active SYCL `src/prefill/sycl/postops.cpp:22-27,138-145` has a local `bf` that performs the ordinary RNE add/truncate, while its optional hi/lo image path is designed for activation decomposition. Its NaN path does not use the shared helper's explicit NaN-preserving rule (some signaling NaNs can round to infinity). The other existing SYCL path `src/kernels/sycl/elementwise.cpp` already calls `bf16_from_f32`, but it is a different API/module. Prefer a narrow residual pack/unpack API that uses the shared helper rather than silently changing unrelated postops behavior. `include/strata/prefill/kernels.hpp` already declares `to_bf16` but has no BF16-to-FP32 restore declaration; the layer-major restore needs a checked implementation on the actual SYCL prefill queue. This work concerns the configured SYCL engine; CUDA/HIP portability is outside this report's scope.
