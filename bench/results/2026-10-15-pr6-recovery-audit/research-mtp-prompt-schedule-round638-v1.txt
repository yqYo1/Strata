Date: 2026-10-15 JST
Status: READ-ONLY SOURCE AUDIT. No code changes, builds, tests, process/GPU actions, Git operations, cleanup, or active benchmark raw artifacts were accessed. Source claims describe the current working tree, not GPU qualification or measured speed.

Question and verdict

The current prompt path already batches MTP K/V work at each prefill chunk boundary: E-9 `Prefill::draft_kv` runs across up to the chunk's residual rows, and fallback `MtpDrafter::prefill` batches rows into its own capture groups. It is not a per-token MTP pass on the supported single-GPU path. I found no safe “defer all MTP prompt work to after prefill” switch that avoids new storage or recomputation. The callback's `R_rows` is the current chunk's reused device residual buffer, and MTP needs K/V for prompt cells before the first verify/draft window can use them. Deferral would require retaining/copying the needed residual rows and token IDs, or rerunning target prompt work. The existing pipeline can be tuned at chunk granularity, but that is a separate measured prefill change with potentially large target-side memory and residency effects; this audit does not recommend it as an MTP-only optimization.

`STRATA_MTP_BATCH=0` disables only E-9 and forces the drafter's own K/V prefill pass. It does not disable MTP prompt work. The header's E-9 comment still says ring K/V is inapplicable, while current implementation explicitly accepts `kv_mode == 2` when `STRATA_MTP_BATCH_RING` is not `0`; treat the code as behavior and update the stale comment in a future code task. Turning MTP off may reduce prompt work, but it also removes speculative decode and is not a production improvement absent an end-to-end comparison.

Call order and timer scope

- `src/prefill/prefill.cpp:3079-3088`: after each target chunk's compute stream has synchronized successfully, the final stage calls `on_chunk(m.R, T, p0, err)`. The layer-split path reports this callback from the last stage, after its own stream sync; earlier stages can already be working on a later chunk. `m.R` is borrowed chunk storage, not a persistent full-prompt residual array.
- Serve (`src/program/generate.cpp:4961-4978`) builds `nxt[t] = cur[p0+t+1]`, then attempts `sp.draft_kv(mtp, R_rows, nxt, T, p0)` and, when not applicable with empty error, calls `mtp.prefill` on the same rows. Only after this work does it publish prompt progress and potentially save a checkpoint. The callback is installed on the final stage for multi-GPU, but the fast E-9 route is guarded by `!multi_gpu`.
- Standalone generation (`generate.cpp:6435-6441`) pairs each `R_rows[i]` with prompt token `o.tokens[p0+i+1]` and follows the same E-9-then-fallback order. Its optional sampled-logit callback is composed before MTP and drains its own work before the MTP callback can reuse scratch.
- Serve's reported `prompt_ms` starts at request timer `r0` and stops only after all prompt segments/checkpoint reads and slot refill (`generate.cpp:5892, 5964`). Therefore it includes target prefill, every per-chunk MTP K/V callback, checkpoint work performed inside callbacks, window reads, and slot refill, in addition to request-side prompt preparation since `r0`. The `PP` progress timer likewise spans MTP work because the callback prints only after it finishes. Standalone `prefill_ms`/`prefill_batched_ms` also include callback time; `PrefillStats::ms_total` is an internal prefill statistic and is not interchangeable with those outer wall timers.
- Only MTP K/V/state for the prompt positions needed by the drafter, plus loaded expert weights and any decode graph state, must be ready before first speculative decode. Prompt MTP uses `record_forward(..., -1, ...)`, a K/V-only path; MoE experts are used by the later full draft/verify routes. It does not need to compute speculative draft tokens for every prompt token during prefill.

Batching, storage, and ordering constraints

`draft_kv` is already a multi-row GPU path (`src/prefill/prefill.cpp:965+`). It calculates `r0=max(0, mtp.first_needed()-cell0)` to skip prompt cells that the draft window cannot reach. It derives per-row scratch demand and takes `B=min(n-r0, region_bytes/per_row rounded down to 64 rows)`. In ring mode it additionally caps each batch to at most `(n_slots-1)*page_size`, rounded down to 64, so cells within one batch do not alias ring slots that may still be read by attention. It returns “not applicable” when scratch gives fewer than 64 rows, required tensors/embedding are unsupported, device differs, hybrid KV is active, ring batching is explicitly disabled, or mode is unsupported; caller then executes fallback. In mode 0, it can batch all eligible rows subject to scratch. `STRATA_MTP_BATCH_F16=1` selects FP16 GEMMs; default may use Q8 MMQ when built/fitting. E-9's FP16 activation path is explicitly not bit-identical to MTP's own Q8_1 activation path and can change draft choices, while target logits/tokens remain independent.

Fallback `MtpDrafter::prefill` (`src/core/mtp.cpp:1004-1133`) also skips rows before `first_needed = prompt_len - window - 64` when a sliding window is active. Default non-HIP E-4 packs token/step/position records for the whole supplied `n` into one host upload, launches groups of at most `max_t_`, then performs a checked final stream sync. HIP defaults to the old per-group sync loop because the source records prior gfx1201/ROCm hangs in E-4. The callback boundary keeps the current residual rows valid until both routes finish. In a layer split, callback placement also preserves the “last stage owns the drafter rows” invariant.

The ring cap is a within-batch read/write alias guard, not a claim that all 256K prompt K/V fits resident. `kv_restore(resume)` restores the ring's last relevant pages from host backing on checkpoint resume (`mtp.cpp:994-1000`; serve call at `generate.cpp:5669`). For repeated prompts, the batch path only writes cells at/after `first_needed`, and resume restoration occurs before new prompt processing. Full attention (`window_ == 0`) has no early-window pruning, so it must preserve all prompt K/V needed by decode; 256K behavior depends on actual selected KV mode, host/resident configuration, chunk and scratch sizes, and has no evidence in this source audit. Avoid extrapolating from 32K runs.

Release-experts route: separate memory optimization, not scheduling

The current `run_prompt_with_mtp_experts` (`generate.cpp:119-173`) is an opt-in wrapper around synchronous `prompt.run`. It requires exact `STRATA_PREFILL_RELEASE_MTP_EXPERTS=1`, exact layer-major mode, a long chunked prompt, SYCL, native supported MTP4, and a single-GPU route without split/peer/remote experts. It detaches after draining the MTP stream and retiring four full decode graph families, executes prompt work (including per-chunk K/V callbacks), drains again, restores expert bytes from the owned source, then returns to decode. The wrapper covers ordinary true/false returns and exceptions; restore/telemetry failure is fail-stop. The MTP prompt graphs are K/V-only, so they are not decode graphs retaining MoE expert pointers. This path reclaims a memory owner during target prefill; it does not reduce or postpone prompt K/V computation. The output's free-byte samples are telemetry, not attribution or proof that the device physically made all bytes available. Short/window reads bypass it. Release behavior has source review but no result here establishing runtime memory return, quality or speed.

What is and is not an optimization candidate

1. Keep the established per-chunk E-9 batching and measure it against fallback only in separate, owned processes with identical MTP enabled, tokens, chunking, KV mode, and output checks. `STRATA_MTP_BATCH=0` is a route comparison, not “MTP off.” It should first reconcile the stale public comment about ring mode with actual current support.
2. A post-target-prefill MTP pass is only a candidate if it owns a bounded residual/token staging region and proves correct cell selection, prompt checkpoint/resume, window pruning, ring aliasing, final-stage ordering, borrowed `R_rows` lifetime, and first-decode readiness. It could lower callback serialization but would add copies/storage and delay TTFT; no source or measurement here shows net benefit.
3. Chunk size changes affect target prefill residency/workspace and callback cadence simultaneously. Do not attribute any speed change solely to MTP without pinning the target path and reporting the complete prompt timer and first speculative decode latency.
4. Do not infer MTP-off benefit from target prefill stats alone. Compare total prompt + generation latency and draft acceptance/output correctness under the same request.
