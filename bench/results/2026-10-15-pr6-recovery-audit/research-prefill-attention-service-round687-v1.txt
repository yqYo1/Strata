# R687 — selected INT8 prefill attention: service bound and a smaller KV tile candidate

Date: 2026-10-15 JST. Read-only source/report research for the configured Strata Arc SYCL path. No implementation, build, test, GPU/device query, service run, profiler run, cleanup, or edits outside this report.

## Evidence pinned to this question

The source profile is the closed `prefill-window-profile-long-v4.json`, summarized in `prefill-window-long-interval-summary-v2.json` and reviewed in `main-prefill-window-profile-review.ja.md`. It was the real 34,603-token request window (34,602 batched rows), C4096, K8V8 with 32,768 resident cells, same queue, native b1 binary. The attention role had 108 calls and 44.051705577 seconds of device service. The window also includes restore and one generated token, and its 140.145-second sum covers all GPU operations; therefore 44.052 seconds is a role total, not a pure-prefill wall interval or clean benchmark.

The two launch geometries for the role are 96 calls of `[SIMD16 {8192;1;1} {128;1;1}]` and 12 of `[SIMD16 {3668;1;1} {128;1;1}]`. At 2 KV heads and one work-group per query/KV-head pair, these are 4,096-query chunks (8 full chunks) and the 1,834-query tail (one chunk), repeated across 12 QSA layers: 9*12=108. The entrypoint name is `launch<1,false,false>`: SYCL `prompt_attention.cpp` mode 1 means INT8 K and INT8 V, and Direct=false means the local `final` output path. The model's 24 query heads are grouped 12 per KV head; this kernel handles all 12 query heads sharing that KV head inside each work-group.

For real QSA geometry, `kStepCount=4`; `steps[...,kStepWidth]` is the active selected-ID count. It is not `cap`, `topkmaxcells`, or resident KV count. `qsa_selection_width(n_kv)=min(n_kv, idx_top_k+idx_block-1)`, with `idx_top_k=2048`, `idx_block=4`; hence max width is 2,051. Selection width grows causally with `n_kv` until 2,051, then stays there. The 32,768 resident cells are allocation/residency state, not the number of attention cells read. The physical context limit 262,144 is also not the selected width. `page_size=4`; each selected logical cell resolves via ids and page table into `[page][kv_head][page_size][head_dim]`, with dim contiguous. Selection differs per query, so simply reusing a neighboring query's selected rows would change semantics.

For this geometry at width 2,051, current CH32 has 65 tile iterations. Per query and KV head, the useful QK and PV products each perform 12,601,344 MAC; combined useful work is 50,405,376 FLOP. With two KV heads, that is 100,810,752 useful FLOP/query. With INT8 K/V, each query and KV head logically stages 2,051*256 bytes each for K and V, plus 4 FP16 scale values per row for K and 4 for V: 1,050,112 code bytes and 32,816 scale bytes per KV head, or 2,165,856 bytes/query across two KV heads, before ID/page metadata. These are requested source bytes, not measured external-memory traffic: cache reuse may reduce DRAM traffic. The work is high enough for arithmetic to matter, but there are no operation counters, memory-stall counters, compiler spill/resource data, or per-kernel occupancy evidence in the retained trace. The trace records service duration, not achieved bandwidth or matrix utilization. Thus it cannot establish memory-bandwidth, local-memory throughput, occupancy, or arithmetic as the limiting resource.

## Candidate: CH16 mode-1 geometry screen

A new, bounded candidate is to reduce the selected-cell tile from CH32 to CH16 while leaving 128 work-items, subgroup size 16, 12-query-head sharing, score/value mathematics, IDs, page resolution, online-softmax recurrence, output path and external layouts unchanged. One work-group still owns one `(query, KV head)` pair; it processes 16 selected cells per loop step. It would increase the loop from 65 to 129 iterations at width 2,051, but cuts the row-dependent local staging and may release enough local memory to improve residency. It is a mode-1-only experimental arm initially, not a proposed default.

The current source declarations in mode 1 are: qhi/qlo=16,384 B total, kv=16,384 B, phi/plo=8,192 B, scores=2,048 B, ks/vs=2,048 B, state/factors=112 B, final=16,384 B (Direct=false), rows=256 B: 60,880 B total. For CH16, the same declarations become qhi/qlo 16,384; kv 8,192; phi/plo 4,096; scores 1,024; ks/vs 1,024; state/factors 112; final 16,384; rows 128: **51,440 B**, a 9,440-B (15.5%) reduction. (The prior Direct=true path removes `final`, giving 43,248 B.) This is only the explicit accessor sum. It does not establish physical SLM allocation, per-EU residency or launch admission. Tail waste falls from 29 padded cell lanes in the final CH32 tile (2,080 issued slots) to 13 in the final CH16 tile (2,064 slots). Useful FLOPs are unchanged; chunk loop/barrier count nearly doubles. Thus the candidate has a clear occupancy-versus-serialization trade, rather than a promised speedup.

This hypothesis is more diagnostic than repeating the old QSA headtile/layout proposal. R568 (`research-qsa-headtile-slm-round568-v1.txt`) already analyzed CH64 plus two head tiles; it doubled logical K/V staging and was not adopted. Separately, `qsa-layout-screen-summary.json` reports layout1 median +4.0903% versus layout0 on its synthetic `nq=32, cap=2051` fallback microbench; that changed local Q layout in the decode fallback and is unrelated to the selected INT8 joint-matrix prompt kernel. Neither is evidence for or against CH16.

## Smallest useful experiment and decision gate

First gather evidence on the exact production route using existing diagnostics/compiler reports, without changing algorithms: confirm mode 1 and direct=false per call; get compiled local-memory, register/spill and occupancy/resource figures for this exact kernel; if available, collect memory-throughput and matrix-active/stall counters. Do not infer those values from source declarations. If the SLM allocation is the occupancy limiter and the device has useful additional residency headroom, compare only current CH32 against CH16 in an isolated kernel fixture, identical inputs and IDs, widths including 2,051 and causal widths near 16/32 boundaries, same queue and page table. Check output against the same current path with the existing numerical contract, including missing/nonresident IDs and nonidentity page mapping. Measure individual kernel samples and source dispatch count; do not use the unitrace service sum as a clean rate. A result with lower SLM but no added occupancy or slower service rejects CH16. A result with added occupancy but no repeatable latency gain also rejects it.

Only after a component result is useful should an explicit production opt-in be considered, followed by clean long-prefill measurements at the fixed production workload and quality/RESTORE/context gates. The run's selected width does not justify using 32,768 as the kernel's loop extent; it must continue to read the per-query step width and preserve all 262,144 logical-cell/page-table boundary behavior.

## Primary references and interpretation

Intel's GPU optimization workflow recommends measuring occupancy and using SLM to remove redundant global reads; it also directs users to the Intel GPU Occupancy Calculator. Intel's joint-matrix guide describes the subgroup-scoped joint-matrix load/MAD/apply operations used by this kernel. FlashAttention's author paper establishes the value of online softmax and tiling to reduce high-bandwidth-memory/on-chip-memory traffic; this kernel already uses online softmax and local K/V tiles, so that general result does not identify its current bottleneck. These references motivate what to measure and the resource trade being tested; their generic guidance does not predict Arc B570 results.

- Intel, [GPU optimization workflow](https://www.intel.com/content/www/us/en/developer/tools/oneapi/training/gpu-optimization-workflow.html)
- Intel, [Programming Intel XMX using SYCL joint_matrix](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2024-1/joint-matrix.html)
- Dao et al., [FlashAttention: Fast and Memory-Efficient Exact Attention with IO-Awareness](https://arxiv.org/abs/2205.14135)

Disposition: CH16 is a source-derived, unmeasured component candidate. The evidence currently supports neither a bandwidth-bound nor an occupancy-bound label; counters/resource reporting are the missing discriminator. No performance or adoption claim is made.
