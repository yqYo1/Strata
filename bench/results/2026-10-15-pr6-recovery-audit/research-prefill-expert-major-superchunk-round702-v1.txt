# R702 — 64K expert-major superchunkのsource/liveness review

2026-10-15 JST。指定されたread-only調査。production source、build、test、GPU、process、環境、Git、branch、既存artifactは変更していない。新規書込みは本reportのみ。R622の全prefix deferred MoE、R633の2/4 chunk wave、R601のdequant cacheとは候補自体が重なるため、ここではそれらを再提案せず、64K（8192×8）での現在Arc実装依存と正確なowner/byteを追った。性能値は測定していない。

## 結論

「64K分の因果的attention/GDNとrouter準備を順序通り終え、層内FFN/MoEだけをexpert-majorでまとめる」ことに、数式上の禁止はない。層入力残差は前層の確定出力であり、同一層の後続token attentionが同層の先行token FFN出力を読む依存はない。一方、GDN/QSA/PLEのstate更新とKV追加は必ずtoken順で完了させ、各routeはその時点の正しい入力から確定させる。従ってこれはattention/GDNを64K一発kernelにする案ではなく、既存8192以下のoperator chunkを8回順に回した後にMoE barrierを置く案である。

最大の阻害はメモリと演算順である。64K全routeのFP32 expert出力を既存`moe_combine`順で保持するだけで6.25 GiB、FP16 `mixed_h`が320 MiB、shared outputが640 MiBとなる。route配列等込みでretained payloadは少なくとも7,729,315,840 B（約7.2 GiB）。さらにattention後のHC residualを別置きすれば2.5 GiB（FP32）加わる。GPU側の既存workset/weight/cache/KVも同時に必要なので、専用の巨大device buffer案は現在の配置では成立性が低い。host/RAMへ移す案も数GiBの追加転送を生む。

`Dm`を持たず640 MiBのtoken×hidden FP32 accumulatorへ専門家完了順に加算すれば小さくできるが、現在のArc combineはtokenごとにtop-10 slot順で`sycl::fma`してからshared結果を加算する。expert-ID順の累積は加算順が変わりbitwise同値ではない。既存の品質ゲートを通す前提で、これは同じ設計として扱えない。正確なslot順を維持するなら、10 slot分のFP32出力plane、つまり上記6.25 GiBの`Dm`相当を保持するか、slotごとにexpert計算を反復する必要がある。後者はdequant/launch削減を取り戻す可能性がある。

R633が示すbounded waveの上限（8K×4=32K）を超えるだけでなく、64Kはその保持量の約2倍。64Kを必須にせず、まず既存レポートのbounded-wave gateとroute再利用量を評価すべきである。本報告は64K候補の性能優位を主張しない。

## 実sourceの順序と依存

`src/prefill/layer_major.inc`は外側をlayerとし、各layerについて`run_impl(tokens,n,pos0)`を一度呼ぶ。`run_impl`内は現在の`m.T<=8192`ずつchunkを進める。各chunk内ではHC attention halfの後にattention/GDN、次にHC FFN half、router、shared expert、routed experts、combine、HC FFN writeを実行する（`src/prefill/prefill.cpp`のrun_impl chunk loop、HC half、GDN/QSA、MoE、`gr_write`）。従って現在の候補はlayer→chunk→attention+MoEである。

GDN pathは層別`ss.gdn_state`のstate/conv historyを`gdn_recurrence`/convで更新する。QSA pathは各token位置のindexer/select/KVを作り、完了blockと現在tailを区別した後に各queryのattentionを計算する。これらは再帰・因果依存を持つ。8192ずつ昇順に実行し、各小chunkのstate/KV commitを完了させてから次へ進むなら、64K全行のrouting準備はその後の独立した層内計算として構成できる。QSA future-block sentinelや現在tailのmask/公開規則は変えられず、「全64KのKVを先に書いて通常attentionを一度行う」置換は許されない。

PLEはlayer 1で`ss.ple.hist`をtoken順にadvanceする（`ple_block`またはbatch postops）。superchunkで後段へ遅延させず、layer1の8192 subchunkごとに履歴更新を完了させる必要がある。RやKV/stateと違い、PLEも次chunkの正しい入力履歴を要求する。

各chunkのattention後は`gr_write(R, bo, inj)`で4-way HC residualを書き戻す。MoE側は`mixed_h`を使ってexpert inputをgatherし、`Dm`へFP32出力を書く。routerはBF16系のmixed入力からlogits、top10 IDs/weightsを作る。shared expertは同じFFN入力から先に作られ、最終combineで加えられる。したがって各route/weightとshared resultは、superchunkの他行や次層に移る前にそのtokenのexact FFN inputに結びつけて保持する。

FFN MoEを全subchunkで後回しにしても、同一layerのGDN/QSA演算はMoE結果を参照しないためstate因果は保てる。ただし次のlayerに入るためのlayer boundary residualは全行のfinal FFN write後まで未完成であり、layer-major wrapperの`on_chunk`/RESTORE/checkpoint callbackを途中で公開してはならない。現在wrapperがlayer全体の完了後に次層へ進み、最終層の完了時だけstage callbackを通す契約を維持する必要がある。cancel/errorならstate/KVが進んだ一方でresidualは未commitの可能性があるため、そのrequestを通常decode/RESTORE可能な完成境界として扱えない。owner/drain/失敗処理は別実装gateである。

## 64Kのpayloadと現在scratchとの関係

寸法は`N=2560`, `K=10`, `HC=4`, `T=65536`。下記は十進byteを2^30でGiB換算。route配列は現実装のids, slot, src各int32とweights float32の4 arraysを上限として数える。

| 保存対象 | 算式 | 64K byte | 用途/制約 |
| --- | ---: | ---: | --- |
| FFN入力`mixed_h` | T×N×2 | 335,544,320 (0.3125 GiB) | per-expert gatherは別の小bufferで反復可能。既存`m.Xs`はこの保持ではなくchunk内gather scratch |
| FP32 expert results `Dm` | T×K×N×4 | 6,710,886,400 (6.25 GiB) | unchanged top-k slot-order combineに必要な行result plane |
| shared result | T×N×4 | 671,088,640 (0.625 GiB) | combine時まで保持 |
| HC injection + scalar gate | T×(HC+1)×4 | 1,310,720 | FFN postprocess時に必要 |
| routes/weights/maps | T×K×(3×4+4) | 10,485,760 | route slotと元tokenの対応を保つ |
| 上記合計 |  | **7,729,315,840 B (約7.2 GiB)** | alignment/counts等は未算入 |

per-token内訳は`Dm` 102,400 + `mixed_h` 5,120 + shared 10,240 + injection/gate 20 + route arrays 160 = 117,940 B。117,940×65,536 = 7,729,315,840 B。compact route metadataで減る量はこの支配項に対して小さい。

現sourceではこれらはすべて現在chunk用owner。`m.Dm=T*K*N*4`だけで8192時に838,860,800 B（0.78125 GiB）。これに`m.Xs` compact FP16 input 41,943,040 B、`m.shared` 83,886,080 B、scalar shared gate、routes等が重なり、他のGDN/QSA/attention scratchと三者最大のregionを共有する。記録済みC8192 shared regionは1,180,698,624 Bで、これはGDN/QSA/MoE領域を順次再利用した現行chunk向け値である。8倍capacityに伸ばして7GiB級保持配列の場所に使える空き領域ではない。`m.Dm`を含むscratchは他operator bufferとpeak liveを精査せず単純に新規追加/region aliasしてはならない。

### R_after_attentionとlayer residual owner

各tokenのHC residual `R`は`D=4×2560=10240` FP32である。attention halfを書いた後の全superchunk `R_after_attention`を独立に保つならT×D×4 = **2,684,354,560 B = 2.5 GiB**。後段FFN halfのnorm/mix、`gr_write`に必要であり、FP16にすると既存FP32 referenceと同じとは言えない。これを保存せず再生成するならattention/GDN/QSA/H C計算を再実行する必要があり、因果state/KV更新を二重適用しない別state replayが要る。

既存layer-major `rows/device_rows`は前層境界の一つのresidual bankであり、`on_chunk`で完成layer outputを書き、次層の入力として読む。これをR_after_attentionに再利用できる可能性はあるが、現コードはそこへattention中間値を書かない。合法化には各行の旧layer inputを読み終えたことを確認した後、その行の同じbank spanへFP32 partial Rを書き、MoE/FFN postprocess後に同じspanを完成layer outputで上書きする明示的なin-place phase/lifetime設計が必要。GPU/host placement、8192 subchunkと64K deferred phase間のqueue drain、partially complete rowの識別を含む所有変更であり、「layer-boundary residual storeがあるからR_after_attentionが無料」とは言えない。FP16 `LayerMajorResidualPlan`はこの一時値にも適用できず、reference精度を保つにはそのspanをFP32にする。再利用が成立しない場合、独立2.5GiBを上のroute/result保持量へ加える。

仮説で示されたXN (T×2560×2=320 MiB) とtoken accumulator (T×2560×4=640 MiB) は容量としては明確。ただしXNはrouteを作る正確なmixed_h representation/optional low partと一致する必要があり、640MiB accumulatorはexpert完了順の加算でslot順を変える。精密なroute-slot orderを保つ必要がある現状では、`Dm`を置き換える根拠にはならない。

## メモリ所有と容量上の見込み

現在のC8192実装は、full decode weights/canonical配置、per-layer temporary expert cache、GDN/QSA state/KV、work region、layer-major residual bankを同時に扱う。`NativeDense-onlybank`案はcanonical ownerを残すので、このsource-reviewだけで1.34GiB常駐weightを回収することも、64K workspaceに転用することもできない。combined layer bankは未実装の仮説で、per-layer cache ownerを実際に置換/withdrawし、reader retirement後にcanonical/native allocationsを確実に解放してはじめてVRAM容量へ反映される。

- **追加dedicated GPU arrays**: `Dm` + mixed_h + shared + inj/gate + routesで少なくとも約7.22 GiB。さらに専用FP32 `R_after_attention`を加えるなら約9.72 GiB。これはdevice total 9.93 GiBに近づく以前に現行operator scratch, active-layer packed/native/canonical owners, QSA/GDN full state/KV, runtime余裕を排除しており、不可能に近い。
- **既存residual bankをFP32 in-placeでR_after_attentionへ転用**: 独立2.5GiBを避けられるかもしれないが、7.22GiB retained MoE setに対する全workset admissionは依然必要。C8192の1.18GB regionはMoE retained arrays用に拡張できない。
- **FP32 accumulator設計**: 0.625GiB output planeへ削減できるが、combine reduction orderが変わる。数学的実数演算では同じ weighted sumでも浮動小数点順序/roundingは不変でない。task品質とfull model output gateが必要。
- **Host spill**: GPU live bytesは抑えられる一方、少なくとも`Dm` 6.25GiB/layerをexpert stage後にcombine用GPUへ戻す方向のI/O、さらにR bankのplacement次第では2.5GiB書込み+読戻しを追加する。既存single-device link bandwidthとのend-to-end計測なしにlaunch/dequant削減が勝つと言えない。RAM余力はGPU余力と同義でなく、reserved host tail/state budgetも守る。

よって専用full-64K `Dm`保持は現在のmemory topologyと不整合。FP32 in-place residual reuseで一部圧縮しても、route-slot結果全体が最大ownerであり、64Kを採択する根拠には不足する。短いbounded waveより64Kの方がdequant再訪を減らす可能性はあるが、8×larger GEMMのoccupancyはroute histogram/実測で決める。

## 統合前に必要な条件

1. 既存R633のroute identity censusを使い、64K内の実expert union/repeated active routes、expert row count、各layerのdequant/GEMM回数を得る。単に総top10 rows/512を平均した約1,280 rows/expertはuniform routing時の期待値であり実分布ではない。8K chunkの約160との比較も均等routing仮定に留める。
2. 64K attention prepassとMoE/postprocessを分離し、QSA future/tail masking、KV publication、GDN recurrence/conv state、PLE history、nonzero pos/262144末尾partialまで昇順stateを検証する。物理262Kを一度にrunせず8×64K以下+partial windowsにする場合も同じstate contractを守る。
3. row単位の`R_after_attention` ownerを定義し、既存residual bankを使うなら旧入力消費後・MoE完了前・final output store後の3 lifetimeをin-place sourceで証明する。FP32を保ち、次layer norm lookaheadやHC read/write consumerと重ならないことを検査する。
4. まずslotごとのFP32 `Dm`を保つ案で総live GPU/RAM peakとdequant savingsを入場計算する。容量不足時にexpert-major accumulatorへ切替えるなら、別の数値設計としてroute/combine/residual/logit/task品質を確認する。
5. 64K独立のworkset allocationでcurrent full-resident KV/decode/canonical ownersを含む実peak admissionを行い、host-spillならbytes transferred、GPU-link時間、GEMM/dequant時間、end-to-end PPを記録する。clean 32K/64K反復を同一binaryで比較するまで速度主張しない。短入力decode配置・thinking ON・physical contextの正しさは保つ。
6. QSA device-batch clean runがMainで継続中のため、そのprocess/GPU/host env/benchmark filesには介入しない。
