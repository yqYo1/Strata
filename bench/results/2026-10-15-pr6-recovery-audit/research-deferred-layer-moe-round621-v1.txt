# Deferred layer-wide MoE preparation and expert-major execution — R621

Date: 2026-10-15 JST. Read-only source research on the configured Arc B570 10 GiB / Ryzen 5600X / 128 GiB RAM target and `feature/sycl`. Only this new report was written. No source changes, build, test, GPU, service, process inspection, Git operation, or active-artifact inspection was performed. No runtime, speed, correctness, or admission success is claimed.

## Question and conclusion

Can one layer first run all chunks' attention/GDN/QSA, PLE, hyper-connection and router/shared-expert preparation, retain those intermediates in RAM, then iterate experts outside chunks, dequantizing each expert once and consuming its rows from all chunks in bounded GEMM tiles?

**The dependency order is mathematically plausible for the narrow currently admitted single-GPU native compact-FP16 full-model route, provided each layer still visits chunks in ascending order for its causal state and the per-row pre-MoE activation and route are retained. But it is not a small “reuse Rstore” optimization.** Current residual storage can be reused as the next-layer output bank once each row's input has been captured, but the schedule also needs prefix-wide BF16 activation and router metadata, shared-expert values, and expert output slots if it must preserve the current route-weighted accumulation order. At 262,144 rows, the dominant extra live tensors are approximately 1.25 GiB of BF16 activation, 2.50 GiB of shared FP32 output, and 25.00 GiB for all 10 routed FP32 expert products. The output bank can reuse the existing 10 GiB layer-major residual store after its input is consumed; the other tensors cannot. This is a substantial host-memory design, lifetime, admission and disk/NUMA traffic question, not evidence of a feasible or faster implementation.

A bounded expert-weight tile is compatible in principle: only one decoded FP16 expert pair is needed at a time (9,830,400 bytes, 9.375 MiB), and it can serve that expert's rows across all chunks before the next expert. But every token's prepared activation and route must stay available, and all outputs must stay available until `moe_combine` performs its existing ten-slot weighted sum in slot order. If instead each expert is immediately accumulated into one output row, expert-major order changes the current `k=0..9` FMA order and is not an exact source-preserving transformation. Even without this storage hurdle, there is no R621 measurement of dequant service fraction or resulting wall-time benefit.

## Prior-art check / novelty boundary

Read R565 (`research-layer-major-concrete-port-round565-v1.txt`), R601 (`research-profiled-dequant-reuse-round601-v1.txt`), R620 (`research-current-layermajor-mix-round620-v1.txt`) and `research-index.json`. R565 already establishes the valid layer-then-ascending-chunk causal schedule, the 10,240-wide residual, the existing host/device residual store and callback/restore concerns. R601 already proposes a bounded per-layer decoded-weight cache across chunks, with no measured reuse rate. R620 describes current route aggregation and MoE issuer instrumentation. This report's distinct question is whether an expert-outer loop can batch *all prefix rows for an expert* after chunk-wide per-layer precomputation, and what retained data and reduction-order obligations that introduces. It does not repeat or adopt the earlier cache proposal.

## Source-derived dependency audit

- Geometry is `N=2560`, `HC=4`, `D=N*HC=10240`, `K=10`, `NE=512` (`src/prefill/prefill.cpp:96-100`). The layer-major residual plan uses `width=D`; it stores one inter-layer residual snapshot over the prefix, split between host and optional GPU rows (`include/strata/prefill/layer_major_plan.hpp:78-117`; admission/owner setup `src/prefill/layer_major.inc:127-163`).
- Current layer-major orchestration loops layer outside `run_impl`, then resets a cursor and runs all prompt chunks for that layer (`src/prefill/layer_major.inc:279-313,362-373`). The residual callback stores each completed layer output and the next pass reads it (`:322-360`; chunk input in `src/prefill/prefill.cpp:1660-1696`).
- Within a layer/chunk, the two HC halves are sequential. The attention half normalizes/projects current residual and runs either GDN or QSA, then `gr_write` commits the attention residual (`prefill.cpp:2036-2056,2061-2086,2087-2298,2989-3013`). The FFN half then derives `mixed_h`, router output, shared output and shared gate, routes, computes experts, combines them, and writes the final residual (`:2300-2335,2492-2501,2803-2890,2958-2963,2989-3013`). Thus the proposed deferred segment begins only after each chunk's attention half and its FFN prelude; the expert outputs and FFN HC write remain unfinished until later.
- GDN changes its per-layer recurrence/convolution state during `gdn_conv` and `gdn_recurrence` (`:2068-2080`); QSA appends current K/V and indexer state before current query attention (`:2106-2135,2142-2161`) and attends to causal selected history (`:2264-2298`). Their state must continue to advance in ascending chunk order for each layer. The next chunk's attention input comes from the previous model layer's residual bank, not from the previous chunk's not-yet-completed FFN output; all rows of that prior-layer bank already exist. Therefore delaying only current-layer FFN expert work does not itself break GDN/QSA causality. Do not interleave chunks across layers or defer attention-state updates.
- PLE is enabled only for a range including layer 1 (`:1621`) and consumes/upgrades its rolling history token by token in the layer-1 pass (`:1980-2034`). PLE must remain in ascending token order, before the FFN-preparation snapshot for those rows. `ple_prev` is advanced from the request tokens in the chunk loop (`:1781`) and saved to session state at pass completion (`:3083-3085`); pass-level reset/restore semantics already handled by layer-major wrapper (`layer_major.inc:123-125,311`). Chunk-wide precompute must preserve these behaviors and callback cardinality.
- FFN shared expert inputs (`mixed_h`) and router inputs (`mixed_bf`) are both computed from the post-attention residual (`:2300-2318`). Router ids/weights are consumed by grouping, scatter metadata, and final combination (`:2317-2318,2436-2484,2958-2960`). Shared expert projection results (`m.shared`) and scalar gate (`m.sg`) are also required by final combine (`:2328-2335,703-713` in `src/prefill/kernels.cu`). None may be reconstructed from the *next-layer* residual, since that already includes the delayed FFN result.
- MoE expert contributions are currently written to `Dm` at the expert's route-group slot (`prefill.cpp:2882-2889`), and `moe_combine` computes `s=0`, then `s=fmaf(w[t*10+k], Dm[slot[t*10+k]], s)` for `k=0..9`, then adds shared output times sigmoid gate (`kernels.cu:703-713`). This slot order is a concrete arithmetic contract. Expert-major execution can fill the same per-token, per-route `Dm` slot and later invoke the unchanged combine, but cannot combine one expert at a time into a shared accumulator without changing FMA order. Keep the original `ids`, `w`, and exact slot mapping (`prefill.cpp:2478-2484`) or construct a demonstrably equivalent stable map.
- The existing `on_chunk`/`on_stage_chunk` hooks run only after chunk compute queue synchronization and then expose final residual/checkpoint (`prefill.cpp:3070-3079`). With delayed expert work, the final per-layer output callback must not fire during preparation. MTP/on_chunk and stage-ready must be delivered once per original chunk, only after all expert tiles for that chunk have populated `Dm`, `moe_combine` and FFN HC output. The final model layer alone may publish final model results; intermediate layer callbacks remain private residual handoffs (R565).

## Retained intermediate size at full logical prefix

Scenario: `n=262144`, model `D=10240`, `N=2560`, `K=10`; decimal bytes are computed directly from those logical shapes, excluding allocator alignment, helper tables and existing model/session memory. These are design estimates, not measurements or an admission result.

| Retained object for deferred work | Logical payload | At 262,144 rows | Reuse/constraint |
|---|---:|---:|---|
| Current post-attention FFN activation `mixed_h` as BF16 (N values) | `n*N*2` | 1,342,177,280 B = 1.25 GiB | New prefix owner; required to run GU later. BF16 is the actual `mixed_h` representation used by the current compact route. |
| Router IDs plus FP32 route weights (10 of each per row) | `n*K*(4+4)` | 20,971,520 B = 20 MiB | New owner, or a compact stable slot/source mapping of comparable order. |
| Shared expert output `shared` (N FP32) | `n*N*4` | 2,684,354,560 B = 2.50 GiB | New owner unless shared expert is recomputed after expert work; recomputation retains extra compute and does not remove dependency on the saved activation. |
| Shared scalar gate `sg` (one FP32) | `n*4` | 1,048,576 B = 1 MiB | New small owner, or recompute from saved activation. |
| `Dm` expert products for each route slot (10*N FP32) | `n*K*N*4` | 26,843,545,600 B = 25.00 GiB | New owner if exact current combine/FMA slot order is kept. Can be bounded in chunks only if computation returns to chunk-major batching; otherwise immediate expert-order accumulation changes summation order. |
| Existing inter-layer residual bank | `n*D*4` for FP32 | 10,737,418,240 B = 10 GiB | Already part of layer-major plan; once all current-layer input rows have been converted/snapshotted to `mixed_h` and route metadata, it can be reused as output destination. It cannot simultaneously preserve old residual input and new output before each row is captured. Existing FP16 storage option halves its size but introduces its documented boundary rounding and is not assumed here. |
| One active decoded FP16 expert pair | `1280*2560*2 + 2560*640*2` | 9,830,400 B = 9.375 MiB | One bounded per-expert workspace suffices for a sequential outer expert loop. Existing `DQ=2` allocates 19,660,800 B total (18.75 MiB), alternated by `j%DQ` (`prefill.cpp:163,2860-2868`; R601). |

The activation + route + shared result + gate owners total 4,048,551,936 B = 3.771 GiB additional host payload. Adding exact-order `Dm` raises additional prefix payload to 30,892,097,536 B = 28.771 GiB, before metadata/alignment and the existing 10 GiB residual bank. 128 GiB physical RAM does not prove these allocations fit alongside model weights, session, host KV, operating system, server, other requests or allocator slack. Current layer-major admission reserves 8 GiB headroom and admits its residual/cache owners through `conversation_memory_admit` (`layer_major.inc:127-150`); an implementation would need to include every new owner in checked aggregate admission before any state-mutating work.

A possible alternative is per-token accumulation into one N-wide output (2.5 GiB) as experts are processed. That cuts the 25 GiB `Dm` owner but executes contributions in expert-ID order, whereas current results execute slot order k=0..9. This is a numerical-order change; it should not be called source-equivalent. It would need explicit numerical contract review and model-level validation, and could change outputs through FP32 rounding. Another alternative is bounded wavefronts of chunks: preprocess a group of chunks, run expert outer over that group, combine and commit those chunks, then advance the group. This bounds storage but dequantizes again for every wave. Wave size 1 degenerates to the current per-chunk execution; larger waves trade RAM for repeated dequantization. It does not satisfy one expansion per expert for the whole prompt unless every expert's expansion can remain resident until all waves finish.

## Dequant call comparison and possible work avoided

Current native compact FP16 code dequantizes both GU and Down once per active `(layer, chunk, expert)` and uses `DQ=2` scratch buffers (`prefill.cpp:163,2860-2868`). At prompt length `n` with configured chunk `C`, the chunk counts are `ceil(n/C)`: 32 chunks at 262144/8192 and 64 chunks at 262144/4096. Per layer, at most 512 active expert calls occur in a chunk and at most 512 distinct experts over the complete prefix. Therefore the source upper bounds are:

| Scenario | Current upper bound per layer | Proposed whole-prefix distinct-expert upper bound | Maximum avoided dequant pairs per layer |
|---|---:|---:|---:|
| 262,144 tokens, C=8192 (32 chunks) | 16,384 active calls | 512 | 15,872 |
| 262,144 tokens, C=4096 (64 chunks) | 32,768 active calls | 512 | 32,256 |

These are route-independent maxima, not observed calls. Actual calls are the sum of nonzero routed experts per chunk; route recurrence may leave experts inactive, and R620 confirms the current layer-major issuer lacks the requested joint current route histogram. Across 48 layers the theoretical ceilings are 786,432 and 1,572,864 current active-expert calls versus 24,576 unique layer/expert decodes. Each “call” here means one GU+Down pair, not a single kernel. Even at those ceilings, dequant is only avoided if each expert's entire prompt row set is processed while its one decoded FP16 pair remains available. Bounded `ne` GEMM tiles are feasible at source-design level by gathering activation rows for the current expert into chunk-sized scratch; if one expert's rows exceed the tile, split them into tiles while retaining the same decoded weight. Route and `Dm` indexing must handle the non-contiguous rows across all chunks. No speedup follows from this count alone.

## Existing `Rstore`, transfers and safety boundaries

`LayerMajorResidualPlan` currently describes exactly `n*D` elements (FP32 by default) with a GPU prefix and host tail (`include/strata/prefill/layer_major_plan.hpp:87-117`). Each layer callback copies each chunk result to that store, and the following layer reads it back (`layer_major.inc:322-360`; `prefill.cpp:1660-1696`). This is sufficient storage for inter-layer residual values, not a bank of every stage's FFN inputs or routed products. New strategy must not silently reinterpret the store as both previous-layer input and current-layer output while outstanding consumers exist.

Potential transfers are additional host-resident precompute input/intermediate writes and reads. If each layer stores mixed_h and shared output then later reads each once for expert compute/combine, logical host traffic is at least a write+read of 1.25 GiB activation plus 2.50 GiB shared output (about 7.5 GiB decimal total per layer at full prefix), plus route metadata and `Dm` traffic. Storing/re-reading exact-order `Dm` adds 50 GiB of logical write+read per layer. These are transfer-volume scenarios derived from logical tensor sizes; they are not measured bandwidth, and actual route sparsity/compression/placement can change them. Keeping the exact `Dm` tensor in RAM still imposes the same memory requirement even if it stays resident until combine. Host/device residual partition does not make these extra retained arrays automatically GPU-resident; the proposed architecture explicitly says RAM, so CPU-side source ownership and bounded H2D transfers need a defined interface.

Failure handling is especially delicate because GDN/QSA/Ple state mutates during the precompute sweep, while later deferred expert/exceptions may fail. Existing layer-major checked queue lease retains temporary owners across drains and aborts if it cannot prove retirement (`layer_major.inc:193-231,362-385`), but it does not roll back session tensors (`:193-195`). Cancellation is checked at layer/chunk and upload boundaries (`:279-280,292-296`); the new expert sweep also needs cancellation checks and must not publish callbacks/checkpoints until all outputs for the layer are complete. Do not free saved activations, route data, output slots, decoded weights, residual stores or callback captures after an unverified queue error. Do not use current `StagerDone::finish()` as a new lifetime proof (`prefill.cpp:1870-1873`; R565 notes unchecked retirement). Ensure callbacks remain exactly once and preserve RESTORE behavior by preserving all existing caller callbacks, `ple_prev`, stage bounds, hand-off pointers, cache pointers and session lifetime. The current layer-major route explicitly disallows reentry, peer/device split, vision rows, hand-in, and unsupported options (`layer_major.inc:35-43`); expanding any of those is separate work.

The 262144-token admission boundary already checks `n<=262144`, `pos0+n<=ss.max_cells`, full logical QSA host/stage availability, and geometry (`layer_major.inc:45-58,91-109`). This does not include deferred MoE arrays today. Full-context operation is therefore not admitted for this design until checked host budget includes all retained arrays, not merely residual/cache storage. In the fixed 128 GiB PC scenario, the 28.771 GiB additional exact-order owner set is an arithmetic estimate, not evidence that the available-memory query will admit it or that full-context runtime is safe.

## Smallest safe investigation / implementation boundary

1. Keep the current `run_layer_major` entry/admission and default route unchanged. Prototype only one opt-in native compact-FP16 layer with two or more chunks, no MTP/callback publication until successful completion; don't start with full 48-layer/262K operation.
2. Preserve chunk-ascending attention/QSA/GDN/PLE and FFN prelude. At end of each chunk's prelude, snapshot `mixed_h`, router IDs/weights, shared result/gate, plus a stable mapping that lets each expert's output go back to exactly its existing route slot. Keep the current input residual bank until its row's needed values and route are captured; then allow output residual writes only after all delayed expert products and `moe_combine` for that row are done.
3. Add a separate default-off checked storage planner for activation, metadata, shared, gate and `Dm` (or explicitly named different accumulation policy), with overflow checks and one aggregate `conversation_memory_admit` before any layer state mutation. Do not fold these owners into `LayerMajorResidualPlan` unless its semantic type/API is deliberately extended. At full 262K, report the 3.771 GiB or 28.771 GiB cases honestly and fail admission without partial work.
4. Expert-major sweep one expert at a time: load/dequant GU+Down once, walk prepared rows across chunks in bounded GEMM tiles, write FP32 results into the corresponding original route-slot offsets in `Dm`, and retain the decoded pair until its rows drain. Only after all experts complete, run current slot-ordered `moe_combine` and HC residual write per chunk, then deliver callbacks in original order. Retire the decoded pair only after its last queued GEMM read completes.
5. The first correctness gate should compare full current versus candidate layer outputs for a small prompt containing a GDN layer and QSA layer, PLE enabled through layer 1, routes with multiple experts per token, and a partial final chunk. Check router ID/weight, shared outputs, every `Dm` route slot, exact combine order, final residual, state fingerprints, MTP callback count/order, cancel/failure and checked owner retirement. Then separately evaluate RAM admission, full logical KV boundary, and paired whole-request wall time. No source-level analysis substitutes for these gates.

Disposition: **the deferred expert-major schedule is dependency-plausible under strict ascending per-layer precompute and delayed callbacks, but exact current reduction order entails a 25 GiB full-prefix `Dm` owner at 262K in addition to 3.771 GiB of prepared activation/shared data. `Rstore` can serve as the inter-layer input/output bank only after per-row input capture; it does not remove these owners. No implementation or performance claim is justified.**
