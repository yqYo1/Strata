# R669 v2 — profile route for the 600/1,000 tok/s long-prefill targets

2026-10-15 JST. This corrected companion supersedes R669 v1's mistaken interpretation of the target units. The requested thresholds are **more than 600 prefill tokens/second**, followed by the retained **1,000 prefill tokens/second** goal. They are not input lengths. The intended long performance inputs are 32,768 and 65,536 tokens; configured physical context is 262,144 cells. Do not attempt a 600K- or 1M-token input: that exceeds the configured context. R669 v1 is preserved unchanged and should not be used for its erroneous input-size recommendation.

Read-only research only. No source edit, build/test, compiler, GPU/profile run, process/service inspection, Git mutation, cleanup, or private environment/log access was performed. This v2 is the only new file.

## Recommendation

The existing official unitrace `--device-timing` profile is the quick coarse census, but the retained 34,603-input/128-output receipt covers startup, prefill, and decode together. It reports operation-duration sums; it cannot isolate long-prefill wall, calculate same-queue busy union, or prove a rate over 600 tok/s. The existing historical PR6 result of 645.85 tok/s used 32,768 input tokens, 8,192 chunks, context 65,538, all KV resident, warm PLE, no timed MTP, and all requested FP32 residual rows on GPU. It does not establish the current-root result with 4,096-row chunks, context 262,144, `R_GPU=4096`, and MTP4.

For the critical-path question, use one bounded official unitrace Chrome activity collection around the actual `run_layer_major` prefill region of the current admitted workload. Start collection after request/tokenization and immediately before this call; stop after its final checked drain and last prefill callback, before decode. Mark the whole region with an ITT task. The local pinned unitrace documentation explicitly supports `--start-paused` plus either in-application `PTI_ENABLE_COLLECTION` toggles or `__itt_resume()` / `__itt_pause()`; it says ITT pause/resume takes precedence if both controls are present. The pinned `itt_collector.h` implements those calls by forwarding to the unitrace controller. Prefer the ITT API here so the runtime process environment remains immutable after provider/SYCL initialization. This facility is documented and present in the pinned local source; it has not been tested with Strata's binary or this source route.

The diagnostic hook must be default-off. First collect one 32,768-token case, then only if useful a separate 65,536-token case. Keep exact input hash, actual batched rows, 4,096 chunk setting, `R_GPU=4096` FP32, context 262,144, KV mode/residency, MTP4 callback, cache and other production settings pinned. The rate targets are clean performance criteria, so profiler-enabled output is diagnostic only. After profiling, the official clean benchmark must measure prefill wall and prefill tok/s separately from generation, at each actual input length. Do not extrapolate a 32K result to 64K or context 256K.

For diagnosis, report monotonic owner wall around prefill separately from (a) device execution-duration sums, (b) same-compute-queue execution interval union and overlap, and (c) host call/wait durations. Match device activity to native PID, B570, queue, flow/operation identity, and actual copy endpoints. A provider's operation sum is not prefill wall; queue interval union is not a clean application throughput result. Keep device and host absolute timestamps separate until actual trace clock-domain correlation is qualified; the historic `UNITRACE_SystemTime=1` CPU header check did not establish GPU event timestamp correlation. Do not call missing activity GPU idle or convert requested copy bytes into PCIe traffic.

The legacy `STRATA_PREFILL_TIMING` is explicitly rejected by layer-major admission. Its `PfTimer` uses CUDA events and ignores create/record errors. `STRATA_PREFILL_PHASE_AUDIT` copies selected tensor/state data for numerical inspection; it does not time work. A new aggregate host-only observer can report call and wait spans but cannot identify GPU service or busy union. Adding SYCL event timing would require queue profiling properties and checked event lifetime/error paths; per-phase forced drains would perturb the existing in-order route. Thus bounded official provider activity is the least invasive path if the actual hook/provider integration is validated. If that integration is unavailable, use host-only whole-prefill wall plus coarse summary as limited evidence and do not claim device critical-path attribution.

## Current owner limits and old proposal limits

The public comparable real-model receipt `model-device-profile-v1.json` records the owner's limits as wall 1,800 s, request 1,500 s, RSS 88 GiB, combined text/provider 64 MiB, job output 256 MiB, and per-file 64 MiB. These are observed bounds from a prior completed real-model profile, not automatically approved budgets for the next diagnostic. Main should carry over those public ceilings only after checking the current owned profile recipe and ensuring the profiled 32K/64K request and trace stay inside them. In particular, provider output needs a prelaunch aggregate-byte monitor; mark the collection incomplete and stop at the cap. Do not silently truncate/roll over. No existing public receipt demonstrates a suitable bound for a full Chrome activity trace, so don't promise it fits.

R576's 300 s deadline, 8 GiB RSS, 64 MiB one-layer trace and 512 MiB whole-prefill exception were historical design proposals. They are not the current model owner's limits and are not transplanted here. Choose a finite deadline within the current request/model limits and a total provider/output cap no larger than the current public 64 MiB text/provider and 256 MiB job ceilings unless Main records a reviewed reason and explicit larger bound. The current cap is an experiment guard, not a claim the capture will be complete. A cap stop is incomplete, not a pass.

After extraction, retain only the compact hashes, source/binary/provider revisions, exact command/environment, input identity, actual row/chunk/residual settings, request result, prefill wall, interval-union and operation-sum evidence, host durations, completeness/identity checks, and fresh fault/closure result. Retire raw successful activity after compact evidence is verified under `docs/ARTIFACT_RETENTION.md`; preserve a representative diagnostic if it resolves a distinct failure mechanism.
