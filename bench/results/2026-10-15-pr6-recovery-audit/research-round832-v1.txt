# R832 — Producer/consumer ownership and multistage prefetch on GPUs

**Purpose:** knowledge collection. **Scope:** two implemented non-LLM GPU designs, one Intel Xe/SYCL template and one independent CUDA pipeline example. This report compares subgroup roles, barrier reuse, stage lifetime, resource cost, and the boundary for a possible Xe2 SYCL adaptation. It is source analysis only: no implementation, build, device measurement, or Strata performance claim.

## Novelty and overlap

R769 already compares long-prefill one-slot, resident-prefix, and two-window copy/compute schedules, with event dependencies, buffer lifetime, memory-headroom arithmetic, and the warning that queue names do not prove overlap. R773 covers chunk size, tail efficiency, and recurrent state. R820 covers materialized recurrence state versus recomputation, and R822 studies low-precision bandwidth kernels and register pressure. This report adds a different evidence increment: it follows actual *in-kernel* subgroup/workgroup ownership and barrier reuse in two code designs, distinguishes cache-prefetch lookahead from explicit shared-memory stages, and derives when a reserved producer subgroup can lose compute capacity. It does not revisit transfer queues, chunk selection, layout alignment, precision, or model quality.

## Design 1: Intel XeTLA subgroup lookahead

The Intel XeTLA v0.3.6 Xe/XMX GEMM implementation uses a workgroup composed of a configurable two-dimensional array of subgroups. `g.get_id()` maps each subgroup to `(sg_idx, sg_idy)`, which selects its output tile. That subgroup owns the A and B tile coordinates for its own output region and the sequential K loop. There is no separate loader subgroup: every participating subgroup both loads its current operands and issues prefetches for its own later operands. This is a useful contrast with a producer warp that gives up compute lanes.

The source creates current-tile payloads plus separate `matA_prefetch_payload` and `matB_prefetch_payload` objects. A warm-up loop issues `tile_prefetch` `stages` times, advancing the prefetch descriptors after each issue. In the K loop it loads the current A/B tiles, issues prefetches for later coordinates, advances current and prefetch descriptors, then converts/transforms operands and executes MMA. The configurable `stages` therefore means *lookahead distance* in this implementation. It does not allocate that many software-owned SLM slots. The source reports `slm_size = 0`, and has no per-prefetch completion token or producer/consumer release operation. Cache residency and the exact number of outstanding requests are not exposed by this loop; a prefetch instruction is a hint, not a reserved buffer whose ownership can be proven from source.

This distinction matters when reading its barriers. `SW_BARRIER()` is documented in the source as a software scheduling barrier for code control; it is not a workgroup memory barrier or a prefetch-completion wait. The code also initializes separate XeTLA nbarriers for the X and Y subgroup axes and conditionally calls `arrive()` before the K-step and `wait()` after MMA at the configured `sync_freq`. Those are real subgroup-coordination points, but they do not assign ownership of a prefetch slot. The report does not infer a hardware phase count or asynchronous completion guarantee from the software scheduling markers.

At source level the design has no explicit SLM payload bytes. The subgroup's live tile payload is approximately `K*Mm*bA + K*Nn*bB` bytes for current A and B, plus converted/packed MMA inputs `K*Mm*bMA + K*Nn*bMB` and an `Mm*Nn*bAcc` accumulator; `Mm` and `Nn` are subgroup tile dimensions, `K` is the reduction stride, and each `b` is the bytes per source or accumulator element. These are logical live values before mapping across lanes. `matA`, `matB`, converted inputs, and the accumulator can overlap in lifetime, but compiler allocation and actual GRF count require the generated kernel report. Prefetched cache lines have no stable source-level byte budget. Thus increasing `stages` may hide cache latency, but can also issue useless lookahead at short K tails or evict useful lines; the source does not establish which effect dominates.

This is Intel Xe-specific template code, not portable SYCL and not evidence of BMG behavior. The v0.3.6 release is pinned at commit `aa2323e4462948a093d08823dc42579113ac8972`; its repository documents Intel Data Center GPU Max as the supported card family. The source file carries Apache-2.0 terms. It is cited to explain one implementation, not as a reuse proposal.

## Design 2: CUDA shared-buffer producer/consumer pipeline

The CUDA C++ Programming Guide 13.0.3 gives two related implementations that make stage ownership explicit. Its spatially partitioned producer/consumer example assigns the first warp as producer and remaining warps as consumers. Each block alternates between two shared-memory buffers. For each buffer there is a `ready` barrier and a `filled` barrier, for four block-scope barriers total. All block threads participate in each barrier's expected arrival count even though only one role waits on each side.

Initially, consumers arrive on both `ready` barriers, declaring both slots available. For iteration `i`, producers wait for `ready[i%2]`, fill that slot, and arrive on `filled[i%2]`; consumers wait for `filled[i%2]`, consume the same slot, and arrive on `ready[i%2]` after their last read. Reaching the barrier's expected arrival count completes its current phase and resets it for reuse. The `i%2` slot index and each barrier's phase together prevent a producer from overwriting a buffer still being consumed. The producer owns a slot from ready through fill; the consumer owns it from filled through its last read; the consumer's ready arrival returns ownership. A short input still needs a uniform tail and drain path so every required participant completes the same phase sequence.

The guide's `cuda::pipeline` two-stage copy example makes the multistage schedule concrete: it allocates two block-sized shared tiles plus a two-stage pipeline state, primes stage 0, then acquires a free stage, submits `cuda::memcpy_async`, commits it, waits for the oldest completed stage, computes from that stage, and releases it. The final stage is explicitly drained. In that example all threads act on both producer and consumer sides; the separate warp-specialized example shows role separation but uses a regular producer body. This distinction avoids conflating “two buffers” with “one producer warp,” or assuming that specialization itself creates asynchronous copy hardware.

For `int` input and a block of `T` threads, the two payload slots cost `2*T*sizeof(int)` shared bytes, plus implementation-dependent pipeline metadata. In the warp-specialized illustration the corresponding payload is `2*buffer_len*sizeof(float)`, plus four barrier objects. These bytes are per block, so a deeper pipeline multiplies shared-memory payload and may reduce resident blocks; registers used by the compute body impose a separate limit. CUDA documents that `memcpy_async` can use hardware acceleration on compute capability 8.0 or newer, but neither that path nor CUDA barrier/pipeline objects are SYCL contracts. The example is not a TMA requirement and gives no BMG performance result.

## Break-even, occupancy, and validation

A useful first bound for explicit copy/compute staging is to let `L` be the measured time from issuing one tile copy to its data being ready, and `C` the compute time per tile. With `D` owned buffer slots, a steady-state pipeline can cover at most `(D-1)*C` of copy latency; hiding all of `L` requires `D >= 1 + ceil(L/C)`. If `L=3.2C`, four stages can hide at most `3C`, so at least five are needed by this idealized model. Each added slot costs one more tile of local storage, and occupancy may fall before the latency target is met. The model assumes independent tiles and balanced service rates; causal state dependencies, tails, barrier time, copy throttling, and unequal tile work reduce overlap.

For a reserved producer fraction `f` of compute lanes, compare a serialized baseline `T0 = L + C` with the idealized split `T1 = max(L, C/(1-f)) + H`, where `H` includes barrier, handoff, prologue, and drain costs. Specialization wins this baseline only if `H < L + C - max(L, C/(1-f))`. With one producer warp in a four-warp block, `f=0.25`: if `C=2L`, there is at most `L/3` available for all extra overhead; if `C=4L`, then `C/(1-f)=5.33L` exceeds the serialized `5L`, so specialization loses before barrier cost. It can lose sooner against an all-warp asynchronous pipeline, whose compute side retains all lanes. This is the requested hurt case: a compute-heavy tile, or a baseline whose memory stall is already hidden, gets less compute throughput while paying for role coordination.

These equations are screening bounds, not speed predictions. Record actual tile bytes, load and compute service intervals, barrier time, and tail/drain cost for the same shape. Also record the compiler's registers per thread, spill bytes, SLM bytes per workgroup, and measured active workgroups/subgroups; source-level bytes alone do not yield occupancy. A pipeline should pass a same-kernel no-specialization baseline and a no-prefetch baseline. For phase correctness, validate that all work-items counted by each barrier arrive exactly once per phase, that no divergent bounds branch skips a barrier, that each slot's producer and consumer use the same iteration/phase, that the final partial tile drains, and that storage is not reused before its last consumer. Exercise zero/one-tile and non-multiple tails as well as steady-state depth. CUDA's requirement for explicit barrier participation and phase-aware reuse is a correctness lesson, not a reason to reproduce its API.

## What transfers to Intel Xe2 SYCL

At the SYCL language level, `local_accessor` storage and group barriers can express a cooperative tile load, workgroup-wide visibility, and reuse after all readers finish. `nd_item::barrier` or `group_barrier` is a supported programming-model primitive, subject to the selected device/runtime and its queried local-memory capacity. Standard SYCL `async_work_group_copy` has an event/wait contract in the specification but is deprecated in SYCL 2020; API presence alone does not establish a hardware asynchronous path. Intel's experimental oneAPI prefetch extension can request cache prefetches, including group-cooperative forms, but it is experimental and has no SLM-slot ownership or transfer-completion token. It is closest to XeTLA's cache-lookahead idea, not CUDA's producer/consumer buffer protocol.

A Xe2 adaptation is therefore a proposal to test, not a supported drop-in: first keep all subgroups computing and compare prefetch distances `0, 1, 2, 3` on the actual repeated tile stream; then, only if profiling shows exposed load latency and a supported async-copy/handoff primitive exists for the device, compare one reserved loader subgroup with two or more `local_accessor` slots and a correct group-level reuse protocol. If only a workgroup barrier is available, the stage handoff may stop every subgroup, leaving no overlap during that handoff; do not emulate CUDA split-phase barriers with divergent ordinary barriers. Query subgroup size, local-memory capacity, extension/device support, and compiler resource reports, and verify the generated code actually prefetches or overlaps. Published XeTLA target support, CUDA acceleration, and all break-even arithmetic here are design evidence only: no Xe2 BMG result, shape-specific speed, or Strata applicability has been measured.
