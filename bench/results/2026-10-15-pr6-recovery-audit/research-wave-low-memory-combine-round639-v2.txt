## Actual model capacity scale

Model geometry is `N=2560`, `K=10` (R621, `src/prefill/prefill.cpp:96-100`). Therefore exact routed-output storage is 102,400 bytes per token row. The following are decimal source bytes and binary units for readability; they are arithmetic, not measured resident memory or a claim that these wave sizes were run.

| Rows `W` | `Dm = W*10*2560*4` | One FP32 `W*N` accumulator | Current chunk Dm at `T=4096 / 8192` |
|---:|---:|---:|---:|
| 4,096 | 400 MiB | 40 MiB | 400 / 800 MiB |
| 8,192 | 800 MiB | 80 MiB | 400 / 800 MiB |
| 16,384 | 1.5625 GiB | 160 MiB | 400 / 800 MiB |

The current chunk formula is the same `102,400*T` bytes: 4096 rows = 419,430,400 B (400 MiB), 8192 rows = 838,860,800 B (800 MiB). For a proposed q-chunk wave, `W <= q*T` and is reduced on a tail. A W-row accumulator is still large; a B-row tile is `102,400*B` bytes for routed Dm or `10,240*B` bytes for one output accumulator. Subtract existing chunk allocation only when doing a complete peak-live allocation comparison; do not count aliased regions as concurrently free.

## Candidate 1: output tiles and expert-weight lifetime

An output-tiled proposal may retain only B rows of routed Dm, combine them in unchanged slot order, and retire them. But there is a real scheduling tradeoff:

- Expert-outer scheduling can decode each expert once and emit results for all token tiles, but later tiles' routed results must remain live until their output tile can perform its ordered combine. Without another strategy, this restores wave-sized routed-output retention.
- Tile-outer scheduling can retire each tile, but then each expert needed by each tile must be decoded/re-expanded as the tile loop advances, unless the needed decoded weights remain resident across the full tile loop.

For `A` active experts, retaining all decoded FP16 GU+Down pairs costs `A * (1280*2560 + 2560*640) * 2 = A*9,830,400` bytes (9.375 MiB per expert; at 512 experts, 5,033,164,800 B, about 4.69 GiB). The existing `DQ=2` pairs total 19,660,800 B, enough for two pairs, not all active experts. If decoded weights are not retained, tile-outer execution can require up to `ceil(W/B)` decode/compute visits per active expert (actual visits depend on that expert's references in each tile). Encoded blob residency or a larger cache has its own separately budgeted capacity and does not make decoded weights free.

Thus the no-conditions claim that the full wave can be computed in one expert pass while retiring output tiles is removed. This candidate needs a measured route distribution and a concrete memory-versus-redecode design before it can be judged.

## Candidate 2: slot-major ordered accumulation

A B-row tile can initialize one FP32 output accumulator, then process routed contributions in slot order 0 through 9 and issue `sycl::fma` into that accumulator; shared contribution follows slot 9. This avoids retaining B×K routed outputs and preserves the current per-token operation order. It likely repeats expert work across slots in which an expert has rows; quantify expert/slot multiplicity and visits from actual route data first. Chunk `m.bo` may serve as output accumulator only if its lifetime, alias, and queue dependencies allow it; no such alias is established here.

## Candidate 3: SCC dependency scheduling — defer pending observer work

A route-precedence graph may theoretically permit expert-topological execution with a single output accumulator if acyclic; SCC condensation could bound outputs that remain order-dependent within a component. This is only a hypothesis. It does not warrant implementing or expanding an observer before using the already prepared q2/q4 census work.

Evidence status: `layermajor-wave-census-v2/` is a NOT_BUILT / NOT_TESTED / NOT_RUN source proposal. It specifies the bounded q2/q4 aggregation to add to the optional existing census.
