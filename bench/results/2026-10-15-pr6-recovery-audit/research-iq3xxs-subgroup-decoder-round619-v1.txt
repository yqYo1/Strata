# IQ3_XXS subgroup decoder research — Round 619

Date: 2026-10-15 JST. Read-only source and primary-SYCL research for the Strata personal SYCL fork. No code, build, test, GPU, profiler, process, cleanup, or Git action was performed. This report is the only new file.

## Finding and boundary

Type 18 (IQ3_XXS) has a straightforward subgroup mapping that assigns 8 or 16 outputs per lane while preserving the existing scalar decode arithmetic. It offers a concrete alternative to `parallel_iq_dequant<Type=18>`'s one work-item per output: map each subgroup to one 256-value block, have adjacent lanes own adjacent output positions, and iterate over the block in lane-stride order. The work is cooperative at metadata/codebook-unit granularity: each four-element codebook word and its sign bits can be loaded/decoded once by a designated lane and exchanged to the other three lanes. The output stores remain adjacent and coalesced.

This is an architecture proposal only. The R610/R616 packed-to-XMX GEMM proposal answers a different question; this proposal still writes the existing FP16 materialization buffer and leaves oneMKL unchanged. R617 audited the six-format per-element helper, but its current proposed kernel still launches one work item for each output. The current IQ3_XXS18 single-shape timing is one sample (old 404.6 us, new 434.2 us) and gives no performance conclusion. Other type samples are promising but do not establish that this subgroup design will win. The active parallel-IQ product is unapplied; the work in progress reported by Main is not altered or inspected through live runtime/process state.

## Type 18 indexing contract

A type-18 block is 98 bytes and represents 256 values. Bytes 0..1 are FP16 `d`; bytes 2..65 contain 8 groups × 8 word indices; bytes 66..97 contain 8 groups × 4 aux bytes. Each group has 32 outputs. Each word index selects one packed four-byte entry from `iq3_xxs_grid`; each selected byte is one magnitude for one output. For local output `j` in `[0,256)` define:

```
group = j / 32
k     = j % 32
word  = k / 4
lane4 = k % 4
aux   = load_le32(block + 66 + 4*group)
scale = d * (0.5f + float(aux >> 28)) * 0.5f
index = block[2 + 8*group + word]
grid  = iq3_xxs_grid[index]
signs = iq_even_parity_signs(aux >> (7 * (word / 2)))
m      = int((grid >> (8*lane4)) & 255)
sign   = ((signs >> (4*(word % 2) + lane4)) & 1) ? -1.f : 1.f
value  = scale * m * sign
```

Keep the operations and order shown: first `scale`, then multiplication by integer magnitude, then multiplication by the sign float, then the existing `f16_from_f32`. Do not combine `scale` with magnitude/sign, substitute a signed integer multiply, or rely on reassociation/FMA. These are the existing helper's formulas, already checked against this fork's scalar decoder in R617; no alternate format interpretation is proposed. Relevant sources: `include/strata/artifact/iq_codebooks.hpp:1134-1152`, `include/strata/artifact/dequant.hpp`, and `parallel-iq-dequant-v1/proposed/include/strata/sycl/iq_parallel_decode.hpp:65-75`.

## Two lane mappings

Let `S` be the admitted subgroup width, either 16 or 32. A subgroup owns exactly one source block and its contiguous 256-half output span. For each iteration `r` in `[0,256/S)`, lane `l` owns

```
j = r*S + l
```

so `S=16` gives each lane 16 consecutive positions in the block across 16 rounds, and `S=32` gives each lane 8 positions across 8 rounds. In both cases all output locations are covered exactly once, `group/word/lane4` follow the formula above, and a subgroup's stores on each round are contiguous halfwords. Iteration count and base are uniform across the subgroup. Because 32 divides S*2 in both choices, this basic mapping crosses group boundaries on a round boundary (S=16 handles two 16-value halves of a 32-value group; S=32 handles one whole group per round).

For a first implementation, a simpler lane-owned loop `j=l + n*S` avoids staging and yields contiguous stores each iteration. Metadata sharing then occurs within four-lane clusters: all four lanes for one word derive the same `group` and `word`, and have different `lane4` output bytes. The cluster leader loads the word index and aux word, computes table lookup and parity-sign byte, and the other lanes select those values. For `S=16`, cluster boundaries remain aligned because both S and 4 divide evenly; for `S=32`, likewise. This is one subgroup per block, no cross-subgroup communication.

There is a tradeoff: each lane has its own `lane4`, so the 4 output bytes of the selected grid must be distributed. One option is a packed `uint32_t grid` exchange followed by lane-local byte extraction. A second is to have each leader load the grid once and exchange the already selected byte through a four-lane select; that reduces per-lane shifts but repeats the subgroup collective four times or requires a permute sequence. Measure both. Either way there is one grid-table lookup per 4 outputs instead of four independently repeated gathers. Scale is constant across the whole block, so lane zero can load/decode it once and broadcast it. The 4-byte aux word is also needed for sign parity; within an 8-lane pair of four-lane clusters, both words share the same parity input (`word/2`), while the nibble selecting the sign differs. Do not assume metadata loads/table accesses are cached or free; capture generated code and resource behavior in the eventual owner-run fixture.

A more throughput-oriented variant can assign the subgroup a 32-output group per iteration and use a cyclic/strided mapping, but keep the simple lane-stride version as the indexing oracle. Avoid a 256-element subgroup collective or local-memory transpose: neither is needed for this layout.

## SYCL collective legality and shape contract

Use `sycl::select_from_group(sg, value, source_lane)` for four-lane cluster exchange if the installed DPC++ implementation supports it for the selected kernel/device. The SYCL 2020 specification defines it for `sycl::sub_group`; the source lane must be within the subgroup. Its remote id is an input to the selecting work-item, so `source_lane = (lane/4)*4` may vary between four-lane clusters. Call the collective convergently on every subgroup lane in each iteration. The SYCL group-functions reference explicitly requires group functions to be encountered in converged control flow.

Do not use `group_broadcast(sg, value, source_lane)` with this varying source lane: the specification requires the `local_linear_id` argument to be identical for every lane in the group. `group_broadcast` is valid for the block scale from lane zero because that source id is uniform. `group_broadcast(sg,value)` also broadcasts lane zero. A simpler alternative is for every lane to load the byte metadata it needs and avoid collectives, but that abandons the intended metadata-sharing experiment. `select_from_group` and `group_broadcast` have collective semantics, but no workgroup barrier is needed for subgroup-local register exchange. All lanes must execute the same sequence of collectives, including tail rounds; the fixed 256/S loop guarantees no per-lane tail branch.

Set an explicit required subgroup size only in a separate specialization and only after device/compiler admission. Intel's optimization guide documents `reqd_sub_group_size` options for its GPUs and explains the occupancy/register tradeoff, but does not prove this B570 runtime/compiler's support for this kernel. Query the configured device's supported subgroup sizes and build the exact specialization. Launch local size as an integral number of S lanes and map each subgroup to one block. The safest first shape is one workgroup containing a small fixed number of subgroups, with global work rounded to whole workgroups; guard only the block id uniformly at subgroup scope or pass an exact block count. Do not let some lanes exit before a collective. If the implementation cannot guarantee subgroup arrangement/size, retain the scalar or existing per-output path.

## Dispatch, buffers, and arithmetic boundary

Dispatch only from the existing type-18 FP16 materialization entrypoint and only when all existing pointer/span/count/row-width checks have passed. Preserve the current row-major GGUF block mapping and the GU gate/up alternating-row destination mapping. For GU, source rows map as the existing helper defines: destination output row `r` selects gate for even `r`, up for odd `r`, and packed source row `r/2`; type-18 row width must be divisible into 256-value blocks. Generic type-18 dequant maps each consecutive 256 values to one block. A whole subgroup owns one block, so source and destination offsets are respectively `block_id*98` bytes and `block_id*256` halfwords (plus validated matrix row offsets for GU). No writes cross a block or row boundary.

The kernel should write exactly the same half bits as `f16_from_f32(parallel_iq_element<18>(block,j))`; it changes only who computes and shares source metadata. Preserve `d` decoding, parity (`iq_even_parity_signs`), byte selection, multiplication order, final half conversion, in-order queue placement and finish semantics. Keep default dispatch off until the product's existing CPU, GPU correctness/fault, and clean timing gates are completed by Main. No optimizer flag or arithmetic mode should be changed in this candidate.

## Resource and likely failure modes

Each subgroup needs a block scale, one aux word per active group, word index, four-byte grid, parity/sign byte, four output values, and a small number of integer temporaries. It should avoid the current scalar work item's 256-float temporary and one work item's serial 256-output decode. Codebook gather traffic is addressed once per four output elements by a cluster leader, though the actual table lives according to existing codebook declarations and may still compile to costly loads. Packed input reads can be adjacent across lanes for output bytes only if the mapping respects the packed word granularity; the base lane-stride mapping makes stores coalesced but metadata is shared/repeated by cluster, and source bytes need not be read coalesced in every iteration. Cache behavior and compiler scalarization may erase expected benefits.

Main risks are subgroup collective lowering overhead, increased register pressure from loop unrolling, irregular 4-lane cluster exchange code, codebook table cache behavior, and conversion instruction cost. The potential benefit is from distributing 256 outputs across lanes, reducing large temporaries and redundant per-element metadata/table decoding, while preserving the same output materialization and matrix math. It cannot remove FP16 matrix writes/reads or oneMKL work.
