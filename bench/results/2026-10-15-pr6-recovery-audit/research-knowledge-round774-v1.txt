# R774 — Host CPU cost and latency tradeoffs in GPU completion waits

2026-10-16 JST. Bounded, read-only knowledge collection from public primary sources. This report is not an implementation or performance recommendation for Strata. No code, build, test, GPU run, profiler, process inspection, Git command, cleanup, or environment change was performed. The supplied measurement of 165.704 CPU seconds inside explicit waits is context only: it does not identify the runtime stack or show that changing a wait mode improves prefill.

## Findings

A wait policy is a workload and runtime choice, not a portable SYCL setting. SYCL 2020 specifies that `event::wait`/`queue::wait` wait for represented commands to complete, but it does not promise whether the implementation spins, yields, sleeps, or receives an interrupt. The standard therefore provides no cross-backend guarantee for CPU use, wake latency, or jitter. Intel's experimental Unified Runtime (UR) low-power-events extension describes Level Zero's default host synchronization as busy polling, then proposes opt-in low-power queue/event hints that may use interrupt-driven completion. It requires an adapter capability query; its specification is explicitly experimental. Level Zero exposes a lower-level event-creation hint for low-power host waits, with a separate optional interrupt signal mode. None of those contracts proves that an existing SYCL `wait_and_throw()` call maps to a particular mode, or that the installed adapter/driver supports the hint.

Four useful strategies have distinct costs:

| Strategy | Host use and latency tradeoff | Setup/signaling and best fit | Evidence limit |
| --- | --- | --- | --- |
| Active poll / spin | Repeatedly inspect completion; uses a core while the event is pending. Avoids a sleep-and-wakeup path and can return quickly for a very short wait, but consumes CPU and can steal scheduling time from host submission or other work. | Usually little additional event setup; an explicit query loop adds calls. Most plausible when waits are predictably brief, tail latency matters, and a CPU is dedicated. | NVIDIA's documentation describes shorter, more stable synchronization overhead for spin waits than blocking waits; this is not a B570 or Level Zero measurement. |
| Blocking / low-power wait | The host thread yields or sleeps, reducing active polling. Completion handling then includes OS scheduling and wakeup delay; measured latency can be less stable, especially when the pending interval is short. | Can be a native queue/event wait, or an opt-in low-power hint where supported. Use when work is expected to run long enough for the CPU savings to exceed wake cost, or when the CPU has useful concurrent work. | SYCL's semantic “wait” does not guarantee sleeping. UR low-power events are experimental and require support discovery. |
| Interrupt-backed notification | A device/driver notification can wake a sleeping host thread, avoiding repeated host queries. It still pays notification delivery and OS wakeup costs. | Level Zero says interrupt signaling may add GPU commands to signal an event; it may use the interrupt to wake a low-power waiter. Per-event creation and signaling overhead can dominate tiny commands or high-frequency events. | The specification says the driver chooses which calls use interrupts and gives no latency or overhead measurements. Do not assume every wait is interrupt-backed. |
| Adaptive spin-then-sleep | Poll for a bounded interval, then block if incomplete. A good bound can keep short-wait latency low while avoiding burning a full wait interval on long work; a bad estimate either wastes CPU or sleeps through completion. | Needs an estimate or policy per wait class, plus query-loop overhead and a correct fallback wait/error path. Useful to test when wait durations are repeatable or CPU scheduling is shared. | One CUDA/NAMD study found a large gain in a particular oversubscribed VM, but it does not establish a generally useful threshold or a SYCL/Level Zero implementation. |

### Empirical comparisons and counterevidence

Elmougy et al. compare polling, blocking, and polling-then-blocking with CUDA events in NAMD and GROMACS running in a KVM GPU-cloud setup. Their host had four Xeon Gold 6138 processors and two Tesla P100s; GPU workloads used CUDA 10.1 in a VM with a passed-through vGPU. They created 16-, 32-, and 64-vCPU instances and ran CPU-intensive co-runners, including a synthetic maximum-interference case. The important mechanism was CPU scheduling discontinuity: an always-polling vCPU could consume its time slice just before it needed to submit the next kernel or consume a completed result. Under the paper's maximum-interference evaluation, the adaptive NAMD variant reported up to 4.2x performance and 5.4x vGPU-utilization increases against polling; it reported 1.9x performance over blocking. Its timing table gives kernel-invocation delays of 29.79 ms for polling, negligible for blocking, and 5.42 ms for hybrid; completion-receive delays were 28.65, 13.58, and 1.49 ms respectively. A NAMD CPU/GPU cycle averaged 4.5 ms. The hybrid chose a polling window from a moving average of per-kernel execution time, then called blocking event synchronization if the event was still incomplete.

This is counterevidence to both blanket rules: polling can hurt when CPU time slices are shared, while blocking can add costly wake delay even when it saves CPU. But it is specifically a vCPU-overcommit study; its multi-millisecond scheduling stalls are not evidence about a dedicated consumer-PC CPU, an Intel GPU, or this application's driver. The paper did not sweep queue depth or provide a portable spin threshold. NVIDIA's TensorRT performance guide makes the complementary qualitative point: spin can give shorter and more stable synchronization overhead at higher CPU use, while blocking yields CPU capacity but can have unstable OS-dependent overhead. Neither source quantifies the power, latency distribution, or event signaling cost for Strata's exact stack.

### Queue depth, duration, and runtime boundaries

Queue depth changes how often the host must wait and what completion represents. If the host can enqueue independent work and wait once on a later event, it may amortize host synchronization over more GPU work and avoid a wait per short command. That changes the work and dependency boundary, so it is not a fair comparison of wait modes unless the same commands, event position, and host decisions are preserved. A deeper queue can also make the eventual wait longer; that generally gives a sleeping policy more time to recover its overhead, while a shallow queue or a short event can make wake latency a larger share of observed completion time. This is an engineering inference from the dependency path, not a published guarantee or a Strata result. Frequent synchronization in the NAMD study amplified CPU scheduling effects, but the paper did not isolate queue depth as a variable.

Wait duration and event count should be varied separately. Very short waits are the strongest case for active polling because even one scheduler wake can cost more than the residual GPU work. Long waits favor blocking if the core would otherwise be idle or useful elsewhere. Interrupt-backed waits have an additional signaling cost: Level Zero explicitly allows driver-inserted GPU commands, so the comparison must include event creation and signal work as well as caller CPU and wake latency. If one event is reused or a single barrier marks a batch, setup and device signaling can be amortized; if a separate interrupt signal is generated for every tiny operation, its value may be negative. Those cases are hypotheses to measure, not an API-level cost model.

At the API layers, standard SYCL specifies completion semantics only. UR's low-power extension adds opt-in API shapes and a support query but has no conformance or stability requirement. Level Zero's `ZE_EVENT_SYNC_MODE_FLAG_LOW_POWER_WAIT` is attached to an event at creation; `ZE_EVENT_SYNC_MODE_FLAG_SIGNAL_INTERRUPT` may add device commands and the driver selects applicable calls. These are not interchangeable with a generic environment switch. A runtime may also have backend-specific behavior that the SYCL source call does not expose. Therefore a result from a CUDA event or a UR adapter cannot be transferred as a numerical policy to another backend, operating system, driver, or queue implementation without verifying the actual path.

## Concrete future experiment

On the exact Arc device and installed SYCL/UR/Level Zero versions, first query whether the adapter advertises UR low-power-events support and whether the low-power event reaches the synchronization call being measured. Then run a small, owned, non-model diagnostic with identical GPU command sequences, event placement, and correctness checks at two controlled wait durations (brief and multi-millisecond) and two queue depths (one command and a short in-flight batch). Compare: (a) default SYCL wait, (b) capability-gated UR/Level Zero low-power event wait, including interrupt signaling only if that mode is advertised, and (c) a bounded query-then-wait arm with a small predeclared spin budget. Record per-wait caller thread CPU time, wall-time p50/p95, event creation and GPU signal overhead, host submission delay after completion, and command completion time; report unsupported arms as unsupported. Keep each mode immutable for its owned process and preserve the same command graph. If an arm materially reduces wait CPU without worsening the complete dependency interval, only then repeat a paired full-prefill comparison and retain correctness/fault checks. This is a proposed experiment, not an inferred fix.

## Evidence boundary

The sources establish API semantics, selected implementation choices, and one oversubscribed CUDA/HPC case. They do not establish UR/Level Zero low-power support in the installed Strata build, identify the current wait implementation, or predict prefill speed, CPU savings, interrupt overhead, or a useful spin budget on the target machine. The current wait attribution motivates a measurement question only; no wait-mode change or performance adoption follows from this report.
