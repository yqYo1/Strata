# R1014 — expert-major MoE window capacity audit

Classification: **decision support**. Read-only source audit of immutable Main extraction `c05c2545d90fb3bedcfff51400919977b6c276ca`; no implementation, performance claim, build, test, or GPU result. The central answer is that 81,920 is representable by the generic accumulator planner, but not reachable by the pinned mode-8 engine: independent hard limits in the admission expression, route factory, and operator entrypoint all stop at 65,536. Raising only one ceiling is insufficient. For the observed 78,452 batched MoE rows, one 81,920 cap would make one window only if the whole row range is device-resident and the 1.059 GB arena plus a 400 MiB mixed bank actually fit. The current two-window measurement is not evidence for the one-window hypothesis.

## Exact reachability and end-to-end boundaries

1. **Admission and mode parsing.** `moe_window_requested()` accepts only `0`, `2`, or `8`; it is not a row-cap parser. In `layer_major.inc`, mode 8 currently derives `count = min(65536, plan.gpu_rows)`, computes the separate FP16 mixed allocation `count * N * 2`, checks remaining free GPU bytes after cache, optional QSA prefix, chosen residual GPU prefix/staging, and the existing 512 MiB headroom, then calls `MoeAccumPlan::make_contiguous(count, bytes, m.region_bytes)` before model work. This preflight is the right seam to derive or validate a new cap. `LayerMajorResidualPlan` rounds a user decimal GPU-row request down to complete 8,192-row chunks except when the request is exactly the total request length; it can also leave a host tail. A larger MoE cap must never imply a larger residual allocation or bypass the currently retained headroom.
2. **Window slicing and dispatch.** `run_impl` starts a window only when two adjacent residual spans are both device-backed and another chunk remains. It extends `window_end` to the minimum of request end, GPU prefix end, and `c0 + maximum_rows`; it stores each attention/PLE-produced 8K-or-final-partial residual piece, then calls the accumulation helper once at the boundary. Completion invokes `on_stage_chunk` and `complete_piece` for each constituent logical chunk after FFN writes drain. Keep ascending chunk order, whole-piece boundary rules, and final partial count. A cap of 81,920 is a maximum window, not a new operator batch size.
3. **Entry point and route factory.** `run_moe_accum_window` independently rejects `rows > 65536`; `MoeWindowRoutes::max_accum_rows` and `build_accum()` independently reject above 65,536. `MoeAccumPlan::maximum_rows` is already 81,920. All three admission/consumer ceilings need one shared policy or compile-time consistency check. Existing ordinary mode-2 `build()` stays capped at 16,384. Preserve 8,192 as every projection, gather, expert job, final shared projection, finish, write, and `m.T` loop bound.
4. **Plan/layout and views.** `MoeAccumPlan::make_contiguous()` sizes the accumulator and W-dependent route planes from rows, fixed job planes from J=8,192, and gives every region view 256-byte alignment plus 256-byte guard reservation. Its pointer-difference and multiplication overflow checks are part of the contract. Recomputed total reserved region at W=81,920 is **1,059,131,904 bytes** (1,010.07 MiB); at W=65,536 it is **888,410,624 bytes** (847.25 MiB). The difference is 170,721,280 bytes (162.81 MiB). The prior legacy-window 998,443,520-byte arena figure is a different layout; it must not be substituted for this planner’s actual `m.region_bytes`. Preflight needs to evaluate the new plan against the real region, while the helper keeps its plan and typed-span checks.
5. **Host route metadata.** For W=81,920 the owner’s router ID vector plus route object `source_rows`, `slot_map`, and inverse `original_slots` are four `W*K*4` arrays: **13,107,200 bytes (12.5 MiB)** before job vectors and small fixed arrays. At most 5,120 jobs exist (512 experts × ceil(81,920/8,192)); with 16-byte `Job`, that is 81,920 bytes, plus vector capacity/allocator overhead. The existing host admission’s 16 MiB accumulator allowance appears large enough for these raw payloads by arithmetic (about 3.5 MiB left before allocator overhead); still verify any new representation/temporary duplication against the owner’s lifetime, rather than assume that the GPU memory cap bounds host memory. Current route builder validates all W×10 IDs, disallows repeated expert within a token, stable-groups source rows, and records original slots; these cardinality and ordering invariants remain necessary.
6. **Device indices, status, and lease.** W×10 route positions at W=81,920 are 819,200, fitting the current signed 32-bit indices; assert the derived maximum rather than relying on this silently if cap becomes dynamic. `moe_job_weights` checks inverse slots and sets status bit 1; `moe_accumulate` checks source token and slot agreement and sets bit 2, then atomically FMA-scatters into one FP32 accumulator row per token. The zeroed device status and host `status_observed` readback/drain must still gate shared projections and output writes. The in-order queue requirement is explicitly checked. `owner.ids` and immutable `owner.routes` stay alive across asynchronous map uploads; the outer `DraftUploadGuard` lease drains before owners and temporary allocations retire, aborting with owners live if retirement cannot be proven. Keep these exact failure semantics and status checks for all enlarged extents.
7. **Cross-chunk/model state.** The helper is FFN-only: attention and PLE have already advanced each chunk once. It retains original BF16 mixed producer for router and shared scalar gate; saved FP16 mixed feeds expert gather and later shared projection. Do not reconstruct BF16 input from FP16. Router readback/grouping/upload expands to the entire MoE window; routed jobs are grouped across that window, while every GEMM remains ≤8,192. Final expert sum order is FP32 FMA in expert-major job order, differing from the existing top-k-slot combine order. Shared gate scalars and injection are W-sized in this plan so the final combine/write can be chunked without losing data. Device status must be checked before finish. The exact production numerical contract and impact of the changed sum order remain separate gates.
8. **Physical 262,144 and host-tail.** Never make the whole physical context resident by raising this cap. The residual plan can split GPU prefix from host tail, but `window_piece` starts only when both spans are device-backed; each window must end at or before `gpu_rows`. On a 262,144-row request, capacity-bounded windows may be followed by existing non-window host-tail chunks and callbacks. Preserve all 32 logical 8K chunks, final partial semantics for nonmultiples, token positions, PLE/recurrent advancement exactly once, boundary/MTP callback order after drained writes, and next-layer/decode/RESTORE behavior. The 81,920 cap would imply up to four windows over a fully resident 262,144 rows (3×81,920 + 16,384), but this is arithmetic only and says nothing about device admission or host-tail correctness.

## Memory and strategy comparison

All figures below are deterministic source/layout arithmetic, not observed allocation, free VRAM, GPU residency, or timing. FP16 is two bytes per value. Mixed bank at W=65,536 is 335,544,320 B (320 MiB); at W=81,920 it is 419,430,400 B (400 MiB), an extra 80 MiB. For the measured window rows, 78,452 × 2,560 × 2 = **401,674,240 B**; 78,453 actual request rows would require 401,679,360 B. The log distinction “actual 78,453 / batched 78,452” means the extra row must be reconciled with the exact MoE callback count before claiming a single window covers it. The FP32 accumulator alone grows from 640 MiB to 800 MiB. Keep the separate dedicated mixed bank: no source evidence establishes that residual storage can be safely aliased or that aliasing is required to admit a larger cap.

- **Fixed 81,920 cap:** simplest policy and one large reservation. It can reduce per-window route readback/grouping/upload and boundary drain/dispatch count for 78,452 rows from two to one if all those rows are device-resident. It always pays the 400 MiB mixed admission and 1.010 GiB planner region limit, including short or host-tailed requests. Risks: rejecting otherwise valid mode-8 workloads on either GPU headroom or actual arena capacity; no evidence this additional peak memory buys enough time. The source ceiling 81,920 is not a capacity guarantee.
- **Capacity-derived cap (preferred policy shape for a proposal):** before allocating or beginning layer callbacks, choose the largest complete 8K cap no greater than generic 81,920 and the current GPU residual prefix, whose dedicated mixed bytes fit `free_gpu - cache - prefix - residual_gpu - staging - 512 MiB`, and whose `MoeAccumPlan` fits actual `m.region_bytes`. Apply checked integer arithmetic, `MoeAccumPlan::make_contiguous`, and existing RAM admission; fall back to mode 2 or current 65,536 policy on admission failure according to the intended compatibility contract. For the final request window allow the existing partial logical last chunk. This avoids promising a cap that the machine cannot fund and keeps operator jobs fixed. A capacity-derived cap still needs no performance claim and needs fresh capacity/allocator evidence.
- **Layer/last-window scheduling:** cap selection can be per request/window, but allocation is established once before processing, and each layer runs a full ordered token pass with callbacks/state. A last-window-only increase cannot merge the already completed first 65,536 rows into a single route grouping, so it does not establish the one-window hypothesis for 78,452 rows. Enlarging only the last partial window can be useful for a *different* capacity/placement case, but its cap must be known before the first row of that window and the region must have been reserved. Per-layer caps add policy complexity without a known layer-varying arena or workload benefit. The useful first experiment is a single admitted larger cap across the request, then profile only after capacity and correctness gates; no dynamic scheduler is justified by current evidence.
