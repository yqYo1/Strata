# R758 — SYCL host submission controls and replay options for long prefill

2026-10-16 JST. Bounded read-only research; this report is the sole file written. No GPU, build, tests, profiler, process, environment, service, Git mutation, cleanup, or product edit was performed. One initial read-only `git status` command was run inadvertently despite the task boundary; no repository state was changed. No XeStrata code or derived artifact was read or used.

## Finding

The current workload already creates in-order SYCL queues, so explicitly adding `in_order` is not an optimization candidate. The measured explicit event-accounting CPU time is only about 0.00005 s across the 78K diagnostic, so suppressing event creation is unlikely to matter unless that counter excludes backend event bookkeeping. The more credible new submission experiment is to compare supported Level Zero UR queue implementation modes in separate owned processes, while holding the safety environment and workload fixed. This is a hypothesis: Intel documents different submission paths and warns immediate append may increase host overhead for many short kernels. It does not predict which mode is faster for this B570 run.

A SYCL command graph can amortize host submission for a repeated, stable sequence. It is a poor immediate fit for MoE expert dispatch: each chunk's active experts, row counts and pointer/offset arguments change after host-visible routing. Capturing one graph per route shape or padding to a fixed maximum has material graph/update complexity and possible extra GPU work. Keep it behind evidence that a stable expensive subgraph remains after attribution. Kernel bundles address device compilation/JIT, not repeated enqueue overhead; they are not a submission fix for the current measurement.

## Prior evidence and applicability

The index and R751–R756 reports show: main CPU 216.98 s, of which 168.47 s is inside explicit waits; outside-wait CPU includes 37.35 s unclassified, 6.78 s GEMM submit, 4.86 s source copy, and 0.165 s host grouping. The GEMM counter spans 239,458 calls. These measurements do not show that submission lies on the latency critical path. R755 already proposed grouped GEMM; R758 does not repeat it.

`src/sycl/runtime.cpp` constructs in-order compute and transfer queues. Thus SYCL `property::queue::in_order` semantics are already in effect: operations have implicit queue order. R751's busy-polling finding concerns CPU inside waits; changing queue order or disabling events does not establish a reduction in that wait cost.

## Candidate controls

**UR Level Zero submission modes.** The official UR Level Zero reference documents `UR_L0_USE_IMMEDIATE_COMMANDLISTS` (0: no immediate lists, 1: per-queue, 2: per-thread per-queue) and `UR_L0_USE_DRIVER_INORDER_LISTS` (0/1). The current UR reference also describes `UR_L0_CMD_BUFFER_USE_IMMEDIATE_APPEND_PATH`, which selects between immediate append and a wait-event path when prerequisites permit. These controls affect adapter submission mechanics, not inference math. The Intel GPU optimization guide explains that immediate lists submit each append promptly and can raise host append overhead; regular lists can batch commands before submission but carry list-management/submit costs. The docs are not a guarantee that each control is honored by the installed v711 L0v2 path, nor that the legacy `UR_L0_USE_IMMEDIATE_COMMANDLISTS` applies identically to V2. Confirm actual adapter/version and effective path from a bounded receipt/diagnostic before interpreting an arm. Change one control at a time in separate child processes; preserve the existing `UR_L0_V2_FORCE_DISABLE_COPY_OFFLOAD=1` safety condition and all other inherited settings. Do not mutate environment after runtime initialization. Compare total prefill wall time plus submit-call CPU/wall and wait CPU/wall; do not infer a win from lower submit CPU if queueing moves work into waits or increases device idle gaps.

**Discard queue events.** Intel's supported DPC++ extension allows `ext::oneapi::property::queue::discard_event` where returned events are not needed. It can reduce event allocation/retention overhead, but makes returned events invalid for operations such as dependency/wait; use is unsafe anywhere a wrapper consumes the event or error/wait contract depends on it. Graph recording also forbids using discarded events to create edges. The actual event CPU counter is tiny, so do not apply it globally. If a finer counter shows event construction/destruction cost in specific fire-and-forget submissions, try a separate queue/property only for those calls and preserve real event-producing paths and async error handling.

**SYCL command graph / UR command buffer.** Intel's experimental SYCL graph can record and replay queue submissions; queue recording can capture external queue work such as libraries, which makes it more plausible for stable kernels than a hand-built graph. But an in-order recorded queue is a straight-line graph; every command and dependency is captured. Native recording needs backend support and an in-order immediate command list, disallows host tasks and graph update, and cannot use discarded queue events to form graph dependencies. UR command buffers are explicitly experimental; support and update fields must be queried on the device/adapter. Kernel launch arguments/ranges can only be updated for advertised capabilities, updates are synchronous and may block, and signal-event reuse has strict execution-order constraints. Nothing in these contracts promises that oneMKL's internal GEMM submissions can be captured/replayed as a single node or safely updated for changing dimensions. This should be a later component experiment only after runtime capability evidence and a stable phase are identified.

**Kernel bundles / AOT.** Intel's compiler design docs distinguish ahead-of-time device compilation from runtime JIT. AOT or explicit kernel bundle materialization can move compilation out of the measured region and improve first-use latency, but does not combine repeated host queue submissions. Only investigate if the actual 78K request includes first-use compilation in its wall time; do not count a warmup-only benefit as steady-state submission reduction.

## Next measurable experiment

After the current CPU attribution splits the 37.35 s residual, run a small clean same-binary comparison of the current UR submission setting versus one documented alternate at a time (prefer the UR L0v2 command-buffer immediate-append toggle if the installed reference confirms it applies). Use separate native processes, same prompt/chunk/device/safety variables, equivalent warmup, and repeated samples. Record effective adapter/runtime versions and setting, full-phase wall time, caller CPU, `gemm_submit` and other enqueue CPU/wall, explicit wait CPU/wall, and GPU fault/correctness status. Keep all event-producing waits and validations intact. If submission CPU drops but whole-phase latency does not, reject the setting as a performance change. If no material submission attribution remains, stop this branch and prioritize the measured critical path.
