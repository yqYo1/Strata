Relevant source path

`tools/strata_bench.py` has a durable chained request journal. `Suite.request()` fsyncs a `start` row before HTTP, then appends a `result` row after `chat()` returns; an exception raised inside `chat()` instead gets an `interrupted` row. A returned HTTP/SSE error is still a normal return: its digest contains `err`, and the request journal gets a result row, which closes `pending`. `Suite.fail()` only appends to `out['failures']` and logs. `run_long_generation()` records an ineligible request and proceeds through the remaining workloads and later suite phases. Thus the completed request result is already useful compact failure evidence, but it does not stop the next request.

At normal completion, `main()` writes `results.json` and marks the request journal complete. On an exception, it only writes journal state `terminal='interrupted', complete=false` and re-raises; the full suite result is never materialized. For a fail-fast request error, the desired terminal state is `failed`, not `complete` or generic `interrupted`, and the failed request must have a terminal journal row so `pending=[]`. Do not mark the suite complete just because its request journal is structurally valid.

`serve/server.py` intentionally returns an engine failure with wording that the next request restarts the engine; `StrataEngine.restart()` is existing recovery behavior. The official wrapper `run_server_job.py` runs `bench.sh` to completion and then gracefully stops the server. The clean-arm controller `check_prompt_direct_bench_v1.py` calls `good(record)` (`passed && complete && !active`) for Direct0 before it creates Direct1 output. It additionally checks binary identity, fresh faults/dump/boot, owner closure and owner identities. This is already a sound fail-closed pair gate: failed Direct0 correctly prevents Direct1 from launching.

The selected `engine_wrapper_v3.py` writes a single `engine-start.json` and `engine-exit.json` using `write_text`. Every server restart starts the wrapper again and replaces those paths, so they represent only the latest lifecycle, not the earlier failed native. The wrapper does retain the individual native exit in the file it last wrote, but loses prior starts/exits from the measurement evidence.

Minimal opt-in blueprint

1. Add a benchmark-client option, default OFF, such as `--fail-fast-engine-error`. It must be an explicit field in the bench command/record and be passed only by Main’s formal measurement recipe. Keep ordinary `bench.sh` and server defaults unchanged. In this mode, classify a server/native error (SSE error event, HTTP 5xx, transport closure/incomplete response tied to engine death, or watchdog/native nonzero recorded by the owner) as fatal. Do not classify a valid completed-but-ineligible workload sample as a native error merely because it misses output length/MTP eligibility.

2. Keep request journal ordering: fsync `start`; after a returned API failure, fsync exactly one `result` row containing the request digest, compact response/error classification and available progress/sample fields; this clears `pending`. Then record the first fatal failure in the suite state and abort before issuing another request. If transport interruption prevents receiving a response, append exactly one `interrupted` terminal row with the error and request identity. Never append both `result` and `interrupted` for one request. Persist `terminal='failed'`, `complete=false`, `qualified=false`, and an explicit fatal reason. The hash chain and `verify_request_journal()` should remain valid with no dangling pending request for a handled failure.

3. In the suite exception/fail-fast path, persist a compact partial `results.json` (the successful samples already accumulated, failed request and phase, failure class, `complete=false`) before propagating nonzero status. Also preserve the journal and outer controller record. This is needed because current `main()` only serializes the aggregate after `suite.run()` returns; otherwise the first two samples survive only in journal rows and the failed pair is harder to review. The individual samples remain original results, not a qualified benchmark.

4. The absence of a subsequent request after fail-fast already prevents the current “next request restarts” path in the common case. If the controller needs a stronger guarantee, pass a measurement-only server setting from the owned job config that disables *automatic recovery for the remainder of that measurement server process* after a native death. Default it to enabled and leave normal server behavior untouched. In the disabled mode, return the usual request error, remain stopped, and do not start another engine. Do not toggle process environment after SYCL/provider initialization. The benchmark option should still stop immediately; a later diagnostic/retry must be a separately owned process with a new explicit recipe and receipt, never an automatic retry inside the failed formal arm.

5. Replace overwrite-only engine lifecycle files in the measurement wrapper with a compact append-only JSONL identity ledger plus derived counters in the outer receipt. Each start and exit record needs a stable instance key (boot ID, native PID and start ticks), wrapper PID/start ticks, binary hash, argv/config identity, UTC start/finish, exit code, and whether a watchdog/native error was observed. Append and fsync each small record; set a modest count/byte cap and fail closed on overflow rather than truncating history. An unmatched start remains visible as an unresolved lifecycle. Store no API bodies or token text. Keep server recovery available in its ordinary default mode.

6. Keep the existing owner model: the unreaped direct child/session leader anchors ownership until the final scan and closure proof; signal only pinned pidfds; never use `killpg`, infer ownership from a reaped SID, or rescan a numeric SID after its leader has been reaped. Close the original owner after the failed run, wait for its direct child, confirm its session empty and record the result, then take the fresh fault/dump/boot receipt. Do not launch Direct1 while that closure and the failed Direct0 record are pending.

Pair preservation and independent diagnostics

Freeze the formal OFF/ON pair receipt identity at launch. On this failure, Direct0 remains `passed=false`, `complete=false`; no Direct1 speed comparison exists, and no A/B completion or performance claim is valid. Retain the individual completed requests plus the failed request/error and lifecycle/fault facts. Do not re-label a later same-binary recovery sample as completion of the failed third request or as a continuation of the formal suite.

After owner closure and the fault review, Main may lift the source/binary freeze for a truly independent diagnostic only by creating a separate run identity, owner directory, recipe/source/binary pins, and result receipt. Mark its scope `diagnostic only`, `unpaired`, `not performance-qualified`; it cannot satisfy the Direct0 gate or authorize a Direct1 pair. Any diagnostic retry is explicit and gets its own request count and lifecycle ledger. This preserves the failed formal arm while allowing distinct investigation.

Independent host-only acceptance cases for an implementation

- A fake API returns two successful long-generation responses, then an SSE/native error on request 3. Assert exactly three requests were sent; rows 1–3 are durable and hash-valid; no request 4 begins; rows 1–2 retain individual values; row 3 retains the fatal error; pending is empty; journal terminal is `failed`, incomplete and unqualified; top-level partial result is also incomplete/failed; controller exits nonzero.
- A 503-before-stream and an abrupt transport close after request start each create one terminal failure row (result or interrupted respectively), never a stranded pending request or duplicated terminal row, and stop before the next request.
- A fully completed response that is merely below long-generation eligibility remains a workload failure/ineligible sample, not a fabricated engine error. Verify the default no-option suite behavior stays unchanged.
- In a fake server harness, default configuration still restarts on a later request after native exit; measurement-only no-recovery mode returns the error without starting another engine. A separate new process can explicitly start for a later diagnostic.
- Two simulated wrapper/native lifecycles produce two retained start/exit pairs and counters; an abnormal exit remains visible; a cap overflow errors without erasing the first lifecycle. No API payload is present in the ledger.
- The pair gate continues to reject a failed/incomplete Direct0 receipt and any diagnostic-only receipt. A complete healthy Direct0 with exact identity/owner/fault gates remains eligible for the pre-existing Direct1 path.
- An owner fixture with a living descendant after direct leader exit cannot report closed; a correctly owned run closes via pinned identities and final pre-reap session observation, with no process-group signal and no post-reap SID scan.
