## What M2D/D2M mean

In the pinned unitrace source (`intel/pti-gpu` revision `6c0d6b0b80c6dbac4b5902d9d5ade1c75b9e9033`), `AppendMemoryCommand` calls `zeMemGetAllocProperties` for the source and destination, maps `ZE_MEMORY_TYPE_HOST` and `HOST_IMPORTED` to `H`, `DEVICE` to `D`, `UNKNOWN` to `M`, and `SHARED` to `S`, then forms the direction name from those two pointer classes (`tools/unitrace/src/levelzero/ze_collector.h:3792-3794,5013-5098`; names at `:402-450`). Therefore:

| unitrace label | Source pointer class | Destination pointer class |
|---|---|---|
| `M2D` | Level Zero `ZE_MEMORY_TYPE_UNKNOWN` | device allocation |
| `D2M` | device allocation | `ZE_MEMORY_TYPE_UNKNOWN` |
| `H2D` / `D2H` | host allocation / device allocation, respectively | device / host allocation |
| `S2D` / `D2S` | shared ownership allocation / device allocation, respectively | device / shared ownership allocation |

Thus `M` does **not** mean “system RAM”, managed memory, or shared USM. `S` is the shared-allocation class. The official Level Zero specification defines `UNKNOWN`, `HOST`, `DEVICE`, `SHARED` and `HOST_IMPORTED` separately; it also says unrelated-context queries can return `UNKNOWN` ([`ze_memory_type_t` and `zeMemGetAllocProperties`](https://oneapi-src.github.io/level-zero-spec/level-zero/latest/core/api/apis/mem.html)). For these Strata operations, source code independently identifies several `M` endpoints as ordinary host `new[]` buffers. That establishes the application-side allocation path, not a physical memory location, page state, fabric path, or PCIe byte count. The pinned KV backing instead comes from `cudaHostAlloc` mapped to SYCL `malloc_host`, and its stage destination is device USM (`src/core/layer.cpp:633-662`; `src/sycl/runtime.cpp:159-163`).

Unitrace appends the intercepted `zeCommandListAppendMemoryCopy` `*psize` to the event name; the operation metadata's `provider_requested_bytes` and size histogram therefore sum requested API lengths, not measured wire bytes (`ze_collector.h:1160-1190,5110-5130`). GPU event duration is device-side operation service; CPU `zeCommandListAppendMemoryCopy` duration is submission/API cost, while `zeCommandListHostSynchronize` is a host wait. They are separate measurements.

## Four copy groups and source reconciliation

All values below are API-requested lengths from the validated compact summary. “Exact” means the complete size histogram equals the source-derived logical copy lengths for that owner; it does not assert PCIe bytes or physical transfer placement.

| Device copy type | Calls / bytes | Source-derived accounting |
|---|---:|---|
| `M2D` | 25,439 / 109,754,670,264 B | 24,576 packed-expert fills exactly 50,292,326,400 B, plus 376 host-tail residual reloads exactly 58,727,710,720 B; 487 other calls / 734,633,144 B remain unattributed to a specific source owner. |
| `D2M` | 389 / 58,727,711,492 B | 376 host-tail residual stores exactly 58,727,710,720 B, plus 13 small calls / 772 B (twelve 64-byte and one 4-byte copies). |
| `H2D` | 393 / 2,222,886,912 B | 384 KV-prefix-stage transfers exactly 1,868,562,432 B; eight 41,943,040-byte transfers and one 18,780,160-byte transfer (354,324,480 B) are not mapped here to a specific prefill owner. |
| `D2D` | 400 / 17,115,676,672 B | 94 residual copies exactly 15,770,583,040 B (47 GPU-prefix stores plus 47 reloads); another 306 calls / 1,345,093,632 B are not assigned to this residual owner. |

The residual ledger follows the current FP32 source path. The model's residual row is 10,240 floats, or 40,960 B. Of 34,603 rows, 4,096 are GPU-backed and 30,507 are host-backed. For each of 47 inter-layer boundaries, seven full 4,096-row host chunks and one 1,835-row tail are stored and reloaded:

`47 * (7 * 167,772,160 + 75,120,640) = 58,727,710,720 B` per direction.

The compact histogram contains precisely 329 copies of 167,772,160 B and 47 of 75,120,640 B in both `M2D` reloads and `D2M` stores. The GPU-backed 4,096-row prefix is `167,772,160 B` per boundary; 47 stores plus 47 reloads give `15,770,583,040 B`, matching the 94 `D2D` copies. `src/prefill/layer_major.inc` writes the output chunk to the GPU prefix or host tail and drains it; `src/prefill/prefill.cpp:1664-1691` reloads that span at the next layer. Those paths are explicit host/device or device/device copies. The small 772 B D2M excess is separately retained rather than forced into the residual ledger.

The packed expert path uploads all 512 expert blobs once for each of 48 layers through `ExpertCache::fill_slot` (`src/prefill/layer_major.inc:305-325`; `src/core/expert_cache.cpp:358-378`). The actual histogram has 24,576 calls. Its seven size buckets sum exactly to the indexed `native_experts.txt` layer payload total of 50,292,326,400 B. `copy_blob` first fills a normal host upload slab; then `cudaMemcpyAsync` copies each expert to its active device slot. This is a source-proven host-to-device operation whose source pointer is reported by unitrace as unknown (`M`), not proof that all `M2D` traffic is host memory.

The KV-prefix-stage ledger is also source-verifiable. For each of 12 streamed QSA layers and each of eight nonempty prior-chunk prefixes, `kv_stage_from_host` copies the four INT8 K/V code/scale arrays from the layer's pinned host backing into the full-range device stage (`src/prefill/prefill.cpp:2110-2118`; `src/kernels/sycl/kv_stream.cpp:301-315`; `src/core/layer.cpp:633-662`). The source has four `q.memcpy` operations per prefix; the H2D histogram has 384 calls. Prefix lengths total `4096 * (1+...+8) = 147,456` token rows per QSA layer. At 1,056 B per token row, `147,456 * 12 * 1,056 = 1,868,562,432 B`, matching the first 16 H2D histogram bins exactly. This is repeated per-chunk prefix staging, distinct from appending new K/V.

New QSA cells are appended by kernels, not by `zeCommandListAppendMemoryCopy`. The supported INT8 branch passes both `&st.host` and the staging pool to `kv_append` (`src/prefill/prefill.cpp:2123-2138`; SYCL implementation `src/kernels/sycl/kv.cpp:114-152`). At the request size, the K/V code-plus-scale payload is `34,603 * 12 * 1,056 = 438,489,216 B` per destination across all QSA layers; this is a logical payload scale for host mirror and stage writes. The active-slot write is conditional on the page's current residency mapping (`page >= 0` in `kv.cpp`); mode-1 states start with no resident blocks (`src/core/layer.cpp:684-687`), so the configured 32,768-slot capacity is not evidence that all 32,768 cells were resident or that append wrote that many bytes to slots. These are device-kernel stores (including writes to mapped host backing), not copy-API bytes. They must not be silently added to the unitrace copy histogram or interpreted as measured bus traffic.

Across the four GPU-copy categories the requested lengths total 187,820,945,340 B. The source-mapped categories above total 185,386,893,312 B; the remaining 2,434,052,028 B spans the M2D, H2D and D2D residual buckets plus 772 small D2M bytes. Because this capture encloses restore and one decode as well as prefill, and has no allocation-address/range map, the remaining operations cannot be assigned safely to prefill. Keep them explicitly unclassified.

## Duration, ordering and limits of the inference

The compact summary reports M2D 27.401 s, D2M 11.901 s, H2D 0.562 s, and D2D 0.103 s of event service; the all-copy visible interval union is 39.950 s. Compute service is 100.154 s, visible GPU busy union 140.105 s, and compute/copy interval overlap 1.690 ms. The host made 2,456 `zeCommandListHostSynchronize` calls with 75.700 s summed duration; host waits overlap GPU-busy intervals for 75.147 s. These API waits are not extra transfer time, and host wait duration cannot be treated as removable idle time.

The layer-major admission requires `m.copy == m.cs` (`src/prefill/layer_major.inc:45-53`); the SYCL compatibility path submits `cudaMemcpyAsync` to `queue(st)`, and the runtime compute queue is in-order (`src/sycl/compat.cpp:258-263`; `src/sycl/runtime.cpp:45-52`). This ties the normal layer-major source sequence to one in-order queue, but unitrace's engine lane is not a queue-handle identifier. `kv_stage_from_host` also waits for its last event before returning. Do not infer broad transfer/compute overlap from names or durations alone.

The measured copy share and 39.950 s copy union do not establish PCIe saturation or a PCIe-bound prefill. `M` is an unknown pointer type, `D2D` is not host traffic, host-memory mirror writes are kernels rather than copy events, and copy/event lengths are requested bytes. The profile also contains non-prefill phases, host queue/API waiting, and substantial uncovered intervals. A PCIe bottleneck claim would need classified allocation endpoints for all material copies, a clean prefill bracket, and link/engine evidence tied to this same run. None is provided by this profile or report.

## Evidence needed for the next decisive diagnosis

1. A compact per-operation allocation map that joins copy source/destination addresses or ranges to the application's owner and Level Zero allocation type, with lifetime/generation; unitrace's current JSON does not emit those addresses.
2. A clean, exact prefill-only window (or trustworthy in-process boundaries) that separates startup/state restore, prefill, decoder restore and one-token decode while retaining the same long input and session configuration.
3. Direction- and engine-specific link evidence or an independent transfer benchmark/telemetry on the same B570 run, plus queue/event dependencies. API byte counts and summed event durations cannot provide effective PCIe bandwidth.
4. If evaluating hidden-tail removal or KV staging, compare matched source-backed transfer inventories and whole-path completion time; include host mirror kernel stores, synchronization, allocation setup and numerical/correctness gates. This R681 audit did not run that comparison.
