# R825 — Independent adversarial accuracy screens for direct-16 GEMM output

Purpose: decision support. Scope: two independent numerical screens; no implementation or runtime validation.

## Decision scope and evidence boundary

This note adds a numerical screen after the already source-reviewed R810 vLLM Xe2 BMG AOT kernel. Main reports that its kernel has local FP32 accumulation and direct FP16/BF16 output, with smoke32, guards26, strictspecial16, chain8 and full120 all PASS; the paired performance measurement is executing. Those results are useful mechanical and regression evidence, but the exact dyadic/rank2 inputs do not expose long reduction behavior or difficult cancellation. Nothing here changes or replaces those checks, changes their status, or proposes an inference-quality threshold.

R783 already separates input, accumulator and output types and warns that an API signature does not establish accumulator precision. R805 explains how to establish the selected lowering and its operand types. R817 limits what an ISA listing can prove. This scope is the missing independent numerical question: for exactly representable 16-bit operands and a high precision real-dot oracle, what cases reveal order sensitivity and final 16-bit conversion behavior?

The IGC DPAS description specifies `D = C + A x B`, 16-bit HF/BF operands and a 32-bit floating-point `Src0`/`Dst` accumulator path, with successive systolic stages. The SYCL matrix extension lists BMG G21/G31 combinations with FP16 or BF16 A/B, FP32 C and 16-bit D. These establish typed intent / advertised combinations. Neither document specifies the exact partial-sum order, every intermediate rounding point, overflow behavior, NaN payload, or subnormal handling of this particular BMG AOT binary. A `FP32` accumulator type is not a claim that every multiply, pairwise dot, stage boundary and tile merge follows one specified scalar FP32 sequence.

## Recipe 1 — Long-K cancellation, exponent spread and accumulated small terms

Use two independent GEMMs, one FP16 and one BF16, with `M=N=16`, `K=65536`, row-major A[M,K], B[K,N], C=0, alpha=1 and beta=0. Repeat each constructed A row and each B column so every output is the same scalar dot product; this keeps a full matrix tile while making the oracle simple. If the actual entry has a documented K limit, use its largest legal aligned K and recompute counts and oracle values instead of padding an unsupported request and calling it a pass. The proposed K is divisible by common 16/32 inner tiles, but R825 does not establish BMG support for this exact shape.

Use only ordinary normal finite operands for this recipe, shared by both formats: `1`, `2^14`, `2^-14`, `2^4`, `2^-10`. Set per-index A and B so the products below are exact powers of two in FP32 as well as in the 16-bit input formats. This avoids relying on input subnormal behavior. For every case, generate two or more permutations with the same multiset of products and compare their output. The independent reference decodes each 16-bit input to an exact signed significand times a power of two, multiplies exactly, aligns exponents with a big-integer dyadic accumulator, and sums exactly. A 128-bit-or-wider MPFR oracle also suffices for these bounded exponents; do not use device FP64 as the only oracle unless its exactness for this range has been checked.

**Small-term/order pair.** For all K except one or two marked positions, set `A[k]=2^-14`, `B[k]=2^-10`, giving `2^-24`. In pattern L, put a `1` product at k=0 by using `A=2^-14, B=2^14`; in pattern L-reversed, put that same pair at k=K-1. The exact sum in both is `1 + 65535*2^-24`. For a second same-multiset pair, add one `2^-10` product (`A=2^-14, B=2^4`) and use 65534 `2^-24` products. Put the `1` and `2^-10` first in one ordering and last in the other. Its exact sum is `1 + 2^-10 + 65534*2^-24 = 1.0048826932907104`. Under one illustrative sequential round-to-nearest FP32 order, a `2^-24` increment added repeatedly to `1+2^-10` is a half-ULP tie and can keep rounding to the same even value; grouping the tiny terms before the large terms can preserve them. This is a sensitivity example, not a prediction of DPAS order or a claim that a different valid sum order is wrong. The exact once-rounded outputs for the latter sum are FP16 `1.0048828125` and BF16 `1.0078125`, assuming round-to-nearest-even narrowing.

**Cancellation/mixed-exponent pair.** In both patterns make 16,384 products `+2^14` (`A=1,B=+2^14`), 16,384 products `-2^14` (`A=1,B=-2^14`), and 32,768 products `2^-24` (`A=2^-14,B=2^-10`). Pattern C1 orders positive block, tiny block, negative block; C2 orders positive block, negative block, tiny block. The exact result for both is `32768*2^-24 = 2^-9 = 0.001953125`; the sum of product magnitudes is about `2^29`, so the relative condition number is about `2^38`. A scalar sequential FP32 sum can discard all tiny increments while the partial sum is near `2^14`, then cancel to zero in C1; C2 cancels the large terms first. Again, this demonstrates order sensitivity and conditioning, not a DPAS defect. It makes the error scale visible without using input quantization as a confounder.

For each output, retain the exact real dot S, exact `sum(abs(a[k]*b[k]))`, FP16/BF16 once-rounded S, actual 16-bit bits, absolute error, ULP distance to once-rounded S, error divided by `sum(abs(products))`, and between-permutation spread. Higham's analysis shows that summation order and algorithm affect accuracy and that no method is uniformly best; his standard `gamma_n`-style bounds assume a particular floating-point operation model and no underflow. A sequential FP32 bound of roughly `gamma_K * sum(abs(products))`, where `u=2^-24`, is only a contextual comparison if every add follows that model and products are exact. It is not a published bound for this DPAS kernel, nor a meaningful universal pass tolerance for the deliberately ill-conditioned cancellation case. Do not fail the kernel merely because C1 and C2 differ or because the result differs from one scalar order. Treat unexpectedly large error, wrong sign/category, or a discrepancy inconsistent with the exact typed path as a characterization requiring binary/contract review.

## Recipe 2 — Output range, narrowing and special-value classification

Use `M=N=16`, `K=32`, C=0, alpha=1 and beta=0 for each format, repeating a single constructed dot across rows and columns. Fill unused k positions with `A=B=0` so they contribute finite zero. Compare finite sums to an independent exact-dyadic oracle, then to a software conversion oracle for the intended destination format and rounding mode. This test isolates final narrowing from long reduction effects because its finite examples use only a few exactly summed terms.

For FP16, with A terms equal to 1, case Hmax has one B term 65504 and must reach the largest finite binary16 value in an IEEE round-to-nearest conversion. Case Hover has B terms 65504 and 32, whose exact FP32 sum is 65536, safely beyond the binary16 overflow boundary; record whether output is infinity or max-finite rather than presuming a saturation instruction. Test both signs. For BF16, with A=1, use B terms `max_bf16 = 2^128 - 2^120`, `2^119`, and `2^116`. Their exact sum is `2^128 - (7/16)*2^120`: finite and exactly representable in FP32, but above the midpoint from largest finite BF16 to the next exponent value. Under round-to-nearest-even narrowing the expected category is positive infinity; the negative construction tests negative infinity. This checks that output conversion behavior is not inferred merely from the shared FP32 accumulator type. The Khronos Intel BF16 conversion extension defines its own float-to-BF16 conversion as round-to-nearest-even, but that OpenCL conversion contract does not automatically specify the instruction sequence in this SYCL AOT kernel.

Run three special-value cases separately for each input format: (a) quiet NaN times 1, (b) positive infinity times 1, and (c) positive and negative infinity terms summed together. Use raw quiet-NaN and infinity encodings in one lane and ones in the matching B lanes; all other A/B lane pairs are zero/zero, avoiding accidental `0*infinity`. Compare only `isnan`, `isinf` and infinity sign. Do not compare NaN payloads or demand identical NaN bits. These are probes of the implemented DPAS and conversion path; the cited DPAS description does not promise payload propagation or exact NaN handling. If the device reports optional half `inf_nan`, denormal and rounding capabilities, record those too, but capability query results alone are not a kernel-level special-value guarantee.

## Reading results and preserving the contract

Keep both recipes as a new, separately named adversarial screen. Preserve the prior 68-test and qualified special-case contract verbatim; do not turn this screen into a global epsilon, loosen existing thresholds, or combine its status with the old gate. For finite cases report exact-oracle errors per construction and per dtype; for special cases report classification counts. A mismatch against once-rounded exact S identifies accuracy lost between real dot and stored output, but unless the kernel's operation ordering and rounding contract are specified it does not by itself distinguish permitted FP32 order effects from unexpected internal behavior. A mismatch in Recipe 2 is less confounded because its finite inputs sum exactly in FP32, but still characterize it against the active binary's output conversion contract before calling it a conformance failure.

This is a GEMM quality screen, not a model-quality decision. After any numerical characterization, model-quality acceptance still requires Main's separate natural-input/task-quality evidence and performance decision. It does not change the running paired performance measure and requires no alteration to the R810 source proposal or prior receipts.

## Explicit evidence limits and sources

**Documented:** IGC DPAS defines operand/accumulator type roles and stage semantics; Intel's SYCL extension lists BMG architecture combinations including FP32 C and FP16/BF16 D; Khronos's Intel BF16 conversion extension specifies RNE for its defined OpenCL conversions. **Published numerical analysis:** Higham describes the dependence of summation accuracy on ordering/algorithm and the assumptions behind standard rounding bounds. **Unknown for this BMG binary:** internal sum tree, per-stage rounding, product exactness beyond the typed instruction model, subnormal behavior, NaN/Inf behavior and direct-store overflow conversion. Intel's architecture table is not an accuracy guarantee for every BMG device/compiler, and a generic DPAS description does not establish this binary's numerical conformance. Do not claim BMG accumulation is exact, that it uses scalar left-to-right FP32, or that a different valid order is information loss. **Model quality:** neither these docs nor a standalone GEMM oracle establish model task quality.
