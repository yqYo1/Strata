## Three dispatch designs

| Design | Work assigned to device | What stays on host | Variable expert map and partial chunks | Principal tradeoff |
|---|---|---|---|---|
| **Persistent device-side tile queue** | A bounded worker kernel claims ready descriptors (expert, projection, row/tile span, weight slot, global token base) and performs the existing GPU math. | Prepare/validate and upload descriptors/weights; launch, retain owners to completion. | Dynamic map and exact/tail row counts are data. Preallocate maximum queue, check overflow and preserve output ownership. | Can remove per-expert/tile submissions and balance irregular jobs; adds atomics, indirection, random weight access and long-kernel occupancy risk. A prefilled queue needs no inter-group spin barrier. |
| **Indirect or batched command list** | Existing GPU kernels; one list can contain many launches and an indirect launch can read grid counts from device memory. | Encode/select commands and arguments, submit/update lists, prepare routes and weights. | Host lists still need rebuilding for changed active experts unless a generic kernel reads device descriptors. Indirect grid counts handle tile count only; tail masks remain required. | Amortizes submits while retaining kernel boundaries; may leave per-expert host encoding intact. A changed count does not create a new command topology. Immediate append differs from deferred list execution. |
| **Graph replay with dynamic data** | Replay a fixed operator DAG over new tensor data; a generic MoE node can read a stable pointer to per-window route records. | Upload routes/weights, choose a captured shape key, update supported arguments, enqueue and retain owners. | Route differences must be data inside a generic node or one of predeclared alternatives. Tail handling needs padded masked rows, supported range update, another capture key or eager fallback. | Cuts repeated submission for a recurring DAG; data transfer, keys/updates, experimental API and graph lifetimes remain costs. |

These approaches act at different levels. A device queue reduces per-job host dispatch; command-list batching reduces API submissions while keeping an encoded list; graph replay replaces repeated submissions of the same dependency DAG. A graph could replay a persistent-queue kernel, but that combination still needs evidence and inherits both mechanisms' lifetime and runtime constraints.

### Persistent queue: progress and occupancy are the safety gate

SYCL 2020 revision 12 guarantees only weakly-parallel work-item progress; stronger progress is implementation-defined. Its extra barrier guarantee is within one work-group. It does not promise one group will run while another spins, so do not derive a safe resident-group count or global barrier from an assumed occupancy model.

A bounded queue prefilled by the host (or by a producer kernel ordered before the consumer) avoids producer/consumer spinning across groups: workers independently claim ready jobs and exit at the bounded end. Avoid a global barrier and any worker waiting for another group to publish. If jobs depend on a prior wave, end the kernel and express an event/queue dependency for the next stage. A Level Zero cooperative launch is conditional on a queue group advertising support and a queried maximum group count; it is not a portable SYCL default.

Too few workers can underfill the device; too many can run in waves, while registers/local memory reduce active groups. A global ticket can serialize, and random expert IDs can hurt weight locality. These are B570 measurement questions, not facts derivable from nominal topology. Cancellation also needs an owner rule: no kernel/graph preemption is assumed. Either establish device-visible cancel semantics or stop at a kernel boundary, wait for completion, invalidate partial output/state, then reclaim queue, upload and weight storage.

### Indirect / batched commands: grid indirection is narrower than dynamic scheduling

Level Zero 1.18.31 regular lists record a sequence and close before execution. Immediate lists create an implicit queue for low-latency append; appends may execute synchronously. `zeCommandListAppendLaunchKernelIndirect` reads device-visible grid counts, so a prior device operation can choose dimensions. It cannot create arbitrary commands or select unknown kernels.

Batching expert-specific launches still costs host list/argument work when routes change. A generic kernel over device route descriptors is more flexible but approaches the persistent-queue design. Batching a small fixed sequence may help if host submit gaps are measured; it does not guarantee faster kernels. A SYCL queue alone does not prove the actual list mode, and current calibration has not isolated host submission as a limiter.

Do not reset/reuse command lists or storage until device references retire. Keep host route/weight upload bytes immutable through copy completion. Every partial chunk needs true rows and base; padded rows must be masked before writes/reductions, and expert lists must preserve all and only routed rows.

### Graph replay: data may vary while dependencies stay fixed

Intel's `sycl_ext_oneapi_graph` is experimental. Dynamic parameters update kernel args (including USM pointers/scalars), but executable updates do not change graph structure or edges; all uses of a new buffer pointer must be updated coherently. An update may block for an in-flight execution. Dynamic command groups are limited to kernel/host-task nodes with identical dependencies.

Native recording is stricter: the L0v2 path requires one in-order queue backed by an immediate list, graph update is unsupported, and captured events are graph-scoped. Ordinary SYCL recording does not capture arbitrary host work. Native backend recording has explicit interoperability rules; do not assume direct Level Zero commands enter every graph mode. The spec also does not make copy-node argument updates a general dynamic-parameter facility. Weight uploads can remain outside replay with an explicit dependency and retained source lifetime.

A route-flexible graph can use a stable pointer to a device buffer of per-window descriptors, but the descriptors still need creation/upload or an ordered GPU producer. Per-expert graph nodes can require new keys for random maps and tails, with more capture/memory cost. Practical LLM engines show this tradeoff: vLLM keys CUDA graphs by padded batch descriptors and falls back FULL→PIECEWISE→eager; SGLang XPU documents full decode and breakable prefill, with prefill capture opt-in. These PyTorch/CUDA/XPU patterns do not establish oneAPI graph support or performance in Strata.

Gaudi HPU Graphs provide a static-accelerator counterexample: their guide requires device inputs/stable output addresses and excludes dynamic shapes and data-dependent Python control flow. Values can vary inside fixed device work, but per-request host-created command topology cannot be assumed capture-safe.

## MoE, windowing and 262,144-context invariants

Across all three designs, route construction can remain a compact CPU control task while expert tensor arithmetic stays on GPU. The control format must retain exact expert identity, source/output row mapping, projection kind, row count, chunk/window index and absolute token base. Do not reinterpret a per-chunk row offset as the full prompt position. For a final partial chunk, preserve all valid rows and mask padding in gather, GEMM, output scatter and any accumulation. Dispatch must not alter the model's route choices, weight/format, accumulation or round points; a work-stealing order that changes reductions is a numerical change and needs a reference-path comparison, not just a scheduling test.

A two-chunk window's weight upload, route descriptors and outputs must live until all consumers complete. Do not recycle a staging slot after submit returns. For host-to-device copies, freeze the host source until the copy event proves it is no longer read; for graph replay or multiple in-flight windows, use separately owned/versioned slots or explicit dependencies. The current window's safe release/commit boundary still governs reusable buffers and shared recurrent/attention state. Any canceled or failed window must be excluded from checkpoint/RESTORE state. A scheduling queue, indirect command list or graph must not truncate/skip the physical 262,144-context range or make success conditional on a captured length that is smaller than the requested context. These are design obligations, not validated behavior of an alternative.

## What evidence would make one worth studying

No immediate option is selected. First the owner needs a source-pinned attribution from the actual production queue that separates CPU descriptor construction/submission, host wait/poll time, device command service and inter-command gaps for the same complete long-prefill dependency path. The existing 52 ns API timer calibration gives timestamp resolution and basic event-path correctness; its minimum kernel and post-drain query wall time do not answer this attribution question. One saturated host thread would also need to be separated from completion polling, per the project rule.

If that path shows many host command gaps and no dominant compute interval, compare one mechanism at a time against the same binary/route maps. Preserve a compact owner record of submit count and host time, command/kernel device times and gaps, transfer/weight residency, queue/graph update cost, peak live memory and end-to-end prefill. Test with route maps that vary across the combined 8K chunks, both full and partial chunks, and retain all output/state, fault, cancellation, buffer owner and physical-context checks. Feature availability, kernel occupancy/resource use and graph shape-key coverage must be measured on the actual target stack. A lower launch count alone is not a speed result.

## Sources, revision pins and transfer limits

* **Prior MoE design work:** local `research-round985-v1.txt`, SHA-256 `ee96d013e099d9ccbe84411eae3c096d2a31f933ee1605112d40fc05cab84b12`; R985's retrieved grouped/ragged GEMM and persistent scheduler discussion. It is local project research, not source code. It supports avoiding a duplicate GEMM survey; it has no dispatch measurement.
* **SYCL progress contract:** [SYCL 2020 revision 12, section 3.8.3.4](https://registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html). Khronos standard specification. Directly governs portable SYCL progress language; it does not describe B570's undocumented scheduler.
* **Cross-GPU progress evidence:** Donaldson et al., “Forward Progress on GPU Concurrency,” CONCUR 2017, DOI [10.4230/LIPIcs.CONCUR.2017.1](https://doi.org/10.4230/LIPIcs.CONCUR.2017.1), [author-hosted paper](https://johnwickerson.github.io/papers/forwardprogress_concur2017.pdf), CC-BY. It reports empirical models across older GPUs and large differences in barrier trade-offs. It is not a B570 or current-driver guarantee.
* **More recent progress-model counterevidence:** Sorensen et al., “Specifying and Testing GPU Workgroup Progress Models,” OOPSLA 2021, DOI [10.1145/3485508](https://doi.org/10.1145/3485508), [arXiv record](https://arxiv.org/abs/2109.06132). Rights retained; no source code reused. Its eight-GPU/five-vendor litmus campaign found progress behavior differed, including failures of an occupancy-bound model on Apple and ARM. This cautions against porting occupancy assumptions, rather than proving Intel B570 behavior.
* **Persistent-thread trade-offs:** Gupta, Stuart and Owens, “A Study of Persistent Threads Style GPU Programming for GPGPU Workloads,” InPar 2012, DOI [10.1109/InPar.2012.6339596](https://doi.org/10.1109/InPar.2012.6339596), [UC eScholarship record](https://escholarship.org/uc/item/3j76d3td). IEEE paper; no code reused. It frames load balancing, CPU-GPU synchronization, locality and global synchronization as use cases, and reports both up-to-order-of-magnitude wins and regressions across microkernels. Its workloads/GPUs are not LLM MoE or B570.
* **Level Zero commands:** [Level Zero specification 1.18.31, Command List](https://oneapi-src.github.io/level-zero-spec/level-zero/1.18.31/core/api/apis/command_list.html). The `zeCommandListAppendLaunchKernelIndirect` entry is core v1.0. The cited 1.18.31 spec documents regular and immediate list semantics; this is not proof of support in the supplied driver/runtime. The official `oneapi-src/level-zero` headers/loader repository is MIT; no API implementation was copied. The API docs establish parameters and requirements, not adapter/device support or performance.
* **SYCL Graph contract:** Intel LLVM graph spec pinned to [`intel/llvm` commit `3655fb6719eb82da79c317b49aff7f7fdf9ac496`](https://github.com/intel/llvm/blob/3655fb6719eb82da79c317b49aff7f7fdf9ac496/sycl/doc/extensions/experimental/sycl_ext_oneapi_graph.asciidoc); companion [usage guide at the same commit](https://github.com/intel/llvm/blob/3655fb6719eb82da79c317b49aff7f7fdf9ac496/sycl/doc/syclgraph/SYCLGraphUsageGuide.md). Intel LLVM code is Apache-2.0 with LLVM exceptions, but this report copies no code. The extension itself calls its API experimental and documents varying backend support; exact compiler, adapter and device support must be probed.
* **Practical LLM graph dispatch:** vLLM `docs/design/cuda_graphs.md` at commit [`5be4266f5c7c10c69e4be5f3ec01d6a1d8bae9a1`](https://github.com/vllm-project/vllm/blob/5be4266f5c7c10c69e4be5f3ec01d6a1d8bae9a1/docs/design/cuda_graphs.md), Apache-2.0. Useful for shape-key dispatch, full/piecewise modes and eager fallback; CUDA/PyTorch capture is not a SYCL result.
* **Practical Intel XPU LLM graph:** SGLang [XPU hardware guide at `main` revision `44be30d`, read 2026-10-17](https://github.com/sgl-project/sglang/blob/44be30d/docs/docs/hardware-platforms/xpu.mdx), Apache-2.0. It documents device-specific phase capture, shape buckets and a disabled-by-default prefill graph path. This is an XPU serving stack, not Strata's C++ queue or current B570 feature attestation.
* **Accelerator static-graph limit example:** Habana, [Inference Using HPU Graphs, Gaudi docs 1.24.2](https://docs.habana.ai/en/latest/PyTorch/Inference_on_PyTorch/Inference_Using_HPU_Graphs.html). Vendor documentation; no code reused. It says graph replay needs device inputs/stable output addresses and excludes dynamic shapes/data-dependent Python flow. This is an HPU constraint, included as counterevidence to assuming all accelerators provide general dynamic command graphs.
* **GPU-driven task scheduling reference:** NVIDIA, [“Advancing GPU-Driven Rendering with Work Graphs in Direct3D 12”](https://developer.nvidia.com/blog/advancing-gpu-driven-rendering-with-work-graphs-in-direct3d-12), original engineering blog (read 2026-10-17; NVIDIA-specific article, no code copied). It describes device-generated work-graph nodes as a way to avoid a CPU round-trip for dynamic shader work. The article's availability is specific to supported NVIDIA D3D12 GPUs and shader stages; it is an architectural analogy, not a SYCL/Level Zero API or port source.

No source establishes that any of these mechanisms is implemented, supported, or faster in this Strata build. The report contains no B570 dispatch measurements, no new code, and no recommendation to adopt a scheduler.
