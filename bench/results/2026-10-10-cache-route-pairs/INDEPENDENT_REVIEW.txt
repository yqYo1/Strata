# Round 38 — Independent review of the opt-in pair diagnostic

## Verdict

The current frozen header and call-site wiring support a bounded, host-only, per-request count of main multi-token dispatch classifications for the explicitly gated one-stage native 48×512 MTP/spec-split configuration. The counters are attached at the final route-kind classification and reconcile entry-wise with the existing request `DONE` deltas. They do not count CPU jobs, weighted route mass, layer-worker tasks, or traffic. No implementation or runtime qualification is claimed here.

The root cancellation correction makes a canceled/unexpected-finish request incomplete even when partial counters happen to reconcile. Two review issues remain before using frames as a complete data source: strict invalid-env parsing throws an uncaught `std::runtime_error`, and the wire `error=1` field conflates cancellation with dispatch/diagnostic errors. Neither issue changes the correctly computed successful-request counts, but both affect failure interpretation and operation.

## Supported source behavior

- `CacheRoutePairs::enabled()` accepts only unset/`0`/`1` and is called before the rest of `main`'s setup (`generate.cpp:1634-1636`). The object is allocated only when opted in (`:4971-4975`). The always-present `ExpertDispatch` addition is a nullable pointer; the multi-dispatch path only has two pointer branches around classification, with no collector allocation or device operation when off (`expert_source.hpp:260`, `expert_source.cpp:2745,2760,2772`). Existing IDs, `kind`, cache counters, row handling and pool job creation are not modified by the collector. This establishes no diagnostic allocation or decision change when off; it does not establish timing neutrality.
- The collector begins after decode scalar snapshots, so prompt work is excluded; it is detached before the report and before `DONE`/the next request's prefill (`generate.cpp:10414-10427,11495-11503`). The runtime gate requires native expert layout, one stage, MTP with split spec-4, no batch/pipeline, no elastic KV/cache, empty adaptation usage, no async adaptation job, no peer/remote expert route, and zero PCIe share (`:10420-10427`). Geometry and exact `host_res` length are separately required by `begin` (`cache_route_pairs.hpp:24-29`). Scalar callbacks while attached mark the collector erroneous (`generate.cpp:984-989`). Unsupported or non-serving/batch entrypoints emit a mode-level `supported=0` line, never a complete pair frame (`:4974-4975`).
- The verifier invokes the pool boundary callback synchronously after boundary readiness, and dispatch returns after CPU jobs finish; the collector is called from that dispatch caller, not from expert worker kernels. `begin` records caller thread identity; `callback` and `entry` refuse non-owner writes through the atomic error latch (`cache_route_pairs.hpp:24-42,79-80`). Actual report also runs on the serving caller after the final `wait_commit` (`generate.cpp:11313-11318,11498-11503`). Host residency is copied at request start and compared byte-for-byte at report; emitted FNV-1a64 is only a joinable fingerprint, while `unchanged` rests on `memcmp` (`cache_route_pairs.hpp:27-28,44-48,82-85`). This is adequate for the fixed no-adaptation scope; it is not a fingerprint of cache weight bytes or model identity.
- For each validated routed entry, the hook uses final `kind`: 0 hit, negative CPU/refused, positive offload. It is placed beside the corresponding original scalar increments (`expert_source.cpp:2752-2773`). A CPU blob failure can occur after its refused count is recorded; the request's `d.failed` must make the frame incomplete. The corrected report call passes that failure plus cancellation and any finish other than `length` or `stop` as incomplete (`generate.cpp:11498-11503`). The collector's equations require `hits == req_hits`, `hits + refused == req_look`, and `offloaded == req_offload`; `look` excludes offloads and in this supported static-cache configuration admissions are absent. Collector overflow, invalid dimensions/IDs, wrong-thread callback, changed residency, dispatch failure, empty entries, or mismatch all block `complete=1` (`cache_route_pairs.hpp:49-61`).
- Sparse output is bounded: exactly 24,576 cells; at most one PAIR line per cell, each below the stated 140-byte bound; even the maximal record set remains below 4 MiB. Arithmetic for all counters/totals is checked; arrays and output order are fixed/ascending. There is no truncate-on-overflow path: `truncated=0` is consistent with the fixed capacity, and unsupported shapes produce incomplete/unsupported output. Producer flushes `stderr` before emitting and flushing `DONE` on `stdout` (`:11500-11503,11521-11528`); the controller still needs to reject missing, duplicate, incomplete, or unmatched frames.

## Defects and limits, prioritized

1. **Invalid environment value is rejected by an uncaught exception (medium).** `CacheRoutePairs::enabled()` throws `std::runtime_error` (`cache_route_pairs.hpp:18-22`), but `main`'s function-try-block only catches `sycl::exception` at EOF (`generate.cpp:12839-12843`). An invalid value therefore reaches `std::terminate` rather than an explicit diagnostic/status path. It does fail before GPU setup, but the report's strict-parsing test only proves that the helper throws; it does not prove the executable rejects cleanly. Recommend an explicit parse-result/error path or a `std::exception` catch that prints an actionable message and returns nonzero. Root's CPU fixture is a direct helper test and cannot cover this production catch boundary.
2. **Frame field `error` mislabels cancellation (medium/low).** In `report`, `error` is printed as `!owner || error_.load() || dispatch_failed` (`cache_route_pairs.hpp:62-63`); root now passes `cancelled || finish-not-length-or-stop` through the `dispatch_failed` parameter (`generate.cpp:11501-11503`). A user cancel with valid partial counts consequently yields `error=1 complete=0`, even when no diagnostic or dispatch error occurred. `complete=0` is correct, but consumers cannot distinguish an expected cancel from corruption/failure. Add a distinct `cancelled`/`finish` or `incomplete_reason` field, or reserve `error` for actual errors. The added cancellation fixture passes `failed=true` to the generic helper, so it proves only that the complete bit is lowered, not the framing's semantic label or production finish mapping.
3. **Fixture validates the accumulator, not production callback semantics or framing parser (low).** The CPU fixture directly calls `begin/callback/entry`, checks selected PAIR substrings and count substrings, and never calls `expert_pool_dispatch_multi`, `drive_pool_multi`, the serving request boundary, or root's controller parser. New repeated-token and repeated-across-callback cases are useful and overlap R36's accounting examples; they do not independently establish that production `kind` and IDs are wired to those values. It does not assert a complete golden BEGIN/RESIDENCY/END stream or test the `finish`/cancel call-site. Root's owned model diagnostic should be the integration gate; broaden a CPU parser/lifecycle fixture only if it is needed to make the collector protocol itself independently falsifiable.
4. **Completeness only means a positive reconciled classification frame, not full workload coverage (low, intentional).** It records a frame-level success for the supported request, but does not prove all expected decode windows/layers occurred or bind model/config/request identity. The controller must join exactly one frame with each corresponding DONE and validate expected target/accepted/output counts, request IDs, command/config/model identity, dimensions, route/hit/refused/offload sums, and normal exit/fault/health. It must reject a missing frame even though the program may exit early before reporting.

## Runtime gates before any policy conclusion

The root-owned test must use a fresh diagnostic-enabled process separate from clean timing results, exact closed H command/model/pack and same workload/request identity, and only the supported single-stage native MTP/spec-split/no-adaptation/no-peer/no-offload mode. Require for every expected completed request exactly one BEGIN, RESIDENCY, and END with matching ordinal, correct dimensions, `supported=1`, `complete=1`, `unchanged=1`, no error, no cancellation, exact equality to sparse PAIR sums, and the three DONE reconciliation equations. Preserve normal exit 0, no forced cleanup/faults/survivors, all-head/all-state/logprob and other existing correctness gates; keep per-request records. Treat current D's original full numerical gate as still rejected and unrelated to this diagnostic. Do not infer benefit from rank, callback-pair counts, or a passing histogram; any cache-policy A/B remains a separate root-owned experiment after the exact per-pair evidence exists.
