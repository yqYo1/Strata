# R144: VTune phase-marker, stdio, and supervision contract

Date: 2026-10-11 (JST)
Scope: read-only source and installed-file review plus Intel documentation. No profiler, model, runtime, GPU, or device command was run; no build/test was run. This is a collection design and admission contract, not a measurement or authorization to launch a profile.

## Decision

For a useful first VTune trace, launch the same server/engine as a child of VTune with XPU Offload collection initially paused. Wait for the engine's normal READY, then resume collection immediately before sending the exact recorded GEN request. This excludes process startup and the initialization path that occurs before READY. Keep the existing request untouched: wait for the usual final PP, then DONE, send normal QUIT, and let the server and VTune finalize normally.

That external-only boundary is approximate. In current source, PP is flushed from the prefill chunk callback after chunk synchronization and the draft/MTP callback, but before Prefill::run completes its final bookkeeping/return. For a common prompt path, bulk prefill handles n_prompt - 1 tokens; the final prompt token is consumed in the first verification window. Thus the last PP does not mean that all prompt work has ended or that decode has begun. An external pause triggered after reading that line races the final prefill tail and can include early verification/decode. Treat such a trace as request-level/phase-nearby evidence, not an exact prefill-only window.

If the question requires an exact bulk-prefill interval with cold decode excluded, add diagnostic-only source ITT pause/resume calls at explicit serving-path boundaries: resume immediately before the prompt Prefill::run work and pause only after the run has completed its queue synchronization, final fold/bookkeeping, and return. Keep stable ITT task/domain markers around host logical phases (for example Strata.Prefill and labels for chunk submit/wait, draft or MTP callback, and final fold). The marker must cover the actual submission thread and phase operations. A named task is only host-side attribution: it neither pauses collection nor establishes a GPU dependency by itself. Confirm with a test trace that the chosen task boundaries appear and device tasks link to their submitter. Keep the patch behind an opt-in diagnostic build/runtime gate; this source instrumentation does not exist in the inspected baseline.

## External CLI and control design

Installed files were inspected statically under /opt/intel/oneapi/vtune/2026.4/; no VTune executable was run. Its analysis configuration defines the xpu-offload alias and exposes itt-domains, user task/event collection, GPU programming API collection, and target-GPU controls. The documented paused-collection flow is -start-paused, followed by vtune -command resume and vtune -command pause against the result. A bounded launch proposal is:

    vtune -collect xpu-offload -start-paused -data-limit=64 \
      -result-dir "$RESULT_DIR" -knob itt-domains=Strata.Prefill \
      -- "$SUPERVISOR" -- "$ENGINE" <exact-frozen-serve-arguments>

This is a proposal, not a command validated against this host. Verify locally that this analysis accepts the knob combination and that result-dir control commands target the launched collection. If using external resume/pause, issue them only after confirming the collection's state and recording timestamps. Do not pass target-pid to attach to a debugger-owned process: launch a fresh target under VTune ownership. Generic VTune attach documentation does not establish that attach is supported for this XPU Offload configuration.

The installed XPU Offload default is CPU ITT plus GPU compute-runtime tracing; API-level tracing can add host overhead. Keep the first pass minimal, allow only the intended Strata ITT domain, and enable programming-API detail only if the initial trace cannot resolve submit/wait boundaries. Do not add GPU Hotspots characterization or hardware counter collection to this pass. Counter presets can require elevated permissions; no privilege, kernel module, device reset, or permission change is in scope. If the needed counter is denied or unavailable, record that fact and stop that pass. A second counter-oriented pass would require separate admission and must not be conflated with this timing trace.

## Stdio and process ownership contract

The server's protocol is line-oriented on engine stdout, with progress/status records and explicit flushes; timing diagnostics use stderr. VTune also emits its own status text. Directly merging VTune's stdout/stderr with engine stdout would corrupt the protocol, and this review did not establish that VTune launch preserves the target's three streams unchanged.

Use a supervisor as the direct VTune child. It must preserve distinct engine stdin/stdout/stderr channels for the existing controller, send VTune/controller output to separately bounded files, and relay engine bytes without rewriting, reordering, buffering across protocol lines, or merging streams. Before any model run, qualify this relay using a harmless short-lived target: prove READY, a sample progress line, and exit status arrive on the expected channels with flush behavior intact, while VTune messages remain separate. If stream ownership or relay fidelity is unclear, do not start the model trace.

The controller owns the engine protocol; VTune owns the launched collection and result directory; the supervisor owns stream relays and bounded logs. Keep PID plus process start time for the wrapper, engine, VTune, and any descendants so PID reuse cannot confuse ownership. Do not send QUIT before DONE. After DONE, send the normal QUIT, wait for engine exit and normal VTune finalization, then verify the result is closed before inspection. A finite wall deadline may prevent an indefinitely hung supervisor, but timeout recovery must preserve the failure status and diagnostic; do not silently kill a live target or label an interrupted run successful.

## Interpreting the trace

A GPU device task linked to a host submitter helps attribute work, but does not alone prove what is on the response critical path. To distinguish hypotheses, look for a complete interval and its dependencies:

- H2D/service limit: transfer intervals consume the relevant window, overlap is insufficient, and queue/request dependencies show the transfer gates the next useful work. The prior quiet campaign measured H2D at 6.446834 GB/s; that isolated number alone does not prove current request critical path.
- Compute-service limit: kernels occupy the interval, compute throughput/occupancy metrics are actually supported and collected, and host gaps are not the dominant wait. Runtime task duration is not an occupancy counter.
- Overlap limit: copy and compute tasks exist but execute serially or leave avoidable gaps; verify queue dependencies and concurrency before proposing a scheduling change.
- Host enqueue/synchronization limit: CPU submit, waits, fences, or synchronization dominate while GPU queues are idle; correlate host call stacks/task regions with device idle intervals.
- Profiler overhead: compare an identical quiet request and the profiled run, record added elapsed time and dropped/partial data, and do not interpret a slower trace as an engine regression. The quiet reference's prefill/decode numbers are not interchangeable with the profile's timing.

VTune's offload view links device tasks to CPU submitter tasks, but idle/overlap views are diagnostic heuristics. Claims about a bottleneck or hardware maximum need supported per-device metrics and an unprofiled correctness/performance follow-up; a successful collection or visible GPU lane is not evidence of achieved maximum occupancy/bandwidth.
