**The grouped APIs dimension each expert's M tiles using the largest expert row count in that launch group.** That creates two distinct costs: whole M-tile work-groups launched but immediately returned for smaller experts, and valid last tiles that still run fixed-shape matrix/dequant work on padded rows. These costs must not be conflated. A count-based partition of each existing ordered expert batch into *contiguous subgroups* can lower max M height and reduce launched empty work-groups without reordering routes, moving output rows, or changing expert ownership. It necessarily trades against extra launch and setup cost. It cannot remove per-expert tail padding. Sorting experts by count would reorder existing rows/weights and is a different, higher-risk design.

## What controls row ranges, tile geometry, and branch selection

`prefill.cpp:1879-1970` builds `m.cnt[e]` from route selections, omits zero-row experts from `order`, puts eligible resident/fusable experts first, and builds prefix offsets `m.off[e]`. Thus each expert owns one contiguous interval `[off[e], off[e]+cnt[e])` in the packed route-row layout. The fallback grouped tail is emitted in batches of up to `g_expert_group` (default 16, source clamp 1..64; `:189`, `:1024`), with `maxr=max(cnt[order[j]])`, `G` and the bounds passed to the grouped product (`:2318-2378`, `:2345`). This maximum—not the sum of the batch's rows—is the M-height bound. The resident native IQ prefix is a different route, grouped by up to `kIqGemmGroup=32`; it admits fusable experts only when `cnt[e] <= kIqGemmTileRows=256` (`:1953`, `iq_kernels.hpp:70-73`).

The resident IQ padded arithmetic fraction may be substantial even with no empty M tiles: for each expert, the last 256-row tile covers `256-cnt[e]` padded row slots. It also still performs the tile's weight dequantization. By contrast, a fallback group with a single unusually large `cnt[e]` can make every other expert in that group launch additional M tiles that branch out, as well as pad each expert's own last tile.

## Exact source-derived counters to distinguish the costs

For one grouped call with positive row counts `c_i`, group size `G`, active output-column tile count `nN`, and effective M tile `WM`, define `q_i=ceil(c_i/WM)` and `qmax=ceil(max(c_i)/WM)`:

- Launched M work-group slots: `G * qmax * nN`.
- Active M-tile work-groups: `sum(q_i) * nN`.
- Whole work-groups launched and immediately exited on row bounds: `(G*qmax - sum(q_i))*nN`.
- Fixed-shape padded M row slots among active tiles: `sum(q_i*WM - c_i)*nN`.
- Useful row fraction among active matrix tiles: `sum(c_i) / (WM * sum(q_i))`.

These are source-derived scheduling/arithmetic exposure counts, not kernel time or GPU utilization. For xmx's edge path, the checked load/store guards correctness but the source still issues matrix multiply for the full tile. For IQ, multiply padded M slots by the relevant N/K product shape to produce only an arithmetic upper-bound proxy; dequant instructions and barriers are separately repeated per active M tile. For a custom grouped path with `nN=ceil(N/WN)`, include N tails if a future shape has them. The current XMX product Ns are aligned as above. Always calculate `WM` from the effective kernel branch, not a build option guessed from source.

The retained R139 census reported 8,684 fallback grouped GU calls and 8,684 Down calls over six chunks (current logical G16 windows), plus 255 resident IQ group calls per product. These are source-implied dispatch counts, not observed device launches or timing. That census lacks the ordered `cnt[e]` vectors / group row sums; therefore the exact empty-group count, active M tile count, padded row count, and any potential partition benefit cannot be reconstructed from its histograms. Its totals and max chunk size are not a substitute for per-group row counts.

## Can a row-size grouping reduce empty tiles while preserving current order/ownership?

**Yes, if grouping means splitting ordered groups, not sorting them.** Scan each existing logical group in its current `order` sequence, then split at contiguous boundaries when the next run's `ceil(max(cnt)/WM)` would otherwise force many empty M tiles. Keep each expert's original `[off,off+cnt)` rows, weights, Dm route positions, and route-to-token metadata unchanged. Run the current SwiGLU over the contiguous interval for each contiguous subgroup; submit GU, SwiGLU, and Down on the same compute queue in the same order. Do not cross an existing resident/fallback boundary, G16 dequant q-slot window, format boundary, or native-batch flush boundary. This preserves logical route order and combination addressing while making each new call's `max_rows` smaller. It increases grouped-call count (GU and Down) and may increase SwiGLU calls; whether time improves is unknown.

For streamed/fallback weights, keep the existing source-blob `m.used` event/publication lifetime unchanged, and do not overwrite `dq_gu/dq_d` group scratch until the final subgroup's queued consumers have retired. If a logical G16 window is split, rebase each subgroup's weight pointer to its first q-slot (`dq_gu + q0*GU_ELEMS`, `dq_d + q0*D_ELEMS`) while retaining per-expert stride; continue using the corresponding contiguous bounds and route-row offsets. The custom XMX/MMA/DP4a wrappers wait only when passed a null stream; with `m.cs` they enqueue asynchronously, so same in-order queue sequencing is the relevant device ordering, not a host return. `Gemm::f16_groups` consumes host bounds synchronously but its device operands remain live until its queued work completes. For resident IQ, the pointer array is copied into the kernel argument at submission; expert weight storage remains resident. A split does not justify early freeing, slot release, host mutation of descriptors still read by queued work, or a new host wait.

This local contiguous split can remove only the first category (launched empty tiles caused by a group-wide max); it cannot reduce padded rows inside an expert's last fixed tile. To reduce that second category needs a different M tile (or another kernel/API with smaller-M variants), which could reduce matrix utilization, change register/local-memory/barrier behavior, change checked-edge operations and output rounding, or create more dispatches. Sorting experts by `cnt` could reduce max skew across arbitrary mixtures but would reorder the compact route layout and weight slot sequence. XMX expects contiguous `W + ex*w_stride`; IQ has a host pointer list, but both write output rows at `bounds[ex]`, and post-GEMM activation/combine and staged weight lifetimes must remain aligned. It is not a no-change scheduling tweak.

## Minimal diagnostic and measurable ceiling

Before any optimization, add/use a bounded, default-off aggregation at the current host-known group formation boundary, without per-expert printing or extra queue events. For every eligible layer/chunk/group record: effective backend (`Gemm::path`, XMX/MMA/DP4a/IQ), format, role GU/Down, `T`, `WM/WN/KC`, `N/K`, `G`, ordered `cnt[e]` or a lossless compact ordered tile-count sequence, `max_rows`, `nM`, `nN`, and group ordinal/window boundary. Emit request-end totals for launch slots, active tile groups, early-exit groups, active padded M rows, useful rows, active IQ M tiles, and extra subgroup/activation call counts under candidate contiguous partitions. Keep every original group's identity so the measured schedule can be joined to source order. The record should be small and bounded; keep the detailed per-group sequence only until exact partition feasibility is computed, then retain its hash plus sufficient aggregate bins and decision.

Then separate three measurements on a future already-qualified run:

1. **Dispatch/host cost:** count grouped submissions and capture host enqueue spans or the existing coarse phase clock. Compare one baseline and a candidate with identical expert/routing order, data, and kernel backend. This detects the extra-launch tradeoff; it does not reveal padded matrix utilization.
2. **Device service:** use queue events around coarse batches (not every expert) to measure GPU elapsed service, and if supported/permissioned, hardware matrix active/busy and memory/local-memory metrics. Keep event perturbation against a quiet wall baseline. Launched CTAs, a long event, `--stats`, or theoretical row fraction alone cannot prove low GPU utilization.
3. **Correctness/lifetime:** validate every output row covers each original route row once, unchanged route IDs/weights/order and Down destination offsets, boundary tails, dequant q-slot ownership, and asynchronous completion before scratch/ring reuse. Compare full prompt outputs/state under predeclared numerical criteria before performance interpretation.

A cost model may screen contiguous partitions by minimizing measured launch cost times extra calls plus measured per-active-tile service and predicted early-exit/padded exposure. It must not assign elapsed time from the exposure formulas without calibrating on the actual backend and row counts. No numeric speedup or utilization claim follows from this static review.

## Primary-source comparison

Intel's ARK README documents an XPU/Battlemage MoE grouped-GEMM interface with activations `[total_tokens,K]`, weights `[num_experts,K,N]`, and explicit `num_tokens_per_expert[num_experts]` metadata. This supports making exact per-expert counts first-class inputs to the schedule, but the README does not specify its internal tile scheduler, so it cannot validate a particular tiling strategy: [Intel ARK MoE grouped GEMM API](https://github.com/intel/auto-round/blob/main/auto_round_extension/ark/README.md).

The Intel SYCL joint-matrix extension states that matrix operations are subgroup collective functions, require supported shapes for the selected device, and require converged control flow for group functions. This aligns with the source's supported-shape gate and with retaining uniform subgroup control around tile/edge work; it is not a performance model: [Intel SYCL joint-matrix extension](https://github.com/intel/llvm/blob/sycl/sycl/doc/extensions/experimental/sycl_ext_matrix/sycl_ext_oneapi_matrix.asciidoc).

As a concrete grouped scheduling comparison, NVIDIA CUTLASS documents a persistent grouped scheduler that maps thread blocks to tiles across variable-shaped GEMMs; it specifically analyzes wasted assignments and load imbalance, and says size sorting can help but is not guaranteed. Its reported ~30% example is on GA100 for a different problem and does not transfer to XeStrata. The useful point is that scheduling by actual per-problem tile counts differs from launching each problem at a group-wide maximum; it is a design precedent, not evidence of Xe speedup: [CUTLASS grouped-kernel scheduler](https://github.com/NVIDIA/cutlass/blob/main/media/docs/cpp/grouped_scheduler.md).

A merged llama.cpp SYCL MoE-prefill PR reports a counting-sort-based routed-row path and a measured project-specific improvement. That demonstrates an implementer optimizing row packing/order, but it changes the routing data path and is neither evidence about XeStrata's GEMM tile padding nor a directly transferable gain: [llama.cpp SYCL MoE prefill PR #23142](https://github.com/ggml-org/llama.cpp/pull/23142). The raw search result describes a later B70 wrong-output report involving that area; do not use the headline improvement as correctness or speed evidence for this source.
