## Resource-based priority, not predicted performance

The measured machine receipts in the campaign correction report 125.716 GiB physical RAM, initial MemAvailable about 90.803 GiB on a representative sample, and 9.936 GiB B570 VRAM (R344/R365 receipts). These are capacity context, not reserved headroom at later allocation points. The campaign's default resident expert arena is about 46.838 GiB; do not assume it is mmap/reclaimable. A separate measured Host-USM H2D effective rate is 6.446834 GB/s (R135/R365 lineage); it is a transfer-service reference, not proof that every prompt byte transfers at that rate or lies on the critical path. Therefore prioritize settings that alter repeated expert traffic and cache residency only after recording actual cache/ring/PP geometry. Use observed request counters/timing; do not rank a candidate by dividing logical expert bytes by H2D rate.

## Bounded search once both phase gates pass

Use exact frozen pack/shards, profile, tokenizer, prompt token IDs/hash, sampling, runtime/device, queue settings and outputs. Run 32K and 64K as separate blocks, with `max-context` held constant within each block at the smallest qualified value that fits prompt plus requested output and margin. Batched conditioning processes `n_prompt-1` positions; report the terminal prompt-position/token-loop cost separately. Preserve 262K context as a separate capacity workload; do not let a 262K setting contaminate a 32K chunk comparison.

**Fresh prefill screen (one variable group at a time).** Use a fresh uncached request/session and hold decode policy fixed: profile/cache policy, workers, PCIe fraction, KV format/residency, speculation and output count. First retain a clearly labelled default-policy baseline (`--prefill` omitted is token path, not “auto”). Then screen fixed requested chunks 4096, 6144, and 8192, one fresh-process sample each, in an interleaved baseline/candidate order. These form a compact practical bracket; they are not asserted optimal. Include `--prefill auto` only as a separate policy arm and only with its effective chunk/ring recorded. Consider `auto:16384` only if the selected fixed rows show repeated-pass traffic remains material and admission logs show room; do not jump to 32768 by default. Hold `STRATA_PREFILL_RING`/`STRATA_RING_BYTES` and other prefill env constant across the chunk screen. A second ring experiment may compare source default against one specified ring after actual resolved ring and cache traffic are known. Do not simultaneously vary FIRST, STREAM_MIN/ALL, LEND_PCT, MMQ, PLE IO, or borrowing. Screen results require full correctness and all requested component checks, not merely a PP rate.

**Restored/warm decode screen, separately.** Construct one valid post-prefill session state per 32K/64K context and retain its identity/hash. Restore that same logical state in fresh independent processes for each decode arm; report restore time separately from generation wall. Keep selected prefill configuration, cache/profile/admission, context/KV, PLE/native route and prompt unchanged. First compare pool workers omitted (auto) vs explicit 5; add one lower count (e.g. 3) only if this host's actual topology and samples justify it. Keep affinity/host-worker policy fixed. Next, and only as separate axes, screen a cache budget/profile change (request vs actual slots), then one nonzero PCIe fraction only if that exact supported route is safe and its INFO confirms it; this changes CPU/GPU miss service, not prefill. Finally screen one alternate speculation width (e.g. 2 vs 4) with the same draft artifact and output/quality gate. Keep accepted output tokens/logprobs and draft/accept counters. Do not bundle workers, cache, PCIe fraction, and spec width in one “tuned” arm.

For selected settings, gather at least three independent fresh-process restored-decode samples, with identical restored state and generation length; report every sample, median and range. Multiple generations in one warm server process are useful request-level data but not independent process repetitions. Separately run a fresh uncached request to measure whole request and prefill; do not use it to substitute for restored decode. If production-like warm requests use prompt cache, add that as its own labelled service scenario with exact cache hit/miss/replayed-token count and restore cost.

## Admission, comparison, and stop rules

At screening, one sample per arm is for selection only. Bracket candidate runs with the same safe baseline to detect drift; serialize GPU work. Before comparing speed, require complete prompt conditioning, same exact state/output protocol, no clamp surprises, healthy completion, and the intended numerical/output gate. A rejected or non-admitted arm remains in records with its reason. Keep all raw samples and the original statuses. If fixed chunks collapse to the same actual chunk, they are not distinct observations and should not be treated as such. If cache slots differ, a prefill chunk comparison is confounded until cache geometry is matched or the result is explicitly a policy comparison. If 64K fails admission, report that boundary; do not extrapolate from 32K.

Persist argv/env, source and executable hashes, compiler/runtime/driver/device, model/profile/shard hashes, token count/hash, cache/restore identity, requested/resolved/actual chunk/ring/cache/KV/workers/fraction/spec, PP progress and timing, decode timing, output/state/correctness status, and every per-process sample. Use quiet timing for selection; optional phase diagnostics are separately labelled and compared against quiet runs for perturbation. The INFO line contains effective context, KV, cache, spec/MTP, free VRAM, workers and PCIe fraction, but not chunk; preserve adjacent auto/clamp/ring logs and PP lines too.

This contract does not authorize an official run, repair the source, establish a safe toolchain/runtime tuple, or claim an optimal configuration. The concrete next gate remains qualification of safe source/runtime handoffs; parameter selection follows that gate.
