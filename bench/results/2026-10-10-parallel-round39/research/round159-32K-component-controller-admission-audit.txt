## Benchmark source and parser accounting

For the admitted controller command `--bench 32768 --chunk 8192 --repeats 3`, the fixture requires a positive divisor of 32,768 no greater than 8,192 and 3–9 repeats. Four chunks form each 32K prefix. It performs a complete untimed 32K warmup, carrying equal nonzero recurrent and convolution history through both arms. Each measured sample reinitializes the two arms to the same deterministic nonzero state/history, then carries each continuously through the same four chunks. In each chunk it alternates which arm runs first using `(sample+chunk)%2`; within every sample, each arm therefore runs first twice and second twice. Timer output records each arm's chunk position. The controller re-derives that position for all 24 rows.

Each timed interval begins after flushed `STAGE` output and immediately before submissions for gates, convolution, and recurrence/output norm. `stage()` calls `wait_and_throw()` and checks the asynchronous-error flag before the end timestamp. Upload/preparation, warmup, materialized-loggate diagnostic, readback, bitwise checks, hash generation and interval summation are outside the clock. The fixture checks gate/factor, beta, convolution output/history, recurrent state, FP32 output and FP16 output bitwise after each pair. Across samples the controller also requires each arm's state/history/output hashes to repeat exactly. Its reported sample value is the sum of the four corresponding logged chunk intervals, verified with `isclose`; the controller records medians only over those three per-arm sums. This is synthetic component service time, not model wall time, token throughput, or an adoption result.

The parser's expected counts agree with source:

- Warmup emits one `BENCH_WARMUP_COMPLETE` row after 4 carried chunks and writes no warmup timing rows.
- Three measured samples × four chunks × two arms yield 24 `BENCH_CHUNK` and 6 `BENCH_SAMPLE` rows, and 12 paired chunk boundaries.
- Each timed chunk emits two `STAGE` rows (`service_stage` per arm): 24 total. The fixture destructor adds one successful `final_drain` stage, so the controller's total of 25 is correct.
- The required terminal row and scope fields preserve synthetic-only, model-false, full-KV-false and performance-adopted-false status.

Rows are checked for identity, schema, uniqueness/completeness, exact offsets/live size/variant, strict per-arm pairing hashes, exact position, finite positive intervals and valid 64-bit decimal hashes. Every aggregate is tied back to its four parsed intervals. `BENCH_COMPLETE` is exact. The same run first verifies the legacy default fixture: 22 chunk fingerprints (11 deterministic lengths twice), 267 stage lines, and exact equality of its `CHUNK_PASS` rows with the prior closed quad diagnostic. The 267 count is consistent with two initializations, 22 chunks × (prepare, two arms, materialized-exp, readback, and seven immutable-input readbacks), plus final drain.

One bounded parser strictness gap remains: the benchmark parser counts recognized tags and validates key records but does not reject every unknown extra stdout row or verify exact `STAGE` label ordering. It does require the terminal row last, exact row counts for major records, empty benchmark stderr, and the controller pins the binary/source, so this does not invalidate source-established accounting for the pinned fixture. For future reuse as a generic output parser, reject unknown row tags and assert the 25 stage labels/order explicitly. No unexpected row is reported here, since this review did not inspect or generate a run trace.

## Process ownership, failures, limits and closure

The pinned `Owner.run` starts each child in a new session, records direct PID/start-time/SID/PGID identity, holds a pidfd, polls the session every 50 ms, samples aggregate non-zombie session RSS, checks wall time and combined output size, and leaves the leader unreaped until the final session scan. On failure it scans and signals only owned PID/start-time pairs with TERM then KILL, waits up to three seconds for each pass, records cleanup and errors, performs a final session scan and reaps the child. `completed()` requires an observed-complete run, reaped direct child, empty session, no error/error list, and no cleanup signal; a command terminated by the owner cannot be treated as a successful measurement. The closed host-check harness covers normal exit, nonzero exit, timeout, output-cap breach and a reparented process group.

The R159 controller applies its three checked source substitutions to the exact hashed parent source before compiling it in-process: per-child address-space cap 16→24 GiB, per-child CPU soft/hard limit 120/121→600/601 seconds, and sampled whole-session RSS limit 2→4 GiB. It records the resulting 24 GiB AS, 600/601 CPU, 4 GiB session RSS, 600-second benchmark wall deadline, 8 MiB combined output, 4 MiB per-file size limit, 256 descriptors and disabled core dumps. Output is sampled during execution and checked at exit; RLIMIT_FSIZE additionally bounds each log. These are sampled session RSS and per-process rlimits, not a cgroup aggregate memory/CPU reservation. The 50 ms polling and up-to-six-second TERM/KILL cleanup allowance are source limitations represented in the owner behavior.

The controller captures a zero-length journal cursor before GPU-runtime launch and refuses an existing device coredump. If any failure follows launch and no complete interval was recorded, `finally` attempts a journal query after that cursor once the owner reports no active child, even if the benchmark parser or exit check failed. Successful completion requires the interval command to close normally with empty stderr, no matching `xe`/`i915`/hang/coredump line, and no after-run coredump. Final source, binary, runtime/dependency and boot-id pins are rechecked, then `active` is derived from actual owner state; `passed` requires all checks and a normally closed owner. This is coherent source-level failure/closure accounting. It does not establish that a live quiet run succeeded; that status remains with the root-owned run receipt.
