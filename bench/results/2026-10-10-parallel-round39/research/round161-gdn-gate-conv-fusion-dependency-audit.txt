## Decision

A distinct candidate merits one bounded prototype-and-measure discriminator after the root closes the current gate-factor timing attempt: horizontally combine gate/beta generation with the first convolution pass in one SYCL kernel submission, while keeping their existing expressions, output buffers, downstream history update, Q/K normalization, and recurrence unchanged. This is not the previously screened same-slot exp representation change. The two operations have separate inputs and outputs, no data edge between them, and are currently submitted sequentially to the same in-order queue. That gives a sound dependency basis for a work-group-partitioned kernel that executes both task types in parallel without a global barrier.

**Hold implementation and performance claims until the active gate-factor diagnostic/bounded timer is closed.** The current root v5 diagnostic passed, but that controller stopped when its host-rejection parser expected `FAIL ` while the actual fixture emitted `FAIL,bench admission\n`; the kernel journal interval was empty. The 32K quiet timing did not run. This is a controller admission mismatch, not a GPU fault and not evidence for either gate encoding's speed. Keep this candidate independent of that timer repair and do not combine horizontal fusion with a gate-encoding or recurrence change.

## Current producer/consumer graph and data mapping

At the shared production site in `prefill.cpp`, QKV projection writes `m.qkv`; alpha/beta projections write `m.ab`; then gate production writes `m.gate` and `m.beta`, and convolution reads `m.qkv` plus convolution weights and the carried convolution history, writing `m.hbuf` and the new history. Recurrence consumes `m.hbuf`, gate, beta, and the recurrent state afterward. The arena takes distinct slices for QKV, AB, gate, beta, and hbuf. In this stage the possible `m.y=m.qkv` reuse is written only by later recurrence, after convolution has consumed QKV. The conv history is a separate tail of the layer's persistent GDN state, not the recurrence matrix. The existing component fixture similarly allocates distinct arrays for `ab`, `qkv`, both gate arms, `hA/hB`, and independent carried history.

The ordinary gate kernel launches `ceil(T*HV/256)` 256-work-item groups (`HV=48`). Each work-item handles one `(token, head)` and computes, in this order, FP32 `v=ab+dt`, the `v>20` conditional or `log1p(native::exp(v))`, multiplication by `ssm_a`, store of gate, then sigmoid beta from the other AB plane. The feature-on factor copy retains that gate expression as a named FP32 `loggate` then stores `native::exp(loggate)` in the same gate slot; it is a separate representation and must not be silently substituted in a fusion comparison.

For `T<=64`, the default convolution route is `gdn_conv_kernel`: 128 work-items each own a channel and walk all tokens in order with three rolling scalar inputs seeded from old history. Each token computes `s=v0*w0+v1*w1+v2*w2+x*w3`, writes `s/(1+native::exp(-s))`, then advances the rolling values; the kernel writes its final three inputs back to history. For `T>64`, unless `STRATA_GDN_CONV_SERIAL` is set, the default first pass is `gdn_conv_tiled_kernel`, with 128 threads per `(tile, 128-channel block)`, 64-token tiles, and old history used only for the first tile's three predecessors. A separate history kernel writes the last three QKV inputs, including the `T<3` carry case in the serial route. A separate `gdn_l2_kernel` normalizes the 32 Q/K heads. The opt-in `STRATA_GDN_CONVL2` instead uses an existing conv-plus-Q/K-norm kernel with work-group barriers, followed by the same separate history kernel. These existing conv/L2 fusions are not new candidates.

The R159 quiet benchmark environment omits both `STRATA_GDN_CONV_SERIAL` and `STRATA_GDN_CONVL2`; by source dispatch at `T=8192` it therefore requests tiled convolution, separate history update, and separate L2, in addition to the gate producer. This is a source-derived expected selection, not an observation from an actual quiet device trace.

## Why horizontal fusion is possible, and what changes

The gate/beta task reads `ab`, `dt`, `ssm_a` and writes gate/beta. The convolution task reads `qkv`, conv weights and old history and writes `hbuf` and updated history. There is no producer-consumer edge between those tasks and no shared output. Same-queue order currently makes gates finish before convolution starts even though recurrence is the first consumer of either set of results. A fused submission could assign complete work-groups to one task or the other, keeping each gate/conv group uniform. No work-group or device-wide synchronization is then needed between the two branches. Recurrence remains a subsequent queue command after all outputs and history are complete.

This is specifically **horizontal fusion**: retain the materialized FP32 gate/beta and h arrays because recurrence needs them, and retain the current convolution history update. The potential gain is one fewer kernel submission and the ability for independent task groups to execute in the same kernel interval; it does not remove an array, global-memory handoff to recurrence, or convolution work. It is not a producer-consumer in-register fusion.

The current helpers cannot simply be called unchanged from one common `nd_range`: gate launches with local size 256, conv with local size 128 and uses 3D group coordinates for tile/channel ownership. A practical first prototype needs a compact flattened work-group ID mapping (or equivalent) with 128 threads: one range of groups maps to 128-element gate spans; the other maps to `(tile, channel-block)` spans for tiled convolution, or channel blocks for the serial route. This halves gate work-items per group versus the present launch. A rectangular 3D range with max gate/conv extents would create avoidable inactive groups. Each whole work-group must select one branch uniformly. Do not place gate and conv work-items in one mixed work-group and then encounter a barrier from only the conv subset.

At the benchmark chunk `T=8192`, the gate contains 393,216 work-items (1,536 current 256-thread groups, or 3,072 groups at 128 threads). The default tiled conv first pass has 80 channel blocks × 128 tiles = 10,240 128-thread groups, followed by 80 history groups; separate L2 dispatches 8192 × 32 = 262,144 work-groups of 128 for Q/K normalization. Combining gate with only the conv first pass would therefore replace two submissions with one, while keeping history and L2. It also makes the fused stage contain both native gate exponentials/sigmoid and convolution SiLU native exponential in one kernel image, and adds 1,536 gate groups relative to its current 256-thread grid. Launch saving is plausible; work-group scheduling, code size/register allocation, occupancy, and the small gate share of total long-chunk work could erase it. No percentage is estimated.

For `T<=64`, gate plus the serial channel-walk conv can likewise be separate whole work-groups in one launch, retaining each channel's ordered token loop and old-history carry. This shape may be more launch-sensitive, but those chunk sizes are the final short remainder in a typical long prompt, so a win there alone does not justify claiming a long-prefill improvement. The `T=64/65` boundary also changes the existing conv route; measure both only if the first 8192 discriminator supports the candidate.

## Numerical, state, and queue obligations

A fusion prototype must preserve both allowed gate encodings as separately selected modes. For each mode, keep the gate expression's FP32 evaluation and store semantics, including the strict `v>20` branch, native exp/log1p, beta sigmoid, and for factor mode the stored-loggate then native-exp value. Keep the convolution four-tap multiply/add association, native SiLU exp, FP32 stores, normalization scope/order, and FP16 conversion unchanged. Sharing one kernel translation unit can alter compiler context/lowering for native math even under unchanged precise flags; source similarity does not establish bitwise identity. Compare baseline versus fused gate, beta, hbuf, conv history, recurrence state, FP32 y, and FP16 y bits, and compare error/fault behavior. Never change representation, recurrence route, subgroup, fast-math flags, or norm in the same A/B.

Carry is continuous across chunks and layers. Initialize equal but distinct recurrent and convolution states; never reset history between chunks in a prefix. Check full updated conv history at every chunk boundary, particularly T=1/2/3 where old-history elements supply missing tail entries, and check recurrent-state carry through a 32K synthetic prefix. The fused branch must write each output once and update history exactly once. Ensure T=0 retains the existing no-submission/no-dereference contract if a new private API exposes it. The production `m.cs` queue is in-order; keep recurrence submitted only after fused producer+conv and the existing history/L2 work. Preserve stage-level async error checks and stop without retry after any uncertain submitted-kernel failure.

## Candidate discriminator and stop rules

After current controller admission/timing closes normally, the smallest useful root-owned discriminator is an isolated feature/test binary on the same B570 and compiler/runtime that compares current separate launches against a prototype fused first pass at `T=8192`, using each gate encoding in separate matched A/B pairs. If candidate source supports it cleanly, include a short `T=64` serial case and `T=65` tiled case to cover dispatch change; do not widen to a shape sweep. Use identical buffers/inputs/initial state, warm both variants fully before timing, carry through four chunks (32K) per sample, balance arm order, and time from just before the gate+conv work until `wait_and_throw` plus async check after all relevant history/L2 submissions. Exclude upload, reset, readback, comparison and hash from the service interval. Record individual sample pairs, per-chunk bitwise results, and exact selected route/source/runtime identity. Keep one process and unchanged quiet environment, no profiler. The existing R154 service interval includes recurrence/norm as well and cannot by itself isolate the gate+conv delta; use a dedicated bounded fixture interval for this discriminator, then require the same 32K full GDN component measurement before claiming the end-to-end component impact.

Reject the prototype on any gate/beta/h/history/state/y/y16 mismatch, error-check difference, missing carry, wrong T-tail handling, spill/occupancy or resource cliff, unsupported selector fallback, or unstable interval. Continue only if isolated paired service sums improve beyond observed run variation at the intended chunk size and the complete GDN component remains no slower. This remains synthetic prefill-component evidence; model latency, physical 262,144-token lifecycle and adoption need separate root-owned gates. If the clean 32K baseline fails to show a material gate+conv portion or the fused branch does not win clearly, stop without implementation.

## Prior decisions and external evidence

This delta is distinct from R108's conditional final-decay-exp precomputation (now separately implemented and correctness-tested but not performance-qualified), from R108's already-existing conv+Q/K norm fusion, from token-block staging, and from R76's command-list/event/queue-mode discussion. Do not re-open the WY/chunkwise recurrence, exponential-removal, GRF, norm fusion, or token-block proposals as part of this candidate. R108's author implementations of WY reduction and H100 chunk/GEMM kernels use different dataflows and do not validate gate+conv horizontal fusion or transfer their timing.

The [PyTorch graph-transformation blog](https://pytorch.org/blog/optimizing-production-pytorch-performance-with-graph-transformations/) describes horizontal fusion of independent operations as a way to reduce kernel launches; that is the pattern-level rationale only, not an expected Strata speedup. Khronos [SYCL 2020 execution and synchronization rules](https://registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html) define work-group barriers as group-scoped and queue submission as the application-level ordering point; this supports the uniform-workgroup branch design and retaining a kernel boundary before recurrence. The [FlashInfer GDN prefill implementation](https://github.com/flashinfer-ai/flashinfer/blob/main/flashinfer/gdn_prefill.py) is a chunked GDN formulation with different layouts and algorithm, so it is not evidence for bitwise equivalence or a target-specific fusion win. No external result is transferred.
