# R160 — actual 262,144-token GDN-factor prefill boundary

Date: 2026-10-10 (Asia/Tokyo). Read-only source and protocol audit. No model/tensor payload, runtime, build/compiler/disassembly, test, GPU/device query, profiler, Git operation, cleanup, lock, service or reset was used. This records the current interface boundary and a qualification protocol; it is not a model or candidate pass.

## Decision

The current generate CLI and GEN service cannot admit an exactly 262,144-token prompt with max_context=262144: both require a positive output budget and require prompt length plus that budget to fit max_context. Both reject max_new=0. No prefill-only mode was found. Therefore a strict full-context no-output request is not expressible through the current interface.

For prompt N=262144, normal generation batches the first N-1=262143 prompt positions, then processes the final prompt token at position 262143 through the token/verify path. This consumes N prompt positions only if that final stage completes; the factor prefill caller sees only the first 262143. The final prompt position can produce a prediction, but that output is not appended to the consumed prompt state. Feeding it as an additional input would require position N and exceed the physical context.

A strict qualification requires a reviewed test-only no-output path: admit N prompt inputs, process the final prompt token and compute final logits, drain work and snapshot state, then stop before sampling or appending output. It may bypass only the output-reservation admission check in this explicit test mode; retain the physical position bound N and ordinary generation behavior. Until such a path exists, do not report an exact physical full-context candidate pass.

If a positive-output run is used with max_context=N+1 and max_new=1, it may corroborate that N input positions were consumed if the saved endpoint proves position N was never consumed. Label it as occupancy with a logical cap of N+1, not as strict max_context=N qualification.

## Qualification protocol

Use identical canonical prompt IDs, model weights, binary except for the factor selector, device/cache configuration, and runtime selectors. Start each arm from clean equivalent state. Require a fresh-session receipt (RESUME0, REUSED0), prompt/read count N, completion of the final input position, no context sliding, and a saved session endpoint showing exactly positions 0 through N-1 consumed. Record final logits/top-5 and output IDs where applicable.

Compare full GDN state by layer and chunk, including all recurrence matrices and convolution histories. Compare full QSA state, including KV code and scales, paged host authority/page tables, indexer tail/dead/pool/block-position/selected IDs, plus PLE and MTP KV/history when enabled. Capture first-difference location per layer/chunk and final comparator results. Run same-arm repeats as well as legacy-versus-factor comparisons to establish repeatability. Retain compact hashes and first-difference evidence; raw state only under the project retention rules.

For a normal production prompt of length N, the relevant split is 262143 factor-prefill positions plus one token-path position. A CLI split at 262140 has 262140 factor-prefill positions plus four token-path positions. R141's 262140+4 GDN fixture uses bounded GDN chunk calls; it does not establish physical model context or factor-prefill on the final four. Exercising those four through the candidate prefill requires a real model/session-state driver that calls the production prefill chunk body at explicit T boundaries; a synthetic prefix fixture is insufficient. Do not launch a single T=262144 kernel.

R21 records a prior layer-major 262140+4 first run that passed and a repeat after an intervening 32K run that diverged in observed K/V code/scale near position 98328. That remains a repeat defect, not causal localization. Avoid intervening unrelated runs and preserve the original result status.
