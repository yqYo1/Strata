# R158 — GDN/MoE profiler discriminator screen

Date: 2026-10-10 (Asia/Tokyo). Read-only review of the fixed component-timing source, compact prior profiler/event reports, and current official Intel/SYCL/Level Zero documentation. No profiler, device query, runtime/GPU/model/payload execution, test, build/compiler/disassembly, Git operation, cleanup, lock, service, or reset was used/performed. This is a profile-plan decision, not a measurement or tool qualification.

## Decision

For the immediate 32K synthetic GDN comparison, reuse the R154 --bench 32768 --chunk 8192 --repeats 3 service fixture after the root's serial admission gates. It is the only currently admitted bounded discriminator in this source set. It compares the actual gate producer + convolution + recurrence/norm service call on the same in-order queue and reports host steady-clock time through queue completion. It excludes prepared-input upload and diagnostic readback from the interval. Interpret it only as combined synthetic service; it cannot split those kernels, identify device execution versus submission/wait, measure transfers, or predict model/MoE time.

The current fixed source has an optional STRATA_GDN_QUAD_EVENT_DIAGNOSTIC compile path in the GDN recurrence wrappers, but the flag is OFF by default and the checked-in parity fixture does not bind a GdnEventDiagnosticCapture sink, query timestamps, or enable queue profiling. Its source-only capture points retain recurrence and output-normalization events and host submit/admission intervals; gates and convolution are not captured. The fixture constructs an in-order queue without enable_profiling. Thus the event API is not a currently runnable discriminator from this fixture as-is. A post-drain event profile of recurrence/norm could separate those command durations from host-call-plus-wait only after a separately admitted diagnostic build/wiring uses an eligible profiling queue; R106's API/error split applies. It still would not split producer/conv, nor provide SFU/reduction attribution. Do not toggle production queue properties or use such instrumentation as the quiet comparison binary.

For the next actual >=32K model tuning question, keep three quantities separate: (1) existing clean end-to-end/prefill and MoE phase timing from the model harness, (2) the R154 synthetic combined GDN service, and (3) any separately qualified diagnostic event/counter profile. The first locates whether MoE or GDN matters to the user-visible phase; the second controls synthetic GDN exposure; only a future qualified per-kernel profile can attribute device time or hardware causes. Existing evidence does not establish a root-only profiler that cleanly measures transfer, GDN SFU/reduction, or MoE cost together. No new profiler command is admitted here.

## Profiler screen and pending facts

- VTune GPU Compute/Media Hotspots: current Intel documentation describes GPU task time, occupancy, task identity and architecture metrics and lists Battlemage-family support in release documentation. Metric availability varies by hardware; this is workflow support, not proof for this Arc B570, this installed stack, or an individual counter. VTune's separate software Hotspots path is a known rejection: R16 records its local smoke exiting before target execution because Yama ptrace_scope=1; do not repeat it, lower sysctls, or attach it to a GDB-owned process.
- PTI unitrace: the official README documents -d -v per-kernel timing/resource summaries, --metric-list, and Level Zero per-kernel -q counter queries. Metric groups require Level Zero/flat hierarchy and are runtime/device dependent. R90 records an external B580 -q failure with ZE_RESULT_ERROR_DEPENDENCY_UNAVAILABLE on an older stack; that is not a B570 result. No current B570 metric-list/smoke or successful PTI profile is in the read evidence. Do not use -q, stall sampling, or long trace as the next discriminator unless the owner later admits a tiny, bounded profiler smoke; a metric-name example is not proof of availability.
- SYCL events: a returned sycl::event can report command start/end only if its submitting queue was made with enable_profiling; timestamps describe the associated command action and share a backend timebase, not host steady time. The present parity queue lacks that property, and event capture is unwired, so no event result exists to prefer over the existing service samples.
- Level Zero raw kernel timestamps: the current specification requires timer frequency and valid-bit wrap handling and warns kernel-event timestamps are not interchangeable with global-timestamp writes. The existing SYCL event API is narrower and sufficient for elapsed command time if properly admitted; bypassing it for raw Level Zero is not justified here.
- SFU/reduction attribution: no inspected report proves a B570 counter for SFU activity or a subgroup-reduction/shuffle count. A future cause test needs exact kernel identity, generated ISA/instruction evidence, and only metrics advertised by the installed collector. Generic GPU-time or XVE busy/stall values cannot be relabeled as SFU or reduction cost.

Installed provenance supplied for this screen: oneAPI/DPC++ 2026.1.1-325, VTune 2026.4, Level Zero loader 1.32, compute runtime 26.31.39395.14, Arc B570 root 0000:05:00.0. This is recorded provenance, not a profiler success. The exact pending tool fact is whether this installed B570/driver/UR stack can expose a bounded per-kernel timing/resource summary and which hardware metric groups (if any) it supports without changing the quiet path. No device query or profiler admission was performed.

A future diagnostic must be a separate run/binary from clean quiet timing, have fixed kernel selectors and exact image/source hashes, a small output/wall budget, and preserve normal async-error and teardown gates. The R154 owner-controlled environment guard and exact route attribution remain required. Any profiler failure or timeout is diagnostic failure, not a partial timing pass; do not retry through another collector or manipulate the system to make one work.
