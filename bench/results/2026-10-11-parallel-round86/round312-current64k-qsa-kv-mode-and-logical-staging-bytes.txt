## Determination

The 81375 clean64K run selects the **main QSA streamed KV mode 1** (`st.kv_mode == 1`), so the batched-prefill `kv_stage_from_host([0,p0))` branch is source-required under this run's configuration. `STRATA_KV_STAGE_OWN=1` changes where the staging pool is allocated (its own allocation instead of borrowed expert slots); it does not select the KV mode. `STRATA_KV_PREFETCH=0` disables the prefetch-ahead path, so the caller stages the prefix directly at the QSA layer/chunk site. Mode 2 is selected by the ring-state allocation branch when `ring_cells > 0`; the main QSA allocation uses `ring_cells <= 0` and the `--kv-resident=32768` policy.

The request record says `--max-context 262144 --kv int8 --kv-resident 32768 --prefill 8192`, with the above two environment values, and a 65,536-ID fixture. The startup receipt says `context=262144 kv=int8 kv_resident=32768` and reports 32,768 of 262,144 cells per QSA layer in VRAM. Those are capacity/resident limits; this run's batched prefill processes 65,535 rows (the terminal prompt token is handled by the separate one-token verifier). It does not mean 262,144 cells were occupied or staged by this request.

There is a layer-count discrepancy to preserve: the requested 13-layer multiplier does not join to the run's pack evidence. The actual pack `index.txt` has QSA `attn_q.weight` entries at blocks 3, 7, 11, 15, 19, 23, 27, 31, 35, 39, 43, and 47: **12 QSA layers**. This agrees with the startup's “3.09 GiB pinned RAM” capacity figure: 12 × 262,144 × 1,056 = 3,321,888,768 bytes = 3.094 GiB (binary GiB), before allocator/metadata differences. Thirteen full layers would be 3,598,712,832 bytes = 3.351 GiB. I therefore use 12 for the actual-pack total, and show the requested 13-layer arithmetic separately as a counterfactual; I do not silently apply 13 to this binary.

## Packing and exact branch arithmetic

The pinned Q8 layout uses 2 KV heads, head dimension 256, page size 4, and 64-value scale groups. Per cell:

`K codes + V codes = 2 heads × 256 × 2 arrays × 1 byte = 1,024 B`.

`K scales + V scales = 2 heads × (256 / 64) groups × 2 arrays × 2-byte FP16 scale = 32 B`.

Thus `kv_q8_bytes_per_cell = 1,056 B`; one 4-cell block is `kv_block_bytes = 4 × 1,056 = 4,224 B`. The copies move packed int8 codes plus FP16 scales, not two FP16 K/V tensors.

For 65,535 batched rows at chunk size 8,192, the chunk starts are 0, 8,192, 16,384, 24,576, 32,768, 40,960, 49,152, and 57,344; lengths are seven × 8,192 plus a final 8,191. Every `p0` is page aligned. The direct staging helper is called for `ceil(p0/4)` blocks before each chunk append. Therefore the prefix sum is:

`Σ p0 = 8,192 × (0+1+…+7) = 229,376 cell-equivalents/layer`

`Σ blocks = 229,376 / 4 = 57,344 blocks/layer`

`prefix staged bytes/layer = 57,344 × 4,224 = 242,221,056 B`.

At the pack-supported 12 QSA layers, that is **2,906,652,672 B** (2.708 GiB) of source-required logical host-to-stage copy payload over the request. For 13 layers it would be 3,148,873,728 B (2.934 GiB), but that is not the layer count evidenced by this run's pack. The final 8,191-row tail does not change prefix bytes: the final chunk's prefix is still exactly 57,344 prior cells.

The matching 32K control shape has four 8,192-row chunks, 32,767 batched rows, and prefix sum 49,152 cells/layer = 12,288 blocks/layer. The count ratio is `229,376 / 49,152 = 14/3 = 4.666666…`; thus R310's 4.67× conditional prefix-count statement **does apply to this mode-1 control/configuration**, as source-required logical payload, not as measured elapsed time or physical bus traffic. This is not the 2× append payload ratio.

The 65,535 newly appended rows have `65,535 × 1,056 = 69,204,960 B/layer` of packed KV values. For 12 layers this is 830,459,520 B per full destination copy; for the requested 13-layer hypothetical, 899,664,480 B. In this branch the source appends new packed rows to the authoritative host copy and to the staging pool, and writes mapped resident slots; the precise resident-slot write count depends on page residency/mapping and is not separately counted in the run receipt. These append values are logical store bytes by destination, not evidence that the same bytes crossed PCIe. The last partial chunk writes 8,191 rows; no new row is inferred for the separate terminal verifier.
