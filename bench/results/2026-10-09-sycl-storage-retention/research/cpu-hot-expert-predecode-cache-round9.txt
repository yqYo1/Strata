Round 9 — hot-expert exact codebook/sign predecode cache on Zen 3 AVX2

Verdict

A bounded cache of decoded integer vectors is technically possible and can preserve the existing dot product exactly, but the most straightforward representation is expensive: about 2 bytes per weight for magnitude plus sign bytes, or about 3 bytes per weight if it also stores the already-expanded int16 scale vector. For these experts, a cache of full hot experts would therefore consume several MiB per expert. The existing NT1..4 kernels already decode each weight block once for all tokens in a window, so this cache only avoids decoding across later windows. Whether that saves enough decode work to offset another memory stream, bookkeeping, and cache pollution is unknown. It merits a tightly bounded, profile-guided experiment only if existing per-layer/expert traffic data shows repeated hot experts across adjacent windows; there is no evidence here that it improves decode throughput on Zen 3.

A smaller and safer first candidate is a small per-expert cache of resolved grid magnitudes only, retaining sign and scale decode in the current kernel. For IQ3_XXS (type 18), each 32-weight half needs eight grid bytes resolved to eight 32-bit grid words (32 bytes); eight halves per 256-weight block therefore cost 256 bytes, versus 98 source bytes. Adding the 32-byte sign vector per half raises this to 512 bytes/block, 5.22x source size. IQ3_S (type 21) source is 110 bytes/block and has eight halves: grid magnitudes plus sign vectors likewise cost 512 bytes/block (4.65x); scale vectors add 256 bytes/block. IQ2_S (22) similarly costs 512 bytes/block before scale vectors versus 82 source bytes (6.24x). IQ2_XXS (16) is 66 source bytes and 512 bytes for eight cached magnitude/sign pairs (7.76x); IQ2_XS (17) is 74 bytes and 512 bytes (6.92x). IQ4_XS (23) has a different layout and is only one GU layer in this pack; inspect its decode specialization separately before including it. These are computed representation sizes from the AVX2 kernel's vectors and source block sizes, not measured allocation or runtime costs.

Why correctness can be exact

`iq_avx2.cpp` resolves codebook indices into `g`, constructs one sign vector `sgn`, and constructs per-half integer scale lanes `sc`. `iq_avx2_rows.inl` then applies `_mm256_sign_epi8(yv, sgn)`, `_mm256_maddubs_epi16(g, ys)`, `madd_add`, and the existing float accumulation. A cached record keyed by `(model/weight generation, layer, expert, matrix, row, block, format)` could store only the decoded `g` vector (8 int32 lanes for the four 8-value grid entries, or its precise existing lane representation) plus the 32-byte ±1 sign vector; keep the original block's fp16 multiplier and packed scale bytes, and execute all existing integer and FP32/FMA operations in the same order. The bytes must be generated with the same code as `Fmt32<TY>::decode`, including parity reconstruction (`even_signs`), high index bits (`hi_spread`), and gathered-format selection. Do not cache float-expanded weights or regroup/add the partials: those alter arithmetic and greatly increase storage. A cache that stores the final 32-byte signed activation transform is impossible because activations change every token; the cacheable state belongs to the weights.

For a compact implementation, store decoded magnitude and sign data in an aligned, row-major per-block side array. Lookup should be direct by block number so it does not re-parse block metadata or incur a hash lookup in the inner loop. Keep the original quantized blobs authoritative for scales and the layer-specific `dx`; invalidate the side array whenever the source bytes or expert format identity changes. Construct it lazily only after an expert crosses a repeated-use threshold, publish immutable entries safely before worker access, and evict whole experts outside active jobs. Preserve fallback to the current kernel on allocation failure. The expert pointers may be backed by file mappings, cache complements, or staged buffers, so cache lifetime must be tied to the owning expert source and not to a transient job buffer.

Footprint examples (approximate lower-bound, without allocator/index overhead)

The routed pack uses hidden size H=2560 and FF=640 (registry-v11 correction: 48 MoE layers/512 experts; GU format counts 18×17, 21×10, 22×20, 23×1; Down counts 20×39, 42×9). A GU expert has two 640×2560 matrices; its down matrix has 2560×640 weights. Storing 64 bytes per 32 weights (magnitude+sign) requires 9.38 MiB for all three matrices of one expert. Storing the 32-byte int16 scale vector too increases that to 14.06 MiB. Thus a 64 MiB budget holds at most six such complete experts before metadata/alignment, and a 256 MiB budget at most 27. These figures are representation capacities, not a recommendation for those budgets. A codebook-only side cache at 32 bytes/32 weights is 4.69 MiB/expert. A per-layer budget and a global budget both need to account for all resident active representations; independently caching all 48 layers' hot experts can rapidly consume RAM. The existing native arena is reported at roughly 48 GiB on a 128 GiB host, so total physical RAM alone is not the right budget: reclaim/commit headroom and the GPU/OS allocations remain relevant.

The benefit ceiling is limited. Each token group currently decodes each participating weight block once and reuses it across nt=1..4 token vectors (the AVX2 row loops hold `g`, `sgn`, `sc` outside the token loop). A predecode cache therefore removes cross-window repeated decode work but does not reduce activation loads, integer dot products, scales, or weight bytes read. It also expands the working set by roughly 3.7–7.8x for the stated IQ formats if signs are included, potentially making DRAM/cache traffic worse. Hot-only admission is essential; full-model expansion is explicitly unsuitable.

Activation sign and saturation contract

For IQ2/IQ3 GU, native activation blocks are Q8_K, produced through the ggml type-traits `from_float` path or Strata's AVX2 Q8_K routine (`native_expert.cpp` and `q8k_quant_avx2` in `iq_avx2.cpp`). The optimized routine's source describes equivalence to the reference and clamps via the Q8_K quantizer's 127 magnitude scale. That supports the normal finite-input producer path, but a cache cannot assume arbitrary externally supplied quantized activation blocks never contain -128 without checking every construction/import path. `vpsignb` negation of -128 remains the byte 0x80; mathematically it should become +128, which is not representable as signed byte. Thus this particular sign-transform scheme is exact only under an established activation range contract or with a correction for -128. For `maddubs`, its unsigned grid magnitude is at most 127 and each signed activation byte at least -128, so one adjacent pair has magnitude at most 2×127×128=32512, below 32767; there is no pair saturation even if -128 occurs. That does not repair the sign-negation mismatch. Validate activation provenance/range and parity against the pinned reference before any cache change; do not infer safety from the fact that `maddubs` does not saturate.

IQ4_NL down weights use Q8_0 activations and a separate kernel (`iq_avx2_rows.inl`, `iq4nl_rows`). It obtains the IQ4_NL signed codebook values, computes `aq=abs(q4)`, and uses `sign(q8,q4)` before `maddubs`. The source comment bounds pair products at 2×127×128=32512, so maddubs itself cannot saturate. If Q8_0 activation bytes can be -128, the same `vpsignb` issue applies. This report did not establish the complete producer/import range contract for all Q8_0 blocks; treat the constraint as open rather than relying on observed values. IQ4_NL blocks are 18 bytes (two-byte fp16 scale plus sixteen code bytes); an older report's “16-byte scale” phrase is registry-v11-corrected as a typo.

Scheduling and cache policy

The route is per-layer mixed-format (`NativeFmt`), and the row kernel already takes distinct nt=1,2,3,4 specializations. Cache entries must not be shared across GU and down formats or across layers merely because type IDs match. A hit should preserve NT behavior and be read-only across threads. At job aggregation, duplicate expert IDs should be deduplicated for predecode admission; do not have several workers redundantly build the same entry. Maintain a byte-bounded LRU or frequency/recency policy at expert granularity, admit only after repeated dispatches, and pin entries while jobs are in flight. Eviction must not invalidate worker pointers. Keep cache disabled by default until end-to-end comparisons show a benefit; count hit bytes, misses, build time, evictions, cache RAM, and per-format phase times in the same request-differential profile already under review. Compare cold-start and steady decode, nt=1 versus nt=2..4, and forced AVX2 on the same Zen 3 machine. Do not extrapolate from B570/5600X predictions or Intel AVX-VNNI/AVX-512/AMX measurements.

Prior work and external references

Registry-v11 and the 21 earlier reports were consulted for scope and rejected leads. The existing token-group decode reuse is already implemented. Two-row IQ4_NL, compiler swaps (including GCC Down), and generic prefetch proposals are previously rejected or measured worse at engine level and are not proposed again. Round 9 is specifically a cross-window hot-expert side cache, which has not been measured. The registry also records that the per-request ms_multi_gu/q/down diagnostic patch at 7d0105f2 is reviewed but unbuilt/unmeasured; use that evidence when choosing which phase to profile.
