# SYCL prefill exact expert-major reuse audit (2026-10-09)

## Scope and summary

Read-only inspection of base worktree `/home/yayoi/ghq/github.com/yqYo1/Strata/.worktree/sync-upstream-v0.1.41-20261009`, commit `23268953314d12588fd3f496414a46bd426a7306`, especially `sycl/src/prefill/prefill.cpp`, plus the current layer-major streamed-KV implementation report and prior reports/registry. No source changes, build, test, model run, GPU, profiler, service, or git operation was performed. Capacity figures below are shape-derived, not measured allocation peaks or timing.

The proposed cross-chunk expert-major schedule is algorithmically possible only if the implementation separates each layer's first (attention) half from its second (MoE) half while preserving QSA/GDN/PLE state order, saves the post-attention expert inputs and exact route metadata, and delays residual commit until that layer's MoE outputs are available. But one-pass dequantization per expert then creates a large exactness/storage problem: the current combine applies ten routed outputs in router rank order using FP32 FMA. If experts are processed in expert-ID order, their contributions must be retained until the combine can consume them in original per-token rank order. A full FP32 contribution plane is **25 GiB per layer at 262144 tokens**, before the already-required 10-GiB layer-major residual plane and 3.094-GiB host KV. This introduces large host/device traffic every MoE layer. Reordering the ten additions or accumulating by expert instead changes floating-point results.

A narrower, potentially cleaner weight-reuse candidate is to dequantize one layer's 512 experts once into an FP16 device cache, then keep the existing per-chunk attention/router/expert/combine/GR order. For 2560×640 SwiGLU geometry, FP16 gate+up and down matrices total **4.6875 GiB** for all 512 experts, plus the temporary packed source/cache and existing scratch during conversion unless the packed source is streamed/released incrementally. This avoids host activations and preserves current chunkwise combine order, but target B570 free VRAM and conversion peak are unknown. It is a different resource tradeoff from the requested host-intermediate schedule and should only be measured as a separate narrow experiment. Neither candidate is qualified or recommended for default use. Do not revive XMX/fused-kernel work; existing SYCL XMX is separately audited and has no production MoE caller.

## Existing SYCL layer and MoE dataflow

`run_layer_major` loads one layer's expert blobs into a temporary one-slot-per-expert `ExpertCache`, sets `stage_lb_=layer`, `stage_le_=layer+1`, then calls `run_impl(tokens,n,pos0)` (`prefill.cpp:2612-2616,2683-2745`). `run_impl` iterates chunks in token order and executes a layer's two halves in order: attention/GDN/QSA half, GR write, then MoE half, GR write (`:3501-3564,3562-3644,4945ff`). `on_chunk` persists the resulting full residual rows after the full layer (`:2726-2744`). Thus the existing schedule reuses the *compressed one-layer blob cache* for the layer, but each chunk independently routes and calls `compute` for the routed experts.

The FP16 fallback's native expert `compute` lambda runs `iq_dequant_gu_f16` and `iq_dequant_f16` (or `blob_dequant_f16`) for each routed expert invocation, then gathers expert rows, runs `m.gemm.f16` for gate/up, `swiglu_interleaved`, and another `m.gemm.f16` for down (`:4706-4711,4777-4803`). Layer-major repeats this path in each 8K chunk, so an expert routed in multiple chunks is dequantized in each of those chunk calls. This is a code-path fact, not a measured count or evidence dequant is the bottleneck. The path first groups token/top-k assignments by expert in ascending expert ID; `cnt/off/fill` and `src/slot` are constructed at `:4077-4162`, then `order` lists active experts (`:4163-4169`). Per expert, `ne=cnt[e]` selects its routed rows. In noncompact mode these are gathered to `Xs`; compact mode gathers that expert's rows to a smaller scratch (`:4791-4800`). Each expert's gate/up and down outputs are FP32 GEMM results, while `Hh` is FP16 after SwiGLU.

Before this path, router input is `mixed_bf` (BF16 projection of the post-GR mixed row; possible BF16x2 low-part path), router logits are projected then `route()` writes top-10 IDs and FP32 weights (`:3974-3984`; route kernel `sycl/src/prefill/kernels.dp.cpp:1675-1734`). `route_kernel` softmax-normalizes logits, selects ten distinct expert IDs by score rank with tie-break by lower expert ID, and renormalizes selected weights (`:1687-1733`). Shared expert gate/up/down and its scalar gate are separately calculated for each chunk from `mixed_h`/`mixed_bf` (`prefill.cpp:3977-3984`).

`m.Dm` contains expert outputs in packed expert-row order for the chunk, and `slot[t,k]` maps each token's route-rank slot to that row. `moe_combine` reads all ten contributions in route-rank order, starting from zero and applying FP32 `fma(weight, Dm, sum)` for k=0..9, then adds `shared * sigmoid(shared_gate)` (`kernels.dp.cpp:1814-1832`; vectorized kernel is explicitly documented bitwise equal and preserves k order `:1834-1874`). Its result `bo` is then consumed by the FFN GR write. Therefore merely looping experts outside chunks and immediately accumulating their output by expert ID is not exact relative to existing behavior. The `slot` indirection means a new implementation can preserve route order if it stores each per-expert result into its original route slot and invokes the unchanged combine later.

The shared residual `rows` plane is four hyperconnection streams, not one 2560-wide hidden row: `D=2560×4=10240` floats/token (`prefill.cpp:112,2647`). It already costs 10 GiB at 262144 and carries the canonical layer input/output. For every next layer, all prior-layer MoE/GR output for those rows must be complete. QSA K/V plus indexer and GDN recurrence/conv are independent canonical session states and must be advanced once in token order during attention; they cannot be reconstructed from router metadata. PLE at layer 1 is stateful across tokens (`:3506-3560`) and must execute once in original order, before its affected attention computation. The earlier staged-KV report's one-stage reuse is orthogonal: it changes only QSA storage/copy lifetime and does not solve the MoE activation/output problem.

## What a host-intermediate exact schedule would require

For a single layer, a safe conceptual sequence is:

1. For chunks in original order, run PLE as applicable, QSA/GDN attention, and the attention-half GR write. Keep all QSA K/V/indexer appends, GDN recurrence/conv updates, and PLE-history advances in that same order. Commit the post-attention residual rows for every chunk, but do not run that layer's MoE/FFN GR write yet.
2. For each chunk, compute its FFN GR-read input, route top-10 IDs and exact FP32 weights, and shared scalar gate. Save the expert input in FP16 (`mixed_h`) and route metadata. Router and shared gate may be completed while the row is on device; only resulting IDs, weights, scalar gate and the expert input need survive. Preserve input FP16 bits; storing FP32 `mixed` and converting later is not needed for native FP16 expert input but router projections must already have run on the exact BF16/BF16x2 input.
3. For each expert in fixed order, load/dequantize its weights once and process its rows from every chunk. Keep the same per-chunk row order and per-expert GEMM M dimension as the original path if exact GEMM behavior is required. Store each down output at that assignment's packed row/route slot in a host plane.
4. In original chunk order, restore that chunk's outputs to the existing `Dm` workspace, run the existing `moe_combine` unchanged in k=0..9 order, compute/reuse shared FFN output and gate, then run the original FFN GR write. Only after all chunks are finalized may the next layer start.

This requires splitting `run_impl`'s coupled half loop and its single `on_chunk` completion point (`:3501-3564,4945ff,2726-2745`) into attention and FFN phases. A plain outer expert loop is incorrect because the next layer requires the completed MoE/GR output, while the current chunk loop couples the two halves. The plan preserves layer-to-layer dependency but delays within-layer MoE until all same-layer attention chunks have been processed. It is only safe if no stateful operation accidentally runs twice and each QSA/GDN/PLE state sees the same token sequence.

For a phase implementation, the 8K chunk can remain the arithmetic tile: process each expert's rows chunk-by-chunk with the same `ne`, route-local order, oneMKL call shape, SWIGLU kernel and down-output layout, while retaining the dequantized expert matrices across chunk calls. This avoids changing per-call M dimensions and makes output comparison sharper. However, it does not avoid staging all chunk results to host until rank-ordered combine, and host input staging still feeds later GPU expert GEMMs.

## Capacity at max context (binary GiB, no padding)

Model-local constants and buffers: `N=2560`, `D=10240`, `K=10`, `NE=512` (`prefill.cpp:112`). Context `P=262144` is 32 existing 8192-token chunks. Current scratch is allocated for chunk `T`, not `P` (`:1262-1301,1333-1351`).

- Existing four-stream layer residual plane: `P×D×4 = 10,737,418,240 B = 10 GiB` host when the optional GPU prefix is zero (`:2617-2648`). It is already required by layer-major.
- Saved per-token expert input `mixed_h` in FP16: `P×N×2 = 1,342,177,280 B = 1.25 GiB`. It is one input per token, reused for all chosen experts. Using 4-byte `mixed` instead would be 2.5 GiB and would not be necessary for the existing FP16 expert input path.
- Route IDs and weights: each is `P×K×4 = 10 MiB`; optional saved `slot` and `src` each another 10 MiB. Four full arrays total 40 MiB; prefix offsets/counts are negligible. Save the exact FP32 weights from `route()`, not recomputed weights.
- Exact per-route FP32 expert output contribution plane: `P×K×N×4 = 26,843,545,600 B = 25 GiB`. There are ten weighted contributions per token. This is the main host-memory cost required to defer combine while preserving current route-rank FMA order. At one chunk, the current `Dm` workspace is `8192×10×2560×4 = 838,860,800 B = 800 MiB` (`:1341`); it is reused and need not grow on GPU.
- Combined just these host allocations with full int8 KV from round 3: 10 + 1.25 + 0.039 + 25 + 3.094 ≈ **39.38 GiB**, before PLE staging, runtime allocations, allocator overhead, decode/session objects, filesystem page cache, and temporary copy buffers. At 128 GiB RAM this is mathematically below physical capacity, but not a measured peak and does not establish acceptable paging or memlock behavior. Treat the 25-GiB contribution store as pageable system memory unless a bounded pinned ring is explicitly designed; pinning it all is not a reasonable assumption.
- For per-chunk host/device transfer, the output plane would require at least 25 GiB D2H per MoE layer to preserve all route results; 48 MoE layers imply 1.2 TiB D2H over a full context. Copying contributions back to GPU for the unchanged combine adds up to another 1.2 TiB H2D. CPU-side combine could reduce return traffic to one 2.5-GiB combined output per layer, but would move 25 GiB/layer off device and requires a CPU implementation that exactly reproduces the ordered FP32 FMA and sigmoid/shared add. These are byte counts, not bandwidth/time estimates.
- FP16 dense weights for one expert are gate/up `1280×2560×2=6,553,600 B` (6.25 MiB) plus down `2560×640×2=3,276,800 B` (3.125 MiB), total 9.375 MiB. All 512 experts are **5,033,164,800 B = 4.6875 GiB**. Two `DQ` scratch pairs only hold 18.75 MiB in total (`:1351`); current code overwrites them rather than caching all experts. Retaining this full layer's decoded matrices avoids the 25-GiB output plane and keeps current chunk/combine order, but free B570 memory and conversion peak must be measured. A raw packed one-layer cache remains live during conversion unless streamed or explicitly freed, increasing peak. Do not infer fit from card capacity alone.

Smaller dimensions can use the same formulae. For context P, host expert input grows as 5 KiB/token; routed output grows as 100 KiB/token; residual grows as 40 KiB/token; int8 QSA host KV grows as 12×1056=12,672 bytes/token. Any schedule that stores only a small prefix but promises all-token expert-major reuse is not the described exact schedule.

## Exactness limits and possible first step

The original result for token t, feature d is concretely `s=0; for k=0..9: s=fma(w[t,k], Dm[slot[t,k],d],s); bo=s+shared[t,d]*sigmoid(sg[t])`. Processing expert IDs in increasing order would visit each token's routes in an unrelated order; because FP32 addition/FMA is non-associative, storing one FP32 running sum per token cannot reproduce this sequence if an earlier-ranked contribution is still unavailable. Exact expert-major execution therefore must either retain all ten contributions (25 GiB at 256K), retain the ten expert weights simultaneously so each token can be evaluated in route-rank order without re-decode, or accept a changed accumulation order/precision. The last choice is outside an exact-output objective.

A small source-only design review should first compare existing layer-major `compute` call/dequant counts against a candidate layer-dense-weight cache while leaving chunk execution untouched. If measured free VRAM permits 4.69 GiB weights plus conversion temporary and existing layer scratch, this is the least invasive exact candidate: dequant each layer's experts once, run the existing per-chunk expert path and unchanged `moe_combine`, and compare state/logits. If it does not fit, the true host expert-major path needs a bounded-memory experiment with P=2×8192 first, but its full-context cost must remain reported as 25 GiB outputs and transfer accounting; a 16K success does not qualify 256K. No code change/build/test is suggested for this report turn.

A bounded alternative for research only is expert-by-route-rank, then expert ID, accumulating each rank into a per-token FP32 accumulator. This preserves route order but can dequantize the same expert for up to ten ranks, which defeats one-decode-per-expert reuse. It also cannot be called exact expert-major *reuse* without retaining dense weights. It is not recommended absent measured evidence that rank-filtered decode savings outweigh repeated dequantization.

## External implementations and how far they transfer

- DeepSpeed’s inference path `deepspeed/ops/transformer/inference/moe_inference.py` dispatches router-selected rows, runs a per-expert loop, then combines expert outputs with the route weights (`expert_exec`, `scale_expert_output`); its tensor shapes make the expert-output materialization explicit. The separate `deepspeed/moe/ep_experts.py` grouped-GEMM path groups rows using `num_tokens_per_expert` and offsets for gate/up, SwiGLU, and down. Both are useful dispatch/grouped-compute patterns, but they assume device-resident input/weights and one forward batch; neither supplies Strata’s host-stored cross-chunk schedule or exact route-order FMA contract. Sources: https://github.com/deepspeedai/DeepSpeed/blob/master/deepspeed/ops/transformer/inference/moe_inference.py and https://github.com/deepspeedai/DeepSpeed/blob/master/deepspeed/moe/ep_experts.py
- S-MoE's layer-major prefill write-up is the closest external conceptual match: it states that exact routing is computed per token and each claimed expert is applied to all routed tokens in the batch using a two-pass gate/up and down dispatch with one dequantization stream. Its documented batch is bounded (up to 64 tokens) and combines layer-major execution with a vault/streaming design; it is useful as an implementation sequence, not proof for Strata's 8192 chunk, 256K context, QSA/GDN state or floating-point result order. The author/project doc is not a vendor-neutral benchmark. Source: https://docs.s-moe.com/v1/internals/layer-major-prefill
- NVIDIA TensorRT-LLM's MoE-as-dense-GEMM primary engineering post distinguishes routed expert grouped GEMM from a dense expert formulation and emphasizes token-count regime; its measured DeepSeek-V3-style B200 TP8 module result is up to 1.12× for 64–208 tokens and excludes surrounding all-reduces. This is evidence that crossover is hardware/batch-specific, not a B570 forecast or proof that dense execution helps Strata. It keeps routing/TopK and shared experts outside the current dense backend. Source: https://github.com/NVIDIA/TensorRT-LLM/blob/main/docs/source/blogs/tech_blog/blog24_MoE_as_Dense_GEMM.md
- FlexGen's paper schedules weight, activation and attention-cache tensors across GPU, CPU and disk using a resource/throughput optimization for latency-insensitive batched inference. It contributes the resource-placement viewpoint but is not an expert-major MoE implementation or evidence for Strata's exact combine. Its OPT-175B / 16-GiB numbers are its own workload/hardware and should not be transported. Source: https://arxiv.org/abs/2303.06865
- AirLLM's repository is described as layer-by-layer weight streaming. That is ordinary model-layer offload; it does not establish per-expert cross-chunk reuse or QSA/GDN/PLE scheduling. Treat it only as a general weight-residency reference: https://github.com/hmzainjamil/airllm
- Prior Strata report `prefill-code-audit-addendum.txt` discusses staged expert blobs, host grouping, native dequant+oneMKL versus the missing fused path, and notes that future-layer routing is unavailable until its layer input exists. `prefill-xmx-existing-code-audit.txt` audits `xmx_gemm_iq` (already implemented but with no production call path; separate B70 performance caveat). The current layer-major streamed-KV implementation is code-only and addresses the one KV stage lifetime. None implements the cross-chunk router/activation/route-output store proposed here. Do not present these prior mechanisms as new work.

## Qualification plan if a candidate survives memory review

1. Add no default behavior. First instrument native fallback per layer/chunk to count each active expert's dequant call and row count, without timing claims.
2. On one MoE layer and exactly two 8192 chunks, compare baseline to an expert-major prototype. Keep each expert's per-chunk GEMM shapes and row ordering unchanged; compare FP16 `mixed_h`, route IDs, FP32 route weights, each down output, each final `bo`, post-GR rows, and canonical QSA/GDN/PLE/indexer state. Require exact output/state parity if claiming exact scheduling. Exercise expert-skew, zero-row experts, and all ten distinct routes.
3. Repeat on one 32K layer, resumed prefix and page/tail boundaries; verify chunk and PLE/QSA/GDN state advances once only. Check the host output map covers every `(token,k)` exactly once and `moe_combine` reads original ranks.
4. Before 256K, report physical host and device peak bytes, pinned bytes, copy counts and queue waits. Full-context qualification must keep all 262144 tokens and existing 8192 chunks; compare saved/restored full KV/indexer/GDN/conv/PLE states and boundary positions. Measure end-to-end B570 time only after parity, separately for host-output and dense-device-cache variants. Do not infer performance from reduced dequant counts alone.
