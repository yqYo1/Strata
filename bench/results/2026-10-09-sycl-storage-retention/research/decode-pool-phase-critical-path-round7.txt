## Result

The native serve path already accumulates the useful phase boundaries, but its per-request `STRATA_DECODE_TIMING=1` line does not print the `ExpertPool::ms_multi_gu`, `ms_multi_q`, and `ms_multi_down` counters. The smallest useful diagnostic is to snapshot those existing cumulative counters at the same request boundary as `DecSnap`, then print their request deltas normalized per verification window next to the existing wall-clock decomposition. This distinguishes gate/up, intermediate activation quantization, and down work without adding timers inside AVX2 kernels or workers.

Those three values are *phase wall durations on the host callback path*, not total CPU core-time and not serialized additions to physical decode time. For each layer, the verifier waits for the router/GPU doorbell, invokes the host callback, and lets GPU-resident work and expert copies progress while the CPU handles CPU-miss experts. The callback returns before the verifier publishes the CPU plan/output and resumes the GPU graph. CPU phase time can therefore be partly hidden by GPU work. Use physical request/window wall time and emitted tokens as the outcome; never calculate decode latency by adding GPU-stage event totals to the CPU phase sums.

## Concrete active call chain and timers

- `generate.cpp` constructs one `ExpertPool` for the SYCL process (`:4161`), used by the `Drive` object. In the serve speculative-window path, `drive_pool_multi` calls `expert_pool_dispatch_multi` once per layer/window (`:1010-1017`; call at `:12393`). The native IQ pack enters `run_split_multi_native` (`expert_source.cpp:2793-2798`). This is the active multi-token route, not the single-token `run()` path.
- At `expert_source.cpp:2576-2585`, dispatch starts its own `c0` timer, begins the layer, and submits the GPU plan/copy work. With CPU misses, per-token input activations are quantized between `c1` and `c2` (`:2718-2735`, native `native_quant_act` at `:2727-2732`), routed CPU jobs are assembled between `c2` and `c3` (`:2736-2793`), and pool work plus remote/peer completion is between `c3` and `c4` (`:2793-2817`). `Drive::cpu_ms` wraps the entire dispatch call (`generate.cpp:1014-1017`); it is main-thread elapsed time for this callback, not the sum of worker CPU time.
- `run_split_multi_native` (`pool.cpp:759-787`) executes each native batch sequentially: gate/up row phase (`run_phase(5)`), then the serial per-expert/per-token FF activation quantization (`native_quant_h` or Q2 quantization, lines 772-776), then down rows (`run_phase(6)`). It records `b-a`, `c-b`, and `d-c` into `ms_multi_gu`, `ms_multi_q`, and `ms_multi_down` (`:769-783`). The middle phase is distinct from input activation quantization in `drive.d.ms_actq`; it quantizes the FF output for the Down dot.
- GU and Down are pool-parallel over flattened row tasks. `phase_tasks` chooses `min(rows, tasks_)`, or with auto setting zero `3 * (workers + host participation)` (`pool.cpp:716-718`). The baseline configuration supplied for this audit is five workers plus main-thread draining, hence auto 18 tasks per phase. The explicit six-task candidate is owned by the root's current 32K qualification; this audit did not run or alter it.
- `run_phase` includes `wait_parked`, batch publication, worker plus optional host drain, `wait_done`, and re-park (`pool.cpp:688-698, 489-537`). Thus `ms_multi_gu/down` include synchronization and host drain elapsed inside the phase, not just SIMD kernel execution. `ms_multi_q` is the serial quantization loop plus loop overhead. `phase_ms()` in `pool.hpp:196-207` describes the separate regular `run()` timing; `run_split_multi_native` does not add its barriers to those three `phase_ms` buckets. `ms_drain_` also receives aggregate split elapsed in this path (`pool.cpp:787`), so it is not a clean multi-token work-only timer.
- `Verifier` waits for the GPU to reach the host boundary, calls the pool callback, then publishes the host plan/output and resumes the graph (`verify.cpp:3057-3112`; other verifier route at `:1712-1742`). `ms_wait` is the pre-callback GPU-reach wait; `ms_pool` is the host service/callback interval (and in one route includes a copy wait). Those host intervals occur at per-layer synchronization points, but asynchronous GPU work during the callback may overlap them.
- Serve's request-level `STRATA_DECODE_TIMING` snapshots verifier/dispatch counters before the request at `generate.cpp:10372-10392`, then prints request-window, wait/pool/host, dispatch plan/actq/jobs/run, commit/draft, route counts, and GPU profiles when separately enabled at `:11277-11300`. It currently omits `pool.ms_multi_*`. `generate.cpp:12539-12543` does print the three phase counters, but in the standalone speculative-run summary, not in the per-request serve timing line. The pool counters persist for the pool lifetime, so serve must difference request-start and request-end snapshots rather than report raw totals.

## Minimal diagnostic proposal

Keep `STRATA_DECODE_TIMING` as the opt-in gate. Extend its existing `DecSnap` with the three `pool.ms_multi_*` values and `pool.multi_bytes`; snapshot them at the same request start/end. Print one additional line per completed request, for example:

```
strata decode CPU pool phases: GU 8.2, FF-quant 1.1, Down 6.4 ms/window (host phase wall; nested with GPU); CPU expert jobs 7.8, routed entries 9.5 per layer-window; packed bytes 10.2 MB/window
```

Use the actual request deltas, divided by the number of completed verify windows; report zero/omit rates when there are no windows. `drive.d.multi_misses` is the count of distinct CPU expert jobs accumulated after dispatch (`expert_source.cpp:2827`); `drive.d.multi_entries` counts routed entries sent to CPU (`:2791`). These should also be request-delta values, not the process-lifetime counters. The existing `DecSnap` already takes both. `pool.multi_bytes` increments by `n * f.bytes` at the end of each multi call (`pool.cpp:785`); label this as packed expert-blob bytes submitted to the CPU path, not measured DRAM traffic. Existing worker/host and affinity startup lines identify the participating threads. If the task setting is available to this run, print it as `auto` or the explicit setting, while avoiding a claim that `auto` always resolves to 18 when thread configuration differs.

The existing `ver.ms_wait + ver.ms_pool`, `drive.d.ms_plan/actq/jobs/run`, `dt_run`, `dt_commit`, `dt_draft`, and decode physical wall time already answer the larger attribution question. Display the new phase line adjacent to (not arithmetically added into) `strata decode timing`. Do not fold the per-layer phase totals into `verify ms/window` or compare the sum directly to 14.29 ms/output token. The serve line's `dt_run` is the verify-window wall interval; `decode_ms` is request decode wall including loop work through the final commit wait. Divide physical elapsed time by *emitted* tokens for the observed output rate; divide CPU phase totals by windows for the phase view. Keep the average T, accepted/output tokens per window, and CPU route counts so differing MTP acceptance or GPU cache hits do not masquerade as pool speed changes.

First pass should not add per-task timers. If phase totals identify a long GU/Down interval and the task sweep remains ambiguous, a follow-up diagnostic may collect per-worker claimed-task counts and phase elapsed spans, plus a work proxy `sum(rows assigned * expert.nt)` across each flattened range. Keep that diagnostic separately opt-in: per-task clocks/atomics can alter short CPU phases, and task count alone does not prove work balance because experts carry different token-group sizes. Compare the same routing/state and task configuration; report the distribution and wall outcome. No timing from this audit or other hardware is transferred to B570.

## How to read outcomes

- High `FF-quant` relative to the multi-phase subtotal indicates the current serial middle segment is a candidate to investigate; it does not prove it is exposed on the critical path until request/window wall time improves in a controlled change.
- High GU/Down phase wall with low per-window decode wall contribution suggests much of CPU work may be hidden behind GPU/copy work. A phase timing alone is not a reason for a kernel rewrite.
- High `ver.ms_wait` with modest pool phase times points toward GPU-to-host arrival latency or other work before the callback; high host callback/dispatch with modest GPU stage time puts more focus on host planning/service, but GPU stage event sums can themselves overlap and profile mode perturbs timing.
- Compare `tasks=0 (auto 18)` and the root-controlled `tasks=6` only under the same server request, restored context, CPU workers/affinity, cache/KV settings, and acceptance behavior. Read the root's held four-run 32K diagnostic only after it completes; this research task intentionally did not run any of those tests. A task change may trade shorter queue/dispatch overhead for load-balance tail. Confirm with paired/interleaved physical decode timing, not just lower `ms_multi_*` or isolated component throughput.
