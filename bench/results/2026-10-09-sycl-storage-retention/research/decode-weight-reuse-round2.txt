## Findings from the target source

1. The native expert blob already has a row-oriented, zero-conversion layout. `include/strata/kernels/cpu/expert_layout.hpp:3-6,18-42` says each layer records its own byte size and format; each expert address is `layer_offset + expert * blob_bytes`. `src/kernels/cpu/native_expert.cpp:46-80` derives `gu_row`/`d_row` with `ggml_row_size`, then lays out one blob as `[gate rows][up rows][down rows]`, with `up_off = gu_row*n_ff`, `down_off=2*up_off`, and size `down_off+d_row*n_embd`. GGUF checker `src/core/expert_source.cpp:3630-3654` checks expert tensor shapes `[n_embd,n_ff,n_expert]` for gate/up and `[n_ff,n_embd,n_expert]` for down. This is native packed rows; there is no decode-time dequantized duplicate of all expert weights in the CPU path.

2. CPU gate/up loops pair corresponding gate and up row pointers (`native_expert.cpp:164-174`) and the multi-token kernels reuse decoded weight data across the token group (`:125-130`). Down likewise iterates rows (`:178-204`). In the current IQ3_S layout, gate/up and down use the ggml block row format selected by the per-layer `NativeFmt`; any proposed tile must honor `ggml_row_size` and quant block boundaries. Repacking to interleave gate/up rows might improve locality, but it adds a full second representation or requires changing pack/load compatibility. No source evidence shows duplicated reads between experts or across layers that could simply be eliminated. Gate and up are different matrices, so their bytes are intrinsically distinct; they can share cache residency in a paired row kernel but not weight values.

3. Each routed expert is added to a job once per verify window and accumulates its token pointers (`src/core/expert_source.cpp:3323-3345`); the pool calls `run_split_multi_native` once per layer (`:3347-3351`). Each such job computes gate/up, quantizes intermediate activation, then down. Native pool `src/kernels/cpu/pool.cpp:759-787` may batch many distinct experts only up to `kMaxSplitMulti`, so overflow experts run in later batches. This batching is a buffer-capacity constraint, not repeat weight reads within a job. The layer’s job blobs are reused through all token rows of that expert in the current window.

4. GPU/cache classification happens before CPU work (`expert_source.cpp:3250-3274`). CPU activation quantization then occurs serially for every token when any CPU expert exists (`:3275-3289`); only after that does the code collect unique CPU-miss expert IDs and call `d.src->prefetch` (`:3290-3298`). CPU job assembly and native pool execution follow (`:3323-3351`). This ordering exposes one conditional scheduling opportunity: on the staged/file-backed source path, exact expert I/O prefetch begins only after activation quantization. `FileExpertSource::prefetch` can enqueue uncached blobs to I/O workers and return (`src/core/expert_source.cpp:1297-1310`), then the CPU kernel waits on requested stage pages when it reaches them (`:1280-1294`). For an arena/RAM-resident source, this is not a useful I/O optimization and must be a no-op. The present B570 setup’s active source mode must be checked before considering it.

5. The expert source groups chunks and has existing stage buffers, in-flight IO jobs, cache lookup, and exact source fallback; therefore “add a generic prefetcher” is not new. The narrow observation is specifically the order between exact current-layer miss discovery/prefetch and current-window activation quantization on staged/file-backed loads. Since routing IDs are already known before either, prefetching the current exact miss set before serial activation quantization can hide some cold-page wait behind work that already must happen. Its ceiling is bounded by the lesser of that activation-quantization duration and the outstanding file/page-fill duration, and only when cold or uncached pages exist. Quantization is described as a few microseconds/token/layer in `native_expert.cpp:85-88`; no B570 window-level saving should be claimed without measurement. The prior round’s pool quantization parallelism suggestion is a separate implementation and must not be combined in the first A/B.

## New small implementation candidate (conditional)

**Move only the current-layer exact-source prefetch call ahead of serial CPU activation quantization.** First gate on the active source being staged/file-backed and `prefetch` being nonblocking for this source; otherwise keep existing order. The current exact list can be built from route IDs and GPU `kind` before the quantization loop. Keep activation quantization and all CPU expert math byte-for-byte/order-identical. No prediction, omitted expert, changed precision, or change to which rows are computed.

This is a candidate only if the actual source is staged and measurements show nonzero cold/uncached reads with wait time on those exact blobs. The active stated mode uses RAM-resident experts, so if source is arena-backed or all pages are already resident, expected gain is zero and this candidate should be closed without implementation. This candidate targets file/page-fill overlap, not PCIe DMA; it cannot be used to explain or reduce the ambiguous PLE counters.

Minimal experiment for the main agent: instrument existing `FileExpertSource` counters for current-layer exact-prefetch demand, fetched bytes, useful/unused prefetches, and CPU wait-for-stage time; verify the active source mode and page residency first. Then use the exact same 32K restored state and 256K-complete state, alternate baseline/candidate with fixed prompt, MTP4, cache and pool settings. Compare physical wall-clock output latency, source bytes and wait, serial quantization time, CPU pool time, accepted MTP tokens/window, and logits/output. Require a stable >=3% decode win beyond run noise and a corresponding drop in measured cold-page critical wait; otherwise revert. 256K state must be fully constructed and decode checked at max context before qualification.

## Larger design candidate (research lead, not a ready implementation)

**A per-layer cost-aware exact CPU/GPU work split with asynchronous transient GPU staging for CPU misses.** The existing `--pciefrac` is a fixed fraction knob and is already known; this design would use actual current-window routed expert IDs plus measured per-layer CPU row cost, GPU queue cost, available expert-cache slots, and copy bytes to decide whether a CPU-designated expert should run on CPU or be staged to the B570. Preserve all expert outputs and router weights. Double-buffer transient copies and overlap their transfer with CPU work for other experts, then join before combine. Never skip, mask, or approximate an expert.

This is distinct from changing cache capacity or the fixed `pciefrac` knob, but likely expensive: the expert bytes are in native GGUF layout, the B570 link is only measured around 6 GB/s, and the CPU’s sustained memory bandwidth/kernel time is unknown. Transfer can help only when its cost is hidden by CPU work or is lower than CPU critical time; a simple bound per candidate batch is `time >= bytes_to_stage / measured_transfer_rate`, and speedup cannot exceed the CPU work actually removed from the critical path. Do not predict a positive result from cache-hit counts alone. GPU staging may also displace persistent expert cache or resident KV from 10 GiB; record physical VRAM and preserve current 32K/256K capacity requirements. Priority is low until per-layer profiling reports CPU kernel critical time, exact bytes and transfer completion independently.

Suggested first research/prototype measurement (main-owned, not performed here): for each verify window/layer record CPU expert IDs, token count per expert, native blob bytes per layer, cache hit/refused, CPU run wall time, actual async H2D bytes and event completion, queue wait, and whether copy overlaps CPU work. Isolate a single-layer replay of exact outputs before full decode. Proceed only if a stable layer exists where measured transfer finishes under useful CPU work and the GPU has headroom; abandon if DMA is exposed, persistent cache/KV evictions increase latency, or full logits diverge beyond accepted backend floating-point tolerance. Never use a 64-token output-only match as proof of MTP/LP equivalence.

## Correctness, capacity, and floating-point checks

Reordering I/O submission does not alter mathematical operations; verify exact prefetch returns each requested `(layer, expert)` blob and never changes `kind`/routing IDs. For a new CPU/GPU split, compare full logits and state at each token across CPU-only/GPU-only/hybrid runs, including MTP draft and verify paths, routing IDs/weights, PLE state and all QSA K/V/GDN/indexer state at layer/window boundaries. Distinguish ordinary floating-point ordering/rounding differences from undefined behavior: use sanitizer/debug checks where suitable, guard every row and scratch range, ensure stage/event lifetimes outlive kernel use, and repeat deterministic state restoration. The 256K qualification must complete all context tokens without truncation/shortening; exercise boundaries around 32K resident KV, 32K+1 streamed KV, intermediate long context, and exactly 262144, then resume decode and compare state/logits with the established reference path. Check VRAM, pinned RAM, RSS and allocations throughout; do not let cache growth silently reduce KV capacity or trigger device paging.

## External implementation references and limits

- KTransformers SOSP 2025 paper: https://madsys.cs.tsinghua.edu.cn/publication/ktransformers-unleashing-the-full-potential-of-cpu/gpu-hybrid-inference-for-moe-models/SOSP25-chen.pdf . It motivates placing shared experts on GPU and routed experts on CPU and analyzes hybrid scheduling/layout. Its server CPUs, models, GPUs and measurements do not predict Ryzen 5600X/B570 performance.
- Upstream llama.cpp expert cache source: https://github.com/ggml-org/llama.cpp/blob/master/src/llama-moe-cache.cpp . Source is a useful example of expert-sized host-to-device cache fills and slot management. It does not prove benefit for this B570 link or this runtime’s event/queue behavior.
- Upstream GGML quant block declarations: https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-common.h and row-size/type implementation: https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml.c . These are the primary references for packed block layout; native pack keeps the tensors in that format.
- vLLM MoE expert parallel guide: https://docs.vllm.ai/en/latest/serving/expert_parallel_deployment/ . Grouped GEMM and async scheduling are useful general context, but focus is GPU expert-parallel execution and not AVX2 CPU-offloaded IQ3_S decode.
- Intel LLM Scaler source: https://github.com/intel/llm-scaler . It targets Intel XPU deployments and different quantization/CPU-GPU combinations; no relevant B570/Ryzen/IQ3_S result was found.
- Individual vLLM CPU offload implementation lead: https://github.com/leoustc/vllm-moe . It describes CPU canonical expert weights and GPU prefetch, but is an independent implementation with different kernels/hardware. No measured result is transferred to Strata.

A separate newer study surfaced in search, “Achieving Cloud-Grade SLOs for Local Mixture-of-Experts Inference through CPU-GPU Hybrid Design” (https://arxiv.org/abs/2606.10493), reporting AVX-512 FP8 and server hardware. It is useful design context only; its reported tok/s is not a B570 forecast and the CPU ISA/weights differ. No unique implementation result there justified a direct port in this pass.
