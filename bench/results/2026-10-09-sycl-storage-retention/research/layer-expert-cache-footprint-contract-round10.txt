## 結論

layer-majorの一層用cacheは512 slotを`MAXBLOB()`幅で一括確保します。今回のIQ3_S packでは`MAXBLOB=2,662,400 B` (最大のlayer 47)、したがって固定容量は`512 × 2,662,400 = 1,363,148,800 B = 1.26953125 GiB`です。GPU receiptの失敗値`1,363,148,800 B`と完全一致します。実際の各layerはformatにより737.5〜1,300 MiBのpayloadしか持たず、slot末尾の未使用域はcache内にゼロ初期化されたままです。

この差は個別layer長を使えば減らせます。ただしlayer 47は最大値そのものなので、全512 expertを一度にresidentに保つ設計のピーク要件は1.2695 GiBから下がりません。receiptでは2回目のread前にExpertCacheが「1.27 GiB必要、free 0.99 GiB」と拒否し、prefillは開始していません。このrunはfull-lifecycle passでも性能対象でもありません。最大層のallocationを除くためには、既存のchunk内stagingへ戻るfallbackなど、同時resident expert数も制限する設計が別途必要です。

## 現行のslot・copy契約

- `sycl/src/prefill/prefill.cpp:115,2612-2616`は一時cacheを`open_sized(vector<int64_t>(n_expert, MAXBLOB()), 1, n_expert, err)`で作ります。全slotは同じ最大長です。`run_layer_major():2690-2715`は現在layerの各expertをsourceから取得し、各slotへ実長`layout.blob_bytes(layer)`だけcopyします。そのlayer内では1 expertを1 slotに対応させ、`residency[e]=e`です。GPU slot間隔は最大長ですが、blob内のGU/up/down offsetはそのlayerのmetadataとblob先頭からの相対offsetを使うため、短いlayer用のslot tailは読まれません。
- `ExpertCache::open_sized()` (`sycl/src/core/expert_cache.cpp:691-719`)は各入力slot長を256-byteへ切り上げ、prefix-sumでslot offsetを作り、合計byte数を単一のallocationとして`open(total_bytes, ..., blob_bytes=1)`へ渡します。現在の`MAXBLOB`および全48個の`blob_bytes`はいずれも256の倍数なので、現行／正確長slotにslot末尾のalignment slackはありません。現行のwasteはmixed-format長を一様な最大長へ広げた分です。
- `open()`はallocation前にfree VRAMを確認し、足りなければ正確な要求/free値を含めて拒否します (`expert_cache.cpp:578-612`)。成功時は一時arena全体をzero-fillします (`:649-679`)。長さを縮める改修では、単に`device_slot(e)`の間隔だけ変えるのではなく、slot offset table・total allocation・zeroing・slot bounds・各copy長を同じ`open_sized`契約で一致させる必要があります。
- 既存layer-majorは層を替える前にcompute/copy/stagerをdrainし、次層の512 expertを同じ一時cacheへcopyします (`prefill.cpp:2683-2715,2747-2754`)。これによりblob pointerの非同期参照が終わってからslotを上書きできます。新しい長さで再openする場合も、先にこのdrainを満たし、`m.cache`/resident mapが古いallocationを指さない状態で置換しなければなりません。`ExpertCache::close()`は通常arenaを解放しますが、copy完了を呼出側が保証する現在の層境界を省略してよい根拠にはなりません。

If one hypothetically summed the current fixed arena across 48 sequential layer visits, it would be 65,431,142,400 B (60.9375 GiB) of capacity; exact packed data over those same visits is 50,292,326,400 B (46.8384 GiB), leaving 15,138,816,000 B (14.0991 GiB) of cumulative slot tail. This is not simultaneous GPU use: only one layer arena exists at a time. PCIe/source payload for a full pass is the 50.292 GB packed size because current code copies each blob's actual layer size once into the layer cache; the unused slot tails are allocation/zero-fill, not transferred expert data. No speed implication follows from those byte counts.

## Safe allocation options and hard limit

1. **Exact-size one-layer arena (straightforward, partial memory relief).** At each layer boundary, after compute and copy completion, close and reopen the 512-slot arena with `slot_bytes[e]=layout.blob_bytes(layer)`. The `ExpertCache::open_sized()` API already has variable slot offsets; for a single layer all 512 lengths are equal and divisible by 256. Keep `residency[e]=e`, copy exact bytes, and pass the new base/offset contract only to that layer's `run_impl()`. This removes the table's 162.5–562.5 MiB tail on 47 of 48 layers. It does not help layer 47 and adds repeated allocation/zero-fill work, so feasibility/overhead are unmeasured. With the receipt's 0.99 GiB free, only 24 layers' exact arenas are <= that free amount before considering concurrent runtime allocations; layer 0 is 1,062.5 MiB and layer 47 is 1,300 MiB. This cannot qualify a full 48-layer request at that reported headroom.
2. **Bounded arena plus existing streaming fallback (full-run safety, no reuse promise).** Add an explicit capacity admission before trying the all-512 arena. When the current exact layer arena does not fit the chosen budget, run that layer through the existing `run_impl()` expert ring with no temporary all-layer residency, letting the established route-order copies and slot-use events operate per chunk. This retains the existing expert order, dequant/GEMM arithmetic, token/chunk schedule, and outputs; it may repeat weight transfers for each chunk and therefore is only a correctness-preserving fallback, not a performance proposal. A hybrid can use exact-size full-layer arenas for fitting layers and fallback for larger ones, but allocation/free boundaries and resident-map reset must be explicit.
3. **Do not treat a tiny LRU as guaranteed reuse.** The expert walk is ordered through routed expert IDs, then each 8K chunk builds a new route. A small cache could repeatedly evict earlier experts and reload in the next chunk; no hit distribution from this task establishes a useful bound. Likewise round 9's bounded dequant cache is a separate extra 9.375 MiB per expert dense FP16 value and is not a substitute for the packed source cache allocation that failed here.

Any variant must retain physical context 262144 and chunk 8192, preserve exact route/token and math order, and wait for all queued readers before resizing/reusing the arena. The 1.2695-GiB single-layer peak is an inherent cost of the current all-512-resident-per-layer contract, not a consequence of alignment padding; reducing it requires relaxing that residency contract with a route-safe fallback. Existing KV-stage and decode-cache mechanisms are outside this report's main recommendation.
