The prior XMX audit's geometry (n_embd 2560, n_ff 640) is consistent, but the type counts above come from the actual pack metadata and are a separate check. `include/strata/artifact/gguf_reader.hpp:83-99` maps 18/20/21/22/23 to IQ3_XXS/IQ4_NL/IQ3_S/IQ2_S/IQ4_XS. ## Dispatch and operations actually used

- `src/kernels/cpu/native_expert.cpp:40-44,125-175` dispatches Gate/Up IQ formats 18, 21, 22, and 23 into the AVX2 multi-token kernel on an AVX2-only CPU when `nt >= mt_min`. Unsupported types fall back to ggml's per-token dot. Default `mt_min` is 2; the same expert with one token therefore uses ggml by default. `STRATA_IQ_MT_MIN` changes this threshold and may change floating reduction behavior; I am not recommending forcing it to 1.
- The pack has only Down types 20 and 42. `native_expert.cpp:178-205` dispatches type 20 to `iq4nl256_down_rows` for `nt >= mt_min` (unless the existing `STRATA_NO_IQ4NL` fallback is set); otherwise it loops over ggml's one-token `vec_dot`. In the pool, type 42 is handled by `q2_rows_any` (`src/kernels/cpu/pool.cpp:651-660`) and the Q2_0 row kernel supports compile-time `NT=1..4` (`src/kernels/cpu/q2_avx2_rows.inl:16-48,51-63`). That kernel decodes each Q2_0 block once and then applies it across the token group.
- IQ4_NL layout and loop: `src/kernels/cpu/iq_avx2_rows.inl:238-287`. IQ4_NL uses 32-weight/18-byte blocks (16 half-scale bytes and 16 code bytes); the real n_ff=640 row has 20 blocks and is block-aligned. Per block the kernel loads packed codes, decodes the codebook magnitudes once, makes absolute weights once, then loops over `NT` Q8_0 activations and accumulates separate outputs (`:254-271`). The native blob keeps gate, up and down as GGUF-native row slices; `native_expert.cpp:65-80` derives each row size with `ggml_row_size` and validates whole-block geometry. No transposition or eager CPU full-precision copy is needed to reach this path.
- Zen 3 / Ryzen 5600X has AVX2 but no AVX-512 or AVX-VNNI. The production `iq_avx2.cpp` separates `plain` AVX2 and target-gated VNNI implementations (`:369-383`); `vnni_on()` calls the runtime CPU feature check. Therefore only plain AVX2 is relevant for this machine. CMake source flags are `-mavx2;-mfma;-mf16c` (`CMakeLists.txt:1188-1205`). The prebuilt CMake cache has AVX-VNNI compiler support enabled, but that does not enable its runtime path on the 5600X.

## Static codegen and arithmetic review

Targeted symbol lookup in the qualified baseline's `libstrata_kernels_cpu.a` found the plain `iq4nl_nt` wrapper. The existing compiled wrapper contains the NT=1..4 specializations and is about 0xa2f bytes. In its targeted disassembly I found no YMM/XMM loads or stores to `%rsp` (no evident vector accumulator spills in this function); the NT=1 path visibly keeps its partial accumulator in a YMM register and uses `vpmaddubs`, `vpmaddwd`, conversion and FMA. This is a static observation of one prebuilt compiler object, not a throughput claim or a claim about every compiler/target. It gives no evidence for the proposed register-pressure failure mode on the qualified build.

Arithmetic hazards were checked against the current source:

- The AVX2 IQ4_NL signed-product path applies `abs(weight)` to the unsigned `maddubs` operand and carries weight sign through activation sign (`iq_avx2_rows.inl:257-268`). IQ4_NL codebook magnitudes are at most 127; Q8_0 activation magnitude is at most 128, so the worst adjacent pair is at most `2*127*128 = 32512`, below signed-int16 saturation at 32767. The subsequent `madd_epi16` pair and per-row accumulation are in int32 lanes; for 640 inputs this is far below int32 overflow. Q2_0's code×activation pair bound is smaller and is documented in `q2_avx2_rows.inl:5-13`.
- IQ4_NL uses `nb = n / 32` and assumes full blocks. The production `NativeFmt` validation enforces block-aligned n, and the actual Down width 640 is 20 complete blocks. Row range ownership is half-open in the pool and each row is written once. Keep those assumptions explicit if changing tile boundaries.
- The current IQ4_NL multi-token kernel's float accumulation order differs from ggml's one-token dot (`iq_avx2_rows.inl:241-242`). Existing `native_expert_parity.cpp:243-259` compares it to ggml on the same Q8_0 activations and uses a relative error cutoff of 1e-5 (source comment says measured 1e-7). This is not bitwise parity. A change must preserve the pool's row coverage and prove finite outputs, full expert rows, all NT sizes and MTP/LP behavior. Group-width-dependent rounding or a 64-token text match alone is not correctness evidence.

## Existing measurements and implementation history: do not repeat rejected work

Several closely related optimizations have already been tried on this exact Ryzen 5 5600X, so they are not new proposals:

- Commit history records a two-output-row IQ4_NL kernel sharing Q8 input blocks. The historical `docs/SYCL_IMPLEMENTATION.md` note at commit `3bd22ada` says its isolated production object was 11.66%/11.59% faster for 8/64 real experts, but three alternating full-engine pairs made all four decode medians 0.13–1.77% slower; median sum of four decode times increased 0.70%. It was rejected and the earlier gate/up-only path restored. The same text says signed-zero preservation and 576 boundary cases were checked.
- The earlier experiment JSON at commit `a817032b` identifies hardware as Ryzen 5 5600X / 125 GiB and compares actual GGUF IQ4_NL Down geometry 640 input × 2560 rows, across expert counts. Its interpretation: no 64-expert benefit from IQ4NL loop expansion/wider shuffle and no consistent gain from table-lookup scales; the two-row candidate did improve a component, but the production decision required end-to-end confirmation. Do not relabel component speed as token/s.
- Commit `d15cef90` rejected using a GCC-built alternative for the Down loop: the existing report `bench/results/2026-10-05-sycl-prefill-scaling/cpu-gcc-down-probe/README.md` says on the 5600X, precise icpx 2026.1 production object vs GCC 13.3 alternate, all 19,285,056 compared real/synthetic outputs were exact, yet GCC was slower by about 3–35% depending on group width. It also notes `nt=1` defaults to ggml, so a one-token component gain would not automatically change engine behavior. This rules out a compiler swap as the candidate.
- Existing multi-token parity is already scoped over the real GGUF formats in `src/kernels/native_expert_parity.cpp:243-275`; it compares IQ4_NL multi rows against ggml and times them as component diagnostics. No new implementation is justified by the mere fact the model is mixed-quantized.

## Small conditional candidate: split software-prefetch control for IQ4_NL Down

The one untested implementation-shaped lead is a per-kernel prefetch distance for IQ4_NL Down, separated from the shared IQ prefetch setting only if the simple A/B below shows a repeatable benefit. `src/kernels/cpu/iq_avx2.cpp:177-195` documents the global `STRATA_IQ_PREFETCH` default of 2048 bytes. The comment attributes its evidence to a Ryzen 7 5700X3D IQ3_S Gate/Up decode: -4% gate/up time, +1.0 GB/s over rows, -1.3% ms/round. Those numbers are not a 5600X or IQ4_NL-specific result.

The same distance spans roughly two 1,100-byte IQ3_S Gate/Up rows, but about 5.7 actual IQ4_NL Down rows (n=640, 20×18=360 bytes per row). `iq4nl_rows` calls `rows_ahead` at each 18-byte block (`iq_avx2_rows.inl:249-260`), so the common global value may have different locality behavior on the Down geometry. This difference is a hypothesis only; no prefetch penalty or benefit was measured for this model/CPU. A minimal experiment is an all-engine decode sweep with shared setting 0 / 512 / 1024 / 2048, paired in alternating order on the same fixed 32K state and MTP4, while recording per-layer `nt` distribution and separate Gate/Up vs Down CPU times. Because the shared knob affects both phases, add an IQ4_NL-only override only if the sweep demonstrates a stable Down-specific effect that gets cancelled by Gate/Up changes. The override should default to the existing shared setting and leave arithmetic unchanged. Require unchanged full logits, MTP draft/verify state, and no 256K capacity loss; otherwise do not add the knob. This is a narrow diagnostic candidate, not a speed claim.

Large row-tile or loop-rewrite proposals are deferred. The two-row path is already tested and rejected at engine level on this CPU, loop expansion was measured without a consistent gain, and static disassembly shows no vector stack spill in the existing multi-token kernel. A new multi-row×multi-token design would need fresh critical-path evidence before it is worth revisiting. Do not treat the 39 IQ4_NL layers as proof that the Down phase dominates decode.

## Main-agent measurement and failure gates

1. Using the current production path only, report per layer the actual `(gu_type, d_type)`, number of experts with nt=1/2/3/4, actual dispatch (GGML fallback vs AVX2 multi row), CPU phase wall time, and 64-token/full-window emitted token count. This is instrumentation/analysis of known paths, not a new kernel recommendation.
2. If IQ4_NL Down occupies enough critical time, A/B the existing shared prefetch setting with fixed context/state and all other parameters unchanged. Alternate run order and distinguish fresh decode from restored-state decode. The production profile's CPU expert aggregate must be apportioned by phase before deciding the down kernel is the target.
3. Failure: no repeatable full decode improvement beyond noise; improvement only in an isolated component; changed logits/route IDs/MTP acceptance/state; any invalid AVX2 instruction path; row holes/overwrites; finite/guard mismatch; or 256K state failing at boundaries. Any candidate must retain all context tokens through exactly 262144, then decode with same KV/GDN/PLE/indexer state and compare the complete output path. CPU/GPU floating differences should be triaged with full logits and UB/scratch/lifetime checks, not waved away as backend rounding.
