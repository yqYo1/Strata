Conclusion

This is a plausible but unproven way to remove the CPU staging memcpy for a subset of sources. It is not safe to add a prepare call at each expert pointer or to treat API declaration/library symbols as proof of driver support. The smallest defensible source candidate is a single, bounded, page-aligned range from a stable ArenaExpertSource allocation, used only by explicit H2D copies on the existing prefill copy queue, with a unique non-overlapping import lease and release after the last DMA is known complete. The current implementation cannot yet prove that this last-DMA point can be reached without adding a new blocking wait or disturbing overlap; that must be checked by the main owner. If it requires adding queue waits, this candidate should stay held because the earlier immediate-copy-queue/event-wait proposal was held after ~8% cold-decode regression and intermittent retirement-log mismatch. No speed gain is established here.

Local data path and pointer lifetimes

1. The ordinary source path is Stager, not direct DMA. In prefill.cpp:352-356 the code says ~2 MB copies into host buffers were stalling the GPU and records that staging is intended for arena experts that could not be pinned. Stager::init allocates a ring with malloc_host at :392-420 and falls back to pageable vectors. Workers wait for the prior DMA and slot completion at :453-460, then copy/read the source into the ring at :461-479. The issuer submits the H2D operation from that ring and records its event at :3340-3350 / :4626-4644. EventCompletion retains the last event for a ring slot and only marks it complete after a positive status query (event_completion.hpp:11-44; prefill.cpp:518-527).
2. The SYCL PinnedArena implementation currently does not register ordinary host ranges. pinned.dp.cpp:365-368 states “SYCL pageable host arena (queue copies)”; :382-394 says existing-host registration was replaced by no-op comments. ArenaExpertSource::open nevertheless keeps registered_bytes and aliases conditionally (expert_source.cpp:3544-3565), and pinned() uses that byte prefix (3630-3640). For this build, inspect PinnedArena::registered_bytes at runtime before assuming any fraction is already imported; source comments indicate none. Thus a prepare experiment must not re-import an already imported SYCL allocation, but the present implementation is not doing a device-copy import for this arena.
3. ArenaExpertSource has two stable candidate backings. Default experts.bin is loaded into the owned PinnedArena mapping; pointers from blob() are offsets into its fixed base (expert_source.cpp:3318-3355, 3544-3576, 3643+). STRATA_ARENA_MMAP maps the padded experts.bin read-only with MAP_SHARED and explicitly sets pinned_bytes_=0 (3363-3392); it is a stable virtual range while ArenaExpertSource remains open, but its pages are deliberately reclaimable. Importing it may lock or otherwise retain pages and defeat the mmap/RAM-pressure intent. Do not use mmap mode for the first experiment.
4. GGUF-backed data has two distinct modes. When GGUF tensors are assembled into ArenaExpertSource, the loader writes the roles into the canonical, contiguous arena during startup (expert_source.cpp:3332-3340, 3465-3500); after open the resulting blob pointers can be stable and immutable. GgufExpertSource direct-streaming is ineligible: its header says the blob ring pointer is only valid until the next blob() call (gguf_expert_source.hpp:1-12); read_into() assembles three role slices from open shard FDs into caller-owned destination (same file :37-41, implementation in sycl/src/core/gguf_expert_source.cpp). Those transient assembled buffers belong to the stager and should stay on the existing path. A raw mmap of the model's three GGUF tensors is not an existing source abstraction and would need new multi-file offset/lifetime logic; not a minimal candidate.
5. Expert chunks are not guaranteed to align to pages. ArenaExpertSource uses one slice per layer in its existing pinned backend to avoid an expert straddling registrations (expert_source.cpp:3432-3439), but SYCL staging currently ignores that behavior. Arena boundaries come from ExpertLayout::layer_offset/blob_bytes and can be non-page-aligned. Per-expert prepare calls would create a huge number of import/release operations, and adjacent expert ranges/pages overlap. The SYCL extension specification makes overlapping prepare calls undefined even if contexts differ, with no diagnostic. Do not call prepare repeatedly on expert blobs or on each ring slot.

oneAPI 2026.1 and Level Zero support: what is and is not established

- Local header declaration exists at /opt/intel/oneapi/compiler/2026.1/include/sycl/usm.hpp:337-351, as the requester already confirmed. Local compiler runtime library also contains symbols named ZeUSMImport, doZeUSMImport, doZeUSMRelease, urUSMImportExp and urUSMReleaseExp in libur_adapter_level_zero_v2.so.0.12.0. This is static file inspection only; no function was called and no GPU tested. It proves the adapter binary contains an import path, not that the selected B570 driver exposes it or that a given allocation can be imported.
- The Intel extension is explicitly experimental, not a finalized SYCL feature. Its primary spec is https://github.com/intel/llvm/blob/sycl/sycl/doc/extensions/experimental/sycl_ext_oneapi_copy_optimize.asciidoc (status/early access at lines 214-225). The spec says prepare informs the implementation that a host range may be used for explicit copy operations in a context; use is generally useful only for several subsequent copies (:229-257). It says overlapping prepare ranges are undefined behavior and no error is issued (:250-252). release must use the same pointer and context as the outstanding prepare, or behavior is undefined (:259-267). Intel's 2025.2 guide repeats that ownership/lifetime correctness is the caller's responsibility and importing more than the actual allocation is user error: https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2025-2/optimizing-data-transfers.html . These are explicit UB/contract constraints.
- Intel guide examples call prepare once before a repeated-copy loop and release once after it, not once per copy. The published 256 MB benchmark (26.9 vs 45.4 GB/s H2D in the prior Intel report) does not identify a B570 and is not evidence for ~2 MB expert operations or this engine.
- The corresponding Level Zero v1 UR implementation is publicly inspectable at https://github.com/intel/llvm/blob/sycl/unified-runtime/source/adapters/level_zero/usm.cpp around urUSMImportExp/urUSMReleaseExp (current source lines 3112-3168). It checks ZeUSMImport.Supported, asks zeMemGetAllocProperties, imports only when allocation type is UNKNOWN, and then returns UR_RESULT_SUCCESS even if ZeUSMImport.Supported is false. That means the SYCL void API gives no direct “import succeeded” boolean; exception/error detection alone cannot identify a silent unsupported/no-op case in this implementation. The same source dispatches the extension by adapter/driver function pointers; installation of the API symbols is not driver support.
- Intel UR maintainers' issue https://github.com/oneapi-src/unified-runtime/issues/1528 names SYCL_USM_HOSTPTR_IMPORT as a switch controlling whether L0 imports host buffers, and says wider workload evaluation was still needed. This is maintainer-authored implementation context, not a support guarantee or measurement. The current public repo is now in intel/llvm and exposes both normal and experimental L0 v2 adapters; the exact 2026.1 package source revision and whether its v2 path has identical no-op/error behavior were not established from a matching source tag. Keep this as an explicit unknown. The installed binary's v2 symbols do not close that gap.
- The Level Zero external-memory map spec requires system-memory pointer and size alignment to host page size for that API: https://oneapi-src.github.io/level-zero-spec/level-zero/latest/core/EXT_ExternalMemMap.html. This is adjacent implementation detail, not proof that the specific internal ZeUSMImport path uses that same API. The SYCL extension itself does not publish an alignment rule. Therefore require page-aligned candidate ranges as a conservative test precondition, and confirm exact UR/driver requirements before relying on it; do not claim alignment is a SYCL spec requirement.
- Experimental APIs may change; ordinary H2D queue memcpy remains the safe baseline. No direct system allocation becomes safe to dereference from a GPU kernel merely by using prepare_for_device_copy: the spec only describes explicit copy operations. Keep this experiment limited to queue.memcpy, not the GPU-side host-polling or direct pointer kernel path.

Smallest bounded candidate, if main elects to prototype

Candidate eligibility: canonical ArenaExpertSource only (anonymous resident PinnedArena first; optionally later the mmap experts.bin source if RAM-lock behavior is understood). Exclude GgufExpertSource transient reads, CPU-input buffers, buffers allocated by malloc_host, and any source already registered/imported for this context. Restrict to the existing explicit H2D expert copy in prefill.cpp and existing m.copy queue. This is a more precise version of the earlier staging-bounce proposal: workers must not mutate source bytes; the existing destination stage_dev remains in place; the CPU source-to-ring memcpy is skipped only for an eligible range.

Range/lease design constraints:
- A single reusable lease may span one bounded, contiguous arena segment (prefer one layer when it is at least page aligned after conservative rounding; otherwise group adjacent layers into the smallest page-aligned, non-overlapping segment). Compute checked [start,end) from the real ExpertLayout, round start down/end up to OS page size only after proving the rounded range remains inside the actual backing allocation, and use exactly that rounded base for both prepare and release. Do not prepare a layer and also the whole arena, or prepare per expert under a layer lease.
- Since adjacent rounded layer ranges may overlap at an unaligned boundary, build disjoint ranges ahead of use or merge those neighbor layers; never let two live leases overlap. Also don't re-import a range while an earlier prepare remains live. For this first version, process only one range at a time, and maintain a small explicit lease state {base,size,context,active,last_copy_event}.
- m.copy is the queue actually used for these transfer submissions (:1109-1112 and :3348/:4622). Use that queue overload and ensure it has the same context as the copy events. The release API matches context + base pointer, not byte count. No other queue may copy from an imported range. Existing compute/stage buffers and their event dependencies remain as-is.
- The lease must cover all DMA reads that reference that range, including repeated experts in multiple prompt chunks and any early exit. In-order m.copy means a retained event after the final copy from the lease can stand for earlier copies only if it truly belongs to that same queue and all submissions were enqueued before it. Use positive event-completion status only. Existing EventCompletion helpers already poll nonblocking and treat failed queries as incomplete (event_completion.hpp:35-44); however there is no current per-import lease ledger, and stream_all's job-finish is not itself DMA completion. Releasing at Stager::finish/destructor is therefore unsafe.
- If there is no safe existing retirement point at which the final DMA event can be queried complete without introducing the held blocking-wait behavior, stop at this design stage: do not release early. Keep the source in the current stager path. On exceptions/abort-like exits, drain/retire the copy queue using the existing lifecycle teardown before unmapping/freeing the source, then release active imports; do not let ArenaExpertSource::close/munmap or PinnedArena destruction race a pending import/DMA.
- Fallback must be per-request/per-range and conservative. Any API exception, unsupported feature/query, invalid/unprovable allocation base/size, mmap source, transient source, or lease bookkeeping failure marks this range ineligible for the rest of the process and uses the current Stager host-USM/pageable path. Since UR can silently no-op, “no exception” is only “attempt returned”; it is not evidence that imported DMA or performance improved. A startup/runtime capability check must not infer B570 support just from __has_include, SYCL_EXT_ONEAPI_COPY_OPTIMIZE, compiler version, or binary symbols. The initial main-owned test should report API attempt, exact backend/device/driver/runtime versions, imported range bytes, number of calls/releases, and parity; only then can source review and repeated A/B interpret whether path was active.
- Cleanup: on successful path retain exact prepared base/context and release exactly once after last DMA completion query succeeds. Do not rely on double-prepare reference counting. If a copy or event-status query fails, quarantine the range as active; first drain the queue through existing shutdown, then release and only afterward allow source unmap/free. A failed prepare must never switch to the imported pointer; it should revert to staging. A failed release means no safe unmap/free; surface a clear request failure and retain backing through process shutdown if necessary.

32K -> 256K constraints and whether this candidate is worth moving

At minimum 32K, a bounded one-layer-at-a-time lease could avoid extra CPU copies for the specific streamed arena experts in that layer while keeping locked/imported bytes limited to roughly one layer plus page padding. But if chunk-major revisits a layer for each context chunk, it may need prepare/release repeatedly or hold many ranges simultaneously. Per Intel's spec the API's intended target is repeated copies of the same system-memory range; per-expert-per-chunk copying through a ring is not a valid pattern. This is why the candidate should first measure actual streamed source bytes/copy counts and determine schedule visits per range. Large request token count does not itself change the expert-source allocation size but KV/context host usage and other allocator pressure do.
At physical 262144, do not import the full arena by default. With 128 GiB system RAM, a full expert arena plus page cache, process model/host buffers, stager/GGUF shard mappings, KV/state, and OS margin can be substantial. With mmap experts, pinning/importing broad ranges can defeat reclaimable page-cache behavior. No actual arena byte size, import resident/locked footprint, allocation cap, or 256K headroom was measured in this research. Record peak RSS, locked/pinned/imported bytes and mmap major/minor faults during the main-owned validation. If complete 256K requires importing a wide/full arena or retaining it over all chunks, require an explicit RAM headroom calculation and a separate opt-in; never silently alter the 128 GiB machine's RAM behavior.

Minimal verification plan for main (not executed here)

1. First inspect actual registered_bytes, source dynamic type (ArenaExpertSource vs GgufExpertSource), arena allocation byte size, real layer offsets/lengths/alignment, and exact DMA count/bytes for one 32K request. Record configured maximum context and backend/runtime/driver version from the actual executable/environment.
2. Do an isolated minimal runtime capability/correctness probe on a separately allocated, page-aligned small system range, not on a live Strata arena: feature macro and active queue backend, prepare once, H2D explicit memcpy, verify bytes, query event completion, release exactly once. This only establishes API behavior for that small allocation/driver; do not modify or build as part of this research.
3. If probe proves driver path and source range eligibility, implement an opt-in mode only for one disjoint arena range per lease; keep baseline fallback. Run a one-layer or one-contiguous-range 32K prefill A/B with interleaved fresh engines, exact token/logprob parity, CPU memcpy time/bytes, wall prefill time, RSS/locked bytes, event retirement status and faults. Do not infer an end-to-end speed claim from a microcopy result.
4. Only if 32K correctness/memory lifetime is clean and prefill has a measured win with no decode regression, move to full 32K and then 64K. Test decode separately. Before 262144, measure maximum live/imported bytes and RAM headroom with full context; verify all final token/logprob and state parity. The import experiment does not qualify the current stager-affinity branch or waive its independent full-context qualification.

Uncertainties / review checklist

- Exact installed UR/Level Zero v2 source corresponding to 2026.1 and selected B570 driver support for the host pointer import extension are unverified.
- Does the actual L0 v2 import implementation require page aligned pointer+size, and does it lock/register memory in a way that defeats mmap reclaimability? Public SYCL docs do not say; Level Zero external-memory mapping alignment is only adjacent evidence.
- Does the runtime silently no-op on absent driver extension in the installed v2 implementation as in the inspectable v1 source? The binary exports function symbols, but no runtime call has been made.
- Does Strata's actual chunk-major schedule expose a safe final-copy event for each bounded range without adding a blocking wait? Current staging ring event state tracks destination ring slot reuse; it is not an import lease ledger. This is the key local lifetime gap.
- Which ArenaExpertSource backing does the actual IQ3_S run use, what is the arena byte count, and what source mix remains streamed after VRAM cache selection? Not measured here.
- Any successful optimization would be prefill-specific evidence. Decode uses separate verify/window paths and current SYCL arena does not advertise existing-host registration. Do not assume decode improves.
