Contract

- A successful `queue::wait()` is a retirement point: SYCL specifies that it blocks until all previously enqueued queue commands have completed. It does not deliver async errors to the handler. The Khronos queue reference distinguishes this from `wait_and_throw()`, which also passes unconsumed async errors to the handler ([Khronos queue reference](https://github.khronos.org/SYCL_Reference/iface/queue.html), [SYCL 2020 spec](https://registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html)). Thus a *normal return* from wait is sufficient to retire queue accesses even if a kernel has failed asynchronously; it is not evidence that model/KV state is valid, and that async failure can remain pending until a later `wait_and_throw`.
- A `wait_and_throw()` that reaches and reports the async handler also has the blocking-completion effect. But this project’s handler throws the first async exception (`sycl/include/strata/sycl_error.hpp:8-19`), so it unwinds after reporting. Do not conflate that case with a synchronous wait/runtime failure. The local oneAPI 2026.1 UR header documents `urQueueFinish` as blocking until all enqueued commands are processed and finished, but also lists `DEVICE_LOST` and `ADAPTER_SPECIFIC` errors (`/opt/intel/oneapi/compiler/2026.1/include/unified-runtime/ur_api.h:7320-7349`). It gives no promise that a failed `urQueueFinish` return proves command retirement. On any thrown synchronous queue-wait/runtime error, completion is unknown unless a separate successful completion event/queue fence proves otherwise.
- Consequently, catch-and-continue is not safe as a general fix. Catching a wait exception and then freeing workspace, shrinking/growing cache, returning borrowed expert slots, releasing imported host memory, or refreshing/replaying a graph can race commands that remain live. The safe state after an unclassified failed wait is **quarantined/poisoned**: retain every potentially referenced host/device allocation and graph/cache backing, prohibit reuse/reset/reinit of that session, surface fatal error, and require process/device-level recovery. If a runtime-specific, documented completion result distinguishes “all complete but execution failed,” then it can permit retirement while still poisoning logical state.

What the current implementation proves

`run_impl`’s RAII `KvDrain` waits its selected `stream`, then the retained compute queue (`prefill.cpp:2915-2924`). On a healthy cancellation/ordinary `false` return, normal completion of those waits means the commands already submitted to those queues are done. In the streamed branch, `stream` is the DPCT default in-order queue and `retained_compute` is caller queue `m.cs`; they need not be the same queue (`init` sets `m.cs = strata::q_of(stream)`, `:1050-1057`). The extra retained wait is candidate-only; baseline `23268953` had only the selected stream wait. If either wait throws inside this implicitly-noexcept destructor, C++ terminates; the outer `run_layer_major` catch cannot convert it to an error. This is partly inherited: baseline’s `KvDrain` already waited in its destructor. Candidate adds a second potentially throwing drain and retained behavior.

The layer-major `Restore` guard waits compute, copy, finishes Stager, optionally waits `kv_copy`, and only then restores callbacks, queue mode, cache/residency and residual pointers (`:2693-2702`). The first compute/copy/stager waits predate the correction; candidate adds the optional retained `kv_copy` wait. If any wait/finish throws, the guard exits before pointer/state restoration and, because its destructor is implicitly noexcept, terminates. The temp layer cache is declared before this guard and therefore would normally be destroyed after the guard; failed queue completion prevents reaching that safe lifetime order. The current loop finishes Stager jobs before it enters `run_impl` for each layer (`:2734-2760`), so there is no live layer-load producer expected during a per-layer `run_impl`; `run_impl` itself joins/finishes producer scopes before its `KvDrain` destructor. Preserve this producer-before-final-fence ordering if refactored.

`m.copy` is an owned in-order profiling queue with exception handler enabled (`prefill.cpp:1105-1116`, factory `sycl/include/dpct/device.hpp:625-634`). The streamed layer cache expert DMA uses it; its successful wait plus Stager completion retires source/destination references. `m.kv_copy` is created with exception handling enabled (`:2899-2910`) and is drained before candidate mode switch (`:2708-2711`); streamed mode suppresses later prefetch. `m.cs` is provided by caller and must be in-order for streamed mode; the admission gate checks this (`:2434-2443`). The default DPCT queues are initialized with the shared exception handler (`device.hpp:680-700`); created copy/kv queues also pass `true`, while the specialized in-order profiling factory uses that same handler when requested.

Healthy cancellation and runtime failure must be separate paths

1. Healthy cancel: `should_stop` returns true, or a callback returns false, while queues are healthy. Host producers/issuer are stopped and joined; then wait every queue that can still reference task-local or temporary storage: default queue, `m.cs`, `m.copy`, any outstanding `m.kv_copy`, plus peer/helper queues if actually bound. `Stager::finish()` must settle host producers before the final wait on queues those producers may submit to. A successful wait is the retirement proof; then restore guard state and close temporary cache/graphs. Cancellation is a normal error result but does not poison the session when the queue fences all return normally.
2. Async execution error: current `wait()` can return normally after all commands complete without consuming async exceptions. Memory can be retired, but stage/KV/cache/session results are untrusted. Use the configured async error reporting point (`wait_and_throw` or explicitly surfaced handler state) outside destructors; return an operation error and mark session state unusable/reset-required. Do not silently resume generation using partially written KV/indexer state.
3. Synchronous `wait()` / backend `urQueueFinish` failure: completion is not established by the failing call. Do not release/reuse any referenced region. The current C++ destructors cannot recover and instead terminate; this is fail-stop, which is safer than catch-and-free but skips orderly application error reporting. If root requires a recoverable API error instead of termination, it needs a larger ownership design: keep resources in a poison/quarantine owner that outlives the failed prefill and prevent all subsequent borrow/reset/graph operations. It cannot return the memory to general allocators.
4. A `wait_and_throw` exception specifically known to originate from the async handler is different: the wait portion completed, then `rethrow_sycl_errors` throws. It is safe to retire memory once that distinction is explicit; logical session state still must be poisoned. A generic catch around `wait_and_throw` cannot tell this from synchronous/runtime exceptions and must conservatively quarantine.

Queue and path matrix

- `m.cs`: candidate waits in `KvDrain` on early exits, then `Restore` also waits; normal successful `run_impl` already executes a compute wait and clears fallback (`:5330-5334`). Successful cancellation fence retires layer stage and compute buffers. If this wait fails synchronously, stage/temporary allocations must stay alive; current noexcept unwind terminates.
- DPCT default in-order queue: candidate’s `KvDrain.stream` is default queue when no async `kv_prefetch`, even if `m.cs` is a different caller queue. On success it retires any default-queue work. On wait failure it is not proof for default-queue buffers. If it returns normally after device async error, memory is retired but default handler has not consumed/reported that error.
- `m.kv_copy`: pre-mode-switch wait retires stale ordinary prefetch before sharing stage plane. Streamed candidate queues none afterward. The optional outer `kv_copy->wait()` is conservative but can throw in a destructor; its no-op cost is usually small but redundant if previous queue was successfully fenced and no new work scheduled. Do not remove without proving no intervening producer and update its exception policy.
- `m.copy` / Stager: ordinary cancellation path’s producer scopes are joined before outer restore; restore’s successful `copy->wait()` plus `Stager::finish()` settles DMA and staging jobs. A generic cleanup helper must join/stop every producer before final queue waits, otherwise wait only covers commands enqueued before the fence and a producer could enqueue afterward. If either producer join or copy wait fails, preserve backing storage.
- Peer/helper streams: `HelpScope` waits peer queues in its destructor (`:2935-2947`), also implicitly noexcept and inherited. If a peer was actually engaged, it must join the same poison/fatal logic; unrelated code paths must not be “fixed” only for the streamed path.

`wait_and_throw` implications

Do not mechanically replace the many existing `m.cs->wait()` / `.wait()` calls with `wait_and_throw()`. Current Intel LLVM queue implementation’s `queue_impl::wait` calls `urQueueFinish` after event waits (`queue_impl.cpp` around 1271-1328); queue API `wait_and_throw` additionally delivers queued async errors to the handler. This changes which failures surface at intermediate timing/checkpoint fences and can invoke the project's throwing handler earlier, changing error route and state rollback, not just adding diagnostics. The queue APIs both block; `wait_and_throw` is not inherently an additional second drain if it replaces a wait, but it adds async-error-handler work/error propagation. Restrict it to deliberate error-reporting boundaries, keep it out of destructors, and classify error origin before deciding whether backing may be released.

CPU fake-queue test oracle for root (no GPU fault needed)

Use a fake queue interface that records submitted producer IDs and has injectable drain outcomes: (A) healthy complete; (B) complete-with-async-error where the handler rethrows after completion; (C) synchronous/runtime error with completion unknown. Also fake the Stager issuer/finish. Assert order: stop/join producers; successful fences for all producer queues; then restore callbacks/cache pointers; then close/free temporary cache. Outcome A must return cancellation/error with restored state and exactly-once release. Outcome B may retire/free backing only when the fake explicitly marks completion before throwing async; it must surface error and poison logical KV/session state. Outcome C must not free/shrink/reassign/refresh/capture/release anything, must mark poisoned/fatal, and must not call later generations/reset with those pointers. In C++, do not inject a thrown wait from a destructor in-process: that test should be isolated in a child process and expect fail-stop/terminate. Separately test recoverable quarantine only if implementation moves ownership out of the destructor. The oracle is the state/lifetime contract above, not “no exception escaped” and not pretending a thrown wait means completed.

Default behavior and scope of findings

Without `STRATA_PREFILL_LAYER_MAJOR_STREAMED_KV=1`, baseline resident-only layer-major behavior stays; candidate streamed admission rejects nonresident KV and does not set `layer_major_streamed_kv`. The changed `KvDrain` adds a second compute wait only when the new scoped mode is true; successful normal path disables it after existing compute fence. The cleanup-exception hazard is partly inherited from baseline `KvDrain`/`Restore`/`HelpScope`, with candidate-specific new wait sites called out above. This report does not establish a demonstrated runtime failure, only that the API and code do not permit assuming retirement after an unclassified failed wait.
