## Finding

There is an existing retirement point that can safely release one *single, bounded lease spanning the whole `run_impl` copy batch*: the end-of-chunk `cudaStreamSynchronize(m.copy)` at `src/prefill/prefill.cpp:3991`. On successful completion it occurs after the issuer has submitted the batch; the issuer is local and joined by its scope guard (`:2325-2329`), and the issued host-to-device transfers all use `m.copy` (`:2297-2305`, threaded issuer `:2343-2352`). The destination staging slot is subsequently consumed by compute, but source retirement concerns only DMA's read of the host source; after the copy stream sync, later compute reads `m.stage_dev`, not the source arena. `Prefill::run` then drains its CPU pipeline (`:4074-4085`).

That point does **not** permit per-expert or per-layer prepare/release while the issuer is running. `stream_all` constructs a layer-major sequence and starts staging work (`:2238-2284`); the issuer can enqueue many source copies before the chunk-end synchronization. `Stager::finish` is not a DMA completion fence: it joins host copies, while CUDA DMA is enqueued later on `m.copy` (`:2301-2303`). The chunk-end sync therefore works only if the import lease covers every direct-from-source transfer in that chunk that it is intended to accelerate. A proposed implementation that prepares a fresh range per expert and releases it as soon as `issued_one` returns is unsafe. There is no existing per-layer `m.copy` retirement boundary in this stream-all path.

A narrow experiment is possible if it imports one stable, bounded source interval (for example, a single layer's expert span, page-rounded) before starting the issuer, routes only source copies whose bytes lie inside that span through the imported address, and keeps the lease until the existing `m.copy` sync at `:3991`. Other transfers continue through the current Stager path. If several layers' spans are to be imported, a single lease must cover their combined interval; this can become too large and is not a bounded-memory win. For repeated chunks, prepare/release the same bounded interval once per `run_impl` invocation, after each existing sync. This is a candidate design, not proof that L0 import gives a performance benefit or that all platforms support the required semantics.

## Failure and ownership

`run_impl` can return before its normal copy-stream sync. `Prefill::run` calls `drain_pipeline` after `run_impl` (`:4075-4080`), but that is not a device fence. Therefore a stack-local RAII object that unconditionally calls `release_from_device_copy` on every exit would be incorrect. Keep the lease owned by `Prefill::Impl`; on the successful path release it after the `m.copy` sync and before returning. On any early error, retain/quarantine it until `Prefill::release()` synchronizes `m.copy` (`:852-856`), then release the import before destroying queue/events/resources (`:857-878`). `reset()` calls `release()` before replacing Impl (`:846-849`), and the destructor calls it (`:843-844`). Any RAII wrapper must represent an active vs retired lease and must not issue a new wait in its destructor. If `release()` has to be callable on a failed request while the server continues, it already has the necessary sync, but its failure handling should preserve the lease until that sync has actually succeeded; current code ignores sync return values, so the proposed owner needs explicit quarantine on sync failure rather than freeing the imported mapping.

The source lifetime is longer than the request prefill object: `ArenaExpertSource arena_src` is created in `generate.cpp:4143`, and the one-shot `Prefill prefill` is created at `:11130`. In serve, `Prefill sp` is constructed near `:1020` and persists across request-loop turns. The arena is opened synchronously before request handling; `srcp` is assigned to it at `:4252`. The arena destructor calls `close()` (`src/core/expert_source.cpp:3845`); `close()` is at `:4099` onward. Thus the import owner must die/release before arena close, and the current stack lifetime supports this only when the prefill/import holder is destroyed or explicitly reset before its source.

SAVE/RESTORE is a between-request branch (`generate.cpp:8698-8709`): successful restore transfers session state (`:8883-8905`) and continues the loop (`:8907-8908`); it does not execute expert-source DMA itself. On the successful prefill path the import should already be retired at `prefill.cpp:3991`, so SAVE/RESTORE needs no extra synchronization. A failed prefill is different: `run()`'s `drain_pipeline` does not retire a lease. The serve caller must either reset/release the prefill before accepting another command/request, or keep the failed lease quarantined until normal teardown. Do not infer safety merely from SAVE/RESTORE being between requests.

## Source and deferred loading

`ArenaExpertSource::open` is synchronous at the caller (`generate.cpp:4143-4158`; selection of arena source at `:4252`). In this build's source, its deferred arena branch is guarded in `expert_source.cpp:3978-3983`; the Linux branch sets `deferred = false` (`:3981`). Consequently this checkout does not start deferred arena registration on a preload thread before opening. The separate file-tier async I/O and routing lookahead are distinct source paths (`generate.cpp:4177-4188`, `:4959-4984`) and may fault/read files, but they are not evidence that arena import has completed. Any import must follow stable-pointer acquisition and must exclude transient blobs (`ExpertSource::transient`/`blob_stable`, called while sequence is built at `prefill.cpp:2255-2276`).

Search surfaced v2 source path `unified-runtime/source/adapters/level_zero/v2/usm.cpp`, but this audit did not establish that exact file revision/build corresponds to the supplied binary hash. Therefore I cannot make a source-backed claim about this binary's unsupported-import behavior. The v1 silent-success behavior from earlier rounds must not be generalized to v2. Treat import as unavailable unless a call reports success with a usable import result under the matching installed build; do not rely on a no-op success or assume release semantics from v1.

## Recommendation

Proceed only with a one-range-per-chunk prototype guarded by verified import support, retaining the lease across all matching queued copies and releasing only after the already-existing `m.copy` synchronization. Store ownership in `Prefill::Impl`; successful chunk completion retires it, while every error path quarantines it until `Prefill::release()` has successfully synchronized the copy queue. Keep the first prototype to a single bounded, stable arena span and preserve Stager for everything else. Reject per-expert/per-layer lease turnover in the current chunk-major issuer: it lacks an existing DMA completion boundary between those ranges, and adding one would violate the no-new-wait requirement. Before implementation, verify exact L0 v2 import/release behavior and binary provenance, plus whether the actual SYCL-prefill branch shares these CUDA retirement points; this target checkout itself implements this path with CUDA streams, not a SYCL queue.
