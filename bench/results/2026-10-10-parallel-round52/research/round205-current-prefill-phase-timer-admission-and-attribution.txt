## Finding

The existing STRATA_PREFILL_TIMING timer is sufficient for one current-version coarse phase-ranking run. It places ordered barrier-event markers on the active compute queue and charges the difference between consecutive marker command_end timestamps to the phase named by the earlier marker. This is phase-attributed queue timeline, including compute-queue idle time while the host groups experts or waits for copy dependencies. It is not kernel execution time, exclusive device time, or whole-request wall time.

The ordinary DPCT device queue factory gives its standard queues enable_profiling; the compute queue used by Prefill is obtained through strata::q_of(m.cs) (or defaults to the in-order queue). The timer itself does not verify the selected queue's profiling property/device aspect or validate every timestamp pair. When a profiling query throws, DPCT_CHECK_ERROR catches/logs the exception and fold() skips that interval without setting a failure flag. If command_end(next) < command_end(previous), the subtraction is unsigned and can wrap to a huge positive interval. Therefore, before treating the phase JSON as authoritative, either add a small source guard that fails closed on a missing profiling result or invalid timestamp order, or have root require explicit output checks that reject missing/non-finite/out-of-range phase data. This is the material source blocker for interpreting a malformed report; a valid, fully accounted report can still answer the coarse phase-ranking question without source changes.

For a normal diagnostic, set STRATA_PREFILL_TIMING=1 and leave STRATA_PREFILL_SYNC unset. The timer is enabled by environment-variable presence, not by parsing its value: STRATA_PREFILL_TIMING=0 still enables it. STRATA_PREFILL_SYNC also uses presence and waits for the compute queue at every marker, which changes the schedule and invalidates ordinary phase timing. Keep STRATA_PREFILL_TRANSFER_TIMING unset for this first coarse pass: it instruments the separate copy queue and emits a distinct report, while the coarse phase timer does not profile copy commands individually.

## Admission and emitted evidence

PfTimer owns per-run marker and phase-index vectors. mark(phase, cs) records an event with dpct::sync_barrier; marks are placed on cs, the queue selected by strata::q_of(m.cs). During normal execution, no explicit profiling preflight occurs. The default device manager's create_queue_impl constructs its regular queues with sycl::property::queue::enable_profiling() and an async handler. The separately created copy queue has profiling enabled only when STRATA_PREFILL_TRANSFER_TIMING is present. If a caller supplies a queue outside the regular factory path, the timer does not verify its property before recording markers.

At existing layer/chunk synchronization boundaries, the caller waits for queued work and calls fold(). For each adjacent pair it queries command_end on both events, subtracts the earlier marker's end timestamp from the later marker's end timestamp, converts nanoseconds to milliseconds, and adds that interval to the earlier marker's phase. It retains the final marker across folds as the starting boundary for subsequent work. This convention makes per-phase values a partition of the covered marker timeline (up to float conversion/rounding) if every timestamp query succeeds and is ordered. It omits time before the first and after the final mark.

The structured output is one strata prefill phases JSON line per phase report. It contains gpu_timeline_ms, host_setup_ms, host_chunk_wait_ms, host_after_chunk_ms, ple_gather_wall_ms, ple_host_wait_ms, and every named phase_ms entry. The human-readable line also prints percentages. In the normal path, run_impl reports at its end when it owns the timer. Layer-major attaches one PfTimer across its per-layer run_impl calls, folds at its end, and reports one aggregate after the run. Neither path emits a layer-by-chunk heatmap.

On a single GPU this timer covers only the active compute queue. Multi-GPU PeTimer emits separate peer-queue marks/phase totals; do not add them to the primary queue timeline. The independent STRATA_PREFILL_TRANSFER_TIMING report measures copy events' active intervals and first-to-last span on the copy queue; its commands can overlap compute-queue intervals. Do not add those active times to gpu_timeline_ms or use their span as a replacement for the primary timeline.

## What the labels cover in this source

Each label is determined by the interval after a mark until the next mark. Several labels aggregate different portions of the pipeline, and idle gaps are attributed to whichever phase's mark was open.

- embed+steps is the initial chunk/setup interval from the start marker through the first later phase marker. It is not just embedding lookup.
- hc read begins at kPfHc in each attention/feed-forward hyper-connection half. It includes intervening normalization, hyper-connection projections, activation/mixing and host work until a later phase mark; interpret it as the broad HC-side interval.
- gdn covers the first GDN projection sequence (attn_qkv, attn_gate, ssm_alpha, ssm_beta) until gdn conv+gates. gdn conv+gates covers gdn_gates and gdn_conv; gdn recurrence covers the state recurrence; gdn out proj covers the output projection until the next marker. Queue gaps within each span are included.
- qsa proj includes the initial Q/K/V and indexer projections plus associated normalization, RoPE and KV append work. The same name is marked again after prompt attention/transform before gate_attn and attn_output projection, so its sum combines the opening projection region and the post-attention output projection region.
- kv stage wraps the staged-prefix handoff interval on the compute queue. It may contain a barrier waiting for the separate prefetch queue or synchronous host-to-device stage work; it is not a standalone DMA timer.
- qsa indexer brackets native_qsa_indexer_append_batch, or the optional per-token comparison path. qsa select covers score computation and top-k for the selection batches. Debug comparison/dump flags add copies, waits and CPU work within these marked spans and must be off for timing.
- qsa attn begins before qsa_prompt_attn_batch or its fallback dispatch and ends after attention and any output format transform. It does not include the later attention gate/output projection, which is attributed to the subsequent qsa proj span. It may include fallback/control work and queue gaps, not only a kernel.
- router+shared includes router projection/route and shared-expert work until the expert-path phase mark. It is broader than the router kernel.
- host grouping starts before copying route IDs and waiting for the compute queue, then includes CPU grouping and preparation before the expert loop. The GPU is often idle during the CPU part, so this label can be large even though it is not GPU execution time.
- gather includes the explicitly marked row-gather or fused-expert preparation intervals. Its scope differs by route.
- wait copy marks periods before a compute-queue dependency on streamed-expert copy events. Its interval includes time until the following mark and can include queue idle/dependency waiting; it is not expert-copy active time.
- dequant marks the direct native expert dequant path, including submitted GU and Down dequant work and intervening host path before the next marker. Under MMQ it marks group gather/dequant work instead. Thus the same label is route-dependent.
- gemm gate/up begins before the GU product; in the direct FP16 route it also includes SwiGLU up to the Down mark. Under MMQ, it includes the group product and SwiGLU plus setup. It is not solely oneMKL GU kernel service.
- gemm down is the direct FP16 Down GEMM interval; under MMQ it includes H quantization plus the grouped Down product. It is route-dependent and includes any gaps through the next marker.
- combine covers weighted expert/shared-output accumulation. ple, ple read wait, hc write+norm, layer weight preload, and residual copy have their named caller-side spans but can likewise absorb queue idle time and host work between markers.

The current ordinary native MoE route in audited closed evidence is native IQ-to-FP16 dequantization followed by oneMKL FP16-input/FP32-compute-and-output GEMM; MMQ and fused paths are false in the recorded current route. R203's v0.1.40.2 timer ranking is not a current v0.1.41 phase measurement, and this source inspection cannot establish which runtime path a new run will select. Report loaded model/route settings and actual receipts; do not infer route from source eligibility alone.

## Queue errors and timestamp failure behavior

PfTimer::mark submits the synchronization barrier without a timer-local queue error receipt. Synchronous submission exceptions can propagate through the caller, but the phase timer does not bind each mark to an operation ledger. Its fold() wraps timestamp arithmetic in DPCT_CHECK_ERROR. The macro catches std::exception, prints it, and returns a generic error code; fold() only adds the sample when the macro returns success. A failed query therefore silently removes that interval from ms[]; no error count or completeness bit is emitted. report() still emits every phase name, with zero for any phase with no accumulated samples. A zero can therefore mean “no marked interval” or “failed query removed the interval.”

Timestamp subtraction is performed before validating order and uses unsigned event timestamps. There is no check for end >= start, no marker-count reconciliation, and no finite/range check on the result before adding it. A reversed timestamp can wrap, then convert to an implausibly large float. The outer catch(sycl::exception) does not fix this query path because the macro catches standard exceptions inside the loop. The timer also does not use wait_and_throw() as a per-report asynchronous error gate. Other existing caller error paths may report faults, but a phase JSON line alone is not evidence that every queued command completed successfully.

For an added hardening patch, minimally preserve per-interval query success and raw begin/end values; reject a query error, end < begin, implausible delta, or unexpected marker/report state; emit a diagnostic failure status instead of partial phase JSON. At existing synchronization boundaries, use the queue's established error-reporting contract without adding a wait after every mark or changing the work schedule. This patch would make the receipt self-validating. If root runs current source without that patch, reject the raw console record when the query printed an error, any phase is implausibly huge, or independent expected marker/phase coverage does not reconcile.

## Smallest useful root-owned phase measurement contract

Run one separate diagnostic process on frozen v0.1.41 source/build with intended ordinary production settings and at least 32,768 actual batched input positions. The public CLI's 32,768 prompt tokens ordinarily give only 32,767 batched positions because the last input position is handled separately; supply at least 32,769 input tokens and record the actual n/batched position count passed to Prefill::run (and any prefill chunks). Use a positive output budget and do not cap prefill with a smaller --prefill-until. Do not label requested prompt length as the measured batched count.

Set only STRATA_PREFILL_TIMING=1 for this phase diagnostic; leave STRATA_PREFILL_SYNC, transfer timing, route-debug switches, state dumps, trace output, QSA dump/check/overlap switches and per-step synchronization unset. Capture complete stderr/stdout, exact source/build/model identity, GPU/driver/compiler identity from the pre-existing closed build record, all environment variables, prefill mode/chunk geometry, input token count, actual batched count, output count, status, and unique JSON phase line(s). Preserve parser input and line counts; do not keep only a chart or hand-transcribed winner.

Root may parse an individual phase_ms value, rank labels within that same run, and verify that the sum of phase values approximately matches gpu_timeline_ms (allowing printed float rounding). It may compare like-named totals across repeated diagnostic runs as diagnostic queue-timeline observations. It must not rename these into per-kernel durations, add host fields to gpu_timeline_ms, add compute and copy-queue values, infer an exclusive CPU/GPU share, divide phase time by total prompt wall to claim request-time fraction, or use the instrumented report as a clean throughput sample. Keep a quiet, timer-off process as a separate control if timer overhead needs quantification; report its whole-request wall independently and do not transfer the timer-on phase distribution onto it.

One JSON receipt is expected for a normal run (or one aggregate receipt for layer-major). If multiple report lines appear, count and explain them against the invoked stage/run mode; do not silently sum duplicated or partial runs. A valid receipt must have successful process status, no profiling-query error text, finite nonnegative phase values, plausible gpu_timeline_ms, and explicit actual input/batched/output count. Until the timer has a fail-closed validity status, zero and missing values require interpretation from raw records.

This first sample answers only whether current broad phases merit targeted second diagnosis. It cannot reveal which layer/chunk drives a total because the timer stores per-phase sums, not per-layer/per-chunk values. It cannot attribute a GU/down wrapper to internal oneMKL commands; R190's separate event/dependency profiler plan addresses that question and should not be folded into this phase timer report. It also cannot prove optimization value, route call counts, or full physical-context readiness.
