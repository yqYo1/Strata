# R174 — author-run prefill/cache phase swaps and graph-rebuild cost

Date: 2026-10-12 (Asia/Tokyo). Static reads plus primary-source web review. No builds, tests, imports, AST/runtime inspection, Git operation, cleanup, source edit, model/server execution, GPU, profiler, or process query. This is the only artifact written for R174.

## Finding

A small-engineer/personal implementation has measured the proposed phase swap directly: before long prefill, release the GPU expert cache, decode compute buffers, and CUDA pools; allocate a larger prefill workspace; then restore the cache and decode buffers before generation. On that author's dual-RTX-3090 system, 8K/37K/119K prompts improved reported prefill throughput from 99.9/88.1/81.3 to 223.7/212.6/206.5 tokens/s. The same post says the transaction imposed about 2.8 seconds fixed cost per prompt; later short-follow-up measurements found a 2.5-second cost for one-token follow-ups and 4–4.5 seconds in a real chat after a fuller decode cache had to be re-uploaded. The author attributed an additional 1.6 seconds to reserve plus graph rebuild, beyond transition timers. A follow-up sweep found the swap first paid at 2,048 *new* prompt tokens; 64–1,024-token follow-ups lost time. This is concrete evidence that releasing decode residency can buy prefill room, and that graph/cache reconstruction is a material part of the decision. It does not establish a gain on the B570/5600X.

The discriminating variable is actual uncached/pending prefill tokens, not total displayed context. The author added a pending-token threshold after discovering that cached-prefix follow-ups paid the whole transaction but had little work to amortize it. Cache refill cost also depended on cache fullness, so a constant inferred only from “release” timing was inadequate. For a non-CUDA/AMD target, the CUDA-pool and graph numbers are not portable; measure the target's whole transaction, including graph/capture reconstitution, from request boundary to first generated token.

## Primary author evidence

- **Direct positive and negative phase-swap case:** the author’s part-4 report gives machine/configuration, the release/restore design, paired headline numbers and test caveats. It uses two RTX 3090s, dual Broadwell Xeons, Qwen3.8-Flash-Next, 150 cache slots, 261K capacity, FP16 KV, and a 512-to-2048 prefill microbatch. It frees cache slots, decode compute buffers and CUDA pools, runs the prompt with the larger batch, then restores before decode. Fresh-server same-day figures: 8K prefill 99.9→223.7 t/s, ~37K 88.1→212.6, ~119K 81.3→206.5; decode medians were 33.4→34.3, 41.7→41.2, and 33.9→33.9 t/s respectively. The post explicitly describes its data as development/operator measurements rather than an independent benchmark. [Author's phase-prefill report](https://www.reddit.com/r/LocalLLaMA/comments/1wc6fsk/qwen38flashnext_on_2x3090_ddr4_part_4_2225x/)
- **Graph rebuild and threshold correction:** in the same thread, the author reports graph rebuild plus reserve accounting for 1.6 seconds outside release/restore timers. In the author's later five-request-per-length sweep, swap-on vs swap-off medians were 64 tokens 5.7 vs 3.3 s (8K prefix), 256 7.8 vs 5.3, 512 8.9 vs 6.4, 1,024 15.6 vs 12.8, 2,048 17.9 vs 23.7, and 4,096 27.7 vs 47.8. At 37K prefix the corresponding values were 5.9 vs 3.4, 8.2 vs 5.6, 9.1 vs 6.5, 16.1 vs 13.1, 18.3 vs 25.7, and 28.2 vs 50.0. The posted branch then used a 2,048 pending-token threshold. Restore took longer when more cache entries had been filled; the author reports 4–4.5 seconds for ordinary chat after fuller decode. These are author observations on that build/hardware, and no variance estimate is given for most rows. [Measured threshold follow-up](https://www.reddit.com/r/LocalLLaMA/comments/1wc6fsk/qwen38flashnext_on_2x3090_ddr4_part_4_2225x/)
- **Different author's cache-preserving policy:** the `--moe-expert-cache` RFC reports that dynamic LRU caches let prefill bursts evict decode hot entries. Its implementation instead bypasses the persistent slot pool whenever a ubatch could touch more distinct experts than fit, and sends that ubatch through the existing selective-copy route. The author reports prefill unchanged at pp512/pp2048 and says prefill does not evict decode state. This is an alternative decision point when the cost is cache churn rather than insufficient prefill workspace: retain the decode pool and bypass it for batches that cannot fit. It uses graph-input ID remapping and adds an ID readback sync per offloaded MoE layer/token; it is not the Strata packed-bank design. The author discloses AI assistance and says they personally ran, verified, and debugged the results. [Author implementation RFC](https://github.com/ggml-org/llama.cpp/discussions/28248)
- **Personal engineering blog, 12 GB setup:** the `nothin` Mini-SGLang writeup describes full host-resident expert weights, bounded pinned staging, fixed per-layer GPU LRU slots, asynchronous H2D with per-slot events, and prefill in waves when the routed set exceeds capacity. It says slot size is deducted before KV sizing and explains wave-size tradeoffs; it provides no comparable measured phase-release/graph-rebuild A/B. This is an implementation reference for bounded staging/lifetime discipline, not evidence that a persistent cache is cheaper than rebuilding on this target. [Author's Mini-SGLang blog](https://nothiny.github.io/2026/09/15/mini-moe/)
- **Personal implementation history:** Adrian Hoehne’s engineer-authored hot-cache journey labels its performance arc development observations, says the cache is additive to retained CPU/RAM experts, and says warmup/transient compute buffers require a conservative VRAM reserve. It also reports that routing, worklist, view, and merge overhead matter at one-token decode and that an initially successful graph could be slower with a poor hot list. Useful warning against treating hit rate or freed bytes as an end-to-end result; it does not test releasing/rebuilding the cache per prompt. [Hot-cache journey and learnings](https://adrianhoehne.github.io/llama.cpp/docs/moe-hot-cache/moe-hot-cache-journey-learnings.html)

## Strata mapping and novelty boundary

The author's transaction resembles the already-audited R157/R158 lifecycle question, so R174 does not propose a new scratch-retirement or cache-rebuild architecture. R157 records that standalone native Prefill owns disposable scratch separately from SessionState/MTP/cache/decoder graphs, while borrowed scratch aliases cache-owned slots and must be refilled and republished before decode. It also warns that rebuilding or changing cache geometry invalidates pointer snapshots and verifier/cache graph inputs. R158 says native standalone capture is not all one persistent graph: session/token graphs are skipped in native mode, but verifier window/commit capture remains lazy and MTP owns separate graphs. Retiring scratch alone need not rebuild those graphs; reallocating cache storage or moving its maps can.

The current diagnostic worktree inspected for this turn is `/home/yayoi/ghq/github.com/yqYo1/Strata/.worktree/diag-xe-host-issuer-ledger-20261012` at the supplied base `69495` plus four host-observer files. Source comments at `src/core/expert_source.cpp:2526` distinguish reclaimable file-mapping pages from locked/pinned memory: dropping the page cache too caused about 200 major faults/s and added about 8 ms/window in the source's historical measurement. That is a separate RAM-residency cost; a phase experiment must distinguish releasing pinned/VRAM ownership from discarding OS page-cache contents. `src/prefill/prefill.cpp:1254-1256` also rewrites the MMQ identity table because prompt use overwrites borrowed cache slots. These source observations agree with R157's ownership contract; they do not show that a cache teardown improves current throughput.

Novel result here is limited to the personal-source screen: one author supplies a concrete phase-swap A/B with measured graph-rebuild and cache-restore penalties and a pending-token threshold; another authors a route-capacity bypass to preserve decode cache across prefill. This makes “release the cache?” a testable choice between (a) transactionally releasing enough decode-only GPU storage to admit a larger prefill chunk, and (b) retaining cache/map/graph allocations while taking a prefill fallback/bypass. The existing R150/R151 bounded-bank proposals and R158 retirement seam remain distinct, previously documented designs and are not claimed as new.

## Main-owned next discriminator

Keep this as a measurement design only. At fixed build, model, target, route policy and actual context, compare current compact 8,192 prefill plus the current cache-borrow/refill path against a candidate phase transaction that releases only eligible decode cache/buffers, selects a larger prefill chunk, and restores decode state before the first token. Use the real pending-token count and matched prefix/session class; include short 64/256/512/1,024-token follow-ups and sufficiently large requests, since the external author's sign changed between 1,024 and 2,048. Record separate wall intervals for release, replacement allocation, prompt, graph capture/rebuild, cache refill/map publication, and time-to-first-token; the adoption metric is full request latency plus subsequent physical decode, not a sum of component timers or logical H2D bytes. Pair at least three observer-off repetitions per arm, interleave order, and retain exact correctness/state receipts. Require the full 262,144-position capacity and existing 6.1875-GiB INT8-KV reserve throughout; no short-context result qualifies the full-capacity claim. Do not choose a threshold from the 2x3090 author's value: derive it from target pending-token cohorts and the measured all-in transaction.

This discriminator must separately preserve the authoritative host/device expert map and any graph inputs across the transition. For an owned Prefill scratch retire, preserve the cache and captured decoder owners. For a cache rebuild, first quiesce all readers, refill from retained RAM sources, republish the map, then rebuild/refresh each graph consumer that captured old addresses. Preserve reclaimable file page-cache data; do not treat mapped logical extents or submitted copy payloads as physical bytes. No user-visible performance promise follows from the external reports.
