# R173 — batch-off mixed-format dequant service candidates

Date: 2026-10-12 (Asia/Tokyo). Read-only source and primary-source research. No build, test, inference, GPU/device/process query, profiler run, source edit, cleanup, or Git command was performed. This report is a candidate screen, not a performance result.

## Decision

For the exact quiet64K batch-off path, the strongest source-grounded candidate is to extend the existing fused packed-IQ GEMM route from cache-resident experts to eligible streamed experts whose packed blob is already in the device staging ring. That path can avoid separate GU and Down dequant submissions and the full FP16 GU/Down weight materialization followed by GEMM rereads. The candidate is conditional on XMX support, the existing fused-kernel format/shape support, and a route count no greater than the kernel's 256-row tile. It would keep the ring slot live through the Down GEMM, which can reduce staging overlap; this ownership cost is the central risk.

A lower-risk API experiment is one heterogeneous grouped dequant launch accepting distinct `gu_type` and `down_type`, instead of the current two launches per window. It reduces launches while preserving the current expanded-weight/GEMM arithmetic, but does not remove dequantization or the FP16 write/read traffic. Prefer the fused-GEMM candidate only if the actual route census shows enough streamed experts in eligible row bins to justify its longer source-blob lifetime.

No candidate is adopted here. Existing quiet64K data (three samples per chunk setting) reports 8192-chunk mean 353.58 tokens/s and 6144-chunk mean 285.51 tokens/s. Those numbers compare chunk settings, not dequant implementations. No new GPU measurement is available. The coarse PHASE observer's 30.85 s CPU cost and 200,451 marker calls make its phase totals unsuitable as proof that device dequant is the exclusive bottleneck.

## Pin and actual batch-off path

Source worktree: `/home/yayoi/ghq/github.com/MistVVK/XeStrata/.worktree/perf-xe-prefill-row-bounded-scratch-20261011`, supplied HEAD `39e395a103af36323262cdc0dbaea27cba81f3e4`. Local guidance names the CPU as Ryzen 5 5600X (AVX2, no AVX-512) and GPU as Intel Arc B570 (about 10 GiB); it also requires runtime capability checks rather than product-name dispatch. No hardware was queried for this report.

The qualified quiet-arm setting is `STRATA_PREFILL_NATIVE_DEQUANT_BATCH=0`, confirmed in R171's source/recipe audit. In the pinned caller, the opt-in at `src/prefill/prefill.cpp:2219-2223` selects grouped dequant only when this value is nonzero, `lay.native` is true, and MMQ is off. Thus this quiet arm uses the existing per-expert calls; it must not be described as a batch-on grouped run. The exact source key includes `PREFILL` and `DEQUANT`; `STRATA_NATIVE_BATCH` is not the source variable used at this call site.

There is an eligibility split before those calls. `STRATA_PREFILL_FUSED` defaults on (`prefill.cpp:1975-1980`). When the layer is native, non-MMQ, XMX is available, formats/dimensions pass, the expert is resident, and its routed row count is at most `kIqGemmTileRows=256`, `fusable()` routes it to `iq_gemm_grouped_f16` (`prefill.cpp:1981-1991`). That existing route consumes packed GU/Down bytes in the GEMM and does not use the per-expert FP16 dequant wrappers. The remaining native experts are ordered for staged/cache access (`prefill.cpp:1970-1974, 1992-2001`) and are handled by the streamed compute path.

For each eligible nonresident native expert on batch-off, the current compute branch calls `iq_dequant_gu_f16` and then `iq_dequant_f16` for Down into reusable FP16 slots (`prefill.cpp:2465-2482`), then eventually runs the unchanged GU/SwiGLU/Down products (`prefill.cpp:2176-2215, 2485-2489`). `iq_dequant_gu_f16` submits one `parallel_for` whose parity plane handles both gate and up; it is not two calls (`iq_kernels.cpp:1622-1637`). Down submits a second `parallel_for` through `iq_dequant_f16` (`iq_kernels.cpp:1607-1620`). Both use runtime `dq_dispatch`, which selects the layer's GGML format (`iq_kernels.cpp:1298-1320`). `NativeFmt` carries separate GU and Down type IDs and offsets; Unsloth layouts can therefore have mixed GU/Down formats (`iq_kernels.hpp:9-13, 84-91`).

The component directions are real: a standard expert expands `GU_ELEMS=2*2560*640` and `D_ELEMS=2560*640` half weights, about 9.83 MB decimal total, then the dense products read those weights. This is a source extent, not physical traffic or a critical-path duration. The old R170 IQ3_S report's 110-byte block and dequant arithmetic describe only that exact type and must not be generalized to the model's mixed per-layer format pairs.

## Candidate A: reuse packed-IQ fused GEMM for eligible streamed experts

Existing `iq_gemm_grouped_f16` already takes a per-layer type and an array of packed expert pointers, decodes weights into a local tile, and multiplies them without writing the full dequantized matrices (`iq_kernels.hpp:66-81`; `iq_kernels.cpp:1335-1343, 1780-1802`). Current prefill admits it only for cache-resident experts (`prefill.cpp:1981-1991`). A narrow extension would build the same bounded pointer list from staged ring-slot addresses for a contiguous eligible window, use the existing fused GU/SwiGLU/Down product order, and fall back to current materialization for any unsupported format, hardware, or routed-row count.

Source supports these bounds: `kIqGemmGroup=32`, `kIqGemmTileRows=256`, the kernel has compile-time type dispatch, and the existing caller already checks both GU and Down format/dimensions with `iq_gemm_grouped_ok` (`iq_kernels.hpp:66-74`; `prefill.cpp:1981-1989`). The kernel comments state it decodes each 128×128 K slice into local FP16 and that a 256-row tile avoids decoding weights again for each row group (`iq_kernels.cpp:1335-1339, 1380-1384`). A 16-entry staging ring is below the 32-expert API cap, but it does not itself prove a 16-expert contiguous eligible window exists.

Main risk: today a streamed slot's `m.used[slot]` event is recorded after dequantization has consumed the source. Fused GU and Down still read the packed blob, so slot reuse must wait until the Down product completes. That moves release later, can stall the producer, and can reduce the overlap that the ring currently provides. Any experiment must preserve the sequence frontier, copy completion and queue ordering, bounds lifetime, row scatter, and failure/drain semantics. No route-histogram share or availability of enough `<=256`-row streamed experts is established by this report.

## Candidate B: mixed GU/Down grouped dequant submission

The existing grouped APIs each issue one command: GU launch has expert and gate/up parity dimensions; Down has an expert dimension (`iq_kernels.cpp:1724-1773`). The caller supplies the same `IqDequantGroup` but calls them separately and may independently fall back per axis (`prefill.cpp:2259-2282` in the batch-on branch). A new API taking both layer types could flatten two output regions into one launch. Per-layer type dispatch is uniform across experts, and the source already has the runtime `dq_dispatch` needed for distinct types. It could remove one API/launch per grouped window; at `n=1` it would replace two launches per expert with one.

This saves command overhead only. All three matrices still need expansion, the FP16 write/read and dense GEMMs remain, and a shared launch may have extra role-branching or poor tail utilization. Unlike Candidate A, it need not extend ring ownership beyond the two dequant readers, provided its completion marker follows the joint command. This is a useful controlled microbenchmark if the issuer ledger shows wrapper submission cost is exposed, but it has no evidence of production benefit by itself.

## External implementation comparison

- **ggml SYCL:** its backend documentation describes an XMX gather path that dequantizes supported weights straight into XMX tiles and performs the product without a standalone expanded-weight tensor. The documented type list includes IQ3_S, IQ3_XXS, and other IQ formats; it says unsupported shapes/types fall back. It reports about 50% faster prompt processing for one Qwen3-30B-A3B UD-IQ3_XXS case on Arc Pro B60. This supports the execution pattern and explicit eligibility/fallback design. It does not predict Strata's result: that is a different codebase, model, card, shape and measurement. [ggml SYCL backend documentation](https://github.com/ggml-org/llama.cpp/blob/master/docs/backend/SYCL.md#xmx-gather)
- **SGLang:** its expert-parallelism docs split MoE dispatch, permutation, grouped-GEMM runner, and combine into explicit stages, with fused/permutation backends. This supports keeping scheduling/lifetime policy distinct from format-specific kernels; it does not provide a transferable GGUF-IQ dequant kernel for this single-GPU path. [SGLang expert parallelism](https://github.com/sgl-project/sglang/blob/main/docs/docs/advanced_features/expert_parallelism.mdx)
- **vLLM:** its fusion guide catalogs fusions and lists platform/quantization eligibility. The general lesson is to gate specialized fusions and retain fallbacks, not to infer compatibility with Strata's IQ layout. [vLLM fusion design](https://github.com/vllm-project/vllm/blob/main/docs/design/fusions.md)
- **Intel LLM Scaler:** its primary repository describes Arc Pro B60/B70 support and its vLLM distribution supports GPTQ/INT4 and FP8. The README is product/backend context only; this audit did not inspect a corresponding IQ/GGUF kernel or claim LLM Scaler implements the candidate. [Intel LLM Scaler](https://github.com/intel/llm-scaler)

## Novelty versus prior reports and evidence limits

R170 already audited exact IQ3_S block work and proposed an isolated dequant component arm; this report does not restate its IQ3_S-specific roofline. R171 corrected the real quiet-arm environment to `STRATA_PREFILL_NATIVE_DEQUANT_BATCH=0` and defined the host issuer ledger, whose results Main owns. R172 reviewed the bounded ledger candidate and identified residual observer overhead; that is why this note treats host submission exposure as unproven. R158 covered reuse/cache and overlap contracts. The earlier native-batch caller and service-bound reports already proposed window-length counts and warned that component timings do not establish an end-to-end gain. R270 considered a resident-only small-M direct packed-IQ projection; R173 narrows a different seam in the current pinned caller: reuse the already-existing fused grouped GEMM for eligible *staged* experts, with ring-source lifetime moved to the last packed-weight reader. Candidate B, a one-launch mixed GU/Down grouping API, was not part of those prior group-window counts.

Do not convert the model's logical H2D request total (about 400 GB over eight chunks in the cited accounting) into PCIe traffic or a device ceiling using the isolated 6.446 GB/s component figure. Do not call a 380 GB/s quotient from vendor bandwidth a measured attainable rate. Likewise, profiler phase spans contain inter-command gaps and the cited observer added 30.85 s CPU-clock time across 200,451 marker calls; neither is exclusive dequant GPU service.

## Main-owned next experiment and stop conditions

First join the actual quiet64K per-layer format pair, streamed/resident/fused classification, routed-row count, and grouped `nd_n` window counts to the authoritative route census. If too few streamed experts are eligible by the 256-row limit, stop Candidate A. Do not infer an eligible population from total prompt rows or total H2D bytes.

If a real eligible bin recurs, Main can make a source-matched synthetic device arm using its actual GU/Down type pair and observed `ne` values: current dequant-to-FP16 plus current GEMMs versus the existing fused `iq_gemm_grouped_f16` using the staged-pointer lifecycle. Report host enqueue and checked device completion separately, use paired ABBA ordering, and compare exact output bits at both projection outputs where the existing contract allows. The first fused test must include group tails and a staged ring slot whose release event follows the final Down reader. If it passes, run a quiet matched 64K request with only the candidate switch changed, preserving the exact batch-off setting, route/H2D counts, selected outputs, health and fault gates; retain every sample and compare repeated prefill wall intervals.

Stop if parity fails, a failure path releases a ring slot early, any required type/device falls out of the current fallback safely, source staging stalls enough to erase the quiet wall result, or a quiet paired interval does not show a repeatable improvement beyond run variation. The mixed dequant launch is the fallback research arm only if the issuer ledger indicates exposed API submission cost and Candidate A has inadequate eligibility or unsafe overlap tradeoffs. No hardware-independent threshold or speedup promise follows from these sources.
