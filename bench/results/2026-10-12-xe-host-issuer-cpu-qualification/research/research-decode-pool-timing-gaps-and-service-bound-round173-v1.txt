## Finding

The current source provides a useful host-side phase boundary, but the dominant exposed decode bound is not inferable from the present evidence. The physical decode rate must remain the outcome. The request counters and pool phase timers explain where host elapsed intervals occur, but they do not distinguish worker compute from pool synchronization, quantify CPU/GPU overlap, or prove that either CPU expert service or GPU/cache re-entry is on the critical path.

The current verifier launches the window graph, waits until each layer raises its host sequence word, invokes the CPU pool callback, checks copy status, and then raises the flag that lets the graph proceed (`src/core/verify.cpp:1510-1514,1535-1595`). The native dispatcher submits the GPU plan/copies before building and running CPU jobs (`src/core/expert_source.cpp:1640 onward; current CPU job path 1802-1885`). This creates a plausible CPU/GPU overlap interval but also a callback dependency at each layer. A slow `ms_run` can be hidden by GPU work, or can be the layer tail; the source order and aggregate timers alone cannot distinguish those cases. GPU stage event totals are not a synchronized critical-path timeline and must not be added to host counters or used as aggregate ceilings.

The current `DecSnap` reports request-level verifier waits/pool/host and dispatch plan/activation-quantization/jobs/CPU values, plus route counts (`src/program/generate.cpp:9047-9058,9793-9807`). `ExpertPool::run_split_multi_native` already takes wall-clock intervals around GU, intermediate FF quantization and Down (`src/kernels/cpu/pool.cpp:470-505`), but this request timing path does not snapshot or print those pool counters. Its `ms_multi_*` counters accumulate for the pool lifetime (`include/strata/kernels/cpu/pool.hpp:145-149`). Printing request deltas is the lowest-cost first addition: use the existing counters and request-boundary snapshots, no task clocks, atomics, synchronization or added timers. Label GU/FF-quant/Down as nested host phase wall, and packed blob bytes as logical submitted extent rather than DRAM traffic.

The phase clocks still do not partition `drive.d.ms_run`. Each GU/Down `run_phase` includes pre-publication parked wait, batch publication, worker plus optional host draining, wait for completion, and re-park (`pool.cpp:381-390`). Its native `ms_multi_*` interval surrounds that entire phase, so it includes pool waits and scheduling. FF quantization is serial caller work between those phases. The pre-existing `phase_ms()` buckets are updated on the regular `run()` path and do not split these native multi-token phases (`pool.cpp:519-565`; `pool.hpp:156-167`). A single-token throughput or CPU kernel microbenchmark cannot be substituted for the actual verify-window mixture of CPU-owned job counts and `ExpertJobMulti.nt` values.

## Existing evidence and novelty boundary

The earlier round-7 report already recommended request-delta output for the three pool counters and bytes; the implementation report records that diagnostic in a different W0141 worktree. R204 reviewed a closed task-6 diagnostic and established that its phase spans are not additive or equal to CPU-dispatch time. Its four phase sums were 153.823–160.918 ms/window while the separate fresh-first `CPU` dispatch host-counter mean was 123.7767 ms/window; these are different scopes, not a contradiction to repair. The closed task-6 report was explicitly diagnostic-only and not performance eligible.

R215 and R284 already specify a bounded deeper diagnostic: count actual per-window expert jobs and `nt`, preserve layer `(GU type, Down type)` pairs, record each pool participant’s worker-local CPU and wall time around its actual native row fragments, maintain a phase start-to-finish envelope, and separately measure pre-publication wait, wait-for-done, and re-park. The host drainer gets its own slot; fixed storage is allocated before workers start; workers write only their own records; the disabled path makes no clock calls; and the result is joined only after worker completion. R284 explicitly warns that fragment wall sums are not phase latency, and that neither thread CPU time nor logical bytes prove DRAM saturation. This round does not repeat that proposal as a new one.

The specific new result is a source-pinned reconciliation for XeStrata revision `39e395a103af36323262cdc0dbaea27cba81f3e4`: its source has built-in per-phase host timers but has not connected them to `DecSnap` output; its current worker loop claims flattened row tasks (`src/kernels/cpu/pool.cpp:337-379`) and resolves expert/range fragments before row kernels, so a task ID alone cannot be joined to one expert or NT cohort. Unlike the older W0141 report, current `pool.cpp` has no `run_phase` wait split exposed for native multi phases, and no request-window/layer/worker service record. The existing round-284 design remains the closest implementation contract and should be reused if Main chooses that separate instrumentation experiment.

The R147/630 latest report registry (`2026-10-12-unitrace-v711-health-qualification`) says actual profiler qualification failed, no model was launched, and the original profiler campaign failed after a host SIGSEGV. Its tiny health trace is not performance-eligible and its collection overhead was not measured. Therefore no new GPU timeline, unitrace/PTI, or event-correlation claim is admissible from that campaign. Current source stage profiles, when enabled, are only supplementary diagnostics; they do not fix the missing causal host/device join.

## Lowest-cost bounded measurement sequence for Main

1. **Whole-request baseline, observer off.** Keep independent prefill and decode selection. Preserve the existing per-phase decode knob and hold all other inputs/settings fixed. Use at least three repeated decode samples per arm, with the same actual context position, restored/fresh state class, emitted-token count, MTP path/acceptance, task setting, route/cache policy, build, and hardware. A fresh request and a restored continuation are separate cohorts. Compare paired physical decode latency/tokens per second from this observer-off arm; do not use a phase subtotal as an adoption result.
2. **Counters-only phase view.** Add no new timing calls: snapshot `ms_multi_gu`, `ms_multi_q`, `ms_multi_down`, and `multi_bytes` alongside `DecSnap`, and print their per-window request deltas. Also retain current CPU callback and verifier wait counters, exact window denominator, and CPU miss/entry counts. Require one line per completed request, same window counts, and explicit zero-window behavior. This answers whether the current main callback spans are concentrated in GU, quantization, Down, or pre-pool dispatch, while preserving the caveat that GU/Down include waits and may overlap GPU work.
3. **Worker service only if step 2 leaves a decision question.** Reuse R284’s bounded preallocated design on the actual default task-0 setting, not the task-6 diagnostic. Collect per-layer/window exact `(GU type, Down type, NT)` job/row counts; worker and host per-fragment monotonic wall plus per-thread CPU time; active drain CPU/wall; phase envelope; and the three host wait sites. Reconcile job/row counts to the already-built job arrays. Report thread CPU service sums separately from wall spans and phase envelope. Keep output fixed-size and bounded, emit after the request, and do not log each task or expert.
4. **Observer calibration before using instrumented values as evidence.** On identical input/state/configuration, compare clocks-off baseline, counters-only, and clocks-on cohorts. Record timer-helper cost separately; keep the optimization outcome from clocks-off runs. Predeclare an overhead acceptance limit, keep counter collection and clocks enabled as separate modes, and invalidate component attribution if the worker clocks materially alter physical latency or scheduling. Do not treat event profiler data as an overhead control until tool qualification and collection overhead are independently established.
5. **Bounded architecture decision.** If per-worker CPU service occupies the phase envelope and request/window wall moves with it, investigate CPU service or task partitioning. If CPU completion precedes the relevant GPU/plan/copy tail, or phase spans change without physical decode benefit, do not pursue a CPU-kernel rewrite from those counters. If the result remains ambiguous without a trusted device timeline, keep the service-bound conclusion unknown; do not infer bandwidth from `multi_bytes` or other CPU ceilings.

## External primary-source screen

- **KTransformers SOSP’25 is the closest concrete hybrid design.** Its paper describes a lock-free CPU task queue running routed-expert work while GPU shared-expert kernels execute, followed by a wait/merge; it puts host submit/sync callbacks in the device stream to avoid host interruptions. It separately introduces expert deferral across layers to create more overlap, but that changes the immediate/deferred computation and allows slight model-behavior changes. It also distinguishes AMX for high arithmetic-intensity work from AVX-512 for decode at four or fewer tokens per expert, reporting a measured decode crossover on its Xeon test setup. The queue/overlap pattern is an architectural comparison, not a transferable speed claim: XeStrata already starts the GPU plan before synchronous CPU pool service, uses MTP multi-token expert rows, and targets a 5600X/B570 rather than dual-socket AMX hardware. Expert deferral is out of scope for exact-output optimization without a separately authorized numerical-quality policy. [KTransformers paper, §3.3–4](https://madsys.cs.tsinghua.edu.cn/publication/ktransformers-unleashing-the-full-potential-of-cpu/gpu-hybrid-inference-for-moe-models/SOSP25-chen.pdf)
- **llama.cpp exposes a different GPU/cache path, not a direct CPU-pool alternative.** Its public issue/source description documents CPU-resident experts and selective per-forward copies of selected expert rows to a GPU tensor, and proposes persistent GPU slots to avoid repeated copies. This is relevant to GPU cache re-entry: the differentiator is residency across forwards, not worker scheduling. The report also includes author-reported numbers for a separate PoC; do not treat those as controlled XeStrata evidence. XeStrata already has its own GPU expert cache and route counts, so the testable question is whether cache misses/copy re-entry lie on the timed critical path, not whether the other project's cache result transfers. [llama.cpp issue #20757](https://github.com/ggml-org/llama.cpp/issues/20757)
- **Intel LLM Scaler is useful ecosystem context but supplied no CPU MoE kernel or offload result for this question.** Its official repo describes a vLLM-based stack and release notes for Qwen MoE and MTP support on Arc Pro B70; it does not establish a comparable CPU-expert service path or a transferable timing decomposition. [Intel LLM Scaler repository](https://github.com/intel/llm-scaler)
- **Current vLLM and SGLang EP documentation concern GPU expert parallelism and communication overlap.** vLLM’s EPLB tracks forward-pass expert-load skew to rebalance expert placement across EP ranks; SGLang describes all-to-all and grouped-GEMM backends with computation/communication overlap. These apply to multi-GPU expert distribution, not a single-GPU plus system-RAM CPU worker pool, so they suggest no immediate code transplant. [vLLM expert parallel deployment](https://github.com/vllm-project/vllm/blob/main/docs/serving/expert_parallel_deployment.md), [SGLang expert parallelism](https://github.com/sgl-project/sglang/blob/main/docs/docs/advanced_features/expert_parallelism.mdx)

## Selection and workload constraints

The user-supplied cold 16-token decode-at-64K observation (means 7.04 versus 7.64 tok/s, with a paired rank reversal) is too short and too order-sensitive to identify warmed steady-state decode performance. It is not an adoption result. Keep decode knob selection separate from prefill selection, and require at least three repeated decodes per candidate with paired/interleaved order and matching continuation state before deciding. Report sample values and uncertainty; do not pool them with prefill or claim aggregate TPS from a ceiling.

The next Main-owned run should use an actual context of at least 32K and distinguish fresh-first decode from restored continuation. Preserve full 256K-context capacity constraints throughout; do not lower the memory/KV/VRAM reserves or claim 256K qualification from a smaller resident state. A full-256K claim requires the model input/state actually to reach 262,144 positions and decode there under the same lifecycle and correctness gates. The R147/630 status keeps full 262,144 qualification open. Any candidate changes need its own observer-off repeated decode comparison before selection.
