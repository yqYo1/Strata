## What the measured hardware budget says

A 70-token/s decode target gives **14.286 ms per emitted token** for the entire request critical path. The Ryzen 5 5600X / Arc B570 three-process capacities in `bench/results/2026-10-10-hardware-architecture-decisions/` are component controls, not attained model service: CPU RAM read 36.87 GB/s, RAM copy 37.58 GB/s, synthetic three-worker packed host copy 13.74 GB/s, H2D host-USM 6.447 GB/s, D2H host-USM 5.643 GB/s, pageable H2D/D2H 4.605/5.274 GB/s, VRAM copy 330.07 GB/s, and M80 rotating-eight GPU FP16-input GEMM 13.16/10.08 TFLOP/s for GU/Down. The 0.818 TFLOP/s six-core register-FMA value is not a ceiling for the quantized integer SIMD dot path. The B570 has no qualified production-shape native IQ dequant capacity or full routed-decode capacity in this matrix.

If all 14.286 ms were available to a single serial transfer component, that budget is 92.1 MB at the measured H2D host-USM rate, 65.8 MB at pageable H2D, 80.6 MB at D2H host-USM, or 196.4 MB at the synthetic ordinary-RAM host-copy rate. These are payload-equivalent ceilings with every other operation assigned zero time. They cannot be combined as if the same bytes traverse all links, and observed production H2D may not match the one-way 256 MiB benchmark's memory/queue path.

The CPU capacity fixture is exactly the GU22/IQ2_S + Down20/IQ4_NL pair at H=2560, FF=640. Its five-worker-pool-plus-host complete service per expert-token is 72.204/90.978 µs for NT1 hot/streaming, 48.452/54.215 µs for NT2, 39.076/42.931 µs for NT3, and 34.736/38.738 µs for NT4. The latter numbers are fixture medians over two disjoint cohorts and three processes; the hot and streaming cohorts differ in expert set and job count, so they do not isolate cache causality. Direct single-caller service is much slower (NT1 261.405/286.466 µs, NT4 147.419/148.362 µs). “Streaming” here means the selected 192-blob CPU fixture, not production GPU cache misses or measured DRAM traffic.

For a scale check only, a 48-layer, K=10 route has at most 480 expert-token entries per output token. Multiplying 480 by the CPU pooled service anchors gives these **conditional service sums**:

These arithmetic products do **not** establish a model lower bound, latency prediction, or actual CPU miss share. They assume every route entry uses the measured 22/20 pair and its matching NT service, charge all CPU fixture service serially to this token's budget, and leave no time for routing, attention, residual transfers, CPU/GPU orchestration, or unrelated work. A standard one-row decode has NT1; NT2–4 require the same expert to recur across multiple verifier rows. Not all routed rows become CPU jobs, and calls with other current formats have no matching CPU capacity result. The current active pair set is `(18,20), (18,42), (21,20), (21,42), (22,20), (22,42), (23,20)`; only `(22,20)` is covered by this CPU fixture. Do not assign its rate to the other six pairs.

The corresponding routed-miss thresholds illustrate how much moving work would be necessary **only under the same all-22/20, zero-other-work scenario**: at NT1 no more than about 198 hot-fixture-equivalent or 157 streaming-fixture-equivalent CPU expert-token units fit the full budget; at NT4 the values are 411 and 369. If 480 entries all followed that branch, these thresholds would require roughly 59–67% of NT1 entries or 14–23% of NT4 entries to run elsewhere or be avoided. In a real route, use observed calls per pair and branch, not the 480-entry envelope.

## Cache misses and the CPU/GPU split

“512 experts” is the per-layer expert population, not a cache-hit rate. The route's relevant quantity is the count of **selected** experts per layer/chunk that are actually resident on the GPU, versus those sent to CPU-native service, peer/helper GPU, or streamed to the primary GPU. A denominator of 512 tells how many experts are available for placement, not how many of the K routed entries hit. The transfer capacity figures do not tell which weights are resident or which source path feeds a miss.

The present production code classifies routes using the actual `NativeFmt` at each layer, route counts, `host_res` cache slots, staging order, and `stream_all`/MMQ/fused decisions. In the normal GPU expert path, an expert already resident in the cache avoids its packed-weight H2D copy; a nonresident expert is streamed from the pinned blob or host stager and pays one packed-blob copy before its products. A CPU-owned decode job instead uses native packed weights in host RAM and avoids that GPU transfer while paying the CPU expert service. For current exact `blob_bytes(l)`, one selected streamed miss consumes one payload copy; cache misses across tokens may also repeat if the expert is evicted before reuse. The source does not establish a current hit/miss histogram, actual reuse distance, transfer bytes by pair, or evictions for the target decode.

At 70 tok/s, the 92.1 MB/token H2D host-USM payload-equivalent ceiling is far below the hypothetical transfer of 480 full expert blobs if all were copied on every token. But this is not a finding that actual decoding copies 480 blobs: GPU residency, CPU routing, per-layer pair-specific blob size, cache lifetime, and reuse are unresolved. Conversely, moving CPU work to GPU by streaming a blob for each miss can spend the saved CPU time on PCIe and lose the budget. Moving a hot expert to GPU residency can amortize transfer over reuse, but is useful only when the measured selection rate and simultaneous VRAM budget justify its residence and its GPU compute/dequant service fits the remaining critical path.

Current storage evidence says full expert residency does not fit the B570: an all-layer cache is larger than the device budget, and even QSA/KV/state/scratch reservations consume substantial space. The architecture decision is therefore a placement trade, not “put all 512 experts on GPU.” A route-weighted cache policy could be considered only after recording resident selected calls, per-expert route frequencies/reuse distance, and per-layer source bytes in a clean decode run. The number of cache slots or the route top-k alone cannot choose the hot set.

## Speculative grouping versus prefill

The CPU decoder verifier uses the multi-row expert dispatch: for each layer/window it groups rows by expert ID, increments that job's `nt`, and submits one job per distinct CPU-missed expert. A single-token decode sets `T=1`, so every CPU job is NT1 even if several jobs run in parallel. For a verifier window of `T` rows, each layer has `T*K` route entries, distinct jobs are no greater, and a job's `nt` is the number of rows in that window routed to that particular expert and owned by CPU. The calibrated CPU set covers NT1–4 only; an `nt` of 5–8 is permitted by caller storage but uncharacterized. Speculation can reduce service per expert-token if real router collisions create repeated rows, but it also executes suffix rows later rejected by verification. Record accepted draft length and separate CPU work for committed versus discarded rows. Do not treat NT4 capacity as four times more decode throughput or assume every expert job has NT4.

A 32K prefill is a different workload. Its chunk may carry many rows per expert, use GPU MMQ/fused routes, and stream/cache weights once per layer/chunk; its row geometry, cache behavior, and path mix cannot be applied to one-row decode. In the current decoder capacity evidence, and the committed layer-major prefill worksheet, keep prompt and decode service, cache lifetime, transfers, and 70 tok/s timing budgets separate.

## Architecture candidates and primary implementation evidence

No new optimization is admissible from the available measurements alone. Three conditional avenues remain, selected by the route census rather than by isolated capacity rates:

1. **Place frequently routed experts in GPU residency** only if actual route frequency/reuse is high enough to amortize the exact per-pair transfer, all required VRAM reservations still admit, and measured GPU dequant/GEMM rather than PCIe becomes acceptable. Cold or low-reuse misses are candidates for CPU native execution only if their pair and `nt` have a capacity measurement. This is cache-placement/route evidence, not a kernel proposal.
2. **Use speculative row grouping** only if the verifier histogram shows enough same-expert CPU rows at NT2–4 to move the CPU service sum under the remaining budget, and accepted-versus-discarded compute does not erase the throughput gain. If mostly NT1 or NT5–8, the existing fixture gives no justification.
3. **Prefer the already-existing quantized GPU branches where they are actually eligible** only after the route records generic IQ→FP16 dequant, MMQ gather+MMQ GEMM, or fused-native execution per layer/chunk and a matched device-capacity measurement proves the branch lowers the request critical path. This is a route/measurement question, not a new fusion design; the earlier R148/R242 fusion/SG16 proposals are not restated as new work.

For implementation precedent, llama.cpp's CUDA `mmq.cu`/`mmq.cuh` has quantized matrix-multiplication kernels with direct type-specific packed-tile load and dot routines, and its support list includes IQ2_S, IQ3_XXS, IQ3_S, IQ4_XS, and IQ4_NL. This demonstrates that low-bit weights can be consumed by tiled dot kernels without first writing a complete FP16 weight matrix. It is CUDA-specific and the B570 uses SYCL; the active Strata tree already has its own MMQ/fused branches. The precedent does not establish portability, numerical behavior, or a B570 speedup. [llama.cpp MMQ type support and fallback](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cuda/mmq.cu), [MMQ packed-tile and dot dispatch](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cuda/mmq.cuh)

SGLang documents a different row-reuse pattern: dispatch/permutation, grouped GEMM, and inverse permutation, with separate prefill and masked-decode backends. Its grouped Triton kernel sorts token rows by expert and pads groups to the GEMM tile. This is a useful structural reference for preserving expert row reuse and batching multiple experts, but it targets different quantization/hardware paths, and this Strata decoder already groups verifier rows by expert while prefill already has grouped MMQ. It is not a new candidate or performance proof for the 5600X/B570 route. [SGLang expert-parallel grouped runner overview](https://github.com/sgl-project/sglang/blob/main/docs/docs/advanced_features/expert_parallelism.mdx), [SGLang grouped MoE kernel](https://github.com/sgl-project/sglang/blob/main/python/sglang/kernels/ops/moe/fused_moe_triton_kernels.py)

## Decisive measurement before architecture choice

The selector is one clean route census for ordinary decode and a separately labeled speculative decode, using the exact current pack and the same target hardware/build/settings. For each `(request,chunk,layer)` report loaded `(gu_type,d_type)`, exact role bytes and `blob_bytes`, `T`, K, routed entries, distinct expert jobs, each job's `ne`, actual generic IQ dequant / generic oneMKL GEMM versus MMQ/fused branch, primary/peer/CPU owner, GPU-resident versus copied miss, copy source (pinned versus host stager), bytes copied, and actual completion/call counts. Keep the 512-expert population and actual selected-routed count separate. For speculation add accepted prefix, discarded suffix rows, and NT1–8 frequency; NT5–8 remain uncalibrated. Join only `(22,20), NT1–4` CPU jobs to the existing fixture; acquire pair-specific CPU service for all other active pairs if they are material. For the GPU branch, require production-shape actual-format dequant and GEMM service plus proof that the existing event source covers internal library work before treating event spans as complete.

Compare clean request wall latency and critical-path phase time on the same input with CPU/GPU placement held fixed; separately account CPU host/worker time, pageable or host-USM copy payload/time, and GPU event/device work. If route-level counts are incomplete or service clocks cannot be reconciled, report the component budget and missing data without selecting an optimization. In particular, do not multiply 480 expert calls by the isolated pool time and call it a model lower bound, and do not use prefill capacity as decode service.
