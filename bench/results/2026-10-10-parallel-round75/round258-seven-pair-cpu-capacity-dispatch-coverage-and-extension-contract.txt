## Zen 3 dispatch by role and NT

This is the default source-selected behavior for a build with AVX2 and without AVX-512, `STRATA_NO_IQ256`, `STRATA_NO_IQ4NL`, or a nondefault `STRATA_IQ_MT_MIN`; it is eligibility derived from source, not a fresh runtime dispatch census. `native_gu_dispatch` defaults the multi-token threshold to 2. `native_down_dispatch` independently uses the same default threshold for IQ4_NL. Q2_0 Down does not use `native_down_rows`: the pool's type-42 branch invokes `q2_rows_any`, and the harness reports its Q2 AVX2/AVX-512 dispatch separately.

| --- | --- | --- | --- |
| GU 18 (IQ3_XXS) | GGML `vec_dot` | AVX2 `iq256_gu_rows` | AVX2 `iq256_gu_rows` |
| GU 21 (IQ3_S) | GGML `vec_dot` | AVX2 `iq256_gu_rows` | AVX2 `iq256_gu_rows` |

| Down 20 (IQ4_NL) | GGML `vec_dot` | AVX2 `iq4nl256_down_rows` | AVX2 `iq4nl256_down_rows` |
| Down 42 (Q2_0) | AVX2 `q2_rows_any` | AVX2 `q2_rows_any` | AVX2 `q2_rows_any` |

AVX-512-specific kernels are not eligible on Zen 3. `STRATA_IQ3S_MT1=1` is not a default Zen 3 exception: the opt-in single-token IQ3_S path also requires Intel gather-fast CPU detection. Environment overrides can change the table and must be captured in any later run. NT5–8 are not accepted by the present calibration harness (`kMaxNT=4`), and no NT5–8 capacity is measured here.

Primary implementation evidence: `src/kernels/cpu/native_expert.cpp` (`iq512_supported`, `iq256_supported`, `native_gu_mt_min`, `native_gu_dispatch`, `native_down_dispatch`, `native_down_rows`); `src/kernels/cpu/pool.cpp` (`q2_rows_any` and `native_down_rows` branches); `src/kernels/cpu/expert_layout.cpp` (`q2_rows_any`); `sycl/tools/native-service-calibration/native_service_calibration.cpp` (`run_direct`, `run_pool`, route output). This conclusion is specific to the frozen source and the stated default settings.

## Existing harness admission and correctness gates

`native_service_calibration.cpp` admits GU `{18,21,22,23}`, Down `{20,42}`, NT `1..4`, tasks `0|6`, batch `1|6`; all six pairings in the active set pass the argument-type gate. It loads a 48-layer/512-expert layout, opens `NativeRolePlan` on the primary index, reads exactly 384 unique `(layer,expert)` IDs split into two disjoint 192-ID cohorts, and rejects any selected case whose actual `NativeFmt` is not the requested GU/Down pair or H/FF geometry. For each selected expert it obtains all three role extents, checks extent existence, bounds/bytes, owns the exact selected packed blob, and reports path/tensor/offset/bytes. This gives actual source identity rather than a synthetic format-only payload. Cohort construction remains the data-side gap: the current controller points only to `native-service-calibration-cohort-22-20-nt1-v2/cohort.tsv` and its matching manifest.

Before timing, each process computes direct service, quantizer checks, and independent GGML references for every selected expert/token. It checks output guards; activation and intermediate quantizers; full row and output counts; direct/pool parity; placement and task/job counts. For NT1, GU must be bitwise equal to independent GGML for all four GU types. Down20 and its full chain must also be bitwise equal. Down42 is measured against the independent reference and emitted as a diagnostic, but the source does not impose the same NT1 bitwise assertion on Down42. For NT2–4, all six predeclared per-stage gates (maxabs and normalized RMS for GU, Down, and independent full chain) are mandatory before preparation and enforced per expert-token; no tolerance is learned from the measured result. Each output/reference compares 640 GU rows and 2560 Down/full-chain rows per token. Each successful cell must reconcile all `384*NT` reference-token entries and all rows and complete the declared round set. Controller2 additionally pins build/source/binary, cohort SHA, qualifiers, expected reference keys, row counts, worker placement, job order, and all timing rows. Use the archived v2 README and controller2 as the acceptance model.

The actual selected population is 512 experts per layer in the indexed layout. Even a pair appearing in only one layer therefore supplies enough unique IDs for the existing 384-source/two-cohort shape; a 384-ID selection leaves the other 128 layer experts out. A pair seen across multiple layers has a larger candidate population, but choosing 384 IDs does not make a layer-balanced or model-frequency-weighted sample unless the manifest explicitly does that. Preserve each exact `(layer, expert)` identity and prove the manifest contains 192 disjoint unique IDs per cohort with pair/geometry matching. If the current census/layout identity differs at run time, stop at admission and regenerate the manifest from that captured pack; do not substitute repeated IDs, another pair, or synthetic weights.

## Smallest bounded actual-data extension

1. Keep the existing 22/20 reports immutable and reuse their qualified source/binary/gate policy as the reference implementation template. For each missing pair, construct one exact pair-homogeneous cohort manifest from `NativeRolePlan`/the current index, with 192 unique actual experts per disjoint cohort (384 total). Store source, pack/index identity, format layout, cohort TSV/manifest hashes, layer/expert IDs, and pair counts. Use deterministic, recorded sampling and do not read payloads to plan the cohort; payload ownership and full validation occur only in an authorized later calibration run.
2. Add controller admission for the six exact pairs, preserving the existing NT=1..4 cell geometry, NT-specific predeclared error gates, process ownership and timing checks. Qualify each new pair and NT with a correctness-only pass before its measurements. Reject an unqualified pair/NT rather than borrowing the 22/20 gate or capacity result. Do not expand the kernel harness's NT bound as part of this seven-pair extension.
3. For each missing pair, measure NT1–4 under both existing active-set conditions: the eight-ID intended-hot subset and all 192 cohort IDs. Use the already-defined three fresh-process repeats per cell, serially (current protocol: two disjoint cohorts, five arms, warmups and 25 measurement rounds per cohort). That yields 24 timing processes per pair (4 NT × 2 modes × 3 processes), 144 for the six new pairs, plus pair-specific correctness-only qualifiers. Record every sample, error/reference result, source identity and cohort hash. This is bounded to the current 384-source format and does not claim a full-layer or full-model population.
4. Report each pair independently. Within a fixed pair, compare NT at fixed active-set mode; compare intended-hot with streaming at fixed pair and NT. Between-pair differences are descriptive only: formats occupy different current layers and may have different cohort composition, so a pair comparison does not isolate format cost from layer/weights. Neither the hot-vs-streaming contrast nor the existing fixture establishes cache residency or DRAM traffic. The pair-specific results also do not establish route frequency, end-to-end token throughput, or a CPU/GPU split.

## Resource scope and limits

The fixture measures CPU kernel service over three packed roles (GU, UP, Down) for 384 selected actual expert blobs, with synthetic activation inputs. `hot-eight` selects eight IDs from each 192-ID cohort; streaming serves all 192. Those are intended active-set sizes, not cache-state measurements. The existing README reports 5.0 worker threads plus host, pool job partitioning, and separate GU, FF quantization, Down, direct-complete and pool-complete times. Preserve those exactly for the pair matrix. It is not a GPU/CPU integrated run, does not measure host copies elsewhere in the model, and does not infer a whole-token budget. Pair-specific blob bytes and actual selected payload identities should be reported from each run's source extents/owned-byte metadata; do not infer them from fixture count alone.
