## Finding

The latest valid-marker diagnostic reports 22,255.597 ms `PLE gather wall` and 5,942.902 ms `PLE host wait` for its fresh 32,768-position request. These are different, overlapping scopes. Gather wall covers CPU n-gram row generation, request construction/submission/collection and associated reader work over all chunks, including time overlapped with compute. Host wait is the foreground time blocked waiting for a prefetched gather at the PLE consumption point. Neither is SSD service time, active device time, or physical flash transfer time. The phase ledger independently reports a 5,942.785 ms PLE-read-wait interval; the phase timer's validity does not narrow its scope. See R212 for the receipt status and phase-timer caveats.

The frozen source has the machinery to measure reader API work (`ReaderStats`, including row requests, row-cache hits, same-ticket page deduplication, direct read requests and bytes, collect wait, submission time, read latency samples, and keepalive reads). `generate.cpp` prints `PleTable::io_report()` under `--stats`. The R212 summary does not contain that report or per-reader counters for the fresh request. Therefore the current evidence gives a large PLE exposure, but does not establish how many bytes the reader submitted, how long read requests took, whether SSD service was saturated, or what storage capacity is needed. No current SSD model, firmware, filesystem/device mapping, or matched-device capacity receipt is established by this diagnostic.

## Reconciled workload and capacity envelope

On the pinned route, the default IQ4_NL PLE table has 320,001,536 rows of 90 bytes: 28,800,138,240 bytes (26.82 GiB). A token asks for 16 rows (1,440 nominal row bytes). At 262,144 positions that is 4,194,304 requested rows and 377,487,360 nominal bytes (360 MiB) before row-cache hits and page deduplication. At 32,768 positions the corresponding nominal row payload is 47,185,920 bytes (45 MiB). These are logical requested-row payloads, not the direct-read byte count and not hardware traffic. A 1,048,576-row cache holds 94,371,840 bytes (90 MiB) of row data, plus keys and metadata.

The current direct-file path aligns I/O to 4,096-byte pages. Since 90-byte rows are unaligned, adjacent rows are sorted and grouped by page for each gather ticket; one row may straddle a page. `DirectFile` submits aligned buffers and batches through an in-flight slab. The default `--ple-inflight` value is 256 (2 MiB at two 4 KiB pages per slot); the reader uses a background worker and defaults to up to 64 I/O threads on POSIX, with `STRATA_IO_THREADS` allowing 1–64. Those are configured limits, not evidence that 64 threads or depth 256 were achieved, nor that the SSD benefited. Windows uses the buffered-I/O bypass/overlapped path and has different worker defaults. Keepalive is enabled by `generate` by default: one page can be read while idle, separately counted from ordinary `reads` and `bytes`, and can appear in whole-device counters. Disable it for a clean capacity run or record its activity separately.

The `--ple-io mmap` / RAM paths are different capacity controls. They use mapped/file-cache access or resident table memory rather than the same direct-read path; the whole table is about 26.82 GiB. A result from those modes cannot stand in for SSD capacity of the default direct path. Likewise, the historical B70/NVMe report in `prefill-code-audit-addendum.txt` is a different machine, model/quantization and workload. Its staged readers / O_DIRECT implementation was already audited; it supplies no B570 direct-reader throughput measurement.

## Why O_DIRECT and timing counters need qualification

The POSIX implementation opens the PLE extent with `O_DIRECT`; its aligned requests are intended to avoid the OS page cache. The Linux `open(2)` documentation says O_DIRECT minimizes cache effects and has filesystem/kernel-dependent alignment rules; it does not promise a physical NAND transaction. A device/controller cache can satisfy reads, and a virtual, network, or layered filesystem changes what the flag means. Validate direct-I/O support and alignment on the mounted filesystem before interpreting a run. [Linux open(2)](https://man7.org/linux/man-pages/man2/open.2.html)

Reader `bytes` means bytes completed through the reader's I/O path. It is the best direct per-request numerator in this source but does not prove flash-media bytes. Linux `/proc/diskstats` and `/sys/block/<device>/stat` expose block-layer counters; requests can be merged and counters are for the selected block device/layer, so use deltas on the actual backing device and label them as block-layer traffic, not NAND writes/reads. Whole-device deltas also include other processes and background work. [Linux kernel I/O statistics](https://docs.kernel.org/next/admin-guide/iostats.html)

O_DIRECT alone does not establish that an SSD was uncached at every layer. Do not drop system caches or claim a physically cold SSD. Instead label trials as process-cold / row-cache-cold, repeat / likely-warm, and report reader and device-counter deltas. Fio is useful for independent capacity bounds only when its achieved queue depth and direct settings are verified; its documentation warns that synchronous engines do not honor iodepth as async depth and that even async engines may fail to achieve the requested depth. A generic fio randread is not a substitute for the 90-byte row-to-4KiB page grouping and production offset distribution. [fio I/O depth documentation](https://fio.readthedocs.io/en/master/fio_doc.html)

## Minimal read-only SSD capacity control

First record the read-only environment needed to interpret a future run: PLE file/table extent and hash, filesystem and mount type, backing block device(s) including device-mapper/RAID layers if present, logical sector and direct-I/O alignment, SSD model/firmware, and available memory. These facts are not present in the R212 timing summary. Do not infer or query them from that closed receipt.

Use an unchanged, numerically checked diagnostic request with the frozen binary and same input/row sequence. Capture the `--stats` `ple io` line immediately around just that request, with `STRATA_SSD_KEEPALIVE=0`; retain `requests`, `cache_hits`, `dedup_rows`, `reads`, `bytes`, `wait_us`, `submit_us`, `read_us_sum` and read-latency percentiles, plus the PLE host/gather and request wall values. Ensure one request per process (or explicitly reset/record row-cache state) so process cache state is clear. Record row-cache size and capacity. For matched OS counters, snapshot block-layer stats for the identified backing device immediately before and after the request, with an idle/background-I/O note; report deltas and device identity. This is read-only and needs no cache dropping or root intervention if those counters are readable. If system-wide activity is nontrivial, mark the delta inconclusive rather than subtracting estimated background traffic.

The smallest useful comparison is one process-cold, row-cache-cold pass and one repeat pass with the same request and table. Keep table, route, reader thread/depth, filesystem, power state, and device fixed. A third bounded reader-only replay is useful only if it reuses the exact captured PLE row IDs / grouped offsets and 4 KiB alignment against the same read-only PLE extent, while suppressing model/GPU work; it separates CPU hash/compute overlap from reader service. Compare no more than one tuning dimension at a time (e.g. threads 1 vs 16 vs default 64, or in-flight depth 16 vs 256). Record achieved concurrency, not only requested settings. Preserve correctness and the original aggregate run status.

Report four different rates separately: logical row payload (`n × 16 × 90`), reader submitted bytes (`ReaderStats.bytes`), backing block-layer read-byte delta, and exposed foreground wait / request wall. The first three should reconcile approximately only after accounting for cache hits, same-ticket page dedup, page straddles, keepalive, and unrelated device traffic. The quotient `360 MiB / 22.256 s` must not be presented as SSD bandwidth: gather wall includes software and overlap. The numerator may exceed actual direct reads or be smaller than page traffic. A capacity conclusion requires a repeatable matched path and unambiguously identified target device; one current phase timer is not sufficient.
