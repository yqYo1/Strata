## What standard `sycl::exp` promises

The Khronos SYCL Reference states that SYCL's namespace math functions have the same precision guarantees as OpenCL 1.2 math built-ins on host and device. OpenCL 1.2 §7.4, Table 7.1 gives `exp` a single-precision maximum error of ≤3 ULP, measured against the infinitely precise result. This is a bound for the standard function, not correct rounding, bitwise equality to host `std::exp`, or a promise of equivalence to Intel's separate `ha` entry point. `sycl::native::exp` is explicitly implementation-defined in precision and range, so it is not a suitable substitute for the current high-accuracy call.

The installed open-source builtin header `sycl/detail/builtins/math_functions.inc` registers ordinary `exp` through the standard builtin path; the `BUILTIN_GENF_NATIVE_OPT(ONE_ARG, exp)` macro selects its native builtin only under `use_fast_math_v<T>`. The selected primary CMake source flags currently disable fast math for `native_q2.cpp`; explicit `sycl::native::exp` would bypass that protection and would be a semantic/performance policy change. `sycl::exp` is therefore the standard API fallback when the Intel high-accuracy extension is unavailable, but its spec does not establish that Q2's downstream activation codes remain identical.

The cited OpenCL 1.2 guarantee applies to the standard built-in contract. Primary's per-source `-fno-fast-math` is useful evidence that this translation unit does not request fast math; still record the actual compile flags in Main's build evidence and inspect the final effective command rather than infer all compiler options from this research.

## Compatibility detection recommendation

Prefer capability detection at configure time, based on compiling a small expression against the *selected* SYCL compiler and headers:

1. Include `<sycl/ext/intel/math.hpp>` and compile a probe that forms `sycl::ext::intel::math::ha::exp(-1.0f)` in a device-callable context with the same SYCL options as `native_q2.cpp`.
2. If it compiles, define one target-local feature macro such as `STRATA_SYCL_HAS_INTEL_HA_EXP`; use the existing high-accuracy call.
3. If it does not, compile the standard `sycl::exp(-g)` fallback. Keep `fdiv_rn`, the `1.f + ...` FP32 expression, multiplication order, `-fno-fast-math`, and `-ffp-contract=off` unchanged. Record in build provenance that the standard exp path was selected and correctness qualified separately.

A source-specific CMake `try_compile`/feature check can make this decision explicit. It must use `-fsycl` (and the selected compiler/include configuration) and test the expression itself. A plain `__has_include` only sees the header, which exists in both installs. A `__SYCL_COMPILER_VERSION` threshold is also weaker than checking the API actually present in the header; it risks treating derivative/newer toolchains as the same API surface. If the project chooses a universal standard `sycl::exp` call instead, that removes the vendor extension dependency but changes the implementation on the oneAPI build too and therefore still needs the same correctness comparison. Do not shadow the missing function name or hand-declare `__imf_expf_ha` against an unrelated libdevice ABI.

## Precision and validation boundary

The relevant value is not merely a standalone exp result. A small difference in exp can change the rounded FP32 SwiGLU intermediate. That intermediate feeds a max-derived per-32-value quantization scale, each `round(value * inverse)` code, the code-sum correction, and then the Down projection. Thus a close activation/output tolerance alone can miss a Q2 activation-code change. The change is confined to `native_q2_expert_cpu_order`; generic `native_q2_0_esimd`, prefill grouped MMQ/fused routes, and other formats are separate.

Existing source/test coverage:

- `tests/sycl/native_single_dispatch.cpp:75-105` checks exact Q2 CPU-order activation scales, activation byte codes (including ties and zeros) and stored sums for standalone input values.
- `tests/sycl/native_single_dispatch.cpp:108-204,261-273` exercises native Q2 CPU-order GPU hits with changing activation/layer/route input through `gpu_hits(q2, pool, true)`, but the integrated CPU/GPU output assertion at `:187-204` allows a relative/absolute tolerance of `1e-4`. It is not an exact comparison of the SwiGLU-produced Q2 activation codes/scales against the prior toolchain. The exact standalone quantizer test does not create inputs by running SwiGLU.
- `src/core/expert_source.cpp:2366-2378` restricts the CPU-order hit path to Q2_0/Q2_0, 2560×640, AVX2 CPU behavior, then calls `native_q2_quantize_cpu_order` and `native_q2_expert_cpu_order`; this is a concrete downstream path the test covers.

After the compile is unblocked, Main should first keep source options unchanged and compare both exp choices on a fixed batch of GU logits/up values, including finite extremes and values around quantizer thresholds. Record exp ULP/error against a higher-precision host reference as descriptive evidence, but decide compatibility on the actual FP32 pipeline: compare SwiGLU intermediate bits where practical, every Q2 block's FP32 scale, 32 activation codes and stored sum exactly, and final Down outputs. Add adversarial inputs around code-boundary changes in addition to the existing tie/zero quantizer fixture. Then run `sycl_native_single_dispatch_test` on B570 with `gpu_hits(q2,pool,true)` checking its existing scope and preferably exact intermediate code parity, followed by fixed-history logits/state comparison through the native Q2 hit path. Keep an old-SDK result or output fingerprint as the paired control; do not compare two different generated histories. Report any output/code divergence and do not promote a speed result as a precision pass. No such verification was run in this round.
