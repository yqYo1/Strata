## Finding

The next bottleneck is not established. This primary HEAD has no fresh, clean B570 model throughput baseline in the reviewed evidence. The 667–694 token/s figures are from the reference Xe-derived tree at `28a7b9ae7ca5eba28eecd65f6453a7479c04fce8`, not primary. R448 and the 2026-10-14 project README also explicitly separate these from primary results. An earlier decode diagnostic (R314, summarized in R401) averaged 124.09 ms per one-token window, but it carried validation/observer overhead and nested wall timers; it is not an eligible rate sample. Therefore neither “PCIe bound”, “CPU bound”, nor “GPU bound” follows from current numbers.

The strongest next action is one compact, bounded attribution pass on the exact primary source and workload, followed by clean timing without instrumentation. Preserve prefill and decode as separate objectives: strict 64K-or-larger prompt prefill toward 1,000 token/s, and a separate long-context no-MTP/explicitly fixed-MTP decode workload toward 70 token/s. For decode, the target allows 14.29 ms per emitted token; at the previously supplied approximate 6 GB/s host-link rate, 85.7 MB/token is only a theoretical all-budget transfer ceiling. Real available transfer time is less, and this equation does not show that decode currently copies that volume.

## What current instrumentation can and cannot establish

- `src/program/generate.cpp:5871-5880,6003-6016` (`STRATA_DECODE_TIMING`) separates request verify wall, commit/emit and draft; accumulates GPU-reach wait, per-layer host, plan, activation quantization, job setup, CPU run, and per-layer-window miss/entry/cache-hit/PCIe counts. It can name a phase for follow-up. The values are nested/overlapping: GPU-reach wait can cover device work, per-layer host includes CPU work, and the report has no route-format/source join, bytes/token, exclusive CPU active/wait split, or exclusive device-kernel timeline. The optional GPU stage report is not a complete host/device critical-path timeline. Do not add the displayed terms as if disjoint.
- `src/core/expert_source.cpp:1869-1913,2024-2041,2042-2090` forms routed windows, chooses VRAM/PCIe/CPU ownership, quantizes CPU inputs, builds deduplicated expert jobs and enters the pool. It already has timestamps for `ms_plan`, `ms_actq`, `ms_jobs` and `ms_run` elsewhere in the dispatch; aggregate counters include entries/misses/hits/PCIe. These do not identify each CPU job's actual GU/Down format service cost or physical memory traffic.
- `src/kernels/cpu/native_expert.cpp:101-135,138-162` selects IQ GU and Down routes separately. For IQ3_S, GU may reach AVX-512 or AVX2 multi-token paths when `nt >= STRATA_IQ_MT_MIN` (default 2), the opt-in `STRATA_IQ_SINGLE_EXACT` AVX2 route for eligible `nt==1` on a non-AVX512 CPU, or ggml-cpu fallback. Down has its own format-specific path and fallback. A grouped-kernel NT>1 result cannot qualify no-MTP NT=1 decode.
- `src/prefill/prefill.cpp:1224-1260` (`STRATA_PREFILL_TIMING`) folds ordered compute-stream event gaps into named phases, including wait-copy, host-grouping, GU GEMM and Down GEMM. It is useful to locate a phase, but a gap assigned to a phase may include waiting for host grouping or a copy; it is not kernel-only active time. The streamed issuer path at `:1488-1492,1555-1567,1573-1593,1596-1644` records streamed/DMA counts and host elapsed around staging wait plus asynchronous copy submission. In the threaded arm `iss_ms` covers host-side issuer work (`:1606-1640`); it does not measure DMA-completion time, exposed transfer time or copy-engine utilization. The existing ring and stager also already overlap host preparation and copy submission with compute.
- `src/kernels/cpu/pool.cpp:493-503` is a completion wait and stall detector. Aggregate pool run/wait duration does not yield exclusive per-worker service or distinguish memory stall from arithmetic. The opt-in `STRATA_POOL_TRACE` at `src/core/expert_source.cpp:1898-1901` prints event progress and perturbs timing; it is not an appropriate speed run.

For the attribution run, extend or consume bounded counters that join, per request and layer: actual routed unique experts and row count; GU and Down GGUF types, NT, CPU/VRAM/PCIe owner, cache state and logical blob bytes; CPU worker active/claim/wait time; host source/read/prefetch time; host-to-device bytes and copy submit/completion event intervals; device event time for QSA/indexer, attention, routed expert kernels and output head; and blocking host waits. Keep only aggregate histograms, not full route traces. Build an interval timeline and compute the union/overlap of CPU, GPU, copy and host wait intervals. Then use a separate diagnostics-off official-client run for speed. A per-phase sum, host submit duration, logical packed bytes or nominal bandwidth is not a limiting-path proof.

## Priority port candidates (all conditional; none adopted)

1. **Owned contiguous layer-span upload as a narrow transfer primitive.** Donor: Xe-derived reference tree, Z HEAD `28a7b9ae7ca5eba28eecd65f6453a7479c04fce8`, selected Niko functionality; R448 names `STRATA_PREFILL_LAYER_BULK_COPY=1`. This is a discrete candidate distinct from moving the whole prefill schedule. Its gate is an exactly owned, contiguous Host-USM span for all 512 experts in one layer, validated owner/stride/byte extent; prior device users drained; one checked synchronous copy; source remains alive through close; cache residency is published only after success; unsupported mapped/shared/split/transient sources fall back before mutation, and a failed copy fails closed. The reference's compact qualification reports CPU/ASan/UBSan cases, small real-device tests across 512 experts and seven widths, and matching fixed-history FP32 logits at two positions. It also records 48 layer copies and 50,292,326,400 logical copied bytes for the tested GEN. These facts qualify limited donor behavior only: not primary, not whole-model, not 256K/RESTORE and not a speedup. R448 says the planned quiet three-run speed comparison was still pending. Primary uses different `ExpertSource` and cache lease/lifetime contracts; adapt only after source inspection. Smallest port would add one opt-in `ExpertSource` capability that returns a validated layer span or declines, then route that exact case through existing copy/cache ownership while preserving the current per-expert fallback. First measure host issue gaps, completed transfer intervals, actual transferred bytes and source type; if copy submission itself is not exposed on the critical path, do not port it.

2. **Per-layer expert reuse/admission (layer-major scheduling), only when prompt misses dominate.** Donor: reference Z's `include/strata/prefill/layer_major.hpp` and `src/prefill/prefill.cpp`, same HEAD as above. This candidate avoids re-fetching experts across prompt chunks by retaining an admitted layer's working set. It is not the same as bulk-copying one layer span and it replaces important primary scheduling behavior if done wholesale. Primary `src/prefill/prefill.cpp:94-112,1488-1492` currently uses an 8-slot small-chunk path and a streamed ring (default 384 slots when pinned share is high, else 96; stream-all starts at 1024 tokens), with source pinning and host stager policy; ring entries are reused only after `used` events, while current-layer GPU execution overlaps subsequent host-issued copies. The reference layer-major route uses private all-expert cache admission and does not retain this ordinary ring behavior for misses. Prior old PR#6 reports cited by R448 gave 3-pair 32K medians 453.2935 versus 645.848 token/s and matching outputs, but that was old source/recipe/hardware; it does not qualify current Z or primary. R448 reports only up-to-32768 fresh GEN/reference evidence and excludes MTP, helper/split, pipeline, vision, borrowed workspace, adaptive swap, SAVE/RESTORE, batch, VRAM commands and callback/checkpoint states. The smallest safe exploration is a separately gated *admitted resident prefix/cache slice* for one supported chunk/configuration, with the existing ring as miss/fallback route, explicit fresh-free VRAM reserve and source/cache leases. Measure per-layer hit/miss reuse, bytes avoided, actual capacity and event waits first. Do not port whole layer-major scheduling unless full primary state/lifetime and matched B570 results support it. Its prefill results have no bearing on decode.

3. **CPU IQ3_S GU paired-row kernel; keep Down separate.** Donor: the diagnostic CPU branch source identified by R441 and retained in reference Z; the current primary `src/kernels/cpu/native_expert.cpp:101-135` has separate GU dispatch but does not contain that paired-GU dispatch. This is a narrow potential decode component, unlike prefill's many-row SYCL IQ path. Prior R436/R441 evidence cited by R448: synthetic IQ3_S GU NT=1 was 3.76% faster, while NT=8 was 2.31% slower; parity/geometry fixture exists. These are isolated synthetic numbers, not model-level B570 results. The candidate reduces a repeated activation traversal (logical Q8_K extent cited by R401: 1,868,800 B across 640 rows/expert for paired work); that is not a measured DRAM reduction. On the 5600X decode path, first establish the actual CPU IQ3_S GU NT=1 denominator, same-layer Down type/service, and CPU worker critical-path share. Only if eligible GU work is a material exposed bottleneck, adapt the exact NT=1 dispatch and retain existing fallback. Check fixed-history logits/state and AVX2 dispatch, then interleave at least three clean decode comparisons; do not adopt an NT8 prefill/verify gain as decode qualification. No IQ3_S Down candidate is presently supported by the cited evidence, so leave its current format-specific path intact until separate Down service evidence identifies a concrete issue.

A further decode pool task-grain screen is lower priority than the attribution pass. R401 proposes testing one task-grain axis only if CPU pool completion dominates; current primary source already uses split GU/Down jobs (`src/kernels/cpu/pool.cpp:527-568,663-739`) and the cited R314 phase diagnostic is not clean throughput evidence. Avoid changing worker count, task grain, paired GU and cache policy together.

## Minimal decision protocol for Main

1. Confirm the safe current binary/source and run the clean primary control separately from an instrumented control. Use Niko's unmodified official `bench.sh` and client per project policy where supported, pin the source/binary/model/tokenizer and all settings. For prefill, report actual input tokens (at least 65,536 for the stated 64K goal), context/KV mode, chunk, cache, pin share, source layout, actual streamed and resident bytes, and at least three individual samples. For decode, use a fixed long-history workload, no MTP for the single-token claim (or explicitly report a separate MTP arm), fixed generated-token count, and individual samples. A 24-token decode row is not sustained decode. Keep validation/profiling disabled for the speed samples.
2. In a separate bounded diagnostic request, capture the joined counters above and construct the overlap timeline. Do not use diagnostic throughput as the clean rate. Report instrumentation overhead by comparing its wall time to the clean control, and retain a compact aggregate receipt only.
3. Select one candidate only if its resource is on the exposed critical path. For transfer, require event-completed payload/time and bytes/token; for CPU, actual type/NT/worker time and route denominator; for GPU, device events plus blocking host wait; for reuse, resident/miss/copy counts and actual admission. Re-run fixed-history correctness/state and at least three interleaved clean arm samples. Keep prompt and decode verdicts separate; reject any candidate that trades a decode regression for prefill gain when pursuing both targets.
4. Record candidate SHA/origin, exact source dispatch and shape, each sample, error/fault/close result, and component decision. Primary full-256K, RESTORE and error-path qualification are separate from a short small-device proof. Keep the existing ring, pinned-share selection, staging-event lifetime, cache publication and fallback semantics unless the exact replacement is separately proven.
