The report records host/service and setup tests, but not native model/HTTP operation, install/update success, or full C++ support. These migrated files therefore close only their stated source/mock/host scopes.

Explicit remaining main feature dependencies that block promotion of primary as fork default are recorded in `bench/results/2026-10-14-niko-main-service-port/README.ja.md` lines 32–46 and 106–108:

- **Parallel requests:** Python feature is present; native C++ `BGEN/BGENI/BSTOP/BYIELD`, slot state, partial prefill, cancellation and image-input semantics are not reconciled.
- **Dynamic VRAM:** Python API/config/UI are present; native segment/lease/resize, safe retirement of in-use buffers/events, failure capacity behavior and actual VRAM reporting remain.
- **C++ CLI/build surface:** candidates still include batch groups, trim-stage, remote cache/automatic placement and elastic cache. Do not carry CUDA VMM semantics over without a native design. This list was scoped by R447/R449 plus `cli-option-inventory.json`; exact option existence alone is not semantics.
- **Operational verification:** native install/update uses the existing binary; selected binary capability and hardware VRAM/image/model-format support are not established. A real native model HTTP/engine integration and bounded runtime/state validation remain.

The Python-side migration did not make fork default safe while these C++ behavior gaps remain. A clean normal merge is also not the right promotion mechanism: the current primary has archival main ancestry, and the earlier true-tree preview had the above conflicts. The next default update needs deliberate function-level reconciliation, validation of native counterparts, then a fork PR that changes `main` to the reviewed primary tree while retaining selected required Niko features.
