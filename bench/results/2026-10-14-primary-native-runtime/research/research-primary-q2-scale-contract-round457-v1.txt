## Finding

The failed scale comparison is explained by an operation mismatch. The primary CPU Q8 activation quantizer computes `amax / 127.f` (one floating-point division); the earlier GPU code computed `amax * (1.f / 127.f)` (a rounded reciprocal followed by a rounded multiply). These are not generally bit-identical, even with fast math disabled. The exact-scale test failure reported after build v11 is consistent with this source difference; this audit did not independently rerun or reproduce it.

Main's current dirty fix, `sycl::ext::intel::math::fdiv_rn(maximum,127.f)`, matches the CPU's direct division under the normal round-to-nearest execution mode and the selected no-fast-math build. It is the right correction for the observed mismatch. The current source comment correctly attributes the old mismatch to multiplication by a rounded reciprocal. “Compiler-dependent” would be too broad unless the effective flags or generated instructions show reciprocal approximation; the concrete cause here is two separately rounded operations versus direct division. The current selected OpenSYCL build records `-O3 -ffp-contract=off -fsycl -fno-fast-math` for `native_q2.cpp` and reports `STRATA_SYCL_HAS_INTEL_HA_EXP=0`; those flags do not turn reciprocal-multiply into the same value as direct division.

This fixes scale parity only. Exact codes and sums, standard-exp versus HA-exp parity, expert output/model quality, and performance remain separate gates. The scale/code test that failed is reached before the test's later `gpu_hits(q2, pool, true)` call, so that run says nothing about SwiGLU or the CPU-order GPU expert body.

## Scale comment and residual numeric edge cases

The current comment in `src/kernels/sycl/native_q2.cpp:90-92` says multiplication by a rounded reciprocal can change scale by one bit even without fast math. That is accurate: `round(amax * round(1/127))` can differ from `round(amax/127)`. It should be read as an IEEE operation-sequence distinction, not evidence of an optimizer bug or a varying runtime compiler choice. The current explicit `fdiv_rn` also makes the selected SYCL rounding rule unambiguous.

The CPU/SYCL implementations have an implicit representability precondition that is not checked at this quantizer boundary:

- Values must be finite. If a chunk contains NaN/Inf, max/scale/inverse may become non-finite or zero in backend-specific ways; converting NaN/Inf to `int` is not a portable defined path. AVX2 conversion instructions have hardware results, but that does not define the scalar C++ or SYCL conversion behavior.
- Finite values must also avoid a positive subnormal scale whose reciprocal overflows to infinity. For example, sufficiently tiny nonzero finite `amax` can yield nonzero subnormal `s`, but `1.f/s` can overflow; then `x*inv` can be Inf/NaN before integer conversion. Thus “all values finite” alone is not a complete formal safety precondition. Ordinary model activations are expected to be far from this range, but this source audit contains no model activation range receipt.
- For normal in-domain inputs, `|x| <= amax` implies the mathematical ratio is at most 127; the clamp handles small rounding excursions. The code's intended safety claim `|t| <= 127` is approximate when `inv` is rounded, though the actual result remains close to that bound and safely within int32. The current code does not check finiteness or reciprocal representability.

A low-cost fixture can make the precondition explicit without changing production arithmetic: exact compare only finite inputs in the supported range; add a separate classification case for zero/subnormal/near-underflow and nonfinite inputs, expecting either a documented rejection or a deliberately specified behavior rather than accepting accidental casts. If production inputs should never leave the supported range, record that contract and add a debug-only finite/range assertion at a suitable boundary rather than silently broadening this opt-in route.
