Conclusion
I found no new correctness blocker in the serialized session/token-graph handoff changes within the requested scope. The implementation closes the R342 generate-path gap by gating both token-graph generation setup branches and by rejecting direct token-graph capture/run when host/device concurrent handoff is unqualified. host_handoff_concurrent() is unconditionally false in the inspected build. The ordinary per-layer session_loop path waits for pre completion before reading h_seq or host-USM payload, then performs CPU pool work, queues the parts copy and post graph, and only then submits the next pre graph. The event is recorded after the pre graph and synchronized before host reads. This sequencing prevents concurrent access to the mutable seq word and prevents the GPU from rewriting the payload while the CPU consumes it.

Coverage and ordering
- generate.cpp only tries the hit-enabled TokenGraph and regular TokenGraph setup when host_handoff_concurrent(main_cs) is true. Its per-token dispatch selects session_run_token only when the graph was captured; otherwise it falls through to session_loop. The token graph capture/run entry points independently check the same gate, so direct callers cannot bypass the generate condition.
- In session_loop, a stream drain precedes stage_token; no asynchronous command is issued before local scratch setup and validation. The initial parts transfer, pre[0], and its completion event are submitted in order. Each iteration waits for that event before reading the sequence word and payload. It then invokes the hit launch callback and CPU pool while pre has completed; queues miss-parts copy, hit-combine callback, post[l], optional residual copy, and pre[l+1] in stream order. The next iteration waits for the newly recorded pre event. Final stream synchronization completes the final layer.
- The runtime wrapper implements event synchronization with event.wait_and_throw() followed by async-error checking. This is a host-blocking completion point, unlike the old live volatile poll.
- Host payload arrays are read only after pre completion and remain untouched by the next pre until CPU pool use returns. The shared per-session staging is not reused concurrently: token-loop completion synchronizes the stream, and the next invocation begins with another stream drain.
- The resident hit callback's Launch work is submitted after pre completion and reads the stable layer IDs; CPU pool work runs before the next pre can overwrite them. Combine is queued after the parts copy and before post[l].
- Remaining session_replay* helpers launch graph work without a CPU pool callback or host-side doorbell polling; they do not form an alternate CPU handoff path.

Failure/lifetime observation
session_loop's local scratch cleanup is ordered after its Drain guard by C++ reverse destruction order, so asynchronous users are drained before local pinned memory/event cleanup. Error returns after submission also drain the stream. The drain guard calls std::terminate() if its fallback synchronization fails; this is fail-closed behavior to avoid returning while a local pinned source might still be in use. It can turn an asynchronous GPU failure into process termination, but I found no safe local-free alternative in this code path without a runtime guarantee that failed sync implies no outstanding memory access. Treat as an explicit failure policy, not a handoff race.
