## Admission decision

**Do not admit a normal official v0.1.42 B570 generation run with CPU expert service under the current capability receipt.** The ordinary SYCL route concurrently polls and writes `seq` / `flag` words in host USM from device and host code. The default device operations are cache-hinted ordinary loads/stores plus system-scope fences; the host side uses `volatile` accesses and host fences. It does not use one shared host/device atomic object. The current receipt says host USM is accessible but `ATOMIC_HOST_USM=0`, and the Level Zero host allocation capabilities do not report concurrent access. System-scope atomic and fence capabilities are present, but they do not grant concurrent atomic access to these host allocations or turn non-atomic accesses into atomics.

The receipt is `/home/yayoi/.local/state/strata-sycl/post-reboot-tuning-20261007/xe-host-capabilities-root-v2/record.json` (compiler `icpx` 2026.1.1; selected B570 `0000:05:00.0`; `HOST_USM 1`, `ATOMIC_HOST_USM 0`, atomic orders through `seq_cst`, atomic scopes including `system`, fence orders through `seq_cst`, fence scopes including `system`, `ZE_HOST_CAPS 3`). The existing receipt is already enough to refuse the ordinary path for the queried device/runtime tuple. A later run must repeat the query only if the actual compiler/runtime, backend, selected device, or allocation route differs; a repeat is not a substitute for the missing concurrent-access capability. Receipt source: `xe-host-capabilities-v2` as recorded by `round344-xe-hwbench-and-production-bottleneck-measurement-selection.txt`.

## Source path and live accesses

- `sycl/src/core/layer.cpp:1363-1390` allocates separate host-USM `x_f`, `ids`, `weights`, `seq`, and `flag` regions with `sycl::malloc_host`; device pointers alias the host pointers. The sequence region is 64 bytes (sequence plus payload tags/checksums), the flag is 4 bytes. Reset is by host `volatile` stores.
- `sycl/include/strata/sycl_doorbell.hpp:26-27` declares a system-scope `atomic_ref` alias, but it is used only by compile-time atomic alternatives. The default at `:51-60,72-83` is an uncached annotated-pointer load/store bracketed by system-scope fences. The `STRATA_DOORBELL_ATOMIC_LOAD/STORE` alternatives at `:61-64,91-98` still would not repair the host half: ordinary session host code accesses the same words through `volatile` pointers, and the device capability receipt lacks `usm_atomic_host_allocations`.
- `sycl/src/kernels/cuda/elementwise.dp.cpp:372-395` rings `seq` with a system-scope fence and `sys_store`; `doorbell_wait_kernel` repeatedly polls `flag` and `seq` with `sys_load`, then fences. With the header's default, these control accesses are not atomic operations.
- The standard per-layer route in `sycl/src/core/session.cpp:954-993` polls host `h_seq` while the graph is still running and also calls `sycl_event_query`; after payload validation at `:1005-1010`, it runs CPU experts at `:1018-1019`, queues the miss-output copy and post graph at `:1035-1042`, and proceeds to the next layer. The event query is not a completed-event boundary when it reports work still active. `overlap=false` at `:1095-1100` synchronizes only after this poll, pool call, and post launch, so it does not serialize the control-word access.
- The token graph is selected by default when capture is enabled and the route is eligible (`sycl/src/program/generate.cpp:5808-5815`). Its capture inserts the device-side `doorbell_wait` inside the all-layer graph (`sycl/src/core/session.cpp:1219-1276`). `session_run_token` concurrently host-polls `h_seq`, runs the CPU pool, then stores `h_flag` after host fences (`:1335-1418`). The graph can therefore be spinning on the same flag while host writes it. `--no-token-graph` falls back to the per-layer `session_loop` and retains its concurrent poll. `--no-capture` calls `session_token`, which has no CPU pool hook; `generate.cpp:5235-5240` refuses `--no-capture` with the pool enabled. The explicitly allowed `--no-pool` GPU-only floor omits CPU expert work and is not a compatible ordinary generation route.

There is no startup gate in the official SYCL tree for `aspect::usm_atomic_host_allocations`, system atomic/fence scope capabilities, or Level Zero concurrent host-allocation access. A source search finds only the general `usm_host_allocations` compatibility query in `sycl/include/dpct/device.hpp:317`; the verifier header documents the known missing atomic-host aspect, but does not create a generation-wide capability gate.

## Existing serialized route and scope

`STRATA_VERIFY_STEPPED=1` is an existing verifier-only segmented route. `sycl/include/strata/core/verify.hpp:358-369` describes it; `sycl/src/core/verify.cpp:2034-2148` launches segments, drains the queue at each serve (`:2059-2066`), serves CPU experts after the drain, raises required flags before submitting the next segment, and does not use the ordinary mid-window host/device handoff at those boundaries. This is a possible route for verifier work when its other conditions are met, not a generation fallback. The ordinary verifier path still has concurrent polling (`:2167-2255`), and its all-resident `STRATA_VERIFY_NO_HOST` case is limited to an all-resident cache (`:2173-2178`). No compatible, sequential CPU-expert generation route is already wired: disabling token graphs, `overlap=false`, and sync-every-layer do not remove the earlier doorbell handoff.

## Required admission condition

For ordinary CPU-pool generation, refuse while any control location can be concurrently accessed by host and device without the selected allocation/device contract. A green overlap path would require the exact selected device and control allocation to support host-USM concurrent atomic modification; a suitably aligned single atomic object; matching system-scope device `sycl::atomic_ref` and host atomic operations on that object; and the required memory orders/scopes. If any requirement is absent or unknown, source must route generation through an explicit segmented/serialized handoff that waits for device completion before host reads payload, and raises host-produced control state before submitting the next device segment. There is no such fallback in this pristine generation path, so the present decision is **refuse normal B570 CPU-pool GPU runs pending a corrected/gated source route or a capability/runtime change that actually satisfies the contract**. A capability query alone cannot make the existing volatile protocol safe.

## Primary sources and limits

- Khronos, [SYCL 2020 specification, revision 12](https://registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html): `usm_host_allocations` permits device access; `usm_atomic_host_allocations` is the aspect for concurrent host/device atomic modification of host USM. System scope is defined subject to the allocation capabilities.
- Level Zero, [Core Programming Guide: memory access capabilities](https://oneapi-src.github.io/level-zero-spec/level-zero/latest/core/PROG.html#memory-access-capabilities): host allocation access flags distinguish ordinary read/write from concurrent and concurrent-atomic host/device access; concurrent access alone is not an ordering guarantee.
- Existing source/spec cross-check: R340 `round340-latest-xe-doorbell-memory-model-contract.txt`; capability provenance and current run gate: R344 `round344-xe-hwbench-and-production-bottleneck-measurement-selection.txt`.

This is an admission/source-contract result only. It neither tests actual handoff behavior nor attributes a historical device failure.
