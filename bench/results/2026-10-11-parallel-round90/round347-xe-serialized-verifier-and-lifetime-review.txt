Finding: asynchronous commit completion errors can make live session state look quiescent
Severity: correctness risk on GPU API failure paths; normal successful completion is ordered correctly.

`Verifier::commit()` launches `commit_exec_` before recording `commit_done_` (`src/core/verify.cpp:2339-2358`). If `event_record` fails, it returns false without marking a pending commit. `wait_commit()` only waits when `commit_pending_` is true (`1761-1772`), so it can report success while the already-launched graph may still be writing SessionState. The synchronous path has the analogous shape: a failed `stream_sync(cs_)` returns false after launch, without recording a state that forces later drains.

There is a second state-loss path in `wait_commit()`: it clears `commit_pending_` before calling `event_sync`; when that synchronization fails, a subsequent call skips the wait and can return success (`1761-1770`). These paths matter because generation invokes `wait_commit()` around cancellation, session snapshot/restore, and reuse boundaries. The caller currently receives an error on the first failure, but the verifier itself no longer guarantees that a later boundary call drains the graph.

Suggested repair: preserve a poisoned/incomplete state until a successful stream/event drain; on event-record failure, synchronize `cs_` immediately and report failure even if drained; if the drain also fails, prevent snapshot/restore/reuse (fail-stop if required by the backend contract). Do not clear pending state until the event wait succeeds. Apply the same invariant to the synchronous wait failure. `pl_commit_async()` has the same launch-then-event-record pattern at `2619-2622`, but is unreachable under the current capability gate described below.

No active-path GPU-to-host read-before-completion or callback/control-word host-host race found
`host_handoff_concurrent()` is a compile-time false (`include/strata/core/gpu.hpp:48`). `Verifier::init()` therefore selects segmented execution irrespective of `STRATA_VERIFY_SEGMENTED` (`src/core/verify.cpp:414`). In that path, `run()` waits for `cs_` before reading the sequence word and waits for `copy_` before inspecting DMA/error flags or advancing to another segment; the final path waits before reading output/profile state. The run-scope drain guard syncs both queues on early exits. The DMA completion host callback captures its flag/wanted value by value and atomically raises flag B; the caller synchronizes the copy queue before inspecting it (`verify.cpp` around `1437+` and the callback near `1739`). Plan publication uses flag A in the synchronous CPU-pool path. The kernel-side `wait_flag_ge`/`wait_flag_or` routines reject before enqueue, and `doorbell_visible()` returns false (`src/kernels/xe/verify_kernels.cpp:706-719,795-803`). Thus the old concurrent polling branches cannot execute under this gate. Resident graph execution does not use this host handoff.

Batch/pipeline refusal coverage
The constant false capability prevents concurrent mode even when the segmented environment option requests otherwise. Batch initialization/staging rejects segmented mode (`verify.cpp:1775+, 1928+`); the normal slot launch routes through staging. Pipeline capture rejects it (`2391+`); prestage and launch each directly check the same capability (`2443-2459`). The top-level `--pipeline-windows` setup also disables the option for unsupported configurations (`generate.cpp:2286-2298`), while downstream capture/launch paths fail closed if reached. Poll/finish/commit continuation methods do not all repeat the capability check, but no supported launch/capture route can establish their active/prepared state under the current invariant. This is not a present bypass; repeating the guard in continuations would be defense in depth. The unsafe pipelined commit event-record failure noted above is consequently dormant today.

Conclusion
The serialized segmented handoff closes the reviewed active-path host-read and callback races, and batch/pipeline launch paths fail closed under the current constant gate. The remaining actionable issue is the commit error-state invariant: a completion-record/wait failure after graph submission can lose the fact that device work may still be in flight, allowing a later `wait_commit()` to claim quiescence.
