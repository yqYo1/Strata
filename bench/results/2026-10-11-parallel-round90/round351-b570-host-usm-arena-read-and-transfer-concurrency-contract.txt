# Round 351 — B570 host-USM arena read / transfer concurrency contract

Date: 2026-10-11 (Asia/Tokyo). Read-only source and primary-specification review. No source edits, build, test, GPU/runtime query, process/service query, or Git action was performed. Source reviewed: corrected XeStrata worktree `/home/yayoi/ghq/github.com/MistVVK/XeStrata/.worktree/fix-xestrata-e32-host-handoff-20261011`. This is a usage-contract review, not fault attribution.

## Finding

There is one concrete unsupported overlap when the corrected source runs the explicit/converted host-USM expert arena with prefill CPU sharing enabled, the planner selects at least one CPU expert (`rows_cpu > 0`), and at least one other expert in that layer is GPU-streamed: the CPU expert pool reads selected experts from a layer's host-USM block while the GPU copy queue asynchronously reads other experts from that same block for H2D staging. The expert byte ranges are disjoint and both accesses are reads, so this is not a C++ data race. It still violates the selected B570's Level Zero allocation-level concurrency contract: `ZE_HOST_CAPS 3` has RW and ATOMIC, but lacks CONCURRENT; the guide makes concurrency capability whole-allocation and says the device must support concurrent access for host/device accesses to overlap. Disjoint ranges do not carve a large layer allocation into independently concurrent allocations. The capability record separately says host-USM atomic support is absent, but this read/read finding needs the missing CONCURRENT capability, not a claim that a non-atomic read requires CONCURRENT_ATOMIC.

This finding is conditional on the expert source actually being `PinnedArena` host USM and CPU sharing being active. It does not say that all ordinary malloc/mmap/registered host RAM is illegal for DMA, nor that this source path caused an observed GPU fault. The ordinary registered-mapping path is a different allocation/interoperability case and needs its own backend contract; the host-USM result below should not be generalized to it.

## Contract by allocation kind

SYCL 2020 rev. 12 distinguishes the three USM kinds. `aspect::usm_host_allocations` means the device can access `sycl::malloc_host` memory; the specification says concurrent access and atomic modification are supported only with `aspect::usm_atomic_host_allocations`. The latter says host and device may concurrently access and atomically modify host allocations. Host-USM memory stays in host memory and the spec tells applications to synchronize host execution and kernels. In contrast, shared USM has `aspect::usm_shared_allocations`, and its own section explicitly says a device without concurrent-access support requires host and device to take turns on the shared allocation. `aspect::usm_atomic_shared_allocations` is the stronger shared-atomic capability.

The selected L0 backend makes the allocation-wide distinction concrete. Its host-allocation capability definitions state that `CONCURRENT` permits device access concurrent with host access, at whole-allocation granularity; `CONCURRENT_ATOMIC` is the separate concurrent-atomic property. The same guide says concurrent access without `CONCURRENT` has undefined behavior. Therefore, for a B570 `malloc_host` layer block with host and device access in flight, two read-only spans do not become permitted merely because the spans differ. A host callback is still host execution; routing CPU work through `std::async` does not make it device access or create a memory-model exception.

The root-owned capability query (`.../xe-host-capabilities-root-v2/record.json`, completed PASS, selected device `0000:05:00.0`) records:

- `HOST_USM 1`, `ATOMIC_HOST_USM 0`; `ZE_HOST_CAPS 3` = RW|ATOMIC, with no CONCURRENT or CONCURRENT_ATOMIC bit.
- `SHARED_USM 1`, `ATOMIC_SHARED_USM 0`; `ZE_SHARED_SINGLE_CAPS 3` likewise has no CONCURRENT bit.
- `ZE_SHARED_SYSTEM_CAPS 15` includes RW|ATOMIC|CONCURRENT|CONCURRENT_ATOMIC for the queried shared-system class.
- System atomic order and scope (including system scope) and fence order/scope were reported available; those do not add a missing allocation concurrency flag.

The last line does not convert `malloc_host` into shared-system memory. SYCL's `usm_system_allocations` applies to using the system allocator for `usm::alloc::shared`; it does not change ordinary `malloc/new` into host USM, and it does not replace `sycl::malloc_host`'s capability contract. Similarly, these flags are not a blanket ruling about an imported mmap or OS-registered legacy host pointer; identify its allocation/import path and applicable extension contract first.

## Corrected-source path and active overlap

1. In `PinnedArena(bytes, bounds, pad, host_usm, ...)`, the `host_usm` arm allocates one `sycl::malloc_host` block per layer (`src/core/pinned.cpp:132-160`). In `ArenaExpertSource::open`, `STRATA_ARENA_HOST_USM=1` selects that arm; if import/registration setup fails on the non-host-USM arm, source has an explicit fallback that retries with `host_usm=true` (`src/core/expert_source.cpp:2385-2407`). Arena loading finishes before `arena_`/`base_` are published for inference. `ArenaExpertSource::pinned` classifies in-bounds expert blobs as pinned, and `blob` returns their layer-specific address (`src/core/expert_source.cpp:2543-2547`; see R305 for allocation bounds/lifetime detail).
2. For chunks where `stream_all` is false and CPU sharing is on, `cpu_maybe` is true when a native expert layout and source are available (`src/prefill/prefill.cpp:1774-1777`). The default `STRATA_PREFILL_CPU_SHARE` value is `auto` / `-1`, so `cpu_share_on()` returns true by default (`src/prefill/prefill.cpp:122-137`). `stream_all` requires `T >= STREAM_ALL_MIN` (2048), among other conditions (`:1294-1298`), so this is a live path for smaller eligible chunks.
3. The planner considers CPU candidates only when `m.src->pinned(l,e)` (`src/prefill/prefill.cpp:1815-1825`) and stores `m.src->blob(l,e)` pointers in the CPU jobs (`:1900-1909`). The async worker invokes the native pool over those blobs while the launching thread streams GPU-assigned experts (`:1919-1940`, plus the layer's GPU expert loop). No per-allocation serialization exists between those operations.
4. For a GPU-assigned, pinned expert, `stage_one` enqueues `gpu::copy_async(slot_ptr, b, bytes, copy)` directly from `m.src->blob(...)` (`src/prefill/prefill.cpp:2039-2047`). `gpu::copy_async` submits queue `memcpy` (`src/core/gpu.cpp:236-239`). For an ArenaExpertSource host-USM layer, `b` is an offset in the same one-layer `malloc_host` allocation read by the CPU jobs. With at least one CPU expert and one GPU-streamed expert in the layer, the two concurrent reads target different experts but share that allocation.
5. The post-copy source and `m.cpu_rows` are distinct host allocations. CPU results are joined before their host-to-device `copy_async` (`src/prefill/prefill.cpp:2256-2267`), so that result upload is not the same overlap. The input activations use `m.cpu_x` allocated separately by `alloc_host`; their device-to-host copy is enqueued before `stream_sync(m.cs)`, which completes before CPU routing/pool work (`:1778-1788` and `:1790` vicinity). These are separate lifetimes/allocations from the expert arena.

## HostVec and Stager checks

`HostVec<T>` allocates a separate host-USM block per table (or a `std::vector` fallback) and uses device kernels for pinned `from_device`/`to_device` (`src/prefill/prefill.cpp:83-106`). The corrected source comments state that the host rewrites a table only after the next layer's sync, when the kernel using it is done (`:78-82`). For the routed-ID path, `ids_host.from_device` is followed by `stream_sync(m.cs)` before the host reads IDs and writes the slot/source tables (`:1772-1800`); the later host table writes precede `to_device` submissions in the same queue (`:1873-1879`). Thus this audit found no live host/device overlap on those HostVec bytes. Pageable fallback uses explicit async copies rather than direct kernel access. `m.steps_host`, `m.tok_host`, and CPU outputs are likewise copied after host production; the audited active CPU/expert arena overlap is separate.

Stager's `buf[i]` entries are individually `alloc_host` allocations (or individually owned pageable vectors), not slices of the expert source arena (`:260-278`). A slot's `dma_done[b]` is synchronized before the worker overwrites it, and `issued_one` records H2D completion after enqueue (`:312-324` and `:354-357`). That protects each staging buffer against overwrite while its own DMA reads it. It does not protect the distinct direct-DMA path above, where the CPU pool reads an expert-source allocation during DMA of another expert.

## Narrow source/runtime gate

For this B570 qualification, the smallest conservative gate is to keep CPU prefill sharing off whenever the source's selected layer bytes are host USM and the device lacks whole-allocation host/device concurrent access. That gate should apply whether host USM was selected explicitly or reached through the existing conversion/fallback path. A source-level `is_host_usm`/allocation-kind query or retained `ArenaExpertSource` host-USM mode is needed: `pinned()` alone intentionally conflates DMA-capable registered mappings with host-USM allocations. If the code later wants to re-enable sharing, it needs an actual source-allocation/backend contract that grants host/device concurrent access; for read-only disjoint spans, CONCURRENT is the relevant capability, while concurrent atomic handshakes separately need their stronger atomic capability. If no source-specific capability contract exists, serialize source reads against direct DMA or use a source copy owned by another allocation before overlap.

Do not globally disable legacy registered-memory DMA based on this host-USM result. The ordinary `!host_usm` constructor is a mapped/registered arena (`src/core/pinned.cpp:135-144`); `make_kernel_readable` can later convert it to host USM only when required (`src/core/expert_source.cpp:2549-2565`). An ordinary mapping being pageable, registered, imported for copies, or device-readable are different facts. Establish its particular L0/UR extension contract and actual allocation classification before deciding whether concurrent host reads are supported.
