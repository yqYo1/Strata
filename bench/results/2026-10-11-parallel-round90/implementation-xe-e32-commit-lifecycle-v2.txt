Production change
The new host-only strata::core::CommitTransaction helper stores pending ownership, whether the event was successfully recorded for the current transaction, and the first fault. Verifier uses this real helper, rather than a separate test model.

- commit() first calls wait_commit() before modifying mapped h_commit_ arguments or starting another transaction. This waits any earlier writes and rejects an already-poisoned transaction.
- For the graph path, begin() marks pending before graph_launch. A rejected launch is recorded as a sticky failure and immediately calls checked completion handling. An unconfirmed local drain terminates before quietly abandoning ownership.
- In async mode, event_record success explicitly marks the current event usable. An event_record failure records the first error, immediately drains cs_ through wait_commit(), reports failure even if that drain succeeded, and terminates if local completion remains unconfirmed. An older event object cannot qualify this transaction because recorded state began false.
- In synchronous mode, wait_commit() uses a checked queue drain; pending clears only when that drain succeeds. Failure preserves pending, records the first fault and blocks reuse. Later wait_commit() retries the queue drain while continuing to return the sticky failure.
- wait_commit() uses event_sync only for an event successfully recorded for the current transaction. Failed event_sync retains pending and makes that event unusable, so a later call must use checked stream_sync. A later successful drain releases ownership but cannot report the failed session state as valid.
- wait_commit() also visits downstream stages even if the current stage failed, preserving the current stage's original error while draining/qualifying later stages independently. run() calls wait_commit() before its existing queue waits/staging, so no subsequent window silently reuses failed committed state.
- The one-token self-commit route submits no additional commit graph; its existing run-time completion remains the ownership boundary. It still waits/rejects an earlier commit before host bookkeeping.
- pl_commit_async() now directly rejects the universal concurrent-handoff gate before staging/submission. The dormant legacy pipeline transaction code is not redesigned because the capability gate remains false and capture/launch are already refused. Reenabling concurrent mode still requires the separate atomic/ownership redesign documented in v1.

Failure semantics
A fault remains sticky after checked completion, intentionally blocking commit, run and wait_commit from claiming reusable/valid session state. Device state may have advanced while host PLE bookkeeping did not; safe completion alone cannot establish a valid transaction. Caller must reconstruct the verifier/session or use its higher-level recovery path after an error. This differs from a retryable transient wait: repeated calls may drain outstanding work, but do not erase the original fault. This conservative state policy is deliberate.
No early destructor/free is introduced. Existing verifier destructor first checks compute and copy completion and terminates on an unconfirmed drain. Immediate rejected launch/event-record drains use the same conservative fail-stop rule; it is not a GPU driver recovery guarantee or historical fault attribution.
