## PLE row mapping and what an offline census can establish

The committed hash source is deterministic host code. `PLE_N_HEADS=16), `NGRAM_SIZE=3), and `HEADS_PER_NGRAM=8). For each token position, there are 8 bigram-head rows and 8 trigram-head rows. The token context for a row is `ctx[0]=current token`, then newest and older predecessors; predecessor storage is oldest-first, `prev=[t-2,t-1]`, and lookup order is `prev[1]` then `prev[0]`. A missing predecessor (`t<0`, including `TOKEN_NULL=-1`) or EOS predecessor (ID 248044) starts a cascading cut: that predecessor and all older context positions used for this token become EOS. The current token being EOS does not cut its own row; it becomes a predecessor that cuts the next token's row. Token ID 0 is ordinary data, not null.

Each mixed hash starts with the current-token product and XORs predecessor products using unsigned 64-bit wraparound. Each head row is `offset[h] + (mixed % vocab[h])`; every channel's vocabulary and offset are compile-time artifact constants. An independent offline implementation can exactly enumerate all 16 row IDs for each of the 32,768 batched positions, including the inserted ID and chunk carry, using only the token fixture and the constants. It needs neither a GPU nor PLE tensor bytes. It should explicitly mask each multiplication/XOR to 64 bits to match C++ unsigned overflow, and check every result is in `[0, 320001536)`.

Given those rows, the source geometry permits an exact *logical page-job model* for a cold row cache: for each valid row, `at = 192 + row * 90`; the first page is `floor(at/4096)*4096`; request length is 4096 or 8192 if the 90-byte span crosses the 4KiB boundary. Deduplicate by that first aligned page exactly as `PleReader::issue` does, extend a shared job to 8192 if any fan-out use straddles, then sort first-page offsets. This also determines page-boundary cases and requested-vs-logical-read bytes. A straddling read can overlap the following page's separately keyed job: the current implementation deduplicates by first page only, so an offline model must reproduce that rather than collapsing every overlapping byte range.

This model is not a measured cache/record census. In Direct mode, a fresh reader begins with an empty set-associative RowCache (default 1,048,576 rows, 8 ways per set), and the first `issue` scans the whole ticket before any completion can insert a row. Therefore first-chunk `cache_hits` should be zero absent an earlier table read; duplicate row requests inside that ticket become same-page `dedup_rows` (they are not hits from an in-ticket cache). Subsequent chunks can hit rows inserted on prior chunk completions. RowCache insertions happen as jobs complete; DirectFile can complete jobs out of submission order, and for any set with more than 8 candidate rows the replacement survivors depend on that order. A source-only simulation cannot know exact later-chunk hit counts or exact cache contents without the observed completion order. The 1M-row nominal capacity does not prove all selected rows survive: 8-way set conflicts matter.

The default `ReaderStats` gives cumulative requests, cache hits, same-ticket dedup rows, read count, returned bytes, collect wait/submit time and a bounded recent latency ring. It does not expose per-ticket page offsets, record IDs, per-chunk counters, job completion order, or ZFS data-block extents. An aggregate snapshot after a run cannot be apportioned exactly to the four prefill chunks if any additional token-path/keepalive reads are included. Any future attribution should capture per-ticket/per-chunk counters at the gather boundary and report the token-tail path separately; do not claim exact cache behavior from the offline model.

## Record eligibility boundary

The 4KiB page model above is source-computable. A 128KiB *record* model is conditional only: `PleReader` enforces 4096-byte direct-I/O alignment and does not know ZFS record size. A dataset `recordsize` property or the separate same-file storage-capacity control is not evidence that every block in this PLE GGUF is physically stored as a 128KiB dbuf. Exact record census requires separately verified geometry for the actual GGUF extent (including its header/tensor data offset and final short/tail record); no filesystem/device query or shard data read was performed in this audit. If 128KiB is independently confirmed for this exact file, a model can group the logical page jobs by `floor(file_offset/131072)`, but it remains a conditional model, not actual read service.

For each confirmed actual record, the offline row/page model can count requested distinct pages and straddler jobs within it. It can identify when the logical request set contains more than one page for a record. It cannot determine row-cache-pruned requests from later chunks, filesystem metadata/ARC activity, physical storage service, actual DIO returned bytes, or the counter behavior of this file without the corresponding ReaderStats plus separately verified filesystem/block evidence. Do not present R236's uniform-random estimate as the actual coding-review prompt result.

## Fresh versus RESTORE/history boundary

The first A request is fresh: `session_zero` sets `ple_prev=[-1,-1]` and clears PLE convolution history. Prefill's row gather captures these two values; for chunk start `c0), it seeds the rolling pair from the previous sequence or `tokens[c0-2:c0]`, then advances one token at a time. The two most recent prompt IDs carry across every 8,192 boundary. At the end of all 32,768 conditioning positions, `Prefill::run_impl` stores the final pair (IDs 32,766 and 32,767) in session state. Token position 32,768 then uses that pair.

The controller's later requests RESTORE a checkpoint at 32,832 consumed tokens and extend the same ID sequence to 32,833. The controller verifies `RESUME 32832`, `REUSED 32832`, and no `PP` events on those repetitions. Conversation restore restores PLE convolution history and reconstructs `ple_prev` from the last two saved IDs. Those are not a second read of the fresh 32,768-position prompt; any PLE reads during their continuation are decode/verify reads and must be reported separately. The only prompt census for this comparison is the fresh first A request.
