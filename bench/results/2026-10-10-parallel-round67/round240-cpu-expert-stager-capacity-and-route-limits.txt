R240 — production expert staging, dequantization, and capacity gap
Date: 2026-10-10
Scope: read-only source/evidence reconciliation; no implementation or runtime work.

Finding
The standard streamed MoE path in frozen SYCL source commit 495369cf4dc6e6da564095a1c26504dd3694e3f2 does not dequantize expert weights on the CPU. `Stager::work` (`sycl/src/prefill/prefill.cpp:358-535`) copies a packed expert blob to a reusable host ring: `memcpy`, `ExpertSource::copy_blob`, or the GGUF source's `read_into`. The launching thread waits for readiness and submits the packed blob H2D at `:4728-4765`; pinned experts bypass the host copy and DMA directly from the pinned arena. After the copy event, `compute` calls device `iq_dequant_gu_f16` and `iq_dequant_f16` at `:4900-4908`, then calls `m.gemm.f16` twice for each expert's actual `ne` rows at `:4928-4947`. The GPU dequant kernels are in `sycl/src/kernels/cuda/iq_kernels.dp.cpp:4292-4316,4390-4417`. This is followed by the existing oneMKL/DPCT GEMM in `sycl/src/prefill/gemm.dp.cpp:765-786`: column-major `W^T[N,T] = W^T[N,K] * X^T[K,T]`, `trans/nontrans`, `M=N, N=T, K=K`, W leading dimension K, X leading dimension K, Y leading dimension ldy, FP16 inputs and FP32 accumulation/output. The service-event variant preserves the same args at `:790-805`.

Thus the actual CPU-capacity gap is packed-blob source-to-host-ring staging (plus optional source reads), not CPU IQ dequantization. CPU native quantized GEMV/complete-chain numbers in the existing capacity report are a separate decoder/verifier path and cannot stand in for this `memcpy`/read operation or GPU dequant+GEMM. A CPU dequant benchmark would measure an alternate implementation, not a production stage.

Exact default production geometry and byte accounting
For H=2560, FF=640, 384 experts/layer, GU IQ2_S and Down IQ4_NL (the measured CPU fixture's selected types; type IDs 22 and 20), GGML block sizes are 82 bytes/256 values for IQ2_S and 18 bytes/32 values for IQ4_NL (`sycl/third_party/ggml/ggml-common.h:403,453-454`; row-byte dispatch in `sycl/src/kernels/cuda/iq_kernels.dp.cpp:4231-4240`). Native expert layout puts gate then up then down (`:4426-4439`).
- Each GU matrix is FF×H = 1,638,400 values = 6,400 blocks × 82 = 524,800 B. Gate+up = 1,049,600 B.
- Down is H×FF = 1,638,400 values = 51,200 blocks × 18 = 921,600 B.
- Packed blob/H2D payload per expert = 1,971,200 B (1.88 MiB); all 384 = 756,940,800 B (721.6 MiB) per layer if each is transferred once.
- Device FP16 expanded weights per expert: GU 2×FF×H×2 = 6,553,600 B; down H×FF×2 = 3,276,800 B; total 9,830,400 B. The packed payload is not the FP16 scratch footprint.
- Per expert-token, two GU products plus Down are 2×(2×H×FF + H×FF) = 9,830,400 FLOPs, counting multiply-add as two. Top-10 gives 98.304 MFLOPs/token/layer; 48 layers gives 4.718592 GFLOPs/token for these products. These counts exclude dequant, routing, other model work, and reductions.
- Per expert/chunk the code issues one dequant-GU kernel and one dequant-Down kernel, then two GEMMs with M=`ne` routed rows (or compacted `ne`), GU `(N,K)=(1280,2560)`, Down `(2560,640)`. Do not substitute M=80/160/640 as an asserted route histogram: actual `ne` distribution by expert and chunk is required. Weight expanded once per chunk/expert, then reused across that expert's `ne` rows. The stream's in-order compute queue places dequant then both GEMMs for each expert; inter-expert submissions can be outstanding until `expert_wait_batch` forces a wait.

Host-stager configuration: defaults to 2–4 threads (`max(2,min(4, hardware_concurrency/4))`) and 16 slots; `STRATA_STAGER_THREADS` clamps 1–32, `STRATA_STAGER_RING` clamps 2–256 (`:358-400,1120-1137`). File-transient sources use 32 threads and default ring 128. A CPU-only result must state which source arm it represents; RAM memcpy/copy_blob and disk `read_into` are different workloads.

Reconciliation with measured ceilings (Ryzen 5 5600X, 6 cores, Arc B570, 2026-10-10)
`bench/results/2026-10-10-hardware-concurrency/HARDWARE_LIMITS.md` reports effective host-USM H2D 6.447 GB/s one-way, pageable H2D 4.605 GB/s, RAM read 36.87 GB/s, non-temporal copy 37.58 GB/s (read+write logical bytes), cached copy 22.95 GB/s (read+write), and CPU register FMA 0.818 TFLOP/s. These make 1.9712 MB/expert about 0.306 ms of host-USM transfer at the separate control rate, if every blob is transferred; this is only a conditional payload/rate division, not production DMA latency. The prior measured 32K route's ~190.2 GB would be ~29.5 s at that rate; HARDWARE_LIMITS explicitly says that historical route used `STRATA_PREFILL_LAYER_MAJOR=0`, and the quotient is not a latest-route service measurement or physical lower bound.

The same doc's actual-shaped GPU GEMM M=80/160 rates are synthetic and lack the current route row histogram; M=8192 hot GEMM and CPU register FMA are not valid per-expert model ceilings. Its separate native CPU IQ2_S/IQ4_NL service fixture (H=2560, FF=640) measures direct streaming complete chain 286.466 µs/expert-token at NT1 and 148.362 µs at NT4; a fixed five-worker-plus-host pool gives 90.978 and 38.738 µs respectively. That work computes quantized CPU products and is not the production GPU stager. Counterfactual estimates at `bench/results/2026-10-10-ple-offline-census/capacity-workload-estimates.json` assume historical 190.2 GB and hypothetical all-call M shapes, so they are not route measurements.

Decisive remaining capacity measurement and exact CPU-only control recipe
First, qualify only the host packed-blob stage in isolation, using 1,971,200-byte blobs and the selected source arm. Create a deterministic source corpus with 192 blobs (the existing streaming cohort size) and a ring with exactly 16 reusable 1,971,200-byte output buffers. Run the same byte-for-byte copy (`memcpy` for resident RAM source; in a separate arm, the exact `read_into` source behavior if the production route uses file-transient experts), with one producer and 4 worker threads, matching defaults on this 6-core host; include NT=1 as the pinned-caller/direct control. Block slot reuse until the prior consumer acknowledgment exactly as `Stager::work` does, but substitute a host completion marker and perform no accelerator enqueue, device query, DMA, dequantization, or GEMM. Warm once; capture per-blob and whole-window wall times and bytes, 25+ samples across three fresh processes, report medians/ranges and process controls, verify every output hash, and retain CPU affinity/governor/source corpus cache state. Keep this result explicitly a host staging-only capacity control; it cannot claim H2D, source-I/O service, GPU dequant, or total-model latency. If the production path uses pinned host output, record that the nearest no-GPU control uses OS-locked destination pages and does not exactly reproduce SYCL host-USM allocation semantics; do not label it a pinned-USM measurement.

The separate operation-specific end-to-end qualifier, required before attributing production's device phase, should use the actual GGUF IQ2_S/IQ4_NL source blob and production dimensions, stage packed bytes, H2D once, run the two exact dequant kernels and two same-argument oneMKL GEMMs for a captured set of real `(layer, expert, chunk, ne)` rows; return wall/host time and device event spans per operation plus exactness checks. Obtain the actual route shape/bytes from a matched route trace. It must be a GPU qualification and is outside this CPU-only report's allowed work. Do not infer current bottleneck from host copy timer alone; historical Down phase marker includes stager waits.

Architectural changes that can alter the bound
- Mandatory H2D payload falls only if fewer packed expert blobs are transferred (resident/cache hits, reuse retained across token chunks/layer-major route), or if the packed representation is made smaller; the latter must include device decode and numerical qualification. Pinned direct DMA changes host-copy cost, not H2D payload. Mapped host reads still consume PCIe payload on demand and are not equivalent to elimination of transfer.
- Larger `ne` per expert-weight load amortizes one packed transfer and one dequantization over more rows, but needs the measured actual row distribution and a route that reuses the layer/expert weights across chunks without changing numerical behavior. Existing layer-major source code alone is not evidence that the path is selected or accepted; a separate full-context numerical issue remains unresolved.
- Reordering copy/kernel submissions or changing dependency order does not reduce required bytes or FLOPs. With current safe runtime settings, the separate two-queue control found essentially serial GU wall time and zero PTI overlap across target copies/GEMMs; this falsifies assuming scheduler reordering alone will hide the transfer for that control, not all possible schedulers.
