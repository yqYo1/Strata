# R239 independent audit: offline PLE census evidence

## Verdict

The two committed census receipts support a **CPU-only, source-pinned, per-row-verified logical geometry result** for the stated token sequences and an explicitly cold cache at each 8,192-token chunk. I found no arithmetic or history counterexample in the reviewed oracle, independent equation, first-page grouping, 8K extension, page union, assumed-record histograms, or EOF accounting. The stronger storage/performance interpretation remains unqualified: these results are not production `PleReader` request traces, cache/ReaderStats evidence, physical ZFS extent counts, successful EOF reads, or full-context inference.

The cold-control conclusion is correctly narrow. For the 32K fixture, expanded page-job bytes are 1,417,633,792 versus 36,945,476,800 conditionally coalesced logical record bytes (about 26x). Thus “larger reads are automatically faster” is not supported by this geometry. It does **not** establish that larger reads are slower on the measured storage device. Keep the proposed density-gated grouping and matched fresh-state service comparison as hypotheses pending real reader evidence.

## What the source and receipts establish

- The oracle calls unchanged `ple_artifact_consts()` and `ngram_rows()` from the frozen source object; it does not reimplement the hash. The archived build receipt pins the source/header/object, command and executable evidence. The separate C++ external-golden receipt passes 304 rows. The v2 qualifier independently checks the same 304 vectors in Python.
- I checked the source semantics against both translations. `ngram_rows` consumes predecessor history oldest-first, uses the newest predecessor first, cuts the predecessor and every older context position to EOS for a negative/EOS predecessor, leaves the current token itself intact, and computes modulo-2^64 products. The oracle's chunk history reconstruction (`tokens[c0+i+j-2]` after initial history) and Python's distance-1-then-2 reconstruction agree, including the first two positions and chunk boundaries.
- The 32K census pins the original 32,768-token file and admits the separately recorded 198 insertion before index 32,759. It compares 32,768 PP positions plus the explicitly separate token-32,768 tail: 524,304 rows total. The full-context-shaped receipt is carefully corrected for the original fixture's 262,145 IDs: it uses the first 262,144 IDs, counts 262,143 as PP and one separate tail, compares 4,194,304 rows, and does not claim the candidate engine supports a 262,144-token inference. The extra source-fixture ID is not admitted to that result.
- For both model-shaped receipts, the independent Python equation compares every head of every supplied C++ row before emitting any normal aggregate; it requires exact file length, no trailing bytes, and verifies the consumed-byte hash. The saved reports show 524,304/524,304 and 4,194,304/4,194,304. The matched-history mutation correction uses the same `--prev 7 11` for the clean and corrupt files and rejects the first and last in-range row changes at token 0/head 0 and token 10/head 15. This repairs the earlier history-mismatched mutation evidence; the original receipt was not rewritten.
- The geometry agrees with `PleReader::issue` for the specified no-cache-hit control: an aligned first-page key, one job per key, maximum job length extended from 4K to 8K when any associated row straddles, and duplicate uses retained. Expanded-page union is calculated separately, correctly preserving overlap between adjacent jobs. The qualifier checks rows 42/43/44 (two jobs, one 8K, 12,288 summed job bytes versus an 8,192-byte page union), row 1,454 at the assumed record boundary, and the last table row.
- Histogram arithmetic is explicit and scoped: unique expanded 4K pages per assumed record and baseline jobs per assumed record are separate histograms. Record boundaries are assumed whole-file 128KiB multiples, not observed physical extents. The conditional record plan counts one touched record once, clips its logical bytes at the admitted table EOF, and can cover header/unrequested bytes; the report does not present that as a valid direct-I/O request or measured I/O.
- EOF is handled as geometry only. The last row ends at the admitted table end; its aligned 4K baseline page extends 832 bytes beyond that end. The conditional coalesced plan clips at EOF. No read was issued, so no outcome about actual short reads or production EOF handling follows.

## Remaining gates and audit notes

1. The reported 8,192-token chunks each reset the hypothetical row cache independently. Production retains an 8-way cache, can have hits before job formation, and cache replacement depends on asynchronous completion order. Census sums are therefore sums of independent cold controls, not a simulation of whole-request cache behavior or a global unique-row/job count. Use actual `ReaderStats` and a controlled fresh-state production comparison before making a cache or throughput claim.
2. Matching `ngram_rows` and source-inspected `Prefill::ple_gather` history proves the admitted equation/sequence, not that a complete inference route issued this exact token stream or these row requests. No full-context model execution, GPU work, `ReaderStats`, successful shard read, or hardware latency evidence exists in these receipts. In particular, do not cite 4,194,304 rows as a qualified full-context inference result.
3. The 128KiB record histograms cannot establish physical ZFS/SSD block behavior. The separate ZFS logical control may make the “larger reads” comparison less intuitive, but neither it nor this census measures media service. Keep all record language explicitly conditional.
4. A small provenance-label inconsistency remains: both result JSONs identify `kind` as “bounded CPU offline PLE census v1,” while the embedded census-source digest is the archived v2 source (`81732251…b513`) and the latest receipt set includes v2 source preparation/qualification. The full digests and commands make the evidence recoverable, and this does not invalidate the arithmetic, but downstream summaries should identify the executable/source version by digest rather than relying on that `kind` string. Do not mutate the frozen receipts; correct only future regenerated metadata if rerun.

## Actionable disposition

Accept the receipts for the narrow offline conclusion: the exact admitted inputs yield the recorded PLE row sequences and cold per-chunk logical page/assumed-record geometry, with a large conditional record-byte expansion relative to the baseline page-job geometry. Preserve the explicitly corrected 262,145-ID admission and matched-history mutation record alongside the original receipts. Do not adopt a production read/coalescing policy or state a storage bottleneck from this census. The next evidence gate is a separate, source-matched service run that records real request geometry and `ReaderStats`, with cache state and physical storage behavior stated independently; full-context qualification remains its own inference gate.
