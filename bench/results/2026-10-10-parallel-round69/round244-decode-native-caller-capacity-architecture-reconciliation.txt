# R244 — Decoder native CPU caller and capacity reconciliation

Date: 2026-10-10 (Asia/Tokyo). Read-only reconciliation of the frozen default decoder/verifier CPU expert caller with the attained native NT1–4 capacity evidence. No source edits, build, test, benchmark, profile, inference, GPU/device/process query, Git operation, or cleanup was performed. Only this report was written.

## Finding

The attained IQ2_S GU22 / IQ4_NL Down20 NT1–4 cells are eligible only for decoder CPU expert jobs whose actual layer has the matching `(gu_type,d_type)=(22,20)`, whose routed expert is assigned to CPU, and whose grouped job has the measured `nt`. A 384-blob fixture is a capacity control for that exact format pair; it is not 384 calls in a decoder request, nor evidence that all 48 layers or all routed rows take the CPU path. Decode is mixed-format by layer, and GPU-resident, PCIe-offloaded, peer/helper-GPU and invalid rows do not become CPU native jobs. The actual caller's histogram of `(layer,format,nt,CPU/GPU route,job count,entries)` is absent from the reviewed capacity receipts, so no measured NT1–4 capacity point can yet be weighted into a production decode time.

Speculative verification groups multiple token rows at the expert level: for each verifier window and layer, the dispatcher makes one job per distinct CPU-missed expert, then appends each token's activation/output pointer to that job and increments its `nt`. Thus `nt` is the number of rows for that expert in the current window, bounded by window length (MAXT=8), not the number of experts in the window. The maximum routed entry count is `T*K` (default router K=10 for the 512-expert route); distinct jobs and CPU jobs are no greater and depend on repeated IDs and placement. One-row native verify decode has `T=1`, so every CPU expert job is NT1 even if several experts run concurrently in the pool. In a verifier window `T>1`, actual expert groups can still be NT1, and NT2–4 capacity applies only when that same expert occurs in two to four rows and those rows miss GPU tiers. NT5–8 are allowed by caller storage but are outside the NT1–4 capacity fixture and must remain uncharacterized here.

## Caller graph and accounting

In the frozen production source, native expert packs are dispatched through the generation callback `drive_pool_multi` and `expert_pool_dispatch_multi`; the separate single-token `expert_pool_dispatch` explicitly rejects a native pack. The verifier callback passes its rows to the multi dispatcher, including a one-row (`T=1`) window. That function first counts and classifies `n_tok*K` route entries, publishes a GPU plan, launches peer/remote routes where applicable, and sets `kind[i]` for each entry. It quantizes input activations only where CPU work remains. It then scans entries in token-major order: GPU/offload entries are zeroed or left for their producer; each CPU entry is appended to `jobs_multi[e].act[]`, `nact[]`, and `out[]`, with `jobs_multi[e].nt` incremented. `job_of` deduplicates experts within the layer-window. The native pool receives `njobs`, not `n_tok*K`, and runs one GU phase over `nb*FF` flattened expert rows, caller-side FF quantization for every CPU job token, then a Down phase over `nb*H` rows. Task units are row ranges crossing expert boundaries, not token tasks. This is why `work(384)`/384 fixture blobs, `BATCH=1|6`, layer top-K entries, `njobs`, and each expert's `nt` are distinct counts.

GPU participation changes the denominator before native kernels run. The residency plan assigns resident experts to the primary GPU; missed experts can be assigned a PCIe share; peer/helper GPU ownership is separately recognized. The default decode CPU job list is therefore the subset of routed entries with `kind<0`, deduplicated by expert. A GPU result is not a CPU kernel invocation and must not be included in native service multiplication. On the no-plan fallback, host residency, peer availability and remote ownership still classify entries. The lookahead thread's up-to-eight-row routing is only a warm/prefetch hint; it does not execute those rows in the current decode dispatch and is not evidence for CPU `nt`.

For speculation, the verifier computes a `T`-row output window and commits only the accepted prefix. With `a` accepted drafts, outputs rows `0..a` are emitted (the last is the mismatch/bonus token), while rows `a+1..T-1` are discarded and do not enter committed state. CPU expert work for those later rows was still executed before acceptance was known. A useful-versus-discarded work report must therefore count per-token entries/jobs against the verifier's post-hoc accepted length, without treating every evaluated row as useful generated output. On an all-accepted window, all T outputs are used; early rejection makes a suffix of computed outputs wasted. This distinction further prevents equating grouped NT capacity with output-token throughput.

## Formats and fixture eligibility

The installed-pack metadata audits already on record report 48 mixed GU layers: type 18 on 17 layers, type 21 on 10, type 22 on 20, type 23 on one. Separate metadata audit reports Down type 20 on 39 of 48 layers and type 42 on the other nine. These are format inventories, not a runtime process-to-pack attestation or a per-layer paired format map; they do not establish the intersection of GU22 and Down20 layers. The active source reads the loaded `NativeFmt` for each layer and dispatches by its actual per-layer `gu_type` and `d_type`. A route census must record both values per layer rather than apply either marginal count as a pair count.

For the 384-selected-blob capacity fixture, the eligible exact-format cells are the 22/20 measurements only, and only as shape/service controls. For an actual decode call to match them, record: loaded layer format 22/20; H=2560 and FF=640; native expert CPU job rather than fallback source; measured NT bucket; selected kernel branch; ISA/build and dispatch environment; direct or pool mode; and correctness admission. A layer with GU18/21/23 or Down42 is a different measured workload; same hidden dimensions do not make its service interchangeable. A matching-format route handled by VRAM, PCIe or another GPU is also not eligible. The 384 IDs identify fixture weight samples; they do not imply 384 distinct experts, requests, routed calls, actual rows, or a complete decode window. Existing capacity reports label weights host-resident and inputs synthetic; streaming cohorts exceed nominal L3 in logical extent but do not prove physical DRAM traffic.

The frozen `native_expert.cpp` dispatch further narrows eligibility. On the Zen 3 AVX2 path and default `STRATA_IQ_MT_MIN=2`, GU22 NT1 calls GGML's single-token dot fallback; NT2–4 can select the custom IQ AVX2 grouped path if AVX2 is available and `STRATA_NO_IQ256` is absent. Down20 NT1 likewise uses GGML; NT2–4 can select IQ4NL AVX2 if AVX2 is available, `STRATA_NO_IQ4NL` is absent, and the NT threshold is met. Thus R220's NT1 and NT2–4 rows measure distinct dispatches. Runtime flags (`STRATA_IQ_MT_MIN`, `STRATA_NO_IQ256`, `STRATA_NO_IQ4NL`, `STRATA_IQ256_GATHER`, `STRATA_IQ_PREFETCH`) and worker-local CPU/ISA must be recorded; AVX2 compilation/availability alone does not prove the custom grouped branch ran. In particular, the Zen 3 default gather setting is the plain decode per R224's source audit; a forced gather variant is separate and already screened as an unproven probe.

## Capacity and architecture limits

R235's NT4 service anchors are complete native service, not an instruction ceiling: direct hot/streaming medians 147.419/148.362 microseconds per expert-token and existing five-worker-pool-plus-host medians 34.736/38.738 microseconds per expert-token, respectively. The 24 clean samples, three processes per NT/set, and denominator are fixture-specific. Hot and streaming differ in expert subset/work geometry; logical packed bytes are not physical memory transactions. R235 explicitly rejects multiplying 480 routed entries by the fixture number to predict 54 tokens/s. This reconciliation adds no production estimate or lower bound.

The defensible Zen 3 architecture statement is operation-specific: with AVX2 but no AVX-VNNI, NT2–4 grouped IQ2_S GU amortizes packed codebook/grid/sign/scale decode across the expert's activation rows, but each token still needs Q8_K activation loads, sign application, byte-pair multiply/add work (`vpmaddubsw`, `vpmaddwd`), integer accumulation (`vpaddd`), and FP accumulation (FMA). IQ4_NL Down reuses nibble decode/preparation across tokens but retains each token's activation dot, integer reductions, and FP accumulation. Both kernels therefore consume packed-data decode, dependent lookup/shuffle or gather work, integer SIMD issue/reduction, register/accumulator capacity, and FP accumulation; `NT` amortizes only some decode work. They are not bounded or described by an FP32 FMA peak or dense-equivalent MAC count.

R224's pinned emitted-code review found explicit YMM accumulator stack stores/reloads in the NT4 IQ2_S GU specialization in that particular calibration build, while the inspected NT3 specialization had no corresponding YMM accumulator stack traffic. This is static code evidence for a plausible NT4 register-pressure cost, not cycles or proof NT3 is faster. R224 also says the inspected build disabled AVX-VNNI. The system's Family 19h guide and a Zen 3 scheduling model can inform further instruction analysis, but without matching dynamic instruction/latency/throughput measurements or admitted PMU access, no instruction-operation ceiling is established. Existing PMU access records were unavailable; no uncore or CPU roof should be inferred from nominal core issue limits, packed-byte ratios, or FMA rates.

## Architecture reconciliation and next evidence

The completed capacity evidence says that a specific grouped decode mechanism exists and that NT4 has an emitted register-pressure concern. It does not answer current path frequency. The minimum joining evidence is one clean request-side compact histogram by layer and `(gu_type,d_type)`, `T`, `K`, distinct routed experts, CPU entries, GPU-resident entries, PCIe/peer/helper entries, and each CPU job's `nt`; preserve accepted draft count so useful and discarded rows can be separated. For CPU-only work, distinguish activation quantization, GU kernel branch/rows, caller FF quantization, Down branch/rows, and pool/direct wall and worker CPU-time spans. Ensure counts reconcile: all `T*K` entries = invalid-free classified entries; distinct expert jobs reconcile across route tiers; each CPU job's `nt` reconciles to CPU entries; and per-layer jobs reconcile to pool phase rows. Record actual per-layer pair formats and ISA/dispatch settings. Only matching 22/20 CPU calls at matching NT may be joined to the 384-fixture cells, and even then as a calibrated component envelope rather than a model bound until real route activations, worker placement/schedule and the measured whole request are joined.

No new external CPU quantized-MoE optimization is recommended from this pass: candidate reuse and task shaping mechanisms have already been screened in R17/R220, and importing a non-AVX2 engine result would not make it eligible for this source caller. Primary Zen 3 reference for any future instruction-model work: [AMD Family 19h Software Optimization Guide](https://docs.amd.com/v/u/en-US/56665). Prior emitted-code and NT-specific evidence: R220 and R224; denominator/floor correction: R235. No external implementation result supplies a Strata route histogram or an operation ceiling.
