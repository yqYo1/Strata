Scope: read-only source and primary-reference research. No runtime measurement or implementation change.
Frozen production tree: `/home/yayoi/ghq/github.com/yqYo1/Strata/.worktree/diag-sycl-prefill-service-events-20261010`, commit `495369cf4dc6e6da564095a1c26504dd3694e3f2`.

Finding
The resident-RAM staging operation is one packed-blob copy per non-pinned expert into a reusable host ring, then host-to-device DMA. In `sycl/src/prefill/prefill.cpp:358-535`, `Stager::work` either calls `memcpy(buf[b], jb.src, jb.bytes)` for a direct source pointer or `ExpertSource::copy_blob`; the latter (`src/core/expert_source.cpp:1007-1011`) resolves the blob and calls `std::memcpy`. `FileExpertSource::copy_blob`'s mapping is described as in-place mapped files at `src/core/expert_source.cpp:1026+`; some GGUF arms instead call `read_into` and assemble three role slices. Do not mix that source assembly / storage-fault arm with a resident source-to-ring memory-copy result. Pinned experts bypass the host copy. The consumer waits for readiness, submits H2D, then records its completion before a slot can be overwritten; the data contract is not a free-running memcpy loop.

For the R240 representative IQ2_S/IQ4_NL fixture, each packed copy is 1,971,200 B (1.88 MiB). At six cores / twelve logical processors, the actual default expression is `max(2, min(4, hardware_concurrency()/4))`, hence **3 workers**, not 4. Four is a valid explicit test arm, not the production default. The default ring is 16 buffers, or 31,539,200 B (30.08 MiB) of destination storage. AMD lists the Ryzen 5 5600X as 6 cores / 12 threads with 32 MB L3. Thus the whole ring is close to the nominal shared L3 capacity, but a single copy is only about 6% of it; workers share that cache and other host work also uses it. The full source working set per layer in the 384-expert fixture is 756,940,800 B (721.6 MiB), so source traversal is much larger than L3 while output ring reuse is near L3 scale.

Do not infer a libc path merely from “large copy.” Current glibc's x86 vector routine selects non-temporal stores only when a non-overlapping copy reaches the runtime `__x86_shared_non_temporal_threshold`; it also has REP MOVSB and vector paths, and its NT path varies with size and source/destination page aliasing. The threshold is runtime libc/CPU/cache configuration, not a fixed universal 2 MiB boundary. glibc's tunable documentation says this knob controls the size at which some memcpy/memmove implementations use non-temporal stores. Its 2020 maintainer change explains the threshold's cache-sharing rationale and warns that a threshold optimized to let one thread consume too much shared cache can hurt other active threads. Therefore 1.9712 MB might be temporal or NT on this host: must inspect the installed glibc's effective tunable / implementation or verify with dispatch evidence before claiming either. Changing a process-wide glibc tunable is not a safe product-level candidate.

Accounting and implications
A `memcpy` of B payload bytes causes at least B bytes of source reads and B bytes of destination writes in the logical copy accounting. Report both `B / elapsed` as payload GB/s and `2B / elapsed` as logical read+write GB/s, and label these separately. This 2x convention is not a physical memory-controller counter; write allocation, cache hits, eviction, and write combining can change actual DRAM traffic. Historical R240 values are explicitly read+write rates: 22.95 GB/s cached copy and 37.58 GB/s NT copy; they are not payload rates. On the same denominator these correspond to 11.475 and 18.79 GB/s payload, respectively. They are old isolated controls, not current Stager rates or proof of which libc branch ran.

The stager output is page-locked SYCL host USM when allocation succeeds, with pageable fallback (`prefill.cpp:395-415`); it is consumed by the H2D copy engine and reused after DMA. That lifecycle makes an NT-store experiment plausible if the current `memcpy` path is temporal: destination bytes are not CPU-read, and writes can otherwise displace useful cache lines. But source bytes are cold/streaming too, so an explicit NT loop may not help if libc already dispatches NT, and its effect depends on socket/cache sharing, page alignment/alias, write-combining, pinning, worker concurrency, and DMA's host reads. CUDA's guide similarly establishes that pinned memory supports highest-bandwidth transfers but should not be overused; it does not say that CPU-side NT stores improve staging. Neither reference settles this SYCL implementation's outcome.

Novel source-eligible candidate, with a hard evidence gate
Candidate: a narrowly scoped A/B implementation for the **direct resident packed-source → reusable pinned host-ring** arm that substitutes an explicit streaming-store copy for `memcpy` only for ~1.97 MB blobs, retaining the same three-worker default, same 16-slot ring, DMA acknowledgment/reuse, and exact payload. Keep ordinary `memcpy` for small copies and every file-read/assembly arm. This is justified as a targeted experiment because each payload is much smaller than the 32 MB L3 while the full source stream exceeds it and the copy destination is only read by the DMA consumer. It is not an adopted optimization.

Gate before coding: establish actual glibc version/active IFUNC implementation and the effective `x86_non_temporal_threshold` on the target Linux runtime. If the effective path already uses NT at 1,971,200 bytes, rule this source candidate out unless a different issue is demonstrated. If temporal, compare only the two implementation arms in the matched, previously authorized resident-copy control; do not alter global glibc settings. Use the production 3 workers as primary and 4 only as a separate sensitivity arm. Preserve destination allocation type, 16-slot reuse handshake, source corpus/ring addresses and cache state; verify all output bytes. Report payload rate, read+write logical rate, per-blob latency, queue-level wall time and worker/host CPU utilization. If this wins only in a one-copy hot-cache microcase or fails to improve ring-window wall time, reject it. No claim about full inference or H2D follows.

This refines rather than repeats the earlier generic isolated-control recipe: the new candidate hinges on the per-blob dispatch boundary and its mismatch with aggregate source/ring working sets. The current concurrent synthetic host-copy control/results were not inspected.
