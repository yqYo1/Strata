# R219 — layer-major reuse and full-context memory envelope

Date: 2026-10-10 (Asia/Tokyo). Read-only source and closed-report review. No source edit, build, test, profile, inference, GPU/device or process query, Git/service operation, cleanup, or inspection of the root's live implementation worktree was performed. This report records a source and arithmetic envelope; it is not a performance or adoption result.

## Decision

The current `STRATA_PREFILL_LAYER_MAJOR` path already loads a layer's packed expert blobs once, then reuses those same bytes while `run_impl` processes every configured prompt chunk for that layer. It does not reload the layer per chunk. With MMQ disabled, it still performs routed per-expert GU and Down GEMMs per chunk; it does not concatenate an expert's rows across chunks, and it repeats dequantization for routed experts on each chunk. Thus layer-major already captures the unambiguous cross-chunk *weight-load* reuse. Any proposed cross-chunk routed-GEMM batching is a separate algorithm with an output/route-retention cost, not an additional weight-transfer saving established by this path.

For a full physical 262,144-position request, layer-major's residual handoff alone accounts for 10 GiB across host and device backing before workspace, KV, cache, allocator and graph allocations. If all rows are put on the B570, the 10-GiB residual extent is 71,303,168 bytes larger than the closed runtime capacity receipt (10,666,115,072 bytes), before other live allocations. An all-GPU full-context setting therefore cannot be admitted by nominal capacity arithmetic; partial GPU residency still requires an actual allocation receipt and full lifecycle test. With no GPU rows, the host row vector alone is 10 GiB. Neither scenario has been validated with a 262,144-position model input.

No gain follows from the source audit. Hold adoption until the selected mode and exact route are recorded, the math/state gate passes, a paired request measurement demonstrates repeatable end-to-end improvement, and the true 262,144-position lifecycle meets memory and restore/decode gates.

## What the layer-major route does

`Prefill::run` selects layer-major when `STRATA_PREFILL_LAYER_MAJOR=2`, or when it is `1` and the call has multiple chunks (`prefill.cpp:2407-2430`). The deterministic selector for a qualification is `=2`. For positive `n`, `run_layer_major` admits only the full, single-GPU, compact FP16 path with a source; it rejects partial layer ranges, helper/peer paths, nonresident K/V pages and PLE preload (`:2479-2500`). It creates one temporary cache with `g.n_expert` slots each sized to `MAXBLOB()`, then loops layers (`:2700-2703`, `:2784-2807`). For each layer it resolves a source job for every expert, stages and copies every expert blob to that cache, waits for copy/stager completion, marks the layer's residency map, then calls `run_impl(tokens, n, ...)` (`:2790-2840`). Transfer bytes for a layer are the sum of the actual `layout.blob_bytes(layer)` for all `g.n_expert` entries; they are not determined by route counts. Use runtime layout and transfer receipts, not `n_expert × a guessed blob size`.

`run_impl` divides the request into its configured `m.T` chunks. Each chunk independently computes routes, host counts/offsets/order and compact per-expert row maps (`:2882+`, `:4070-4240`). With the layer cache resident, the selected expert reads `m.cache->device_slot(...)` directly; the ordinary streamed STAGE ring is not refilled for these cache hits. In the direct (non-MMQ) compute arm, each routed expert's rows are gathered into the compact workspace; GU GEMM, SwiGLU, then Down GEMM run in expert-ID order. The same packed layer bytes remain resident across subsequent chunks, while the DQ scratch is reused in queue order. `run_layer_major`'s residual callback stores each completed chunk's output for the next layer (`:2814-2839`); only after the full request has traversed this layer does it load the next one.

The direct native dequant/GEMM arm is conditional. The MMQ branch returns before direct dequant; fused branches can also bypass it. A type-20 layer or `STRATA_PREFILL_LAYER_MAJOR` setting alone does not prove the direct helper/call route. For a direct-path comparison use a fresh process with `STRATA_PREFILL_LAYER_MAJOR=2` and `STRATA_PREFILL_MMQ=0`, then record per-layer format, routed expert counts, actual direct/MMQ/fused selection and helper calls. This report does not establish which arm a production binary would select.

For a request with layer set L and chunk set C, the source-defined direct-path call-count shape is: `2 × Σ_l∈L Σ_c∈C E(l,c)` GEMM calls, where `E(l,c)` is the set of experts with nonzero routed rows in that layer/chunk (one GU and one Down per such expert). The exact counts and each `M_e` require a route receipt. Weight cache-fill count instead is `g.n_expert` blob copies per layer, regardless of `E(l,c)`. Direct-path dequant is per routed expert per chunk; layer residency does not cache the expanded FP16 matrices across chunks. The source does not establish the bytes saved by batching, because it already performs one layer load for all chunks and no route histogram shows how many calls would merge or their M sizes.

## Full physical 262,144-position backing and workspace

The source defines `D = 10,240` float elements per residual row. `run_layer_major` computes `gpu_tokens`, optional in-place scratch reuse, then allocates `rows` for exactly `(n - gpu_tokens) * D` floats on the host and device rows for `allocated_tokens * D` floats (`:2721-2762`). It logs those extents. At `n=262,144`, ignoring the optional in-place reuse, the split satisfies:

- Total residual backing: `262,144 × 10,240 × 4 = 10,737,418,240 bytes = 10 GiB` across the host vector and device rows.
- All host (`gpu_tokens=0`): 10 GiB host row allocation.
- All GPU (`gpu_tokens=n`): 10 GiB device residual request before any in-place reduction. The closed B570 runtime capacity of 10,666,115,072 bytes is already smaller by 71,303,168 bytes; the source's free-VRAM comparison also has to admit all other live GPU objects.
- Mixed placement: it moves bytes between host and GPU; it does not lower the combined 10-GiB row extent. The source does not impose a host-RAM headroom check.

`STRATA_PREFILL_LAYER_MAJOR_INPLACE=1` may reuse the first `first_len` rows in `m.R` when all chunks stay on GPU (`:2733-2739`). This reuses an existing workspace extent, not free capacity; by default `first_len` is controlled by cache state/`STRATA_PREFILL_FIRST` and `m.T`, so record its value. For every other GPU row, allocation remains an explicit additional device request. Host-resident rows still require the source's full backing. The `get_memory_info` check only rejects when its current free counter is nonzero and smaller than this one device-row request; it is not a complete peak-memory receipt.

Additional simultaneous objects include the one-layer expert cache (`:2700-2703`), the already initialized Prefill workspace and current `m.T` activation/MoE scratch, resident full-context K/V pages (explicit prerequisite `:2489-2495`), runtime/graph/cache allocations, and possibly decode-cache/MTP lifetimes depending on the existing release hooks. A prior measured layout recorded a 1,363,148,800-byte layer cache (1.27 GiB), but that is a previous layout/run receipt, not a current pinned-runtime allocation measurement. The present cache size is `g.n_expert × align256(MAXBLOB())` by `ExpertCache::open_sized`; obtain the actual pack's `max_blob` and `layer_cache.bytes()` from the qualifying binary. Do not treat nominal board capacity or the old cache receipt as guaranteed available headroom.

The source calls `run_impl` with full request `n` once per layer and relies on `m.T` chunks; total residual handoff must cover the whole request, while route maps and MoE intermediates are chunk-sized. At a hypothetical `T=8192`, 262,144 positions are 32 chunks; this is arithmetic only until `m.T` and tail are recorded. The full-context gate must record each chunk and final tail, `n=262144` actual batched positions (not only `--max-context=262144`), last position 262143, all-layer and final state/KV/indexer continuity, cancellation/failure cleanup, cache/MTP restore, and a follow-up decode. Prior 32K and repeat-capture receipts do not meet this gate.

## Routed-GEMM batching versus existing reuse

A cross-chunk batching design would have to preserve, for each token, the routed expert IDs, rank/order, expert input rows and combine destinations/weights across the chunks while the layer is resident. Current compact scratch is bounded by `T`: maps cover `T*K` routed slots; compact `Xs`, `GU` and `Hh` are reused for each expert; `Dm` is route-sized for the current chunk and consumed by the combine before the next chunk. Growing these to full `n` changes storage scaling. For the source's `K=10`, `N=2560` geometry, a full-request FP32 `Dm` extent alone would be `n*K*N*4 = 26,843,545,600 bytes` (25 GiB); retaining one FP16 source row per token is `n*N*2 = 1,342,177,280 bytes` (1.25 GiB), while retaining a separate FP16 gathered row for every routed `(token, expert)` pair is `n*K*N*2 = 26,843,545,600 bytes` (25 GiB). These are simple shape envelopes, not recommendations or actual allocator requests. A different bounded schedule could stream compacted expert rows and their inverse scatter/output destinations in tiles, but it would need to retain or regenerate route data and delay/accumulate combine outputs without changing token/rank order or intermediate semantics. No such implementation or memory proof is present here.

This separates two hypotheses:

1. **Reuse/cache hypothesis:** already implemented for packed source weights across chunks within the layer. More reuse would require an observable repeated load or expanded-weight re-dequant cost that remains exposed; current source alone does not show either.
2. **Batched-GEMM hypothesis:** merge per-chunk expert rows to increase M/reduce launches. This changes the loop/retention schedule and must be evaluated against exact route coverage, GEMM shape distributions, added memory traffic, host+VRAM peak, and output/state parity. The M=8 to M=8192 synthetic envelope indicates shape can matter, but is not evidence that the actual request's expert shapes fall at either endpoint or that larger calls win end-to-end.

## Transfer scenario and evidence limits

The 190-GB scenario divided by 6.448533 GB/s is approximately 29.46 seconds of serialized payload transfer. If the exact same logical bytes and route applied, this is a useful scale comparison with the measured GEMM shape envelope, not a prediction of this layer-major path. The 190-GB figure is logical queued bytes from an older route; layer-major's transfer schedule copies all expert blobs once per layer, and current exact bytes, staging medium, route, and overlap were not measured for the requested full-context input. The B570's installed external Gen4 x4 link has a 7.8769 GB/s encoding ceiling, while 6.448533 GB/s is a probe median; neither establishes current route bandwidth. Ordinary streamed MoE already overlaps copies and compute within a layer. The present layer-major loop instead waits for each full layer load before its compute; R191 also shows its shared queue/stager terminal waits prevent a useful next-layer prefetch with current ownership. Double-cache prefetch is therefore a separate candidate with extra full-layer cache headroom and error-lifetime requirements, not something this report adopts.

## Qualification gates

Before considering any batching or schedule change, retain one compact receipt from an actual selected direct layer-major run: immutable source/build/model-pack hashes; actual `n`, configured `m.T` and chunk/tail boundaries; per-layer direct/MMQ/fused route; routed expert `M_e` histogram; GU/Down calls and bytes by layer/chunk; per-layer blob bytes/cache capacity; host source/stager time and successful H2D bytes/completion separately; host and device residual extents; peak/free memory at the same phase boundaries; and uninstrumented total prefill wall. First require exact route/output/logit and all relevant saved-state equality under the established math gate. Then compare a change against the identical schedule/control on at least 32,768 actual batched positions and repeat the true 262,144-position lifecycle with memory, restore, and decode checks. Preserve per-run samples and failure status. Reject any result that changes route/work, lacks complete state parity, fails memory admission or does not yield repeatable total-request improvement beyond run variation.
