Exact contract implemented
--------------------------
The C++ oracle includes the original public ngram.hpp and calls actual
ple_artifact_consts() and ngram_rows(). It contains no hash implementation or
copied multiplier/vocabulary arrays. Root must link the frozen ngram.cpp with
function/data sections and gc-sections, keeping unrelated table-I/O functions
unreferenced. No SYCL, GPU, model shard or table payload is needed.

Oracle CLI:
ORACLE INPUT_TOKEN_TEXT PP_COUNT NEW_ROWS_BINARY
       [--insert198] [--prev OLDEST NEWEST]
PP_COUNT is 1..262144. --insert198 requires exactly 32768 original tokens,
inserts token 198 before zero-based index 32759, and produces 32769 tokens.
Both implementations independently apply that transformation.
--prev defaults to {-1,-1}; custom histories are for tiny CPU contract fixtures.
Every token is int32; only whitespace-separated strict decimal text is accepted.
Both tools reject plus signs and leading-zero decimal forms. The qualification
plan includes strict-parser failure cases for both tools.
The C++ oracle processes at most 8192 tokens per call. prev is oldest-first:
for absolute token position i its pair is stream[i-2], stream[i-1], replacing
negative absolute positions with initial prev entries. This exactly reproduces
both frozen Prefill::ple_gather histories, preserving history across chunks.
The session source initializes both predecessors to -1.
The actual original hash treats predecessor EOS 248044 or ANY negative
predecessor as a cut before storage, cutting that position and every older
position. An EOS in the current token does not cut its own history. uint64
products wrap modulo 2^64. Python translates those operations independently.

Oracle binary is pure token-major/head-major uint32 little-endian, 16 rows/token.
No header or host-endian reinterpretation. Output is O_EXCL, so existing files
are never overwritten. Root must require exit 0 AND success:true and exact byte
counts before use. Failure can leave a partial NEW output; the agent does not
delete it, and root must never use it as a successful oracle.

Geometry
--------
Each <=8192-token PP chunk is an independent CACHE-EMPTY control.
There are <=131072 descriptor uses/chunk. Every row has offset
192 + row_id*90 in the admitted [160,320001536] IQ4_NL geometry.
No shard is opened. The admitted file/table end is 28800138432.

Matching frozen PleReader::issue's grouping geometry only, rows group by FIRST
aligned 4096-byte page; a job extends to 8192 bytes if any of its uses straddles
the page. It is NOT a global union-merge optimization: adjacent extended jobs
can overlap. All descriptors remain uses, including duplicate row IDs; cache
find/insert timing is deliberately absent.
Each chunk reports requests, unique rows/payload, straddling requests,
dedup job count/4K/8K counts, use and unique-row occupancy, baseline sum-of-job
logical bytes (overlap retained), expanded-page union count/bytes, row-payload
records and baseline-job records including straddlers.

128KiB records are ASSUMED at whole-file offsets divisible by 131072, NOT
discovered physical ZFS blocks. Occupancy counts UNIQUE expanded 4K pages
per assumed record, with a second histogram of baseline jobs touching records.
Conditional coalescing reads each touched assumed record once; reports full
record spans and an EOF-clipped logical read plan, plus the ratio to baseline
sum-of-job bytes. This compares logical geometry, not latency/capacity.

The admitted file end is NOT 4096-aligned (remainder3264), nor 128KiB-aligned
(remainder81088). Baseline aligned job geometry can therefore extend beyond
EOF for last-page rows; explicit counts/bytes record that possibility. There
are no actual reads, so no assertion is made about production EOF handling.
The conditional coalesced plan clips at EOF and can include header bytes and
unrequested rows. It is not a proposal to submit invalid aligned reads.

Whole-context totals are clearly labeled SUM OF INDEPENDENT CHUNKS. Summed
unique-row or record counts are NOT global unique counts. No default 8-way
cache simulation, cache-hit claim, completion-order approximation, or
unbounded-cache scenario is included.
