# R227: Native service-capacity v2 fixture source audit

Date: 2026-10-10
Scope: independent read-only source/admission audit before root-owned build and host runs. I did not build, test, execute, profile, inspect live processes, or query hardware. No source or run artifact was changed. This is source evidence, not a validation result.

## Admission finding

The v2 harness is structurally suitable for bounded NT1–4 calibration on the 384 selected real payloads, with an intended-hot eight-ID view drawn from the exact same loaded source cohort. Its direct native GU, quantization, Down, full-chain, and pool paths are separately staged; the NT2–4 per-token/per-stage gates are explicit ANDs of max-absolute and normalized-RMS limits. Source review found no pointer-range or missing-row path that would make a passing result trivially vacuous.

The root-admission record predeclares these limits before any fixture run: GU maxabs `1e-4` AND NRMS `1e-5`; staged Down the same; independent full-chain maxabs `1e-3` AND NRMS `1e-4`. NT1 retains existing exact controls. The `root-admission.json` says `tested:false` and `adopted:false`; no numerical or timing cell is qualified yet. A pass would qualify only this bounded synthetic-input fixture, not model adoption, exact NT2–4 equality, or production request behavior.

One correction for capacity accounting: `static_assert(sizeof(ExpertPool) <= 256 KiB)` bounds only the C++ object. It does not include its dynamically allocated worker scratch, `split_`, `split_multi_`, or thread stacks. Those allocations are source-bounded by fixed counts and dimensions, but the asserted 256 KiB is not a transitive pool-memory cap. Root should treat `sizeof(Buffers) * 384 <= 512 MiB`, `sizeof(LayerInput) * 48 <= 8 MiB`, selected blob aggregate `<= 1 GiB`, Q2 local scratch and six-job-array asserts as separate stated bounds, and avoid presenting them as a total process-memory ceiling. The pool object/scratch distinction is the only source-accounting correction I consider necessary before interpreting capacity.

## Source identity and hot/streaming eligibility

The harness reads exactly 192 `train` and 192 `holdout` `(layer, expert)` rows from a bounded TSV. It requires distinct IDs across both cohorts and in-range layer `<48`, expert `<512`. For every selected row, it checks homogeneous GU/Down types, dimensions, row sizes, activation sizes and contiguous blob geometry against the opened role plan. `NativeRolePlan` independently verifies tensor names, type, shape, payload length, bounds, and absolute file offsets against the model's native layout before it copies Gate, Up and Down bytes into the owned blob. It emits each role's source path/tensor/offset/stride and an FNV of every assembled expert blob. The handoff's `selected-real-weight-role-identities.json` records exact source extents and SHA-256 values; source emits identity rows during a root-owned run. Thus hot and streaming refer to the same loaded cohort and exact weight bytes, not separately chosen packs.

Streaming uses all 192 IDs in each cohort. Hot selects cohort ranks `0,24,48,72,96,120,144,168`, exactly eight IDs per cohort; the seed only changes their per-round order. `order_check` verifies size, cohort, range, uniqueness and hot-rank membership. Since there are exactly eight eligible ranks and the checked order has eight unique eligible entries, it covers the full selected hot subset. `HOT_ID` rows preserve source index, real layer/expert and blob hash. All 384 payloads still receive the untimed numerical reference and pool parity pass in hot mode.

The active eight and full 192 use the same seed-dependent SplitMix64 modulo Fisher–Yates schedule implementation. Hot draws fewer numbers because it shuffles eight ranks. Source structure supports the streaming schedule shape, but historical v1 order-hash equality still needs a root-side comparison with the archived records before treating order continuity as verified. This supports a paired *logical working-set geometry* comparison. It is not a pure cache-residency experiment: the job count and bytes per measured arm change by 24x, hot selects a strided subset that may differ in expert weights, correctness prepasses touch all 384 blobs, and the source cannot guarantee hardware cache residency. Compare normalized per-job or per-active-byte service rates; do not call the printed hot footprint a measured L3-resident set or interpret raw total milliseconds as an equal-work contrast. The harness reports whole-cohort and active logical GU/Down/blob bytes separately.

Inputs are deterministic finite floats keyed only by layer and token, not expert/cohort. Native input quantization is checked byte-for-byte against the selected GGML quantizer before references and again outside each timing interval. Therefore each selected expert at a given layer sees the same source activation for that token; hot selection does not alter inputs.

## NT bounds, pointers and memory

The harness caps NT at four, below production `MAXT=8`, with compile-time `kMaxNT=4`. `LayerInput` and every `Buffers` array, including quantized inputs, FF/quantized-FF references and expectations, outputs, staged/full-chain references, pool outputs, guards and pointer arrays, are sized to four. `bind()` checks `1<=NT<=4` and initializes only the active prefix. The fixed-size input and work vectors are fully sized before any pointers are bound and are not resized afterward. Each selected blob is a separate owned vector; the 384-case vector is reserved before population. Pool job descriptors point into these stable owned blobs and buffers and are consumed synchronously. All loops and reference totals use the checked NT prefix.

The blob aggregate check is subtraction-safe under its maintained `aggregate<=1 GiB` invariant; role-plan code separately checks multiplication/addition and mapped tensor extent bounds before pointer construction. The input TSV is limited to 16 KiB and exactly parsed. Paths are limited to 4,096 bytes; decimal positional values are range/overflow checked. NT2–4 gates must be all present before model loading. Tolerance syntax is bounded to 64 characters and finite nonnegative values <=1e6; that ceiling is a parser limit, not the approved budget. Invalid/missing/duplicate/partial options reject before payload preparation.

`Floats<N>` initializes outputs to NaN and checks every active output is finite plus a 64-byte tail guard. `Bytes<N>` initializes the payload and 64-byte guard region, then checks the entire unused tail after the expected byte count. Q2 buffers have a tail canary and geometry/field checks. Input, quantized activation, direct output, pooled output, expected/reference FF and reference outputs are checked before use or after production calls. Output, reference and metadata stream state is flushed and checked before success. Heap bounds for work and inputs are compile-time checked; selected payloads have a runtime aggregate limit. Additional dynamically sized objects also have source-level caps (384 cases/jobs, 48 inputs, 192-entry order, 192-row batch descriptor limit, 384-case reference pass), but they are not all included in the two heap asserts. The pool's transitive dynamic allocations are likewise outside `sizeof(ExpertPool)` as noted above.

## Independent references and numerical coverage

For each of 384 source rows and every active token, the direct path computes native GU/SwiGLU, production FF quantization, and native Down, then checks finite and initialized outputs. The independent GU reference uses GGML scalar Gate and Up dot products on the already byte-checked input activation and computes SwiGLU; it compares all 640 FF values. The staged Down reference quantizes the *actual native FF* through the GGML activation quantizer and independently computes all 2,560 Down rows. This isolates Down arithmetic conditional on actual FF. Separately, the full-chain reference quantizes the independently computed GGML FF and computes all 2,560 Down rows, so actual FF cannot mask upstream GU error. Both references use distinct FF/quantized-FF/output buffers from the native result and carry finite checks and guards.

For NT2–4, each token and each of the three stages emits `REFERENCE_TOKEN` and must satisfy both its stage's maxabs and NRMS gates. The formula is `sqrt(sum((actual-reference)^2)/n) / max(sqrt(sum(reference^2)/n),1e-12)` for NRMS; maxabs is absolute maximum elementwise error. The fixed denominator floor and finite accumulation checks prevent divide-by-zero/NaN pass behavior. `REFERENCE_COUNTS` reconciles `384*NT` tokens, `384*NT*(640+2*2560)` compared row values, and three stage records per token. At NT4 this is 1,536 tokens, 8,847,360 compared values and 4,608 token-stage records. The emitted total and per-stage worst summaries provide independent count checks.

NT1 requires bitwise GU equality to GGML for all formats and bitwise staged Down and independent full-chain Down equality for Down20. Down42 keeps its pre-existing non-bitwise diagnostic reference scope; its production activation-quantizer representation is checked against the selected Q2 quantizer and repeats, but it does not gain a new NT1 full-chain bitwise assertion. This matches the handoff, and should be reported accurately as the existing NT1 control.

The untimed pool prepass runs the pool over all 384 experts before any timing and compares every pool output row bitwise with the independently captured direct output. The direct output itself has the full-chain GGML error gate. Timed pool rounds also compare pool outputs against direct expected output with finite and canary checks. Internal pool scratch intermediates do not have harness canaries, and pool correctness is final-output parity rather than separately emitted pool GU/quant/Down references; this is adequate for a final service-output parity gate but should not be described as independent per-stage pool numerical evidence.

## Timing and pool semantics

Preparation, reference checks, scheduling validation, job descriptor construction, canary/numerical checks, input rechecks, diagnostics and output are outside each measured `steady_clock` interval. The interval encloses the requested direct production calls and bounded order traversal, or the synchronous pool calls. Full means direct GU + FF quantization + Down. Pool invokes `run_split_multi_native` for each batch; that call completes before the end timestamp, including its gate/up row work, activation quantization and Down row work. Pool phase-counter deltas are captured around the interval. No correctness-only rows are emitted as timings.

There are five workers and `host_works=true`; the caller is a sixth participant. `tasks=0` means automatic three row partitions per participating thread, thus 18 row tasks per phase here. Explicit `tasks=6` means up to six row partitions per phase, capped by row count; it is not a six-worker pool. The constructor receives five workers for both values. Batch 6 means six distinct expert jobs per synchronous pool call; hot mode requires batch 1, preventing padded or dropped jobs. Streaming batch 1 and 6 cover equal active jobs because 192 divides by six. The pool is constructed before caller affinity is pinned, then host and five workers are expected on distinct planned singleton CPUs. Source checks the six observed Linux affinities; this is a run-time condition root must confirm. Each cell uses a fresh process, so tasks0 and6 are not changed within one pool lifetime.

The schedule contains 28 orders per cohort: three explicitly labelled warmups plus 25 measured rounds, with each of five arms receiving exactly three warmups and 25 measurements per cohort. Arm order rotates by round and seed. Final assertions require 30 warmup and 250 measurement rows globally and per-cohort/per-arm counts. The row output records active job count, pool batch count, order hash, elapsed time, pool phase deltas, checksum and host CPU. The stream is flushed and checked before success. Root should parse and reconcile these row counts and the cohort-specific order hashes in every receipt rather than rely on `RESULT` alone.

The timing interval excludes host-side validation overhead but every completed round then scans outputs, references and inputs, and each process has a full 384-case prepass. This is a deliberately measured service-call interval under the fixture's repeated-access regime, not request latency or cold-load behavior. Source logs feature-selection environment variables and rejects forced ISA/AVX2, histogram, preload/audit and timing-process loader debug. Other logged dispatch knobs can still affect the selected code path; root must confirm their recorded values match the intended ordinary environment. Frequency, thermal, OS scheduling and concurrent machine load are not controlled by this source.

## Smallest necessary admission gate

Before interpreting a capacity result, require one fresh NT1 correctness-only process to pass its existing exact controls, then fresh NT2–4 correctness-only processes with the already predeclared six values and complete 384-case coverage. For each NT2–4, require all three per-token stage metrics, all count totals, normal exit/output completion, direct/pool output parity, untouched guards, expected two-cohort ID/hash coverage, and no changed source/payload/environment identity. Only then admit a separate fresh timing process with no loader/feature instrumentation and exactly 25 measurement rows per cohort/arm after three warmups. Never adjust gates to fit observations; preserve a failed cell as failed. The predeclared numerical thresholds qualify bounded fixture error only. A nonzero exit, missing/truncated output, wrong counts/order, hash mismatch, guard error, or failed numeric gate is a rejection, not a cell to average away.

No fixture execution was performed by this audit. Source provenance: handoff and `root-admission.json` explicitly state root owns all serial validation and the fixture is untested/unadopted. R224's emitted NT4 stack-spill observation motivates this measurement but supplies no prediction that NT3 or NT4 is faster.
