## Finding

The new B570 device receipt qualifies the `Gemm::f16_event` wrapper for correct FP16/FP16 to FP32 output, completion, and all three SYCL profiling fields on one exact call. It does not qualify the returned event's timestamps as a full oneMKL routine interval or as the service time of production GU/Down calls. The next device discriminator is a narrowly bounded unitrace/PTI capture of isolated production-shaped GEMMs, followed only if that passes by one actual native-expert prefill capture with route coverage reconciled. Until then, the ledger's `returned_event_ms` means the duration attached to the returned SYCL event; it must not be relabeled as full GEMM service.

This distinction follows the contracts. oneMKL defines the USM GEMM return value as an event to wait on to ensure the routine computation completes; it does not specify that the event's SYCL `command_start..command_end` encloses every internal command. SYCL defines those profiling fields for the command group/action associated with the event. PTI must establish whether the installed oneMKL implementation's internal work is one operation or several and whether the returned event span covers it.

## New device evidence and exact boundary

The committed `bench/results/2026-10-10-prefill-service-device-qualification/README.md` and receipts report a successful isolated diagnostic build against byte-pinned cached numerical libraries. The actual B570 check used `Gemm::f16_event` and the unchanged `Gemm::f16` wrapper with `T=7, N=11, K=13, ldy=17`, FP16 inputs and FP32 output. It checked all 119 output floats and padding, completion, and monotone `submit/start/end` values; it exited normally with no fresh fault indication. The returned-event timestamps were `submit=312823995371247`, `start=312823995614270`, `end=312823995623020` ns: submit-to-start is 243,023 ns and the reported event action is 8,750 ns. These are meaningful checks of the wrapper and profiling queries, but the tiny synthetic dimensions say nothing about production algorithm dispatch or internal-command coverage. The qualification stdout explicitly says “not internal kernel coverage”; the trace summary has no visible GPU kernel entries. The diagnostic used a narrow startup/safety environment and is not a clean performance result.

The frozen production seam is correctly narrow: `Gemm::f16_event` passes the same half/half/float oneMKL call arguments as `f16`, with `trans/nontrans`, matrix dimensions `(N,T,K)`, `T=ne`, and `ldy=out`. In the observed native expert fallback, GU supplies `out=1280, inner=model_hidden_width`; Down supplies `out=model_hidden_width, inner=640`. The exact routed row count `ne`, model width/configuration, and route are request data; the small receipt does not establish them. The ledger records each event internally with `(chunk,layer,expert,role,rows,N,K,ldy)` and a local sequence, and checks one GU plus one Down at matching rows for each expected routed pair. Its current public report aggregates by shape and `(chunk,layer,role)`; it does not emit a per-call event table or individual timestamps. Thus it can report call counts and aggregate event duration after a valid full request, but it cannot by itself join a specific returned event to specific PTI operation IDs.

## Interpretation and telemetry limits

`command_submit <= command_start <= command_end` is an event-local validity check. Same-backend SYCL events share a timebase, but the returned event alone is not evidence that all oneMKL internal operations occur between its start and end. A positive interval between sampled event endpoints may include helper/dequantization/activation work, other queue commands, or unclassified time; it is not proof of idle. The host call duration remains a host-clock field and must not be subtracted from device timestamps.

For the full actual-request ledger, preserve exact route denominator and expected pair count; distinguish attempted, submitted, retained, folded, queried, dropped and complete pairs; enforce event and aggregate caps; validate queue/context identity and async errors after the existing synchronization; and suppress all aggregates if any required coverage fails. The current compact aggregates are useful for request shape distribution once valid, but a oneMKL/PTI join requires per-call sequence evidence (or an isolated single-call window). Keep only a compact normalized PTI operation table and receipt after the question is settled; delete raw traces later only with the repository's required path/hash/reason manifest and serialized cleanup.
