## Disposition: one narrow, conditional candidate

Prototype a **same-row-count adjacent-expert oneMKL GEMM batch** in the compiled native-IQ FP16 fallback, limited initially to noncompact, single-device execution and pairs of adjacent active experts with exactly equal routed-row count `ne`. It targets the two per-expert GEMM submissions, not route construction or weight dequantization. The opportunity is concrete but unqualified: source proves a compatible `gemm_batch` helper and two live dequant scratch slots, while no active profiler evidence establishes that GEMM submission overhead is material or that oneMKL implements the batch as fewer device launches. Advance only to a counter/timing discriminator; keep the existing per-expert route as fallback.

This differs from the active-route grouping candidate (R146) and from prior weight-cache, cross-chunk expert-major, or XMX work. R146 establishes that the compiled native-IQ path is host grouped, dequantized to FP16, then passed through `Gemm::f16`/oneMKL; its GPU grouping idea is separately being qualified. R9 already treats `dq_gu/dq_d` as two transient expert scratch slots, not a persistent weight cache. R5 rejects full-context expert-major staging on memory/ordered-combine grounds. The existing XMX source is not the production caller and `docs/INTEL.md` records a different-card 4–5x slowdown against dequant plus oneMKL. I therefore do not nominate XMX, cross-chunk caching, general grouped GEMM with unequal `ne`, or command graphs as a second candidate.

## Active path and exact shapes

At `prefill.cpp:112`, native model geometry is `N=2560`, top-k `K=10`, `NE=512`. The usual layer-major chunk is 8,192 tokens (`:3502` and comments at `:140`); memory pressure can reduce it, so candidate uses actual `T`, not a hard-coded size. For a chunk, the route table contains `T*K` assignments (81,920 at T=8,192). Host grouping counts `m.cnt[e]`, builds expert offsets/order, and calls only for experts with `ne=m.cnt[e]>0` (`:4080–4180`). Thus each expert's GEMM row count is data dependent; do not assert 160 rows or assume equal sizes without measuring the per-layer histogram.

For each active native expert, `compute()` dequantizes its gate/up and down weights to FP16 (`:4778–4785`), then issues:

- gate/up: `X_s[ne,2560] × W_gu[1280,2560]^T`, producing FP32 `GU[ne,1280]`; call `Gemm::f16(...,T=ne,N=1280,K=2560,ldy=1280)` (`prefill.cpp:4799`, `gemm.dp.cpp:750–785`).
- elementwise interleaved SwiGLU on the corresponding `ne×1280` GU rows, writing `Hh[ne,640]` (`prefill.cpp:4800`).
- down: `Hh[ne,640] × W_d[2560,640]^T`, producing FP32 `Dm[ne,2560]`; call `Gemm::f16(...,T=ne,N=2560,K=640,ldy=2560)` (`:4802`).

The column-major oneMKL view is `C^T[N,ne]=W[N,K] (transposed) × X^T[K,ne]`, `lda=K`, `ldb=K`, `ldc=ldy`; `gemm.dp.cpp:776–783` spells this out. `m.compact` gathers each expert's activation rows to row zero (`prefill.cpp:4792–4797`); the initial prototype should exclude compact mode because two independent output row spans and their pointers must be shown disjoint. In noncompact mode each expert's rows occupy its own `o0` segment and outputs have disjoint route-major spans.

The candidate batches two equal-`ne` experts separately for GU and down: first dequant both experts into the existing `DQ=2` pairs of `dq_gu/dq_d` (`:242`, allocation at `:1351`), then submit one pointer-array batch for both GU products, run SwiGLU separately for each disjoint GU segment, then one pointer-array batch for both down products. It does not change dequant arithmetic, the GEMM dimensions, beta=0 semantics, route slot/source mapping, or the final combine's route-rank order. Equal dimensions are a hard eligibility condition; no padding or zero-row GEMMs.

The host batch pointer arrays must remain allocated and unchanged through the returned oneMKL event. Prefer a persistent per-stage two-element array or a call-owned object retained until event completion; do not pass a temporary whose storage expires on return. Keep `dq_gu[q]`, `dq_d[q]`, Xs, GU, Hh, and Dm live until the event(s) that consume them finish. The current ring slot is marked reusable after dequant has read its compressed blob (`:4787–4789`); batching must preserve that ordering and must not delay or move the event before both dequant reads. Dequant, GEMM, SwiGLU, and next pair's scratch overwrite must stay ordered on the same compute queue, or carry explicit event dependencies. A queue wait every pair would erase much of the submission benefit; asynchronous exceptions still need to surface at the existing enclosing wait/error boundary. `gemm_batch_impl` itself keeps its `matrix_info_t` alive until its completion event using a dependent host task (`blas_utils_detail.hpp:372–417`), but caller-owned A/B/C pointer arrays are a separate lifetime obligation.

`GEMM_SCRATCH` is 32M FP16 elements (~64 MiB) and `GEMM_WS=0` for this SYCL wrapper (`prefill.cpp:843–844,1223–1226`); the two expert dequant pairs total 18.75 MiB. A pair-batch uses no full-context tensor and no added dense-weight residency. It should remain within the stated 10 GiB scratch allowance at 256K because it reuses these allocations, but must not quietly add a per-expert cache. The existing 256K path is 32 chunks at 8,192 where that chunk fits; `run_impl` retains one chunk's route/activation/output arrays and advances state chunkwise. The pair scheduler must flush a final singleton, safely handle expert counts of zero, ties crossing the end of the active order, and the last partial chunk. No cross-chunk or cross-layer pointer survives.

## Existing API and external evidence

The active `Gemm::f16` path uses `dpct::blas::gemm` with FP16 A/B, FP32 C, and FP32 compute mode (`gemm.dp.cpp:776–783`). It makes two independent calls per expert; there is no active oneMKL batch call in `prefill.cpp` or `gemm.dp.cpp`. The DPCT compatibility header already has a pointer-array `gemm_batch` wrapper for `real_half, real_half, real_float, real_float` (`sycl/include/dpct/blas_utils.hpp:1078–1224`, especially `:1207–1212`), forwarding to oneMKL's group form in `blas_utils_detail.hpp:372–417`. This is a candidate seam, not evidence that current calls are grouped or that batching is faster.

Intel's oneMKL DPC++ GEMM batch reference documents the USM group API, pointer arrays for A/B/C, shared matrix dimensions/leading dimensions within each group, optional dependencies, an event return, and the output-completion rule ([Intel oneMKL GEMM batch reference, 2025.0](https://www.intel.com/content/www/us/en/docs/onemkl/developer-reference-dpcpp/2025-0/gemm-batch.html), reviewed 2026-10-10). This precisely fits a same-`ne` pair; it does not make unequal-`ne` experts a single group. The ordinary GEMM reference lists FP16 inputs with FP32 output and documents transpose/leading dimension semantics ([Intel oneMKL GEMM reference, 2024.2](https://www.intel.com/content/www/us/en/docs/onemkl/developer-reference-dpcpp/2024-2/gemm.html)). No Intel Xe2-specific author tuning post was found that transfers more directly to these variable-M, streamed expert calls than the official API contract. The official feature reference establishes legality, not performance.

## Numerical/operational risks and smallest discriminator

Batching changes the library submission/selection path and may change floating-point reduction details even though each GEMM remains mathematically independent. Require baseline-vs-batch comparisons of per-expert GU, post-SwiGLU Hh, down Dm, final MoE-combined residual, prompt logits, and saved QSA/GDN/PLE state; record max absolute/relative error, non-finites, and generated-token agreement. Preserve expert row order and each expert's existing row stride exactly. Do not claim bit identity until measured.

First add source counters only in a later authorized implementation: per layer/chunk count active experts, `ne` histogram, adjacent equal-`ne` pairs in expert order, compact/noncompact mode, resident/streamed status, separate GEMM calls versus successful batch calls, dequant calls, and queue events/waits. Compare the standalone baseline and the pair path on the same B570, model/format, cache/ring settings, and prompts at 32K and 256K. Retain 8K chunking where capacity permits. Report `ne` pair eligibility and number of GEMM submissions saved, not a predicted percentage. If same-count adjacent pairs are rare, or batch APIs lower but do not reduce the bottleneck, stop. If they are common, measure batch-call device duration and total MoE/prefill across repeats while checking full parity. No active-path B570 timing or new speed evidence is asserted in this report.

Other factors screened: a general expert-grouped GEMM would need unequal M support and broader staging changes; command-graph capture would have to account for route-dependent dimensions and rotating ring/dequant/output pointers, with rebuild/replay overhead and graph-owned pointer lifetime not established; persistent dense FP16 weights cost 4.6875 GiB per layer and overlap R5/R9. These do not qualify over the bounded equal-M pair experiment.
