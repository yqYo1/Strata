## Finding

I found no arithmetic, bounds, or queue-order defect in the submitted count/scan/place sequence for valid, nonoverlapping typed USM pointers and a stable opt-in configuration. Counts and maps are completed before the caller consumes them; an invalid ID makes the candidate return an error before downstream map consumers. The remaining limits are runtime facts the source cannot establish: whether the exact opt-in binary compiles and runs on the selected Level Zero device, whether its carved raw-USM `int32_t` storage meets the toolchain's object-lifetime interpretation, and whether the root's full parity/fault gates pass. The candidate is private, disabled by default, narrowly eligible, and unmeasured.

## Defined path and bounds

`route_group_scratch_words(E)` accepts only `1 <= E <= 1024` and returns `3E+1`; the view partitions this as `counts[E]`, `offsets[E+1]`, and `fill[E]` (`route_group.hpp:18-22`, `route_group.dp.cpp:19-21`). `shape()` rejects negative `T`, nonpositive `K`, unsupported `E`, `T > INT32_MAX/K`, short ID/slot/src capacities, and absent/short scratch before submission (`route_group.dp.cpp:8-11`). Consequently `T*K` is at most `INT32_MAX` before it is multiplied for the kernel range. The prefix total and each reservation also fit signed 32-bit: their aggregate cannot exceed that route count. The per-element byte extents used by alias checks are at most `4*INT32_MAX`; the configured application is 64-bit Windows/Linux.

Before any queue command, `route_group_submit` rechecks shape and in-order queue, treats `T==0` as a no-op, rejects null maps, checks each `int32_t` alignment, and rejects overlapping or address-wrapping ranges for IDs, slot, src, and scratch (`route_group.dp.cpp:27-34`). The source assumes those nonnull pointers are valid USM allocations associated with the stream context and that declared capacities truthfully describe their backing allocations; it cannot prove pointer provenance or allocation extent. For the integrated call, the three maps and scratch are distinct sequential `Alloc::take` regions; each take includes 256-byte guard/alignment padding (`prefill.cpp:322-342,1347-1354`). This supports, but does not replace, runtime validation of the borrowed arena and typed-USM use.

The three phases are submitted on the same queue: fill counts with zero; relaxed device-scope atomic count of in-range IDs; one-work-item prefix scan initializing offsets and fill; relaxed device-scope atomic placement into each expert's interval, writing `slot[i]` and `src[p]=i/K` (`route_group.dp.cpp:34-41`). `route_group_supported` requires `is_in_order()` and the integration passes `m.cs`; `q_of` resolves that queue pointer (`route_group.dp.cpp:23-25`, `sycl_queue.hpp:11-14`). The caller enqueues the count copy on that same queue and calls `wait_and_throw()` before using counts or proceeding (`prefill.cpp:4117-4125`). Thus relaxed atomics are used only to reserve unique integer positions within each phase; no inter-phase flag publication depends on atomic ordering. This matches SYCL's in-order queue and atomic operation model ([Khronos SYCL queue reference](https://github.khronos.org/SYCL_Reference/iface/queue.html), [Khronos `atomic_ref` reference](https://github.khronos.org/SYCL_Reference/iface/atomic_ref.html)). The source uses queue `wait_and_throw`, the API that waits for submitted commands and reports asynchronous errors ([Khronos SYCL queue reference](https://github.khronos.org/SYCL_Reference/iface/queue.html)).

For every valid ID `e`, the count phase increments `counts[e]`; scan gives `offsets[e]` and initializes the reservation cursor; placement gives a unique `p` in `[offsets[e], offsets[e+1])`, sets `slot[i]=p`, and `src[p]=floor(i/K)`. Placement within an expert is intentionally not stable. IDs outside `[0,E)` are skipped by both kernels (`route_group.dp.cpp:37-40`). The caller then checks each copied count is in `[0,T*K]` and the `int64_t` sum equals `T*K`; otherwise it returns the existing routed-ID error before gather/GEMM/combine consumers (`prefill.cpp:4128-4133`). No invalid-ID map contents are consumed. A submission or asynchronous error propagates; there is no catch/retry/fallback around partially submitted mutable commands (`route_group.dp.cpp:35`, `prefill.cpp:4120-4125`).

## Accounting and lifetime boundaries

With the build option on, count-only `moe_set_bytes()` adds the scratch take only when route grouping is requested and the layout is noncompact/nonfused; `carve()` uses the same predicate/order after the three route maps (`prefill.cpp:1031-1042,1345-1355`). `bytes_needed`, init and relayout use this region-size calculation; carve rejects an undersized region through `Alloc::take` (`prefill.cpp:1305-1313,1410-1449,2016+`). The workspace is the max of its attention and MoE consumers, so this reserves enough for the MoE scratch when that side dominates; it need not increase the total if the other half already sets the max. The assignment handoff records 6,656 accounted bytes for E=512 and 12,800 for E=1024 (logical 6,148 and 12,292 bytes after the allocator's 256-byte guard/rounding). No full-context allocation is introduced; maps and scratch remain per chunk and the same in-order workspace reuse boundary applies.

The descriptor is a typed `int32_t*` into raw device USM carved from the shared region; no placement construction or explicit typed-lifetime operation appears in this source. `Alloc` uses a byte-region pointer and returns typed pointer casts (`prefill.cpp:322-342,1312-1354`). This is a review question for the pinned compiler/SYCL implementation and the C++ object-lifetime model, not a demonstrated violation from source inspection. Runtime must also keep `STRATA_SYCL_ROUTE_GROUP` unchanged across size calculation, init, carve/relayout, and run: the header reads the environment on each call rather than snapshotting it (`route_group.hpp:8-16`; `prefill.cpp:1038-1041,1062,1351-1354,4112`). Changing it mid-lifecycle could make capacity accounting disagree with carve/selection. The handoff explicitly requires a stable environment.

## Opt-in, fallback, and production reachability

`STRATA_SYCL_ROUTE_GROUP` defaults OFF and only adds `route_group.dp.cpp` plus a private compile definition to `strata_prefill` when ON (`CMakeLists.txt:282-286`). When compiled OFF, unset/`0` request the old path and request `1` throws "unavailable in this build" before run work (`route_group.hpp:8-16`; `prefill.cpp:1062`). Malformed values throw. With the option ON, env unset/`0` keeps old sizing/carving/host grouping; env `1` opts in. Shape/capacity/non-in-order failures return false from `supported`, leaving `device_group=false` and preserving host grouping before any candidate submission (`route_group.dp.cpp:23-25`; `prefill.cpp:4112-4118`). The API's later null/alignment/alias checks are not duplicated by `supported`; production carving supplies those pointers from disjoint aligned allocator takes. If those invariants are violated, `submit` throws rather than trying host fallback after submission selection.

The source gate is conservative: whole `run_impl` input `n>=32768`, current chunk `T>=1024`, noncompact, nonfused, non-MMQ, not fused layer mode, native layout with `mmq_gt==21`, no peer/helper/split/stage callback path, full layer range, supported capacities, and in-order queue (`prefill.cpp:4102-4125`). Therefore short tails and all unsupported paths stay host-grouped. The threshold is a prototype eligibility constant, not a measured crossover. For an admitted layer, host counts/order are still derived in expert-ID order from the copied counts; map transfer/upload is skipped, and the preexisting gather/dequant/GEMM path consumes device `src_dev`/`slot_dev` (`prefill.cpp:4211-4261,4295-4297,4770+`). Resident-sort is ineligible for this route because the gate requires `use_mmq==false` (`prefill.cpp:4231-4235`). Runtime instrumentation must still prove the intended branch was selected; environment value and source reachability do not prove execution.
