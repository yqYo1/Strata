## Finding

The implemented route-group path leaves each expert's GEMM dimensions, data types, transpose flags, leading dimensions, beta, and individual Gemm::f16 call structure unchanged. It changes the order of activation rows within an expert: the atomic placement order in src[p] is not stable. No source evidence shows that this row permutation changes oneMKL's shape-based dispatch; the problem size for expert e remains its count ne, and its output interval remains the same prefix-sum interval. But neither mathematical independence of output rows nor oneMKL documentation supplies a contract that results are bitwise invariant when input columns are permuted and results are permuted back. The candidate therefore remains numerically unqualified until root compares actual matrix data and downstream state.

This is distinct from R149's proposed equal-ne gemm_batch: R149 changes the oneMKL API/submission form and might select a different library path. R153 assesses only the already implemented route permutation. Do not combine the two experiments or import a batch result as route-group evidence.

## Active matrix contract

- Gate/up: expert rows ne; output width N=1280; reduction width K=2560; logical operation W[1280,2560] × X[ne,2560]^T, with lda=2560, ldb=2560, and ldc=1280.
- Down: ne; output width N=2560; reduction width K=640; logical operation W[2560,640] × H[ne,640]^T, with lda=640, ldb=640, and ldc=2560.

The call sites are prefill.cpp:4799-4802; ne=m.cnt[e]. swiglu_interleaved consumes the gate/up rows in their current expert-row order and writes the matching Hh rows, then down GEMM consumes that same order. For each expert, root's comparison must match rows by routed token source, undo the row permutation on gate/up output, apply SwiGLU to corresponding rows, compare down output by source, and finally check that the route slot map sends each expert result to the same token/rank. Compare expert GU, post-SwiGLU Hh, Dm, combined residual/logits, and saved recurrent/KV/indexer state. ## What oneMKL does and does not promise

The exact DPCT wrapper maps this call to dpct::blas::gemm (sycl/include/dpct/blas_utils.hpp); the helper passes through transpose, dimensions, pointers, and leading dimensions to oneapi::mkl::blas::column_major::gemm (sycl/include/dpct/detail/blas_utils_detail.hpp). compute_mode::f32 reflects this call's precision request, not a reproducibility promise. Source does not select a oneMKL conditional-numerical-reproducibility (CNR) mode. Establish linked oneMKL version and production CNR/MKL_CBWR configuration before treating any reproducibility mode as in force.

Intel's DPC++ oneMKL reference says ordinary GEMM supports sycl::half inputs and float output and defines matrix storage/leading-dimension rules ([GEMM reference, 2025.0](https://www.intel.com/content/www/us/en/docs/onemkl/developer-reference-dpcpp/2025-0/gemm.html)). Its GEMM batch reference documents pointer-array group calls, shared parameters within a group, and an event that marks output completion; this is relevant to R149, not evidence about the active route-group call ([GEMM batch reference, 2025.0](https://www.intel.com/content/www/us/en/docs/onemkl/developer-reference-dpcpp/2025-0/gemm-batch.html)). Intel's reproducibility reference explicitly notes that floating-point summation order can change results and that CNR gives run-to-run bitwise guarantees only under specified circumstances ([Numerical Reproducibility, 2025.2](https://www.intel.com/content/www/us/en/docs/onemkl/developer-reference-dpcpp/2025-2/numerical-reproducibility.html)). The Intel guide lists GPU BLAS level-3 GEMM and batched extensions at all precisions when CNR is enabled, and limits its guarantee to repeat execution on the same GPU (or matching product names) ([GPU reproducibility conditions](https://www.intel.com/content/www/us/en/docs/onemkl/developer-guide-windows/2024-1/reproducibility-conditions.html)). That is not a documented guarantee that reordered matrix columns produce corresponding bitwise-reordered results, nor that this build has CNR enabled.

Intel's batch-GEMM technical article describes independent GEMMs being issued in one batch and says the library may optimize overall performance ([Introducing Batch GEMM Operations](https://www.intel.com/content/www/us/en/developer/articles/technical/introducing-batch-gemm-operations.html)). It is generic author guidance, not evidence about this variable-row MoE call, this GPU, the active oneMKL version, row-permutation invariance, or a speedup. No author article or sample found establishes a stronger numerical contract than the official references.
