# R151 — narrow active IQ dequant specialization and admission screen

Date: 2026-10-10 (Asia/Tokyo). Read-only review of the fixed WPROBE609a270d source, the current native-expert manifest, R136, R146, R148 and R149. No source edit, compiler/disassembler, build, test, runtime/model execution, GPU, profiler, Git operation, cleanup or capture was performed. No performance result or gain estimate is asserted.

## Finding: reduce R148 to one format, one helper, one caller

R148 proposed removing the runtime format switch from active IQ-to-FP16 dequant kernels. The smallest bounded probe is **only the active type-20 (IQ4_NL) flat/down dequant call** in `iq_dequant_f16()`, by dispatching `t==20` to a compile-time format-20 kernel instantiation while leaving the existing runtime-switch kernel as the fallback for every other accepted type. Do not specialize `dequant_gu_kernel` or other formats in the same experiment.

This is a source-level hypothesis, not an adoption recommendation. It removes only the uniform type switch in `dq_dispatch`; it leaves the per-lane IQ4_NL low/high-nibble branch, the codebook gathers, packed loads, arithmetic and FP16 stores intact. A host-side branch can choose the instantiation because `t` is fixed for the entire launch. This is a single-factor comparison with no new weight format, row layout, kernel tile, buffer, cache, or algorithm. If the compiler already lowers the uniform switch to a cheap uniform branch, or if type-20 dequant is not a measurable part of a selected 32K+ run, there is no reason to keep it.

The specialization should be admitted only when the existing `iq_dequant_f16` argument checks pass (`n % 256 == 0`, `is_iq(t)`), and `t==20`. All other inputs must reach the existing generic path with its current checks. In the production caller, this only applies to `lay.native` experts; non-native formats continue through `blob_dequant_f16` (`prefill.cpp:4778–4785`). The native pack loader separately validates type traits, block geometry and blob size (`src/kernels/cpu/native_expert.cpp:46–74`, `src/kernels/cpu/expert_layout.cpp:389–423`); preserve that policy and do not turn an otherwise rejected pack into a partially handled one.

## Current model IDs and reachability

The read-only manifest `/home/yayoi/.local/share/strata-sycl/packs/qwen3.8-flash-next-iq3_s/native_experts.txt` identifies a 48-layer, 512-expert Qwen3.8-Flash-Next GSQ-RCO IQ3_S pack. Its layer records give GU IDs 18 (17 layers), 21 (10), 22 (20), 23 (1), and Down IDs 20 (39), 42 (9). Thus type 20 is an actual, repeated down-projection format in this pack and is present in 39/48 layers; this is a layer-count exposure fact, not a claim that all experts run or that its time fraction is 39/48. The same manifest also shows why specializing every `is_iq()` case would be broader than this first discriminator. Confirm at run time that the intended request loads this native layout and actually reaches `f.d_type==20`; manifest presence alone does not qualify the path.

The linked production path is explicit: `sycl/CMakeLists.txt:249–262` resolves `iq_kernels.cu` to its migrated translation unit in `strata_kernels`; the active native fallback calls `iq_dequant_f16(f.d_type, ..., f.n_embd*f.n_ff, ...)` at `sycl/src/prefill/prefill.cpp:4778–4785`. R146 establishes the SYCL build uses host route grouping followed by this dequant/GEMM path, with fused/MMQ stubs inactive. At H=2560 and FF=640, type 20's down input has 1,638,400 values, exactly 6,400 256-value dispatch groups. In the active 39 type-20 layers each selected expert's down matrix therefore takes the flat dequant path; do not count all 512 experts as executed without route counters.

Admission layers are distinct. `src/kernels/cpu/native_expert.cpp:46–74` requires GGML dot/activation traits and whole-block shapes; `iq_kernels.dp.cpp:4420–4423` additionally requires supported GU/down qk values, `is_iq` membership, `n_embd % qg == 0`, `n_ff % qd == 0`, `n_embd % 256 == 0`, and `(n_ff*n_embd) % 256 == 0`. `STRATA_D_FMTS` includes type 20 and type 42, while `is_iq` also admits many formats beyond the current model's IDs (`iq_kernels.dp.cpp:771–775,2776–2785`). `iq_dequant_f16` itself is a general helper; type 42/Q2_0 and other allowed IDs must remain on its current generic implementation. `embed_type_supported` additionally accepts type 30 for embeddings, but `is_iq` excludes it, so it is not a candidate dequant case. The compile-time candidate is not allowed to bypass any of these guards.

## Exact source seam and bit-level contract

`dq_dispatch<dst_t>(ty,...)` contains a 19-arm type switch with type 20 routing to `dq_iq4_nl` (`iq_kernels.dp.cpp:2721–2762`). `dequant_flat_kernel` obtains one group index and invokes this dispatch for each of 32 work-items. `iq_dequant_f16` submits one 32-work-item group for each 256 output values after validating `n` and `is_iq(t)` (`:4292–4317`). The candidate is a `t==20` branch in that host entry point, calling an otherwise identical flat-kernel form whose type is a compile-time parameter and whose format-20 arm calls the existing `dq_iq4_nl`; the generic kernel remains the fallback. Keep the same group size, `n/256` grid, group-to-`ibs` mapping, destination offset, stream/queue, `check()` boundary, and FP16 capability check.

The GGML definition is `block_iq4_nl { ggml_half d; uint8_t qs[16]; }`, QK4_NL=32 and size=18 bytes (`third_party/ggml/ggml-common.h:448–452`). One 256-value superblock contains eight such blocks. Each lane maps to `ib=tid/4`, `il=tid%4`; it reads one 8-code nibble run and either the low or high nibbles, multiplies by the same half scale converted to float and `kvalues_iq4nl`, then writes the existing `store_run<half,8>` output (`iq_kernels.dp.cpp:2363–2385,2487–2505`). Keep these expressions, lane mapping, lookup-table bytes, multiplication order and `store_run` unchanged. In particular, compile-time format dispatch must not become a new IQ4_NL implementation or a different conversion path. `sycl/CMakeLists.txt:66` requests `-fp-model=precise`; no flag change is part of this candidate.

A correctness discriminator needs both packed-input corner coverage and the actual model matrix path:

- For a bounded synthetic fixture, cover all 16 IQ4_NL nibble codes in both low- and high-nibble positions, across all `il` values and all eight 32-value blocks in a 256-value superblock. Include patterns where adjacent nibbles differ, so swapped-half, lane, and block-index errors are observable.
- Use scale bit patterns spanning positive/negative zero, smallest/largest subnormal, the subnormal-to-normal boundary, ordinary positive finite values, largest finite, and negative finite values if legal for the pack. For arbitrary NaN/Inf half bit patterns, compare classifications and document that they are outside the valid-pack contract unless the pack validator accepts them; do not claim NaN payload identity unless observed and required.
- Compare every FP16 output bit from the generic baseline and type-20 arm on that fixture, then compare full type-20 down matrices from actual pack bytes for representative active experts. Include all selected rows, not sampled output elements, and compare GU/down GEMM outputs and end-to-end residual/state/logits as later gates. The specialization must be byte-identical at dequant output before any performance comparison is considered.
- Cover the admission boundary: `n=0` behavior as currently defined by caller contract; valid 256-multiple sizes; invalid nonmultiple `n`; type 20 and generic types 42/21/22/23; and non-native format fallback. Preserve current error behavior for invalid arguments.

## What external evidence does and does not establish

Intel's OpenCL GPU Developer Guide says uniform conditions can be converted into compile-time branches through specialization ([Using Specialization in Branching, 2019.4](https://www.intel.com/content/www/us/en/docs/opencl-sdk/developer-guide-processor-graphics/2019-4/using-specialization-in-branching.html)). Intel's oneAPI GPU Optimization Guide explains SYCL specialization constants and shows a STREAM loop where a known trip count enables unrolling; its page includes its own example timings and generated-code discussion ([Specialization Constants, 2024.0](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2024-0/specialization-constants.html)). These provide general compiler mechanisms and a reason to test a uniform runtime switch, but neither measures a format switch in a 32-lane IQ4_NL workgroup or this B570 kernel. The specialization-constant route would introduce JIT/runtime behavior and is not proposed; the candidate uses ordinary compile-time instantiation plus host dispatch.

Upstream [llama.cpp SYCL `convert.cpp`](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-sycl/convert.cpp), accessed 2026-10-10, provides a code-organization precedent: type-specific dequantizer functions are supplied as compile-time template parameters to shared flat conversion kernels, with the host selecting format-specific entry points. That does not establish a measured speedup and is not a direct B570 prefill comparison. No author blog or repository-history measurement was found for removing a uniform runtime format switch from this class of already coalesced IQ4_NL dequantizer. The existing Strata source comment reports that vectorized FP16 stores were already introduced after a Xe dequant-write bottleneck; that source history argues to preserve those stores, but does not establish the current B570 bottleneck or benefit of this dispatch-only change.

## Prior-round overlap and qualification plan

R148 already introduced the broad format-specialization idea; R151 narrows its first experiment to only type 20 Down because it is present in 39 of this pack's 48 layers. It does not add a second mechanism. R149's adjacent-equal-row oneMKL batch idea changes GEMM submission and scratch scheduling, so it is separate and must not be combined with this test. R136 already screened per-format lookup/decode and grouped-kernel architecture ideas in the inactive fused/native-MMQ area; this source screen is restricted to the distinct compiled host-group → flat IQ dequant → oneMKL fallback and reuses existing lookup/store code. The overlap is the general concept of format specialization; the candidate is admitted only as a minimal, measured branch-removal probe, not as a novel decoder or broad rollout.

Root's smallest performance discriminator, after any separate implementation authorization, is one opt-in type-20 `iq_dequant_f16` specialization with generic fallback. First add bounded counters for native vs non-native branch, per-layer `f.d_type`, number of calls/output bytes, actual `n`, and type-20 expert count; this establishes reachability and exposure. Compare the generic and specialized arms on the same B570, IQ3_S pack, ≥32K prompt, chunk size, cache/ring settings and expert stream configuration, with paired repeated runs. Measure the dequant kernel/event duration separately without per-call host waits, plus total MoE and end-to-end prefill; report cold first-use/module/JIT effects separately from steady state. Do not infer savings from removed source branches. Reject the specialization if the active type-20 branch is absent, exact dequant bytes differ, isolated dequant does not improve beyond run variation, or whole-prefill change is within noise/regression. For 256K qualification, retain the existing chunk/carry/state lifecycle and 10-GiB scratch ceiling; no persistent tensors are proposed.
