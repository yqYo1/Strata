# R272 — actual32K route, capacity budget and candidate reach

Date: 2026-10-10 (Asia/Tokyo). Read-only quantitative audit after R270. No build, test, inference, profile, GPU/process/hardware query, state change, cleanup, Git operation, implementation, or additional agent was used. Only this report was written.

## Decision

The completed actual 32K census changes R270's candidate decision: retire the **resident-only small-M direct-IQ prototype as a priority**. Although 49.7% of expert calls have `ne<=80`, just 168 of those calls are resident; 46,319 are staged. The resident candidate therefore reaches 0.18% of all expert calls and 0.036% of routed rows. Its format-weighted isolated expansion-service equivalent is about 21 ms, only 0.20% of the corresponding 10.74-second all-call expansion-service estimate. This is not a bound on possible GEMM savings, which have not been measured by actual `ne`, but there is no evidence to justify an implementation for this narrow resident slice.

A direct packed-IQ path covering staged small-`ne` experts could reach much more of the call histogram, but it would have to keep each staged packed expert alive through both projections. The current path records the slot-use event after dequantization; extending it through GU/SwiGLU/Down changes ring ownership and copy overlap. Treat that as a separate event/lifetime experiment, not as an easy extension of the resident proposal. The joined counts and isolated capacities are sufficient to reject a “small resident experts are the main service bottleneck” claim; they do not select the next performance bottleneck.

## Independent service-capacity terms — keep separate

**Packed-copy payload scenario.** Dividing 190,240,998,400 logical copied bytes by the independent pinned/USM H2D attained rate 6.446833643 GB/s gives 29.51 seconds. The pageable fixture rate 4.605214183 GB/s gives 41.31 seconds; the encoded Gen4x4 external-link ceiling 7.876923077 GB/s gives 24.15 seconds. These are conditional payload service-time comparisons for the census byte total. They are not the model's observed copy duration, an absolute lower/upper bound for its transfers, or proof that the DMA engine was busy for that interval. Actual source mix, submission granularity, transfer-completion intervals, caching and overlap all matter.

**Generic-IQ expansion scenario.** The isolated seven-pair fixture reports end-to-end host-submit-plus-completion medians per expert (GU and Down expansion together) of 129.134, 99.681, 115.101, 75.876, 114.156, 76.033, and 207.700 microseconds for the pair order above. Multiplying each pair's actual census calls by its paired median and summing gives 10.743 seconds of *capacity-equivalent expansion service*. Substituting the reported process-median ranges yields 10.333–10.828 seconds. This arithmetic uses all 93,505 actual format-pair calls, with no row-size interpolation. The fixture used device-resident packed weights, three fresh processes and seven samples/process; its O2 AOT build is not the production O3 build. It is neither an exclusive model-phase measurement nor proof that production expansion takes this sum.

The same `ne<=80`, `source=3` call slice has a format-weighted expansion-service equivalent of 5.345 seconds (5.143–5.386 seconds using process-median ranges); resident `ne<=80` has 0.0210 seconds (0.0204–0.0212). These explain candidate reach, not achievable savings. They must not be added to the 29.51-second copy scenario: those operations may overlap, and the existing copy and compute completion structure must be measured in the actual run.

The join separately reports 919,191,552,000 logical bytes written by GU+Down FP16 expansion for all calls. This is output-byte accounting, not a third transfer stream to add to packed input bytes or to the isolated service estimates. GEMM may subsequently read these matrices, but its actual memory traffic and caching are unmeasured here.

## Budget model for the next critical-path decision

For one exact, clean matched request, define observed service spans from qualified completion events, but compute request wall time from the application clock. Partition device compute spans into DQ-GU, DQ-Down, GU GEMM, SwiGLU, and Down GEMM; retain host submission/route preparation; separately record successful staged-copy completion spans and queue waits. For each item, preserve the owner queue, source, expert/pair/`ne`, start/end event, and whether its interval overlaps another item. Report both summed service time by class and the union of intervals on each independent engine/queue. The sum describes work volume; interval unions and dependencies describe exposed wall time. Never sum overlapping H2D and compute durations as if serial, count a host wait again as device execution, or count the expansion output bytes as H2D payload.

The source gives ordered dependencies within each expert: native GU and Down dequantization feed the GU GEMM, SwiGLU, then Down GEMM; the staged expert's packed blob is currently released after the dequant reads. This does not supply actual command durations or prove phase exclusivity. The queue property and event ownership in the production binary must be taken from the already-owned service-event qualification, not inferred from census counters. A source route's logical `transfer_calls` is not an H2D active-time counter.

Do not form a `29.51 + 10.74 = request seconds` estimate: data transfer and compute can overlap and both rates come from isolated fixtures. Do not infer GEMM time from the M=80 capacity sample, `weighted_mean_rows_per_expert=168.21`, a bucket midpoint, or another “nearest” expert size. A correct upper bound on request wall time or on candidate headroom is not available until same-run measured timings exist.

## Measurements that would change the decision

Main is continuing default-off parity, service-event qualification, and repeated clean matched `>=32K` timing. For the first performance-eligible matched sample, the useful minimum is:

1. Clean application wall time with prompt/tokenizer/model/build/config identities and repeated individual samples; exclude the diagnostic route-census run and its long trace.
2. Actual production-build paired completion spans for dequant GU/Down and GEMM GU/Down at the *observed exact* `(format, ne)` bins, plus SwiGLU and host-submit spans. Keep enough samples to report variation; no interpolation from the existing M=80 or O2 data.
3. Staged-copy submit-to-completion spans and successful payload by source, and a same-run overlap/dependency timeline that can distinguish copy-only, compute-only, overlapped, and wait intervals. Preserve the qualified event owner and do not insert waits just to make timings easy.
4. A joined attribution table: number of calls, rows, logical bytes, sum of measured service by category, engine/queue interval union, and the uninstrumented request wall. If profile instrumentation perturbs the request, keep it separate and use the uninstrumented sample for performance.

Only consider expanding the R270 direct-IQ work beyond the resident slice if those data show dequant is materially exposed on the actual critical path. For a staged implementation, also quantify the ring occupancy and lost/retained copy overlap when its release event moves from after dequant to after Down. If copy overlap is already the limiting exposed segment, a small-M kernel that lengthens slot hold time could regress the service even if its isolated device kernel is faster.
