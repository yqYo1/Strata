The captured workers are not in the host `memcpy`/GGUF-read path or asleep on the Stager condition variable. There are no symbols/locals showing the event handles, generation values or return statuses, and the saved stack is a single captured state. ## Exact application protocol that reaches the query

In the pinned source, `STRATA_PREFILL_SERVICE_TIMING` makes `Prefill::init` construct `m.copy` with queue profiling enabled. It also enables the returned-event ledgers. `ExpertServiceLedger::record` retains the returned copy event in `pending`; it submits no marker or wait. The same `q->memcpy` result is then passed to `Stager::issued_one`, which stores it in `done_seq[slot]` with an increasing generation before publishing `issued=j+1` to the Stager workers.

A Stager worker processes a host job in this order: wait until the job preceding this buffer's last DMA has been issued; call `buffer_free(slot)`; copy/read the expert blob into the host buffer; publish `ready[j]=1`. `buffer_free` calls `event_completed(done_seq, want, dma_completed)`. `event_completed` first checks the cached completed generation, then holds the completion-state mutex while asking `sycl::event::get_info<command_execution_status>()`; only a successful `complete` answer advances the cached generation. `Stager::wait(j)` on the request thread polls `ready[j]` and yields until a worker publishes it.

This ordering narrows what can be said. A worker does not query a buffer generation until its preceding DMA has been submitted by the issuer and its event has been retained/published by `issued_one`; thus this is not a query of a host job for which the application has not yet called `queue::memcpy`. The worker may quite normally find that already-submitted command still not complete. That should be a returned non-complete status so the worker can retry. The saved stack shows the query call did not return at capture. It does **not** establish whether the command had reached hardware, was merely submitted/queued, had signaled, or what `ze_result_t` would have been.

`STRATA_PREFILL_SERVICE_TIMING` also retains a second copy of each returned event in the ledger until later fold. This may extend the event object's host lifetime, but does not itself issue another queue command or status query at copy submission. The saved stack and missing locals do not implicate this extra reference as a lifetime fault. Source ownership keeps the copy queue, `Stager`, event-completion state and worker threads alive during the request; the staging buffer is not reused unless completion polling acknowledges its prior generation. No application use-after-free or premature buffer reuse is demonstrated.

There is an important flag interaction: `STRATA_PREFILL_TRANSFER_TIMING` also enables copy-queue profiling, while it additionally measures host copy time. The present failure used `SERVICE_TIMING`; `Stager::measure_copies` is enabled only by `TRANSFER_TIMING`, so the measured host-copy timer is not the differentiating behavior in this run. The queue profiling property and event-ledger retention are the relevant source-level differences. The prior default-off and route-census passes did not profile the copy queue, so they show the ordinary unprofiled route works once, but do not establish which of those two profiling changes triggers the stall.

## API contracts and version boundary

SYCL 2020 defines `event::get_info<info::event::command_execution_status>` as a status query returning `submitted`, `running` or `complete`; a status query is distinct from `get_profiling_info(command_start/command_end)`. The saved frame is the former. Profiling start/end queries have their own specified blocking behavior; no such timestamp-query frame appears here. [Khronos SYCL 2020, event information and profiling descriptors](https://registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html)

Level Zero specifies `zeEventQueryStatus` as a host event-status query whose implementation **should be lock-free**, and permits `ZE_RESULT_NOT_READY` for an unsignaled event. `zeEventHostSynchronize` is the separate waiting API with an explicit timeout parameter. This supports the expectation that a not-yet-complete event should be polled as not-ready; it does not prove this installed stack followed that path. [Level Zero event API](https://oneapi-src.github.io/level-zero-spec/level-zero/latest/core/api/apis/event.html)

The closest public NEO implementation audited previously is compute-runtime `26.31.39395.13`; the selected host package is `libze-intel-gpu1 26.31.39395.14-1~24.04~ppa1`. Exact `.14` source/package patch equivalence is not established, and no exact `.14` upstream release source was found in the reviewed evidence. In `.13`, the public `zeEventQueryStatus` entry point dispatches `event->queryStatus(0)`. The normal event packet and counter-based query paths pass `blockOnMiss=false` to `WaitUtils::pollFunctionWithPredicate`; that path performs a bounded pause/check and can return `ZE_RESULT_NOT_READY` rather than blocking until signal. This describes `.13` source only. It is not proof for the installed `.14` binary, the validation-layer wrapper, or the `urEventGetInfo` implementation loaded at the time of the failure.

The stack includes `libze_validation_layer.so` and the `.14` driver library, but the failure file has no debug symbols for those internal frames and no exact installed `.14` source or matching public issue demonstrating this particular single-B570 Stager stall. A different Strata report (#867 / fix #866) documents a B60 multi-GPU graph/ring path where an event never rang after the graph; later #1054 reports a separate two-B70 multi-GPU startup spin, with its author explicitly leaving a host-mapped visibility guess unverified. Those cases are useful precedent that Level Zero V2/event-poll interactions have caused Strata-specific stalls, but their hardware, path and evidence differ; neither identifies this single-GPU copy-queue status stall. [Strata #867](https://github.com/Niko1221/Strata/issues/867), [fix #866](https://github.com/Niko1221/Strata/pull/866), [separate #1054](https://github.com/Niko1221/Strata/issues/1054).

## Distinguishing the candidate mechanisms

- **Never submitted vs. submitted but not signaled:** Source order proves `queue::memcpy` returned and `issued_one` published an event before the worker passes the preceding-issued gate and queries that generation. It does not prove the device started the command. A future bounded diagnostic needs only scalar per-ring sequence facts at the existing submission/publication boundary plus the selected event's returned status after a safely bounded query; do not infer hardware submission from `issued_one` alone. If the query cannot return, its absence of a status is itself the only observed fact.
- **Status API stuck vs. timestamp behavior:** Current captured frame is `command_execution_status` through UR event info, not a profiling timestamp retrieval. Profiling changes queue/event creation mode, but the event-status query is still the specific blocking stack. A returned `submitted/running/complete` status followed by a later `command_start/end` stall would be a different failure; this capture has no timestamp-query call.
- **Producer starvation vs. completion poll:** At capture, all three Stager workers are within the event-status query and the request thread is waiting for host-buffer readiness. They are not all asleep awaiting work or blocked in GGUF/file reads. The immediate application-level chain is therefore worker status-query nonreturn → no ready host slot → request-thread spin. A missing/slow device copy could explain why a *returned* status remains not-ready, but cannot explain why the current status call itself is still inside UR/validation/driver when captured.
- **Application event or buffer lifetime:** The code stores a shared `EventCompletion`, a copied `sycl::event`, and a monotonically increasing generation under a mutex; it does not acknowledge false/throwing query results or reuse the source buffer before completion. The queue and stager outlive the active request. The extra ledger reference retains an event longer. The capture has no event address, generation, destruction stack, freed-buffer evidence or returned API error. Thus a host-lifetime defect remains possible in principle but has no positive evidence here.
- **Driver/validation/UR internal stall:** Three simultaneous workers stop at the same wrapper/driver status chain. This makes the API path the observed location and a candidate shared internal lock/wait, but one stack snapshot cannot decide whether they share one event, contend on a lock, or each wait in separate polls. The installed `.14` source and internal frame symbols are unavailable; do not label it a `.14` driver bug.

## Safe diagnostic and instrumentation boundary

The main's source-only GEMM-only measurement flag is the appropriate next isolation: profile only the compute/GEMM queue and leave the copy queue unprofiled, with the normal Stager completion protocol and no additional command or wait. This answers whether useful GEMM timing can be collected without enabling the copy-event mode implicated by the current capture. It does not answer copy active time.

For copy context without changing the Stager dependency protocol, use measurements already available at host boundaries: job-copy worker duration, host wait for stager readiness, copy submission duration, and wall duration of an existing layer/chunk copy-queue wait. Label the last as a layer/chunk copy-queue envelope (including idle gaps/other queued work), not per-copy DMA service. Keep logical byte counts separate from active transfer time. Do not call `get_profiling_info` on unprofiled events or add a host task/event to the copy queue.

If per-command copy duration remains necessary, first isolate a single preallocated copy plus one retained event in a separate, finite, owner-controlled driver qualification using the installed runtime stack, with an external deadline and preserved raw result/stack. Vary queue profiling and validation-layer selection one dimension at a time, and establish status-query behavior on an incomplete event and after an existing explicit completion boundary. This is a future diagnosis proposal, not authorization for this agent to run it or to repeat the failed model request. No validation-layer removal or runtime workaround is adopted here.
