## What can request a larger chunk now

The CLI already has an opt-in larger auto ceiling: `--prefill auto:16384`, `--prefill auto:32768`, or `STRATA_PREFILL_AUTO_MAX`; bare `--prefill auto` stays capped at 8,192. The parser clamps the requested ceiling to 8,192/16,384/32,768, and the auto planner also caps it at `max_context`. The documented current candidate ceiling is therefore 32,768, not an arbitrary larger value. For an auto plan using the expert-cache loan, `Prefill::bytes_needed` determines the exact slots for each candidate; it scans downward to the largest size whose loan leaves at least 128 slots and satisfies the auto lend-percent rule. The code then narrows a chunk to the request length if appropriate and relayouts the last shorter chunk. A fixed chunk follows different fit behavior and can fall back to its own buffers.

`Prefill::carve` allocates a large number of arrays proportional to `T`, plus a shared region sized as the maximum of the HC, PLE, GDN, QSA and MoE workspaces. Several state/index tables are also `T * K` or `T * cap`. Thus 16,384 roughly doubles chunk-dependent terms from 8,192; 32,768 roughly quadruples them. These are source-level scaling estimates only: the measured 8,192 `accounted` and `shared` numbers cannot be scaled into allocator-fit proof because fixed GEMM/ring allocations, layout selection, sharing, rounding and cache-loan capacity matter. `Prefill::init` either carves the passed borrowed cache span or allocates owned device buffers; allocation errors report the failing buffer and current free bytes. Neither code nor the completed evidence establishes that 16K or 32K fits this 10-GiB B570.

The source has no evidence of an unconditional engine-level 8,192 kernel cap: `T` and the principal buffer calculations use `size_t`/`int64_t`, and 16K/32K are explicit opt-in chunk values. Some interfaces narrow values to `int`/`int32_t` (for example embedding gather length and QSA diagnostic headers); 32,768 tokens and 262,144 positions remain below signed 32-bit range. QSA also sizes token-by-selection arrays from `T * cap` and context-dependent `max_blocks`, so device capacity is the practical gate. The prompt attention launch batch is separately capped at 1,024 (default 32); increasing the prefill chunk does not increase that per-launch batch. No source-only reading proves every backend grid/driver limit at a 32K chunk; treat 32K as the repository's declared experiment ceiling, subject to runtime allocation and correctness checks.

At a 262,144-token prompt, generation deliberately sets `n_batched = n_prompt - 1`: positions 0 through 262,142 are conditioned in prefill, and the final prompt token at position 262,143 is processed through the normal token/first-verify path. This is not padding the input to a power of two. At 16K/32K, the loop processes a shorter final chunk and keeps the same last-token rule. The chunk can therefore be below the context size without changing context capacity; the session's full KV/state allocations remain a separate large fixed cost. Existing source keeps PLE's two-token recurrence across chunks and resets `ple_prev` to the two tokens before `pos_start` for the token path. QSA/GDN state and KV pages are updated during prefill. A full-context qualification must compare these states and final-token behavior; the 32K census did not test that boundary.

## Decode/draft release mechanisms and their real placement

The draft-weight release is an opt-in (`STRATA_PREFILL_RELEASE_DRAFT`) implemented by `MtpDrafter::suspend_decode_weights`/`restore_decode_weights`. The owning caller installs the callbacks after `Prefill::init` and before `Prefill::run`; the release callback is reached only when `run_layer_major` is selected. That route requires a full single-GPU compact path, a valid source, all main QSA K/V pages resident in VRAM, and no PLE preload. It is selected explicitly by `STRATA_PREFILL_LAYER_MAJOR`; mode 1 uses it when the request spans multiple chunks, mode 2 forces it. The ordinary 8K/16K `run_impl` path does not invoke the decode-suspend callback.

When entered, `run_layer_major` waits for device queues, checks that complete immutable RAM copies of the draft expert/head payloads exist, optionally verifies the current bytes, drops all draft graphs/command lists, then shrinks draft expert and head storage. It keeps the drafter's dense projection data, K/V/state arena, scratch, and queues. On restoration it grows storage, requires the original virtual addresses, copies back the immutable payload, optionally verifies it, and permits draft graphs to be recaptured. `draft()` and `draft_first()` restore suspended weights before decode. This is the source-supported shape for freeing only decode weights while preserving draft state, but the saved copy must exist and restoration must complete before speculative/token decode. Failure is intentionally fail-closed (the RAII paths terminate rather than replay a graph against released memory). The source does not show a release amount for the B570 run; the startup's `834 MiB` draft line includes experts and dense data, while the 212.9-MiB head is logged separately. Since dense/state allocations remain, do not call their sum the released amount; the runtime release log reports the actual mapped expert/head bytes.

Prompt MTP state has to survive this lease. The prefill route's `draft_kv` consumes named MTP dense tensors and writes the drafter's existing K/V state; its source does not use the draft head or MoE expert storage in that path. If `draft_kv` declines, the MTP prefill route also updates K/V before ordinary decode. Keep dense tensors, K/V state, token positions and PLE/QSA state resident. Do not bypass the prompt MTP callback or discard recurrent state merely to obtain memory. A future change moving the lease before `Prefill::init` must keep the MTP K/V update path functional while those decode-only weights are absent, then restore/verify before first draft generation.

There is a separate `STRATA_PREFILL_RELEASE_CACHE` lease in `run_layer_major`. It waits queues, snapshots the released expert-cache tail or records resident RAM spans, retires graph/backend references through callbacks, shrinks cache backing, then grows it back at the same address/slot geometry and restores the exact bytes (optionally verified) before refreshing decode pointers. This runs after `Prefill::init`, too. The prompt buffer loan is taken from the top/end of the expert cache (`device_slot(first)`); the current lease can shrink that same cache while the loaned workspace is live. Source alone does not demonstrate that the active prefill workspace is disjoint from backing removed by the cache lease. Do not combine cache release with a borrowed prefill span until that alias/lifetime is established. With `--no-prefill-borrow`, owned prefill buffers do not alias the cache, but those buffers are already allocated before the cache lease runs, so cache release still does not create the headroom needed to allocate them. This cache lease is not a path to make `Prefill::init` fit a larger chunk without changing allocation order and proving non-overlap.

## Minimal prefill-only candidate set for later qualification

1. First try the existing explicit opt-in `--prefill auto:16384`, leaving draft/cache lifecycle and default settings unchanged. It is eligible only if the existing exact auto loan/admission actually selects 16,384 and preserves the 128-slot floor, or if an owned-buffer allocation succeeds at init. This isolates the chunk-size question and is the smallest source-supported candidate. The ordinary baseline remains `auto`/8,192. Do not call a requested ceiling a selected chunk: record the actual selection and actual chunks.

2. If candidate 1 is admission-limited by lack of cache loan and host RAM contains the complete immutable MTP expert/head copies, a later narrowly scoped change could bind/prepare the MTP lease before prefill allocation, retire its graphs, suspend only expert/head storage, allocate/run prefill with the dense MTP and recurrent state intact, then restore same-address bytes and graphs before decode. Keep this prefill-only and opt-in; use 16,384 first, then only consider 32,768 if the 16K allocation and exact state/output gates pass. This may recover only the measured mapped draft expert/head allocations and does not itself increase cache slots. It is not implemented by the current callback placement, cannot be assumed to solve an init OOM, and must not be paired with cache release while a borrowed span aliases the cache. If more space is needed after those facts are measured, stop and redesign the ownership/lease sequence rather than stacking speculative releases.

For either candidate, qualify with one BDF/device, immutable model/weights, same full-context rotary/YaRN settings, prompt, cache admission and route; record exact allocated workspace, high-water/free memory, chunks, status, host wall time, route census, and output. Compare QSA K/V pages/state hashes and GDN recurrent state including both `ple_prev` values, the MTP K/V state, final prompt-token handling, output tokens, and decode speed after restoration. On cancellation or allocation/copy/verification failure, restoration must run before any graph replay; otherwise fail closed. Preserve the no-fault/overflow conditions from the 32K census. A passing 32K context census does not substitute for a 262,144-context run, and logical expert transfer bytes/census counts do not measure physical DRAM traffic or predict bandwidth.

No larger-chunk or release candidate was run. Remaining blockers are exact linked-binary/source reconciliation, whether the actual B570 memory loan or own-buffer path admits 16K, actual mapped draft bytes reclaimable on this host, and correctness/performance at the target full context.
