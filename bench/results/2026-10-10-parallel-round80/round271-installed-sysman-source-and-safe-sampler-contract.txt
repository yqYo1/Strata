## BMG eligibility and returned values in the matched source

The `.14` modern Linux implementation `LinuxMemoryImp::getBandwidth` delegates to `SysmanProductHelper::getMemoryBandwidth`; it is separate from the older `level_zero/tools/source/sysman/...` path. The modern Sysman driver creates memory handles for the device/subdevices, and BMG's `SysmanProductHelperHw<IGFX_BMG>` specialization is in the matched helper file. This is the standalone `zesInit` route discussed in the accepted round-269 report. The separate old `zeInit`-attached tools route and its model checks do not gate this modern helper.

The BMG helper searches telemetry nodes beneath that device's PCI root path. It accepts the BMG PUNIT GUIDs `0x1e2f8200`/`01`/`02` and OOBMSM GUID `0x5e2f8210`. OOBMSM carries `MSU_BITMASK`, per-GDDR-channel GT/SOC 32-byte and 64-byte request counters, and max-bandwidth data; the helper sums only MSUs selected by the bitmask, across up to eight MSUs. It packs each low/high 32-bit register pair to a 64-bit counter and multiplies each `_32B_` value by 32 or each `_64B_` value by 64 exactly once before adding it to `readCounter` or `writeCounter`. Therefore a successful `zesMemoryGetBandwidth` result already contains byte totals. Never multiply the API counters or their deltas by 32/64 again.

The helper separately reads `VRAM_BANDWIDTH`, shifts the field, and converts its 100-Mbps units to bytes/sec for `maxBandwidth`. That is a reported limit, not observed traffic and not a scaling factor for the cumulative counters. The timestamp is `SysmanDevice::getSysmanTimestamp()` in microseconds. The API result represents selected PMT memory-request counters, not application bytes; cache reuse, writeback/expansion, compute loads, rendering/display traffic, other applications, and allocator/runtime activity can all make physical request bytes differ from logical bytes.

Eligibility/error behavior from this source is conditional, not unconditional: no telemetry nodes or no recognized GUID/key map returns `ZE_RESULT_ERROR_UNSUPPORTED_FEATURE`; PMT reads may return their underlying error; a failed `MSU_BITMASK`, register pair, or max-bandwidth read returns an error (counter/max subpaths return `ZE_RESULT_ERROR_NOT_AVAILABLE`). A zero MSU bitmask can yield a successful zero counter reading, so success alone is not evidence of a changing, useful counter. Missing required `GDDR<n>_*` keys for a selected MSU also makes the read unavailable. Runtime should enumerate the intended device by PCI BDF, enumerate its memory handles, and require two successful, valid readings before treating sampling as usable.

## Minimal safe sampler contract for a later qualification

Keep the sampler read-only and bounded to one chosen BMG adapter. Call standalone `zesInit`, enumerate Sysman devices, identify the target by full PCI BDF, enumerate memory handles, and select exactly one handle for that adapter. Record the handle count and returned memory location/subdevice metadata. Do not sum values across handles or across PMT nodes: BMG's helper already aggregates selected MSUs and does not establish that multiple Sysman handles expose disjoint totals. If handles appear per subdevice and the API gives no way to establish disjoint counter scope, report that ambiguity rather than double-counting.

Take exactly two successful `zesMemoryGetBandwidth` snapshots on the same selected handle around one already-bounded workload window. Record both raw API structs, monotonic host start/end timestamps, result codes, BDF, UUID, handle/subdevice identity, API/driver versions, and workload's logical bytes and direction. Do not add queue settings, environment changes, resets, or telemetry writes. Use the API's own microsecond timestamp delta for the reported counter rate; also use host monotonic time to define the wall window and detect a stalled/reset API timestamp. Require `timestamp2 > timestamp1`. If timestamp decreases, repeats, or otherwise resets, reject the interval; do not substitute an arbitrary delay or combine across reset.

For each counter, use direct unsigned subtraction only when the second value is not smaller. If it decreases, treat it as reset/wrap and discard this two-sample interval unless the implementation's effective width and single-wrap interpretation are independently established. The public struct's `uint64_t` field width alone does not prove the hardware counter width. Although the BMG source assembles 64-bit register values, it does not expose a BMG valid-bit-width contract through this helper. A minimal qualification should therefore avoid guessing a 32-bit wrap or silently repairing a decrease. Keep `deltaReadBytes` and `deltaWriteBytes` separate; total physical-counter traffic is their sum. Rate is `(deltaReadBytes + deltaWriteBytes) / (timestampDeltaMicroseconds * 1e-6)` bytes/sec. Preserve the raw samples and validity decision.

Compare that physical-byte delta/rate with the workload's application logical-byte count as two distinct measures. For a copy, state whether logical bytes denote bytes copied once or expected read-plus-write bytes (often 2× the copy size), and do not present either as guaranteed DRAM traffic. For inference, use the exact actual model/workload window and count logical model/input/output bytes separately if available; do not infer physical bytes from parameter count. `maxBandwidth` is only the device-reported ceiling/context. It may sanity-check an observed rate but is not a target, measured traffic, or denominator that turns logical bytes into bandwidth.

A practical first qualification is an idle pair followed by one finite known-byte device-local copy window using already-supported application defaults, with completion fenced before the second sample, then a matching idle pair. The copy is a signal check, not a calibration equation: device writes/reads and caches can alter the physical/logical ratio. Require a positive active-window delta materially above idle drift, consistent counter direction, stable BDF/handle, successful status, and a positive timestamp interval. Preserve negative/flat or unsupported readings as results; do not rescale the counters to force agreement. If any eligibility, monotonicity, or attribution condition fails, mark Sysman sampling unavailable/ambiguous and keep the model comparison based on host wall time and logical throughput.

No BMG runtime sample was executed in this round. The remaining uncertainty is whether the installed shared library is byte-for-byte the PPA-built output and whether this host's live KMD exposes the expected telemetry nodes/GUIDs and changing counters; only a later, explicitly bounded read-only runtime qualification can answer that.
