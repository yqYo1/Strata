## Decision

In the non-MMQ native-IQ `compute` arm, `iq_dequant_gu_f16` expands the packed GU weights and `iq_dequant_f16` expands Down into one of two rotating DQ slots; the existing event on a streamed slot is recorded after those reads. It then calls `Gemm::f16` for GU over this expert's compact `ne × H` rows, applies SwiGLU, and calls `Gemm::f16` for Down over `ne × FF`, writing the expert's rows into `Dm`. This is an expert-at-a-time sequence on the existing queue. The alternate MMQ branch gathers weights and runs grouped quantized products; it is not the generic-IQ path and must not be combined into this proposal. Build-time fused stubs are not evidence of an active native fused route.

The fixed service geometry in the inspected caller is normally `H=2560`, `FF=640`, `K=10`, with format-specific native dimensions/offsets from `lay.fmt[l]`. The per-expert `ne` is the routed-row count from the current chunk, not request token count. The current materialized FP16 GU extent is `4*H*FF` bytes (about 6.55 MB) and Down is `2*H*FF` bytes (about 3.28 MB) for the standard geometry; together, roughly 9.83 MB is expanded for each routed expert on each chunk. The independently qualified seven-pair probe measures generic IQ expansion at 75.88–207.70 µs/expert wall (host submit plus completion wait) on Ryzen 5 5600X / Arc B570, with data-resident weights. This is component evidence only: it does not isolate the production critical path, establish a per-format model bottleneck, or imply an end-to-end gain. Its compiled/report scope is `bench/results/2026-10-10-gpu-iq-dequant-capacity/three-process-summary.json` and the hardware guide records the qualifications.

## Candidate: resident-only, small-M direct packed-IQ projection

If the actual histogram shows that a meaningful number of generic-IQ calls lie in a small-`ne` region, first prototype only resident experts (`source=resident`) for one selected native format/pair. Have a direct packed-weight kernel consume the existing native blob sections and compute the projection without writing a full FP16 matrix. The GU result still needs the established FP16 rounding contract before SwiGLU; Down must preserve its FP16 weight conversion and FP32 GEMM accumulation/output semantics. Reuse existing route offsets, compact activation rows, output row destinations, and the current in-order queue. Dispatch only on the census-qualified format and `ne` range; preserve exact fallback otherwise.

This is supported as a direction by llama.cpp's CUDA backend, which has a dedicated MMVQ route, per-format IQ2/IQ3 vecdot implementations, and type/architecture/batch eligibility logic (`mmvq.cu`, `ggml-cuda.cu`). That is evidence that a low-batch quantized matrix-vector path is a recognized engine design, not evidence for SYCL legality or speed on Arc B570. The CUDA source's IQ block handling and accumulation contract must not be transplanted without checking against Strata's native block layout and arithmetic.

The resident-only restriction is deliberate. In the current streamed path, `m.used[slot]` allows the packed staging slot to be reused as soon as dequantization has consumed the blob. A direct kernel would keep reading packed GU/Down bytes through the projection work; the slot-release event would have to move until the last read completes. Changing that ownership boundary is a separate safety change and is excluded from the first candidate. For the resident source, the layer cache keeps the packed blob in device memory across the current call and subsequent chunks; the existing chunk-local DQ scratch can remain unchanged for fallback calls.

Minimal qualification: select a real census bin, then compare only its actual format and observed `ne` values against the existing generic route using the same inputs. Prove packed-byte bounds, route/output scatter identity, GU FP16 rounding, Down FP16-weight/FP32-accumulate behavior, full output parity under the project's numerical gate, completion before packed/cache lifetime ends, and no effect on following layer/state. Include correctness for zero/tail and neighboring `ne` values. Time the whole per-expert submission/completion and the full request in repeated fresh-process comparisons; report every sample. Advance only if that exact bin recurs in the true 32K route and improvement exceeds run variation without extra memory admission or numerical regressions. No percentage or speedup threshold is inferable from current component data.

## Rejected as first step: retain expanded expert weights across chunks

Packed expert blobs are already retained in the layer-major cache across chunks; prior source audit R219 records this explicitly. Expanded FP16 matrices are different: generic native route dequantizes each routed expert per chunk and reuses only two rotating DQ slots. Retaining expanded matrices would require a new cache sized per expert, admission/eviction policy, residency and error ownership, and measured VRAM headroom. The normal GU-plus-Down FP16 matrices total roughly 9.83 MB/expert; even a small cache of 16 experts would be about 150 MiB before alignment/allocator overhead. No current per-request peak-memory receipt or repeated-hot-expert census justifies that cost. Cross-chunk route/GEMM batching additionally changes route/output retention; R219 calculates that a full-request routed `Dm` envelope is 25 GiB for the standard geometry. Neither is a minimal service change on present evidence.
