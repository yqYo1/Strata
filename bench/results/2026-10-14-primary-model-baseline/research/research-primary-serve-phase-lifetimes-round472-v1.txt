R472 — primary HTTP serve phase and persistent allocation lifetime correction

Scope
Source-only correction to R471 for the currently selected primary Main path. I read the configured engine source, the HTTP job/wrapper and server readiness flow, and the existing v6 `engine-start.json` argv. I did not start/query a process, read active logs, run CPU/GPU work, build, test, profile, measure, fetch, mutate Git, or clean artifacts. Current v6 is a Main-controlled in-progress session; this report uses its recorded argv and the supplied 1405/1047 trace markers as context only.

Correct route and v6 invocation
The v6 `engine-start.json` identifies the binary SHA-256 `3fa2375eab38dbd3be187e2bed410099b03103a73429d29e67d5b11e975943ee`; its native argv includes `--serve`, `--max-context 262144`, `--kv int8 --kv-resident 32768`, `--expert-cache 128 --expert-cache-per-layer`, `--spec 4 --mtp ...`, `--prefill 4096 --no-prefill-borrow`, and `--vram-reserve-mib 700`. The wrapper starts `serve/server.py`; its readiness poll is for `/v1/models` (`run_server_job_v2.py:78-98`). Engine `main` enters the serve branch at `src/program/generate.cpp:4260`, initializes and binds the serve verifier and MTP at `:4699-4700`, prints engine `READY` at `:5217`, then enters the stdin request loop. The HTTP server cannot become ready before the engine's READY (`serve/server.py:463-485`; job poll above).

The 1405 -> 1047 MiB markers supplied for v6 are both upfront startup markers. `mem_mark("the expert cache and the graphs")` is at `generate.cpp:3657`; the later `mem_mark("the verifier and the drafter's binding")` is at `:4714`, immediately after `ver.init(...)` and `mtp.bind(...)` at `:4699-4700`. They are before `READY` (`:5217`) and before any request prompt. Prompt buffers are initialized still later at `:4471-4570` (source order: serve setup encloses these before verifier init), with the `--no-prefill-borrow` prompt allocations included in that initialization. Thus the marker delta does not measure memory released or allocated after a prompt; it reflects work in the preceding startup span, with the named 4714 marker specifically taken after verifier initialization and MTP binding. The R471 framing of 1405 -> 1047 as a prompt/decode phase transition was incorrect.

What is live before the first prompt
The serve branch creates `strata::prefill::Prefill sp` once at `generate.cpp:4267`. For this argv, `pf_borrow` is false (`:2498`, from `--no-prefill-borrow` and the profile condition), so `borrow` stays null and `sp.init` takes its own-buffer path (`:4463-4491`). Its planner/initialization runs before the verifier bind marker in source order. `Prefill::init` registers its device allocations in `Impl::owned` (`src/prefill/prefill.cpp:181-200, 667-779`), including chunk buffers/ring and QSA/attention workspace; they are allocations for the configured chunk, not just temporary per-call locals. In a single-GPU serve request, `sp.run` uses that same object for batched prompt reads, while the unborrowed case has no cache loan/refill to release those buffers. `sp` is scoped around the entire serve branch (`generate.cpp:4260-6223`), and there is no `sp.reset()` at request end or before decode. Therefore the no-prefill-borrow 4K workspace remains allocated during decode and between requests in the current serve path.

For comparison, the standalone CLI route below the serve branch uses a different local `Prefill prefill` (`generate.cpp:6230+`). It runs its one prompt, refills any lent slots, records stats, and under SYCL explicitly calls `prefill.reset()` before entering its token-generation loop (`:6294-6338`). That standalone behavior is real but does not describe HTTP `--serve`; the serve branch returns at `:6223` before the CLI path.

The verifier's device arena is allocated by `Verifier::init` before the first request: the source carves for the maximum configured window, does one `cudaMalloc(&arena_, count.used)`, then retains the arena (`src/core/verify.cpp:323-364`). The plan/staging data is also mapped at init (`:284-321`). The window graphs are captured lazily and cached per T (`:1051-1106`), and the commit graph is separate (`:1114-1171`); after creation, the `Verifier` destructor destroys those graph executables and frees the arena (`:191-218`). The `Verifier` carries `VerifyHits` cache pointers (`verify.cpp:231-235`), and capture/record code uses these pointers in its graph path. `mtp.bind` occurs before READY and allocates its persistent draft logits and optional draft-head subset (`src/core/mtp.cpp:416-450`); the serve prompt callback uses MTP prefill on each chunk (`generate.cpp:4860-4865`). These are live serve allocations even though no prompt has run yet. Any cache relocation/reallocation would therefore need to account for verifier/cache raw pointers and rebuild affected verifier graph executables, not just alter an `ExpertCache` capacity integer. MTP binding and its own captured paths also have separate lifetime.

Prompt/decode/reset boundary
Each valid request starts inside the `while (next_line(line))` loop (`generate.cpp:5234+`). Conversation cache restores at `:5450-5496` restore saved session/KV contents into the existing live session/MTP state; they do not recreate the engine or rebind verifier/cache pointers. The prompt's batched portions call `sp.run(...)` (`:5815`), then the current path refills any lent slots before it prints `REUSED` (`:5844-5851`). In this v6 no-borrow case there are no lent slots. Prompt chunks synchronously fence `sp.cs` before `on_chunk` (`prefill.cpp:2668-2677`); the single-GPU MTP prefill callback completes its own stream (`mtp.cpp:794-823`). This is a safe candidate point for retiring prompt-only buffers only after all prompt and callback work is complete, but present code does not do so.

Decode reuses the same verifier, MTP, session, expert cache and prompt object. The serve decode loop first applies pending adaptive expert swaps at its window boundary (`generate.cpp:5918`); after each verify window it commits (`:5947`) and may run draft/adaptation work (`:5973-5983`). At request end it explicitly waits for the last verifier commit (`:5997-6001`) before emitting DONE (`:6141-6149`). That wait alone is not a full resize boundary: a future resize must also ensure no prompt/copy/refill or MTP work remains, join adaptive work, resolve `pending` refill events and peer/stage events (`:4954-4978`), and preserve or restore session/checkpoint data. The loop itself processes one input request at a time, so a completed request before the next `GEN` is a plausible serialization point; however `QUIT`, STOP, cancellation, error, and process shutdown have different exits and need an explicit contract.

STOP sets `stop_req`; prompt reads test it between chunks and verifier work tests it between windows (`:5067-5109`, `:5802-5812`, `:5991-5995`). A cancellation still reaches request-end handling and `ver.wait_commit` before DONE (`:5997-6001`), but prompt cancellation can leave a partial session and current checkpoints; the code marks that state non-continuable and reports the read prefix (`:6018-6024`, `:6137-6148`). A resize protocol must treat it as a completed/cancelled boundary only after the same drains and preserve the existing checkpoint semantics. `QUIT` breaks the request loop then leaves the serve scope (`:5239`, `:6222-6223`); it is teardown, not an opportunity to grow the same live server for another request.

Candidate to reclaim the 4K prompt workspace
Source supports a design candidate: after successful prompt completion and refilling borrowed slots, and before decode, wait for all Prefill work to finish, then call `sp.reset()` to synchronize its `cs`/`copy` streams and free `Impl::owned` allocations (`prefill.cpp:541-563`). Keep the session/cache/verifier/MTP allocations alive. Before the next batched prompt, initialize a replacement `Prefill` object for the selected chunk; in a between-request resize, do this only after pending expert swaps and all device queues/events are committed. In single-GPU no-borrow mode this could exchange prompt-only memory for cache capacity during decode, then rebuild prompt workspace later. This is not implemented or runtime-qualified, and actual free-memory accounting, allocator reuse, re-init peak, and whether it improves fit/performance are unknown. Because the current Prefill initialization is upfront and held for the process, simply growing the cache after the current `mem_mark` would likely hit the same capacity already occupied by that scratch; reclaim needs a real reset, not merely a planner change.

Resize safety and raw-pointer obligations
A future expert-cache resize cannot just map/unmap storage while the server is live. Stop new HTTP admission and serialize the request loop; reach a completed prompt/decode/commit boundary; drain Prefill and verifier streams, adaptive refill/peer events and every transfer queue; ensure no `ExpertCache` slot owner, Prefill loan, stage or pending swap references the tail. Then update host/device residency tables and cache slot count/offsets as one publication step. Rebuild `Verifier` as required because the arena/graphs and `VerifyHits` plan reference cache pointers; rebind/rebuild MTP if any bound input or arena address changes. Preserve all live session/KV and conversation checkpoints (current restore/copy semantics are contents in the preallocated storage). For grow, fully map/initialize new segments and slot metadata before exposing them; for shrink, only release a tail proven unowned and nonresident. Restore old capacity/state on any failure or return an explicit error without publishing a partial resize.

The serve stdin protocol accepts `GEN`, `GENI`, `STOP`, and `QUIT`; it has no standalone `RESTORE` control command (`generate.cpp:5103-5108, 5234-5251`). The scoped RESTORE here is the internal conversation/checkpoint restore at `generate.cpp:5450-5496` and `:5544+`: it writes prior state into existing buffers. This is not an engine restart and does not make cache pointer movement safe. Standalone CLI generation is a separate route and has no next HTTP request; it releases only its prompt object before token generation as shown above. HTTP STOP/cancel, HTTP server restart, normal QUIT and in-process next-request restoration must not be conflated.

Conclusion
For the actual v6 `--serve --prefill 4096 --no-prefill-borrow` invocation, prompt workspace is allocated during startup, before READY, and persists through decode and idle intervals because the serve `Prefill sp` is not reset. The verifier arena and MTP binding are also live before the first prompt. The R471 CLI-only evidence cannot establish HTTP allocation lifetime. Releasing `sp` after the synchronized prompt and before decode is a plausible source-level reclaim seam, but making live expert-cache resize safe additionally requires a serialized request boundary, full queue/pending/lease quiescence, cache table publication, and verifier/MTP graph rebinding. No runtime memory return or resize success is claimed.
