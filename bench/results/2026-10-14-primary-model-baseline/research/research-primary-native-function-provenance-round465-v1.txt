### G active-SYCL route and adaptation boundary

G's top-level CMake chooses `sycl/` and returns when `STRATA_ENABLE_SYCL=ON` (`beddab2:CMakeLists.txt:12-21`). Its resolver prefers migrated SYCL files and otherwise root files (`sycl/CMakeLists.txt:55-75`); it selects the SYCL `generate.cpp`, core/cache/expert code and prefill path (`:156-175`). `serve/server.py` is the same blob as Niko and P. This gives three separate layers to audit: upstream service contract, G's active-SYCL adaptation or explicit stub, and P's selected primary engine. A root CUDA implementation is not active merely because it exists in G.

The G elastic path is not simply CUDA source. Lines `156-260` of its cache file preserve a `#if 0` driver VMM implementation, while lines `262-344` provide a separate SYCL virtual-memory implementation; `open_segmented` checks `sycl::aspect::ext_oneapi_virtual_mem` and returns a diagnostic if unavailable. Therefore classify it as a real G adaptation and a P source-level gap, but do not claim it runs on the Arc without runtime evidence. Conversely the G peer path explicitly refuses, and G's active SYCL source has no multi-request slot protocol. `sycl/src/core/verify` batch verifier windows for speculation are not equivalent to independent server request slots (`BGEN/BSTOP/BADM/BT/BDONE`).

## Saved-setting handling

At source level, the settings are not silently erased:

- The Niko/P/G shared server layer retains config keys and applies them to engine startup. P `engine_args` appends `--vram-elastic` for `vram_elastic:true` (`serve/server.py:1471-1478`) and `--batch N` for integer `parallel > 1` (`:1482-1503`).
- P's strict argument parser rejects unsupported forwarded options. Thus the saved elastic or parallel setting causes a visible startup error. The server's VRAM API also has an explicit capability error if an engine lacks the method. This behavior is undesirable for a migrated setting unless the failure is explained to the user, but it is not silent success with the setting dropped.
- `vram_reserve_mib` is a different, supported static startup option: P generator parses it at `src/program/generate.cpp:1242`; keep it when `vram_elastic` is absent or unsupported. Do not conflate static reserve with dynamic cache resize.
- `setup.py` saves `parallel` only when explicitly supplied and carries an earlier value otherwise (`:4344-4355`). It also stores `vram_reserve_mib` in config. The server's pass-through means a migration should either implement the applicable function or reject/translate it with an explicit status; it must not silently delete persisted values.
- `batch-groups`, trim-stage, remote helper caches and peer selection are only meaningful with multi-GPU stage/cache features. On the specified one-GPU target they should receive an explicit applicability/unsupported disposition; retaining their raw CLI args and receiving the strict unknown-argument failure is at least visible, but a good user migration path should name the unsupported condition.

## Required-function decision

For this PC, prioritize source-level adaptation of two user-visible functions if the project intends to preserve Niko's service capabilities on the primary branch: (1) one-GPU elastic VRAM control, with device-aspect gate and a truthful `POST /v1/vram` capability response; G's extension implementation is a candidate reference, not a proven runtime solution; (2) shared single-GPU multi-request service protocol if Niko's `parallel` setting is in the supported product contract. Implementing C++ protocol/state is within scope; importing CUDA kernels/graphs is not. `batch-groups` remains multi-GPU-only.

Do not make trim-stage, remote helper placement, `--peer-device`, or multi-GPU `--layer-split auto` blockers for the one-Arc PC. Keep their status distinct from the above shared single-GPU services. The same applies to G features that are explicitly device-gated or stubbed: source presence alone is no runtime proof. CUDA/HIP behavior and Xe whole-engine integration remain outside scope.
