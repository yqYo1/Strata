# R474 — Primary prompt progress boundary, same-queue copies and the v7 layer-0 failure

## Scope and status

Read-only review of the primary P source, the indexed v6/component receipts, and only the public v7 `record.json` and `owned/engine.stderr`. The forbidden private component receipt was not opened. No run, build, test, GPU/profiler/process action, fetch, Git/config/service change, or cleanup was performed. This report makes no root-cause claim.

The public v7 record describes a failed diagnostic, not a speed sample: the same initial short request failed after the service became ready, the native child exited by SIGABRT (`-6`), `passed=false`, `complete=false`, no normal native exit was proved, fresh fault search was empty, and no driver dump existed. Its stderr shows the 27-token prefill chunk entered layer 0, hit the 60-second watchdog with zero expert-pool jobs and all five pool workers parked, then after the watchdog's GPU-wait release printed `*** stack smashing detected ***`. That is a host stack-canary failure signal, but the record has no thread/frame that localizes it. Empty GPU-fault evidence does not identify which host/runtime path failed.

The successful v6 long request is materially different evidence: the same 61,055-input request completed with parameter validation/timers, XMX off, in 968,021 ms (63.1 input tokens/s), with no fresh GPU fault. The accepted exact/tile-8/compact component receipt is also a different scope: the direct `sycl_prefill_mmq_test` fixtures completed in about 105 seconds with no fresh GPU fault; it sets `model_executed=false` and `performance_qualified=false`. Neither result isolates v7's first model-level layer, staging, or first-use compilation behavior.

## Where prompt progress is actually issued

`include/strata/core/progress.hpp:48-56` shows `progress_at()` stores the status text/detail/chunk/time; it does not increment the heartbeat. `progress_beat()` increments `beats`. The watchdog at `src/program/generate.cpp:5193-5213` resets its 60-second timer only when `busy` clears or `beats` changes. It prints the most recently stored `where/detail/chunk`; `stall_report()`'s “layers served” value is `ticks` (`:834-848,5209-5211`), not a prefill-layer counter. `progress_tick()` is used in the verifier path, not the prefill loop. Therefore the v7 `0 layers served` text is not evidence that no prefill layers had started or that a particular GPU phase had made no progress.

In `Prefill::run`, the chunk marker is set at `src/prefill/prefill.cpp:1381-1387`. Before each layer body, the loop calls `progress_beat()` and then sets the marker to that layer and chunk (`:1664-1667`). For the single-GPU v7 request, the observed “layer 0” marker means layer 0's entry heartbeat occurred; the watchdog then saw no next heartbeat for 60 seconds. It does not distinguish time in layer-0 attention/GDN, routing, host source/staging, gather/quantize, GU/Down product, combine, queue/JIT work, or a wait. The per-phase `PfTimer` marks exist in the layer body, but the report is emitted only at normal prefill end; the aborting log contains no such completed phase breakdown.

The chunk callback is later. PLE input can be gathered on a `std::async` host future while layer 0 runs (`:1377-1379,1443-1474`), but `ple_land()` joins it and uploads at layer 1 (`:1451-1474,1668`), so that future is not a layer-0 device dependency. On one GPU there is no `next_run` layer-stage future. After the full layer loop, prefill finishes the issuer and sets a “finishing chunk” marker (`:2627-2636`), synchronizes before invoking `on_chunk` (`:2668-2678`), then serve's callback performs MTP draft prefill before printing `PP` and issuing its next progress beat (`src/program/generate.cpp:4860-4877`). The v7 log fails before those chunk-completion/MTP callbacks. No hidden arithmetic callback or callback-driven heartbeat occurs inside layer 0.

## What `same_queue=1` changes, and what remains ordered

In the SYCL build, `Prefill::init` always assigns `m.copy = m.cs` (`src/prefill/prefill.cpp:693-699`), and `queue_for()` requires that queue to have the in-order property (`include/strata/sycl/launch.hpp:47-57`). Thus `STRATA_SYCL_PREFILL_SAME_QUEUE=1` does not move work onto a different queue in v7. It makes `copy_events` false (`prefill.cpp:1321-1328`), omitting the explicit per-slot `copied`/`used` event waits and records. With the in-order queue, the intended device sequence is still copy → gather/read → subsequent slot overwrite; the source comments state that ordering rationale (`:1317-1320`). This is an event-elision difference from v6's unset option, not a queue-topology change.

The host-side stager-release event is separate and remains active. For an unpinned routed miss, `stage_one` waits for the stager buffer, queues its H2D copy, calls `m.stager->issued_one(job, m.copy)`, and only then advances (`:2380-2393`). `issued_one()` records `dma_done[j % kRing]` before publishing `issued=j+1` (`:322-330`). The stager worker waits for the prior `issued` frontier and synchronizes that DMA event before reusing its pinned host buffer (`:270-300`, `:327-330`). The `same_queue` conditional does not disable this event or the buffer-lifetime gate. Direct pinned-source copies have no stager buffer to release.

The explicit v7 `STRATA_PREFILL_RING=8` takes the routed-only path even for a large prompt: `ring_slots()` preserves an explicit `STAGE` value, and `stream_all` requires `ring > STAGE` (`prefill.cpp:94-110,138-155,1492`). The short 27-token request is routed-only in any case. Here `order` is built from the experts actually routed in the layer; `stage_one` pipelines up to eight misses, then `compute` consumes them (`:2336-2400,2441-2494,2519-2534`). This excludes the full nonresident-expert sequence used by large-ring mode. It makes expert-source reads/stager waits and per-expert ring reuse candidates specific to v7, while preserving the in-order device queue and the host staging-DMA release event.

## NT=27 / compact MMQ shape and source-level bounds

For the observed `T=27` prompt rows and `K=10`, the MoE activation table has `T*K=270` routed rows (`K` and `N` are defined at `prefill.cpp:90`). The per-layer host table is sized as `n + 1 + ceil(n/16)*17`, where `n=order.size()` is the unique routed-expert count; its absolute GU boundaries end at `rows_local`, and each 16-expert group's Down boundaries are made relative (`:2152-2159`). Each product is submitted with at most 16 experts (`ngx=q+1`), `total_rows<=270`, and `max_rows<=270`; GU host bounds point at the group's absolute slice, and Down bounds at its relative slice (`:2465-2493`).

In the exact tile-8 compact path, `native_mmq_xmx.cpp:391-409` reads exactly `p.experts+1` host boundary values synchronously to build a fixed `std::array<int32_t,17>` prefix. The API comment explicitly limits `host_bounds` to synchronous submission use (`include/strata/sycl/native_mmq.hpp:18-20`); the device kernel uses the copied prefix and device bounds, not the host pointer. With 270 total routed rows, valid prefix growth is at most `ceil(270/8)=34` tiles. The uniform fallback's upper tile bound is at most `16*ceil(270/8)=544`. The output row dimensions are 1,280 for GU and 2,560 for Down, padded to 80/160 row groups of 16 (`native_mmq_xmx.cpp:318-383`). These ranges and the 17-entry prefix are small; the source shows no NT=27-sized automatic array or apparent host stack-span overflow in this compact-grid boundary handling. This rules down that particular stack-size hypothesis, not arbitrary corruption elsewhere or a compiler/runtime defect.

The public accepted component fixtures cover standalone quantize/product/gather/MMQ shapes, including 37 routed rows, three-expert bounds, a compact product with 73 rows, all tested format pairs/widths, and the XMX-versus-prior-reduction check when exact XMX is requested (`tests/sycl/prefill_mmq.cpp:70-235`; public `main-primary-accepted-mmq-gpu-root-v1` receipt). They validate the component contracts but do not exercise the real 27-token prefill sequence, the eight-slot stager lifecycle, chunk callback, or first full model-layer graph. Passing them cannot clear the integrated layer-0 failure.

## Causal boundary and remaining evidence gap

The available data supports a narrow statement: the first short request did not produce the next prefill-layer heartbeat within 60 seconds; cleanup/release was followed by a host stack-smash report. It does not say whether the trigger was first-use XMX compilation/launch, the routed-only source and staging sequence, another earlier layer-0 kernel, or an independent host/runtime error. The current exact-XMX fixture result makes “XMX component is universally broken” unsupported; it does not test cold model JIT or composition. The same-queue source ordering and retained stager event make “same_queue=1 removed the pinned-buffer DMA completion event” specifically inconsistent with the code. The host-bounds and fixed-prefix arithmetic for NT=27 show no obvious size-overrun mechanism.

The first layer is the unresolved stage; there is no finer public marker or captured canary-failure stack/frame. The existing source has phase boundaries in the layer body and a later chunk callback, but no public per-subphase host marker between `stage_one`/gather and GU/Down submit. Until the separately planned cold-JIT/stack investigation adds a thread/frame or a narrow operation marker, retain the v7 failure as an unresolved host stack-smash following a layer-0 watchdog, not as a proven XMX, same-queue, stager, or NT=27 root cause. Keep v6 completion, v7 failure, and the standalone component pass as separate result statuses.
