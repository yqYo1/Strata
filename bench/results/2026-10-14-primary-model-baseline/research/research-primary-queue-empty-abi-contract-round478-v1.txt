# R478 — Queue-empty ABI, Level Zero query, and watchdog-thread hypothesis

## Scope and inputs

Read-only source-contract review for the `cudaStreamQuery` → SYCL queue-empty → Unified Runtime → Level Zero path. Toolchain source: Intel LLVM worktree `toolchain-sycl-v711-b570-20261011`, supplied SHA `504366f4b82ff00bbac7b0c956635eed8bc599d8`; installed toolchain noted by Main is XeStrata `.tools/intel-llvm-v711/install`. I did not build, run tests, query a device, use a debugger, or change project/toolchain source. I read the requested v7 `engine.stderr`, R476 retained report, and research index; I did not open the prohibited private component receipt.

## Exact source contract

1. `src/sycl/compat.cpp:332-342`: `cudaStreamQuery(cudaStream_t st)` initializes a local C++ `bool ready = false`, then executes `ready = queue(st).ext_oneapi_empty()` inside `attempt`. If ready, it also calls `queue(st).throw_asynchronous()` and `runtime_for()->check()`. It returns `cudaErrorNotReady` only when the wrapped operation succeeded and `ready` is false. Thus the queue-empty query is synchronous host API work; it is not itself an asynchronous callback.
2. Intel SYCL `sycl/source/queue.cpp:245`: `queue::ext_oneapi_empty() const` directly returns `impl->queue_empty()`. The public declaration at `sycl/include/sycl/queue.hpp:3607` returns C++ `bool`. The extension specifies true when all previously submitted queue commands have completed at the call point (`sycl/doc/extensions/supported/sycl_ext_oneapi_queue_empty.asciidoc:108`).
3. `sycl/source/detail/queue_impl.cpp:1084-1115`: the implementation first checks SYCL-side state. For in-order queues it reads `MEmpty` with acquire ordering and may lock `MMutex` to inspect the last event; for out-of-order queues it locks `MMutex` while checking unsubmitted host/blocked events. If neither path establishes the result, it declares `ur_bool_t IsReady = false`, calls `urQueueGetInfo(MQueue, UR_QUEUE_INFO_EMPTY, sizeof(IsReady), &IsReady, nullptr)`, and returns `IsReady`. `ur_bool_t` is `uint8_t` (`unified-runtime/include/unified-runtime/ur_api.h:730`). The queue state locks are released before this fallback UR call (their lock guards are branch-local).
4. UR defines `UR_QUEUE_INFO_EMPTY = 6` as an optional `[ur_bool_t]` result, true if empty at query time (`unified-runtime/include/unified-runtime/ur_api.h:6989-7000`). The C API accepts `size_t propSize`, `void *pPropValue`, optional `size_t *pPropSizeRet`; this call supplies size 1, a non-null pointer to one byte, and null size-return pointer. This is a valid optional-query form (`:7058-7088`).
5. The Level Zero v2 `ur_queue_immediate_in_order_t::queueGetInfo` and `ur_queue_immediate_out_of_order_t::queueGetInfo` handle `UR_QUEUE_INFO_EMPTY` by calling `zeCommandListHostSynchronize(..., 0)` on their command list(s). Success maps to `ReturnValue(true)`, `ZE_RESULT_NOT_READY` to `ReturnValue(false)`, other statuses propagate as UR errors. The out-of-order path locks its array of command-list managers while it checks each list (`unified-runtime/source/adapters/level_zero/v2/queue_immediate_{in_order,out_of_order}.cpp:62-87`). The v2 batched queue checks active-batch emptiness and synchronizes its immediate list only when the batch is empty (`queue_batched.cpp:1045-1060`).
6. `UrReturnHelper`'s scalar overload forwards the supplied C++ scalar to `ur::getInfo` (`unified-runtime/source/ur/ur.hpp:310-333`). Its `true` / `false` literals have C++ `bool` type, while the SYCL receiver has `ur_bool_t` type. On the target ABI both are one byte; `ur::getInfo` copies `sizeof(T)` bytes, so the true/false value is copied as one byte to the one-byte destination. No source-level size mismatch or adjacent-byte overwrite is apparent in this path. The enum/property, value pointer, and lifetimes are valid for the duration of the synchronous call; the caller-owned `IsReady` remains live until return.

## Thread and lifetime assessment

`ext_oneapi_empty`/`queue_empty` is `const`, but `const` alone does not establish a general concurrency guarantee. At SYCL level, the queue implementation performs its own short state checks and locks. The Level Zero v2 out-of-order adapter additionally locks command-list managers during the actual host synchronization. The v2 in-order adapter shown here fetches its immediate command list with `get_no_lock()` and synchronizes it without a UR-side mutex in this method. I found no evidence in this call path that a watchdog query itself writes into expired stack memory or uses an invalid output pointer. A simultaneous query and submit to the same in-order queue may deserve a separate guarantee audit: this source excerpt does not establish that the Level Zero command-list handle is protected against concurrent host operations. That is a possible thread-safety question, not evidence of stack corruption.

The query can take host time because it enters the UR/Level Zero adapter and calls a driver synchronization API, even with a zero timeout. A watchdog thread executing it could therefore be delayed or blocked in driver code. That does not make the stack-local output invalid during the call, and the Level Zero API receives the live command-list handle plus timeout zero. The v7 report's 60-second watchdog stage and subsequent `released the verify window's GPU waits ... GPU finished in 0 ms` are consistent with the watchdog's later verifier release finding those verifier streams idle; they do not show that `cudaStreamQuery` was executing or that the queue query corrupted memory. The report ends with `*** stack smashing detected ***`; that runtime signal does not identify which stack frame or write caused it.

## Assessment

The proposed `bool`/output-size mismatch is disfavored by the inspected source: the SYCL-to-UR buffer is exactly `sizeof(ur_bool_t) == 1`, and the Level Zero scalar result is a one-byte `bool` on the target ABI. No exact ABI overwrite mechanism was found. A driver/adapter query on a watchdog thread remains a conceivable concurrency or latency surface, particularly for concurrent in-order submit/query, but this source inspection cannot establish such misuse or connect it to the canary abort.

Given Main's reported later native pass with a 300-second watchdog and a measured `zeModuleCreate` duration of 89.276 seconds (greater than the default 60 seconds), the cold-JIT timeout remains a better-supported explanation for the earlier watchdog trigger. It does not, by itself, explain the separate host stack-canary abort. No API/threading changes or inference decision follow from this report.
