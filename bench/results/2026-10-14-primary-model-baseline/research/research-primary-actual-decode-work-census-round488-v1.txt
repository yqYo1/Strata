## Finding

The 4K and 16K short runs have similar median decode rates (5.9 and 5.8 output tok/s). The three 32,049-token requests are slower (4.2, 2.8, 3.4; median 3.4), even though decode work per emitted output is comparable to 16K in two samples. The clearest source-bound long-context candidate is the SYCL QSA selector: each verify row scores every valid index block from block 0 through the current context block before top-k, so the number of valid block scores grows with context. This is a mechanism candidate, not a measured time attribution. The request summaries also show low expert-cache hit fractions (about 1.8–2.1% for these long requests), and each 32K request reports 108–120 MiB KV read from RAM, while the 4K runs report about 45 MiB. These correlate with the slower long requests but do not establish causal shares.

## Method and source meaning

Inputs are `stock-baseline.json`, `stock-native-evidence.json`, and `decode-work-model.json` under `bench/results/2026-10-14-primary-model-baseline/`; source audit is against current `src/core/verify.cpp` (the audited source files have no diff between the recorded stock revision and current HEAD), `src/core/expert_source.cpp`, `src/kernels/sycl/qsa_select.cpp`, `src/kernels/sycl/kv_stream.cpp`, `src/kernels/sycl/decode_attention.cpp`, and `src/program/generate.cpp`. R481/R485/R486 source dispositions are not repeated here; R481’s corrected arithmetic in `decode-work-model.json` is authoritative. No raw trace or token payload was read.

`expert_lookups` is the request delta of `cache_hits + cache_admitted + cache_refused` in `generate.cpp`; it counts each routed top-10 entry. With 48 MoE layers, 480 lookups equal one fully routed token row. In native single-GPU mode with `pcie-frac=0`, a cache hit is GPU hit-path work and a non-hit is a CPU miss. Thus `lookups - hits` and its fraction give CPU-miss *entry* counts, not the CPU’s unique expert-job count. The multi-row dispatch deduplicates expert IDs within each layer when making CPU jobs, so duplicates across verify rows reduce jobs and blob fetches but do not reduce token-row arithmetic. The cache percentage is entry weighted, not byte weighted.

Per complete routed row, metadata gives 982,272,000 bytes of selected expert blobs (10 experts × the 48 per-layer per-expert blob sizes) and 4,718,592,000 useful routed GU/Down FLOPs. The byte value is logical payload, not observed RAM/DRAM/PCIe traffic. A request with R routed rows has R × 4.718592 GFLOP useful expert work. Its distinct logical expert-weight set is bounded by at least one row (0.982272 GB) and at most R rows (0.0982272 × R GB): exact within-request ID overlap is absent from these summaries. These bounds include both GPU-hit and CPU-miss expert weights. They do not include any measured memory traffic.

`drafts accepted/offered` counts MTP proposals, not a direct verify-row count. The exact source-bound row count is `expert_lookups / 480` (all request values divide evenly); it includes actual routed work across verification windows. Useful FLOPs per emitted output are total row FLOPs divided by generated tokens. Decode tok/s is the engine’s generated/decode-ms clock and includes the request’s speculative decode work; prompt tok/s is a different clock and is not mixed into the ratios below.

For each verify row, `Verifier::run` advances all active layers. In QSA layers the graph calls `qsa_block_scores` with `blocks=max_blocks_` and default `active=-1`; the kernel guards and scores `b <= nb` where `nb` is the current position’s block index. Thus it performs valid score work through the current context (roughly position/4 blocks per QSA query row) even though `qsa_block_topk` retains only a bounded selection. The kernel’s launch grid is sized to configured capacity and out-of-range groups return; exact kernel elapsed time and whether launch padding also costs materially are unmeasured. `qsa_decode_attn_batch` then consumes the selected blocks. This scan is the most direct source explanation for a context-dependent QSA cost.

KV lines report block-read counters and host RAM bytes as printed by the native request summaries. A stated 75 MiB host read is not PCIe H2D byte traffic: QSA resolves selected host-backed KV blocks and the printed MiB is `misses × 4224 B`, not an observed bus counter. The reported high VRAM block-hit fractions therefore do not imply zero host traffic.

## Matched-context summary and interpretation

- **4k** (3 requests): decode rate 6.1, 5.5, 5.9 tok/s (median 5.9); routed rows/output 1.71, 1.88, 1.71 (median 1.71); CPU miss fraction 98.12% median; KV host RAM read 44.5, 45.3, 45.8 MiB; KV VRAM block hit 95.62, 95.94, 95.50%.
- **16k** (3 requests): decode rate 5.8, 5.3, 5.9 tok/s (median 5.8); routed rows/output 1.88, 1.88, 1.88 (median 1.88); CPU miss fraction 98.09% median; KV host RAM read 92.3, 91.9, 91.8 MiB; KV VRAM block hit 91.73, 91.77, 91.78%.
- **32k** (3 requests): decode rate 4.2, 2.8, 3.4 tok/s (median 3.4); routed rows/output 1.71, 2.54, 1.88 (median 1.88); CPU miss fraction 97.94% median; KV host RAM read 108.3, 119.6, 109.9 MiB; KV VRAM block hit 89.36, 92.10, 90.16%.

At 32K, median routed rows/output (1.875) matches 16K (1.875), but useful routed work/output remains roughly 8.85 GFLOP in the 32K median sample versus 8.85 GFLOP at 16K; extra expert work per emitted output does not explain the median drop. The 32K samples vary substantially: 41, 61, 45 rows for 24 outputs, and acceptance is 15/30, 10/45, 12/33. These short outputs are too brief to establish steady decode rates, and draft acceptance changes the amount of work per output.

QSA index scoring grows with actual context per row and has a source-confirmed full block-prefix scan before top-k. This supplies a plausible context-dependent cost absent from the routed expert FLOP count. The lower KV VRAM hit percentages at 16K/32K and larger reported RAM-read amounts are another plausible contribution. Expert cache hit percentages stay near 2% in the 4K/16K/32K short samples, so GPU expert hits do not take much entry-count work away at any of those points; the similar fractions do not identify whether CPU dot-product compute, worker scheduling, source/memory access, GPU kernels, or synchronization dominates.

CPU pool timing, workers’ active/idle cycles, per-layer unique miss jobs, exact routed IDs, exact byte-weighted hit/miss fractions, memory-controller traffic, and per-kernel timings are not present in the allowed request summaries. The run’s startup evidence says this CPU lacks AVX-512, so the native expert kernels use AVX2; it configures five expert-pool workers plus the host thread. CPU misses are therefore substantial in entry count, and the CPU path quantizes activations then executes native GU + Down, but neither pool active time nor worker wait/idle time was retained for these requests. `Verifier::run` has per-stage wait/pool timing hooks, but the quiet stock run did not record them. Ryzen 5600X theoretical compute/bandwidth is deliberately not used as measured traffic or a hardware roofline. No claim of CPU or GPU saturation follows.

## Evidence limits and next discriminating evidence

- The 24-token outputs do not qualify steady decode performance or the 70-token/s target. This census preserves the recorded original result status: stock-native evidence, not speed-qualified optimized final, physical 262144-context qualification, upstream engine measurement, or long continuation proof.
- Exact unique routed weights/job count needs the per-layer expert IDs for each verified row or a bounded aggregate counter from the same request; these are absent and cannot be recovered from hits/lookups.
- A causal QSA attribution needs request-aligned kernel spans or an existing timing record for QSA score/top-k/resolve/attention stages at equal output counts and controlled draft acceptance. No profiler/timing was run in this read-only round.
- A CPU attribution needs request-aligned pool active work/unique miss jobs and worker scheduling evidence, with CPU memory traffic counters if making a memory-bound claim. The five-worker configuration alone says nothing about utilization.
- KV read MiB is derived pinned-RAM block payload and does not count exact PCIe H2D bytes; retain this distinction in any follow-on transfer comparison.
