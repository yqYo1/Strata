# R476 — Verifier watchdog snapshot, callback lifetime, and phase-scoped rescue

## Scope

Read-only source review of `include/strata/core/progress.hpp`, `include/strata/core/verify.hpp`, `src/core/verify.cpp`, `src/program/generate.cpp`, and `src/kernels/cpu/pool.cpp`, reconciled with primary research rounds R459–R474 and the current `bench/results/2026-10-14-primary-model-baseline/research-index.json` corrections. The closed B records were consulted only through the retained Git gzip/indexed evidence; the prohibited private component receipt was not opened. No process or service query, build, test, CPU/GPU run, profiler, fetch, Git/config change, or cleanup was performed. This report proposes a design; Main owns validation.

## Current race and lifetime contracts

`Verifier::init` publishes `this` in `g_diag_verifier`, installs the global `diag_active_verifier` callback, inserts `this` into the first free `g_live` atomic slot, and installs `release_live_verifiers` (`src/core/verify.cpp:121-139,220-229`). The slot scan has no failure path if all 16 entries are occupied. `g_live` is a registry of initialized objects, not currently running windows. There is one global diagnostic pointer even when a layer split has several verifiers.

`Verifier::run` writes the ordinary `int last_t_` and `int64_t last_pos0_` at `verify.cpp:1220-1222`. The detached serve watchdog calls the diagnostic callback on another thread (`src/program/generate.cpp:5197-5215`; `stall_report` at `:834-856`), and `Verifier::diag` reads both plain members at `verify.cpp:174-189`. If it fires during `run`, these conflicting accesses are a C++ data race. Making the two fields separate atomics would remove that race but would still permit an inconsistent `(T, pos0)` pair from adjacent windows. `cur_layer_`, `reached_`, and the registry slots are atomic; that does not make `last_t_`/`last_pos0_` safe. The current R473 v7 report happened in prefill before that request entered `Verifier::run`, so this is a real general race surface, not evidence for that specific stack-canary failure.

The destructor compare-exchanges `this` out of `g_diag_verifier` and each `g_live` slot, then synchronizes/destroys streams, graphs, events, and host buffers (`verify.cpp:191-218`). Atomic pointer removal alone is not a lifetime barrier: a callback can load a non-null raw pointer, be descheduled, and resume after the destructor has removed the slot and started freeing members. `diag_active_verifier` has the same load-then-call shape (`:123-125`). The global function pointers remain installed after destruction; that leaves a callable static function, but safety depends on the pointed-to object lookup being safe. `init` can also overwrite the single diagnostic pointer as later split stages initialize.

The serve watchdog is detached and has no stop condition or join (`generate.cpp:5197-5215`). Its normal loop accesses only process-wide `Progress` until it fires, but on fire it reads verifier/pool callbacks and may hold their object pointers. Normal serve teardown does not join it before stack-scoped verifier objects are destroyed. The pool's own `wait_parked` and `wait_done` timeout paths also call the same global release function before aborting (`pool.cpp:472-514`), so quiescing the serve watchdog alone is not sufficient to protect release callbacks.

## Phase mismatch in the existing GPU rescue

`release_live_verifiers` visits every non-null slot and calls `release_gpu_waits(5000)` (`verify.cpp:129-139`). That method permanently sets `released_`, writes `UINT32_MAX` to the three mapped host flags, fences, and polls only that verifier's `cs_` and `copy_` streams for up to five seconds (`:153-171`). It does not ask whether a verify window is active, nor whether the watchdog's stage is prefill, verify, idle, or another request phase. `g_live` remains populated for the lifetime of each initialized serve verifier.

The rescue is correctly targeted when a verify graph is blocked on those host flags: the bounded release lets the spin graph drain before engine termination. It is phase-mismatched during prefill. R473's public v7 record reported a prefill layer-0 stall followed by “GPU finished in 0 ms”; as R473 established, that only says the idle verifier streams queried complete after its flags were changed. It says nothing about the prefill queue or device work. Releasing an idle verifier also marks it unusable for any later window, though the watchdog's intended terminal path aborts the engine. This evidence does not implicate the release path as the stack-smash cause.

A single `active` bool on one verifier is insufficient for layer splits. Serve wires `ver` through `next_` to other stage verifiers (`generate.cpp:4629-4643,4661-4692`); one window can have several stage objects and streams participating. The targeted rescue must cover the active window's full verifier chain, while a prefill-only stall must not release an unrelated, idle chain.

## Minimum safe diagnostic snapshot

Use one small CPU-side snapshot object containing a sequence/window generation, phase (`inactive`, `verify-window`, optionally `commit`), an in-flight `T`/`pos0` pair, the last published host layer, and a separate last-completed `T`/`pos0` pair. Protect phase and each pair together with a short per-verifier mutex: publish the in-flight pair at window entry (where the current two assignments occur), promote it to last-completed only after the existing GPU/copy completion boundary succeeds, and record an error/aborted phase on failure. `diag` copies this object under the same mutex, then unlocks before formatting or sampling mapped/device flags. Keep the existing members for the serialized request-thread path if desired. This adds no lock to a kernel, pool callback, graph wait, or per-layer step; writers take it only at window entry/completion and diagnostics only on a report. A tiny mutex is simpler and less error-prone than a sequence counter here.

If a lock-free snapshot is chosen instead, publish a single coherent immutable record or use a sequence protocol in which every concurrently accessed payload field is itself atomic. A sequence counter around non-atomic `T`/`pos0` still has a C++ data race, and two independent atomics do not provide a coherent pair. Label the device-written mapped flag values as best-effort point samples; do not hold the snapshot lock while calling a device API or waiting. When inactive, show the last-completed pair as historical data; on a failed window show its in-flight pair with the failed phase rather than labeling it complete.

## Safe registration and shutdown ordering

Replace raw-pointer load-and-call with a registry lease. Under a registry mutex, callbacks select only eligible entries and increment an in-flight reference before releasing the mutex. After diagnostic/release calls finish they decrement it and notify waiters. Destruction first unregisters the entry, marks it closing, and waits for its in-flight callback leases to reach zero before destroying streams or buffers. Registration must report capacity exhaustion instead of silently leaving an unregistered verifier. The diagnostic path can alternatively publish a value-only snapshot outside the object registry, which removes object lifetime from `diag`; the GPU rescue still needs a lifetime lease.

Make the serve watchdog joinable and scoped to the serve-engine lifetime, with a stop flag/condition variable so ordinary shutdown can wake and join it before verifier teardown. Keep the existing terminal watchdog behavior: on timeout it first snapshots/reports, acquires leases for the active verify chain, releases that chain's waits with the current bounded rescue, then aborts. The pool timeout caller must use the same lease-protected active registry. Ensure shutdown also quiesces the pool wait/release call sites before object storage is reclaimed. Clear or disable global callback publication only after all callback sources have stopped; atomically setting a callback to null is not enough while an invocation already holds a function pointer or object lease.

Mark activity with a request/window generation and phase. At `Verifier::run` entry, atomically register the full participating `next_` chain as the current verification window; only after each participant's GPU and copy work reaches the existing end boundary should the chain become inactive. On every return/error path, publish a coherent inactive/error state with RAII. The main watchdog uses the phase snapshot to report accurately. `release_live_verifiers` becomes `release_active_verify_chain`, and it retains the existing flag-store, fence, bounded stream-drain behavior for precisely those active objects. The synchronous `release_gpu_waits` calls inside verify's own timeout/error paths continue to rescue that active chain. Do not release every verifier merely because the global request watchdog fired.

## Prefill progress without per-kernel synchronization

R474 shows the prefill heartbeat is issued at layer entry, so one legitimate layer exceeding 60 seconds looks identical to a deadlock; `progress_at` changes the label but does not beat the watchdog. If Main adds finer progress, report host submission phases separately from GPU completion. Advance a heartbeat only at a meaningful, bounded unit of forward progress already observable at the host (for example, after a group of routed work has actually been issued or a completion boundary already required by the existing algorithm). Do not insert a stream/device synchronization after each kernel, treat a successful asynchronous submit as device completion, or repeatedly reset the watchdog timeout during a blocked phase. Keep the current terminal threshold and verifier rescue contract unless measurement supports a deliberate, bounded policy change; a per-stage diagnostic label can improve attribution without changing liveness policy.

## Validation targets for Main

The design should be validated with deterministic CPU tests for (1) repeated concurrent snapshot publication/read always returns a matching `T`/`pos0` generation, (2) diagnostics see either a complete current snapshot or a marked inactive last snapshot, (3) unregister waits for an in-flight callback lease before destruction, (4) slot-capacity exhaustion fails visibly, (5) ordinary shutdown stops and joins the serve watchdog before verifier teardown, and (6) a prefill-phase timeout releases no verifier while an injected active verify stall still releases every stage in its active chain and drains within the existing bound. Then run the existing verify-stall rescue test and the normal primary validation. These checks must not weaken or replace the current spin-rescue behavior.

## Decision boundary

The source confirms the plain-member snapshot race, raw-pointer callback lifetime window, detached-watchdog teardown gap, and phase-unfiltered release. It does not prove any caused the R473 stack-canary failure or explain the layer-0 delay. The minimum design is a coherent value snapshot plus lease-protected verifier registry and joinable watchdog, with release eligibility limited to the active verify chain. No inference behavior, verify spin rescue, or timeout policy is changed by this read-only report.
