## Decision and correction carried forward

The first safe attribution pass should be an explicitly hardware-counter-free VTune `xpu-offload` collection after Main releases the device. Use API/programming-runtime trace plus the GPU task/queue timeline, with CPU sampling disabled, GPU characterization metrics disabled, memory-bandwidth collection disabled, and a finite data cap. The primary evidence gate is a short collector smoke against the already-qualified `sycl_runtime_test` (64 changing cross-queue handoffs). Local config expresses the requested options; it cannot prove that this B570 driver/runtime actually produces a usable API and GPU-task timeline. Only if that smoke shows both API events and device task rows should Main profile a real owned native request.

The installed `offload.cfg` maps CPU samples to an event-based PMU collector through `runtool.xsl` when `collect-cpu-sampling=true` on the expected local Linux route. `collect-cpu-sampling=false` is the safe initial choice for Ryzen 5 5600X under the known `perf_event_paranoid=4`, `yama/ptrace_scope=1` environment. The xpu config's `runss` route requires ptrace availability and `not(isPtraceScopeLimited)`; the `runsa` route configures PMU events for CPU sampling. Thus no reliable *CPU software-sampling fallback inside xpu-offload* is established for this host from these files. Do not turn on the knob and call it software sampling: the 10 ms software-sampling note in R459 applies to a separate `hotspots` analysis type, not this xpu-offload knob. If CPU stacks/samples are necessary later, treat that as a separate capability-gated run; do not weaken sysctls or add drivers in this pass. With CPU sampling off, host CPU samples/stacks are absent; the xpu API trace can still show traced runtime-call spans and their correlation to device tasks if the smoke proves it.

Correction from Main's `bench/results/2026-10-14-primary-model-baseline/decode-work-model.json`: R481's byte values were divided by ten in several statements. For the registered 48-layer model, `sum_one_expert_blob_across_layers_bytes=98,227,200`, but top_k=10 means T=1 unique selected expert blobs total **982,272,000 bytes**, and a T=4 window's deduplicated blob-byte range is **982,272,000 to 3,929,088,000 bytes**. The corresponding values per proposed row are 245,568,000 to 982,272,000 bytes. `useful_FLOPs_per_expert_token=9,830,400` and `useful_routed_FLOPs_per_proposed_token=4,718,592,000` were correct. These are logical selected weights/work, not measured RAM/PCIe traffic or a throughput ceiling. This pass uses them only to motivate timestamped CPU/GPU attribution; it does not infer a 70-token/s result.

## Stage A: post-benchmark collector smoke

Only after Main declares the stock benchmark and its owned server/native children closed and releases the GPU, run the existing binary recorded by the primary runtime fixture: `/home/yayoi/.local/state/strata-sycl/post-reboot-tuning-20261007/main-primary-native-build-root-v1/build/sycl_runtime_test`. It is already qualified as a non-model GPU runtime test with 64 changing cross-queue handoffs and boundary/ownership/sticky-error checks (primary baseline README, “runtime health” section). This smoke does not reset or reinitialize the device. Put it in its own unique result directory and enforce a 180-second owner deadline. Keep the event fixture output/result and the VTune result separate; do not turn this into a throughput sample.

A run-launched child is preferable to attaching to an already-running process. Since this binary is short-lived, do not use `-start-paused` unless a small shell gate is used to hold it before `exec`; the ordinary short smoke can collect immediately. Suggested shape, using the already recorded R459 command syntax and only after GPU release:

```sh

  -knob collect-programming-api=true \
  -knob enable-characterization-insights=false \
  -knob collect-memory-bandwidth=false \
  -knob enable-tasks-stack-collection=false \
  -knob enable-user-tasks=true \
  -- /home/yayoi/.local/state/strata-sycl/post-reboot-tuning-20261007/main-primary-native-build-root-v1/build/sycl_runtime_test
```

Add the explicit `target-gpu=<observed B570 selector>` only if that exact selector is already available from a prior saved receipt/installed launch configuration; the `targetGPUAtk` setting must not remain `none` for programming API trace to activate. The target is the configured B570 adapter, not another device. `-follow-child` is retained for a consistent launch policy; the test may be the directly launched process. The 100 MB smoke cap is an owner budget for this tiny fixture and may be raised only if a complete result is shown to hit the cap; do not silently accept truncation.

Smoke passes only if all conditions hold: test exits 0 and still reports its 64 changing cross-queue handoffs; VTune exits normally and saves a result; the API/event view contains SYCL/Level-Zero runtime calls associated with this process; the device-task view contains nonempty B570 task/queue rows with start/end timestamps and relationships to those API calls; the result timestamps cover the test's active interval; no GPU hardware counters or CPU PMU events are requested. An empty API or GPU task lane is a failed capability gate, even if the CPU task-only result opens. Record the missing lane and stop: do not expand into model profiling and do not label the config as proof. If the XPU result collects API calls but no device tasks, preserve the result and ask for a separate collector/driver capability diagnosis after the task; do not turn on hardware metrics to paper over the missing timeline.

## Stage B: one owned 32K-prefill/128-output request

Proceed only after Stage A passes, the unchanged Niko run has ended normally, and the smoke result is closed. Keep the current primary settings and environment identical to the post-benchmark recipe. Do not set `STRATA_PREFILL_TIMING`, `STRATA_DECODE_TIMING`, `STRATA_POOL_TRACE`, throw observer, UR full validation, or any XMX/ring/cache variation: R467 explains these perturb phase costs or queue behavior. Keep current compiler/range flags, exact XMX/tile8/compact/pack0, ring8/same-queue, cache128, int8 KV resident32768, context262144, prefill4096/no-borrow, MTP spec4, pool5, and `pcie-frac=0` as recorded. The 262144 context remains the configured capacity; the request is 32,768 prompt tokens. This is a diagnostic collection, not part of the clean rate series.

Use a unique *owned launcher* that preserves the existing `run_server_job_v3.py` ownership checks and `engine_wrapper_v3.py` native child identity capture, but has explicit gates for: server-ready, warmup complete, marked request start, request complete, and shutdown. Do not run the current v3 `diagnostic` mode unchanged: it sends a 58K diagnostic prompt with one output token, not the required 32K+128 request. A minimal copied/adapted controller should preserve the v3 invariants, not edit source or mutate the existing receipt. Launch that controller as VTune's target with `-start-paused -follow-child -data-limit=500 -r <unique-dir>`. It must start the server and wait for readiness while paused, then make a small 4K/8-token warmup request (same model/settings and chunk geometry), discard its timing, wait for completion and allow any initialization/graph capture to settle. This pays config/JIT/setup costs outside the marked request, while leaving profiler injection installed in the process tree. After warmup, keep server+native alive and idle. Use a second control shell for VTune commands and the request trigger.

Process/injection ownership:

- VTune launches the controller; controller launches `serve/server.py`; server starts `engine_wrapper_v3.py`; wrapper launches the real native binary. Retain `-follow-child` because the server/native are grandchildren of the profile target. Do not attach to PIDs or use `target-pid`.
- v3 wrapper copies `os.environ`, removes only `STRATA_MEASUREMENT_THROW_OBSERVER`, hashes the engine, records parent/native PID, session and start ticks, then starts the engine with that copied environment. For this pass ensure the throw-observer variable is absent before VTune launch. Do not let observer handling overwrite VTune's preload/injection environment. Verify wrapper/native identity files and normal native/server exit as the existing v3 runner does. Preserve the collector's inherited environment through any adapted controller/wrapper; do not reconstruct a reduced env dictionary.
- Bound the whole owned collection to 180 seconds from the beginning of the marked request, plus a separately stated short normal-stop grace. At the deadline, only the controller may send `STOP` through the already-verified owned engine stdin/pidfd identity. Do not signal a similarly named process, kill by process name, reset/unbind the GPU, or launch another run. If STOP does not yield a normal result within the agreed grace, preserve incomplete status, close only the owned process tree through its identity-checked owner path, and report no model profiling success.

Mark sequence:

1. VTune target is started paused, server is ready, and warmup has returned. Confirm the owner has the expected one engine/native identity and the server has the expected URL; do not read model payloads.
2. Issue `vtune -command resume -r <R>`; issue `vtune -command mark -r <R>` immediately before the request trigger (label the mark in the owner ledger as `32k-prefill+128-decode-start`).
3. Trigger exactly one fixed prompt that the model's tokenizer and native request ledger confirm as 32,768 prompt tokens, with max output 128. Include the same decoded history/seed in the owner ledger by SHA-256 so a rerun is reproducible. Require successful response and exactly 128 generated tokens for a complete target interval; if the API stops at EOS early, retain as a shorter request and do not call it the requested 128-output case.
4. On normal response, write request end wall/monotonic timestamps, actual prompt/reused/output token counts and client digest; issue `vtune -command mark -r <R>` (`32k-prefill+128-decode-end`) and then `vtune -command pause -r <R>`. Collection is now paused while engine/server perform a normal orderly shutdown (server SIGINT/QUIT protocol); keep VTune owner alive until both exit codes are 0 and wrapper has written its exit identity. Finally run `vtune -command stop -r <R>` to close the result. Do not profile shutdown in the marked workload; retaining process ownership until clean exit matters more than excluding all post-request milliseconds.
5. If the result reaches 180 seconds before normal response, record the deadline event, mark `request-incomplete-deadline`, stop the request only through the owner-verified native STOP path, then pause and shut down normally. Do not reinterpret partial prompt progress or an early STOP as a 32K/128 success.

Avoid using shell `timeout` as the only owner: it can kill the VTune target/server/native descendants together and bypass the runner's ID-checked STOP, leading to incomplete native-exit evidence. The owner watchdog should supervise by PID plus start ticks/session/pidfd, not PID alone. No GPU reset or device service change is authorized or needed.

For process and request timestamps, keep a compact owner ledger: UTC + monotonic start/readiness/warmup-end/request-trigger/request-complete/mark/pause/shutdown; controller/server/wrapper/native PID, PPID, SID, start ticks and exit codes; native binary SHA-256; URL/port; prompt token count, generated token count, request-body hash; and whether STOP fired. Use the existing wrapper records and response digest, not per-layer terminal traces. VTune's event timestamps and task/queue lanes must share the marked interval and include the engine PID/thread IDs. Since CPU samples are disabled, do not promise host stacks or CPU-active attribution.

## Evidence to retain and interpretation limits

For the smoke retain: exact VTune argv/knobs, result directory, VTune/test exit statuses, bounded stdout/stderr, selected GPU identity, summary/timeline reports, and one compact API/GPU-task event excerpt with clock domain and process/thread IDs. For the model run retain: knob recipe and VTune result under a 500 MB cap; owner ledger; normal wrapper/native/server completion receipt; response digest + prompt/output tokens; `vtune -report summary` and `vtune -report timeline` text/exports if the local 2026.4 command accepts those already-known report names; and a compact process/thread/API/task timestamp table. Verify result creation/report extraction only after the collector has stopped. Keep raw result until timeline evidence is verified; then apply `docs/ARTIFACT_RETENTION.md` (data-limit, owner, consumer, review point, and path/hash deletion manifest). Do not retain full API trace, repeated polling, or duplicate windows once a compact verified report exists.

The first profile can establish host submission-call spans and device task/queue chronology, which lets Main correlate graph submit/replay and API activity with GPU execution gaps. Without CPU sampling it cannot resolve Python/native CPU hot functions, worker-thread stacks, CPU memory bandwidth, PMU counters, GPU hardware saturation or per-kernel bandwidth. `collect-programming-api` tracing has overhead; the request interval is diagnostic and must not be compared as benchmark throughput. A visible GPU task lane and continuous activity do not by themselves prove the GPU is the bottleneck. Correlate API/task timelines with the native request's accepted-token/window ledger and end-to-end wall; phase timers remain off as required by R467.

Corrected R481 work bounds may be included only as metadata context: 982.272 MB of unique selected expert blobs for T=1, and 982.272–3,929.088 MB for a T=4 window before cache hits, repeated-row deduplication, CPU/GPU placement, or measured traffic. They do not define expected transfer bytes in this `pcie-frac=0` run or a 70 output-token/s ceiling. The profiled 32K+128 request is one attribution point, not a replacement for the unchanged stock series.

## Findings that make this more specific than R459/R467

R459 correctly recorded available VTune action names/data cap and recommended child launch, but called xpu-offload CPU samples “software” without tracing the installed analysis's actual `runtool.xsl` branch. R467 correctly warned against phase timers/validation overlays but did not resolve whether API-only tracing can run without GPU hardware counters on this target. R484 resolves both from the 2026.4 installed config: PMU sampling is not a safe default at the current perf/yama settings, CPU samples remain disabled; `enable-characterization-insights=false` avoids hardware metrics while `collect-programming-api=true` activates the GPU runtime API lane only when a real GPU target is selected. The runtime smoke is the missing empirical gate before a long model collector.

The new R481 correction also prevents using the tenfold-low expert-byte statements as a reason to predict an output rate. See `decode-work-model.json` for authoritative arithmetic. No run, rate, collector capability, or root-cause result is established by this report.
