## Result and scope

The installed native metadata pins down the target's sparse expert work much more tightly than a generic “MoE model” estimate. It has 48 MoE layers, 512 experts per layer, and top-10 routing. One distinct expert blob per layer averages 2,046,400 bytes; the actual mixed-format values range from 1,510,400 to 2,662,400 bytes. Thus a single-token route selects 480 expert-token entries and represents **98,227,200 bytes of distinct layer/expert weights** if all ten experts are different in each layer. The 98.2 MB is logical expert payload used by routed computations, not a claim that 98.2 MB reaches DRAM or PCIe each token.

For a four-token verify window, the source deduplicates expert IDs within each layer before making CPU jobs or GPU hit groups. Depending on routing overlap, the number of unique blobs per window is bounded from 480 (same ten experts recur in all four token rows) to 1,920 (no within-layer overlap); corresponding distinct expert payload is **98.2–392.9 MB per T=4 window**. There are still 1,920 expert-token evaluations in that window. The actual bytes read from host RAM depend on cache residency, deduplication, OS/cache state, and which misses the CPU computes. The current `pcie-frac=0` configuration disables the per-window PCIe-miss assignment, so an expert miss is computed by the CPU; cache-resident hits run in the GPU shared/hit graph. This is a CPU/GPU work split, not an expert-upload schedule during decode.

The metadata therefore yields useful minimum work and traffic accounting, but **not a hardware throughput ceiling**. It does not bound the dense attention/GDN/QSA/H-C/state path tightly enough, nor the speed of CPU IQ dot products, GPU kernels, synchronization, or effective MTP acceptance. A valid conversion to the 70 target must use accepted output tokens and end-to-end decode wall time from the unchanged run, with matching output/fault status. No claim that 70 is achievable or unattainable follows from these bounds.

The latter declares `n_expert 512`, `total 50,292,326,400`, and 48 layer rows. The per-layer `blob_bytes` values sum to 98,227,200 bytes across one expert from each layer; multiplying by 512 reproduces the declared 50,292,326,400-byte arena. Every layer has distinct GU and Down native types. Layer counts are GU type 18:17, 22:20, 21:10, 23:1; Down type 20:39, 42:9. Their blob sizes already include GU and Down together, so do not count the GU and Down entries as separate full blobs.

The calculation is:

- `48 layers * 10 selected experts = 480 expert-token entries` per target token.
- No route overlap / distinct expert payload: `10 * sum(blob_bytes[layer], 48 layers) = 982,272,000 bytes` if all selected entries are counted independently. That is a *per-token-entry byte count*, including duplicate experts selected in different layers (which are distinct weights).
- For CPU/GPU unique blob traffic and a T=4 window: each layer has 10–40 unique expert IDs. Sum actual per-layer bytes times 10 for the minimum (98,227,200 bytes/window), times 40 for the maximum (392,908,800 bytes/window). Divide by four for 24.56–98.23 MB/token-equivalent of unique blobs in that window; this is not equivalent to the 98.23 MB of expert-token work, because reusing one blob across rows still performs multiple token computations.
- For `T=1`, distinct count is exactly ten per valid layer, and its unique blob payload is 98,227,200 bytes. Cache-resident entries move the corresponding computation to GPU but do not make the routed calculation disappear.

A useful arithmetic work floor is also derivable from the metadata geometry and active implementation. With `N=2560`, `FF=640`, `K=10`, each selected expert row performs two `1280 x 2560` GU matrix products and one `2560 x 640` Down product: 9,830,400 multiply/add FLOPs per expert-token. Ten experts across 48 layers are **4,718,592,000 useful routed-expert FLOPs per target token**; T=4 evaluates 18,874,368,000 such FLOPs. A 70-token/s target therefore requires at least 330.3 GFLOP/s of routed expert arithmetic averaged per accepted output token, excluding all dense, shared expert, attention/state, MTP, router, and host costs. This is a count of required arithmetic, not a measured useful FLOP rate and not proof that the device can reach it.

## Active primary execution route

The call path below is the SYCL primary route in this fork; it is not inferred from Niko's CUDA generator.

1. `generate.cpp` uses MTP/speculation to choose a verify `T`; the first window is explicitly forced to `T=1`, while ordinary later windows can use `S_mtp=4` (or fewer from minimum-probability/suffix policy). The successful result must report its observed T/acceptance distribution. “spec4” does not mean every window processes four new user-visible tokens.
2. `Verifier::run` launches a captured, segmented GPU graph, waits on `layer_done_` at a layer boundary, then calls the CPU pool callback for that layer/window. The event synchronization measures completion of preceding GPU commands; it is not automatically GPU idle time. After CPU planning, shared-expert/cache-hit GPU work is launched on the compute stream and overlaps the CPU expert pool when the graph's dependency plan allows it. The copy stream is synchronized at each layer/window boundary, although with this configuration its expert H2D fetch count should be zero.
3. `expert_pool_dispatch_multi` handles `n_tok=T`, `k=10`. It deduplicates IDs within the layer, classifies resident experts as GPU cache hits, and leaves nonresident misses on the CPU with `pcie_num=0`. It quantizes each token activation to that layer's native GU activation type, constructs one `ExpertJobMulti` per distinct CPU-miss expert, and attaches all token rows selecting that expert.
4. The selected call is `ExpertPool::run_split_multi_native`. Each expert job runs Gate/Up across `nt` rows, quantizes the intermediate `FF=640` values separately per row, then runs Down across those rows. The five configured pool workers and optional host worker are the pool's cooperating execution resources; the actual number of jobs per layer is determined by unique nonresident experts, not by the ten expert-token entries or the `pool_workers` setting. `multi_bytes` is incremented by `unique CPU jobs * exact blob_bytes`, while phase timers split GU, intermediate quantization and Down. They do not provide per-worker active cycles versus parked/wait time.
5. GPU dense/shared/state work remains separate from the CPU pool. The verify graph carries QSA, GDN, HC, shared-expert and cache-hit work for the T rows; the MTP drafter has its own dense/head/KV path; session KV and QSA state may include a long-context-dependent component. Do not attribute these costs to the routed CPU matrix count or count them twice when their kernels overlap CPU work.

Useful source anchors at this HEAD: `src/program/generate.cpp:5895-5920` (serve verify-window selection), `src/core/verify.cpp:1322-1405` (layer completion, pool call, CPU/GPU overlap and stream drains), `src/core/verify.cpp:1530-1558` (async DMA fetch callback; no copies when n<=0), `src/core/expert_source.cpp:1845-1878,1910-2115` (multi-token dedup, cache/PCIe classification, activation conversion, CPU job construction and native pool dispatch), `src/kernels/cpu/pool.cpp:663-690` (native multi-token GU / quant / Down phases), `src/core/verify.cpp:1060-1074` (captured shared/hit graphs), and `src/core/mtp.cpp:450-520` (MTP forward/dense path).

## Converting measured windows to the requested target

For each completed clean decode interval, compute `accepted_tokens / decode_wall_seconds`; preserve the benchmark's stated decode-rate convention and report generated output count, wall time, window count, T histogram, accepted tokens/window, and speculative rejection/faults. At 70 accepted output tokens/s, the permitted average end-to-end time is 14.286 ms per accepted token. If the measured mean is `A` accepted output tokens per verify window, the corresponding required verified-window rate is `70/A` windows/s and maximum mean window wall budget is `1000*A/70` ms, including whatever the benchmark's decode clock includes. For example, only at the theoretical four accepted outputs per T=4 window would that be 17.5 windows/s or 57.14 ms/window. Use measured A, not the configured proposal length, and keep draft time, verify wall, commit/emit and idle gaps consistent with the benchmark denominator. This is a target conversion, not a second decode target or an assumption about acceptance.

A clean Niko result and primary-run model can answer whether 70 is currently reached under the specified settings. It cannot identify the limiting resource by itself. Decode throughput does not scale with the 98.2 MB/token number alone: CPU and GPU phases overlap, duplicate routes reduce unique blob loads in T>1, and the shared/dense/attention work is not represented in that number.

## One bounded attribution repeat that distinguishes likely limits

Keep the clean, unchanged Niko run free of timers and profiler. After Main releases the GPU and approves/starts its separate diagnostic request, run one short fixed-history decode through the exact primary server as a child of the installed VTune `xpu-offload` collector, as prescribed by R459/R467. Mark only the request interval. Preserve the R466 recipe: native hit graphs active, exact XMX tile 8, compact enabled, pack off, ring 8/same queue, cache 128 per-layer, int8 KV with 32,768 resident cells, context 262,144, pool workers 5, `pcie-frac=0`, adaptive swaps off, MTP/spec4 and no-borrow. Do not enable `STRATA_POOL_TRACE`; it prints every layer/job and perturbs the schedule. Do not put profiler/timer results in the clean speed series.

Collect one synchronized evidence set with the request/window ledger and VTune host+device timeline: `STRATA_DECODE_TIMING` stage counters; per-layer selected/unique/hit/miss counts and format-specific blob bytes (only if existing counters or a bounded low-overhead diagnostic can provide them); CPU stacks/samples; GPU kernel/task queue spans; and request wall/accepted tokens. VTune timeline is useful for correlating CPU and GPU activity and separating CPU-busy gaps from sustained GPU work, but GPU hardware metrics and CPU memory bandwidth counters are conditional on this machine/tool configuration. Do not infer bandwidth from busy percentage alone. Intel's guide states that long GPU-busy intervals indicate GPU-bound work while large gaps with busy CPU can indicate CPU-bound work, and cautions that serialized engine use can make a CPU scheduling problem look GPU-bound. The local R459 plan already uses a capped, child-launched XPU Offload collection for this reason.

Interpret the marked interval as follows:

- **CPU compute candidate:** pool worker stacks spend most active sample time in native GU/Down dot kernels, phase active-time grows with bytes/rows, workers stay occupied, and the GPU timeline overlaps useful work without a dominant uncovered dependency. A CPU-bound label requires the CPU span to control the request critical path; summed pool time alone overlaps GPU and overstates wall.
- **CPU memory/source candidate:** CPU pool wall is large, worker samples show stalls/source load or scheduling gaps rather than arithmetic, host memory-bandwidth evidence approaches a measured platform ceiling, and the route is dominated by large cold/nonresident blobs. Separate file page faults/source read time from DRAM traffic; logical `blob_bytes` and prefetch calls are not DRAM-byte counters. If memory bandwidth instrumentation is unavailable, say so and do not label a memory ceiling from samples alone.
- **GPU compute or GPU memory candidate:** the device queue is continuously occupied on the request critical path. Attribute time to actual dense/shared/hit/attention kernels; hardware counters are required to distinguish compute saturation from bandwidth/latency inside a kernel. GPU utilization alone cannot make that distinction.
- **Host/runtime/launch candidate:** significant CPU gaps before device work or between layers, with worker pools and GPU not both busy; inspect queue submission, event completion, host API/driver stacks, plan/activation/job phases, and launch count. `ms_wait` is a completion interval, not a standalone GPU wait-cost verdict; `ms_pool` includes CPU work and can overlap GPU hit work.
- **Transfer candidate:** record exact copy submissions and bytes separately from `pcie_experts`; R459 establishes that the latter counts planned groups, not successful payload bytes. With `pcie-frac=0`, expected per-window expert fetch count is zero. If nonzero copy-engine traffic appears, find its source before attributing it to sparse expert misses.

Official references support the instrumentation method, not a performance claim for this model: Intel [VTune GPU Offload Analysis](https://www.intel.com/content/www/us/en/docs/vtune-profiler/user-guide/2025-1/gpu-offload-analysis.html) describes aligned CPU/GPU timeline correlation and CPU/GPU-bound diagnosis; Khronos [SYCL 2020 Specification revision 12](https://registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html) defines queue profiling timestamps and requires a profiling-enabled queue; Intel [Level Zero Programming Guide](https://oneapi-src.github.io/level-zero-spec/level-zero/latest/core/PROG.html) describes command-list/event ordering. R480 already details the distinction between host issue, event completion and transfer bytes. These are analytical tools, not a measured ceiling for B570/5600X.

## Conditional optimization candidates

Do not adopt either until the primary timeline establishes the corresponding bottleneck and a matched output/state gate is available.

1. **If the CPU miss pool controls decode and measured cold/streamed host traffic dominates:** test a cache-profile adjustment that places the most frequently reused format-aware `(layer, expert)` blobs in the existing 128 GPU slots, preserving the same slot bytes and native outputs. This directly trades some CPU blob reads/dot jobs for GPU hit-graph work without increasing cache capacity or introducing decode PCIe copies. Use a fixed route history to compare CPU unique-miss bytes, GPU hit work, critical-path wall and MTP acceptance. Reject it if GPU work becomes the new serial bottleneck or acceptance/state changes. This is a conditional profile experiment, not proof that 128 slots are sufficient or that current resident selection is poor.
2. **If the GPU is continuously critical and kernel metrics identify memory/launch overhead in the cache-hit or dense path:** target only the measured dominant kernel/launch stage with a one-variable SYCL experiment (for example, a plan/launch consolidation for the repeated per-layer hit/shared work if launch gaps are the evidence). Do not swap in a CUDA/HIP implementation or assume XMX arithmetic changes improve non-MoE dense/attention work. Keep graph capture, exact output/logit checks and identical routing history fixed. A kernel change is unjustified if the timeline instead shows CPU misses or driver/event gaps controlling completion.

The rejected paired IQ3_S GU CPU load-sharing experiment in R464 is not proposed again. It already tested NT1 and NT8 with actual weights and was slower. R470's prefill transfer/compute estimates are not decode traffic, and its combined-GU wording/values should not be carried into this report as a decode measurement. R480's isolated transfer rates likewise are not a current decode link ceiling.
