# R463: SYCL range-contract exception during first 4096-token prefill

Scope: read-only audit of the specified run log and the active Strata SYCL launch paths. No source/config edits, build, tests, model/GPU/profiler execution, fetch, or cleanup were performed. The report does not establish a successful 61055-token run.

## Finding

The exact message `Provided range and/or offset does not fit in int` is the Intel SYCL host-side `id_queries_fit_in_int` contract diagnostic. It is not evidence of a GPU fault or memory corruption. The primary executable's unannotated launch graph is not enough to identify which particular launch raised it: the run's stderr stops immediately after `prompt chunk 0 of 61054`, with no named per-layer phase or kernel marker. In particular, do not attribute it to QSA or oneMKL solely from the failure location.

Intel LLVM source at `/home/yayoi/ghq/github.com/intel/llvm/.worktree/toolchain-sycl-v711-b570-20261011/sycl/include/sycl/detail/id_queries_fit_in_int.hpp` documents the mode as assuming global range, work-group range, global IDs, and local IDs fit in `INT_MAX`; the host helper checks range products, IDs, `nd_range` offsets and emits this exact message. `defines.hpp` generates the assumptions when the mode is enabled; `queue.hpp` and `handler.hpp` call the helper on host submission paths. The adjacent `sycl/test-e2e/Basic/range_offset_fit_in_int.cpp` is a focused test of this contract. This makes the public `-fsycl-id-queries-range=size_t` change a relevant diagnostic bypass for launches whose implicit ID-query values exceed `int`, but it does not by itself identify or correct an oversized launch.

## First-chunk source checks

The prefill path batches QSA selection in groups of 256 (`src/prefill/prefill.cpp:444, 1843-1857`) and uses `active = last query's block id + 1`. At the start of the prompt, positions are only in the first 4096 tokens; with the configured 4-token index block this means at most roughly 1024 completed blocks for the last query. `qsa_block_scores` uses `size_t(nq * launched) * 32` with `nq <= 65535` and `blocks <= INT_MAX` validation (`src/kernels/sycl/qsa_select.cpp:8-15, 26-63`). At the first batch these dimensions are approximately 256 × 1024 × 32 = 8,388,608, below `INT_MAX`; this path is not a high-confidence explanation for this first chunk. QSA top-k launches `nq * 256`, also below the limit for this batch.

The batched indexer (`src/kernels/sycl/native_qsa_indexer.cpp:173-190`) currently loops through `n` and submits the single-cell append kernel once per token; each append kernel has global size 256 (`:84-85`). Its API narrows position and capacity to `int` (`:189-190`), but for this run's chunk start and configured capacity (262144) those values fit in signed 32-bit. The batch itself does not create a large global range.

The selected-cell prompt attention kernel launches `size_t(queries) * n_head_kv * 128` work items (`src/kernels/sycl/prompt_attention.cpp:19, 66-84`). Even with 4096 queries and the model's small KV-head count this is below `INT_MAX`. The fallback decode-attention batch defaults to 32 queries (`src/prefill/prefill.cpp:447, 1954-1958`). These are concrete early QSA entry paths but neither currently demonstrates an over-limit range.

Other direct prefill kernels inspected use bounded token/row widths (`gdn.cpp:62-70`, `ple.cpp:58-66,112-120`); the formulas shown there are far below the limit at T=4096 for the model dimensions. The first-layer projection sequence in `prefill.cpp:1755-1783` does call the SYCL oneMKL GEMM wrapper (`src/prefill/sycl/gemm.cpp:11-29`), which passes 64-bit T/N/K after checked byte-size products. oneMKL is therefore an unresolved internal launch source: without the matching oneMKL implementation or a host stack/operation marker, its internal `nd_range` construction cannot be ruled in or out. The wrapper itself does not narrow those dimensions or show a range exceeding `INT_MAX`.

Conclusion: current source review rules down the obvious first-chunk QSA scoring, QSA attention, and direct small launch grids. It does not yield a high-confidence culprit. A host-side exception can happen before GPU submission, consistent with the lack of GPU-fault evidence.

## What the size_t mode does not solve

The compiler option changes the type/assumption of SYCL's implicit ID/range query contract; it does not widen explicit application casts, intermediate arithmetic, or API fields already declared `int`. For example, QSA indexer append explicitly casts `capacity` and positions to `int` (`native_qsa_indexer.cpp:161-190`), and other kernels contain explicit `int` fields and products that must be reviewed independently. Nor does disabling the helper make signed overflow safe, validate buffer byte spans, guarantee backend/device support for arbitrary dimensions, or prevent an explicit `range<int>`/narrowed oneMKL argument from truncating. Existing `checked_count`/span guards remain necessary.

For any candidate where a product is computed before conversion, move the conversion before multiplication and retain overflow/range checks; for any API with 32-bit parameters, validate representability before narrowing. Do not infer safety from the absence of this specific diagnostic once the option is enabled.

## Evidence limitation and next diagnostic

The error log identifies the host helper but not the launch site. The cleanest next discriminator is a narrow host-side phase/submit marker (or host stack captured at the exception) around first-chunk operations, preserving the same model/run settings; then record each concrete launch's dimensions before dispatch. This can separate oneMKL internals from project kernels without assuming that max_context itself is the global range. The existing helper test verifies the compiler/runtime contract, not the full prefill graph or long-context correctness.
