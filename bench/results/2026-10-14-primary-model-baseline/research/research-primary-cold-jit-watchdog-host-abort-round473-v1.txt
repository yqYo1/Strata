R473 outcome and its relation to v6
The v7 root receipt records HTTP readiness, one short diagnostic request failing with `exit code 134`, server exit 0, and native engine exit -6 (SIGABRT); its result is `passed:false`, `complete:false`, and the full owner session is empty. Its saved engine log stops on a watchdog report at prompt chunk 0, layer 0, then prints `*** stack smashing detected ***`; it has no fresh GPU fault or native stack dump according to Main. The engine was built from the same binary SHA-256 `3fa2375eab38dbd3be187e2bed410099b03103a73429d29e67d5b11e975943ee` and has the same model/config argv as v6, but its environment re-enables `STRATA_SYCL_MMQ_XMX=1`, `..._TILE=8`, `..._EXACT=1`, `..._COMPACT=1`, `STRATA_SYCL_PREFILL_SAME_QUEUE=1`, and `STRATA_PREFILL_RING=8`. It also has `SYCL_CACHE_PERSISTENT=0`, parameter validation and the diagnostic observer/timers.

This failure is separate from Main's v6 61,055-token HTTP run, which Main reports completed with engine/server exit 0 and no GPU fault under parameter validation/timing. The accepted compact XMX fixture Main cites also completed in 105.36 seconds with exit 0 and bitwise/canary checks passing for the current size_t, exact tile-8, compact fixture. These results show that the full v7 service outcome is a failed diagnostic, not a general engine/server shutdown failure, and that a related XMX fixture can pass. They do not prove the 27-token prompt's stalled call was the same fixture operation or that it was in `zeModuleCreate`.

Why the 60-second watchdog can misclassify a slow first layer
The watchdog's contract says that a request heartbeat stopping means a stuck flag wait (`include/strata/core/progress.hpp:3-7`). In the batched prompt, however, `Prefill::run` calls `progress_beat()` once at the *start* of each layer, then starts that layer's work (`src/prefill/prefill.cpp:1664-1668`). The serve watchdog resets its timer when it observes a new beat; if no beat arrives for the configured 60 seconds it reports and then aborts (`src/program/generate.cpp:5193-5214`; default set at `:5194-5196`). A single layer taking longer than 60 seconds is therefore indistinguishable to this heartbeat from a deadlock. The layer-entry marker is not proof that any kernel has hung.

In the current source, the opt-in XMX prompt product expands a family of SYCL kernel templates over data type, tile, exact reduction and compact dispatch. It issues a `parallel_for` from `src/kernels/sycl/native_mmq_xmx.cpp:381-383`; environment parsing and dispatch are at `:385-409,464-526`. The prefill caller reaches the native MMQ path at `src/kernels/sycl/native_mmvq.cpp:1181-1184`. Strata itself does not call Level Zero `zeModuleCreate`; a cold SYCL/IGC module creation while the runtime first builds or submits one of these kernels is a plausible downstream source of a long host call. The v7 receipt's `SYCL_CACHE_PERSISTENT=0` makes a cold compilation explanation more plausible. However neither the receipt nor `engine.stderr` records the host call or a stack in it, so `zeModuleCreate`/IGC is a hypothesis, not an observed cause. The 105.36-second fixture shows that a related cold configuration can exceed the current watchdog interval, but it is not proof of duration or operation identity for this model layer.

The v7 stall report says zero layers served, all five expert-pool workers sleeping, and verifier state `0 tokens at position 0`, then the same two seconds later. This places the reported phase before the verifier request window and suggests the CPU pool was not the immediate source of active work. Its 1,895 major page faults and roughly 49 GiB RSS are diagnostic context only; they do not identify a JIT call, RAM-pressure stall, or device fault.

What `release_gpu_waits ... finished in 0 ms` proves
`stall_report` invokes the active verifier diagnostic callback from the watchdog thread, then the watchdog calls the global GPU-wait release callback (`generate.cpp:834-856,5210-5213`). The verifier callback reads its last window status (`src/core/verify.cpp:174-189`); `release_live_verifiers` calls `release_gpu_waits` for every registered verifier (`:126-139`) regardless of whether the current phase is prefill or verify. That method permanently sets `released_`, writes its mapped verifier flags, and queries only the verifier's `cs_` and `copy_` streams (`:153-171`). In this v7 log, the verifier has not handled a window; both streams can be idle, so 0 ms means only that those verifier streams queried as complete after the release. It does not establish that Prefill's queue/device work completed, that the first prompt layer finished, that IGC compilation completed, or that the whole device was drained.

`release_gpu_waits` is intended to break a GPU spin in a stuck verify window; it is not a generic prefill cancellation/drain. Its call here is a phase-mismatched diagnostic action. That does not itself explain the later stack guard: no overrun is visible in the reviewed path, and the verifier's `released_` being set is not a stack-corruption mechanism. Since the engine then aborts, there is no next verifier window in this process.

Keep the canary failure separate
`*** stack smashing detected ***` is a host-side stack-protector failure message. The retained engine status is SIGABRT (-6), while the GPU fault counter is zero per Main; neither identifies a GPU fault. The watchdog's explicit terminal action is `std::abort()` after it finishes the report/release calls (`generate.cpp:5210-5213`), but that alone would not explain the distinct stack-smashing message. The exact corrupted frame and whether corruption preceded, occurred during, or was detected while unwinding the diagnostic path are unknown without a core/all-thread backtrace. The configured `exception_backtrace.cpp` observer interposes `__cxa_throw` and reports SYCL-named C++ exceptions (`:20-35`); it does not observe glibc's stack-canary failure. `stall_report` contains Linux memory sampling and a Windows-only `MiniDumpWriteDump` path (`generate.cpp:858-877`), so its current implementation does not promise a Linux thread dump.

There is a concurrency review item, not a proven cause: the detached watchdog thread invokes `Verifier::diag` while the request thread is running. `diag` reads plain `last_t_` and `last_pos0_` while `Verifier::run` writes them (`verify.hpp:213-215`; `verify.cpp:1220-1222`). If a watchdog fires during verifier execution, this is a C++ data race; the current failure fires during Prefill, before that request's `run`, so these values are quiescent for this occurrence. Likewise, the global release callback races deliberately with an active verifier when rescuing a spin, but in this occurrence it targets idle verifier streams. This concurrency surface deserves a stable snapshot/phase guard; the current log does not tie it to the canary.

Smallest useful next diagnostic proposal
1. Keep the production 60-second watchdog unchanged. For one explicitly cold-JIT diagnostic only, use a larger but still bounded `STRATA_WATCHDOG_S` above the known 105.36-second fixture duration (for example 180-240 seconds), with the outer owner deadline longer than that. This avoids the known threshold collision without disabling hang termination. Preserve the current environment in the result so the run remains identified as cold and diagnostic; restore normal settings for ordinary qualification.
2. Add compact phase markers around the first native MMQ submission and its completion boundary: layer/chunk, GGUF type, row/column shape, selected tile/exact/compact branch, host time before/after `queue.parallel_for`/`submit`, and the first following queue wait/completion. Use one record per distinct first specialization, not per expert/tile. The current code's `queue.parallel_for` can return before device completion on the prefill stream, so separate host submission time from subsequent chunk/queue completion. Do not log a completed `zeModuleCreate` unless a Level Zero API trace or stack actually observed it.
3. For the stack-canary question, retain a bounded Linux core on `SIGABRT` or run the supervised diagnostic under a debugger configured to stop on `SIGABRT`/`__stack_chk_fail` and record symbolized `thread apply all bt`; include the watchdog, prompt/issuer, and runtime/JIT host threads. A backtrace of only the watchdog thread is insufficient if the prompt thread is blocked in runtime code. The current Windows-only minidump code does not supply this Linux evidence.
4. Make watchdog diagnostics phase-aware and race-free before relying on them: publish a stable verifier diagnostic snapshot (atomics or a small lock/seqlock over the fields) and indicate whether a verifier window is active. On a prefill phase, report verifier last-state as inactive and do not release verifier waits; on a verify phase, release only after the snapshot and retain the existing bounded rescue behavior. This preserves the targeted stuck-spin safeguard while preventing an idle verifier's `finished 0 ms` line from being read as a prefill/device-drain result.

Disposition
Cold SYCL/IGC JIT exceeding 60 seconds is a credible explanation for the watchdog false-positive given the heartbeat placement, `SYCL_CACHE_PERSISTENT=0`, and the Main-reported 105.36-second related fixture. It is not established as the v7 stalled operation. The subsequent stack-smashing/SIGABRT is a distinct host failure with unknown corrupting frame. The verifier callback/release path is phase-mismatched and has a potential data-race surface, but source does not prove it caused stack corruption. Treat v7 as incomplete/failed; do not count it as a GPU fault, successful long request, or a generic cold-JIT failure. No code or environment change is made by this report.
