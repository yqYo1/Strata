# Round 485 — 実際に選択されている SYCL cache/borrow 経路の再監査

調査日: 2026-10-14
範囲: ソースと既存の構成 cache、指定済みの実行ログ、`decode-work-model.json` による静的確認。GPU/build/test/benchmark は起動していない。計算値を新しい runtime 観測として扱わない。

## 結論

R483の「`--expert-cache 128 --expert-cache-per-layer` から161 slotsを作る」という分岐説明は、明示的128 cacheには当てはまらない。SYCL/native pack/per-layerのサイズ付きslot化は行うが、slot数を `per_layer_slots_that_fit` で増やすのは `auto_cache` のときだけ (`src/program/generate.cpp:3021-3035`)。明示的128では、47層に2 slotずつ、最後の層47に残り34 slotを割り当て、合計128 slotsとなる。実行ログも「128 slots」「0.26 GiB」「each layer owns 2 slots (0..1)」と記録しており、この経路と一致する。R483の161は、同じ128-slot相当byte budgetを**auto**でper-layer expansionした場合の静的計算であって、明示的128で実際に割り当てた数ではない。

この実行の`--no-prefill-borrow`は、profileありでもborrowを禁止する。フラグを外しても、128 slotsではborrowの保留128 slotsを残す条件により貸出できない。固定4096-token prefillは独立bufferを使う。したがって「フラグを外せば現在の128 cacheから4096 chunkが借りられる」という予測は誤り。

## 実際のSYCL build入口

`build-sycl/CMakeCache.txt` は `STRATA_ENABLE_SYCL=ON`, `GGML_CUDA=OFF`, `GGML_HIP=OFF`, `CMAKE_GENERATOR=Unix Makefiles` を示す。`CMakeLists.txt:177-178` はSYCL時に `cmake/sycl_backend.cmake` をincludeし、同ファイルはSYCL kernel群、`src/core/expert_cache.cpp`, `src/core/verify.cpp`, SYCL版prefill群を組み、最後に `add_executable(strata src/program/generate.cpp)` を選択する。従って設定済みSYCL generator入口は共有 `src/program/generate.cpp` の `STRATA_ENABLE_SYCL` compile-time branch。CUDA root generatorやHIP実装を実行経路の根拠として使っていない。

これは既存CMake設定とソース選択の証拠であり、指定された実行バイナリのhashとbuild receiptをこの調査範囲から直接確認できたという意味ではない。実行ログ自身の `GPU ... Intel(R) Arc ... (SYCL)` と `SYCL cached experts use native Q8_1 arithmetic` が実行時backendの証拠となる。

## Byte計算と R483 の修正

`bench/results/2026-10-14-primary-model-baseline/decode-work-model.json` はscopeを metadata/source arithmetic と明記し、native metadata SHA256を `d9ac2dfa3ee63c55c9c6a6db26f72da0cec0ee41733f007e5cbbbba71617aa5d` としている。48層のblob総和は98,227,200 B、最大は2,662,400 B。各層値は256-byte境界に既に整列している。

明示的128: `128 * 2,662,400 = 340,787,200 B` がuniform上限相当額だが、実際は `per_layer_slot_sizes(bytes,128)` により、各層2 slotsと最後の層34 slotsを作る。割当byte数は `2 * sum(layer[0..46]) + 34 * layer[47] = 281,651,200 B = 268.60 MiB = 0.2623 GiB`。実行ログの丸め表示0.26 GiBと整合する。slot数は128のまま。admissionの範囲も `ExpertCache::layer_slot_range` で `q=slots/n_layers`、最後の層だけ残余を取る (`src/core/expert_cache.cpp:291-303`)。profileはslotを一度埋める順序に使われるが、per-layer admissionでは層ごとのslot範囲を越えない (`generate.cpp:3170-3230` 周辺)。

auto時: uniform計算で得た初期 slot count `n` に対し、SYCL per-layer分岐はまずbudget `n * max_blob`を作り、helperでslot数を byte-budget内に展開する (`generate.cpp:3021-3035`, `expert_slot_sizes.hpp:15-33`)。helperは全層1slotずつの整列byte合計をroundとし、完全な周回数を全層に配り、残額のslotsを最後の層に配る。もしautoのuniform初期値が128なら、`q=3` + 最後に20 = 161 slots、実サイズ339,942,400 B (324.2 MiB)となる。これはR483の算術自体はhelperの仮想入力に対して正しいが、明示的128に誤って適用した点が誤り。

autoはその後、cacheをtouch/zeroしてからfree bytesを再読し、reserve700MiBに64MiBの許容差を加味して縮小する。縮小時もper-layer helperでbyte budgetからslotsを再計算し、closeして再openする。autoのcache数は従って静的な161ではなく、auto sizing時点のfree bytes、既存allocation、profile上限、cache touch後のfree memoryで決まる (`generate.cpp:2928-2948, 3070-3155`)。ログで確認できるexplicit128のslot数をauto時の実slot数と取り違えないこと。

## borrowと auto の分岐

borrowの共有predicateは `pf_borrow = !no_prefill_borrow && !expert_profile.empty()` (`generate.cpp:2499`)。`--expert-cache-per-layer` はslot配置/admissionの選択であってprofile要件の代替ではない。今回のprofileは24576 ranked pairs。`--no-prefill-borrow`ありなら、profileがあってもno-borrow経路であり、prefill用のdevice buffersはcache外に確保する。ログには「prompt path allocates its own buffers (too few cache slots to borrow)」と出ている。

フラグを除去した場合の固定chunk `plan_lend` は `Prefill::bytes_needed`から必要slots `k` を求め、`k+128 <= xcache.slots()`を要求する。sized cacheでは最大blob一律換算ではなく、cache末尾から累積実byteを数える (`generate.cpp:4139-4154`)。128 slotsならkが0以上のどのchunkでも `k+128<=128`を満たさずborrow不可。次候補を小さくしても、0 slots分借りる動作にはならない。prefill 4096の実needed-byte数は `bytes_needed(g,ss,4096)`のruntime形状依存値であり、この調査では実行せず数値を捏造していない。

`--expert-cache auto`だけを128指定から切り替え、`--no-prefill-borrow`を維持した場合、auto sizingのprefill reserveは `160 + 4096*680/1024 = 2,880 MiB`、加えてreserve700MiBおよびMTP bind分がcacheの前に控除される (`generate.cpp:2932-2945`)。これはborrowありのauto経路には当たらない。現在のログでcacheを除いてもfreeは約1.9 GiB以下と推定できる(観測1669 MiBに0.262GiBを戻した概算。計測点/他の同時allocation差を含むのでauto sizing時のfree測定ではない)。よって同じsetupのauto/no-borrowがcache0になりうる強い静的予測だが、現時点の実測結果ではない。MTP bind分も控除されるため余裕はさらに減る。

`--no-prefill-borrow`だけを外し、explicit128を保つ案もborrow可にはならない。serve時に現在profileでcacheをprefillし、decode時のresident hit setを構成した後、prompt loanは末尾slotを一時的にresident mapから外し、prompt完了後にrefillする設計。borrowの際は`Prefill::relayout`でそのcache領域をprompt workspaceに組み替える。128 slotsでは貸出後にdecode用128-slot reserveを保てず、借りない。これは単独変更の測定候補から除外できる。

有効な比較候補は変更を分ける:

1. **auto分岐だけを検証**する場合は`auto + no-prefill-borrow + prefill4096 + reserve700 + per-layer`を静的事前判定で最初に落とす。prefill reserve込みで `free_b > 700MiB + 2880MiB + mtp_bind` がauto sizing時に成立しないなら起動せず、実際のその時点の`cudaMemGetInfo`, computed reserve, resulting slot countを既存ログに明示する。現ログからは不成立が有力だが、サイズ実測ではない。
2. **borrowフラグだけを比較**するなら、128では両armとも独立buffer経路になるのが予想結果で、borrow対照にならない。loan可否を比較する前に、各armの実slot数と`lend_slots(4096)`、`k+128`をログで記録する。cache増量も同時に行わない。
3. 実際にborrowを評価する将来候補は、4096固定chunkで`available_slots >= 128 + ceil(actual_prefill_bytes / actual_tail_slot_bytes)`を満たすcache countを先に計算し、tail rangeの実slot bytesが必要bytesを満たすことを確認してから試す。per-layer quota/末尾slot偏りのため、総cache GiBだけでlend可否を判定しない。設定変更はcache countの単独armとborrow旗の単独armに分ける。

## lifetime、decode graph、KV、release可能範囲

- expert cacheはprofile上位128 pairを一度fillし、decodeのhit kernelsがresidentのcache slot pointerを使う。cacheはserve中に保持され、missとadaptive swapがあっても同じslot arenaのポインタ契約が前提。`ExpertCache::close`でarenaを解放できるが、live graphやresident mapが参照中に解放してはならない。arenaの後半slotだけを独立にfreeするAPIはなく、単一allocationである。
- SYCL verifierはT=1/T=4向けのarenaに含むstaging、hit scratch、logitsや活性workspaceを持つ (`src/core/verify.cpp:350-375`)。記録されたverify graphはcapture済みsegment/work graphとしてVerifier内に保持される。ログのfreeはcapture1後1429.1MiB、capture4後1298.9MiBで、合計約370MiB減ったことを示す。この値は既存runの実測。細目別内訳や全額が即時free可能なtemporaryであることは示さない。live verifier/graphで使うmemoryはdecode中の永続作業領域で、capture後に単純freeできない。
- speculative decodeはdraft head 834MiBをロードし、ログではheadが111MiB、draft expertsが675MiB。Verifierのwindow4は4-token proposal/verify arraysを使い、MTPとそのKV/stateはspeculation中に必要。`--spec 4`を維持する限りその容量をcache追加予算として二重計上しない。ログの `draft head over 106299 tokens (212.9 MiB)` は別のdraft data allocationの実測表示で、834MiBロード表示と同一allocationとは仮定しない。
- KV `int8 --kv-resident 32768` はQSAごとに32768 of 262144 cellsをGPUに残し、残りを3.09GiB pinned RAMに保持するというrun logの観測。KV GPU resident cells/model session stateはdecode live dataであり、prefill終了で一般に解放できる一時cacheではない。session自体は262144 contextの生成継続に必要。
- no-borrowのprefill workspaceはcacheから借りないので、cache領域との物理重複はない。prefillが各要求後にdestroyされるか、serveで同じPrefill objectを次要求にも保持するかは別のlifetimeであり、`--serve`のserve path / object ownerを追わずに「prompt後に全buffer解放」と断定しない。今回のログには個別Prefill allocationのbytes/free pointはない。
- reserve700はautoのcache sizing/retryで見ているfree-memory target。明示的single-GPU cache branchにはreserve対比によるslot減量がない。explicit128のprefill workspaceは後で別allocationになる。従ってmanual cache + no-borrow構成の安全性は設定値の足し算だけで保証されず、実allocationとrunでのfree watermarkを確認する必要がある。

## 測定前のguardと不足

1. 各候補の直前に、引数をparse後のeffective値として `cache_mode(explicit/auto), cache_slots, cache_bytes, profile_count, no_prefill_borrow, pf_borrow, prefill_chunk, reserve, mtp_bind` を1行で記録する。`auto`は各縮小後も同じ行で更新する。
2. cache allocation前のfree, cache open/touch後free, graph capture後free, prefill workspace init後free, request中のlow watermarkを同じdevice/phase labelsで採取する。既存ログの“everything loaded”とauto sizing時点を混同しない。
3. per-layer cacheのslot countとbyte totalを別々に出す。layer count map (base q, tail count, last layer id)を示し、borrow計算はtail開始offset・actual tail bytes・`bytes_needed`・`k`・残すslots128の四条件をログにする。
4. 明示cache+no-borrowのsingle GPUは、起動前のfit guardがreserveを反映していない。`free_before_cache >= cache_bytes + estimated_or_exact_prefill_bytes + verifier/draft/KV headroom + reserve`を別々に確認し、同じallocationの二重計上を避ける。実装guardを追加するなら、`Prefill::bytes_needed(g,ss,chunk)`とVerifierの実arena見積を使うのが現行コード上の具体的な境界。今回コード変更は禁止範囲なので提案に留める。
5. fault/health、温度/driver状態、baseline測定条件はMainの現在の直列run protocolに従う。autoまたはborrowの候補結果は、ログ行だけで性能採用せず、同条件のprefill/decode試料を保って比較する。
