# R469 — Elastic VRAM contract and SYCL adaptation audit

## Scope and source identity

Read-only source audit; no build, test, GPU, benchmark, profiler, process/config/service, fetch, Git, or cleanup actions were run. The upstream comparison uses the explicitly named pristine Niko worktree `bench-upstream-v0143-pristine-20261012` (v0.1.43); the ghq root has newer contents and was not used for upstream line claims. Fork code was read from the `yqYo1/Strata` main checkout and its active `sycl/` overlay. This report describes source contracts, not runtime support on the B570 or any other device.

## Niko v0.1.43 contract

- Elastic mode is opt-in at server configuration: `vram_elastic: true` appends `--vram-elastic`, and a positive integer `vram_segment_mib` appends the segment-size switch (`serve/server.py:2361-2367`). The REST command is therefore not an implicit allocator policy.
- `POST /v1/vram` accepts `reserve_mib` as a nonnegative integer MiB count, or `null` to restore the startup reserve; it rejects booleans, nonintegers, and negatives (`serve/server.py:5058-5068`). A model's page authorization check is applied before the mutation.
- Server behavior is explicitly between requests: it acquires the service FIFO with a 300-second timeout, optionally takes the batch control lock, and returns a busy response if those locks do not become available. If unloaded, it records the reserve for load and returns `status: not loaded`. If loaded, it calls the engine and updates `vram_reserve` only after engine success (`serve/server.py:3050-3080`). It refuses honestly if the engine object has no `vram` method (`:3057-58`).
- The engine protocol is one `VRAM [reserve_mib]` line and a `VRAM key=value...` response, or `ERR ...`; the client maps `ERR` to `ValueError`, updates reported slot/free figures only on success, and times out if no answer arrives (`serve/server.py:930-959`). This keeps an API-level capability failure distinct from an engine death.
- The command parser explicitly refuses when the process was not started elastic, the resident low-RAM complement is active, peer mode is active, a prompt loan is outstanding, or verifier commit/swap work is not drained. It then synchronizes device work before changing the cache (`src/program/generate.cpp:9094-9119`). Shrink evicts tail-slot residency, uploads the residency table, and re-lends the prefill buffers with a smaller chunk if needed; grow refills evicted slots and synchronizes copies before publishing the table (`:9120-9175`). It reports actual reserve/cache/free/chunk values (`:9176-9187`).
- Segmenting itself is NVIDIA CUDA VMM: `src/core/expert_cache.cpp:214-293` loads/uses the driver VMM entry points and allocates physical segments. A lower-level segment allocation failure is not the same as an unavailable capability; the command should return its failure rather than claim the requested reserve was met.
- Setup's persisted `vram_reserve_mib` is a startup `--vram-reserve-mib` argument, not the elastic opt-in. Existing reserve args are updated in the config on setup rerun (`setup.py:4277-4292`, `5653-5663`). The live endpoint's current reserve is separate mutable service state.

## Fork SYCL state and VMM limitation

- The main fork has the parallel CUDA VMM implementation at `src/core/expert_cache.cpp:322-384`, and the SYCL overlay has a different backend implementation at `sycl/src/core/expert_cache.cpp:290-346,363-419`. The overlay's `open_segmented` explicitly gates on `sycl::aspect::ext_oneapi_virtual_mem`, gets granularity, reserves one VA range, maps physical objects, and releases partial setup on failure. Its shrink/grow operates from the tail and updates `live_slots_` from mapped bytes. The specific source comments that Arc B570 can reject a 5 MiB physical allocation despite a 64 KiB reported minimum and that 6 MiB and 64 MiB succeeded (`:304-307`); this establishes why segment rounding/probing matters, not that runtime VMM is available on every device.
- SYCL CLI parses both elastic switches (`sycl/src/program/generate.cpp:1470-1471`) and admits only `--serve`, one GPU, no remote helper cache, segment size at least 64 MiB; HIP is refused (`:3495-3511`). A VMM aspect/gate failure at allocation is still possible after those option checks.
- The active SYCL command has the same essential drain and state transitions: no segmented cache, resident low-RAM complement, peer device, or outstanding prompt loan; wait verifier commit, finish adaptive swaps, wait device queues, adjust cache and residency, re-lend prefill buffers (`sycl/src/program/generate.cpp:6139-6185,6207-6260`). The API can expose these through the common server only if it preserves the engine `ERR` path and success data; the SYCL port does not get upstream CUDA VMM merely because the upstream root implements it.
- The command's current catch of `sycl::exception` logs and calls `std::exit(1)` (`sycl/src/program/generate.cpp:6282-6286`), while ordinary precondition and cache failures return a refusal. For a stable server/API contract, recoverable mapping errors should flow through `ERR` without killing the engine when the backend can preserve a valid mapped prefix and consistent residency. Device-loss/queue-fatal errors must remain process errors, not false success.

## Safe adaptation against primary cache/session behavior

The primary cache is an append-only expert residency table (`src/core/expert_cache.cpp:551-579`): `admit()` assigns a slot once and does not evict; filling a slot may enqueue asynchronous H2D copies (`:588-665`). The SYCL implementation likewise has host residency and live-slot accounting. Consequently, changing the mapping alone is insufficient: every host/device residency reference to removed tail slots must be invalidated before another decode can consult it, and any retained expert must be refilled before its residency is published after grow.

The safe boundary evidenced by the existing loop is process-level between requests, not an arbitrary in-flight resize. Keep the server FIFO/admission exclusion; in the engine, reject if any prefill loan remains out, wait verifier commit and adaptive swaps, then drain **all queues/copy callbacks that can touch the cache**. Resize only tail segments. Rebuild/publish the residency table after tail eviction; on growth, refill from stable host blobs, wait those copies, then publish. Recompute prefill borrow placement and chunk against the new live slot count. Ensure stale raw pointers / captured graphs cannot reference unmapped addresses; the existing opt-in gate excludes many cases (including multigpu/peer) but a port still must audit whether this run's captured graph or per-session state stores cache addresses. Keep the old reserve on failure and return a truthful refusal; do not update server state until the engine confirms actual results. No autonomous resize should be introduced.

Non-VMM choices:

1. Best direct port: implement an actual SYCL virtual-memory backend only when the device/runtime capability is present, then retain the same truthful opt-in / between-request / refusal contract.
2. If safe reclamation can be proven, an explicitly selected stop-the-world cache close/reopen or full-cache reallocation fallback could emulate the API, but it must drain pointer holders, reconstruct residency and refill before resuming; account for allocation failure and rollback. Existing nonsegmented `shrink(0)`/`grow(full)` in the SYCL cache demonstrates only full release/reallocation (`expert_cache.cpp:363-403`), not partial elastic sizing. Do not silently select this path without validating graphs, session state, and recovery semantics.
3. Otherwise expose capability as false and return a clear unsupported error (engine `ERR`, surfaced as API error); never return `status: ok` or update the configured reserve just because the HTTP request was syntactically valid.

The API should distinguish capability absence from transient segment allocation failure and device-fatal failure. A build-time / capability check alone is not proof that mapping succeeds at runtime. If partial map/unmap failure can leave uncertain backend state, mark the cache unavailable and fail the command/process safely rather than continuing with stale residency.

## Evidence limits

This was source-only. No claim is made about runtime ext-oneapi virtual memory support, successful segment allocation, device memory reuse, speed, or correctness on Arc B570. The source audit also does not establish whether every currently captured session graph in the primary SYCL serve path embeds cache addresses; this needs a targeted ownership/pointer audit before implementing resize.
