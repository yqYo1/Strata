# R470 — Primary chunk-major prefill transfer and 64K roofline condition

## Scope and conclusion

Read-only calculation from the primary P source, the recorded IQ3_S native pack layout and R466/R467 primary-run records. No source/config/Git changes, build, test, process inspection, profiler, CPU/GPU work, or cleanup was performed. This is a conditional source projection for a 65,536-token prompt, not a measured run or throughput claim. The current 61,055-token diagnostic stopped at the 53,248 chunk-start marker and has no completed long-prompt timing.

With the current 128-slot cache, no explicit `STRATA_PREFILL_RING=8`, and 4,096- or 8,192-token chunks, P enters its large-chunk `stream_all` route. It issues one host-to-device expert-blob copy for every expert that is not resident, in every chunk, before router selection is used to choose compute work. A 64K request therefore repeats roughly the whole 50.292 GB expert arena 16 times at 4K chunks or 8 times at 8K chunks. Filling all 128 cache slots only reduces that by at most 128 expert blobs per chunk. The 8K choice halves this route's expert-copy bytes per input token; it does not reduce the number of routed experts or the mathematical expert FLOPs.

## Copy count and bytes for 65,536 input tokens

Let `R` be the number of expert entries actually resident in the 128-slot cache at the start of the prompt (`0 <= R <= 128`). This residency inventory is not in the available completed-run evidence. Let `B_R` be the sum of those entries' actual layer-specific blob sizes. For either chunk size, the source path implies:

- Per chunk: `24,576 - R` H2D copy submissions and `50,292,326,400 - B_R` expert-weight bytes.
- At 4,096 tokens: 16 chunks. Copy submissions are `393,216 - 16R` (at most 393,216; 391,168 if all 128 cache entries are resident). Expert bytes are `804,677,222,400 - 16B_R` (804.677 GB with no residency; 799.225 GB at the most favorable possible 128-entry residency, where each cached blob is the largest 2,662,400-byte type).
- At 8,192 tokens: 8 chunks. Copy submissions are `196,608 - 8R` (at most 196,608; 195,584 if all 128 entries are resident). Expert bytes are `402,338,611,200 - 8B_R` (402.339 GB with no residency; 399.612 GB at the same most favorable 128-entry bound).

Thus, even a fully occupied 128-slot cache removes no more than 0.341 GB of the 50.292 GB arena from each chunk; actual savings depend on which formats occupy those slots. These figures count expert H2D payloads. For unpinned experts, CPU source-to-stager copying and issue/wait time add work, but do not add another H2D payload. `experts_streamed` and `experts_dma` are not completed-byte counters (R459); the final copy-stream sync only proves completion for a successful request. No current per-layer submitted/completed-byte trace exists.

## Necessary 1,000 input-token/s conditions

A 65,536-token input at 1,000 input tokens/s must finish its prefill in `65.536 s`. Dividing the conditional expert-byte totals by that wall budget gives the required *effective sustained H2D payload rate*, before allowing for scheduling gaps or other device traffic:

| Chunk | Expert H2D rate with no resident entries | Lowest rate possible with 128 max-sized resident entries |
| --- | ---: | ---: |
| 4,096 | 12.278 GB/s | 12.195 GB/s |
| 8,192 | 6.139 GB/s | 6.098 GB/s |

These are decimal GB/s. If non-expert traffic shares the copy engine, the engine must provide that rate plus the other traffic. If copies cannot overlap the critical compute path, the effective copy duration must fit within the smaller residual after compute; the rates above are necessary aggregate payload rates, not a prediction that the B570 can sustain them or that overlap is perfect.

The expert arithmetic gives an independent necessary compute floor. For N=2,560, FF=640, K=10 and 48 MoE layers, one selected expert performs two `1280 x 2560` gate/up products and one `2560 x 640` down product. Counting multiply and add as two FLOPs, that is `2 * (1280*2560 + 2560*640) = 9,830,400` FLOPs per selected expert row/token. Across 10 selected experts and 48 layers, the routed-expert work is `4,718,592,000` FLOPs per input token, or `309,237,645,312,000` FLOPs for 65,536 tokens. It requires at least **4.719 TFLOP/s sustained useful routed-expert arithmetic** to meet the 65.536-second budget, before shared experts, attention, dense projections, routing, quantized-decode overhead, launch/host costs, or stalls. It is a geometry-based lower-bound calculation, not measured device throughput. Total useful model work is higher.

For 8K chunks, transfers per token are approximately half the 4K case because the same nonresident expert set is copied once per chunk. The source does not establish that 8K chunks fit the current VRAM/borrow budget or preserve numerical behavior under the same context settings; a run must verify both before treating the lower transfer requirement as an available speed setting.

## Limits and decision

The historical 6.5 GB/s figure is not used as a current capability claim. No measurement in this report says that the B570, host RAM pinning path, or this configuration sustains the derived rate. Actual `R`, copy bytes, routing distribution, stage time, compute time, overlap, and 8K memory fit remain unknown without a completed, diagnostics-off 64K run plus a separately bounded transfer census. Do not label 1,000 tokens/s achievable from this arithmetic alone. It shows why the current chunk-major full-stream schedule places a roughly 12.2–12.3 GB/s expert-transfer floor at 4K and roughly 6.1 GB/s at 8K, alongside at least 4.72 TFLOP/s useful MoE work.
