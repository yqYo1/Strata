## Finding

There is no single “fastest settings” result equivalent to the present 61K-input, 262144-capacity diagnostic. The strongest clean long-prefill number in the Oct 4 IQ3_S campaign is 184.61 input tokens/s for a 4,007-token prompt (three alternating pairs; median 21,705.2 ms), with exact XMX tile 8, compact grids, ring 8, same-queue prefill, direct FP16 prompt KV, five pool workers, and adaptive swaps off. It used `--max-context 8192`, FP16 KV in VRAM, and 512 expert slots on the same B570/5600X. The current diagnostic instead uses a 61,055-token model prompt, context capacity 262144, int8 KV with 32,768 resident cells, and 128 expert slots, while reaching only input position 53,248 before a 1,200-second owner deadline. Those measurements differ materially in prompt length, capacity, KV representation/residency, cache capacity and completion status; 184.61 is a historical reference and not a current speed target or baseline.

The key state distinction is `--native`: when followed by a GGUF path it means both “load the native GGUF source” and “enable the native full-context preset.” It is not a neutral label for native expert weights. The parser sets a bundle of experimental native operations whenever the path is nonempty. The current diagnostic already passes a GGUF path, so those preset operations are not “disabled optimizations” waiting to be activated. The independent setting `STRATA_SYCL_NATIVE_HIT_GRAPH=0` does disable the measured captured GPU expert-hit path; the historical accepted runs left it unset and log that native hit kernels were captured. Clear only that `=0` to restore the default capture path for a clean follow-up, subject to current runtime validation.

## What `--native GGUFpath` does in P

At the audited current source, argument parsing stores the value in `o.native_preset`; startup resolves every shard and PLE table; then a nonempty preset sets `stream_token`, `gr_native_mmvf`, `native_bf16`, `native_bf16_extra`, `native_ple_key`, `native_moe_combine`, `native_gdn`, `native_router`, `native_qsa`, `native_qsa_indexer`, `native_rope`, and `native_ple_postops`. It also defaults the native head to the same GGUF and the dense projection inputs to all model shards plus a non-standalone PLE shard. The native hit graph is prepared later from the expert-cache path and is controlled separately by `STRATA_SYCL_NATIVE_HIT_GRAPH` / `--no-capture`.

Do not remove the model path to turn off experiments: it is the source for P's native model and required to reproduce these runs. Do not treat it as enabling exact CPU-oracle q8_0: the startup comment says the CPU expert pool remains on its VNNI kernel; `--cpu-oracle-q8-0` is a distinct explicit option. Likewise native preset, native cache hit, token graph, and graph-recording property are separate choices. The historical `STRATA_SYCL_NATIVE_RECORDING=1` experiment lowered median decode from 22.98 to 21.52 token/s under its own 128-token context-512 fixture and was not accepted as a speed setting. `STRATA_SYCL_VERIFY_NATIVE_CAPTURE` is a third graph control: its `small` mode applies native recording only to short speculative verifier windows, separately from the ordinary native expert-hit graphs and full native-recording experiment. Do not enable it by analogy with the measured native expert-hit graph.

## Decode measurements: separate fixture rankings

The Oct 4 selected context-512 setup's strongest later repeated coding medians were around 20.18 token/s (`2026-10-04-sycl-cpu-iq3s-index/run.json`: 20.120→20.183 with five alternating engine pairs); first coding was effectively unchanged. `STRATA_IQ_SINGLE_EXACT=1` passed CPU-object/GGML bitwise component checks and the five-run engine screen matched output IDs, but decode change was small and fixture-specific.

Older October 3 accepted-path screens report higher decode rates under different cold/warm 37-token prompts, FP16 KV, context 512, four workers, cache policy, PLE placement, speculation and host-load conditions. Examples include 22.86 token/s median for a 128-token ordinary run with Q2 XMX, and 21.61 token/s for single-column Q4_K ESIMD. A single settings screen reached 25.32 token/s for Python with adaptive refills; later controlled measurements say that policy did not establish a better setting. Two service processes' third warm Python request was 28.88/28.77 token/s after prior requests had filled the cache; this is a warm repeated request, not a steady-state or matched candidate median. These values should not be collapsed into one “fastest decode” claim or compared with the current diagnostic. The broadly supported simple result remains that captured resident GPU hit graphs improved the 128-token fixture's median from 18.93 to 19.51 token/s (+3.1%) with same IDs and cache-hit counts; their exact 2,048-slot/context-512/four-worker setup is also unlike the current 128-slot/262K/int8 request.

## Numerical and measurement gates

For a no-source-change follow-up, set the accepted environment toggles before starting a new process; retain current int8 KV, `kv-resident`, expert-cache capacity, 262144 context, `--no-prefill-borrow`, fixed prompt, MTP runtime and spec arguments. First check the built-in mode/route messages show exact XMX tile 8, compact dispatch, ring 8, same queue, and GPU hit graph captured. Keep clean benchmark timing separate from UR full trace/timers. Validate completion to the same prompt end and fixed output count, compare output IDs, MTP acceptance/round/window counters, request fault/event/lifecycle result, and a fixed-token logit ledger against the corresponding baseline. Source-level or host microbenchmark parity alone is not an endpoint gate. If the longer diagnostic does not finish within its owner deadline, report it as incomplete and do not turn partial reached context into a throughput rate.

The old whole-model prefill acceptance compares output IDs and separate component tests establish bitwise arithmetic for the selected kernels; it does not establish that int8/resident-KV and the current bundled native preset reproduce FP16 logits. Preserve those differences explicitly. The next clean Niko stock benchmark should compare identical model/shard hashes, prompt token IDs, sampler, max output, context/KV/cache settings, runtime and instrumentation status against a successful P baseline; the older numbers only give proven candidate settings for its own fixture.

## Primary rejected or non-adopted settings

- Routed ring 96 was slower than ring 8 in its three-pair 4K comparison; use ring 8 for the accepted chunk>=1024 route. Do not misread the shared `--expert-cache-per-layer` setting as Xe layer-major scheduling.
- XMX packing (`STRATA_SYCL_MMQ_XMX_PACK=1`) and array/quarter reductions or tile-16 alternatives were rejected/slower or introduced scratch/spill tradeoffs. The accepted long-prompt environment explicitly has pack `0`, exact arithmetic, tile `8`.
- `STRATA_SYCL_IQ_ESIMD=0` restores the preceding IQ dispatch and is slower in the relevant measured products; default enabled was bitwise-equal in 56 real-expert arrays. The whole-model dataset still does not turn component speedup into a general generation claim.
- Context/KV format changes, cache size, prompt borrowing, adaptive replacements, or MTP policy changes are not part of merely enabling these accepted kernel paths. Keep them fixed during the next baseline comparison.
