Question answered
Existing timers can identify phase work, but they do not by themselves establish the end-to-end critical path. Several timings overlap: prefill host issue and device copy overlap compute; decode CPU expert work may overlap the GPU hit graph; event waits measure completion of prior device work, not necessarily idle. Attribute the critical path by pairing one marked HTTP request window with the VTune host/device timeline and Strata's stage counters, preserving overlap instead of summing all phase durations.

Source attribution and interpretation

Prefill:
- `src/prefill/prefill.cpp:1224-1262` implements `STRATA_PREFILL_TIMING` phase intervals on the compute stream. The interval since one marker is charged to the preceding phase. A reported interval can include a device wait for host grouping or a copy dependency; it is not a kernel-only duration.
- `src/prefill/prefill.cpp:1488-1492,1573-1653` implements the streamed expert ring. The inline `ms_experts_host` interval includes slot/stager waits and submission work. In the threaded issuer path, `iss_ms` includes staging/slot waits and API submission on the issuer thread. Neither is DMA-completion time. `experts_streamed` counts streamed experts; `experts_dma` counts only the direct pinned path, so neither alone is a byte-completion counter.
- `src/prefill/prefill.cpp:2036-2042` makes the compute stream wait on the prior `copied` event before GEMM. The device-timeline wait-copy span is a dependency wait, and may expose a copy critical path; compare it with copy completion and issue times rather than adding it to host issue time.
- On successful completion, the final compute/copy stream synchronization around `src/prefill/prefill.cpp:2704-2712` establishes that submitted copies have completed. The current aggregate output does not provide per-layer completed bytes. A minimal follow-up counter, if attribution remains ambiguous, is per-layer submitted blob count and `count * ExpertLayout::blob_bytes(layer)`, plus a completion marker after the copy stream synchronization; record failed/incomplete requests separately. Pair this with request wall time, issuer CPU span, copy-event intervals, and compute dependency waits. Do not sum overlapping intervals.

Decode:
- `src/program/generate.cpp:5871-5889,6003-6016` prints `STRATA_DECODE_TIMING` request windows/average token time, wall verification time, `ver.ms_wait`, per-layer host `ver.ms_pool`, plan/activation/job/CPU-drive intervals, commit/emit and draft work, routing/cache counters, `pcie_experts`, and the GPU profile stages.
- In SYCL, `src/core/verify.cpp:1260-1280` measures `ms_wait` around `cudaEventSynchronize(layer_done_)`. This is completion latency for the preceding GPU segment, not necessarily GPU idle time. `ms_pool` spans host planning/activation/CPU work after that event and can overlap the optional GPU hit graph. The `copy_` synchronization around `src/core/verify.cpp:1332-1336` ensures the preceding asynchronous source-copy callback has completed before advancing.
- `src/core/verify.cpp:1492-1501` enqueues `n` expert blobs of `bytes` through `fetch_dma`; its host callback signals after queued H2D completion. For true copied bytes, count actual enqueued copies times per-layer blob bytes and count them complete only after that callback/synchronization. Do not use `pcie_experts` as bytes: `src/core/expert_source.cpp:1927-1995` increments that counter when planning fetch groups, before fetch execution; mapped/alias modes can read directly and pass zero copies to `fetch`. Keep separate planned groups, direct-mapped reads, H2D-submitted bytes, and H2D-completed bytes if this becomes a suspected bottleneck.
- `src/core/expert_source.cpp:2032-2114` separates planning, activation queue, job creation, and CPU run time. The job count is actual unique misses; source format is available per layer. File/source logical bytes and prefetch counts are not physical storage I/O or DRAM bandwidth.
- `src/kernels/cpu/pool.cpp:669-691` reports per-phase wall time for the native split path (Gate/Up, quantization, Down), but not worker-active versus worker-wait time. The generic `ExpertPool::phase_ms` wait-for-park/drain/repark counters belong to `run()` and should not be assumed to describe `run_split_multi_native`. `--stats` can give aggregate pool phases; `STRATA_POOL_TRACE` is too perturbative for the first pass. If VTune stacks and phase times still cannot distinguish compute from pool synchronization, the smallest useful instrumentation is bounded per-worker active and wait nanoseconds/jobs per phase, aggregated by `(layer, gu_type, down_type)` rather than a full per-expert trace.

Reading the result
For each marked request, compare host request wall, CPU stack/sample timeline, GPU queue/task timeline, existing phase spans, copy completions, and pool phase totals on the same interval. Identify which dependency controls request completion. A phase's CPU time may overlap GPU execution; `ms_wait` may simply await useful GPU work; planned PCIe group count is not transfer volume; and worker-phase wall time is not aggregate worker CPU time. Only after this correlation should a bottleneck or optimization target be named. The initial collection uses `xpu-offload`; `gpu-hotspots` is a separate optional experiment only if the local Arc B570 driver/tool capability check confirms GPU hardware metrics are available.
