## Existing protocol and its semantics

The shared Python server code is Niko's service implementation in the exact same blob in all three trees. Its `StrataEngine` behavior is in `serve/server.py:391-417,488-515,517-532,708-779,781-811,815-844,864-1115`.

- At startup, the server reads `INFO` and `READY`; `INFO batch_slots=N` is the negotiated engine capability, not a promise inferred from the config. It creates one per-slot output queue, slot busy/held-prefix/live state, one admission/control lock, a serialized stdin write lock, and one stdout pump that demultiplexes `BT <slot> ...` and `BDONE <slot> ...` to that slot's consumer.
- `parallel=N` is an opt-in persisted by setup. `parallel_args()` maps it to `--batch N`; the server uses batch mode only when the engine reports a nonzero `batch_slots`. `--batch-groups G` changes slot order and pipeline groups for split stages; it is not a requirement for single-GPU batching.
- Concurrent HTTP requests do not concurrently write control commands. The `ctl` lock serializes request admission/prompt reads; each request thread can then wait on its own slot queue while the pump routes output. A per-thread `last` result keeps each response's `DONE` metrics associated with that request.
- When alone, `generate_batched()` starts on the normal fast `GEN`/`GENI` path, including MTP drafts where configured. If another request waits, it sends `STOP`, consumes the solo request through `DONE`, and if it can continue sends `BGEN` with the original prompt plus emitted output. That migration avoids losing the prefix already computed.
- Otherwise it chooses a free slot preferring the longest exact held-token prefix of the prompt, then an empty/least-recently-used slot. It sends `BGEN`/`BGENI` under the admission lock. The engine reads the prompt and obtains the first output on the normal one-request path, then returns `BADM <slot> <continues>`. On acceptance the slot owns its session; subsequent generated tokens are `BT <slot> <token>`, and completion is `BDONE <slot> <count> <reason> <ms>`.
- Cancellation is a state transition, not immediate slot release. A cancelled/abandoned solo stream sends `STOP` and drains through `DONE`; an admission drains through `BADM`; an admitted request sends `BSTOP <slot>` once and the background consumer holds the slot until its `BDONE`. The engine stops the slot at a safe next decode window. The held prefix is only the prompt plus tokens actually fed into session state (the final emitted token may still be pending as the next input).
- Current Niko server also implements prompt fairness: `_take_control()` tracks queued prompt lengths and a control epoch; a long read may yield to a much shorter prompt using `BYIELD <slot>` and later `YIELDED <slot> <tokens>`. It tries at most two yields. It can return a sufficiently long, now-solo slot to the normal `GEN` path when slot-cache is reported. An unchanged server may emit these commands, so a P engine cannot assume only BGEN/BSTOP unless the server is capability-gated or updated.

Niko's C++ implementation confirms that the batch window means independent sequences, not ordinary speculative rows: `include/strata/core/verify.hpp:131-168` describes one token per slot with each slot's own GDN/QSA/Ple state, exposes `init_slots`, `run_slots`/`run_slot_rows`, `commit_slots`, and per-slot sampling. `src/program/generate.cpp:5879-5910,5918-5941,6020-6037,6061-6074,6195-6225,7352-7385` maintains slot request metadata, copies session state into slot storage, emits per-slot tokens/completion and sends `BADM`. In the ordinary batch verifier, drafts are not the batch row contract; the separate solo path retains the faster drafted stream.

## Primary's current loop and state boundary

P advertises `READY <context> stop` at `src/program/generate.cpp:5217`, and its stdin reader treats `STOP` as an atomic signal (`:5067-5122`). The main service loop at `:5234-5255` accepts only `GEN`/`GENI`, clears the one stop flag per request, and processes one request body through completion before reading the next command. At `:5248-5250`, other commands receive an `ERR expected: GEN ...` response; there is no batch capability announcement, slot demultiplexing or `BGEN/BSTOP/BADM/BT/BDONE` state machine in the P generator. P's strict startup argument parser also rejects an unsupported `--batch` option (`:1381-1386`).

The inference state is single-request today: one `SessionState ss` in the main engine scope (`src/program/generate.cpp:2144`) and one serve `Verifier ver` (`:4629-4643`), one bound `MtpDrafter mtp` (`:2718-2730`), request-local input/history/draft/output vectors inside the `GEN` loop (`:5253-5288,5853-5890`), and one `Verifier::ss_` pointer (`include/strata/core/verify.hpp:207-218`). P's `Verifier::run(T, tokens, pos0, ...)` consumes a contiguous speculative window for this one session (`verify.hpp:76-78`); T rows are not distinct requests. P has existing session snapshot machinery (`include/strata/core/conversation_snapshot.hpp:50-77`, `conversation_state.cpp:247-293`) that captures/restores a complete `SavedConversation` with its session, checkpoints, KV layers and draft KV, and explicitly rejects use after a partial failed restore. This is useful for slot isolation/context switching, but it does not by itself provide a slot scheduler.

The primary route worth preserving is the existing single-request `GEN` path: P prefill/sampling/session setup, its native SYCL `Verifier`, existing cache/expert-source/CPU-pool dispatch and MTP behavior. P already handles cancellation at prompt chunk and verifier-window boundaries (`src/program/generate.cpp:5602,5822-5836,5990-5999`) and waits for the final asynchronous commit before session snapshots or future work (`:5997-6000`). Batch support should be an opt-in service/control path around this machinery.

## Minimal correctness-first adaptation

Implement an explicit single-GPU slot mode in the primary generator while leaving `GEN` untouched. This is a control/service adaptation plus isolated per-slot state; it does not copy CUDA batch kernels. It should be staged so P never reports batch support before every part of the contract is present.

1. **Capability and admission.** Parse `--batch N` only for serve mode and a documented range. Compute the number of slots that fit using P's actual `session_bytes`/snapshot budget, existing VRAM cache and reserve; return `INFO batch_slots=N` only for usable slots, otherwise `INFO batch_slots=0` plus a reason. The shared Python server already warns when requested N differs from the engine's reported count, then uses serialized `GEN` if count is zero. On one GPU reject `--batch-groups > 1` clearly; never claim stage pipelining. Use `INFO slot_cache=1` only if prompt/session prefix reuse really works.
2. **Keep command ingress single-owner.** Preserve the existing stdin reader thread and `STOP` signal, but route non-STOP lines into a single state-machine owner. Validate slot range/free state and parse sampling/max-new/token IDs before touching inference state. Serialize prompt admission and model/cache mutations; do not run two `ExpertSource`/pool mutations concurrently. Preserve `GEN` and its output/finish schema verbatim.
3. **BGEN admission through the existing fast route.** Initially handle BGEN by using the same prompt parsing and P prefill path as GEN, including its first-token behavior. After the prompt/first output and `ver.wait_commit()` establish a safe boundary, save a complete primary session image into that request's slot. Reply `BADM slot 1` only after the image validates and the slot is usable; reply `BADM slot 0` for an ended/invalid/cancelled request. This mirrors Niko's actual promotion mechanism: normal GEN first, copy session to the slot, then keep the next un-fed token in slot metadata. If admission/copy/restore fails, invalidate the slot and return an error; never infer from a partially restored session.
4. **Independent slot state; reuse P inference, not Niko's GPU implementation.** Each active slot needs the prompt/prefix it holds, next input token and position, generated/max-new counts, finish/stop state, sampling and penalty history, control vector setting, image identity/state when supported, timing and returned usage. Its saved engine state must isolate every mutable sequence field: recurrent GDN/PLE history and previous tokens, QSA KV/indexer, session checkpoints, and any draft state. The smallest source-level implementation can time-slice one live P `SessionState`/`Verifier` by saving slot A, restoring slot B at committed boundaries, executing one ordinary single-token `Verifier::run(1, ...)` plus commit, and saving B. P's snapshot API already provides a possible safe transfer contract. This serializes device work and can copy large KV state on every switch; it is a correctness-first service mode, not Niko's batched throughput. A resident `SessionState`+`Verifier` per slot avoids per-step snapshot copies but spends VRAM proportional to slot contexts and duplicates graph/session buffers; either option must be budgeted and reported honestly. Do not reinterpret `run(T)` speculative rows as separate slot rows.
5. **Token scheduler and messages.** At each committed boundary, fairly select a runnable slot and run its next token through P's same T=1 path (batch mode can disable MTP drafts just as Niko's independent-slot verifier does). Emit and flush `BT slot token`. After EOS, length/context exhaustion or a requested stop, finish the last committed token and emit exactly one `BDONE slot count reason ms`; only then clear/reuse the slot. Keep `GEN` MTP fastpath unchanged when there is one ordinary request. Initially either implement BYIELD/YIELDED as serialized prompt-chunk boundaries or add an explicit capability/version to the server so it will not send them to P; silently ignoring them can strand the admission lock.
6. **Prefix and promotion rules.** Keep each slot's exact session-held token prefix. For BGEN, select/reuse only a slot whose stored prefix is strictly shorter than the prompt and byte-for-byte matches, with matching control-vector and any image identity; otherwise process the full prompt. Do not count the last emitted token as held until it was fed and committed. When promoting a running solo request, drain `STOP` through its `DONE`, then submit its full original prompt plus emitted tokens as BGEN; compare the new prompt to the live session before reporting REUSED. For image requests, disable prefix reuse unless embeddings/image identity is part of the match key. Preserve per-slot conversation turn checkpoints if session reuse is offered; a token-prefix match alone must not cross conversation/control-vector/image boundaries.
7. **Cancellation and HTTP disconnect.** A stop/cancel request is sticky for its slot, checked after prompt chunks and after each completed inference/commit boundary. The HTTP consumer may stop receiving immediately, but its slot remains busy until engine `BDONE`; slot state and queued output are drained before the next admission can reuse it. Solo request cancellation drains through `DONE`. Admission cancellation drains through `BADM`. Invalid slot IDs, duplicate BGEN, malformed `BSTOP`, EOF, engine error and duplicate terminal messages must not leak tokens across `slot_q` streams.
8. **Memory limit and truthful capability.** Setup's `parallel` recommendation is opt-in; P must report requested and effective slot count and why capacity reduced to zero/lower N. Consider session plus graph/work buffers, P's cache reserve and existing server load, not just token count. If no useful slot count fits the current B570 configuration, preserve saved config but emit a clear capability message and run one request at a time only if the product explicitly allows that fallback. Do not claim that saved `parallel=2` means simultaneous GPU decode unless the implementation does independent-row scheduling.

This is the minimal correctness-first design for concurrent service streams while retaining P's inference kernels and solo speed path. If product semantics require the same throughput promise as Niko's “up to N requests decode together”, a later native `Verifier` independent-row path is required: per-row slot positions and sampling/history, per-slot session writes for GDN/PLE/QSA, shared model/cache dispatch semantics, per-row commit and EOS/stop handling. Niko's `init_slots/run_slots/commit_slots` is a useful contract reference; it is not code to transplant blindly into P. The sequential snapshot mode must be described as interleaved/serialized computation, not equivalent batching. Performance and user-visible throughput need a separate future measurement.

## Correctness and review gates before advertising support

- Protocol state-machine checks: `INFO/READY`, malformed and duplicate slot commands, free/busy lifecycle, one `BADM` per BGEN, `BT` routing, exactly one `BDONE`, EOF/engine death, pipe write serialization, and compatibility with both image and text command formats. If server sends BYIELD/YIELDED, assert prompt-chunk resume and lock release/reacquire order.
- Cancellation tests at prompt, first-token admission, between tokens, after a generated stop token, before asynchronous commit completes, client disconnect, and slot reuse. Verify that no token/DONE/BDONE from a previous slot is consumed by a later HTTP response.
- Interleaved two-prompt state-isolation tests against independent serial GEN results: alternate different positions and prompt lengths, then verify each request's token sequence and final state hash. Include QSA KV/indexer, GDN recurrence, PLE previous tokens/history, cache slots, penalties/seeds, cvec toggles, context limit and EOS/length. A restore/transfer error must invalidate that slot, never continue.
- Prefix tests: exact reuse, first-token-not-yet-fed boundary, common-prefix mismatch, turn checkpoint, differing cvec, images/embeddings, and a slot whose prior response was cancelled. Report `REUSED` only for state actually present.
- Regression check the unchanged single-request GEN output/sampling/MTP/session behavior and ensure batch opt-in does not alter default `parallel=1`. Separately enforce slot memory cap and correct `INFO batch_slots` negotiation. None of these checks was run for R468.

## New evidence and limits

R465 already established the main point: P's shared server maps persisted `parallel >= 2` to `--batch`, but P generator rejects it as unknown; the service code is Niko-identical. R468's new detail is that Niko's `BGEN` deliberately runs the initial prompt/first token through the solo GEN route, then copies the live session into a slot and acknowledges with `BADM`; it uses exact held-prefix selection, cancellation draining, and per-slot response queues. It also distinguishes Niko's independent one-token slot rows from P's speculative multi-token window, and identifies P's existing complete conversation snapshot as a state-transfer primitive for a low-memory correctness-first adaptation.
