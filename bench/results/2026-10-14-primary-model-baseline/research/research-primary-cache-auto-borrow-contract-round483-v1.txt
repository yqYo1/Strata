No build, test, model execution, process query, GPU/profiler work, GGUF payload read, source/config/Git mutation, or cleanup was performed. The only write is this report. ## Conclusion

The current explicit 128-cache/no-borrow recipe is a valid comparison point, but “128 slots” has two meanings in its SYCL per-layer path: the CLI value is first converted to a budget of 128 maximum-blob sizes, then exact per-layer blobs use that budget. From the installed 48-row metadata this yields 161 actual slots and 339,942,400 allocated bytes, under the 340,787,200-byte budget. `--expert-cache auto` uses the same largest-blob budget as its unit before applying per-layer expansion. Neither count is itself proof of enough room for the whole serve process.

`--expert-cache auto` is a reserve-based estimate taken before some serve allocations. It accounts for the selected prefill mode/chunk estimate and, when the native head is loaded, `MtpDrafter::bind_bytes`; it also reserves the configured VRAM reserve. It cannot observe the later exact prefill arena, verifier device arena, lazy T=1/T=4 graph capture/instantiation overhead, or other allocations made after the sizing snapshot. There is a post-touch cache retry loop and later serve free-memory check, but the check prints a LOW/stall warning below the requested reserve rather than failing startup. Thus auto is a useful sizing candidate with staged admission checks, not a blind OOM-proof or peak-memory planner.

Borrowing is a specific lifetime choice: with an expert profile present and no `--no-prefill-borrow`, prompt scratch is carved from the end of the same cache allocation, the corresponding cache residents are unpublished while the prompt owns those bytes, and they are refilled/published before decode resumes. It does not create a second cache allocation and does not permanently remove cache capacity. Without borrowing, the serve `Prefill` owns its prompt workspace in addition to the cache and retains that workspace through decode and subsequent requests (R472). This makes the cache/borrow lever meaningful only when a valid profile is available and the exact lend plan passes.

The source establishes no performance winner among the proposed arms. The measured current hit rate of 0.8–2.3% does not show whether the cache is on the critical path, whether those hits justify extra resident bytes, or whether a larger cache improves accepted-token throughput. Keep all kernel, context, KV, MTP, speculation and PCIe settings fixed in each arm. Require full startup and lazy-capture headroom checks before comparing speed.

## Exact sizing and fill semantics at this pack

The configured text metadata is `native_experts.txt` for 48 layers, 512 experts/layer. Its `blob_bytes` are 1,510,400–2,662,400 bytes and sum to 98,227,200 bytes for one expert in each layer; every entry is a mixed-format GU+Down blob. The per-layer slot helper rounds sizes to 256-byte boundaries (these sizes are already aligned).

`--expert-cache N` parser semantics are direct integer `N`; `--expert-cache auto` stores `-1`. If an expert-profile file is loaded and CLI value is `0`, the code also changes it to auto. In the auto branch, before the per-layer adjustment, the base count is approximately:

`slots0 = max( floor((free_at_cache_snapshot - reserve_bytes) / max_blob), 0 )`

where `max_blob = 2,662,400`, `reserve_bytes = (vram_reserve_mib + prefill_mib) * 2^20 + mtp_bind_bytes`. The profile length caps `slots0` when a profile exists. For the current **no-borrow, explicit prefill 4096, reserve 700 MiB** mode, the source's estimate is `prefill_mib = 160 + floor(4096*680/1024) = 2,880 MiB`; thus the prefill+configured reserve term is 3,580 MiB before the MTP bind estimate. This is a source formula, not a measured 4K workspace size.

For `--expert-cache 128 --expert-cache-per-layer`, the requested uniform-equivalent budget is `128 * 2,662,400 = 340,787,200` bytes. `per_layer_slots_that_fit` divides this by the sum of one aligned blob per layer, assigns three slots to each of 48 layers, then uses the remaining budget for 17 additional last-layer slots: 161 slots total, 339,942,400 bytes. The largest layer (47) therefore owns 20 slots; other layers own 3. This is the exact static slot map implied by the checked-in helper and supplied `native_experts.txt`, not a runtime observation of cache fills/hits.

In the auto path, the code first calculates a largest-blob-equivalent budget and then applies this same per-layer expansion. During allocation it checks actual `cudaMemGetInfo`, zeroes/touches the cache, rechecks free memory, and may close/reopen smaller until the configured reserve is met within its 64 MiB tolerance or the cache becomes too small. On allocation failures, auto can retry at three-quarter byte budgets (up to its retry count). This may make the actual count smaller than initial estimate. The cache is then filled once from the profile in rank order, respecting each layer's own slot range; the route starts with those entries resident. No eviction occurs in the static profile path. Per-layer admission without a profile fills from whichever routes first arrive, separately within each layer; `--expert-cache-per-layer` alone does not create a frequency profile.

The serve verifier requires a non-null profile-filled VRAM tier. Its error text says the graph hit route additionally needs `--expert-profile`. Therefore any candidate relying on graph hits must preserve the exact matching profile and verify that profile fill completed. The small observed hit fraction is not a reason to substitute a foreign profile or to change cache arithmetic without a route-history comparison.

## Borrowing and chunk selection: what the flags actually do

The source's serve predicate is exactly `pf_borrow = !o.no_prefill_borrow && !o.expert_profile.empty()`. A profile is required; `--expert-cache-per-layer` is a separate admission/layout policy. `--no-prefill-borrow` keeps prompt workspace in its own device allocation, alongside cache. With the default profile-backed borrow path, `Prefill::bytes_needed(g, ss, chunk)` is measured against the cache tail. For sized slots, the code walks backward from the end of `xcache.slot_offsets()` until the accumulated tail bytes cover this exact need. For uniform slots it rounds bytes by `max_blob`.

The serve plan requires both (a) enough actual tail bytes for `Prefill::relayout` and (b) `borrowed_slots + 128 <= xcache.slots()`. With explicit `--prefill 4096`, it tries 4096, then halves until 256; an explicit chunk has no percentage cap. If no cache loan is available, the serve path can use owned prompt buffers and runs its own free-VRAM check, with a 512 MiB allowance, stepping among its supported smaller chunks where necessary. It reports the chosen chunk/borrow and errors if initialization still cannot fit. For short requests the actual loan is based on `request_chunk(tokens, configured_chunk)`, rounded to 256 and capped at the configured chunk; unused tail capacity is not lent merely because the configured chunk is large.

For the current per-layer 128-equivalent budget, the metadata-derived slot count is 161. The borrowing floor leaves at most 33 slot indices available to lend; those last 33 slots represent 82,457,600 bytes for this exact layer ordering. This is the *maximum tail storage before the floor*, not proof that a 4096 or even 256 chunk fits; `Prefill::bytes_needed` includes fixed scratch, QSA/session-dependent staging, MMQ buffers and the ring, and it must be checked at runtime with the actual initialized model/session. An important consequence: do not infer “128 cache slots means a 4096 borrow is available” from CLI arguments. The actual allocated slot count and byte tail are separate quantities.

When a prompt segment lends slots, the host residency entries in that participant's tail are marked nonresident and uploaded; the streamed prompt path uses the alias as scratch. After the segment, `refill_issue` copies each lent `(layer, expert)` back into its original cache slot; `refill_wait` synchronizes queued fills, then residency is uploaded. A cache restoration failure ends the request before normal decode; cancellation during prompt also executes refill. For requests restored entirely from existing checkpoints, `windows_ok` can use stored windows without a new batched prompt/loan. For ordinary batched prefill, decode sees the restored cache after the prompt's final refill. Refill correctness and state hashes must be checked on a candidate; do not treat pointer aliasing as persistent expert residency while the prompt owns the tail.

`--prefill auto` is an independent chunk policy. At argument validation it is forced off and set to 2048 when `--no-prefill-borrow` is given or no expert profile exists. With borrowing available, the planner scans its supported chunk list and applies `STRATA_PREFILL_LEND_PCT` (default 90% when pinned-share is at least 0.9, otherwise 85%) plus the 128-slot floor. Chunks above 8192 require `auto:N` / `STRATA_PREFILL_AUTO_MAX`, and remain capped by `--max-context`. The percentage environment value is parsed as an integer; this report recommends leaving it unset. Keep the current explicit `--prefill 4096` for a one-lever comparison; do not assume `--prefill auto` means the same setting under no-borrow.

## Where auto sizing ends and serve allocations begin

For the requested single-GPU serve shape, the important order is:

1. Model/session and MTP draft model/state are loaded; the native main head is loaded before cache sizing. These allocations are included in the free-memory snapshot or reflected through `MtpDrafter::bind_bytes` for the later bind-time logits/head subset.
2. `ExpertCache` allocates and touches storage. `--expert-cache auto` tries to leave `--vram-reserve-mib` after touching; profile fills and sample slot verification follow.
3. `serve` initializes `Prefill sp`. No-borrow allocates its own chunk workspace; borrow uses a cache-tail alias. `Prefill::bytes_needed` includes a fixed 8 MiB slack, model/session QSA geometry, MMQ/GEMM scratch and its chosen ring. The source reserve estimate is not a substitute for this exact value.
4. Serve allocates penalty history; `Verifier::init` allocates mapped staging and one device arena sized for configured `max_t` (here spec=4), then `mtp.bind` allocates draft logits and any optional vocab-subset draft head. MTP expert/dense weights and its context-sized K/V state were already loaded. `--spec-min-p` changes request-time T selection; it does not shrink the configured verifier/MTP maximum-T arenas or remove the T=4 graph-capture path.
5. On first use of a T, verifier segments and associated shared/hit graphs are captured/instantiated and cached lazily. Current serve startup free-memory check runs after Prefill init, verifier init and MTP binding but before the first request has captured every verify T. A T=1 capture is followed by T=4 only after the request's first draft. These first-capture allocations and driver/JIT/runtime peaks are absent from the initial `--expert-cache auto` calculation. Inspect free VRAM after startup and after first T=1/T=4 capture. `capture` records free memory after capture, but any higher short-lived peak during capture requires observing the run separately.

At `--max-context 262144 --kv int8 --kv-resident 32768`, the session and streaming host backing remain sized for the requested capacity; do not lower context or change KV to make cache auto fit. MTP uses its own K/V/state allocations at the configured max context/window policy. No exact available free-byte amount is asserted here. The dynamic system desktop/driver/other allocations can change between query and first use.

The serve post-allocation guard is diagnostic: it prints the current free MiB, calls `<256 MiB` LOW (unless the reserve was already adapted), but does not fail merely because free memory is under the 700 MiB configured reserve. For a cautious candidate admission, require at least the configured 700 MiB after all engine allocations and after first-use T=1 and T=4 capture, not only after cache touch. Keep the existing model's reserve explicit and fixed in all arms. If this gate cannot be met, reject that arm before speed qualification; the source's successful allocation alone is insufficient.

## What cannot be claimed from source/metadata

- The 0.8–2.3% current cache hit figure does not prove the cache is useless or critical; cache-hit GPU work may overlap CPU misses, and global hit percentage hides layer/T distribution.
- Auto cache sizing cannot be called safe solely because it emits an expert-cache count, `ExpertCache::open` succeeds, or startup free memory exceeds 256 MiB. Reserve adaptation may lower the configured reserve only in the specific unsupplied-reserve small-card case; with an explicit 700 MiB reserve, the code keeps it and can refuse to fit. Later capture peak remains unpriced.
- Borrowing cannot be credited with the full `xcache.bytes()` as free memory. The allocation remains; only the tail changes owner for the prompt and its resident experts are unavailable until refill.
- No cache capacity, prefill chunk, hit ratio, or MinP/spec change is recommended as a performance winner. `spec_min_p` is a runtime trade in T/acceptance, not a way to shrink preallocated spec4 verifier/MTP resources. CUDA/HIP behavior and Xe settings are outside this primary SYCL conclusion.
