## Finding

Two distinct, measured external implementation ideas may be useful to screen after P's own model baseline: (1) pinning file-backed host weight pages and extending a bounded event-owned prefetch ring so eligible large-batch expert copies can overlap current compute; and (2) for Qwen3.8's separate PLE/ngram table, using direct file reads into short-lived working buffers instead of letting random page faults grow its resident page-cache footprint. Neither has been run on P or on a B570, and neither is an adoption decision.

The first changes where weight bytes reside and when transfers are issued, leaving the GEMM math and expert outputs unchanged in its source author's tested CUDA build. It is not the R452 all-512-expert owned-layer-span copy: its predicate targets the large-batch case where routing is late but almost all experts are expected to be used, then uses a bounded ring to stage tensor uploads ahead of the consuming split. Its extra slots cost VRAM and it may transfer unused weights. P's actual mixed GU/Down formats and per-layer byte sizes make the source's model-specific assumption unsafe to generalize.

The second is not an expert-weight transfer optimization. It targets Qwen3.8's large, sparse-access PLE table, which can consume tens of GiB of host page cache. It can reduce cold prefill stalls and steady host residency, but it does not reduce H2D weight submissions. It is relevant only if P's model artifact contains that table and host fault/page-cache pressure appears in its measurements.

## Candidate A — file-backed host registration plus a guarded upload ring

The implementation reference is Codacus's llama.cpp fork, branch `fable5/prefetch-experts`, source commit `5f83fbb` (three commits atop upstream `4fc4ec554`); its vendored source tree is recorded as `1cbce4cc79442bc287c823937d965d7b73b2e0c6`. The personal `llamacppMoEMaster` source/attribution record links the exact fork and records its three patch commits; the branch README describes the opt-in controls and benchmark. Sources: https://github.com/thecodacus/llama.cpp/tree/fable5/prefetch-experts and https://github.com/biggiehorizon/llamacppMoEMaster .

- Host placement: after loading, the fork registers mmap-backed CPU expert pages with CUDA host registration so transfers can DMA directly instead of going through pageable-memory bounce buffers. Its README reports about 6–7 to 20 GB/s copy rate on its NVIDIA setup. Pinning alone on RTX 3060 / Qwen3.6-35B-A3B, `pp2048`, reportedly changed 1144 to 1385 tokens/s. It is opt-in. The author explicitly notes the mapping registration path is POSIX-only there; the Windows implementation is a no-op.
- Scheduling: in `ggml_backend_sched_compute_splits()`, a second backend instance on the same device issues eligible expert-tensor uploads while the previous split computes. CUDA events protect a staging-slot ring. The guard requires asynchronous copy/events, an expert-ID matmul node with host `USAGE_WEIGHTS`, no evaluation callback, and `ids->ne[0] * ids->ne[1] >= 2 * n_expert`. The rationale is that at sufficiently large batch size nearly every expert will be touched, so waiting for router IDs can cost more than eagerly uploading that expert tensor. Compared with many per-expert slice submissions, this could lower host issue count to tensor-level submissions, but the reference publishes no copy-call count and does not prove fewer bytes. The slots are sized at graph setup from the largest tensor; default is three, maximum eight, and each consumes one largest-expert-tensor-sized VRAM allocation. The author's README warns that smaller physical batches can make this route inactive.
- Reported combined result: RTX 3060 12 GB, Qwen3.6-35B-A3B, 26 MoE layers assigned to CPU, `pp2048`, `-b 2048 -ub 2048`, five benchmark repetitions; approximately 1143 to 1880 tokens/s (+64%), with token-identical output claimed. The README does not publish the individual samples or dispersion. This is a short 2K-prompt CUDA result, not a long-prefill, primary, Arc or SYCL measurement.

P already has a streamed/staged ring, a pinned-share policy and copy/compute overlap in its primary prefill path (R452: `src/prefill/prefill.cpp`, `expert_source.cpp`). Its source also has file-backed mmap and pinned/mapped arena paths. Therefore the donor is a *question to test*, not evidence that P lacks pinning or overlap. A small first attribution must distinguish: model-file pages already host-registered vs ordinary mmap; source-to-stager CPU copies; number/bytes of H2D submissions; time queued vs completed; and exposed waits. If most bytes already enter pinned staging and copy completion overlaps, the CUDA result supplies no reason to add a second ring.

If the primary trace shows host page registration or transfer issue/wait is exposed, the smallest candidate is an opt-in, event-owned ring depth for already-selected, pinned staging blobs, or a supported host-registration experiment for an exact file-backed range. Keep current expert selection, format dispatch, matrix values and ordering unchanged. Require explicit eligibility on actual `ids`, checked source range/format size, B570-reported async/event capability, preallocated VRAM budget, lifetime until copy completion, and exact fallback to today's path. Pinning an entire large model mapping is not assumed safe: OS pin limits, mapping page alignment and memory pressure need explicit caps. Do not port CUDA backend objects or treat a SYCL queue as equivalent without testing.

## Candidate B — PLE table direct-read working set (different bottleneck)

llama.cpp PR #28136 adds `--lazy-mode on-direct` for sparse Qwen4Exp PLE reads. The cited benchmark used llama.cpp build 10743 at `54ed7d366` plus that PR, ROCm 10.0, Strix Halo gfx1151 with 128 GB unified memory (125 GiB usable) and NVMe; model was Qwen3.8-Flash-Next GGUF. The tested PLE `per_layer_token_embd.weight` was 26.8 GiB for UD-Q4_K_XL and 50.7 GiB for UD-Q5_K_XL (147.4 GiB total model, larger than usable RAM). Primary source and benchmark discussion: https://github.com/ggml-org/llama.cpp/pull/28136 .

The author compared `--lazy-mode off|on|on-direct` after dropping caches, with cold and warm requests, `cache_prompt:false`, `n_predict:1`, and prompts of 2,392 / 3,767 / 6,490 tokens. Five repetitions × two quants × three modes produced 180 timed prefills with no failures. On-direct vs `on` raised cold prompt throughput by 20–32% (Q4: 250→325, 264→321, 259→311 tok/s; Q5: 256→337, 269→332, 266→323). Warm mode was within −0.4% to +2.1%, as expected after page-cache warmup. Major faults fell from roughly 30,732–61,395 to 0 while explicit reads replaced them; bytes read were identical. For Q5, eager `off` loaded in 159 s versus 19 s for on-direct and used about 43 GiB swap. The PR's report says the benefit shrinks with prompt length because PLE fetch work is approximately fixed per unique row while prefill compute rises.

Interpretation for P: this is an unusually close architecture and memory-capacity reference, but different accelerator, runtime, quant and weight ownership. It supports measuring PLE residency and cold major-fault/host wait separately from expert H2D traffic. It does not support moving the PLE table to SSD for this fork without confirming the actual model file, Linux path, storage latency and direct-reader lifetime. It should be considered only if the baseline shows PLE page faults/residency matter; warm baseline runs may see no speed gain. It does not change expert GEMM values, but it changes IO timing/cache residency, so retain output/state checks.

## What vLLM and SGLang establish (and what they do not)

The official SGLang expert-parallel guide describes expert weights distributed over multiple devices, all-to-all dispatch and multi-GPU TP/EP examples such as TP=8, EP=8. That is useful for grouped-GEMM/dispatch vocabulary but does not give this single-B570 machine a peer GPU or 128 GB host-memory execution path: https://github.com/sgl-project/sglang/blob/main/docs/docs/advanced_features/expert_parallelism.mdx . SGLang's CPU backend roadmap separately describes GPU-CPU MoE offload and pipelining, but as CPU-backend work items, not evidence that its default EP route runs on one 10-GiB Arc: https://github.com/sgl-project/sglang/issues/8281 .

vLLM's v0.6.2 API documentation says `cpu_offload_gb` virtually increases memory available for weights but copies CPU weights to GPU for each forward pass and requires a fast CPU-GPU interconnect; its normal memory sizing still budgets weights, activations and KV cache on GPU. This generic dense/offload setting is not a sparse expert pager: https://docs.vllm.ai/_/downloads/en/v0.6.2/pdf/ . A separate vLLM expert-cache fork documents CPU-pinned expert source plus fixed per-layer GPU slots and LRU hit/miss remapping, but requires eager mode and excludes EP/DP/sequence parallel; its example is OLMoE 64 experts on an 8 GB GPU with 16 cached per layer. That is a useful low-VRAM ownership pattern, not prefill evidence for the target model: https://github.com/pedrohedro/vllm-expert-offload/blob/main/docs/features/moe_cache_policies.md .

These sources do not justify saying that all current SGLang/vLLM MoE execution is dense-GPU resident. They show a more specific mismatch: the standard high-throughput EP path assumes multiple GPU ranks, generic CPU offload pays repeated transfer cost, and specialized CPU expert caches have different execution/runtime constraints. P's per-layer mixed GGUF data, one B570, and explicit host/VRAM leases must be measured directly.
