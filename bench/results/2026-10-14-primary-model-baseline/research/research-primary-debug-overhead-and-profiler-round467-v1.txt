## Separate the layers

1. **Large-range compiler contract.** `-fsycl-id-queries-range=size_t` is a compile/device-link option on `strata_sycl_runtime` with PUBLIC propagation (`cmake/sycl_backend.cmake:7-10,31-37`). It changes the SYCL implicit range/ID type contract for consumers and can affect generated kernel arithmetic. It does not enable/disable driver validation, insert event markers, or add a runtime check to every launch. Keep it for large-context runs; its performance effect has not been measured on the complete primary model.

2. **Runtime parameter validation.** The v5 `ZE_ENABLE_VALIDATION_LAYER=1` opts into the Level Zero validation layer. Per-command parameter validation and warning reporting can add host/driver work across a high-count submission path. This is distinct from UR lifetime tracking and from Strata's exception observer. The README says full lifetime checks were exercised in a small fixture and proposes reducing parameter-validation/logging during the next long diagnostic; that separation preserves the lifetime result without treating the long diagnostic as a full-validation run. The v5 receipt alone does not prove the cost attributable to this layer.

3. **Strata CUDA-compatibility adapter.** In SYCL, `cudaEventRecord` is not a host timestamp: `src/sycl/compat.cpp:364-379` calls `queue.ext_oneapi_submit_barrier()`, looks up stream capture state under the registry mutex, then locks and updates the event state. `cudaStreamWaitEvent` adds a dependency barrier (`:400-406`). `attempt()` calls `runtime_for()->check()` on each compatibility operation (`:60-76`); `queue()` resolves the queue and checks its context (`:82-86`); event query/sync/elapsed-time take event-state locks and may wait (`:381-423`). Direct kernel launch paths also validate the explicit queue's in-order property (`include/strata/sycl/launch.hpp:47-57`). These are specific candidate host/command costs, not evidence that they dominate.

4. **Graph record and replay.** `compat.cpp:433-465` begins a oneAPI command graph; normal recording records and retains nodes, while native recording enables `enable_native_recording`. `launch_graph` submits `ext_oneapi_graph`, orders replays against `graph->last`, and refreshes event states associated with graph-internal markers (`:478-509`). `graph_launch_with_completion` binds one disabled-timing event to the graph submission instead of submitting a separate completion barrier (`:514-518`; declared as such in `include/strata/sycl/compat/cuda_runtime.h:109-116`). The `spec=4` verifier is segmented: the 48-layer path reports 49 segments and normally has per-layer event-completed boundaries; it waits for each completion, runs CPU experts, waits for copies, and launches the next segment (`src/core/verify.cpp:1216-1255,1289-1346`; `docs/SYCL_IMPLEMENTATION.md:1599-1619`). With `STRATA_SYCL_VERIFY_NATIVE_CAPTURE=0`, the v5 verifier chose normal graph recording for every window; it did not exercise the opt-in native recorder. `--native` is the native IQ GGUF pack option (`generate.cpp:218-224,1635-1663`), not native SYCL graph recording.

5. **Explicit timing instrumentation.** `STRATA_PREFILL_TIMING=1` causes `PfTimer::mark` to record compatibility events at phase boundaries and `fold()` to call `cudaEventElapsedTime` for adjacent marks (`src/prefill/prefill.cpp:1224-1262`). Since each event record is an SYCL queue barrier and elapsed-time evaluation waits for the ending event (`compat.cpp:364-379,408-423`), this flag adds both markers and event queries; the reported intervals also charge dependency/host gaps to the preceding phase, so they are not kernel-only. `STRATA_DECODE_TIMING=1` enables request/stage snapshots and reporting in `generate.cpp:5871-5889`; it is less structural than the prefill GPU markers but is still diagnostic work. Leave both unset for a profiler pass whose target is normal submission/replay overhead.

## Configuration and safety disposition

Keep the `--native` GGUF pack and current model settings constant: they select the actual data format and execution workload. Keep `-fsycl-id-queries-range=size_t`, checked-span validation, and exact arithmetic build options (`-fno-fast-math`, `-ffp-contract=off`) in every long-context run. They guard different correctness conditions and are not debug logging switches.

Keep `--no-prefill-borrow`, cache sizing, `--spec 4`, and `--no-spec-split` fixed while profiling. Borrowing changes VRAM reservation/cache slot ownership; verifier split settings change graph/segment count. Changing them would mix memory and scheduling differences with the adapter-overhead question. `--no-capture` is not a safe way to test ordinary launch cost on this workload: `generate.cpp:3625-3639` refuses it with the CPU expert pool because the uncaptured `session_token` path omits the routed CPU experts. For a narrow hit-kernel comparison, `STRATA_SYCL_NATIVE_HIT_GRAPH=0` is a separate supported opt-out (`generate.cpp:3483-3491`, `docs/SYCL_IMPLEMENTATION.md:1060-1084`); do it only as its own correctness-preserving diagnostic and keep verifier capture unchanged. Do not combine this with the initial profiler collection.

The `ZE_ENABLE_VALIDATION_LAYER` setting should be isolated from the lifetime-validation policy: retain a complete lifetime fixture/check as already recorded, then profile the healthy model with the lighter parameter-validation mode that Main has separately approved. Do not use a profiled/validated diagnostic as the speed result. The throw observer should also be off in that timing run once the expected range exception is resolved; its purpose is exception attribution, not normal operation.

## Focused Main-owned collection after a healthy unprofiled run

The least confounded source-specific collection is one bounded, representative prefill/decode window on the same native pack and settings after an unprofiled normal benchmark has completed. Launch the exact server as the VTune child as in R459 (to avoid attach restrictions), but keep the marked interval to one request and the profiler data cap bounded. Use the existing `xpu-offload` API/task trace with CPU sampling/stacks and programming-API collection. Do not set `STRATA_PREFILL_TIMING`, `STRATA_DECODE_TIMING`, `STRATA_POOL_TRACE`, or the throw observer for this pass. Keep profiler timings diagnostic-only.

Look for three values on the same marked interval: (a) host CPU time and call stacks in compatibility submission/queue/event routines versus the Level Zero parameter-validation calls, (b) counts and host duration for queue barriers/event waits and graph submit/replay calls, and (c) GPU queue active time and gaps between segment completion and next segment submission. These distinguish host API/validation overhead, graph segment/event cost, and actual device work. Do not add `cudaEventSynchronize` waits or phase timers as instrumentation; they perturb the boundary being measured. Correlate the API stack with the device timeline rather than summing overlapping host/queue/device times.

If the focused run shows time in the validation layer, a second bounded diagnostic can compare only the Level Zero parameter-validation switch while holding model, graph mode, and Strata timings fixed; report it as diagnostic overhead, not an optimized product setting. If the host timeline instead identifies compatibility barriers/replay as material, then compare normal verifier recording (`0`) against the default small-window native recording (`small`) in separate runs, matching accepted tokens and output IDs. A hit-graph toggle is a different experiment. Do not begin these A/Bs before the clean baseline and successful long-input completion are known.
