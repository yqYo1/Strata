## New shared behavior ledger

1. **Responses API inherits configured `reasoning_effort` (required compatibility fix).** Source commit `5d08c753c2` (merged at observed HEAD); source/test are `serve/server.py` and new `serve/test_effort_paths.py`. Niko commit title states configured effort now reaches Responses and `reasoning_effort: false` is treated as a level; tests pin every request form's prompt. P already supports `/v1/responses` (`serve/server.py:3418+`) and stores/validates effort (`:3800-3816`), but its shared Responses path has no default propagation equivalent to Chat (`:1933-39`); a request-level explicit value must continue to win. Adapter: update only shared request normalization / Responses prompt construction; preserve all supported levels and false as an explicit level (do not use truthiness to decide override). First implementation in sequence because it is a small, local API compatibility correction. Carry upstream tests for chat/responses, stream/non-stream, request override and configured false; no inference engine change.

2. **Setup rerun preserves selected installed model size and owner environment.** Source commit `de9115fac7`; `setup.py`, setup tests and 0.1.44 engine minimum/model metadata. On an installed-model rerun, retain the installed size/model and three environment entries rather than falling back to a newly preferred default; specifically protects a GSQ-RCO config. P setup can discover installed configs (`setup.py:2849,3629`) and reads an old config later (`:4356-57`) but has no 0.1.44 installed-size preservation behavior. Adapter: perform config discovery before model selection; seed model/size from the selected installed config when caller did not explicitly choose another; preserve only the documented owner-controlled environment keys while merging generated settings. Explicit CLI selection still wins. Tests should cover rerun unchanged, explicit change, multiple installed configs/selection, and the three entries retained; setup-only, no model run.

3. **Literal tool-tag text survives frontend parsing.** Source commits `62185aab77` and follow-up test `a0e577de95`; `serve/frontend.py`, `serve/server.py`, frontend tests. Quoted `<tool_call>`, `<tool_response>`, and `</tool_response>` in user/model text must remain text, including the outer-pair exception, rather than being interpreted as control markup. P's shared frontend is older and its literal-tag tests do not pin the added cases. Adapter: bring parser state/escaping semantics and fixtures into common frontend; ensure both OpenAI and Anthropic conversion use the same literal protection. This is API correctness and independent of engine.

4. **Opt-in `env_to_user` system-prompt cache reuse.** Source commit `d8a49433e3`; server/frontend/config tests. With config opt-in, move OpenCode's `<env>` block into the first user message so changing folder/day does not invalidate the cached system prefix; default remains off. Upstream reports first-request change 11.9 to 1.1 s (upstream-specific measurement, not a P claim). P has no such setting. Adapter: implement a narrowly validated config option and request normalization before template conversion, preserving text and order; prove off-by-default exact compatibility and opt-in cache-prefix behavior in fixture tests. No kernel dependency.

5. **Prompt fairness at the next engine chunk.** Source commit `ac21812c1a`; `serve/server.py`, parallel/service tests. A short queued request can preempt a long read at the next chunk boundary, instead of waiting an entire later chunk or indefinitely. P is serial today and R468 documents that it lacks Niko's slot protocol; this behavior depends on either implementing that protocol and prompt-yield control or preserving equivalent fairness in an adapted engine loop. Sequence after negotiated batch/slot protocol: port control-state and tests together, then integrate fairness; do not bolt a server-side interrupt onto the current GEN-only engine. This is required when adopting upstream concurrent service semantics, but not independently callable on today's serial engine.

6. **Clear engine-start failure and narrowly classified GPU-runtime retry.** Source commits `3d5819df3b`, `d981a51013`, `9aa674edf8`; `serve/server.py`, server tests. Upstream retries only early transient GPU-runtime initialization failures (2/4/8 s), not crashes; reports signal/NTSTATUS and CPU ISA context for illegal instruction, and distinguishes “engine said error” from process/system termination. P's current startup error handling predates these diagnostics/retry guards. Adapter: port exit classifier and notes first, then retry only when process exit and bounded startup log satisfy upstream transient predicate; exclude signal/NTSTATUS crashes, timeout and engine's own explicit error. Keep bounded retries and test synthetic exit/log cases. This is server reliability, no CUDA/HIP validation requirement.

7. **Client disconnect during preparation is treated as gone.** Server commit `serve/server.py` adds `ClientGone` for image download/encoding or request-turn wait; ensure a disconnected client does not strand FIFO/service state or generate a spurious error response. P server must be checked for disconnect handling in its applicable preparation paths. Adapter with the later image path or shared queue changes; unit fixture should close client during preparation and verify cleanup/release.

8. **Image-generation API (optional product capability, distinct from text inference).** Commit `a5b3b6c27b` introduces `POST /v1/images/generations` for Qwen-Image-2.1-Turbo through `stable-diffusion.cpp`; new `serve/images.py` blob `f322a571...`, server route blob above, test `serve/test_images.py` `2842e523...`, `docs/IMAGES.md`, setup and image-native runner commits `5be585a2cf`, `c711ba071f`. P has no route/module/runner. This is a real new API function, but requires its own model/config/download/build lifecycle and same-GPU arbitration with text serving. Adapter sequence: port schema/config and fake-runner tests first; add isolated `serve/images.py` subprocess lifecycle and error/cancel cleanup; then add setup opt-in and pinned model assets/runner build for the supported native route; finally serialize GPU admission with the text engine and prove cancellation/cleanup. CUDA/HIP-native DiT kernels are outside scope: on Arc, either use a supported non-CUDA backend (upstream has Vulkan) or report the capability unavailable. Do not advertise endpoint as usable until runner/backend exists. This can be a separately tracked optional product feature, rather than a prerequisite to text serving.

9. **Image/vision request correctness and lifetime fixes.** Across `cf1b0edf91` / `9341ebd213` and related serve commits, image-bearing reusable state is keyed by original image byte hash and grid, and rejection due only to changed picture embeddings is named; image encoder can be elastic (config `vision.elastic`) and temp combined embeddings use `/dev/shm`/short-lived files; `ClientGone` covers disconnect during image prep. These shared behaviors matter only when vision is configured. P already has a vision path, but must compare current `serve/server.py`/vision tests against upstream behavior. The elastic encoder is a server/encoder lifecycle feature, not Niko expert-cache `vram_elastic`; its engine flag/free-VRAM semantics need a truthful primary engine adapter. Temp-file/hash fixes are shared Python work and can be adapted independently. Do not claim upstream CUDA/HIP encoder lifecycle on Arc without a compatible encoder build.

10. **Request keepalives / unload wait / retry-after / reasoning loop recovery.** Server additions include queued-request keepalives, `POST /unload?wait=` parsing (bounded wait), `Retry-After` for GPU-busy 503, reasoning-repeat loop stop/recovery and optional one-time close of an unterminated thinking-only reply. These are user-visible server semantics. P's server should be diffed feature-by-feature against head; only take defaults/opt-ins and bounded behavior with tests. Their dependencies are server queue/unload lifecycle and frontend token parser, not the GPU engine. In this round I confirmed the upstream head additions from raw-file diff; the commit API result is too large to assign every intermediate addition to an individual source SHA here, so these particular subfeatures are leads for the implementation audit rather than claimed complete per-commit tracing.

## Setup/model surface and applicability

The 0.1.43→HEAD setup delta is much larger than a single option: updated model menu and pinned artifacts (NVFP4 packs, Unsloth UD-Q5/UD-Q6/Q8, Qwen3.6 family), recommendation/default changes by RAM, images/model runner setup, pinned `strata_kq`, Windows/Debian toolchain handling, model geometry checks and many platform-specific diagnostics. These are concrete new setup/model compatibility surfaces, but do not mean every pack or engine must be imported into this personal Qwen3.8 Arc fork. Keep the model-selection function and the model's required inference backend distinct. NVFP4/Unsloth/Qwen3.6 engine/kernel work is inference and is out of this report; setup should expose a model only after P engine compatibility is established. Platform changes limited to CUDA/HIP or Apple Metal are not applicable for this Arc-only task. Qwen3.6 recognition/setup without an engine path is not a usable feature by itself.

Other upstream changes in the range include multi-GPU placement, peer cache, batch-groups, split-stage trimming, image generation backends and extensive inference kernels. R465 already classifies one-GPU-inapplicable multi-GPU items; the policy requires no CUDA/HIP import and XeStrata remains optional. The shared parallel service obligation still applies as covered by R465/R468; no requirement here to import CUDA batch kernels or the whole engine.
