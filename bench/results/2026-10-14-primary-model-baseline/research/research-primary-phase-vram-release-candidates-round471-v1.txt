# R471 — Phase-specific VRAM release candidates for longer prefill chunks

## Scope and status

Read-only source/report review for the current primary SYCL build. No build, test, benchmark, profiler, process, Git, fetch, configuration/service, or cleanup action was performed. R459–R469 and the primary research registry/README were reviewed; R470 was still in progress and was not awaited. The reported 61,055-token diagnostic remains incomplete: the README records that v5 reached the 53,248 prefill position, then its owner deadline stopped it; it has no `DONE` sample, normal real-engine exit receipt, or speed qualification (`README.ja.md:150-168`). This report makes no claim that 262,144-context or 61,055-token validation has passed.

The active SYCL build compiles the primary `src/` sources through `cmake/sycl_backend.cmake` (`CMakeLists.txt:177-179`; `cmake/sycl_backend.cmake:90-102`), including `src/core/expert_cache.cpp`, `src/core/verify.cpp`, `src/core/mtp.cpp`, `src/core/session.cpp`, and `src/prefill/prefill.cpp`. The active expert cache uses one ordinary allocation on this configuration; no VMM implementation is present in this primary source. The upstream/fork VMM comparison in R469 is not an implemented primary capability.

## Finding

There is a credible **phase-lifetime** experiment, but the approximately 357 MiB verifier allocation is not a prefill candidate in the current source order. The verifier is created only after prompt prefill and its workspaces are reset; graph capture occurs later on the first verifier run. Releasing/recreating that verifier storage cannot increase the earlier prompt chunk. The best source-supported releasable decode payload during prefill is the MTP expert-weight array, because both prompt-time MTP paths stop before the MTP MoE. A larger candidate is to temporarily release the 128-slot primary expert cache and route prompt experts through the already-open host expert source, then restore the cache after prompt buffers are freed. Cache residency helps current prefill performance, so this trade must be measured. A longer chunk is plausible only if the net freed memory covers the measured incremental scratch requirement while preserving the 700 MiB reserve and the later decode allocation set.

## Chunk budget and decision threshold

The primary's auto-cache reserve estimate for an owned prompt buffer is `160 + chunk * 680 / 1024` MiB (`src/program/generate.cpp:2931-2940`; explicit-cache budgeting at `:2998-3006`). At chunk 4,096 this is 2,880 MiB; at 8,192 it is 5,600 MiB; the estimated incremental requirement is **2,720 MiB**. This is a sizing reservation, not a measured physical allocation size or a guarantee that all layers allocate exactly this amount. The authoritative future check is `Prefill::bytes_needed()` plus the actual allocator/free-memory ledger for the configured model (`prefill.hpp:82-83`).

A simple condition is: let `F4` be free VRAM while the current 4K prompt buffers are live, `R=700 MiB` the chosen minimum reserve, and `G` the net free bytes reclaimed by phase release after adding any host/device metadata or remap overhead. An 8K attempt is viable only if `F4 + G - 2720 MiB >= R`, with additional allowance for allocation granularity/driver overhead, and if the decode-phase cache + MTP weights + verifier arena still fit after restoration. In this record, 1,405 MiB free before and 1,047 MiB after verifier setup are post-prompt markers; source order puts them after `Prefill::reset()`. They therefore cannot be substituted for `F4`. The 834 MiB MTP report is a total upper bound, not recoverable bytes from a single allocation; dropping only the MTP expert payload is smaller. MTP release alone cannot be said to fund the 2,720 MiB increment. The cache's actual byte count is not supplied here, so a combined cache+MTP release cannot yet be declared sufficient.

## Minimal source-change experiment proposal

Keep the context, int8/resident-KV 32,768, MTP, reserve 700, cache profile, native settings and numerical behavior fixed. Add an opt-in per-request phase plan, initially on the serial primary serve path only:

1. At the boundary after prompt/session restore and before `Prefill::init`, copy the MTP expert payload to bounded host RAM, synchronize its stream, then free only MTP `experts_`. Keep all dense K/V weights, main/draft K/V state and prompt code path.
2. If the measured 4K free-space ledger still cannot support a trial 8K chunk, add a separate cache-release arm. Snapshot exact resident slots and profile; wait the main, transfer and MTP work queues plus cache fill callbacks; invalidate/upload `host_res`; close the single GPU cache. Run prefill through the same source with no expert-cache pointers, accepting that all prompt experts will be streamed.
3. `Prefill::run` still advances every actual input token and MTP draft K/V. Preserve `n_batched = prompt_tokens - 1`, the final pending cell, max-context check and all existing stop/RESTORE behavior. After the final chunk, synchronize the prefill and MTP streams and call the existing SYCL `prefill.reset()` before allocating the decode cache again.
4. Reopen/refill the same profile and slot layout from `ExpertSource`, synchronize every copy, then atomically publish the complete device residency table and refresh cache base/offset pointers. Restore MTP experts from RAM and bind the MTP head before any MTP draft. Initialize the verifier only after all decode allocations are restored; its fresh graphs then capture current session/cache addresses. If this cannot restore the exact cache/residency image, discard the partial cache and retain the normal safe CPU-miss path rather than exposing stale slots.
5. Preserve a 4K fallback if the larger `Prefill::bytes_needed()` allocation or reserve check fails. Compare one change at a time: MTP experts only first, then cache+MTP. Log exact bytes released/restored, free VRAM before/after each phase, cache hits/streamed experts during prompt, graph reuse/recreation, request completion, output IDs/logits, final KV cell, MTP acceptance, RESTORE fingerprints and all allocation failures. Do not call the incomplete long diagnostic a successful baseline.

The primary cache currently has no partial VMM sizing in this path, so closing/reopening the whole GPU tier is the code-supported primitive to evaluate; it is riskier than a small reversible MTP-expert lease. If the graph/raw-pointer refresh cannot be made airtight, do not release the cache: keep the MTP-only variant or return to existing 4K behavior. None of these changes has been implemented or measured.

## Evidence limits

This audit identifies lifetime and ownership from source. It cannot determine the actual live cache byte count, amount of free VRAM while 4K scratch is allocated, MTP host-RAM cost, 8K allocation success, prefill slowdown from disabling resident cache hits, remap reliability, or long-prompt numerical/correctness outcome. Those require a later authorized implementation and GPU run. Source and the current README explicitly leave physical full-context completion and RESTORE/final-cell qualification open.
