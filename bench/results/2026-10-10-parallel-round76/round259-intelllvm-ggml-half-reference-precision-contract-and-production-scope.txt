# R259 — Intel LLVM / GGML half-reference precision contract and production scope

Date: 2026-10-10 (Asia/Tokyo). Source and primary-document audit of the immutable CPU-admission receipts. No source edits, builds, tests, profiles, inference, model payload reads, hardware/device/process queries or cleanup were performed. No mutable current GPU run was read. One read-only `git rev-parse HEAD` query was inadvertently run against the frozen production source tree while checking its identity; no repository state was changed.

## Decision

The archived CPU-reference failure is real and precisely scoped: the prebuilt GGML base library converted one finite FP32 input well above the representable FP16 range to a finite half (`0x6057`), while an independent round-to-nearest-even (RNE) encoder returned positive infinity (`0x7c00`). The host test itself used `-fp-model=precise`, but that flag did not retroactively change the already-built static GGML library it called. The archived compile command for that library used Intel `icx -O3` without an explicit floating-point model; Intel documents `-fp-model=fast` as the default and says it enables more aggressive FP optimizations which may affect accuracy or reproducibility. This is a credible explanation for a reference-build precision mismatch, not proof of the particular optimization or emitted instructions in that archived object. [Intel’s compiler reference](https://www.intel.com/content/www/us/en/docs/dpcpp-cpp-compiler/developer-guide-reference/2025-1/fp-model-fp.html) documents `fast`, `precise`, and their defaults.

A repaired diagnostic reference was produced from the unchanged pinned GGML sources, compiling `ggml.c` and `ggml-quants.c` with `-fp-model=precise -ffp-contract=off`. It passed 99,615 non-NaN random binary32 conversions, 24 literal conversion edges, and 12 injected output/canary fault checks. This establishes a viable CPU-only reference configuration for this diagnostic. It does not qualify production model arithmetic, the GPU kernels, or output/performance.

The failure input, `0x540ae211`, decodes to `2,385,993,007,104.0`, about 36.4 million times the largest finite binary16 value (65,504). So the counterexample is far outside the finite FP16 range. It does not show a wrong conversion for ordinary values whose magnitudes fit in finite FP16. The v3 random test also exercised broad finite FP32 inputs and passed against independent RNE, but it was a finite sample, not an actual model-range survey. Whether production activations or scales ever exceed the half range remains unmeasured because no model payload or inference was used.

## Documented behavior versus inference

Intel’s 2025.1 compiler reference says the default `-fp-model` is `fast`; `fast` permits more aggressive floating-point optimizations, while `precise` disables optimizations that are not value-safe. Intel also documents `strict` as precise with contraction disabled. The actual archived `icx -O3` command omits `-fp-model`, so applying the documented Intel default to that command is supported. [Intel `fp-model` reference](https://www.intel.com/content/www/us/en/docs/dpcpp-cpp-compiler/developer-guide-reference/2025-1/fp-model-fp.html).

**Inference, not directly demonstrated:** because the GGML converter's initial chained power-of-two multiplications can overflow at large magnitudes before the scale-down, a compiler transformation that changes the intermediate evaluation can alter the over-range result. The exact witness is consistent with a fast-mode transformation changing that behavior, and rebuilding the same source with precise semantics removes the mismatch across the tested sample. No assembly/disassembly, optimizer report or controlled one-flag-at-a-time comparison is present. Therefore the audit does not claim that reassociation, contraction, vectorization or any named pass caused `0x6057`, and it does not attribute the outcome to a particular CPU instruction.

The v3 rebuild used both `-fp-model=precise` and `-ffp-contract=off`, so this A/B receipt cannot isolate which flag was necessary. For this conversion expression, the prominent risk hypothesis is changing the overflow-sensitive evaluation of the chained multiply; no FMA exists in that two-multiply subexpression. The later additions and bit extraction are also part of the routine, so the existing evidence is not a formal proof of the single causal operation.

## Ordinary model values and practical boundary

RNE conversion of finite values above binary16's overflow threshold should produce infinity; the observed `0x6057` is wrong for that input. The witness is dramatically outside finite-half range, not near ordinary representable scales. Within the finite binary16 magnitude range (`|x| <= 65,504`), the counterexample itself offers no evidence of a wrong result. The v3 sample gives additional evidence for the repaired configuration, including subnormals, boundary cases, infinities in literal cases, and 99,615 random finite bit patterns, but finite sampling cannot establish all possible converter inputs.

No current model tensors, scale metadata or live activations were read, so there is no evidence here about the range actually encountered by Strata. A model-path gate should measure the FP32 values at each actual FP32-to-FP16 boundary (count, min/max absolute value, non-finite count and exact over-range examples), then compare output bits from the production conversion with the independent RNE contract on those captured values. Preserve the input values/hashes and distinguish expected overflow-to-infinity from NaN policy. If all captured values remain within finite FP16 range, the present witness alone does not indicate a routine output discrepancy; if values exceed the range, the production path must be checked directly.

## Production-scope and validation boundary

The archived artifact is a standalone host reference for the generic IQ dequant capacity diagnostic. It uses current-pack metadata and unchanged production GPU dequant wrappers in a separate harness, but the CPU reference failure occurred before any GPU execution or model inference; v3’s pass is CPU-only. It must not be treated as a production kernel failure, actual model numerical error, GPU-hang explanation, or performance result. The production GPU source snapshot is `/home/yayoi/ghq/github.com/yqYo1/Strata/.worktree/diag-sycl-prefill-service-events-20261010`, commit `495369cf4dc6e6da564095a1c26504dd3694e3f2`; its generic IQ wrappers use device-side `sycl::half` conversion. The standalone host oracle's GGML build mode and the GPU compiler's conversion behavior are separate questions.

For an original-engine numerical gate:

1. Freeze the production source, compiler, complete compile commands, device/runtime flags, pack identity and exact GGML base/CPU archive hashes. Record the effective FP model for the converter object rather than relying on flags passed to a caller or harness.
2. Keep the cached fast-default reference result as immutable historical evidence. Use the exact-source precise reference as the diagnostic oracle; do not overwrite the historical library or retrofit the reference fix into production without an explicit production change and review.
3. Run the independent conversion edge and actual-value bit checks at the production CPU and device conversion boundaries, with finite-overflow, subnormal, tie, Inf/NaN policy and guard checks. Record whether the production path's captured values overlap the faulty magnitude domain.
4. Only then run source-aligned model/state comparison on the original engine with the normal production route, fresh session and matched inputs. Separate conversion/reference mismatch from GPU execution faults, numerical drift elsewhere, and wall/performance results.

This audit qualifies only the repaired host reference against its independent conversion contract for the recorded sample. It does not qualify the production GPU conversion, whole-engine outputs, ordinary model-value range, historical GPU hangs or throughput.
