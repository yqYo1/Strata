# R167 — prefill-owned asynchronous error chain for IQ4_NL dequant

Date: 2026-10-10 (Asia/Tokyo). Read-only source trace against WPROBE `609a270daac23c9b1a26d26ec092b2f60d2da335` plus the immutable IQ4_NL prototype snapshot from `45affbb0fd2f4adb2064a7ccb5fe3364b952dcf4`. No implementation, build, compiler/disassembly, tests, import, GPU/device query, profiler, model/payload, Git, lock, cleanup, service, or reset operation was performed. This resolves the source-level async-error question only; no injected fault/runtime behavior was tested.

## Finding

R164's narrow statement needs refinement: `check()` is a no-op, so the private helper's post-submit `check("iq_dequant_f16")` does not report a kernel failure. The ordinary production caller does nevertheless have eventual supported error drains, but they are late and are not tied to this helper's return: `Prefill::run_impl` ends with `m.cs->wait()` (not `wait_and_throw()`), `Prefill::release()` later calls `m.cs->wait_and_throw()`, and server shutdown calls `queues_wait_and_throw()`. Since the normal generation queue is created with async handling enabled, a queued async failure is not wholly unobserved forever. The source does not establish that it reaches the caller before output/state is consumed, or that it is attributed to this dequant rather than any prior queued work.

The first risk is delayed error visibility and use of bad data, rather than an evidenced early free/use-after-free. In-order queue submissions serialize the private dequant, following MoE GEMM, and later commands; the normal run path also waits for queue completion before returning. That completion protects the DQ slot and source lifetime against concurrent reuse/free at the time of return. But `wait()` is not `wait_and_throw()`: the run can report success and hand off results after failed work, with the error surfaced only by a later release or global drain. At teardown, `release()` waits before freeing owned buffers, so it does not free those buffers while pending commands remain. If `wait_and_throw()` throws there, `release()` has no catch and `Prefill::~Prefill()` calls it; normal C++ destructor exception rules can terminate the process. This favors process failure over unsafe reclamation but is not a usable prefill error return.

## Production queue and call chain

1. `dpct::device_ext::init_queues()` constructs the default in-order and out-of-order queues with `create_queue_impl(true, ...)`. The enabled handler is `dpct::exception_handler`, which calls `strata::rethrow_sycl_errors`; that helper logs errors and rethrows the first exception. The device tracks these queues, and `queues_wait_and_throw()` invokes `wait_and_throw()` on each tracked queue.
2. The normal `generate.cpp` main path creates `main_stream` with `create_queue(true)` and passes it to `Prefill::init`. Layer-split stages also create their streams with `create_queue(true)`. `Prefill::init` stores `m.cs = strata::q_of(stream)` and requires an in-order queue. It does not install a handler or make the passed queue device-owned; in production these queues already have the handler and are registered with the device.
3. At the private site in the immutable prototype, the call is inside native expert `compute`: the GU dequant and private type-20 Down dequant submit to `m.cs`; then `m.used[slot]` is set up for the next ring reuse and `m.gemm.f16` consumes `m.dq_d[q]`. Both the helper's `check()` and the generic helper's equivalent check are empty. There is no per-helper event retained by `Prefill` and no helper-specific host wait.
4. The slot event/barrier path protects reuse ordering, not error propagation. `dpct::sync_barrier(m.used[slot], m.cs)` enqueues the dependency before reusing a streamed staging slot; it does not constitute a host `wait_and_throw()` boundary. The queue is in order, and later GEMM work follows the dequant on that queue.
5. `Prefill::run()` selects `run_impl` or `run_layer_major`, then drains successor stages. The private branch is in `run_impl`; that function's tail calls `DPCT_CHECK_ERROR(m.cs->wait())`, then returns true. Other intermediate `wait()` calls also occur; the source does not show `wait_and_throw()` on the main compute queue at the private helper boundary. With output callbacks, a completed `m.cs->wait()` precedes the handoff callback, yet does not check async exceptions.
6. `Prefill::release()` joins successor work, then calls `m.cs->wait_and_throw()`, waits owned copy queues, and only after those waits destroys events/frees owned buffers. The destructor calls `release()` directly with no exception boundary. At serving shutdown, `finish_sycl_serve(drain_sycl_devices)` uses device-wide `queues_wait_and_throw()` and on failure chooses `_Exit`, before reclaiming GPU allocations. Thus queue completion/error is eventually demanded at object release or global shutdown, but the ordinary run result can precede it.

## Smallest correction candidate and constraints

The smallest prefill-owned candidate is an opt-in-only propagation gate at the existing host synchronization that already bounds the affected private submissions: where the private arm can reach the `run_impl` tail (and, if a callback returns data earlier, at the pre-callback compute-queue drain), use `m.cs->wait_and_throw()` for the experiment and translate the exception into the existing `err`/false result. This adds no per-expert wait and should not add another synchronization at the normal tail, which already calls `wait()`. It must be limited to the private-prefill opt-in so default behavior and decode are unchanged. It must not retry the generic kernel after private submission.

Before adopting that approach, the error path must account for the existing `run_impl` outer `catch(sycl::exception)` which currently prints and calls `std::exit(1)`, and the later destructor's second `wait_and_throw()`. A candidate should return a concrete error without allowing a second teardown throw to turn a recoverable run failure into termination; teardown must still establish completion before freeing buffers. An event-scoped error receipt or a recorded/consumed private failure state could be considered, but this source audit does not select or implement one. Do not add host waits after every expert: that would serialize the existing asynchronous dequant/GEMM schedule and alter performance.

The required runtime gate is a fault-injection test on the actual supported queue configuration: inject one asynchronous command failure after the private kernel has been accepted, then show that no generic retry occurs, `Prefill::run` reports failure before the result is handed to decode/callback consumers, no DQ/staging/workspace allocation is reused or freed while commands are pending, teardown completes without a second uncaught exception, and a subsequent request/process outcome is explicit. Also record that default-off and decode paths retain their previous behavior. The fixture's private collector/wait behavior cannot establish this production chain.

Decision: R164 correctly identified that the helper's immediate `check()` does nothing. The larger owning chain provides later rethrowing drains, which prevents claiming total absence of eventual reporting, but they are too late to certify the run result and can surface only during destructor/shutdown. A private, opt-in, non-retrying run-boundary error receipt plus runtime fault-injection remains a gate. No source or runtime correction was made.
