# R193 — layer-major prefetch publication fence and overlap reassessment

Date: 2026-10-10 (Asia/Tokyo). Read-only correction of one queue-ordering inference in R191, against the pinned source and recorded reports. No source edit, build, compiler, test, device query, inference, profiler, service, Git action, cleanup, or prototype was performed. No claim about actual memory headroom, device overlap, performance, or adoption is made.

## Decision

R191 is right that `run_impl`'s terminal `m.copy->wait()` must complete any L+1 transfers already submitted to `m.copy` before it returns. Its further conclusion that this wait removes all useful L/L+1 overlap is not supported by the ordering: if the queue copies run while `run_impl` is submitting/running L's compute on `m.cs`, a wait after the compute fence is a publication fence. It waits for work that may already have overlapped; it does not retroactively serialize that earlier interval. The same is true of the layer-major callback waits: they wait on `m.cs`, and the callback handoffs need to finish before changing the active layer inputs, but those waits do not themselves drain `m.copy`.

The concrete hypothetical in the task is feasible at the source/API ordering level: if every L+1 source job is fully staged/claimed and every H2D copy is submitted to the independent in-order `m.copy` queue targeting a distinct inactive full-layer cache before `run_impl(L)` begins, then L compute on `m.cs` can be in flight while trailing L+1 copies execute. At normal return, the `m.cs` wait drains L compute/callbacks and the terminal `m.copy` wait drains L+1 copies; only then may L+1's cache/map be published as active. This is a valid possible overlap timeline, not evidence the driver/hardware executes the queues concurrently or that any copy remains outstanding long enough to overlap.

R191's producer-lifetime concern is still real, but conditional. The current layer-major route marks every current-layer expert resident, so `run_impl` builds an empty ordinary staging job set. In non-`stream_all` mode it still creates `StagerDone`, whose `finish()` runs at function exit. If the speculative producer has already staged/claimed all jobs and the issuer has submitted every copy before `run_impl`, that finish does not revoke any needed host data; the terminal queue fence can safely bound destination readiness, subject to normal successful completion and retained owners. If the producer is still staging/claiming jobs during `run_impl`, `StagerDone::finish()` can stop it at exit; on early/error exit, shared stager generation and cleanup ownership must also be coordinated. Reusing the single stager for asynchronously produced jobs therefore needs an explicit contract; it is not proven impossible merely by the existence of `finish()`.

## Discriminating timeline

The following hypothetical spells out the case R191's terminal-fence argument omitted. `C1..Cn` are writes only to the inactive L+1 cache; `K1..Km` and layer callback work consume only the still-active L cache/residual path.

| Host / copy queue | Compute queue / callbacks |
|---|---|
| L cache is complete and active. Resolve L+1 source descriptors on the issuer thread. | No L+1 cache/map is visible to `run_impl(L)`. |
| Start the L+1 staging jobs. For each expert, wait until its host staging buffer is ready, submit `Ci` to in-order `m.copy`, and give the DMA event to the stager before that ring buffer can be reused. Finish staging/claiming every L+1 job; retain source and inactive-cache owners. | — |
| Enter `run_impl(L)`. Do not start another nonempty shared-stager generation. | Submit/execute `K1..Km` on `m.cs`; ordinary chunk callback waits drain compute as needed and finish L residual/state handoff. |
| The already-submitted `C` commands continue on `m.copy`; because it is a separate queue, the API does not order them after `K`. | L continues to read its unchanged active cache. Any actual concurrent device service is hardware/runtime dependent and unmeasured. |
| Terminal `m.copy->wait()` returns once all previously submitted `C` work completes (if it succeeds). | Terminal `m.cs->wait()` returns once L compute is complete; callbacks have followed their existing order. |
| Only after both successful completion fences, full-copy success checks and completed host production, publish the L+1 residency map/cache for the next `run_impl`. | L+1 starts with complete data. Former L storage remains owned until L's reads are known complete; reuse for L+2 is deferred until then. |

In the pinned implementation, `run_layer_major` currently performs a queue/stager drain before loading each layer, stages/copies the whole active layer, and waits for both staging and H2D before entering `run_impl` (`prefill.cpp:2704-2741`). This is deliberately serial today. The terminal waits at `:5239-5269` occur after chunk work and the final `m.cs` wait; they can serve as the end fences in the hypothetical. Ordinary callbacks around `:5183-5206` wait `m.cs`. The opt-in `STRATA_PF_STEP_SYNC=1` helper at `:3490-3502` is a different case: it explicitly waits both `m.cs` and `m.copy` after each named step, so it would force any queued L+1 copy to finish at that earlier diagnostic point and distort the schedule. The pre-load `m.cs->wait(); m.copy->wait(); m.stager->finish()` at `:2704-2708` is also a prefetch barrier if left between speculative submission and L compute. A prototype must place/review those fences deliberately; this report does not change them.

The shared stager is one mutable generation/job set (`start` replaces nonempty jobs/generation; `finish` stops new claims and joins active CPU workers, `:495-538`). Layer-major makes all L experts resident in `m.host_res`, so the ordinary per-layer run's `js` is empty (`:4592-4619`). In non-`stream_all` it still installs `StagerDone`, which calls `finish` when `run_impl` exits; in `stream_all` that guard is null. If all L+1 jobs are ready before entry, there is no host producer left for that guard to interrupt. If readiness or issuing continues concurrently, the producer needs a distinct owner whose lifecycle cannot be ended/replaced by current-layer cleanup. An independent issuer thread is required to issue more copies while the `run_impl` host thread is occupied submitting chunks; it is not required merely to execute copies already submitted before `run_impl` starts. Conversely, a second queue alone does not create host issue concurrency, and neither queue nor issuer proves device-side overlap.

## Minimum source-safe architecture choices

1. **Bounded bulk submission on the current caller (smallest plausible experiment).** Keep two full-layer caches. After L is loaded and active, stage/claim all L+1 host jobs and enqueue all L+1 copies to the existing in-order `m.copy` queue before calling `run_impl(L)`. Require an empty-current-resident run plan, ensure the shared `m.stager` has no outstanding L+1 host work before entering `run_impl`, retain staging buffers and source/destination allocations through their DMA completion events, and do not run `STRATA_PF_STEP_SYNC`. Preserve the existing terminal compute/copy fences as publication gates. This can expose only the remaining H2D tail after L compute begins; bulk CPU staging and queue issue still happen before compute, so its benefit may be zero. It does not require a second queue or independent issuer, but it does require a distinct inactive cache and explicit error/cancel owner. R191's extra cache capacity gate still applies.

2. **Concurrent host producer for full staging/issue overlap.** If measurements show bulk staging/issue dominates, give L+1 a separate issuer and independently owned stager generation/ring (and a destination cache distinct from L). Use retained per-copy events and an explicit stop/join protocol. The host producer must not share mutable `m.stager` jobs/generation or have `run_impl`'s `StagerDone` stop/reassign it. A second copy queue may isolate its error handler/order domain, but is optional for a producer that is already issuing to `m.copy`; choose it only with an explicit async-error drain and dependency/lifetime design. This design can issue/stage during L compute, but no source/API fact establishes that the device overlaps the work.

Both options need a caller-owned state machine: keep the active cache/map immutable during all L consumers; don't publish a partly copied L+1 cache; wait for L callbacks/residual/state handoff plus all compute reads before retiring L; only expose L+1 after all intended copies completed successfully; join producers and account for submitted copies on every cancellation/error path; preserve both cache allocations and host sources if a wait fails and completion is unknown. No retry, freeing unknown in-flight storage, or driver reset is justified. The current destructor guard's plain waits are not evidence of safe recovery from an unknown completion. Decode/MTP restore and existing non-layer-major/decode paths retain their current ownership boundaries. These are design requirements, not authorization or recommendation to implement.

## Root-owned receipt that would discriminate

Before a prototype, record one actual selected layer-major run's per-layer source-staging intervals, each H2D submit and completion interval/event, compute interval spanning all chunks, callbacks/handoffs, exposed waits, `m.T`/chunk boundaries, cache bytes, expert count and bytes, and total prefill. Record issuer CPU time separately from source staging, H2D service and device compute. The decisive overlap evidence is a same-run interval intersection of completed/active L+1 H2D service with L compute on the separate queue, plus the amount of H2D still outstanding at L compute start and the wait remaining at the publication boundary. A host submit timestamp alone cannot establish transfer service overlap. Repeat with the bulk-submission control and matching serial control; report actual selected mode and exact settings. A queue wait that returns after both operations cannot distinguish whether they overlapped, so per-copy event profiling or an equivalent clock-domain-safe device timeline is needed; do not mix host and device clocks without calibration.

Separately record actual `layer_cache.bytes()` and same-phase free/peak-memory/lease receipts including live residual, KV, workspace and decode-cache suspend/restore allocations before deciding that a second cache fits. Then use R189's actual >=32,768-position full-model qualification and physical 262,144-position boundary/tail control, paired repeat controls, output/logit and recurrent/KV/indexer-state comparisons, failure/cancellation receipts, exact copied bytes, decode-after-prefill and decode-cache restoration. Decode remains independent. No arbitrary gain minimum is introduced: require improvement beyond measured run variation and no correctness, failure, memory or exposed-wait regression before adoption. Current memory headroom and overlap are unseen; no such root receipt was inspected here. Root's separate component timer remains in another frozen worktree and was not inspected. The unrelated IQ helper qualification (768 calls, normal/no fault) does not resolve this question.

No new implementation or adoption decision follows. R191 should remain unchanged as the original source/lifetime audit; this report records only the correction that a terminal publication fence can preserve earlier queue overlap and distinguishes pre-submission/partial-bulk/concurrent-producer cases.
