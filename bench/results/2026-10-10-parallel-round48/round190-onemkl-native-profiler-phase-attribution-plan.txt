Date: 2026-10-10 (Asia/Tokyo). Read-only research and bounded experiment plan. No source edit, build, test, compiler, device query, GPU work, inference, profiler, service operation, Git operation, cleanup, or GPU recovery was performed. The only new file is this report. This plan proposes a future root-owned diagnostic; it is not an installed-tool qualification, profiler result, performance result, or implementation approval.

## Question and decision

The current source has no dependable record joining an active native-IQ MoE expert's GU/down call to the actual internal device work issued by oneMKL. A host stopwatch around the wrapper includes host dispatch and later completion; the oneMKL event is a completion handle, not a documented whole-library service timer; a generic profiler kernel row does not identify a Strata expert by itself. This is the remaining attribution gap.

Use a diagnostic-only, root-owned trace of one bounded actual MoE prefill window, with a host-side ordered operation ledger and ITT labels, plus the returned oneMKL event handle if the trace can expose a real linkage. Use Intel PTI `unitrace` as the first candidate because its documented kernel trace includes host/device interactions and dependencies, it can capture Level Zero calls and SYCL/UR calls, and it supports ITT task annotations and in-application pause/resume. Keep hardware-counter mode out of this first pass. Optionally use VTune XPU Offload only if the owner separately confirms its collection requirements and permissions; it exposes the relationship between user ITT tasks and submitted device tasks, but adds no reason to assume B570 metric support. Do not use Intel GPA for this SYCL compute attribution: Intel positions it for graphics APIs, its published supported Windows API list does not include SYCL/Level Zero compute, and Intel announced GPA 2025.1 as its final release with no further support.

The diagnostic must preserve the existing oneMKL precision, expert order, queue, scheduling, no-per-expert-wait policy and completion/error path. It may expose the event already returned by oneMKL through a diagnostic sink, but it must not add a GEMM, an extra wait, an extra dependent marker, or an event-driven fallback. If the event's native handle cannot be matched to trace dependencies and actual commands, report that join as unavailable and retain only the proven queue-order observations; do not use the oneMKL event duration as a proxy for all internal GEMM kernels.

## Recommended bounded instrument design

Add instrumentation only to a disposable, root-owned diagnostic build/snapshot derived from the pinned immutable source after the owner chooses an integration point. Do not modify this immutable source tree. Keep the production binary/path and normal service untouched.

For each GU or down oneMKL call on the existing in-order compute queue, append one fixed-size `NativeGemmRecord` in host enqueue order. Give each record a process-local monotonically increasing `op_id`; include phase (`GU`/`down`), layer, expert, routed rows, M/N/K, dtype/compute mode, queue identity, wrapper call ordinal, submit thread, and the oneMKL `sycl::event` retained until the already-existing safe completion boundary. The only host labels needed for human-readable phase tracking are ITT tasks such as `strata.moe.prefill.layer=<n>.expert=<e>.phase=GU` and `...phase=down`. If putting IDs in the task name is too costly, use an ITT task domain/name for layer+expert+phase and keep the numeric `op_id` in the ledger. Do not add host timestamps to the event ledger as a way to estimate device time.

Make the smallest event-visibility seam: a diagnostic-only out-sink at the DPCT/oneMKL GEMM boundary that stores the exact event returned by oneMKL for this existing call. The current wrapper's public return is `void`, so the normal form has no event to inspect. Keep the ordinary production call signature/behavior for non-diagnostic callers. Do not confuse the output event with any subsequent host-task event, do not wrap it in another dependent submission, and do not wait on it per expert. Retain event objects/records through the same existing queue drain that closes this chunk; retire them only after that drain and profile queries. Preserve the existing async-error and fail-stop rules. A completion or async error after accepted work invalidates the diagnostic and must not permit scalar retry or output reuse.

For identity linkage, the oneAPI Level Zero backend interop reference documents `sycl::get_native<backend::ext_oneapi_level_zero>(event)` as exposing a native `ze_event_handle_t` for SYCL event on that backend. In the diagnostic, record the handle value as an opaque per-process identity only if backend is Level Zero, the call succeeds, and ownership remains with SYCL. Do not call Level Zero wait/reset/query/submit operations through that handle. Try to join it to the native trace only where the trace visibly records the same event in a signal/wait/dependency field. Handle values can be reused after lifetime ends; do not use them without the live operation ordinal and source event lifetime. Native interoperability is a backend-specific aid, not a portable SYCL guarantee, and it is not proven that the exact installed queue/library trace will display the needed references.

The ordered record is crucial even if native-event linkage fails. The current flow is a serial expert scheduler on a shared in-order queue; record every GU/down call as issued and keep the expert/phase order. In the device trace retain queue/engine identity, actual native kernel and copy records, per-command start/end in the profiler's own domain, and native queue/event dependency handles where emitted. Correlate by explicit returned-event handle first, and by queue order and source call order only when the trace proves there were no intervening unrelated queue commands. If neither proves a one-to-one/many-to-one assignment, mark the internal launch set `unattributed`; kernel names alone do not prove expert ownership.

Use the profiler's own timeline correlation and timestamp domain for any visual relationship between host ITT tasks and GPU commands. Do not subtract a host `steady_clock` sample from a SYCL or Level Zero timestamp, convert one domain with an unverified offset, or present mixed-clock differences. R184 explains that event start/end refers to the associated action and oneMKL only promises that the returned event can be waited on to ensure computation completion. A completion event may therefore be valid while its interval omits internal work or represents a tail command. Query returned-event `command_start/end` only if the exact owning queue already enables profiling, the device advertises `queue_profiling`, and post-drain queries succeed; do not enable profiling by constructing/changing the production queue. Keep event timestamps as separate columns and never equate their duration with whole-GEMM service absent trace evidence.

## Concrete tool comparison and invocation

**First choice — PTI unitrace, software command/kernel trace, no hardware counters.** Current official PTI docs support `--chrome-call-logging` for Level Zero host calls, `--chrome-kernel-logging` for device activity plus host/device interactions and dependencies, `--chrome-sycl-logging` for SYCL runtime and UR, and `--chrome-itt-logging` for app ITT annotations. The tool supports `--start-paused` and in-process `__itt_resume()` / `__itt_pause()` to collect one bounded region. Run only in the root-owned traced diagnostic process, with existing runtime environment fixed:

```sh
unitrace --chrome-call-logging --chrome-kernel-logging \
  --chrome-sycl-logging --chrome-itt-logging \
  --start-paused --session r190 --output-dir-path "$TRACE_DIR" \
  <root-owned-diagnostic-runner> <same-model-and-input-arguments>
```

The runner's diagnostic build resumes capture immediately before the selected actual MoE phase/window and pauses only after its already-existing completion/drain boundary succeeds. This is necessary because asynchronous work submitted before a pause may execute later; ending collection at host return would truncate the kernel tail. The chosen region must include both GU and down for the selected layer/chunk and all associated copies/dequant work, not only a wrapper call. Use a fresh application process. PTI launcher process supervision, hard wall-time deadline, private output directory, and an uncompressed trace total cap of 64 MiB are mandatory. On cap, timeout, or collector error, close as incomplete/diagnostic failure, retain the status and relevant excerpt, and do not quietly trim evidence then call it complete.

PTI documents `-d -v` as per-kernel timing/resource summary and `-s` as queued/submit/execute intervals. They are useful only as a separate small discovery pass if the basic trace needs a compact kernel inventory; no metric `-q`, stall sampling, raw timestamp arithmetic, or repeat collector is needed in the initial phase join. Existing R90/R158 reports note hardware metric availability varies and a B580 PTI metric query failed on another stack. Do not assume B570 counters or repeat the counter installation/support exploration. Do not collect a trace on top of the clean timing process.

**Optional independent view — VTune XPU Offload.** Current 2026.1 docs say its timeline records ITT user tasks and device-side tasks and links a GPU task to its submitting CPU task. If the unitrace trace cannot show useful host-task association, a separately owned, deadline-bound `vtune -collect gpu-offload -- <same bounded diagnostic runner>` collection is a reasonable one-pass cross-check, using the matching ITT labels. This is a different trace run, not something to overlay numerically. Its permissions and collection behavior must be established by the owner before execution: Intel's documentation says to run GPU analyses with root privileges on Linux typically, and detailed counters/available metrics are hardware-dependent. Do not elevate, alter sysctls, enable/disable kernel tracing, or claim the tool works on B570 without an admitted smoke. Existing ptrace-denied VTune software-hotspots reports are not a reason to retry that unrelated analysis. No hardware metrics are in scope here.

**Excluded — Intel GPA.** Current Intel product docs identify GPA as graphics application analysis (DX/Vulkan/limited OpenGL/OpenCL workflows), while the current product page marks 2025.1 as final and says it is discontinued in 2026. It is not a supported evidenced SYCL oneMKL compute-tracing route here. **Excluded — raw Level Zero counter correlation**: PTI's Level Zero metric guide requires matching metric query timestamps to device activity, with timer conversion rules; this needs counters and clock-domain handling not required for the first attribution pass. No raw `zeDeviceGetGlobalTimestamps`/host offset conversion is part of this plan.

## What the result may and may not say

Report these measurements separately, never collapse them under one label:

1. **oneMKL operation completion:** whether the retained oneMKL return event completed successfully at the existing queue drain, with async errors closed. This is a boolean/lifecycle fact, not a duration.
2. **Returned-event action time:** if the queue was already profiling-enabled and event queries work, record raw `command_start`, `command_end` and their same-event delta. This times the SYCL event-associated action. It is not a whole-GEMM promise.
3. **Library-internal service tail:** the trace's last internal device/command completion proven to be in the operation dependency chain. This can be named the observed tail only if the event signal/wait or a complete dependency/queue-order chain proves ownership. Otherwise say `tail_unjoined`.
4. **Native kernel service:** list each attributed kernel/command's profiler start/end and duration, keeping command kind (kernel/copy/other), queue/engine, operation ID, actual expert/phase join evidence, and exact kernel identity. Do not include a library host wait in kernel duration.
5. **Kernel-duration sum:** sum only attributed same-domain kernel durations and label it `sum`, never operation elapsed time. With overlap or multiple engines, this sum can exceed the wall span.
6. **Device span/critical path:** report `max(end)-min(start)` only as the observed native-work envelope for the matched set. It includes idle/dispatch gaps within that span. A critical path may be claimed only if the trace exports enough dependency edges to compute that path; a kernel list, queue order by itself, or time interval does not establish a multi-queue dependency graph.
7. **Unattributed library dispatch gaps:** if host ITT wrapper bounds surround device activity in the profiler's internally correlated timeline but some device commands cannot be assigned, list those commands and gaps as unattributed. Do not derive a gap duration by subtracting host and device timestamps in application code. ITT task and profiler thread relationship is diagnostic context, not proof that every kernel issued in that scope belongs to that expert.

Likewise preserve successful actual model route counts and failures as separate observations. A trace of one selected chunk is not an inference-performance sample. No threshold for adoption, speedup, precision loosening, model/service status, or route change is inferred from this work.

## Interpretation stop conditions

Stop attribution as unresolved if: no event can be retained from the actual helper without changing completion semantics; the exact queue/backend or runtime is not the task-pinned stack; the existing queue lacks profiling and someone proposes changing it; collector isn't admitted or exceeds the finite bound; trace is incomplete; internal oneMKL kernel tasks appear on multiple queues/engines without a dependency edge; operation ID joins only by wall-clock overlap; the event's native handle is absent or ambiguous; or any async completion/fault state is uncertain. Preserve what was observed and make no guessed attribution. The host headless Orca recovery issue is separate and excluded.
