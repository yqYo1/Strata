## Finding

The fixture has a credible source path for measuring the returned-event service intervals of the two existing IQ4NL helper submissions under its exact, warmed, direct-buffer workload. I found no source defect that by itself turns a recorded `end-start` interval into a different helper's interval: each wrapper passes its own local `queue.submit` return directly into the receipt hook, and the fixture independently validates arm, type, `n`, queue, pointers, scope and serial before querying that retained event after the planned drain. It checks receipt counts separately from call attempts and successful wrapper returns. A sticky receipt loss or async error rejects the completed batch; a drain uncertainty takes the fail-stop path without releasing potentially live allocations. This supports component timing validity when the run's full terminal and per-batch records pass. It does not make service timing a model, cache-capacity, or production-path measurement.

Two interpretation limits deserve emphasis. First, the four cells in every service block use only four cyclic rotations of one cell sequence, repeated twice. This balances each cell across the four positions, but does not sample general cell permutations. The emitted predecessor and position fields permit a narrow check of observed sequence effects; they do not make the sequence independent or fully crossed. Second, every cell's post-completion numerical readback copies both outputs and the *entire 64-input device cohort* to host memory and drains that copy before the next cell. Those copies are outside the measured call and event intervals, but they create a material and repeated cache-conditioning step between cells. Treat the resulting comparison as the specified address-regime contrast under this readback cadence, not as an isolated or equal-cache-state contrast.

## Event mapping and numerical boundary

The service fixture calls only `iq_dequant_f16` and `iq_dequant_f16_prefill_iq4nl`; it adds no kernel body. In the frozen kernel translation unit, each wrapper stores the exact event returned by its existing submit into a local and passes that local to `iq4nl_receipt_record` after submission. The receipt hook does not obtain a queue-tail event. It records the arm and argument tuple, resolves the queue tag, and attempts to retain that event in the preallocated slot; any retention exception marks the sink invalid. The fixture then drains the in-order profiling queue before metadata validation and timestamp queries. It checks pairwise event inequality, `submit <= start <= end`, and nondecreasing event intervals in call order, while preserving zero service intervals. The queue/device admission checks the actual queue's profiling and in-order properties, Level Zero backend, profiling aspect/resolution and the pinned B570 identity.

The host plan is built independently of the sink. Capacity and tuple checks precede scope installation/submission; the receipt count and serial must both equal the planned count. Attempted and successfully returned calls are counted independently. On any post-drain receipt, timestamp, async, or numerical rejection, the batch does not become a timing pass. A synchronous submit or planned-drain exception exits through fail-stop, retaining device allocations and event state. This is consistent with R179's distinction between known completion and uncertain completion.

For correctness, the full prephase and final replay exercise both wrappers on all 64 input views against the independent scalar RNE oracle, with input immutability and full guards. Each timed service cell has 64 calls that overwrite only two output slots; its readback compares only the final occupant in each slot. The code labels that scope and does not claim per-call numerical checking from those two surviving outputs. Thus the per-call timing receipts are covered by exact event accounting, while full per-input numerical qualification comes from the separate replay phases. A run should retain these phase distinctions in any result summary.

The CMake target is opt-in and requires the dequant, event-receipt, parity and public `ze_loader` options. The target has no default production enablement. The fixture's host-only mode constructs no queue, and malformed arguments reject before GPU setup. The source's fixed schedule, shape and memory sizes match the handoff. None of these source observations establishes successful compilation or device execution.

## Schedule, conditioning, and clock interpretation

The planned service cells are generic/same-address, private/same-address, generic/rotation64 and private/rotation64. Each has 64 calls, alternates two output slots and uses `n=1,638,400`. Same-address repeats input 0; rotation visits all 64 distinct addresses once per cell, with a block-dependent starting index. All packed inputs contain identical bytes. Consequently this compares repeated use of one address against rotating among 64 equivalent addresses; it does not compare different input data or prove a working-set/cache level.

The eight service blocks are generated from `[0,1,2,3]`, `[1,2,3,0]`, `[2,3,0,1]`, `[3,0,1,2]`, then those same four orders again. Every cell appears twice in each position across the eight blocks. However, these are rotations of one cyclic order rather than independently permuted sequences. Exact-position and predecessor summaries can reveal large observed drift or predecessor dependence, but the sequence design cannot estimate arbitrary order interactions. Only two repeats exist for each of the four block orders, so order-stratified uncertainty will be coarse. The order design is suitable for a small component screen with those limits stated; it should not be described as randomization or full counterbalancing.

Within a batch the measured service value is the retained event's device-backend `end-start`, and queue delay is separately `start-submit`. Host submit duration and batch submission/wait clocks use `steady_clock`; they are not mixed with event timestamps. The event hooks, per-call host clock reads, 64 retained event objects, and output logging make this an instrumented submission path. Event service remains the reported quantity, while host submission and batch wall are separate observations. Any measured difference is for this instrumented fixture and fixed cadence; there is no uninstrumented paired control here. Timer resolution and raw timestamps, zero-duration counts, paired differences, order/position, predecessor and block trend should remain visible in interpretation.

After each service batch's DQ drain and event queries/logging, `readback(..., all=true, ...)` submits D2H copies for both output allocations and all 64 complete input allocations, then drains that copy. The DQ service timestamps and `host_submit_window` finish before this step, so the copy does not directly enter a timed call. It does mean the next cell begins after a full-cohort device readback. Device-cache effects of that operation are unspecified by this source and cannot be quantified from the fixture, but the operation is an intervention on the memory/queue history. In particular, cell order, predecessor and the intervening full-cohort readback cadence belong to the measurement condition. This is why same-address and rotation64 remain address-regime labels and cannot establish coldness, cache residency, cache level, or equality of cache state between cells. No source change is recommended based on this audit; removing readback or inserting another conditioning sequence would change the frozen protocol and its correctness checks.

The two warm passes run both helpers over all 64 addresses, alternating output slots, followed by one drain. The full prephase and its readbacks precede warmup; the warm pass therefore does not establish a known cache state, and it cannot erase the later per-cell readback effect. The source appropriately makes no cache-capacity or cold-cache claim. These measurements also omit the production expert-copy/ring-wrap schedule, DQ/GEMM overlap, routed expert-row counts and first-token latency.

## Result boundary

This audit finds the exact-event receipt and known-completion boundaries statically coherent for the planned fixture. The main qualification caveats are the repeated cyclic order family and full-cohort readback conditioning between cells. If the clean `--service` run is otherwise valid, report its measurements narrowly as instrumented direct-helper component service under the specified warmup, four-cell sequence, input address regimes and readback cadence. Include per-call receipts/raw timestamps and batch rejection accounting; show paired/order/position and block drift, and preserve zero durations. Do not infer equal cache state or a particular cache level. Do not treat the qualification mode's correctness pass as a service result.

The root-owned service qualification and later adoption evidence remain separate. In particular, this source audit does not establish the requested minimum 32,768 actual model prompt positions, the full physical 262,144-token lifecycle, independent repeated decode, or any model-level benefit. Those claims require their own evidence at the exact production call path.
