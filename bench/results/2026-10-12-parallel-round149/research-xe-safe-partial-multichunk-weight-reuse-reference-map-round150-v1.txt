## Finding

A useful, source-plausible intermediate point between current chunk-major and R142's full-prompt layer-major schedule is a **bounded layer-major window of G existing token chunks**. It can reduce repeated materialization of experts without allocating a full-context residual plane. This is a new proposal, not existing Xe behavior or a qualified optimization. It gives deterministic reuse only if the active layer's full expert set stays resident in a GPU bank for the whole window; retaining only a partial, dynamically routed set gives hit-rate-dependent reuse and no worst-case guarantee.

Let `T` be the existing chunk size and `G >= 1` the number of chunks in a window. For each window `[g0, g1)`, run layer `l` over its chunks in increasing token order, then advance to layer `l+1`; keep at most the window's FP32 residual rows between layers. This adds a host handoff buffer sized `min(n-g0, G*T) * D * sizeof(float)`, `D = HC*n_embd = 10,240`, not `n*D` for the whole prompt. `G=1` is the present chunk-major order and provides no cross-chunk expert reuse. `G` equal to all chunks approaches R142 and its full plane. Intermediate G bounds the host plane and offers at most G-way reuse before the active layer is changed. This is window-bounded layer-major scheduling, not a recommendation to enable the prior full-context schedule.

## Why the source order can preserve model state

`Prefill::run` currently loops over chunks (`src/prefill/prefill.cpp:1288`) and, inside each chunk, processes the stage's layers in order. Its `R` is an FP32 `T*D` activation (`:782`) and each layer writes the updated residual through the existing hyper-connection path (`:2875-2902`). A window schedule would store that same FP32 boundary value for each row and upload it into the existing `m.R` chunk buffer at the next layer. It does not quantize, recompute, or otherwise change the hidden-state representation; existing per-layer projection, normalization and activation quantization stay in the ordinary layer body.

The decisive state invariant is: for every individual layer, its chunk sequence remains strictly increasing and identical to today. GDN uses its layer-specific recurrent and convolution state, both FP32, addressed by the layer's GDN ordinal (`prefill.cpp:1246-1247,1645-1656`; `core/session.cpp:42-48,102-103`). QSA uses its own indexed `QsaState`; its K/V append, indexer update, selection and attention remain inside the normal layer pass. For streamed QSA, past K/V is staged from the host authority and the current chunk is appended/mirrored before selection and attention (`prefill.cpp:1661-1687,1689+`; `core/layer.cpp:1072-1089,1110-1123`). As long as each QSA layer sees chunks once in order, the schedule does not need a new cache authority or state replay. Preserve the actual state ordinal when layers interleave GDN and QSA; do not use `qsa_primary()` as a proxy for the currently active QSA layer.

MoE routing is content-dependent per token. The chunk route must be computed by the ordinary layer body for that chunk; this proposal does not speculate routes or reuse another chunk's token-to-expert assignment. Current streamed prefill plans per-chunk, per-layer expert transfers (`prefill.cpp:1385-1429`) and consumes source/cache slots in that chunk. A dedicated layer bank can instead copy the active layer's native experts once per window and map that layer's entries to stable slots for all G chunks. All other layer mappings must remain untouched, as must the decode/profile cache. To guarantee no repeats for arbitrary routes, the bank must fit the whole layer expert set (plus existing workspace and safety margin); a smaller hot subset can still be evicted by a later chunk's route. The ordinary tail-slot scratch loan is not proof that an additional layer bank fits.

PLE history is session-owned and advances with token positions, while its n-gram rows depend on prompt tokens; current code gathers rows into two chunk buffers and uses PLE only at layer 1 (`prefill.cpp:1257-1275,1260,1348+`; `session.cpp:52-55,75-78`). Keep `ple_prev` stable while earlier layers of a window execute; allow layer 1 to advance it once, in chunk order; do not advance or reset it again for higher layers. Existing `on_chunk` is called after a complete current chunk and the callback drives draft-KV/MTP processing (`prefill.cpp:2981-2989`, `generate.cpp:6455-6456`). In a window schedule, call it once per prompt chunk only after that chunk has completed the final layer, preserving order. Do not emit intermediate-layer results to the callback.

## Lifecycle boundary and limit

After a window's first layer has reached `g1`, but its later layers have not, the per-layer session states describe different token prefixes. That is adequate for an internal one-shot prefill loop because no layer consumes another layer's GDN/QSA state. It is not a coherent request checkpoint, cancellation point, decoder-ready prefix, or recoverable serve boundary. Initially this schedule should be one-shot/session-discard-only on any partial failure, with no stage/pipeline handoff or cache checkpoint, matching the safety restriction already identified by R142. Publishing callbacks only after final-layer work for each chunk does not make the other-layer state coherent. A serving integration needs transactional capture/restore of all relevant GDN, QSA host K/V, indexer/map, PLE and MTP state across the window, and must account for the duplicate live state memory.

The full-context boundary remains `max_cells=262144`: for ordinary generation, preserve the current split where the batched prompt path may handle `n_prompt-1` and the final prompt token is handled by the single-token path; never lower context capacity to fit the buffer. The separate exact-full-context probe can include all rows, with a final short window. The host plane is sized by actual rows in the active window, not by shrinking the session's fixed max-context QSA host pool.

## Reference implementations and transfer limits

- The 2025 Layered Prefill paper and its authors' repository shift scheduling from token chunks to contiguous layer groups to avoid repeated MoE expert loads; the repository also says it can combine layer scheduling with chunking. This validates the general scheduling axis, not this design's memory formula or recurrent-state correctness. The published/example implementation focuses on transformer serving and keeps decode running in each iteration; it does not establish GDN recurrence, QSA sparse-index selection, streamed host-KV, MTP, or Strata callback/checkpoint parity. Source: [Layered Prefill paper](https://arxiv.org/abs/2510.08055) (submitted 2025-10-09) and [authors' implementation/algorithm](https://github.com/scale-snu/layered-prefill) (reviewed 2026-10-12; mutable `main`, no immutable commit recorded by this lookup).
- KTransformers' KT-Kernel README has a direct long-prefill reference: for RAWINT4/FP8, a token threshold selects hybrid CPU/GPU prefill below threshold and layerwise GPU prefill above it, with the README explicitly requiring VRAM for one extra MoE layer. This supports a thresholded active-layer residency plan, not a bounded residual-window proof. Its heterogeneous path and model/kernel formats differ, and the cited README does not show GDN/QSA state semantics. [KT-Kernel README](https://github.com/kvcache-ai/ktransformers/blob/main/kt-kernel/README.md), reviewed 2026-10-12; mutable `main`, no immutable commit recorded.
- vLLM's scheduler and SGLang's `PrefillAdder` demonstrate conventional chunked prefill as token-budget admission/resumption; that is relevant to per-chunk KV/state ownership and fairness, but it still repeats the stack for each chunk and does not retain an active layer's experts across multiple chunks. [vLLM scheduler](https://github.com/vllm-project/vllm/blob/main/vllm/v1/core/sched/scheduler.py), [SGLang scheduler guide](https://github.com/sgl-project/sglang-jax/blob/main/docs/architecture/03-scheduler.md), reviewed 2026-10-12.
- Intel LLM Scaler's public README lists model streaming load and Qwen/MoE support, but this search did not find a directly documented multi-chunk layer-major schedule or reference code path applicable to this stateful Xe loop. Treat its general model-loading feature as out of scope rather than implying it proves this schedule. [Intel LLM Scaler](https://github.com/intel/llm-scaler), reviewed 2026-10-12.

## Next evidence needed

Before implementation or any claim of benefit, compare the present chunk-major stream against window sizes G=1 and at least one G>1 on an isolated diagnostic path. Record per-layer/per-window source bytes and copy calls, expert bank occupancy and route-union/capacity misses, host-plane reserved/committed/RSS, device peak allocations, QSA host/stage pages, and timing split by copy/compute. For correctness, compare exact per-chunk residuals, every layer's final GDN state and QSA host K/V/indexer/page map against current chunk-major for mixed GDN/QSA model paths; include early/cancel/error disposal and full final partial window. Tests/probes must establish cache state and callback order. No speed, memory-fit, or quality threshold is proposed here; no evidence in this report establishes benefit or acceptance.
