## Chunk arithmetic

`Prefill::run` advances `c0` by `m.T` and uses `T=min(m.T,n-c0)` (`prefill.cpp` around 1223, 1288). For `n=65,535`:

| Fixed T | Full chunks | Tail | Total Prefill rows | Chunk invocations |
|---:|---:|---:|---:|---:|
| 6144 | 10 | 4095 | 65,535 | 11 |
| 8192 | 7 | 8191 | 65,535 | 8 |

Thus a truly per-chunk/per-layer fixed submission or state setup repeats 11 versus 8 times, a 27.27% reduction in such repeats at T8192. A truly per-row operation still sees 65,535 rows in both arms. Batch tails change individual call shapes, padding, expert coverage and QSA bounds; they do not change the total input-row count. Exact 64K prompt Prefill arithmetic does not include the final prompt token at position 65,535, which goes through the native verifier path separately.

## What repeats, and what scales with rows

The outer chunk loop encloses the whole layer traversal. For every chunk, source rebuilds token/step and route tables, prepares PLE batch inputs, then executes every selected layer and its two hyper-connection halves. The dense projections, GDN recurrence/convolution, QSA KV append/indexer/select/attention, MoE route/shared/expert/combine, and PLE work are therefore invoked anew per chunk, but their useful token work covers the same aggregate 65,535 rows (except stateful attention's context-dependent selected keys). Chunk count changes launches, framework calls, per-chunk synchronization/host setup, tails, grouping boundaries, and repeated full-weight transformations. It does not by itself multiply the number of input tokens.

The particularly important repeated work missed by a token-FLOPs-only view is `Gemm::native`: each `native_proj` calls it for the current T rows; for native weight references it dequantizes the full `[N,K]` matrix into the configured scratch (32 Mi FP16 elements = 64 MiB of FP16 storage) (or row slices if it exceeds scratch) and then calls `f16` (`gemm.cpp:363+`). Consequently, every native projection's packed-weight read/dequant output and full matrix-preparation pass are repeated once per chunk, while its GEMM activation MAC count sums over the fixed 65,535 rows. Reconstruct packed bytes from the actual ref's type and shape, not “one weight read per token” and not the model's total pack size. BF16 projections use `Gemm::bf16` and don't take the native-IQ full-matrix dequant route; their products still recur per chunk with T row count. The current code invokes native projections three times per GDN layer (`attn_qkv`, `attn_gate`, `ssm_out`), four times per QSA layer (`attn_k`, `attn_v`, `attn_q`, `attn_output`), plus the native PLE-key path only when its source predicate selects it. Source comments describe 36 GDN and 12 QSA layers for this geometry; the receipt must confirm actual geometry/layer count.

Other repeat-sensitive work:

- `qsa_step_fill`, token/embedding gather, broadcast, rowwise HC, dense projections, GDN recurrence, output and KV append cover the same number of token rows in total; per-call launches and fixed setup repeat per chunk. Position-dependent QSA/indexer work is not a constant per row: selector's `active` extent is taken from the last query of each `m.sel_batch` batch, so report query widths/active block counts rather than treating total rows as a complete work measure.
- Batched QSA indexer append is selected once for each QSA layer/chunk unless the per-token diagnostic override is set. QSA selection loops in `m.sel_batch` query batches; 6144/8192 can therefore alter the number and size of selection submissions even with equal total query rows. QSA attention appends the same K/V rows but reads each query's selected causal cells; logical selected-cell bytes depend on the per-position width and actual KV format, not just T.
- PLE lookup/gather and upload, if enabled, process rows at layer 1 and can be read ahead; their row count is invariant, while chunk gather/copy/event boundaries and double-buffer ownership repeat per chunk. PLE's two host buffers scale with T as R148 records.
- MoE router/shared/expert/combine process T rows each layer; routed assignments are exactly `T*K` per layer where K=10, so sum assignments over the 65,535-row prefix is 655,350 per MoE layer in both arms. Expert activation rows per expert and active GPU expert set are data- and chunk-dependent. Compact grouping can also alter number of grouped product calls/row bounds, although its row sum stays conserved.
- `stream_all` is selected for T>=2048 with a ring >8 and an ExpertSource. It builds the per-chunk sequence of all nonresident expert blobs but the streaming consumer skips IDs not routed; H2D copies and dequant are for actually consumed/routed nonresident experts, not automatically every sequence entry. For non-stream-all path it stages only the active `order` entries. Cache residency and pin/transient state change which of those are copies versus resident reads.
- Initialization and weight load are once per Prefill object; they are not multiplied by the chunk count. Per-chunk host scaffolding, route formation, issuer/stager wave, and phase marks do repeat. R148 allocation-byte scaling is a separate requested-memory fact, not evidence of the workload or physical bandwidth.

## Per-layer expert compute and logical-byte equations

Pinned `prefill.cpp` fixes `N=n_embd=2560`, `K=top-k=10`, `n_ff=640`; the native expert layout has per-layer `gu_type`, `d_type`, `gu_row`, `d_row`, `up_off`, `down_off`, and `bytes` (`NativeExpertLayout` / `iq_row_bytes`). Gate/up each have `n_ff` rows of `n_embd` values; down has `n_embd` rows of `n_ff` values. Let `b_gu(l)=iq_row_bytes(gu_type_l, n_embd)` and `b_d(l)=iq_row_bytes(d_type_l,n_ff)`. Then for one expert in one chunk:

- Packed bytes read by explicit native dequant (logical tensor payload): `Q_l = 2*n_ff*b_gu(l) + n_embd*b_d(l)`. This comes from the separate gate and up matrices at `[640,2560]` and down at `[2560,640]`; native blob padding and unrelated expert metadata are excluded. If type is not an IQ type supported by `iq_row_bytes`, use that exact type's source layout/row-size function and blob bounds rather than inventing an IQ size.
- FP16 bytes written by GU+down dequant: `H_l = 2 bytes * (2*n_ff*n_embd + n_embd*n_ff) = 9,830,400 bytes (9.375 MiB)`. This is independent of IQ type and T for each whole expert decode. With `STRATA_PREFILL_NATIVE_DEQUANT_BATCH=0`, the source calls the per-expert GU and Down functions; group dequant calls and group acceptance are not part of this arm.
- For `m_e` routed rows assigned to that expert, ideal dense-MAC work is GU `2*m_e*n_ff*n_embd`, SwiGLU `O(m_e*n_ff)`, Down `2*m_e*n_embd*n_ff`; using 2 FLOP/MAC, products total `6*m_e*n_ff*n_embd = 9,830,400*m_e` FLOP, plus the elementwise gate/nonlinearity/combine operations. Summing experts gives `9,830,400 * rows_gpu` FLOPs per MoE layer, where `rows_gpu = T*K - rows_cpu`; when CPU share is off, this is `9,830,400*10*T` per layer. Useful product FLOPs sum to the same value over the full prompt regardless of T if the GPU/CPU split and exact row assignments are held constant.
- The fallback's whole-expert dequant count is instead the number `A_l,c` of active GPU-side experts in layer l/chunk c. Its logical packed decode input is `sum_l,c A_l,c*Q_l`, and its FP16 writes are `sum_l,c A_l,c*H_l`. Those counts are not proportional to routed rows: a single route row incurs a full expert weight decode in this path. Larger T changes A through the union of routed experts and can reduce the number of chunk-level whole-expert decodes, but this cannot be quantified without the per-chunk route census.
- The later grouped product reads decoded FP16 expert weights again: for each product group, logical matrix weight payload is `G*H_l`, plus activation/accumulator/output accesses. Those FP16 weight values may be served from cache; this is a logical load count, not DRAM traffic. Compact mode gathers only `group.rows` activation rows (16-bit `Xs` `[rows,2560]`) and builds bounds; the product output writes float `Dm` rows `[rows,2560]`. Across experts, gathered row count is `rows_gpu` (no duplications), whereas model-weight decode bytes depend on A. For a useful-I/O tally per routed row, GU reads `2560*2` B from X and writes `1280*4` B to GU; SwiGLU reads `1280*4` B from GU and writes `640*2` B to H; Down reads `640*2` B from H and writes `2560*4` B to Dm. These logical per-row accesses omit rereads/reuse inside GEMM tiles, bounds/padding and cache transactions; actual kernel transactions need counters.

The native FP16 fallback product shapes per expert are GU `[2*640,2560]` with interleaved output `[m_e,1280]`, and Down `[2560,640]` to `[m_e,2560]`. Products are grouped in `compact_moe_groups`; all expert counts and route-prefix bounds are validated, each group sums rows `<=T`, and `max_rows` controls grouped-kernel tile launch geometry. In the DP4a `f16_groups` path, one BLAS call per nonempty expert may be attempted; otherwise code falls back to `xmx_gemm_grouped`, whose backend may be joint-matrix/XMX, DP4a, or another configured route. Receipt and microbenchmark must record actual accepted/declined calls and backend. Compact scratch changes the active row gather and group split, not the logical total of assigned expert rows. `FUSED=0` prevents resident native experts from taking the IQ-fused grouped product; it does not turn off XMX for the later FP16 GEMM.

For every native dense projection weight `w`, use `w.native_type` and `w.ne0/ne1`. A per-call logical payload ledger for its `T x ne0` FP16 activation, `[ne1,ne0]` FP16 dequant output, and `T x ne1` FP32 result is respectively `2*T*ne0`, `2*ne1*ne0`, and `4*T*ne1` bytes. Weight transform and product can overlap other queued work, so do not sum these as elapsed time or external-memory traffic:

- Packed payload per full matrix pass: `P_w = ne1 * iq_row_bytes(native_type, ne0)` for formats handled by this row-size table; check exact layout bytes for any other native type.
- FP16 temporary write: `2*ne0*ne1` bytes. The downstream GEMM logically reads that temporary once per product invocation.
- Useful GEMM work: `2*T*ne0*ne1` FLOPs, with T rows for that chunk; across chunks, `2*65,535*ne0*ne1` FLOPs (for a projection executed on all prompt rows).
- Candidate total for a fixed set of native projections is `sum_w chunks_c P_w` packed reads and `sum_w chunks_c 2*ne0*ne1` temporary writes if the full matrix dequant occurs once per invocation. The row-sliced case preserves the same total payload, with additional slice/call boundaries.

BF16 weight types use the BF16 route and shape-specific reference matrix reads; `Gemm::bf16` may select FP16 conversion, oneMKL, XMX or row GEMM. Do not fold these calls into IQ-dequant bytes. For all phase families, “logical bytes” means source tensor or buffer payload inferred from the actual source shape and dispatch; it does not include cache-line/transaction amplification, uncoalesced traffic, repeated cache fills, staging page faults, padding, or physical DRAM traffic.

## Dispatch-matched discriminator beyond R146

R146 already defines three useful legs—dequant-only, product-only from the same FP16 materialization, and joined production group—plus conditional staging. R150 adds the chunk-repeat decomposition and requires that the per-expert versus per-row effects be explicit:

1. From a closed 64K receipt, record each chunk's actual T, layer and expert route counts, `A_l,c`, CPU rows, resident/streamed status, exact packed bytes, dequant calls, product groups, group `max_rows`, and accepted/fallback backend. Compare two summaries: totals by unique processed row/route; totals by chunk-level full-matrix visits and launch/group calls. This identifies whether T8192 mainly removes repeated weight transforms/dispatch or changes row-tail utilization and expert union.
2. Dequant-only must use the actual layer `gu_type`/`d_type`, dimensions and packed blobs, production single-expert GU+down calls, same stream and output layout, but no GEMM. Measure device interval and host submit/completion separately. Report `Q_l` reads and `H_l` writes per expert and count. An external-memory counter and L3 counter are needed to say whether those logical bytes reached device memory; without them, report only observed time and logical-byte/time.
3. Product-only reuses the correctly materialized FP16 weights and exact compact group boundaries and route rows. Preserve group count, bounds, `max_rows`, N/K, `w_stride`, output placement, and `Gemm::f16_groups` attempt plus fallback. Compare one-call production chunk shape and rotating/hot cases only as separate cache regimes. Collect GU, SwiGLU and Down intervals separately. A square GEMM or padded full-T GEMM would not match the route.
4. Joined case uses the production gather → dequant → grouped GU → SwiGLU → grouped Down chain with those actual expert groups; separate stage device intervals, queue dependencies, and endpoint wall. Keep allocations, source staging, cache ring and H2D events distinct. A stage event duration does not prove critical-path contribution when copies or other kernels overlap.
5. Per-row/dense layers need a separate matched shape sample: for each actual `w`, compare T=6144 and T=8192/tail call shapes but report both per-invocation timings and normalized per-row products. Native projections must include their production full-matrix dequant before product; an XMX-only benchmark would miss the repeated preparation cost. BF16 projections remain their own dispatch cohort.

To distinguish memory from compute, use supported exact-device counters, not arithmetic roofs: device external-memory reads/writes and L3 bytes/hit/miss for each phase, paired with command start/end events and predecessor/successor dependency chain; record whether the measured group is hot or a rotating set larger than verified cache. Dequant time with substantial measured reads/writes and low execution pressure is evidence for a memory/decoder path only when counters say so; high L3 with low external traffic suggests cache service; product time needs actual XMX/compute/occupancy metrics plus external and L3 traffic. Counter unavailability is an unavailable result, not a reason to call logical bytes “DRAM bytes.” Never use `Q_l+H_l` divided by advertised bandwidth as an achieved bandwidth or floor; never substitute an INT8 TOPS number for FP16 GEMM throughput. Preserve quiet endpoints around instrumented samples and do not use profiled time for product-level speed claims if instrumentation moves it materially. R146's minimum warmup/repetition, fixed random order, correctness-first, completion-gated process, and serialized GPU-work guidance remain applicable.

No hardware documentation was added in this round; R146 already cites primary Intel oneAPI/Vtune timing and counter docs. No local metric availability, cache size, clock, bandwidth, FP16 peak, current per-layer quant census, active-expert union or CPU share was queried or established here.

## Interpretation and remaining evidence

The source supports two competing effects: fewer chunks reduce per-call overhead and repeat whole native dense matrix dequantization; fewer/larger chunks also change route union/compact grouping, tail utilization and QSA selector batches. Expert useful GEMM FLOPs and ordinary dense projection activation FLOPs remain row-conserving when the route and offload split are the same. Expert full-weight dequant work is chunk-sensitive because whole expert matrices decode once for each active GPU expert in each chunk. Therefore a blanket “T8192 does 33% fewer FLOPs” or “same bytes” statement is incorrect.

A quantitative result still needs (a) actual per-layer weight types/shapes, (b) closed route/residency/CPU-share histogram, (c) exact accepted backend counters, and (d) supported device memory/cache/compute metrics. The full context and quality gates in R148 remain separate. This report does not read or qualify the main agent's ongoing run and makes no capacity, speed, or ability conclusion.
