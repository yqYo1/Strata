# R236 — PleReader record-coalescing eligibility and context contract

Status: source and prior-art audit only; no implementation, build, test, benchmark, process/device query, cleanup, or Git mutation performed. Source is the frozen Strata worktree at commit `495369cf4dc6e6da564095a1c26504dd3694e3f2`; storage evidence is the frozen results worktree at commit `7ea2650ba3ae1b15807a32a67b62d56131046569`.

## Finding

A 128 KiB record read is a plausible opt-in experiment only for batches that demonstrably place multiple uncached 4 KiB pages in the same 128 KiB file record. It is not a safe default for random PLE rows. The 32 KiB prompt batch has 524,288 row requests (32,768 tokens × 16 PLE heads); if those rows were uniform over the IQ4_NL shard, a rough occupancy model predicts touching about 90% of its ~219,727 records. Reading one complete record for each touched record would therefore transfer roughly 26 GB to serve at most 45 MiB of raw requested rows. This estimate is a hypothesis from uniform sampling, not a measurement; routing correlation, row-cache hits, duplicate rows/pages, and actual selector distributions can change it substantially. The existing storage control establishes that direct-DMU counters charge 131,072 bytes for each 4 KiB application read on the tested ZFS dataset, but does not establish the PleReader workload’s page/record occupancy or its best batch size.

Eligibility should be decided from the actual pending set after row-cache lookup and page deduplication, grouped by the verified file-record geometry. For each record, compare its useful distinct pages/bytes against the record bytes and issue it only when the measured expected reduction in reads/latency justifies the extra returned bytes and buffer cost. Preserve the existing page-read path for sparse records, unknown record size, mmap/Windows, any unsupported format, and all out-of-range rows. Do not infer filesystem record size from the PLE format or the read alignment. The 128 KiB size is specific to the measured dataset.

For this ZFS control, the direct-DMU byte counter charged 128 KiB per 4 KiB request. Therefore a record group with one distinct requested page has no demonstrated DMU-byte saving from full-record coalescing and returns 128 KiB instead of 4 KiB at the application boundary. Two or more requested pages in one record are the minimum theoretical eligibility for reducing direct-DMU request bytes (from at least 256 KiB to about 128 KiB), but still return more application bytes than the pages themselves; eligibility must be based on the matched PLE outcome, not just this counter arithmetic.

## Existing contracts and geometry

- `PleReader::issue` increments request counts, zero-fills rows outside `n_rows`, checks the bounded row cache, computes `at = table_offset + row * row_bytes`, aligns reads down to 4096 bytes, extends a read to 8192 bytes for a page-straddling row, deduplicates by first page offset, and sorts jobs by offset. Jobs retain a fan-out list of `Use(row, in_page, dst)`; completion checks short reads, copies each row, and inserts it into RowCache. A coalescer must preserve these results, including duplicate rows, page-straddlers, out-of-range zeros, error behavior, and per-row cache insertion. The current sort is page ordering only; it does not coalesce adjacent pages or records.
- DirectFile requires offset, length, and buffer address multiples of 4096. Existing slot buffers are two pages per `max_inflight` slot (default 256, about 2 MiB); a naïve 128 KiB-per-slot design would be about 32 MiB at that default. Existing cap `max_inflight <= 1024` means that design could reach 128 MiB. The row cache defaults to 1,048,576 rows; at 90 bytes per IQ4_NL row its data alone is 90 MiB, in addition to row keys and set metadata.
- The shard measurement records a 192-byte table offset, 28,800,138,240-byte table, 90-byte IQ4_NL rows, 4096-byte direct-I/O alignment and 131,072-byte ZFS records. Thus one record spans 32 pages and about 1,456.36 rows; the table starts inside the first record, and row starts drift through page boundaries. A record implementation must clip/alignment-check at EOF, preserve straddlers, and not assume each row or page begins at a record boundary.
- Current direct `gather_batch` allocates a raw staging vector of `n_tokens * 16 * row_bytes` before issuing one ticket. At 32,768 tokens this is 47,185,920 bytes (45 MiB); at 262,144 context tokens in one batch it is 377,487,360 bytes (360 MiB). Prompt prefill normally runs chunks bounded by `m.T` (configured up to 32,768), and double-buffers gather work. Full context is therefore safe only if the coalescer remains chunk-bounded and never allocates a context-wide record staging area or record-index map. Keep the existing `m.T` chunk boundary and account for both buffers if changing storage ownership.
- The same uniform-random approximation at 262,144 tokens gives ~4,194,304 row requests, >99.999% record occupancy, and near-whole-table record traffic (~28.8 GB). Do not batch the full context into records. Actual chunks can still have a high record count, so bound live record buffers independently of the full group-index list (or use a streaming/partitioned strategy) and state the maximum. An uncapped full group vector is not an acceptable design merely because input is chunked.

## Proposed finite candidate and discriminating validation

Candidate only: an opt-in `PleReader` Direct mode behind a verified record-size capability and an explicit per-chunk byte budget. After cache lookup and 4 KiB page dedup, sort/group requested pages by `floor(file_offset / record_bytes)`. For each group, issue an aligned record read only when the group crosses a predeclared density/usefulness threshold; scatter just the requested rows through the existing `Use` destinations and cache insertion path. Keep page reads for the remainder. Bound record buffers to 16 concurrent slots (2 MiB at 128 KiB each), so this path does not silently scale with the legacy 256-slot setting; bound pending descriptors as well, and reject/fall back before exceeding a documented per-chunk metadata cap. This is a candidate contract, not an implementation recommendation to ship.

One matched validation: at the existing 32,768-token full PLE gather, alternate baseline and candidate within the same fresh model/storage session and identical token/row input; repeat enough paired arms to report each sample, order, cache state, row-cache hits, deduplicated pages, distinct records, bytes returned by reader, read count/latency, gather wall/critical-path wait, and end-to-end prefill time. Assert output parity bit-for-bit and verify all rows (including crafted out-of-range, duplicate, page-straddling and record-boundary cases) against the existing reader contract before timing. Keep the candidate disabled unless it cuts measured reader bytes/time without a material prefill regression, stays within its fixed buffer/descriptor budget, and repeats across paired arms. Test full 262,144-token context only after the 32K result, using normal chunks and recording peak staging/metadata allocation; no context-sized aggregation.
