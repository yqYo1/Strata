## Receipt-supported findings

The summary reports `passed=true`, `complete=true`, `active=false`, 147 individual sample rows, seven GU/Down type pairs, three fresh timing processes, and seven timed samples per pair per process. The hardware recorded is Ryzen 5 5600X, 128 GB system RAM and Intel Arc B570. All runs preserve the prior safety settings: forced Level Zero v2 adapter, copy offload disabled, direct submission disabled, and Level Zero GPU selection. The compiler policy is IntelLLVM precise, AOT target `bmg-g21`, default subgroup 32. This receipt is for a standalone probe built with wrapper optimization O2, whereas the production engine uses O3; it is not a production-build speed result or an optimization ceiling.

The measured medians are host submit-through-completion wall time normalized per expert. The process-median ranges are across the three fresh processes. The timer submits a batch of 32 distinct actual expert blobs, calls one GU and one Down wrapper per blob, then includes one terminal queue wait. Parsing, host-to-device staging, warmup/JIT, oracle checks and readbacks are outside the timed sample. Inputs are device-resident; cold cache state is not established. The wrappers return void and profiling markers are disabled, so these rates combine host submission and completion; no exclusive kernel service duration is present. The 20–26 µs/expert median submit component in the summary is part of, not additional to, the wall time. Treating the logical byte rate as physical DRAM throughput, or as a measured bandwidth ceiling, would be unsupported.

The selected data are real blobs from the current IQ3_S pack, not generated stand-ins. The records identify the GGUF shard as 54,817,524,224 bytes and `native_experts.txt` as 3,304 bytes, with unchanged file stats during the run. One qualification expert is selected for each of the seven pairs; each timing pair selects 32 distinct experts. The pair records include tensor names, offsets, byte lengths and payload fingerprints. This establishes representative actual-pack generic dequant inputs, not coverage of all 512 experts, actual expert routing, the production kernel route, or a request's copy/row behavior.

The comparison counts reconcile exactly. The separate qualifier compared 4,915,200 output half values per pair across seven pairs: 34,406,400 half values total, plus 48 device conversion edges. For each timing process and pair, `values_compared_all_selected` is 157,286,400 (= 32 experts × 4,915,200 halves), and `values_compared_timed_end_slots` is 68,812,800 (= 14 end-slot occupants × 4,915,200). These are 226,099,200 checked half values per pair/process; × 7 pairs × 3 processes = the summary's 4,748,083,200. The timed-end check covers the two reusable output slots at the end of each of seven samples. Intermediate outputs overwritten in those slots are not individually read back; they are covered by the all-selected gate only where that gate applies. Every allocated source/output guard is checked. All these checks/readbacks are outside the timed interval. Thus “4.748B checks” is supported as element comparisons, not 4.748B independent experts or timed outputs.

The original cached GGML half-conversion reference failed an overflow-domain CPU test. The archived repair rebuilds exact unchanged GGML sources into a precise/no-contraction CPU reference; its qualification used 99,615 non-NaN binary32 bit patterns, 24 literals and 12 output/canary fault injections. Do not describe the random set as finite-only: non-NaN can include infinities. The effective CPU library hashes and precise reference library are in the timing records. The independent reference passes the actual selected GPU output bits, and host GGML versus independent conversion edges pass. This qualifies a diagnostic oracle for the selected domain; it does not change the production engine math, establish all possible input-domain behavior, or prove an adopted engine path.

The README and receipts report normal completion for the qualifier and all three timing processes, zero exit codes, empty owned-process sessions, no survivors/errors, complete timing rows, and empty fresh kernel-fault intervals. The qualify process passed its gates; timing runs reference that qualifier. This supports “no fault observed in these closed run intervals,” not a general no-fault guarantee. The retention manifest records closed runs and absent owned processes, says original receipts were not rewritten, and gives a deletion manifest for 151 retired files / 955,207 logical bytes; it explicitly makes no physical-free-space claim.

## Comparability and model-capacity join

This result is useful as a calibrated isolated generic-IQ service cell for the stated B570, compiler/runtime settings, selected actual-pack blobs, batch 32, two output slots, and host-submit-plus-wait timer. It can inform a model-capacity estimate only conditionally. The following join evidence is needed, in order:

1. **Join the production request to this exact work.** For a real inference, record which of these GU/Down types and shapes the selected backend dispatches, expert IDs and bytes, number of active experts per token/batch, rows, and whether this generic wrapper is actually called. Demonstrate the production route is this generic IQ path rather than MMQ, fused, CPU, or another kernel. Until then the measured cell has no direct per-token or per-request multiplier.
2. **Match build and launch context.** Establish the O3 production wrapper's implementation/dispatch identity, compiler/flags and effective subgroup, and compare its timing with this O2 isolated probe under the same device and safe runtime controls. Keep queue/batch size, reuse, wait placement and copy policy aligned. Current samples exclude staging and use a single terminal wait; production may include interleaved work or different synchronization.
3. **Measure the request's actual copies and residency.** Account for H2D/D2H, cache/residency and host staging in the request path. If physical bandwidth is the question, use a documented device counter or independent calibrated measurement. Do not substitute the logical input-plus-output quotient for physical DRAM traffic.
4. **Validate end-to-end under representative load.** Measure production requests across relevant prefill/decode lengths and batch/concurrency conditions, with correctness and failure gates retained. Join selected-expert frequency and per-expert bytes to request rows; report the resulting capacity distribution and uncertainty rather than multiplying one median by nominal experts without a route census.

Until those joins are available, keep the conclusion at isolated generic IQ dequant capacity. The current evidence does not establish current production critical-path share, full-context capacity, request tokens/s, an engine-wide bandwidth limit, or a speedup from changing the kernel. The earlier R255/R256 admission and control limits remain applicable; the R259 CPU-reference correction narrows the oracle issue but does not remove these route/build/measurement gaps.
