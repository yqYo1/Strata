R340 — XeStrata latest doorbell memory-model contract audit
Date: 2026-10-11 (Asia/Tokyo)
Scope: read-only review of public XeStrata commit e32b8b0594095352365db0e140a68d5bf56d8b0f against 39bdadcc, focused on the live GPU/host doorbell. No GPU/runtime query, build, test, source edit, or historical fault attribution was performed.

Finding
The e32 doorbell's system-scope fences are legal SYCL constructs where the device supports system-scope fences, but the current plain volatile load/store handshake is not a portable SYCL host/device synchronization protocol. A fence does not make its adjacent volatile access atomic. The source's protocol has concurrent CPU/GPU reads and writes of the same 32-bit host-USM seq/flag locations; neither the SYCL USM contract nor the Level Zero host allocation contract promises this non-atomic polling handshake. Treat it as unsupported/data-race risk on unqualified backends, not as established portable behavior. The author's B70 test and Xe driver comments are empirical implementation-specific evidence, not a memory-model contract.

Source facts
- src/core/layer.cpp::doorbell_init allocates five distinct host-USM allocations via gpu::alloc_host, maps each using gpu::device_pointer, and zero-initializes them. They contain x_f (float model/input data), ids (int32), weights (float), seq (uint32), and flag (uint32). This is host USM, not shared USM. The payload arrays are written by GPU then read by host callback; their later reads are not concurrent with GPU writes if the ring protocol is respected. That is distinct from the concurrently polled seq/flag words.
- src/kernels/xe/elementwise.cpp: read_host does volatile uint32_t load then system acquire fence; bump_host volatile-loads seq, issues system acq_rel fence, then volatile-stores increment. doorbell_wait repeatedly polls seq and flag in a device kernel. There is no device atomic_ref in the latest code. verify_kernels.cpp::doorbell_visible similarly writes ring through volatile pointer, then release fence, then spins on flag.
- src/core/session.cpp host side polls h_seq through volatile uint32_t*; after running CPU expert work it issues std::atomic_thread_fence(seq_cst), _mm_sfence(), then plain volatile store to h_flag. Another session loop polls seq and calls event_query on each iteration; comments explicitly say this driver call is required to expose mapped writes on that driver. These host-side fences and driver calls are not device/host atomic synchronization.
- src/core/verify.cpp chooses segmented_ = env override or !doorbell_visible(cs_); the functional probe checks if a running kernel sees a host write. It does not query usm_atomic_host_allocations, concurrent atomic access, or system-scope-fence support. Thus it cannot qualify the non-atomic handshake. Segmented verification is an available fallback for this verify path, but the cited session/token doorbell path must separately be routed to a serialized host/device handoff if its contract is not met.
- Latest source comments report no available GPU supports usm_atomic_host_allocations, and report B70 volatile store probe success in 2,000/2,000 trials with 4.9us median vs 11us atomic. Those are source comments/bench reports, not a capability check or portable guarantee.

Contract and consequence
Khronos SYCL 2020 rev. 12 defines usm_host_allocations as device access to host USM; concurrent access and atomic modification is only supported when usm_atomic_host_allocations is also present. The latter explicitly means host and device may concurrently access and atomically modify host USM. It does not say a plain volatile access becomes atomic. SYCL specifies atomic_fence as a way to order loads/stores when paired with synchronization through an atomic object; its host/device interop section requires the same atomic object and C++ fence synchronization rules. Volatile is not such an object. Consequently the code does not establish a happens-before edge by fence alone.
Level Zero's programming guide similarly distinguishes host allocation RW / device atomics from concurrent access and concurrent atomic access. It says the concurrent capability alone gives no coherency or memory-consistency guarantee, while concurrent atomic capability permits host/device atomic access; concurrent accesses without the relevant capability can be undefined behavior. A device/driver anecdote cannot stand in for these capabilities.
The actual atomic_ref<uint32_t, ..., system, global_space> used by older/current local corrected code would also need system-scope support and the host-USM atomic capability for concurrent host/device atomic modification. usm_atomic_host_allocations is about concurrent atomic modification of host USM, not a generic prerequisite for host reading immutable model/payload bytes after synchronization. Avoid conflating the payload case with polling the same mutable control word.

Before running an unsafe optimization
1. Do not treat successful doorbell_visible or volatile/fence B70 measurements as proof of legal concurrent polling. No unqualified device run should be used to validate this protocol.
2. Preferred portable fallback: disable resident GPU spin/CPU overlap unless the selected backend documents and reports required concurrent host/device atomic access and system fence support; use graph/event completion and explicit staged/segmented launches, with host-to-device/device-to-host copies or supported USM synchronization. Extend gating to all paths using the doorbell, not only verify's segmented_ mode.
3. If retaining overlap as a backend-specific optimization, add a capability/contract gate and use one shared atomic object consistently: SYCL atomic_ref on device and a host atomic_ref on the same suitably aligned uint32_t, with supported system scope and usm_atomic_host_allocations; otherwise take fallback. Validate compiler/driver behavior separately. A host atomic fence around non-atomic accesses is insufficient.
4. Keep payload publication ordered by that control atomic (release publication / acquire consumption); if platform requirements exceed SYCL's documented guarantees, encapsulate the path under an explicit backend extension/interoperability contract and test that exact device/driver/compiler tuple.
