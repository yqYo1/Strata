# R336 — 既存界面での固定トークン decode 比較契約

日付: 2026-10-11 (Asia/Tokyo)。読み取り専用のソース監査。Xe は `ce70467423d97497979b05ef604e2bcecac47b2b` (`/home/yayoi/ghq/github.com/MistVVK/XeStrata/.worktree/fix-b570-prefill-publication-20261011/src/program/generate.cpp`)、baseline は WT HEAD `7d0105f2` (`/home/yayoi/ghq/github.com/yqYo1/Strata/.worktree/perf-sycl-decode-pool-phase-timing-v0141-20261009/sycl/src/program/generate.cpp`)。両者の dump と serving protocol は対応箇所がほぼ同じ。GPU、service/process、build/test、Git変更は行っていない。これはソース契約であり runtime 実証ではない。

## 結論

既存の公開CLI/`--serve`だけでは、生成 token 列を一つの持続セッション内で教師強制しながら各 decode 位置の **full target distribution** を収集し、長いprefillを一度だけにする機能は確認できない。`--dump-logits` はfloat32の full-vocabulary rows を書けるが、standalone invocation の静的な prompt/decode 区間用であり、`--serve` の動的な複数 `GEN` request に対応しない。`--logits-stride > 1` は `--max-new 1` とdump pathを要求するが、行を間引くだけでforced-token入力機能ではない。

`--serve` は prompt prefix と session の再利用、SAVE/RESTOREを持つ。しかし `GEN` は要求promptを読み込み、その後 target sampler が出したtokenを進めるAPIであり、次のtokenを指定する引数はない。出力は次の会話状態に含まれ、そこへreference tokenを差し込むとその実出力の後ろに付く。よってこれは教師強制にはならない。SAVE/RESTOREもtoken state保存であって任意位置への置換・分岐APIではない。独立CLIを毎回呼んで prefix を延ばす方法はできても、long prefixを毎回再計算するので要求されたprefill削減にならない。

## 実装契約と位置

- Xe flags: `--dump-logits` / `--logits-stride` parse at `src/program/generate.cpp:1562-1568`; stride guard at `2060-2062`; baseline corresponding locations `sycl/src/program/generate.cpp:1703-1709`, `2322-2324`.
- Dump file is opened once before serve loop (`Xe:4191-4216`; baseline `5290-5311`). Header counts `n_prompt - 1 + max_new` rows, then stride selection reduces written rows. Values are float32, vocabulary-wide (`Xe:9600,10040`; baseline `11969`); no per-request path/flush protocol is described.
- Native pack sets `dump_first = tokens.size()-1`, so its dump rows are generated-position rows only. A `--max-new 1` native invocation can yield the first next-token distribution for its supplied final prompt token; it cannot emit each intermediate prompt row. Non-native prompt logits are a different execution mode and do not establish the corrected native decode path's per-position behavior.
- `--serve` starts its request loop at `Xe:4995` and accepts `GEN <max_new> <id,id,...>` (`4818`, `7271+`). `RESUME n` announces how many existing prompt tokens are reused; `REUSED n` follows prompt reading (`4825-4826`, `7754`, `8259`). These are common-prefix cache/session reuse indicators, not a request to force token n or rewind one generated token.
- SAVE/RESTORE are between-request disk session operations (`Xe:7053-7063`, responses `7193`, `7265`; baseline `9102-9112`, `9239`, `9313`). They persist/restore parked conversation contents; they do not select a decode position or override the next token. They entail session serialization/storage and restore work, so are not lightweight per-token snapshots.
- After a successful request, the serving state advances to `consumed` (`Xe:9064`), while generated output is emitted from the verify loop; the next prompt can reuse matching live prefix. Request sampling (`seed`, penalties, etc.) is parsed per request (`Xe:7278-7328`, resolved at `8119`). This permits deterministic greedy runs, but a request seed does not provide token forcing. SAVE/RESTORE does not add a documented RNG continuation contract.
- `--spec-follow` / `--spec-oracle` are loaded in standalone flow (`Xe:9706-9713`) and substitute/provide speculative continuation inputs; they are not a serve-side per-position teacher-forcing interface and do not provide full target rows at arbitrary reference prefixes. Do not interpret MTP/spec acceptance counts as full-distribution quality metrics.

## What a supported run can honestly measure

1. Existing same-prefix `GEN 64` pair: report greedy generated-text exact match/common-prefix length, EOS/length outcome, per-token or aggregate timing, and the existing speculative draft offered/accepted counts. Current owner's already-recorded pair is 64K context, both `GEN 64` fullpassed, common prefix 5 then diverged; decode 8.855 vs 11.607 (units as recorded by owner), MTP 37/78 vs 40/72. This is ordinary free-running quality/performance evidence; it does not isolate equal reference prefixes after divergence.
2. A standalone native `--dump-logits --max-new 1` can compare one next-token full distribution for an identical exact prompt prefix (provided source/model/config and prompt token IDs match). With a fixed external reference continuation, each subsequent position would require a new call whose supplied prompt includes the longer prefix. Existing native pack batches that prompt anew; this repeats long prefill, so it is only a correctness diagnostic, not a low-prefill decode throughput comparison.
3. If only API logprobs/top-k or token scores are captured, restrict claims to the actual exposed candidates/selected-token score. Top-k overlap, exact top-1, or reference-token rank within returned candidates may be useful limited metrics, but are not KL, full-distribution distance, or a substitute for full-tail mass. The current internal `--dump-logits` is full-vocabulary; no serving export hook was found.

File-size planning: header is two int32s (8 bytes), each full row is `4*n_vocab` bytes. For `V` vocabulary entries, one row costs `4V`; e.g. at V=151,936, 607,744 bytes (0.58 MiB). Sixty-four rows cost 38,895,616 bytes (37.1 MiB); 63 rows cost 38,287,872 bytes (36.5 MiB). This is disk output, not GPU memory, but dumping entails vocabulary readback and I/O and may perturb measured latency. Since serve dump dimensions are initialized from the CLI `o.tokens` before requests, do not rely on a persistent dump path under `--serve`; run-time request lengths do not update that header/selection contract.

## Recommended next decision

For the already-completed equal-prompt free-running comparison, retain current text/common-prefix, decode timing, and acceptance results with the limitation above. To make a true same-reference-prefix decode quality comparison without repeated long prefill, a new narrow serve-side feature is required: accept a reference token for each step (or a token-fed scoring request), append that token to live KV/session state, and optionally emit the target full logits for the preceding position. This is distinct from the already-recorded R322 proposal for a native-pack first/full-distribution follow hook; do not count that earlier proposal as a new finding. Main should decide whether that new implementation is worth its cost; no source change is made here.
