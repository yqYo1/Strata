## Measurement boundary and LP5 scope

The prompt is fresh (RESUME 0, REUSED 0), and the 64K request should report read_n=65536. Prompt reading batches 65,535 positions; the final prompt token is consumed by the first verifier window after prompt_ms ends. Service throughput uses read_n / prompt_ms, so that numerator includes one token whose verifier work falls outside the prompt timer. Preserve the protocol PP rows, DONE, timer values, read count, and host send-to-DONE timing separately. Model loading is outside prompt_ms; request setup, cache refill, session/checkpoint work and prompt work can be inside it. Do not compare PP's cumulative progress timestamps as though they were the service prompt timer.

GEN 64 ckpt=1 logprobs=5 is the existing controller shape. A decode timing sample is eligible only for 64 returned T tokens and DONE ... length; preserve all accepted/offered speculative counts. If either arm stops early, keep its clean prefill timing separately and obtain a prompt/run that reaches 64 tokens before making a decode comparison. Three repetitions must be three fresh runs per arm, not repeated decode in one warmed session.

LP5 reports the selected token and five log-prob alternatives at each emitted token under this protocol. It is useful for first-token/top-five and sequence-local comparisons, but it is not full-vocabulary logit equivalence, state equality, quality, or a standalone correctness proof. Keep LP5 observations separate from the performance score; logprob generation is part of the measured protocol on both arms.
