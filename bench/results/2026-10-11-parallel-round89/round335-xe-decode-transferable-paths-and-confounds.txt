R335 — Xe decode transferability and confounds
Date: 2026-10-11
Scope: read-only source/build/run-evidence audit. No build, test, service, GPU, Git, or source mutation performed.

Decision
The paired R1 sample shows a decode-rate increase worth investigating (8.855 to 11.607 tokens/s, about 1.31x), while prompt rate is effectively unchanged (204.635 to 205.205 tokens/s). It does not establish a Xe CPU-kernel speedup or quality parity: each arm is one 64-token sample, generated IDs diverge after the first five, MTP work differs (37/78 vs 40/72), and both records remain math_equivalence=false, quality=false, full262144=false. LP5 and the reported first LP40 are local diagnostics, not a global quality result.

The strongest narrow candidate already exists in current Strata: opt-in `STRATA_IQ3S_MT1=1`. It selects the AVX2 gathered IQ3_S multi-token gate/up path for one-token groups on AVX2/no-AVX512 CPUs, where default dispatch uses ggml's one-token dot. In the current D source this affects only IQ3_S and requires gather-fast; other formats retain the default threshold. The Xe source broadens the default to all non-IQ2_XXS formats on qualifying CPUs. Its comments cite one-token timings on an i7-14700, not the R1 host, and this policy also changes rounding and can change token choice. This makes it a focused decode-only experiment, not a qualified production default.

Actual comparison and provenance
The baseline D binary receipt is `post-reboot-tuning-20261007/prefill-gemm-only-linked-root-v1/record.json` (executable SHA-256 81375b88f043f6b791bd2fee5df7b512e25b584ad5631e0b915d5ac354db237c; 37,809,128 bytes). It rebuilds only `prefill.cpp.o` in the recorded archive; the caller source is pinned to immutable `prefill-gemm-service-only-v1/prefill.cpp` SHA-256 1cf7e911a555e8611c1368a4d18d4ba81c95027bb8de77f89ad65ac64b05fc3c. The Xe binary receipt is `post-reboot-tuning-20261007/xe-prefill-failclosed-linked-root-v7/record.json` (SHA-256 6685135337d7538903d6b624bfb5b309ccf0a243d5cfd52b3ccd814ba87685e5; 21,141,976 bytes; upstream 0.1.40.2 / Xe 0.1.40.2.1). Its recorded archive comparison likewise replaces only its prior `prefill.cpp.o`; that does not mean the two executables differ only in prefill. The builds have materially different source trees, compiler/link options, SYCL implementation and runtime paths. D's recorded link uses oneAPI icpx 2026.1 with `-fsycl`, `-cl-fp32-correctly-rounded-divide-sqrt`, per-kernel device code split and sequential MKL. Xe's uses `-foffload-fp32-prec-div`, `-foffload-fp32-prec-sqrt`, SPIR-V integer-dot extension and `-lonemath`. Therefore the R1 pair is not a single-variable decode comparison.

The Xe-specific CPU threshold is at `XeStrata/src/kernels/cpu/native_expert.cpp:94-112`; one-token dispatch is implemented in `native_gu_rows` immediately below. Current D's narrower opt-in is at `Strata/src/kernels/cpu/native_expert.cpp:106-119`. The Xe rule defaults to minimum group size 1 for non-IQ2_XXS on AVX2 without AVX-512 unless `STRATA_IQ_MT_MIN` explicitly overrides it. Current D defaults to 2 and permits only IQ3_S via `STRATA_IQ3S_MT1`, with AVX2, no AVX-512, no `STRATA_NO_IQ256`, and gather-fast guards. Both implementations explain that the one-token choice changes rounding; MTP group size can therefore change outputs even when the same prompt is supplied.

Other Xe differences are not isolated CPU decode kernels:

- Expert memory: the D run reports a pageable SYCL host arena with queue copies; Xe reports a pinned host-USM arena directly readable by GPU kernels. This changes how expert bytes are resident/accessed and can change CPU memory behavior as well as GPU access. No paired counter measures CPU worker time attributable to this distinction. It cannot be credited as a CPU-kernel improvement from R1.
- Cache state: both requested 128 expert-cache slots, but D reports 128 slots / 128 prefilled and Xe 144 / 29 prefilled; measured decode cache hit ratios are 4.6% (2393/50400) and 1.7% (774/46560). KV reads, VRAM hit ratios and host-byte totals also differ (647,004 / 93.21% / 176.9 MiB vs 597,708 / 90.05% / 239.6 MiB). Cache residency and the token/MTP trajectories are confounds. Both requested 32,768 resident cells out of 262,144, with about 3.09 GiB pinned RAM; that is a reservation/capacity, not evidence all context cells were resident.
- Both used five CPU workers, speculative width four and PCIe split fraction zero; Xe logs 18 tasks per phase for five workers plus host. But work actually routed to CPU differs with token routes and MTP windows, and decode cache/KV counts differ. Matching requested settings does not match executed work.
- The linked Xe tree contains extensive source changes beyond native expert dispatch (including queue, mapped-source and decoder paths); binary-size and archive-member receipts are not semantic equivalence evidence. Neither R1 run carries the decode phase timing output needed to separate those paths.

Measurement evidence and limits
D's `sycl/src/program/generate.cpp:10389-10412` gates `STRATA_DECODE_TIMING`; its output around lines 11296-11340 reports verify GPU-reach wait, host planning/queue/job work, CPU expert hits/misses and GU/FF quant/Down phase totals. Xe has its own timing gate at `src/program/generate.cpp:8293-8294`; `--stats` code around lines 10232-10268 reports pool wait/park/drain and request work. These counters are absent from both R1 stderr logs. CPU phase counters are nested with GPU activity and must not be summed as serial latency. Even when collected, these totals do not identify per-layer QSA/KV prefix latency, launch/event gaps, mapped-host traffic, or true worker busy time versus barrier wait.

Validation that would answer the transferable question
1. On the same CPU and production kernel, compare IQ3_S one-token native rows to the ggml oracle for nt=1..4, with representative row ranges and guard/canary checks. Record per-core dispatch, exact or bounded numerical differences, and output/argmax differences. This tests correctness and rounding explicitly; it is not a quality qualification.
2. Use a fixed token sequence (teacher-forced decode or draft disabled) so both arms execute identical tokens, expert routes, and MTP-independent work. Compare current D with `STRATA_IQ3S_MT1` off/on, pin executable/source hashes, argv and relevant environment, and hold actual cache capacity, filled/resident IDs, KV residency and arena mode constant. Alternate at least three fresh runs per arm and collect per-window phase counters. Verify prompt path counters and prompt latency remain unchanged; this flag has no CPU ExpertPool caller in `sycl/src/prefill/prefill.cpp` (which only sets the nonresident share), so the expected scope is decode.
3. Separately test free-running generation for output/quality and full-context qualification. Do not infer it from fixed-token speed, LP5, or a 64-token sample. Keep exact-output changes as an explicit decision criterion because the dispatch changes rounding.

Until these controls are available, the evidence supports testing the existing narrow IQ3_S opt-in on the target CPU; it does not support porting Xe's blanket all-i-quant policy or attributing the observed 1.31x to CPU dispatch alone.
