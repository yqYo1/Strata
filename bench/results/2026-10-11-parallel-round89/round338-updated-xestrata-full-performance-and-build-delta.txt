R338 — XeStrata latest-tip performance/build delta
Date: 2026-10-11
Scope: read-only full compare of pristine XeStrata evaluation commit 39bdadcc9e2b89b1e3c8be7bb2a603b04fa0e197 through main e32b8b0594095352365db0e140a68d5bf56d8b0f (40 commits). Performance, architecture, CPU/SYCL kernels, capacity/target flags, build/runtime dependencies, and relevance to official Strata v0.1.42. No build, test, GPU, process, service, or Git mutation was done. R339 separately owns publication/stager caller safety review.

Decision and score by phase
- Decode / verify-window work: one narrow kernel change has a measured B70 microbenchmark signal: doorbell store publication changes from system-scope atomic to volatile store with system fence. The standalone probe reports ring visibility in 2,000/2,000 direct runs, median 11.0 us for atomic vs 4.9 us for the fence+store mode; for graph replay 7.4 vs 6.5 us. This supports a small handoff-latency candidate, not a 1.3x decode-token throughput claim. The production helper increments the counter (read, fence, write), so the standalone probe's exact mode is not an exact measurement of the production helper. No end-to-end decode comparison for tip e32b8 is included.
- Prefill GEMM throughput: no GEMM arithmetic/kernel implementation was added in this range. `src/prefill/gemm.cpp` changes the reported path string to name oneMath's actual backend and XeStrata's own kernel path. `src/kernels/xe/xmx_gemm.cpp` changes a diagnostic message and removes duplicate fallback-path logging. Do not score these as prefill speedups.
- Serve short-prompt latency: the new `ShortReadCost` in `src/program/generate.cpp` estimates verify-window cost per token and batched prompt fixed-plus-per-token cost from recent reads, then chooses a path for fresh short text parts. This is a prompt-serving policy that runs those short parts through verify/decode windows; it can reduce short-turn latency if its estimate is right. It does not accelerate the batched long-prefill kernel and must be measured separately from prefill tokens/s and normal output tokens/s. Explicit `--short-read` remains a fixed override; the learned choice is only for the default in `--serve`. Probe/warmup samples are intentionally excluded and history is bounded to 16 samples.
- Native CPU decode: this full delta contains no `src/kernels/cpu/native_expert.cpp`, `iq_avx2.cpp`, or `iq_avx2_rows.inl` changes. The broad AVX2/no-AVX512 one-token multi-token dispatch discussed in R293 was already in the pristine evaluation source, not a new feature of the current update. There is no new CPU-kernel speedup to import from this commit range.
- Capacity/admission: no GPU or host allocation-capacity calculation, B570 memory admission, or model-fit policy change appears in the inference source delta. The added CPU-pool `check_multi_jobs` and Q2_0 calibration ActQ setup are failure/correctness checks, not a capacity increase or optimization.

Delta details that affect interpretation
The doorbell change is in `src/kernels/xe/elementwise.cpp` (`doorbell_ring` and `doorbell_publish`) and `src/kernels/xe/verify_kernels.cpp` (`doorbell_visible`). The rationale is the Xe driver's handling of system-memory atomics on discrete GPUs without reported host-USM atomic support, including an Arc B60 atomic page-fault report. The B70 probe does not reproduce that B60 fault; the README explicitly calls B60 behavior unverified. On B70, volatile-store modes were visible during both direct and graph kernel execution. The UHD 770 could not observe the host writes while its spin kernel ran and was reset; XeStrata already uses segmented windows on that device. Thus treat this as B-series doorbell ordering/latency work with a hardware-specific fallback, not a portable speedup.

The other functional performance change is `ShortReadCost` plus instrumentation in `src/program/generate.cpp`. It learns the crossover for fresh text parts from prior window and batched reads. A batch includes slot lending and refill in its timing; verify-window time is normalized by token count. The default explores windows only under a 100 ms estimate until it has three usable observations of each path, and then compares a median window cost against a least-squares batched cost. It is opt-in only by being the default server policy; explicit `--short-read N` retains user control. Its value depends on request-shape mix and cache state, so don't fold it into normal model prefill or decode scores.

`--hw-bench` and `--kernel-bench` are new setup diagnostics in `src/program/generate.cpp` / `tools/bench.py`. They report RAM, pinned/pageable copy, SSD, dense BF16 and grouped expert-matrix times. The kernel test uses synthetic matrices of pack shapes, warm-up plus 10 timings; it can classify device kernel capability but does not measure a real prompt, dequant/layout costs or end-to-end speed. It is useful as a diagnostic, not a user-facing performance qualification.

Build, B570 target, and dependency delta
The declared engine base remains `STRATA_UPSTREAM_VERSION=0.1.40.2` and `STRATA_UPSTREAM_COMMIT=e8ca9af` in latest `CMakeLists.txt`; only `XESTRATA_REVISION` advances 2→3, which the file's naming rule maps to XeStrata 0.1.40.2.2 (package revision 3). The B570 offload architecture selection itself is not changed in this range. The new `-fsycl-max-parallel-link-jobs=<logical core count>` is a build-time device-link throughput control, not a runtime kernel flag; it may increase concurrent link memory pressure and needs a package-build check before adopting in another build environment.

The oneMath dependency changes from fork tag `xestrata-2` to `xestrata-3`, SHA-256 `9a5203102002e5e85f1ad4a8b91b9f6134365f016bba1a430b038df95517e61d`; CMake says this incorporates oneMath develop through 1308c5e. CMake now applies CUDA/ROCm compile/link flags directly to the cuBLAS/rocBLAS backend targets instead of directory-wide options, and identifies those backend targets conditionally. This avoids sending those target flags to unrelated oneMath objects. It can affect contrib CUDA/AMD builds but does not alter B570's Intel device kernel path. The Intel LLVM builder adds `lld`, disables LLVM assertions and uses lld; package builds enable a per-distro ccache with a default 30 GiB cap. These shorten/reuse build work; they are not engine runtime dependencies added to the installed package except whatever compiler/runtime bundle the existing package already carries.

The release evidence committed in this compare is for XeStrata xe0.1.40.2.1 commit 94287ef0 against upstream v0.1.41, not for tip e32b8. It reports two alternating fresh-process runs per tier on B70, RTX 4070 and RX 9060 XT, 256 generated tokens, each engine's own text and shipped expert profile. On B70 it reports Xe 74.3–82.8 output tok/s vs upstream 28.7–40.6 and Xe 1,501–2,310 prompt tok/s at 4K–32K vs upstream 732–735. These are published comparison results for that older release and full engine differences; the README notes output rate includes each engine's own drafting/text and shows notable Xe run variance (B70 64K 79.6 vs 69.1). They are neither a causal measurement of the latest delta nor a v0.1.42 comparison.

Relationship to official v0.1.42
Official Strata v0.1.42 is commit 61b3fb5dd3f1e8ec09cf7e4e05208bc6d3c46406 (per R333), whereas XeStrata tip still declares its upstream base as 0.1.40.2/e8ca9af. The Xe update is therefore not an integration of official v0.1.42. R333's official v0.1.41→v0.1.42 audit identifies relevant SYCL changes including high-offset oneMKL operand staging/scratch lifetime, memory/capacity accounting fixes, and source/queue updates; B570 applicability must be judged individually because some official changes are A770-only and don't transfer to BMG. Refresh the upstream baseline and source contracts before using this Xe release matrix to score current Strata. Do not bulk-merge either branch based on the Xe release table.

Recommended evaluation / apply boundaries
1. Decode: if evaluating the doorbell optimization, compare old/new handoff in a decode-only or verify-window microbenchmark on B570, then a fixed-token request with identical routes and captures of phase/handoff timing. Keep the Q2 calibration/pool checks as correctness work and qualify separately. Only use free-running output tests for quality, not as the first perf isolation.
2. Serve short inputs: run fixed request lengths around learned crossover, alternate fixed `--short-read` values with adaptive default, include cold/warm and cache-state controls, and report first-token/request latency separately from batched prefill and generation tok/s. Confirm adaptation warms up as intended and does not regress full prompt reads.
3. Prefill: no direct GEMM patch in this Xe range merits import. Test the official v0.1.42 operand/capacity/lifetime changes against the current B570 source as an independent integration; keep correctness, capacity, and steady-state speed outcomes separate.
4. Build: preserve B570 AOT/device target and test dependency pin/hash plus actual compiler command before incorporating oneMath xestrata-3 or parallel-link options. The release package's non-B570 CUDA/AMD target flags are not evidence about B570.
