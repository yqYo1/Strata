Conclusion
Verifier's segmented fallback is scoped only to Verifier. It does not protect generate's normal session loop or its captured TokenGraph path. The strongest overlap path has a host spin on h_seq while device updates it and host/device exchange h_flag; TokenGraph captures a device spin in the graph itself, so a whole-token graph cannot be safely repaired merely by waiting on its completion event. A low-disruption safe path is available using existing per-layer pre/post graphs: on an unqualified device, run pre, wait for its completion event (or synchronize its stream), then run the CPU pool, enqueue the pool result transfer, and launch post; never poll seq or make GPU wait on flag. Route token-graph requests through that same per-layer path. This removes overlap and costs latency, but avoids the unsynchronized live poll. The existing overlap=false switch alone is insufficient: current implementation still polls seq before it reaches the pool.

Call-path map
1. Doorbell creation and producer: core/layer.cpp::doorbell_init allocates mapped host-USM payloads plus 32-bit seq/flag control words; moe_route writes payload then calls doorbell_ring (or doorbell_publish, depending on publication mode). In e32, elementwise.cpp::bump_host performs volatile seq read, system acq_rel fence, volatile store; the fused publish kernel also emits a fence and calls the same bump helper.
2. Normal generation and graph-per-layer overlap: generate.cpp captures SessionGraphs once. session_capture creates a pre graph per layer containing route/publication and subsequent shared-expert work, plus a post graph per layer. session_loop launches pre[0], then polls s.db->h_seq with a volatile host load while calling event_query, runs CPU pool on h_x_f/ids/weights when the ring appears, copies the miss output, launches post[l], then pre[l+1]. This is the primary active doorbell path. Its events currently support fault/completion observation and driver entry; they do not make the concurrent volatile seq poll atomic.
3. Captured one-launch-per-token path: when token graph eligibility is met, session_capture_token captures all layers in one graph, including a device-side doorbell_wait after each route and before copying y_miss / combining / post. session_run_token launches the whole graph, host-polls h_seq, runs CPU pool, and writes h_flag while the graph spins on that word. This is an even stronger cross-thread, same-location concurrent handshake. The generation branch chooses this path when tgraph.captured; no STRATA_VERIFY_SEGMENTED check is consulted.
4. MTP/speculation: no separate doorbell implementation exists in the MTP component. Main target token evaluation still enters the same generate dispatch above, so MTP does not add a safety gate. Depending on token-graph eligibility it uses the TokenGraph handshake; otherwise it uses session_loop. A draft model using the same generation runtime also reaches the same dispatch. Width, draft acceptance, or MTP restore does not itself serialize this shared host/device protocol.
5. Uncaptured session_token: its per-layer block_layer calls pass db=nullptr and have no CPU pool hook; generate source explicitly refuses --no-capture with CPU experts unless --no-pool. Thus this GPU-only/direct path is not a serialized CPU doorbell fallback for ordinary CPU expert service.
6. Verifier: Verifier::init sets segmented_ from STRATA_VERIFY_SEGMENTED or !doorbell_visible(cs_). Its path has a functional visibility probe and segmented graph/window execution; this is verifier-local. It neither gates the session generation paths nor establishes atomic host-USM capability. The probe measures whether a running kernel sees a host write, not whether concurrent control-word accesses are supported.
7. Other graph replay/measurement helpers: session_replay and session_replay_full enqueue graph work rather than running the pool host loop. A pre graph can still write the ring; these helpers are not a general gate or CPU handoff. Do not mistake a captured graph boundary or graph replay for a host-visible atomic handshake. The relevant interactive paths remain session_loop and session_run_token.

Serialized event-based fallback candidate
- At selection/setup time, if the complete runtime contract is absent, do not capture/use TokenGraph. Use the existing SessionGraphs pre/post pair and an explicit serialized branch in session_loop.
- For each layer: launch pre[l]; wait on a recorded event after pre completion (preferred over spin; stream synchronization is the simpler conservative choice); then read mapped payload and run CPU pool; enqueue the existing y_miss-to-parts transfer and launch post[l]; proceed to pre[l+1]. The event/queue completion API is the host/device sequencing boundary, so there is no need to read h_seq. The pre graph's device store may remain only if the host does not concurrently touch the control word; alternatively capture route with no doorbell and append explicit D2H payload copies after pre. Keep copy directions, lifetimes and error propagation explicit.
- On the TokenGraph selection branch, force this per-layer execution route. A completion event cannot unblock a TokenGraph whose internal device doorbell_wait is awaiting CPU work from later in the same graph. Reusing its graph needs a graph redesign into per-layer pre/post submissions; using SessionGraphs is a smaller structural fallback.
- Do not use current overlap=false as a substitute. It only adds a sync after pool/post and leaves the earlier host seq polling in place.
- Keep Verifier segmented mode independent unless the same per-layer serialized logic is intentionally made common. It already illustrates the performance/correctness tradeoff but does not route session/token paths.

Capability/contract gate needed to keep overlap
For each selected queue device/context and each relevant host allocation, require and record:
- SYCL aspect::usm_host_allocations for host-USM access and aspect::usm_atomic_host_allocations for simultaneous host/device atomic modification of those host-USM control words.
- info::device::atomic_memory_scope_capabilities includes memory_scope::system for device atomic_ref; and atomic_fence_scope_capabilities includes system for fences. Check required memory orders (release/acquire or acq_rel) using device/context atomic order capability queries. Do not assume fence-scope support implies atomic-scope support.
- A single aligned uint32 atomic object and matching host/device atomic operations on that same object. For a SYCL device operation use atomic_ref with system scope; host must use atomic_ref (not plain volatile plus a fence). Capability and object alignment constraints must be met.
- Where relying on the Level Zero backend directly, determine the exact allocation type and query the selected device's host allocation access properties; require concurrent-atomic access for device host-USM allocation concurrent with the host (ZE_MEMORY_ACCESS_CAP_FLAG_CONCURRENT_ATOMIC), in addition to RW. CONCURRENT alone is not coherence/order. Also record driver/runtime/compiler/backend identity and any vendor-documented system-scope contract.
- Validate the actual selected device and allocation (not just adapter family or a separate probe allocation), and fail closed to the serialized path when any required item is absent/unknown. doorbell_visible is not one of these capability checks.
