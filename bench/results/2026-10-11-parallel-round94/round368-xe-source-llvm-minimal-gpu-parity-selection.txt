## What these tests do not cover: dense GEMM needs a separate correctness hook

The current tree has no CTest/no-model parity test for `strata::prefill::Gemm::bf16`/`Gemm::f16` comparing the full dense product to a CPU reference across free-own versus contrib-oneMath. `--kernel-bench` exists (`generate.cpp`, `Gemm::path`, and `tools/bench.py`) but it is a **timing-only** synthetic exercise: dense BF16 `T=4096, N=4K, K=K` uses repeated `0x3c` data; it does not compare output to a reference, and `bench_us` ignores the return value of `gpu::stream_sync`. Do not count it as first-run correctness or as proof every submitted product completed successfully. `Gemm::prepare()` does separately trial oneMath FP16 and BF16 on a 16×16 product using `q.wait_and_throw`, catches BF16 fallback, then `Gemm::path()` reports the resulting backend; that does not parity-check the actual dense product output.

The arms are source-distinct only when their configuration and runtime path are recorded:

- Free CMake licence forces `STRATA_ONEMKL=OFF`; dense BF16 goes to XeStrata's own `Gemm` kernels (XMX/joint_matrix or DP4a as effective path allows). `Gemm::path()` and `KB dense-bf16 ...` say the actual path.
- Contrib-llvm's `STRATA_ONEMKL=auto` enables oneMKL if Intel GPU PCI devices are found at configure; explicit `STRATA_ONEMKL=ON` is the supported deterministic build choice, but inspect existing build cache rather than reconfiguring. At runtime the FP16/BF16 trials can reject/fallback; oneMath is not guaranteed merely by a contrib label. Require the runtime `Gemm::path()` line to name oneMKL before calling it a oneMath arm.
- On a contrib binary, `STRATA_NO_BLAS=1` is a supported runtime switch forcing own kernels, allowing a later timing-only matched path contrast. `STRATA_NO_XMX=1` disables matrix-engine kernel variants, and `STRATA_NO_BF16_MMA=1` removes BF16 matrix combinations and suppresses oneMath BF16; on contrib these are not all independent backend arms. `tools/bench.py`'s `default/no-xmx/no-bf16-mma` sweep does not by itself prove oneMath vs custom. `STRATA_NO_INT8_MMA=1` suppresses device-reported INT8 matrix combinations; it does not disable all integer GPU work. Keep these env variables unset for the first correctness sequence.
- `--kernel-bench` only submits BF16 dense GEMM plus optional first-native-layer expert MMQ shape (16 experts × 64 rows). If `native_experts.txt` selects a type unsupported by MMQ, it prints `off`/`unsupported-type`; its INT8 expert line is not a generic dense INT8 GEMM. `src/prefill/moe_mmq.cpp`/`iq_mmq.cpp` have a separate route and `STRATA_NO_XMX` is read in IQ-MMQ capability selection. `qsa_prompt_attn_parity` exercises attention on FP16/INT8/Q4 KV, not these dense GEMMs. `bf16_gemv_parity` is GEMV, not GEMM. Therefore do not infer FP16 dense, BF16 dense, INT8 MMQ, attention and KV as one common arm from a CTest pass.

The closest existing no-model specialized attention parity candidate is order 4. It gives old-vs-new output and FP64 checks; its Q4 subcase may be explicitly skipped by source if the path is not supported. The closest current INT8 GEMM/expert parity candidate is the one-format `native_expert_parity --synthetic GU/DOWN` arm after type selection. Neither covers the complete batched prefill producer, staging lifetime, verify graph, CPU-share, or model path. A separate tiny dense-GEMM parity fixture (own path versus oneMath against a CPU BF16 reference, checked queue completion and small bounded inputs) is a missing test; no code may be added in this source-only pass. Until that exists and is selected by Main, use kernel-bench only later as separately labelled diagnostic timing, not validation.

## Refuse these routes for the initial pass

- Do not use the all-GPU CTest suite. `qsa_parity` contains substantial command-graph captures/replays over the indexer/selection path; `elementwise_parity` also tests graph capture. The code's local `stream_sync` checks do not qualify reused Level Zero/native graph executable lifetime under the v7.1.0 pre-release stack. Gate these behind an isolated graph microtest and explicit review.
- Defer `kv_stream_parity`: unlike `kv_q8_parity`, it allocates host-USM K/V pools directly addressed by device kernels. Though the fixture appears to sync between writes and reads, it exercises the host-USM property whose B570 capability is the reason concurrency routes were gated; source-only review should not upgrade it without a separate non-concurrent host-USM qualification.
- Defer `tests/core/expert_cache_per_layer_test`, `native_dense_ple_key_test`, `vmm_test`, `file_expert_source_rotation_test`, context/snapshot tests, `tools/test_full_context_probe`, and real shard tests. Host-only `test_prefill_publication`, `test_commit_transaction`, `test_mtp_completion`, and `test_context_bounds` already belong to CPU validation and do not validate device execution.
- Do not call `strata --serve`, long-prefill, expert stager, decode doorbell, or a real model for this initial test set. Do not invoke VTune/unitrace; the current toolchain/driver graph route is not qualified. No env override can turn a source refusal into a memory-model proof.
