## What the selected implementations do

Both source paths call GDN in the same high-level order and for the same model geometry: whole-chunk projections for `attn_qkv`, `attn_gate`, `ssm_alpha`, and `ssm_beta`; derive gate and beta arrays; causal convolution and q/k normalization; recurrent update/output normalization; `ssm_out` projection. The projection input choices in both are `native_proj` for qkv/gate and output (FP16 activation/result interface), and `bf16_proj` for alpha/beta (BF16 activation path). The operation names, high-level activation types and token row count `T` match in the inspected old/current prefill sources. The old and current GEMM implementations differ; R511 records the row-major versus column-major oneMKL forms and confirms no measured dispatch effect. That remains a possible projection component, not a GDN recurrence finding.

The recurrent state is FP32 and laid out as 128 state rows × 48 value heads × 128 columns per GDN layer in both implementations. Conv history is FP32, 3 × 10,240 channels per GDN layer in both. The normal prefill call processes all `T` rows and commits final recurrent state and the last-three-input convolution tail once per outer prefill chunk. With 48 GDN layers, the recurrent tensor is 3 MiB/layer and history 120 KiB/layer. There is no source evidence here for an old/current state dtype or capacity difference.

**Old recurrence.** For the recorded old stock environment the GDN-specific selectors are absent. Source defaults therefore select the SYCL column-split recurrence with its software pipeline (`STRATA_GDN_PIPELINE` defaults on); the key-head variant is opt-in and remains off, and the serial head variant is selected only by presence of `STRATA_GDN_REC_HEADS`. The selected launch has four column blocks of 32 columns per value head: 48 × 4 = 192 work-groups, each 4 row groups × 32 lanes = 128 work-items with subgroup 32. Each thread keeps 32 FP32 state values in registers. It stages q/k and then preloads the next token's q/k, v, gate and beta in registers while doing the current token update. Shared/local arrays are 128 floats each for q and k plus 4×32 reduction floats (about 1.5 KiB per work-group). It retains the serial time dependence and uses five work-group barriers per token in the source path. It writes an intermediate FP32 output and runs a separate output-normalization kernel after recurrence.

The old gate formula uses `sycl::native::exp` for softplus and beta sigmoid. Recurrence decay uses `sycl::native::exp`. For each convolution output it evaluates a left-associated four-term product sum then SiLU with `sycl::native::exp`. At `T=4096` with no GDN override, the old convolution source selects independent 64-token tiles (64 is `CONV_TILE`) plus an ordered history commit, then a separate q/k normalization kernel. A serial convolution override or short `T<=64` uses the single per-channel token walk instead. The optional fused conv+norm branch is disabled by default.

**Current recurrence.** The current launch is one work-group per value head: 48 groups × 512 work-items, subgroup 32. Each work-item holds 32 FP32 state values in registers. Shared/local arrays are q=128, k=128, reduction=512 and norm partials=16 floats (about 3.1 KiB/group). It loads q/k into local memory for the current token and has a serial `for (t=0; t<T; ++t)` with barriers around those loads, the row-group reductions and output work. It does not software-pipeline the next token. It computes output normalization within this recurrence kernel and stores normalized FP32 plus FP16 output. Current gate and decay use `sycl::exp`/`sycl::log1p`; current beta uses the standard sigmoid helper. Current conv maps one work-item to each token/channel, computes the four taps with explicit `sycl::fma` accumulation and standard `sycl::exp` SiLU, normalizes q/k in the same kernel, then updates history in a subsequent ordered queue operation.

The old recurrence's 192 smaller groups and current 48 larger groups have the same total 24,576 work-items per recurrence launch, and both keep 32 state floats per work-item. They differ in how those work-items are partitioned (four 32-column tiles/head versus all 128 columns/head) and in local-memory footprint, token load schedule, norm fusion, and math functions. The source proves a distinct kernel mapping; it does not prove which mapping is faster on this Arc or whether occupancy/launch/barrier changes explain any whole-model result.

## Compiler and runtime confounds

Old selected C++ commands use `/opt/intel/oneapi/compiler/2026.1/bin/icpx`, `-O3 -std=c++20 -fsycl`, subgroup size 32, per-kernel device code split, `-fp-model=precise`, and sequential oneMKL. The recorded current selected commands use LLVM 7.1.1 / Clang 22, `-O3 -fsycl`, subgroup 32 and `-ffp-contract=off`; current prefill TUs also explicitly use `-fno-fast-math`. The old commands do not contain `-ffp-contract=off` or `-fno-fast-math`; they specify `-fp-model=precise`. These are materially different compiler floating-point contracts and compiler/runtime stacks. Device JIT, emitted instructions, and register allocation were not inspected. The binary/source environment therefore remains confounded with the observed kernel difference.

The recorded old run was stock compact=2/layout=1, 4096 outer chunk, MMQ=0, split off, context 262144, and used its oneAPI 2026.1.1 stack. Current comparison arms are root-native LLVM/Clang and use compact off or on; current compact-on median is 194.2 t/s and compact-off median 187.5 t/s. The old compact2 median is 343.8 t/s (341.5/343.8/347.5). These are complete whole-model observations, not GDN-only timings. They came from one process per arm and do not include critical-path attribution. Compact, attention layout, GEMM, compiler/runtime and surrounding source remain separate confounders; do not report any as the cause of the old/current gap.

## Narrow candidate and next comparison

A concrete separate-kernel experiment is justified by the selected source difference: add an opt-in current-build prefill recurrence variant that uses the old four 32-column blocks/head and one-token-ahead register staging, while preserving current state layout, FP32 arithmetic choices (`sycl::exp`, explicit delta FMA and current norm expression), current FP32 state and output behavior. Keep current recurrence default. First compare these two variants in the same current binary, same queue, same compiler/runtime, identical input tensors, `T` values including tail sizes, and identical output/final-state checks. This isolates mapping plus load-pipeline schedule as a combined candidate; if it wins and correctness holds, split layout and prefetch into separate switches before deciding which part to retain. Do not also change conv/gates, GEMM orientation, projection precision, output normalization, or outer chunk in that comparison.

After that kernel A/B, collect phase-level GDN recurrence timing separately from projections, conv/gates and output projection. If projections dominate, use R511's same-binary orientation A/B over actual qkv/gate/alpha/beta/output shapes. If conv/gates dominate, compare those functions separately under one compiler/runtime while preserving current arithmetic and history commit order. Any adopted change still needs the all-context/tail and restore contracts from R518: token outputs, final FP32 recurrent state, convolution tail, multi-outer-chunk continuation, exact actual context boundary, cancellation/rollback, and checkpoint save/restore. Numerical comparison must allow for old/current math-library and contraction differences as explicit variables; a faster kernel sample alone does not satisfy model quality or lifecycle gates.

No source change, dispatch, performance claim, causality claim, or inference adoption follows from this report.
