R551 — SYCL QSA score grid-stride contract audit
Date: 2026-10-15
Scope: source-level correctness review of the root SYCL QSA score kernel and the proposed opt-in bounded grid-stride mapping. This is not a benchmark or an implementation change.

Decision

The proposed mapping is bijective over valid score blocks if each query gets G = min(active_bound, 4096) work-groups, G is positive, and each group starts at its group residue r and advances by G while b <= the device n_bid. For query qi, group id g maps to qi = g / G and r = g % G. The proposed loop then assigns b = r + kG, k >= 0. Every integer b in [0, n_bid] has exactly one residue r in [0, G), so every valid block is scored once, with no duplicate score stores. This conclusion depends on the device loop bound being n_bid and on not retaining the current `nb >= launched` guard with `launched` redefined as G.

The implementation must preserve the current `active_bound` contract: a positive value is an exclusive upper bound on `n_bid` for every query in the call; `-1` resolves to `blocks`. The proposed `G` is only the number of work-groups per query. The device check must still validate `n >= 0`, `nb == n / 4`, and `nb < active_bound`, then iterate through `nb`. Comparing `nb` with G would reject valid longer contexts whenever G is capped at 4096. In the captured Verifier path, the existing omitted argument resolves to `max_blocks_`, a fixed capacity (`max_cells / idx_block + 2`); this is compatible with replay as the host stages new step values but reuses the graph. The header explicitly says the positive bound is not for a captured graph, so an opt-in captured caller must use a fixed capacity bound rather than a bound derived from the current position. A per-query/per-token launch bound is not an appropriate graph parameter.

Current source and captured inputs

`src/kernels/sycl/qsa_select.cpp` launches `nq * launched` work-groups of 32 work-items. One group owns one `(qi,b)` pair. It reads `n` and `nb` from `steps + qi * kStepCount`; rejects negative n, inconsistent `nb != n / 4`, `nb >= launched`, and `b > nb`; and writes only lane 0 to `scores[qi * blocks + b]`. Query rows use `query + qi * 512`. The pooled row is `pooled + b * 128`, except that the terminal candidate `b == nb` uses `dead`. For a partial final block (`n % 4 != 0`), lane 0 adds the existing `1e9f` bias to that terminal score. The grid-stride loop must enclose the unchanged per-block scoring body and terminal handling, with `b` substituted for the current per-group block id.

`include/strata/kernels/qsa_select.hpp` defines `active_blocks` as the batch's largest `n_bid + 1` and marks that scalar as unsuitable for a captured graph. `Verifier::init` sets `max_blocks_ = max_cells / idx_block + 2`; `record_window` calls score and top-k with the default bound, with each split segment's query, step, and score pointers offset by `tb`. Therefore score rows remain separated by the full `blocks` capacity even though only G groups are launched; using G as the score stride would overlap rows. The new decomposition must retain the segment-relative query and step row mapping and the capacity score stride. `qsa_block_topk` consumes scores with this same full-capacity row stride and uses the per-query `nb` from the device step row.

For SYCL capture, `Verifier::record_window` captures a `copy_i32_from_mapped(step_, m_step_, T * kStepCount, cs)` before the workload. On each `run`, the host rewrites `h_step_` using `qsa_step_fill` before replaying the cached `segments_[T][0]`. The score kernel's stable device `step_` pointer is therefore read at replay with the new row values; no host scalar needs to encode the current `nb`. The grid-stride loop must load/observe `nb` from this device buffer on every invocation. The current SYCL `capture(T)` returns early when that window graph already exists, while `run` stages the new steps before graph launch.

Bounds and ownership obligations

- Preserve `validate`: `1 <= nq <= 65535`, `1 <= blocks <= INT_MAX`, `active == -1` or `1 <= active <= blocks`, and the required QSA geometry. Thus G is in `[1, 4096]` for the proposed cap.
- Keep `b`, `nb`, and group arithmetic in signed 64-bit after widening the device int32 values. With `nb < active <= blocks <= INT_MAX`, `b + G` cannot approach int64 overflow. Do not compute the next b in int32 at the top capacity boundary.
- Check that `nq * G * 32` fits `size_t` and the SYCL global range before constructing `nd_range`; current geometry bounds make the product small in int64, but a 32-bit `size_t` would not hold the maximum product. Continue using checked spans for `scores[nq * blocks]`, `pooled[blocks * 128]`, `query[nq * 512]`, and `steps[nq * kStepCount]`.
- Use a linear work-group id and derive `qi = group_id / G`, `r = group_id % G`. This yields exactly G groups for each query because the global work-group count is `nq * G`. Keep local size 32 and `[[sycl::reqd_sub_group_size(32)]]`; each lane's index remains the local id. The per-block output address remains `qi * blocks + b`, not `qi * G + b`.
- Keep the source's early return for invalid step state and blocks outside `[0, nb]`, but remove only the old comparison against the launch group count. If the existing contract check `nb >= active_bound` is retained, `active_bound` must be the original exclusive candidate bound, not G.
- The loop includes b == nb exactly once. Therefore the dead candidate and the partial-tail bias remain unchanged. Candidates above nb stay unwritten, as today; the top-k reader visits only through nb.

SYCL collective and floating-point review

The current score body calls `sycl::permute_group_by_xor` for offsets 16, 8, 4, 2, and 1. SYCL requires group functions to be encountered by all work-items in converged control flow, and the XOR mask must match for every lane. With one 32-lane group per query-residue pair, every lane reads the same step row, uses the same `b` and loop condition, and has the same fixed `off` at each shuffle. The proposed loop remains converged if it does not add lane-dependent branches around any shuffle; the lane-0 store remains after the collectives. Khronos documents the linear group id on `nd_item`, the convergence requirement for group functions, and the uniform-mask precondition for `permute_group_by_xor` ([`nd_item`](https://github.khronos.org/SYCL_Reference/iface/nd_item.html), [group functions](https://github.khronos.org/SYCL_Reference/iface/group-functions.html), [group algorithms](https://github.khronos.org/SYCL_Reference/iface/group-algorithms-library.html)).

The score body's per-block operation order can be retained: four heads; four multiply/add terms per lane; the same five subgroup exchanges per head; ReLU; then the same tail bias. `cmake/sycl_backend.cmake` applies `-ffp-contract=off` to `strata_kernels`, and Intel documents that this disables fused floating-point operations. This does not by itself establish bitwise equivalence after adding a dynamic outer loop: only a compile and the repository's correctness validation can establish the changed kernel's result. No float-contraction or numerical-equivalence claim is made here.

Work distribution and performance status

For a query with M = nb + 1 valid block ids, residue group r owns `max(0, floor((M - 1 - r) / G) + 1)` blocks. Active residues differ in work count by at most one; residues r >= M have no body iteration. A cap of 4096 therefore changes the number of launched groups per query and can put multiple block scores into each group's sequential loop at large M. This is a mapping fact, not evidence that surplus groups are a measured bottleneck or that the bounded grid is faster. The extra dynamic loop, source reuse, device occupancy, and end-to-end score time remain unmeasured.
