# SYCL async host-pointer lifetime audit — round 541

## Scope and conclusion

This is a source-only audit of host pointers passed through the CUDA-shaped `cudaMemcpyAsync` adapter, scoped to the current canonical single-device SYCL prompt/MTP path (native68, MTP on, split off, short-read 0, same-queue, prefill chunk 4096, no borrow, prefill MMQ off, compact path on). It does not report a run, reproduction, or measured corruption.

The adapter submits `queue(st).memcpy(dst, src, bytes)` and discards the returned SYCL event (`src/sycl/compat.cpp:253-260`). It does not pin or stage ordinary host pointers. On the SYCL contract, the host source/destination must remain valid for the operation; returning from this wrapper is not an established completion edge. CUDA's pageable-memory behavior therefore cannot be assumed for this adapter. This source-level difference is material for one MTP path:

**`Prefill::draft_kv` queues copies from a reusable `std::vector<int32_t> tk` and loop-local stack array `bh`, then overwrites/reuses them on a later batch iteration before its only stream synchronization, which is after the loop (`src/prefill/prefill.cpp:1019-1031,1077-1081`).** This violates the required source-lifetime ordering whenever `n-r0 > B`. The callback reaches this path in the single-device prompt MTP flow (`src/program/generate.cpp:6296-6302`, and serve at 4861-4883); it is disabled only by `STRATA_MTP_BATCH=0` or the explicit eligibility/geometry gates at `prefill.cpp:926-978`. The canonical 4096-token case with the recorded 607,128,320-byte shared region is source-sized for multiple batches by `B = min(n-r0, floor(region_bytes/per_row) rounded down to 64)`; the exact compiled geometry and runtime `B` were not instrumented here. Treat the hazard as source-proven conditional on the loop running more than once, not as observed corruption. The q8 bounds upload has the same lifetime gap when q8 is selected; the token upload is unconditional on this batched route.

The previously questioned prompt token/step arrays and short-read token/history paths do not share this gap in the canonical mode: prompt chunks synchronize before the MTP callback, and the batched draft path synchronizes before returning; short-read is inactive at `--short-read 0`. Other inspected host arrays have an explicit per-use completion edge, are pinned/mapped with an event edge, or belong to an inactive branch. Completion checks still need care: the compatibility runtime's sticky error check can prevent a synchronization body from running after an earlier error, so a checked return alone is not historical proof that a prior transfer drained. No hang or earlier failure is attributed to this lifetime finding.

## Source contract

- `src/sycl/compat.cpp:253-260`: async wrapper validates non-null pointers, submits `queue(st).memcpy`, returns through `attempt`, and retains no event or host staging.
- `src/sycl/compat.cpp:261-269`: synchronous wrapper first calls `wait_all()` and then waits for its copy event.
- `src/sycl/runtime.cpp`: runtime queue construction is in-order; `Runtime::wait` waits the event then checks runtime status. Queue ordering orders device commands, but does not order a later CPU overwrite of a host source against an earlier queued command's read of that source.
- SYCL reference: [handler `memcpy`](https://github.khronos.org/SYCL_Reference/iface/command-group-handler.html), [queue and event behavior](https://github.khronos.org/SYCL_Reference/iface/queue.html). CUDA's documented pageable-memory staging behavior is described separately in the [CUDA Driver API synchronization behavior](https://docs.nvidia.com/cuda/archive/12.1.1/cuda-driver-api/api-sync-behavior.html) and [CUDA Runtime API `cudaMemcpyAsync`](https://docs.nvidia.com/cuda/cuda-runtime-api/group__CUDART__MEMORY.html); those guarantees do not establish behavior for this SYCL wrapper.

## Error/completion caveat

This is a lifetime audit, not an error-handling fix. `attempt` consults sticky runtime status before executing its body, and the reviewed stager-error evidence says an earlier sticky error can cause a later wait/record/copy operation to be skipped. Thus the source ordering above is the intended successful path; it does not turn a returned success status into proof that the underlying queue drained after an earlier error. Prior reviews found no evidence tying that separate behavior to a historical hang. The proposed fail-stop guard remains unapplied and unvalidated; this report neither applies it nor treats it as a fix.
