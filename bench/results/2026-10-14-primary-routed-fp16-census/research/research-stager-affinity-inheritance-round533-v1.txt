## Finding

There is a concrete source-level route for prefill Stager workers to inherit the serving thread's CPU-0-only mask. In the actual `--serve --spec4` route, `loop_scratch.init()` is not called in the earlier SYCL post-handoff branch because that branch requires `o.spec == 0` (`src/program/generate.cpp:3584-3600`). It is then initialized unconditionally at `src/program/generate.cpp:4027`, before the persistent server block and its `init_prompt_paths` calls around lines 4114 and 4472-4535. `SessionLoopScratch::init()` allocates its pinned buffers/events, calls `physical_cores(false)`, and pins its calling thread to the first core returned (`src/core/session.cpp:631-678`). The scratch object retains that pin through the server lifetime and restores it in `free()` (`src/core/session.cpp:680-699`).

Later, `init_prompt_paths()` calls `Prefill::init()` for the primary and any other stages (`src/program/generate.cpp:4484-4491`). `Prefill::init()` creates a `Stager` if absent and launches its worker threads with `std::thread` (`src/prefill/prefill.cpp:729-741`). The default count is `max(2, min(4, hardware_concurrency()/4))`; for the observed logical CPU count of 12 this is three threads. `Stager::work()` does not set CPU affinity. The Stager is owned by the Prefill implementation, and persists between requests until that implementation is released/reset (`src/prefill/prefill.cpp:212-280, 540-558`). Linux `pthread_create(3)` documents that a new thread inherits a copy of its creator's CPU-affinity mask. Thus if the serving caller is restricted to CPU 0 when `Stager::init()` starts those threads, the new Stager workers inherit `{0}`.

This mechanism is supported directly by source and Linux thread semantics. It is not proof that every observed generic `strata` thread is a Stager worker. In the supplied placement receipt, native TID 334431 is observed with affinity `{0}` and processor 0; pool TIDs 335841-335845 have affinities `{1}` through `{5}`; and three later TIDs 336818-336820 have affinity `{0}` with 72.71, 72.88, and 72.79 cumulative CPU seconds. Three matches the default Stager count, and the observed six distinct physical-core IDs 0-5 with sibling IDs 6-11 fit the expected 5600X placement. However, the receipt names all threads `strata`, contains no thread creation stack or role, and its CPU counters span warmup, prefill, and decode. It does not prove those three TIDs' identity, when their CPU time accrued, or their decode contribution. Treat “these are the three Stager workers” as a high-plausibility inference, not a source-proved identity.

## Stager threads versus SYCL queue and pointer behavior

The root Stager workers are ordinary host `std::thread`s. They set the current device, wait on a slot's prior DMA event, copy source bytes into a host staging buffer (or call `copy_blob`), then publish the buffer as ready (`src/prefill/prefill.cpp:245-290`). They do not create a `sycl::queue` or submit the expert H2D copy. The prefill issuer waits for a ready slot, calls `cudaMemcpyAsync` on `m.copy`, and records the slot's completion event with `issued_one()` (`src/prefill/prefill.cpp:2590-2618`). In the configured SYCL source, `m.copy = m.cs` is the in-order compute queue (`src/prefill/prefill.cpp:713-720`). Queue creation and the compatibility adapter's event wait are separate runtime mechanisms (`src/sycl/runtime.cpp:35-53, 78-98`; `src/sycl/compat.cpp:302-318, 364-405`).

This distinguishes the source-level worker-affinity mechanism from pointer or queue policy. CPU affinity controls where the host thread may execute; it says nothing about whether `m.copy` aliases `m.cs`, whether an allocation is host-USM/pinned, or where a SYCL command executes. The source proves the Stager-created host workers share the creator's mask unless explicitly reset; it does not prove the identity or affinity behavior of implementation-internal oneAPI/Level Zero helper threads. The placement receipt's generic names cannot distinguish those internals from application-created threads.

The default Stager count uses `std::thread::hardware_concurrency()`, rather than the calling thread's current allowed CPU set. On this observation it yields three, but under a restricted cpuset it can request more workers than there are allowed physical cores. Also, `physical_cores(false)` derives its allowed CPU set from `sched_getaffinity()` when called. Inside `SessionLoopScratch::init()` this query occurs before the function pins the caller, so it sees the caller's then-current mask. A later call after the pin would see only CPU 0; it must not be used to reconstruct the original topology. Linux `sched_setaffinity(2)` documents both the per-thread nature of affinity and the kernel's intersection with cpuset constraints.

## Minimal remedy ranking

1. **Preferred narrow fix: snapshot the allowed topology before pinning and pass an explicit Stager placement.** Capture the caller's allowed CPU mask and applicable physical/hybrid topology before restricting the serving issuer. Keep the decode issuer pinned to its reserved core. Place Stager workers on a bounded set derived from the saved allowed topology, excluding the issuer core and respecting the process cpuset; use worker count no greater than the available chosen cores. On the observed non-hybrid six-core machine this could keep issuer 0 and assign the three prompt-copy workers to allowed physical cores 1-3, with the CPU expert pool idle during prompt staging. On another machine, derive from its actual allowed/topology data and existing affinity policy rather than assuming IDs or six cores. Pass this saved placement into Stager initialization; do not call `physical_cores()` after pinning and treat its single returned CPU as the original set.

2. **Smaller lifecycle alternative: split scratch allocation from issuer pinning.** Construct the scratch buffers without pinning, initialize all persistent prefill paths/Stagers while the serving caller still has its original allowed mask, then pin the issuer to its reserved core immediately before request processing. This lets Stager threads inherit the original mask and leaves the decode issuer at CPU 0. The pin must still occur before the first decode doorbell loop. Review every serve error/retry path and any helper threads created after the pin; thread creation after that point will inherit the restricted mask unless it supplies an explicit placement.

3. **Temporary restore around Stager creation is less robust.** Temporarily restoring a saved original mask before `Prefill::init()` and re-pinning afterward can make newly created Stager workers inherit the broad allowed set, but all worker/runtime threads created during that call inherit that set, and retries/stage splits complicate restoration. Use only if the code preserves/restores the exact original mask on every return path and a measured reason favors this over explicit worker placement.

In each remedy, preserve cpuset/cgroup limits: the saved affinity is the thread's currently permitted set, not permission to use every CPU present in the machine. For a hybrid CPU, preserve the configured topology policy and the selected issuer core; for restricted masks, handle empty worker sets and a smaller worker count. Do not pin Stager helpers to an assumed “first N CPUs.” No source change or remedy is adopted here.
