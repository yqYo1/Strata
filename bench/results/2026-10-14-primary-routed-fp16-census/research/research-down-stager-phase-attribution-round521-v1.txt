## Why 61.5 s is not exclusive Down service

`PfTimer` in `src/prefill/prefill.cpp:1254-1430` records ordered markers on the compute queue and charges each interval to the phase name attached to its first marker. Its source comment explicitly says a GPU gap while waiting for host expert grouping or an expert copy lands on whichever phase is open. Under the observed `!stream_all` route (`ring=8`, `STAGE=8`; stream-all requires ring greater than 8), `stage_one` can block the issuing thread in `Stager::wait(job)` before it submits the expert H2D copy and following compute commands (`:2593-2618, 2750+`). With the actual same-queue setting, `m.copy=m.cs` (`:713-720`) and `copy_events` is false (`:1486-1492`): host-issued H2D copies, dequant kernels, gather, GU, SwiGLU and Down are all serialized in one in-order queue. A stalled host submitter therefore leaves a queue gap inside the last open interval.

For compact FP16, the expert sequence marks `kPfDequant`, enqueues native GU and Down dequantization, marks/enqueues gather, marks GU, enqueues the GU GEMM and SwiGLU, then marks `kPfGemmD` immediately before the Down GEMM (`:2664-2750`). The `kPfGemmD` interval ends only at the next marker, commonly a wait-copy or next expert's dequant marker. It includes the current Down command plus any queue idle between those markers; because copies are submitted by lookahead before the expert compute, a copy queued before the Down marker can also be drained during an interval whose label is Down. A host wait for a later Stager job can delay submission of the next marker and extend the currently open Down interval. Conversely, current expert H2D/dequant/GU work may fall in preceding wait/dequant/GU intervals. Thus the 61.5 s is a cumulative, marker-delimited queue timeline bucket containing Down work and potentially adjacent copy/host-submit gaps; it cannot be called exclusive Down GEMM time or whole-operation BLAS time. The 32.5 s dequant bucket has the same limitation. The 75.5 s staging accumulator is parallel host work and must not be added to phase times.

The observation does not measure per-copy successful bytes/time, worker `memcpy` versus source-copy service, GPU H2D duration, per-kernel DQ duration, or the dependency chain that reaches the last logit. It therefore does not yet establish whether stager wait, host copy, H2D, dequant, BLAS, or QSA is the critical-path limiter.

## Candidate relevance and invariants

**Private copy queue:** not active in this build. `Prefill::init` explicitly aliases `m.copy=m.cs` in SYCL because the two-queue ring stalled at realistic expert shapes, and the run explicitly sets same-queue override. A private queue would change the observed queue policy and is not a clean explanation of the current interval. It could in principle overlap H2D with compute, but needs a separate controlled experiment after attribution. Preserve both levels of lifetime ordering: device staging-slot reuse waits for the last compute read before the copy queue overwrites the slot; Stager host-buffer reuse waits for `dma_done` after the H2D completes. `issued_one` records that event on the queue after copy submission, then publishes `issued`; workers wait for DMA completion before overwriting the pinned/pageable host buffer (`:286-333, 2606-2618`). A distinct queue also requires an explicit copy-completion dependency before compute dequant reads the blob and before any used-slot release/reuse; the current same-queue ordering/`copy_events=false` shortcut cannot be carried over unchanged. R509 similarly notes a separate skip-side dependency would be required. Do not change the queue or lease protocol based on this report.

**Grouped activation gather:** R517 is an own-fork proposal (not Xe donor code), still unapplied and unmeasured. Its compact FP16 condition matches this run, and the current per-expert `gather_rows16` at `:2735-2741` is actually active. It groups contiguous CSR route rows into spans no larger than allocated `m.T`, gathers each span once, and uses local Xs/GU/Hh row offsets while Down keeps global `m.off[e]` output rows. At T=4096, K=10 there are 40960 route rows, so it needs multiple bounded groups; do not allocate one full `T*K` scratch group into a `T`-row workspace. It preserves each expert's `ne` and GEMM shapes, dequantization, queue policy, host/device staging and slot leases. The in-order queue must order each group gather before its first GU reader and the next gather after prior scratch readers; route-table copy must already precede the gather. Keep checked actual-T/capacity, CSR span and int32 bounds, zero-count skips, non-aliasing, and streamed/non-streamed lease behavior from R517. This is a relevant way to reduce repeated gather launches for many small `ne`, but its possible gain is bounded neither by the 5.27 s gather bucket nor by call percentages; correctness, timing and full-context behavior remain unmeasured.
