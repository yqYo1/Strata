# Closed suite evidence finalizer review — round 557

Date: 2026-10-15 JST. Read-only source audit of the upload-fix suite finalizer and its named callers/schema. No code was changed and no Git operation, script execution/import, test, build, service/process/GPU inspection, profiler, cleanup or live-run artifact inspection was performed. I did not inspect the excluded `B/prefill-gemm-only-contract-root-v1/record.json`, private Codex state, PR6/history, or model/session data.

## Conclusion

The normal terminal-ownership path is conservative: the finalizer requires the recorded runner inactive, every exact command receipt closed, exactly the three expected command labels, and (on the same boot) absence of the recorded PID/start-time identities. `direct_owner.closed()` requires a reaped direct child, observed empty session and no cleanup/errors. `run_server_job.py` also records normal server and real-engine exits, and its result must agree with the runner's engine-exit receipt. I found no source-backed false PASS in those ownership/exit gates.

The request journal has a hash chain, request-start/result identity join, and terminal-state check. The finalizer independently requires 18 complete, stop-finished thinking agent turns, three prompt/32K rows, and three eligible strong and weak long-generation rows with actual-input/output, thinking, body, fresh-prefix, timing and draft-count/rate conditions. It cross-checks the long-generation suite rows against the journal. Its deterministic gzip (`mtime=0`) and create-only byte comparison make a repeat on the same inputs idempotent.

I found two concrete evidence-gate defects that can allow a false qualification if saved artifacts differ from the runner's original receipts. One also permits a below-threshold prompt to be labeled nominal 32K. See findings below. These are source-level integrity/gate defects, not claims that the current run artifacts were changed or that either condition occurred.

## Findings

### 1. Finalizer does not bind consumed result files to the runner's recorded hashes

`check_extended_upload_fix.py` records `benchmark_result_sha256` and, for the request journal, its SHA-256, byte count, verification result and saved journal state (`check_extended_upload_fix.py:120-138`). The finalizer reads the current `result.json`, `results.json` and `requests.jsonl`, verifies the journal's internal chain, then archives those current bytes (`finalize_upload_fix_suite.py:75-90, 167-180`). It never compares the current suite hash to `record['benchmark_result_sha256']`, the current journal hash/size/state to `record['request_journals'][0]`, or the current `result.json` to the runner's saved `record['result']`.

Therefore a post-run replacement of `results.json` and journal with a self-consistent qualifying sample set can pass all fresh recomputed gates while the preserved runner receipt still describes different benchmark evidence. The hash chain only proves internal consistency; it is not an anchor to the receipt created at run closure. This is a concrete false-PASS path for artifact substitution/corruption and weakens the intended immutable-original-status/evidence boundary.

**Fix:** before interpreting or archiving, require the unique suite file's SHA-256 to equal `record['benchmark_result_sha256']`; require the journal relative path, SHA-256, byte count, verification and state to equal the single saved `record['request_journals']` entry; and require `result.json` to match the saved `record['result']` (or record and verify its hash at collection). Refuse on any mismatch. Keep original status fields immutable.

### 2. “nominal_32k_complete” does not enforce actual prompt usage

The `prompt_complete` gate checks three runs, thinking, `ok`, `stream_complete`, positive engine `prompt_tps`, and its source, but never checks `sample.prompt_tokens` (`finalize_upload_fix_suite.py:109-113`). `digest()` exposes actual `usage.prompt_tokens` as `prompt_tokens`, and marks a sample `ok` only with positive usage and terminal stream completion (`tools/strata_bench.py:206-239`). The prompt generator targets approximately 32,768 tokens; calibration is explicitly approximate (`tools/strata_bench.py:487-489`), while the long-generation eligibility gate correctly checks actual usage against 32,768 (`tools/long_generation_bench.py:45-58`).

A complete prompt request with positive engine timing but actual usage below 32,768 can therefore set `nominal_32k_complete=true`. This is a false PASS for the stated nominal 32K evidence gate, even though the run remains a completed prompt measurement.

**Fix:** require `type(sample['prompt_tokens']) is int and sample['prompt_tokens'] >= 32768` for each nominal-32K row (and keep the actual value in the summary). If a different tolerance is intended, encode and name that threshold explicitly rather than qualifying an arbitrary under-target prompt.

## Other gate observations

- Long-generation's finalizer check requires three unique runs in each band, `thinking is True`, `ok`, complete stream, stop/length finish, `eligible`, actual `prompt_tokens >= 32768`, 1,024–16,384 generated tokens, 512 answer-body characters, zero reused tokens, positive engine decode rate/time, at least 256 offers, valid accepted/offered counts, exact recomputed rate and per-run strong/weak thresholds (`finalize_upload_fix_suite.py:114-132`). `sample_eligibility()` itself derives eligibility from actual usage, body, fresh-prefix, timing and counts (`tools/long_generation_bench.py:45-75`). No missing 3-run gate was found.
- Agent turns require all 18 run/turn pairs, thinking, normal stop, stream completion, positive generated-token count and nonempty answer body (`finalize_upload_fix_suite.py:102-108`). `digest()` requires positive actual completion and prompt usage before `ok` is true. This is stricter than the previously noted generic agent benchmark helper; it avoids counting a capped `length` turn as complete.
- Journal validation allows an `interrupted` terminal row to close a pending item, but the finalizer's required per-phase result counts and completion gates prevent such a row from substituting for required samples. The suite's own completion state is separately required.
- The finalizer writes an archive before computing whether every protocol gate passes. It preserves the original receipt/status and emits `benchmark_protocol_qualified=false` when a gate fails; this is conservative evidence retention, not a false PASS.
- After a reboot, `boot_still_unchanged` changes to false and same-boot live identity scans are skipped. If an identical archive already exists, a repeated finalization can then reach `write_new()` with a different final summary and refuse because overwriting is forbidden. This is a conservative refusal after the original-boot evidence is unavailable, but it means retries across a reboot are not idempotent. If cross-boot retries are required, return the already verified archived summary unchanged instead of recomputing a changed qualification record.
