# R534 — Stager worker parallelism and runtime lifetime contract

Date: 2026-10-14 JST. Read-only review of the Stager and SYCL runtime adapter. Sole write: this report. No product or Git change, test/build, GPU/profiler work, process/service operation, cleanup, or inspection of the active run itself occurred; only the specifically shared thread-placement artifact was read. The excluded prefill-GEMM-only record and private session state were not accessed. Main owns the active run; this report requests no intervention.

## Finding

The Stager is already a multiworker design. Its normal successful-path ownership chain appears structured to permit workers to copy different expert blobs concurrently: workers claim distinct job indices, write different host-ring slots, publish `ready[j]` with release semantics, and the single consumer/issuer waits with acquire semantics before queuing each H2D copy. A per-slot SYCL-compatible event then prevents a worker from overwriting that host slot while its previous H2D is pending. Widening the workers' CPU affinity alone does not change those C++ ownership edges.

I found no source evidence that the ordinary successful path requires all workers to run serially on CPU 0. I did find two contracts that should be made explicit before treating the affinity change as fully cleared:

- Several CUDA-compatibility return values in the worker/issuer path are ignored. In particular, a failed `cudaEventSynchronize` or `cudaEventRecord` does not become a failed job state. On an already-failed SYCL runtime or queue, the worker may proceed to reuse a buffer without a successful completion result. This is a pre-existing error-path hole, not evidence of a normal-path race caused by parallel execution.
- The direct `Job::src` path depends on a stable source pointer after job-plan construction. The general `ExpertSource::blob` interface promises only a short lifetime unless the source provides a stable cache; short-lived sources must set `transient` and be copied with `copy_blob`. The current `FileExpertSource` transient route uses its thread-safe direct-copy override, but the contract should remain enforced for any other source implementation.

These findings do not show a runtime fault, a successful throughput improvement, or that the active process exercised this precise source mode.

## Worker job and generation ownership

The core is `Stager` at `prefill.cpp:212–338`.

- `start` moves the complete jobs vector under `mu`, sizes/replaces `ready` only after the preceding Stager generation has been finished by the caller, clears each used ready flag, resets `issued`, increments `gen`, and publishes the packed generation/count/head through a release store (`308–320`). A worker wakes while holding the same mutex, then claims from `head`; its CAS uses acquire ordering (`266–305`). A job cannot be claimed from a stale generation.
- Each worker increments `active` before trying to claim and decrements after either an empty claim or after copy completion (`277–295`). `finish` closes the current generation to new claims, raises the issue watermark so already-claimed ring-waiting jobs cannot remain blocked, and waits until active workers return (`332–337`). This accounts for a worker between entering the loop and attempting its claim.
- A worker chooses slot `b = j % kRing`. For `j >= kRing`, it waits until the single issuer has passed `j-kRing`, then synchronizes `dma_done[b]` before writing the slot. It copies either from a stable `Job::src` or calls `Job::from->copy_blob(l,e,buf[b])`; only after the host bytes are complete does it release-store `ready[j]=1` (`280–295`). The consumer acquire-loads `ready[j]` before reading that slot (`322–325`).
- `issued_one(j, copy)` records `dma_done[j % kRing]` after the queued host-to-device copy, then release-stores `issued=j+1` (`327–330`). The issuer is single-threaded for this Stager generation: the ordinary path calls it from the consumer loop; the threaded issue path has one issuer thread and the host consumer does not call `issue_until` concurrently (`1809–1869`). Since that issuer walks entries in order, a later job's watermark cannot pass its prior ring generation before the prior event record call.
- On normal lexical exits, non-streamed work has a per-layer `StagerDone`; stream-all work has a per-chunk `StagerDone`. The threaded issuer has a join guard declared after the chunk guard, so C++ reverse destruction stops and joins it before `chunk_stager_done` calls `finish` (`1777–1780`, `1819–1825`). It is joined explicitly at the ordinary path's end (`2868–2875`). Thus jobs/ready storage is not replaced while those workers or the issuer still refer to it.
- Stream-all planning assigns contiguous job indices over the chunk and calls `start` once (`1726–1775`); non-streamed planning starts a layer's jobs before its `stage_one` walk and closes that generation on leaving the layer (`2570–2592`). In either case, a later generation resets `ready` only after the prior host workers are finished.

These edges are enough for ordinary concurrent worker copies if each job's source is safe and the compatibility API calls succeed. They are not a substitute for return-value handling on asynchronous errors.

## Reuse of `dma_done`, unrecorded slots, and queue ordering

Each `dma_done[b]` is created once with timing disabled during Stager initialization (`237–254`) and reused for subsequent H2D copies into host buffer `b`. The compatibility adapter stores one current SYCL event in each EventState. `cudaEventRecord` obtains the queue event from `q.ext_oneapi_submit_barrier()` and replaces that stored event while holding the event mutex (`compat.cpp:364–379`). `cudaEventSynchronize` snapshots the stored event under the same mutex and waits it through `Runtime::wait(event)` (`394–398`, `runtime.cpp:112–115`). Re-recording therefore changes which operation a *future* host event wait observes; it does not mutate an event copy already returned by `event_of`.

For this ring, the call order provides a reuse rule: before a worker overwrites slot `b`, it waits for the prior `j-kRing` issue watermark, then waits the current `dma_done[b]`; only after it finishes and publishes ready can the single issuer queue the new H2D and re-record the event for that slot. The first `kRing` jobs in a new generation have no `j-kRing` job in that generation, but their event waits see the last recorded event for the same host slot from an earlier generation. If that slot has never been issued, the wrapper's optional event is empty and `cudaEventSynchronize` returns success without waiting; this is safe only because no earlier H2D could still be reading that never-used slot. A skipped job has no H2D of its own; the previous recorded event still covers the last actual use of that modulo slot.

SYCL's in-order requirement applies to this adapter: `queue(st)` verifies the explicit queue uses the runtime device-0 context, while `queue_for` requires the queue's `in_order` property. Under SYCL, prefill sets `m.copy = m.cs` (`prefill.cpp:712–718`). The wrapper maps `cudaMemcpyAsync` to `queue(st).memcpy` and event record to an enqueued oneAPI barrier. The barrier is submitted after the copy on that queue. Main/issuer ownership handoffs and the existing stage-slot `copied/used` ordering remain relevant for device-buffer reuse; this report does not propose changing them or adding barriers. The [Intel enqueue-barrier extension](https://github.com/intel/llvm/blob/sycl/sycl/doc/extensions/supported/sycl_ext_oneapi_enqueue_barrier.asciidoc) defines the returned barrier event as complete after its same-queue predecessors complete. The [SYCL queue reference](https://github.khronos.org/SYCL_Reference/iface/queue.html) describes in-order queues and the event returned for command submission.

The [SYCL USM copy contract](https://github.khronos.org/SYCL_Reference/iface/command-group-handler.html) allows each memcpy endpoint to be a host pointer or a USM pointer accessible to the queue's device, with matching context for USM. The adapter's `cudaHostAlloc` uses `sycl::malloc_host` (`runtime.cpp:146–163`), and a host-allocation failure falls back to a stable `std::vector<uint8_t>` per Stager slot (`prefill.cpp:243–249`). Both are host-accessible endpoints; in either case, their storage must stay alive and unchanged until the queued copy completes. The project does so on normal completion through the final copy-queue synchronization and on teardown through `Prefill::release`.

## Source lifetime and thread safety

The source interface explicitly warns that `blob()` only has to remain valid until the next `blob()` call and requires a caching source to return cache-owned pointers (`expert_source.hpp:106–111`). Stager plans many jobs before workers start (`prefill.cpp:1740–1768`, `2576–2589`). Therefore a source whose blob is transient must not put that pointer in `Job::src`: it must report `transient()` and set `Job::from`, so the worker uses `copy_blob`.

The interface documents `copy_blob` as safe from several threads for a source whose `transient` can be true (`expert_source.hpp:130–137`). `FileExpertSource::transient` identifies staged GGUF blobs and its override of `copy_blob` copies into the caller's destination directly (`expert_source.cpp:1164–1192`); it does not hand the worker a short-lived staging-cache pointer. `copy_from_files` copies the immutable mapped role slices into the unique Stager slot (`658–678`). On this reviewed path, different worker jobs write disjoint Stager buffers. The source object and its mappings/configuration still must remain alive and stable until Stager workers finish. Concurrent source reconfiguration/close is outside the demonstrated contract.

The `from == nullptr` branch uses `std::memcpy` from `Job::src` (`prefill.cpp:287–288`). This is safe only for source pointers that remain stable while queued jobs wait and copy. The source's `transient` marker is the mechanism for avoiding that lifetime hazard; the root FileExpertSource marks its short-lived GGUF staging path accordingly. This is a contract condition for other sources, not proof that the current configured source violates it.

## Device selection, errors, and teardown

The Stager worker begins with `cudaSetDevice(device)` but ignores its result (`prefill.cpp:266–268`). In the SYCL adapter, `cudaGetDevice` always returns ordinal 0 and `cudaSetDevice(0)` only instantiates/checks `runtime_for()`; there is no current-device thread-local state (`compat.cpp:157–171`). The thread-local values are instead `last_error`, `detail_code`, and `detail` (`compat.cpp:47–48`). The event path uses a host EventState mutex, and the queue is the explicit stream pointer. Thus broader worker affinity does not create a device-selection race in the current single-GPU SYCL adapter. However, failures written to an individual worker's thread-local last-error state are not automatically visible to the issuer thread.

The main error path has a concrete gap: `cudaEventSynchronize(dma_done[b])` is unchecked at `prefill.cpp:286`; `cudaMemcpyAsync` and `cudaEventRecord` are also unchecked in the Stager consumer/issuer (`1794–1798`, `1851–1855`, `2611–2616`). `issued_one` stores the issue watermark regardless of whether event recording succeeded. The worker always publishes ready after the source-copy branch unless `copy_blob` returns false, in which case it calls `std::abort` (`289–294`). No per-job status carries wait/record/copy errors back to the issuer. Compatibility wrappers convert thrown SYCL exceptions to CUDA-style error returns in thread-local error fields (`compat.cpp:60–76`); `cudaEventSynchronize` waits with `wait_and_throw`, but the Stager discards its returned error. The runtime also shares a sticky asynchronous-error slot among queues (`runtime.cpp:40–56`, `59–89`). Under normal success these calls return success and the event order works. On a failed event/queue, the code can lose the failure and cannot prove that a host slot was released after successful DMA completion. This is a failure-propagation concern already present before any affinity change; do not characterize it as a reproduced data race.

`Stager::finish` is intentionally a host-worker join protocol, not a DMA drain. It waits until active source-copy workers stop, but does not synchronize `m.copy` (`332–337`). This permits the host buffer ring to be reused under `dma_done` and avoids a per-generation queue wait. Normal `Prefill::run` checks `m.copy` at the end (`2953–2957`). `Prefill::release` synchronizes compute and copy queues before destroying ordinary ring events and before the Impl's Stager member is destroyed (`548–564`); the Stager destructor then finishes workers, joins them, destroys `dma_done`, and frees pinned buffers (`256–265`). This is a sound teardown order on a healthy queue and should be retained. An early function return first runs the issuer-join/StagerDone guards; actual buffer reclamation still depends on later `release` synchronization. The error returns from `release` are currently ignored, so failed queue completion can prevent the compat allocator from freeing host USM while the caller drops its pointer; that is a cleanup/error-reporting limitation rather than a new normal-path race.

## Minimal recommendations

1. Keep the existing per-slot wait and issue-generation order unchanged while widening only the worker affinity. Do not add per-worker queues, blanket queue synchronization, extra events, or waits.
2. Treat successful `cudaEventSynchronize`, `cudaMemcpyAsync`, and `cudaEventRecord` return values as ownership transitions. If a call fails, do not mark the job ready/issued as though it succeeded; publish a failure state that the issuing thread observes and report it through the existing run error path. This is targeted error propagation, not extra normal-path synchronization.
3. Preserve the distinction between stable `Job::src` and transient `Job::from`. Add/keep source contracts so any short-lived `blob()` implementation sets `transient` and overrides or safely implements concurrent `copy_blob`. Do not store ephemeral blob pointers across the entire job-plan pass.
4. Keep Stager destruction after the final copy-queue drain; `finish()` alone does not release a source-buffer lease. Preserve source object lifetime through the host worker join.

No product change is proposed here, and nothing proves that additional CPU affinity improves copy service or end-to-end prefill. Re-evaluate the full exact source, event and generation contract before extending worker parallelism beyond the existing pool.
