## Finding

The untouched `bench.sh` wrapper has no long-decode or arbitrary-prompt option. It only `exec`s `tools/strata_bench.py` with the provided arguments (`bench.sh:1-9`). Its supported request-shaping controls are `--runs`, `--long`, `--clients`, `--think` and server/config/output options (`strata_bench.py:834-848`). `--long` invokes a calibrated prompt around 32,768 tokens, but `LONG_MAX_TOKENS` is a fixed 24 (`strata_bench.py:55-58,281-302,401-411`); it cannot be raised by CLI, environment or config. It reports prompt speed for that request, not a useful long decode stream. `--runs` repeats the prompt with unique tags, but each invocation uses the already-running server or starts one server for the entire suite (`strata_bench.py:882-908`), so it is not independent cold-process replication. It exposes no fixed-prompt hash or RESTORE phase.

Thus `./bench.sh --long --runs 3` (or more runs) remains the unchanged formal stock result, and does establish the approximately-32K prefill reference. It cannot answer long-context decode throughput.

The closest existing stock decode client is `tools/agent_turns_bench.py`, run directly as a separate supporting benchmark. It constructs deterministic repository-backed request histories, with 23 post-tool turns documented as approximately 2.5K–100K input tokens (`agent_turns_bench.py:1-16,58-128`). `--max-new` sets a per-request output cap (default 256); `--rounds` controls repetitions (default 2); each arm is started on a fresh server for each round, alternating arm order (`agent_turns_bench.py:140-196`). Its JSONL records each turn tag, measured `prompt_n`, prompt/decode tok/s and actual generated `n` (`:180-189`). Consequently it can produce repeated independent-process decode samples at turns with actual `prompt_n >= 32049`, if that context is reached on the target checkout/config. Keep only rows meeting the input threshold and a predeclared actual-output floor; report their individual values and rejected rows. The `--max-new` value is only a cap: it does not guarantee the model emits that many tokens.

This is not a repeated cold decode of one identical long prompt: late turns occur after earlier turns have warmed that server's conversation/prompt cache, and `--max-turns` selects only the first N turns, not an arbitrary long turn. The client does not save or restore a model snapshot. Describe these as repeated-process, cache-warmed long-turn samples; do not call them cold or RESTORE samples. The generated request histories are replayed from the same fixed tasks and repository content when the frozen checkout is unchanged, but the report contains no input-byte hashes. Record the exact repository commit and client hashes; derive/store a canonical hash for each selected request body in an external harness if byte identity is required.

`tools/ab_engine.py` exposes `--rounds`, `--max-new`, and `--long-words` (`ab_engine.py:67-76`). Its generated long input is deterministic (`long_prompt`, fixed RNG seed; `:33-39`), and every arm restarts the server each round (`:86-125`). It offers a practical independent-process fixed-long-prompt A/B, but its fixed instruction asks for a five-sentence summary, so a larger `--max-new` cap does not ensure long output. The request JSONL records input token count (`prompt_n`) and actual completion count (`n`) but only the first 80 output characters (`:107-118`); retain per-sample rows and apply the same actual-input/output gates. `--long-words` is a word count, not an exact token count: choose it from a prior calibration and gate on returned `prompt_n >= 32049`, rather than assuming 30,000 words equals 32,049 tokens. It remains a supporting A/B tool, not the `bench.sh` community-suite report.

`tools/serve_load.py` supports `--max-tokens` and `--words` (the latter changes the requested essay length), fixed prompt topics, concurrent clients and rounds (`serve_load.py:28-40,84-99`). Its prompt has no 32K input control; it measures concurrent bursts, not serial single-request decode. `tools/strata_bench.py --clients` delegates to the same short fixed prompts, with a 128-token cap (`strata_bench.py:370-399`). Neither is the right long-context single-stream evidence.

No inspected stock client implements explicit SAVE/RESTORE. `strata_bench.py` measures conversation cache reuse during its agent scenario (`:340-368`), which is not a controlled snapshot restore. `agent_turns_bench.py` replays a conversation sequence and records prompt timings, likewise not a RESTORE API. Do not label either behavior RESTORE.

## Suggested bounded evidence plan

1. Preserve `./bench.sh --long --runs 3` on the unchanged upstream checkout/config as the stock formal long-prefill reference. The stock cap stays 24; keep its original status and results intact.
2. For decode that can reach the required context with a stock client, run the frozen `tools/agent_turns_bench.py CONFIG ARM... --rounds 6 --max-new 256 --log UNIQUE.jsonl` (or a higher cap only if the request budget/context allow it). Require actual `prompt_n >= 32049` and choose an actual generated-token floor before launch (for example, `n >= 128`); report every individual qualifying and rejected turn. Six rounds gives six process-start samples per arm per selected turn, with alternating arm order. The output cap is not the floor. This is long-turn, cache-warmed evidence, not cold/restore.
3. If one identical cold long prompt and longer sustained output are required, neither `bench.sh` nor the available fixed-prompt tools fully express both. Use an unmodified server/API with a small separate diagnostic client: send the exact canonical request body (input whose tokenizer count is verified >=32049, explicit `max_tokens`, deterministic decoding), restart the server between independent repetitions, and retain body SHA256, actual prompt/completion token counts, per-request engine timings, output digest/quality check and process identity. If explicit restore is the target, first use a supported snapshot save/restore route and record that API's real restore evidence; these clients expose no such operation. Keep the resulting custom run labeled supplementary diagnostic/measurement, never as the formal `bench.sh` result.

For the bounded comparison, match model/config, binary, context, prefill chunk and decode settings between arms; differ only in the target decode component. Keep prompt bytes identical and use paired repetition order (A/B then B/A), separate each prefill, cold decode and restore phase, and preserve all individual samples, actual counts, rejected/failed samples and correctness/fault outcome. A performance conclusion requires candidate acceptance rules set before execution: sufficient actual context and decoded-token count, successful completion and correctness gate, plus paired per-process samples; a missing threshold is incomplete evidence, not a pass. Do not infer stable regression/equivalence from the earlier three-request short suite: stock compact0 measured PP 187.5 and decode median 5.4 / pooled 5.134 over 24 outputs; compact1 PP 194.2 and decode median 3.7 / pooled 3.871; the settings/drafts differed and neither equivalence nor stable regression was established. The historical own-fork 32,768-input/64-output/chunk8192/split-ON 449.7 PP and immediate decode 16.635, with RESTORE decode 22.165 in its separate phase, are unlike-config historical evidence, not a matched threshold.

No service exposure or server configuration change is implied. For a local API test, preserve loopback-only binding unless an existing API key protects the endpoint, per project instructions.
