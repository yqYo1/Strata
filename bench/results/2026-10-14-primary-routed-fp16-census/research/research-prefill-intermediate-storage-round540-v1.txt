# R540 — Prefill transient intermediate storage and precision candidates

Date: 2026-10-14 JST. Read-only source and literature review. I read the census registry/research R519–R538, the long-generation registry R525–R530, and the earlier compact-MoE recovery reports, including R508, R517 as summarized in R521, and the GDN recurrence review R518. The existing compact FP16 MoE scratch optimization is already in this tree; the grouped activation gather is a separate unadopted proposal. Neither is re-proposed here. Current source is identified by SHA256 below. No implementation, tests, build, GPU/profiler/live-run access, process/service/reset/cleanup, Git command, model-blob access, or broad private environment/session access occurred. I did not read the excluded GEMM-only contract record. All byte figures are source-derived projections, not runtime allocation, memory-fit, quality, or speed evidence.

## Finding

The current prefill allocates one device `region` sized as the maximum of GDN scratch, QSA scratch, and MoE scratch, because each layer completes attention and writes its residual before its MoE half uses the same region. It already aliases these lifetimes at the large-block level. At a full 262,144-cell QSA capacity and the reported compact-FP16/MMQ-off/ring-8 route, source estimates put the shared region at about 579 MiB for chunk 4096 and 1.10 GiB for chunk 8192. GDN scratch is largest at 8192; QSA's fixed block-score array is the 4096 region maximum. The outside-region chunk arrays add about 607 MiB and 1.19 GiB, respectively, before fixed GEMM, expert-dequant, ring, session/KV and alignment slack. Doubling chunk size therefore adds about 1.13 GiB to carved prefill buffers; `bytes_needed()` conservatively adds another 160 MiB because it counts an FP32 `xn` array that `carve()` omits when `STRATA_GR_UNFUSED` is off. Its projected increase is about 1.28 GiB. These are estimator/source bounds, not an assertion that 8192 fits this GPU.

The largest single obvious transient candidate is routed Down output `Dm`: it occupies `T × K × N × 4` bytes, or 400 MiB at 4096 and 800 MiB at 8192. Storing it as 16-bit while accumulating the weighted top-k reduction in FP32 would nominally halve that buffer, but would round each expert's Down result before `moe_combine`. Under the current arena maxima that change alone does **not** reduce the allocated shared-region peak at either chunk: QSA is larger at 4096, GDN is larger at 8192. It may still affect write/read traffic, which has not been measured. A separate low-risk storage cleanup is possible in GDN: recurrence currently computes a normalized FP32 `y` and the exact same values rounded to `y_h`, while the subsequent output projection reads only `y_h`. Removing the unused FP32 materialization could save up to 96 MiB at 4096 / 192 MiB at 8192 from the GDN region before comparing the next-largest region. The output math and half values need not change, but kernel API and parity proof are still required.

The QSA fixed term is `sel_batch × max_blocks × 4`, with `sel_batch=256`, `max_blocks=max_cells/4+2`; for `max_cells=262144` it is 67,110,912 bytes. The decode-attention scratch is separately sized for 32 rows. Full-context state/KV allocation is not part of this region calculation.

## Source estimates: chunk 4096 to 8192

The calculation uses the geometry above, `max_cells=262144`, `--spec`-independent prompt scratch, compact FP16 effective, MMQ off, BF16x2 off, GR-unfused off, ring explicitly 8, and `Alloc::take`'s 256-byte rounded allocation rule. It assumes the same model layout and runtime configuration at both chunk sizes. Fixed QSA/KV and expert staging terms stay separate; the 256K boundary is not evaluated here.

The table excludes the fixed 64 MiB GEMM scratch, 32 MiB GEMM workspace, two fixed dequant slots, eight fixed staging slots (`MAXBLOB`-sized), `ple_norm`, optional staged KV storage, and the 8 MiB `bytes_needed()` slack; those should be added for a complete arena request. `bytes_needed()` estimates the same region but, with GR-unfused off, includes one extra `T×D` FP32 `xn` allocation: its 4096→8192 delta is about 1.28 GiB, versus 1.13 GiB of carved buffers. This source-accounting discrepancy should be reconciled before using the estimator to claim a reliable admission margin. These projections also omit device allocator/driver overhead and say nothing about currently free VRAM.

At the full-context setting, reducing only `Dm` to half yields nominal saves of 200 MiB at 4096 and 400 MiB at 8192 inside the MoE set, but does not reduce the max-set region in this estimate: QSA and GDN remain larger. Removing the unused GDN `y` array would lower GDN by approximately 96 MiB at 4096 and 192 MiB at 8192; region peak would remain QSA-bound at 4096 and switch to QSA-bound at 8192, so the latter could lower the shared arena by only about 57 MiB. This is a useful candidate calculation, not guaranteed actual allocation savings until the exact context and flags are fixed and estimator/carve are checked. Other transient outputs may warrant the same per-buffer consumer/lifetime audit, but an FP32 accumulation result cannot be declared safely replaceable merely because its inputs or weights are FP16/BF16.

## Precision evidence and limits

The current routed GPU path dequantizes packed expert weights into FP16, uses FP16 activations, and asks oneMKL to write FP32 outputs. `Gemm::f16` in `src/prefill/sycl/gemm.cpp` is templated on FP16 inputs but takes `float* y`; the public contract in `include/strata/prefill/gemm.hpp` explicitly documents FP32 outputs. The Down results are then weighted and accumulated by `moe_combine` in FP32. A candidate that stores each Down result as FP16/BF16 changes the value at the materialization boundary even if accumulation stays FP32. Retaining FP32 accumulation does not restore the rounded value. The current oneMKL DPC++ GEMM type table documents FP16×FP16→FP16 and FP16×FP16→FP32 combinations, but does not list half-output with a separate FP32 accumulator type. Therefore a direct half-output/FP32-accumulate API must be proven for the installed target/library, or implemented as a verified kernel/epilogue; a FP32 GEMM followed by a separate cast still requires temporary FP32 storage and may not lower the memory peak. See [Intel oneMKL 2026.0 GEMM type combinations](https://www.intel.com/content/www/us/en/docs/onemkl/developer-reference-dpcpp/2026-0/gemm.html).

There is precedent for low-precision storage with higher-precision accumulation, but it is not target-model quality evidence. TensorRT documents casting inputs to FP32 for accumulation then casting the result back to output precision, and describes fusing that cast pattern into its layer tactic ([NVIDIA TensorRT precision control](https://docs.nvidia.com/deeplearning/tensorrt/latest/inference-library/precision-control.html)). FlashAttention's implementation accepts FP16/BF16 input types and its public tests compare to a reference with numerical tolerances, not bit identity ([FlashAttention repository/tests](https://github.com/Dao-AILab/flash-attention)). The original FlashAttention paper's “exact” qualifier describes the attention algorithm relative to approximate attention, not FP32 bitwise equality after low-precision I/O ([paper](https://arxiv.org/abs/2205.14135)). oneMKL itself warns that alternate compute modes can have different numerical properties and says accuracy is application-dependent ([oneMKL compute modes](https://www.intel.com/content/www/us/en/docs/onemkl/developer-reference-dpcpp/2026-0/compute-modes.html)). None of these sources measures transient `Dm` narrowing for this quantized Qwen-family checkpoint, B570 path, router, 262K context, or downstream generated-task quality. BF16 adds exponent range but has fewer significand bits than FP16; FP16 has more fraction precision but narrower exponent range. Both remain hypotheses for this output distribution.

## Bounded decision gate

Keep all persistent/history state FP32: GDN recurrence state, convolution history, QSA KV/indexer state, session snapshots and MTP cache are separate long-lived contracts. The current request is about scratch; a short lifetime does not make state narrowing or cache-format changes equivalent.

First qualify the no-new-loss GDN cleanup in a source-only patch and parity fixture: compare current `y_h` and final recurrent state/output with the variant that skips only the unused FP32 `y` store; use odd/tail `T`, 4096 and 8192, and multi-chunk state continuation. Then evaluate `Dm` FP16 and BF16 as separate candidates, preserving the existing route IDs/slots and FP32 weighted accumulation. Capture all routed `Dm` values for same-input reference pairs at `T=1`, sparse and dense expert-row counts, 4096, and 8192; report finite/overflow/underflow counts, absolute and relative RMS, p99 and max error, and router/first-logit changes. Test FP16 and BF16 independently. Do not require identical outputs, and do not infer quality from first logits alone.

For a bounded practical-quality decision, run a fixed, versioned set of 24 prompts (ordinary instruction, coding, reasoning and long-document retrieval; six per category) at representative short and at least 32K/64K contexts, with fixed template, decoding, and continuation references. Compare teacher-forced continuation log-probability/perplexity and task outcomes, blind-score generated responses, and report token agreement only as a diagnostic. Predeclare a non-inferiority margin based on repeated baseline noise (for example, no more than 1 percentage point on task success and no more than 0.5% relative perplexity change); retain every per-item result and do not average away a retrieval/category regression. If the intended claim covers full 256K use, test the actual full-boundary prompt/output separately for capacity, KV/indexer behavior and long-context retrieval. Passing a 64K test is not a 256K boundary pass. A candidate only becomes a quality claim after this target-model comparison; the current research and literature establish no negligible-loss result.

After numerical/task gates, compare clean paired full-prefill runs with the identical source format mix, chunk sequence, prompt IDs, context, cache, ring and settings. Record estimator bytes, actual arena/carve high-water and free device memory; include separate uninstrumented samples and compare against repeat variation. A change is useful for larger-chunk admission only if it reduces the actual max-set/request peak; if it only halves `Dm` within a region still bounded by GDN/QSA, its main justification must be a measured memory-traffic or speed gain. Keep the 256K physical boundary and quality gate distinct from this scratch projection.

## Prior proposals and external references

- R508 already proposed compact FP16 MoE input scratch reuse: it reuses Xs/GU/Hh row zero but keeps full `Dm` and routing tables. That path is present in `compact_moe_fp16()` and the canonical census already records compact FP16 effective; do not count its 103,680 bytes per row nominal saving as a new candidate.
- R521 records R517's unadopted grouped activation gather (bounded contiguous route spans, preserving global Down output offsets), explicitly separate from output dtype. It avoids duplicate gathering work and has its own queue/lifetime checks; this report does not restate it as a new proposal.
- R518 requires keeping persistent GDN state FP32 until exact-model quality evidence supports a change. The proposed y-buffer cleanup applies only to a duplicate transient output; it leaves recurrent state/conv history unchanged.
- External precision references: [Intel oneMKL 2026.0 GEMM](https://www.intel.com/content/www/us/en/docs/onemkl/developer-reference-dpcpp/2026-0/gemm.html), [NVIDIA TensorRT precision control](https://docs.nvidia.com/deeplearning/tensorrt/latest/inference-library/precision-control.html), [FlashAttention implementation and tolerance tests](https://github.com/Dao-AILab/flash-attention), and [FlashAttention paper](https://arxiv.org/abs/2205.14135). They support implementation patterns and bounded numerical comparison; they do not qualify Strata output quality.
