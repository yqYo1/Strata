# R542 — SYCL verifier graph, callback and event lifetimes

Date: 2026-10-14 JST. Read-only review of the current root SYCL compatibility adapter and MTP verifier path. I used the census registry and prior R534, R537, R539/R540 and Main corrections, including the stager error-guard review. I did not inspect the live suite or its files, run Git, tests, builds, GPU/profiler/process/service/reset/cleanup actions, or inspect models, private session state, or the excluded prefill-GEMM-only record. No runtime fault is reproduced and this is not a safety completion claim. Main owns all testing and application.

## Finding

On a healthy runtime, the current MTP verifier has explicit ownership boundaries: each GPU segment is launched with a reusable completion event; the host waits for that graph before reading its output or handing routed rows to the CPU pool; the pool dispatch returns after its worker work; a separate copy queue carries PCIe expert copies and a host task that raises the graph's B flag; the copy queue is synchronized before the next GPU segment consumes the staging rows. Window and commit graphs share the verifier queue and the compatibility layer also orders repeat launches of each executable graph.

The important unresolved risk is failure teardown, specifically for a callback whose argument points into the `Verifier`. `fetch_dma` passes a `FlagSet&` from `Verifier::flag_sets_` to `cudaLaunchHostFunc` and ignores the return values of both `cudaMemcpyAsync` and `cudaLaunchHostFunc` (`verify.cpp:1530–1540`). Normal per-layer and window copy-stream waits retire those tasks before reuse or destruction. But the adapter's `attempt()` first calls `Runtime::check()` and skips its body once a sticky async error has been captured (`compat.cpp:54–76`). Thus a destructor's `cudaStreamSynchronize(copy_)` can return an error without waiting; the destructor ignores that result and proceeds (`verify.cpp:215–231`). If an earlier host task remains queued, it retains a pointer into the object being destroyed. This is a source-level conditional lifetime hazard, not evidence that it occurred in the canonical run. The same precheck limits what the existing event/graph destruction calls prove after a sticky error; this overlaps the corrected R534 ignored-wait finding and the Main stager-guard review, not a new diagnosis that normal event waits hang.

## Selected path and boundaries

The R542 handoff's canonical native68 conditions are MTP/spec capacity 4, split disabled, suffix draft disabled, `STRATA_SYCL_VERIFY_NATIVE_CAPTURE=0`, and `STRATA_SYCL_PREFILL_SAME_QUEUE=1`. Source conditions select these distinct paths:

- `generate.cpp` uses the speculative verifier when MTP is active; the first request window is T=1 and subsequent windows can be T=4 (`generate.cpp:5902–5924`). `T` is the actual graph width for that window, not every window unconditionally being four rows.
- `splitOFF` means `Verifier::record_window` computes `G=1` for both widths; the two-group A/B split is not taken (`verify.cpp:481`). This is independent of the number of GPU graph segments.
- `STRATA_SYCL_VERIFY_NATIVE_CAPTURE=0` selects normal SYCL graph recording for every verifier width. With the variable unset, the default is `small`, which selects native recording only for `0<T<4`; explicit zero therefore does not mean native graph capture is on. The `samequeue=1` setting is `STRATA_SYCL_PREFILL_SAME_QUEUE`; it controls prefill queue/event behavior, not verifier queue topology or graph capture.
- The SYCL verifier still records a sequence of per-layer segments and launches each with a completion event. Graph-internal event markers are captured, then the wrapper rebinds their host EventStates to the corresponding graph-submission completion event. The executable graph's `last` event serializes another launch of that same graph, even if the launch queue changes. The actual serving path supplies the verifier's same `cs_` queue for window segments, work graphs and commits.
- `STRATA_SYCL_VERIFY_OVERLAP` defaults on unless set to `0`. On this one-group path the worker callback can submit the separate shared/hit work graph while the CPU pool is running, and the copy queue may progress alongside that work. An absent configuration is not proof that every source branch ran in a recorded serving request.

This reading establishes what the supplied configuration selects from current source; it does not inspect or infer the live run's branch events or completion status.

## Ownership on the ordinary success path

**Captured work and graph reuse.** `cudaStreamBeginCapture` and the explicit native variant attach a `ModGraph` to an owned stream under `registry_mutex`; `cudaStreamEndCapture` finalizes it, and normal mode also materializes nodes for compatibility queries (`compat.cpp:430–470`). `GraphExec` retains weak references to captured event states, a mutex, and the last launch event. Launch holds that mutex while it submits the graph with a dependency on the previous `last`, sets the new last event, and updates any surviving event states (`compat.cpp:473–510`). This serializes replay of mutable graph inputs and state even if two callers submit the same graph on different queues. A completion event is required to be timing-disabled and cannot be bound during capture. It is set to the submission event, not a separate trailing barrier.

`EventState` protects the optional event and captured/timing metadata with its own mutex. `cudaEventRecord` submits an in-order queue barrier and then atomically replaces the host-visible recording; `cudaEventSynchronize` snapshots that event under the mutex. Re-recording replaces future observations but cannot mutate a `sycl::event` value already snapshotted by a caller. Captured events are added as weak references to the graph; destroying the public event makes later rebinding unnecessary. A recorded graph-internal event is conservatively rebound to whole-graph submission completion, so an event placed mid-graph may over-wait to graph end in this adapter. This is a possible semantic/performance limitation, not a premature-release hazard on the reviewed completion path.

**Queues and session buffers.** Runtime compute, transfer and `make_queue` queues are in-order and share one context plus sticky asynchronous-error state (`runtime.cpp:44–79`). Compatibility streams are separately owned `sycl::queue` objects in a registry; `queue(stream)` checks runtime context, and `queue_for` additionally requires in-order. Verifier uses its explicit `cs_` and `copy_` streams, rather than prefill's same-queue alias. The captured SYCL graph stores source pointers and reads their current contents on replay, so window staging arrays, plan memory, arena, mapped flags and session state must outlive replay. `window_scope` marks normal drained/completed windows and marks an early-returned active window failed (`verify.cpp:1218–1232, 1393–1498`). The next graph segment is submitted only after CPU routing and a successful `cudaStreamSynchronize(copy_)`; this retires PCIe DMAs and their callback before the next graph can use the staging area (`verify.cpp:1374–1390`). At window end both `cs_` and `copy_` are synchronized before sampling/output and completion state is published (`1393–1405`).

**CPU handoff.** The verifier calls `PoolMultiFn` on the serving host thread with pointers into its mapped x/ids/output arrays (`verify.cpp:1333–1337`). The MTP adapter calls `expert_pool_dispatch_multi` with actual `n_tok` (`generate.cpp:710–719`); that dispatch validates width and entry capacity, assembles per-expert jobs pointing at activation and output rows, then invokes the long-lived `ExpertPool` split-multi native path (`expert_source.cpp:1869–1900+`, `pool.cpp:663+`). It returns synchronously after pool work. Therefore the verifier's host row slices remain owned through CPU completion, and it does not start the next layer until the callback returns. This is a host thread-pool handoff, distinct from SYCL's `h.host_task` used for DMA completion.

**PCIe callback lease.** In SYCL, `fetch_dma` queues one or more host-to-device copies to `copy_`, then submits a SYCL host task that raises B after those prior in-order commands (`verify.cpp:1530–1540`; `compat.cpp:250–258`). Its `FlagSet` argument comes from a fixed verifier-owned array indexed by layer and group (`verify.hpp:253–255`). For the one-group path there is one slot per layer. The normal copy-stream sync occurs before moving to the next graph segment and before another window reuses the array, so a successful sync is the lease-retirement edge. On the graph side, plan A is published after CPU plan writes; B denotes that the PCIe share has landed. On a layer with no plan publish, the host supplies empty A and raises B itself (`verify.cpp:1349–1359`).

**Commit.** `commit()` submits the commit graph on `cs_` with `commit_done_` as completion. In normal SYCL mode it synchronizes `cs_` before returning; the async mode is compile-time guarded to non-SYCL for event recording, so SYCL still waits. `wait_commit()` recurses the verifier chain and only synchronizes if `commit_pending_` was set (`verify.cpp:1630–1674`). This keeps state updates complete before the request's later reads. The code sets `commit_pending_` in the async branch but that branch is not selected for SYCL.

## Error, cancel and destruction paths

API-level failures are surfaced for graph launch, layer-event wait, per-layer copy-queue sync, final verify/copy stream sync and commit sync; `WindowScope` marks an early failed window as failed rather than completed. Cancellation in generation is checked between prompt or decode windows (`generate.cpp:6004`), then the request calls `wait_commit` before returning from its ordinary completion path (`6010`); a request-level early `return` on error instead relies on local destructors and later engine cleanup.

Several concrete limits remain:

1. The two submission calls in `fetch_dma` are unchecked. A failed copy or callback submission is not directly stored in a verifier-side error field. The later copy stream synchronization can report a queue failure, but it cannot retroactively make an unsubmitted host task raise B. If a device graph is already waiting for B, recovery depends on the existing watchdog path that raises all mapped flags; source alone does not establish a bounded response for every host-task submission failure.
2. The callback argument is a pointer to `Verifier::flag_sets_`. `Verifier::~Verifier` removes watchdog registry leases first, synchronizes `cs_`, destroys graphs/events, then synchronizes and destroys `copy_`, and finally frees mapped arrays (`verify.cpp:215–231`). The registry lease protects concurrent watchdog visitation, not already-submitted SYCL host tasks. On a healthy queue, synchronization before object deallocation closes this gap. Following a sticky asynchronous failure, `attempt()`'s `Runtime::check()` preflight can skip the queue wait body. Since the destructor ignores these API results and still proceeds, source does not prove the callback has retired before the embedded `FlagSet` storage dies. Compat host/device `cudaFree*` likewise may skip its wait body after sticky failure; this tends to retain allocations in the registry rather than make them safe to reuse, but does not extend the lifetime of the `Verifier` object's inline callback arguments.
3. `cudaGraphExecDestroy` correctly leaves an executable graph allocated when its checked wait fails; its comment explicitly says ownership is uncertain (`compat.cpp:541–553`). This is safer than deleting in-flight graph storage, but callers ignore the returned result and discard their handles during teardown, so it can leak. `cudaStreamDestroy` similarly only erases an owned stream after queue wait and will reject recording streams; a sticky-error precheck can leave its registry-owned queue behind. These are conditional cleanup leaks, not proof of completed work.
4. `cudaEventDestroy` directly deletes its wrapper (`compat.cpp:383–385`) without `attempt()` or a queue wait. Host event synchronization snapshots a copied SYCL event under the mutex before waiting. Reviewed graph completion uses the longer-lived `layer_done_`/`work_done_` handles across sequential submissions, but arbitrary destruction while another host thread concurrently uses the same CUDA-shaped handle is not protected by an object-lifetime protocol. No such concurrent destroy/use is demonstrated in the selected serving path.
5. `release_gpu_waits` raises mapped flags then polls both queues through `cudaStreamQuery`; it is a rescue for GPU spin waits, not queue cancellation. It reports a five-second drain timeout but does not free device work. The callback registry's close waits for active watchdog leases; it does not cancel queued host tasks. Process abort, if chosen by Main's separate stager error-guard proposal, is an abnormal exit and not a drain guarantee.

The scope does not establish all teardown paths safe after asynchronous failure. It does establish the ordinary successful-path edge required to keep `FlagSet` pointers and staging memory alive until callback and DMA completion. Preserve the distinction between a wait that ran and returned an error and a wrapper preflight that returned before calling the wait.

## Primary SYCL contract and version boundary

The Khronos SYCL reference defines `sycl::event::wait_and_throw()` as waiting for its command and passing unconsumed asynchronous errors to the associated handler; its queue reference gives the corresponding queue-wide semantics. These support the healthy completion edge but do not justify an adapter helper that skips the wait on an already-sticky error. Intel's official SYCL Graph extension spec and usage guide document record/replay graphs, graph submission, and use of host tasks for host work. The graph spec marks storage-lifetime support under “Future Direction,” so this report does not rely on graphs implicitly owning host memory captured by raw pointers. Strata's explicit caller-owned arenas and waits are the source evidence for those lifetimes.

Version caveat: Intel's official enqueue-barrier page identifies itself as a final-draft preview extension, currently revision 2 (built 2026-08-10), rather than stable core SYCL. The code uses `ext_oneapi_submit_barrier`; the local report chain identifies oneAPI/Level Zero elsewhere but this pass did not inspect the exact compiler/runtime binary or establish that its version matches the page's current revision. The graph references are Intel extension documentation, not CUDA semantics and not a claim that every SYCL implementation shares identical graph behavior.

## Review disposition

This report adds a verifier callback-argument lifetime case to the existing sticky-error/ignored-wait concern. It does not repeat R534's worker `dma_done` ring analysis or R537's MTP coverage map. No implementation is proposed. After Main's benchmark and PR#6 boundaries, a focused host-only error fixture could verify that an injected submission error remains visible and that `FlagSet` retirement is required before verifier destruction; healthy SYCL comparison remains Main-owned. Any remedy must preserve the normal same-queue ordering and avoid adding waits on the successful path unless a measured contract requires them.
