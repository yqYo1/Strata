## Transposed local-memory contract

The old group has 256 threads (8 subgroups of 32), handles one query, one KV head and one 64-cell selection chunk. It stages that KV head's 12 query-head rows in `sq[12][256]` as 12,288 bytes of FP32 local memory. For linear source index `i = h*256+d`, the `TRANSPOSE_Q` write is `sq[h][(d % 8)*32 + floor(d/8)] = q[h*256+d]`. Thus each source row is stored as a 32-by-8 transpose of its natural `[dim/8][dim%8]` tiling. During score calculation lane `l` reads `sq[h][l], sq[h][32+l], …, sq[h][224+l]`, giving query dimensions `l, l+8, …, l+248`; each lane still reads the matching eight consecutive K dimensions `8*l..8*l+7`. This is a query staging/read-layout change; the logical Q vector and selected KV rows do not change.

The other live group-local arrays are `sp[12][64]` (3,072 bytes) for scores then weights and `srow[64]` (512 bytes) for resolved physical row IDs. Their declared total is 15,872 bytes per work-group before compiler/runtime overhead. The variant-1 launch requests subgroup 32 and 256 work-items. A current-port launch should retain that geometry and three arrays; query transposition does not increase declared local-memory bytes over the current fallback's `sq(12*256) + sp(12*64) + rows(64)` footprint. No B570 runtime local-memory limit was queried in this read-only pass. Therefore the byte requirement is known (15,872) but device acceptance must be established from the actual B570 capability/admission result; the 49,455 ms QSA phase or donor build cannot establish it.

All work-items execute the same `n_here` branch because it depends only on the query's shared step width and group chunk. The old `n_here <= 0` early return is therefore work-group-uniform and occurs before any barrier. Otherwise the path has three work-group barriers: after Q/row staging, after score writes, and after weight writes. Their convergence is safe only while these conditions remain uniform across the group; no lane-dependent early return may be introduced before them. Row validity checks and tail masks are per-cell, but every work-item reaches each barrier. The current root fallback uses the same three logical phase boundaries, with a first barrier after staging and final values written after weights are made visible.

## Inputs, formats, selected width, and index safety

Both implementations take FP32 Q, int32 IDs with per-query `cap` stride, four-int32 step rows, paged K/V pools, FP32 scratch/output, and a page table. The step contract is `pos`, `n_kv=pos+1`, `n_bid=floor(n_kv/4)`, and `width=min(n_kv, 2048+4-1)`. `kStepWidth` is the number of active selected IDs, not physical context or KV capacity. For the actual shape (`idx_top_k=2048`, block=4), width saturates at 2,051, while `cap` is the allocated selection capacity (must be at least that width). The independent top-k source ceiling `kTopkMaxCells=32768` is context accepted by selection, not 32,768 selected IDs. Physical context at the reported boundary is 262,144 cells: valid logical IDs are 0 through 262,143; position 262,143 is the 262,144th valid input and produces no further valid input position. At capacity, an additional input/output position must be refused. Context length, active selected width, and number of new prefill queries must remain separate quantities.

For active ID index `j < width`, the producer's valid contract is `0 <= ids[j] < n_kv <= 262144`. Below the selection cap IDs are the identity selection; above it the indexer-selected set is sparse but still refers to causal logical cells no later than the query position. IDs at `j >= width` are padding and must not be read. The old donor reads `ids[c0+t]` for `t<n_here`, without a negative-ID check before `cell/page_size` indexes `page_table`; it also computes `n_here=min(64,width-c0)` without clamping width to `cap`. It is unsafe to port those assumptions as API behavior. Current root clamps step count into the chunk interval and masks negative IDs, but for a nonnegative ID it still indexes `page_table[cell/page_size]`; its pointer-span guard does not prove the ID is inside the logical page table or the physical pool. Negative IDs should not be injected into a valid-ID case: if a test injects one, the host-side test validator should reject it before launch unless a separately specified sentinel policy is deliberately exercised. Likewise reject width outside `[0,cap]`, width above the step's causal `n_kv`, or any active ID `>= n_kv` / physical context at the host test boundary instead of letting it become a page-table index.

The real page size is 4 cells. Logical lookup is `logical_page=cell/4`, `physical_page=page_table[logical_page]`, then `row=(physical_page*n_head_kv+kvh)*4 + cell%4`. A table entry of `-1` denotes a page not resident in the supplied pool and is masked to zero contribution; other negative values or a physical page beyond the pool's page allocation are malformed metadata. The page table is not assumed identity-mapped. K/V int8 pools use 256 signed-byte codes per row and four FP16 scales per row, each scale covering 64 dimensions; load converts half scale to float and computes `float(code)*scale`. FP16 mode reads half rows; Q4 modes use different layouts and rotation behavior. The R522 run used int8 KV and 32,768 resident cells, but current ring/staging page-table semantics must be preserved: the physical page mapping and resident-page lifetime belong to the existing stream/append path. This candidate must not gather/reorder IDs or K/V or alter ring ownership. Validate mapped-page boundary and nonresident masking against the active int8 pool.

Current root API has checked size arithmetic and span validation for `nq*heads*HD`, `nq*cap` IDs, `nq*kStepCount`, per-query scratch and output. It checks cap/shape and batch count (up to 65,535), and checks its `size_t` scratch/byte products before enqueue. The donor validates much less: it rejects absent primary pointers and oversized `n_q` but has no equivalent robust `size_t` span/index checks; it casts `cap` to `int`, derives `n_chunks`/stride with unchecked intermediates, and dereferences page-table and pool rows based on IDs. A port should keep the root `checked_count`/`validate_spans` and overflow guards, strengthen shape guards for positive `n_head_kv` and `page_size`, check all required mode pointers as a coherent format, and validate step/ID metadata at the host-owned boundary used by adversarial tests. A raw device selection buffer cannot be validated on CPU without a copy/synchronization; production must rely on the already validated producer invariant and avoid introducing that transfer into the measured path.

## Math and smallest scope

Both formats dequantize Q/K/V loads to FP32 before attention arithmetic. The old 1eb variant's score path forms each lane's eight-term dot with ordinary multiply/add expressions, then subgroup XOR-sums at offsets 16, 8, 4, 2, 1, and scales by `1/sqrt(256)=1/16`. Its chunk max and normalization use `sycl::native::exp`; value accumulation uses FP32 `sycl::fma`; merge also uses `sycl::native::exp` and FP32 FMA. The current root fallback instead chains the per-lane score terms through `sycl::fma`, uses `sycl::exp` for chunk normalization and merge, and has its current sum/max reduction and FMA ordering. Therefore copying old variant 1 wholesale changes floating-point math even though the tensor algorithm is the same. Such a port can legitimately show numerical drift and needs attention-output/residual comparisons, logits/logprob checks, perplexity, and the established model quality suite; exact token equality is not a suitable sole criterion. Report the drift and whether it changes decisions/quality.

The narrowest candidate that isolates layout is the current root fallback with only the Q local-store index permuted to `(d%8)*32+d/8` and the read changed to the old transposed addresses. Keep the current root score expression/FMA sequence, `sycl::exp`, max/sum reduction, 64-cell partials, current merge, current formats, selected-ID/page mapping, checks and dispatch default exactly as they are. Then the layout arm has the same output math as current by construction, and should be expected to have close numerical parity (subject to any compiler reassociation caused by changed loads); verify output and residual numerically. A donor-faithful arm that also restores old score/exp arithmetic is a distinct math variant and requires the quality gates above. The old variant API was explicitly experimental; do not transplant its broad migrated TU or variant selector.

## Validation cases before any admission claim

Use adversarial host-built fixtures whose metadata is validated before device launch. At minimum cover: lifecycle positions 0, 1, 2, 3, 4 and width transition at 2,051/2,052; one query and 32-query batch plus a final partial query batch; selected width 1, 63, 64, 65 and 2,051 to exercise 64-cell chunks and partial final chunks; the maximum physical input position 262,143 with valid selected IDs at 262,140..262,143 and refusal of a next position; logical-page crossings 3/4, 63/64, and final page 65,535/65,536, including a deliberately nonidentity page table; int8 code/scale rows across page slots and correct per-64-dimension scale boundaries; resident pages, `-1` nonresident page entries, and ring slot reuse with an explicit producer/consumer lifetime check. Compare old-layout candidate and root fallback for all valid cases, including all 24 query heads / both KV heads and empty or all-masked active selection only if the official width contract allows it.

Pre-enqueue rejection cases should include negative or over-context active IDs, active ID `>= n_kv`, width negative/greater-than-cap/greater-than-`n_kv`, invalid page-table logical extent, physical page `< -1` or beyond allocated pages, null/inconsistent int8 pool/scale pointers, unsupported page size/head geometry, negative or excessive `nq`, cap overflow, and checked byte/count overflow. Do not pass these values to a kernel and then call a fault-free return a safety pass. Keep zero-width/zero-query semantics explicit: current root returns immediately for `nq==0`; old API returns for `n_q<=0`; real prefill QSA requests here have nonzero queries and positive causal widths. Tail `n_here==0` chunks must write neutral max/sum and zero accumulator scratch exactly once per chunk so merge cannot read stale partials.
