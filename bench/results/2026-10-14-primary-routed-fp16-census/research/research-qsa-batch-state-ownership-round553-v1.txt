R553 — QSA indexer batch state ownership audit
Date: 2026-10-15 JST
Scope: independent, read-only integer-geometry and state-transition review of `qsa-indexer-batch-proposal-v1`. This report does not assess floating-point parity, benchmark performance, or adoption.

Finding

For validated calls, I found no integer-planning or state-ownership counterexample in the proposed mapping. The proof depends on the current source's exact append control flow: for nonzero positions, lanes update the partial tail first, then all lanes return unless `pos % 4 == 3`. Thus only position zero initializes `dead`/pooled row zero, and only a completed four-cell block writes its pooled key, next spare row, and `block_pos`. The report's claim that the batch leaves the state as serial appends do is consistent with these transitions, subject to the deferred device parity checks for the shared math refactor and all supported runtime paths.

Mapping and state ownership

For validated `p0 >= 0`, `n > 0`, and `end = p0 + n <= capacity`, the plan uses `first_block = floor(p0/4)` and `completed = floor(end/4) - floor(p0/4)`. The completed blocks are exactly `[first_block, first_block + completed)`. For each row j in a completed block b, `input_row(b,j)` returns the old `tail[j]` only when `4*b+j < p0`; otherwise it returns raw row `4*b+j-p0`. A completed block ends before `end`, so every returned raw row is in `[0,n)`. Only the first block can read the old tail, and only rows below `p0 % 4` can do so; row 3 is always current input. The bulk stage reads old tail values before the later metadata stage updates them.

Each bulk work-group owns one completed block and writes only `pooled[b]`, with lanes d=0..127 writing distinct dimensions. Its input reads are read-only; no work-group writes an intermediate spare. After all bulk groups on the in-order queue, the metadata submission writes the last input row for each tail slot 0..2, leaving an untouched slot unchanged. If at least one block completed, it writes `pooled[floor(end/4)] = dead` and sets `block_pos = base + 4*(floor(end/4)-1)`. This spare index is immediately after the bulk output range, so the final spare cannot race with a completed key. The initial `p0 == 0` serial append is submitted before both stages; it establishes dead and the initial spare from raw row zero. Bulk then overwrites completed pooled rows as appropriate.

Directed hand-traces against the current serial path agree:

- `p0=0,n=1..3`: position zero performs the initial dead/key/spare write; later positions only update tail slots. The plan performs the same initialization, then writes those final tail slots. No completion means no block-position update.
- `p0=1,n=2`: positions 1 and 2 update tail slots 1 and 2 but do not reach the block-completion path. The plan leaves pooled rows and `block_pos` unchanged and writes those same tail slots.
- `p0=3,n=1`: block zero is completed by position 3. The first three inputs come from old tail slots 0..2 and row 3 comes from raw row zero. The plan writes pooled row zero, spare row one from dead, and `block_pos=base`; the serial append does the same.
- `p0=0,n=5`: block zero completes at position 3, then position 4 changes only tail slot zero. The plan writes pooled row zero and final spare row one, and updates tail zero; it does not incorrectly advance `block_pos` to the incomplete block.
- Multiple chunks compose: an incomplete first chunk leaves its tail for the next bulk stage; a later completion reads that prefix before metadata changes tail. The next final tail and spare correspond to the serial transition at the concatenated end position.

The `completed == 0` behavior is important: the serial append's early return prevents both spare and `block_pos` stores for a partial block. When `p0 == 0`, the separate initial append still writes pooled row zero and its spare, matching serial position zero. The fixture's independent serial model includes that early return and checks whole state, but it was not executed for this review.

Full capacity and integer bounds

At the configured `capacity = 262144`, appending the full range (`p0=0,n=262144`) plans 65,536 completed blocks: bulk writes pooled rows 0..65,535, metadata writes the spare at row 65,536, and the initial append first establishes dead. The last valid cell is 262,143; its completed-block RoPE position is `base + 262140`, and `block_pos` receives that value. Tail slots retain the half-rounded raw values for positions 262,140..262,142. The session carve allocates `capacity/4 + 2 = 65,538` rows, while the existing API span covers `capacity/4 + 1 = 65,537` rows. The accessed spare row 65,536 is in both; physical row 65,537 is outside the validated span and remains untouched. A final-cell continuation (`p0=262143,n=1`) reads the old tail for rows 0..2, raw row zero for row 3, completes row 65,535, writes spare row 65,536 and leaves row 65,537 untouched.

The public batch entry checks `p0 <= capacity`, `n <= capacity-p0`, and the existing validator constrains `capacity <= INT32_MAX`, `base >= 0`, `base % 4 == 0`, and `int64_t(base)+capacity <= INT32_MAX` before building the plan or launching work. Under those checks, `p0+n`, block counts, raw row indices, `4*block+3`, and `base+4*block` remain in range; conversions of block IDs to `int` are safe. At 262,144 capacity, the bulk range has 65,536 work-groups and 16,777,216 work-items, and the arithmetic fits 32-bit signed indices where used and 64-bit `size_t`. The implementation still forms span byte counts and launch sizes in `size_t`; as in the baseline, this assumes the project's 64-bit host/device address environment and does not add a 32-bit overflow guard. Device-specific maximum global-range acceptance is not established by source review.

The extra `+2` allocation is not consumed as a second spare: the final valid spare is always `floor(end/4)`, at most `floor(capacity/4)`. The extra physical row is unused by both baseline and proposal. For non-divisible capacities, the same bound holds; a final incomplete cell does not enter a completed block or trigger a pooled write.

Validation, queue, and pointer lifetimes

The candidate retains the baseline `validate` call and its spans: raw has `n*128` FP32 values, gamma has 128, tail 3x128, dead 128, pooled `capacity/4+1` rows, and block_pos one int32. It also retains the existing registered cos/sin context and output-overlap checks. Raw, gamma, and state spans must remain disjoint under that validator. The new helper adds no buffers or aliases. The per-block bulk writes are within pooled's validated extent; tail/dead/block_pos writes use their validated extents.

The adapter is explicitly host-positioned and not for graph capture. Prefill passes a chunk pointer `m.idx_raw` representing the current `[n,128]` rows and a separate sequence-relative `p0`; the planner correctly subtracts `p0` before indexing this chunk pointer. `queue_for(stream)` requires an in-order queue. The initial append, bulk `submit`, and final `parallel_for` are therefore ordered without a new event or wait. Prefill's subsequent score submissions use the same `m.cs`; existing input/state lifetime and run-drain boundaries remain the ownership contract. The decode/verifier path's device-position single append is unchanged and does not consult this opt-in batch branch. Registered RoPE/MRoPE pointers remain borrowed by value in device arguments under their existing context/replay lifetime rules; the proposal creates no new host staging or owned allocation.
