# R546 — Zen 3 mixed-IQ lossless weight-layout and codebook reuse review

Date: 2026-10-15 JST. Read-only source and external implementation review. This report is the sole write. No model blobs, live run files, private environment/session values, build/test, GPU/profiler, process/service, Git, reset or cleanup work was performed. I did not inspect the prohibited `prefill-gemm-only-contract-root-v1/record.json`. Main owns any implementation and serial measurement after the existing boundaries.

## Scope and corrected workload

I followed the primary census `research-index.json`/`previous_registry` chain and read R535, R538, R539 plus the R535–540 reviews. The corrected actual model has seven GU/Down pairs: `(18,20)` x14 layers, `(22,20)` x15, `(21,20)` x9, `(22,42)` x5, `(18,42)` x3, `(21,42)` x1, `(23,20)` x1. Thus GU types are IQ3_XXS, IQ3_S, IQ2_S, IQ4_XS; Down types are IQ4_NL or Q2_0. There are seven pairs, not eight. MTP draft count and per-expert CPU job `nt` are different quantities. The pool divides flattened routed rows; expert count alone does not determine task fill.

The host target is the Zen 3 / AVX2 path already built for `znver3`; AVX2 kernel flags, CPU arch, activation quantization-once, pool row splitting, Q2 Down42 AVX2 and multi-token `nt=2..4` decode reuse are existing behavior. Do not count them as new proposals. On the described default dispatch, GU `nt=1` uses GGML `vec_dot` (except the opt-in exact helper for IQ3_XXS/IQ3_S/IQ2_S); GU `nt=2..4` uses `iq256_*`. Down20 `nt=1` uses GGML and `nt>=2` uses `iq4nl256`; Down42 already uses its Q2 AVX2 rows for `nt=1..4`. Actual current-run per-pair/job-nt counts remain required before prioritization.

R535 records the expert-only arena as 50.293 GB packed versus 241.592 GB if expanded to FP16. These are logical-format sizes, not observed DRAM traffic, cache misses or host-RAM capacity left after other model allocations. The prior 36.87 GB/s host read control and kernel comments are distinct evidence; they do not establish this workload's physical traffic or bottleneck.

## What current kernels already reuse

In `iq_avx2.cpp`, `Fmt32<TY>::decode` expands each 32-value half from the native code/index bits to magnitude lanes `g`, sign lanes, and scale lanes. `row_dot<TY,NT>` calls that decode once for each half of a packed block, then loops over all `t < NT`, loading each Q8_K activation and accumulating with `vpsignb`, `vpmaddubsw`, `vpmaddwd`, integer adds, then FP32 FMA with the block/activation scale. The same native weight block is therefore decoded once for all tokens in that job. The specialized IQ2_XS route follows the same pattern. `gu_rows` does this separately for gate and up matrices, applies the GGML IQ math, then computes `silu(g)*u`. The matching Down20 multi-token kernel decodes/unpacks nibbles and absolute values once per packed block, then applies them to all tokens; Down42 unpacks Q2 weights once and reuses them over `NT` rows.

For GGML IQ dot semantics, each block/half has codebook integer magnitudes and a sign vector; activation bytes are sign-adjusted, integer dot products are multiplied by decoded per-half scale(s), then block `d` and activation `d` are multiplied and accumulated in FP32. IQ2_S/IQ2_XS carry two subscales per 32 values; IQ3/IQ2_XXS classes use their own encoded scale contract; IQ4_XS folds signed subscales into the integer operand. A cache must preserve each format's decoded magnitudes/sign/scale and the existing accumulator/reduction order to claim exact output. A different grouping or floating reduction can change bits even when the decoded weights are lossless. Down42 is a distinct Q2_0 arithmetic path with Q8_1 activations and correction term; it is not an IQ codebook candidate.

The remaining repeated decode work is consequently concentrated in separate calls/jobs, especially GU gate versus up, and repeated calls to the same expert across different decode windows. The existing `nt=2..4` path already handles reuse inside one expert job. Because type23 has no exact `nt=1` helper, it is not valid to assume IQ3/IQ2 exact-helper results transfer to IQ4_XS.

## Ranked candidate and decision

**1. Conditional research candidate: a bounded, immutable per-expert decoded-block cache for recurrent `nt=1` IQ experts, with packed weights as the source of truth.** Keep a strict byte budget and only cache a format's predecoded integer magnitudes, sign representation and per-half scales after the same native block decode used by the kernel. A hit could avoid repeating codebook/index/sign expansion for a recurrent expert across otherwise independent `nt=1` calls while retaining the current integer-dot and FP32 reduction order. Cache gate/up independently, invalidate only with the packed-weight identity/lifetime, and fall back to native packed blocks on misses. The seven-pair/job-nt observer must first show meaningful repeated same-expert `nt=1` calls within cache lifetime; a frequently selected expert alone is insufficient evidence of a cache hit.

This is a testable hypothesis, not an adoption recommendation. At `nt=1`, a predecode pass plus write and later read adds memory traffic to eliminate decode instructions. A decoded representation storing even one byte per weight has a rough 2.4x total-arena footprint versus the recorded 50.293 GB mixed packed arena (about 120.8 GB before scales/alignment); storing separate sign and magnitude vectors expands more. This rough denominator is a representation bound, not a proposed exact format or a traffic measurement. A whole-model decoded copy is therefore not a credible default for a 128 GB class machine already carrying the model and runtime. Any test should begin with an explicitly small per-layer/per-expert cache cap and report bytes, insertion/decode cost, hits/misses, eviction, exact routed `nt=1` population, worker CPU time, wall time, and model/runtime RAM headroom. Compare end-to-end decode and matched host memory controls; do not infer physical DRAM savings from source extents or hit counts. Correctness gates: block-level decoded fields versus GGML reference for each used IQ format, exact same integer sums and scale handling, then full row/output parity and continuation-level checks. For IQ4_XS and any changed reduction, report exact versus tolerated differences separately.

**2. Lower priority: short-lived row-tile decode/reuse across two or more independent `nt=1` calls for the same expert.** This could share the existing decoded block over different activation rows without retaining model-wide derived weights. It only helps if the current scheduler can identify and co-locate identical expert/weight rows without delaying jobs or changing completion/fault semantics. Current pool jobs already group routed rows by expert into `nt`; R538/R539's flattened-row and actual-job-nt corrections mean a new cross-job grouping is not justified by an expert-count argument. It also has to stage/hold multiple Q8 activations and preserve per-token results. Test only if the actual observer shows repeated `nt=1` groups for the same expert close enough to combine; otherwise reject as added scheduling and buffer cost.

**No broad lossless on-disk repack candidate is ranked.** Repacking IQ data into fully expanded signed bytes at load time removes some decode operations but increases the live weight footprint and adds conversion/writes. For `nt>=2`, it duplicates work already shared by `iq256_*`; for `nt=1`, whether fewer instructions outweigh added bytes is unknown and likely depends on recurring expert reuse. A cache-repacked file would also duplicate or replace native packed storage and must retain format/version identity. No evidence supports a speedup claim.

## External implementation references and transfer limits

- The matching upstream GGML checkout is pinned in local CMake to llama.cpp commit `3cf03257f219afbe7334045ff7c6a06ac68c627d`. Its x86 quant implementation is the correct format/math reference: [pinned llama.cpp x86 quant kernels](https://github.com/ggml-org/llama.cpp/blob/3cf03257f219afbe7334045ff7c6a06ac68c627d/ggml/src/ggml-cpu/arch/x86/quants.c). Current GGML AVX2 IQ dot decodes each vector for a single-token dot; Strata's NT kernels already add job-local cross-token reuse. Do not compare them as if Strata lacks packed math or as if GGML were an unoptimized scalar baseline.
- The [vLLM CPU MoE group-size-32 INT4 PR](https://github.com/vllm-project/vllm/pull/51546) documents an AMX CPUExpertsInt4 path for symmetric INT4/group-32 compressed-tensors weights and DeepSeekV3 routing. It confirms that weight handling/post-load packing is a real backend design dimension, but its AMX, INT4 and checkpoint representation do not match Zen3 AVX2 GGUF IQ2/IQ3/IQ4_XS or Q2_0. It is not a kernel to import or a performance prediction here.
- SGLang's [fused MoE Triton kernel](https://github.com/sgl-project/sglang/blob/main/python/sglang/kernels/ops/moe/fused_moe_triton_kernels.py) describes expert-stacked weights and token/expert sorting/padding for block matmul. That is a GPU/Triton scheduling/layout pattern, not a demonstrated CPU IQ decode/cache solution. Its utility here is limited to reminding us that a layout choice must be evaluated together with routed-row grouping.
- The SOSP'25 [KTransformers paper](https://madsys.cs.tsinghua.edu.cn/publication/ktransformers-unleashing-the-full-potential-of-cpu/gpu-hybrid-inference-for-moe-models/SOSP25-chen.pdf) reports CPU MoE kernels for different models, quantization and a dual-socket Xeon AMX/DDR5 setup. The paper's setup/results are not comparable to this six-core Ryzen 5 5600X PC target and mixed-GGUF-format CPU route; its reported rates cannot be applied to Strata.
- A personal Reddit implementation post (not benchmark-quality evidence) describes the same general pitfall of expanding Q4 weights to F32 and thereby multiplying weight bytes versus fusing unpack with dot: [C99 CPU LLM implementation discussion](https://www.reddit.com/r/LocalLLaMA/comments/1u5va0u/building_a_cpu_engine_in_c99_stuck_at_190/). Treat that only as an anecdotal design warning. Here the relevant source-of-truth and math are GGML's native IQ blocks, and a byte-expanded cache would have its own measured cost.

These sources offer design patterns but do not show that a decoded cache beats the current kernels on this host. No external format conversion, quantization-quality claim, speedup estimate or near-zero quality-loss claim is made.

## Evidence boundary and next useful measurement

Use the already planned bounded observer after Main's serial suite: per-layer native `(GU,Down)` pair, actual CPU job `nt`, expert identity only in a bounded transient counter if permitted by that observer, routed rows, kernel path, and decode-window/layer boundary. To make cacheability measurable without retaining route history, count same-expert reuses per layer in a bounded histogram and track how many fall within the proposed cache lifetime/capacity. Then compare the native baseline to an opt-in bounded decoded-block cache on synthetic legal blocks first and the actual seven format pairs only where `nt=1` has material exposure. Keep packed model bytes, derived-cache capacity, bytes converted, hit ratio, worker CPU time, wall time, actual task rows and completion counts separate. Any measured win needs repeated clean process samples and complete-request decode evidence beyond run variation, plus numerical and continuation-quality gates. Prefill and GPU paths are outside this candidate's inference.
