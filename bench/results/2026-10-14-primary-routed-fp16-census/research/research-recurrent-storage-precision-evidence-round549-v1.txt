# Recurrent-state storage precision evidence for Strata's GDN path (R549)

Date: 2026-10-15 JST. Read-only source and literature research; this report is the sole write. No product source, tests, build, GPU/profiler, process/service, reset/cleanup, Git mutation, model blobs, or private run artifacts were accessed. The excluded `B/prefill-gemm-only-contract-root-v1/record.json` was not opened. Main owns any implementation and validation.

## Finding

The evidence supports a narrowly scoped, exact-model FP16 and BF16 recurrent-state experiment. It does not support adopting a reduced state dtype or claiming negligible quality loss for Strata. In particular, the reported Qwen3.8 BF16 deployment evidence is a small, self-reported qualitative check, while a peer-reviewed-in-the-sense-of-primary-paper empirical study on other GDN models shows that FP16 and BF16 state storage can have materially different task accuracy despite the same 16-bit size. Separate decode and prefill tests are required because state rounding must happen at each recurrence update to reproduce the candidate behavior.

Persistent state is not interchangeable with a transient activation. A transient value is consumed and discarded; recurrent state is read, updated, and written repeatedly, and each stored rounding error becomes an input to future updates. A scratch-dtype or duplicate-output-store result therefore cannot qualify this proposal.

## Current Strata implementation and cost

Source identity is the file SHA-256 set below; the checkout's commit may advance as Main integrates concurrent work. Current code declares `SessionState::gdn_state` as `float*`; `session_init` allocates four bytes per recurrent-state and convolution-history value. Per-layer state geometry is 128 × 48 × 128 FP32 recurrent values plus 3 × 10,240 FP32 convolution-history values. Existing source review records 36 GDN layers and 12 QSA layers. This is 3 MiB recurrent state and 120 KiB convolution history per GDN layer, or 108 MiB + 4.22 MiB across 36 layers. If only the recurrent matrix were changed to 16-bit storage, its nominal allocation would fall by 54 MiB; changing the convolution history too would be a separate experiment and is not included in that arithmetic.

The SYCL recurrence loads state elements into FP32 registers, computes the serial update in FP32, and writes the recurrent matrix after processing its supplied token batch. The prefill kernel also accepts FP32 state. Therefore a real reduced-storage implementation needs an explicit round to the candidate storage dtype after every logical token update, then an upcast on the next read. Merely changing the allocation and casting once at the end of a prefill chunk would test a different, more favorable error process than decode. The current `float*` APIs and session snapshot/copy contracts also assume four-byte elements.

The recurrent matrix and convolution tail are distinct state objects. Keep convolution history FP32 during the first experiment so the comparison isolates recurrence-state storage. Keep the transient `y` output-store cleanup from R540 separate: its `y_h` output is already computed, and removing an unused duplicate FP32 write creates no new recurrent rounding. No repeated scratch carve or buffer-removal proposal is made here.

## Direct and adjacent empirical evidence

**DAMP, recurrent-state quantization for GDN/KDA.** The arXiv v2 paper (30 Sep 2026) directly studies recurrent-state storage and round-trips quantized values through recurrence updates. On Qwen3.6-35B-A3B, the six reported benchmark scores (AIME 2026, HMMT, IMO-Ans, GPQA-Diamond, MMLU-Pro, LiveCodeBench-v6) are FP32: 85.46, 57.57, 50.29, 81.97, 84.66, 86.95; FP16: 84.58, 55.82, 49.42, 82.13, 84.61, 86.80; BF16: 79.71, 54.97, 43.71, 81.66, 84.65, 84.10. On Kimi-Linear-48B, FP16 is also closer to FP32 than BF16 on average, while Kimi-K3's two reported math scores show BF16 close to FP32. This is evidence that (a) FP16 state can preserve quality on some GDN models and (b) BF16 is not interchangeable with FP16 or automatically safe. It is not Qwen3.8-Flash-Next or Strata validation; the authors also use calibration, reorderings, and a custom fused mixed FP16/INT8 representation for their larger compression result. The paper's 9.9-bit DAMP result is not evidence for plain 16-bit storage and should not be imported as a recommendation.

The paper explains the mechanism: each update quantizes the resulting state, and later transitions propagate prior error; decay varies by head/channel. It reports 36 calibration prompts, 1,024 input tokens and 4,096 generated tokens for its offline channel calibration, plus six downstream evaluation tasks. That is stronger than a one-shot tensor comparison but still a different model family/version and inference implementation. Source: https://arxiv.org/html/2608.27513v2 (especially §§3, 6.1–6.2 and Table 1).

**Qwen3.8 support in a different serving stack.** NVIDIA TensorRT-LLM's Qwen3.8 deployment guide exposes `mamba_ssm_cache_dtype` independently of attention KV dtype, with `auto`, `float16`, `bfloat16`, and `float32` options. This establishes that a production serving stack offers these formats, not that all have equivalent quality. Its guide targets Blackwell (and Hopper for the BF16 checkpoint), Linux, CUDA 575+, with multi-GPU minimums for BF16; it is not evidence for Strata's single-card SYCL implementation. Source: https://nvidia.github.io/TensorRT-LLM/deployment-guide/deployment-guide-for-qwen3.8-flash-next-on-trtllm.html#key-configuration-options .

**Qwen3.8 community deployment, bounded evidence.** A DGX Spark (GB10) vLLM deployment reports overriding the model-configured FP32 GDN state to BF16. With 512K YaRN, MTP-3, FP8 attention KV, up to eight streams, and three throughput repeats, the authors report decode +6.8% at one stream and +8.5% at eight streams; eight-stream step time falls 7.8%, and tokens/step stays 2.80. The report says only the eight-stream result clears its three-repeat ±5% bar. Quality evidence is five runs of 32K needles (15/15) and one four-turn continuation judged to recall every conversation element; the authors explicitly call it one night's ungraded evidence. Their README separately notes 95%-depth needle misses and that a small all-pass reasoning suite cannot detect finer drift. These numbers are useful as a candidate signal, not a Strata result: hardware, vLLM kernels, checkpoint/quantization, attention KV dtype, MTP and prompt workload differ, and the quality checks are too small to establish non-inferiority. Source: https://github.com/MiaAI-Lab/Qwen3.8-Flash-Next-Single-DGX-Spark/blob/main/README.md#bf16-recurrent-state-default .

**Adjacent recurrent-cache warning.** NVIDIA's Nemotron 3 Super report found on an early, different Mamba model/checkpoint that directly storing its SSM cache in FP16 while updating in FP32 increased generated completion-token counts by 36.95% on LiveCodeBench and 2.19% on SciCode, even with W16A16; in the W8A8 setting the increases were 40.27% and 2.70%. Their FP16 plus stochastic-rounding recipe reduced those differences substantially. The paper attributes risk to recurrent error accumulation and biased round-to-nearest casting. This is not GDN/Qwen3.8 evidence and must not be projected numerically onto Strata; it is an empirical reason to measure verbosity/termination and to record rounding mode rather than assuming a cast is harmless. Source: https://research.nvidia.com/labs/nemotron/files/NVIDIA-Nemotron-3-Super-Technical-Report.pdf, §4.3, Table 9.

**Architecture connection.** Qwen3.8-Flash-Next combines recurrent GDN state with periodic full-attention and QSA components. The architecture paper describes GDN as a content-updated fixed-size key/value matrix state and full attention as retaining direct token access. This makes recurrence precision and sparse/full attention retrieval distinct potential failure modes: state narrowing must be tested on both task reasoning and long-context retrieval, while comparisons must hold KV/indexer behavior fixed. Source: https://arxiv.org/html/2608.30320 (GDN recurrence and architecture sections).

## Recommended experiment, not an adoption decision

Run only after Main opens a serial implementation/validation window. Preserve the current FP32 path as the reference and make independent candidate builds or runtime modes for (1) FP16 storage with FP32 update math and round-to-nearest-even after every token, and (2) BF16 storage with the same update/rounding boundary. Do not combine formats, stochastic rounding, recurrent kernel remapping, convolution-history narrowing, transient `y` cleanup, weight/KV changes, or scratch changes in this test. If stochastic rounding is later considered, it is its own candidate with a recorded seed/policy and repeated seeds.

For both prefill and decode, compare after every token at selected checkpoints: recurrent state normalized RMS, p99/max absolute error, finite/overflow/underflow counts, GDN output error, post-GDN residual error, logits/log-probability difference, and the first point where greedy token selection changes. Include `T=1`, odd/tail batch sizes, short and chunked prefill, 4,096 and 8,192 chunks, multi-chunk continuation, and the actual full context boundary. In prefill, inject candidate-dtype rounding *inside* the serial loop per token; final-only chunk rounding is not parity for token-stepped decode. Restore the session snapshot after FP32 and candidate runs and continue decoding to verify that serialize/restore preserves each chosen state representation and its results.

Use the same pinned model/tokenizer/template, prompt IDs, routing/configuration, QSA/KV dtype, sampler, output budget, and host/device build for paired runs. Keep conv history FP32. Evaluate prompt classes that can expose recurrence drift—reasoning, code, long-document retrieval, long generation/termination and multi-turn continuation—at short, 32K/64K and, if claiming maximum-context support, exactly 262,144 input cells. Measure decode separately from prefill. Numerical agreement and first-logit checks are diagnostics, not a quality pass. Score held-out task outcomes, teacher-forced continuation log-probabilities, blind response comparisons, repeated-answer/verbosity/termination anomalies and retrieval facts; retain per-prompt and per-category results.

The R540 24-prompt/1-percentage-point example is only a gross-regression screen. In a 24-item binary sample one item changes the total by 4.17 percentage points; with zero harmful pairs, the one-sided 95% upper bound on harm incidence is about 11.73% under an independent-trial assumption. About 299 independent zero-harm pairs are needed for that upper bound to fall below 1%; prompts/categories are not naturally IID, so cluster/report by task and context and do not treat correlated tokens as independent observations. Choose a non-inferiority margin from repeated FP32 baseline noise, predeclare it, and use prompt-level paired confidence intervals. A small suite with all passes cannot rule out uncommon or category-specific failures.

Only after the exact-model quality gate passes should Main measure the memory/performance benefit. Record actual session allocation and free-memory high-water, state read/write traffic, and paired decode throughput/latency on the target card with uninstrumented repeat samples. FP16/BF16 allocation saves 54 MiB for the recurrent matrix under the source geometry, but actual process peak and throughput changes need measurement. A smaller persistent-state allocation may enable a device-memory fit or reduce decode traffic; it does not reduce transient prefill scratch automatically.

## Decision

Keep Strata recurrent GDN matrix and convolution history FP32. The literature identifies a plausible persistent-state bandwidth/capacity opportunity and shows a model-dependent difference between FP16 and BF16. Qwen3.8 deployment support plus a community check is enough to justify an isolated, serial exact-model experiment, but no available evidence qualifies a storage dtype change in Strata. Keep R540's duplicate transient `y` store question separate and do not infer recurrent-state safety from activation/weight/KV precision results.
