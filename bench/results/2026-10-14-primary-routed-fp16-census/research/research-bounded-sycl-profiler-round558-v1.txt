## Result

There is a concrete, in-process UnitRace control path. UnitRace's current README explicitly documents changing `PTI_ENABLE_COLLECTION` with `setenv(..., "1", 1)` and then `setenv(..., "0", 1)` inside the application; only events in that region are collected. This is not a launch-time-only variable. The profiler must be launched with `--start-paused` for these in-process changes to take effect. The documentation also says `__itt_pause()` / `__itt_resume()` are alternatives, and take precedence if both mechanisms are used. The project does not currently use ITT pause/resume. For the documented environment-toggle path, the verifier needs no PTI header, PTI library, or extra link dependency: the implementation hook calls the process environment API already provided by the C runtime. UnitRace itself supplies the observer.

This resolves the command-only gap in R555: a command can start UnitRace paused, but a source hook must turn collection on and off around the selected verifier call. A suitable diagnostic command shape is:

```sh
PTI_ENABLE_COLLECTION=0 unitrace --device-timing --kernel-submission --device-timeline \
  --start-paused --output-dir-path <private-bounded-dir> <compiled-verifier> <same-args>
```

The exact executable and arguments must come from Main's compiled verifier recipe; they are not established by this source review. Do not add graph profiling or new SYCL waits. Set collection off on every normal and error exit once the selected window's existing work has drained. A process-wide one-shot selector should match one configured window (for example, target T and position), and emit one compact begin/end label with that identity and outcome. The profiler's `--start-paused` option is essential; without it the README says the environment control has no effect and the whole process is traced.

## Where the hook belongs

`Verifier::run(T, ..., pos0, ...)` validates the window, captures the window and commit graphs, stages host inputs, then submits the first segment at `src/core/verify.cpp:1204–1272`. The selected collection interval should begin immediately before that first `graph_launch_with_completion()` call, after `capture(T)` / `capture_commit()` and host staging have finished. It should end after the existing `cs_` and `copy_` drains succeed at `:1390–1401`, before sampling and ordinary host post-processing. An RAII guard may turn collection off on early error returns without adding a synchronization; its destructor must only restore the environment control and label the failed/incomplete window. Keep all existing layer completion waits, copy drains, window drains, and commit ordering unchanged.

One outermost-call guard is needed if a logical window recurses through `next_->run()` for layer-split verifier stages (`:1439–1444`). The collection state is process-wide: nested stages should not toggle it independently. A bounded first check should use a single-stage verifier when available, or explicitly define the selected logical window as the full nested stage chain. In the multi-stage case, the outer guard should remain enabled until all nested stage runs return; otherwise it would omit later stages. Existing commit is a separate graph launch (`:1630–1665`), so disabling at the completed run boundary excludes commit. If commit attribution is later required, it needs a separately named collection window and must preserve its existing asynchronous semantics.

Before selecting the diagnostic replay, ensure the target T graph is already captured for every stage (or record capture as a separately labeled first-window condition). Window graph creation is lazy: `capture(T)` returns early only when `segments_[T]` is already populated (`:1044–1067`). The simplest clean diagnostic selector is one warmed, previously captured T=1 replay, bounded to a single `Verifier::run`; the source does not prove that every higher-level caller can issue an isolated T=1 call without additional surrounding work. The hook must not force a new barrier, drain, or device-wide wait to delimit collection.

## What the current graph mode contains, and what UnitRace may see

The supplied/counted configuration is `STRATA_SYCL_VERIFY_NATIVE_CAPTURE=0`. In source this selects ordinary `cudaStreamBeginCapture`, not native recording (`verify.cpp:59–70`). Compat constructs an experimental `command_graph` with an empty property list, records and finalizes it, and on the ordinary path retains its SYCL graph nodes via `get_nodes()` (`src/sycl/compat.cpp:20–45, 438–466`). Replay is submitted by `h.ext_oneapi_graph(graph->value)` (`:473–510`). Native recording uses `enable_native_recording` and does not expose those nodes through the compat node listing (`:542–552`).

UnitRace documents Level Zero device/kernel timing, submission intervals, and timelines, and supports Intel GPU applications. This makes replayed kernels a plausible target for its Level Zero activity observer, but the UnitRace documentation does not promise per-node enumeration for this exact DPC++ experimental `command_graph` replay path. Source graph-node visibility inside Strata is not itself proof that UnitRace will report each node as an individual device kernel. The public PTI SDK separately documents graph support beginning with SDK 1.1.0, with Level Zero native graph support requiring icpx 2026.1.1 and runtime 1.15.39122+12; it describes SYCL graph support with additional environment settings for its legacy graph path. That is adjacent SDK evidence, not a guarantee about UnitRace's own adapters or this compat replay. Do not add those settings to this project configuration based on that note.

The committed runtime hints are DPC++ 2026.1.1 and Level Zero driver `1.17.39395+14` in `docs/SYCL_STATUS_2026-10-03.md`, `docs/sycl/B570_OPERATIONS_PROBE.txt`, and R545. `docs/sycl/INSTALLED_HEADERS.tsv` pins the installed DPC++ command-graph header. These are committed environment/build clues, not proof of the binaries loaded by a later verifier process. There is no committed PTI/UnitRace version or adapter receipt in the reviewed census reports, so exact local UnitRace graph coverage remains unverified.

Admit the eventual diagnostic only after a bounded smoke check confirms that this installed UnitRace/runtime reports device kernels from the normal (non-native) graph replay and that the selected window's events are present through its end. If the replay collapses to a graph/command-list envelope or no node kernels appear, report that result as a profiler limitation; do not infer per-node timing from Strata's `get_nodes()` output. PTI kernel events still need source-backed attribution, and their summed durations need not equal the graph/window wall interval.

## Public control API and integration boundary

For this UnitRace run, the applicable public control is the documented `PTI_ENABLE_COLLECTION` environment control coupled to `--start-paused`. It is an in-process mutable environment setting; the UnitRace tool owns the tracing callbacks. No `pti_view.h`, `libpti_view`, or ITT linkage is required for this route. The value should be explicitly initialized to `0` in the launch environment and toggled only around the selected interval.

A different option is to embed Intel's PTI View SDK. Its public functions are `ptiViewEnable(pti_view_kind)` and `ptiViewDisable(pti_view_kind)`, declared in `pti/pti_view.h`; the SDK's CMake package example links `Pti::pti_view`. SDK README version 0.7.0 introduced local collection, whose documented runtime requirement is Level Zero 1.9.0 or newer. Before `ptiViewEnable`, the SDK requires callbacks to be defined and registered with `ptiViewSetCallbacks`. This is a separate linked-library integration, not the minimal UnitRace environment toggle; avoid combining it with UnitRace collection in this diagnostic unless a later design explicitly requires an embedded collector. Current SDK docs are marked draft/active development, and no local SDK version is pinned in the committed evidence.
