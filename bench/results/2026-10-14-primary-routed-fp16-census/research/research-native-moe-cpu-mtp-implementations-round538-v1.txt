# R538 — CPU MoE and hybrid MTP implementation references for the Zen 3 path

Date: 2026-10-14 JST. Read-only implementation research for current `feature/sycl`. Sole write: this report. No product/Git edits, builds, tests, GPU/profiler work, process/service/reset/cleanup, live-run reads, or model-blob access. I excluded the prohibited record and broad private session/environment data. Main owns the benchmark boundary; this report makes no runtime or speed claim.

## Finding

The most relevant reusable mechanisms are already partly present in root Strata: each verifier dispatch quantizes each activation row once, deduplicates CPU misses by expert across the actual window, collects routed rows into `ExpertJobMulti.nt`, and runs shape-aware packed kernels through a persistent worker pool. For the supplied canonical screen, use the corrected mode: MTP pack loaded, `--spec 4 --no-spec-split --suffix-draft 0`. `spec=4` is a capacity; actual dispatch `T` and each expert's `nt` vary by window. R536's archived ledger is explicitly gated to no-MTP/actual-NT1, so it cannot be reused unchanged. Its row expectations and `layers × emitted` coverage assumption do not qualify MTP.

No external implementation establishes a faster implementation for this Ryzen 5 5600X, its IQ3/IQ2/IQ4 mixed expert pack, or this exact MTP route. The immediate high-value step is to count actual `T`, unique CPU jobs, each `nt`, type pair, ownership, pool task fill, and per-role service within completed windows. Only then choose between pool scheduling and a format-specific kernel. The CPU FMA peak and isolated bandwidth figures do not identify CPU decode as the bottleneck.

## Current source contract

The configured current source is root `src/core/expert_source.cpp` and `src/kernels/cpu/{native_expert,pool}.cpp`; `cmake/sycl_backend.cmake` selects these TUs. The relevant contracts are:

- `expert_pool_dispatch_multi` validates actual `n_tok` against `MAXT`, quantizes each input token once (`expert_source.cpp:1869–1885,2024–2031`), walks the actual `n_tok*k` entries, deduplicates each expert's CPU-miss routes, and records the corresponding activation/output pointers into one job with incremented `nt` (`:2033–2085`). It also prefetches the unique miss list. This already coalesces repeated expert routes within a verify window; it does not coalesce across autoregressive windows.
- The native pool maps flattened expert-row ranges to `3 * (workers + host participant)` tasks; GU, activation quantization, and Down are distinct pool phases (`pool.cpp:663–691`). MTP's distinct missed experts may be fewer than workers and each job may have only one activation row, so the fixed task count can be underfilled. This is a question for observed `nt`/task counts, not proof of a pool defect.
- `native_gu_rows` chooses multi-token kernels at `nt >= STRATA_IQ_MT_MIN` (default 2), with AVX-512 then AVX2 dispatch; otherwise it uses GGML `vec_dot`. Strata's optional exact NT1 GU path is separate and limited by actual supported type/ISA. `native_down_rows` has the IQ4_NL mult-token path only for type 20; other down types use fallback unless their explicit kernel path applies (`native_expert.cpp:79–163`). The source documents that multi-token reductions can round differently from NT1, which can make greedy output depend on MTP window contents. Keep thresholds, GU/Down and format/ISA dispatch independent.
- Current host counters expose total `multi_misses`, `multi_entries` and cumulative plan/actq/jobs/run clocks, but no serialized per-window/per-format/per-`nt` histogram (`expert_source.hpp`, `generate.cpp:5882–5900`). The decode timing print is an aggregate average and its intervals overlap (`generate.cpp:6018–6027`).

## Ranked mechanisms from external implementations

1. **Keep expert grouping at the actual verify-window boundary; measure its fill before changing it.** The CPU MoE kernel in vLLM's [`csrc/cpu/sgl-kernels/moe.cpp`](https://github.com/vllm-project/vllm/blob/main/csrc/cpu/sgl-kernels/moe.cpp) sorts routed token rows by expert and uses per-expert offsets, tiles, and a BRGEMM path when average rows permit it. This is a useful comparison for how to dispatch grouped expert work, but it targets PyTorch CPU quantization methods and larger batch shapes. Root Strata already groups rows by expert at each `expert_pool_dispatch_multi`; its MTP rows are at most the actual verify width and may be sparse. First report unique CPU-miss experts and `nt` distribution, including jobs by format. If eligible batches are commonly `nt=1` or very few jobs, test the existing exact NT1 or task-count gates in a narrow format/role fixture instead of transplanting a large fused expert operator. Require per-row CPU parity and full output/logit checks; preserve the GGML reduction contract where required.

2. **Overlap CPU misses with independent GPU work only where the existing schedule leaves a visible tail.** SGLang's [`kt_ep_wrapper.py`](https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/layers/moe/kt_ep_wrapper.py) demonstrates the simple pattern: submit CPU expert work asynchronously, run GPU experts, wait for CPU completion and merge. Its CPU/GPU expert layout and CUDA implementation differ. Strata already classifies expert owners and submits the GPU plan/fetch before CPU native jobs in `expert_source.cpp`; it also has verifier event/worker handoffs. This is an architectural reminder to preserve useful overlap, not a recommendation to add another queue or wait. SGLang's [CPU backend roadmap](https://github.com/sgl-project/sglang/issues/8281) separately labels sequential CPU/GPU offload and parallel pipelining as work items; roadmap entries are not measured results. Measure same-window CPU service, GPU work, waits and completed dependencies with an uninstrumented paired reference before considering any schedule change.

3. **Check expert-weight locality only after counting repeated IDs and file/RAM reads.** The llama.cpp maintainer/user RFC [GPU cache plus CPU-miss hybrid execution](https://github.com/ggml-org/llama.cpp/discussions/24528) and the later [persistent expert-slot pool RFC](https://github.com/ggml-org/llama.cpp/discussions/28248) describe keeping selected hot experts in GPU slots while CPU computes misses; the latter reports a different CUDA/RTX setup and is a discussion branch, not upstream Strata evidence. Strata already has GPU expert cache, CPU-resident/file tiers, owner classification, and per-window GPU hit versus CPU miss paths. A new cache/pool is only justified if target counters show recurring misses to hot experts plus nontrivial source or CPU service; routing skew from another model cannot predict this screen's hit rate. If explored, preserve model-layer/format identity and residency leases, compare equal cache/RAM budgets, and verify miss fallback and eviction/refill correctness.

4. **Consider ZenDNN grouped matmul only as a kernel design reference, not a direct replacement.** AMD's [ZenDNN support page in llama.cpp](https://github.com/ggml-org/llama.cpp/blob/master/docs/backend/ZenDNN.md) lists Zen 3 support for MUL_MAT/MUL_MAT_ID and documents that Q8_0 is the quantized format supported there; other formats fall back. AMD's [`group_matmul_direct` documentation](https://github.com/amd/ZenDNN/blob/main/docs/operator/low_overhead_operator/lowoha_group_matmul_operator.md) describes running independent GEMMs together, fusing gate+up activation and an optional MoE reduction. This suggests a bounded per-layer batched-dispatch experiment, but the Strata pack uses mixed IQ3/IQ2 GU and IQ4_NL/Q2_0 Down. Converting it to Q8_0 changes storage, quantization error and per-token memory traffic. MTP4 is not a large prompt GEMM. Do not import the backend or infer that its documented group speedups transfer to this model. A useful first experiment is a host-only grouped-dispatch fixture with native blobs and exact format math; any Q8 conversion needs its own quality/bytes/service comparison.

5. **Treat ISA-specific packed kernels as a targeted option, with exact route and numerics gates.** llama.cpp's current CPU type traits dispatch IQ3_S/IQ3_XXS/IQ2_S to quantized dot functions and its [AVX2 CPU quant code](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cpu/arch/x86/quants.c) is an implementation reference. A current [Qwen3.8 Vulkan MTP batching report](https://github.com/ggml-org/llama.cpp/issues/25356) describes dispatch thresholds/cliffs around speculative verify batch sizes for that model, but on an AMD iGPU/Vulkan path; it supports recording exact actual `T`/dispatch sizes, not a Zen3 CPU speed claim. Strata already has AVX2 multi-token IQ kernels for Zen 3 and separate exact NT1 GU support. Only consider a new ISA kernel if request-local evidence shows a material supported `(role, type, nt)` population. Compare per-format/role against the exact baseline, include compiled ISA and dispatch proof, preserve bounds/tails, require scalar/reference parity, and check end-to-end MTP output acceptance and model quality. Avoid blanket compiler flags or type conversion.

Activation work is a low-priority independent check: input `native_quant_act` is already once per token/layer and reused by every expert job in that window; `native_quant_h` is generated per expert's GU output, so it is expert-specific. Only profile these separately if plan/actq counters show material service. Reusing the input quant across jobs again would duplicate work already avoided. A down-activation reuse across separate experts would be incorrect because each expert's hidden output differs.

## Main-owned serial measurement and validation plan

After the user benchmark boundary closes, first consume its existing request-level MTP offered/accepted/window data and formal individual samples; do not inspect or intervene in the active session. Then, if CPU attribution is still needed:

1. Adapt the request-local route and service ledgers from R536 to accept actual MTP mode. Keep a single bounded request identity and close footer. Record each completed verifier window's actual `T`, offered/accepted drafts, each layer's CPU/GPU ownership and cache route, unique CPU-job count, `nt` histogram by GU/Down source format, pool task/worker counts, per-role CPU thread/wall service, activation quantization, host wait and existing verifier timing deltas. Preserve the existing commit/rollback and row association. Count only observed completed dispatches and join/cross-check counters; do not derive rows from `emitted × layers`, and do not infer width from `spec=4`.
2. Keep observation default-off, host-only and output-on-close. No new SYCL events, queue, copies, waits, device branch, or per-entry log output. Preserve `--spec 4 --no-spec-split --suffix-draft 0`, MTP pack, client/request hashes and all settings. The ledger must identify the actual `T` and job `nt`, including the first one-token window and boundary/cancellation cases.
3. Main validates the fixtures, source build and short exact-mode off/on request serially. Require normal close, stable observer coverage, unchanged greedy result where the same route/math guarantees it, exact per-layer/per-window sums, owner/format totals, actual worker task totals, and a fresh fault check. The ledger-on timings quantify observer effect only.
4. If coverage shows enough jobs in a specific `(format, role, nt)` branch, run one host-only kernel fixture with real packed-format weights, activation/output boundary cases, several jobs and task counts, and actual compiler/ISA dispatch. Preserve output and downstream router/acceptance behavior. Then run clean alternating paired MTP4 complete requests for any candidate; report emitted tokens, offered/accepted drafts, decode wall, prefill separately, and individual samples. If changing split or `STRATA_IQ_MT_MIN`, treat altered reduction/order and row grouping as a numerical/quality factor, not just scheduling.
5. If a pipeline candidate is evaluated, verify dependency overlap in a bounded trace after clean baselines and preserve existing wait/lease/fault semantics. Do not compare profiled throughput. No candidate is adopted until repeated end-to-end results show gains beyond run variation and correctness/quality gates pass.
