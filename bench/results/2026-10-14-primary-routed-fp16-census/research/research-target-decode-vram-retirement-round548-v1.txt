# R548 — target decode workspace retained through batched prefill

Date: 2026-10-15 JST. Read-only source and primary-reference audit of decode-side workspace ownership while the server runs its separate batched prompt path. The target is the supplied MTP/spec-4, split-off, suffix-off, no-borrow configuration, normal verifier graph recording, prefill same-queue enabled, with a 262,144-cell context and 4,096/8,192-token prompt chunks. I did not inspect current run artifacts, model blobs, private session/environment data, the excluded `B/prefill-gemm-only-contract-root-v1/record.json`, build/test/GPU/profiler/process/service/reset/cleanup state, or Git; I made no product changes. Main owns validation and the active run.

## Finding and disposition

The verifier's device arena and its executable window/work/commit graphs are decode workspace, separate from the `SessionState` whose GDN recurrence, QSA KV/indexer state and PLE history the batched prompt path must advance. The source's ordinary window graph is lazy-captured on first verifier run; at later request boundaries, however, it may already hold graph executables referring into the arena. The serve path keeps its `Verifier` object alive around per-request batched prefill, so those device bytes and graph objects remain resident while `Prefill` allocates its chunk workspace.

A precise candidate for a future pressure-managed path is to retire and rebuild the verifier *workspace as a unit* around a successful long-prompt prefill: at the incoming request boundary, first require the prior verifier commit to complete; before prompt work, detach the drafter's borrowed `final_R_all()` input using the existing MTP bind protocol; destroy the verifier's executable window, work and commit graphs; then release the device arena. Keep `SessionState`, its model-layer state, model/native weights, the expert cache/residency data, the verifier host plan and any stable host-side sink handles. After prompt completion and the existing `Prefill::reset()`, rebuild the same verifier carve from `(g, ss, hits, head, max_t, layer range)`, recapture on the next decode window, and rebind any required residual pointer before that window. This is reconstruction of scratch and graphs, not session save/restore or model reload. It needs an explicit reset/rebuild API and Main review; none exists today, and the separate R547 drafter audit must confirm the exact borrowed-pointer protocol before an implementation.

This proposal covers only the target `Verifier::arena_` and the executable graphs that refer into it. It does not retire or rebuild `MtpDrafter` storage or its graphs; R547 is the separate audit for those resources and should govern any MTP-side lifetime decision. The two candidates must not be combined into a blanket MTP arena release.

The candidate is conditional on healthy successful completion. `wait_commit()` alone does not retire a prior window's copy callbacks; the successful `run()` path already synchronizes both verifier and copy queues, but a reset routine should still check its own retirement results before freeing anything. R542's sticky-error caveat remains: compatibility `attempt()` can return on a sticky runtime error before executing a requested wait, and `cudaGraphExecDestroy` then keeps graph ownership uncertain. A failed sync/destroy/free must stop retirement and keep the referenced storage alive. This is not a teardown-safety claim.

The target `SessionLoopScratch` is a separate, small pinned-host allocation rather than verifier VRAM. Its `y_miss` is `K * n_embd` floats (about 100 KiB for K=10 and n_embd=2,560), alongside one event and a small SYCL add-hits flag. Its ordinary consumers are `session_loop` and `session_run_token`; the target MTP verifier path uses `Verifier::run` and `drive_pool_multi`, and the batched prefill uses `Prefill`, not this scratch. In the target MTP configuration, `captured_post` is only supplied for `spec == 0`, and SYCL's whole-token graph capture refuses the SYCL build, so the target path does not capture this scratch pointer into those alternatives. A future config-aware server can avoid initializing it for MTP plus batched prefill, or release only its buffers before the prompt begins. `free()` also restores the serving thread's affinity, so freeing mid-session changes a separate property; a split buffer-release operation would have to retain affinity if that is still required. In any case, this only saves host-USM/pinned host storage, not a meaningful portion of device VRAM.

`NativeHitGraphs` is likewise a conditional decode cache, not model state. It owns one pinned host plan and the unique executable graphs for native hit format keys; its `layers` list may alias those unique executables. The graph nodes read that host plan and write the `ExpertDispatch` hit output through captured device pointers. Current MTP serving invokes `expert_pool_dispatch_multi` through `drive_pool_multi`; the `NativeHitGraphs` replay is only called by `expert_hit_run`'s ordinary per-layer hit path. Thus if native hit graphs were prepared by the setup gate, they are not consumed by the selected MTP verifier/prefill path and are a candidate to omit or retire for that configuration. Do not free `ExpertDispatch` device buffers or residency/cache pointers as part of this object-only retirement: their broader ownership and the cache remain decode inputs. If a later path needs `expert_hit_run`, recreate the graph bundle with `expert_hit_prepare_graphs()` after ensuring its inputs are complete. The host plan itself is only `20 * cap + 8` bytes by its source formula; runtime executable/driver cost is not exposed as a C++ object size.

## Geometry and accounting limits

At `max_t = 4`, most of the verifier arena's arrays are O(T) and its decode-only QSA score array is O(T * max_blocks), where `max_blocks = max_cells / idx_block + 2` (`verify.cpp:260–266, 326–384`). For the SYCL QSA shape with `idx_block = 4`, `max_cells = 262,144` gives 65,538 blocks; the four-row float score array is 1,048,608 bytes, about 1.0 MiB. The context-sized QSA KV/indexer state is in `SessionState`, not the Verifier carve, and is required by prompt and decode. Captured graph/internal backend resources are separate from this `Bump::used` count.

The prompt arena's row buffers and its largest per-chunk scratch region are carved using chunk `T`; moving from 4,096 to 8,192 rows increases row-proportional terms substantially (roughly twofold where linear) while fixed scratch, rings, optional paths and loan sizing make the total non-exactly-linear. Under no-borrow, Prefill requests its own buffers; after its synchronized reset those buffers are released. The R540/Main correction remains the authority on exact carve-vs-`bytes_needed` accounting, so this review does not repeat the known `xn`/`grs` discrepancy or the `Dm`/`y` region conclusions. A resource release can improve the starting free budget, but it cannot promise that a 4,096- or 8,192-token chunk fits: actual availability also depends on loaded weights/cache/session, native head, runtime/driver allocations, and other consumers.

`Verifier` logs its source `Bump::used` MiB at initialization, but the source-only pass did not read a run log or allocate anything. The executable graph wrappers expose no byte accounting for implementation/driver command buffers, kernels/code, internal event pools, residency or caching. Destroying a C++ wrapper proves only that the adapter requested destruction; it does not prove a specific amount of VRAM or system RAM returned to the application. The official graph extension distinguishes graph-owned allocations from raw pointer operands and describes raw storage-lifetime rules as future direction; Strata must continue to enforce its own raw-pointer leases by keeping captured pointees alive through successful graph retirement.

## Rebuild inputs and safe ordering

For an eventual workspace API, the retained inputs are the same live `ModelGeometry`, `WeightTable`, `SessionState`, `VerifyHits` pointers/slot metadata, `NativeHead`, `max_t`, and stage range. The carve also recomputes context-dependent `max_blocks_`, selection width and attention scratch from the still-live session geometry. Rebuilding does not need to re-run prompt computation, restore a saved session, recreate the weights or cache, or zero `SessionState`; it must zero/reinitialize only the temporary verifier buffers that `init()` currently zeros. Re-capture must happen after those new pointers exist. Keep `GpuPlanSink` host members stable, or explicitly rebind `ExpertDispatch::plan` if the whole `Verifier` is replaced.

Proposed boundary ordering for the candidate, not implemented: (1) complete `wait_commit()` for the previous request and ensure the prior successful `run()` has drained both verifier queues; (2) use the existing drafter binding protocol to clear any borrow of `final_R_all()`; (3) check graph-exec destruction for every T and the commit graph, then free the arena only when all destroys and queue waits succeeded; (4) run batched prefill and its normal completion/refill path; (5) let `Prefill::reset()` release its own buffers; (6) reconstruct verifier arena and rebind as required before the first decode window. On an error or sticky runtime state, do not take steps 3–6 as ordinary retirement: preserve storage and use the existing engine failure handling.

This is a design candidate for Main review, not an intervention or adopted memory policy. It avoids blanket graph offload and excludes all persistent sequence/model state. Before any implementation, R547 must settle MTP residual-pointer users and the exact point at which rebind is required; then a host-only resource lifecycle test and Main-owned GPU equivalence/fit validation can decide whether the reconstructed workspace is worthwhile.
