## Current MTP verifier and CPU dispatch flow

In root `src/program/generate.cpp`:

- `Options` defines `--spec` as verify-window capacity and `--mtp` as the draft runtime (`:372-380`); suffix lookup defaults on but `--suffix-draft 0` selects MTP-only proposals (`:432-438`). `--no-spec-split` keeps `spec_split=false` (`:395`, parser `:1268-1269,1329`). The serve validation requires `--spec`, `--mtp`, and prefill (`:4261-4266`), then binds the loaded drafter to the verifier's residual stream (`:4700-4703`). With this command, `S=4`, `S_mtp=4`, and `suffix_draft=0` (`:5232-5236`); the screen's actual request counters, not this arithmetic, remain authoritative for run results.
- Each GEN request enters decode at `d0` after the prompt has been read, with the last prompt token pending as `window[0]` (`:5860-5881`). `first_window` forces `T=1` (`:5873-5875,5903-5908`); it verifies that final prompt token and emits the first generated token. The request then calls `mtp.draft(T, ..., a, ...)` after each committed window unless EOS or the output cap ends the request (`:5981-5985`). On later iterations, `T` is chosen from `S_mtp` (or the configured probability floor) and suffix mode is disabled (`:5902-5919`). Thus actual verifier `T` is a per-window value, at most 4 for this command, with a first `T=1` window; it is not `--spec` applied as the CPU job row count.
- `Verifier::run(T, ...)` validates `1 <= T <= max_t_`, stores all T tokens, runs the captured T-row window, and invokes the pool callback once per layer in the unsplit path with `n=T` (`src/core/verify.cpp:1204-1267,1282-1387`). SYCL completes the window's segment and copy-stream work before returning (`:1392-1404`). A failed callback/window is not a completed verifier window (`WindowScope` marks it failed at `:1220-1231`).
- `drive_pool_multi` forwards `n_tok` unchanged to `expert_pool_dispatch_multi` (`generate.cpp:712-718`). That function validates actual `n_tok` against `MAXT`, quantizes T activations, classifies each routed entry by owner, deduplicates CPU misses by expert ID, and appends each CPU-owned route row to that expert's `ExpertJobMulti`, incrementing that job's actual `nt` (`src/core/expert_source.cpp:1869-1897,1996-2041,2042-2089`). `ExpertJobMulti::nt` is a per-expert row count with arrays bounded by `MAXT` (`include/strata/kernels/cpu/pool.hpp:55-64`). It can be 1..T for this model's unique top-k routes, but remains a different quantity from dispatch T: GPU-owned routes do not enter CPU jobs, and multiple token rows may coalesce into one CPU job.
- `run_split_multi_native` processes `n` unique CPU jobs in bounded batches, with GU, intermediate activation quantization, and Down phases (`src/kernels/cpu/pool.cpp:663-692`). A zero-job dispatch returns without pool phases (`:663-664`) but still represents a real layer/window dispatch. Do not infer a missing verifier callback from zero CPU jobs.
- After a successful `ver.run`, the caller computes accepted-prefix length `a`, commits `a+1` tokens, adds `T-1` offered and `a` accepted drafts, then emits up to `a+1` outputs, stopping on the output cap or first EOS (`generate.cpp:5944-5977`). `Verifier::commit(n_keep)` keeps exactly the first `n_keep` rows and replays/repairs state (`include/strata/core/verify.hpp:15-20,124-133`; `verify.cpp:1630-1665`). Rejected draft rows are `T-(a+1)`; the graph restores/overwrites state for them. The final async commit is waited before request close (`generate.cpp:6008-6013`; `verify.cpp:1667-1675`).

The engine's accepted/offered totals (`generate.cpp:6152-6159`) are proposal-position counts, not verifier-window counts or output counts. R527 explains the same boundary: first `T=1` contributes zero offers; aggregate accepted/offered can include verified accepted candidates that were not emitted after a terminal EOS or output cap. `--suffix-draft 0` makes these proposal positions MTP-only for this requested mode, but does not make emitted, accepted, committed, and verified counts interchangeable.

## Correct coverage arithmetic for this mode

For each request and each successful verified window `w`, record actual `T_w`, accepted prefix `a_w` with `0 <= a_w <= T_w-1`, successful commit `nkeep_w`, and actual emitted outputs `emit_w`:

| Quantity | Required observed formula |
|---|---|
| Completed windows `W` | Count `ver.run` calls that returned success and whose commit also returned success. Preserve attempted/partially dispatched windows separately on failure. |
| Verified rows `R` | `sum_w T_w`. Per layer, one successful dispatch per completed window; each layer's dispatch count must equal `W` and its actual T-row sum must equal `R`. |
| MTP positions offered `D` | `sum_w (T_w - 1) = R - W`. This includes the first T=1 window as zero. |
| MTP positions accepted `A` | `sum_w a_w`, and `0 <= A <= D`. |
| Rolled-back/rejected draft rows `X` | `sum_w (T_w - (a_w+1)) = D - A`. This is work verified and discarded by the accepted-prefix commit; do not call it emitted-token count. |
| Committed input rows `C` | `sum_w nkeep_w = sum_w(a_w+1) = W + A`, only when every counted window's commit succeeded. |
| Emitted completion tokens `E` | `sum_w emit_w = produced_n`, from actual T outputs written. Require `0 <= emit_w <= nkeep_w`; generally `E <= C`. Record `C-E` as committed-but-unemitted terminal rows when positive, which can occur at EOS or the max-new cap. |
| CPU jobs and rows | Per layer/window, CPU unique-miss groups equal jobs; sum of their job `nt` values equals CPU-owned routed entries. Keep job count, CPU rows and dispatch T separate. |
| Route entries | For each layer/window, owner-partitioned route entries sum to `T_w * k` (here `k` is the actual routed experts per token), if the path is single-device with no peer/remote owner and the route callback completed. |

Do not set a complete MTP receipt from `layers × emitted`, `layers × accepted`, or a dispatch NT=1 requirement. For normal `length`/EOS `stop` close, completeness requires successful full-window dispatch and commit coverage, every layer's observed `(count=W, row_sum=R)` match, route/CPU cross-checks, bounded/correct counters, and exact agreement between source window totals and emitted DONE totals where semantics overlap (`D/A/E`). Any failed window, failed commit/wait, cancellation, invalid input/format/owner, overflow or missing callback remains incomplete while retaining its observed prefix. An expected value can detect missing observations; it cannot fill them.

`Verifier::windows`, `Verifier::ms_*`, and `ExpertDispatch` counters are cumulative and may include prompt short-read or previous request work. Current `generate.cpp:5884-5900` already snapshots verifier and dispatcher deltas at decode entry, but the new ledger must also start its request-local `W/R/D/A/X/C/E` accounting at `d0`. The final prompt token's first T=1 verifier window belongs to this decode window count; earlier prompt work does not. `decode_ms` is measured before the final `wait_commit`, so record its existing interval separately from the final commit-wait status and close only after `wait_commit` succeeds.

### Bounded storage and output

Old route state is `[64 layers][4 owners][8 actual-job-nt bins]` (2048 buckets), with a 128 KiB static state cap and 512 KiB output cap. MTP mode needs to distinguish actual verifier T from per-expert job nt. A conservative target-specific shape is `[64][T=1..4][4 owners][job-nt=1..8]`, 8192 buckets. At five 64-bit values per bucket, raw bucket storage is 327,680 bytes (320 KiB), before format/window/footer metadata. Raise and statically assert a state budget of at least 384 KiB; 512 KiB gives headroom. Existing output can grow to thousands of layer/T/owner/nt rows; raise the explicit cap to 2 MiB and emit only nonzero aggregates plus fixed per-T acceptance/commit/emission histograms. Never emit one row per expert or per request window.

The host service observer's 128-worker bound can remain fixed. Add only fixed per-layer/per-T dispatch coverage and request-level window outcome histograms; recompute its complete-state size and output budget, with a suggested 128 KiB request state and 128 KiB close-output cap. Keep `NativeServiceBudget`'s own slot/task envelope separately bounded. A request may have up to its admitted `max_new` windows if every round accepts zero, so do not allocate per-window vectors proportional to output length; use checked u64 aggregates/histograms and a fixed terminal-window summary. For any future max-T above 4, use an explicit new admission gate and recalculate these bounds rather than silently using this spec-4 receipt format.

## Scope and lifetime contracts

- Bind the request ledger after prompt processing at the existing decode entry, then set the active window number and expected upper bound before each `ver.run(T, ...)`. Pool dispatch is synchronous within the SYCL verifier handoff and receives actual `n_tok`; update aggregation only from the existing host callback. Caller-side outcome fields `a`, `nkeep`, `emit_w` are available only after `ver.run` and commit. Do not infer a completed window from an observer callback alone.
- Per-window service and route writes must finish before the next window overwrites the active window metadata. `ExpertPool::run_split_multi_native` returns after GU, intermediate quantization and Down phases complete; worker slot reads/merge happen only after its existing run-phase park boundary. Do not move observation to an asynchronous issuer or create a second outstanding-generation protocol.
- `commit(a+1)` may return with the commit graph pending on the single GPU. The request-owned counters remain ordinary host data, but successful final close must follow the existing `wait_commit`. Do not add a new event, queue wait or synchronization for the observer. A failed wait yields an incomplete ledger and original error status.
- Early `ERR` returns from `ver.run`, commit, MTP draft, adaptive refill or output path must close as incomplete (or leave no receipt if the process itself is killed, clearly recorded as absent by the external owner). Preserve observed partial counts and never synthesize normal status. `length` and EOS `stop` can be normal terminal statuses only after verified/commit coverage passes; server STOP/cancel is not a complete normal generation.
- Output runs to stderr after normal request close, separate from the T/DONE protocol on stdout. It must be default-off, with no route IDs, tensors, hot-path text, queue events or extra waits. On the off path there should be no new clock reads or per-window allocation. Host timing sums overlap, and observer-on timing is diagnostic only.
