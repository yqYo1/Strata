## Result

The configured source path is the root SYCL build, not a historical overlay: `cmake/sycl_backend.cmake` creates `strata` from root `src/program/generate.cpp`, links root `src/core/session.cpp` and `src/core/expert_source.cpp`, and links `strata_kernels_cpu`, whose native path includes root `src/kernels/cpu/native_expert.cpp` plus the pinned GGML CPU implementation. The current IQ3_S-labelled model is mixed-format per layer; the pack label does not imply every expert tensor is IQ3_S. CPU misses remain native packed weights and use GGML's per-layer activation/dot formats; the prefill compact-FP16 path dequantizes expert weights for SYCL/oneMKL. Treating prefill FP16 timing as CPU decode work would mix separate paths.

Decode is host-driven and layer-serial at the handoff boundary. In the captured-token path, `session_run_token` launches the captured graph, waits for its layer doorbell, calls the pool with the layer's host activations/routes, fences the result, publishes the completion flag, then waits for stream completion before returning. `expert_pool_dispatch_multi` classifies routed entries, excludes cache/peer/remote hits, quantizes host activations, deduplicates CPU misses into per-expert multi-token jobs, and synchronously calls `run_split_multi_native`. The CPU pool has persistent workers, fixed per-worker scratch, one layer batch at a time, and a host participant by default. For native IQ types, `native_gu_rows` selects an IQ AVX-512/AVX2 multi-token kernel only when its token threshold is met; single-token work falls back to GGML's native dot except for separately enabled exact/specialized paths. The corresponding down rows use their own per-layer type and activation contract. Do not assume FP32 activation or FP16 expert arithmetic from the container/model name alone.

The memory/queue contract is material to any asynchronous issuer proposal. The graph captures stable session/device addresses; host outputs are written into persistent pinned staging, copied on the session stream, and signalled through the doorbell only after CPU writes are fenced. Replaying another token reuses those addresses. The pool's batch descriptor and job outputs remain live through the synchronous drain and re-park barriers. Moving issue or completion to another thread/queue would need per-generation ownership for route/activation/output buffers, a reader-before-reuse edge, and a completion edge before graph consumers proceed. Current counters and barriers are correctness/lifetime mechanisms, not evidence that their cost dominates.

## Evidence boundary and what is already measured

The strongest decode result currently reported to Main is the active v3 strong-code screen: 3,025 generated tokens, 9.3 tokens/s and 84.9% draft agreement. The weak-code arm stopped with `SIGXCPU` under a CPU-time limit incorrectly equal to its wall-time limit; it is not a GPU-failure or a valid speed comparison. This is a finite workload result, not MTP speedup, quality/full-256K qualification, or a clean attribution result. The separate stock 32K/24-output medians (compact0 5.4, compact1 3.7 tokens/s) have different workload and are not a comparison to the long screen.

Committed long-input phase evidence is prefill-side, not generated-token decode. The closed 34,560-batched-token census recorded 207.576 s with existing queue-marker intervals: 61.535 s in the nonexclusive Down bucket, 49.455 s QSA attention, 32.529 s dequant, and 75.519 s accumulated Stager consumer time. It also recorded 89,743 staging copy attempts / 183.863 GB requested payload and 90,297 GU plus 90,297 Down calls. R521 establishes that the Stager time overlaps the device timeline and includes consumer wait plus H2D submission, not worker memcpy sum or successful DMA duration. None of these values is decode host-pool service, exclusive kernel time, or critical-path attribution. Use them only to keep prefill work separate and to explain why transfer lifetime questions remain important.

The project already has bounded decode counters in source: `Verifier` tracks per-window wait, pool, host-staging and commit; `ExpertDispatch` tracks plan, activation quantization, job construction and run; `ExpertPool` accumulates multi-token GU, intermediate quantization and Down service, plus pool wait-park/drain/re-park. Ordinary `--stats` reports decode token host phases and pool totals. These counters are useful but different scopes and some are cumulative across prompt and decode unless snapshotted at the decode boundary. No committed ledger reviewed here joins these counters to actual per-window token count, per-layer unique CPU misses, expert format, cache-hit source, copy ownership, and an uninstrumented generated-token wall sample. That joined, decode-only ledger is the next measurement gap.

## Ranked measurement and implementation candidates

1. **First measure the decode issuer-to-worker critical path without changing scheduling.** Use the current completed long-screen recipe/binary after Main closes its run, then add one bounded opt-in ledger around each verify window and layer. Record `T`, routed entries, unique CPU misses, format pair, GPU-cache/peer/remote split, host-side plan/de-dup/activation/job time, pool wait-park/drain/re-park, multi-token GU/quant/Down service, host-to-device result submission, ring wait, and request/window wall. Report host CPU service, queue/device markers, and elapsed wall separately. Snapshot counters at decode entry so prompt values cannot leak into decode totals. No per-expert text, event-per-layer wait, or new synchronization in the timing arm. This distinguishes whether the next bottleneck is host issue/barriers, native IQ row work, CPU memory service, GPU overlap, or output transfer; the current screens do not settle that question.

2. **Then A/B only the host pool policy if its measured share warrants it.** The current code already supports worker count, affinity, host-thread participation (`--no-host-worker`), spin-before-sleep, and pool phase counters. The host can participate in CPU work while persistent workers are pinned; a session scratch path can pin the doorbell-driving thread to the reserved host core and restore affinity on close. These are different policies: the isolated historical pool result in `pool.hpp` says the host thread could raise measured bandwidth from 33.7 GB/s with five workers to use all six cores, while the session path's old note attributes lower in-loop bandwidth to an unpinned spinning host. Those historical micro/engine figures are not evidence for the current MTP workload or current options. Run a same-binary, same-request paired sweep only after measuring the current thread/core map and verifying whether the active path pins its issuer. Compare decode wall, CPU pool service, wait/re-park, thread CPU distribution and output agreement; keep routed batch shape and cache placement fixed. Do not carry over an isolated bandwidth gain as a decode win.

3. **Evaluate CPU IQ3_S work by actual verify token groups and row work, not nominal expert count.** The native path groups repeated experts within a verify window and shares one expert-weight read over that expert's participating tokens; `STRATA_IQ_MT_MIN` selects the multi-token IQ row path at `nt>=2` by default. Source comments report a 2.0–2.4× kernel speedup at three tokens versus GGML, no advantage at one, and a 1–3% decode loss when forcing the multi-token path at every size because rounding can differ. This is source-documented historical evidence, not current-workload attribution. Next ledger should report per-layer `nt` histogram, unique expert count and rows per selected kernel/format, with exact output/logit checks; only then test a same-binary threshold or pool partition change against independent end-to-end decode samples. Preserve current rounding/greedy-output contract and no-default adoption until quality gates pass.

4. **Treat a second issuer/queue as a lifetime redesign, not a scheduler flag.** The CPU pool intentionally publishes one flat layer batch because a layer must finish before its routed result is consumed. An asynchronous per-token issuer could hide launch/setup only if the next activation/routes exist early enough and buffers cannot be overwritten until the graph and CPU workers release them. The current graph/doorbell and pinned result buffer do not provide multiple outstanding generations. Before implementation, measure host issue time versus the ring's available GPU work and record the current graph/host pointer lease boundaries. If issue time is not exposed on the critical path, a second issuer only adds synchronization and storage. Keep transfer and CPU computation separate: host CPU decode reads packed expert blobs; the long prefill Stager's expert H2D path is not a proxy for decode blob service.

5. **Defer cross-request batching and TBO until the shared engine contract exists.** `docs/UPSTREAM_INTEGRATION.md` says the server can emit `--batch`, but the active engine lacks independent request slots and the matching batch protocol; speculative rows are not independent requests. SGLang's official EP material documents dispatch/permute/core/combine stages and its Two-Batch Overlap (TBO) interleaves micro-batches. That is a useful future design reference if Strata implements independent request slots, but it cannot be applied directly to the current serial single-request decode path. In the current architecture, measured MTP/verify grouping is the existing token batch and has separate output-equivalence constraints.

## External references and compatibility

- [vLLM CPU backend docs](https://docs.vllm.ai/en/stable/getting_started/installation/cpu/index.html) document CPU thread binding, reserving cores, and batch-size tuning. This supports measuring topology/issuer reservation and workload size explicitly. Strata already pins worker threads and has a reserved-host-core path; adopting vLLM environment variables or OpenMP policy directly is neither necessary nor compatible with its custom persistent pool.
- [SGLang expert-parallelism docs/source](https://github.com/sgl-project/sglang/blob/main/docs/docs/advanced_features/expert_parallelism.mdx) describe staged MoE dispatch and two-batch overlap. Their distributed GPU expert-parallel execution is not a drop-in for a single Arc plus CPU-resident packed experts. The micro-batch-overlap idea is relevant only after Strata's independent request-slot protocol is implemented and measured.
- [vLLM CPU MoE source](https://github.com/vllm-project/vllm/blob/main/csrc/cpu/sgl-kernels/moe.cpp) provides a concrete CPU implementation organized around per-thread expert/token counts and aligned blocks. It uses different tensor/library contracts from Strata's native GGML CPU IQ kernels. The transferable idea is to log per-expert work distribution and row-tail waste; replacing kernels is unproven and would risk IQ3_S output/rounding compatibility.
- [Intel llm-scaler README](https://github.com/intel/llm-scaler/blob/main/vllm/README.md) describes a vLLM fork optimized for Intel multi-GPU systems and NUMA placement. Its Xe/GPU-stack and model/kernel contracts do not map to the Ryzen-host CPU pool plus single B570, so it is background only; no code or runtime setting is proposed for porting.
- [HybriMoE paper](https://arxiv.org/abs/2504.05897) proposes dynamic intra-layer CPU/GPU scheduling, inter-layer expert prefetch, and score-based caching. Strata already has a router-lookahead/prefetch path and GPU cache controls; the paper motivates measuring the actual split and prediction hit rate, not re-implementing those components without a distinct trace-derived need.
