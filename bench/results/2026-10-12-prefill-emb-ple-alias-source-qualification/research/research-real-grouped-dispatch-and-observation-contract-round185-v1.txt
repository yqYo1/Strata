## Source path: reaching a grouped product is conditional

The grouped dispatcher is only reached from the dequantized fallback product path. In `prefill.cpp:1956+`, the expert layer first has routing counts and builds GPU expert order. With native weights and `STRATA_PREFILL_FUSED` enabled, eligible resident experts with at most `kIqGemmTileRows` can go through `iq_gemm_grouped_f16` (`:1960-1975, 2146-2168`); that fused-IQ path does **not** call `xmx_gemm_grouped` and does not launch `GroupedKernel<128,256,3>`. `use_mmq` selects another branch before dense FP16 grouped products (`:2070+`). Only the `fallback_products` lambda (`:2186+`) calls `Gemm::f16_groups` for GU and Down and, when it returns false, calls `xmx_gemm_grouped` (`:2194-2208` for compact rows; `:2218-2224` for noncompact rows). Thus image presence, an XMX-capable device, `STRATA_PREFILL_FUSED=0`, and non-MMQ source settings do not alone prove the real prompt made one of these calls; the active `ExpertLayout`, cache residency, CPU assignment, group membership, bounds and runtime flags matter.

The caller uses FP16 activation/weight products with FP32 output: GU has N=1280,K=2048, followed by rowwise SwiGLU; Down has N=2048,K=640. The grouped device API receives per-expert bounds and `max_rows`. A call with G<=0 or max_rows<=0 returns without launching. In normal compact fallback, each product group has G experts and its own `group.max_rows`; the overall group count/row cohorts vary with the routed experts. Current code launches XMX with M tile count `ceil(max_rows/128)`, five N tiles for GU and eight for Down when N is 1280/2048, 16 subgroups per workgroup, and the `GroupedKernel<128,256,3>` entry. These are launch-shape rules if the XMX branch is reached, not observed model cohorts.

## Source branch selection after `xmx_gemm_grouped` is reached

`Gemm::f16_groups` is a separate caller gate. In a `STRATA_ONEMATH=0` build it always returns false, so the caller enters XeStrata's grouped backend for each fallback product. The supplied free build evidence summarized by R175 identifies this configuration. In a oneMath build, it first asks `gemm_path(F16)`: when the path is not `DP4a`, it returns false immediately; when it is `DP4a`, it tries oneMath products per nonempty expert and returns true only if all calls accept. A failed later product returns false and queues the full grouped fallback, potentially after earlier oneMath products were already submitted and then overwritten. Therefore an aggregate `Gemm::path()`/"oneMath plus own kernels" startup string does not prove whether oneMath served a particular GU/Down group or whether the grouped fallback followed it.

Once `xmx_gemm_grouped()` executes, its source priority (`xmx_gemm.cpp:316-340`) is:

| Selected path | Source condition | Submitted implementation |
|---|---|---|
| Portable `joint_matrix` / MMA | `mma_usable(q,false)` and (`STRATA_MMA` forced or `use_xmx(F16)` false) | `mma_gemm_grouped`, which selects a supported portable grouped `Kernel<S, half, false, true>` shape. |
| DP4a grouped | Portable condition false and `use_xmx(F16)` false | `dp4a_gemm_grouped`. |
| Intel XMX grouped | Portable condition false and `use_xmx(F16)` true | `GroupedKernel<128,256,3>` on `m.cs` with the exact large-GRF and subgroup-16 kernel properties. |

`use_xmx(F16)` is a cached capability decision (`xmx.cpp:209-263`): absent `STRATA_NO_XMX`, the device must report subgroup size 16 and the FP16 8x16x16 matrix combination with FP32 accumulation/output, and `large_grf_ok()` must succeed. The large-GRF preflight currently requests an executable bundle for dense `GemmKernel<half,128,256,3>`, not the grouped kernel ID; grouped XMX launch has no explicit catch-and-fallback if its own compilation/submission fails. So `use_xmx(F16)==true` is a selection predicate, not evidence that the grouped specialization successfully compiled or ran.

`mma_usable()` also requires a reported subgroup and a compatible FP16/FP32 matrix-combination shape whose grouped layout passes local-memory/workgroup checks. `STRATA_MMA=1` can force portable MMA even when `use_xmx(F16)` is true. `STRATA_NO_XMX=1` suppresses both XMX and (unless `STRATA_MMA=1`) portable MMA. If neither matrix path is selected, the grouped dispatcher submits DP4a. All of these are source-defined dispatch conditions; a path report without the exact environment, build mode, runtime capability values and callsite is not an invocation receipt.
