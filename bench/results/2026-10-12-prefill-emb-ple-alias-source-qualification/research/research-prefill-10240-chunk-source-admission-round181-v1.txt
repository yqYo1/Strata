# R181 — source admission screen for fixed prefill chunk 10,240

Date: 2026-10-12 (Asia/Tokyo). Read-only source and retained-report review; no source edit, import/AST execution, test, build, runtime/process/device/GPU query, Git command, cleanup, or measurement was performed. The only write is this report. This is a static eligibility and admission design, not evidence that the larger allocation fits, that results stay within an accepted quality bound, or that throughput improves.

## Decision

A fixed 10,240-token chunk is **source-eligible for a bounded capacity/correctness screen** on the supplied Strata worktree. The parser accepts an explicit integer unchanged; with `--no-prefill-borrow`, the serving path skips the slot-lending/halving code and passes that exact value to `Prefill::init`. `init` stores it in `m.T`/`m.T_max`, and `Prefill::run` processes `min(m.T, remaining_rows)`. No source limit at 8,192 was found. At this candidate size the compact-route guard also passes algebraically: `T=10240`, `K=10`, so `T*K=102400`, well below `INT32_MAX`; the `size_t` product guard has ample range on the supplied 64-bit host.

This does **not** establish hardware allocation eligibility. R179’s stated additional GPU request relative to the qualified T8192 recipe, including the separately allocated `tok_dev`, is 613,785,600 bytes (about 585.35 MiB). Against the 714 MiB READY free-space figure this leaves only about 128.6 MiB nominally, before fragmentation, allocator/page rounding, runtime allocations that occur later, or any difference in the READY measurement phase. Since `--no-prefill-borrow` keeps the 144-slot cache live, its 281 MiB is not reclaimable headroom for this candidate. A free-space total is not enough: Main must check the exact whole-source request, every separately allocated live owner, the device’s per-allocation maximum, and the largest individual request. For the 10,240 configuration the largest `Prefill` allocation is the single GDN-sized shared region, approximately 1,475,872,768 bytes by current source geometry; that and the other large individual takes must be below the receipt’s device maximum-allocation limit. That limit is not established in the current report packet.

The candidate needs no kernel or geometry source change. Its required gate is an exact, same-owner startup admission: before the first `GEN` is accepted, `Prefill::init` for 10,240 must complete with the requested fixed settings, no borrow, and no clamp; preserve at least the full-context/output admission and fail-before-prompt-consumption behavior. A successful process startup alone is not a T10240 fit result unless the effective setting and successful initialization are bound to that process’s source/binary/recipe receipt.

## Current source path and geometry checks

The source identity for this review is Main-supplied immutable W `/home/yayoi/ghq/github.com/yqYo1/Strata/.worktree/diag-xe-host-issuer-ledger-20261012`, revision `337255086026f6eef21a861c297183d05a5f7a22`; it is the production fork/source under qualification, not the pristine official tree.

- In `src/program/generate.cpp`, `--prefill 10240` is parsed using `atoll` into `o.prefill_chunk`; no 8K rounding/clamp occurs in that parser. In `--serve` startup, the explicit fixed chunk is passed to `plan_lend` only when borrowing is enabled. With `--no-prefill-borrow`, that branch is skipped and the serving setup calls `sp.init(..., o.prefill_chunk, ..., nullptr, 0)` before reading the first request/`GEN`. Fixed-mode cache borrowing is the only startup path found here that halves an oversized chunk to fit lendable slots. The auto-policy’s discrete chunk ladder and 8,192 default ceiling do not apply to a fixed 10,240 request.
- In `src/prefill/prefill.cpp`, `Prefill::init` records `m.T=chunk` and `m.T_max=chunk`, allocates the token and host buffers, sizes the row arrays, then carves buffers. It errors if the compact-route guard fails, a host allocation fails, or a device take does not fit. For this static candidate, a completed init is the real device allocator admission test for the Prefill-owned takes; it is not a guarantee for allocations that the later verifier/runtime may create.
- The grouped route dimensions are fixed by this model: `N=2560`, `HC=4`, `D=10240`, `LR=320`, `K=10`, and `E=512`. The compact MoE route tables are bounded by `T*K=102,400` route entries per chunk; per-expert count/offset tables remain 512/513 rows. No expert-specific row count is assumed. `xmx_gemm_grouped`/the fallback receive the existing dynamic `max_rows` and bounds; the compact guard rejects unsupported integer/product ranges before allocation. At T=10,240 these source-level bounds remain within int32 and `size_t`, but they say nothing about the device allocator’s per-allocation ceiling.
- GDN prompt buffers are row-shaped with no 8,192-specific tile cap. The exact GDN shared region scales with T and is about 1.476 GB at 10,240. QSA row data is also T-sized; selection is explicitly tiled in 256-query batches and its fallback attention path in 32-query batches, so T=10,240 is a multiple of both. The normal prompt-attention entry may consume the whole T range; it has no source-side 8,192 cap in the call path reviewed. Its actual backend grid/resource acceptance still needs to be observed in Main’s admitted run.
- QSA selection capacity and `max_blocks` derive from full session/context geometry and remain fixed by the required 262,144 maximum context, not by the chunk. Position/step records are four int32 fields per row. With KV pages of four cells, 10,240 is page-aligned; the final prompt chunk may be shorter, which `Prefill::run` handles by passing its actual row count.
- MTP is a chunk callback consumer, not a fixed-chunk allocation of 10,240 rows. The callback receives each chunk, and `MtpDrafter::prefill` slices it into `max_t` batches; prefill graph capture requires each captured T to be no greater than `max_t` and 8. Thus T=10,240 does not enlarge an MTP graph’s row shape. The separate MTP K/V-update callback and its absolute context-span checks remain live and must complete for each chunk. Do not disable MTP, discard its draft state, or reduce output/context slots to manufacture capacity.
- PLE host input rows, two PLE embedding staging buffers, and row callbacks scale as `T*PLE_N_HEADS` (16 heads) and `T*N`; their host allocation/page-lock success is another admission result. Existing output slots, full configured context, int8 KV policy, resident-cell limit, prefix/session state, and overflow refusal remain unchanged. Chunk size controls work buffers and grouping only; it does not shrink full-context state or extend the endpoint’s output budget.

The main non-`Prefill` owners remain as catalogued in R179: full-context session/KV, MTP weights/state and input staging, hit/output/sampler buffers, and graph executables. Verifier window graphs use their own small decode-window bound; MTP prompt graphs use `max_t<=8`. They are not included in `Prefill::bytes_needed`, and graph/runtime resources can arise after Prefill init. Keep them live and include them in observed before/after free-space accounting; do not assume their bytes are available to the larger chunk.

## Required admission record before accepting the candidate

Hold fixed the R179 qualified recipe: physical/max context 262,144; main int8 KV; resident limit 32,768; compact MoE scratch enabled; group 16; requested prefill ring 8 (effective ring 16, because `ring_slots()` clamps the ring to a minimum of 16); fused mode 0; native batch 0; CPU share 0; cache 144 slots/about 281 MiB; `--no-prefill-borrow`; same model/profile, runtime, queue, source, compiler and all other startup environment. Use explicit `--prefill 10240`, not `auto`. Both T8192 and T10240 are above `STREAM_ALL_MIN` and 8192, so the same ring calculation/stream-all regime applies when the effective ring is held at 16.

Before the first `GEN`/PP, Main’s receipt should bind:

1. Exact W source and executable hashes, full argv/allowlisted environment, model/profile hashes, and the unchanged full-context/output settings. Record that fixed parse produced 10,240 and borrowing is disabled. The source path above establishes no intervening clamp for this exact mode.
2. `Prefill::bytes_needed(g, ss, 10240)` and the separate `tok_dev=4*T` request, plus the individual device takes and alignment guards from the exact source. Compare that complete request and all already-live/later-live owners against actual free bytes. Preserve the R179 stated 613,785,600-byte delta as an arithmetic screen against the T8192 baseline; do not mistake it for a T10240 allocation receipt.
3. A device receipt for `maxMemAllocSize` (or the exact runtime API field exposed by the selected backend), compared against the largest individual take. The GDN shared region is approximately 1,475,872,768 bytes at 10,240. Also record the next largest source takes, including the row residual `T*D*sizeof(float)` = 419,430,400 bytes, and any stage/handoff/host allocations that apply. Source-side `bytes_needed` is aggregate accounting, not evidence that one large take fits.
4. Free VRAM and cache ownership at the same named points used by R179: after all baseline owners are loaded, after T10240 `Prefill::init`, and after all pre-`GEN` verifier/MTP/output initialization. Require init success and no memory pressure/fault; if the device field or setting receipt is missing, leave the candidate OPEN. Stop if allocator failure, a per-allocation limit, page-lock failure, or unexpected effective setting occurs. Do not retry by silently lowering context, evicting the 144-slot cache, reducing resident cells, or removing prefix/MTP/output state.
5. Before consuming prompt tokens, preserve source’s hard full-context/output budget and prompt-span checks. An init that fits does not prove the 262,144 endpoint with its original output slots fits; the 32K/64K screen is a smaller workload under the same full configured context and policy.

The existing R179 714 MiB figure is a useful *screen*, not a standalone proof. If it is the same post-owner READY point as the T8192 recipe, the source delta leaves roughly 128.6 MiB before allocator slack. If it was measured before some relevant owner or at a different startup stage, it cannot be directly subtracted. Candidate admission requires the corresponding fresh-process T10240 receipt.

## Conditional transfer expectation and bounded follow-up

At a 32,768-token prompt, conditioning processes 32,767 rows. Both T8192 and T10240 produce four Prefill chunks (T8192: 8,192×3 plus 8,191; T10240: 10,240×3 plus 2,047). There is no chunk-count reduction in this smallest correctness sample. At 65,536 tokens, 65,535 conditioning rows make eight chunks at T8192 and seven at T10240 (six full 10,240 chunks plus 4,095). Since nonresident expert weights can be streamed again when a new chunk routes to them, the larger chunk offers one fewer chunk boundary for reloads in that 64K case, conditional on actual per-chunk active experts and residency. It does not justify a fixed byte-saving estimate: route sets, resident experts, zero-row experts, and source types vary by chunk. Logical host-to-device request bytes are not PCIe-exclusive traffic, DMA service, or a critical-path measurement; make no physical transfer or speed claim from the chunk count.

If source admission succeeds, first run one fresh 32K correctness sample at T10240 against the same T8192 token IDs/state/output protocol and full numerical/output gate. Record actual chunk progress, final outputs/logprobs or the established state oracle, memory, fault/health results, and any refusal; retain failures. Do not call this a speed comparison.

Only if that passes, compare 64K with three independent fresh-process repetitions per arm, interleaved to expose drift (for example A=T8192, B=T10240, B, A, A, B). Keep the same 262,144 context, int8/resident KV, cache/profile, MTP/spec, group/ring, prompt tokens, output slots, and correctness gates. Report each prefill interval/sample and full prompt completion separately. Check decode independently from one identical restored 64K session state/hash in fresh processes for both arms, report restore time separately, and keep decode settings fixed; do not conflate different Prefill states or use a fresh-prefill request as a restored-decode sample. Preserve per-sample status, no-fault health and output parity; stop if the candidate fails allocation, any correctness/fault gate, or has no repeatable prefill gain after the matched pairs. No change is adopted by this report.
