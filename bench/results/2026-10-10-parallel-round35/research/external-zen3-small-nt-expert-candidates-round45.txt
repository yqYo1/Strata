# External Zen 3 small-NT expert optimization screening — round 45

## Scope and decision

Read-only screen for one distinct exact-weight AVX2 optimization applicable to the existing CPU expert GU/Down row kernels on Ryzen 5 5600X (Zen 3). Code is frozen at W-cache HEAD 66aaec3a, H 96bd5bb4, T 7d0105f2 as supplied by the owner. The closed native histogram has 78–79% NT1 jobs and max NT2; these are job-shape counts, not service times. The owner reports H/T matched the production wrapper across nine profiles and 864 cases byte-for-byte; the new pair build has 115 matching objects/flags and passed CPU preflight, while actual GPU pair trace remains unexecuted. I made no source edits, builds, tests, inference, profiling, Git actions, cleanup, or model performance claims.

I found no source-backed *distinct* external optimization that can responsibly be proposed for these exact packed weights and NT1/2 shape. This is a no-candidate result, not a claim that the current kernels are optimal. Existing proposals and exact-path mechanisms already cover the nearest analogues; the external alternatives either use a different quantized representation, require larger token panels, or target hardware outside Zen 3 AVX2.

## Current implementation and exclusions

The active IQ row implementation is `src/kernels/cpu/iq_avx2_rows.inl` at W-cache: `row_dot<TY,NT>` decodes each weight block once and accumulates each token in block order (31–57); `gu_rows` invokes the row dot for Gate and Up and performs SwiGLU (154–165); Down rows use the same row-dot routine (168–176). Its supported pack types are GU 18/21/22/23 and Down 20; Down 42 uses `src/kernels/cpu/q2_avx2_rows.inl` where `row_multi<NT>` unpacks each Q2_0 block once and applies it to NT activations (16–39). The 48-layer mix is layer-metadata dependent, not one uniform kernel case.

The exact nearby proposals are already screened: R9 hot-expert predecode; R17 Gate/Up activation-load reuse; R25 Q2_0 paired Gate/Up; and R30 IQ row-panel-by-token GEMM. R30's llama.cpp IQP implementation batches a panel at NT=8 minimum, so the actual max NT2 disqualifies its transfer prerequisite. R33 previously documented the NT1 ggml path and the existing AVX2 gathered-IQ256 route; the current round's closed histogram improves workload-shape confidence but does not identify per-format CPU service cost or a new inner-kernel operation. I therefore do not re-label any of these as a new proposal. The root's static cache ranking task is also a different question and is not evidence for changing the row kernels.

## External source screen and transfer limits

- **llama.cpp tiled CPU kernel:** the current upstream tiled implementation has an AVX2 8x16 microtile for conventional quantized matrix operands (see the AVX2 implementation and its packed/repacked layout in [tiled-kernel.cpp](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cpu/tiled/tiled-kernel.cpp), lines 1956 onward in the fetched source). It uses its own tile layout and quantized formats; it does not implement the Strata IQ3_XXS/IQ3_S/IQ2_S/IQ4_XS or Q2_0 expert row ABI. The PR's wider-batch IQ panel path is [commit 85c55223](https://github.com/ggml-org/llama.cpp/commit/85c55223caf0a2ad0d1d88e5a73ab3fe36107867), but its stated minimum is eight token rows and it is already R30. Neither source gives a new small-NT implementation.
- **Independent implementer / fork:** [ik_llama.cpp](https://github.com/ikawrakow/ik_llama.cpp/) documents AVX2 CPU paths and custom IQK quant formats. Its [IQK author discussion](https://github.com/ikawrakow/ik_llama.cpp/discussions/8) explains small 4/8/16/32-value nonlinear tables that map to AVX2 byte shuffles. Strata's IQ4_XS/IQ4_NL already use a small `pshufb` lookup; the larger grid types already have selected AVX2 scalar/gather implementations. A custom IQK format or alternative repack changes the exact packed-weight contract, so those results do not identify an exact-weight kernel substitution.
- **Personal implementation:** [infer-zero/cpu's Q4_K implementation](https://github.com/infer-zero/cpu/blob/main/src/ops/q4_k.zig) is a useful example of a compact integer dot that consumes quantized weights directly rather than materializing a full float matrix. It targets Q4_K in Zig, not Strata's listed IQ/Q2 formats; Strata's present row kernels already consume packed weights directly. The remaining improvement would need a specifically mapped instruction/dataflow gap, which this code does not demonstrate.
- **vLLM / SGLang CPU path:** vLLM's [MoE kernel feature matrix](https://github.com/vllm-project/vllm/blob/main/docs/design/moe_kernel_features.md) lists its CPU experts as unquantized, separate from the GPU quantized expert backends. The [CPU/SGLang MoE source](https://github.com/vllm-project/vllm/blob/main/csrc/cpu/sgl-kernels/moe.cpp) includes CPU fused MoE flows using packed GEMM forms such as INT4 W4A8 or FP8 W8A8, but its packing, activation, and ISA path are not the Strata exact packed IQ/Q2 row kernels. Shape-level grouping in those kernels cannot be transplanted as an unchanged-weight AVX2 optimization on the 5600X.
- **IPEX-LLM and Intel llm-scaler:** IPEX-LLM's [official overview](https://github.com/intel/ipex-llm) describes low-bit CPU/XPU support and FlashMoE for Intel Arc; its [CPU INT4 inference example](https://github.com/intel/intel-extension-for-pytorch/tree/main/examples/cpu/llm/inference) is a weight-only quantized PyTorch/Intel path, not a Zen3 AVX2 expert-row implementation using these GGUF blocks. [intel/llm-scaler](https://github.com/intel/llm-scaler) describes the Intel XPU/vLLM distribution and its GPU-oriented quantized MoE kernels, not an AVX2 CPU kernel. These sources do not give a suitable algorithm for the requested CPU and exact-weight constraint.
- **SGLang implementer notes:** the [Arm engineering account](https://developer.arm.com/community/arm-community-blogs/b/ai-blog/posts/bringing-sglang-high-performance-llm-inference-to-arm-neoverse) describes an Arm CPU execution path and INT8/MoE work. It demonstrates a platform-specific implementation effort but no AVX2 Zen3 dataflow or matching weight format; Neon operations and quantized format are not transferable as exact-weight AVX2 evidence.
- **Architecture scope:** AMD's [Family 19h optimization guide](https://docs.amd.com/v/u/en-US/56665) is relevant for Zen 3 microarchitecture constraints. Intel AVX-VNNI, AVX-512, AMX or XPU throughput claims cannot be applied to the 5600X, which has AVX2/FMA but not those Intel/AVX-512 extensions.

The external search therefore finds precedents for tiled GEMM, direct quantized dots, and platform-specific fused MoE, but no distinct operation supported for Strata's actual NT1/2 expert-row kernels that preserves the existing packed weights and their exact per-row math.

## Required discriminator before proposing a kernel

The available discriminator is *per-format, per-NT service evidence from the exact admitted CPU executable*, not the route histogram alone. At the next permitted CPU-only work boundary, first capture production compiler flags and symbols for the three reviewed worktrees, then measure the existing wrapper/row kernels by each routed (GU type, Down type, NT1/NT2) cell with the actual H=2560/FF=640 shapes, production Q8 activation blocks, worker configuration and affinity. Record repeated per-expert latency, cycles/instructions, cache misses and disassembly for the inner loop; record exact output parity against the current row path and numerical oracle. This identifies whether the cost is codebook decode, memory loads, wrapper/task overhead or scheduling before selecting an alternative. The actual pair GPU trace remains unexecuted and must keep its current status.

Only if those results reveal a concrete operation missing from the current source should the root open a separately bounded prototype at `src/kernels/cpu/iq_avx2_rows.inl` for IQ formats or `src/kernels/cpu/q2_avx2_rows.inl` for type 42. Keep packed bytes, Q8 activations, each row's reduction/FMA order, Gate/Up/Down equations and output bits unchanged; require exact parity and a repeatable isolated NT1/2 win before any model-level comparison. I do not nominate that prototype now because external sources reviewed here do not establish such an operation, and the current histogram has no cost attribution.
