## Four projection calls and matrix contracts

The GDN branch in D `sycl/src/prefill/prefill.cpp:3748-3762` calls `native_proj` for QKV and gate, `bf16_proj` for alpha and beta, and `native_proj` for output. `native_proj` forwards `T`, `w->ne1` as output width N, and `w->ne0` as input width K, with beta exactly `0.0f`; `bf16_proj` likewise passes beta 0 for its first product (`:2085-2100`). The canonical GDN tensor declarations in `src/core/layout.cpp:62-70` and geometry constants in `sycl/src/prefill/prefill.cpp:114` give these dimensions:

| Projection | Weight `[K,N]` | Input `[T,K]` | Output `[T,N]` | C row stride |
|---|---:|---:|---:|---:|
| `attn_qkv.weight` | `[2560,10240]` | `mixed_h` FP16 | `qkv` FP32 | 10240 |
| `attn_gate.weight` | `[2560,6144]` | `mixed_h` FP16 | `z` FP32 | 6144 |
| `ssm_alpha.weight` | `[2560,48]` | `mixed_bf` BF16 | alpha half of `ab` FP32 | 96 |
| `ssm_beta.weight` | `[2560,48]` | `mixed_bf` BF16 | beta half of `ab` FP32 | 96 |
| `ssm_out.weight` | `[6144,2560]` | `y_h` FP16 | `bo` FP32 | 2560 |

At `T=8192`, outputs span full rows across the chunk. The alpha/beta calls use `ldy=2*HV=96` and separate bases `ab` and `ab+48`: for token t, alpha writes columns 0–47 and beta columns 48–95 of that row. They are disjoint. `bf16_proj` sends these matrices through `Gemm::bf16`; its normal SYCL terminal branch declares BF16 inputs, FP32 output and FP32 compute in oneMKL (`gemm.dp.cpp:690-748`). A conditional SYCL branch can first convert BF16 weights and activations to FP16 when `bf16_path()==1`, `N>1`, and beta is zero (`:704-714`); the runtime's device-reported version and `STRATA_BF16_TC` decide that branch. Therefore the exact capture route should be taken from its pinned environment/metadata, not assumed from this source read. The optional beta=1 low-part pass does not meet that branch's beta-zero condition. If `X_lo` is present through the opt-in BF16X2 mode, `bf16_proj` submits a second product into the same output with beta 1.0 to add the low-part contribution (`prefill.cpp:2091-2100`); that is the one intentional in-place accumulation. Source default BF16X2 is off (`prefill.cpp:245-258`); the exact live environment decides whether the second call was selected.

On the non-HIP SYCL branch, `Gemm::native` dequantizes the compressed GGUF weight to FP16 scratch and calls `Gemm::f16`; `Gemm::f16` reaches the DPCT BLAS GEMM wrapper with oneMKL transpose enums and FP32 compute (`gemm.dp.cpp:876-898,750-785`). The column-major call is `W^T[N,K] * X^T[K,T] -> Y^T[N,T]`, which corresponds to the row-major `[T,N]` output above. Its leading dimensions are `lda=K`, `ldb=K`, `ldc=ldy`; native inputs have no padded stride here. `Gemm::bf16` uses the same transpose/leading-dimension convention and an FP32 output. HIP-only hipBLASLt/WMMA branches are not this SYCL call path.

The oneMKL GEMM contract states `C = alpha*op(A)*op(B) + beta*C`; when beta is zero, C need not be initialized on entry. Thus the five first-pass outputs above do not require a prior clear. It does not establish that arbitrary operand overlap is supported, and this audit does not rely on that: in these calls, weight/dequant scratch, input activation, and output C are distinct live ranges. Alpha and beta have separate nonoverlapping output subranges; BF16X2's second pass intentionally reuses the same C only after the first pass with beta 1. [oneMKL SYCL GEMM reference](https://oneapi-spec.uxlfoundation.org/specifications/oneapi/v1.3-rev-1/elements/onemkl/source/domains/blas/gemm).

## Weight and temporary lifetimes

The native QKV, gate, and output weights are quantized GGUF matrices. The native-dense loader validates tensor shape and payload spans, uploads supported native matrix bytes, and publishes `WeightRef::native_data` while retaining the owning allocations in `NativeDense` (`sycl/src/core/native_dense.cpp:146-180,230-265,336-390`). That model-level uploaded representation is persistent; `Gemm::native` does not cache a dequantized weight. It dequantizes the requested complete matrix to the shared FP16 scratch on each call, then immediately submits the GEMM (`gemm.dp.cpp:876-898`). With the configured `GEMM_SCRATCH=32<<20` FP16 elements (`prefill.cpp:846`), the largest QKV matrix is 26,214,400 FP16 elements, below the 33,554,432-element capacity; gate and output are smaller. The source therefore takes the full-matrix path for these shapes, not weight-row slicing. There is no per-layer/per-expert/dequant cache key in this dense path. The optional `STRATA_Q8_PACKED` native-dense copy is a separate packed representation registered for decode MMVQ; the prefill GEMM continues using `native_data` and its FP16 dequant scratch (`native_dense.cpp:260-296`).

Alpha/beta are resident BF16-in-F32 tensors checked by `bf16_proj`; they are passed directly as BF16 matrices, without a native dequant step. Their `ab` output is shared only as a token-major 96-float row split into two disjoint 48-wide outputs. `bf16x2` optionally adds a second activation GEMM into the same rows, not a cached weight transform.

The authoritative capture receipt's recorded environment requests `STRATA_PREFILL_COMPACT=2`, leaves `STRATA_PREFILL_BF16X2` and `STRATA_BF16_TC` unset, and contains no `STRATA_GDN_*` overrides (per root's receipt review). Compact activation still depends on `compact_prefill()`'s source guard `mmq_plan().fallback && !mmq_plan().any` and its other predicates; I do not infer that runtime branch from the environment request alone. BF16X2 therefore follows its source default-off path for this capture.

The chunk's dequant scratch is carved into the prefill borrow region and passed to `Gemm::init_external`; the GEMM handle is bound to `strata::q_of(stream)` (`prefill.cpp:1224-1235`, `gemm.dp.cpp:402-425`). On a later chunk, `Prefill::relayout` drains compute/copy queues before rebinding the scratch to the new borrowed layout (`prefill.cpp:1391-1415`). Projection/dequant operations use that compute queue, and the prior report's in-order admission check applies. Therefore scratch reuse across projections/chunks is ordered; it is not a persistent weight cache and there is no source-level overlap between an active dequant write and the GEMM that consumes the same scratch.

There is a deliberate compact-workspace overlay worth distinguishing from GEMM A/C aliasing. If the requested `STRATA_PREFILL_COMPACT=2` passes the compact-layout guard, `m.y=m.qkv`, and `m.y_h` begins at `m.qkv + T*ZV` (`prefill.cpp:1316-1324`). Convolution has consumed the QKV values before recurrence writes `y`; the FP32 recurrence result occupies the first `T*ZV` FP32 values and the FP16 normalized result begins after it. The static assertion `3*ZV <= 2*C` proves those two outputs fit within the original QKV allocation. The subsequent output GEMM reads `y_h` as X and writes `bo` as C, a separate allocation. Compact mode is off unless explicitly requested (`compact_prefill`, `:992-1002`). This overlay has a sequenced producer/consumer lifetime and does not make the output-projection GEMM in-place.

## What a capture result would justify

If layer-9 `R_input` matches and `R_post_attention_gdn` differs first, a staged internal comparison can justify recording only the first four GDN projection outputs at layer 9: `qkv`, `z`, `ab` (with alpha and beta halves reported separately), and `bo`, along with their exact input images `mixed_h`/`mixed_bf` and the actual BF16X2/compact flags. Compare full-chunk hashes first; only retain raw bytes for the first differing projection and necessary bounded rows. Matching input images but different QKV/gate output puts the first changed captured stage at native dequant/GEMM; matching those and changed `ab` directs attention to BF16 alpha/beta GEMM (including whether the beta=1 low-part call ran); matching all projection outputs shifts focus to convolution/recurrence or residual write. If `mixed_h`/`mixed_bf` differ already, projection libraries are downstream and do not explain the first difference.

If the three existing residual records match but final recurrent state differs, their 32-row window cannot clear a projection that first differs in later rows of the 8192-token chunk. A projection follow-up would then need full-chunk hashes or state-at-chunk-boundary comparison, not conclusions from the fixed sample. Keep the all-head, all-66-state-part, IDs/logprob/MTP checks and original C rejection unchanged. oneMKL's beta documentation establishes C initialization behavior; it makes no claim here about bitwise reproducibility across hardware/library versions, so no nondeterminism conclusion follows from this static audit.
