## Version-matched interpretation and current adapter/mode

For the recorded Strata runs, loading the explicit v2 adapter path on an Arc B570, plus Intel's 2025.3+ documentation that L0 V2 is the default adapter for Arc B Series / Xe2 and only supports immediate command lists, gives strong evidence that these runs used V2's immediate in-order queue model. Strata's current queues are in-order, matching V2's supported queue mode. This is a conclusion from historical run environment plus documented V2 restrictions, not a queue query.

The 2026.1 DPC++ package contains both v1 and v2 adapter libraries. The run record's explicit UR_ADAPTERS_FORCE_LOAD selected v2, so defaults based only on GPU family are secondary for that recorded process. With V2 selected and without UR_L0_V2_FORCE_BATCHED, V2's documented supported mode is immediate. V2's debug variable UR_L0_V2_FORCE_BATCHED is documented as adding UR_QUEUE_FLAG_SUBMISSION_BATCHED and can produce invalid flag combinations; it is not a supported regular-mode switch for a V2 queue. Do not set it as a batching experiment.

Intel's current public environment-variable documentation uses SYCL_UR_USE_LEVEL_ZERO_V2 to select/disable V2; by default it selects V2 for GPUs based on Xe2 or later (Battlemage/B570). Current Unified Runtime-facing controls seen in Intel materials and 2026 Intel/LLVM test invocations use UR_L0_USE_IMMEDIATE_COMMANDLISTS, UR_L0_BATCH_SIZE, and UR_L0_COPY_BATCH_SIZE. The SYCL_PI_LEVEL_ZERO_* names are PI-era/legacy spellings documented for the older adapter path; do not set both spellings and assume one wins. For this installed UR adapter, use UR_L0_* only when a V1 run has been explicitly selected and the control is confirmed active. V2-specific names are separately prefixed UR_L0_V2_*.

## Strata queue creation and effect scope

- The default DPCT in-order queue is constructed via create_queue_impl(true, sycl::property::queue::in_order()) in sycl/include/dpct/device.hpp:685-686; create_queue_impl adds enable_profiling and uses a SYCL queue constructor (around lines 692–704).
- The prefill copy queue is separately created by create_in_order_queue_with_profiling in sycl/src/prefill/prefill.cpp:1116–1123; it also uses a SYCL queue constructor, in-order property, and optional profiling.
- These queues do not set Intel's per-queue immediate_command_list or no_immediate_command_list properties. The adapter/environment policy applies to constructor-created queues; an environment sweep is process-wide and changes all such queues, not just prefill's copy queue.
- Intel's per-queue property is available for the legacy adapter path and lets a future source experiment target queue construction individually. It is not a path to regular lists on L0 V2, which supports only immediate lists. No property change is recommended by this source-only audit.
- EnableDirectSubmission=0 is a separate NEO/driver variable. It does not select the UR queue mode. Preserve it at 0 in every future arm, as well as the rest of the functional environment. Do not conflate direct submission with SYCL/UR immediate command lists.
- Keep all copied and used event/barrier dependencies unchanged. The copy queue's completion event protects compute visibility and each used event protects stage-slot reuse across copy and compute queues; command-list selection does not remove either lifetime edge.

## How to prove the selected mode

The process environment and UR_ADAPTERS_FORCE_LOAD prove which path was requested; they do not alone prove which queue mode was actually created. SYCL_UR_TRACE=2 records UR API calls but should be treated as selection diagnostics, not authoritative performance data; tracing can perturb timing and Intel/LLVM issue 18424 documents a hang whose likelihood changed with tracing. Intel's backend extension says native Level Zero get_native(queue) returns a ze_command_list_handle_t or ze_command_queue_handle_t according to how the SYCL queue was created. A future one-time startup diagnostic can record actual object kind for compute and copy queues, adapter path/version, queue in-order/profiling properties, and override environment before timed requests. Verify that diagnostic's semantics on the selected adapter first. Do not introduce tracing into the timing phase.

A proof record should include exact package versions, libsycl.so and loaded adapter path, runtime/driver build identifiers from already permitted diagnostics, selected device family, full relevant process environment (secrets omitted), per-queue native object kind, and observed effective batch behavior if regular mode is active. If no reliable native queue kind or runtime mode diagnostic is available, mark effective mode unknown and don't interpret its speed.
