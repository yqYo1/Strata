A queue command event start/end is device event elapsed for that submitted kernel command. It is not a host admission interval, and it is not a timestamp around an in-kernel barrier. Since recurrence and norm are submitted asynchronously and host enqueue can overlap recurrence execution, do not claim the components add up to service time or subtract the sum of events from service to invent a “wait” number. Compare same-kernel event durations and host admission durations across order positions; retain service sum as the user-visible combined quantity. If the existing compiler runtime does not provide useful command profiling despite the queue property, stop that branch with an explicit unsupported result.

This is enough to answer the specific discriminator: if candidate admission consumes most of the extra host service while candidate recurrence/norm event durations are comparable, repeated admission host work is implicated. If admission is small and recurrence/norm event elapsed is larger, the measured gap is principally device command work. Mixed or order-correlated changes in both mean interaction/thermal/cache effects and should stay unresolved. The counterbalanced two-process order split remains useful, but a single quiet service ratio cannot establish this attribution.
