Decision

The existing public `ExpertPool::run_split_multi_native(fmt, jobs, n)` is already the smallest production CPU pool entry point for this calibration. It directly runs the production batched GU, intermediate activation quantization and Down phases on a supplied logical expert blob. It does not require `strata_engine`, a GPU callback, a queue, or a device object. The function exposes cumulative public `ms_multi_gu`, `ms_multi_q`, and `ms_multi_down` phase wall counters; a serial harness can set them to zero or snapshot/subtract before and after each call, while placing one monotonic outer timer around that call. No additive timing API is required to isolate those three existing phase intervals. The counters are cumulative doubles and must not be read/reset concurrently with calls.

This interface ends at per-expert H-wide outputs. Router weighting, the shared-expert output and final expert mixing occur later in `moe_combine_parts`/`moe_combine` in the GPU layer path. Do not include that GPU work, invent a CPU replacement, or label one `run_split_multi_native` output as a complete MoE layer result. If a pure weighted-mix check is useful, keep it a separately named host scalar oracle outside pool timing; it still will not qualify production GPU mixing.

Exact call contract and order

1. Load the frozen layer metadata and construct that layer's production `NativeFmt`; require `n_embd=H=2560`, `n_ff=FF=640`, format IDs matching the selected route cell, and `fmt.bytes` matching the validated role extents. Use the R61/R70 shared host role-plan contract to copy one selected `(layer,expert)` into a caller-owned logical blob `[gate | up | down]`; keep that blob immutable and alive until all synchronous pool calls using it finish. Time and report GGUF open/map, role assembly/first touch, and extent hashing separately. R48 establishes that the three role extents may be separately located/sharded; `gguf_off + expert*fmt.bytes` is invalid.
2. Select only in-range routed expert IDs from a validated route/extent manifest. Each ID must be eligible for the intended CPU/refused cell, and its layer-local GU/Down type pair and extent hashes must be frozen. Bind train and disjoint holdout IDs per R46; no ID is independent merely because it appears in a second trace. R63's captured route evidence supports NT1/NT2 exposure. It does not establish real NT4/NT8 callback workloads; unless a new validated callback record supplies those groups, label NT4/NT8 as controlled format-kernel/pool calibration, not observed routed-work calibration.
3. For a per-expert calibration call, make one `ExpertJobMulti` with `blob=owned_blob`, `nt=NT`, and `out[t]` pointing to disjoint per-token H-float output rows. For IQ GU types 18/21/22/23, `nact[t]` points to each input token's production `native_quant_act` bytes; mode 5 consumes these. `act[t]` is only read by the pool's Q2-GU special case, so it is not needed for these IQ cells. Validate `1 <= NT <= MAXT=8` yourself; the public pool function does not enforce every job's pointer/nt contract. For a batch, use one job per distinct expert and `n` equal to that expert-job count (at most `kMaxSplitMulti=96`), not one job per token. The engine routes repeated token hits to a shared expert into one `ExpertJobMulti`.
4. Construct the pool once before timing and use the deployment-equivalent profile from the production call site. On the recorded Ryzen 5 5600X profile: five pinned workers, host participation enabled, `PoolAffinity::All`, task count zero (automatic), i.e. `ExpertPool(5, true, true, PoolAffinity::All, 0)`, with the harness caller pinned to the same reserved host core as production. This is six participants. Automatic phases schedule `3*(5+1)=18` row tasks, even if a one-expert phase has only 640 or 2560 rows; task boundaries are balanced contiguous ranges and empty ranges are legal. If measuring the task-6 treatment, use an explicitly separate `tasks=6` arm and record that it is not the default profile. Record actual worker IDs, affinity, host placement and per-phase task count; do not infer those from the constructor request alone.
5. Before timing, call `native_quant_act(fmt,x[t],nact[t])` once per token and keep the quantized bytes read-only for all experts in that calibration job set. Use distinct deterministic finite FP32 `x[t][H]` for each token; NT2/4/8 must not accidentally reuse token zero's activation. This is a controlled service input, not a sampled decode activation. For current IQ GU cells, only `fmt.act_bytes` bytes are meaningful in each 4096-byte aligned slot. Preserve the exact bytes and compare them independently with the pinned GGML `from_float` for `fmt.gu_act`.
6. Call `run_split_multi_native(fmt,&job,1)` for a single-expert phase sample or `run_split_multi_native(fmt,jobs,n)` for a homogeneous batch. In mode 5 it runs GU rows across `n*FF`, then per-token `silu(gate)*up` in the same float operation order as `native_gu_rows`. It next quantizes each FF=640 intermediate: Down20 uses `native_quant_h` into the pool's native `hq` slot; Down42 uses `act_quant_any` into its `ActQ`. Mode 6 then runs Down rows across `n*H`, using `native_down_rows` for Down20 and `q2_rows_any` for Down42. The public call is synchronous and outputs remain caller-owned.
7. Validate and compare before collecting timing samples. The direct wrapper arm can compute GU from the same `fmt/blob/nact`, quantize FF with the correct Down quantizer, and compute Down through the same production wrappers. For identical source bytes, activation bytes, settings and dispatch, the full direct-wrapper and pool outputs should be bit-identical: task partitioning changes row ownership, not per-row arithmetic. Separately compare activation quantization to GGML, GU/Down rows to per-row GGML CPU `vec_dot` references, and Down42 to the existing independent Q2 block/ActQ oracle. Do not treat direct-vs-pool equality as an independent arithmetic oracle. R64 notes that a blanket full-FFN tolerance is not yet approved; use an already accepted per-cell bound or report oracle deltas as characterization rather than relaxing a gate.
8. Keep the pool call timed as its own boundary. Snapshot/reset its three public phase counters before the call; capture one outer monotonic interval and post-call phase deltas. `ms_multi_gu` and `ms_multi_down` each include phase publication, worker/host drain, wait and re-park, so they are batch completion wall times. `ms_multi_q` covers the host-side per-job/per-token intermediate quantization between those phases. Retain outer duration separately because it includes method setup/loop overhead not represented by simply adding phase fields. Do not sum phase medians from different calls, divide a mixed batch duration by `n_jobs` to manufacture per-expert service, or subtract scheduler costs to derive a direct kernel cost.

Prepared buffers and lifetimes

For each job, `NativeFmt.bytes` is the exact full blob allocation; role slices are assembled into that logical form and must not be aliased with reader-owned or reusable staging memory. For each NT cell, allocate separate aligned `x[NT][H]`, `nact[NT][kNativeActBytes]`, and `out[NT][H]` storage. At H=2560, FF=640, the fixed per-token host buffers are:

| NT | FP32 input bytes | max native input slot bytes | FP32 output bytes |
|---:|---:|---:|---:|
| 1 | 10,240 | 4,096 | 10,240 |
| 2 | 20,480 | 8,192 | 20,480 |
| 4 | 40,960 | 16,384 | 40,960 |
| 8 | 81,920 | 32,768 | 81,920 |

Only `fmt.act_bytes` in each native input slot is meaningful. Use the exact `NativeFmt` row sizing for the assembled blob rather than a hard-coded type size. If the batch holds N distinct selected experts, caller-held full blobs use `N*fmt.bytes`; maintain R46's 1 GiB cap and run batches no larger than 96 jobs. Keep all job structs, blobs, activation bytes and output arrays stable across the synchronous call; do not allocate/free them inside the timed region.

The pool itself allocates on construction. `split_multi_` has 96 `SplitBufMulti` entries, each containing `float[8][640]`, `ActQ[8]` and `uint8_t[8][1024]`; the quantized-down buffers are reserved even for Down20. It also allocates per-worker and host scratch, starts worker threads and pins them. Constructor/startup and destructor/join costs therefore are not per-call pool service and must be reported separately if relevant. The steady-state `run_split_multi_native` body does not allocate a blob, job, or output buffer. A one-expert call still uses the same pool construction footprint and barrier protocol.

Timing and interpretation

- Keep `copy_blob`/role assembly, pack hashing, file open/map and page-fault/residency observations out of the wrapper/pool interval; R68 specifies passive residency observations and natural-load labels. Report source assembly as its own arm. Pre-touch only according to the declared cohort protocol; do not reset/drop the OS page cache.
- Keep input `native_quant_act` outside the pool call and time it separately: production converts each token's input once before it forms all expert jobs. The pool's intermediate FF quantization is inside `ms_multi_q` and is necessarily repeated per expert/token.
- Use the R46 cohort/round and train/holdout plan for actual weights. For each format/NT cell, report actual IDs, extents, source identity, per-round samples, faults and correctness. Keep direct per-expert wrapper service and pooled homogeneous/mixed batch results as different metrics. The public pool method can process larger batches, but it has no stored per-job completion time; mixed callback distributions require captured callback-level jobs to replay faithfully.
- This fixture measures CPU service for actual weights and controlled finite activations under a declared CPU/affinity state. It does not sample real model activations, reproduce GPU overlap or dispatch/admission, validate routed weighted mix/shared expert, estimate end-to-end decode latency, or establish benefits from a pool time hidden behind GPU work.

Isolated phase and callback answer

No engine/GPU callback is required for `ExpertPool::run_split_multi_native`. Construction installs the CPU pool diagnostic observer (`diag_pool_fn`) only. `pool.cpp` also has stall branches that call the inline `release_gpu_waits`; without engine registration `release_gpu_fn()` is null and that call is a no-op. Preserve this condition and do not link engine code. This is a source-path statement, not a runtime no-device admission result. The existing phase counters are sufficient to isolate GU, intermediate quantization and Down as non-overlapping intervals. No new seam is needed for that. If a future harness wants a stable per-call snapshot API rather than directly snapshotting/resetting the public accumulators, the smallest additive change is a value-returning/resettable pool phase-stat snapshot; it must not move instrumentation into row kernels or change dispatch/timing boundaries. It is optional for the current calibration.
