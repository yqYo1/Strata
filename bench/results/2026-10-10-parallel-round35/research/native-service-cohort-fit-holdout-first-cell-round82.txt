How to freeze the two cohorts
The R6 receipt is `owned-cache-route-pairs-v0141-code32k-tasks6-diagnostic-r6/record.json`, SHA-256 `f606f5a1f2d00dba240213a7feeb3cc84c9da4f1487075d1e97c336a558e4c89`. R79’s trace audit shows four blocks collapse to only two unique request patterns: A1/A3 are identical and B2/B4 are identical. Count one copy of each pattern; the repeats add no independent routes, IDs or workload evidence. For each eligible exact-pair NT1 expert, use `J1=2*callback_pairs-entries` as R79 defines, retaining the per-pattern and per-layer CPU-refused exposure needed for sampling. Do not use aggregate repeated captures to double frequency weights.

Freeze a deterministic split from the route-selected 22/20/NT1 union before opening calibration timings. Allocate both cohorts by exact layer and predeclared refused-call frequency bands, with band quotas proportional to the unique-pattern NT1 refused-call exposure. Keep the selected `(layer,expert)` IDs disjoint between train and holdout, preserve layer coverage where the routed population supports it, and record the seed, each stratum’s eligible count/exposure/quota, plus the resulting IDs. Do not balance layers equally if that would greatly distort the observed layer exposure; do not let the hottest few experts consume the entire cohort. Because the harness measures every chosen ID once per round, this stratified selection makes its equal-per-ID aggregate closer to the observed route mix, but it is still a sample, not an exact frequency replay.

Holdout admission is limited. The R6 A/B patterns are repeated diagnostic requests, not an independent workload holdout. A disjoint expert-ID split prevents the same weight identity appearing on both sides; it does not make the two sets independent prompts or certify generalization to other 32K+ conversations. Keep both cohort results as expert-sample validation. An independent 32K+ actual-engine request with unchanged routing/payload identity and its own route/activation/callback evidence is still required before treating a calibration result as representative of long-context serving.

New source-level limit on pool/task-factor interpretation
The currently exposed task contrast is `TASKS=0` versus `TASKS=6`: `phase_tasks()` maps zero to 18 tasks for five workers plus host, and six to six row tasks (`pool.cpp:719-720`). The pool internally processes up to `kMaxSplitMulti=96` expert jobs per `run_split_multi_native` phase chunk (`pool.hpp:181-186`, `pool.cpp:849-879`). In contrast, calibration accepts only BATCH=1 or BATCH=6 and creates a fresh public pool call for each batch (`README.md:27,31`; `native_service_calibration.cpp:260-274`). For BATCH=6 the 192 selected IDs become 32 six-job calls. The production callback calls `run_split_multi_native` once per layer with that layer’s unique CPU-miss jobs (`expert_source.cpp:3299-3351`); it is not a stream of 32 cross-layer six-job calls. Because the calibration’s order shuffles all selected cohort indices and forms batches from that global order (`native_service_calibration.cpp:260-274`), one six-job group can contain experts from different layers, whereas a production call is scoped to one `d.layers` value. This is a valid homogeneous-kernel microservice path, but it does not preserve the production call boundary, per-layer batch size, or layer-local working-set order.

Therefore compare `TASKS=0` and `TASKS=6` only as a controlled **six-job homogeneous pool treatment** on the selected weight sample. Use identical IDs, order seed, `BATCH=6`, compiler, CPU affinity and environment in fresh processes; compare whole-round outer time and internal GU/Q/Down phase deltas. Do not infer actual 32K callback time or task-factor benefit from the direct GU/Q/Down per-expert arms: they run serial wrapper/quantizer calls outside the pool, while task-factor changes affect pool GU and Down row partitioning/barriers (quantization remains serial). The internal pool phase values are phase wall times, not sums of expert service costs.

R79’s count rule reconstructs NT1/NT2 incidence per expert, but the aggregate request trace does not reconstruct which different experts co-occurred in a given callback, the callback’s `njobs`, per-job NT mix, or partial-batch tails. The calibration pins all experts in a cell to one NT, whereas production stores an independent `nt` per expert job (`expert_source.cpp:3335-3345`). Thus even an excellent NT1 single-cell pool result cannot predict the scheduling tail of a real mixed NT callback. To make a task-factor result predictive for a 32K request, the next evidence must capture callback-level `(layer, unique njobs, per-job nt, order)` for one representative actual request and run an engine-level paired task-0/task-6 comparison on that same request. If that mixed shape is material, use an exact mixed replay or full-engine comparison; do not synthesize it by summing homogeneous per-call timings.

Activation, residency and fit gates
The current harness input is generated by `((i*37+layer*11+token*101)%509-254)/257.0f` (`native_service_calibration.cpp:228-230`), independent of expert and cohort. It verifies production input quantization but is not activation data from the 32K model. Timing uses actual selected expert weights prepared before the interval and reports a large host working set, but it is not disk-I/O timing, live activation service, a full model request, DRAM-bandwidth proof, or inference latency. Describe it as host-resident streaming CPU service characterization. Any live-activation claim still requires aggregate, payload-free activation evidence at the real GU boundary and a separate exact-engine run.

Apply R46’s statistical gates outside the program: 25 round-level samples per cohort, bootstrap over rounds rather than treating 192 IDs × 25 repeats as independent samples, relative 95% interval width at most 5%, and overlapping train/holdout intervals; if those fail, label the result unresolved. V1’s 25-round schema does not authorize a silent extension; any 50-round continuation requires a separately frozen recipe/source as its implementation report says. Observe thermal/frequency/load and counterbalance profile order. Train is always emitted before holdout within each process and the same round order is reused across arms, so arm rotation alone does not remove cohort-order drift (already documented in R81/v1 README).
