## Actual source dataflow and ownership

The native path call is synchronous from `expert_pool_dispatch_multi`: it forms `ExpertJobMulti` records, calls `run_split_multi_native` for the current layer, then continues only after the call returns (`src/core/expert_source.cpp:3336-3351`). Each job represents one unique routed expert with `nt` token entries and a distinct `out[t]` pointer for each routed token row (`pool.hpp:55-64`; `expert_source.cpp:3300-3345`). `nact[t]` and `act[t]` are the already-quantized layer input pointers; they must stay alive and unchanged until that synchronous call finishes.

`run_split_multi_native` processes jobs in batches of at most `kMaxSplitMulti=96` (`pool.hpp:181-186`, `pool.cpp:849-858`). For each batch it sets shared `mjobs_`, `nfmt_`, `mrows_`, and `mtasks_`, runs mode 5 over `nb*FF` flattened GU rows, calls the native-dispatch histogram on the caller, quantizes every complete expert/token FF vector on the caller, runs mode 6 over `nb*H` flattened Down rows, calls the Down histogram, then updates phase totals and resets mode (`pool.cpp:849-879`). In the frozen target path, configured `--pool-tasks 6` makes each large phase six equal ranges across the flattened row space. A range can cross expert boundaries; it is not one task per expert.

For native GU, worker mode 5 maps each flattened row to `(expert,row)` and writes only that expert's row in `SplitBufMulti.ff[t][r]` (`pool.cpp:630-654`). The ordinary `native_gu_rows` computes the same row's gate dot, up dot, then `silu(g)*u` (`native_expert.cpp:167-194`). The Q2-special GU path uses worker-local `thread_local` gate/up scratch and writes `sb.ff[t][r]`; preserve its existing Q2 row dispatch and activation calculation (`pool.cpp:638-650`). No task may change row kernels, dispatch selection, token grouping, or within-row arithmetic order.

The intermediate is not independently quantized by arbitrary row fragments in the current implementation. For each expert, the caller invokes the existing quantizer once for each full length-`FF` token vector in ascending `t`: either `act_quant_any(ff, FF, a2)` for Q2 Down or `native_quant_h(f, ff, hq)` for other native Down types (`pool.cpp:863-866`; `native_expert.cpp:101-103`). Keep a whole-expert readiness join before quantization; do not quantize a partial FF vector or change its block boundaries/scale calculation. Before moving these calls off the caller or running them concurrently, establish that the selected ggml `from_float`/Q8 quantizer is reentrant for this build. The current code only establishes the caller-serial order, not this property.

Down mode 6 reads the full expert's quantized activation and writes `out[t][r]` for disjoint output rows; the scalar implementation assigns each row/token dot result directly without a cross-row reduction (`pool.cpp:654-664`, `native_expert.cpp:217-237`). The row kernels' output buffers belong to distinct routed token/expert rows. Preserve each call's `nt`, activation pointers, exact Down dispatch and row dot order. The caller's downstream combination/router-weight handling remains outside this pool operation; no task should add to or reorder those output rows. The final return/join must precede reuse of jobs, activation arrays, output buffers, layer format, scratch, and the next layer/callback.

## Which rendezvous are data dependencies?

A join of all GU work for one expert before that expert's current whole-vector quantizer is a true data dependency. Once that expert's quantized vector exists, its Down rows need no other expert's GU or quantization result. Different experts write different `ff`/`hq`/`a2` scratch and different output rows. Therefore an all-expert GU join and all-expert Down join are not numerical dependencies of the current per-expert computation; they are imposed by `run_phase`'s one-global-batch scheduler and the caller's serial quantization loop. There is no source-level need to wait for expert B's GU before quantizing or running Down for expert A, provided task ownership, visibility and object lifetimes below are upheld.

This is only algorithmic feasibility. The current pool does not already implement a ready-task DAG: `run_phase` waits for every worker to park, selects one mode, publishes one epoch with a fixed task count, waits for all jobs, and waits for every worker to park again (`pool.cpp:691-701`). Workers claim monotonically indexed tasks from one packed `(epoch,count,index)` atomic and increment one batch-wide `done_` counter (`:542-564,611-688`). Six tasks currently mean six broad row ranges, not six workers with arbitrary dependency events. Removing `wait_done`/`wait_parked` by itself would allow quantization/Down to observe incomplete GU rows and would permit reuse of shared mode/pointer state while old work still runs. A meaningful expert-local pipeline needs a ready-work mechanism and per-expert dependency bookkeeping; it is more than deleting the phase barrier.

## Minimum safe prototype contract, if telemetry warrants one

Keep the existing per-layer call, job list, exact `NativeFmt`, packed blob pointers, input activations, dispatch decisions and whole-vector quantizer. Within each existing `b0..b0+nb` batch only:

1. Construct a bounded, preallocated set of GU row-tile descriptors for each expert, initialize every expert's expected completion count before publishing any task, and preserve disjoint `[r0,r1)` ownership for all token rows. Existing flattened tasks may cross expert boundaries; either account for each expert intersection explicitly or switch to explicit expert-local row tiles. A single expert's `nt` group must remain intact for its row-kernel dispatch.
2. After an expert's complete GU row set has finished, publish exactly one quantization node for that expert. That node calls the existing full-FF quantizer once for each `t` in its current order and stores to the existing `a2[t]` or `hq[t]` buffer. Do not permit a Down node to read those buffers until quantization completion is published.
3. Publish that expert's existing Down row calls only after its quantization node completes. Down tiles must write disjoint row intervals of each `out[t]`; no cross-expert sum is introduced. Preserve the final all-Down join before returning to `expert_pool_dispatch_multi`.
4. Keep the diagnostic `native_histogram_add`, cumulative `ms_multi_*`/`multi_bytes` updates, `mode_` reset, and caller-owned error/return behavior on the pool caller, not worker callbacks. Preserve one-call-at-a-time ownership of the shared pool fields. A full join is required before the next 96-job batch reinitializes descriptors or reuses `split_multi_`, before a second layer/callback changes `mjobs_`/`nfmt_`, and before any owner buffers go out of scope.
5. Establish publication semantics explicitly. Row stores must happen-before the quantizer that reads them, and quantizer stores must happen-before Down readers. Initialize counters before workers can run; publish each completed tile with a release operation and consume readiness with a transitive acquire/join (for example, a per-tile completion array acquired by the consumer, or a carefully specified acq_rel RMW chain). Publish newly ready queue entries with release/acquire semantics. Avoid relying on the current batch-wide `done_` alone: it only proves all tasks from one epoch are finished, not that a particular expert's rows are complete.
6. Bound descriptor/queue storage for `nb<=96` and a declared tile count, without decode-time allocation. Preserve a generation/epoch across each batch so stale readiness cannot leak between b0 batches or calls. No cross-layer expert deferral and no math-gate change.

`run_split_multi_native` and its `mode_`, `mjobs_`, `nfmt_`, `mrows_`, and `mtasks_` fields are shared mutable single-batch state. The prototype must either preserve this single-caller serialization or make every state object call-local; it cannot make the existing method reentrant implicitly. Reusing the same `SplitBufMulti` rows before both producer and consumer nodes have completed is unsafe even if the queued task indices look complete. With `host_works_`, the host currently joins `drain(-1,host_scratch_,epoch)`; a replacement scheduler must decide how the host participates in the same ready queue and preserve existing worker affinity/ownership rather than silently changing the participant set.

## Feasibility decision and go/no-go evidence

**Decision:** the dependency graph is mathematically expressible with unchanged per-expert kernels, but the specific R53 phrase “small fixed-task-count DAG” is not established as a drop-in extension of this source. A fixed count of six broad ranges cannot by itself express many expert-local completion edges. A bounded preallocated DAG can represent up to 96 jobs and their row tiles, but its descriptor count, queue traffic and quantizer thread-safety must be specified. Treat the candidate as *conditional and not implementation-ready*. Do not prototype it unless independent active/wait/tail data shows material all-expert idle time at the current phase boundaries.

Before code, collect a matched baseline's per-window/per-layer `nt`, actual GU/Down dispatch, useful rows, task publish/claim/start/end, per-worker active time and last-finish-to-phase-release tail; separately time `wait_parked`, `wait_done`, and caller-serial quantization. Include host-participant intervals and a bounded no-op control with the same worker/phase publication sequence to estimate dispatch/park cost. Keep whole-pool CPU time and physical decode time beside these measures. Existing phase durations overlap GPU work and are not additive latency; they cannot identify a queue/barrier cause alone. R17 already calls for per-worker/tail evidence on NT-weighted within-phase shaping; this DAG question is different only if it specifically shows idle time between completed individual experts' GU and their potential quant/Down successors.

Proceed only if measured idle-tail/barrier time is substantial relative to per-expert quant and remaining compute and is repeatable on the exact NT/dispatch mix. Then prototype one fixed descriptor policy, first verify exact output heads, logprobs, MTP and all live-state parts against the frozen passing reference, and compare end-to-end outcomes under matched conditions. If workers remain busy through GU/Down or queue/wakeup cost is comparable to the alleged tail, stop. No current evidence supplied here selects a speedup or establishes a barrier bottleneck.
