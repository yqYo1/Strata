Scope is the current `gdn_variant_parity` harness and concrete gaps relevant to a future opt-in SG32 quad pipeline; this does not repeat the prior lane/synchronization design reviews.

## What current parity actually tests

`sycl/src/prefill/gdn_variant_parity.cpp` currently compares the ordinary `gdn_recurrence` against **the SG16/256-GRF keyhead variant**, not an SG32 quad kernel (`gdn_variant.hpp`, `kernels.dp.cpp`, parity lines 67–83). Its cases are `T={1,17,255,256,257,1024,4096,8192}` (169–172). The `after` path asserts eligibility at `T>=256`; below that it calls the ordinary recurrence on the second buffer (72–80). Therefore T=1,17,255 test identical baseline-vs-baseline outputs and fallback eligibility; they do not test any candidate kernel. T=256 exercises keyhead and resource lookup, while larger eligible values exercise keyhead output/state parity.

For each single call, it starts both complete 128×48×128 FP32 recurrence state arrays from the same random small **nonzero** state and gives both routes the same random Q/K/V, gate, beta, z, and gamma. It checks every active FP32 state and output bit-for-bit using `bit_cast<uint32_t>`, every FP16 output bit-for-bit, and finiteness of active state/output (`:27–41,85–114,146–150`). It also checks 32 sentinel floats/halves immediately before and after each whole allocation (`:18–20,42–58,92–114`). These are meaningful exact-parity checks for this keyhead variant on these inputs; current thresholds are bitwise equality, not an adjustable tolerance.

The subsequent timing loop calls each route 15 more times on carried, mutated state (`:128–145`) but performs no correctness comparison, does not restore the initial state, and does not compare at each repeat. It is not repeat/carry correctness coverage. The harness does not invoke the production prompt path or its convolution, projection, chunking, session state, or request lifecycle.

## Concrete false-negative / coverage gaps for SG32 quad

- **Wrong kernel can pass today:** the harness never references an SG32 quad entry point or named kernel. A future quad bug is invisible until the harness dispatches that candidate explicitly.
- **Unsupported/admission fallback is not covered:** current `launched` checks only the keyhead function's `T>=256` threshold. It does not force subgroup/kernel-bundle/resource preflight failure, assert the legacy branch was chosen before any candidate submission, or prove that no retry occurs after candidate submission. A future candidate that silently falls back on all cases could appear green if its route is not separately asserted.
- **No T=0 contract:** zero tokens are absent. Current harness allocates zero-length input/output buffers for T=0 and invokes ordinary recurrence, whose output normalization launch has a zero range; it does not define/test an empty no-op. A candidate must establish a no-submit/no-mutation empty path separately rather than assuming this current test covers it.
- **Tail values only cover the old variant:** 1, 17, and 257 are nonmultiples of four, but the candidate is not called for 1/17 and 257 selects the different keyhead kernel. If quad processing uses a four-token staged loop, these do not test its tail. Add candidate-targeted tail/edge values around the pipeline unit (e.g. 3, 4, 5) and a longer final partial chunk. For the actual ordinary recurrence, all current T>0 cases cover output/state shape only for the compared keyhead path.
- **No zero-state, controlled carry, or repeat check:** all initial recurrent values are random nonzero. No exact zero-state fixture tests the first update from zero. Correctness is compared only after one invocation. Repeated timing calls mutate state but are not compared. A wrong state load/store or state carry bug could escape if the single random call happens to overwrite/obscure the affected cells. No convolution-history carry is tested.
- **No directed 48-head/key-group pattern:** full arrays include 48 heads, so random data is compared across all heads. But the inputs and state are generated from one flat deterministic PRNG stream, not encoded with head/key-head identities, and there is no assertion for all three value heads per `head % 16` group. A gather/index bug that aliases groups can be data-dependent and harder to diagnose; no explicit group-map fixture currently detects it by construction.
- **No cancellation fixture for ordered partials:** the bitwise full-output comparison may expose changed reduction order for random data, but the harness has no deliberately cancellation-sensitive four-partial pattern and records no partial values. A candidate could accidentally permute partials yet pass these chosen inputs if the affected values round identically. It also does not isolate whether a mismatch arose in KV partial order versus output-partial order.
- **NaN coverage is only a final-value check:** no NaN/Inf is injected in state or inputs. The `finite` boolean catches unexpected nonfinite active FP32 state/output and FP16 inf/NaN bit patterns, but does not validate expected NaN propagation or distinguish it from wrong finite/NaN behavior. The guard check covers only the outer allocation boundaries; it does not place canaries between rows, heads, or tiles, so an in-bounds cross-slice write can corrupt another active cell without tripping a guard. Full bitwise comparison can catch many such corruptions, not guarantee each inner boundary.
- **No production length/lifecycle coverage:** maximum direct kernel length is T=8192. The harness does not test a 32K prompt, physical context 262144, fresh-session zeroing, prompt chunk sequence, the final chunk of that sequence, or state carry between chunks. Production passes a per-chunk `T` into recurrence (`prefill.cpp:2912–2919, 3654–3668`); the total request length and the individual recurrence launch length are different. A 32K/262144 model test remains a separate end-to-end lifecycle gate, not a reason to force one recurrence allocation of T=262144.
- **No GPU/reference math discrimination:** the current GPU-to-GPU comparison requires bitwise equality for keyhead vs ordinary. A CPU equation oracle can find mathematical/indexing errors but does not reproduce GPU `sycl::fma`, `sycl::native::exp`, or `sycl::rsqrt` rounding. Do not use a CPU floating mismatch as proof of a GPU defect, and do not use a CPU tolerance to relax the existing GPU/model acceptance thresholds. For intentional NaN cases, compare NaN/Inf classifications and expected affected regions separately from NaN payload bits.

## Minimum useful additions for the quad candidate

Keep the existing test and all existing bitwise/model thresholds unchanged. Add a candidate-specific correctness path whose output states which route actually launched and why; first assert that the opt-in candidate was selected for eligible cases. Make a compact deterministic fixture cover these independent failure modes:

1. **Empty and pre-submit fallback:** T=0 must leave state/output sentinels and full state hash unchanged and submit neither recurrence; a forced negative admission result must select the old recurrence before candidate submission, with candidate-submit count zero and legacy-submit count one. A post-submit error must be surfaced, never retried as legacy on possibly modified state. This is routing coverage; it does not claim a mock proves hardware support.
2. **Tail + carry:** run candidate and the exact current GPU reference from the same all-zero state through short candidate cases straddling any four-token staging boundary (3, 4, 5), then continue both from their respective carried states with a second distinct chunk and compare after each call. Also run one controlled nonzero initial state. This tests initial state, per-call state carry, update-once behavior, tail, output, and final state. Include a maximum *actual configured prefill chunk* only if it fits the approved diagnostic budget; keep full 32K and physical-262144 checks at their existing model/lifecycle stage.
3. **All-head mapping:** within one deterministic fixture, assign distinct finite values by key group `head%16`, value-head index among the three heads sharing each key group, row group, column, and token. Verify every active FP32 output and final state for all 48 heads against the current GPU recurrence. Ensure the data makes each group/head contribute, so dropped/aliased heads cannot be hidden by zero or identical inputs.
4. **Ordered-partial sensitivity:** include a deliberately cancellation-sensitive setup where the four row-group KV partials and four output partials have known, distinct values that produce a different result if permuted/reassociated. Check the ordered reference result and complete final state/output; if test hooks can expose per-group partials, record them, otherwise use final observable state/output chosen to distinguish the faulty order. Do not substitute an unordered group reduction. CPU oracle may validate equation and intended partial placement, but is not a bitwise GPU arithmetic oracle.
5. **NaN/guards:** add one isolated NaN injection with an explicit expected propagation/classification mask, keeping finite checks for ordinary fixtures. Retain whole-allocation canaries and, if the fixture is small, add red-zones around at least per-head or per-tile output/state slices to detect cross-slice writes. Compare NaN class, not NaN payload bit patterns.

Run full-state/fp32-output/fp16-output comparisons on each eligible candidate case, not just output or selected rows. Keep the exact current GPU reference differential gate (bitwise where it is currently bitwise); any proposed exception needs separate evidence and must not silently weaken established thresholds. Keep the independent CPU equation oracle as a mathematical/indexing check with its own stated scope, not as GPU rounding authority.
