What the three source arms actually are
1. **Traits baseline.** `rows()` resolves `ggml_get_type_traits_cpu(GGML_TYPE_IQ2_S)`, checks `vec_dot_type==Q8_K` and `nrows==1`, stores `traits->vec_dot` in `baseline`, then calls that function pointer with the pinned C ABI: `n`, output pointer, three byte strides, two data pointers, and `nrc=1`. This is the actual GGML trait implementation from the built closure, not a copy. Its call may be indirect or devirtualized/inlined by the final link; source alone does not establish that. The GGML trait table maps IQ2_S to `ggml_vec_dot_iq2_s_q8_K`, Q8_K and one row.
2. **`direct_control`.** A separate C++ noinline function returns a scalar `float` and takes only `n`, `block_iq2_s*`, and `block_q8_K*`. It is an independently copied AVX2 body, with zero strides and one row hard-coded by the wrapper. It does not simply invoke the baseline function at a direct address while preserving its ABI. It adds a width guard (`n<256 || n>8192 || n%256` throws) and C++ exception/unwind behavior; it has no `s`, stride or `nrc` parameters, and uses a float-return ABI. Its source also performs a shared `memcpy` of packed sign bytes into local `uint16_t sign_words[16]` before reading them. These changes are shared with `index_candidate`, not with the traits baseline.
3. **`index_candidate`.** Another separate noinline float-return helper with the same signature, guard, exception behavior, sign-word memcpy, setup, dot, reduction, and return shape as `direct_control`. Within the loop, the source swaps the direct scalar index expressions for `high[qh[...]]`, `grid_indices(qs, ...)` / `grid_indices(qs+4, ...)`, temporary `uint16_t sp1[8], sp2[8]`, and the four scalar codebook reads in the same constructor order. This is the intended single source-level mechanism difference between control and candidate. It is an isolated source factor; generated code may still change register allocation, spills, instruction scheduling and surrounding code as a compiler consequence, which must be measured/inspected rather than assumed away.

Attribution judgement
**Control versus candidate is a usable index-spread source contrast, with a common wrapper/aliasing adaptation.** Both functions live in the same translation unit, are built with the same target and global options, share noinline, signature, width branch/throw path, sign memcpy, codebook table and remaining arithmetic. Their only meaningful source-body delta is index formation. Therefore a candidate/control comparison can be attributed to index-spread source mechanism for this fixture, subject to successful linked-code confirmation and no accidental other changes. The two new index temporary arrays and 2 KiB spread table are part of that mechanism's cost. They must not be normalized away or described as free. Both forms may have different spills or register pressure after optimization; that is a mechanism outcome.

**Baseline versus control is not a call-target-only arm.** The baseline-to-control difference includes at least:
- trait function-pointer dispatch versus a direct call to a separate noinline helper; only linked code can show whether the baseline call remains indirect, was devirtualized, or otherwise altered;
- C ABI output-pointer/stride/`nrc` call contract versus C++ scalar-return helper ABI with fixed one-row, zero-stride assumptions;
- generic trait implementation's own `n`/row behavior versus added wrapper width validation and throw/unwind path (normal fixture widths take the nonthrowing edge, but the wrapper changes symbol and call code);
- the shared local sign-word `memcpy` in the copies versus the pinned GGML body’s typed `uint16_t` pointer into `qs` sign storage; this can change alias assumptions, alignment facts, stack/copy loads, and code generation, even if it protects the intended logical bytes;
- separate C and C++ translation units and their possibly different compile definitions, target flags, FP flags, LTO/inlining visibility and link closure.

Consequently baseline/control output equality proves a value relation for the exercised fixture only; it does not quantify the cost of direct dispatch. Any measured baseline-to-control difference is a composite (and may be zero if direct-call/compiler effects offset copy and ABI costs), not evidence for a call-target benefit. If root still needs a call-only control, it requires another arm that preserves the actual trait function signature, arguments, body, sign access, flags, and data path while changing only the call-site target where technically possible; otherwise report that call-only effect is not isolated and omit that interpretation. The current three-arm source does not supply that arm.

Call order and timing consequence
For each profile, source calls Gate baseline, Up baseline, Gate control, Up control, Gate candidate, Up candidate in that fixed order. Each width/seed/mode is warmed/prepared by prior work only to the extent the harness naturally does so; no randomized or counterbalanced order is present. The executable has no timing loop. This fixed order is acceptable for exactness checks, but if timing is later added around these arms it must not be reported as a clean three-arm comparison without addressing systematic order/cache/frequency effects: keep preparation/checks outside timed regions, use equal work and repetitions, rotate or randomize arm order across paired trials, and retain raw per-arm samples. Do not change the source now; this is a future measurement constraint, not a request to extend the fixture in this review.

Source and build provenance that must accompany a linked comparison
The README's recipe selects IntelLLVM `icx/icpx`, C++20, `-fp-model=precise`, and per-fixture `-mavx2 -mfma -mf16c`; it rejects a few global options (`fast-math`, `fsycl`, `march`, `ffp-contract=fast`). CMake forces `GGML_NATIVE=ON`, `GGML_CPU=ON`, static libraries, CPU-only backend options and `GGML_CPU_ALL_VARIANTS=OFF`, then adds the pinned GGML subdirectory. This does **not** itself prove that all three symbols were compiled under identical ISA/FP settings: the fixture TU gets explicit AVX2/FMA/F16C options, while GGML's own CMake conditionally adds architecture flags for `GGML_NATIVE`. In the pinned `ggml-cpu/CMakeLists.txt`, the native x86 configuration appends `-march=native` (the separate `-mtune=native` fallback seen elsewhere in the file is in a non-x86 branch). The x86 branch does not read `/proc/cpuinfo`; the compiler resolves `-march=native` for its build host. The CMake fixture's global-option guard only checks the caller-provided C/C++/link flag variables; it does not remove or neutralize GGML's target-local native flags. So the exact compile command for the actual IQ2_S baseline and the candidate TU must be captured and compared. `GGML_NATIVE=ON` is not a substitute for recording the emitted baseline ISA. The active baseline must be the AVX2 function in the linked executable on the intended Zen 3 host; the CPU model was not queried here.

Also record exact compiler build/version, CMake cache/configure command, C and C++ compiler paths, target-local and transitive options/definitions, FP contraction/fast-math behavior, sanitizer state, LTO state, architecture branch macros, source/object/archive identities, static dependency closure, link command and final binary SHA-256. `GGML_CPU_FP16_TO_FP32` is selected by the pinned `simd-mappings.h` macro path at compile time and may resolve to the GGML FP16 lookup table on x86; verify the actual path and linked address/loads for the baseline and copies. Do not rely solely on the README command or source resemblance. No compile commands/build outputs exist as evidence in this source-only report.

Required linked-code comparison set
For a valid codegen review, compare these three functions in the same owner-bound final executable, plus their calling context:

- **Baseline symbol:** the exact linked `ggml_vec_dot_iq2_s_q8_K` AVX2 implementation selected by the IQ2_S trait in this closure. Confirm which body/ISA branch is active, with its symbol/object or archive provenance.
- **Control symbol:** full linked `isolated_iq2s::direct_control(int, ...)`, including prologue/epilogue, width guard and any out-of-line/unwind helper calls.
- **Candidate symbol:** full linked `isolated_iq2s::index_candidate(int, ...)`, including any inlined `grid_indices`/`high` table data or helper, spills and stack accesses.

Include Gate/Up call order. If profiling/measurement wrapper adds calls, counters or barriers, compare that closure too.

Within `direct_control` versus `index_candidate`, annotate the hot-loop block per iteration and per row: shift/mask/OR/extension operations removed; spread-table load(s), qword loads, unpack/interleave and moves added; codebook scalar loads (expected four per vector/eight per inner iteration), q8 loads, sign reads/copies, scale accesses; all stack stores/reloads and vector spills; function/helper calls; register saves and loop structure. Establish that non-index arithmetic retains sign transfer, `maddubs` saturation semantics, `madd`, separate `sumi1`/`sumi2`, block order/FMA, horizontal tree and post-scale. Do not infer changed pressure from source count alone; compare emitted code. For baseline versus control, annotate ABI/call and sign-copy differences before assigning any residual cost.

Comparison interpretation gates
- Exact three-arm Gate/Up/final bit equality on the bounded synthetic fixture is a correctness result only. It does not establish ABI/call cost, live workload representativeness, or same codegen.
- The exhaustive 262,144 index comparisons plus lane tests establish the index helper mapping for its exercised byte domain, not call attribution or performance.
- Candidate versus direct control is the correct narrow candidate contrast once same-C++ flags and actual linked code are verified. If the emitted direct-control core was auto-vectorized/rearranged differently from the candidate outside index work, document that as a codegen interaction; do not label it a pure instruction substitution without qualification.
- Trait baseline versus direct control can be called a dispatch experiment only if linked caller evidence proves the only difference is call target and the body/ABI/data accesses are equivalent. The current wrapper/sign-copy design makes that condition false at source level; likely interpretation is “real trait baseline versus copied direct helper,” a composite contrast.
- No speed/adoption statement is supported until owner-run timing and the separate live-service/materiality gates exist. This review itself does not authorize or perform any build/timing.

Conclusion
The fixture has three valuable correctness arms, and the control/candidate pair is deliberately close enough at source level to test index formation alone. The baseline/control pair is not a call-target-only comparison because the helper changes ABI, range handling and sign-word access, as well as compilation/link boundaries. The first codegen review must inspect all three dot symbols and the complete `rows()` caller in the same hashed executable, bind each object to its exact source and flags, and explicitly report any remaining trait dispatch. Keep baseline-versus-control interpretation composite unless a separate ABI-preserving call-only control is built and verified. All speed implications remain unmeasured.
