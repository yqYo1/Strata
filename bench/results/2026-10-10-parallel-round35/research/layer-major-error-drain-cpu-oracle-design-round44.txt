# Layer-major error-drain CPU oracle design — round 44

Source-backed design for a future CPU-only ownership discriminator, based on frozen D commit `9c2ebde89e5157c81a9c9ae135719452a0244ca3` and C commit `6cdf81078128488e5797afb9e92824b7ebe51124`; it is not an implementation or test result. No code edits, build/test, GPU/model work, Git mutation, or cleanup. No incident is attributed to asynchronous SYCL failure.

## Source constraints and integration point

`Prefill::run` calls `run_layer_major`, then drains only the cross-stage future pipeline (`prefill.cpp:2335-2348`). This is too late to protect layer-major local backing because `run_layer_major` owns `layer_cache`, `device_rows`, host `rows`, and `residency` in its own scope; its `Restore` is destroyed before `run_layer_major` returns. `Restore::~Restore` calls compute/copy queue `wait()`, `Stager::finish()`, and sometimes KV queue `wait()`, then restores callbacks and temporary pointers (`:2688-2708`). `KvDrain::~KvDrain` also waits on the selected stream and sometimes retained compute queue on `run_impl` exits (`:2915-2925`). These waits are implicitly-noexcept destructor work; a thrown exception during normal destruction or stack unwinding terminates before the outer `run_layer_major` catch at `:2833-2835` or `Prefill::run` can return an error. `Prefill::release` has explicit `wait_and_throw()` calls before freeing persistent buffers (`:809-843`), but an exception there also escapes a destructor when called by `~Prefill` (`:800-801`).

The narrow integration point is the layer-major `Restore` ownership boundary, while all local backing is still alive. Replace destructor-only success/error control with an explicit owner-controlled `finish(err)` outcome called on ordinary success, cancellation, and failure exits before local backing leaves scope. Keep a nonthrowing destructor only as an emergency invariant guard. Since many returns exist inside the layer-major body and `run_impl`, a future implementation should funnel the layer-major body through a common outcome/cleanup epilogue or use a scope object that stores explicit completion status and transfers backing on unknown completion. Do not rely on the later `Prefill::run` future drain to recover already-destroyed local buffers.

The owner must first stop/join all CPU producers (`Stager::finish`, and any issuer/successor that can enqueue work), then fence every queue that could access affected backing. At minimum, source shows `m.cs`, `m.copy`, and conditional `m.kv_copy`; `KvDrain` also uses `dpct::get_in_order_queue()` when no KV prefetch is active, so the queue set must be derived from actual submissions, deduplicated by identity, rather than guessed from member names. Do not restore callbacks/cache/residual pointers, close `layer_cache`, release `device_rows`, or allow session reuse until the relevant completion status is known.

## Owner-controlled drain result

Use an explicit result with separate fields for `completion_known`, `async_error_seen`, and diagnostic(s), rather than a single `bool` that conflates retirement with logical success. For each queue, after all enqueuers are quiescent:

1. Call blocking `wait()` and catch/store exceptions. A normal return establishes the SYCL queue completion fence. A thrown wait is **unknown completion** unless a backend contract or a separate successful fence proves retirement.
2. Continue to attempt the first fence on every other relevant queue even if one failed; record the first error and retain later errors for context. An exception from one queue must not skip another queue that can still be using shared storage.
3. For queues whose first `wait()` returned normally, call `wait_and_throw()` to deliver pending asynchronous errors through the associated handler. Catch and record the propagated diagnostic. The prior successful blocking fence means the queue's submitted accesses have retired even if the handler throws; this is a known-completion failure, not an inference that the output is valid.
4. Only after every queue touching shared backing has a successful first fence may the owner reclaim it. If any first fence or required producer join leaves completion unknown, poison the session and transfer all possibly referenced owners to a long-lived quarantine owner before returning. If such transfer is not available, fail-stop while ownership is still live; never unwind through ordinary local destructors that free buffers potentially used by in-flight work.

`Stager::finish()` currently stops claims and waits for its CPU `active` count (`:531-540`); it does not inspect device work or async errors. If stopping/joining a producer fails, CPU writes into staging memory are still possible, so that backing also stays quarantined. A `wait_and_throw()` exception must be caught to build the explicit status, not suppressed: propagate it to the request/API as failure and mark session state poisoned. A successful fence plus async exception permits storage retirement under the SYCL blocking contract; it does not validate residual/KV/model results and must not permit another inference on the affected logical session. A wait failure with unknown completion permits neither reuse nor free.

## CPU fake oracle cases and sequence assertions

The fake interfaces should expose queue identity, submission/in-flight counts, `wait()` versus `wait_and_throw()`, a tri-state completion flag, and an ordered log. A fake Stager should log stop, join, and whether host DMA sources remain live. The outcome should be checked independently from exception text.

- **Successful cancellation drain:** enqueue work on compute and copy queues, then simulate cancellation. Expect stop/join first, successful first waits on all queues, async checks, then exact callback/cache pointer restoration, release each temporary owner once, return ordinary cancellation/error, and leave session reusable. No queue use can occur after release.
- **Completed queue with pending async error:** make both first waits complete successfully and defer an async exception until `wait_and_throw`. Expect the error to be captured and surfaced, all queues still checked, storage reclaimed once because completion is known, logical session poisoned, and no success response or subsequent inference/reset on that session. This specifically proves catch-and-report does not silently convert a failed command into success.
- **Unknown completion:** make the first fence throw on a queue that still owns backing; let other queue fences succeed. Expect all queues attempted, no callback/cache restoration that exposes backing for reuse, no close/free/reassignment of any possibly shared allocation, owner transferred to quarantine (or fail-stop before unwind), and session poisoned. A successful unrelated queue cannot establish completion for the failed queue.
- **First queue fence fails, second remains outstanding:** arrange compute queue A to fail its first wait while copy queue B remains active. Verify B's wait is still attempted and can complete; shared backing remains retained because A's completion is unknown. This guards against a short-circuit `return` or catch-and-free after the first error.
- **Exception during unwinding:** throw a simulated host exception after enqueue but before normal cleanup. Save the original exception, run the same explicit drain while ownership remains live, and report the original failure plus cleanup diagnostics. If all first fences succeed, release after the drain and return/rethrow the combined failure; if any completion is unknown, quarantine/fail-stop. No destructor may throw a second exception during unwinding.
- **Emergency destructor path:** omit the explicit `finish()` call deliberately. The destructor must be `noexcept`, must not silently claim success, and must not release backing without successful proof. Its only safe fallback is a durable poison/error record plus ownership transfer to quarantine, or fail-stop while objects remain live. Assert no destructor exception escapes and no backing owner is destroyed while a fake queue reports in-flight access.

A CPU test can prove ordering, first-error preservation, all-queue attempts, state transitions, and exactly-once retirement/release under the fake's stated semantics. It cannot prove that a real SYCL backend returned from `wait()` after a hardware/device-loss condition, that a runtime exception means queue work is retired, or that a driver can still safely deallocate memory after reset. Do not model a thrown `wait()` as “done”; keep that state unknown.

## SYCL contract boundary

The [Khronos queue reference](https://github.khronos.org/SYCL_Reference/iface/queue.html) distinguishes `wait()` (blocking completion, synchronous errors) from `wait_and_throw()` (blocking completion plus dispatch of unconsumed async errors). The [asynchronous error-handler reference](https://github.khronos.org/SYCL_Reference/iface/async_handler.html) says handlers can be invoked by `wait_and_throw()` and automatically when a queue/context is destroyed with pending errors. This project handler logs and rethrows the first exception (`include/strata/sycl_error.hpp:8-19`); queues made by `device_ext` and the layer-major copy/KV factories attach it (`include/dpct/device.hpp:685-696,625-634`; `prefill.cpp:1112-1115,2898-2910`). For a queue whose `wait()` already returned successfully, a subsequent handler throw from `wait_and_throw()` is therefore surfaced only after a completion fence. The type of a generic exception alone is not enough to infer retirement when the first fence itself failed.

These API/source facts define the fake oracle, not the behavior of a specific driver under lost-device errors. No binary-matched runtime fault injection or actual failed-wait trace is available here. Keep failure status and completion/ownership status separate, and retain the original numerical failures regardless of any future drain fix.
