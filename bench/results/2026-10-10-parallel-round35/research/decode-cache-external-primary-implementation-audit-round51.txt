## llama.cpp: real global-LRU implementation, generic GPU abstraction with important geometry limits

Pinned upstream revision: [`ggml-org/llama.cpp` 79e2e74eb11022c1ba2e438df7f0ca2d4c10f8b6 (2026-10-09)](https://github.com/ggml-org/llama.cpp/commit/79e2e74eb11022c1ba2e438df7f0ca2d4c10f8b6). The cache code is [`src/llama-moe-cache.cpp` at that commit](https://github.com/ggml-org/llama.cpp/blob/79e2e74eb11022c1ba2e438df7f0ca2d4c10f8b6/src/llama-moe-cache.cpp#L133-L149).

The R50 description that it was “CUDA/backend-specific” was too narrow. At lines 221–239 this implementation accepts ggml devices classified GPU or integrated GPU, allocates through backend buffer types, and only expressly rejects tensor-parallel mode. It has no CUDA-only dispatch gate. A CUDA MMQ overread is the reason for one extra allocated bank slot (lines 270–277); this is a safety margin, not a CUDA requirement for the whole design. So the source is backend-generic within the ggml GPU/IGPU backend and buffer contracts, but that does not prove every backend has a working supported path. It requires whole expert tensors resident in host-weight buffers and a GPU assigned to each cached layer (lines 145–149, 241–263). The cache handles the gate/up/down or combined gate_up/down tensor list (lines 123–142), and co-groups layers only when tensor count, quant type, shape, and expert stride `nb[2]` match. Device identity is part of the grouping key (lines 247–263). Each group has one shared slot bank per tensor; expert bytes per slot are the sum of each tensor's `nb[2]`, padded to that backend buffer's alignment. This is fixed-geometry within a group, not one variable-size byte-slot pool for arbitrary layer formats.

A GPU/device budget is divided by tensor split or reported free memory, then within a device split among groups proportional to their host bytes; each group grows its slot count subject to padded allocation size and at least `n_expert_used` slots (lines 270–326). At inference, selected expert IDs are deduplicated; hits are touched to MRU; misses evict the global LRU, update the owning layer's slot map, and queue uploads (lines 16–120, 462–473, 2405–2452). This is genuinely cross-layer recency sharing, but only among layers in the same compatible layout group and device.

The large-batch bypass is concrete: `max_batch` is 32; `get_slot_map` returns null for zero tokens, `n_tokens > 32`, or when the upper bound on distinct routed experts (`min(n_tokens*n_expert_used, n_experts)`) exceeds group slots (lines 196, 462–473). The comment says this avoids large prefill batches evicting generation entries. This condition concerns microbatch `n_tokens`, not configured context length. The cache is created once when the llama context is initialized if `moe_cache_size > 0` ([`llama-context.cpp`, pinned lines 459–469](https://github.com/ggml-org/llama.cpp/blob/79e2e74eb11022c1ba2e438df7f0ca2d4c10f8b6/src/llama-context.cpp#L459-L469)) and held as a context member ([`llama-context.h`, pinned](https://github.com/ggml-org/llama.cpp/blob/79e2e74eb11022c1ba2e438df7f0ca2d4c10f8b6/src/llama-context.h#L296-L306)); it is not allocated per request or per 257k-token sequence. At a 257k context, its persistent allocation still competes with KV/other buffers for the same GPU memory and may make context initialization or KV allocation fail. No source evidence says the cache changes KV state/lifetime or scales with context length.

**Port boundary:** the algorithm worth testing is the *policy question*—can a fixed-byte budget be shared among compatible layers with route-driven recency, with large-batch bypass? There is no direct code transplant: Strata packs a layer's expert as three role extents, uses actual variable per-layer format/role sizes, and runs CPU experts through its own pool; llama.cpp expects host-resident ggml expert tensors then uploads tensor slices to GPU banks. An offline replay can test the allocation principle first. A runtime port would require verified groups by exact Strata role geometry/device, an explicit padded byte budget, fallback behavior for layers that cannot form a compatible group, and context/KV headroom measurement. The external source has hit/miss/upload-byte counters, not evidence of net 5600X/Arc-B570 latency reduction.

## moe-autopilot: cost gate exists in source; its comparison is not validated

The README's v3 policy is not just a prose proposal. The referenced [`JigSawPT/llama.cpp` branch `aipc-v2-teaming`, commit `1bde70825241477038aa578536d60697b5cad6f4`](https://github.com/JigSawPT/llama.cpp/commit/1bde70825241477038aa578536d60697b5cad6f4), contains the implementation in [`src/llama-context.cpp` lines 1638–1727](https://github.com/JigSawPT/llama.cpp/blob/1bde70825241477038aa578536d60697b5cad6f4/src/llama-context.cpp#L1638-L1727) and the decode refresh loop at [lines 1730–1760](https://github.com/JigSawPT/llama.cpp/blob/1bde70825241477038aa578536d60697b5cad6f4/src/llama-context.cpp#L1730-L1760). It is applied over a static hot-copy split: each layer already has hot experts copied into VRAM, and the refresh re-ranks/swaps those resident IDs based on route counters, copying gate/up/down data and updating maps. The `AUTO` gate predicts hits over a 512-token window and accepts a swap when `(extra hits × estimated host-vs-VRAM byte-time gain) > margin × estimated H2D copy time`. The bandwidth defaults are fixed scalar values (57.9, 69.0, 1800 GB/s) with environment overrides (lines 1645–1652); byte estimates sum the source tensor expert strides (lines 1689–1698). The loop observes inter-token time with an EMA after refresh; a >5% slowdown halves the per-layer swap budget, otherwise it grows toward four (lines 1742–1759). The refresh is synchronous at decode start, with no graph in flight (lines 1638–1642).

These values are bandwidth-model inputs, not individually timed CPU service costs for real role formats or measured per-expert benefit. The public README states A/B against v2.1 and the upstream pooled expert cache is pending; its reported +26%/+31.6% results concern the static hot/cold split on an RTX 5090 and Ryzen 9950X3D, not the `AUTO` policy comparison ([pinned README at `moe-autopilot` commit `d10e527ab5108830310ac2d303681d3dbe5c16b3`](https://github.com/JigSawPT/moe-autopilot/blob/d10e527ab5108830310ac2d303681d3dbe5c16b3/README.md#L383-L391)). Thus the code implements a formula-driven controller, but external evidence does not validate its cost model as a win. For Strata, only the decision form is worth carrying forward: estimate expected avoided production CPU service using independently calibrated service by actual format/role and compare against measured load/copy and swap overhead. The specific byte/bandwidth formula is not suitable for transplant as-is, and its hot/cold dual-chain execution path is structurally different.

## moecache: explicit simulator, synthetic routing oracle

Pinned revision: [`joelvarun/moecache` 50dad509640e4447ccb44a31410215bbb8671d64](https://github.com/joelvarun/moecache/commit/50dad509640e4447ccb44a31410215bbb8671d64). Its [`README.md` lines 203–220 and 253–264](https://github.com/joelvarun/moecache/blob/50dad509640e4447ccb44a31410215bbb8671d64/README.md#L203-L264) explicitly calls the project a simulator. It takes per-layer token routing traces and compares LRU, warmup LFU pinning, and a hot-pinned plus co-activation-prefetch buffer at equal simulated capacity. Its reported 64-expert/top-6/20-slot numbers average five traces, and the trace generator synthesizes Zipf popularity, temporal reuse, and co-activation groups. The output hit-rate and “PCIe stall” are simulator metrics; the repository does not measure a live inference runtime, CPU service, or device copies. It offers an independent trace-simulation policy, not primary evidence of a physical stall or a deployable cache implementation.

## Decision

No full external implementation merits a direct Strata runtime port on the current evidence. The only concrete next step worth retaining is a target-specific offline comparison of the llama.cpp-style *compatible-group global LRU* against the current 128-slot static plan, using Strata's actual layer/role byte geometry and held-out route trace. Keep moe-autopilot's measured-net-benefit inequality as a candidate scoring rule only after substituting real measured CPU service and admission costs; do not reuse its coefficients. Do not use moecache's synthetic trace results as an oracle for expected Strata gains. R50's cache-policy decision remains pending actual layer-resolved evidence and a matched correctness-gated target comparison.
