Exact workload and source map
- Default NT1 IQ2_S Gate/Up uses GGML's per-row trait dot `ggml_vec_dot_iq2_s_q8_K`; the native multi-token row path has a default minimum of two tokens. The exact pinned AVX2 source is `ggml/src/ggml-cpu/arch/x86/quants.c`. It processes 2560-input Gate/Up rows as ten Q8_K blocks, with a two-iteration-step inner loop and eight scalar 64-bit `iq2s_grid` reads per inner iteration (32 per block / 320 per row). It also expands qh/qs indices, packed sign bits and odd scales, then performs the existing integer accumulators and per-block floating FMA/reduction.
- Root's just-qualified register-index candidate is a separate fixed-factor variant on that type-22 Gate/Up work. R103 showed its old packed-index stores/reloads gone and no visible replacement accumulator spill. It still has scalar grid reads, the 2 KiB `high` map, and the sign/scale work. It has not been timed on the actual-weight cohort; the next comparison is still required before attributing value to that codegen change.
- `src/core/expert_source.cpp` quantizes each token's H=2560 input once, then stores a shared Q8_K pointer in every expert job for that token. Therefore repeated Q8_K quantization across the routed experts is not an unused NT1 opportunity. In NT2+ `src/kernels/cpu/iq_avx2_rows.inl`, the existing row path decodes each block once for the token group. These mechanisms do not justify a duplicate cache or a token-independent weight predecode proposal.
- Keep Down type 20 separate: it is IQ4_NL with Q8_0 activations and K=640, not IQ2_S/Q8_K. Its existing dot and its FP/reduction contract are distinct. No candidate screened here mixes that Down row with the H=2560 Gate/Up path.

External implementation findings and applicability
- **KTransformers AVX2 MXFP4 grouped path (new source reviewed this round):** commit [`9481291`](https://github.com/kvcache-ai/ktransformers/commit/9481291) reports a 32-value MXFP4 path that removes repeated weight-order shuffles by converting each BF16 activation row once to the decoder's fixed output order, and amortizes decode over four tokens, with a single-row remainder. Its reported measurements are on two EPYC 7452 sockets and DeepSeek-V4-Flash MXFP4. This is useful proof that a fixed packed-weight permutation can sometimes be moved to the activation side. It is not a concrete IQ2_S proposal: IQ2_S has a dynamic 10-bit index selecting one of 1024 packed 8-byte grids, Q8_K activations, and an existing scalar-grid/integer-dot path; there is no corresponding fixed weight decode order that the current body then permutes away. Four-token decode amortization also does not apply to the NT1 trait call. Applying the MXFP4 lane permutation would add activation work and change the quantized dot dataflow without removing a verified operation. Do not port it.
- **KTransformers CPU AMX expert path:** the project describes prearranged AMX tile-sized expert submatrices and AMX tile accumulation in its [AMX implementation note](https://github.com/kvcache-ai/ktransformers/blob/main/doc/en/AMX.md). It targets AMX and a different expert layout. Ryzen 5 5600X Zen 3 has AVX2 but no AMX; arranging conventional tile panels would change the IQ2_S representation / access path and requires a larger multirow panel. Not an NT1 AVX2 decoder candidate.
- **FastLLM Qwen3.8 / Qwen4-Exp:** the project documents the model and CPU MoE placement / `moe_dtype` options in its [Qwen4-Exp guide](https://github.com/ztxz16/fastllm/blob/master/docs/qwen4_exp.md) and [README](https://github.com/ztxz16/fastllm/blob/master/README_EN.md). Those are model/runtime and quantization/placement features, not an exposed Zen3 AVX2 IQ2_S GGUF row microkernel or proof of matching integer/FMA order. Its formats and optional weights are not the pinned IQ2_S bytes. No NT1 operation can be transferred while keeping this block and exact-result contract.
- **XNNPACK:** its [fully-connected operator implementation](https://chromium.googlesource.com/external/github.com/google/XNNPACK/%2B/a8d4bb35c3107d4e97b7a75574e49f7581ce3033/src/operators/fully-connected-nc.c) sets up GEMM/GEMM-packed paths for QD8 and QC4W/QB4W and prepares packed weights/scales. That is conventional block-quantized dense GEMM with packing/cache interfaces, not dynamic IQ2_S grid lookup. Transposing/repacking Strata's expert weights would be an additional data-format/cache mechanism and already falls under the screened predecode/alternate-layout family; nothing in this implementation supplies an exact-quantizer, exact-reduction single-factor substitute.
- **llama.cpp:** the pinned [GGML IQ2_S AVX2 dot](https://github.com/ggml-org/llama.cpp/blob/3cf03257f219afbe7334045ff7c6a06ac68c627d/ggml/src/ggml-cpu/arch/x86/quants.c) is the exact NT1 baseline, not a different route. Its tiled and IQ-panel paths have different packed/tile/activation and batching dataflow and were already filtered by R30/R45/R89; they do not supply a distinct NT1 same-byte/same-order path.

Candidate disposition and next decision gate
No new candidate is recommended. The only active implementation question is whether the already isolated R103 index-spread variant is useful with the real IQ2_S GU weights under the existing actual-weight cohort and fixed prepared activation inputs. If it is not a repeatable material gain there, stop this path. If it is, retain that single factor and then let the root's separate measured service gate decide whether any broader work is justified. Only if those results attribute material remaining NT1 time to a specific sign/scale/decode operation should that operation be reopened as its own factor; current external evidence does not choose one. Keep finite bitwise Gate, Up and GU finish checks and the pinned FMA/reduction order. Any future Down screen must use IQ4_NL/Q8_0, K=640 and the separate Down route.
