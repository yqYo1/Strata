## Meaning of 5056 and what it does not mean

Level Zero `ze_kernel_properties_t::spillMemSize` is defined as the spill-memory size allocated by the compiler; the same struct defines `privateMemSize` as compiler-allocated private memory used by each thread and `localMemSize` as local memory used by each thread group. The Level Zero field description itself does not give `spillMemSize` a byte unit or per-thread qualifier. Intel's oneAPI GPU Optimization Guide describes unitrace's `Spill Memory Per Thread` as a byte value; a nonzero value indicates the kernel spills registers. Therefore the saved runtime's returned value 5056 is best read in Intel's tool/runtime context as 5,056 bytes of compiler spill allocation per thread. It is not a measured amount of traffic per invocation, not a spill count, not total device traffic, and not an allocated-GRF count. The raw property alone cannot turn it into runtime cost or elapsed time.

`privateMemSize=0` is a separate metric and does not cancel the spill result. Intel explicitly distinguishes these: nonzero private memory means there is at least one private variable not promoted to registers; a nonzero spill field indicates register spills. Both kernel records have private=0; only candidate has nonzero spill. Candidate's lower local allocation (1,024 vs 1,536 bytes per workgroup) and max-WG=1024 do not outweigh or explain away its spill property. Conversely, the property comparison alone does not prove a slower kernel or quantify impact.

## Source-derived mechanisms: hypotheses only

The legacy kernel `gdn_rec_cols_pipe_kernel` is at `kernels.dp.cpp:882-997`; it stages Q/K into workgroup-local `sq` and `sk`, computes four shared partial reductions in `red[RG][CB]`, and synchronizes five times per token (`:932,944,961,979,990`). The candidate `gdn_rec_quad_pipeline_sg32_kernel` is at `:1001-58`; it retains workgroup Q/K staging but uses actual subgroup-local IDs, with `rg=lane/8`, `c=lane%8`, `col=cb*CB+sgid*8+c`, and `stage=local_linear_id` (`:1004-24`). It replaces the shared partial reduction with four `select_from_group` operations for KV and four for output (`:1037-54`), uses two per-token barriers, and keeps `float s[RPG]` loaded/updated/stored in the recurrent loop (`:1014-18,1035-47,1056-58`). In this build those two kernels use the same 32-lane subgroup and same max work-group size; candidate uses less reported local memory but has the nonzero spill allocation.

Plausible, unproven contributors include increased live ranges from the 32 FP32 state values plus four cross-lane source values during the fully unrolled recurrence; compiler lowering/temporaries for lane-dependent `select_from_group` source IDs; and new lane/column/stage address expressions. These are hypotheses, not diagnoses: the source does not reveal the IGC physical register allocation, spill load/store instruction count, or allocation lifetime. The candidate does not explicitly materialize per-token 32-element K/Q arrays; unlike the AMD quad kernel at `:1381-91`, the SYCL SG32 candidate keeps Q/K in local memory and loads scalar `sk` values in the recurrence. Do not attribute these observed spills to a specific source variable without a kernel-specific IGC VISA/GenISA or final ISA/resource dump. Also do not infer `registers allocated=128` from these Level Zero fields; they expose no GRF allocation count.

The existing 256-GRF property at `kernels.dp.cpp:2725-36` is attached to a distinct SG16 tuned keyhead kernel, `gdn_rec_kh_tuned_kernel`, not this SG32 lane remap. Its presence in source does not show B570/Xe2 support or predict an SG32 result.

## Can a separate SG32/GRF-256 candidate use exact bundle admission?

Architecturally, the source already has the useful admission pattern in `kernels.dp.cpp:2680-2718`: get the named candidate's `kernel_id`, obtain an executable bundle for that exact ID and device, require `bundle.has_kernel`, query the compiled subgroup and max work-group size, then call `handler.use_kernel_bundle(*executable)` before submitting that exact kernel. A future isolated comparison can use a different named kernel ID, for example `GdnRecQuadPipelineSG32Grf256`, whose callable reuses the exact SG32 arithmetic and launch geometry and whose per-kernel property is `sycl::ext::intel::experimental::grf_size<256>`. Its preflight must fetch and bind that variant's own executable bundle and must never admit the default SG32 image by mistake. Keep the norm launcher, math flags, group geometry, inputs, and all other code identical between default and 256-GRF variants.

That mechanism is implementable in source, but documented safe 256-GRF use on this exact B570/Xe2 stack is **not established**. The Intel LLVM `sycl_ext_intel_grf_size` page is experimental, restricts implementation to Intel GPU with Level Zero/OpenCL, and its legal-size table lists PVC, DG2, and CRI but not BMG/Xe2. It says unsupported devices/backends may have undefined behavior and that an illegal size is undefined behavior. A compiling header, current oneAPI 2026.1.1 package, existing SG16 code, or successful exact bundle admission would not by itself prove the selected 256-GRF mode is supported or honored on B570. Do not execute this candidate on the device until the installed compiler/IGC/driver combination provides a positive target-specific support basis; the current public extension table gives none for BMG.

If support is established, separate the kernel by a distinct stable kernel type/name and ensure the GRF property is attached to that named kernel as a compile-time kernel property (rather than a broad process/compiler flag). Pre-submit admission should use only that kernel ID's executable bundle and require bundle presence, compiled subgroup size 32, work-group capacity at least 128, correct target image/device, and the same candidate source/build identity. Record `spill_memory_size`, `private_mem_size`, `localMemSize`, max work-group, subgroup size, kernel name/UUID, and the exact executable/binary identity; these resource queries are observations, not the admission proof of a 256-GRF allocation. Confirm property realization using the resulting device-image/program metadata (`sycl-grf-size=256` where represented) and compiler/IGC kernel-specific resource/ISA output (e.g. allocated GRF count). If the metadata is missing/automatic or the actual GRF count cannot be verified, mark the comparison unsupported/inconclusive; do not describe it as a 256-GRF test. Keep all pre-submit fallback behavior separate from post-submit errors, as in the existing fail-stop contract.

The Intel SYCL binary property-sets document names `sycl-grf-size` as the GRF size, with 0 or absence denoting automatic. That is a useful check on the image, but should be paired with the IGC/final device-code evidence and target support. The exact bundle is valuable because it binds the admitted ID to the same executable image later submitted; it cannot convert an unsupported extension setting into defined behavior.

## Minimal quiet discriminator after target support and parity

Keep the already accepted default SG32 kernel and a new 256-GRF SG32 kernel as two separately named variants of the same arithmetic; keep the legacy pipeline only as the correctness/performance reference, not as a combined-factor experiment. First capture compile acceptance and property realization without timing. Then run warm, unprofiled, serialized exact-bundle comparisons at a recurrence length of at least `T=32768` (or longer if needed for stable event times), with preallocated identical state, Q/K/V/gate/beta, exact workload/launch, warmed images, identical clocks/power conditions, no overlapping GPU jobs, and repeated per-kernel event timings. Compare both state and output bitwise after each path. Collect individual samples and robust summaries; keep compile/JIT time separate from kernel time. Run a distinct profiler/resource pass only after the low-overhead timing pass. Re-query exact per-kernel spill/private/local/WG/subgroup properties and collect allocated GRF count plus spill loads/stores from the exact kernel's IGC or final ISA artifact. At least one accepted parity case must cover positive T and tails/carry relevant to the full kernel; preserve fault/denial evidence separately.

The 5.0045 s controller duration from the initial gate must not be used as a latency measurement or input to any speed estimate. The 5056-byte spill property is a compelling reason to investigate, not a conversion factor for runtime. If 256 GRFs lower spill allocation, the timing comparison still decides whether total kernel time improves; the larger register file may trade against thread occupancy. If the target/property is unsupported or no reliable allocation evidence can be produced, stop this branch rather than substitute a broad global large-GRF flag, which changes unrelated kernels and no longer isolates this one variable.
