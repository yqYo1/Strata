## Exact handoff geometry and ownership

The full model geometry is 48 layers, `D=10,240` residual floats per token, and a maximum chunk `m.T=8,192`; the receipt's `STRATA_PREFILL_FIRST=0` means no short first chunk. The final chunk has `T=8,187` rows. `run_layer_major()` allocates `std::vector<float> rows((n-gpu_tokens)*D)` (`prefill.cpp:2679`); on the receipt's host-only residual path this is `262,139 × 10,240 × 4 = 10,737,213,440` bytes, 9.99981 GiB (about 10 GiB). It is ordinary host `std::vector` storage, not a second GPU residual copy. Per row the stride is `D*4 = 40,960` bytes. A full chunk spans 335,544,320 bytes; the tail spans 335,339,520 bytes.

For each layer, `run_layer_major()` sets `hand_in_` to the device residual plane only when every row is device-resident; otherwise it points at `rows.data()` (`:2760`). The per-layer `run_impl()` visits `c0=0,8192,...`, derives `T=min(m.T,n-c0)`, chooses `m.R` as the chunk's device plane or `residual_scratch`, and computes the input pointer from `(c0-gpu_tokens)*D` on the host suffix (`:3027-3060`). For the current receipt, `m.R` is the per-chunk borrowed workspace scratch, while `hand_in_` points to the host vector. The workspace carving allocates `m.R` as `T*D` floats in `take_compact_base()` (`:877-889`) and the noncompact carve (`:1279`) also has a distinct `T*D` residual plane. The compact layer-major admission uses the compact path.

The layer's `on_chunk` callback belongs to the `run_layer_major()` stack frame and closes over `rows`, `gpu_tokens`, `transfers`, and the current layer. The callback maps `row=position-pos0`; for a GPU-prefix chunk it writes to `residual_gpu_row(row)`, otherwise to `rows.data()+(row-gpu_tokens)*D`. It copies exactly `count*D*sizeof(float)` bytes (`:2766-2781`). `rows` and the optional device plane outlive the callback and every layer iteration; the layer-major `Restore` guard is declared after them and therefore drains before their automatic destruction on ordinary return/unwinding. The callback does not run concurrently with another layer's callback: each `run_impl()` is called synchronously inside the outer layer loop.

With host backing, the expected data invariant is exact and simple:

`post_moe(layer L, p0, T) == R_input(layer L+1, p0, T)` byte-for-byte.

The left side is the `m.R` image after the layer's second residual write. The handoff callback copies those `T*D` floats into the same host row interval. The next layer's input path copies that interval back into its chunk scratch before running the layer. A mismatch between these two observed records would localize a spill/reload, row-offset, scratch-rebind, or callback-boundary problem independently of GDN projections. The identity is defined for matching `p0,T`, layer adjacency, and session/request; it is not a claim that the comparison was already performed for all chunks/layers. Round-34 capture only covered 32 selected rows and layers 0–12; round 39 proposes full hashes at all boundaries but has not implemented them.

## Queue order, completion, and host reuse

`Prefill::init()` rejects a compute stream that is not in-order (`prefill.cpp:1057-1058`). `run_layer_major()` also requires an in-order compute queue for streamed-KV admission (`:2433-2435`). Residual uploads and device-prefix copies use `transfers.device_residual(m.cs,...)`, which calls `q->memcpy` on the supplied compute queue (`:2208-2211`); host transfers use `transfers.activation(m.cs,...)` on the same queue (`:2213-2216`). The copy queue `m.copy` streams expert weights; it does not own the residual handoff. No cross-queue dependency is needed for this residual copy path because the source/destination work is submitted to `m.cs`.

At each chunk, `run_impl()` submits the chunk's upload before its consumers. With an in-order queue, the asynchronous host-to-device copy is ordered before kernels subsequently submitted to `m.cs`; there is no separate host wait at that upload call (`:3057-3061`). Before calling `on_chunk`, `run_impl()` waits for `m.cs` when a layer-major callback is installed (`:5313-5333`). The callback then submits device-to-host `q->memcpy` to `rows` and waits on its returned event before it returns (`run_layer_major():2771-2778`). Thus the producer is finished before the host copy starts, and the host interval is complete before the next layer can read or overwrite it. The outer loop also waits `m.cs`, `m.copy`, and finishes the expert stager before beginning the next layer (`:2725`); this is a conservative layer boundary, not a missing residual dependency.

For the D receipt's all-host path, the byte offsets are consistent: producer output uses `(row-gpu_tokens)*D`, next-layer input uses `(c0-gpu_tokens)*D`, and both use `T*D*4` bytes. With `gpu_tokens=0`, the first full chunk uses byte interval `[0,335544320)`, each later full chunk advances by that amount, and the final tail starts at `31*335544320` and ends exactly at `10,737,213,440`. The source has no fixed-8192 copy length in the callback or upload; both use current `count/T`. Therefore the short tail does not read or write beyond the allocated host vector on this path.

For optional GPU-prefix configurations, `gpu_tokens` is rounded to a complete chunk boundary when it is less than `n` (`:2658-2662`). This prevents a chunk from straddling the device/host split. `residual_gpu_row()` maps the reused scratch prefix or allocated device suffix (`:658-660`). With `inplace=false`, input is copied to `m.R` and the callback copies out to a separate GPU/host backing slot; with `inplace=true` and all rows on GPU, `m.R` aliases the row's persistent backing and the input copy is skipped when pointers match. Those routes have distinct alias rules and must be recorded if later selected; they are not active according to the D receipt's environment/defaults.

The Khronos SYCL 2020 specification says `queue::memcpy` returns an event and accepts host pointers or USM pointers accessible to the queue; `event::wait()` blocks for completion, while `wait_and_throw()` additionally reports asynchronous errors. It also states that `in_order` orders submissions on that queue, not on other queues. [SYCL 2020 queue/event and USM copy contract](https://registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html). The source's `event.wait()` is sufficient to protect `rows` from reuse before the copy completes, but it is not itself an asynchronous-error report.

## Failure and cancellation paths; concrete limitation

A normal success path drains each layer/chunk as above. Cancellation is checked before each outer layer and before each inner chunk (`:2725,:3028`); a cancellation returns false, and the `Restore` guard attempts `m.cs->wait()`, `m.copy->wait()`, `m.stager->finish()`, and any retained KV-copy drain before restoring object fields (`:2693-2708`). Since the guard is declared after `rows`/device rows, successful drains precede host/device backing release on early return. A `run_impl()` failure similarly exits to this guard. If queue operations are still in flight, this drain is the ownership barrier preventing use-after-free or host-vector destruction.

There is one concrete async-error-handling limitation in this otherwise ordered ownership path. `transfers.device_residual(...).wait()` and `transfers.activation(...).wait()` use `event.wait()`, not `wait_and_throw()`. The per-chunk `DPCT_CHECK_ERROR(m.cs->wait())` and normal `m.cs->wait()` calls likewise use queue `wait()`; `DPCT_CHECK_ERROR` catches synchronous C++ exceptions but the compatibility header says SYCL asynchronous errors are not error codes. More importantly for failed/cancel returns, `Restore::~Restore()` calls queue `wait()`/stager drain directly without a `try/catch` (`:2693-2708`), while it is implicitly `noexcept`. If a drain surfaces a C++ exception, it can terminate during stack unwinding instead of returning a clean diagnostic failure; the source does not prove whether this target's async handler will surface an error at those exact waits. This is a bounded error-reporting caveat, not evidence of a residual data race or a captured spill/reload mismatch. On a failed drain the residual buffers cannot be considered safely reusable; retain failure status and quarantine them until completion/error handling is established.

The outer `Prefill::run()` calls `drain_pipeline()` after `run_layer_major()` (`:2342-2347`), but that function joins successor layer-split tasks; in this single-GPU layer-major path it is not the residual completion barrier. The relevant same-queue drains are the `run_impl` callback wait and `run_layer_major`'s layer/restore waits. Do not credit the pipeline drain with cross-queue or host-buffer completion that it does not establish.
