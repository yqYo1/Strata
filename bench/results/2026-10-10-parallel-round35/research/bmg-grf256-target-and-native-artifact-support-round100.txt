# BMG/Xe2 GRF-256 target support and native-artifact review (R100)

Review date: 2026-10-10. Type: read-only source, documentation and artifact inventory. No builds, tests, executions, GPU/device/CPU queries, profiler queries, Git operations, configuration changes, source edits, or cleanup were performed.

## Finding

**BMG/Xe2 can compile and run kernels described as using a 256-GRF allocation in at least one published Intel-project report, so the public extension table's omission is not proof that BMG hardware cannot do 256 GRF. However, safe/defined use of `sycl::ext::intel::experimental::grf_size<256>` on this B570 stack (oneAPI 2026.1, L0 Intel driver 1.17.39395, exact IGC/NEO package) remains UNKNOWN.** No version-matched Intel target support declaration or product-helper legal-size table for the pinned build was found in reviewed primary material. Do not treat this as authorization to execute a property-256 candidate.

The public experimental SYCL extension says it is implemented only for Intel GPUs via Level Zero/OpenCL, but also warns use on unsupported devices/backends may be undefined without a diagnostic. Its legal-size table enumerates PVC and DG2 (128/256) and CRI (128/256/512), omitting BMG; it says non-listed sizes for the device cause undefined behavior. This establishes a documentation gap and a safety constraint, not a negative hardware capability claim. The local oneAPI 2026.1 header defines the API/macro and statically accepts 128 or 256. Header acceptance is not a target capability test.

Positive but non-version-matched evidence: Intel LLVM issue #22240 reports an Intel Arc Pro B60 / BMG-G21 kernel with `GRF count: 256`, under oneAPI 2025.3.2 and IGC 2.28.4/2.34.4. It reports differing spill outcomes across compiler versions. This is evidence that 256-GRF code generation is used on BMG in a distinct workload/configuration; it is not an Intel support contract, not evidence that the SYCL kernel property was used, and not evidence for B570 or the pinned 2026.1 + driver combination. Intel's LLVM SYCL lowering source recognizes image property `sycl-grf-size=256` and appends `-ze-opt-large-register-file` for a non-ESIMD Level Zero image; that proves a lowering path in the current source branch, not this installed binary's target-specific legality or realized allocation. NEO's current debug setting has a broad 256-GRF compilation flag, likewise not proof for this per-kernel SYCL property or pinned stack.

## Evidence and applicability

- Intel LLVM experimental extension: https://github.com/intel/llvm/blob/sycl/sycl/doc/extensions/experimental/sycl_ext_intel_grf_size.asciidoc (experimental; backend statement and legal-size table). BMG absent; unsupported target behavior is warned undefined. Current public table is not version-pinned to installed oneAPI package.
- Installed header `/opt/intel/oneapi/compiler/2026.1/include/sycl/ext/intel/experimental/grf_size_properties.hpp`: defines `SYCL_EXT_INTEL_GRF_SIZE 1`, `sycl-grf-size`, and compile-time static assertion for 128/256 only. Does not enumerate target/device support.
- Intel LLVM program manager source: https://github.com/intel/llvm/blob/sycl/sycl/source/detail/program_manager/program_manager.cpp (current sycl branch, lines 2635-2748): maps image property 256 to `-ze-opt-large-register-file`, 512 to `-ze-opt-register-file-size=512`, 0 to auto-large-GRF option. Branch not verified against exact 2026.1.1 compiler source commit.
- Intel LLVM report: https://github.com/intel/llvm/issues/22240 (user-reported, Intel project): BMG-G21 Arc Pro B60, oneAPI 2025.3.2; reports a 256-GRF kernel and IGC spill regression. Relevant affirmative feasibility evidence, but version/workload/property limitations above apply.
- Intel Compute Runtime current source: https://github.com/intel/compute-runtime/blob/master/shared/source/debug_settings/debug_variables_base.inl contains `ForceLargeGrfCompilationMode`, described as adding `-cl-intel-256-GRF-per-thread`. It is a broad debug setting and current master, not pinned driver proof.
- Intel LLVM offload design: https://github.com/intel/llvm/blob/sycl/sycl/doc/design/OffloadDesign.md documents AOT pipeline through post-link, llvm-spirv, OCLOC, each `(triple, arch)` creating a separate device binary; lists Battlemage G21 as `bmg_g21`. Validating BMG as a target name does not establish legal GRF sizes.
- The frozen R99 gate says the exact SG32 candidate has Level Zero `spillMemSize=5056`, private memory 0, local memory 1024; reference spill 0, local 1536. These kernel resource queries do not reveal selected GRF count. The run identity pins SYCL 2026.1 / UR 0.12 / Level Zero loader 1.32 / Intel driver 1.17.39395, but no captured kernel VISA/GenISA or version-matched capability response is present.

## Safe inspection path for a future authorized artifact capture

First preserve the exact executable's SYCL device image (including its property sets and target triple) and hash it. Use `syclbin-dump` on that saved executable/image as a read-only metadata inspection; confirm the image carries `sycl-grf-size=256` on the separately named kernel and the expected BMG-compatible target. This only proves the request metadata survived packaging. For actual allocation/spill attribution, capture an IGC kernel-specific VISA/GenISA/final-ISA resource dump from compilation with compiler/driver build IDs, kernel identity and allocated GRF count; correlate its spill allocation with the matching kernel. AOT compilation to `bmg_g21` via the documented offline compiler route can produce an artifact without GPU execution, but it is a new compile and is not evidence of what the existing JIT image did. Do not change global `IGC_ExtraOCLOptions` or other compiler settings for a per-kernel experiment. An offline build that accepts `-ze-opt-large-register-file` alone still would not settle whether the pinned runtime/device accepts and honors this SYCL property. Exact bundle admission and Level Zero spill/private/local queries are useful further identity/resource checks, but cannot certify legal support or physical GRF allocation by themselves.

## Conclusion for the current candidate

Retain the default-SG32 candidate as the only supported path pending authoritative target-specific support for the exact compiler/IGC/NEO stack. The 5056-byte spill report motivates investigating code generation, but does not justify testing an undefined property. To change UNKNOWN, obtain version-matched Intel documentation/source or Intel confirmation naming BMG/Xe2 and 256-GRF support, then inspect exact candidate image metadata plus kernel-specific final ISA/resource data. Any eventual timing experiment should follow only after the support and realization gate passes.
