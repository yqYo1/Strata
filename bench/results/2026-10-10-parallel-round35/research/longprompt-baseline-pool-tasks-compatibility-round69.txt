Finding: baseline 869 cannot take `--pool-tasks`

The baseline binary SHA-256 is `86972697ecb1903750d202f8be29a7a1da351eb3415678c3e3b6af790804d1c8`; its recorded build receipt is `20589f1486dedaf825052e95560155acd30e6017b7967e2df476b5dd41989c43`. It predates the CLI wiring and has no `--pool-tasks` parser option. Do not add that argument to a reference command: the baseline will reject it. The source review in `pool-tasks-implementation.txt` records the sole candidate-source change as `sycl/src/program/generate.cpp`: CLI option definition/parser and passing its value to the existing `ExpertPool` fifth argument. The constructor already defaulted that argument to zero.

`--pool-tasks` only sets the number of row-range jobs used by batched GU/Down phases: `phase_tasks(rows)` returns the automatic `3 * (workers + host-participant)` when zero, otherwise `min(rows, requested)`. `drain()` maps each claimed task to a contiguous interval in the concatenated expert-row range (`g0 = mrows * i / mtasks`, `g1 = mrows * (i+1) / mtasks`) and calls the same row kernel for that interval. The source change does not alter the kernel, reduction order within a row, synchronization, cache, KV or prefill. It does alter job granularity and scheduling. Thus the option's absence prevents a matched task-count/performance control on 869; it does not invalidate 869 as a separate numerical reference.
