# Round 46: R45 chunk-major resident-residual novelty audit

## Finding

Withdraw the R45 candidate's novelty and its description of the qualified 869 run as currently using layer-major. The proposed schedule—one prompt chunk traverses all layers while its FP32 residual stays in device scratch—is the ordinary `Prefill::run_impl` path in the exact source object associated with the qualified binary. The run explicitly selected that path (`STRATA_PREFILL_LAYER_MAJOR=0`). It already avoids the 10.7 GB full-context host residual plane that R45 attributed to the current run. There is no residual-traffic optimization left to claim by simply restoring that schedule.

This is a source/applicability conclusion, not a timing conclusion. It does not establish that ordinary chunk-major is faster or establish the current layer-major tradeoff. If that known tradeoff is revisited, compare the already-existing `run_impl` arm against `run_layer_major` under matched prompts, exact executable and environment, with correctness/state gates and measured residual and expert transfer bytes plus end-to-end timing. Do not present chunk-major residency as a new algorithm.

## Source trace at the exact object

- `Prefill::run` at `prefill.cpp:2332-2345` chooses `run_layer_major` only when the opt-in environment is `2`, or is `1` and the prompt is multi-chunk. With recorded value `0`, it calls `run_impl`, then drains the pipeline.
- In `run_impl` (`:2794+`), the outer loop is chunk-first (`:2955`, `c0 += chunk_len(c0)`); the layer loop `l=LB..LE` is inside that chunk loop (`:3501`). Thus each chunk passes through the layer stack before the next chunk.
- The residual `m.R` is allocated as per-chunk device storage: `take_compact_base` takes `T*D` floats for it (`:874-880`; compact mode is selected for this receipt), with the non-compact allocation also taking `T*D` at `:1276`. Per chunk, `m.R` is pointed at the device resident residual row window or reusable device scratch (`:2964-2966`). In the ordinary no-layer-split case, embeddings are written into this buffer; the conditional `hand_in_` upload at `:2978-2993` only applies to layer split. The layer kernels consume and update `m.R` as layers proceed (e.g. hyperconnection norm reads at `:3574-3575`). There is no full-context residual-plane allocation in this ordinary path.
- By contrast, the explicit layer-major arm requires one full-context host `rows` plane and calls `run_impl` by layer/chunk with callbacks to transfer rows (`:2381+`, especially `:2647-2648` and `:2683-2786`). This is the source of the large residual handoff described by R45, but it is an opt-in branch that the 869 run disabled.
- Existing ordinary QSA staging is also chunk-scoped: chunk-local prefetch bookkeeping begins at `:3147-3205`; the `kv_prefetch` path copies a prefix from host into the shared stage, subject to its guards (`:3151-3194`). K/V append mirrors to host authority and the stage (`:3717-3748`). `take_stage` allocates the single shared stage based on session maximum capacity (`:1382`; documented allocation details in R3). For this run, int8 KV and 32768 resident cells are explicit CLI settings while max context is 262144. This is an already-existing different lifetime/copy schedule question, not a new residual-residency candidate.
- Expert staging is performed in `run_impl`'s chunk execution. `stream_all` setup and expert-job sequencing are at `:3206+`; the layer loop follows at `:3501`. Therefore chunk-major may repeat portions of layer weight staging across chunks, depending on cache/admission and this source path. That is the known cost to measure against layer-major's weight reuse. No byte count or performance estimate is inferred here.
- `run_layer_major` has additional eligibility restrictions at `:2399-2412`, including `kv_mode != 0` rejection (`:2404-2408`) and PLE preload rejection. Its residual-plane schedule and all-resident-KV requirement should not be conflated: the 869 run's int8/32768 configuration cannot use that layer-major arm, and already ran the ordinary chunk-major fallback.

## Decision

R45's lines 5-13 and 33 describe the chunk-major resident-residual schedule as distinct from the current qualified run; that is incorrect for this baseline. Retain the R45 external-literature context only as context for scheduling tradeoffs, not as evidence of a new optimization. The remaining potentially distinct topic is whether a carefully gated layer-major implementation can support streamed int8 KV by retaining/reusing its existing single QSA staging plane across chunks, as scoped in `layer-major-streamed-kv-round3.txt`. That changes the layer-major branch's KV eligibility/stage lifetime and needs its own source and measured-arm comparison; it does not rehabilitate the R45 residual proposal. No implementation, test, build, GPU run, or cleanup was performed for this audit.
