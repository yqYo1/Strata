Question and scope

Do not combine that with scale expansion, gathered lookup, paired Gate/Up Q8 loads, call-target elimination, row batching, or predecode. This is a hypothesis and an implementation contract, not an implementation, performance estimate, or adoption recommendation. The source candidate: index spread only
In `src/kernels/cpu/iq_avx2.cpp`, `HiSpread::iq2s` stores the two high index bits from each qh byte in the low byte of each 64-bit lane. `grid_indices` interleaves those bytes with the low `qs` bytes into 16-bit indices. `Fmt32<22>::decode` already uses this mechanism, then performs the same four scalar codebook reads; `Fmt32<122>` instead uses a 64-bit gather. These are NT-batched row-kernel decode helpers, not the NT1 GGML trait routine.

A future type-22 NT1 helper would copy only the index-construction substitution: for each IQ2_S grid byte, replace the direct GPR shift/mask/OR construction of `qs[k] | ((qh << (8-2*k)) & 0x300)` with the existing HiSpread lookup plus low/high-byte interleave. Keep exactly the same four 10-bit indices in each q2 vector and the same scalar `iq2s_grid[index]` loads and lane order. It must be a type-22 NT1-only route; no default dispatch or other format changes. This isolates the repeated index work visible in the linked loop.

Do not also use `ScaleVecs::s16` in this first candidate. In the pinned NT1 source, scale unpacking occurs once per Q8_K block, while grid-index construction recurs in four inner iterations per block. `ScaleVecs` substitutes a data-dependent scale-table load for the current nibble extraction/shift/pack sequence. Combining that with index spread would prevent attributing code-size, cache-load, spill, correctness, or timing changes to one mechanism. It is a separate hypothesis, not part of this candidate. Similarly excluded are the already-screened `_mm256_i32gather_epi64` IQ2_S path, R85 paired Gate/Up activation-load reuse, direct-call-only control, NT2 `Fmt32<22>` arithmetic, and expert-local decoded caches.

Exact integer and floating-point preservation contract
The candidate changes integer index construction only. For each `qh` byte and four `qs` low bytes, it must produce exactly the same indices `qs[k] | ((qh << (8-2*k)) & 0x300)` for `k=0..3`, each in `[0,1023]`, in the same lane order used by `_mm256_set_epi64x`. Exhaustively compare the helper against that scalar expression for every `qh` value `0..255`, every `qs` byte `0..255`, and each of the four shifts. Confirm every possible IQ2_S grid index is exercised. Confirm accesses remain within the `block_iq2_s` object and retain exactly four active codebook values in each vector.

Do not change any of the pinned dot's surrounding arithmetic: `d = fp16_to_fp32(weight.d) * q8.d`; scale-byte decoding; Q8 vector loads; sign mask creation and two's-complement sign transfer; `maddubs` and its saturating pair semantics; `madd`; additions to `sumi1` then `sumi2`; block `sumi1+sumi2`; int32-to-float conversion; one `fmadd(d, block_sum, accumf)` per 256-value block in ascending block order; final eight-lane horizontal-add tree; and post-reduction multiplication by `0.125f`. Preserve separate row accumulators and the scalar Gate/Up finish expression. No reassociation, multiply folding, FMA relocation, or combined Gate/Up accumulator is allowed.

R88's admitted production-quantized Q8_K domain is required for the bitwise proof: finite source blocks, finite nonzero selected max, finite iscale and scaled products within the normal quantizer range; keep raw `-128`, NaN/Inf, and exceptional-scale cases in a separately labeled robustness bucket. For admitted Q8_K bytes, the signed range is `[-127,127]`; IQ2_S grid magnitude is at most 43 and encoded scales at most 31. R88 bounds each adjacent signed-byte pair sum by `2*43*127=10,922`, below int16 saturation, and bounds the scaled int32 lane update by `677,164`; the per-lane running bound stays far below int32 overflow. These bounds justify retaining the existing integer dot schedule, not a different one.

Prototype and generated-code acceptance gates
Before any production change, root should require all of these checks for the candidate build:

1. Establish the actual active baseline and test cost of an NT1 type-22 direct-call-only control, which R85 already specifies. `native_gu_rows` calls the type-trait function pointer per row; a direct helper may otherwise mix call-target removal with index decoding. Keep baseline, direct-call-only control, and index-only candidate distinct. If linked baseline output already devirtualizes the call, record that and drop the call-control arm.
2. Compare candidate indices and decoded grid vectors exactly to the pinned function over the exhaustive finite index domain. Then compare every row dot bitwise with the pinned direct symbol and current NT1 trait path using Q8_K bytes made by the production quantizer on R88-admitted source inputs. Keep the R85 per-row Gate, Up, and final GU result checks; for the bounded H=2560 cohort, cover all ten blocks per row and all 640 Gate/Up output pairs per selected expert. Do not hand-fabricate legal Q8_K bytes or substitute synthetic data for a live activation claim.
3. Inspect the candidate's linked helper and full caller loop, not source intent alone. Confirm the index masks/shifts/OR chain is actually reduced; the same eight scalar codebook loads per inner iteration remain; no gather appears; signed Q8, `maddubs`/`madd`, both accumulators, block FMA order, reduction and post-scale remain; there is no extra hot-loop stack scratch/spill, helper call, or register-save traffic that erases the intended change. Compare against the saved baseline symbol from the exact calibration executable and bind new disassembly to its own binary hash, compiler, flags, and source/object identity.
4. Only after exactness and codegen gates, compare isolated component measurements on the same Zen 3 host, compiler, inputs, weights and placement, with train/disjoint holdout and per-row samples. Keep the three arms separate. Existing calibration summary describes synthetic activation characterization and marks its pool-fit gate false; it is not evidence that this decoder is material to live inference. A future measured service gate must justify additional kernel work. No performance result or estimated speedup is made here.

Likely code-generation failure modes are material: `grid_indices` writes an eight-element temporary index array, and a table lookup adds a data-dependent load. The source does not show whether the compiler can avoid stack stores/reloads or whether the new table access is cheaper than the existing shifts and ORs on Zen 3. If the linked candidate retains the GPR sequence, introduces a scratch spill, increases hot-loop work, or fails the call-isolated component gate, reject it. Do not add `ScaleVecs`, gather, or paired-load fusion to rescue that result in the same comparison.

External applicability remains negative for the target loop. The [pinned llama.cpp IQ-panel change](https://github.com/ggml-org/llama.cpp/commit/85c55223caf0a2ad0d1d88e5a73ab3fe36107867) is batched IQ-panel/8x8 GEMM with a different dataflow and minimum useful batch; it is not an NT1 exact-row decoder. The [ik_llama IQK discussion](https://github.com/ikawrakow/ik_llama.cpp/discussions/8) concerns `pshufb` lookup for very small alphabets and different layouts; IQ2_S has a 1024-entry packed grid and still needs the 10-bit index-to-qword mapping. The [Vec-LUT article](https://xxxxyu.github.io/blog/vec-lut-parallel-low-bit-llm/) targets ternary/small-alphabet and parallel-token lookup layouts, not this packed IQ2_S NT1 schedule. These sources add no applicable new mechanism. The historical gather reports in R89 remain architecture/format-specific; the i7-12850HX IQ2_S gather regression and Ryzen 7950X IQ3 gather result are not Zen 3 IQ2_S evidence and are not used to predict this index-spread candidate.

Conclusion
One narrow source-level experiment can be specified: change only IQ2_S NT1 grid-index high-bit expansion to the existing HiSpread/grid_indices mechanism, retaining scalar codebook loads and every sign, integer, and floating-point operation. This is reuse of existing local source machinery, not a new algorithm. Its temporary-array and table-load costs may defeat the change; only the linked-code and isolated Zen 3 validation gates can determine whether it survives. No candidate speed, current live input distribution, or adoption priority is established.
