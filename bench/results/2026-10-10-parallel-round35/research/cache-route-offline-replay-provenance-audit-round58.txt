## Provenance and replay path

The consumer is a separate CPU utility and does not import the controller at module top level. It verifies the exact v6 controller bytes, AST-extracts only `HISTOGRAM_*` constants and `parse_histogram`, and compiles that selected code. This binds the independent histogram parser to the closed v6 caller while avoiding execution of controller setup or lifecycle code.

All source/data reads go through `bounded_file`/`verified_file`: no-follow final open, owned regular single-link file, size limit, same-open-file metadata recheck after reading, and SHA-256 comparison. Caps are 64 MiB generally, 16 MiB for the receipt, 262,144 bytes for the controller, 131,072 for helpers/metadata, and 196,632 bytes for the exact profile. The full raw stderr path must resolve to the receipt run's `debugger/inferior.stderr`; the full byte count and SHA are checked before replay. Each of the four request intervals is ordered/nonoverlapping, range-checked, independently SHA-checked, bound to the same raw path, and compared with the receipt's offsets and parser/shape/profile hashes. Raw pair-frame lines must be newline-terminated, at most 65,536 bytes, and each marker must be inside exactly one request interval. The four requests' pair-frame bytes are cumulatively capped at 16 MiB.

For each request, the consumer requires its exact math gate, one DONE row, one raw native-dispatch histogram row, and an interval whose parser returns the expected ordinal, complete fresh 64-token/32K request, static-residency map and reconciled counts. The parser requires strict sorted unique `(layer,expert)` pairs, exact sparse totals, full equal-layer route coverage, DONE reconciliation, and the fixed no-offload classification. The STRP profile parser checks geometry, complete rank table, inverse table, derives the existing 128-resident map and checks its FNV slot fingerprint. The pinned metadata parser validates the 48-layer type/layout map. The shape helper derives NT1/NT2 job counts, reconciles refused-pair jobs against actual per-format/per-phase histogram cells, and returns ordered canonical pair shapes; the consumer compares their SHA with each receipt's canonical digest.

The output separates observed CPU exposure cells from `default_resident_coverage` (entries, callback pairs and typed logical rows for the default residents). Source and docstrings explicitly limit the result to fixed captured static-route coverage counts. The consumer has no reference order/window stream or measured costs and does not reconstruct compatible-group LRU, traffic, CPU service time, latency, a new quota vector, or policy benefit. Counts reflect the recorded routes under the actual default map; different residency may change later numerical routes. This matches the R42/R52/R53 evidence boundary.

The receipt also carries candidate-header and H-source pins, model/profile identity, pack metadata hashes, and the v6 wrapper source hash. The consumer directly enforces the v6 controller, parser, shape helper, profile and `native_experts.txt` hashes it uses; the receipt SHA binds the broader recorded source-pin fields but this utility does not independently reopen or revalidate every H-source/header/model shard. That is appropriate for count replay inputs only if the caller supplies the intended exact receipt digest and does not promote this utility to a model/build qualification check.

The C/D/r5 negative-status gate is explicit: it requires C original math false, D original health and math false, and r5 original math/health false. Diagnostic/non-adoption fields are also required false. The literal fixture source covers exact-boolean success gates, active receipt rejection, one preserved r5 failure negative, cleanup-true rejection, controller identity rejection, malformed digest rejection, full-file/interval SHA and range errors, orphan/extra/misplaced frame errors, overlapping intervals, literal canonical hash/order/shape changes, and resident-only coverage arithmetic. These are source fixtures; this review did not execute them.

## Source-only findings and limits

1. **Narrow cleanup-evidence gap in the generic gate.** `closed_gate` rejects any truthy value in `record.get('cleanup', {}).values()`, but it does not require the cleanup object or expected keys to exist, nor does it check an explicit survivor list. An absent or empty cleanup map passes that clause; the fixture's accepted record deliberately uses `cleanup={}`. The supplied pinned v6 receipt has the explicit three false cleanup flags and therefore satisfies the evidence we inspected, but the consumer's generic negative gate is weaker than its “no survivor/cleanup” claim for a different externally supplied receipt. Before using it as a reusable admission gate, require the expected cleanup keys to be present with literal `False` values (and any explicit survivor field to be empty when the receipt schema provides one), then add missing-key/empty-map fixture negatives. No source edit was made.
2. **Receipt digest is caller-supplied, not built in.** `--receipt-sha256` is mandatory and validated as a lowercase 64-hex digest; the utility verifies the receipt against that value. The digest is not a constant in the utility, so the invocation must supply the exact closed v6 receipt SHA above. The nearby source comment still says the future closed-v6 digest is “deliberately unknown now,” which is stale for this closed receipt, but does not weaken the explicit hash check. This audit did not inspect or run the invocation.
3. **No replay result is asserted.** The code and receipt pins establish a reviewable replay contract, not successful consumer execution. Tests and replay remain separate evidence. No runtime/model/GPU qualification or performance claim follows from the source review.

The compact output's intended consumer is fixed-trace count analysis. Keep it separate from the actual v6 result and any future static quota selection/holdout decision; the A/B/A/B requests contain two prompt fixtures repeated, not four independent prompt samples.
