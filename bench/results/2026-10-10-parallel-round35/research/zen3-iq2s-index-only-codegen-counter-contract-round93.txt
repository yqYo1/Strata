R92 offset correction
R92's phrase “qword starts at byte offset 30 relative to `qs[0]`” mixed coordinate origins. For final `j=3, half=1`, the qword starts at `block_iq2_s` byte offset `2 + 8*3 + 4 = 30`, which is `qs[0]`-relative offset `30 - 2 = 28`. It reads `qs[28..35]`, within `qs[0..63]`. The bounds conclusion remains correct. The qh access and the intentionally unused unpack outputs remain within the object geometry as R92 described.

Decision question and minimum discriminators
R91's candidate changes index expansion only: current GPR shifts/masks/ORs are intended to become a small `HiSpread` table load plus byte interleave/unpack, while keeping scalar codebook lookups and the dot/reduction schedule. The minimum evidence should answer three distinct questions:

1. Did linked machine code remove the targeted scalar integer work, and what work replaced it? This is a disassembly/count question, not a counter question. Diff complete hot-loop blocks from the exact baseline and candidate executable. Record per loop iteration and per 256-value block: macro-instruction counts; index-related shift, mask, OR and move operations; spread-table loads; unpack/interleave instructions; address-generation forms; codebook loads and their count; register usage; stack-frame delta and every hot-loop stack access; spills/reloads; branches/calls; and any changed loop unroll. Include the full caller and helper (or inlined region), exact binary hashes, tool/version, compiler/flags, ISA, source/object identities. The baseline's scalar codebook load count is not a performance proxy; verify it stays eight per inner iteration and that no additional hot-loop loads or spill traffic obscure the substitution.
2. Did the complete isolated CPU work take fewer cycles? For the already-approved controlled CPU component harness, the first counter pair is `cycles` plus `instructions` (with the exact PMU/event aliases resolved on that host). Report raw counts, enabled/running time or multiplex scaling, repetitions, affinity/CPU identity and frequency context. `cycles` directly discriminates end-to-end work cost; `instructions` checks whether the compiler removed or added dynamic instructions at the measured scope. Neither counter identifies a specific source instruction, queue, or AGU bottleneck; correlate them with the linked-code diff. If events cannot be scheduled together without multiplexing, collect separate, equivalent passes. Counter availability and permission on the current host are UNKNOWN.
3. Did a newly introduced table access behave as a data-load problem? Only if available and justified by the counter preflight, run a separate low-rate AMD IBS Op sample pass. IBS Op can attach precise IP to sampled operations and report data-cache/TLB source/latency information; inspect whether samples land on the new `HiSpread` lookup or spill loads and whether their source/latency differs across the two versions. This is a diagnostic discriminator for load behavior, not the primary timing comparison. Sampling has overhead and finite-sample uncertainty, so it must not replace cycles and should not be run simultaneously with the uninstrumented timing pass.

How observations map to the proposed machine-code differences
- Fewer scalar shifts/masks/ORs with fewer dynamic `instructions`, and no compensating integer instructions, supports the narrow code-generation hypothesis. Static disassembly is the exact proof of which instruction classes disappeared. The standard retired-instruction counter only gives aggregate instruction count and cannot attribute a delta to those operations by itself.
- An added `HiSpread` memory lookup and `vpunpck*`/move work are visible statically. If total `instructions` falls but `cycles` does not, the replacement may have shifted pressure from integer execution to load/address generation, front end, dependency latency, or other resources; counts alone cannot identify which. IBS Op's precise IP/data-source data can test whether sampled load latency/cache misses concentrate on the spread-table access, subject to event support and sample quality.
- More address-generation instructions, memory operands, or stack-slot traffic are directly enumerable in disassembly. Ordinary aggregate PMCs do not measure “AGU pressure” as a self-explanatory quantity. Do not claim AGU saturation from a static load count, a `cycles` delta, or an LLVM model alone. If a specific dispatch/LS event is later proposed, first identify its exact name/encoding and semantics for the detected family/model and kernel; then demonstrate it is exposed, schedulable and reliable on this host before adding it.
- A stack spill is first and most decisively a generated-code finding: record stack loads/stores inside the hot loop and compare stack-frame shape. Aggregate cycles/instructions cannot tell whether an extra load is a spill. IBS can optionally locate sampled stack-load cost, but cannot be used to rule out rare spill cost from absence of samples.
- The LLVM Znver3 scheduling model describes modeled resource usage (including ALU, AGU, load and instruction scheduling) but is a compiler cost model, not a hardware observation for this binary. Use it only to label candidate pressure hypotheses after the emitted instruction stream is known; do not convert model occupancy into predicted Zen 3 speed.

Profiler and PMU selection cautions
Intel VTune hardware event-based sampling requires a genuine Intel processor per Intel's requirements; VTune may still be useful for non-PMU/general tasks, but it is not the chosen PMU collector for AMD Zen 3 here. AMD uProf or Linux `perf` are the relevant AMD-facing paths. Do not borrow Intel Top-Down metrics or Intel event names for this comparison.

Linux `perf` event names and permissions must be checked at collection time. Kernel `perf list` and the per-PMU sysfs `events`, `format`, and `type` files expose the local event vocabulary/encoding; the kernel's `perf_event_paranoid`, Linux capabilities, container/VM restrictions, kernel version, `perf` version and whether PMU access is virtualized can change what the process can collect. Record those facts, selected core/PMU device, event aliases and underlying encodings. Do not assume that a generic alias maps to a particular raw event or that an AMD event listed in a different kernel/CPU model is usable here. This report deliberately performs no host query; all availability fields remain UNKNOWN.

AMD Family 19h revision material makes indiscriminate use of retired-op counters especially risky. The Family 19h Models 00h–0Fh Revision Guide notes a retire-event overcount erratum covering PMC 0xC0 (retired instructions) and 0xC1 (retired uops), among other retire events, and documents an IBS sample signaling issue. Applicability depends on exact family/model/stepping and firmware workaround; identify the actual Zen 3 CPU before interpreting these entries. Do not label PMC 0xC1 as executed micro-ops merely because older tool labels say “uops”: the cited AMD revision document describes it as retired Uops, while AMD uProf's guide describes the corresponding event as retired macro operations. Resolve the event semantics against the applicable PPR and current perf event map. If 0xC0 is affected on the actual processor, treat `instructions` as a cross-check only or prefer static instruction counts and an alternate validated observation; do not silently claim exact counts. IBS Op may also be unavailable, restricted, virtualized, or affected by errata. Keep all such status UNKNOWN until host-specific validation.

Minimal collection order (no counters until the code boundary is closed)
A. Confirm bitwise/correctness gates and the linked-candidate comparison for the same compiler, flags and target. If it still has targeted shift/or chains, spills, helper overhead or changed dot work, stop the candidate; counters cannot rescue it.
B. Record the exact processor signature (family/model/stepping), BIOS/microcode, OS/kernel, `perf` and compiler versions, privilege state, PMU device list and event metadata. Resolve `cycles` / `instructions` names to local event config; ensure events open and are not multiplexed, or report the scale/limitations. Check applicable AMD errata and PPR event descriptions before interpreting raw counts.
C. Run the isolated component timing passes without IBS/profiling instrumentation, with the two generic counters if validated. Preserve per-trial counts rather than only aggregate averages and bind outputs to binary hashes and commands. The candidate's timing conclusion is still a measured component result, not a model or service result.
D. Only if A–C leave a concrete uncertainty about the spread-table load or spill traffic, run the optional IBS Op diagnostic in a distinct collection. Record sampling period/configuration, accepted sample count/loss, precise IP distribution and event fields available. If IBS is unsupported, restricted or affected in a relevant way, record UNKNOWN/unavailable and stop rather than substituting guessed PMCs.
E. Do not widen the counter set unless the initial observations leave a specific unresolved discriminator. For each additional raw event, document source, selector/umask, unit, filters, model validity, scheduling conflict/multiplexing, known errata, and the expected result under each competing mechanism before collecting it.

Conclusion
For this narrow candidate the minimal defensible evidence is: exact linked-code delta including loads and spills; validated uninstrumented `cycles` plus `instructions` on an isolated component; and optional, separate IBS Op sampling only if the added table load's behavior remains unclear. Static instruction counts directly answer what changed; counters establish aggregate runtime behavior; IBS can help locate a load-related explanation. Zen 3 event availability, perf permissions, exact alias mappings, counter reliability and IBS support on the intended host all remain UNKNOWN pending the explicitly deferred host preflight. No performance direction or size is predicted here.
