## Fixture independence and limits

The nine new tests do not import or execute controller top-level code. The framing tests execute extracted named controller functions against fake `os.read`, in-memory stdout/events, a temporary directory, and the pure pinned framer. Literal byte strings, line order, raw-byte preservation, and expected failures provide useful black-box expectations for `available_stdout`, `boundary`, `protocol_line_kind`, and budget helpers. They cover a coalesced DONE+extra row, a partial DONE suffix with EIO, unexpected QUIT output versus empty-read EOF, SAVE-vs-GEN grammar examples, an exact line-limit burst and raw retention on framing failure, write-reservation failure, external aggregate overflow, and cleanup/signal/exit inputs to the source's health expression.

The oracle is not a controller emulator: it never executes `line`, `send`, startup/GEN/SAVE/QUIT loops, OwnedGdb, real file writes through the whole lifecycle, or final `SystemExit`. The process-health test parses and evaluates the implementation's own `healthy` expression with selected dictionaries; it checks those terms but is not an independent assertion of the final exit gate. Source-presence assertions guard selected call sites but do not establish their runtime order. Negative branch coverage is sparse: no malformed/duplicate READY, ERR, DONE cardinality/numeric fields, `LP nan`, malformed SAVED/SERR, non-EIO read error, raw-write budget error, partial command write, or state after a terminal SAVE tail is exercised. These omissions do not show a source defect by themselves, but a pass cannot be represented as full protocol grammar or lifecycle fault qualification.

The compact-budget test begins with `math_gate_passed=false` and asserts it remains false after the reservation failure. This is a good guard against upgrading an existing numerical rejection. It does not exercise the dual case `math_gate_passed=true` followed by text-budget failure; source inspection shows `failure_save` copies the observed value while setting overall health/text gate false, but the fixture does not discriminate accidental future rewriting of a genuine math pass. The final-reservation fixture triggers `save()`'s pre-write reservation rejection on a 63-MiB sparse file; because it fails before creating `record.json.tmp`, it does not drive the actual post-write `final_total > limit` branch or an interruption during temp-file replacement. The external-overflow test correctly asserts the retained text may exceed the ceiling while gates remain failed; it does not prove uncontrolled helper writes are prevented.

## Concrete source edge for final QUIT

`boundary(label, allow_eof=True)` permits a no-tail boundary when `available_stdout()` returned EAGAIN, because `eof` is false and only `eof and not allow_eof` is rejected. After the QUIT loop, source calls `boundary('after-QUIT-exit', allow_eof=True)`, then unconditionally calls `protocol.finish()` and sets `protocol_boundary_gate_passed=True`. Thus, if the final boundary drained bytes and got EAGAIN rather than observing `os.read()==b''`/PTY EIO, the subsequent explicit `finish()` fabricates the framer's EOF bit. The independent child exit-code/no-signal gate remains intact, so this alone does not turn a nonzero or signalled exit into a pass, and the synchronous emitter contract reduces the practical risk. It does mean the receipt cannot use the helper's EOF flag as proof the PTY stream reached EOF. To claim clean transport EOF, require `protocol.state().eof` to have been set by `available_stdout()` before finalization, and keep normal child exit as a separate requirement. The current CPU fixture tests an observed empty read in its happy QUIT case, but never tests the controller's post-exit/EAGAIN path before the unconditional `finish()`.

A related existing failure-path caveat: the `finally` block calls `g.close()` and closes the output streams before its final save. The fixture only evaluates the health expression for a `cleanup={'forced': True}` value; it does not fake a `g.close()` exception or prove a terminal record can be written after cleanup throws. This is unchanged from v2 and is not evidence that `OwnedGdb.close()` throws on the target. Keep close exceptions / incomplete cleanup separate from a normal exit and never infer cleanup success from process exit alone.
