## Finding: safe work units exist, but this is an already-recorded unmeasured candidate

`ExpertPool::run_split_multi_native` first calls `run_phase(5, mtasks_)` for all GU rows, which returns after worker completion and parking. The caller then serially iterates `e` and `t`, quantizing one full `FF` vector per `(expert, token)` using either `act_quant_any(ff[t], FF, a2[t])` for the Q2 native kernel path or `native_quant_h(f, ff[t], hq[t])`; only after this loop does it call `run_phase(6, mtasks_)` for Down (`pool.cpp:849-880`, especially 860-870). Existing timers isolate `ms_multi_q` between the GU and Down phase timestamps (873-875).

This gives a natural task unit without changing quantization arithmetic: one complete vector of `FF` floats. Do not divide a vector at quantization-block boundaries. The matching `ff[t]` is read-only after GU has joined; a `(e,t)` task has its own `a2[t]` or `hq[t]` destination within that expert's split buffer. Keep the current GU join, publish a quantization phase, wait for every job to finish, and only then publish Down. Batching by expert does not mean the output arrays are shared across experts; the task identity must include both `e` and `t`.

Source inspection supports reentrancy as plausible but not yet proved for every dispatch: the custom Q2 activation quantizer dispatches to Q8_1 AVX-512 or AVX2 (`expert_layout.cpp:354-357`); native H quantization dispatches either to an AVX2 Q8_K routine or `ggml_get_type_traits_cpu(d_act)->from_float` (`native_expert.cpp:101-104`). `native_fmt` initializes GGML once with `std::call_once` and validates immutable trait pointers and block-aligned dimensions (`native_expert.cpp:21-26,46-82`). The GGML reference Q8_0 and Q8_1 implementations use per-call locals and write the provided destination (`ggml-quants.c:276-330`); their independent blocks do not require another vector's temporary state. The type-trait array is static and lookup returns a pointer (`ggml-cpu.c:418-420`). These facts show no obvious shared scratch in the inspected reference path, but do not establish thread-safety of every architecture-selected `from_float` implementation, dynamic initialization side effect, compiler floating-point environment, or the custom Q8_K AVX2 function. Confirm those exact selected implementations and run race/correctness checks before enabling workers.

Quantization bytes need not be assumed invariant merely because each vector runs on a separate thread. Check the selected routine's rounding semantics, dispatch ISA, MXCSR/floating-point rounding state, and any per-thread initialization. Compare all output bytes to the serial baseline for representative actual model weights and all reachable `d_act` formats. For the custom Q2 path compare complete `ActQ` bytes; for native H compare `h_bytes` per vector and subsequent CPU expert outputs. Do not claim all NativeFmt paths are covered by Q8_0/Q8_1 source examples; those GGML examples illustrate row-local state only.

## Scheduling cost and minimum experiment

The pool's `run_phase` is not a free function call: it waits for workers to be parked before publication, waits for task completion, then waits for workers to park again (`pool.cpp:691-698`). A quant phase therefore adds a full publish/claim/completion/repark cycle between the existing two phases. In the current code the workers are already parked after GU, so they can be reused without creating threads, but the added phase and `N = sum_e jobs[e].nt` job dispatch still have cost. Avoid heap allocation or one queue allocation per vector: use the existing expert/token buffers and fixed-capacity phase representation if measured useful. If `N` is smaller than the participating workers, or per-vector work is too short relative to wake/claim/barrier cost, the serial loop can win. Do not split one vector just to increase task count until data show that whole-vector parallelism lacks enough tasks.

Minimum experiment after the root's shared build/model gate permits it: first measure unchanged actual-weight `ms_multi_q`, total `N`, worker availability and whole native call wall time on the active formats/batch sizes; then compare serial against a candidate quant phase with identical input bytes and worker count. Record per-sample `ms_multi_q`, quant-phase wall time including the added phase, GU and Down times, whole call/decode latency, CPU worker useful time/idle tail, `N`, and exact byte/output parity. Include NT=1 and the observed NT=2/multi-token shapes. Treat correctness as a hard gate; adopt only if full-call/end-to-end improvement is repeatable beyond noise and the added phase overhead is recovered. Reject if `ms_multi_q` is a small fraction of wall time, tasks underfill workers, added scheduling/barrier erases the saved serial time, parity fails, or end-to-end decode does not improve. This report makes no speed estimate and does not promote the candidate to accepted.

## Prior-art and novelty check

This proposal is not new in this project. `moe-decode-cpu.txt` candidate B (lines 46-58) already describes `(expert,token)` jobs, full-vector quantization, immutable `ff`, unique `a2/hq` destinations, a barrier before Down, the `ms_multi_q` prerequisite, and parity/end-to-end rejection gates. Its status is hypothesis/unmeasured, not rejected. R11 explicitly says quantization parallelization was avoided because an earlier report already covered it; R12 likewise records it as already covered. R56's expert-local asynchronous DAG is a different design (overlap local quant with Down for another expert) and has separate reentrancy proof requirements. R75's GU/Down task counts are also distinct. R76 therefore contributes the narrower source-backed dispatch/reentrancy audit and precise added-phase cost, not a duplicate optimization proposal.

External source cross-checks (not performance evidence for Strata):

- Pinned GGML reference Q8 row quantizers are in [`ggml-quants.c` at the exact dependency commit](https://github.com/ggml-org/llama.cpp/blob/3cf03257f219afbe7334045ff7c6a06ac68c627d/ggml/src/ggml-quants.c#L276-L330). They process a complete row via caller-provided input and output; quantization block loops and temporaries are local. This supports testing a whole row as the independent unit, not claiming a speedup.
- The same pinned source has static CPU type traits and a direct lookup in [`ggml-cpu.c`](https://github.com/ggml-org/llama.cpp/blob/3cf03257f219afbe7334045ff7c6a06ac68c627d/ggml/src/ggml-cpu/ggml-cpu.c#L418-L420), and registers Q8_0/Q8_1 conversions in [`ggml.c`](https://github.com/ggml-org/llama.cpp/blob/3cf03257f219afbe7334045ff7c6a06ac68c627d/ggml/src/ggml.c#L743-L750). In GGML's CPU graph executor, operation work is divided across tasks (`ith`/`nth`) in the CPU backend rather than requiring quantizers themselves to create threads; this is a scheduler precedent, not proof that Strata's pool phase is beneficial.
- oneDNN's CPU implementation is organized into generic and architecture-specific kernels, with threading delegated to its execution infrastructure ([oneDNN CPU implementation overview](https://github.com/uxlfoundation/oneDNN/blob/main/src/cpu/README.md)). Its quantize operation explicitly leaves rounding mode implementation-defined ([oneAPI quantize specification](https://oneapi-spec.uxlfoundation.org/specifications/oneapi/v1.3-rev-1/elements/onednn/source/graph/ops/quantize)). That reinforces the requirement to compare exact bytes and selected backend behavior; it does not validate GGML's rounding or Strata's parallel execution.
- Search did not find an implementer blog with a concrete CPU activation-quantization pattern that adds evidence beyond these source examples; no blog-derived claim is used. The relevant research contribution from external implementations is the established pattern of scheduling independent rows at the operator/graph level while keeping each row kernel's arithmetic intact, which exactly motivates—but does not validate—the already-recorded experiment.

## Decision

Keep the existing serial quantization. Do not implement or accept parallelization from source inspection alone. The next discriminating evidence is measured actual-weight `ms_multi_q` and a per-format proof/test of the exact selected quantizer's thread safety and byte parity. The existing experiment candidate and rejection gates remain authoritative; this round narrows its correctness audit and accounts explicitly for the extra pool phase.
