# Installed IGC/NEO provenance and BMG GRF contract — R103

Date 2026-10-10. Read-only package/file/source-document review. No compiler, disassembler, syclbin-dump, executable, device/GPU/CPU query, build, test, profiler, Git operation or cleanup was run.

## Verdict

There is now positive evidence that BMG/Xe2 is a supported target for current IGC releases and that BMG kernels have actually been generated with 256 GRFs. This still does **not** establish the documented legal-size contract for `sycl::ext::intel::experimental::grf_size<256>` on the exact B570 + oneAPI 2026.1 runtime combination. The exact IGC loaded during the prior GPU gate also was not pinned. Keep the unsupported per-kernel property disabled; exact support remains UNKNOWN.

## What GRF evidence proves

1. Public IGC release v2.41.5 lists Battlemage as supported. The immediately relevant upstream Compute Runtime/IGC baseline (26.31.39395.13 / IGC v2.40.13) is also a BMG-capable stack; the local package bumps runtime to `.14` and co-installs IGC variants, so the precise compiler component actually selected at runtime remains unproven.
2. Intel IGC issue [#412](https://github.com/intel/intel-graphics-compiler/issues/412) records a BMG-G21 Arc Pro B60 SAGE kernel with GRF count 256 and IGC 2.28.4/2.34.4. It is direct feasibility evidence, but different hardware SKU/kernel/versions and does not establish the SYCL per-kernel property or present support contract.
3. Intel's public experimental SYCL GRF extension still specifies that supported sizes are PVC 128/256, DG2 128/256, CRI 128/256/512; BMG is omitted. It warns use on unsupported devices or an illegal size may be undefined. The local 2026.1 header defines the feature and statically admits 128/256, but carries no BMG target table. Header acceptance is not runtime legality.
4. Intel LLVM `program_manager.cpp` lowering recognizes device-image metadata `sycl-grf-size=256` and maps it to `-ze-opt-large-register-file` for non-ESIMD. That proves a generic metadata/lowering route on the inspected source branch; no package/source pin ties that branch to the exact 2026.1.1 binary, and no target-specific gate was found in the public lowering description. The runtime option's existence is not a guarantee that the target property is defined or honored.
5. Current NEO debug source exposes a broad `ForceLargeGrfCompilationMode` that appends `-cl-intel-256-GRF-per-thread`; this is process-wide OpenCL compilation control and says nothing authoritative about the per-kernel SYCL extension contract. IntelLabs examples using broad flags are practical configuration examples, not Intel API support promises.

Relevant primary links: [SYCL experimental GRF extension](https://github.com/intel/llvm/blob/sycl/sycl/doc/extensions/experimental/sycl_ext_intel_grf_size.asciidoc), [IGC v2.41.5 release](https://github.com/intel/intel-graphics-compiler/releases/tag/v2.41.5), [Compute Runtime 26.31 release](https://github.com/intel/compute-runtime/releases/tag/26.31.39395.13), [IGC BMG 256-GRF issue](https://github.com/intel/intel-graphics-compiler/issues/412), [NEO large-GRF debug option](https://github.com/intel/compute-runtime/blob/master/shared/source/debug_settings/debug_variables_base.inl), and [Intel LLVM GRF-property lowering](https://github.com/intel/llvm/blob/sycl/sycl/source/detail/program_manager/program_manager.cpp).

## Remaining UNKNOWN and disposition

No public version-matched product-helper/legal-GRF-size table for BMG was found for Compute Runtime 26.31.39395.14, nor a version-matched `grf_size<256>` guarantee for oneAPI 2026.1.1 + the actual dynamically selected IGC. We can now distinguish this from a claim that Xe2 hardware lacks 256-GRF mode: Intel's release and kernel evidence contradict that hardware-level claim. They do not override the extension's device-specific legal-value requirement. A positive resolution needs an Intel contract or source tied to the exact loaded package stack that names BMG and the per-kernel request, or equivalent Intel confirmation. Until then, no recommendation to run the undefined property. The previous v2 executable's packaged target image (R101) and its 5056 spill field are independent facts and do not change this support decision.
