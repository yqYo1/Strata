# Native ExpertPool phase-specific row-task candidate (round 75)

## Finding

A separate GU/Down task count is source-feasible and is distinct from the prior all-phases `--pool-tasks` knob and the R56 expert-local dependency-DAG idea. It is not yet supported by measurements, and should remain an opt-in calibration control only. The concrete compare is the existing automatic `GU=18, Down=18` against `GU=6, Down=18` and `GU=18, Down=6` for the recorded six-participant host pool. Use matched actual-weight harness inputs, fixed `NativeFmt`, NT vectors, dispatch environment, affinities, and cohort. These arms distinguish which phase responds to coarser claims; retain phase counters and the outer pool-call duration. Do not claim a winner from source reasoning or from a single phase subtotal.

There is no measured prior result that screens this split. R7 says phase totals alone do not diagnose barriers or critical path. R17 notes that GU and Down have different row counts and kernels and explicitly says not to force shared task boundaries; it lacked per-worker tail and NT histogram. The existing 6-task diagnostic passed its exact 32K correctness gates, but R69 explicitly classifies it as correctness-only, not a speed measurement. The task-factor CMake experiment is stale in the current tree and is not evidence for either split arm. Therefore this is a new calibration question, not a request to rerun a failed optimization or revive an already-measured speed claim.

`ExpertPool` stores one constructor `tasks_` value. `phase_tasks(rows)` returns `3 * (workers + host participant)` when zero, otherwise `min(rows, tasks_)` (`pool.cpp:719-720`). The native multi-token entry sets `mrows = nb*FF` before mode 5/GU, runs the complete phase, performs each whole expert/token FF quantization on the caller, then sets `mrows = nb*H` before mode 6/Down (`849-875`). The R71 host profile is five workers plus host work, hence six participants: default auto means 18 tasks for both phases. At H=2560 and FF=640, a single expert has 640 GU rows and 2,560 Down rows; for a batch of `nb` jobs the extents scale to `nb*640` and `nb*2560`. Requested task counts clip to the current phase's total rows.

The current CLI `--pool-tasks N` is a single `tasks_` setting, so a positive N changes both native GU and Down phases. It also feeds the other batched pool paths that use `phase_tasks`. Do not silently redefine its existing meaning.

The separate CMake cache variable `STRATA_NATIVE_POOL_TASK_FACTOR` is not a working alternative on this source. Its nonzero configure branch still searches for the old literal `mtasks_ = 3 * threads;` followed by `mrows_ = nb*FF` (`sycl/CMakeLists.txt:125-136`). The current `run_split_multi_native` instead sets `mrows_` then calls `phase_tasks(mrows_)` for GU and independently repeats that for Down. The literal is absent, so the branch's exact replacement-count guard would fail configuration. Its attempted source substitution was GU-site-only in the older source shape; it would not have supplied a Down count even if the guard matched. This is static text/source evidence, not an executed configure result.

## Arithmetic and worker ownership

Changing only the number of contiguous row tasks preserves per-row arithmetic, provided each task keeps the same production kernel calls and each output row still has one writer. The scheduler partitions `g0=floor(mrows*i/mtasks)` through `g1=floor(mrows*(i+1)/mtasks)`; the worker maps that interval to `(expert,row)` segments and calls the same row routine on each subrange (`pool.cpp:630-666`). GU dispatch remains selected by `f.gu_type` and each job's `nt`; Down dispatch remains selected by `f.d_type` and `nt` (`native_expert.cpp:125-194,196-237`). For a fixed row, the kernels retain their existing gate/up dot and SwiGLU order, FF quantizer invocation, Down dot and output store. There is no reduction across output rows. Thus a task-count change should change scheduling/partition boundaries only, not row bits. This is a source-level expectation; exact output parity must still be asserted by the harness for each split arm.

`run_phase` still waits for every worker to be parked, publishes one batch epoch and count, drains on workers plus the optional host, waits for `done == n_tasks`, then waits for every worker to re-park (`pool.cpp:691-701`; worker claims in `542-564,611-688`). Changing the count does not remove a phase boundary, alter epoch progression, or allow the caller to quantize before all GU rows complete / return before all Down rows complete. Preserve the whole-phase join between GU and the caller's existing complete-vector quantization, and the final join before the pool call returns. This is not the asynchronous per-expert DAG screened in R56; no task may consume another expert's incomplete intermediate.

The workload is not uniform in compute per row. GU work depends on `gu_type`, selected IQ/KQ/GGML path, and per-job NT; native GU's multi-token path can amortize weight decode, so row work is not simply `rows * nt` (`native_expert.cpp:125-194`). Down depends independently on `d_type`, its dispatch and NT, with IQ4NL/Q2/KQ routes differing from scalar GGML (`196-237`). Flattened task ranges can cross expert boundaries. A smaller task count reduces claim granularity and may reduce scheduling overhead, but also reduces opportunities for dynamic balancing across high/low-NT or dispatch-cost experts. Neither GU-vs-Down row ratio nor static arithmetic predicts which split wins.

## Minimal opt-in seam

For the forthcoming standalone service harness, the narrowest useful addition is an additive overload or per-call task config for `run_split_multi_native`, e.g. a `NativePhaseTasks { gu, down }` argument whose zero fields mean the existing configured/default policy. Apply the GU value only when selecting mode 5's task count and the Down value only for mode 6. Preserve the current public three-argument method and its output by delegating to the new overload with the existing `tasks_` policy for both phases. Keep `--pool-tasks` unchanged as a common value for backward compatibility; add no user-facing CLI controls until service data justifies them. Validate each explicit field against `kMaxTasks`, and continue clipping it to `mrows`.

If a production API change is premature, the harness may instead use a local-only experiment adapter/compile-time seam, but it must invoke the same production GU/Down kernels and same joins. Do not edit kernel loops, change task queue ownership, create a second pool, or use CMake text replacement. Keep phase parameters immutable for the duration of the synchronous call.

## Evidence that can reject the candidate

First collect the uninstrumented 25-round baseline on actual weights as planned. Then, only if the existing `ms_multi_gu`, `ms_multi_q`, and `ms_multi_down` component samples show a repeatable opportunity, compare the split arms against `18/18` in a separate matched calibration. These counters bound GU and Down phase wall (including `run_phase` publication, host/worker drain, completion wait and re-park); `ms_multi_q` is the unchanged caller-serial middle segment. Retain one outer call duration because phase components do not include every method boundary and their sum should not be used to manufacture a different per-expert metric. Use the same actual expert IDs, source hashes, activations/NT, job order, page-residency cohort, pool construction and CPU placement; preserve R46 cohort/holdout identity.

The candidate is falsified for a phase if changing its task count does not consistently improve that phase's component samples beyond run-to-run variation, or if coarsening one phase reduces its counter while increasing the other phase or outer call duration enough to erase any service improvement. It is also falsified if output bits or existing correctness gates differ, task clipping changes the intended arm unnoticed, any worker fails to park/drain, or the result depends on a changed NT/kernel-dispatch mix. If counters are ambiguous, a separate bounded diagnostic can record task index/range, expert intersection and NT/dispatch, per-worker useful rows and start/finish times, and last-finisher-to-phase-release tail. Keep that extra instrumentation out of the 25-round timing arm; the phase counters include synchronization, while R7/R17 show that counters alone cannot distinguish useful work from barrier/tail cost.

No single-core kernel estimate, hardware instruction interpretation, or GPU/serve latency conclusion follows from these CPU service samples. A smaller GU or Down phase subtotal alone is not a user-visible speedup. Do not implement unless the upcoming actual-weight component samples show that one of the two phases materially limits the measured pool call and a controlled split can test it.
