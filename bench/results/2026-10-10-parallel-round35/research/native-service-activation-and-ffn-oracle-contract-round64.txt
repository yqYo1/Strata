## Finding

A future no-engine CPU service executable can use deterministic finite FP32 inputs and the production activation quantizers with actual packed expert weights. This is a valid **kernel and pool service fixture**: it checks the selected production quantization, packed-row wrappers, FFN composition, output writes, and pool partitioning for the supplied shapes. It does not reproduce actual decode activations. Decode inputs depend on prior model layers, normalization, routing and residual state, so synthetic activations cannot establish their distribution, real request-level output correctness, GPU overlap, or end-to-end latency.

The production unit is `ExpertJobMulti`: one blob, `nt` distinct token activations and `nt` output pointers. The ordinary expert pool stores one `float[FF]` intermediate per token, applies SiLU to Gate then multiplies by Up, quantizes each intermediate separately, and produces one H-float output per token. For the requested formats the service cells are GU types 18/21/22/23 × Down 20/42, NT1 and NT2, with `H=2560`, `FF=640`. Confirm each pair against the selected `NativeFmt`; do not infer geometry from a type number alone.

## Exact production data path and buffers

The engine caller at `src/core/expert_source.cpp:3276–3287` quantizes each actual FP32 layer input once per token. For native IQ GU rows it writes `native_quant_act(fmt,x,d.nact_multi+t*4096)`; a native Q2 GU pack instead uses `act_quant_any` into `ActQ`. It groups repeated routes to one expert as one `ExpertJobMulti` and fills `blob`, `nt`, `act[t]`, `nact[t]`, and `out[t]` at `:3300–3345`; it then calls `run_split_multi_native` at `:3347–3351`. The requested GU types are IQ types, so the production input is each token's `nact` bytes, not `ActQ`.

`ExpertJobMulti` is declared in `include/strata/kernels/cpu/pool.hpp:55–64`. It has `const uint8_t* blob`, `int nt`, `const ActQ* act[MAXT]`, `float* out[MAXT]`, and `const void* nact[MAXT]`. `MAXT` is the fixed per-window capacity; the cell contract here uses only 1 or 2 distinct token rows. Keep the input and weight buffers alive through the synchronous call, and use distinct, non-overlapping `float[H]` output slices and `float[FF]` intermediates per token. Do not alias token outputs or reuse a scratch vector until Down has finished.

`NativeFmt` is built by `native_fmt` in `src/kernels/cpu/native_expert.cpp:46–78`: `gu_row=ggml_row_size(gu_type,H)`, `d_row=ggml_row_size(d_type,FF)`, `up_off=gu_row*FF`, `down_off=2*up_off`, and `bytes=down_off+d_row*H`; `act_bytes` and `h_bytes` come from the corresponding ggml `vec_dot_type`. The logical blob has Gate rows `[0,up_off)`, Up rows `[up_off,down_off)`, then Down rows `[down_off,bytes)`. The reader must assemble the three exact role slices as documented in R48; there is no contiguous GGUF blob to pass directly.

Activation formats and alignment:

- `native_quant_act(fmt,x,dst)` writes `fmt.act_bytes` (maximum pool slot 4096 bytes) using the GU weight type's `vec_dot_type` quantizer (`native_expert.cpp:96–99`). For IQ GU 18/21/22/23, this is the ggml CPU type-specific activation representation (normally Q8_K); the optional Q8_K AVX2 route is guarded by `q8k_avx2` and is intended to match ggml's quantizer. Allocate the 4096-byte pool slot with at least 64-byte alignment, but pass/compare only `fmt.act_bytes` meaningful bytes.
- After GU+SwiGLU, Down20 uses `native_quant_h(fmt,ff,dst)` (`pool.cpp:863–866`, implementation `native_expert.cpp:101–104`), writing `fmt.h_bytes` for the Down type's `vec_dot_type` (normally Q8_0, maximum pool slot 1024 bytes). Use a separate 1024-byte aligned slot per token; only `fmt.h_bytes` are meaningful.
- Down42 follows the production Q2 route: `act_quant_any(ff,FF,ActQ&)` creates the aligned Q8_1-style `ActQ`, not `native_quant_h`. `ActQ` contains q bytes, scales, sums, correction values and optional AVX2 bit-plane image (`include/strata/kernels/cpu/expert.hpp:64+`); construct a full independent `ActQ` per token. `act_quant_any` selects AVX-512 or AVX2 implementation from runtime CPU support (`expert_layout.cpp:354–361`).
- The production pool's `SplitBufMulti` owns `float ff[MAXT][FF]`, native `hq[MAXT][kNativeHBytes]`, and Q2 `a2[MAXT]` (`include/strata/kernels/cpu/pool.hpp:300+`). The output is written in row-major token slices of H floats. Caller-provided direct-harness buffers need equivalent alignment/size and lifetime.

`native_gu_rows` implements `ff[t][r] = silu(gate_r·a[t]) * (up_r·a[t])` and `native_down_rows` implements `out[t][r] = down_r·hq[t]` (`native_expert.hpp:56–65`). In the pool, GU is phase 5 and Down is phase 6. For the specified IQ GU types, mode 5 calls `native_gu_rows`; the Q2-GU special path does not apply. For Down20 the pool quantizes FF via `native_quant_h`, then calls `native_down_rows`; for Down42 it quantizes via `act_quant_any`, then calls `q2_rows_any` over `blob+down_off` with `nblocks=FF/64` (`pool.cpp:638–663, 863–870`). The format/type, runtime CPU features, and dispatch settings determine which underlying implementation runs; record actual selection and flags rather than forcing a faster path.

## What the deterministic activation fixture proves

Use fixed, finite, nonconstant FP32 inputs with a recorded seed and scaling, and make the NT2 vectors distinct (not duplicate copies). Feed each through the same production `native_quant_act` / `act_quant_any` functions used by the engine. For the GU and Down activation bytes, compare the entire written region against a second call to the pinned ggml CPU `from_float` implementation or the expected production quantizer route; also verify bytes beyond `fmt.act_bytes` / `fmt.h_bytes` remain canaries. For Q2, compare each `ActQ` field or its canonical serialization, including the optional bit-plane state when that runtime mode is enabled. This ensures the fixture is finite, correctly shaped, quantized by production code and NT2 does not accidentally reuse token 0's activation. It does **not** make it a sampled decode activation or validate the model's upstream FP32 values.

Pool correctness must use real selected weight bytes but can use deterministic activations. Exercise, before any timing:

1. **Buffer and write integrity.** Fill guard regions and output arrays with sentinels; require no guard changes, every expected H output element written exactly once, no untouched interior canary, no out-of-range access, finite intermediate/output values, and stable repeat results. Check `nt` is 1 or 2 and distinct input/output pointers where required.
2. **Quantizer gate.** Compare production activation quantization outputs with independently invoked pinned GGML type quantizers for the exact `NativeFmt` act types and with the expected Q2 AVX2/AVX-512 route. Do this separately for the input activation and FF intermediate. Do not benchmark conversion or use quantization bytes from a different source path.
3. **GU row gate.** Call the production GU wrapper for all FF rows and compare to an independent row oracle on those *same quantized activation bytes*. The oracle should use ggml CPU `vec_dot` for each packed Gate/Up row and the same float `silu(g)*u` composition, recording maximum absolute/relative errors and selected dispatch. Then separately compare direct-wrapper output against `ExpertPool` output for the same blob/activation bytes; identical production row functions and complete row coverage should be bitwise equal even when six tasks split rows.
4. **Intermediate gate.** Check each FF vector against the reference composition before quantizing it. Compare full quantized intermediate bytes/ActQ against the independent quantizer result. Keep GU output arrays separate for token 0 and token 1.
5. **Down row gate.** Compare all H rows from `native_down_rows` (Down20) or `q2_rows_any` (Down42) to per-row ggml `vec_dot` on the exact quantized FF inputs. Compare direct wrappers with pool output using the same dispatch; verify all H rows, canaries, finite values and NT2's two outputs independently.
6. **Full expert gate.** Compose the scalar FFN oracle from exact packed weights: per token, quantized input dot each Gate and Up row, the production `silu(g)*u` expression, the correct Down-specific FF quantizer, and each Down dot. Compare the direct full-expert result with the independently composed oracle and pool result. Preserve exact equality checks where the same implementation and same bytes should produce it; for a different accumulation or vectorization order, report numerical error against an already accepted production bound. Existing parity code uses a `1e-5` relative threshold for certain native-vs-ggml row controls, but that is not a blanket established full-FFN acceptance threshold. Do not invent or relax a tolerance to pass; if no approved end-to-end oracle threshold is pinned for this cell, record oracle comparison as characterization and require production parity before timing.

These checks are per expert and per NT cell. NT2 must use two different finite x vectors, independently quantized, and its two output vectors must each match their own reference. A check that NT2 equals NT1 is not a sufficient oracle.

## Numerical equivalence: rows, full FFN and pool splitting

A direct row oracle and production wrapper are not generally bit-equivalent merely because they consume the same packed payload. GGML CPU `vec_dot`, scalar FP32/FP64 reference reductions, AVX2/AVX-512 multi-token rows and activation quantization can round differently. The existing `native_expert_parity` helper explicitly compares native output with GGML and uses relative error `1e-5` for selected rows; its float-dequantized FP64 reference is a different, higher precision computation. That harness uses synthetic legal weights, NT=3 and also contains a GPU arm, so it is not evidence that actual-payload full FFN is bit-exact or queue-free. R61 further distinguishes its 864 synthetic wrapper cases from an ExpertPool service run.

The pool's six-task partition changes **which worker writes which row**, not the row's mathematical inputs: `pool.cpp:630–665` partitions the flattened `nb*FF` or `nb*H` row ranges and calls the same row wrapper on each subrange. For deterministic per-row wrappers, direct and pooled output should be byte-identical when they use the same activation bytes and selected dispatch; any mismatch is a correctness failure. The pool timing still includes barriers, host participation, worker wake/park and task tails, so pool phase time is not direct one-expert service time. When `tasks=6`, `phase_tasks()` selects at most six tasks, and split boundaries can divide one expert's rows across tasks; verify full coverage and no double-write. Do not compare a pool batch mean with a direct row call as though the arithmetic order or scheduling boundary were identical.

The public `ExpertPool::run_split_multi_native` path performs GU, FF quantization and Down serially by phase inside each batch (`pool.cpp:849–876`). Its `ms_multi_gu`, `ms_multi_q`, and `ms_multi_down` are separately recorded wall intervals; they include worker-phase completion, while `ms_drain` spans the complete call. Preserve those boundaries. A direct service harness should at minimum time: (a) input activation quantization separately, once per input token/layer; (b) GU wrapper for each expert; (c) FF quantization per expert/token; (d) Down wrapper per expert; and (e) full direct expert service as the sum-of-phases measured with a separate outer timer (do not construct it by summing independently sampled medians). In a separate pool arm, time full `run_split_multi_native` and retain per-phase pool values. Keep blob assembly/page preparation outside kernel timing or report it as its own boundary. Never convert bytes, route counts, or phase wall time into decode latency without an actual paired request measurement.

## Evidence limits and next gates

This source contract specifies how to prepare and validate a future actual-payload CPU fixture. It does not prove that the host-only reader link seam from R60/R61 exists or works, that the executable constructs no queue/device object at runtime, or that any selected actual payload has passed correctness. Establish the R60/R61 reader and no-device executable boundary first; bind actual blob identities/extents; pass these independent correctness gates; then apply the existing R46 cohort and repetition protocol. Synthetic finite FP32 activations remain a controlled service input. Actual decode-activation representativeness, mixed callback batches, worker-level distributions and end-to-end benefit remain separate questions.
