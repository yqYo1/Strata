## Ranked next work: service calibration before a new kernel

No additional low-risk inner-kernel algorithm is justified by counts alone. The exact packed types, current implementations, and the nearest reuse/codebook proposals are already covered by R9, R17, R21, R25, R30, R33, R45, R46 and R48. The useful update is a data-based ordering of the next service measurements and a narrower comparison of an already-present dispatch alternative.

**Priority 1: Down type 20, NT1 `ggml` versus the existing `iq4nl256` kernel.** This is the most exposed joint cell (46,254 calls and 118.4M logical output rows across one A/B pair). `native_down_dispatch` currently sends NT1 to ggml and NT2 to the AVX2 IQ4_NL multi-token kernel. The latter decodes the 4-bit values once per weight block across the NT activation rows; the current NT1 ggml path is already a format-specialized dot, not a scalar generic fallback. A bounded component experiment can compare the two *existing* implementations on the same actual IQ4_NL expert bytes and same production-quantized input, first at NT1; test NT2 as a control, where the production selection is already `iq4nl256`. This is a dispatch/service question, not a new decoder proposal or a recommendation to change the threshold. Include the exact weight load/assembly boundary, wrapper invocation, and activation preparation as separately reported costs. Before any selection change, require component output equivalence against the existing ggml result and current model correctness gates; if float order differs, do not silently call it bit-equivalent or relax the current acceptance policy.

**Priority 2: Down type 42, NT1/NT2 `q2-avx2` calibration, then stop or inspect one narrow row-pair prototype.** This contributes 10,476 NT1 and 3,032 NT2 jobs (26.8M and 7.76M logical rows) across one A/B pair. Unlike type 20, both shapes already use the same Q2 AVX2 row kernel. `row_multi<NT>` unpacks the packed two-bit weight block once and applies it across NT activations; merely “share unpack across tokens” or switching NT1 to a native path would duplicate existing work. First measure the actual Q2_0 payload on the exact NT1 and NT2 cases. Only if measured row-call data and generated code show repeated activation loads are exposed—not just L1-resident reloads—test a two-output-row microtile sharing activation vectors across two independent Q2 weight rows. Keep this as a gated prototype idea, because prior two-row IQ4_NL/component work regressed engine medians (R7), and the Q2 case has not been shown to behave differently. Reject at the first spill, arithmetic-order mismatch, no isolated repeatable service win, or no model-level benefit.

The next calibration must use actual packed payload, not the synthetic legal blocks from the prior wrapper parity fixture. R48 corrected the key loader detail: a GGUF expert is three role extents (Gate, Up, Down), not one contiguous source interval. For each selected layer/expert, the production-compatible `FileExpertSource::copy_blob` path assembles the logical blob in gate/up/down order; do not derive expert bytes as `gguf_offset + expert*blob_bytes`. Verify selected source-shard identities, role offsets/sizes, `NativeFmt`, format metadata and sampled extent hashes before timing; keep payload reads out of the timed section and retain only the small ID/extent/hash manifest. Use the r6 raw intervals only to select route-derived sample IDs if adequate independent IDs exist; A-repeat and B-repeat are not holdout cohorts. Otherwise label a deterministic metadata sample a format-kernel calibration, not route-weighted service evidence.

For each actual `(phase, type, NT)` and selected dispatch, report repeated full-expert service samples with fixed CPU/compiler/flags, affinity, worker conditions and actual `H=2560`, `FF=640` geometry. Reuse production Q8 activation quantizers, two distinct token activations at NT2, and preallocated outputs. Separate `GU`, per-expert intermediate FF quantization, and `Down`; do not multiply NT2 by two and infer twice the service. Include direct dispatch controls on identical blobs/activations, compiler-generated code and spill checks where available, untimed reference/parity checks, complete sample IDs/source provenance, and a holdout set. R46 provides the longer timing/LLC/round-bound contract; R48's split-role correction supersedes its raw-mmap pointer assumption. Only after repeatable per-cell calibration should route counts be combined with service estimates, and that combined quantity must be called an estimate, not physical decode latency.

## Already present or screened; do not reopen as novel

- **NT2 weight decode reuse is already in the code.** `iq_avx2_rows.inl::row_dot<TY,NT>` decodes each IQ block before the token loop. `q2_avx2_rows.inl::row_multi<NT>` unpacks each Q2 block before the token loop. The native NT2 selections (IQ types 18/21/22/23, IQ4_NL Down20, Q2 Down42) already take these multi-token variants. The actual traces confirm the eligible exposure but do not create a missing decode-reuse mechanism.
- **NT1 algorithm switching is not automatically a win.** GU NT1 is ggml for every observed IQ type. Existing source comments report that the native IQ multi-token path is faster at NT3 but not NT1 because both are codebook-limited; type21 has an opt-in gather-special case only for other CPU conditions, and this run reports scalar variant 0. R33 screened the NT1 ggml hot path. Do not lower all GU thresholds, force gather, or port AVX-VNNI/AVX-512 from unrelated processors based only on counts.
- **The nearest pair/reuse proposals have real falsifiers already.** R17's paired Gate/Up activation load idea is an existing hypothesis; the new exposure makes IQ2_S GU NT2 (6,432 jobs) more prevalent than IQ3_S GU NT2 (3,566) in A+B, but does not show load cost, register availability, or a speed opportunity. Any extension should wait for calibration and disassembly, not be described as a new optimization. R25's paired Q2 Gate/Up proposal applies to a different Q2 GU branch, not observed Down42; it also has an AVX2 register-pressure risk.
- **Higher-NT IQ panel GEMM does not fit.** The llama.cpp IQ panel path was designed for batch/panel size at least eight; this exact run's maximum native expert group is NT2. Repacking/model-format changes, hot-expert predecode caches, generic prefetch, historical two-row IQ4_NL, or a task scheduler change without per-worker tail evidence are outside the next kernel experiment.
- **Small codebooks and in-register tricks do not transfer as a format-preserving shortcut.** IQ4_NL/IQ4_XS already use small `pshufb` tables. Other IQ grids use larger index tables/gather or scalar decode. The ik_llama IQK approach uses small 4/8/16/32-entry mappings for its custom quant formats; it changes the encoded weight representation. The IQ2_XS implementer experiment that replaces a sign lookup with in-register bit arithmetic requires a changed sign-table ordering in the discussion's prototype. Neither is a drop-in operation for these GGUF weights without a separate decode proof and format-preservation gate.

## External source screen and limits of transfer

- AMD's [Family 19h / EPYC 7003 software optimization guide](https://docs.amd.com/v/u/en-US/56665) is the official Zen 3-family reference for instruction/cache behavior. Use it to reason about the 5600X's AVX2 implementation and verify a targeted instruction hypothesis against generated code; EPYC server measurements are not Ryzen 5600X service data. AMD's [processor developer resources](https://www.amd.com/en/developer/browse-by-product-type/processor-resources.html) list the current Ryzen performance guide and other tuning material.
- The pinned primary implementation is [ggml `quants.c` at the build's source commit](https://github.com/ggml-org/llama.cpp/blob/3cf03257f219afbe7334045ff7c6a06ac68c627d/ggml/src/ggml-cpu/arch/x86/quants.c). It is the code behind the selected ggml NT1 cells; inspect its exact quant decoder/accumulation path as a baseline rather than treating “ggml” as unoptimized fallback. The current Strata kernels are separately pinned above.
- An implementer report in [llama.cpp discussion #5152](https://github.com/ggml-org/llama.cpp/discussions/5152) describes vectorizing IQ2_XS sign reconstruction fully in AVX2 registers, while also noting the table ordering would require changing GGUF encoding. That is a useful codebook-decode design precedent and a concrete reason to keep byte-compatible codebook proofs separate from format-repacked experiments; the author used an i5-4300U, so its reported speed cannot predict Zen3.
- Another implementer write-up, [ik_llama.cpp discussion #8](https://github.com/ikawrakow/ik_llama.cpp/discussions/8), explains why small 4/8/16/32-entry codebooks fit AVX2 `pshufb` lookups and reports its own quant-format results on Ryzen 7950X and M2. That supports table-size-aware kernel design in general, but those IQK encodings and machines differ from this fixed IQ3_XXS/IQ3_S/IQ2_S/IQ4_XS/Q2_0 pack. Strata already uses a 16-entry shuffle path for its IQ4 types.
- The [llama.cpp IQ panel AVX2 commit](https://github.com/ggml-org/llama.cpp/commit/85c55223caf0a2ad0d1d88e5a73ab3fe36107867) is a second implementation precedent for grouping quantized rows/tokens, but its panel path requires a much larger batch than the observed NT≤2. It cannot be cited as a candidate for this traffic.

These sources establish design patterns and constraints only. No external result establishes a faster exact-packed Strata path, nor can processor-level microarchitecture guidance establish output equivalence or worker-pool behavior.

## Decision

Use the actual exposure to order calibration: first direct service comparison of existing Down20 NT1 ggml against existing IQ4_NL AVX2 candidate on identical payload; second measure existing Q2_0 Down42 NT1/NT2 and only then decide whether an output-row microtile has a measurable basis. Keep GU type22 NT2 as the next fallback cell if a calibrated service ranking puts it ahead; the 6,432 jobs are meaningful exposure but not measured service priority. No novel kernel should be implemented from this report. The missing evidence is actual-payload, exact-dispatch per-format/NT service on the admitted build, with bit-equivalence checks and a separately measured full decode outcome. All potential estimates must retain explicit limitations: output-row/job counts are exposure, not service time, compute cost, bytes moved, or latency benefit.
