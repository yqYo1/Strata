Current production math
For NT1, `native_gu_rows` selects the GGML trait `vec_dot`, calls it separately for each Gate and Up row, then computes `(g/(1+exp(-g)))*u` (`native_expert.cpp:167-194`). There is no generic GGML vector-SiLU call in this route; R80’s activation-path ambiguity is closed for this callsite. The default native IQ multi-token threshold is 2 (`:106-123`), so the current NT1 path is GGML on this host/build. Down20 NT1 likewise remains GGML; the existing IQ4_NL AVX2 path is selected at NT>=2 (`:196-225`).

Pinned GGML already has a substantial AVX2 IQ2_S single-row dot. For each 256-value IQ2_S block it uses sign shuffles and scalar IQ2_S grid lookups, Q8_K vector loads, `maddubs`/`madd` integer sums in two accumulators, one float FMA into the running block accumulator, then `0.125f * hsum_float_8` (`quants.c:2776-2849`). This is not an unoptimized scalar fallback. Strata’s existing AVX2 IQ2_S row code has a useful NT2 block-decoding path, but it is not a safe NT1 substitution: its generic row dot applies `Fmt32<22>::K == 0.125` before the scale product/FMA and finishes with its own horizontal sum (`iq_avx2.cpp:231-241`, `iq_avx2_rows.inl:31-57`). That differs from GGML’s placement of 0.125 after its horizontal reduction, so matching the integer dot alone does not establish bit identity. R59 also shows the active NT2 route is `iq256/scalar`; neither that dispatch nor its output qualifies an NT1 change.

For Down20, R70 already compared the existing AVX2 NT1 row with GGML: its integer dot agrees, but block FMA accumulation and final reduction order differ. R70’s narrow candidate—reproduce GGML’s exact pair-of-block accumulation/reduction while removing only the per-row indirect call—is still unmeasured and is not new here. Do not force `STRATA_IQ_MT_MIN=1` or loosen output gates.

Strongest still-unmeasured candidate: exact paired IQ2_S Gate/Up row work at NT1
The most concrete new *application* to discriminate with the first GU22/Down20 cohort is to process each IQ2_S Gate/Up row pair together while reusing the same Q8_K activation block load. Preserve independent Gate and Up integer accumulators, exact GGML decode/sign/scales, block iteration, float FMA sequence, final reduction and scalar GU finish; weights and packed layout remain untouched. If this is implemented as an interleaving of the same ordered operations for each row, it could retain GGML’s per-output result while removing a repeated activation load and two per-row indirect dot calls. It is a hypothesis only: the activation vectors are small and likely cache-resident, so the saved loads may only remove L1 traffic/uops; dual-row live state and two sets of IQ2_S grid decodes can cause register pressure or spills on AVX2. It has no measured win and no source-only exactness proof.

This mechanism is related to the already known R17 paired Gate/Up activation-reuse proposal, which targeted the Strata AVX2 multi-token row kernel for IQ3_S. Round 83 does not claim a new general algorithm. The unmeasured distinction is a single-token type-22 implementation constrained to the *GGML NT1 floating-point order*, rather than fusing the existing NT2 Strata path. R17 and R21’s high-NT/spill observations, and R59’s route priority, do not prove this NT1 candidate profitable. The GU22/Down20 experiment can first establish whether GU22 service is a material component on actual selected weights; it cannot show that activation reloads are exposed or that the paired loop helps. Only then is a small exactness/perf prototype warranted.

A less invasive exact alternative is a dedicated type-22 NT1 row wrapper that invokes the same pinned GGML dot symbol and finish for every row, avoiding repeated dynamic trait indirection if compiler output confirms one remains. The current code loads the trait function pointer once outside the row loop (`native_expert.cpp:181`) but calls it twice per row. A direct external function call still pays a call per dot and may only change branch prediction/linkage; no cost evidence says it is important. Treat this as a low-risk control for the paired-row prototype, not as a predicted win. Do not copy/modify the dot arithmetic unless the exact pinned accumulation order is retained and bitwise tested.

What prior art does and does not transfer
- Pinned GGML’s AVX2 dot is the authoritative exact baseline, not an alternative approximate kernel: [quants.c at the pinned commit](https://github.com/ggml-org/llama.cpp/blob/3cf03257f219afbe7334045ff7c6a06ac68c627d/ggml/src/ggml-cpu/arch/x86/quants.c).
- The upstream [llama.cpp IQ panel AVX2 change](https://github.com/ggml-org/llama.cpp/commit/85c55223caf0a2ad0d1d88e5a73ab3fe36107867) is built for larger token panels (at least eight); it is not applicable to this NT1 cell. It also changes panel/reduction execution and does not give an exact NT1 substitution.
- The ik_llama [IQK implementation discussion](https://github.com/ikawrakow/ik_llama.cpp/discussions/8) concerns custom IQK encodings with small lookup tables. IQ2_S has a large indexed grid; a format repack or altered codebook ordering is outside the unchanged-weight/exact-math constraint. R30/R45 already screened these codebook/table ideas and the external CPU/GPU examples.
- Generic prefetch and forced gather are already screened (R17/R30/R45/R59); the current NT1 route is GGML, not the Strata IQ256 decoder where those controls apply. No new prefetch layout is evidenced here.

The closest cross-engine pattern for paired projection reuse is the S-MoE [Metal kernel documentation](https://docs.s-moe.com/v1/internals/metal-kernels.html), which describes sharing input/scale work for two row dots. That is a GPU implementation with different layout and math, so it establishes a design pattern, not exact compatibility or CPU benefit. R17/R21 already document the same concept and the AVX2 register-pressure risk; this report narrows it to type-22 NT1 with an explicit GGML-order constraint.

Use of first calibration and remaining gate
R79 shows the selected exact 22/20/NT1 cell has routed IDs across 15 layers and enough for disjoint 192+192, but root intentionally froze its cohort as equal-layer format-kernel characterization rather than frequency-weighted workload holdout. Keep that sample interpretation. The current calibration supplies actual selected weights but formula-generated input vectors, and its correctness gates do not establish live activation distributions or whole-model behavior (R80). Its per-round phase service measurements can rank GU and Down components on this exact cell, but cannot prove a kernel candidate or speedup.

If a prototype is later authorized, first compare per-row Gate and Up floats bitwise against the pinned GGML path over the admitted actual weights and independent finite controls, including final GU and Down outputs. Inspect Zen3 AVX2 code for spills. Then compare the unchanged GGML path and paired exact-order path on the same 192+192 cohort, separate direct component and production-pool timings, and retain every sample. Reject if any bit differs, if the pair loop spills, or if the holdout service difference is not repeatable. A model-level 32K+ output/state comparison remains necessary before a serving claim. No implementation, tolerance, default, or ISA override change is proposed here.
