## Outcome

V3 materially closes the two earlier source gaps: it checks already queued and partial stdout tails at each inter-command boundary, and it reserves aggregate bytes for every controller-owned text write including simultaneous old/new JSON serialization, then checks the post-final-save total. The source fixture now has discriminating cases for these behaviors, but remains unexecuted. The remaining concrete protocol-evidence gap is that PTY `EIO` is collapsed into the helper's generic EOF bit: the record stores EOF state and inferior exit status separately, so this cannot alone convert a nonzero/signal exit to success, but it does not preserve whether transport EOF was an `EIO` or a zero-byte read nor when it occurred relative to inferior exit. There is also a narrow failure-receipt reserve check that measures a compact JSON payload before adding its final fields; under a near-1-MiB metadata case, the resulting receipt can exceed the declared reserve.

## Stream ownership and process result

The single `BoundedProtocolLines` instance is kept for the complete PTY stream. Every successful read is written to `protocol.stdout.raw` before framing; CR is rejected, LF is the only delimiter removed, and the line/payload bounds are explicit (`bounded_engine_protocol_v1.py:34-131`; controller `:462-465,520-528,636-648`). Complete rows and partial suffixes survive in the bounded queue/pending buffer. `boundary()` drains currently readable bytes, records framer counters, and fails if either queue or pending suffix is nonempty (`:531-558`). It is called after each DONE, before the next GEN, immediately before every command write, before/after SAVE, before QUIT, during QUIT drain and after process exit (`:654,790,806,841-848,856-868`). This is a concrete correction to R43's old buffered-tail gap: a burst `DONE…\nT 999\n` or partial `DONE…\nT ` cannot be silently reassigned to the next command. The one immediate pre-write boundary is repeated inside `send`; bytes arriving after that nonblocking observation remain a transport race, but the frozen emitter is synchronous, flushes DONE, and emits no legal post-DONE stdout in this no-batch configuration (R44); any bytes available at subsequent GEN/SAVE/QUIT boundaries fail closed.

The actual exit status is not inferred from PTY EOF. V3 requires `g.exit_code == 0` and no signal at `:870`, and the final `healthy` predicate again requires exit code zero/no signal, successful completion, all gates, no error, no faults, and no forced cleanup (`:977-990`). The pinned `OwnedGdb.poll` maps GDB/MI inferior `exited-normally` to 0, a nonzero `exited` reason to its decoded exit code, and `exited-signalled` to `exit_signal` (`owned_gdb.py:105-113`). Thus the good-path/cleanup fixture at controller test `:105-118` correctly distinguishes process success from cleanup and signal failure; normal GDB/debugger termination is not substituted for an inferior result.

Transport evidence is less precise. `available_stdout()` catches PTY `EIO`, turns it into `data=b''`, and calls `protocol.finish()` exactly as for a zero-byte read (`:531-542`). `boundary()` records only `eof=true`, and does not record an EOF source or whether the inferior was already known exited at that instant (`:545-558)). In the final QUIT window, EOF is allowed before `g.exit_code` is asserted (`:860-870)). No false-success case was found for an ordinary nonzero exit or signal, because the independent exit gate rejects it. But a distinguishing case is missing: a fake PTY returns `OSError(EIO)` during QUIT while the inferior is still running, then GDB reports normal exit shortly after; v3's final status can pass, and the receipt cannot show that EIO preceded process exit. The fixture's EIO test only combines EIO with an unterminated suffix, which correctly raises framing error; its normal-EOF case uses `b''` (`test_cache_route_pairs_protocol_integration_v3.py:54-68`). Add source/ordering evidence for `pty_eio` separately from zero-read EOF and test EIO-with-empty-tail while exit is still unknown. Keep the process exit gate independent; the present code already does that.

## Message grammar against the frozen emitter

The admission pin requires the exact helper hash before importing the framer (`:147-157`). Startup admits only `READY <digits> stop` or `ERR`; GEN admits the frozen `RESUME`, `REUSED`, `T`, `PP`, `LP`, 16-field `DONE`, or `ERR`; SAVE has separate `SESSION`, `SWAIT`, `SAVED`, `SERR`, or `ERR` classification (`:503-517`). These shapes agree with the frozen `generate.cpp`: READY at 8457; PP at 7637/9950/10003; RESUME and REUSED at 9820/10369; T and LP at 11000/11248-11261; 16-field default DONE at 11527; SAVE's SESSION/SWAIT/SERR/SAVED at 9136-9252. The selected argv excludes `--batch`, so the emitter's optional BADM is absent. YIELDED belongs to BYIELD cooperative prompt preemption; this controller sends GEN/SAVE/QUIT only and runs no concurrent batch client, so allowing it is not needed here. Error-classified SERR/ERR never set a success result: SAVE exits on `error` then retains the failed numerical result and records the preservation attempt (`:838-853`).

The GEN grammar deliberately admits only numeric finite-decimal LP rows; the emitter can print `LP nan` for invalid logits, which is rejected as unexpected rather than accepted as a numerical result. DONE token-count/finish/timing/logprob/MTP checks remain in `validate_fresh` and later output/state/reference comparisons (`:31-53,808-837`); the grammar's 16-field check is not treated as sufficient numerical validation. This preserves original C/D rejection: the controller pins C's failed math/full-lifecycle receipt and the failed D receipt without promoting either (`:342-348,363-375`); failure compaction retains C/D flags and math gate state (`:565-568`).

## Artifact accounting and failure evidence

Controller-owned writes are pre-reserved against the 64-MiB aggregate with a 1-MiB reserve. `text_bytes` counts every regular non-`.bin` artifact, including `record.json.tmp`; `reserve_write` checks actual current file sizes plus proposed bytes (`:470-482`). Raw stdout and JSONL events reserve before append (`:497-528`). JSON serialization reserves the full newly encoded payload while the old record and temp coexist (`:485-495`); because the temporary has no `.bin` suffix it is counted. Polling checks the current aggregate at 63 MiB, and finalization rescans after the final JSON replacement (`:622-634,993-1001`). The v3 fixture exercises final-record reservation failure and external-helper overshoot separately, requiring compact failure state and refusing to relabel over-limit output as success (`test_cache_route_pairs_protocol_integration_v3.py:86-104`). These tests are source-only and unexecuted here.

External helpers still write their own `debugger/*` and inferior stderr files without synchronous controller reservations. The script cannot prevent a burst of external writes from crossing the cap; it detects such growth on polling/final rescan, marks `text_budget_gate_passed=false`, and records `external_or_prior_text_overflow` in the compact failure receipt (`:629-630,575-582,996-1001`). That is an acceptance gate with failure evidence, not a hard filesystem quota. The normal controller-owned writes reserve the failure region; they do not erase raw or source logs to recover the budget. V3 therefore implements the missing final JSON/aggregate accounting guard that R43 had identified; its behavior still awaits root's serial fixture/preflight, and external overshoot remains possible by design.

One bounded-reserve edge remains in `failure_save`: it serializes `compact` and checks `len(payload) <= FAILURE_RESERVE` at `:572-573`, then adds `external_or_prior_text_overflow` and `final_text_bytes_observed_before_field` and writes a second, larger JSON serialization at `:575-582` without rechecking its length. A compact record just under 1 MiB before those fields can cross the declared reserve after them. Its component fields include external fault messages and retained protocol tails, whose lengths are not constrained by `FAILURE_RESERVE` itself. The final payload remains text-budget-failed and overall unhealthy, so this is not a success-gate weakening; it is a failure-receipt size guarantee gap. A discriminating fixture can choose a bounded large `new_fault_messages` value so the first compact JSON is within (for example) 32 bytes of the reserve, then verify the *final* serialized record stays within 1 MiB. Better check/reserve the final serialization after all fields are added, or add those fields before the existing size check.
