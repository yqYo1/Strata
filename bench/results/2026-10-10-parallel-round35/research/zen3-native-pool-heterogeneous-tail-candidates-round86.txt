Round 86: Zen 3 native pool task granularity and heterogeneous tails

Question
Does the current Zen 3 native expert pool expose a source-bound, non-overlapping task-granularity or tail-balancing candidate for GU/Down phases with mixed NT and formats? What do six versus eighteen jobs imply statically?

Scope and evidence
This is a read-only source and prior-report review. No source was edited; no build, import, test, runtime, model, GPU, profiler, Git, or cleanup operation was performed. Static inspection used the native role-plan worktree `/home/yayoi/ghq/github.com/yqYo1/Strata/.worktree/diag-sycl-native-role-plan-v0141-20261010`. Its source hashes were: `pool.cpp` `5ef33f7d2020a17ecc36ad15796c6f021b4b5963998aa964dccedbe733637368`; `pool.hpp` `5c200f068a27d43414cbca2159459944a2541476d0d99cf55f8b962b4b62299b`; `generate.cpp` `f495e69556fb096c8d051d490a92bebb040c624c519ed2d920a6d35f76f4e502`; and `expert_source.cpp` `5cc617c9887e80175f5325957b02cd034ac1f7ce7a5fb310cda5492e1e25d5f1`. These are source identities, not a claim that the source was built or executed in this investigation.

The old tasks=0/6 r1/r2 microbench placement put all workers on CPU 0 because it pinned the parent before pool creation; those timing values cannot support a speed comparison. Production creates the pool before host pinning, and no equivalent placement fault was established there. Corrected r3/r4 microbench runs ended normally with six distinct physical CPUs. They remain microbenchmarks and do not establish engine speed or a preferred task count.

Current source contract
`phase_tasks` in `pool.cpp` selects `3 * (workers + host)` when the configured task count is zero, and otherwise caps the configured count at the number of rows (pool.cpp around lines 719–720). `run_phase` distributes tasks using atomic claim/done state and joins at the phase boundary. It does not make a new worker pool per job.

`run_split_multi_native` invokes a phase for one native format at a time; its batch is bounded by `kMaxSplitMulti`. In mode 5, GU presents `nb * 640` rows; in mode 6, Down presents `nb * 2560` rows. Each phase independently chooses task count and divides the flattened row interval into equal-width contiguous ranges using integer endpoints `floor(mrows*i/mtasks)`. The ranges can cross expert boundaries and map to the per-expert native NT routine. NT is heterogeneous within a call; the weight format is fixed for a given `NativeFmt` call, while different formats may occur in sequential calls/layers. Caller-side quantization between GU and Down and the phase joins are separate boundaries; changing job count does not remove them.

Static six versus eighteen comparison
For six participants, the default formula gives eighteen tasks; explicit six gives six, assuming enough rows. At `nb=1`, GU’s 640 rows become widths 35/36 under 18 tasks versus 106/107 under 6. Down’s 2560 rows become widths 142/143 versus 426/427. At larger `nb`, mean spans scale to approximately `35.6*nb` versus `106.7*nb` GU rows and `142.2*nb` versus `426.7*nb` Down rows. These widths describe the scheduler’s row ranges, not equal execution time: native row cost varies by NT and format, including the distinct NT1 GGML and NT>=2 native-format routes.

Eighteen jobs provide about three claims per participant on average, which leaves more opportunities to pick up work after a long range but requires more claim/done operations. Six jobs provide one range per participant when all are available, reducing scheduling operations but exposing a slower range as a tail. Neither count changes the number of GU/Down phases, the phase join, NT-specific arithmetic, or serialized inter-phase work. The code alone does not establish which side wins on Zen 3, how much heterogeneity is present in representative batches, or whether a tail is material.

Candidate conclusion
No additional source-grounded candidate was identified that is both distinct from the prior proposals and justified by this pool contract. “Use smaller/equal tiles”, dispatch-weighted tiles, per-NT chunking, and changing phase job count are already covered by the task-shaping/NT and phase-count investigations. A guided or stolen-range subdivision scheme would be a generic variant of those same grain-size ideas; the cited systems do not provide a Zen 3/native-NT rule that would make it a distinct recommendation. In particular, subdividing only a stolen long interval would add coordination and needs measured evidence of a persistent tail before it is a credible candidate.

This conclusion does not establish that the current default is optimal. A falsifiable follow-up, if pursued, should use the corrected six-CPU placement and the production call path, compare a small predeclared task-count set under identical batch, format, NT, affinity and warm-up conditions, retain per-sample phase times and correctness/fault status, and keep microbench results labeled separately from engine inference. Instrumented ranges should report the actual NT/format mix and per-task completion times so a tail can be distinguished from phase overhead. No values from the old r1/r2 placement should be rehabilitated.

Prior work and external references

This confirms a familiar dynamic-claim pattern, not a new Strata-specific policy: https://github.com/ggml-org/llama.cpp/blob/3cf03257f219afbe7334045ff7c6a06ac68c627d/ggml/src/ggml-cpu/ggml-cpu.c

vLLM v0.20.1 expert parallel deployment describes expert placement/load balancing across EP ranks, which operates at a different level from these local CPU row jobs: https://docs.vllm.ai/en/v0.20.1/serving/expert_parallel_deployment/ . SGLang’s expert-parallel documentation likewise discusses expert placement/replication and grouped GPUs, not native CPU phase row granularity: https://github.com/sgl-project/sglang/blob/main/docs/docs/advanced_features/expert_parallelism.mdx .

oneTBB’s `auto_partitioner` subdivides ranges in the context of task stealing; this is a general-purpose scheduling mechanism and offers no specific NT/format service-cost contract for this pool: https://oneapi-spec.uxlfoundation.org/specifications/oneapi/v1.3-rev-1/elements/onetbb/source/algorithms/partitioners/auto_partitioner . OpenMP guided scheduling is another generic decreasing-chunk policy, not a demonstrated fix for the source’s per-row cost variation: https://www.openmp.org/spec-html/5.1/openmpsu48.html . The personal OpenMP loop-scheduling benchmark used dual Xeon Broadwell and generic loops, so it is not transferable evidence for this Zen 3 engine path: https://markxio.github.io/blog/benchmarking-loop-scheduling-algorithms-in-openmp/ .

Unmeasured limits
No representative per-format/per-NT service-time distribution, task completion timeline, production batch distribution, or controlled six-versus-eighteen engine comparison was collected here. External scheduling references demonstrate available patterns, not performance in this pool. The analysis therefore supports a “no distinct candidate established” decision, not a performance ranking.
