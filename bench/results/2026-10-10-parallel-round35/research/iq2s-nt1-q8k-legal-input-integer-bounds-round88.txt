Round 88: Q8_K input contract and IQ2_S AVX2 integer bounds

Question
What input domain does the production Q8_K quantizer establish for the pinned IQ2_S NT1 dot, and what bounds then make the AVX2 signed-byte conversion, `vpmaddubsw`-style saturating pair multiply-add, and int32 accumulators safe? Which exceptional values are outside that proof?

Scope
Read-only source review of the current native expert path and pinned GGML commit `3cf03257f219afbe7334045ff7c6a06ac68c627d`, plus the R85 exact-order prototype contract and existing quantizer parity source. No execution, import, preprocessing, disassembly, build, test, profiling, device/runtime/model, Git, or cleanup action was performed. Existing parity-source comments are treated as descriptions of its fixture design, not as results from this investigation or as a production-input distribution.

Production quantizer path
For an IQ2_S native GU format, `native_quant_act` chooses Q8_K for its activation type. It calls Strata's `q8k_quant_avx2` when runtime AVX2 is available and `STRATA_NO_Q8K_AVX2` is unset; otherwise it calls the GGML type trait's `from_float`. The source comments identify the GGML x86 Q8_K quantizer as the scalar `quantize_row_q8_K_ref`; the x86 `quantize_row_q8_K` wrapper calls that reference. The Strata AVX2 copy states it preserves the reference arithmetic/bytes, but a comment or a parity harness is not evidence that every exceptional FP input is a supported production input.

For one 256-element block, the reference finds the first element whose absolute value strictly exceeds the running `amax`, retaining that element's signed value as `max`. NaNs do not win the comparison. If `amax` is zero (including an all-zero block, or all NaNs), it sets `d=0` and zeroes `qs`; it does not write the `bsums` array in that early branch. Otherwise it computes `iscale = -127.f / max`, quantizes `nearest_int(iscale*x[j])`, clamps only the upper side with `MIN(127,v)`, stores to signed int8, computes sixteen-element `bsums`, and sets `d=1/iscale`.

The source-supported normal finite domain for a simple range proof is: each block contains finite inputs; its selected `max` is finite and nonzero; `iscale` remains finite; and every scaled value is within `nearest_int`'s asserted range. In exact arithmetic, `|iscale*x[j]| <= 127`; normal float rounding stays far inside `nearest_int`'s `4,194,303` bound. The intended byte range is then `[-127,127]`, and the explicit upper clamp enforces 127. This is the condition under which the source scaling argument excludes `-128`; it is not a blanket guarantee for all possible float bit patterns passed to the API.

The implementation has no input validation that rejects NaN, infinity, or tiny values causing `iscale` to overflow. NaNs are skipped while selecting `amax`, but a NaN in the quantization pass reaches the magic-add/bit-extraction `nearest_int` code; infinities can produce `0*Inf`/NaN after `iscale` becomes signed zero; an all-subnormal tiny block can make `-127/max` overflow to infinity, and zero entries then form `0*Inf`. The source comment in the AVX2 copy explicitly mentions scale overflow in a degenerate block, but does not promise a mathematical Q8 value range for such inputs. The parity helper has stress cases for denormals, NaNs, infinities, and large finite values; those are useful implementation-parity robustness fixtures, not proof that such inputs are in the ordinary activation contract or evidence about their frequency. Zero elements in an otherwise finite, nondegenerate block are straightforward; an all-zero block has the special early path. Subnormal elements in a block whose scale remains finite need separate FP-environment care for bytewise parity; no FTZ/DAZ contract was established here.

Therefore the exact paired-kernel control should define its admitted domain by going through the production quantizer on finite, nondegenerate float input blocks with finite scale and bounded scaled values, then consume those resulting `block_q8_K` bytes in both reference and candidate. Do not call hand-written Q8 byte arrays or the quantizer stress-only NaN/Inf/denormal cases “legal production inputs” without a separately specified contract. To exercise signed endpoints, supply finite float source patterns that produce both `-127` and `+127` through the quantizer and record resulting Q8 bytes/hash. If raw `-128` is separately injected, label it an out-of-domain robustness test; it is representable in the struct but is not produced by the finite-scale range proof.

All-zero `bsums` detail: the dot reads `d` and `qs`, not `bsums`, so the unwritten `bsums` bytes do not affect IQ2_S results. A full-struct byte comparison of a zero block must prefill both destinations identically or compare only fields the quantizer defines; otherwise uninitialized/prefill differences are not a quantizer mismatch.

IQ2_S grid and scale bounds
The pinned `iq2s_grid` is a 1024-entry table of eight packed bytes per entry. Its byte alphabet is `0x08`, `0x19`, and `0x2b` (unsigned magnitudes 8, 25, and 43); therefore each first operand byte presented to `_mm256_maddubs_epi16` is in `[8,43]`. The IQ2_S packed scale nibbles are expanded as `2*nibble+1`, hence the signed 16-bit scale values lie in `[1,31]`. The sign stream is separate from grid magnitudes.

The AVX2 sign expansion builds an all-zero or all-one byte mask and computes `(q8 XOR mask) - mask`. For Q8_K values in `[-127,127]`, that operation exactly preserves or negates the signed byte, producing `[-127,127]`. For `q8=-128` with a negative sign, two's-complement byte arithmetic wraps back to `-128`, rather than yielding the unrepresentable `+128`; that breaks the intended mathematical sign transfer and can disagree with the generic scalar expression. This is a further reason not to admit raw `-128` into the paired bitwise contract.

For every adjacent pair entering `_mm256_maddubs_epi16`, the absolute product sum is at most `2 * 43 * 127 = 10,922`, below both signed int16 limits. Thus the instruction's signed-int16 saturation cannot activate on the finite-scale Q8_K domain. (Even the out-of-domain byte value -128 would give the crude bound 11,008, also below int16 saturation, but sign negation would still be wrong.)

Each `_mm256_madd_epi16` lane sums two int16 products with positive scales no larger than 31, so its absolute bound is `2 * 10,922 * 31 = 677,164`. In a 256-element block, each of `sumi1` and `sumi2` receives four such updates (`ib32 = 0,2,4,6`), giving at most `2,708,656` per accumulator lane; their final sum is at most `5,417,312`. These are conservative independent maxima and remain far below signed int32 max `2,147,483,647`, so the `add_epi32` accumulations do not wrap for admitted input bytes and valid IQ2_S grid/scale fields. These bounds justify the integer stages only; they do not alter R85's required exact float FMA, horizontal reduction, or final scale order.

The IQ2_S source's actual AVX2 sequence is: sign-adjust Q8 bytes; `_mm256_maddubs_epi16` with grid magnitudes; `_mm256_madd_epi16` with unpacked scales; add into two int32 vectors; sum those vectors, convert to float, and apply one block FMA. The separate `quants.c` generic path multiplies each signed Q8 by grid values and sign in scalar promoted-int arithmetic. The AVX2 bound establishes no saturation/wrap for valid inputs, but it does not prove float output bit identity or any new paired-row schedule; those remain R85's exact-order controls.

Required prototype-control correction
R85 already requires deterministic legal controls, per-row Gate/Up/dot/output comparisons, and the exact GGML operation schedule. R88 tightens the word “legal”: store the source float control recipe and hash; quantize via `native_quant_act` (and, for the fallback branch comparison, the pinned GGML quantizer) under the recorded FP environment; verify the resulting Q8_K block bytes are equal before dot comparison; restrict the primary bitwise set to finite, nondegenerate blocks for which the scale and rounded products satisfy the quantizer's ordinary range assumptions. Include production-quantized zero, both signs/endpoints, mixed signs, and multiple finite block scales only when those conditions hold. Keep the exceptional parity cases in a distinct robustness bucket, not in the claimed production-input domain. Do not hand-fabricate Q8 arrays to stand in for production quantizer outputs.

No claim is made here that captured engine activations satisfy the finite/nondegenerate assumptions or that NaN/Inf/subnormal inputs occur in actual serving. Establishing that would require a separately authorized aggregate input-domain observation. The quantizer's source contract alone does not supply that distribution.
