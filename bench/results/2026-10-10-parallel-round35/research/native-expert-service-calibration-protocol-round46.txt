## Minimal extension to the wrapper harness

The existing wrapper harness is the right kernel boundary, but its current input source and output are wrong for timing: synthetic `fill_blob` weights, a single deterministic activation fixture, one call per tuple, no timed output. Extend that harness in an opt-in service mode; keep its correctness mode and binary schema/gates unchanged. This needs a read-only selected-expert loader over the production metadata/shard layout and phase timing output. Prefer an existing exported pack-reader/source API if one exposes checked extents. If none exists for this standalone linked target, report that as the precise missing API and add a small bounded read-only adapter in the harness only after the root authorizes implementation; do not duplicate engine dispatch predicates or alter the model pack.

For each selected layer/format pair, keep `NativeFmt` from the resolved production library. Reuse `native_quant_act` / `native_quant_h` (or the existing `Acts` constructors that invoke them) with fixed documented seeds and legal finite input. Use two distinct inputs for NT2; for every sampled expert the same per-token activation vector(s) represents the shared layer activations across experts. Preallocate outputs/intermediates, write each result to its own output slice, and checksum/validate outputs after the timed interval so compiler elimination is impossible without adding checksum work to the measured phase. Keep the GGML/reference, finite, sentinel and partition checks from the existing harness as a separate untimed gate. Record dispatch selection for every (phase,type,NT), including whether NT1 takes ggml or native AVX2; do not force a different dispatch profile and then call it production.

Calibrate these components separately, on the same exact bytes and fixed inputs:

1. GU wrapper: one `native_gu_rows(f, blob, nact, nt, ...)` over all FF rows. This includes both Gate and Up and the existing SwiGLU operation.
2. Down-input quantization: one production `native_quant_h` or Q2 `act_quant_any` per token from that expert's measured GU output. Preserve it as a separate component; this is per CPU expert and therefore belongs in a CPU-hit service total.
3. Down wrapper: `native_down_rows` or `q2_rows_any` over all H rows using those exact quantized intermediate activations.
4. The input activation quantization before a native layer is a per-layer/token preparation operation, not a per-expert row-dot cost. Record it separately if useful; do not multiply it by callback_pairs when scoring a candidate set.

Only combine the first three as a direct compute-demand estimate for a format pair: `C_direct(GUtype,Downtype,NT)=GU+intermediate-quant+Down`. Preserve component timings; calibration does not predict critical-path latency. Both the paired IQ3_S and Q2_0 model pack variants must be reported separately where their actual format pair differs.

## Cache-state sample and bounds

Do not time one expert in a tight loop. That would leave a small weight blob and codebook repeatedly resident in the Ryzen L3 and answer a warm-cache question. AMD lists the Ryzen 5 5600X with 32 MB L3 ([AMD product specification](https://www.amd.com/en/products/processors/desktops/ryzen/5000-series/amd-ryzen-5-5600x.html)). Use a file-backed cohort of distinct expert IDs and randomize order once per timed pass. The pass's *relevant phase bytes* must exceed twice that L3 size, computed from the actual selected row extents, not estimated from nominal bpw. Set each disjoint cohort size as `N=max(192,ceil((2*32 MiB)/phase_bytes_per_expert)+1)` distinct experts. Require `N*phase_bytes_per_expert >64 MiB` for each phase/cell; if a phase cannot meet this with the selected routed IDs, mark it LLC-sensitive/underpowered and do not use it to weight route counts. N=192 per cohort should clear the 64 MiB threshold even for a roughly 0.4 MiB Q2_0 Down region, but always verify with metadata-derived byte extents. The train and holdout cohorts together therefore contain at least 384 disjoint expert IDs; if a format pool has too few IDs, report the cell as infeasible instead of reducing either cohort.

Use N distinct train IDs and N disjoint holdout IDs per format cohort where the route set permits (at least 384 unique IDs total at the 192-per-cohort floor); if the calculated minimum N is greater, increase both cohorts together and record the resulting extent bytes. Include the exact sample IDs, layer format strata, selection seed and inclusion rule. Stratify across available layers and routed-frequency bands; don't select only hottest experts. For type 23 (one GU layer in IQ3_S pack), sample distinct expert IDs within that layer. For Down 42, state which pack and layers supplied the blobs. The holdout cohort must independently clear the same >64 MiB phase-byte bound.

Map/process one format cohort at a time. Maximum full-blob virtual cohort is `N * max(blob_bytes)`; cap the live mapped/referenced cohort at 1 GiB, never copy it into a second buffer, and stream a single expert into a small scratch buffer only if the production reader cannot pass a mapped extent directly. This keeps RAM bounded and avoids crowding the model's roughly 48 GiB native arena. Pre-touch/map pages before timing to remove first-use file faults; page-cache residency is expected, but the distinct working set remains larger than L3. Do not use explicit cache flushes. Report the sample as “resident in host RAM, streaming beyond L3,” not as cold disk I/O. If the required corpus exceeds the 1 GiB cap, shorten neither the corpus nor the statistical condition; stop and state that this calibration is not feasible under this bound.

Use 25 full-corpus rounds for each (phase,type,NT) training cell and 25 on its disjoint holdout cohort. Each round visits every unique expert once, in a seeded shuffled order; collect one outer monotonic-clock duration for the whole round and divide by the cohort size N (the number of distinct calls in that round). This avoids per-call timer overhead and avoids treating the N experts in one round as N independent repetitions. Randomize/rotate the order of (type,NT,phase) cells in blocks to avoid confounding format with boost/thermal drift. Record every round. Report median per-call service and a 95% bootstrap interval over rounds, with the train/holdout gap and coefficient of variation. Require the holdout interval to overlap the training interval and relative 95% interval width ≤5%; otherwise add rounds up to 50 and label unresolved if still wide. Retain all individual round values, IDs, extents and correctness/fault outcomes in the compact receipt. Keep CPU frequency/power/thermal conditions observational: record CPU brand/flags, effective affinity, governors and system load; don't change system policy inside this read-only calibration proposal.

For Zen 3 diagnosis, a separate counter pass may use Linux `perf stat` over the bounded calibration process for `cycles:u,instructions:u` and only AMD events whose Family 19h mapping and availability have been verified. Record event encodings, enabled/running percentages, CPU affinity and multiplexing; reject/qualify counters if multiplexed or unavailable. Generic `cache-misses` is not a substitute for a documented LLC event. The [perf-stat manual](https://man7.org/linux/man-pages/man1/perf-stat.1.html) explains per-program statistics; AMD's [Family 19h Software Optimization Guide](https://docs.amd.com/v/u/en-US/56665) is the architecture reference. Timing remains primary; do not use PMU sampling as a proxy for per-job milliseconds.

## Keep pool scheduling and overlap separate

The wrapper harness directly measures a single-expert service call. It excludes ExpertPool task publication, six-task partitioning, five worker wake/park behavior, mixed-expert tails, and overlap with GPU work. Add a second, separately labeled production-pool arm using the existing public `ExpertPool::run_split_multi_native` interface, not a replacement scheduler. Source at `src/kernels/cpu/pool.cpp:439-467,691-701,719-721,849-879` shows that `ExpertPool(5, true, true, PoolAffinity::All, 6)` uses five pinned worker threads plus host participation; `tasks=6` yields six row tasks per phase when row count permits. The callback's `ms_multi_gu`, `ms_multi_q`, and `ms_multi_down` record wall duration of the GU phase, intermediate quantization and Down phase. At `pool.cpp:630-664`, each task can span expert row ranges; parallel reduction makes one phase time a batch completion time, not a sum of independent expert costs.

For pool arm, build homogeneous batches per measured format/NT cell of N routed experts at a bounded set of n values (1, 6, the median routed n and the observed upper quartile/max callback count). Feed exact blobs and legal activations; run all nt=1 jobs or all nt=2 jobs only as isolated diagnostic batches. If callback-level receipts later become available, add a separate exact mixed callback replay and bind its job IDs/NT mix. The current R42 request-aggregate trace cannot reconstruct a real mixed callback batch. Record `n_jobs`, task count, per-phase pool ms, `phase_ms(wait_park,drain,repark)`, outputs, and worker affinity. Never divide whole-batch time by n and call it C; never subtract scheduler/phase counters from direct service times to manufacture per-job costs.

Current timing telemetry lives in these existing cumulative fields, but there is no service-timed, actual-weight API in the wrapper harness. The pool arm gives scheduler+parallel kernel completion by phase; R7 establishes that these host callback phase durations can be hidden by GPU work. They cannot be added to request wall time or described as GPU-unhidden latency. A final paired end-to-end request remains the only evidence for inference latency after a measured CPU kernel win and unchanged output/state/MTP gates; it is deliberately outside this calibration and the new pair GPU trace remains unexecuted.

## Decision use

Use direct `C_direct(GUtype,Downtype,NT)` only as an offline CPU service-demand weight in a fixed-set replay, with each pair's derived NT1/NT2 job counts from R42 and exact layer metadata. Keep pool batch samples as a separate scheduler diagnostic. Neither is a latency forecast, cache-adoption criterion, or change to residency policy. Report no candidate if the direct service differences are below measurement uncertainty or if holdout does not replicate. Preserve source/build, environment, per-round samples, sample provenance, correctness and fault results at the next work boundary; retain no raw activation/model captures once hashes and compact samples are recorded.
