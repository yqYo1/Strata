## Candidate: chunk-major residual residency

A distinct candidate is to process one 8,192-token chunk through layers 0→47 while keeping that chunk's existing FP32 residual workspace resident on the GPU, then advance to the next chunk. This changes only traversal order and residual location: preserve the 10,240-float FP32 row, the existing `run_impl` kernel path and chunk extent, and each layer's token order. The current source takes the opposite order: `run_layer_major()` loops over layers, calls `run_impl()` on all prompt chunks for that layer, and its `on_chunk` callback writes each layer output to the full host `rows` plane (`prefill.cpp:2679,2724-2786`). The next layer re-uploads each chunk. Current D receipt uses `gpu_tokens=0` and `inplace=false`, so the plane is `262,139 × 10,240 × 4 = 10,737,213,440` bytes (9.99981 GiB). Across 47 layer boundaries, it implies 47 full-plane D2H writes plus 47 full-plane H2D reads, or 1,009,298,063,360 bytes of residual handoff per request, before accounting for input embedding or other traffic. That is a source-derived byte count, not a timing or bottleneck claim.

With chunk-major traversal, one current chunk is `8,192 × 10,240 × 4 = 335,544,320` bytes (320 MiB); the final 8,187-row tail is 335,339,520 bytes. `run_impl` already has a per-chunk `m.R` workspace and its host handoff path copies data into that workspace (`:3034-3065`). A chunk-major design could carry `m.R` directly from one layer call to the next, avoiding the full-context host plane and its repeated PCIe transfers. The fixed 320-MiB figure describes the current chunk workspace, not necessarily added VRAM; real feasibility must include the temporary expert cache, model workspace, KV staging, and current free-VRAM headroom.

The concrete cost is repeated expert-layer staging. Current source constructs all expert jobs for one layer and loads that layer once before running its full sequence of chunks (`:2729-2747`). A chunk-major loop would visit 32 chunks and stage each layer for each chunk unless more expert layers fit and are retained in VRAM. That makes the current one-pass layer weight staging pattern repeat up to 32 times. Exact bytes depend on model `blob_bytes(layer)`, source type and cache behavior; no transfer-size or performance prediction is made. This trade is credible only if measured residual-link pressure justifies repeated weight reads and available host/VRAM budgets support the chosen plan.

## External precedent and limits of analogy

The ZeRO-Inference implementer description says it streams model weights layer by layer to GPU and retains each layer's output on GPU as the next layer's input; it explicitly motivates using the freed GPU space for long sequences or larger batches. This is the closest precedent for keeping the live activation on device while weights are streamed ([DeepSpeed ZeRO-Inference design](https://www.deepspeed.ai/2022/09/09/zero-inference.html), especially its layerwise weight-offload discussion). It does not demonstrate the proposed multi-chunk traversal for this recurrent/MoE model, and their GPU budget and workload differ.

FlexGen's authors model offload placement and execution schedule together. Their paper contrasts schedules that reuse weights with schedules that must store activations/KV in CPU or disk, then implements a block schedule that balances data movement and compute ([FlexGen paper, ICML/PMLR](https://proceedings.mlr.press/v202/sheng23a/sheng23a.pdf); [official FlexGen repository](https://github.com/FMInference/FlexGen)). This supports treating residual residency and expert/weight reloads as one joint schedule decision. FlexGen's block schedule operates over generation batches and cache/activation storage and is not direct evidence that a chunk-major Qwen prefill will preserve this implementation's results or improve its end-to-end time.

The vLLM/DeepSpeed literature reviewed here primarily covers KV-cache offload, layer-weight offload, and activation checkpointing, not a drop-in way to reduce this engine's FP32 residual handoff. HybridServe's activation cache stores intermediate activations to recompute KV entries and reports reduced KV storage/traffic; it does not remove the need for adjacent layers' residual inputs in this path ([HybridServe paper](https://arxiv.org/abs/2501.01792)). vLLM's long-context chunked prefill focuses on memory pressure and scheduling around concurrent requests, not elimination of per-layer residual traffic ([vLLM Llama 3.1 support blog](https://vllm-project.github.io/2024/07/23/llama31.html)). These are useful context but are excluded as direct candidates. No quantization, approximate activation cache, zero-copy USM/import, or generic double-buffering proposal is made.

## Required source changes and semantic hazards

This is a schedule rewrite, not a safe one-line option. The current `hand_in_` contract represents a full-context base pointer and `run_impl` adds `(c0 - gpu_tokens) * D` to select each chunk (`:3057-3061`). Passing `m.R` as a chunk-local pointer without changing that contract would produce an invalid offset. A future design needs an explicit chunk-local input view/argument for the next layer, or an equivalent bounded owner that identifies its token base without forming an out-of-object pointer. The layer cache cannot be overwritten while previous compute is still reading its expert slots: `m.copy` is a separate queue, so retain a successful compute fence before reusing that same layer-cache allocation for the next layer. Keep the stager stopped/joined and transfer completions established before its host source buffers or expert cache are recycled, following the separate R42/R44 failure-drain ownership constraints.

All mutable sequence state must follow per-layer token chronology. Each QSA layer's KV state and each GDN layer's recurrent/conv state must see chunks in increasing `p0` order, with exactly one append/update per token. PLE adds a concrete shared-state wrinkle: `run_layer_major()` saves the original `ss.ple_prev` and restores it before each layer (`:2452,:2762`), while each `run_impl` advances that pair through its chunk tokens and writes it back (`:2929,:3206,:5340-5341`). In a chunk-major traversal, each layer processing the same chunk needs the same history from before that chunk; later layers must not inherit the already-advanced pair from the earlier layer. Snapshot the pre-chunk PLE history, restore it for each layer's call, then commit the post-chunk history once for the next chunk. This requirement is source-derived and needs a focused CPU schedule oracle before any device comparison.

A minimal CPU discriminator should fake `layer_compute(layer, p0, T, input, state)` and the expert/stager owner. Assert order `(chunk, layer)`, monotonically increasing token positions independently per layer, exact full/tail `T`, one residual buffer reused with no full-context host allocation, one weight-cache reuse only after compute fence, and the PLE history rule above. Assert QSA/GDN state handles are per-layer and advanced once per chunk, not copied/reset. This proves schedule/ownership bookkeeping only; it cannot prove actual FP32 kernel identity or state equality.

If a later GPU experiment becomes eligible after the existing candidate failures are resolved, compare the same prompt/environment/executable against a passing reference. Preserve exact IDs, logprobs, all-head output, all 66 serialized state parts, MTP counts against the observed baseline, and normal lifecycle/physical-boundary gates. Additionally capture per-layer/per-chunk input/output identity at a bounded selection around the first differing state, and count actual weight bytes/reloads and residual bytes on the links. A source-level or CPU schedule pass is not a correctness or performance result. Keep the present C/D numerical failures unchanged.

## Decision

The chunk-major resident window is a genuinely different, source-applicable way to remove the current full-context residual spill/reload bytes without reducing FP32 precision. Its hard trade is repeated layer-weight streaming, plus nontrivial state-ordering and per-chunk input-ownership changes. It is a candidate only under measured link/VRAM/RAM conditions; external systems establish the scheduling trade, not that it wins here. Do not run it, forecast speed, or adopt it while the frozen full-context math failures remain unresolved.
