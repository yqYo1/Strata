## Changed guards and preserved result gates

The diff makes three focused changes: it caps each protocol line at 65,536 bytes including newline and rejects an unterminated pending line once its length reaches 65,536 (`:529-555`); it reads and records the target's resolved `/proc/<pid>/cwd` and asserts it equals the frozen worktree root (`:668-682`); and it skips making a second `project-messages.txt` copy of the inferior stderr, recording `project_messages_duplicate_skipped` instead (`:772-776`). The supplied v2 digest matches the requested identity.

For protocol bursts, `line()` searches for a newline before checking the pending-buffer limit, partitions and returns one line, and retains the tail for the next call. Thus multiple complete short lines already present in one 64-KiB `read()` are consumed one at a time without losing bytes. A complete line with 65,535 content bytes plus LF is accepted; 65,536 content bytes plus LF is rejected. A no-LF buffer of 65,536 bytes is rejected, correctly preventing a future line from exceeding 65,536 bytes including LF. Each `os.read` is capped at 65,536 bytes; raw stdout and per-read events are recorded. The bound is per logical line, not a cap on all bytes received or the aggregate pending buffer when it contains complete lines.

One trailing-data gap remains: after `DONE`, bytes after that line can remain in `pending`. The final `QUIT` drain reads directly from the PTY and never checks or drains that already-buffered tail (`:755-772`). Nor does the controller require `pending` to be empty before sending the next `GEN`. Normal engine output appears to work with the existing protocol, and the current success gates still require four valid `DONE` records, output/logprob counts, fresh resume/reuse markers, prefill progress, numerical comparisons, normal QUIT and clean exit (`:31-53,:688-752,:755-772`). But irrelevant or trailing protocol text is not rejected as a global framing violation; recognized markers in a tail might be attributed to a later request. A CPU fake-engine fixture should exercise multiple lines in one write, exact maximum accepted/rejected boundaries, a split newline across writes, and trailing complete/unterminated bytes after DONE and before the next GEN/QUIT. If strict message ownership is required, assert the buffer state is empty at those boundaries or explicitly consume and validate the tail. No such fixture was run here.

The CWD addition materially closes the prior source-inferred gap: the script `chdir`s to the candidate root before creating `OwnedGdb`, and the helper inherits it, but v1 did not observe the inferior's actual working directory. V2 checks the live inferior's `/proc` cwd after matching its process identity, executable hash, argv, and environment; a mismatch fails before requests. This binds relative paths at runtime more directly. It still relies on the process identity remaining stable across the separate `/proc` reads; the source does not recheck start ticks immediately after reading cwd, though the target is under the active debugger and this is a narrow race rather than a gate omission.

The removed derivative is not a needed input to the controller's later checks: v2 parses `debugger/inferior.stderr` directly for phase/histogram lines and request-scoped cache-route frames (`:778-846`), retains its offsets and final size/hash, and the full stderr remains in the diagnostic output. `project-messages.txt` was a duplicate filtered view, not a source for validation, admission, or comparison in this controller. Skipping it removes the exact post-copy aggregate-budget overrun flagged in round 41 without weakening a success condition.

## Remaining aggregate text-budget limitation

The original 64-MiB setting is still a polling guard, not a hard write-time or final-total cap. `poll()` sums non-`.bin`/non-`.tmp` files below the output directory and raises when the sum is already at least the limit (`:515-526`). It runs before reads/writes and periodically saves, so bytes added after one poll can overshoot before the next. More importantly, the `.tmp` record is excluded during serialization; `save()` then atomically replaces `record.json` (`:463-471`). After QUIT, the source parses the complete engine log and stores all parsed route-pair objects into the record (`:778-849`), hashes outputs, then final `save()` occurs in `finally` (`:874-891`); no final aggregate rescan enforces the total including the enlarged `record.json`. The separate stderr size assertion at `:772-774` only limits that one file. Therefore v2 removes the known duplicate expansion, but cannot claim the complete final text artifact set is guaranteed below 64 MiB. The pair parser bounds raw route-frame bytes at 4 MiB per request and 16 MiB total (`cache_route_pairs_parser_v1.py:10-11,81-90`), but parsed JSON object representation and existing logs/record/events also consume text budget.

A minimal CPU-only boundary test can populate synthetic output files to just below 64 MiB, make a `save()` whose final JSON grows the aggregate above it, and verify the post-run admission rejects that total; a separate synthetic PTY burst can demonstrate the bounded overshoot between `poll()` calls. A robust adjustment would reserve a documented serialization margin or perform a final total-size check after final `save()` and mark the receipt unhealthy if it exceeds the cap. Do not delete raw output or relax per-request/parser/math gates to fit the budget.
