## Source findings

The helper is a raw byte LF framer and does not parse engine grammar. `feed()` validates type, per-read chunk size, aggregate *payload* budget, CR policy, and every complete/pending line length before appending any part of a candidate chunk. On a framing rejection it latches an error and leaves all prior admitted queue/pending bytes inspectable and consumable. `pop_line()` returns only complete raw lines including LF. `finish()` is explicit EOF: it retains completed queued lines, and raises while retaining any unterminated final tail. Empty feed is not EOF. On a healthy EOF with complete lines queued, `eof=true` and `has_unconsumed=true` until the caller consumes them. This correctly distinguishes incomplete EOF from clean EOF plus unconsumed complete output, provided the caller checks both fields.

The default CR policy preserves bytes exactly; CR counts against the line cap, and CRLF is returned unchanged. The explicit `reject` mode rejects any chunk containing CR atomically. No decode, newline conversion, trim, or content classification happens. An engine caller must select and document the policy; if it preserves CR, parser code should remove only the known LF delimiter and must not silently strip arbitrary whitespace/CR.

For defaults, each accepted read is at most 65,536 bytes, each raw LF-terminated line at most 65,536 bytes including LF, and queued-plus-partial payload at most 131,072 bytes. Since every complete line contains at least one LF, the queue can still hold as many as 131,072 one-byte line objects. Thus the limit is a rigorous payload-byte cap, not a 128-KiB Python RSS cap: bytes-object headers, deque blocks/references, a temporary line copy, the caller's input chunk, `pending_tail()` copies, and `queued_tail()` tuple references add bounded per-call overhead. Repeatedly retaining tail snapshots in the caller can accumulate additional memory. The implementation report discloses object overhead, but an integration must not label `buffer_limit` as a total-memory cap. If a strict RSS ceiling is required, add an explicit line-count/object-overhead budget rather than relying on payload bytes alone.

One small hardening point before treating constructor limits as a security boundary: `line_limit`, `chunk_limit`, `buffer_limit`, and `cr_policy` are public writable attributes after validation. A caller can change them midstream, e.g. raise `buffer_limit` beyond 131,072 or `line_limit` beyond the canonical bound, bypassing constructor policy. No current fixture mutates configuration. Keep the instance private and immutable by contract in integration, or make settings read-only / revalidate them on use before relying on the constructor as an enforced bound.

Preserve the original process/read error separately; call `finish()` only when the transport reports actual EOF. An `OSError`, timeout, child signal/exit, or PTY `EIO` must not be rewritten as a clean EOF. Record process exit status independently. At EOF, require no unterminated tail, consume/classify all queued lines, and reject unexpected post-protocol output.
- The helper has no discard/reset or request-attribution API, intentionally. After a `DONE`, inspect all already-buffered complete and partial tails before sending another `GEN`, `SAVE`, or `QUIT`. Do not instantiate a fresh framer per request, drop pending bytes, or attribute a prior request's buffered suffix to a new request. A complete expected row can be assigned only by controller grammar; unexpected complete rows are errors. An unfinished suffix at DONE is ambiguous: retain it and continue the same byte-stream ownership or fail the protocol; do not send a new command and let later bytes complete it under another request. At QUIT, inspect both already-buffered tails and fresh reads through actual process EOF; clean completion requires expected empty stdout tail, no partial, and normal child exit.
