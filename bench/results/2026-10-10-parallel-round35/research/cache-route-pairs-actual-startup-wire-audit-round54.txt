## Complete normal stdout grammar for this argv

This is the command-surface inventory relevant to the pinned one-process `--serve`, no-batch controller; other interactive commands are not issued.

- **Startup:** `INFO <fixed-format status>`, then `READY 262144 stop`, once each and in that order. Startup error/exception remains a failure; it must not be converted into readiness.
- **Each GEN:** request is `GEN 64 ckpt=1 logprobs=5 <32768 token IDs>`. For a fresh prompt, source emits `RESUME 0` before prompt work, bounded `PP <done> <total> <ms> <tok/s>` progress while reading, then `REUSED 0` before decode. For this 8192 prefill chunk the controller later requires progress endpoints `[8192,16384,24576,32767]`. Decode emits `T <token-id>` rows and, for requested logprobs, `LP <logprob> <id>:<logprob>...` rows; non-finite `LP nan` is intentionally rejected by the exact grammar. The normal terminal is the 16-field `DONE` line. GEN errors use `ERR ...` and do not pass a request. The controller separately checks token/logprob cardinalities and values, finish reason, timings, MTP and reference/state gates.
- **Unavailable with selected argv:** `BADM`/batch rows require `--batch`; `YIELDED` is for cooperative batch preemption. This controller has no batch client or batch option. Lookup-chain adds optional DONE suffix fields, but INFO reports `lookup=0`, so the selected run expects the 16-field DONE shape. There is no legal stdout response after DONE in this no-batch path; boundary checks reject queued or pending extra bytes rather than assigning them to a later request.
- **SAVE:** only the deliberate numerical-failure preservation path issues SAVE. It may emit zero or more `SESSION <done> <total>` and `SWAIT <phase> <seconds>` progress lines, then `SAVED <tokens> <bytes> <ms>` on success; refusal emits `SERR <kind> <published> <reason>`; verifier/commit failure can emit `ERR ...`. These belong to the SAVE grammar, not GEN. SAVE does not upgrade the failed mathematical request.
- **QUIT:** no stdout acknowledgment is defined. The collector requires an empty post-command stdout tail, observed transport EOF, and separately observed GDB/MI normal exit code 0 with no signal. EOF or READY alone is not process success.

These are response shapes/order conditions for the pinned command flow. Runtime status numbers such as current VRAM free are diagnostics; the saved INFO row is valuable evidence of actual configuration readback, but it is not proof of request math, successful completion, or normal process exit.

## Why R44 and R49 missed INFO

R44's scope reviewed request boundaries and enumerated startup as the READY handshake, GEN responses, SAVE and QUIT. It cited the READY emitter at line 8457 and the v1 collector loop, but did not inventory all stdout writes before READY. The v1 loop accepted and retained arbitrary startup lines until READY, so the omission did not fail that controller. The missing source scope was the pre-READY startup transcript, specifically the Monitor-tab `printf` at lines 8394–8411.

R49 then described startup grammar as READY/ERR while relying on the R44 emitter/message list. Its source-to-protocol review enumerated RESUME/PP/REUSED/T/LP/DONE and SAVE rows, but again did not scan and classify the normal INFO stdout emitted before READY. In v3-v5, the newly strict `protocol_line_kind` turned that inherited inventory gap into a hard admission failure. The root cause is not an unexpected engine line: both reviews treated diagnostic status as outside the protocol because they reviewed command responses/readiness individually instead of every stdout frame on the same PTY stream and its actual emission order.

## Required future startup-mock wire

The v5 fixture extracts pure helpers and never executes the startup loop; it contains no INFO or READY startup test. A source-only mock should model the full boundary, not only call the classifier on individual known responses:

1. Feed canonical INFO then `READY 262144 stop\n` in one read burst, including the exact pinned field order and no batch suffix. Require both rows consumed in order and assert the validated fixed settings are recorded while math/completion remain false.
2. Feed INFO and READY in separate chunks, including a partial INFO/READY tail, to ensure stream framing—not read chunk boundaries—defines rows.
3. Reject each required startup distinction: missing INFO, duplicate INFO, INFO after READY, READY before INFO, wrong context/readiness mode, wrong fixed field such as expert slots/KV/spec, malformed/missing/extra/reordered INFO field, and the batch-only suffix. Keep dynamic values type-checked and retained without comparing them to hard-coded sample readings.
4. Feed a startup ERR or EOF before READY and require failure with preserved raw evidence. Do not treat INFO as an error or a success terminal.
5. Continue a valid wire into the pinned four GEN rows, an isolated SAVE branch for its progress/terminal and refusal/error forms, then QUIT with no stdout tail and a separate normal process exit. Preserve request math gates and process status as independent results.

A realistic fixture must exercise the stateful startup-to-command transition or a small extracted startup-state function. Testing only that `protocol_line_kind('INFO ...','startup')` returns a classification would not prove INFO is consumed exactly once, READY is still pending/consumed next, or READY's context is checked.

## Conclusion

The actual run failed before any GEN because v5 omitted a normal, argv-compatible INFO status frame from its strict startup grammar. The following READY frame was already buffered but not consumed. The frozen source requires INFO then READY; future admission should parse that exact status format and verify its fixed launch values, while keeping status, numerical gates and process exit separate. R44/R49 missed the row because they scoped startup as only the READY handshake and did not enumerate stdout emitted before READY.
