# Round 53: external small-NT MoE phase-scheduling screen

Retrieved 2026-10-10. Read-only external/source review; no tests, build, model, CPU/GPU query, profile, service, benchmark, Git mutation, or implementation change was performed. Target under review: Ryzen 5 5600X AVX2, five CPU workers and six tasks, native GU H=2560/FF=640 with NT1/2, then per-token FF quantization, then Down; expert formats GU IQ3_XXS/IQ3_S/IQ2_S/IQ4_XS and Down IQ4_NL/Q2_0. Reported nested GPU-concurrent intervals are roughly GU 120 ms and Down 44 ms. They are not additive end-to-end times and do not themselves show a queue or barrier bottleneck.

## Local baseline and duplicate boundary

The relevant source baseline already has a persistent `ExpertPool`, shared atomic task claiming, a host participant when configured, and six explicit phase tasks in this run. At frozen T commit `7d0105f2a942ac72ca20fef69d4c2e7960653de3`, `ExpertPool::run_split_multi_native` runs the GU row tasks, quantizes each expert's FF vectors on the caller, then runs Down row tasks (`src/kernels/cpu/pool.cpp:759-785`). Each `run_phase` waits for workers to be parked, publishes one phase epoch, drains work, waits for all tasks, then waits for workers to park again (`:688-698`). Each worker remains alive and takes tasks from the shared claim counter; it spins briefly and then parks on a condition variable when idle (`:476-527,608-685`). This is already a persistent queue, not per-expert thread creation.

Past work is deliberately excluded: R17 already screened NT-aware task cost/tile shaping and phase/worker-tail telemetry; the pool-tasks implementation already introduced the fixed `--pool-tasks` control; R45/R30 already cover AVX2 row/panel kernels and reject the NT8 IQ panel for NT1/2; affinity/worker allocation and source path are separately audited. This screen does not propose another task-count sweep, core pinning change, weighted-tile policy, or row kernel.

## External technique with a distinct scheduling boundary

The closest scheduling precedent is an individual implementer's [llama.cpp tile-level task-DAG experiment](https://github.com/ggml-org/llama.cpp/discussions/27331), with source pinned to [`head-with-nothing/llama.cpp` commit `1e3aa0d41b3369e7198131458f9ab40ed3ee77a4](https://github.com/head-with-nothing/llama.cpp/commit/1e3aa0d41b3369e7198131458f9ab40ed3ee77a4). The experimental [`src/llama-taskgraph.cpp`](https://github.com/head-with-nothing/llama.cpp/blob/1e3aa0d41b3369e7198131458f9ab40ed3ee77a4/src/llama-taskgraph.cpp#L1-L4) describes a persistent pthread pool executing a static whole-model DAG without per-node barriers. It uses per-task dependency counters and worker-local deques with stealing (source lines 126–170, 760–880), rather than releasing the whole pool at every operation boundary. Its FFN graph encodes Gate/Up, activation, Down, and reduction dependencies explicitly (lines 1278–1310). This is a plausible *scheduling pattern* for a cross-stage pipeline: start an expert's quantization only after all its GU rows finish, and its Down tiles only after that expert's quantized FF vector is ready, while other experts still run GU.

The cited POC is not a CPU MoE GU/quant/Down result. It bypasses the ordinary graph for single-token Qwen3.5 dense models, is POSIX-only, and its author reports M2 batch-1 results (+13.7% for Qwen3.5-2B Q4_K_M, other model results in the discussion). The same author says the largest single gain was removal of scheduler `usleep` backoff oversleep, and that larger batches fall back to stock. Strata already has a spin-before-condition-variable worker park, a shared task counter, and phase timing; therefore the sleep-backoff fix is not a new candidate here. The DAG approach would also introduce many more dependency updates and queue operations than six current tasks. Its benefit must be established on the actual pool rather than inferred from the M2 timings.

A second external system, KTransformers, uses CPU/GPU overlap and deferred experts. Its SOSP'25 paper describes scheduling some routed-expert outputs one layer later to overlap CPU execution with subsequent attention; it reports throughput gains but also small behavior changes rather than exact output equivalence ([paper, §§4.2 and 6.3](https://madsys.cs.tsinghua.edu.cn/publication/ktransformers-unleashing-the-full-potential-of-cpu/gpu-hybrid-inference-for-moe-models/SOSP25-chen.pdf)). Its current [`experts_base.py`, pinned at `kvcache-ai/ktransformers` commit `2ac8cf9c88fa7d6de106bcc3ab3ef7645e7476a0`](https://github.com/kvcache-ai/ktransformers/blob/2ac8cf9c88fa7d6de106bcc3ab3ef7645e7476a0/kt-kernel/python/experts_base.py#L3063-L3151), submits immediate and deferred tasks to a WorkerPool and uses a separate stream/callback path. This solves a heterogeneous overlap problem; it does not remove Strata's within-pool phase barriers and cannot be transplanted into the exact-output path because delaying routed outputs changes layer dependencies/model results. The paper's Xeon/AMX/AVX-512 and CUDA environment does not match Zen3 AVX2 plus Arc.

No Intel-specific primary source found in this screen supplied a small-NT AVX2 MoE phase scheduler that removes these GU/quant/Down boundaries while preserving the current packed weights and exact outputs. oneDNN/Intel LLM work is centered on different quantized formats, ISA paths, or CPU/GPU backend integration, already screened as kernel/path mismatches in R45. The separate `ncnn-MoE-Runtime` cross-request batch scheduler is a serving/microbatching design and would add queueing latency/session semantics; it is not a direct single-request phase-pool optimization.

## Candidate boundary and independent discriminator

There is one distinct conditional source candidate: a small, fixed-task-count dependency DAG *within each existing routed batch*, pipelining expert-local `GU rows → FF quant → Down rows` when data dependencies permit. Preserve each expert's existing row kernel, packed role extents, NT, quantizer output, per-row accumulation order, output buffers, and final router-weight/reduction order. Do not defer work across transformer layers or alter routing. This would remove a whole-phase rendezvous only if worker-tail evidence shows GU and Down batches have substantial early-finisher idle time; otherwise it adds scheduler overhead with no work saved.

The independent discriminator should first separate active compute from dispatch/wait before implementing the DAG. In a matched root-owned run, capture per phase: task publish time; each worker's wake, first claim, last completion, and re-park; host claim/work interval; completion wait; serial quant interval; queue claim count; and exact task/job/NT/type. Add a bounded no-op/replay control with the same six tasks and publication/wait sequence to estimate scheduler/park cost independently of the row kernels. Keep per-format/NT service timing separate, and align worker intervals to distinguish a long single-worker tail from balanced compute or wake/park latency. Compare these against whole CPU-pool and physical decode measurements; phase counters overlap GPU work and must not be summed. Only if the measured barrier/tail share is material should a fixed-task DAG prototype be considered, with exact reference heads, all live-state parts, logprobs and MTP gates. If worker active time dominates and tails are short, stop without changing scheduling.

This adds a cross-stage dependency-DAG lead beyond R17's within-phase cost-weighted partition, not an inference that synchronization caused the current 120/44 ms intervals. No external schedule has measured this 5600X workload, these GGUF formats, or this five-worker/six-task setup. There is no validated speed prediction.
