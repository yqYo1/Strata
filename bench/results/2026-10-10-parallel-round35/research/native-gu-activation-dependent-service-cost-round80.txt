The existing `native_gu_dispatch` uses a default `mt_min=2`: NT1 goes through the GGML row-dot route; for supported IQ formats, NT2 uses the IQ AVX2 route. The source documents that grouping multiple tokens can round expert rows differently. The IQ implementation accumulates integer dot chunks, converts each chunk to float with an FMA, horizontally reduces, then applies `g/(1+exp(-g))*u`. The scalar GU finish is in `native_expert.cpp`; the IQ path has the same mathematical expression in `iq_avx2_rows.inl`. The NT2 route’s token grouping and dot reduction are not evidence that NT1 can be changed while retaining GGML’s exact output.

The harness host computes synthetic activation values as `(((i*37+layer*11+expert*3+token*101)%509)-254)/257.0f`, a bounded interval near [-0.988, 0.988]. This is deterministic fixture data, not captured model activation. The independent harness reference performs its own GGML row dot and then uses the same `std::exp` expression for SiLU. Root-reported CPU smoke says NT1 GU and Down20 were exact PASS; NT2 Q2 is characterization with numerical deltas, not exact equivalence. Hot traced samples are not representative timing weights. These results establish the stated fixtures and tested paths only; they do not quantify the frequency or cost of SiLU behavior on live gate outputs.

Pinned GGML source distinction
In the pinned source, scalar `ggml_silu_f32` is `x/(1.0f + expf(-x))` (`ggml/src/ggml-cpu/vec.h:1046-1048`). The vector `ggml_vec_silu_f32` uses AVX2/FMA `ggml_v_silu` for complete 8-float groups and falls back to scalar for a remainder (`ggml/src/ggml-cpu/vec.cpp:380-414`). Its AVX2 exponential is a polynomial/range-reduction implementation whose source comment gives maximum error “1.45358 plus 0.5 ulps”, with overflow/underflow handling around the stated exponent limits (`vec.h:1211-1261`). Therefore “GGML reference” does not by itself prove the activation used one scalar libm call per element: the concrete row-dot/vector dispatch and compiler/CPU path matter. The harness’s call site is scalar C++ and is a separate expression, not a proof of bitwise identity with every GGML vector path.

The precise optimization conclusion
Do not recommend approximate SiLU, fast-math, or a substitute vector exponential as an NT1 optimization on this evidence. Those can change values and the NT1 contract is to preserve GGML output. The existing smoke confirms exact output for the tested fixtures but says nothing about activation-specific service time. For an exact NT1 candidate, compare only transformations that preserve each GGML row-dot result and activation result bitwise under the pinned compiler, FP environment, and dispatch. Any batching/reordering across experts or rows must preserve the same reduction and operation order; otherwise it becomes a new numerical mode, not an exact optimization.

The bounded fixture also cannot characterize which inputs reach any library or vector range path. Actual `g` is a weight-dependent dot product, not the activation fixture’s raw input interval. A timing argument that invokes exp range, subnormal, or branch costs needs the actual gate-output distribution and the actual compiled instruction/library path. The Intel oneAPI `-fp-model=precise` documentation says precise mode avoids value-changing FP optimizations and assumes the default FP environment; it does not claim input-distribution-independent latency or exact cross-implementation equivalence: https://www.intel.com/content/www/us/en/docs/dpcpp-cpp-compiler/developer-guide-reference/2024-0/fp-model-fp.html. The source setting is not proof of the generated code for a specific host TU.
