## What runs on every positive-T candidate chunk today

In `gdn_recurrence_quad_variant` (`kernels.dp.cpp` around 2664–2720), each positive-T call performs these candidate admission steps afresh before submission:

1. `q_of(stream)`, in-order queue property check, and `q.get_device()`.
2. Device queries for subgroup sizes, max workgroup size and max work-item dimensions; reject unless dimensions cover the existing RG/CB geometry, SG32 is present, and device limit is at least 128.
3. `get_kernel_id<GdnRecQuadPipelineSG32>()`, then `get_kernel_bundle<executable>(q.get_context(), {device}, {id})`.
4. `bundle.has_kernel(id, device)`, `bundle.get_kernel(id)`, and mandatory kernel-device queries for compiled subgroup size and kernel workgroup size; reject unless 32 and >=128 respectively.
5. Optional `private_mem_size` and Intel `spill_memory_size` queries. Each is wrapped in its own `catch (std::exception)` and records `known=false` if unavailable; neither value controls admission.
6. Submit the recurrence with `handler.use_kernel_bundle(*executable)`; then submit output normalization.

The recorded quiet case used 2048-token chunks over 32768 tokens, so the exact admission above is performed 16 times per candidate arm/prefix. It is absent on the legacy arm. The per-call optional private/spill queries also repeat 16 times. These are exact source call counts, not evidence that each query recompiles, reloads, or is costly. DPC++ has an internal per-context program/kernel cache, and the source itself obtains an executable bundle by ID for each chunk; host-side query overhead remains unmeasured.

`T==0` returns before queue lookup or cache access. Negative T, padded-row validation, and the diagnostic denial seam remain before admission. Queue in-order property is a queue property; check it on each actual queue call even if device admission is reused.

## Portability and object-lifetime contract

SYCL 2020 defines a kernel bundle as a set of device images associated with one context and a set of devices. The executable state is invocable. The overload used here explicitly requests an executable bundle filtered to the candidate kernel ID and a single device. `handler::use_kernel_bundle` requires the submission handler’s context to match the bundle context; the compatible device image must contain the kernel. Khronos describes `kernel_bundle` and `kernel` as common-reference runtime classes: copying them retains the same underlying SYCL object semantics. Thus an application-owned copy can be retained and reused; the API does not require the bundle to be reacquired for every submission. This is a legal reuse opportunity, not proof of a runtime-cost reduction.

For this exact candidate, the conservative entry key/ownership contract is:

- Candidate kernel identity is the compile-time `GdnRecQuadPipelineSG32` kernel ID and the current binary/image/build configuration. Do not key by the implementation-defined kernel name string; SYCL does not guarantee that name is unique or stable across runs.
- Use the exact `sycl::context` returned by the owning queue and the exact `sycl::device` returned by that queue. The executable bundle is created with `{that device}` and the one candidate kernel ID. Do not share a cache entry across a newly-created context merely because it selects the same physical GPU or reports the same name/driver.
- The simplest safe home is an immutable cache entry owned by the Strata queue/device/context owner, or by an explicit owner object that controls those same objects. Store SYCL values (`context`, `device`, `kernel_bundle<executable>`, and optionally `kernel`) rather than raw Level Zero handles. The SYCL reference semantics keep the underlying objects alive while SYCL copies remain. Do not make a process-global map keyed only by GPU index/name/native pointer.
- If an owner intentionally shares an entry among multiple queues, every consuming queue must use the same context and the exact supported device represented in the bundle; an equality check on SYCL context/device values is a possible guard. The context may have other devices, but that does not make a bundle for device A automatically valid for device B. Keep the per-queue `in_order` gate separate. The lowest-risk first version is one cache per exact queue owner, avoiding global identity and invalidation logic.
- Publish a cache entry only after all mandatory current checks succeed. Hold the bundle and, if useful, the kernel descriptor in the entry. The current submit still uses `handler.use_kernel_bundle(*bundle)` and its named lambda, so retaining the bundle is sufficient for exact-image dispatch. If a future path launches a `sycl::kernel` object directly, its argument-binding requirements and launch semantics need a separate review; reuse does not imply arbitrary kernel objects can be substituted without changing code.
- Serialize first construction/publication (e.g. a mutex or once-state scoped to that owner); expose the completed entry as immutable to concurrent readers. Do not hold a cache mutex across queue submission, a wait, or user callbacks. The SYCL spec does not give this design a universal guarantee that every implementation-specific initialization sequence may be raced by arbitrary host threads.
- Retain the entry for as long as calls may submit using it. On orderly owner teardown, first quiesce/drain its queues under the existing lifecycle; queue/context destructors are not a synchronization substitute. Then release the entry with its owner. If the last cache/bundle reference goes away, SYCL reference semantics release underlying backend resources according to implementation rules.
- Treat a new context/device after queue recreation or device reset as a cache miss and perform all admission checks again. Level Zero states modules are created on a context for a device (or its sub-devices); using an object after a device hang/reset invalidates the context-associated handles, and recovery requires destroying the context and creating a new one. Do not attempt to revive a stale entry or retry the same potentially partially-mutated state after an asynchronous/post-submit error. Existing fail-stop/no-fallback behavior remains authoritative.
- If specialization constants, compile/link options, kernel implementation/image, relevant selector policy, or device binary changes, rebuild the entry in the corresponding new process/configuration. This current kernel sets no specialization constants and uses a fixed named image; that assumption belongs in the cache contract rather than a cross-version/global persistent cache.

The public APIs are standard SYCL. The runtime-object ownership analogy is visible below the abstraction too: Unified Runtime exposes retain/release APIs for context/program/kernel handles; raw-handle management would therefore add manual lifetime obligations with no need in this path. Level Zero module handles are context/device-scoped and cannot safely be treated as GPU-global objects.

## First phase versus steady phase

A conservative first cache-miss phase performs the current admission sequence once: verify this queue is ordered; obtain its context/device; run current device workgroup/dimension/subgroup checks; obtain the executable bundle for exact context+device+kernel ID; check membership; obtain the kernel; query mandatory compiled subgroup/workgroup constraints; and query optional resource descriptors. Only then publish `Ready` with an immutable record, including whether each optional descriptor was successfully read. Cache-construction exceptions remain pre-submit denials. Do not publish partially initialized state.

For later calls through that same owner/key, the steady path may reuse the retained executable bundle and admitted metadata, skip repeated device and kernel queries and bundle/kernel acquisition, and still check the actual queue's in-order property. Continue using the exact bundle through `handler.use_kernel_bundle`. Optional resource descriptors are metadata for the same executable kernel/device and are not gates; if cached, mark them as an entry-time snapshot (`known/value`) rather than implying they were re-queried for the current chunk. If compatibility requires retaining per-call resource freshness, keep just those optional queries per call and measure them separately. A failed optional query remains unknown and never becomes an admission failure.

If the owner can present a queue that does not match its entry, create/obtain a different owner entry or take the existing pre-submit denial path. Never silently use a cache hit from a different context/device. A device-loss/async exception after submit is not a cache miss and cannot select legacy fallback.

## What implementations and public Intel GPU examples establish

The Khronos SYCL 2020 spec/reference (`get_kernel_bundle`, `has_kernel`, `get_kernel`, `handler::use_kernel_bundle`, common reference semantics) gives the portable legality and exact context/device constraints. It does not require `get_kernel_bundle` to be costly, nor prescribe an application cache policy.

The Intel DPC++ implementation documentation says its in-memory cache stores underlying UR program/kernel objects per SYCL context; program keys include device-image ID, specialization-constant values and device set, and kernel entries are keyed by program plus kernel name. The in-memory cache is enabled by default in current DPC++ documentation; persistent on-disk caching is separate and off unless enabled. This implementation already avoids some repeated compilation/object construction, so a user-level retained bundle may mostly save repeated API calls/metadata queries, or may matter little. The public cache docs are implementation behavior, not a SYCL promise and not a timing result for this binary/device.

Intel's SYCL Graph usage guide constructs `MyBundle` once from `MyContext`/`MyDevice`, obtains `kernel` objects from it, captures those objects in command groups, then reuses and replays the executable graph while changing dynamic parameters. Intel's 2026 DPC++ migration article likewise shows fetching an executable bundle outside a submission and passing the retained bundle to `handler::use_kernel_bundle`, or getting a kernel from the bundle and submitting it later. The Intel GPU Optimization Guide presents `sycl::build(kb_src)` followed by use of the executable-state bundle. These are concrete Intel/DPC++ API reuse patterns, but none measures the per-chunk admission path here.

The Codeplay runtime-compilation article discusses source bundles, conversion to executable bundles and persistent cache use, and states Intel GPUs are supported through Level Zero/OpenCL in its compiler support context. This is a runtime-compilation example rather than evidence about DPC++'s handling of this precompiled kernel or Battlemage performance. No inspected llama.cpp/Battlemage implementer report gave evidence of caching this sort of SYCL executable bundle in its hot dispatch. Keep external examples as API usage patterns, not performance proof.

## Measurement-safe next decision, without an adoption claim

The host admission cost is currently unmeasured. A future owner-run experiment should separate first miss from steady hits and retain the current legacy/quad matched checks. Record each host subphase: queue property, device queries, exact executable-bundle retrieval, membership/kernel extraction, mandatory kernel queries, and optional resource queries. Count actual candidate chunks and cache hits/misses. Keep a valid executable bundle alive through submissions. Compare cold-first and warm-steady runs separately, and do not label host query elapsed as GPU elapsed or subtract it from prior full service sums as if the phases were measured in the same run. Preserve output parity, submission errors, normal queue drains and the rule that post-submit errors are fatal/no-fallback. If source/runtime change causes a miss or error, report that path, not a speed estimate.

Only after a safe implementation and a finite component measurement could a clean >=32K quiet timing determine whether reusing admission metadata changes the combined service measure. No cost, speedup, candidate adoption, production default or timing result is claimed here.
