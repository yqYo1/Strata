## Admission and exact identity

The controller has a strong explicit pin chain for a reviewed future candidate. It requires caller-supplied SHA256 values for itself, parser, build receipt, flags receipt, and binary, plus an exact 40-hex engine commit; it refuses Python optimization so admission assertions stay active (`:134-156`). The expected tree path is fixed, HEAD must equal the submitted commit, the tree must be clean, and the commit must descend from frozen H `96bd5bb4e054f6ddcf677fd96e161b499a013fd7`. Source changes are limited to the five reviewed pair files plus docs/bench (`:158-168`). It binds required C/D-independent H resolver/pool/callsite hashes to both the worktree and Git objects, pins the four core pair source files, and checks that the build receipt's source HEAD is the submitted commit (`:203-240`).

The binary must be named `strata`, live beneath the isolated diagnostic worktree, and match both the caller pin and build receipt SHA. The flags receipt must hash exactly, refer to that build receipt and binary, and show 115 compile objects, 114 distinct sources, and no missing/different flags (`:203-217,:277-281`). Build receipt must claim complete/passed/compiled, not active/GPU-tested/adopted, with no cleanup/survivors and owners no longer alive (`:205-214`). CPU-only pair validation pins each production source and explicitly says no GPU/model opened (`:241-245`). These checks are all source-level: SHA256 makes caller-supplied identities exact, but the caller's reviewed commit and receipts remain trust inputs, not signed provenance.

Two schema boundaries are not fully self-authenticating. The build receipt's `source_sha256` items are validated if present, but the controller does not require an exact key set or nonempty owner-role set (`:207-217`). The flags gate enforces counts/no flag changes but does not independently rebuild or inspect compiler invocations (`:277-281`). With caller-pinned reviewed receipts this can be adequate operational admission; it should not be described as cryptographic proof that every receipt producer was truthful. Keep the required exact future build/flags hashes and full compile-coverage evidence as hard preconditions.

The model/profile path is bound coherently. The controller hashes the profile at the isolated worktree's `data/expert-profile.bin`, checks exact STRP geometry and 128-entry static residency through the parser, records path/hash, and rehashes it after the run (`:246-249,:432,:852-853`). It pins pack metadata and checks named model shards' sizes and before/after device/inode/mtime/ctime; it explicitly does not hash full weight payloads (`:250-268,:847-851`). Baseline `--pack` and `--native` paths are required to match those named installed artifacts. It loads the qualified invocation, adds only the selected task count and known fixed inputs, and compares the final argv exactly to the qualified full-context baseline argv (`:619-627`). The script changes its own CWD to the isolated worktree before constructing `OwnedGdb`; that helper starts GDB without a `cwd` override, so GDB and the inferior inherit that CWD. It then verifies the actual inferior argv and environment from `/proc` (`:425,:650-675`). The source does not separately assert `/proc/<inferior>/cwd`, but inheritance is explicit in the helper. A small integration fixture should record the inferior CWD and resolve the relative profile argument, so the runtime binding is directly observed rather than inferred from source.

## CPU-only boundary and stale D fault cursor

The `--cpu-preflight` branch is below all source/receipt/profile/model-stat checks and above import of the native counter capture helper, output-directory creation, health helper execution, `chdir`, GDB startup, and target launch (`:412-425`). Before that branch, it reads files, hashes the binary and inputs, stats model shards, inspects CPU features, checks disk space, inspects process identities, and uses read-only Git commands. The target health helper is extracted/executed only after the branch (`:421-424`); `capture_owned_native_counter` is imported at `:416`, also below the exit. Thus source supports a no-GPU/no-target preflight boundary. One small filesystem side effect precedes it: opening `owned-v0141-measurement.lock` with mode `'a'` can create an empty lock file at `:297`; successful preflight unlocks and closes it at `:414`, and it does not create the measurement output directory. A failed preflight relies on process exit to release the lock and may leave that empty file.

The latest D cursor is treated correctly as a failed-but-closed diagnostic, not as a qualified success. The record SHA is fixed; the controller requires active/healthy/completed false, exit code 0/no signal, no fault messages, no forced cleanup/survivors, same boot, at least one failed request math gate, dead/recycled inferior and debugger identities, and one successful non-timeout `kernel-after` step (`:358-370`). It takes that step's `--after-cursor`, runs a bounded journal gap check, filters target-device/xe fault messages, and requires none before proceeding (`:585-596`). D does not go through `terminal_owned()`'s success-only gate. This preserves D's original failure while allowing a separate candidate experiment. The current gap command is bounded to 5 seconds through `Runner.run`; nonzero/timeout commands raise, so an empty output from a failed journal command cannot silently pass. The new process also snapshots a pre-run cursor and checks for new fault messages in `finally` (`:645,:880-884`).

A useful unexecuted negative fixture is a valid D closure receipt with a deliberately failed math request and exit 0; it must pass only the cursor-admission shape and still leave D's own `healthy/math` status false. Separate fixtures should make the D inferior alive, cleanup forced, kernel-after timed out, and the cursor-gap command fail or return a matching fault; each must prevent target startup. Those branches have not been exercised by this source review.

## Fresh process/request accounting and numerical reference gates

This protocol means four fresh sessions in one owned engine process, not four new engine processes. It launches one exact binary under one `OwnedGdb`, verifies the actual inferior executable hash, argv, environment, PID/start ticks, then sends A/B/A/B 32,768-token requests with `GEN 64 ckpt=1 logprobs=5` (`:647-679,:682-701`). The fixed fixtures are SHA-pinned and exactly 32,768 tokens; output collection requires complete token IDs/logprobs, fresh RESUME/REUSED counts of zero, complete prefill prefix, normal finish, finite values/timings, and valid MTP counts (`:31-53,:631-644`). It compares each candidate request with its corresponding independent four-fresh qualified reference, compares A and B repeats, requires first-head hash equality, all 66 live-state parts equality, and the observed 8192-token progress boundaries (`:713-731`). The baseline normalization requires exactly 64 output IDs and complete logprobs and checks its own DONE/MTP structure (`:60-70`). `same_output()` includes IDs, logprobs, MTP counts, and finish reason; therefore actual baseline MTP values, including the current baseline's 1/5, are compared exactly and are not replaced by a new 5/5 requirement.

Full raw state parts remain required and are SHA-checked in bounded 1 MiB reads before comparison; FNV or route/histogram summaries do not replace them (`:382-395`). The 256K qualified full-capacity receipt remains the independent physical reference, while this new target work is explicitly four fresh 32K sessions and not a physical-boundary/full-lifecycle/adoption qualification (`:186-202,:427`). The output record initializes performance, full-lifecycle and adoption false, records original C/D failures as false, separates `healthy` from `math_gate_passed`, and final exit is nonzero if any required gate fails (`:426-450,:858-892`). If a request fails math, the controller preserves a numerical-failure session before QUIT (`:733-745`). It then requires normal QUIT/exit 0/no signal within the bounded loop; `OwnedGdb.close()` marks forced termination distinctly, and any cleanup flag keeps `healthy=false` (`:748-765,:871-885`). A parser or histogram error also leaves the record incomplete/unhealthy and the controller exits nonzero.

Freshness is evidenced by engine protocol markers and request-level IDs, not process restarts. The actual process is intentionally long-lived for all A/B/A/B reads, and prompt-cache/reused token counts must remain zero. A separate small fake-engine integration fixture should show one process identity across four requests, zero reuse at each, and exact failure if a nonzero reused count appears. No such controller integration fixture has run.

## Log bounds, request ownership, and one cross-cutting parser issue

The controller's live `poll()` bounds total non-binary/non-temporary text beneath the output directory to 64 MiB, and the inferior stderr file is checked against that limit at closure. Protocol stdout is read in bounded 64 KiB system calls and retained in a raw file; total text accounting includes this raw file, event journal, GDB logs and stderr. Request stderr intervals are byte offsets captured immediately before GEN and after DONE; the controller requires exactly one histogram and phase report in each interval, one route frame bound to the request ordinal/DONE counters, and rejects route markers outside all four intervals (`:515-551,:682-703,:766-768,:785-845`). The parser independently caps each request and total route bytes; its full strict wire grammar and known omissions are covered by the supplied parser audit, not repeated here.

One output-bound gap: after the last live `poll()`/64 MiB total-text check, the controller writes `project-messages.txt` by copying every `strata ` line from `inferior.stderr` (`:766-772`). It checks only the original stderr file's size, not the total text size again after adding this derivative. A near-limit run can therefore exceed the declared 64 MiB aggregate text budget by approximately the size of the copied project lines. This does not permit an unbounded target run—the original engine log is still capped—but the total-artifact budget claim is not exact. A CPU fixture can use a synthetic 40 MiB strata-only stderr plus enough other text to stay below 64 MiB before extraction and show the derived file pushes the output above the cap; either include derived output in the budget or omit it after recording the needed summary. The line parser later enforces a maximum 65,536-byte line for stderr records, but the PTY stdout `line()` helper has only the whole-directory budget and no independent line-length limit (`:529-551`). The fixed server protocol is local, but a 64 MiB unterminated line could consume significant memory before the aggregate check stops it. Add a bounded pending-line limit fixture if controller hardening is desired.

Cross-cutting blocker from the independent parser audit: the controller trusts `parse_request()` and sets `pair_gate_passed=True` when aggregate reconciliation succeeds (`:813-845`). That audit found the parser checks each pair's `callback_pairs <= callbacks/48` but does not require the sum of callback pairs within a layer to be `<= callbacks/48`. A malformed frame could therefore pass this controller's current route gate with an impossible per-layer callback-pair sum, despite all other framing being strict. I did not duplicate that parser audit; see `cache-route-pairs-parser-source-audit-round41.txt` for its exact suggested fixture and correction. Until the producer semantics are source-proven and the per-layer sum is checked (or a stronger exact relation established), describe the route-pair gate as parser-accepted aggregate accounting, not a fully closed callback-accounting proof.

The native histogram is reconciled by phase: native GU and Down token totals must equal refused entries, and native expert jobs must equal the sum of refused callback pairs for nonresident profile entries (`:823-830`). The parser report confirms this distinguishes CPU misses from total callback pairs (which include GPU hits), but V1 does not carry per-window identities or per-pair NT bins. This route result is exposure accounting, not an observed timing/traffic/worker-tail measurement or performance claim (`:808-812,:843-844`).

## Lifecycle/artifact behavior and smallest independent fixtures

The output directory is required absent; it is created mode 0700 only after CPU preflight. Raw full-state/head captures are renamed per request and preserved, the original numerical failure session is retained on failure, source status/HEAD are checked again before completion, the final inferior log and record are hashed, and there is no cleanup path that deletes run evidence (`:295-298,:418-420,:478-513,:733-745,:854-889`). `healthy` requires process completion, normal exit, histogram and pair gates, no new fault/error, and no cleanup; math remains separately required for final process success. Normal QUIT is distinct from `OwnedGdb.close()` fallback termination: a zero exit/signalless path is required before cleanup can be considered clean. This preserves failed D and C records; no existing result is rewritten.

Recommended CPU-only discriminating fixtures before any target integration are: (1) all pin-chain valid/invalid substitutions, including absent source hashes/owner roles; (2) CPU preflight asserts no health/capture module invocation, no GDB/target, no output directory, and documents the lock-file side effect; (3) D failed-math normal-closure admission versus alive/forced/timed-out/fault variants; (4) one-process A/B/A/B protocol with zero reuse, exact output/state gates, early math failure and preserved SAVE session; (5) stderr/request interval, orphan frame, line cap, aggregate output cap after `project-messages.txt`, and cursor-gap fault/timeout cases; (6) normal QUIT versus timeout/forced cleanup with all PIDs/identities and artifact states reconciled. The supplied parser tests do not cover controller interval attribution, runtime environment/CWD capture, or the histogram join; the parser audit explicitly did not run them. None of these tests or target integrations were executed here.

## Overall finding

The source has a strong, fail-closed identity/reference/lifecycle design and deliberately treats the newest D receipt as a normal process close with a preserved math failure, not a successful baseline. The CPU-preflight branch does not launch the target or invoke the GPU health/counter helpers. Exact runtime CWD is inherited from a source-proven `chdir` but is not directly recorded from `/proc`. The controller's strongest open gate issues are the parser's known per-layer callback-pair-sum omission, the aggregate text budget's post-extraction copy, and the absence of controller integration fixtures. These are source-audit findings, not a measured controller run. Keep the unknown future commit/build/binary/flags pins unresolved until the root supplies and reviews them, and keep all existing math and physical-context failures unchanged.
