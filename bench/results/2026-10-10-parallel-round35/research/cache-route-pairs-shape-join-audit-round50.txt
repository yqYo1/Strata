## Arithmetic and histogram join

No arithmetic defect was found for the stated workload. R42's source proof establishes the needed invariant: each PAIR's `entries=N` is the sum of each grouped job's `nt`; `callback_pairs=J` counts one expert job per callback for that pair. Spec4/S=4 plus split verification bounds each group to at most two rows; top-10 IDs are unique within each token, so a given expert occurs at most twice in a callback. Thus `J1=2J-N` and `J2=N-J`, with the checked admission `J <= N <= 2J`. The source anchors are `cache_route_pairs.hpp:30-77`, `expert_source.cpp:2745-2794`, `verify.cpp:773-785,1681-1723`, and the two router selections. In the pool, each grouped expert is counted once with `cell.experts++`, `cell.tokens += jobs[e].nt`, and `cell.rows += FF` for GU or `H` for Down (`pool.cpp:794-813)); output rows are therefore 640 GU or 2560 Down per job, independent of NT. The module's derived (experts,tokens,rows) increments match this emitter contract.

For every pair, the module checks its coordinates and shape before using metadata indexed by layer (`cache_route_shapes_v1.py:52-60`). It derives both NT cells, then skips resident pairs only after requiring an all-hit/no-refusal/no-offload classification; nonresidents must be all-refused (`:62-74`). That is correct for the frozen static 128 profile: a resident pair contributes no current CPU job, while an absent pair contributes `callback_pairs` jobs. It maps GU type and Down type separately from the layer row, and requires exact equality of the complete `(phase,type,nt) -> (experts,tokens,output_rows)` dictionary to histogram cells (`:68-80`). This catches format, NT, count, row, missing-cell, and extra-cell differences rather than only global sums. It remains a count/exposure reconciliation; it does not infer service time, bytes moved, pool tails, or latency. R46 calibration is a separate, unexecuted demand-calibration protocol, and even its future values would not turn this cell join into measured request speed.

## Metadata interpretation and trust boundary

The metadata parser fixes the IQ3_S v3 file identity by comparing the supplied SHA, accepts exactly 48 ordered rows, enforces header `n_expert 512`, and permits only GU IDs 18/21/22/23 and Down IDs 20/42 (`:16-42`). Its geometry uses H=2560/FF=640, not the residual R=10240. The hardcoded row-size terms are internally consistent with `NativeFmt` geometry: `up_off=ggml_row_size(gu,H)*FF`, `down_off=2*up_off`, `bytes=down_off+ggml_row_size(down,FF)*H` (`native_expert.cpp:46-64`). The metadata examples also agree: layer 0 (18/20) has 2,176,000 B; layer 1 (22/42) 1,510,400 B; layer 47 (23/20) 2,662,400 B. The parser checks contiguous logical pack offsets and each blob formula. The actual metadata's exact hash is a critical trust anchor; callers must pass the literal pinned SHA, never compute the “expected” hash from the same newly read bytes.

The helper intentionally extracts a per-layer type map, not a payload reader. It checks only that GGUF role offsets are positive, not their shard identity, bounds, alignment, or tensor extents; R48's `FileExpertSource`/reader validation remains separately required if samples are actually loaded. It also duplicates ggml row-size facts in `gu_blocks` and the Down block divisor/size constants instead of querying `native_fmt`. Those constants reproduce the listed metadata blob sizes for the four supported GU types and two Down types, but the helper itself does not prove their equivalence to the frozen ggml type traits. A clean integration must bind these constants to the pinned `NativeFmt` source / matching metadata hash and reject any mismatch; the shape helper should not be represented as validating GGUF payload bytes.

There is also an input trust boundary at `reconcile_shapes`: it requires `parsed.passed is True`, `histogram.passed is True`, 48 formats, completion and zero offload, but does not itself revalidate the route parser's other BEGIN/END status, the histogram resolver/settings/schema, or that the residents set is the exact 128-entry profile. It compares `histogram['cells']` but not its `totals` field. That is reasonable only when the caller supplies the exact pinned parser's and exact frozen histogram parser's admitted objects and the profile parser's verified resident set; the function is not an independent validator for arbitrary dictionaries. Its own interface would accept a fabricated `passed=True` wrapper and non-128 resident set if the cells/classifications happen to reconcile. Record these preconditions in the integrating caller and test that it passes the literal metadata hash, parser outputs, and the host residency set authenticated by the existing profile fingerprint.

## Fixture oracle and missing discriminating cases

The scalar oracle is usefully independent of the formula under test: `reference()` declares explicit token-list jobs, aggregates entries/job occurrences, and builds histogram cells from each job's token-list length (`test_cache_route_shapes_v1.py:9-31`). The mixed fixture exercises an NT1 and NT2 occurrence for one nonresident pair, a different layer/type, and a resident pair with mixed token-list sizes; it checks derived shapes. Further cases cover a GU type relabel with global totals preserved, rows/missing/extra cells, all-hit/all-miss, impossible `J,N`, classification changes, and pinned actual metadata identity/geometry (`:34-99`). These are a suitable basic oracle set.

One test title overstates its discrimination: `test_wrong_nt_preserving_expert_total_rejected` changes the first histogram cell's NT from 1 to 2 (`:50-53`). The fixture already has a `('GU',18,2)` cell, so it fails at duplicate-key detection, before the exact expected-versus-actual NT join. It does not show that a *unique-key*, valid-looking, NT redistribution that preserves phase expert/token/row totals is rejected by `actual == expected`. Add a mutation that shifts one job's NT1/NT2 label between existing format cells, adjusts experts/tokens/rows consistently, keeps keys unique and preserves aggregate experts/tokens/rows; expect the specific `per-format/NT histogram differs` branch. This is the most useful missing negative for the implementation's differentiating behavior. A similarly direct Down-type relabel negative would protect the separate Down metadata mapping; the present format relabel changes only GU (`:42-48`). Metadata negatives for malformed/extra v3 fields or declared header total inconsistent with all rows are optional under the literal SHA pin, but the helper currently ignores the optional ninth shard token and header total (it validates neither); don't elevate the type-map parser into a full layout/payload validator.

The fixture's positive reference uses only one resident entry as a small algebra fixture (`:10-15`), so it does not prove the production 128-resident admission. The real controller must retain the existing static profile/fingerprint checks; this is not a shape-math defect in a reusable join helper. Likewise the synthetic route fixture is not an actual inference, native histogram, current candidate, or decision about which experts to cache.

## Conclusion

The derived NT shape and per-format/NT cell equality are correct under R42's proved two-row/static-route assumptions, and resident exclusion plus the 640/2560 output-row accounting matches the frozen pool emitter. No per-job speed, traffic, or mathematical adoption follows.
