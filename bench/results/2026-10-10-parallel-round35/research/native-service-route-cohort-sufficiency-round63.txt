## Selection and holdout contract

For each `(model-pack identity, metadata SHA, phase, format type, NT, dispatch)` cell, construct its eligibility set using the rules above, then bind every candidate ID to its layer-local format, the selected shard, role offsets/lengths, expected logical blob length, and source identity. Hash the actual selected role extents (or bind an immutable pack manifest plus selected-extent hashes) before timing and recheck pack identity afterward. Do not persist a second expert corpus.

After filtering invalid candidates, stratify by available layer and captured frequency band, then sort IDs within strata by a documented stable key and use a fixed declared seed to allocate 192 IDs to train and 192 disjoint IDs to holdout. Selection should balance strata as evenly as possible without excluding low-frequency eligible IDs. Record exact sorted ID lists and the allocator version/seed; do not derive the selection from timing results. Reuse the identical eligible source pool only as needed, but keep the train/holdout split disjoint within each cell. Record cross-cell expert reuse explicitly. If an eligible set has fewer than 384 IDs after source validation, use deterministic metadata-selected IDs only as a separately labeled format-kernel calibration; do not call it route-weighted service evidence.

The manifest for each selected ID should contain `(layer, expert)`, phase/type/NT cell, A/B source-pattern presence, per-pattern logical job count, route eligibility reason (`refused>0`), train/holdout assignment, metadata path/hash, shard path/size/hash, role offsets and byte lengths, expected blob size, selected extent hashes, and pack identity. Preserve the repeated-job totals as context, never as sample weights until service times have actually been measured. This capture supplies default-policy route exposure only; it does not establish how a live routing/cost policy would select jobs or prove that calibration samples represent an uncaptured workload.
