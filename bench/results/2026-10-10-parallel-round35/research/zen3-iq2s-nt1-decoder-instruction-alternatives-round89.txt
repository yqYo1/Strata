Round 89: IQ2_S NT1 decoder instruction alternatives on Zen 3

Question and scope
Does an implementation source, personal engineering write-up, or Zen 3 quantized GEMV show a portable way to reduce IQ2_S NT1 grid/index/sign/scale instruction pressure beyond R17/R21 paired-row and register-pressure work, R33 NT1/gather screen, R70 direct exact-row/call control, R83/R85 paired Gate/Up Q8 reuse, and R87/R88 emitted-ISA/input-domain closure? This was a read-only review of the current Strata CPU source, pinned GGML commit `3cf03257f219afbe7334045ff7c6a06ac68c627d`, those assigned reports, and web primary/author sources. No implementation, build, import, preprocess, disassembly, test, device/runtime, model, profiling, Git, or cleanup action was performed. Root-reported emitted code now confirms the current calibration binary's IQ2_S dot uses AVX2 integer dot instructions and YMM FMA; no new ISA-discovery claim is made here.

Current source path and decode shape
The current IQ2_S NT1 route calls GGML's `ggml_vec_dot_iq2_s_q8_K` as the type trait (R33/R85). The pinned AVX2 body gets a 10-bit grid index from each `qs` low byte plus two `qh` bits, performs scalar `iq2s_grid[index]` reads to build four qword lanes per vector, then expands sign bits, performs the Q8 sign transfer, scale shuffle, `maddubs`/`madd`, and ordered accumulation. Its packed IQ2_S format and exact reduction/FMA order are constraints; changing codebook or weight layout is out of scope.

The current Strata AVX2 multi-token source already contains two decoder mechanisms for type 22 in `src/kernels/cpu/iq_avx2.cpp`: `Fmt32<22>` constructs indices with a constexpr 256-entry `HiSpread::iq2s` table and `grid_indices` (unpack low-index bytes with spread high bits), keeps four scalar 64-bit `iq2s_grid` reads, and obtains expanded odd scales from `ScaleVecs::s16`; `Fmt32<122>` uses a vector index and `_mm256_i32gather_epi64` for the same four 64-bit codebook words. `ScaleVecs` documents one vector load instead of the nibble shift/or/broadcast sequence. These fast decoders are part of the NT-batched row path, not the active NT1 GGML trait path. The row path's scalar/vector float schedule remains unsuitable as an NT1 replacement by itself; any reuse must retain GGML's two int32 accumulators, per-block FMA order, final horizontal tree, and post-reduction 0.125 factor.

One narrow, unmeasured source-reuse candidate remains
A dedicated type-22 NT1 exact-order helper could reuse only the current Strata `HiSpread`/`grid_indices` index construction and `ScaleVecs::s16` scale expansion while retaining the pinned GGML grid values, Q8 sign handling for the R88 admitted byte domain, integer grouping, two per-row int32 accumulators, ten block FMAs at H=2560, horizontal sum, and post-sum scale. This targets index-construction and scale-expansion instructions. It leaves four scalar codebook-word loads per output vector; it is not the paired raw-Q8-load proposal, not per-expert cache/predecode, and not call-target elimination. At the algorithm level, these small lookup tables already exist locally, so this is a *new NT1 application of existing source machinery*, not a new external algorithm or a reason to change default dispatch.

This is only a source-level hypothesis. The current `Fmt32<22>` decode also stages an index scratch array, and scale-table loads can compete with data loads; no source proves fewer total cycles, less register pressure, or a Zen 3 win. A future bounded prototype would have to compare every constructed grid vector, signed Q8 vector, and scale vector with the current GGML decode on legal Q8_K outputs, then compare every dot result bitwise. Keep GGML float order unchanged, inspect the actual helper's spills, and benchmark only after root's corrected service gate identifies GU22 NT1 as material. Do not combine it with paired-row fusion in the first comparison, since that would confound decode and activation-load effects.

Gather screen and Zen 3 instruction evidence
Gather is not a newly discovered candidate: R33 already records that Strata has gathered IQ2_S variants and that GGML's analogous IQ3_S gather was reported slower on a Ryzen 9 7950X. The current local gathered IQ2_S implementation is `Fmt32<122>`; its comments describe a 14900KF P-core benefit for IQ2_S but say IQ2_XXS's gathered 64-bit grid variant was slower. The public Strata #622 write-up reports a separate i7-12850HX experiment: the 64-bit IQ2_S gather variant went 246→284 μs, while IQ3_XXS/IQ3_S 32-bit gathers improved on P-cores. These are CPU- and route-specific historical measurements, not Zen 3 outcomes and not NT1 exact-order evidence. They argue against a portable “one gather is cheaper than scalar lookup” claim.

For instruction context, Agner Fog's Zen 3 instruction table lists the four-lane AVX2 `VPGATHERDQ` form (qword data with 32-bit indices, matching the `_mm256_i32gather_epi64` shape) at roughly 19-cycle latency and 4-cycle reciprocal throughput; its table is a per-instruction measurement, not a prediction for a cache-hot codebook sequence or the complete IQ2_S row. [Agner Fog instruction tables](https://www.agner.org/optimize/instruction_tables.pdf). The broader uops.info site describes its data as measured instruction latency/throughput/port-use records, but the queried gather forms do not by themselves compare this exact GGML sequence against four scalar indexed loads plus vector assembly: https://uops.info/ . Therefore no speed ranking is inferred from instruction tables.

External implementation screen
- Mainline llama.cpp's pinned AVX2 IQ-panel commit uses vectorized IQ panel decode and an 8x8 Q8_K GEMM, with a minimum batch of eight; it changes the panel/dataflow and is already screened in R30/R45. It is not an NT1 exact-row decoder substitute: https://github.com/ggml-org/llama.cpp/commit/85c55223caf0a2ad0d1d88e5a73ab3fe36107867 .
- The current upstream tiled-kernel source includes IQ2_S in its tiled quantized microkernel, but it uses a separate tile/activation-bias dataflow rather than the GGML per-row floating-point schedule. It is not an unchanged exact NT1 path: https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cpu/tiled/tiled-kernel.cpp .
- The ik_llama IQK author discussion recommends `pshufb` for very small 4/8/16/32-entry quantization alphabets. IQ2_S instead indexes a 1024-entry packed grid; a small alphabet within the table does not make the 10-bit index-to-eight-byte mapping a single-register shuffle. IQK also uses different quant encodings. That small-LUT technique is already screened and does not supply a same-format NT1 implementation: https://github.com/ikawrakow/ik_llama.cpp/discussions/8 .
- The 2026 Vec-LUT article's vector lookup mechanism targets ternary/small-alphabet weight patterns and parallel token tables. It modifies the LUT/dataflow and targets a different quant family; it does not preserve IQ2_S packed bytes or GGML's NT1 reduction contract: https://xxxxyu.github.io/blog/vec-lut-parallel-low-bit-llm/ .

Conclusion
No distinct external or Zen 3 implementation mechanism was found beyond the gathered decode, tiled/panel GEMM, and small-LUT ideas already screened. The only remaining narrow, source-bound candidate is an exact-order NT1 adaptation of Strata's existing `HiSpread` index-spread and scale-vector tables. It is unmeasured and should remain a hypothesis pending the material-service gate; it does not justify changing dispatch or recommending gather. This is not evidence that a decoder optimization will improve component or engine speed.
