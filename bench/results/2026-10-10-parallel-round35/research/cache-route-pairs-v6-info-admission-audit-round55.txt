## Is `arena_mib=47962` an overfit sample?

For this exact invocation it is a defensible fixed configuration readback, not a generally portable constant. The status emitter computes `arena_mib` as `(o.mmap_experts ? src.resident_bytes() : expert_layout().total) >> 20` (`generate.cpp:8406`). The admitted argv has no `--mmap-experts`, so this is the native expert layout's logical arena total, rounded down to whole MiB, rather than a runtime RSS reading or the sum of all original GGUF shard file sizes.

The pinned `ExpertLayout` loader reads the pack's `native_experts.txt`, validates each type-derived per-expert blob size, then accumulates `L.bytes[layer] * L.n_expert` over layers into `L.total` (`expert_layout.cpp:390–474)). V6 retains the exact engine/build/binary, pack metadata hashes, conversions/source-shard identities, model argv, and other source/profile pins that identify this geometry. The prior qualified full-context receipt and failed r5 receipt both record the same INFO value 47962 under the same pinned configuration. In that scope fixing the deterministic layout-derived value catches an unexpected pack/layout change; accepting arbitrary arena values would weaken config readback.

The limit matters: `47962` is not a universal Strata value and should not be reused for another pack/build, layer geometry, or mmap mode. It means floor(`ExpertLayout.total / 1 MiB`) for this pinned non-mmap run. I did not independently read/recompute the pack metadata or model payload in this audit; the value correspondence rests on the source formula, frozen pack pins and the two existing matching INFO receipts. A future pack or mmap-policy change must derive/review the expected field again rather than copying this sample.

## Stateful order and actual v5 closure admission

V6's `startup_step(value, seen)` enforces progress INFO only when `seen=[]`, then terminal READY only when `seen=['progress']`; a second INFO, early/wrong/duplicate READY, or other line fails. Generic ERR is classified as an error and raises. The loop appends each exact line to `record['startup']`, calls `startup_step`, and only breaks on READY. The existing before-GEN boundary then detects any extra buffered row after READY. Thus the actual r5 failure is admitted as a known prior failed startup job, not relabeled success.

Before a new job, v6 hash-pins the r5 receipt and asserts inactive/incomplete/unhealthy/math-false, no request records, null process exit/signal, exact forced-cleanup/no-survivor values, same boot, no GPU fault message, exactly the observed INFO line and the startup grammar ValueError. It also checks the recorded inferior/debugger PID and start ticks no longer identify the same live processes. This is closure evidence for a failed pre-GEN owner; it does not call `terminal_owned` or require a successful exit/math gate. The original r5 failure values are copied into the new run record separately.

For precision, the pinned r5 receipt says `cleanup.forced=true`, `inferior_survived=false`, `gdb_survived=false`, exit code/signal null, and no fault messages. Its math flag is false because no GEN/request occurred. V6 preserves those facts without implying a numerical failure.
