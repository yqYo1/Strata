# Round 47: layer-group schedule capacity boundary

## Scope and disposition

Read-only source/metadata audit only. No source edit, test, build, GPU query, inference, profiler, Git mutation, or cleanup. I searched registry-v34 and the shared R3/R34/R39-R46 reports. They cover per-layer chunk-major/layer-major schedules, full residual spill/reload ownership, the streamed-KV stage lifetime, and the withdrawn R45 all-layer chunk-major proposal. I found no prior proposal or analysis of a bounded adjacent-layer group that keeps a group's expert weights resident while processing each chunk through the group and spills residual only between groups. This report records only its source/metadata capacity boundary; it does not recommend or claim feasibility/performance.

## Exact packed expert-cache lower bound

Pack metadata is `/home/yayoi/.local/share/strata-sycl/packs/qwen3.8-flash-next-iq3_s/native_experts.txt`, header `n_expert=512`, with each layer's `blob_bytes` and model geometry already recorded in `layer-expert-cache-footprint-contract-round10.txt`. Summing exactly 512 packed expert blobs per adjacent layer gives these group-cache requirements if all group experts must remain device resident:

| Adjacent group size | Lowest group | Highest group | Highest exact packed cache | Highest with current uniform `MAXBLOB` slots |
|---:|---|---|---:|---:|
| 1 | layer 8/10/13/36 | layer 47 | 1,363,148,800 B (1.2695 GiB) | 1.2695 GiB |
| 2 | layers 0-1 | layers 46-47 | 2,477,260,800 B (2.3071 GiB) | 2.5391 GiB |
| 4 | layers 0-3 | layers 44-47 | 4,862,771,200 B (4.5288 GiB) | 5.0781 GiB |

These are exact payload capacities, not runtime free-memory readings. Current `run_layer_major` allocates 512 slots each of `MAXBLOB()` (`prefill.cpp:2612-2616`), so only the one-layer 1.2695-GiB arena is currently wired. `ExpertCache::open_sized()` supports a single arena with variable 256-byte-aligned slot lengths (`expert_cache.cpp:691-721`), so the exact sums are expressible in that allocator. That API fact does not make grouped residency work by itself: current layer-major sets a 512-entry layer residency mapping to slot `e`, loads one layer's 512 blobs, and exposes only `[layer,layer+1)` to `run_impl` (`prefill.cpp:2648,2671,2683-2719`). A group arena would need disjoint 512-slot ranges and exact per-layer cache-slot mappings for every simultaneously resident layer, then use those same maps for every chunk in the group. Existing one-layer residency setup is insufficient.

The current streamed-KV full-capacity stage is shared, not one stage per QSA layer. For int8 at 262,144 cells it is 276,824,064 B (264 MiB), as established in R3. It can be counted once in the existing gross working set; do not multiply it by group width. The layer-major residual backing is host memory, 10,737,213,440 B for 262,139 rows, not VRAM. With the group cache substituted for the current one-layer arena, the known cache-plus-QSA-stage subtotal is 2.5651 GiB for width 2 and 4.7868 GiB for width 4. Those subtotals exclude all other live device allocations and are not a fit guarantee.

The configured 384-MiB main cache and 896-MiB MTP weights are suspended/released around the layer-major temporary cache and restored afterward (`prefill.cpp:2578-2609,2747-2764`). They should not be added as if simultaneously live with that arena during the prompt phase; nor should their released bytes be counted as available without an exact memory snapshot. R12's 1,571,250,176-B before-lease, 496,001,024-B after-lease, and later free-memory deltas were explicitly not attributable to a single allocation. R10 has a separate prior attempt in which only 0.99 GiB was free when the 1.2695-GiB one-layer arena was requested and allocation was refused. That is not the exact frozen C environment's free-byte snapshot and must not be used to assert C's current headroom.

Consequently, the exact capacity gap is a missing same-boundary free-memory measurement/receipt for the frozen C6cdf810... setup after the same cache/MTP lease and before group-cache allocation, together with bytes for the other simultaneously live prompt buffers. Physical card capacity of 10 GiB minus the stated lease sizes is not enough to resolve it. Width 2 requires at least 2.3071 GiB free for the exact expert arena alone (plus the 264-MiB stage and all other extant allocations); width 4 requires at least 4.5288 GiB for the arena alone (plus the same). Current reports do not show either threshold satisfied or rejected for the exact frozen run. No live device query was performed as instructed.

## State and ownership boundaries relevant to that gap

This schedule would retain the same single QSA stage and process QSA state in each layer's increasing chunk order; QSA host backing, resident-page maps, indexer state, and GDN recurrence/conv state remain per-layer session state. PLE's shared `ple_prev` cannot simply flow from one layer's full-prompt `run_impl` into the next layer: R45 already identifies the need to restore a per-chunk pre-layer history for each layer call and commit its advancement only once per chunk. This is a previously identified correctness constraint, not a new result here.

The existing one-layer load boundary waits compute, copy, and stager before replacing the temporary cache, then synchronously loads all 512 experts (`prefill.cpp:2683-2715`). The layer-major restore guard also owns queue drain and pointer restoration. A grouped cache could stay allocated across member layers, but changing its slot map, reusing the single KV stage, and handling cancellation/error while queues may still reference the group arena require explicit successful-completion ownership. R42/R44 document that a failed/unknown queue completion is not permission to free or reuse an owner. No source trace here proves a new multi-layer cache's error path or lifetime safe.

A group-width schedule therefore remains unqualified on both capacity evidence and cache/state/queue ownership. The precise next discriminant, if reconsidered after the frozen numerical failures are resolved, is a frozen-environment pre-allocation free-byte/active-allocation snapshot plus a source-reviewed slot-map and successful-fence contract. The C/D full-context math failures remain unchanged. No schedule, capacity admission, performance, or adoption claim follows from this audit.
