## Queue identity and handler

`Prefill::init` stores `m.cs = strata::q_of(stream)` (`prefill.cpp:1050-1059`). A null stream maps to `dpct::get_in_order_queue()` (`include/strata/sycl_queue.hpp:12`). `device_ext::init_queues` creates both default queues through `create_queue_impl(true, ...)` (`include/dpct/device.hpp:685-696`), so these queues carry the project's `strata::rethrow_sycl_errors` handler. A non-null `m.cs` is caller-supplied; its construction and handler cannot be established from this function alone.

The layer-major copy queue is explicitly created with `create_in_order_queue_with_profiling(true, ...)` (`prefill.cpp:1112-1115); the factory attaches `exception_handler` when its first argument is true (`device.hpp:625-634`). Experimental `kv_copy` is made by `create_queue(true)` (`prefill.cpp:2898-2910), which likewise attaches that handler. `strata::rethrow_sycl_errors` prints every exception and rethrows the first (`include/strata/sycl_error.hpp:8-19`). Therefore the project handler is not print-and-consume: when a handler invocation is triggered, it propagates an exception to the invoking call (subject to that API's contract).

## What the drain calls mean

Khronos SYCL specifies `queue::wait()` as blocking until commands already submitted to the queue complete; its description reports synchronous errors, but does not dispatch unconsumed asynchronous errors. `wait_and_throw()` also blocks, and passes unconsumed asynchronous errors to the queue/context handler. Consequently a successful `wait()` can retire accesses while failing to surface an asynchronous device error; it is not a correctness-success signal. The handler is also specified to be invoked automatically on destruction when unconsumed asynchronous errors remain. The default handler, when no user handler is associated, must report errors and invoke `std::terminate` or equivalent. Here the project does provide a handler on queues it constructs, and that handler itself throws.

The layer-major `Restore` destructor calls `m.cs->wait(); m.copy->wait(); m.stager->finish();` and conditionally `m.kv_copy->wait()` (`prefill.cpp:2693-2708`). `Stager::finish()` stops new claims and waits for active CPU workers (`:531-540`); it does not inspect SYCL async errors or fence the queues. The layer-major normal path also uses plain waits at `:2710`, `:2788-2792`. The `KvDrain` guard in `run_impl` waits its stream and, for retained staging, `m.cs` (`:2915-2925`). None of those `wait()` calls itself delivers queued async errors. Elsewhere explicit `wait_and_throw()` exists, including batched compute (`:4873`) and `Prefill::release` (`:819-822`), but these do not make the Restore/KvDrain cleanup calls error-reporting waits.

C++ destructors are implicitly `noexcept` unless declared otherwise. Thus if a synchronous wait error escapes one of these guards, or if `Stager::finish()` throws, stack unwinding terminates rather than reaching the caller's `false`/`err` path. If the waits return normally after an asynchronous kernel error, the guard can restore pointers and the call can appear to return ordinary cancellation/failure while the queued error remains unconsumed. A later `wait_and_throw()` may report it; an automatic queue/context destruction handler is another reporting point. Exact behavior at the actual device/runtime endpoint is not established here: no matching binary trace or fault injection was performed, and which queue owns an error can be runtime-dependent. In particular, do not infer that a failed wait proves queue work has retired.

## Safe handling direction and discriminator

Move the observable drain out of destructor-only control flow: an explicit owner-controlled `drain(error)` should stop/join the Stager, attempt the relevant `wait_and_throw()` on each owned queue, preserve the first diagnostic while continuing best-effort observation of other queues, then return an explicit status to the enclosing operation. Keep the destructor as a nonthrowing last-resort lifetime guard. Crucially, do not free, reuse, restore, or reassign backing memory after a wait whose failure leaves completion unknown; mark the session/resources poisoned and retain/quarantine owners until a documented completion fence or process-level recovery. A handler that logs and returns alone is unsafe because the API call can then report success; if adopting a nonthrowing handler, pair it with a durable error latch checked by the explicit drain. This is a design recommendation, not an implemented or validated fix.

A CPU-only source/unit discriminator can use a fake queue/stager: (1) normal completion, (2) completed work plus a deferred async error delivered by `wait_and_throw`, and (3) a synchronous fence failure with completion unknown. Assert async errors reach the returned error/status; all queues and CPU workers are attempted; state restoration/release happens only when completion is known; unknown completion poisons and retains owners. Test destructor-throw behavior only in a subprocess expecting terminate. This checks the ownership/error contract without GPU work; it cannot establish a particular backend's handling of a real hardware fault.
