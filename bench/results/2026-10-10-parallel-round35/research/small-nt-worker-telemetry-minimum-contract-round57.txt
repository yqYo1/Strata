## Question and source boundary

The sole decision question is whether the present all-GU / serial-FF-quant / all-Down rendezvous leaves meaningful *expert-local* GU-ready time that a bounded same-layer dependency scheduler could use. Source feasibility is described in R56. This telemetry does not profile arbitrary kernels or capture every row fragment for later reconstruction; it estimates (a) actual active worker work, (b) busy-spin and parked/wake behavior, (c) host publication/completion wait, and (d) expert readiness lead relative to the batch-wide GU completion.

The frozen pool (`diag-sycl-cache-route-pairs-v0141-20261010`, HEAD `66aaec3a66ad9ed12e6d042cffe743c47e364432`) uses one shared epoch/task counter. `run_phase` waits for workers to park, publishes one batch, optionally has the host drain, waits for all tasks, then waits for workers to park again (`src/kernels/cpu/pool.cpp:479-539,542-564,567-608,611-688,691-701`). Worker idle includes `_mm_pause` before it transitions to the condition-variable sleep path; the host's `wait_done` and `wait_parked` are spin loops. Worker activity and the host are therefore different threads/states and must not be collapsed into a single “active” number. Current `STRATA_DECODE_TIMING` gives phase elapsed aggregates while `STRATA_NATIVE_DISPATCH_HISTOGRAM` gives logical job counts by format/NT/dispatch. Neither gives per-worker active CPU, queue/wait state, or when each expert's final GU rows became ready. Existing counters remain useful context, not replacements for these measurements.

## What the clocks mean

Use two distinct Linux clock dimensions in a bounded root-owned instrumentation build:

- `CLOCK_MONOTONIC_RAW` timestamps order publication, worker observation, first claim, segment finishes, joins and wake/park boundaries across all participants. Linux documents it as raw hardware-based monotonic time not adjusted by NTP/`adjtime`; record `clock_getres` and do not assume calls have distinct nanosecond values. `CLOCK_MONOTONIC` is also nondecreasing but can be rate-adjusted. Do not mix these wall timestamps with CPU-clock values in subtraction.
- `CLOCK_THREAD_CPUTIME_ID` deltas measure CPU time charged to the thread that sampled them. Linux defines it as the current thread's CPU time. It counts busy spin, task-claim/scheduler instructions and kernel-wrapper work executed on that thread; it excludes time while that thread is blocked in the condition variable or otherwise not scheduled. It is **not** a matmul/row-kernel cycle count and not pure useful compute. Around only a row-kernel call it still includes that function's complete CPU execution and instrumentation boundaries, not a hardware event count or instruction attribution.

For one bounded interval, `wall_ns - thread_cpu_ns` is a non-running/blocked/preempted portion, not an attribution to “scheduler wake,” condition wait, GPU wait, or a particular OS cause. Keep state labels beside each pair of deltas. `CLOCK_THREAD_CPUTIME_ID` during the current worker spin loop specifically quantifies CPU consumed in the wait state; the same clock around `pthread_cond_wait` is close to zero during the sleep, while wall time includes suspension and return/mutex reacquisition. Condition-variable wall duration is not pure kernel wakeup latency either.

An internal `publish_ns → worker observed new epoch_ns` delta is user-level publish-to-observation latency: it includes the producer's publication/notify and any delay until the worker next runs/reads the epoch. `worker observed epoch → first claim` is the worker's user-level wake-to-claim path. `publish → first claim` does **not** isolate scheduler latency. To separate runnable-to-running scheduler delay, Linux kernel `sched_wakeup` and `sched_switch` events can be paired; that is a different kernel trace/privilege-sensitive measurement and is excluded here. Intel's VTune documentation likewise separates wait, spin/overhead, thread transitions and preemption wait; it notes spin can be counted with wait depending on collection mode. These definitions support keeping the categories separate; they do not justify retrying the already-rejected local VTune/gprofng collection routes.

Primary semantics references:

- Linux [`clock_gettime(3)`](https://www.man7.org/linux/man-pages/man3/clock_gettime.3.html): MONOTONIC, MONOTONIC_RAW and THREAD_CPUTIME_ID descriptions.
- Linux [`pthread_cond_wait(3)`](https://man7.org/linux/man-pages/man3/pthread_cond_wait.3.html): condition waits suspend execution and do not consume CPU time until signaled; return includes mutex reacquisition.
- Linux kernel [event tracing documentation](https://origin.kernel.org/doc/html/latest/trace/events.html): `sched_wakeup` event fields and trace events; only a kernel trace can distinguish actual wake-to-scheduled transitions.
- Intel [Threading Efficiency View](https://www.intel.com/content/www/us/en/docs/vtune-profiler/user-guide/2026-0/threading-efficiency-view.html): wait, spin/overhead, transitions and preemption wait are separate diagnostic categories, with possible wait/spin overlap by collection mode.
- The pinned llama.cpp implementer's [tile-DAG discussion #27331](https://github.com/ggml-org/llama.cpp/discussions/27331) reports its own traced M2/dense-Qwen experiment and states its largest single gain was removing a scheduler `usleep` oversleep. This is a reason to observe spin/park/wake separately, not a portable speed claim or a mechanism proven for Strata.

## Minimum record per phase batch

Keep enough identity to join CPU counters to the model's actual work: root request ordinal (the four fresh 32K requests in the run), output/speculation window sequence within that request, layer id, batch `b0/nb` (each pool batch is at most 96 experts), `n_tok`, worker count/host-participation setting, phase (GU or Down), exact per-layer GU/Down format, and each job's `nt` plus selected native dispatch. Record logical `n_jobs`, logical token total, and row total separately. Use the actual `n_tok`/window boundaries; do not infer task rows or output count from aggregate submitted bytes. `ExpertJobMulti` batches are grouped by expert and can carry different NTs; the histogram's logical expert-job count is not a task-fragment count or traffic measure.

For the five workers plus a possible host participant, the smallest useful per-phase-batch fields are:

1. **Publication and wake path:** host wall/thread-CPU time in `wait_parked` immediately before publish; `begin_batch/publish` wall/thread-CPU interval; publish wall timestamp; for each participant, epoch-observed wall timestamp, first claim wall timestamp, first-to-claim CPU delta, and whether it was already a worker, asleep in the CV path, or the host participant. Keep publish-to-observe and observe-to-claim as distinct user-level intervals.
2. **Useful phase work:** task/segment count, exact `g0/g1` row spans and the expert intersections they cover; per participant count of claimed tasks, useful rows, jobs and NT by actual dispatch; summed wall and thread-CPU deltas around native row-call segments. Do not call the thread-CPU sum “matmul time”; label it row-call CPU. The wall span around a row call includes preemption, so report it separately. Keep the host's drain contributions as its own participant.
3. **Wait and tail:** worker park-spin wall/thread-CPU deltas before sleeping; CV wait wall delta and thread-CPU delta; post-wake-to-claim; host `wait_done` wall/thread-CPU delta; host `wait_parked` wall/thread-CPU delta after the batch; batch's first task finish, last task finish, all-done return and all-parked return. This separates worker's productive row-call CPU, busy waiting, sleeping, publication, completion wait and repark tail. If a worker claims no task, preserve the zero-work participant and its wait values.
4. **Serial FF quantization:** owner-thread wall/thread-CPU interval for the existing full-vector `e,t` quantization loop between GU and Down; count experts/tokens and summarize per exact Down format and NT. This current serial time must not be folded into GU/Down worker-active totals.
5. **Expert-ready lead proxy:** on GU only, timestamp each completed `(task, expert)` contiguous row intersection after its row call; after the phase, compute per expert `GU_ready = max(finish of every task intersection covering its FF rows)` and `GU_batch_done = last GU task completion`. Retain only the lead `GU_batch_done - GU_ready`, grouped by layer format/NT/window size, plus counters and bounded distributions, not the per-fragment event list. In the existing six-task flattened layout a task can cross expert boundaries, and one expert can intersect multiple tasks; using only the task's own final completion is wrong if that task covered several experts or if other tasks wrote this expert's rows. The lead is a potential same-batch scheduling window, not measured idle time or a predicted saving: other work may keep workers busy, quantization has its own cost, and a DAG would contend with remaining GU work.

Preallocate fixed per-batch scratch for at most `nb<=96` experts and the actual `mtasks` intersections; each task/expert pair is written by its unique claimed task. Merge after the existing global join on the caller. Do not write rows or timestamps from worker threads into a dynamically growing vector or shared file. Leave the existing math, task ownership, `--pool-tasks 6`, host participation, worker placement, dispatch, and request state unchanged while collecting baseline telemetry.

## Window and join discipline

Reset a monotonically increasing pool-window sequence at each request boundary. A window record needs the source `n_tok`, number of expert jobs, batch index and model layer; if the serving call does not expose generated-token/speculation identity at the pool call site, record `window_seq` and join it later to that request's producer callback order. Do not claim exact output-token attribution without such a source join. Keep the four requests separate. Do not sum the per-layer/per-window wall times into decode latency: CPU work overlaps GPU execution and existing phase counters are nested. Continue to report the whole request wall/decode interval and math/state gates as separate outer measurements.

Collect all work participants, including the host if `host_works_` is true. The host can claim tasks and perform drain work; counting only the five worker threads understates productive work and overstates worker-tail time. Keep worker identity stable within the process, and record whether each participant was pinned. Separate `wait_done` from `wait_parked`; the first ends when task completion is visible, while the second includes workers returning to the park boundary. Treat the final repark as current scheduler behavior, not as required per-expert dataflow.

## Bounded aggregation, overhead control and retention

This is a targeted diagnosis of cross-stage expert readiness, not a long-form thread timeline. Do not retain every row task/fragment event by default. For each request/output-window/layer/phase, merge all internal `b0` expert batches into fixed summaries (sum/count/min/max plus compact logarithmic buckets for wait, row-call CPU/wall, first-claim and final-tail durations). Keep the internal batch count and per-format/NT/job counters so unlike work is not silently combined. For expert-ready lead, retain count/sum/max and a bounded histogram keyed by request/layer format/NT/window size. The key must include the request and output/speculation window; keep the decode output-window sequence separate from prompt prefill. Preserve a bounded exception summary only if a queue stall or missing participant explains an unresolved mechanism. Do not emit token IDs, input contents, output tensors, model/session bytes or unrelated API traces in these rows.

Proposed cap: one telemetry summary at **24 MiB**, including identity/environment/command/hash/clock-resolution metadata and aggregate bins. The fixed logical key space is at most 4 requests × 64 generated output windows × 48 layers × 2 phases; each phase summary merges the pool’s internal expert batches rather than writing one event per task or batch. Store each row in a fixed binary record no larger than 512 bytes: six worker summaries plus an optional host summary, fixed counters, and at most 16 logarithmic bucket counters; add a separate fixed-size expert-ready lead histogram by layer/NT/window. This gives a concrete upper bound below 24 MiB for 24,576 phase rows plus those histograms and a bounded header. Record actual encoded bytes and enforce the cap before writing. Compute and verify the final schema size before collection. If more than 64 output windows occur, if the source cannot separate them from prefill, or if an encoded record exceeds the precomputed limit, fail the telemetry completeness gate instead of truncating or mixing work. Keep no raw profiler timeline and no per-fragment full trace. The named consumer is the R56 expert-local DAG go/no-go; owner is root; review after the current v6 4×32K run and telemetry question closes. Then retain only the compact aggregate summary plus its identity/source/command/environment/clock-resolution metadata, retiring any temporary raw event file with a verified path/hash/reason manifest if one was needed for debugging.

Clock calls and counters can change a short task's scheduling. First count the maximum instrumentation sites: one timing envelope per `run_phase`/wait, per worker wake/first claim, and per existing task/expert row intersection—not per row. Measure observer overhead in a paired same-binary control after the current owner run closes: identical fixed requests/settings and task policy, telemetry disabled versus enabled, report added thread-CPU and whole-window wall time with the same correctness gates. A back-to-back clock-call micro-test alone is not enough because it misses cache-line/counter contention. Keep only one compact overhead comparison and do not use profiled throughput as a speed result. If the added telemetry shifts task/wait distributions materially, simplify or stop before using the data to judge the DAG.

## Interpretation and decision thresholds

- High thread-CPU around row calls with short completion skew suggests participants spent CPU in the row-call path; it does not identify multiply-only time or disprove memory stalls.
- High thread-CPU during explicitly labeled spin, with a low CV-wait interval, means CPU was consumed in the current busy-wait path; high CV wall with low thread-CPU means the thread was suspended or waiting to reacquire the mutex. Neither alone says that the phase is on the physical decode critical path.
- A large host `wait_done` with early expert-ready leads may show opportunity for an expert-local pipeline, but only if useful work was not already consumed by other ready GU tasks and quantizer reentrancy/queue costs are separately resolved. Large `wait_parked`/repark time is a pool boundary cost but does not itself prove a per-expert DAG wins.
- A long publish-to-first-claim is a user-level delay; without kernel scheduler evidence it cannot be named OS wake latency. A large wall-minus-threadCPU gap around a row call means non-running time in that interval, not a specific scheduler cause.
- Keep external phase time, histogram job exposure, worker activity/wait distributions, and request-level decode wall separate. No phase addition, submitted-byte-to-traffic conversion, GPU-overlap inference, or unmeasured speed prediction is permitted.

If the R56 expert-ready lead and worker wait/tail histograms are small relative to row-call/quantization work, the fixed-phase path remains the correct stopping point. Only substantial repeated lead plus a material host/worker barrier tail can justify asking for a bounded prototype; the telemetry itself does not authorize source implementation. Do not retry local VTune, PMU, Yama, gprofng, ptrace, or profiler collection: R13/R14/R16 recorded the relevant access/ownership limitations, and this contract uses only explicitly labeled in-process clocks and counters.
