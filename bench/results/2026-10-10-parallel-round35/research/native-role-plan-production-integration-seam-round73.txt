## Existing production paths

`FileExpertSource::open_gguf` first calls `check_experts_gguf` (`sycl/src/core/expert_source.cpp:715-718`), then separately opens/maps each role shard and constructs `role_ptr_`, `role_bytes_`, and `role_file_` (`720-789`). The map loop deduplicates by resolved path within this source; it rechecks span-vs-map size after the checker. `check_experts_gguf` separately creates a `GgufFile` per path and validates offset table presence, tensor name/type/3-D shape/payload byte count, exact absolute offset, and payload bounds (`3096-3147`). This is a check-then-reopen sequence; production mappings are the mappings later used for reads.

For that source, mapped `role_ptr_` slices feed `copy_from_files`; if direct I/O is enabled, `read_direct` is tried first and failure falls back to those mapped slices (`~795-810`, `1137+`). Blob assembly is cached in stage buffers, with asynchronous prefetch/warm paths reserving/filling/publishing buffers (`claim_stage`, `fill_stage`, `prefetch`, `warm` around `~810-1000`, `~1417`). Mapping lifetime is owned by `FileExpertSource` and survives callers borrowing staged blob pointers; `close()` is the teardown boundary (`594+`). The GGUF role path is therefore not a safe place to swap in short-lived pointers from a validator.

`load_experts_gguf` is a separate arena loader, whose comment states that the caller checks spans first (`3153-3157`). It re-resolves paths and reads chunks from files; on Windows optional no-buffering uses aligned buffers and scattering (`3160+`). Keep this loader's ready-layer synchronization and unbuffered behavior intact. The likely `open`/load callers should continue to preserve their existing caller-specific error prefixes and error propagation.

`GgufExpertSource::open` (stream-experts) only checks native layout, offset-vector length, and nonzero offsets, then opens/deduplicates role shard file descriptors (`sycl/src/core/gguf_expert_source.cpp:29-55,60-74`). `blob`/`read_into` issue `pread` from those fds using offset plus expert stride (`76-113,184-203`); currently this open path does not check tensor metadata or file extent before reads. It owns a 512-entry blob ring and may retain a pinned host mirror; `close` frees mirror and closes fds (`21-27`). Validate before exposing this source, but keep its fd/ring/mirror ownership independent.

## Recommended smallest safe seam

Use `NativeRolePlan` first as the authoritative metadata/extent validator, not as a production data source. Its current public interface owns GGUF mappings until close and only exposes extent metadata plus `copy_blob`; it does not expose a caller's existing mappings/fds, a borrowed role span, nor direct-I/O handles. Replacing `FileExpertSource` reads with `copy_blob` while retaining its own mappings would map every shard twice; retaining only the plan mappings would remove the current direct-I/O path and alter pointer/lifetime and staging semantics. Neither is a minimal behavior-preserving integration.

The smallest low-risk first change is to invoke the plan validator in the `FileExpertSource::open_gguf` validation seam and in `GgufExpertSource::open`, then close the temporary plan after a successful check and continue the existing map/fd setup. Preserve the `FileExpertSource:` and `--stream-experts:` error context at those callsites, and preserve the old checker diagnostic contract for default callers (either keep `check_experts_gguf` as a compatibility wrapper translating the shared plan result, or first verify exact diagnostic parity before replacing its body). This removes duplicate validation logic while leaving existing mapping count, direct I/O, prefetch/warm, ring and mirror lifetimes unchanged. It does not eliminate TOCTOU between validation and later mapping/open; the existing bounds recheck protects FileExpertSource's mapped span, but stream pread still needs a file-size/checked-extent defense. State that limitation plainly.

For a stronger single-open design later, extend the shared layer with a non-owning validation operation over already-open file identity/size and verified tensor metadata, or make plan accept/borrow the production-owned maps/fds with explicit lifetime ownership. Do not bolt the current owning `NativeRolePlan` beside the FileExpertSource mappings and call that single mapping. If using the owning plan for streaming, either keep it as the retained source and implement buffered reads through it, or transfer/reuse its file descriptors; the current API cannot do this. Any design change must settle who holds the plan through pending prefetch/device-copy borrowers before making close/reopen possible.
