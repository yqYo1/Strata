# Native ExpertPool host-affinity construction-order audit (round 84)

## Question and result

Does production construct or reconstruct `ExpertPool` after Strata itself narrows the calling thread to the host CPU, as the quiet calibration fixture did? The source audit finds no such production ordering on the pinned baseline, integrated, frozen-route, or current-role source trees. In the engine, the pool is constructed first; `SessionLoopScratch::init` pins the main thread later. Its affinity is per-thread, so this later main-thread pin does not rewrite already-running worker masks. The calibration behavior is therefore a fixture construction-order defect, not evidence of an engine/server construction defect.

This is a code-path conclusion, not a claim that every deployment has a broad CPU mask. A service manager, container cpuset, taskset, or parent can constrain the process before `main`; pool topology is designed to use the calling thread's allowed set in that environment. No runtime test was performed for this audit.

## Production construction and ownership

- In baseline 869, `src/program/generate.cpp:2871` constructs the one `ExpertPool` at the top-level engine setup. The `Drive`/`ExpertDispatch` stores its address later (`:3386`); the expert-source dispatch consumes that pointer to call pool work (`src/core/expert_source.cpp:1731+`, with `d.pool->run_split` at `:1848`). It does not construct a pool.
- In integrated 23268953, frozen route 66aaec3a, and current role 59323e66, `generate.cpp:4254-4255` is the sole `ExpertPool` construction in `src/`, `include/`, and `serve/` source search. The pool is then assigned to the persistent `drive.d.pool` (`:4952`). `ExpertSource` setup and lazy file/cache staging may start or use their own I/O mechanisms, but do not create or reconstruct `ExpertPool`.
- The pool constructor initializes `topo_` by calling `detect_cpu_topology(true, affinity)` before it starts workers (`pool.cpp:439-440`, `:460-466`). On Linux, topology reads the calling thread’s currently allowed set (`pool.cpp:233-237` in current-role; the baseline uses `sched_getaffinity(0, ...)` at `:164-172`). It excludes the reserved host core when forming worker cores. Default worker count follows the topology; explicit worker counts beyond the listed cores receive `core=-1` and are not pinned to a selected CPU. Each normal worker is pinned to its planned core inside its own thread.
- Production sets `--host-core` as a topology preference before constructing the pool (`generate.cpp:1961-1966` in current-role); this changes the chosen reserved core and does not call `pin_current_thread` on the main thread.
- The actual host pin occurs later, in `SessionLoopScratch::init` (`session.cpp:541-559` in current-role; `:667-678` in baseline 869). `generate.cpp` constructs that scratch and calls `init` at `:5536-5545`, well after pool construction and dispatch wiring. The scratch owns the saved affinity and restores it in `free` (`session.cpp:562-571`, baseline `:681-689`). It is initialized once per engine process, not per token or per request.
- The `--serve` engine remains resident while it reads request lines and serves them through its request loop. `serve/server.py` launches one `strata --serve` subprocess (`:572-580`, `:647-652`); if that engine dies, the next start is a new process with a newly constructed pool. In-process request/session/checkpoint/reload work does not reconstruct `ExpertPool`. Thus the later host pin persists for that process's main thread, but cannot retroactively narrow worker masks.

## Why the fixture differs

The calibration evidence supplied with this task reports that fixture setup first pins its main thread to host CPU 0 and only then constructs a pool with five explicit workers. On Linux, `sched_getaffinity(0, ...)` asks for the calling thread's mask. `pthread_create` gives a new thread a copy of its creator's CPU-affinity mask; see the Linux man-pages for [`sched_getaffinity(2)`](https://man7.org/linux/man-pages/man2/sched_setaffinity.2.html) and [`pthread_create(3)`](https://www.man7.org/linux/man-pages/man3/pthread_create.3.html). With only CPU 0 visible to topology, the explicit workers have no planned worker-core entries and use `core=-1`; they inherit the narrowed single-CPU mask. That source ordering matches the reported `Cpus_allowed_list: 0` for the main thread and all five workers.

Production does the reverse: worker topology and thread creation happen while the main thread still has its process-allowed mask; only afterward is the main thread pinned to the reserved host core. The distinction is the construction order, not a different per-request expert-source route. An externally imposed one-CPU process mask remains a real deployment constraint and would appropriately be observed by topology detection.

The calibration timing interpretation remains ineligible per the supplied root evidence: its pool medians cannot represent a five-worker placement. This report makes no change to correctness receipts, no policy recommendation, and no speed claim.

## Evidence and limits

Read-only source inspection covered the five hash-pinned files listed above and pool-affinity helper headers/call sites. The server lifecycle and Linux affinity semantics were checked against primary Linux man-pages. The root-provided quiet-profile placement artifact is `B/native-service-calibration-22-20-nt1-timing-tasks6-batch6-r1/uninstrumented-rounds/stdout.csv` and the corresponding other profiles; this audit did not reread or alter those run artifacts. It did not execute the engine, a test, or a runtime command. The result establishes the application source ordering; it does not prove the process-wide affinity granted by any particular service manager or container.
