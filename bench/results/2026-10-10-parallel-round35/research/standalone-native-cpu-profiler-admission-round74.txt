# Standalone actual-weight CPU profiler admission (round 74)

## Decision

The forthcoming `ExpertPool` harness is a much cleaner process boundary for a profiler than the engine: no GPU work, no engine callback, and no GDB-owned inferior. This removes GPU overlap and the specific conflict of a second tracer trying to seize a GDB-controlled process. It does not clear the host's recorded profiler restrictions. VTune's software collector already failed its own restricted-ptrace preflight at `ptrace_scope=1`; launching a separate child without GDB does not remove that policy. Hardware PMU collection remains a separate blocked path under the recorded `perf_event_paranoid=4`/no privilege conditions. gprofng's launched-target clock sampler has a further independent observed failure: its collector returned `cerror 9: itimer could not be set`, including under a native CPU-only target, with no profile frames.

One distinct, bounded profiler-admission candidate is **gperftools CPU Profiler using its default `ITIMER_PROF` path**, because it uses `setitimer` and process-directed `SIGPROF`, rather than VTune's ptrace-based user-mode collector or gprofng 2.42's failing `timer_create(CLOCK_THREAD_CPUTIME_ID, SIGEV_THREAD_ID)` initialization. This is a testable alternate timer mechanism, not an expected success or a workaround already validated on this host. Do not install it or change the system. If the existing library/toolchain is unavailable, stop with “no profiler admitted.” Do not fall back to PMU, permissions, sysctls, services, or another profiler in this round.

If admitted, make one diagnostic run of the **full actual-weight CPU harness** in its own child process after the separate uninstrumented 25-round calibration has closed. Use the same harness executable and workload; keep `LD_PRELOAD`/profiler controls out of calibration. Gate the profiler with gperftools' configured control signal: wait until role loading, correctness setup and warmup are complete, enable immediately before the already-defined timed pool-call window, disable immediately afterward, then let the normal harness finish. Set a conservative fixed rate (e.g. 100 samples/s), retain the profile only while answering a named function-hotspot question, and require a nonempty profile, resolved production function symbols, correctness gates, normal exit, and no leaked child. The profile is diagnostic only: its elapsed times and throughput are excluded from calibration, and no speedup/slowdown is inferred from samples. Gperftools' process-wide `ITIMER_PROF` does not provide per-thread CPU timers; signal delivery may select one eligible worker, so interpret output only as coarse statistical function attribution, not per-worker balance or complete call-path truth. If stack quality or production symbol attribution is poor, reject the result.

This is intentionally the only proposed new admission experiment. A harmless protocol or thin GGUF fixture is not CPU ExpertPool evidence. The actual-weight full harness is the only target for the diagnostic profile; normal uninstrumented calibration remains its own measurement arm.

## Evidence from prior work

The VTune R13/R14 design distinguished software user-mode sampling from PMU sampling and correctly rejected attachment to the GDB-controlled engine: Linux has one tracer per tracee, and the software collector may use ptrace. R16 then recorded an actual VTune child-launch smoke failure before target protocol: collector exit 1 after 1.655 s, `ptrace_scope=1`, target steps zero. This is stronger than the earlier design hypothesis: removing GDB avoids the competing-tracer problem, but cannot be assumed to satisfy VTune's own scope preflight. VTune's documentation describes its user-mode collector as embedding an agent and using per-thread timer signals (usually SIGPROF), with higher overhead; that does not make it a PMU-free path that bypasses the recorded ptrace rejection.

The R16 gprofng route was also only a candidate at first. R18's harmless CPU/protocol smoke reached READY/DONE and gprofng exited zero, yet the experiment had `cerror 9`, no positive `ptimer` profile schema and a zero-byte frame file. R18 traced that installed 2.42 path to `timer_create(CLOCK_THREAD_CPUTIME_ID, SIGEV_THREAD_ID | SIGEV_SIGNAL)` / `timer_settime`; the standard error does not identify which operation or errno failed. R23's native C target then reproduced cerror 9 with protocol and process lifecycle otherwise clean, so the problem is not specific to Python, model loading, GDB, or GPU overlap. R23 also found that the installed collector lacks the diagnostic strings needed for a reliable `SP_COLLECTOR_DEBUG=4` runtime toggle. Preserve all failed receipts as failures; this review does not replace or reinterpret them.

## One candidate's scope and limits

The gperftools user guide documents `LD_PRELOAD` for an existing dynamically linked executable, `CPUPROFILE` output, `CPUPROFILESIGNAL` start/stop control, and default 100 Hz sampling. Its implementation source distinguishes the default `ITIMER_PROF`/SIGPROF path from optional per-thread timers; do **not** set `CPUPROFILE_PER_THREAD_TIMERS`, because that would reintroduce the POSIX thread-timer mechanism implicated in gprofng's failure. Keep `CPUPROFILE_REALTIME` unset: wall-clock `ITIMER_REAL` has different semantics and can interact with alarm handling. Before the actual-weight diagnostic, verify by static identity that the intended signal is unused by the harness and dependencies, and that the exact installed library is already available. The parent owns runtime admission and process control; this review performed neither.

`ITIMER_PROF` is not identical to gprofng's per-thread CPU sampler: Linux defines it over total process user+system CPU time, with SIGPROF delivered to the process. Consequently the proposed result can indicate active CPU function hot spots across the isolated pool workload, but it cannot recover per-worker sample rates, PMU events, cycles, cache/bandwidth causes, blocked wait time, GPU overlap, or production decode critical path. Sampling perturbs scheduling and the signal handler itself; there is no time or speed conclusion from that run. It should not be used to alter the uninstrumented calibration or excuse any correctness mismatch.

## Evidence versus inference

**Recorded evidence:** R13/R14/R16 VTune reports show the local 2026.4 software-hotspots scope failure and no target execution; local R16/R18/R23 gprofng reports and receipts show no usable clock profile and cerror 9, including for a native CPU-only smoke; those reports preserve recorded local restrictions (`ptrace_scope=1`, `perf_event_paranoid=4`) and no root/privilege change. The standalone helper receipt is host-only synthetic validation, not actual weights. External documentation confirms VTune's software agent/signal design, Linux timer clock and process-vs-thread timer semantics, Linux perf access control, and gperftools' configurable CPU profiler signals/frequency/runtime loading.

**Inference:** the isolated harness removes GDB ownership conflict and GPU co-scheduling from a future profile, but it does not change VTune's Yama check, PMU access policy, or gprofng's `timer_create` failure. Because gperftools' ordinary profile uses a distinct `ITIMER_PROF` route, it is a reasonable single new admission candidate. No source reviewed proves this host permits that timer path, that gperftools is installed, that its signal can safely gate the exact harness window, or that stacks resolve adequately. Admission remains conditional on one root-owned run and those gates.
