## Finding

A bounded WY kernel can remove the **within-chunk** token-by-token state chain in principle, while preserving one state matrix per value head and carrying it chunk to chunk. But a safe, attractive SYCL schedule is not established. The one-work-group-per-value-head/output-column-tile mapping is the most concrete candidate: keep the existing 128-thread, four-32-column tile (192 groups total for 48 heads), loop over the internal C-sized chunks of the current prefill batch, build/solve the chunk-local triangular system, apply that chunk's state transfer to the resident FP32 state tile, emit its outputs, and carry the updated state into the next internal chunk. This avoids all-context or all-batch `[chunk,head,128,128]` state. It still serializes chunk handoffs, adds KKT/triangular-solve work, duplicates key-only KKT work across the three interleaved value heads and potentially across four output-column blocks, and may need global scratch or more work-items to distribute the triangular solve. No implementation from the inspected sources proves that this schedule has net benefit or acceptable per-thread resources.

## Current active work and bounded chunk count

SYCL geometry is `S=128`, `HK=16`, `HV=48`, `C=10240`, with 36 GDN layers in the 48-layer model. The current default recurrence is `gdn_rec_cols_pipe_kernel` (`STRATA_GDN_PIPELINE` defaults on, `STRATA_GDN_KEYHEAD` defaults off); its grid has `HV * (S/32) = 192` work-groups and each group is 128 work-items (`RG=4, CB=32`). Each group owns one value head and 32 output columns, keeps 32 state rows per lane in registers, and advances one token at a time with shared Q/K, four partial dot products, state update and output reduction. Its arithmetic order is stated to match `gdn_rec_cols_kernel`; R36 audited deterministic ownership but not whole-model parity.

The request's 262144 physical context is **not** passed as one GDN T by default. `generate.cpp` defaults `o.prefill_chunk=2048` (the user's/auto-selected value may differ); `Prefill::init` allocates buffers for that chunk and `run_impl` processes `n` in chunks up to `m.T` (`prefill.cpp:1115, 2914–2962`). Thus, at the source default and a 262144-token prompt, there are 128 outer prompt batches; a WY C=64 kernel batch would contain 32 consecutive WY blocks and the entire prompt would have 4096 state handoffs per GDN layer. For C=32,16,8 the corresponding internal blocks per outer batch are 64,128,256, and full-prompt handoffs are 8192,16384,32768. A shorter final outer batch and/or final WY block needs live-token masking and must still write exact state after its last real token. This is a source-derived default scenario, not a claim about a particular current process configuration.

## Work and synchronization comparison

Existing recurrence performs the exact sequential rank-one GDN update once per token. In the SYCL body there are five explicit cross-work-item barriers around the shared-Q/K and reduction/output phases (the source has the barrier before publishing shared data and barriers around `red` reuse); count carefully for the selected compiled variant rather than assuming barriers fuse. So C=64 removes neither computation nor state handoff between chunks, but replaces 64 state-dependent token steps (and roughly 4 barriers each) with chunk-local KKT/WY construction, a triangular solve and one chunk-level state handoff. C=16 replaces 16 such steps. The FLA `chunk_fwd.py` implementation forms ten lower-triangular 16x16 blocks for a 64-token chunk, solves diagonal blocks and merges them; this is not a zero-cost/logarithmic black box. Its chunkwise method reduces serial dependence depth but adds dense KKT and solve work. The Prysmlabs article describes a different chunk-8 repeated-squaring strategy; no source for its particular GDN kernel was found in the linked public Alloy source listing, so do not count its stages as an implementable Strata schedule.

The recurrence arithmetic has a plausible work tradeoff: serial form is O(C*S^2) per value head. WY intra-chunk work includes KKT O(C^2*S), a triangular solve (up to O(C^3)), state transfer/update O(C*S^2), and output work. C is at most S/2 here; no dominant-work or timing conclusion follows without a concrete fused mapping. KKT over key heads can be shared mathematically across each modulo-mapped set of three value heads, but each value head has its own gate/beta and therefore its own gated triangular system. FLA's native head mapping is contiguous groups of three (`value_head // 3`), unlike Strata's modulo groups (`value_head % 16`); maintain R82's exact permutation/custom-map requirement, and do not interpret grouping as work-free reuse.

## Bounded storage estimate and the physical-context peak

These are byte arithmetic, not allocation/runtime observations. For one active full GDN batch T=2048, Strata's current compact GDN arrays are QKV 80 MiB, z 48 MiB, alpha/beta 0.75 MiB, gate 0.375 MiB, beta 0.375 MiB and post-convolution h 80 MiB, total 209.5 MiB. Current compact output reuses QKV allocation; noncompact output adds 72 MiB, total 281.5 MiB. The main prefill arena is sized to the maximum of GDN/QSA/MoE scratch, so this is the GDN component, not the whole arena. At a hypothetical single T=262144 allocation these GDN arrays would be 26.19 GiB compact (35.19 GiB noncompact), before state/other arena. The ordinary 262144 path instead recycles the 2048-token arena 128 times (assuming the source default and no auto-chunk change). The separate persistent 36-layer GDN recurrent+conv session state is 117,669,888 B (112.2 MiB), zeroed on fresh sequence and retained across outer batches.

For a bounded single WY block, global staging for all 48 value heads would require W+U `[48,C,128]` FP32, A `[48,C,C]` FP32, plus the per-head 3 MiB FP32 state tile if state is staged rather than kept distributed. At C=8/16/32/64 those one-block workspace totals (W+U+A+one state tile) are about 3.47/3.80/4.69/6.75 MiB. These bounded figures can coexist with the existing 209.5 MiB GDN scratch at outer T=2048 in byte arithmetic, but **do not include** allocator alignment, any second solver buffer, key-head duplication, queue/run overhead, QSA/MoE arena max, or an extra ping-pong tile. At C64, FLA's all-context h states alone would be 12 GiB, W+U 12 GiB and A 3 GiB (27 GiB, before v_new/output); do not adopt that all-chunk schedule for a 10 GiB-class B570.

A likely single-kernel schedule loops 32 C=64 chunks inside each T=2048 launch, holding the state partition in registers and using one C-bounded A tile plus per-chunk W/U scratch. This keeps the fixed launch count near the existing per-layer/per-batch dispatch, and each local WY block is parallel across its tokens/heads/columns. However, a work-group has no cross-group barrier: the triangular solve and each state transfer must be completed within its owning group, or split across kernels with explicit global-memory handoff. If split, two or three kernels per WY chunk would mean up to 8,192–12,288 extra kernel submissions per GDN layer for a 262144 prompt at C64; at C16 that becomes 32,768–49,152. These counts are avoidable only by doing several dependent chunks in one kernel, or by a parallel-prefix scheme that again needs chunk summaries/storage and more complicated state propagation.

## Work-group / SLM feasibility and hardware fact boundary

Existing 128 work-items (4x32) are below the 1024 maximum work-group size in Intel's Xe2-HPG architecture table for the documented B580 and below the general SYCL non-custom-device minimum limit. This proves only the existing group shape is conventional; it does not establish the maximum for a compiled B570 kernel. Intel's official table describes B580 (Xe2-HPG), with 128 KiB SLM per Xe-core and max SLM per work-group 128 KiB, 1024 work-items and subgroups 16/32. Intel's B570 product page confirms Xe2 and 18 Xe-cores, but the B580 row is not a B570 per-kernel query. Treat those B580 values as architectural context, not measured B570 capabilities. [Intel Xe GPU architecture table](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2025-2/intel-xe-gpu-architecture.html), [Intel B570 specs](https://www.intel.com/content/www/us/en/products/sku/241676/intel-arc-b570-graphics/specifications.html).

The SYCL 2020 device properties `local_mem_size`, `max_work_group_size`, `max_work_item_sizes`, subgroup sizes and kernel-specific work-group limits are the right documented queries. The spec's local memory minimum is 32 KiB for non-custom devices and its maximum group size is a device/kernel upper bound, not a performance recommendation. Intel's optimization guide says usable SLM is device-dependent and demonstrates querying it; no such query was run here. [SYCL 2020 revision 12 device information descriptors](https://registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html?from=20423&from_column=20423), [Intel SLM guide](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2024-1/slm.html).

A conservative, illustrative one-head work-group tile that loads K `[C,128]` and holds two `[C,C]` matrices for KKT/solve needs approximately 4.5/10/24/64 KiB at C=8/16/32/64, before gate/beta, q/v, reductions, alignment or another solver buffer. This is a design estimate; the actual FLA fused kernel uses blocked register math and need not materialize these exact matrices in SLM. C64 lands at a 64 KiB edge if a second CxC temporary is needed, and an extra `[C,128]` array would add 32 KiB. C32 has materially more headroom; C16/C8 reduce the local matrix but increase serial chunk loops. If three interleaved value heads are computed together, per-head A/solve storage multiplies; if four output-column groups each solve it, KKT/solve repeats four times. Conversely, one WG doing all 128 columns per head would raise the state tile to 128 FP32 values per work-item (512 B, before all other live values), likely increasing register pressure. Intel's architecture table reports 128 GRFs/thread for regular mode and 256 in large-register mode for B580, but there is no B570 compiled-kernel register/spill report here. None of these designs is cleared on resources.

The SYCL device and kernel queries that a later design review would need are `local_mem_size`, `max_work_group_size`, `max_work_item_sizes<3>`, subgroup sizes, and for the compiled kernel, kernel-specific `work_group_size`, `private_mem_size`, and `preferred_work_group_size_multiple`; query results, compile resource reports and a truthful local-memory allocation are required before describing a shape as viable on this B570. No runtime/device query occurred in R83.

## Candidate decision and next discriminator

A **single-work-group-per-value-head/output-column-tile, C-bounded in-kernel loop** is the best storage-bounded candidate, with C=16 or 32 the plausible first mathematical shapes to inspect because their illustrative A/K tiles have more SLM headroom than C64. It would reduce 16/32 serial state steps per WY block to one chunk carry, but it introduces KKT and triangular solve, likely repeated across the current four column tiles and three modulo value-head siblings. We cannot conclude that meaningful wall time is removed. A two-kernel-per-chunk design has clean parallelism but intolerable-looking submission counts unless a command graph or kernel loop absorbs those handoffs; do not assume graphs are admissible/available in the current ordinary path.

Before any GPU implementation assignment, root should first settle the exact scalar WY equations and head permutation with a separately authorized CPU equation oracle (per root instruction), then require a source-level single-kernel schedule with per-work-group memory/register accounting and output/state storage. It must use the existing in-order compute queue and session-owned state, preserve copy-offload disable/direct-submission off, preserve Q/KV/MoE queue ownership and request reset, and pass existing serial/repeat/all-state/logit/ID/MTP gates unchanged. No new tolerance or adoption decision is supplied here.

Prior decisions read: R33 ordinal/state layout and fresh reset; R35 says sampled residual rows do not prove state equality and requires whole-state/repeat gates; R36 default pipeline ownership and no-race barrier audit, not whole-model determinism; R81 proposes WY conditionally; R82 establishes the algebraic fit, FLA head-layout mismatch, full-sequence storage rejection and exact output/state gates.
