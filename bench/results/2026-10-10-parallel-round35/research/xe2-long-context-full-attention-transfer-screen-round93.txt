# Xe2 long-context full-attention prefill transfer screen (round 93)

Date: 2026-10-10. Read-only source/report and public-source review. No build, import, test, device/runtime/model execution, profiling, Git operation, cleanup, or implementation. Strata source reference: frozen `diag-sycl-cache-route-pairs-v0141-20261010`, HEAD `66aaec3a66ad9ed12e6d042cffe743c47e364432`; research registry v47 SHA-256 `1aaa7ccf01cb74d3c8441a9467cb7136a8e583b3d9ab8c8ac3767dfc564ef839`; evidence storage HEAD `3acff3b3`. Scope is Xe2 long-context full-attention/QSA prefill and streamed K/V memory movement/batching. GDN, CPU tuning, decode, quantization/precision/math changes, and active quad source are excluded.

## Disposition

No new exact, plausible Strata candidate emerged from the current llama.cpp, OpenVINO, IPEX-LLM/LLM-scaler, and individual implementer/blog material screened. The concrete public techniques fall into three buckets: attention sparsification (changes which keys participate), KV representation/quantization changes, or converting and caching expanded KV values to avoid a format-conversion cost that Strata does not have in the same form. The remaining exact-transfer ideas—keeping one active layer's complete KV staging plane alive across chunks, staging/prefetch overlap, and batching/tiling the QSA attention work—are already represented in the Strata reports and v47 candidate inventory. This is a novelty screen, not evidence that the existing designs are fast or complete.

## Frozen Strata constraints

The static code reference is the frozen prefill implementation and its QSA kernels in `sycl/src/prefill/prefill.cpp` and the related prefill kernel sources at the reference commit above. It already has chunked prompt processing, a shared full-context QSA stage, selected-ID attention batches, local KV tile staging in the attention kernel, host-authoritative streamed KV, and per-layer scheduling work. The long-context reports explain the important lifetimes: at 262144 cells, one full QSA int8 KV plane is 264 MiB; 12 host KV backings are 3.09375 GiB; the 32768-cell resident pools are 396 MiB total; QSA indexer arrays are about 384 MiB total; and layer-major processing needs a 10 GiB host residual plane for the four-stream hidden state. These are geometry-derived capacities, not measured peak memory or a 10 GiB device feasibility guarantee.

The existing `layer-major-streamed-kv-round3.txt` proposal already describes serial reuse of the single full-context QSA stage across chunks and layers, including stage owner/generation, valid prefix, event retirement, resume-prefix copy, and preserving host KV/indexer state. `qsa-long-context-kernel-mechanisms-round13.txt` and `long-prefill-qsa-optimization-round25.txt` cover exact score/key-tile reuse, radix top-k selection, selected-K/V tile-union reuse across neighboring queries, and selection/attention overlap diagnostics. `prefill-transfer-reuse-external-new-candidates-round81.txt`, R76 and R80 cover transfers, queue dependencies, and overlap. These should not be restated as new recommendations.

## External source screen

- OpenVINO GenAI's sparse-attention-prefill note describes tri-shape/XAttention methods that identify and omit KV blocks during early prefill, then use dense attention for a final tail. This is an attention-computation approximation/selection policy, not an exact memory-transfer schedule for Strata's QSA top-k semantics: [OpenVINO sparse attention prefill](https://github.com/openvinotoolkit/openvino.genai/blob/master/site/docs/concepts/optimization-techniques/sparse-attention-prefill.md). Excluded under the exact-math and unchanged-selection requirement. OpenVINO's KV-cache eviction guidance likewise concerns cache capacity and does not establish a new exact prefill transfer opportunity; prefill context cannot simply be evicted while later queries still require it.
- OpenVINO's Intel GPU blog on int4 KV support describes a changed cache representation and its memory/bandwidth tradeoff: [int4 KV cache support](https://github.com/openvinotoolkit/openvino/blob/master/src/plugins/intel_gpu/docs/blog/int4_kv_cache_support_in_2026_2.md). It is not transferable under unchanged Strata int8 KV semantics.
- Intel LLM-scaler issue #738 reports an FP8 KV-cache prefill penalty on a 2× B70 setup with Qwen3.8-27B-FP8, and proposes converting a whole KV chunk to temporary FP16 and reusing it across query tiles. Its reported medians show a penalty increasing from about 2% at 8K to 19% at 96K for the tested FP8 path; these are not Strata or B570 measurements: [LLM-scaler issue #738](https://github.com/intel/llm-scaler/issues/738). The conversion-cache suggestion targets costly FP8 conversion repeated for query tiles. Strata stores int8 codes and separate scales; exact integer unpacking is not the same expensive conversion, while a full-context expanded half cache would double code traffic and require roughly 512 MiB for a 262144-cell QSA plane. Therefore it is not a justified candidate without a separate exact source-level bottleneck, and no performance is projected.
- llama.cpp's SYCL backend documentation has B580 prompt-processing figures across oneAPI/compiler versions, but does not isolate long-context KV movement or show a novel exact batching/lifetime technique: [llama.cpp SYCL backend documentation](https://github.com/ggml-org/llama.cpp/blob/master/docs/backend/SYCL.md). The B580 implementation discussion and its XMX/q4 KV/weight-layout material are covered by R91 and do not establish an applicable Strata mechanism: [llama.cpp B580 discussion #29643](https://github.com/ggml-org/llama.cpp/discussions/29643).

## Result and boundary

Do not add an external candidate on this pass. The potentially useful direction from the Intel issue is only a future diagnostic question if source inspection finds repeated costly conversion in Strata's exact QSA path; the current code representation and existing tile staging do not support carrying over the FP8 result as a recommendation. Existing stage lifetime and selected-attention reuse candidates remain the relevant exact designs, with correctness, peak allocation, queue ownership, and full-prompt performance still requiring their own validation. This report makes no Strata speed estimate and does not alter any implementation or result status.
