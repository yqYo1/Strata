# Round 70 — IQ4_NL Down NT1: exact-row comparison and candidate boundary

## Finding

On the frozen source, the current Down IQ4_NL NT1 route is ggml's `vec_dot`, not Strata's AVX2 row kernel. The existing Strata AVX2 `nt=1` IQ4_NL row computes the same integer dot and fp16-scale product, but it does **not** preserve ggml's float accumulation/reduction order. It is therefore not source-level bit-equivalent to the production NT1 ggml result, and forcing it with the generic `STRATA_IQ_MT_MIN=1` is not an exactness-preserving dispatch change. A prompt can still pass numerically in many cases, but source inspection does not establish bit identity or LP/state equality.

A narrow exact-row formulation is possible: preserve the pinned ggml AVX2 pair-of-block accumulators, order, and final reduction exactly while removing only the per-row indirect `vec_dot` call. This is a candidate for exactness testing, not a performance recommendation. It largely reproduces ggml work; without actual service evidence that per-row indirect-call/setup overhead matters, the defensible present choice is **no adopted NT1 kernel change**. The prior generic two-row and GCC-object alternatives remain rejected, not revived.

## Active geometry and production selection

The actual MoE geometry is `H=2560`, `FF=640`. For IQ4_NL Down, the row dot reduces 640 values: 20 blocks of 32 values. Each IQ4_NL block is 18 bytes (2-byte fp16 `d` plus 16 nibble bytes), so the row is 360 bytes and one expert's 2,560 Down rows occupy 921,600 bytes. The active IQ3_S pack has Down type 20 in 39 layers and type 42 in 9 layers. The old distinct A+B route exposure records 46,254 Down20 NT1 jobs and 118,410,240 logical rows; R63's eligible union has 8,115 Down20 NT1 IDs. These counts prioritize a later service measurement only; they are not timings or independent holdout evidence.

`native_down_dispatch(type,nt)` in `native_expert.cpp:196-214` has a default `STRATA_IQ_MT_MIN=2` and `STRATA_NO_IQ4NL` disable. It selects `Iq4nl256` for Down type 20 only when `cpu_avx2_ok()`, `nt >= mt_min`, and IQ4NL is not disabled; otherwise it returns `Ggml`. Thus NT1 defaults to ggml. `native_down_rows` (`:217+`) calls the format trait's `vec_dot` once per output row and token in the ggml branch; the ggml CPU trait table maps `GGML_TYPE_IQ4_NL` to `ggml_vec_dot_iq4_nl_q8_0` and Q8_0 activation (`ggml-cpu.c:380-383`).

`STRATA_IQ_MT_MIN=1` would route all eligible NT1 IQ4_NL Down calls into the already-existing AVX2 row routine, but it is a broad GU/Down threshold knob and was already exercised as a dispatch profile in the wrapper receipt. It is not proof that this path is exact against ggml, and this report does not recommend repeating it as a new optimization. `STRATA_NO_IQ4NL` selects the current ggml fallback; it is not an optimization candidate.

The AVX2 files are compiled with `-mavx2 -mfma -mf16c`; `cpu_avx2_ok()` verifies AVX, OSXSAVE/YMM state and AVX2 before dispatch. The optional AVX-VNNI copy is compile-time gated and reached only when `cpu_avxvnni_ok()` is true; the Ryzen 5 5600X host recorded in prior receipts has AVX2/FMA/F16C and no AVX-VNNI, so its applicable Strata variant would be the plain AVX2 one. A machine-specific flag or old host receipt is not a substitute for recording the actual build/CPU for any future service arm.

## Arithmetic comparison: same packed dot, different float sequence

Both implementations use the same 16-entry `kvalues_iq4nl` table (`-127,-104,-83,-65,-49,-35,-22,-10,1,13,25,38,53,69,89,113`), unpack low/high nibbles in the same 0–31 logical order, multiply decoded IQ4_NL values by signed Q8_0 activation bytes, sum the integer products, multiply the integer result by the two decoded fp16 scales, and accumulate in float. `native_quant_h()` chooses the ggml trait's Q8_0 quantizer (the special Strata AVX2 quantizer is only for Q8_K), so a controlled comparison can pass the same exact Q8_0 activation bytes to both row functions. Keep quantization outside the row-dot comparison and report it as its own cost.

The mismatch is the row's block reduction:

- Pinned ggml's AVX2 body (`quants.c:3920-3964`) processes blocks in adjacent pairs. It has `accum1` for even blocks and `accum2` for odd blocks. Each pair applies `_mm256_fmadd_ps(scale_product, integer_partial, that_parity_accumulator)`. For `FF=640`, 20 blocks make ten such pairs, with no scalar tail. It then computes `hsum_float_8(_mm256_add_ps(accum1,accum2))`.
- Strata's `iq4nl_rows<NT>` (`iq_avx2_rows.inl:238-272`) maintains one `accf[t]` and applies an FMA for each consecutive block in order 0..19, then calls Strata `hsum8`. Its horizontal reduction tree also differs: Strata first adds low/high halves and uses two `hadd`; ggml first adds high/low halves then uses `movehl` and `movshdup` adds.

Each scale product and integer partial can agree, but sequential accumulation versus two interleaved accumulators changes float rounding, and the final horizontal-add tree changes it again. The FMA is explicit in both, so this is not simply an FMA-versus-multiply distinction. The source comment in Strata already calls out that “only the order of the float additions differs.” Consequently, equal mathematical sums do not establish bitwise equal outputs. Tiny per-row differences may propagate through the residual and future router/head calculations; LP, top-token, route, or saved prefill-state comparisons can then diverge. Do not state that the NT1 AVX2 branch is exact based only on identical integer products, a parity pass against itself, or a tolerance comparison.

GGML's non-AVX2 branches and scalar odd-block tail exist for other build/geometry cases, but a future exact candidate for this specific 640-wide host geometry must bind to the same production ggml trait/build branch and preserve the model's 20-block case. Reimplementing only its math while compiling under different reassociation/FMA settings is not a source-level guarantee; the direct byte-output comparison against the pinned reference remains mandatory.

## Minimal exact-row candidate, if service evidence justifies one

The narrowest exactness-preserving formulation is a separate NT1-only IQ4_NL helper in Strata's AVX2 translation unit that reproduces the pinned ggml AVX2 row operation, then loops rows without the indirect trait-function call. It must preserve:

1. Q4 nibble-to-`kvalues_iq4nl` table order; the same signed multiply-dot integer grouping (`maddubs` then `madd_epi16`) and no changed/saturated codebook semantics.
2. For each pair of 32-value blocks, the same separate even/odd 8-lane accumulators, scale product rounding, explicit FMA inputs and pair iteration order as ggml.
3. The exact final `accum1 + accum2` vector add and ggml's `hsum_float_8` reduction tree; for this geometry process all 10 pairs and no synthetic scalar tail.
4. The same `NativeFmt` row extent, Q8_0 activation bytes and row output writes as `native_down_rows`; no format change, altered activation quantization, skipped row, approximate table, or route loss.

A per-expert call may process rows in a loop over this helper, replacing only the internal ggml function-pointer call for Down20 NT1. Put it behind a dedicated, Down20/NT1-only test dispatch or direct harness entry; do not enable the broad `STRATA_IQ_MT_MIN=1` policy as a proxy. First verify bitwise equality for every row over independent synthetic edge/random blocks and exact Q8_0 fixtures, then on selected actual pack extents. Compare to the direct pinned ggml trait call, not to a copy of the new helper. If bytes differ, stop; do not lower the model LP/state gate. If outputs are bit-identical, component service timing must still show the actual operation faster on disjoint actual-weight train/holdout cohorts before keeping the experiment. Since this duplicates ggml's optimized reduction and integer code, it has no established benefit other than possibly removing per-row indirect call/setup overhead; inspect generated code and measure that narrow hypothesis before proposing it as a speed candidate.

The historical two-output-row IQ4_NL/component work is already rejected: R7 reports four engine-decode medians regressed by median `+0.70%`; the compiler/object substitution was 3–35% slower in its recorded 5600X comparison. Neither is an exact NT1 candidate. A two-row tile also changes register scheduling and must not be revived under a new name absent a different source mechanism and new service evidence.

## Feature/build and wrapper-receipt cautions

The option name is IQ2S-focused even though the object includes IQ4_NL; do not mistake the alias for active production dispatch or a new arithmetic.
