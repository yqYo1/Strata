## Kernel source shape and subgroup collective contract

The existing SYCL submissions use a named type through `dpct_kernel_name<class ...>` and put the standard-spelling attribute directly on the lambda call operator, after its parameter list, e.g. `parallel_for<...>(nd_range, properties, [=](sycl::nd_item<3> item) [[sycl::reqd_sub_group_size(32)]] { ... });` at `kernels.dp.cpp:2702–2708`; another tuned GDN submission applies size 16 at `2593–2595`. The subgroup-32 candidate should be a distinct named kernel type and its lambda should carry `[[sycl::reqd_sub_group_size(32)]]`; do not apply the attribute only to an inlined helper. Khronos SYCL 2020 revision 12 defines `reqd_sub_group_size` as an optional kernel feature for some values: implementations must accept source containing it, while application must submit only on supporting devices; unsupported invocation can raise `errc::kernel_not_supported` ([SYCL 2020 rev12 §5.7](https://registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html)). Current source spells it as `sycl::reqd_sub_group_size`, so retain that convention. Existing code precedent does not prove the particular new kernel compiles or fits on B570.

For a 128-item work-group and required subgroup size 32 there are four subgroups. Use `item.get_sub_group()` (or the source's oneAPI `this_work_item::get_sub_group()` form) and obtain lane local ID and subgroup group ID from the subgroup object. The candidate's logical roles are `rg=lane/8`, `c=lane%8`, and output column `8*subgroup_id+c`; do not infer these roles from `nd_item` local dimension coordinates. SYCL leaves how work-items are partitioned into subgroups implementation-defined; local coordinates are not a portable subgroup-lane mapping. The work-group size/required subgroup size guarantee the count, while IDs from the actual subgroup define the mapping.

For each four-partial gather, each participating lane calls `sycl::select_from_group(sg, partial, c+8*r)` for r=0..3 in convergent control flow, with a valid remote lane ID [0,31]. Explicitly add gathered values in the original ordered expression; `reduce_over_group` is not a substitute because the reduction order is unspecified. SYCL specifies `select_from_group` blocks until all work-items in that subgroup reach the collective and returns the named lane's value; IDs outside the group yield unspecified results. `permute_group_by_xor` has the same convergence requirement and out-of-range caveat ([SYCL 2020 rev12 §4.17.3.3–4](https://registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html)). All subgroup lanes must execute every collective in the same order, including any masked/tail token paths. Then preserve unique state ownership: each lane updates only its assigned row group, and only the designated row-group owner writes each output value. This remains a design obligation, not a source implementation reviewed here.

## Capability/resource preflight

Before any state-mutating recurrence submission, evaluate a read-only admission predicate on the exact queue/device/context to be used for that inference path:

1. The opt-in is explicitly enabled; otherwise dispatch the current default SYCL recurrence unchanged.
2. `q.get_device().get_info<sycl::info::device::sub_group_sizes>()` contains 32, and device maximum work-group size is at least 128. These are necessary coarse guards only. Strata already checks device subgroup sizes globally in `device.dp.cpp:338+`, but that startup gate does not prove the candidate is supported.
3. Resolve the **specific candidate kernel** in an executable kernel bundle for `q.get_context()` and `q.get_device()` (e.g. exact `sycl::get_kernel_id<dpct_kernel_name<class gdn_rec_quad_sycl_kernel>>()`, then `get_kernel_bundle<executable>(context,{device},{id})`, `has_kernel(id,device)`, `get_kernel(id)`). Prefer a stable type-level kernel ID; do not use `get_kernel_ids()` plus substring matching as the decision key. Query `kernel_device_specific::compile_sub_group_size` and require 32; query `work_group_size` and require at least the actual 128 work-items; retain `compile_work_group_size`, `compile_num_sub_groups`, `max_sub_group_size`, and `max_num_sub_groups` as diagnostic consistency checks if supported by the implementation. If the exact executable kernel is unavailable, query throws, required size differs, or the launch shape is unsupported, select the old kernel before submitting the candidate.
4. Record candidate's `private_mem_size`, and Intel's `spill_memory_size` when that extension is available, with the exact executable kernel identity/device. These are evidence for review, not a portable pass/fail threshold and not a substitute for compiler register reports or performance tests. `private_mem_size` is a minimum per-work-item amount and can include implementation bookkeeping; it is not the number of physical registers, spill bytes, or an automatic resource-clearance result.

SYCL rev12 says `device::sub_group_sizes` is the set of sizes supported by the device, and device `max_work_group_size` is only an upper bound; the kernel-specific limit depends on the kernel, so use `kernel_device_specific::work_group_size`. The spec exposes per-kernel `compile_sub_group_size` (0 if unspecified), `private_mem_size`, max/compile subgroup fields, and requires query via the kernel object ([SYCL rev12 device subgroup descriptors and kernel info descriptors](https://registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html)). These queries say nothing about profitable occupancy or adequate numerical parity. No such query was executed here. Intel's guide likewise presents subgroup widths as device/kernel choices and resource-dependent performance inputs, not a universal B570 guarantee ([Intel GPU optimization guide, thread mapping/occupancy](https://www.intel.com/content/www/us/en/docs/oneapi/optimization-guide-gpu/2025-2/thread-mapping-and-gpu-occupancy.html)).

Root-provided UR/oneAPI package provenance is only provenance: it is not proof that a compiled B570 candidate has subgroup size 32, a 128-item kernel limit, acceptable private/spill behavior, or exact numerical outputs. Existing `device_code_error()` in `device.dp.cpp:280–287` checks a poison-kernel executable image, not this exact recurrence kernel. Existing diagnostics in `gdn_variant_parity.cpp:116–125` demonstrate resource-query mechanics but are run-time diagnostics and must not be mistaken for admission evidence until called as a preflight before state writes.

## Fallback and ownership contract

Resolve the route before the first candidate state update in the current prefill execution (ideally before any layer's recurrence work is submitted), and cache it only with the selected queue's device/context plus the candidate build identity. Dispatch either the subgroup candidate or the existing SYCL recurrence on the same established in-order compute queue, preserving current queue/context, session-owned FP32 state pointer, convolution history, Q/K/V/gate/beta inputs, output normalization/gating, and live-tail handling. Do not create a new queue, move state, or alter head mapping. Preserve all existing numerical/repeat/state/logit/ID/MTP gates and their thresholds; R84's exact-order partial sum is only an arithmetic design requirement, not parity clearance.

Fallback is a **pre-submit branch only**. If capability/resource lookup fails before candidate submission, choose the legacy route once and proceed normally. Do not catch a `parallel_for`, event, asynchronous, or execution exception and retry the legacy recurrence against the same state: the candidate may have partially updated a session-owned state matrix, and replay can double-apply tokens or leave mixed state. An uncertain post-submit failure is an error requiring the existing request/session fault and reset policy, not a fallback signal. Do not let unsupported-kernel detection happen after partial submission; preflight must cover the exact candidate and launch geometry. No startup or request failure is relabeled as a successful legacy fallback after possible mutation.

No implementation, performance, device-resource, B570 subgroup support, or numerical acceptance clearance is granted. Next implementation review, if separately assigned, must verify exact kernel-ID retrieval in the actual build/link model, true preflight placement before any mutable submission, and state/output exactly-once ownership.
