## CPU-only regression-test contract

A useful next test should execute the actual v5 controller's startup and command-driving functions, including the exact startup grammar and protocol framer, with process/model/GPU-facing dependencies replaced at a narrow seam. Avoid testing a copied or reimplemented startup loop. Prefer extracting a callable session driver from the script and injecting an `OwnedGdb`-compatible peer/factory; alternatively run the real controller in a clearly named CPU-mock mode with an injected peer. The mock must not load model files, run inference, query hardware, claim mathematical checks, or change ordinary production admission.

The peer should have deterministic scenarios and record writes/events. In the regression case, it emits the captured INFO-shaped line first, then `READY <n> stop`; the controller must retain/recognize the informational line without treating it as a response or aborting, continue to READY, issue one valid `GEN` command through the real command path, consume scripted progress and a valid 16-field `DONE`, then send `QUIT` and complete the mock peer's normal-exit/EOF cleanup path. Assertions should cover exact ordering, no command before READY, exactly one GEN, no INFO token leakage into request results, INFO retained in raw/startup evidence, `DONE` consumed by the correct request, QUIT only after request terminal, zero mock exit, EOF/framing boundary, and no survivors. The scripted output is protocol data only; report the receipt as `cpu_mock_passed`, with `model_math_evaluated=false`, `gpu_work_submitted=false`, `model_opened=false`, `full_lifecycle_passed=false`, and `performance_eligible=false`.

Add negative controls around the same real driver: startup `ERR` must fail with its message; EOF before READY must fail; malformed/unknown startup text must fail explicitly rather than be silently ignored; a READY-shaped line after an invalid frame must not rescue it; command progress after DONE must trip the existing boundary; command timeout and nonzero/signal exit must remain failure; EAGAIN must not count as EOF. A minimal case that only unit-tests a revised INFO predicate would be valuable but insufficient by itself, because it would not establish that the startup loop consumes INFO and proceeds to the command driver.

This CPU mock is not a substitute for later owner-run actual-engine startup. It establishes controller protocol orchestration against a deterministic peer only. The eventual real run must separately show INFO handling, READY, all intended requests and math/state comparisons, QUIT, actual PTY EOF and MI normal exit, cleanup, and preserved fault/model gates before any full-lifecycle claim.

## Limits and recommendation

The v5 source currently rejects the observed INFO line at startup. The right immediate regression target is the exact controller startup/command driver with a peer that emits INFO before READY, not another test of independently extracted framing helpers and not a simulated model. Preserve `INFO` as startup diagnostic data, while continuing to reject malformed or unrecognized protocol lines according to an explicit grammar. This is a test-design finding only; no source change or new qualification is claimed.
