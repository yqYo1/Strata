# R487 — unitrace の primary Arc runtime trace 契約

Date: 2026-10-14 (Asia/Tokyo). P=`/home/yayoi/orca/workspaces/Strata/sycl`, `feature/sycl`, 調査指定の HEAD `e5ee58cb`。読み取り専用 source/docs 調査。build、test、GPU/process/service操作、fetch、Git/source変更、cleanupは実施していない。GPU traceの成立、負荷影響、現行runtime/driverでの機能対応は未測定であり、以下は調査結果とMain向けの実行候補である。

## 結論

unitrace/PTI はLevel Zero API callとGPU kernel/device activityを同じ trace に記録し、各activityのhost/device intervalと相関情報を表現する設計である。unitrace README は `--chrome-call-logging` をhost L0/OpenCL trace、`--chrome-kernel-logging` をdevice eventに加えてhost-device interactions/dependenciesを含むtraceと説明する。`--chrome-sycl-logging` はSYCL runtimeとURの両方を追加する。PTI view APIの個別record schemaにはhost timestamp(ns)、API process/thread id、API correlation id、GPU kernel instance id、backend queue/context handles、kernel start/end、memory-copy recordがある。このため、API呼出しとkernel/copyの区間・関連付けを調査する能力はある。ただし公開unitrace docsは各Chrome trace eventで必ず全correlation ID/clock-domain fieldsが出るとも、Arcのこのdriver/runtimeでそれが正しく出るとも保証しない。64-handoff smokeのevent実体で確かめる。

`--chrome-kernel-logging` は kernelに加えhost-device dependencyも記録し、trace instrumentation自体がlaunch/capture/replayを含む大量の呼出し経路へ介入する。trace結果はclean throughput値でなく診断である。SYCL/UR/L0三層を全て有効化するとevent増と負荷が増える。最初の64 handoff fixtureでは三層・kernel/device traceを同時収集してlane/correlation有無を確認し、長文modelでは必要だったlaneだけ有効化する。

これは「model profilingに進める」というruntime capability結果ではない。Mainが予定するcollector smokeが 64 handoffsを含むactive interval、L0 API events、GPU device tasks、共通時間軸、PID/TID/queue識別を全て確認した場合だけ次の長文runtime候補へ進める。missing lane、timestampゼロ/不整合、overflow/truncation、trace finalize異常は明示的unsupported/incompleteとして止める。設定だけで成功扱いしない。

## trace区間・timestamp・correlation

- PTI view API referenceではAPI call recordに `_start_timestamp`, `_end_timestamp` (ns), `_process_id`, `_thread_id`, `_correlation_id`, API group/idがある。kernel recordは `_kernel_id` (kernel instance unique), `_queue_handle`, `_context_handle`, kernel名、start/end timestampを持つ。memory copy v2 recordもschema上用意される。timestampがcollectionで得られなければ0になる場合がある。従ってvalidatorは0 timestampを有効intervalと解釈しない。
- unitrace `--device-timeline` はkernel instanceごとにqueuing/submission/start/end timestampを出すと説明される。`--kernel-submission` はappend/queued, submit, executeを集計する。`--chrome-kernel-logging` はChrome/Perfetto traceにdevice events、host-device interaction/dependenciesを出す。CLI docsはcross API/device timelineが持つ時間軸について単一のclock-domain field名を規定していないため、validatorはactual trace metadata/record semanticsを検査し、host intervalとdevice intervalの相関を明示確認する。
- Intel PTI Level Zero metric docsはGPU kernel timestampがGPU clock cycles、metric query timestampがnsの場合があること、その場合の周波数変換方法を説明する。これは hardware metric correlation文脈であり、unitrace API/device traceが異なるclockをどう正規化したかの実測証明ではない。trace fieldsの時間単位・起点を推測しない。
- `--pid` はhost APIとdevice activityのPID、`--tid` はhost API traceのTIDを出す。device activityは既定でper-thread/per-Level-Zero-engine/queueに分類され、`--chrome-no-thread-on-device`/`--chrome-no-engine-on-device`で消えるため、first smokeでは指定しない。validatorはengine/queue識別子を保存する。
- kernel loggingでhost-device dependenciesが出たとしても、graph replay内各nodeへのpersistent 1:1相関を保証する記述はない。graph capture側のAPI recordとreplay submit、各device kernel eventが存在するかを分けて検証する。

## 観測が与える runtime/graph影響

`--chrome-call-logging` と `--chrome-sycl-logging` はAPI callback/interception traceなのでAPI entry/exit、timestamp取得、buffer書き込みを加え、host submit costや高頻度compat APIの時間を変える。`--chrome-kernel-logging` はkernel/device recordsと依存を収集するため、各kernel/transferでevent件数と記録処理が増え、queue submission/replayの時間にも影響しうる。unitrace README自身がhost programming API tracingでCPU性能に影響する旨を記載。したがって traced host intervalは通常実行のレイテンシ値ではなく、同じ traceの中で順序・gap・call countsを見る診断観測値である。profilerで観測したcounts/timingをclean throughputと混ぜない。

このtraceがSYCL graph executableのnative record modeを切り替える、graphを通常listへ展開する、アプリ側にquery/resetを足すという根拠は見つからない。PTI toolは外部からruntime/driver APIをtraceするので、基本的には既存native graph pathを実行したままAPI callとdevice activityを観測する。けれど、Arc driverがgraph node内部のkernel activitiesや相関を公開しなければ内部nodeは見えず、replay API一件/graph一件にまとめられる可能性がある。再生ごとのdevice kernel rowsが欠けた場合、それはtrace unsupported/incompleteであり、手動イベントやquery/resetを入れて代用してはいけない。

P `src/sycl/compat.cpp` は通常/nativeのcommand_graphを構築し、native `begin_recording`時に`enable_native_recording`を付ける。`cudaEventRecord` adapterは通常SYCL queue barrierをsubmitし、graph capture中はそのevent stateをgraphに保持する。`launch_graph`はgraph executableをqueueへsubmitし、前回graph eventへの依存を記録、graph-internal event statesをreplay completion eventに更新する。native graphで`cudaGraphGetNodes`/node type/params introspectionを要求すると明示的にunsupported例外にする箇所がある。したがってnative recording時にnode inventory/個々のnode parameters/完全なnode別submission countを期待しない。ordinary graphのGET_NODESが見えてもそれは別modeであり、調査のためnative graph modeを変えない。

No intrusive timers: `STRATA_PREFILL_TIMING`は各markでevent barrierをsubmitし elapsed-timeでend eventをwaitするため必ずoff。`STRATA_DECODE_TIMING`, pool trace、validation layerもこのtrace runではoff (R467/R484の既存指針)。unitrace itself adds events/callback work; instrumentしたrequestのrate比較はしない。

## event volume、buffer、bounded handling

unitrace CLI `--chrome-event-buffer-size N` は**host上のthreadごとのevent buffer size (number of events)**であり、default -1/unlimited。byte capでもtotal trace-file capでもない。N件で設定した際のあふれで何が落ちるか/終了statusへの影響は公開READMEで十分に規定されていない。従って finite Nはbounded-memory guardであり、trace complete保証と扱わない。model runのoutput file上限はunitrace READMEに見当たらず、`--output-dir-path`/`--result-dir`は保存先であってbyte boundではない。Mainは私有のempty unique dir、owner deadline、filesystem free-space precondition/monitoring、result-size hard stop policyを設け、上限/stopなら`incomplete`と記録する必要がある。silent truncationをPASS扱いしない。

Long promptは32K prefill chunkingで膨大なGPU kernel/UR eventを作る可能性がある。最初は既存 `tests/sycl/runtime.cpp` の64 changing cross-queue handoffsのみ。smoke自体の小サイズにも最小有限 buffer（例えば per-thread 65,536 event、実装が拒否する場合は記録して小さく調整）を候補とできるが、正確な必要件数やdrop behaviorは未検証である。smokeが同一fixtureの各期待handoffを識別できるほどcountが揃うかを確認。もし数量が失われる、overflow疑い、複数 laneが不完全ならmodelへ広げない。

Long traceでUR+L0+SYCL全層を同時有効化したままraw Chrome JSONを大容量保管しない。先に smokeでSYCL/UR/L0 record familyとdependenciesのconsumer価値を確認し、modelではMain timeline validatorが必要とする最小layerに落とす。retention policyのdefault 64 MiB raw text log budgetはmeasurement/investigation artifactsに適用。trace file/structured traceは必ずしもtext logではないが、独自に明記した同等の有限byte budgetとstop条件を置く。event capに達したか不明なまま長文で継続しない。成功後はtimeline extract、count、hash/size、owner/consumer/review pointを残し、未解決questionがcomplete traceを必要とするときだけnamed exceptionを記録する。

## Long-model timeline validator fields

Compact validation output (full JSONを開かず必要sliceだけ読む)には次を持たせる。

- `run_identity`: unitrace binary/version/source revision/CLI+effective options、target process tree IDs、model binary hash、assigned device識別 (Arc B570)、boot ID/UTC+monotonic bounds、request prompt/output counts & digest、request start/end marks。
- `trace_integrity`: status complete/incomplete/unsupported; file path,size,SHA-256, parser version; event buffer setting, event/drop/overflow indications, process exit, flush/stop result; owner bytes/deadline/stop policy。
- `clock`: each record family/API group/device engine time domain, units, zero/missing timestamps, normalization/correlation evidence; API/device clocks comparable yes/no and basis. Unknown must remain unknown.
- `host_api`: per `(pid,tid,api_group,api_id/name)` call count, summed and distribution spans, timestamp min/max; separate queue/list create, append, close, execute/submit, synchronize/wait, query/reset, copy call categories when actually present. No assumption of specific UR/L0 API mapping until trace rows name them.
- `kernel_device`: per `(pid,tid,device,queue/engine,kernel_name,kernel_id)` count; queued/append, submit, start/end/duration if fields exist; parent API/correlation ID(s), dependencies; note graph replay boundaries and whether per-node replay count was exposed.
- `copies`: host copy API call counts; device memory-copy activity counts, bytes known/unknown, start/end intervals and correlation; independently mark submitted vs device-completed activity where event semantics support it. Do not report planned source blob counts as physical bytes.
- `waits`: last dependency event / final synchronization host API begin/end; queue waits, event wait/query and graph completion event/replay occurrences; link to predecessor tasks if trace provides IDs. The trace can't independently identify an application's semantic “last wait” without mapping its API calls/compat boundary; keep this as correlation/inference flag.
- `intervals`: prompt request wall; host submission spans; each GPU kernel/copy interval; graph replay submit interval; queue/device idle intervals only where trace permits; preserve overlap and never sum concurrent spans as elapsed time.
- `graph`: graph capture begin/end, instantiate/finalize/submit/replay IDs if logged; ordinary/native mode from unchanged application setting; internal nodes visible count, node/correlation granularity, completion markers, opaque/unsupported result.

Per-kernel timestamp itself is observability, not a measured rate qualification; browser screenshot is not enough. Keep concise table counts/gaps and one representative excerpt with IDs and clock note under the existing artifact-retention policy.

## Explicit unsupported/fallback semantics

- **No GPU timeline lane or unsupported Arc/driver collection:** stop after fixture; classify `unsupported_device_timeline`, preserve minimal stderr + API trace and exact identity; do not try model, hardware metrics, sysctl/driver/service/device changes.
- **API lane works but kernel/device lane absent:** `unsupported_kernel_correlation`; do not infer device time from host waits or enable metrics to compensate.
- **Graph internal tasks are opaque but replay event visible:** report replay-only granularity. It cannot answer per-kernel attribution; possible later fallback is a separately designated ordinary-recorded-graph diagnostic, only if it preserves correctness and user/Main approves after smoke. Do not toggle production graph setting for first test or silently force graph-disabled execution.
- **Trace result is capped/buffer overflow, time domains not correlatable, or callbacks perturb/alter request correctness/normal completion:** mark incomplete/invalid; preserve failure evidence and stop. No fallback to invasive SYCL timing markers or per-layer logging.
- **Graph API/native recording fails due to collector instrumentation:** captured smoke failure is evidence that this collector configuration is incompatible with this runtime path, not permission to change Arc graph execution mode. Retain exact error and use no profiler result.

Given existing 32K clean series (prefill 118.4–118.9 t/s, decode 24 generation 2.8–4.2 t/s) and separate fresh-transfer smoke PASS, tracing remains a diagnostic-only follow-up and cannot supersede that baseline.
