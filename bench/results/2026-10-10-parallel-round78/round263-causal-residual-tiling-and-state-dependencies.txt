# R263 — residual tiling schedules, causal state and RAM traffic

Date: 2026-10-10 (Asia/Tokyo). Read-only schedule/dependency audit. This report addresses which traversal orders can keep causal attention and GDN state correct while lowering the number of host residual handoffs. It does not redo R262's arithmetic budget, establish memory fit, measure B570 performance, or identify a production bottleneck.

## Fixed inputs and source boundary

The source snapshot is the parent-pinned worktree `diag-sycl-prefill-service-events-20261010`, fixed commit `495369cf4dc6e6da564095a1c26504dd3694e3f2`. The permitted file `sycl/src/prefill/prefill.cpp` hashes to the supplied SHA256 `f6cbc4acb9f84b19480a25892a2e6864896a3e3ab0f68ace3c3f51a788591f69`. I used this pinned file and archived R253/R254/R257/R261 reports, the reviewed registry v99 (SHA256 `878bec604ea0b200e2f911ce5c4aa3b0ced876436eab92665611c1b707dab42b`), and root corrections in that registry. I did not inspect live implementation edits or issue Git commands, builds, tests, inference, profiles, GPU/process/hardware queries, payload scans, cleanup, or source edits. External source research is linked below.

The source's `run_impl` processes chunks in increasing `c0`, then layers in increasing `l` for each chunk. The ordinary chunk-major path carries the per-chunk `m.R` activation through all layers; it does not allocate the layer-major full-context residual plane. It can instead repeat expert streaming across chunks when the relevant weights are not resident. `run_layer_major` has the opposite outer order: for each layer it loads that layer's expert set, calls `run_impl` across all chunks, then hands each output chunk to the next layer via a full-context host residual plane (or a configured GPU prefix). It thereby avoids repeated layer-weight streaming at the cost of residual handoffs. These are existing alternatives; chunk-major is not a newly discovered residual optimization (R46 correction).

This branch currently rejects streamed QSA KV (`kv_mode != 0`), peer/layer split, non-compact/non-FP16 paths, and PLE preload. Its caller keeps the entire QSA K/V state resident while it visits layers. Therefore the group schedule described below inherits the resident-QSA-KV restriction unless a separate KV-stage design is qualified. It cannot reclaim or reset QSA/GDN request state as a way to free space.

## Schedules that preserve the state dependencies

**1. Existing chunk-major (`run_impl` only).** Keep the current token tile on the GPU and run it through the layer stack before advancing to the next tile. Each layer sees tile positions in increasing order; the within-tile causal QSA mask/indexer still restricts each query to its legal prefix. Each GDN layer applies its conv-history and recurrence update once for that tile, starting from that layer's prior state. This keeps the residual handoff between layers in device scratch and needs no full-prompt residual plane. The schedule already provides the lowest host residual traffic among the current choices. Its cost is the existing cache/staging policy: absent resident weights, layer weights may need to be fetched again for each token tile. This path is the appropriate control, not a claim of better performance.

**2. Existing layer-major (group width one).** The current `run_layer_major` visits all token tiles for one layer before advancing to the next. QSA/GDN state for that layer advances in increasing token order, once per tile. Layer input/output residuals between layers are written/read through the host residual plane unless placed in the optional GPU prefix; the plane itself remains a full-context backing. This can reuse one layer's expert set across all tiles, but it is the schedule with repeated host residual transfers. The R253 prefix correction and R257 allocation/lease limits apply; the correction is a bounds/compile qualification, not a numerical or full-context run.

**3. Bounded adjacent-layer groups (conditional design, not implemented).** A plausible middle schedule uses a small resident group of adjacent layers, processes the entire prompt in token tiles through that group, then spills only the group's final residual to the existing host row plane before starting the next group:

```text
for each adjacent layer group [g0, g1):
    stage that group's expert weights into disjoint cache slots
    for token tile (p0, T) in increasing order:
        read embedding or preceding group's residual tile
        run layers g0 .. g1-1 in normal order, keeping m.R on device within the group
        if not the final group, write this tile's group output to the host residual plane
    fence all group consumers before reusing cache slots
```

This order is compatible with state chronology: each QSA and GDN layer is called once per tile, in increasing `p0`, and all layers for a tile run in normal model order. QSA's chunk positions and per-query `steps`/causal selection remain attached to the same `p0,T`; the prior KV pages stay visible and no future KV may be read. GDN's session-owned recurrent matrix and convolution-history suffix remain attached to their own layer and are fed into the next tile unchanged from the previous tile's completed update. GDN updates must not be reset or replayed when moving between groups. The normal last-short-tile extent must be preserved.

At a group boundary the final tile output is still needed by the next group. Unless a different schedule can retain all prompt activations on GPU, that output must still pass through a full-context host backing plane; grouped execution reduces how often each row is written/read, not the full residual plane's host capacity. Inside a group, `m.R` is the transient device activation and is reused tile by tile. In the idealized source schedule, a group of adjacent layers retains its weights for all prompt tiles and the full-context host plane is crossed only between groups. The total weight residency requirement grows with group size. R47 documents the necessary disjoint slot map and conditional group-cache capacity; current code exposes only one layer's 512 expert slots and cannot directly run this schedule. No current peak-allocation receipt establishes what group fits on this B570 with resident KV/session state, Prefill buffers, model allocations and runtime/graph memory.

A group width of one is the existing layer-major schedule; a group spanning every layer tends toward chunk-major behavior but would require the entire model's expert weights resident at once for this formulation. The useful candidate space is therefore the small-width groups admitted by actual phase-aligned free memory, starting with width two and then width four only if memory and slot-map constraints allow. These are candidate widths for an experiment, not a recommendation or predicted win. Do not derive numeric bytes here; R262 owns the separate arithmetic budget audit.

**4. Tile-major through all groups.** Running a token tile through all layers and then advancing to the next tile preserves the state order and uses only the per-tile activation, but is just the existing chunk-major schedule. It avoids the host residual plane entirely; it does not retain weights for all layers at once, so use the existing chunk-major weight reload/caching measurements for comparison.

## PLE, callbacks, and ownership details

The shared PLE history (`ss.ple_prev`) is not an independent per-layer state. Current layer-major snapshots the starting pair and restores it before each full-sequence layer call so that the PLE block at model layer 1 sees the correct initial n-gram prefix. A group implementation that calls `run_impl` once per whole group (all tiles) naturally processes the PLE block only in the group containing layer 1 and advances the shared history once through the prompt. A more granular per-tile/per-layer invocation must snapshot the history before a tile, restore that same pre-tile history when each layer's PLE computation needs it, then commit the tile's advancement exactly once. It must not let later layers inherit already-advanced history for the same tile or reset history before the next tile. R45 records this ownership rule; the actual target arrangement must be tied to the chosen call boundary.

The cache slot map must identify `(layer, expert)` to a stable disjoint slot for all members of a group, and only layers in that group may resolve through the temporary group cache. A cache slot must not be overwritten while a compute queue or captured graph can still read it. Maintain the existing copy/stager/compute fences and drain on every error/cancellation path before recycling slots or residual storage. The existing layer-major callback uses a whole-context `hand_in_` base and offsets per tile; a tile-local pointer cannot be passed through that interface without changing its ownership/offset contract. An explicit tile view or a carefully preserved whole-plane owner is required.

## Rematerialization and cache/host restore are different levers

Rematerializing a prior layer's output could reduce saved activations only by rerunning the required prefix from the correct input and state. GDN recurrence and convolution history mutate per layer; QSA appends K/V and indexer state; PLE advances shared history. Replaying without restoring every affected state would apply the same tokens twice or expose stale/future state. A safe recomputation plan must checkpoint/restore the complete affected per-layer QSA/GDN state, PLE history, positions and any route inputs, then prove replay has the same outputs and final state. It adds weight work and compute. No current report qualifies such a checkpoint/recompute path. Do not infer that ordinary transformer activation-checkpointing recipes transfer directly to this inference state machine.

FlashAttention-style tiling/recomputation is a narrower and transferable idea: exact online-softmax attention can avoid materializing and rereading a large attention-score/probability matrix. It can remove attention-kernel scratch traffic if the active QSA implementation has such materialized intermediates. It does not eliminate the cross-layer FP32 residual handoff, the causal QSA K/V pages, GDN recurrent/conv history, or final model outputs. FlashAttention's GPU SRAM/HBM tiling is also not by itself a claim about unified/shared memory traffic on B570.

Releasing the original decode expert cache or MTP weight backing before allocating a temporary layer/group cache can create VRAM headroom. Per R257, that requires completed queue drains, graph retirement and refresh, then backing release and later restoration. It must leave QSA KV plus GDN/PLE request state intact. Main-cache `snapshot` restore adds host snapshot bytes that can overlap the residual host plane; `ram` restore avoids a second payload image only with a complete resident RAM expert arena. The temporary group cache and any GPU residual rows must be freed before restoring the decode allocations. Cache release changes the memory peak, not the number of residual row transfers; choosing RAM as a weight source is not the same as choosing RAM for residual backing. No current source receipt proves group-cache allocation headroom or system-RAM peak.

## What transfers from other implementations

- **vLLM scheduler and GDN backend.** The official [scheduler configuration](https://github.com/vllm-project/vllm/blob/main/vllm/config/scheduler.py) chunks a long prefill against a per-step token budget; that is request scheduling and does not by itself change layer order. More relevantly, [vLLM's GDN attention metadata builder](https://github.com/vllm-project/vllm/blob/main/vllm/v1/attention/backends/gdn_attn.py) carries prefill chunk indices/offsets, per-request state indices and a `has_initial_state` flag into the chunk kernel. This supports the general implementation contract that GDN chunks need explicit state-in/state ownership. It is PyTorch/CUDA/ROCm backend code, not evidence for Strata's numerical identity, Intel backend support, performance, or group-cache memory fit.
- **SGLang.** The official [PrefillAdder/schedule policy](https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/managers/schedule_policy.py) admits a bounded token chunk and retains a request for later prefill steps. This is useful scheduling structure, not a causal-attention or GDN kernel proof. The [SGLang JAX scheduler description](https://github.com/sgl-project/sglang-jax/blob/main/docs/architecture/03-scheduler.md) explicitly aligns chunks to its page size; it is a separate JAX backend, so only the boundary-alignment principle transfers.
- **llama.cpp.** Its [recurrent memory implementation](https://github.com/ggml-org/llama.cpp/blob/master/src/llama-memory-recurrent.cpp) models recurrent state as a whole-sequence state cell and snapshots/restores state while checking whether a set of microbatches can be prepared. The relevant lesson is that recurrent state has ownership/rollback semantics separate from KV; it does not establish Strata GDN layout or a GPU tiling schedule.
- **Intel LLM Scaler.** Intel's [LLM Scaler repository](https://github.com/intel/llm-scaler) documents a vLLM stack for Arc Pro B60/B70 and reports model streaming-load work in release notes. That is useful platform context, but the repository description provides no equivalent layer-group schedule or residual traffic measurement; it cannot be used as B570 capacity evidence.
- **Layerwise weight streaming.** The DeepSpeed authors' [ZeRO-Inference design](https://www.deepspeed.ai/2022/09/09/zero-inference.html) streams weights layer by layer and keeps a layer's output on the GPU as the next layer's input. This validates the weights-versus-activation placement trade as a systems design pattern, but it does not handle this model's recurrent state, sparse MoE cache, or layer-group correctness.
- **Attention-only rematerialization.** Tri Dao's [FlashAttention-3 author blog](https://tridao.me/blog/2024/flash3/) explains exact tiled/online attention with recomputation to avoid writing the full attention matrix; the [FlashAttention paper](https://arxiv.org/abs/2205.14135) establishes the exact IO-aware attention algorithm. This transfers to attention scratch residency, not to persistent residual/KV/GDN state. Its specialized asynchronous Hopper optimizations do not transfer to B570.

These references show that token-bounded scheduling, layerwise weight movement, exact attention tiling and explicit recurrent-state chunk metadata exist as distinct mechanisms. None demonstrates that changing Strata's loop order preserves its own outputs or reduces its measured bottleneck.

## Minimum qualification and measurement sequence

1. **Freeze a state-aware schedule oracle first.** For the exact fixed source identity, test the ordinary path, group width one, and a group width greater than one with a fake `layer_compute(layer,p0,T,activation,state)`. Assert each layer sees strictly increasing positions and each token exactly once; exact full and tail tile extents; each group's tile outputs connect only to the next group; QSA and GDN state handles are per-layer and updated once per tile; PLE prefix/history advances once; state is not reset at group boundaries. Assert cache-slot map uniqueness and no slot reuse before the modeled completion fence. This checks control/data ownership only.
2. **Admit memory by phase, not card capacity.** Before a GPU comparison, capture free/total VRAM and host available/resident memory around main-cache/MTP lease, QSA/GDN/PLE session state, temporary group-cache allocation, residual host-plane allocation, every group, release and restore. Record exact loaded group slot sizes, active QSA KV mode, effective chunk/tail schedule and all simultaneous owners. Keep the RAM restore arena/snapshot and host residual overlap visible. R257 provides the required retirement and restore contract; R262 owns arithmetic estimates.
3. **Prove numerical and causal state parity on B570.** First compare against a passing same-source baseline at the admitted 32K boundary, with identical prompt, chunk schedule, math selectors, environment and fresh request state. Record positions consumed, all-head outputs/logprobs/token IDs, first mismatch, residual fingerprints at group boundaries, every QSA layer's appended K/V/indexer extent and all GDN recurrence plus convolution state. Include PLE history and full serialized request state after completion. Only advance to physical full context if earlier gates and phase-aligned memory admission pass. The R253 fix is not a substitute for this run; R261's isolated generic-IQ receipt is not a model result.
4. **Measure separate traffic lanes and end-to-end time.** Count actual residual D2H/H2D bytes and waits, expert source/stager copies/reloads by `(layer, group, tile)`, and any QSA KV staging separately. Compare chunk-major, layer-major width one, and admitted group widths on the same clean request; retain separate cache-release and resident-KV settings. Use instrumentation for route/byte accounting, then a matched uninstrumented request for total wall time. Do not add overlapping copy, GPU event and host intervals as if they were a serial critical path. Require the R254 production-route census before assigning these costs to current requests or declaring residuals critical.

## Disposition

The only currently evidence-backed zero-host-residual-plane schedule is ordinary chunk-major, which already exists and pays its known weight-streaming trade. Current layer-major preserves state only under its resident-QSA restrictions and pays host residual transfers at each layer boundary. A layer-group outer schedule with token tiles inner can preserve causal attention and GDN chronology while reducing those host residual round trips to group boundaries, provided all group expert slots stay resident and the state/callback/fence rules above are implemented. It still needs a full-context host residual backing plane and resident QSA K/V, and it has a larger temporary expert-cache lifetime. That is a conditional design candidate, not an existing implementation, performance prediction, memory-fit claim, or adoption recommendation. No evidence presently shows which schedule is on the B570 model's actual critical path.
