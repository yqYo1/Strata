# R264 — bounded production critical-path collector plan for Arc B570

## Finding

Use the existing route/transfer/service census plus a short PTI Level Zero activity trace to determine which operations overlap, their dependencies/queue placement, and which request phases they belong to. Keep clean matched requests for latency. Profile intervals can establish overlap and dependencies when the trace attributes the operations; they do not provide clean latency. The prior R262 correction applies: do not require an uninstrumented event timeline.

Hardware metrics are capability-discovered, not assumed. Public PTI documentation covers Arc graphics and lists Ubuntu/Windows B580 as regularly tested. It does not promise that every counter is available on B570 with the installed Level Zero v2.12/driver. The PTI repository also has a B580 report of `unitrace --metric-query` being unable to query kernel metrics, so general Arc or B580 support is not proof that the B570 metric path works. VTune’s current public guide inspected here is 2026.1 / metrics reference 2025.4; its metrics reference names Arc Alchemist and newer for some metric families, but it does not certify the user’s stated VTune 2026.4 plus B570 combination. Record the installed tool and driver versions from their existing package receipts; do not infer them from current public pages.

## Candidate signals and limits

| Question | Candidate source | What it can support | What it cannot support without further qualification |
|---|---|---|---|
| Operation order, duration, queue and overlap | PTI `unitrace` Level Zero host/device tracing; keep per-operation host API and device intervals, flow IDs, thread, queue/engine labels and command IDs | Attribute submitted copies and kernels to the request and show observed time intersection/dependency relations where the source/API flow join is complete. Current local source audit says PTI engine labels are tracked ordinal/index, and both emitted flow directions anchor at `command_start`; neither is a hardware busy counter nor completion marker. | Physical engine utilization, true memory traffic, or host time spent blocked. The queue/engine ordinal is a label. Host submit/API intervals are not device service. Use R237’s existing oneMKL returned-event/internal-operation coverage contract; this report does not restate it. |
| GPU memory traffic / bandwidth | Enumerate PTI Level Zero metric groups at runtime (`gpuinfo` / `unitrace --metric-list`, and capture exact names, descriptions, units, group and status). Candidate PTI names include `GPU_MEMORY_BYTE_READ`, `GPU_MEMORY_BYTE_WRITE`, `L3_BYTE_READ/WRITE`, `XVE_ACTIVE`, `XVE_STALL`, and XMX utilization/instruction metrics. VTune candidate names include GPU memory read/write bandwidth, XVE XMX active/instructions, and XVE stall breakdown. | If the B570 collector actually returns a named counter, its raw value and scope can characterize that supported hardware event. `XVE_ACTIVE`/`XVE_STALL` and XMX metrics can distinguish active/stalled execution and XMX use at the resolution/scope provided. | No name is guaranteed available on B570. “GPU Memory Read Bandwidth” in VTune is documented as accesses missing/bypassing GPU L3 and served by uncore or main memory; do not automatically call it GDDR-controller bytes. L3 bytes are cache-level traffic, not DRAM bytes. EU/XMX active is a utilization indicator, not FLOP rate or whole-device busy time. Ratios/cycles from a counter group are not byte totals. |
| GPU-local memory-controller traffic | Candidate Level Zero Sysman `zesMemoryGetBandwidth` read/write counters, only if memory handles/API succeed and properties expose them; also inspect enumerated PTI metrics for documented GPU memory byte counters. | Sysman spec defines read/write counter deltas in 32-byte transactions; multiply transaction deltas by 32, handle rollover and use the API timestamps. This is a stronger candidate for physical memory traffic than source-level logical bytes if B570 exposes the counter and its memory-module scope is confirmed. | Public docs do not establish that the B570/installed driver exports it. Not per process/kernel; background traffic is included. Don’t enable a missing feature or alter driver settings to get it. |
| PCIe link byte traffic | Candidate Level Zero Sysman `zesDevicePciGetProperties` + `zesDevicePciGetStats`; use only if `haveBandwidthCounters=true` and snapshots return success. Capture `rxCounter`, `txCounter`, API timestamps, current speed and BDF. | Endpoint-wide RX/TX byte deltas over a request bracket can independently cross-check the direction and approximate magnitude of link activity. The API says TX includes replay bytes, counters sum lanes, and static PCI max-speed is only a capability. | Availability on this B570 is unknown until enumerated. A snapshot is device-wide and includes unrelated traffic; it cannot assign bytes to a copy operation. The microsecond API timestamp has its own base and cannot be subtracted from PTI/device or host steady clocks. A single request-scale delta is not per-DMA telemetry. |
| Host staging, submission and waits | Existing route/transfer ledgers and request wall time; add/retain monotonic host spans for CPU staging copy, route accounting, `event.wait`/queue wait, and transfer-stager/ring waits. Optional VTune XPU Offload/CPU Hotspots view for CPU thread/stack context. | Host steady-clock intervals can separate CPU copy/service, blocking waits, and API submission. PTI/VTune’s CPU↔GPU task linkage can show which thread submitted a device task. | PTI append-call duration is not completion wait; device event duration is not CPU staging or request latency. CPU usage sampling alone cannot say a sleeping thread waited on this GPU request; preserve explicit software wait spans. Do not subtract host timestamps from device timestamps without a measured clock map. |
| Logical work bytes | Route census `calls`, `ne`, packed tensor byte lengths and branch; transfer ledger’s exact copy count/source/bytes; source-derived materialized-output bytes. | Exact software-level amounts offered to each route and submitted for copy, reconciled by chunk/layer/pair/branch. | Not a memory-controller or PCIe counter. Cache hits, write allocation, read-modify-write, paging, BAR mappings, protocol traffic and background transfers can change physical traffic. Never label logical bytes as measured DRAM/PCIe bytes. |

Counter availability gates: enumerate metric groups and descriptions before collecting; record every unavailable/permission/error result. Some metrics require permission for observation access under the Linux `xe` driver. PTI documentation describes changing `/proc/sys/dev/xe/observation_paranoid` to enable it; this plan explicitly does not change that setting, request a reset, or alter the runtime/offload configuration. If collection is denied or the metric group is absent, mark that counter unavailable and proceed with the activity trace/software census only. The metric-group list is the authority for this B570 installation, not a generic Xe2 table. Where PTI query and time-sampling modes expose the same candidate metric, start with query mode for per-kernel work only if it enumerates and succeeds; retain its query-mode/metric-group identity. PTI docs state hardware query enables device timing and that query/sampling can collect all counters in a group. Metric availability and semantic scope must be preserved; don’t combine separate groups or time-multiplexed passes into one workload without marking them as separate perturbed runs.

## Minimal main-owned collection

1. **Pin, don’t probe from this report.** Main records the frozen source/build hash, loaded model/pack manifest hash, compiler/runtime/driver/tool versions, queue policy, existing safe environment, request identity and current pair census. Do not change Direct Submission/copy-offload controls or device scheduling. Preserve the existing model request and validation status.
2. **Capability preflight before the request.** Main saves `unitrace --device-list` and `--metric-list` output for the selected device, including exact group/metric names/units and any errors. If attempting Sysman memory or PCI counters, record feature flags, properties, timestamps and API status without writing controls. If metrics are inaccessible, stop that branch without changing sysctls/permissions. No counters is a supported outcome.
3. **Clean latency series.** Run the same deterministic, already-qualified >=32K prompt three times without PTI/VTune/counter sampling. Keep request end-to-end wall times, status/correctness, prompt token count and latency environment; report median and min/max, not a counter-derived rate. These clean samples are the latency evidence. Keep background workload/device contention constant or record it as a mismatch.
4. **One profiled request.** Run one >=32K request under the bounded PTI activity trace with the existing default-off route census enabled. Do not add device markers, barriers, waits, synchronizations, or per-expert event records. The census records sparse `(chunk,layer,pair,branch,owner/source,ne)` bins, logical packed/output bytes, and exact transfer bytes/source; reconcile routed rows, calls and transfers exactly as R254 requires. PTI supplies actual copy/kernel command intervals, host append calls, flow/queue identity, and observed intersection/dependency evidence. Join by source IDs and verified PTI host API flows. Keep host CPU staging/explicit wait spans on a separate lane.
5. **Hardware metrics, conditional.** On that same profile only if the selected group is available and `unitrace` can collect it without changing runtime state; otherwise record `not available` and do not retry with a driver-setting change. Prefer one group with a clear question (memory byte traffic, XMX/active-stall, or other) over broad group accumulation. If the enabled group requires a separately collected pass or loses full trace coverage, keep the PTI activity trace as the primary overlap evidence and label the counter pass as a separate perturbation. If PCI Sysman counters are supported, take one before and after snapshot outside the timed request interval plus one short idle bracket; disclose their device-wide nature and keep raw counters, timestamp deltas and rollover method. Don’t poll continuously.
6. **Hard bounds and stop conditions.** Bound the profiled case to one request, 60 seconds from trace start, and 64 MiB combined raw trace/counter/log output. If trace size reaches the budget, PTI reports lost events, request/census counts do not reconcile, a counter fails mid-run, or the 60-second limit expires, mark the profile incomplete and make no capacity join from partial data. Stop collection cleanly; do not terminate/reset the device or delete anything while the process/run remains active. Keep the existing retention owner/budget/consumer/review-point manifest and a compact interval/metric table after validation.
7. **Quantify instrumentation separately.** Compare the profiled request wall time with the three clean matched samples only as an overhead diagnostic, never as a corrected latency. Report ratio to the clean median and absolute delta; if it is outside ±10% of the clean min/max band, call the profile materially perturbative for whole-request timing. Regardless of that test, treat event timestamps as profiling evidence and only the clean series as latency.

## Interpretation gates

For every candidate rate, join exact request counts/bytes/shape/branch to the exact capacity measurement denominator and report exposed service separately from total service. A time interval is critical-path-exposed only when the trace/source dependencies show it is not hidden behind other useful work; overlapping intervals must be counted by interval union or explicit path analysis, not by summing event durations. Only compare available memory metrics to their matching layer: cache traffic to cache traffic, controller counters to controller bytes, endpoint PCI counters to endpoint PCI traffic, and logical software amounts to logical amounts. An unsupported metric, missing event, overflow/cap hit, dropped record, route mismatch or uncertain clock relation is “unqualified,” not zero.
