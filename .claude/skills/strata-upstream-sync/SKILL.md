# Strata 上流更新の評価と取り込み

このリポジトリに付属するプロジェクト専用スキル。`.agents/skills/strata-upstream-sync` で
管理し、ユーザー共通の skills ディレクトリにはインストールしない。別プロジェクトには
適用せず、Strata の関連 clone/worktree を使う場合もこのプロジェクトの更新作業として扱う。

ベースと唯一のアップストリームは `Niko1221/Strata`。この fork はユーザー自身のPCの
Intel GPU・CPU・RAMへ最適化するためのもので、現時点で上流への貢献は予定しない。
CUDA/HIPの推論移植や検証は行わない。ユーザーのライセンス上の制約により、
`MistVVK/XeStrata` は**性能の参考値だけ**に使う。コードのコピー・移植・翻案や、
そのソースを下敷きにした再実装は行わない。helper・診断・テスト・保存用source提案も含む。
既存の由来がある場合は独立した安全修正を保って現行treeから撤去し、出自と測定の
compactな記録をGitへ残す。著作権表示の削除や改名で由来を消したことにしない。
他の実装を参考にする場合も、出自と利用条件を確認してから判断する。

主の作業ブランチは `feature/sycl`。独立した実装が必要な場合だけ、その現在の commit から
子ブランチを切る。作業が終わったら source・テスト・スキル・レポートの実体を
`feature/sycl` に取り込み、区切りごとに PR 経由で fork のデフォルトも更新する。
原 commit の履歴を維持し、統合後の不要な子ブランチと worktree をローカル・remote の
両方で削除する。履歴保存だけの merge をコード統合や推論採用と数えない。
未完了の子ブランチは残作業・consumer・次の見直し時点を記録する。

Strata の更新を一度で終わらせず、更新が来るたびに同じ比較基準で確認・評価・統合する。
今回の到達点は、本家の対象リビジョンの差分を網羅した機能対応表、上流単体の測定、
部品別の推論採否、統合後の検証、Git に保存した判断である。
更新の確認を自動スケジュール化する指示ではない。
読み取り専用の依頼では調査と計画までに留め、fetch、実装、測定、commit/pushを実行しない。
この手順は依頼の範囲と権限を広げず、既に許可された実装・検証を不要な確認で止めない。

## 判断の原則

- **推論エンジン以外の機能は全て取り込む。** サーバー、API、CLI、Web UI、設定、
  セットアップ等の変更を機能単位で列挙し、移植漏れを確認する。
  ファイル名で分類せず、C++ の generate にある CLI/API 機能も対象にする。
  推論実装に依存する機能は、この fork の計算経路へ意味を保って適合させる。
- **推論実装は部品ごとに選ぶ。** prefill/decode、CPU/GPU、量子化形式、
  単一/複数 token、MoE の GU/Down、GEMM、Attention、転送、配置、scheduler 等を分ける。
  上流の方が優れる部品を取り込み、この fork の方が優れる部品は維持する。
  エンジン全体が速いだけでは全置換せず、prefill の改善で decode の退行を正当化しない。
  prefill と decode は原則として独立した処理経路・kernel・配置・schedule を選ぶ。
  同じ実装を選んだ場合も偶然の一致として扱い、一方の採否を他方へ適用しない。
  共通処理は、独立経路より速いことを同条件の実測で確認した範囲だけで採用する。
  既存の共通経路やphase分岐があること自体を、共通化の性能根拠にしない。
- 必須の不具合修正と API 機能を、任意の高速化と切り離す。
  必須修正が遅くなる場合は機能と修正の意味を保った適合を試し、差と制限を報告する。
- ばらつき、単体 kernel の改善、別モデル・別設定の速さだけでは採用を確定しない。
  同等なら既存の検証済み部品を維持し、未評価の候補は未評価として残す。

## 毎回の進め方

1. 作業対象の AGENTS.md、計測・ログ保持方針と最新のコミット済みレポートを読む。
   ユーザーの既存指示を引き継ぐ。[更新と機能対応](references/integration.md) を読む。
   ghq と worktree による `git-workflow` を使い、dirty なユーザー作業を変更しない。
1. 設定済み remote と本家の実際の更新先を確認し、fetch した SHA/tag を固定する。
   表示バージョンだけで統合状態を判断しない。開始点、対象点、既存の最良構成を記録する。
   fork の採用済み高速化と実際の呼び出し経路も一覧にし、source の入口変更で失わせない。
   主ブランチの表示版や直近のcommitだけを最良構成としない。同一セッションの過去測定と
   元のcompiled source・設定を照合し、主へ未統合のNiko由来の速い作業系統も比較対象にする。
   古い主ブランチを再開して「元の最適化を保持」と報告せず、履歴保存mergeと実コードの
   統合を実source resolver・dispatchで区別する。Xe評価前の測定をXe由来と分類しない。
1. 差分の全機能を対応表にし、必須機能、必須修正、任意の推論部品と依存関係を分ける。
   本家由来の変更は本家のsource/commitを起点に評価・移植する。
   同じ機能がXeStrataにあることを、そのコードを使う理由にしない。
1. **改変していない上流単体を実環境で測る。** ローカルパッチを混ぜない。
   箱出しに加えて、この環境で設定を調整した上流も評価する。
   [計測と部品別採否](references/evaluation.md) を読む。
1. 必須機能を移植し、任意の推論変更は部品ごとの正しさと性能で採否を決める。
   可能なら役割や形状ごとの dispatch で優れた実装を選び、改善を失う一括置換を避ける。
1. 統合後の機能、数値、対象の長文実行と速度を確認する。退行が出たら既存の最良構成と
   同条件で再測定し、設定差を確認して部品別に切り分ける。過去の速い測定を棚上げしない。
1. コマンド、全個別結果、対象 SHA、採否・保留理由、機能対応表と次の評価を Git に残し、
   作業境界で commit/push する。既存承認の範囲で進み、公開・サービス停止等の新しい権限を
   このスキルから推測しない。未完了項目を成功や統合済みに変えない。

XeStrataは独立した実行環境での性能比較に限定し、source採用候補にしない。
測定する場合も本家の全機能対応表とは分け、revision・設定・個別結果を記録する。
他の参考先でも更新を本家との同期に数えない。

## 並行調査と反復

このユーザーの Strata 作業では、読み取り専用の調査を複数の `gpt-6-luna` に分ける。
後の依頼で代理作業が禁止されている場合は、その制約を優先する。
例えば一方は機能差分と依存関係、他方は性能履歴と個別 kernel の候補を調べる。
次の更新・評価ラウンドでも反復し、過去レポートのディレクトリと最新 registry を必ず渡す。
各調査はレポートをファイルに保存し、Main は返答まで途中介入せず自分の作業を続ける。
実装は Main が行い、調査エージェントに実装させない。
2026-10-16の利用量に関する指示に従い、`gpt-6.1-sol` のサブエージェントは新規起動しない。
既に実行中のものには介入せず完了を待つ。調査用Lunaとレビュー用Luna-maxの指定は維持する。
ビルド・テスト・GPU・profiler実行は Main が直列に管理する。
同時に GPU 測定、ビルド、テスト、ログ cleanup を走らせない。
モデルや代理作業の可否が環境と異なる場合は、その制約を示して代替を判断する。

## 完了の報告

対象となった本家の SHA/tag、上流単体と統合後の実設定・個別測定、
全機能の対応状況、部品ごとの採用・維持・保留、prefill/decodeの退行有無を示す。
「最新版を取り込んだ」だけの報告や、サーバーテストだけによる推論性能の合格判定はしない。
参考forkを調べた場合はその SHA/tag と用途を示す。XeStrataには性能参考のみと明記する。
不明点は必要な情報を調べてから質問し、独立して進められる評価を止めない。
