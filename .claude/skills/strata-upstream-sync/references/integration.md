# 更新と機能対応

## 対象の確認

この Strata 作業で評価する起点は本家 `Niko1221/Strata` と
`MistVVK/XeStrata`、統合先はユーザーの fork である。毎回 remote、作業ブランチ、
採用済みの source と対象 SHA を実際に確認する。過去のパスや版を現在値と決めつけない。
初回取得は ghq、更新は既存 clone の fetch、各評価と統合は専用 worktree で行う。
既存の checkout を切り替えない。上流の評価用 tree はパッチなしで維持する。

「前回確認した更新」と「機能を統合した更新」と「推論部品を採用した更新」は別である。
それぞれ元 SHA と部品の由来を記録する。最新 tag を書き換えて古い実装を最新版と呼ばない。
更新範囲は commit 差分に加え、両端の tree 差分と依存変更でも確認する。
評価中に次の更新が来たらまず現在の結果を閉じ、その後に新しい対象を追加する。
更新発見だけで進行中の比較をやり直さない。

## 既存の速い経路

fork の採用済み最適化について source/設定/呼び出し元と元測定を一覧にする。
新しい source 系統や entrypoint に切り替える場合、以前の部品が実際に呼ばれるか確認する。
例えば layer-major の重み再利用と per-chunk scratch alias は別の仕組みである。
似た名前の設定、新しい kernel や上流全体の性能で、既存の最適化を残したことにしない。
維持、同等実装へ移植、個別評価で置換、未移植のどれかを明記し、黙って失わせない。

## 全機能の対応表

変更した行やファイルだけでなく、ユーザーが使う機能を単位にする。
最低限、由来 SHA、機能/部品、必須性、依存、移植先、検証、状態と理由を記録する。
状態には取り込み済み、既存同等機能を確認、対象外、評価待ち、保留を区別する。
対象外には理由を付け、必須機能の未実装をその状態へ隠さない。

確認する面は server/API、streaming、キャンセルと復帰、複数要求と replica、
CLI オプションと help、設定と defaults、Web UI、setup/installer、対応形式と互換性である。
これは列挙の起点であり、差分に現れるその他の非推論機能も全て対象に含める。
テスト・文書が更新された機能や、別 commit に分離された後続修正も追う。
ユーザーの指示では HIP/CUDA の推論移植と性能評価は対象外。
共通の CLI/API 機能を、HIP/CUDA ファイルに関連するというだけで落とさない。

必須機能が upstream の新しい engine interface を呼ぶ場合、意味とエラー契約を理解して
fork の既存 engine に適合させる。必須機能のために不要な kernel 一式を黙って置換しない。
既存実装で同じ機能を満たせると判断するには、振る舞いと対応テストの証拠を残す。
サーバー、CLI、setup の機能テストと、GPU の正しさ・速度検証を分けて記録する。

## 推論部品の対応表

部品ごとに upstream/fork の実装 SHA、適用量子化、形状、device capabilities、
prefill/decode の役割、精度、同期と寿命、個別性能、モデルへの影響を記録する。
例えば MoE IQ3 の GU が速くても、IQ3 の Down や他の形式まで採用したことにしない。
同じ kernel 名でも NT=1 と複数 token、AVX2 と AVX-512、XMX 有無で比較結果を分ける。
この環境用の compiler flags を使う場合、両側の条件を揃えて特化範囲を記録する。

上流全体が遅くても、一部が優れていればその部品を取り込む。
上流全体が速くても、一部で fork が優れていればその部品を維持する。
dispatch の条件を能力・形状・役割から決め、未確認の経路には検証済みの fallback を残す。
同じ共通実装を prefill と decode に一括適用するしかない場合は、その制約と両方の結果を
示し、先に分離可能性を調べる。速度の合計や一方の利益で他方の退行を隠さない。

必須の境界・数値・回復修正が kernel と混ざる場合、その修正を失う単純 revert をしない。
修正を残して既存の速い計算に適合させる案を検討する。
適合不能で判断に必要なユーザー方針が欠ける場合は、具体的な変更と結果を示して質問する。

## 記録と次の反復

再開点は commit されたレポートで管理し、別の progress backup を増やさない。
調査 registry には新しい報告と訂正の由来を追加し、旧報告を上書きしない。
実装エージェントの報告は実装案であり、Main のテスト結果と混同しない。
取り込み後に remote を再確認し、追加更新があれば次の差分と対象を記録する。
新しい更新がない場合も、保留の部品評価や未完了の機能移植を既存結果から継続する。
